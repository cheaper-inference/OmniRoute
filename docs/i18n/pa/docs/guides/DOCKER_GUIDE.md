## ਤੇਜ਼ ਦੌੜ

> **ਇੱਕ ਕਮਾਂਡ ਵਿੱਚ ਸਵੈ-ਹੋਸਟ?** [ਸਵੈ-ਹੋਸਟ ਗਾਈਡ](../getting-started/SELF_HOST_GUIDE.md) — `docker compose -f docker-compose.selfhost.yml up -d` (ਪ੍ਰਕਾਸ਼ਿਤ ਚਿੱਤਰ + Redis, ਲੂਪਬੈਕ-ਸਿਰਫ਼, ਕੋਈ ਪ੍ਰੋਫਾਈਲ ਵਿਕਲਪ ਨਹੀਂ) ਦੇਖੋ। ਹੇਠਾਂ ਦਿੱਤੀ ਤਤਕਾਲ ਰਨ ਉਹਨਾਂ ਉਪਭੋਗਤਾਵਾਂ ਲਈ ਸਿੰਗਲ-ਕੰਟੇਨਰ ਮਾਰਗ ਹੈ ਜੋ ਪਹਿਲਾਂ ਹੀ ਕਿਤੇ ਹੋਰ Redis ਚਲਾ ਰਹੇ ਹਨ।

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  cheaperinference/omniroute:latest
```

## ਵਾਤਾਵਰਣ ਫਾਈਲ ਦੇ ਨਾਲ

```bash
# Copy and edit .env first

  --name omniroute \

  --stop-timeout 40 \
  --env-file .env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  cheaperinference/omniroute:latest
```

## Docker Compose

```bash
# ਬੇਸ ਪ੍ਰੋਫ਼ਾਈਲ (ਕੋਈ CLI ਟੂਲ ਨਹੀਂ)
docker compose --profile base up -d

# CLI ਪ੍ਰੋਫ਼ਾਈਲ (Claude Code, Codex, OpenClaw ਬਿਲਟ-ਇਨ)
docker compose --profile cli up -d

# ਹੋਸਟ ਪ੍ਰੋਫ਼ਾਈਲ (ਮੁੱਖ ਤੌਰ 'ਤੇ Linux ਲਈ; ਹੋਸਟ CLI ਬਾਈਨਰੀਆਂ ਨੂੰ ਸਿਰਫ਼-ਪੜ੍ਹਨਯੋਗ ਢੰਗ ਨਾਲ ਮਾਊਂਟ ਕਰਦਾ ਹੈ)
docker compose --profile host up -d

# ਵੈੱਬ ਪ੍ਰੋਫ਼ਾਈਲ (ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI ਸਾਈਡਕਾਰ ਨੂੰ ਜੋੜੋ
docker compose --profile cli --profile cliproxyapi up -d
```

## ਉਪਲਬਧ ਪ੍ਰੋਫ਼ਾਈਲ

OmniRoute ਮੁੱਖ ਡਿਪਲੌਇਮੈਂਟ ਰੂਪਾਂ ਲਈ Compose ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਨਾਲ ਆਉਂਦਾ ਹੈ। ਆਪਣੇ ਇਨਵਾਇਰਨਮੈਂਟ ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਪ੍ਰੋਫ਼ਾਈਲ ਚੁਣੋ।

| ਪ੍ਰੋਫ਼ਾਈਲ     | ਸਰਵਿਸ            | ਕਦੋਂ ਵਰਤਣਾ ਹੈ                                                                                                                                        | ਕਮਾਂਡ                                        |
| ------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (ਮੂਲ)  | `omniroute-base` | ਹੈੱਡਲੈੱਸ ਸਰਵਰ / ਘੱਟੋ-ਘੱਟ ਰਨਟਾਈਮ, ਕੋਈ ਪ੍ਰਦਾਤਾ CLI ਬੰਡਲ ਨਹੀਂ                                                                                           | `docker compose --profile base up -d`        |
| `cli`         | `omniroute-cli`  | `omniroute providers/setup/doctor` ਅਤੇ ਬੰਡਲ ਕੀਤੇ CLI (Codex, Claude Code, Droid, OpenClaw) ਨੂੰ ਕਾਲ ਕਰਨ ਵਾਲੇ ਏਜੰਟਿਕ ਵਰਕਫ਼ਲੋ                           | `docker compose --profile cli up -d`         |
| `host`        | `omniroute-host` | ਉਹ Linux ਹੋਸਟ ਜੋ `~/.local/bin`, `~/.codex`, `~/.claude` ਆਦਿ ਨੂੰ ਸਿਰਫ਼-ਪੜ੍ਹਨਯੋਗ ਢੰਗ ਨਾਲ ਮਾਊਂਟ ਕਰਕੇ ਹੋਸਟ CLI ਤੱਕ `network_mode`-ਵਰਗੀ ਪਹੁੰਚ ਚਾਹੁੰਦੇ ਹਨ | `docker compose --profile host up -d`        |
| `cliproxyapi` | `cliproxyapi`    | ਅੱਪਸਟ੍ਰੀਮ CLI ਪ੍ਰੌਕਸੀ ਲਈ ਪੋਰਟ `8317` ਉੱਤੇ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) ਸਾਈਡਕਾਰ ਚਲਾਓ                                   | `docker compose --profile cliproxyapi up -d` |
| `web`         | `omniroute-web`  | ਉਹ ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾ ਜਿਨ੍ਹਾਂ ਨੂੰ ਬ੍ਰਾਊਜ਼ਰ ਚਾਹੀਦਾ ਹੈ: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ਬਣਾਉਂਦਾ ਹੈ, Chromium ਸ਼ਾਮਲ ਹੈ)    | `docker compose --profile web up -d`         |

> ਕਈ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਨੂੰ ਇਕੱਠੇ ਵਰਤਿਆ ਜਾ ਸਕਦਾ ਹੈ: `docker compose --profile cli --profile cliproxyapi up -d`।

## ਜਦੋਂ OmniRoute Docker ਵਿੱਚ ਚੱਲਦਾ ਹੋਵੇ ਤਾਂ ਹੋਸਟ CLI ਟੂਲਾਂ ਦੀ ਸੰਰਚਨਾ ਕਰਨੀ

`omniroute setup-codex`, `setup-claude`, `config set <tool>` ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਦਾ
**ਸੰਰਚਨਾ ਸੰਭਾਲੋ** ਬਟਨ ਸਾਰੇ `~/.codex/*.config.toml` ਵਰਗੀਆਂ ਫ਼ਾਈਲਾਂ ਲਿਖਦੇ ਹਨ। ਉਹ ਪਾਥ
ਸਿਰਫ਼ ਉਸ ਮਸ਼ੀਨ ਉੱਤੇ ਅਰਥ ਰੱਖਦੇ ਹਨ ਜਿੱਥੇ CLI ਅਸਲ ਵਿੱਚ ਚੱਲਦਾ ਹੈ। ਇਨ੍ਹਾਂ ਨੂੰ
ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਚਲਾਉਣ ਨਾਲ ਲਿਖਤ ਕੰਟੇਨਰ ਦੇ ਆਪਣੇ ਹੋਮ (`/home/node` —
ਇਮੇਜ `USER node` ਵਜੋਂ ਚੱਲਦਾ ਹੈ) ਵਿੱਚ ਜਾਂਦੀ ਹੈ, ਜਿੱਥੋਂ ਕੋਈ ਵੀ ਹੋਸਟ CLI ਇਸਨੂੰ ਕਦੇ ਨਹੀਂ ਪੜ੍ਹੇਗਾ ਅਤੇ ਕੰਟੇਨਰ
ਮੁੜ ਬਣਾਏ ਜਾਣ ਦੇ ਪਲ ਹੀ ਇਹ ਮਿਟ ਜਾਂਦੀ ਹੈ।

OmniRoute ਇਸਦਾ ਪਤਾ ਲਗਾਉਂਦਾ ਹੈ ਅਤੇ ਅਜਿਹੀ ਸਫਲਤਾ ਰਿਪੋਰਟ ਕਰਨ ਦੀ ਬਜਾਏ, ਜਿਸਨੂੰ ਤੁਸੀਂ ਵਰਤ ਨਹੀਂ ਸਕਦੇ,
ਹਦਾਇਤਾਂ ਦੇ ਨਾਲ ਲਿਖਣ ਤੋਂ ਇਨਕਾਰ ਕਰਦਾ ਹੈ: CLI `2` ਨਾਲ ਬੰਦ ਹੁੰਦਾ ਹੈ ਅਤੇ API `422`
ਦੇ ਨਾਲ `containerEphemeralTarget: true` ਵਾਪਸ ਕਰਦਾ ਹੈ।

### ਸਿਫ਼ਾਰਸ਼ੀ: CLI ਨੂੰ ਹੋਸਟ ਉੱਤੇ ਅਤੇ OmniRoute ਨੂੰ Docker ਵਿੱਚ ਚਲਾਓ

ਕੰਟੇਨਰ API ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ; CLI ਤੁਹਾਡੇ ਹੋਸਟ ਟੂਲਾਂ ਦੀ ਸੰਰਚਨਾ ਕਰਦਾ ਹੈ।

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLI ਨੂੰ ਕੰਟੇਨਰ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਵਾਓ
omniroute setup-codex                      # ਤੁਹਾਡੇ ਹੋਸਟ ਉੱਤੇ ਅਸਲ ~/.codex ਲਿਖਦਾ ਹੈ
```

ਜਦੋਂ Codex, Claude Code, Cursor ਜਾਂ ਇਸੇ ਤਰ੍ਹਾਂ ਦੇ ਟੂਲ ਤੁਹਾਡੇ
ਲੈਪਟਾਪ ਉੱਤੇ ਚੱਲਦੇ ਹਨ ਤਾਂ ਇਹ ਸਹੀ ਚੋਣ ਹੈ — ਅਤੇ ਆਮ ਤੌਰ ਉੱਤੇ ਸੈੱਟਅੱਪ ਵੀ ਇਹੀ ਹੁੰਦਾ ਹੈ।

### ਵਿਕਲਪ: ਹੋਸਟ ਸੰਰਚਨਾ ਡਾਇਰੈਕਟਰੀਆਂ ਨੂੰ bind-mount ਕਰੋ (`host` ਪ੍ਰੋਫ਼ਾਈਲ)

ਜੇ ਤੁਸੀਂ ਚਾਹੁੰਦੇ ਹੋ ਕਿ ਕੰਟੇਨਰ ਖੁਦ ਤੁਹਾਡੀ ਹੋਸਟ ਸੰਰਚਨਾ ਲਿਖੇ, ਤਾਂ
ਡਾਇਰੈਕਟਰੀਆਂ ਨੂੰ ਅੰਦਰ ਮਾਊਂਟ ਕਰੋ ਅਤੇ `CLI_CONFIG_HOME` ਨੂੰ ਮਾਊਂਟ ਰੂਟ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਵਾਓ। `host` ਪ੍ਰੋਫ਼ਾਈਲ
ਪਹਿਲਾਂ ਹੀ ਇਹ ਕਰਦਾ ਹੈ:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

bind mount ਹੀ ਪਾਥ ਨੂੰ ਭਰੋਸੇਯੋਗ ਬਣਾਉਂਦਾ ਹੈ: OmniRoute
`/proc/self/mountinfo` ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ ਮਾਊਂਟ ਕੀਤੇ ਪਾਥਾਂ (ਅਤੇ ਉਹਨਾਂ ਡਾਇਰੈਕਟਰੀਆਂ,
ਜਿਨ੍ਹਾਂ ਦੇ ਚਾਈਲਡ ਮਾਊਂਟ ਹਨ, ਜੋ ਉੱਪਰ ਦਿੱਤੇ `/host-home` ਦੇ ਰੂਪ ਨਾਲ ਬਿਲਕੁਲ ਮੇਲ ਖਾਂਦਾ ਹੈ) ਉੱਤੇ ਲਿਖਣ ਦੀ ਇਜਾਜ਼ਤ ਦਿੰਦਾ ਹੈ, ਜਦਕਿ
ਮਾਊਂਟ ਨਾ ਕੀਤੇ ਪਾਥਾਂ ਲਈ ਅਜੇ ਵੀ ਇਨਕਾਰ ਕਰਦਾ ਹੈ।

### ਬਚਾਅ ਦਾ ਰਸਤਾ: ਕੰਟੇਨਰ ਦੇ ਆਪਣੇ CLIs ਦੀ ਸੰਰਚਨਾ ਕਰੋ (ਸੰਜਮ ਨਾਲ ਵਰਤੋ)

ਜਦੋਂ CLIs ਸੱਚਮੁੱਚ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਹੀ ਮੌਜੂਦ ਹੋਣ (`cli` ਪ੍ਰੋਫ਼ਾਈਲ), ਤਾਂ ਇਹ ਲਿਖਤ
ਜਾਣਬੁੱਝ ਕੇ ਕੀਤੀ ਜਾਂਦੀ ਹੈ। ਕਿਸੇ ਵੀ `setup-*` ਕਮਾਂਡ ਨੂੰ `--allow-container-write` ਦਿਓ, ਜਾਂ ਸਰਵਰ ਲਈ
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ਸੈੱਟ ਕਰੋ। ਲਿਖਤ ਇਸ ਚੇਤਾਵਨੀ ਨਾਲ ਅੱਗੇ ਵਧਦੀ ਹੈ
ਕਿ ਇਹ ਕੰਟੇਨਰ ਤੋਂ ਬਾਅਦ ਕਾਇਮ ਨਹੀਂ ਰਹੇਗੀ।

> **ਸੁਰੱਖਿਆ ਚੇਤਾਵਨੀ — `cli` ਪ੍ਰੋਫ਼ਾਈਲ + `docker.sock` ਮਾਊਂਟ।**
> `cli` ਪ੍ਰੋਫ਼ਾਈਲ `/var/run/docker.sock` ਨੂੰ bind-mount ਕਰਦਾ ਹੈ ਤਾਂ ਜੋ ਕੰਟੇਨਰ ਅੰਦਰਲਾ
> ਆਟੋ-ਅੱਪਡੇਟਰ ਹੋਸਟ ਡੀਮਨ ਤੋਂ ਸਟੈਕ ਮੁੜ ਬਣਾ ਸਕੇ
> (`src/lib/system/autoUpdate.ts` ਉਸ ਸਾਕਟ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ ਅਤੇ ਜਦੋਂ ਇਹ
> ਮੌਜੂਦ ਨਾ ਹੋਵੇ ਤਾਂ Docker ਪਾਥ ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ)। ਉਹ ਸਾਕਟ **ਹੋਸਟ-root ਭਰੋਸੇ ਦੀ
> ਸੀਮਾ** ਹੈ: ਜੋ ਵੀ ਇਸ ਤੱਕ ਪਹੁੰਚ ਸਕਦਾ ਹੈ, ਉਹ ਹੋਸਟ Docker ਡੀਮਨ ਨੂੰ
> root ਵਜੋਂ ਚਲਾਉਂਦਾ ਹੈ — ਉਹ ਹੋਸਟ ਉੱਤੇ ਕਿਸੇ ਵੀ ਕੰਟੇਨਰ ਨੂੰ ਬਣਾ, ਜਾਂਚ, ਰੋਕ ਅਤੇ ਹਟਾ ਸਕਦਾ ਹੈ।
> ਪ੍ਰਭਾਵ:
>
> 1. **`cli` ਪ੍ਰੋਫ਼ਾਈਲ ਦਾ ਪੋਰਟ ਕਦੇ ਵੀ ਨੈੱਟਵਰਕ ਉੱਤੇ ਉਪਲਬਧ ਨਾ ਕਰੋ।** ਇਸਨੂੰ
>    `127.0.0.1` ਉੱਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰੋ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN ਤੋਂ ਪਹੁੰਚਯੋਗ `cli` ਪ੍ਰੋਫ਼ਾਈਲ ਕਿਸੇ ਵੀ ਡੈਸ਼ਬੋਰਡ-ਪੱਧਰੀ RCE ਨੂੰ
>    ਪੂਰੇ ਹੋਸਟ ਦੇ ਸਮਝੌਤੇ ਵਿੱਚ ਬਦਲ ਦਿੰਦਾ ਹੈ।
> 2. **`cli` ਪ੍ਰੋਫ਼ਾਈਲ ਵਿੱਚ ਕੋਈ ਵਾਧੂ ਹੋਸਟ ਡਾਇਰੈਕਟਰੀ bind ਨਾ ਕਰੋ।**
>    Docker ਸਾਕਟ ਦੇ ਨਾਲ ਕੋਈ ਵੀ ਹੋਰ ਮਾਊਂਟ ਕੰਟੇਨਰ ਨੂੰ ਤੁਹਾਡੇ ਫ਼ਾਈਲ-ਸਿਸਟਮ
>    ਅਤੇ ਹੋਸਟ ਸੰਰਚਨਾ ਲਈ ਪੂਰੀ ਪੜ੍ਹਨ/ਲਿਖਣ ਪਹੁੰਚ ਦਿੰਦਾ ਹੈ। ਜੇ ਕਿਸੇ ਟੂਲ ਨੂੰ
>    ਪ੍ਰੋਜੈਕਟ ਵੇਖਣ ਦੀ ਲੋੜ ਹੈ, ਤਾਂ ਉਸਨੂੰ CLI ਬਾਈਨਰੀ ਨਾਲ ਸਥਾਨਕ ਤੌਰ ਉੱਤੇ ਚਲਾਓ — ਇਸਨੂੰ
>    `cli` ਕੰਟੇਨਰ ਵਿੱਚ ਮਾਊਂਟ ਨਾ ਕਰੋ।
>
> ਜੇ ਤੁਹਾਨੂੰ ਕੰਟੇਨਰ ਅੰਦਰ ਆਟੋ-ਅੱਪਡੇਟ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ, ਤਾਂ `cli` ਪ੍ਰੋਫ਼ਾਈਲ ਨੂੰ ਬੰਦ ਰੱਖੋ
> (`COMPOSE_PROFILES=core,redis` ਜਾਂ ਇਸ ਤੋਂ ਛੋਟਾ)। ਹੋਰ ਪ੍ਰੋਫ਼ਾਈਲ
> Docker ਸਾਕਟ ਨੂੰ ਮਾਊਂਟ ਨਹੀਂ ਕਰਦੇ।
>
> MITM ਨਾਲ ਸੰਬੰਧਿਤ ਖ਼ਤਰਾ ਮਾਡਲ ਲਈ `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs` ਵਿੱਚ ਕੰਪਾਇਲ ਨਹੀਂ ਕੀਤਾ ਗਿਆ) ਵੇਖੋ,
> ਅਤੇ `codex`/`claude-code`/`droid`/`openclaw` ਬਾਈਨਰੀ ਦੇ ਸਰੋਤ ਦੀ ਲੜੀ ਲਈ
> `docs/security/SUPPLY_CHAIN.md` ਵੇਖੋ।

## Redis ਸਾਈਡਕਾਰ

OmniRoute ਡਿਸਟ੍ਰਿਬਿਊਟਡ ਰੇਟ ਲਿਮਿਟਰ ਅਤੇ ਸਾਂਝੇ ਕੈਸ਼ ਲਈ Redis 'ਤੇ ਨਿਰਭਰ ਕਰਦਾ ਹੈ। `redis` ਸਰਵਿਸ `docker-compose.yml` ਵਿੱਚ **ਹਮੇਸ਼ਾ ਪਰਿਭਾਸ਼ਿਤ** ਹੁੰਦੀ ਹੈ (ਇਸ ਉੱਤੇ ਕੋਈ ਪ੍ਰੋਫ਼ਾਈਲ ਗੇਟ ਨਹੀਂ ਹੈ) ਅਤੇ ਕਿਸੇ ਵੀ ਹੋਰ ਪ੍ਰੋਫ਼ਾਈਲ ਦੇ ਨਾਲ ਸ਼ੁਰੂ ਹੁੰਦੀ ਹੈ।

| ਵੇਰਵਾ                | ਮੁੱਲ                                   |
| -------------------- | -------------------------------------- |
| ਇਮੇਜ                 | `redis:7-alpine`                       |
| ਕੰਟੇਨਰ ਦਾ ਨਾਮ        | `omniroute-redis`                      |
| ਅੰਦਰੂਨੀ ਪੋਰਟ         | `6379`                                 |
| ਹੋਸਟ ਪੋਰਟ (ਓਵਰਰਾਈਡ)  | `REDIS_PORT` (ਡਿਫਾਲਟ `6379`)           |
| ਹੋਸਟ ਬਾਈਂਡ (ਓਵਰਰਾਈਡ) | `REDIS_BIND_HOST` (ਡਿਫਾਲਟ `127.0.0.1`) |
| ਵਾਲਿਊਮ               | `omniroute-redis-data` → `/data`       |
| ਹੈਲਥਚੈੱਕ             | `redis-cli ping` (10s ਦਾ ਅੰਤਰਾਲ)       |

ਸੰਬੰਧਿਤ ਵਾਤਾਵਰਣ ਵੇਰੀਏਬਲ:

- `REDIS_URL` — ਐਪ ਵਿੱਚ ਇੰਜੈਕਟ ਕੀਤੀ ਕਨੈਕਸ਼ਨ ਸਟ੍ਰਿੰਗ (ਡਿਫਾਲਟ ਰੂਪ ਵਿੱਚ `redis://redis:6379`)।
- `REDIS_PORT` — Redis ਕੰਟੇਨਰ ਲਈ ਹੋਸਟ-ਸਾਈਡ ਪੋਰਟ ਮੈਪਿੰਗ।
- `REDIS_BIND_HOST` — ਉਹ ਹੋਸਟ ਇੰਟਰਫੇਸ ਜਿਸ 'ਤੇ ਪੋਰਟ ਪ੍ਰਕਾਸ਼ਿਤ ਕੀਤੀ ਜਾਂਦੀ ਹੈ। ਡਿਫਾਲਟ `127.0.0.1` ਹੈ।

> **ਡਿਫਾਲਟ ਰੂਪ ਵਿੱਚ ਲੂਪਬੈਕ ਕਿਉਂ:** ਸਾਈਡਕਾਰ `requirepass` ਤੋਂ ਬਿਨਾਂ ਚੱਲਦਾ ਹੈ, ਅਤੇ ਐਪ
> ਕੰਟੇਨਰ ਕੰਪੋਜ਼ ਨੈੱਟਵਰਕ (`redis:6379`) ਰਾਹੀਂ ਇਸ ਤੱਕ ਪਹੁੰਚਦੇ ਹਨ — ਪ੍ਰਕਾਸ਼ਿਤ ਪੋਰਟ
> ਸਿਰਫ਼ ਹੋਸਟ-ਸਾਈਡ ਟੂਲਿੰਗ (`redis-cli`, ਇੱਕ ਲੋਕਲ `npm run dev`) ਲਈ ਹੈ। ਇਸਨੂੰ
> `0.0.0.0` 'ਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਨ ਨਾਲ ਬਿਨਾਂ ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲਾ Redis ਤੁਹਾਡੇ LAN ਦੇ ਹਰੇਕ ਹੋਸਟ ਲਈ ਉਪਲਬਧ ਹੋ ਜਾਵੇਗਾ। ਜੇ ਤੁਸੀਂ
> `REDIS_BIND_HOST=0.0.0.0` ਸੈੱਟ ਕਰਦੇ ਹੋ, ਤਾਂ ਸਰਵਿਸ ਦੇ `command:` ਵਿੱਚ `--requirepass` ਵੀ ਸ਼ਾਮਲ ਕਰੋ।

**Redis ਨੂੰ ਅਸਮਰੱਥ ਕਰਨਾ** ਸਿਫ਼ਾਰਸ਼ੀ ਨਹੀਂ ਹੈ (ਰੇਟ ਲਿਮਿਟਰ ਇਨ-ਮੈਮੋਰੀ ਫਾਲਬੈਕ 'ਤੇ ਆ ਜਾਵੇਗਾ)। ਜੇ ਇਹ ਲਾਜ਼ਮੀ ਹੋਵੇ, ਤਾਂ ਜਾਂ `docker-compose.yml` ਵਿੱਚੋਂ `redis:` ਸਰਵਿਸ ਬਲਾਕ ਹਟਾਓ/ਕਮੈਂਟ ਕਰੋ ਜਾਂ ਇਸਨੂੰ ਸਿਫ਼ਰ ਤੱਕ ਸਕੇਲ ਕਰੋ:

```bash
docker compose up -d --scale redis=0
```

## ਪ੍ਰੋਡਕਸ਼ਨ ਕੰਪੋਜ਼

ਡਿਵੈਲਪਮੈਂਟ ਦੇ ਨਾਲ-ਨਾਲ ਚੱਲਣ ਵਾਲੇ ਇੱਕ ਅਲੱਗ ਪ੍ਰੋਡਕਸ਼ਨ ਸਨੈਪਸ਼ਾਟ ਲਈ `docker-compose.prod.yml` ਵਰਤੋ।

| ਵੇਰਵਾ                | ਮੁੱਲ                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------- |
| ਫ਼ਾਈਲ                | `docker-compose.prod.yml`                                                                   |
| ਡਿਫਾਲਟ ਡੈਸ਼ਬੋਰਡ ਪੋਰਟ | `PROD_DASHBOARD_PORT=20130` (ਅੰਦਰੂਨੀ `${DASHBOARD_PORT:-20128}` ਨਾਲ ਮੈਪ ਕੀਤਾ)               |
| ਡਿਫਾਲਟ API ਪੋਰਟ      | `PROD_API_PORT=20131`                                                                       |
| ਇਮੇਜ                 | `omniroute:prod` (`runner-cli` ਟਾਰਗੇਟ ਤੋਂ ਬਿਲਡ ਕੀਤਾ)                                        |
| Redis ਕੰਟੇਨਰ         | `omniroute-redis-prod` (`redis:8.6.2`, ਸਮਰਪਿਤ `redis-prod-data` ਵਾਲਿਊਮ)                     |
| ਡਾਟਾ ਵਾਲਿਊਮ          | `omniroute-prod-data` (ਨਾਮਿਤ, ਮੁੜ ਬਿਲਡ ਕਰਨ ਦੌਰਾਨ ਵੀ ਕਾਇਮ ਰਹਿੰਦਾ ਹੈ)                         |
| ਹੈਲਥਚੈੱਕ             | `node healthcheck.mjs` + `redis-cli ping`, ਜਿਸ ਵਿੱਚ `depends_on` Redis ਦੀ ਸਿਹਤ 'ਤੇ ਨਿਰਭਰ ਹੈ |

ਵਰਤਣ ਦਾ ਤਰੀਕਾ:

```bash
# ਪ੍ਰੋਡਕਸ਼ਨ ਸਟੈਕ ਨੂੰ ਬਿਲਡ ਅਤੇ ਸ਼ੁਰੂ ਕਰੋ
docker compose -f docker-compose.prod.yml up -d --build

# ਲੌਗਾਂ ਨੂੰ ਸਟ੍ਰੀਮ ਕਰੋ
docker compose -f docker-compose.prod.yml logs -f

# ਬੰਦ ਕਰੋ (ਵਾਲਿਊਮ ਕਾਇਮ ਰੱਖੋ)
docker compose -f docker-compose.prod.yml down
```

ਪ੍ਰੋਡ ਸਟੈਕ ਡਿਵੈਲਪਮੈਂਟ ਕੰਪੋਜ਼ ਦੇ ਸਮਾਂਤਰ ਚੱਲਦਾ ਹੈ (ਕੰਟੇਨਰਾਂ ਦੇ ਨਾਮ, ਪੋਰਟ ਅਤੇ ਵਾਲਿਊਮ ਵੱਖਰੇ ਹਨ), ਇਸ ਲਈ ਪ੍ਰੋਡਕਸ਼ਨ ਨੂੰ ਚਾਲੂ ਰੱਖਦੇ ਹੋਏ ਤੁਸੀਂ ਲੋਕਲ ਤੌਰ 'ਤੇ ਕੰਮ ਕਰਨਾ ਜਾਰੀ ਰੱਖ ਸਕਦੇ ਹੋ।

## ਡੌਕਰਫਾਈਲ ਪੜਾਅ

ਰਿਪੋਜ਼ਟਰੀ ਇੱਕ ਮਲਟੀ-ਸਟੇਜ ਡੌਕਰਫਾਈਲ (`Dockerfile`) ਭੇਜਦੀ ਹੈ। ਚਾਰ ਪੜਾਵਾਂ ਦਾ ਸਾਹਮਣਾ ਕੀਤਾ ਜਾਂਦਾ ਹੈ; ਆਪਣੇ ਵਰਤੋਂ ਦੇ ਕੇਸ ਲਈ ਸਹੀ `target` ਚੁਣੋ।

| ਸਟੇਜ          | ਬੇਸ ਚਿੱਤਰ             | ਮਕਸਦ                                                                                                                                                                                                                                                                                            |
| ------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | deps (`npm ci --legacy-peer-deps`) ਨੂੰ ਸਥਾਪਿਤ ਕਰਦਾ ਹੈ ਅਤੇ `npm run build` ਚਲਾਉਂਦਾ ਹੈ (Turbopack ਮੂਲ ਰੂਪ ਵਿੱਚ — ਹੇਠਾਂ ਬਿਲਡ-ਟਾਈਮ ਸਰੋਤ ਵੇਖੋ)                                                                                                                                                       |
| `runner-base` | `node:26-trixie-slim` | Next.js ਸਟੈਂਡਅਲੋਨ ਆਉਟਪੁੱਟ ਦੇ ਨਾਲ ਉਤਪਾਦਨ ਰਨਟਾਈਮ।** ਕੋਈ ਪ੍ਰਦਾਤਾ CLIs ਬੰਡਲ ਨਹੀਂ ਹੈ।**                                                                                                                                                                                                              |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` ਅਤੇ ਗਲੋਬਲ CLIs ਜੋੜਦਾ ਹੈ: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`.** ਏਜੰਟਿਕ ਵਰਕਫਲੋ ਲਈ ਇਸਨੂੰ ਚੁਣੋ।**                                                                                                                               |
| `runner-web`  | `runner-base`         | ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ Playwright + ਇੱਕ Chromium ਬ੍ਰਾਊਜ਼ਰ (`--with-deps`) ਜੋੜਦਾ ਹੈ: `gemini-web`, `claude-web`, `claude-turnstile`।** ਜਦੋਂ ਤੁਸੀਂ ਉਹਨਾਂ ਪ੍ਰਦਾਤਾਵਾਂ ਦੀ ਵਰਤੋਂ ਕਰਦੇ ਹੋ ਤਾਂ ਇਸਨੂੰ ਚੁਣੋ** — ਸਾਦਾ ਚਿੱਤਰ ਬਿਨਾਂ ਬੇਨਤੀ ਦੇ ਸਮੇਂ ਫੇਲ ਹੋ ਜਾਂਦਾ ਹੈ (ਰਿਲੀਜ਼ ਚੈਨਲਾਂ ਦੇ ਅਧੀਨ `-web` ਨੋਟ ਦੇਖੋ)। |

ਹੱਥੀਂ ਇੱਕ ਖਾਸ ਟੀਚਾ ਬਣਾਓ:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### ਬਿਲਡ-ਟਾਈਮ ਸਰੋਤ

ਤਿੰਨ ਬਿਲਡ ਆਰਗਸ ਨਿਯੰਤਰਿਤ ਕਰਦੇ ਹਨ ਕਿ `builder` ਪੜਾਅ ਦੀ ਕੀਮਤ ਕਿੰਨੀ ਹੈ। ਉਹ ਬਿਲਡ-ਟਾਈਮ ਹਨ ਸਿਰਫ — `OMNIROUTE_MEMORY_MB` (ਹੇਠਾਂ) ਇੱਕ ਵੱਖਰਾ, ਰਨਟਾਈਮ ਨੌਬ ਹੈ।

| ਆਰਗ ਬਣਾਓ                    | ਡਿਫਾਲਟ | ਪ੍ਰਭਾਵ                                                                                 |
| --------------------------- | ------ | -------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`    | `0` ਵੈੱਬਪੈਕ ਨਾਲ ਬਣਾਉਂਦਾ ਹੈ: ਲੋਅਰ ਪੀਕ ਮੈਮੋਰੀ, ਹੌਲੀ। `1` Turbopack ਦੀ ਚੋਣ ਕਰਦਾ ਹੈ।       |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144` | ਪੈਦਾ ਹੋਏ `next build` ਲਈ V8 ਹੀਪ ਸੀਲਿੰਗ (`--max-old-space-size`)।                       |
| `OMNIROUTE_BUILD_WORKERS`   | `2`    | ਫੀਡ `CIRCLE_NODE_TOTAL`; ਅਗਲਾ ਪੰਨਾ-ਡਾਟਾ ਇਕੱਠਾ ਕਰਨ ਲਈ `workers = N - 1` ਪ੍ਰਾਪਤ ਕਰਦਾ ਹੈ। |

`OMNIROUTE_BUILD_WORKERS` ਉਹ ਹੈ ਜੋ ਇੱਕ ਵੱਡੇ ਬਿਲਡਰ 'ਤੇ ਉਠਾਉਣਾ ਹੈ ਅਤੇ ਜਦੋਂ ਇੱਕ ਅੜਚਨ ਵਾਲੇ ਬਿਲਡ ਦੇ ਮਰਨ 'ਤੇ ਸ਼ੱਕ ਕਰਨਾ ਹੈ** ਬਾਅਦ** `✓ Compiled successfully` ਹਰੇਕ ਪੇਜ-ਡਾਟਾ ਵਰਕਰ ਦੀ ਆਪਣੀ ਪ੍ਰਕਿਰਿਆ ਹੈ, ਅਤੇ ਇਸੇ ਤਰ੍ਹਾਂ ਪੇਰੈਂਟ `next build` ਵੀ ਹੈ; ਇੱਕ ਲਾਈਵ VPS ਰੀਪ੍ਰੋਡਕਸ਼ਨ (ਇਸ਼ੂ #7518) ਨੇ ਹਰੇਕ ਪ੍ਰਕਿਰਿਆ ਦੇ ਪੀਕ RSS ~ 4.5 GB 'ਤੇ `NODE_OPTIONS` ਹੀਪ ਫਲੈਗ ਤੋਂ ਸੁਤੰਤਰ ਮਾਪਿਆ (Turbopack V8 ਹੀਪ ਦੇ ਬਾਹਰ native/Rust ਮੈਮੋਰੀ ਵਿੱਚ ਕੰਪਾਈਲ ਕਰਦਾ ਹੈ)। `2` (→ 1 ਵਰਕਰ, ਕੁੱਲ 2 ਪ੍ਰਕਿਰਿਆਵਾਂ) ਦਾ ਆਕਾਰ 16 GB / 4 vCPU GitHub-ਹੋਸਟਡ ਦੌੜਾਕਾਂ ਲਈ ਹੈ ਜੋ ਪਬਲਿਸ਼ ਪਾਈਪਲਾਈਨ ਦੀ ਵਰਤੋਂ ਕਰਦੇ ਹਨ। `8` (→ 7 ਵਰਕਰ) 'ਤੇ ਉਸ ਦੌੜਾਕ ਦੀ ਮੈਮੋਰੀ ਖਤਮ ਹੋ ਗਈ ਅਤੇ ਬਿਲਡਕਿੱਟ `ResourceExhausted: ... cannot allocate memory` ਨਾਲ ਕਦਮ ਨੂੰ ਅਸਫਲ ਕਰ ਦਿੱਤਾ; `3` (→ 2 ਵਰਕਰ) ਅਜੇ ਵੀ ਫਿੱਟ ਨਹੀਂ ਹੋਏ ਜਦੋਂ ਪ੍ਰਤੀ-ਪ੍ਰਕਿਰਿਆ RSS ਅਨੁਮਾਨ ਦੀ ਬਜਾਏ ਸਿੱਧੇ ਮਾਪਿਆ ਗਿਆ ਸੀ। `tests/unit/docker-build-memory-budget.test.ts` ਮਾਪੇ ਗਏ ਅੰਕੜੇ ਦੇ ਵਿਰੁੱਧ ਗਣਿਤ ਕਰਦਾ ਹੈ ਅਤੇ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ ਜੇਕਰ ਕੋਈ ਨੋਬ ਦੌੜਾਕ ਨੂੰ ਪਛਾੜ ਦਿੰਦਾ ਹੈ।

Turbopack ਨੇਟਿਵ ਰਸਟ ਮੈਮੋਰੀ ਵਿੱਚ ਕੰਪਾਈਲ ਕਰਦਾ ਹੈ ਜੋ ਰਹਿੰਦੀ ਹੈ** ਬਾਹਰ** V8 ਹੀਪ, ਇਸਲਈ `OMNIROUTE_BUILD_MEMORY_MB` ਇਸ ਨੂੰ ਬੰਨ੍ਹਦਾ ਨਹੀਂ ਹੈ। ਮੈਮੋਰੀ ਸੀਲਿੰਗ ਵਾਲੇ ਹੋਸਟ 'ਤੇ ਬਿਲਡ ਨੂੰ OOM ਕਿਲਰ ਦੁਆਰਾ SIGKILLed ਹੈ, ਬਿਨਾਂ ਕਿਸੇ ਗਲਤੀ ਦੇ ਟੈਕਸਟ ਦੇ — ਇਹ ਬਸ ਮੱਧ-`Creating an optimized production build` ਨੂੰ ਰੋਕਦਾ ਹੈ, ਜੋ ਕਿ ਮੈਮੋਰੀ ਤੋਂ ਬਾਹਰ ਹੋਣ ਦੀ ਬਜਾਏ ਹੈਂਗ ਵਾਂਗ ਪੜ੍ਹਦਾ ਹੈ। ਇਹੀ ਕਾਰਨ ਹੈ ਕਿ `Dockerfile` /`OMNIROUTE_USE_TURBOPACK=0` ਦੇ ਉਲਟ, `npm run dev` / `npm run build` ਦੇ ਉਲਟ, ਜਿੱਥੇ Turbopack ਕੋਡ ਡਿਫੌਲਟ ਹੈ: ਇੱਕ ਬੇਅਰ `docker build .` ਬਿਨਾਂ ਬਿਲਡ ਆਰਗਸ (ਜੋ ਰੇਲਵੇ ਅਤੇ ਹੋਰ ਇੱਕ-ਕਲਿੱਕ ਹੋਸਟ ਚਲਾਉਂਦੇ ਹਨ) ਇੱਕ ਮੈਮੋਰੀ-ਕੈਪਡ ਬਿਲਡਰ 'ਤੇ ਚੁੱਪ-ਚਾਪ ਨਹੀਂ ਮਰਨਾ ਚਾਹੀਦਾ। ਪ੍ਰਕਾਸ਼ਿਤ ਚਿੱਤਰ ਪਹਿਲਾਂ ਹੀ `docker-publish.yml` ਵਿੱਚ ਸਪੱਸ਼ਟ ਤੌਰ 'ਤੇ `OMNIROUTE_USE_TURBOPACK=0` ਪਾਸ ਕਰਦੇ ਹਨ। ਬਹੁਤ ਸਾਰੇ RAM ਵਾਲੇ ਬਿਲਡਰ 'ਤੇ, ਇੱਕ ਤੇਜ਼ ਬਿਲਡ ਲਈ Turbopack ਦੀ ਚੋਣ ਕਰੋ:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` ਸਮਰਥਿਤ ਹੈ, ਇਸਲਈ `next build` ਇੱਕ ਮਾਤਾ ਜਾਂ ਪਿਤਾ ਨੂੰ ਚਲਾਉਂਦਾ ਹੈ** ਅਤੇ** ਇੱਕ ਵਰਕਰ ਪ੍ਰਕਿਰਿਆ ਅਤੇ ਹਰ ਇੱਕ ਵੱਖਰੇ ਤੌਰ 'ਤੇ `OMNIROUTE_BUILD_MEMORY_MB` ਦਾ ਸਨਮਾਨ ਕਰਦਾ ਹੈ। ਕੰਟੇਨਰ ਦੀ ਛੱਤ ਦਾ ਆਕਾਰ ਉਸ ਮੁੱਲ ਤੋਂ ਲਗਭਗ ਦੁੱਗਣਾ ਕਰੋ, ਇੱਕ ਵਾਰ ਨਹੀਂ।

ਇਸ ਰੁੱਖ 'ਤੇ ਮਾਪਿਆ (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| ਬੰਡਲਰ     | ਕੰਟੇਨਰ ਦੀ ਛੱਤ  | ਨਤੀਜਾ                                    |
| --------- | -------------- | ---------------------------------------- |
| Turbopack | 8 GiB / 16 GiB | ਊਮ-ਦੋਹਾਂ 'ਤੇ ਮਾਰਿਆ, ਚੁੱਪਚਾਪ              |
| ਵੈਬਪੈਕ    | 8 GiB          | ਵਰਕਰ SIGKILLed ਬਣਾਓ                      |
| ਵੈਬਪੈਕ    | 12 GiB         | ਸਫਲ ਰਿਹਾ, 11.1 GiB ਤੇ ਸਿਖਰ 'ਤੇ ਪਹੁੰਚ ਗਿਆ |

### ਰਨਟਾਈਮ ਪੂਰਵ-ਨਿਰਧਾਰਤ

`runner-base` ਦੁਆਰਾ ਨਿਰਯਾਤ ਕੀਤੇ ਡਿਫੌਲਟ : `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`.

Docker ਵਿੱਚ ਮੈਮੋਰੀ ਵਿਵਹਾਰ:

- ਚਿੱਤਰ `OMNIROUTE_MEMORY_MB=1024` ਸੈੱਟ ਕਰਦਾ ਹੈ ਅਤੇ ਇਸ ਤੋਂ `NODE_OPTIONS=--max-old-space-size=1024` ਲਿਆ ਜਾਂਦਾ ਹੈ।
- ਅਸਲ ਸਰਵਰ ਪ੍ਰਕਿਰਿਆ ਸਟੈਂਡਅਲੋਨ ਲਾਂਚਰ ਦੁਆਰਾ ਸ਼ੁਰੂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਜੋ `OMNIROUTE_MEMORY_MB` ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ਜੋੜਦਾ ਹੈ।
- ਨੋਡ ਆਖਰੀ ਵਾਰ ਦੁਹਰਾਇਆ ਗਿਆ `--max-old-space-size` ਮੁੱਲ ਵਰਤਦਾ ਹੈ, ਇਸਲਈ `OMNIROUTE_MEMORY_MB` ਸੈੱਟ ਕਰਨਾ ਪ੍ਰਭਾਵਸ਼ਾਲੀ Docker ਹੀਪ ਸੀਮਾ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਦਾ ਹੈ।
- ਕਿਉਂਕਿ ਚਿੱਤਰ ਹਮੇਸ਼ਾ ਇਸਨੂੰ ਸੈੱਟ ਕਰਦਾ ਹੈ, ਲਾਂਚਰ ਦਾ ਆਪਣਾ ਰੈਮ-ਕੈਲੀਬਰੇਟਿਡ ਫਾਲਬੈਕ ਕਦੇ ਵੀ Docker ਦੇ ਅਧੀਨ ਲਾਗੂ ਨਹੀਂ ਹੁੰਦਾ। ਵਰਕਲੋਡ (ਹੇਠਾਂ ਦਿੱਤੀ ਸਾਰਣੀ) ਲਈ ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਵਧਾਓ। `2048` ਅਜੇ ਵੀ ਕੋਡਿੰਗ-ਏਜੰਟ `/v1/responses` ਲਈ ਬਹੁਤ ਛੋਟਾ ਹੈ।

### ਕੋਡਿੰਗ ਏਜੰਟਾਂ ਲਈ ਰਨਟਾਈਮ RAM

1 GiB Docker ਡਿਫੌਲਟ ਇੱਕ dashboard/light-chat ਫਲੋਰ ਹੈ, ਉਤਪਾਦਨ ਦਾ ਆਕਾਰ ਨਹੀਂ। ਲੰਬੀਆਂ `POST /v1/responses` ਬਾਡੀਜ਼ (ਸੈਂਕੜੇ ਸੁਨੇਹੇ, ਦਸਾਂ ਟੂਲ) ਕੰਪਰੈਸ਼ਨ ਦੌਰਾਨ ਕਈ ਇਨ-ਮੈਮੋਰੀ ਗ੍ਰਾਫ ਬਰਕਰਾਰ ਰੱਖਦੇ ਹਨ। ਦੋ ਓਵਰਲੈਪਿੰਗ ~ 3 MiB / ~ 750k-ਟੋਕਨ ਬੇਨਤੀਆਂ ਨੇ ਇੱਕ 'ਤੇ V8 ਨੂੰ ਰੱਦ ਕਰ ਦਿੱਤਾ ਹੈ** 12 GiB** old-space (`FATAL ERROR: Reached heap limit`) ਅਤੇ ਇੱਕ 16 GiB cgroup OOM ਵੀ ਮਾਰਿਆ। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ਵੇਖੋ.

ਆਕਾਰ** cgroup `--memory` ਢੇਰ ਦੇ ਉੱਪਰ** — ਨੇਟਿਵ ਬਫਰ, SQLite, ਅਤੇ ਕੰਪਰੈਸ਼ਨ ਇੰਟਰਮੀਡੀਏਟ V8 ਦੇ ਬਾਹਰ ਬੈਠਦੇ ਹਨ।

| ਕੰਮ ਦਾ ਬੋਝ                          | `OMNIROUTE_MEMORY_MB`   | ਕੰਟੇਨਰ / cgroup      | ਨੋਟਸ                                                                                          |
| ----------------------------------- | ----------------------- | -------------------- | --------------------------------------------------------------------------------------------- |
| ਡੈਸ਼ਬੋਰਡ, ਇੱਕ ਹਲਕਾ ਚੈਟ              | `1024` (ਚਿੱਤਰ ਮੂਲ)      | ≥2 GiB               |                                                                                               |
| ਇੱਕ ਕੋਡਿੰਗ ਏਜੰਟ (Claude/Codex/Grok) | `8192`                  | ≥10 GiB              | ਆਮ ਸਿੰਗਲ-ਸੈਸ਼ਨ `/v1/responses`                                                                |
| ਦੋ ਸਮਕਾਲੀ ਲੰਬੇ `/v1/responses`      | `10240`–`12288`         | ≥12–16 GiB           | ~ 12 GiB ਹੀਪ 'ਤੇ ਮਾਪਿਆ ਗਿਆ V8 ਅਧੂਰਾ ਛੱਡਿਆ ਗਿਆ                                                 |
| ਤਿੰਨ + ਸਮਕਾਲੀ ਲੰਬੇ ਸੰਦਰਭ            | ਇੱਕ ਪ੍ਰਕਿਰਿਆ 'ਤੇ ਨਾ ਕਰੋ | ਸੀਰੀਅਲਾਈਜ਼ / ਹੋਰ RAM | ਡਿਫੌਲਟ ਹੈਵੀਵੇਟ ਦਾਖਲਾ 1 ਇਨ-ਫਲਾਈਟ ਹੈ; RAM ਤੋਂ ਬਿਨਾਂ ਇਸ ਨੂੰ ਵਧਾਉਣਾ ਅਧੂਰੇ ਨੂੰ ਦੁਬਾਰਾ ਪੇਸ਼ ਕਰਦਾ ਹੈ |

ਬੇਅਰ ਮੈਟਲ 'ਤੇ`omniroute serve` ~ ਦਾ 35% RAM (ਕੈਂਪਡ `[512, 4096]`) ਨੂੰ ਕੈਲੀਬ੍ਰੇਟ ਕਰਦਾ ਹੈ ਜਦੋਂ `OMNIROUTE_MEMORY_MB` ਹੁੰਦਾ ਹੈ** ਅਣਸੈੱਟ** . Docker ਹਮੇਸ਼ਾ `1024` ਸੈੱਟ ਕਰਦਾ ਹੈ, ਤਾਂ ਕਿ ਕੈਲੀਬ੍ਰੇਸ਼ਨ ਕਦੇ ਵੀ ਅਧਿਕਾਰਤ ਚਿੱਤਰ ਵਿੱਚ ਨਾ ਚੱਲੇ।

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data cheaperinference/omniroute:latest
```

## ਸਬਪਾਥ 'ਤੇ ਉਲਟਾ ਪ੍ਰੌਕਸੀ (ਟ੍ਰੈਫਿਕ / ਐਨਜੀਨੈਕਸ)

Next.js `basePath` ਨੂੰ ਸਟੈਂਡਅਲੋਨ ਬੰਡਲ ਵਿੱਚ ਕੰਪਾਇਲ ਕੀਤਾ ਗਿਆ ਹੈ। OmniRoute ਐਪ ਰੂਟ ( `npm run build` ਦੇ ਦੌਰਾਨ ਲਿਖਿਆ ਗਿਆ; `scripts/docker/ensure-docker-base-path.mjs` ਦੁਆਰਾ ਪੜ੍ਹਿਆ ਗਿਆ) 'ਤੇ ਇੱਕ ਸੈਂਟੀਨੇਲ ਫਾਈਲ ਵਿੱਚ ਬੇਕਡ ਮੁੱਲ ਨੂੰ ਰਿਕਾਰਡ ਕਰਦਾ ਹੈ ਅਤੇ ਜਦੋਂ ਕੰਟੇਨਰ ਸ਼ੁਰੂ ਹੁੰਦਾ ਹੈ ਤਾਂ `OMNIROUTE_BASE_PATH` ਨਾਲ ਇਸਦੀ ਤੁਲਨਾ ਕਰਦਾ ਹੈ। ਜਦੋਂ ਉਹ ਵੱਖਰੇ ਹੁੰਦੇ ਹਨ ਅਤੇ ਚਿੱਤਰ ਨੂੰ ਡੋਮੇਨ ਰੂਟ ਲਈ ਬਣਾਇਆ ਗਿਆ ਸੀ, ਤਾਂ ਐਂਟਰੀਪੁਆਇੰਟ ਸਟੈਂਡਅਲੋਨ ਮੈਨੀਫੈਸਟ ਨੂੰ ਦੁਬਾਰਾ ਲਿਖਦਾ ਹੈ, ਏਮਬੈਡਡ `basePath`/`assetPrefix` ਲਿਟਰਲ (ਅਗਲਾ 16 SSR ਸੰਪਤੀ URLs `assetPrefix` ਤੋਂ ਇਕੱਲੇ — ਪੇਸ਼ ਕਰਦਾ ਹੈ, ਪੈਚਰ ਇਸ ਵਿੱਚ ਸਬਪਾਥ ਨੂੰ ਮਿਰਰ ਕਰਦਾ ਹੈ), `/_next/static` asqn URLs, ਮੀਡੀਆ ਆਯਾਤ, ਪਹਿਲਾਂ ਤੋਂ ਰੈਂਡਰਡ ਐਰਰ ਪੇਜ) ਅਤੇ `node dev/run-standalone.mjs` ਚੱਲਣ ਤੋਂ ਪਹਿਲਾਂ ਕਲਾਇੰਟ `process.env` ਸ਼ਿਮ।

### ਕੰਪੋਜ਼ ਬਿਲਡ (ਸਿਫਾਰਸ਼ੀ)

`.env` ਵਿੱਚ ਦੋਵੇਂ ਵੇਰੀਏਬਲ ਸੈਟ ਕਰੋ, ਫਿਰ ਦੁਬਾਰਾ ਬਣਾਓ ਤਾਂ ਕਿ ਚਿੱਤਰ ਅਤੇ ਰਨਟਾਈਮ ਸਹਿਮਤ ਹੋਣ:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml` `OMNIROUTE_BASE_PATH` Docker ਬਿਲਡ-ਆਰਗ ਅਤੇ ਰਨਟਾਈਮ ਵਾਤਾਵਰਣ ਵੇਰੀਏਬਲ ਵਜੋਂ ਅੱਗੇ ਭੇਜਦਾ ਹੈ।

### ਪ੍ਰੀ-ਬਿਲਟ ਰੂਟ ਚਿੱਤਰ + ਰਨਟਾਈਮ ਸਬਪਾਥ

ਪ੍ਰਕਾਸ਼ਿਤ `cheaperinference/omniroute:*` ਚਿੱਤਰ ਡੋਮੇਨ ਰੂਟ ਲਈ ਬਣਾਏ ਗਏ ਹਨ। ਤੁਸੀਂ ਅਜੇ ਵੀ ਰਨਟਾਈਮ 'ਤੇ `OMNIROUTE_BASE_PATH` ਸੈੱਟ ਕਰ ਸਕਦੇ ਹੋ; ਕੰਟੇਨਰ ਇੱਕ ਵਾਰ ਸ਼ੁਰੂ ਹੋਣ 'ਤੇ ਬੰਡਲ ਨੂੰ ਪੈਚ ਕਰਦਾ ਹੈ। ਇਸ ਨੂੰ ਮੇਲ ਖਾਂਦੇ ਜਨਤਕ ਮੂਲ ਨਾਲ ਜੋੜੋ:

```yaml
services:
  omniroute:
    image: cheaperinference/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

ਨੂੰ ਅੱਗੇ ਭੇਜਣ ਲਈ ਰਿਵਰਸ ਪ੍ਰੌਕਸੀ ਨੂੰ ਕੌਂਫਿਗਰ ਕਰੋ** ਪੂਰਾ** ਬਾਹਰੀ ਮਾਰਗ (ਅਗੇਤਰ ਨੂੰ ਨਾ ਹਟਾਓ)। Traefik ਨੂੰ `PathPrefix(`/omniroute `)` `StripPrefix` ਤੋਂ ਬਿਨਾਂ ਕੰਟੇਨਰ ਤੱਕ ਰੂਟ ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ, ਇਸਲਈ Next.js `/omniroute/...` ਪ੍ਰਾਪਤ ਕਰਦਾ ਹੈ ਅਤੇ `/omniroute/_next/...` ਤੋਂ ਸੰਪਤੀਆਂ ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ।

Docker ਹੈਲਥ-ਚੈੱਕ ਲਾਈਟਵੇਟ `/healthz` ਲਾਈਫਸਾਈਕਲ ਐਂਡਪੁਆਇੰਟ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ ਜੋ ਕਿਰਿਆਸ਼ੀਲ `OMNIROUTE_BASE_PATH` ਨਾਲ ਪ੍ਰੀਫਿਕਸ ਹੁੰਦਾ ਹੈ। `/api/monitoring/health` human/dashboard ਡਾਇਗਨੌਸਟਿਕਸ ਲਈ ਉਪਲਬਧ ਰਹਿੰਦਾ ਹੈ; ਕੰਟੇਨਰ HEALTHCHECK ਇਸ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਨ ਲਈ (ਉਦਾਹਰਨ ਲਈ ਡੂੰਘੇ ਸਿਹਤ ਲਾਗੂ ਕਰਨ ਲਈ), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` ਸੈੱਟ ਕਰੋ। ਉਹ ਮਾਰਗ ਏ** ਡੂੰਘੀ** ਚੈੱਕ ਕਰੋ (DB + ਨਿਗਰਾਨੀ ਸੰਖੇਪ) — Docker ਦੇ ਵਿਰਲੇ `HEALTHCHECK` ਲਈ ਉਚਿਤ ਹੈ ਜੇਕਰ ਤੁਸੀਂ ਵਾਪਸ ਚੁਣਦੇ ਹੋ, ਪਰ** ਨਹੀਂ** Kubernetes `livenessProbe` ਅੰਤਰਾਲਾਂ ਲਈ।

ਆਰਕੈਸਟਰੇਟਰਾਂ ਲਈ (ਕੁਬਰਨੇਟਸ, ਨੋਮੈਡ, ਆਦਿ):

| ਪੜਤਾਲ            | ਤਰਜੀਹ                                                              | ਬਚੋ                                                     |
| ---------------- | ------------------------------------------------------------------ | ------------------------------------------------------- |
| ਜੀਵੰਤਤਾ          | HTTP `GET /livez`, ਜਾਂ ਮੁੱਖ ਪੋਰਟ ਉੱਤੇ TCP (`PORT`, ਡਿਫਾਲਟ `20128`) | `/api/monitoring/health` ਜੀਵਣਤਾ ਵਜੋਂ                    |
| ਤਤਪਰਤਾ           | HTTP `GET /healthz`                                                | ਤੰਗ ਸਮਾਂ ਸਮਾਪਤ ਜੋ ਇਵੈਂਟ-ਲੂਪ ਰੁੱਝੇ ਹੋਏ ਨੂੰ ਮਰਿਆ ਸਮਝਦੇ ਹਨ |
| ਡੂੰਘੇ / ਬਲੈਕਬਾਕਸ | `/api/monitoring/health`                                           | —                                                       |

`/healthz` ਰਿਪੋਰਟ ਪ੍ਰਕਿਰਿਆ ਜੀਵਨ ਚੱਕਰ (`ok` / `starting` / `stopping`)। `/livez` ਸਿਰਫ਼ ਪ੍ਰਕਿਰਿਆ-ਜ਼ਿੰਦਾ ਹੈ (200 ਜਦੋਂ ਵੀ ਹੈਂਡਲਰ ਚੱਲ ਸਕਦਾ ਹੈ; ਇਹ ਤਿਆਰੀ ਦੀ ਉਡੀਕ ਨਹੀਂ ਕਰਦਾ)। ਦੋਵੇਂ ਅਜੇ ਵੀ ਬੇਨਤੀ ਹੈਂਡਲਿੰਗ ਦੇ ਤੌਰ 'ਤੇ ਉਸੇ ਨੋਡ ਇਵੈਂਟ ਲੂਪ 'ਤੇ ਚੱਲਦੇ ਹਨ, ਇਸਲਈ CPU-ਬੱਧ ਕੈਟਾਲਾਗ ਜਾਂ ਕੰਪਰੈਸ਼ਨ ਕੰਮ ਉਨ੍ਹਾਂ ਨੂੰ — ਵਿਅਸਤ ≠ ਡੈੱਡ ਦੇਰੀ ਕਰ ਸਕਦਾ ਹੈ। ਜੇ HTTP ਜਾਂਚ ਦਾ ਸਮਾਂ ਸਮਾਪਤ ਹੁੰਦਾ ਹੈ ਤਾਂ TCP ਜੀਵਣਤਾ ਨੂੰ ਤਰਜੀਹ ਦਿਓ। ਪੂਰੀ ਪੜਤਾਲ ਮਾਰਗਦਰਸ਼ਨ: [ਨਿਗਰਾਨੀ ਗਾਈਡ — Kubernetes ਪੜਤਾਲ ਸਿਫਾਰਸ਼ਾਂ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) ।

## Docker ਕੈਡੀ ਨਾਲ ਕੰਪੋਜ਼ ਕਰੋ (HTTPS ਆਟੋ-TLS)

OmniRoute Caddy ਦੇ ਆਟੋਮੈਟਿਕ SSL ਪ੍ਰੋਵਿਜ਼ਨਿੰਗ ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਸੁਰੱਖਿਅਤ ਢੰਗ ਨਾਲ ਪ੍ਰਗਟ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ। ਯਕੀਨੀ ਬਣਾਓ ਕਿ ਤੁਹਾਡੇ ਡੋਮੇਨ ਦਾ DNS A ਰਿਕਾਰਡ ਤੁਹਾਡੇ ਸਰਵਰ ਦੇ IP ਵੱਲ ਪੁਆਇੰਟ ਕਰਦਾ ਹੈ।

```yaml
services:
  omniroute:
    image: cheaperinference/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # Browser-facing origin for OAuth callbacks, dashboard links, and generated public URLs.
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # Internal server-to-server URL for scheduled jobs / self-fetches.
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

ਕੈਡੀ ਅੱਪਸਟ੍ਰੀਮ ਕੰਟੇਨਰ ਲਈ ਸਟੈਂਡਰਡ ਫਾਰਵਰਡਿੰਗ ਹੈਡਰ ਸੈੱਟ ਕਰਦਾ ਹੈ। OmniRoute OAuth ਕਾਲਬੈਕਸ ਅਤੇ ਜਨਰੇਟ ਕੀਤੇ ਜਨਤਕ ਲਿੰਕਾਂ ਲਈ `NEXT_PUBLIC_BASE_URL` ਕੈਨੋਨੀਕਲ ਜਨਤਕ ਮੂਲ ਵਜੋਂ ਵਰਤਦਾ ਹੈ; ਪ੍ਰਮਾਣਿਤ ਡੈਸ਼ਬੋਰਡ ਉਸੇ-ਮੂਲ ਬੇਨਤੀਆਂ ਅਤੇ ਸੈਸ਼ਨ-ਬਾਊਂਡ CSRF ਸੁਰੱਖਿਆ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। ਸਿਰਫ਼ ਉੱਨਤ ਤੈਨਾਤੀਆਂ ਲਈ `OMNIROUTE_TRUST_PROXY` ਸਮਰੱਥ ਬਣਾਓ ਜਿੱਥੇ ਤੁਸੀਂ ਜਾਣਬੁੱਝ ਕੇ OmniRoute ਸਪਸ਼ਟ ਸੰਰਚਨਾ ਦੀ ਬਜਾਏ ਭਰੋਸੇਯੋਗ ਫਾਰਵਰਡ ਕੀਤੇ ਸਿਰਲੇਖਾਂ ਤੋਂ ਜਨਤਕ ਮੂਲ ਪ੍ਰਾਪਤ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹੋ।

## Cloudflare Quick Tunnel

Docker ਡਿਪਲੌਇਮੈਂਟਾਂ ਲਈ ਡੈਸ਼ਬੋਰਡ ਸਹਾਇਤਾ ਵਿੱਚ `Dashboard → Endpoints` ਉੱਤੇ ਇੱਕ-ਕਲਿੱਕ **Cloudflare Quick Tunnel** ਸ਼ਾਮਲ ਹੈ। ਪਹਿਲੀ ਵਾਰ ਸਮਰੱਥ ਕਰਨ ਉੱਤੇ `cloudflared` ਕੇਵਲ ਲੋੜ ਪੈਣ 'ਤੇ ਡਾਊਨਲੋਡ ਹੁੰਦਾ ਹੈ, ਤੁਹਾਡੇ ਮੌਜੂਦਾ `/v1` ਐਂਡਪੌਇੰਟ ਲਈ ਇੱਕ ਅਸਥਾਈ ਟਨਲ ਸ਼ੁਰੂ ਕਰਦਾ ਹੈ ਅਤੇ ਤਿਆਰ ਕੀਤਾ `https://*.trycloudflare.com/v1` URL ਤੁਹਾਡੇ ਸਧਾਰਨ ਜਨਤਕ URL ਦੇ ਸਿੱਧੇ ਹੇਠਾਂ ਦਿਖਾਉਂਦਾ ਹੈ।

ਐਂਡਪੌਇੰਟ ਟਨਲ ਪੈਨਲਾਂ (Cloudflare, Tailscale, ngrok) ਨੂੰ ਸਰਗਰਮ ਟਨਲ ਦੀ ਸਥਿਤੀ ਬਦਲੇ ਬਿਨਾਂ `Settings → Appearance` ਤੋਂ ਦਿਖਾਇਆ ਜਾਂ ਲੁਕਾਇਆ ਜਾ ਸਕਦਾ ਹੈ।

### ਟਨਲ ਸੰਬੰਧੀ ਨੋਟਸ

- Quick Tunnel URLs ਅਸਥਾਈ ਹੁੰਦੇ ਹਨ ਅਤੇ ਹਰ ਰੀਸਟਾਰਟ ਤੋਂ ਬਾਅਦ ਬਦਲ ਜਾਂਦੇ ਹਨ।
- OmniRoute ਜਾਂ ਕੰਟੇਨਰ ਦੇ ਰੀਸਟਾਰਟ ਤੋਂ ਬਾਅਦ Quick Tunnels ਆਪਣੇ ਆਪ ਮੁੜ-ਬਹਾਲ ਨਹੀਂ ਹੁੰਦੇ। ਲੋੜ ਪੈਣ 'ਤੇ ਉਹਨਾਂ ਨੂੰ ਡੈਸ਼ਬੋਰਡ ਤੋਂ ਮੁੜ ਸਮਰੱਥ ਕਰੋ।
- ਪ੍ਰਬੰਧਿਤ ਇੰਸਟਾਲ ਇਸ ਵੇਲੇ `x64` / `arm64` ਉੱਤੇ Linux, macOS ਅਤੇ Windows ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ।
- ਸੀਮਤ ਕੰਟੇਨਰ ਵਾਤਾਵਰਣਾਂ ਵਿੱਚ ਸ਼ੋਰ-ਭਰੀਆਂ QUIC UDP ਬਫਰ ਚੇਤਾਵਨੀਆਂ ਤੋਂ ਬਚਣ ਲਈ ਪ੍ਰਬੰਧਿਤ Quick Tunnels ਮੂਲ ਰੂਪ ਵਿੱਚ HTTP/2 ਟ੍ਰਾਂਸਪੋਰਟ ਵਰਤਦੇ ਹਨ। ਜੇ ਤੁਸੀਂ ਕੋਈ ਵੱਖਰਾ ਟ੍ਰਾਂਸਪੋਰਟ ਚਾਹੁੰਦੇ ਹੋ ਤਾਂ `CLOUDFLARED_PROTOCOL=quic` ਜਾਂ `auto` ਸੈੱਟ ਕਰੋ।
- Docker ਇਮੇਜਾਂ ਵਿੱਚ ਸਿਸਟਮ CA ਰੂਟ ਸ਼ਾਮਲ ਹੁੰਦੇ ਹਨ ਅਤੇ ਉਹਨਾਂ ਨੂੰ ਪ੍ਰਬੰਧਿਤ `cloudflared` ਤੱਕ ਪਹੁੰਚਾਇਆ ਜਾਂਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਟਨਲ ਬੂਟਸਟਰੈਪ ਹੋਣ ਵੇਲੇ TLS ਭਰੋਸਾ ਅਸਫਲਤਾਵਾਂ ਤੋਂ ਬਚਿਆ ਜਾਂਦਾ ਹੈ।
- ਜੇ ਤੁਸੀਂ ਚਾਹੁੰਦੇ ਹੋ ਕਿ OmniRoute ਕੋਈ ਬਾਈਨਰੀ ਡਾਊਨਲੋਡ ਕਰਨ ਦੀ ਬਜਾਏ ਮੌਜੂਦਾ ਬਾਈਨਰੀ ਦੀ ਵਰਤੋਂ ਕਰੇ, ਤਾਂ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ਸੈੱਟ ਕਰੋ।

#### ਵੈੱਬ-ਸ਼ੈਸ਼ਨ ਪ੍ਰਦਾਤਾ: `-web` ਚਿੱਤਰ

ਉਪਰੋਕਤ ਹਰੇਕ ਚੈਨਲ `-web` ਟੈਗ (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) ਦੇ ਰੂਪ ਵਿੱਚ ਦੁੱਗਣਾ ਹੋ ਜਾਂਦਾ ਹੈ , `runner-web` ਪੜਾਅ — ਉਸੇ ਚਿੱਤਰ ਤੋਂ ਇਲਾਵਾ Playwright ਅਤੇ ਇੱਕ Chromium ਬ੍ਰਾਊਜ਼ਰ ਤੋਂ ਬਣਾਇਆ ਗਿਆ ਹੈ। ਸਾਦਾ ਚਿੱਤਰ ਜਹਾਜ਼** ਬਿਨਾ** ਕਰੋਮੀਅਮ; `gemini-web`, `claude-web` ਅਤੇ `claude-turnstile` ਇਸਦੀ ਲੋੜ ਹੈ।

ਅਸਫਲਤਾ ਨੂੰ ਮੁਲਤਵੀ ਕੀਤਾ ਗਿਆ ਹੈ, ਸ਼ੁਰੂਆਤੀ ਸਮਾਂ ਨਹੀਂ: ਉਹ ਪ੍ਰਦਾਤਾ ਆਪਣੇ ਮਾਡਲਾਂ ਦੀ ਸੂਚੀ ਬਣਾਉਂਦੇ ਹਨ ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਜੁੜੇ ਹੋਏ ਦਿਖਾਉਂਦੇ ਹਨ, ਅਤੇ ਸਿਰਫ਼ ਪਹਿਲੀ ਬੇਨਤੀ ਇਸ ਨਾਲ ਅਸਫਲ ਹੁੰਦੀ ਹੈ

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

ਜੇ ਤੁਸੀਂ ਉਹਨਾਂ ਪ੍ਰਦਾਤਾਵਾਂ ਦੀ ਵਰਤੋਂ ਕਰਦੇ ਹੋ, ਤਾਂ ਉਸ ਚੈਨਲ ਦੇ `-web` ਟੈਗ ਨੂੰ ਖਿੱਚੋ ਜੋ ਤੁਸੀਂ ਪਹਿਲਾਂ ਹੀ — 'ਤੇ ਹੋ ਹੋਰ ਕੁਝ ਨਹੀਂ ਬਦਲਦਾ। ਇੱਕ npm/CLI ਇੰਸਟਾਲ (ਕੋਈ Docker ਚਿੱਤਰ ਨਹੀਂ) 'ਤੇ, ਬਰਾਬਰ ਦਾ ਗੁੰਮ ਹੋਇਆ ਟੁਕੜਾ ਬ੍ਰਾਊਜ਼ਰ ਬਾਈਨਰੀ ਹੈ: ਹੋਸਟ 'ਤੇ `npx playwright install chromium` ਚਲਾਓ।

#### ਪ੍ਰੀ-ਰਿਲੀਜ਼ ਚੈਨਲ ਦੀ ਵਰਤੋਂ ਕਰਨਾ

`next` ਚੈਨਲ ਨੂੰ ਮੌਜੂਦਾ ਡਿਫਾਲਟ `release/v*` ਸ਼ਾਖਾ ਵਿੱਚ ਹਰ ਪੁਸ਼ 'ਤੇ ਦੁਬਾਰਾ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ ਅਤੇ AMD64 ਅਤੇ ARM64 ਦੋਵਾਂ ਲਈ ਪ੍ਰਕਾਸ਼ਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਪੁਰਾਣੀਆਂ ਰੱਖ-ਰਖਾਅ ਸ਼ਾਖਾਵਾਂ ਇਸ ਨੂੰ ਓਵਰਰਾਈਟ ਨਹੀਂ ਕਰ ਸਕਦੀਆਂ। ਚੈਨਲ ਉਹਨਾਂ ਫਿਕਸਾਂ ਲਈ ਇੱਕ ਖਿੱਚਣ ਯੋਗ ਚਿੱਤਰ ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ ਜੋ ਅਗਲੇ ਸਟੇਬਲ ਟੈਗ ਨੂੰ ਕੱਟਣ ਤੋਂ ਪਹਿਲਾਂ ਕਿਰਿਆਸ਼ੀਲ ਰੀਲੀਜ਼ ਸ਼ਾਖਾ ਵਿੱਚ ਮਿਲ ਗਏ ਹਨ।

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker ਕੰਪੋਜ਼ ਲਈ, ਚੁਣੇ ਗਏ ਪ੍ਰੋਫਾਈਲ ਦੁਆਰਾ ਵਰਤੇ ਗਏ ਚਿੱਤਰ ਟੈਗ ਨੂੰ ਓਵਰਰਾਈਡ ਕਰੋ, ਫਿਰ ਸੇਵਾ ਨੂੰ ਖਿੱਚੋ ਅਤੇ ਦੁਬਾਰਾ ਬਣਾਓ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### ਸੁਰੱਖਿਆ ਅਤੇ ਰੋਲਬੈਕ

`next` ਇੱਕ ਫਲੋਟਿੰਗ ਪ੍ਰੀ-ਰਿਲੀਜ਼ ਚੈਨਲ ਹੈ। ਇਹ ਸਰਗਰਮ ਰੀਲੀਜ਼ ਸ਼ਾਖਾ ਨੂੰ ਕਿਸੇ ਵੀ ਪੁਸ਼ 'ਤੇ ਬਦਲ ਸਕਦਾ ਹੈ ਅਤੇ ਹੈ** ਉਤਪਾਦਨ ਦੀ ਵਰਤੋਂ ਲਈ ਸਮਰਥਿਤ ਨਹੀਂ ਹੈ** . ਕਿਸੇ ਖਾਸ ਬਿਲਡ ਦਾ ਮੁਲਾਂਕਣ ਕਰਦੇ ਹੋਏ ਚਿੱਤਰ ਡਾਇਜੈਸਟ ਨੂੰ ਪਿੰਨ ਕਰੋ:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

ਜਾਂਚ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ, OmniRoute ਡੇਟਾ ਵਾਲੀਅਮ ਜਾਂ ਬਾਇੰਡ-ਮਾਊਂਟਡ ਡੇਟਾ ਡਾਇਰੈਕਟਰੀ ਦਾ ਬੈਕਅੱਪ ਲਓ। ਵਾਪਸ ਰੋਲ ਕਰਨ ਲਈ, ਪਹਿਲਾਂ ਵਰਤੇ ਗਏ ਸਥਿਰ ਸੰਸਕਰਣ ਨੂੰ ਰੀਸਟੋਰ ਕਰੋ ਜਾਂ ਡਾਇਜੈਸਟ ਕਰੋ ਅਤੇ ਕੰਟੇਨਰ ਨੂੰ ਦੁਬਾਰਾ ਬਣਾਓ:

```bash
docker pull cheaperinference/omniroute:<stable-version>
docker compose up -d
```

ਇੱਕ ਰੀਲਿਜ਼-ਬ੍ਰਾਂਚ ਬਿਲਡ ਕਦੇ ਵੀ `latest` ਹਿਲਾ ਨਹੀਂ ਸਕਦਾ; ਕੇਵਲ ਇੱਕ ਯੋਗ ਸਥਿਰ ਅਰਥ ਸੰਸਕਰਣ ਹੀ ਸਥਿਰ ਪੁਆਇੰਟਰ ਨੂੰ ਉਤਸ਼ਾਹਿਤ ਕਰ ਸਕਦਾ ਹੈ। `next` ਚਿੱਤਰ ਰੀਲੀਜ਼ ਚਿੱਤਰ ਨਿਰੀਖਣ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦੇ ਹਨ ਅਤੇ CRITICAL- ਕਮਜ਼ੋਰੀ ਵਾਲੇ ਗੇਟ ਨੂੰ ਬਲੌਕ ਕਰਦੇ ਹਨ।

**`latest` git ਲਈ ਮੁਦਰਾ ਗਰੰਟੀ ਨਹੀਂ ਹੈ।** `main` ਤੇ ਜਾਂ ਸਰਗਰਮ `release/v*` ਸ਼ਾਖਾ 'ਤੇ ਵਿਲੀਨ ਕੀਤੇ ਫਿਕਸ ਹਨ** ਨਹੀਂ** `:latest` ਵਿੱਚ ਜਦੋਂ ਤੱਕ ਇੱਕ ਸਥਿਰ SemVer ਚਿੱਤਰ ਪ੍ਰਕਾਸ਼ਿਤ ਨਹੀਂ ਹੁੰਦਾ ਹੈ ਅਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਨੌਕਰੀ `:latest` ਉਤਸ਼ਾਹਿਤ ਕਰਦੀ ਹੈ (ਉਸ SemVer ਵਾਂਗ ਹੀ ਡਾਇਜੈਸਟ)। ਜੇਕਰ `latest` ਫ੍ਰੀਜ਼ ਕੀਤਾ ਜਾ ਰਿਹਾ ਹੈ ਜਦੋਂ ਕਿ GitHub ਪਹਿਲਾਂ ਹੀ ਫਿਕਸ ਦਿਖਾ ਰਿਹਾ ਹੈ, ਤਾਂ ਰੀਲੀਜ਼ ਸ਼ਾਖਾ ਦੀ ਜਾਂਚ ਕਰਨ ਲਈ `:next` ਖਿੱਚੋ ਜਾਂ SemVer ਟੈਗ ਦੀ ਉਡੀਕ ਕਰੋ।

## Docker ਵਿੱਚ ਡੈਸ਼ਬੋਰਡ ਅੱਪਡੇਟ

ਪ੍ਰਕਾਸ਼ਿਤ ਇਮੇਜ ਵਾਲਾ ਕੰਟੇਨਰ ਆਪਣੇ ਆਪ ਨੂੰ ਬਦਲ ਨਹੀਂ ਸਕਦਾ। ਜਦੋਂ OmniRoute ਨੂੰ ਪਤਾ ਲੱਗਦਾ ਹੈ ਕਿ ਇਹ ਕਿਸੇ
ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਚੱਲ ਰਿਹਾ ਹੈ (`.git` ਚੈੱਕਆਉਟ ਨਹੀਂ, npm ਇੰਸਟਾਲ ਨਹੀਂ), ਤਾਂ ਹੋਮ ਡੈਸ਼ਬੋਰਡ ਦਾ ਅੱਪਡੇਟ ਬੈਨਰ
npm/git ਹਦਾਇਤਾਂ ਦੀ ਬਜਾਏ ਚਲਾਉਣ ਲਈ ਹੋਸਟ ਕਮਾਂਡ, ਕਾਪੀ ਬਟਨ ਸਮੇਤ, ਦਿਖਾਉਂਦਾ ਹੈ:

```bash
docker compose pull omniroute && docker compose up -d --force-recreate omniroute
```

ਸੇਵਾ ਦਾ ਨਾਮ `AUTO_UPDATE_SERVICE` ਤੋਂ ਆਉਂਦਾ ਹੈ (ਡਿਫਾਲਟ `omniroute`, ਜੋ
`docker-compose.selfhost.yml` ਵਿੱਚ ਸੇਵਾ ਹੈ)। `pull` ਸਿਰਫ਼ ਇੱਕ ਬਦਲਦੇ ਟੈਗ (`latest`, `next`) ਨੂੰ ਅੱਗੇ ਵਧਾਉਂਦਾ ਹੈ; ਪਿੰਨ ਕੀਤੇ
`:X.Y.Z` ਟੈਗ ਨਾਲ, ਪਹਿਲਾਂ ਟੈਗ ਸੋਧੋ।

### ਹੋਸਟ ਟ੍ਰਿਗਰ ਫ਼ਾਈਲ ਨਾਲ ਇੱਕ-ਕਲਿੱਕ ਅੱਪਡੇਟ

`/var/run/docker.sock` ਨੂੰ ਮਾਊਂਟ ਕੀਤੇ ਬਿਨਾਂ **ਹੁਣੇ ਅੱਪਡੇਟ ਕਰੋ** ਨੂੰ ਕਾਰਜਸ਼ੀਲ ਰੱਖਣ ਲਈ (ਜੋ ਕੰਟੇਨਰ ਨੂੰ
ਹੋਸਟ ਉੱਤੇ root ਪਹੁੰਚ ਦਿੰਦਾ ਹੈ — ਉੱਪਰ ਦਿੱਤੀ `cli` ਪ੍ਰੋਫ਼ਾਈਲ ਚੇਤਾਵਨੀ ਵੇਖੋ), OmniRoute ਸੇਵਾ ਉੱਤੇ
`DOCKER_UPDATE_TRIGGER_FILE` ਸੈੱਟ ਕਰੋ ਅਤੇ ਹੋਸਟ ਉੱਤੇ ਇੱਕ ਵਾਚਰ ਚਲਾਓ:

```yaml
services:
  omniroute:
    environment:
      DOCKER_UPDATE_TRIGGER_FILE: /app/data/update/docker-update.request
    volumes:
      - ./data:/app/data
```

ਪਾਥ `DATA_DIR` ਦੇ ਅੰਦਰ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ (ਸਾਪੇਖ ਮੁੱਲ ਇਸਦੇ ਮੁਤਾਬਕ ਰਿਜ਼ਾਲਵ ਹੁੰਦੇ ਹਨ); ਹੋਰ ਕੁਝ ਵੀ
ਰੱਦ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। ਫਿਰ **ਹੁਣੇ ਅੱਪਡੇਟ ਕਰੋ** ਉਸ ਫ਼ਾਈਲ ਵਿੱਚ `{ "requestedAt": "...", "targetVersion": "X.Y.Z" }`
ਲਿਖਦਾ ਹੈ, `202` ਨਾਲ ਜਵਾਬ ਦਿੰਦਾ ਹੈ, ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਨਵਾਂ ਵਰਜਨ ਲਾਈਵ ਹੋਣ ਤੱਕ
`/api/system/version` ਨੂੰ ਪੋਲ ਕਰਦਾ ਹੈ ਅਤੇ ਫਿਰ ਰੀਲੋਡ ਹੁੰਦਾ ਹੈ। ਇਸ ਮੋਡ ਵਿੱਚ OmniRoute ਕਦੇ ਵੀ ਕੋਈ ਸ਼ੈੱਲ ਜਾਂ Docker ਕਮਾਂਡ ਨਹੀਂ ਚਲਾਉਂਦਾ।
ਹਰ ਅੱਪਡੇਟ ਕਾਰਵਾਈ ਵਾਂਗ, ਬੇਨਤੀ ਸਿਰਫ਼ ਲੂਪਬੈਕ/LAN ਕਲਾਇੰਟਾਂ ਤੋਂ ਹੀ ਸਵੀਕਾਰ ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

ਬਾਇਂਡ-ਮਾਊਂਟ ਕੀਤੀ ਡਾਟਾ ਡਾਇਰੈਕਟਰੀ ਹੋਸਟ ਨੂੰ ਨਿਗਰਾਨੀ ਲਈ ਇੱਕ ਸਥਿਰ ਪਾਥ ਦਿੰਦੀ ਹੈ। ਨਮੂਨਾ `systemd` ਯੂਨਿਟ
(`/srv/omniroute` ਨੂੰ ਉਸ ਡਾਇਰੈਕਟਰੀ ਅਨੁਸਾਰ ਬਦਲੋ ਜਿਸ ਵਿੱਚ ਤੁਹਾਡੀ compose ਫ਼ਾਈਲ ਅਤੇ `data/` ਮੌਜੂਦ ਹਨ):

```ini
# /etc/systemd/system/omniroute-update.path
[Unit]
Description=Watch for OmniRoute dashboard update requests

[Path]
PathExists=/srv/omniroute/data/update/docker-update.request

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/omniroute-update.service
[Unit]
Description=Pull and recreate the OmniRoute container

[Service]
Type=oneshot
WorkingDirectory=/srv/omniroute
ExecStartPre=/usr/bin/rm -f /srv/omniroute/data/update/docker-update.request
ExecStart=/bin/sh -c 'docker compose pull omniroute || (sleep 15 && docker compose pull omniroute)'
ExecStart=/usr/bin/docker compose up -d --force-recreate omniroute
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now omniroute-update.path
```

ਸੇਵਾ ਪੁੱਲ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਬੇਨਤੀ ਨੂੰ ਹਟਾਉਂਦੀ ਹੈ, ਤਾਂ ਜੋ ਅਸਫਲ ਰਨ ਲੂਪ ਵਿੱਚ ਨਾ ਪਵੇ।
`DOCKER_UPDATE_TRIGGER_FILE` ਤੋਂ ਬਿਨਾਂ ਡੈਸ਼ਬੋਰਡ ਮੈਨੁਅਲ ਕਮਾਂਡ ਪ੍ਰਵਾਹ ਨੂੰ ਜਾਰੀ ਰੱਖਦਾ ਹੈ।

## ਉਪਲਬਧਤਾ: ਡਿਫੌਲਟ SQLite ਸਿੰਗਲ-ਰਿਪਲੀਕਾ ਹੈ

ਸਟਾਕ Docker / Kubernetes OmniRoute ਹੈ** ਇੱਕ ਨੋਡ ਪ੍ਰਕਿਰਿਆ + ਇੱਕ SQLite ਲੇਖਕ** . ਉੱਚ ਉਪਲਬਧਤਾ ਹੈ** ਸਮਰਥਿਤ ਨਹੀਂ ਹੈ** ਉਸ ਟੋਪੋਲੋਜੀ 'ਤੇ.

| ਪਾਬੰਦੀ                                        | ਨਤੀਜਾ                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ਸਿੰਗਲ ਲੇਖਕ                                    | ਕਰੋ** ਨਹੀਂ** ਇੱਕੋ SQLite ਫਾਈਲ ਦੇ ਵਿਰੁੱਧ ਕਈ ਪ੍ਰਤੀਕ੍ਰਿਤੀਆਂ ਚਲਾਓ। ਇਹ DB ਨੂੰ ਵਿਗਾੜਦਾ ਹੈ।                                                                                                                                                                                                                        |
| ਦੁਬਾਰਾ ਬਣਾਓ / ਮੁੜ ਚਾਲੂ ਕਰੋ / HEALTHCHECK ਮਾਰੋ | **ਪੂਰੀ ਆਊਟੇਜ** ਇਨ-ਫਲਾਈਟ SSE, ਡੈਸ਼ਬੋਰਡ ਸੈਸ਼ਨਾਂ, ਅਤੇ ਇਨ-ਮੈਮੋਰੀ ਸਥਿਤੀ ਦਾ। ਹਰ ਕਨੈਕਟ ਕੀਤਾ ਕਲਾਇੰਟ ਘੱਟ ਜਾਂਦਾ ਹੈ। ਖਾਲੀ-ਐਂਡਪੁਆਇੰਟ ਵਿੰਡੋ ਦੇ ਦੌਰਾਨ ਨਵੀਆਂ ਬੇਨਤੀਆਂ ਨੂੰ ਰਿਵਰਸ-ਪ੍ਰਾਕਸੀ ਮਿਲਦੀ ਹੈ**`502 Bad Gateway: Unknown error`** , OmniRoute JSON ਨਹੀਂ — ਕਲਾਇੰਟ ਇਸ ਨੂੰ ਪ੍ਰਦਾਤਾ ਅਸਫਲਤਾ (#11015) ਤੋਂ ਵੱਖ ਨਹੀਂ ਕਰ ਸਕਦੇ ਹਨ। |
| `/healthz` ਵਾਂਗ ਹੀ ਇਵੈਂਟ ਲੂਪ                  | ਇੱਕ ਵਿਅਸਤ ਕੈਟਾਲਾਗ ਜਾਂ ਕੰਪਰੈਸ਼ਨ ਟਿੱਕ ਪੜਤਾਲ ਵਿੱਚ ਦੇਰੀ ਕਰ ਸਕਦਾ ਹੈ; ਇੱਕ ਛੋਟਾ ਸਮਾਂ ਸਮਾਪਤ ਫਿਰ ਮੁੜ ਚਾਲੂ ਹੁੰਦਾ ਹੈ** ਸਿਰਫ਼** ਪ੍ਰਤੀਕ੍ਰਿਤੀ.                                                                                                                                                                            |

**ਪੜਤਾਲ ਮੈਟ੍ਰਿਕਸ** ( [ਕੁਬਰਨੇਟਸ ਪੜਤਾਲ ਸਿਫ਼ਾਰਿਸ਼ਾਂ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) ਵੀ ਵੇਖੋ):

| ਪੜਤਾਲ         | ਨਿਸ਼ਾਨਾ                                                  | ਦੀ ਵਰਤੋਂ ਨਾ ਕਰੋ                                         |
| ------------- | -------------------------------------------------------- | ------------------------------------------------------- |
| ਜੀਵੰਤਤਾ       | TCP ਤੇ `PORT` (ਡਿਫਾਲਟ `20128`), ਜਾਂ ਸਾਫਟ HTTP `/healthz` | `/api/monitoring/health`                                |
| ਤਤਪਰਤਾ        | HTTP `GET /healthz`                                      | ਤੰਗ ਸਮਾਂ ਸਮਾਪਤ ਜੋ ਇਵੈਂਟ-ਲੂਪ ਰੁੱਝੇ ਹੋਏ ਨੂੰ ਮਰਿਆ ਸਮਝਦੇ ਹਨ |
| ਡੂੰਘੇ / ਮਨੁੱਖ | `/api/monitoring/health`                                 | ਸਵੈਚਲਿਤ ਕੁਬੇਲੇਟ ਲੀਨਤਾ                                   |

**ਅੱਪਗ੍ਰੇਡ:** ਹਰ ਸੈਸ਼ਨ ਦੇ ਡਿੱਗਣ ਦੀ ਉਮੀਦ ਕਰੋ. ਜੇ ਤੁਸੀਂ ਕਰ ਸਕਦੇ ਹੋ ਤਾਂ ਗਾਹਕਾਂ ਨੂੰ ਕੱਢੋ; ਡਿਫਾਲਟ SQLite ਤੇ ਕੋਈ ਰੋਲਿੰਗ ਅਪਡੇਟ ਨਹੀਂ ਹੈ। ਕੰਪੋਜ਼ `restart: unless-stopped` ਪਲੱਸ Docker `HEALTHCHECK` ਵੀ ਸਿਰਫ਼ ਉਸੇ ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਬਦਲ ਦੇਵੇਗਾ ਜਦੋਂ ਕੰਟੇਨਰ ਗੈਰ-ਸਿਹਤਮੰਦ ਹੋਵੇ — ਸਮਾਨ ਧਮਾਕੇ ਦਾ ਘੇਰਾ।

ਰੈਡੀ-ਮੇਡ ਮੈਨੀਫੈਸਟ ਅਤੇ ਇੱਕ ਹੈਲਮ ਚਾਰਟ `deploy/kubernetes/` ਅਤੇ `deploy/helm/omniroute/` ਵਿੱਚ ਰਹਿੰਦੇ ਹਨ — [Kubernetes ਡਿਪਲਾਇਮੈਂਟ ਗਾਈਡ](../ops/KUBERNETES_DEPLOYMENT_GUIDE.md) ਦੇਖੋ।

ਏ ਲਈ ਕੁਬਰਨੇਟਸ ਸਨਿੱਪਟ** ਸਿੰਗਲ ਪ੍ਰਤੀਕ੍ਰਿਤੀ** (ਮੁੜ ਬਣਾਉਣ ਦੀ ਲੋੜ ਹੈ; ਇੱਕ SQLite ਫਾਈਲ ਦੇ ਵਿਰੁੱਧ `replicas` ਨਾ ਉਠਾਓ):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` ਸਲੀਪ ਕੁਬੇ ਨੂੰ SIGTERM ਤੋਂ ਪਹਿਲਾਂ ਸਰਵਿਸ ਐਂਡਪੁਆਇੰਟ ਨੂੰ ਛੱਡਣ ਦਿੰਦਾ ਹੈ** ਨਵਾਂ** ਟ੍ਰੈਫਿਕ ਮਰਨ ਦੀ ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਰੋਕਦਾ ਹੈ. ਇਨ-ਫਲਾਈਟ `/v1/responses` SSE ਹੈਵੀਵੇਟ ਦਾਖਲਾ ਲੀਜ਼ (#11015) ਰਾਹੀਂ `SHUTDOWN_TIMEOUT_MS` (ਡਿਫਾਲਟ 30s) ਤੱਕ ਕੱਢਿਆ ਜਾਂਦਾ ਹੈ। ਨਵੀਆਂ ਬੇਨਤੀਆਂ ਜੋ ਅਜੇ ਵੀ ਪ੍ਰਕਿਰਿਆ ਤੱਕ ਪਹੁੰਚਦੀਆਂ ਹਨ `503` + `Retry-After: 5` ਪ੍ਰਾਪਤ ਕਰਦੀਆਂ ਹਨ। ਰੀਕ੍ਰਿਏਟ ਖਾਲੀ-ਐਂਡਪੁਆਇੰਟ ਗੈਪ ਜਦੋਂ ਤੱਕ ਰਿਪਲੇਸਮੈਂਟ ਰੈਡੀ ਨਹੀਂ ਹੁੰਦਾ ਇੱਕ ਹਾਰਡ ਆਊਟੇਜ ਰਹਿੰਦਾ ਹੈ — ਜੋ ਕਿ SQLite ਟੌਪੋਲੋਜੀ ਹੈ, ਨਾ ਕਿ ਇੱਕ ਜਾਂਚ ਗਲਤ ਸੰਰਚਨਾ।

ਬਾਹਰੀ Postgres / ਬਹੁ-ਲੇਖਕ HA ਹੈ** ਨਹੀਂ** ਇੱਕ ਦਸਤਾਵੇਜ਼ੀ ਸਟਾਕ ਮਾਰਗ। ਜੇਕਰ ਤੁਹਾਨੂੰ HA ਦੀ ਲੋੜ ਹੈ, ਤਾਂ ਇੱਕ ਸਿੰਗਲ ਰਿਪਲੀਕਾ ਰੱਖੋ ਜਾਂ ਇੱਕ ਟੌਪੌਲੋਜੀ ਚਲਾਓ ਜੋ ਪ੍ਰੋਜੈਕਟ ਦੁਆਰਾ ਟੈਸਟ ਕੀਤਾ ਗਿਆ ਹੈ ਅਤੇ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਦਸਤਾਵੇਜ਼ ਕੀਤਾ ਗਿਆ ਹੈ। Postgres/MySQL ਕੰਮ [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ਵਿੱਚ ਰਹਿੰਦਾ ਹੈ। ਹੈ, ਜੋ ਕਿ ਜਹਾਜ਼ ਤੱਕ, ਗੁਣਾ ਕਰਨ ਲਈ ਇੱਕੋ ਇੱਕ ਸਮਰਥਿਤ ਤਰੀਕਾ ਹੈ** ਵੱਡਾ** `/v1/responses` ਸਮਰੱਥਾ N ਸੁਤੰਤਰ ਪ੍ਰਕਿਰਿਆਵਾਂ (ਅਗਲਾ ਭਾਗ) ਹੈ, ਇੱਕ ਵਾਲੀਅਮ 'ਤੇ `replicas > 1` ਨਹੀਂ।

## ਸਕੇਲ-ਆਊਟ: N ਸੁਤੰਤਰ ਪ੍ਰਕਿਰਿਆਵਾਂ

### Codex ਟੋਕਨ ਰੋਟੇਸ਼ਨ ਮਲਕੀਅਤ

ਇੱਕ Codex ਖਾਤੇ ਦੀਆਂ ਕਾਪੀਆਂ ਨੂੰ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਇਸਦੇ ਸਿੰਗਲ-ਯੂਜ਼ ਰਿਫਰੈਸ਼ ਟੋਕਨ ਦੀ ਵਰਤੋਂ ਨਹੀਂ ਕਰਨੀ ਚਾਹੀਦੀ। ਉਹਨਾਂ ਮੌਕਿਆਂ 'ਤੇ ਜੋ ਸਿਰਫ਼ ਸਿੰਕ੍ਰੋਨਾਈਜ਼ਡ ਪ੍ਰਮਾਣ ਪੱਤਰਾਂ ਦੀ ਵਰਤੋਂ ਕਰਦੇ ਹਨ, `OMNIROUTE_TOKEN_REFRESH_PASSIVE_PROVIDERS=codex` (ਉਰਫ਼ `cx`) ਸੈੱਟ ਕਰੋ। ਇਸ ਨੂੰ ਸਿੰਗਲ ਰੋਟੇਸ਼ਨ ਮਾਲਕ 'ਤੇ ਬਿਨਾਂ ਸੈੱਟ ਕੀਤੇ ਛੱਡੋ। ਹਰੇਕ ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਅਜੇ ਵੀ ਆਪਣੀ ਖੁਦ ਦੀ `DATA_DIR` ਲੋੜ ਹੁੰਦੀ ਹੈ; ਇਹ ਵਿਕਲਪ ਨਾ ਤਾਂ SQLite ਸਾਂਝਾ ਕਰਦਾ ਹੈ ਅਤੇ ਨਾ ਹੀ ਟੋਕਨ ਸਿੰਕ੍ਰੋਨਾਈਜ਼ੇਸ਼ਨ ਜਾਂ ਵੰਡਿਆ ਲਾਕ ਸਪਲਾਈ ਕਰਦਾ ਹੈ।

ਪੈਸਿਵ ਉਦਾਹਰਨ ਕੁਨੈਕਸ਼ਨ ਨੂੰ ਮੁੜ ਪੜ੍ਹਦਾ ਹੈ ਜਦੋਂ ਇੱਕ ਰਿਫਰੈਸ਼ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ ਅਤੇ ਸਿਰਫ਼ ਇੱਕ ਵੱਖਰਾ, ਅਣਕਿਆਸਿਆ ਐਕਸੈਸ ਟੋਕਨ ਅਪਣਾਉਂਦੀ ਹੈ। ਨਹੀਂ ਤਾਂ ਰਿਫ੍ਰੈਸ਼ ਨੂੰ ਕਨੈਕਸ਼ਨ ਦੀ ਮਿਆਦ ਪੁੱਗਣ ਜਾਂ ਅਕਿਰਿਆਸ਼ੀਲ ਕੀਤੇ ਜਾਂ ਰਿਫ੍ਰੈਸ਼-ਬ੍ਰੇਕਰ ਅਸਫਲਤਾ ਦੀ ਗਿਣਤੀ ਕੀਤੇ ਬਿਨਾਂ ਅਯੋਗ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। ਅਸਲ ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰਮਾਣਿਕਤਾ ਅਸਫਲਤਾਵਾਂ ਅਜੇ ਵੀ ਆਮ ਅਸਫਲ ਲੇਖਾਕਾਰੀ, ਘਾਤਕ ਕੂਲਡਾਉਨ ਅਤੇ ਆਮ ਕਲਾਇੰਟ ਗਲਤੀ ਦੀ ਵਰਤੋਂ ਕਰਦੀਆਂ ਹਨ; ਖਾਤਾ ਬੰਦ ਕਰਨਾ ਸਥਾਈ ਰਹਿੰਦਾ ਹੈ। ਐਕਸੈਸ ਟੋਕਨਾਂ ਦੀ ਮਿਆਦ ਪੁੱਗਣ ਤੋਂ ਪਹਿਲਾਂ ਮਾਲਕ ਦੇ ਘੁੰਮਾਏ ਗਏ ਟੋਕਨਾਂ ਨੂੰ ਸਿੰਕ੍ਰੋਨਾਈਜ਼ ਕਰੋ (ਡਿਫੌਲਟ ਪ੍ਰੋਐਕਟਿਵ ਰਿਫਰੈਸ਼ ਲੀਡ ਪੰਜ ਮਿੰਟ ਹੈ), ਜਾਂ Codex ਪ੍ਰਮਾਣੀਕਰਣ ਫਾਈਲ ਨੂੰ ਮੁੜ-ਆਯਾਤ ਕਰੋ। ਪੈਸਿਵ ਆਯਾਤ ਸਪਲਾਈ ਕੀਤੇ ਟੋਕਨਾਂ ਨੂੰ ਟੋਕਨ ਐਂਡਪੁਆਇੰਟ 'ਤੇ ਪ੍ਰਮਾਣਿਤ ਕੀਤੇ ਬਿਨਾਂ ਸਟੋਰ ਕਰਦੇ ਹਨ। ਮੈਨੁਅਲ dashboard/API ਰਿਫਰੈਸ਼ `409 refresh_disabled` ਰਿਟਰਨ ਕਰਦਾ ਹੈ; ਨਵੇਂ OAuth ਲਾਗਇਨ ਬਦਲੇ ਨਹੀਂ ਹਨ। [ਵਾਤਾਵਰਣ ਸੰਦਰਭ](../reference/ENVIRONMENT.md#passive-codex-token-refresh) ਵੇਖੋ.

ਇੱਕ ਨੋਡ ਪ੍ਰਕਿਰਿਆ ਹੈ** ਇੱਕ V8 ਹੀਪ** . ਦੋ ਓਵਰਲੈਪਿੰਗ ~ 3 MiB / ~ 750k-ਟੋਕਨ ਕੋਡਿੰਗ-ਏਜੰਟ `POST /v1/responses` (RTK + Caveman) ਉਸ ਹੀਪ ਨੂੰ ~ 12 Gi (`FATAL ERROR: Reached heap limit`) 'ਤੇ ਛੱਡ ਦਿੰਦੇ ਹਨ ਅਤੇ 16 Gi cgroup ਨੂੰ OOM ਕਰ ਸਕਦੇ ਹਨ। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ਵੇਖੋ। ਉਹ ਮਾਪ ਏ** ਮੈਮੋਰੀ-ਬਜਟ** ਚੇਤਾਵਨੀ, ਦੋ ਸਮਕਾਲੀ ਲੰਬੇ `/v1/responses` ਦਾ ਉਤਪਾਦ ਹਾਰਡ-ਅਧਿਕਤਮ ਨਹੀਂ। ਹੈਵੀਵੇਟ ਚੈਟ ਦਾਖਲਾ ਇੱਕ ਸਵੈ-ਉਤਪੰਨ ਇੰਜੈਸਟ ਬਾਈਟ ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ਦੁਆਰਾ ਉਸੇ V8/cgroup ਸੀਲਿੰਗ — ਦੇ ਆਕਾਰ ਦੁਆਰਾ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ ਜੋ ਪਹਿਲਾਂ ਤੋਂ ਹੀ ਆਕਾਰ ਦੀ ਪ੍ਰਕਿਰਿਆ 'ਤੇ ਇਸ ਨੂੰ ਉੱਪਰ ਵੱਲ (ਜਾਂ ਵਿਰਾਸਤੀ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ਬੇਨਤੀ-ਗਿਣਤੀ ਕੈਪ ਨੂੰ ਸੈਟ ਕਰਨਾ) ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ। ਸਮਾਲ ਚੈਟ, `/healthz`, `/v1/models`, ਅਤੇ MCP ਹਨ** ਨਹੀਂ** ਉਸ ਟੋਪੀ ਵਿੱਚ.

### ਇੱਕ-ਪ੍ਰਕਿਰਿਆ: ਦੋ ਤੋਂ ਵੱਧ ਲੰਬੇ `/v1/responses`

ਏ** ਸਿਹਤਮੰਦ** ਪ੍ਰਕਿਰਿਆ ( `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO` ਦੇ ਹੇਠਾਂ ਹੀਪ, ਡਿਫਾਲਟ `0.75`)** ਹੋ ਸਕਦਾ ਹੈ** ਜਦੋਂ ਪ੍ਰਕਿਰਿਆ-ਵਿਆਪਕ ਇਨਫਲਾਈਟ-ਬਾਈਟ ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ਕੋਲ ਅਜੇ ਵੀ ਜਗ੍ਹਾ ਹੈ ਤਾਂ ਦੋ ਤੋਂ ਵੱਧ ਸਮਕਾਲੀ ਲੰਬੇ `POST /v1/responses` ਚਲਾਓ। `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (ਡਿਫਾਲਟ 256 KiB) 'ਤੇ ਜਾਂ ਇਸ ਤੋਂ ਉੱਪਰ ਦੀਆਂ ਸੰਸਥਾਵਾਂ ਢਾਂਚਾ-ਭਾਰੀ ਬੇਨਤੀਆਂ ਵਾਂਗ ਹੀ ਹੈਵੀਵੇਟ ਲੀਜ਼ ਲੈਂਦੀਆਂ ਹਨ ਅਤੇ ਉਹੀ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` ਐਸਕੇਪ (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ਦੀ ਵਰਤੋਂ ਕਰਦੀਆਂ ਹਨ। ਸਮਕਾਲੀ ਲੰਬੇ SSE ਕਲਾਇੰਟਸ (ਓਪਰੇਟਰਾਂ ਨੂੰ ਅਕਸਰ 40-50 ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ) a** ਮੈਮੋਰੀ-ਬਜਟ** ਸਵਾਲ — ਸਾਈਜ਼ ਹੀਪ + primary/headroom ਸਲਾਟ + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` — ਇੱਕ ਸਖ਼ਤ “ਅਧਿਕਤਮ 2” ਉਤਪਾਦ ਸੀਮਾ ਨਹੀਂ ਹੈ। ਇੱਕ ਦਬਾਅ ਵਾਲਾ ਢੇਰ ਅਜੇ ਵੀ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕਰਨ ਯੋਗ `503` ਨਾਲ ਸ਼ੈੱਡ ਕਰਦਾ ਹੈ ਤਾਂ ਕਿ #7849 ਵਾਪਸ ਨਹੀਂ ਆਉਂਦਾ।

ਸੈਸ਼ਨ-ਤੋਂ-ਖਾਤੇ ਦੀ ਸਾਂਝ ਨੂੰ Redis ਦੁਆਰਾ ਵੀ ਸਾਂਝਾ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ: ਹਰੇਕ ਪ੍ਰਕਿਰਿਆ 'ਤੇ `OMNIROUTE_SESSION_AFFINITY_STORE=redis` ਅਤੇ `REDIS_URL` ਸੈੱਟ ਕਰੋ, ਉਸੇ `REDIS_KEY_PREFIX` ਅਤੇ ਇੱਕ ਸਕਾਰਾਤਮਕ `sessionAffinityTtlMs` ਸੈਟਿੰਗ ਨਾਲ। ਪਿੰਨ ਹਰੇਕ ਪ੍ਰਕਿਰਿਆ ਦੇ ਯੋਗ ਸਥਾਨਕ ਕਨੈਕਸ਼ਨ ਲਈ ਹੈਸ਼ਡ ਵਰਤੋਂ-ਖਾਤਾ ਪਛਾਣਾਂ ਨੂੰ ਹੱਲ ਕਰਦੇ ਹਨ, ਇਸਲਈ ਮੇਲ ਖਾਂਦੇ ਪਛਾਣ ਮੈਟਾਡੇਟਾ ਵਾਲੇ OAuth ਖਾਤਿਆਂ ਨੂੰ ਮੇਲ ਖਾਂਦੇ ਕਨੈਕਸ਼ਨ IDs ਦੀ ਲੋੜ ਨਹੀਂ ਹੁੰਦੀ ਹੈ। ਜਾਣੀ-ਪਛਾਣੀ ਖਾਤਾ ਪਛਾਣ ਪਿੰਨ ਰੈਜ਼ੋਲਿਊਸ਼ਨ ਅਤੇ ਸੁਰੱਖਿਅਤ ਬੇਦਖਲੀ ਵਿੱਚ ਵਿਰੋਧਾਭਾਸੀ ਸਥਾਨਕ IDs ਉੱਤੇ ਪਹਿਲ ਦਿੰਦੀ ਹੈ; ਬਿਨਾਂ ਪਛਾਣ ਦੇ ਰਿਕਾਰਡ (ਜਾਂ ਪਛਾਣ ਤੋਂ ਬਿਨਾਂ ਬੇਦਖਲ ਕਾਲਰ) ਵਿਰਾਸਤੀ ID ਗਾਰਡ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦੇ ਹਨ। ਸਥਿਰ ਵਰਤੋਂ ਪਛਾਣ ਤੋਂ ਬਿਨਾਂ ਖਾਤਿਆਂ ਲਈ ਅਜੇ ਵੀ ਮੇਲ ਖਾਂਦੇ IDs ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ। Redis ਗਲਤੀਆਂ ਜਾਂ 100 ms ਤੋਂ ਵੱਧ ਕਾਲਾਂ ਲੋਕਲ SQLite ਵਿੱਚ ਵਾਪਸ ਆਉਂਦੀਆਂ ਹਨ। ਹਰੇਕ Redis ਐਫੀਨਿਟੀ ਸਟੋਰ ਬਕਾਇਆ ਓਪਰੇਸ਼ਨਾਂ ਨੂੰ 8 'ਤੇ ਕੈਪਸ ਕਰਦਾ ਹੈ, ਜਦੋਂ ਪੂਰਾ ਹੁੰਦਾ ਹੈ ਤਾਂ ਤੁਰੰਤ Redis ਬਾਈਪਾਸ ਕਰਦਾ ਹੈ, ਅਤੇ ਕਾਲਰ ਦੀ ਸਮਾਂ-ਸੀਮਾ 'ਤੇ ਨਹੀਂ, ਅੰਡਰਲਾਈੰਗ ਕੰਮ ਦੇ ਨਿਪਟਾਰੇ 'ਤੇ ਹੀ ਸਲਾਟ ਜਾਰੀ ਕਰਦਾ ਹੈ। ਇੱਕ Redis ਆਊਟੇਜ ਦੇ ਦੌਰਾਨ ਕੋਈ ਸਾਂਝਾ ਸੱਚ ਨਹੀਂ ਹੈ: ਹਰ ਇੱਕ ਉਦਾਹਰਣ ਇਸਦੇ ਆਪਣੇ ਸਥਾਨਕ ਸਬੰਧਾਂ ਵਿੱਚ ਵਾਪਸ ਆਉਂਦੀ ਹੈ, ਸੈਸ਼ਨ ਪ੍ਰਤੀ ਉਦਾਹਰਨ ਵਿੱਚ ਇੱਕ ਵਾਰ ਮੁੜ ਪਿੰਨ ਹੋ ਸਕਦੇ ਹਨ, ਅਤੇ ਉਦਾਹਰਨਾਂ ਵੱਖ ਹੋ ਸਕਦੀਆਂ ਹਨ। ਜਦੋਂ ਇਹ ਠੀਕ ਹੋ ਜਾਂਦੀ ਹੈ ਤਾਂ ਸਟਿੱਕੀਨੇਸ Redis ਰਾਹੀਂ ਮੁੜ-ਇਕਸਾਰ ਹੋ ਜਾਂਦੀ ਹੈ। ਸਮਾਂ ਸਮਾਪਤੀ ਉਡੀਕ ਦੀ ਸੀਮਾ ਹੈ, ਨਾ ਕਿ ਭੇਜੀ ਗਈ EVAL, ਜੋ ਕਿ ਫਾਲਬੈਕ ਤੋਂ ਬਾਅਦ ਉਤਰ ਸਕਦੀ ਹੈ। ਰੂਟਿੰਗ ਰਾਈਟਿੰਗ ਰੂਟਿੰਗ ਫੈਸਲੇ ਦੁਆਰਾ ਨਿਰੀਖਣ ਕੀਤੇ ਗਏ ਸਹੀ ਮੁੱਲ ਦੀ ਤੁਲਨਾ ਕਰਦੇ ਹਨ, ਨਾ ਕਿ ਇੱਕ ਤਾਜ਼ਾ ਪਰਿਵਰਤਨ-ਸਮਾਂ ਪੜ੍ਹਿਆ ਗਿਆ; ਇੱਕ ਨਿਰੀਖਣ ਕੀਤੀ ਮਿਸ ਜਾਂ ਇੱਕ SQLite ਫਾਲਬੈਕ ਨਿਰੀਖਣ ਇੱਕ ਗੈਰਹਾਜ਼ਰ Redis ਕੁੰਜੀ ਵਜੋਂ ਤੁਲਨਾ ਕਰਦਾ ਹੈ। ਪੁਰਾਣੀਆਂ ਪਿੰਨਾਂ ਨੂੰ ਇੱਕ CAS ਵਿੱਚ ਬਦਲਿਆ ਜਾਂਦਾ ਹੈ, ਇਸਲਈ ਇੱਕ ਲੇਟ ਕਮਾਂਡ ਇੱਕ ਨਵੇਂ, ਵੱਖਰੇ ਪਿੰਨ ਨੂੰ ਬਦਲ ਜਾਂ ਮਿਟਾ ਨਹੀਂ ਸਕਦੀ। Redis ਰੀਡ ਪਰਮਾਣੂ ਤੌਰ 'ਤੇ ਮੁੱਲ ਵਾਪਸ ਕਰਦਾ ਹੈ ਅਤੇ ਬਾਕੀ ਸਰਵਰ TTL; ਸਕਾਰਾਤਮਕ PTTL (ਜਾਂ ਕੋਈ ਮਿਆਦ ਨਹੀਂ) ਜੀਵਣਤਾ ਨੂੰ ਨਿਰਧਾਰਤ ਕਰਦੀ ਹੈ, ਨਾ ਕਿ ਲੇਖਕ ਦੀ JSON ਟਾਈਮਸਟੈਂਪ ਜਾਂ ਪਾਠਕ ਦੀ ਘੜੀ। ਸਥਾਨਕ ਸਨੈਪਸ਼ਾਟ ਮੈਪ ਜੋ ਕਿ ਇੱਕ ਸਥਾਨਕ ਡੈੱਡਲਾਈਨ ਤੱਕ TTL ਬਾਕੀ ਹੈ; ਮੌਜੂਦਾ JSON ਕੁੰਜੀਆਂ ਪੜ੍ਹਨਯੋਗ ਰਹਿੰਦੀਆਂ ਹਨ ਅਤੇ ਉਹਨਾਂ ਦੀਆਂ ਕੱਚੀਆਂ ਬਾਈਟਾਂ ਨੂੰ CAS ਲਈ ਬਰਕਰਾਰ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ। Redis ਸੱਚਾਈ ਦਾ ਇੱਕੋ ਇੱਕ ਸਰੋਤ ਹੈ ਜਦੋਂ ਕਿ ਇਹ ਜਵਾਬ ਦਿੰਦਾ ਹੈ। ਪੁਸ਼ਟੀ ਕੀਤੀ ਸ਼ੇਅਰ ਅੱਪਸਰਟ, ਛੂਹ ਅਤੇ ਮਿਟਾਉਣ ਸਥਾਨਕ ਇੰਦਰਾਜ਼ ਨੂੰ ਹਟਾ, ਇਸ ਨੂੰ ਇੰਸਟਾਲ ਜ ਤਾਜ਼ਾ ਨਾ ਕਰੋ. Redis ਮਾਰਗ 'ਤੇ SQLite Redis ਤਰੁਟੀਆਂ, ਸਮਾਂ ਸਮਾਪਤੀ ਜਾਂ ਦਾਖਲਾ ਸੰਤ੍ਰਿਪਤਾ, ਪਹਿਲਾਂ ਵਾਂਗ TTL-ਬਾਊਂਡਡ ਤੋਂ ਸਿਰਫ ਇਸ ਉਦਾਹਰਣ ਦੇ ਆਪਣੇ ਫਾਲਬੈਕ ਫੈਸਲਿਆਂ ਨੂੰ ਰੱਖਦਾ ਹੈ। ਬਾਅਦ ਦੇ ਆਊਟੇਜ 'ਤੇ ਗੁੰਮ ਹੋਏ ਸਥਾਨਕ ਪਿੰਨ ਦੀ ਕੀਮਤ ਇੱਕ ਤਾਜ਼ਾ ਪਿਕ (ਇੱਕ ਪ੍ਰੋਂਪਟ-ਕੈਸ਼ ਮਿਸ) ਹੁੰਦੀ ਹੈ, ਨਾ ਕਿ ਗਲਤ ਜਾਂ ਬੇਦਖਲ ਕੀਤਾ ਖਾਤਾ। ਅਸਵੀਕਾਰ ਕੀਤੇ ਗਏ ਅਪਸਰਟ ਸਾਂਝੇ ਵਿਜੇਤਾ ਅਤੇ ਇਸਦੇ ਬਾਕੀ ਬਚੇ TTL ਪ੍ਰਮਾਣੂ ਰੂਪ ਵਿੱਚ ਵਾਪਸ ਕਰਦੇ ਹਨ: ਆਮ ਚੋਣ ਮੈਪ ਕੀਤੀ ਸਥਾਨਕ ਸਮਾਂ-ਸੀਮਾ ਦੀ ਮੁੜ ਜਾਂਚ ਕਰਦੀ ਹੈ ਅਤੇ ਇੱਕ ਸਥਿਰ-ਜੀਵਨ ਯੋਗ ਵਿਜੇਤਾ ਦੀ ਵਰਤੋਂ ਕਰਦੀ ਹੈ, ਵਰਤੋਂ ਨੂੰ ਛੂਹਦੀ ਹੈ ਅਤੇ ਉਸ ਖਾਤੇ ਲਈ ਕਿਸੇ ਹੋਰ ਸਾਂਝੀ ਲਿਖਤ ਤੋਂ ਬਿਨਾਂ ਲੌਗਿੰਗ ਕਰਦੀ ਹੈ। ਜੇਕਰ ਇਹ ਉਪਲਬਧ ਨਹੀਂ ਹੈ, ਤਾਂ ਚੋਣ ਸਥਾਨਕ ਉਮੀਦਵਾਰ ਨੂੰ ਰੱਖਦੀ ਹੈ, ਸ਼ੇਅਰ ਕੀਤੇ ਪਿੰਨ ਨੂੰ ਬਿਨਾਂ ਕਿਸੇ ਬਦਲਾਅ ਦੇ ਛੱਡਦੀ ਹੈ ਅਤੇ ਇੱਕ ਡੀਬੱਗ ਸੁਨੇਹਾ ਛੱਡਦੀ ਹੈ। ਰੱਦ ਕੀਤਾ CAS SQLite ਨਹੀਂ ਲਿਖਦਾ; Redis ਤਰੁਟੀਆਂ, ਸਮਾਂ ਸਮਾਪਤੀ ਜਾਂ ਦਾਖਲਾ ਸੰਤ੍ਰਿਪਤਾ ਇਸ ਦੀ ਬਜਾਏ ਮੌਜੂਦਾ ਸਥਾਨਕ ਕਾਰਵਾਈ ਨੂੰ ਲਾਗੂ ਕਰਦੇ ਹਨ। ਜੇਕਰ ਇੱਕ ਭੇਜੇ ਗਏ ਪਰਿਵਰਤਨ ਦਾ ਜਵਾਬ ਸਮਾਂ ਸਮਾਪਤ (ਸਵੀਕਾਰ, ਅਸਵੀਕਾਰ ਜਾਂ ਗਲਤੀ) ਤੋਂ ਬਾਅਦ ਆਉਂਦਾ ਹੈ, ਤਾਂ ਇੱਕ ਸਮਕਾਲੀ ਸਹੀ ਸੀਰੀਅਲਾਈਜ਼ਡ-ਮੁੱਲ ਦੀ ਤੁਲਨਾ-ਅਤੇ-ਮਿਟਾਉਣਾ ਸਿਰਫ਼ ਬਾਈਟ-ਸਮਾਨ ਸਮਾਂ ਸਮਾਪਤੀ ਫਾਲਬੈਕ ਕਤਾਰ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ। ਉਸ ਤੁਲਨਾ ਅਤੇ ਮਿਟਾਉਣ ਦੇ ਵਿਚਕਾਰ ਕੋਈ ਉਡੀਕ ਨਹੀਂ ਹੈ; ਇੱਕ ਨਵੀਂ ਆਊਟੇਜ ਰਾਈਟ ਸੁਰੱਖਿਅਤ ਹੈ। ਗਾਰਡਡ ਬੇਦਖਲੀ ਅਸਫਲ ਖਾਤੇ ਦੇ ਆਪਣੇ ਸਥਾਨਕ ਪਿੰਨ ਨੂੰ Redis ਡਾਊਨ ਦੇ ਨਾਲ ਵੀ ਹਟਾ ਦਿੰਦੀ ਹੈ, ਅਤੇ ਪੁਸ਼ਟੀ ਕੀਤੀ ਸ਼ੇਅਰ ਬੇਦਖਲੀ ਤੋਂ ਬਾਅਦ ਇਸਨੂੰ ਦੁਬਾਰਾ ਸਾਫ਼ ਕਰਦੀ ਹੈ। ਬਕਾਇਆ ਪਹਿਲਾਂ ਸਾਂਝੇ ਕੀਤੇ ਜਵਾਬਾਂ ਵਿੱਚ ਇੱਕ ਬੇਦਖਲ ਲੋਕਲ ਪਿੰਨ ਨੂੰ ਬਹਾਲ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ ਕਿਉਂਕਿ ਸਾਂਝੀਆਂ ਸਫਲਤਾਵਾਂ ਕਦੇ ਵੀ SQLite ਨਹੀਂ ਲਿਖਦੀਆਂ ਹਨ। ਇੱਕ ਬਾਅਦ ਵਿੱਚ ਆਊਟੇਜ ਫਾਲਬੈਕ ਇੱਕ ਖਾਤੇ ਨੂੰ ਮੁੜ ਪਿੰਨ ਕਰ ਸਕਦਾ ਹੈ; ਬਾਅਦ ਵਿੱਚ ਸਵੀਕਾਰ ਕੀਤਾ ਸਾਂਝਾ ਰਾਈਟ ਸਿਰਫ Redis ਵਿੱਚ ਮੌਜੂਦ ਹੈ। Redis misses ਸਥਾਨਕ ਫਾਲਬੈਕ ਸਟੇਟ ਨਾਲ ਸਲਾਹ ਨਾ ਕਰੋ। ਡਰਾਈਵਰ ਬੰਦ ਹੋਣ ਦੇ ਨਾਲ, ਨਵੇਂ ਚੁਣੇ ਗਏ ਪਿੰਨ ਵਿਰਾਸਤੀ ਚਾਰ-ਫੀਲਡ SQLite JSON ਸ਼ਕਲ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦੇ ਹਨ; ਸਿਰਫ਼ Redis ਰਾਊਟਿੰਗ ਹੈਸ਼ਡ ਖਾਤੇ ਦੀ ਪਛਾਣ ਨੂੰ ਜੋੜਦੀ ਹੈ। ਪ੍ਰੀਫੈਚ ਕੀਤੇ ਪਿੰਨਾਂ ਦੀ ਉਹਨਾਂ ਦੀ ਮਿਆਦ ਪੁੱਗਣ ਵਾਲੀ ਸੀਮਾ 'ਤੇ ਮੁੜ ਜਾਂਚ ਕੀਤੀ ਜਾਂਦੀ ਹੈ। Redis ਗੈਰ-ਲੀਜ਼ ਚੋਣ ਸਟੋਰ ਨੂੰ ਮੁੜ-ਪੜ੍ਹਦੀ ਹੈ, ਪਰ ਸਮਕਾਲੀ ਲੀਜ਼ ਯੋਜਨਾ ਅਜੇ ਵੀ ਪ੍ਰੀਫੈਚ ਅਤੇ ਯੋਜਨਾਬੰਦੀ (ਇੱਕ ਸਵੀਕਾਰ ਕੀਤੀ ਸਰਬੋਤਮ ਕੋਸ਼ਿਸ਼ ਵਿੰਡੋ) ਦੇ ਵਿਚਕਾਰ ਬੇਦਖਲ ਕੀਤੇ ਪਿੰਨ ਦੀ ਵਰਤੋਂ ਕਰ ਸਕਦੀ ਹੈ। ਇੱਕ ਟਿਕਾਊ ਦਾਅਵੇ ਤੋਂ ਬਾਅਦ ਇੱਕ ਲੀਜ਼ ਪ੍ਰਤੀਬੱਧਤਾ ਖਾਤਿਆਂ ਨੂੰ ਬਦਲ ਨਹੀਂ ਸਕਦੀ: ਅਸਵੀਕਾਰ ਕੀਤੇ ਜਾਣ 'ਤੇ ਇਹ ਦਾਅਵਾ ਕੀਤੇ ਉਮੀਦਵਾਰ ਨੂੰ ਸਿਰਫ਼ ਉਸ ਬੇਨਤੀ ਲਈ ਰੱਖਦਾ ਹੈ ਅਤੇ ਸਾਂਝੇ ਵਿਜੇਤਾ ਨੂੰ ਅਛੂਤਾ ਛੱਡਦਾ ਹੈ, ਇਸਲਈ ਸਥਿਤੀਆਂ ਵਿੱਚ ਸਮਝੌਤਾ ਉਸ ਮਾਰਗ 'ਤੇ ਸੀਮਾ ਹੈ। ਬਾਕੀ ਦੀ ਸਾਰਣੀ ਅਜੇ ਵੀ ਲਾਗੂ ਹੁੰਦੀ ਹੈ: ਇਹ ਕੰਬੋ ਸੈਸ਼ਨ ਸਟਿੱਕੀਨੇਸ, ਨੇਟਿਵ Codex ਟਰਨ ਪਿੰਨ, ਖਾਤਾ ਸੇਮਫੋਰਸ, ਲਾਕਆਉਟ, ਖਰਚ ਸੀਮਾਵਾਂ, ਕੌਂਫਿਗਰੇਸ਼ਨ ਜਾਂ ਕਾਲ ਲੌਗ ਨੂੰ ਸਾਂਝਾ ਨਹੀਂ ਕਰਦਾ ਹੈ।

ਹਾਰਡਵੇਅਰ: ਪ੍ਰਤੀ-ਉਦਹਾਰਨ ਸਮਕਾਲੀ ਲੰਬਾ `/v1/responses` ਹੈ** ਮੈਮੋਰੀ-ਬਜਟ** ਸਵਾਲ (ਹੀਪ + ਇਨਫਲਾਈਟ-ਬਾਈਟ / #10110)। `N` ਸੁਤੰਤਰ `DATA_DIR` s ਅਜੇ ਵੀ ਗੁਣਾ ਢੇਰ: ਹੋਸਟ RAM `N × cgroup` ਕਵਰ ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ, ਨਾ ਕਿ “N = 8 ਦੇ ਨਾਲ ਇੱਕ 16 Gi ਪੌਡ।” ਇੱਕ SQLite ਫਾਈਲ 'ਤੇ ਕਦੇ ਵੀ `replicas > 1` ਨਾ ਕਰੋ।

ਸਕੈਚ ਲਿਖੋ (ਦੋ ਢੇਰ, ਦੋ ਖੰਡ — `deploy.replicas: 2` ਨਹੀਂ):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

ਇਨ-ਪ੍ਰੋਸੈਸ ਘਣਤਾ ( HTTP ਆਈਸੋਲੇਟ ਤੋਂ ਕੰਪਰੈਸ਼ਨ) [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023) ਹੈ। ਸ਼ੇਅਰਡ ਡਿਊਰੇਬਲ ਸਟੇਟ ਉੱਤੇ ਇੱਕ ਲਾਜ਼ੀਕਲ ਕਲੱਸਟਰ [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ਹੈ।

IPv4/IPv6 ਕਨੈਕਟਿਵਿਟੀ, VPN ਰੂਟਿੰਗ ਅਤੇ ਸੰਰਚਿਤ ਪ੍ਰਾਕਸੀਆਂ ਵੱਖਰੀਆਂ ਹੋ ਸਕਦੀਆਂ ਹਨ।
[Google ਦੇ ਸਮਰਥਿਤ ਖੇਤਰਾਂ](https://ai.google.dev/gemini-api/docs/available-regions)
ਦੇ ਨਾਲ-ਨਾਲ ਅਸਲ ਕਨੈਕਸ਼ਨ ਰੂਟ ਦੀ ਵੀ ਜਾਂਚ ਕਰੋ; ਸਿਰਫ਼ ਇਹ ਤਰੁੱਟੀ ਕਿਸੇ ਖ਼ਰਾਬ API ਕੁੰਜੀ ਦੀ ਪਛਾਣ ਨਹੀਂ ਕਰਦੀ।

### ਕਨੈਕਸ਼ਨ-ਵਿਸ਼ੇਸ਼ ਪ੍ਰਾਕਸੀ ਨੂੰ ਤਰਜੀਹ ਦਿਓ

ਪ੍ਰਭਾਵਿਤ Gemini ਕਨੈਕਸ਼ਨ ਲਈ OmniRoute ਦੀ
[ਪ੍ਰਤੀ-ਕਨੈਕਸ਼ਨ ਪ੍ਰਾਕਸੀ ਸੰਰਚਨਾ](../ops/PROXY_GUIDE.md#4-level-proxy-system)
ਵਰਤੋ, ਫਿਰ ਉਸੇ ਮਾਡਲ ਨਾਲ **ਕਨੈਕਸ਼ਨ ਦੀ ਜਾਂਚ ਕਰੋ** ਅਤੇ ਇੱਕ ਛੋਟੀ ਬੇਨਤੀ ਦੁਹਰਾਓ।
ਇਸ ਨਾਲ ਰੂਟਿੰਗ ਤਬਦੀਲੀ ਉਸੇ ਕਨੈਕਸ਼ਨ ਤੱਕ ਸੀਮਿਤ ਰਹਿੰਦੀ ਹੈ। ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰਾਕਸੀ ਤੱਕ
ਕੰਟੇਨਰ ਤੋਂ ਪਹੁੰਚਿਆ ਜਾ ਸਕਦਾ ਹੈ ਅਤੇ ਕਨੈਕਸ਼ਨ ਵਾਸਤਵ ਵਿੱਚ ਉਸੇ ਨੂੰ ਚੁਣਦਾ ਹੈ।
ਰੂਟ ਬਦਲਣ ਨਾਲ ਅੱਪਸਟ੍ਰੀਮ ਖੇਤਰੀ ਯੋਗਤਾ ਦੀ ਗਾਰੰਟੀ ਨਹੀਂ ਮਿਲਦੀ।

### ਹੋਸਟ ਅਤੇ ਕੰਟੇਨਰ ਨੈੱਟਵਰਕਿੰਗ ਦੀ ਤੁਲਨਾ ਕਰੋ

ਪ੍ਰਮਾਣਿਤ ਨਤੀਜਿਆਂ ਦੀ ਤੁਲਨਾ ਕਰਦੇ ਸਮੇਂ ਕੁੰਜੀ, ਮਾਡਲ ਅਤੇ ਬੇਨਤੀ ਇੱਕੋ ਜਿਹੇ ਰੱਖੋ; ਕਿਸੇ ਮੁੱਦੇ ਵਿੱਚ
ਕਦੇ ਵੀ ਪ੍ਰਮਾਣ-ਪੱਤਰ, ਪ੍ਰਾਕਸੀ ਪਾਸਵਰਡ ਜਾਂ ਪੂਰੇ ਪ੍ਰਮਾਣੀਕਰਨ ਹੈਡਰ ਪੇਸਟ ਨਾ ਕਰੋ।
ਪਹਿਲਾਂ ਜਾਂਚੋ ਕਿ OS ਰਿਜ਼ਾਲਵਰ ਕਿਹੜੇ ਐਡਰੈੱਸ ਪਰਿਵਾਰ ਪੇਸ਼ ਕਰਦਾ ਹੈ, ਹੋਸਟ ਅਤੇ
ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਇੱਕੋ ਕਮਾਂਡ ਵਰਤਦੇ ਹੋਏ:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute` ਨੂੰ ਉਸ ਸੇਵਾ ਨਾਲ ਬਦਲੋ ਜੋ ਤੁਸੀਂ ਚਲਾਉਂਦੇ ਹੋ (ਉਦਾਹਰਨ ਲਈ, `omniroute-web`)।
ਇਹ ਕਮਾਂਡਾਂ ਪ੍ਰਮਾਣ-ਪੱਤਰਾਂ ਜਾਂ IP ਐਡਰੈੱਸਾਂ ਤੋਂ ਬਿਨਾਂ ਐਡਰੈੱਸ ਪਰਿਵਾਰ ਪ੍ਰਿੰਟ ਕਰਦੀਆਂ ਹਨ।
ਵਾਪਸ ਆਇਆ `6` ਸਿਰਫ਼ IPv6 DNS ਨਤੀਜਾ ਦਰਸਾਉਂਦਾ ਹੈ: ਇਹ ਵਰਤਣਯੋਗ IPv6 ਰੂਟ ਜਾਂ
API ਪਹੁੰਚ ਨੂੰ **ਸਾਬਤ ਨਹੀਂ** ਕਰਦਾ। ਜਿੱਥੇ `curl` ਇੰਸਟਾਲ ਹੈ, ਦੋਵੇਂ ਵਾਤਾਵਰਨਾਂ ਵਿੱਚ
`curl -4 -I https://generativelanguage.googleapis.com` ਦੀ ਤੁਲਨਾ
`curl -6 -I https://generativelanguage.googleapis.com` ਨਾਲ ਕਰੋ।
HTTP ਜਵਾਬ ਉਸ ਜਾਂਚ ਲਈ ਕਨੈਕਟਿਵਿਟੀ ਸਾਬਤ ਕਰਦਾ ਹੈ, ਭਾਵੇਂ ਉਹ ਗੈਰ-ਪ੍ਰਮਾਣਿਤ
ਤਰੁੱਟੀ ਹੋਵੇ; ਕੇਵਲ ਪ੍ਰਮਾਣਿਤ ਮਾਡਲ ਬੇਨਤੀ ਹੀ Gemini ਯੋਗਤਾ ਦੀ ਜਾਂਚ ਕਰਦੀ ਹੈ।

### ਹੋਸਟ-ਪੱਧਰੀ ਵਿਕਲਪ: ਕਾਰਜਸ਼ੀਲ IPv6 ਅਤੇ ਰਿਜ਼ਾਲਵਰ ਨੀਤੀ

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762) ਦੇ ਰਿਪੋਰਟਰ ਨੇ
ਆਪਣੇ ਵਾਤਾਵਰਨ ਵਿੱਚ ਕੰਟੇਨਰ IPv6 ਸਮਰੱਥ ਕਰਕੇ ਅਤੇ glibc ਐਡਰੈੱਸ ਚੋਣ ਬਦਲ ਕੇ ਪਹੁੰਚ
ਮੁੜ ਬਹਾਲ ਕੀਤੀ। ਇਸਨੂੰ ਵਾਤਾਵਰਨ-ਵਿਸ਼ੇਸ਼ ਵਿਕਲਪ ਵਜੋਂ ਲਓ। ਰਿਜ਼ਾਲਵਰ ਤਰਜੀਹਾਂ ਬਦਲਣ ਤੋਂ ਪਹਿਲਾਂ
ਕਾਰਜਸ਼ੀਲ ਹੋਸਟ IPv6, ਕੰਟੇਨਰ ਈਗ੍ਰੈੱਸ/ਰੂਟਿੰਗ ਅਤੇ ਫਾਇਰਵਾਲ ਨਿਯਮਾਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ।
ਆਪਣੇ ਆਪ ਵਿੱਚ ਇੱਕ ਨਿੱਜੀ ULA ਐਡਰੈੱਸ ਜਨਤਕ IPv6 ਕਨੈਕਟਿਵਿਟੀ ਸਥਾਪਿਤ ਨਹੀਂ ਕਰਦਾ।

Compose ਦੇ ਡਿਫਾਲਟ ਨੈੱਟਵਰਕ ਨਾਲ ਪਹਿਲਾਂ ਹੀ ਜੁੜੀਆਂ ਸੇਵਾਵਾਂ ਲਈ, ਇਹ ਫ੍ਰੈਗਮੈਂਟ
ਉਸ ਨੈੱਟਵਰਕ ਉੱਤੇ IPv6 ਸਮਰੱਥ ਕਰਦਾ ਹੈ; ਆਪਣੀ ਸੇਵਾ, ਪੋਰਟਾਂ, ਵਾਲੀਅਮਾਂ ਅਤੇ ਸੰਰਚਨਾ ਦਾ
ਬਾਕੀ ਹਿੱਸਾ ਬਰਕਰਾਰ ਰੱਖੋ:

```yaml
networks:
  default:
    enable_ipv6: true
```

ਨਾਮਿਤ ਨੈੱਟਵਰਕ ਲਈ, ਇਸਨੂੰ ਉਸ ਨੈੱਟਵਰਕ ਉੱਤੇ ਸਮਰੱਥ ਕਰੋ ਜਿਸ ਨਾਲ ਸੇਵਾ ਵਾਸਤਵ ਵਿੱਚ ਜੁੜਦੀ ਹੈ।
Docker ਇੱਕ ULA ਸਬਨੈੱਟ ਨਿਰਧਾਰਤ ਕਰ ਸਕਦਾ ਹੈ; ਸਪਸ਼ਟ, ਨਾ-ਓਵਰਲੈਪ ਹੋਣ ਵਾਲਾ ਸਬਨੈੱਟ
ਸਿਰਫ਼ ਉਦੋਂ ਚੁਣੋ ਜਦੋਂ ਤੁਹਾਡੇ ਨੈੱਟਵਰਕ ਨੂੰ ਇਸਦੀ ਲੋੜ ਹੋਵੇ।
[Docker IPv6 ਨੈੱਟਵਰਕਿੰਗ](https://docs.docker.com/engine/daemon/ipv6/)
ਅਤੇ [Compose ਨੈੱਟਵਰਕ ਵਿਕਲਪ](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) ਵੇਖੋ।

ਇੱਕ **glibc-ਅਧਾਰਿਤ ਇਮੇਜ** ਉੱਤੇ, `/etc/gai.conf` ਐਡਰੈੱਸ ਚੋਣ ਨੂੰ ਬਦਲ ਸਕਦੀ ਹੈ।
ਮੌਜੂਦਾ ਰਿਪੋਜ਼ਟਰੀ Dockerfile Debian ਵਰਤਦੀ ਹੈ; ਕਸਟਮ musl-ਅਧਾਰਿਤ ਇਮੇਜਾਂ ਇਹ ਪ੍ਰਣਾਲੀ
ਸਾਂਝੀ ਨਹੀਂ ਕਰਦੀਆਂ। ਰਿਪੋਰਟ ਕੀਤੀ ਤਬਦੀਲੀ ULA ਲੇਬਲ ਨੂੰ `label fc00::/7 6` ਤੋਂ
`label fc00::/7 1` ਵਿੱਚ ਬਦਲਦੀ ਹੈ। ਇਮੇਜ ਦੀ ਪੂਰੀ ਨੀਤੀ ਸਾਰਣੀ ਤੋਂ ਸ਼ੁਰੂ ਕਰੋ ਅਤੇ ਇਸ ਦੀਆਂ
ਹੋਰ ਐਂਟਰੀਆਂ ਨੂੰ ਸੁਰੱਖਿਅਤ ਰੱਖੋ: ਇੱਕ `label` ਜਾਂ `precedence` ਐਂਟਰੀ ਜੋੜਨ ਨਾਲ ਉਹ
ਡਿਫਾਲਟ ਸਾਰਣੀ ਬਦਲ ਜਾਂਦੀ ਹੈ, ਇਸ ਲਈ ਸਿਰਫ਼ ਬਦਲੀ ਹੋਈ ਲਾਈਨ ਵਾਲੀ ਫਾਇਲ ਕਾਫ਼ੀ ਨਹੀਂ ਹੈ।
[glibc ਸੰਰਚਨਾ ਹਵਾਲਾ](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
ਉਨ੍ਹਾਂ ਅਰਥ-ਨਿਯਮਾਂ ਦਾ ਦਸਤਾਵੇਜ਼ੀਕਰਨ ਕਰਦਾ ਹੈ। ਸਮੀਖਿਆ ਕੀਤੀ ਫਾਇਲ ਨੂੰ `/etc/gai.conf`
ਉੱਤੇ ਸਿਰਫ਼-ਪੜ੍ਹਨਯੋਗ ਢੰਗ ਨਾਲ ਬਾਈਂਡ-ਮਾਊਂਟ ਕਰੋ ਅਤੇ ਇਸਨੂੰ ਲਾਗੂ ਕਰਨ ਲਈ ਸੇਵਾ ਮੁੜ ਬਣਾਓ।

ਇਹ ਉਸ ਕੰਟੇਨਰ ਦੇ **ਸਾਰੇ ਆਉਟਬਾਊਂਡ ਟ੍ਰੈਫਿਕ** ਲਈ OS ਐਡਰੈੱਸ ਚੋਣ ਬਦਲਦਾ ਹੈ।
ਇਹ ਹਰ ਐਪਲੀਕੇਸ਼ਨ ਨੂੰ IPv6 ਚੁਣਨ ਲਈ ਮਜਬੂਰ ਨਹੀਂ ਕਰਦਾ: Node ਦਾ DNS ਕ੍ਰਮ ਅਤੇ
ਕਨੈਕਸ਼ਨ ਚੋਣ ਵੀ ਮਹੱਤਵਪੂਰਨ ਹਨ। ਖ਼ਾਸ ਤੌਰ ਉੱਤੇ, `--dns-result-order=ipv4first`
IPv4 ਨੂੰ ਤਰਜੀਹ ਦਿੰਦਾ ਹੈ ਅਤੇ IPv4-ਮਾਤਰ ਅਸਫਲਤਾ ਲਈ ਉਪਾਅ ਨਹੀਂ ਹੈ।
[Node DNS ਕ੍ਰਮ](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) ਵੇਖੋ।

ਹੋਸਟ-ਪੱਧਰੀ ਕਿਸੇ ਵੀ ਤਬਦੀਲੀ ਤੋਂ ਬਾਅਦ Gemini ਅਤੇ ਆਪਣੇ ਹੋਰ ਪ੍ਰਦਾਤਾਵਾਂ ਦੀ ਮੁੜ ਜਾਂਚ ਕਰੋ।
ਵਾਪਸ ਪਿਛਲੀ ਸਥਿਤੀ ਵਿੱਚ ਜਾਣ ਲਈ, ਕਸਟਮ `gai.conf` ਮਾਊਂਟ ਹਟਾਓ, ਪਿਛਲੀ ਨੈੱਟਵਰਕ ਸੰਰਚਨਾ
ਮੁੜ ਬਹਾਲ ਕਰੋ ਅਤੇ ਰੱਖ-ਰਖਾਅ ਅੰਤਰਾਲ ਦੌਰਾਨ ਪ੍ਰਭਾਵਿਤ ਸੇਵਾ/ਨੈੱਟਵਰਕ ਨੂੰ ਮੁੜ ਬਣਾਓ।
ਨੈੱਟਵਰਕ ਮੁੜ ਬਣਾਉਣ ਨਾਲ ਇਸ ਨਾਲ ਜੁੜੇ ਹੋਰ ਕੰਟੇਨਰਾਂ ਵਿੱਚ ਵਿਘਨ ਪੈ ਸਕਦਾ ਹੈ;
ਸਥਾਈ ਡਾਟਾ ਵਾਲੀਅਮ ਨੂੰ ਨਾ ਮਿਟਾਓ।

## ਮਹੱਤਵਪੂਰਨ ਨੋਟਸ

- **SQLite WAL ਮੋਡ:** `docker stop` ਨੂੰ ਪੂਰਾ ਹੋਣ ਦਿਓ ਤਾਂ ਜੋ OmniRoute ਨਵੀਨਤਮ ਤਬਦੀਲੀਆਂ ਨੂੰ ਵਾਪਸ `storage.sqlite` ਵਿੱਚ ਚੈਕਪੌਇੰਟ ਕਰ ਸਕੇ। ਨਾਲ ਸ਼ਾਮਲ Compose ਫ਼ਾਈਲਾਂ ਵਿੱਚ ਪਹਿਲਾਂ ਹੀ 40s ਦੀ ਸਟਾਪ ਗ੍ਰੇਸ ਮਿਆਦ ਸੈੱਟ ਕੀਤੀ ਹੋਈ ਹੈ। ਜੇ ਤੁਸੀਂ ਇਮੇਜ ਨੂੰ ਸਿੱਧਾ ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ `--stop-timeout 40` ਨੂੰ ਬਰਕਰਾਰ ਰੱਖੋ।
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ਜੇ ਨਿਯਮਤ/ਲਿਖਣ ਤੋਂ ਪਹਿਲਾਂ ਵਾਲੇ ਬੈਕਅੱਪ ਬਾਹਰੀ ਤੌਰ 'ਤੇ ਪ੍ਰਬੰਧਿਤ ਕੀਤੇ ਜਾਂਦੇ ਹਨ, ਤਾਂ ਇਸ ਨੂੰ `true` 'ਤੇ ਸੈੱਟ ਕਰੋ। ਮੌਜੂਦਾ ਡੇਟਾਬੇਸ ਦੀਆਂ ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ ਲਈ ਫਿਰ ਵੀ ਆਪਣਾ ਟਿਕਾਊ ਸੁਰੱਖਿਆ ਸਨੈਪਸ਼ਾਟ ਅਤੇ ਵਿਆਪਕ ਮਾਈਗ੍ਰੇਸ਼ਨ ਗਾਰਡ ਲੋੜੀਂਦਾ ਹੈ।
- **ਡੇਟਾ ਸਥਿਰਤਾ:** ਕੰਟੇਨਰ ਰੀਸਟਾਰਟਾਂ ਦੌਰਾਨ ਆਪਣੇ ਡੇਟਾਬੇਸ, ਕੁੰਜੀਆਂ ਅਤੇ ਸੰਰਚਨਾਵਾਂ ਨੂੰ ਕਾਇਮ ਰੱਖਣ ਲਈ ਹਮੇਸ਼ਾ `/app/data` 'ਤੇ ਇੱਕ ਵਾਲਿਊਮ ਮਾਊਂਟ ਕਰੋ।
- **ਪੋਰਟ ਸੰਰਚਨਾ:** ਡਿਫੌਲਟ `20128` ਪੋਰਟ ਨੂੰ ਬਦਲਣ ਲਈ `PORT` ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ ਨੂੰ ਓਵਰਰਾਈਡ ਕਰੋ।
