## आढावा

कोटा शेअरिंग इंजिन प्रदात्याचा कालावधी-आधारित कोटा (उदा. Codex
ची 5-तासांची विंडो, Kimi 1500 req/h) समान कनेक्शन सामायिक करणाऱ्या अनेक API
कींमध्ये न्याय्य रीतीने वितरित करते.

**हे सोडवत असलेली समस्या:** OmniRoute एकाच अपस्ट्रीम प्रदाता खात्यासाठी अनेक API
की प्रॉक्सी करते. सामायिकरणाचे तर्कशास्त्र नसल्यास, की A कडून अचानक मोठ्या प्रमाणात आलेल्या विनंत्या
त्या तासासाठीचा प्रदाता कोटा संपवू शकतात, ज्यामुळे विंडो रीसेट होईपर्यंत की B आणि C अवरोधित राहतात.
इंजिन हे पुढील प्रकारे प्रतिबंधित करते:

1. प्रत्येक परिमाणासाठी (%, विनंत्या, टोकन, $) प्रत्येक कीच्या रोलिंग वापराचा मागोवा घेणे.
2. कार्य-संरक्षण करणारा न्याय्य-वाटा अल्गोरिदम लागू करणे: जागतिक पूल संतृप्त नसताना की निष्क्रिय
   वाट्यांमधून उधार घेऊ शकते.
3. विनंती अपस्ट्रीम एक्झिक्युटरपर्यंत पोहोचण्यापूर्वी हॉट पाथमध्ये (`chatCore.ts`) परिणामाची
   अंमलबजावणी करणे.

## अल्गोरिदम: फेअर-शेअर वर्क-संवर्धन

`src/lib/quota/fairShare.ts` मध्ये लागू केले.

### मोड्स

| अट                                         | मोड      | वागणूक                                         |
| ------------------------------------------ | -------- | ---------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **उदार** | की जागतिक मर्यादेपर्यंत उधार घेऊ शकते वजा-एकूण |
| `globalUsedPercent >= saturationThreshold` | **कडक**  | वैयक्तिक न्याय्य वाटा काटेकोरपणे लागू करा      |

डीफॉल्ट `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`).

हे दोन मोड डीफॉल्ट कर्ज मोड, `saturation` मधील पूलचे वर्णन करतात. `consent` मोडमधील पूल नेहमीच कठोर नियम लागू करतो, संपृक्तता काहीही असो. [संमती कर्ज (प्रति-पूल ऑप्ट-इन)](#consented-lending-per-pool-opt-in) पहा.

### प्रति-परिमाण निर्णय

पूलमधील प्रत्येक सक्रिय परिमाणासाठी, इंजिन गणना करते:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

`percent` परिमाणांसाठी, `consumed` त्याऐवजी विशेषता पुस्तकातून येतो ( [टक्के परिमाणे: प्रति-की विशेषता](#percent-dimensions-per-key-attribution) पहा).

मग:

- **`policy = hard`** : `consumed > fairShareAllowed` आणि मोड कठोर → असल्यास** ब्लॉक** .
- **`policy = soft`** : `consumed > fairShareAllowed` आणि मोड कठोर → असल्यास** दंड करणे** (कॉम्बोमध्ये वंचित ठेवा; कधीही हार्ड-ब्लॉक).
- **`policy = burst`** : योग्य शेअरची पर्वा न करता जागतिक हेडरूम अस्तित्वात असताना अनुमती द्या.

### कॅप निरपेक्ष

वाटपावरील `capValue` + `capUnit` ही एक कठोर मर्यादा आहे जी मोड किंवा पॉलिसीपासून स्वतंत्र आहे. कोणताही परिमाण जेथे नेहमी `consumed >= capValue`** ब्लॉक** विनंती. `percent` कॅपसाठी, `consumed` हा फक्त कीला दिलेला भाग आहे.

### बहु-आयामी तपासणी

जर एक विनंती अवरोधित केली आहे** कोणतेही** पूलमधील परिमाण ते अवरोधित करेल. परिमाणे स्वतंत्र — आहेत आणि 5h% थकवा साप्ताहिक% परिमाण प्रभावित करत नाही.

### कर्ज घेणे

उदार मोडमध्ये, एक की ज्याचे वाटप कमी-उपभोग घेतलेले आहे, ती इतर कीच्या न वाटप केलेल्या शेअर्समधील अधिशेष वापरू शकते. सूत्र आहे:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

कुठे `consumedByOtherKeys = consumedTotal - consumedByThisKey` टेटो ग्लोबल (त्या परिमाणासाठी पूल `limit` ) नेहमीच कठोर कमाल मर्यादा असते.

### संमतीकृत कर्ज (प्रति-पूल निवड)

प्रत्येक पूलमध्ये कर्ज घेण्याची पद्धत असते. `saturation` डीफॉल्ट आहे आणि वरील नियम ठेवते. `consent` मोडमध्ये `hard` की त्याचा वाटा इतर किल्यांनी उधार देण्यास सहमती दर्शविल्याच्या क्षमतेतच पास करते. प्रशासक प्रत्येक पूलचा मोड सेट करतो. प्रत्येक की धारक [कर्ज देण्याच्या संमतीद्वारे](#lending-consent) त्यांची स्वतःची संमती निश्चित करतो.

संमती म्हणजे 0 ते 100 पर्यंतची टक्केवारी आणि युग मिलिसेकंदांमधील पर्यायी अंतिम मुदत. की अंतिम मुदत भविष्यात असताना त्याच्या निष्क्रिय शेअरची टक्केवारी देते.

एका परिमाणासाठी, `L` ही प्रभावी मर्यादा आहे: योजना मर्यादा पूलमधील खात्यांच्या वेळा. विनंती करणाऱ्या कीसाठी गेट गणना करते:

```
share_k         = w_k / 100 × L
idle_k          = max(0, share_k − consumed_k)
lent            = Σ over the other keys of lend_k / 100 × idle_k
taken           = Σ over the other keys of max(0, consumed_k − share_k)
borrowAvailable = max(0, lent − taken)
```

`w_k` हे कीचे वजन आहे, किंवा 0 पेक्षा जास्त वजन नसताना प्रत्येक कीसाठी `100 / n` `lend_k` ही कीची सक्रिय टक्केवारी आहे, आणि 0 एकदा त्याची अंतिम मुदत संपल्यानंतर. विनंती करणाऱ्या कीची स्वतःची संमती कधीही मोजली जात नाही. एकदा `hard` की तिचा वापर त्याच्या समभाग आणि `borrowAvailable` वर पोहोचल्यावर ती नाकारली जाते.

कोणत्याही वाटपाचा दावा नसलेली क्षमता (वजनाची बेरीज 100 वजा) उधारी नाही. कोणतीही चावी उधार देण्याचे मान्य केले नाही.

**उदाहरण.** `L` 1000 आहे.

| की  | वजन | शेअर करा | सेवन केले | उधार देतो |
| --- | --- | -------- | --------- | --------- |
| ए   | 50  | 500      | 530       | 0%        |
| बी  | 30  | 300      | 100       | 50%       |
| सी  | 0   | 0        | 60        | 0%        |

- B त्याच्या निष्क्रिय 200 पैकी 50% उधार देतो, जे 100 आहे. C ने आधीच त्याचा हिस्सा 60 वर घेतला आहे. A 40 कर्ज घेऊ शकते.
- A 530 वर दिला जातो आणि एकदा त्याचा वापर 540 वर पोहोचल्यानंतर नाकारला जातो.
- C ने काहीही वापरण्यापूर्वी, A सोबत किंवा त्याच्या शेअरखाली, C 100 कर्ज घेऊ शकतो.
- C ने काहीही वापरण्यापूर्वी, A सह 530 वर, C 70 उधार घेऊ शकतो.

**शून्य वजन.** वजन 0 असलेल्या किल्लीचा वाटा 0 असतो. ती फक्त तेव्हाच दिली जाते जेव्हा तिचा वापर इतरांनी दिलेल्या कर्जापेक्षा कमी असतो. जेव्हा कोणीही कर्ज देत नाही, तेव्हा त्याची पहिली विनंती नाकारली जाते.

**मुदती.** कोणतेही पार्श्वभूमी कार्य संमती कालबाह्य होत नाही. प्रत्येक विनंती अंतिम मुदतीची त्याच्या स्वतःच्या वेळेशी तुलना करते आणि त्या वेळेइतकी अंतिम मुदत निघून गेली आहे. संचयित केलेली अंतिम मुदत जी मर्यादित संख्या नाही किंवा `Date` धारण करू शकणाऱ्या सर्वात मोठ्या तारखेच्या ओलांडली आहे, ती पास झाली म्हणून मोजली जाते.

**`soft` आणि `burst`.** कर्ज देणे त्यांना मर्यादित करत नाही. `soft` की एकदा तिचा हिस्सा संपल्यानंतर वंचित केली जाते. पूलमध्ये खोली असताना `burst` की पास होते. पूलची एकूण मर्यादा त्याच्या मर्यादेपर्यंत पोहोचली की पूल कमाल मर्यादा अजूनही प्रत्येक की नाकारते.

**विनंती मार्गावरील खर्च.** `saturation` पूल पूर्वीपेक्षा अधिक काही वाचत नाही. `consent` पूलमध्ये, मोजता येण्याजोगा परिमाण फक्त `hard` की त्याच्या शेअरवर किंवा त्यावरील इतर की वाचतो तर दुसरी की उधार देते. ते नंतर समांतरपणे, प्रति इतर की एक वाचन करते. एक अयशस्वी वाचन त्या की साठी 0 चा वापर म्हणून मोजले जाते. एक `percent` परिमाण कोणतेही वाचन जोडत नाही, कारण विशेषता पुस्तकात प्रत्येक की असते.

**पूल संपादित करणे.** संपादन किल्याची संमती ठेवते जी राहते. हे वाटप संपादने, गट-व्यापी बदली आणि `ensure` कॉलसाठी धारण करते. काढलेली की तिची संमती गमावते आणि परत जोडलेली की 0 पासून सुरू होते. प्रशासक मार्ग प्रत्येक कीची संमती परत करतात आणि ती कधीही लिहित नाहीत. पूल परत `saturation` वर स्विच करणे प्रत्येक संग्रहित संमती ठेवते, ज्याचा त्या मोडमध्ये कोणताही परिणाम होत नाही. पूल पुन्हा `consent` वर स्विच केल्याने संचयित संमती पुन्हा सक्रिय होतात ज्यांची अंतिम मुदत गेली नाही. की धारक कोणत्याही मोडमध्ये संग्रहित संमती साफ करू शकतो.

**अपग्रेड करत आहे.** स्तंभ `lending_percent` आणि `lending_until` आधीपासून अस्तित्वात असल्यास, स्थलांतर केवळ `borrow_mode` जोडते आणि संग्रहित टक्केवारी जशी आहे तशीच राहते. प्रत्येक पूल `saturation` मोडमध्ये सुरू होतो. पूल विझार्डमध्ये प्रति पूल `consent` चालू करा. संग्रहित मूल्यांवरून काहीही अनुमान काढले जात नाही.

**मर्यादा.**

- सावकार स्वतःचा हिस्सा वापरण्यापूर्वी त्याच्या कमाल मर्यादेवर पूल शोधू शकतो. इतरांनी उधार घेतलेली क्षमता ही पूलच्या एकूण संख्यामध्ये मोजली जाते.
- चेक विनंतीपूर्वी चालतो आणि काहीही राखून ठेवत नाही. समवर्ती विनंत्या कोणत्याही रेकॉर्ड करण्यापूर्वी वापर वाचतात, त्यामुळे उधार क्षमता एकापेक्षा जास्त वेळा खर्च केली जाऊ शकते, फ्लाइटमधील विनंत्यांद्वारे मर्यादित. `saturation` मोडच्या शेअर चेकमध्ये समान मालमत्ता आहे.

## स्लाइडिंग विंडो काउंटर

`src/lib/quota/sqliteQuotaStore.ts` आणि `redisQuotaStore.ts` मध्ये अंमलात आणले आहे.

प्रत्येक `(apiKeyId, dimensionKey)` साठी दोन बकेट:

- `curr`: वर्तमान बकेट (`floor(nowMs / windowMs)`)
- `prev`: मागील बकेट (`curr - 1`)

प्रभावी रोलिंग मूल्य:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**अचूकता**: ~99% अचूक. बकेटच्या सीमेवर त्रुटी ही विंडोच्या आकाराच्या कमाल 1%
असू शकते (2-बकेट अंदाज पद्धतीची अंतर्निहित मर्यादा).

### समवर्ती प्रक्रिया

SQLite ड्रायव्हर: प्रत्येक `(apiKeyId | dimensionKey)` कीसाठी इन-मेमरी म्युटेक्स
रीड-मॉडिफाय-राइट रेस प्रतिबंधित करते. हा पॅटर्न `src/sse/services/auth.ts` मधील
anti-thundering-herd पद्धतीसारखा आहे.

Redis ड्रायव्हर: अणुस्तरीय इन्क्रिमेंटसाठी Lua EVAL स्क्रिप्ट — एकाच Redis कमांडच्या रूपात चालते.

## ड्रायव्हर्स

### SQLite (डीफॉल्ट, 0-इन्स्टॉल)

- टेबल: `quota_consumption` (मायग्रेशन `073_quota_pools.sql` / `074_quota_consumption.sql` पहा).
- एकल-इन्स्टन्स डिप्लॉयमेंटसाठी सर्वोत्तम.
- सर्व कायमस्वरूपी डेटा विद्यमान OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`) मध्ये असतो.

### Redis (पर्यायी, मल्टी-इन्स्टन्स)

- `ioredis` npm पॅकेज आवश्यक आहे.
- काउंटर Redis मध्ये संग्रहित केले जातात; मेटाडेटा (पूल्स/अलोकेशन्स) अजूनही SQLite मध्ये असतो.
- जिथे काउंटर सामायिक करणे आवश्यक आहे अशा मल्टी-रेप्लिका डिप्लॉयमेंटसाठी सर्वोत्तम.

### ड्रायव्हर्स बदलणे

सेटिंग्ज UI (`/dashboard/settings` → कोटा स्टोअर) द्वारे किंवा env vars द्वारे:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

DB सेटिंगला env पेक्षा प्राधान्य असते. `driver=redis` असल्यास, परंतु URL उपलब्ध नसल्यास किंवा
`ioredis` इन्स्टॉल केलेले नसल्यास, फॅक्टरी SQLite वर परत जाते आणि इशारा लॉग करते.

ड्रायव्हर निवडीचा क्रम:

1. DB सेटिंग `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. डीफॉल्ट: `sqlite`

## बहु-आयामी

पूलमध्ये अनेक आयाम असू शकतात. प्रत्येक परिमाण स्वतंत्र आहे:

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // global pool ceiling for this dimension
}
```

**उदाहरण: Codex योजना** (5h% + साप्ताहिक%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

विनंतीला परवानगी मिळण्यासाठी सर्व परिमाणे पूर्ण करणे आवश्यक आहे.

### टक्के परिमाणे: प्रति-की विशेषता

टक्के योजना प्रति खाते आणि प्लॅन विंडोसाठी एक वापराचा आकडा नोंदवते. प्रदाता प्रति API की कोणतेही काउंटर देत नाही.

ती आकृती की दरम्यान विभाजित करण्यासाठी, प्रत्येक पूल प्रति खाते आणि योजना विंडोमध्ये एक विशेषता पुस्तक ठेवते. `src/lib/quota/percentLedger.ts` पुस्तकाचे नियम धारण करतो. `src/lib/quota/percentAttribution.ts` पुस्तकाला अंमलबजावणी करणाऱ्या आकड्यांमध्ये बदलते. परिणाम म्हणजे प्रत्येक प्रमुख मार्गाच्या टोकनवरून तयार केलेला अंदाज.

#### पुस्तक हलवणारे वाचन

विनंती केलेल्या प्लॅन विंडोसाठी पुस्तक फक्त प्रदात्याच्या स्वतःच्या आकृतीवर फिरते. हे कनेक्शन एक अहवाल देतात:

| प्रदाता                     | खिडक्या योजना करा |
| --------------------------- | ----------------- |
| Claude, OAuth कनेक्शनद्वारे | `5h`, `weekly`    |
| Codex                       | `5h`, `weekly`    |

हे वाचन म्हणून गणले जात नाही:

- एक प्रतिसाद प्रदाता क्लायंट शिळा म्हणून चिन्हांकित करतो
- Claude विंडो ज्याची टक्केवारी प्रदात्याने नोंदवली नाही
- दुसऱ्या विंडोची आकृती, किंवा खिडक्यांमधील सर्वात वाईट केस
- दर-मर्यादा शीर्षलेख फॉलबॅक
- अयशस्वी वाचन

API की सह Claude सह इतर प्रदात्यांकडे कोणतेही पुस्तक नाही. या बदलापूर्वीप्रमाणेच प्रत्येक कीला त्यांच्या टक्के परिमाणांवर 0 आकारले जाते.

वाचन संपृक्तता सिग्नलचे 30-सेकंद कॅशे सामायिक करते. Claude वाचन ही आकृती प्रतिसाद शीर्षलेखांमध्ये पाहिली गेली किंवा वापराच्या शेवटच्या बिंदूवरून वाचली गेली, जेव्हा ती वेळ ओळखली जाते तेव्हाची तारीख असते. इतर वाचन ही कॅशे एंट्री केव्हा तयार केली गेली याची तारीख आहे.

#### पुस्तक काय ठेवते

प्रत्येक रेकॉर्ड केलेली विनंती प्रत्येक पूल, खाते आणि की एक काउंटरवर, एकदा त्याचे टोकन जोडते. एक काउंटर फक्त वाढतो. पुस्तक तीन गोष्टी ठेवते:

- बेसलाइन: पुस्तक उघडले किंवा खिडकी शेवटची वळली तेव्हाची आकृती
- शेवटची लागू केलेली आकृती
- प्रति की, त्याच क्षणी त्याचे टोकन काउंटर, ज्याला त्याचे चिन्ह म्हणतात

जेव्हा अंमलबजावणी किंवा वापर मार्ग विशेषताची गणना करते तेव्हा पुस्तक अद्यतनित केले जाते. लेखन पुनरावृत्ती क्रमांकावर तुलना-आणि-सेट केले जाते. हरवलेला लेखक एकदा नव्याने वाचल्यावर पुन्हा प्रयत्न करतो.

#### किल्लीचा भाग कसा मोजला जातो

जेव्हा पुस्तक वाचले जाते तेव्हा प्रत्येक कीच्या भागाची गणना केली जाते. आकृतीची वाढ चिन्हांकित केल्यापासून प्रत्येक राउट केलेल्या टोकनच्या प्रमाणात की दरम्यान विभाजित केली आहे.

Together, ते टोकन प्रति `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` टोकन्स (डिफॉल्ट 1,000) आकृतीच्या एका बिंदूवर स्पष्ट करतात. त्यांनी जी वाढ स्पष्ट केली नाही ती बाह्य आहे. बेसलाइन देखील बाह्य आहे.

उदाहरणार्थ, एखादे पुस्तक 0 वाजता उघडते. की A नंतर 900,000 टोकन्स आणि की B रूट 100,000. 60 च्या आकृतीवर, A चा भाग 54 गुण आहे आणि B चा भाग 6 आहे.

त्याच्या कीच्या चिन्हाखालील काउंटर रीस्टार्ट झाले आणि पूर्ण मोजले गेले. चिन्ह नसलेली की, जसे की खिडकीच्या मध्यभागी असलेल्या पूलमध्ये सामील होणारी की, तिचे सर्व टोकन मोजते. टोकन मागे ठेवणारी आकृती पुढील वाचनात निघून जाणारी त्रुटी निर्माण करते. ते जमत नाही.

`QUOTA_PERCENT_MIN_TOKENS_PER_POINT` प्रत्येक विशेषतावर वाचला जातो. किमान 1 ची मर्यादित संख्या नसलेले मूल्य 1,000 वर येते.

#### वाचनाने पुस्तक कसे बदलते

पहिला जुळणारा नियम लागू होतो:

1. **अद्याप कोणतेही पुस्तक नाही:** वाचन पुस्तक उघडते. त्याची आकृती बेसलाइन आहे आणि प्रत्येक काउंटर चिन्हांकित आहे.
2. **जुने वाचन:** शेवटचे लागू करण्यापूर्वीचे वाचन दुर्लक्षित केले जाते. असे वाचन आहे ज्याची रीसेट वेळ संग्रहित केलेल्या पेक्षा 30 मिनिटांपेक्षा जास्त आहे.
3. **नवीन प्रदाता विंडो:** संग्रहित केलेल्या पुस्तकापेक्षा 30 मिनिटांपेक्षा जास्त वेळाने रीसेट वेळ. आकृती बेसलाइन बनते आणि प्रत्येक काउंटर पुन्हा चिन्हांकित केले जाते. काउंटरशिवाय की पुस्तक सोडतात.
4. **समाप्त विंडो:** संग्रहित रीसेट वेळ जी वाचनाच्या डेटा वेळेनंतर नाही याचा अर्थ विंडो समाप्त झाली आहे. वाचनाने पुस्तक बदलते, मग त्याची आकृती काहीही असो.
5. **उच्च आकृती:** फक्त शेवटची आकृती हलते. बेसलाइन आणि मार्क्स राहतात.
6. **समान आकृती:** आकृती, आधाररेखा आणि गुण राहतात. पुस्तकाची उणीव असलेली फक्त रीसेट वेळ लिहिली जाते.
7. **खालची आकृती:** कमी आकृती कधीही लागू केली जात नाही. तीन गोष्टी धरल्या तरच पुस्तक वळते. ते शेवटच्या लागू केलेल्या वाचनापेक्षा किमान दोन मिनिटे नवीन आहे. काहीही म्हणत नाही की खिडकी सारखीच उघडी आहे. ते एक बिंदूपेक्षा जास्त कमी आहे.

जेव्हा तीन गोष्टी धरून ठेवतात तेव्हा विंडो समान उघडलेली म्हणून मोजली जाते. दोन्ही रीसेट वेळा ज्ञात आहेत. ते एकमेकांच्या 30 मिनिटांच्या आत आहेत. संग्रहित एक अजूनही वाचन पुढे आहे. त्या खिडकीतील खालची आकृती काहीही बदलत नाही.

रिसेट टाइम फक्त तेव्हाच साठवला जातो जेव्हा तो रीडिंगच्या डेटा वेळेच्या पुढे असतो. उच्च आकृती वापरण्यायोग्य असताना वाचनाची रीसेट वेळ संग्रहित करते आणि अन्यथा संग्रहित ठेवते. पुस्तकात काहीही नसतानाच एक समान आकृती त्याच्या वाचनाची रीसेट वेळ नोंदवते. ते इतर काहीही बदलत नाही. एक कमी आकृती जी पुस्तकाची नोंद करत नाही ती रीसेट वेळ नाही.

#### जेव्हा पुस्तक वापरले जाते

वाचनानंतर, पुस्तक वापरले जाते जोपर्यंत त्याची संग्रहित रीसेट वेळ चालू वेळेनंतर होत नाही. हे प्रकरण उद्भवते जेव्हा रीसेट करण्यापूर्वी घेतलेले वाचन, जसे की कॅशेमधून दिलेले वाचन, त्यानंतर लगेचच पाहिले जाते.

वापरण्यायोग्य वाचनाशिवाय, संग्रहित पुस्तक फक्त तेव्हाच वापरले जाते जेव्हा ते अद्याप वर्तमान विंडोचे पुस्तक असू शकते. हे दोन प्रकरणांमध्ये आहे:

- त्याची रीसेट वेळ ज्ञात आहे आणि अजूनही पुढे आहे
- त्याची रीसेट वेळ नाही, आणि शेवटचे वाचन ज्याने ते बदलले ते जास्तीत जास्त 15 मिनिटे जुने आहे

अन्यथा पुस्तक नसताना कशाचेही श्रेय दिले जात नाही. ज्या पुस्तकाचा संग्रहित रीसेट वेळ निघून गेला आहे त्यावर कधीही शुल्क आकारले जात नाही.

#### अंमलबजावणी

टक्के परिमाणावर किल्लीचा वापर हा त्याचा गुणधर्म असलेला भाग आणि बाह्य भागाचा हिस्सा असतो. बाह्य भाग प्रथम क्षमतेचा वापर करतो ज्यात कोणतेही वाटप दावा नाही (वजनांची बेरीज 100 वजा). वजनानुसार फक्त जादा कळा सामायिक केल्या जातात.

त्या उपभोगाची तुलना इतर कोणत्याही परिमाणांप्रमाणेच कीच्या वाजवी शेअरशी केली जाते. जेव्हा संपृक्तता सिग्नल `QUOTA_SATURATION_THRESHOLD` (डिफॉल्ट 0.5) पर्यंत पोहोचतो तेव्हा कठोर मोड अजूनही सुरू होतो. प्रत्येक संख्या प्रभावी मर्यादेने मोजली जाते: प्रति-खाते मर्यादा पूलमधील खात्यांच्या संख्येच्या गुणाकार करते.

`capUnit: "percent"` सह परिपूर्ण कॅप फक्त त्याच प्रकारे स्केल केलेल्या कीला दिलेला भाग मोजतो. 100 आणि k खात्यांची प्रति-खाते मर्यादा घ्या. सर्व्हिंग खात्याच्या आकृतीचा कीचा भाग N/k पॉइंटपर्यंत पोहोचल्यावर N ची टोपी गाठली जाते. प्रत्येक खाते त्याच्या स्वतःच्या पुस्तकात तपासले जाते. उदाहरणार्थ, दोन खात्यांसह, एका खात्याच्या आकृतीच्या 5 गुणांवर 10 ची कॅप गाठली जाते.

जेव्हा स्टोअर वाचले जाऊ शकत नाही, तेव्हा कशाचेही श्रेय दिले जात नाही आणि प्रत्येक की त्या परिमाणावर 0 आकारली जाते. जेव्हा एखादे पुस्तक लिहिणे अयशस्वी होते, तेव्हा ती विशेषता पुस्तक वाचल्याप्रमाणे वापरते. अयशस्वी टोकन लिहिल्यास त्या विनंतीचे टोकन पुस्तकातून बाहेर पडतात. यापैकी कोणतेही अपयश विनंती अवरोधित करत नाही.

`consent` पूलमध्ये, कर्ज देण्याचे सूत्र वर वर्णन केल्याप्रमाणे टक्केवारीच्या परिमाणावर प्रत्येक कीच्या वापराचा वापर करते. जेव्हा दुसरी की उधार देते, तेव्हा पुस्तक एकदा वाचले जाते आणि प्रत्येक किल्लीचे श्रेय दिले जाते. वापरण्यायोग्य पुस्तकाशिवाय प्रत्येक किल्ली 0 आकारली जाते. वजन असलेली की नंतर पास होते आणि 0 वजन असलेली की दुसरी की उधार देते तेव्हाच पास होते.

#### वापर मार्ग

`GET /api/quota/pools/{id}/usage` समान फंक्शनद्वारे समान संख्यांचा अहवाल देतो. `accounts` मधील प्रत्येक पूल कनेक्शनमध्ये टक्के परिमाण एक एंट्री आहे. त्याची उच्च-स्तरीय `consumedTotal` आणि `perKey` पहिल्या एंट्रीला मिरर करतात.

मार्ग सध्याच्या वाचनाला देखील लागू करतो, त्यामुळे विनंती केल्याप्रमाणे ते पुस्तक पुढे करू शकते. `internal + external` `consumedTotal` पेक्षा वेगळे असू शकते जेव्हा कोणतेही वापरण्यायोग्य वाचन नसते किंवा जेव्हा कमी आकृती लागू केली जात नाही.

#### स्टोरेज आणि धारणा

दोन्ही कोटा स्टोअर्स पुस्तक ठेवतात. SQLite वर, स्वयंचलित डेटाबेस क्लीनअप, सक्षम केल्यावर, 60 दिवसांसाठी अपडेट न केलेल्या पंक्ती काढून टाकते. Redis वर, पूल कनेक्शनची पुस्तके आणि काउंटर एक की सामायिक करतात. शेवटचे टोकन लिहिल्यानंतर किंवा पुस्तक बदलल्यानंतर ६० दिवसांनी ते कालबाह्य होते. जे पुस्तक बदलत नाही ते पुन्हा लिहिले जात नाही, म्हणून कटऑफ सर्वात लांब योजना विंडोच्या वर सेट केला जातो. मॅन्युअल वापर-इतिहास रीसेट देखील SQLite वरील पुस्तके साफ करते (मर्यादा पहा).

#### मर्यादा

- तेव्हापासून राउट केलेल्या प्रत्येक कीला टोकन्सद्वारे बेसलाइन विभाजित केल्यापासून खाते आकृतीची सर्व वाढ. जेव्हा ती वाढ झाली तेव्हा फरक पडत नाही.
- म्हणून OmniRoute बाहेर केलेल्या वापरावर त्यांच्या टोकन्सची परवानगी असलेल्या किल्लीवर शुल्क आकारले जाते. त्यामध्ये किल्लीच्या विंडोच्या पहिल्या विनंतीपूर्वी, पुस्तक आधीच उघडलेले असताना केलेला वापर समाविष्ट आहे.
- उदाहरणार्थ, मुख्य मार्ग नसताना बाहेरचा वापर खाते 60 गुण वाढवतो. एक की नंतर 30,000 टोकन रूट करते आणि आकृती 60.6 पर्यंत पोहोचते.
- जर पुस्तक वापरण्यापूर्वी उघडले असेल तर, कीचा भाग 30 गुणांचा आहे. हे बाह्य वापराचे 7.65 देखील वाहून घेते, 25 वजनाच्या चार कळांसह.
- त्या वापरानंतर पुस्तक उघडल्यास, 60 गुण बेसलाइन आहेत. कीचा भाग 0.6 गुणांचा आहे आणि त्यात 15 बाह्य वापर आहेत.
- विनंती किंवा वापर मार्गाची भेट पुस्तक उघडते. त्यामुळे असा वापर बेसलाइन म्हणून मोजला जातो की नाही हे पुस्तक कधी उघडले यावर अवलंबून असते.
- डीफॉल्ट फ्लोअरसह, 60,000 टोकन रूट करणारी की बाहेरून वापरल्यास खाते 60 पॉइंट्स वाढवते आणि सर्व 60 स्वतःचा भाग म्हणून मिळतात.
- मजला 50,000 सह, त्याचा स्वतःचा भाग 1.2 गुण आहे. इतर 58.8 बाह्य आहेत आणि कोणत्याही बाह्य वापराप्रमाणे वजनाने आकारले जातात.
- तुमच्या योजनेवर एका पॉइंटची किंमत किती आहे याच्या जवळ `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` सेट करा. बाहेरील वापरामध्ये पूलच्या बाहेरील की पासून समान खात्यावरील रहदारी समाविष्ट आहे.
- प्रत्येक मोडमध्ये एक टक्के कॅप लागू होते. खाते संपृक्तता थ्रेशोल्डच्या खूप खाली असताना कॅप केलेली की नाकारली जाऊ शकते.
- 10 आणि 12 पॉइंट्सच्या बाहेरील वापराच्या आधी विंडोमध्ये कॅप घ्या. 20,000 टोकन्स रूट करणारी की नंतर 12.4% च्या खात्यावर नाकारली जाते.
- विभाजन हा टोकन व्हॉल्यूमनुसार अंदाज आहे. विनंतीची त्याची प्रॉम्प्ट टोकन्स आणि त्याची पूर्णता टोकन म्हणून गणना केली जाते. कॅशे सवलत आणि मॉडेलच्या किमती त्या संख्येत बदल करत नाहीत.
- स्टेटस 200 ने समाप्त होणारी विनंती टोकन नाही. क्लायंटने डिस्कनेक्ट केलेला प्रवाह आणि वापर झाल्यानंतर अपस्ट्रीम त्रुटी ही उदाहरणे आहेत.
- अशा विनंतीचा वापर केल्याने टोकन रेकॉर्ड करणाऱ्या कीजवर शुल्क आकारले जाते, त्यांच्या टोकन्सची अनुमती मिळेपर्यंत. बाकी बाह्य आहे. तो मागे सरकत नाही. कोणताही टोकन वापर नोंदवणारा प्रतिसाद टोकनही नोंदवत नाही.
- प्रगतीपथावर असलेल्या विनंतीचा वापर संपूर्ण विनंतीसाठी दुसऱ्या सक्रिय कीच्या भागामध्ये दर्शविला जाऊ शकतो. जेव्हा विनंती स्टेटस 200 सह समाप्त होते तेव्हाच ते मागे सरकते.
- जेव्हा एखादे पुस्तक उघडते तेव्हा खात्यावर आधीपासूनच वापर बाह्य म्हणून मोजला जातो. यात अपग्रेड, नवीन पूल आणि नवीन खाते समाविष्ट आहे. नवीन विंडोमध्ये वापराच्या पहिल्या रीडिंगची गणना करण्यापूर्वी बाह्य म्हणूनही गणली जाते.
- प्रत्येक की त्या वापराच्या वजनाच्या वाटा पासून सुरू होते, क्षमता नंतर कोणतेही वाटप दावा नाही. 85% वर एक खाते आणि वजन 20 च्या पाच की, प्रत्येक वापरलेल्या 20 पैकी 17 ने सुरू होते.
- अनेक खाती असलेल्या पूलमध्ये, सर्व्हिंग खात्याचा आकडा एकत्रित बजेटवर लागू केला जातो. हे पुस्तकात अपरिवर्तित आहे.
- खिडकीच्या आतील खालची आकृती प्रदात्याने उघडली असल्याचे कळवले आहे लागू केलेले नाही. रीसेट वेळ जो 30 मिनिटांपेक्षा जास्त मागे सरकतो त्याला जुने वाचन मानले जाते.
- दोन्ही प्रकरणांमध्ये संग्रहित रीसेट वेळ संपेपर्यंत पुस्तक त्याची स्थिती ठेवते. त्यानंतर, पुस्तक वाचनात बदल होईपर्यंत शुल्क आकारले जात नाही.
- उपाय म्हणजे मॅन्युअल वापर-इतिहास रीसेट (`POST /api/settings/purge-usage-history`). हे SQLite डेटाबेसमधील विशेषता पुस्तके आणि त्यांचे टोकन काउंटर साफ करते.
- `all` कालावधी प्रत्येक पुस्तक आणि काउंटर साफ करतो. एक लहान कालावधी प्रथम त्यामध्ये न लिहिलेली पुस्तके साफ करतो. हे नंतर त्यामध्ये लिहिलेले नसलेले काउंटर साफ करते, परंतु केवळ एका पूल कनेक्शनसाठी ज्यामध्ये कोणतेही पुस्तक शिल्लक नाही. ठेवलेले पुस्तक अजूनही प्रत्येक की त्याच्या काउंटरवर चिन्हांकित करते.
- ज्या पुस्तकाची आकृती हललेली नाही ती पुन्हा लिहिली जात नाही, म्हणून लहान कालावधी देखील वर्तमान विंडोचे पुस्तक साफ करू शकते. पुढील वाचन नंतर वर्तमान आकृतीवर एक नवीन पुस्तक उघडते.
- रीसेट Redis कोटा स्टोअरला स्पर्श करत नाही. तिथे एखादे पुस्तक त्याच्या खिडकीने संपते किंवा शेवटच्या लेखनानंतर ६० दिवसांनी संपते.
- जेव्हा प्रदाता रीसेट वेळ पाठवत नाही, तेव्हा दोन रीडिंगमधील जुन्या आकृतीच्या वर रिसेट आणि रिफिल करणारी विंडो उच्च आकृतीसारखी दिसते. पुस्तक जुन्या आधाररेखा आणि गुण ठेवते.
- वाचन स्थानिक घड्याळाद्वारे दिनांकित केले जातात. जेव्हा ते प्रदात्याच्या पुढे चालते, किंवा स्त्रोत थोडा लवकर रीसेट वेळेचा अहवाल देतो, तेव्हा पुस्तक लवकर त्या फरकाकडे वळू शकते.
- त्या अल्प कालावधीतील वाढ त्यामध्ये राउट केलेल्या टोकनद्वारे विभाजित केली जाते. पुढील विंडोचे पहिले वाचन ते दुरुस्त करते. जेव्हा वळलेल्या पुस्तकात रीसेट वेळ नसतो, तेव्हा त्या सुधारणेसाठी शेवटच्या लागू केलेल्या वाचनापेक्षा कमीत कमी दोन मिनिटे नवीन आकृती आवश्यक असते.
- Redis स्टोअरच्या तारखेचे वाचन त्यांच्या स्वत:च्या घड्याळांसह शेअर करणारी उदाहरणे, त्यामुळे ती घड्याळे समक्रमित ठेवा. ज्याचे घड्याळ मागे चालते त्या उदाहरणाचे वाचन जुने दिसते आणि दुर्लक्ष केले जाते.
- संचयित रीसेट वेळेनंतर कोणतेही वापरण्यायोग्य वाचन येत नाही, तेव्हा वाचन परत येईपर्यंत प्रति-की टक्के शेअर्स आणि टक्के कॅप्स लागू केले जात नाहीत. रीसेट वेळेशिवाय, हे पुस्तक बदललेल्या शेवटच्या वाचनानंतर 15 मिनिटांनी सुरू होते.
- Redis स्टोअरवर, 60 दिवसांसाठी निष्क्रिय असलेले पुस्तक लेखकाचा चेक आणि त्याचे लेखन दरम्यान कालबाह्य होऊ शकते. ते नंतर 1 वरील पुनरावृत्तीवर पुन्हा तयार केले जाते, जी वैध स्थिती आहे.

## पाइपलाइन एकत्रीकरण

### PRE हुक (`open-sse/handlers/chatCore.ts`)

प्रमाणीकरण आणि पॉलिसी तपासल्यानंतर, अपस्ट्रीम एक्झिक्युटरसमोर चालते:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() per dimension
      → fairShare.decideFairShare()
      → if block → return 429 (buildErrorBody, Hard Rule #12)
      → if allow + deprioritize → set quotaSoftPenalty=true on candidate
  → executor.execute()
```

**फेल-ओपन** : `enforceQuotaShare` फेकल्यास, विनंतीला `pino.warn` लॉगद्वारे परवानगी दिली जाते. हे कोटा-इंजिन बगला सर्व रहदारी अवरोधित करण्यापासून प्रतिबंधित करते.

**जेव्हा क्षमता परत येते.** किल्लीच्या शेअरवर किंवा पूलच्या कमाल मर्यादेवर नकार दोनपैकी एका वाक्याने समाप्त होतो, दोन्ही कर्ज मोडमध्ये:

- `percent` विंडो: `. The <window> window resets at <time>.` प्रदाता अहवाल रीसेट करण्याची वेळ आहे.
- मोजता येण्याजोगे एकक: `. Enough <window> usage is expected to clear by <time>.` किल्लीने दुसरे काहीही पाठवले नाही तर वेळ ही स्लाइडिंग विंडोच्या वरची सीमा असते.

`<time>` हे UTC मध्ये ISO 8601 झटपट आहे. नकार नंतर `Retry-After` असतो : त्या क्षणापर्यंत संपूर्ण सेकंद, अधिक एक. इतका वेळ प्रतीक्षा करणारा क्लायंट झटपट नंतर जास्तीत जास्त एक सेकंद पुन्हा प्रयत्न करतो. जेव्हा झटपट ओळखले जात नाही, तेव्हा नकारात वाक्य किंवा शीर्षलेख नसतो. परिपूर्ण कॅप नकार दोन्हीही धारण करत नाही. सार्वजनिक संहिता `quota_share_blocked` राहते.

शेअर नकार शेअर केलेल्या कनेक्शनला स्पर्श करत नाही. हे कूलडाउन सेट करत नाही, मॉडेल लॉक नाही आणि प्रदाता ब्रेकर अयशस्वी होत नाही आणि पूलच्या इतर की सर्व्ह केल्या जातात. जेव्हा कॉम्बोचे प्रत्येक लक्ष्य त्याच्या शेअरची किल्ली नाकारते, तेव्हा कॉम्बो वाट न पाहता 429 उत्तर देते. त्याच्या उत्तरात `Retry-After` असा इशारा आहे. एम्बेडिंग पथ त्याच वाक्याने नकार संपवतो आणि `Retry-After` पाठवत नाही.

### POST हुक (विक्रमी वापर)

यशस्वी प्रतिसादानंतर:

```
executor returns success
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() per dimension
      → fail-open: errors logged as pino.warn, never propagated to client
```

**वाहून नेणे** : `consume` उत्तरोत्तर अयशस्वी झाल्यास, रोलिंग काउंटर कमी मोजले जाईल. प्रदात्याकडील संपृक्तता सिग्नल (उदा. `anthropic-ratelimit-unified-5h-utilization`) पुढील विनंतीवर जागतिक अंदाज दुरुस्त करतो.

### कॉम्बो सॉफ्ट पेनल्टी (`open-sse/services/combo.ts`)

जेव्हा `decision.deprioritize === true`:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // default 0.7
}
```

इतर सर्व स्कोअरिंग घटकांनंतर दंड लागू केला जातो. हे हार्ड-ब्लॉक न करता संतृप्त की निवडण्याची स्वयं-कॉम्बो संभाव्यता कमी करते.

## स्वयं-सेवा कोटा API (निवड करा)

`GET /api/v1/me/quota/{provider}` ( `/v1/me/quota/{provider}` वर देखील दिले जाते) API की धारकास त्यांच्या स्वत: च्या कीसह, किती सामायिक सदस्यता त्यांचे आहे आणि त्यांना काय अवरोधित करत आहे हे वाचू देते. मार्ग `src/server/selfService/quotaHandler.ts` वर एक पातळ कवच आहे; दृश्य `src/lib/quota/selfView.ts` द्वारे तयार केले आहे आणि त्याचा प्रतिसाद करार `src/shared/schemas/selfQuota.ts` ( `docs/openapi.yaml` मध्ये`SelfQuotaView` ) आहे.

### सक्षम आणि प्रमाणीकरण

- वैशिष्ट्य ध्वज `QUOTA_SELF_PANEL`, डीफॉल्ट `false`. तो बंद असताना, मार्गावर पोहोचणारी विनंती 404 मिळते. `REQUIRE_API_KEY=true` सह, क्लायंट API पॉलिसी मार्ग चालू होण्यापूर्वी 401 असलेली गहाळ किंवा अवैध की नाकारते, ध्वज काहीही असो. कोणतीही की नसलेली विनंती परंतु साइन इन केलेले डॅशबोर्ड सत्र ते धोरण पास करते आणि मार्गाचे स्वतःचे उत्तर मिळवते. ध्वज इतर प्रत्येक ध्वज प्रमाणे निराकरण करतो (डॅशबोर्ड किंवा REST ओव्हरराइड, नंतर त्याच नावाचे पर्यावरण व्हेरिएबल); [`FEATURE_FLAGS.md`](../reference/FEATURE_FLAGS.md) पहा.
- प्रत्येक पूलचे डिस्प्ले नाव आणि प्रत्येक शेड्यूलचे लेबल प्रशासकाने लिहिल्याप्रमाणे पूलच्या की धारकांना परत केले जातात. ध्वज चालू करण्यापूर्वी, ते त्या की धारकांद्वारे वाचण्यासाठी योग्य आहेत का ते तपासा.
- की फक्त शीर्षलेखांमधून वाचली जाते: `Authorization: Bearer <key>` किंवा `x-api-key: <key>`. जेव्हा दोन्ही पाठवले जातात, तेव्हा पहिले प्रमाणीकरण वापरले जाते. क्वेरी स्ट्रिंगमधील की किंवा कुकीकडे दुर्लक्ष केले जाते. सर्व्हरची पर्यावरण की नाकारली आहे (401).
- की `self:usage` स्कोप आवश्यक आहे (त्याशिवाय 403).
- प्रदाता विभाग ट्रिम केला जातो, लोअरकेस केला जातो आणि `^[a-z0-9][a-z0-9._-]{0,63}$` (400 अन्यथा) विरुद्ध तपासला जातो, नंतर प्रदाता नोंदणीद्वारे निराकरण केला जातो, म्हणून `cc` सारखे उपनाव `claude` पूल वाचते. `claude` आणि `anthropic` समान पूल वाचतात.

### प्रत्येक दृश्यमानता काय दर्शवते

| दृश्यमानता   | आवश्यक आहे                                                                            | फील्ड                                                                                                                                                                                                                                       |
| ------------ | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| स्वतःचा वाटा | `self:usage`                                                                          | `pools[]` (संदर्भ, नाव, प्रदाता, धोरण, वजन, कॅप), `dimensions[].yourShare`, `accounts[]` सह `yourShare` ( `attributed` आणि `external` शिवाय `percent` विंडोवर), `blocks`, `availableModels`, `expiresAt`, `apiBaseUrl`                      |
| खाते स्तर    | `self:usage` + `self:account-quota`, आणि की च्या `sharedQuotaProviders` मध्ये प्रदाता | `percent` विंडोच्या `yourShare` वर `dimensions[].total`, `accounts[].dimensions[].account` आणि `accounts[].modelWindows`, `attributed` आणि `external` आणि सदस्य वापर चालू असलेल्या पूलवर `members` जोडते ( [सदस्य वापर](#member-usage) पहा) |

- `sharedQuotaProviders` ही प्रति-की सेटिंग आहे (`PUT /api/keys/[id]/self-service`): `null`, डीफॉल्ट, म्हणजे प्रत्येक प्रदात्यापर्यंत की पोहोचते; `[]` म्हणजे काहीही नाही. प्रत्येक पूलचे `accountVisible` त्यावर कोणती दृश्यमानता लागू होते ते सांगते.
- खाते बार आणि मॉडेल विंडो फक्त त्या खात्यांसाठी दर्शविल्या जातात ज्यांचे कनेक्शन की वापरू शकते. जेव्हा की मध्ये परवानगी असलेल्या कनेक्शनची सूची असते, तेव्हा त्याच्या बाहेरील खाते `account` किंवा `modelWindows` शिवाय `Account N` एंट्री ठेवते. रिक्त यादी म्हणजे कोणतेही बंधन नाही, `/v1/me/status` साठी. एकूण पूल (`dimensions[].total`) त्या यादीवर अवलंबून नाही.
- फक्त `self:usage` सह दर्शविलेले दोन आकडे इतर कीच्या वापरातून येतात. शेड्यूल बजेटचा `exhausted` त्या शेड्यूल अंतर्गत प्रत्येक कीचा वापर प्रतिबिंबित करतो. ज्या पूलमध्ये सर्व वजन शून्य आहे, की चा `weight` `100 / number of members` आहे. दोन्ही गोष्टी की अंमलबजावणी लागू होतात.
- पूल केवळ `ref` द्वारे ओळखला जातो, एक अपारदर्शक मूल्य कॉलिंग कीशी बांधील आहे. त्याचे प्रदर्शन नाव (`name`) प्रशासकाने लिहिलेले आहे. सर्व्हरच्या API-की गुप्त (`API_KEY_SECRET`) सह की आणि पूलमधून `ref` मिळवला जातो. क्लायंटने ते कायम ठेवू नये: जर ते रहस्य फिरवले तर ते बदलते.
- खाती `Account 1`, `Account 2`, … म्हणून पूल क्रमाने सूचीबद्ध आहेत. कोणताही पूल आयडी, कनेक्शन आयडी, खाते ई-मेल किंवा खात्याचे नाव परत केले जात नाही आणि प्रतिसाद कॉन्ट्रॅक्ट स्कीमाद्वारे जातो, जे त्याच्या बाहेरील कोणतेही फील्ड ड्रॉप करते.
- मोजण्यायोग्य युनिट्स (`requests`, `tokens`, `usd`) कोटा गेट लागू करत असलेल्या पूल बकेट म्हणून नोंदवले जातात: `limit` = योजना पूलमधील × खाती, `fairShare` = वजन / 100 × `limit` (प्रत्येक काउंटर qz qz'0 चे स्वतःचे वजन असते तेव्हा समान विभाजन), =, `consumed` `remaining` = `fairShare` − `consumed` 0 वर मजला.
- `blocks.schedules` की च्या शेड्यूल विंडोची यादी करते (`open`/`closed`, `blackout` किंवा `outside-window`, `retryAfterSeconds`, राखीव मजले, आणि विंडोचे बजेट खर्च झाले आहे की नाही); `blocks.modelCaps` त्याच्या प्रति-मॉडेल तासावार कॅप्स वापरासह सूचीबद्ध करते.
- प्रदात्याच्या प्रत्येक पूलबाहेरील एक किल्ली `pools: []` सह 200 मिळते; `availableModels` (की `/v1/models` मध्ये पाहते `qtSd/` ids), `expiresAt` आणि `apiBaseUrl` अजूनही भरलेले आहेत.
- `apiBaseUrl` `OMNIROUTE_PUBLIC_API_BASE_URL` आहे, नंतर `OMNIROUTE_PUBLIC_BASE_URL`, अन्यथा `null`. हे कधीही विनंतीचे स्वतःचे मूळ नसते.

### `status` आणि `reason`

| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ok`          | वर्तमान वाचन.                                                                                                                                                                                                                                                                                                                                        |
| `stale`       | कॅशे केलेले खाते वाचन जुने म्हणून चिन्हांकित केले आहे, किंवा ज्याची रीसेट वेळ वाचल्यापासून निघून गेली आहे. क्रमांक ठेवले आहेत. एक मॉडेल विंडो जिची रीसेट वेळ निघून गेली आहे ती संपूर्ण `modelWindows` गट `stale` चिन्हांकित करते. `percent` विंडोच्या कीच्या स्वतःच्या शेअरसाठी: पुष्टी करण्यासाठी गेटच्या कॅशेमध्ये खाते न वाचता पुस्तक वाचले गेले. |
| `unavailable` | वाचन नाही; संख्या `null` आहेत, कधीही `0` नाही. `reason` म्हणतो का.                                                                                                                                                                                                                                                                                   |

| `reason`                          | जेव्हा                                                                                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `store_unavailable`               | कोटा स्टोअर वाचता आले नाही किंवा ते विशेषता पुस्तके वाचू शकत नाही.                                                                                |
| `percent_attribution_unavailable` | `percent` विंडोचा कीचा स्वतःचा वाटा: त्या खात्यासाठी आणि विंडोसाठी अद्याप कोणतेही विशेषता पुस्तक अस्तित्वात नाही किंवा पुस्तकात की सूचीबद्ध नाही. |
| `percent_window_ended`            | `percent` विंडोचा स्वतःचा वाटा: पुस्तक संपलेल्या प्लॅन विंडोचे आहे.                                                                               |
| `account_not_used_by_key`         | `percent` विंडोचा कीचा स्वतःचा वाटा: खात्याचे कनेक्शन कीच्या अनुमत कनेक्शनच्या बाहेर आहे. त्याचे पुस्तक वाचले जात नाही.                           |
| `window_not_reported`             | त्या प्लॅन विंडोसाठी प्रदाता-मर्यादा कॅशेमध्ये कोणतेही वाचन नाही.                                                                                 |
| `connection_lookup_failed`        | खात्याचे कनेक्शन वाचले जाऊ शकले नाही.                                                                                                             |
| `not_supported`                   | OmniRoute खात्याच्या प्रदात्यासाठी वापर मर्यादा वाचू शकत नाही.                                                                                    |
| `fetch_failed`                    | कोणतेही कॅशे केलेले वाचन वापरण्यायोग्य नव्हते आणि प्रदाता-मर्यादा रिफ्रेश अयशस्वी झाले.                                                           |

जेव्हा कोटा स्टोअर वाचता येत नाही, तेव्हा `blocks` (शेड्युल बजेटचे `exhausted`, मॉडेल कॅपचे `consumed` आणि `reached`) चे स्टोअर-बॅक केलेले फील्ड देखील `null` असतात.

### कर्ज देण्याची संमती

`PATCH /api/v1/me/quota/{provider}` एका पूलसाठी कॉलिंग कीची स्वतःची संमती नोंदवते. हे `GET` चे ध्वज, शीर्षलेख आणि प्रदाता नियम वापरते. `self:usage` स्कोप हे लेखन अधिकृत करते, जरी त्याचे नाव केवळ वाचनीय म्हणून वाचले जाते.

```json
{
  "pool": "qpr_0123456789abcdef0123456789abcdef",
  "lendingPercent": 30,
  "lendingUntil": 1893456000000
}
```

- `pool` हा `ref` आहे त्या पूलसाठी `GET` परतावा.
- `lendingPercent` हा 0 ते 100 पर्यंतचा पूर्णांक आहे. 0 चे मूल्य संमती आणि त्याची अंतिम मुदत साफ करते. `lendingPercent` 0 असलेली बॉडी एकतर मोडमध्ये स्वीकारली जाते.
- `lendingUntil` पर्यायी आहे: epoch milliseconds, किंवा `null` कोणतीही अंतिम मुदत नाही. ते भविष्यात आणि जास्तीत जास्त 8640000000000000 असणे आवश्यक आहे. 1000000000000 पेक्षा कमी मूल्य सेकंद म्हणून वाचले जाते आणि ते नाकारले जाते.
- इतर कोणतेही क्षेत्र नाकारले जाते. 4096 बाइट्सपेक्षा जास्त लांबीचा भाग नाकारला आहे. वाचन त्या आकारावर थांबते, त्यामुळे लांब शरीर कधीही पूर्ण धरले जात नाही.

चेक या टेबलच्या क्रमाने चालतात. प्रत्येक नकार निश्चित संदेशासह मानक त्रुटी मुख्य भाग वापरतो. यापैकी एका चेकने नकार दिल्याने काहीही लिहिले जात नाही.

| स्थिती | संदेश                                                                                              | जेव्हा                                                              |
| ------ | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 404    | `Not found`                                                                                        | `QUOTA_SELF_PANEL` ध्वज बंद आहे.                                    |
| 401    | `Valid API key required`                                                                           | की गहाळ किंवा अवैध आहे किंवा सर्व्हरची पर्यावरण की आहे.             |
| 403    | `API key lacks the self:usage scope`                                                               | की मध्ये `self:usage` कमतरता आहे.                                   |
| 400    | `Invalid provider`                                                                                 | प्रदाता विभाग अवैध आहे.                                             |
| 429    | `Too many lending changes. Retry later.`                                                           | किल्लीने त्याची मर्यादा पार केली. उत्तरात `Retry-After` आहे.        |
| 400    | `Body must be { pool, lendingPercent, lendingUntil }. lendingPercent is an integer from 0 to 100.` | शरीर JSON नाही, खूप लांब आहे, किंवा स्कीमाशी जुळत नाही.             |
| 400    | `lendingUntil must be a Unix time in milliseconds`                                                 | अंतिम मुदत सेकंद म्हणून वाचते.                                      |
| 400    | `lendingUntil must be in the future`                                                               | अंतिम मुदत विनंती वेळेवर किंवा त्यापूर्वी आहे.                      |
| 404    | `Pool not found`                                                                                   | `ref` ने या प्रदात्यासाठी या की च्या कोणत्याही पूलला नाव दिले नाही. |
| 403    | `Lending is not enabled for this pool`                                                             | पूल `saturation` मोडमध्ये आहे आणि `lendingPercent` 0 च्या वर आहे.   |
| 500    | `Failed to build quota view`                                                                       | इतर कोणतेही अपयश. त्याचे कारण सर्व्हरवर लॉग इन केले आहे.            |

मर्यादा प्रत्येक की साठी 20 विनंत्या प्रति 60 सेकंद आहे. प्रदाता चेक पास करणारी प्रत्येक विनंती मोजली जाते, अगदी नंतर नाकारलेली किंवा काहीही बदलणारी विनंती. कीच्या विनंती दर मर्यादेव्यतिरिक्त त्याचे स्वतःचे काउंटर आहे.

संचयित संमती बदलणारी विनंती एक `quota.pool.lending.updated` ऑडिट रेकॉर्ड लिहिते. हे जुन्या आणि नवीन मूल्यांसह किल्लीचे नाव देते. एकच बॉडी दोनदा पाठवते एकदा लिहते आणि एकदा ऑडिट करते. उत्तर पूर्ण `GET` दृश्यासह 200 आहे, लेखनानंतर तयार केले आहे.

`GET` व्ह्यू खालीलप्रमाणे कर्ज देण्याचा अहवाल देतो:

- प्रत्येक पूलमध्ये `borrowMode` (`saturation` किंवा `consent`), आणि कीची स्वतःची `lendingPercent` आणि `lendingUntil` असते.
- `lendingActive` फक्त `consent` पूलमध्ये `true` आहे, 0 वरील टक्केवारी आणि अंतिम मुदत गाठली नाही.
- `consent` पूलमध्ये, प्रत्येक मोजण्यायोग्य `dimensions[].yourShare` मध्ये `borrowAvailable` असतो. इतर किल्ली द्वारे दिलेली किल्ली आता त्याच्या शेअरच्या वर वापरू शकते.
- `borrowAvailable` गेटचे सूत्र वापरते. ती प्रत्येक इतर की वाचते, की त्याच्या शेअरखाली असताना देखील. `hard` की साठी जी इतर की आणि मोजण्यायोग्य परिमाणानुसार एक अतिरिक्त वाचन आहे, समांतर.
- `borrowAvailable` हे `soft` किंवा `burst` कीसाठी `null` आहे आणि वाचन अयशस्वी झाल्यावर `null`.
- `borrowAvailable` इतर सर्व कळांसाठी एक आकृती आहे. दोन कळांच्या पूलमध्ये ती दुसऱ्या कीची स्वतःची आकृती असते.
- `borrowAvailable` अद्याप `percent` विंडोसाठी किंवा `accounts[]` मध्ये नोंदवलेले नाही.
- `saturation` पूलमध्ये व्ह्यू `lendingActive: false` आणि नो `borrowAvailable` सह संग्रहित संमतीचा अहवाल देतो.

### चुका

या मार्गाचा प्रत्येक प्रतिसाद, यश किंवा त्रुटी, `Cache-Control: no-store` आहे. मार्ग चालण्यापूर्वी नकार दिला जात नाही, उदाहरणार्थ क्लायंट API पॉलिसीची 401 किंवा IP फिल्टरची 403. मार्गातील त्रुटी निश्चित संदेशासह मानक त्रुटी मुख्य भाग वापरतात: 400 (अवैध प्रदाता), 401 (गहाळ किंवा अवैध की), 403 ( `self:usage`) आणि 403 (मिसिंग ऑफ) (`Failed to build quota view`) एकदा विनंती मार्गावर पोहोचल्यानंतर 500 कोणत्याही अपयशाला कव्हर करते, की लुकअपसह; त्याचे कारण सर्व्हरवर लॉग इन केले आहे आणि परत आले नाही. `PATCH` च्या त्रुटी [कर्ज देण्याच्या संमतीमध्ये](#lending-consent) सूचीबद्ध केल्या आहेत.

### मर्यादा

- `remaining` हा किल्लीच्या योग्य शेअरचा भाग आहे जो त्याने वापरला नाही. त्याची हमी नाही. पूलमध्ये खोली असतानाही त्यापलीकडे एक चावी दिली जाऊ शकते. एकदा पूलची एकूण संख्या `limit` वर पोहोचली की, पूलची प्रत्येक की स्वतःची `remaining` काहीही असली तरी ती नाकारली जाते आणि `self:account-quota` शिवाय असलेली की ती टोटल पाहू शकत नाही.
- `remaining` वाटपाचे संपूर्ण `cap` विचारात घेत नाही. कॅपच्या युनिटच्या खिडकीतील स्वतःचा वापर कॅपच्या मूल्यापर्यंत पोहोचल्यावर अंमलबजावणी की नाकारते.
- खाते-स्तरीय बार प्रदाता-मर्यादा कॅशेमधून येतो आणि अंमलबजावणीच्या निर्णयाला काही मिनिटांनी मागे टाकू शकतो. रिसेटची वेळ निघून गेलेले वाचन `stale` म्हणून नोंदवले जाते.
- प्रति-मॉडेल विंडो (`modelWindows`) फक्त प्लॅन-विंडो मॅपिंग असलेल्या प्रदात्यांसाठी नोंदवले जातात: Claude आणि Codex आज. इतर प्रदात्यांसाठी `modelWindows` रिकाम्या `windows` सूचीसह खाते डेटा दर्शविला जातो तेव्हा देखील उपस्थित असतो.
- `percent` विंडोचा स्वतःचा वाटा हा एक अंदाज आहे. हे विशेषता पुस्तकातून आले आहे आणि वरील "टक्के परिमाणे: प्रति-की विशेषता" अंतर्गत सूचीबद्ध केलेली प्रत्येक मर्यादा आहे.
- `consumed` ही संख्या अंमलबजावणी योग्य शेअरशी तुलना करते. हे `attributed` अधिक `external` आहे, अगदी. `attributed` हा पुस्तक राउट केलेल्या टोकनसाठी चावी देणारा भाग आहे. `external` हा खात्याच्या वापराचा कीचा भाग आहे ज्यासाठी पूलच्या की खाते नाही.
- जेव्हा पूलचा `accountVisible` सत्य असेल तेव्हाच दोन्ही भाग पाठवले जातात: कीमध्ये `self:account-quota` आहे आणि प्रदाता त्याच्या `sharedQuotaProviders` मध्ये आहे. त्याशिवाय एक की `consumed` एकटीच मिळते, त्याच `status` आणि `reason` सह.
- दोन्ही भाग आणि त्याचे स्वतःचे वजन, धारक पूलच्या बाहेर केलेल्या वापरावर काम करू शकतो जे पूलच्या चाव्यांवर शुल्क आकारले जाते. खाते व्याप्ती असलेला धारक आधीच खात्याची एकूण रक्कम पाहतो.
- विंडोमध्ये काहीही न फिरवणारी की अजूनही `consumed` वरून त्याचे बाह्य शुल्क वाचू शकते, कारण तिचा गुणविशेष भाग नंतर 0 आहे.
- उदाहरणार्थ, एक पुस्तक 0 वाजता उघडते, ज्यात A आणि B की प्रत्येकी 50 वजन असतात. की A 900,000 टोकन आणि की B 100,000 मार्गे. त्यानंतर खाते 100 च्या मर्यादेच्या 60% पर्यंत पोहोचते. नंतर `attributed` की A साठी 54 आणि B साठी 6 आहे आणि `external` दोन्हीसाठी 0 आहे.
- दृश्य पुस्तक वाचतो आणि त्याची अवस्था कधीच लिहित नाही. ते पुस्तक उघडत नाही आणि ते प्रदात्याला वाचण्यासाठी कधीही विचारत नाही. Redis स्टोअरसह, गेटच्या रीड्सप्रमाणे, रीड पार्श्वभूमीतील बदललेली पुनरावृत्ती फील्ड काढून टाकते.
- गेटच्या कॅशेमध्ये खात्याचे रीडिंग असते तेव्हाच हिस्सा `ok` असतो. एकाशिवाय ते `stale` आहे, त्यामुळे अलीकडील विनंती नसलेल्या पूलमध्ये ते कदाचित कालबाह्य असल्याचे दर्शविते.
- विनंती पूलमधून जाईपर्यंत, शेअर अनुपलब्ध असतो. ती विनंती पुस्तक उघडते आणि त्या क्षणी खात्याचा आकडा पूलच्या बाहेर केलेला वापर म्हणून मोजला जातो.
- अनेक खाती असलेल्या पूलमध्ये, प्रत्येक खाते एंट्री त्या खात्याचे स्वतःचे पुस्तक आणि एका खात्याची मर्यादा वापरते. अंमलबजावणी खात्यांच्या संख्येनुसार दोन्ही बाजूंना मोजते, त्यामुळे प्रमाण समान आहे.
- प्रति-मॉडेल विंडोमध्ये किल्लीचा कोणताही हिस्सा नसतो. पुस्तक प्रति-मॉडेल डेटा ठेवत नाही.
- शेड्यूलच्या राखीव मजल्यांचे दृश्याद्वारे मूल्यांकन केले जात नाही: `schedule-reserve` कारणास्तव विनंती नाकारली जाते तेव्हा शेड्यूल `open` म्हणून दर्शवू शकते.
- जेव्हा एकाच कीचे दोन पूल कनेक्शन सामायिक करतात, तेव्हा अंमलबजावणी त्यापैकी एक लागू होते आणि दृश्य दोन्हीची यादी करते.
- अयशस्वी की प्रयत्नांवर प्रति-पत्ता मर्यादा नाही: उलट प्रॉक्सी कॉलर मागे एक पत्ता सामायिक करू शकतात (फॉरवर्ड केलेले क्लायंट पत्ते विश्वसनीय आहेत की नाही यावर ते अवलंबून असते), त्यामुळे लॉकआउट प्रत्येक की धारकाचा मार्ग नाकारू शकतो. `REQUIRE_API_KEY=true` सह, मार्ग चालण्यापूर्वी क्लायंट API पॉलिसीद्वारे अवैध की नाकारली जाते, या मार्गाऐवजी त्या पॉलिसीच्या 401 मुख्य भागासह.

### सदस्य वापर

ॲडमिनिस्ट्रेटर की धारकांना विंडोचा वापर पूलच्या सदस्यांमध्ये कसा विभाजित होतो हे पाहू शकतो. पर्याय म्हणजे पूलचा `memberBreakdown`, डीफॉल्टनुसार बंद. ते पूल विझार्डमध्ये किंवा `PATCH /api/quota/pools/{id}` सह सेट केले आहे. `GET /api/quota/pools` आणि `GET /api/quota/pools/{id}` त्याचा अहवाल देतात.

या सर्व गोष्टी धारण केल्यावरच दृश्याचा परिमाण `members` असतो:

- पूलचा पर्याय चालू आहे
- पूलमध्ये जास्तीत जास्त 20 वाटप केलेल्या कळा आहेत आणि त्यापैकी किमान तीन विनंत्या करू शकतात: सक्रिय, रद्द केलेले नाही, बंदी नाही आणि त्यांची मुदत संपलेली नाही
- पूलचा `accountVisible` सत्य आहे: की मध्ये `self:account-quota` आहे आणि प्रदाता त्याच्या `sharedQuotaProviders` मध्ये आहे
- `percent` विंडोवर, खात्याचे कनेक्शन ही एक की वापरू शकते
- त्या खिडकीची की चा स्वतःचा वाटा वाचला: त्याचा `status` `unavailable` नाही

अन्यथा `members` अनुपस्थित आहे. ती कधीही रिकामी यादी नसते.

- प्रत्येक स्लाइस `{ slot, consumed, isYou }` आहे. प्रतिसाद स्कीमा स्लाइसवरील इतर कोणतीही मालमत्ता आणि 20 पेक्षा जास्त स्लाइसची सूची नाकारते. स्लाइस स्लॉट क्रमाने सूचीबद्ध आहेत.
- प्रति वाटप केलेल्या कीसाठी एक स्लाइस आहे, यापुढे विनंत्या करू शकत नसलेल्या कीसह. वापर नसलेला सदस्य वास्तविक शून्य दाखवतो.
- `isYou` सत्यासह स्लॉट 1 नेहमी विचारणारी की असते. इतर स्लॉट क्रमांक हे कीड हॅशचे रँक आहेत. हे `API_KEY_SECRET` सह की केलेले आहे आणि पूल, विचारणारी की आणि सदस्य कव्हर करते.
- त्यामुळे संख्या धारकांमध्ये एकसंध होत नाही. एका धारकासाठी ते भेटी दरम्यान समान राहतात. जेव्हा की जोडली जाते किंवा पूल सोडते तेव्हा किंवा ते रहस्य फिरवले जाते तेव्हा ते बदलू शकतात.
- मोजता येण्याजोग्या विंडोवर स्लाइस कोटा स्टोअरमधील सदस्याचा काउंटर असतो, तोच काउंटर त्याच्या स्वत:च्या `consumed` सारखा असतो.
- `percent` विंडोवर एक स्लाइस सदस्याचा `attributed` भाग आहे, त्याच पुस्तकातील कीच्या स्वतःच्या शेअरप्रमाणे वाचला जातो. तलावाच्या बाहेर केलेला वापर कधीही स्लाइसमध्ये विभागला जात नाही. हे शुल्क वजनाने विभाजित केले जाते, म्हणून ते वाहून नेणारे तुकडे वजन दर्शवतील.
- प्रत्येक दृश्य प्रति इतर सदस्य एक मूल्य वाचते आणि समांतरपणे मोजण्यायोग्य विंडो. `percent` विंडोवर स्लाइसची किंमत शेअरच्या स्वतःच्या पुस्तकाच्या वाचनाच्या पलीकडे नाही. जेव्हा एक मूल्य वाचले जाऊ शकत नाही, तेव्हा त्या विंडोमध्ये कोणतेही `members` नसते आणि कीचा स्वतःचा हिस्सा राहतो.
- पर्याय आणि वापरण्यायोग्य की ची संख्या प्रति पूल एकदा वाचली जाते आणि फक्त खाते डेटा पाहू शकणाऱ्या कीसाठी. पर्याय किंवा वापरण्यायोग्य-की संख्याचे अयशस्वी वाचन त्या पूलसाठी बार बंद करते. सर्व्हर एक चेतावणी लॉग करतो आणि उर्वरित दृश्य तयार केले जाते.

बारमध्ये नावे किंवा आयडी नाहीत. ते अजूनही मुख्य धारकास इतर सदस्यांबद्दल गोष्टी सांगतात:

- धारक अजूनही त्यांच्या मूल्यांनुसार स्लाइस जुळवू शकतात.
- स्थिर क्रमांकन धारकाला कालांतराने एका सदस्याचे अनुसरण करू देते.
- स्लाइसची संख्या पूलमध्ये किती की वाटप केल्या आहेत हे दर्शविते.
- तीन कळांच्या पूलमध्ये, एक की कोणती वापरली हे ज्याला माहित आहे ती शेवटची की काय वापरली हे सांगू शकते.
- जेव्हा पूल तीन वापरण्यायोग्य की खाली येतो तेव्हा बार अदृश्य होतात. आधी घेतलेली दृश्ये प्रत्येक सदस्याने काय वापरले हे अजूनही दर्शवितात.
- मोजता येण्याजोग्या विंडोवर, पूल एकूण वजा स्लाइस यापुढे वाटप न केलेल्या की चा वापर दर्शवू शकतात.
- एका खात्यावर शून्य दाखवणारा आणि दुसऱ्या खात्यावर वापरणारा सदस्य कोणता सदस्य कोणते खाते वापरतो हे दाखवू शकतो.
- `hard` पॉलिसीसह मोजता येण्याजोग्या पूलमध्ये, सदस्याच्या वाजवी वाटणीवर वाढणारा तुकडा त्या सदस्याच्या वजनावर संकेत देतो.

### वापर मालिका (`GET /api/v1/me/usage`)

`GET /api/v1/me/usage?range=<range>` ( `/v1/me/usage` वर देखील दिले जाते) कॉलिंग कीच्या स्वतःच्या विनंत्यांचा वापर आणि किंमत परत करते: बेरीज, प्रति UTC दिवस, प्रति दिवस आणि मॉडेल, प्रति मॉडेल आणि प्रति प्रदाता. हे ध्वज, प्रमाणीकरण नियम, `self:usage` स्कोप, `Cache-Control: no-store` आणि वरील कोटा मार्गाचे त्रुटी वर्तन सामायिक करते. `range` च्या आधी की तपासली जाते. त्रुटी 400 (`Invalid range`), 401, 403, 404 आणि 500 (`Failed to build usage`) आहेत.

- `range` हे `1d`, `7d`, `30d` (डिफॉल्ट) किंवा `90d` पैकी एक आहे. इतर कोणतेही मूल्य, रिक्त मूल्य किंवा पुनरावृत्ती केलेले पॅरामीटर 400 आहे. कॉलची किंमत बांधण्यासाठी सेट `90d` वर थांबतो. दृश्य केवळ कच्चा वापर इतिहास वाचतो, कधीही दैनिक सारांश नाही, ज्यामध्ये कोणतीही कळ नसते.
- कॉलिंग कीच्या आयडीद्वारे पंक्ती निवडल्या जातात. की नावाचा स्तंभ कधीही जुळत नाही आणि की आयडीशिवाय रेकॉर्ड केलेल्या पंक्ती कधीही मोजल्या जात नाहीत.
- मालिका तयार करताना विंडोमधील कीच्या पंक्तींवर पाच गटबद्ध क्वेरी चालवल्या जातात. तयार केलेली मालिका 60 सेकंद प्रति की आणि श्रेणीसाठी पुन्हा वापरली जाते आणि पुन्हा वापरलेला कॉल काहीही चालत नाही. त्याचे `generatedAt` त्याचे वय देते.
- मालिका तयार झाल्यावर विंडो संपते. नंतर स्टँप केलेली पंक्ती, उदाहरणार्थ घड्याळाच्या स्क्यूद्वारे, मोजली जात नाही.
- `coverage.retentionDays` ही ऑपरेटरची रॉ वापर-इतिहास धारणा सेटिंग आहे (डेटाबेस सेटिंग्जमध्ये`retention.usageHistory` ). जेव्हा विनंती केलेली श्रेणी त्या सेटिंगपेक्षा मोठी असते तेव्हा `coverage.truncatedByRetention` सत्य असते. हे दोन संख्यांची तुलना करते आणि पंक्ती गहाळ आहेत की नाही हे तपासत नाही.
- कीच्या स्वतःच्या विनंत्यांसाठी रेकॉर्ड केल्याप्रमाणे प्रदाता परत केला जातो. मॉडेल हे त्याच्या शेवटच्या `/` नंतर रेकॉर्ड केलेले नाव आहे आणि पंक्ती त्याद्वारे गटबद्ध केल्या आहेत. कॉम्बो विनंती ज्याचे प्रत्येक लक्ष्य नाकारले गेले होते ती प्रदाता (कॉम्बो नाव, `auto` किंवा `combo`) आणि क्लायंटने पाठवलेल्या मॉडेल स्ट्रिंगसह राउटिंग लेबलसह रेकॉर्ड केली जाते. इतर नाकारलेल्या विनंत्या, उदाहरणार्थ ओपन सर्किट ब्रेकर, मॉडेल कूलडाउन किंवा कोटा-पार्क स्किप, लक्ष्य प्रदाता आणि मॉडेल ठेवा.
- संख्या आणि खर्चाव्यतिरिक्त, प्रतिसादामध्ये सरासरी विलंबता, यश दर आणि पहिल्या आणि शेवटच्या विनंतीच्या वेळा असतात.
- `byModel` सर्वाधिक विनंत्या असलेल्या 50 प्रदाता-आणि-मॉडेल जोड्यांची यादी करते. अधिक जोड्यांसह त्याच्या नोंदी `summary` पर्यंत जोडल्या जात नाहीत आणि `summary.uniqueModels` प्रत्येक रेकॉर्ड केलेल्या मॉडेल स्पेलिंगची गणना करते. `byModelTruncated` नंतर सत्य आहे, आणि एक मॉडेल ज्याच्या जोड्या कटच्या दोन्ही बाजूंना पडतात त्या आंशिक बेरीज दर्शवतात.
- दोन खर्च नोंदवले आहेत. `costUsd` ही बिल केलेली किंमत आहे, जसे की वापर विश्लेषणे ते दर्शवतात. फ्लॅट-रेट सबस्क्रिप्शन प्रदाते, जसे की Claude कोड योजना, तेथे $0 मोजा. `listPriceUsd` हा सूची किंमतीनुसार समान वापर आहे, सदस्यता समाविष्ट आहे. विनंती ज्याच्या मॉडेलची किंमत पंक्ती नाही ती त्याची संग्रहित किंमत मोजते: प्रदात्याने नोंदवलेला खर्च किंवा विनंती रेकॉर्ड केल्यावर मोजलेली किंमत. मार्करशिवाय ० गणती नसलेली फक्त विनंती, त्यामुळे एकूण आंशिक असू शकते.
- प्रतिसाद करार `src/shared/schemas/selfUsage.ts` ( `docs/openapi.yaml` मध्ये`SelfUsageSeries` ) आहे.

### स्वयं-सेवा पृष्ठ

`QUOTA_SELF_PANEL` चालू असताना, `/quota/{provider}` हे सार्वजनिक पृष्ठ आहे. की धारक तेथे API की टाइप करतो आणि प्रदात्यासाठी की चा पूल पाहतो. प्रत्येक पूल प्रत्येक पूलच्या खिडकीवर एक कार्ड दाखवतो, ज्यामध्ये प्रत्येकासाठी पूलचा वापर असतो आणि किल्लीचा स्वतःचा वाटा असतो. पूलच्या प्रत्येक खात्याचे स्वतःचे कार्ड आहेत, ज्यामध्ये खात्याचा वापर आणि किल्लीचा वाटा आहे. जेव्हा की खाते डेटा पाहू शकते तेव्हाच खात्याचा वापर दिसून येतो. पृष्ठ प्रत्येक खात्याच्या प्रति-मॉडेल मर्यादा आणि कीचा स्वतःचा वापर देखील सूचीबद्ध करते. जेव्हा शेड्यूल आत्ता की ब्लॉक करते तेव्हा एक सूचना दिसते. कार्ड किल्लीच्या प्रत्येक मॉडेल कॅपच्या वापरासह सूचीबद्ध करते आणि पोहोचलेल्यांना चिन्हांकित करते. `{provider}` हा प्रदाता आयडी किंवा त्याचे उपनाव आहे (`/quota/claude`, `/quota/cc`). अज्ञात प्रदाता, आणि ध्वज बंद असताना प्रत्येक `/quota/*` मार्ग, उत्तर 404. सानुकूल OpenAI- किंवा Anthropic-compatible नोडवरील पूलमध्ये कोणतेही पृष्ठ नसते. API अजूनही त्यांच्यासाठी उत्तर देतो.

पृष्ठावर कोणतेही सत्र नाही. की फक्त `GET /api/v1/me/quota/{provider}`, `PATCH /api/v1/me/quota/{provider}` आणि `GET /api/v1/me/usage` च्या `Authorization` शीर्षलेखात पाठविली जाते, कधीही URL मध्ये नाही. सर्व्हर स्वीकारत असलेली की टॅबच्या `sessionStorage` मध्ये ठेवली जाते. "या डिव्हाइसवर लक्षात ठेवा" सह ते त्याऐवजी `localStorage` मध्ये ठेवले जाते आणि "Forget key" ते दोन्हीमधून काढून टाकते. सर्व्हरने नाकारलेली की स्टोरेजमधून काढून टाकली जाते.

`consent` मोडमधील पूल कर्ज देणारे कार्ड दाखवतो. तेथे की धारक कर्ज देण्यासाठी कीच्या निष्क्रिय वाटापैकी 0 ते 100 पर्यंत संपूर्ण टक्केवारी सेट करतो. संमती किती काळ टिकते हे देखील धारक निवडतो: बंद होईपर्यंत, 1 तास, 8 तास, 24 तास, 7 दिवस किंवा 30 दिवस. बचत करण्याच्या क्षणापासून कालावधी मोजला जातो. अंतिम मुदत लागू असताना, धारक त्याऐवजी ती ठेवू शकतो. जर ती मुदत जतन करण्यापूर्वी पास झाली, तर कार्ड काहीही पाठवत नाही आणि दुसरा पर्याय विचारेल. 0% सह कोणतीही अंतिम मुदत पाठविली जात नाही. कार्ड त्याच्या टाइम झोन नावासह संग्रहित अंतिम मुदत दर्शवते. ज्या संमतीची अंतिम मुदत संपली आहे ती संपली म्हणून दाखवली आहे.

`hard` कीसाठी, कार्ड प्रत्येक पूल विंडोची यादी देखील देते, आत्ता इतर कोणत्या किल्ली कीला उधार देतात. प्रत्येक पंक्ती इतर सर्व की एकत्र करण्यासाठी एक आकृती आहे. दोन कळांच्या पूलमध्ये ती दुसऱ्या कीची स्वतःची आकृती असते. दृश्य अहवाल देत नसलेली आकृती उपलब्ध नाही म्हणून वाचते, शून्य नाही. `soft` किंवा `burst` की साठी कार्ड म्हणते की कोणतीही आकृती लागू होत नाही.

`saturation` मोडमधील एक पूल ज्याची की 0 वरील टक्केवारी संचयित करते फक्त पैसे काढणे दर्शवते. ते म्हणतात की संचयित टक्केवारीचा तेथे कोणताही परिणाम होत नाही. त्याचे पैसे काढा बटण 0 पाठवते ज्याची अंतिम मुदत नाही. संचयित 0 सह `saturation` मोडमधील पूल कोणतेही कर्ज देणारे कार्ड दाखवत नाही. सेव्ह केल्यानंतर, परत केलेल्या व्ह्यूला यापुढे आवश्यक नसलेले कार्ड पृष्ठाचे दृश्य पुन्हा बदलेपर्यंत त्याच्या संदेशासोबत राहते.

जोपर्यंत धारक सेव्ह किंवा विथड्रॉ दाबत नाही तोपर्यंत काहीही सेव्ह होत नाही. प्रत्येक प्रेस एक `PATCH /api/v1/me/quota/{provider}` विनंती पाठवते, आणि दुसरी प्रेस प्रथम प्रलंबित असताना काहीही पाठवत नाही. दृश्य, टक्केवारी आणि अंतिम मुदत यावरून बॉडी पूलचे अपारदर्शक `ref` घेऊन जाते. उत्तर पुनर्निर्मित कोटा दृश्य आहे, आणि पृष्ठ ते कोणत्याही सेकंदाच्या वाचनाशिवाय दाखवते. जेव्हा दोन सेव्ह ओव्हरलॅप होतात, तेव्हा पृष्ठ शेवटच्या उत्तरानंतर एकदा कोटा वाचते. पृष्ठ ब्राउझर स्टोरेजमध्ये संमती ठेवत नाही.

HTTP स्थितीतून निवडलेल्या मजकुराद्वारे कार्डवर नकार दिलेला बदल स्पष्ट केला जातो. त्रुटी मुख्य भाग वाचलेला नाही. A 401 म्हणते की की स्वीकारली गेली नाही आणि कोटा पुन्हा लोड करते. एक 403 म्हणतो की पूल कर्ज बदल घेत नाही आणि 404 म्हणतो की पूल संपला आहे. दोघेही कोटा रीलोड करणारे बटण ऑफर करतात. 400 किंवा दुसरे 4xx उत्तर धारकास टक्केवारी आणि अंतिम मुदत तपासण्यास सांगते. A 429 धारकास प्रतीक्षा करण्यास सांगतो, `Retry-After` च्या सेकंदांसह उत्तर देते तेव्हा. 5xx उत्तर, 408 किंवा नेटवर्क बिघाड म्हणते की बदल जतन केला गेला नाही आणि टाइप केलेली मूल्ये ठेवते. कराराच्या बाहेरचे उत्तर कोटा रीलोड करते. अयशस्वी जतन केल्याने की स्वतःच काढून टाकत नाही. नकार दिल्यानंतर रीलोड केल्यावर, पृष्ठ कोणत्याही नाकारलेल्या वाचनाप्रमाणे की काढून टाकते.

एकदा की स्वीकारल्यानंतर, पृष्ठ तीन टॅबसह "तुमची साधने सेट करा" कार्ड देखील दर्शवते. "Claude कोड" `~/.claude/settings.json` साठी `env` ब्लॉक देतो. "शेल" `export` लाईन्स प्रमाणेच व्हेरिएबल्स देते. "Claude डेस्कटॉप" त्याच्या तृतीय-पक्ष अनुमान विंडोसाठी मूल्ये देते. मॉडेल हे कोटा-शेअर मॉडेल आहेत की त्या प्रदात्यासाठी कॉल करू शकतात. जेव्हा अशी कोणतीही यादी कीसह येत नाही, तेव्हा ब्लॉक गेटवे मॉडेल शोध चालू करतो. गेटवे पत्ता हा सार्वजनिक API मूळ सर्व्हर अहवाल आहे (`OMNIROUTE_PUBLIC_API_BASE_URL`, नंतर `OMNIROUTE_PUBLIC_BASE_URL`). दोन्हीपैकी कोणतेही सेट नसताना, कार्ड प्लेसहोल्डर दाखवते आणि धारकाला प्रशासकाला विचारण्यास सांगते. की प्लेसहोल्डर म्हणून दर्शविली आहे. "माझी की समाविष्ट करा" संपूर्ण की स्क्रीनवरील मजकूरात ठेवते आणि कॉपी बटण काय कॉपी करते. ते बॉक्स साफ होईपर्यंत, की विसरले किंवा बदलले जाईपर्यंत किंवा पृष्ठ बाकी राहेपर्यंत टिकते. कार्ड कोणतीही विनंती पाठवत नाही आणि फाइल डाउनलोड करण्याची ऑफर देत नाही.

API मार्क्स `stale` वाचणे शक्यतो कालबाह्य असल्याचे दाखवले आहे. `unavailable` वर चिन्हांकित केलेले वाचन त्याच्या कारणासह दाखवले जाते, शून्य म्हणून कधीही नाही.

टक्केवारी योजनांवर जेव्हा API अहवाल देतो तेव्हा पृष्ठ स्वतःचा हिस्सा काढतो. त्यात म्हटले आहे की संख्या एक अंदाज आहे आणि त्याच्या दोन भागांची नावे आहेत. प्रति-मॉडेल मर्यादा फक्त खाते दर्शवतात.

जेव्हा विंडोमध्ये `members` असते, तेव्हा त्याचे कार्ड स्लॉट क्रमाने प्रति सदस्य एक सेगमेंट असलेली बार देखील दर्शवते. विचारणाऱ्या कीचा विभाग उच्चारण रंग वापरतो. इतर विभाग थीमच्या चार्ट रंगांद्वारे चक्र करतात. मजकूर आख्यायिका प्रत्येक विभागाला त्याच्या मूल्यासह सूचीबद्ध करते, म्हणून काहीही रंगावर अवलंबून नसते. विभागांना `You` किंवा `Member N` असे लेबल केले जाते, जेथे N हा स्लॉट आहे.

### पृष्ठासाठी समर्पित पोर्ट

`QUOTA_PANEL_PORT` दुसरा श्रोता उघडतो जो फक्त सेल्फ-सर्व्हिस पेजला सर्व्ह करतो. व्हेरिएबल सेट केल्याशिवाय ते बंद आहे. `QUOTA_PANEL_HOST` हा बाइंड पत्ता आहे आणि `127.0.0.1` ला डीफॉल्ट आहे.

श्रोता हे मार्ग मुख्य पोर्टवर रिले करतो आणि प्रत्येक इतर मार्गासाठी 404 उत्तर देतो:

| मार्ग                                                                    | सर्व्ह करते                         |
| ------------------------------------------------------------------------ | ----------------------------------- |
| `/quota/{provider}`                                                      | पान                                 |
| `/api/v1/me/quota/{provider}`, `/v1/me/quota/{provider}`                 | कोटा दृश्य पृष्ठ वाचतो              |
| `/api/v1/me/usage`, `/v1/me/usage`                                       | पृष्ठ वाचत असलेली वापर मालिका       |
| `/_next/static/`                                                         | बिल्डच्या स्क्रिप्ट, शैली आणि फॉन्ट |
| `/favicon.ico`, `/favicon.svg`, `/icon-512.png`, `/apple-touch-icon.png` | चिन्हे                              |

`GET` आणि `HEAD` शरीराशिवाय रिले केले जातात. मुख्य भागासह एक विनंती देखील रिले केली जाते: कोटा व्ह्यू पाथचा एक `PATCH`, जो पृष्ठ कर्जाची निवड जतन करण्यासाठी पाठवते. इतर कोणतीही पद्धत 404 उत्तर देते, CONNECT विनंती वगळता, ज्याचे कनेक्शन कोणतेही उत्तर नसताना बंद आहे. बॉडी घोषित करणारी इतर कोणतीही विनंती 404 उत्तर देते आणि तिचे कनेक्शन बंद आहे. अपग्रेड विनंत्या नाकारल्या जातात आणि त्यांचे कनेक्शन बंद केले जाते. API पोर्ट प्रमाणे डॉट सेगमेंट किंवा फ्रॅगमेंट मार्कर असलेला मार्ग नाकारला आहे. प्रिंट करण्यायोग्य ASCII बाहेरील वर्णासह विनंती लक्ष्य देखील आहे. या पोर्टच्या स्वतःच्या तपासणीपूर्वी लक्ष्यातील एका रॉ कंट्रोल कॅरेक्टरला HTTP पार्सरद्वारे 400 उत्तर दिले जाते. हेडरची विनंती करा की फ्रेमवर्क त्याच्या स्वतःच्या वापरासाठी राखीव रिले केले जात नाही: `x-middleware-`, `x-invoke-`, `x-nextjs-`, `x-now-` किंवा `x-next-` ने सुरू होणारी नावे आणि `x-matched-path` आणि `next-resume` ही नावे. विनंती त्यांच्याशिवाय रिले केली जाते. डॅशबोर्ड, लॉगिन पृष्ठ, व्यवस्थापन API आणि अनुमान मार्ग या पोर्टद्वारे पोहोचू शकत नाहीत.

`PATCH` `Content-Type: application/json` असणे आवश्यक आहे, कोणत्याही पॅरामीटरशिवाय किंवा फक्त `charset=utf-8` सह. त्यात 1 ते 4096 पर्यंत एक `Content-Length` असणे आवश्यक आहे, साधे अंक म्हणून लिहिलेले आणि `Transfer-Encoding` नाही. यापैकी एक नियम तोडणारा `PATCH` उत्तर देतो 404. काही विकृत लांबी, जसे की स्वाक्षरी किंवा पुनरावृत्ती, या पोर्टच्या स्वतःच्या तपासणीपूर्वी HTTP पार्सरद्वारे 400 उत्तर दिले जाते. मुख्य पोर्टशी संपर्क साधण्यापूर्वी पोर्ट घोषित बाइट्स वाचतो आणि त्यांच्यासाठी जास्तीत जास्त 5 सेकंद प्रतीक्षा करतो. तोपर्यंत पूर्ण नसलेली बॉडी 404 उत्तर देते आणि त्याचे कनेक्शन बंद होते. त्या प्रकरणात, किंवा क्लायंट प्रथम सोडल्यावर काहीही मुख्य पोर्टपर्यंत पोहोचत नाही. पोर्ट त्याच `Content-Length` सह, घोषित बाइट्स अचूकपणे रिले करते. त्यांच्या नंतरचे बाइट कनेक्शनवर पुढील विनंती म्हणून वाचले जातात. समोरील TLS रिव्हर्स प्रॉक्सीने `Content-Length` फॉरवर्ड करणे आवश्यक आहे आणि विनंतीचे मुख्य भाग पुन्हा खंडित करू नये. मुख्य पोर्ट `Authorization` शीर्षलेखातील API की तपासते, `GET` साठी.

404 शरीर `{"error":"not_found","message":"Not found."}` आहे. अयशस्वी रिले `detail` फील्डशिवाय 502 (`api_bridge_unavailable`) किंवा 504 (`api_bridge_timeout`) उत्तर देते.

ऐकणारा `QUOTA_SELF_PANEL` वाचत नाही आणि तो पान चालू करत नाही. ध्वज बंद असताना, मुख्य पोर्टवर पृष्ठ आणि त्याचे API उत्तर 404, आणि श्रोता ते उत्तर रिले करतो.

डेव्हलपमेंट सर्व्हर (`next dev`) अंतर्गत, पृष्ठ या पोर्टद्वारे परस्परसंवादी होत नाही. डेव्हलपमेंट हॉट-रीलोड सॉकेट ही अपग्रेड विनंती आहे आणि पोर्टने ती नाकारली आहे. विकसित करताना मुख्य पोर्ट वापरा.

पोर्ट साधा HTTP सर्व्ह करते आणि पृष्ठ API की पाठवते. डिफॉल्ट बाइंड ॲड्रेस ठेवा आणि त्याच्या समोर TLS सह रिव्हर्स प्रॉक्सी ठेवा. लूपबॅक व्यतिरिक्त एक बंधन पत्ता ही सूचना लॉग करतो:

```text
[Quota Panel] Bound to <host>. This port serves plain HTTP and the page sends API keys. Put a TLS reverse proxy in front of it.
```

फॉरवर्डिंग हेडर न पाठवणारा लूपबॅक पीअर मुख्य पोर्टवर स्थानिक म्हणून गणला जातो. त्यामुळे त्याच होस्टवरील प्रॉक्सीने `X-Forwarded-For` पाठवणे आवश्यक आहे. खाजगी पत्त्यावरील प्रॉक्सी केवळ `OMNIROUTE_TRUST_PROXY=private` (किंवा `lan`) सह त्या शीर्षलेखासाठी विश्वसनीय आहे. इतर कोणत्याही पीअरचा त्याच्या कनेक्शनच्या पत्त्याद्वारे अहवाल दिला जातो आणि त्याने पाठवलेले फॉरवर्डिंग शीर्षलेख टाकले जातात.

श्रोत्याकडे एका वेळी जास्तीत जास्त 256 कनेक्शन असतात. क्लायंटकडे विनंती शीर्षलेख पाठवण्यासाठी 10 सेकंद आणि संपूर्ण विनंती पाठवण्यासाठी 30 सेकंद असतात. निष्क्रिय ठेवलेले-जिवंत कनेक्शन सुमारे 5 सेकंदांनंतर बंद होते. 60 सेकंदांसाठी कोणतेही क्रियाकलाप नसलेले कनेक्शन बंद आहे. ही मूल्ये निश्चित आहेत. समोरील रिव्हर्स प्रॉक्सीवर कनेक्शन आणि दर मर्यादा सेट करा. समोरील रिव्हर्स प्रॉक्सीने त्याचे निष्क्रिय अपस्ट्रीम कनेक्शन 5 सेकंदांपेक्षा कमी ठेवावे किंवा त्यांचा पुन्हा वापर करू नये. मुख्य पोर्टचा रिले API पोर्ट (`API_BRIDGE_*`) च्या अपस्ट्रीम टाइमआउट्सचा वापर करतो.

`API_PORT` सेट नसताना ऐकणारा देखील सुरू होतो. `QUOTA_PANEL_PORT` फक्त अंकांमध्ये लिहिलेले 1 ते 65535 पर्यंतचे पोर्ट असणे आवश्यक आहे. ते डॅशबोर्ड पोर्ट आणि API पोर्टपेक्षा वेगळे असले पाहिजे. लाइव्ह WebSocket सर्व्हर चालू असताना, ते `LIVE_WS_PORT` (डिफॉल्ट 20132) पेक्षा वेगळे देखील असले पाहिजे. इतर कोणतेही मूल्य काहीही उघडत नाही आणि एक चेतावणी लॉग करते. नाकारलेल्या मूल्याबद्दल चेतावणी व्हेरिएबलला नाव देते आणि मूल्याची पुनरावृत्ती करत नाही. आधीच वापरात असलेले पोर्ट काहीही उघडत नाही आणि ही चेतावणी लॉग करते:

```text
[Quota Panel] Port <port> is already in use. The quota panel port stays off.
```

`OMNIROUTE_BASE_PATH` सेटसह, श्रोता त्या उपसर्गाखाली वरील प्रत्येक मार्गाची अपेक्षा करतो. बिल्ड टाइम आणि रन टाइममध्ये समान `OMNIROUTE_BASE_PATH` वापरा. ते अग्रगण्य स्लॅशसह लिहा आणि ट्रेलिंग स्लॅश न करता, उदाहरणार्थ `/omniroute`. `/` आणि `/omniroute/` सह आणखी एक आकार, चेतावणी देऊन बंदर सोडतो, जरी बिल्ड ते फॉर्म स्वीकारते. त्याचप्रमाणे बेस पाथ ज्याच्या पहिल्या सेगमेंटला ऍप्लिकेशन मार्गाचे नाव दिले जाते: `api`, `v1`, `v1beta`, `_next`, `quota`, `dashboard`, `docs`, `login`, `codex`, `responses`, `anthropic`, `openai`, `v0`, किंवा कोणत्याही परिस्थितीत `connect`.

मर्यादा:

- या पोर्टवर ट्रेलिंग स्लॅशसह `/quota/{provider}/` 404 उत्तर देते.
- सेवा कर्मचारी आणि वेब ॲप मॅनिफेस्ट या पोर्टवर दिले जात नाहीत.
- डॅशबोर्डमध्ये सानुकूल फेविकॉन सेट या पोर्टवर दर्शविला जात नाही.
- जेव्हा ऍप्लिकेशन बेस पाथ अंतर्गत चालते तेव्हा चिन्ह दर्शवले जात नाहीत.
- बंदर साधा HTTP/1.1. बोलतो
- प्रक्रिया रीस्टार्ट होईपर्यंत अयशस्वी झालेल्या बंधनाचा पुन्हा प्रयत्न केला जात नाही.
- श्रोत्याला प्रति क्लायंट पत्त्यावर कोणतेही कनेक्शन किंवा दर मर्यादा नाही.
- कंटेनर सेटअप या विभागामध्ये समाविष्ट नाहीत.

## समस्या निवारण

### Redis कॉन्फिगर केलेले आहे, परंतु कनेक्ट होत नाही

`ioredis` इन्स्टॉल केलेले आहे (`npm ls ioredis`) आणि `QUOTA_STORE_REDIS_URL`
पर्यंत पोहोचता येते हे तपासा. कनेक्शन अयशस्वी झाल्यास फॅक्टरी SQLite वर
फॉलबॅक करते (`warn` स्तरावर नोंद केली जाते).

### `peek` जुना डेटा परत करते / फेल-ओपन होते

`peek` ने अपवाद दिल्यास, `enforceQuotaShare` परिणामाला "परवानगी द्या" (फेल-ओपन)
असे मानते. मूळ कारण ओळखण्यासाठी `pino` लॉगमधील `quota:enforce` आणि
`quota:factory` नोंदी तपासा.

### वापर काउंटरमध्ये तफावत

प्रत्यक्ष प्रदाता वापर काउंटर्सपेक्षा वेगळा असल्यास ते अपेक्षित आहे — 2-बकेट
स्लाइडिंग विंडोमध्ये विंडो सीमांवर ~1% त्रुटी असते आणि `consume` हे
प्रतिसादानंतर फायर-अँड-फरगेट पद्धतीने चालते. सॅच्युरेशन सिग्नल
(`saturationSignals.ts`) 30 सेकंदांच्या TTL सह प्रदात्याचा प्रत्यक्ष वापर
वाचतो आणि त्यानुसार `globalUsedPercent` समायोजित करतो.

### पूलच्या वापर-दरासाठी "डेटा नाही" दिसते

`computeBurnRate` साठी किमान 2 ऐतिहासिक नमुने आवश्यक आहेत. पूर्वीचे `consume`
कॉल नसलेल्या नवीन पूलमध्ये `tokensPerSecond: 0` आणि `timeToExhaustionMs: null`
दिसेल.

## localStorage मधून स्थलांतर

`/dashboard/costs/quota-share` प्रथम लोड झाल्यावर, `useLocalStoragePoolMigration` हुक पुढील बाबी तपासतो:

1. `localStorage.getItem("omniroute:quota-share:pools")` रिक्त नाही.
2. `GET /api/quota/pools` हे `[]` परत करते (DB रिक्त आहे).

दोन्ही अटी सत्य असल्यास, तो प्रत्येक लेगसी पूल बॅचमध्ये `POST /api/quota/pools` वर पोस्ट करतो आणि त्यानंतर localStorage की काढून टाकतो. हे स्थलांतर आयडेम्पोटंट आहे: अट 2 पुन्हा स्थलांतर होण्यापासून प्रतिबंध करते.

## DB स्कीमा सारांश

स्थलांतर `078`, `079` आणि `085` द्वारे जोडलेल्या तीन सारण्या :

- `quota_pools` + `quota_allocations` — पूल व्याख्या आणि प्रति-की वाटप.
- `quota_consumption` — रोलिंग 2-बकेट काउंटर प्रति `(apiKeyId, dimensionKey)`.
- `provider_plans` — मॅन्युअल प्रदाता योजना ओव्हरराइड करते (परिमाणे JSON प्रति connectionId).

सर्व सारण्या idempotent `CREATE TABLE IF NOT EXISTS` स्थलांतराद्वारे जोडल्या गेल्या.

संमती दिलेल्या कर्जामध्ये तीन स्तंभ जोडले जातात: `quota_allocations.lending_percent` (पूर्णांक, डीफॉल्ट 0), `quota_allocations.lending_until` (युग मिलिसेकंद, किंवा `NULL` कोणतीही अंतिम मुदत नाही) आणि `quota_pools.borrow_mode` (डीफॉल्ट `saturation`). त्याचे स्थलांतर केवळ हे स्तंभ जोडते आणि विद्यमान पंक्ती लिहित नाही.

टक्के एट्रिब्युशन बुकमध्ये `quota_percent_ledger` (एक पंक्ती प्रति पूल, खाते आणि योजना विंडो) आणि `quota_percent_ledger_tokens` (प्रति पूल, खाते आणि API की एक टोकन काउंटर) जोडले जाते. `src/lib/db/quotaPercentLedger.ts` त्यांना वाचतो आणि लिहितो.
