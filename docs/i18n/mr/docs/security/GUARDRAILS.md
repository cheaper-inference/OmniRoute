> हुक कोणत्या रूट्स आणि प्रतिसाद मार्गांपर्यंत पोहोचतात, विलीन केलेले अक्षम हेडर्स (#16412), अनिवार्य सीमा म्हणून इंजेक्शन ब्लॉक मोड (#16413), आणि पोस्ट-कॉलपूर्वी प्रतिसाद कोण पाहतो)

गार्डरेल्स OmniRoute आणि अपस्ट्रीम प्रदात्यांच्या दरम्यानच्या सीमेवर सुरक्षा, धोरण आणि सामग्री रूपांतरे लागू करतात. प्रत्येक गार्डरेल विनंती पेलोड (`preCall`) आणि अपस्ट्रीम प्रतिसादांचे (`postCall`) परीक्षण करू शकतो (आणि ऐच्छिकतेने नाकारू, रूपांतरित किंवा टिप्पणी-अधिष्ठित करू शकतो).

ही प्रणाली **फेल-ओपन** आहे: कार्यान्वित होत असताना गार्डरेलने त्रुटी टाकल्यास, रजिस्ट्री ती त्रुटी नोंदवते आणि विनंती अयशस्वी करण्याऐवजी पुढील गार्डरेलसह पुढे चालू ठेवते. अवरोधन हा एक स्पष्ट निर्णय आहे (`block: true`), कधीही अपघाताने होत नाही. याला एकच अपवाद आहे — रद्द केलेली विनंती: कॉलरचा `signal` रद्द झाल्यावर, त्रुटी टाकणारा गार्डरेल वगळला जाण्याऐवजी हुक रन नाकारतो.

हुक प्रत्येक रूटवर किंवा प्रत्येक प्रतिसादावर चालत **नाहीत**. गार्डरेलवर सुरक्षा नियंत्रण म्हणून विसंबण्यापूर्वी [व्याप्ती आणि मर्यादा](#coverage-and-limits) वाचा.

## अंगभूत गार्डरेल्स

रजिस्ट्री आयात केल्यावर प्राधान्य क्रमाने सहा गार्डरेल्स स्वयं-लोड करते
(पहा `registry.ts` → `registerDefaultGuardrails()`):

| प्राधान्य | नाव                 | टप्पा (टप्पे)  | फाइल                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

कमी प्राधान्य क्रमांक **आधी** चालतात.

### व्हिजन ब्रिज (`visionBridge.ts`) — मोडॅलिटी ब्रिज PR-1

GLM 5.3 बेस मॉडेल आणि `glm-5.3-{low,high,max}` यांच्याकडे स्पष्ट
`supportsVision:false` रजिस्ट्री/स्पेक मेटाडेटा आहे. GLM 5.3 Flash प्रकार
नेटिव्ह-व्हिजन मॉडेल्सच राहतात. Claude Code चा `/v1/messages` रूट
Claude-to-OpenAI भाषांतरापूर्वी **आधीच** सामायिक `handleChat` प्री-कॉल गार्डरेल
शृंखलेत प्रवेश करतो; त्या भाषांतराद्वारे ते OpenAI `image_url` सामग्रीत उचलले
जाण्यापूर्वी नेस्टेड `Read` टूल-परिणामातील प्रतिमांचे वर्णन केले किंवा त्या हाताळल्या
गेल्या पाहिजेत (#17069).

**नॉन-व्हिजन मॉडेल्स**कडे जाणाऱ्या प्रतिमा-युक्त विनंत्या अडवते आणि एकतर संपूर्ण
विनंती व्हिजन-सक्षम मॉडेलकडे पुनर्मार्गित करते किंवा अपस्ट्रीम कॉलपूर्वी प्रतिमा भाग
कॉन्फिगर करण्यायोग्य व्हिजन मॉडेलने तयार केलेल्या मजकूर वर्णनांनी बदलते. यामुळे
फक्त-मजकूर प्रदाते मल्टिमोडल पेलोड पारदर्शकपणे हाताळू शकतात.

प्रवाह:

1. लक्ष्य मॉडेल आधीच व्हिजन समर्थन करत असल्यास वगळा (जोपर्यंत ते
   फोर्स्ड-ब्रिज सूची `isVisionBridgeForcedModel` मध्ये दिसत नाही).
2. `extractImageParts(messages)` द्वारे प्रतिमा भाग काढा
   (`visionBridgeHelpers.ts`), जे `open-sse/utils/mediaParts.ts` मधील
   **युनिफाइड मीडिया डिटेक्टर** `detectMediaParts()` कडे सोपवते — कॉम्बो
   सुसंगतता फिल्टरसह सामायिक केलेला सत्याचा एकमेव स्रोत.
   एक्स्ट्रॅक्शन `replaceImageParts` परत जोडू शकणाऱ्या आकारांपुरतेच अलाउलिस्टेड
   आहे (extract↔replace करार): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"`, आणि Responses
   API `input_image`. Claude Code `tool_result.content` आणि Responses टूल
   आउटपुटमध्ये नेस्टेड असलेल्या जुळणाऱ्या प्रतिमा देखील काढल्या जातात आणि त्यांच्या
   मूळ मार्गांवर बदलल्या जातात; केवळ-निर्देशक आकार हे कॉम्बो-फिल्टर साहित्य आहेत
   आणि ते काढले जात नाहीत. एकही प्रतिमा सापडली नाही तर वगळा.
3. `resolveVisionBridgeRuntimeSettings()` द्वारे रनटाइम कॉन्फिग ठरवा
   (`src/shared/constants/modalityBridgeDefaults.ts`): नवीन `modalityBridge*`
   सेटिंग्ज की जिंकतात; लेगसी `visionBridge*` की **एक-चक्र फॉलबॅक**
   (रोलबॅक विंडो) म्हणून राहतात. ब्रिज अक्षम असताना कोणत्याही मीडिया
   ट्रॅव्हर्सलपूर्वीच वगळा.
4. मोड निवडक (`modalityBridgeVisionMode`, खालील तक्ता पहा) पुनर्मार्गन की
   वर्णन हे ठरवतो. पुनर्मार्गनामध्ये फक्त `model` बदलेलेला `modifiedPayload` परत
   येतो, तसेच मेटा `{ rerouted, fromModel, toModel, imagesKept }`.
5. वर्णन मार्ग: प्रतिमा `maxImages` इतक्या मर्यादित करा, कार्य-जागरूक प्रॉम्प्ट
   तयार करा, वर्णन कॅशे तपासा, व्हिजन मॉडेलला **समांतरपणे** कॉल करा
   (`Promise.allSettled`), आणि त्यांच्या जागी `[Image N]: <description>` मजकूर
   भाग टाका. अयशस्वी वर्णन `null` देते: अज्ञात/व्हिजन-सक्षम लक्ष्यांसाठी कच्ची
   प्रतिमा जसीच्या तशी जतन केली जाते (#4012), परंतु **निश्चित फक्त-मजकूर थेट
   लक्ष्य** किंवा शून्य-व्हिजन कॉम्बोला प्रत्येक अवर्णित प्रतिमेसाठी स्पष्ट
   `(unavailable — no vision-capable provider connected)` मजकूर स्टब मिळतो,
   ज्यात आंशिक अपयशे आणि वर्णन-कॉल मर्यादेबाहेरील प्रतिमा समाविष्ट आहेत
   (#17069). विद्यमान सर्व-अयशस्वी कॉम्बो वर्णन फॉलबॅक जसाच्या तसा राहतो
   (#8430).
6. `modifiedPayload` + मेटा (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) परत करा.

#### मोड निवडक (`modalityBridgeVisionMode`)

| मोड        | डीफॉल्ट | वर्तन                                                                                                                                                                                                                                                                                                        |
| ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔       | जुनी ह्युरिस्टिक, अबदलित (#6640/#7204): non-combo/`auto/` मॉडेल्स सर्वोत्तम व्हिजन मॉडेलकडे रिराउट होतात, जोपर्यंत मूळ मॉडेलमध्ये आधीच वापरण्यायोग्य क्रेडेन्शियल्स नाहीत (मग describe); combo टार्गेट्स नेहमी describe करतात.                                                                               |
| `describe` |         | नेहमी describe — reroute ब्लॉक पूर्णपणे वगळला जातो; वापरकर्त्याने निवडलेले मॉडेल नेहमी उत्तर देते.                                                                                                                                                                                                           |
| `reroute`  |         | जबरदस्तीने reroute: keep-credentialed-model गार्ड बायपास केला जातो. reroute-**target** क्रेडेन्शियल गार्ड अजूनही लागू राहतो — जेव्हा कोणतेही वापरण्यायोग्य व्हिजन टार्गेट अस्तित्वात नसते, तेव्हा ब्रिज describe करण्याऐवजी किंवा text-only टार्गेटकडे कच्च्या प्रतिमा पाठवण्याऐवजी स्पष्ट एररसह ब्लॉक करतो. |

फोर्स्ड मोड्स auto ह्युरिस्टिक चालू होण्याआधीच शॉर्ट-सर्किट होतात; `auto` वर्तन
pre-PR-1 गार्डरेलशी बाइट-समान आहे.

#### API-की स्कोप (`visionBridgeKeyScope.ts`)

जेव्हा कॉलरची API की `allowedConnections`, कोटा पूल
(`allowedQuotas`) किंवा मॉडेल्स (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) मर्यादित करते, तेव्हा ब्रिज केवळ तेच
reroute आणि describe मॉडेल्स निवडतो जे की वापरू शकते, आणि केवळ त्या
कनेक्शन्सवर जे की वापरू शकते. describe कॉल नंतर नेहमी
`x-omniroute-self-loop-key-id` हेडरसह OmniRoute सेल्फ-लूपमधून जातो,
जेणेकरून प्राप्त होणारी चॅट विनंती त्या कीचे कनेक्शन आणि मॉडेल धोरण
पुन्हा लागू करते. `enforceApiKeyPolicy()` तो हेडर केवळ सेल्फ-लूप बियररसोबतच
मान्य करते, म्हणून ते केवळ प्रवेश संकुचित करू शकते, आणि रिझॉल्व्ह न होणारा
id नाकारला जातो.

जर कीसाठी कोणतेही व्हिजन मॉडेल परवानगीपात्र नसेल, तर **निश्चित text-only
टार्गेट** प्रतिमा बाइट्स अक्षम अपस्ट्रीमकडे फॉरवर्ड करण्याऐवजी स्पष्ट HTTP 400 सह
प्रतिमा विनंती स्थानिक पातळीवर नाकारते (#17069). अज्ञात किंवा मूळ व्हिजन क्षमता
असलेल्या टार्गेट्ससाठी, describe पाथ त्याचे पूर्वीचे fail-open वर्तन राखते
(meta `{ skipped: true, reason: "no_permitted_vision_model" }`).
की नसलेल्या विनंत्या, आणि या निर्बंधांशिवाय असलेल्या की, पूर्वीप्रमाणेच
वागतात.

#### टास्क-अवेअर describe प्रॉम्प्ट (`modalityBridgeVisionTaskAware`)

डीफॉल्ट **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) बेस
describe प्रॉम्प्टला **शेवटच्या वापरकर्ता संदेशाचा** मजकूर (500 अक्षरांपर्यंत छाटलेला)
जोडते, जेणेकरून वर्णन वापरकर्त्याने प्रत्यक्षात विचारलेल्या गोष्टीकडे वळते
(codex-vision-proxy पॅटर्न) आणि व्हिजन मॉडेलला दृश्यमान मजकूर
ट्रान्सक्राइब करण्यास सांगते. फ्लॅग बंद असल्यास — किंवा वापरकर्ता मजकूर नसल्यास —
बेस प्रॉम्प्ट न बदलता वापरला जातो.

describe सेल्फ-लूपची स्वतःची OpenAI-सुसंगत विनंती (`visionBridgeHelpers.ts`
मधील `callVisionModelSingle()`) नेहमी `image_url.detail: "high"` मागते —
बिनशर्त, प्रत्येक कॉलर/प्रोव्हायडरसाठी, कोणत्याही क्लायंट सिग्नलवर अवलंबून नाही.
लो-डिटेल सॅम्पलिंग या प्रॉम्प्टने मागितलेल्या नेमक्या टेक्स्ट-ट्रान्सक्रिप्शन
टास्कसाठी OCR अचूकता घटवते, म्हणून describe कॉल स्वतः नेहमीच हाय डिटेल मागतो,
मूळ इनबाउंड विनंतीने कोणतीही डिटेल पातळी वापरली असली तरी. याचा
परिणाम केवळ अंतर्गत describe विनंती बॉडीवर होतो; हे OmniRoute प्राइमरी
विनंतीवर कॉलरचा स्वतःचा `image_url.detail` कसा फॉरवर्ड करते यात बदल करत नाही —
तो डीफॉल्ट स्वतंत्रपणे लागू केला जातो, आणि केवळ शोधलेल्या OpenCode क्लायंट्ससाठी,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) मध्ये.
describe सेल्फ-लूपच्या Anthropic वायर-फॉरमॅट ब्रँचमध्ये `detail` फील्ड नाही
आणि ती दोन्ही डीफॉल्ट्सपासून प्रभावित होत नाही.

#### Describe आउटपुट मर्यादा (`modalityBridgeVisionMaxChars`)

| की                             | डीफॉल्ट | पल्ला               |
| ------------------------------ | ------- | ------------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` किंवा 100–50000 |

`0` (डीफॉल्ट) म्हणजे **मर्यादा नाही** — `callVisionModel()` ने परत केलेले वर्णन
न बदलता पुढे दिले जाते, विद्यमान वर्तन टिकवून. 100–50000 पल्ल्यातील
कोणतेही मूल्य वर्णनाला `…` प्रत्ययासह छाटते, त्यानंतर ते
`[Image N]: <description>` म्हणून परत जोडले जाते
(`src/lib/guardrails/visionBridge.ts` मधील `VisionBridgeGuardrail.preCall()`).
डिटेल-जड OCR टास्क्ससाठी हे वाढवा जिथे डाउनस्ट्रीम मॉडेलला संपूर्ण
ट्रान्सक्रिप्शन हवे असते; बोलक्या व्हिजन मॉडेल्सवर टोकन वापर मर्यादित करण्यासाठी
ते कमी करा. डॅशबोर्ड फील्ड Vision टॅबच्या Advanced पॅनेलवर आहे
(`ModalityBridgeVisionTab.tsx` मधील `modality-bridge-max-chars`) आणि 1 ते 99 मधील
कोणतेही मूल्य 100 च्या तळाशी क्लॅम्प करते, तर स्पष्ट `0` न बदलता ठेवते — `0` हे
स्वतःच्या हक्काने वैध Zod मूल्य आहे
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), केवळ "unset"
डीफॉल्ट नाही.

केलेले** ब्रिज मॉडेल आहे, प्रत्यक्षात उत्तर देणारे मॉडेल नाही —
`callVisionModel` अंतर्गत फॉल बॅक करू शकते, आणि प्रत्येक प्रयत्नानुसार कींग
केल्याने कॅशे विखुरी होईल. अयशस्वी describes कधीही कॅश केले जात नाहीत. सेटिंग्ज:

#### रिमोट इमेज नॉर्मलायझेशन (सेल्फ-लूप describe/base64 फेच)

जेव्हा ब्रिज स्वतः **रिमोट** इमेज फेच करतो — Anthropic describe सेल्फ-कॉल आणि claude-wire-format base64 रूपांतरण (`ensureBase64ImagesForClaudeWire`), दोन्ही `visionBridgeHelpers.ts` मधील `fetchRemoteImageAsDataUri()` मार्फत — तेव्हा मिळालेला data URI व्हिजन-मॉडेल विनंतीत एम्बेड होण्यापूर्वी `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) मधून पास केला जातो. अतिमोठ्या इमेजेस **2048px लांब बाजू** वर डाउनस्केल केल्या जातात (OpenAI/Anthropic सर्व्हर-साइडवर आधीपासून लागू करत असलेल्या रीसाइझ कॅपशी जुळणारी), ज्यामुळे व्हिजन मॉडेल काय पाहते ते न बदलता अपलोड बाइट्स/लेटन्सी कमी होते. रीसाइझिंग `sharp` वापरते, जे dynamic import मार्फत लोड केले जाते: ज्या प्लॅटफॉर्मवर त्याचे नेटिव्ह बायनरी लोड होण्यात अयशस्वी होते, तिथे `normalizeDataUri()` **कधीही थ्रो करत नाही** — ते मूळ बाइट्सच्या पासथ्रूवर परत जाते, त्यामुळे describe/base64-रूपांतरण मार्ग नेहमी चालू राहतो. इमेज नसलेले बाइट्स (डिकोड करण्यायोग्य इमेज परत न देणारे फेच) देखील न स्पर्श करता पासथ्रू केले जातात. हे नॉर्मलायझेशन केवळ ब्रिज त्याच्या स्वतःच्या सेल्फ-कॉलसाठी फेच करत असलेल्या इमेजेसपुरते मर्यादित आहे — ते कॉलरच्या रॉ पासथ्रू पेलोडवर कधीही लागू केले जात नाही, हे opt-in-only म्युटेशन तत्त्वाशी (हार्ड नियम #20) सुसंगत आहे.

#### सेटिंग्ज स्कीमा + मायग्रेशन

नवीन `modalityBridge*` की `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`) मध्ये Zod-वैध केल्या जातात: `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` त्रिकूट, आणि Audio Bridge वापरत असलेला `modalityBridgeAudio*` गट. `141_modality_bridge_settings.sql` मायग्रेशन विद्यमान लेगसी `visionBridge*` मूल्ये जुळणाऱ्या नवीन कींवर कॉपी करते (आयडेम्पोटंट, ऑपरेटरने सेट केलेले `modalityBridge*` मूल्य कधीही ओव्हरराइट करत नाही); लेगसी की एका रिलीज सायकलसाठी रीड फॉलबॅक म्हणून स्वीकारल्या जात राहतात.

#### पारदर्शकता हेडर + आकडेवारी

Describe-रूपांतरित प्रतिसादांमध्ये `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` असते (`modalityBridge/bridgeStats.ts` मधील `buildModalityBridgeHeader()` द्वारे तयार केलेले, `src/sse/handlers/chatHelpers.ts` मधील `withModalityBridgeHeader()` द्वारे स्टॅम्प केलेले). रीरूट केलेल्या विनंत्यांना **कोणतेही** हेडर मिळत नाही — पेलोड न स्पर्श केलेला होता आणि मॉडेल स्वॅप प्रतिसाद बॉडीच्या `model` फील्डमध्ये आधीच दिसत असते.

`GET /api/modality-bridge/stats` (मॅनेजमेंट ऑथ, `GET /api/settings` प्रमाणेच स्तर) `vision`, `audio` आणि `video` साठी इन-मेमरी प्रति-मोडॅलिटी काउंटर्स `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` परत करते. `averageLatencyMs` भाजक म्हणून सर्व प्रयत्न नव्हे तर `latencySamples` वापरते; टायमिंग नसलेली ऑपरेशन शून्य-मिलीसेकंद नमुना तयार करत नाही. `bridged` यशस्वी रूपांतरणांसाठी बॅकवर्ड-कंपॅटिबल उपनाव राहते; अयशस्वी प्रयत्न ते वाढवत नाहीत. प्रोसेस रीस्टार्टवर काउंटर्स डिझाइननुसार रीसेट होतात (टेलीमेट्री, अकाउंटिंग नाही).

#### डॅशबोर्ड कॉन्फिगरेशन

समर्पित डॅशबोर्ड पेज `/dashboard/settings/modality-bridge` आहे. त्याचे URL-अॅड्रेसेबल `Vision`, `Audio` आणि `Video` टॅब `tab` मूल्य बदलताना क्वेरी पॅरामीटर्स टिकवतात. व्हिजन टॅब सक्षमता, मोड, मॉडेल निवड (स्वयंचलित डीफॉल्टसह), टास्क-अवेअर प्रॉम्प्टिंग, प्रगत टाइमआउट/इमेज/वर्णन-लांबी/कॅश मर्यादा, रनटाइम काउंटर्स आणि संरक्षित नमुना विनंती उघड करतो. ऑडिओ टॅब देखील लाइव्ह आहे: तो सक्षमता, Auto सह STT-ओनली मॉडेल पिकर, टाइमआउट/मॅक्स-क्लिप मर्यादा, ऑडिओ काउंटर्स आणि `input_audio` नमुना चाचणी उघड करतो. व्हिडिओ टॅब कार्यक्षम आहे: तो FFmpeg/ffprobe रनटाइम स्थिती नोंदवतो — चार स्पष्ट UI स्थितींपैकी एक (प्रोब प्रगतीपथावर असताना किंवा पूर्ण होऊ न शकल्यास `unknown`, प्रोब क्लायंट-साइडवर वगळला जाणाऱ्या नॉन-लूपबॅक डॅशबोर्ड होस्टवर `restricted`, प्रोब झाल्यानंतर आणि हरवल्याची पुष्टी झाल्यावर `unavailable`, किंवा FFmpeg/ffprobe आवृत्त्यांसह `available`) — सक्षम/मॉडेल/फ्रेम/व्हिडिओ/टाइमआउट मर्यादा टिकवतो, मॉडेल पिकर व्हिजन-सक्षम मॉडेलांपुरता फिल्टर करतो आणि व्हिडिओ काउंटर्स उघड करतो.

AI सेटिंग्जखालील पूर्वीचे Vision Bridge कार्ड नवीन पेजशी जोडणारी कंपॅटिबिलिटी लिंक आहे; ते आता फॉर्मची दुसरी प्रत धारण करत नाही. Media Providers विद्यमान Speech-to-Text प्लेग्राउंड न काढता Image-to-Text आणि Speech-to-Text वर्कफ्लो संबंधित Modality Bridge टॅबांशी लिंक करतात.

**सेल्फ-लूप अॅडमिशन बायपास:** जेव्हा describe कॉल OmniRoute च्या स्वतःच्या `/v1` सेल्फ-लूपमधून (नॉन-स्टँडर्ड प्रोव्हायडर मॉडेल) रूट होतो, तेव्हा सब-विनंती `x-omniroute-admission-bypass: internal` पाठवते आणि रिझॉल्व्ह केलेल्या सेल्फ-लूप क्रेडेन्शियलने प्रमाणित केली जाते — लोकल मोडमध्ये लोकल `sk_omniroute` सेंटिनेल, किंवा ऑपरेटर-कॉन्फिगर केलेली `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env की (#1350) जेणेकरून `REQUIRE_API_KEY=true` डिप्लॉयमेंट्स अजूनही describe कॉल चालवू शकतील. बायपास फक्त त्या नेमक्या क्रेडेन्शियल्ससाठीच मान्य केला जातो, त्यामुळे बाह्य क्लायंट अॅडमिशन वगळण्यासाठी हेडर वापरू शकत नाहीत.

लेगसी डीफॉल्ट्स `src/shared/constants/visionBridgeDefaults.ts` मध्ये आहेत; नवीन मोड/टास्क-अवेअर/कॅश डीफॉल्ट्स आणि सेटिंग्ज रिझॉल्व्हर `src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत. गार्डरेल `deps` कन्स्ट्रक्टर ऑप्शन उघड करते जेणेकरून चाचण्या बनावट `getSettings` आणि `callVisionModel` इम्प्लिमेंटेशन्स इंजेक्ट करू शकतील.

### ऑडिओ ब्रिज (`audioBridge.ts`) — मोडॅलिटी ब्रिज PR-3

ऑडिओ इनपुट स्वीकारत असल्याचे माहीत नसलेल्या टार्गेटपर्यंत पोहोचण्यापूर्वी ऑडिओ-युक्त चॅट विनंत्यांना इंटरसेप्ट करते. ते चॅट विनंती कधीही रीरूट करत नाही: ऑडिओ पार्ट्स विद्यमान OpenAI-कंपॅटिबल मल्टीपार्ट एंडपॉइंटमधून ट्रान्सक्राइब केले जातात आणि निवडलेले चॅट मॉडेल टेक्स्ट ट्रान्सक्रिप्ट्ससह पुढे चालू राहते.

फ्लो:

1. `getResolvedModelCapabilities()` द्वारे `supportsAudio` रिझॉल्व्ह करा. स्पष्ट
   प्रोव्हायडर-रजिस्ट्री मेटाडेटाला प्रथम प्राधान्य मिळते, नंतर स्टॅटिक मॉडेल
   मेटाडेटा, नंतर सिंक केलेले `modalities_input`. `audio` नसलेली घोषित इनपुट
   यादी `false` असते; क्षमतेचा कोणताही पुरावा नसल्यास `null` राहते. `false` आणि
   `null` दोन्ही कंझर्व्हेटिव्ह ब्रिज सक्रिय करतात, तर `true` ते बायपास करते.
2. `modalityBridgeAudio*` सेटिंग्ज रिझॉल्व्ह करा आणि शेअर्ड `detectMediaParts()`
   डिटेक्टरद्वारे प्रत्येक मेसेजमधून स्प्लाइस करता येणारे टॉप-लेव्हल ऑडिओ पार्ट्स
   काढा. समर्थित वायर आकार OpenAI `input_audio`, `audio_url` आणि
   `source.media_type: "audio/*"` आहेत. नेस्टेड ऑडिओ रूटिंगसाठी शोधले जाते पण
   स्प्लाइस पाथद्वारे काढले जात नाही. काम `modalityBridgeAudioMaxClips` द्वारे
   मर्यादित आहे; नंतरचे पार्ट्स अलगद राहतात.
3. कॉन्फिगर केलेले `provider/model` मान्य करा, किंवा `selectAudioBridgeModel()` ला
   `AUDIO_TRANSCRIPTION_PROVIDERS` मध्ये स्थिर कॅटलॉग क्रमाने फिरवून
   वापरण्यायोग्य सक्रिय प्रोव्हायडर क्रेडेन्शियल असलेले पहिले मॉडेल निवडू द्या.
4. `callAudioTranscription()` base64/data-URI ऑडिओचे multipart `file` मध्ये
   रूपांतर करते, किंवा DNS पिनिंगसह पब्लिक-ओन्ली आउटबाउंड गार्डद्वारे 25 MB
   मर्यादेने रिमोट `audio_url` डाउनलोड करते. नंतर ते
   `resolveSelfLoopBearer()` ने प्रमाणित केलेल्या लोकल
   `/v1/audio/transcriptions` सेल्फ-लूपवर फाइल आणि निवडलेले मॉडेल POST करते.
   विद्यमान ट्रान्सक्रिप्शन रूट सामान्य क्रेडेन्शियल लुकअप, कूलडाउन/रेट-लिमिट
   हाताळणी आणि प्रोव्हायडर डिस्पॅच करते.
5. यशस्वी कॉल त्यांचे पार्ट्स `[Audio N]: <transcript>` ने बदलतात. कॉल
   `Promise.allSettled` ने चालतात: वैयक्तिक अयशस्वीता तो मूळ ऑडिओ पार्ट जतन
   करते (#4012 कॉन्ट्रॅक्ट). प्रत्येक कॉल अयशस्वी झाला आणि टार्गेट
   `supportsAudio === false` असल्याचे सिद्ध झाल्यास, पार्ट्स
   `[Audio N]: (unavailable — no STT provider connected)` बनतात (#8430 कॉन्ट्रॅक्ट).
   अज्ञात टार्गेटसाठी (`null`), सर्व-अयशस्वी निकाल अलगद राहतो. वापरण्यायोग्य STT
   क्रेडेन्शियल नसलेले सिद्ध टेक्स्ट-ओन्ली टार्गेट नेटवर्क कॉल न करता तोच स्पष्ट
   स्टब मिळवते.

यशस्वी ट्रान्सक्रिप्ट्स प्रोसेस-व्यापी मोडॅलिटी ब्रिज LRU/TTL कॅशे वापरतात. की
ही ऑडिओ संदर्भ, स्थिर `audio-transcription` ऑपरेशन लेबल आणि निवडलेले STT मॉडेल
एकत्र करते; अयशस्वीता कधीही कॅशे केली जात नाही. ऑडिओ प्रयत्न शेअर्ड `bridged`,
`cacheHits`, `failures` आणि `lastUsedAt` काउंटर अपडेट करतात. रूपांतरित
रिस्पॉन्सेस
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` घेऊन जातात;
अलगद रिक्वेस्ट्सना ऑडिओ ब्रिज सेगमेंट मिळत नाही.

रनटाइम सेटिंग्ज DB-बॅक्ड आणि Zod-व्हॅलिडेटेड आहेत:

| ----------------------------- | ------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                |
| `modalityBridgeAudioModel`    | `""`    | ऑटो किंवा STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10             |

शेअर्ड कॅशे `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` आणि
`modalityBridgeCacheMaxEntries` द्वारे नियंत्रित राहते.

### व्हिडिओ ब्रिज (`videoBridge.ts`, `videoBridgePipeline.ts`)

चॅट पूर्णता `messages` मधील उच्च-स्तरीय व्हिडिओ भागांना इंटरसेप्ट करते आणि ज्ञात नेटिव्ह व्हिडिओ समर्थनाशिवाय लक्ष्यापूर्वी API `input` प्रतिसाद देते. समर्थित आकार `input_video`, `video_url`, `video_source`, HTTPS URLs, आणि `data:video/*;base64,...` डेटा URIs आहेत. मजकूरातील साध्या फाइलनावांना व्हिडिओ म्हणून हाताळले जात नाही.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) कडे विनंती ट्रॅव्हर्सल, capability/policy चेक, प्रति-विनंती एकत्रीकरण आणि प्रतिसाद पेलोड आहे. प्रति-व्हिडिओ कार्य — संपादन, संपूर्ण-परिणाम कॅशे, फ्रेम क्रमाचे वर्णन करणारा (जे कोणत्याही कॉलर-घोषित ऑडिओ ट्रान्सक्रिप्टला फ्यूज करते), आणि प्रति-प्रयत्न metrics/abort/cleanup — हे `videoBridgePipeline.ts` मध्ये `processVideoPart` मागे लपलेले असते, `preCall` च्या लूपमध्ये प्रति व्हिडिओ भाग एकदा म्हणतात. ते मॉड्यूल स्पष्ट पोर्ट सीमा `VideoMediaBrokerPort` (बाइट मिळवणे आणि नमुना फ्रेम्स काढणे), `VideoAudioTranscriptionPort` (नमुनादार मथळ्यांसह कॉलर-घोषित ऑडिओ ट्रान्सक्रिप्ट फ्यूज करणे), आणि `VideoDrilldownPort` (लेगेसी रॉ-स्टोअर आकार) देखील परिभाषित करते. उत्पादन STT आणि फ्रेम धारणा `createVideoSttAdapter` आणि `createVideoDrilldownAdapter` द्वारे वर्णन करणाऱ्या पोर्टभोवती बनलेले आहे; नंतरचे सामायिक अपारदर्शक-हँडल लाइफसायकल वापरते.

सार्वजनिक `/v1` विनंती मार्ग कधीही उपप्रक्रिया आयात करत नाही किंवा आमंत्रित करत नाही. रिमोट व्हिडिओ 50 MiB बाउंड अंतर्गत डाउनलोड केले जातात; इनलाइन बेस64 व्हिडिओंमध्ये पुराणमतवादी 36 MiB डीकोड केलेले प्रति-व्हिडिओ कॅप आहे त्यामुळे model/messages/framing लिफाफा 50 MiB च्या सार्वजनिक JSON विनंती प्रवेश मर्यादेच्या आत राहू शकतो. वाटप करण्यापूर्वी इनलाइन लांबी आणि डीकोड-आकार अंदाज तपासले जातात. DNS पिनिंगसह विद्यमान सार्वजनिक-फक्त आउटबाउंड गार्ड वापरून, प्रारंभिक रिमोट URL आणि प्रत्येक पुनर्निर्देशनावर HTTPS आवश्यक आहे. बाइट्स नंतर अचूक अंतर्गत `POST /api/modality-bridge/video/extract` ब्रोकर सीमा ओलांडतात. तो मार्ग `LOCAL_ONLY` आणि `SPAWN_CAPABLE` दोन्ही आहे, केवळ प्रति-प्रक्रिया प्रमाणीकृत, विश्वासार्ह-लूपबॅक विनंती स्वीकारतो आणि URL, फाइल सिस्टम पथ, एक्झिक्युटेबल किंवा वितर्क सूची कधीही स्वीकारत नाही. API बॉडी-साइज पाइपलाइन आणि हँडलरचे वाढीव बॉडी रीडर स्वतंत्रपणे 50 MiB ब्रोकर इनपुट कॅप लागू करतात. त्याची बाउंडेड रांग एका वेळी एक एक्सट्रॅक्शन चालवते, चार प्रलंबित नोकऱ्यांना परवानगी देते आणि 100 MiB वर प्रलंबित इनपुट कॅप्स करते.

ब्रोकरच्या आत, `ffprobe` खाजगी स्थानिक फाइल वाचते; फिक्स्ड फॉरमॅट अनुमत यादीमध्ये प्लेलिस्ट आणि मॅनिफेस्ट फॉरमॅट्स वगळले जातात. अनुमत MOV-फॅमिली कंटेनरसाठी, बाह्य MOV डेटा संदर्भ डीफॉल्टनुसार अक्षम राहतात आणि निश्चित कमांड त्यांना निवडत नाही. `ffprobe` आणि `ffmpeg` दोन्ही `file` -only प्रोटोकॉल श्वेतसूची, एक थ्रेड, फिक्स्ड आर्ग्युमेंट ॲरे, कोणतेही शेल आणि `PATH` वरून सोडवलेले एक्झिक्यूटेबल्स वापरतात. संलग्न-चित्र कव्हर प्रवाह प्ले करण्यायोग्य उमेदवार नाहीत. सर्व प्ले करण्यायोग्य प्रवाहांनी मर्यादा पूर्ण केल्या पाहिजेत आणि सर्वात कमी-इंडेक्स फॉलबॅकच्या निर्धारकाच्या आधी स्पष्ट डीफॉल्ट प्रवाहाला प्राधान्य दिले जाते. व्हिडिओ 600 सेकंद, 8,192 पिक्सेल प्रति आयाम आणि 33,554,432 स्त्रोत पिक्सेल इतके मर्यादित आहेत. FFmpeg नमुने 1-16 मिडपॉइंट JPEG फ्रेम्स, लहान इनपुट अपस्केल न करता लांब किनार्याला जास्तीत जास्त 1,024 पिक्सेल पर्यंत स्केल करते आणि कधीही URL प्राप्त करत नाही. सॅम्पलिंग डीफॉल्टनुसार `uniform` आहे. पर्यायी `scene_aware` आणि प्रायोगिक `segment_aware` धोरणे आधीच प्रमाणित केलेल्या स्थानिक प्रवाहावर एक अतिरिक्त निश्चित FFmpeg पास करतात, बाउंडेड `showinfo` सीन टाइमस्टॅम्प निवडतात आणि डिटेक्टर अयशस्वी, कालबाह्य, विकृत आउटपुट किंवा रिक्त उमेदवार सेटवर समान समान मध्यबिंदूंवर निश्चितपणे परत येतात. सेगमेंट-अवेअर मोड प्रमाणित दृश्य अंतरालच्या प्रमाणात मध्यबिंदू नमुने वाटप करतो; विभाग-जागरूक पुरावे आणि फॉलबॅक वर्तन खाली तपशीलवार आहेत. प्रत्येक पॉलिसीमध्ये निवड केल्यानंतर हार्ड 16-फ्रेम कॅप लागू केली जाते. जेव्हा दृश्य-जागरूक विनंतीचे फक्त एक-फ्रेम बजेट असते, तेव्हा ते सक्रिय पूर्ण-व्हिडिओ किंवा फोकस विंडोचा एकसमान मध्यबिंदू वापरते आणि `policyEffective: uniform` अहवाल देते: एकच निवडलेली दृश्य फ्रेम दोन्ही टेम्पोरल टोके जतन करू शकत नाही. कॉलर वैकल्पिकरित्या मर्यादित फोकस विंडो प्रदान करू शकतो (`start`/`end` सेकंद); बाउंड्स मीडिया कालावधीसाठी क्लॅम्प केले जातात, उलट किंवा मर्यादित नसलेल्या विंडो नाकारल्या जातात आणि सर्व सॅम्पलिंग पॉलिसी फक्त सामान्यीकृत अंतरालमध्येच केल्या जातात. परिणामी विंडो सॅम्पलिंग मेटाडेटा आणि अविश्वासू वर्णन उपसर्गामध्ये समाविष्ट केली आहे जेणेकरून डाउनस्ट्रीम मॉडेल पूर्ण टाइमलाइनमधून फोकस केलेला उतारा वेगळे करू शकतात.

सिमेंटिक कॅप्शन फोकस ही एक वेगळी, स्पष्ट सेटिंग आहे. डीफॉल्ट `full` विश्लेषण मोड विद्यमान फ्रेम प्रॉम्प्ट जतन करतो आणि मथळा मॉडेलवर विनंती मजकूर कधीही फॉरवर्ड करत नाही. `focused` मोडमध्ये, ब्रिज त्याच चॅट किंवा रिस्पॉन्स कंटेनरमधून फक्त नवीनतम नॉन-रिक्त वापरकर्ता-लेखक `text`/`input_text` वाचतो, ते NFC वर सामान्य करतो, नियंत्रण वर्ण आणि व्हाइटस्पेस कोलॅप्स करतो आणि 500 युनिकोड कोड पॉइंट्सपर्यंत मर्यादित करतो. रिक्त परिणाम अचूक `full` प्रॉम्प्टवर परत येतो. वापरण्यायोग्य इशारा समर्पित अविश्वासू-वापरकर्ता-संदर्भ ब्लॉकमध्ये JSON म्हणून अनुक्रमित केला जातो आणि केवळ निरीक्षण करण्यायोग्य तपशीलांना प्राधान्य देऊ शकतो; ते मीडियामध्ये दृश्यमान किंवा ऐकू येण्याजोग्या खालील सूचनांविरूद्ध स्वतंत्र चेतावणी ओव्हरराइड करू शकत नाही. मजकूर फोकस कधीही `start`/`end` अनुमानित करत नाही किंवा टेम्पोरल सॅम्पलर बदलत नाही.

#### FU-07 स्ट्रक्चरल सेगमेंट पुरावा

`segment_aware` आधीच प्रमाणित केलेल्या स्थानिक व्हिडिओ प्रवाहावर एक बाउंडेड प्री-विश्लेषण पास वापरते. फिक्स्ड फिल्टर चेन प्रथम जास्तीत जास्त 320 पिक्सेल रुंदीपर्यंत स्केल करते, दृश्य बदल आणि गोठवलेले अंतर शोधते, नंतर ब्लर, सरासरी लुमा आणि spatial/temporal माहितीसाठी प्रति सेकंद 1 फ्रेम दराने नमुने. पास 600 स्ट्रक्चरल नमुने, एक FFmpeg/filter थ्रेड, समान `file` -only प्रोटोकॉल आणि कंटेनर अनुमत सूची, 1 MiB प्रक्रिया-आउटपुट बाउंड, आणि ब्रोकरच्या सामायिक केलेल्या abort/deadline. मध्ये जास्तीत जास्त 30 सेकंदांपर्यंत मर्यादित आहे तो कधीही आदेश, फिल्टर, मार्ग किंवा URL कडील विनंती स्वीकारत नाही.

स्ट्रक्चरल व्हॅल्यू हे निर्धारवादी नमुन्याचे पुरावे आहेत, सिमेंटिक व्हिडिओ समज नाही. ते विषय, क्रिया, मथळे, भाषण किंवा वापरकर्त्याच्या हेतूचा अंदाज लावत नाहीत. देखावा आणि फ्रीझ सीमा विभाग तयार करतात; फ्रीझ कव्हरेज, ब्लर, एक्सपोजर, स्थानिक तपशील आणि तात्पुरते बदल केवळ विद्यमान 1-16 फ्रेम बजेटचे वाटप कसे केले जाते यावर प्रभाव पाडतात. पूर्णपणे गोठवलेला विभाग एका फ्रेममध्ये बंद केला जातो, तर नॉन-फ्रोझन सेगमेंट उर्वरित बजेटसाठी स्पर्धा करतात. जेव्हा सीमा फ्रेम्सपेक्षा जास्त असतात, तेव्हा एकसमान टाइमलाइन कव्हरेज राखले जाते त्यामुळे जलद सुरुवातीचे कट दीर्घ अनुगामी भाग लपवू शकत नाहीत. फ्रीझ सीमेच्या 1-सेकंद विश्लेषण रिझोल्यूशनमधील दृश्य सीमा एकत्र केल्या जातात.

गहाळ फिल्टर, malformed/empty पुरावा, डिटेक्टर त्रुटी, किंवा बाउंडेड पूर्व-विश्लेषण कालबाह्य अचूक एकसमान मध्यबिंदू धोरणासाठी अयशस्वी. कॉलर ॲबॉर्ट किंवा ब्रोकर डेडलाइन ओपन अयशस्वी होत नाही: ते इन-फ्लाइट सबप्रोसेस संपुष्टात आणते, नंतर फ्रेम एक्सट्रॅक्शन प्रतिबंधित करते आणि `finally` मध्ये खाजगी तात्पुरते झाड काढले जाते.

`scripts/perf/video-bridge-fu07-eval.ts` पोस्ट-डेडअप कॅप्शन-कॉल बचत, दाट-मोशन बजेट वाटप, blur/exposure/SI-TI पुरावे, लांब शेपटासह जलद कट आणि हळूहळू-फिकट खोट्या सकारात्मकतेसाठी निर्धारवादी वास्तविक FFmpeg फिक्स्चर व्युत्पन्न करते. हे पूर्व-विश्लेषण भिंत वेळ आणि, जेथे `/usr/bin/time` उपलब्ध आहे, चाइल्ड CPU आणि पीक RSS रेकॉर्ड करते. त्याची गुणवत्ता तपासणी केवळ स्ट्रक्चरल ऑरॅकल्स आहेत. वास्तविक मथळा-मॉडेल गुणवत्ता `HOLD` राहते कारण या हार्नेसला कोणतेही अधिकृत एंडपॉइंट किंवा गोठलेले न्यायाधीश नाहीत. जोपर्यंत `--caption-cost-per-call-usd` स्पष्ट सकारात्मक प्रति-कॉल अंदाज पुरवत नाही तोपर्यंत आर्थिक बचत देखील `HOLD` राहते; स्क्रिप्ट कधीही एकतर परिणाम तयार करत नाही.

प्रत्येक फ्रेम 4 MiB पर्यंत मर्यादित आहे, सर्व कच्च्या फ्रेम्स एकत्रितपणे 23 MiB पर्यंत आणि अनुक्रमित ब्रोकर प्रतिसाद 32 MiB पर्यंत मर्यादित आहे. एक खाजगी तात्पुरती निर्देशिका `finally` मध्ये काढली जाते. OmniRoute FFmpeg बंडल करत नाही आणि सानुकूल एक्झिक्युटेबल पथ स्वीकारत नाही. कॅप्शन देण्यापूर्वी, ब्रिज एक पुराणमतवादी व्हिज्युअल डिडुप्लिकेशन पास लागू करतो: प्रत्येक JPEG 16 × 16 ग्रेस्केल बफरवर कमी केला जातो आणि फक्त शेवटच्या फ्रेमशी तुलना केली जाते. एका फ्रेमच्या वर विनंती केलेल्या कॅप्शन बजेटसाठी, एक्सट्रॅक्शन त्या बजेटच्या दुप्पट आणि कधीही 16 फ्रेम्सपेक्षा जास्त नसलेला एक बाउंडेड उमेदवार पूल पुरवतो. विनंती केलेली कॅप केवळ डुप्लिकेशननंतर लागू केली जाते, पहिल्या आणि अंतिम निवडलेल्या उमेदवारांना अंतिम पातळ करताना जतन केले जाते जेव्हा बजेट किमान दोन असते. व्हर्जन केलेले `grayscale-16x16-mean-cells-v2` पॉलिसी मध्यम लुमा डेल्टा आणि थंबनेल सेलचे प्रमाण वापरते ज्यांचे सामान्यीकृत डेल्टा किमान 0.05 आहे. डुप्लिकेट थ्रेशोल्ड हा स्थिर 0.04 आहे, जो रनटाइम सेटिंग म्हणून उघड करण्याऐवजी अंदाजानुसार निवडला जातो. हा दुय्यम उच्च-कॉन्ट्रास्ट सिग्नल लहान हालचाल आणि दृश्यमान-मजकूर बदल जतन करतो जे केवळ सरासरी तुलना लपवू शकते. कम्पॅरेटर किंवा डीकोडर एरर अयशस्वी होतात आणि कव्हरेज ठेवतात. आउटपुट मेटाडेटा काढलेल्या उमेदवारांना, यशस्वीरित्या वापरलेल्या फ्रेम्स आणि व्हिज्युअल डुप्लिकेट्स सोडले जातात.

स्पष्टपणे चिन्हांकित केलेला व्हिडिओ भाग टाइमस्टॅम्प केलेल्या संपर्क पत्रकाची विनंती करू शकतो. पूल जास्तीत जास्त 4-स्तंभ, 16-फ्रेम JPEG ग्रिड तयार करतो. प्रत्येक 512-पिक्सेल सेल त्याच्या स्त्रोत टाइमस्टॅम्पला उच्च-कॉन्ट्रास्ट तळाच्या बँडमध्ये बर्न करतो, तर तेच टाइमस्टॅम्प डाउनस्ट्रीम असोसिएशन आणि ऑडिटसाठी मजकूर मेटाडेटामध्ये राहतात. पूर्ण JPEG 32 MiB वर मर्यादित राहते. जर `sharp` ग्रिड डीकोड करू शकत नाही किंवा तयार करू शकत नाही, तर पूल वैयक्तिक JPEG फ्रेमवर परत येतो; क्लायंट अबॉर्ट अजूनही शीट ऑपरेशनद्वारे प्रसारित होतो.

प्रोमोशनचा पुरावा कृत्रिम रचना मायक्रोबेंचमार्कपासून मुद्दाम वेगळा आहे. `scripts/perf/video-bridge-contact-sheet-eval.ts` वास्तविक OpenAI-सुसंगत व्हिजन मॉडेल्ससाठी स्कीमा-आवृत्ती असलेले A/B हार्नेस परिभाषित करते. हे प्रदाता-रिपोर्ट केलेले टोकन, एंड-टू-एंड वॉल लेटन्सी (शीट कंपोझिशनसह), मॉडेल-कॉल संख्या आणि मॅनिफेस्ट-परिभाषित तथ्य धारणा मोजते. रॉ मॉडेल प्रतिसाद अहवालावर लिहिलेले नाहीत; फक्त SHA-256 पचते आणि जुळलेली वस्तुस्थिती IDs ठेवली जाते. `--execute-real` पास केल्याशिवाय आणि `--model`, `OMNIROUTE_BASE_URL` आणि `OMNIROUTE_API_KEY` कॉन्फिगर केल्याशिवाय हार्नेस नेटवर्क किंवा सशुल्क मॉडेल कॉल करत नाही. त्या स्पष्ट वास्तविक धावाशिवाय, त्याचा मशीन-वाचनीय निर्णय `HOLD` राहतो; सिंथेटिक payload/call-count मोजमाप केवळ जाहिरात पुरावा नाहीत.

कॉलर त्यांच्याकडे आधीपासूनच संरेखित मजकूर असल्यास समर्थित व्हिडिओ भागामध्ये पर्यायी `transcript.cues` ॲरे संलग्न करू शकतात. प्रत्येक क्यूमध्ये `text`, एक मर्यादित `start`/`end` अंतराल तपासलेल्या कालावधीमध्ये आणि श्वेतसूचीबद्ध `source` (`client`, `embedded`, किंवा `audio-bridge`); `confidence` `1` वर डीफॉल्ट आहे आणि `0` आणि `1` मध्ये राहणे आवश्यक आहे. अचूक डुप्लिकेट संकेत कोलमडले आहेत. OmniRoute कधीही या मेटाडेटामधून लिप्यंतरण सुरू करत नाही: प्रमाणित संकेत वर्णित परिणामामध्ये स्त्रोत, आत्मविश्वास आणि मध्यांतरासह कॉपी केले जातात आणि फ्रेम मथळ्यांच्या बाजूने अविश्वासू निरीक्षणे म्हणून प्रस्तुत केले जातात. कॅप्शन प्रवाहात मिसळण्याऐवजी अवैध, श्रेणीबाहेरील किंवा मूळ-मुक्त मजकूर नाकारला जातो. दोन्ही रिक्वेस्ट-बॉडी ट्रान्स्क्रिप्ट चॅनेल `client` ला पुरवठा केलेल्या मूळतेला सामान्य करतात, ज्यात स्व-ॲस्र्टेड `embedded` किंवा `audio-bridge` लेबल्स समाविष्ट आहेत. केवळ सर्व्हर-मालकीचे अडॅप्टर कोड-केवळ `trustedSource` युक्तिवादाद्वारे ती विश्वसनीय लेबले नियुक्त करू शकतात; विनंती JSON फील्ड त्या युक्तिवादापर्यंत पोहोचू शकत नाही. ट्रान्सक्रिप्ट मजकूर अविश्वासू मीडिया-व्युत्पन्न सामग्री राहते, त्याच्या मूळ गोष्टीकडे दुर्लक्ष करून, आणि अधिकृतता कधीही निर्धारित करू नये.

प्रगत कॉलर त्याच व्हिडिओसाठी `audioTranscript` ट्रॅक देऊ शकतो; तो क्लायंट-प्रदान केलेला मजकूर मानला जातो, सर्व्हर ट्रान्सक्रिप्शनचा पुरावा नाही. फ्यूजन सीम व्हिज्युअल आणि ऑडिओ निरीक्षणे एका अंतिम मुदत आणि निरस्त सिग्नल अंतर्गत चालवते, त्यांना सामान्य टाइमलाइनवर ऑर्डर करते, अचूक डुप्लिकेट कोलॅप्स करते आणि जेव्हा फक्त एक बाजू यशस्वी होते तेव्हा आंशिक परिणाम नोंदवते. एक अवैध `audioTranscript` त्या आंशिक परिणामास कमी करते — व्हिज्युअल वर्णन ठेवले जाते आणि ऑडिओ शाखा संपूर्ण व्हिडिओ अयशस्वी होण्याऐवजी सॅनिटाइज्ड अपयश कोड — रेकॉर्ड करते. प्रति-शाखा उपलब्धता, आंशिक ध्वज आणि सॅनिटाइज्ड अपयश कोड वर्णन केलेल्या परिणामामध्ये, रेलिंग मेटाडेटा (`audioFusionRuns`/`audioFusionPartials`/ `audioFusionFailureCodes`), परिणाम-कॅशे मेटाडेटामध्ये आणि ब्रिज फ्यूजन काउंटरमध्ये जतन केले जातात. डीफॉल्ट व्हिडिओ ब्रिज पथ स्पीच-टू-टेक्स्ट किंवा दुसरी मीडिया कॉपी डाउनलोड करत नाही; त्या सुस्पष्ट ट्रॅकशिवाय, ते केवळ व्हिडिओसाठीच राहते.

**प्रतिलिपी धारणा (#12150 P1).** जेव्हा जेव्हा व्हिडिओ ब्रिज (स्वतःच ऑप्ट-इन) ट्रान्सक्रिप्ट क्यू — रेंडर करते तेव्हा कोणताही वेगळा धारण ध्वज नसतो तेव्हा हे आपोआप लागू होते. जेव्हा एखादी विनंती कोणताही ट्रान्स्क्रिप्ट क्यू (कॉलर-घोषित `transcript` किंवा फ्यूज्ड `audioTranscript`) रेंडर करते, तेव्हा रेलिंग त्यावर `videoBridgeObserved` चिन्हांकित करते आणि व्हिडिओ वर्णन — ची एक समान रेंडरिंग तयार करते ज्यामध्ये प्रत्येक क्यूचा फ्री-टेक्स्ट बॉडी `[redacted-video-transcript]` द्वारे बदलला जातो, stubdse फील्डच्या आधी strings म्हणून तयार केला जातो. (सपाट केलेला मजकूर पार्स करून कधीही करू नका, त्यामुळे `[inaudible]`/`[music]` — सारख्या `]` असलेल्या बॉडीसह कोणतीही क्यू सामग्री — विरोधी किंवा सामान्य नाही). पर्सिस्टेड कॉल-लॉग रिक्वेस्ट बॉडी प्रत्येक व्हिडिओ-व्युत्पन्न मजकूर भाग बदलून त्या दुरुस्त केलेल्या सावलीसाठी, सामग्री समानतेने जुळते; `fullText` अँकर पूर्ण झालेल्या प्री-कॉल रेलिंग पेलोडमधून पुन्हा वाचले जाते, त्यामुळे नंतरच्या चेन रेलिंगने ( PII आणि क्रेडेन्शियल मास्कर्स, प्राधान्यक्रम 10/95) वर्णन मजकूर जागेवर पुन्हा लिहिल्यानंतर आणि system-prompt/handoff/memory इंजेक्शनने संदेश ॲरेचा आकार बदलल्यानंतरही सामना यशस्वी होतो. मॉडेलला अपस्ट्रीम पाठविलेले शरीर अपरिवर्तित आहे. निरीक्षण केलेल्या विनंतीमध्ये कोणतीही टिकाऊ मेमरी नसते (दोन्ही विनंती- आणि प्रतिसाद-व्युत्पन्न एक्स्ट्रॅक्शन वगळले जातात), त्यामुळे मॉडेलचे स्वतःचे उत्तर मेमरीमध्ये ट्रान्सक्रिप्ट मजकूर प्रतिध्वनी करू शकत नाही.

**रॉ व्हिडिओ फील्ड (#12430).** जेव्हा ब्रिज सक्षम केला जातो आणि मूळ व्हिडिओ समर्थन अज्ञात किंवा अनुपस्थित असतो, परिभाषित `transcript`/`audioTranscript` फील्ड देखील `videoBridgeObserved` सक्रिय करतात, अगदी वर्णन अयशस्वी किंवा `maxVideos` मर्यादेनंतरही. `null` आणि रिक्त तारांची संख्या; अनुपस्थित फील्ड आणि नॉन-व्हिडिओ मेटाडेटा नाही. राखून ठेवलेल्या प्रती या फील्ड रिडॅक्ट करतात किंवा विनंती वगळतात आणि caches/Memory बायपास केले जाते.

त्या फॉलबॅक मार्गांवर, वैध कॉलर संकेत नॉनस्टँडर्ड प्रदाता फील्डऐवजी समर्थित `text`/`input_text` भाग बनतात. व्हिडिओचे वर्णन केलेले नाही आणि टाइमस्टॅम्प मीडियाच्या विरोधात सत्यापित केलेले नाहीत अशा स्पष्ट चेतावणीसह विनंती-पुरवलेल्या दोन्ही ट्रॅकवर अविश्वासू `client` निरीक्षणे आहेत. विद्यमान 256-cue/64-KiB एकूण आणि प्रति-क्यू बजेट दोन्ही ट्रॅकवर एकत्रितपणे लागू होतात; टाइमस्टॅम्प ब्रोकरच्या 600-सेकंद कमाल मर्यादा आणि पुरवलेल्या फोकस विंडोमध्ये बसणे आवश्यक आहे. अवैध ट्रॅक टाकून दिले आहेत, अनियंत्रित मजकूर म्हणून फॉरवर्ड केले जात नाहीत; वैध भावंडाचा एकत्रित अर्थसंकल्प ओलांडल्याशिवाय वापरला जाऊ शकतो. Null/empty फील्ड मजकूर जोडत नाहीत. या फॉलबॅकद्वारे कोणतेही मीडिया फेच किंवा ट्रान्सक्रिप्शन जोडलेले नाही. फॉलबॅक व्हिडिओ वाहक आणि त्याच्या `video_url`/`source` ऑब्जेक्ट्समधून ट्रान्सक्रिप्ट विस्तार फील्ड काढले जातात. OpenAI वायर अनुमत सूची कठोर राहते; अज्ञात-नेटिव्ह व्हिडिओ वाहक उपलब्ध राहतात आणि ज्ञात मजकूर-केवळ लक्ष्य सुरक्षित मार्कर ठेवतात. स्ट्रक्चर्ड रिडॅक्शन शॅडोज जोडलेल्या ट्रान्सक्रिप्ट मजकूराचे संरक्षण करतात, तर मूळ कॉलरच्या मालकीची विनंती अपरिवर्तित राहते. नेटिव्ह-समर्थित लक्ष्य आणि अक्षम पूल त्यांचे विद्यमान बायपास वर्तन राखून ठेवतात.

अतिरिक्त राखून ठेवलेल्या प्रती समान निरीक्षण-विनंती सिग्नल वापरतात. कच्चा पूर्व रेलिंग क्लायंट-विनंती स्नॅपशॉट, इन-मेमरी प्रलंबित विनंती, आणि लवकर नाकारलेले-विनंती लॉग व्हिडिओ भागांमध्ये ट्रान्सक्रिप्ट फील्ड संरचनात्मकपणे पुनर्स्थित करतात; पाइपलाइन स्टेज आणि कॉन्टेक्स्ट हँडऑफद्वारे संश्लेषित स्ट्रिंग प्रॉम्प्ट पर्सिस्टेड-रिक्वेस्ट-बॉडी सिंकवर रिडॅक्ट केले जातात. सतत `video_content_removed` मार्कर हेतुपुरस्सर टाकून दिलेला मजकूर पुनर्रचना करण्याऐवजी `previous_response_id` सातत्य अयशस्वी करते. जर निरीक्षण केलेल्या विनंतीने लॉग इन करण्यापूर्वी तिची प्रति-भाग पुनर्रचना सावली गमावली किंवा नंतरच्या विनंती उत्परिवर्तनानंतर अनेक व्हिडिओ सावल्यांपैकी एकही जुळत नसेल, तर राखून ठेवलेली विनंती मुख्य भाग अंशतः सुधारित प्रतिलेख ठेवण्याऐवजी पूर्णपणे वगळण्यात येईल.

निरीक्षण केलेल्या विनंतीसाठी, मॉडेल प्रतिसाद संरचित क्यू सीमाविना उताऱ्याचा कोणताही भाग उद्धृत करू शकतो. त्यामुळे त्याचा कायम असलेला कॉल-लॉग `responseBody` वगळलेल्या मार्करने बदलले आहे; तपशीलवार पाइपलाइन आर्टिफॅक्ट (ज्यामध्ये upstream/client बॉडी आणि स्ट्रीम भाग समाविष्ट असू शकतात) राखून ठेवलेले नाहीत. त्या विनंतीसाठी सिमेंटिक, idempotency, आणि तर्क-रिप्ले कॅशे बायपास वाचतो आणि लिहितो. प्रदाता विनंती आणि क्लायंट-दृश्यमान प्रतिसाद अपरिवर्तित राहतात. जेव्हा तपशीलवार आर्टिफॅक्ट वगळले जाते तेव्हा प्रारंभिक Keepalive बाइट्स तात्पुरत्या बफरमधून काढून टाकले जातात. Kiro ची विकृत EventStream चेतावणी केवळ पेलोड बाइट संख्या दर्शवते, कधीही त्यातील सामग्री किंवा JSON पार्सरची रॉ एरर नाही. हे असा दावा करत नाही की प्रत्येक असंबंधित provider/plugin निदानाचे ऑडिट केले गेले आहे; रुंद राखून ठेवलेले-सिंक स्वीप #11658 मध्ये ट्रॅक केले जाते.

अंतर्गत `/api/modality-bridge/video/drilldown` जीवनचक्र एक स्वतंत्र, loopback/token-authenticated कॅशे सब्सट्रेट आहे. प्रत्येक ऑपरेशनसाठी कॅनोनिकल अपारदर्शक प्रिन्सिपल ID देखील आवश्यक आहे. प्रॉडक्शन कॉलर सक्षम करण्यापूर्वी, ते प्रमाणीकृत भाडेकरूकडून ID प्राप्त करणे आवश्यक आहे आणि क्लायंट-निवडलेले मूल्य कधीही फॉरवर्ड करू नये. कॅशे की त्या प्रिन्सिपलला कॅनॉनिकल सेशन आणि व्हिडिओ-रेफरन्स IDs ला बांधतात, फक्त त्यांच्या SHA-256-derived की स्टोअर करतात आणि त्याच प्रिन्सिपलला वाचणे आणि हटवणे या दोन्ही गोष्टींचा व्याप्ती असतो. कॅशे जास्तीत जास्त 16 व्युत्पन्न JPEG फ्रेम्स प्रति एंट्री संग्रहित करते, दहा मिनिटांनंतर ते कालबाह्य होते आणि बाउंडेड `start`/`end` वाचन किंवा स्पष्ट सत्र हटविण्यास समर्थन देते.

प्रत्येक प्रिन्सिपल 16 नोंदी आणि कॅनॉनिकल JPEG डेटाच्या 64 MiB पर्यंत मर्यादित आहे. त्या मर्यादा जागतिक 64-entry/256 MiB कमाल मर्यादेपासून स्वतंत्र आहेत: प्रिन्सिपल कोटा प्रेशर केवळ त्या प्रिन्सिपलच्या कमीत कमी-अलीकडे-वापरलेल्या नोंदी जागतिक LRU बेदखल करण्याआधी बेदखल करतो. कालबाह्य झालेल्या नोंदी कॅशे ॲक्टिव्हिटीवरील प्रिन्सिपल आणि ग्लोबल अकाउंटिंग या दोन्हींमधून स्वीप केल्या जातात, तर रद्दीकरण आणि प्रमाणीकरण अयशस्वी झाल्यामुळे आंशिक बदली होत नाही.

कॅशे नॉन-कॅनॉनिकल बेस64, अतिरिक्त पॅडिंग, नॉन-जेपीईजी मीडिया, विकृत किंवा कापलेले JPEGs, आणि JPEGs नाकारते जे पूर्ण-प्रतिमा `sharp` डीकोड दरम्यान चेतावणी देते. ते प्रत्येक स्वीकृत प्रतिमेला कॅनोनिकल JPEG म्हणून पुन्हा एन्कोड करते, कॉलर फील्डवर विश्वास ठेवण्याऐवजी डीकोड केलेल्या बाइट्समधून रुंदी आणि उंची मिळवते आणि कोणत्याही ट्रेलिंग पॉलीग्लॉट बाइट्स ठेवण्याऐवजी टाकून देते. दोन्ही कोट्यांसाठी फक्त बाउंडेड कॅनॉनिकल कॉम्प्रेस्ड बफर चार्ज केला जातो. JSON वायर मर्यादेमध्ये 32 MiB डीकोड-इनपुट कमाल मर्यादेसाठी बेस64 ओव्हरहेड समाविष्ट आहे. प्रत्येक संचयित व्युत्पन्न त्याचे प्रमाणित JPEG format/resolution, नमुना धोरण, व्युत्पन्न आवृत्ती, निर्मिती वेळ, सर्व्हर-संगणित सामग्री हॅश आणि हॅश केलेले पालक संदर्भ तसेच विश्वसनीय कॉलरचे पालक-सामग्री हॅश रेकॉर्ड करते. ॲटोमिक कॅशे कमिट करण्यापूर्वी ॲसिंक्रोनस decode/hash टप्प्यांमध्ये रद्दीकरण तपासले जाते.

उत्पादन निर्माते यशस्वी व्हिज्युअल विश्लेषणानंतरच आधीपासून मिळवलेल्या ब्रोकर फ्रेम्सचा पुनर्वापर करतात, दुसरा व्हिडिओ download/extraction. शिवाय यासाठी ऑपरेटर `modalityBridgeVideoDrilldownEnabled=true`, कठोर प्रति-भाग `drilldown: true` आणि प्रमाणीकृत API-की रेकॉर्ड ID आवश्यक आहे. क्लायंट-घोषित principal/session मूल्ये कधीही मालकी स्थापित करत नाहीत. तिन्ही अटींशिवाय ते हॅश करत नाही, आकार बदलत नाही किंवा अतिरिक्त फ्रेम ठेवत नाही. धारणा अयशस्वी वापरण्यायोग्य व्हिज्युअल प्रतिसाद संरक्षित करते. संमती दिलेल्या विनंत्या संपूर्ण-व्हिडिओ निकाल कॅशेला बायपास करतात म्हणून कॅशे केलेले परिणाम कधीही हँडल रिप्ले करत नाहीत.

यशस्वी JSON आणि SSE प्रतिसाद बाउंडेड `x-omniroute-video-drilldown` हेडरमध्ये जास्तीत जास्त चार अपारदर्शक हँडल उघड करतात. अधिकृत ब्राउझर मूळ हेडर CORS मूळ धोरण विस्तृत न करता वाचू शकतात. नवीन हँडल `v1.<32-byte random base64url token>` वापरतात, आणि रेजिस्ट्री फक्त त्यांचे SHA-256 हॅश राखून ठेवते. reader/header पार्सर लेगेसी 64-हेक्स टोकन देखील स्वीकारतो. प्रमाणीकृत सार्वजनिक ग्राहक `GET /api/v1/video-bridge/drilldown?handle=...` आहे, स्वतंत्रपणे `modalityBridgeVideoDrilldownRemoteEnabled=true` द्वारे गेट केलेले आहे. लीगेसी `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env फॉलबॅक सक्षम असताना देखील स्पष्टपणे कायम खोटे प्रवेश रद्द करते. उत्पादन धारणामध्ये समान वारसा `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` फॉलबॅक आहे. दोन्ही फॉलबॅक डीफॉल्ट बंद.

ग्राहक ऑथेंटिकेटेड की वरून मालकी मिळवतो आणि की पॉलिसी लागू करतो: GET आणि DELETE दोन्ही `/v1` आणि `/api/v1` उपनामांसह `video` एंडपॉइंट श्रेणीशी संबंधित आहेत. नॉन-रिक्त एंडपॉइंट अनुमत सूची असलेल्या की मध्ये `video` समाविष्ट करणे आवश्यक आहे; अप्रतिबंधित की सुसंगत राहतील. अज्ञात, कालबाह्य झालेल्या आणि दुसऱ्या कीच्या हँडलसाठी ग्राहक तेच 404 परत करतो. हे `variant=preview|standard|detail` (कमाल JPEG परिमाण 320/640/1280, कधीही अपस्केल केलेले नाही), `limit=1..8` (किंवा लीगेसी `frames` उर्फ, कधीही दोन्ही नाही), शून्य-आधारित `page` आणि पर्यायी `start`/`end` फोकस सेकंद स्वीकारते. डुप्लिकेट क्वेरी की आणि रिव्हर्स फोकस विंडो नाकारल्या जातात. प्रत्येक परत केलेल्या व्हेरियंटमध्ये त्याच्या वास्तविक सामग्रीचा हॅश आणि वास्तविक रिझोल्यूशन मेटाडेटा असतो, जो राखून ठेवलेल्या स्त्रोताशी जोडलेला असतो. अतिरिक्त राखून ठेवलेल्या प्रती म्हणून संग्रहित करण्याऐवजी वाचनावर रूपे प्राप्त केली जातात. Base64/envelope सह JSON प्रतिसाद, 32 MiB वर मर्यादित आहे; मोठ्या आकाराचे पृष्ठ 413 देते आणि क्लायंटने कमी फ्रेम्सची विनंती करणे आवश्यक आहे. प्रत्येक आकार बदलाभोवती रद्दीकरण तपासा आणि परत येण्यापूर्वी हँडलची वैधता पुन्हा तपासा. मालकाद्वारे `DELETE` निर्बुद्ध आहे; हटवणे किंवा TTL एक्सपायरी राखून ठेवलेले स्त्रोत आणि वापर लेखांकन जारी करते.

शेअर्ड स्टोअर प्रक्रिया-स्थानिक आहे: हँडल्स रीस्टार्ट झाल्यावर कालबाह्य होतात आणि स्वतंत्र OmniRoute प्रक्रियेदरम्यान हस्तांतरणीय नाहीत. व्यवस्थापन आकडेवारी प्रभावी धारणा/रिमोट पॉलिसी उघड करते आणि केवळ राखून ठेवलेले entries/bytes, कधीही मीडिया, संदर्भ, मुख्य IDs किंवा हँडल नाही. व्हिडिओ सेटिंग्ज पॅनल ती मूल्ये दाखवते आणि दोन्ही संमती स्विच कायम ठेवू शकतात. हे अंमलबजावणी दस्तऐवजीकरण थेट उपयोजन किंवा जाहिरात पुरावा नाही; वास्तविक-मॉडेल स्वीकृती स्वतंत्रपणे ट्रॅक केली जाते.

कॉन्फिगर केलेल्या व्हिडिओ मॉडेलसह फ्रेम्स अनुक्रमे कॅप्शन दिले आहेत. रिकाम्या व्हिडीओ ओव्हरराइडमुळे व्हिजन सेटिंग इनहेरिट होते; दोन्ही रिकामे असल्यास, व्हिजन ऑटो-राउटर प्रभावी दृष्टी-सक्षम मॉडेल निवडतो. यशस्वी मथळे मूळ भागाला स्थिर `[Video description:` उपसर्गाने बदलतात जे अविश्वासू मीडिया-व्युत्पन्न निरीक्षण म्हणून मजकूर देखील चिन्हांकित करते आणि डाउनस्ट्रीम मॉडेल्सना मीडियामध्ये आढळलेल्या सूचनांचे पालन करू नका असे सांगतात. फ्रेम-मथळा कॅशे की मध्ये JPEG बाइट्स, प्रॉम्प्ट, टाइमस्टॅम्प आणि प्रभावी मॉडेल समाविष्ट आहेत; फक्त यशस्वी मथळे कॅश केले जातात. कॅशे एंट्री फॉलबॅक मॉडेलसह वास्तविक यशस्वी निर्माता मॉडेल राखून ठेवतात; ब्रिज `mixed` चा अहवाल देतो जेव्हा वेगवेगळ्या मॉडेल्सद्वारे वेगवेगळ्या फ्रेम्स तयार केल्या गेल्या. कॅशे हिट विनंती केलेल्या राउटिंग प्लॅन म्हणून रिलेबल करण्याऐवजी त्या उत्पादक ओळखीचा पुन्हा वापर करते. आउटपुट — प्रॉम्प्ट, प्रभावी मॉडेल, सॅम्पलिंग पॉलिसी, फ्रेम काउंट, सिमेंटिक ॲनालिसिस मोड, सामान्यीकृत फोकस हिंटचे SHA-256 फिंगरप्रिंट, फोकस विंडो, `transcript`, `audioTranscript`, आणि कॉन्टॅक्ट-शीट ध्वज — बदलणाऱ्या प्रत्येक इनपुटवर संपूर्ण-व्हिडिओ निकाल कॅशे की केला जातो, त्यामुळे यापैकी कोणतेही बदल करणे कधीही चुकत नाही. व्हिज्युअल डिडअप पॉलिसी आवृत्ती, थ्रेशोल्ड आणि बाउंडेड उमेदवार-फ्रेम संख्या परिणाम-कॅशे की आणि मेटाडेटामध्ये देखील स्पष्ट आहेत; त्यामुळे धोरणातील बदल एक जुना संपूर्ण-व्हिडिओ वर्णन पुन्हा वापरू शकत नाही. रिझल्ट-कॅशे v4 मेटाडेटा मोड आणि फिंगरप्रिंट ठेवतो, कधीही रॉ वापरकर्ता कार्य नाही. रेलिंग मेटाडेटा विनंती केलेल्या आणि प्रभावी विश्लेषण पद्धतींचा अहवाल देतो; वापरता येण्याजोग्या वापरकर्त्याच्या मजकुराशिवाय विनंती केलेला `focused` मोड प्रभावीपणे `full` म्हणून नोंदवला जातो.

रेलिंग प्रत्येक समर्थित व्हिडिओ भाग काढते परंतु `modalityBridgeVideoMaxVideos` पेक्षा जास्त वर्णन करत नाही. `supportsVideo === false` असल्याचे सिद्ध केलेल्या लक्ष्यासाठी, अयशस्वी आणि ओव्हर-लिमिट व्हिडिओ स्पष्ट सुरक्षित मजकूर मार्कर बनतात त्यामुळे कोणताही कच्चा व्हिडिओ टिकत नाही. जेव्हा क्षमता अज्ञात असते, तेव्हा ते भाग त्यांचे व्हिडिओ वाहक राखून ठेवतात; कोणताही फॉलबॅक उतारा वरील बाउंडेड मजकूर रूपांतरणाचे अनुसरण करतो. `supportsVideo === true` सह लक्ष्ये पुलाला बायपास करतात. क्लायंट रिक्वेस्ट ॲबॉर्ट सिग्नल डाउनलोड, ब्रोकर क्यू, सबप्रोसेस आणि कॅप्शन कॉलद्वारे प्रसारित होते; व्हिडिओंमध्ये गर्भपात थांबतो आणि कच्च्या मीडियासाठी कधीही अयशस्वी होत नाही.

रनटाइम सेटिंग्ज DB-बॅक्ड आणि Zod-प्रमाणित आहेत:

120 सेकंदांवरील व्हिडिओ टाइमआउट व्हॅल्यूज ब्रोकर डेडलाइनवर क्लॅम्प केले जातात; नवीन सेटिंग्ज त्या मर्यादेच्या वर लिहितात नाकारल्या जातात. प्रमाणीकरण किंवा रनटाइम प्रोबिंगपूर्वी `GET /api/modality-bridge/video/runtime` विश्वसनीय मुद्रांकित लूपबॅक लोकॅलिटी आवश्यक आहे, त्यानंतर व्यवस्थापन प्रमाणीकरण आवश्यक आहे. हे फक्त `available`, सॅनिटाइज्ड FFmpeg/ffprobe आवृत्त्या आणि रनटाइम अनुपलब्ध असताना एक निश्चित कारण परत करते. अंतर्गत एक्सट्रॅक्शन एंडपॉइंट सार्वजनिक अपलोड API नाही : रांग संपृक्तता `503` अधिक `Retry-After` परत करते, कॉलर डिस्कनेक्ट `499` परत करतो आणि निश्चित ब्रोकरची अंतिम मुदत `504` परत करते. रूपांतरित प्रतिसाद व्हिजन किंवा ऑडिओ विभाग न काढता मध्यवर्ती `x-omniroute-modality-bridge` शीर्षलेखात `video->text;model=<visionModel>;parts=<videos>` जोडतात.

### PII मास्कर (`piiMasker.ts`)

वर चालते**दोन्ही** टप्पे

- **`preCall`** पेलोड क्लोन करते, `system`, `messages`, `input`, आणि `prompt` (साध्या स्ट्रिंग आयटमसह) चालते आणि `content`/`text` फील्ड स्ट्रिंगवर `processPII()` ( `@/shared/utils/inputSanitizer` वरून) लागू करते. जेव्हा `PII_REDACTION_ENABLED=true`, आढळलेले PII आउटबाउंड पेलोडमध्ये सुधारित केले जाते. हे `INPUT_SANITIZER_MODE` पासून स्वतंत्र आहे (जे फक्त प्रॉम्प्ट-इंजेक्शन धोरण नियंत्रित करते). जेव्हा रिडेक्शन बंद असते, तेव्हा सामग्री पुन्हा न लिहिता कॉल रेकॉर्ड डिटेक्शनची संख्या.
- **`postCall`** प्रतिसादाला डीप-क्लोन करते, `sanitizePIIResponse()` अधिक प्रतिसाद-API-आकार मास्कर चालवते (`maskResponsesOutput` — `output_text` आणि `output[].content[].text` कव्हर करते). कोणतीही सुधारणा घडल्यास, सुधारित प्रतिसाद मूळ प्रतिक्रियेची जागा घेतो.

रेलिंग कधीच अडवत नाही; ते फक्त भाष्य करते (`meta.detections`, `meta.redacted`) किंवा पुन्हा लिहिते.

#### प्रति-प्रकार निवड, सानुकूल नमुने आणि शोध काउंटर

**डॅशबोर्ड → सेटिंग्ज → सुरक्षा → PII मास्किंग** मुखवटा घातलेला _what_ निवडतो. हे मास्किंग चालू करत नाही: ते अजूनही `PII_REDACTION_ENABLED` (विनंती) आणि `PII_RESPONSE_SANITIZATION` (प्रतिसाद + SSE) आहे, दोन्ही डीफॉल्टनुसार बंद आहेत.

- **प्रति-प्रकार निवड** — अंगभूत आयडी `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`) मध्ये सूचीबद्ध आहेत. अनसेट म्हणजे प्रत्येक प्रकार (या सेटिंगपूर्वीचे वर्तन अस्तित्वात होते). विनंती इंजिनचा `ssn_us` नमुना `ssn` वर मॅप करतो. टेम्पलेट्स (किमान, मानक, आर्थिक, ब्राझिलियन, USA, GDPR, POPIA, पूर्ण) फक्त UI मध्ये चेकबॉक्सेस भरतात.
- **GDPR आणि POPIA अभिज्ञापक** — बारा अंगभूत आयडी जे EU आणि दक्षिण आफ्रिकन वैयक्तिक अभिज्ञापक (खाली सारणी) कव्हर करतात. त्यांचे regexes, प्रमाणीकरणकर्ते आणि अधिकार क्षेत्र टॅग `src/shared/utils/piiPatterns.ts`, एका टेबलमध्ये राहतात, जे रिस्पॉन्स सॅनिटायझर (`src/lib/piiSanitizer.ts`) आणि रिक्वेस्ट मास्कर (`src/shared/utils/inputSanitizer.ts`) दोन्ही वापरतात. जुळणी केवळ तेव्हाच दुरुस्त केली जाते जेव्हा त्याचा वैधकर्ता तो स्वीकारतो; अंकांची एक उघडी धाव कधीही पुरेशी नसते. ज्या ऑपरेटरने या आयडी अस्तित्वात येण्यापूर्वी एक संकुचित निवड जतन केली आहे तो नवीन आयडी टिक होईपर्यंत त्याचे वर्तन ठेवतो.
- **सानुकूल नमुने** — पर्यंत 20 regex किंवा वाइल्डकार्ड पॅटर्न (`*` = 64 नॉन-व्हाइटस्पेस वर्णांपर्यंत, `?` = एक). सामने `[CUSTOM_REDACTED]` होतात. प्रत्येक पॅटर्न `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`) द्वारे जातो: जास्तीत जास्त 500 वर्ण, `g i m s u` पर्यंत मर्यादित ध्वज संकलित करणे आवश्यक आहे, `safe-regex` (आपत्तीजनक बॅकट्रॅकिंग) पास करणे आवश्यक आहे, आणि रिक्त स्ट्रिंग किंवा रिडेक्शन प्लेसहोल्डरशी जुळू नये. अयशस्वी झालेला नमुना जतन केल्यावर आणि चाचणी केल्यावर नाकारला जातो आणि अयशस्वी होणारी संचयित पंक्ती संकलित होण्याऐवजी रनटाइमवर वगळली जाते. मास्किंग चालू असतानाच कस्टम पॅटर्न चालतात.
- **डिटेक्शन काउंटर** — प्रति-प्रकार संख्या (कधीही जुळलेली मूल्ये), मेमरीमध्ये ठेवली जातात आणि रीस्टार्ट (`src/lib/pii/piiDetectionStats.ts`) वर रीसेट केली जातात. मास्किंग चालू असतानाच ते वाढतात.

सेटिंग्ज `key_value` टेबलमध्ये राहतात (नेमस्पेस `pii_settings`, `src/lib/db/piiSettings.ts`) आणि 1 s कॅशेद्वारे वाचल्या जातात. API:

| मेथड   | पाथ                      | उद्देश                                                                            |
| ------ | ------------------------ | --------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | फ्लॅग स्थिती, `enabledTypes`, `customPatterns`, डिटेक्शन काउंटर                   |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = सर्व) आणि/किंवा `customPatterns` बदलणे                   |
| `POST` | `/api/settings/pii/test` | जास्तीत जास्त 8 KB च्या नमुन्यावर एक पॅटर्न ड्राय-रन करणे; काहीही साठवले जात नाही |

तिघांना व्यवस्थापन प्रमाणीकरण आवश्यक आहे आणि Zod (`src/shared/validation/schemas/piiSettings.ts`) सह बॉडी प्रमाणित करा. लॉगिन अक्षम केल्यामुळे (`requireLogin=false`) `GET` आणि चाचणी एंडपॉईंट उघडे आहेत, परंतु `PUT` अजूनही डॅशबोर्ड सत्र, `manage` -scope API की, लेखन स्कोप किंवा त्याहून अधिक `oma_` प्रवेश टोकन किंवा लूपबॅकमधून पाठवलेले CLI टोकन किंवा अंतर्गत-सेवा टोकन आवश्यक आहे.

### प्रॉम्प्ट इंजेक्शन (`promptInjection.ts`)

वापरकर्त्याने दिलेल्या कंटेंटमधील प्रतिकूल संरचना शोधते आणि कॉन्फिगर केलेली
पॉलिसी लागू करते. वर्तन एन्व्हायरनमेंट व्हेरिएबल्स आणि कन्स्ट्रक्टर पर्यायांद्वारे
चालवले जाते:

| सेटिंग          | एन्व्ह व्हेरिएबल                                                                                      | डीफॉल्ट | परिणाम                                                                                                                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| सक्षम           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | `false` असताना, गार्डरेल शॉर्ट-सर्किट होते.                                                                                                                                                  |
| मोड             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | इंजेक्शन पॉलिसी: `block`, `warn`, किंवा `log`. (`redact` बॅक-कम्पॅट साठी स्वीकारले जाते पण इंजेक्शन मजकूर **काढत नाही**; रिक्वेस्ट PII रीराइट `PII_REDACTION_ENABLED` द्वारे नियंत्रित आहे.) |
| ब्लॉक थ्रेशोल्ड | `blockThreshold` पर्याय / `INPUT_SANITIZER_BLOCK_THRESHOLD` (उपनाम `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | ब्लॉक करण्यासाठी आवश्यक किमान गंभीरता. डीफॉल्टनुसार मीडियम फक्त-निरीक्षण आहे.                                                                                                                |

**मोड प्राधान्य** (`getMode`): कॉलर `options.mode` →
`INJECTION_GUARD_MODE` **DB फीचर-फ्लॅग ओव्हरराइड** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. त्यामुळे डॅशबोर्ड ओव्हरराइड env व्हेरिएबल्सवर जिंकते, म्हणून Feature
Flags UI चालू गार्डला लाइव्ह नियंत्रित करते (रीस्टार्ट नाही). DB रीड फेल-सेफ आहे:
जर त्यात त्रुटी आली, तर गार्ड env-आधारित वर्तनाकडे परत जाते, आणि जेव्हा कोणतेही
ओव्हरराइड सेट नसते तेव्हा वर्तन फक्त-env रिझोल्यूशनसारखेच असते.

डिटेक्शन स्रोत:

1. `@/shared/utils/inputSanitizer` मधील `sanitizeRequest()` (पाइपलाइनमध्ये
   इतरत्र वापरले जाणारे शेअर्ड डिटेक्टर सेट).
2. बिल्ट-इन `DEFAULT_GUARD_PATTERNS` (सध्या `system_override_inline` आणि
   `markdown_system_block`, दोन्ही `high` गंभीरता).
3. कन्स्ट्रक्टर पर्यायांद्वारे दिलेले ऐच्छिक `customPatterns` (स्ट्रिंग्ज, रेजेक्स,
   किंवा `{ name, pattern, severity }` रेकॉर्ड्स).

जेव्हा `mode === "block"` **आणि** किमान एक डिटेक्शन सीव्हिअरिटी थ्रेशोल्ड पूर्ण करते, तेव्हा `preCall` हे `{ block: true, message: "Request rejected: suspicious content detected" }` रिटर्न करते. `warn`/`log` मोडमध्ये guardrail लॉग करते पण कॉलला परवानगी देते. रजिस्ट्रीमधून न जाता प्रॉम्प्ट्सचे मूल्यमापन करायचे असलेल्या कॉलर्ससाठी शेअर्ड हेल्पर `evaluatePromptInjection()` देखील एक्सपोर्ट केलेले आहे.

**स्कॅन मर्यादा (v3.8.20):** डिटेक्टर फक्त जोडलेल्या प्रॉम्प्ट टेक्स्टचे **पहिले 16 KB** तपासते — `src/shared/utils/inputSanitizer.ts` मध्ये `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 बाइट्स). `detectInjection()` आणि `evaluatePromptInjection()` दोन्ही पॅटर्न लूप चालवण्यापूर्वी `slice(0, MAX_INJECTION_SCAN_BYTES)` करतात. इंजेक्शन डायरेक्टिव्ह्ज इनपुटच्या वरच्या भागाजवळ असतात, त्यामुळे डिटेक्शन कमकुवत न करता हे अनेक-शंभर-KB पेलोड्सवर regex CPU/GC मर्यादित ठेवते (पहा #3932, #4041).

### क्रेडेन्शियल मास्कर (`credentialMasker.ts`)

हे **दोन्ही** स्टेजेसवर चालते, डिफॉल्ट चेनमध्ये शेवटी (प्रायऑरिटी `95`). आउटबाउंड पेलोड (मेसेज कंटेंट, टूल-कॉल आर्ग्युमेंट्स, टूल रिझल्ट्स) **आणि** प्रोव्हायडर रिस्पॉन्समधून सुपरिचित API-की / सीक्रेट-टोकन पॅटर्न्स रिडॅक्ट करते, जेणेकरून प्रॉम्प्टमध्ये पेस्ट केलेले (किंवा टूल रिझल्टने परत दिलेले) क्रेडेन्शियल अपस्ट्रीम प्रोव्हायडरकडे किंवा क्लायंटकडे परत लीक होत नाही.

- **फक्त ऑप्ट-इन**, PII रिडॅक्शनसारखीच परंपरा (Hard Rule #20-जवळची): `settings.credentialRedactionEnabled === true` **किंवा** `CREDENTIAL_REDACTION_ENABLED=true` नसेल तर बंद राहते. ते बंद असल्यास हा guardrail no-op आहे — तो कधीही ब्लॉक करत नाही आणि कधीही रिराइट करत नाही.
- `redactCredentials()` संपूर्ण पेलोड/रिस्पॉन्स ट्री तपासते (`walkValue()`, prototype-pollution-safe, `WeakSet` मुळे cycle-safe) आणि जुळणाऱ्या मजकुराला `[REDACTED:<type>]` प्लेसहोल्डरने बदलते, फक्त खरोखर बदललेल्या ब्रांचेस क्लोन करते.
- `CREDENTIAL_PATTERNS` मध्ये LLM प्रोव्हायडर कीज (OpenAI, OpenAI-proj, Anthropic, Google, Hugging Face, Replicate), VCS/SaaS टोकन्स (GitHub, Slack, Linear, Notion, npm, Postman, Discord), पेमेंट कीज (Stripe, Square), क्लाउड कीज (AWS ऍक्सेस की, Twilio, SendGrid, Mailgun), प्रायव्हेट कीज / JWTs, क्रेडेन्शियल असलेले कनेक्शन स्ट्रिंग्ज (`mongodb://user:pass@...`, इ.) आणि एक सामान्य `Authorization`/`x-api-key`/`api-key`/`apikey` हेडर-व्हॅल्यू पॅटर्न यांचा समावेश आहे. हेडर-आकाराच्या कीज (`authorization`, `x-api-key`, `api-key`, `apikey`) सामान्य टेक्स्ट regex ऐवजी संरचनात्मकरीत्या रिडॅक्ट केल्या जातात (फक्त व्हॅल्यू, `Bearer `/`Basic ` सारखा स्कीम प्रीफिक्स जतन केला जातो).
- हा guardrail कधीही ब्लॉक करत नाही; तो फक्त रिराइट करतो (`modifiedPayload` / `modifiedResponse`) आणि अॅनोटेट करतो (`meta.credentialsRedacted`, `meta.count`).

रिग्रेशन गार्ड: `tests/unit/credential-masker-guardrail.test.ts`.

## बेस कॉन्ट्रॅक्ट (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true असल्यास चेन शॉर्ट-सर्किट होते
  message?: string; // ब्लॉक करताना दाखवले जाते
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // विनंती पुन्हा लिहिण्यासाठी preCall द्वारे परत केले जाते
  modifiedResponse?: TValue; // प्रतिसाद पुन्हा लिहिण्यासाठी postCall द्वारे परत केले जाते
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

गार्डरेल `void`, `{}` किंवा `{ block: false }` परत करून "बदल नाही" असे सूचित करते. `modifiedPayload`/`modifiedResponse` परत केल्याने डाउनस्ट्रीम गार्डरेल्ससाठी चेनमधून वाहणारे मूल्य बदलले जाते. `signal?: AbortSignal` कॉलर लाइफसायकल गार्डरेल्समध्ये घेऊन जाते. विनंती रद्द करणे (abort) हा जाणीवपूर्वक ठेवलेला फेल-ओपन अपवाद आहे: मीडिया ब्रिजेस काम थांबवतात आणि कच्चा मीडिया समर्थित नसल्याचे ठरलेल्या लक्ष्यावर तो पुनर्स्थापित न करता क्लीनअप करतात.

## रजिस्ट्री (`registry.ts`)

सिंगलटन `guardrailRegistry` खालील गोष्टी एक्सपोज करते:

- `register(guardrail)` — गार्डरेल जोडते (किंवा नॉर्मलाइज केलेल्या नावाने बदलते) आणि
  `priority` च्या चढत्या क्रमाने पुन्हा क्रमवारी लावते.
- `clear()` / `list()` — प्रशासकीय हेल्पर फंक्शन्स.
- `runPreCallHooks(payload, context)` — सक्रिय गार्डरेल्सवर इटरेट करते, पेलोडला
  `modifiedPayload` मधून पुढे नेते आणि पहिल्या `block: true` वर थांबते.
- `runPostCallHooks(response, context)` — प्रतिसाद बाजूने त्याच प्रवाहाची पुनरावृत्ती.
- `resetGuardrailsForTests({ registerDefaults })` — स्टेट साफ करते आणि स्वच्छ टेस्ट
  आयसोलेशनसाठी ऐच्छिकपणे डीफॉल्ट्स पुन्हा नोंदवते.

दोन्ही रनर्स `{ blocked, payload|response, results, guardrail?, message? }` परत करतात, जिथे `results` हा `GuardrailExecutionResult` रेकॉर्ड्सचा अॅरे असतो ज्यामध्ये प्रत्येक गार्डरेलसाठी `blocked`, `skipped`, `modified`, `error` आणि `meta` फील्ड्स असतात — ट्रेसिंगसाठी उपयुक्त.

### प्रति-विनंती गार्डरेल्स अक्षम करणे

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` सध्याच्या विनंतीसाठी वगळावयाच्या गार्डरेल नावांची डुप्लिकेट-विरहित यादी एकत्र करते. पाच चॅनेल्स आहेत, जे या क्रमाने वाचले जातात आणि एका यादीत विलीन केले जातात (डुप्लिकेट काढताना पहिली घटना जिंकते):

1. `apiKeyInfo.disabledGuardrails`
2. विनंती बॉडी `disabledGuardrails` (टॉप-लेव्हल)
3. विनंती बॉडी `metadata.disabledGuardrails` (फक्त `metadata` हे ऑब्जेक्ट असताना)
4. हेडर `x-omniroute-disabled-guardrails`
5. लेगसी हेडर `x-disabled-guardrails`

सर्व पाच चॅनेल्स विलीन केले जातात, दोन्ही हेडरंसह: `x-omniroute-disabled-guardrails` आणि `x-disabled-guardrails` दोन्ही पाठवल्यास त्यांच्या यादींचे युनियन वगळले जाते, आणि रिकामे आधुनिक हेडर आता लेगसी हेडर लपवत नाही ([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), [#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805) मध्ये दुरुस्त).

व्हॅल्यूज स्ट्रिंग्जचे अॅरे किंवा स्वल्पविरामाने वेगळी केलेली स्ट्रिंग असू शकतात; नावे ट्रिम केली जातात आणि लोअरकेस kebab-case मध्ये नॉर्मलाइज केली जातात (`pii_masker` → `pii-masker`), आणि रिकाम्या एन्ट्रीज काढून टाकल्या जातात. निकाल `context.disabledGuardrails` मधून रजिस्ट्रीकडे पाठवला जातो, जी जुळणाऱ्या गार्डरेल्स वगळते (`results` मध्ये `skipped: true`).

अक्षम करण्याची यादी फक्त **रजिस्ट्री**वर परिणाम करते. प्रॉम्प्ट-इंजेक्शन `block` मोड ही एक अनिवार्य सीमा आहे: इंजेक्शन-गार्ड मिडलवेअर (`src/middleware/promptInjectionGuard.ts`) कोणत्याही कॉलर-नियंत्रित अक्षम यादीशिवाय `evaluatePromptInjection()` कॉल करते (पूर्वी तो करत असलेला निरुपयोगी `resolveDisabledGuardrails({ body })` कॉल [#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934) मध्ये काढून टाकला गेला), त्यामुळे `prompt-injection` अक्षम करणारी विनंती `block` मोडमध्ये तरीही नाकारली जाते. हे जाणीवपूर्वक असे डिझाइन केलेले आहे. अक्षम करण्याचे चॅनेल्स कॉलर-नियंत्रित आहेत (विनंती बॉडी, मेटाडेटा, हेडर्स), आणि ऑपरेटरने सेट केलेले सुरक्षा नियंत्रण कॉलर बंद करू शकू नये ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412) मधील हेडर युनियन केवळ कोणती रजिस्ट्री गार्डरेल्स वगळली जातात हे बदलते; ते क्लायंटला मिडलवेअर बायपास करू देत नाही. प्रति-की आणि प्रति-ग्रुप अनिवार्य गार्डरेल धोरणे v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417) मध्ये ट्रॅक केली जातात. [कव्हरेज आणि मर्यादा](#coverage-and-limits) पहा.

## अंमलबजावणी क्रम

`src/sse/handlers/chat.ts` आणि `open-sse/handlers/chatCore.ts` मधून वाहणाऱ्या प्रत्येक विनंतीसाठी ([व्याप्ती आणि मर्यादा](#coverage-and-limits) अंतर्गत सूचीबद्ध केलेले चॅट-कुटुंब मार्ग):

1. `resolveDisabledGuardrails(...)` API की, बॉडी आणि हेडर्समधून स्किप यादी तयार करते.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` चढत्या प्राधान्य क्रमाने गार्डरेल्स चालवते:
   - अक्षम गार्डरेल्स `skipped` म्हणून नोंदवले जातात.
   - प्रत्येक गार्डरेलचा `preCall` `modifiedPayload` द्वारे पेलोड पुन्हा लिहू शकतो.
   - पहिला `block: true` शृंखला शॉर्ट-सर्किट करतो आणि हँडलर गार्डरेल नकार प्रतिसाद देते.
3. (संभाव्यपणे पुन्हा लिहिलेला) पेलोड कॉम्बो राउटिंग आणि अपस्ट्रीम डिस्पॅचमध्ये वाहतो.
4. **फक्त नॉन-स्ट्रीमिंग:** प्रतिसाद तयार झाल्यानंतर, `guardrailRegistry.runPostCallHooks(...)` प्रतिसादावर तीच शृंखला चालवते. येथे `block: true` अपस्ट्रीम प्रतिसाद काढून टाकते आणि HTTP 400 देते. स्ट्रीम केलेले प्रतिसाद ही पायरी पूर्णपणे वगळतात.

थ्रो करणारे गार्डरेल्स `error: <message>` सह नोंदवले जातात आणि `logger.warn` द्वारे लॉग केले जातात, परंतु शृंखला चालू राहते — डिझाइननुसार फेल-ओपन.

### काय समाविष्ट नाही

- **मीडिया, एम्बेडिंग्ज आणि डेटा मार्ग** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) रजिस्ट्रीपर्यंत कधीही पोहोचत नाहीत. तेथे
  PII मास्किंग, क्रेडेन्शियल मास्किंग किंवा मोडॅलिटी ब्रिज चालत नाही. त्यांची एकमेव
  तपासणी म्हणजे लेगसी इंजेक्शन-गार्ड मिडलवेअर.
- **स्ट्रीम केलेल्या प्रतिसादांना** कोणतेही पोस्ट-कॉल गार्डरेल्स मिळत नाहीत: `pii-masker` किंवा
  `credential-masker` पोस्ट-कॉल नाही, आणि पोस्ट-कॉल ब्लॉक नाही. फक्त स्ट्रीमिंग PII
  ट्रान्सफॉर्म लागू होतो (जेव्हा `PII_RESPONSE_SANITIZATION` चालू असते). स्ट्रीम केलेल्या प्रतिसादात परत आलेले क्रेडेन्शियल
  रिडॅक्ट केले जात नाही.
- **अक्षम चॅनेल्स विरुद्ध मिडलवेअर (डिझाइननुसार):** मिडलवेअर
  `evaluatePromptInjection()` च्या स्वतःच्या कॉलसह प्रॉम्प्ट इंजेक्शनचे मूल्यमापन करते, कोणतीही कॉलर-नियंत्रित
  अक्षम यादी न देता. `block` मोड ही एक अनिवार्य सीमा आहे जी कॉलर-नियंत्रित अक्षमे
  बायपास करू शकत नाहीत, चॅट-कुटुंब मार्गांवरसुद्धा
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). `prompt-injection` अक्षम करणे
  फक्त रजिस्ट्री गार्डरेल वगळते.

### पोस्ट-कॉलपूर्वी प्रतिसाद काय पाहतो

नॉन-स्ट्रीमिंग मार्गावर क्रम असा आहे: मेमरी एक्स्ट्रॅक्शन → बिल्ट-इन टूल
अंमलबजावणी → पोस्ट-कॉल गार्डरेल्स → पोस्ट-कॉल ब्लॉक एग्झिट → सिमँटिक-कॅशे स्टोअर.

- **मेमरी एक्स्ट्रॅक्शन** आणि **टूल एक्झिक्युशन** पोस्ट-कॉल
  गार्डरेल्स रिस्पॉन्स पुन्हा लिहू किंवा ब्लॉक करू शकण्याआधी तो पाहतात.
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) पासून, मेमरी
  एक्स्ट्रॅक्शन `PII_RESPONSE_SANITIZATION` चालू असताना एक्स्ट्रॅक्ट केलेला
  मजकूर `sanitizePII` मधून चालवते (स्ट्रीमिंग आणि नॉन-स्ट्रीमिंग दोन्ही), परंतु
  पोस्ट-कॉल नंतर ब्लॉक केला जाणारा रिस्पॉन्स तरीही मेमरी आणि
  टूल्सना आधीच दिलेला असतो.
- **सिमँटिक कॅशे** पोस्ट-कॉल नंतर रिस्पॉन्स साठवते, म्हणून ती
  पुन्हा लिहिलेला रिस्पॉन्स साठवते, आणि ब्लॉक केलेला रिस्पॉन्स कधीही कॅशे केला
  जात नाही. कॅशे एंट्री प्रत्येक API कीनुसार की केलेल्या असतात.

## कॉन्फिगरेशन

अंगभूत गार्डरेल्सद्वारे वाचले जाणारे एन्व्हायरनमेंट व्हेरिएबल्स:

| व्हेरिएबल                             | वापरले जाते                | प्रभाव                                                                                                |
| ------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | डिटेक्शन पूर्णपणे अक्षम करण्यासाठी `false` सेट करा.                                                   |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | इंजेक्शन धोरण: `warn`, `block` किंवा `log`. जुने मूल्य `redact` इंजेक्शन मजकुराचे पुनर्लेखन करत नाही. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | इंजेक्शन गार्डसाठी मोड; तसेच env vars ला **अधिलेखित** करणारा DB फीचर फ्लॅग (DB > ENV).                |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` नाकारण्यासाठीची किमान तीव्रता: `high` (डीफॉल्ट), `medium` किंवा `low`.                   |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` चा जुना उपनाम.                                                      |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | `true` असताना, विनंतीतील PII मास्क केले जाते (इंजेक्शन मोडपासून स्वतंत्र).                            |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (डाउनस्ट्रीम) | प्रतिसाद-बाजूच्या मास्करच्या वर्तनावर नियंत्रण ठेवते.                                                 |

Modality Bridge गार्डरेल्स env vars ऐवजी DB-आधारित सेटिंग्ज स्टोअरमधून (`getSettings()`) रनटाइम कॉन्फिग वाचतात. Vision च्या प्राथमिक की आहेत
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, आणि
`modalityBridgeCacheMaxEntries`. जुन्या
`visionBridge*` की फक्त दस्तऐवजीकृत एक-चकर वाचन फॉलबॅक म्हणून
स्वीकारल्या जातात; डॅशबोर्ड लेखन प्राथमिक की वापरते. डीफॉल्ट्स आणि फॉलबॅक
रिझॉल्व्हर `src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत, तर जुने
स्थिरांक `src/shared/constants/visionBridgeDefaults.ts` मध्ये ठेवलेले आहेत.

Audio `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, आणि `modalityBridgeAudioMaxClips` वापरते, तसेच सामायिक
`modalityBridgeCache*` सेटिंग्ज. Audio ला जुन्या-की फॉलबॅक नाही कारण या
की Modality Bridge स्कीमासोबतच सादर करण्यात आल्या होत्या.

Video `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, आणि
`modalityBridgeVideoTimeout` वापरते, तसेच सामायिक `modalityBridgeCache*` सेटिंग्ज.
FFmpeg/ffprobe हे ऐच्छिक परिचालन अवलंब असल्यामुळे आणि फ्रेम कॅप्शनिंगमुळे विलंब व मॉडेल खर्च वाढल्यामुळे ते डीफॉल्टनुसार अक्षम असते.

## कस्टम गार्डरेल्स

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

पायऱ्या:

1. `BaseGuardrail` एक्स्टेंड करणारी `src/lib/guardrails/myGuardrail.ts` तयार करा.
2. `preCall` आणि/किंवा `postCall` अंमलात आणा.
3. इम्पोर्ट वेळी नोंदणी करा (`registerDefaultGuardrails` मधून push करून) किंवा
   रनटाइमदरम्यान `guardrailRegistry.register(...)` कॉल करा — रजिस्ट्री त्याच
   नॉर्मलाइज केलेल्या नावाचा कोणताही आधीचा गार्डरेल बदलून टाकते.
4. `tests/unit/` खाली चाचण्या जोडा (विद्यमान उदाहरणे:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## इंजेक्शन-गार्ड रूट कव्हरेज आणि रेड-टीम (टप्पा 8 · ब्लॉक D)

इंजेक्शन-गार्ड (`createInjectionGuard` / `withInjectionGuard`) वापरकर्ता प्रॉम्प्ट्स
स्वीकारणारे सर्व रूट्स कव्हर करतो. तो `INJECTION_GUARD_MODE` चे पालन करतो (डीफॉल्ट
`warn` = फक्त लॉग; `block` = HTTP 400 `SECURITY_001` परत करतो).

| प्रकार           | रूट्स                                                                                                                                                | डीफॉल्ट मोड |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| मजकूर (विद्यमान) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| जनरेटिव्ह        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| डेटा             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

मजकूर एक्स्ट्रॅक्शन (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` कव्हर करते.

**रेड-टीम (नाइटली, `nightly-llm-security.yml`):** promptfoo प्रत्येक रूट
`INJECTION_GUARD_MODE=block` मध्ये OWASP-LLM कॉर्पस ब्लॉक करतो याची पडताळणी करतो;
garak प्रोब्स चालवतो (सीक्रेट नसल्यास स्किप करतो). सुसंगतेसाठी `moderations` समाविष्ट
आहे. ब्लॉक मोड ही एक अनिवार्य सीमा आहे: `evaluatePromptInjection()` मिडलवेअर दिलेली
प्रति-विनंती डिसेबल यादी दुर्लक्षित करतो, त्यामुळे `disabledGuardrails` रूटला त्यातून
सूट देत **नाही** ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

नाइटली वर्कफ्लो (`.github/workflows/nightly-llm-security.yml`, क्रॉन + मॅन्युअल
डिस्पॅच) मध्ये दोन जॉब्स आहेत:

- **`promptfoo-guard` (ब्लॉकिंग)** — `INJECTION_GUARD_MODE=block` सह
  `promptfoo eval -c promptfooconfig.yaml` चालवतो. प्रत्येक adversarial केस
  (उदा. "ignore all previous instructions…", DAN-शैलीतील जेलब्रेक्स) रिस्पॉन्समध्ये
  `error.code === "SECURITY_001"` असल्याची खात्री करतो, म्हणजे गार्डने विनंती
  प्रत्यक्षात नाकारली.
- **`garak` (अॅडव्हायझरी)** — स्थानिक OmniRoute इन्स्टन्सविरुद्ध
  (`http://localhost:20128/v1`) garak `--probes promptinject,dan,leakreplay`
  चालवतो. प्रोव्हायडर सीक्रेटवर (`PROMPTFOO_PROVIDER_KEY`) गेटेड; सुयोग्यपणे स्किप
  होतो आणि `|| true` सफिक्स असल्याने CI नापास न करता रिपोर्ट करतो.

गार्ड हेल्पर (`createInjectionGuard` / `withInjectionGuard`) चे कव्हरेज प्रत्येक
प्रॉम्प्ट-बेअरिंग `/v1` रूटवर पसरले आहे; प्रॉम्प्ट मजकूर
`src/shared/utils/inputSanitizer.ts` मधील `extractMessageContents()` द्वारे
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` मधून काढला
जातो.
