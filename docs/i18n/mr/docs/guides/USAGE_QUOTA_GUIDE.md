> **TL;DR**: OmniRoute प्रत्येक विनंतीचा टोकन वापर ट्रॅक करते, खर्चाची गणना करते, प्रत्येक API कीसाठी कोटा लागू करते आणि डॅशबोर्डमध्ये विश्लेषण दाखवते. हे सर्व कसे कार्य करते, हे या मार्गदर्शकामध्ये स्पष्ट केले आहे.

**स्रोत:**

- `open-sse/services/usage.ts` (~70KB) — मुख्य वापर ट्रॅकिंग
- `src/lib/usageAnalytics.ts` (~10KB) — डॅशबोर्डसाठी एकत्रीकरण
- `src/lib/db/quotaSnapshots.ts` — ऐतिहासिक कोटा डेटा
- `src/lib/db/usage*.ts` — वापराशी संबंधित अनेक DB मॉड्यूल

## आढावा

OmniRoute मधून जाणारी प्रत्येक विनंती एक **वापर नोंद** तयार करते, ज्यामध्ये पुढील माहिती नोंदवली जाते:

- **ओळख**: कोणती API की, प्रदाता, मॉडेल, कॉम्बो
- **टोकन**: प्रॉम्प्ट टोकन, कम्प्लिशन टोकन, कॅश केलेले टोकन, एकूण
- **खर्च**: USD रक्कम (किंमत डेटावरून गणना केलेली)
- **वेळ**: विलंब, सुरुवात/समाप्ती टाइमस्टॅम्प
- **स्थिती**: यशस्वी, त्रुटी, दर-मर्यादित इत्यादी

या नोंदी एकत्रित करून **विश्लेषणे** तयार केली जातात, ती **कोटा स्नॅपशॉट्स** म्हणून कायमस्वरूपी साठवली जातात आणि **प्रत्येक कीसाठी अर्थसंकल्पीय मर्यादा** लागू करण्यासाठी वापरली जातात.

```
विनंती ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    विश्लेषण   कोटा    बिलिंग
                    (डॅशबोर्ड) (अंमलबजावणी) (निर्यात)
```

## काय नोंदवले जाते

`usage.ts` सेवा प्रत्येक विनंतीसाठी एक **वापर इव्हेंट** नोंदवते:

| फील्ड              | प्रकार  | स्रोत                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | नोंद करताना तयार केलेला UUID                               |
| `apiKeyId`         | string  | विनंती सुरू करणारी API की                                  |
| `provider`         | string  | प्रदाता ID (openai, anthropic, इ.)                         |
| `model`            | string  | मॉडेल ID (gpt-5, claude-opus-4-6, इ.)                      |
| `comboId`          | string? | कॉम्बोद्वारे रूट केले असल्यास कॉम्बो ID                    |
| `promptTokens`     | number  | अपस्ट्रीम प्रतिसादातून                                     |
| `completionTokens` | number  | अपस्ट्रीम प्रतिसादातून                                     |
| `cachedTokens`     | number  | कॅश हिट टोकन (Anthropic प्रॉम्प्ट कॅशिंग, इ.)              |
| `totalTokens`      | number  | प्रॉम्प्ट + पूर्णता                                        |
| `costUsd`          | number  | किंमत डेटावरून गणना केलेला खर्च                            |
| `latencyMs`        | number  | विनंतीचा सुरुवातीपासून शेवटपर्यंतचा कालावधी                |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | स्थिती != success असल्यास त्रुटी वर्ग                      |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | प्लगइनद्वारे समाविष्ट केलेला सानुकूल डेटा                  |

### टोकन कुठून येतात

**प्रतिसाद हँडलरमध्ये** अपस्ट्रीम प्रदात्याच्या प्रतिसादातून टोकन काढले जातात:

```ts
// open-sse/handlers/chatCore.ts मधून
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

जे प्रदाते वापराची माहिती परत करत नाहीत (काही वेब-कुकी प्रदाते), त्यांच्यासाठी OmniRoute `~4 chars per token` या अंदाजाधारित नियमाचा वापर करून टोकनचा **अंदाज लावते** (`open-sse/services/autoCombo/pipelineRouter.ts` पहा).

### कॅश केलेले टोकन

OmniRoute `cached_tokens` ची नोंद `prompt_tokens` पासून स्वतंत्रपणे ठेवते, कारण:

- Anthropic प्रॉम्प्ट कॅशिंगमध्ये कॅश केलेल्या टोकनसाठी कमी दर आकारला जातो (सामान्य दराच्या 10%)
- काही प्रदाते `cache_read_input_tokens` परत करतात, ज्यांसाठी वेगळा दर लागू केला पाहिजे
- विश्लेषणामध्ये **कॅश हिट दर** = `cached_tokens / prompt_tokens` दाखवता येतो

### कॅश-लेखन स्तराचे निदान

Analytics डॅशबोर्डवरील प्रॉम्प्ट-कॅश स्थिती पॅनेल प्रदात्याने नोंदवलेल्या
5-मिनिटांच्या आणि 1-तासाच्या कॅश लेखनांमध्ये फरक करते. Anthropic चे
`usage.cache_creation.ephemeral_5m_input_tokens` आणि
`usage.cache_creation.ephemeral_1h_input_tokens` हे स्ट्रीमिंग आणि
नॉन-स्ट्रीमिंग वापर रूपांतरणादरम्यान जतन केले जातात आणि कॉल-लॉग सारांशांसह साठवले जातात. एकत्रित
कॅश-लेखनाची एकूण संख्या त्या गटांमध्ये दुसऱ्यांदा जोडली जात नाही.

केवळ एकत्रित लेखन काउंटर असलेल्या कॉलचा स्तर अज्ञात असतो; यात जुन्या नोंदींचाही समावेश होतो.
अंशतः विभागणी उपलब्ध असल्यास, तिचा वाटप न झालेला उर्वरित भाग अज्ञात ठेवला जातो; अवैध किंवा
परस्परविरोधी काउंटरना गुपचूप TTL देण्याऐवजी चिन्हांकित केले जाते. विनंतीच्या बाजूचे
TTL निर्देशक हे शुल्क आकारलेल्या स्तराचा पुरावा नसतात.

पॅनेलचा API-समतुल्य लेखन अंदाज केवळ नोंदवलेल्या आणि किंमत उपलब्ध असलेल्या स्तरांपुरता मर्यादित असतो,
संपूर्ण विनंतीसाठी नसतो. मूळ Claude/Anthropic मॉडेल किंमतींसाठी, तो 5-मिनिटांच्या लेखनासाठी
इनपुट दराच्या 1.25 पट आणि 1-तासाच्या लेखनासाठी इनपुट दराच्या दुप्पट दर वापरतो. किंमत उपलब्ध नसल्यास
ती अनुपलब्ध मानली जाते, शून्य नाही. प्रत्येक नवीन कॉल नोंदवला जाताना किंमती नोंदवल्या जातात;
जुन्या नोंदींच्या किंमती पुन्हा मोजल्या जात नाहीत. त्यामुळे सदस्यता खात्यांसाठी
API-समतुल्य अंदाज उपलब्ध असू शकतो, पण तितकी रक्कम प्रत्यक्ष खर्च म्हणून किंवा सदस्यता
कोट्यातून वजा होईलच असे नाही. विद्यमान कोटा, बजेट आणि प्रदात्याच्या अचूक खर्चाच्या गणना बदललेल्या नाहीत.

हे निदान विद्यमान मर्यादित कॅश-स्थिती सारांश आणि कॉल-लॉग
जतन व्यवस्थेचा वापर करते. त्यामुळे विनंतीचे डीफॉल्ट TTL, रूटिंग किंवा खाते निवड बदलत नाही.
प्रदात्याकडे पाठवण्याच्या टप्प्यावर क्लायंटने विनंती केलेला TTL आणि प्रत्यक्ष बाहेर पाठवला जाणारा TTL यांची
नोंद करणे पुढे ढकलले आहे; हे पॅनेल पावतीवरील स्तर दाखवते, प्रत्यक्ष बाहेर पाठवला जाणारा TTL नाही.

अंमलबजावणी: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, आणि `open-sse/utils/cacheWriteUsage.ts`.

## खर्चाची गणना

खर्चाची गणना LiteLLM वरून समक्रमित केलेल्या **किंमत डेटावरून** (`src/lib/pricingSync.ts`) केली जाते:

| मॉडेल             | इनपुट $/1M | आउटपुट $/1M | कॅश केलेले $/1M |
| ----------------- | ---------- | ----------- | --------------- |
| gpt-5             | $2.50      | $10.00      | —               |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50           |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30           |
| gemini-2.5-pro    | $1.25      | $10.00      | —               |

खर्चाचे सूत्र (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **प्रॉम्प्टमधून कॅश केलेले टोकन वजा का करायचे?** कॅश केलेल्या भागाची किंमत स्वतंत्रपणे मोजली जाते; संपूर्ण प्रॉम्प्टवर इनपुटची किंमत आकारल्यास खर्च जास्त मोजला जाईल.

### किंमत समक्रमण

`/api/pricing/sync` एंडपॉइंटद्वारे LiteLLM वरून किंमत डेटा स्वयंचलितपणे समक्रमित केला जातो (अंगभूत cron कार्याद्वारे ट्रिगर केला जातो, वापरकर्त्यांसाठी असलेल्या env var द्वारे नाही):

```bash
# स्वहस्ते ट्रिगर करा
curl -X POST http://localhost:20128/api/pricing/sync
```

ज्या मॉडेलसाठी किंमत डेटा उपलब्ध नाही, त्यांच्यासाठी OmniRoute अंतर्गत सरासरी दर वापरून **खर्चाचा अंदाज** लावते (हे दर LiteLLM च्या किंमत डेटावरून घेतलेले असतात).

## दिनांक श्रेणी एकत्रीकरण

`usageAnalytics.ts` मॉड्यूल वापराच्या कच्च्या डेटावरून डॅशबोर्ड विजेट्सची गणना करते. ते 7 कालावधींना समर्थन देते:

| श्रेणी   | कालखंड                                | वापराचे उदाहरण                    |
| -------- | ------------------------------------- | --------------------------------- |
| `1d`     | मागील 24 तास                          | तासागणिक खर्चातील अचानक वाढ शोधणे |
| `7d`     | मागील 7 दिवस                          | साप्ताहिक आढावा                   |
| `30d`    | मागील 30 दिवस                         | मासिक बिलिंग                      |
| `90d`    | मागील 90 दिवस                         | त्रैमासिक विश्लेषण                |
| `ytd`    | चालू वर्षाच्या 1 जानेवारीपासून        | वार्षिक बजेटचा मागोवा             |
| `all`    | संपूर्ण कालावधी                       | एकूण कालावधीची आकडेवारी           |
| `custom` | वापरकर्त्याने ठरवलेली सुरुवात/समाप्ती | लेखापरीक्षणे, तदर्थ क्वेरीज       |

### गणना केली जाणारी डॅशबोर्ड विजेट्स

कोणत्याही दिनांक श्रेणीसाठी, विश्लेषण स्तर पुढील गणना करतो:

| विजेट                      | वर्णन                                                          |
| -------------------------- | -------------------------------------------------------------- |
| **सारांश कार्डे**          | एकूण विनंत्या, एकूण खर्च, एकूण टोकन्स, यशाचे प्रमाण            |
| **दैनंदिन कल आलेख**        | प्रतिदिन खर्च + टोकन्स, मॉडेलनुसार रचलेले                      |
| **सक्रियता हीटमॅप**        | दिवसातील तास × आठवड्यातील दिवस यांची जाळी, रंग = विनंती संख्या |
| **मॉडेलनुसार विभागणी**     | मॉडेलनुसार खर्चाचा वर्तुळ आलेख                                 |
| **प्रदात्यानुसार विभागणी** | प्रदात्यानुसार विनंत्यांचा स्तंभ आलेख                          |
| **अव्वल API कीज**          | खर्चानुसार अव्वल 10 कीजचा तक्ता                                |
| **त्रुटी विश्लेषण**        | कालानुसार त्रुटींचे प्रमाण, प्रमुख त्रुटी वर्ग                 |

### प्रोग्रामद्वारे प्रवेश

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // वापराच्या इतिहासातील नोंदी
  "7d",                 // कालावधी: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // प्रदाता कनेक्शन नकाशा (connectionId → खात्याचे नाव)
  {
    startDate: "2025-01-01",  // ऐच्छिक: "custom" श्रेणीसाठी
    endDate: "2025-06-01",   // ऐच्छिक: "custom" श्रेणीसाठी
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (सेंट)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## कोट्याची अंमलबजावणी

प्रत्येक API कीसाठी कोट्याची अंमलबजावणी दोन ठिकाणी केली जाते:

1. **सौम्य मर्यादा** (`quotaWarnAt`): वापराने उंबरठा ओलांडल्यावर डॅशबोर्डवर चेतावणी
2. **कठोर मर्यादा** (`quotaLimit`): मर्यादा ओलांडल्यावर HTTP 429 सह विनंती नाकारली जाते

### कॉन्फिगरेशन

```ts
// प्रत्येक API कीसाठी
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — चेतावणी दाखवा
  quotaLimit: 10_00,    // $10.00 — पूर्णपणे थांबवा
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### अंमलबजावणीचा प्रवाह

```
विनंती ──▶ quotaCheck()
              │
              ├── मर्यादेत आहे?  ──▶ परवानगी द्या
              │
              └── मर्यादा ओलांडली?  ──▶ 429 खूप जास्त विनंत्या
                                   Retry-After हेडरसह
```

### कोट्याचे स्नॅपशॉट्स

`quotaSnapshots` तक्ता कल विश्लेषणासाठी **कोट्याची ऐतिहासिक स्थिती** साठवतो:

| फील्ड | वर्णन |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | मागोवा घेतली जाणारी की |
| `window` | "day" | "week" | "month" |
| `used` | या कालखंडात वापरलेला खर्च (सेंट) |
| `limit` | मर्यादा (सेंट) |
| `resetAt` | कालखंड कधी रीसेट होतो |
| `createdAt` | स्नॅपशॉट कधी घेतला गेला |

ज्या विनंतीचा खर्च > 0 असतो अशा **प्रत्येक विनंतीवेळी** स्नॅपशॉट्स घेतले जातात आणि त्यांचा वापर पुढील गोष्टींसाठी केला जातो:

- डॅशबोर्डवर कोट्याची प्रगती पट्टी प्रदर्शित करणे
- 30 दिवसांचे कोटा कल आलेख दाखवणे
- वापर मर्यादेच्या जवळ पोहोचल्यावर सूचना सक्रिय करणे

## डेटा जतन आणि साफसफाई

प्रत्येक विनंतीमागे वापराचा डेटा ~1-10KB ने वाढतो. मोठ्या प्रमाणावर ही वाढ लक्षणीय ठरू शकते.

### डेटा जतन करण्याच्या सेटिंग्ज

वापराचा इतिहास जतन करण्याचा कालावधी UI मधील डेटाबेस सेटिंग्जद्वारे किंवा `/api/settings/database` द्वारे कॉन्फिगर केला जातो.

डीफॉल्टनुसार, वापराचा इतिहास **90 दिवस** जतन केला जातो.

### साफसफाई

जुन्या नोंदींची साफसफाई `src/lib/db/cleanup.ts` द्वारे केली जाते:

- पार्श्वभूमीतील cron प्रक्रियेद्वारे सुरू केली जाते
- कॉन्फिगर केलेल्या `usageHistory` जतन कालावधीपेक्षा जुन्या नोंदी `usage_history` मधून हटवते

### स्टोरेजचा अंदाज

| विनंत्यांचा दर        | 30 दिवसांचे स्टोरेज | 90 दिवसांचे स्टोरेज |
| --------------------- | ------------------- | ------------------- |
| 100 विनंत्या/दिवस     | ~3MB                | ~9MB                |
| 1,000 विनंत्या/दिवस   | ~30MB               | ~90MB               |
| 10,000 विनंत्या/दिवस  | ~300MB              | ~900MB              |
| 100,000 विनंत्या/दिवस | ~3GB                | ~9GB                |

अतिशय जास्त ट्रॅफिक असल्यास, पुढील पर्यायांचा विचार करा:

- डेटाबेस सेटिंग्जद्वारे डेटा जतन करण्याचा कालावधी कमी करणे
- मूळ नोंदींऐवजी `aggregated_metrics` वापरणे (केवळ विश्लेषणासाठी)

// कॅशिंग स्वयंचलित आहे — फक्त तोच मोठा सिस्टम प्रॉम्प्ट समाविष्ट करा
const response = await openai.chat({

RTK + Caveman कॉम्प्रेशनमुळे **साधनांचा मोठ्या प्रमाणात वापर असलेल्या सत्रांमध्ये 15-95% बचत होते**:

const config = {

## समस्यांचे निराकरण

### "खर्च अपेक्षेपेक्षा जास्त आहे"

1. **`/api/usage/analytics?groupBy=model`** तपासा — महागडे मॉडेल शोधा
2. **`/api/usage/analytics?groupBy=apiKey`** तपासा — जास्त वापर करणारा शोधा
3. किंमतींचा डेटा अद्ययावत असल्याची खात्री करा: `POST /api/pricing/sync`

### "नोंदी आढळत नाहीत"

- डॅशबोर्ड → डेटाबेस → साफसफाई अंतर्गत DB मधील नोंदी जतन करण्याची सेटिंग्ज तपासा — नियतकालिक साफसफाईच्या कार्याद्वारे जुन्या नोंदी हटवल्या जातात (`src/lib/db/cleanup.ts`)
- `src/lib/db/usage*.ts` मधील त्रुटी तपासा — DB मध्ये लिहिताना आलेल्या अपयशांची लॉगमध्ये नोंद होते, पण ती उघडपणे दर्शवली जात नाहीत
- विनंती प्रत्यक्षात `chatCore` पर्यंत पोहोचल्याची खात्री करा — कॉम्बो राउटिंग तपासा

### "कोटा लागू होत नाही"

- कीची `quotaLimit` सेटिंग तपासा
- `quotaWindow` योग्यरीत्या सेट केले असल्याची खात्री करा
- `quotaSnapshots` नोंदी शोधा — प्रत्येक विनंतीवर त्या तयार झाल्या पाहिजेत
