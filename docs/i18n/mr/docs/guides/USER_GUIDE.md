## 🎯 वापराची प्रकरणे

### प्रकरण 1: "माझ्याकडे Claude Pro सदस्यत्व आहे"

**समस्या:** न वापरलेला कोटा कालबाह्य होतो आणि मोठ्या प्रमाणावर कोडिंग करताना दरमर्यादा लागू होतात

```
कॉम्बो: "maximize-claude"
  1. cc/claude-opus-4-7        (सदस्यत्वाचा पूर्ण वापर करा)
  2. glm/glm-4.7               (कोटा संपल्यावर स्वस्त बॅकअप)
  3. if/qwen3.8-max-preview       (आपत्कालीन मोफत पर्याय)

मासिक खर्च: $20 (सदस्यत्व) + ~$5 (बॅकअप) = एकूण $25
याउलट $20 + मर्यादा गाठणे = निराशा
```

### प्रकरण 2: "मला शून्य खर्च हवा आहे"

**समस्या:** सदस्यत्वे परवडत नाहीत, विश्वासार्ह AI कोडिंग आवश्यक आहे

```
कॉम्बो: "zero-cost"
  1. if/kimi-k2.7-code          (सूचीबद्ध मोफत प्रवेश; दरमर्यादा लागू होऊ शकतात)
  2. kr/qwen3-coder-next        (Kiro चा मोफत पर्याय)

मासिक खर्च: $0
गुणवत्ता: तुमच्या कार्यभारासाठी मॉडेल, मर्यादा, गोपनीयता आणि SLA पडताळा
```

### प्रकरण 3: "मला कोणत्याही व्यत्ययाशिवाय 24/7 कोडिंग हवे आहे"

**समस्या:** अंतिम मुदती आहेत, सेवा खंडित होणे परवडणारे नाही

```
कॉम्बो: "always-on"
  1. cc/claude-opus-4-7        (सर्वोत्तम गुणवत्ता)
  2. cx/gpt-5.5                (दुसरे सदस्यत्व)
  3. glm/glm-4.7               (स्वस्त, दररोज रीसेट होते)
  4. minimax/MiniMax-M2.1      (सर्वांत स्वस्त, 5 तासांनी रीसेट)
  5. if/deepseek-v4-flash       (सूचीबद्ध मोफत प्रवेश; दरमर्यादा लागू होऊ शकतात)

परिणाम: पर्यायांचे 5 स्तर लवचिकता वाढवतात; अपस्ट्रीम उपलब्धतेची हमी नाही
मासिक खर्च: $20-200 (सदस्यत्वे) + $10-20 (बॅकअप)
```

## 📖 प्रदाता सेटअप

CSV किंवा JSON फाइलमधून मोठ्या प्रमाणात API-की कनेक्शन्स जोडण्यासाठी, **डॅशबोर्ड → प्रदाते → फाइलमधून आयात करा** वापरा. स्तंभांचे स्थान निश्चित आहे (`provider,name,apiKey,baseUrl,priority`); `provider` हा आधीपासून व्यवस्थापित प्रदाता किंवा सुसंगत नोड म्हणून अस्तित्वात असणे आवश्यक आहे. [CSV किंवा JSON फाइलमधून प्रदाते आयात करा](../providers/CSV-IMPORT.md) पहा.

### 🔐 सदस्यता प्रदाते

#### Claude Code (Pro/Max)

```bash
डॅशबोर्ड → प्रदाते → Claude Code कनेक्ट करा
→ OAuth लॉगिन → स्वयंचलित टोकन रिफ्रेश
→ 5-तासांची + साप्ताहिक कोटा ट्रॅकिंग

मॉडेल्स:
  cc/claude-opus-4-7
  cc/claude-sonnet-4-6
  cc/claude-haiku-4-5-20251001
```

**उपयुक्त सूचना:** जटिल कार्यांसाठी Opus आणि वेगासाठी Sonnet वापरा. OmniRoute प्रत्येक मॉडेलनुसार कोटा ट्रॅक करते!

OmniRoute होस्टवर ब्राउझर नाही? Claude Code मध्ये लॉगिन केलेल्या कोणत्याही ठिकाणी `claude setup-token` चालवा आणि एक वर्षासाठी वैध असलेले टोकन **Setup Token** टॅबमध्ये पेस्ट करा. [सेटअप टोकनसह Claude Code](../providers/CLAUDE_CODE_SETUP_TOKEN.md) पहा.

Claude आणि Claude Code-सुसंगत रूट्स Opus आणि Sonnet मॉडेल्ससाठी `max` विचार-प्रयत्न पातळी कायम ठेवतात. Haiku मॉडेल्स `max` प्रयत्न स्तर स्वीकारत नाहीत, त्यामुळे विनंती अपस्ट्रीमकडे पाठवण्यापूर्वी OmniRoute ती उच्च विचार-बजेटवर डाउनग्रेड करते.

#### OpenAI Codex (Plus/Pro)

```bash
डॅशबोर्ड → प्रदाते → Codex कनेक्ट करा
→ OAuth लॉगिन (पोर्ट 1455)
→ 5-तासांची + साप्ताहिक रीसेट

मॉडेल्स:
  cx/gpt-5.5
  cx/gpt-5.4
  cx/gpt-5.3-codex
  cx/gpt-5.3-codex-spark
```

### ग्लोबल npm इन्स्टॉल (शिफारस केलेले)

```bash
npm install -g omniroute

# कॉन्फिगरेशन डिरेक्टरी तयार करा
mkdir -p ~/.omniroute

# .env फाइल तयार करा (.env.example पहा)
cp .env.example ~/.omniroute/.env

# सर्व्हर सुरू करा
omniroute
# किंवा सानुकूल पोर्टसह:
omniroute --port 3000
```

CLI आपोआप `~/.omniroute/.env` किंवा `./.env` मधून `.env` लोड करते.

### ट्रे मोड

सिस्टम ट्रेमध्ये OmniRoute सुरू करा:

```bash
omniroute serve --tray
```

सर्व्हर आणि ट्रे तयार झाल्यानंतर कमांड पूर्ण होते.

टर्मिनलशिवाय सर्व्हर चालू राहतो.

ट्रे मोड macOS, Windows आणि ग्राफिकल Linux सत्रांना समर्थन देतो. ट्रे मोड डॅशबोर्ड आपोआप उघडत नाही.

पुढील क्रियांसाठी ट्रे मेनू वापरा:

- डॅशबोर्ड उघडा.
- `/dashboard/logs` उघडा.
- स्वयंचलित प्रारंभ बदला.
- OmniRoute थांबवा.

पुढील पर्यायांसोबत `--tray` वापरू नका:

- `--daemon`
- `--log`
- `--no-recovery`

या मोड्सना वेगवेगळ्या प्रक्रिया मालकीची आवश्यकता असते.

मशीनमध्ये पुढील वेळी लॉग इन करताना स्टार्टअप सक्षम करा:

```bash
omniroute autostart enable
```

macOS, Windows आणि ग्राफिकल Linux सत्रांवर स्वयंचलित प्रारंभ ट्रे मोड वापरतो. हेडलेस Linux विद्यमान systemd वापरकर्ता सेवा वापरतो.

लॉगिनवेळी स्टार्टअप अक्षम करा:

```bash
omniroute autostart disable
```

### अनइन्स्टॉल करणे

जेव्हा तुम्हाला OmniRoute ची गरज नसेल, तेव्हा पूर्णपणे काढून टाकण्यासाठी आम्ही दोन जलद स्क्रिप्ट्स पुरवतो:

| कमांड                    | कृती                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| `npm run uninstall`      | सिस्टम अॅप काढून टाकते, परंतु `~/.omniroute` मधील **तुमचा DB आणि कॉन्फिगरेशन्स जतन करते**. |
| `npm run uninstall:full` | अॅप काढून टाकते आणि **सर्व कॉन्फिगरेशन्स, की आणि डेटाबेसेस कायमचे पुसते**.                 |

> टीप: या कमांड्स चालवण्यासाठी, OmniRoute प्रकल्प फोल्डरमध्ये जा (जर तुम्ही तो क्लोन केला असेल) आणि त्या चालवा. पर्यायाने, ग्लोबलरीत्या इन्स्टॉल केले असल्यास, तुम्ही फक्त `npm uninstall -g omniroute` चालवू शकता.

```bash

version=3.8.0
revision=1
hostmakedepends="nodejs python3 make"
depends="openssl"
short_desc="Universal AI gateway with smart routing for multiple LLM providers"
maintainer="zenobit <zenobit@disroot.org>"
license="MIT"
homepage="https://github.com/diegosouzapw/OmniRoute"
distfiles="https://github.com/diegosouzapw/OmniRoute/archive/refs/tags/v${version}.tar.gz"

system_accounts="_omniroute"
omniroute_homedir="/var/lib/omniroute"
export NODE_ENV=production
export npm_config_engine_strict=false
export npm_config_loglevel=error
export npm_config_fund=false

do_build() {
	# node-gyp साठी लक्ष्य CPU आर्किटेक्चर निश्चित करा
	local _gyp_arch
	case "$XBPS_TARGET_MACHINE" in
		aarch64*) _gyp_arch=arm64 ;;
		armv7*|armv6*) _gyp_arch=arm ;;
		i686*) _gyp_arch=ia32 ;;
		*) _gyp_arch=x64 ;;
	esac

	# 1) सर्व अवलंबित्वे स्थापित करा – स्क्रिप्ट्स वगळा
	NODE_ENV=development npm ci --ignore-scripts

	# 2) Next.js स्टँडअलोन बंडल बिल्ड करा
	npm run build

	# 3) स्टॅटिक असेट्स स्टँडअलोनमध्ये कॉपी करा
	cp -r .next/static .next/standalone/.next/static
	[ -d public ] && cp -r public .next/standalone/public || true

	# 4) better-sqlite3 नेटिव्ह बाइंडिंग कंपाइल करा
	local _node_gyp=/usr/lib/node_modules/npm/node_modules/node-gyp/bin/node-gyp.js

	# 5) कंपाइल केलेले बाइंडिंग स्टँडअलोन बंडलमध्ये ठेवा
	local _bs3_release=.next/standalone/node_modules/better-sqlite3/build/Release
	mkdir -p "$_bs3_release"
	cp node_modules/better-sqlite3/build/Release/better_sqlite3.node "$_bs3_release/"

	# 6) आर्किटेक्चर-विशिष्ट sharp बंडल्स काढून टाका
	rm -rf .next/standalone/node_modules/@img

	# 7) Next.js स्टॅटिक विश्लेषणातून वगळलेली pino रनटाइम अवलंबित्वे कॉपी करा:
	for _mod in pino-abstract-transport split2 process-warning; do
		cp -r "node_modules/$_mod" .next/standalone/node_modules/
	done
}

do_check() {
	npm run test:unit
}

do_install() {
	vmkdir usr/lib/omniroute/.next
	vcopy .next/standalone/. usr/lib/omniroute/.next/standalone

	# पोस्ट-इन्स्टॉल हुकद्वारे रिकाम्या Next.js अॅप राउटर डिरेक्टरीज काढल्या जाण्यापासून प्रतिबंधित करा
	for _d in \
		.next/standalone/.next/server/app/dashboard \
		.next/standalone/.next/server/app/dashboard/settings \
		.next/standalone/.next/server/app/dashboard/providers; do
		touch "${DESTDIR}/usr/lib/omniroute/${_d}/.keep"
	done

#!/bin/sh
export PORT="${PORT:-20128}"
export DATA_DIR="${DATA_DIR:-${XDG_DATA_HOME:-${HOME}/.local/share}/omniroute}"

	vbin "${WRKDIR}/omniroute"
}

post_install() {
```

## 🧩 प्रगत वैशिष्ट्ये

### कस्टम मॉडेल्स

अॅप अपडेटची वाट न पाहता कोणत्याही प्रोव्हायडरमध्ये कोणतेही मॉडेल ID जोडा:

```bash
# API द्वारे
curl -X POST http://localhost:20128/api/provider-models \
  -H "Content-Type: application/json" \
  -d '{"provider": "openai", "modelId": "gpt-5.2", "modelName": "GPT-5.2"}'

# सूची: curl http://localhost:20128/api/provider-models?provider=openai
# काढा: curl -X DELETE "http://localhost:20128/api/provider-models?provider=openai&model=gpt-5.2"
```

किंवा डॅशबोर्ड वापरा: **प्रोव्हायडर्स → [प्रोव्हायडर] → कस्टम मॉडेल्स**.

टीपा:

- OpenRouter आणि OpenAI/Anthropic-सुसंगत प्रोव्हायडर्स केवळ **उपलब्ध मॉडेल्स** मधून व्यवस्थापित केले जातात. मॅन्युअल ॲड, इम्पोर्ट आणि ऑटो-सिंक हे सर्व एकाच उपलब्ध-मॉडेल सूचीत जतन होतात, म्हणून त्या प्रोव्हायडर्ससाठी स्वतंत्र कस्टम मॉडेल्स विभाग नसतो.
- **कस्टम मॉडेल्स** विभाग जे प्रोव्हायडर व्यवस्थापित उपलब्ध-मॉडेल इम्पोर्ट्स उपलब्ध करून देत नाहीत त्यांच्यासाठी आहे.

### कस्टम OpenAI-सुसंगत प्रोव्हायडर्स

OpenAI API बोलणारे कोणतेही गेटवे (सेल्फ-होस्टेड प्रॉक्सी, vLLM, किंवा तृतीय-पक्ष अग्रिगेटर)
स्वतःचा स्वतंत्र प्रोव्हायडर नोड म्हणून जोडले जाऊ शकते:

1. **प्रोव्हायडर्स → OpenAI सुसंगत जोडा**.
2. **नाव**: नोडसाठी दाखवायचे लेबल.
3. **प्रीफिक्स**: राउटिंग नाव. क्लायंट्स `<prefix>/<model>` या स्वरूपात मॉडेल्स कॉल करतात, म्हणून
   `mygw` प्रीफिक्स असलेला नोड `mygw/gpt-4o-mini` पुरवतो. आवश्यक; वर्णांचे कोणतेही निर्बंध नाहीत.
4. **API प्रकार**: गेटवे जे एंडपॉइंट कुटुंब पुरवतो (Chat Completions, Responses,
   Embeddings, ऑडिओ, इमेजेस).
5. **बेस URL**: `/v1` पर्यंतचा (तो समाविष्ट करून) API रूट (उदाहरणार्थ
   `https://gateway.example.com/v1`), संपूर्ण `/chat/completions` पाथ नव्हे. नॉन-स्टँडर्ड
   पाथ्स असलेले गेटवे ते **प्रगत सेटिंग्ज** खाली सेट करतात (chat path, models path).
6. **API की (तपासणीसाठी)** हे फील्ड फक्त कनेक्शन तपासते. नोड तयार केल्यानंतर,
   तो उघडा आणि विनंत्या वापरतील ती की साठवण्यासाठी **कनेक्शन जोडा** वापरा.

नोडला `openai-compatible-<apiType>-<uuid>` या स्वरूपाचा अंतर्गत id मिळतो; तुम्हाला तो कधीही
टाइप करण्याची गरज नाही, प्रीफिक्स हेच सार्वजनिक नाव आहे.

#### राखीव प्रीफिक्सेस

प्रीफिक्स हा बिल्ट-इन प्रोव्हायडरचा id किंवा उपनाम (उदाहरणार्थ `openai`, `cf`) असू शकत नाही,
किंवा निवृत्त (retired) प्रोव्हायडरचा idही असू शकत नाही. मॉडेल रिझॉल्व्हर कस्टम नोड्सपूर्वी
बिल्ट-इन ids आणि उपनामे तपासतो, म्हणून त्या प्रीफिक्सपैकी एक वापरणाऱ्या नोडकडे कधीही ट्रॅफिक
जाणार नाही: `<prefix>/model` ही विनंती बिल्ट-इन प्रोव्हायडरकडे जाईल, किंवा तो प्रोव्हायडर
निवृत्त झाला असल्यास fail closed होईल. अशा प्रीफिक्ससह नोड तयार करणे किंवा संपादित करणे
खालीलप्रमाणे नाकारले जाते:

```text
prefix: "<prefix>" is a reserved provider prefix — choose a different prefix (reserved ids/aliases cannot be used for custom nodes because requests like <prefix>/model route to a built-in provider or fail closed when retired)
```

वेगळा प्रीफिक्स निवडा (`mygw`, `acme-proxy`). कस्टम नोडवरील विनंत्या बिल्ट-इन प्रोव्हायडर
किंवा त्याच्या क्रेडेन्शियल्सचे नाव घेणाऱ्या एररसह अयशस्वी झाल्यास, नोडचा प्रीफिक्स राखीव
आहे का ते तपासा: हा नियम अस्तित्वात येण्यापूर्वी सेव्ह केलेले नोड्स अजूनही साठवलेले आहेत, पण
त्यांचा प्रीफिक्स बिल्ट-इन प्रोव्हायडरकडे रूट होतो. नोड संपादित करा आणि त्याला नवीन प्रीफिक्स द्या.

#### प्रति-कनेक्शन गेटवे पर्याय

हे keys कनेक्शनच्या `providerSpecificData` मध्ये जातात (उदाहरणार्थ
`PUT /api/providers/{id}` द्वारे):

- `toolNameMaxLength` (पूर्णांक, 1–1024) — ज्या OpenAI chat-फॉरमॅट सुसंगत कनेक्शन्सचे
  गेटवे लांब टूल नावे नाकारते त्यांच्यासाठी. लांब नावे छोट्या उपनामांनी पाठवली जातात आणि
  प्रत्युत्तरात पुन्हा मूळ स्वरूपात आणली जातात.
- `quotaEndpoint` — गेटवेचा quota/credits एंडपॉइंट, डॅशबोर्ड कोटा स्ट्रिप आणि
  कोटा-आधारित राउटिंगसाठी वाचला जातो. OpenAI- आणि Anthropic-सुसंगत दोन्ही कनेक्शन्सवर कार्य
  करते; संपूर्ण आकार `open-sse/services/usage/openaiCompatible.ts` मध्ये दस्तऐवजीकरण केला आहे.

```json

  "toolNameMaxLength": 64,
  "quotaEndpoint": {
    "url": "https://gateway.example.com/key/info",
    "auth": "bearer",
    "quotas": {
      "budget": { "used": "$.info.spend", "total": "$.info.max_budget", "currency": "USD" }
```

### OmniRoute पियर्स चेन करणे

दुसरे OmniRoute गेटवे **कस्टम OpenAI-सुसंगत** प्रोव्हायडर म्हणून जोडले जाऊ शकते. पियरचा
`/v1` बेस URL आणि त्या पियरने जारी केलेली समर्पित, किमान-परवानगी (least-privilege) API की वापरा.

पारस्परिक किंवा मल्टी-हॉप चेनसाठी, प्रत्येक गेटवेवर ऑप्ट-इन लूप गार्ड सक्षम करा:

```bash
# gateway-a
OMNIROUTE_INSTANCE_ID=gateway-a
OMNIROUTE_PEER_URLS=http://gateway-b:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

```bash
# gateway-b
OMNIROUTE_INSTANCE_ID=gateway-b
OMNIROUTE_PEER_URLS=http://gateway-a:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

स्पष्टपणे allowlist केलेल्या पियर URL वर पाठवलेल्या विनंत्यानाच
`X-OmniRoute-Peer-Trace` हेडर मिळतो. गेटवे पुनरावृत्त झालेला instance ID किंवा संपलेले hop
budget HTTP `508 Loop Detected` सह नाकारतो; सामान्य अपस्ट्रीम प्रोव्हायडर्सना कोणतेही पियर
मेटाडेटा मिळत नाही.

पियर चेनिंग म्हणजे डेटाबेस रेप्लिकेशन किंवा होस्ट फेलओव्हर नव्हे. प्रत्येक गेटवे स्वतंत्र
SQLite स्टेट, कॅशे, रेट काउंटर्स आणि सेशन्स ठेवतो. active/passive किंवा active/active
उपलब्धतेसाठी हेल्थ-चेक केलेले रिव्हर्स प्रॉक्सी किंवा क्लायंट फेलओव्हर वापरा, आणि एकाच SQLite
डेटाबेस अनेक चालू OmniRoute इन्स्टन्सेसमध्ये कधीही माउंट करू नका.

### Cloudflare Quick Tunnel

- Docker आणि इतर सेल्फ-होस्टेड डिप्लॉयमेंटसाठी **Dashboard → Endpoints** मध्ये उपलब्ध
- तुमच्या विद्यमान OpenAI-सुसंगत `/v1` एंडपॉइंटकडे फॉरवर्ड करणारी तात्पुरती `https://*.trycloudflare.com` URL तयार करते
- पहिल्यांदा सक्षम केल्यावर `cloudflared` फक्त गरज असताच इन्स्टॉल होते; नंतरच्या रीस्टार्टमध्ये तेच मॅनेज्ड बायनरी पुन्हा वापरले जाते
- OmniRoute किंवा कंटेनर रीस्टार्टनंतर Quick Tunnels आपोआप पुनर्संचयित होत नाहीत; गरजेनुसार डॅशबोर्डवरून ते पुन्हा सक्षम करा
- Tunnel URL अल्पावधी असतात आणि तुम्ही tunnel थांबवा/सुरू करा त्यावेळी प्रत्येक वेळी बदलतात
- मर्यादित कंटेनरमधील QUIC UDP बफर वॉर्निंग्ज टाळण्यासाठी Managed Quick Tunnels डीफॉल्टनुसार HTTP/2 ट्रान्सपोर्ट वापरतात
- मॅनेज्ड ट्रान्सपोर्ट निवड ओव्हरराइड करायची असल्यास `CLOUDFLARED_PROTOCOL=quic` किंवा `auto` सेट करा
- मॅनेज्ड डाउनलोडऐवजी आधीच इन्स्टॉल केलेले `cloudflared` बायनरी वापरायचे असल्यास `CLOUDFLARED_BIN` सेट करा
- Cloudflare Quick Tunnel, Tailscale Funnel आणि ngrok Tunnel पॅनेल **Settings → Appearance** मध्ये दाखवता किंवा लपवता येतात. पॅनेल लपवल्याने चालू tunnel थांबत नाही.

### LLM Gateway Intelligence (Phase 9)

- **Semantic Cache** — नॉन-स्ट्रीमिंग, temperature=0 रिस्पॉन्सेस आपोआप कॅशे करते (`X-OmniRoute-No-Cache: true` ने बायपास करा)
- **Request Idempotency** — `Idempotency-Key` किंवा `X-Request-Id` हेडरद्वारे 5 सेकंदांच्या आत डुप्लिकेट विनंत्या अळवते
- **Progress Tracking** — `X-OmniRoute-Progress: true` हेडरद्वारे ऑप्ट-इन SSE `event: progress` इव्हेंट्स

### राउटिंग धोरणे

**Dashboard → Settings → Routing** मधून कॉन्फिगर करा. डॅशबोर्डवर सर्वाधिक वापरली जाणारी सहा धोरणे दिसतात; कॉम्बो आणि ऑटो-राउटर अंतर्गतपणे अधिक विस्तृत संच समर्थन करतात.

**डॅशबोर्डवर दिसणारी धोरणे (अकाउंट-स्तरीय राउटिंग):**

| धोरण                           | वर्णन                                                                                                            |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| **Fill First**                 | अकाउंट्स प्राधान्य क्रमाने वापरते — प्राथमिक अकाउंट अनुपलब्ध होईपर्यंत सर्व विनंत्या हाताळते                     |
| **Round Robin**                | कॉन्फिगर करण्यायोग्य स्टिकी लिमिटसह (डीफॉल्ट: प्रत्येक अकाउंटसाठी 3 कॉल्स) सर्व अकाउंट्समधून फिरते               |
| **P2C (Power of Two Choices)** | 2 यादृच्छिक अकाउंट्स निवडते आणि अधिक निरोगी अकाउंटकडे राउट करते — आरोग्य जाणीवसह लोड संतुलित करते                |
| **Random**                     | Fisher-Yates shuffle वापरून प्रत्येक विनंतीसाठी यादृच्छिकपणे अकाउंट निवडते                                       |
| **Least Used**                 | सर्वात जुनी `lastUsedAt` टाइमस्टॅम्प असलेल्या अकाउंटकडे राउट करते, ट्रॅफिक समान वाटते                            |
| **Cost Optimized**             | सर्वात कमी प्रायोरिटी व्हॅल्यू असलेल्या अकाउंटकडे राउट करते, सर्वात कमी खर्चाच्या प्रोव्हायडरसाठी ऑप्टिमाइझ करते |

**प्रगत कॉम्बो आणि ऑटो धोरणे** (प्रत्येक कॉम्बोनुसार किंवा `auto/*` प्रीफिक्सद्वारे कॉन्फिगर करण्यायोग्य — [AUTO-COMBO.md](../routing/AUTO-COMBO.md) पाहा):

- `priority` — कठोर क्रम, कधीही राउंड-रॉबिन करत नाही
- `weighted` — प्रत्येक मॉडेलच्या वेट्सनुसार प्रमाणित ट्रॅफिक वाटप
- `fill-first` — लिमिट येईपर्यंत पहिले मॉडेल वापरणे
- `round-robin` / `strict-random` / `random`
- `p2c` (Power of Two Choices)
- `least-used` आणि `cost-optimized`
- `auto` — सर्व उमेदवारांमध्ये स्कोअर-आधारित निवड
- `lkgp` (Last Known Good Provider) — शेवटच्या यशस्वी प्रोव्हायडरला पिन करते, नंतर नियमांकडे फॉलबॅक करते
- `context-optimized` — सर्वात मोठी मोकळी context window असलेले मॉडेल निवडते
- `context-relay` — पुढील टर्नसाठी लांब-context मॉडेल्स चेन करते

#### External Sticky Session Header

बाह्य सेशन affinity साठी (उदाहरणार्थ, reverse proxies मागील Claude Code/Codex एजंट्स), पाठवा:

```http
X-Session-Id: your-session-key
```

OmniRoute `x_session_id` देखील स्वीकारते आणि प्रभावी सेशन की `X-OmniRoute-Session-Id` मध्ये परत देते.

तुम्ही Nginx वापरत असाल आणि अंडरस्कोअर-फॉर्म हेडर्स पाठवत असाल, तर हे सक्षम करा:

```nginx
underscores_in_headers on;
```

#### Wildcard Model Aliases

मॉडेल नावे रीमॅप करण्यासाठी wildcard पॅटर्न तयार करा:

```
Pattern: claude-sonnet-*     →  Target: cc/claude-sonnet-4-6
Pattern: gpt-*               →  Target: gh/gpt-5.3-codex
```

Wildcards `*` (कोणतेही अक्षरे) आणि `?` (एकल अक्षर) समर्थन करतात.

#### Fallback Chains

सर्व विनंत्यांवर लागू होणाऱ्या ग्लोबल fallback चेन परिभाषित करा:

```
Chain: production-fallback
  1. cc/claude-opus-4-7
  2. gh/gpt-5.3-codex
  3. glm/glm-4.7
```

### सामान्य प्रोव्हायडर कॉम्बिनेशन्स आणि राउटिंग पॅटर्न

OmniRoute मध्ये अनेक प्रोव्हायडर एकत्र करण्याच्या आणि त्यांच्यामध्ये राउटिंग करण्याच्या उदाहरण पॅटर्न येथे आहेत:

#### १. कोडिंग एजंट कॉम्बो: कॉस्ट/स्पीड फॉलबॅकसह हाय-एंड रीजनिंग

कोडिंग एजंट्ससाठी (OpenCode, Claude Code, Cursor, Cline) आदर्श. सुरुवातीला फ्रंटियर रीजनिंग मॉडेल्सकडे रूट करते, कोटा संपल्यावर किंवा एरर आल्यावर फास्ट कोडिंग मॉडेल्सकडे फॉलबॅक करते.

- **डॅशबोर्ड**: Combos → New Combo → नाव: `agent-coding` → स्ट्रॅटेजी: `Priority`
- **मॉडेल्स**:
  1. `claude/claude-sonnet-4-6` (प्राथमिक कोडिंग एजंट)
  2. `openai/gpt-4o` (दुय्यम उच्च-क्षमता फॉलबॅक)
  3. `deepseek/deepseek-v4-flash` (उच्च-कार्यक्षमता, किफायतशीर फॉलबॅक)

```bash
# API द्वारे उदाहरण
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "agent-coding",
    "strategy": "priority",
    "models": [
      { "model": "claude/claude-sonnet-4-6" },
      { "model": "openai/gpt-4o" },
      { "model": "deepseek/deepseek-v4-flash" }
    ]
  }'
```

#### २. फ्री-टियर ऑटो फेलओव्हर कॉम्बो

API खर्चाशिवाय अपटाइम वाढवण्यासाठी अनेक फ्री-टियर आणि कीलेस प्रोव्हायडर्सना जोडते.

### रेझिलियन्स आणि सर्किट ब्रेकर्स

**Dashboard → Settings → Resilience** मधून कॉन्फिगर करा.

OmniRoute पाच घटकांसह प्रोव्हायडर-स्तरीय रेझिलियन्स लागू करते:

1. **रिक्वेस्ट क्यू आणि पेसिंग** — सिस्टम-स्तरीय रिक्वेस्ट शेपिंग:
   - **Requests Per Minute (RPM)** — प्रत्येक अकाउंटसाठी प्रति मिनिट कमाल रिक्वेस्ट्स
   - **Min Time Between Requests** — रिक्वेस्ट्समधील मिलिसेकंदांमधील किमान अंतर
   - **Max Concurrent Requests** — प्रत्येक अकाउंटसाठी कमाल एकाच वेळी चालणाऱ्या रिक्वेस्ट्स

2. **कनेक्शन कूलडाउन** — रिट्राय करण्यायोग्य अपयशांनंतर एकल कनेक्शनसाठी प्रति-ऑथ-प्रकार कॉन्फिगरेशन:
   - **Base Cooldown** — रिट्राय करण्यायोग्य अपस्ट्रीम अपयशांसाठी डीफॉल्ट कूलडाउन विंडो
   - **Use Upstream Retry Hints** — दिल्यावर अधिकृत `Retry-After` किंवा रीसेट हिंट्स मान्य करते
   - **Max Backoff Steps** — वारंवार अपयशांसाठी कमाल एक्स्पोनेंशियल बॅकऑफ पातळी

3. **प्रोव्हायडर सर्किट ब्रेकर** — एंड-टू-एंड प्रोव्हायडर अपयशांचा मागोवा घेते, कॉन्फिगर केलेल्या वॉर्निंग थ्रेशोल्डवर प्रोव्हायडरला डिग्रेडेड म्हणून चिन्हांकित करते आणि कॉन्फिगर केलेली अपयश थ्रेशोल्ड पूर्ण झाल्यावर ब्रेकर उघडते:
   - **Degradation Threshold** — `DEGRADED` मध्ये जाण्यापूर्वी सलग प्रोव्हायडर अपयशे
   - **Failure Threshold** — `OPEN` मध्ये जाण्यापूर्वी सलग प्रोव्हायडर अपयशे
   - **Reset Timeout** — प्रोव्हायडर पुन्हा तपासण्यापूर्वीची वेळ विंडो
   - **CLOSED** (निरोगी) — रिक्वेस्ट्स सहजपणे वाहतात
   - **DEGRADED** — वाढलेली अपयशे ट्रॅक केली जात असतानाही रिक्वेस्ट्स वाहत राहतात
   - **OPEN** — वारंवार अपयशांनंतर प्रोव्हायडर तात्पुरता ब्लॉक केला जातो
   - **HALF_OPEN** — प्रोव्हायडर पुनर्प्राप्त झाला आहे का याची चाचणी करत आहे

   कनेक्शन-स्कोप्ड `429` रेट लिमिट्स **Connection Cooldown** मध्येच राहतात आणि प्रोव्हायडर ब्रेकरमध्ये मोजल्या जात नाहीत.

   प्रोव्हायडर ब्रेकरची रनटाइम स्थिती फक्त **Dashboard → Health** वर दाखवली जाते.

4. **Wait For Cooldown** — प्रत्येक उमेदवार कनेक्शन आधीच कूलडाउनमध्ये असल्यास, OmniRoute सर्वात लवकरच्या कूलडाउनची वाट पाहू शकते आणि तीच क्लायंट रिक्वेस्ट आपोआप पुन्हा प्रयत्न करू शकते.

5. **रेट लिमिट ऑटो-डिटेक्शन** — जेव्हा अपस्ट्रीम प्रोव्हायडर्स स्पष्ट प्रतीक्षा विंडो परत करतात, तेव्हा सेटिंग सक्षम असल्यास ते हिंट्स लोकल कनेक्शन कूलडाउनला ओव्हरराइड करतात.

**प्रो टीप:** आउटेजनंतर थेट प्रोव्हायडर ब्रेकर्स तपासण्यासाठी आणि रीसेट करण्यासाठी **Health** पेज वापरा. Resilience पेज फक्त कॉन्फिगरेशन बदलते.

### डेटाबेस एक्सपोर्ट / इम्पोर्ट

**Dashboard → Settings → System & Storage** मध्ये डेटाबेस बॅकअप्स व्यवस्थापित करा.

| क्रिया                   | वर्णन                                                                                                                                                |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Export Database**      | सध्याचा SQLite डेटाबेस `.sqlite` फाइल म्हणून डाउनलोड करते                                                                                            |
| **Export All (.tar.gz)** | पूर्ण बॅकअप आर्काइव्ह डाउनलोड करते ज्यामध्ये समाविष्ट आहे: डेटाबेस, सेटिंग्ज, कॉम्बोज, प्रोव्हायडर कनेक्शन्स (क्रेडेन्शियल्स शिवाय), API की मेटाडेटा |
| **Import Database**      | सध्याचा डेटाबेस बदलण्यासाठी `.sqlite` फाइल अपलोड करा. `DISABLE_SQLITE_AUTO_BACKUP=true` नसल्यास प्री-इम्पोर्ट बॅकअप आपोआप तयार केला जातो             |

```bash
# API: डेटाबेस एक्सपोर्ट करा
curl -o backup.sqlite http://localhost:20128/api/db-backups/export

# API: सर्व एक्सपोर्ट करा (पूर्ण आर्काइव्ह)
curl -o backup.tar.gz http://localhost:20128/api/db-backups/exportAll

# API: डेटाबेस इम्पोर्ट करा
curl -X POST http://localhost:20128/api/db-backups/import \
  -F "file=@backup.sqlite"
```

**इम्पोर्ट व्हॅलिडेशन:** इम्पोर्ट केलेली फाइल इंटेग्रिटीसाठी (SQLite pragma तपासणी), आवश्यक टेबल्ससाठी (`provider_connections`, `provider_nodes`, `combos`, `api_keys`), आणि आकारासाठी (कमाल 100MB) व्हॅलिडेट केली जाते.

**वापर प्रकरणे:**

- OmniRoute ला मशीनदरम्यान स्थानांतरित करणे
- आपत्ती पुनर्प्राप्तीसाठी बाह्य बॅकअप्स तयार करणे
- टीम सदस्यांमध्ये कॉन्फिगरेशन्स शेअर करणे (सर्व एक्सपोर्ट करा → आर्काइव्ह शेअर करा)

| टॅब            | मजकूर                                                                                                                                                          |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| **सुरक्षा**    | लॉगिन/पासवर्ड सेटिंग्ज, IP ऍक्सेस कंट्रोल, `/models` साठी API ऑथ, प्रोव्हायडर ब्लॉकिंग, प्रॉम्प्ट-इंजेक्शन गार्ड                                               |
| **रूटिंग**     | ग्लोबल रूटिंग स्ट्रॅटेजी (Fill First / Round Robin / P2C / Random / Least Used / Cost Optimized), वाइल्डकार्ड मॉडेल उपनामे, फॉलबॅक चेन्स, कॉम्बो डीफॉल्ट्स     |
| **रेसिलियन्स** | रिक्वेस्ट क्यू, कनेक्शन कूलडाउन, प्रोव्हायडर ब्रेकर कॉन्फिग आणि wait-for-cooldown वर्तन                                                                        |
| **प्रगत**      | ग्लोबल प्रॉक्सी कॉन्फिगरेशन (HTTP/SOCKS5), प्रति-प्रोव्हायडर प्रॉक्सी ओव्हरराइड्स                                                                              |

सामान्य विभाग आता रीड-ओन्ली लॉगिंग आणि कॅशे नोट्स डुप्लिकेट करत नाही. डेटाबेस रिटेन्शन आणि
ऑप्टिमायझेशन सेटिंग्ज `/api/settings/database` द्वारे साठवल्या जातात; मॅन्युअल कॅशे क्लिअरिंगसाठी
`DELETE /api/cache` वापरले जाते. रिक्वेस्ट आणि प्रॉक्सी लॉग रो कॅप्स
`CALL_LOGS_TABLE_MAX_ROWS` आणि `PROXY_LOGS_TABLE_MAX_ROWS` द्वारे नियंत्रित केले जातात.

### कॉम्बो बॅलन्सिंग स्ट्रॅटेजीज

**डॅशबोर्ड → कॉम्बोज → तयार करा/संपादित करा → स्ट्रॅटेजी** मध्ये प्रति-कॉम्बो बॅलन्सिंग कॉन्फिगर करा.

| स्ट्रॅटेजी         | वर्णन                                                                             |
| ------------------ | --------------------------------------------------------------------------------- |
| **Round-Robin**    | मॉडेल्समधून क्रमाने फिरते                                                         |
| **Priority**       | नेहमी पहिले मॉडेल वापरण्याचा प्रयत्न करते; फक्त एरर झाल्यावरच फॉलबॅक करते         |
| **Random**         | प्रत्येक रिक्वेस्टसाठी कॉम्बोमधून यादृच्छिक मॉडेल निवडते                          |
| **Weighted**       | प्रत्येक मॉडेलला दिलेल्या वेट्सनुसार प्रमाणात रूट करते                            |
| **Least-Used**     | सर्वात कमी अलीकडील रिक्वेस्ट असलेल्या मॉडेलकडे रूट करते (कॉम्बो मेट्रिक्स वापरते) |
| **Cost-Optimized** | सर्वात स्वस्त उपलब्ध मॉडेलकडे रूट करते (किंमत तक्ता वापरते)                       |

ग्लोबल कॉम्बो डीफॉल्ट्स **डॅशबोर्ड → सेटिंग्ज → रूटिंग → कॉम्बो डीफॉल्ट्स** मध्ये सेट करता येतात.
कॉम्बो टार्गेट टाइमआउट्स डीफॉल्टनुसार सध्याचा रिक्वेस्ट टाइमआउट इन्हेरिट करतात. प्रति-टार्गेट
कमी मर्यादेने जलद फॉलबॅक ट्रिगर व्हावे असे हवे असल्यासच कॉम्बो डीफॉल्ट्सवर किंवा वैयक्तिक
कॉम्बोवर **टार्गेट टाइमआउट (सेकंद)** वापरा.

झिरो-लॅटन्सी कॉम्बो ऑप्टिमायझेशन्स ऑप्ट-इन आहेत. या लॅटन्सी वैशिष्ट्यांना फॉलबॅक
टार्गेट्सशी स्पर्धा करण्यापासून, TTFT इतिहासावर आधारित टार्गेट्स वगळण्यापासून किंवा फॉलबॅक
रिक्वेस्ट कॉम्प्रेस करण्यापासून रोखण्यासाठी **झिरो-लॅटन्सी ऑप्टिमायझेशन्स** अक्षमच ठेवा; ती सक्षम
केल्यास कॉन्फिगर केलेले हेजिंग, प्रिडिक्टिव्ह TTFT स्किप्स आणि प्रोअॅक्टिव्ह फॉलबॅक कॉम्प्रेशनला
कमी टेल लॅटन्सीच्या बदल्यात रूटिंग/रिक्वेस्ट फिडेलिटीची तडजोड करता येते.

अपस्ट्रीम प्रोव्हायडर्सना कठोर `max_tokens` / `maxOutputTokens` मर्यादा आवश्यक असताना **रीजनिंग टोकन बफर** अक्षम करा. सक्षम केल्यावर, कॉम्बो रूटिंग केवळ ज्ञात आउटपुट कॅप असलेल्या मॉडेल्ससाठी रीजनिंग-मॉडेल हेडरूम जोडते आणि सुरक्षित बफर केलेले मूल्य त्या कॅपपेक्षा जास्त जात असेल तेव्हा क्लायंट टोकन मर्यादा अपरिवर्तित ठेवते. क्लायंट मर्यादा आधीच ज्ञात कॅपपेक्षा जास्त असल्यास, OmniRoute अपस्ट्रीम विनंती पाठवण्यापूर्वी ती त्या कॅपपर्यंत कमी करते.

| **रेट लिमिट्स**        | उरलेल्या वेळेसह प्रत्येक खात्याचे सक्रिय कनेक्शन कूलडाउन |
| **सक्रिय लॉकआउट**      | सक्रिय मॉडेल-स्कोप्ड लॉकआउट आणि तात्पुरती वगळणी          |
| **सिग्नेचर कॅशे**      | डीडुप्लिकेशन कॅशे आकडेवारी (सक्रिय की, हिट रेट)          |
| **लेटन्सी टेलेमेट्री** | प्रत्येक प्रोव्हायडरसाठी p50/p95/p99 लेटन्सी एकत्रीकरण   |

**प्रो टिप:** हेल्थ पेज दर 10 सेकंदांनी स्वयंचलितपणे रीफ्रेश होते. कोणते प्रोव्हायडर समस्यांचा सामना करत आहेत हे ओळखण्यासाठी सर्किट ब्रेकर कार्ड वापरा.

## 🤖 स्वयंचलित रूटिंग (शून्य-कॉन्फिगरेशन)

OmniRoute मध्ये **स्कोअर-आधारित स्वयंचलित राउटर** समाविष्ट आहे, जो प्रत्येक कनेक्ट केलेल्या प्रदात्यामधून प्रत्येक विनंतीसाठी सर्वोत्तम मॉडेल निवडतो — कोणताही कॉम्बो सांभाळण्याची गरज नाही. फक्त `auto/*` उपसर्गांपैकी एक वापरून विनंती पाठवा आणि OmniRoute तत्काळ एक आभासी कॉम्बो तयार करेल. तो विलंब, खर्च, यशाचा दर, संदर्भाची अनुरूपता, कार्यासाठी मॉडेलची योग्यता, अलीकडील अपयशे, कोटा आणि सर्किट-ब्रेकरची स्थिती यांच्या आधारे उमेदवारांना स्कोअर देतो.

| उपसर्ग         | कशासाठी अनुकूलित करतो                                                                        |
| -------------- | -------------------------------------------------------------------------------------------- |
| `auto`         | संतुलित डीफॉल्ट (विलंब × खर्च × यशाचा दर)                                                    |
| `auto/coding`  | कोडिंग कार्ये: Claude, GPT-5, GLM, Kimi, Qwen Coder, DeepSeek कोडरना प्राधान्य देतो          |
| `auto/cheap`   | सर्वात कमी $/token, जास्त विलंब स्वीकारतो                                                    |
| `auto/fast`    | सर्वात कमी विलंब, खर्चाकडे दुर्लक्ष करतो                                                     |
| `auto/offline` | केवळ स्थानिक प्रदाते (Ollama, vLLM, llama.cpp) — एअर-गॅप्ड सेटअपसाठी उपयुक्त                 |
| `auto/smart`   | तर्कशक्तीच्या गुणवत्तेला सर्वोच्च प्राधान्य (Opus, GPT-5 xhigh, R1, GLM 5.1 reasoning)       |
| `auto/lkgp`    | "शेवटचा ज्ञात चांगला प्रदाता" — शेवटच्या यशस्वी प्रदात्यावर स्थिर राहतो, नंतर नियमांकडे वळतो |

उदाहरण:

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer $OMNIROUTE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto/coding",
    "messages": [{ "role": "user", "content": "Refactor this Python function" }],
    "stream": true
  }'
```

स्वयंचलित राउटरचे संपूर्ण वर्णन [AUTO-COMBO.md](../routing/AUTO-COMBO.md) मध्ये दिले आहे — यात स्कोअरिंगचे भार कसे समायोजित करायचे, प्रदात्यांना काळ्या यादीत कसे टाकायचे आणि **Dashboard → Auto Combo** मध्ये रूटिंगचे निर्णय कसे तपासायचे याचाही समावेश आहे.

## 🔌 MCP आणि A2A एकत्रीकरण

OmniRoute हा **MCP सर्व्हर** (Model Context Protocol) आणि **A2A सर्व्हर** (Agent-to-Agent JSON-RPC 2.0) दोन्ही आहे. कोणतेही MCP-सुसंगत IDE किंवा एजंट होस्ट OmniRoute साधनांना थेट कॉल करू शकते — कोणत्याही अतिरिक्त रॅपरची आवश्यकता नाही.

### MCP ट्रान्सपोर्ट

- **SSE**: `http://localhost:20128/api/mcp/sse`
- **स्ट्रीम करण्यायोग्य HTTP**: `http://localhost:20128/api/mcp/stream`
- **stdio**: `omniroute --mcp` (stdio ला प्राधान्य देणाऱ्या IDE प्लगइनसाठी)

### Claude Desktop कनेक्ट करा

macOS वरील `~/Library/Application Support/Claude/claude_desktop_config.json` किंवा Windows/Linux वरील समतुल्य फाइल संपादित करा:

```json
{
  "mcpServers": {
    "omniroute": {
      "command": "omniroute",
      "args": ["--mcp"]
    }
  }
}
```

### Cursor / Continue / VS Code MCP कनेक्ट करा

SSE URL `http://localhost:20128/api/mcp/sse` आणि **Dashboard → API Keys** मध्ये तयार केलेली Bearer API की वापरा.

### व्याप्ती

MCP सध्या 32 नामांकित व्याप्ती परिभाषित करते. प्रत्येक Bearer की विशिष्ट व्याप्तींपुरती मर्यादित करता येते — अधिकृत व्याप्ती आणि साधन-सूचीसाठी [MCP-SERVER.md](../frameworks/MCP-SERVER.md), तसेच JSON-RPC स्कीमासाठी [A2A-SERVER.md](../frameworks/A2A-SERVER.md) पहा.

- **प्रति-की स्कोप्स** — कोणत्या API की कोणती कौशल्ये वापरू शकतात हे मर्यादित करा

## 💾 मेमरी प्रणाली

OmniRoute हायब्रिड पुनर्प्राप्तीसह **दीर्घकालीन संभाषणात्मक मेमरी** कायमस्वरूपी साठवते:

- मागील संवादांमध्ये कीवर्ड शोधण्यासाठी **SQLite FTS5**
- अर्थाधारित पुनर्स्मरणासाठी **Qdrant vector store** (पर्यायी)
- **स्वयंचलित तथ्य निष्कर्षण** — प्रत्येक सत्रानंतर घटक, प्राधान्ये आणि निर्णयांचा सारांश तयार करून ते `memory_facts` टेबलमध्ये साठवले जातात
- मेमरी प्रत्येक API की आणि प्रत्येक सत्रानुसार स्वतंत्र ठेवली जाते

**डॅशबोर्ड → मेमरी** मध्ये मेमरी व्यवस्थापित करा (शोधा, संपादित करा, निर्यात करा, पूर्णपणे हटवा). HTTP इंटरफेस (`/api/memory/*`) एजंट्सना प्रोग्रामद्वारे तथ्ये पाठवण्याची आणि क्वेरी करण्याची सुविधा देतो — [MEMORY.md](../frameworks/MEMORY.md) पहा.

## 🛠️ प्रोग्रामद्वारे व्यवस्थापन

**`manage` स्कोप असलेली Bearer की** वापरून तुम्ही HTTP द्वारे प्रत्येक OmniRoute संसाधन (प्रदाते, कॉम्बोज, कीज, सेटिंग्ज) व्यवस्थापित करू शकता.

**डॅशबोर्ड → API कीज → नवीन की → स्कोप: manage** मध्ये की तयार करा, त्यानंतर:

```bash
# प्रदात्यांची सूची दाखवा
curl http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"

# प्रदाता कनेक्शन जोडा
curl -X POST http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "provider": "openai", "apiKey": "sk-...", "name": "main" }'

# कॉम्बो तयार करा
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "premium", "strategy": "priority", "models": [{ "model": "cc/claude-opus-4-7" }, { "model": "glm/glm-5.1" }] }'

# API कीजची सूची दाखवा/तयार करा
curl http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"
curl -X POST http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -d '{ "name": "ci-bot", "scopes": ["chat"] }'
```

संपूर्ण एंडपॉइंट कॅटलॉग आणि विनंती/प्रतिसाद स्कीमांसाठी [API_REFERENCE.md](../reference/API_REFERENCE.md) पहा.

## 💻 अंतर्गत CLI

OmniRoute सेटअप, निदान आणि रनटाइम नियंत्रणासाठी अंतर्गत CLI (`omniroute …`) सह उपलब्ध होते. हे **डॅशबोर्डमधील "CLI साधने" पृष्ठापेक्षा वेगळे आहे**, जे तृतीय-पक्षीय CLI (Claude Code, Cursor, Codex, Cline, …) कॉन्फिगर करते, जेणेकरून ते OmniRoute शी संवाद साधू शकतील.

```bash
omniroute setup                    # परस्परसंवादी विझार्ड (पासवर्ड, प्रदाते, कॉम्बो)
omniroute setup --non-interactive  # CI-सुसंगत
omniroute doctor                   # आरोग्य निदान (डेटा डिरेक्टरी, DB, प्रदाते, पोर्ट)
omniroute providers available      # समर्थित प्रदात्यांची सूची
omniroute providers list           # कॉन्फिगर केलेल्या कनेक्शनची सूची
omniroute providers test <id>      # प्रदाता कनेक्शनची थेट चाचणी
omniroute combos list              # कॉम्बोंची सूची
omniroute combos switch <name>     # डीफॉल्ट कॉम्बो सेट करा
omniroute models                   # उपलब्ध मॉडेलची सूची (--json, --search)
omniroute keys add | list | remove # टर्मिनलमधून API की व्यवस्थापित करा
omniroute backup                   # कॉन्फिगरेशन + DB चा स्नॅपशॉट
omniroute restore [<timestamp>]    # स्नॅपशॉटमधून पुनर्संचयित करा
omniroute health                   # सविस्तर आरोग्य माहिती (ब्रेकर्स, कॅशे, मेमरी)
omniroute quota                    # प्रदाता कोटा वापर
omniroute mcp status               # MCP सर्व्हरची स्थिती
omniroute a2a status               # A2A सर्व्हरची स्थिती
omniroute tunnel list|create|stop  # Cloudflare/Tailscale/ngrok टनेल
omniroute reset-password           # प्रशासकाचा पासवर्ड रीसेट करा
omniroute --mcp                    # stdio वर MCP सर्व्हर सुरू करा
omniroute --port 3000              # सानुकूल पोर्टवर सर्व्हर सुरू करा
```

टीप: प्रदाता कनेक्शन अस्वस्थ असल्यास सूचना मिळवण्यासाठी `omniroute doctor --json` आपल्या निरीक्षण साधनासोबत वापरा.
