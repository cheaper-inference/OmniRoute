OmniRoute कॉल लॉगचे बाह्य विश्लेषणात्मक डेटा स्टोअरमध्ये सातत्यपूर्ण, वाढीव निर्यात.

लॉग डॅशबोर्डचा टॅब विनंत्यांचा इतिहास SQLite (`call_logs`) मध्ये ठेवतो, ज्याला
रोटेशन आणि धारणा कालावधीच्या मर्यादा लागू होतात. लॉग निर्यात हाच रेकॉर्ड संच नियोजित वेळापत्रकानुसार बाहेर पाठवते, जेणेकरून तो
स्थानिक डेटाबेसपेक्षा अधिक काळ टिकू शकेल आणि इतर डेटासोबत जोडता येईल. BigQuery हे पहिले गंतव्य आहे;
पाइपलाइन ही एक रजिस्ट्री असल्यामुळे, अधिक गंतव्ये विद्यमान व्यवस्थेत भर म्हणून जोडता येतात.

## 1. हे कसे कार्य करते

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **वेळापत्रक** — एक `JobRegistry` cron जॉब, `log_export`, ज्याचे डीफॉल्ट मूल्य `0 * * * *` आहे (दर तासाला,
  UTC). याची नोंदणी `src/lib/initCloudSync.ts` मध्ये होते; `OMNIROUTE_LOG_EXPORT_CRON` वापरून ते बदलता येते.
  प्रत्येक नियोजित आवर्तनात सर्व **सक्षम** गंतव्यांचा प्रलंबित डेटा क्रमाने निर्यात केला जातो.
- **कर्सर** — SQLite चा अप्रत्यक्ष `call_logs.rowid`, जो प्रत्येक गंतव्यासाठी
  `log_export_destinations.cursor_row_id` मध्ये जतन केला जातो. `timestamp` जाणीवपूर्वक कर्सर म्हणून वापरलेला नाही: कॉल करणारे
  स्वतःचे मूल्य देऊ शकतात, त्यामुळे एखादी संथ विनंती तिच्यानंतर सुरू झालेल्या जलद विनंतीनंतर लिहिली जाऊ शकते,
  आणि टाइमस्टॅम्प कर्सर वापरल्यास ती वगळली जाईल.
- **बॅचिंग** — प्रत्येक विनंतीत `batch_size` ओळी (डीफॉल्ट 500), प्रत्येक रनमध्ये `max_rows_per_run` ओळी
  (डीफॉल्ट 10000), जेणेकरून मोठा अनुशेष एकाच आवर्तनाला अडवण्याऐवजी अनेक आवर्तनांत निर्यात होईल.
- **वितरण** — `send()` यशस्वीरीत्या पूर्ण झाल्यानंतरच कर्सर पुढे जातो. एखादी बॅच अयशस्वी झाल्यास
  कर्सर आधीच्याच जागी राहतो, त्यामुळे पुढील रनमध्ये त्याच ओळी पुन्हा पाठवण्याचा प्रयत्न होतो. यामध्ये
  किमान एकदा वितरण आणि गंतव्याकडील डुप्लिकेट निर्मूलन यांची हमी आहे, खऱ्या अर्थाने नेमके एकदाच वितरणाची नाही: BigQuery प्रत्येक
  ओळीसाठी कॉल-लॉग आयडी कळ म्हणून वापरतो आणि स्वतःच्या डुप्लिकेट निर्मूलन कालावधीत शक्य तितक्या प्रयत्नाने त्याचा मान राखतो.
- **एकाचवेळी चालण्यापासून संरक्षण** — cron आवर्तन आणि `POST .../run` एकाचवेळी सुरू होऊ शकतात. एखाद्या गंतव्याचा
  डेटा आधीच निर्यात होत असल्यास, त्याची पुन्हा निर्यात करण्याऐवजी ते वगळले जाते (रनच्या निकालात `skipped: true`),
  त्यामुळे समांतर रन बॅच पुन्हा पाठवू शकत नाही किंवा कर्सर मागे नेऊ शकत नाही.
- **संपूर्ण डेटा साफ केल्यानंतर पुनर्प्राप्ती** — `cursor_row_id` चे मूल्य `MAX(rowid)` पेक्षा जास्त झाल्यास (संपूर्ण टेबल
  साफ केले गेले आणि rowid पुन्हा सुरुवातीपासून सुरू झाले), रनर कायमचा नवीन डेटा पाहू न शकण्याऐवजी कर्सर 0 वर परत नेतो.

### विलग रनर आणि मर्यादा

Node वरील प्रत्येक गंतव्याचा रन स्वतंत्र, अल्पकाळ चालणारी OS चाइल्ड प्रक्रिया सुरू करतो (IPC सह `child_process`,
`worker_threads` नव्हे). बॉडी वाचन, पेलोड JSON पार्सिंग/सीरियलायझेशन, गंतव्याचे
`prepare()` आणि गंतव्याचे नेटवर्क I/O हे सर्व तिथे चालते, सर्व्हरच्या इव्हेंट लूपवर नाही.
फक्त कॉन्फिगरेशन आणि लहान प्रगती संदेश IPC मधून जातात; निर्यात केलेले रेकॉर्ड कधीही
सर्व्हरवर परत येत नाहीत. cron जॉब आणि आता चालवा रूट यांचा सार्वजनिक निकाल आणि एकाचवेळी चालण्यापासूनचे संरक्षण पूर्वीप्रमाणेच राहते.

चाइल्ड प्रक्रिया `node:sqlite` वापरून सर्व्हरचा निर्धारित `DATA_DIR/storage.sqlite` केवळ-वाचन मोडमध्ये उघडते,
आणि `busy_timeout=5000` व `query_only=ON` वापरते. ती कोणताही DB सिंगलटन आयात करत नाही आणि
मायग्रेशन, बॅकअप किंवा SQLite अपडेट करत नाही. गहाळ/दूषित आर्टिफॅक्टचे व्यवस्थापन (दूषित आर्टिफॅक्टच्या
UPDATE सह) फक्त डॅशबोर्डच्या तपशील मार्गातच राहते. दोन्ही मार्ग एकच शुद्ध
तपशील रिझॉल्वर वापरतात; निर्यात असिंक्रोनस फाइलसिस्टम वाचन आणि तोच आर्टिफॅक्ट → जुने
इनलाइन → जुने डिस्क → काहीही नाही असा शोधक्रम वापरते. चाइल्ड प्रक्रिया आपला रीडर उघडते तेव्हा रन कमाल समावेश rowid चा स्नॅपशॉट घेतो;
त्यानंतर समाविष्ट केलेल्या नोंदी पुढील रनपर्यंत थांबतात. ही समावेशाची
सीमा आहे, दीर्घकाळ चालणारा SQLite व्यवहार नाही: नेटवर्क प्रतिसादाची वाट पाहताना WAL रायटर्स आणि चेकपॉइंट्स मोकळे राहतात.
विद्यमान ओळींमधील अपडेट/हटवणे या सीमेमुळे गोठवले जात नाही.

प्रत्येक बॅच स्वीकारल्यानंतर, चाइल्ड प्रक्रिया पोचपावतीची वाट पाहते. सर्व्हर प्रथम
`advanceLogExportCursor` वापरून कर्सर जतन करतो, त्यानंतर `ack` पाठवतो; त्यापूर्वी पुढील बॅच सुरू होत नाही.
पाठवण्यातील अपयश, क्रॅश किंवा टाइमआउट आल्यास, त्या बॅचचा कर्सर पुढे न नेता अपयश नोंदवले जाते. आधी
पोचपावती मिळालेल्या बॅचेस कायम राहतात; जास्तीत जास्त पोचपावती न मिळालेली एकच बॅच पुन्हा पाठवली जाऊ शकते.
`done` मिळाल्यानंतर आणि चाइल्ड प्रक्रिया व्यवस्थित बंद झाल्यानंतरच यश नोंदवले जाते. अपयश आल्यास चाइल्ड प्रक्रिया
SIGTERM ने बंद केली जाते, 500 ms नंतर आवश्यक असल्यास SIGKILL वापरले जाते, आणि रनर प्रक्रिया पूर्णपणे बंद होईपर्यंत थांबतो.

| पर्यावरण चल                                   | डीफॉल्ट | उद्देश                                           |
| --------------------------------------------- | ------- | ------------------------------------------------ |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000  | प्रत्येक गंतव्यासाठी प्रत्यक्ष कालावधीची मर्यादा |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024    | चाइल्ड प्रक्रियेची V8 old-space मर्यादा MB मध्ये |

अवैध/धन नसलेली/पूर्णांक नसलेली मूल्ये दिल्यास डीफॉल्ट मूल्ये वापरली जातात. हीप सेटिंग म्हणजे एकूण
RSS मर्यादा नाही; खूप मोठ्या बॅचमुळे चाइल्ड प्रक्रियेची मेमरी तरीही संपुष्टात येऊ शकते आणि रन सुरक्षितपणे अयशस्वी होऊ शकतो.
1024 MB चे डीफॉल्ट मूल्य, बॉडी सक्षम असताना 512 KiB आर्टिफॅक्टच्या डीफॉल्ट 500-ओळींच्या बॅचसाठी,
BigQuery च्या बाइट-खंडित JSON सीरियलायझेशनसह, अतिरिक्त जागा उपलब्ध ठेवते. यामुळे
10000-ओळींची बॉडी असलेली बॅच सुरक्षित होत नाही. V8 हीप संपुष्टात आल्यास उपाय करता येईल असे अपयश नोंदवले जाते: बॅचचा
आकार कमी करा किंवा `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` वाढवा; कर्सर शेवटच्या
पोचपावती मिळालेल्या बॅचवरच राहतो. जुन्या इनलाइन/डिस्क बॉडींना आधुनिक आर्टिफॅक्ट मर्यादा लागू होत नाही.
ऑपरेटरनी RSS साठी स्वतंत्रपणे मेमरीचे नियोजन केले पाहिजे, विशेषतः मर्यादित मेमरी असलेल्या कंटेनरमध्ये.

चाइल्ड प्रक्रियेला केवळ निराकरण केलेले `DATA_DIR`, `NODE_ENV`, स्पष्टपणे दिलेले `TZ` (जुन्या फाइलनावांसाठी
स्थानिक वेळेचे निराकरण), उपस्थित असल्यास `ELECTRON_RUN_AS_NODE`, आणि पुढील आउटबाउंड इनपुट वारशाने मिळतात:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (आणि त्यांची लघुअक्षरी रूपे),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
जागतिक Undici डिस्पॅचर सर्व्हरचे केवळ पर्यावरणावर आधारित प्रॉक्सी निराकरण आणि स्थानिक होस्ट
वगळण्याचे नियम सामायिक करतो, ज्यात `NO_PROXY` समाविष्ट आहे; तो `proxyFetch.ts` किंवा त्याचे DB/वैशिष्ट्य फ्लॅग आयात करत नाही.
पुढे पाठवलेल्या आउटपुटमधून आणि नोंदवलेल्या त्रुटींमधून प्रॉक्सीची प्रमाणीकरण माहिती लपवली जाते. गंतव्यस्थानाची प्रमाणीकरण माहिती
केवळ एका प्रारंभिक IPC संदेशातून पाठवली जाते, argv किंवा पर्यावरणातून कधीही नाही; आउटपुट/त्रुटी पुढे पाठवताना
उपसर्ग जोडला जातो आणि संवेदनशील माहिती काढून टाकली जाते. प्रत्येक cron रनमध्ये Node च्या SQLite चेतावणीची पुनरावृत्ती टाळण्यासाठी
चाइल्ड exec आर्ग्युमेंटमध्ये केवळ `ExperimentalWarning` अक्षम केले जाते; इतर प्रकारच्या चेतावण्या दिसत राहतात.

गंतव्यस्थान मॉड्यूल Next.js/server-only अवलंबित्वांशिवाय आयात करता येणे आवश्यक आहे. विद्यमान
BigQuery अंमलबजावणी आधीच ही अट पूर्ण करते. ॲक्सेस-टोकन कॅश केवळ चाइल्ड
रनपुरते टिकतात, अनेक रनमध्ये टिकत नाहीत. Node हा समर्थित रनटाइम आहे (`package.json` engines), परंतु README मधील Bun
स्थापना विभाग आणि `Dockerfile.bun` हेही
`bun:sqlite` (`src/lib/db/core.ts` / अडॅप्टर) वापरून उत्पादनासाठी सुसंगततेचा मार्ग दर्शवतात. त्यामुळे Bun अंतर्गत, निर्यातींसाठी पूर्वीचा
प्रक्रियेतच चालणारा मार्ग कायम ठेवला जातो आणि एकदाच चेतावणी दिली जाते: चाइल्ड हीप/टाइमआउट विलगीकरण उपलब्ध नाही. इव्हेंट-लूप आणि OOM विलगीकरणासाठी
Node वापरा; येथे Bun ला केवळ विकासापुरते मानलेले नाही.

`includeBodies` सक्षम असताना, तासाभराच्या पेलोडचा अनुशेष साचू देण्याऐवजी
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` सारखी मिनिटांच्या पातळीवरील वारंवारता वापरण्यास प्राधान्य द्या.
बॅच आणि ओळींच्या मर्यादा तरीही प्रत्येक रनला मर्यादित ठेवतात. प्रत्येक रनमध्ये प्रत्येक गंतव्यस्थानासाठी प्रक्रिया सुरू करण्याचा खर्च येतो;
एकूण CPU वापर कमी करण्याऐवजी, सर्व्हरच्या इव्हेंट-लूप विलगीकरणासाठी हा छोटासा प्रारंभिक खर्च स्वीकारला जातो.

### पेलोड (प्रॉम्प्ट आणि पूर्णत्वे)

डीफॉल्टनुसार, निर्यातीत केवळ लॉगच्या **यादीत** दिसणारी सारांश फील्ड असतात.
**प्रॉम्प्ट आणि प्रतिसाद निर्यात करा** (`includeBodies`) सुरू केल्यास, प्रत्येक कॉलसाठी लॉगच्या **तपशील**
पटलात दिसणारी पुढील माहितीही पाठवली जाते:

| फील्ड                            | त्यात काय असते                                                     |
| -------------------------------- | ------------------------------------------------------------------ |
| `request_body` / `response_body` | डॅशबोर्डवर जसे दाखवले जातात तसे कॉलचे पेलोड                        |
| `pipeline_route_decision`        | राउटरने निवडलेले लक्ष्य आणि मॉडेल                                  |
| `pipeline_client_request`        | क्लायंटने पाठवली तशीच मूळ विनंती                                   |
| `pipeline_openai_request`        | अंतर्गत OpenAI स्वरूपात रूपांतरित केल्यानंतरची विनंती              |
| `pipeline_provider_request`      | प्रदात्याच्या विशिष्ट स्वरूपात प्रत्यक्ष अपस्ट्रीम पाठवलेली विनंती |
| `pipeline_provider_response`     | मूळ अपस्ट्रीम प्रतिसाद                                             |
| `pipeline_client_response`       | कॉल करणाऱ्याला परत दिलेली माहिती                                   |
| `pipeline_error`                 | अयशस्वी कॉलसाठी पाइपलाइन-स्तरीय त्रुटीचा तपशील                     |
| `bodies_truncated`               | वरील कोणतेही फील्ड `maxBodyBytes` मर्यादेपर्यंत पोहोचल्यास True    |

हा प्रॉम्प्टमधील मजकूर असल्यामुळे, हे **डीफॉल्टनुसार बंद** असते आणि जाणीवपूर्वक प्रत्येक गंतव्यस्थानासाठी स्वतंत्र निवड असते.
डॅशबोर्डवर जे दिसते तेच पाठवले जाते, कारण निर्यात आणि `getCallLogById` तपशील
निराकरणाची समान पद्धत वापरतात: पेलोड
लिहितानाच त्यांमधून वैयक्तिक ओळख पटवणारी माहिती (PII) काढलेली आणि गुप्त माहिती लपवलेली असते, आणि
`noLog` API की वापरून केलेला कॉल कोणताही पेलोड साठवत नाही, त्यामुळे निर्यात करण्यासारखे काहीही नसते.

पेलोड प्रत्येक ओळीसाठी फाइलसिस्टम आर्टिफॅक्टमधून वाचले जातात, त्यामुळे ही माहिती भरण्याची प्रक्रिया केवळ
ती मागितलेल्या गंतव्यस्थानांसाठीच चालते. आर्टिफॅक्ट गहाळ किंवा खराब असल्यास, बॅच अयशस्वी करून कर्सर अडकवण्याऐवजी
त्याचा सारांश null पेलोडसह निर्यात केला जातो.

`maxBodyBytes` (डीफॉल्ट 262144) प्रत्येक फील्डच्या आकारावर मर्यादा घालते. मोठे पेलोड **वगळण्याऐवजी
कापले जातात** — कापलेला प्रॉम्प्टही "काय विचारले होते" याचे उत्तर देतो — आणि त्या ओळीला
`bodies_truncated` ने चिन्हांकित केले जाते. प्रवाहित केलेले तुकड्या-तुकड्यांतील बदल निर्यात केले जात नाहीत; एकत्रित प्रतिसाद
आधीच `pipeline_provider_response` आणि `pipeline_client_response` मध्ये असतो.

## 3. REST API

सर्व मार्गांसाठी व्यवस्थापन प्रमाणीकरण केले जाते (`requireManagementAuth`). गुपिते कधीही परत केली जात नाहीत:
साठवलेले गुपित अक्षरशः `__stored__` या मूल्यासह परत येते आणि अद्यतन करताना तेच मूल्य परत पाठवल्यास
साठवलेले क्रेडेन्शियल कायम राहते.

ज्या गंतव्याच्या प्रकारात गुपित घोषित केलेले आहे, ते तयार किंवा अद्यतनित करण्यासाठी **`STORAGE_ENCRYPTION_KEY`

लेखन 400 प्रतिसादासह नाकारले जाते (Telegram webhook मध्येही हाच सुरक्षा प्रतिबंध
लागू केला जातो).

## 4. BigQuery गंतव्य

कॉन्फिगरेशन की (`type: "bigquery"`):

| की                   | टिपा                                                                               |
| -------------------- | ---------------------------------------------------------------------------------- |
| `projectId`          | डेटासेट असलेला GCP प्रकल्प                                                         |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                    |
| `tableId`            | `[A-Za-z0-9_]+`                                                                    |
| `location`           | डेटासेट तयार करावा लागतो तेव्हाच वापरले जाते (डीफॉल्ट `EU`)                        |
| `serviceAccountJson` | सेवा-खाते की. गुपित: साठवलेल्या स्थितीत एन्क्रिप्ट केलेली, कधीही परत केली जात नाही |
| `autoCreate`         | पहिल्या निर्यातीवेळी डेटासेट आणि टेबल तयार करा (डीफॉल्ट `true`)                    |

सेवा खात्याला लक्ष्य टेबलवर `bigquery.tables.updateData` परवानगी आवश्यक आहे, तसेच
`autoCreate` चालू असताना `bigquery.datasets.create` / `bigquery.tables.create` परवानग्याही आवश्यक आहेत.

कॉन्फिगर केलेला बॅच हे **कर्सर** एकक आहे, HTTP एकक नाही: `send()` त्याचे जास्तीत जास्त 500 ओळींच्या insertAll
कॉलमध्ये तुकडे करते, त्यामुळे मोठ्या `batch_size` मुळे BigQuery ची 10 MB विनंती मर्यादा ओलांडली जात नाही.
तात्पुरत्या स्थितींसाठी (408/429/500/502/503/504) तेच insertIds पुन्हा वापरून, घातांकीय
विलंबासह जास्तीत जास्त तीन वेळा पुनर्प्रयत्न केले जातात; प्रमाणीकरण आणि स्कीमा अपयशांवर रन वाया घालवण्याऐवजी
पहिल्याच प्रयत्नात अपवाद फेकला जातो.

नुकतेच तयार केलेले टेबल स्ट्रीमिंग एंडपॉइंटला अद्याप दिसत नाही, त्यामुळे तो काही सेकंद
404 प्रतिसाद देतो. त्या 404 साठी पुनर्प्रयत्न केला जातो, पण **या रनने टेबल तयार केले असेल तेव्हाच** —
खरोखरच अस्तित्वात नसलेल्या टेबलसाठी मात्र लगेच अपयश येते. लक्षात घ्या की नुकतेच हटवलेल्या नावाने
टेबल पुन्हा तयार केल्यास BigQuery अनेक मिनिटांसाठी स्ट्रीमिंग इन्सर्ट नाकारते; हे
हटवून-पुन्हा-तयार करण्याचे वैशिष्ट्य आहे, त्यामुळे टेबल हटवून पुन्हा जोडण्याऐवजी नवीन टेबल नाव वापरण्यास प्राधान्य द्या.

**आंशिक अपयश HTTP 200 सह आणि रिकामे नसलेल्या `insertErrors[]` सह येते.** ते
अपयश म्हणून हाताळले जाते आणि अपवाद फेकला जातो, ज्यामुळे BigQuery ने कधीही स्वीकारल्या नसलेल्या ओळींच्या पुढे कर्सर
सरकत नाही; `tests/unit/log-export-bigquery.test.ts` हे वर्तन निश्चित करते.

डेटा हस्तांतरणासाठी साधे REST वापरले जाते — स्व-स्वाक्षरी केलेल्या RS256 असर्शनच्या बदल्यात
`https://oauth2.googleapis.com/token` येथे ॲक्सेस टोकन मिळवले जाते, त्यानंतर ओळी `tabledata.insertAll` कडे जातात. कोणताही Google SDK
समाविष्ट केला जात नाही. ॲक्सेस टोकन प्रत्येक (सेवा खाते, व्याप्ती) जोडीसाठी प्रक्रियेत कॅश केले जातात.

तयार केलेल्या टेबलमध्ये Logs टॅबमधील प्रत्येक फील्डसाठी एक स्तंभ आणि त्यासोबत `exported_at` असतो, आणि कॉल लॉगवर
प्रत्यक्षात जशा क्वेरी केल्या जातात त्यानुसार त्याची रचना केली जाते:

- **`timestamp` वर दिवसानुसार विभाजित**, त्यामुळे तारखेची मर्यादा असलेली क्वेरी फक्त त्या दिवसांचेच स्कॅन करते.
- **`api_key_name`, `provider`, `model`, `status` नुसार क्लस्टर केलेले** (याच क्रमाने), त्यामुळे
  ते कोणी चालवले, ते कुठे गेले किंवा ते अयशस्वी झाले का यानुसार फिल्टर केल्यास प्रत्येक विभाजनातील अनावश्यक ब्लॉक वगळले जातात. BigQuery
  जास्तीत जास्त चार क्लस्टरिंग स्तंभांना परवानगी देते आणि क्रम महत्त्वाचा असतो: फक्त `api_key_name` वरील फिल्टर
  ब्लॉक वगळतो, पण फक्त `status` वरील फिल्टर तसे करत नाही.
- **पर्यायी विभाजन धारणा कालावधी** `partitionExpirationDays` द्वारे (0 सर्वकाही जतन करते), जो
  टेबल तयार करताना लागू केला जातो.

दोन्ही सेटिंग्ज निर्मितीच्या वेळी लागू होतात. विद्यमान टेबलची आधीचीच रचना कायम राहते, त्यामुळे
त्या सेटिंग्ज स्वीकारायच्या असल्यास गंतव्य नवीन टेबल आयडीकडे निर्देशित करा.

`tests/unit/log-export-bigquery.test.ts` मॅपर आणि टेबल स्कीमा यांच्यात सुसंगती कायम असल्याची
पडताळणी करते, त्यामुळे निर्यात करताना नवीन कॉल-लॉग स्तंभ नकळत वगळला जाऊ शकत नाही.

बॅचचे तुकडे ओळींची संख्या आणि सिरियलाइझ केलेले बाइट्स या **दोन्हींनुसार** केले जातात. पेलोड निर्यात केले जातात तेव्हा
केवळ ओळींची संख्या पुरेशी नसते: प्रॉम्प्ट असलेल्या 500 ओळींचा आकार अनेक दहा मेगाबाइट असू शकतो, आणि insertAll
10 MB पेक्षा मोठी विनंती नाकारते. 500 ओळी किंवा 9 MB यांपैकी जी मर्यादा आधी येईल तिथे तुकडा पूर्ण केला जातो.

## 5. OTLP/HTTP ट्रेसेसचे गंतव्य

कॉन्फिगरेशनमध्ये `type: "otlp-http"` वापरले जाते. हे कायमस्वरूपी साठवलेल्या कॉल लॉगचे नियोजित, कर्सर-आधारित निर्यात कार्य आहे,
`open-sse/services/routing/otel.ts` मधील सर्वोत्तम-प्रयत्न तत्त्वावरील थेट राउटिंग-इव्हेंट सिंक नाही.
हे त्या सिंकची एन्व्हायर्नमेंट व्हेरिएबल्स, टाइमर्स किंवा बफर्स वाचत किंवा बदलत नाही.
दोन्ही सक्षम केल्यास दोन स्वतंत्र प्रकारचे स्पॅन्स तयार होऊ शकतात;
या कॉल-लॉग स्पॅन्सना वेगळे ओळखण्यासाठी `omniroute.log-export` इन्स्ट्रुमेंटेशन स्कोप वापरा.

| की                       | डीफॉल्ट / उद्देश                                                               |
| ------------------------ | ------------------------------------------------------------------------------ |
| `endpoint`               | संपूर्ण HTTP(S) ट्रेसेस URL आवश्यक; `/v1/traces` प्रत्यय जोडला जात नाही        |
| `headers`                | ऐच्छिक `Name: value` ओळी किंवा स्ट्रिंग्सचे JSON ऑब्जेक्ट; एन्क्रिप्ट केलेले   |
| `requestHeaderAllowlist` | रिकामे (बंद); स्पॅन ॲट्रिब्यूट्स म्हणून टिपण्यासाठी क्लायंट हेडरची नावे/उपसर्ग |
| `serviceName`            | `omniroute`; रिसोर्स `service.name`                                            |
| `langfuseMapping`        | `false`; Langfuse जनरेशन/सेशन/वापरकर्ता ॲट्रिब्यूट्स जोडते                     |
| `identity`               | `pseudonymous`, `keyName`, किंवा `none`                                        |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                        |
| `timeoutMs`              | प्रत्येक HTTP प्रयत्नासाठी `30000`                                             |
| `environment`            | सेट केलेले नाही; ऐच्छिक `langfuse.environment`                                 |

सर्वसाधारण डॅशबोर्ड ही फील्ड्स प्रदर्शित करतो. `paths` मध्ये API ॲरे किंवा
नवीन ओळींनी/स्वल्पविरामांनी विभक्त केलेले अचूक पाथ असलेला टेक्स्टएरिया स्वीकारला जातो. स्पष्टपणे परवानगी दिल्याशिवाय एम्बेडिंग्स, रीरँक आणि इतर पाथ
वगळले जातात. वगळलेल्या ओळींमुळेही कर्सर पुढे सरकतो; विद्यमान
रनरचे `exported`/`exportedTotal` काउंटर्स स्वीकारलेल्या स्पॅन्सऐवजी, फिल्टर केलेल्या
ओळींसह प्रक्रिया केलेल्या स्रोत ओळी मोजतात. फिल्टरिंग चाइल्डमध्ये केले जाते, त्याचा
IPC/कर्सर करार न बदलता.

URL पडताळणीसाठी `src/shared/network/outboundUrlGuard.ts` मधील DB-विरहित
`parseAndValidateNonMetadataUrl` हेल्पर वापरला जातो: `block-metadata` धोरण. यात खाजगी URLsना परवानगी दिलेल्या
वेबहुक पडताळणीकर्त्याप्रमाणेच बिनशर्त मेटाडेटा/प्रोटोकॉल/एम्बेड केलेली क्रेडेन्शियल्स तपासणी
असते, परंतु जागतिक फीचर-फ्लॅग ओव्हरराइडशिवाय localhost/LAN लक्ष्यांना जाणीवपूर्वक परवानगी दिली जाते.
यामुळे खाजगी HTTP एंडपॉइंट्ससह स्वयं-होस्टेड Langfuse, Phoenix, Tempo आणि Collector
एंडपॉइंट्स वापरता येतात. क्लाउड-मेटाडेटा होस्ट नेहमी अवरोधित केले जातात.
रीडायरेक्ट्सचे अनुसरण केले जात नाही, त्यामुळे कलेक्टर क्रेडेन्शियल्स दुसऱ्या होस्टकडे रीडायरेक्ट करू शकत नाही.
विद्यमान लेक्सिकल URL गार्डप्रमाणेच, हे DNS रिझोल्यूशन पिन करत नाही; फक्त
ऑपरेटरच्या नियंत्रणातील होस्ट कॉन्फिगर करा. एंडपॉइंट विश्वसनीय नेटवर्कवर नसल्यास शक्यतो HTTPS वापरा.

### पेलोड आणि वितरण

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) प्रत्येक
परवानगी दिलेल्या ओळीसाठी एक CLIENT स्पॅन वाहून नेतो, ज्याचे नाव तिच्या अचूक रिक्वेस्ट पाथनुसार असते. पाथनुसार नामकरण केल्याने
स्पॅनच्या नावात मॉडेल किंवा ओळख डेटा न घालता Chat Completions, Responses आणि Messages यांच्यात फरक करता येतो.
रिसोर्स ॲट्रिब्यूट्समध्ये `service.name` आणि पॅकेजचे `service.version` समाविष्ट असतात.

सामान्य चॅट प्रयत्न लॉगर (`open-sse/handlers/chatCore/attemptLogging.ts`) पूर्ण झाल्यावर
`duration = Date.now() - startTime` लिहितो आणि टाइमस्टॅम्प देत नाही;
`src/lib/usage/callLogs.ts` मधील `saveCallLogOperation` टाइमस्टॅम्पचे डीफॉल्ट मूल्य लिहिण्याची
(पूर्ण होण्याची) वेळ ठेवते. त्यामुळे निर्यातीत शेवट = ओळीचा टाइमस्टॅम्प आणि सुरुवात = शेवट − कालावधी
(मिलिसेकंद, दशमान नॅनोसेकंदांत रूपांतरित) असे सेट केले जाते. कॉलरने दिलेले ऐतिहासिक टाइमस्टॅम्पदेखील
शेवटची वेळ म्हणून जतन केले जातात; प्रत्येक ओळीसाठी सुरुवात/पूर्णता वेगळी ओळखणारा निर्देशक नाही.
null कालावधी शून्य होतो. अवैध/गहाळ टाइमस्टॅम्प असल्यास अनिश्चित स्पॅन्स तयार करण्याऐवजी
बॅच अयशस्वी होते. `ttftMs` null असू शकते आणि ते `omniroute.ttft_ms` शी मॅप होते.

ॲट्रिब्यूट्समध्ये `gen_ai.operation.name="chat"`, प्रदाता, विनंती केलेले/प्रतिसादातील मॉडेल,
इनपुट/आउटपुट टोकन्स, ऐच्छिक कॅश-वाचन/कॅश-निर्मिती/रीझनिंग टोकन्स, HTTP स्थिती,
कॉम्बो, कॅश स्रोत, सेशन टॅग आणि कोरिलेशन आयडी समाविष्ट असतात. पूर्णांक OTLP मूल्ये आणि टाइमस्टॅम्प
दशमान स्ट्रिंग्स असतात; स्ट्रिंग्स, बुलियन आणि अपूर्णांक संख्या त्यांच्या मूळ OTLP मूल्य
प्रकारांचा वापर करतात. त्रुटी स्पॅन्सना ERROR स्थिती आणि सॅनिटाइझ केलेला स्थिती संदेश असतो. प्रमाणित
रेकॉर्डमध्ये अपस्ट्रीम होस्ट URL नसतो, त्यामुळे कलेक्टरला चुकीने मॉडेल सर्व्हर
म्हणून ओळखण्याऐवजी `server.address` वगळले जाते. खर्च निर्यात केला जात नाही.

फक्त `includeBodies=true` असतानाच आशय लोड केला जातो. `langfuseMapping=false` असताना,
`gen_ai.input.messages` / `gen_ai.output.messages` मध्ये OmniRoute ने साठवलेला सॅनिटाइझ केलेला रिक्वेस्ट/रिस्पॉन्स
बॉडी JSON असतो (पार्स करता आल्यास प्रमाणित केलेला), पुनर्रचित semconv
मेसेजेस ॲरे नसतो. कापलेल्या/JSON नसलेल्या बॉडीज कच्चा मजकूर म्हणूनच राहतात. `langfuseMapping=true` असताना,
बॉडीज फक्त `langfuse.observation.input` / `langfuse.observation.output` म्हणून पाठवल्या जातात;
प्रत्येक बॉडी एकदाच पाठवली जावी म्हणून `gen_ai.*.messages` ॲट्रिब्यूट्स वगळले जातात. दोन्ही मोड्स
विद्यमान हायड्रेशन पाथमधून `maxBodyBytes` घेतात;
`omniroute.bodies_truncated=true` कापल्याचे दर्शवते.
हे गंतव्य कोणतेही अतिरिक्त पाइपलाइन स्नॅपशॉट्स किंवा सॅनिटाइझ न केलेल्या आर्टिफॅक्टचे वाचन जोडत नाही;
ऐच्छिक रिक्वेस्ट-हेडर कॅप्चर खाली वर्णन केलेला विद्यमान हायड्रेटेड क्लायंट स्नॅपशॉट वापरते.
बॉडीज निर्यात करताना तासाभराचा अनुशेष साचू देण्याऐवजी
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` सारखे मिनिट-स्तरीय वेळापत्रक वापरा.

### ऐच्छिक क्लायंट रिक्वेस्ट हेडर्स

हेडर कॅप्चर **डीफॉल्टनुसार बंद** असते. गंतव्याच्या कॉन्फिगरेशनमध्ये `requestHeaderAllowlist` सेट करा
आणि **प्रॉम्प्ट्स आणि प्रतिसाद निर्यात करा** सक्षम करा (गंतव्यावर `includeBodies: true`).
परवानगी-सूची API ॲरे किंवा नवीन ओळींनी/स्वल्पविरामांनी विभक्त केलेली नावे असलेला टेक्स्टएरिया स्वीकारते:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

नावांची जुळवणी इंग्रजी अक्षरांचे मोठे-लहान रूप विचारात न घेता आणि तंतोतंत केली जाते, मात्र शेवटी असलेला एकमेव `*` रिक्त नसलेला
हेडर-नाव उपसर्ग निवडतो. एकटा `*`, नावाच्या मधील वाइल्डकार्ड आणि अवैध HTTP हेडर नावे नाकारली जातात.
जास्तीत जास्त 64 निवडकर्ते असू शकतात, आणि प्रत्येकाचे नाव/उपसर्ग जास्तीत जास्त 256 ASCII बाइट्सचे असू शकते.
ही सेटिंग `headers` पासून स्वतंत्र आहे; `headers` निर्यातकाचे कलेक्टरकडे प्रमाणीकरण करते.

कॅप्चर फक्त `pipeline_client_request` वाचते, जे जतन केलेल्या तपशीलवार पाइपलाइनच्या
`clientRawRequest` मधून (किंवा जुन्या `clientRequest` मधून) भरले जाते. ते पर्याय म्हणून प्रदात्याच्या विनंती हेडर्सचा कधीही वापर करत नाही.
विनंती नोंदवली गेली तेव्हा तपशीलवार पाइपलाइन लॉगिंग सक्षम असणे आवश्यक आहे.
`includeBodies` अक्षम असल्यास, किंवा क्लायंट-स्नॅपशॉट JSON गहाळ, दूषित किंवा कापलेले असल्यास, कोणतेही हेडर
अॅट्रिब्यूट्स तयार केले जात नाहीत. `maxBodyBytes` वाढवल्याने निर्यातीच्या वेळी स्नॅपशॉट कापला जाणे टाळता येऊ शकते;
कधीही जतन न केलेला तपशील मात्र त्याने पुनर्संचयित करता येत नाही. 1 MiB पेक्षा मोठा किंवा
256 पेक्षा जास्त हेडर नोंदी असलेला स्नॅपशॉट दुर्लक्षित केला जातो. विद्यमान प्रॉम्प्ट/प्रतिसाद निर्यात हेडर कॅप्चरसह
सक्षम राहते; अनुमतीसूची केवळ हेडर्ससाठी हायड्रेशन मोड पुरवत नाही.

निवडलेली मूल्ये `http.request.header.<full lowercase header name>` या OTLP स्ट्रिंग अॅरेमध्ये रूपांतरित होतात,
अगदी एकच स्ट्रिंग असली तरीही. उदाहरणार्थ, `X-OmniRoute-Meta-Team: example-team` चे रूपांतर
`http.request.header.x-omniroute-meta-team` मध्ये होते, ज्याचे मूल्य
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}` असते.
संपूर्ण उपसर्ग जतन केला जातो: हे सामान्य हेडर्स आहेत; त्यांच्यावर कोणतेही व्यवसाय-फील्ड पार्सिंग किंवा
`omniroute.metadata.*` / Langfuse मेटाडेटा रूपांतरण केले जात नाही. `langfuseMapping` हेडरच्या
अर्थामध्ये बदल करत नाही. निवडलेला एकल-मूल्याचा `User-Agent` मानक स्केलर
`user_agent.original` देखील सेट करतो. एका मूल्यातील स्वल्पविरामांवरून मूल्य विभाजित केले जात नाही. अक्षरांच्या मोठ्या-लहान रूपांतील भेद जतन केलेल्या
नोंदींच्या क्रमाने एकत्र केले जातात; कोणताही भेद अवैध असल्यास तो संपूर्ण हेडर वगळला जातो. अॅट्रिब्यूट्स लहान अक्षरांतील नावानुसार क्रमबद्ध केले जातात.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, API-की हेडर्स, नावांमध्ये
auth/token/secret/password/credential निर्देशक असलेले हेडर्स आणि अंतर्गत गेटवे क्रेडेन्शियल्स नेहमी
वगळले जातात, जरी ते निवडलेले असले किंवा स्टोरेजमध्ये अंशतः लपवलेले असले तरीही. ज्ञात क्रेडेन्शियल नमुन्यांसाठी
सामायिक क्रेडेन्शियल शोधक पुन्हा वापरला जातो; माहिती लपवल्याचे निर्देशक वगळले जातात, सुरक्षित मूल्ये म्हणून निर्यात केले जात नाहीत.
फक्त स्ट्रिंग्स आणि रिक्त नसलेले स्ट्रिंग अॅरे स्वीकारले जातात; संख्या किंवा ऑब्जेक्ट्सचे सक्तीने रूपांतरण केले जात नाही.
अवैध नावे, प्रोटोटाइप की, नियंत्रण वर्ण (आडवा टॅब वगळता) आणि चुकीच्या स्वरूपातील Unicode
बॅच अयशस्वी न करता किंवा त्रुटींमध्ये त्यांचा मजकूर न दाखवता दुर्लक्षित केले जातात.

प्रत्येक स्पॅन जास्तीत जास्त 32 हेडर्स, प्रत्येक हेडरमागे 16 मूल्ये, प्रत्येक मूल्यामागे 4096 UTF-8 बाइट्स,
आणि कॅप्चर केलेल्या हेडर नावांमध्ये व मूल्यांमध्ये मिळून एकूण 16384 UTF-8 बाइट्स कॅप्चर करतो. मर्यादेपेक्षा मोठे/अवैध हेडर्स
पूर्णपणे वगळले जातात, कापले जात नाहीत. निवड हा ऑपरेटरचा गोपनीयतेविषयक निर्णय आहे: सुरक्षित वाटणाऱ्या नावांमध्येही
वैयक्तिक डेटा असू शकतो, आणि या मर्यादा/शोधक हे सर्वसाधारण PII काढून टाकण्याचे साधन नाहीत.

### वितरण मर्यादा

विनंत्या एन्व्हलपसह 500 स्पॅन्स आणि 4 MiB UTF-8 JSON पर्यंत मर्यादित असतात.
कर्सर बॅचच्या पहिल्या विनंतीपूर्वी प्रत्येक अनुमत स्पॅनचा आकार तपासला जातो. एखादा स्वतंत्र
स्पॅन मर्यादेपेक्षा मोठा असल्यास त्या बॅचचा कोणताही भाग पाठवला जात नाही आणि `maxBodyBytes`
कमी करण्याच्या मार्गदर्शनासह प्रक्रिया अयशस्वी होते; तो गुपचूप वगळला जात नाही. पूर्वतपासणीत फक्त रेकॉर्ड संदर्भ आणि
बाइट संख्या ठेवली जाते, आणि प्रत्येक तात्पुरता स्पॅन/JSON काढून टाकला जातो; बॅचची दुसरी सिरियलाइज केलेली प्रत
ठेवण्याऐवजी मर्यादित भागांसाठी स्पॅन्स पुन्हा तयार केले जातात. HTTP 408/429/5xx, नेटवर्क अपयश आणि टाइमआउटसाठी जास्तीत जास्त
तीन प्रयत्न केले जातात, 250/500 ms च्या घातांकीय वाढत्या विलंबासह. `Retry-After` मधील सेकंद किंवा HTTP तारखा
विलंब 5 सेकंदांपर्यंत वाढवू शकतात. इतर स्टेटस आल्यास प्रक्रिया त्वरित अयशस्वी होते. OTLP 2xx अंशतः नकार आल्यासही
हरवलेल्या स्पॅनची पोच देण्याऐवजी त्रुटी निर्माण केली जाते; रिक्त किंवा वैध JSON पोच स्वीकारल्या जातात, आणि
प्रतिसाद वाचण्याची मर्यादा 64 KiB असते.

त्रुटींमध्ये फक्त निर्यातकाच्या नियंत्रणातील तथ्ये असतात: HTTP स्टेटस, पुनर्प्रयत्न वर्ग, प्रयत्नांची आणि पाठवलेल्या स्पॅन्सची
संख्या, किंवा पोच/नेटवर्क अपयशासाठी निश्चित मजकूर. कलेक्टरच्या प्रतिसाद बॉडी,
अंशतः यशाच्या संख्या आणि प्रतिसाद हेडर्स त्रुटी, लॉग किंवा
डॅशबोर्डमध्ये कधीही कॉपी केले जात नाहीत. अयशस्वी किंवा अंशतः स्वीकारलेल्या बॅचची पोच दिली जात नाही: गंतव्य त्या स्टेटससह
अयशस्वी स्थिती दाखवते, कर्सर शेवटच्या पोच दिलेल्या बॅचवर राहतो, आणि पुढील रनमध्ये
त्याच ओळी पुन्हा पाठवल्या जातात. कलेक्टर किंवा कॉन्फिगरेशन
दुरुस्त होईपर्यंत कायमस्वरूपी स्टेटसमुळे प्रक्रिया अयशस्वी होत राहते. प्रतिसादाच्या तपशीलांसाठी कलेक्टरचे स्वतःचे लॉग वापरा. कॉल-लॉग त्रुटी सारांशांमध्ये
त्यांचे स्वतंत्र माहिती-लपवणे कायम राहते.
`prepare()` कोणतीही संसाधने तयार करत नाही; चाचणी नेमके `{"resourceSpans":[]}` पोस्ट करते आणि
कॉल-लॉग स्पॅन्स न लिहिता HTTP स्टेटस कळवते.

ट्रेस आयडी आणि स्पॅन आयडी हे अनुक्रमे
`"omniroute.trace\\0" + callLogId` आणि `"omniroute.span\\0" + callLogId` यांच्या SHA-256 मधील पहिले 32/16 हेक्स अंक असतात. पुन्हा पाठवताना
तेच आयडी वापरले जातात. ही डुप्लिकेट नोंदी टाळण्याची हमी नाही: Langfuse
v4 इनजेशनसह काही बॅकएंड समान आयडीच्या स्पॅन्समधील डुप्लिकेट नोंदी काढून टाकत नाहीत. क्रॅश किंवा एखादा भाग अंशतः अयशस्वी झाल्यास
जास्तीत जास्त पोच न दिलेली एक कर्सर बॅच पुन्हा पाठवली जाऊ शकते; ती संपूर्ण बॅच डुप्लिकेट होऊ शकते,
फक्त तिचा शेवटचा HTTP भाग नव्हे. ही तडजोड लक्षात घेऊन कर्सर बॅचचा आकार निवडा.

### Langfuse उदाहरण

स्वतः होस्ट केलेल्या Langfuse इन्स्टन्ससाठी ही फील्ड्स कॉन्फिगर करा:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

अक्षरशः `public-key:secret-key` स्ट्रिंगचे Base64 रूपांतर करून Authorization मूल्य स्थानिकरीत्या तयार करा
(उदाहरणार्थ `Buffer.from(publicKey + ":" + secretKey).toString("base64")` वापरून).
खरी क्रेडेन्शियल्स लॉग, स्क्रीनशॉट किंवा इश्यूंमध्ये पेस्ट करू नका. मॅपिंग आपोआप
`x-langfuse-ingestion-version: 4` सेट करते; Authorization तरीही `headers` मध्ये दिले जाते.
हेडर्स आणि तयार केलेले ओळख सॉल्ट दोन्ही विद्यमान एन्क्रिप्ट केलेल्या गुप्त-फील्डची
यंत्रणा आणि API प्लेसहोल्डर्स वापरतात; `STORAGE_ENCRYPTION_KEY` आवश्यक आहे.

मॅपिंगमध्ये जनरेशन प्रकार/मॉडेल, JSON वापर तपशील (इनपुट/आउटपुट/एकूण आणि उपलब्ध
कॅश की), JSON इनपुट/आउटपुट स्नॅपशॉट, ERROR/DEFAULT स्तर, संवेदनशील माहिती काढलेला स्थिती संदेश,
ट्रेस नाव, सत्र आयडी, पर्यायी एन्व्हायर्नमेंट आणि प्रदाता, विनंती केलेले मॉडेल, पाथ, कॉम्बो, कॅश
स्रोत आणि स्थिती यांसाठी फिल्टर करता येणारे `langfuse.observation.metadata.<key>` जोडले जाते.
`langfuse.observation.completion_start_time` हे ISO 8601 स्वरूपात
प्रारंभ + TTFT असते, पण फक्त TTFT ज्ञात असेल आणि कालावधीच्या आत असेल तेव्हाच. खर्चाचे कोणतेही अॅट्रिब्यूट पाठवले जात नाहीत.

ओळख मोड `langfuse.user.id` ला लागू होतात:

- `pseudonymous` (डीफॉल्ट): प्रत्येक डेस्टिनेशनसाठी यादृच्छिक
  32-बाइट सॉल्ट वापरून API कीच्या अंतर्गत आयडीचे HMAC-SHA256. सॉल्ट नसल्यास तो निर्मितीवेळी तयार केला जातो,
  `identitySalt` म्हणून एन्क्रिप्ट केला जातो, कधीही परत दिला जात नाही आणि संपादनादरम्यान कायम ठेवला जातो. मूळ की आयडी कधीही
  स्पॅन अॅट्रिब्यूटमध्ये ठेवले जात नाहीत. डेस्टिनेशनचा सॉल्ट पुन्हा तयार केल्याने/बदलल्याने ओळखी बदलतात.
- `keyName`: कॉन्फिगर केलेले API कीचे नाव; यामुळे ऑपरेटरचे ते लेबल जाणीवपूर्वक उघड केले जाते.
- `none`: वापरकर्ता आयडी नाही. सत्र टॅग उपस्थित असल्यास तरीही निर्यात केले जातात; हे मोड
  कोणत्याही प्रॉम्प्टमधील मजकूर किंवा ऑपरेटरने दिलेली सत्र/परस्परसंबंध लेबले अनामिक करत नाहीत.

### बॅकफिलशिवाय सुरुवात करणे

फक्त निर्मितीवेळी, **सध्याच्या स्थानापासून सुरुवात करा (विद्यमान लॉग वगळा)** सक्षम करा किंवा
निर्मिती API पेलोडच्या सर्वोच्च स्तरावर `startFromCurrentPosition: true` द्या. हे विद्यमान कर्सर
हेल्पर वापरून, कोणत्याही मायग्रेशनशिवाय, `cursor_row_id` ला सध्या जतन केलेल्या कॉल-लॉगमधील कमाल rowid वर
सेट करते. डीफॉल्ट false आहे (कर्सर 0 आणि जतन केलेल्या इतिहासाचे बॅकफिल).
हे अपडेटवेळी कर्सर रीसेट करण्याचे सेटिंग नाही.

सामायिक `ttftMs` जोडणीमुळे BigQuery मॅपर
आणि नवीन-टेबल स्कीमामध्ये null स्वीकारणारा `ttft_ms` स्तंभही जोडला जातो: त्याच्या स्कीमा चाचणीनुसार प्रत्येक प्रमाणित रेकॉर्ड फील्डसाठी
एक स्तंभ असणे आवश्यक आहे. विद्यमान टेबलमधून निर्यात कोणत्याही बदलाशिवाय सुरू राहते: `prepare()` टेबलचा स्कीमा वाचते आणि
तो स्तंभ नसल्यास फक्त `ttft_ms` वगळते. पुढील रनमध्ये TTFT मिळवण्यासाठी
null स्वीकारणारा INT64 स्तंभ जोडा किंवा नवीन टेबल वापरा. PATCH, स्वयंचलित स्कीमा बदल किंवा अतिरिक्त
परवानग्या आवश्यक नाहीत; इतर सर्व रो फील्डसाठी कठोर स्कीमा तपासणी कायम राहते.

## 6. गंतव्यस्थान जोडणे

1. `LogExportDestinationType` एक्सपोर्ट करणारी `src/lib/logExport/destinations/<name>.ts` फाइल तयार करा:
   एक Zod `configSchema`, UI साठी `fields` वर्णनकर्ता अ‍ॅरे, `secretFields`, आणि
   `test()` / `prepare()` / `send(records)` परत करणारे `createClient(config)`.
2. ते `src/lib/logExport/registry.ts` मधील `DESTINATIONS` अ‍ॅरेमध्ये जोडा.
3. `tests/unit/` अंतर्गत चाचण्या लिहा.

एवढाच संपूर्ण बदल आहे: कायमस्वरूपी संचयन, cron जॉब, REST स्तर, गुपितांचे एन्क्रिप्शन आणि
डॅशबोर्ड फॉर्म हे सर्व रजिस्ट्री वाचतात.

नवीन गंतव्यस्थानासाठी दोन नियम:

- अंशतः अपयश आल्यास `send()` ने **अपवाद फेकलाच पाहिजे**. यशस्वीरीत्या पूर्ण होणे म्हणजे "गंतव्यस्थानाकडे या पंक्ती आहेत",
  आणि कर्सर कायमचा त्यांच्या पुढे सरकतो.
- वापरकर्त्याने दिलेला URL स्वीकारणाऱ्या गंतव्यस्थानाने फेच करण्यापूर्वी
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) द्वारे त्याची पडताळणी केली पाहिजे,
  जशी वेबहुक्स करतात. BigQuery ला याची गरज नाही: त्याचे होस्ट स्थिर आहेत.

## 7. ते चालवणे

- **डॅशबोर्ड**: इंटिग्रेशन्स → लॉग एक्सपोर्ट. गंतव्यस्थान जोडा, पंक्ती न लिहिता क्रेडेन्शियल्स तपासण्यासाठी
  **चाचणी** चालवा, त्यानंतर ते सक्षम करा.
- **प्रलंबित नोंदी**: प्रत्येक गंतव्यस्थानाच्या कार्डवर प्रलंबित पंक्ती आणि कर्सर दिसतो; `GET
/api/log-export/status` हेच आकडे आणि मागील 20 जॉब रन परत करते.
- **एका गंतव्यस्थानाचे अपयश इतरांना अपयशी करत नाही** — रनचा सारांश प्रत्येक गंतव्यस्थानाची
  स्थिती `last_status` / `last_error` मध्ये नोंदवतो, आणि जॉब रनचा इतिहास एकत्रित माहिती ठेवतो.
- **गंतव्यस्थान हटवल्यास त्याचा कर्सरही हटतो.** ते पुन्हा जोडल्यावर सुरुवात जतन केलेल्या सर्वात जुन्या
  कॉल लॉगपासून होते, त्यामुळे गंतव्यस्थानाकडे आधीपासून असू शकणाऱ्या पंक्ती पुन्हा पाठवल्या जातात. BigQuery मध्ये प्रत्येक पंक्तीचा
  `insertId` हे केवळ BigQuery च्या स्वतःच्या डुप्लिकेट निर्मूलन कालावधीतच हाताळतो, म्हणून गंतव्यस्थान हटवण्याऐवजी
  ते अक्षम करण्यास प्राधान्य द्या.
