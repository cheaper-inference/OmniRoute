## चॅट पूर्णता

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "यासाठी फंक्शन लिहा..."}
  ],
  "stream": true
}
```

### सानुकूल हेडर्स

| हेडर                     | दिशा     | वर्णन                                                                                                                                                                                                                         |
| ------------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | विनंती   | कॅशे टाळण्यासाठी `true` वर सेट करा                                                                                                                                                                                            |
| `x-omniroute-no-memory`  | विनंती   | या विनंतीसाठी मेमरी + कौशल्य अंतःक्षेपण वगळण्यासाठी `true` वर सेट करा (नो-कॅशेसारखेच; प्रत्येक कॉलचा टोकन/खर्च ओव्हरहेड टाळते)                                                                                                |
| `X-OmniRoute-Progress`   | विनंती   | प्रगती इव्हेंट्ससाठी `true` वर सेट करा                                                                                                                                                                                        |
| `X-Session-Id`           | विनंती   | बाह्य सत्र संलग्नतेसाठी स्टिकी सत्र की                                                                                                                                                                                        |
| `x_session_id`           | विनंती   | अंडरस्कोर प्रकारही स्वीकारला जातो (थेट HTTP)                                                                                                                                                                                  |
| `X-OmniRoute-Session-Id` | विनंती   | कॉलरने दिलेला सत्र/संभाषण टॅग (मेमरीलाही पुरवला जातो). उपस्थित असल्यास, प्रत्येक सत्राच्या खर्च-वाटपासाठी `call_logs.session_tag` मध्ये जशाच्या तसा कायम ठेवला जातो (#8249) — अनुपस्थित असल्यास कधीही संश्लेषित केला जात नाही |
| `Idempotency-Key`        | विनंती   | डीडुप्लिकेशन की (5 सेकंदांची विंडो)                                                                                                                                                                                           |
| `X-Request-Id`           | विनंती   | पर्यायी डीडुप्लिकेशन की                                                                                                                                                                                                       |
| `x-omniroute-connection` | विनंती   | एकल-मॉडेल विनंती तिच्या id द्वारे एका प्रदाता कनेक्शनला (खाते) पिन करा — [प्रति विनंती खाते पिनिंग](#account-pinning-per-request) पहा                                                                                         |
| `X-OmniRoute-Cache`      | प्रतिसाद | `HIT` किंवा `MISS` (नॉन-स्ट्रीमिंग)                                                                                                                                                                                           |
| `X-OmniRoute-Idempotent` | प्रतिसाद | डीडुप्लिकेट केले असल्यास `true`                                                                                                                                                                                               |
| `X-OmniRoute-Progress`   | प्रतिसाद | प्रगती ट्रॅकिंग सुरू असल्यास `enabled`                                                                                                                                                                                        |
| `X-OmniRoute-Session-Id` | प्रतिसाद | OmniRoute ने वापरलेला प्रभावी सत्र ID                                                                                                                                                                                         |
| `X-OmniRoute-Request-Id` | प्रतिसाद | विनंती सहसंबंध id (माहित असल्यास)                                                                                                                                                                                             |
| `X-OmniRoute-Version`    | प्रतिसाद | OmniRoute बिल्ड आवृत्ती (नेहमी उपस्थित)                                                                                                                                                                                       |
| `X-OmniRoute-Cost-Saved` | प्रतिसाद | HIT वर कॅशेमुळे वाचलेले USD (केवळ कॅशे हिट्स)                                                                                                                                                                                 |
| `X-OmniRoute-Decision`   | प्रतिसाद | राउटिंग ट्रेस: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` हे कॉम्बो धोरण आहे किंवा नॉन-कॉम्बो विनंतीसाठी `single`) — पूर्णता प्रतिसादांमध्ये नेहमी उपस्थित                                                 |

> Nginx टीप: तुम्ही अंडरस्कोर हेडर्सवर (उदाहरणार्थ `x_session_id`) अवलंबून असल्यास, `underscores_in_headers on;` सक्षम करा.

#### प्रति विनंती खाते पिनिंग

जेव्हा एखाद्या प्रदात्याकडे अनेक कनेक्शन्स (खाती किंवा कीज) असतात, तेव्हा OmniRoute सामान्यतः त्याच्या खाते-निवड धोरणाद्वारे एक निवडते.
त्याऐवजी विनंती `x-omniroute-connection` हेडर वापरून एक विशिष्ट कनेक्शन पिन करू शकते:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <तुमची OmniRoute API की>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "नमस्कार"}]}'
```

- **id कुठे शोधायचा.** डॅशबोर्डमध्ये प्रदात्याचे पृष्ठ उघडा
  (**डॅशबोर्ड → प्रदाते → <provider>**) आणि कनेक्शनच्या ओळीवरील `xxxxxxxx…` id चिपवर क्लिक करा
  — यामुळे संपूर्ण कनेक्शन id कॉपी होतो.
- **कोणत्या विनंत्या त्याचा मान राखतात.** `/v1/chat/completions`,
  `/v1/messages` आणि `/v1/responses` वरील एकल-मॉडेल विनंत्या (`provider/model`). कॉम्बो हेडरकडे दुर्लक्ष करतात:
  त्याऐवजी प्रत्येक कॉम्बो टप्प्यासाठी त्या टप्प्याच्या स्वतःच्या कनेक्शनद्वारे खाते पिन करा.
- **पिन कठोर आहे, केवळ प्राधान्य नाही.** पिन केलेले कनेक्शनच विशेषतः वापरले जाते. विनंतीमध्ये
  बिघाड झाल्यास खात्याचा कूलडाउन नोंदवला जातो, परंतु त्याच प्रदात्याच्या
  दुसऱ्या खात्याकडे **रोटेट केले जात नाही**.
- **कूलडाउन आणि कोटा पिन सोडवतात.** पिन केलेले कनेक्शन कूलडाउनमध्ये असताना,
  त्याचा कोटा संपलेला असताना किंवा कोटा धोरणामुळे ते ब्लॉक झालेले असताना, नंतरच्या विनंत्या पिन न केलेल्या ट्रॅफिकप्रमाणेच
  प्रदात्याच्या इतर कनेक्शनवर फॉलबॅक होतात.
- **अज्ञात किंवा अक्षम केलेले ids अयशस्वी होतात.** प्रदात्याच्या सक्रिय पूलमध्ये नसलेल्या id मुळे (हटवलेला,
  निष्क्रिय केलेला किंवा दुसऱ्या प्रदात्याशी संबंधित) कोणतेही पात्र खाते शिल्लक राहत नाही, त्यामुळे विनंती
  इतरत्र गुप्तपणे रूट होण्याऐवजी अयशस्वी होते.

Claude Code हे `ANTHROPIC_CUSTOM_HEADERS` द्वारे कस्टम हेडर्स पाठवते. प्रत्येक प्रकल्पासाठी वेगळे
खाते पिन करण्यासाठी ते `~/.claude/settings.json` मधील `env` ब्लॉकमध्ये किंवा प्रकल्प-स्तरीय
`.claude/settings.json` मध्ये ठेवा:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

स्रोत: `src/sse/handlers/chat.ts` (हेडर वाचन), `src/sse/services/auth.ts` आणि
`src/sse/services/sessionAffinityPin.ts` (पिन सोडणे आणि पूलमध्ये नसल्याची तपासणी).

> **खर्च टेलिमेट्री हेडर्स:** नॉन-स्ट्रीमिंग यशस्वी प्रतिसादांमध्ये `X-OmniRoute-*` खर्च-टेलिमेट्री संचही असतो — `X-OmniRoute-Response-Cost` (USD, निश्चित 10 दशांश स्थाने; विनामूल्य/किंमत उपलब्ध नसल्यास `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` आणि `X-OmniRoute-Fallback-Attempts` (केवळ > 0 असताना), तसेच `X-OmniRoute-Request-Id` आणि `X-OmniRoute-Version`. हे chat completions, `/v1/responses`, `/v1/messages` **आणि मीडिया एंडपॉइंट्सद्वारेही** उत्सर्जित केले जातात — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` आणि `/v1/moderations` (खर्च नेहमी `0`). किंमत उपलब्ध असताना मीडिया खर्च प्रत्येक मोडॅलिटीनुसार (प्रति-प्रतिमा, प्रति-सेकंद, प्रति-अक्षर, प्रति शोध-युनिट) मोजला जातो; अन्यथा तो `0` असतो (fail-open).

> **कॅश-हिट खर्चाचे अर्थनिर्णयन:** semantic-cache HIT (`X-OmniRoute-Cache-Hit: true`) वर कोणताही अपस्ट्रीम कॉल केला जात नाही, त्यामुळे `X-OmniRoute-Response-Cost` हा `0.0000000000` असतो (हिट सर्व्ह करण्याचा **वाढीव** खर्च). मूळ/झाला असता असा खर्च `X-OmniRoute-Cost-Saved` मध्ये स्वतंत्रपणे नोंदवला जातो. बिलिंग ग्राहकांनी `X-OmniRoute-Response-Cost` ची बेरीज करावी (हिटसाठी काहीही खर्च येत नाही); कॅश विश्लेषणासाठी `X-OmniRoute-Cost-Saved` एकत्रित करता येतो.

## एक्सक्लुझिव्ह मॅनेज्ड सेशन लीज

एक्सक्लुझिव्ह मॅनेज्ड सेशन लीजिंग हा एक ऑप्ट-इन, क्लायंट-न्यूट्रल राउटिंग करार आहे: एक सक्रिय मालक एक पात्र OmniRoute कनेक्शन धारण करतो. याला मॉडेल लीज करण्याची, OAuth ची आवश्यकता नाही, विशिष्ट क्लायंट ओळखण्याची किंवा विशिष्ट प्रदात्याची आवश्यकता नाही.

प्रमाणीकरण करणार्या API की मध्ये `lease:exclusive` स्कोप आणि एक स्पष्ट नॉन-एम्प्टी `allowedConnections` सूची असणे आवश्यक आहे. डेटाबेस म्युटेशन बाउंड्री की तयार करताना आणि आंशिक अद्यतनांवर दोन्ही फील्ड एकत्र लागू करते.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

यशस्वी अधिग्रहण, नूतनीकरण आणि प्रकाशन प्रतिसाद टाइमस्टॅम्प, `state` आणि अचूक सकारात्मक `generation` उघड करतात, परंतु निवडलेले कनेक्शन किंवा क्रेडेन्शियल्स कधीही नाही. नूतनीकरण आणि प्रकाशन JSON बॉडीमध्ये जनरेशन पुरवतात:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

एक सक्रिय लीज मालक त्याच्या सध्याच्या बाइंडिंगसाठी गोपनीयता-सुरक्षित डिस्प्ले मेटाडेटाची स्पष्टपणे विनंती करू शकतो:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

ही ऑप्ट-इन स्टेटस ॲक्शन अपारदर्शक मालक, प्रमाणीकृत व्यवस्थापित API की आणि एका डेटाबेस ट्रान्झॅक्शनमधील अचूक सक्रिय जनरेशनद्वारे संरक्षित आहे. `displayName` हे केवळ ट्रिम केलेले कॉन्फिगर केलेले कनेक्शन नाव आहे; जेव्हा कोणतेही सुरक्षित कॉन्फिगर केलेले नाव अस्तित्वात नसते तेव्हा ते `null` असते. OmniRoute कधीही ईमेल किंवा व्युत्पन्न खाते ओळख बदलत नाही. प्रदाता मूल्य एक गैर-संवेदनशील डिस्प्ले लेबल आहे आणि कधीही व्युत्पन्न सुसंगत-प्रदाता ओळखकर्ता नाही. क्रेडेन्शियल्स, टोकन, कुकीज, रॉ कनेक्शन किंवा API की आयडी, मालक हॅश, फेंसिंग सिक्रेट्स आणि अंतर्गत राउटिंग डेटा वगळले जातात.

चुकीची-की, चुकीचा-मालक, जुनी-जनरेशन, गहाळ, कालबाह्य, रिलीज केलेले आणि अवैध केलेले सर्व लुकअप कनेक्शन मेटाडेटाशिवाय समान `409 LEASE_FENCE_STALE` एरर परत करतात. ज्या क्लायंटला क्षमता-प्रतीक्षा प्रतिसाद मिळाला आहे त्याला तपासण्यासाठी कोणतेही सक्रिय बाइंडिंग नाही. जेव्हा राउटिंग सक्रिय लीजचे संक्रमण करते, तेव्हा समान जनरेशन वैध राहते आणि स्थिती अणूने नवीन बाइंडिंग परत करते, जुने कधीही नाही. विद्यमान क्लायंट अपरिवर्तित राहतात कारण अधिग्रहण, नूतनीकरण, प्रकाशन आणि प्रतीक्षा प्रतिसाद त्यांचे मागील आकार टिकवून ठेवतात.

हा सर्व्हर करार स्टॉक OpenAI Codex `/status` बदलत नाही. स्टॉक कोडेक्स सध्या त्याचा मॉडेल प्रदाता आणि अंगभूत प्रमाणीकरण/खाते स्थितीची नोंद करतो परंतु मनमानी सानुकूल प्रदाता खाते मेटाडेटा प्रस्तुत करत नाही; नंतरच्या क्लायंट एकत्रीकरणाने ही ॲक्शन कॉल करणे आवश्यक आहे आणि `connection.displayName` कसे प्रदर्शित करावे हे ठरवावे लागेल.

प्रत्येक व्यवस्थापित अनुमान विनंती नंतर दोन्ही नियंत्रण हेडर पुरवते:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

प्रत्येक समर्थित अपस्ट्रीम प्रयत्नापूर्वी अचूक मालक, जनरेशन, सक्रिय कनेक्शन आणि प्रमाणीकृत API की त्वरित संरक्षित केली जातात. दुसर्या कीसह मालक आणि जनरेशन पुन्हा प्ले करणे अयशस्वी होते जरी ती की समान कनेक्शनला परवानगी देत असेल. रॉ मालक टिकवून ठेवले जात नाहीत, लॉग केले जात नाहीत, विनंती स्नॅपशॉटमध्ये ठेवले जात नाहीत किंवा अपस्ट्रीम फॉरवर्ड केले जात नाहीत.

तात्पुरती स्पर्धा HTTP `429` `Retry-After` आणि यासह परत करते:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

या प्रतिसादाचा अर्थ असा आहे की सामान्य पात्र संच नॉन-एम्प्टी होता आणि प्रत्येक मोकळा उमेदवार परदेशी सक्रिय लीजद्वारे धारण केला गेला होता. असमर्थित मॉडेल/प्रदाते, धोरण जुळत नाही, कूलडाउन, कोटा, आरोग्य आणि इतर सामान्य पात्रता अपयश त्यांचे विद्यमान OmniRoute प्रतिसाद टिकवून ठेवतात.

### `x-omniroute-compression`

कॉम्प्रेशन योजनेची प्रति-विनंती ओव्हरराइड. सर्वोच्च प्राधान्य — राउटिंग-कॉम्बो ओव्हरराइड, सक्रिय प्रोफाइल, ऑटो-ट्रिगर आणि पॅनेल डिफॉल्टला हरवते. मूल्ये:

| मूल्य         | परिणाम                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `off`         | या विनंतीसाठी कॉम्प्रेशन नाही.                                                                      |
| `default`     | पॅनेल-व्युत्पन्न डिफॉल्ट प्रोफाइल (सक्रिय प्रोफाइलकडे दुर्लक्ष करते). लॉसलेस इंजिन बंद ठेवले जातात. |
| `safe`        | केवळ डेडअप आणि व्हाईटस्पेस फोल्डिंग.                                                                |
| `allow-lossy` | सारांश आणि शैली पुनर्लेखनांसह या विनंतीसाठी ऑपरेटर योजना ठेवा.                                      |
| `engine:<id>` | सक्षम असताना एकच इंजिन, उदा. `engine:rtk`. त्या इंजिनसाठी प्रति-विनंती ऑप्ट-इन.                     |
| `<combo>`     | एक नामांकित कॉम्बो, प्रथम नावाने (केस-असंवेदनशील), नंतर आयडीने जुळवला जातो.                         |

टिपा:

- अज्ञात मूल्ये दुर्लक्षित केली जातात (विनंती कधीही नाकारली जात नाही); रिझोल्यूशन सामान्य ऑपरेटर प्राधान्याकडे जाते.
- जर अनेक कॉम्बो समान नाव सामायिक करत असतील, तर निश्चित जुळणीसाठी कॉम्बो **आयडी** पास करा.
- ज्या कॉम्बोचे नाव `off` किंवा `default` आहे ते नावाने निवडले जाऊ शकत नाही (ते कीवर्ड प्रथम इंटरप्रिट केले जातात); अशा कॉम्बोचा त्याच्या आयडीने संदर्भ घ्या.
- मास्टर कॉम्प्रेशन स्विच एक हार्ड गेट आहे: जेव्हा कॉम्प्रेशन जागतिक स्तरावर अक्षम केले जाते, तेव्हा हे हेडर ते सक्षम करू शकत नाही.

लागू केलेली योजना प्रतिसाद हेडरमध्ये परत दिली जाते:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

जिथे `<source>` हे `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, किंवा `off` यापैकी एक आहे.

## एम्बेडिंग्ज

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

उपलब्ध प्रदाते: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

कॅटलॉग आयडी `provider/model` स्वरूपात असतात (उदाहरण: `jina-ai/jina-embeddings-v5-omni-small`). रजिस्ट्रीमध्ये दिसणारे केवळ Jina मॉडेल आयडी (उदाहरणार्थ `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) देखील रिझॉल्व्ह होतात. Jina embed/rerank/classify/segment सर्वप्रथम डॅशबोर्डवरील `jina-ai` क्रेडेन्शियल्स वापरतात; डॅशबोर्ड की अस्तित्वात नसल्यासच `JINA_AI_API_KEY` फॉलबॅक म्हणून वापरली जाते. `jina-reader` कार्ड केवळ Reader / `r.jina.ai` साठी आहे (`POST /v1/web/fetch`) आणि ते कधीही एम्बेडिंग्ज किंवा रीरँक पुरवत नाही.

मल्टिमोडल समर्थन जाहीर करणारी रजिस्ट्री मॉडेल्स कमाल 32 प्रदाता-निरपेक्ष संरचित
आयटमदेखील स्वीकारतात. मीडिया आयटमचे प्रकार `text`, `image`, `audio`, `video`, आणि `document` आहेत. त्यांचा मीडिया `source`
एकतर `{"type":"url","url":"https://..."}` किंवा
`{"type":"base64","data":"...","media_type":"..."}` असतो.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
आणि फॅमिली उपनाव `jina-ai/jina-embeddings-v5-omni` → omni-small) Jina चे मूळ
EmbeddingsV5Request दस्तऐवजदेखील स्वीकारते आणि ते `https://api.jina.ai/v1/embeddings` कडे **कोणताही बदल न करता फॉरवर्ड करते**:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    {
      "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }]
    }
  ]
}
```

मूळ `{ image | audio | video | pdf }` मूल्ये सार्वजनिक HTTPS URL, `data:` URI किंवा रॉ
base64 असू शकतात. OmniRoute त्या ऑब्जेक्ट्सना स्ट्रिंगमध्ये रूपांतरित करत नाही किंवा मूळ इमेज URL फेच करत नाही — Jina
सार्वजनिक मीडिया स्वतः प्राप्त करते. अतिरिक्त Jina फील्ड्स (`task`, `normalized`, `truncate`, `embedding_type`)
फॉरवर्ड केली जातात. केवळ मजकूर समर्थित करणारे Jina SKU अजूनही मजकूर नसलेले दस्तऐवज नाकारतात.

सुरक्षा आणि ट्रान्सपोर्ट मर्यादा:

- रिमोट मीडिया URL सार्वजनिक HTTPS असणे आवश्यक आहे. कॅनॉनिकल `{type,source:url}` आयटम
  सर्व्हरच्या बाजूने फेच केले जातात (रीडायरेक्टचे पुनर्वैधीकरण, टाइमआउट, आकारमर्यादा, सार्वजनिक DNS, कनेक्शन पिनिंग) आणि
  प्रदात्याला कॉल करण्यापूर्वी इनलाइन केले जातात. Jina-मूळ `{image:"https://..."}` आयटम
  त्याच सार्वजनिक-HTTPS तपासणीनंतर जसेच्या तसे फॉरवर्ड केले जातात; Jina URL फेच करते.
- इनलाइन base64 मीडिया प्रत्येक आयटमसाठी डीकोड केल्यानंतर 8 MiB आणि संपूर्ण विनंतीमध्ये डीकोड केल्यानंतर एकूण 16 MiB पर्यंत मर्यादित आहे.

प्रदात्यानुसार रूपांतरण (कॅनॉनिकल आयटम कधीही बदल न करता फॉरवर्ड केले जात नाहीत):

- Jina मल्टिमोडल मॉडेल्स: प्रत्येक उच्च-स्तरीय आयटम हा एक मोडॅलिटी-की असलेला ऑब्जेक्ट बनतो
  (`text` / `image` / `audio` / `video` / `pdf`), ज्यामध्ये इनलाइन मीडियासाठी डेटा URI वापरले जातात; प्रत्येक
  उच्च-स्तरीय आयटमसाठी एक व्हेक्टर.
- Gemini Embedding 2 फॅमिली: एक उच्च-स्तरीय ॲरे हे `content.parts` (`text` किंवा `inline_data`) असलेले एकच मूळ
  `models/{model}:embedContent` विनंतीरूप बनते.
- llama.cpp (`llama-cpp/<model>`, स्थानिक सर्व्हरने लोड केलेले कोणतेही मॉडेल): कॅनॉनिकल `text` आयटम
  साध्या स्ट्रिंग्जमध्ये रूपांतरित होतात आणि `image` / `audio` / `video` हे प्रत्येकी एका
  `{"content": [part]}` ऑब्जेक्टमध्ये रूपांतरित होतात; यासाठी llama-server चे चॅट कंटेंट पार्ट्स (`image_url`,
  `input_audio` सह स्वरूप `wav` / `mp3` / `flac`, `input_video`) आणि इनलाइन डेटा वापरला जातो; प्रत्येक उच्च-स्तरीय
  आयटमसाठी एक व्हेक्टर. सर्व्हर `--embedding --mmproj …` सह चालणे आवश्यक आहे; प्रोजेक्टरशिवाय तो
  मीडिया स्वतःच नाकारतो. `document` समर्थित नाही.
- स्पष्ट मोडॅलिटी मेटाडेटा नसलेली अज्ञात/डायनॅमिक मॉडेल्स HTTP 400 सह संरचित इनपुट नाकारतात.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

असमर्थित मॉडेल/मोडॅलिटी संयोजनांमध्ये आयटमचे जबरदस्तीने रूपांतरण करण्याऐवजी HTTP 400 परत केले जाते. जुन्या स्ट्रिंग/टोकन विनंत्यांमधील इनपुटशी संबंधित नसलेली
एक्स्टेन्शन फील्ड्स कोणताही बदल न करता पुढे पाठवली जातात.

```bash
# सर्व एम्बेडिंग मॉडेल्सची सूची दाखवा
GET /v1/embeddings
```

## प्रतिमा निर्मिती

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "पर्वतांवरील एक सुंदर सूर्यास्त",
  "size": "1024x1024"
}
```

उपलब्ध प्रदात्यांमध्ये OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (स्थानिक), ComfyUI (स्थानिक) यांचा समावेश आहे.

`n`, `data[]` मध्ये `n` प्रतिमा परत करते. ज्या प्रदात्यांची अपस्ट्रीम API प्रत्येक कॉलसाठी एक प्रतिमा परत करते
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), त्यांच्यासाठी `n` स्वतंत्र अपस्ट्रीम कॉल केले जातात आणि एका वेळी जास्तीत जास्त 4 कॉल सुरू असतात. निश्चित
`seed` मध्ये कॉल निर्देशांकानुसार वाढ केली जाते (`seed`, `seed + 1`, …), त्यामुळे प्रतिमा वेगळ्या असतात, परंतु त्यांची
पुनरुत्पादकता कायम राहते. `n` ची कमाल मर्यादा 10 आहे. कोणताही कॉल अयशस्वी झाल्यास संपूर्ण विनंती
अयशस्वी होते. फॅन-आउट स्वरूपांची सूची `open-sse/handlers/imageGeneration/fanOut.ts`
मधील `SINGLE_IMAGE_FANOUT_FORMATS` आहे.

ZenMux विद्यमान API-की कनेक्शनचा पुनर्वापर करते आणि `zenmux/` किंवा `zm/` उपसर्ग स्वीकारते:

- `zenmux/openai/gpt-image-2`, ZenMux चे OpenAI Images API वापरते. पर्यायांमध्ये `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background`, आणि `response_format` यांचा समावेश आहे.
- `zm/meta/muse-image-1.0` सारखे इतर प्रकाशक ZenMux चे Vertex AI `:predict`
  एंडपॉइंट वापरतात. `n` चे मॅपिंग `sampleCount` शी, `aspect_ratio` चे `aspectRatio` शी, आणि `image_size`
  (`1K`, `2K`, `4K`) चे `sampleImageSize` शी केले जाते. पिक्सेलमधील `size` केवळ आस्पेक्ट रेशो पुरवते,
  हमीशीर पिक्सेल परिमाणे नाही. समर्थित गुणोत्तरे, रिझोल्यूशन आणि संख्या मॉडेलनुसार बदलतात.
- `zm/inclusionai/ming-image-0.1-design` स्वतःची परिमाणे निवडते. `size`,
  `aspect_ratio`, आणि `image_size` वगळा; स्पष्टपणे दिलेल्या मूल्यांमुळे HTTP 400 परत येते. `output_format` वापरून PNG, JPEG, आणि WebP
  ची विनंती केली जाऊ शकते.

हे एकत्रीकरण मजकुरावरून प्रतिमा निर्मितीला समर्थन देते, संदर्भ-प्रतिमा संपादनाला नाही. Vertex
आउटपुट `data[].b64_json` मध्ये सामान्यीकृत केले जाते; `response_format: "url"` अपस्ट्रीम
HTTPS URL परत करते किंवा केवळ प्रतिमा बाइट्स उपलब्ध असल्यास base64 डेटा URL परत करते. रिक्त/फिल्टर केलेले आउटपुट
रिक्त यशस्वी प्रतिसादाऐवजी त्रुटी परत करतात. मॉडेलचा प्रवेश ZenMux खात्यावर अवलंबून असतो.
[ZenMux चे Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) आणि
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) पहा.

```bash
# सर्व प्रतिमा मॉडेल्सची सूची दाखवा
GET /v1/images/generations
```

## दस्तऐवज OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`, `provider/model` उपसर्गाद्वारे OCR प्रदाता निवडते; केवळ मॉडेल आयडी (उदा.
`mistral-ocr-latest`) दिल्यास तो त्याच्या नोंदणीकृत प्रदात्याशी जुळवला जातो आणि `model` वगळल्यास
डीफॉल्ट म्हणून Mistral (`mistral-ocr-latest`) वापरले जाते. नोंदणीकृत प्रदाते (`open-sse/config/ocrRegistry.ts`):

| प्रदाता आयडी                  | मॉडेल आयडी           | `model` मूल्य                                                  | टिपा                                                                                                      |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (किंवा केवळ `mistral-ocr-latest`) | समकालिक — एकाच अपस्ट्रीम कॉलमधून प्रतिसाद थेट परत केला जातो.                                              |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | असमकालिक अपस्ट्रीम (`analyze` + पोलिंग) — खाली पहा.                                                       |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | समकालिक, Vertex AI च्या `openapi/chat/completions` भागीदार एंडपॉइंटद्वारे — प्रमाणीकरण/URL साठी खाली पहा. |

तिन्ही प्रदाते समान Mistral-स्वरूपाच्या बॉडीमध्ये प्रतिसाद देतात:

```json
{
  "pages": [{ "index": 0, "markdown": "# काढलेला मजकूर..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence पोलिंग प्रवाह

Azure Document Intelligence चे `analyze` API असमकालिक आहे: प्रारंभिक विनंती बॉडीऐवजी
`Operation-Location` हेडर परत करते आणि निकालासाठी पोलिंग करावे लागते. हँडलर
(`open-sse/handlers/ocr.ts`) त्या URL वर दर सेकंदाला, जास्तीत जास्त 30 प्रयत्नांपर्यंत पोलिंग करतो; `ok` नसलेला पोल प्रतिसाद किंवा `"failed"` स्थिती आल्यास तो त्वरित अयशस्वी होतो (पोलिंग
सुरू ठेवत नाही) आणि प्रयत्नांची मर्यादा संपल्यानंतरही प्रक्रिया सुरू असल्यास `504` परत करतो.
कॉलरला परत करण्यापूर्वी अंतिम Azure प्रतिसाद Mistral द्वारे वापरल्या जाणाऱ्या त्याच
`pages`/`markdown` स्वरूपात सामान्यीकृत केला जातो, त्यामुळे क्लायंट कोडला प्रदात्यासाठी वेगळे प्रकरण हाताळण्याची आवश्यकता नसते.

### Vertex AI DeepSeek OCR प्रमाणीकरण आणि एंडपॉइंट निराकरण

`vertex-deepseek-ocr`, चॅट/प्रतिमा ट्रॅफिकसाठी OmniRoute आधीपासून समर्थित करत असलेले तेच Vertex AI प्रमाणीकरण पुन्हा वापरते
(`open-sse/executors/vertex.ts`): कनेक्शनची API की ही एकतर
Service Account JSON क्रेडेन्शियल असते (JWT-bearer प्रवाहाद्वारे अल्पकालीन OAuth ॲक्सेस टोकनसाठी अदलाबदल केलेली)
किंवा आधीच तयार केलेले OAuth ॲक्सेस टोकन असते, जे जसेच्या तसे वापरले जाते. अपस्ट्रीम एंडपॉइंट URL हा Vertex चा
सर्वसाधारण `openapi/chat/completions` भागीदार एंडपॉइंट आहे, जो कनेक्शनच्या प्रकल्प आणि
प्रदेशावरून तयार केला जातो — स्पष्टपणे दिलेले `providerSpecificData.project`/`providerSpecificData.region` नेहमी प्राधान्य घेते;
अन्यथा प्रकल्प Service Account JSON मधील `project_id` वरून निर्धारित केला जातो आणि प्रदेशासाठी
डीफॉल्ट मूल्य `us-central1` असते. दोन्ही निराकरणे `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) मध्ये होतात आणि `handleOcr` कडे पाठवण्यापूर्वी
`src/app/api/v1/ocr/route.ts` द्वारे वापरली जातात.

## मॉडेल्सची सूची

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ सर्व चॅट, एम्बेडिंग आणि इमेज मॉडेल्स + कॉम्बोज OpenAI स्वरूपात परत करते
```

### मॉडेल आयडी उपसर्ग (`?prefix=`)

बहुतेक मॉडेल्स **प्रदाता उपसर्गा**अंतर्गत दर्शविली जातात. तुम्हाला कोणता उपसर्ग मिळतो हे
`MODELS_CATALOG_PREFIX_MODE` फीचर फ्लॅगद्वारे नियंत्रित केले जाते आणि क्वेरी पॅरामीटर वापरून
**प्रत्येक विनंतीसाठी** ओव्हरराइड करता येते — इतर सर्वांसाठी सर्व्हर-व्यापी सेटिंग न बदलता
स्वच्छ सूची हवी असलेल्या क्लायंटसाठी हे उपयुक्त आहे:

```bash
GET /v1/models?prefix=alias        # प्रत्येक मॉडेलसाठी एक आयडी — लघु उपनाव उपसर्ग
GET /v1/models?prefix=dual         # दोन्ही स्वरूपे (सर्व्हर डीफॉल्ट)
GET /v1/models?prefix=canonical    # केवळ पूर्ण provider-id उपसर्ग
```

| मोड         | उत्सर्जित मूल्ये                                          | टिपा                                                                                                                                                                                                |
| ----------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **आणि** `claude/claude-sonnet-4-6` | **डीफॉल्ट.** दोन्ही आयडी समान मॉडेलकडे रूट होतात; दोन्हीपैकी कोणतेही स्वरूप हार्डकोड केलेली क्लायंट कॉन्फिगरेशन कार्यरत राहावीत म्हणून हे ठेवले आहे. यामुळे कॅटलॉगचा आकार साधारणपणे दुप्पट होतो.    |
| `alias`     | `cc/claude-sonnet-4-6`                                    | प्रत्येक मॉडेलसाठी एक नोंद. वेगळे उपनाव नसलेले प्रदातेदेखील त्यांची नोंद उत्सर्जित करतात, त्यामुळे काहीही गमावले जात नाही.                                                                          |
| `canonical` | `claude/claude-sonnet-4-6`                                | पूर्ण provider-id उपसर्गाअंतर्गत प्रत्येक मॉडेलसाठी एक नोंद. वेगळे उपनाव नसलेले प्रदाते (उदा. `antigravity/…`, `agy/…`) येथेही त्यांचा एकमेव आयडी उत्सर्जित करतात, त्यामुळे काहीही गमावले जात नाही. |

क्वेरी पॅरामीटरशिवायही `dual`-मोड मिरर ओळखता येतो: त्यामध्ये प्राथमिक आयडीकडे निर्देश करणारे
`parent` फील्ड असते.

मॉडेल निवडक रेंडर करणाऱ्या क्लायंट्सनी `?prefix=alias` ची विनंती करावी —
[OmniCopilot VS Code एक्स्टेंशन](../guides/VSCODE-COPILOT.md) हेच करते.

### शोध फिल्टर्स (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` हे निवडीनुसार वापरता येणारे शोध फिल्टर्स स्वीकारते. यांपैकी कोणताही फिल्टर नसल्यास
प्रतिसाद बदलत नाही. हे कॉलरला आधीपासून दिसणारा कॅटलॉग संकुचित करतात (API-की परवानग्या प्रथम लागू होतात)
आणि OpenAI-शैलीतील `limit` / `after` पेजिंगपूर्वी चालतात:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # सूचीबद्ध केलेली प्रत्येक क्षमता true असणे आवश्यक
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # कॅटलॉग `type`; ते नसलेल्या ओळी `chat` असतात
GET /v1/models?q=sonnet&limit=10                           # आयडी किंवा नावावरील केस-असंवेदनशील जुळणी
```

| पॅरामीटर      | मूल्ये                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ऋणेतर पूर्णांक, `context_length` सोबत तुलना केली जाते                                               |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 वर्ण                                                                                          |

अज्ञात मूल्य किंवा ऋणेतर पूर्णांक नसलेले `min_context` (उदाहरणार्थ `1.5`) दिल्यास,
HTTP `400` परत केले जाते आणि संदेशामध्ये वैध मूल्यांची सूची दिली जाते. अंमलबजावणी:
`src/app/api/v1/models/catalogFilters.ts`.

### मॉडेल शॉर्टलिस्ट (`POST /v1/models/query`)

`POST /v1/models/query` समान कॅटलॉगमधून एक छोटी, निर्धारक सूची परत करते, ज्यामध्ये
`GET /v1/models` प्रमाणेच प्रमाणीकरण आणि प्रत्येक कीसाठीची दृश्यमानता असते:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

प्रत्येक फील्ड ऐच्छिक आहे. `capabilities` आणि `exclude` हे अॅरे किंवा स्वल्पविरामाने विभक्त केलेली स्ट्रिंग
स्वीकारतात; `max_output` ची तुलना `max_output_tokens` सोबत केली जाते. निकाल आधी `owned_by` आणि नंतर `id`
नुसार क्रमबद्ध केले जातात. `limit` चे डीफॉल्ट मूल्य `20` आहे आणि `100` पेक्षा जास्त मूल्ये `100` पर्यंत
मर्यादित केली जातात. अवैध JSON, अज्ञात फील्ड किंवा अवैध मूल्य दिल्यास HTTP `400` परत केले जाते.

### स्वतंत्रपणे लपवलेली चॅट मॉडेल्स

एखाद्या मॉडेलच्या प्रदाता पृष्ठावर ते **लपवलेले** म्हणून चिन्हांकित केले असल्यास, ते कॅटलॉगमधून वगळले जाते
आणि त्याची स्पष्टपणे विनंती केल्यावर HTTP `404` / `model_not_found` सह नाकारले जाते. या तपासणीमध्ये
प्रदाता उपनावे, सुसंगत-प्रदाता नोड उपसर्ग आणि कनेक्शन डीफॉल्ट्स यांसह निराकरण केलेला प्रदाता आणि मॉडेल
वापरले जातात. कॉम्बो लपवलेली लक्ष्ये वगळतो आणि दृश्यमान समकक्ष वापरू शकतो; अंमलबजावणीयोग्य कोणतेही
लक्ष्य उरले नाही, तर तो समान त्रुटी कोड परत करतो. मॉडेल पुन्हा दृश्यमान केल्यास तो बदल पुढील विनंतीपासून
लागू होतो. केवळ-इमेज दृश्यमानता ओव्हरराइड्स समान आयडी असलेले चॅट मॉडेल लपवत नाहीत.

ही स्वतंत्र मॉडेल सेटिंग
[मॉडेल एक्सपोजर अनुमती/नकार सूचींपासून](../routing/MODEL_EXPOSURE_LIST.md) वेगळी आहे; त्या स्पष्ट डिस्पॅच
कायम ठेवून कॅटलॉगमधील प्रदर्शन आणि स्वयंचलित-रूटिंग उमेदवार फिल्टर करतात. API-की मॉडेल परवानग्या स्वतंत्रपणे
लागू राहतात. डीफॉल्ट कॅटलॉग उपसर्ग मोड `dual` राहतो.

### विचार-विरहित मॉडेल प्रकार

विचार-क्षम Claude मॉडेल्ससाठी, `/v1/models` एक **विचार-विरहित** प्रकारही दर्शवते, ज्याच्या आयडीला `claude-3-omniroute-no-thinking/` हा उपसर्ग असतो:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

हा id निवडल्यास (उदा. नेहमी `thinking` ब्लॉक जोडणाऱ्या Claude Code कॉन्फिगरेशनमध्ये), reasoning दडपून तो पुन्हा वास्तविक `<provider>/<model>` कडे निराकरण केला जातो — `/v1/messages` पाथवर `thinking:{type:"disabled"}`, किंवा `/v1/chat/completions` पाथवर `reasoning`/`reasoning_effort` फील्ड वगळले जातात. हा व्हेरिएंट फक्त thinking ला समर्थन देणाऱ्या **आणि** `disabled` चे पालन करणाऱ्या Claude-कुटुंबातील मॉडेल्ससाठी सूचीबद्ध केला जातो (त्यामुळे, उदा. `disabled` नाकारणारी केवळ adaptive मॉडेल्स वगळली जातात). ऑपरेटर्स `ModelSpec.noThinkingAlias` द्वारे प्रत्येक मॉडेलनुसार हा व्हेरिएंट सक्तीने सुरू किंवा बंद करू शकतात.

ज्या क्लायंटना `Authorization: Bearer ...` जोडता येत नाही, त्यांच्यासाठी OmniRoute क्वेरी-स्ट्रिंग सुसंगततेद्वारे (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) किंवा खाली दस्तऐवजीकरण केलेल्या समर्पित `/api/v1/vscode/{token}/...` एंडपॉइंट्सद्वारे URL मधील API की देखील स्वीकारते.

```bash
# पुनर्क्रमांकन (क्लाउड रजिस्ट्री प्रदाता किंवा "<prefix>/<model>" स्वरूपातील OpenAI-सुसंगत प्रदाता नोड)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina वर्गीकरण (Foundation API क्रेडेन्शियल्स)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina सेगमेंटर
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina शोध (s.jina.ai; प्रदाता उपनाम: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# मॉडरेशन्स
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (किंवा विनंती केलेल्या स्वरूपाची) बॉडी परत करते
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS साठी भाषा आणि आवाज आवश्यक आहेत: `language` चे डीफॉल्ट मूल्य "en" आहे; आवाज
# नसल्यास किंवा OpenAI च्या मानक आवाजाचे नाव (alloy, nova, …) असल्यास ते "Adrian" बनते
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# प्रतिमा संपादन (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# व्हिडिओ / संगीत निर्मिती (प्रदाता-उपसर्ग असलेला मॉडेल आयडी)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **रिरँक प्रदाता नोड्स:** `POST /v1/rerank` हे `<node-prefix>/<model>` अशा स्वरूपात पत्ता दिलेल्या OpenAI-सुसंगत प्रदाता नोड्सकडेही
> (oMLX, vLLM, Infinity, गेटवेमागील TEI, …) रूट केले जाते. लूपबॅक
> नोड्स (`localhost`, `127.0.0.1`, `172.16.0.0/12`) नेहमीच पात्र असतात आणि ऑपरेटरने
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` मध्ये सूचीबद्ध केलेली होस्टनावेही पात्र असतात (उदा. `http://reranker:8080/v1`
> सारखे Docker/Compose सेवेचे नाव; यांना नेहमी थेट कॉल केला जातो, `HTTP(S)_PROXY` किंवा
> कनेक्शनच्या पिन केलेल्या प्रॉक्सीद्वारे कधीही नाही). इतर कोणत्याही
> होस्टवरील नोड्स — LAN मशीन किंवा Tailscale पीअर — केवळ तेव्हाच पात्र असतात, जेव्हा ऑपरेटर
> `RERANK_REMOTE_PROVIDER_NODES` फीचर फ्लॅग सक्षम करतो **आणि** नोडचा बेस URL प्रदात्याच्या
> आउटबाउंड URL धोरणाचे (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) पालन करतो.
> मेमरी इंजिनची रिरँक पायरी लूपबॅकवरून या रूटला कॉल करते,
> त्यामुळे हाच नियम Memory सेटिंग्जमधील `rerankProviderModel` वर लागू होतो.
>
> **स्थानिक सर्व्हरची स्वरूपे:** नोडला `<base>/v1/rerank` येथे आणि 404 आल्यास `<base>/rerank`
> (Infinity, TEI) येथे कॉल केला जातो. अपस्ट्रीम बॉडीमध्ये Cohere/OpenAI शब्दलेखन (`documents`,
> `return_documents`) आणि TEI शब्दलेखन (`texts`, `return_text`) हे दोन्ही असतात आणि अपस्ट्रीम प्रतिसाद
> Cohere एन्व्हलपमध्ये सामान्यीकृत केला जातो: TEI चे साधे `[{index, score, text}]`, हलक्या गेटवेमधून येणारे
> `{results: [{index, score}]}` आणि Voyage-शैलीतील `{data: [...]}` हे सर्व क्लायंटकडे
> `{results: [{index, relevance_score, document?}]}` या स्वरूपात परत येतात, स्कोअरनुसार क्रमबद्ध केलेले आणि `top_n` पर्यंत मर्यादित.
>
> **प्रदाता-नोड शोध:** OpenAI-सुसंगत प्रदाता नोडवरील मॉडेल्स `GET /v1/models` मध्ये
> नोड प्रिफिक्सअंतर्गत दिसतात. एंडपॉइंट मेटाडेटा नसलेल्या नोंदी (स्थानिक `/v1/models` सूचींसाठी हे सामान्य आहे)
> नोडचा `apiType` वारशाने घेतात, त्यामुळे डीफॉल्टनुसार चॅट प्रकार घेण्याऐवजी `embeddings` नोडची मॉडेल्स
> `type: "embedding"` आणि `rerank` नोडची मॉडेल्स `type: "rerank"` असतात; सिंक केलेल्या किंवा स्वतः जोडलेल्या
> नोंदीवरील स्पष्ट `supportedEndpoints` ला तरीही प्राधान्य दिले जाते.

| पद्धत  | पथ                       | वर्णन                                                                                                           |
| ------ | ------------------------ | --------------------------------------------------------------------------------------------------------------- |

**प्रमाणीकरण:** Bearer API की — `getApiKeyRequestScope` द्वारे फाइल्स प्रत्येक API कीनुसार मर्यादित केल्या जातात. एखाद्या कीला
फक्त स्वतःच्या फाइल्स पाहता, डाउनलोड करता आणि हटवता येतात; की नसलेले डॅशबोर्ड सत्र संपूर्ण
इन्स्टन्स वाचू शकते; मालक नसलेली फाइल (अनामिक किंवा डॅशबोर्ड-सत्र अपलोड) प्रत्येक
सत्रेतर कॉलरसाठी प्रतिबंधित असते. `GET /v1/files` अनामिक कॉलरला — आणि प्रदान केलेली पण
निराकरण न होणारी की असल्यासही — `REQUIRE_API_KEY=false` असतानादेखील प्रत्येक टेनंटच्या
फाइल्सची सूची दाखवण्याऐवजी `401` सह नाकारते (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523).

वेब/शोध प्रदाता अमूर्तीकरण (Tavily, Brave, Exa, Serper इ.).

| पद्धत | पथ                     | वर्णन                                                                                                         |
| ----- | ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| GET   | `/v1/search`           | संरूपित शोध प्रदाते + क्षमता सूचीबद्ध करते                                                                    |
| POST  | `/v1/search`           | शोध क्वेरी चालवते — विनंतीचा मुख्य भाग `v1SearchSchema` द्वारे प्रमाणित केला जातो, कॅशिंग/एकत्रीकरणाला समर्थन |
| GET   | `/v1/search/analytics` | प्रत्येक प्रदात्यासाठी हिट/विलंब/कॅश आकडेवारी                                                                 |

**प्रमाणीकरण:** Bearer API की (`extractApiKey` + `isValidApiKey`). शोध धोरणाची अंमलबजावणी `enforceApiKeyPolicy` द्वारे केली जाते.

### Exa आणि Tavily `provider_options`

Exa आणि Tavily प्रदाता-विशिष्ट फील्ड नामविश्व असलेल्या संग्रहातून वाचतात:
`provider_options.exa` (किंवा `provider_options["exa-search"]`) आणि `provider_options.tavily`
(किंवा `provider_options["tavily-search"]`). खालील कीच पुढे पाठवल्या जातात. प्रत्येक कीची
`open-sse/handlers/search/providerOptionsPassthrough.ts` मधील तिच्या स्वतःच्या Zod स्कीमाशी
तपासणी केली जाते आणि चुकीचा प्रकार असलेली की वगळली जाते. प्रमाणीकरण, बेस URL,
`stream` आणि `outputSchema` यांसह इतर कोणत्याही कीकडे दुर्लक्ष केले जाते. इतर प्रदात्यांकडून
वापरल्या जाणाऱ्या सपाट की (`cx`, `depth`, ...) पूर्वीप्रमाणेच कार्य करतात.

| प्रदाता | उच्च-स्तरीय फील्ड                                                                                                                                                                                                                                                                                                                                                         | नेस्टेड                                                                                                                                                           |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (सपाट मूलभूत मूल्ये), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                           | डीफॉल्ट `{ text: true, highlights: true }` वर विलीन केलेले `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` |
| Tavily  | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                 |

सामान्य फील्डना नेहमी प्राधान्य मिळते: `query`, `max_results`, `filters` (डोमेन), `country` आणि
`search_type` वरून मिळालेला विषय. Exa वर, `search_type: "news"` हे `category: "news"` कायम ठेवते.
Tavily `search_type: "finance"` (`topic: "finance"`) देखील स्वीकारते.

सामान्य `time_range` आता दोन्ही प्रदात्यांपर्यंत पोहोचतो: Exa ला `startPublishedDate` (ISO
टाइमस्टॅम्प) मिळतो आणि Tavily ला `start_date` (`YYYY-MM-DD`) मिळतो. `provider_options` मधील
स्पष्ट तारीख मॅप केलेल्या तारखेवर अधिलिखित होते.

Exa निकालांमध्ये `id`, `highlight_scores`, `summary`, `subpages`, `entities` आणि `extras` हे
`provider_raw` मध्ये कायम राहतात. Tavily निकालांमध्ये `images` आणि `favicon` कायम राहतात.

खर्चाचा हिशोब अजूनही सपाट रजिस्ट्री `costPerQuery` वापरतो. Tavily मध्ये
`search_depth: "advanced"` साठी प्रत्येक कॉलमागे अधिक क्रेडिट आकारले जाते आणि तो फरक
`usage.search_cost_usd` मध्ये प्रतिबिंबित होत नाही.

## Web Fetch API

कॉन्फिगर केलेल्या web-fetch प्रदात्यामार्फत (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) URL मधील सामग्री एक्स्ट्रॅक्ट करा.

Parallel Extract (`parallel-search`, Parallel Search सारखीच API key) केवळ Markdown
परत करते — इतर कोणत्याही `format` साठी `400` मिळतो — आणि सामग्रीची मर्यादा 100,000 वर्ण आहे. जेव्हा
लक्ष्य पृष्ठच एक्स्ट्रॅक्ट करता येत नाही, तेव्हा अपस्ट्रीम त्याची माहिती HTTP 200 मध्ये देते;
OmniRoute ती निश्चित संदेशासह `422` म्हणून दर्शवते.

| पद्धत | पाथ             | वर्णन                                                                       |
| ----- | --------------- | --------------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | URL फेच/स्क्रेप करा — बॉडीचे प्रमाणीकरण `v1WebFetchSchema` द्वारे केले जाते |

**प्रमाणीकरण:** Bearer API key (`extractApiKey` + `isValidApiKey`). धोरण `enforceApiKeyPolicy` द्वारे लागू केले जाते.

**कोटा-जागरूक फॉलबॅक (#8297):** जेव्हा स्पष्ट `provider` दिलेला नसतो, तेव्हा पूलमधून
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) निश्चित
प्राधान्यक्रमाने (fill-first) पुढे गेले जाते — दर-मर्यादित परंतु कॉन्फिगर केलेला प्रदाता
विनंती त्वरित थांबवण्याऐवजी वगळला जातो आणि पुन्हा प्रयत्न करण्यायोग्य/कोटासंबंधित अपस्ट्रीम अपयश
(HTTP 429 नेहमी; Firecrawl/Tavily/TinyFish च्या कोटा-शैलीतील मोफत स्तरांसाठी 402/403 —
Jina Reader साठी नाही आणि साध्या 400 चुकीच्या विनंतीसाठी कधीही नाही) झाल्यास विनंतीच्या वेळी
क्रेडेन्शियल असलेल्या पुढील अद्याप न वापरलेल्या प्रदात्याकडे प्रयत्न केला जातो. पूलमधील प्रत्येक प्रदाता
संपल्यावर, मागील सर्वसाधारण `400` ऐवजी एंडपॉइंट एकच `429` (`Retry-After`
हेडरसह) परत करतो. जेव्हा स्पष्ट `provider` ची विनंती केली जाते, तेव्हा
**कोणताही** मूक फॉलबॅक होत नाही — दर-मर्यादित किंवा अयशस्वी स्पष्ट
प्रदाता स्वतःची त्रुटी दर्शवतो (दर-मर्यादित असल्यास `429`, अन्यथा अपस्ट्रीम
स्थिती).

## WebSocket Streaming

```bash
GET /v1/ws?handshake=1
```

WebSocket upgrade handshake चे प्रमाणीकरण करते आणि wire protocol ची उदाहरण संदेशे (`request`, `cancel`) परत करते. प्रत्यक्ष WS frames हे Next.js route table च्या बाहेर असलेल्या समाविष्ट WS server द्वारे हाताळले जातात.

**प्रमाणीकरण:** handshake दरम्यान Bearer API key.

### WebSocket वर Responses API (केवळ codex)

```bash
# HTTP API सारखाच host:port (default 20128); connection upgrade करा:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (किंवा: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# पहिला frame response.create असलाच पाहिजे:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxy **केवळ `codex` शी** (ChatGPT
backend) जोडलेला आहे. तो API/dashboard सारख्याच port वर `/v1/responses`,
`/responses` आणि `/api/v1/responses` या paths वर ऐकतो. पहिल्या `response.create` frame वर तो
अंतर्गत `codex-responses-ws` bridge द्वारे प्रमाणीकरण + तयारी करतो, एक
codex OAuth connection निवडतो आणि `wreq-js` transport द्वारे `wss://chatgpt.com/backend-api/codex/responses`
कडे tunnel करतो. **codex व्यतिरिक्त इतर models नाकारले जातात** (`codex_ws_provider_required`).
quota-share routing साठी `model: "qtSd/<group>/codex/<model>"` वापरा. याची अंमलबजावणी
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` मध्ये केली आहे.

**प्रमाणीकरण:** handshake दरम्यान Bearer API key. समाविष्ट HTTP server (`server-ws.mjs`)
हा सक्रिय entrypoint असला पाहिजे (`app/server-ws.mjs` अस्तित्वात असताना तो default ने सक्रिय असतो).

#### Model id: मूळ ChatGPT id वापरा (`codex/` prefix शिवाय)

OpenAI **Codex CLI**, `supports_websockets = true` असताना, client-side वर model name चे प्रमाणीकरण करते आणि
`codex/gpt-5.5` सारखे **provider-prefixed ids नाकारते**
(`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). **मूळ** id पाठवा (उदा. `gpt-5.5`). OmniRoute चा bridge
केवळ codex साठी असल्यामुळे, upstream कडे tunnel करण्यापूर्वी तो मूळ id ला codex model म्हणून
(`resolveCodexWsModelInfo`) पुन्हा resolve करतो — जरी मूळ
`gpt-5.5` अन्यथा HTTP वरून दुसऱ्या प्रदात्याकडे route झाले असते.

#### OpenAI Codex CLI कॉन्फिगर करणे

`~/.codex/config.toml` मध्ये WebSocket समर्थन असलेला custom provider जोडून
Codex CLI ला OmniRoute कडे निर्देशित करा (विद्यमान config मध्ये बदल करणे टाळण्यासाठी स्वतंत्र `CODEX_HOME` वापरा):

```toml
model = "gpt-5.5"                 # मूळ id — "codex/gpt-5.5" नाही
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # शेवटी slash नाही; WS URL यावरून तयार होतो (production मध्ये https/wss वापरा)
wire_api = "responses"                    # Feb 2026 पासून समर्थित असलेले एकमेव value
supports_websockets = true                # Responses-over-WS transport सक्षम करते
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API key (Bearer) ठेवते
```

```bash
export OMNIROUTE_API_KEY=sk-...           # एक OmniRoute API key (REQUIRE_API_KEY=false असल्यास कोणतीही key)
codex exec "Responda apenas: PONG"
```

CLI, `base_url + /responses` ला WebSocket मध्ये upgrade करते आणि OmniRoute त्याला
निवडलेल्या codex OAuth connection कडे tunnel करते. स्थानिक server विरुद्ध end-to-end प्रमाणीकरण केले आहे:
ChatGPT `codex.rate_limits` + `response.created` परत करते आणि completion stream करते.

## स्व-सेवा वापर (`/api/usage/om-usage`)

कोणतीही API की **स्वतःचा** वापर आणि कोटा वाचू शकते — व्यवस्थापन प्रमाणीकरणाची गरज नाही. की धारकाला त्याचा खर्च दाखवण्यासाठी क्लायंट (CLI, OmniCopilot पॅनेल) हा एंडपॉइंट वापरतो.

```bash
# मजकूर स्वरूप (ऐतिहासिक करार — टर्मिनलसाठी साधा मजकूर)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# संरचित स्वरूप — UI ज्याचा वापर करतो
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

कीसाठी **`allowUsageCommand`** सक्षम असणे आवश्यक आहे (डीफॉल्टनुसार बंद — डॅशबोर्डचा API-की व्यवस्थापक प्रत्येक कीसाठी ते टॉगल करतो). ते नसल्यास एंडपॉइंट `403` प्रतिसाद देतो.

`?format=json` विभेदित संरचना परत करतो, जेणेकरून कॉलरने नकाराच्या प्रतिसादातून कधीही डेटा फील्ड वाचू नये. यशस्वी झाल्यास:

```jsonc
{
  "allowed": true,
  // कीने प्रति-की वापर मर्यादा (दैनिक/साप्ताहिक USD) स्वीकारल्या असतील तेव्हाच उपस्थित:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // निवडलेल्या प्रदात्याचा कोटा स्नॅपशॉट, किंवा अद्याप काहीही कॅश केलेले नसल्यास null:
  "provider": {
    "connectionId": "…",
    "provider": "claude",
    "plan": "…",
    "quotas": {/* … */},
  },
  // प्रत्येक कनेक्शनचा स्नॅपशॉट, जेणेकरून UI अनेक प्रदाते शेजारी-शेजारी रेंडर करू शकेल:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

नकार दिल्यास (`401` चुकीची की / `403` परवानगी नाही), हाच रूट
`{ "allowed": false, "error": { "message": "…" } }` परत करतो — उपस्थित-परंतु-रिक्त `personal`/`provider`
(कीला परवानगी आहे, अद्याप काहीही समजलेले नाही) ही नकारापेक्षा वेगळी स्थिती आहे आणि केवळ JSON स्वरूप त्यांच्यात फरक करते.

**प्रमाणीकरण:** कॉलरची स्वतःची Bearer API की, `isValidApiKey` वापरून सत्यापित केली जाते — हे
व्यवस्थापन पृष्ठभाग (`/api/keys/…`) _नाही_, जो `requireManagementAuth`च्या मागेच राहतो.

### कच्ची विरुद्ध कटऑफ-समायोजित कोटा टक्केवारी

`/api/usage/om-usage` वापरताना, कॉलरने **साध्या-मजकूर आउटपुटमध्ये** आणि संरचित **JSON आउटपुटमध्ये** दर्शविलेल्या टक्केवारीमधील फरक लक्षात घ्यावा:

| पैलू                | साधे-मजकूर स्वरूप (`/api/usage/om-usage` / `@@om-usage`)                                          | JSON स्वरूप (`?format=json`)                                                       |
| :------------------ | :------------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------------------- |
| **आउटपुट फील्ड**    | `NN% left` (उदा., `20% left`)                                                                     | `provider.quotas` / `providers[].quotas`                                           |
| **मापन**            | **कटऑफ-समायोजित वापरण्यायोग्य भत्ता**: कटऑफ मर्यादेपेक्षा जास्त उर्वरित क्षमता                    | **कच्चा अपस्ट्रीम कोटा**: प्रदात्याचे न समायोजित केलेले मापन                       |
| **कटऑफ स्केलिंग**   | `effectiveRemainingPercent()` द्वारे स्केल केलेले, जेणेकरून संरक्षित राखीव `0% left` म्हणून दिसेल | काहीही नाही (प्रदात्याने दिल्याप्रमाणे कच्ची स्नॅपशॉट मूल्ये)                      |
| **मर्यादा डेटा**    | प्रदर्शित टक्केवारीमध्ये समाविष्ट                                                                 | प्रत्येक कनेक्शनसाठी `quotaWindowThresholds`मध्ये संग्रहित (किंवा सर्व्हर डीफॉल्ट) |
| **प्राथमिक ग्राहक** | परस्परसंवादी CLI, टर्मिनल प्रॉम्प्ट, मानवी ऑपरेटर                                                 | प्रोग्रामॅटिक एकत्रीकरणे, डॅशबोर्ड, विश्लेषण, बिलिंग ट्रॅकर                        |

#### कटऑफ समायोजन सूत्र

अपस्ट्रीम कोटा संपुष्टात येण्यापासून रोखण्यासाठी OmniRoute सक्रिय कोटा कटऑफना समर्थन देतो (कनेक्शन
`quotaWindowThresholds`, प्रदाता डीफॉल्ट किंवा जागतिक लवचिकता सेटिंग्जद्वारे कॉन्फिगर केलेले). कोटा विंडोवर कटऑफ मर्यादा
(उदा., `cutoff = 25%`) सक्रिय असताना, मजकूर रेंडरर उर्वरित भत्त्याची गणना अशी करतो:

- `remaining <= cutoff` असल्यास: `0%` परत करतो.
- `remaining > cutoff` असल्यास: `((remaining - cutoff) / (100 - cutoff)) * 100` परत करतो.

स्वरूपित मजकूर आउटपुट हे जवळच्या पूर्णांकापर्यंत राउंड करतो (`Math.round(...)`).

#### स्पष्टीकरणात्मक उदाहरण

**60% कच्चा वापर** (म्हणून **40% कच्चा उर्वरित कोटा**) असलेली प्रदाता विंडो आणि कॉन्फिगर केलेली
**25% उर्वरित-कोटा कटऑफ** मर्यादा विचारात घ्या:

| सादरीकरण                        | गणना                                               | उर्वरित |              सूचित वापरलेले              |
| :------------------------------ | :------------------------------------------------- | :-----: | :--------------------------------------: |
| **कच्चा JSON (`?format=json`)** | अपस्ट्रीम स्नॅपशॉट (`quotas[window]`)              | **40%** |                 **60%**                  |
| **मजकूर स्वरूप (`NN% left`)**   | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (`100 - remaining` गणना केल्यास) |

- **मजकूर 20% शिल्लक का दाखवतो:** खात्यावर शिल्लक असलेल्या 40% प्रत्यक्ष कोट्यापैकी 25% कटऑफ धोरणाद्वारे
  राखीव ठेवला जातो. राउटरने या कनेक्शनकडे रूटिंग थांबवण्यापूर्वी कॉलरकडे वापरण्यायोग्य 75% मोकळ्या क्षमतेपैकी
  केवळ 15% शिल्लक आहे. स्केलिंग हे सुनिश्चित करते की रूटिंग थांबेल त्याच वेळी कनेक्शन संपुष्टात आल्याचे
  (`0% left`) दर्शवेल.
- **JSON कच्ची मूल्ये का जतन करतो:** JSON पेलोड प्रदात्याचा अचूक स्नॅपशॉट (`UsageSnapshot`) परत करतो,
  जेणेकरून बाह्य साधनांना सर्व्हर-साइड हानिकारक स्केलिंगशिवाय सत्याधारित अपस्ट्रीम वापर आणि कनेक्शन-स्तरीय
  `quotaWindowThresholds` उपलब्ध होतील.

#### ग्राहक स्थलांतर मार्गदर्शन

जर एखाद्या बाह्य एकत्रीकरणाने (जसे की संपादक प्लगइन किंवा एजंट एक्स्टेंशन) यापूर्वी मजकूर
एंडपॉइंट (`NN% left`) स्क्रेप केला असेल आणि वापरलेली टक्केवारी `100 - NN` म्हणून मोजली असेल, तर `?format=json`कडे स्थलांतर करण्याचा अर्थ:

- कच्ची JSON मूल्ये वाचल्याने **प्रत्यक्ष अपस्ट्रीम वापर** दिसेल (वरील उदाहरणात 60% वापरलेले).
- एकत्रीकरणाला मजकूर एंडपॉइंटचे वापरण्यायोग्य-भत्ता शब्दार्थ जतन करायचे असल्यास, ते कनेक्शन-स्तरीय ओव्हरराइडसाठी `quotaWindowThresholds` वापरून प्रभावी उर्वरित सूत्र क्लायंट-साइडवर मूल्यांकित करू शकते.

### विलंबावरील परिणाम

सिमॅंटिक कॅश HIT प्रतिसाद **अपस्ट्रीम कॉलशिवाय** कॅशमधून देते, त्यामुळे नोंदवलेला `X-OmniRoute-Response-Latency` जवळजवळ शून्य असतो (मूळ अपस्ट्रीम विलंब कितीही असला तरी). विलंबाबाबत संवेदनशील क्लायंटनी (बेंचमार्किंग, p50/p99 निरीक्षण) `X-OmniRoute-Cache-Latency` प्रतिसाद हेडर तपासावे:

| मूल्य         | अर्थ                                                        |
| ------------- | ----------------------------------------------------------- |
| `synthetic`   | प्रतिसाद कॅशमधून दिला; हा विलंब वास्तविक अपस्ट्रीम वेळ नाही |
| _(अनुपस्थित)_ | वास्तविक अपस्ट्रीम कॉलमधून मिळालेला प्रतिसाद                |

### प्रत्येक-की कॅश बायपास

API की `cacheDefaultMode` द्वारे सिमॅंटिक कॅश वाचनातून बाहेर पडण्याचा पर्याय निवडू शकतात:

| मूल्य    | वर्तन                                              |
| -------- | -------------------------------------------------- |
| `legacy` | सामान्य कॅश वर्तन (डीफॉल्ट)                        |
| `bypass` | कॅश लुकअप पूर्णपणे वगळा; नेहमी अपस्ट्रीमवर कॉल करा |

```json

```

### प्रत्येक-विनंती बायपास

की सेटिंग्जची पर्वा न करता कोणतीही विनंती कॅश बायपास करू शकते:

`modelOutputOverrides` मध्ये परत देते, ज्यात कस्टम-मॉडेल पंक्ती नसलेली मॉडेल्सही समाविष्ट आहेत. ओव्हरराइड
रनटाइम `max_output_tokens` क्षमता वापरते आणि मॉडेल री-सिंकनंतरही टिकते. OpenAI-सुसंगत
प्रोव्हायडर पृष्ठ त्याच संपादन/साफ नियंत्रणे देते आणि स्पष्ट व्हिजन सपोर्ट असलेली मॉडेल्स चिन्हांकित करते.

कस्टम Chat Completions नोड्स स्पष्ट रीझनिंग ऑप्ट-आउट्स अपस्ट्रीम बॅकएंडशी जुळवतात. यशस्वी
कनेक्शन चाचणी प्रत्येक नेमक्या मॉडेल ID साठी आपोआप चॅट-टेम्पलेट नियंत्रणे निवडते
ज्याची `/models` एंट्री ओळखलेले `owned_by` मूल्य सिद्ध करते: `vllm`, `sglang`, किंवा `llamacpp`.
पारदर्शक OpenAI-सुसंगत रॅपर्स मूळ मॉडेल एंट्री नेस्टेड
`openai` ऑब्जेक्टमध्ये टिकवू शकतात; डिटेक्शन अशा तीनपर्यंत एन्व्हलप्समागून जाते. गहाळ, अज्ञात किंवा
विसंगत मालकी असलेली मॉडेल्स सामान्य OpenAI वर्तन ठेवतात. डिटेक्शन विद्यमान कॅटलॉग विनंतीचा पुन्हा वापर करते,
कोणतेही कम्प्लीशन टोकन तयार करत नाही, आणि कनेक्शन एंडपॉइंट बदलल्यावर अवैध होते.

तो मेटाडेटा उघड करत नसलेल्या बॅकएंडसाठी वर्तन पिन करण्यासाठी, विद्यमान आंशिक
प्रोव्हायडर अपडेट API वापरा:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

तो body `PUT /api/providers/<connection-id>` सह पाठवा. त्या कनेक्शनवर, `none` चा स्पष्ट reasoning effort `chat_template_kwargs.thinking=false` आणि `chat_template_kwargs.enable_thinking=false` म्हणून पाठवला जातो. सर्व्हर-साइड reasoning नियम effort बलजबरीने लागू करत नाही तोपर्यंत स्पष्ट native template मूल्ये अधिकृत राहतात. ही सेटिंग फक्त जेव्हा कस्टम OpenAI-सुसंगत कनेक्शन Chat Completions body पाठवते तेव्हाच लागू होते; Responses विनंत्या आणि सामान्य प्रोव्हायडर्स त्यांचे native request आकार कायम ठेवतात. सामान्य OpenAI `reasoning_effort` passthrough बलजबरीने वापरण्यासाठी `reasoningControl` ला `openai` वर सेट करा, किंवा automatic detection वापरण्यासाठी ते वगळा/`null` वर सेट करा.

Claude Code auto-mode classifier विनंत्या, ज्यांमध्ये स्पष्ट reasoning नियंत्रणे नसतात, native thinking ला डीफॉल्टनुसार अक्षम करतात. Detection मध्ये Claude-format विनंत्यांतील classifier चा system marker वापरला जातो, मॉडेल नावे किंवा completion मर्यादा नाहीत. स्पष्ट body नियंत्रणे, समर्थित effort/thinking headers, routing नियम आणि resolved model effort त्यांची विद्यमान प्राथमिकता कायम ठेवतात. दोन्ही classifier टप्पे त्यांचे prompts, completion मर्यादा, stop sequences आणि खरे upstream permission निकाल कायम ठेवतात; दुसरा टप्पा अजूनही विनंती केलेला दृश्यमान reasoning सामान्य मजकूर म्हणून तयार करू शकतो.

### आवृत्ती आणि रिलीज चॅनेल

```bash
GET /api/system/version
```

केवळ-लूपबॅक व्यवस्थापन रूट (अॅडमिन ऑथ). चालू आवृत्ती, नवीनतम प्रकाशित आवृत्ती आणि स्वयं-अद्यतन स्थिती मिळवते. `releaseChannel` आणि `channels` हे अॅडिटिव्ह फील्ड्स आहेत (rail 3.8.54); `channel` त्याचा अर्थ कायम ठेवते — डॅशबोर्ड अद्यतनकर्ता वापरत असलेली डिप्लॉयमेंट पद्धत (`npm`, `source` किंवा `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — चालू बिल्डचा npm चॅनेल: `-nightly.*` आवृत्त्यांसाठी `nightly`, इतर प्री-रिलीजसाठी (`-rc.*`, `-beta.*`, `-alpha.*`) `next`, `channels.latest` पेक्षा जुन्या मेजरच्या स्थिर आवृत्तीसाठी `lts`, अन्यथा `latest`. `scripts/release/dist-tag.mjs` यांचेच नियम, जे प्रकाशनाच्या वेळी npm dist-tag निवडते.
- `channels` — प्रत्येक dist-tag चा प्रकाशित हेड, `npm view omniroute dist-tags` वरून (रजिस्ट्री HTTP फॉलबॅक), `latest` प्रमाणेच 10-मिनिटांच्या TTL सह कॅशे केलेला. `latest` नेहमी उपस्थित असतो (`latest` फील्डवर फॉलबॅक करतो, नंतर `"unavailable"`); `next`, `nightly` आणि `lts` फक्त तो dist-tag अस्तित्वात असतानाच दिसतात. `Cache-Control: no-cache` विनंती दोन्ही लुकअप्स रीफ्रेश करते.

चॅनेल मॉडेल (4.0 GA पर्यंत `latest` = v3, `next` = rc, `nightly` = `develop` बिल्ड्स, 4.0 GA नंतर `lts` = v3 पॅचेस) `docs/ops/RELEASE_STRATEGY.md` मध्ये वर्णन केले आहे.

## ऑडिओ लिप्यंतरण

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

कॉन्फिगर केलेल्या कोणत्याही STT प्रदात्याचा वापर करून ऑडिओ फाइल्सचे लिप्यंतरण करा. पाथचा पहिला
सेगमेंट मूळ प्रदाता निवडतो (`openai/…`, `deepgram/…`). दुसऱ्या विक्रेत्याचे मॉडेल
पुन्हा निर्यात करणारे गेटवे पूर्णपणे पात्र id वापरतात
(`openrouter/deepgram/nova-3`).

**विनंती:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**प्रतिसाद:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**उदाहरणार्थ मॉडेल ids:** `openai/whisper-1` (OpenAI की आवश्यक आहे),
`openrouter/deepgram/nova-3` (OpenRouter की आवश्यक आहे),
`deepgram/nova-3` (मूळ Deepgram की आवश्यक आहे). केवळ
`deepgram/nova-3` विनंती OpenRouter वापरत **नाही**.

**समर्थित स्वरूपे:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## टोकनयुक्त VS Code / हेडरविरहित उपनावे

जेव्हा एखादे इंटिग्रेशन `Authorization` हेडर अंतर्भूत करू शकत नाही आणि API की बेस URL मध्ये एम्बेड करणे आवश्यक असते, तेव्हा ही उपनावे वापरा.

```bash
# OpenAI-शैलीतील कॅटलॉग उपनाव
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-शैलीतील चॅट उपनावे
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-शैलीतील उपनावे
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

उदाहरण:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

नोंदी:

- टोकनयुक्त उपनावे `/v1/*` आणि `/api/tags` प्रमाणेच हँडलर्स पुन्हा वापरतात; प्रतिसादांची संरचना तशीच राहते.
- क्लायंट कस्टम हेडर्सना समर्थन देत असेल, तेव्हा शक्यतो `Authorization: Bearer ...` वापरा.
- URL-आधारित टोकन्स रिव्हर्स-प्रॉक्सी लॉग्स, ब्राउझर इतिहास आणि OmniRoute च्या बाहेरील टेलिमेट्रीमध्ये दिसू शकतात. त्यांना डीफॉल्ट प्रमाणीकरण पद्धत न मानता सुसंगतता पर्याय म्हणून वापरा.

## टोकन मर्यादा

प्रत्येक API कीसाठी **टोकन** बजेट (वरील USD-आधारित बजेटपेक्षा वेगळे). विनंती मार्गावरच त्यांची अंमलबजावणी केली जाते: एखाद्या कीचा सध्याच्या कालावधीतील वापर तिच्या मर्यादेपर्यंत पोहोचल्यावर, विनंत्या `429 Too Many Requests` सह नाकारल्या जातात. मर्यादा विशिष्ट `model`, `provider` यांच्यापुरत्या व्याप्त केल्या जाऊ शकतात किंवा संपूर्ण कीवर `global` पातळीवर लागू केल्या जाऊ शकतात; जेव्हा अनेक मर्यादा एखाद्या विनंतीशी जुळतात, तेव्हा सर्वाधिक प्रतिबंधात्मक मर्यादा लागू होते.

```bash
# कीच्या टोकन मर्यादांची यादी दाखवा (सध्याच्या कालावधीतील प्रत्यक्ष वापरासह)
GET /api/usage/token-limits?apiKeyId=key-123

# टोकन मर्यादा तयार करा किंवा अद्ययावत करा
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id नुसार टोकन मर्यादा हटवा
DELETE /api/usage/token-limits?id=tl-abc
```

> **स्कीमा नोंदी** (`setTokenLimitSchema`): `apiKeyId` आणि `scopeType` (`model` | `provider` | `global`) आवश्यक आहेत. `scopeType` हे `global` नसल्यास `scopeValue` आवश्यक आहे (उदा. `model` व्याप्तीसाठी मॉडेल id, `provider` व्याप्तीसाठी प्रदाता id). `tokenLimit` हा धन पूर्णांक असणे आवश्यक आहे (स्ट्रिंगमधून रूपांतरित केला जातो). पर्यायी: `id` (तयार करण्यासाठी वगळा, अद्ययावत करण्यासाठी द्या), `resetInterval` (`daily` | `weekly` | `monthly`, डीफॉल्ट `monthly`), `resetTime` (`HH:MM`), `enabled` (डीफॉल्ट `true`). `GET` प्रतिसाद प्रत्येक मर्यादेला `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, आणि `nextResetAt` या माहितीसह समृद्ध करतात. हा व्यवस्थापन-वर्गातील एंडपॉइंट आहे (authz पाइपलाइनद्वारे प्रमाणीकरणाची अंमलबजावणी मध्यवर्ती पद्धतीने केली जाते).

## विनंती प्रक्रिया

1. क्लायंट `/v1/*` वर विनंती पाठवतो
2. रूट हँडलर `handleChat`, `handleEmbedding`, `handleAudioTranscription`, किंवा `handleImageGeneration` कॉल करतो
3. मॉडेलचे निराकरण केले जाते (थेट provider/model किंवा alias/combo)
4. खात्याच्या उपलब्धतेनुसार फिल्टरिंग करून स्थानिक DB मधून क्रेडेन्शियल्स निवडली जातात
5. चॅटसाठी: `handleChatCore` सिमॅंटिक/सिग्नेचर कॅश तपासतो आणि combo कॉम्प्रेशन सेटिंग्जचे निराकरण करतो
6. सक्षम केलेले असताना प्रदाता रूपांतरणापूर्वी सक्रिय कॉम्प्रेशन चालते (`lite`, Caveman, RTK, किंवा त्यांचे एकत्रित स्टॅक)
7. प्रदाता एक्झिक्युटर अपस्ट्रीम विनंती पाठवतो
8. प्रतिसाद परत क्लायंटच्या स्वरूपात रूपांतरित केला जातो (चॅट) किंवा जसाच्या तसा परत केला जातो (एम्बेडिंग्ज/प्रतिमा/ऑडिओ)

## लवचिकता (विस्तारित)

OmniRoute तीन स्वतंत्र तात्पुरते-अपयश यंत्रणा उघड करतो; खालील व्यवस्थापन एंडपॉइंट्स ऑपरेटरना त्या वाचण्याची आणि ओव्हरराइड करण्याची अनुमती देतात:

| व्याप्ती           | स्थिती साठवण                               | वाचा                                      | रीसेट / साफ करा                                        |
| ------------------ | ------------------------------------------ | ----------------------------------------- | ------------------------------------------------------ |
| प्रोव्हायडर ब्रेकर | `domain_circuit_breakers` + इन-मेमरी       | `/api/monitoring/health`                  | `POST /api/resilience/reset`                           |
| कनेक्शन कूलडाउन    | प्रोव्हायडर कनेक्शनवरील `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (आळशीपणे पुन्हा-सक्षम; प्रोव्हायडर PUT द्वारे साफ करा) |
| मॉडेल लॉकआउट       | इन-मेमरी मॉडेल-उपलब्धता नोंदवही            | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`               |

`PATCH /api/resilience` `providerBreaker.oauth` आणि `providerBreaker.apikey` अंतर्गत प्रोव्हायडर ब्रेकर ओव्हरराइड स्वीकारते. प्रत्येक प्रोफाइल `degradationThreshold`, `failureThreshold` आणि `resetTimeoutMs` ला समर्थन देते; तेच फील्ड्स डॅशबोर्ड → सेटिंग्ज → लवचिकता मध्ये उघड केले जातात.

```bash
# एकल मॉडेल लॉकआउट साफ करा
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# सर्व लॉकआउट पुसा
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

संपूर्ण संकल्पनात्मक संदर्भ आणि ब्रेकर डीफॉल्ट्स: [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" आणि [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) पहा.

### रेट-लिमिट रांग आणि ऑटो-एनेबल सेफ्टी नेट

- **समर्थित लेखन मार्ग**: `POST /api/rate-limits` आणि `{"connectionId": "<id>", "enabled": true|false}` या बॉडीसह हा कनेक्शनसाठी रेट-लिमिट संरक्षण टॉगल करण्याचा समर्थित व्यवस्थापन एंडपॉइंट आहे. `PUT /api/providers/[id]` जाणीवपूर्वक `rateLimitProtection` बदलत नाही किंवा फ्लिप करत नाही (#11278).
- **`enabled: false` चे अर्थशास्त्र**: `enabled: false` सेट केल्याने कनेक्शनचे स्पष्ट संरक्षण काढले जाते, परंतु सक्रिय API-की कनेक्शनला जागतिक ऑटो-एनेबल सेफ्टी नेटमधून (`autoEnableApiKeyProviders = true`) बाहेर काढत **नाही**. `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) मध्ये, `false` आणि `undefined` समतुल्य आहेत; स्पष्ट संरक्षणाशिवाय सक्रिय API-की कनेक्शन्स ऑटो-एनेबल सेफ्टी नेट अंतर्गत संरक्षित राहतात.
- **जागतिक अक्षम**: रेट-लिमिट रांगांशिवाय API-की कनेक्शन्स चालवण्यासाठी, `RATE_LIMIT_AUTO_ENABLE=false` (पर्यावरण चल) किंवा `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (सेटिंग्ज → लवचिकता / `PATCH /api/resilience`) द्वारे सेफ्टी नेट जागतिक स्तरावर अक्षम करा.

## MCP सर्व्हर

OmniRoute मध्ये 3 transports (stdio, SSE, streamable-http) आणि व्याप्तीबद्ध साधनांसह अंतर्भूत Model Context Protocol सर्व्हर समाविष्ट आहे. खालील dashboard endpoints स्थिती/audit डेटा वाचतात आणि HTTP transports ना प्रॉक्सी करतात.

| पद्धत | पथ | वर्णन |

| GET | `/api/mcp/status` | Heartbeat, transport, ऑनलाइन स्थिती, शेवटचा कॉल, प्रमुख साधने, 24 तासांचा यशाचा दर |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` सह MCP साधनांची सूची |
| GET | `/api/mcp/sse` | SSE transport साठी SSE stream उघडा (MCP अक्षम असल्यास किंवा transport जुळत नसल्यास `503` परत करतो) |
| POST | `/api/mcp/sse` | SSE transport वर JSON-RPC frame पाठवा |
| GET | `/api/mcp/stream` | Streamable HTTP transport ची SSE बाजू उघडा (सर्व्हरद्वारे सुरू केलेले संदेश) |
| POST | `/api/mcp/stream` | Streamable HTTP transport वर JSON-RPC frame पाठवा |
| DELETE | `/api/mcp/stream` | Streamable HTTP सत्र समाप्त करा |
| GET | `/api/mcp/audit` | audit log क्वेरी करा — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | एकत्रित audit आकडेवारी (एकूण संख्या, यशाचा दर, सरासरी कालावधी, प्रमुख साधने) |

**प्रमाणीकरण:** `sse`/`stream` transports MCP-विशिष्ट प्रमाणीकरण पृष्ठभागाचा सन्मान करतात (`mcp` scope असलेली Bearer API की); `status`/`tools`/`audit*` routes dashboard वरून वाचता येतात (dashboard host पर्यंत पोहोचण्याव्यतिरिक्त कोणतेही अतिरिक्त प्रमाणीकरण आवश्यक नाही).

> दोन्ही HTTP transports `settings.mcpEnabled` आणि `settings.mcpTransport` द्वारे नियंत्रित केले जातात — transport जुळत नसल्यास `400`, तर MCP अक्षम स्थितीत `503` परत केले जाते.

## A2A सर्व्हर

OmniRoute तपासणी/डॅशबोर्ड वापरासाठी REST रॅपरसह A2A (Agent-to-Agent) JSON-RPC 2.0 एंडपॉइंट उपलब्ध करून देते.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY सेट केलेले नसल्यास ऐच्छिक
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

समर्थित पद्धती (सर्व `settings.a2aEnabled` द्वारे नियंत्रित):

| पद्धत            | वर्णन                                                             |
| ---------------- | ----------------------------------------------------------------- |
| `message/send`   | समकालिक कौशल्य अंमलबजावणी; `{task, artifacts, metadata}` परत करते |
| `message/stream` | त्याच कौशल्य संचाची स्ट्रीमिंग SSE अंमलबजावणी                     |
| `tasks/get`      | `taskId` द्वारे कार्य मिळवा                                       |
| `tasks/cancel`   | `taskId` द्वारे कार्य रद्द करा                                    |

अंगभूत कौशल्ये: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### एजंट कार्ड

```bash
GET /.well-known/agent.json
```

सार्वजनिक A2A एजंट कार्ड (नाव, वर्णन, क्षमता, कौशल्य कॅटलॉग, प्रमाणीकरण योजना) परत करते — 1 तासासाठी सार्वजनिकरीत्या कॅश केलेले. प्रमाणीकरण आवश्यक नाही.

### REST सहाय्यक

| पद्धत | पथ                           | वर्णन                                                                                                               |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | A2A सक्षम स्थिती + कार्य आकडेवारी + कॅश केलेल्या एजंट कार्डचा सारांश                                                |
| GET   | `/api/a2a/tasks`             | कार्यांची सूची — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (REST सहाय्यक म्हणून अंमलात आणलेले नाही — JSON-RPC `message/send` द्वारे तयार करा)                                  |
| GET   | `/api/a2a/tasks/[id]`        | एक कार्य मिळवा                                                                                                      |
| POST  | `/api/a2a/tasks/[id]/cancel` | कार्य रद्द करा                                                                                                      |

**प्रमाणीकरण:** REST सहाय्यक व्यवस्थापन प्रमाणीकरणाशिवाय चालतात (डॅशबोर्डवर वाचण्यायोग्य); कॉन्फिगर केले असल्यास JSON-RPC `/a2a` मार्ग Bearer `OMNIROUTE_API_KEY` वापरतो.

## ACP (Agent Client Protocol) व्यवस्थापन

चाइल्ड प्रोसेसेस म्हणून. हे एंडपॉइंट्स ACP एजंट शोध आणि कस्टम एजंट
नोंदणी व्यवस्थापित करतात.

| पद्धत  | पाथ               | वर्णन                                                                                                                                                           |
| ------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | इंस्टॉलेशन स्थिती, आवृत्ती आणि बायनरीसह सर्व ज्ञात CLI एजंट्सची (अंगभूत + कस्टम) यादी                                                                           |
| POST   | `/api/acp/agents` | कस्टम ACP एजंटची नोंदणी करा किंवा कॅशे रिफ्रेश करा — बॉडी: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` किंवा `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | कस्टम ACP एजंट काढून टाका — क्वेरी पॅरामीटर: `?id=<agentId>`                                                                                                    |

**प्रतिसादाचे उदाहरण** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**प्रमाणीकरण:** व्यवस्थापन सत्र (डॅशबोर्ड `auth_token` कुकी) किंवा
व्यवस्थापन-व्याप्ती असलेली API की आवश्यक आहे.

संपूर्ण तपशीलांसाठी [ACP फ्रेमवर्क](../frameworks/ACP.md) पहा.

| ----- | ---------------------- | ------------------------------------------------------------------------------------------------ |
| GET   | `/api/guardrails`      | नोंदणीकृत गार्डरेल्स आणि त्यांची स्थिती (नाव / सक्षम / प्राधान्य) सूचीबद्ध करा                   |

## प्रमाणीकरण

चार क्रेडेन्शियल प्रकारांसाठी (डॅशबोर्ड सत्र, स्थानिक CLI टोकन, `oma_live_…` Access Token, व्यवस्थापन-व्याप्ती असलेली API की) आणि ते इन्फरन्स कींपेक्षा कसे वेगळे आहेत हे जाणून घेण्यासाठी [व्यवस्थापन प्रमाणीकरण](../guides/MANAGEMENT-AUTH.md) पहा.

- डॅशबोर्ड मार्ग (`/dashboard/*`) `auth_token` कुकी वापरतात
- लॉगिन जतन केलेला पासवर्ड हॅश वापरते; उपलब्ध नसल्यास `INITIAL_PASSWORD` वापरला जातो
- `requireLogin` हे `/api/settings/require-login` द्वारे बदलता येते
- `REQUIRE_API_KEY=true` असताना `/v1/*` मार्गांना पर्यायाने Bearer API की आवश्यक असते
- या संदर्भातील "व्यवस्थापन टोकन" / "व्यवस्थापन-व्याप्ती असलेली API की" म्हणजे त्या मार्गदर्शिकेतील प्रकारांपैकी एक — कोणताही अपरिभाषित अतिरिक्त गुप्त प्रकार नव्हे

> **ब्रेकिंग बदल (v3.8.0)** — `/api/v1/agents/tasks/*` आणि कूलडाउन व्यवस्थापन एंडपॉइंट्सना आता **व्यवस्थापन प्रमाणीकरण** (डॅशबोर्ड `auth_token` कुकी किंवा व्यवस्थापन-व्याप्ती असलेली API की) आवश्यक आहे. पूर्वी प्रमाणीकरणाशिवाय हे मार्ग कॉल करणाऱ्या क्लायंटना `401 Unauthorized` प्रतिसाद मिळेल. कमिट `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) पहा.
