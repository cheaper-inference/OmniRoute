> **थोडक्यात**: OmniRoute त्याचे प्राथमिक संचयन म्हणून **WAL जर्नलिंगसह SQLite** वापरते आणि संवेदनशील फील्डसाठी स्थिर स्थितीतील **AES-256-GCM** एन्क्रिप्शन वापरते. या मार्गदर्शकामध्ये स्कीमा, मायग्रेशन्स, बॅकअप/रिकव्हरी आणि परिचालन रनबुक्स समाविष्ट आहेत.

**स्रोत:**

- `src/lib/db/core.ts` — सिंगलटन + SCHEMA_SQL (17 मूलभूत टेबल्स)
- `src/lib/db/migrationRunner.ts` — आवृत्तीबद्ध मायग्रेशन्स
- `src/lib/db/migrations/` — 167 आवृत्तीबद्ध SQL फाइल्स
- `src/lib/db/encryption.ts` — एन्क्रिप्शन सहाय्यक
- `src/lib/db/backup.ts` — बॅकअप एक्सपोर्ट/इम्पोर्ट
- `src/lib/db/healthCheck.ts` — स्थिती निदान

## SQLite का?

OmniRoute ने अनेक कारणांमुळे PostgreSQL/MySQL ऐवजी SQLite निवडले:

| घटक                | SQLite                                 | PostgreSQL                            |
| ------------------ | -------------------------------------- | ------------------------------------- |
| **उपयोजन**         | एम्बेडेड — स्वतंत्र सर्व्हरची गरज नाही | सर्व्हर सेटअप आवश्यक                  |
| **एन्क्रिप्शन**    | ॲप्लिकेशन-स्तरावरील (AES-256-GCM)      | अंगभूत TDE                            |
| **कार्यक्षमता**    | लहान/मध्यम वर्कलोड्ससाठी अधिक जलद      | प्रचंड समकालीन लेखनांसाठी अधिक चांगले |
| **समवर्तीपणा**     | WAL मोड समकालीन वाचनांना अनुमती देतो   | संपूर्ण MVCC                          |
| **बॅकअप**          | एकाच फाइलची प्रत                       | `pg_dump` किंवा फाइलसिस्टम स्नॅपशॉट   |
| **वापराचे प्रकरण** | प्रति-वापरकर्ता इन्स्टॉलेशन, एम्बेडेड  | मल्टी-टेनंट SaaS                      |

**एकल-वापरकर्ता, एकल-इन्स्टन्स** उपयोजनांसाठी (OmniRoute चे प्राथमिक वापराचे प्रकरण), SQLite अधिक सोपे आणि जलद आहे.

### WAL जर्नलिंग

`core.ts` डेटाबेस **WAL (Write-Ahead Logging) मोडमध्ये** उघडते:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL लेखन सुरू असताना **समकालीन वाचनांना** अनुमती देते — विनंत्या नोंदवल्या जात असताना क्वेरी करणाऱ्या डॅशबोर्डसाठी हे महत्त्वाचे आहे.

डीफॉल्ट कॅशे आकार **65,536 KiB (64 MiB)** आहे. SQLite ऋण
`cache_size` ला KiB मधील अंदाजे कमाल मर्यादा मानते आणि गरजेनुसार पेजेस वाटप करते.
**सेटिंग्ज > सिस्टम आणि स्टोरेज > कॅशे आकार** येथे **1 ते
1,000,000 KiB** पर्यंतच्या पूर्णांक मूल्यांचा स्वीकार केला जातो; सेटिंग सेव्ह केल्यावर ते सक्रिय डेटाबेस कनेक्शनवर लागू होते,
आणि OmniRoute स्टार्टअपवेळी जतन केलेले मूल्य पुनर्स्थापित करते.

## डेटाबेसचे स्थान

SQLite फाइल येथे संग्रहित केली जाते:

| OS      | पथ                                                                  |
| ------- | ------------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                       |
| macOS   | `~/.omniroute/storage.sqlite`                                       |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                           |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` द्वारे कॉन्फिगर करण्यायोग्य) |

सोबतच्या फाइल्स:

- `storage.sqlite-wal` — राइट-अहेड लॉग
- `storage.sqlite-shm` — शेअर्ड मेमरी फाइल
- `call_logs/` — विनंती पेलोड आर्टिफॅक्ट्स (सक्षम केले असल्यास)

**स्थान ओव्हरराइड करा:**

```bash
DATA_DIR=/custom/path omniroute
```

### मॉड्यूल सीमा

एक मुख्य आर्किटेक्चरल नियम: **मॉड्यूल्स एकमेकांच्या टेबल्समध्ये थेट प्रवेश करत नाहीत**. दुसऱ्या मॉड्यूलच्या डेटासह काम करण्यासाठी, त्या मॉड्यूलमधील फंक्शन इम्पोर्ट करा.

```ts
// ❌ चुकीचे: दुसऱ्या मॉड्यूलमधून थेट SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ योग्य: providers मॉड्यूलचे फंक्शन वापरा
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

हा नियम कोड पुनरावलोकनाद्वारे लागू केला जातो — यासाठी कोणतीही स्थिर तपासणी नाही, परंतु उल्लंघने निदर्शनास आणली जातात.

### अतिरिक्त तक्ते (नंतरच्या migrations द्वारे जोडलेले)

- `mcp_*` तक्ते — MCP सर्व्हर ऑडिट
- `a2a_*` तक्ते — A2A कार्य स्थिती
- `usage_*` तक्ते — वापराचा मागोवा

- `compression_*` तक्ते — कॉम्प्रेशन प्रणाली
- `webhook_*` तक्ते — वेबहुक वितरण लॉग
- `acp_*` तक्ते — एजंट क्लायंट प्रोटोकॉल
- `oneproxy_*` तक्ते — 1proxy मार्केटप्लेस
- `proxy_assignments` — प्रॉक्सी व्याप्ती बाइंडिंग्ज
- `detailed_call_artifacts` — कॉल लॉग आर्टिफॅक्ट्सचे मेटाडेटा

- `command_code_auth_sessions` — कमांड कोड OAuth सत्रे

## स्थलांतर

OmniRoute वापरते** आवृत्तीबद्ध, निर्दोष स्थलांतर** `src/lib/db/migrations/` मध्ये प्रत्येक स्थलांतर एकच SQL फाइल आहे. दोन नामकरण स्वरूप एकत्र आहेत; `_omniroute_migrations` मध्ये रेकॉर्ड केलेली आवृत्ती अंकीय उपसर्ग आहे.

### स्थलांतर नामकरण

| स्वरूप                                         | उदाहरण                               | साठी वापरले जाते                                                                                                                                         |
| ---------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (नक्की 3 अंक)            | `241_seen_models.sql`                | जुनी मालिका `001`–`241`. टाइमस्टॅम्प फॉरमॅट उतरल्यावर गोठवले (`240` आणि `241` त्याच्या आधी विलीन केले गेले): कोणत्याही नवीन फाइलला अनुक्रमांक मिळत नाही. |
| `YYYYMMDDHHMMSS_description.sql` (14 अंक, UTC) | `20261113120000_add_usage_index.sql` | 2026-11-13 पासून तयार झालेले प्रत्येक स्थलांतर.                                                                                                          |

बदल का: अनुक्रमिक संख्यांसह, समांतर PRs समान पुढील संख्या निवडली आणि विलीन होण्याआधी एक सोडून सर्वांची संख्या पुनर्संख्या होती. UTC टाइमस्टॅम्प प्रत्येक PR त्याची स्वतःची आवृत्ती देतो.

टाइमस्टॅम्प फॉरमॅटचे नियम ( `npm run check:migration-numbering` द्वारे लागू केलेले, `scripts/check/lib/migrationNaming.mjs` मध्ये जनरेटरसह सामायिक केलेले):

- टाइमस्टॅम्प ही वास्तविक UTC तारीख आणि वेळ आहे, `20261113000000` पेक्षा पूर्वीची नाही आणि भविष्यात 10 मिनिटांपेक्षा जास्त नाही.
- वर्णन लोअरकेस `snake_case` अक्षराने सुरू होणारे आहे (`a-z`, `0-9`, शब्दांमधील एकल `_` ), जास्तीत जास्त 80 वर्ण.
- एकाच टाइमस्टॅम्पसह दोन फाइल्स डुप्लिकेट आहेत.
- नो-गॅप नियम फक्त जुन्या मालिकांना लागू होतो: `001` ते `241` पर्यंतची प्रत्येक संख्या `026`, `055` आणि `121` या ज्ञात अंतरांशिवाय अस्तित्वात असणे आवश्यक आहे. `241` (किंवा कोणतीही जुनी फाइल) हटवल्याने गेट अयशस्वी होते. `001` आणि `241` कधीही `KNOWN_GAPS` अनुमत सूचीमध्ये जोडले जाऊ शकत नाहीत. टाइमस्टॅम्प केलेल्या फायली कधीही अंतर निर्माण करत नाहीत.
- `src/lib/db/migrations/` मधील प्रत्येक एंट्री वैध लोअरकेस `.sql` नावासह नियमित फाइल असणे आवश्यक आहे. डिरेक्टरी, सिमलिंक, `.SQL` किंवा `.sql.bak` फाइल, छुपी फाइल किंवा स्पेस असलेले नाव गेट अयशस्वी करते, कारण धावणारा तो शांतपणे वगळतो किंवा बूट करताना क्रॅश होतो.

**ऑर्डर लागू करा.** रनर उपसर्गाच्या अंकीय मूल्यानुसार क्रमवारी लावतो, मजकूरानुसार नाही: जुन्या `001`–`241` फाइल्स प्रथम, नंतर टाइमस्टॅम्प क्रमाने टाइमस्टॅम्प केलेल्या फाइल्स, नंतर `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` ( `ee-001` सारख्या आवृत्त्या) सह नोंदणीकृत कोणत्याही नेमस्पेस निर्देशिका. प्रलंबित स्थलांतर ही कोणतीही फाईल आहे जिची आवृत्ती `_omniroute_migrations` मध्ये नाही, म्हणून जुन्या शाखेतून स्थलांतरण जे नवीन नंतर विलीन होते ते अद्याप विद्यमान डेटाबेसवर लागू होते.

**टाइमस्टॅम्प हा क्रिएशन ऑर्डर आहे, मर्ज ऑर्डर नाही.** जर तुमचे स्थलांतर अ सह स्थलांतराने तयार केलेल्या टेबल किंवा स्तंभावर अवलंबून असेल** नवीन** टाइमस्टॅम्प (उदाहरणार्थ, प्रथम विलीन झालेल्या दुसऱ्या PR मधील एक), एक नवीन डेटाबेस प्रथम तुमचा रन करेल आणि अयशस्वी होईल. तुमचे PR अजूनही उघडे असताना, फाईलचे नाव `npm run db:new-migration` सह पुन्हा निर्माण करा जेणेकरून त्यास नवीन टाइमस्टॅम्प मिळेल किंवा ते स्वतंत्र करा. `npm run test:migrations:fresh` रिकाम्या डेटाबेसवर प्रत्येक स्थलांतर लागू करते आणि ते पकडते.

### विलीन केलेले स्थलांतर कधीही हटवले जात नाही किंवा पुनर्नामित केले जात नाही

एकदा माइग्रेशन फाइल रिलीझ ब्रँच किंवा `main` वर आली की, ती आधीपासून homolog आणि डेव्हलपर डेटाबेसवर, VPS इंस्टॉलवर आणि एंटरप्राइझ सिंकमध्ये चालते. तेव्हापासून:

- **ते कधीही हटवू नका.** अपग्रेड केलेले डेटाबेस ते ठेवत असताना फ्रेश इन्स्टॉल स्कीमा गमावतील.
- **त्याचे नाव कधीही बदलू नका.** `_omniroute_migrations` मधील आवृत्ती यापुढे फाइलशी जुळणार नाही, त्यामुळे आधीपासून लागू केलेला प्रत्येक डेटाबेस ती पुन्हा चालवेल. नॉन-इडम्पोटंट SQL नंतर डेटा डुप्लिकेट करते किंवा बूट थांबवते.
- **वेगळ्या स्कीमाची आवश्यकता आहे?** `npm run db:new-migration` सह नवीन स्थलांतर तयार करा.

पुनर्नामित करणे केवळ अशा फाईलसाठी सुरक्षित आहे जी अद्याप विलीन केलेली नाही, ज्या बाबतीत गेटचे संकेत संदर्भित आहेत. रिलीझ टॅग येथे काहीही बदलत नाही: `release/v*` शाखेतील प्रत्येक पुश Docker `:next` प्रतिमा प्रकाशित करते आणि homolog, VPS इंस्टॉल आणि एंटरप्राइझ सिंकवर चालते, म्हणून कोणतेही `vX.Y.Z` टॅग अस्तित्वात येण्यापूर्वी विलीन केलेले स्थलांतर वास्तविक डेटाबेसवर चालते. गेट बेस फाइलच्या प्रत्येक काढण्यात अपयशी ठरते, टॅग केलेली किंवा नाही.

- **विलीन केलेले स्थलांतर परत करत आहे.** फाईल हटवणारा `git revert` गेट अयशस्वी करतो. फाइल ठेवा आणि तिचा स्कीमा नवीन स्थलांतरामध्ये पूर्ववत करा: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` आणि असेच. अपग्रेड केलेले आणि नवीन डेटाबेस नंतर त्याच स्कीमासह समाप्त होतात.
- **एक स्वीकृत पुनर्नाव: एक सुसंगतता प्रविष्टी आणि समान सामग्री.** विलीन केलेली फाईल हलवणे आवश्यक असल्यास (उदाहरणार्थ, दोन विलीन केलेल्या फायली टाइमस्टॅम्प सामायिक करतात आणि धावणारा आवृत्ती टक्कर देऊन थांबतो), नंतरच्या SQL स्पर्श न करता त्याचे नाव बदला आणि `src/lib/db/migrationRunner/constants.ts` मध्ये `{ fromVersion, fromName, toVersion, toName }` ला `RENAMED_MIGRATION_COMPATIBILITY` मध्ये जोडा. जुनी आवृत्ती लागू करणाऱ्या डेटाबेसना फाइल पुन्हा चालवण्याऐवजी त्यांची `_omniroute_migrations` पंक्ती हलवली जाते. गेट अशा नावाच्या बदलाविषयी चेतावणी देतो आणि नवीन टाइमस्टॅम्प काहीही असो, त्यावर नेहमी कम्युटेशन चेक चालवतो: नवीन इंस्टॉलेशन्स फाइलला तिच्या नवीन स्थानावर लागू करतात, अपग्रेड केलेले डेटाबेस तसे करत नाहीत, त्यामुळे जुन्याच्या जवळ एक नवीन टाइमस्टॅम्प निवडा. जर सामग्री बदलली असेल (स्कीमा बदल अद्याप नवीन स्थलांतरात असेल) किंवा एंट्रीची लक्ष्य फाइल डिस्कवर नसेल तर गेट नाव बदलण्यात अपयशी ठरते.
- **त्याच टाइमस्टॅम्पमध्ये कधीही नाव बदलू नका.** टाइमस्टॅम्प ठेवणारे आणि केवळ वर्णन बदलणारे नाव एंट्रीसह किंवा त्याशिवाय गेट अयशस्वी करते. `toVersion` त्याच्या `fromVersion` च्या बरोबरीच्या एंट्रीसह, धावणारा जुनी `_omniroute_migrations` पंक्ती हटवतो आणि फाइल आधीपासून चालवलेल्या प्रत्येक डेटाबेसवर पुन्हा लागू करतो. एंट्रीशिवाय, धावपटू फक्त आवृत्तीचा मागोवा घेतो: ते त्या डेटाबेसवरील फाइल वगळते (नवीन सामग्री तेथे कधीही चालत नाही) आणि प्रत्येक बूटवर पुनर्क्रमण त्रुटी लॉग करते. दुसरा टाइमस्टॅम्प वापरा आणि एक सुसंगतता एंट्री वापरा किंवा नाव ठेवा.
- **गेट तपासते की पुनर्नामित फाइल पुन्हा चालत नाही.** प्रत्येक कव्हर केलेल्या नामांतरासाठी, गेट नवीन फाइल नाव `--must-not-apply` सह कम्युटेशन चेकमध्ये पास करते. चेक रिअल रनरसह अपग्रेड केलेला डेटाबेस बूट करतो आणि जर रनरने ती फाईल पुन्हा लागू केली (उदाहरणार्थ, एंट्रीमध्ये चुकीची आवृत्ती किंवा नाव असल्यामुळे किंवा गेटच्या मजकूर पार्सरने TypeScript पेक्षा वेगळ्या पद्धतीने `constants.ts` वाचल्यामुळे), गेट `migration renomeada rodaria de novo` सह अयशस्वी होते आणि तुम्हाला एंट्रीच्या जुन्या आणि नवीन आवृत्त्या आणि नाव तपासण्यास सांगते.

### गेट बेस विरुद्ध काय तपासतो

पुल रिक्वेस्ट आणि मर्ज-क्यू रन केल्यावर, `npm run check:migration-numbering` डिस्कवरील `src/lib/db/migrations/` बेस ब्रँचवरील समान निर्देशिकेशी तुलना करते. या क्रमाने आधार आहे: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` व्हेरिएबल, किंवा, जेव्हा `GITHUB_EVENT_NAME` `pull_request`, `pull_request_target` किंवा `merge_group` असतो, तेव्हा मर्ज कमिटचा पहिला पालक, इव्हेंट पेलोडचा `merge_group.base_sha` किंवा `git merge-base HEAD origin/$GITHUB_BASE_REF`. रिझोल्व्हेबल बेसशिवाय पुल रिक्वेस्ट किंवा मर्ज-क्यूमध्ये गेट अयशस्वी होते. `--base` शिवाय CI बाहेर ते `comparação com a base: pulada (sem --base)` प्रिंट करते आणि हे नियम वगळते.

`--base-latest-tag` नवीनतम रिलीझ टॅगशी तुलना करते (`vX.Y.Z` semver क्रमाने; प्रत्यय टॅग जसे की नाइटलीज मोजत नाहीत) जे `HEAD` च्या इतिहासात आहे, `--base` सारख्याच नियमांसह. रिलीज-ग्रीन (`scripts/quality/validate-release-green.mjs`) गेट अशा प्रकारे चालवते, कारण पुश आणि शेड्यूल केलेल्या धावांना पुल रिक्वेस्ट बेस नसतो आणि मर्ज नवीन CI रनशिवाय उतरू शकतो. इतिहासात कोणतेही प्रकाशन टॅग नसल्यामुळे गेट अयशस्वी होते; `git fetch --tags` चालवा ( CI मध्ये, `actions/checkout` सह `fetch-depth: 0` टॅग आणते).

कम्युटेशन चेकच्या एका रनमध्ये ऑर्डरबाह्य, संपादित केलेल्या आणि पुनर्नामित केलेल्या फायली एकत्र येतात.

कम्युटेशन चेक (`scripts/check/migration-commutation.ts`) वास्तविक स्थापना मार्गासह दोन तात्पुरते डेटाबेस तयार करते: एक** अपग्रेड केले** एक (बेस माइग्रेशन्ससह बूट करा, नंतर पुल रिक्वेस्टच्या स्थलांतरासह त्याच फाइलवर पुन्हा बूट करा) आणि a** ताजे** एक (पुल विनंतीच्या स्थलांतरासह एक बूट). हे परिणामी स्कीमाची तुलना करते: सारण्या आणि स्तंभ (स्तंभ क्रमाकडे दुर्लक्ष करून), UNIQUE / PRIMARY KEY आणि FOREIGN KEY मर्यादा, प्रत्येक सारणीचा सामान्यीकृत `CREATE TABLE` मजकूर (ज्यामध्ये CHECK मर्यादा, कोलेशन, व्युत्पन्न केलेले स्तंभ आणि इंडेक्स पर्याय समाविष्ट आहेत), टेबल पर्याय. पंक्ती डेटाची तुलना केली जात नाही. जर ते जुळले, तर गेट प्रिंट करतो की फाइल व्यवस्थित नाही परंतु प्रवास करते आणि पास होते. जर ते वेगळे असतील तर, फरकासह गेट अयशस्वी झाले आणि केससाठी एक इशारा: ऑर्डरबाह्य फाइलसाठी, त्याचे नाव `npm run db:new-migration` ने पुन्हा निर्माण करा, जे सुरक्षित आहे कारण फाइल अद्याप विलीन केलेली नाही; संपादित बेस फाइलसाठी, मूळ सामग्री पुनर्संचयित करा आणि नवीन स्थलांतरामध्ये बदल करा; पुनर्नामित केलेल्या फाईलसाठी, पुनर्नामित पूर्ववत करा किंवा दुसरा नवीन टाइमस्टॅम्प निवडा जिथे तो प्रवास करतो, दुसऱ्या नावाचा समान टाइमस्टॅम्प कधीही घेऊ नका. चेक स्वतः चालू शकत नसल्यास, गेट CI मध्ये अयशस्वी होते आणि फक्त स्थानिक पातळीवर चेतावणी देते. संपादित बेस फाइलसाठी, अपग्रेड केलेला डेटाबेस त्या फाइलच्या बेसच्या सामग्रीसह तयार केला जातो आणि दुसरा बूट तो वगळतो कारण त्याची आवृत्ती आधीच रेकॉर्ड केलेली असते. पुनर्नामित केलेल्या फाईलसाठी, अपग्रेड केलेला डेटाबेस त्याच्या जुन्या नावाखाली फाइलसह तयार केला जातो आणि दुसरा बूट पुन्हा चालवण्याऐवजी त्याची `_omniroute_migrations` पंक्ती सुसंगतता एंट्रीद्वारे हलवते; गेट नवीन नाव `--must-not-apply` ने पास करते, त्यामुळे दुसरा बूट लागू झाल्यास चेक अयशस्वी होतो. अपग्रेड केलेल्या मार्गावर पुल रिक्वेस्ट माइग्रेशन लागू करण्यात अयशस्वी झाल्यास, म्हणजेच, प्रत्येक बेस माइग्रेशननंतर (ते नवीन इन्स्टॉल करताना देखील अयशस्वी झाले की नाही), गेट `migration do PR não aplica` अहवाल देतो आणि तुम्हाला बेसच्या सध्याच्या स्कीमाच्या विरुद्ध SQL निश्चित करण्यास सांगतो; फाईल नंतरच्या टाइमस्टॅम्पसह दुसऱ्या पुल विनंती स्थलांतरावर अवलंबून असल्यास, `npm run db:new-migration` सह तिचे नाव पुन्हा निर्माण करा.

स्थानिक पातळीवर समान तुलना चालविण्यासाठी, बेस स्पष्टपणे पास करा, उदाहरणार्थ `npm run check:migration-numbering -- --base origin/<base-branch>`, किंवा नवीनतम प्रकाशनाशी तुलना करण्यासाठी `npm run check:migration-numbering -- --base-latest-tag`.

### ओपन PR चे `NNN` स्थलांतर

स्विच करण्यापूर्वी उघडलेली पुल विनंती अद्याप `242_add_widgets.sql` सारखी अनुक्रमिक फाइल असू शकते. `241` वरील जुने क्रमांक नाकारले गेले आहेत, म्हणून विलीन करण्यापूर्वी ते रूपांतरित करा:

1. **वर्णन ठेवून जनरेटरसह फाइलचे नाव बदला.** नवीन नाव मिळविण्यासाठी `npm run db:new-migration -- <same description>` चालवा, त्यात SQL हलवा आणि जुनी `NNN_` फाइल हटवा. वर्णन सारखेच असले पाहिजे: खालील सुसंगतता एंट्री त्यावर जुळते.
2. **जर कायमचा डेटाबेस जुना क्रमांक चालवत असेल तर एक सुसंगतता प्रविष्टी जोडा.** जर कोणताही डेटाबेस ठेवला असेल (होमोलॉग, एक VPS, योगदानकर्त्याची स्वतःची स्थापना) `NNN_` फाइलसह PR ची बिल्ड चालवली असेल तर `src/lib/db/migrationRunner/constants.ts` मध्ये `RENAMED_MIGRATION_COMPATIBILITY` ला `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` जोडा. हे आहे** `237` ते `241` साठी आवश्यक** : त्या स्लॉटमध्ये आता कॅनोनिकल `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` आणि `241_seen_models.sql` धारण केले आहे आणि एंट्रीशिवाय असा डेटाबेस कॅनॉनिकल स्थलांतर कायमचा वगळतो आणि रूपांतरित केलेला पुन्हा चालवतो. हे एका स्लॉटसाठी देखील कार्य करते जे रिक्त राहते, जसे की `242`, जेव्हा गंतव्य टाइमस्टॅम्प असते. शंका असल्यास, एंट्री जोडा. तुम्ही ते ॲरेमध्ये कुठे जोडता याने काही फरक पडत नाही: जेव्हा एंट्रीच्या टार्गेट स्लॉटमध्ये एक पंक्ती असते जी दुसरी एंट्री दूर जाते (उदाहरणार्थ `237` PR पंक्ती धरलेली असते तर जुनी `usage_history_calculated_cost` पंक्ती `237` मध्ये जाण्याची वाट पाहत असते), रनर त्या एंट्रीला स्लॉट मोकळे होईपर्यंत प्रतीक्षा करू देतो. केवळ खरा संघर्ष, जसे की एका पंक्तीने धरलेला स्लॉट, नो एंट्री मूव्ह, किंवा दोन नोंदी ज्या स्लॉट स्वॅप करतात, `Cannot reconcile ...` सह बूट थांबवतात.
3. **SQL निर्दयी ठेवा** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), कारण रूपांतरित स्थलांतर डेटाबेसला भेटू शकते जिथे त्याचा स्कीमा आधीच अस्तित्वात आहे.
4. **आवृत्ती-कीड विशेष केस हलवा.** PR त्याच्या जुन्या क्रमांकासाठी `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) किंवा `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) मध्ये केस जोडल्यास, नवीन टाइमस्टॅम्पमध्ये की बदला.

`tests/unit/db/codex-fence-migration-rename.test.ts` हे पुनर्नामित स्थलांतरासाठी चाचणीचे कार्यरत उदाहरण आहे.

### स्विच करण्यापूर्वी शाखांना बॅकपोर्ट

कधीही चेरी-पिक किंवा `YYYYMMDDHHMMSS_` फाईल स्वीचच्या आधीच्या शाखेत बॅकपोर्ट करू नका (उदाहरणार्थ जुनी `release/v*` शाखा). तेथे धावणारा फाईलची नावे मजकूर म्हणून वर्गीकृत करतो, त्यामुळे टाइमस्टँप केलेली फाईल `201_` आणि `202_` दरम्यान ताज्या डेटाबेसवर चालते आणि जुन्या गेटला 14-अंकी उपसर्ग समजत नाहीत. अशा शाखेवर, त्या शाखेची स्वतःची पुढची `NNN_` फाईल, idempotent असा बदल लिहा, त्यामुळे टाइमस्टँप केलेली आवृत्ती नंतर येईल तेव्हा ते नो-ऑप आहे.

### स्थलांतर कसे चालते

स्टार्टअपवर, `migrationRunner.ts`:

1. अस्तित्वात नसल्यास `_omniroute_migrations` सारणी तयार करते
2. आधीच लागू केलेल्या स्थलांतरासाठी क्वेरी
3. कोणतेही नवीन स्थलांतर क्रमाने लागू करते, प्रत्येक व्यवहारात
4. टाइमस्टॅम्पसह लागू केलेल्या प्रत्येक स्थलांतराची नोंद करते

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### निर्बुद्धता

स्थलांतर होणे आवश्यक आहे** अशक्त** — त्यांना दोनदा चालवणे नो-ऑप असावे:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, आणि `OR IGNORE` / `OR REPLACE` कलमे उदारपणे वापरा.

### नवीन स्थलांतर जोडत आहे

1. **जनरेटरसह फाइल तयार करा** : `npm run db:new-migration -- <description>` (उदाहरणार्थ `npm run db:new-migration -- add combo priority`). हे वर्तमान UTC वेळ आणि टिप्पणी शीर्षलेखासह `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` लिहिते, जर तो टाइमस्टॅम्प घेतला असेल तर एक सेकंद पुढे सरकतो आणि फाइल कधीही ओव्हरराईट करत नाही. हाताने नंबर घेऊ नका.
2. **सुरक्षित DDL वापरा** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **डेटा काळजीपूर्वक बॅकफिल करा** : विद्यमान पंक्ती हाताळण्यासाठी `UPDATE ... WHERE ...` वापरा
4. **ऑर्डर आणि नामकरण तपासा** : `npm run test:migrations:fresh` (रिक्त डेटाबेसवरील सर्व स्थलांतर) आणि `npm run check:migration-numbering`
5. **कॉपीवर चाचणी घ्या** : उत्पादनावर कधीही न तपासलेले स्थलांतर करू नका

उदाहरण:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **मागे-विसंगत बदल** (उदा., स्तंभ सोडणे) अवघड आहेत. एकदा स्थलांतर लागू झाल्यानंतर OmniRoute NOT डाउनग्रेड — ला समर्थन देते, स्कीमा बदल कायमचा असतो. त्यानुसार नियोजन करा.

## संग्रहित डेटाचे कूटलेखन

संवेदनशील फील्ड (API कळा, OAuth टोकन, कनेक्शन स्ट्रिंग) **AES-256-GCM** वापरून संग्रहित स्थितीत कूटबद्ध केली जातात.

### ते कसे कार्य करते

```ts
// src/lib/db/encryption.ts (सुलभीकृत)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### ते कुठे वापरले जाते

- `provider_connections.api_key` — ॲप्लिकेशन स्तरावर कूटबद्ध
- `provider_connections.access_token`, `refresh_token`, `id_token` — ॲप्लिकेशन स्तरावर कूटबद्ध
- `namespace = "secrets"` असलेल्या `key_value` नोंदी — ॲप्लिकेशन स्तरावर कूटबद्ध
- `proxy_registry.auth` — ॲप्लिकेशन स्तरावर कूटबद्ध (उपस्थित असल्यास)

### कूटलेखन कळ

कूटलेखन कळ एका **पासफ्रेज**वरून (`STORAGE_ENCRYPTION_KEY` पर्यावरण चलाद्वारे सेट केलेली) आणि एका **सॉल्ट**वरून (DB मध्ये संग्रहित) व्युत्पन्न केली जाते. डेटा विकूटबद्ध करण्यासाठी दोन्ही आवश्यक आहेत.

```bash
# सुरक्षित पासफ्रेज तयार करा
openssl rand -hex 32

# .env मध्ये सेट करा
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **अत्यंत महत्त्वाचे**: कूटलेखन कळ हरवल्यास सर्व कूटबद्ध डेटावरील प्रवेश गमावला जाईल. **कळीचा बॅकअप डेटाबेसपासून स्वतंत्रपणे घ्या**.

### काय कूटबद्ध केले जात नाही

कार्यक्षमतेच्या कारणांमुळे, पुढील माहिती साध्या मजकूरात संग्रहित केली जाते:

- प्रदात्यांची प्रदर्शन नावे
- मॉडेल व्याख्या (आधीपासूनच सार्वजनिक)
- राउटिंग नियम
- वापर नोंदी (कोणतीही PII नाही)

दोन एन्क्रिप्शन योजना पारदर्शकपणे हाताळण्यासाठी OmniRoute **`migrateLegacyEncryptedString()`** वापरते:

| व्हेरिएबल                                   | डीफॉल्ट | वर्णन                                                                                                                                |
| ------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000` | मिलीसेकंदांमधील टिक अंतराल (किमान `5000`). जुळणाऱ्या cron मिनिटाच्या आत विश्वसनीयपणे येण्यासाठी ते 60 सेकंदांपेक्षा कमी असले पाहिजे. |

## कामगिरी ट्यूनिंग

### WAL मोड

WAL डीफॉल्टनुसार सक्षम आहे. उच्च-लेखन वर्कलोडसाठी, विचार करा:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` सेट करत नाही. चेकपॉईंट WAL फ्रेम्स मुख्य फाईलमध्ये हलवते, परंतु WAL फाइल तिचा सर्वात मोठा वाटप केलेला आकार ठेवते. `OMNIROUTE_WAL_GUARD_MAX_MB` गार्ड फक्त चेतावणी देतो आणि `wal_checkpoint(RESTART)` चालवतो; ती डिस्क-आकाराची टोपी नाही.

### निर्देशांक

कार्यप्रदर्शनासाठी प्रमुख निर्देशांक (स्थलांतराने स्वयं-निर्मित):

- प्रदात्याद्वारे`idx_models_provider` — मॉडेल लुकअप
- `idx_combo_targets_combo_id` — कॉम्बो लक्ष्य विस्तार
- `idx_usage_history_api_key_timestamp` — वापर विश्लेषण
- `idx_quota_snapshots_api_key_window` — कोटा ट्रॅकिंग
- `idx_call_logs_timestamp` — कॉल लॉग क्वेरी

नवीन अनुक्रमणिका जोडण्यासाठी, एक स्थलांतर तयार करा:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### मेमरी-मॅप्ड I/O

खूप मोठ्या डेटाबेससाठी (> 10GB), मेमरी मॅपिंग SQLite pragma द्वारे समायोजित केले जाऊ शकते:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### कॉम्पॅक्शन

दीर्घकाळ चालू असलेल्या OmniRoute उदाहरणांना अधूनमधून `VACUUM` चा फायदा होतो:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

कमी रहदारीच्या खिडक्या दरम्यान मासिक चालवा. (WAL मोड गरज कमी करते, परंतु ती दूर करत नाही.)

## आरोग्य तपासणी

`src/lib/db/healthCheck.ts` **डेटाबेस-स्तरीय आरोग्य निदान** प्रदान करते:

दोन्ही व्हर्बसाठी प्रमाणीकरण आवश्यक आहे (अन्यथा `401`). `GET` केवळ निदान करते; `POST`, `autoRepair` सक्षम करून तीच तपासणी चालवते.

```bash
GET  /api/db/health   # निदान करा
POST /api/db/health   # निदान करा + दुरुस्ती करा
```

प्रतिसादामध्ये `runDbHealthCheck()` द्वारे तयार केलेला `DbHealthCheckResult` असतो
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "डोमेन बजेटमध्ये यापुढे अस्तित्वात नसलेल्या API कीचा संदर्भ होता.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| फील्ड             | अर्थ                                                                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | `issues` रिकामे असताना `true`. `driver` यावर कधीही परिणाम करत नाही.                                                                      |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` यांपैकी एक.                                              |
| `repairedCount`   | या रनदरम्यान दुरुस्त केलेल्या पंक्ती; `autoRepair` false असताना नेहमी `0`.                                                               |
| `backupCreated`   | दुरुस्तीपूर्वी बॅकअप घेतला होता का.                                                                                                      |
| `checkedAt`       | रन आणि त्याद्वारे लिहिल्या जाणाऱ्या कोणत्याही दुरुस्ती नोंदीमध्ये सामायिक असलेला ISO टाइमस्टॅम्प.                                        |
| `driver.name`     | तपासलेल्या डेटाबेसला सेवा देणारा SQLite ड्रायव्हर.                                                                                       |
| `driver.degraded` | लेखन डेटाबेस फाइलमध्ये कायमस्वरूपी जतन केले जात नसल्यास `true` — `sql.js` WASM फॉलबॅक (संपूर्ण-फाइल पर्सिस्टन्स) किंवा इन-मेमरी डेटाबेस. |

तोच पेलोड `omniroute_db_health_check` MCP टूलद्वारे परत केला जातो.

डेटा करप्शन शोधण्यासाठी `PRAGMA integrity_check` चालवा:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# हे प्रिंट झाले पाहिजे: ok
```

जर `ok` व्यतिरिक्त काहीही परत आले, तर **डेटाबेसचा वापर त्वरित थांबवा** आणि बॅकअपमधून पुनर्संचयित करा.

## आपत्ती पुनर्प्राप्ती

### परिस्थिती 1: WAL फाइल हरवली

`-wal` फाइल सापडत नाही, परंतु `-shm` आणि मुख्य DB अखंड आहेत:

```bash
# पुढील वेळी उघडल्यावर स्वयंचलितपणे पुनर्प्राप्त होते
omniroute
```

SQLite स्वयंचलितपणे पुनर्प्राप्त करू शकत नसल्यास:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### परिस्थिती 2: मुख्य DB फाइल दूषित झाली

बॅकअपमधून पुनर्संचयित करा:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` फक्त कार्यरत सर्व्हरवरून संपूर्ण `.tar.gz` संग्रहण डाउनलोड करते
(`GET /api/db-backups/exportAll`, ऑपरेटरचे क्रेडेन्शियल आवश्यक); ते कोणतीही गोष्ट पुनर्संचयित करत नाही.

### परिस्थिती 3: एन्क्रिप्शन की हरवली

कीशिवाय **पुनर्प्राप्ती शक्य नाही**. एन्क्रिप्ट केलेली फील्ड वाचता येत नाहीत. नवीन क्रेडेन्शियलसह सर्व प्रोव्हायडर स्वहस्ते पुन्हा जोडा.

> **जोखीम कमी करण्याचा उपाय**: एन्क्रिप्शन कीचा बॅकअप नेहमी स्वतंत्रपणे घ्या; शक्यतो पासवर्ड मॅनेजर किंवा KMS मध्ये.

### परिस्थिती 4: डिस्क पूर्ण भरली

SQLite `SQLITE_FULL` त्रुटी परत करेल. डिस्कवरील जागा मोकळी करा, त्यानंतर:

```bash
# जागा मोकळी करण्यासाठी WAL चेकपॉइंट करा
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## समस्यानिवारण

### "डेटाबेस लॉक केलेला आहे"

दुसऱ्या प्रक्रियेने लेखन लॉक धरून ठेवला आहे. पुढीलपैकी एक करा:

- दुसरी प्रक्रिया पूर्ण होण्याची प्रतीक्षा करा (`lsof | grep storage.sqlite` तपासा)
- दुसरी प्रक्रिया बंद करा
- समस्या कायम राहिल्यास, OmniRoute पुन्हा सुरू करा

### "फॉरेन की कन्स्ट्रेंट अयशस्वी झाले"

एखादे डोमेन मॉड्यूल संदर्भात्मक अखंडतेचे उल्लंघन करत आहे. पुढील गोष्टी तपासा:

- अवलंबित टेबलमधील अनाथ पंक्ती
- प्रसारित न झालेले कॅस्केडिंग डिलीट्स
- फॉरेन की बदलणारे अलीकडील माइग्रेशन

उल्लंघने शोधण्यासाठी `PRAGMA foreign_key_check;` चालवा.

### "मेमरी अपुरी आहे"

SQLite चे मेमरी-मॅप केलेले I/O OS मर्यादेपेक्षा अधिक आहे. SQLite pragma वापरून ते कमी करा:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB ऐवजी 128MB
```

किंवा ते अक्षम करा:

```sql
PRAGMA mmap_size = 0;
```

### "माइग्रेशन अर्ध्यावर अयशस्वी झाले"

माइग्रेशन ट्रान्झॅक्शनमध्ये चालवले गेले होते, त्यामुळे ते रोलबॅक झालेले असायला हवे. तसे झाले नसल्यास:

1. **OmniRoute थांबवा** (पुढील प्रयत्न टाळा)
2. `sqlite3` वापरून **DB ची स्थिती तपासा**
3. अर्धवट माइग्रेशन **मॅन्युअली दुरुस्त करा**
4. OmniRoute **पुन्हा चालवा** (माइग्रेशनचा पुन्हा प्रयत्न केला जाईल)

हे टाळण्यासाठी, माइग्रेशन्सची नेहमी प्रथम एका प्रतीवर चाचणी करा.
