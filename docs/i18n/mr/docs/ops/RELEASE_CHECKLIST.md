## npm Trusted Publishing (v3.8.51 पासून डीफॉल्ट) — विनंतीनुसार staged, पर्याय म्हणून direct

`npm-publish.yml` डीफॉल्टनुसार **npm Trusted Publishing (OIDC)** द्वारे प्रकाशित करते:
`stage-npm` job (github-hosted) त्या रनसाठी GitHub च्या id-token ची अल्पकालीन npm
credential शी देवाणघेवाण करते — repository secrets मध्ये दीर्घकालीन npm token नाही, 2FA prompt नाही आणि provenance जोडलेला असतो.
2FA वगळणारे token निवृत्त केले जात असल्यामुळे npm आता मान्य करत असलेला हा bypass आहे;
यामुळे WS1.3 ची हमी कायम ठेवत प्रकल्पात v3.8.48 पर्यंत असलेला पूर्णपणे स्वयंचलित
प्रवाह पुन्हा उपलब्ध होतो (लीक झालेला token एकट्याने प्रकाशित करू शकत नाही — कारण token अस्तित्वातच नाही).

**एकदाच करायचे सेटअप (मालक):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none). हे अस्तित्वात येईपर्यंत स्वयंचलित पायरी `ENEEDAUTH` सह अयशस्वी होते:
`publish_mode=staged` (खाली) किंवा `direct` वापरून पुन्हा dispatch करा.

### Staged प्रकाशन (विनंतीनुसार — `publish_mode=staged`)

npm-publish workflow आता थेट प्रकाशित करत नाही: ती पॅक केलेला tarball
(`check:pack-boot`) बूट करते आणि नंतर `npm stage publish` चालवते — नेमके तेच bytes registry वर ठेवले जातात,
परंतु मालकाने मंजुरी देईपर्यंत ते **इन्स्टॉल करता येत नाहीत**. मानवी 2FA तपासणी
पुराव्याआधी नव्हे, तर त्यानंतर हलवली आहे.

**workflow हिरवी झाल्यानंतरचा मालकाचा प्रवाह:**

1. `npm stage list omniroute` — stage id शोधा (तो workflow summary मध्येही छापला जातो).
2. staged bytes सत्यापित करा (शिफारस केलेले): `npm stage download <id>`, त्यानंतर डाउनलोड केलेला
   tarball तात्पुरत्या prefix मध्ये इन्स्टॉल करून तो बूट करा (`npm run check:pack-boot` CI मध्ये
   हाच pack→install→boot निकाल स्वयंचलित करते).
3. `npm stage approve <id>` — 2FA prompt म्हणजेच प्रकाशन. `npm stage reject <id>` ते रद्द करते.
4. प्रकाशनानंतरची सुरक्षा-जाळी: post-publish verifier (v3.8.49 योजनेतील WS1.4)
   सार्वजनिक registry मधून प्रकाशित आवृत्ती स्वच्छ container मध्ये इन्स्टॉल करून ती बूट करते.

**आणीबाणीतील पर्याय:** `publish_mode=direct` सह `workflow_dispatch` केल्यास जुने
तात्काळ `npm publish` पुनर्स्थापित होते (staging मध्येच बिघाड झाल्यास फक्त तेव्हाच वापरा; कारण नोंदवा).

**एकदाच करायचे hardening (मालक, npmjs.com):** `omniroute` साठी Trusted Publisher
stage-only mode मध्ये configure करा, जेणेकरून लीक झालेला दीर्घकालीन token कुठूनही थेट `npm publish`
करू शकणार नाही — CI केवळ stage करू शकते; फक्त मालकाचे 2FA रिलीज करू शकते.

**दोषपूर्ण artifact साठी playbook (अपरिवर्तित):** डीफॉल्ट प्रतिसाद म्हणून
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` वापरा (काही मिनिटांत, परत पूर्ववत करता येण्याजोगे);
`npm unpublish` फक्त 72h/no-dependents मर्यादेत आणि पहिली कृती म्हणून कधीही नाही. Docker:
आवृत्तीचा tag कधीही पुन्हा लिहू नका — rollback म्हणजे `latest` ला शेवटच्या योग्य digest कडे पुन्हा निर्देशित करणे.

**Docker Hub `latest` (प्रत्येक स्थिर SemVer प्रकाशनासाठी आवश्यक):**
`docker-publish` workflow ने **दोन्ही** `X.Y.Z` आणि,
`should-promote-latest.sh` ही सर्वात उच्च स्थिर SemVer आवृत्ती असल्याचे मान्य करत असेल तेव्हा, `:latest`
यांना **समान digest** सह tag करणे आवश्यक आहे. job नंतर: Hub वरील `latest` digest नवीन
SemVer digest च्या समान असतो आणि `last_updated` पुढे सरकलेले असते. रिलीज नोंदींमध्ये फक्त git वर
अस्तित्वात असलेल्या सुधारणांचा उल्लेख असताना `:latest` एखाद्या जुन्या build वर ठेवू नका. Compose
quickstart मध्ये `:latest` वापरले जाते; GitOps ने `X.Y.Z` pin करणे सुरू ठेवावे.
[Docker रिलीज channels](../guides/DOCKER_GUIDE.md#release-channels) आणि #10317 पहा.

## हॉटफिक्स फास्ट-लेन (`hotfix` लेबल)

`hotfix` लेबल असलेला PR जड CI मॅट्रिक्स (9-शार्ड E2E, coverage ratchet,
quality-gate, quality-extended) वगळतो आणि जलद, उच्च-सिग्नल गेट्स कायम ठेवतो: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
आणि tarball boot-smoke (`check:pack-boot`). लक्ष्य: ~33min ऐवजी ≤15min मध्ये यशस्वी निकाल.

**प्रवेश धोरण — चारही अटी आवश्यक (Chromium/VS Code/Node आपत्कालीन लेन्सवर आधारित):**

1. **तीव्रता**: production बंद पडले आहे — प्रकाशित artifact boot होताना क्रॅश होते /
   सुरक्षा दुरुस्ती / रिलीजचा प्रत्येक वापरकर्ता प्रभावित झाला आहे. "महत्त्वाचे" म्हणजे "बंद पडलेले" नव्हे.
2. **अधिकार**: फक्त repository मालक `hotfix` लेबल लावतो. लेबल हेच
   अनुमोदन आहे — campaign PR वर ते स्वतःहून कधीही वापरू नका.
3. **पुरावा**: PR body मध्ये मागील पूर्णपणे यशस्वी heavy run ची लिंक (वगळलेले jobs
   जी suite पुन्हा validate करतील) आणि त्या दुरुस्तीची स्वतःची आधी अपयशी व नंतर यशस्वी झालेली test दिलेली असते.
4. **व्याप्ती**: फक्त cherry-pick — किमान आवश्यक दुरुस्ती, refactors नाहीत, असंबंधित बदल नाहीत.

वगळलेली coverage/ratchet व्याप्ती release branch वरील पुढील पूर्ण run द्वारे
पुन्हा validate केली जाते (सतत release-green) — ही lane फक्त प्रतीक्षा वगळते, validation कधीही नाही.
फक्त tests मधील बदल (`tests/` अंतर्गत सर्व files, `tests/e2e/` अंतर्गत एकही नाही) कोणत्याही
लेबलशिवाय E2E मॅट्रिक्स आपोआप वगळतात.

### लेआउट तयार करा

रेपॉजिटरी तीन वेगळ्या आउटपुट डिरेक्टरी वापरते — त्यांना कधीही मिसळत नाही:

| निर्देशिका | उद्देश                                                 | ट्रॅक केले?          |
| ---------- | ------------------------------------------------------ | -------------------- |
| `src/`     | अर्जाचा स्रोत (TypeScript / TSX)                       | होय                  |
| `.build/`  | बिल्ड इंटरमीडिएट्स — `next build` आउटपुट (`distDir`)   | नाही (गट दुर्लक्षित) |
| `dist/`    | `assembleStandalone` द्वारे शिप करण्यायोग्य npm बंडल — | नाही (गट दुर्लक्षित) |

> **ऑपरेटर टीप:** रिमोट VPS प्रतिमा निर्देशिका `/usr/lib/node_modules/omniroute/app/` राहते. फक्त द** इन-रेपो** बिल्ड आउटपुट हलवले (`app/` → `dist/`). रिमोट `dist/` `app/` — नाही VPS मार्ग बदल आवश्यक आहे.

**सिंगल-बिल्ड प्रवाह:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

NOT रन `npm run build` आणि त्यानंतर — तैनात करण्यासाठी स्वतंत्र `npm run build:cli` `npm run build:release` वापरा जे एका कमांडमध्ये स्वच्छ रीबिल्ड + सेंटिनल करते.

3.8.58 मध्ये फोर्कवर त्याचा सुरुवातीपासून शेवटपर्यंत पूर्वाभ्यास केला जातो आणि 3.8.59
[GO/NO-GO तपासणीसूची](./LTS_GO_NO_GO.md) सह पूर्ण होते.

### प्रायोगिक चाचणी (केवळ-वाचन, कधीही सुरक्षित)

```bash
npm run release:dry-run-lts-cut                       # प्रत्यक्ष शाखा-विभाजन: HEAD पासून 3.9.0, मागील टॅग v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # स्रोत कमिट निश्चित करा
```

`scripts/release/dry-run-lts-cut.mjs` काहीही कार्यान्वित करत नाही: ते git आणि `gh` वाचते आणि
संपूर्ण क्रम प्रिंट करते — पूर्वअटी (स्रोत रिझॉल्व्ह होतो, स्रोत रिपॉझिटरीमध्ये संपूर्ण इतिहास आहे —
शॅलो क्लोन `stable/v3` पुश करू शकत नाही, पहिल्या
ग्राफ्ट केलेल्या पॅरेंटवर प्राप्तकर्ता बाजू पॅक नाकारते, म्हणून संपूर्ण क्लोनमधून शाखा-विभाजन करा किंवा आधी `git fetch --unshallow origin` चालवा — मागील
टॅग अस्तित्वात आहे, `package.json` ही लक्ष्य आवृत्ती आहे, `release-freeze` इश्यू खुला आहे, अस्तित्वात असलेल्या
रिलीज शाखेवर कोणताही खुला `Release branch not green` इश्यू
नाही — अस्तित्वात नसलेली शाखा `?` अज्ञात दर्शवते, ती कधीही
हिरवी नसते — Mergify `release` रांग कॉन्फिगर केलेली आहे (G11: `queue_rules`, `checks_timeout`,
लेबल `queue`), `release/*` नियमसंच अजूनही हटवणे आणि फोर्स-पुश प्रतिबंधित करतो आणि
`stable/v3` व `develop` अद्याप अस्तित्वात नाहीत), दोन शाखा टप्पे, कोणते निष्क्रिय-वर्कफ्लो
ट्रिगर आणि `if:` अटी सत्य होतात (आणि कोणते रिपॉझिटरी व्हेरिएबलद्वारे प्रतिबंधित राहतात किंवा
कॅनॉनिकल रिपॉझिटरीशी निश्चित केलेले असतात), अपेक्षित dist-tags (`latest` → 3.9.0, `next` आणि
`nightly` रिकामे) आणि रोलबॅक. एक्झिट `0` = `RESULT: READY`, `1` = एखादी अवरोधक पूर्वअट
अयशस्वी झाली (`✗`), `2` = वापर त्रुटी. `--advisory <id,...>` तपासणी न लपवता तिला इशाऱ्याच्या (`!`)
पातळीवर आणते.

3.9.0 रिलीज फ्रीझ अद्याप खुला असतानाच प्रत्यक्ष शाखा-विभाजनाची प्रायोगिक चाचणी चालवा — टॅगनंतर आणि
टप्पा 12c मध्ये फ्रीझ हटवण्यापूर्वी शाखा तयार केल्या जातात.

### PR पूर्वावलोकन आर्टिफॅक्ट (एकदाच बिल्ड करा, त्याच बाइट्सना पुढे न्या)

`.github/workflows/preview-artifact.yml` PR हेडपासून एक प्रॉडक्शन टारबॉल बिल्ड करते आणि
नेमक्या त्याच बिल्डची पडताळणी करते (#8084 भाग (a)). केवळ त्याच रिपॉझिटरीतील PR; काहीही प्रकाशित केले जात नाही.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # किंवा `preview-artifact` लेबल जोडा
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # पूर्वावलोकन इंस्टॉल
```

ही रन `npm ci`, `npm run build:release`, `npm run check:pack-artifact` चालवते, टारबॉल
पॅक करते, `npm run check:pack-boot` (बनावट सिक्रेट्स, तात्पुरती डेटा डिरेक्टरी) चालवते, पुन्हा पॅक करते आणि
डायजेस्ट एकसारखा नसल्यास अयशस्वी होते; त्यानंतर `artifact-identity.json` (हेड SHA, बेस
SHA, लॉकफाइल हॅश, प्लॅटफॉर्म, आर्किटेक्चर, node ABI, बंडलर, बिल्ड धोरण —
`scripts/release/artifact-identity.mjs`) नोंदवते आणि स्वतंत्र जॉबमध्ये टारबॉलचे प्रमाणीकरण करते. पूर्वावलोकन
पुढे नेणे म्हणजे तो टारबॉल इंस्टॉल करणे: स्रोतापासून पुन्हा कधीही बिल्ड करू नका.

## रोलबॅक

रिलीजमध्ये गंभीर समस्या असल्यास:

1. `gh release edit vX.Y.Z --prerelease` (नवीनतम नसल्याचे चिन्हांकित करते)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (वापरकर्त्यांनी अद्याप स्वीकारले नसेल तरच)
3. किंवा: `release/vX.Y.0` वर हॉटफिक्स → पॅच रिलीज `vX.Y.(Z+1)`
4. GitHub Discussions आणि Discord मध्ये त्वरित कळवा

## कठोर नियम

- `main` वर कधीही थेट कमिट करू नका

- Husky हुक्स (`--no-verify`) कधीही वगळू नका
- गुपिते, क्रेडेन्शियल्स किंवा `.env` फाइल्स कधीही कमिट करू नका

- `src/`, `open-sse/`, `electron/` किंवा `bin/` मधील प्रॉडक्शन कोड बदलताना नेहमी चाचण्या समाविष्ट करा किंवा अद्ययावत करा
