## जॅनिटर स्थापित करा (एकदाच, मशीनवर)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): दर 30 मिनिटांनी, /var/log/runner-janitor.log मध्ये लॉग करा
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` आवश्यक आहे: जॅनिटर एखादा पथ काढून टाकण्यापूर्वी खुल्या
फायलींच्या एका स्नॅपशॉटद्वारे तो निष्क्रिय असल्याची खात्री करतो आणि हे साधन उपलब्ध नसल्यास तो काहीही काढून टाकत नाही व तसे
सांगतो (exit 1). कोणताही बदल प्रथम `--dry-run` सह वापरून पाहा — तो नेमके काय
करणार आहे ते दाखवतो आणि कशालाही स्पर्श करत नाही.

प्रत्येक रनमध्ये तो काय करतो: **tmpfs वर 3 तासांनंतर** आणि डिस्कवरील
`_work/_temp` मध्ये 24 तासांनंतर आमचे स्वतःचे अवशेष (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) साफ करतो; 75 मिनिटांपेक्षा जुना `next-build`
समाप्त करतो (कोणतेही जॉब इतका वेळ चालत नाही — 2026-08-27 रोजी GitHub ने त्याचा जॉब हरवलेला
घोषित केल्यानंतर एक जॉब 70 मिनिटे चालला होता); ज्यांची युनिट **थांबलेली** आहे अशा रनर्सचे
48 तास जुने checkouts काढून टाकतो; डिस्क ≥ 85 %, मेमरी PSI
`full/avg60` ≥ 10 %, आणि `MAX_ACTIVE_RUNNERS` पेक्षा अधिक listeners असल्यास
(omniroute/other विभागणीसह) सूचना देतो. Exit 1 = लक्ष देणे आवश्यक; लॉग वाचा.

75-मिनिटांचा नियम असा बिल्ड पकडत नाही ज्याचा जॉब GitHub ने आधीच सोडून दिला आहे. जेव्हा
`Runner.Listener` त्याचा जॉब नूतनीकरण करू शकत नाही, तेव्हा `_diag/Runner_*.log` मध्ये
`POST request to …/renewjob timed out after 100 seconds` दिसते, शेवटच्या यशस्वी नूतनीकरणानंतर
सुमारे दहा मिनिटांनी API जॉब `completed` (failure) असल्याचे दाखवते आणि कोणताही जॉब जोडलेला
नसतानाही `next-build` चालू राहतो (2026-10-18: #17066 चा बिल्ड 19:43 वाजता अयशस्वी झाला आणि
पाच मिनिटांनंतरही त्याचा बिल्ड 40 GB व्यापून होता). सर्वात नवीन `_diag/Worker_*.log` मध्ये ref ची
पुष्टी करा, त्यानंतर PID द्वारे केवळ बिल्ड ट्रीला SIGTERM पाठवा — `next-build`, `npm run build`,
`build-next-isolated.mjs` आणि `_work` workers. `Runner.Listener`, `RunnerService.js` किंवा
`Runner.Worker` यांना कधीही स्पर्श करू नका: worker जॉब रद्द झाल्याचे नोंदवतो आणि listener
स्वतःच पुन्हा ऑनलाइन होतो.

## रनर युनिट्स: KillMode

रनरचा डीफॉल्ट `KillMode=process`, युनिट थांबवले किंवा रीस्टार्ट केले असता
`Runner.Worker → npm → next-build` चालूच ठेवतो — कोणताही जॉब जोडलेला नसताना अनाथ बिल्ड
RAM आणि CPU वापरत राहतो. प्रत्येक OmniRoute युनिटमध्ये
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
येथे `KillMode=mixed` असलेला drop-in आहे: प्रथम listener ला SIGTERM, त्यानंतर
`TimeoutStop` वेळी संपूर्ण cgroup ला SIGKILL. युनिटच्या पुढील रीस्टार्टवेळी तो लागू होतो —
**एकावेळी फक्त एक रनर आणि तो निष्क्रिय असतानाच** रीस्टार्ट करा, तसेच निष्क्रियता तपासणे आणि
रीस्टार्ट करणे एकाच कमांडमध्ये करा.

## कार्यपद्धतीचे नियम

- **एका वेळी एकच Turbopack बिल्ड — लेबलद्वारे सक्तीने लागू.** पूर्ण Turbopack
  `next build` चालवणारे प्रत्येक जॉब `[self-hosted, omni-build]` ला लक्ष्य करतात आणि फक्त **`omniroute-113-5`** कडेच ते
  लेबल आहे: `ci.yml` मधील `Build`, `npm-publish.yml` मधील `publish`, `nightly-v4-build`, `preview-artifact`,
  रात्रीचा a11y बिल्ड (#16853) आणि `docker-publish.yml` मधील **amd64** (BuildKit अंतर्गत webpack —
  तेथे Turbopack पॅनिक झाले, रन 33253576569). arm64 Docker लेग `ubuntu-24.04-arm` वरच राहतो.
  `docker-publish` चा amd64 लेग `ci.yml` मधील `Build` सोबत `heavy-build-main` concurrency गट सामायिक करतो
  (`cancel-in-progress: false`). Docker Engine `omniroute-113-5` वर असणे आवश्यक आहे. दुसरा Turbopack
  स्लॉट 78 GB मध्ये बसत नाही (2 × 33–37 GB आणि त्यासोबत बॉक्सवरील उर्वरित वापर); दुसरा स्लॉट केवळ
  webpack बिल्डसाठी सुरक्षित आहे.
- **Pull-request बिल्ड्स hosted वर चालतात (2026-10-18).** `ci.yml` मधील `Build` फक्त
  `push` आणि `workflow_dispatch` साठी `omni-build` पर्यंत पोहोचतो; प्रत्येक `pull_request` (स्वतःच्या origin मधील किंवा fork मधील) आणि `merge_group` बिल्ड
  webpack सह `ubuntu-latest` वर चालतो. स्वतःच्या origin मधील प्रत्येक PR स्लॉटकडे वळवल्यावर, एका Turbopack
  बिल्डने तो 29–58 मिनिटे व्यापून ठेवला, 18 बिल्ड्स 18 तासांपर्यंत रांगेत राहिले आणि release line च्या स्वतःच्या push बिल्डला
  40 जॉब्समध्ये फक्त एकदाच स्लॉट मिळाला. Hosted वर तोच PR बिल्ड PR च्या इतर
  जॉब्ससोबत 8–12 मिनिटांत पूर्ण होतो. `npm-publish` ज्या bundler चे वितरण करते तो Turbopack, release line वर
  default branch च्या रात्रीच्या a11y बिल्डद्वारे (04:41 UTC), स्लॉटपर्यंत पोहोचणाऱ्या प्रत्येक push किंवा dispatch बिल्डद्वारे
  आणि स्वतः `npm-publish` द्वारे सतत तपासला जातो. `tests/unit/build/heavy-build-queue.test.ts`
  चार-कलमी gate निश्चित करते.
- **Turbopack स्लॉटचा आकार त्याच्या मोजलेल्या गरजेपेक्षा कधीही कमी करू नका.** 2026-10-18 रोजी 18:06 वाजता
  `omni-release` साठी जागा करण्याकरिता स्लॉट 56G/60G वरून 40G/44G पर्यंत कमी करण्यात आला. compile टप्पा त्याच्या
  संपूर्ण रनदरम्यान `MemoryHigh` वर अडकून राहिला (memory PSI `full` 30–43 %), आणि cgroup सामायिक करणारा
  `Runner.Listener` त्याचा जॉब नूतनीकृत करू शकला नाही. 2026-10-17 मधील मालकाची 56G/60G संरचना त्याच
