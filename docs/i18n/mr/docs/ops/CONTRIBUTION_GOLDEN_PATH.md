पुल रिक्वेस्टसाठी सर्वात लहान आणि विश्वासार्ह विकास चक्र निवडण्यासाठी हे मार्गदर्शक वापरा. हे खाली लिंक केलेल्या क्षेत्र-विशिष्ट आर्किटेक्चर आणि सुरक्षा दस्तऐवजांची
जागा घेत नाही; ते प्रत्येक सामान्य बदल प्रकाराला त्याच्या करारांशी, केंद्रित तपासण्यांशी आणि CI व्याप्तीशी जोडते.

## प्रत्येक बदलाचा मार्ग

1. **संपादन करण्यापूर्वी बेस निवडा.** सर्वाधिक सक्रिय `release/v*` शाखा शोधा आणि
   तिच्या टोकापासून शाखा तयार करा. `main` नव्हे, तर त्या शाखेला लक्ष्य करा. रिलीझ फ्रीझ सक्रिय असल्यास, फ्रीझ केलेल्या
   शाखेला लक्ष्य करू नका; त्याऐवजी
   [शाखाकरण आणि रिलीझ मॉडेल](BRANCHING_MODEL.md) मध्ये वर्णन केलेले पुढील सक्रिय चक्र वापरा.
2. **करारांची नावे नोंदवा.** बदलामुळे प्रभावित होणारा प्रत्येक कॅटलॉग, स्कीमा, जनरेट केलेला आर्टिफॅक्ट, सार्वजनिक API किंवा वापरकर्ता
   इंटरफेस ओळखा. खालील तक्ता किमान प्रारंभिक संच देतो.
3. **केंद्रित चाचण्या लिहा किंवा अद्ययावत करा.** `src/`, `open-sse/`, `electron/`, किंवा
   `bin/` मधील प्रॉडक्शन बदलांसाठी त्याच PR मध्ये स्वयंचलित चाचणी आवश्यक आहे. वर्तन सिद्ध करणाऱ्या सर्वात लहान चाचणी फाइल्स
   चालवा, त्यानंतर सूचीबद्ध केंद्रित गेट्स चालवा.
4. **CI ला व्यापक मॅट्रिक्स चालवू द्या.** संपूर्ण युनिट शार्ड्स, Vitest, कव्हरेज रॅचेट आणि
   प्रॉडक्शन बिल्ड PR वर चालतात. केंद्रित अपयश व्यापक परिणामाकडे निर्देश करत असेल किंवा बदल अनेक
   उपप्रणालींमध्ये पसरत असेल, तेव्हाच व्यापक संच स्थानिकरीत्या चालवा.
5. **पुनरावलोकनापूर्वी सुसंगती साधा.** सक्रिय बेस फेच करा, त्यातील नवीन कमिट्स आणि त्याच्या तुलनेतील तुमचा diff तपासा,
   त्यानंतर योगदानकर्ता कार्यप्रवाहानुसार बेस rebase किंवा merge करा. जनरेट केलेल्या फाइल्समधील
   आणि कॅटलॉगमधील संघर्ष त्यांच्या स्रोतातून सोडवा, त्या पुन्हा जनरेट करा, केंद्रित चक्र पुन्हा चालवा आणि
   PR अजूनही सक्रिय रिलीझ शाखेलाच लक्ष्य करत असल्याची पुष्टी करा.
6. **पुरावे नोंदवा.** PR टेम्पलेटमध्ये चालवलेल्या कमांड्स, जोडलेली किंवा बदललेली प्रत्येक चाचणी फाइल,
   मायग्रेशन्स किंवा फीचर फ्लॅग्स आणि अद्याप प्रलंबित असलेले कोणतेही केवळ-CI प्रमाणीकरण सूचीबद्ध करा.

## बदलाच्या प्रकारानुसार सुवर्ण मार्ग

खालील आदेश किमान केंद्रित तपासण्या आहेत, तुम्ही बदललेले वर्तन थेट कव्हर करणारी चाचणी वगळण्याची परवानगी नाही.

### प्रदाता

**करार**

- `src/shared/constants/providers/` मध्ये प्रदाता व्याख्या आणि `src/shared/constants/providers.ts` मध्ये त्याची रचना.
- `open-sse/config/providerRegistry.ts` मधील मॉडेल आणि क्षमता किंवा त्याच्या काढलेल्या रेजिस्ट्री फायली.
- Executor/translator निवड, OAuth किंवा API-की कॉन्फिगरेशन आणि डॅशबोर्ड मालमत्ता. पुनर्जन्मित `docs/reference/PROVIDER_REFERENCE.md` किंवा README आकृत्या कमिट करू नका: रिलीझ रिफ्रेश त्यांना पुन्हा लिहितो (`check:pr-derived-paths` त्यांना वाहून नेणारे वैशिष्ट्य PR अपयशी ठरते).
- सार्वजनिक क्रेडेन्शियलमध्ये `resolvePublicCred()` वापरणे आवश्यक आहे; त्रुटी प्रतिसादांनी सामायिक सॅनिटाइज्ड त्रुटी मदतनीस वापरणे आवश्यक आहे. `docs/security/PUBLIC_CREDS.md` (git; `/docs` मध्ये संकलित केलेले नाही) आणि [एरर सॅनिटायझेशन](../security/ERROR_SANITIZATION.md) पहा.

**केंद्रित लूप**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # preview the generated reference; do not commit it
npm run lint
```

प्रत्येक प्रभावित विनंती कुटुंबाची देखील चाचणी करा: चॅट, प्रतिसाद, प्रतिमा, एम्बेडिंग, ऑडिओ किंवा व्हिडिओ. व्युत्पन्न कॅटलॉग आणि गोल्डन डिफचे पुनरावलोकन करा जसे करार बदलतात; त्यांना आंधळेपणाने स्वीकारू नका.

### राउटिंग

**करार**

- `src/shared/constants/routingStrategies.ts` मध्ये सार्वजनिक धोरण मूल्ये आणि UI मेटाडेटा.
- `open-sse/services/combo.ts` आणि `open-sse/services/combo/` अंतर्गत पाठवणे आणि ऑर्डर करणे.
- कॉम्बो स्कीमा, चिकाटी, लवचिकता स्थिती, मॉडेल क्षमता आणि API/UI नियंत्रणे.
- वर्तन बदलते तेव्हा [ऑटो-कॉम्बो इंजिन](../routing/AUTO-COMBO.md) आणि लवचिकता दस्तऐवजीकरण.

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy or dispatch changes
npm run check:known-symbols      # strategy registration changes
npm run lint
```

स्थानिक पातळीवर निर्धारवादी मॉक-अपस्ट्रीम चाचण्या वापरा. लाइव्ह कॉम्बो स्मोकसाठी क्रेडेन्शियल्स आवश्यक आहेत आणि ते मॅन्युअल आहेत, CI पर्याय नाहीत.

### UI / UX

**करार**

- Next.js route/page आणि `src/app/` आणि `src/shared/components/` अंतर्गत सामायिक घटक सीमा.
- API प्रतिसाद आकार, loading/empty/error स्थिती, कीबोर्ड आणि स्क्रीन-रीडर वर्तन, प्रतिसादात्मक मांडणी, थीमिंग आणि लोकेल विस्तार.
- `src/i18n/messages/en.json` मध्ये इंग्रजी UI स्रोत स्ट्रिंग्स; नवीन वापरकर्ता-फेसिंग कॉपी हार्ड-कोड करू नका.

**केंद्रित लूप**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

संवाद किंवा व्हिज्युअल बदलांसाठी ॲप चालवा आणि अरुंद आणि रुंद दोन्ही व्ह्यूपोर्ट तपासा. CI प्रॉडक्शन बिल्ड आणि ब्रॉडर स्वीट्स चालवते; व्हिज्युअल वर्तनाला अजूनही एका केंद्रित घटकाची आवश्यकता आहे, Playwright, किंवा बदलासाठी योग्य दस्तऐवजीकृत मॅन्युअल तपासणी.

### i18n

**करार**

- `src/i18n/messages/en.json` हा UI स्त्रोत आहे; `config/i18n.json` हा लोकेल स्त्रोत आहे.
- CLI कॅटलॉग `bin/cli/locales/` अंतर्गत स्वतंत्रपणे राहतात.
- ICU प्लेसहोल्डर्स आणि टॅग्स तंतोतंत जतन करा. product/provider/model नावे, प्रोटोकॉल आणि शीर्षलेख नावे, आदेश, code/JSON अभिज्ञापक, URLs, पर्यावरण व्हेरिएबल्स किंवा संरक्षित संज्ञा जसे की `OmniRoute`, `OAuth`, `MCP`, आणि `A2A` भाषांतर करू नका. वर्तमान स्रोत सूची `scripts/i18n/glossary/protected-terms.json` आहे.

एक वैशिष्ट्य PR केवळ `src/i18n/messages/en.json` संपादित करते (CLI: `bin/cli/locales/en.json`); इतर लोकॅल्स रिलीझ रिफ्रेश किंवा ट्रान्सलेशन वेव्ह (`docs/guides/I18N.md` → "फीचर PRs touch `en.json` फक्त") द्वारे प्रति रिलीज एकदा पूर्ण केल्या जातात. `npm run check:pr-derived-paths` PR वैशिष्ट्य अयशस्वी करते जे दुसरे लोकॅल कॅटलॉग संपादित करते.

**केंद्रित लूप**

```bash
npm run i18n:check-ui-coverage
npm run check:ui-icu
node scripts/i18n/check-key-completeness.mjs --mode=pr      # what CI runs on your PR
node scripts/i18n/check-ui-value-drift.mjs --mode=pr
node scripts/check/check-cli-i18n.mjs --mode=pr              # when CLI strings change
npm run i18n:check-glossary
npm run lint
```

`--mode=pr` शिवाय हे गेट्स स्थानिक पातळीवर रिलीझ मोडमध्ये चालतात आणि `en.json` मध्ये जोडलेल्या किंवा पुन्हा लिहिलेल्या प्रत्येक कीचा अहवाल देतात; ते रिलीझ रिफ्रेशचे काम आहे, तुमच्या PR चे नाही.

हे विद्यमान प्रणालीसाठी मार्गदर्शन आहे, त्याचे टूलिंग किंवा की मॉडेल विस्तृत करण्याचे आमंत्रण नाही. बदलण्याची प्रणाली तयार केली जात असताना i18n पॅचेस सर्जिकल ठेवा. बाह्य सेवांना कॉल करणाऱ्या भाषांतर आदेश चालवू नका जोपर्यंत कार्याला स्पष्टपणे व्युत्पन्न केलेल्या भाषांतरांची आवश्यकता नाही आणि तुम्ही परिणामी भिन्नतेचे पुनरावलोकन केले नसेल.

### CLI

**करार**

- `bin/cli/` मधील सार्वजनिक आदेश आणि ध्वज, व्युत्पन्न केलेल्या API आदेश, एक्झिट कोड, stdout/stderr आणि JSON आउटपुट आकार, config/environment वर्तन आणि पॅकेज केलेल्या फाइल्स.
- CLI वापरकर्ता-फेसिंग स्ट्रिंग्सने CLI i18n स्तर ( `bin/cli/locales/en.json` मध्ये अस्तित्वात असलेल्या`t()` की) वापरणे आवश्यक आहे. एक वैशिष्ट्य PR केवळ `en.json` संपादित करते; `pt-BR` आणि इतर लोकॅल्स रिलीज झाल्यावर पूर्ण होतात.
- समर्थित रनटाइम आणि प्रकाशित बायनरी करार म्हणून नोड जतन करा.

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
node scripts/check/check-cli-i18n.mjs --mode=pr
npm run build:cli             # generated/bundled CLI changes
npm run check:pack-policy     # package-surface changes
npm run lint
```

जेव्हा वर्तन पार्सिंग, फाइल्स किंवा निर्गमन स्थितीवर अवलंबून असते तेव्हा तात्पुरत्या डेटा निर्देशिकेत अचूक कमांड वापरा. CI विस्तृत पॅकेज आर्टिफॅक्ट आणि इकोसिस्टम तपासणी करते.

### डेटाबेस

**करार**

- `src/lib/db/` अंतर्गत डोमेन मॉड्यूल; विशिष्ट मॉड्यूल थेट आयात करा (जुना `localDb.ts` री-एक्सपोर्ट लेयर काढून टाकला होता).
- क्रमांकित, `src/lib/db/migrations/` अंतर्गत अदम्य SQL स्थलांतर, व्यवहार सुरक्षितता, श्रेणीसुधारित वर्तन, अनुक्रमणिका आणि स्कीमाने प्रभावित होणारा प्रत्येक कॉलर.
- मार्ग आणि हँडलर कधीही कच्चा SQL थेट जारी करत नाहीत.

**केंद्रित लूप**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

मायग्रेशन जोडताना ताज्या डेटाबेसची चाचणी घ्या आणि आधीच्या स्कीमावरून अपग्रेड करा. डेटाबेस चाचण्यांनी क्लीनअप दरम्यान हँडल बंद करणे आणि `resetDbInstance()` कॉल करणे आवश्यक आहे. सर्वोत्तम-प्रयत्न Bun अडॅप्टर मार्ग बदलल्यावरच `npm run test:bun:db` चालवा; नोड अधिकृत राहते.

### तयार / तैनात

**करार**

- रूट आणि वर्कस्पेस manifests/lockfile, `scripts/build/`, Next.js स्टँडअलोन असेंब्ली, `dist/` पॅकेज कंटेंट्स, Electron प्लॅटफॉर्म मेटाडेटा, CI वर्कफ्लो आणि डिप्लॉयमेंट सेन्टिनल्स.
- समर्थित नोड श्रेणी आणि `CLAUDE.md` मध्ये अनुमत-सूचीबद्ध Bun वापर अबाधित असणे आवश्यक आहे.
- बिल्ड आर्टिफॅक्ट अनट्रॅक राहतात; अवलंबित्व, परवाना, कार्यप्रवाह आणि पॅकेज धोरणे लागू होतात.

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency or lockfile changes
npm run check:pack-policy      # published package surface changes
npm run lint
```

जेव्हा बदल संकलन, स्टँडअलोन असेंब्ली, मालमत्ता किंवा रनटाइम बंडलिंगवर परिणाम करतो तेव्हाच स्थानिक पातळीवर `npm run build` वापरा. फक्त release/deploy प्रमाणीकरणासाठी `npm run build:release` वापरा. CI चे बिल्ड अंतिम क्रॉस-प्लॅटफॉर्म सिग्नल आहे; प्लॅटफॉर्म-विशिष्ट Electron बदलांसाठी जुळणारे फोकस केलेले बिल्ड किंवा स्मोक पुरावे आवश्यक आहेत.

## सामायिक मशीनसाठी डेव्हलपर स्क्रिप्ट्स

इतर सत्रे सक्रिय असलेल्या devbox वरील स्थानिक लूप दोन `scripts/dev/` सहाय्यकांमध्ये परिभाषित केला आहे:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD मधील फाइल्स
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # नेमक्या याच फाइल्स
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # विलग worktree, समांतरपणे सुरक्षित
```

- `typecheck-touched.sh` तात्पुरत्या `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`,
  `types: ["node"]`, `noEmit`, `incremental: false`) द्वारे केवळ बदललेल्या `.ts/.tsx` फाइल्सचे
  6 GB heap अंतर्गत typecheck करते, त्यामुळे जास्त भार असलेल्या मशीनवर OOM होणाऱ्या प्रकल्प-व्यापी
  `tsc -p tsconfig.json` ची ती जागा घेते. ती बदललेल्या फाइल्समधील त्रुटी आणि एक सारांश ओळ
  मुद्रित करते आणि बदललेल्या फाइल्समध्ये त्रुटी असल्यास `1`, केवळ आयात केलेल्या फाइल्समध्ये त्रुटी
  असल्यास किंवा निदान न देता tsc बंद पडल्यास `2` (तिने `_artifacts/typecheck-touched/` अंतर्गत
  नमूद केलेला लॉग वाचा), आणि सर्वकाही त्रुटीमुक्त असल्यास `0` सह बाहेर पडते. तात्पुरता tsconfig
  नेहमी काढून टाकला जातो; तो कधीही commit करू नका.
- `new-worktree.sh` `<git-common-dir>/omniroute-new-worktree.lock` वर समवर्ती रन क्रमवार करते
  (दृश्यमान संदेशासह डीफॉल्टनुसार 600 s पर्यंत प्रतीक्षा करते; override करण्याची पद्धत स्क्रिप्टच्या
  शीर्षलेखात दिली आहे) आणि worktree अस्तित्वात येण्यापूर्वी `git worktree add` अयशस्वी झाल्यास
  तिने तयार केलेली branch मागे घेते, त्यामुळे पुन्हा प्रयत्न करण्यासाठी स्वहस्ते
  `git branch -D` चालवण्याची आवश्यकता नसते. hard-linked `node_modules` आणि `.husky/_` ची प्रत
  बदलत नाही.

## स्थानिक candidate लूप

पॅकेज केलेले artifact सुरू होते हे source tests सिद्ध करू शकत नाहीत: packaging lists, छाटलेल्या
dependencies आणि native binaries मधील बिघाड tarball install करून सुरू केल्यानंतरच दिसून येतो.
`npm run dev:candidate` (`scripts/dev/candidate.mjs`) ही RFC #8084 मधील build-once / validate /
promote प्रवाहाची स्थानिक बाजू आहे: ती एक candidate build करते, नेमक्या त्याच artifact चे
validation करते, directory renames वापरून त्याला promote करते आणि promote केलेल्या slot ची
health check अयशस्वी झाल्यास त्याला roll back करते.

```bash
npm run dev:candidate -- run --dry-run --json  # योजना दाखवा, काहीही बदलू नका
npm run dev:candidate -- run                   # build + validate + promote, स्वयंचलित rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ मध्ये install
npm run dev:candidate -- validate --id <id>    # उपलब्ध port वर सुरू करा, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current आणि previous यांची अदलाबदल करा
npm run dev:candidate -- run --from-tarball <file.tgz>  # अन्यत्र (CI मध्ये) build केलेला tarball पुन्हा वापरा
```

- **एकदाच build करा.** `build` वर्तमान tree चे पॅकेज बनवते (त्यासाठी `dist/server.js` आवश्यक
  असल्यामुळे आधी `npm run build:release` चालवा) किंवा `--from-tarball` ची प्रत बनवते आणि नंतर
  tarball एका विलग npm prefix मध्ये install करते, कारण tarball मध्ये `node_modules` नसते. id हा
  लहान `HEAD` sha (tree मध्ये स्थानिक बदल असल्यास `-dirty`) किंवा tarball साठी `tgz-<sha256>`
  असतो. आधीच build केलेला clean id पुन्हा build करण्याऐवजी पुन्हा वापरला जातो; तो पुन्हा build
  करण्यासाठी `--force` द्या.
- **Source चे नव्हे, package चे validation करा.** `validate` नवीन
  `DATA_DIR=<candidate>/data`, बनावट secrets वापरून आणि operator चे `OMNIROUTE_API_KEY`,
  `STORAGE_ENCRYPTION_KEY` व `INITIAL_PASSWORD` environment मधून काढून installed CLI
  (`serve --port <free port>`) सुरू करते, ज्यामुळे ती नव्या install ची keyless loopback posture
  तपासते. ती `GET /api/health` कडून 200 मिळेपर्यंत प्रतीक्षा करते, `GET /v1/models` कडून 200
  मिळणे आवश्यक करते, process group थांबवते आणि tarball hash सोबत निकाल `validation.json` मध्ये
  नोंदवते.
- **त्याच artifact ला promote करा.** सध्याच्या tarball hash साठी यशस्वी validation नसलेला
  candidate `promote` नाकारते. डीफॉल्ट active slot `_artifacts/candidate/current` आहे;
  `--target <dir>` त्याच filesystem वरील दुसरी directory निवडते आणि तिचा previous slot
  `<dir>.previous` असतो. प्रत्येक rename atomic असते आणि प्रक्रियेदरम्यान अपयश आल्यास आधीच
  झालेली renames उलटवली जातात.
- **Roll back करा.** `run` promote केलेल्या slot चे पुन्हा validation करते आणि ती तपासणी अयशस्वी
  झाल्यास `current` आणि `previous` यांची पुन्हा अदलाबदल करते. पहिल्या validation मध्ये अयशस्वी
  झालेला candidate कधीही promote केला जात नाही.

सर्वकाही gitignored `_artifacts/candidate/` अंतर्गत लिहिले जाते; विद्यमान OmniRoute installation
आणि त्याची data directory यांना कधीही स्पर्श केला जात नाही. Promote केलेला CLI
`_artifacts/candidate/current/prefix/bin/omniroute` आहे; तो वापरताना तुमच्या स्वतःच्या `DATA_DIR`
सह सुरू करा. Exit codes: यशासाठी `0`, validation किंवा promotion अयशस्वी झाल्यास `1`, वापरातील
त्रुटी किंवा build उपलब्ध नसल्यास `2`.

| प्रत्येक पॅचसाठी स्थानिकरीत्या चालवा                                           | CI व्यापक संकेत पुरवते                                                       |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| वरील थेट वर्तन चाचण्या आणि श्रेणी गेट्स                                        | शार्ड केलेला संपूर्ण युनिट संच आणि अनुक्रमिक चाचण्या                         |
| `npm run lint`                                                                 | Vitest संच आणि कव्हरेज/गुणवत्ता रॅचेट्स                                      |
| प्रभावित करारानुसार आवश्यक असेल तेव्हाच प्रकार-तपासणी किंवा बिल्ड              | उत्पादन बिल्ड, सुरक्षा, दस्तऐवजीकरण, अवलंबित्व आणि PR-धोरण गेट्स             |
| स्वयंचलन वर्तन सिद्ध करू शकत नसेल तेव्हाच मॅन्युअल परस्परसंवाद/लाइव्ह तपासण्या | वर्कफ्लोद्वारे कॉन्फिगर केलेल्या क्रॉस-जॉब एकत्रीकरण आणि प्लॅटफॉर्म तपासण्या |

यशस्वी केंद्रित लूप हा बदललेल्या कराराबद्दलचा पुरावा आहे; असंबंधित CI तपासण्या
यशस्वी होतील याचा तो पुरावा नाही. याउलट, प्रत्येक स्थानिक संपादनासाठी संपूर्ण रिपॉझिटरी मॅट्रिक्स पूर्ण होईपर्यंत प्रतीक्षा करू नका.

## समेट तपासणीसूची

पुनरावलोकनाची विनंती करण्यापूर्वी:

- PR बेस अजूनही सर्वोच्च सक्रिय `release/v*` शाखा असल्याची खात्री करा.
- तो बेस फेच करा आणि तुम्ही शाखा तयार केल्यापासून समाविष्ट झालेले कमिट्स तपासा.
- अनवधानाने झालेले किंवा व्युत्पन्न बदल शोधण्यासाठी `git diff <active-base>...HEAD` तपासा.
- स्रोत अद्ययावत करून आणि आउटपुट पुन्हा व्युत्पन्न करून कॅटलॉग व व्युत्पन्न-दस्तऐवज संघर्ष सोडवा.
- समेटानंतर PR वर्णनात सूचीबद्ध केलेली प्रत्येक केंद्रित चाचणी/गेट पुन्हा चालवा.
- बदललेल्या बेसशी जुळवून घेण्यासाठी केवळ असर्शन्स कमकुवत करू नका किंवा आवश्यक चाचण्या वगळू नका.

[शाखाकरण आणि रिलीज मॉडेल](BRANCHING_MODEL.md) वापरा. संपूर्ण CI सूचीसाठी,
[गुणवत्ता गेट्स संदर्भ](../architecture/QUALITY_GATES.md) वापरा.
