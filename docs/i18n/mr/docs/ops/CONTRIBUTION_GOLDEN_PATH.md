पुल रिक्वेस्टसाठी सर्वात लहान आणि विश्वासार्ह विकास चक्र निवडण्यासाठी हे मार्गदर्शक वापरा. हे खाली लिंक केलेल्या क्षेत्र-विशिष्ट आर्किटेक्चर आणि सुरक्षा दस्तऐवजांची
जागा घेत नाही; ते प्रत्येक सामान्य बदल प्रकाराला त्याच्या करारांशी, केंद्रित तपासण्यांशी आणि CI व्याप्तीशी जोडते.

## प्रत्येक बदलाचा मार्ग

1. **संपादन करण्यापूर्वी बेस निवडा.** सर्वाधिक सक्रिय `release/v*` शाखा शोधा आणि
   तिच्या टोकापासून शाखा तयार करा. `main` नव्हे, तर त्या शाखेला लक्ष्य करा. रिलीझ फ्रीझ सक्रिय असल्यास, फ्रीझ केलेल्या
   शाखेला लक्ष्य करू नका; त्याऐवजी
   [शाखाकरण आणि रिलीझ मॉडेल](BRANCHING_MODEL.md) मध्ये वर्णन केलेले पुढील सक्रिय चक्र वापरा.
2. **करारांची नावे नोंदवा.** बदलामुळे प्रभावित होणारा प्रत्येक कॅटलॉग, स्कीमा, जनरेट केलेला आर्टिफॅक्ट, सार्वजनिक API किंवा वापरकर्ता
   इंटरफेस ओळखा. खालील तक्ता किमान प्रारंभिक संच देतो.
3. **केंद्रित चाचण्या लिहा किंवा अद्ययावत करा.** `src/`, `open-sse/`, `electron/`, किंवा
   `bin/` मधील प्रॉडक्शन बदलांसाठी त्याच PR मध्ये स्वयंचलित चाचणी आवश्यक आहे. वर्तन सिद्ध करणाऱ्या सर्वात लहान चाचणी फाइल्स
   चालवा, त्यानंतर सूचीबद्ध केंद्रित गेट्स चालवा.
4. **CI ला व्यापक मॅट्रिक्स चालवू द्या.** संपूर्ण युनिट शार्ड्स, Vitest, कव्हरेज रॅचेट आणि
   प्रॉडक्शन बिल्ड PR वर चालतात. केंद्रित अपयश व्यापक परिणामाकडे निर्देश करत असेल किंवा बदल अनेक
   उपप्रणालींमध्ये पसरत असेल, तेव्हाच व्यापक संच स्थानिकरीत्या चालवा.
5. **पुनरावलोकनापूर्वी सुसंगती साधा.** सक्रिय बेस फेच करा, त्यातील नवीन कमिट्स आणि त्याच्या तुलनेतील तुमचा diff तपासा,
   त्यानंतर योगदानकर्ता कार्यप्रवाहानुसार बेस rebase किंवा merge करा. जनरेट केलेल्या फाइल्समधील
   आणि कॅटलॉगमधील संघर्ष त्यांच्या स्रोतातून सोडवा, त्या पुन्हा जनरेट करा, केंद्रित चक्र पुन्हा चालवा आणि
   PR अजूनही सक्रिय रिलीझ शाखेलाच लक्ष्य करत असल्याची पुष्टी करा.
6. **पुरावे नोंदवा.** PR टेम्पलेटमध्ये चालवलेल्या कमांड्स, जोडलेली किंवा बदललेली प्रत्येक चाचणी फाइल,
   मायग्रेशन्स किंवा फीचर फ्लॅग्स आणि अद्याप प्रलंबित असलेले कोणतेही केवळ-CI प्रमाणीकरण सूचीबद्ध करा.

## बदल प्रकारानुसार आदर्श मार्ग

खालील कमांड्स किमान केंद्रित तपासण्या आहेत; तुम्ही बदललेल्या वर्तनाचे थेट परीक्षण करणारी चाचणी
वगळण्याची ही परवानगी नाही.

### प्रोव्हायडर

**करार**

- `src/shared/constants/providers/` मधील प्रोव्हायडर व्याख्या आणि
  `src/shared/constants/providers.ts` मधील तिची रचना.
- `open-sse/config/providerRegistry.ts` किंवा त्यातून वेगळ्या केलेल्या रजिस्ट्री फाइल्समधील मॉडेल्स आणि क्षमता.
- लागू असल्यास, एक्झिक्युटर/ट्रान्सलेटर निवड, OAuth किंवा API-key कॉन्फिगरेशन, डॅशबोर्ड ॲसेट्स आणि जनरेट केलेला
  प्रोव्हायडर संदर्भ.
- सार्वजनिक क्रेडेन्शियल्सनी `resolvePublicCred()` वापरणे आवश्यक आहे; त्रुटी प्रतिसादांनी सामायिक सॅनिटाइज्ड
  त्रुटी सहाय्यक वापरणे आवश्यक आहे. `docs/security/PUBLIC_CREDS.md` (git; `/docs` मध्ये संकलित केलेले नाही) आणि
  [त्रुटी सॅनिटायझेशन](../security/ERROR_SANITIZATION.md) पहा.

**केंद्रित चक्र**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # कॅटलॉग बदलल्यावर; जनरेट केलेला diff कमिट करा
npm run lint
```

प्रभावित झालेल्या प्रत्येक विनंती प्रकाराचीही चाचणी करा: chat, Responses, images, embeddings, audio किंवा video.
जनरेट केलेल्या कॅटलॉग आणि golden diffs चे करारातील बदल म्हणून पुनरावलोकन करा; ते विचार न करता स्वीकारू नका.

### राउटिंग

**करार**

- `src/shared/constants/routingStrategies.ts` मधील सार्वजनिक स्ट्रॅटेजी मूल्ये आणि UI मेटाडेटा.
- `open-sse/services/combo.ts` आणि `open-sse/services/combo/` अंतर्गत डिस्पॅच आणि क्रमवारी.
- Combo स्कीमा, पर्सिस्टन्स, रिझिलियन्स स्थिती, मॉडेल क्षमता आणि API/UI नियंत्रणे.
- वर्तन बदलल्यास [Auto-Combo Engine](../routing/AUTO-COMBO.md) आणि रिझिलियन्स दस्तऐवजीकरण.

**केंद्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # स्ट्रॅटेजी किंवा डिस्पॅचमधील बदल
npm run check:known-symbols      # स्ट्रॅटेजी नोंदणीमधील बदल
npm run lint
```

स्थानिकरीत्या निर्धारक, मॉक-अपस्ट्रीम चाचण्या वापरा. Live combo smoke चाचण्यांसाठी क्रेडेन्शियल्स आवश्यक असतात आणि त्या
मॅन्युअल आहेत, CI चे पर्याय नाहीत.

### UI / UX

**करार**

- `src/app/` आणि `src/shared/components/` अंतर्गत Next.js रूट/पेज आणि सामायिक कॉम्पोनंटच्या सीमा.
- API प्रतिसादांचे आकार, लोडिंग/रिक्त/त्रुटी स्थिती, कीबोर्ड आणि स्क्रीन-रीडर वर्तन,
  प्रतिसादक्षम लेआउट, थीमिंग आणि लोकेल विस्तार.
- `src/i18n/messages/en.json` मधील इंग्रजी UI स्रोत स्ट्रिंग्स; वापरकर्त्यांना दिसणारा नवीन मजकूर हार्ड-कोड करू नका.

**केंद्रित चक्र**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

परस्परसंवाद किंवा दृश्यात्मक बदलांसाठी ॲप चालवा आणि अरुंद तसेच रुंद अशा दोन्ही व्ह्यूपोर्ट्सची तपासणी करा. CI
प्रॉडक्शन बिल्ड आणि व्यापक संच चालवते; दृश्यात्मक वर्तनासाठी तरीही बदलाला अनुरूप अशी केंद्रित कॉम्पोनंट चाचणी, Playwright
किंवा दस्तऐवजीकृत मॅन्युअल तपासणी आवश्यक आहे.

### i18n

**करार**

- `src/i18n/messages/en.json` हा UI स्रोत आहे; `config/i18n.json` हा लोकेल स्रोत आहे.
- CLI कॅटलॉग्स `bin/cli/locales/` अंतर्गत स्वतंत्रपणे आहेत.
- ICU प्लेसहोल्डर्स आणि टॅग्ज तंतोतंत जतन करा. उत्पादन/प्रोव्हायडर/मॉडेलची नावे,
  प्रोटोकॉल आणि हेडरची नावे, कमांड्स, कोड/JSON आयडेंटिफायर्स, URLs, एन्व्हायर्नमेंट व्हेरिएबल्स किंवा
  `OmniRoute`, `OAuth`, `MCP`, आणि `A2A` यांसारख्या संरक्षित संज्ञांचे भाषांतर करू नका. सध्याची स्रोत सूची
  `scripts/i18n/glossary/protected-terms.json` आहे.

**केंद्रित चक्र**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI स्ट्रिंग्स/कॅटलॉग्स बदलल्यावर
npm run lint
```

हे विद्यमान प्रणालीसाठी मार्गदर्शन आहे, तिची साधने किंवा key model विस्तारित करण्याचे आमंत्रण नाही.
पर्यायी प्रणालीची रचना होत असताना i18n पॅचेस अत्यंत नेमके आणि मर्यादित ठेवा. कार्यासाठी जनरेट केलेली भाषांतरे स्पष्टपणे आवश्यक नसतील आणि
तुम्ही परिणामी diff चे पुनरावलोकन केलेले नसेल, तर बाह्य सेवांना कॉल करणाऱ्या भाषांतर कमांड्स चालवू नका.

### CLI

**करार**

- `bin/cli/` मधील सार्वजनिक आदेश आणि फ्लॅग्स, जनरेट केलेले API आदेश, exit codes, stdout/stderr आणि
  JSON आउटपुटची रचना, config/environment वर्तन आणि पॅकेज केलेल्या फाइल्स.
- CLI मधील वापरकर्त्यांसाठीचे मजकूर CLI i18n स्तर वापरून लिहिलेले असावेत आणि `en`/`pt-BR` कॅटलॉग परस्पर सुसंगत ठेवावेत.
- समर्थित runtime म्हणून Node आणि प्रकाशित binary contract जतन करा.

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # जनरेट केलेले/बंडल केलेले CLI बदल
npm run check:pack-policy     # पॅकेजच्या सार्वजनिक पृष्ठभागातील बदल
npm run lint
```

वर्तन parsing, फाइल्स किंवा exit status वर अवलंबून असेल तेव्हा तात्पुरत्या data directory मध्ये नेमका आदेश वापरा.
CI व्यापक package artifact आणि ecosystem तपासण्या करते.

### डेटाबेस

**करार**

- `src/lib/db/` अंतर्गत domain modules; विशिष्ट modules थेट import करा (जुना `localDb.ts` re-export स्तर काढून टाकला आहे).
- `src/lib/db/migrations/` अंतर्गत क्रमांकित, idempotent SQL migrations, transaction safety, upgrade
  वर्तन, indexes आणि schema मुळे प्रभावित होणारा प्रत्येक caller.
- Routes आणि handlers कधीही थेट raw SQL चालवत नाहीत.

**केंद्रित लूप**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration जोडताना नवीन डेटाबेस आणि आधीच्या schema वरून upgrade या दोन्हींची चाचणी करा. डेटाबेस चाचण्यांनी
handles बंद करणे आणि cleanup दरम्यान `resetDbInstance()` कॉल करणे आवश्यक आहे. केवळ best-effort Bun adapter मार्ग
बदलत असेल तेव्हाच `npm run test:bun:db` चालवा; Node अधिकृत राहतो.

### Build / deploy

**करार**

- Root आणि workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  पॅकेजमधील सामग्री, Electron platform metadata, CI workflows आणि deployment sentinels.
- समर्थित Node ranges आणि `CLAUDE.md` मधील allow-listed Bun वापर अबाधित राहिला पाहिजे.
- Build artifacts ट्रॅक न केलेलेच राहतात; dependency, license, workflow आणि package policies लागू होतात.

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency किंवा lockfile मधील बदल
npm run check:pack-policy      # प्रकाशित पॅकेजच्या सार्वजनिक पृष्ठभागातील बदल
npm run lint
```

बदलाचा compilation, standalone assembly, assets किंवा runtime bundling वर परिणाम होत असेल तेव्हाच स्थानिकरीत्या `npm run build` वापरा.
केवळ release/deploy validation साठी `npm run build:release` वापरा. CI चा build हा अंतिम cross-platform संकेत आहे;
platform-specific Electron बदलांसाठी संबंधित focused build किंवा smoke evidence आवश्यक आहे.

## सामायिक मशीनसाठी डेव्हलपर स्क्रिप्ट्स

इतर सत्रे सक्रिय असलेल्या devbox वरील स्थानिक लूप दोन `scripts/dev/` सहाय्यकांमध्ये परिभाषित केला आहे:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD मधील फाइल्स
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # नेमक्या याच फाइल्स
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # विलग worktree, समांतरपणे सुरक्षित
```

- `typecheck-touched.sh` तात्पुरत्या `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`,
  `types: ["node"]`, `noEmit`, `incremental: false`) द्वारे केवळ बदललेल्या `.ts/.tsx` फाइल्सचे
  6 GB heap अंतर्गत typecheck करते, त्यामुळे जास्त भार असलेल्या मशीनवर OOM होणाऱ्या प्रकल्प-व्यापी
  `tsc -p tsconfig.json` ची ती जागा घेते. ती बदललेल्या फाइल्समधील त्रुटी आणि एक सारांश ओळ
  मुद्रित करते आणि बदललेल्या फाइल्समध्ये त्रुटी असल्यास `1`, केवळ आयात केलेल्या फाइल्समध्ये त्रुटी
  असल्यास किंवा निदान न देता tsc बंद पडल्यास `2` (तिने `_artifacts/typecheck-touched/` अंतर्गत
  नमूद केलेला लॉग वाचा), आणि सर्वकाही त्रुटीमुक्त असल्यास `0` सह बाहेर पडते. तात्पुरता tsconfig
  नेहमी काढून टाकला जातो; तो कधीही commit करू नका.
- `new-worktree.sh` `<git-common-dir>/omniroute-new-worktree.lock` वर समवर्ती रन क्रमवार करते
  (दृश्यमान संदेशासह डीफॉल्टनुसार 600 s पर्यंत प्रतीक्षा करते; override करण्याची पद्धत स्क्रिप्टच्या
  शीर्षलेखात दिली आहे) आणि worktree अस्तित्वात येण्यापूर्वी `git worktree add` अयशस्वी झाल्यास
  तिने तयार केलेली branch मागे घेते, त्यामुळे पुन्हा प्रयत्न करण्यासाठी स्वहस्ते
  `git branch -D` चालवण्याची आवश्यकता नसते. hard-linked `node_modules` आणि `.husky/_` ची प्रत
  बदलत नाही.

## स्थानिक candidate लूप

पॅकेज केलेले artifact सुरू होते हे source tests सिद्ध करू शकत नाहीत: packaging lists, छाटलेल्या
dependencies आणि native binaries मधील बिघाड tarball install करून सुरू केल्यानंतरच दिसून येतो.
`npm run dev:candidate` (`scripts/dev/candidate.mjs`) ही RFC #8084 मधील build-once / validate /
promote प्रवाहाची स्थानिक बाजू आहे: ती एक candidate build करते, नेमक्या त्याच artifact चे
validation करते, directory renames वापरून त्याला promote करते आणि promote केलेल्या slot ची
health check अयशस्वी झाल्यास त्याला roll back करते.

```bash
npm run dev:candidate -- run --dry-run --json  # योजना दाखवा, काहीही बदलू नका
npm run dev:candidate -- run                   # build + validate + promote, स्वयंचलित rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ मध्ये install
npm run dev:candidate -- validate --id <id>    # उपलब्ध port वर सुरू करा, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current आणि previous यांची अदलाबदल करा
npm run dev:candidate -- run --from-tarball <file.tgz>  # अन्यत्र (CI मध्ये) build केलेला tarball पुन्हा वापरा
```

- **एकदाच build करा.** `build` वर्तमान tree चे पॅकेज बनवते (त्यासाठी `dist/server.js` आवश्यक
  असल्यामुळे आधी `npm run build:release` चालवा) किंवा `--from-tarball` ची प्रत बनवते आणि नंतर
  tarball एका विलग npm prefix मध्ये install करते, कारण tarball मध्ये `node_modules` नसते. id हा
  लहान `HEAD` sha (tree मध्ये स्थानिक बदल असल्यास `-dirty`) किंवा tarball साठी `tgz-<sha256>`
  असतो. आधीच build केलेला clean id पुन्हा build करण्याऐवजी पुन्हा वापरला जातो; तो पुन्हा build
  करण्यासाठी `--force` द्या.
- **Source चे नव्हे, package चे validation करा.** `validate` नवीन
  `DATA_DIR=<candidate>/data`, बनावट secrets वापरून आणि operator चे `OMNIROUTE_API_KEY`,
  `STORAGE_ENCRYPTION_KEY` व `INITIAL_PASSWORD` environment मधून काढून installed CLI
  (`serve --port <free port>`) सुरू करते, ज्यामुळे ती नव्या install ची keyless loopback posture
  तपासते. ती `GET /api/health` कडून 200 मिळेपर्यंत प्रतीक्षा करते, `GET /v1/models` कडून 200
  मिळणे आवश्यक करते, process group थांबवते आणि tarball hash सोबत निकाल `validation.json` मध्ये
  नोंदवते.
- **त्याच artifact ला promote करा.** सध्याच्या tarball hash साठी यशस्वी validation नसलेला
  candidate `promote` नाकारते. डीफॉल्ट active slot `_artifacts/candidate/current` आहे;
  `--target <dir>` त्याच filesystem वरील दुसरी directory निवडते आणि तिचा previous slot
  `<dir>.previous` असतो. प्रत्येक rename atomic असते आणि प्रक्रियेदरम्यान अपयश आल्यास आधीच
  झालेली renames उलटवली जातात.
- **Roll back करा.** `run` promote केलेल्या slot चे पुन्हा validation करते आणि ती तपासणी अयशस्वी
  झाल्यास `current` आणि `previous` यांची पुन्हा अदलाबदल करते. पहिल्या validation मध्ये अयशस्वी
  झालेला candidate कधीही promote केला जात नाही.

सर्वकाही gitignored `_artifacts/candidate/` अंतर्गत लिहिले जाते; विद्यमान OmniRoute installation
आणि त्याची data directory यांना कधीही स्पर्श केला जात नाही. Promote केलेला CLI
`_artifacts/candidate/current/prefix/bin/omniroute` आहे; तो वापरताना तुमच्या स्वतःच्या `DATA_DIR`
सह सुरू करा. Exit codes: यशासाठी `0`, validation किंवा promotion अयशस्वी झाल्यास `1`, वापरातील
त्रुटी किंवा build उपलब्ध नसल्यास `2`.

## समेट तपासणीसूची

पुनरावलोकनाची विनंती करण्यापूर्वी:

- PR बेस अजूनही सर्वोच्च सक्रिय `release/v*` शाखा असल्याची खात्री करा.
- तो बेस फेच करा आणि तुम्ही शाखा तयार केल्यापासून समाविष्ट झालेले कमिट्स तपासा.
- अनवधानाने झालेले किंवा व्युत्पन्न बदल शोधण्यासाठी `git diff <active-base>...HEAD` तपासा.
- स्रोत अद्ययावत करून आणि आउटपुट पुन्हा व्युत्पन्न करून कॅटलॉग व व्युत्पन्न-दस्तऐवज संघर्ष सोडवा.
- समेटानंतर PR वर्णनात सूचीबद्ध केलेली प्रत्येक केंद्रित चाचणी/गेट पुन्हा चालवा.
- बदललेल्या बेसशी जुळवून घेण्यासाठी केवळ असर्शन्स कमकुवत करू नका किंवा आवश्यक चाचण्या वगळू नका.

[शाखाकरण आणि रिलीज मॉडेल](BRANCHING_MODEL.md) वापरा. संपूर्ण CI सूचीसाठी,
[गुणवत्ता गेट्स संदर्भ](../architecture/QUALITY_GATES.md) वापरा.
