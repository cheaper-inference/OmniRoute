## प्रकाशन शाखेवर लँडिंग

सर्व-रांग `release/vX.Y.Z` मध्ये लँडिंग नियंत्रित करते. PR उतरण्यापूर्वी डीफॉल्ट शाखेवर `config/merge-queue/config.json` मधील उच्च-स्तरीय `mode` वाचा. [Omni-Queue](OMNI_QUEUE.md) पहा.

- **`shadow`** प्रमाणीकरण चालवते आणि मॅन्युअल विलीनीकरणावर लँडिंग सोडते. मंजूर PR ला त्याच्या अंतिम शीर्षस्थानी `omni-queue` लागू करा. `npm run queue -- why <PR>` सह पात्रता तपासा. `npm run queue -- history --base <branch>` मध्ये त्या डोक्याच्या निकालाची प्रतीक्षा करा. `would-land` वर पुढे जा. `culprit-found` किंवा `would-dequeue` वर, मर्ज धरून ठेवा आणि कारण निश्चित करा.
- **छाया अपवाद.** सध्याच्या बेस टीपच्या विरुद्ध हिरव्या पूर्ण CI असलेली ट्रेन वेगळ्या रांगेच्या निर्णयाशिवाय पुढे जाऊ शकते. जेव्हा PR हेडमध्ये आधीपासूनच वर्तमान बेस टीप असते तेव्हा समान अपवाद लागू होतो.
- **`live`** लँडिंग ट्रिगर करण्यासाठी `omni-queue` लेबल वापरते. एकटी रांग PR ला उतरते. मर्ज कमांड सोडा आणि थेट रांगेत पुश करा.

प्रत्येक लँडिंगसाठी मालकाची अधिकृतता आणि लागू आवश्यक चेक आवश्यक असतात. मालकाने लँडिंग अधिकृत केल्यानंतरच `omni-queue` लागू करा. रांगेत PRs टचिंग संरक्षित पथांना त्या PR साठी मालकाचा `protected-approved` निर्णय आवश्यक आहे.

"सक्रिय रीलिझवर हिरवे दरवाजे आवश्यक आहेत" नियमांना डोक्यावर हिरवा `Gate / CI` आणि `Gate / Quality` आवश्यक आहे. लाल गेटला बायपास करण्यासाठी कधीही `--admin` वापरू नका. रिलीझ फ्रीझ ब्लॉक्स गोठलेल्या शाखेत विलीन होतात. [कठोर नियम 21](HARD_RULES_DETAIL.md) पहा. दुसरे सत्र कार्यरत आहे असे पुल विनंतीवर कधीही लेबल करू नका, विलीन करू नका किंवा पुश करू नका. [कठोर नियम 22](HARD_RULES_DETAIL.md) पहा.

## ट्रेन पुल विनंती

1. सध्याच्या रिलीझ बेस टीपवर ट्रेनची शाखा सुरू करा. विलीनीकरण कमिट वापरून अचूक मंजूर सदस्य हेड एकत्रित करा. स्क्वॅश आणि रिबेस टाळून त्यांचा प्रतिबद्ध इतिहास जतन करा.
2. रेल्वे शाखेसाठी एक पुल विनंती उघडा. सध्याच्या बेस टीपवर तो PR स्वतःच्या पूर्ण CI सह सत्यापित करा. लँडिंग करण्यापूर्वी बेस टीप आणि मंजूर सदस्य हेड पुन्हा तपासा. प्रमाणित उमेदवार बदलल्यावर ट्रेन आणि तिची CI रिफ्रेश करा.
3. लागू असलेल्या रांग मोडमध्ये मर्ज कमिटसह ट्रेन PR उतरवा. लाइव्ह मोडमध्ये, रांगेची `merge-ff` लँडिंग पद्धत मर्ज कमिट जतन करते. मूळ सदस्य प्रमुखांना प्रकाशन शाखेतून पोहोचता येते. GitHub सदस्य PRs ला विलीन केल्याचे चिन्हांकित करते आणि कमिट त्यांचे लेखक राखून ठेवतात.

सार्वजनिक उदाहरण म्हणजे [PR #21071](https://github.com/cheaper-inference/OmniRoute/pull/21071). हे 18 सदस्य PRs एकत्र केले आणि 2026-11-24 रोजी विलीनीकरण कमिटसह उतरले.

`main` वरून पुढच्या रिलीझ शाखेत एक सिंक-बॅक देखील मर्ज कमिटद्वारे येतो. नंतरच्या सिंक-बॅकसाठी `main` वंश जतन करणे आवश्यक आहे. [वर्कट्री आयसोलेशन](WORKTREE_ISOLATION.md#sync-back-landings-are-merge-commits-never-squash) पहा.

## स्थानिक मर्ज-ट्रेन प्रमाणीकरणकर्ता

```bash
scripts/release/merge-train.sh [--plan] [--fast] <base-branch> <PR#> [<PR#>...]
```

व्हॅलिडेटर बेस आणि PR हेड आणतो आणि डिस्पोजेबल वर्कट्रीमध्ये एकत्र करतो. परिणामी झाडावर ते एकदा त्याचे पॅरिटी सूट चालवते. एक अयशस्वी हेड फेच किंवा मर्ज विरोध PR बाहेर काढतो आणि स्क्रिप्ट उर्वरित PRs सह चालू राहते.

- **`--plan`** निवडलेल्या मोडच्या पायऱ्या मुद्रित करते आणि वर्कट्री तयार न करता किंवा रिमोटशी संपर्क न करता बाहेर पडते. जलद योजनेची तपासणी करण्यासाठी ते `--fast` सह एकत्र करा.
- **`--fast`** सामान्य स्थिर गेट्स चालवते, `tests/unit/` आणि `npm run test:vitest` अंतर्गत निवडलेल्या बदललेल्या `node:test` फाइल्स. जलद मोड वापरताना जमा झालेल्या टिपवर दिवसातून किमान एकदा पूर्ण स्थानिक प्रमाणीकरण चालवा.
- **पूर्ण मोड** पूर्ण-केवळ स्थिर गेट जोडते आणि `npm run test:unit` आणि `npm run test:vitest` चालवते.

बेस प्रोब उपलब्ध असल्यास अस्पर्श केलेले स्थिर गेट पुन्हा चालू केले जाते. स्क्रिप्ट अनुवांशिक अपयशाचा अहवाल देते आणि जेव्हा प्रत्येक मान्यताप्राप्त उल्लंघन रेषा बेसवर देखील दिसून येते आणि एकूण संख्या वाढलेली नसते तेव्हा ती चालू राहते.

| बाहेर पडा | अर्थ                                                                                                                                         |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`       | योजना छापली किंवा सुट पूर्ण केली. सूट सारांश कोणत्याही वारशाने मिळालेल्या स्थिर अपयशांची आणि बाहेर काढलेली PRs सूचीबद्ध करतो.                |
| `1`       | अवैध युक्तिवाद, कोणतेही Git चेकआउट नाही, अयशस्वी प्रीफ्लाइट, किंवा PR बोर्ड केलेले नाही.                                                     |
| `2`       | संच तपासणी अयशस्वी झाली आणि वारसा म्हणून पात्र ठरली नाही. ऑपरेटर बॅचचे दुभाजक करू शकतो, आक्षेपार्ह PR बाहेर काढू शकतो आणि पुन्हा चालवू शकतो. |

स्थानिक पास फक्त मालकाच्या डॉसियरसाठी निदान पुरावे पुरवतो. प्रत्येक लँडिंगला अजूनही मालकाची अधिकृतता, त्याच्या स्वतःच्या आवश्यक तपासण्या आणि लागू असताना सावलीच्या रांगेचा निर्णय आवश्यक असतो.

## टियरिंग

- **प्रति PR** बदललेल्या पथांवर आधारित CI आणि गुणवत्ता निवडा. कोड PRs वेगवान दर्जाचे गेट्स आणि प्रभावित चाचण्या चालवते, CI मध्ये स्वतंत्र युनिट आणि Vitest जॉब्ससह.
- **प्रति रांगेतील उमेदवार.** CI आणि क्वालिटी तयार केलेल्या उमेदवारासाठी पूर्ण प्रोफाइल त्याच्या रांगेतील संदर्भावर चालवतात.
- **प्रति रिलीझ टीप.** रिलीज-ग्रीन त्याच्या पथ फिल्टरशी जुळणाऱ्या पुशांवर द्रुत हार्ड गेट्स चालवते. दररोज तीन शेड्यूल रन रिलीझ शाखेसाठी पूर्ण स्वीप वापरतात.
- **प्रति प्रकाशन.** पूर्ण CI मॅट्रिक्समध्ये E2E शार्ड्स, पॅकेज प्रमाणीकरण, टारबॉल बूट स्मोक आणि कव्हरेज चेक समाविष्ट आहेत. [प्रकाशन चेकलिस्ट](RELEASE_CHECKLIST.md) पहा.

## `merge-train.sh` साठी फ्रेश-चेकआउटची पूर्वतयारी

वर्कट्रीज तयार करण्यापूर्वी प्रीफ्लाइट चालते. `npm ci` सह अवलंबित्व स्थापित करा. पुष्टी करा की `node_modules/.bin/tsc` एक्झिक्युटेबल आहे आणि `node_modules/node_modules` अनुपस्थित आहे. `node_modules/.bin/bun --version` यशस्वी होत असल्याचे तपासा.

Bun पोस्टइंस्टॉल वगळले असल्यास, `(cd node_modules/bun && node install.js)` चालवा. प्रदाता सुसंगतता आणि ज्ञात-प्रतीक तपासणी Bun वापरतात. व्हॅलिडेटर `npm run check:cycles:ratchet` ब्लॉकिंग गेट म्हणून चालवतो. स्टँडअलोन `npm run check:cycles` कमांड सल्लागार आहे.
