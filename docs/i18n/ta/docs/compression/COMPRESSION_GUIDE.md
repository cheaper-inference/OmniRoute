> தகுதியான சூழலில் 15-95% வரை தானாகச் சேமிக்கவும். விரைவான மேலோட்டத்திற்கு, [README Compression பகுதியைப்](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) பார்க்கவும்.

## மேலோட்டம்

OmniRoute, கோரிக்கைகள் மேல்நிலை வழங்குநர்களை அடைவதற்கு முன்பே **முன்கூட்டியே** இயங்கும் ஒரு கூறுநிலை prompt compression pipeline-ஐச் செயல்படுத்துகிறது. இதனால் உங்கள் token சேமிப்பு வெளிப்படையாக நிகழ்கிறது — உங்கள் பணிப்பாய்வில் எந்த மாற்றமும் தேவையில்லை.

```
Client கோரிக்கை
  → Compression உத்தித் தேர்வி
    → Combo override உள்ளதா? → combo அமைப்பைப் பயன்படுத்து
    → Auto-trigger வரம்பு உள்ளதா? → auto mode-ஐப் பயன்படுத்து
    → இயல்புநிலை mode உள்ளதா? → global அமைப்பைப் பயன்படுத்து
    → Off ஆக உள்ளதா? → compression-ஐத் தவிர்
  → தேர்ந்தெடுக்கப்பட்ட Compression Mode
    → Off: Compression இல்லை
    → Lite: பாதுகாப்பான whitespace/வடிவமைப்புச் சுத்திகரிப்பு (~15%)
    → Standard: Caveman பாணியிலான தேவையற்ற சொல் நீக்கம் (~30%)
    → Aggressive: வரலாற்றுப் பழமையாக்கம் + சுருக்கமாக்கல் (~50%)
    → Ultra: Heuristic pruning + code-block thinning (~75%)
    → RTK: கட்டளையை அறிந்த terminal/tool-output வடிகட்டல் (மேல்நிலை வரம்பில் 60-90%)
    → Stacked: வரிசைப்படுத்தப்பட்ட பல-engine pipeline, பொதுவாக முதலில் RTK, பின்னர் Caveman (தகுதியான வரம்பில் 78-95%)
  → சுருக்கப்பட்ட கோரிக்கை → வழங்குநர்
```

## Compression Modes

### Off

Compression எதுவும் பயன்படுத்தப்படாது. அனைத்து செய்திகளும் மாற்றமின்றி அனுப்பப்படும்.

### Lite Mode (~15% சேமிப்பு, <1ms தாமதம்)

மிகவும் பாதுகாப்பான mode — அர்த்தத்தில் எந்த மாற்றமும் இல்லை; வடிவமைப்பு மட்டும் சுத்திகரிக்கப்படும்:

| நுட்பம்                  | விளக்கம்                                                               |
| ------------------------ | ---------------------------------------------------------------------- |
| `collapseWhitespace`     | தொடர்ச்சியான வெற்று வரிகளையும் வரி இறுதி இடைவெளிகளையும் ஒன்றிணைக்கிறது |
| `dedupSystemPrompt`      | நகலான system செய்திகளை நீக்குகிறது                                     |
| `compressToolResults`    | விரிவான tool/function வெளியீடுகளைச் சுருக்குகிறது                      |
| `removeRedundantContent` | மீண்டும் இடம்பெறும் வழிமுறைகளை நீக்குகிறது                             |
| `replaceImageUrls`       | base64 படத் தரவு URI-களைச் சுருக்குகிறது                               |

**இதற்கு உகந்தது:** எப்போதும் இயக்கத்தில் இருக்கும் பயன்பாடு, பாதுகாப்பு மிக முக்கியமான பணிப்பாய்வுகள்.

### Standard Mode (~30% சேமிப்பு)

[Caveman](https://github.com/JuliusBrussee/caveman)-இலிருந்து உத்வேகம் பெற்றது — பொருளைப் பாதுகாத்தபடி தேவையற்ற சொற்களையும் நீளமான சொற்றொடர்களையும் நீக்குகிறது:

- தேவையற்ற சொற்களை நீக்குகிறது ("please", "I think", "basically", "actually")
- நீளமான சொற்றொடர்களைச் சுருக்குகிறது ("in order to" → "to", "as a result of" → "because")
- பணிவான தயக்க வெளிப்பாடுகளை நீக்குகிறது ("Would you mind...", "If you could possibly...")
- Coding prompt-களுக்காகச் சீரமைக்கப்பட்ட 30+ regex விதிகள்

**இதற்கு உகந்தது:** அன்றாட coding பணிப்பாய்வுகள், செலவில் கவனம் செலுத்தும் அணிகள்.

### Aggressive Mode (~50% சேமிப்பு)

நீண்ட அமர்வுகளுக்கான அறிவார்ந்த வரலாற்று மேலாண்மை:

- **செய்திப் பழமையாக்கம்** — பழைய செய்திகள் படிப்படியாக அதிகமாகச் சுருக்கப்படும்
- **Tool Result Compression** — நீண்ட tool வெளியீடுகள் துண்டிக்கப்படும் அல்லது விடுபடுத்தப்படும் (முதல்/கடைசி வரிகள்,
  பொருந்தும்-வரி வடிகட்டல், JSON key சுருக்கம்)
- **கட்டமைப்பு ஒருமைப்பாட்டுப் பாதுகாப்புகள்** — `tool_use` + `tool_result` இணைகள் சீராக இருப்பதை உறுதிசெய்கின்றன
- **Context Window விழிப்புணர்வு** — ஒவ்வொரு model-க்குமான token வரம்புகளை மதிக்கிறது

**இதற்கு உகந்தது:** நீண்டகால debugging அமர்வுகள், பெரிய codebase-கள்.

### Ultra Mode (~75% சேமிப்பு)

Token மிக முக்கியமான சூழல்களுக்கான அதிகபட்ச compression:

- **Heuristic Pruning** — உரைநடையின் மதிப்பெண் அடிப்படையிலான token pruning
- **கட்டமைப்புப் பாதுகாப்பு** — fenced code block-கள், inline code, URL-கள் மற்றும் identifier-கள்
  tombstone செய்யப்பட்டு, pruning செய்யப்படாமல், அப்படியே மீண்டும் இணைக்கப்படுகின்றன
- **விருப்பத்திற்குரிய SLM tier** — கட்டமைக்கப்பட்டிருந்தால், சிறிய local model ஒன்று prune-ஐச் செம்மைப்படுத்தலாம்
- Aggressive mode-இலிருந்து சுயாதீனமானது: இது message aging, tool-result compression
  அல்லது fallback summarizer-ஐ இயக்காது (SLM-tier தோல்வி மட்டுமே fallback pass ஒன்றை
  aggressive வழியாக அனுப்பக்கூடும்)

**இதற்கு உகந்தது:** Context வரம்புகளை நீங்கள் மீண்டும் மீண்டும் எட்டும்போது.

### RTK Mode (மேல்நிலை வரம்பில் 60-90%)

Coding-agent அமர்வுகளில் தோன்றும் விரிவான tool வெளியீடுகளுக்காக RTK mode மேம்படுத்தப்பட்டுள்ளது:

- `git status`, `git diff`, `git log`, test runner-கள்,
  TypeScript/Vite/Webpack build-கள், ESLint/Biome/Prettier, npm audit/install-கள், Docker log-கள், infra
  வெளியீடு மற்றும் பொதுவான shell வெளியீடு போன்ற command/output வகைகளைக் கண்டறிகிறது
- `open-sse/services/compression/engines/rtk/filters/` இலிருந்து JSON filter pack-களைப் பயன்படுத்துகிறது
- Project அல்லது global `filters.toml` கோப்புகளிலிருந்து RTK TOML schema v1 filter-களை இறக்குமதி செய்கிறது; இதில் inline-test
  validation மற்றும் project கோப்புகளுக்கான trust-gating அடங்கும்
- Inline verify sample-களுடன் 55 built-in filter-களை வழங்குகிறது
- ANSI கட்டுப்பாட்டு வரிசைகள், progress bar-கள், மீண்டும் வரும் வரிகள் மற்றும் செயல்படுத்த இயலாத இரைச்சலை நீக்குகிறது
- தோல்விகள், பிழைகள், எச்சரிக்கைகள், மாற்றப்பட்ட கோப்புகள், சுருக்கங்கள் மற்றும் நீண்ட வெளியீட்டின் இறுதிப் பகுதியைப் பாதுகாக்கிறது
- Trust-gated project filter-கள், global filter-கள் மற்றும் விருப்பத்திற்குரிய திருத்தப்பட்ட raw-output மீட்டெடுப்பை ஆதரிக்கிறது

**இதற்கு உகந்தது:** Shell, build, test, git, grep மற்றும் file-output transcript-களைக் கொண்ட agent அமர்வுகள்.

### Stacked Mode (தகுதியான வரம்பில் 78-95%)

Stacked mode பல compression engine-களைத் தீர்மானிக்கப்பட்ட வரிசையில் இயக்குகிறது. இயல்புநிலை pipeline:

```txt
RTK -> Caveman
```

இந்த வரிசை முதலில் terminal/tool வெளியீட்டைச் சுருக்கமாக வைத்திருந்து, பின்னர் மீதமுள்ள இயல்புமொழி prompt-க்கு Caveman semantic condensation-ஐப் பயன்படுத்துகிறது. Stacked pipeline-களை global அளவில் அல்லது routing combo-களுக்கு ஒதுக்கப்பட்ட
compression combo-கள் வழியாகக் கட்டமைக்கலாம்.

**இதற்கு உகந்தது:** பெரிய tool log-களுடன் மனித வழிமுறைகள் அல்லது assistant சுருக்கங்கள் கலந்த context.

| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` குறைவான வெளியீட்டு டோக்கன்கள், அளவீடுகளில் சராசரியாக `65%` வெளியீட்டுச் சேமிப்பு, `22-87%` வரம்பு மற்றும் `~46%` உள்ளீட்டுச் சுருக்கக் கருவி |
| RTK     | கட்டளை வெளியீட்டில் `60-90%` சேமிப்பு; மாதிரி அமர்வில் `~118,000 -> ~23,900` டோக்கன்கள் அல்லது `79.7%` சேமிப்பு (`~80%`)                            |

ஒன்றுடன் ஒன்று மேற்பொருந்தும் கருவி/சூழல் பேலோடுகளுக்கு, இயல்புநிலை OmniRoute சேர்க்கை எஞ்சின்களை அடுக்குகிறது:

```txt
RTK -> Caveman
```

ஒருங்கிணைந்த சேமிப்புகள் கூட்டல் முறையிலானவை அல்ல, பெருக்கல் முறையிலானவை:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

RTK மற்றும் Caveman இரண்டும் ஒரே உள்ளீடு/சூழல் பேலோடைக் குறைக்க முடியும் போது அந்த `78-95%` அளவு பொருந்தும்.
Caveman மறுமொழி வெளியீட்டு முறை தனியானது: அது இயக்கப்பட்டிருக்கும்போது, Caveman-இன் சொந்த வெளியீட்டுச் சேமிப்புகளைப் பயன்படுத்தவும் (`65%`
சராசரி, `~75%` முதன்மை மதிப்பு, `22-87%` வரம்பு). மொத்த பில்லிங் சேமிப்புகள் உங்கள் ப்ராம்ப்ட்/வெளியீட்டு விகிதத்தைச் சார்ந்தவை.

### "தகுதியானது" என்பதன் உண்மையான பொருள்

15-95% என்ற முதன்மை வரம்பு உண்மையானதே, ஆனால் அது **தேவையற்ற விதத்தில் மீண்டும் வரும் அல்லது அளவுக்கு அதிகமாக விவரமான** உள்ளடக்கத்திற்கு மட்டுமே பொருந்தும் — மீண்டும் மீண்டும் வரும்
பிழை வரிகள், ஒரே எச்சரிக்கையைத் தொடர்ந்து வெளியிடும் பில்ட் பதிவு, அளவுக்கு அதிகமான `grep`/கோப்பு-வாசிப்பு டம்ப் போன்றவை. இது
ஒவ்வொரு கோரிக்கையிலும் அவ்வளவு சேமிப்பு கிடைக்கும் என்று **பொருளல்ல**.

சோதனை மூலம் உறுதிசெய்யப்பட்டது (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): ஒரே மாதிரியான 300
பிழை வரிகளைக் கொண்ட Anthropic-வடிவ `tool_result` தொகுதிக்கு எதிராக இயக்கப்பட்ட
`stacked` (RTK + Caveman) செயலாக்கம் **95.93% டோக்கன் சேமிப்பு / 96.26% எழுத்துச் சேமிப்பு** அளித்தது — இது விளம்பரப்படுத்தப்பட்ட
வரம்பிற்குள் துல்லியமாக உள்ளது. ஆனால் அதே பைப்லைனை இயல்பான, மீளுருவாக்கமற்ற கருவி வெளியீட்டில் (சுத்தமான `grep` பொருத்தப் பட்டியல்,
குறுகிய கோப்பு வாசிப்பு, சாதாரண உரையாடல் உரை) இயக்கும்போது, அது சரியாகவே **கிட்டத்தட்ட பூஜ்ஜிய சேமிப்பை** அளிக்கிறது; ஏனெனில்
அகற்றுவதற்கு மீண்டும் வரும் எதுவும் இல்லை, மேலும் குறியீட்டுத் தொகுதிகள், URL-கள், தலைப்புகள், பதிப்புகள் அல்லது ALL-CAPS மாறிலி அடையாளங்காட்டிகளை நீக்கும் அல்லது மாற்றும்
மறுஎழுத்தாக்கத்தை அனுப்ப `validateCompression()` (`validation.ts`) மறுக்கிறது.

இது எதிர்பார்க்கப்பட்ட, பாதுகாப்பான நடத்தை; பிழை அல்ல: பெரும்பாலும் சுத்தமான கோப்புகளை வாசிக்கும்/grep செய்யும் ஒரு குறியீட்டாக்க அமர்வு,
சுருக்கம் முழுமையாக இயக்கப்பட்டிருந்தாலும், மிதமான மொத்தச் சேமிப்பையே காணும்; அதே சமயம் தோல்வியுறும்
சுழற்சி அல்லது அதிக வெளியீட்டை உருவாக்கும் லின்டரை எதிர்கொள்ளும் அமர்வு, அந்தப் போக்குவரத்தில் முழு 78-95% வரம்பைக் காணும். ஒரே அமர்வின்
குறைந்த மொத்தச் சேமிப்பு சதவீதத்தைச் சுருக்கம் தவறாக உள்ளமைக்கப்பட்டுள்ளது என்பதற்கான ஆதாரமாகப் பயன்படுத்த வேண்டாம் — முதலில்
அடிப்படைக் கருவி வெளியீடு உண்மையில் மீண்டும் மீண்டும் வந்ததா என்பதைச் சரிபார்க்கவும்.

## உள்ளமைவு

### கட்டுப்பாட்டுப் பலகை

`Dashboard → Context & Cache` என்பதற்குச் செல்லவும்:

- **Caveman** — பயன்முறைத் தேர்வு, மொழித் தொகுப்புகள், முன்னோட்டம் மற்றும் உலகளாவிய இயல்புநிலைகள்
- **RTK** — கட்டளை-வடிகட்டி முன்னோட்டம், RTK பாதுகாப்பு அமைப்புகள் மற்றும் வடிகட்டி பட்டியல்
- **Compression Combos** — வழிச்செலுத்தல் சேர்க்கைகளுக்கு ஒதுக்கப்பட்ட பெயரிடப்பட்ட எஞ்சின் செயலாக்கத் தொடர்கள்
- **Auto-Trigger Threshold** — டோக்கன் எண்ணிக்கை வரம்பை மீறும்போது சுருக்கத்தைத் தானாகச் செயல்படுத்தும்

### ஒவ்வொரு சேர்க்கைக்குமான மீறல்

`Dashboard → Context & Cache → Compression Combos` என்பதில், ஒரு வழிச்செலுத்தல் சேர்க்கைக்கு சுருக்கச் சேர்க்கை ஒன்றை ஒதுக்கவும்:

```txt
சேர்க்கை: "free-tier-fallback"
  சுருக்கச் சேர்க்கை: "coding-agent-stack"
  செயலாக்கத் தொடர்: RTK -> Caveman
  இலக்குகள்:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

கட்டணச் சந்தாக்களில் லைட் பயன்முறையை வைத்துக்கொண்டே, இலவச/நிரலாக்க வழங்குநர்களில் அடுக்கப்பட்ட சுருக்கத்தைப் பயன்படுத்த இது உங்களை அனுமதிக்கிறது.

இந்த "ஒவ்வொரு சேர்க்கைக்குமான மீறல்" ஒதுக்கீடு, **வழிச்செலுத்தல்-சேர்க்கை சுருக்கப் பயன்முறை** மீறலில் (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — அந்தப் புலத்தின் திட்டவடிவம் `rtk`, `stacked` மற்றும் `omniglyph` ஆகியவற்றையும் ஏற்கிறது) இருந்து வேறுபட்ட ஒரு கட்டுப்பாடாகும் — அந்த மீறல் பெயரிடப்பட்ட சுருக்கச்-சேர்க்கை செயலாக்கத் தொடரைத் தேர்ந்தெடுக்காது; அது `resolveCompressionPlan` பயன்படுத்தும் `compressionMode` புலத்தை மட்டும் அமைக்கிறது. இதைச் சேர்க்கை அட்டையில் (`Dashboard → Combos`) அல்லது, #6760 முதல், மேலே ஆவணப்படுத்தப்பட்ட செயலாக்கத் தொடர்-ஒதுக்கீட்டுத் தேர்வுப்பெட்டிக்கு அடுத்துள்ள `Dashboard → Context & Cache → Compression Combos` என்பதன் "Assign to routing" பட்டியலில் ஒவ்வொரு வழிச்செலுத்தல் சேர்க்கைக்கும் அமைக்கலாம். இரு இடைமுகங்களும் ஒரே `PUT /api/combos/{id}` முனைப்புள்ளி வழியாக நிலைநிறுத்தப்படுகின்றன.

### ஒவ்வொரு கோரிக்கைக்குமான மீறல்

ஒற்றைக் கோரிக்கைக்கான சுருக்கத் திட்டத்தை மீற `x-omniroute-compression` கோரிக்கைத் தலைப்பை அனுப்பவும். இதுவே மிக உயர்ந்த முன்னுரிமையைக் கொண்டுள்ளது — இது வழிச்செலுத்தல்-சேர்க்கை மீறல், செயலில் உள்ள சுயவிவரம், தானியங்கித் தூண்டுதல் மற்றும் பலகையின் Default ஆகியவற்றை மீறுகிறது. அறியப்படாத மதிப்புகள் புறக்கணிக்கப்படும் (கோரிக்கை ஒருபோதும் நிராகரிக்கப்படாது), மேலும் உலகளாவிய முதன்மைச் சுவிட்ச் அனைத்தையும் தொடர்ந்து கட்டுப்படுத்தும்: சுருக்கம் உலகளவில் முடக்கப்பட்டிருக்கும்போது, தலைப்பால் அதை இயக்க முடியாது. மதிப்புகள்:

| மதிப்பு       | விளைவு                                                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `off`         | இந்தக் கோரிக்கைக்குச் சுருக்கம் இல்லை.                                                                                                |
| `default`     | பலகையிலிருந்து பெறப்பட்ட Default சுயவிவரம் (செயலில் உள்ள சுயவிவரத்தைப் புறக்கணிக்கும்). இழப்புடைய எஞ்சின்கள் முடக்கப்பட்டே இருக்கும். |
| `safe`        | தலைப்பைத் தவிர்ப்பதற்குச் சமம்: நகல்நீக்கம் மற்றும் வெற்றிட மடிப்பு மட்டும்.                                                          |
| `allow-lossy` | சுருக்கங்கள், பொருத்த வடிகட்டிகள் மற்றும் பாணி மறுஎழுத்துகள் உள்ளிட்ட இந்தக் கோரிக்கையின் இயக்குநர் திட்டத்தைத் தக்கவைக்கும்.         |
| `engine:<id>` | இயக்கப்பட்டிருக்கும்போது ஒற்றை எஞ்சின், எ.கா. `engine:rtk`. அந்த எஞ்சினுக்கான ஒவ்வொரு கோரிக்கைக்குமான விருப்பச் சேர்க்கை இதுவாகும்.   |
| `<combo>`     | பெயரிடப்பட்ட ஒரு சேர்க்கை; முதலில் பெயரால் (எழுத்துப் பெட்டி வேறுபாட்டைப் பொருட்படுத்தாமல்), பின்னர் id மூலம் பொருத்தப்படும்.         |

`allow-lossy`, `engine:<id>` அல்லது பெயரிடப்பட்ட சேர்க்கை இல்லாமல், இழப்புடைய எஞ்சின்கள் பயன்படுத்தப்படாது. சுருக்கம் இயக்கப்பட்டிருக்கும்போது, கோரிக்கைக்கு அமர்வு நகல்நீக்கமும் வெற்றிட மடிப்பும் தொடர்ந்து பயன்படுத்தப்படும்.

பயன்படுத்தப்பட்ட திட்டம் `X-OmniRoute-Compression: <mode>; source=<source>` பதில் தலைப்பில் திருப்பி அனுப்பப்படும்; இங்கு `<source>` என்பது `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` அல்லது `off` ஆகியவற்றில் ஒன்றாகும்.

மேலே விவரிக்கப்பட்டுள்ள 7 முறைகளுக்கு அப்பால் (மூலக் குறியீடு `codex-responses` மற்றும்
`omniglyph` முறைகளையும் ஏற்கிறது; இந்த வழிகாட்டி அவற்றை உள்ளடக்கவில்லை), கீழேயுள்ள பகுதிகள்
அந்த முறைகளுக்குள் அல்லது அவற்றுடன் இணைந்து செயல்படும் அம்சங்களை விவரிக்கின்றன: கருவி முடிவு சுருக்கம் மற்றும் படிப்படியான பழமையாக்கம்
ஆகியவை தீவிர இயந்திரத்தின் படிகள் 1 மற்றும் 2 ஆகும் (தீவிர முறை மற்றும் அடுக்கப்பட்ட
செயலாக்கக் குழாயின் `aggressive` படி), அடுக்கப்பட்ட செயலாக்கக் குழாய் என்பது அடுக்கப்பட்ட முறை செயல்படும் விதமாகும், கேச்-விழிப்புணர்வு சுருக்கம்
கேச்சிங் வழங்குநர்களுக்காக, சுருக்கம் இயக்கப்பட்டிருக்கும்போது `aggressive` மற்றும் `ultra` ஆகியவற்றை `standard` ஆகத்
தரமிறக்குகிறது; மேலும் குகைமனித வெளியீட்டு முறை மற்றும் வெளியீட்டுப் பாணிகள் ஆகியவை விருப்பத்தேர்வாக இயக்கப்படும் கணினி-தூண்டல் அறிவுறுத்தல்கள் ஆகும்,
இவை இயல்பாக முடக்கப்பட்டிருக்கும் மற்றும் கோரிக்கையைச் சுருக்குவதற்குப் பதிலாக மாதிரியின் வெளியீட்டை வடிவமைக்கின்றன.

### கேச்-விழிப்புணர்வு சுருக்கம்

சில வழங்குநர்கள் (தூண்டல் கேச்சிங்கைக் கொண்ட Anthropic போன்றவை) **தூண்டல் கேச்சிங்கை**
ஆதரிக்கின்றனர்; இது செலவுகளையும் தாமதத்தையும் குறைப்பதற்காகத் தூண்டலின் சில பகுதிகளை கேச் செய்ய
அவர்களுக்கு உதவுகிறது. கேச்சிங் இயக்கப்பட்டிருக்கும்போது, தீவிர சுருக்கம் உண்மையில் செயல்திறனைப்
**பாதிக்கக்கூடும்**, ஏனெனில் அது கேச் செய்யப்பட்ட டோக்கன்களை மாற்றி, கேச்சைச் செல்லாததாக்குகிறது.

`cachingAware.ts` தொகுதி, **கேச்சிங் சூழலைக் கண்டறிந்து**, அதற்கேற்ப
**சுருக்க உத்தியைச் சரிசெய்வதன்** மூலம் இதைத் தீர்க்கிறது.

#### இது செயல்படும் விதம்

1. **கேச்சிங் சூழலைக் கண்டறிதல்** — கோரிக்கை உடலில் `cache_control` குறியீடுகள் உள்ளதா எனச் சோதிக்கிறது
2. **கேச்சிங் வழங்குநர்களை அடையாளம் காணுதல்** — இலக்கு வழங்குநர் கேச்சிங்கை ஆதரிக்கிறாரா எனச் சரிபார்க்கிறது
3. **உத்தியைச் சரிசெய்தல்** — கேச்சிங் வழங்குநர்களுக்காக `aggressive`/`ultra` ஆகியவற்றை `standard` ஆகத் தரமிறக்குகிறது
4. **கணினித் தூண்டலைத் தவிர்த்தல்** — கணினித் தூண்டல்கள் வழக்கமாக கேச் செய்யப்படுவதால், அவற்றைச் சுருக்குவதில்லை

உத்தி உதவிச் செயல்பாடு ஒரு `deterministicOnly` கொடியையும் வழங்குகிறது; ஆனால் திட்ட உருவாக்கி
உத்தியை மட்டுமே பயன்படுத்துகிறது — தற்போது அதன் பின்வரும் எந்தச் செயலாக்கமும் அந்தக் கொடியைப் படிப்பதில்லை.

#### குறியீட்டு எடுத்துக்காட்டு

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← கேச் குறியீடு
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### எப்போது பயன்படுத்த வேண்டும்

கேச்-விழிப்புணர்வு சுருக்கம் **எப்போதும் இயக்கப்பட்டிருக்கும்** — எந்த உள்ளமைவும் தேவையில்லை. சுருக்கம்
இயக்கப்பட்டு, இலக்கு வழங்குநர் தூண்டல் கேச்சிங்கை ஆதரிக்கும் போதெல்லாம் (Anthropic, OpenAI
போன்றவை) இது செயல்படும்; வெளிப்படையான `cache_control` குறியீடுகள் தேவையில்லை — கேச்சிங் வழங்குநர்
மட்டுமே இருந்தாலும் தரமிறக்கம் தூண்டப்படும், ஆனால் குறியீடுகள் மட்டும் அதை ஒருபோதும் தூண்டாது (குறியீடு கண்டறிதல் கேச்
தொலைஅளவீட்டுக்கு உள்ளீடு அளிக்கிறது, உத்தி முடிவுக்கு அல்ல).

### படிப்படியான பழமையாக்கம்

நீண்ட உரையாடல்களில் பல செய்திச் சுற்றுகள் குவிகின்றன; ஆனால் பழைய சுற்றுகளின்
பொருத்தம் படிப்படியாகக் குறைகிறது. `progressiveAging.ts` தொகுதி **சுற்று இடைவெளியின் அடிப்படையில் செய்திகளின் விவரத்தைக் குறைக்கிறது**
(உரையாடலின் முடிவிலிருந்து இடைவெளி அளவிடப்படுகிறது). வழங்கப்படும் இயல்புநிலைகளுடன்
(`verbatim: 2, light: 2, moderate: 3`):

- **கடைசி 2 சுற்றுகள் (இடைவெளி ≤ 2)**: சொற்சொல்லாக வைத்திருக்கப்படும்
- **இடைவெளி 3**: குகைமனித சுருக்கம் (நிரப்புச் சொற்களை அகற்றுதல்)
- **இடைவெளி 4+**: உதவியாளர் செய்திகள் சுருக்கமாக்கப்படும்; பயனர் செய்திகள் அவற்றின் முதல்
  வரியாகக் குறைக்கப்பட்டு, 120 எழுத்துகளுக்குள் வரம்பிடப்படும்; மற்ற பாத்திரங்கள் மாற்றப்படாது. கணினித் தூண்டல்கள், ஏற்கெனவே பழமையாக்கப்பட்ட
  செய்திகள் மற்றும் சமீபத்திய பயனர் செய்தி ஆகியவை இடைவெளியைப் பொருட்படுத்தாமல் எப்போதும் சொற்சொல்லாக வைத்திருக்கப்படும்.
  எதுவும் முழுமையாக நீக்கப்படாது; மேலும் வழங்கப்படும் இயல்புநிலைகளில் (`light` என்பது `verbatim`-க்குச் சமம்)
  `light` வரம்பை அடைய முடியாது.

#### குறியீட்டு எடுத்துக்காட்டு

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... மேலும் 50 சுற்றுகள் ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // கடைசி 3 சுற்றுகள்: சொற்சொல்லாக
  light: 8, // இடைவெளி <= 8: இலகு சுருக்கம்
  moderate: 20, // இடைவெளி <= 20: குகைமனித சுருக்கம்
  fullSummary: 5, // வகைக்கு அவசியம்; வரம்பிடல் குறியீடு இதைப் படிப்பதில்லை
  // இடைவெளி > 20: சுருக்கமாக்கப்படும் (உதவியாளர்) / முதல் வரி வைத்திருக்கப்படும் (பயனர்)
});

// saved = சேமிக்கப்பட்ட டோக்கன்களின் எண்ணிக்கை
```

#### எப்போது பயன்படுத்த வேண்டும்

`aggressive` முறைக்கு படிப்படியான பழமையாக்கம் **எப்போதும் இயக்கப்பட்டிருக்கும்** — இது
`compressAggressive()`-இன் படி 2 ஆகும். Ultra முறை இதை இயக்குவதில்லை. இது குறிப்பாகப் பின்வருவனவற்றுக்கு
பயனுள்ளதாக இருக்கும்:

- நீண்டகாலம் நீடிக்கும் குறியீட்டாக்க அமர்வுகள்
- பல நாட்கள் நீடிக்கும் உரையாடல்கள்
- பல கருவி அழைப்புகளைக் கொண்ட முகவர் சார்ந்த பணிப்பாய்வுகள்

### குகைமனித வெளியீட்டு முறை

குகைமனித வெளியீட்டு முறை, சுருக்கமான வெளியீட்டை வழங்குமாறு மாதிரியிடமே கேட்கும்
**கணினித் தூண்டல் அறிவுறுத்தல்களைச்** சேர்க்கிறது — `lite` நிலை முழுமையான வாக்கியங்களைத் தக்கவைக்கும் சுருக்கமான பதில்களைக் கேட்கிறது; `full`
நிலை "புத்திசாலி குகைமனிதனைப் போலச் சுருக்கமாகப் பதிலளி" எனக் கேட்கிறது; `ultra` நிலை தந்தி பாணியிலான வெளியீட்டைக் கேட்கிறது;
அறிவுறுத்தல்கள் கேட்க மட்டுமே முடியும், அவற்றால் அதை உறுதிசெய்ய முடியாது. கோரிக்கைகள் அவற்றை
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) வழியாகப் பெறுகின்றன:
`open-sse/handlers/chatCore.ts` முதலில் பின்னோக்கி இணக்கத்தன்மை இடைமாற்றியின் மூலம் தேர்வைத் தீர்மானிக்கிறது
(`open-sse/services/compression/outputStyles/backCompat.ts`-இல் உள்ள `resolveOutputStyleSelection()`); `outputStyles`
காலியாக இருக்கும்போது, இயக்கப்பட்ட `cavemanOutputMode`-ஐ
`cavemanOutputMode.intensity` தீவிரத்திலுள்ள `terse-prose` வெளியீட்டுப் பாணிக்கு இது பொருத்துகிறது (கீழே பின்னோக்கி இணக்கத்தன்மையைப் பார்க்கவும்); காலியாக இல்லாத `outputStyles`
தேர்வு அப்படியே பயன்படுத்தப்படும்; அதன் பின்னர் `cavemanOutputMode.enabled` மற்றும் `intensity` எந்த
விளைவையும் ஏற்படுத்தாது, ஆனால் அதன் `autoClarity` மாற்று இன்னும் பொருந்தும். `outputMode.ts`-இல்
அறிவுறுத்தல் உரைகள் (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), உள்ளடக்கத் தவிர்ப்பு மற்றும்
உட்செலுத்தல் பயன்படுத்தும் இடமிடல் உதவிச் செயல்பாடு உள்ளன; அதன் சொந்த `applyCavemanOutputMode()` உட்செலுத்திக்குத்
தயாரிப்புச் சூழலில் எந்த அழைப்பாளரும் இல்லை.

#### இது செயல்படும் விதம்

இந்தப் பயன்முறை உள்ளீட்டைச் சுருக்காது. இது system prompt-இல் ஒரு அறிவுறுத்தல் தொகுதியைச் சேர்க்கிறது
(கீழே உள்ள உட்செலுத்தல் எவ்வாறு செயல்படுகிறது என்பதைப் பார்க்கவும்), மேலும் கோரிக்கைக்காகத் தேர்ந்தெடுக்கப்பட்ட எந்த உள்ளீட்டுச் சுருக்கப் பயன்முறையும்
அந்தத் தொகுதியை இப்போது கொண்டுள்ள body மீது பின்னர் தொடர்ந்து இயங்கும். ஒவ்வொரு நிலையும் இறுதியில் கொண்டிருக்கும் பகிரப்பட்ட
வரம்புகள் பிரிவுக்கு முன், ஆங்கில `full` நிலை இவ்வாறு உள்ளது:

> "புத்திசாலியான குகைமனிதனைப் போலச் சுருக்கமாகப் பதிலளி. articles (a/an/the), நிரப்புச் சொற்கள் (just/really/basically/actually/simply), மரியாதைச் சொற்கள், தயக்கமான மொழி ஆகியவற்றைத் தவிர். சொற்றொடர்கள் மட்டும் இருந்தாலும் பரவாயில்லை. குறுகிய இணைச்சொற்களைப் பயன்படுத்து (extensive என்பதற்குப் பதில் big, implement என்பதற்குப் பதில் fix). அனைத்து தொழில்நுட்ப உள்ளடக்கம், code, errors, URLs, identifiers ஆகியவற்றையும் துல்லியமாக வைத்திரு."

இது குறிப்பாகப் பின்வருவனவற்றுக்கு நன்றாகச் செயல்படுகிறது:

- Code உருவாக்கம் (சுருக்கமான output = குறைவான tokens)
- விரைவான கேள்வி-பதில் (விரிவான விளக்கங்கள் தேவையில்லை)
- தொகுதிச் செயலாக்கம் (செயல்திறனை அதிகப்படுத்துதல்)

#### எப்போது பயன்படுத்துவது

Caveman output mode என்பது **opt-in**. சுருக்கம் இயக்கப்பட்டிருக்கும்போது (`enabled: true`, Compression Settings பக்கத்தில் உள்ள முதன்மை மாற்றி
இயக்கப்பட்ட நிலையில்), `cavemanOutputMode.enabled` மூலம் இதை இயக்கவும்; `intensity`
என்பது `lite`, `full` அல்லது `ultra` என்பதைத் தேர்ந்தெடுக்கிறது:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ஒரு compression combo-வின் **Output Mode** மாற்றி (`outputMode`, அதன் நிலை `outputModeIntensity`-இல்)
அந்த combo பொருந்தும் கோரிக்கைகளுக்கு அதே மாற்றியை அமைக்கிறது; மேலும்
`omniroute_set_compression_engine` MCP கருவி தனது boolean `outputMode`
argument மூலம் அதை எழுதுகிறது. காலியாக இல்லாத `outputStyles` தேர்வு, இந்த மாற்றியைவிட முன்னுரிமை பெறுகிறது. Dashboard-இல், **Terse prose** output style-ஐ இயக்குவது அதே தொகுதியை உட்செலுத்துகிறது (கீழே உள்ள Output
Styles பகுதியைப் பார்க்கவும்).

#### உட்செலுத்தல் எவ்வாறு செயல்படுகிறது

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) தேர்வைப்
பட்டியலுடன் ஒப்பிட்டுத் தீர்மானிக்கிறது (அறியப்படாத id-களும் locale பொருந்தாத பாணிகளும்
நீக்கப்படும்; அவை ஒருபோதும் பிழையாகாது; எந்தப் பாணியாகவும் தீர்மானிக்கப்படாத தேர்வு,
உள்ளடக்கத்தை மாற்றாமல் `no_styles` எனத் தவிர்க்கப்படும்), தேர்ந்தெடுக்கப்பட்ட வழிமுறைகளைப்
பட்டியல் வரிசையில் ஒன்றிணைக்கிறது,
எல்லைகள் குறித்த உட்பிரிவை **ஒரே முறை** சேர்க்கிறது (மேலும் `less-code` அல்லது `ponytail`
தேர்ந்தெடுக்கப்படும்போது பாதுகாப்பு உட்பிரிவு, `SAFETY_BOUNDARIES` அல்லது அதன் மொழிபெயர்ப்பு,
சேர்க்கப்படும்), அத்துடன் தொகுதியை ஒற்றை idempotency குறியீட்டுடன்
(`[OmniRoute Output Styles]`) தொடங்குகிறது; எனவே மீண்டும் பயன்படுத்துவது எந்த மாற்றத்தையும்
ஏற்படுத்தாது. தீர்மானிக்கப்பட்ட மொழிக்கு (கீழே உள்ள மொழித் தேர்வைப் பார்க்கவும்) மொழிபெயர்ப்பு
இருந்தால், ஆங்கிலத்திற்குப் பதிலாக உள்ளூர்மயமாக்கப்பட்ட வழிமுறை உட்செலுத்தப்படும்.

காலியாக இல்லாத `messages` அணியைக் கொண்ட body-இல், உள்ளடக்க bypass-க்கு முன்பாக
idempotency சரிபார்ப்பு இயங்கும்: `[OmniRoute Output Styles]` குறியீடு ஏற்கனவே மேல்நிலை
`system` புலத்தில் (ஒரு string அல்லது content-block array) அல்லது string உள்ளடக்கமுள்ள
system செய்தியில் இருந்தால், body `already_applied` என மாற்றமின்றி விடப்பட்டு, keyword
சரிபார்ப்பு எதுவும் இயங்காது. இல்லையெனில், உள்ளடக்க bypass
(`open-sse/services/compression/outputMode.ts`-இல் உள்ள
`shouldBypassCavemanOutputMode()`) கடைசி மூன்று செய்திகளின் உரையை, அவற்றின் role எதுவாக
இருந்தாலும், சரிபார்க்கிறது. அந்த உரை அதன் பாதுகாப்பு, மீளமுடியாத செயல் அல்லது
தெளிவுபடுத்தல் keywords-உடன் பொருந்தினால், அல்லது வரிசையைச் சார்ந்த பின்வரும் தொடருடன்
பொருந்தினால், முழு turn-க்கும் பாணிகள் தவிர்க்கப்படும்: `first`, `then`, `after that`,
`before`, `rollback` அல்லது `backup` ஆகியவற்றில் ஒன்றைத் தொடர்ந்து 240 எழுத்துகளுக்குள்
`delete`, `drop`, `migrate`, `deploy` அல்லது `release` வருவது. **Auto-Clarity Bypass**
toggle (`cavemanOutputMode.autoClarity`, இயல்புநிலையில் இயக்கத்தில் இருக்கும்)
இயக்கப்பட்டிருக்கும்போது bypass இயங்கும்; toggle-ஐ அணைத்தால் keyword சரிபார்ப்பு
தவிர்க்கப்படும்.

bypass அந்த turn-ஐ அனுமதிக்கும்போது, புதிய `messages[0]`-ஐ ஒருபோதும் உருவாக்காத
`placeSystemInstruction()` (அதே கோப்பு), பின்வருவனவற்றில் முதலில் கண்ட இடத்தில் தொகுதியை
வைக்கிறது:

1. தொடக்கத்தில் string உள்ளடக்கமுள்ள system செய்தி: அதன் உரைக்குப் பிறகு தொகுதி
   சேர்க்கப்படும்.
2. மேல்நிலை `system` புலம்: string-இன் உரைக்குப் பிறகு தொகுதி சேர்க்கப்படும், அல்லது
   content-block array-இல் புதிய text block ஆகச் சேர்க்கப்படும்.
3. பின்னர் வரும் முதல் string உள்ளடக்கமுள்ள system செய்தி: அதன் உரைக்குப் பிறகு தொகுதி
   சேர்க்கப்படும்.
4. மேலே உள்ளவை எதுவும் இல்லையெனில்: `messages`-இன் இறுதியில் ஒரு புதிய system
   செய்திக்குள் தொகுதி வைக்கப்படும்.

`messages` array இல்லாத body-இல் (அல்லது காலியான array உள்ள body-இல்), உள்ளடக்க bypass
எதுவும் இயங்காது; மேல்நிலை `system` புலமும் பரிசீலிக்கப்படாது. string வகையிலான
`instructions` புலத்தின் உரைக்குப் பிறகு தொகுதி சேர்க்கப்படும்; ஆனால் அந்தப் புலத்தில்
ஏற்கனவே `[OmniRoute Output Styles]` குறியீடு இருந்தால், body `already_applied` என
மாற்றமின்றி விடப்படும். body-இல் string வகையிலான `instructions` புலம் இல்லாமல்,
`input` (ஒரு string அல்லது array) இருந்தால், அந்தப் புலத்தில் முன்பு இருந்த string அல்லாத
மதிப்பை மாற்றி, தொகுதி `instructions` ஆகிறது. string வகையிலான `instructions` புலமும்,
string அல்லது array வகையிலான `input`-உம் இல்லாத body மாற்றமின்றி விடப்பட்டு
`no_messages` எனத் தவிர்க்கப்படும்.

### அடுக்கப்பட்ட Pipeline

Stacked mode **பல engine-களைத் தொடர்ச்சியாக** இயக்குகிறது — வழக்கமாக முதலில் RTK
(tool output-இல் 60-90% சேமிப்பு), பின்னர் மீதமுள்ள உரையில் Caveman (~46% input
சேமிப்பு). இணைக்கப்பட்டால், அது **தகுதியான 78-95% வரம்பு** ஆகும் (மேலே உள்ள Upstream Savings Math-ஐப் பார்க்கவும்):
`1 - (1 - 0.60..0.90) × (1 - 0.46)`-இன் சராசரி ≈89%.

#### இது எவ்வாறு செயல்படுகிறது

```
உள்ளீடு (1000 token-கள்)
  → RTK (command-ஐ அறியும் filter) → 200 token-கள்
    → Caveman (தேவையற்ற உரை நீக்கம்) → 108 token-கள்
  → வெளியீடு (108 token-கள், ~89% சேமிப்பு)
```

#### எப்போது பயன்படுத்துவது

Stacked mode-ஐப் பின்வருவனவற்றுக்குப் பயன்படுத்தவும்:

- கருவிகள் அதிகம் பயன்படுத்தப்படும் workflow-கள் (agentic coding, research)
- செலவைக் கருத்தில் கொள்ளும் batch processing
- உங்களுக்கு அதிகபட்ச token சேமிப்பு தேவைப்படும்போது

setting மூலமாகவோ அல்லது routing combo-வுக்கு ஒதுக்கப்பட்ட பெயரிடப்பட்ட compression combo மூலமாகவோ அமைக்கப்படுகின்றன (மேலே உள்ள
Per-Combo Override-ஐப் பார்க்கவும்) — auto-combo `modePack` மூலம் அல்ல (அந்த field
auto-combo model தேர்வின் weight-ஐ மட்டுமே மாற்றும்; மேலும் `stacked` என்பது செல்லுபடியாகும் pack name அல்ல).

## சுருக்கச் சேர்க்கை மேலெழுதல்கள்

வெவ்வேறு பயன்பாட்டு நிலைகளுக்கான நடத்தையை நுணுக்கமாகச் சரிசெய்ய, உலகளாவிய சுருக்க முறையை **ஒவ்வொரு சேர்க்கைக்கும் தனித்தனியாக** மேலெழுதலாம்:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

இது பின்வருவனவற்றுக்குப் பயனுள்ளதாக இருக்கும்:

- **குறியீட்டாக்கச் சேர்க்கைகள்**: நீண்ட அமர்வுகளுக்கு `aggressive` முறையைப் பயன்படுத்தவும்
- **விரைவான கேள்வி-பதில் சேர்க்கைகள்**: விரைவான பதில்களுக்கு `lite` முறையைப் பயன்படுத்தவும்
- **கருவி-செறிந்த சேர்க்கைகள்**: அதிகபட்சச் சேமிப்புக்கு `stacked` முறையைப் பயன்படுத்தவும்
- **உற்பத்திச் சேர்க்கைகள்**: தேக்கக வழங்குநர்களுக்கு மேலெழுதலை முடக்கியே வைக்கவும் — எப்போதும் செயல்பாட்டிலுள்ள
  தேக்கக-விழிப்புணர்வு சரிசெய்தல், `aggressive`/`ultra` முறைகளைத் தானாகவே `standard` முறைக்குத் தரமிறக்கும்
  (தேர்ந்தெடுக்கக்கூடிய `cache-aware` முறை எதுவும் இல்லை)
