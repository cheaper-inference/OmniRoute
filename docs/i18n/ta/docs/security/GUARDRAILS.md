> **கடைசியாகப் புதுப்பிக்கப்பட்டது:** 2026-10-17 — v3.8.52 ([கவரேஜ் மற்றும் வரம்புகள்](#coverage-and-limits) சேர்க்கப்பட்டது:
> ஹுக்குகள் எந்த ரூட்டுகள் மற்றும் ரெஸ்பான்ஸ் பாதைகளை அடைகின்றன, ஒன்றிணைக்கப்பட்ட டிசேபிள் ஹெடர்கள் (#16412), கட்டாய
> எல்லையாக இன்ஜெக்ஷன் பிளாக் மோட் (#16413), மற்றும் post-call-க்கு முன் ரெஸ்பான்ஸை எது பார்க்கிறது)

Guardrail-கள் OmniRoute-க்கும் அப்ஸ்ட்ரீம் புரொவைடர்களுக்கும் இடையிலான எல்லையில்
பாதுகாப்பு, பாலிசி மற்றும் கண்டென்ட் டிரான்ஸ்ஃபார்மேஷன்களை நடைமுறைப்படுத்துகின்றன. ஒவ்வொரு
guardrail-மும் ரிக்வெஸ்ட் பேலோடுகளை (`preCall`) மற்றும் அப்ஸ்ட்ரீம் ரெஸ்பான்ஸ்களை (`postCall`)
ஆய்வு செய்யலாம் (மற்றும் விரும்பினால் நிராகரிக்கலாம், டிரான்ஸ்ஃபார்ம் செய்யலாம், அல்லது குறிப்பிடலாம்).

இந்த சிஸ்டம் **fail-open**: ஒரு guardrail இயங்கும்போது throw செய்தால், registry
அந்த எர்ரை பதிவு செய்து, ரிக்வெஸ்டை தோல்வியடையச் செய்யாமல் அடுத்த guardrail-லுடன்
தொடரும். பிளாக் செய்வது ஒரு வெளிப்படையான முடிவு (`block: true`), ஒருபோதும் விபத்து அல்ல.
ஒரே விதிவிலக்கு நிறுத்தப்பட்ட (aborted) ரிக்வெஸ்ட்: காலரின் `signal` abort
செய்யப்பட்டால், throw செய்யும் guardrail தவிர்க்கப்படாமல் ஹுக் ரன்னை reject செய்யும்.

இந்த ஹுக்குகள் ஒவ்வொரு ரூட்டிலும் அல்லது ஒவ்வொரு ரெஸ்பான்ஸிலும் இயங்காது.
ஒரு guardrail-ஐ செக்யூரிட்டி கன்ட்ரோலாக நம்புவதற்கு முன்
[கவரேஜ் மற்றும் வரம்புகள்](#coverage-and-limits)-ஐ படியுங்கள்.

## உள்ளமைந்த Guardrail-கள்

Registry இம்போர்ட் செய்யும்போது ஆறு guardrail-களை பிரையாரிட்டி வரிசையில் தானாகவே ஏற்றுகிறது
(`registry.ts` → `registerDefaultGuardrails()` என்பதைப் பார்க்கவும்):

| பிரையாரிட்டி | பெயர்               | நிலை(கள்)      | கோப்பு                |
| ------------ | ------------------- | -------------- | --------------------- |
| `5`          | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`          | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`          | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`         | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`         | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`         | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

குறைந்த பிரையாரிட்டி எண்கள் **முதலில்** இயங்கும்.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

GLM 5.3 பேஸ் மாடலுக்கும் `glm-5.3-{low,high,max}`-க்கும் வெளிப்படையான
`supportsVision:false` registry/spec மெட்டாடேட்டா உள்ளது. GLM 5.3 Flash வேரியன்ட்கள்
நேட்டிவ்-விஷன் மாடல்களாகவே உள்ளன. Claude Code-இன் `/v1/messages` ரூட், Claude-to-OpenAI
டிரான்ஸ்லேஷனுக்கு **முன்** பகிரப்பட்ட `handleChat` pre-call guardrail செயினில்
நுழைகிறது; உள்ளடக்கப்பட்ட `Read` டூல்-ரிசல்ட் இமேஜ்கள், அந்த டிரான்ஸ்லேஷன் அவற்றை
OpenAI `image_url` கண்டென்டாக உயர்த்துவதற்கு முன் விவரிக்கப்பட வேண்டும் அல்லது
கையாளப்பட வேண்டும் (#17069).

**விஷன் அல்லாத மாடல்களை** நோக்கிச் செல்லும் இமேஜ் கொண்ட ரிக்வெஸ்டுகளை இண்டர்செப்ட்
செய்து, முழு ரிக்வெஸ்டையும் விஷன்-ஆதரவு மாடலுக்கு ரீரூட் செய்கிறது அல்லது அப்ஸ்ட்ரீம்
காலுக்கு முன் கான்ஃபிகர் செய்யக்கூடிய விஷன் மாடலால் உருவாக்கப்பட்ட டெக்ஸ்ட் விளக்கங்களால்
இமேஜ் பாகங்களை மாற்றுகிறது. இது டெக்ஸ்ட்-மட்டும் புரொவைடர்கள் மல்டிமோடல் பேலோடுகளை
வெளிப்படையாகக் கையாள அனுமதிக்கிறது.

செயல்முறை ஓட்டம்:

1. டார்கெட் மாடல் ஏற்கனவே விஷனை ஆதரித்தால் தவிர்க்கவும் (அது கட்டாய-பிரிட்ஜ்
   பட்டியலான `isVisionBridgeForcedModel`-இல் தோன்றினால் தவிர).
2. `extractImageParts(messages)` மூலம் இமேஜ் பாகங்களை எடுக்கவும்
   (`visionBridgeHelpers.ts`), இது காம்போ கம்பாட்டிபிலிட்டி ஃபில்ட்டருடன் பகிரப்பட்ட
   ஒரே உண்மையின் மூலமான `open-sse/utils/mediaParts.ts`-இல் உள்ள **ஒருங்கிணைந்த
   மீடியா டிடெக்டர்** `detectMediaParts()`-க்கு டெலிகேட் செய்கிறது. எக்ஸ்டிராக்ஷன்,
   `replaceImageParts` மீண்டும் இணைக்கக்கூடிய வடிவங்களுக்கு மட்டுமே அனுமதிக்கப்பட்டுள்ளது
   (extract↔replace ஒப்பந்தம்): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"`, மற்றும் Responses
   API `input_image`. Claude Code `tool_result.content` மற்றும் Responses டூல்
   அவுட்புட்டுகளுக்குள் உள்ளடக்கப்பட்ட பொருந்தும் இமேஜ்களும் எடுக்கப்பட்டு அவற்றின்
   அசல் பாதைகளில் மாற்றப்படுகின்றன; indicator-மட்டும் வடிவங்கள் காம்போ-ஃபில்ட்டர்
   பொருள் ஆகும், அவை எடுக்கப்படாது. எதுவும் கிடைக்காவிட்டால் தவிர்க்கவும்.
3. `resolveVisionBridgeRuntimeSettings()` மூலம் ரன்டைம் கான்ஃபிகை தீர்க்கவும்
   (`src/shared/constants/modalityBridgeDefaults.ts`): புதிய `modalityBridge*`
   செட்டிங்ஸ் கீகள் வெல்லும்; பழைய (legacy) `visionBridge*` கீகள் **ஒரு-சுழற்சி
   ஃபால்பேக்** ஆக உள்ளன (ரோல்பேக் சாளரம்). பிரிட்ஜ் டிசேபிள் செய்யப்பட்டிருக்கும்போது
   எந்த மீடியா டிராவர்சலுக்கும் முன் தவிர்க்கவும்.
4. மோட் செலக்டர் (`modalityBridgeVisionMode`, கீழே உள்ள அட்டவணையைப் பார்க்கவும்)
   reroute vs describe என்பதைத் தீர்மானிக்கிறது. Reroute, `model` மட்டும்
   மாற்றப்பட்ட `modifiedPayload`-ஐயும், கூடுதலாக meta
   `{ rerouted, fromModel, toModel, imagesKept }`-ஐயும் திருப்புகிறது.
5. Describe பாதை: இமேஜ்களை `maxImages`-இல் கட்டுப்படுத்தவும், டாஸ்க்-அறிந்த ப்ராம்டை
   உருவாக்கவும், describe கேஷைப் பார்க்கவும், விஷன் மாடலை **இணையாக** அழைக்கவும்
   (`Promise.allSettled`), மற்றும் அவற்றின் இடத்தில் `[Image N]: <description>`
   டெக்ஸ்ட் பாகங்களை இன்ஜெக்ட் செய்யவும். தோல்வியுற்ற describe `null`-ஐ தரும்:
   அசல் இமேஜ் அறியப்படாத/விஷன்-ஆதரவு டார்கெட்டுகளுக்காகப் பாதுகாக்கப்படுகிறது (#4012),
   ஆனால் **உறுதிப்படுத்தப்பட்ட டெக்ஸ்ட்-மட்டும் நேரடி டார்கெட்** அல்லது சீரோ-விஷன்
   காம்போ, விவரிக்கப்படாத ஒவ்வொரு இமேஜுக்கும் — பகுதி தோல்விகள் மற்றும் describe-கால்
   வரம்புக்கு அப்பாற்பட்ட இமேஜ்கள் உட்பட — வெளிப்படையான
   `(unavailable — no vision-capable provider connected)` டெக்ஸ்ட் ஸ்டப்-ஐப் பெறுகிறது
   (#17069). தற்போதைய அனைத்தும்-தோல்வியுற்ற காம்போ describe ஃபால்பேக் அப்படியே
   உள்ளது (#8430).
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)-ஐ திருப்பவும்.

| `auto`     | ✔          | பழமையான heuristic, மாற்றப்படாதது (#6640/#7204): non-combo/`auto/` மாதிரிகள் சிறந்த vision மாதிரிக்கு reroute செய்யப்படுகின்றன — அசல் மாதிரியில் ஏற்கனவே பயன்படுத்தக்கூடிய சான்றுகள் இருந்தால் தவிர (அப்போது describe); combo இலக்குகள் எப்போதும் describe செய்கின்றன.                                        |
| `describe` |            | எப்போதும் describe — reroute தொகுதி முழுவதும் தவிர்க்கப்படுகிறது; பயனர் தேர்ந்தெடுத்த மாதிரி எப்போதும் பதிலளிக்கிறது.                                                                                                                                                                                        |
| `reroute`  |            | கட்டாய reroute: சான்றுள்ள-மாதிரியை-தக்கவைக்கும் guard புறக்கணிக்கப்படுகிறது. reroute-**இலக்கு** சான்று guard இன்னும் பொருந்துகிறது — பயன்படுத்தக்கூடிய vision இலக்கு எதுவும் இல்லாதபோது, bridge ஆனது describe செய்வதற்கோ text-only இலக்கிற்கு மூல படங்களை அனுப்புவதற்கோ பதிலாக தெளிவான பிழையுடன் தடுக்கிறது. |

கட்டாய முறைகள் auto heuristic இயங்குவதற்கு **முன்பே** short-circuit செய்கின்றன; `auto` நடத்தை
pre-PR-1 guardrail உடன் byte-அளவில் ஒரே மாதிரியானது.

#### Describe வெளியீட்டு வரம்பு (`modalityBridgeVisionMaxChars`)

(`src/lib/guardrails/visionBridge.ts` இல் உள்ள `VisionBridgeGuardrail.preCall()`).
downstream மாதிரிக்கு முழு நகலெழுத்து தேவைப்படும் விவரம் நிறைந்த OCR
பணிகளுக்கு இதை உயர்த்தவும்; அதிகம் பேசும் vision மாதிரிகளில் token பயன்பாட்டைக்
கட்டுப்படுத்த இதைக் குறைக்கவும். dashboard field ஆனது Vision தாவலின் Advanced
பலகத்தில் உள்ளது (`ModalityBridgeVisionTab.tsx` இல் `modality-bridge-max-chars`),
மேலும் 1 முதல் 99 வரையிலான எந்த மதிப்பையும் 100 கீழ்வரம்பிற்கு உயர்த்துகிறது,
அதே நேரத்தில் வெளிப்படையான `0` ஐத் தொடாமல் விடுகிறது — `0` என்பது தன்னிச்சையாகச்
சரியான Zod மதிப்பு (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`),

#### தொலைநிலைப் பட இயல்பாக்கம் (சுய-சுழற்சி விவரிப்பு/base64 பெறுதல்)

பிரிட்ஜ் ஒரு **தொலைநிலை**ப் படத்தைத் தானாகப் பெறும்போது — Anthropic விவரிப்பு
சுய-அழைப்பு மற்றும் claude-wire-format base64 மாற்றம்
(`ensureBase64ImagesForClaudeWire`) ஆகிய இரண்டும்
`visionBridgeHelpers.ts`-இல் உள்ள `fetchRemoteImageAsDataUri()` வழியாகச் செயல்படுகின்றன — பெறப்படும் தரவு
URI, பார்வை-மாதிரி கோரிக்கையில் உட்பொதிக்கப்படுவதற்கு முன் `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) வழியாக அனுப்பப்படுகிறது. அளவுக்கு மீறிய படங்கள்
**2048px நீளமான விளிம்பாக** குறைக்கப்படுகின்றன (OpenAI/Anthropic ஏற்கெனவே சேவையகப் பக்கத்தில்
பயன்படுத்தும் மறுஅளவிடல் வரம்புடன் பொருந்துமாறு); இதனால் பார்வை மாதிரி காண்பது
மாறாமல் பதிவேற்ற பைட்டுகளும்/தாமதமும் குறைகின்றன. மறுஅளவிடல்
டைனமிக் இறக்குமதி மூலம் ஏற்றப்படும் `sharp`-ஐப் பயன்படுத்துகிறது: அதன் சொந்த
பைனரி ஏற்றப்படத் தவறும் தளத்தில், `normalizeDataUri()` **ஒருபோதும் விதிவிலக்கை எறியாது** — அது
அசல் பைட்டுகளை மாற்றமின்றி அனுப்புவதற்குத் திரும்பிச் செல்கிறது; எனவே விவரிப்பு/base64-மாற்றப்
பாதை எப்போதும் தொடர்ந்து செயல்படும். படம் அல்லாத பைட்டுகளும் (குறியாக்கத்தை நீக்கக்கூடிய
படத்தைத் தராத ஒரு பெறுதல்) எந்த மாற்றமும் இல்லாமல் அனுப்பப்படுகின்றன. இந்த இயல்பாக்கம்,
பிரிட்ஜ் தனது சொந்த சுய-அழைப்புக்காகப் பெறும் படங்களுக்கு மட்டுமே வரையறுக்கப்பட்டுள்ளது — அழைப்பவரின்
மூல மாற்றமில்லா பேலோடில் இது ஒருபோதும் பயன்படுத்தப்படாது; இது
விருப்பத்தேர்வு மூலம் மட்டும் மாற்றம் செய்யும் கொள்கையுடன் (கடுமையான விதி #20) ஒத்துப்போகிறது.

`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
என்பதைக் கொண்டிருக்கும் (`modalityBridge/bridgeStats.ts`-இல் உள்ள `buildModalityBridgeHeader()` மூலம்
உருவாக்கப்பட்டு, `src/sse/handlers/chatHelpers.ts`-இல் உள்ள `withModalityBridgeHeader()` மூலம்
பதிக்கப்படுகிறது). மறுவழிப்படுத்தப்பட்ட கோரிக்கைகளுக்கு **எந்தத்** தலைப்பும் கிடையாது — பேலோடு
மாற்றப்படவில்லை; மேலும் மாதிரி மாற்றம் பதில் உடலின் `model` புலத்தில் ஏற்கெனவே தெரியும்.

`GET /api/modality-bridge/stats` (மேலாண்மை அங்கீகாரம், `GET /api/settings`-இன் அதே நிலை)
`vision`, `audio`, மற்றும் `video` ஆகியவற்றுக்கான நினைவகத்திலுள்ள ஒவ்வொரு ஊடகவகை
எதிரெண்களையும் `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` என்ற வடிவில் வழங்குகிறது.
`averageLatencyMs`, அனைத்து முயற்சிகளையும் அல்லாமல் `latencySamples`-ஐ அதன்
வகுப்பானாகப் பயன்படுத்துகிறது; நேர அளவீடு இல்லாத ஒரு செயல்பாடு, பூஜ்ஜிய-மில்லிவினாடி
மாதிரியைப் புனையாது. வெற்றிகரமான மாற்றங்களுக்கான பின்னோக்கி-இணக்கமான மாற்றுப்பெயராக
`bridged` தொடர்கிறது; தோல்வியுற்ற முயற்சிகள் அதை அதிகரிக்காது.
வடிவமைப்பின்படி, செயல்முறை மறுதொடக்கத்தின்போது எதிரெண்கள் மீட்டமைக்கப்படும்
(இது தொலைஅளவீடு; கணக்குப் பதிவு அல்ல).

#### கட்டுப்பாட்டக உள்ளமைவு

பிரத்யேக கட்டுப்பாட்டகப் பக்கம்
`/dashboard/settings/modality-bridge` ஆகும். URL மூலம் நேரடியாக அணுகக்கூடிய அதன் `Vision`, `Audio`,
மற்றும் `Video` தாவல்கள், `tab` மதிப்பை மாற்றும்போது வினவல் அளவுருக்களைத் தக்கவைக்கின்றன.
Vision தாவல் செயல்படுத்தல், பயன்முறை, மாதிரித் தேர்வு (தானியக்க
இயல்புநிலை உட்பட), பணி-விழிப்புணர்வுள்ள தூண்டுதல், மேம்பட்ட நேரமுடிவு/படம்/விளக்க-நீளம்/தேக்கக
வரம்புகள், இயக்கநேர
எதிரெண்கள் மற்றும் பாதுகாப்புடன் கூடிய மாதிரிக் கோரிக்கையை வழங்குகிறது. Audio தாவலும் செயல்பாட்டில் உள்ளது:
இது செயல்படுத்தல், Auto உடனான STT-மட்டும் மாதிரித் தேர்வி, நேரமுடிவு/அதிகபட்ச-கிளிப் வரம்புகள், ஒலி
எதிரெண்கள் மற்றும் ஓர் `input_audio` மாதிரிச் சோதனையை வழங்குகிறது. Video தாவல் செயல்படக்கூடியது:
இது FFmpeg/ffprobe இயக்கநேர நிலையைத் தெரிவிக்கிறது — நான்கு வெளிப்படையான UI நிலைகளில் ஒன்று
(ஆய்வு நடந்துகொண்டிருக்கும்போது அல்லது அதை முடிக்க முடியாதபோது `unknown`, லூப்பேக் அல்லாத
கட்டுப்பாட்டக ஹோஸ்டில் ஆய்வு கிளையன்ட் பக்கத்தில் தவிர்க்கப்படும்போது `restricted`, ஆய்வு செய்யப்பட்டு
கிடைக்கவில்லை என்பது உறுதிசெய்யப்பட்டதும் `unavailable`, அல்லது FFmpeg/ffprobe பதிப்புகளுடன்
`available`) — செயல்படுத்தல்/மாதிரி/ஃப்ரேம்/வீடியோ/நேரமுடிவு வரம்புகளை நிலைநிறுத்துகிறது, மாதிரித் தேர்வியை
பார்வைத் திறனுள்ள மாதிரிகளுக்கு மட்டும் வடிகட்டுகிறது, மேலும் வீடியோ எதிரெண்களை வழங்குகிறது.

AI அமைப்புகளின் கீழிருந்த முந்தைய Vision Bridge அட்டை, புதிய பக்கத்திற்கான
இணக்கத்தன்மை இணைப்பாகும்; படிவத்தின் இரண்டாவது நகலை இனி அது நிர்வகிக்காது. ஏற்கெனவே உள்ள
Speech-to-Text பயிற்சிக்களத்தை அகற்றாமல், Media Providers பகுதியும் Image-to-Text மற்றும்
Speech-to-Text பணிப்பாய்வுகளைத் தொடர்புடைய Modality Bridge தாவல்களுடன் இணைக்கிறது.

**சுய-சுழற்சி அனுமதி புறக்கணிப்பு:** விவரிப்பு அழைப்பு OmniRoute-இன் சொந்த
`/v1` சுய-சுழற்சி வழியாகச் செல்லும்போது (தரநிலையற்ற வழங்குநர் மாதிரி), துணைக் கோரிக்கை
`x-omniroute-admission-bypass: internal`-ஐ அனுப்புகிறது மற்றும் தீர்மானிக்கப்பட்ட
சுய-சுழற்சி நற்சான்றுடன் அங்கீகரிக்கப்படுகிறது — உள்ளூர் பயன்முறையில் உள்ளூர்
`sk_omniroute` சென்டினல், அல்லது இயக்குநரால் உள்ளமைக்கப்பட்ட `OMNIROUTE_API_KEY` /
`ROUTER_API_KEY` சூழல் விசை (#1350); இதனால் `REQUIRE_API_KEY=true` வரிசைப்படுத்தல்களிலும்
விவரிப்பு அழைப்பை இயக்க முடியும். அந்தச் சரியான நற்சான்றுகளுக்கு மட்டுமே புறக்கணிப்பு
அங்கீகரிக்கப்படும்; எனவே வெளிப்புற கிளையன்ட்கள் அனுமதியைத் தவிர்க்க அந்தத் தலைப்பைப்
பயன்படுத்த முடியாது.

மரபுவழி இயல்புநிலைகள் `src/shared/constants/visionBridgeDefaults.ts`-இல் உள்ளன;
புதிய பயன்முறை/பணி-விழிப்புணர்வு/தேக்கக இயல்புநிலைகளும் அமைப்புகள் தீர்மானிப்பானும்
`src/shared/constants/modalityBridgeDefaults.ts`-இல் உள்ளன. சோதனைகள் போலியான `getSettings` மற்றும்
`callVisionModel` செயலாக்கங்களைச் செலுத்தக்கூடிய வகையில், பாதுகாப்புத் தடுப்பு
`deps` உருவாக்கி விருப்பத்தை வழங்குகிறது.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ஒலி உள்ளீட்டை ஏற்கும் என்று அறியப்படாத இலக்கை அடைவதற்கு முன், ஒலி கொண்ட அரட்டை
கோரிக்கைகளை இடைமறிக்கிறது. இது அரட்டை கோரிக்கையை ஒருபோதும் மறுவழிப்படுத்தாது: ஏற்கெனவே உள்ள
OpenAI-இணக்கமான multipart முனைப்புள்ளி வழியாக ஒலிப் பகுதிகள் உரையாக மாற்றப்படுகின்றன; பின்னர்
தேர்ந்தெடுக்கப்பட்ட அரட்டை மாதிரி உரைப் பிரதிகளுடன் தொடர்கிறது.

செயலோட்டம்:

1. `getResolvedModelCapabilities()` மூலம் `supportsAudio`-ஐத் தீர்மானிக்கவும். வெளிப்படையான
   provider-registry மெட்டாடேட்டா முதலில் வெல்லும், பின்னர் நிலையான மாதிரி மெட்டாடேட்டா,
   பின்னர் ஒத்திசைக்கப்பட்ட `modalities_input`. `audio` இல்லாத அறிவிக்கப்பட்ட உள்ளீட்டு
   பட்டியல் `false` ஆகும்; திறன் ஆதாரம் இல்லையெனில் `null` ஆகவே நிலையும். `false` மற்றும்
   `null` இரண்டும் பாதுகாப்பான பிரிட்ஜைச் செயல்படுத்தும், அதேசமயம் `true` அதைத்
   தவிர்த்துச் செல்லும்.
2. `modalityBridgeAudio*` அமைப்புகளைத் தீர்மானித்து, பகிரப்பட்ட `detectMediaParts()`
   கண்டறிவான் வழியாக ஒவ்வொரு செய்தியிலிருந்தும் splice செய்யக்கூடிய மேல்நிலை ஆடியோ
   பாகங்களை எடுக்கவும். ஆதரிக்கப்படும் wire வடிவங்கள் OpenAI `input_audio`, `audio_url`,
   மற்றும் `source.media_type: "audio/*"` ஆகும். உள்ளடக்க ஆடியோ வழிநிர்ணயத்திற்காகக்
   கண்டறியப்படும், ஆனால் splice பாதையால் அகற்றப்படாது. வேலை
   `modalityBridgeAudioMaxClips` ஆல் வரம்புபடுத்தப்படுகிறது; பின்னர் வரும் பாகங்கள்
   தொடப்படாமல் இருக்கும்.
3. கட்டமைக்கப்பட்ட `provider/model`-ஐ மதிப்பிடவும், அல்லது `selectAudioBridgeModel()`
   நிலையான catalog வரிசையில் `AUDIO_TRANSCRIPTION_PROVIDERS`-ஐக் கடந்து சென்று,
   பயன்படுத்தக்கூடிய செயலில் உள்ள provider சான்று கொண்ட முதல் மாதிரியைத்
   தேர்ந்தெடுக்கட்டும்.
4. `callAudioTranscription()` base64/data-URI ஆடியோவை multipart `file` ஆக மாற்றுகிறது,
   அல்லது DNS pinning மற்றும் 25 MB வரம்புடன் கூடிய பொது-மட்டும் வெளிச்செல்லும் பாதுகாவலன்
   வழியாக தொலை `audio_url`-ஐப் பதிவிறக்குகிறது. பின்னர் அது கோப்பு மற்றும் தேர்ந்தெடுக்கப்பட்ட
   மாதிரியை உள்ளூர் `/v1/audio/transcriptions` self-loop-க்கு POST செய்கிறது,
   `resolveSelfLoopBearer()` மூலம் அங்கீகரிக்கப்பட்டு. இருக்கும் transcription வழி சாதாரண
   சான்று தேடல், cooldown/rate-limit கையாளுதல், மற்றும் provider அனுப்புதல் ஆகியவற்றைச்
   செய்கிறது.
5. வெற்றிகரமான அழைப்புகள் தங்கள் பாகங்களை `[Audio N]: <transcript>` ஆக மாற்றும்.
   அழைப்புகள் `Promise.allSettled` உடன் இயங்கும்: தனிப்பட்ட தோல்வி அந்த அசல் ஆடியோ
   பாகத்தைப் பாதுகாக்கும் (#4012 ஒப்பந்தம்). ஒவ்வொரு அழைப்பும் தோல்வியடைந்து, இலக்கு
   `supportsAudio === false` என நிரூபிக்கப்பட்டால், பாகங்கள்
   `[Audio N]: (unavailable — no STT provider connected)` ஆக மாறும் (#8430 ஒப்பந்தம்).
   அறியப்படாத இலக்கிற்கு (`null`), அனைத்து-தோல்வி முடிவும் தொடப்படாமல் இருக்கும்.
   பயன்படுத்தக்கூடிய STT சான்று இல்லாத, நிரூபிக்கப்பட்ட உரை-மட்டும் இலக்கு நெட்வொர்க்
   அழைப்பு இன்றியே அதே வெளிப்படையான stub-ஐப் பெறும்.

வெற்றிகரமான transcripts செயல்முறை-முழுவதும் பரவிய Modality Bridge LRU/TTL cache-ஐப்
பயன்படுத்துகின்றன. விசை ஆடியோ குறிப்பு, நிலையான `audio-transcription` செயலாக்க
லேபிள், மற்றும் தேர்ந்தெடுக்கப்பட்ட STT மாதிரி ஆகியவற்றை இணைக்கிறது; தோல்விகள்
ஒருபோதும் cache செய்யப்படாது. ஆடியோ முயற்சிகள் பகிரப்பட்ட `bridged`, `cacheHits`,
`failures`, மற்றும் `lastUsedAt` எண்ணிக்கைகளைப் புதுப்பிக்கின்றன. மாற்றப்பட்ட பதில்கள்
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`-ஐச் சுமக்கும்;
தொடப்படாத கோரிக்கைகள் Audio Bridge பிரிவைப் பெறாது.

பிரேம்கள் கட்டமைக்கப்பட்ட Video மாதிரியுடன் தொடர்ச்சியாகத் தலைப்புரையிடப்படுகின்றன. வெற்று Video மேலெழுதல் Vision அமைப்பைப் பெறுகிறது; இரண்டும் வெற்றாக இருந்தால், Vision தன்னியக்க ரூட்டர் செயலில் உள்ள பார்வை-திறன் மாதிரியைத் தேர்ந்தெடுக்கிறது. வெற்றிகரமான தலைப்புரைகள் அசல் பகுதியை நிலையான `[Video description:` முன்னொட்டால் மாற்றுகின்றன; இது உரையை நம்பகமற்ற, ஊடகத்திலிருந்து பெறப்பட்ட கண்காணிப்பாகவும் குறித்து, ஊடகத்தில் காணப்படும் அறிவுரைகளைப் பின்பற்ற வேண்டாம் என்று பின்னோக்கு மாதிரிகளுக்குச் சொல்கிறது. பிரேம்-தலைப்புரை தேக்ககச் சாவிகளில் JPEG பைட்டுகள், ப்ராம்ட், நேரமுத்திரை மற்றும் செயலில் உள்ள மாதிரி ஆகியவை அடங்கும்; வெற்றிகரமான தலைப்புரைகள் மட்டுமே தேக்ககப்படுத்தப்படுகின்றன. தேக்ககப் பதிவுகள் உண்மையான வெற்றிகரமான தயாரிப்பாளர் மாதிரியைத் தக்கவைக்கின்றன — மிச்ச மாதிரி உட்பட; வெவ்வேறு பிரேம்கள் வெவ்வேறு மாதிரிகளால் உருவாக்கப்பட்டிருந்தால், பிரிட்ஜ் `mixed` என்று அறிவிக்கிறது. தேக்கக வெற்றி, அந்தத் தயாரிப்பாளர் அடையாளத்தைக் கோரப்பட்ட ரூட்டிங் திட்டமாக மறுபெயரிடாமல் மீண்டும் பயன்படுத்துகிறது. முழு-வீடியோ முடிவுத் தேக்ககம் வெளியீட்டை மாற்றும் ஒவ்வொரு உள்ளீட்டிலும் சாவியிடப்பட்டுள்ளது — ப்ராம்ட், செயலில் உள்ள மாதிரி, மாதிரியீட்டுக் கொள்கை, பிரேம் எண்ணிக்கை, சொற்பொருள் பகுப்பாய்வு முறை, இயல்பாக்கப்பட்ட கவனம் குறிப்பின் SHA-256 கைரேகை, கவனம் சாளரம், `transcript`, `audioTranscript`, மற்றும் தொடர்பு-தாள் கொடி — எனவே அந்தப் பரிமாணங்களில் ஏதேனும் ஒன்றை மாற்றினால் அது தேக்ககத் தவறு, ஒருபோதும் பழைய மறுபயன்பாடு அல்ல. காட்சி நகல்-நீக்கக் கொள்கை பதிப்பு, வாயில் மதிப்பு மற்றும் வரம்புக்குட்பட்ட வேட்பாளர்-பிரேம் எண்ணிக்கை ஆகியவையும் முடிவு-தேக்ககச் சாவி மற்றும் மெட்டாடேட்டாவில் வெளிப்படையாக உள்ளன; எனவே கொள்கை மாற்றம் பழைய முழு-வீடியோ விளக்கத்தை மீண்டும் பயன்படுத்த முடியாது. முடிவு-தேக்கக v4 மெட்டாடேட்டா முறை மற்றும் கைரேகையை மட்டுமே வைத்திருக்கிறது, மூல பயனர் பணியை ஒருபோதும் அல்ல. காவலர் மெட்டாடேட்டா கோரப்பட்ட மற்றும் செயலில் உள்ள பகுப்பாய்வு முறைகள் இரண்டையும் அறிவிக்கிறது; பயன்படுத்தக்கூடிய பயனர் உரை இல்லாத கோரப்பட்ட `focused` முறை, செயலில் `full` என அறிவிக்கப்படுகிறது.

காவலர் ஆதரிக்கப்படும் ஒவ்வொரு வீடியோ பகுதியையும் பிரித்தெடுக்கிறது, ஆனால் `modalityBridgeVideoMaxVideos`-ஐ விட அதிகமாக விவரிக்காது. `supportsVideo === false` என நிரூிக்கப்பட்ட இலக்குக்கு, தோல்வியுற்ற மற்றும் வரம்புக்கு மீறிய வீடியோக்கள் வெளிப்படையான பாதுகாப்பான உரைக் குறிப்பான்களாக மாறுகின்றன, இதனால் எந்த மூல வீடியோவும் எஞ்சாது. திறன் தெரியாதபோது, அந்தப் பகுதிகள் தங்கள் வீடியோ கேரியரைத் தக்கவைக்கின்றன; ஏதேனும் மிச்ச டிரான்ஸ்கிரிப்ட் மேலே உள்ள வரம்புக்குட்பட்ட உரை மாற்றத்தைப் பின்பற்றுகிறது. `supportsVideo === true` கொண்ட இலக்குகள் பிரிட்ஜைத் தவிர்த்துச் செல்கின்றன. கிளையன்ட் கோரிக்கை கைவிடல் சமிக்ஞை பதிவிறக்கம், தரகர் வரிசை, துணைச் செயல்முறைகள் மற்றும் தலைப்புரை அழைப்புகள் வழியாகப் பரவுகிறது; கைவிடல்கள் வீடியோக்களுக்கு இடையில் நிறுத்தப்படுகின்றன, ஒருபோதும் மூல ஊடகத்திற்குத் திறந்த தோல்வியாக மாறாது.

`GET /api/modality-bridge/video/runtime` அங்கீகரிப்பு அல்லது இயக்கக ஆய்வுக்கு முன் நம்பகமான முத்திரையிடப்பட்ட loopback இடத்தைத் தேவைப்படுத்துகிறது, பின்னர் நிர்வாக அங்கீகரிப்பைத் தேவைப்படுத்துகிறது. இது `available`, சுத்தம் செய்யப்பட்ட FFmpeg/ffprobe பதிப்புகள், மற்றும் இயக்ககம் கிடைக்காதபோது ஒரு நிலையான காரணத்தை மட்டுமே தருகிறது. உள் பிரித்தெடுப்பு முனைப்புள்ளி ஒரு பொது பதிவேற்ற API அல்ல: வரிசை நிரம்பல் `503` மற்றும் `Retry-After`-ஐத் தருகிறது, அழைப்பாளர் துண்டிப்பு `499`-ஐத் தருகிறது, மற்றும் நிலையான தரகர் காலக்கெடு `504`-ஐத் தருகிறது. மாற்றப்பட்ட பதில்கள் மத்திய `x-omniroute-modality-bridge` தலைப்புப் பகுதியில் `video->text;model=<visionModel>;parts=<videos>`-ஐச் சேர்க்கின்றன, Vision அல்லது Audio பகுதிகளை நீக்காமல்.

### PII மறைப்பான் (`piiMasker.ts`)

**இரண்டு** நிலைகளிலும் இயங்குகிறது.

- **`preCall`** பேலோடை நகலெடுத்து, `system`, `messages`, `input`, மற்றும்
  `prompt` (எளிய சரம் உருப்படிகள் உட்பட) ஆகியவற்றைத் தாண்டிச் சென்று, சரம்
  `content`/`text` புலங்களில் `processPII()` ஐ
  (`@/shared/utils/inputSanitizer`-இலிருந்து) பயன்படுத்துகிறது.
  `PII_REDACTION_ENABLED=true` ஆக இருக்கும்போது, கண்டறியப்பட்ட PII வெளிச்செல்லும்
  பேலோடில் மறைக்கப்படுகிறது. இது `INPUT_SANITIZER_MODE`-இலிருந்து சுயாதீனமானது
  (அது prompt-injection கொள்கையை மட்டுமே கட்டுப்படுத்துகிறது). மறைத்தல்
  அணைக்கப்பட்டிருக்கும்போது, அழைப்பு உள்ளடக்கத்தை மீளெழுதாமல் கண்டறிதல்
  எண்ணிக்கைகளை மட்டும் பதிவு செய்கிறது.
- **`postCall`** பதிலை ஆழமாக நகலெடுத்து, `sanitizePIIResponse()` ஐயும்
  Responses-API-வடிவ மாஸ்கரையும் (`maskResponsesOutput` — `output_text`
  மற்றும் `output[].content[].text` ஆகியவற்றை உள்ளடக்கியது) இயக்குகிறது.
  ஏதேனும் மறைத்தல் நிகழ்ந்தால், மாற்றப்பட்ட பதில் அசல் பதிலை மாற்றுகிறது.

கார்ட்ரெயில் ஒருபோதும் தடுக்காது; அது குறிப்பிடுதல் (`meta.detections`,
`meta.redacted`) அல்லது மீளெழுதல் மட்டுமே செய்கிறது.

#### வகை வாரியான தேர்வு, தனிப்பயன் முறைங்கள் மற்றும் கண்டறிதல் எண்ணிக்கைகள்

**டாஷ்போர்டு → அமைப்புகள் → பாதுகாப்பு → PII மறைத்தல்** என்ன மறைக்கப்படுகிறது
என்பதைத் தேர்ந்தெடுக்கிறது. இது மறைத்தலை இயக்காது: அது இன்னும்
`PII_REDACTION_ENABLED` (கோரிக்கை) மற்றும் `PII_RESPONSE_SANITIZATION`
(பதில் + SSE) ஆகியவற்றால் கட்டுப்படுத்தப்படுகிறது, இரண்டும் இயல்பாக
அணைக்கப்பட்டிருக்கும்.

- **வகை வாரியான தேர்வு** — உள்ளமைந்த id-கள்
  `src/shared/constants/piiTypes.ts`-இல் (`PII_BUILTIN_TYPES`) பட்டியலிடப்பட்டுள்ளன.
  அமைக்கப்படாதிருப்பது எல்லா வகைகளையும் குறிக்கிறது (இந்த அமைப்பு இருப்பதற்கு
  முந்தைய நடத்தை). கோரிக்கை இயந்திரத்தின் `ssn_us` முறை `ssn`-க்கு
  வரைபடமாக்கப்படுகிறது. வார்ப்புருக்கள் (Minimal, Standard, Financial,
  Brazilian, USA, Full) UI-இல் தேர்வுப்பெட்டிகளை மட்டுமே நிரப்புகின்றன.
- **தனிப்பயன் முறைங்கள்** — அதிகபட்சம் 20 regex அல்லது wildcard முறைங்கள்
  (`*` = அதிகபட்சம் 64 வெற்றிடமற்ற எழுத்துகள், `?` = ஒன்று). பொருத்தங்கள்
  `[CUSTOM_REDACTED]` ஆக மாறுகின்றன. ஒவ்வொரு முறையும் `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`) வழியாகச் செல்கிறது: அதிகபட்சம் 500
  எழுத்துகள், கொடிகள் `g i m s u`-க்கு மட்டுப்படுத்தப்பட்டவை, தொகுக்கப்பட வேண்டும்,
  `safe-regex`-இல் (பேரழிவு பின்னடைவு) தேர்ச்சி பெற வேண்டும், மேலும் வெற்றுச்
  சரம் அல்லது மறைத்தல் இடம்பிடிப்புடன் பொருந்தக்கூடாது. தோல்வியுறும் முறை
  சேமிக்கும்போதும் சோதிக்கும்போதும் நிராகரிக்கப்படுகிறது, மேலும் தோல்வியுறும்
  சேமிக்கப்பட்ட வரிசை இயக்க நேரத்தில் தொகுக்கப்படாமல் தவிர்க்கப்படுகிறது.
  தனிப்பயன் முறைங்கள் மறைத்தல் இயக்கப்பட்டிருக்கும்போது மட்டுமே இயங்கும்.
- **கண்டறிதல் எண்ணிக்கைகள்** — வகை வாரியான எண்ணிக்கைகள் (பொருந்திய மதிப்புகள்
  ஒருபோதும் இல்லை), நினைவகத்தில் வைத்திருக்கப்பட்டு மறுதொடக்கத்தில்
  மீட்டமைக்கப்படுகின்றன (`src/lib/pii/piiDetectionStats.ts`). மறைத்தல்
  இயக்கப்பட்டிருக்கும்போது மட்டுமே அவை அதிகரிக்கும்.

அமைப்புகள் `key_value` அட்டவணையில் (பெயர்வெளி `pii_settings`,
`src/lib/db/piiSettings.ts`) உள்ளன, மேலும் 1 நொடி தற்காலிக சேமிப்பு வழியாகப்
படிக்கப்படுகின்றன. API:

| முறை   | பாதை                     | நோக்கம்                                                                              |
| ------ | ------------------------ | ------------------------------------------------------------------------------------ |
| `GET`  | `/api/settings/pii`      | கொடி நிலை, `enabledTypes`, `customPatterns`, கண்டறிதல் எண்ணிக்கைகள்                  |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = அனைத்தும்) மற்றும்/அல்லது `customPatterns` ஐ மாற்றுதல்      |
| `POST` | `/api/settings/pii/test` | அதிகபட்சம் 8 KB மாதிரியின் மீது ஒரு முறையை முன்சோதனை செய்தல்; எதுவும் சேமிக்கப்படாது |

மூன்றுக்கும் நிர்வாக அங்கீகாரம் தேவை, மேலும் அவை உடலை Zod மூலம்
சரிபார்க்கின்றன (`src/shared/validation/schemas/piiSettings.ts`).

### ப்ராம்ட் இன்ஜெக்ஷன் (`promptInjection.ts`)

பயனர் வழங்கிய உள்ளடக்கத்தில் எதிரணி அமைப்புகளைக் கண்டறிந்து கட்டமைக்கப்பட்ட
கொள்கையை நடைமுறைப்படுத்துகிறது. நடத்தை சூழல் மாறிகள் மற்றும் கன்ஸ்ட்ரக்டர்
விருப்பங்களால் இயக்கப்படுகிறது:

| அமைப்பு       | சூழல் மாறி                                                                                               | இயல்புநிலை | விளைவு                                                                                                                                                                                                                        |
| ------------- | -------------------------------------------------------------------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| இயக்கப்பட்டது | `INPUT_SANITIZER_ENABLED`                                                                                | `true`     | `false` ஆக இருக்கும்போது, கார்ட்ரெயில் குறுக்குவழி செல்கிறது.                                                                                                                                                                 |
| பயன்முறை      | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`     | இன்ஜெக்ஷன் கொள்கை: `block`, `warn`, அல்லது `log`. (`redact` பின்னோக்கு இணக்கத்திற்காக ஏற்றுக்கொள்ளப்படுகிறது, ஆனால் இன்ஜெக்ஷன் உரையை நீக்காது; கோரிக்கை PII மீளெழுதல் `PII_REDACTION_ENABLED` மூலம் கட்டுப்படுத்தப்படுகிறது.) |
| தடுப்பு வாசல் | `blockThreshold` விருப்பம் / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`     | தடுக்கத் தேவையான குறைந்தபட்ச தீவிரம். இயல்புநிலையில் நடுத்தரம் கண்காணிப்பு மட்டுமே.                                                                                                                                           |

**பயன்முறை முன்னுரிமை** (`getMode`): அழைப்பாளர் `options.mode` →
`INJECTION_GUARD_MODE` **DB அம்ச-கொடி மேலெழுதல்** (டாஷ்போர்டு → அமைப்புகள் →
அம்சக் கொடிகள்) → `INJECTION_GUARD_MODE` சூழல் மாறி → `INPUT_SANITIZER_MODE`
சூழல் மாறி → `warn`. எனவே டாஷ்போர்டு மேலெழுதல் சூழல் மாறிகளை வெல்கிறது, ஆகவே
Feature Flags UI இயங்கும் கார்டை நேரடியாகக் கட்டுப்படுத்துகிறது (மறுதொடக்கம்
தேவையில்லை). DB வாசிப்பு fail-safe: அது பிழையுற்றால், கார்டு சூழல்-அடிப்படையிலான
நடத்தைக்குத் திரும்புகிறது, மேலும் எந்த மேலெழுதலும் அமைக்கப்படாதபோது நடத்தை
சூழல்-மட்டும் தீர்மானத்திற்கு ஒத்ததாக இருக்கும்.

கண்டறிதல் மூலங்கள்:

1. `@/shared/utils/inputSanitizer`-இலிருந்து `sanitizeRequest()` (குழுவின்
   வேறு இடங்களில் பயன்படுத்தப்படும் பகிரப்பட்ட கண்டறியாளர் தொகுப்பு).
2. உள்ளமைந்த `DEFAULT_GUARD_PATTERNS` (தற்போது `system_override_inline` மற்றும்
   `markdown_system_block`, இரண்டும் `high` தீவிரம்).
3. கன்ஸ்ட்ரக்டர் விருப்பங்கள் வழியாக அனுப்பப்படும் விருப்ப `customPatterns`
   (சரங்கள், regex, அல்லது `{ name, pattern, severity }` பதிவுகள்).

`mode === "block"` ஆக இருக்கும்போது **மற்றும்** குறைந்தது ஒரு கண்டறிதல் தீவிரத்தன்மை வரம்பை எட்டும்போது, `preCall` `{ block: true, message: "Request rejected: suspicious content detected" }` என்பதைத் திருப்பி அனுப்பும். `warn`/`log` முறைகளில் guardrail பதிவு செய்கிறது ஆனால் அழைப்பை அனுமதிக்கிறது. Registry வழியாகச் செல்லாமல் prompt-களை மதிப்பிட வேண்டிய அழைப்பாளர்களுக்காகப் பகிரப்பட்ட துணைநிரல் `evaluatePromptInjection()`-ம் export செய்யப்பட்டுள்ளது.

**ஸ்கேன் வரம்பு (v3.8.20):** கண்டறிவான் இணைக்கப்பட்ட prompt உரையின் **முதல் 16 KB**-ஐ மட்டுமே ஆய்வு செய்கிறது — `src/shared/utils/inputSanitizer.ts`-இல் `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes). `detectInjection()` மற்றும் `evaluatePromptInjection()` இரண்டும் pattern loop-ஐ இயக்குவதற்கு முன் `slice(0, MAX_INJECTION_SCAN_BYTES)` செய்கின்றன. Injection வழிமுறைகள் ஒரு உள்ளீட்டின் மேற்பகுதிக்கு அருகில் இருப்பதால், இது கண்டறிதலைப் பலவீனப்படுத்தாமல் பல நூறு KB payload-களில் regex CPU/GC-ஐ மட்டுப்படுத்துகிறது (cf. #3932, #4041).

### சான்று மறைப்பான் (`credentialMasker.ts`)

**இரண்டு** நிலைகளிலும் இயங்குகிறது, இயல்புநிலைச் சங்கிலியில் கடைசியாக (priority `95`). வெளிச்செல்லும் payload-லிருந்து (செய்தி உள்ளடக்கம், tool-call அளவுருக்கள், tool முடிவுகள்) **மற்றும்** provider பதிலிலிருந்து நன்கு அறியப்பட்ட API-key / secret-token முறைபாடுகளை மறைக்கிறது, இதனால் prompt-இல் ஒட்டப்பட்ட (அல்லது tool முடிவால் எதிரொலிக்கப்பட்ட) சான்று upstream provider-க்கோ அல்லது client-க்குத் திரும்பவோ கசிவதில்லை.

- **Opt-in மட்டுமே**, PII மறைப்பைப் போன்ற அதே மரபு (Hard Rule #20-க்கு அருகாமை): `settings.credentialRedactionEnabled === true` **அல்லது** `CREDENTIAL_REDACTION_ENABLED=true` இல்லாவிட்டால் முடக்கப்பட்டுள்ளது. இது அணைக்கப்பட்டிருக்கும்போது, guardrail ஒரு no-op — இது ஒருபோதும் தடுப்பதில்லை, ஒருபோதும் மீளெழுதுவதில்லை.
- `redactCredentials()` முழு payload/response மரத்தையும் கடந்து செல்கிறது (`walkValue()`, prototype-pollution-safe, `WeakSet` மூலம் cycle-safe) மற்றும் பொருத்தங்களை `[REDACTED:<type>]` placeholder-ஆல் மாற்றுகிறது, உண்மையில் மாறிய கிளைகளை மட்டுமே clone செய்கிறது.
- `CREDENTIAL_PATTERNS` LLM provider விசைகள் (OpenAI, OpenAI-proj, Anthropic, Google, Hugging Face, Replicate), VCS/SaaS token-கள் (GitHub, Slack, Linear, Notion, npm, Postman, Discord), கட்டண விசைகள் (Stripe, Square), cloud விசைகள் (AWS access key, Twilio, SendGrid, Mailgun), தனியார் விசைகள் / JWT-கள், சான்று கொண்ட இணைப்புச் சரங்கள் (`mongodb://user:pass@...` போன்றவை), மற்றும் ஒரு பொதுவான `Authorization`/`x-api-key`/`api-key`/`apikey` header-value முறைபாடு ஆகியவற்றை உள்ளடக்குகிறது. Header வடிவ விசைகள் (`authorization`, `x-api-key`, `api-key`, `apikey`) பொதுவான உரை regex மூலம் அல்லாமல் கட்டமைப்பு ரீதியாக மறைக்கப்படுகின்றன (value மட்டும்; `Bearer `/`Basic ` போன்ற scheme முன்னொட்டு பாதுகாக்கப்படுகிறது).
- Guardrail ஒருபோதும் தடுப்பதில்லை; இது மீளெழுதுதல் (`modifiedPayload` / `modifiedResponse`) மற்றும் குறிப்பு சேர்த்தல் (`meta.credentialsRedacted`, `meta.count`) மட்டுமே செய்கிறது.

Regression பாதுகாப்பு: `tests/unit/credential-masker-guardrail.test.ts`.

## அடிப்படை ஒப்பந்தம் (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true எனில் சங்கிலி உடனே நிறுத்தப்படும்
  message?: string; // தடுக்கும்போது வெளிக்காட்டப்படும்
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // கோரிக்கையை மீளெழுத preCall திருப்பியனுப்புகிறது
  modifiedResponse?: TValue; // பதிலை மீளெழுத postCall திருப்பியனுப்புகிறது
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ஒரு guardrail `void`, `{}`, அல்லது `{ block: false }` ஆகியவற்றில் ஏதேனும் ஒன்றைத் திருப்பியனுப்புவதன் மூலம் "மாற்றமில்லை" என்பதைக் குறிக்கிறது. `modifiedPayload`/`modifiedResponse` திருப்பியனுப்புவது, downstream guardrail-களுக்குச் சங்கிலி வழியாகப் பாயும் மதிப்பை மாற்றியமைக்கிறது. `signal?: AbortSignal` அழைப்பாளரின் lifecycle-ஐ guardrail-களுக்குள் கொண்டு செல்கிறது. கோரிக்கை abort என்பது வேண்டுமென்றே விதிக்கப்பட்ட fail-open விதிவிலக்கு: media bridge-கள் வேலையை நிறுத்தி, அதை ஆதரிக்காது என அறியப்பட்ட இலக்குக்கு மூல (raw) media-வை மீட்டமைக்காமல் சுத்தம் செய்கின்றன.

## பதிவேடு (`registry.ts`)

`guardrailRegistry` singleton பின்வருவனவற்றை வெளிப்படுத்துகிறது:

- `register(guardrail)` — ஒரு guardrail-ஐச் சேர்க்கிறது (அல்லது இயல்பாக்கப்பட்ட பெயரால் மாற்றுகிறது), மேலும் ஏறுவரிசை `priority`-படி மீண்டும் வரிசைப்படுத்துகிறது.
- `clear()` / `list()` — நிர்வாக உதவிகள்.
- `runPreCallHooks(payload, context)` — செயலிலுள்ள guardrail-கள் வழியே சென்று, payload-ஐ `modifiedPayload` மூலம் தொடர்ச்சியாக அனுப்பி, முதல் `block: true`-இல் நிற்கிறது.
- `runPostCallHooks(response, context)` — response பக்கத்திலும் அதே ஓட்டம்.
- `resetGuardrailsForTests({ registerDefaults })` — நிலையை அழித்து, சுத்தமான test தனிமைக்காக விருப்பமானால் இயல்புநிலைகளை மீண்டும் பதிவு செய்கிறது.

இரு runner-களும் `{ blocked, payload|response, results, guardrail?, message? }` ஐத் திருப்பியனுப்புகின்றன; இங்கு `results` என்பது guardrail தோறும் `blocked`, `skipped`, `modified`, `error`, மற்றும் `meta` புலங்களைக் கொண்ட `GuardrailExecutionResult` பதிவுகளின் array ஆகும் — இது tracing-க்குப் பயனுள்ளதாக உள்ளது.

### ஒவ்வொரு கோரிக்கைக்கும் Guardrail-களை முடக்குதல்

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` தற்போதைய கோரிக்கைக்குத் தவிர்க்கப்பட வேண்டிய guardrail பெயர்களின் நகல்-நீக்கப்பட்ட பட்டியலை ஒன்றுபடுத்துகிறது. ஐந்து வழிகள் (channels) உள்ளன; அவை இந்த வரிசையில் படிக்கப்பட்டு ஒரே பட்டியலில் இணைக்கப்படுகின்றன (நகல் நீக்கும்போது முதன்முதலில் தோன்றியதே நிலைக்கும்):

1. `apiKeyInfo.disabledGuardrails`
2. கோரிக்கை body `disabledGuardrails` (மேல்-நிலை)
3. கோரிக்கை body `metadata.disabledGuardrails` (`metadata` ஒரு object ஆக இருக்கும்போது மட்டுமே)
4. Header `x-omniroute-disabled-guardrails`
5. பழமையான (legacy) header `x-disabled-guardrails`

ஐந்து வழிகளும் — இரண்டு header-களும் உட்பட — இணைக்கப்படுகின்றன: `x-omniroute-disabled-guardrails` மற்றும் `x-disabled-guardrails` இரண்டையும் அனுப்பினால், அவற்றின் பட்டியல்களின் ஒன்றிப்பு தவிர்க்கப்படும்; மேலும் வெற்று நவீன header இனி பழமையானதை மறைக்காது
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412),
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)-இல் சரிசெய்யப்பட்டது).

மதிப்புகள் string-களின் array-களாகவோ அல்லது கமாவால் பிரிக்கப்பட்ட string-ஆகவோ இருக்கலாம்; பெயர்கள் trim செய்யப்பட்டு சிற்றெழுத்து kebab-case-க்கு இயல்பாக்கப்படுகின்றன (`pii_masker` → `pii-masker`), வெற்று உள்ளீடுகள் கைவிடப்படுகின்றன. இதன் விளைவு `context.disabledGuardrails` வழியாக பதிவேட்டிற்கு அனுப்பப்படுகிறது; பதிவேடு பொருந்தும் guardrail-களைத் தவிர்க்கிறது (`results`-இல் `skipped: true`).

முடக்குப் பட்டியல் **பதிவேட்டை** மட்டுமே பாதிக்கிறது. Prompt-injection `block` பயன்முறை ஒரு கட்டாய எல்லை: injection-guard middleware
(`src/middleware/promptInjectionGuard.ts`) எந்த அழைப்பாளர்-கட்டுப்பாட்டு முடக்குப் பட்டியலும் இன்றி `evaluatePromptInjection()`-ஐ அழைக்கிறது (அது முன்பு செய்துவந்த செயலற்ற
`resolveDisabledGuardrails({ body })` அழைப்பு
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)-இல் நீக்கப்பட்டது), எனவே `prompt-injection`-ஐ முடக்கும் கோரிக்கைக்கூட `block` பயன்முறையில் இன்னும் நிராகரிக்கப்படுகிறது. இது வேண்டுமென்றே அப்படி வடிவமைக்கப்பட்டது. முடக்கு வழிகள் அழைப்பாளரின் கட்டுப்பாட்டில் உள்ளன (கோரிக்கை body, metadata, headers); operator அமைத்த பாதுகாப்புக் கட்டுப்பாட்டை அழைப்பாளரால் அணைக்க முடியாதிருக்க வேண்டும்
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).
[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)-இன் header ஒன்றிப்பு எந்த பதிவேட்டு guardrail-கள் தவிர்க்கப்படுகின்றன என்பதை மட்டுமே மாற்றுகிறது; அது client-ஐ middleware-ஐத் தாண்டிச் செல்ல அனுமதிக்காது. key தோறும் மற்றும் group தோறும் கட்டாய guardrail கொள்கைகள் v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417)-இல் கண்காணிக்கப்படுகின்றன.
[கவரேஜ் மற்றும் வரம்புகள்](#coverage-and-limits) ஐப் பார்க்கவும்.

## செயலாக்க வரிசை

`src/sse/handlers/chat.ts` மற்றும்
`open-sse/handlers/chatCore.ts` வழியாகப் பாயும் ஒவ்வொரு கோரிக்கைக்கும்
([உள்ளடக்கம் மற்றும் வரம்புகள்](#உள்ளடக்கம்-மற்றும்-வரம்புகள்) என்ற பிரிவில் பட்டியலிடப்பட்டுள்ள chat-குடும்ப வழித்தடங்கள்):

1. `resolveDisabledGuardrails(...)` API key, body மற்றும் headers ஆகியவற்றிலிருந்து
   தவிர்ப்பு பட்டியலை உருவாக்குகிறது.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` guardrail-களை முன்னுரிமை
   ஏறுவரிசையில் இயக்குகிறது:
   - முடக்கப்பட்ட guardrail-கள் `skipped` என பதிவு செய்யப்படுகின்றன.
   - ஒவ்வொரு guardrail-ன் `preCall`-மும் `modifiedPayload` வழியாக payload-ஐ மாற்றியமைக்கலாம்.
   - முதல் `block: true` சங்கிலியை முன்கூட்டியே நிறுத்துகிறது (short-circuit), handler ஒரு
     guardrail நிராகரிப்பு பதிலை திருப்புகிறது.
3. (மாற்றியமைக்கப்பட்டிருக்கக்கூடிய) payload combo routing மற்றும் upstream
   அனுப்புதலுக்குச் (dispatch) செல்கிறது.
4. **ஸ்ட்ரீமிங் அல்லாதவற்றில் மட்டும்:** பதில் உருவாக்கப்பட்ட பின்,
   `guardrailRegistry.runPostCallHooks(...)` அதே சங்கிலியை பதிலின் மீது
   இயக்குகிறது. இங்கு `block: true` upstream பதிலை கைவிட்டு HTTP 400-ஐ திருப்புகிறது. ஸ்ட்ரீம் செய்யப்பட்ட பதில்கள் இந்த படியை முழுவதுமாக தவிர்க்கின்றன.

பிழையை எறியும் (throw) guardrail-கள் `error: <message>` உடன் பதிவு செய்யப்பட்டு
`logger.warn` வழியாக log செய்யப்படுகின்றன, ஆனால் சங்கிலி தொடர்கிறது — வடிவமைப்பால் fail-open.

`tests/unit/guardrail-pipeline-wiring-characterization.test.ts` மற்றும்

### எது உள்ளடக்கப்படவில்லை

- **மீடியா, embeddings மற்றும் தரவு வழித்தடங்கள்** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) registry-ஐ எப்போதும் அடைவதில்லை. அங்கே
  PII மறைத்தல், சான்று மறைத்தல் (credential masking) அல்லது modality bridge எதுவும்
  இயங்குவதில்லை. அவற்றின் ஒரே சோதனை பழைய injection-guard middleware ஆகும்.
- **ஸ்ட்ரீம் செய்யப்பட்ட பதில்கள்** post-call guardrail-களைப் பெறுவதில்லை: `pii-masker` அல்லது
  `credential-masker` post-call இல்லை, post-call block-மும் இல்லை. ஸ்ட்ரீமிங் PII
  transform மட்டுமே பொருந்தும் (`PII_RESPONSE_SANITIZATION` இயக்கத்தில் இருக்கும்போது). ஸ்ட்ரீம் செய்யப்பட்ட
  பதிலில் திரும்ப எதிரொலிக்கப்படும் சான்று மறைக்கப்படுவதில்லை (redact).
- **முடக்கு வழிகள் vs. middleware (வடிவமைப்பால்):** middleware தனது சொந்த
  `evaluatePromptInjection()` அழைப்புடன் prompt injection-ஐ மதிப்பிடுகிறது,
  அழைப்பாளர் கட்டுப்பாட்டிலுள்ள முடக்கு பட்டியலை எதுவும் அனுப்பாமல். `block` முறை ஒரு
  கட்டாய எல்லை; அழைப்பாளர் கட்டுப்பாட்டிலுள்ள முடக்கங்களால் அதை மீற முடியாது, chat-குடும்ப
  வழித்தடங்களிலும் கூட
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). `prompt-injection`-ஐ முடக்குவது
  registry guardrail-ஐ மட்டுமே தவிர்க்கிறது.

### Post-call-க்கு முன் பதிலை எது பார்க்கிறது

ஸ்ட்ரீமிங் அல்லாத பாதையில் வரிசை: நினைவக பிரித்தெடுப்பு → உள்ளமைந்த கருவி
செயலாக்கம் → post-call guardrail-கள் → post-call block வெளியேற்றம் → semantic-cache சேமிப்பு.

- **நினைவக பிரித்தெடுப்பு** மற்றும் **கருவி செயலாக்கம்** ஆகியவை, post-call
  guardrails பதிலை மறுஎழுத அல்லது தடுக்கும் முன் அதனைப் பார்க்கின்றன.
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) முதல்,
  `PII_RESPONSE_SANITIZATION` இயக்கத்தில் இருக்கும்போது (streaming மற்றும்
  non-streaming இரண்டிலும்) நினைவக பிரித்தெடுப்பு, பிரித்தெடுக்கப்பட்ட உரையை
  `sanitizePII` வழியாக இயக்குகிறது; இருப்பினும், post-call பின்னர் தடுக்கும்
  ஒரு பதில் ஏற்கனவே நினைவகம் மற்றும் கருவிகளுக்கு வழங்கப்பட்டுவிட்டது.
- **சொற்பொருள் தற்காலிக சேமிப்பு (semantic cache)** post-call-க்குப் பிறகு
  பதிலைச் சேமிக்கிறது, எனவே அது மறுஎழுதப்பட்ட பதிலையே சேமிக்கிறது; மேலும்
  தடுக்கப்பட்ட பதில் ஒருபோதும் cache-இல் சேமிக்கப்படாது. Cache பதிவுகள்
  ஒவ்வொரு API விசைக்கும் தனித்தனியாக விசையிடப்படுகின்றன.

உள்ளமைந்த கார்ட்ரெயில்களால் படிக்கப்படும் சூழல் மாறிகள்:

| மாறி                                  | பயன்படுத்துவது            | விளைவு                                                                                                  |
| ------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | கண்டறிதலை முழுமையாக முடக்க `false` என அமைக்கவும்.                                                       |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | இன்ஜெக்ஷன் கொள்கை: `warn`, `block`, அல்லது `log`. பழைய மதிப்பான `redact` இன்ஜெக்ஷன் உரையை மீளெழுதாது.   |

## தனிப்பயன் கார்ட்ரெயில்கள்

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

படிகள்:

1. `BaseGuardrail`-ஐ நீட்டிக்கும் `src/lib/guardrails/myGuardrail.ts` ஐ உருவாக்கவும்.
2. `preCall` மற்றும்/அல்லது `postCall` ஐ செயலாக்கவும்.
3. இம்போர்ட் நேரத்தில் பதிவு செய்யவும் (`registerDefaultGuardrails`-இலிருந்து push செய்து) அல்லது
   ரன்டைமில் `guardrailRegistry.register(...)` ஐ அழைக்கவும் — ரெஜிஸ்ட்ரி அதே இயல்பாக்கப்பட்ட
   (normalized) பெயரைக் கொண்ட முந்தைய எந்த கார்ட்ரெயிலையும் மாற்றிவிடும்.
4. `tests/unit/`-இன் கீழ் டெஸ்டுகளைச் சேர்க்கவும் (தற்போதைய எடுத்துக்காட்டுகள்:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## சோதனை

சோதனைகளுக்கு இடையில் அறியப்பட்ட நிலையிலிருந்து தொடங்க `resetGuardrailsForTests()` ஐப் பயன்படுத்தவும்.
வெற்று ரெஜிஸ்ட்ரியுடன் தொடங்கி, சோதனையில் உள்ள கார்ட்ரெயில்களை மட்டும் பதிவு செய்ய
`{ registerDefaults: false }` ஐ அனுப்பவும். Vision Bridge சார்பு செலுத்துதலை

படியெழுத்தல் (transcription) ஆகியவற்றுக்கான சமமான இடைவெளிகளை (seams) வெளிப்படுத்துகிறது.
எனவே சோதனைகள் DB அல்லது நெட்வொர்க் அணுகல் இல்லாமலேயே இரு ஓட்டங்களையும் சோதிக்க முடியும்.

## Injection-guard ரூட் கவரேஜ் & ரெட்-டீம் (Phase 8 · Block D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) பயனர் ப்ராம்ட்டுகளை ஏற்கும்
அனைத்து ரூட்டுகளையும் உள்ளடக்குகிறது. இது `INJECTION_GUARD_MODE` ஐ மதிக்கிறது (இயல்புநிலை `warn` = லாக் மட்டும்;
`block` = HTTP 400 `SECURITY_001` திருப்புகிறது).

| வகை            | ரூட்டுகள்                                                                                                                                            | இயல்புநிலை முறை |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| உரை (தற்போதைய) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn            |
| ஜெனரேட்டிவ்    | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn            |
| தரவு           | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn            |

உரை பிரித்தெடுப்பு (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ஐ உள்ளடக்குகிறது.

**ரெட்-டீம் (இரவுநேர, `nightly-llm-security.yml`):** promptfoo ஒவ்வொரு ரூட்டும்
`INJECTION_GUARD_MODE=block`-இல் OWASP-LLM கார்பஸைத் தடுக்கிறது என்பதைச் சரிபார்க்கிறது; garak
ப்ரோபுகளை இயக்குகிறது (ரகசியம் இல்லையெனில் தவிர்க்கிறது). `moderations` நிலைத்தன்மைக்காகச்
சேர்க்கப்பட்டுள்ளது. Block முறை ஒரு கட்டாய எல்லை: `evaluatePromptInjection()`
மிடில்வேர் அனுப்பும் கோரிக்கை-வாரி முடக்கு பட்டியலைப் புறக்கணிக்கிறது, எனவே `disabledGuardrails`
ஒரு ரூட்டை அதிலிருந்து **விலக்காது** ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

இரவுநேர வொர்க்ஃப்ளோ (`.github/workflows/nightly-llm-security.yml`, cron + கைமுறை
dispatch) இரண்டு ஜாபுகளைக் கொண்டுள்ளது:

- **`promptfoo-guard` (தடுக்கும்)** — `INJECTION_GUARD_MODE=block` உடன்
  `promptfoo eval -c promptfooconfig.yaml` ஐ இயக்குகிறது. ஒவ்வொரு adversarial
  வழக்கும் (எ.கா. "ignore all previous instructions…", DAN-பாணி ஜெயில்பிரேக்குகள்)
  பதிலில் `error.code === "SECURITY_001"` இருப்பதை உறுதிப்படுத்துகிறது, அதாவது
  கார்டு உண்மையில் கோரிக்கையை நிராகரித்தது என்பதை.
- **`garak` (ஆலோசனை)** — உள்ளூர் OmniRoute நிகழ்வுக்கு எதிராக
  (`http://localhost:20128/v1`) garak `--probes promptinject,dan,leakreplay` ஐ இயக்குகிறது.
  வழங்குநர் ரகசியத்தால் (`PROMPTFOO_PROVIDER_KEY`) கட்டுப்படுத்தப்பட்டது; மென்மையாகத்
  தவிர்க்கிறது மற்றும் `|| true` பின்னொட்டுடன் உள்ளது, எனவே CI ஐ தோல்வியடையச்
  செய்யாமல் அறிக்கை செய்கிறது.

கார்டு ஹெல்பரின் கவரேஜ் (`createInjectionGuard` / `withInjectionGuard`)
ப்ராம்ட் சுமக்கும் ஒவ்வொரு `/v1` ரூட்டையும் உள்ளடக்குகிறது; ப்ராம்ட் உரை
`src/shared/utils/inputSanitizer.ts`-இல் உள்ள `extractMessageContents()` மூலம்
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-இலிருந்து எடுக்கப்படுகிறது.
