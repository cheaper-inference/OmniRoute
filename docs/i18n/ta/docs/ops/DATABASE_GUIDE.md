> **சுருக்கமாக**: OmniRoute தனது முதன்மைத் தரவுச் சேமிப்பகமாக **WAL பதிவேட்டுடன் கூடிய SQLite**-ஐப் பயன்படுத்துகிறது; முக்கியமான புலங்களின் சேமிப்பு நிலைப் பாதுகாப்புக்கு **AES-256-GCM** குறியாக்கத்தைப் பயன்படுத்துகிறது. இந்த வழிகாட்டி தரவுத்தளத் திட்டவடிவம், இடம்பெயர்வுகள், காப்புப்பிரதி/மீட்பு மற்றும் செயல்பாட்டு நடைமுறைகளைக் கையாள்கிறது.

**மூலங்கள்:**

- `src/lib/db/core.ts` — singleton + SCHEMA_SQL (17 அடிப்படை அட்டவணைகள்)
- `src/lib/db/migrationRunner.ts` — பதிப்பிடப்பட்ட இடம்பெயர்வுகள்
- `src/lib/db/migrations/` — பதிப்பிடப்பட்ட 167 SQL கோப்புகள்
- `src/lib/db/encryption.ts` — குறியாக்க உதவிச் செயல்பாடுகள்
- `src/lib/db/backup.ts` — காப்புப்பிரதி ஏற்றுமதி/இறக்குமதி
- `src/lib/db/healthCheck.ts` — ஆரோக்கிய நிலைக் கண்டறிதல்

## ஏன் SQLite?

பல காரணங்களுக்காக PostgreSQL/MySQL-ஐ விட SQLite-ஐ OmniRoute தேர்ந்தெடுத்துள்ளது:

| காரணி                  | SQLite                                           | PostgreSQL                                  |
| ---------------------- | ------------------------------------------------ | ------------------------------------------- |
| **நிறுவல்**            | உட்பொதிக்கப்பட்டது — தனி சேவையகம் தேவையில்லை     | சேவையக அமைப்பு தேவை                         |
| **குறியாக்கம்**        | பயன்பாட்டு அடுக்கு (AES-256-GCM)                 | உள்ளமைக்கப்பட்ட TDE                         |
| **செயல்திறன்**         | சிறிய/நடுத்தர பணிச்சுமைகளுக்கு வேகமானது          | மிகப்பெரிய ஒரேநேர எழுத்துகளுக்குச் சிறந்தது |
| **ஒரேநேரச் செயல்பாடு** | WAL பயன்முறை ஒரேநேர வாசிப்புகளை அனுமதிக்கிறது    | முழுமையான MVCC                              |
| **காப்புப்பிரதி**      | ஒற்றைக் கோப்பு நகல்                              | `pg_dump` அல்லது கோப்பு முறைமை நொடிப்படம்   |
| **பயன்பாட்டு நிலை**    | ஒவ்வொரு பயனருக்குமான நிறுவல், உட்பொதிக்கப்பட்டது | பல-குத்தகையாளர் SaaS                        |

**ஒற்றைப் பயனர், ஒற்றை நிகழ்வு** நிறுவல்களுக்கு (OmniRoute-இன் முதன்மைப் பயன்பாட்டு நிலை), SQLite எளிமையாகவும் வேகமாகவும் உள்ளது.

### WAL பதிவேடு

`core.ts`, தரவுத்தளத்தை **WAL (முன்கூட்டிய எழுத்துப் பதிவேடு) பயன்முறையில்** திறக்கிறது:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

எழுதும் செயல்பாடுகளின்போது **ஒரேநேர வாசிப்புகளை** WAL அனுமதிக்கிறது — கோரிக்கைகள் பதிவுசெய்யப்படும் வேளையில் வினவல்களை இயக்கும் முகப்புப் பலகைக்கு இது முக்கியமானது.

இயல்புநிலை தற்காலிகச் சேமிப்பக அளவு **65,536 KiB (64 MiB)** ஆகும். எதிர்மறையான
`cache_size` மதிப்பை KiB-இல் உள்ள தோராயமான உச்ச வரம்பாக SQLite புரிந்துகொண்டு, தேவைக்கேற்ப பக்கங்களை ஒதுக்குகிறது.
**அமைப்புகள் > அமைப்பு & சேமிப்பகம் > தற்காலிகச் சேமிப்பக அளவு** என்பதில் **1 முதல்
1,000,000 KiB** வரையிலான முழு எண் மதிப்புகளை ஏற்கலாம்; அமைப்பைச் சேமிப்பது அதைச் செயலிலுள்ள தரவுத்தள இணைப்பிற்குப் பயன்படுத்தும்,
மேலும் தொடக்கத்தின்போது சேமிக்கப்பட்ட மதிப்பை OmniRoute மீட்டமைக்கும்.

## தரவுத்தள இருப்பிடம்

SQLite கோப்பு இங்கு சேமிக்கப்படுகிறது:

| இயங்குதளம் | பாதை                                                        |
| ---------- | ----------------------------------------------------------- |
| Linux      | `~/.omniroute/storage.sqlite`                               |
| macOS      | `~/.omniroute/storage.sqlite`                               |
| Windows    | `%USERPROFILE%\.omniroute\storage.sqlite`                   |
| Docker     | `/app/data/storage.sqlite` (`DATA_DIR` மூலம் உள்ளமைக்கலாம்) |

துணைக் கோப்புகள்:

- `storage.sqlite-wal` — முன்கூட்டிய எழுத்துப் பதிவு
- `storage.sqlite-shm` — பகிரப்பட்ட நினைவகக் கோப்பு
- `call_logs/` — கோரிக்கை தரவுச் சுமைத் துணைக்கோப்புகள் (இயக்கப்பட்டிருந்தால்)

**இருப்பிடத்தை மாற்றியமைக்க:**

```bash
DATA_DIR=/custom/path omniroute
```

## டொமைன் தொகுதி கட்டமைப்பு

OmniRoute-இன் தரவுத்தளத்தில் `src/lib/db/`-இல் **110 உயர்மட்ட TypeScript தொகுதிகள்** உள்ளன. ஒவ்வொரு டொமைன் தொகுதியும்:

- ஒன்று அல்லது அதற்கு மேற்பட்ட குறிப்பிட்ட அட்டவணைகளுக்குப் பொறுப்பேற்கிறது
- வகையிடப்பட்ட CRUD செயல்பாடுகளை ஏற்றுமதி செய்கிறது
- மற்றொரு தொகுதியின் அட்டவணைகளை ஒருபோதும் அணுகுவதில்லை
- DB-ஐ அணுகுவதற்கு `core.ts`-இலிருந்து `getDbInstance()`-ஐப் பயன்படுத்துகிறது

ஒரு முக்கியக் கட்டமைப்பு விதி: **தொகுதிகள் ஒன்றுக்கொன்று உரிய அட்டவணைகளை நேரடியாக அணுகுவதில்லை**. மற்றொரு தொகுதியின் தரவுடன் செயல்பட, அந்தத் தொகுதியிலிருந்து செயல்பாட்டை இறக்குமதி செய்யவும்.

```ts
// ❌ தவறு: மற்றொரு தொகுதியிலிருந்து நேரடி SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ சரி: providers தொகுதியின் செயல்பாட்டைப் பயன்படுத்தவும்
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

இந்த விதி குறியீட்டு மதிப்பாய்வு மூலம் அமல்படுத்தப்படுகிறது — நிலையான சரிபார்ப்பு எதுவும் இல்லை, ஆனால் மீறல்கள் சுட்டிக்காட்டப்படுகின்றன.

## இடம்பெயர்வுகள்

OmniRoute பயன்படுத்துகிறது** பதிப்பு செய்யப்பட்ட, வலிமையற்ற இடம்பெயர்வுகள்** `src/lib/db/migrations/` இல். ஒவ்வொரு இடமாற்றமும் ஒரு SQL கோப்பு. இரண்டு பெயரிடும் வடிவங்கள் இணைந்துள்ளன; `_omniroute_migrations` இல் பதிவுசெய்யப்பட்ட பதிப்பு எண் முன்னொட்டு ஆகும்.

### இடம்பெயர்தல் பெயரிடுதல்

| வடிவம்                                                | உதாரணம்                              | பயன்படுத்தப்பட்டது                                                                                                                                                    |
| ----------------------------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (சரியாக 3 இலக்கங்கள்)           | `241_seen_models.sql`                | பழைய தொடர் `001`–`241`. நேர முத்திரை வடிவம் தரையிறங்கும்போது உறைந்தது (`240` மற்றும் `241` அதற்கு சற்று முன்பு இணைக்கப்பட்டது): எந்த புதிய கோப்பும் வரிசை எண் பெறாது. |
| `YYYYMMDDHHMMSS_description.sql` (14 இலக்கங்கள், UTC) | `20261113120000_add_usage_index.sql` | 2026-11-13 முதல் உருவாக்கப்பட்ட ஒவ்வொரு இடம்பெயர்வும்.                                                                                                                |

ஏன் மாற்றம்: வரிசை எண்களுடன், இணையான PRs அதே அடுத்த எண்ணைத் தேர்ந்தெடுத்தது மற்றும் ஒன்றிணைக்கும் முன் ஒன்றைத் தவிர மற்ற அனைத்தும் மறுபெயரிட வேண்டும். ஒரு UTC நேர முத்திரை ஒவ்வொரு PR க்கும் அதன் சொந்த பதிப்பை வழங்குகிறது.

நேர முத்திரை வடிவமைப்பிற்கான விதிகள் ( `npm run check:migration-numbering` ஆல் செயல்படுத்தப்பட்டது, `scripts/check/lib/migrationNaming.mjs` இல் ஜெனரேட்டருடன் பகிரப்பட்டது):

- நேர முத்திரை உண்மையான UTC தேதி மற்றும் நேரமாகும், இது `20261113000000` க்கு முந்தையது அல்ல, எதிர்காலத்தில் 10 நிமிடங்களுக்கு மேல் இல்லை.
- விளக்கம் சிறிய எழுத்து `snake_case` என்பது ஒரு எழுத்தில் (`a-z`, `0-9`, ஒற்றை `_` வார்த்தைகளுக்கு இடையே) தொடங்கும், அதிகபட்சம் 80 எழுத்துகள்.
- ஒரே நேர முத்திரையைக் கொண்ட இரண்டு கோப்புகள் நகல் ஆகும்.
- இடைவெளி இல்லாத விதி பழைய தொடருக்கு மட்டுமே பொருந்தும்: `001` முதல் `241` வரையிலான ஒவ்வொரு எண்ணும் இருக்க வேண்டும், தெரிந்த இடைவெளிகளான `026`, `055` மற்றும் `121`. `241` நீக்குவது (அல்லது ஏதேனும் பழைய கோப்பு) கேட் தோல்வியடையும். `001` மற்றும் `241` `KNOWN_GAPS` அனுமதிப்பட்டியலில் ஒருபோதும் சேர்க்க முடியாது. நேரமுத்திரையிடப்பட்ட கோப்புகள் ஒருபோதும் இடைவெளியை உருவாக்காது.
- `src/lib/db/migrations/` இல் உள்ள ஒவ்வொரு நுழைவும் செல்லுபடியாகும் சிறிய `.sql` பெயருடன் வழக்கமான கோப்பாக இருக்க வேண்டும். ஒரு கோப்பகம், ஒரு சிம்லிங்க், ஒரு `.SQL` அல்லது `.sql.bak` கோப்பு, ஒரு மறைக்கப்பட்ட கோப்பு அல்லது இடம் உள்ள பெயர் ஆகியவை நுழைவாயிலில் தோல்வியடைகின்றன, ஏனெனில் ரன்னர் அதை அமைதியாகத் தவிர்த்துவிடுவார் அல்லது துவக்கத்தில் செயலிழப்பார்.

**ஆர்டரை விண்ணப்பிக்கவும்.** ரன்னர் முன்னொட்டின் எண் மதிப்பின்படி வரிசைப்படுத்துகிறார், உரை மூலம் அல்ல: பழைய `001`-`241` கோப்புகள் முதலில், பின்னர் நேரமுத்திரை வரிசையில் நேரமுத்திரையிடப்பட்ட கோப்புகள், பின்னர் `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` இல் பதிவுசெய்யப்பட்ட பெயர்வெளி கோப்பகங்கள் ( `ee-001` போன்ற பதிப்புகள்). நிலுவையில் உள்ள இடம்பெயர்வு என்பது `_omniroute_migrations` இல் இல்லாத எந்தக் கோப்பாகும், எனவே பழைய கிளையிலிருந்து இடம்பெயர்வது புதியதுக்குப் பிறகு ஒன்றிணைவது ஏற்கனவே உள்ள தரவுத்தளங்களில் பொருந்தும்.

**நேரமுத்திரை என்பது உருவாக்கும் வரிசை, ஒன்றிணைக்கும் வரிசை அல்ல.** உங்கள் இடம்பெயர்வு ஒரு அட்டவணை அல்லது நெடுவரிசையில் ஒரு இடம்பெயர்வு மூலம் உருவாக்கப்பட்டால்** புதியது** நேர முத்திரை (உதாரணமாக, முதலில் இணைக்கப்பட்ட மற்றொரு PR இலிருந்து ஒன்று), ஒரு புதிய தரவுத்தளமானது முதலில் உங்களுடையதை இயக்கி தோல்வியடையும். உங்கள் PR இன்னும் திறந்திருக்கும் போது, கோப்பு பெயரை `npm run db:new-migration` உடன் மீண்டும் உருவாக்கவும், அதனால் அது ஒரு புதிய நேர முத்திரையைப் பெறுகிறது அல்லது அதைச் சுதந்திரமாக மாற்றவும். `npm run test:migrations:fresh` ஒவ்வொரு இடம்பெயர்வையும் வெற்று தரவுத்தளத்திற்குப் பயன்படுத்துகிறது மற்றும் இதைப் பிடிக்கிறது.

### இணைக்கப்பட்ட இடம்பெயர்வு ஒருபோதும் நீக்கப்படாது அல்லது மறுபெயரிடப்படாது

ஒரு இடம்பெயர்வு கோப்பு வெளியீட்டு கிளை அல்லது `main` இல் இருந்தால், அது ஏற்கனவே ஹோமோலாக் மற்றும் டெவலப்பர் தரவுத்தளங்கள், VPS நிறுவல்கள் மற்றும் நிறுவன ஒத்திசைவு ஆகியவற்றில் இயங்குகிறது. அதிலிருந்து:

- **அதை ஒருபோதும் நீக்க வேண்டாம்.** மேம்படுத்தப்பட்ட தரவுத்தளங்கள் அதை வைத்திருக்கும் போது புதிய நிறுவல்கள் அதன் திட்டத்தை இழக்கும்.
- **அதை ஒருபோதும் மறுபெயரிட வேண்டாம்.** `_omniroute_migrations` இல் உள்ள பதிப்பு இனி ஒரு கோப்புடன் பொருந்தாது, எனவே ஏற்கனவே பயன்படுத்திய ஒவ்வொரு தரவுத்தளமும் அதை மீண்டும் இயக்கும். Idempotent அல்லாத SQL பின்னர் தரவை நகலெடுக்கிறது அல்லது துவக்கத்தை நிறுத்துகிறது.
- **வேறு திட்டம் வேண்டுமா?** `npm run db:new-migration` உடன் புதிய இடம்பெயர்வை உருவாக்கவும்.

மறுபெயரிடுதல் என்பது இன்னும் ஒன்றிணைக்கப்படாத ஒரு கோப்பிற்கு மட்டுமே பாதுகாப்பானது, இது வாயிலின் குறிப்புகள் குறிப்பிடுகிறது. ஒரு வெளியீட்டு குறிச்சொல் இங்கே எதையும் மாற்றாது: `release/v*` கிளைக்கான ஒவ்வொரு அழுத்தமும் Docker `:next` படத்தை வெளியிடுகிறது மற்றும் ஹோமோலாக், VPS நிறுவல்கள் மற்றும் நிறுவன ஒத்திசைவில் இயங்குகிறது, எனவே எந்த `vX.Y.Z` குறிச்சொல் இருப்பதற்கு முன்பே ஒரு இணைக்கப்பட்ட இடம்பெயர்வு உண்மையான தரவுத்தளங்களில் இயங்கும். குறியிடப்பட்டாலும் இல்லாவிட்டாலும், அடிப்படைக் கோப்பின் ஒவ்வொரு அகற்றுதலிலும் கேட் தோல்வியடைகிறது.

- **இணைக்கப்பட்ட இடம்பெயர்வை மாற்றியமைக்கிறது.** கோப்பை நீக்கும் ஒரு `git revert` வாயில் தோல்வியடைகிறது. கோப்பை வைத்து அதன் திட்டத்தை செயல்தவிர்க்கவும்: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` மற்றும் பல. மேம்படுத்தப்பட்ட மற்றும் புதிய தரவுத்தளங்கள் பின்னர் அதே திட்டத்துடன் முடிவடையும்.
- **ஏற்றுக்கொள்ளப்பட்ட மறுபெயர்: பொருந்தக்கூடிய உள்ளீடு மற்றும் ஒரே மாதிரியான உள்ளடக்கம்.** இணைக்கப்பட்ட கோப்பு நகர்த்த வேண்டும் என்றால் (உதாரணமாக, இணைக்கப்பட்ட இரண்டு கோப்புகள் நேர முத்திரையைப் பகிர்ந்து கொள்கின்றன, மேலும் ரன்னர் பதிப்பு மோதலுடன் நின்று விடுகிறது), அதன் SQL தொடாமல், பிந்தையதை மறுபெயரிடவும் மற்றும் `src/lib/db/migrationRunner/constants.ts` இல் `RENAMED_MIGRATION_COMPATIBILITY` இல் `{ fromVersion, fromName, toVersion, toName }` சேர்க்கவும். பழைய பதிப்பைப் பயன்படுத்திய தரவுத்தளங்கள் கோப்பை மீண்டும் இயக்குவதற்குப் பதிலாக அவற்றின் `_omniroute_migrations` வரிசையை நகர்த்துகின்றன. கேட் அத்தகைய மறுபெயரைப் பற்றி எச்சரிக்கிறது மற்றும் புதிய நேர முத்திரை எதுவாக இருந்தாலும், அதன் மீது எப்போதும் பரிமாற்றச் சரிபார்ப்பை இயக்கும்: புதிய நிறுவல்கள் கோப்பை அதன் புதிய நிலையில் பயன்படுத்துகின்றன, மேம்படுத்தப்பட்ட தரவுத்தளங்கள் அவ்வாறு செய்யாது, எனவே பழைய நேரத்தின் அருகே புதிய நேர முத்திரையைத் தேர்ந்தெடுக்கவும். உள்ளடக்கம் மாற்றப்பட்டால் (புதிய இடமாற்றத்தில் ஒரு திட்ட மாற்றம் தொடரும்) அல்லது நுழைவு இலக்கு கோப்பு வட்டில் இல்லை என்றால் கேட் மறுபெயரிடுவதில் தோல்வியடையும்.
- **ஒரே நேர முத்திரைக்குள் மறுபெயரிட வேண்டாம்.** நேர முத்திரையை வைத்து, விளக்கத்தை மட்டும் மாற்றும் மறுபெயரானது நுழைவு இருந்தோ அல்லது இல்லாமலோ நுழைவாயிலில் தோல்வியடையும். `toVersion` அதன் `fromVersion` க்கு சமமான ஒரு உள்ளீட்டில், ரன்னர் பழைய `_omniroute_migrations` வரிசையை நீக்கி, ஏற்கனவே இயங்கிய ஒவ்வொரு தரவுத்தளத்திலும் கோப்பை மீண்டும் பயன்படுத்துகிறார். நுழைவு இல்லாமல், ரன்னர் பதிப்பை மட்டுமே கண்காணிக்கும்: அது அந்த தரவுத்தளங்களில் உள்ள கோப்பைத் தவிர்க்கிறது (புதிய உள்ளடக்கம் அங்கு இயங்காது) மற்றும் ஒவ்வொரு துவக்கத்திலும் மறுபெயரிடுதல் பிழையை பதிவு செய்கிறது. மற்றொரு நேர முத்திரை மற்றும் பொருந்தக்கூடிய உள்ளீட்டைப் பயன்படுத்தவும் அல்லது பெயரை வைத்திருக்கவும்.
- **மறுபெயரிடப்பட்ட கோப்பு மீண்டும் இயங்கவில்லை என்பதை கேட் சரிபார்க்கிறது.** மூடப்பட்ட ஒவ்வொரு மறுபெயருக்கும், கேட் புதிய கோப்பு பெயரை `--must-not-apply` உடன் பரிமாற்ற சரிபார்ப்பிற்கு அனுப்புகிறது. காசோலை உண்மையான ரன்னர் மூலம் மேம்படுத்தப்பட்ட தரவுத்தளத்தை துவக்குகிறது, மேலும் ரன்னர் அந்த கோப்பை மீண்டும் பயன்படுத்தினால் (உதாரணமாக, நுழைவு தவறான பதிப்பு அல்லது பெயரைக் கொண்டிருப்பதால், அல்லது கேட்டின் உரை பாகுபடுத்தி TypeScript இலிருந்து வித்தியாசமாக `constants.ts` படிப்பதால்), கேட் `migration renomeada rodaria de novo` இல் தோல்வியடைந்து, நுழைவின் பழைய மற்றும் புதிய பதிப்பைச் சரிபார்க்கும்படி கேட்கும்.

### கேட் தளத்திற்கு எதிராக என்ன சரிபார்க்கிறது

இழுக்கும் கோரிக்கை மற்றும் மெர்ஜ்-க்யூ ரன்களில், `npm run check:migration-numbering` `src/lib/db/migrations/` வட்டில் உள்ள அதே கோப்பகத்துடன் அடிப்படை கிளையில் ஒப்பிடுகிறது. அடிப்படையானது, இந்த வரிசையில் உள்ளது: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` மாறி, அல்லது, `GITHUB_EVENT_NAME` `pull_request`, `pull_request_target` அல்லது `merge_group` ஆக இருக்கும் போது, ஒன்றிணைப்பு உறுதிப்பாட்டின் முதல் பெற்றோர், நிகழ்வு பேலோடின் `merge_group.base_sha` அல்லது `git merge-base HEAD origin/$GITHUB_BASE_REF`. இழுக்கக் கோரிக்கை அல்லது ஒன்றிணைப்பு-வரிசையில் எந்தத் தீர்க்கக்கூடிய அடிப்படையும் இல்லாமல் கேட் தோல்வியடைகிறது. `--base` இல்லாமல் CI வெளியே அது `comparação com a base: pulada (sem --base)` அச்சிட்டு இந்த விதிகளைத் தவிர்க்கிறது.

`--base-latest-tag` புதிய வெளியீட்டு குறிச்சொல்லுடன் ஒப்பிடுகிறது (செம்வர் வரிசையில்`vX.Y.Z` ; இரவு நேரங்கள் போன்ற பின்னொட்டு குறிச்சொற்கள் கணக்கிடப்படாது) இது `HEAD` இன் வரலாற்றில் `--base` போன்ற அதே விதிகளுடன் உள்ளது. வெளியீடு-பசுமை (`scripts/quality/validate-release-green.mjs`) இந்த வழியில் நுழைவாயிலை இயக்குகிறது, ஏனெனில் புஷ் மற்றும் திட்டமிடப்பட்ட ரன்களுக்கு இழுப்பு கோரிக்கை அடிப்படை இல்லை மற்றும் ஒரு புதிய CI ரன் இல்லாமல் ஒன்றிணைக்க முடியும். வரலாற்றில் எந்த வெளியீட்டு குறியும் இல்லாமல் கேட் தோல்வியடைகிறது; `git fetch --tags` இயக்கவும் ( CI இல், `actions/checkout` உடன் `fetch-depth: 0` குறிச்சொற்களைக் கொண்டுவருகிறது).

திருத்தப்பட்ட அடிப்படைக் கோப்பிற்கு, அடிப்படை உள்ளடக்கத்தை மீட்டமைத்து, மாற்றத்தை புதிய இடமாற்றத்தில் வைக்கவும்; மறுபெயரிடப்பட்ட கோப்பிற்கு, மறுபெயரைச் செயல்தவிர்க்கவும் அல்லது அது பயணிக்கும் மற்றொரு புதிய நேர முத்திரையைத் தேர்ந்தெடுக்கவும், வேறொரு பெயருடன் ஒரே நேர முத்திரையை ஒருபோதும் பயன்படுத்த வேண்டாம். காசோலையே இயங்க முடியாவிட்டால், கேட் CI இல் தோல்வியடைந்து உள்நாட்டில் மட்டுமே எச்சரிக்கும். திருத்தப்பட்ட அடிப்படைக் கோப்பிற்கு, மேம்படுத்தப்பட்ட தரவுத்தளம் அந்தக் கோப்பின் அடிப்படை உள்ளடக்கத்துடன் கட்டமைக்கப்பட்டுள்ளது, மேலும் அதன் பதிப்பு ஏற்கனவே பதிவு செய்யப்பட்டுள்ளதால் இரண்டாவது துவக்கமானது அதைத் தவிர்க்கிறது. மறுபெயரிடப்பட்ட கோப்பிற்கு, மேம்படுத்தப்பட்ட தரவுத்தளமானது அதன் பழைய பெயரின் கீழ் கோப்புடன் கட்டமைக்கப்பட்டுள்ளது, மேலும் இரண்டாவது துவக்கமானது அதன் `_omniroute_migrations` வரிசையை மீண்டும் இயங்குவதற்குப் பதிலாக பொருந்தக்கூடிய நுழைவு மூலம் நகர்த்துகிறது; கேட் புதிய பெயரை `--must-not-apply` உடன் கடந்து செல்கிறது, எனவே இரண்டாவது பூட் அதைச் செயல்படுத்தினால் காசோலை தோல்வியடையும். மேம்படுத்தப்பட்ட பாதையில் இழுக்க கோரிக்கை இடம்பெயர்வு தோல்வியடைந்தால், அதாவது, ஒவ்வொரு அடிப்படை இடம்பெயர்வுக்குப் பிறகும் (புதிய நிறுவலில் அது தோல்வியுற்றாலும் இல்லாவிட்டாலும்), கேட் `migration do PR não aplica` புகாரளித்து, தளத்தின் தற்போதைய திட்டத்திற்கு எதிராக SQL சரிசெய்யும்படி கேட்கிறது; ### திறந்த PR இன் `NNN` இடம்பெயர்வை மாற்றுகிறது

ஸ்விட்ச்க்கு முன் திறக்கப்பட்ட ஒரு இழுப்புக் கோரிக்கையானது `242_add_widgets.sql` போன்ற தொடர் கோப்புகளைக் கொண்டிருக்கலாம். `241` மேலே உள்ள பழைய எண்கள் நிராகரிக்கப்படுகின்றன, எனவே ஒன்றிணைக்கும் முன் அதை மாற்றவும்:

1. **விளக்கத்தை வைத்து, ஜெனரேட்டர் மூலம் கோப்பை மறுபெயரிடவும்.** புதிய பெயரைப் பெற `npm run db:new-migration -- <same description>` இயக்கவும், SQL ஐ அதில் நகர்த்தவும் மற்றும் பழைய `NNN_` கோப்பை நீக்கவும். விளக்கம் ஒரே மாதிரியாக இருக்க வேண்டும்: கீழே உள்ள பொருந்தக்கூடிய உள்ளீடு அதனுடன் பொருந்துகிறது.
2. **நிலையான தரவுத்தளம் பழைய எண்ணை இயக்கினால், பொருந்தக்கூடிய உள்ளீட்டைச் சேர்க்கவும்.** வைத்திருக்கும் தரவுத்தளமானது (ஹோமோலாக், ஒரு VPS, ஒரு பங்களிப்பாளரின் சொந்த நிறுவல்) `NNN_` கோப்புடன் PR ஐ உருவாக்கினால், `src/lib/db/migrationRunner/constants.ts` இல் `RENAMED_MIGRATION_COMPATIBILITY` க்கு `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` சேர்க்கவும். இது** `237` முதல் `241` வரை தேவை** : அந்த இடங்கள் இப்போது `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` மற்றும் `241_seen_models.sql` ஐ வைத்திருக்கின்றன, மேலும் அத்தகைய தரவுத்தளமானது நுழைவு இல்லாமல் நியமன இடம்பெயர்வை எப்போதும் தவிர்த்துவிட்டு மாற்றப்பட்டதை மீண்டும் இயக்குகிறது. சேருமிடம் நேர முத்திரையாக இருக்கும் போது `242` போன்ற காலியாக இருக்கும் ஸ்லாட்டிற்கும் இது வேலை செய்யும். சந்தேகம் இருந்தால், உள்ளீட்டைச் சேர்க்கவும். நீங்கள் அதை வரிசையில் எங்கு சேர்த்தாலும் பரவாயில்லை: ஒரு நுழைவின் இலக்கு ஸ்லாட் மற்றொரு நுழைவு விலகிச் செல்லும் வரிசையை வைத்திருக்கும் போது (உதாரணமாக `237` ஒரு PR வரிசையை வைத்திருக்கும் போது பழைய `usage_history_calculated_cost` வரிசை `237` க்கு செல்ல காத்திருக்கிறது), ரன்னர் அந்த நுழைவை ஸ்லாட் இலவசம் வரை காத்திருக்க அனுமதிக்கிறது. வரிசை இல்லை நுழைவு நகர்வுகள் அல்லது இடங்களை மாற்றும் இரண்டு உள்ளீடுகள் போன்ற ஒரு உண்மையான மோதல் மட்டுமே `Cannot reconcile ...` உடன் துவக்கத்தை நிறுத்துகிறது.
3. **SQL ஐடியம்போடென்டாக வைத்திருங்கள்** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), ஏனெனில் மாற்றப்பட்ட இடம்பெயர்வு அதன் ஸ்கீமா ஏற்கனவே இருக்கும் தரவுத்தளத்தை சந்திக்கலாம்.
4. **பதிப்பு முக்கிய சிறப்பு வழக்குகளை நகர்த்தவும்.** PR அதன் பழைய எண்ணுக்கு `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) அல்லது `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) இல் ஒரு வழக்கைச் சேர்த்தால், விசையை புதிய நேர முத்திரைக்கு மாற்றவும்.

`tests/unit/db/codex-fence-migration-rename.test.ts` என்பது மறுபெயரிடப்பட்ட இடம்பெயர்வுக்கான சோதனையின் ஒரு சிறந்த எடுத்துக்காட்டு.

### மாறுவதற்கு முன் கிளைகளுக்கு பேக்போர்ட்

`YYYYMMDDHHMMSS_` கோப்பை ஸ்விட்ச்க்கு முந்தைய கிளைக்கு ஒருபோதும் செர்ரி-பிக் அல்லது பேக்போர்ட் செய்ய வேண்டாம் (உதாரணமாக பழைய `release/v*` கிளை). அங்குள்ள ரன்னர் கோப்பு பெயர்களை உரையாக வரிசைப்படுத்துகிறார், எனவே நேர முத்திரையிடப்பட்ட கோப்பு `201_` மற்றும் `202_` க்கு இடையில் புதிய தரவுத்தளத்தில் இயங்கும், மேலும் அங்குள்ள பழைய கேட் 14 இலக்க முன்னொட்டுகளைப் புரிந்து கொள்ளாது. அத்தகைய கிளையில், மாற்றத்தை அந்த கிளையின் சொந்த அடுத்த `NNN_` கோப்பு, idempotent என எழுதவும், எனவே நேர முத்திரை பதிப்பானது பின்னர் வரும்போது அது தடையாக இருக்கும்.

### இடம்பெயர்வுகள் எவ்வாறு இயங்குகின்றன

தொடக்கத்தில், `migrationRunner.ts`:

1. `_omniroute_migrations` அட்டவணை இல்லை என்றால் உருவாக்குகிறது
2. ஏற்கனவே பயன்படுத்தப்பட்ட இடம்பெயர்வுகளுக்கான வினவல்கள்
3. புதிய இடம்பெயர்வுகளை வரிசையாகப் பயன்படுத்துகிறது, ஒவ்வொன்றும் ஒரு பரிவர்த்தனையில்
4. பயன்படுத்தப்பட்ட ஒவ்வொரு இடம்பெயர்வையும் நேர முத்திரையுடன் பதிவு செய்கிறது

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### இயலாமை

இடம்பெயர்வுகள் இருக்க வேண்டும்** முட்டாள்தனமான** — இரண்டு முறை அவற்றை இயக்குவது ஒரு தடையாக இருக்க வேண்டும்:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, மற்றும் `OR IGNORE` / `OR REPLACE` உட்பிரிவுகளை தாராளமாகப் பயன்படுத்தவும்.

### புதிய இடம்பெயர்வைச் சேர்த்தல்

1. **ஜெனரேட்டருடன் கோப்பை உருவாக்கவும்** : `npm run db:new-migration -- <description>` (உதாரணமாக `npm run db:new-migration -- add combo priority`). இது தற்போதைய UTC நேரம் மற்றும் கருத்துத் தலைப்புடன் `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` எழுதுகிறது, அந்த நேரமுத்திரை எடுக்கப்பட்டால் ஒரு நொடி முன்னோக்கி நகர்கிறது, மேலும் ஒரு கோப்பை மேலெழுதுவதில்லை. கையால் எண்ணை எடுக்க வேண்டாம்.
2. **பாதுகாப்பான DDL பயன்படுத்தவும்** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **தரவை கவனமாக நிரப்பவும்** : ஏற்கனவே உள்ள வரிசைகளைக் கையாள `UPDATE ... WHERE ...` பயன்படுத்தவும்
4. **வரிசையையும் பெயரிடலையும் சரிபார்க்கவும்** : `npm run test:migrations:fresh` (வெற்று தரவுத்தளத்தில் உள்ள அனைத்து இடம்பெயர்வுகளும்) மற்றும் `npm run check:migration-numbering`
5. **ஒரு நகலில் சோதிக்கவும்** : உற்பத்தியில் சோதிக்கப்படாத இடம்பெயர்வுகளை ஒருபோதும் இயக்க வேண்டாம்
6. **குறியீட்டிலிருந்து உருவாக்கப்பட்ட அட்டவணைக்கு இடம்பெயர்வு தேவை** : ஒரு தொகுதியானது அட்டவணையை சோம்பேறித்தனமாக உருவாக்கினால் (`CREATE TABLE IF NOT EXISTS`, ஒரு சுய-குணப்படுத்தும் பாதையாக வைக்கப்படுகிறது), ஒரு இடம்பெயர்வு அதை அதே DDL உடன் உருவாக்க வேண்டும். இல்லையெனில், ஒரு சுத்தமான நிறுவல் மற்றும் மேம்படுத்தப்பட்ட நிறுவல் அந்த குறியீடு பாதை இயங்குகிறதா என்பதைப் பொறுத்து வெவ்வேறு திட்டங்களுடன் முடிவடையும். `tests/unit/db/lazy-table-migration-guard.test.ts` `src/` மற்றும் `open-sse/` ஐ ஸ்கேன் செய்கிறது மற்றும் இடம்பெயர்வு இல்லாமல் ஒரு சோம்பேறி `CREATE` இல் தோல்வியடைகிறது (#20557). எடுத்துக்காட்டு: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

எடுத்துக்காட்டு:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **பின்னோக்கி - பொருந்தாத மாற்றங்கள்** (எ.கா., நெடுவரிசைகளை கைவிடுவது) தந்திரமானவை. OmniRoute ஆனது NOT — ஐ தரமிறக்க ஆதரிக்கிறது, ஒருமுறை இடம்பெயர்வு பயன்படுத்தப்பட்டால், திட்ட மாற்றம் நிரந்தரமாக இருக்கும். அதன்படி திட்டமிடுங்கள்.

## சேமிப்பு நிலையில் குறியாக்கம்

முக்கியமான புலங்கள் (API விசைகள், OAuth டோக்கன்கள், இணைப்புச் சரங்கள்) சேமிப்பு நிலையில் **AES-256-GCM** பயன்படுத்திக் குறியாக்கப்படுகின்றன.

### இது எவ்வாறு செயல்படுகிறது

```ts
// src/lib/db/encryption.ts (எளிமைப்படுத்தப்பட்டது)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### இது எங்கு பயன்படுத்தப்படுகிறது

- `provider_connections.api_key` — பயன்பாட்டு மட்டத்தில் குறியாக்கப்பட்டது
- `provider_connections.access_token`, `refresh_token`, `id_token` — பயன்பாட்டு மட்டத்தில் குறியாக்கப்பட்டவை
- `namespace = "secrets"` கொண்ட `key_value` உள்ளீடுகள் — பயன்பாட்டு மட்டத்தில் குறியாக்கப்பட்டவை
- `proxy_registry.auth` — இருந்தால், பயன்பாட்டு மட்டத்தில் குறியாக்கப்பட்டது

### குறியாக்க விசை

குறியாக்க விசை ஒரு **கடவுச்சொற்றொடரிலிருந்தும்** (`STORAGE_ENCRYPTION_KEY` சூழல் மாறி வழியாக அமைக்கப்படுகிறது) ஒரு **salt-இலிருந்தும்** (DB-இல் சேமிக்கப்படுகிறது) பெறப்படுகிறது. தரவைக் குறிவிலக்க இவை இரண்டும் தேவை.

```bash
# பாதுகாப்பான கடவுச்சொற்றொடரை உருவாக்கவும்
openssl rand -hex 32

# .env-இல் அமைக்கவும்
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **மிக முக்கியம்**: குறியாக்க விசையை இழந்தால், குறியாக்கப்பட்ட அனைத்து தரவுகளுக்குமான அணுகலையும் இழக்க நேரிடும். **தரவுத்தளத்திலிருந்து தனியாக விசையைக் காப்புப் பிரதி எடுக்கவும்**.

### குறியாக்கப்படாதவை

செயல்திறன் காரணங்களுக்காக, பின்வருவன எளிய உரையாகச் சேமிக்கப்படுகின்றன:

- வழங்குநரின் காட்சிப் பெயர்கள்
- மாதிரி வரையறைகள் (ஏற்கனவே பொதுவானவை)
- வழிப்படுத்தல் விதிகள்
- பயன்பாட்டுப் பதிவுகள் (PII இல்லை)

## குறியாக்க எச்சரிக்கைகள் (v3.8.16+)

இரண்டு குறியாக்க முறைகளையும் வெளிப்படையாகக் கையாள OmniRoute **`migrateLegacyEncryptedString()`**-ஐப் பயன்படுத்துகிறது:

- **பழைய முறை** (v3.5.0-க்கு முந்தையது): XOR-அடிப்படையிலான "குறியாக்கம்" (உண்மையான குறியாக்கவியல் அல்ல)
- **தற்போதைய முறை**: முறையான IV மற்றும் அங்கீகாரக் குறிச்சொல்லுடன் கூடிய AES-256-GCM

இடம்பெயர்வு உதவிக்கருவி பழைய வடிவமைப்பைக் கண்டறிந்து, முதல் வாசிப்பின்போது புதிய முறையைக் கொண்டு மீண்டும் குறியாக்குகிறது. இதனால் சான்றுகளை இழக்காமல் பழைய தரவுத்தளத்தை மேம்படுத்தலாம்.

## வாசிப்புத் தற்காலிகச் சேமிப்பு

அடிக்கடி வாசிக்கப்படும் தரவுகளுக்கு (மாதிரிகள், வழங்குநர்கள், அமைப்புகள்), `readCache.ts` ஒரு **நினைவகத் தற்காலிகச் சேமிப்பை** வழங்குகிறது:

```ts
// தொடக்கத்தின்போது தற்காலிகச் சேமிப்பில் வைக்கப்பட்டு, எழுதும்போது செல்லாததாக்கப்படும்
const providers = await getCachedProviders(); // வேகமானது, நினைவகத்திலிருந்து
const fresh = await listProviders(); // மெதுவானது, DB-ஐ அணுகும்
```

| தற்காலிகச் சேமிப்பிலுள்ள உருப்படி | தற்காலிகச் சேமிப்புச் சாவி | TTL         |
| --------------------------------- | -------------------------- | ----------- |
| `models`                          | `models:v1`                | எழுதும் வரை |
| `provider_connections`            | `providers:v1`             | எழுதும் வரை |
| `settings`                        | `settings:v1`              | எழுதும் வரை |
| `combos`                          | `combos:v1`                | எழுதும் வரை |

தொடர்புடைய அட்டவணையில் ஒவ்வொரு முறை எழுதும்போதும் தற்காலிகச் சேமிப்பு செல்லாததாக்கப்படும்.

## காப்புப்பிரதி மற்றும் மீட்டெடுப்பு

### கைமுறைக் காப்புப்பிரதி

```bash
# உள்ளூர் காப்புப்பிரதியை உருவாக்க CLI-ஐப் பயன்படுத்தவும்
omniroute backup create --name pre-migration

# அல்லது API வழியாக
curl -X PUT http://localhost:20128/api/db-backups \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

காப்புப்பிரதிக் கோப்பில் பின்வருபவை அடங்கும்:

- அனைத்து DB அட்டவணைகளும் (JSON ஆகத் தொடராக்கப்பட்டவை)
- அழைப்புப் பதிவுக் கலைப்பொருட்கள் (base64-குறியாக்கப்பட்டவை, விருப்பத்திற்குரியவை)
- அமைப்புகள் + இரகசியங்கள் (குறியாக்கப்பட்டவை)
- செருகுநிரல் உள்ளமைவு

### மீட்டெடுப்பு

```bash
# CLI வழியாக
omniroute restore pre-migration

# API வழியாக
curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

> **எச்சரிக்கை**: மீட்டெடுப்பு முழு DB-யையும் மேலெழுதும். முதலில் அனைத்து கிளையன்ட்களையும் நிறுத்தவும்.

### தானியங்குக் காப்புப்பிரதிகள்

```bash
# CLI வழியாகத் தானியங்கு தினசரிக் காப்புப்பிரதிகளை இயக்கவும்
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

ஒவ்வொரு 30 வினாடிகளுக்கும் இயங்கும் (இயல்புநிலை) பின்னணிப் பணியால் அட்டவணை சேவையகப் பக்கத்தில் செயல்படுத்தப்பட்டு, உள்ளூர் சேவையக நேரத்துடன் cron கோவை மதிப்பீடு செய்யப்படுகிறது.

| மாறி                                        | இயல்புநிலை | விளக்கம்                                                                                                                                        |
| ------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`    | ms-இல் இயங்கும் இடைவெளி (குறைந்தபட்சம் `5000`). பொருந்தும் cron நிமிடத்திற்குள் நம்பகமாக இயங்குவதற்கு இது 60 s-ஐ விடக் குறைவாக இருக்க வேண்டும். |

### SQLite இயங்குநிலைக் காப்புப்பிரதி

இயங்கிக்கொண்டிருக்கும் DB-ஐச் சேவை இடைநிறுத்தமின்றி காப்புப்பிரதி எடுக்க:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

இது SQLite-இன் இணையநிலைக் காப்புப்பிரதி API-ஐப் பயன்படுத்துகிறது — OmniRoute இயங்கிக்கொண்டிருக்கும்போது இதை இயக்குவது பாதுகாப்பானது.

## செயல்திறன் ட்யூனிங்

### WAL பயன்முறை

WAL முன்னிருப்பாக இயக்கப்பட்டது. அதிக எழுதும் பணிச்சுமைகளுக்கு, கருத்தில் கொள்ளுங்கள்:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` அமைக்கவில்லை. ஒரு சோதனைச் சாவடி WAL பிரேம்களை பிரதான கோப்பில் நகர்த்துகிறது, ஆனால் WAL கோப்பு அதன் மிகப்பெரிய ஒதுக்கப்பட்ட அளவை வைத்திருக்கிறது. `OMNIROUTE_WAL_GUARD_MAX_MB` காவலர் `wal_checkpoint(RESTART)` மட்டுமே எச்சரித்து இயக்குகிறார்; இது வட்டு அளவு தொப்பி அல்ல.

### குறியீடுகள்

செயல்திறனுக்கான முக்கிய குறியீடுகள் (இடம்பெயர்வுகளால் தானாக உருவாக்கப்பட்டது):

- வழங்குநரால்`idx_models_provider` — மாதிரி தேடல்கள்
- `idx_combo_targets_combo_id` — சேர்க்கை இலக்கு விரிவாக்கம்
- `idx_usage_history_api_key_timestamp` — பயன்பாட்டு பகுப்பாய்வு
- `idx_quota_snapshots_api_key_window` — ஒதுக்கீடு கண்காணிப்பு
- `idx_call_logs_timestamp` — அழைப்பு பதிவு வினவல்கள்

புதிய குறியீட்டைச் சேர்க்க, இடம்பெயர்வை உருவாக்கவும்:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### நினைவகம்-வரைபடப்பட்ட I/O

மிகப் பெரிய தரவுத்தளங்களுக்கு (> 10GB), நினைவக மேப்பிங்கை SQLite ப்ராக்மா மூலம் சரிசெய்யலாம்:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### சுருக்கம்

நீண்ட காலமாக இயங்கும் OmniRoute நிகழ்வுகள் அவ்வப்போது `VACUUM` இலிருந்து பயனடைகின்றன:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

குறைந்த டிராஃபிக் ஜன்னல்களின் போது மாதந்தோறும் இயக்கவும். (WAL பயன்முறை தேவையை குறைக்கிறது, ஆனால் அதை அகற்றாது.)

## ஆரோக்கியச் சரிபார்ப்பு

`src/lib/db/healthCheck.ts` **தரவுத்தள-நிலை ஆரோக்கியக் கண்டறிதல்களை** வழங்குகிறது:

இரண்டு வினைச்சொற்களுக்கும் அங்கீகாரம் தேவை (இல்லையெனில் `401`). `GET` கண்டறிதலை மட்டும் செய்கிறது; `POST`, `autoRepair` இயக்கப்பட்ட நிலையில் அதே சரிபார்ப்பை இயக்குகிறது.

```bash
GET  /api/db/health   # கண்டறிதல்
POST /api/db/health   # கண்டறிதல் + பழுதுபார்த்தல்
```

பதில் என்பது `runDbHealthCheck()` உருவாக்கும் `DbHealthCheckResult`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "இனி இல்லாத API விசைகளை டொமைன் வரவுசெலவுத் திட்டங்கள் மேற்கோள் காட்டின.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| புலம்             | பொருள்                                                                                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | `issues` காலியாக இருக்கும்போது `true`. `driver` இதை ஒருபோதும் பாதிக்காது.                                                                                   |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` ஆகியவற்றில் ஒன்று.                                                          |
| `repairedCount`   | இந்த இயக்கத்தின்போது பழுதுபார்க்கப்பட்ட வரிசைகள்; `autoRepair` false ஆக இருக்கும்போது எப்போதும் `0`.                                                        |
| `backupCreated`   | பழுதுபார்ப்பதற்கு முன் காப்புப்பிரதி எடுக்கப்பட்டதா என்பதைக் குறிக்கிறது.                                                                                   |
| `checkedAt`       | இயக்கமும் அது எழுதும் எந்தவொரு பழுதுபார்ப்புக் குறிப்பும் பகிர்ந்துகொள்ளும் ISO நேரமுத்திரை.                                                                |
| `driver.name`     | சரிபார்க்கப்பட்ட தரவுத்தளத்திற்குச் சேவையளிக்கும் SQLite இயக்கி.                                                                                            |
| `driver.degraded` | எழுதுதல்கள் தரவுத்தளக் கோப்பால் நிலையாகப் பாதுகாக்கப்படாதபோது `true` — `sql.js` WASM மாற்று ஏற்பாடு (முழுக் கோப்புத் தொடர்நிலை) அல்லது நினைவகத் தரவுத்தளம். |

இதே தரவுத் தொகுப்பு `omniroute_db_health_check` MCP கருவியாலும் திருப்பி அனுப்பப்படுகிறது.

சிதைவைக் கண்டறிய `PRAGMA integrity_check`-ஐ இயக்கவும்:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# அச்சிடப்பட வேண்டியது: ok
```

இது `ok` என்பதைத் தவிர வேறு எதையாவது திருப்பி அனுப்பினால், **தரவுத்தளத்தைப் பயன்படுத்துவதை உடனடியாக நிறுத்தி**, காப்புப்பிரதியிலிருந்து மீட்டமைக்கவும்.

## பேரிடர் மீட்பு

### சூழ்நிலை 1: WAL கோப்பு இழப்பு

`-wal` கோப்பு காணவில்லை, ஆனால் `-shm` மற்றும் முதன்மை DB சேதமின்றி உள்ளன:

```bash
# அடுத்த முறை திறக்கும்போது தானாகவே மீட்டெடுக்கப்படும்
omniroute
```

SQLite-ஆல் தானாக மீட்டெடுக்க முடியாவிட்டால்:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### சூழ்நிலை 2: முதன்மை DB கோப்பு சிதைந்துள்ளது

காப்புப்பிரதியிலிருந்து மீட்டெடுக்கவும்:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` என்பது இயங்கிக்கொண்டிருக்கும் சேவையகத்திலிருந்து முழுமையான `.tar.gz` காப்பகத்தை மட்டுமே பதிவிறக்குகிறது
(`GET /api/db-backups/exportAll`, இயக்குநர் நற்சான்று தேவை); இது எதையும் மீட்டமைக்காது.

### சூழ்நிலை 3: குறியாக்க விசை இழப்பு

விசை இல்லாமல் **மீட்டெடுப்பது சாத்தியமில்லை**. குறியாக்கம் செய்யப்பட்ட புலங்களைப் படிக்க முடியாது. புதிய நற்சான்றுகளுடன் அனைத்து வழங்குநர்களையும் கைமுறையாக மீண்டும் சேர்க்கவும்.

> **தணிப்பு**: குறியாக்க விசையை எப்போதும் தனியாகக் காப்புப்பிரதி எடுக்கவும்; கடவுச்சொல் நிர்வாகி அல்லது KMS-இல் சேமிப்பது சிறந்தது.

### சூழ்நிலை 4: வட்டு நிரம்பியுள்ளது

SQLite `SQLITE_FULL` பிழைகளை வழங்கும். வட்டு இடத்தைக் காலி செய்த பிறகு:

```bash
# இடத்தைக் காலி செய்ய WAL சோதனைப்புள்ளியை உருவாக்கவும்
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## பொதுவான செயல்பாடுகள்

### அட்டவணையை ஆய்வு செய்தல்

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### அனைத்து அட்டவணைகளிலும் உள்ள வரிசைகளை எண்ணுதல்

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### எல்லா தரவையும் மீட்டமைத்தல் (அழித்தல்)

```bash
# முதலில் OmniRoute-ஐ நிறுத்தவும்
omniroute stop

# DB கோப்பை நீக்கவும்
rm ~/.omniroute/storage.sqlite*

# மீண்டும் தொடங்கவும் (காலியான DB-ஐ மீண்டும் உருவாக்கும்)
omniroute
```

**தேர்ந்தெடுக்கப்பட்ட** மீட்டமைப்புக்கு (வழங்குநர்களை வைத்துக்கொண்டு, பயன்பாட்டுத் தரவை அழிக்க):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### ஒற்றை அட்டவணையை ஏற்றுமதி செய்தல்

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## சிக்கல் தீர்த்தல்

### "தரவுத்தளம் பூட்டப்பட்டுள்ளது"

மற்றொரு செயல்முறை எழுதுவதற்கான பூட்டைப் பிடித்துள்ளது. பின்வருவனவற்றில் ஒன்றைச் செய்யவும்:

- மற்ற செயல்முறை முடிவடையும் வரை காத்திருக்கவும் (`lsof | grep storage.sqlite` மூலம் சரிபார்க்கவும்)
- மற்ற செயல்முறையை நிறுத்தவும்
- சிக்கல் தொடர்ந்தால், OmniRoute-ஐ மீண்டும் தொடங்கவும்

### "அந்நிய விசைக் கட்டுப்பாடு தோல்வியடைந்தது"

ஒரு டொமைன் தொகுதி, தொடர்புநிலை ஒருமைப்பாட்டை மீறுகிறது. பின்வருவனவற்றைச் சரிபார்க்கவும்:

- சார்பு அட்டவணைகளில் தொடர்பற்ற வரிசைகள்
- பரவாமல் போன தொடர் நீக்கங்கள்
- அந்நிய விசையை மாற்றிய சமீபத்திய இடமாற்றம்

மீறல்களைக் கண்டறிய `PRAGMA foreign_key_check;`-ஐ இயக்கவும்.

### "நினைவகம் போதவில்லை"

SQLite-இன் நினைவக-வரைபட I/O, OS வரம்பை மீறுகிறது. SQLite pragma மூலம் அதைக் குறைக்கவும்:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB-க்கு பதிலாக 128MB
```

அல்லது முடக்கவும்:

```sql
PRAGMA mmap_size = 0;
```

### "இடமாற்றம் இடையில் தோல்வியடைந்தது"

இடமாற்றம் ஒரு பரிவர்த்தனைக்குள் இயங்கியதால், அது மீளமைக்கப்பட்டிருக்க வேண்டும். அவ்வாறு நடக்கவில்லை என்றால்:

1. **OmniRoute-ஐ நிறுத்தவும்** (மேலும் முயற்சிகள் நடைபெறுவதைத் தடுக்க)
2. `sqlite3` மூலம் **DB நிலையைச் சரிபார்க்கவும்**
3. பகுதியளவிலான இடமாற்றத்தை **கைமுறையாகச் சரிசெய்யவும்**
4. OmniRoute-ஐ **மீண்டும் இயக்கவும்** (இடமாற்றம் மீண்டும் முயற்சிக்கப்படும்)

இதைத் தடுக்க, இடமாற்றங்களை எப்போதும் முதலில் ஒரு நகலில் சோதிக்கவும்.
