ஒரு pull request-க்கான மிகச் சிறிய, நம்பகமான development loop-ஐத் தேர்வுசெய்ய இந்த வழிகாட்டியைப் பயன்படுத்தவும். இது கீழே இணைக்கப்பட்டுள்ள
பகுதி சார்ந்த architecture மற்றும் security ஆவணங்களுக்கு மாற்றாகாது; பொதுவான ஒவ்வொரு
மாற்ற வகையையும் அதற்கான contracts, கவனம் செலுத்திய checks மற்றும் CI coverage ஆகியவற்றுடன் இணைக்கிறது.

## ஒவ்வொரு மாற்றமும் பின்பற்றும் பாதை

1. **திருத்துவதற்கு முன் base-ஐத் தேர்வுசெய்யவும்.** செயலில் உள்ள மிக உயர்ந்த `release/v*` branch-ஐக் கண்டறிந்து, அதன்
   tip-இலிருந்து branch உருவாக்கவும். `main`-ஐ அல்ல, அந்த branch-ஐ இலக்காகக் கொள்ளவும். release freeze செயலில் இருந்தால், freeze செய்யப்பட்ட
   branch-ஐ இலக்காகக் கொள்ள வேண்டாம்; [Branching & Release Model](BRANCHING_MODEL.md)-இல்
   விவரிக்கப்பட்டுள்ள அடுத்த செயலில் உள்ள cycle-ஐப் பயன்படுத்தவும்.
2. **Contracts-ஐப் பெயரிடவும்.** மாற்றம் பாதிக்கும் ஒவ்வொரு catalog, schema, உருவாக்கப்பட்ட artifact, public API அல்லது பயனர்
   interface-ஐ அடையாளம் காணவும். கீழே உள்ள அட்டவணை குறைந்தபட்சத் தொடக்கத் தொகுப்பைக் குறிப்பிடுகிறது.
3. **கவனம் செலுத்திய tests-ஐ எழுதவும் அல்லது புதுப்பிக்கவும்.** `src/`, `open-sse/`, `electron/` அல்லது
   `bin/`-இல் செய்யப்படும் production மாற்றங்களுக்கு, அதே PR-இல் ஒரு automated test அவசியம். நடத்தையை நிரூபிக்கும் மிகச் சிறிய test files-ஐ
   முதலில் இயக்கி, பின்னர் பட்டியலிடப்பட்டுள்ள focused gates-ஐ இயக்கவும்.
4. **பரந்த matrix-ஐ CI இயக்கட்டும்.** முழுமையான unit shards, Vitest, coverage ratchet மற்றும்
   production build ஆகியவை PR-இல் இயங்கும். focused failure ஒன்று பரந்த தாக்கத்தைக் காட்டும்போது அல்லது மாற்றம் பல
   subsystems-ஐ உள்ளடக்கும் போது மட்டுமே பரந்த suite ஒன்றை உள்ளூரில் இயக்கவும்.
5. **Review-க்கு முன் ஒத்திசைக்கவும்.** செயலில் உள்ள base-ஐ fetch செய்து, அதன் புதிய commits மற்றும் அதற்கு எதிரான உங்கள் diff-ஐ
   ஆய்வு செய்த பின், contributor workflow-க்கு ஏற்ப base-ஐ rebase அல்லது merge செய்யவும். உருவாக்கப்பட்ட file மற்றும்
   catalog conflicts-ஐ அவற்றின் source-இலிருந்து சரிசெய்து, அவற்றை மீண்டும் உருவாக்கி, focused loop-ஐ மீண்டும் இயக்கி,
   PR இன்னும் செயலில் உள்ள release branch-ஐ இலக்காகக் கொண்டிருப்பதை உறுதிசெய்யவும்.
6. **ஆதாரத்தைப் பதிவுசெய்யவும்.** PR template-இல் இயக்கப்பட்ட commands, சேர்க்கப்பட்ட அல்லது மாற்றப்பட்ட ஒவ்வொரு test file,
   migrations அல்லது feature flags மற்றும் இன்னும் நிலுவையில் உள்ள CI-only validation ஆகியவற்றைப் பட்டியலிடவும்.

## மாற்ற வகை வாரியான Golden paths

கீழே உள்ள commands குறைந்தபட்ச focused checks மட்டுமே; நீங்கள் மாற்றிய நடத்தையை நேரடியாகச் சரிபார்க்கும் test ஒன்றைத்
தவிர்ப்பதற்கான அனுமதி அல்ல.

### Provider

**Contracts**

- `src/shared/constants/providers/`-இல் உள்ள Provider definition மற்றும்
  `src/shared/constants/providers.ts`-இல் அதன் composition.
- `open-sse/config/providerRegistry.ts` அல்லது அதிலிருந்து பிரிக்கப்பட்ட registry files-இல் உள்ள models மற்றும் capabilities.
- பொருந்தும் இடங்களில் executor/translator தேர்வு, OAuth அல்லது API-key configuration, dashboard assets மற்றும் உருவாக்கப்பட்ட
  provider reference.
- Public credentials, `resolvePublicCred()`-ஐப் பயன்படுத்த வேண்டும்; error responses, பகிரப்பட்ட sanitized
  error helpers-ஐப் பயன்படுத்த வேண்டும். `docs/security/PUBLIC_CREDS.md` (git; `/docs`-இல் compile செய்யப்படுவதில்லை) மற்றும்
  [Error Sanitization](../security/ERROR_SANITIZATION.md)-ஐப் பார்க்கவும்.

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog மாறும்போது; உருவாக்கப்பட்ட diff-ஐ commit செய்யவும்
npm run lint
```

பாதிக்கப்பட்ட ஒவ்வொரு request family-யையும் சோதிக்கவும்: chat, Responses, images, embeddings, audio அல்லது video.
உருவாக்கப்பட்ட catalog மற்றும் golden diffs-ஐ contract changes ஆக review செய்யவும்; அவற்றைக் கண்மூடித்தனமாக ஏற்க வேண்டாம்.

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts`-இல் உள்ள public strategy values மற்றும் UI metadata.
- `open-sse/services/combo.ts` மற்றும் `open-sse/services/combo/`-இன் கீழ் உள்ள dispatch மற்றும் ordering.
- Combo schemas, persistence, resilience state, model capabilities மற்றும் API/UI controls.
- நடத்தை மாறும்போது [Auto-Combo Engine](../routing/AUTO-COMBO.md) மற்றும் resilience documentation.

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy அல்லது dispatch மாற்றங்கள்
npm run check:known-symbols      # strategy registration மாற்றங்கள்
npm run lint
```

உள்ளூரில் deterministic mocked-upstream tests-ஐப் பயன்படுத்தவும். Live combo smokes-க்கு credentials தேவைப்படுகின்றன; அவை
manual சோதனைகள், CI-க்கான மாற்றுகள் அல்ல.

### UI / UX

**Contracts**

- `src/app/` மற்றும் `src/shared/components/`-இன் கீழ் உள்ள Next.js route/page மற்றும் shared component boundaries.
- API response shapes, loading/empty/error states, keyboard மற்றும் screen-reader நடத்தை,
  responsive layout, theming மற்றும் locale expansion.
- `src/i18n/messages/en.json`-இல் உள்ள ஆங்கில UI source strings; பயனருக்குத் தெரியும் புதிய உரையை hard-code செய்ய வேண்டாம்.

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction அல்லது visual மாற்றங்களுக்கு app-ஐ இயக்கி, குறுகிய மற்றும் அகலமான viewports இரண்டிலும் சரிபார்க்கவும். CI,
production build மற்றும் பரந்த suites-ஐ இயக்குகிறது; visual நடத்தைக்கு இன்னும் மாற்றத்திற்கு ஏற்ற focused component, Playwright
அல்லது ஆவணப்படுத்தப்பட்ட manual check தேவைப்படுகிறது.

### i18n

**Contracts**

- `src/i18n/messages/en.json` என்பது UI source; `config/i18n.json` என்பது locale source.
- CLI catalogs, `bin/cli/locales/`-இன் கீழ் தனியாக உள்ளன.
- ICU placeholders மற்றும் tags-ஐ அப்படியே பாதுகாக்கவும். product/provider/model பெயர்கள்,
  protocol மற்றும் header பெயர்கள், commands, code/JSON identifiers, URLs, environment variables அல்லது
  `OmniRoute`, `OAuth`, `MCP` மற்றும் `A2A` போன்ற பாதுகாக்கப்பட்ட சொற்களை மொழிபெயர்க்க வேண்டாம். தற்போதைய source list
  `scripts/i18n/glossary/protected-terms.json` ஆகும்.

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI strings/catalogs மாறும்போது
npm run lint
```

இது ஏற்கனவே உள்ள system-க்கான வழிகாட்டுதல்; அதன் tooling அல்லது key model-ஐ விரிவுபடுத்துவதற்கான அழைப்பு அல்ல.
மாற்று system வடிவமைக்கப்பட்டுக் கொண்டிருக்கும் போது i18n patches-ஐத் துல்லியமாகவும் குறுகியதாகவும் வைத்திருக்கவும். task-க்கு உருவாக்கப்பட்ட translations வெளிப்படையாகத் தேவைப்பட்டு,
அதன் விளைவான diff-ஐ நீங்கள் review செய்திருந்தாலன்றி, external services-ஐ அழைக்கும் translation
commands-ஐ இயக்க வேண்டாம்.

### CLI

**Contracts**

- `bin/cli/`-இல் உள்ள பொது கட்டளைகள் மற்றும் கொடிகள், உருவாக்கப்பட்ட API கட்டளைகள், வெளியேற்றக் குறியீடுகள், stdout/stderr மற்றும்
  JSON வெளியீட்டு வடிவங்கள், உள்ளமைவு/சூழல் நடத்தை மற்றும் தொகுக்கப்பட்ட கோப்புகள்.
- CLI-யின் பயனர் எதிர்கொள்ளும் சரங்கள் CLI i18n அடுக்கைப் பயன்படுத்த வேண்டும்; மேலும் `en`/`pt-BR` பட்டியல்கள் ஒரே நிலையில் பராமரிக்கப்பட வேண்டும்.
- ஆதரிக்கப்படும் இயக்கச் சூழலாக Node-ஐயும், வெளியிடப்பட்ட பைனரி ஒப்பந்தத்தையும் பாதுகாக்கவும்.

**கவனம் செலுத்திய சுழற்சி**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # உருவாக்கப்பட்ட/தொகுப்பாக்கப்பட்ட CLI மாற்றங்கள்
npm run check:pack-policy     # தொகுப்பு இடைமுக மாற்றங்கள்
npm run lint
```

நடத்தை பகுப்பாய்வு, கோப்புகள் அல்லது வெளியேற்ற நிலையைச் சார்ந்திருக்கும்போது, சரியான கட்டளையை ஒரு தற்காலிக தரவுக் கோப்பகத்தில் பயன்படுத்தவும். CI விரிவான தொகுப்பு உருவாக்கப்பொருள் மற்றும் சூழலமைப்புச் சோதனைகளைச் செய்கிறது.

### தரவுத்தளம்

**ஒப்பந்தங்கள்**

- `src/lib/db/`-இன் கீழுள்ள களத் தொகுதிகள்; குறிப்பிட்ட தொகுதிகளை நேரடியாக இறக்குமதி செய்யவும் (பழைய `localDb.ts` மறு-ஏற்றுமதி அடுக்கு அகற்றப்பட்டது).
- `src/lib/db/migrations/`-இன் கீழுள்ள எண்ணிடப்பட்ட, மீண்டும் செயல்படுத்தினாலும் ஒரே விளைவைத் தரும் SQL இடம்பெயர்வுகள், பரிவர்த்தனைப் பாதுகாப்பு, மேம்படுத்தல்
  நடத்தை, சுட்டிகள் மற்றும் திட்டவடிவத்தால் பாதிக்கப்படும் ஒவ்வொரு அழைப்பாளரும்.
- வழித்தடங்களும் கையாளிகளும் ஒருபோதும் மூல SQL-ஐ நேரடியாக இயக்கக்கூடாது.

**கவனம் செலுத்திய சுழற்சி**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

இடம்பெயர்வைச் சேர்க்கும்போது, புதிய தரவுத்தளத்தையும் முந்தைய திட்டவடிவத்திலிருந்து செய்யப்படும் மேம்படுத்தலையும் சோதிக்கவும். தரவுத்தளச் சோதனைகள்
கைப்பிடிகளை மூடி, சுத்தப்படுத்தலின்போது `resetDbInstance()`-ஐ அழைக்க வேண்டும். சிறந்த முயற்சி அடிப்படையிலான Bun ஏற்பி பாதை மாறும்போது மட்டுமே `npm run test:bun:db`-ஐ இயக்கவும்; Node தொடர்ந்து அதிகாரப்பூர்வமானதாக இருக்கும்.

### உருவாக்கம் / பயன்பாட்டிற்கு வெளியிடுதல்

**ஒப்பந்தங்கள்**

- மூல மற்றும் பணியிட அறிக்கைகள்/பூட்டுக் கோப்பு, `scripts/build/`, Next.js தனித்தியங்கும் ஒருங்கிணைப்பு, `dist/`
  தொகுப்பு உள்ளடக்கங்கள், Electron தள மெட்டாதரவு, CI பணிப்பாய்வுகள் மற்றும் பயன்பாட்டிற்கு வெளியிடுதல் கண்காணிப்புகள்.
- ஆதரிக்கப்படும் Node வரம்புகளும் `CLAUDE.md`-இல் அனுமதிப் பட்டியலில் சேர்க்கப்பட்டுள்ள Bun பயன்பாடும் மாற்றமின்றி இருக்க வேண்டும்.
- உருவாக்கப்பொருட்கள் கண்காணிக்கப்படாமல் இருக்க வேண்டும்; சார்பு, உரிமம், பணிப்பாய்வு மற்றும் தொகுப்புக் கொள்கைகள் பொருந்தும்.

**கவனம் செலுத்திய சுழற்சி**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # சார்பு அல்லது பூட்டுக் கோப்பு மாற்றங்கள்
npm run check:pack-policy      # வெளியிடப்பட்ட தொகுப்பு இடைமுக மாற்றங்கள்
npm run lint
```

மாற்றம் தொகுத்தல், தனித்தியங்கும் ஒருங்கிணைப்பு, வளங்கள் அல்லது இயக்கநேரத் தொகுப்பாக்கத்தைப் பாதிக்கும்போது மட்டுமே உள்ளூரில் `npm run build`-ஐப் பயன்படுத்தவும். வெளியீடு/பயன்பாட்டிற்கு வெளியிடுதல் சரிபார்ப்புக்கு மட்டுமே `npm run build:release`-ஐப் பயன்படுத்தவும். CI-யின் உருவாக்கமே
இறுதியான பன்முகத் தளச் சமிக்ஞையாகும்; தளம் சார்ந்த Electron மாற்றங்களுக்கு அதற்குப் பொருந்தும் கவனம் செலுத்திய உருவாக்கம் அல்லது புகைச் சோதனைச் சான்று தேவை.

## பகிரப்பட்ட கணினிக்கான டெவலப்பர் ஸ்கிரிப்ட்கள்

பிற அமர்வுகள் செயலில் இருக்கும் devbox-இல் உள்ளூர் சுழற்சியை இரண்டு `scripts/dev/` உதவிக்கருவிகள் செயல்படுத்துகின்றன:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD இலிருந்து கோப்புகள்
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # துல்லியமாக இந்தக் கோப்புகள்
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # தனிமைப்படுத்தப்பட்ட worktree, இணையாகப் பயன்படுத்தப் பாதுகாப்பானது
```

- `typecheck-touched.sh`, 6 GB heap-இன் கீழ் தற்காலிக
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) மூலம் மாற்றப்பட்ட `.ts/.tsx` கோப்புகளுக்கு மட்டும் typecheck செய்கிறது; எனவே, அதிகச் சுமையுள்ள கணினியில் OOM ஆகும் திட்டம் முழுவதற்குமான `tsc -p tsconfig.json`-ஐ இது மாற்றுகிறது.
  மாற்றப்பட்ட கோப்புகளில் உள்ள பிழைகளுடன் ஒரு சுருக்க வரியையும் இது அச்சிடுகிறது; மாற்றப்பட்ட கோப்புகளில் பிழைகள் இருந்தால்
  `1`, பிழைகள் import செய்யப்பட்ட கோப்புகளில் மட்டும் இருந்தால் அல்லது diagnostics இல்லாமல் tsc செயலிழந்தால்
  `2` (`_artifacts/typecheck-touched/`-இன் கீழ் அது குறிப்பிடும் பதிவைப் படிக்கவும்), பிழைகள் இல்லாவிட்டால்
  `0` என்ற வெளியேறும் குறியீட்டை வழங்குகிறது. தற்காலிக tsconfig எப்போதும் அகற்றப்படும்; அதை ஒருபோதும் commit செய்ய வேண்டாம்.
- `new-worktree.sh`, `<git-common-dir>/omniroute-new-worktree.lock`-இல் ஒரே நேரத்தில் நிகழும் இயக்கங்களை வரிசைப்படுத்துகிறது
  (இயல்பாக அதிகபட்சம் 600 s வரை காத்திருக்கும், அதற்கான செய்தி காண்பிக்கப்படும்; இதை மாற்றுவதற்கான வழியை ஸ்கிரிப்டின் தலைப்புப் பகுதி ஆவணப்படுத்துகிறது), மேலும் worktree உருவாவதற்கு முன் `git worktree add` தோல்வியுற்றால்
  அது உருவாக்கிய branch-ஐ மீளமைக்கிறது; எனவே மீண்டும் முயற்சிக்கும்போது கைமுறையாக `git branch -D` இயக்க வேண்டியதில்லை. Hard-link செய்யப்பட்ட `node_modules` மற்றும் `.husky/_` நகல் மாற்றப்படாது.

## உள்ளூர் candidate சுழற்சி

தொகுப்பாக்கப்பட்ட artifact துவங்குகிறது என்பதை source சோதனைகளால் நிரூபிக்க முடியாது: packaging பட்டியல்கள், நீக்கப்பட்ட dependencies,
மற்றும் native binaries ஆகியவை tarball நிறுவப்பட்டுத் தொடங்கப்பட்ட பிறகே தோல்வியடையும். `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) என்பது RFC #8084-இல் உள்ள ஒருமுறை build செய் / சரிபார் / promote செய் செயல்முறையின் உள்ளூர் பகுதியாகும்: இது ஒரு candidate-ஐ build செய்து, அதே artifact-ஐ சரிபார்த்து, directory rename-கள் மூலம் அதை promote செய்து, promote செய்யப்பட்ட slot அதன் health check-இல் தோல்வியுற்றால் அதை rollback செய்கிறது.

```bash
npm run dev:candidate -- run --dry-run --json  # திட்டத்தை அச்சிடு, எதையும் மாற்றாதே
npm run dev:candidate -- run                   # build + validate + promote, தானியங்கி rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ இல் நிறுவு
npm run dev:candidate -- validate --id <id>    # காலியாக உள்ள port-இல் தொடங்கி, /api/health + /v1/models-ஐச் சரிபார்
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current மற்றும் previous-ஐ இடமாற்று
npm run dev:candidate -- run --from-tarball <file.tgz>  # வேறெங்காவது (CI) build செய்யப்பட்ட tarball-ஐ மீண்டும் பயன்படுத்து
```

- **ஒருமுறை build செய்யவும்.** `build`, தற்போதைய tree-ஐ pack செய்கிறது (அதற்கு `dist/server.js` தேவைப்படுவதால், முதலில்
  `npm run build:release`-ஐ இயக்கவும்) அல்லது `--from-tarball`-ஐ நகலெடுக்கிறது; பின்னர் tarball-இல் `node_modules` இல்லாததால், அதைத் தனிமைப்படுத்தப்பட்ட npm prefix-இல் நிறுவுகிறது. id என்பது குறுகிய `HEAD`
  sha (tree-இல் உள்ளூர் மாற்றங்கள் இருந்தால் `-dirty`) அல்லது tarball-க்கான `tgz-<sha256>` ஆகும். ஏற்கனவே build செய்யப்பட்ட clean id மீண்டும் build செய்யப்படுவதற்குப் பதிலாக மறுபயன்பாடு செய்யப்படும்; அதை மீண்டும் build செய்ய `--force`-ஐ வழங்கவும்.
- **Source-ஐ அல்ல, package-ஐச் சரிபார்க்கவும்.** `validate`, நிறுவப்பட்ட CLI-ஐ
  (`serve --port <free port>`) புதிய `DATA_DIR=<candidate>/data`, போலியான secrets ஆகியவற்றுடன் தொடங்குகிறது; மேலும் operator-இன் `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` மற்றும் `INITIAL_PASSWORD` ஆகியவற்றை environment-இலிருந்து அகற்றுகிறது. இதனால், புதிய installation-இன் key இல்லாத loopback நிலைப்பாட்டை இது சரிபார்க்கிறது. இது
  `GET /api/health` 200-ஐத் திருப்பும் வரை காத்திருந்து, `GET /v1/models` 200-ஐத் திருப்ப வேண்டும் எனக் கோருகிறது, process group-ஐ நிறுத்துகிறது,
  மேலும் tarball hash-உடன் முடிவை `validation.json`-இல் பதிவு செய்கிறது.
- **அதே artifact-ஐ promote செய்யவும்.** தற்போதைய tarball hash-க்கான வெற்றிகரமான validation இல்லாத candidate-ஐ `promote` நிராகரிக்கிறது.
  இயல்புநிலை active slot `_artifacts/candidate/current` ஆகும்; `--target <dir>`
  அதே filesystem-இல் மற்றொரு directory-ஐத் தேர்ந்தெடுக்கிறது, மேலும் அதன் previous slot `<dir>.previous` ஆகும்.
  ஒவ்வொரு rename-உம் atomic ஆகும்; செயல்பாட்டின் இடையில் தோல்வி ஏற்பட்டால், ஏற்கனவே செய்யப்பட்ட rename-களை அது பின்னோக்கி மாற்றும்.
- **Rollback செய்யவும்.** `run`, promote செய்யப்பட்ட slot-ஐ மீண்டும் சரிபார்த்து, அந்தச் சரிபார்ப்பு தோல்வியுற்றால்
  `current` மற்றும் `previous`-ஐ மீண்டும் இடமாற்றுகிறது. முதல் validation-இல் தோல்வியுறும் candidate ஒருபோதும் promote செய்யப்படாது.

அனைத்தும் gitignore செய்யப்பட்ட `_artifacts/candidate/`-இன் கீழ் எழுதப்படும்; ஏற்கனவே உள்ள OmniRoute
installation மற்றும் அதன் data directory ஒருபோதும் தொடப்படாது. Promote செய்யப்பட்ட CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ஆகும்; அதைப் பயன்படுத்தும்போது உங்களுடைய `DATA_DIR`-உடன் அதைத் தொடங்கவும்.

| -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| மேலே உள்ள நேரடி நடத்தைச் சோதனைகளும் வகை gates-உம்                                      | பிரிக்கப்பட்ட முழு unit suite மற்றும் தொடர் சோதனைகள்                       |
| `npm run lint`                                                                         | Vitest suites மற்றும் coverage/quality ratchets                            |
| பாதிக்கப்பட்ட contract தேவைப்படும்போது மட்டும் typecheck அல்லது build                  | Production build, security, docs, dependency மற்றும் PR-policy gates       |
| automation மூலம் நடத்தையை நிரூபிக்க முடியாதபோது மட்டும் கைமுறை interaction/live checks | workflow-ஆல் கட்டமைக்கப்பட்ட cross-job integration மற்றும் platform checks |

பச்சை நிலையில் உள்ள கவனக்குவிப்புச் சுழற்சி, மாற்றப்பட்ட contract குறித்த ஆதாரமாகும்; தொடர்பில்லாத CI checks
வெற்றிபெறும் என்பதற்கான நிரூபணம் அல்ல. அதேபோல், ஒவ்வொரு உள்ளூர் திருத்தமும் repository-யின் முழு matrix-க்காகக் காத்திருக்குமாறு செய்ய வேண்டாம்.

## ஒத்திசைவு சரிபார்ப்புப் பட்டியல்

மதிப்பாய்வைக் கோருவதற்கு முன்:

- PR base இன்னும் செயலிலுள்ள உயர்ந்த `release/v*` branch என்பதை உறுதிப்படுத்தவும்.
- அந்த base-ஐ fetch செய்து, நீங்கள் branch உருவாக்கியதிலிருந்து சேர்க்கப்பட்ட commits-ஐ மதிப்பாய்வு செய்யவும்.
- எதிர்பாராத அல்லது உருவாக்கப்பட்ட மாற்றங்களுக்காக `git diff <active-base>...HEAD`-ஐ மதிப்பாய்வு செய்யவும்.
- source-ஐப் புதுப்பித்து output-ஐ மீண்டும் உருவாக்குவதன் மூலம் catalog மற்றும் உருவாக்கப்பட்ட-document conflicts-ஐத் தீர்க்கவும்.
- ஒத்திசைவுக்குப் பிறகு PR விளக்கத்தில் பட்டியலிடப்பட்டுள்ள ஒவ்வொரு கவனக்குவிப்பு test/gate-ஐயும் மீண்டும் இயக்கவும்.
- நகர்த்தப்பட்ட base-உடன் பொருந்துவதற்காக மட்டும் assertions-ஐ ஒருபோதும் பலவீனப்படுத்தவோ, தேவையான tests-ஐ நீக்கவோ வேண்டாம்.
