## npm நம்பகமான வெளியீடு (வி3.8.51 இலிருந்து இயல்புநிலை) — கோரிக்கையின் பேரில், ஃபால்பேக்காக நேரடியாக அமைக்கப்பட்டது

`npm-publish.yml` மூலம் வெளியிடுகிறது** npm நம்பகமான வெளியீடு (OIDC)** முன்னிருப்பாக: `stage-npm` வேலை (github-hosted) GitHub இன் ஐடி-டோக்கனை ஒரு குறுகிய கால — நற்சான்றிதழாக மாற்றுகிறது. அதுதான் பைபாஸ் npm தடைகள் இப்போது 2FA ஐத் தவிர்க்கும் டோக்கன்கள் ஓய்வு பெறுகின்றன; இது WS1.3 உத்தரவாதத்தை வைத்திருக்கும் போது திட்டம் v3.8.48 வரை இருந்த முழு தானியங்கி ஓட்டத்தை மீட்டெடுக்கிறது (கசிந்த டோக்கனை தனியாக வெளியிட முடியாது — டோக்கன் இல்லை).

**ஒரு முறை அமைவு (உரிமையாளர்):** npmjs.com → தொகுப்பு `omniroute` → அமைப்புகள் → _Trusted Publisher_ → GitHub: உரிமையாளர் `diegosouzapw`, repo `OmniRoute`, பணிப்பாய்வு `npm-publish.yml` (சுற்றுச்சூழல்: எதுவுமில்லை). அது இருக்கும் வரை, `ENEEDAUTH` உடன் தானியங்கி படி தோல்வியடையும்: `publish_mode=staged` (கீழே) அல்லது `direct` உடன் மீண்டும் அனுப்பவும்.

### நிலை வெளியீடு (கோரிக்கை — `publish_mode=staged`)

npm-publish பணிப்பாய்வு நேரடியாக வெளியிடாது: இது நிரம்பிய டார்பாலை (`check:pack-boot`) துவக்கி, பின்னர் `npm stage publish` — இயக்குகிறது, பதிவேட்டில் நிறுத்தப்பட்டுள்ள சரியான பைட்டுகள்,** நிறுவ முடியாது** உரிமையாளர் அங்கீகரிக்கும் வரை. மனித 2FA கேட் ஆதாரத்தை AFTER க்கு நகர்த்தியது, அதற்கு முன் அல்ல.

**பணிப்பாய்வு பச்சை நிறமாக மாறிய பிறகு உரிமையாளர் ஓட்டம்:**

1. `npm stage list omniroute` — ஸ்டேஜ் ஐடியைக் கண்டறியவும் (பணிப்பாய்வு சுருக்கத்திலும் அச்சிடப்பட்டுள்ளது).
2. ஸ்டேஜ் செய்யப்பட்ட பைட்டுகளை சரிபார்க்கவும் (பரிந்துரைக்கப்பட்டது): `npm stage download <id>`, பின்னர் பதிவிறக்கம் செய்யப்பட்ட டார்பாலை ஒரு தற்காலிக முன்னொட்டாக நிறுவி அதை துவக்கவும் (`npm run check:pack-boot` அதே பேக்கை→ நிறுவும்→ பூட் தீர்ப்பை CI இல் தானியங்குபடுத்துகிறது).
3. `npm stage approve <id>` — 2FA வரியில் IS வெளியிடவும். `npm stage reject <id>` நிராகரிக்கிறது.
4. பிந்தைய வெளியீட்டு நிகரம்: பிந்தைய வெளியீட்டுச் சரிபார்ப்பு (v3.8.49 திட்டத்தின்WS1.4) வெளியிடப்பட்ட பதிப்பை பொதுப் பதிவேட்டில் இருந்து சுத்தமான கொள்கலனில் நிறுவி அதை துவக்குகிறது.

**அவசர பின்னடைவு:** `publish_mode=direct` உடன் `workflow_dispatch` மரபு உடனடி `npm publish` மீட்டெடுக்கிறது (அரங்கம் தவறாக நடந்து கொண்டால் மட்டுமே பயன்படுத்தவும்; ஏன் என்று பதிவு செய்யவும்).

**ஒரு முறை கடினப்படுத்துதல் (உரிமையாளர், npmjs.com):** `omniroute` க்கு நம்பகமான வெளியீட்டாளரை நிலை-மட்டுமே முறையில் உள்ளமைக்கவும், அதனால் கசிந்த நீண்ட கால டோக்கனை நேரடியாக எங்கிருந்தும் `npm publish` செய்ய முடியாது — CI மட்டுமே மேடையில் முடியும்; உரிமையாளரின் 2FA வெளியீடுகள் மட்டுமே.

**உடைந்த கலைப்புத்தகம் (மாறாமல்):** இயல்புநிலை அனிச்சையாக `npm deprecate omniroute@<bad> "<reason> — use <fixed>"` (நிமிடங்கள், மீளக்கூடியது); `npm unpublish` 72h/no-dependents சாளரத்தின் உள்ளே மட்டுமே மற்றும் முதல் நகர்வாக இல்லை. Docker: பதிப்பு குறிச்சொல்லை மீண்டும் எழுத வேண்டாம் — ரோல்பேக் என்பது `latest` கடைசி நல்ல டைஜெஸ்டுக்கு மீண்டும் சுட்டிக்காட்டுகிறது.

**Docker Hub `latest` (ஒவ்வொரு நிலையான SemVer வெளியீட்டிலும் தேவை):** `docker-publish` பணிப்பாய்வு குறியிட வேண்டும்** இரண்டும்** `X.Y.Z` மற்றும், `should-promote-latest.sh` ஒப்புக்கொண்டால், இது மிக உயர்ந்த நிலையான SemVer ஆகும், `:latest` உடன்** அதே செரிமானம்** . வேலைக்குப் பிறகு: Hub `latest` digest என்பது புதிய SemVer டைஜஸ்ட் மற்றும் `last_updated` நகர்த்தப்பட்டது. `:latest` பழைய கட்டமைப்பில் விடாதீர்கள், வெளியீட்டு குறிப்புகள் ஜிட்டில் மட்டுமே இருக்கும் திருத்தங்களைப் பற்றி பேசுகின்றன. `:latest` பயன்படுத்த விரைவு தொடக்கங்களை எழுதுங்கள்; GitOps `X.Y.Z` ஐப் பின்னிங் செய்ய வேண்டும். [Docker வெளியீட்டு சேனல்கள்](../guides/DOCKER_GUIDE.md#release-channels) மற்றும் #10317 ஐப் பார்க்கவும்.

**Docker Hub அமைப்பு களஞ்சியம் (`cheaperinference/omniroute`):** Docker Hub ஆனது பெயர்வெளிகளுக்கு இடையில் ஒரு களஞ்சியத்தை நகர்த்த முடியாது, எனவே `diegosouzapw/omniroute` அதன் இழுக்கும் வரலாற்றையும் ஒவ்வொரு வெளியீட்டையும் வைத்திருக்கிறது, மேலும் `docker-publish` இன் `mirror-org-dockerhub` வேலை ஒவ்வொரு வெளியிடப்பட்ட பதிப்பையும் (மேலும் `:latest` ஐ மேம்படுத்தும்போது) `ghcr.io/cheaper-inference/omniroute` இலிருந்து நிறுவன களஞ்சியத்திற்கு நகலெடுக்கிறது. இதற்கு `DOCKERHUB_ORG_USERNAME` / `DOCKERHUB_ORG_TOKEN` ரகசியங்கள் தேவை; அவர்கள் இல்லாமல் "Docker Hub org மிரர் ஸ்கிப்ட்" எச்சரிக்கையுடன் வேலை பச்சையாக இருக்கும், மற்ற பதிவுகள் பொதுவாக வெளியிடப்படும். வெளியிடப்பட்ட பதிப்பை பின்னர் வெளியிட, இயக்கவும்** செயல்கள் → மிரர் Docker படத்தை Docker Hub org → க்கு இயக்கு பணிப்பாய்வு** `version=X.Y.Z` உடன் (மற்றும் மிக உயர்ந்த நிலையான பதிப்பிற்கு `promote_latest` ): இது ஏற்கனவே உள்ள படங்களை நகலெடுக்கிறது, மறுகட்டமைப்பு இல்லை.

## ஹாட்ஃபிக்ஸ் விரைவுப் பாதை (`hotfix` லேபிள்)

`hotfix` என லேபிளிடப்பட்ட PR, கனமான CI மேட்ரிக்ஸை (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) தவிர்த்து, விரைவான, அதிகத் தெளிவான கேட்களைத் தக்கவைக்கிறது: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
மற்றும் tarball boot-smoke (`check:pack-boot`). இலக்கு: ~33 நிமிடங்களுக்குப் பதிலாக ≤15 நிமிடங்களில் வெற்றி நிலை.

**நுழைவுக் கொள்கை — நான்கும் கட்டாயம் (Chromium/VS Code/Node அவசரப் பாதைகளை அடிப்படையாகக் கொண்டது):**

1. **தீவிரம்**: production செயலிழந்துள்ளது — வெளியிடப்பட்ட artifact தொடங்கும்போது செயலிழக்கிறது / ஒரு
   பாதுகாப்புத் திருத்தம் / வெளியீட்டின் ஒவ்வொரு பயனரும் பாதிக்கப்படுகின்றனர். "முக்கியமானது" என்பது "செயலிழந்தது" அல்ல.
2. **அதிகாரம்**: repository உரிமையாளர் மட்டுமே `hotfix` லேபிளைப் பயன்படுத்துவார். அந்த லேபிளே
   ஒப்புதல் — campaign PR-இல் ஒருபோதும் சுயமாகப் பயன்படுத்த வேண்டாம்.
3. **ஆதாரம்**: PR விளக்கத்தில், முன்பு முழுமையாக வெற்றிபெற்ற கனமான run-க்கான இணைப்பும் (தவிர்க்கப்பட்ட jobs
   மீண்டும் சரிபார்த்திருக்கும் suite), திருத்தத்துக்கான முதலில் தோல்வியடைந்து பின்னர் வெற்றிபெற்ற test-உம் இருக்க வேண்டும்.
4. **வரம்பு**: cherry-pick மட்டும் — குறைந்தபட்சத் திருத்தம்; refactors அல்லது தொடர்பற்ற மாற்றங்கள் கூடாது.

தவிர்க்கப்பட்ட coverage/ratchet பரப்பு, release branch-இன் அடுத்த முழு run-இல்
மீண்டும் சரிபார்க்கப்படும் (தொடர்ச்சியான release-green) — இந்தப் பாதை காத்திருப்பை மட்டுமே தவிர்க்கிறது, சரிபார்ப்பை ஒருபோதும் தவிர்ப்பதில்லை.
Tests மட்டும் கொண்ட diffs (`tests/`-இன் கீழுள்ள அனைத்து files; `tests/e2e/`-இன் கீழ் எதுவுமில்லை) எந்த லேபிளும் இல்லாமல் E2E
மேட்ரிக்ஸைத் தானாகவே தவிர்க்கும்.

### தளவமைப்பை உருவாக்கவும்

களஞ்சியம் மூன்று தனித்துவமான வெளியீட்டு கோப்பகங்களைப் பயன்படுத்துகிறது — அவற்றை ஒருபோதும் கலக்காது:

| அடைவு     | நோக்கம்                                                                     | கண்காணிக்கப்பட்டதா?         |
| --------- | --------------------------------------------------------------------------- | --------------------------- |
| `src/`    | விண்ணப்ப ஆதாரம் (TypeScript / TSX)                                          | ஆம்                         |
| `.build/` | இடைநிலைகளை உருவாக்கு — `next build` வெளியீடு (`distDir`)                    | இல்லை (புறக்கணிக்கப்பட்டது) |
| `dist/`   | `assembleStandalone` ஆல் அசெம்பிள் செய்யப்பட்ட — அனுப்பக்கூடிய npm தொகுப்பு | இல்லை (புறக்கணிக்கப்பட்டது) |

> **ஆபரேட்டர் குறிப்பு:** ரிமோட் VPS பட அடைவு `/usr/lib/node_modules/omniroute/app/` ஆக உள்ளது. மட்டுமே** இன்-ரெப்போ** உருவாக்க வெளியீடு நகர்த்தப்பட்டது (`app/` → `dist/`). ரிமோட் `app/` dir — இல் rsync `dist/` உள்ளடக்கங்களை வரிசைப்படுத்தும் திறன் VPS பாதையில் மாற்றங்கள் தேவையில்லை.

**ஒற்றை கட்ட ஓட்டம்:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

NOT இயக்கவும் `npm run build` தொடர்ந்து — பயன்பாட்டு `npm run build:release` வரிசைப்படுத்த ஒரு தனி `npm run build:cli` செய்யவும், இது ஒரு கட்டளையில் + செண்டினலை மீண்டும் உருவாக்குகிறது.

v3.8.59 க்குப் பிறகு அடுத்த பதிப்பு 3.9.0 ஆகும், மேலும் அதன் முனை இரண்டு நீண்ட கிளைகளாக மாறும்: `stable/v3` (v3 LTS வரி, npm `latest`) மற்றும் `develop` (v4, 4.0.0 க்கு பம்ப், npm `nightly`). branch/channel மாதிரி, முன்னோக்கி-போர்ட் மற்றும் லேபிள்கள் [RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md) இல் உள்ளன; திட்டம் [ROADMAP](../../ROADMAP.md) இல் உள்ளது (கட்டம் 3). வெட்டு ஒரு முறை ஓடுகிறது; 3.8.58 முட்கரண்டியில் முடிவடைவதை ஒத்திகை பார்க்கிறது, மேலும் 3.8.59 [GO/NO-GO சரிபார்ப்புப் பட்டியலுடன்](./LTS_GO_NO_GO.md) முடிவடைகிறது.

### உலர் ஓட்டம் (படிக்க மட்டும், எந்த நேரத்திலும் பாதுகாப்பானது)

```bash
npm run release:dry-run-lts-cut                       # the real cut: 3.9.0 from HEAD, previous tag v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # pin the source commit
```

`scripts/release/dry-run-lts-cut.mjs` executes nothing: it reads git and `gh` and prints the whole sequence — preconditions (source resolves, the source repository has full history — a shallow clone cannot push `stable/v3`, the receiving side rejects the pack at the first grafted parent, so cut from a full clone or `git fetch --unshallow origin` first — previous tag exists, `package.json` is the target version, a `release-freeze` issue is open, no open `Release branch not green` issue on an existing release branch — a branch that does not exist reports `?` unknown, never green — omni-queue lands the release PRs (G11: `config/merge-queue/config.json` valid, its `bases` manage the release branch, `mode` `live`, its label exists), the `release/*` ruleset still blocks deletion and force-push, and `stable/v3` and `develop` do not exist yet), the two branch steps, which dormant-workflow triggers and `if:` conditions turn true (and which stay gated by a repository variable or pinned to the canonical repository), the expected dist-tags (`latest` → 3.9.0, `next` and `nightly` empty) and the rollback. Exit `0` = `RESULT: READY`, `1` = a blocking precondition failed (`✗`), `2` = usage error. `--advisory <id,...>` downgrades a check to a warning (`!`) without hiding it.

3.9.0 வெளியீட்டு முடக்கம் — திறந்திருக்கும் போது உண்மையான வெட்டு ட்ரை-ரன் இயக்கவும்.

### 3.8.58 ஒத்திகை (முட்கரண்டி மட்டும்)

### PR முன்னோட்ட கலைப்பொருள் (ஒருமுறை உருவாக்கவும், அதே பைட்டுகளை விளம்பரப்படுத்தவும்)

`.github/workflows/preview-artifact.yml` ஒரு PR தலையிலிருந்து ஒரு உற்பத்தி டார்பாலை உருவாக்குகிறது மற்றும் அந்த துல்லியமான கட்டமைப்பை சரிபார்க்கிறது (#8084 ஸ்லைஸ் (அ)). ஒரே களஞ்சியமான PRs மட்டும்; எதுவும் வெளியிடப்படவில்லை.

```bash

gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview

ரன் `npm ci` செய்கிறது , `npm run build:release`, `npm run check:pack-artifact`, டார்பால் பேக் செய்கிறது, `npm run check:pack-boot` (போலி ரகசியங்கள், எபிமரல் டேட்டா dir), ரீ-பேக் மற்றும் டைஜெஸ்ட் ஒரே மாதிரியாக இல்லாவிட்டால், `artifact-identity.json` பதிவு செய்கிறது (head SHA, base SHA, lockfile பில்ட், ப்ளாட்ஃபார்ம், ABI, ப்ளாட்ஃபார்ம், ப்ளாட்ஃபார்ம் இல்லை — `scripts/release/artifact-identity.mjs`) மற்றும் ஒரு தனி வேலையில் டார்பால் சான்றளிக்கிறது. முன்னோட்டத்தை விளம்பரப்படுத்துவது என்பது அந்த டார்பாலை நிறுவுவதாகும்: மூலத்திலிருந்து மீண்டும் உருவாக்க வேண்டாம்.

### வெட்டு (3.9.0, GO க்குப் பிறகு)

   ```

4. முதல் PR தரையிறங்குவதற்கு முன் `stable/v3` மற்றும் `develop` (ரூல்செட் + மெர்ஜ் வரிசை) ஆகியவற்றைப் பாதுகாக்கவும்.
5. செயலற்ற பணிப்பாய்வுகள் கிளை இருப்பின் மூலம் மாறுகின்றன: `forward-port.yml` ( `stable/v3` க்கு தள்ளவும்), `validate-stable-pr.yml` (PRs to `stable/v3`) மற்றும் `nightly-v4-build.yml` ( `develop` உருவாக்குகிறது). கோ-லைவ்க்கு முன், `secrets.FORWARD_PORT_TOKEN` களஞ்சிய ரகசியத்தை அமைக்கவும் (எனவே CI முன்னோக்கி-போர்ட் PRs இல் இயங்குகிறது); உரிமையாளர் களஞ்சிய மாறி `vars.NIGHTLY_PUBLISH` ஐ `true` ஆக அமைக்கும் வரை இரவு வெளியீடு நிறுத்தப்படும் மற்றும் npm நம்பகமான பதிப்பகம் `nightly-v4-build.yml` ஏற்கும். சேனல் தெளிவுத்திறன் `scripts/release/dist-tag.mjs` ஆகும், அதே தீர்வு `npm-publish.yml` பயன்படுத்துகிறது.
6. சேனல்களைச் சரிபார்க்கவும்: `npm view omniroute dist-tags --json` `latest` = 3.9.0 ஐக் காட்டுகிறது மற்றும் v4 வெளியிடும் வரை `next` / `nightly` இல்லை.
7. ரோல்பேக், தேவைப்பட்டால்: `git push origin --delete refs/heads/stable/v3 refs/heads/develop` மற்றும் `npm dist-tag add omniroute@3.8.59 latest`.

## முந்தைய நிலைக்குத் திரும்புதல்

வெளியீட்டில் கடுமையான சிக்கல் இருந்தால்:

1. `gh release edit vX.Y.Z --prerelease` (சமீபத்திய வெளியீடு அல்ல எனக் குறிக்கும்)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (பயனர்கள் இன்னும் ஏற்றுக்கொள்ளவில்லை என்றால் மட்டும்)
3. அல்லது: `release/vX.Y.0`-இல் hotfix → patch வெளியீடு `vX.Y.(Z+1)`
4. GitHub Discussions மற்றும் Discord-இல் உடனடியாகத் தெரிவிக்கவும்

## கட்டாய விதிகள்

- `main`-க்கு ஒருபோதும் நேரடியாக commit செய்ய வேண்டாம்
- `main` அல்லது `release/*` கிளைகளுக்கு `git push --force`-ஐ ஒருபோதும் பயன்படுத்த வேண்டாம்
- Husky hooks-ஐ (`--no-verify`) ஒருபோதும் தவிர்க்க வேண்டாம்
- secrets, credentials அல்லது `.env` கோப்புகளை ஒருபோதும் commit செய்ய வேண்டாம்
- Coverage ≥60/60/60/60 (statements/lines/functions/branches) ஆகத் தொடர்ந்து இருக்க வேண்டும்
- `src/`, `open-sse/`, `electron/` அல்லது `bin/`-இல் உள்ள production code-ஐ மாற்றும்போது எப்போதும் tests-ஐச் சேர்க்கவும் அல்லது புதுப்பிக்கவும்
