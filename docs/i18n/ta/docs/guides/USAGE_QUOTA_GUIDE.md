> **சுருக்கமாக**: OmniRoute ஒவ்வொரு கோரிக்கையின் டோக்கன் பயன்பாட்டையும் கண்காணித்து, செலவைக் கணக்கிட்டு, ஒவ்வொரு API விசைக்குமான ஒதுக்கீட்டைச் செயல்படுத்தி, பகுப்பாய்வுகளை டாஷ்போர்டில் காட்டுகிறது. இவை அனைத்தும் எவ்வாறு செயல்படுகின்றன என்பதை இந்த வழிகாட்டி விளக்குகிறது.

**மூலங்கள்:**

- `open-sse/services/usage.ts` (~70KB) — முதன்மைப் பயன்பாட்டுக் கண்காணிப்பு
- `src/lib/usageAnalytics.ts` (~10KB) — டாஷ்போர்டுக்கான திரட்டல்
- `src/lib/db/quotaSnapshots.ts` — வரலாற்று ஒதுக்கீட்டுத் தரவு
- `src/lib/db/usage*.ts` — பயன்பாடு தொடர்பான பல DB தொகுதிகள்

## மேலோட்டம்

OmniRoute வழியாகச் செல்லும் ஒவ்வொரு கோரிக்கையும் பின்வருவனவற்றைப் பதிவு செய்யும் ஒரு **பயன்பாட்டுப் பதிவை** உருவாக்குகிறது:

- **அடையாளம்**: எந்த API விசை, வழங்குநர், மாதிரி, காம்போ
- **டோக்கன்கள்**: ப்ராம்ப்ட் டோக்கன்கள், நிறைவு டோக்கன்கள், தற்காலிகச் சேமிப்பு டோக்கன்கள், மொத்தம்
- **செலவு**: USD தொகை (விலைத் தரவிலிருந்து கணக்கிடப்பட்டது)
- **நேர விவரங்கள்**: தாமதம், தொடக்க/முடிவு நேரமுத்திரைகள்
- **நிலை**: வெற்றி, பிழை, விகித வரம்பிடப்பட்டது போன்றவை

இந்தப் பதிவுகள் **பகுப்பாய்வுகளாகத்** திரட்டப்பட்டு, **ஒதுக்கீட்டு ஸ்னாப்ஷாட்களாகச்** சேமிக்கப்பட்டு, **ஒவ்வொரு விசைக்குமான பட்ஜெட் வரம்புகளைச்** செயல்படுத்தப் பயன்படுத்தப்படுகின்றன.

```
கோரிக்கை ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    பகுப்பாய்வு  ஒதுக்கீடு  பில்லிங்
                    (டாஷ்போர்டு) (செயலாக்கம்) (ஏற்றுமதி)
```

## எவை பதிவு செய்யப்படுகின்றன

`usage.ts` சேவை ஒவ்வொரு கோரிக்கைக்கும் ஒரு **பயன்பாட்டு நிகழ்வைப்** பதிவு செய்கிறது:

| புலம்              | வகை         | மூலம்                                                                                       |
| ------------------ | ----------- | ------------------------------------------------------------------------------------------- |
| `id`               | சரம்        | பதிவு செய்யும்போது உருவாக்கப்படும் UUID                                                     |
| `apiKeyId`         | சரம்        | கோரிக்கையைத் தொடங்கிய API விசை                                                              |
| `provider`         | சரம்        | வழங்குநர் ID (openai, anthropic போன்றவை)                                                    |
| `model`            | சரம்        | மாதிரி ID (gpt-5, claude-opus-4-6 போன்றவை)                                                  |
| `comboId`          | சரம்?       | ஒரு கூட்டமைப்பு வழியாக வழிசெலுத்தப்பட்டால் அதன் ID                                          |
| `promptTokens`     | எண்         | மேல்நிலைப் பதிலிலிருந்து                                                                    |
| `completionTokens` | எண்         | மேல்நிலைப் பதிலிலிருந்து                                                                    |
| `cachedTokens`     | எண்         | தற்காலிகச் சேமிப்பில் கிடைத்த டோக்கன்கள் (Anthropic ப்ராம்ப்ட் தற்காலிகச் சேமிப்பு போன்றவை) |
| `totalTokens`      | எண்         | ப்ராம்ப்ட் + நிறைவு                                                                         |
| `costUsd`          | எண்         | விலைத் தரவிலிருந்து கணக்கிடப்பட்டது                                                         |
| `latencyMs`        | எண்         | கோரிக்கையின் தொடக்கம் முதல் முடிவு வரையிலான கால அளவு                                        |
| `status`           | பட்டியல்வகை | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                                  |
| `errorClass`       | சரம்?       | நிலை != வெற்றி எனில் பிழை வகை                                                               |
| `timestamp`        | சரம்        | ISO 8601 UTC                                                                                |
| `metadata`         | பொருள்      | செருகுநிரலால் சேர்க்கப்பட்ட தனிப்பயன் தரவு                                                  |

### டோக்கன்கள் எங்கிருந்து வருகின்றன

மேல்நிலை வழங்குநரின் பதிலிலிருந்து **பதில் கையாளியில்** டோக்கன்கள் பிரித்தெடுக்கப்படுகின்றன:

```ts
// open-sse/handlers/chatCore.ts இலிருந்து
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

பயன்பாட்டுத் தகவலைத் திருப்பியனுப்பாத வழங்குநர்களுக்கு (சில web-cookie வழங்குநர்கள்), OmniRoute ஒரு `~4 chars per token` தோராய விதியைப் பயன்படுத்தி டோக்கன்களை **மதிப்பிடுகிறது** (`open-sse/services/autoCombo/pipelineRouter.ts` பார்க்கவும்).

### தற்காலிகச் சேமிப்பிலுள்ள டோக்கன்கள்

OmniRoute, `prompt_tokens` என்பதிலிருந்து `cached_tokens` என்பதைத் தனியாகக் கண்காணிக்கிறது. ஏனெனில்:

- Anthropic ப்ராம்ப்ட் தற்காலிகச் சேமிப்பு, சேமிக்கப்பட்ட டோக்கன்களுக்குக் குறைந்த கட்டணத்தை வசூலிக்கிறது (வழக்கமான கட்டணத்தில் 10%)
- சில வழங்குநர்கள் வேறுபட்ட விலையில் கணக்கிடப்பட வேண்டிய `cache_read_input_tokens` என்பதைத் திருப்பியனுப்புகின்றனர்
- பகுப்பாய்வில் **தற்காலிகச் சேமிப்பில் கிடைக்கும் விகிதத்தை** = `cached_tokens / prompt_tokens` காட்ட முடியும்

### தற்காலிகச் சேமிப்பு எழுதுதல் அடுக்கு ஆய்வுகள்

பகுப்பாய்வு முகப்புப் பலகையின் ப்ராம்ப்ட் தற்காலிகச் சேமிப்பு நலப் பலகம், வழங்குநர் தெரிவிக்கும்
5 நிமிட மற்றும் 1 மணிநேர தற்காலிகச் சேமிப்பு எழுதுதல்களை வேறுபடுத்திக் காட்டுகிறது. Anthropic-இன்
`usage.cache_creation.ephemeral_5m_input_tokens` மற்றும்
`usage.cache_creation.ephemeral_1h_input_tokens` ஆகியவை ஸ்ட்ரீமிங் மற்றும்
ஸ்ட்ரீமிங் அல்லாத பயன்பாட்டுத் தரவு மாற்றத்தின்போது தக்கவைக்கப்பட்டு, அழைப்புப் பதிவுச் சுருக்கங்களுடன் சேமிக்கப்படுகின்றன. ஒருங்கிணைந்த
தற்காலிகச் சேமிப்பு எழுதுதல் மொத்தம் அந்தப் பிரிவுகளில் இரண்டாவது முறையாகச் சேர்க்கப்படுவதில்லை.

பழைய பதிவுகள் உட்பட, ஒருங்கிணைந்த எழுதுதல் எண்ணிக்கையை மட்டுமே கொண்ட அழைப்புகளின்
அடுக்கு தெரியாததாகக் கருதப்படுகிறது. பகுதியளவிலான பிரிப்பு இருந்தால், ஒதுக்கப்படாத மீதம் தெரியாததாகவே வைக்கப்படும்; செல்லாத அல்லது
முரண்படும் எண்ணிக்கைகளுக்கு மறைமுகமாக TTL ஒதுக்குவதற்குப் பதிலாக அவை குறியிடப்படுகின்றன. கோரிக்கைப் பக்க
TTL குறிப்பான்கள், கட்டணம் விதிக்கப்பட்ட அடுக்கிற்கான ஆதாரம் அல்ல.

பலகையின் API-க்கு இணையான எழுதுதல் மதிப்பீடு, தெரிவிக்கப்பட்டு விலை நிர்ணயிக்கப்பட்ட அடுக்குகளை மட்டுமே உள்ளடக்குகிறது;
முழுக் கோரிக்கையையும் அல்ல. நேரடி Claude/Anthropic மாதிரி விலை நிர்ணயத்திற்கு, 5 நிமிட எழுதுதல்களுக்கு
உள்ளீட்டுக் கட்டணத்தின் 1.25 மடங்கையும், 1 மணிநேர எழுதுதல்களுக்கு உள்ளீட்டுக் கட்டணத்தின் இரு மடங்கையும் பயன்படுத்துகிறது. விடுபட்ட
விலைத் தகவல் கிடைக்காததாகக் கருதப்படுகிறது; பூஜ்ஜியமாக அல்ல. ஒவ்வொரு புதிய அழைப்பும் பதிவு செய்யப்படும்போது விலைகள் சேமிக்கப்படுகின்றன;
வரலாற்றுப் பதிவுகளின் விலைகள் மீண்டும் கணக்கிடப்படுவதில்லை. எனவே, சந்தாக் கணக்குகளுக்கு
API-க்கு இணையான மதிப்பீடு இருக்கலாம்; ஆனால் அந்தத் தொகை பணச் செலவாகவோ சந்தா
ஒதுக்கீட்டுப் பயன்பாடாகவோ ஏற்பட வேண்டியதில்லை. ஏற்கெனவே உள்ள ஒதுக்கீடு, செலவுத்திட்டம் மற்றும் வழங்குநரின் துல்லியமான செலவுக் கணக்கீடுகள் மாறாமல் உள்ளன.

இந்த ஆய்வுகள், ஏற்கெனவே உள்ள வரம்புக்குட்பட்ட தற்காலிகச் சேமிப்பு நலச் சுருக்கத்தையும் அழைப்புப் பதிவு
தக்கவைப்பையும் பயன்படுத்துகின்றன. இவை கோரிக்கையின் இயல்புநிலை TTL, வழிசெலுத்தல் அல்லது கணக்குத் தேர்வை மாற்றுவதில்லை.
வழங்குநருக்கு அனுப்பும் எல்லையில், வாடிக்கையாளர் கோரிய TTL மற்றும் நடைமுறையில் வெளியே அனுப்பப்படும் TTL ஆகியவற்றைப் பதிவு செய்வது
ஒத்திவைக்கப்பட்டுள்ளது; இந்தப் பலகம் ரசீது அடுக்குகளைத் தெரிவிக்கிறது, நடைமுறையில் வெளியே அனுப்பப்படும் TTL-ஐ அல்ல.

செயலாக்கம்: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, மற்றும் `open-sse/utils/cacheWriteUsage.ts`.

## செலவுக் கணக்கீடு

LiteLLM இலிருந்து ஒத்திசைக்கப்பட்ட **விலை நிர்ணயத் தரவைக்** (`src/lib/pricingSync.ts`) கொண்டு செலவுகள் கணக்கிடப்படுகின்றன:

| மாடல்             | உள்ளீடு $/1M | வெளியீடு $/1M | தற்காலிகச் சேமிப்பு $/1M |
| ----------------- | ------------ | ------------- | ------------------------ |
| gpt-5             | $2.50        | $10.00        | —                        |
| claude-opus-4-6   | $15.00       | $75.00        | $1.50                    |
| claude-sonnet-4-5 | $3.00        | $15.00        | $0.30                    |
| gemini-2.5-pro    | $1.25        | $10.00        | —                        |

செலவுச் சூத்திரம் (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Prompt இலிருந்து தற்காலிகச் சேமிப்பை ஏன் கழிக்க வேண்டும்?** தற்காலிகச் சேமிப்பில் உள்ள பகுதிக்குத் தனியாக விலை நிர்ணயிக்கப்படுகிறது; முழு prompt-க்கும் உள்ளீட்டு விலையை வசூலித்தால் செலவு அதிகமாகக் கணக்கிடப்படும்.

### விலை நிர்ணய ஒத்திசைவு

உள்ளமைக்கப்பட்ட cron பணியால் தூண்டப்படும் `/api/pricing/sync` endpoint வழியாக LiteLLM இலிருந்து விலை நிர்ணயத் தரவு தானாக ஒத்திசைக்கப்படுகிறது; இது பயனர் அணுகக்கூடிய env var அல்ல:

```bash
# கைமுறையாகத் தூண்டுதல்
curl -X POST http://localhost:20128/api/pricing/sync
```

விலை நிர்ணயத் தரவு இல்லாத மாடல்களுக்கு, உள்நிலை சராசரி விகிதங்களைப் பயன்படுத்தி OmniRoute **செலவை மதிப்பிடும்**; இந்த விகிதங்கள் LiteLLM இன் விலை நிர்ணயத் தரவிலிருந்து பெறப்படுகின்றன.

## தேதி வரம்புத் திரட்டல்

`usageAnalytics.ts` தொகுதி, மூலப் பயன்பாட்டுத் தரவிலிருந்து கட்டுப்பாட்டுப் பலகை விட்ஜெட்களைக் கணக்கிடுகிறது. இது 7 கால வரம்புகளை ஆதரிக்கிறது:

| வரம்பு   | காலச் சாளரம்                       | பயன்பாட்டு நோக்கம்                         |
| -------- | ---------------------------------- | ------------------------------------------ |
| `1d`     | கடந்த 24 மணிநேரம்                  | மணிநேரச் செலவு அதிகரிப்பைக் கண்டறிதல்      |
| `7d`     | கடந்த 7 நாட்கள்                    | வாராந்திர மதிப்பாய்வு                      |
| `30d`    | கடந்த 30 நாட்கள்                   | மாதாந்திரக் கட்டணக் கணக்கீடு               |
| `90d`    | கடந்த 90 நாட்கள்                   | காலாண்டுப் பகுப்பாய்வு                     |
| `ytd`    | நடப்பு ஆண்டின் ஜனவரி 1 முதல்       | வருடாந்திர வரவுசெலவுத் திட்டக் கண்காணிப்பு |
| `all`    | முழுக் காலமும்                     | மொத்தக் காலப் புள்ளிவிவரங்கள்              |
| `custom` | பயனர் வரையறுக்கும் தொடக்கம்/முடிவு | தணிக்கைகள், தேவைக்கேற்ற வினவல்கள்          |

### கணக்கிடப்படும் கட்டுப்பாட்டுப் பலகை விட்ஜெட்கள்

எந்தத் தேதி வரம்பிற்கும், பகுப்பாய்வு அடுக்கு பின்வருவனவற்றைக் கணக்கிடுகிறது:

| விட்ஜெட்                      | விளக்கம்                                                             |
| ----------------------------- | -------------------------------------------------------------------- |
| **சுருக்க அட்டைகள்**          | மொத்தக் கோரிக்கைகள், மொத்தச் செலவு, மொத்த டோக்கன்கள், வெற்றி விகிதம் |
| **தினசரிப் போக்கு வரைபடம்**   | நாளொன்றுக்கான செலவு + டோக்கன்கள், மாதிரி வாரியாக அடுக்கப்பட்டவை      |
| **செயல்பாட்டு வெப்ப வரைபடம்** | நாளின் மணிநேரம் × வாரத்தின் நாள் கட்டம், நிறம் = கோரிக்கை எண்ணிக்கை  |
| **மாதிரி வாரியான விவரம்**     | மாதிரி வாரியான செலவின் வட்ட வரைபடம்                                  |
| **வழங்குநர் வாரியான விவரம்**  | வழங்குநர் வாரியான கோரிக்கைகளின் பட்டை வரைபடம்                        |
| **முன்னணி API விசைகள்**       | செலவின் அடிப்படையில் முதல் 10 விசைகளின் அட்டவணை                      |
| **பிழைப் பகுப்பாய்வு**        | காலப்போக்கில் பிழை விகிதம், முன்னணி பிழை வகைகள்                      |

### நிரல் வழி அணுகல்

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // பயன்பாட்டு வரலாற்றுப் பதிவுகள்
  "7d",                 // கால வரம்பு: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // வழங்குநர் இணைப்பு வரைபடம் (connectionId → கணக்குப் பெயர்)
  {
    startDate: "2025-01-01",  // விருப்பத்தேர்வு: "custom" வரம்பிற்கு
    endDate: "2025-06-01",   // விருப்பத்தேர்வு: "custom" வரம்பிற்கு
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (சென்ட்கள்)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## ஒதுக்கீட்டை அமல்படுத்துதல்

ஒவ்வொரு API விசைக்குமான ஒதுக்கீடு இரண்டு இடங்களில் அமல்படுத்தப்படுகிறது:

1. **மென்மையான வரம்பு** (`quotaWarnAt`): பயன்பாடு வரம்புநிலையை மீறும்போது கட்டுப்பாட்டுப் பலகையில் எச்சரிக்கை
2. **கடுமையான வரம்பு** (`quotaLimit`): வரம்பை மீறும்போது HTTP 429 உடன் கோரிக்கை நிராகரிக்கப்படும்

### உள்ளமைவு

```ts
// ஒவ்வொரு API விசைக்கும்
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — எச்சரிக்கையைக் காட்டு
  quotaLimit: 10_00,    // $10.00 — கட்டாய நிறுத்தம்
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### அமலாக்க ஓட்டம்

```
கோரிக்கை ──▶ quotaCheck()
              │
              ├── வரம்பிற்குள் உள்ளதா?  ──▶ அனுமதி
              │
              └── வரம்பை மீறியதா?  ──▶ 429 Too Many Requests
                                   Retry-After தலைப்புடன்
```

### ஒதுக்கீட்டு நிலைப்பதிவுகள்

போக்குப் பகுப்பாய்விற்காக `quotaSnapshots` அட்டவணை **வரலாற்று ஒதுக்கீட்டு நிலையைச்** சேமிக்கிறது:

| புலம் | விளக்கம் |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | கண்காணிக்கப்படும் விசை |
| `window` | "day" | "week" | "month" |
| `used` | இந்தக் காலச் சாளரத்தில் பயன்படுத்தப்பட்ட செலவு (சென்ட்கள்) |
| `limit` | வரம்பு (சென்ட்கள்) |
| `resetAt` | காலச் சாளரம் மீட்டமைக்கப்படும் நேரம் |
| `createdAt` | நிலைப்பதிவு எடுக்கப்பட்ட நேரம் |

செலவு > 0 ஆக உள்ள **ஒவ்வொரு கோரிக்கையின்போதும்** நிலைப்பதிவுகள் எடுக்கப்படுகின்றன. அவை பின்வருவனவற்றிற்குப் பயன்படுத்தப்படுகின்றன:

- கட்டுப்பாட்டுப் பலகையில் ஒதுக்கீட்டு முன்னேற்றப் பட்டையைக் காட்டுதல்
- 30 நாள் ஒதுக்கீட்டுப் போக்கு வரைபடங்களைக் காட்டுதல்
- பயன்பாடு வரம்பை நெருங்கும்போது எச்சரிக்கைகளைத் தூண்டுதல்

## தக்கவைப்பு மற்றும் தூய்மைப்படுத்தல்

ஒவ்வொரு கோரிக்கைக்கும் பயன்பாட்டுத் தரவு ~1-10KB அதிகரிக்கிறது. பெரிய அளவில், இது கணிசமானதாக இருக்கலாம்.

### தக்கவைப்பு அமைப்புகள்

பயன்பாட்டு வரலாற்றின் தக்கவைப்பு, பயனர் இடைமுகத்தில் உள்ள தரவுத்தள அமைப்புகள் வழியாக அல்லது `/api/settings/database` வழியாக உள்ளமைக்கப்படுகிறது.

இயல்பாக, பயன்பாட்டு வரலாறு **90 நாட்களுக்கு** தக்கவைக்கப்படுகிறது.

### தூய்மைப்படுத்தல்

பழைய பதிவுகள் `src/lib/db/cleanup.ts` மூலம் அகற்றப்படுகின்றன:

- பின்னணி cron செயல்முறையால் தூண்டப்படுகிறது
- உள்ளமைக்கப்பட்ட `usageHistory` தக்கவைப்பு அமைப்பில் குறிப்பிடப்பட்ட காலத்தைவிடப் பழைய பதிவுகளை `usage_history` இலிருந்து நீக்குகிறது

### சேமிப்பக மதிப்பீடு

| கோரிக்கை வீதம்           | 30 நாள் சேமிப்பகம் | 90 நாள் சேமிப்பகம் |
| ------------------------ | ------------------ | ------------------ |
| 100 கோரிக்கைகள்/நாள்     | ~3MB               | ~9MB               |
| 1,000 கோரிக்கைகள்/நாள்   | ~30MB              | ~90MB              |
| 10,000 கோரிக்கைகள்/நாள்  | ~300MB             | ~900MB             |
| 100,000 கோரிக்கைகள்/நாள் | ~3GB               | ~9GB               |

மிக அதிகப் போக்குவரத்து இருந்தால், பின்வருவனவற்றைக் கருத்தில் கொள்ளவும்:

- தரவுத்தள அமைப்புகள் வழியாகத் தக்கவைப்புக் காலத்தைக் குறைத்தல்
- மூலப் பதிவுகளுக்குப் பதிலாக `aggregated_metrics` ஐப் பயன்படுத்துதல் (பகுப்பாய்வுக்கு மட்டும்)

## செலவை மேம்படுத்துவதற்கான குறிப்புகள்

### 1. சரியான மாதிரியைப் பயன்படுத்தவும்

```bash
# விரைவான பதில் — குறைந்த செலவு + வேகமானதைப் பயன்படுத்தவும்
curl -d '{"model":"auto/fast","messages":[...]}'

# சிக்கலான பணி — தரமானதைப் பயன்படுத்தவும்
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. தற்காலிகச் சேமிப்பை இயக்கவும்

Anthropic ப்ராம்ப்ட் தற்காலிகச் சேமிப்பு **மீண்டும் பயன்படுத்தப்படும் சூழலுக்கான செலவில் 90% சேமிக்கிறது**:

```ts
// தற்காலிகச் சேமிப்பு தானாகவே நடைபெறும் — அதே பெரிய சிஸ்டம் ப்ராம்ப்ட்டைச் சேர்த்தால் போதும்
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // தானாகவே தற்காலிகமாகச் சேமிக்கப்படும்
  messages: [{ role: "user", content: "..." }],
});
```

### 3. சுருக்கத்தைப் பயன்படுத்தவும்

RTK + Caveman சுருக்கம் **கருவிகள் அதிகம் பயன்படுத்தப்படும் அமர்வுகளில் 15-95% சேமிக்கிறது**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. ஒவ்வொரு விசைக்கும் ஒதுக்கீட்டு வரம்புகளை அமைக்கவும்

கட்டுப்பாடின்றி செலவு அதிகரிப்பதைத் தடுக்க எப்போதும் `quotaLimit` அமைக்கவும்:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // மாதத்திற்கு $10 வரம்பு
```

### 5. அதிகம் பயன்படுத்துபவர்களை ஆய்வு செய்யவும்

API விசையின் அடிப்படையில் குழுவாக்கி, செலவின் அடிப்படையில் வரிசைப்படுத்த, கட்டுப்பாட்டுப் பலகம் அல்லது **`/api/usage/analytics`** பயன்படுத்தவும்:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## சிக்கல்களைத் தீர்த்தல்

### "செலவு எதிர்பார்த்ததைவிட அதிகமாக உள்ளது"

1. **`/api/usage/analytics?groupBy=model`** என்பதைச் சரிபார்க்கவும் — அதிக செலவுள்ள மாதிரியைக் கண்டறியவும்
2. **`/api/usage/analytics?groupBy=apiKey`** என்பதைச் சரிபார்க்கவும் — அதிகம் பயன்படுத்துபவரைக் கண்டறியவும்
3. விலைத் தரவு புதுப்பித்த நிலையில் உள்ளதா என்பதைச் சரிபார்க்கவும்: `POST /api/pricing/sync`

### "பதிவுகள் காணவில்லை"

- கட்டுப்பாட்டுப் பலகம் → தரவுத்தளம் → சுத்தப்படுத்தல் என்பதன் கீழுள்ள தரவுத்தளத் தக்கவைப்பு அமைப்புகளைச் சரிபார்க்கவும் — பழைய பதிவுகள் குறிப்பிட்ட இடைவெளியில் இயங்கும் சுத்தப்படுத்தும் பணியால் நீக்கப்படுகின்றன (`src/lib/db/cleanup.ts`)
- `src/lib/db/usage*.ts` இல் பிழைகள் உள்ளனவா என்பதைச் சரிபார்க்கவும் — தரவுத்தளத்தில் எழுதுவதில் ஏற்படும் தோல்விகள் பதிவுசெய்யப்படுகின்றன, ஆனால் வெளிப்படையாகக் காட்டப்படுவதில்லை
- கோரிக்கை உண்மையில் `chatCore` ஐ அடைந்ததா என்பதைச் சரிபார்க்கவும் — காம்போ வழித்தட அமைப்பைச் சரிபார்க்கவும்

### "ஒதுக்கீட்டு வரம்பு அமல்படுத்தப்படவில்லை"

- விசையின் `quotaLimit` அமைப்பைச் சரிபார்க்கவும்
- `quotaWindow` சரியாக அமைக்கப்பட்டுள்ளதா என்பதைச் சரிபார்க்கவும்
- `quotaSnapshots` பதிவுகளைத் தேடவும் — ஒவ்வொரு கோரிக்கையின்போதும் அவை உருவாக்கப்பட வேண்டும்
