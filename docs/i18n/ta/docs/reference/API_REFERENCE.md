## Chat Completions

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### தனிப்பயன் தலைப்புகள்

| Header                   | Direction | Description                                                                                                                                                                                                                                         |
| ------------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | கோரிக்கை  | தற்காலிகச் சேமிப்பைப் புறக்கணிக்க `true` ஆக அமைக்கவும்                                                                                                                                                                                              |
| `x-omniroute-no-memory`  | கோரிக்கை  | இந்தக் கோரிக்கைக்கான நினைவகம் + திறன்கள் உட்சேர்ப்பைத் தவிர்க்க `true` ஆக அமைக்கவும் (no-cache-ஐப் பிரதிபலிக்கிறது; ஒவ்வொரு அழைப்புக்குமான டோக்கன்/செலவு மேல்செலவைத் தவிர்க்கிறது)                                                                  |
| `X-OmniRoute-Progress`   | கோரிக்கை  | முன்னேற்ற நிகழ்வுகளுக்கு `true` ஆக அமைக்கவும்                                                                                                                                                                                                       |
| `X-Session-Id`           | கோரிக்கை  | வெளிப்புற அமர்வு ஒட்டுமைக்கான நிலையான அமர்வு விசை                                                                                                                                                                                                   |
| `x_session_id`           | கோரிக்கை  | அடிக்கோடு மாறுபாடும் ஏற்கப்படுகிறது (நேரடி HTTP)                                                                                                                                                                                                    |
| `X-OmniRoute-Session-Id` | கோரிக்கை  | அழைப்பாளர் வழங்கிய அமர்வு/உரையாடல் குறிச்சொல் (நினைவகத்திற்கும் வழங்கப்படுகிறது). இது இருந்தால், ஒவ்வொரு அமர்வுக்குமான செலவுப் பண்புக்கூறலுக்காக (#8249) `call_logs.session_tag`-இல் அப்படியே சேமிக்கப்படும் — இல்லாதபோது ஒருபோதும் உருவாக்கப்படாது |
| `Idempotency-Key`        | கோரிக்கை  | நகல் நீக்கல் விசை (5 வினாடி காலவரம்பு)                                                                                                                                                                                                              |
| `X-Request-Id`           | கோரிக்கை  | மாற்று நகல் நீக்கல் விசை                                                                                                                                                                                                                            |
| `x-omniroute-connection` | கோரிக்கை  | ஒற்றை-மாதிரி கோரிக்கையை அதன் அடையாளத்தின் மூலம் ஒரு வழங்குநர் இணைப்பில் (கணக்கில்) நிலைநிறுத்தவும் — [ஒரு கோரிக்கைக்கான கணக்கு நிலைநிறுத்தல்](#account-pinning-per-request) என்பதைப் பார்க்கவும்                                                    |
| `X-OmniRoute-Cache`      | பதில்     | `HIT` அல்லது `MISS` (ஸ்ட்ரீமிங் அல்லாதது)                                                                                                                                                                                                           |
| `X-OmniRoute-Idempotent` | பதில்     | நகல் நீக்கம் செய்யப்பட்டிருந்தால் `true`                                                                                                                                                                                                            |
| `X-OmniRoute-Progress`   | பதில்     | முன்னேற்றக் கண்காணிப்பு இயக்கப்பட்டிருந்தால் `enabled`                                                                                                                                                                                              |
| `X-OmniRoute-Session-Id` | பதில்     | OmniRoute பயன்படுத்திய செயல்திறன் அமர்வு ID                                                                                                                                                                                                         |
| `X-OmniRoute-Request-Id` | பதில்     | கோரிக்கை தொடர்பு ID (தெரிந்திருக்கும்போது)                                                                                                                                                                                                          |
| `X-OmniRoute-Version`    | பதில்     | OmniRoute உருவாக்கப் பதிப்பு (எப்போதும் இருக்கும்)                                                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | பதில்     | `HIT`-இல் தற்காலிகச் சேமிப்பால் தவிர்க்கப்பட்ட USD செலவு (தற்காலிகச் சேமிப்பு வெற்றிகளுக்கு மட்டும்)                                                                                                                                                |
| `X-OmniRoute-Decision`   | பதில்     | வழிமாற்றுத் தடம்: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` என்பது கூட்டு உத்தி; கூட்டு அல்லாத கோரிக்கைக்கு `single`) — நிறைவு பதில்களில் எப்போதும் இருக்கும்                                                                   |

> Nginx குறிப்பு: அடிக்கோடு கொண்ட தலைப்புகளை (எடுத்துக்காட்டாக `x_session_id`) சார்ந்திருந்தால், `underscores_in_headers on;` என்பதை இயக்கவும்.

#### ஒரு கோரிக்கைக்கான கணக்கு நிலைநிறுத்தல்

ஒரு வழங்குநரிடம் பல இணைப்புகள் (கணக்குகள் அல்லது விசைகள்) இருக்கும்போது, OmniRoute பொதுவாக அதன் கணக்குத் தேர்வு உத்தியின் மூலம் ஒன்றைத் தேர்ந்தெடுக்கும். அதற்குப் பதிலாக, ஒரு கோரிக்கை குறிப்பிட்ட இணைப்பொன்றை `x-omniroute-connection` தலைப்பின் மூலம் நிலைநிறுத்தலாம்:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id-ஐ எங்கே கண்டறிவது.** Dashboard-இல் provider பக்கத்தைத் திறந்து
  (**Dashboard → Providers → <provider>**), connection வரிசையில் உள்ள `xxxxxxxx…` id chip-ஐக் கிளிக்
  செய்யவும் — அது முழு connection id-ஐ நகலெடுக்கும்.
- **எந்தக் கோரிக்கைகள் இதை மதிக்கும்.** `/v1/chat/completions`, `/v1/messages` மற்றும்
  `/v1/responses` ஆகியவற்றில் உள்ள ஒற்றை-model கோரிக்கைகள் (`provider/model`). Combos இந்த
  header-ஐப் புறக்கணிக்கும்: ஒவ்வொரு combo படிக்கும் அதன் சொந்த connection மூலம் account-ஐ pin
  செய்யவும்.
- **இந்த pin ஒரு கடுமையான கட்டுப்பாடு; விருப்பத்தேர்வு அல்ல.** Pin செய்யப்பட்ட connection மட்டுமே
  பயன்படுத்தப்படும். கோரிக்கைக்குள் ஏற்படும் தோல்வி account-இன் cooldown-ஐப் பதிவு செய்யும்; ஆனால்
  அதே provider-இன் sibling account-க்கு மாறாது.
- **Cooldown மற்றும் quota ஆகியவை pin-ஐ விடுவிக்கும்.** Pin செய்யப்பட்ட connection cooldown-இல்
  இருக்கும் போது, quota முடிந்திருந்தால் அல்லது quota policy காரணமாகத் தடுக்கப்பட்டிருந்தால், அடுத்த
  கோரிக்கைகள் provider-இன் பிற connections-க்கு fallback ஆகும்; இது pin செய்யப்படாத traffic போலவே
  செயல்படும்.
- **அறியப்படாத அல்லது முடக்கப்பட்ட ids தோல்வியடையும்.** Provider-இன் active pool-இல் இல்லாத id
  (நீக்கப்பட்டது, செயலிழக்கச் செய்யப்பட்டது அல்லது வேறு provider-க்கு சொந்தமானது) eligible account
  எதுவும் இல்லாத நிலையை உருவாக்கும்; எனவே கோரிக்கை வேறு இடத்துக்கு அமைதியாக route ஆகாமல்
  தோல்வியடையும்.

Claude Code தனிப்பயன் headers-ஐ `ANTHROPIC_CUSTOM_HEADERS` மூலம் அனுப்புகிறது. அதை
`~/.claude/settings.json` இன் `env` block-இல் அமைக்கவும்; அல்லது ஒவ்வொரு project-க்கும் வேறு
account-ஐ pin செய்ய project-level `.claude/settings.json` இல் அமைக்கவும்:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

மூலம்: `src/sse/handlers/chat.ts` (header read), `src/sse/services/auth.ts` மற்றும்
`src/sse/services/sessionAffinityPin.ts` (pin release மற்றும் pool-இல் இல்லாததற்கான சரிபார்ப்பு).

> **Cost telemetry headers:** streaming அல்லாத வெற்றிகரமான responses-களிலும் `X-OmniRoute-*` cost-telemetry தொகுப்பு இருக்கும் — `X-OmniRoute-Response-Cost` (USD, நிலையான 10 தசமங்கள்; இலவசம்/விலை நிர்ணயிக்கப்படாததற்கு `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit`, மற்றும் `X-OmniRoute-Fallback-Attempts` (`> 0` இருக்கும் போது மட்டும்), மேலும் `X-OmniRoute-Request-Id` மற்றும் `X-OmniRoute-Version`. இவை chat completions, `/v1/responses`, `/v1/messages`, **மற்றும் media endpoints** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations`, மற்றும் `/v1/moderations` — அனைத்திலும் வெளியிடப்படும் (`/v1/moderations` இல் எப்போதும் cost `0`). Pricing கிடைக்கும் போது media cost ஒவ்வொரு modality-க்கும் (ஒவ்வொரு image-க்கும், ஒவ்வொரு second-க்கும், ஒவ்வொரு character-க்கும், ஒவ்வொரு search-unit-க்கும்) கணக்கிடப்படும்; இல்லையெனில் `0` (fail-open).

> **Cache-hit cost semantics:** semantic-cache HIT-இல் (`X-OmniRoute-Cache-Hit: true`) upstream call எதுவும் செய்யப்படாது; எனவே `X-OmniRoute-Response-Cost` என்பது `0.0000000000` (அந்த hit-ஐ வழங்குவதற்கான **incremental** cost). முதலில் இருந்த/இருந்திருக்கக்கூடிய cost தனியாக `X-OmniRoute-Cost-Saved` இல் தெரிவிக்கப்படும். Billing consumers `X-OmniRoute-Response-Cost`-ஐ கூட்ட வேண்டும் (hits-க்கு எந்தச் செலவும் இல்லை); cache analytics `X-OmniRoute-Cost-Saved`-ஐத் தொகுக்கலாம்.

## பிரத்தியேக நிர்வகிக்கப்படும் அமர்வு குத்தகைகள்

பிரத்தியேக நிர்வகிக்கப்படும் அமர்வு குத்தகை என்பது விருப்பத்தேர்வாகப் பயன்படுத்தக்கூடிய, கிளையன்ட்-நடுநிலை வழிமுறை ஒப்பந்தமாகும்: ஒரு செயலில் உள்ள உரிமையாளர், தகுதியான ஒரு OmniRoute இணைப்பை வைத்திருப்பார். இது ஒரு மாதிரியை குத்தகைக்கு விடாது, OAuth-ஐக் கோராது, குறிப்பிட்ட கிளையன்ட்டை அடையாளம் காணாது, குறிப்பிட்ட வழங்குநரையும் கட்டாயப்படுத்தாது.

அங்கீகரிக்கும் API விசையில் `lease:exclusive` வரம்பும், காலியாக இல்லாத வெளிப்படையான
`allowedConnections` பட்டியலும் இருக்க வேண்டும். விசை உருவாக்கம் மற்றும் பகுதி புதுப்பிப்புகளின்போது, தரவுத்தள மாற்ற எல்லை இந்த இரு புலங்களும் ஒன்றாக இருப்பதை அமல்படுத்துகிறது.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

வெற்றிகரமான acquire, renew, release பதில்கள் நேர முத்திரைகள், `state`, மற்றும் சரியான நேர்மறை
`generation` ஆகியவற்றை வெளிப்படுத்தும்; ஆனால் தேர்ந்தெடுக்கப்பட்ட இணைப்பு அல்லது நற்சான்றிதழ்களை ஒருபோதும் வெளிப்படுத்தாது. Renew மற்றும் release செயல்கள் JSON உடலில் generation-ஐ வழங்கும்:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

செயலில் உள்ள குத்தகை உரிமையாளர், தனது தற்போதைய பிணைப்புக்கான தனியுரிமை-பாதுகாப்பான காட்சித் தரவை வெளிப்படையாகக் கோரலாம்:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

இந்த விருப்பத்தேர்வு status செயலானது, ஒரு தரவுத்தள பரிவர்த்தனையில் opaque உரிமையாளர், அங்கீகரிக்கப்பட்ட managed API விசை, மற்றும் சரியான செயலில் உள்ள generation ஆகியவற்றால் பாதுகாக்கப்படுகிறது. `displayName` என்பது கட்டமைக்கப்பட்ட இணைப்பின் trim செய்யப்பட்ட பெயர் மட்டுமே; பாதுகாப்பாகப் பயன்படுத்தக்கூடிய கட்டமைக்கப்பட்ட பெயர் இல்லாதபோது அது `null` ஆகும். OmniRoute ஒருபோதும் மின்னஞ்சல் அல்லது உருவாக்கப்பட்ட கணக்கு அடையாளத்தை மாற்றாகப் பயன்படுத்தாது. provider மதிப்பு, முக்கியத் தகவல் இல்லாத காட்சிப் பெயராகும்; அது ஒருபோதும் உருவாக்கப்பட்ட compatible-provider அடையாளங்காட்டியாக இருக்காது. நற்சான்றிதழ்கள், டோக்கன்கள், குக்கீகள், மூல இணைப்பு அல்லது API key id-கள், உரிமையாளர் hash-கள், fencing secrets, மற்றும் உள் வழிமுறைத் தரவு ஆகியவை விலக்கப்பட்டுள்ளன.

தவறான key, தவறான உரிமையாளர், காலாவதியான generation, காணாமற்போன, காலாவதியான, வெளியிடப்பட்ட, மற்றும் invalidated lookup-கள் அனைத்தும் இணைப்பு metadata இல்லாமல் ஒரே `409 LEASE_FENCE_STALE` பிழையைத் திருப்பி அனுப்பும். capacity-wait பதிலைப் பெற்ற கிளையன்ட்டிடம் ஆய்வு செய்யக்கூடிய செயலில் உள்ள binding இருக்காது. வழிமுறை செயலில் உள்ள குத்தகையை மாற்றும்போது, அதே generation செல்லுபடியாகத் தொடரும்; status அணுவியல் முறையில் புதிய binding-ஐத் திருப்பி அனுப்பும், பழைய binding-ஐ ஒருபோதும் அல்ல. acquire, renew, release, மற்றும் waiting பதில்கள் தங்களின் முந்தைய வடிவங்களிலேயே தொடர்வதால், ஏற்கனவே உள்ள கிளையன்ட்கள் மாற்றமின்றி செயல்படும்.

இந்த server contract, stock OpenAI Codex `/status`-ஐ மாற்றாது. Stock Codex தற்போது அதன் மாதிரி வழங்குநரையும் உள்ளமைக்கப்பட்ட அங்கீகாரம்/கணக்கு நிலையையும் தெரிவிக்கிறது; ஆனால் தன்னிச்சையான custom provider கணக்கு metadata-வை வழங்காது. பின்னர் உருவாகும் client integration இந்தச் செயலியை அழைத்து, `connection.displayName`-ஐ எவ்வாறு காட்சிப்படுத்துவது என்பதைத் தீர்மானிக்க வேண்டும்.

ஒவ்வொரு managed inference request-உம் பின்வரும் இரு control headers-ஐ வழங்கும்:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ஒவ்வொரு ஆதரிக்கப்படும் upstream முயற்சிக்கும் உடனடியாக முன், சரியான owner, generation, active connection, மற்றும் authenticated API key ஆகியவை fence செய்யப்படும். வேறு ஒரு key-யுடன் owner மற்றும் generation-ஐ மீண்டும் பயன்படுத்தினால், அந்த key-க்கும் அதே connection-ஐப் பயன்படுத்த அனுமதி இருந்தாலும் தோல்வியடையும். Raw owners சேமிக்கப்படவோ, log செய்யப்படவோ, request snapshot-ல் வைத்திருக்கப்படவோ, upstream-க்கு அனுப்பப்படவோ மாட்டார்கள்.

தற்காலிகப் போட்டி HTTP `429` உடன் `Retry-After` மற்றும் பின்வரும் பதிலைத் திருப்பி அனுப்பும்:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

இந்தப் பதில், வழக்கமான தகுதியான தொகுப்பு காலியாக இல்லை என்றும், கிடைக்கக்கூடிய ஒவ்வொரு இணைப்பும் வேறு ஒரு செயலில் உள்ள குத்தகையால் பிடிக்கப்பட்டிருந்தது என்றும் மட்டுமே குறிக்கும். ஆதரிக்கப்படாத மாதிரிகள்/வழங்குநர்கள், policy mismatch, cooldown, quota, health, மற்றும் பிற வழக்கமான தகுதி தோல்விகள், ஏற்கனவே உள்ள OmniRoute பதில்களையே தொடர்ந்து பயன்படுத்தும்.

### `x-omniroute-compression`

ஒவ்வொரு request-க்குமான compression திட்ட override. அதிகபட்ச முன்னுரிமை — routing-combo
override, active profile, auto-trigger, மற்றும் panel Default ஆகியவற்றை மிஞ்சும். மதிப்புகள்:

| மதிப்பு       | விளைவு                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `off`         | இந்த request-க்கு compression இல்லை.                                                                                |
| `default`     | panel-இலிருந்து பெறப்பட்ட Default profile (active profile புறக்கணிக்கப்படும்). Lossy engines செயலிழந்தே இருக்கும்.  |
| `safe`        | Dedup மற்றும் whitespace folding மட்டும்.                                                                           |
| `allow-lossy` | summaries மற்றும் style rewrites உட்பட, இந்த request-க்கான operator plan-ஐத் தொடரும்.                               |
| `engine:<id>` | இயக்கப்பட்டிருக்கும் போது ஒரு engine மட்டும், எ.கா. `engine:rtk`. அந்த engine-க்கான ஒவ்வொரு request-க்குமான opt-in. |
| `<combo>`     | பெயரால் முதலில் (case-insensitive), பின்னர் id-ஆல் பொருத்தப்படும் named combo.                                      |

குறிப்புகள்:

- அறியப்படாத மதிப்புகள் புறக்கணிக்கப்படும் (request ஒருபோதும் நிராகரிக்கப்படாது); resolution வழக்கமான operator precedence-க்கு தொடர்ந்து செல்லும்.
- பல combos ஒரே பெயரைப் பகிர்ந்தால், தீர்மானமான match-க்காக combo **id**-ஐ அனுப்பவும்.
- `off` அல்லது `default` என்ற பெயரைக் கொண்ட combo-வை பெயரால் தேர்ந்தெடுக்க முடியாது (அந்த keyword-கள் முதலில் பொருள் கொள்ளப்படும்); அத்தகைய combo-வை அதன் id மூலம் குறிப்பிடவும்.
- master compression switch ஒரு கடுமையான gate: compression உலகளவில் முடக்கப்பட்டிருக்கும்போது, இந்த header அதை இயக்க முடியாது.

பயன்படுத்தப்பட்ட plan, response header-ல் மீண்டும் வழங்கப்படும்:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

இங்கு `<source>` பின்வருவனவற்றில் ஒன்றாக இருக்கும்: `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, அல்லது `off`.

## உட்பொதிவுகள்

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

கிடைக்கும் வழங்குநர்கள்: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

கேட்டலாக் ஐடிகள் `provider/model` வடிவில் இருக்கும் (எடுத்துக்காட்டு: `jina-ai/jina-embeddings-v5-omni-small`). பதிவேட்டில் தோன்றும் bare Jina model ids (எடுத்துக்காட்டாக `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ஆகியவையும் resolve செய்யப்படும். Jina embed/rerank/classify/segment ஆகியவை முதலில் dashboard `jina-ai` credentials-ஐப் பயன்படுத்தும்; dashboard key எதுவும் இல்லாதபோது மட்டும் `JINA_AI_API_KEY` fallback ஆகும். `jina-reader` card என்பது Reader / `r.jina.ai` க்கு மட்டுமே (`POST /v1/web/fetch`); embeddings அல்லது rerank சேவைகளை ஒருபோதும் வழங்காது.

Multimodal ஆதரவை அறிவிக்கும் பதிவேட்டு மாதிரிகள், provider-neutral கட்டமைக்கப்பட்ட உருப்படிகள் 32 வரை ஏற்றுக்கொள்ளும். Media item வகைகள் `text`, `image`, `audio`, `video`, மற்றும் `document` ஆகும். அவற்றின் media `source` என்பது `{"type":"url","url":"https://..."}` அல்லது `{"type":"base64","data":"...","media_type":"..."}` ஆக இருக்கும்.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`, மற்றும் family alias `jina-ai/jina-embeddings-v5-omni` → omni-small) ஆகியவையும் Jina-வின் native EmbeddingsV5Request docs-ஐ ஏற்றுக்கொண்டு, அவற்றை மாற்றமின்றி `https://api.jina.ai/v1/embeddings` க்கு **அனுப்புகின்றன**:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Native `{ image | audio | video | pdf }` மதிப்புகள் public HTTPS URL, `data:` URI அல்லது raw base64 ஆக இருக்கலாம். OmniRoute அந்த objects-ஐ string ஆக மாற்றாது அல்லது native image URLs-ஐ fetch செய்யாது — Jina தானாகவே public media-ஐ retrieve செய்யும். கூடுதல் Jina fields (`task`, `normalized`, `truncate`, `embedding_type`) அனுப்பப்படும். Text-only Jina SKUs, text அல்லாத docs-ஐ இன்னும் நிராகரிக்கும்.

பாதுகாப்பு மற்றும் போக்குவரத்து வரம்புகள்:

- Remote media URLs public HTTPS ஆக இருக்க வேண்டும். Canonical `{type,source:url}` items server-side-ல் fetch செய்யப்படும் (redirect revalidation, timeout, size limits, public DNS, connection pinning), மேலும் provider call-க்கு முன் inline செய்யப்படும். Jina-native `{image:"https://..."}` items அதே public-HTTPS சரிபார்ப்புக்குப் பிறகு அப்படியே அனுப்பப்படும்; URL-ஐ Jina fetch செய்யும்.
- Inline base64 media ஒவ்வொரு item-க்கும் decoded நிலையில் 8 MiB-க்கும், request முழுவதும் decoded நிலையில் 16 MiB-க்கும் வரையறுக்கப்பட்டுள்ளது.

Provider translation (canonical items ஒருபோதும் மாற்றமின்றி அனுப்பப்படாது):

- Jina multimodal models: ஒவ்வொரு top-level item-மும் data URIs பயன்படுத்தும் modality-keyed object (`text` / `image` / `audio` / `video` / `pdf`) ஆக மாறும்; ஒவ்வொரு top-level item-க்கும் ஒரு vector உருவாகும்.
- Gemini Embedding 2 family: ஒரு top-level array, `content.parts` (`text` அல்லது `inline_data`) கொண்ட ஒற்றை native `models/{model}:embedContent` request ஆக மாறும்.
- llama.cpp (`llama-cpp/<model>`, local server ஏற்றிய எந்த model-மும்): canonical `text` items plain strings ஆகவும், `image` / `audio` / `video` items ஒவ்வொன்றும் `{"content": [part]}` object ஆகவும் மாறும். இவை llama-server-ன் chat content parts (`image_url`, `input_audio` with format `wav` / `mp3` / `flac`, `input_video`) மற்றும் inline data-ஐப் பயன்படுத்தும்; ஒவ்வொரு top-level item-க்கும் ஒரு vector உருவாகும். `document` ஆதரிக்கப்படாது. Server `--embedding --mmproj …` உடன் இயங்க வேண்டும்; projector இல்லையெனில் media-ஐ அது தானாகவே நிராகரிக்கும்.
- Explicit modality metadata இல்லாத அறியப்படாத/dynamic models, structured input-ஐ HTTP 400 உடன் நிராகரிக்கும்.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

ஆதரிக்கப்படாத model/modality சேர்க்கைகள், item-ஐ கட்டாயமாக மாற்றுவதற்குப் பதிலாக HTTP 400 ஐத் திருப்பும். Legacy string/token requests-இல் உள்ள input அல்லாத extension fields, தொடர்ந்து மாற்றமின்றி அனுப்பப்படும்.

```bash

GET /v1/embeddings
```

Azure Document Intelligence-ன் `analyze` API ஒத்திசைவற்றதாகும்: தொடக்கக் கோரிக்கை body-க்குப் பதிலாக
`Operation-Location` header-ஐத் திருப்பி வழங்கும்; மேலும், முடிவைப் பெற poll செய்ய வேண்டும். handler
(`open-sse/handlers/ocr.ts`), அந்த URL-ஐ ஒவ்வொரு வினாடியும் அதிகபட்சம் 30 முயற்சிகளுக்கு poll செய்யும்; `ok` அல்லாத poll பதில் அல்லது `"failed"` status ஏற்பட்டால், உடனடியாகத் தோல்வியடையும் (poll செய்வதைத் தொடராது); மேலும், முயற்சி வரம்பு முடிந்த பிறகும் operation இயங்கிக்கொண்டிருந்தால் `504`-ஐத் திருப்பி வழங்கும். இறுதி Azure பதில்,
caller-க்குத் திருப்பி வழங்கப்படுவதற்கு முன், Mistral பயன்படுத்தும் அதே `pages`/`markdown` வடிவத்திற்கு
இயல்பாக்கப்படும்; ஆகவே client code-ல் வழங்குநருக்கேற்ப தனிப்பட்ட செயலாக்கம் தேவையில்லை.

### Vertex AI DeepSeek OCR auth and endpoint resolution

`vertex-deepseek-ocr`, chat/image traffic-க்காக OmniRoute ஏற்கனவே ஆதரிக்கும் அதே Vertex AI authentication-ஐ மீண்டும் பயன்படுத்துகிறது
(`open-sse/executors/vertex.ts`): connection-ன் API key, Service Account JSON credential ஆக இருந்து JWT-bearer
flow மூலம் குறுகிய கால OAuth access token-ஆக மாற்றப்படலாம், அல்லது ஏற்கனவே உருவாக்கப்பட்ட OAuth access token
அப்படியே பயன்படுத்தப்படலாம். upstream endpoint URL, connection-ன் project மற்றும் region-இலிருந்து உருவாக்கப்படும் Vertex-ன்
பொதுவான `openapi/chat/completions` partner endpoint ஆகும் — வெளிப்படையாக வழங்கப்படும்
`providerSpecificData.project`/`providerSpecificData.region` எப்போதும் முன்னுரிமை பெறும்; இல்லையெனில் project,
Service Account JSON-ன் `project_id`-இலிருந்து பெறப்படும்; region, `us-central1` ஆக இயல்புநிலைப்படும். இரண்டு தீர்மானங்களும்
`open-sse/handlers/ocr.ts` (`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) இல் நடைபெறும்; மேலும்
`handleOcr`-க்கு dispatch செய்வதற்கு முன் `src/app/api/v1/ocr/route.ts` மூலம் பயன்படுத்தப்படும்.

### மாடல் விலைகள் (`pricing`)

OmniRoute-க்கு மாடலின் விலை தெரிந்திருக்கும்போது, ஒரு பதிவில் `pricing` பொருள் இருக்கும். இந்த விலை,
செலவுக் கணக்கீடு பயன்படுத்தும் விலை அட்டவணையிலிருந்து வருகிறது: உள்ளமைக்கப்பட்ட இயல்புநிலைகள், ஒத்திசைக்கப்பட்ட விலைகள் மற்றும்
`/api/pricing` மூலம் அமைக்கப்பட்ட மேலெழுதல்கள். இவை பட்டியல் விலைகள் என்பதால், சந்தா வழங்குநர்களுக்கும் ஒரு டோக்கனுக்கான விலை காட்டப்படும்.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| புலங்கள்                                                        | அலகு                          | குறிப்புகள்                                                                                                                                                                                 |
| --------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | ஒரு டோக்கனுக்கு USD, தசம சரம் | OpenRouter-உடன் இணக்கமானது; exponent குறியீட்டில் ஒருபோதும் இருக்காது. cache விலை இருக்கும்போது மட்டுமே இரண்டு cache புலங்களும் தோன்றும்.                                                   |
| `input`, `output`, `cached`, `cache_creation`                   | 1M டோக்கனுக்கு USD, எண்       | முந்தைய catalog பதிப்புகளிலிருந்து வந்த புலங்கள்; ஏற்கனவே உள்ள client-களுக்காக வைத்திருக்கப்படுகின்றன. விலை வரிசையில் அவை இருந்தால் `reasoning` மற்றும் `long_context` ஆகியவையும் தோன்றும். |

- **சேர்க்கைகள்** அவற்றின் முதல் காணக்கூடிய இலக்கின் விலையை ஏந்தும். உள்ளமைக்கப்பட்ட `auto/*` சேர்க்கைகள்
  கோரிக்கை நேரத்தில் இலக்கைத் தேர்ந்தெடுப்பதால், அவற்றில் `pricing` இருக்காது.
- **இலவச மாடல்கள்** அவற்றின் விலை பூஜ்ஜியமாக இருக்கும்போது `"0"` (மற்றும் `0`) எனக் காட்டப்படும். விலை வரிசை இல்லாத
  ஒரு மாடலையும் catalog இலவசமாகக் குறித்திருந்தால் (`free: true`) அல்லது உள்ளமைக்கப்பட்ட இலவச-மாடல் catalog-ல்
  பட்டியலிட்டிருந்தால், அது `"0"` எனக் காட்டப்படும்.
- **தெரியாத விலை:** அந்தப் பதிவில் `pricing` விசை இருக்காது.
- **Credit-metered வழங்குநர்கள்** (Kiro போன்றவை) ஒரு டோக்கனுக்கு பதிலாக ஒவ்வொரு கோரிக்கைக்கும் கட்டணம் வசூலிப்பார்கள். அவர்களின்
  பதிவுகளில் முன்பு இருந்த 1M-க்கு-ஒரு numeric புலங்கள் தொடரும்; ஒரு டோக்கனுக்கான string புலங்கள் இருக்காது.
- **மாறுபாடுகள்** (reasoning-effort ids, no-thinking aliases, discovery மற்றும் gateway mirrors)
  அவை வழிமாற்றும் மாடலின் விலையை நகலெடுக்கும்.
- இந்தப் புலங்கள் அடிப்படை விகிதங்களை மட்டுமே ஏந்தும். நீண்ட-சூழல் அடுக்குகள் (numeric `long_context` புலம்) மற்றும்
  service-tier பெருக்கிகள் (எடுத்துக்காட்டாக Codex fast அல்லது flex) `prompt` அல்லது
  `completion`-ஐ மாற்றாது.
- Anthropic-பாணி கோரிக்கையில் `x-api-key` மற்றும் `anthropic-version` பயன்படுத்தப்படுவது உட்பட, ஒவ்வொரு authentication முறைக்கும்
  பொருள் ஒன்றே (பதில் `{ "object": "list", "data": [...] }` ஆகவே இருக்கும்). செயலாக்கம்: `src/app/api/v1/models/catalogPricing.ts`.

### மாடல் id முன்னொட்டுகள் (`?prefix=`)

பெரும்பாலான மாடல்கள் **வழங்குநர் முன்னொட்டு** ஒன்றின் கீழ் விளம்பரப்படுத்தப்படுகின்றன. எந்த முன்னொட்டைப் பெறுகிறீர்கள் என்பது
`MODELS_CATALOG_PREFIX_MODE` feature flag மூலம் கட்டுப்படுத்தப்படுகிறது; மேலும் ஒவ்வொரு கோரிக்கைக்கும் **தனித்தனியாக** query parameter மூலம்
மேலெழுதலாம் — அனைவருக்குமான server-wide அமைப்பை மாற்றாமல், சுத்தமான பட்டியலை விரும்பும் client-க்கு இது பயனுள்ளதாகும்:

```bash
GET /v1/models?prefix=alias        # ஒவ்வொரு மாடலுக்கும் ஒரு id — குறுகிய alias முன்னொட்டு
GET /v1/models?prefix=dual         # இரு வடிவங்களும் (server இயல்புநிலை)
GET /v1/models?prefix=canonical    # முழுமையான provider-id முன்னொட்டு மட்டும்
```

| Mode        | Emits                                                     | குறிப்புகள்                                                                                                                                                                                                       |
| ----------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **and** `claude/claude-sonnet-4-6` | **இயல்புநிலை.** இரு id-களும் ஒரே மாடலுக்குச் செலுத்தும்; இரு வடிவங்களில் ஏதேனும் ஒன்றை hardcode செய்த client அமைப்புகள் தொடர்ந்து செயல்படுவதற்காக வைத்திருக்கப்படுகின்றன. catalog தோராயமாக இரட்டிப்பாகும்.        |
| `alias`     | `cc/claude-sonnet-4-6`                                    | ஒவ்வொரு மாடலுக்கும் ஒரு பதிவு. தனித்த alias இல்லாத வழங்குநர்களும் தங்கள் பதிவை வெளியிடுவார்கள்; எனவே எதுவும் இழக்கப்படாது.                                                                                        |
| `canonical` | `claude/claude-sonnet-4-6`                                | முழுமையான provider-id முன்னொட்டின் கீழ் ஒவ்வொரு மாடலுக்கும் ஒரு பதிவு. தனித்த alias இல்லாத வழங்குநர்கள் (எ.கா. `antigravity/…`, `agy/…`) தங்கள் ஒற்றை id-யையும் இங்கே வெளியிடுவார்கள்; எனவே எதுவும் இழக்கப்படாது. |

`dual`-mode mirror-ஐ query parameter இல்லாமலும் அடையாளம் காணலாம்: அதில் primary id-ஐச் சுட்டும் `parent`
புலம் இருக்கும்.

மாடல் தேர்வியை வழங்கும் client-கள் `?prefix=alias`-ஐக் கோர வேண்டும் — இதையே
[OmniCopilot VS Code extension](../guides/VSCODE-COPILOT.md) செய்கிறது.

### Discovery வடிகட்டிகள் (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` opt-in discovery வடிகட்டிகளை ஏற்கிறது. இவற்றில் எதுவும் இல்லாமல் இருந்தால் பதில்
மாறாது. இவை caller ஏற்கனவே காணும் catalog-ஐக் குறுக்கும் (API-key permissions முதலில் பயன்படுத்தப்படும்),
மேலும் OpenAI-பாணி `limit` / `after` paging-க்கு முன்பாக இயங்கும்:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # பட்டியலிடப்பட்ட ஒவ்வொரு capability-யும் true ஆக இருக்க வேண்டும்
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # catalog `type`; ஒன்று இல்லாத rows `chat` ஆகும்
GET /v1/models?q=sonnet&limit=10                           # id அல்லது name-இல் case-insensitive பொருத்தம்
```

| அளவுரு        | மதிப்புகள்                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | எதிர்மறையற்ற முழு எண், `context_length` உடன் ஒப்பிடப்படுகிறது                                       |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 எழுத்துகள்                                                                                    |

தெரியாத மதிப்பு அல்லது எதிர்மறையற்ற முழு எண்ணாக இல்லாத `min_context` (எடுத்துக்காட்டாக `1.5`) இருந்தால்,
HTTP `400` திருப்பி அனுப்பப்பட்டு, செய்தியில் செல்லுபடியாகும் மதிப்புகள் பட்டியலிடப்படும். செயல்படுத்தல்:
`src/app/api/v1/models/catalogFilters.ts`.

### மாதிரி குறும்பட்டியல் (`POST /v1/models/query`)

`POST /v1/models/query`, `GET /v1/models` போன்ற அதே அட்டவணையிலிருந்து, அதே
அங்கீகாரம் மற்றும் ஒரு விசைக்கான தெரிவுநிலையுடன், குறுகிய மற்றும் தீர்மானிக்கக்கூடிய பட்டியலைத் திருப்பி அனுப்புகிறது:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ஒவ்வொரு புலமும் விருப்பமானது. `capabilities` மற்றும் `exclude` ஆகியவை ஒரு வரிசை அல்லது காற்புள்ளியால் பிரிக்கப்பட்ட சரத்தை ஏற்கின்றன;
`max_output`, `max_output_tokens` உடன் ஒப்பிடப்படுகிறது. முடிவுகள் முதலில் `owned_by`, பின்னர் `id` அடிப்படையில் வரிசைப்படுத்தப்படுகின்றன.
`limit` என்பதன் இயல்புநிலை `20`; `100`-ஐ விட அதிகமான மதிப்புகள் `100` ஆகக் கட்டுப்படுத்தப்படும். தவறான JSON, தெரியாத
புலம் அல்லது தவறான மதிப்பு இருந்தால் HTTP `400` திருப்பி அனுப்பப்படும்.

### தனித்தனியாக மறைக்கப்பட்ட chat மாதிரிகள்

வழங்குநர் பக்கத்தில் **மறைக்கப்பட்டது** என்று குறிக்கப்பட்ட மாதிரி அட்டவணையிலிருந்து விலக்கப்பட்டு,
வெளிப்படையாகக் கோரப்படும்போது HTTP `404` / `model_not_found` உடன் நிராகரிக்கப்படும். இந்தச் சரிபார்ப்பு
தீர்மானிக்கப்பட்ட வழங்குநர் மற்றும் மாதிரியைப் பயன்படுத்துகிறது; இதில் வழங்குநர் மாற்றுப்பெயர்கள்,
இணக்கமான வழங்குநர் முனைய முன்னொட்டுகள் மற்றும் இணைப்பு இயல்புநிலைகள் ஆகியவையும் அடங்கும். ஒரு combo
மறைக்கப்பட்ட இலக்குகளைத் தவிர்த்து, தெரிவுநிலையில் உள்ள சகோதர மாதிரியைப் பயன்படுத்தலாம்; செயல்படுத்தக்கூடிய
இலக்கு எதுவும் மீதமில்லாதபோது அதே பிழைக் குறியீட்டைத் திருப்பி அனுப்பும். மறைநிலையை நீக்கியது அடுத்த
கோரிக்கையில் நடைமுறைக்கு வரும். படங்களுக்கு மட்டும் பொருந்தும் தெரிவுநிலை மேலெழுத்துகள், அதே ID கொண்ட
chat மாதிரியை மறைக்காது.

இந்தத் தனிப்பட்ட மாதிரி அமைப்பு
[மாதிரி வெளிப்படுத்தல் அனுமதி/மறுப்பு பட்டியல்களிலிருந்து](../routing/MODEL_EXPOSURE_LIST.md) தனித்துவமானது;
அவை அட்டவணை விளம்பரத்தையும் தானியங்கி வழிச்செலுத்தல் வேட்பாளர்களையும் வடிகட்டுகின்றன, ஆனால்
வெளிப்படையான அனுப்புதலைத் தக்கவைத்துக் கொள்கின்றன. API விசைக்கான மாதிரி அனுமதிகள் தொடர்ந்து
தனித்தனியாகப் பயன்படுத்தப்படும். இயல்புநிலை அட்டவணை முன்னொட்டு முறை `dual` ஆகவே இருக்கும்.

### சிந்தனையற்ற மாதிரி மாறுபாடுகள்

சிந்தனைத் திறன் கொண்ட Claude மாதிரிகளுக்கு, `/v1/models` `no-thinking` மாறுபாட்டையும் விளம்பரப்படுத்துகிறது;
அதன் id, `claude-3-omniroute-no-thinking/` முன்னொட்டைக் கொண்டிருக்கும்:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

இந்த id-ஐத் தேர்ந்தெடுக்கும்போது (எடுத்துக்காட்டாக, எப்போதும் `thinking` தொகுதியை இணைக்கும் Claude Code
கட்டமைப்பில்), அது உண்மையான `<provider>/<model>`-க்கு மீண்டும் தீர்மானிக்கப்பட்டு, reasoning ஒடுக்கப்படும் —
`/v1/messages` பாதையில் `thinking:{type:"disabled"}` அல்லது `/v1/chat/completions` பாதையில்
`reasoning`/`reasoning_effort` புலங்கள் நீக்கப்படும். சிந்தனையை ஆதரிப்பதுடன் **மேலும்** `disabled`-ஐ
ஏற்றுக்கொள்ளும் Claude குடும்ப மாதிரிகளுக்கு மட்டுமே இந்த மாறுபாடு பட்டியலிடப்படும் (எடுத்துக்காட்டாக,
`disabled`-ஐ நிராகரிக்கும் adaptive-only மாதிரிகள் விலக்கப்படும்). `ModelSpec.noThinkingAlias` வழியாக
ஒவ்வொரு மாதிரிக்கும் இந்த மாறுபாட்டை இயக்கவோ முடக்கவோ இயக்குநர்கள் கட்டாயப்படுத்தலாம்.

## ElevenLabs ஆடியோ உருவாக்கம்

உங்கள் ElevenLabs API key-யுடன் OmniRoute-இல் `elevenlabs` provider connection-ஐ உள்ளமைக்கவும். Clients தங்கள் **OmniRoute** key-யைப் பயன்படுத்தி அங்கீகரிக்கப்படுகின்றன (`Authorization: Bearer $OMNIROUTE_API_KEY`); gateway சேமிக்கப்பட்ட provider key-ஐ `xi-api-key` ஆக வழங்குகிறது. ElevenLabs key-ஐ gateway bearer token ஆக ஒருபோதும் அனுப்ப வேண்டாம்.

| Method | Path                        | Response                                    | API key endpoint category |
| ------ | --------------------------- | ------------------------------------------- | ------------------------- |
| POST   | `/v1/sound-generation`      | Native audio bytes                          | `elevenlabs`              |
| POST   | `/v1/music`                 | Native audio bytes                          | `music`                   |
| POST   | `/v1/music/stream`          | Streaming audio bytes                       | `music`                   |
| POST   | `/v1/music/detailed`        | Native multipart audio and composition plan | `music`                   |
| POST   | `/v1/music/detailed/stream` | Native SSE metadata and audio chunks        | `music`                   |
| POST   | `/v1/music/plan`            | JSON composition plan                       | `music`                   |

இந்த endpoints ஏற்கனவே உள்ள `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` மற்றும் `/v1/speech-to-text` routes-க்கு துணையாக உள்ளன. Native JSON fields
மற்றும் `output_format`, `enable_logging` போன்ற query parameters பாதுகாக்கப்படுகின்றன.
`/v1/music/detailed` பதில்கள் அவற்றின் multipart boundaries-ஐத் தக்கவைத்துக் கொள்கின்றன; அவற்றை multipart ஆகப் parse செய்யவும்.
`/v1/music/detailed/stream` composition metadata மற்றும் SSE events-இல் base64 audio chunks உடன் `text/event-stream`-ஐத் திருப்பி வழங்குகிறது. ஆறு routes-உம் CORS preflight-ஐ ஆதரிக்கின்றன.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# குறுகிய ஒலி விளைவு. கால அளவு: 0.5 முதல் 30 வினாடிகள் வரை.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# இசையின் கால அளவு milliseconds-ல் குறிப்பிடப்படுகிறது: 3000 முதல் 600000 வரை.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

பகுதி பகுதியாக audio delivery வழங்க, அதே JSON body-யுடன் `/v1/music/stream`-ஐப் பயன்படுத்தவும். Composition-க்கு `prompt` அல்லது `composition_plan` ஆகியவற்றில் சரியாக ஒன்றை ஏற்கிறது; `/v1/music/plan`-க்கு `prompt` தேவைப்படுகிறது, மேலும் விருப்பமாக `source_composition_plan`-ஐ ஏற்கிறது. Native schemas கூடுதல் provider fields-ஐப் பாதுகாப்பதால், composition-plan versions மற்றும் fine-tuning options ElevenLabs-ஐ சென்றடைகின்றன.

ஒருங்கிணைந்த `/v1/music/generations` endpoint `elevenlabs/music_v1`,
`elevenlabs/music_v2` மற்றும் `elevenlabs/music_v2_5` ஆகியவற்றையும் ஏற்கிறது. செயலில் உள்ள ElevenLabs connection இருந்தால், இந்த models music catalog-ல் வெளிப்படுத்தப்படுகின்றன. இந்த endpoint
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`-ஐத் திருப்பி வழங்குகிறது. இதன் `duration` field
seconds-ல் உள்ளது, மேலும் `music_length_ms`-க்கு map செய்யப்படுகிறது; வெளிப்படையாக வழங்கப்பட்ட `music_length_ms` முன்னுரிமை பெறுகிறது.
`instrumental` என்பது `force_instrumental`-க்கு map செய்யப்படுகிறது; native field வழங்கப்பட்டிருந்தால் அதற்கு முன்னுரிமை கிடைக்கும்.
Streaming-க்கு native streaming endpoints-ஐயும், composition plan மட்டுமே அடிப்படையாகக் கொண்ட requests-க்கு native composition endpoint-ஐயும் பயன்படுத்தவும்.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Upstream call நடைபெறுவதற்கு முன் endpoint, model, budget மற்றும் connection restrictions செயல்படுத்தப்படுகின்றன. Native
routes upstream status codes மற்றும் error bodies-ஐ எந்த மாற்றமும் இன்றி திருப்பி வழங்குகின்றன; இதில் plan restriction-க்கான `402` மற்றும் quota limit-க்கான `429` ஆகியவையும் அடங்கும். `character-cost`, `song-id`, `request-id` மற்றும் `retry-after`
headers இருந்தால் அவை பாதுகாக்கப்படுகின்றன. Free credit balance இருப்பது ஒவ்வொரு
music model, output format அல்லது API feature-க்கும் அணுகல் கிடைக்கும் என்பதற்கு உத்தரவாதமல்ல: ஒவ்வொரு request-க்குமான entitlement-ஐ ElevenLabs தீர்மானிக்கிறது.
ஒருங்கிணைந்த endpoint error status codes-ஐ OmniRoute-ன் normalized error envelope-ல் பாதுகாக்கிறது.

Upstream contracts: [sound effects](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[music composition](https://elevenlabs.io/docs/api-reference/music/compose) மற்றும்
[streaming music details](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

```bash
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# TTS — audio/mpeg (அல்லது கோரப்பட்ட வடிவம்) body-ஐத் திருப்பியளிக்கும்
```

> **மறுவரிசைப்படுத்தல் வழங்குநர் முனைகள்:** `POST /v1/rerank` ஆனது `<node-prefix>/<model>` எனக் குறிப்பிடப்படும் OpenAI-இணக்கமான வழங்குநர் முனைகளுக்கும் (oMLX, vLLM, Infinity, ஒரு gateway-க்குப் பின்னால் உள்ள TEI, …) வழியிடுகிறது. Loopback முனைகள் (`localhost`, `127.0.0.1`, `172.16.0.0/12`) எப்போதும் தகுதியுடையவை; மேலும் `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`-ல் இயக்குநர் பட்டியலிடும் ஹோஸ்ட் பெயர்களும் தகுதியுடையவை (எ.கா., `http://reranker:8080/v1` போன்ற Docker/Compose சேவைப் பெயர்; இவை நேரடியாக அழைக்கப்படுகின்றன, `HTTP(S)_PROXY` அல்லது இணைப்பில் பொருத்தப்பட்ட proxy வழியாக ஒருபோதும் செல்லாது). வேறு எந்த host-லும் உள்ள முனைகள் — LAN பெட்டி அல்லது Tailscale peer — இயக்குநர் `RERANK_REMOTE_PROVIDER_NODES` feature flag-ஐ இயக்கி, முனையின் base URL வழங்குநர் outbound URL கொள்கையை (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) கடந்து சென்றால் மட்டுமே தகுதியுடையவை. நினைவக இயந்திரத்தின் மறுவரிசைப்படுத்தல் படி இந்த வழித்தடத்தை loopback வழியாக அழைக்கிறது; எனவே Memory அமைப்புகளில் உள்ள `rerankProviderModel`-க்கும் இதே விதி பொருந்தும்.
>
> **உள்ளக சேவையக வடிவங்கள்:** முனை `<base>/v1/rerank` வழியாகவும், 404 ஏற்பட்டால் `<base>/rerank` வழியாகவும் (Infinity, TEI) அழைக்கப்படுகிறது. upstream body-யில் Cohere/OpenAI எழுத்துவடிவம் (`documents`, `return_documents`) மற்றும் TEI எழுத்துவடிவம் (`texts`, `return_text`) இரண்டும் உள்ளன; upstream response ஆனது Cohere envelope-ஆக இயல்பாக்கப்படுகிறது: TEI-யின் bare `[{index, score, text}]`, மெல்லிய gateway-களிலிருந்து வரும் `{results: [{index, score}]}`, மற்றும் Voyage-பாணி `{data: [...]}` ஆகிய அனைத்தும் client-க்கு `{results: [{index, relevance_score, document?}]}` எனத் திரும்புகின்றன; இவை score அடிப்படையில் வரிசைப்படுத்தப்பட்டு `top_n` அளவில் கட்டுப்படுத்தப்படுகின்றன.

> **வழங்குநர்-முனை கண்டறிதல்:** OpenAI-இணக்கமான வழங்குநர் முனையில் உள்ள மாதிரிகள் `GET /v1/models`-ல் முனை prefix-ன் கீழ் தோன்றும். endpoint metadata எதையும் கொண்டிருக்காத வரிசைகள் (உள்ளக `/v1/models` பட்டியல்களில் வழக்கமானவை) முனையின் `apiType`-ஐப் பெறுகின்றன; ஆகவே `embeddings` முனையின் மாதிரிகள் `type: "embedding"` ஆகவும், `rerank` முனையின் மாதிரிகள் `type: "rerank"` ஆகவும் இருக்கும்; இவை இயல்பாக chat ஆக மாறாது. ஒத்திசைக்கப்பட்ட அல்லது கைமுறையாகச் சேர்க்கப்பட்ட வரிசையில் வெளிப்படையான `supportedEndpoints` இருந்தால் அதற்கே முன்னுரிமை வழங்கப்படும்.

## கோப்புகள் API

தொகுதி உள்ளீடு/வெளியீடு மற்றும் கோப்பு-நோக்கப் பதிவேற்றங்களுக்கான OpenAI-இணக்கமான கோப்புகள் endpoint.

| முறை   | பாதை                     | விளக்கம்                                                                                                                         |
| ------ | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | ஒரு கோப்பைப் பதிவேற்றவும் (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — அதிகபட்சம் 512 MiB |
| GET    | `/v1/files`              | அங்கீகரிக்கப்பட்ட API விசைக்கான கோப்புகளைப் பட்டியலிடவும்                                                                        |
| GET    | `/v1/files/[id]`         | கோப்பின் மெட்டாடேட்டாவைப் பெறவும்                                                                                                |
| DELETE | `/v1/files/[id]`         | ஒரு கோப்பை நீக்கவும்                                                                                                             |
| GET    | `/v1/files/[id]/content` | மூலக் கோப்பு உடலை ஸ்ட்ரீம் செய்யவும்                                                                                             |

**அங்கீகாரம்:** Bearer API விசை — `getApiKeyRequestScope` மூலம் கோப்புகள் ஒவ்வொரு API விசைக்கும் தனித்தனியாக வரையறுக்கப்படுகின்றன. ஒரு விசை
தனக்குச் சொந்தமான கோப்புகளை மட்டுமே பார்க்கவும், பதிவிறக்கவும், நீக்கவும் முடியும்; விசையில்லாத டாஷ்போர்டு அமர்வு
முழு நிகழ்வையும் படிக்க முடியும்; உரிமையாளர் இல்லாத கோப்பு (அநாமதேய அல்லது டாஷ்போர்டு-அமர்வு பதிவேற்றம்) ஒவ்வொரு
அமர்வு அல்லாத அழைப்பாளருக்கும் மறுக்கப்படுகிறது. `GET /v1/files`, `REQUIRE_API_KEY=false` ஆக இருந்தாலும், அநாமதேய அழைப்பாளரையும்
தீர்மானிக்க முடியாத வழங்கப்பட்ட விசையையும் `401` பிழையுடன் நிராகரிக்கிறது; அதற்குப் பதிலாக ஒவ்வொரு டெனன்ட்டின் கோப்புகளையும் பட்டியலிடாது
(GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523).

## தேடல் API

வலை/தேடல் வழங்குநர் abstraction (Tavily, Brave, Exa, Serper போன்றவை).

| Method | Path                   | Description                                                                                                |
| ------ | ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| GET    | `/v1/search`           | உள்ளமைக்கப்பட்ட தேடல் வழங்குநர்கள் மற்றும் திறன்களின் பட்டியல்                                             |
| POST   | `/v1/search`           | தேடல் வினவலை இயக்குதல் — உடல் `v1SearchSchema` மூலம் சரிபார்க்கப்படுகிறது; caching/coalescing ஆதரவு உள்ளது |

### Exa மற்றும் Tavily `provider_options`

Exa மற்றும் Tavily, namespace செய்யப்பட்ட bag-இலிருந்து வழங்குநர்-குறிப்பிட்ட புலங்களைப் படிக்கின்றன:
`provider_options.exa` (அல்லது `provider_options["exa-search"]`) மற்றும் `provider_options.tavily`
(அல்லது `provider_options["tavily-search"]`). கீழே உள்ள keys மட்டுமே முன்னோக்கி அனுப்பப்படும். ஒவ்வொன்றும்
`open-sse/handlers/search/providerOptionsPassthrough.ts`-இல் உள்ள தனித்தனி Zod schema-க்கு எதிராகச் சரிபார்க்கப்படுகிறது,
தவறான வகையுடைய key நீக்கப்படும். வேறு எந்த key-யும் புறக்கணிக்கப்படும்; இதில் auth, base URL,
`stream` மற்றும் `outputSchema` ஆகியவையும் அடங்கும். பிற வழங்குநர்களால் பயன்படுத்தப்படும் flat keys (`cx`, `depth`, ...)
முன்பைப் போலவே செயல்படும்.

| Provider | Top-level fields                                                                                                                                                                                                                                                                                                                                                          | Nested                                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (flat primitives), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                              | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` இயல்புநிலை `{ text: true, highlights: true }` மீது merge செய்யப்படும் |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                   |

பொதுவான புலங்கள் எப்போதும் முன்னுரிமை பெறும்: `query`, `max_results`, `filters` (domains), `country` மற்றும்
`search_type`-இலிருந்து பெறப்படும் topic. Exa-வில், `search_type: "news"` ஆனது `category: "news"`-ஐத்
தக்கவைக்கிறது. Tavily, `search_type: "finance"` (`topic: "finance"`) என்பதையும் ஏற்கிறது.

Firecrawl தேடல் செலவு, திருப்பி வழங்கப்பட்ட முடிவுகளின் ஒவ்வொரு தொடங்கிய 10-முடிவுகள் block-க்கும் $0.002 (2
credits) என்ற விகிதத்தில், ஒவ்வொரு அழைப்புக்கும் குறைந்தது ஒரு block என்ற அடிப்படையில் பதிவு செய்யப்படுகிறது
([Firecrawl கட்டண விவரங்கள்](https://docs.firecrawl.dev/billing)): 11 முடிவுகளுக்கு $0.004 செலவாகும்.

பொதுவான `time_range` இப்போது இரு வழங்குநர்களையும் சென்றடைகிறது: Exa-க்கு `startPublishedDate` (ISO
timestamp), Tavily-க்கு `start_date` (`YYYY-MM-DD`) கிடைக்கும். `provider_options`-இல் வெளிப்படையாகக்
குறிப்பிடப்பட்ட தேதி, map செய்யப்பட்ட தேதியை மீறுகிறது.

Exa முடிவுகள் `id`, `highlights` (`snippet`-ஆகப் பயன்படுத்தப்படும் முதல் highlight மட்டும் அல்லாமல், ஒவ்வொரு
highlight-உம்), `highlight_scores`, `summary`, `subpages`, `entities` மற்றும் `extras` ஆகியவற்றை
`provider_raw`-இல் தக்கவைத்துக்கொள்கின்றன. Tavily முடிவுகள் `images` மற்றும் `favicon` ஆகியவற்றைத் தக்கவைத்துக்கொள்கின்றன.

Linkup தேடல் செலவு `depth` `fast` மற்றும் `standard` ஆகியவற்றுக்கு $0.005 ஆகவும், `deep`-க்கு $0.05 ஆகவும்
பதிவு செய்யப்படுகிறது ([Linkup விலை நிர்ணயம்](https://docs.linkup.so/pages/documentation/development/pricing)),
`depth` `provider_options`-இலிருந்து வந்தாலும் அல்லது connection-ன் settings-இலிருந்து வந்தாலும் இதே விதி பொருந்தும்.

Exa `type: "lite"` (Exa 3.0) குறைந்த எண்ணிக்கையிலான புலங்களை மட்டுமே ஏற்கிறது; வேறு ஏதேனும் புலம்
அமைக்கப்பட்டால் முழு request-ஐயும் நிராகரிக்கிறது. lite-க்கு, `additionalQueries`, `systemPrompt` மற்றும்
`contents`-இல் உள்ள `text` மற்றும் `highlights` தவிர்ந்த ஒவ்வொரு key-யும் அழைப்புக்கு முன் நீக்கப்படும்.
நீக்கப்பட்ட `subpages`, `subpageTarget`, `highlights.numSentences` மற்றும் `highlights.highlightsPerUrl`
இனி முன்னோக்கி அனுப்பப்படாது.

செலவுக் கணக்கீடு flat registry `costPerQuery`-ஆகும்; ஆனால் Exa மட்டும் Exa-வின் சொந்த விலை நிர்ணயத்தைப்
பின்பற்றுகிறது: `auto` (மற்றும் legacy `fast`)-க்கு ஒவ்வொரு அழைப்புக்கும் $0.007 அல்லது `lite` (மற்றும்
legacy `instant`)-க்கு $0.004, இது 10 முடிவுகளை உள்ளடக்கியது; அதன் பின்னர் வரும் ஒவ்வொரு முடிவுக்கும்
$0.001; மேலும் `contents.summary` அமைக்கப்பட்டிருந்தால் திருப்பி வழங்கப்படும் ஒவ்வொரு முடிவுக்கும் $0.001.

## Web Fetch API

கட்டமைக்கப்பட்ட web-fetch வழங்குநர் (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) மூலம் URL-இலிருந்து உள்ளடக்கத்தைப் பிரித்தெடுக்கவும்.

Parallel Extract (`parallel-search`, Parallel Search-க்கு பயன்படுத்தப்படும் அதே API key) Markdown-ஐ மட்டுமே
திருப்பி அளிக்கிறது — வேறு எந்த `format` மதிப்பும் `400` பிழையை ஏற்படுத்தும் — மேலும் உள்ளடக்கத்தை 100,000 எழுத்துகளாக வரம்பிடுகிறது. இலக்கு பக்கத்தையே பிரித்தெடுக்க முடியாதபோது, upstream அதை HTTP 200-க்குள் தெரிவிக்கிறது;
OmniRoute அதை நிலையான செய்தியுடன் `422` ஆக வெளிப்படுத்துகிறது.

| Method | Path            | Description                                                                       |
| ------ | --------------- | --------------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | URL-ஐ fetch/scrape செய்கிறது — body `v1WebFetchSchema` மூலம் சரிபார்க்கப்படுகிறது |

**அங்கீகாரம்:** Bearer API key (`extractApiKey` + `isValidApiKey`).

`enforceApiKeyPolicy` மூலம் கொள்கை அமல்படுத்தப்படுகிறது.

**Quota-aware fallback (#8297):** வெளிப்படையான `provider` எதுவும் வழங்கப்படாதபோது, pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) நிலையான
முன்னுரிமை வரிசையில் (fill-first) பரிசோதிக்கப்படுகிறது — rate-limited ஆனாலும் கட்டமைக்கப்பட்ட வழங்குநர், கோரிக்கையை உடனடியாக நிறுத்துவதற்குப் பதிலாகத் தவிர்க்கப்படுகிறார்; மேலும் retry செய்யக்கூடிய/quota சார்ந்த upstream தோல்வி
(HTTP 429 எப்போதும்; Firecrawl/Tavily/TinyFish quota-வகை இலவச அடுக்குகளுக்கு 402/403 —
Jina Reader-க்கு அல்ல, மேலும் சாதாரண 400 தவறான கோரிக்கைக்கு ஒருபோதும் அல்ல) கோரிக்கை நேரத்தில் அடுத்ததாக முயற்சிக்கப்படாத credential கொண்ட வழங்குநரிடம் தொடர்ந்து செல்கிறது. pool-இல் உள்ள ஒவ்வொரு வழங்குநரும் exhausted ஆகும்போது, endpoint முந்தைய பொதுவான `400`-க்குப் பதிலாக
`Retry-After` header உடன் ஒரே ஒரு `429`-ஐத் திருப்பி அளிக்கிறது. வெளிப்படையான `provider` கோரப்பட்டால், அமைதியான fallback எதுவும் இல்லை — rate-limited அல்லது தோல்வியடைந்த வெளிப்படையான வழங்குநர் தனது சொந்தப் பிழையை வெளிப்படுத்துகிறது (rate-limited ஆக இருந்தால் `429`, இல்லையெனில் upstream status).

## WebSocket Streaming

```bash
GET /v1/ws?handshake=1
```

WebSocket upgrade handshake-ஐச் சரிபார்த்து, wire protocol-ன் எடுத்துக்காட்டு செய்திகளை (`request`, `cancel`) திருப்பி அளிக்கிறது. உண்மையான WS frames, Next.js route table-க்கு வெளியே bundled WS server மூலம் கையாளப்படுகின்றன.

**அங்கீகாரம்:** handshake-இன் போது Bearer API key.

### WebSocket வழியாக Responses API (codex மட்டும்)

```bash
# HTTP API-க்கான அதே host:port (இயல்புநிலை 20128); connection-ஐ upgrade செய்யவும்:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (அல்லது: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# முதல் frame கட்டாயம் response.create ஆக இருக்க வேண்டும்:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxy, **`codex`-க்கு மட்டும்** பிரத்தியேகமாக இணைக்கப்பட்டுள்ளது (ChatGPT backend). இது API/dashboard-ன் அதே port-ல் `/v1/responses`,
`/responses`, மற்றும் `/api/v1/responses` paths-ல் கேட்கிறது. முதல் `response.create` frame-இல், இது
உள்புற `codex-responses-ws` bridge வழியாக அங்கீகரித்து + தயார் செய்து, codex OAuth connection-ஐத் தேர்ந்தெடுத்து, `wreq-js` transport மூலம்
`wss://chatgpt.com/backend-api/codex/responses`-க்கு tunnel செய்கிறது. **codex அல்லாத models நிராகரிக்கப்படுகின்றன** (`codex_ws_provider_required`).
Quota-share routing-க்கு `model: "qtSd/<group>/codex/<model>"` பயன்படுத்தவும். இது
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`-ல் செயல்படுத்தப்பட்டுள்ளது.

**அங்கீகாரம்:** handshake-இன் போது Bearer API key. Bundled HTTP server (`server-ws.mjs`)
active entrypoint ஆக இருக்க வேண்டும் (`app/server-ws.mjs` இருக்கும் போது இயல்பாக அதுவே ஆகும்).

#### Model id: bare ChatGPT id-ஐப் பயன்படுத்தவும் (`codex/` prefix இல்லாமல்)

OpenAI **Codex CLI**, `supports_websockets = true` ஆக இருக்கும்போது model name-ஐ client-side-ல் சரிபார்த்து,
`codex/gpt-5.5` போன்ற provider-prefixed ids-ஐ நிராகரிக்கிறது (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Bare id-ஐ (எ.கா. `gpt-5.5`) அனுப்பவும். OmniRoute-ன் bridge codex-only ஆக இருப்பதால், upstream-க்கு tunneling செய்வதற்கு முன், அது bare id-ஐ codex model ஆக
மீண்டும் தீர்மானிக்கிறது (`resolveCodexWsModelInfo`) — HTTP வழியாக bare
`gpt-5.5` வேறு provider-க்கு route ஆகக்கூடியிருந்தாலும்.

#### OpenAI Codex CLI-ஐ கட்டமைத்தல்

WebSocket
support உடன் custom provider-ஐ `~/.codex/config.toml`-ல் சேர்த்து Codex CLI-ஐ OmniRoute-க்கு சுட்டிக்காட்டவும் (ஏற்கனவே உள்ள config-ஐ மாற்றாமல் இருக்க தனி `CODEX_HOME`-ஐப் பயன்படுத்தவும்):

```toml
model = "gpt-5.5"                 # bare id — "codex/gpt-5.5" அல்ல
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # முடிவில் slash வேண்டாம்; WS URL பெறப்படுகிறது (production-ல் https/wss பயன்படுத்தவும்)
wire_api = "responses"                    # Feb 2026 முதல் ஆதரிக்கப்படும் ஒரே மதிப்பு
supports_websockets = true                # Responses-over-WS transport-ஐ இயக்குகிறது
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API key-ஐ (Bearer) வைத்திருக்கும்
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ஒரு OmniRoute API key (REQUIRE_API_KEY=false என்றால் எந்த key-யும் பயன்படுத்தலாம்)
codex exec "Responda apenas: PONG"
```

CLI, `base_url + /responses`-ஐ WebSocket ஆக upgrade செய்து, OmniRoute அதைத் தேர்ந்தெடுக்கப்பட்ட codex OAuth connection-க்கு tunnel செய்கிறது. Local server-க்கு எதிராக end-to-end சரிபார்க்கப்பட்டது: ChatGPT `codex.rate_limits` + `response.created`-ஐத் திருப்பி அளித்து completion-ஐ stream செய்கிறது.

Tickets-ஐ அவற்றை உருவாக்கிய API key மட்டுமே காண முடியும். மீண்டும் இயக்கப்பட்டதன் முடிவு உறுதியற்றதாக இருந்தால், அது இருமுறை அனுப்பப்படுவதற்குப் பதிலாக `needs_confirmation` நிலையில் முடிவடையும். மூலம்: `src/lib/quota/quotaSessionRecovery.ts`.

```bash
  "http://localhost:20128/api/usage/om-usage?format=json"
```

இந்த key-க்கு **`allowUsageCommand`** இயக்கப்பட்டிருக்க வேண்டும் (இயல்புநிலையில் முடக்கப்பட்டுள்ளது — dashboard-இன் API-key manager இதை ஒவ்வொரு key-க்கும் மாற்றுகிறது). இது இல்லையெனில் endpoint `403` பதிலை வழங்கும்.

`?format=json` வேறுபடுத்தப்பட்ட வடிவத்தைத் திருப்பி வழங்குகிறது; எனவே ஒரு caller ஒருபோதும் மறுப்புப் பதிலிலிருந்து data field-ஐப் படிக்காது. வெற்றியடைந்தபோது:

```jsonc
{
  "allowed": true,
  // key தனிப்பட்ட பயன்பாட்டு வரம்புகளை (தினசரி/வாராந்திர USD) தேர்வுசெய்திருந்தால் மட்டுமே இருக்கும்:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // தேர்ந்தெடுக்கப்பட்ட provider-இன் quota snapshot, இதுவரை எதுவும் cache செய்யப்படவில்லை என்றால் null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // ஒவ்வொரு connection-இன் snapshot; இதனால் UI பல provider-களை அருகருகே காட்ட முடியும்:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

மறுப்பின்போது (`401` தவறான key / `403` அனுமதிக்கப்படவில்லை), அதே route
`{ "allowed": false, "error": { "message": "…" } }` என்பதைத் திருப்பி வழங்கும் — காலியாக இருந்தாலும் இருக்கும் `personal`/`provider`
(key அனுமதிக்கப்பட்டது, இதுவரை எதுவும் அறியப்படவில்லை) என்பது மறுப்பிலிருந்து வேறுபட்ட நிலையாகும்; மேலும் JSON வடிவம் மட்டுமே இந்த இரு நிலைகளையும் வேறுபடுத்திக் காட்டுகிறது.

**அங்கீகாரம்:** caller-இன் சொந்த Bearer API key, `isValidApiKey` மூலம் சரிபார்க்கப்படுகிறது — இது _management surface_ (`/api/keys/…`) அல்ல; அது `requireManagementAuth`-க்கு பின்னால் தொடர்ந்தும் இருக்கும்.

### Raw மற்றும் Cutoff-Adjusted ஒதுக்கீட்டு சதவீதங்கள்

`/api/usage/om-usage`-ஐப் பயன்படுத்தும்போது, **plain-text output** மற்றும் கட்டமைக்கப்பட்ட **JSON output** ஆகியவற்றில் காட்டப்படும் சதவீதங்களுக்கு இடையிலான வேறுபாட்டைக் callers கவனிக்க வேண்டும்:

| Aspect               | Plain-text format (`/api/usage/om-usage` / `@@om-usage`)                                                        | JSON format (`?format=json`)                                                                         |
| :------------------- | :-------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------- |
| **Output field**     | `NN% left` (எ.கா., `20% left`)                                                                                  | `provider.quotas` / `providers[].quotas`                                                             |
| **Measurement**      | **Cutoff-adjusted usable allowance**: cutoff threshold-க்கு மேலுள்ள மீதமுள்ள திறன்                              | **Raw upstream quota**: மாற்றப்படாத provider அளவீடு                                                  |
| **Cutoff scaling**   | `effectiveRemainingPercent()` மூலம் அளவிடப்படுகிறது; இதனால் பாதுகாக்கப்பட்ட reserve `0% left` எனக் காட்டப்படும் | இல்லை (provider தெரிவித்த raw snapshot values)                                                       |
| **Threshold data**   | காட்டப்படும் சதவீதத்தில் இணைக்கப்பட்டுள்ளது                                                                     | ஒவ்வொரு connection-க்கும் `quotaWindowThresholds`-இல் (அல்லது server defaults-இல்) சேமிக்கப்படுகிறது |
| **Primary consumer** | Interactive CLIs, terminal prompts, human operators                                                             | Programmatic integrations, dashboards, analytics, billing trackers                                   |

#### Cutoff Adjustment Formula

Upstream exhaustion-ஐத் தடுக்க OmniRoute proactive quota cutoffs-ஐ ஆதரிக்கிறது (connection-இன் `quotaWindowThresholds`, provider defaults அல்லது global resilience settings மூலம் கட்டமைக்கப்படுகிறது). ஒரு quota window-இல் cutoff threshold (எ.கா., `cutoff = 25%`) செயல்பாட்டில் இருக்கும்போது, text renderer மீதமுள்ள allowance-ஐ இவ்வாறு கணக்கிடுகிறது:

- `remaining <= cutoff` என்றால்: `0%`-ஐத் திருப்பி வழங்கும்.
- `remaining > cutoff` என்றால்: `((remaining - cutoff) / (100 - cutoff)) * 100`-ஐத் திருப்பி வழங்கும்.

வடிவமைக்கப்பட்ட text output இதை அருகிலுள்ள முழு எண்ணாக (`Math.round(...)`) round செய்கிறது.

#### விளக்க உதாரணம்

வழங்குநர் சாளரம் **60% மூலப் பயன்பாடு** (அதனால் **40% மூல மீத ஒதுக்கீடு**) மற்றும் அமைக்கப்பட்ட
**25% மீத-ஒதுக்கீட்டு வெட்டு** வரம்புடன் இருப்பதாகக் கருதுக:

| பிரதிநிதித்துவம்              | கணக்கீடு                                           |  மீதம்  |            குறிக்கப்படும் பயன்பாடு            |
| :---------------------------- | :------------------------------------------------- | :-----: | :-------------------------------------------: |
| **மூல JSON (`?format=json`)** | மேல்நிலை snapshot (`quotas[window]`)               | **40%** |                    **60%**                    |
| **உரை வடிவம் (`NN% left`)**   | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (`100 - remaining` எனக் கணக்கிட்டால்) |

- **உரை ஏன் 20% மீதம் எனக் காட்டுகிறது:** கணக்கில் உடலளவில் மீதமுள்ள 40% ஒதுக்கீட்டில், வெட்டு கொள்கையால்
  25% ஒதுக்கப்பட்டுள்ளது. இந்த இணைப்பிற்கான வழியனுப்பலை router நிறுத்துவதற்கு முன், பயன்படுத்தக்கூடிய 75% தலைவாய்ப்பில்
  அழைப்பாளர் 15% மட்டுமே மீதமாகக் கொண்டுள்ளார். அளவிடுதல், வழியனுப்பல் நிறுத்தப்படும் நேரத்திலேயே இணைப்பு
  தீர்ந்துவிட்டதைக் (`0% left`) துல்லியமாகச் சுட்டிக்காட்டுவதை உறுதிசெய்கிறது.
- **JSON ஏன் மூல மதிப்புகளைப் பாதுகாக்கிறது:** JSON payload சரியான வழங்குநர் snapshot-ஐ (`UsageSnapshot`)
  வழங்குகிறது; எனவே வெளிப்புறக் கருவிகள், சேவையகப் பக்க இழப்புள்ள அளவிடல் இல்லாமல், உண்மையான மேல்நிலைப் பயன்பாடு
  மற்றும் இணைப்பு-நிலை `quotaWindowThresholds` ஆகியவற்றை அணுக முடியும்.

#### நுகர்வோர் இடமாற்ற வழிகாட்டி

வெளிப்புற ஒருங்கிணைப்பு (எடுத்துக்காட்டாக, ஒரு editor plugin அல்லது agent extension) முன்பு உரை
endpoint-ஐ (`NN% left`) பிரித்து, பயன்படுத்திய சதவீதத்தை `100 - NN` எனக் கணக்கிட்டிருந்தால், `?format=json`-க்கு
மாறுவதன் பொருள்:

- மூல JSON மதிப்புகளைப் படிப்பது **உண்மையான மேல்நிலைப் பயன்பாட்டை** பிரதிபலிக்கும் (மேலுள்ள எடுத்துக்காட்டில் 60% பயன்படுத்தப்பட்டது).
- ஒருங்கிணைப்பு உரை endpoint-இன் பயன்படுத்தக்கூடிய-அனுமதி பொருளைத் தொடர்ந்து பயன்படுத்த விரும்பினால், இணைப்பு-நிலை
  மேலெழுதல்களுக்கான `quotaWindowThresholds`-ஐப் பயன்படுத்தி, பயனுள்ள மீதமுள்ள சதவீத சூத்திரத்தை client-side-இல் மதிப்பிடலாம்.

## Semantic Cache

```bash
# கேச் புள்ளிவிவரங்களைப் பெறுக
GET /api/cache/stats

# அனைத்து கேச்களையும் அழிக்கவும்
DELETE /api/cache/stats
```

பதில் எடுத்துக்காட்டு:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### தாமதத்தின் தாக்கம்

Semantic cache HIT ஆனது பதிலை **upstream அழைப்பு இல்லாமல்** கேச்சிலிருந்து வழங்குகிறது; எனவே, அறிக்கையிடப்படும் `X-OmniRoute-Response-Latency` மதிப்பு (அசல் upstream தாமதத்தைப் பொருட்படுத்தாமல்) கிட்டத்தட்ட பூஜ்ஜியமாக இருக்கும். தாமத உணர்திறன் கொண்ட கிளையன்ட்கள் (benchmarking, p50/p99 monitoring), பதில் தலைப்பான `X-OmniRoute-Cache-Latency`-ஐச் சரிபார்க்க வேண்டும்:

| மதிப்பு     | பொருள்                                                                  |
| ----------- | ----------------------------------------------------------------------- |
| `synthetic` | பதில் கேச்சிலிருந்து வழங்கப்பட்டது; தாமதம் உண்மையான upstream நேரம் அல்ல |
| _(absent)_  | உண்மையான upstream அழைப்பிலிருந்து பெறப்பட்ட பதில்                       |

### ஒவ்வொரு விசைக்கும் கேச் தவிர்ப்பு

API விசைகள் `cacheDefaultMode` வழியாக semantic cache வாசிப்பிலிருந்து விலகலாம்:

| மதிப்பு  | செயல்பாடு                                                      |
| -------- | -------------------------------------------------------------- |
| `legacy` | இயல்பான கேச் செயல்பாடு (இயல்புநிலை)                            |
| `bypass` | கேச் தேடலை முழுமையாகத் தவிர்த்து, எப்போதும் upstream-ஐ அணுகும் |

விசை உருவாக்கத்தின் போது (`POST /api/keys`) அல்லது புதுப்பிக்கும் போது (`PATCH /api/keys/[id]`) அமைக்கவும்:

```json
{ "cacheDefaultMode": "bypass" }
```

### ஒவ்வொரு கோரிக்கைக்கும் கேச் தவிர்ப்பு

விசை அமைப்புகளைப் பொருட்படுத்தாமல், எந்தக் கோரிக்கையும் கேச்சைத் தவிர்க்கலாம்:

```
X-OmniRoute-No-Cache: true
```

## CLIProxyAPI மேலாண்மை இணக்கத்தன்மை

பயன்பாட்டு டாஷ்போர்டுகள் Claude மற்றும் Codex சந்தா வரம்புகளைப் படிக்க அழைக்கும் மூன்று [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) மேலாண்மை endpoint-களுக்குப் OmniRoute பதிலளிக்கிறது (எடுத்துக்காட்டாக, T3 Code-இன் `cliproxy` usage-limit source). கிளையன்ட்டின் base URL-ஐ OmniRoute-க்கு சுட்டிக்காட்டி, `manage` scope கொண்ட API விசையை அதன் management key ஆகப் பயன்படுத்தவும். வழித்தடங்கள் `/v0/management/*` மற்றும் `/api/v0/management/*` ஆகிய இடங்களில் வழங்கப்படுகின்றன.

| Method | Path                         | விளக்கம்                                                                                                                                                              |
| ------ | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }` வடிவில் Claude மற்றும் Codex OAuth இணைப்புகள். Token-கள் எதுவும் இல்லை                         |
| POST   | `/v0/management/api-call`    | Body `{ auth_index, method, url, header?, data? }`. கணக்கின் token-ஐப் பயன்படுத்தி அனுமதிப்பட்ட ஒரு கோரிக்கையை அனுப்பி, `{ status_code, body }`-ஐத் திருப்பி வழங்கும் |
| POST   | `/v0/management/reset-quota` | Body `{ auth_index }`. ஒரு கணக்கின் இணைப்பு cooldown, model lockout-கள் மற்றும் Codex per-scope cooldown-களை அழிக்கும்                                                |

- `auth_index` என்பது OmniRoute இணைப்பு id ஆகும். `provider` என்பது `claude` அல்லது `codex` ஆகும் (OAuth
  இணைப்புகள் மட்டுமே; `anthropic` API-key provider பட்டியலிடப்படாது). Codex-க்கு,
  `id_token.chatgpt_account_id` சேமிக்கப்பட்ட workspace id ஆகவும், `plan_type` சேமிக்கப்பட்ட plan ஆகவும் இருக்கும்.
- `api-call` ஒரு பொதுவான proxy அல்ல. இது Claude `GET
https://api.anthropic.com/api/oauth/usage` மற்றும் Codex `GET https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` மற்றும்
  `POST .../wham/rate-limit-reset-credits/consume` ஆகியவற்றை மட்டுமே ஏற்கும்; ஒவ்வொன்றும் பொருந்தும்
  provider-ஐச் சேர்ந்த கணக்கிற்காக மட்டுமே அனுமதிக்கப்படும். வேறு எதுவும் upstream-ஐத் தொடர்புகொள்ளாமல்
  `403`-ஐத் திருப்பி வழங்கும். அழைப்பாளரின் `Authorization` header (`$TOKEN$` placeholder உட்பட) புறக்கணிக்கப்படுகிறது: OmniRoute
  இணைப்பின் access token-ஐச் செலுத்தி, அது காலாவதியாகும் நிலையில் இருந்தால் முதலில் refresh செய்து, அனுமதிக்கப்பட்ட
  header-களை மட்டுமே (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`;
  `Accept`, `Content-Type`) முன்னனுப்பும். `Chatgpt-Account-Id` விடுபட்டிருந்தால், சேமிக்கப்பட்ட workspace id இயல்புநிலையாகப் பயன்படுத்தப்படும்.
  கோரிக்கைகள் 15 விநாடிகளுக்குப் பிறகு timeout ஆகும் மற்றும் இணைப்பின் proxy-ஐப் பயன்படுத்தும்.
- `reset-quota` terminal state-களை (banned, expired, credits_exhausted) அப்படியே விட்டுவிடும். அறியப்படாத
  `auth_index` `404`-ஐத் திருப்பி வழங்கும்.

**Auth:** dashboard session அல்லது `manage`-scoped API key தேவைப்படுகிறது; login முடக்கப்பட்டிருந்தாலும் இது அவசியம்
(இந்தப் பாதைகள் `ALWAYS_PROTECTED_API_PATHS`-ல் உள்ளன). Inference-only விசைகளுக்கு `403` கிடைக்கும். மூலம்:
`src/lib/cliproxyCompat/managementApi.ts`.

அதை அழித்து இயல்புநிலையை மீட்டமைக்கிறது. `GET /api/provider-models?provider=<provider>` ஆனது இந்த மதிப்புகளை
`modelOutputOverrides`-இல் வழங்குகிறது; இதில் தனிப்பயன்-மாதிரி வரிசை இல்லாத மாதிரிகளும் அடங்கும். இந்த மேலெழுதல்
runtime `max_output_tokens` திறனைப் பயன்படுத்துகிறது மற்றும் மாதிரி மீண்டும் ஒத்திசைக்கப்பட்டாலும் நீடிக்கிறது. OpenAI-இணக்கமான
வழங்குநர் பக்கம் அதே திருத்து/அழி கட்டுப்பாடுகளை வழங்குகிறது மற்றும் வெளிப்படையான vision ஆதரவு கொண்ட மாதிரிகளைக் குறிக்கிறது.

இணக்கமான வழங்குநர் முனையில், எழுதும் வழித்தடங்கள் (`POST`, `PUT`, `PATCH`, `DELETE` மற்றும்
`/api/provider-models/validate-and-add`) மாதிரி id-ஐ upstream-இன் அடிப்படை id ஆகச் சேமிக்கின்றன: முன்னொட்டு கொண்ட பட்டியலிலிருந்து ஒட்டப்பட்ட id-ல், முனையின் சொந்த முன்னொட்டின் தொடக்க அடுக்குகள் ஏதேனும் இருந்தால் அவை சுருக்கப்படுகின்றன, மேலும் பதில்கள் சேமிக்கப்பட்ட id-ஐ எதிரொலிக்கின்றன. canonical வழங்குநர்களின் slash கொண்ட id-கள் (எ.கா. `nvidia/nemotron-…`) அப்படியே சேமிக்கப்படுகின்றன. `/v1/models` ஒருபோதும் அடுக்கப்பட்ட `<prefix>/<prefix>/<model>` id-ஐ வெளியிடாது.

தனிப்பயன் Chat Completions முனைகள், வெளிப்படையாகக் குறிப்பிடப்பட்ட reasoning opt-out-களை upstream backend-க்கு ஏற்றவாறு மாற்றியமைக்கின்றன. வெற்றிகரமான இணைப்புச் சோதனை, `/models` பதிவில் அங்கீகரிக்கப்பட்ட `owned_by` மதிப்பு இருப்பது நிரூபிக்கப்படும் ஒவ்வொரு துல்லியமான model ID-க்கும் chat-template கட்டுப்பாடுகளைத் தானாகத் தேர்ந்தெடுக்கிறது: `vllm`, `sglang`, அல்லது `llamacpp`.
வெளிப்படையான OpenAI-இணக்கமான wrappers, அசல் model பதிவை nested
`openai` object-க்குள் பாதுகாத்திருக்கலாம்; கண்டறிதல் இத்தகைய envelopes-களில் அதிகபட்சம் மூன்று நிலைகள் வரை தொடர்கிறது. Ownership இல்லாத, அறியப்படாத, அல்லது முரண்படும் ownership கொண்ட models, வழக்கமான OpenAI நடத்தையைத் தொடர்கின்றன. கண்டறிதல் ஏற்கனவே உள்ள catalog request-ஐ மீண்டும் பயன்படுத்துகிறது, completion tokens எதையும் உருவாக்காது, மேலும் connection endpoint மாறும்போது செல்லாததாக்கப்படுகிறது.

இந்த metadata-வை வெளிப்படுத்தாத backend-க்கு நடத்தையை நிலைநிறுத்த, ஏற்கனவே உள்ள partial provider update API-ஐப் பயன்படுத்தவும்:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

அந்த body-ஐ `PUT /api/providers/<connection-id>` உடன் அனுப்பவும். அந்த connection-இல், `none` என்ற வெளிப்படையான reasoning effort, `chat_template_kwargs.thinking=false` மற்றும் `chat_template_kwargs.enable_thinking=false` ஆக அனுப்பப்படுகிறது. Server-side reasoning rule ஒன்று effort-ஐ கட்டாயப்படுத்தாவிட்டால், வெளிப்படையான native template values முன்னுரிமை பெறுகின்றன. தனிப்பயன் OpenAI-இணக்கமான connection ஒன்று Chat Completions body-ஐ dispatch செய்யும் போது மட்டுமே இந்த அமைப்பு பொருந்தும்; Responses requests மற்றும் வழக்கமான providers தங்களுடைய native request வடிவத்தையே வைத்திருக்கும். வழக்கமான OpenAI `reasoning_effort` passthrough-ஐ கட்டாயப்படுத்த `reasoningControl`-ஐ `openai` என அமைக்கவும், அல்லது automatic detection-ஐப் பயன்படுத்த அதை விடுபடுத்தவும்/`null` என அமைக்கவும்.

Claude Code auto-mode classifier requests-ல் வெளிப்படையான reasoning controls எதுவும் இல்லாதபோது, native thinking இயல்புநிலையாக disabled ஆக அமைக்கப்படுகிறது. கண்டறிதல், model names அல்லது completion limits-ஐ அல்லாமல், Claude-format requests-இல் உள்ள classifier-ன் system marker-ஐப் பயன்படுத்துகிறது. வெளிப்படையான body controls, ஆதரிக்கப்படும் effort/thinking headers, routing rules, மற்றும் resolved model effort ஆகியவை தங்களுடைய முந்தைய முன்னுரிமையைத் தொடர்கின்றன. இரு classifier நிலைகளும் தங்களுடைய prompts, completion limits, stop sequences, மற்றும் உண்மையான upstream permission verdicts-ஐப் பாதுகாக்கின்றன; இரண்டாவது நிலை, கோரிய visible reasoning-ஐ சாதாரண உரையாக இன்னும் உருவாக்கக்கூடும்.

#### Model limit-ன் மூலம்

`GET /api/models?withLimits=1` (`true` என்பதும் பொருந்தும்; `0`/`false` அல்லது இதை விடுபடுத்துவது இயல்புநிலை payload-ஐ மாற்றமின்றி வைத்திருக்கும்) ஒவ்வொரு model row-க்கும் `contextWindow`, `maxInputTokens`, `maxOutputTokens` மற்றும் `capsSource` object-ஐச் சேர்க்கிறது. ஒவ்வொரு limit-ஐ வழங்கிய rule-ஐ `capsSource` குறிப்பிடுகிறது; இதனால் ஆச்சரியமளிக்கும் limit (உதாரணமாக, 1M model-ல் 128k) அதன் மூலத்திற்குப் பின்தொடரப்படலாம். தீர்மானிக்கப்பட்ட values-களையே routing பயன்படுத்துகிறது; இந்த flag fields-ஐ மட்டுமே சேர்க்கிறது, எந்த value-ஐயும் மாற்றாது. வேறு எந்த `withLimits` value-மும் `400` உடன் நிராகரிக்கப்படும்.

| `capsSource` value                           | Origin                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------------------ |
| `override:context`                           | நிலைநிறுத்தப்பட்ட context-window override (`model_context_overrides`)          |
| `override:max_input` / `override:max_output` | நிலைநிறுத்தப்பட்ட `max_input_tokens` / `max_output_tokens` capability override |
| `static-authoritative:<provider>/<model>`    | Static authoritative context-window அட்டவணை                                    |
| `synced:<provider>/<model>`                  | models.dev-ல் ஒத்திசைக்கப்பட்ட capability row                                  |
| `registry:<provider>/<model>`                | Provider registry பதிவு                                                        |
| `spec:<model>`                               | Static model spec                                                              |
| `effort-base:` prefix                        | effort-suffixed variant-ன் base model-லிருந்து பெறப்பட்ட row                   |
| `none`                                       | எந்த source-மும் limit-ஐ அறிவிக்கவில்லை (value `null`)                         |

### API விசை அனுமதிகள்

`PATCH /api/keys/{id}` ஏற்கனவே உள்ள விசையின் அனுமதிகளைப் புதுப்பிக்கிறது. ஒவ்வொரு `/api/keys*` வழித்தடத்தையும் போலவே, இதற்கும் மேலாண்மை அங்கீகாரம் தேவைப்படுகிறது ([மேலாண்மை அங்கீகாரம்](../guides/MANAGEMENT-AUTH.md)-ஐப் பார்க்கவும்); inference key தேவையில்லை. நீங்கள் மாற்ற விரும்பும் புலங்களை மட்டும் அனுப்பவும்; அவற்றில் எதுவும் இல்லாத கோரிக்கை `No valid fields to update` என்ற செய்தியுடன் நிராகரிக்கப்படும். ஏற்கப்படும் புலங்கள் `src/shared/validation/schemas/keys.ts`-இல் உள்ள `updateKeyPermissionsSchema` மூலம் வரையறுக்கப்படுகின்றன.

| `/api/db-backups`           | DELETE | தக்கவைப்பு அமைப்புகளின்படி சேமிக்கப்பட்ட காப்புப்பிரதிகளை அகற்று                   |
| `/api/db-backups/export`    | GET    | தரவுத்தளத்தை .sqlite கோப்பாகப் பதிவிறக்கு                                          |
| `/api/db-backups/import`    | POST   | தரவுத்தளத்தை மாற்ற .sqlite கோப்பைப் பதிவேற்று (`?dryRun=true` சரிபார்ப்பு மட்டும்) |

`/api/db-backups/export`, `/api/db-backups/exportAll` மற்றும் `/api/settings/export-json` ஆகியவை
சேமிக்கப்பட்டுள்ள அனைத்து நற்சான்றுகளையும் வழங்குகின்றன; எனவே அவற்றுக்கு டாஷ்போர்டு அமர்வு அல்லது
உள்ளூர் CLI தேவை (அல்லது உள்நுழைவு முடக்கப்பட்டிருக்க வேண்டும்). எந்த வரம்புடைய API key-களும்
மற்றும் `oma_` அணுகல் டோக்கன்களும் `403` பிழையைப் பெறும். மீட்டமைப்புகளுக்கும் இதே வரம்பு பொருந்தும்:
`POST /api/db-backups/import` (`dryRun=true` உட்பட), `POST /api/db-backups` (id மூலம் மீட்டமைத்தல்)
மற்றும் `POST /api/settings/import-json` ஆகியவை செயல்பாட்டிலுள்ள தரவுத்தளம் அல்லது அமைப்புகளை
மாற்றுகின்றன; எனவே இயந்திர நற்சான்றும் அங்கே `403` பிழையைப் பெறும்; `omniroute sync import` உள்ளூர்
CLI நற்சான்றை அனுப்புகிறது. ஆகவே `DELETE /api/db-backups` (சேமிக்கப்பட்ட காப்புப்பிரதிகளை அகற்றுதல்)
மற்றும் `PATCH /api/db-backups` (தக்கவைப்பு அமைப்புகள்: ஒவ்வொரு காப்புப்பிரதிக்குப் பிறகும் தானியங்கி
அகற்றலைச் சேமிக்கப்பட்ட மதிப்புகள் கட்டுப்படுத்துகின்றன) ஆகியவற்றைப் பயன்படுத்தவும். பட்டியலிடுதல்

அங்கீகாரத்தைத் தொடர்கின்றன.

### பதிப்பு மற்றும் வெளியீட்டு சேனல்

```bash
GET /api/system/version
```

Loopback-க்கு மட்டும் கிடைக்கும் மேலாண்மை வழித்தடம் (நிர்வாக அங்கீகாரம்). இயங்கும் பதிப்பு, சமீபத்திய
வெளியிடப்பட்ட பதிப்பு மற்றும் தானியங்கி புதுப்பிப்பு நிலையைத் திருப்பியளிக்கிறது. `releaseChannel` மற்றும் `channels` ஆகியவை
கூடுதல் புலங்கள் (rail 3.8.54); `channel` தனது பொருளைத் தக்கவைத்துக்கொள்கிறது — dashboard updater
பயன்படுத்தும் deployment mode (`npm`, `source` அல்லது `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — இயங்கும் build-இன் npm channel: `-nightly.*` பதிப்புகளுக்கு `nightly`,
  பிற pre-release பதிப்புகளுக்கு (`-rc.*`, `-beta.*`, `-alpha.*`) `next`, `channels.latest`-ஐவிட
  பழைய major-இன் stable பதிப்புக்கு `lts`, இல்லையெனில் `latest`. வெளியிடும் நேரத்தில் npm dist-tag-ஐத்
  தேர்ந்தெடுக்கும் `scripts/release/dist-tag.mjs`-இல் உள்ள அதே விதிகள் இங்கும் பயன்படுத்தப்படுகின்றன.
- `channels` — ஒவ்வொரு dist-tag-இன் வெளியிடப்பட்ட head, `npm view omniroute dist-tags`-இலிருந்து
  (registry HTTP fallback) பெறப்படுகிறது; `latest`-க்குப் பயன்படுத்தப்படும் அதே 10-நிமிட TTL-இல்
  cache செய்யப்படுகிறது. `latest` எப்போதும் இருக்கும் (`latest` புலத்திற்குத் திரும்பும், பின்னர்
  `"unavailable"`); அந்த dist-tag இருந்தால் மட்டுமே `next`, `nightly` மற்றும் `lts` தோன்றும்.
  `Cache-Control: no-cache` கோரிக்கை இரு தேடல்களையும் புதுப்பிக்கும்.

சேனல் மாதிரி (`latest` = 4.0 GA வெளியாகும் வரை v3, `next` = rc, `nightly` = `develop` builds,
`lts` = 4.0 GA-க்குப் பிறகான v3 patches) `docs/ops/RELEASE_STRATEGY.md`-இல் விவரிக்கப்பட்டுள்ளது.

பகுதி நேட்டிவ் வழங்குநரைத் தேர்ந்தெடுக்கிறது (`openai/…`, `deepgram/…`). மற்றொரு விற்பனையாளரின்
மாதிரியை மறுவெளியிடும் கேட்வேகள் தகுதிப்படுத்தப்பட்ட id-ஐப் பயன்படுத்துகின்றன
(`openrouter/deepgram/nova-3`).

**கோரிக்கை:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**பதில்:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**மாதிரி id-களின் எடுத்துக்காட்டுகள்:** `openai/whisper-1` (OpenAI விசை தேவை),
`openrouter/deepgram/nova-3` (OpenRouter விசை தேவை),
`deepgram/nova-3` (நேட்டிவ் Deepgram விசை தேவை). வெறும்
`deepgram/nova-3` கோரிக்கை OpenRouter-ஐப் **பயன்படுத்தாது**.

**ஆதரிக்கப்படும் வடிவங்கள்:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** Gemini Live
WebSocket வழியாக கோப்பு-முறை உரைமாற்றம் செய்யப்படுகிறது (Gemini API விசை தேவை). பதிவேற்றம்
`ffmpeg` மூலம் 16 kHz mono PCM ஆக மாற்றப்படுகிறது
(கோப்பு ஏற்கனவே 16 kHz mono PCM WAV ஆக இல்லாவிட்டால், `PATH`-இல் இருக்க வேண்டும்), பின்னர் அமர்வுக்கு
ஸ்ட்ரீம் செய்யப்பட்டு, இறுதி செய்யப்பட்ட உரை `{ "text": "..." }` ஆகத் திருப்பி அனுப்பப்படுகிறது. விருப்பமான
`language` மற்றும் `prompt` படிவப் புலங்கள் முன்னோக்கி அனுப்பப்படுகின்றன. வரம்புகள்: 25 MiB-ஐ விட அதிகமான
பதிவேற்றங்கள் அல்லது 10 நிமிடங்களுக்கும் அதிகமான நீளம் கொண்ட டிகோட் செய்யப்பட்ட ஆடியோ
`413` பதிலைப் பெறும்; 60 s-ஐ விட நீண்ட நேரம் இயங்கும் மாற்றம் நிறுத்தப்பட்டு `504` பதிலை அளிக்கும். API விசை
`x-goog-api-key` தலைப்பில் மட்டுமே அனுப்பப்படுகிறது; WebSocket URL-இல் ஒருபோதும் அனுப்பப்படாது.

## டோக்கனைஸ் செய்யப்பட்ட VS Code / Header இல்லா மாற்றுப்பெயர்கள்

ஒரு ஒருங்கிணைப்பு `Authorization` header-ஐச் சேர்க்க முடியாதபோது, அடிப்படை URL-இல் API key-ஐ உட்பொதிக்க வேண்டியிருந்தால், இந்த மாற்றுப்பெயர்களைப் பயன்படுத்தவும்.

```bash
# OpenAI-பாணி பட்டியல் மாற்றுப்பெயர்
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-பாணி chat மாற்றுப்பெயர்கள்
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-பாணி மாற்றுப்பெயர்கள்
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

எடுத்துக்காட்டு:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

குறிப்புகள்:

- டோக்கனைஸ் செய்யப்பட்ட மாற்றுப்பெயர்கள் `/v1/*` மற்றும் `/api/tags` ஆகியவற்றின் அதே handler-களை மீண்டும் பயன்படுத்துகின்றன; பதில் வடிவங்கள் மாறாமல் இருக்கும்.
- கிளையண்ட் தனிப்பயன் header-களை ஆதரிக்கும் போதெல்லாம் `Authorization: Bearer ...`-ஐ முன்னுரிமையுடன் பயன்படுத்தவும்.
- URL-அடிப்படையிலான டோக்கன்கள் OmniRoute-க்கு வெளியே உள்ள reverse-proxy பதிவுகள், உலாவி வரலாறு மற்றும் telemetry ஆகியவற்றில் தோன்றக்கூடும். அவற்றை இயல்புநிலை அங்கீகார முறையாக அல்லாமல், இணக்கத்தன்மைக்கான விருப்பமாகக் கருதவும்.

```bash
# அனைத்து API key-களுக்குமான பட்ஜெட் நிலையைப் பெறுக
GET /api/usage/budget

POST /api/usage/budget

{
  "apiKeyId": "key-123",
```

> **Schema குறிப்புகள்** (`setBudgetSchema`): `apiKeyId` கட்டாயம்; `dailyLimitUsd`, `weeklyLimitUsd`, அல்லது `monthlyLimitUsd` ஆகியவற்றில் குறைந்தது ஒன்று பூஜ்ஜியத்தை விட அதிகமாக இருக்க வேண்டும். விருப்பப் புலங்கள்: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). மரபுவழி `{keyId, limit, period}` வடிவம் `400 Bad Request`-ஐ வழங்கும்.

## டோக்கன் வரம்புகள்

ஒவ்வொரு API விசைக்குமான **டோக்கன்** பட்ஜெட்டுகள் (மேலே குறிப்பிடப்பட்ட USD அடிப்படையிலான பட்ஜெட்டிலிருந்து தனித்தவை). கோரிக்கை பாதையில் உடனடியாக அமல்படுத்தப்படும்: ஒரு விசையின் தற்போதைய சாளரப் பயன்பாடு அதன் வரம்பை எட்டும்போது, `429 Too Many Requests` உடன் கோரிக்கைகள் நிராகரிக்கப்படும். வரம்புகளை ஒரு குறிப்பிட்ட `model`, ஒரு `provider` அல்லது விசை முழுவதும் `global` ஆகப் பயன்படுத்துமாறு வரையறுக்கலாம்; ஒரு கோரிக்கைக்கு பல வரம்புகள் பொருந்தும்போது, மிகவும் கட்டுப்படுத்தக்கூடிய வரம்பே அமலாகும்.

```bash
# ஒரு விசையின் டோக்கன் வரம்புகளைப் பட்டியலிடு (நடப்பு சாளரப் பயன்பாடும் அடங்கும்)
GET /api/usage/token-limits?apiKeyId=key-123

# டோக்கன் வரம்பை உருவாக்கு அல்லது புதுப்பி
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id மூலம் டோக்கன் வரம்பை நீக்கு
DELETE /api/usage/token-limits?id=tl-abc
```

> **Schema குறிப்புகள்** (`setTokenLimitSchema`): `apiKeyId` மற்றும் `scopeType` (`model` | `provider` | `global`) ஆகியவை தேவை. `scopeType` `global` அல்லாதபோது `scopeValue` தேவை (`model` வரம்புக்கு ஒரு model id, `provider` வரம்புக்கு ஒரு provider id போன்றவை). `tokenLimit` நேர்மறை முழு எண்ணாக இருக்க வேண்டும் (சரத்திலிருந்து மாற்றப்படும்). விருப்பத்தேர்வுகள்: `id` (உருவாக்கும்போது விடுபட வேண்டும், புதுப்பிக்கும்போது வழங்க வேண்டும்), `resetInterval` (`daily` | `weekly` | `monthly`, இயல்புநிலை `monthly`), `resetTime` (`HH:MM`), `enabled` (இயல்புநிலை `true`). `GET` பதில்கள் ஒவ்வொரு வரம்பையும் `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, மற்றும் `nextResetAt` ஆகியவற்றுடன் விரிவுபடுத்தும். இது மேலாண்மை-வகை endpoint ஆகும் (அங்கீகாரம் authz pipeline மூலம் மையமாக அமல்படுத்தப்படுகிறது).

## கோரிக்கை செயலாக்கம்

1. கிளையன்ட் `/v1/*` க்கு கோரிக்கையை அனுப்புகிறது
2. Route handler `handleChat`, `handleEmbedding`, `handleAudioTranscription`, அல்லது `handleImageGeneration` ஐ அழைக்கிறது
3. Model தீர்மானிக்கப்படுகிறது (நேரடி provider/model அல்லது alias/combo)
4. கணக்கு கிடைக்கும் தன்மை வடிகட்டலுடன் உள்ளூர் DB-யிலிருந்து நற்சான்றுகள் தேர்ந்தெடுக்கப்படுகின்றன
5. Chat-க்கு: `handleChatCore` semantic/signature cache-ஐ சரிபார்த்து combo compression அமைப்புகளைத் தீர்மானிக்கிறது
6. செயல்படுத்தப்பட்டிருக்கும்போது provider translation-க்கு முன் proactive compression இயக்கப்படுகிறது (`lite`, Caveman, RTK, அல்லது stacked)
7. Provider executor upstream கோரிக்கையை அனுப்புகிறது
8. பதில் கிளையன்ட் வடிவத்திற்குத் திரும்ப மொழிபெயர்க்கப்படுகிறது (chat) அல்லது மாற்றமின்றி திருப்பி அனுப்பப்படுகிறது (embeddings/images/audio)
9. பயன்பாடு, compression analytics, மற்றும் கோரிக்கைப் பதிவுகள் பதிவு செய்யப்படுகின்றன
10. combo விதிகளின்படி பிழைகள் ஏற்பட்டால் fallback பயன்படுத்தப்படுகிறது

முழுமையான கட்டமைப்புக் குறிப்புக்கு: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Combo மேலாண்மை

உயர்நிலை routing combo-களை (`/api/combos*` இன் கீழ் ஏற்கனவே சுருக்கமாகக் குறிப்பிடப்பட்டவை) model id pattern-இலிருந்து 1:1 ஆகவும் map செய்யலாம். இதன் மூலம் OpenAI-பாணி model id ஒன்று வெளிப்படையாக combo-க்கு திருப்பிவிடப்படலாம்.

| Method | Path                             | Description                                                                         |
| ------ | -------------------------------- | ----------------------------------------------------------------------------------- |
| GET    | `/api/model-combo-mappings`      | அனைத்து model→combo mapping-களையும் பட்டியலிடு                                      |
| POST   | `/api/model-combo-mappings`      | Mapping-ஐ உருவாக்கு — body: `{pattern, comboId, priority?, enabled?, description?}` |
| GET    | `/api/model-combo-mappings/[id]` | ஒற்றை mapping-ஐப் பெறு                                                              |
| PUT    | `/api/model-combo-mappings/[id]` | ஏற்கனவே உள்ள mapping-இன் புலங்களைப் புதுப்பி                                        |
| DELETE | `/api/model-combo-mappings/[id]` | Mapping-ஐ அகற்று                                                                    |

**Auth:** management session/API key (`requireManagementAuth`).

## வெப்ஹுக்குகள்

OmniRoute நிகழ்வுகளுக்கான வெளிச்செல்லும் வெப்ஹுக் சந்தாக்கள் (கோரிக்கை நிறைவு, ஒதுக்கீடு தீர்தல், விசைச் சுழற்சி போன்றவை).

| Method | Path                      | Description                                                                 |
| ------ | ------------------------- | --------------------------------------------------------------------------- |
| GET    | `/api/webhooks`           | வெப்ஹுக்குகளைப் பட்டியலிடு (ரகசியங்கள் `<prefix>...` என மறைக்கப்படும்)      |
| POST   | `/api/webhooks`           | வெப்ஹுக்கை உருவாக்கு — body: `{url, events?: ["*"], secret?, description?}` |
| GET    | `/api/webhooks/[id]`      | வெப்ஹுக்கைப் பெறுக                                                          |
| PUT    | `/api/webhooks/[id]`      | url/events/secret/description-ஐப் புதுப்பிக்கவும்                           |
| DELETE | `/api/webhooks/[id]`      | வெப்ஹுக்கை அகற்றுக                                                          |

## பதிவுசெய்யப்பட்ட விசைகள் (தானியங்கி மேலாண்மை)

## நெகிழ்திறன் (விரிவாக்கப்பட்டது)

OmniRoute மூன்று தனித்தனி தற்காலிகத் தோல்வி வழிமுறைகளை வழங்குகிறது; கீழே உள்ள மேலாண்மை endpoint-கள் அவற்றைப் படிக்கவும் மேலெழுதவும் அனுமதிக்கின்றன:

| வரம்பு              | நிலைச் சேமிப்பு                          | படித்தல்                                  | மீட்டமைத்தல் / அழித்தல்                                              |
| ------------------- | ---------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------- |
| Provider breaker    | `domain_circuit_breakers` + நினைவகத்தில் | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                         |
| Connection cooldown | provider இணைப்புகளில் `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (மந்தமாக மீண்டும் செயல்படுத்தப்படும்; provider PUT மூலம் அழிக்கலாம்) |
| Model lockout       | நினைவக model-கிடைக்கும் பதிவேடு          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                             |

`PATCH /api/resilience`, `providerBreaker.oauth` மற்றும் `providerBreaker.apikey` ஆகியவற்றின் கீழ் provider breaker மேலெழுதல்களை ஏற்கிறது. ஒவ்வொரு சுயவிவரமும் `degradationThreshold`, `failureThreshold`, மற்றும் `resetTimeoutMs` ஆகியவற்றை ஆதரிக்கிறது; இதே புலங்கள் Dashboard → Settings → Resilience என்பதிலும் வழங்கப்படுகின்றன.

```bash
# ஒரு model lockout-ஐ அழிக்கவும்
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# அனைத்து lockout-களையும் அழிக்கவும்
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

முழுமையான கருத்தியல் குறிப்பு மற்றும் breaker இயல்புநிலைகளுக்கு: [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" மற்றும் [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) ஆகியவற்றைப் பார்க்கவும்.

### Rate-Limit Queue & Auto-Enable Safety Net

- **ஆதரிக்கப்படும் எழுதும் வழி**: `POST /api/rate-limits`, body `{"connectionId": "<id>", "enabled": true|false}`, ஒரு இணைப்புக்கான rate-limit பாதுகாப்பை மாற்றுவதற்கான ஆதரிக்கப்படும் மேலாண்மை endpoint ஆகும். `PUT /api/providers/[id]` திட்டமிட்டு `rateLimitProtection`-ஐ மாற்றவோ புரட்டவோ செய்யாது (#11278).
- **`enabled: false` என்பதன் பொருள்**: `enabled: false` அமைப்பது இணைப்புக்கான வெளிப்படையான பாதுகாப்பை நீக்குகிறது, ஆனால் செயலில் உள்ள API-key இணைப்பை உலகளாவிய auto-enable பாதுகாப்பு வலையிலிருந்து (`autoEnableApiKeyProviders = true`) **விலக்காது**. `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) இல், `false` மற்றும் `undefined` ஆகியவை சமமானவை; வெளிப்படையான பாதுகாப்பு இல்லாத செயலில் உள்ள API-key இணைப்புகள் auto-enable பாதுகாப்பு வலையின் கீழ் பாதுகாக்கப்பட்டே இருக்கும்.
- **உலகளாவிய முடக்கம்**: rate-limit queue-கள் இல்லாமல் API-key இணைப்புகளை இயக்க, `RATE_LIMIT_AUTO_ENABLE=false` (env) அல்லது `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) மூலம் பாதுகாப்பு வலையை உலகளவில் முடக்கவும்.

ஒரு API விசை / அமர்வுக்கான வரம்பில் உள்ள நிலைத்த உரையாடல்/உண்மைத் தகவல் நினைவகச் சேமிப்பு.

| முறை   | பாதை                 | விளக்கம்                                                                                                                          |
| ------ | -------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/memory`        | நினைவுகளைப் பட்டியலிடுதல் — `?apiKeyId=`, `?type=`, `?sessionId=`, `?q=`, `offset/limit` அல்லது `page/limit` பக்கமாக்கலுடன்       |
| POST   | `/api/memory`        | நினைவகத்தை உருவாக்குதல் — Zod மூலம் சரிபார்க்கப்படும் உடல்: `{content, key, type?, sessionId?, apiKeyId?, metadata?, expiresAt?}` |
| GET    | `/api/memory/[id]`   | ஒரு நினைவகத்தை மீட்டெடுத்தல்                                                                                                      |
| DELETE | `/api/memory/[id]`   | ஒரு நினைவகத்தை நீக்குதல்                                                                                                          |
| GET    | `/api/memory/health` | நினைவகத் துணை அமைப்பின் நிலை (DB இணைப்பு, embeddings பின்தளம், vector index நிலை)                                                 |

**அங்கீகாரம்:** மேலாண்மை அமர்வு/API விசை (`requireManagementAuth`). `type` enum: `FACTUAL`, `EPISODIC`, `SEMANTIC`, `PROCEDURAL` (`src/lib/memory/types.ts` இல் உள்ள `MemoryType`-ஐப் பார்க்கவும்).

## MCP சேவையகம்

OmniRoute, 3 போக்குவரத்து முறைகள் (stdio, SSE, streamable-http) மற்றும் வரம்புக்குட்பட்ட கருவிகளுடன் உட்பொதிக்கப்பட்ட Model Context Protocol சேவையகத்தைக் கொண்டுள்ளது. கீழே உள்ள dashboard endpoint-கள் நிலை/தணிக்கைத் தரவைப் படித்து, HTTP போக்குவரத்து முறைகளுக்கான proxy ஆகச் செயல்படுகின்றன.

| முறை | பாதை | விளக்கம் |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Heartbeat, போக்குவரத்து, ஆன்லைன் நிலை, கடைசி அழைப்பு, முதன்மைக் கருவிகள், 24 மணி நேர வெற்றி விகிதம் |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` ஆகியவற்றைக் கொண்ட MCP கருவிகளின் பட்டியல் |
| GET | `/api/mcp/sse` | SSE போக்குவரத்திற்கான திறந்த SSE stream (MCP முடக்கப்பட்டிருந்தால் அல்லது போக்குவரத்து பொருந்தாவிட்டால் `503` வழங்கப்படும்) |
| POST | `/api/mcp/sse` | SSE போக்குவரத்தில் JSON-RPC frame-ஐ அனுப்புதல் |
| GET | `/api/mcp/stream` | Streamable HTTP போக்குவரத்தின் SSE பக்கத்தைத் திறத்தல் (சேவையகம் தொடங்கும் செய்திகள்) |
| POST | `/api/mcp/stream` | Streamable HTTP போக்குவரத்தில் JSON-RPC frame-ஐ அனுப்புதல் |
| DELETE | `/api/mcp/stream` | Streamable HTTP அமர்வை முடித்தல் |
| GET | `/api/mcp/audit` | தணிக்கைப் பதிவைக் கேள்வியிடுதல் — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | ஒருங்கிணைக்கப்பட்ட தணிக்கைப் புள்ளிவிவரங்கள் (மொத்தங்கள், வெற்றி விகிதம், சராசரி கால அளவு, முதன்மைக் கருவிகள்) |

**அங்கீகாரம்:** `sse`/`stream` போக்குவரத்து முறைகள் MCP-க்கான தனிப்பட்ட அங்கீகாரப் பரப்பைப் பயன்படுத்துகின்றன (`mcp` scope கொண்ட Bearer API விசை); `status`/`tools`/`audit*` வழித்தடங்களை dashboard-இலிருந்து படிக்கலாம் (dashboard host-ஐ அடைவதற்குத் தேவையான கூடுதல் அங்கீகாரம் எதுவும் இல்லை).

> இரண்டு HTTP போக்குவரத்து முறைகளும் `settings.mcpEnabled` மற்றும் `settings.mcpTransport` மூலம் கட்டுப்படுத்தப்படுகின்றன — போக்குவரத்து பொருந்தாமை `400`-ஐத் திருப்பும், MCP முடக்கப்பட்ட நிலை `503`-ஐத் திருப்பும்.

## A2A சேவையகம்

OmniRoute, ஆய்வு/டாஷ்போர்டு பயன்பாட்டிற்காக A2A (Agent-to-Agent) JSON-RPC 2.0 endpoint மற்றும் REST wrapper ஆகியவற்றை வழங்குகிறது.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # விருப்பத்தேர்வு; OMNIROUTE_API_KEY அமைக்கப்பட்டிருந்தால் மட்டுமே தேவையில்லை
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

ஆதரிக்கப்படும் முறைகள் (`settings.a2aEnabled` இயக்கப்பட்டிருந்தால் மட்டுமே அனைத்தும் செயல்படும்):

| Method           | Description                                                                 |
| ---------------- | --------------------------------------------------------------------------- |
| `message/send`   | ஒத்திசைவான skill செயல்படுத்தல்; `{task, artifacts, metadata}`-ஐ வழங்குகிறது |
| `message/stream` | அதே skill தொகுப்பின் streaming SSE செயல்படுத்தல்                            |
| `tasks/get`      | `taskId` மூலம் ஒரு பணியைப் பெறுதல்                                          |
| `tasks/cancel`   | `taskId` மூலம் ஒரு பணியை ரத்து செய்தல்                                      |

உள்ளமைக்கப்பட்ட skills: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Agent Card

```bash
GET /.well-known/agent.json
```

பொது A2A agent card-ஐ (பெயர், விளக்கம், திறன்கள், skill பட்டியல், அங்கீகாரத் திட்டம்) வழங்குகிறது — 1 மணிநேரத்திற்கு பொதுவாக cache செய்யப்படுகிறது. அங்கீகாரம் தேவையில்லை.

### REST உதவியாளர்கள்

| Method | Path                         | Description                                                                                                            |
| ------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A இயக்கப்பட்டுள்ளதா என்பதையும், பணிப் புள்ளிவிவரங்களையும், cache செய்யப்பட்ட agent card சுருக்கத்தையும் வழங்குகிறது  |
| GET    | `/api/a2a/tasks`             | பணிகளின் பட்டியல் — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (REST உதவியாளராக செயல்படுத்தப்படவில்லை — JSON-RPC `message/send` மூலம் உருவாக்கவும்)                                   |
| GET    | `/api/a2a/tasks/[id]`        | ஒரு பணியைப் பெறுதல்                                                                                                    |
| POST   | `/api/a2a/tasks/[id]/cancel` | ஒரு பணியை ரத்து செய்தல்                                                                                                |

**அங்கீகாரம்:** REST உதவியாளர்கள் management auth இல்லாமல் இயங்குகின்றன (டாஷ்போர்டில் படிக்கக்கூடியவை); கட்டமைக்கப்பட்டிருந்தால், JSON-RPC `/a2a` route, Bearer `OMNIROUTE_API_KEY`-ஐப் பயன்படுத்துகிறது.

## ACP (Agent Client Protocol) மேலாண்மை

child processes ஆக. இந்த endpoint-கள் ACP agent கண்டறிதல் மற்றும் தனிப்பயன் agent
பதிவுசெய்தலை நிர்வகிக்கின்றன.

| Method | Path              | Description                                                                                                                                                                         |
| ------ | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | நிறுவல் நிலை, பதிப்பு, binary ஆகியவற்றுடன் அறியப்பட்ட அனைத்து CLI agent-களையும் (உள்ளமைக்கப்பட்டவை + தனிப்பயன்கள்) பட்டியலிடும்                                                     |
| POST   | `/api/acp/agents` | தனிப்பயன் ACP agent-ஐப் பதிவுசெய்யும் அல்லது cache-ஐப் புதுப்பிக்கும் — body: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` அல்லது `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | தனிப்பயன் ACP agent-ஐ அகற்றும் — query param: `?id=<agentId>`                                                                                                                       |

**பதில் எடுத்துக்காட்டு** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**அங்கீகாரம்:** மேலாண்மை session (dashboard `auth_token` cookie) அல்லது
மேலாண்மை வரம்புடைய API key தேவை.

முழு விவரங்களுக்கு [ACP Framework](../frameworks/ACP.md)-ஐப் பார்க்கவும்.

## பாதுகாப்புக் கட்டுப்பாடுகள்

இயக்கநேர பாதுகாப்புக் கட்டுப்பாடுகளை (PII கண்டறிதல், prompt injection கண்டறிதல், vision bridging) ஆய்வு செய்யவும். பாதுகாப்புக் கட்டுப்பாடுகள் ஒவ்வொரு கோரிக்கையிலும் இயங்குகின்றன; ஒவ்வொரு அழைப்பிற்குமான விலகல் `x-omniroute-disabled-guardrails` கோரிக்கை தலைப்பு மூலம் செய்யப்படுகிறது — நிலைத்த enable/disable மேற்பரப்பு எதுவும் இல்லை.

| முறை | பாதை                   | விளக்கம்                                                                                                                  |
| ---- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| GET  | `/api/guardrails`      | பதிவுசெய்யப்பட்ட பாதுகாப்புக் கட்டுப்பாடுகள் மற்றும் அவற்றின் நிலையைப் பட்டியலிடவும் (பெயர் / இயக்கப்பட்டது / முன்னுரிமை) |
| POST | `/api/guardrails/test` | மாதிரி உள்ளீட்டில் அழைப்பிற்கு முந்தைய pipeline-ஐ dry-run செய்யவும் — body: `{input, disabledGuardrails?}`                |

**அங்கீகாரம்:** நிர்வாக அமர்வு தேவை.

முழு விவரங்களுக்கு [பாதுகாப்பு > பாதுகாப்புக் கட்டுப்பாடுகள்](../security/GUARDRAILS.md) பார்க்கவும்.

## அங்கீகாரம்

நான்கு நற்சான்று குடும்பங்கள் (டாஷ்போர்டு அமர்வு, உள்ளூர் CLI டோக்கன், `oma_live_…` அணுகல் டோக்கன், manage-ஸ்கோப் செய்யப்பட்ட API விசை) மற்றும் அவை inference விசைகளிலிருந்து எவ்வாறு வேறுபடுகின்றன என்பதற்கு [மேலாண்மை அங்கீகாரம்](../guides/MANAGEMENT-AUTH.md)-ஐப் பார்க்கவும்.

- டாஷ்போர்டு வழித்தடங்கள் (`/dashboard/*`) `auth_token` குக்கியைப் பயன்படுத்துகின்றன
- உள்நுழைவு சேமிக்கப்பட்ட கடவுச்சொல் ஹாஷைப் பயன்படுத்துகிறது; மாற்று வழியாக `INITIAL_PASSWORD` பயன்படுத்தப்படுகிறது
- `/api/settings/require-login` வழியாக `requireLogin` மாற்றத்தை இயக்கலாம் அல்லது முடக்கலாம்
- `REQUIRE_API_KEY=true` என இருக்கும் போது `/v1/*` வழித்தடங்களுக்கு விருப்பத்திற்கேற்ப Bearer API விசை தேவைப்படும்
- இந்தக் குறிப்பில் "மேலாண்மை டோக்கன்" / "மேலாண்மை-ஸ்கோப் செய்யப்பட்ட API விசை" என்பது அந்த வழிகாட்டியில் உள்ள குடும்பங்களில் ஒன்றைக் குறிக்கிறது — வரையறுக்கப்படாத கூடுதல் ரகசிய வகையைக் குறிக்காது
