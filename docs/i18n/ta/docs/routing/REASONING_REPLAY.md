> **உண்மையின் ஆதாரம்:** `src/lib/db/reasoningCache.ts`, `open-sse/services/reasoningCache.ts`** கடைசியாக புதுப்பிக்கப்பட்டது:** 2026-06-28 — v3.8.40

திங்கிங்-மோட் மாடல்களால் உருவாக்கப்பட்ட உதவியாளர் `reasoning_content` OmniRoute கைப்பற்றுகிறது மற்றும் அப்ஸ்ட்ரீம் வழங்குநருக்குத் தேவைப்படும்போது அதை மல்டி-டர்ன் கோரிக்கைகளில் வெளிப்படையாக மீண்டும் இயக்குகிறது. ஒரு கிளையண்டின் உரையாடல் வரலாற்றில் முந்தைய முறையின் பகுத்தறிவு இல்லாதபோது கடுமையான வழங்குநர்கள் எழுப்பும் HTTP 400 பிழைகளை இது நீக்குகிறது.

## ஏன் இது இருக்கிறது

பல சிந்தனை முறை வழங்குநர்கள் பின்தொடர்தல் திருப்பத்தை நிராகரிக்கின்றனர்** முந்தைய உதவி செய்தியில் அசல் `reasoning_content` உள்ளது** . அப்ஸ்ட்ரீம் 400ஐ இது போன்ற செய்திகளுடன் வழங்குகிறது:

```
Param Incorrect: The reasoning_content in the thinking mode must be passed back to the API.
```

ஆனால் வழக்கமான வாடிக்கையாளர்கள் (Cursor, Cline, Roo Code, OpenAI SDK) அவர்கள் ரீப்ளே செய்யும் வரலாற்றிலிருந்து `reasoning_content` அகற்றுவார்கள். OmniRoute அதை சர்வர் பக்க தற்காலிக சேமிப்பிலிருந்து மீட்டமைக்கிறது, எனவே அப்ஸ்ட்ரீம் பார்க்கும் கோரிக்கை சீராக இருக்கும். வெளியீடு #1628 ஹைப்ரிட் memory/SQLite நிலைத்தன்மையை அறிமுகப்படுத்தியது, எனவே தற்காலிக சேமிப்பு செயல்முறை மறுதொடக்கம் செய்யப்படுகிறது.

## கட்டிடக்கலை

```
Turn N (assistant generates):
  → response contains reasoning_content + tool_calls
  → if requiresReasoningReplay(provider, model): cacheReasoningFromAssistantMessage()
      writes (memory + DB), one entry per tool_call.id within the request scope
  → forward response to client (which may or may not retain reasoning)

Turn N+1 (client sends follow-up):
  → translator detects: requiresReasoningReplay(provider, model) === true
  → for each assistant message with tool_calls and no reasoning_content:
      lookupReasoning(buildToolCallCacheKey(scope, toolCalls[0].id)) → memory → DB
      hit  → msg.reasoning_content = cached; recordReplay()
      miss → msg.reasoning_content = "" (legacy fallback for older DeepSeek)
  → upstream sees consistent history → no 400
```

பிடிப்பு `open-sse/handlers/chatCore.ts` இல் நடக்கிறது (இரண்டு தளங்கள், இரண்டு `cacheReasoningFromAssistantMessage` அழைப்பு தளங்களில்). ஸ்கீமா வற்புறுத்தலுக்குப் பிறகு, ஆனால் அனுப்புவதற்கு முன்பு `open-sse/translator/index.ts` இல் மறுவிளைவு நடக்கும்.

டூல்-அழைப்பு உள்ளீடுகள் `buildToolCallCacheKey()` இன் கீழ் சேமிக்கப்படும், இது கோரிக்கை நோக்கம் மற்றும் கருவி அழைப்பு ஐடியின் செரிமானமாகும், எனவே மற்றொரு API விசை அல்லது அமர்வு பயன்படுத்தும் அதே ஐடி உள்ளீட்டைத் தேர்ந்தெடுக்காது. நோக்கம் `buildReasoningCacheScope()` இலிருந்து வருகிறது: API விசை ஐடி மற்றும் கோரிக்கையில் ஒன்று இருக்கும்போது அமர்வு விசை. `tool_call_id` நெடுவரிசையும் டாஷ்போர்டும் அந்த உள்ளீடுகளுக்கு இந்த டைஜெஸ்ட்டைக் காட்டுகின்றன.

எளிய (கருவி-அழைப்பு அல்லாத) உதவியாளர் திருப்பங்கள் வித்தியாசமாக விசைப்படுத்தப்படுகின்றன: `buildAssistantMessageCacheKey()` அமர்வு நோக்கத்தையும் அந்தத் திருப்பம் வரை இயல்பாக்கப்பட்ட OpenAI- வடிவ டிரான்ஸ்கிரிப்டையும் ஜீரணிக்கச் செய்கிறது, ஏனெனில் DeepSeek `tools` இருக்கும் போது _every_ முன் திருப்பத்தின் காரணம் தேவைப்படுகிறது. Responses-API இலக்குகளுக்கு (உதாரணமாக `opencode-go/deepseek-v4-flash`, `/responses` க்கு அனுப்பப்பட்டது) அப்ஸ்ட்ரீம் உடல் `input` அல்ல, `messages` கொண்டு செல்கிறது, எனவே `translateRequest()` (`open-sse/translator/index.ts`) ஒரு கால்பேக் விருப்பத்தின் மூலம் ஜீரணித்த பிவோட் டிரான்ஸ்கிரிப்டைப் புகாரளிக்கிறது மற்றும் அதே டிரான்ஸ்கிரிப்டைப் பிடிப்பு தளங்கள் ஜீரணிக்கின்றன. மறுமொழிகள் ரீப்ளே பாஸ் ஒவ்வொரு மூல வடிவத்திற்கும் OpenAI பைவட்டில் இயங்குகிறது, எனவே Anthropic செய்திகள் கிளையன்ட்களும் (Claude → OpenAI → Responses) மீண்டும் இயக்கப்படும்.

## சேமிப்பு — ஹைப்ரிட் நினைவகம் + SQLite

கிராஷ் மீட்பு மற்றும் டாஷ்போர்டு தெரிவுநிலைக்கு SQLite டேபிளால் ஆதரிக்கப்படும் இன்-மெமரி `Map` (LRU-by-creation) ஐ ஹாட் பாதை பயன்படுத்துகிறது.

| அடுக்கு  | செயல்படுத்தல்                                  | நோக்கம்                                                  |
| -------- | ---------------------------------------------- | -------------------------------------------------------- |
| நினைவகம் | `open-sse/services/reasoningCache.ts` இல்`Map` | விரைவான தேடுதல்கள், 200 வயதானவர்களை வெளியேற்றுகிறது      |
| DB       | `reasoning_cache` அட்டவணை (`src/lib/db/`)      | மறுதொடக்கம், டிரைவ் புள்ளிவிவரங்கள் முழுவதும் தொடர்கிறது |

எழுத்துகள் இரண்டிற்கும் செல்லும். முதலில் நினைவகத்தைப் படிக்கிறது, பின்னர் DB க்கு திரும்பும் (DB வெற்றிகள் மீண்டும் நினைவகமாக உயர்த்தப்படும்). DB தோல்விகள் ஆபத்தானது அல்ல — நினைவகத்தில் உள்ள கேச் சூடான பாதையில் தொடர்ந்து சேவை செய்கிறது.

**இயல்புநிலைகள்:**

- TTL: `2h` (`TTL_MS = 2 * 60 * 60 * 1000`)
- அதிகபட்ச நினைவக உள்ளீடுகள்: `200` (`MAX_MEMORY_ENTRIES`)
- வெளியேற்றம்: பழமையான `createdAt` முதலில்

## தரவுத்தள திட்டம்

இடம்பெயர்வு: `src/lib/db/migrations/033_create_reasoning_cache.sql`

```sql
CREATE TABLE IF NOT EXISTS reasoning_cache (
  tool_call_id   TEXT PRIMARY KEY,
  provider       TEXT NOT NULL,
  model          TEXT NOT NULL,
  reasoning      TEXT NOT NULL,
  char_count     INTEGER NOT NULL DEFAULT 0,
  created_at     TEXT NOT NULL DEFAULT (datetime('now')),
  expires_at     INTEGER NOT NULL
);
```

குறியீடுகள்: `expires_at`, `provider`, `model`, `created_at`. `expires_at` Unix சகாப்த வினாடிகளாக சேமிக்கப்படுகிறது; SELECT அடுக்கு `EXPIRES_AT_EPOCH_SQL` வழியாக மரபு உரை மதிப்புகளை இயல்பாக்குகிறது.

## REST API

கேச் `src/app/api/cache/reasoning/route.ts` இன் கீழ் இரண்டு முனைப்புள்ளிகளை வெளிப்படுத்துகிறது. இரண்டுக்கும் மேலாண்மை அங்கீகாரம் தேவை (`isAuthenticated` இலிருந்து `@/shared/utils/apiAuth`).

| முறை   | இறுதிப்புள்ளி                                             | விளக்கம்                                                                      |
| ------ | --------------------------------------------------------- | ----------------------------------------------------------------------------- |
| GET    | `/api/cache/reasoning`                                    | புள்ளிவிவரங்கள் + பக்க உள்ளீடுகள்                                             |
| GET    | `/api/cache/reasoning?provider=deepseek&model=...&limit=` | வடிகட்டப்பட்ட பட்டியல் (`limit` `[1, 200]` உடன் பிணைக்கப்பட்டுள்ளது)          |
| DELETE | `/api/cache/reasoning`                                    | அனைத்தையும் அழித்து (நினைவக + DB) மற்றும் hit/miss எண்ணிக்கையை மீட்டமைக்கவும் |

| DELETE | `/api/cache/reasoning?toolCallId=call_abc`                | ஒரு பதிவை நீக்கவும்                                                           |

## செயல்பாட்டு குறிப்புகள்

- **சுத்தம்:** `cleanupReasoningCache()` காலாவதியான நினைவக உள்ளீடுகளை நீக்குகிறது மற்றும் `DELETE FROM reasoning_cache WHERE expires_at <= unixepoch('now')` இயக்குகிறது. சுகாதாரப் பணியாளர்கள் இதை அவ்வப்போது அழைக்கிறார்கள்.
- **விபத்து மீட்பு:** மறுதொடக்கம் செய்த பிறகு, நினைவகம் காலியாக உள்ளது, ஆனால் DB இன்னும் காலாவதியாகாத உள்ளீடுகளை வைத்திருக்கிறது. கொடுக்கப்பட்ட `tool_call_id` க்கான முதல் தேடல் DB ஹிட் ஆகும்; அடுத்தடுத்த தேடல்கள் மெமரி ஹிட் ஆகும்.
- **காரணம் இல்லை, தற்காலிக சேமிப்பு இல்லை:** உதவி செய்தியில் `reasoning_content` / `reasoning` புலம் இல்லாதபோது `cacheReasoningFromAssistantMessage` `0` வழங்குகிறது, எனவே சிந்திக்காத பதில்களுக்கு எதுவும் செலவாகாது.
- **எழுதவும் நுழைவாயில்:** `chatCore.ts` இல் உள்ள இரண்டு அழைப்பு தளங்களும் (ஸ்ட்ரீமிங் அல்லாத மற்றும் ஸ்ட்ரீமிங்) `requiresReasoningReplay(provider, model)` `true` — இருக்கும் போது மட்டுமே `cacheReasoningFromAssistantMessage()` அழைக்கவும், படிக்கும் பக்க சோதனைகளை முன்னறிவிக்கிறது. ரீப்ளே வழங்குநரைத் தொடாத நிறுவல்கள் எழுதுதல், குறியீட்டுப் புதுப்பித்தல் மற்றும் try/catch ஆகியவற்றிற்குப் பணம் செலுத்துவதை நிறுத்துகின்றன.
- **கண்டிப்பான வழங்குநர்கள்:** `requiresReasoningReplay` என்பது `false` ஆகவும், இலக்கு வடிவம் OpenAI ஆகவும் இருக்கும் போது, மொழிபெயர்ப்பாளர்** கீற்றுகள்** வெளிச்செல்லும் செய்திகளிலிருந்து எந்த `reasoning_content` புலமும் — OpenAI Chat Completions அதை ஏற்காது.

## மியூஸ் ஒளிபுகா-பகுத்தறிவு உரிமை

மியூஸ் (`muse-code`) அழைப்பாளர்-பிணைக்கப்பட்ட ஒளிபுகா பகுத்தறிவை (`encrypted_content`) வழங்குகிறது. வேறொரு கணக்கின் கீழ் அதை மீண்டும் இயக்குவது அல்லது நற்சான்றிதழ் அப்ஸ்ட்ரீமில் தோல்வியடைகிறது, எனவே சொந்த OAuth கோரிக்கைகள் ஒவ்வொரு கோரிக்கை சுழற்சிக்கும் பதிலாக அமர்வு நிலை உரிமையைப் பயன்படுத்துகின்றன (`src/sse/services/museSessionOwnership.ts`, `src/sse/handlers/chat.ts` இல் செயல்படுத்தப்பட்டது ). வெளிப்படையாகத் தேர்ந்தெடுக்கப்பட்ட ஏபிஐ-விசை இணைப்புகள் மற்றும் ஏபிஐ-விசை மட்டும் உள்ளமைவுகள் இந்த உரிமைப் பயன்முறையின்றி ஏற்கனவே உள்ள ரூட்டிங்கைத் தக்கவைத்துக்கொள்கின்றன.

- ஒவ்வொரு திருப்பத்திலும் ஒரு நிலையான அமர்வு ID வழங்கவும்: `x-omniroute-session-id`, `x-omniroute-session`, `x-session-id`, அல்லது `x-codex-session-id`; மாற்றாக உடலில் `prompt_cache_key`, `session_id`, `conversation_id`, அல்லது `metadata.session_id` பயன்படுத்தவும் (அந்த முன்னுரிமை வரிசையில்). இரண்டு அல்லது அதற்கு மேற்பட்ட நேட்டிவ் OAuth கணக்குகள் செயலில் இருக்கும் போது 400ஐக் காணவில்லை அல்லது வெற்று IDs திரும்பப் பெறுங்கள்; ஒரு ஒற்றை OAuth கணக்கில் சுழற்றுவதற்கு எதுவும் இல்லை, எனவே அத்தகைய கோரிக்கையானது அன்பின் செய்யப்படாத ரூட்டிங் வைத்திருக்கும். ஸ்கோப்பில் அழைப்பவரின் OmniRoute API-key ID.
- ID இணைப்பின் மூலம் வரிசைப்படுத்தப்பட்ட API-விசை இணைப்புக் கொள்கையால் அனுமதிக்கப்பட்ட செயலில் உள்ள சொந்த OAuth கணக்குகள் முழுவதும் புதிய சுயாதீன அமர்வுகள் ரவுண்ட்-ராபின். டெர்மினல் நிலை (`banned`, `expired`, `credits_exhausted`) அல்லது கோரப்பட்ட மாடலுக்கான மாடல்-லாக் செய்யப்பட்ட இணைப்பு கூல்டவுனில் ரவுண்ட்-ராபின் கணக்குகளைத் தவிர்க்கிறது; மியூஸ் அப்ஸ்ட்ரீம் தோல்விகள் மற்ற வழங்குநர்களைப் போலவே கூல்டவுன் மற்றும் பிரேக்கர் நிலையைப் பதிவு செய்கின்றன. வெளிப்படையாக கட்டாயப்படுத்தப்பட்ட இணைப்பு புதிய அமர்வுக்கு ரவுண்ட்-ராபினைப் புறக்கணிக்கிறது, ஆனால் ஏற்கனவே உள்ள உரிமையாளரை மீற முடியாது.
- உரிமையாளர் வெற்றிகரமான பதிலை வழங்கும் வரை, அதன் உரிமையாளர் கிடைக்காத அமர்வு ஆரோக்கியமான கணக்கில் மீண்டும் கோரப்படும். முதல் வெற்றிகரமான பதிலுக்குப் பிறகு, அமர்வு 30 நாட்களுக்கு (`MUSE_SESSION_IDLE_TTL_MS`) செயலற்ற நிலையில் இருக்கும் வரை அந்த உரிமையாளரிடம் பின் செய்யப்பட்டிருக்கும்.
- ஒவ்வொரு தொடர்ச்சி மற்றும் கருவி-முடிவு திருப்பம் அமர்வு உரிமையாளருக்குப் பின் செய்யப்பட்டிருக்கும்: இணைப்பு, கணக்கு அடையாளம் மற்றும் அனுமானம்-நற்சான்றிதழ் உருவாக்கம், நற்சான்றிதழ்-புதுப்பிப்பு மறு முயற்சிகள் உட்பட அப்ஸ்ட்ரீம் முயற்சிகளுக்கு முன் மீண்டும் சரிபார்க்கப்பட்டது. பதில்கள் அழைப்பு IDs/item குறிப்புகள் மற்றும் Chat Completions கருவி-அழைப்பு IDs ஆகியவை அந்த அமர்வு மற்றும் தலைமுறைக்கு பதிவு செய்யப்பட்டிருக்க வேண்டும்.
- SQLite `key_value` பதிவுகள் `muse_session_ownership` நேம்ஸ்பேஸில் (`src/lib/db/museSessionOwnership.ts`) உரிமை நிலைத்திருக்கும் மற்றும் மறுதொடக்கம் முழுவதும் சுழற்சி கர்சர். ஒவ்வொரு உரிமைகோரல் மற்றும் வழங்கப்பட்ட பதில் அமர்வின் செயல்பாட்டு முத்திரையைப் புதுப்பிக்கிறது; `MUSE_SESSION_IDLE_TTL_MS` விட நீண்ட நேரம் செயலற்ற ஒரு அமர்வு கத்தரிக்கப்படுகிறது (உரிமையாளர் முள், வழங்கப்பட்ட கொடி மற்றும் பதிவுசெய்யப்பட்ட opaque/reference ஹாஷ்கள்), அதிகபட்சம் ஒவ்வொரு 10 நிமிடங்களுக்கும் ஒருமுறை மற்றும் வரம்பிற்குட்பட்ட தொகுதிகளில், எனவே அதன் வரலாற்றின் மறுபதிப்பு அறியப்படாத உரிமையாளராக தோல்வியடைகிறது. பதிவுகளில் இணைப்பு IDs மற்றும் கணக்கு அடையாளத்தின் ஹாஷ்கள், நற்சான்றிதழ்கள், ஒளிபுகா உள்ளடக்கம் மற்றும் தொடர்ச்சியான குறிப்புகள் உள்ளன, இரகசியங்கள் அல்லது உரையாடல் வரலாறு அல்ல. வாடிக்கையாளர்கள் தங்கள் முழு வரலாறு மற்றும் ஒளிபுகா பகுத்தறிவைத் தக்கவைத்து அனுப்ப வேண்டும்.
- அறியப்படாத அல்லது வெளிநாட்டு ஒளிபுகா பகுத்தறிவு, காணாமல் போன உரிமையாளர், கிடைக்காத உரிமையாளர் கணக்கு அல்லது பதிவுசெய்யப்பட்ட வரலாற்றில் தலைமுறை மாற்றம் தோல்வியுற்றது வெளிப்படையான 4xx/503 — உடன் மூடப்பட்டது.
- அமர்வில் மீண்டும் இயக்கக்கூடிய வரலாற்றைப் பதிவு செய்யாதபோது மட்டுமே, ஒரே கணக்கு விசை ஏற்றுக்கொள்ளப்படுகிறது; பதிவுசெய்யப்பட்ட அமர்வுகள் புதிதாகத் தொடங்கும் வரை தோல்வியடைந்து கொண்டே இருக்கும்.
- ஒரு வெற்று அப்ஸ்ட்ரீம் பதில் (`upstream_empty_response` / `empty_response`, அழைப்பவருக்கு எதுவும் வெளியிடப்படவில்லை) அதே உரிமையாளரிடம் 0.5 வினாடிகளுக்குப் பிறகு 1.5 வினாடிகள் (`MUSE_EMPTY_RESPONSE_RETRY_DELAYS_MS`) அதிகபட்சம் இரண்டு முறை மீண்டும் முயற்சிக்கப்படும். அனைத்து முயற்சிகளும் காலியாக இருந்தால், அசல் 502 கூல்டவுன் அல்லது பிரேக்கர் மார்க்கிங் இல்லாமல் திரும்பப் பெறப்படும், எனவே ஒரு மெல்லிய பதில் உரிமையாளரைப் பூட்டிவிடாது.
- அனைத்து `muse-code` கோரிக்கைகளும் சொற்பொருள்-கேச் வாசிப்பு மற்றும் எழுதுதல்களைத் தவிர்த்து, ஸ்ட்ரீமிங் எழுதுதல்கள் உட்பட, எனவே தற்காலிக சேமிப்பு ஒளிபுகா வெளியீடு வேறு அமர்வு உரிமையாளரைப் பெற முடியாது.
