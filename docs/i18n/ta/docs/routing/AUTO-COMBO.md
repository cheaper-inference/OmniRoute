## பூஜ்ஜிய-கட்டமைப்பு தானியங்கு வழித்தடம் (`auto/` முன்னொட்டு)

> **புதியது:** சேர்க்கையை உருவாக்க வேண்டியதில்லை. எந்த கிளையண்டிலும் `auto/` முன்னொட்டை நேரடியாகப் பயன்படுத்தவும்.

### விரைவு எடுத்துக்காட்டுகள்

| மாதிரி ID      | மாறுபாடு     | செயல்பாடு                                                                          |
| -------------- | ------------ | ---------------------------------------------------------------------------------- |
| `auto`         | இயல்புநிலை   | இணைக்கப்பட்ட அனைத்து வழங்குநர்களும், LKGP உத்தியும், சமநிலைப்படுத்தப்பட்ட எடைகளும் |
| `auto/coding`  | நிரலாக்கம்   | தரத்திற்கு முன்னுரிமை அளிக்கும் எடைகள், குறியீடு உருவாக்குவதற்கு ஏற்றது            |
| `auto/fast`    | வேகமானது     | குறைந்த தாமதம் கொண்ட எடையிட்ட தேர்வு                                               |
| `auto/cheap`   | மலிவானது     | செலவுக்கு உகந்த வழித்தடம் (குறைந்த செலவு முதலில்)                                  |
| `auto/offline` | ஆஃப்லைன்     | அதிக ஒதுக்கீடு கிடைக்கும் வழங்குநர்களுக்கு முன்னுரிமை அளிக்கிறது                   |
| `auto/smart`   | நுண்ணறிவானது | தரத்திற்கு முன்னுரிமை + சிறந்த மாதிரி கண்டறிதலுக்கான அதிக ஆய்வு விகிதம் (10%)      |
| `auto/lkgp`    | lkgp         | வெளிப்படையான LKGP (இயல்புநிலை `auto` போலவே)                                        |
| `auto/chaos`   | குழப்பம்     | இணையான fan-out, ஒவ்வொரு வழங்குநருக்கும் ஒரு மாதிரி (பிழைச் செலுத்தல் அல்ல)         |

### வகை × அடுக்கு சேர்க்கை (`auto/<category>:<tier>`)

OpenRouter பாணியிலான பின்னொட்டுகள், **எந்த வகையான வழித்தடம்** (வகை) என்பதையும் **அதை எவ்வாறு மேம்படுத்துவது** (அடுக்கு) என்பதையும் பிரிக்கின்றன; எனவே அவற்றை நீங்கள் விருப்பப்படி சேர்த்துப் பயன்படுத்தலாம் (#4235 கட்டம் B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **வகைகள்** (திறனின் அடிப்படையில் வேட்பாளர் தொகுப்பை வடிகட்டும்): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` பார்வைத் திறனுள்ள மாதிரிகளைத் தக்கவைக்கும்; `reasoning` பகுத்தறிவு/சிந்தனை மாதிரிகளைத் தக்கவைக்கும்.
- **அடுக்குகள்** (மதிப்பீட்டு எடைகள் / தொகுப்பு வடிகட்டியைத் தேர்ந்தெடுக்கும்): `fast` (விரைவாக வழங்குதல்) · `cheap` (`floor` என்பதன் மாற்றுப்பெயர், செலவு சேமிப்பு) · `reliable` (சர்க்யூட்-பிரேக்கர் ஆரோக்கியம் + தாமத நிலைத்தன்மை) · `free` / `pro` (`classifyTier` வழியாக மாதிரி அடுக்கின் அடிப்படையில் தொகுப்பை வடிகட்டும் — இலவச அடுக்கு எதிராக பிரீமியம்).

| எடுத்துக்காட்டு        | தீர்மானிக்கப்படும் வடிவம்                                                          |
| ---------------------- | ---------------------------------------------------------------------------------- |
| `auto/coding:fast`     | நிரலாக்கத் தொகுப்பு, குறைந்த தாமத எடைகள்                                           |
| `auto/coding:cheap`    | நிரலாக்கத் தொகுப்பு, செலவுக்கு உகந்தது (`auto/coding:floor` என்பதன் மாற்றுப்பெயர்) |
| `auto/reasoning:pro`   | பகுத்தறிவு/சிந்தனை மாதிரிகள் மட்டும், பிரீமியம் அடுக்கு                            |
| `auto/vision`          | பார்வைத் திறனுள்ள மாதிரிகள் (அடுக்கு இல்லை → சமநிலைப்படுத்தப்பட்ட எடைகள்)          |
| `auto/multimodal:free` | பன்முறைமைத் திறனுள்ள மாதிரிகள், இலவச அடுக்கு மட்டும்                               |

செல்லுபடியாகும் எந்த `auto/<category>[:<tier>]` வடிவமும் தேவைக்கேற்ப தீர்மானிக்கப்படும்; தேர்ந்தெடுக்கப்பட்ட ஒரு துணைத்தொகுப்பு `/v1/models` மற்றும் டாஷ்போர்டில் விளம்பரப்படுத்தப்படும் (`open-sse/services/autoCombo/builtinCatalog.ts` கோப்பிலுள்ள `AUTO_SUFFIX_VARIANTS`). வடிகட்டல் **fail-open** முறையில் செயல்படும் — ஒரு கட்டுப்பாட்டுடன் இணைக்கப்பட்ட எந்த மாதிரியும் பொருந்தவில்லை என்றால், வழித்தடம் ஒருபோதும் செயலிழக்காதவாறு முழுத் தொகுப்பும் பயன்படுத்தப்படும். மைய மதிப்பீட்டாளர் (`combo.ts`) மாற்றப்படவில்லை; வகை/அடுக்கு வடிகட்டி `buildAutoCandidates` இல் பயன்படுத்தப்படுகிறது.

> **நேரடி மாதிரி நுண்ணறிவு:** `ARENA_ELO_SYNC_ENABLED` கொடி இயக்கப்பட்டிருக்கும்போது, தானியங்கு வழித்தடப் பொருத்தம் நேரடி **Arena ELO** தரவரிசைகள் + **models.dev** அடுக்குத் தரவுகளால் வழிநடத்தப்படுகிறது (இல்லையெனில் நிலையான பொருத்த வரைபடத்திற்கு மாறும்).

**பயன்படுத்துவது எப்படி:**

```bash
# OpenAI வடிவமைப்பை ஆதரிக்கும் எந்த IDE அல்லது CLI கருவியும்
அடிப்படை URL: http://localhost:20128/v1
API விசை:  <your-endpoint-key>

# உங்கள் குறியீடு/கட்டமைப்பில், மாதிரியை இவ்வாறு அமைக்கவும்:
model: "auto"                 # சமநிலைப்படுத்தப்பட்ட இயல்புநிலை
model: "auto/coding"          # நிரலாக்கப் பணிகளுக்கு மிகச் சிறந்தது
model: "auto/fast"            # கிடைப்பவற்றில் அதிவேகமானது
model: "auto/cheap"           # ஒவ்வொரு டோக்கனுக்கும் மிக மலிவானது
```

**என்ன நடக்கிறது:**

1. `src/sse/handlers/chat.ts` இல் உள்ள `auto/` முன்னொட்டை OmniRoute கண்டறிகிறது
2. தரவுத்தளத்திலிருந்து அனைத்து **செயலில் உள்ள வழங்குநர் இணைப்புகளையும்** வினவுகிறது
3. செல்லுபடியாகும் நற்சான்றுகள் (API விசை அல்லது OAuth டோக்கன்) கொண்டவற்றை மட்டும் வடிகட்டுகிறது
4. ஒவ்வொரு இணைப்பிற்குமான மாதிரியைத் தீர்மானிக்கிறது (`connection.defaultModel` அல்லது வழங்குநரின் முதல் மாதிரி)
5. நினைவகத்தில் ஒரு **மெய்நிகர் சேர்க்கையை** உருவாக்குகிறது (DB-இல் சேமிக்கப்படாது)
6. தேர்ந்தெடுக்கப்பட்ட மாறுபாட்டின் எடைச் சுயவிவரம் + LKGP உத்தியைப் பயன்படுத்தி வழித்தடப்படுத்துகிறது

**முக்கிய பண்புகள்:**

- ✅ **எப்போதும் இயக்கத்தில்:** மாற்றி, சேர்க்கை உருவாக்கம் அல்லது கட்டமைப்பு எதுவும் தேவையில்லை
- ✅ **மாறும் தன்மை:** தற்போது இணைக்கப்பட்டுள்ள வழங்குநர்களைத் தானாகப் பிரதிபலிக்கிறது
- ✅ **அமர்வு ஒட்டுநிலை:** கடைசியாக வெற்றியடைந்த வழங்குநருக்கு முன்னுரிமை வழங்கப்படுவதை LKGP உறுதிசெய்கிறது
- ✅ **பல கணக்குகளை உணர்ந்தது:** ஒவ்வொரு வழங்குநர் இணைப்பும் தனித்தனி வேட்பாளராகிறது
- ✅ **DB எழுதுதல்கள் இல்லை:** மெய்நிகர் சேர்க்கை கோரிக்கைக்காக மட்டுமே இருக்கும்; நிலைத்த சேமிப்புக்கான கூடுதல் சுமை பூஜ்ஜியம்

### ஒவ்வொரு விசைக்குமான வேட்பாளர் கட்டுப்பாடு (#7819, நிலை 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` என்பதற்குப் பிறகுள்ள பின்னொட்டு, அல்லது
அடிப்படை சேனலுக்கான நேரடி `auto`) என்பது ஏற்கெனவே உள்ள மீள்திறன் வாசிப்புகளை மீண்டும் பயன்படுத்தி,
நேரடி அணுகல்தன்மைத் தகவலுடன் அலங்கரிக்கப்பட்ட ஓர் `auto/*` சேனலின் தற்போதைய வேட்பாளர் தொகுப்பைப் பட்டியலிடும்
**வாசிப்பதற்கு மட்டும்** உரிய endpoint ஆகும் (ஒருபோதும் மூல breaker `state` அல்ல):

- வழங்குநர் சர்க்யூட் பிரேக்கர் — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- இணைப்பு cooldown — தீர்மானிக்கப்பட்ட `provider_connections` வரிசையிலுள்ள `rateLimitedUntil` / `testStatus`
- மாதிரி lockout — `isModelLocked(provider, connectionId, model)`

ஒவ்வொரு வேட்பாளரும் இந்த API விசையின் `excluded` கொடியையும் கொண்டிருக்கும். விலக்கல்கள்
ஒவ்வொரு API விசைக்கும் தனித்தனியாகச் சேமிக்கப்படுகின்றன (`auto_candidate_overrides` அட்டவணை, இடம்பெயர்வு `128`) — OmniRoute
`users` அட்டவணை இல்லாத ஒற்றை-tenant அமைப்பு என்பதால், `apiKeyId` என்பதே உண்மையான ஒவ்வொரு அழைப்பாளருக்கும் மிக நெருக்கமான
அடையாளமாகும் — மேலும், தூய்மையானதும் அலகு-சோதனை செய்யப்பட்டதுமான
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) வழியாக
`open-sse/services/autoCombo/virtualFactory.ts` இல் உள்ள வேட்பாளர்-தொகுப்பு இடைநெருக்குப் புள்ளியில் அவை அமல்படுத்தப்படுகின்றன.
இந்த வடிகட்டி **fail-open** முறையில் செயல்படும்: அமைக்கப்படாத apiKeyId/channel அல்லது DB தேடல் தோல்வி ஆகிய இரண்டுமே
தொகுப்பை வடிகட்டப்படாமல் விடும்; எனவே எந்த மேலெழுதல்களையும் கட்டமைக்காத ஓர் இயக்குநர், இந்த அம்சத்திற்கு முன்பிருந்த வழித்தடத்துடன்
பைட்-அளவில் முற்றிலும் ஒரே மாதிரியான வழித்தடத்தைக் காண்பார்.

**தொடர் சிக்கலுக்காக ஒத்திவைக்கப்பட்டது:** ஒவ்வொரு candidate-க்குமான weights + வெளிப்படையான ordering (Level 3
— தற்போதுள்ள weighted/priority strategy பாதைகளுடன் இணைகிறது) மற்றும் ஒவ்வொரு `auto/*`
channel-க்கும் குறிப்பிட்ட `combo.ts` strategy-ஐ pin செய்தல் (Level 4). single-tenant
model-ஐக் கருத்தில் கொண்டு overrides ஒவ்வொரு API key-க்கும் தனித்தனியாக இருக்க வேண்டுமா அல்லது
global ஆக மாற்றப்பட வேண்டுமா என்ற திறந்த கேள்விக்கு #7819 திட்டத்தைப் பார்க்கவும்.

## சேமிக்கப்பட்ட தானியங்கு சேர்க்கைகளுக்கான கணக்கு விருப்பத்தேர்வுகள்

நுண்ணறிவு ஆட்டோ எடிட்டர் ஒரு விருப்பத்தை வழங்குகிறது** கணக்கு விருப்பத்தேர்வுகள்** பிரிவு. ஒவ்வொரு இணைப்பும் விருப்பமானதாகவோ, இயல்பானதாகவோ (இயல்புநிலையாகவோ), ஒதுக்கப்பட்டதாகவோ அல்லது விலக்கப்பட்டதாகவோ இருக்கலாம். பல இணைப்புகள் ஒரு அடுக்கைப் பகிரலாம். முதல் தகுதியான அடுக்குக்குள் ஆட்டோ தேர்ந்தெடுக்கிறது, அதன் scoring/router நடத்தையை அங்கேயே வைத்திருக்கிறது; தோல்வியுற்ற முயற்சிகள் மீதமுள்ள உறுதியான கணக்குகளில் விழும். இந்த சேர்க்கையால் விலக்கப்பட்ட இணைப்புகள் பயன்படுத்தப்படாது.

அமைப்பு `config.accountPreferences` ஆக சேமிக்கப்படுகிறது, ID இணைப்பு மூலம் விசை செய்யப்படுகிறது:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

ஒரு தவிர்க்கப்பட்ட அல்லது வெற்று வரைபடம் ஏற்கனவே உள்ள ரூட்டிங் வைத்திருக்கிறது. விருப்பத்தேர்வுகள் முடக்கப்பட்ட இணைப்புகளை இயக்காது, API-விசை அணுகலை வழங்காது, ஒதுக்கீட்டால் தடுக்கப்பட்ட விண்ணப்பதாரர்களை மீட்டெடுக்க அல்லது பட்ஜெட் சோதனைகளைத் தவிர்க்க முடியாது. ஒவ்வொரு முயற்சியும் அதன் உறுதியான இணைப்பிற்கு மட்டுப்படுத்தப்பட்டுள்ளது, எனவே கணக்கு பின்னடைவு காம்போ ரூட்டருக்குப் பின்னால் அடுக்குகளைத் தாண்ட முடியாது. தற்போதுள்ள அமர்வு தொடர்பு தகுதியான கணக்கைத் தக்க வைத்துக் கொள்ளலாம்; கணக்கைத் தவிர்த்து, ஒரு நேட்டிவ் டர்ன் ஸ்டாப்களுக்குக் கட்டுப்பட்டு, அமைதியாக கணக்குகளை மாற்றுவதற்குப் பதிலாக திரும்பும்.

கட்டமைக்கப்பட்ட விருப்பத்தேர்வுகள் கணக்கு விழிப்புணர்வு தானியங்கு பாதையைப் பயன்படுத்துகின்றன: வரம்பற்ற சூழல்-கேச், ஸ்மார்ட்-பைப்லைன், குழப்பம் மற்றும் நிழல் குறுக்குவழிகள் அனுப்பப்படவில்லை. இந்தக் கோரிக்கைகளுக்கு ஊக ஹெட்ஜிங் முடக்கப்பட்டுள்ளது. மற்ற சேர்க்கை உத்திகள் இந்த அமைப்பை விளக்கவில்லை. ஆட்டோவில் இருந்து காம்போவை மாற்றுவது, பின்னர் மாறுவதற்குச் சேமிக்கப்பட்ட விருப்பங்களை வைத்திருக்கும்.

## உண்மையான Model Id உடன் பொருந்தும் Combo பெயர்கள்

ஒரு combo-வின் `name`, prefix இல்லாத model id-க்கு ஒரே மாதிரியாக இருப்பது (எ.கா., `gpt-5.5` எனப் பெயரிடப்பட்ட combo) ஒரு பிழை அல்ல; அது **வேண்டுமென்றே வடிவமைக்கப்பட்ட, ஆதரிக்கப்படும் முறை**: [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940)-இல் ஆவணப்படுத்தப்பட்டுள்ள, ஒவ்வொரு model id-க்குமான provider fallback இயங்குமுறை இதுவாகும். Prefix இல்லாத model-id resolution-க்கு முன்பாக combo resolution சரிபார்க்கப்படுவதால் (`src/sse/services/model.ts`-இல் உள்ள `getComboForModel()`), prefix இல்லாத id `gpt-5.5`-க்கான கோரிக்கை, நேரடியாக ஒற்றை provider-க்கு அனுப்பப்படுவதற்குப் பதிலாக combo-வின் targets வழியாக (எ.கா., `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) வழிமாற்றப்படுகிறது — இது [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227)-க்காக உருவாக்கப்பட்ட combo-before-rewrite முன்னுரிமையை மீண்டும் பயன்படுத்துகிறது; மேலும் இது `tests/unit/responses-combo-resolution-3227.test.ts` மற்றும் `tests/unit/combo-name-codex-responses-rewrite.test.ts` ஆகியவற்றால் regression சோதனை செய்யப்படுகிறது.

உண்மையான model id-ஐ மறைக்கும் பெயருடன் combo ஒன்றை உருவாக்குவதோ அல்லது அதற்கு அத்தகைய பெயரை மாற்றுவதோ **ஒருபோதும் நிராகரிக்கப்படாது** — அவ்வாறு செய்வது ஆவணப்படுத்தப்பட்ட இந்தப் பணிப்பாய்வை முறித்துவிடும். அதற்குப் பதிலாக (#8530), (புதிய) பெயர் உண்மையான model id உடன் மோதும்போது, `POST /api/combos` மற்றும் `PUT /api/combos/[id]` ஆகியவை response-இல் செயல்பாட்டைத் தடுக்காத `warning` field-ஐ இணைக்கின்றன:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

தொடக்கத்தின்போது, `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ஒரு model id-ஐ மறைக்கும் ஒவ்வொரு existing combo-வையும் பட்டியலிடும் ஒற்றை வரி `[STARTUP]` எச்சரிக்கையையும் பதிவு செய்கிறது. இதனால், #6940-இன்படி வேண்டுமென்றே செய்வதற்குப் பதிலாகத் தற்செயலாக இதைச் சந்திக்கும் operators-க்கு ஓர் அறிகுறி கிடைக்கிறது. கண்டறிதலுக்கான helper, `src/lib/combos/modelNameCollision.ts`-இல் உள்ளது.

## Client-இலிருந்து Custom Combo ஒன்றை அழைத்தல்

சேமிக்கப்பட்ட combos (அமைப்புகள் → Combos), client ஆனது combo-வின் **துல்லியமான பெயரை** `model` field-இல் அனுப்பும்போது மட்டுமே பயன்படுத்தப்படும் — combo பெயருக்கு fuzzy அல்லது partial matching எதுவும் இல்லை; மேலும் `auto/` prefix-உம் இதில் ஈடுபடாது. Resolution வரிசை (`src/sse/services/model.ts`-இல் உள்ள `getComboForModel()`):

1. துல்லியமான combo-name பொருத்தம் (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

பொதுவான இரண்டு இடர்ப்பாடுகள்:

- **`auto` உங்கள் combos-ஐப் பயன்படுத்தாது.** `auto`/`auto/*` அதன் சொந்த zero-config candidate pool-ஐ உருவாக்குகிறது; மேலும் ஒரு combo-வின் பெயர் உண்மையிலேயே `auto` என இருந்தால் மட்டுமே சேமிக்கப்பட்ட combos-ஐப் பரிசீலிக்கும் (பரிந்துரைக்கப்படவில்லை). Combo வழியாக வழிமாற்ற, அதன் துல்லியமான பெயரை அனுப்பவும் — `auto`-ஐ அல்ல.
- **`openrouter/auto` என்பது கட்டணம் வசூலிக்கப்படும் உண்மையான OpenRouter தயாரிப்பு** ("Auto Best Available"); அது OmniRoute alias அல்ல. இது OpenRouter registry-இன் (`open-sse/config/providers/registry/openrouter/index.ts`) ஒற்றை static model entry ஆகும்; இதற்குத் தனியாகக் கட்டணம் வசூலிக்கப்படும். `auto` pools-இலிருந்து இதை விலக்க, அமைப்புகள் → Routing → கட்டண model-களை மறை என்பதைப் பயன்படுத்தவும்.

இங்கு ஆவணப்படுத்தப்பட்டுள்ள இந்த அசல் குழப்பம் குறித்த விவரங்களுக்கு [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) மற்றும் [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) ஆகியவற்றைப் பார்க்கவும்.

## இது எவ்வாறு இயங்குகிறது (தொடர்ச்சியான ஆட்டோ-காம்போஸ்)

ஆட்டோ-காம்போ எஞ்சின் ஒவ்வொரு கோரிக்கைக்கும் ஒரு சிறந்த provider/model பயன்படுத்தி மாறும் வகையில் தேர்ந்தெடுக்கிறது** 16-காரணி மதிப்பெண் செயல்பாடு** ( `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` இல் வரையறுக்கப்பட்டுள்ளது). இயல்புநிலை எடைகளின் கூட்டுத்தொகை `1.0`; தனிப்பயன் எடைகள் `normalizeScoringWeights()` ஆல் மறுசீரமைக்கப்படுகின்றன. பதினாறு — `cacheAffinity` மற்றும் `resetWindowAffinity` — இல் இரண்டு `0` இன் இயல்பு எடையைக் கொண்டுள்ளன; `reliability` `DEFAULT_WEIGHTS` இல் `0` கொண்டு செல்கிறது, ஆனால் `0.03` பொதுவான தொகுப்புகளில் மற்றும் `reliability-first` இல் `0.04`, மற்றும் `quality` பேக்குகளில் `0.02` கொண்டுள்ளது (`0.03` இல் `quality-first`): அவை இன்னும் ஒவ்வொரு வேட்பாளருக்கும் கணக்கிடப்படுகின்றன, மேலும் `cacheAffinity` கேட்கள் ப்ராம்ப்ட்-கேச் டியூப்லிகேஷன் மூலம் மதிப்பெண்ணுக்கு வெளியே உள்ள காரணிகளைக் குறைக்காது. செய்ய.

**தொகை:** `DEFAULT_WEIGHTS` இல் அறிவிக்கப்பட்டுள்ளபடி `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` ; பயனர்-கட்டமைக்கப்பட்ட எடைகள் மதிப்பெண் பெறுவதற்கு முன் `normalizeScoringWeights()` மூலம் விநியோகமாக மறுசீரமைக்கப்படுகின்றன.

## பயன்முறைத் தொகுப்புகள்

`open-sse/services/autoCombo/modePacks.ts`-இல் முன்பே வரையறுக்கப்பட்ட 6 எடைச் சுயவிவரங்கள் உள்ளன. தேர்வை ஒரு இலக்கை நோக்கிச் சாய்க்க, ஒவ்வொரு தொகுப்பும் இயல்புநிலை எடைகளை முழுமையாக மாற்றுகிறது. ஒவ்வொரு தொகுப்பின் கூட்டுத்தொகையும் ஏற்கனவே `1.0` ஆகும் (நான்கு தசம இடங்களில் அச்சிடப்படும்போது `0.9999`), எனவே ஒரு தொகுப்பு செயலில் இருக்கும்போது `normalizeScoringWeights()` அர்த்தமுள்ள வகையில் திருத்துவதற்கு எதுவும் இல்லை — கீழேயுள்ள மதிப்புகள்தான், முழுமையாக்கலைக் கணக்கில் கொண்டால், மதிப்பெண் கணிப்பான் பயன்படுத்துபவை.

- **தொகுப்புகள் `quality` மற்றும் `reliability` ஆகியவற்றைக் கொண்டுள்ளன** (`quality 0.02`, `quality-first 0.03`; `reliability 0.03`, `reliability-first 0.04`) மற்றும் எடை வரைபடத்தை முழுமையாக மாற்றுகின்றன (`weights = pack`, ஒன்றிணைப்பு அல்ல). `DEFAULT_WEIGHTS` ஆனது `quality 0.03 / reliability 0` என்பதைக் கொண்டுள்ளது; `balanced`/`default` என்பதைத் தேர்ந்தெடுப்பது அந்த இயல்புநிலைகளைத் தக்கவைக்கிறது, ஒரு தொகுப்பைத் தேர்ந்தெடுப்பது மேலே உள்ள அந்தத் தொகுப்பின் மதிப்புகளைப் பயன்படுத்துகிறது. தொடக்கநிலை குளத்தில் (இதுவரை கவனிப்புகள் எதுவும் இல்லை, எனவே `quality 0.5` மற்றும் `reliability 1`) இந்த இரண்டு காரணிகளும் பொதுவான தொகுப்பின் கீழ் `+0.04` (`0.03 + 0.01`), `quality-first`-இன் கீழ் `+0.045`, மற்றும் `reliability-first`-இன் கீழ் `+0.05` ஆகியவற்றைச் சேர்க்கின்றன.
- ஒவ்வொரு தொகுப்பிலும் `tierAffinity`, `specificityMatch` மற்றும் `resetWindowAffinity` ஆகியவை வெளிப்படையாக `0` ஆக அமைக்கப்பட்டுள்ளன.
- ஒவ்வொரு தொகுப்பின் முக்கியத்துவமும் ஒரு பார்வையில்:
  - **ship-fast** → latencyInv 0.3048 + health 0.2667 (குறைந்த தாமதமுள்ள, ஆரோக்கியமான இணைப்புகள்)
  - **cost-saver** → costInv 0.3324 (மிகக் குறைந்த விலையுள்ள டோக்கன்கள் வெற்றி பெறும்)
  - **quality-first** → taskFit 0.3524 + stability 0.1429 + quality 0.03, அனைத்து தொகுப்புகளிலும் மிக உயர்ந்தது (பணிக்கு ஏற்ற சிறந்த, நிலையான மாதிரி)
  - **offline-friendly** → quota 0.3324 + health 0.2667 (வேகம்/செலவைப் பொருட்படுத்தாமல் அதிகபட்ச உபரி திறன்)
  - **reliability-first** → health 0.3524 + stability 0.1905 + reliability 0.04, அனைத்து தொகுப்புகளிலும் மிக உயர்ந்தது (மிகக் குறைவான எதிர்பாராத நிகழ்வுகள்)
  - **chaos-mode** → health 0.4000 + taskFit 0.1905 (`auto/chaos` எடைத் தொகுப்பு அதன் குழு உறுப்பினர்களுக்கு ஒதுக்கும் எடைகள்; இணையான விரிவாக்கம் இந்த எடைகளைப் படிப்பதில்லை, மேலும் இது பிழை-செலுத்தல் சுயவிவரம் அல்ல, [CHAOS-MODE.md](../guides/CHAOS-MODE.md#autochaos-parallel-fan-out)-ஐப் பார்க்கவும்)

### கோரிக்கை-வாரியான கட்டுப்பாடுகள் (தலைப்புகள்) — #6023 / #6024 / #6025 / #3470

### `weighted` சொற்பொருள்

`weighted` என்பது a** ஒரு கோரிக்கைக்கு விகிதாசார சீரற்ற டிரா** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), சமநிலைப்படுத்தி அல்ல:

- ஒவ்வொரு கோரிக்கையும் ஈர்க்கிறது** ஒன்று** நிகழ்தகவுடன் படி `weight / totalWeight`; மீதமுள்ள படிகள் அந்த கோரிக்கைக்கான ஃபால்பேக் செயினாக இறங்கு எடை மூலம் வரிசைப்படுத்தப்படுகின்றன.
- `0` (அல்லது காணவில்லை) எடை கொண்ட ஒரு படி** வரையப்படவில்லை** மற்ற படிகள் > 0 — எடையைக் கொண்டிருக்கும் போது, வரையப்பட்ட படி தோல்வியடைந்த பிறகு மட்டுமே அது ஒரு பின்னடைவாக இருக்கும். எப்போது மட்டும்** அனைத்து** எடைகள் 0 என்றால் தேர்வு சீராக மாறுமா.
- — வழங்குநரின் சர்க்யூட் பிரேக்கர் `OPEN`, இணைப்பு கூல்டவுன், மாடல் லாக்அவுட் — போன்ற அனைத்து இலக்குகளையும் கொண்ட படிகள் அது நிகழும் முன் டிராவில் இருந்து அகற்றப்படும் (`open-sse/services/combo/targetResolution.ts`), எனவே ஒரு ஆரோக்கியமான படி தற்காலிகமாக ஒவ்வொரு கோரிக்கையையும் வெல்ல முடியும்.
- `stickyWeightedLimit` (combo config, default `1` = off) மீண்டும் வரைவதற்கு முன் பல தொடர்ச்சியான வெற்றிகளுக்கான வரையப்பட்ட படியை பின் செய்கிறது.

கடுமையான சுழற்சியைப் பயன்படுத்த `round-robin`; `weighted` இல் உள்ள சம எடைகள் புள்ளியியல் — க்கு கடுமையான — இருப்பு இல்லை.

### ஏஜென்டிக் பைப்லைன் முறை

குறைந்தது இரண்டு மாடல்களைக் கொண்ட `pipeline` காம்போ `config.agenticOrchestration.enabled` உடன் planner/executor ரூட்டிங்கைத் தேர்ந்தெடுக்கலாம். முதல் இலக்கு திட்டமிடல் மற்றும் இறுதி பதில்களுக்கு சொந்தமானது; இரண்டாவது இலக்கு கிளையன்ட்-நேட்டிவ் கருவி அழைப்புகளை வெளியிடுகிறது. OmniRoute கோரிக்கை நெறிமுறையிலிருந்து கருவி-முடிவு தொடர்ச்சிகளைக் கண்டறிந்து, மற்றொரு டூல் சுற்று தேவையா என்று திட்டமிடுபவரைக் கேட்கிறது, மேலும் செயல்பாட்டாளர் அல்லது திட்டமிடுபவரை கிளையன்ட் எதிர்கொள்ளும் இறுதிப் படியாக மாறும்.

விருப்பத்தேர்வு `config.agenticOrchestration.contextCompaction` ஒவ்வொரு திட்டமிடுபவர் அல்லது செயல்படுத்துபவர் அனுப்புவதற்கு முன் ஒரு தனி பேலோட் பட்ஜெட்டைப் பயன்படுத்துகிறது. அதை வெளிப்படையாக இயக்கவும்:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

இவை ஆபரேட்டரால் தேர்ந்தெடுக்கப்பட்ட வரிசைப்படுத்தப்பட்ட JSON எழுத்து வரவு செலவுத் திட்டங்களாகும், டோக்கன் சூழல் சாளரங்கள் அல்லது உத்தரவாதமான அப்ஸ்ட்ரீம் வரம்புகள் அல்ல. சரியான மாதிரி IDs இயல்புநிலையை மீறுகிறது. வாசலுக்கு மேலே, சுருக்கமானது ஒரே மாதிரியான கருவி வரையறைகளை நீக்குகிறது, டைஜெஸ்ட் மூலம் பெரிதாக்கப்பட்ட கருவி ஆதாரங்களை ஒழுங்கமைக்கிறது மற்றும் இலக்கு விகிதத்தை நோக்கி பழைய முழுமையான வரலாற்றுக் குழுக்களை நீக்குகிறது. இது system/developer வழிமுறைகள், சமீபத்திய பயனர் கோரிக்கை, இணையான calls/results உள்ளிட்ட கடைசி கருவி சுற்று மற்றும் Gemini இன் முன்னணி ரூட்டிங் வழிமுறைகளை வைத்திருக்கிறது. உயர்மட்ட வழிமுறைகள் மற்றும் கருவி அமைப்புகள் பாதுகாக்கப்படுகின்றன. ஒரு புறக்கணிப்பு குறிப்பான் நீக்கப்பட்ட வரலாற்றைப் பதிவு செய்கிறது; இது உறுதியான டிரிம்மிங், சொற்பொருள் சுருக்கம் அல்ல. பின் செய்யப்பட்ட சூழல் இன்னும் பட்ஜெட்டை விட அதிகமாக இருந்தால், மாடலைத் தொடர்புகொள்வதற்கு முன் கோரிக்கை 413ஐத் தரும். சுருக்கம் முடக்கப்பட்டிருந்தால் அல்லது வரம்புக்குக் கீழே கோரிக்கை மாறாமல் செல்கிறது.

கருவி-முடிவு தொடர்ச்சிகளில், இரண்டு தொடர்ச்சியான நிறைவு சுற்றுகள் அதே கருவி அழைப்புகளை மாற்றமடையாத முடிவுகளுடன் மீண்டும் செய்யும் போது அல்லது இரண்டு தொடர்ச்சியான சுற்றுகளில் வெளிப்படையாகக் குறிக்கப்பட்ட ஒவ்வொரு முடிவும் தோல்வியடையும் போது OmniRoute செயல்பாட்டை நிறுத்துகிறது. மாற்றப்பட்ட முடிவுகள் மீண்டும் மீண்டும் அழைப்புகளை அனுமதிக்கின்றன (எடுத்துக்காட்டாக, வாக்குப்பதிவு). புதிய பயனர் கோரிக்கையின் பேரில் காவலர் மீட்டமைக்கிறது, இணையான அழைப்புகளை ஒரு சுற்றில் குழுவாக்கி, Anthropic, அரட்டை நிறைவுகள், பதில்கள் மற்றும் Gemini வரலாறுகளை ஆதரிக்கிறது. திட்டமிடுபவர் காரணத்தைப் பெறுகிறார் மற்றும் மற்றொரு கருவியைக் கோரினாலும் இறுதிப் பதிலைச் சொந்தமாக வைத்திருப்பார்.

இரண்டாவது இலக்குக்குப் பிறகு கூடுதல் மாதிரிகள் எக்ஸிகியூட்டர் காப்புப்பிரதிகளுக்கு ஆர்டர் செய்யப்படுகின்றன. ஒரு தோல்வியுற்ற HTTP பதில் அல்லது போக்குவரத்து விதிவிலக்கு அடுத்த செயல்பாட்டாளருக்கு முன்னேறுகிறது, அதே திட்டமிடல் முடிவு மற்றும் சொந்த கருவிகளைக் கொண்டு செல்கிறது, ஆனால் அந்த செயல்படுத்துபவரின் சொந்த நடவடிக்கை மற்றும் தீர்க்கப்பட்ட இணைப்பு. SSE ஸ்ட்ரீமிங் உட்பட, முதல் வெற்றிகரமான பதில் மாறாமல் திருப்பி அனுப்பப்பட்டது; ஒரு வெற்றிகரமான ஸ்ட்ரீம் தொடங்கிய பிறகு தோல்விகளை இங்கே மீண்டும் முயற்சிக்க முடியாது. அனைத்து செயல்படுத்துபவர்களும் தோல்வியுற்றால், கடைசி தோல்வி திரும்பும். வாடிக்கையாளர் அனுப்புவதை நிறுத்துகிறார்.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

செயல்படுத்துபவர் ஒரு பதிலில் பல சுயாதீன அழைப்புகளை வெளியிடலாம். ஒவ்வொரு முடிவையும் திட்டமிடுபவர் மதிப்பாய்வு செய்வதன் மூலம், சார்பு அழைப்புகள் பின்னர் கிளையன்ட் கருவி-முடிவு திருப்பங்களில் கையாளப்படுகின்றன. `maxToolRounds` `8` க்கு இயல்புநிலை மற்றும் `1`–`32` ஐ ஏற்றுக்கொள்கிறது; அடைந்தவுடன், திட்டமிடுபவர் சிறந்த இறுதிப் பதிலைத் தர வேண்டும். தேர்ந்தெடுக்கப்பட்ட கிளையன்ட் எதிர்கொள்ளும் பதில் அசல் ஸ்ட்ரீமிங் விருப்பத்தைப் பாதுகாக்கும் அதே வேளையில் உள் திட்டமிடுபவர் முடிவுகள் இடையகப்படுத்தப்படுகின்றன.

### `round-robin` ஒட்டும் தொகுதி மற்றும் கணக்கு விரிவாக்கம்

ரவுண்ட்-ராபின் தொகுப்பானது, ஒரு படிக்கு ஒரு கோரிக்கை அல்ல:

- `stickyRoundRobinLimit` (combo config, பின்னர் `comboStickyRoundRobinLimit`, பின்னர் `settings.stickyRoundRobinLimit`, இயல்புநிலை** 3** ) சுழலும் முன் பல தொடர்ச்சியான வெற்றிகளுக்கு அதே இலக்கை வைத்திருக்கிறது. ஒரு கோரிக்கை சுழற்சிக்கான சேர்க்கை மேலெழுதலை `1` க்கு அமைக்கவும். காம்போ எடிட்டர் பயனுள்ள மதிப்பு மற்றும் எந்த லேயரில் இருந்து வந்தது என்பதைக் காட்டுகிறது.
- `connectionAwareExpansion` (காம்போ config, பின்னர் அமைப்புகள், இயல்புநிலை** பொய்** ) சுழற்சிக்கு முன் ஒவ்வொரு வழங்குநர்-நிலைப் படியையும் ஒவ்வொரு கணக்கின் இலக்குகளாக விரிவுபடுத்துகிறது. குரூப்-பி உத்திகள் (முன்னுரிமை, எடையிடப்பட்ட, ரவுண்ட்-ராபின், சீரற்ற, p2c, குறைந்தபட்சம் பயன்படுத்தப்பட்ட, செலவு-உகந்ததாக, lkgp, நிரப்ப-முதல், கண்டிப்பான-சீரற்ற, சூழல்-உகந்த, கேச்-உகந்த, சூழல்-ரிலே, இணைவு, குழாய், jev) இது இயக்கப்படும் வரை வழங்குநர்-நிலை பார்வையை வைத்திருக்கும். காம்போ எடிட்டர் பரம்பரை / ஆன் / ஆஃப் அம்பலப்படுத்துகிறது; inherit உலகளாவிய இயல்புநிலையை (ஆஃப்) பயன்படுத்துகிறது.
- ப்ராம்ட்-கேச் லோகாலிட்டி ரூட்டிங் (`promptCacheAffinityEnabled`, இயல்புநிலை** உண்மை** ) பொருத்தப்பட்ட கேச் விசைகள் ஒரே கணக்கில் இருக்கும், பின் செய்யப்பட்ட இணைப்புகளை மறுவரிசைப்படுத்துகிறது. ரவுண்ட்-ராபின் மற்றும் ஒரு கணக்கிற்கு பின் செய்யப்பட்ட படிகளில் எடையுள்ள சுழற்சியை விட இது முன்னுரிமை பெறுகிறது. உங்களுக்கு கடுமையான சுழற்சி தேவைப்பட்டால், அமைப்புகள் → காம்போ இயல்புநிலைகளின் கீழ் அதை முடக்கவும். ஒவ்வொரு சேர்க்கை மீறல் இல்லை.

ஒரு மாதிரியில் பல கணக்கு சுழற்சிக்கு, விரும்பவும்** ஒரு டைனமிக் கணக்கு படி** (காலி `connectionId`, முழு குளம்) ஒட்டும் வரம்பு `1`, மூன்று பின் செய்யப்பட்ட `connectionId` s அல்ல. RR கவுண்டர் முன்னேறும் போது, பின் செய்யப்பட்ட படிகள் மற்றும் அஃபினிட்டி அதே கணக்கில் சரிந்துவிடும்.

## ஒன்றிணைப்பு உத்தி

`fusion` என்பது ஒற்றை இலக்கைத் தேர்ந்தெடுக்காத **ஒரே** உத்தியாகும். இது prompt-ஐ
**ஒவ்வொரு panel model-க்கும் இணையாக** அனுப்பி, பின்னர் அமைக்கக்கூடிய **judge model** மூலம்
அனைத்து panel பதில்களிலிருந்தும் ஒற்றை இறுதிப் பதிலைத் தொகுக்கிறது. Upstream `decolua/9router`
(OpenRouter-இன் Fusion வடிவமைப்பு) இலிருந்து port செய்யப்பட்டது; செயலாக்கம் `open-sse/services/fusion.ts`-இல் உள்ளது.

இது செயல்படும் விதம்:

0. **கருவிகளைக் கொண்ட கோரிக்கைக்கான bypass** — காலியாக இல்லாத `tools` array-ஐக் கொண்டதும்,
   `tool_choice` வெளிப்படையாக `"none"` என அமைக்கப்படாததுமான கோரிக்கை panel-ஐ முழுமையாகத் தவிர்க்கிறது:
   அது `tools`/`tool_choice`-ஐ மாற்றமின்றி அனுப்பி, ஒற்றை model-க்கு (அமைக்கப்பட்ட judge அல்லது
   `panel[0]`) நேரடியாக route செய்யப்படுகிறது. Panel உறுப்பினர்களுக்குக் கருவி அணுகல் இல்லை;
   மேலும் judge-இன் தொகுப்பு வழிகாட்டுதல் tool-call வெளியீட்டைத் தவிர்க்கச் சொல்கிறது. எனவே,
   agentic/tool-calling clients தொகுக்கப்பட்ட உரைக்குப் பதிலாக உண்மையான tool-call முடிவைப்
   பெறுகின்றன (#6771).
1. **Fan-out** (கருவிகளைக் கொண்டிராத கோரிக்கைகளுக்கு மட்டும்) — prompt ஒவ்வொரு panel
   model-க்கும் ஒரே நேரத்தில் அனுப்பப்படுகிறது; tools அகற்றப்பட்டு, streaming இல்லாததாகக்
   கட்டாயப்படுத்தப்படுகிறது (தொகுப்பதற்கு judge-க்கு முழுமையான உரை தேவை).
2. **Quorum-grace சேகரிப்பு** — `minPanel` பதில்கள் கிடைத்தவுடன், தாமதிக்கும் model-களுக்காக
   ஒரு குறுகிய grace timer தொடங்குகிறது; அதன் பிறகு சேகரிக்கப்பட்டவற்றைக் கொண்டு fusion
   தொடர்கிறது. இது கடின timeout வரம்பிற்குள், மிக மெதுவான model சுவர்-கடிகார நேரத்தில்
   ஏற்படுத்தும் தாமதத்தைக் கட்டுப்படுத்துகிறது.
3. **Judge தொகுப்பு** — panel பதில்கள் பெயரறியாதவையாக மாற்றப்படுகின்றன (`Source 1`,
   `Source 2`, … — இதனால் judge model brand-ஐ அல்லாமல் உள்ளடக்கத்தையே மதிப்பிடுகிறது);
   பின்னர் அவை judge-க்கு வழங்கப்படுகின்றன. அது ஒருமித்த கருத்து / முரண்பாடுகள் / பகுதியளவு
   உள்ளடக்கம் / தனித்துவமான நுண்ணறிவுகள் / கவனிக்கப்படாத பகுதிகள் ஆகியவற்றைப் பகுப்பாய்வு
   செய்து, **ஒரே** அதிகாரபூர்வமான பதிலை எழுதுகிறது. Judge call, client-இன் அசல்
   `stream` flag + tools-ஐத் தக்கவைத்துக்கொள்கிறது; எனவே streaming மற்றும் downstream
   கருவிப் பயன்பாடு தொடர்ந்து செயல்படும்.
4. **சீரான தரக்குறைப்பு** — 0 panel பதில்கள் → `503`; சரியாக 1 பதில் மட்டும் எஞ்சினால் →
   அந்தப் பதில் நேரடியாகத் திருப்பி அனுப்பப்படும் (ஒன்றிணைக்க எதுவுமில்லை); ஒற்றை-model
   panel நேரடியாகப் பதிலளிக்கும்.

ஒரு panel உறுப்பினர், மற்றொரு combo-ஐக் குறிக்கும் `combo-ref` படியாகவும்
(`{kind: "combo-ref", comboName: "..."}`) இருக்கலாம் — அது **ஒற்றை black-box panel குரலாகத்**
தீர்க்கப்படுகிறது (குறிப்பிடப்பட்ட combo-க்குள் முழுமையான recursive dispatch; அந்த combo-வின் சொந்த
இலக்குகளுக்கான fan-out அல்ல). மற்ற எல்லா combo-ref-ஐப் பயன்படுத்தும் உத்திகளும் ஏற்கனவே பயன்படுத்தும்
அதே depth/cycle பாதுகாப்பு இதற்கும் பொருந்தும் (#6764).

### கட்டமைப்பு

Combo-வின் `config` blob-இல் அமைக்கப்படுகிறது (schema migration இல்லை — ஏற்கனவே உள்ள
`combos` table-ஐ மீண்டும் பயன்படுத்துகிறது):

| புலம்                                    | வகை      | இயல்புநிலை        | நோக்கம்                                                                                                              |
| :--------------------------------------- | :------- | :---------------- | :------------------------------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | முதல் panel model | இறுதிப் பதிலைத் தொகுக்கும் model                                                                                     |
| `config.fusionTuning.minPanel`           | `number` | `2`               | Grace timer தொடங்குவதற்கு முன் தேவைப்படும் வெற்றிகரமான பதில்கள் (`[2, panelSize]` வரம்பிற்குள் கட்டுப்படுத்தப்படும்) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`            | Quorum எட்டப்பட்ட பிறகு தாமதிப்பவர்களுக்காகக் காத்திருக்கும் காலம்                                                   |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`           | பதிலளிக்காமல் சிக்கிய ஒரு model கோரிக்கையைத் தாமதப்படுத்த முடியாதபடி அமைக்கப்படும் முழுமையான உச்சவரம்பு              |

இயல்புநிலைகள் `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`)-இல் உள்ளன.

### எடுத்துக்காட்டு

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

பின்னர், மற்ற combo-களைப் போலவே இதையும் அழைக்கவும்: `{"model":"fusion-panel","messages":[...]}`.

## மெய்நிகர் Auto-Combo தொழிற்சாலை

Auto Combo எஞ்சினுக்குத் முன்-வரையறுக்கப்பட்ட காம்போக்கள் தேவையில்லை. அதற்குப் பதிலாக, `open-sse/services/autoCombo/virtualFactory.ts` இயக்கநேரத்திலேயே தேர்வுக்குரியவற்றை உருவாக்குகிறது:

1. `getProviderConnections({ isActive: true })`-ஐப் பெறுகிறது (இயக்கப்பட்ட அனைத்து இணைப்புகளும்)
2. செல்லுபடியாகும் நற்சான்றுகளைக் கொண்டவற்றை வடிகட்டுகிறது (`hasUsableOAuthToken()` வழியாக API விசை அல்லது காலாவதியாகாத OAuth டோக்கன்)
3. மாடல் கிடைப்புத்தன்மை + விலை நிர்ணயத்திற்காக `getProviderRegistry()` உடன் குறுக்குச் சரிபார்ப்பு செய்கிறது
4. ஒவ்வொரு `(provider, model, connection)` மும்மத்திற்கும், ஒரு `VirtualAutoComboCandidate`-ஐ உருவாக்குகிறது
5. அனுப்பீட்டு இலக்காக `connection.defaultModel`-ஐ (அல்லது பதிவகத்தின் முதல் மாடலை) தேர்ந்தெடுக்கிறது
6. 16-காரணி `scorePool()` மற்றும் மாறுபாட்டின் எடைத் தொகுப்பைப் பயன்படுத்தி ஒவ்வொரு தேர்வுக்குரியதற்கும் மதிப்பெண் அளிக்கிறது
7. `handleComboChat()`-க்காக உருவான நினைவகத்திலுள்ள `AutoComboConfig`-ஐ வழங்குகிறது — தரவுத்தளத்தில் ஒருபோதும் நிலைநிறுத்தப்படாது

இதன் பொருள், **`auto/*` இயக்கப்பட்ட ஒரு புதிய வழங்குநரைச் சேர்ப்பது தேர்வுக்குரியவற்றின் தொகுப்பைத் தானாகவே விரிவுபடுத்தும்** — காம்போவை கைமுறையாகத் திருத்த வேண்டியதில்லை. ஒவ்வொரு கோரிக்கைக்கும் மெய்நிகர் காம்போ மீண்டும் உருவாக்கப்படுவதால், புதிதாகச் சேர்க்கப்பட்ட அல்லது புதிதாக ஆரோக்கியமான நிலையை அடைந்த இணைப்புகள் உடனடியாகத் தேர்ந்தெடுக்கப்படுகின்றன.

## சுய-சீரமைப்பு

- **தற்காலிக விலக்கம்**: மதிப்பெண் < 0.2 → 5 நிமிடங்களுக்கு விலக்கப்படும் (படிப்படியான பின்வாங்கல், அதிகபட்சம் 30 நிமிடங்கள்)
- **சுற்றுத் துண்டிப்பான் நிலை விழிப்புணர்வு**: OPEN → தானாக விலக்கப்படும்; HALF_OPEN → சோதனைக் கோரிக்கைகள்
- **சம்பவ முறை**: >50% OPEN → ஆய்வை முடக்கி, நிலைத்தன்மையை அதிகபட்சமாக்கும்
- **காத்திருப்புக்குப் பிந்தைய மீட்பு**: விலக்கத்திற்குப் பிறகு, முதல் கோரிக்கை குறைக்கப்பட்ட காலக்கெடுவுடன் ஒரு "சோதனை" கோரிக்கையாக இருக்கும்

## Bandit ஆய்வு

5% கோரிக்கைகள் (அமைவாக்கக்கூடியது) ஆய்வுக்காகச் சீரற்ற வழங்குநர்களுக்கு வழிப்படுத்தப்படுகின்றன. சம்பவ முறையில் இது முடக்கப்படும்.

## API

**பிரத்யேகமான `POST /api/combos/auto` முனைப்புள்ளி எதுவும் இல்லை** — Auto-Combo இரண்டு வழிகளில் பயன்படுத்தப்படுகிறது:

1. **பூஜ்ஜியக் கட்டமைப்பு (பரிந்துரைக்கப்படுகிறது):** `model: "auto"` அல்லது `model: "auto/<variant>"` உடன் ஏதேனும் chat completion கோரிக்கையை அனுப்பவும். மெய்நிகர் factory ஒவ்வொரு கோரிக்கைக்கும் combo-வை உருவாக்கும் — நிலைத்த சேமிப்போ API அழைப்புகளோ தேவையில்லை.

2. **`strategy: "auto"` உடன் நிலைத்துச் சேமிக்கப்பட்ட combo:** `POST /api/combos` வழியாக வழக்கமான combo-வை உருவாக்கி, `strategy: "auto"` என்பதையும் `config.auto.weights` / `config.auto.candidatePool` என்பவற்றையும் அமைக்கவும். அதே மதிப்பீட்டு engine பயன்படுத்தப்படும்; combo ஆனது `combos`-இல் சேமிக்கப்பட்டு, ID மூலம் மீண்டும் பயன்படுத்தக்கூடியதாக இருக்கும்.

கண்டறிதலுக்காக, `GET /api/combos/auto` ஒவ்வொரு variant-ஐயும் அதன் தீர்மானிக்கப்பட்ட candidate pool மற்றும் `context_length` / `max_output_tokens` உடன் பட்டியலிடுகிறது — இவை candidate pool-இன் window-கள் அனைத்திலும் உள்ள MAX மதிப்புகளாகும். Client-கள் (எ.கா. opencode plugin) `0` என்பதற்குப் பதிலாக இந்த மதிப்புகளை விளம்பரப்படுத்த வேண்டும்: பூஜ்ஜிய context ஆனது opencode-இன் தானியங்கி compaction-ஐ முழுமையாக முடக்குகிறது; இதனால் gateway-இன் history purge context-ஐ அழிக்கும் வரை session-கள் வளர்கின்றன. MAX-ஐ விளம்பரப்படுத்துவது பாதுகாப்பானது, ஏனெனில் auto-combo context முன்-வடிகட்டி, மிகப் பெரிய கோரிக்கைகளைப் பெரிய-window candidate-களுக்கு வழிப்படுத்துகிறது.

```bash
# பூஜ்ஜியக் கட்டமைப்புப் பயன்பாடு (combo உருவாக்கம் இல்லை)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# வழக்கமான combos முனைப்புள்ளி வழியாக நிலைத்துச் சேமிக்கப்பட்ட auto combo
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router உத்திகள்

நிலைத்துச் சேமிக்கப்பட்ட `strategy: "auto"` combo-கள் `config.routerStrategy` (அல்லது மரபுவழி
`config.auto.routerStrategy`) என்பதைப் பின்வருவனவற்றில் ஒன்றாக அமைக்கலாம்:

- `rules` — இயல்புநிலை எடையிடப்பட்ட மதிப்பீடு
- `score` — கட்டமைக்கப்பட்ட அதிகபட்ச எடையிடப்பட்ட மதிப்பெண்ணைத் தேர்ந்தெடுக்கிறது. துல்லியமான சமநிலைகளில் கட்டமைக்கப்பட்ட
  candidate வரிசை பாதுகாக்கப்படும்; ஏற்கெனவே உள்ள `explorationRate`, முழுமையாக தரவரிசைப்படுத்தப்பட்ட pool-இலிருந்து மாதிரியைத் தேர்ந்தெடுக்கிறது.
- `cost` / `eco` — மிகக் குறைந்த விலையுள்ள ஆரோக்கியமான provider
- `latency` / `fast` — நம்பகத்தன்மைக் கழிவுடன் கூடிய மிகக் குறைந்த p95 latency
- `sla-aware` / `sla` — p95 latency, error-rate மற்றும் விருப்பத்திற்குரிய
  cost SLO-களைப் பூர்த்தி செய்யும் candidate-களுக்கு முன்னுரிமை அளிக்கிறது
- `lkgp` — கடைசியாக நன்றாகச் செயல்பட்டதாக அறியப்பட்ட provider-க்கு முதலில் முன்னுரிமை
- `nadir` — prompt-க்கு pool-இல் எந்த model தேவை என்பதை [Nadir](https://getnadir.com)-இன் decision API-யிடம் கேட்கிறது;
  இது விருப்பத்துடன் இயக்கப்படுவது, தோல்வியின்போது `rules`-க்கு திறந்தவாறு மாறும்

### Router உத்திகள் விரிவாக

Auto-combo engine, `config.routerStrategy` (அல்லது மரபுவழி `config.auto.routerStrategy`)
மூலம் மாற்றக்கூடிய 7 செருகக்கூடிய **RouterStrategy** செயலாக்கங்களை வழங்குகிறது.
ஒவ்வொரு உத்தியும் ஒரு `RoutingContext` (பணி வகை, tool/vision குறிப்புகள், token மதிப்பீடு, விருப்பத்திற்குரிய SLA கொள்கை, விருப்பத்திற்குரிய
கடைசியாக நன்றாகச் செயல்பட்ட provider) அடிப்படையில் candidate pool-இலிருந்து ஒரு provider-ஐத் தேர்ந்தெடுக்கிறது.

#### 1. `rules` (இயல்புநிலை) — 16-காரணி எடையிடப்பட்ட மதிப்பீடு

ஏற்கெனவே உள்ள மதிப்பீட்டு engine-ஐச் சுற்றிப் பொதிகிறது. `OPEN` circuit-breaker
candidate-களை வடிகட்டிவிட்டு, தற்போதைய பணி வகை மற்றும் `getTaskFitness()` உடன் `scorePool()`-ஐ இயக்கி,
அதிக மதிப்பெண் பெற்ற provider-ஐத் தேர்ந்தெடுக்கிறது.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**எப்போது பயன்படுத்துவது**: இயல்புநிலை. அனைத்து signal-களுக்கும் இடையே சமநிலையான பரிமாற்றம் தேவைப்படும்போது பயன்படுத்தவும்.

**மாற்றுப் பெயர்**: `rules` (மாற்றுப் பெயர் இல்லை)

---

#### 2. `cost` / `eco` — மிகக் குறைந்த விலையுள்ள ஆரோக்கியமான provider

Candidate pool-ஐ `costPer1MTokens` அடிப்படையில் (ஏறுவரிசையில்) வரிசைப்படுத்தி, மிகக் குறைந்த விலையுள்ளதைத் தேர்ந்தெடுக்கிறது.
முதலில் `OPEN` candidate-களை வடிகட்டுகிறது.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**எப்போது பயன்படுத்துவது**: செலவு உணர்திறன் கொண்ட பணிச்சுமைகள், தொகுதிச் செயலாக்கம் அல்லது பின்னணிப் பணிகள்.

**மாற்றுப் பெயர்கள்**: `cost`, `eco`

---

#### 3. `latency` / `fast` — நம்பகத்தன்மைக் கழிவுடன் கூடிய மிகக் குறைந்த p95 latency

`p95LatencyMs + (errorRate * 1000)` அடிப்படையில் வரிசைப்படுத்துகிறது. பெயரளவிலான latency குறைவாக இருந்தாலும்,
நம்பகமற்ற provider-கள் கீழ்நிலையில் தரவரிசைப்படுத்தப்படுவதை error-rate கழிவு உறுதிசெய்கிறது.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**எப்போது பயன்படுத்துவது**: நிகழ்நேர chat, autocomplete அல்லது
ஊடாடும் coding assistant-கள் போன்ற latency உணர்திறன் கொண்ட பணிச்சுமைகள்.

**மாற்றுப் பெயர்கள்**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — latency/error/cost SLO இணக்கம்

கட்டமைக்கப்பட்ட SLO கொள்கையை ஒவ்வொரு candidate-ம் எவ்வளவு நன்றாகப் பூர்த்தி செய்கிறது என்பதன் அடிப்படையில் மதிப்பிடுகிறது:

| காரணி                 | எடை | சூத்திரம்                                                     |
| --------------------- | --- | ------------------------------------------------------------- |
| தாமத மதிப்பெண்        | 35% | `threshold / max(value, ε)`                                   |
| பிழை மதிப்பெண்        | 35% | `threshold / max(value, ε)`                                   |
| செயல்நிலை மதிப்பெண்   | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)             |
| செலவு மதிப்பெண்       | 10% | `threshold / max(value, ε)` அல்லது தலைகீழாக இயல்பாக்கப்பட்டது |
| நிலைத்தன்மை மதிப்பெண் | 5%  | தலைகீழாக இயல்பாக்கப்பட்ட தாமதத்தின் திட்ட விலக்கம்            |

`hardConstraints: true` என இருக்கும்போது, தேர்வுகள் முதன்மையாக **மீறல் மதிப்பெண்**
(அவை ஏதேனும் SLO வரம்பை எவ்வளவு மீறுகின்றன) அடிப்படையிலும், பின்னர் ஒருங்கிணைந்த மதிப்பெண் அடிப்படையிலும் வரிசைப்படுத்தப்படும். இல்லையெனில்,
ஒருங்கிணைந்த மதிப்பெண் மட்டுமே பயன்படுத்தப்படும்.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... கொள்கைக்கு எதிராக ஒவ்வொரு தேர்வுக்கும் மதிப்பெண் அளிக்கிறது: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA புலங்கள்** (காம்போ கட்டமைப்பில் அமைக்கப்படுபவை):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**எப்போது பயன்படுத்துவது**: கடுமையான தாமதம், பிழை விகிதம் அல்லது செலவு வரவுசெலவுத் திட்டங்களைக் கொண்ட உற்பத்திப் பணிச்சுமைகளுக்கு.

**மாற்றுப் பெயர்கள்**: `sla-aware`, `sla`

---

#### 5. `lkgp` — கடைசியாக நன்றாகச் செயல்பட்டதாக அறியப்பட்ட வழங்குநருக்கு முன்னுரிமை

**கடைசியாக நன்றாகச் செயல்பட்டதாக அறியப்பட்ட வழங்குநர்** அமைக்கப்பட்டிருந்தால், முதலில் அதனை முயற்சித்து, பின்னர்
`rules` உத்திக்குப் பின்வாங்கும். அமர்வு ஒட்டுநிலைக்கு இது பயனுள்ளதாக இருக்கும் — ஒரு உரையாடலில்
தொடர்ந்து வரும் கோரிக்கைகளை அதே வழங்குநர் கையாளுவார்.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules உத்திக்குப் பின்வாங்குகிறது
    return getStrategy("rules").select(pool, context);
  }
}
```

**எப்போது பயன்படுத்துவது**: தொடர்ந்து வரும் கோரிக்கைகளை அதே வழங்குநர் கையாள வேண்டும் என நீங்கள் விரும்பும்
பல-திருப்ப உரையாடல்களுக்கு (எ.கா., தற்காலிகச் சேமிப்பு, சூழல் தொடர்ச்சி அல்லது விலை நிலைத்தன்மைக்காக).

**மாற்றுப் பெயர்**: `lkgp` (மாற்றுப் பெயர் இல்லை)

#### 6. `nadir` — Nadir வழியாகத் தூண்டுரை-அறிந்த மாதிரித் தேர்வு

மேலே உள்ள ஒவ்வொரு உத்தியும் அவற்றின் சொந்த தொலைஅளவீட்டுத் தரவின் அடிப்படையில் தேர்வுகளைத் தரவரிசைப்படுத்துகின்றன; அவற்றில் எதுவும்
கோரிக்கையைப் படிப்பதில்லை. `nadir`, கடைசி பயனர் திருப்பத்தையும் தொகுப்பிலுள்ள மாதிரி ID-களையும்
[Nadir](https://getnadir.com)-இன் முடிவு API-க்கு (`POST /v1/bucket`) அனுப்பி, அந்தப் பட்டியலிலிருந்து
Nadir தேர்ந்தெடுக்கும் மாதிரிக்கு வழிப்படுத்துகிறது (`simple` → திறன் கொண்டவற்றில் மிகவும் மலிவான மாதிரி, `complex` → முன்னணி
மாதிரி). அந்த மாதிரியை வழங்கும் இணைப்பு இன்னும் `rules` மூலமே தேர்ந்தெடுக்கப்படுகிறது; எனவே ஒதுக்கீடு,
செயல்நிலை மற்றும் செலவு ஆகியவை எந்தக் கணக்கைத் தேர்ந்தெடுக்க வேண்டும் என்பதைத் தொடர்ந்து தீர்மானிக்கும்.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

இந்த இரண்டு சரங்களுக்கும் `OMNIROUTE_NADIR_API_KEY` மற்றும் `OMNIROUTE_NADIR_BASE_URL` ஆகியவை சூழல் மாறி மாற்றுத் தேர்வுகளாக உள்ளன.
சுயமாக ஹோஸ்ட் செய்யப்பட்ட Nadir-க்கு மட்டுமே `baseUrl` தேவை (இறுதியில் வரும் `/v1` ஏற்றுக்கொள்ளப்படும்).
விசையில்லாத அழைப்புகள் Nadir-இன் அநாமதேய அடுக்கிற்குச் செல்லும்; அது ஒவ்வொரு IP-க்கும் வீத வரம்பைக் கொண்டுள்ளது. ஒரு விசையுடன்
([ஒன்றை உருவாக்கவும்](https://app.getnadir.com/dashboard/api-keys)), ஒவ்வொரு முடிவும்
உங்கள் Nadir முகப்புப் பலகையில் பதிவுசெய்யப்படும். முழுமையான அமைப்பும் சரிபார்ப்பும்:
[getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/).

பெட்டிக்கு வெளியே அனுப்பப்படுபவை: கடைசி பயனர் செய்தியின் உரை (முதல் 16k எழுத்துகள்), தேர்வுக்குரிய
மாதிரி ID-கள் மற்றும் ஒரு `source: "omniroute"` சேனல் குறிச்சொல். முறைமைத் தூண்டுரை, வரலாறு, கருவிகள் அல்லது
தலைப்புகள் எதுவும் அனுப்பப்படாது.

தோல்வி ஏற்பட்டாலும் செயல்பாட்டைத் தொடரும் வகையில் இது நடந்து கொள்ளும்: காலக்கெடு முடிதல் (இயல்புநிலை 2000 ms), 2xx அல்லாத பதில், அணுக முடியாத
ஹோஸ்ட், தவறான வடிவமைப்புள்ள பதில் அல்லது தொகுப்புக்கு வெளியேயான தேர்வு ஆகியவை `rules`
முடிவுக்குத் திரும்பும்; மேலும் காரணத்தின் தொடக்கத்தில் `NadirStrategy: fallback (…)` சேர்க்கப்படும். அழைப்பு தோல்வியடைந்த பிறகு,
இந்த உத்தி 30 s நேரத்திற்கு பிணையத்தைத் தவிர்க்கும்; எனவே ஒரு சேவைத் தடை, ஒவ்வொரு கோரிக்கைக்கும் ஒரு காலக்கெடு இழப்பை ஏற்படுத்துவதற்குப் பதிலாக,
ஒவ்வொரு 30 s-க்கும் ஒரு காலக்கெடு இழப்பை மட்டுமே ஏற்படுத்தும். Nadir உண்மையில் தேர்வு செய்தால் மட்டுமே வழிப்படுத்தல் நிகழ்வுகள் `strategy: "nadir"`
என அறிக்கையிடும்.

**எப்போது பயன்படுத்துவது**: பல மாதிரி அடுக்குகளை உள்ளடக்கிய தொகுப்பில் கலவையான கடினத்தன்மை கொண்ட போக்குவரத்திற்கு (ஒரு சிறிய, ஒரு நடுத்தர
மற்றும் ஒரு முன்னணி மாதிரி), எப்போதும் முன்னணி மாதிரியைப் பயன்படுத்துவதால் ஏற்படும் செலவைக் குறைக்க விரும்பும்போது.

**மாற்றுப் பெயர்**: `nadir` (மாற்றுப் பெயர் இல்லை)

### தனிப்பயன் வழிப்படுத்தி உத்திகள்

பொது API வழியாக உங்கள் சொந்த `RouterStrategy` செயலாக்கத்தைப் பதிவுசெய்யலாம்:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // உங்கள் வழிப்படுத்தல் தர்க்கம் இங்கே
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

பின்னர் அதைப் பயன்படுத்தவும்:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## Auto வகைகளின் மீள்பார்வை

அடிப்படை `auto` (இயல்புநிலை) மற்றும் `autoPrefix.ts`-இல் அறிவிக்கப்பட்டுள்ள 6 `AutoVariant` மதிப்புகள் உட்பட, **7 அழைக்கக்கூடிய மாதிரி ID-கள்** உள்ளன:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` தானாகவே 6 மதிப்புகளைப் பட்டியலிடுகிறது; 7-வது விருப்பம் "வகை இல்லை" — அடிப்படை `auto` — இது `parseAutoPrefix()` மூலம் `variant: undefined` ஆகக் கையாளப்படுகிறது.)

## Auto-Combo-இல் அடுக்குகள் எவ்வாறு பொருந்துகின்றன

16-காரணி மதிப்பீட்டுச் செயல்பாடு (`open-sse/services/autoCombo/scoring.ts`), அடுக்கு
உறுப்பினர் நிலையை இரண்டு சிக்னல்களாகக் கருதுகிறது: `tierPriority` (0.0476) மற்றும் `tierAffinity` (0.0476). முழுமையான
`DEFAULT_WEIGHTS` தொகுப்பிற்கு மேலே உள்ள அதிகாரப்பூர்வ [மதிப்பீட்டுக் காரணி அட்டவணையை](#how-it-works-persisted-auto-combos) பார்க்கவும் — ஒவ்வொரு பேக்கிற்குமான மேலெழுதல்கள் (ship-fast/cost-saver/quality-first/
offline-friendly) "ஒவ்வொரு பேக்கிற்குமான எடைச் சுயவிவரங்கள்" அட்டவணையில் பட்டியலிடப்பட்டுள்ளன.

அடுக்கு மட்டும் **Tier 1**-ஐ முதலில் வருமாறு கட்டாயப்படுத்தாது — Tier 1-இன் தாமதம் மோசமாக இருந்தாலோ அல்லது
செலவு-தர விகிதம் உகந்ததாக இல்லாவிட்டாலோ, Tier 2 வெற்றி பெறும். அடுக்கு வரிசையை கட்டாயப்படுத்த, காம்போ
உத்தி `priority`-ஐப் பயன்படுத்தி, வழங்குநர்களை அடுக்கின்படி வரிசைப்படுத்தவும்.

Tier 1-க்கு (சந்தா) வலுவான முன்னுரிமை அளிக்க, `tierPriority` எடையை அதிகரிக்கவும்:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

அடுக்கு வரையறைகள் மற்றும் வழங்குநர் வகைப்பாட்டிற்கு [`docs/guides/TIERS.md`](../guides/TIERS.md)-ஐப் பார்க்கவும்.

## சோதனை & கவரேஜ்

### தீர்மானிக்கும் ரூட்டிங்-முடிவு அணி (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` ரூட்டிங் நிரூபிக்கிறது** முடிவு** அனைத்து 21 பொது உத்திகளில் இறுதி முதல் இறுதி வரை உண்மையான காம்போ பைப்லைன் மூலம் கேலி செய்யப்பட்ட அப்ஸ்ட்ரீம். கவரேஜ் உள்ளடக்கியது:

- அனைத்து 21 `ROUTING_STRATEGY_VALUES` உத்திகள் (வரிசைப்படுத்தப்பட்ட, எடையிடப்பட்ட, செலவு, சூழல், இணைவு, ...).
- `quota-share` (உள்) இறுதி முதல் இறுதி வரை: உண்மையான `selectQuotaShareTarget` மடிப்பு (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`) வழியாக DRR நியாயத்தன்மை + செறிவூட்டல் நீக்கம்.
- ஒவ்வொரு இலக்கு எண்ணிக்கையிலும்`context-relay` உலகளாவிய-கையாளுதல் கவரேஜ்.

இந்தத் தொகுப்பு CI (`test:integration` job) இல் `--test-concurrency=1` மற்றும் `--test-force-exit` உடன் இயங்குகிறது, எனவே இது உறுதியானது மற்றும் நேரடி சான்றுகள் தேவையில்லை.

| `npm run test:combo:live:vps`          | நேரடி OmniRoute சேவையகத்திற்கு எதிராக HTTP அழைக்கிறது ( `COMBO_LIVE_BASE_URL` அமைக்கவும்)         |

இந்த புகை சோதனைகள் உண்மையான கம்பி பாதையை (காம்போ → வழங்குநர் → நிறைவு) செயல்படுத்துகிறது. நேரடி நற்சான்றிதழ்கள் மற்றும் VPS அணுகல் தேவைப்படுவதால் அவை வேண்டுமென்றே CI இலிருந்து விலக்கப்பட்டுள்ளன.
