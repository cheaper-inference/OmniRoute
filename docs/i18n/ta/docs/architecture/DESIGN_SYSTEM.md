## 1. கூறுகள் எங்கு உள்ளன

- **கிட்.** `packages/ui-kit/src` என்பது, `packages/ui-kit/UPSTREAM.md`-இல் பின் செய்யப்பட்ட commit-இன் upstream `src/`-இன் byte-for-byte நகலாகும் (அதில் உரிம அங்கீகாரமும் பதிவுசெய்யப்பட்டுள்ளது); உள்ளூர் patch-களை `PATCHES.md` பட்டியலிடுகிறது (எதுவுமில்லை). இது build ஏதுமின்றி source ஆகப் பயன்படுத்தப்படுகிறது: `next.config.mjs` அதை transpile செய்கிறது, மேலும்
  `tsconfig.json`, `@omniroute/ui-kit` → `packages/ui-kit/src` என்றும் `@omniroute/ui-kit/*` →
  `packages/ui-kit/src/*` என்றும் map செய்கிறது (`vitest.config.ts` மற்றும் `vitest.mcp.config.ts` ஆகியவற்றிலும் இதே alias உள்ளது). கிட் component ஒன்றை அதன் subpath மூலம் import செய்யவும் (`@omniroute/ui-kit/table`, `@omniroute/ui-kit/page-header`…); `@omniroute/ui-kit` barrel வழியாக ஒருபோதும் import செய்ய வேண்டாம்: அந்த barrel ஒவ்வொரு component-ஐயும் (date picker உட்பட)
  ஒவ்வொரு importer-க்குள்ளும் இழுத்துவருகிறது. கிட் stylesheet, `src/app/globals.css` வழியாக நுழைகிறது
  (`@import "../../packages/ui-kit/src/ci-styles.css"`, முழுமையான sheet: மைய `ci-ui.css` மற்றும் ஒவ்வொரு pattern family-யும்).
- **டோக்கன்கள்.** `packages/ui-kit/src/ci-tokens.css`, `--ci-*` டோக்கன்களை அறிவிக்கிறது; `src/app/globals.css`
  அவற்றை பழைய OmniRoute பெயர்களுடன் (`--color-*`, `--radius-*`, `--font-sans`/`--font-mono`,
  `--table-*`, `--orch-status-*`, `--color-fd-*`) இணைக்கிறது; இதனால் ஏற்கனவே உள்ள `var(--color-*)` வாசிப்புகளும் Tailwind
  utility-களும் தொடர்ந்து செயல்படுகின்றன. புதிய code, Tailwind utility-களை (`bg-surface`, `text-text-muted`,
  `border-border`, `text-success`, `bg-success-bg`, `bg-chart-1`…) அல்லது கிட் class-களைப் பயன்படுத்துகிறது — hex மதிப்பை ஒருபோதும் பயன்படுத்தாது
  (`tests/unit/design-kit-bridge.test.ts` இந்த bridge-ஐ அமல்படுத்துகிறது). `text-primary`,
  `--text-color-primary` வழியாக `--color-primary-ink` ஆகத் தீர்மானிக்கப்படுகிறது; எனவே
  `bg-primary`/`border-primary` accent surface-ஐத் தக்கவைத்திருக்கும்போது primary text வாசிக்கக்கூடியதாக இருக்கும்: Editions-இன் கீழ் அது கிட்டின்
  `--ci-color-accent-active` (light-இல் அடர்ந்த copper `#99562f`, dark-இல் copper accent); Classic-இன் கீழ்,
  light-இல் lime-800 மற்றும் dark-இல் lime accent. Chart series-கள்
  `--color-chart-1` … `--color-chart-5` ஆகியவற்றைப் பயன்படுத்துகின்றன.
- **தீம்கள்.** `<html className="ci-theme">` (`src/app/layout.tsx`) ஆவணத்தை கிட் theme-இல் சேர்க்கிறது.
  விருப்பம் `light`, `dark` அல்லது `system` ஆகும் (`src/shared/constants/appConfig.ts`-இல்
  `THEME_CONFIG.defaultTheme = "system"`; `system`, `prefers-color-scheme`-ஐப் பின்பற்றுகிறது). `src/store/themeStore.ts`-இல் உள்ள `applyTheme()`
  (`src/app/layout.tsx`-இல் inline செய்யப்பட்டு hydration-க்கு முன் இயங்கும் `THEME_BOOT_SCRIPT`-ஆலும் பிரதிபலிக்கப்படுகிறது)
  `data-theme="dark"|"light"`-ஐ அமைத்து, அதே நேரத்தில் `<html>`-இல் `.dark` class-ஐ toggle செய்கிறது.
  கிட்டின் dark token தொகுப்பு, `data-theme="dark"`-ஐ அடிப்படையாகக் கொண்டது (`packages/ui-kit/src/ci-tokens.css`);
  OmniRoute-இன் சொந்த dark override-களும் (`globals.css`-இல் உள்ள `.dark` block) பழைய Tailwind `dark:`
  utility-களும் `.dark` class-ஐ அடிப்படையாகக் கொண்டவை. Accent color preset-கள் எதுவுமில்லை: accent எப்போதும்
  கிட்டிலிருந்தே வருகிறது; store load ஆகும்போது பழைய build ஒன்றிலிருந்து persist செய்யப்பட்ட preset நீக்கப்படுகிறது.
- **வண்ணத் தொகுப்புகள்.** இரண்டும் கிட்டிலிருந்தே வருகின்றன (`src/shared/constants/appearancePalette.ts`): இயல்புநிலையான `editions` மற்றும்
  `classic`. Editions என்பது `<html>`-இல் உள்ள கிட்டின் `data-ci-appearance="editions"` attribute ஆகும்; அதை
  `ci-editions.css` (`ci-ui.css` மூலம் import செய்யப்படுகிறது), `data-theme` உடன் இணைக்கிறது; Classic என்பது அந்த attribute இல்லாத நிலையாகும்.
  Root layout அந்த attribute-ஐ server-render செய்கிறது; எனவே எதையும் சேமிக்காத (அல்லது JS இல்லாத) பார்வையாளர்
  dashboard, login, `/status`, error page-கள், `/docs` மற்றும் PWA என ஒவ்வொரு surface-இலும் Editions-ஐப் பெறுகிறார். தேர்வு,
  அதே `theme` store-இல் theme-க்கு அடுத்ததாக persist செய்யப்படுகிறது (`src/store/themeStore.ts`-இல் `palette`, `setPalette()`, `applyPalette()`)
  மற்றும் paint-க்கு முன் `THEME_BOOT_SCRIPT` மூலம் பயன்படுத்தப்படுகிறது
  (`src/shared/utils/themeBootScript.ts`, layout-இன் `<head>`-இல் inline செய்யப்படுகிறது); சேமிக்கப்பட்ட palette
  `"classic"` ஆக இருக்கும்போது மட்டுமே இது attribute-ஐ அகற்றுகிறது; root layout-க்கு வெளியே உள்ள `src/app/global-error.tsx`,
  அதே store-இலிருந்து அதைப் பயன்படுத்துகிறது. வேறு எந்த element-இலும் `data-ci-appearance`-ஐ வைக்க வேண்டாம்: கிட் அதை
  `html:root:has([data-ci-appearance="editions"])` மூலம் பொருத்துகிறது; எனவே ஒரே ஒரு descendant கூட முழு document-ஐ மாற்றிவிடும்.
  Editions-இன் `data-ci-editions-variant="landing"` variant, marketing page-களுக்கானது; dashboard-க்கானது அல்ல.
  Browser chrome: server, இயல்புநிலையான Editions-ஐ `viewport.themeColor`-இலும் (ஒவ்வொரு
  `prefers-color-scheme`-க்கும் ஒரு tag) web manifest-இலும் render செய்கிறது — `src/shared/constants/pwaThemeColors.ts`-இல் உள்ள
  `PWA_THEME_COLORS`, Editions-இன் `--ci-color-background`-இன் ஒரே பிரதியாகும்
  (`#f3f1e9` / `#11120f`); அது `tests/unit/pwa-theme-colors.test.ts` மூலம் `ci-editions.css`-உடன் பின் செய்யப்பட்டுள்ளது. பின்னர் live
  `<meta name="theme-color">`, சேமிக்கப்பட்ட palette மற்றும் mode-ஐப் பின்பற்றுகிறது: `THEME_BOOT_SCRIPT`, paint-க்கு முன்
  tag-களை மீண்டும் எழுதுகிறது; மேலும் theme store-இன் action-கள் ஒவ்வொரு மாற்றத்தின்போதும் அதைச் செய்கின்றன (`src/shared/utils/themeColorMeta.ts`-இல்
  `resolveThemeColor()` / `applyThemeColor()`; கிட்டின் `ciTokens`-இலிருந்து `CLASSIC_PAGE_BACKGROUND` வாசிக்கப்படுகிறது).
  வெளிப்படையான light/dark theme, ஒவ்வொரு tag-ஐயும் அந்த mode-க்கு அமைக்கிறது; `system`, ஒவ்வொரு scheme-க்கும் ஒரு
  colour-ஐ வைத்திருக்கிறது. Manifest Editions ஆகவே இருக்கும்: விருப்பம் இல்லாமல், ஒவ்வொரு install-க்கும் ஒருமுறை மட்டுமே அது பெறப்படுகிறது.
  Monaco தனது colour-களை ஒரு probe-இலிருந்து வாசிக்கிறது (`monacoKitTheme.ts`);
  Editions-இன் கீழ், probe வாசிப்பு ஒரு synchronous pass-க்காக root `data-theme`-ஐ மாற்றுகிறது; ஏனெனில் கிட்
  Editions light/dark-ஐ root-இலிருந்து தீர்மானிக்கிறது.
- **Component-கள் (adapter-கள்).** `src/shared/components/index.tsx`, OmniRoute component API-ஐ (அதே
  பெயர்கள், default export-கள் மற்றும் prop-கள்) தக்கவைக்கிறது; அதன் பின்னால் உள்ள primitive-கள், கிட்டின் மேல் அமைந்த adapter-களாகும்: form-கள்
  (`Button`, `Input`, `Textarea`, `Checkbox`, `Select`, `Toggle`, `Badge`, `Card`), overlay-கள் மற்றும் feedback
  (`Modal`/`ConfirmModal`, `Tooltip`/`InfoTooltip`, `NotificationToast`, `EmptyState`, `Loading`),
  கட்டமைப்பு (`Collapsible`, `CollapsibleSection`, `SegmentedControl`, `Breadcrumbs`, `Avatar`) மற்றும் table-கள்
  (`DataTable`, `FilterBar`, `ColumnToggle`, `FilterPills`, `PresetSlider`). ஒரு adapter, கிட்
  component-ஐ subpath மூலம் import செய்து, பழைய prop-களை அதில் map செய்கிறது — எடுத்துக்காட்டாக, `Button variant="primary"` என்பது கிட்டின்

## 4. அடாப்டரைச் சேர்ப்பது அல்லது மாற்றுவது

1. `src/shared/components/index.tsx`-இன் பொது API-ஐ மாற்றாமல் வைத்திருங்கள்: அதே export பெயர்கள், default export-கள் மற்றும் ஏற்றுக்கொள்ளப்படும் props-கள். பழைய (legacy) props-களை அடாப்டருக்குள் kit-க்கு மேப் செய்யுங்கள் (`Button.tsx` பார்க்கவும்: `VARIANT_TO_KIT`,
   `SIZE_TO_KIT`).
2. Kit-ஐ துணைப்பாதை (subpath) மூலம் import செய்யுங்கள் (`@omniroute/ui-kit/<component>`).
3. Kit-இன் இடைவெளிகளுக்கான மாற்றுவழிகள் (workarounds) அடாப்டரில் இருக்க வேண்டும் (திருத்தம் ஒரு பாணியாக இருந்தால் `globals.css` `@layer components`-இல்), ஒருபோதும் `packages/ui-kit/src`-இல் அல்ல.
4. `tests/unit/ui/adapters/<name>.test.tsx`-ஐச் சேர்க்கவும் அல்லது புதுப்பிக்கவும். பல அழைப்பாளர்கள் உள்ள அடாப்டருக்கு, மாற்றத்திற்கு முன்னும் பின்னும் ரெண்டர் செய்யப்பட்ட markup-ஐ ஒப்பிடுங்கள் — padding அல்லது wrapper மாற்றங்கள் ஒவ்வொரு திரைக்கும் பரவும்.

## 5. கிட் புதுப்பித்தல்

`npm run check:ui-kit-upstream` `packages/ui-kit/UPSTREAM.md` இல் பொருத்தப்பட்ட பதிப்பை, அப்ஸ்ட்ரீம் ரெப்போவின் புதிய `v*` குறிச்சொல்லுடன் ஒப்பிட்டு, வெளியீடு முடிந்ததும் ஒத்திசைவு கட்டளையை அச்சிடுகிறது.

தினசரி `UI Kit upstream watch` பணிப்பாய்வு (`.github/workflows/ui-kit-upstream-watch.yml`) அதே சரிபார்ப்பை இயக்குகிறது. முள் பின்னால் இருக்கும் போது, `scripts/ci/ui-kit-sync-pr.sh` உருளும் கிளை `chore/ui-kit-sync-latest` இல், மிக உயர்ந்த `release/vX.Y.Z` கிளைக்கு எதிராக ஒரு ஒத்திசைவு PR திறந்திருக்கும். இது ஒருபோதும் ஒன்றிணைவதில்லை: ஒவ்வொரு கிட் வெளியீட்டிற்கும் இன்னும் உள்ளூர் VPS இல் காட்சி சரிபார்ப்பு தேவைப்படுகிறது. புதிய வெளியீடு வெளியாகும் போது கிளை மீண்டும் கட்டப்பட்டு இல்லையெனில் தனியாக விடப்படும். ஒரு திறந்த PR, கையால் தள்ளப்பட்ட கமிட்கள் மேலெழுதப்படவில்லை, மேலும் ஒரு பராமரிப்பாளர் மூடிய ஒரு பதிப்பிற்கான PR புதிய வெளியீடு வரை மூடப்பட்டிருக்கும்.

PR திறக்க முடியாதபோது (இலக்கு வெளியீடு உறைந்திருக்கும், PR கையால் தள்ளப்பட்டது, PR மூடப்பட்டது அல்லது PR டோக்கன் அமைக்கப்படவில்லை) பணிப்பாய்வு ஒரு கண்காணிப்பு சிக்கலைத் திறந்து வைத்திருக்கிறது, அது ஏன் என்று கூறுகிறது.

பணிப்பாய்வு இரண்டு ரகசியங்களைப் பயன்படுத்துகிறது:

- `secrets.UI_KIT_READ_TOKEN`: தனியார் அப்ஸ்ட்ரீம் ரெப்போவுக்கான படிக்க-மட்டும் டோக்கன். பணிப்பாய்வு அப்ஸ்ட்ரீமைப் படிக்க முடியாதபோது (டோக்கன் இல்லை, வேலை செய்வதை நிறுத்திய டோக்கன் அல்லது GitHub அணுக முடியாதது) ரன் பச்சை நிறமாக இருக்கும், ஆனால் ஒரு எச்சரிக்கையை எழுதுகிறது மற்றும் ஒரு தனி சிக்கலைத் திறந்து வைத்திருக்கும், அது ஒருமுறை தன்னை மூடிக்கொண்டால், பின்னர் ரன் மீண்டும் அப்ஸ்ட்ரீமைப் படிக்க முடியும்.
- `secrets.UI_KIT_SYNC_PR_TOKEN`: இந்த களஞ்சியத்தில் உள்ளடக்கம் மற்றும் இழுக்கும் கோரிக்கைகள் எழுதும் அணுகலுடன் கூடிய நுண்ணிய டோக்கன். இயல்புநிலை `GITHUB_TOKEN` ஆல் இங்கே PRs உருவாக்க முடியாது, மேலும் அது திறந்த PR CI தூண்டாது. இந்த டோக்கன் இல்லாமல் பணிப்பாய்வு கிளையை மட்டுமே தள்ளுகிறது.

`scripts/dev/sync-ui-kit.sh <commit|latest> [clone]` அப்ஸ்ட்ரீம் `src/` அந்த உறுதிப்பாட்டில் (`latest` = புதிய `v*` டேக்) `packages/ui-kit/src` க்கு நகலெடுக்கிறது, அனுமதிக்கப்பட்ட ஒற்றை மாற்றத்தைப் பயன்படுத்துகிறது (இது தொடர்புடைய இறக்குமதிகளிலிருந்து `.js` பின்னொட்டைக் குறைக்கிறது), மேலும் பணியிட பதிப்பை `packages/ui-kit/package.json` மற்றும் `package-lock.json` இல் அப்ஸ்ட்ரீம் ஒன்றுக்கு அமைக்கிறது. பின்னர்: `git diff packages/ui-kit` மதிப்பாய்வு செய்யவும், வழங்குநர்கள், அமைப்புகள், சேர்க்கைகள், பயன்பாடு மற்றும் முடிவுப் புள்ளி ஆகிய இரண்டு கருப்பொருள்களிலும் காட்சிப் பதிவைச் செய்து, `npm run check:ui-kit-snapshot` மற்றும் `npm run test:vitest:ui` இயக்கவும், மேலும் அப்ஸ்ட்ரீம் சேஞ்ச்லாக் மூலம் PR திறக்கவும்.

## 6. README வரைபடங்கள்

மூல `README.md` உட்பொதிக்கும் பன்னிரண்டு வரைபடங்கள் (`docs/diagrams/*.svg`), ஒரு நிலையான படத்திற்குப் பயன்படுத்தப்பட்ட கிட்டாகும்; அவை கையால் வரையப்படாமல் உருவாக்கப்படுகின்றன: `scripts/docs/gen-readme-*.mjs`-இல் 13 உருவாக்கி கோப்புகள் (பன்னிரண்டு வரைபடங்கள் மற்றும் `gen-readme-diagrams.mjs` இயக்கி) மற்றும் `tests/unit/docs/readme-*-svg.test.ts`-இல் 12 காலாவதித்தன்மைச் சோதனைகள்—ஒவ்வொரு வரைபடத்திற்கும் ஒன்று—ஒவ்வொன்றும் commit செய்யப்பட்ட கோப்பை அதன் உருவாக்கியின் வெளியீட்டுடன் byte அளவில் ஒப்பிடுகிறது (`test-unit` பணி).

- **டோக்கன்கள்.** `scripts/docs/readme-diagram-theme.mjs`, Editions வண்ணத் தொகுப்பை (இயல்புநிலை தோற்றம்) `packages/ui-kit/src/ci-editions.css`-இலிருந்து நகலெடுக்கிறது (`tests/unit/docs/readme-diagram-theme.test.ts` மூலம் அந்தக் கோப்புடன் நிலைப்படுத்தப்பட்டுள்ளது; இது இரண்டு திட்டங்களிலும் ஒவ்வொரு மேற்பரப்பின் மீதுள்ள ஒவ்வொரு உரை நிறத்திற்கும் WCAG AA-ஐச் சரிபார்க்கிறது; ஒரே விதிவிலக்கான ஒளி `warn`, canvas-இல் கிட்டின் மதிப்பு 4.46:1 ஆக இருப்பதால் 10 % கருமையாக்கப்பட்ட கிட்டின் எச்சரிக்கை நிறமாகும்) மற்றும் கிட்டின் எழுத்துரு அளவீட்டில் (`ci-tokens.css`) உரைப் பங்குகளை வரையறுக்கிறது: கிட்டின் தடிமன்களில் (400/500/600, காட்சிக்கு 500) Switzer மற்றும் எல்லாவற்றிற்குமான எழுத்திடைவெளி; ஆனால் குறியீட்டுப் பங்குகள் (`.cmd`, `.term`, `.term-lg`, `.mono`, `.mono-sm`, `.mono-xs`) மட்டும் IBM Plex Mono-வைப் பயன்படுத்துகின்றன, மேலும் அவை கட்டளைகள், URL-கள், அடையாளங்காட்டிகள் மற்றும் முனையத் திரைகளுக்கு மட்டுமே பயன்படுத்தப்படுகின்றன.
  ஒளித் திட்ட மதிப்புகள் `:root`-இலும், இருண்ட திட்ட மதிப்புகள் கோப்பினுள் `prefers-color-scheme: dark`-க்குப் பின்னாலும் இருப்பதால், ஒவ்வொரு படமும் GitHub-இல் பார்வையாளரின் திட்டத்தைப் பின்பற்றுகிறது.
- **எழுத்துருக்கள்.** GitHub Markdown எந்த CSS-ஐயும் கொண்டுசெல்லாது, மேலும் camo proxy ஒவ்வொரு வெளிப்புறப் பெறுதலையும் தடுக்கிறது; எனவே கிட்டின் எழுத்துவடிவம் கோப்பிற்குள்ளேயே பயணிக்க வேண்டும். ஒவ்வொரு உருவாக்கியின் இறுதிப் படியான `scripts/docs/readme-outline.mjs`, HarfBuzz மூலம் Switzer பங்குகளை வடிவமைத்து, அவற்றை வெக்டர் வெளிக்கோடுகளாக (`<defs>` பாதைகள் மற்றும் `<use>`) வரைகிறது; Switzer-இல் இல்லாத அம்புக்குறிகளும் வடிவியல் குறியீடுகளும் அதன் சொந்த அளவீடுகளில் வரையப்படுகின்றன. உட்பொதிக்கப்பட்ட எழுத்துரு அல்ல, எப்போதும் வெளிக்கோடுகளே: Switzer-இன் உரிமம் (`packages/ui-kit/src/fonts/FFL.txt`), எழுத்துப்படங்களைத் துணைத்தொகுப்பாக்குவதையும் எழுத்துப்பூர்வ ஒப்புதல் இல்லாமல் வடிவமைப்பை மாற்றுவதையும் தடைசெய்து, வெக்டர் வரைபடங்களை அனுமதிக்கிறது; எனவே Switzer `@font-face` அல்லது `data:` URI-ஐ மீண்டும் அறிமுகப்படுத்த வேண்டாம். கோப்பில் எஞ்சியிருக்கும் ஒரே எழுத்துரு, உண்மையான குறியீட்டு உரையாக நீடிப்பவற்றுக்கான OFL IBM Plex Mono துணைத்தொகுப்பாகும் (`scripts/docs/readme-fonts.mjs`); அது அந்த எழுத்துகளிலிருந்து உருவாக்கப்படுகிறது, மேலும் உட்பொதிக்க முடியாத எந்த glyph-உம் பிழையை ஏற்படுத்தும்.
- **மீண்டும் உருவாக்குதல்.** `npm run docs:readme-diagrams`, README வரிசையில் பன்னிரண்டையும் மீண்டும் எழுதி, ஒவ்வொரு கோப்புக்கும் அதன் அளவுடன் ஒரு வரியை அச்சிடுகிறது. தனிப்பட்ட உருவாக்கியையும் தனியாக இயக்கலாம் (`node scripts/docs/gen-readme-<name>.mjs`; `free-tier-budget`-க்கு `node --import tsx/esm` தேவை, ஏனெனில் அதன் புள்ளிவிவரங்கள் `open-sse/config/freeModelCatalog.ts`-இல் உள்ள நேரடி catalog ஏற்றியிலிருந்து வருகின்றன; catalog மாற்றத்தின் CI விளைவு `docs/architecture/QUALITY_GATES.md` → `docs-sync-strict`-இல் உள்ளது). உருவாக்கியையும் SVG-யையும் ஒன்றாக commit செய்யவும்.
- **நிரூபணம்.** `scripts/docs/readme-svg-shots.mjs <file.svg> <outdir>`, GitHub ஒரு கோப்பை வழங்கும் அதே முறையில் (`<img>` tag, camo-வின் `Content-Security-Policy`, `image/svg+xml`) அதை render செய்து, ஓர் ஒளிச் சட்டகத்தையும் ஓர் இருண்ட சட்டகத்தையும் கைப்பற்றி, பக்கம் செய்த வெளிப்புற எழுத்துருக் கோரிக்கைகளை அறிக்கையிடுகிறது (0 ஆக இருக்க வேண்டும்).
- **அளவு வரம்பு.** ஒவ்வொரு கோப்பும் 200 KB-க்குக் கீழ் இருக்க வேண்டும் (ஒவ்வொரு காலாவதித்தன்மைச் சோதனையும் இதை உறுதிசெய்கிறது); எந்த README படத்திற்கும் 500 KB என்பது கடுமையான உச்ச வரம்பாகும் (SVG studio validator-இன் விதி).
- **நகல் மாறாமல், gate-இலிருந்து எண்ணிக்கைகள்.** மறுபெயரிடல் எழுத்துவடிவத்தையும் வண்ணத் தொகுப்பையும் மாற்றியது, சொற்களை அல்ல: ஒவ்வொரு உருவாக்கியும் அதன் வரைபடத்தின் நகலை ஒரு `*_COPY` மாறிலியில் கொண்டுள்ளது (அல்லது நேரடி catalog-இலிருந்து அதை உருவாக்குகிறது); அதுவே வரையப்படும் உரையாகவும், வெளிக்கோடாக்கும் படிநிலையின் உள்ளீடாகவும் உள்ளது. அங்கீகரிக்கப்பட்ட புள்ளிவிவரங்கள் `<text>` node-களில் நீடிக்கின்றன (வெளிக்கோடாக்கப்பட்ட பின் கண்ணுக்குத் தெரியாது, `fill-opacity:0`); அவை `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) மூலம் வாசிக்கப்படுகின்றன. அந்த gate வாசிக்கும் வரைபடங்களின் காலாவதித்தன்மைச் சோதனைகள், உருவாக்கப்பட்ட கோப்பின் மீதும் அதன் validator-களை இயக்குகின்றன; எனவே ஒரு புள்ளிவிவரம் குறியீட்டிலிருந்து விலகினால் சோதனை தோல்வியடையும்—உருவாக்கியில் உள்ள எண்ணை அல்ல, gate வாசிக்கும் மூலத்தையே திருத்தவும்.
