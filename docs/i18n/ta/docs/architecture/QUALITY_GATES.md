இந்த ஆவணம் OmniRoute-இல் உள்ள அனைத்து CI தர வாயில்களுக்குமான அதிகாரப்பூர்வ மேற்கோளாகும்.
ஒவ்வொரு வாயிலையும், அது எதைச் சரிபார்க்கிறது, எந்த CI job-இல் இயங்குகிறது, அது
ratchet baseline அல்லது pass/fail கொள்கையைப் பயன்படுத்துகிறதா, மேலும் அது build-ஐத் தடுக்கிறதா அல்லது ஆலோசனை சார்ந்ததா என்பதை விவரிக்கிறது.

சுருக்கமான தொகுப்புக்கும் allowlist கொள்கைக்கும், `AGENTS.md`-இல் உள்ள
"தர வாயில்கள் & Ratchet-கள்" பகுதியைப் பார்க்கவும். அதே அமைப்பின் முக்கியமான மதிப்பீடு,
முதிர்ச்சி வகைப்பாடு மற்றும் கருவி-சார்பற்ற மறுஉருவாக்கத் திட்டத்திற்கு,
[தர வாயில் செயல்திட்டம்](../ops/QUALITY_GATE_PLAYBOOK.md)-ஐப் பார்க்கவும்.

## கேட் பட்டியல் மற்றும் செயல்படுத்தல் சுயவிவரங்கள்

### வேட்பாளர் சேர்க்கை

CI மற்றும் Quality Gates பணிப்பாய்வுகள் ஒவ்வொன்றும் ஒரு நிலையான தீர்ப்பை வெளியிடுகின்றன: `Gate / CI` மற்றும் `Gate / Quality`. அவர்களின் பதிப்புச் சேர்க்கைக் கொள்கையானது ஒவ்வொரு அப்ஸ்ட்ரீம் வேலையையும் தேவை அல்லது ஆலோசனையின்படி கணக்கிடுகிறது. பொருந்தக்கூடிய தேவையான வேலை வெற்றிபெற வேண்டும்: விடுபட்ட, ரத்துசெய்யப்பட்ட, தவிர்க்கப்பட்ட, நிலுவையில் உள்ள மற்றும் அறியப்படாத முடிவுகள் PASS நிறுவ முடியாது. செல்லுபடியாகும் ஆவணம் மட்டும் அல்லது பட்டியல் மட்டும் வகைப்பாடு ஒரு குறியீடு பாதையை பொருந்தாததாக்கும்; ஒரு சாதாரண வரைவு PR ஏற்றுக்கொள்ளப்பட்ட வேட்பாளர் அல்ல. ஒரு `hotfix` லேபிள் ஆதாரத்தை விட்டுவிடாது.

இரண்டு பணிப்பாய்வுகளும் PRs main/release கிளைகளாக உள்ளடக்கியது, `main` க்கு தள்ளுகிறது , கைமுறையாக அனுப்புதல் மற்றும் ஒன்றிணைத்தல்-குழு நிகழ்வுகள். புஷ், டிஸ்பாட்ச் மற்றும் மெர்ஜ்-குரூப் முழு தேர்வையும் இயக்கவும். நம்பகமான Mergify வரிசை வரைவு பொருந்தக்கூடிய `full-code`/`full-code-e2e` வேலைகளையும் இயக்குகிறது; சாதாரண PRs அவற்றைத் தவிர்க்கவும். கைமுறையாக ஒன்றிணைக்கும் முன், சரியான வேட்பாளர் மீது முழு டிஸ்பாட்சை இயக்கவும். `release/**` க்கு தள்ளுவது இந்த பணிப்பாய்வுகளைத் தொடங்காது; வெளியீடு-பசுமை இணைக்கப்பட்ட தளத்தை தனித்தனியாக கவனிக்கிறது (`docs/ops/RUNNER_BOX.md` → ஹோஸ்ட் செய்யப்பட்ட லேன்). ஃபோர்க்ஸ் மற்றும் மெர்ஜ் குழுக்கள் வேலைகளுக்கு ஹோஸ்ட் செய்யப்பட்ட ரன்னர்களைப் பயன்படுத்துகின்றன, இல்லையெனில் சுய-ஹோஸ்ட் ரன்னர்களைத் தேர்ந்தெடுக்கின்றன; வெளியீட்டிற்கு முன் போதுமான ஹோஸ்ட் செய்யப்பட்ட திறன் சரிபார்க்கப்பட வேண்டும்.

ஒரு சாதாரண PR வேகமான தேர்வை இயக்குகிறது. சேர்க்கைக் கொள்கையின் `full-code` மற்றும் `full-code-e2e` பாதைகள் (E2E, ஒருங்கிணைப்பு, தொகுப்பு கலைப்பொருள், Electron புகை, Bun SQLite, சுற்றுச்சூழல் அமைப்பு மற்றும் நெறிமுறை கிளையன்ட்கள்) மெர்ஜிஃபை வரிசை வரைவில் அல்லது முழு ஓட்டத்தில் மட்டுமே இயங்கும்: `gh workflow run ci.yml --ref <branch>`.

ஒவ்வொரு JSON ரசீதும் சரிபார்க்கப்பட்ட SHA, பணிப்பாய்வு ஓட்டம் மற்றும் முயற்சி ஆகியவற்றை அடையாளம் காட்டுகிறது. CLI checkout/event SHA பொருத்தமின்மையை நிராகரிக்கிறது. பணிப்பாய்வு சோதனைகள் கொள்கை உறுப்பினர்களை தீர்ப்பு வேலையின் `needs` பட்டியலில் இணைக்கின்றன, எனவே புதிய அல்லது அகற்றப்பட்ட பாதை அமைதியாக மறைந்துவிடாது. ரசீதுகள் அவற்றின் சொந்த பணிப்பாய்வுகளை உள்ளடக்கியது, வெளியீடு, வரிசைப்படுத்தல் அல்லது ஏற்கனவே உள்ள ஆலோசனை ஸ்கேனரின் உட்புறங்கள் அல்ல. கிளை விதிகளில் தேவைப்படும் பொருந்தக்கூடிய காசோலைகளைச் செய்வது ஒரு தனி நிர்வாக மாற்றமாகும்; அவர்களின் வேலைகளை வரையறுப்பது ஒரு கிளையைப் பாதுகாக்காது.

`API Route Typecheck` என்பது ஒரு சுயாதீனமான பணிப்பாய்வு சரிபார்ப்பு, மொத்த தீர்ப்புகள் மற்றும் உள்ளூர் முழு பார்வையாளரின் நிலையான சுயவிவரம் ஆகிய இரண்டிற்கும் வெளியே உள்ளது. சரியான வேட்பாளருக்கு அதன் முடிவை தனித்தனியாக ஆய்வு செய்யவும். `.github/workflows/api-route-typecheck.yml` PRs இல் `main` அல்லது `release/**` ஆக இயங்குகிறது, கிளை குடும்பம், கையேடு அனுப்புதல் மற்றும் `checks_requested` வகையின் `merge_group` நிகழ்வுகளுக்குத் தள்ளுகிறது. இதில் பாதை வடிகட்டி இல்லை. குழுக்களை ஒன்றிணைக்கவும் `merge_group.head_sha`; மற்ற நிகழ்வுகளை பார்க்கவும் `github.sha`. அனைத்து நிகழ்வுகளும் ஒரே API கண்டறியும் கேட் மற்றும் கேட் யூனிட் சோதனைகளைப் பயன்படுத்துகின்றன. PR அடிப்படை retargets ஒரு புதிய காசோலையை கோருகிறது; body/title திருத்தங்கள் கவனிப்பு-மட்டும் `Admission not requested / API Route Typecheck` என்ற பெயரைப் பயன்படுத்துகின்றன மற்றும் சேர்க்கை சரிபார்ப்பை மாற்ற முடியாது.

### ஏற்றுக்கொள்ளல் reducer-இல் தக்கவைக்கப்பட்ட ஆதாரம்

`scripts/quality/validate-release-acceptance.mjs` வழங்கப்பட்ட plan மற்றும் அதன்
manifest-களைச் சுருக்குகிறது; அந்த plan முழுமையான release pipeline-ஐ உள்ளடக்குகிறது என்பதை அது நிறுவுவதில்லை.
அந்த plan `VERIFIED` ஆக இருந்தாலும், அதன் report-கள் `releaseAcceptance: false` என்பதை வெளிப்படையாக அமைக்கின்றன.
`release-acceptance.yml` workflow இன்னும் உண்மையான build, package, boot அல்லது promotion ரசீதுகளுக்குப் பதிலாக
shadow fixture-களைப் பயன்படுத்துகிறது.

தக்கவைக்கப்பட்ட ஆதாரத்தைச் சரிபார்க்க CLI-க்கு `--evidence-root` தேவை. கோப்புகள்
`<evidence-root>/<artifact_id>/<member>` என resolve செய்யப்பட்டு SHA-256 ஆக hash செய்யப்படுகின்றன. ஆதாரம் இல்லாத PASS record,
காணாமல் போன அல்லது மாற்றப்பட்ட கோப்பு, பாதுகாப்பற்ற path அல்லது symlink ஆகியவை
சரிபார்ப்பைத் தடுக்கின்றன. காணாமல் போன கோப்புகள் வெற்றிகரமான காலி log-களுக்குச் சமமானவை அல்ல. ஏற்கெனவே உள்ள
SHA/run/attempt சோதனைகள் தனித்தே உள்ளன: பொருந்தும் byte-களால் காலாவதியான
receipt-ஐ மீட்டெடுக்க முடியாது. கோப்பு ஒருமைப்பாடு என்பது செயலாக்கத்தின் நம்பகத்தன்மை அல்லது artifact promotion-க்கான சான்றல்ல.

### சரிபார்க்கப்பட்ட CI build-ஐ DAST பயன்படுத்துகிறது

கட்டாயமான `dast-smoke` CI job, `build`-க்குப் பிறகு `.github/workflows/dast-smoke.yml`-ஐ அழைக்கிறது. ஆதரிக்கப்படும் fork PR-கள், release-ஐ இலக்காகக் கொண்ட PR-கள் மற்றும் merge group-கள் உட்பட, build பயன்படுத்தும் அதே code/draft தேர்வை இது பின்பற்றுகிறது. DAST job இல்லாவிட்டாலும், தோல்வியடைந்தாலும், ரத்துசெய்யப்பட்டாலும் அல்லது எதிர்பாராத விதமாகத் தவிர்க்கப்பட்டாலும் `Gate / CI` தடுக்கப்படும். மீண்டும் பயன்படுத்தக்கூடிய இந்த workflow-க்கு தனியான PR/dispatch trigger இல்லை; கையால் செய்யும் validation, CI-இன் dispatch-ஐப் பயன்படுத்துகிறது. இதனால் build-உம் consumer-உம் ஒரே run-இல் இருக்கும்.

`scripts/ci/next-build-provenance.mjs`, முழுமையான Next artifact-ஐ அதன் tar digest, repository/event/run, producer attempt, head/base/checkout/tree, workflow அடையாளங்கள், lockfile, துல்லியமான Node version/ABI, platform மற்றும் bundler ஆகியவற்றுடன் உறுதிப்படுத்துகிறது. DAST, `needs.build.outputs`-இலிருந்து மாற்ற முடியாத artifact ID-ஐத் தேர்ந்தெடுத்து, download digest சரிபார்ப்பைக் கட்டாயப்படுத்துகிறது. அனுமதிப்பட்டியலில் உள்ள அதன் இரண்டு உறுப்புகளை `scripts/ci/unpack-ci-build.py` வழியாகப் பிரித்தெடுக்கும் முன், ZIP-இன் hash-ஐத் தனியாகக் கணக்கிட்டு producer digest-உடன் ஒப்பிடுகிறது. Next tree-ஐப் பிரித்தெடுப்பதற்கு முன் manifest-உம் tar archive-உம் தனித்த producer output-களுடன் பொருந்த வேண்டும். Branch-இன் கடைசியாக வெற்றிபெற்ற build-ஐ இது ஒருபோதும் தேடுவதில்லை. ID-யும் எல்லா input-களும் தொடர்ந்து பொருந்தினால், பகுதியளவு rerun அதே producer attempt-ஐ மீண்டும் பயன்படுத்தலாம்; receipt இரண்டு attempt-களையும் பதிவு செய்கிறது.

Consumer, repository-ஐ வாசிக்க மட்டுமே அனுமதி கொண்டதும் repository secret-கள் இல்லாததுமான hosted Linux runner-இல் இயங்குகிறது. Producer பயன்படுத்திய அதே துல்லியமான Node version-ஐ நிறுவி, `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1` உடன் CLI-ஐ உருவாக்குகிறது. எந்த fallback build-க்கும் முன்பாகவே standalone server இல்லாத நிலையை `scripts/build/standaloneInput.mjs` நிராகரிக்கிறது; வழக்கமான உள்ளூர் CLI build-கள் அவற்றின் தற்போதைய fallback-ஐத் தக்கவைத்துள்ளன. Server readiness, Schemathesis மற்றும் promptfoo அனைத்தும் மாற்றப்படாத 25 நிமிட job வரம்புக்குள் வெற்றிபெற வேண்டும். Provenance receipt, input-இன் அடையாளத்தையும் bytes-ஐயும் நிரூபிக்கிறது; DAST scan வெற்றிபெற்றதை அது நிரூபிக்காது. Artifact காலாவதி, runner தடங்கல் அல்லது scanner தோல்வி ஆகியவை முழுமையற்ற அல்லது தோல்வியடைந்த சான்றாகவே இருக்கும்; advisory wrapper மூலம் அவற்றை PASS ஆக மாற்ற முடியாது.

### Unit coverage சேகரிப்பு

பன்னிரண்டு unit shard-கள் தங்களின் தற்போதைய சோதனைச் செயலாக்கத்தின்போது V8 coverage-ஐச் சேகரிக்கின்றன. வெற்றிகரமான
shard ஒன்று இடைநிலை Istanbul report-ஐ உருவாக்காமல் மூலக் கோப்புகளைச் சுருக்க
`scripts/ci/compact-v8-coverage.mjs`-ஐ இயக்குகிறது. இறுதி Coverage பணி அனைத்து பன்னிரண்டு manifest-களையும்
வேட்பாளர் SHA, runtime, source root மற்றும் data hash-களுக்கு எதிராகச் சரிபார்த்து, பின்னர் c8-இன் reporter-களையும் ஏற்கெனவே உள்ள
coverage threshold-களையும் இயக்குகிறது. Input-கள் c8-இன் global filename order-ஐத் தக்கவைக்கின்றன; கலப்பு
function/block coverage-க்கு ஒவ்வொரு shard-க்கும் முன்கூட்டியே merge செய்வது பாதுகாப்பற்றது. காணாமல் போன, தவறாக அமைக்கப்பட்ட அல்லது பொருந்தாத shard-கள் அனுமதியைத் தோல்வியடையச் செய்கின்றன.
தோல்வியடைந்த test shard-கள் raw diagnostic coverage-ஐத் தனியாகத் தக்கவைக்கின்றன; அது இறுதி merge-க்குள் நுழைய முடியாது.

### அலகுச் சோதனை செயல்படுத்தல் முன்னேற்ற ரசீதுகள்

பகிரப்பட்ட `test:unit:ci:shard` கட்டளை, `scripts/ci/unit-progress-reporter.mjs` மூலம் `primary`, `dashboard` மற்றும் `serial`
கட்டங்களைப் பதிவுசெய்கிறது. வழக்கமான சோதனை அறிக்கை தொடர்ந்து
கிடைக்கும். ஒவ்வொரு கோப்பின் தொடக்கத்தையும் நிறைவையும் தனியான, மெட்டாடேட்டா-மட்டும் கொண்ட ரசீது பதிவுசெய்கிறது;
மேலும், 30-விநாடி இதயத்துடிப்பு, இன்னும் செயலில் உள்ள கோப்புகளையும் அவற்றின் கடந்த நேரத்தையும் பட்டியலிடுகிறது. அனுமதிப்பட்டியலில் உள்ள
செயல்படுத்தல் மெட்டாடேட்டாவை மட்டுமே இது பதிவுசெய்கிறது; சோதனை விளக்கங்கள், வெளியீடு, பிழை விவரங்கள் மற்றும் முழு

தடுக்கப்பட்ட அல்லது நிறுத்தப்பட்ட ரன்னர் செயல்முறையையும் குறிக்கலாம். இந்த ரசீதுகள் தற்போதுள்ள சோதனைத் தேர்வு,
ஒரேநேரச் செயல்பாடு, காலக்கெடுக்கள் மற்றும் வெளியேறும் நிலை ஆகியவற்றைப் பாதுகாக்கின்றன; இவை வேட்பாளர்-அனுமதித் தீர்ப்புகள் அல்ல.

### ஒன்றிணைப்பு வரிசை

`queue` லேபிள் ஒரு PR-ஐ Mergify queue-க்கு அனுப்புகிறது (`.mergify.yml`). Mergify,
`mergify/merge-queue/` branch-இல் ஒரு draft PR-ஐத் திறக்கிறது; CI அங்கு முழுத் தேர்வையும் இயக்குகிறது, மேலும்
`Gate / CI`, `Gate / Quality` மற்றும் `Merge integrity (changelog + generated skills)` ஆகியவை வெற்றிபெறும்போது அசல் PR ஒன்றிணைக்கப்படுகிறது.

Mergify அதன் queue சுருக்கத்தை draft-இன் விளக்கத்தில் எழுதுகிறது; பிற app-களும் அதைத் திருத்த முடியும்.
அத்தகைய draft-இல் நிகழும் `pull_request` `edited` நிகழ்வு, draft-இன் உண்மையான இயக்கத்தை ரத்துசெய்ய முடியாதவாறு
அதற்கென தனி concurrency group-ஐப் (`-queue-edit-<run_id>`) பெறுகிறது; மேலும் அது gate மற்றும்
matrix-ஐத் தவிர்க்கிறது. `Merge integrity` மட்டும் தொடர்ந்து இயங்குகிறது. தவிர்க்கப்பட்ட gate job வேறு check பெயரைக்
கொண்டுள்ளது; ஏனெனில் தவிர்க்கப்பட்ட `Gate / CI`-ஐ Mergify தோல்வியுற்ற check ஆகக் கருதி PR-ஐ queue-இலிருந்து நீக்குகிறது.

queue-இலிருந்து நீக்கிய பிறகு, ஒரு push எப்போதும் PR-ஐ மீண்டும் queue-இல் சேர்ப்பதில்லை. அதில் `@mergifyio queue` என்று கருத்திடவும்.

### Static scan பட்டியல்

பதிப்பிடப்பட்ட npm-alias பட்டியலும் static-scan membership-உம்
`config/quality/gate-manifest.json`-இல் உள்ளன. Script பெயர்களையும் துல்லியமான command-களையும்
`package.json`-க்கு எதிராகச் சரிபார்க்க `npm run check:gate-manifest`-ஐ இயக்கவும்; சேர்த்தல்கள், அகற்றல்கள் மற்றும்
command drift ஆகியவை local hook மற்றும் CI-இல் உள்ள change-classification பணி இரண்டையும் தோல்வியடையச் செய்கின்றன.
Alias என்பது workflow job, matrix instance அல்லது test case அல்ல: இந்த எண்ணிக்கைகளை
ஒன்றுக்கொன்று மாற்றிப் பயன்படுத்தக்கூடியவையாகக் காட்டக்கூடாது.

தேர்ந்தெடுக்கப்பட்ட alias-களை இயக்காமல் ஆய்வு செய்ய `npm run quality:scan -- --list` அல்லது
`npm run quality:scan:fast -- --list`-ஐப் பயன்படுத்தவும். Runner npm entrypoint-ஐ அழைப்பதால்,
அதன் runtime (கட்டமைக்கப்பட்ட இடங்களில் Bun உட்பட) பாதுகாக்கப்படுகிறது.
அந்தச் சுயவிவரங்களுக்கு வெளியே உள்ள alias-களை manifest தனியாக அழைக்கப்பட்டவையாகப் பதிவு செய்கிறது; மேலும்
read-only scan சுயவிவரங்களில் maintenance command-கள் தடைசெய்யப்பட்டுள்ளன.

இந்தச் சுயவிவரங்கள் static scan-ஐ மட்டுமே உள்ளடக்குகின்றன. இவை product test-கள்,
coverage, packaging, external check-கள் அல்லது ஒரு வேட்பாளரின் முழுமையான release acceptance-ஐச் சான்றளிப்பதில்லை.
Workflow admission இணைக்கப்பட்டுள்ள `config/quality/admission-policy.json` மற்றும்
`scripts/quality/admission-verdict.mjs`-ஐப் பயன்படுத்துகிறது. Release-observer சுயவிவரங்கள் தனியாகவே உள்ளன;
அவற்றுக்குப் பொருந்தும் check-களையும் receipt-களையும் தனித்தனியாக ஆய்வு செய்யவும். முழுமையான observer-இன் static
command-கள் `config/quality/release-green-static-profile.json`-இல் அறிவிக்கப்பட்டுள்ளன; இதில்
`audit:deps`, mutation-test தேர்வு மற்றும் translation check-கள் அடங்கும். Loader npm
command-களை package.json மற்றும் மாதிரியாக்கப்பட்ட CI/Quality அறிவிப்புகளுக்கு எதிராகச் சரிபார்க்கிறது; shell token-களை argument-களாக இயக்குவதற்குப் பதிலாக drift-ஐ நிராகரிக்கிறது. கட்டாய scanner-இன் SKIP/INCOMPLETE output
PASS என்பதை நிறுவ முடியாது. சுயவிவரம் அதன் external exclusion-களைப் பதிவு செய்கிறது; மேலும் hosted coverage,
test matrix-கள், package அல்லது deployment ஆதாரத்தை மாற்றீடு செய்யாது. கீழேயுள்ள உரைநடைப் பட்டியல்
ஒரு reference மட்டுமே; ஒரு gate உண்மையில் இயங்கியது என்பதற்கான சான்றல்ல.

Script-கள் `scripts/check/` (policy gate-கள்) மற்றும் `scripts/quality/` (ratchet engine) ஆகியவற்றின் கீழ் உள்ளன.
CI-க்கான source of truth `.github/workflows/ci.yml` ஆகும்.

### வெளியிடப்பட்ட அடிப்படை ஆவணங்களின் நிலை

`.github/workflows/i18n-base-health.yml` தேர்ந்தெடுக்கப்பட்ட `main` மற்றும் `release/v*`

மூல Markdown, `llm.txt`, மொழிபெயர்ப்பு நிலை/உள்ளமைவு மற்றும் தொடர்புடைய i18n கருவிகளை உள்ளடக்குகின்றன.
ஒற்றை `Published base documentation health` job, hosted Ubuntu-ஐயும் ஐந்து நிமிட
காலக்கெடுவையும் பயன்படுத்துகிறது. இது வாசிப்பு-மட்டும் சரிபார்ப்பை மேற்கொண்டு, dependency நிறுவல்,
மொழிபெயர்ப்பு அல்லது நிலை ஏற்றுக்கொள்ளல் எதுவுமின்றி கண்டறிதல் ரசீதை எழுதுகிறது.

`scripts/i18n/check-base-health.mjs`-க்கு source-hash முரண்பாடுகள், target இல்லாமை, target-hash முரண்பாடுகள்,
காலாவதியான மொழிபெயர்ப்பு மற்றும் section-cache முரண்பாடுகள் எதுவும் இருக்கக் கூடாது. இது தற்போதைய மைய
ஆவணம்/locale வரம்பையும், அதன் பதிவுசெய்யப்பட்ட மூலத்தையும் சரிபார்க்கிறது. செல்லாத சூழல், முழுமையற்ற கவரேஜ்
அல்லது இடைநிறுத்தப்பட்ட checker ஆகியவை `INCOMPLETE`-ஐ உருவாக்கும்; உறுதிப்படுத்தப்பட்ட விலகல் `FAIL`-ஐ உருவாக்கும். இரண்டுமே
தோல்வியைக் குறிக்கும் exit status-ஐ வழங்கும். ரசீது checkout SHA, workflow, run மற்றும்
attempt ஆகியவற்றுடன் பிணைக்கப்பட்டு, `i18n-base-health-<sha>-<run>-<attempt>` என்ற பெயரில் தக்கவைக்கப்படுகிறது.

இது வெளியிடப்பட்ட அடிப்படையின் ஒரு சுயாதீனக் கண்காணிப்பாகும். இது PR அல்லது

ஏற்கனவே உள்ள வேறுபாட்டு PR கொள்கையும், அடிப்படையான checker-இன் ஆலோசனை வகைப்பாடுகளும்
தனித்தனியாகவே இருக்கும். வெற்றிகரமான upload, தோல்வியடைந்த health முடிவை PASS ஆக மாற்ற முடியாது.

### PR விரைவுப் பாதையை (`quality.yml`) வெளியிடு

#### மறக்கப்பட்ட உடன்பிறப்பு சோதனை அறிக்கை

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` இன் ஆலோசனைப் படியாக இயங்குகிறது மற்றும் சோதனை-தாக்க வரைபடத்தின் பின்னால் உள்ள இறக்குமதி தீர்வை மீண்டும் பயன்படுத்துகிறது. மாற்றப்பட்ட ஒவ்வொரு உற்பத்தி தொகுதிக்கும், விண்ணப்பதாரர் சோதனையானது இழுத்தல்-கோரிக்கை வித்தியாசத்தில் இல்லாதபோது, அது தீர்மானிக்கும் `changed module/symbol -> static consumer -> candidate sibling test` சங்கிலிகளைப் புகாரளிக்கிறது. மார்க் டவுன் சுருக்கம் மற்றும் JSON முடிவு ஆகியவை `forgotten-sibling-tests` பணிப்பாய்வு கலைப்பொருளாகத் தக்கவைக்கப்படும்.

பீப்பாய் மறு-ஏற்றுமதி மற்றும் மாறும் இறக்குமதிகள் தீர்மானம் கண்டறிதல் மட்டுமே; அவர்கள் ஒருபோதும் தடுக்கும் கண்டுபிடிப்பை உருவாக்க மாட்டார்கள். மதிப்பாய்வு செய்யப்பட்ட விதிவிலக்குகள் `config/quality/forgotten-sibling-allowlist.json` இல் உள்ளன. ஒவ்வொரு உள்ளீடும் நுகர்வோர் மற்றும் வேட்பாளர் சோதனைக்கு பெயரிட வேண்டும், ஒரு குறிப்பிட்ட பகுத்தறிவைக் கொடுக்க வேண்டும், மேலும் GitHub சிக்கலை இணைக்க வேண்டும் அல்லது கோரிக்கையை இழுக்க வேண்டும். தவறான உள்ளீடுகள் தோல்வியடைந்தன. நீக்கப்பட்ட வேட்பாளர் சோதனையையோ அல்லது `.skip`/`.todo` ஐ சேர்க்கும் வித்தியாசத்தையோ விதிவிலக்குகளால் அடக்க முடியாது ; வலியுறுத்தல் வலுவிழக்கச் செய்தல் மற்றும் பிற மறைத்தல் ஆகியவை சுதந்திரமாகத் தடுக்கும் `check:test-masking` வாயிலுக்குச் சொந்தமானவை.

#### இரண்டு typecheck நிரல்கள் வெவ்வேறு பதில்களை வழங்குகின்றன

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`) மற்றும் `check:build-typecheck` ஆகியவை வெவ்வேறு options-ன் கீழ்
வெவ்வேறு நிரல்களை compile செய்கின்றன; ஒரே file ஒன்று இதில் பிழையில்லாமலும் மற்றொன்றில்
பிழைகள் நிறைந்ததாகவும் இருக்கலாம்.

`tsconfig.build.json` `"strict": false` என அமைக்கிறது, எனவே `noImplicitAny` முடக்கப்பட்டுள்ளது. core
config கடுமையான options-ுடன் தேர்ந்தெடுக்கப்பட்ட 27-கோப்பு allowlist-ஐ compile செய்து, ஒவ்வொரு
entry-யின் import graph-ஐப் பின்தொடர்கிறது; ஆகவே build program-ல் ஒருபோதும் தோன்றாத
files-களும் அங்கே சரிபார்க்கப்படுகின்றன.

ஒரு file typed-ஆக உள்ளதா என்பதை மதிப்பிடும்போது இதன் விளைவு முக்கியமானது: **`check:build-typecheck`-ன்
கீழ் zero diagnostics என்பது zero errors என்று பொருளல்ல**. 26 files-லிருந்து
`@ts-nocheck`-ஐ அகற்றியபோது, அவற்றில் 23 build program-ல் பிழையற்றதாக இருந்தன; அவற்றில்
பதினாறு strict program-ல் சுமார் 120 implicit-any errors-ஐ வெளிப்படுத்தின. ஒரு file-ஐ
clean என்று கூறுவதற்கு முன் இரண்டையும் சரிபார்க்கவும்.

#### `check-ui-value-drift` — பழைய மொழிபெயர்ப்பு gate

மற்ற நுழைவாயில்களால் கட்டமைப்பு ரீதியாகக் கண்டறிய முடியாத ஒரு i18n பின்னடைவை இது கண்டறிகிறது: ஒரு ஆங்கில மதிப்பு
மீண்டும் எழுதப்பட்ட பின்னரும், _முந்தைய_ ஆங்கிலத்திலிருந்து பெறப்பட்ட மொழிபெயர்ப்புகள் மாற்றப்படாமல் இருப்பதால்,
ஆங்கிலமல்லாத மொழிகளைப் பயன்படுத்தும் பயனர்கள் நம்பிக்கையுடன் எழுதப்பட்ட, ஆனால் இப்போது தவறான உரையையே தொடர்ந்து படிப்பார்கள்.

இது உண்மையிலேயே வெளியீட்டுக்குச் சென்றது. Antigravity உள்நுழைவு உதவி சேர்க்கப்பட்டபோது (#5203),
`oauthModal.googleOAuthWarning` மீண்டும் எழுதப்பட்டது; **43 மொழியமைவுகளில் 39** மொழியமைவுகள், இயக்குநர்களிடம் "முழு
URL-ஐ நகலெடுத்து கீழே ஒட்டவும்" என்று கூறும் உரையை வைத்திருந்தன — அந்த வழங்குநருக்கு நிறைவுபெற முடியாத ஒரு செயல்முறை.
இது #8463 வரை கவனிக்கப்படவில்லை, ஏனெனில்:

- `sync-ui-keys`, **இல்லாத** விசைகளை மட்டுமே நிரப்புகிறது; **காலாவதியான** விசைகளை ஒருபோதும் புதுப்பிப்பதில்லை;
- `check-ui-keys-coverage`, விசை _இருப்பதை_ எண்ணுகிறது; எனவே காலாவதியான மொழிபெயர்ப்பும் உள்ளடக்கப்பட்டதாக மதிப்பெண் பெறுகிறது;
- `check-translation-drift`, `docs/i18n/<locale>/**.md` ஆவணப்படுத்தல் பிரதிகளைக் கண்காணிக்கிறது —
  அது `src/i18n/messages/*.json`-ஐ ஒருபோதும் படிப்பதில்லை. 2026-09 மறு-ஒத்திசைவுக்குப் பிறகு job `docs-sync-strict`-இல்
  தடுக்கும் விதமாக உள்ளது: ஒரு மைய ஆவணத்தைத் திருத்தவும் → `npm run i18n:run -- --files=<doc>` (பிரிவு-நிலை, செலவு குறைவு).

**Diff-ஐ அறிந்தது; baseline-ஐச் சார்ந்ததல்ல.** இது merge base-இல் உள்ள `en.json`-ஐ working tree-உடன்
ஒப்பிடுகிறது; ஆங்கில மதிப்பு மாறிய ஒவ்வொரு விசைக்கும், தொடப்படாத மொழிபெயர்ப்பை இன்னும் கொண்டிருக்கும் எந்த மொழியமைவும்
காலாவதியானதாகும். இது வேண்டுமென்றே **ஏற்கெனவே உள்ள கடனை உறையவைக்கிறது** — நீண்டகாலமாக உள்ள மொழிபெயர்ப்பு எந்தப் பழைய
ஆங்கிலத்திலிருந்து வந்தது என்பதை ஒரு diff வெளிப்படுத்த முடியாது; எனவே தற்போதைய மாற்றம் தொடுபவற்றை மட்டுமே இந்த நுழைவாயில்
மதிப்பிடுகிறது. மாற்று வழியான (ஒவ்வொரு விசைக்குமான hash baseline) அணுகுமுறைக்கு, தற்போதுள்ள மிகப்பெரிய baseline-ஐவிட 3× பெரிய,
ஒவ்வொரு i18n PR-இலும் மாறிக்கொண்டிருக்கும் ~600 KB உருவாக்கப்பட்ட கோப்பு தேவைப்படும்.

இதைப் பூர்த்திசெய்ய இரண்டு வழிகள் உள்ளன:

1. பாதிக்கப்பட்ட மொழிபெயர்ப்புகளைப் புதுப்பிக்கவும், அல்லது
2. அவற்றை `__MISSING__:<new english>` என அமைக்கவும் — பின்னர் runtime திருத்தப்பட்ட ஆங்கிலத்தை வழங்கும்
   (`src/i18n/request.ts::deepMergeFallback`, #7258), மேலும் அந்த விசை மொழிபெயர்ப்புக்கான வரிசையில் சேர்க்கப்படும்.

சரத்தின் **பொருள்** மாறியிருந்தால், **விசையை மறுபெயரிடுவதை** விரும்பவும்: ஒரு புதிய விசையால்
காலாவதியான மொழிபெயர்ப்பைப் பெற முடியாது. #8463 பயன்படுத்திய முறை இதுவே.

```bash
npm run i18n:check-value-drift          # கடுமையான முறை (CI இயக்குவது)
npm run i18n:check-value-drift:warn     # அறிக்கை மட்டும்
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

மதிப்பு-மாற்றம் மற்றும் புதிய-விசை தடுப்புகள்
`scripts/i18n/resolve-ui-diff-base.mjs` இலிருந்து ஒரே மாற்றமுடியாத ஒப்பீட்டைப் பகிர்கின்றன. பணிப்பாய்வு, இரண்டு சரிபார்ப்புகளுக்கும் ஒரே அடிப்படை, அடிப்படை முனை மற்றும்
வேட்பாளர் SHAs-ஐ அனுப்புகிறது. PR/அடிப்படை-மறுஇலக்கிடல், push மற்றும் merge-group இயக்கங்கள் அவற்றின் event
சூழலைப் பயன்படுத்துகின்றன. ஒரு வேட்பாளர் கிளையை dispatch செய்வதற்கு, அதன் துல்லியமான திறந்த PR அல்லது வெளிப்படையான
`i18n_base_sha` உள்ளீடு தேவை. அந்த உள்ளீடு இல்லாமல் `main` அல்லது `release/vX.Y.Z`-ஐ dispatch செய்வது அல்லது திட்டமிட்ட முறையில் கண்காணிப்பது,
கடைசி commit-ஐ அதன் முதல் parent உடன் ஒப்பிடுகிறது; இது மரபாகப் பெறப்பட்ட அனைத்து மொழிபெயர்ப்புக் கடனுக்குமான தணிக்கை அல்ல.
உள்ளூரில் இயக்குவதற்கு வெளிப்படையான ஒப்பீட்டு அடிப்படை தேவை,
எடுத்துக்காட்டாக மேலே உள்ள `BASE_REF` command.

விடுபட்ட அல்லது தெளிவற்ற ஒப்பீட்டுச் சூழல், படிக்க முடியாத அல்லது செல்லாத அவசியமான catalog மற்றும்
மாற்றப்பட்ட வேட்பாளர் ஆகியவை warn mode உட்பட, exit code **2** உடன் `INCOMPLETE` நிலையை உருவாக்குகின்றன.
Catalog வாசிப்புகள் `scripts/i18n/read-ui-catalog.mjs`-ஐப் பயன்படுத்துகின்றன; வாசிப்புத் தோல்விகள்
வெற்றுப் பொருட்களால் மாற்றீடு செய்யப்படுவதில்லை. கிடைக்காத அடிப்படையோ முழுமையற்ற உள்ளீடோ `PASS` நிலையை உறுதிப்படுத்தாது.

`pull_request` நிகழ்வுகளில், `quality.yml` ஆனது `--base-ref <PR base SHA>` என்பதை `check:file-size`,
`check:complexity-ratchets` மற்றும் `check:dead-code` ஆகியவற்றுக்கு அனுப்புகிறது. `check:complexity-ratchets` மற்றும்
`check:dead-code` ஆகியவற்றுக்கு, தடை HEAD-ஐ merge-base உடன் ஒப்பிடுகிறது; இந்த ஒப்பீடு **PR மாற்றிய கோப்புகளுக்கு
மட்டுமே** வரையறுக்கப்படுகிறது (`scripts/check/newCodeMode.mjs`: merge-base ஒரு தற்காலிக
`git worktree`-இல் உருவாக்கப்படுகிறது; ESLint/knip அங்கேயும் HEAD-இலும் இயக்கப்பட்டு, ஒவ்வொரு கோப்பிற்குமான
எண்ணிக்கைகளின் வேறுபாடு கணக்கிடப்படுகிறது):

- **தடுக்கும்** — PR மாற்றிய கோப்புகளில் cyclomatic/cognitive மீறல்கள் அல்லது dead exports சேர்க்கப்பட்டுள்ளன
  (பதிவில் `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=`);
- **ஆலோசனை** — ஒட்டுமொத்த மொத்த மதிப்பு மற்றும் உறையவைக்கப்பட்ட அடிப்படை மதிப்புக்கு இடையிலான ஒப்பீடு. மரபுரிமையாக வந்த விலகல்
  குற்றமற்ற PR-ஐ ஒருபோதும் சிவப்பு நிலைக்குக் கொண்டுசெல்லாது; அந்த விலகல், வெளியீட்டு ஒத்திசைவின்போது சரிசெய்வதற்காகக் கண்காணிக்கப்பட்டு,
  headroom பணியால் மேற்பார்வையிடப்படுகிறது.

`check:file-size` அதன் சொந்த விதிகளின்படி base ref-ஐப் பயன்படுத்துகிறது (`scripts/check/check-file-size.mjs`, #8522):
அது tree-இல் உள்ள ஒவ்வொரு source மற்றும் test கோப்பையும் சரிபார்த்து, PR base-இல் ஒவ்வொன்றின் வரி எண்ணிக்கையையும்
`git show` மூலம் வாசிக்கிறது; பின்னர் அந்தக் கோப்பு அதன் அடிப்படை உச்சவரம்பு
(`frozen` / `testFrozen`, அல்லது அடிப்படைக்கு வெளியேயுள்ள கோப்பிற்கு `cap` / `testCap`) மற்றும் அதன் base அளவு
ஆகியவற்றில் பெரியதைத் தாண்டி வளர்ந்தால் மட்டுமே தோல்வியடையச் செய்கிறது. எனவே base-இல் ஏற்கெனவே விலகியுள்ள ஒரு கோப்பு,
குற்றமற்ற PR-ஐ ஒருபோதும் தோல்வியடையச் செய்யாது.

`check:boundary:ratchet` அதன் ஒற்றை எண்ணுக்கும் அதே விதியைப் பயன்படுத்துகிறது
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR நிகழ்வுகளில்
`quality.yml` fast-gates மற்றும் `ci.yml` lint job ஆகிய இரண்டும் PR base SHA-ஐ அனுப்புகின்றன; base commit
ஒரு `git archive` export-இலிருந்து அளவிடப்படுகிறது; மேலும் PR-இன் `open-sse → src` edge
எண்ணிக்கை, `metrics.boundaryOpenSseToSrc` மற்றும் base-இல் உள்ள எண்ணிக்கை ஆகியவற்றில் பெரியதை மீறும்போது மட்டுமே PR தோல்வியடைகிறது. உச்சவரம்புக்கு
மேலான base drift புகாரளிக்கப்படுகிறது (`base drift herdado`), ஆனால் குற்றமற்ற PR-ஐ ஒருபோதும் தோல்வியடையச் செய்யாது; push → main
முழுமையான உச்சவரம்பைத் தொடர்ந்து பயன்படுத்துகிறது; மேலும் தீர்மானிக்க முடியாத base SHA, எச்சரிக்கையுடன் அதற்கே fallback செய்கிறது.

`workflow_dispatch` இயக்கங்கள், release-green sweep மற்றும் nightly headroom job ஆகியவற்றுக்கு PR base
இல்லாததால், அவை முழுமையான (global) ஒப்பீட்டையே தொடர்ந்து பயன்படுத்துகின்றன. Coverage, duplication மற்றும் type-coverage ஆகியவை இப்போதைக்கு global ஆகவே

### CodeQL ratchet: candidate admission மற்றும் repository inventory

தெளிவான dependency தொடரின் வழியாக candidate-இன் CodeQL admission-ஐ CI நிர்வகிக்கிறது: `codeql-scan`, `codeql.yml`-இல் உள்ள நான்கு மொழிகளின் matrix-ஐ அழைக்கிறது; அதன் பிறகு `codeql-admission`, `node scripts/check/check-codeql-ratchet.mjs --candidate`-ஐ இயக்குகிறது. `Gate / CI` இரண்டு முடிவுகளையும் கோருகிறது. Quality தனது எண்ணியல் சோதனைகளைத் தக்கவைத்தாலும் producer முடிவதற்கு முன் scanner-ஐ வினவாது; `Gate / Quality` மட்டும் முழுமையான candidate admission அல்ல. ஆவணங்கள் மட்டும் மாற்றப்படும் candidate-களுக்கும் CodeQL கட்டாயமாகவே உள்ளது.

`config/quality/codeql-admission-policy.json`-இல் உள்ள policy, Actions, C/C++, JavaScript/TypeScript மற்றும் Python-ஐத் தேர்ந்தெடுக்கிறது; query suite default, threat model remote, build mode none ஆகியவற்றையும் தேர்ந்தெடுக்கிறது. Producer preflight, நிலுவையிலுள்ள activation பதிவையும் வெளிப்படையான target பட்டியலுக்கு வெளியேயுள்ள branch-களையும் நிராகரிக்கிறது. தொடக்க target-கள் main மற்றும் release/v3.8.53; அடுத்த release-க்கு ஆய்வு செய்யப்பட்ட onboarding தேவை. CI-இன் தற்போதைய விரிவான release PR trigger தொடர்கிறது. ஆனால் onboarding செய்யப்படாத target, அளவிடப்படாத PASS பெறுவதற்குப் பதிலாக extraction-க்கு முன் HOLD என அறிவிக்கிறது.

ஒவ்வொரு matrix job-உம் தனது உண்மையான SARIF upload ID, மொழி, category, run மற்றும் attempt, caller workflow அடையாளம், event ref/head/base/merge SHA மற்றும் policy hash ஆகியவற்றைப் பதிவு செய்கிறது. அதனைச் சார்ந்த job இந்த run-இன் receipt-களை மட்டுமே download செய்து artifact digest-களைச் சரிபார்க்கிறது. நான்கு category-களும், வெற்றிபெற்ற producer-உம், ஒவ்வொரு குறிப்பிட்ட upload-இன் processing முடிவடைந்த நிலையும் தேவை. Branch-இல் கடைசியாகக் கிடைத்த analysis-ஐப் பயன்படுத்தாமல், API-இன் sarif_id filter-ஐப் பயன்படுத்துகிறது. பகுதியளவு rerun-கள், அதே run மற்றும் candidate-இன் முந்தைய attempt-இல் வெற்றிபெற்ற category-களை, அவற்றை உருவாக்கிய attempt அடையாளத்தைப் பாதுகாத்து மீண்டும் பயன்படுத்தலாம்; தற்போதைய producer தோல்வியடைந்திருந்தால் முந்தைய பச்சைச் சான்றை மீண்டும் பயன்படுத்த முடியாது.

CodeQL action processing-க்காகக் காத்திருக்கிறது. ஆனால் அதன் pin செய்யப்பட்ட implementation, status வாசிப்பு தோல்விக்குப் பிறகோ காத்திருப்பு வரம்பு முடிந்த பிறகோ எச்சரிக்கையுடன் தொடரக்கூடும். எனவே admission processing-ஐ மீண்டும் சரிபார்க்கிறது. Category-கள் இல்லாமை, நிலுவையிலுள்ள processing, தோல்வியடைந்த அல்லது ரத்தான job-கள், பழைய அடையாளம், முழுமையற்ற pagination அல்லது API கிடைக்காமை ஆகியவை HOLD-ஐ உருவாக்கி exit 2 தருகின்றன. தனியாக இயங்கும் scanner workflow-க்கான நிர்ணயிக்கப்பட்ட காத்திருப்பு இனி இல்லை. Alert query 0 கொடுத்ததற்காக scan செய்யப்படாத PR தேர்ச்சி பெற முடியாது. அளவிடப்பட்ட எண்ணிக்கை `metrics.codeqlAlerts.value`-ஐ மீறினால் exit 1 தரப்படும்; மற்றொரு branch-இன் alert-களை உள்ளடக்க baseline உயர்த்தப்படாது. [Upload நிலையும் analysis தேடலும்](https://docs.github.com/en/rest/code-scanning/code-scanning).

Receipt, upload மற்றும் analysis ID-கள், category-கள், tool version-கள், ref/SHA, baseline மற்றும் alert எண்ணிக்கைகளைப் பதிவு செய்கிறது. SARIF அடையாளம்/result எண்ணிக்கை, குறைந்தபட்ச rule எண்ணிக்கைகள் மற்றும் துல்லியமான alert instance-கள் தொடர்ந்து கட்டாயமாகும். ஏற்றுக்கொள்வதற்கு முன் PR/analysis அடையாளங்கள் மீண்டும் சரிபார்க்கப்படுகின்றன. இந்தச் சோதனைகள் அமைக்கப்பட்ட category-களின் coverage-ஐ நிறுவுகின்றன; பிரித்தெடுக்கப்பட்ட ஒவ்வொரு source file-இன் inventory-ஐ அல்ல. C/C++ no-build extraction, project build-இன் போது உருவாக்கப்படும் code-ஐ உள்ளடக்காது. Source exclusion-கள் இன்னும் ஆய்வு செய்யப்பட வேண்டும்; contributor-க்கு attribution வழங்க ஒப்பிடத்தக்க துல்லியமான base சான்று தேவை.

`codeql-maintenance.yml`, PR/main producer-களை நகலெடுக்காமல் active release push scan-களையும் வாராந்திர schedule-ஐயும் வழங்குகிறது. `nightly-codeql-inventory.yml`, `--strict-measurement` உடன் repository முழுவதற்குமான baseline-ஐத் தனியாக வைத்திருக்கிறது; அளவீடு கிடைக்காதபோது தோல்வியடைகிறது. உள்ளூர் பழைய collector பிழையின்றித் தவிர்ப்பது candidate admission அல்ல. சரிபார்க்கப்பட்ட குறைந்த மொத்த எண்ணிக்கைக்குப் பிறகு வெளிப்படையான `--update` மூலமே இறுக்குதல் செய்யப்படுகிறது.

Default Setup அமைக்கப்பட்டிருக்கும் நிலையில் Advanced workflow-ஐ வெளியிடக்கூடாது: GitHub அந்த இணைப்பை நிராகரிக்கிறது. ஆய்வு செய்யப்பட்ட நிர்வாக மாற்றம் மீண்டும் வாசித்து உறுதிசெய்யப்படும் வரை, அதன் version செய்யப்பட்ட policy நிலுவையிலேயே இருக்கும். வெளியீட்டிற்கு முன் operator, repository, head/base/tree, policy/patch/rollback hash-கள் மற்றும் காணப்பட்ட setup நிலை ஆகியவற்றை உறுதியாகப் பதிவு செய்கிறார்; `node scripts/quality/codeql-producer.mjs verify-admin-readback`, வழங்கப்பட்ட expected மற்றும் actual JSON பதிவுகளைச் சோதிக்கிறது. இது ஒரு தொழில்நுட்பத் தடுப்பு; operator ஒப்புதலோ புதிய readback-களைப் பெறுவதற்கான மாற்றோ அல்ல. PR token ஒருபோதும் Administration access கோராது. Rollout-க்கும் scanner மாற்றங்கள் அனைத்திற்கும் அந்தத் தனியான readback-உடன் உண்மையான PR, fork மற்றும் merge-group compatibility சான்றும் தேவை.

Fork-கள் hosted runner-களையும், credential-களைச் சேமிக்காத checkout-ஐயும் பயன்படுத்துகின்றன; producer-இல் project install/build இல்லை, repository secret-களும் மரபாக வழங்கப்படாது. குறைக்கப்பட்ட fork token உடன் pull_request நிகழ்வுக்கான SARIF upload-ஐ GitHub ஆதரிக்கிறது; முதன்முறை contribution-ஐ இயக்குவதற்கான ஒப்புதல் தொடர்ந்து GitHub policy-க்கு உட்பட்டது. நம்பத்தகாத code-ஐ இயக்க pull_request_target-ஐ ஒருபோதும் பயன்படுத்தக்கூடாது. Migration முடிந்ததாகக் கருதும் முன், கட்டுப்படுத்தப்பட்ட canary-யில் உண்மையான token permission-கள், analysis_key மற்றும் அனைத்து category environment-களையும் உறுதிப்படுத்த வேண்டும். [Fork upload விதிகள்](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/resource-not-accessible),
[முரண்படும் setup முறைகள்](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/two-codeql-workflows).

tip-இல் பின்னடைந்தால் — அதாவது merge-களின் சேர்க்கை அதைப் பின்னடையச் செய்திருந்தாலும், எந்த ஒரு PR-உம் அதன்

baseline-ஐப் புதுப்பிக்காதீர்கள் (அது உண்மையான பின்னடைவுகளை மறைக்கும்). முதலில் வேறுபடுத்திக் கண்டறியுங்கள்: உங்கள் PR அதற்குக் காரணம் எனக் கருதுவதற்கு முன்,
probe worktree ஒன்றில் தூய tip-க்கு எதிராகத் தோல்வியை மறுஉருவாக்குங்கள்.

`nightly-release-green.yml` → job **`bank-ratchet-shrinks`** அந்தச் சுழற்சியை நிறைவு செய்கிறது:

|              |                                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| இயங்குவது    | `schedule` (ஒரு நாளுக்கு 3×) + `workflow_dispatch` — திட்டமிட்டே `push` அல்ல                                                         |

| எழுதுவது     | `check:file-size --update` மற்றும் `check:complexity-ratchets --update` (இரண்டும் வடிவமைப்பிலேயே குறைக்க மட்டும் அனுமதிப்பவை)        |

ஒவ்வொரு push-க்கும் பதிலாக banking தொகுதியாகச் செய்யப்படுகிறது; ஏனெனில் அதற்கு latency தேவை இல்லை (8 மணிநேரத்திற்குள்
bank செய்யப்படும் குறைப்பு போதுமானது), ஆனால் ஒவ்வொரு merge-க்கும் இயக்குவது merge campaign-களின்போது PR branch-ஐ மீண்டும் மீண்டும்
உருவாக்குவதோடு, ஒவ்வொரு முறையும் முழுமையான ESLint ஆய்வுக்கான செலவையும் ஏற்படுத்தும். கண்டறிதல் தொடர்ந்து
push-இல் (`release-green`) நடைபெறும்; banking மட்டும் தொகுதியாகச் செய்யப்படுகிறது.

### பாதுகாப்புச் சரிபார்ப்பான்

இந்த job மனிதக் கண்காணிப்பின்றி baseline-களில் எழுதுகிறது; எனவே அதை ஏற்றுக்கொள்ளத்தக்கதாக ஆக்குவது `verify-ratchet-bank.mjs` ஆகும்.
இது `--update`-க்குப் பிந்தைய tree-ஐ `HEAD` உடன் diff செய்து, ஒவ்வொரு மாற்றமும் கீழ்க்கண்டவற்றில் ஒன்றாக இல்லாவிட்டால்,
**எந்த commit-உம் உருவாகும் முன்பே job-ஐ நிறுத்திவிடும்** — எந்த PR-உம் திறக்கப்படாது:

- ஒரு `frozen` / `testFrozen` எண் பதிவு **குறைக்கப்பட்டது** அல்லது **அகற்றப்பட்டது**
- `complexity-baseline.json` → `count` **குறைக்கப்பட்டது**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **குறைக்கப்பட்டது**

வேறு எதுவும் தோல்வியடையும்: எண்ணை உயர்த்துவது, பதிவைச் சேர்ப்பது, `cap`/`testCap`-ஐ மாற்றுவது, அல்லது
`_rebaseline_*` குறிப்பை நீக்குவது/மீண்டும் எழுதுவது (ஒவ்வொரு உச்சவரம்பும் ஏன் உள்ளது என்பதற்கான audit trail அந்தக் குறிப்புகளாகும்;
அவை கோப்புப் பதிவுகள் இருக்கும் அதே `frozen` object-இன் உள்ளே சேமிக்கப்படுகின்றன).
ஒரு cap-ஐ உயர்த்தக்கூடிய bot தற்போதைய நிலையைவிட முற்றிலும் மோசமானதாக இருக்கும். பின்னடைவு
guard: `tests/unit/verify-ratchet-bank.test.ts`.

இந்த job ஒருபோதும் `release/*`-க்கு push செய்யாது — ஒரு மனிதர் PR-ஐ merge செய்வார்; எனவே தவறான அளவீடு
மதிப்பாய்வு இல்லாமல் சேர்க்கப்பட முடியாது.

## அனுமதிப்பட்டியல் கொள்கை

முன்பே இருக்கும் மீறல்களால் தோல்வியடையக் கூடாத ஒவ்வொரு வாயிலும் உறையவைக்கப்பட்ட அனுமதிப்பட்டியலைப் பயன்படுத்துகிறது
(எ.கா., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). கொள்கை:

**மூலக் காரணத்தைச் சரிசெய்யவும்; மீறல் முன்பே இருந்தால் மற்றும் அதே PR-இல் அதைச்
சரிசெய்ய முடியாவிட்டால் மட்டுமே அனுமதிப்பட்டியலைப் பயன்படுத்தவும்.**

அனுமதிப்பட்டியலில் ஓர் உள்ளீட்டைச் சேர்க்கும்போது:

1. அதற்கான நியாயப்படுத்தலுடன் ஒரு கருத்துரையைச் சேர்க்கவும்.
2. கண்காணிப்புச் சிக்கலைக் குறிப்பிடவும் (எ.கா., `// #3498 — Phase 2 feature, not yet implemented`).
3. மீறலைச் சரிசெய்யும் அதே PR-இல் உள்ளீட்டை அகற்றவும் — செயலில் உள்ள மீறலை இனி
   ஒடுக்காத காலாவதியான உள்ளீடு தானே ஒரு குறைபாடாகும் (6A.3 காலாவதியான-அமலாக்கம்
   செயல்படுத்தப்பட்டதும், ஆதரவற்ற அனுமதிப்பட்டியல் உள்ளீடு வாயிலைத் தோல்வியடையச் செய்யும்).

சோதனைகள் விரைவாகத் தேர்ச்சி பெறுவதற்காக அனுமதிப்பட்டியல் உள்ளீடுகளைச் சேர்க்க **வேண்டாம்**. தொடர்ந்து
வளரும் அனுமதிப்பட்டியலுடன் கூடிய பச்சை வாயில், தரம் குறித்த தவறான நம்பிக்கையை அளிக்கிறது.

### உங்கள் PR-இல் ஒரு வாயில் தோல்வியடையும்போது

1. **வாயிலின் வெளியீட்டைக் கவனமாகப் படிக்கவும்** — எந்தக் கோப்பு அல்லது குறியீடு விதியை
   மீறியது என்பதை அது துல்லியமாகக் கூறும்.
2. **மீறலைச் சரிசெய்யவும்** — பெரும்பாலான வாயில்கள் தீர்மானகரமான கோப்பு முறைமைச் சோதனைகள்; குறியீடு
   சரியானவுடன் அவை தேர்ச்சி பெறும்.
3. **மீறல் முன்பே இருந்தால்** (அதாவது, அதை நீங்கள் அறிமுகப்படுத்தவில்லை; ஆனால் வாயில் இப்போது
   அதை உள்ளடக்குகிறது): நியாயப்படுத்தும் கருத்துரை மற்றும் கண்காணிப்புச் சிக்கலுடன் ஓர் அனுமதிப்பட்டியல் உள்ளீட்டைச் சேர்க்கவும்.
4. **வாயில் ஒரு ராட்செட் என்றால்** (கவரேஜ், ESLint எச்சரிக்கைகள், நகலாக்கம், சிக்கல்தன்மை):
   உங்கள் மாற்றம் அளவீட்டை மோசமாக்கியுள்ளது. அடிப்படைச் சிக்கலைச் சரிசெய்யவும் அல்லது (அரிதாக) மாற்றம்
   வேண்டுமென்றே செய்யப்பட்டு, அளவீட்டுச் சரிவு ஏற்கத்தக்கதாக இருந்தால் `npm run quality:ratchet -- --update`
   என்பதை இயக்கவும் — ஆனால் அதற்கான காரணத்தை PR விளக்கத்தில் ஆவணப்படுத்தவும்.
5. **ஆலோசனை வாயில்கள்** (`continue-on-error: true`) தகவலுக்காக மட்டுமே — அவை ஒன்றிணைப்பைத்
   தடுக்காது; ஆனால் CI சுருக்கத்தில் தோன்றும். இருப்பினும் அவற்றைச் சரிசெய்யவும்.

## புதிய வாயிலைச் சேர்த்தல்

1. `scripts/check/check-<name>.mjs` (அல்லது `.ts`) உருவாக்கவும். கொள்கை வாயில்கள் 0/1 வெளியேறும் குறியீட்டுடன் முடிவடையும்.
   Ratchet-பாணி வாயில்கள் `collect-metrics.mjs` வழியாக `quality-metrics.json`-க்கு ஓர் அளவீட்டை வெளியிடும்.
2. `package.json`-இல் `"check:<name>": "node scripts/check/check-<name>.mjs"` என்பதைச் சேர்த்து,
   அதன் மாற்றுப்பெயரையும் அதற்கான துல்லியமான கட்டளையையும் `config/quality/gate-manifest.json`-இல் ஒத்திசைக்கவும்.
   ஏற்கனவே உள்ள சரிபார்ப்பு மாற்றுப்பெயரை மாற்றும்போதோ அகற்றும்போதோ இதே ஒத்திசைவைப் பயன்படுத்தவும்.
   `npm run check:gate-manifest`-ஐ இயக்கவும்; pre-commit hook மற்றும் CI மாற்ற வகைப்பாடு
   இந்த ஒப்பந்தத்தை அமல்படுத்துகின்றன.
3. பொருத்தமான பணியின் கீழ் `.github/workflows/ci.yml`-இல் அதை இணைக்கவும்
   (கொள்கை → `lint` அல்லது `docs-sync-strict`; ratchet → `quality-gate`).
4. அதற்கு அனுமதிப்பட்டியல் இருந்தால், காலாவதியான உள்ளீடுகள் தானாகக் கண்டறியப்படுவதற்காக
   `scripts/check/lib/allowlist.mjs`-இலிருந்து `reportStaleEntries()`-ஐப் பயன்படுத்தவும்.
5. வாயிலின் கண்டறிதல் தர்க்கத்தை உள்ளடக்கும் சோதனையை `tests/unit/build/`-இல் எழுதவும்.
6. இந்த ஆவணத்தைப் புதுப்பிக்கவும் (தொடர்புடைய பணியின் அட்டவணையில் ஒரு வரியைச் சேர்க்கவும்).

`.mcp.json`-ஐ உருவாக்கவும்; இதனால் அவர்கள் குறியீட்டை எழுதுவதற்கு **முன்பே** குறியீடுகள் /
கண்டறிதல்களைத் தீர்மானிப்பார்கள் — மூலத்திலேயே "கற்பனையான குறியீடு" பிழைகளைக் குறைக்கும்
`typecheck:core`-க்கான compile-before-claim துணை இது. இது வேண்டுமென்றே
தானாக ஏற்றப்படுவதில்லை (MCP↔LSP பாலத்தை நீங்கள் தேர்ந்தெடுத்துச் சரிபார்க்க வேண்டும்); பழுதான உள்ளீடு ஓர்
இணைப்புப் பிழையை மட்டுமே பதிவு செய்யும், அமர்வுகளை ஒருபோதும் பாதிக்காது.

## பகுத்தறிவாக்கப் பின்னடைவு (ROI மதிப்பாய்வு — கட்டம் 9 அலை 3)

இந்தப் பட்டியல் 2026-06-17 அன்று `ci.yml` உடன் ஒப்பிட்டுச் சரிசெய்யப்பட்டது (முந்தைய பதிப்பில்
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,
`check:codeql-ratchet`, `check:pr-evidence` ஆகியவை விடுபட்டிருந்தன). சரிசெய்யப்பட்ட தொகுப்பின் ROI மதிப்பாய்வு
பின்வரும் பகுத்தறிவாக்கத் தேர்வுகளை அடையாளம் கண்டது. **இணைப்புகள் இயந்திரரீதியான CI
மாற்றங்கள்; நிலைமாற்றங்கள்/நீக்கங்கள் இயக்குநருக்காக ஒதுக்கப்பட்ட கொள்கை முடிவுகள்.** கீழே உள்ள எதுவும்
இன்னும் செயல்படுத்தப்படவில்லை.

**மேலே ஆவணப்படுத்தப்படாத மற்றவை** (ஆலோசனை மட்டுமே; குறைந்த பயனுள்ள சிக்னல்): `docs-lint` job (markdownlint + Vale, முழு job-க்கும் `continue-on-error`) மற்றும் தனித்த scanner workflow-களான `semgrep.yml` / `scorecard.yml`. மேலே கூறப்பட்ட activation தேவைகளுக்கு உட்பட்டு, CodeQL இப்போது `Gate / CI`-இன் கீழ் கட்டாய producer மற்றும் admission job-களைக் கொண்டுள்ளது. `quality-baseline.json`-இல் `semgrepFindings: 0` உள்ளது; ஆனால் அது `ci.yml`-இல் தடுக்கக்கூடிய ratchet-உடன் இணைக்கப்படவில்லை — இந்த metric தற்போது இணைப்பின்றி உள்ளது.

### இணைத்தல் / நகல்நீக்கம் (இயந்திரரீதியானது, குறைந்த ஆபத்து)

ஒவ்வொரு தேர்வும் 2026-06-17 அன்று நடைமுறையிலிருந்த கேட் நிலைக்கு எதிராகச் சரிபார்க்கப்பட்டது (நம்புங்கள், ஆனால் சரிபாருங்கள்);
“வெளிப்படையானவை” எனத் தோன்றிய பல இணைப்புகள் தொழில்நுட்பக் கடனை மறைத்திருப்பது தெரியவந்தது; எனவே அவை **சிக்கலற்ற** நேரடி மாற்றீடுகள் அல்ல.

- **`check:docs-sync` இருமுறை இயங்குகிறது** — `lint` பணியில் தனியாகவும், `check:docs-all` (`docs-sync-strict`) உள்ளேயும், husky முன்-கமிட் ஹுக்கிலும் இயங்குகிறது. ✅ **முடிந்தது** — தனியான `lint` இயக்கம் அகற்றப்பட்டது.
- **CVE ஸ்கேனிங்** — ❌ **சிக்கலற்ற இணைப்பு அல்ல.** `audit:deps` ஐந்து lockfile-களிலும் உள்ள தீவிர ஆலோசனைகள் மற்றும் முழுமையற்ற தணிக்கைகளைத் தடுக்கிறது; தற்போதைய கொள்கையின் கீழ் உயர்-தீவிர ஆலோசனைகளை எச்சரிக்கைகளாகத் தெரிவிக்கிறது. ஆனால் `check:vuln-ratchet` (osv), செக்-இன் செய்யப்பட்ட அடிப்படையுடன் ஒப்பிடுகையில் ஒரு _பின்னடைவு_ ஏற்பட்டால் மட்டுமே தோல்வியடைகிறது; தேவைப்படும் போது அளவீடுகள் இல்லாவிட்டால் அவற்றை நிராகரிக்கிறது. இவற்றின் பொருளியல் வெவ்வேறானது — `audit:deps`-ஐ நீக்குவது முழுமையான தீவிர கேட் மற்றும் தனித்தனி தொகுப்புத் தணிக்கைச் சான்றுகளை இழக்கச் செய்யும். இரண்டையும் வைத்திருக்கவும்.
- **சுழற்சி கண்டறிதல்** — ✅ **முடிந்தது** (#15159 G-01/G-02). இங்கிருந்த பழைய உரை `check:cycles`-ஐ “பச்சை நிலையில் உள்ள, தேர்ந்தெடுத்தமைக்கப்பட்ட” கேட் எனக் குறிப்பிட்டு, `check:circular-deps` (dpdm) 91 சுழற்சிகளை அறிவித்ததால் அதைத் தடுப்புக் கேட்டாக வைத்திருப்பதை நியாயப்படுத்தியது. அந்தப் பச்சை நிலை ஒரு **தவறான பச்சை நிலை**: `check:cycles` 5 துணைக் கோப்பகங்களை (450 கோப்புகள்) ஸ்கேன் செய்தது; நிலையான `import|export … from` உடன் மட்டுமே பொருத்தியது; மேலும் ஒவ்வொரு `@/` மற்றும் `@omniroute/open-sse/` குறிப்பானையும் கைவிட்டது. எனவே ரெப்போவில் ஆதிக்கம் செலுத்திய dynamic-import + alias சுழற்சிகளை அதனால் காண முடியவில்லை. இது சரிசெய்யப்பட்டது: கேட் இப்போது `src` + `open-sse` முழுவதையும் (5023 கோப்புகள்) கடந்து செல்கிறது; TypeScript AST-இலிருந்து குறிப்பான்களைச் சேகரிக்கிறது (எனவே `import("…")` கணக்கிடப்படும்; type-position `typeof import("…")` கணக்கிடப்படாது); மேலும் tsconfig `paths`-ஐத் தீர்க்கிறது. இது 0 அல்ல, **14** சுழற்சிகளைக் கண்டறிகிறது. முன்பே இருந்த 14 சுழற்சிகளை ஒரு கேட் PR-இல் சரிசெய்ய முடியாது என்பதால், `check:cycles` இப்போது ஒரு **ராட்செட்** (`--ratchet`, `quality-baseline.json`-இல் உச்சவரம்பு `metrics.cycles.value = 14`, `direction: down`) — இது எந்தவொரு _பின்னடைவையும்_ தடுக்கிறது; எண்ணிக்கை குறைய மட்டுமே முடியும். CI `npm run check:cycles:ratchet`-ஐ இயக்குகிறது. படிப்படியான குறைப்பு **A-01** உடன் தொடரும். பரந்த இரண்டாவது கருத்தாக `check:circular-deps` (dpdm) ஆலோசனை நிலையில் தொடர்கிறது.
- **சிக்கல்தன்மை** — ✅ **முடிந்தது** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ஒரே ESLint நடை, ruleId அடிப்படையிலான எண்ணிக்கை; இதனால் cyclomatic+max-lines மற்றும் cognitive அடிப்படைகள் தனித்தனியாக உள்ளன; தனிப்பட்ட `check:complexity` / `check:cognitive-complexity` ஆகியவை உள்ளூர் `--update` பயன்பாட்டிற்குத் தொடர்கின்றன.
- **`/api` கற்பனைத் தடுப்பு** — ✅ **முடிந்தது** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api`-க்கு ஒரே FS பட்டியல்; openapi-routes + docs-symbols இன்னும் தனித்தனியாக அறிக்கையிடுகின்றன; தனிப்பட்டவை உள்ளூர் இயக்கங்களுக்குத் தொடர்கின்றன.

- **CI lint-இல் `typecheck:noimplicit:core`** — ✅ **lint பணியிலிருந்து அகற்றப்பட்டது** (ஆலோசனை நிலை `continue-on-error` ஆக இருந்தது); தடைசெய்யும் வகை மேற்பரப்பு `typecheck:core` + `check:type-coverage` ஆகும். உள்ளூர் script தக்கவைக்கப்பட்டது.

### நிலைமாற்றம் / முடிவெடுத்தல் (இயக்குநர் கொள்கை)

- `check:pr-evidence` (தடைசெய்யும் நிலை, PR-body உரைநடையை grep செய்கிறது) — தவறான நேர்மறை முடிவுகளுக்கான ஆபத்து அதிகம்; இதை நீக்கினால் Hard Rule #18 அமலாக்கம் பலவீனமடையும், எனவே இது உண்மையான கொள்கை முடிவாகும்.
- `semgrep` (தனித்தியங்கும் ஆலோசனை நிலை) — OWASP குடும்பங்களில் CodeQL உடன் ஒன்றுபடுகிறது; அதன் அடிப்படையை ஒரு ராட்செட்டுடன் இணைக்கவும் அல்லது அதை நீக்கவும்.
