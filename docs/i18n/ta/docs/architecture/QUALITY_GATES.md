இந்த ஆவணம் OmniRoute-இல் உள்ள அனைத்து CI தர வாயில்களுக்குமான அதிகாரப்பூர்வ மேற்கோளாகும்.
ஒவ்வொரு வாயிலையும், அது எதைச் சரிபார்க்கிறது, எந்த CI job-இல் இயங்குகிறது, அது
ratchet baseline அல்லது pass/fail கொள்கையைப் பயன்படுத்துகிறதா, மேலும் அது build-ஐத் தடுக்கிறதா அல்லது ஆலோசனை சார்ந்ததா என்பதை விவரிக்கிறது.

சுருக்கமான தொகுப்புக்கும் allowlist கொள்கைக்கும், `AGENTS.md`-இல் உள்ள
"தர வாயில்கள் & Ratchet-கள்" பகுதியைப் பார்க்கவும். அதே அமைப்பின் முக்கியமான மதிப்பீடு,
முதிர்ச்சி வகைப்பாடு மற்றும் கருவி-சார்பற்ற மறுஉருவாக்கத் திட்டத்திற்கு,
[தர வாயில் செயல்திட்டம்](../ops/QUALITY_GATE_PLAYBOOK.md)-ஐப் பார்க்கவும்.

## கேட் சரக்கு மற்றும் செயல்படுத்தல் சுயவிவரங்கள்

### வேட்பாளர் சேர்க்கை

CI மற்றும் குவாலிட்டி கேட்ஸ் பணிப்பாய்வுகள் ஒவ்வொன்றும் நிலையான தீர்ப்பை வெளியிடுகின்றன: `Gate / CI` மற்றும் `Gate / Quality`. அவர்களின் பதிப்புச் சேர்க்கைக் கொள்கையானது ஒவ்வொரு அப்ஸ்ட்ரீம் வேலையையும் தேவை அல்லது ஆலோசனையின்படி கணக்கிடுகிறது. பொருந்தக்கூடிய தேவையான வேலை வெற்றியடைய வேண்டும்: விடுபட்ட, ரத்துசெய்யப்பட்ட, தவிர்க்கப்பட்ட, நிலுவையில் உள்ள மற்றும் அறியப்படாத முடிவுகள் PASS நிறுவ முடியாது. செல்லுபடியாகும் ஆவணம் மட்டும் அல்லது பட்டியல் மட்டும் வகைப்பாடு ஒரு குறியீட்டு பாதையை பொருந்தாததாக்கும்; வரைவு PR ஏற்றுக்கொள்ளப்பட்ட வேட்பாளர் அல்ல. ஒரு `hotfix` லேபிள் ஆதாரத்தை விட்டுவிடாது.

இரண்டு பணிப்பாய்வுகளும் PRs main/release கிளைகளாக உள்ளடக்கியது, `main` க்கு தள்ளுகிறது , கைமுறையாக அனுப்புதல் மற்றும் ஒன்றிணைத்தல்-குழு நிகழ்வுகள். முழுத் தேர்வையும் புஷ், டிஸ்பாட்ச் மற்றும் மெர்ஜ்-குரூப் இயக்கவும். `release/**` க்கு தள்ளினால் அவற்றைத் தொடங்க வேண்டாம் (2026-10-18): ஒவ்வொரு மாற்றமும் ஏற்கனவே அதன் PR இல் மேட்ரிக்ஸை இயக்கியுள்ளது மற்றும் ஒன்றிணைக்கப்பட்ட கலவையானது வெளியீடு-பசுமையின் வேலை (`docs/ops/RUNNER_BOX.md` → ஹோஸ்ட் செய்யப்பட்ட லேன்) ஆகும். ஃபோர்க்ஸ் மற்றும் மெர்ஜ் குழுக்கள் வேலைகளுக்கு ஹோஸ்ட் செய்யப்பட்ட ரன்னர்களைப் பயன்படுத்துகின்றன, இல்லையெனில் சுய-ஹோஸ்ட் ரன்னர்களைத் தேர்ந்தெடுக்கின்றன; வெளியீட்டிற்கு முன் போதுமான ஹோஸ்ட் செய்யப்பட்ட திறன் சரிபார்க்கப்பட வேண்டும்.

ஒரு சாதாரண PR வேகமான தேர்வை இயக்குகிறது. சேர்க்கைக் கொள்கையின் `full-code` மற்றும் `full-code-e2e` பாதைகள் (E2E, ஒருங்கிணைப்பு, தொகுப்பு கலைப்பொருள், Electron புகை, Bun SQLite, சுற்றுச்சூழல் அமைப்பு மற்றும் நெறிமுறை கிளையன்ட்கள்) மெர்ஜிஃபை வரிசை வரைவில் அல்லது முழு ஓட்டத்தில் மட்டுமே இயங்கும்: `gh workflow run ci.yml --ref <branch>`.

ஒவ்வொரு JSON ரசீதும் சரிபார்க்கப்பட்ட SHA, பணிப்பாய்வு ஓட்டம் மற்றும் முயற்சி ஆகியவற்றை அடையாளம் காட்டுகிறது. CLI checkout/event SHA பொருத்தமின்மையை நிராகரிக்கிறது. பணிப்பாய்வு சோதனைகள் கொள்கை உறுப்பினர்களை தீர்ப்பு வேலையின் `needs` பட்டியலில் இணைக்கின்றன, எனவே புதிய அல்லது அகற்றப்பட்ட பாதை அமைதியாக மறைந்துவிடாது. ரசீதுகள் அவற்றின் சொந்த பணிப்பாய்வுகளை உள்ளடக்கியது, வெளியீடு, வரிசைப்படுத்தல் அல்லது ஏற்கனவே உள்ள ஆலோசனை ஸ்கேனரின் உட்புறங்கள் அல்ல. கிளை விதிகளில் இரண்டு காசோலைப் பெயர்களையும் செயல்படுத்துவது ஒரு தனி நிர்வாக மாற்றமாகும்; இந்த வேலைகளைச் சேர்ப்பது ஒரு கிளையைப் பாதுகாக்காது.

### வரிசையை இணைக்கவும்

> **2026-11-19: Mergify இணைப்பு வரிசை ஓய்வு பெற்றது** (உரிமையாளரின் முடிவு). `.mergify.yml` இனி ஒரு வரிசையை வரையறுக்காது மற்றும் இழுக்கும் கோரிக்கையை ஒன்றிணைக்கும் அல்லது மீண்டும் எழுதும் Mergify கட்டளைகளை மறுக்கிறது. வெளியீட்டுக் கிளைக்கான இழுக்கும் கோரிக்கைகள் "Require green gates on the active release" (`Gate / CI` + `Gate / Quality`) என்ற களஞ்சிய விதிகளின் கீழ் omni-queue live பயன்முறையில் இயங்கும் வரை கைமுறையாக ஒன்றிணைக்கப்படும், அதன் பிறகு omni-queue வழியாக ([OMNI_QUEUE.md](../ops/OMNI_QUEUE.md)). கீழே விவரிக்கப்பட்டுள்ள Mergify வரைவுகளின் பணிப்பாய்வு கையாளுதல் இன்னும் `ci.yml` மற்றும் `quality.yml` இல் உள்ளது, ஆனால் Mergify வரைவு எதுவும் திறக்கப்படவில்லை.

`queue` லேபிள் மெர்கிஃபை வரிசைக்கு (`.mergify.yml`) PR அனுப்புகிறது. Mergify ஒரு `mergify/merge-queue/` கிளையில் ஒரு வரைவு PR திறக்கிறது, CI அங்கு முழு தேர்வையும் இயக்குகிறது, மேலும் `Gate / CI`, `Gate / Quality` மற்றும் `Merge integrity (changelog + generated skills)` கடந்து செல்லும் போது அசல் PR ஒன்றிணைகிறது.

Mergify அதன் வரிசை சுருக்கத்தை வரைவின் விளக்கத்தில் எழுதுகிறது, மேலும் பிற பயன்பாடுகளும் அதைத் திருத்தலாம். அத்தகைய வரைவில் ஒரு `pull_request` `edited` நிகழ்வு அதன் சொந்த ஒத்திசைவு குழுவை (`-queue-edit-<run_id>`) எடுக்கும், எனவே அது வரைவின் உண்மையான ஓட்டத்தை ரத்து செய்ய முடியாது, மேலும் அது கேட் மற்றும் மேட்ரிக்ஸைத் தவிர்க்கிறது. `Merge integrity` மட்டும் இன்னும் இயங்குகிறது. தவிர்க்கப்பட்ட கேட் வேலை வேறு ஒரு காசோலைப் பெயரைக் கொண்டுள்ளது, ஏனெனில் Mergify தவிர்க்கப்பட்ட `Gate / CI` தோல்வியுற்ற காசோலையாகப் படித்து PR ஐ வரிசைப்படுத்துகிறது.

ஒரு டிக்யூவிற்குப் பிறகு, ஒரு மிகுதியானது எப்போதும் PR கேட்காது. அதில் கருத்து `@mergifyio queue`.

### ஏற்பு குறைப்பாளில் தக்கவைக்கப்பட்ட ஆதாரம்

`scripts/quality/validate-release-acceptance.mjs` ஒரு வழங்கப்பட்ட திட்டத்தை குறைக்கிறது மற்றும் அதன் வெளிப்பாட்டைக் காட்டுகிறது; திட்டமானது முழுமையான வெளியீட்டு குழாய்த்திட்டத்தை உள்ளடக்கியது என்பதை அது நிறுவவில்லை. அதன் அறிக்கைகள் வெளிப்படையாக `releaseAcceptance: false` அமைக்கின்றன, அந்த திட்டம் `VERIFIED` ஆக இருந்தாலும் கூட. `release-acceptance.yml` பணிப்பாய்வு இன்னும் நிழல் பொருத்துதல்களைப் பயன்படுத்துகிறது, உண்மையான உருவாக்கம், தொகுப்பு, துவக்க அல்லது விளம்பர ரசீதுகள் அல்ல.

தக்கவைக்கப்பட்ட சான்றுகளை சரிபார்க்க CLI க்கு `--evidence-root` தேவைப்படுகிறது. கோப்புகள் `<evidence-root>/<artifact_id>/<member>` ஆக தீர்க்கப்பட்டு SHA-256 ஆக ஹாஷ் செய்யப்படுகின்றன. ஆதாரம் இல்லாத PASS பதிவு, காணாமல் போன அல்லது மாற்றப்பட்ட கோப்பு, பாதுகாப்பற்ற பாதை அல்லது சிம்லிங்க் சரிபார்ப்பைத் தடுக்கிறது. விடுபட்ட கோப்புகள் வெற்றிகரமான பதிவுகளை காலி செய்வதற்கு சமமானவை அல்ல. தற்போதுள்ள SHA/run/attempt காசோலைகள் சுயாதீனமாக உள்ளன: பொருந்தக்கூடிய பைட்டுகள் பழைய ரசீதை மீட்டெடுக்க முடியாது. கோப்பு ஒருமைப்பாடு என்பது செயல்பாட்டின் நம்பகத்தன்மை அல்லது கலைப்பொருள் ஊக்குவிப்புக்கான ஆதாரம் அல்ல.

### நிலையான ஸ்கேன் இருப்பு

பதிப்பு செய்யப்பட்ட npm-alias சரக்கு மற்றும் நிலையான ஸ்கேன் உறுப்பினர் `config/quality/gate-manifest.json` இல் வாழ்கின்றனர். ஸ்கிரிப்ட் பெயர்கள் மற்றும் `package.json` க்கு எதிரான சரியான கட்டளைகளை சரிபார்க்க `npm run check:gate-manifest` இயக்கவும்; சேர்த்தல், நீக்குதல் மற்றும் கட்டளை சறுக்கல் ஆகியவை CI இல் உள்ள உள்ளூர் கொக்கி மற்றும் மாற்றம்-வகைப்படுத்தல் வேலைகள் இரண்டிலும் தோல்வியடைகின்றன. மாற்றுப்பெயர் என்பது பணிப்பாய்வு வேலை, மேட்ரிக்ஸ் நிகழ்வு அல்லது சோதனை வழக்கு அல்ல: இந்த எண்ணிக்கைகள் ஒன்றுக்கொன்று மாற்றத்தக்கதாக வழங்கப்படக்கூடாது.

தேர்ந்தெடுக்கப்பட்ட மாற்றுப்பெயர்களை இயக்காமல் ஆய்வு செய்ய `npm run quality:scan -- --list` அல்லது `npm run quality:scan:fast -- --list` பயன்படுத்தவும். ரன்னர் npm நுழைவுப் புள்ளியை அழைக்கிறார், எனவே அதன் இயக்க நேரம் (கமைக்கப்பட்ட Bun உட்பட) பாதுகாக்கப்படுகிறது. மேனிஃபெஸ்ட் ரெக்கார்டுகள் அந்த சுயவிவரங்களுக்கு வெளியே தனித்தனியாக அழைக்கப்படும் மாற்றுப்பெயர்கள், மேலும் படிக்க-மட்டும் ஸ்கேன் சுயவிவரங்களில் பராமரிப்பு கட்டளைகள் தடைசெய்யப்பட்டுள்ளன.

இந்த சுயவிவரங்கள் நிலையான ஸ்கேன் மட்டுமே உள்ளடக்கும். தயாரிப்பு சோதனைகள், கவரேஜ், பேக்கேஜிங், வெளிப்புற காசோலைகள் அல்லது வேட்பாளரின் முழு வெளியீட்டு ஏற்பு ஆகியவற்றை அவர்கள் சான்றளிக்க மாட்டார்கள். பணிப்பாய்வு சேர்க்கை இணைக்கப்பட்ட `config/quality/admission-policy.json` மற்றும் `scripts/quality/admission-verdict.mjs` ஐப் பயன்படுத்துகிறது. வெளியீடு-பார்வையாளர் சுயவிவரங்கள் தனித்தனியாக இருக்கும்; அவற்றின் பொருந்தக்கூடிய காசோலைகள் மற்றும் ரசீதுகளை சுயாதீனமாக சரிபார்க்கவும். முழு பார்வையாளரின் நிலையான கட்டளைகள் `config/quality/release-green-static-profile.json` இல் அறிவிக்கப்படுகின்றன, இதில் `audit:deps`, பிறழ்வு-சோதனை தேர்வு மற்றும் மொழிபெயர்ப்பு சோதனைகள் ஆகியவை அடங்கும். package.json மற்றும் மாதிரியான CI/Quality அறிவிப்புகளுக்கு எதிராக npm கட்டளைகளை ஏற்றி சரிபார்க்கிறது; ஷெல் டோக்கன்களை வாதங்களாக செயல்படுத்துவதற்குப் பதிலாக அது சறுக்கலை நிராகரிக்கிறது. தேவையான ஸ்கேனர் SKIP/INCOMPLETE வெளியீடு PASS நிறுவ முடியாது. சுயவிவரமானது அதன் வெளிப்புற விலக்குகளைப் பதிவுசெய்கிறது மற்றும் ஹோஸ்ட் செய்யப்பட்ட கவரேஜ், சோதனை மெட்ரிக்குகள், தொகுப்பு அல்லது வரிசைப்படுத்தல் சான்றுகளை மாற்றாது. கீழே உள்ள உரைநடை பட்டியல் ஒரு குறிப்பு, ஒரு வாயில் உண்மையில் இயங்கியது என்பதற்கான ஆதாரம் அல்ல.

ஸ்கிரிப்ட்கள் `scripts/check/` (பாலிசி கேட்ஸ்) மற்றும் `scripts/quality/` (ராட்செட் என்ஜின்) ஆகியவற்றின் கீழ் வாழ்கின்றன. உண்மையின் CI மூலமானது `.github/workflows/ci.yml` ஆகும்.

### PR விரைவுப் பாதையை (`quality.yml`) வெளியிடு

`.github/workflows/quality.yml` main/release PRs இல் CI நிரப்புகிறது, `main` க்கு தள்ளுகிறது, குழுக்களை அனுப்புகிறது மற்றும் ஒன்றிணைக்கிறது. PRs பாதை-வடிகட்டப்பட்ட வேகமான சோதனைகளைப் பயன்படுத்துகிறது. நிரந்தரமாக முடக்கப்பட்ட நகல் உருவாக்கம் அகற்றப்பட்டது; உண்மையான build/package/boot காசோலைகள் CI இல் இருக்கும். யூனிட் தொகுப்பு மற்றும் vitest CI (`Unit Tests (N/8)` மற்றும் `Vitest`) இல் மட்டுமே இயங்கும்.

#### மறக்கப்பட்ட உடன்பிறப்பு சோதனை அறிக்கை

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` இன் ஆலோசனைப் படியாக இயங்குகிறது மற்றும் சோதனை-தாக்க வரைபடத்தின் பின்னால் உள்ள இறக்குமதி தீர்வை மீண்டும் பயன்படுத்துகிறது. மாற்றப்பட்ட ஒவ்வொரு உற்பத்தி தொகுதிக்கும், விண்ணப்பதாரர் சோதனையானது இழுத்தல்-கோரிக்கை வித்தியாசத்தில் இல்லாதபோது, அது தீர்மானிக்கும் `changed module/symbol -> static consumer -> candidate sibling test` சங்கிலிகளைப் புகாரளிக்கிறது. மார்க் டவுன் சுருக்கம் மற்றும் JSON முடிவு ஆகியவை `forgotten-sibling-tests` பணிப்பாய்வு கலைப்பொருளாகத் தக்கவைக்கப்படும்.

பீப்பாய் மறு-ஏற்றுமதி மற்றும் மாறும் இறக்குமதிகள் தீர்மானம் கண்டறிதல் மட்டுமே; அவர்கள் ஒருபோதும் தடுக்கும் கண்டுபிடிப்பை உருவாக்க மாட்டார்கள். மதிப்பாய்வு செய்யப்பட்ட விதிவிலக்குகள் `config/quality/forgotten-sibling-allowlist.json` இல் உள்ளன. ஒவ்வொரு உள்ளீடும் நுகர்வோர் மற்றும் வேட்பாளர் சோதனைக்கு பெயரிட வேண்டும், ஒரு குறிப்பிட்ட பகுத்தறிவைக் கொடுக்க வேண்டும், மேலும் ஒரு GitHub சிக்கலை இணைக்க வேண்டும் அல்லது கோரிக்கையை இழுக்க வேண்டும். தவறான உள்ளீடுகள் தோல்வியடைந்தன. நீக்கப்பட்ட வேட்பாளர் சோதனையையோ அல்லது `.skip`/`.todo` ஐ சேர்க்கும் வித்தியாசத்தையோ விதிவிலக்குகளால் அடக்க முடியாது ; வலியுறுத்தல் வலுவிழக்கச் செய்தல் மற்றும் பிற மறைத்தல் ஆகியவை சுதந்திரமாகத் தடுக்கும் `check:test-masking` வாயிலுக்குச் சொந்தமானவை.

#### இரண்டு தட்டச்சுச் சோதனை நிரல்கள் வித்தியாசமாக பதிலளிக்கின்றன

`typecheck:core` மற்றும் `check:build-typecheck` வெவ்வேறு விருப்பங்களின் கீழ் வெவ்வேறு நிரல்களைத் தொகுக்கின்றன, மேலும் ஒரே கோப்பு ஒன்றில் சுத்தமாகவும் மற்றொன்றில் பிழைகள் நிறைந்ததாகவும் இருக்கும்.

`tsconfig.build.json` `"strict": false` அமைக்கிறது, எனவே `noImplicitAny` முடக்கப்பட்டுள்ளது. கோர் கன்ஃபிகரானது, 27-கோப்பு அனுமதிப் பட்டியலைக் கடுமையான விருப்பங்களுடன் தொகுத்து, ஒவ்வொரு உள்ளீட்டின் இறக்குமதி வரைபடத்தையும் பின்பற்றுகிறது, எனவே பில்ட் புரோகிராமில் தோன்றாத கோப்புகள் இன்னும் அங்கு சரிபார்க்கப்படுகின்றன.

கோப்பு தட்டச்சு செய்யப்பட்டுள்ளதா என்பதை தீர்மானிக்கும்போது அதன் விளைவு முக்கியமானது:** `check:build-typecheck` இன் கீழ் பூஜ்ஜிய கண்டறிதல் என்பது பூஜ்ஜியத்தைக் குறிக்காது** . 26 கோப்புகளில் இருந்து `@ts-nocheck` அகற்றுவது, பில்ட் புரோகிராமில் 23ஐ சுத்தமாக காட்டியது; அவற்றில் பதினாறு சுமார் 120 மறைமுகமான பிழைகள் வெளிப்பட்டன. கோப்பை சுத்தமாக அழைப்பதற்கு முன் இரண்டையும் சரிபார்க்கவும்.

#### மொழிபெயர்ப்பு கண்ணாடிகள் பெறப்பட்ட கோப்புகள் (PR முறை மற்றும் வெளியீட்டு முறை)

ஒரு அம்சம் PR ஆங்கில மூலங்களை மட்டுமே திருத்துகிறது. `docs/i18n/<locale>/**` கண்ணாடிகள் (66 `llm.txt` பிரதிகள் மற்றும் மொழிபெயர்க்கப்பட்ட `CHANGELOG.md` கோப்புகள் உட்பட) மற்றும் `.i18n-state.json` மொழிபெயர்ப்பு அலை (`docs/i18n-*` / `chore/i18n-*` கிளைகள், திட்டமிடப்பட்ட `i18n-mirror-refresh.yml`) மற்றும் வெளியீட்டின் (`npm run release:sync-changelog-i18n`) மூலம் ஒரு படியில் மீண்டும் எழுதப்படுகின்றன. எனவே கண்ணாடி வாயில்கள் இரண்டு முறைகளில் இயங்குகின்றன, `scripts/check/lib/gateMode.mjs` (`--mode=pr|release`, பின்னர் `OMNIROUTE_GATE_MODE`, பின்னர் செயல்கள் நிகழ்வு; ஒரு உள்ளூர் ரன் `release`) மூலம் தீர்க்கப்படுகிறது:

- `check:docs-sync` — வெளியீட்டு பயன்முறை ஒவ்வொரு காசோலையிலும் இயங்குகிறது. PR பயன்முறையானது package.json/OpenAPI பதிப்பு, ரூட் CHANGELOG தலைப்புகள் மற்றும் மேற்படிப்பு-டாக்ஸ் PR வைத்திருக்கிறது, மேலும் `llm.txt` கண்ணாடி பிரதிகள் மற்றும் மொழிபெயர்க்கப்பட்ட CHANGELOG பிரிவுகளுக்கு `SKIP reason=pr-mode` — `config/quality/derived-paths/*.json` யாருடைய சொந்த வேறுபாடு `docs/i18n/<locale>/llm.txt` அல்லது `docs/i18n/**` `CHANGELOG.md` திருத்துகிறது, அது கண்டிப்பாக சரிபார்க்கிறது. ஒரு depth-1 செக் அவுட்டில் ( `docs-sync-strict` ஜாப்) டிஃப் பேஸ் தீர்க்கப்படாது, எனவே PR பயன்முறையில் அடிப்படை தேவையில்லாத ஒரு காசோலையும் இயங்குகிறது: ஒவ்வொரு `llm.txt` கண்ணாடியும் இருக்க வேண்டும், அதன் `---` பிரிப்பானை வைத்திருக்க வேண்டும் மற்றும் ரூட் உடல் அல்லது பெரும்பாலான கண்ணாடிகள் பகிர்ந்து கொள்ளும் உடலை எடுத்துச் செல்ல வேண்டும். நகர்த்தப்பட்ட ஒரு தளம் அனைத்து கண்ணாடிகளையும் சமமாக பழையதாக விட்டுவிட்டு கடந்து செல்கிறது; ஒரு கண்ணாடியில் கை திருத்தம் தோல்வியடைந்தது. மொழிபெயர்க்கப்பட்ட `CHANGELOG.md` கோப்புகளுக்கு depth-1 PR செக் அவுட்டில் அத்தகைய சரிபார்ப்பு இல்லை.
- ப்ரீ-கமிட் ஹூக் `check-docs-sync.mjs --mode=pr` இயங்குகிறது: ஒரு உறுதி என்ன செய்கிறது என்பதை தீர்மானிக்கப்படுகிறது. கொடி இல்லாமல் உள்ளூர் ரன் என்பது வெளியீட்டு பயன்முறையாகும், மேலும் ரூட் `llm.txt` திருத்தும் ஒரு இணைக்கப்பட்ட PR அலை இயங்கும் வரை அந்தத் தளத்தில் ஒவ்வொரு கமிட் செய்வதையும் தடுக்கும். ஹஸ்கி ஹூக் இயங்கும் எந்த மோட்-அவேர் கேட்க்கும் இதே விதி உள்ளது: ஹூக் `--mode=pr` கடந்து செல்கிறது, மேலும் கடுமையான தீர்ப்பு வெளியீட்டு பயன்முறை ரன்களுடன் இருக்கும் (வெளியீடு PR, `main` க்கு தள்ளுகிறது, ஒரு சாதாரண உள்ளூர் ரன்).
- மிரர்-உள்ளடக்க அலகு சோதனைகள் (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`, `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`, `docs/*-locales`) — வெளியீட்டு முறை ஒவ்வொரு இடத்தையும் உறுதிப்படுத்துகிறது. PR பயன்முறையானது `.i18n-state.json` (முழு-கோப்பு ஹாஷ் அல்லது சோதனை பின்களின் பிரிவில் பதிவுசெய்யப்பட்ட பகுதி ஹாஷ்) படி ஆங்கில மூலத்துடன் தற்போதைய கண்ணாடிகளை மட்டுமே உறுதிப்படுத்துகிறது மற்றும் பழையவற்றை ஒரு காரணத்துடன் தவிர்க்கிறது. `target_hash` ஆதார சோதனைகள் இரண்டு முறைகளிலும் ஒவ்வொரு லோகேலுக்கும் இயங்கும். ஒரு `## ` பிரிவிற்கு புத்துணர்ச்சி, அலகு `run-translation.mjs` ஹாஷ்கள்; ஒரு நீண்ட பகுதி (இந்த கோப்பின் கேட் இருப்பு அதன் பாதி) அதாவது அதில் ஏதேனும் திருத்தம் இருந்தால், அந்த கண்ணாடிகள் பழையதாகிவிடும், மேலும் அவற்றின் PR-முறை வலியுறுத்தல்கள் அடுத்த அலை வரை தவிர்க்கப்படும். ஆங்கில மூலத்தில் இல்லாத ஒரு நங்கூரம் முழு கோப்பு ஒப்பீட்டுக்கு திரும்பும்.
- PRs இல்`i18n translation drift` — ஆலோசனை , தள்ளுவதில் கண்டிப்பானது, இரவு மற்றும் வெளியீட்டு வெட்டு, எனவே ஒரு பழைய கண்ணாடியை வெளியீட்டில் அனுப்ப முடியாது.

`scripts/i18n/sync-llm-mirrors.mjs` ( `syncLlmMirrors()` ஆகவும் ஏற்றுமதி செய்யப்படுகிறது, `--dry-run` உடன்) `llm.txt` கண்ணாடிகளை மீண்டும் எழுதுகிறது; வெளியீட்டு புதுப்பிப்பு, மொழிபெயர்ப்பு அலை மற்றும் திட்டமிடப்பட்ட `i18n-mirror-refresh.yml` அதை இயக்குகிறது (புதுப்பிப்பு பழைய `llm.txt` கண்ணாடிகளை உலர் ரன் மூலம் கண்டறிந்து, டிரிஃப்ட் அறிக்கை அவற்றை பட்டியலிடவில்லை, மேலும் அவற்றை `check:docs-all` முன் ஒத்திசைக்கிறது).

`docs/diagrams/` இன் கீழ் உள்ள பன்னிரண்டு README SVGs உருவாக்கப்படுகிறது (`scripts/docs/gen-readme-<name>.mjs`; `npm run docs:readme-diagrams` அவை அனைத்தையும் மீண்டும் உருவாக்குகிறது). ஒவ்வொன்றும் ஒரு பைட்-ஒப்பிட அலகு சோதனையை (`tests/unit/docs/readme-*-svg.test.ts`, job `test-unit`) கொண்டுள்ளது, அது உறுதிசெய்யப்பட்ட கோப்பு வெளியீட்டு பயன்முறையில் பழையதாக இருக்கும்போது தோல்வியடைகிறது; ஒரு PR இல், `check:generated-artifacts` ஒரு SVG ஐ PR திருத்துகிறது மற்றும் தளத்தின் சறுக்கல் வெளியீட்டுப் புதுப்பிப்புக்கு விடப்படுகிறது ( [உருவாக்கப்பட்ட கோப்புகள் மற்றும் பெறப்பட்ட அடிப்படைக் குறிப்புகளைப்](#generated-files-and-derived-baselines-written-at-release) பார்க்கவும்) — மற்றும் `check:docs-counts` அவற்றின் `<text>` முனைகளில் இருந்து — இல் இருந்து நியமன எண்களைப் படிக்கிறது, அதனால்தான் கோடிட்டுக் காட்டப்பட்ட ஒவ்வொரு கோப்பிலும் `<text>`. SVG நியமன எண்கள் சரிபார்ப்பு `SVG_DIAGRAM_FILES` (`scripts/check/check-docs-counts-sync.mjs`) இல் பட்டியலிடப்பட்டுள்ள கோப்புகளைப் படிக்கிறது: `docs/diagrams/readme-hero.svg`, `free-tier-budget.svg`, `promise-pillars.svg`, `comparison-table.svg`, `cli-terminal.svg`, `tier-cascade.svg`, பிளஸ் `public/images/tier-flow-dark.svg` மற்றும் `tier-flow-light.svg`; free-forever, catalog-entry, recurring-pool மற்றும் ஸ்கோரிங் காரணிகள் உரிமைகோரல்கள் `promise-pillars.svg`, `free-tier-budget.svg` மற்றும் `strategies-grid.svg`. இந்த ஜெனரேட்டர்கள் வரையப்படும் எண்ணிக்கைகள் (வழங்குபவர்களின் மொத்த, MCP கருவிகள், ரூட்டிங் உத்திகள், இலவசம்-என்றென்றும் வழங்குநர்கள், ...) உண்மைகள் ஸ்னாப்ஷாட் `docs/reference/derived-facts.json` மூலம் `scripts/docs/readmeFacts.mjs` மூலம் வந்தவை, எழுத்து வடிவங்களிலிருந்து அல்ல, எனவே எந்தவொரு கிளையிலும் வரைபடத்தை மீண்டும் உருவாக்குவது உறுதியான கோப்பை மீண்டும் உருவாக்குகிறது. `free-tier-budget.svg` அதன் வரிசைகளை அதே ஸ்னாப்ஷாட்டில் இருந்து வரைகிறது (`code.freeTierBudget`, கேட்லாக் சுருக்கம் உண்மைகள் ஆய்வு பதிவுகள்), எனவே `FREE_MODEL_BUDGETS` க்கு மாற்றம் CI சிவப்பு நிறமாக மாறுவதற்கு பதிலாக அடுத்த புதுப்பிப்பில் அட்டையை அடைகிறது.

### பெறப்பட்ட மதிப்புகள்: `pr` மற்றும் `release` கேட் முறைகள்

ஒரு அம்சம் PR அதன் அடித்தளத்தின் நிலையைப் பொறுத்து மதிப்பை எழுதுவதில்லை: வழங்குநர், இடம்பெயர்வு, MCP-கருவிகள் மற்றும் உத்தி எண்ணிக்கைகள், README SVG எண்கள், உண்மைகள் ஸ்னாப்ஷாட். ஒரு படி அவை அனைத்தையும் மறுகணிப்பீடு செய்கிறது, `npm run release:refresh-derived`, வெளியீடு மற்றும் இரவு பெறப்பட்ட புதுப்பிப்பு PR மூலம் இயக்கப்படும். எனவே** வெளியீடுகளுக்கு இடையே அடிப்படையானது வடிவமைப்பின்படி நேரடிக் குறியீட்டிற்குப் பின்னால் உள்ளது** , மற்றும் ஒரு உடன்பிறப்பு வழங்குநரைச் சேர்த்த பிறகு, மரத்தை நேரடிக் குறியீட்டுடன் ஒப்பிடும் வாயில் அல்லது சோதனை ஒவ்வொரு PR லும் சிவப்பு நிறத்தில் இருக்கும். பெறப்பட்ட மதிப்புகளை தீர்மானிக்கும் வாயில்கள் இரண்டு முறைகளில் ஒன்றில் இயங்கும், `scripts/check/lib/gateMode.mjs` மூலம் தீர்க்கப்படும் (முதல் போட்டியில் வெற்றிகள்):

1. கட்டளை வரியில்`--mode=pr|release` ;
2. `OMNIROUTE_GATE_MODE` சூழல் மாறி (`pr` அல்லது `release`);
3. தானியங்கி, GitHub செயல்கள் நிகழ்விலிருந்து: `release/v*` அல்லாத ஒரு `pull_request`, ஒரு `merge_group`, அல்லது `omni-queue/**` → `pr` க்கு ஒரு புஷ் ; மற்ற அனைத்தும் (தள்ளுதல், அட்டவணை, அனுப்புதல், வெளியீடு PR `release/v* → main`, எந்த உள்ளூர் ரன்) → `release`.

ஒவ்வொரு பயன்முறையிலும் என்ன `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) தோல்வியடைகிறது:

| பயன்முறை  | தோல்வி அடைகிறது                                                                                                                                                                                                                                                                                                                                                                                                                                    | நேரடி உண்மைகள் தேவை |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| `release` | ஒவ்வொரு சரிபார்ப்பும், மரத்திலிருந்து சேகரிக்கப்பட்ட உண்மைகளுக்கு எதிரான கடுமையான சமத்துவச் சரிபார்ப்பு (கேட் எப்போதும் கொண்டிருந்த நடத்தை): காலாவதியான எண்ணிக்கை, பதிப்பு, கவரேஜ் குறைந்தபட்சம் அல்லது SVG எண் ஆகியவற்றில் ஏதேனும் STRICT drift ஆகும்                                                                                                                                                                                             | ஆம்                 |
| `pr`      | மாற்றம் செய்தவை மட்டுமே, அதே claim extractors-ஐப் பயன்படுத்தி PR base-க்கு எதிராக diff செய்யப்படும்: (1) அந்தச் சரிபார்ப்பு மற்றும் கோப்புக்கான base-ல் இல்லாத managed value ("PR edited a managed number — restore the line to the base text"); (2) base-ல் இருந்தும் head-ல் காணாமல் போன required claim. உண்மைகள் தேவையில்லாத content invariants, release mode-ல் இயங்குவது போலவே இயங்கும்; release-only checks பட்டியலிடப்பட்டு தவிர்க்கப்படும் | இல்லை               |

முகவர்-அறிவுறுத்தல் கோப்புகள் எடுத்துச் செல்கின்றன** இல்லை** பெறப்பட்ட எண்ணிக்கை: `AGENTS.md`, `llm.txt` (மற்றும் அதன் `docs/i18n/*/llm.txt` பிரதிகள்), bs `AGENTS.md` ஃபோர்க், `open-sse/services/AGENTS.md`, `src/shared/constants/agentSkills.ts`, `skills/README.md` மற்றும் ஒவ்வொரு `skills/*/SKILL.md` புள்ளியும் மூலத்திற்கு (உதாரணமாக `src/shared/constants/routingStrategies.ts` இல் `ROUTING_STRATEGY_VALUES` ) மற்றும் அதற்கு பதிலாக `npm run facts`. மாறாத "பெறப்பட்ட எண்ணிக்கைகள் இல்லை (ஏஜென்ட்-அறிவுறுத்தல் கோப்பு ...)" இரண்டு முறைகளிலும் (வழங்குபவர்கள், இடம்பெயர்வுகள், MCP கருவிகள் மற்றும் நோக்கங்கள், ரூட்டிங் உத்திகள், மதிப்பெண் காரணிகள், பயன்முறைப் பொதிகள்) எண்ணிக்கையில் தோல்வியடைகிறது, எனவே வெளியீட்டு புதுப்பிப்பு ஒரு அறிவுறுத்தல் கோப்பை மீண்டும் எழுத வேண்டியதில்லை.

`pr` பயன்முறையில் எழுத்தாளர் கிளைகள் நிர்வகிக்கப்பட்ட மதிப்புகளைத் திருத்தலாம்: `chore/derived-*` (இரவு புதுப்பித்தல் PR), `release/v*`, மற்றும் மொழிபெயர்ப்பு அலைகள் `docs/i18n-*` மற்றும் `chore/i18n-*` (`scripts/check/lib/derivedClaimsDiff.mjs`). வரிசை தொகுதிகள் (`merge_group`, Mergify drafts, `omni-queue/**`) மீண்டும் தீர்மானிக்கப்படுவதில்லை: அவை ஏற்கனவே ஒவ்வொன்றாக தீர்மானிக்கப்பட்ட PRs வாயிலின் தொகை.

வெளியேறும் குறியீடுகள்: `0` clean · `1` STRICT drift (அல்லது `--strict` உடன் மென்மையான சறுக்கல்) அல்லது நிர்வகிக்கப்பட்ட CI மீறல் · `2` உள்கட்டமைப்பு — குறியீட்டு உண்மைகளை சேகரிக்க முடியவில்லை (tsx ஆய்வு தோல்வியடைந்தது அல்லது காலாவதியானது; நேரம் முடிந்தது `OMNIROUTE_FACTS_TIMEOUT_MS`, இயல்புநிலை 60,000 PR வேறுபாடு அடிப்படையை தீர்க்க முடியவில்லை. ஒரு வெளியேறு 2 ஒரு ஆவணம் வேறுபாடல்ல: வேலையை மீண்டும் இயக்கவும் அல்லது சூழலை சரிசெய்யவும்.

அதன் பின்னால் உள்ள கட்டளைகள்:

- `npm run facts` ஒவ்வொரு பெறப்பட்ட எண்ணையும் JSON (`scripts/release/facts.mjs`) ஆக அச்சிடுகிறது. `--key=code.mcpTools` ஒரு மதிப்பை அச்சிடுகிறது, நேரடி மரத்திற்கு பதிலாக `--snapshot` உறுதியான ஸ்னாப்ஷாட்டைப் படிக்கிறது. உண்மைகளை சேகரிக்க முடியாத போது 2 லிருந்து வெளியேறவும்.
- `npm run release:refresh-derived` (`scripts/release/refresh-derived.mjs`) பெறப்பட்ட கோப்புகளை இந்த வரிசையில் ( `--only=` க்கான படி ஐடிகள்) ஒரு பாஸில் மீண்டும் கணக்கிடுகிறது: `provider-reference` (`docs/reference/PROVIDER_REFERENCE.md`), `facts` (ஸ்னாப்ஷாட்), `numbers` (கவுண்ட்ஸ் கேட்டின் மறுஎழுத்துத் திட்டம் ஆவணங்களுக்குப் பயன்படுத்தப்பட்டு, பின்னர் `readme-diagrams` `docs/i18n/`, `skills` `SKILL.md` எடுத்துச் செல்லப்படுகிறது), ), `e2e-timings` (மரம் அனுப்பப்படும் வரை `syncE2eTimings`), `ui-keys` (prunes keys `en.json` dropped and, `--rewritten-since=<ref>` — default `origin/main` — உடன் மீண்டும் வரிசைப்படுத்தப்பட்ட ஆங்கில மதிப்புகள் கடந்த வெளியீட்டிலிருந்து மீண்டும் எழுதப்பட்டன; மதிப்புகள் அதே இயக்கத்தில் மொழிபெயர்க்கப்படும் அல்லது பின்தளத்தில் உள்ளமைக்கப்பட்ட விசைகளால் மட்டுமே மாற்றப்படும். Google இன்ஜின் பின்தளத்தில் இல்லாமல் `__MISSING__` குறிப்பான்களை எழுதாது: வெளியீட்டு சுயவிவரம் தோல்வியடைகிறது, இரவு நேர விசைகளைத் `--allow-untranslated` `OMNIROUTE_TRANSLATION_*` நோக்கத்துடன் எழுதுகிறது), `llm-mirrors` மற்றும் `.env` (எழுதப்பட்ட பிறகு, `check:generated-artifacts` மற்றும் `verify-generated` ஆகியவை கடந்து செல்ல வேண்டும்; `--check` இல் தவிர்க்கப்பட்டது மற்றும் `check:agent-skills-sync` வெளியேறும் போது `--only` வெளியேறும்). `changelog` படி தேர்வு செய்யப்பட்டுள்ளது (`--with-changelog`, சுயவிவரத்தை மட்டும் வெளியிடவும்). `--profile=nightly` பதிப்பு உரிமைகோரலை ஒருபோதும் தொடாது. `-- --check` உடன் அது எதையும் எழுதாது மற்றும் 1 இல் இருந்து வெளியேறும் போது எந்த கோப்பு மாறினாலும் அல்லது நிர்வகிக்கப்பட்ட மதிப்புக்கு கைமுறையாகத் திருத்தம் தேவைப்படும் (இரண்டையும் பட்டியலிடுகிறது); உள்கட்டமைப்பு தோல்வியில் வெளியேறு 2. `--json` முடிவை JSON ஆக அச்சிடுகிறது.
- `docs/reference/derived-facts.json` என்பது கடைசியாகப் பயன்படுத்தப்பட்ட உண்மைகளின் ஸ்னாப்ஷாட் ஆகும். புதுப்பிப்பு மட்டுமே அதை எழுதுகிறது. README SVG ஜெனரேட்டர்கள் அதைப் படிக்கின்றன, மேலும் PR-டைம் யூனிட் சோதனைகள் உறுதியான ஆவணங்கள் மற்றும் உருவாக்கப்பட்ட கோப்புகளை அதனுடன் — நேரடி குறியீட்டுடன் ஒப்பிடாது. தொகுப்பின் ஒற்றை நேரடி ஒப்பீடு `tests/unit/check-docs-counts-sync.test.ts` இல் "வெளியீடு புதுப்பிப்பு சுழற்சியை மூடுகிறது" : நேரடி உண்மைகளுடன், நினைவகத்தில் பயன்படுத்தப்படும் புதுப்பிப்பின் மறுஎழுத்து திட்டம் அது புகாரளிக்காத STRICT சறுக்கலை விட்டுவிடாது, மேலும் மறு திட்டமிடல் எதையும் மாற்றாது.

உள்நாட்டில் இனப்பெருக்கம் செய்ய (உள்ளூர் இயக்கமானது `release` க்கு இயல்புநிலையாக இருக்கும்):

```bash
npm run check:docs-counts                                       # release: strict, live facts
node scripts/check/check-docs-counts-sync.mjs --mode=pr          # what a feature PR is judged on
OMNIROUTE_GATE_MODE=pr BASE_REF="origin/release/v$(node -p "require('./package.json').version")" npm run check:docs-counts
npm run release:refresh-derived -- --check                       # what the release would rewrite
```

தீர்க்கக்கூடிய அடிப்படை இல்லாமல் ( `BASE_SHA`/`BASE_REF` இல்லை, உள்ளூர் `origin/release/v<version>` இல்லை) ஒரு உள்ளூர் `pr` ரன் ஒரு எச்சரிக்கையை அச்சிட்டு, தோல்விக்கு பதிலாக வேறுபாட்டைத் தவிர்க்கிறது.

`fetch-depth: 0` — தேவை `en.json`

**இரண்டு முறைகள் (2026-11-13 முதல்).** ஒரு அம்சம் PR `en.json` (மற்றும் `bin/cli/locales/en.json`) இல் விசைகளைச் சேர்க்கிறது அல்லது மீண்டும் எழுதுகிறது மற்றும் வேறு எந்த இடத்தையும் தொடாது; `check:pr-derived-paths` (வேலை `pr-test-policy`, குடும்ப `config/quality/derived-paths/translation.json`) ஒரு அம்சம் PR தோல்வியடைகிறது. மற்ற மொழிகள் ஒரு வெளியீட்டிற்கு ஒரு முறை `release:refresh-derived` ஆல் முடிக்கப்படும், இது `scripts/i18n/sync-ui-keys.mjs` இல் `syncUiKeys()` என்று அழைக்கிறது (காணாமல் போன விசைகளைச் சேர், ப்ரூன் கைவிடப்பட்டவை, மீண்டும் எழுதப்பட்ட ஆங்கிலத்தின் மொழிபெயர்ப்புகளை `rewrittenSinceRef`, மொழிபெயர்ப்பில் குறிக்கவும்) அல்லது மொழிபெயர்ப்பு அலை மூலம். கேட்கள் `scripts/check/lib/gateMode.mjs` இலிருந்து பயன்முறையைப் படிக்கின்றன: `pr` பயன்முறையில் (அம்சம் PRs, `merge_group`, `omni-queue/**`) வெளியீட்டு முறை கேட்களை `SKIP reason=pr-mode` அச்சிட்டு வெளியேறவும் 0; `release` பயன்முறையில் (வெளியீடு PR, `main`, `workflow_dispatch`, லோக்கல் ரன்களுக்குத் தள்ளுகிறது) அவை முன்பு போலவே கண்டிப்பானவை, மேலும் PR வெளியீட்டில் வேறுபாடு தெரிந்தவர்கள் `BASE_REF=origin/main` பெறுவார்கள், எனவே சுழற்சியில் சேர்க்கப்பட்ட அல்லது மீண்டும் எழுதப்பட்ட ஒவ்வொரு விசையையும் அவர்கள் தீர்மானிக்கிறார்கள். அம்சம்-PR தீர்ப்பை உள்நாட்டில் `--mode=pr` உடன் முன்னோட்டமிடுங்கள்.

`pr` பயன்முறையில் (மொழிபெயர்ப்பு அலை, வெளியீட்டு புதுப்பிப்பு, மொழிபெயர்ப்பு-மட்டும் சரிசெய்தல்) லோக்கல் கேட்லாக்குகளை மாற்றும் PR தவிர்க்கப்படவில்லை: `check-key-completeness` ஒவ்வொரு பட்டியலையும் ஒரே அட்டவணையில் மாற்றியமைக்கிறது (`scripts/i18n/lib/touched-catalogs.mjs`) மற்றும் ஒரு விசையில் தோல்வியுற்றால் பட்டியல் இழந்தது அல்லது ஒரு முக்கிய `en.json` இனி மொழிபெயர்ப்பாக மாறாது அல்லது உண்மையான மொழியாக மாறவில்லை `__MISSING__:` தொடாத ஆங்கில சரத்தின் placeholders/tags PR. PR இல் ஒரு புதிய பட்டியல் முழு `en.json` விசை தொகுப்பையும் கொண்டு செல்ல வேண்டும். ஒரு PR தொடும் பட்டியல்களுக்கு, விகிதம் மற்றும் CLI-பாரிட்டி கேட்கள் என்ன பார்க்கின்றன என்பதை உள்ளடக்கியது.

லோக்கல்-பேரிட்டி யூனிட் சோதனைகள் (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) `tests/_helpers/localeParityMode.ts` மூலம் அதே முறைகளைப் பின்பற்றுகின்றன: `pr` பயன்முறையில் அவை விசை-பரிட்டி வலியுறுத்தல்களைத் தவிர்த்துவிட்டு, விசைகளின் ஒதுக்கிட சமநிலையைப் புதுப்பித்து வெளியீட்டிற்கு விட்டுவிடுகின்றன, அதன் ஆங்கிலம் மாறியதால், யூனிட் அடிப்படையைப் படிக்க முடியாது. அந்த உதவியாளர் தான்** மட்டுமே** அனுமதிக்கப்பட்ட பயன்முறை-நிபந்தனை தவிர்: `check:test-masking` `.skip(` மற்றும் `{ skip: true }` ஐக் கணக்கிடுகிறது, ஆனால் கணக்கிடப்பட்ட `{ skip: "<reason>" }` ஐக் கணக்கிடாது, எனவே `tests/unit/locale-parity-mode.test.ts` அதைப் பயன்படுத்த அனுமதிக்கப்படும் சோதனைகளின் பட்டியலைப் பின் செய்கிறது — ஐச் சேர்ப்பது அந்த பட்டியலில் மதிப்பாய்வு செய்யப்பட்ட திருத்தமாகும்.

#### `check-ui-value-drift` — பழமையான-மொழிபெயர்ப்பு வாயில்

ஒரு i18n பின்னடைவை மற்ற வாயில்கள் அமைப்புரீதியாகப் பார்க்க முடியாது: ஆங்கில மதிப்பு மீண்டும் எழுதப்பட்டது மற்றும் _previous_ ஆங்கிலத்திலிருந்து பெறப்பட்ட மொழிபெயர்ப்புகள் பின் தங்கியிருக்கும், எனவே ஆங்கிலம் அல்லாத பயனர்கள் நம்பிக்கையுடன் வார்த்தைகள், இப்போது தவறான நகலைப் படிக்கிறார்கள்.

இது உண்மையாக அனுப்பப்பட்டது. ஆண்டிகிராவிட்டி உள்நுழைவு உதவியாளர் தரையிறங்கியபோது `oauthModal.googleOAuthWarning` மீண்டும் எழுதப்பட்டது (#5203);** 43 வட்டாரங்களில் 39** "முழு URL ஐ நகலெடுத்து அதை கீழே ஒட்டவும்" என்று ஆபரேட்டர்களுக்கு உரை கூறும் — அந்த வழங்குநரால் முடிக்க முடியாத ஒரு ஓட்டம். இது #8463 வரை கவனிக்கப்படாமல் போனது, ஏனெனில்:

- `sync-ui-keys` மட்டும் பின் நிரப்பும் விசைகளை** இல்லாத** , ஒருபோதும் இல்லாதவை** பழமையான** ;
- `check-ui-keys-coverage` விசை _இருப்பு_ஐக் கணக்கிடுகிறது, எனவே பழைய மொழிபெயர்ப்பானது மூடப்பட்டதாக மதிப்பெண்கள் பெறுகிறது;
- `check-translation-drift` `docs/i18n/<locale>/**.md` ஆவணங்களைக் கண்காணிக்கிறது — அது `src/i18n/messages/*.json` படிக்காது. இது ஜாப் `docs-sync-strict` இல் இயங்குகிறது: PRs இல் ஆலோசனை, மிகுதி மற்றும் இரவு நேரங்களில் கண்டிப்பானது; மொழிபெயர்ப்பு அலை கண்ணாடிகளை புதுப்பிக்கிறது, அம்சம் PR அல்ல.

**வித்தியாசம் தெரியும், அடிப்படை ஆதரவு இல்லை.** இது வேலை செய்யும் மரத்திற்கு எதிராக ஒன்றிணைக்கும் தளத்தில் `en.json` ஒப்பிடுகிறது; ஆங்கில மதிப்பு மாறிய ஒவ்வொரு விசைக்கும், தொடப்படாத மொழிபெயர்ப்பை வைத்திருக்கும் எந்த மொழியும் பழையதாக இருக்கும். இது வேண்டுமென்றே** ஏற்கனவே இருந்த கடனை முடக்குகிறது** — ஒரு வித்தியாசம் எந்த பழைய ஆங்கிலத்திலிருந்து நீண்ட கால மொழிபெயர்ப்பு வந்தது என்பதை வெளிப்படுத்த முடியாது, எனவே தற்போதைய மாற்றம் என்ன தொடுகிறது என்பதை மட்டுமே கேட் தீர்மானிக்கிறது. மாற்றீடு (ஒவ்வொரு முக்கிய ஹாஷ் பேஸ்லைன்) ஒரு ~ 600 KB உருவாக்கப்பட்ட கோப்பு, 3 × தற்போதுள்ள மிகப்பெரிய பேஸ்லைன், ஒவ்வொரு i18n PR க்கும் செலவாகும்.

அதை திருப்திப்படுத்த இரண்டு வழிகள்:

1. பாதிக்கப்பட்ட மொழிபெயர்ப்புகளைப் புதுப்பிக்கவும் அல்லது
2. அவற்றை `__MISSING__:<new english>` — க்கு அமைக்கவும், இயக்க நேரம் திருத்தப்பட்ட ஆங்கிலம் (`src/i18n/request.ts::deepMergeFallback`, #7258) மற்றும் மொழிபெயர்ப்பிற்கான முக்கிய வரிசைகளை வழங்குகிறது.

சரம் என்றால்** பொருள்** மாற்றப்பட்டது, விரும்புகிறது** விசையை மறுபெயரிடுகிறது** : ஒரு புதிய விசை பழைய மொழிபெயர்ப்பைப் பெற முடியாது. அதுதான் #8463 மாதிரி பயன்படுத்தப்படுகிறது.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

அடிப்படை பட்டியலைப் படிக்க முடியாதபோது `SKIP reason=base-unresolved` உடன் 0 இலிருந்து வெளியேறுகிறது (அடிப்படை குறிப்பு இல்லாமல் ஆழமற்ற குளோன்), `check-openapi-breaking` பிரதிபலிக்கிறது. வெளியீட்டு பயன்முறை மட்டும்: ஒரு அம்சம் PR ஆங்கிலத்தை மீண்டும் எழுதி அங்கேயே நிறுத்துகிறது; வெளியீடு புதுப்பிப்பு அது விட்டுச்சென்ற மொழிபெயர்ப்புகளைக் குறிக்கிறது (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, அதே `findStaleTranslations`).

`check:complexity-ratchets` மற்றும் `check:dead-code` ஆகியவற்றுக்கு, gate HEAD-ஐ merge-base-உடன் ஒப்பிடுகிறது,
ஆனால் PR மாற்றிய கோப்புகளுக்கு மட்டும் வரையறுக்கப்படுகிறது

- **தடுக்கும்** — PR மாற்றிய கோப்புகளில் cyclomatic/cognitive violations அல்லது dead exports-ஐ PR சேர்த்திருந்தால்

`check:file-size` base ref-ஐ அதன் சொந்த விதிமுறைகளின்படி பயன்படுத்துகிறது
(`scripts/check/check-file-size.mjs`, #8522):
இது tree-இல் உள்ள ஒவ்வொரு source மற்றும் test கோப்பையும் சரிபார்க்கிறது, `git show` மூலம் PR base-இல்
ஒவ்வொரு கோப்பின் line count-ஐப் படிக்கிறது, மேலும் ஒரு கோப்பு அதன் baseline ceiling-ஐ

`git archive` export-இலிருந்து அளவிடப்படுகிறது, மேலும் அதன்
`open-sse → src` edge எண்ணிக்கை `metrics.boundaryOpenSseToSrc` மற்றும் base-இல் உள்ள எண்ணிக்கை ஆகியவற்றில்
பெரியதைக் கடக்கும்போது மட்டுமே PR தோல்வியடைகிறது. ceiling-ஐ மீறும் base drift தெரிவிக்கப்படுகிறது (`base drift herdado`),
ஆனால் அது குற்றமற்ற PR-ஐ ஒருபோதும் சிவப்பாக்காது; push → main
முழுமையான ceiling-ஐத் தொடர்ந்து பயன்படுத்துகிறது, மேலும் தீர்க்க முடியாத base SHA எச்சரிக்கையுடன் அதற்குத் திரும்புகிறது.

ஒரு omni-queue candidate (`omni-queue/**`-க்கு push, [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md)-ஐப் பார்க்கவும்)
pull request-க்கு இணையான செயல்முறையைப் பெறுகிறது: இரண்டு workflows-உம் candidate base-ஐ
(`needs.changes.outputs.candidateBase`) `--base-ref` ஆக அனுப்புகின்றன, மேலும் `check:ts7-diagnostics-ratchet` அதற்கு எதிராகவும் இயங்குகிறது.
புதிய code-க்கான இரண்டு gates-இல், ஒப்பீட்டுக்கான base அந்த SHA-யே; top merge commit-ன் முதல்
parent அல்ல. ஆகவே batch-இன் ஒவ்வொரு pull request-உம் மதிப்பிடப்படுகிறது.

`workflow_dispatch` runs, release-green sweep மற்றும் nightly headroom job ஆகியவற்றுக்கு PR base இல்லை;
அவை முழுமையான (global) ஒப்பீட்டையே தொடர்ந்து பயன்படுத்துகின்றன. Coverage, duplication மற்றும் type-coverage ஆகியவை
தற்போதைக்கு global-ஆகவே உள்ளன (அவற்றின் tools per-file diff-ஐ மலிவாக உருவாக்குவதில்லை) — இதே சிகிச்சைக்கான
candidate-கள்.

**v4.0-இல் கட்டத்தை நிறைவு செய்தல் (LTS = முன்பைவிடக் கடுமையானது, "இயல்புநிலைக்குத் திரும்புதல்" அல்ல)**

1. தூய `release/v4.0.0` tip-இல்: பதிவுக்காக `npm run quality:headroom --json`-ஐ இயக்கவும், பின்னர்
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, ஒவ்வொரு typecheck gate-இன்
   `--update` ஆகியவற்றை இயக்கவும் — ஒவ்வொரு baseline-உம் அளவிடப்பட்ட மதிப்புக்குக் குறையும்.
2. `quality-baseline.json` இலிருந்து `_policy`-ஐ நீக்கவும் (`--require-tighten` மற்றும் nightly
   banking மீண்டும் செயல்படும்), மேலும் `check-openapi-coverage.mjs`-இல் `THRESHOLD = 36` (அல்லது அதற்கு மேல்) என்பதை மீட்டமைக்கவும்.

## Ratchet அடிப்படை (`quality-baseline.json`)

Ratchet engine (`scripts/quality/check-quality-ratchet.mjs`) ஆனது `quality-baseline.json` கோப்பைப் படித்து,
புதிதாகச் சேகரிக்கப்பட்ட `quality-metrics.json` உடன் ஒப்பிடுகிறது. எந்த அளவீடும் அதன் epsilon-ஐத்
தாண்டி பின்னடைந்தால் build தோல்வியடையும்.

தற்போது கண்காணிக்கப்படும் அளவீடுகள்:

| அளவீடு                | திசை   | பொருள்                                              |
| --------------------- | ------ | --------------------------------------------------- |
| `eslintWarnings`      | `down` | ESLint எச்சரிக்கைகளின் எண்ணிக்கை அதிகரிக்கக் கூடாது |
| `coverage.statements` | `up`   | Statement coverage குறையக் கூடாது                   |
| `coverage.lines`      | `up`   | Line coverage குறையக் கூடாது                        |
| `coverage.functions`  | `up`   | Function coverage குறையக் கூடாது                    |
| `coverage.branches`   | `up`   | Branch coverage குறையக் கூடாது                      |

உண்மையான மேம்பாட்டிற்குப் பிறகு அடிப்படையைப் புதுப்பிக்க:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` flag, தற்போதைய அளவிடப்பட்ட மதிப்புகளை `quality-baseline.json`-க்குள் எழுதுகிறது.
மேம்பாட்டை பதிவு செய்வது release/nightly பணியாகும்; feature PR-க்கான பணி அல்ல: `--require-tighten`
(Fase 6A.5), release mode-ல் (push, schedule, release PR,
local runs) மட்டுமே பதிவு செய்யப்படாத மேம்பாட்டைத் தோல்வியடையச் செய்கிறது. Feature PR-ல் (`pr` gate mode)
அது மேம்பாட்டைத் தகவலாக அச்சிட்டு வெற்றியடைகிறது; regression இரு mode-களிலும் தோல்வியடையும்.
Velocity கட்டத்தில் அது எங்கும் அறிவுறுத்தல் மட்டுமே
(`_policy.requireTighten: false`). இதையும் பார்க்கவும்:
[Generated files and derived baselines](#generated-files-and-derived-baselines-written-at-release).

### CodeQL ratchet: புதுப்பிப்பு இடைவெளியும் கைமுறைத் தூண்டுதலும்

`check:codeql-ratchet` ஆனது **ஒவ்வொரு PR-க்கும் அல்ல, அட்டவணைப்படி புதுப்பிக்கப்படும் repo நிலையைப் படிக்கிறது.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ஆனது
`state: configured`, `schedule: weekly` எனக் காட்டுகிறது: இது GitHub-ன் default-setup scan,
ஒவ்வொரு push-க்குமான analysis அல்ல. இதன் விளைவு: alert-களை **சரிசெய்யும்** PR merge ஆன பிறகு,
அடுத்த scheduled scan இயங்கும் வரை ratchet பழைய, அதிகமான எண்ணிக்கையையே தொடர்ந்து படிக்கும் — எனவே
scan புதுப்பிக்கப்படும் வரை, சரிசெய்யும் PR-ன் சொந்த follow-up-கள் உட்பட, திறந்திருக்கும் ஒவ்வொரு PR-லும்
regression எனப் புகாரளிக்கும்.

**கைமுறைப் புதுப்பிப்பு**: `gh workflow run codeql.yml --ref release/vX.Y.Z` கட்டளை
analysis-ஐ மீண்டும் இயக்கி, சில நிமிடங்களுக்குள் alert-களை மீண்டும் வெளியிடும். முதலில்
`.github/workflows/codeql.yml`-ஐப் படிக்கவும் — அதன் header, இது **`workflow_dispatch`-மட்டுமே**
என்பதை விளக்குகிறது; காரணம், இது GitHub-ன் **"default setup"** உடன் முரண்படுகிறது
(`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`).
`push`/`pull_request`/`schedule` triggers-ஐ மீட்டமைக்க முதலில் **owner action** தேவை:
Settings → Code security → CodeQL: Default → Advanced. அந்த மாற்றமின்றி `schedule:` trigger-ஐச்
சேர்க்க வேண்டாம் — அது தோல்வியடைந்த runs-ஐ மட்டுமே உருவாக்கும்.

**எண்ணிக்கை குறைந்த பிறகு அடிப்படையை இறுக்கமாக்கவும்** — `node scripts/check/check-codeql-ratchet.mjs
--update` ஆனது புதிய அளவிடப்பட்ட எண்ணிக்கையை `quality-baseline.json` →
`metrics.codeqlAlerts.value`-ல் எழுதுகிறது; இதனால் ratchet பழைய ceiling வரை மீண்டும் உயர்வதை
மறைமுகமாக அனுமதிக்காது. செயல்முறை எடுத்துக்காட்டு (2026-09-02/03): PR #12502 ஆனது
7 உண்மையான alert-களைச் சரிசெய்தது (அளவிடப்பட்ட திறந்த எண்ணிக்கை 13 → 6); PR #12530 ஆனது
உறையவைக்கப்பட்ட அடிப்படையைப் பொருந்துமாறு 11 → 6 என இறுக்கியது; பின்னர் மீதமிருந்த 6 alert-களும்
ஒவ்வொன்றிற்குமான காரண விளக்கத்துடன் dismiss செய்யப்பட்டு, திறந்த எண்ணிக்கை 0 ஆகக் குறைக்கப்பட்டது.

**Dismissal-கள் operator-ன் முடிவு (Hard Rule #14)** — dismissal comment-ல் தொழில்நுட்ப
காரணத்தைப் பதிவு செய்யாமல் CodeQL alert-ஐ ஒருபோதும் dismiss செய்ய வேண்டாம்: upstream-protocol
தேவைக்காக `won't fix`, test fixture-க்காக `used in tests`, CodeQL காண முடியாத sanitizer-க்காக
`false positive` (முன்னுதாரணம்: `docs/security/ERROR_SANITIZATION.md`).

| வழங்குவது    | release branch-க்கு எதிராக எப்போதும் தற்போதைய நிலையில் இருக்கும் ஒரே ஒரு PR — force-update செய்யப்படும்; ஒருபோதும் spam செய்யப்படாது |

ஒவ்வொரு push-க்கும் பதிலாக banking தொகுதியாகச் செய்யப்படுகிறது; ஏனெனில் அதற்கு latency தேவை இல்லை (8 மணிநேரத்திற்குள்
bank செய்யப்படும் குறைப்பு போதுமானது), ஆனால் ஒவ்வொரு merge-க்கும் இயக்குவது merge campaign-களின்போது PR branch-ஐ மீண்டும் மீண்டும்
உருவாக்குவதோடு, ஒவ்வொரு முறையும் முழுமையான ESLint ஆய்வுக்கான செலவையும் ஏற்படுத்தும். கண்டறிதல் தொடர்ந்து
push-இல் (`release-green`) நடைபெறும்; banking மட்டும் தொகுதியாகச் செய்யப்படுகிறது.

### பாதுகாப்புச் சரிபார்ப்பான்

இந்த job மனிதக் கண்காணிப்பின்றி baseline-களில் எழுதுகிறது; எனவே அதை ஏற்றுக்கொள்ளத்தக்கதாக ஆக்குவது `verify-ratchet-bank.mjs` ஆகும்.
இது `--update`-க்குப் பிந்தைய tree-ஐ `HEAD` உடன் diff செய்து, ஒவ்வொரு மாற்றமும் கீழ்க்கண்டவற்றில் ஒன்றாக இல்லாவிட்டால்,
**எந்த commit-உம் உருவாகும் முன்பே job-ஐ நிறுத்திவிடும்** — எந்த PR-உம் திறக்கப்படாது:

- ஒரு `frozen` / `testFrozen` எண் பதிவு **குறைக்கப்பட்டது** அல்லது **அகற்றப்பட்டது**
- `complexity-baseline.json` → `count` **குறைக்கப்பட்டது**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **குறைக்கப்பட்டது**

வேறு எதுவும் தோல்வியடையும்: எண்ணை உயர்த்துவது, பதிவைச் சேர்ப்பது, `cap`/`testCap`-ஐ மாற்றுவது, அல்லது
`_rebaseline_*` குறிப்பை நீக்குவது/மீண்டும் எழுதுவது (ஒவ்வொரு உச்சவரம்பும் ஏன் உள்ளது என்பதற்கான audit trail அந்தக் குறிப்புகளாகும்;
அவை கோப்புப் பதிவுகள் இருக்கும் அதே `frozen` object-இன் உள்ளே சேமிக்கப்படுகின்றன).
ஒரு cap-ஐ உயர்த்தக்கூடிய bot தற்போதைய நிலையைவிட முற்றிலும் மோசமானதாக இருக்கும். பின்னடைவு
guard: `tests/unit/verify-ratchet-bank.test.ts`.

இந்த job ஒருபோதும் `release/*`-க்கு push செய்யாது — ஒரு மனிதர் PR-ஐ merge செய்வார்; எனவே தவறான அளவீடு
மதிப்பாய்வு இல்லாமல் சேர்க்கப்பட முடியாது.

## அனுமதிப்பட்டியல் கொள்கை

முன்பே இருந்த மீறல்களால் தோல்வியடைய முடியாத ஒவ்வொரு கேட்டும் உறைந்த அனுமதிப்பட்டியலைப் பயன்படுத்துகிறது
(எ.கா., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). கொள்கை:

**மூலக் காரணத்தைச் சரிசெய்யுங்கள்; மீறல் ஏற்கனவே இருந்து, அதே PR-ல் அதைச்
சரிசெய்ய முடியாதபோது மட்டுமே அனுமதிப்பட்டியலைப் பயன்படுத்துங்கள்.**

அனுமதிப்பட்டியலில் ஒரு பதிவைச் சேர்க்கும்போது:

1. காரண விளக்கத்துடன் ஒரு கருத்தைச் சேர்க்கவும்.
2. கண்காணிப்பு issue-ஐக் குறிப்பிடவும் (எ.கா., `// #3498 — Phase 2 feature, not yet implemented`).
3. மீறலைச் சரிசெய்யும் அதே PR-ல் பதிவை அகற்றவும் — செயலில் உள்ள மீறலை இனி
   அடக்காத பழைய பதிவு, தானே ஒரு குறைபாடாகும் (செயல்படுத்தப்பட்டதும், 6A.3 பழைய-பதிவு
   அமலாக்கம், தொடர்பற்ற அனுமதிப்பட்டியல் பதிவில் கேட்டில் தோல்வியடையும்).

சோதனைகள் விரைவாக வெற்றி பெறச் செய்வதற்காக அனுமதிப்பட்டியல் பதிவுகளைச்
சேர்க்க வேண்டாம். வளர்ந்து கொண்டிருக்கும் அனுமதிப்பட்டியலுடன் பச்சை நிற கேட்,
தரத்தைப் பற்றிய தவறான நம்பிக்கையை உருவாக்குகிறது.

### உங்கள் PR-ல் ஒரு கேட் தோல்வியடையும்போது

1. **கேட் வெளியீட்டை கவனமாகப் படியுங்கள்** — எந்தக் கோப்பு அல்லது குறியீட்டு
   அடையாளங்காட்டி விதியை மீறியது என்பதை அது துல்லியமாகக் கூறுகிறது.
2. **மீறலைச் சரிசெய்யுங்கள்** — பெரும்பாலான கேட்டுகள், குறியீடு சரியானவுடன்
   வெற்றி பெறும் நிர்ணயிக்கப்பட்ட கோப்பு முறைமைச் சரிபார்ப்புகளாகும்.
3. **மீறல் முன்பே இருந்ததாக இருந்தால்** (அதாவது, அதை நீங்கள் அறிமுகப்படுத்தவில்லை,
   ஆனால் கேட் இப்போது அதைக் கண்காணிக்கிறது): காரண விளக்கக் கருத்துடனும்
   கண்காணிப்பு issue-உடனும் ஒரு அனுமதிப்பட்டியல் பதிவைச் சேர்க்கவும்.
4. **கேட் ஒரு ratchet ஆக இருந்தால்** (coverage, ESLint எச்சரிக்கைகள்,
   duplication, complexity): உங்கள் மாற்றம் அளவீட்டை மோசமாக்கியுள்ளது. அடிப்படைச்
   சிக்கலைச் சரிசெய்யவும் அல்லது (அரிதாக) மாற்றம் நோக்கமுடையதாகவும், அளவீட்டின்
   சரிவு ஏற்றுக்கொள்ளத்தக்கதாகவும் இருந்தால் `npm run quality:ratchet -- --update`
   இயக்கவும் — ஆனால் ஏன் என்று PR விளக்கத்தில் பதிவு செய்யவும்.
5. **ஆலோசனை கேட்டுகள்** (`continue-on-error: true`) தகவல் வழங்குவதற்கானவை —
   அவை merge-ஐத் தடுக்காது, ஆனால் CI சுருக்கத்தில் தோன்றும். இருந்தாலும் அவற்றைச்
   சரிசெய்யவும்.

## புதிய வாயிலைச் சேர்த்தல்

1. `scripts/check/check-<name>.mjs` (அல்லது `.ts`) உருவாக்கவும். கொள்கை வாயில்கள் 0/1 வெளியேறும் குறியீட்டுடன் முடிவடையும்.
   Ratchet-பாணி வாயில்கள் `collect-metrics.mjs` வழியாக `quality-metrics.json`-க்கு ஓர் அளவீட்டை வெளியிடும்.
2. `package.json`-இல் `"check:<name>": "node scripts/check/check-<name>.mjs"`-ஐச் சேர்க்கவும்.
3. பொருத்தமான பணியின் கீழ் `.github/workflows/ci.yml`-இல் அதை இணைக்கவும்
   (கொள்கை → `lint` அல்லது `docs-sync-strict`; ratchet → `quality-gate`).
4. அதற்கு அனுமதிப்பட்டியல் இருந்தால், காலாவதியான உள்ளீடுகள் தானாகக் கண்டறியப்படுவதற்காக
   `scripts/check/lib/allowlist.mjs`-இலிருந்து `reportStaleEntries()`-ஐப் பயன்படுத்தவும்.
5. வாயிலின் கண்டறிதல் தர்க்கத்தை உள்ளடக்கும் சோதனையை `tests/unit/build/`-இல் எழுதவும்.
6. இந்த ஆவணத்தைப் புதுப்பிக்கவும் (தொடர்புடைய பணியின் அட்டவணையில் ஒரு வரியைச் சேர்க்கவும்).

`.mcp.json`-ஐ உருவாக்கவும்; இதனால் அவர்கள் குறியீட்டை எழுதுவதற்கு **முன்பே** குறியீடுகள் /
கண்டறிதல்களைத் தீர்மானிப்பார்கள் — மூலத்திலேயே "கற்பனையான குறியீடு" பிழைகளைக் குறைக்கும்

தானாக ஏற்றப்படுவதில்லை (MCP↔LSP பாலத்தை நீங்கள் தேர்ந்தெடுத்துச் சரிபார்க்க வேண்டும்); பழுதான உள்ளீடு ஓர்
இணைப்புப் பிழையை மட்டுமே பதிவு செய்யும், அமர்வுகளை ஒருபோதும் பாதிக்காது.

## பகுத்தறிதல் நிலுவைப் பட்டியல் (ROI மதிப்பாய்வு — கட்டம் 9 அலை 3)

இந்தப் பட்டியல் 2026-06-17 அன்று `ci.yml`-க்கு எதிராகச் சரிபார்க்கப்பட்டது (முந்தைய பதிப்பில்
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,
`check:codeql-ratchet`, `check:pr-evidence` ஆகியவை விடுபட்டிருந்தன). சரிபார்க்கப்பட்ட தொகுப்பின்
ROI மதிப்பாய்வு பின்வரும் பகுத்தறிதல் வேட்பாளர்களை அடையாளம் கண்டது. **Merge-கள் இயந்திரமயமான CI
மாற்றங்கள்; flip/drop-கள் இயக்குநருக்காக ஒதுக்கப்பட்ட கொள்கை முடிவுகள்.** கீழே உள்ள எதுவும்
இன்னும் பயன்படுத்தப்படவில்லை.

**மேலும் மேலே ஆவணப்படுத்தப்படாதவை** (ஆலோசனைக்குரியவை, குறைந்த சமிக்ஞை): `docs-lint` job
(markdownlint + Vale, முழு job-க்கும் `continue-on-error`) மற்றும் தனித்த scanner workflows
`semgrep.yml` / `codeql.yml` / `scorecard.yml`. `semgrepFindings: 0` என்பது
`quality-baseline.json`-ல் உள்ளது, ஆனால் `ci.yml`-ல் blocking ratchet-க்கு இணைக்கப்படவில்லை —
இந்த metric தற்போது orphaned நிலையில் உள்ளது.

### Merge / dedup (இயந்திரமயம், குறைந்த ஆபத்து)

ஒவ்வொரு வேட்பாளரும் 2026-06-17 அன்று செயல்பாட்டிலுள்ள gate நிலைக்கு எதிராகச் சரிபார்க்கப்பட்டார் (நம்புங்கள், ஆனால் சரிபார்க்கவும்);
பல "வெளிப்படையான" merge-கள் கடனை மறைத்திருப்பது தெரியவந்ததால், அவை **தயார்நிலை drop-in மாற்றுகள் அல்ல**.

- **`check:docs-sync` இரண்டு முறை இயங்குகிறது** — `lint` job-ல் standalone ஆகவும், மீண்டும் `check:docs-all` (`docs-sync-strict`) மற்றும் husky pre-commit hook-க்குள்ளும். ✅ **முடிந்தது** — standalone `lint` invocation அகற்றப்பட்டது.
- **CVE scanning** — ❌ **சுத்தமான merge அல்ல.** `audit:deps` அனைத்து ஐந்து lockfile-களிலும் critical advisories மற்றும் முழுமையற்ற audits-ஐத் தடுக்கிறது; தற்போதைய கொள்கையின் கீழ் high advisories-ஐ warnings ஆக அறிக்கையிடுகிறது; `check:vuln-ratchet` (osv) சரிபார்க்கப்பட்ட baseline-க்கு எதிரான _regression_ ஏற்பட்டால் மட்டுமே தோல்வியடைகிறது, மேலும் தேவைப்படும் போது missing measurements-ஐ நிராகரிக்கிறது. Semantics வேறுபட்டவை — `audit:deps`-ஐ அகற்றினால் absolute critical gate மற்றும் சுயாதீன package audit receipts இழக்கப்படும். இரண்டையும் வைத்திருக்கவும்.
- **Cycle detection** — ✅ **முடிந்தது** (#15159 G-01/G-02). இங்குள்ள பழைய உரை `check:cycles`-ஐ "green, curated" gate எனக் குறிப்பிட்டு, `check:circular-deps` (dpdm) 91 cycles-ஐ அறிக்கையிட்டதால் அதை blocking நிலையில் வைத்திருக்க வேண்டும் என நியாயப்படுத்தியது. அந்த green ஒரு **false green**: `check:cycles` 5 subdirectories-ஐ (450 files) scan செய்து, static `import|export … from`-ஐ மட்டுமே match செய்தது; ஒவ்வொரு `@/` மற்றும் `@omniroute/open-sse/` specifier-ஐயும் நீக்கியதால், repository-யில் பெரும்பான்மையாக இருந்த dynamic-import + alias cycles-ஐக் காண முடியவில்லை. சரிசெய்யப்பட்டது: gate இப்போது `src` + `open-sse` (5023 files) வழியாகச் சென்று, TypeScript AST-இலிருந்து specifier-களைச் சேகரிக்கிறது (`import("…")` கணக்கில் எடுத்துக்கொள்ளப்படும், type-position `typeof import("…")` கணக்கில் எடுத்துக்கொள்ளப்படாது), மேலும் tsconfig `paths`-ஐ resolve செய்கிறது. இது 0 அல்ல, **14** cycles-ஐக் கண்டறிகிறது. ஏற்கனவே உள்ள 14 cycles-ஐ gate PR-ல் சரிசெய்ய முடியாததால், `check:cycles` இப்போது ஒரு **ratchet** (`--ratchet`, `quality-baseline.json`-ல் ceiling `metrics.cycles.value = 14`, `direction: down`) ஆகும் — இது _regression_-ஐத் தடுக்கிறது, மேலும் எண்ணிக்கை குறைய மட்டுமே முடியும். CI `npm run check:cycles:ratchet`-ஐ இயக்குகிறது. Burn-down **A-01** உடன் நடைபெறும். `check:circular-deps` (dpdm) விரிவான இரண்டாவது கருத்தாக advisory நிலையில் தொடர்கிறது.
- **Complexity** — ✅ **முடிந்தது** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ஒரு ESLint walk, ruleId அடிப்படையில் எண்ணுகிறது; இதனால் cyclomatic மற்றும் max-lines baselines சுயாதீனமாக இருக்கும்; தனித்த `check:complexity` / `check:cognitive-complexity` local `--update`-க்காகத் தொடர்கின்றன.
- **`/api` anti-hallucination** — ✅ **முடிந்தது** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api`-ன் ஒரு FS inventory; openapi-routes + docs-symbols ஆகியவை இன்னும் சுயாதீனமாக அறிக்கையிடுகின்றன; தனித்தவை local runs-க்காகத் தொடர்கின்றன.
- **`check:node-runtime` 11 jobs-ல் இயங்குகிறது** — ⚠️ **குறைந்த ROI.** ஒவ்வொன்றும் தனித்த runner ஆகும், check <1s; ஒவ்வொரு job-க்குமான மலிவான guard-ஐ இழப்பதற்கு எதிராக மொத்தச் சேமிப்பு ~10s மட்டுமே. இந்த churn மதிப்புக்குரியது அல்ல.
- **CI lint-ல் `typecheck:noimplicit:core`** — ✅ **lint job-லிருந்து அகற்றப்பட்டது** (advisory `continue-on-error` ஆக இருந்தது); blocking type surface என்பது `typecheck:core` + `check:type-coverage`; local script தக்கவைக்கப்பட்டது.

### Flip / decide (இயக்குநர் கொள்கை)

- `check:openapi-security-tiers` (advisory) — ❌ **சுத்தமாக flippable அல்ல.** `LOCAL_ONLY_API_PREFIXES`-ன் கீழுள்ள பல `traffic-inspector` routes-ல் `x-loopback-only: true` annotation இல்லை என இது exit 0 ஆனாலும் warning அளிக்கிறது. இதை enforce செய்ய முதலில் `openapi.yaml`-ல் அந்த annotations சேர்க்கப்பட வேண்டும்.
- `typecheck:noimplicit:core` (advisory) — blocking `check:type-coverage` ratchet-ஆல் பெரும்பாலும் subsume செய்யப்பட்டுள்ளது. இதை ratchet ஆக flip செய்யவும் அல்லது redundant இரண்டாவது `tsc` pass-ஐ அகற்றவும்.
- `test:vitest:ui` (இப்போது **blocking**) — ஏற்கனவே இருந்த failures `vitest.config.ts`-ல் `// #8618` tracking comments மூலம் வெளிப்படையாக exclude செய்யப்பட்டுள்ளன; புதிய failures job-ஐ fail செய்யும்.
- `check:secrets` (gitleaks, 3 documented false-positives-ல் blocking ratchet frozen) — 0-ஐ அடைய அந்த 3-ஐ allowlist செய்யவும் அல்லது advisory ஆக demote செய்யவும். GitHub native secret-scanning + `check:public-creds` உடன் overlap உள்ளது.
- `check:pr-evidence` (blocking, PR-body prose-ஐ greps செய்கிறது) — false-positive ஆபத்து அதிகம்; இதை drop செய்தால் Hard Rule #18 enforcement பலவீனமடையும், எனவே இது உண்மையான policy call.
- `semgrep` (advisory standalone) — OWASP families-க்கு CodeQL உடன் overlap உள்ளது; அதன் baseline-ஐ ratchet-க்கு wire செய்யவும் அல்லது drop செய்யவும்.

#### `check-key-completeness` — key-set parity gate

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, job `i18n-ui-coverage`).
ஒவ்வொரு `src/i18n/messages/<locale>.json` கோப்பின் leaf key தொகுப்பையும் `en.json` உடன் ஒப்பிட்டு, key எப்போது சேர்க்கப்பட்டது என்பதைப் பொருட்படுத்தாமல், ஏதேனும் விடுபட்ட அல்லது கூடுதல் leaf இருந்தால் தோல்வியடையும். `__MISSING__:` placeholders இருந்ததாகக் கணக்கிடப்படும் (அவற்றின் உள்ளடக்கம் ratio gate-இன் பொறுப்பு). இது இரண்டு diff-அடிப்படையிலான/சதவீத gates-க்கு முழுமையான எதிர்மறைச் சரிபார்ப்பாகும்: `check-ui-keys-coverage` ஒவ்வொரு locale-க்கும் 80 % குறைந்தபட்ச அளவை அமல்படுத்துகிறது (சுமார் 13,000-இல் 43 key-கள் விடுபட்டிருந்தாலும் 99.7 % ஆகவே படிக்கப்படும்), மேலும் `check-new-key-coverage` PR `en.json`-இல் சேர்க்கும் key-களை மட்டுமே மதிப்பிடுகிறது. ஒரு locale batch, அதன் branch வெட்டப்பட்ட நாளின் `en.json`-இலிருந்து உருவாக்கப்பட்டு, base தொடர்ந்து key-களைச் சேர்த்துக்கொண்டிருக்கும்போது பல நாட்கள் மொழிபெயர்க்கப்படுகிறது; batch PR தானாக எந்த key-யையும் சேர்க்காது, ஆகவே batch 1 (#13044) ஒன்பது locale-களில் 43 key-கள் குறைவாகவும், batch 2 (#13660) எட்டு locale-களில் 10 key-கள் குறைவாகவும் வந்தபோது (2026-09-15), இரு sibling-களும் அமைதியாகவே இருந்தன. சிவப்பு status-ஐ `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers` மூலம் சரிசெய்யவும்; `extra` leaf என்பது source அதைக் கைவிட்டுவிட்டது என்பதைக் குறிக்கும் — `sync-ui-keys` அதை நீக்குகிறது (`--prune-extra`, இயல்புநிலை). `--warn` தோல்வியடையாமல் அறிக்கை அளிக்கும்.
`--catalog=cli` என்பது `bin/cli/locales` மீது அதே ஒப்பீட்டை இயக்குகிறது (`npm run i18n:check-keys:cli`); இரண்டு படிகளும் `i18n-ui-coverage` job-இல் உள்ளன. இந்த முழுமையான சரிபார்ப்பு release mode-இல் மட்டுமே இயங்கும்: feature PR `SKIP reason=pr-mode`-ஐக் காணும், மேலும் fix release refresh அல்லது translation wave-இல் இயங்கும், feature PR-இல் அல்ல; locale catalogs-ஐ மாற்றும் PR-இல், அவை ஒவ்வொன்றும் merge base-க்கு எதிராக மதிப்பிடப்படும் (`i18n-ui-coverage` job-இன் “இரண்டு முறைகள்” பகுதியைப் பார்க்கவும்).

#### `check-new-key-coverage` — new-key i18n gate

`check-ui-value-drift`-இன் sibling. அது மொழிபெயர்ப்புகள் மாற்றப்படாமல் விடப்பட்டபோது, ஆங்கில value **மறுஎழுதப்பட்டதை** கண்டறியும்; இது சில locale-களுக்கு ஒருபோதும் வழங்கப்படாத நிலையில் ஆங்கில key **சேர்க்கப்பட்டதைக்** கண்டறியும்.

`check-ui-keys-coverage` இந்த வகையைப் பார்க்க முடியாது: அது ஒவ்வொரு locale-க்கும் ஒரு சதவீதக் குறைந்தபட்ச அளவை அமல்படுத்துகிறது, மேலும் சுமார் 13,000 leaf-களில் பதினொன்று key-கள் விடுபட்டிருந்தாலும் coverage 99.9% ஆக இருக்கும். ஒரு மொழிக்கான சதவீதம், “இந்த feature மொழிபெயர்க்கப்படாமல் வெளியிடப்பட்டது” என்பதை வெளிப்படுத்த முடியாது — முழு feature ஒன்றும் உரையில்லாமல் புதிய locale-இல் சேர்ந்து, அந்த எண்ணிக்கையை ஒருபோதும் மாற்றாமல் இருக்கலாம்.

இது பதிவுசெய்யும் சம்பவம்: Orchestration Canvas-இன் Phase 3, அப்போது இருந்த 42 locale-களிலும் அதன் பதினொன்று key-களை மொழிபெயர்த்தது. சில மணி நேரங்களுக்குப் பிறகு EU-language batch (#13044) repo-வை 51 locale-களாக உயர்த்தியது, மேலும் புதிதாக வந்த ஒன்பது (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) locale-களுக்கு அவை ஒருபோதும் கிடைக்கவில்லை. `deepMergeFallback`, விடுபட்ட key-க்கு ஆங்கிலத்தை மாற்றாகப் பயன்படுத்துகிறது; ஆகவே தோல்வி நிலை வெற்று UI அல்ல, மொழிபெயர்க்கப்படாத UI — உண்மையானதும், வடிவமைப்பிலேயே அமைதியானதுமாக இருந்தது.

அதன் sibling போலவே இது **diff-aware** ஆகும்; merge base-இல் உள்ள ஆங்கிலத்தை working tree-க்கு எதிராக ஒப்பிடுவதால், முன்பிருந்த gaps அப்படியே நிலைத்திருக்கும், மேலும் gate-ஐ இயக்க migration எதுவும் தேவையில்லை.

**`__MISSING__:<english>` marker இதை நிறைவு செய்யாது (2026-09-17 முதல்).** இது முன்பு ஆவணப்படுத்தப்பட்ட ஒத்திவைப்பாக இருந்தது — runtime சரியான ஆங்கிலத்தை fallback செய்கிறது — ஆனால் 2026-09-16 அன்று எட்டு feature PR-கள் 61 key-களைச் சேர்த்து, மொழிபெயர்ப்பதற்குப் பதிலாக அனைத்து 65 locale-களிலும் marker-ஐப் பதித்தன: இந்த gate ஒவ்வொன்றையும் ஏற்றுக்கொண்டது, PR-களை எதுவும் தடுக்கவில்லை, பின்னர் blocking real-translation ratio gate release tip-இல் அனைவருக்கும் தோல்வியடைந்தது (pt-BR 3.2 % > 2.5 % + 0.5). இப்போது marker, விடுபட்ட மொழிபெயர்ப்பாக மதிப்பிடப்படுகிறது. 2026-11-13 முதல் release mode-இல் மட்டுமே: feature PR `SKIP reason=pr-mode`-ஐக் காணும், மேலும் release PR-இல் (`BASE_REF=origin/main`) cycle சேர்த்த ஒவ்வொரு key-ஐயும் gate மதிப்பிடும். release refresh அல்லது translation wave-இல் `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40` மூலம் சிவப்பு status-ஐ சரிசெய்யவும், அல்லது `npm run i18n:translate-new-keys` (`scripts/i18n/translate-new-keys.sh`, detached-safe, `OMNIROUTE_TRANSLATION_*` env இல்லாமல் தொடங்க மறுக்கும்) மூலம் அனைத்து locale-களிலும் இணையாகச் சரிசெய்யவும். ஆங்கிலத்திலேயே இருக்க வேண்டிய key (pinned product/engine/flag name) `scripts/i18n/untranslatable-keys.json`-இல் சேர வேண்டும்; ஒருபோதும் marker-க்கு பின்னால் இருக்கக்கூடாது. `vi`, marker-களை முற்றிலுமாகத் தடை செய்கிறது (`tests/unit/i18n-vi-completeness.test.ts`).

#### `check-vitest-exclusions` — parked-test gate

`vitest.config.ts`-இன் `exclude` பட்டியலில் உள்ள கோப்பு இயங்காத test ஆகும், மேலும் tree-ஐப் படிப்பவர்களுக்கு அது coverage போலத் தோன்றும். `// #8618 — pre-existing failure; remove this exclusion when fixed` என்ற comment-க்குப் பின்னால் அறுபத்திரண்டு கோப்புகள் சேர்ந்து கொண்டன. #8618 issue, 2026-08-11 அன்று மூடப்பட்டது; ஆனால் அது கண்காணித்த பட்டியல் 45 entries-இலிருந்து 62 ஆக வளர்ந்தது, புதிதாக வந்த ஒவ்வொன்றும் முடக்கப்பட்ட issue-ஐச் சுட்டும் comment-ஐப் பெற்றது. பட்டியல் இறுதியாக file-by-file அளவிடப்பட்டபோது (#13204), **62-இல் 51, source மாற்றமின்றி தற்போதைய tree-க்கு எதிராக வெற்றி பெற்றன**.

உண்மையான file-க்கு resolve ஆகும் ஒவ்வொரு exclusion-மும் (a) tracking issue ஒன்றைக் குறிப்பிட வேண்டும், மேலும் (b) அளவிடப்பட்ட status-உடன் `config/quality/vitest-exclusions.json`-இல் தோன்ற வேண்டும் என்று gate வலியுறுத்துகிறது; இதனால் ஒன்றைச் சேர்ப்பது 60-entry array-இல் இன்னொரு வரியாக இல்லாமல், தனிப்பட்ட கோப்பில் review செய்யக்கூடிய diff ஆகிறது. excluded tests-ஐ இது நோக்கமுடன் மீண்டும் இயக்காது — அதற்கு சுமார் 10 நிமிடங்கள் ஆகும், மேலும் அது periodic job-க்குச் சேரும்; inventory, ஒவ்வொன்றும் கடைசியாக எப்போது அளவிடப்பட்டது என்பதைப் பதிவு செய்கிறது.
