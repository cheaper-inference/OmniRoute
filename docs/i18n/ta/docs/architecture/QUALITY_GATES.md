இந்த ஆவணம் OmniRoute-இல் உள்ள அனைத்து CI தர வாயில்களுக்குமான அதிகாரப்பூர்வ மேற்கோளாகும்.
ஒவ்வொரு வாயிலையும், அது எதைச் சரிபார்க்கிறது, எந்த CI job-இல் இயங்குகிறது, அது
ratchet baseline அல்லது pass/fail கொள்கையைப் பயன்படுத்துகிறதா, மேலும் அது build-ஐத் தடுக்கிறதா அல்லது ஆலோசனை சார்ந்ததா என்பதை விவரிக்கிறது.

சுருக்கமான தொகுப்புக்கும் allowlist கொள்கைக்கும், `AGENTS.md`-இல் உள்ள
"தர வாயில்கள் & Ratchet-கள்" பகுதியைப் பார்க்கவும். அதே அமைப்பின் முக்கியமான மதிப்பீடு,
முதிர்ச்சி வகைப்பாடு மற்றும் கருவி-சார்பற்ற மறுஉருவாக்கத் திட்டத்திற்கு,
[தர வாயில் செயல்திட்டம்](../ops/QUALITY_GATE_PLAYBOOK.md)-ஐப் பார்க்கவும்.

## கேட் சரக்கு மற்றும் செயல்படுத்தல் சுயவிவரங்கள்

### வேட்பாளர் சேர்க்கை

CI மற்றும் குவாலிட்டி கேட்ஸ் பணிப்பாய்வுகள் ஒவ்வொன்றும் நிலையான தீர்ப்பை வெளியிடுகின்றன: `Gate / CI` மற்றும் `Gate / Quality`. அவர்களின் பதிப்புச் சேர்க்கைக் கொள்கையானது ஒவ்வொரு அப்ஸ்ட்ரீம் வேலையையும் தேவை அல்லது ஆலோசனையின்படி கணக்கிடுகிறது. பொருந்தக்கூடிய தேவையான வேலை வெற்றியடைய வேண்டும்: விடுபட்ட, ரத்துசெய்யப்பட்ட, தவிர்க்கப்பட்ட, நிலுவையில் உள்ள மற்றும் அறியப்படாத முடிவுகள் PASS நிறுவ முடியாது. செல்லுபடியாகும் ஆவணம் மட்டும் அல்லது பட்டியல் மட்டும் வகைப்பாடு ஒரு குறியீட்டு பாதையை பொருந்தாததாக்கும்; ஒரு சாதாரண வரைவு PR ஏற்றுக்கொள்ளப்பட்ட வேட்பாளர் அல்ல. `hotfix` லேபிள் ஆதாரத்தை விட்டுவிடாது.

இரண்டு பணிப்பாய்வுகளும் PRs main/release கிளைகளில் உள்ளடக்கியது, `main`, கைமுறையாக அனுப்புதல் மற்றும் ஒன்றிணைக்கும்-குழு நிகழ்வுகளுக்குத் தள்ளுகிறது. புஷ், டிஸ்பாட்ச் மற்றும் மெர்ஜ்-குரூப் முழு தேர்வையும் இயக்கவும். நம்பகமான Mergify வரிசை வரைவு பொருந்தக்கூடிய `full-code`/`full-code-e2e` வேலைகளையும் இயக்குகிறது; சாதாரண PRs அவற்றைத் தவிர்க்கவும். கைமுறையாக ஒன்றிணைக்கும் முன், சரியான வேட்பாளர் மீது முழு டிஸ்பாட்சை இயக்கவும். `release/**` க்கு தள்ளப்படுவது இந்த பணிப்பாய்வுகளைத் தொடங்காது; வெளியீடு-பசுமை இணைக்கப்பட்ட தளத்தை தனித்தனியாகக் கவனிக்கிறது (`docs/ops/RUNNER_BOX.md` → ஹோஸ்ட் செய்யப்பட்ட லேன்). ஃபோர்க்ஸ் மற்றும் மெர்ஜ் குழுக்கள் வேலைகளுக்கு ஹோஸ்ட் செய்யப்பட்ட ரன்னர்களைப் பயன்படுத்துகின்றன, இல்லையெனில் சுய-ஹோஸ்ட் ரன்னர்களைத் தேர்ந்தெடுக்கின்றன; வெளியீட்டிற்கு முன் போதுமான ஹோஸ்ட் செய்யப்பட்ட திறன் சரிபார்க்கப்பட வேண்டும்.

ஒரு சாதாரண PR விரைவான தேர்வை இயக்குகிறது. சேர்க்கை கொள்கையின் `full-code` மற்றும் `full-code-e2e` பாதைகள் (E2E, ஒருங்கிணைப்பு, தொகுப்பு கலைப்பொருள், Electron புகை, Bun SQLite, சுற்றுச்சூழல் அமைப்பு மற்றும் நெறிமுறை கிளையன்ட்கள்) மெர்ஜிஃபை வரிசை வரைவில் அல்லது முழு ஓட்டத்தில் மட்டுமே இயங்கும்: `gh workflow run ci.yml --ref <branch>`.

ஒவ்வொரு JSON ரசீதும் சரிபார்க்கப்பட்ட SHA, பணிப்பாய்வு ஓட்டம் மற்றும் முயற்சி ஆகியவற்றை அடையாளம் காட்டுகிறது. CLI ஆனது checkout/event SHA பொருத்தமின்மையை நிராகரிக்கிறது. பணிப்பாய்வு சோதனைகள் கொள்கை உறுப்பினர்களை தீர்ப்பு வேலையின் `needs` பட்டியலில் இணைக்கின்றன, எனவே புதிய அல்லது அகற்றப்பட்ட பாதை அமைதியாக மறைந்துவிடாது. ரசீதுகள் அவற்றின் சொந்த பணிப்பாய்வுகளை உள்ளடக்கியது, வெளியீடு, வரிசைப்படுத்தல் அல்லது ஏற்கனவே உள்ள ஆலோசனை ஸ்கேனரின் உட்புறங்கள் அல்ல. கிளை விதிகளில் தேவைப்படும் பொருந்தக்கூடிய காசோலைகளைச் செய்வது ஒரு தனி நிர்வாக மாற்றமாகும்; அவர்களின் வேலைகளை வரையறுப்பது ஒரு கிளையைப் பாதுகாக்காது.

`API Route Typecheck` என்பது ஒரு சுயாதீனமான பணிப்பாய்வு சரிபார்ப்பு, மொத்த தீர்ப்புகள் மற்றும் உள்ளூர் முழு பார்வையாளரின் நிலையான சுயவிவரம் ஆகிய இரண்டிற்கும் வெளியே உள்ளது. சரியான வேட்பாளருக்கு அதன் முடிவை தனித்தனியாக ஆய்வு செய்யவும். `.github/workflows/api-route-typecheck.yml` PRs இல் `main` அல்லது `release/**` இல் இயங்குகிறது, கிளை குடும்பம், கைமுறையாக அனுப்புதல் மற்றும் `checks_requested` வகையின் `merge_group` நிகழ்வுகளுக்குத் தள்ளுகிறது. இதில் பாதை வடிகட்டி இல்லை. குழுக்களை ஒன்றிணைக்கவும் `merge_group.head_sha` பார்க்கவும் ; மற்ற நிகழ்வுகள் `github.sha` ஐப் பார்க்கவும். அனைத்து நிகழ்வுகளும் ஒரே API கண்டறியும் கேட் மற்றும் கேட் யூனிட் சோதனைகளைப் பயன்படுத்துகின்றன. PR அடிப்படை retargets ஒரு புதிய காசோலையை கோருகிறது; body/title திருத்தங்கள் கவனிப்பு-மட்டும் `Admission not requested / API Route Typecheck` என்ற பெயரைப் பயன்படுத்துகின்றன மற்றும் சேர்க்கை சரிபார்ப்பை மாற்ற முடியாது.

### ஏற்பு குறைப்பாளில் தக்கவைக்கப்பட்ட ஆதாரம்

`scripts/quality/validate-release-acceptance.mjs` ஒரு வழங்கப்பட்ட திட்டத்தை குறைக்கிறது மற்றும் அதன் வெளிப்பாடுகள்; திட்டமானது முழுமையான வெளியீட்டு குழாய்த்திட்டத்தை உள்ளடக்கியது என்பதை அது நிறுவவில்லை. அதன் அறிக்கைகள் `releaseAcceptance: false` வெளிப்படையாக அமைக்கின்றன, அந்த திட்டம் `VERIFIED` ஆக இருந்தாலும் கூட. `release-acceptance.yml` பணிப்பாய்வு இன்னும் நிழல் பொருத்துதல்களைப் பயன்படுத்துகிறது, உண்மையான உருவாக்கம், தொகுப்பு, துவக்க அல்லது விளம்பர ரசீதுகள் அல்ல.

தக்கவைக்கப்பட்ட ஆதாரங்களைச் சரிபார்க்க CLI க்கு `--evidence-root` தேவைப்படுகிறது. கோப்புகள் `<evidence-root>/<artifact_id>/<member>` ஆக தீர்க்கப்பட்டு SHA-256 ஆக ஹாஷ் செய்யப்படுகின்றன. ஆதாரம் இல்லாத PASS பதிவு, காணாமல் போன அல்லது மாற்றப்பட்ட கோப்பு, பாதுகாப்பற்ற பாதை அல்லது சிம்லிங்க் சரிபார்ப்பைத் தடுக்கிறது. விடுபட்ட கோப்புகள் வெற்றிகரமான பதிவுகளை காலி செய்வதற்கு சமமானவை அல்ல. தற்போதுள்ள SHA/run/attempt காசோலைகள் சுயாதீனமாக உள்ளன: பொருந்தக்கூடிய பைட்டுகள் பழைய ரசீதை மீட்டெடுக்க முடியாது. கோப்பு ஒருமைப்பாடு என்பது செயல்பாட்டின் நம்பகத்தன்மை அல்லது கலைப்பொருள் ஊக்குவிப்புக்கான ஆதாரம் அல்ல.

### சரிபார்க்கப்பட்ட CI கட்டமைப்பைDAST பயன்படுத்துகிறது

தேவையான `dast-smoke` CI வேலை `build` க்குப் பிறகு `.github/workflows/dast-smoke.yml` அழைக்கிறது. ஆதரிக்கப்படும் ஃபோர்க் PRs, வெளியீடு-இலக்கு PRs மற்றும் ஒன்றிணைக்கும் குழுக்களை உள்ளடக்கிய அதே code/draft தேர்வைப் பின்பற்றுகிறது. விடுபட்ட, தோல்வியுற்ற, ரத்துசெய்யப்பட்ட அல்லது எதிர்பாராதவிதமாக தவிர்க்கப்பட்ட DAST வேலைத் தொகுதிகள் `Gate / CI`. மீண்டும் பயன்படுத்தக்கூடிய பணிப்பாய்வுக்கு சுயாதீன PR/dispatch தூண்டுதல் இல்லை; கைமுறை சரிபார்ப்பு CI இன் அனுப்புதலைப் பயன்படுத்துகிறது, எனவே உருவாக்கம் மற்றும் நுகர்வோர் ஒரே ஓட்டத்தில் இருக்கும்.

`scripts/ci/next-build-provenance.mjs` அதன் தார் டைஜஸ்ட், repository/event/run, தயாரிப்பாளர் முயற்சி, head/base/checkout/tree, பணிப்பாய்வு அடையாளங்கள், லாக்ஃபைல், துல்லியமான நோட் version/ABI, இயங்குதளம் மற்றும் பண்ட்லர் ஆகியவற்றைக் கொண்டு முழு அடுத்த கலைப்பொருளையும் மூடுகிறது. DAST `needs.build.outputs` இலிருந்து மாறாத கலைப்பொருளான ID தேர்ந்தெடுக்கிறது, பதிவிறக்கம் டைஜஸ்ட் சரிபார்ப்பு தேவைப்படுகிறது, மேலும் `scripts/ci/unpack-ci-build.py` மூலம் அதன் இரண்டு அனுமதிக்கப்பட்ட உறுப்பினர்களைப் பிரித்தெடுப்பதற்கு முன் தயாரிப்பாளர் டைஜெஸ்டுக்கு எதிராக ZIP சுயாதீனமாக ஹாஷ் செய்கிறது. அடுத்த மரம் பிரித்தெடுக்கப்படுவதற்கு முன், மேனிஃபெஸ்ட் மற்றும் தார் காப்பகமும் சுயாதீன உற்பத்தியாளர் வெளியீடுகளுடன் பொருந்த வேண்டும். சமீபத்திய வெற்றிகரமான கிளை உருவாக்கத்தை இது ஒருபோதும் தேடாது. அதன் ID மற்றும் அனைத்து உள்ளீடுகளும் இன்னும் பொருந்தும்போது, ஒரு பகுதி மறு இயக்கம் அதே தயாரிப்பாளரின் முயற்சியை மீண்டும் பயன்படுத்தலாம்; ரசீது இரண்டு முயற்சிகளையும் பதிவு செய்கிறது.

நுகர்வோர் ஹோஸ்ட் செய்யப்பட்ட Linux ரன்னரில் படிக்க மட்டுமேயான களஞ்சிய அனுமதி மற்றும் களஞ்சிய ரகசியங்கள் இல்லாமல் இருப்பார். இது தயாரிப்பாளரின் சரியான நோட் பதிப்பை நிறுவுகிறது, பின்னர் CLI ஐ `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1` உடன் இணைக்கிறது. எந்தவொரு பின்னடைவு உருவாக்கத்திற்கும் முன், `scripts/build/standaloneInput.mjs` ஒரு விடுபட்ட முழுமையான சேவையகத்தை நிராகரிக்கிறது; சாதாரண உள்ளூர் CLI உருவாக்கங்கள் அவற்றின் தற்போதைய வீழ்ச்சியைத் தக்கவைத்துக்கொள்கின்றன. சேவையகத் தயார்நிலை, திட்டம் மற்றும் ப்ராம்ப்ட்ஃபூ அனைத்தும் மாறாத 25 நிமிட வேலை வரம்பிற்குள் வெற்றிபெற வேண்டும். ஆதார ரசீது உள்ளீட்டு அடையாளத்தையும் பைட்டுகளையும் நிரூபிக்கிறது, வெற்றிகரமான DAST ஸ்கேன் அல்ல. கலைப்பொருள் காலாவதி, ரன்னர் குறுக்கீடு அல்லது தோல்வியுற்ற ஸ்கேனர் முழுமையடையாத அல்லது தோல்வியுற்ற ஆதாரமாக உள்ளது; அது ஒரு ஆலோசனை ரேப்பர் மூலம் PASS ஆக முடியாது.

### UI செயல்படுத்தும் திறன்

CI முழு UI சரக்குகளை நான்கு `test-vitest` மேட்ரிக்ஸ் ஷார்டுகளாக இயக்குகிறது, ஒவ்வொன்றும் ஒரு ஷார்டில் அதிகபட்சம் இரண்டு தொழிலாளர்கள் மற்றும் தற்போதுள்ள 15 நிமிட வேலை காலக்கெடு. முதல் ஷார்ட் MCP/autoCombo Vitest தொகுப்பையும் இயக்குகிறது. தேவையான வேலை முடிவு ஒவ்வொரு மேட்ரிக்ஸ் கால்களையும் உள்ளடக்கியது; ஒரு துண்டு தோல்வி அல்லது ரத்து வேட்பாளர் சேர்க்கை நிறுவ முடியாது.

முதல் ரசீதில் MCP செயல்படுத்தல் உட்பட, ஒவ்வொரு UI ஷார்டுக்கும் தனித்தனியான துல்லியமான-வேட்பாளர் ரசீதை இரவு பார்வையாளர் வைத்திருக்கிறார். நான்கு ரசீதுகள், பதிவுகள் மற்றும் பொருந்தும் செயல்படுத்தல் அடையாளங்கள் தேவை. உள்ளூர் `npm run test:vitest:ui` இன்னும் முழுமையான தொகுப்பைத் தேர்ந்தெடுக்கிறது; ஒரு `--shard` ரன் பகுதி ஆதாரம் மட்டுமே.

### அலகு கவரேஜ் சேகரிப்பு

பன்னிரண்டு யூனிட் ஷார்ட்கள், அவற்றின் தற்போதைய சோதனைச் செயல்பாட்டின் போது V8 கவரேஜை சேகரிக்கின்றன. ஒரு வெற்றிகரமான ஷார்ட் ஒரு இடைநிலை இஸ்தான்புல் அறிக்கையை உருவாக்காமல் அசல் கோப்புகளை சுருக்க `scripts/ci/compact-v8-coverage.mjs` இயக்குகிறது. இறுதி கவரேஜ் வேலையானது, வேட்பாளர் SHA, இயக்க நேரம், மூல ரூட் மற்றும் தரவு ஹாஷ்களுக்கு எதிரான அனைத்து பன்னிரெண்டு வெளிப்பாடுகளையும் சரிபார்க்கிறது, பின்னர் c8 இன் நிருபர்கள் மற்றும் ஏற்கனவே உள்ள கவரேஜ் வரம்புகளை இயக்குகிறது. உள்ளீடுகள் c8 இன் உலகளாவிய கோப்பு பெயர் வரிசையைத் தக்கவைத்துக்கொள்கின்றன; கலப்பு function/block கவரேஜுக்கு ஒரு-துண்டு முன்-இணைத்தல் பாதுகாப்பற்றது. விடுபட்ட, தவறான அல்லது இணக்கமற்ற துண்டுகள் சேர்க்கை தோல்வி. தோல்வியுற்ற சோதனைத் துண்டுகள் மூல நோயறிதல் கவரேஜைத் தனித்தனியாகத் தக்கவைத்துக்கொள்கின்றன; அது இறுதி இணைப்பில் நுழைய முடியாது.

### யூனிட் செயல்பாட்டின் முன்னேற்ற ரசீதுகள்

பகிரப்பட்ட `test:unit:ci:shard` கட்டளை `primary`, `dashboard` மற்றும் `serial` கட்டங்களை `scripts/ci/unit-progress-reporter.mjs` மூலம் பதிவு செய்கிறது. சாதாரண சோதனை அறிக்கை இன்னும் உள்ளது. தனித்தனியான மெட்டாடேட்டா-மட்டும் ரசீது ஒவ்வொரு கோப்பின் தொடக்கத்தையும் முடிவையும் பதிவுசெய்கிறது, மேலும் 30-வினாடி இதயத்துடிப்பு கோப்புகள் இன்னும் செயலில் உள்ளதையும் அவற்றின் கழிந்த நேரத்தையும் பட்டியலிடுகிறது. இது அனுமதிக்கப்பட்ட மெட்டாடேட்டாவை மட்டுமே பதிவு செய்கிறது; சோதனை விளக்கங்கள், வெளியீடு, பிழை உடல்கள் மற்றும் முழு சூழல் ஆகியவை வரிசைப்படுத்தப்படவில்லை.

CI JSONL கோப்புகளை `unit-progress-ci-<run>-<attempt>-<shard>` ஆக வைத்திருக்கிறது. வேலை நேரம் முடிவடைந்த பின் பதிவேற்றத்தைத் தடுக்கலாம்; ஏற்கனவே வெளியிடப்பட்ட இதயத் துடிப்புகள் கண்டறியும் சான்றாக இருக்கின்றன. காணாமல் போன இதயத் துடிப்புகள் தடுக்கப்பட்ட அல்லது நிறுத்தப்பட்ட ரன்னர் செயல்முறையையும் பிரதிபலிக்கும். இந்த ரசீதுகள் ஏற்கனவே உள்ள சோதனைத் தேர்வு, ஒத்திசைவு, காலக்கெடு மற்றும் வெளியேறும் நிலை ஆகியவற்றைப் பாதுகாக்கின்றன; அவை வேட்பாளர் சேர்க்கை தீர்ப்புகள் அல்ல.

### வரிசையை இணைக்கவும்

`queue` லேபிள் மெர்கிஃபை வரிசைக்கு (`.mergify.yml`) PR அனுப்புகிறது. `mergify/merge-queue/` கிளையில் PR வரைவை Mergify திறக்கிறது, CI அங்கு முழு தேர்வையும் இயக்குகிறது, மேலும் `Gate / CI`, `Gate / Quality` மற்றும் `Merge integrity (changelog + generated skills)` கடந்து செல்லும் போது அசல் PR ஒன்றிணைகிறது.

Mergify அதன் வரிசை சுருக்கத்தை வரைவின் விளக்கத்தில் எழுதுகிறது. Body/title-only `pull_request` `edited` நிகழ்வுகள் ரன்-குறிப்பிட்ட ஒத்திசைவு குழுவைப் பயன்படுத்துகின்றன, மேலும் வகைப்படுத்தல், சோதனை மெட்ரிக்குகள், ஒருமைப்பாடு அல்லது சேர்க்கை தீர்ப்பை மீண்டும் இயக்க வேண்டாம். கவனிப்பு-மட்டும் காசோலை பெயர்கள் `Gate / CI` அல்லது `Gate / Quality` மாற்ற முடியாது. இலக்கு அடிப்படையை மாற்றும் ஒரு திருத்தம் புதிய வேட்பாளர் சரிபார்ப்பைக் கோருகிறது.

ஒரு வரிசைக்குப் பிறகு, ஒரு புஷ் எப்போதும் PR ஐப் பெறாது. அதில் `@mergifyio queue` கருத்துத் தெரிவிக்கவும்.

### நிலையான ஸ்கேன் இருப்பு

பதிப்பு செய்யப்பட்ட npm-alias இன்வென்டரி மற்றும் நிலையான ஸ்கேன் உறுப்பினர் ஆகியவை `config/quality/gate-manifest.json` இல் உள்ளன. `package.json` க்கு எதிராக ஸ்கிரிப்ட் பெயர்கள் மற்றும் சரியான கட்டளைகளை சரிபார்க்க `npm run check:gate-manifest` இயக்கவும்; சேர்த்தல், நீக்குதல் மற்றும் கட்டளை சறுக்கல் ஆகியவை CI இல் உள்ள உள்ளூர் ஹூக் மற்றும் மாற்றம்-வகைப்படுத்தல் வேலைகள் இரண்டிலும் தோல்வியடைகின்றன. மாற்றுப்பெயர் என்பது பணிப்பாய்வு வேலை, மேட்ரிக்ஸ் நிகழ்வு அல்லது சோதனை வழக்கு அல்ல: இந்த எண்ணிக்கைகள் ஒன்றுக்கொன்று மாற்றத்தக்கதாக வழங்கப்படக்கூடாது.

தேர்ந்தெடுக்கப்பட்ட மாற்றுப்பெயர்களை இயக்காமல் ஆய்வு செய்ய `npm run quality:scan -- --list` அல்லது `npm run quality:scan:fast -- --list` பயன்படுத்தவும். ரன்னர் npm நுழைவுப் புள்ளியைத் தூண்டுகிறது, எனவே அதன் இயக்க நேரம் (கட்டமைக்கப்பட்ட Bun உட்பட) பாதுகாக்கப்படுகிறது. மேனிஃபெஸ்ட் ரெக்கார்டுகள் அந்த சுயவிவரங்களுக்கு வெளியே தனித்தனியாக அழைக்கப்படும் மாற்றுப்பெயர்கள், மேலும் படிக்க-மட்டும் ஸ்கேன் சுயவிவரங்களில் பராமரிப்பு கட்டளைகள் தடைசெய்யப்பட்டுள்ளன.

இந்த சுயவிவரங்கள் நிலையான ஸ்கேன் மட்டுமே உள்ளடக்கும். தயாரிப்பு சோதனைகள், கவரேஜ், பேக்கேஜிங், வெளிப்புற காசோலைகள் அல்லது வேட்பாளரின் முழு வெளியீட்டு ஏற்பு ஆகியவற்றை அவர்கள் சான்றளிக்க மாட்டார்கள். பணிப்பாய்வு சேர்க்கை இணைக்கப்பட்ட `config/quality/admission-policy.json` மற்றும் `scripts/quality/admission-verdict.mjs` ஐப் பயன்படுத்துகிறது. வெளியீடு-பார்வையாளர் சுயவிவரங்கள் தனித்தனியாக இருக்கும்; அவற்றின் பொருந்தக்கூடிய காசோலைகள் மற்றும் ரசீதுகளை சுயாதீனமாக சரிபார்க்கவும். முழு பார்வையாளரின் நிலையான கட்டளைகள் `config/quality/release-green-static-profile.json` இல் அறிவிக்கப்படுகின்றன, இதில் `audit:deps`, பிறழ்வு-சோதனை தேர்வு மற்றும் மொழிபெயர்ப்பு சோதனைகள் ஆகியவை அடங்கும். package.json மற்றும் மாதிரியான CI/Quality அறிவிப்புகளுக்கு எதிராக npm கட்டளைகளை ஏற்றி சரிபார்க்கிறது; ஷெல் டோக்கன்களை வாதங்களாக செயல்படுத்துவதற்குப் பதிலாக அது சறுக்கலை நிராகரிக்கிறது. தேவையான ஸ்கேனர் SKIP/INCOMPLETE வெளியீடு PASS நிறுவ முடியாது. சுயவிவரம் அதன் வெளிப்புற விலக்குகளைப் பதிவுசெய்கிறது மற்றும் ஹோஸ்ட் செய்யப்பட்ட கவரேஜ், சோதனை மெட்ரிக்குகள், தொகுப்பு அல்லது வரிசைப்படுத்தல் சான்றுகளை மாற்றாது. கீழே உள்ள உரைநடை பட்டியல் ஒரு குறிப்பு, ஒரு வாயில் உண்மையில் இயங்கியது என்பதற்கான ஆதாரம் அல்ல.

ஸ்கிரிப்டுகள் `scripts/check/` (பாலிசி கேட்ஸ்) மற்றும் `scripts/quality/` (ராட்செட் என்ஜின்) ஆகியவற்றின் கீழ் வாழ்கின்றன. CI உண்மையின் ஆதாரம் `.github/workflows/ci.yml` ஆகும்.

### வெளியிடப்பட்ட அடிப்படை ஆவணங்கள் ஆரோக்கியம்

`main` மற்றும் `release/v*` க்கு தேர்ந்தெடுக்கப்பட்ட அழுத்தங்களுக்குப் பிறகும், கைமுறையாக அனுப்பும்போதும்,`.github/workflows/i18n-base-health.yml` ஆவணங்களின் ஆரோக்கியத்தைக் கவனிக்கிறது. அதன் வடிப்பான்கள் ஆவணங்கள், ரூட் மார்க் டவுன், `llm.txt`, மொழிபெயர்ப்பு state/configuration மற்றும் தொடர்புடைய i18n கருவி ஆகியவற்றை உள்ளடக்கியது. ஒற்றை `Published base documentation health` வேலை ஹோஸ்ட் செய்யப்பட்ட உபுண்டு மற்றும் ஐந்து நிமிட காலக்கெடுவைப் பயன்படுத்துகிறது. இது படிக்க-மட்டும் சரிபார்ப்பைச் செய்கிறது மற்றும் சார்பு நிறுவல், மொழிபெயர்ப்பு அல்லது மாநில தத்தெடுப்பு இல்லாமல் கண்டறியும் ரசீதை எழுதுகிறது.

`scripts/i18n/check-base-health.mjs` பூஜ்ஜிய மூல-ஹாஷ், விடுபட்ட-இலக்கு, இலக்கு-ஹாஷ், பழைய-மொழிபெயர்ப்பு மற்றும் பிரிவு-கேச் முரண்பாடுகள் தேவை. இது தற்போதைய முக்கிய document/locale நோக்கத்தையும் அதன் பதிவு செய்யப்பட்ட ஆதாரத்தையும் சரிபார்க்கிறது. தவறான சூழல், முழுமையற்ற கவரேஜ் அல்லது குறுக்கீடு செய்யப்பட்ட சரிபார்ப்பு `INCOMPLETE` உருவாக்குகிறது ; உறுதிப்படுத்தப்பட்ட சறுக்கல் `FAIL` உருவாக்குகிறது. இரண்டும் தோல்வியடைந்த வெளியேறும் நிலையைத் தருகின்றன. ரசீது செக் அவுட் SHA, பணிப்பாய்வு, ரன் மற்றும் முயற்சி ஆகியவற்றுடன் பிணைக்கப்பட்டுள்ளது, மேலும் `i18n-base-health-<sha>-<run>-<attempt>` ஆகத் தக்கவைக்கப்படுகிறது.

இது வெளியிடப்பட்ட தளத்தின் ஒரு சுயாதீனமான அவதானிப்பு ஆகும். இது PR அல்லது ஒன்றிணைப்பு-குழு நிகழ்வு, தேவையான PR சரிபார்ப்பு, npm மாற்று அல்லது நிலையான-ஸ்கேன் சுயவிவர உறுப்பினரைச் சேர்க்காது. அடிப்படை சரிபார்ப்பு ஐந்து வகுப்புகளையும் முழுமையான பயன்முறையில் தடுக்கிறது. சாதாரண PR தயாரிப்பு சேர்க்கையிலிருந்து தனித்தனியாக உள்ளது. ஒரு வெற்றிகரமான பதிவேற்றம் தோல்வியுற்ற ஆரோக்கிய முடிவை PASS ஆக மாற்ற முடியாது.

ஒரு சாதாரண PR `--baseline-evidence` ஆல் உருவாக்கப்பட்ட அடிப்படை அறிக்கையுடன் `--preflight` பயன்படுத்துகிறது. முழுமையான மொழிபெயர்ப்புப் பதிவும் உண்மையான இலக்கு பைட்டுகளும் அந்தத் துல்லியமான அடிப்படையிலிருந்து மாறாமல் இருக்கும்போது மட்டுமே அது ஆங்கில மூலத்தை நிலுவையில் வைக்கலாம். புதிய இலக்கு அல்லது பிரிவு-கேச் முரண்பாடுகள் இன்னும் தடுக்கப்படுகின்றன, மேலும் முழுமையற்ற சான்றுகள் தயாரிப்பை அங்கீகரிக்க முடியாது. அறிக்கை `preparationPending` மற்றும் `mergeReady` தனித்தனியாக அம்பலப்படுத்துகிறது: வெற்றிகரமான தயாரிப்பு, நிலுவையில் உள்ள மொழிபெயர்ப்புகளை ஒன்றிணைக்கத் தயாராக இல்லை. சேர்க்கைக்கு முன் இயற்றப்பட்ட விண்ணப்பத்தில் பாதிக்கப்பட்ட கண்ணாடியைப் புதுப்பிக்கவும். நம்பகமான Mergify வரிசை வேட்பாளர், `merge_group`, கிளை புஷ்கள் மற்றும் கையேடு CI ரன்களுக்கு `--warn` அல்லது பரம்பரை-தோல்வி மன்னிப்பு இல்லாமல் முழுமையான சரிபார்ப்பைப் பயன்படுத்துகிறது. காணாமல் போன இலக்கு ஹாஷ்கள் மற்றும் நீக்கப்பட்ட பதிவுசெய்யப்பட்ட கோர் கோப்புகளால் குறைக்கப்பட்ட ஸ்கோப் ஆகியவை வெற்றிகரமான முழுமையான தீர்ப்பை உருவாக்க முடியாது.

### PR விரைவுப் பாதையை (`quality.yml`) வெளியிடவும்

`.github/workflows/quality.yml` main/release PRs இல் CI நிறைவு செய்கிறது, `main` க்கு தள்ளுகிறது, குழுக்களை அனுப்புகிறது மற்றும் ஒன்றிணைக்கிறது. PRs பாத்-வடிகட்டப்பட்ட வேகமான காசோலைகளைப் பயன்படுத்துகிறது. நிரந்தரமாக முடக்கப்பட்ட நகல் உருவாக்கம் அகற்றப்பட்டது; உண்மையான build/package/boot காசோலைகள் CI இல் இருக்கும். யூனிட் தொகுப்பு மற்றும் vitest CI (`Unit Tests (N/12)` மற்றும் `Vitest`) இல் மட்டுமே இயங்கும்.

#### மறக்கப்பட்ட உடன்பிறப்பு சோதனை அறிக்கை

`npm run check:forgotten-sibling-tests` `Fast Quality Gates` இன் ஆலோசனை படியாக இயங்குகிறது மற்றும் சோதனை-தாக்க வரைபடத்தின் பின்னால் உள்ள இறக்குமதி தீர்வை மீண்டும் பயன்படுத்துகிறது. மாற்றப்பட்ட ஒவ்வொரு உற்பத்தி தொகுதிக்கும், வேட்பாளர் சோதனையானது இழுத்தல்-கோரிக்கை வித்தியாசத்தில் இல்லாதபோது, தீர்மானிக்கும் `changed module/symbol -> static consumer -> candidate sibling test` சங்கிலிகளைப் புகாரளிக்கிறது. மார்க் டவுன் சுருக்கம் மற்றும் JSON முடிவு ஆகியவை எந்தத் தடுப்பையும் வெளியிடும் முன் அளவீடு செய்வதற்கான `forgotten-sibling-tests` பணிப்பாய்வு கலைப்பொருளாகத் தக்கவைக்கப்படுகின்றன.

பீப்பாய் மறு-ஏற்றுமதி மற்றும் மாறும் இறக்குமதிகள் தீர்மானம் கண்டறிதல் மட்டுமே; அவர்கள் ஒருபோதும் தடுக்கும் கண்டுபிடிப்பை உருவாக்க மாட்டார்கள். மதிப்பாய்வு செய்யப்பட்ட விதிவிலக்குகள் `config/quality/forgotten-sibling-allowlist.json` இல் உள்ளன. ஒவ்வொரு உள்ளீடும் நுகர்வோர் மற்றும் வேட்பாளர் சோதனைக்கு பெயரிட வேண்டும், ஒரு குறிப்பிட்ட பகுத்தறிவைக் கொடுக்க வேண்டும் மற்றும் GitHub சிக்கலை இணைக்க வேண்டும் அல்லது கோரிக்கையை இழுக்க வேண்டும். தவறான உள்ளீடுகள் தோல்வியடைந்தன. விதிவிலக்குகள் நீக்கப்பட்ட வேட்பாளர் சோதனை அல்லது `.skip`/`.todo` சேர்க்கும் வேறுபாட்டை அடக்க முடியாது ; வலியுறுத்தல் வலுவிழக்கச் செய்தல் மற்றும் பிற மறைத்தல் ஆகியவை சுயாதீனமாகத் தடுக்கும் `check:test-masking` வாயிலுக்குச் சொந்தமானதாகவே இருக்கும்.

#### இரண்டு தட்டச்சுச் சோதனை நிரல்கள் வித்தியாசமாக பதிலளிக்கின்றன

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`) மற்றும் `check:build-typecheck` வெவ்வேறு விருப்பங்களின் கீழ் வெவ்வேறு நிரல்களைத் தொகுக்கின்றன, மேலும் ஒரே கோப்பு ஒன்றில் சுத்தமாகவும் மற்றொன்றில் பிழைகள் நிறைந்ததாகவும் இருக்கும்.

`tsconfig.build.json` `"strict": false` அமைக்கிறது, எனவே `noImplicitAny` முடக்கப்பட்டுள்ளது. கோர் கன்ஃபிகரானது, 27-கோப்பு அனுமதிப் பட்டியலைக் கடுமையான விருப்பங்களுடன் தொகுத்து, ஒவ்வொரு உள்ளீட்டின் இறக்குமதி வரைபடத்தையும் பின்பற்றுகிறது, எனவே பில்ட் புரோகிராமில் தோன்றாத கோப்புகள் இன்னும் அங்கு சரிபார்க்கப்படுகின்றன.

கோப்பு தட்டச்சு செய்யப்பட்டுள்ளதா என்பதை தீர்மானிக்கும் போது அதன் விளைவு முக்கியமானது:**`check:build-typecheck` இன் கீழ் பூஜ்ஜிய கண்டறிதல் என்பது பூஜ்ஜியத்தைக் குறிக்காது** . 26 கோப்புகளில் இருந்து `@ts-nocheck` அகற்றப்பட்டது, அவற்றில் 23 கோப்புகளை உருவாக்க நிரலில் சுத்தமாக இருந்தது; அவற்றில் பதினாறு சுமார் 120 மறைமுகமான பிழைகள் வெளிப்பட்டன. கோப்பை சுத்தமாக அழைப்பதற்கு முன் இரண்டையும் சரிபார்க்கவும்.

| `check-new-key-coverage` (இன்லைன்) | ஏ **புதிய** ஒவ்வொரு மொழியிலும் ஆங்கில விசை மொழிபெயர்க்கப்பட்டது — ஒரு `__MISSING__:` மார்க்கர் நிராகரிக்கப்படுகிறது                                                                                       | ஆம்          |
| `check-translation-ratio`          | ஒரு மொழிக்கான உண்மையான மொழிபெயர்ப்பு விகிதம் (ஒரே மாதிரியான-ஆங்கிலம் / ஒதுக்கிட / அனுமதிப்பட்டியலுக்கு வெளியே விடுபட்ட இலைகள்) `config/quality/i18n-translation-baseline.json` + ஸ்லாக்கைத் தாண்டக்கூடாது | **தடுப்பது** |

`fetch-depth: 0` — தேவை, வேல்யூ-டிரிஃப்ட் கேட் `en.json` ஒன்றிணைக்கும் தளத்திற்கு எதிராக வேறுபடுகிறது.

#### `check-ui-value-drift` — பழைய-மொழிபெயர்ப்பு வாயில்

ஒரு i18n பின்னடைவை மற்ற வாயில்கள் அமைப்புரீதியாகப் பார்க்க முடியாது: ஆங்கில மதிப்பு மீண்டும் எழுதப்பட்டது மற்றும் _previous_ ஆங்கிலத்திலிருந்து பெறப்பட்ட மொழிபெயர்ப்புகள் பின் தங்கியிருக்கும், எனவே ஆங்கிலம் அல்லாத பயனர்கள் நம்பிக்கையுடன் வார்த்தைகள், இப்போது தவறான நகலைப் படிக்கிறார்கள்.

இது உண்மையாக அனுப்பப்பட்டது. Antigravity உள்நுழைவு உதவியாளர் இறங்கும் போது `oauthModal.googleOAuthWarning` மீண்டும் எழுதப்பட்டது (#5203);**43 வட்டாரங்களில் 39** "முழு URL ஐ நகலெடுத்து கீழே ஒட்டவும்" என்று ஆபரேட்டர்களுக்கு உரை கூறும் — அந்த வழங்குநரால் முடிக்க முடியாத ஒரு ஓட்டம். #8463 வரை இது கவனிக்கப்படாமல் போனது, ஏனெனில்:

- `sync-ui-keys` மட்டுமே விசைகளை மீண்டும் நிரப்புகிறது**இல்லாத** , ஒருபோதும் இல்லாதவை**பழமையான** ;
- `check-ui-keys-coverage` முக்கிய _இருப்பு_ஐக் கணக்கிடுகிறது, எனவே ஒரு பழமையான மொழிபெயர்ப்பானது மூடப்பட்டிருக்கும்;
- `check-translation-drift` `docs/i18n/<locale>/**.md` ஆவணங்களை — பிரதிபலிக்கிறது, அது `src/i18n/messages/*.json` ஒருபோதும் படிக்காது. 2026-09 மறு-ஒத்திசைப்பிலிருந்து வேலை `docs-sync-strict` ஐத் தடுப்பது: முக்கிய ஆவணமான → `npm run i18n:run -- --files=<doc>` யைத் திருத்தவும் (பிரிவு-நிலை, மலிவானது).

**வித்தியாசம் தெரியும், அடிப்படை ஆதரவு இல்லை.** இது `en.json` வேலை செய்யும் மரத்திற்கு எதிராக ஒன்றிணைக்கும் தளத்தில் ஒப்பிடுகிறது; ஆங்கில மதிப்பு மாறிய ஒவ்வொரு விசைக்கும், இன்னும் தொடப்படாத மொழிபெயர்ப்பை வைத்திருக்கும் எந்த மொழியும் பழையதாக இருக்கும். இது வேண்டுமென்றே**ஏற்கனவே இருந்த கடனை முடக்குகிறது** — ஒரு வித்தியாசம் எந்த பழைய ஆங்கிலத்திலிருந்து நீண்ட கால மொழிபெயர்ப்பு வந்தது என்பதை வெளிப்படுத்த முடியாது, எனவே தற்போதைய மாற்றம் என்ன தொடுகிறது என்பதை மட்டுமே கேட் தீர்மானிக்கிறது. மாற்று (ஒவ்வொரு முக்கிய ஹாஷ் பேஸ்லைன்) ~ 600 KB உருவாக்கப்பட்ட கோப்பு, 3 × என்பது தற்போதுள்ள மிகப்பெரிய அடிப்படைக் கோப்பாகும், ஒவ்வொரு i18n PR லும் மாற்றப்படும்.

அதை திருப்திப்படுத்த இரண்டு வழிகள்:

1. பாதிக்கப்பட்ட மொழிபெயர்ப்புகளைப் புதுப்பிக்கவும் அல்லது
2. அவற்றை `__MISSING__:<new english>` — என அமைக்கவும், அதன் இயக்க நேரம் திருத்தப்பட்ட ஆங்கிலம் (`src/i18n/request.ts::deepMergeFallback`, #7258) மற்றும் மொழிபெயர்ப்பிற்கான முக்கிய வரிசைகளை வழங்குகிறது.

சரம் என்றால்**பொருள்** மாற்றப்பட்டது, விரும்புகிறது**விசையை மறுபெயரிடுகிறது** : ஒரு புதிய விசை பழைய மொழிபெயர்ப்பைப் பெற முடியாது. அதுதான் #8463 பயன்படுத்தப்பட்ட மாதிரி.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

மதிப்பு-சறுக்கல் மற்றும் புதிய-விசை வாயில்கள் `scripts/i18n/resolve-ui-diff-base.mjs` இலிருந்து ஒரு மாறாத ஒப்பீட்டைப் பகிர்ந்து கொள்கின்றன. பணிப்பாய்வு இரண்டு காசோலைகளுக்கும் ஒரே அடிப்படை, அடிப்படை-முனை மற்றும் வேட்பாளர் SHAs ஆகியவற்றை அனுப்புகிறது. PR/base-retarget, புஷ் மற்றும் மெர்ஜ்-குரூப் ரன்கள் அவற்றின் நிகழ்வு சூழலைப் பயன்படுத்துகின்றன. ஒரு வேட்பாளர் கிளையை அனுப்புவதற்கு அதன் சரியான திறந்த PR அல்லது வெளிப்படையான `i18n_base_sha` உள்ளீடு தேவைப்படுகிறது. அந்த உள்ளீடு இல்லாமல் `main` அல்லது `release/vX.Y.Z` இன் அனுப்புதல் அல்லது திட்டமிடப்பட்ட கண்காணிப்பு, கடைசி கமிட்டை அதன் முதல் பெற்றோருடன் ஒப்பிடுகிறது; இது அனைத்து மரபுவழி மொழிபெயர்ப்புக் கடனின் தணிக்கை அல்ல. உள்ளூர் அழைப்பிற்கு வெளிப்படையான ஒப்பீட்டு அடிப்படை தேவை, எடுத்துக்காட்டாக மேலே உள்ள `BASE_REF` கட்டளை.

விடுபட்ட அல்லது தெளிவற்ற ஒப்பீட்டு சூழல், படிக்க முடியாத அல்லது தவறான தேவையான பட்டியல், மற்றும் மாற்றப்பட்ட வேட்பாளர் வெளியேறும் குறியீட்டுடன் `INCOMPLETE` உருவாக்குகிறார்**2** , எச்சரிக்கை முறையில் உட்பட. Catalog வாசிப்புகள் `scripts/i18n/read-ui-catalog.mjs` பயன்படுத்துகின்றன; வாசிப்பு தோல்விகள் வெற்று பொருள்களால் மாற்றப்படவில்லை. கிடைக்காத அடிப்படை அல்லது முழுமையற்ற உள்ளீடு PASS நிறுவவில்லை.

**புதிய-குறியீட்டு முறை (Clean-as-You-Code) — 2026-08-30 முதல், PR விரைவுப் பாதைக்கு மட்டும்**

`pull_request` நிகழ்வுகளில், `quality.yml` ஆனது `--base-ref <PR base SHA>` என்பதை `check:file-size`,
`check:complexity-ratchets` மற்றும் `check:dead-code` ஆகியவற்றுக்கு அனுப்புகிறது. `check:complexity-ratchets` மற்றும்
`check:dead-code` ஆகியவற்றுக்கு, தடை HEAD-ஐ merge-base உடன் ஒப்பிடுகிறது; இந்த ஒப்பீடு **PR மாற்றிய கோப்புகளுக்கு
மட்டுமே** வரையறுக்கப்படுகிறது (`scripts/check/newCodeMode.mjs`: merge-base ஒரு தற்காலிக
`git worktree`-இல் உருவாக்கப்படுகிறது; ESLint/knip அங்கேயும் HEAD-இலும் இயக்கப்பட்டு, ஒவ்வொரு கோப்பிற்குமான
எண்ணிக்கைகளின் வேறுபாடு கணக்கிடப்படுகிறது):

- **தடுக்கும்** — PR மாற்றிய கோப்புகளில் cyclomatic/cognitive மீறல்கள் அல்லது dead exports சேர்க்கப்பட்டுள்ளன
  (பதிவில் `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=`);
- **ஆலோசனை** — ஒட்டுமொத்த மொத்த மதிப்பு மற்றும் உறையவைக்கப்பட்ட அடிப்படை மதிப்புக்கு இடையிலான ஒப்பீடு. மரபுரிமையாக வந்த விலகல்
  குற்றமற்ற PR-ஐ ஒருபோதும் சிவப்பு நிலைக்குக் கொண்டுசெல்லாது; அந்த விலகல், வெளியீட்டு ஒத்திசைவின்போது சரிசெய்வதற்காகக் கண்காணிக்கப்பட்டு,
  headroom பணியால் மேற்பார்வையிடப்படுகிறது.

`check:file-size` அதன் சொந்த விதிகளின்படி base ref-ஐப் பயன்படுத்துகிறது (`scripts/check/check-file-size.mjs`, #8522):
அது tree-இல் உள்ள ஒவ்வொரு source மற்றும் test கோப்பையும் சரிபார்த்து, PR base-இல் ஒவ்வொன்றின் வரி எண்ணிக்கையையும்
`git show` மூலம் வாசிக்கிறது; பின்னர் அந்தக் கோப்பு அதன் அடிப்படை உச்சவரம்பு
(`frozen` / `testFrozen`, அல்லது அடிப்படைக்கு வெளியேயுள்ள கோப்பிற்கு `cap` / `testCap`) மற்றும் அதன் base அளவு
ஆகியவற்றில் பெரியதைத் தாண்டி வளர்ந்தால் மட்டுமே தோல்வியடையச் செய்கிறது. எனவே base-இல் ஏற்கெனவே விலகியுள்ள ஒரு கோப்பு,
குற்றமற்ற PR-ஐ ஒருபோதும் தோல்வியடையச் செய்யாது.

`check:boundary:ratchet` அதன் ஒற்றை எண்ணுக்கும் அதே விதியைப் பயன்படுத்துகிறது
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR நிகழ்வுகளில்
`quality.yml` fast-gates மற்றும் `ci.yml` lint job ஆகிய இரண்டும் PR base SHA-ஐ அனுப்புகின்றன; base commit
ஒரு `git archive` export-இலிருந்து அளவிடப்படுகிறது; மேலும் PR-இன் `open-sse → src` edge
எண்ணிக்கை, `metrics.boundaryOpenSseToSrc` மற்றும் base-இல் உள்ள எண்ணிக்கை ஆகியவற்றில் பெரியதை மீறும்போது மட்டுமே PR தோல்வியடைகிறது. உச்சவரம்புக்கு
மேலான base drift புகாரளிக்கப்படுகிறது (`base drift herdado`), ஆனால் குற்றமற்ற PR-ஐ ஒருபோதும் தோல்வியடையச் செய்யாது; push → main
முழுமையான உச்சவரம்பைத் தொடர்ந்து பயன்படுத்துகிறது; மேலும் தீர்மானிக்க முடியாத base SHA, எச்சரிக்கையுடன் அதற்கே fallback செய்கிறது.

`workflow_dispatch` இயக்கங்கள், release-green sweep மற்றும் nightly headroom job ஆகியவற்றுக்கு PR base
இல்லாததால், அவை முழுமையான (global) ஒப்பீட்டையே தொடர்ந்து பயன்படுத்துகின்றன. Coverage, duplication மற்றும் type-coverage ஆகியவை இப்போதைக்கு global ஆகவே
உள்ளன (அவற்றின் கருவிகள் per-file diff-ஐ குறைந்த செலவில் உருவாக்குவதில்லை) — இதே அணுகுமுறைக்கான சாத்தியமான வேட்பாளர்கள்.

## ராட்செட் அடிப்படை (`quality-baseline.json`)

ராட்செட் இயந்திரம் (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json`-ஐப் படித்து,
புதிதாகச் சேகரிக்கப்பட்ட `quality-metrics.json` உடன் ஒப்பிடுகிறது. அதன் எப்சிலான் வரம்பைத் தாண்டிப்
பின்னடையும் எந்த அளவீடும் பில்டைத் தோல்வியடையச் செய்யும்.

தற்போது கண்காணிக்கப்படும் அளவீடுகள்:

| அளவீடு                | திசை   | பொருள்                                              |
| --------------------- | ------ | --------------------------------------------------- |
| `eslintWarnings`      | `down` | ESLint எச்சரிக்கைகளின் எண்ணிக்கை அதிகரிக்கக் கூடாது |
| `coverage.statements` | `up`   | ஸ்டேட்மென்ட் கவரேஜ் குறையக் கூடாது                  |
| `coverage.lines`      | `up`   | வரி கவரேஜ் குறையக் கூடாது                           |
| `coverage.functions`  | `up`   | செயல்பாடு கவரேஜ் குறையக் கூடாது                     |
| `coverage.branches`   | `up`   | கிளை கவரேஜ் குறையக் கூடாது                          |

உண்மையான மேம்பாட்டிற்குப் பிறகு அடிப்படையைப் புதுப்பிக்க:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` கொடி தற்போது அளவிடப்பட்ட மதிப்புகளை `quality-baseline.json`-இல் எழுதுகிறது.
அளவீட்டை மேம்படுத்திய மாற்றத்துடன் இந்தக் கோப்பையும் கமிட் செய்யவும். அடிப்படையைப் புதுப்பிக்காமல்
ஒரு அளவீட்டை மேம்படுத்தும் PR, `--require-tighten` மூலம் கண்டறியப்படும் (கட்டம் 6A.5,
செயல்படுத்தல் நிலுவையில் உள்ளது).

### CodeQL ராட்செட்: வேட்பாளர் சேர்க்கை மற்றும் களஞ்சிய சரக்கு

CI ஒரு வெளிப்படையான சார்பு சங்கிலி மூலம் வேட்பாளர் CodeQL சேர்க்கைக்கு சொந்தமானது: `codeql-scan` நான்கு மொழி மேட்ரிக்ஸை `codeql.yml` இல் அழைக்கிறது, பின்னர் `codeql-admission` `node scripts/check/check-codeql-ratchet.mjs --candidate` இயக்குகிறது. `Gate / CI` இரண்டு முடிவுகளும் தேவை. தரமானது அதன் சொந்த எண் காசோலைகளை வைத்திருக்கிறது ஆனால் தயாரிப்பாளர் முடிக்கும் முன் ஸ்கேனரை வினவுவதில்லை; `Gate / Quality` மட்டும் முழுமையான வேட்பாளர் சேர்க்கை அல்ல. டாக்ஸ்-மட்டும் வேட்பாளர்களுக்கு CodeQL தேவைப்படுகிறது.

`config/quality/codeql-admission-policy.json` இல் உள்ள கொள்கை செயல்கள், C/C++, JavaScript/TypeScript மற்றும் பைதான், வினவல் தொகுப்பு இயல்புநிலை, தொலைநிலை அச்சுறுத்தல் மாதிரி மற்றும் பில்ட் மோட் எதுவுமில்லை. தயாரிப்பாளரின் முன்னோட்டம் நிலுவையில் உள்ள செயல்படுத்தல் பதிவை நிராகரிக்கிறது மற்றும் வெளிப்படையான இலக்கு பட்டியலுக்கு வெளியே கிளைகள். தற்போதைய இலக்குகள் முக்கிய மற்றும் release/v3.8.54. ஒப்பந்தச் சோதனைகள் இந்த வரையறுக்கப்பட்ட பட்டியலையும் பராமரிப்பு புஷ் தூண்டுதலையும் தொகுப்பு பதிப்போடு ஒப்பிடுகின்றன; அடுத்த வெளியீட்டை மதிப்பாய்வு செய்ய வேண்டும். CI இன் தற்போதைய பரந்த வெளியீட்டு PR தூண்டுதல் தக்கவைக்கப்படுகிறது, ஆனால் ஒரு unboarded இலக்கு ஒரு அளவிடப்படாத PASS பெறுவதற்குப் பதிலாக பிரித்தெடுப்பதற்கு முன் HOLD புகாரளிக்கிறது.

ஒவ்வொரு மேட்ரிக்ஸ் வேலையும் அதன் உண்மையான SARIF பதிவேற்றம் ID, மொழி, வகை, ரன் மற்றும் முயற்சி, அழைப்பாளர் பணிப்பாய்வு அடையாளம், நிகழ்வு ref/head/base/merge SHA மற்றும் பாலிசி ஹாஷ் ஆகியவற்றைப் பதிவு செய்கிறது. சார்பு வேலை இந்த ஓட்டத்தின் ரசீதுகளை மட்டுமே பதிவிறக்குகிறது மற்றும் கலைப்பொருள் செரிமானங்களை சரிபார்க்கிறது. இதற்கு நான்கு வகைகளும் தேவை, ஒரு வெற்றிகரமான தயாரிப்பாளர் மற்றும் ஒவ்வொரு சரியான பதிவேற்றத்தின் நிறைவு செயலாக்கம். இது API இன் sarif_id வடிப்பானைப் பயன்படுத்துகிறது, கிளையில் காணப்படும் சமீபத்திய பகுப்பாய்வு அல்ல. பகுதி மறுதொடக்கம், அதே ஓட்டம் மற்றும் வேட்பாளரின் முந்தைய முயற்சியிலிருந்து வெற்றிகரமான வகைகளை மீண்டும் பயன்படுத்தக்கூடும், இது உற்பத்தி முயற்சியைப் பாதுகாக்கிறது; தோல்வியுற்ற தற்போதைய தயாரிப்பாளர் முந்தைய பச்சை ஆதாரத்தை மீண்டும் பயன்படுத்த முடியாது.

CodeQL செயல் செயலாக்கத்திற்காகக் காத்திருக்கிறது, ஆனால் அதன் பின் செய்யப்பட்ட செயலாக்கமானது எச்சரித்து, நிலை-வாசிப்பு தோல்வி அல்லது தீர்ந்த காத்திருப்புக்குப் பிறகு தொடரலாம். எனவே சேர்க்கை செயலாக்கத்தை மீண்டும் சரிபார்க்கிறது. விடுபட்ட பிரிவுகள், நிலுவையில் உள்ள செயலாக்கம், தோல்வியுற்ற அல்லது ரத்துசெய்யப்பட்ட வேலைகள், பழைய அடையாளம், முழுமையடையாத பேஜினேஷன் அல்லது கிடைக்காத APIs ஆகியவை HOLD மற்றும் வெளியேறு 2. ஒரு சுயாதீன ஸ்கேனர் பணிப்பாய்வுக்கு நிலையான காத்திருப்பு இல்லை. ஸ்கேன் செய்யப்படாத PR கடந்து செல்ல முடியாது, ஏனெனில் ஒரு விழிப்பூட்டல் வினவல் 0 திரும்பியது. `metrics.codeqlAlerts.value` மேல் அளவிடப்பட்ட எண்ணிக்கை 1 இல் இருந்து வெளியேறுகிறது; மற்றொரு கிளையின் விழிப்பூட்டல்களை உள்வாங்குவதற்கு அடிப்படை உயர்த்தப்படவில்லை. [நிலை மற்றும் பகுப்பாய்வு தேடலை பதிவேற்றவும்](https://docs.github.com/en/rest/code-scanning/code-scanning).

ரசீது பதிவுகள் பதிவேற்றம் மற்றும் பகுப்பாய்வு IDs, வகைகள், கருவி பதிப்புகள், ref/SHA, அடிப்படை மற்றும் எச்சரிக்கை எண்கள். SARIF identity/result எண்ணிக்கை, குறைந்தபட்ச விதி எண்ணிக்கைகள் மற்றும் சரியான எச்சரிக்கை நிகழ்வுகள் கட்டாயமாக இருக்கும். ஏற்கும் முன் PR/analysis அடையாளங்கள் மீண்டும் சரிபார்க்கப்படும். இந்த காசோலைகள் உள்ளமைக்கப்பட்ட வகை கவரேஜை நிறுவுகின்றன, பிரித்தெடுக்கப்பட்ட ஒவ்வொரு மூல கோப்பின் இருப்பு அல்ல. C/C++ நோ-பில்ட் பிரித்தெடுத்தல் திட்ட உருவாக்கத்தின் போது உருவாக்கப்பட்ட குறியீட்டைக் கொண்டிருக்கவில்லை. மூல விலக்குகளுக்கு இன்னும் மதிப்பாய்வு தேவை, மேலும் பங்களிப்பாளர் பண்புக்கூறுக்கு ஒப்பிடக்கூடிய சரியான-அடிப்படை சான்றுகள் தேவை.

`codeql-maintenance.yml` ஆக்டிவ்-ரிலீஸ் புஷ் ஸ்கேன்கள் மற்றும் PR/main தயாரிப்பாளர்களை நகலெடுக்காமல் வாராந்திர அட்டவணையை வழங்குகிறது. `nightly-codeql-inventory.yml` களஞ்சிய அளவிலான அடிப்படையை தனித்தனியாக வைத்திருக்கிறது, `--strict-measurement` மற்றும் அளவீடு கிடைக்காத போது தோல்வி. உள்ளூர் மரபு சேகரிப்பாளரின் க்ரேஸ்ஃபுல் ஸ்கிப் என்பது வேட்பாளர் சேர்க்கை அல்ல. சரிபார்க்கப்பட்ட குறைந்த உலகளாவிய எண்ணிக்கைக்குப் பிறகு இறுக்குவது வெளிப்படையான `--update` ஆக இருக்கும்.

இயல்புநிலை அமைவு கட்டமைக்கப்படும் போது மேம்பட்ட பணிப்பாய்வு வெளியிடப்படக்கூடாது: GitHub அந்த கலவையை நிராகரிக்கிறது. மதிப்பாய்வு செய்யப்பட்ட நிர்வாக மாற்றம் மீண்டும் வாசிக்கப்படும் வரை அதன் பதிப்புக் கொள்கை நிலுவையில் இருக்கும். வெளியிடுவதற்கு முன், ஒரு ஆபரேட்டர் பின்ஸ் களஞ்சியம், head/base/tree, policy/patch/rollback ஹாஷ்கள் மற்றும் கவனிக்கப்பட்ட அமைவு நிலை; `node scripts/quality/codeql-producer.mjs verify-admin-readback` வழங்கப்பட்ட எதிர்பார்க்கப்படும் மற்றும் உண்மையான JSON பதிவுகளை சரிபார்க்கிறது. இது ஒரு தொழில்நுட்பக் காவலர், ஆபரேட்டர் ஒப்புதல் அல்லது புதிய ரீட்பேக்குகளைப் பெறுவதற்கான மாற்றாக அல்ல. PR டோக்கன் ஒருபோதும் நிர்வாக அணுகலைக் கோராது. ரோல்அவுட் மற்றும் எந்த ஸ்கேனர் மாற்றத்திற்கும் தனித்தனி ரீட்பேக் மற்றும் உண்மையான PR, ஃபோர்க் மற்றும் மெர்ஜ்-குரூப் இணக்கத்தன்மை சான்றுகள் தேவை.

ஃபோர்க்ஸ் ஹோஸ்ட் செய்யப்பட்ட ரன்னர்களைப் பயன்படுத்துகிறது, நிலையான நற்சான்றிதழ்கள் இல்லாமல் செக் அவுட், தயாரிப்பாளரிடம் எந்த திட்டமும் install/build இல்லை, மற்றும் மரபுவழி களஞ்சிய ரகசியங்கள் இல்லை. GitHub அதன் குறைக்கப்பட்ட ஃபோர்க் டோக்கனுடன் pull_request நிகழ்வுக்கான SARIF பதிவேற்றத்தை ஆதரிக்கிறது; முதல் முறையாக பங்களிப்பு செயல்படுத்தல் ஒப்புதல் GitHub கொள்கையாகவே உள்ளது. நம்பத்தகாத குறியீட்டை இயக்க pull_request_target ஐப் பயன்படுத்த வேண்டாம். இடம்பெயர்வு முடிந்ததாகக் கருதும் முன், கட்டுப்படுத்தப்பட்ட கேனரியில் உண்மையான டோக்கன் அனுமதிகள், பகுப்பாய்வு_கீ மற்றும் அனைத்து வகை சூழல்களையும் உறுதிப்படுத்தவும். [ஃபோர்க் பதிவேற்ற விதிகள்](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/resource-not-accessible), [முரண்பட்ட அமைவு முறைகள்](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/two-codeql-workflows).

**பணிநீக்கம் என்பது ஆபரேட்டரின் அழைப்பு (கடினமான விதி #14)** பணிநீக்கக் கருத்தில் தொழில்நுட்ப நியாயத்தை பதிவு செய்யாமல் — ஒருபோதும் CodeQL விழிப்பூட்டலை நிராகரிப்பதில்லை: அப்ஸ்ட்ரீம்-நெறிமுறைத் தேவைக்கான `won't fix`, சோதனை சாதனத்திற்கான `used in tests`, சானிடைசர் CodeQL க்கான `false positive` பார்க்க முடியாது (முன்னோடி: `docs/security/ERROR_SANITIZATION.md`).

**எந்த commit-உம் உருவாகும் முன்பே job-ஐ நிறுத்திவிடும்** — எந்த PR-உம் திறக்கப்படாது:

## அனுமதிப்பட்டியல் கொள்கை

முன்பே இருக்கும் மீறல்களால் தோல்வியடையக் கூடாத ஒவ்வொரு வாயிலும் உறையவைக்கப்பட்ட அனுமதிப்பட்டியலைப் பயன்படுத்துகிறது
(எ.கா., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). கொள்கை:

**மூலக் காரணத்தைச் சரிசெய்யவும்; மீறல் முன்பே இருந்தால் மற்றும் அதே PR-இல் அதைச்
சரிசெய்ய முடியாவிட்டால் மட்டுமே அனுமதிப்பட்டியலைப் பயன்படுத்தவும்.**

அனுமதிப்பட்டியலில் ஓர் உள்ளீட்டைச் சேர்க்கும்போது:

1. அதற்கான நியாயப்படுத்தலுடன் ஒரு கருத்துரையைச் சேர்க்கவும்.
2. கண்காணிப்புச் சிக்கலைக் குறிப்பிடவும் (எ.கா., `// #3498 — Phase 2 feature, not yet implemented`).
3. மீறலைச் சரிசெய்யும் அதே PR-இல் உள்ளீட்டை அகற்றவும் — செயலில் உள்ள மீறலை இனி
   ஒடுக்காத காலாவதியான உள்ளீடு தானே ஒரு குறைபாடாகும் (6A.3 காலாவதியான-அமலாக்கம்
   செயல்படுத்தப்பட்டதும், ஆதரவற்ற அனுமதிப்பட்டியல் உள்ளீடு வாயிலைத் தோல்வியடையச் செய்யும்).

சோதனைகள் விரைவாகத் தேர்ச்சி பெறுவதற்காக அனுமதிப்பட்டியல் உள்ளீடுகளைச் சேர்க்க **வேண்டாம்**. தொடர்ந்து
வளரும் அனுமதிப்பட்டியலுடன் கூடிய பச்சை வாயில், தரம் குறித்த தவறான நம்பிக்கையை அளிக்கிறது.

### உங்கள் PR-இல் ஒரு வாயில் தோல்வியடையும்போது

1. **வாயிலின் வெளியீட்டைக் கவனமாகப் படிக்கவும்** — எந்தக் கோப்பு அல்லது குறியீடு விதியை
   மீறியது என்பதை அது துல்லியமாகக் கூறும்.
2. **மீறலைச் சரிசெய்யவும்** — பெரும்பாலான வாயில்கள் தீர்மானகரமான கோப்பு முறைமைச் சோதனைகள்; குறியீடு
   சரியானவுடன் அவை தேர்ச்சி பெறும்.
3. **மீறல் முன்பே இருந்தால்** (அதாவது, அதை நீங்கள் அறிமுகப்படுத்தவில்லை; ஆனால் வாயில் இப்போது
   அதை உள்ளடக்குகிறது): நியாயப்படுத்தும் கருத்துரை மற்றும் கண்காணிப்புச் சிக்கலுடன் ஓர் அனுமதிப்பட்டியல் உள்ளீட்டைச் சேர்க்கவும்.
4. **வாயில் ஒரு ராட்செட் என்றால்** (கவரேஜ், ESLint எச்சரிக்கைகள், நகலாக்கம், சிக்கல்தன்மை):
   உங்கள் மாற்றம் அளவீட்டை மோசமாக்கியுள்ளது. அடிப்படைச் சிக்கலைச் சரிசெய்யவும் அல்லது (அரிதாக) மாற்றம்
   வேண்டுமென்றே செய்யப்பட்டு, அளவீட்டுச் சரிவு ஏற்கத்தக்கதாக இருந்தால் `npm run quality:ratchet -- --update`
   என்பதை இயக்கவும் — ஆனால் அதற்கான காரணத்தை PR விளக்கத்தில் ஆவணப்படுத்தவும்.
5. **ஆலோசனை வாயில்கள்** (`continue-on-error: true`) தகவலுக்காக மட்டுமே — அவை ஒன்றிணைப்பைத்
   தடுக்காது; ஆனால் CI சுருக்கத்தில் தோன்றும். இருப்பினும் அவற்றைச் சரிசெய்யவும்.

## புதிய வாயிலைச் சேர்த்தல்

1. `scripts/check/check-<name>.mjs` (அல்லது `.ts`) உருவாக்கவும். கொள்கை வாயில்கள் 0/1 வெளியேறும் குறியீட்டுடன் முடிவடையும்.
   Ratchet-பாணி வாயில்கள் `collect-metrics.mjs` வழியாக `quality-metrics.json`-க்கு ஓர் அளவீட்டை வெளியிடும்.
2. `package.json`-இல் `"check:<name>": "node scripts/check/check-<name>.mjs"` என்பதைச் சேர்த்து,
   அதன் மாற்றுப்பெயரையும் அதற்கான துல்லியமான கட்டளையையும் `config/quality/gate-manifest.json`-இல் ஒத்திசைக்கவும்.
   ஏற்கனவே உள்ள சரிபார்ப்பு மாற்றுப்பெயரை மாற்றும்போதோ அகற்றும்போதோ இதே ஒத்திசைவைப் பயன்படுத்தவும்.
   `npm run check:gate-manifest`-ஐ இயக்கவும்; pre-commit hook மற்றும் CI மாற்ற வகைப்பாடு
   இந்த ஒப்பந்தத்தை அமல்படுத்துகின்றன.
3. பொருத்தமான பணியின் கீழ் `.github/workflows/ci.yml`-இல் அதை இணைக்கவும்
   (கொள்கை → `lint` அல்லது `docs-sync-strict`; ratchet → `quality-gate`).
4. அதற்கு அனுமதிப்பட்டியல் இருந்தால், காலாவதியான உள்ளீடுகள் தானாகக் கண்டறியப்படுவதற்காக
   `scripts/check/lib/allowlist.mjs`-இலிருந்து `reportStaleEntries()`-ஐப் பயன்படுத்தவும்.
5. வாயிலின் கண்டறிதல் தர்க்கத்தை உள்ளடக்கும் சோதனையை `tests/unit/build/`-இல் எழுதவும்.
6. இந்த ஆவணத்தைப் புதுப்பிக்கவும் (தொடர்புடைய பணியின் அட்டவணையில் ஒரு வரியைச் சேர்க்கவும்).

இணைப்புப் பிழையை மட்டுமே பதிவு செய்யும், அமர்வுகளை ஒருபோதும் பாதிக்காது.

## பகுத்தறிவாக்கப் பின்னடைவு (ROI மதிப்பாய்வு — கட்டம் 9 அலை 3)

இந்தப் பட்டியல் 2026-06-17 அன்று `ci.yml` உடன் ஒப்பிட்டுச் சரிசெய்யப்பட்டது (முந்தைய பதிப்பில்
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,
`check:codeql-ratchet`, `check:pr-evidence` ஆகியவை விடுபட்டிருந்தன). சரிசெய்யப்பட்ட தொகுப்பின் ROI மதிப்பாய்வு
பின்வரும் பகுத்தறிவாக்கத் தேர்வுகளை அடையாளம் கண்டது. **இணைப்புகள் இயந்திரரீதியான CI
மாற்றங்கள்; நிலைமாற்றங்கள்/நீக்கங்கள் இயக்குநருக்காக ஒதுக்கப்பட்ட கொள்கை முடிவுகள்.** கீழே உள்ள எதுவும்
இன்னும் செயல்படுத்தப்படவில்லை.

**மேலே ஆவணப்படுத்தப்படாத மற்றவை** (ஆலோசனை மட்டுமே; குறைந்த பயனுள்ள சிக்னல்): `docs-lint` job (markdownlint + Vale, முழு job-க்கும் `continue-on-error`) மற்றும் தனித்த scanner workflow-களான `semgrep.yml` / `scorecard.yml`. மேலே கூறப்பட்ட activation தேவைகளுக்கு உட்பட்டு, CodeQL இப்போது `Gate / CI`-இன் கீழ் கட்டாய producer மற்றும் admission job-களைக் கொண்டுள்ளது. `quality-baseline.json`-இல் `semgrepFindings: 0` உள்ளது; ஆனால் அது `ci.yml`-இல் தடுக்கக்கூடிய ratchet-உடன் இணைக்கப்படவில்லை — இந்த metric தற்போது இணைப்பின்றி உள்ளது.

### இணைத்தல் / நகல்நீக்கம் (இயந்திரரீதியானது, குறைந்த ஆபத்து)

ஒவ்வொரு தேர்வும் 2026-06-17 அன்று நடைமுறையிலிருந்த கேட் நிலைக்கு எதிராகச் சரிபார்க்கப்பட்டது (நம்புங்கள், ஆனால் சரிபாருங்கள்);
“வெளிப்படையானவை” எனத் தோன்றிய பல இணைப்புகள் தொழில்நுட்பக் கடனை மறைத்திருப்பது தெரியவந்தது; எனவே அவை **சிக்கலற்ற** நேரடி மாற்றீடுகள் அல்ல.

- **`check:docs-sync` இருமுறை இயங்குகிறது** — `lint` பணியில் தனியாகவும், `check:docs-all` (`docs-sync-strict`) உள்ளேயும், husky முன்-கமிட் ஹுக்கிலும் இயங்குகிறது. ✅ **முடிந்தது** — தனியான `lint` இயக்கம் அகற்றப்பட்டது.
- **CVE ஸ்கேனிங்** — ❌ **சிக்கலற்ற இணைப்பு அல்ல.** `audit:deps` ஐந்து lockfile-களிலும் உள்ள தீவிர ஆலோசனைகள் மற்றும் முழுமையற்ற தணிக்கைகளைத் தடுக்கிறது; தற்போதைய கொள்கையின் கீழ் உயர்-தீவிர ஆலோசனைகளை எச்சரிக்கைகளாகத் தெரிவிக்கிறது. ஆனால் `check:vuln-ratchet` (osv), செக்-இன் செய்யப்பட்ட அடிப்படையுடன் ஒப்பிடுகையில் ஒரு _பின்னடைவு_ ஏற்பட்டால் மட்டுமே தோல்வியடைகிறது; தேவைப்படும் போது அளவீடுகள் இல்லாவிட்டால் அவற்றை நிராகரிக்கிறது. இவற்றின் பொருளியல் வெவ்வேறானது — `audit:deps`-ஐ நீக்குவது முழுமையான தீவிர கேட் மற்றும் தனித்தனி தொகுப்புத் தணிக்கைச் சான்றுகளை இழக்கச் செய்யும். இரண்டையும் வைத்திருக்கவும்.
- **சுழற்சி கண்டறிதல்** — ✅ **முடிந்தது** (#15159 G-01/G-02). இங்கிருந்த பழைய உரை `check:cycles`-ஐ “பச்சை நிலையில் உள்ள, தேர்ந்தெடுத்தமைக்கப்பட்ட” கேட் எனக் குறிப்பிட்டு, `check:circular-deps` (dpdm) 91 சுழற்சிகளை அறிவித்ததால் அதைத் தடுப்புக் கேட்டாக வைத்திருப்பதை நியாயப்படுத்தியது. அந்தப் பச்சை நிலை ஒரு **தவறான பச்சை நிலை**: `check:cycles` 5 துணைக் கோப்பகங்களை (450 கோப்புகள்) ஸ்கேன் செய்தது; நிலையான `import|export … from` உடன் மட்டுமே பொருத்தியது; மேலும் ஒவ்வொரு `@/` மற்றும் `@omniroute/open-sse/` குறிப்பானையும் கைவிட்டது. எனவே ரெப்போவில் ஆதிக்கம் செலுத்திய dynamic-import + alias சுழற்சிகளை அதனால் காண முடியவில்லை. இது சரிசெய்யப்பட்டது: கேட் இப்போது `src` + `open-sse` முழுவதையும் (5023 கோப்புகள்) கடந்து செல்கிறது; TypeScript AST-இலிருந்து குறிப்பான்களைச் சேகரிக்கிறது (எனவே `import("…")` கணக்கிடப்படும்; type-position `typeof import("…")` கணக்கிடப்படாது); மேலும் tsconfig `paths`-ஐத் தீர்க்கிறது. இது 0 அல்ல, **14** சுழற்சிகளைக் கண்டறிகிறது. முன்பே இருந்த 14 சுழற்சிகளை ஒரு கேட் PR-இல் சரிசெய்ய முடியாது என்பதால், `check:cycles` இப்போது ஒரு **ராட்செட்** (`--ratchet`, `quality-baseline.json`-இல் உச்சவரம்பு `metrics.cycles.value = 14`, `direction: down`) — இது எந்தவொரு _பின்னடைவையும்_ தடுக்கிறது; எண்ணிக்கை குறைய மட்டுமே முடியும். CI `npm run check:cycles:ratchet`-ஐ இயக்குகிறது. படிப்படியான குறைப்பு **A-01** உடன் தொடரும். பரந்த இரண்டாவது கருத்தாக `check:circular-deps` (dpdm) ஆலோசனை நிலையில் தொடர்கிறது.
- **சிக்கல்தன்மை** — ✅ **முடிந்தது** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ஒரே ESLint நடை, ruleId அடிப்படையிலான எண்ணிக்கை; இதனால் cyclomatic+max-lines மற்றும் cognitive அடிப்படைகள் தனித்தனியாக உள்ளன; தனிப்பட்ட `check:complexity` / `check:cognitive-complexity` ஆகியவை உள்ளூர் `--update` பயன்பாட்டிற்குத் தொடர்கின்றன.
- **`/api` கற்பனைத் தடுப்பு** — ✅ **முடிந்தது** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api`-க்கு ஒரே FS பட்டியல்; openapi-routes + docs-symbols இன்னும் தனித்தனியாக அறிக்கையிடுகின்றன; தனிப்பட்டவை உள்ளூர் இயக்கங்களுக்குத் தொடர்கின்றன.
- **`check:node-runtime` 11 பணிகளில் இயங்குகிறது** — ⚠️ **குறைந்த ROI.** ஒவ்வொன்றும் தனித்தனி runner; சரிபார்ப்பு <1s; மொத்தச் சேமிப்பு ~10s மட்டுமே, அதற்குப் பதிலாக ஒவ்வொரு பணிக்கும் மலிவான பாதுகாப்புக் கட்டுப்பாட்டை இழக்க நேரிடும். இந்த மாற்றக் குழப்பத்துக்கு மதிப்பில்லை.

### நிலைமாற்றம் / முடிவெடுத்தல் (இயக்குநர் கொள்கை)
