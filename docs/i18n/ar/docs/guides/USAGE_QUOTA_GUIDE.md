> **باختصار**: يتتبّع OmniRoute استخدام الرموز لكل طلب، ويحسب التكلفة، ويفرض حصة لكل مفتاح API، ويعرض التحليلات في لوحة المعلومات. يشرح هذا الدليل كيفية عمل كل ذلك.

**المصادر:**

- `open-sse/services/usage.ts` (~70KB) — الخدمة الرئيسية لتتبّع الاستخدام
- `src/lib/usageAnalytics.ts` (~10KB) — التجميع للوحة المعلومات
- `src/lib/db/quotaSnapshots.ts` — بيانات الحصص التاريخية
- `src/lib/db/usage*.ts` — عدة وحدات لقاعدة البيانات مرتبطة بالاستخدام

## نظرة عامة

يُنشئ كل طلب يمر عبر OmniRoute **سجل استخدام** يتضمن:

- **الهوية**: مفتاح API، والموفّر، والنموذج، والتركيبة المستخدمة
- **الرموز**: رموز المُدخل، ورموز الإكمال، والرموز المخزنة مؤقتًا، والإجمالي
- **التكلفة**: المبلغ بالدولار الأمريكي (محسوب من بيانات التسعير)
- **التوقيت**: زمن الاستجابة والطوابع الزمنية للبدء/الانتهاء
- **الحالة**: نجاح، أو خطأ، أو تقييد بسبب معدل الطلبات، وما إلى ذلك

```
الطلب ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    التحليلات  الحصة   الفوترة
                 (لوحة المعلومات) (الفرض) (التصدير)
```

## ما الذي يُسجَّل

تلتقط خدمة `usage.ts` **حدث استخدام** لكل طلب:

| الحقل              | النوع               | المصدر                                                                                      |
| ------------------ | ------------------- | ------------------------------------------------------------------------------------------- |
| `id`               | سلسلة نصية          | معرّف UUID يُنشأ عند التسجيل                                                                |
| `apiKeyId`         | سلسلة نصية          | مفتاح API الذي بدأ الطلب                                                                    |
| `provider`         | سلسلة نصية          | معرّف المزوّد (openai، anthropic، إلخ.)                                                     |
| `model`            | سلسلة نصية          | معرّف النموذج (gpt-5، claude-opus-4-6، إلخ.)                                                |
| `comboId`          | سلسلة نصية اختيارية | معرّف المجموعة إذا جرى التوجيه عبر مجموعة                                                   |
| `promptTokens`     | عدد                 | من استجابة المزوّد الخارجي                                                                  |
| `completionTokens` | عدد                 | من استجابة المزوّد الخارجي                                                                  |
| `cachedTokens`     | عدد                 | الرموز التي عُثر عليها في ذاكرة التخزين المؤقت (تخزين المطالبات مؤقتًا لدى Anthropic، إلخ.) |
| `totalTokens`      | عدد                 | رموز المطالبة + رموز الإكمال                                                                |
| `costUsd`          | عدد                 | تُحسب من بيانات التسعير                                                                     |
| `latencyMs`        | عدد                 | مدة الطلب من البداية إلى النهاية                                                            |
| `status`           | تعداد               | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                                  |
| `errorClass`       | سلسلة نصية اختيارية | فئة الخطأ إذا لم تكن الحالة نجاحًا                                                          |
| `timestamp`        | سلسلة نصية          | ISO 8601 بتوقيت UTC                                                                         |
| `metadata`         | كائن                | بيانات مخصصة تُدرجها الإضافات                                                               |

### مصدر الرموز

تُستخرج الرموز من استجابة المزوّد الخارجي في **معالج الاستجابة**:

```ts
// من open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

بالنسبة إلى المزوّدين الذين لا يُرجعون بيانات الاستخدام (بعض المزوّدين المعتمدين على ملفات تعريف ارتباط الويب)، **يقدّر** OmniRoute عدد الرموز باستخدام قاعدة تقريبية هي `~4 chars per token` (انظر `open-sse/services/autoCombo/pipelineRouter.ts`).

### الرموز المخزنة مؤقتًا

يتتبّع OmniRoute قيمة `cached_tokens` بشكل منفصل عن `prompt_tokens` للأسباب التالية:

- تفرض ميزة تخزين المطالبات مؤقتًا لدى Anthropic سعرًا مخفضًا للرموز المخزنة مؤقتًا (10% من السعر العادي)
- يُرجع بعض المزوّدين قيمة `cache_read_input_tokens` التي ينبغي تسعيرها بشكل مختلف
- يمكن للتحليلات عرض **معدل العثور في ذاكرة التخزين المؤقت** = `cached_tokens / prompt_tokens`

### تشخيصات فئات الكتابة إلى ذاكرة التخزين المؤقت

تميّز لوحة سلامة التخزين المؤقت للمطالبات في لوحة معلومات التحليلات بين عمليات الكتابة إلى ذاكرة التخزين المؤقت
لمدة 5 دقائق ولمدة ساعة واحدة، وفقًا لما يبلّغ عنه المزوّد. وتُحتفظ بقيمتَي Anthropic
`usage.cache_creation.ephemeral_5m_input_tokens` و
`usage.cache_creation.ephemeral_1h_input_tokens` أثناء تحويل بيانات الاستخدام في وضعي البث
وعدم البث، وتُخزَّنان مع ملخصات سجل الاستدعاءات. ولا يُضاف الإجمالي المجمّع
للكتابة إلى ذاكرة التخزين المؤقت إلى تلك الفئات مرة ثانية.

تكون فئة الاستدعاءات التي لا تحتوي إلا على عدّاد كتابة مجمّع، بما فيها السجلات الأقدم،
غير معروفة. وعند وجود تفصيل جزئي، يظل الجزء المتبقي غير المخصّص مجهول الفئة؛ وتُعلَّم العدّادات غير الصالحة أو
المتعارضة بدلًا من إسناد مدة بقاء (TTL) إليها بصمت. ولا تُعد علامات
TTL في جانب الطلب دليلًا على فئة خاضعة للفوترة.

يغطي تقدير الكتابة المكافئ لاستخدام API في اللوحة الفئات المُبلَّغ عنها التي تتوفر لها أسعار فقط، وليس
الطلب بأكمله. وعند استخدام تسعير نماذج Claude/Anthropic الأصلي، يُستخدم 1.25 ضعف
سعر الإدخال لعمليات الكتابة لمدة 5 دقائق، وضعف سعر الإدخال لعمليات الكتابة لمدة ساعة واحدة. ويُعد التسعير
المفقود غير متاح، وليس صفرًا. تُسجَّل الأسعار عند تسجيل كل استدعاء جديد؛
ولا يُعاد تسعير السجلات التاريخية. لذلك، قد يكون لحسابات الاشتراك
تقدير مكافئ لاستخدام API دون تكبّد ذلك المبلغ كإنفاق نقدي أو استهلاكه من حصة
الاشتراك. وتظل حسابات الحصص والميزانيات والتكلفة الدقيقة الخاصة بالمزوّد دون تغيير.

تستخدم هذه التشخيصات ملخص سلامة ذاكرة التخزين المؤقت المحدود الحالي وآلية الاحتفاظ بسجل
الاستدعاءات. وهي لا تغيّر قيم TTL الافتراضية للطلبات أو التوجيه أو اختيار الحساب.
أُجّل التقاط مدة TTL التي يطلبها العميل مقابل مدة TTL الفعلية الصادرة عند نقطة الإرسال
إلى المزوّد؛ فهذه اللوحة تعرض الفئات الواردة في إيصالات الاستخدام، وليس مدة TTL الفعلية الصادرة.

التنفيذ: `src/lib/usage/cacheWriteEstimate.ts`،
`src/lib/usage/cacheHealth.ts`، و`open-sse/utils/cacheWriteUsage.ts`.

## حساب التكلفة

تُحتسب التكاليف من **بيانات التسعير** المتزامنة من LiteLLM (`src/lib/pricingSync.ts`):

| النموذج           | الإدخال $/1M | الإخراج $/1M | المخزّن مؤقتًا $/1M |
| ----------------- | ------------ | ------------ | ------------------- |
| gpt-5             | $2.50        | $10.00       | —                   |
| claude-opus-4-6   | $15.00       | $75.00       | $1.50               |
| claude-sonnet-4-5 | $3.00        | $15.00       | $0.30               |
| gemini-2.5-pro    | $1.25        | $10.00       | —                   |

معادلة التكلفة (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **لماذا تُطرح الرموز المخزّنة مؤقتًا من رموز المطالبة؟** يُسعَّر الجزء المخزّن مؤقتًا بشكل منفصل؛ واحتساب سعر الإدخال على المطالبة كاملةً سيؤدي إلى زيادة غير صحيحة في الحساب.

### مزامنة التسعير

تتم مزامنة بيانات التسعير تلقائيًا من LiteLLM عبر نقطة النهاية `/api/pricing/sync` (وتُشغَّل بواسطة مهمة cron المضمّنة، وليس بواسطة متغير بيئة موجّه للمستخدم):

```bash
# تشغيل يدوي
curl -X POST http://localhost:20128/api/pricing/sync
```

بالنسبة إلى النماذج التي لا تتوفر لها بيانات تسعير، يلجأ OmniRoute إلى **تقدير التكلفة** باستخدام متوسطات الأسعار الداخلية (المأخوذة من بيانات تسعير LiteLLM).

## تجميع النطاقات الزمنية

تحسب الوحدة `usageAnalytics.ts` عناصر واجهة لوحة المعلومات من بيانات الاستخدام الخام. وهي تدعم 7 نطاقات زمنية:

| النطاق   | الفترة                        | حالة الاستخدام                      |
| -------- | ----------------------------- | ----------------------------------- |
| `1d`     | آخر 24 ساعة                   | اكتشاف ارتفاعات التكلفة بالساعة     |
| `7d`     | آخر 7 أيام                    | المراجعة الأسبوعية                  |
| `30d`    | آخر 30 يومًا                  | الفوترة الشهرية                     |
| `90d`    | آخر 90 يومًا                  | التحليل ربع السنوي                  |
| `ytd`    | منذ 1 يناير من السنة الحالية  | تتبّع الميزانية السنوية             |
| `all`    | كامل الفترة                   | إحصاءات طوال مدة الاستخدام          |
| `custom` | بداية ونهاية يحددهما المستخدم | عمليات التدقيق والاستعلامات المخصصة |

### عناصر واجهة لوحة المعلومات المحسوبة

لكل نطاق زمني، تحسب طبقة التحليلات ما يلي:

| عنصر الواجهة              | الوصف                                                      |
| ------------------------- | ---------------------------------------------------------- |
| **بطاقات الملخص**         | إجمالي الطلبات وإجمالي التكلفة وإجمالي الرموز ومعدل النجاح |
| **مخطط الاتجاه اليومي**   | التكلفة والرموز يوميًا، مكدّسة حسب النموذج                 |
| **خريطة النشاط الحرارية** | شبكة ساعة اليوم × يوم الأسبوع، اللون = عدد الطلبات         |
| **التوزيع حسب النموذج**   | مخطط دائري للتكلفة حسب النموذج                             |
| **التوزيع حسب المزوّد**   | مخطط شريطي للطلبات حسب المزوّد                             |
| **أبرز مفاتيح API**       | جدول بأعلى 10 مفاتيح من حيث التكلفة                        |
| **تحليل الأخطاء**         | معدل الأخطاء بمرور الوقت وأبرز فئات الأخطاء                |

### الوصول البرمجي

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // سجلات الاستخدام
  "7d",                 // النطاق الزمني: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // خريطة اتصالات المزوّد (connectionId → اسم الحساب)
  {
    startDate: "2025-01-01",  // اختياري: للنطاق "custom"
    endDate: "2025-06-01",   // اختياري: للنطاق "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (سنت)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## فرض الحصص

تُفرض الحصة الخاصة بكل مفتاح API في موضعين:

1. **حد مرن** (`quotaWarnAt`): تحذير في لوحة المعلومات عندما يتجاوز الاستخدام العتبة
2. **حد صارم** (`quotaLimit`): يُرفض الطلب برمز HTTP 429 عند تجاوزه

### الإعداد

```ts
// لكل مفتاح API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — إظهار تحذير
  quotaLimit: 10_00,    // $10.00 — إيقاف صارم
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### تدفق فرض الحصص

```
طلب ──▶ quotaCheck()
              │
              ├── ضمن الحد؟  ──▶ سماح
              │
              └── تجاوز الحد؟  ──▶ 429 طلبات كثيرة جدًا
                                   مع ترويسة Retry-After
```

### لقطات الحصص

يخزّن جدول `quotaSnapshots` **الحالة التاريخية للحصص** لتحليل الاتجاهات:

| الحقل | الوصف |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | المفتاح الذي يجري تتبّعه |
| `window` | "day" | "week" | "month" |
| `used` | التكلفة المستهلكة خلال هذه الفترة (بالسنت) |
| `limit` | الحد (بالسنت) |
| `resetAt` | وقت إعادة تعيين الفترة |
| `createdAt` | وقت أخذ اللقطة |

تُؤخذ اللقطات **عند كل طلب** تزيد تكلفته عن 0، وتُستخدم من أجل:

- عرض شريط تقدّم الحصة في لوحة المعلومات
- إظهار مخططات اتجاه الحصة على مدى 30 يومًا
- إطلاق تنبيهات عندما يقترب الاستخدام من الحد

### الاستعلام عن تحليلات الاستخدام

يتم الوصول إلى بيانات الاستخدام عبر لوحة المعلومات أو أدوات MCP، وليس عبر نقاط نهاية REST للتصدير المباشر. التحليلات المتاحة:

- **`/api/usage/analytics`** — مقاييس الاستخدام المجمّعة (التجميع حسب النموذج، أو موفّر الخدمة، أو المفتاح)
- **`/api/usage/quota`** — حالة الحصة الحالية لكل مفتاح API
- **`/api/usage/history`** — سجلات الطلبات السابقة

## الاحتفاظ بالبيانات وتنظيفها

يزداد حجم بيانات الاستخدام بنحو 1-10 كيلوبايت لكل طلب. وقد يصبح هذا الحجم كبيرًا عند التشغيل على نطاق واسع.

### إعدادات الاحتفاظ بالبيانات

يتم ضبط مدة الاحتفاظ بسجل الاستخدام عبر إعدادات قاعدة البيانات في واجهة المستخدم أو عبر `/api/settings/database`.

افتراضيًا، يُحتفظ بسجل الاستخدام لمدة **90 يومًا**.

### التنظيف

تُنظَّف السجلات القديمة بواسطة `src/lib/db/cleanup.ts`:

- تُشغَّل عملية التنظيف بواسطة عملية cron التي تعمل في الخلفية
- تحذف السجلات من `usage_history` التي يتجاوز عمرها مدة الاحتفاظ المحددة في إعداد `usageHistory`

### تقدير مساحة التخزين

| معدل الطلبات    | التخزين لمدة 30 يومًا | التخزين لمدة 90 يومًا |
| --------------- | --------------------- | --------------------- |
| 100 طلب/يوم     | ~3 ميغابايت           | ~9 ميغابايت           |
| 1,000 طلب/يوم   | ~30 ميغابايت          | ~90 ميغابايت          |
| 10,000 طلب/يوم  | ~300 ميغابايت         | ~900 ميغابايت         |
| 100,000 طلب/يوم | ~3 غيغابايت           | ~9 غيغابايت           |

عند التعامل مع حجم طلبات مرتفع جدًا، فكّر في:

- تقليل مدة الاحتفاظ بالبيانات عبر إعدادات قاعدة البيانات
- استخدام `aggregated_metrics` بدلًا من السجلات الخام (للتحليلات فقط)

## نصائح لتحسين التكلفة

### 1. استخدم النموذج المناسب

```bash
# إجابة سريعة — استخدم نموذجًا منخفض التكلفة وسريعًا
curl -d '{"model":"auto/fast","messages":[...]}'

# مهمة معقدة — استخدم نموذجًا عالي الجودة
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. فعّل التخزين المؤقت

يوفّر التخزين المؤقت للموجّهات من Anthropic **90% من تكلفة السياق المتكرر**:

```ts
// التخزين المؤقت تلقائي — ما عليك سوى تضمين موجّه النظام الكبير نفسه
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // سيُخزَّن مؤقتًا تلقائيًا
  messages: [{ role: "user", content: "..." }],
});
```

### 3. استخدم الضغط

يوفّر ضغط RTK + Caveman **15-95% من تكلفة الجلسات كثيفة استخدام الأدوات**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. عيّن حصصًا لكل مفتاح

عيّن `quotaLimit` دائمًا لمنع التكاليف المنفلتة:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // حد أقصى قدره 10 دولارات شهريًا
```

### 5. راجع أعلى المستهلكين

استخدم لوحة التحكم أو **`/api/usage/analytics`** للتجميع حسب مفتاح API والترتيب حسب التكلفة:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## استكشاف الأخطاء وإصلاحها

### "التكلفة أعلى من المتوقع"

1. تحقّق من **`/api/usage/analytics?groupBy=model`** — حدّد النموذج مرتفع التكلفة
2. تحقّق من **`/api/usage/analytics?groupBy=apiKey`** — حدّد المستهلك كثيف الاستخدام
3. تأكّد من أن بيانات التسعير محدّثة: `POST /api/pricing/sync`

### "سجلات مفقودة"

- تحقّق من إعدادات الاحتفاظ بالبيانات في قاعدة البيانات ضمن لوحة التحكم → قاعدة البيانات → التنظيف — تُحذف السجلات القديمة بواسطة مهمة التنظيف الدورية (`src/lib/db/cleanup.ts`)
- تحقّق من وجود أخطاء في `src/lib/db/usage*.ts` — تُسجَّل حالات فشل الكتابة إلى قاعدة البيانات ولكن لا تُعرض
- تأكّد من أن الطلب وصل بالفعل إلى `chatCore` — تحقّق من توجيه المجموعات

### "لا تُطبَّق الحصة"

- تحقّق من إعداد `quotaLimit` الخاص بالمفتاح
- تأكّد من ضبط `quotaWindow` بشكل صحيح
- ابحث عن سجلات `quotaSnapshots` — ينبغي إنشاؤها مع كل طلب
