> وفّر تلقائيًا 15-95% من السياق المؤهل. للحصول على نظرة عامة سريعة، راجع [قسم الضغط في README](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically).

## نظرة عامة

ينفّذ OmniRoute مسارًا معياريًا لضغط المطالبات يعمل **استباقيًا** قبل وصول الطلبات إلى مزوّدي الخدمة في المنبع. وهذا يعني أن توفير الرموز يحدث بشفافية — دون الحاجة إلى أي تغييرات في سير عملك.

```
طلب العميل
  → محدد استراتيجية الضغط
    → هل يوجد تجاوز عبر مجموعة؟ → استخدام إعداد المجموعة
    → هل تم بلوغ حد التشغيل التلقائي؟ → استخدام الوضع التلقائي
    → هل يوجد وضع افتراضي؟ → استخدام الإعداد العام
    → هل الوضع متوقف؟ → تخطي الضغط
  → وضع الضغط المحدد
    → متوقف: بلا ضغط
    → خفيف: تنظيف آمن للمسافات البيضاء/التنسيق (~15%)
    → قياسي: إزالة الحشو بأسلوب الكلام المقتضب (~30%)
    → مكثف: تقادم السجل + التلخيص (~50%)
    → فائق: تقليم استدلالي + تقليل كتل التعليمات البرمجية (~75%)
    → RTK: تصفية مدركة للأوامر لمخرجات الطرفية/الأدوات (نطاق 60-90% في المنبع)
    → مكدّس: مسار مرتب متعدد المحركات، وعادةً RTK ثم Caveman (نطاق 78-95% من المحتوى المؤهل)
  → الطلب المضغوط → مزوّد الخدمة
```

## أوضاع الضغط

### إيقاف

لا يُطبَّق أي ضغط. تمر جميع الرسائل دون تغيير.

### الوضع الخفيف (~15% توفير، زمن استجابة أقل من 1ms)

الوضع الأكثر أمانًا — تنظيف التنسيق. يكون اقتطاع نتائج الأدوات فيه فاقدًا للبيانات، لذلك يشغّل
المسار الافتراضي (من دون `allow-lossy` أو `engine:lite` أو تفعيل مجموعة مسماة) الوضع الخفيف مع
`compressToolResults: false`: تصل نتائج الأدوات السابقة إلى المزوّد دون تغيير.

| التقنية                  | الوصف                                                                                                            |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | دمج الأسطر الفارغة المتتالية والمسافات اللاحقة                                                                   |
| `dedupSystemPrompt`      | إزالة رسائل النظام المكررة                                                                                       |
| `compressToolResults`    | اقتطاع نتائج الأدوات السابقة إلى الحد الأقصى للوضع الخفيف (فاقد للبيانات: لا يُستخدم إلا مع تفعيل صريح من الطلب) |
| `removeRedundantContent` | إزالة التعليمات المتكررة                                                                                         |
| `replaceImageUrls`       | تقصير معرّفات URI لبيانات صور base64                                                                             |

**الأفضل لـ:** الاستخدام الدائم، وسير العمل الحرج للسلامة.

### الوضع القياسي (~30% توفير)

مستوحى من [Caveman](https://github.com/JuliusBrussee/caveman) — يزيل الكلمات الحشو والصياغات المطوّلة مع الحفاظ على المعنى:

- يزيل كلمات الحشو ("please" و"I think" و"basically" و"actually")
- يختصر العبارات المطوّلة ("in order to" ← "to"، و"as a result of" ← "because")
- يزيل الصياغات الاحترازية المهذبة ("Would you mind..." و"If you could possibly...")
- أكثر من 30 قاعدة regex مضبوطة لمطالبات البرمجة

**الأفضل لـ:** سير العمل البرمجي اليومي، والفرق المهتمة بتقليل التكلفة.

### الوضع المكثّف (~50% توفير)

إدارة ذكية للسجل في الجلسات الطويلة:

- **تقادم الرسائل** — تُضغط الرسائل الأقدم تدريجيًا
- **ضغط نتائج الأدوات** — تُقتطع مخرجات الأدوات الطويلة أو تُحذف أجزاء منها (الأسطر الأولى/الأخيرة،
  تصفية الأسطر المطابقة، ضغط مفاتيح JSON)
- **حواجز السلامة البنيوية** — تضمن بقاء أزواج `tool_use` + `tool_result` متسقة
- **الوعي بنافذة السياق** — يراعي حدود الرموز المميزة لكل نموذج

**الأفضل لـ:** جلسات تصحيح الأخطاء الممتدة، وقواعد التعليمات البرمجية الكبيرة.

### الوضع الفائق (~75% توفير)

أقصى ضغط للسيناريوهات الحرجة من حيث عدد الرموز المميزة:

- **الاقتطاع الاستدلالي** — اقتطاع نصوص النثر استنادًا إلى تقييم الرموز المميزة
- **الحفاظ على البنية** — تُحجَب كتل التعليمات البرمجية المُسيّجة، والتعليمات البرمجية المضمّنة، وعناوين URL والمعرّفات، ثم تُعاد خياطتها حرفيًا دون اقتطاع
- **طبقة SLM اختيارية** — يمكن لنموذج محلي صغير تحسين الاقتطاع عند تهيئته
- مستقلة عن الوضع المكثّف: لا تُجري تقادم الرسائل أو ضغط نتائج الأدوات
  أو المُ## الملخّص الاحتياطي (لا يمكن إلا لفشل طبقة SLM توجيه تمريرة احتياطية عبر الوضع المكثّف)

**الأفضل لـ:** الحالات التي تصل فيها إلى حدود السياق بشكل متكرر.

### وضع RTK (نطاق المنبع 60-90%)

وضع RTK مُحسّن لمخرجات الأدوات المطوّلة التي تظهر في جلسات وكلاء البرمجة:

- يكتشف فئات الأوامر/المخرجات مثل `git status` و`git diff` و`git log` ومشغّلات الاختبارات
  وعمليات بناء TypeScript/Vite/Webpack وESLint/Biome/Prettier وتدقيق/تثبيت npm وسجلات Docker ومخرجات البنية التحتية
  ومخرجات shell العامة
- يطبّق حزم تصفية JSON من `open-sse/services/compression/engines/rtk/filters/`
- يستورد مرشحات مخطط RTK TOML v1 من ملفات `filters.toml` الخاصة بالمشروع أو العامة، مع التحقق من الاختبارات المضمّنة
  والتحكم في الثقة لملفات المشروع
- يوفّر 56 مرشحًا مضمّنًا مع عينات تحقق مضمّنة
- يزيل تسلسلات التحكم ANSI وأشرطة التقدم والأسطر المتكررة والضوضاء غير القابلة للتنفيذ
- يحافظ على حالات الفشل والأخطاء والتحذيرات والملفات المتغيرة والملخصات وذيل المخرجات الطويلة
- يدعم مرشحات المشروع الخاضعة للتحكم في الثقة، والمرشحات العامة، والاسترداد الاختياري للمخرجات الأولية المنقّحة

**الأفضل لـ:** جلسات الوكلاء التي تتضمن نصوص shell والبناء والاختبارات وgit وgrep ومخرجات الملفات.

### الوضع المتسلسل (نطاق مؤهل 78-95%)

يشغّل الوضع المتسلسل محركات ضغط متعددة بترتيب حتمي. خط الأنابيب الافتراضي هو:

```txt
RTK -> Caveman
```

يحافظ هذا الترتيب أولًا على ضغط مخرجات الطرفية/الأدوات، ثم يطبّق التكثيف الدلالي لـ Caveman
على المطالبة المتبقية باللغة الطبيعية. يمكن تهيئة خطوط الأنابيب المتسلسلة عالميًا أو عبر
مجموعات الضغط المعيّنة إلى مجموعات التوجيه.

**الأفضل لـ:** السياق المختلط الذي يتضمن سجلات أدوات كبيرة بالإضافة إلى تعليمات بشرية أو ملخصات من المساعد.

## حساب وفورات المشاريع الأصلية

يوثّق OmniRoute وفورات الضغط من مصدرين: المعايير المرجعية للمشاريع الأصلية وتركيبة محركات
OmniRoute الخاصة.

| المصدر  | الرقم المستخدم هنا من README للمشروع الأصلي                                                                                           |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | عدد رموز مخرجات أقل بنسبة `~75%`، ومتوسط وفورات المخرجات في المعايير المرجعية `65%`، ونطاق `22-87%`، وأداة لضغط المدخلات بنسبة `~46%` |
| RTK     | وفورات بنسبة `60-90%` في مخرجات الأوامر؛ جلسة نموذجية من `~118,000 -> ~23,900` رمزًا، أي توفير بنسبة `79.7%` (`~80%`)                 |

بالنسبة إلى حمولات الأدوات/السياق المتداخلة، تجمع توليفة OmniRoute الافتراضية المحركات بالتتابع:

```txt
RTK -> Caveman
```

تكون الوفورات المجمّعة تراكمية بالضرب، وليست بالجمع:

```txt
المجمّع = 1 - (1 - وفورات RTK) * (1 - وفورات مدخلات Caveman)
المتوسط = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
النطاق   = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ينطبق رقم `78-95%` عندما يتمكن كل من RTK وCaveman من تقليل حمولة المدخلات/السياق نفسها.
أما وضع مخرجات استجابة Caveman فهو منفصل: عند تمكينه، استخدم وفورات مخرجات Caveman الخاصة (`65%`
في المتوسط، و`~75%` كرقم رئيسي، ونطاق `22-87%`). تعتمد وفورات الفوترة الإجمالية على مزيج المطالبات/المخرجات لديك.

### ما المقصود فعليًا بالمحتوى «المؤهل»

النطاق الرئيسي 15-95% حقيقي، لكنه ينطبق فقط على المحتوى **المكرر أو المسهب** — مثل أسطر الأخطاء
المتكررة، أو سجل بناء يكرر التحذير نفسه بكثافة، أو مخرجات ضخمة من `grep`/قراءة الملفات. وهذا
**لا** يعني أن كل طلب يحقق هذا القدر من التوفير.

تم التحقق من ذلك تجريبيًا (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): أدى
تشغيل `stacked` ‏(RTK + Caveman) على كتلة `tool_result` بهيئة Anthropic تحتوي على 300 سطر خطأ
متطابق إلى **وفورات في الرموز بنسبة 95.93% / وفورات في الأحرف بنسبة 96.26%** — ضمن النطاق المعلن
تمامًا. لكن تشغيل المسار نفسه على مخرجات أدوات عادية وغير مكررة (قائمة مطابقة نظيفة من `grep`،
وقراءة قصيرة لملف، ونص محادثة عادي) ينتج، وبشكل صحيح، **وفورات تقترب من الصفر**، لأنه
لا يوجد محتوى متكرر لإزالته، ولأن `validateCompression()` ‏(`validation.ts`) يرفض إرسال إعادة
صياغة قد تحذف أو تغيّر كتل التعليمات البرمجية، أو عناوين URL، أو العناوين، أو الإصدارات، أو معرّفات الثوابت المكتوبة بالكامل بأحرف كبيرة.

هذا سلوك متوقع وآمن، وليس خطأً: فجلسة برمجة تقتصر في معظمها على قراءة الملفات النظيفة أو البحث
فيها باستخدام grep ستحقق وفورات إجمالية محدودة حتى مع تمكين الضغط بالكامل، بينما تحقق الجلسة التي
تواجه حلقة فاشلة أو أداة lint كثيرة الرسائل النطاق الكامل 78-95% على تلك البيانات. لا تستخدم انخفاض
نسبة الوفورات الإجمالية في جلسة واحدة دليلًا على سوء إعداد الضغط — بل تحقّق أولًا مما إذا كانت
مخرجات الأداة الأساسية مكررة فعلًا.

## التكوين

### لوحة المعلومات

انتقل إلى `Dashboard → Context & Cache`:

- **Caveman** — اختيار الوضع، وحزم اللغات، والمعاينة، والإعدادات الافتراضية العامة
- **RTK** — معاينة تصفية الأوامر، وإعدادات أمان RTK، وكتالوج عوامل التصفية
- **Compression Combos** — مسارات محركات مُسمّاة مخصّصة لمجموعات التوجيه
- **Auto-Trigger Threshold** — تفعيل الضغط تلقائيًا عندما يتجاوز عدد الرموز الحدّ المحدد

### التجاوز لكل مجموعة

في `Dashboard → Context & Cache → Compression Combos`، عيّن مجموعة ضغط إلى
مجموعة توجيه:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

يتيح لك ذلك استخدام الضغط المتراص مع موفّري الخدمات المجانية/البرمجية، مع الإبقاء على الوضع
الخفيف في الاشتراكات المدفوعة.

يُعد تعيين **Per-Combo Override** هذا عنصر تحكم مختلفًا عن تجاوز **وضع ضغط مجموعة
التوجيه** (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — كما يقبل مخطط الحقل
أيضًا `rtk` و`stacked` و`omniglyph`) — فهذا التجاوز لا يختار مسارًا مُسمّى لمجموعة ضغط؛ بل يعيّن
فقط حقل `compressionMode` الذي تستشيرُه `resolveCompressionPlan`. ويمكن تعيينه إما في بطاقة
المجموعة (`Dashboard → Combos`) أو، منذ #6760، لكل مجموعة توجيه في قائمة "Assign to routing" ضمن
`Dashboard → Context & Cache → Compression Combos`، بجوار مربع اختيار تعيين المسار الموثّق
أعلاه مباشرةً. تحفظ كلتا الواجهتين البيانات عبر نقطة النهاية نفسها
`PUT /api/combos/{id}`.

### التجاوز لكل طلب

أرسل ترويسة الطلب `x-omniroute-compression` لتجاوز خطة الضغط لطلب واحد. وتتمتع هذه الترويسة
بالأولوية الأعلى — إذ تتغلب على تجاوز مجموعة التوجيه، والملف النشط، والتفعيل التلقائي، والقيمة
الافتراضية في اللوحة. ويتم تجاهل القيم غير المعروفة (ولا يُرفض الطلب مطلقًا)، كما يظل مفتاح
التفعيل العام هو المتحكم في كل شيء: عندما يكون الضغط متوقفًا عالميًا، لا يمكن للترويسة
تفعيله. القيم:

| Value         | Effect                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------ |
| `off`         | لا ضغط لهذا الطلب.                                                                               |
| `default`     | الملف الافتراضي المشتق من اللوحة (مع تجاهل الملف النشط). وتظل المحركات الفاقدة للبيانات متوقفة.  |
| `safe`        | نفس النتيجة كما لو حُذفت الترويسة.                                                               |
| `allow-lossy` | الإبقاء على خطة المشغّل لهذا الطلب، بما في ذلك الملخصات، وعوامل تصفية الصلة، وإعادة كتابة النمط. |
| `engine:<id>` | محرك واحد عند تفعيله، مثل `engine:rtk`. وهذا هو خيار التفعيل لكل طلب لذلك المحرك.                |
| `<combo>`     | مجموعة مُسمّاة، تتم مطابقتها بالاسم (مع تجاهل حالة الأحرف) أولًا، ثم بالمعرّف.                   |

من دون `allow-lossy` أو `engine:<id>` أو مجموعة مُسمّاة، لا يتم تطبيق المحركات الفاقدة للبيانات.
عند خفض مستوى Default أو التفعيل التلقائي أو تجاوز التوجيه الفاقد للبيانات، يحتفظ OmniRoute
بالخطوات غير الفاقدة المعروفة من المسار المتراص المكوّن، وبالترتيب المكوّن. ولا يعود إلى
`session-dedup → lite` إلا عندما لا تبقى أي خطوة غير فاقدة مكوّنة.

تعرض معاينة **Effective pipeline** في لوحة الإعدادات الخطة الاعتيادية المحفوظة. وعندما يمكن
تشغيل التفعيل التلقائي، تعرض المعاينة نفسها أيضًا مساره الفعّال الشرطي، بحيث تظل دقة الحل في
اللوحة ووقت التشغيل من دون ترويسة متوافقة.

تُعاد الخطة المطبقة في ترويسة الاستجابة
`X-OmniRoute-Compression: <mode>; source=<source>`، حيث تكون قيمة `<source>` إحدى القيم
`request-header` أو `routing-override` أو `active-profile` أو `auto-trigger` أو `default` أو
`off`.

## شكر وتقدير

قواعد الضغط في الوضع القياسي مستوحاة من **[Caveman](https://github.com/JuliusBrussee/caveman)** من تطوير **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) — المشروع واسع الانتشار الذي يحمل شعار «لماذا تستخدم رموزًا كثيرة بينما تؤدي رموز قليلة الغرض نفسه؟». يفيد Caveman بأنه يحقق عددًا أقل من رموز المخرجات بنسبة `~75%`، ومتوسط توفير في مخرجات الاختبارات المعيارية يبلغ `65%`، ونطاقًا لتقليل المخرجات يتراوح بين `22-87%`، وأداة لضغط المدخلات بنسبة `~46%`.

وضع RTK مستوحى من **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** من تطوير **[RTK AI](https://github.com/rtk-ai)** — مشروع عالي الأداء لضغط مخرجات الأوامر في الطرفية وعمليات البناء والاختبار وgit، ولترشيح مخرجات الأدوات. يفيد RTK بتحقيق توفير قدره `60-90%`، وتُظهر جلسة العينة في ملف README الخاص به توفيرًا يبلغ `~80%`.

## أنظمة الضغط المتقدمة

بالإضافة إلى الأوضاع السبعة الموصوفة أعلاه (يقبل المصدر أيضًا الوضعين `codex-responses` و `omniglyph` ، اللذين لا يغطيهما هذا الدليل)، تغطي الأقسام أدناه الميزات التي تعمل داخل هذه الأوضاع أو جنبًا إلى جنب معها: ضغط نتيجة الأداة والشيخوخة التقدمية هما الخطوتان 1 و2 من المحرك العدواني (الوضع العدواني وخطوة `aggressive` لخط أنابيب مكدس)، خط الأنابيب المكدس هو كيفية تشغيل الوضع المكدس، والضغط المدرك لذاكرة التخزين المؤقت يخفض مستوى `aggressive` و `ultra` إلى `standard` لموفري التخزين المؤقت أثناء تشغيل الضغط، ويعد وضع إخراج رجل الكهف وأنماط الإخراج بمثابة تعليمات موجهة للنظام، يتم إيقاف تشغيلها افتراضيًا، والتي تشكل مخرجات النموذج بدلاً من ضغط الطلب.

### ضغط ذاكرة التخزين المؤقت

يدعم بعض مقدمي الخدمة (مثل Anthropic مع التخزين المؤقت السريع).** التخزين المؤقت الفوري** ، مما يتيح لهم تخزين أجزاء من الموجه مؤقتًا لتقليل التكاليف ووقت الاستجابة. عند تمكين التخزين المؤقت، يمكن الضغط القوي في الواقع** يؤذي** الأداء لأنه يغير الرموز المميزة المخزنة مؤقتًا، مما يؤدي إلى إبطال ذاكرة التخزين المؤقت.

وحدة `cachingAware.ts` تحل هذه المشكلة عن طريق** الكشف عن سياق التخزين المؤقت** و** ضبط استراتيجية الضغط** وفقاً لذلك.

#### كيف يعمل

1. **كشف سياق التخزين المؤقت** — يقوم بمسح نص الطلب بحثًا عن علامات `cache_control`
2. **تحديد موفري التخزين المؤقت** — يتحقق مما إذا كان الموفر المستهدف يدعم التخزين المؤقت
3. **ضبط الاستراتيجية** — يقوم بتخفيض مستوى `aggressive`/`ultra` إلى `standard` لموفري التخزين المؤقت
4. **تخطي موجه النظام** — عادةً ما تكون مطالبات النظام مخزنة مؤقتًا، لذا لا تقم بضغطها

يقوم مساعد الإستراتيجية أيضًا بإرجاع علم `deterministicOnly` ، لكن منشئ الخطة يستهلك فقط الإستراتيجية — ولا شيء يقرأ العلم اليوم.

#### مثال على الكود

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### متى تستخدم

الضغط المدرك لذاكرة التخزين المؤقت هو** دائما على** — لا حاجة للتكوين. يتم تشغيله عندما يكون الضغط قيد التشغيل ويدعم الموفر الهدف التخزين المؤقت الفوري (Anthropic، OpenAI، وما إلى ذلك)؛ علامات `cache_control` الصريحة ليست مطلوبة، — موفر التخزين المؤقت وحده يؤدي إلى التخفيض، ولا تفعل العلامات وحدها أبدًا (يغذي اكتشاف العلامة القياس عن بعد لذاكرة التخزين المؤقت، وليس قرار الإستراتيجية).

يُعد OpenRouter مزود تخزين مؤقت فقط لنماذج `anthropic/*` : تحتفظ طلبات كود Claude بنقاط توقف `cache_control` الخاصة بها (4 على الأكثر) ويحمي الحارس البادئة، بينما تظل كل عائلة OpenRouter الأخرى (`openai/`، `google/`، `qwen/`، ...) مجردة وغير محمية.

### الشيخوخة التقدمية

تتراكم في المحادثات الطويلة العديد من المنعطفات للرسائل، لكن المنعطفات الأقدم تصبح أقل أهمية. وحدة `progressiveAging.ts`** يحط الرسائل عن طريق مسافة بدوره** (المسافة تقاس من نهاية المحادثة). مع الإعدادات الافتراضية التي تم شحنها (`verbatim: 2, light: 2, moderate: 3`):

- **آخر دورتين (المسافة ≤ 2)** : حفظت حرفيا
- **المسافة 3** : ضغط رجل الكهف (إزالة الحشو)
- **المسافة 4 +** : تلخيص رسائل المساعد. تم تقليل رسائل المستخدم إلى السطر الأول، بحيث لا يتجاوز 120 حرفًا؛ أدوار أخرى لم تمس. يتم دائمًا الاحتفاظ بمطالبات النظام والرسائل القديمة وأحدث رسائل المستخدم حرفيًا بغض النظر عن المسافة. لم يتم إسقاط أي شيء تمامًا، ولا يمكن الوصول إلى النطاق `light` مع الإعدادات الافتراضية المشحونة (`light` يساوي `verbatim`).

#### مثال على الكود

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### متى تستخدم

الشيخوخة التدريجية هي** دائما على** بالنسبة لوضع `aggressive` — فهي الخطوة 2 من `compressAggressive()`. الوضع الفائق لا يعمل عليه. إنها فعالة بشكل خاص من أجل:

- جلسات البرمجة طويلة الأمد
- محادثات متعددة الأيام
- سير عمل الوكيل مع العديد من استدعاءات الأدوات

### وضع إخراج رجل الكهف

يضيف وضع إخراج رجل الكهف** تعليمات النظام السريعة** التي تطلب من النموذج نفسه إخراجًا مقتضبًا — ويطلب مستوى `lite` إجابات موجزة تحافظ على الجمل الكاملة، ويطلب منه `full` "الرد بشكل مقتضب مثل رجل الكهف الذكي"، ويطلب `ultra` إخراجًا تلغرافيًا؛ تعليمات تسأل فقط، لا يمكنهم ضمان ذلك. يتم استلام الطلبات من خلال `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`): يقوم `open-sse/handlers/chatCore.ts` أولاً بحل التحديد باستخدام shim المتوافق مع الخلف (`resolveOutputStyleSelection()` في `open-sse/services/compression/outputStyles/backCompat.ts`)، والذي، بينما يكون `outputStyles` فارغًا، يقوم بتعيين `cavemanOutputMode` ممكن إلى نمط إخراج `terse-prose` في `cavemanOutputMode.intensity` (انظر Back-compat أدناه)؛ يتم استخدام تحديد `outputStyles` غير الفارغ كما هو، ولن يكون لـ `cavemanOutputMode.enabled` و `intensity` أي تأثير، بينما لا يزال تبديل `autoClarity` الخاص به ساريًا. يحتوي `outputMode.ts` على نصوص التعليمات (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`)، وتجاوز المحتوى ومساعد الموضع الذي يستخدمه الحقن؛ حاقن `applyCavemanOutputMode()` الخاص به لا يحتوي على متصل بالإنتاج.

#### كيف يعمل

هذا الوضع لا يضغط الإدخال. فهو يضيف كتلة تعليمات إلى موجه النظام (انظر كيفية عمل الحقن أدناه)، وأي وضع ضغط إدخال محدد للطلب يظل يعمل بعد ذلك، على الجسم الذي يحمل الكتلة الآن. قبل بند الحدود المشتركة الذي ينتهي به كل مستوى، يقرأ مستوى `full` باللغة الإنجليزية:

> "رد بإيجاز مثل رجل الكهف الذكي. قم بإسقاط المقالات (a/an/the)، والحشو (just/really/basically/actually/simply)، والمجاملات، والتحوط. الأجزاء OK. المرادفات القصيرة (كبيرة وليست واسعة النطاق، والإصلاح غير قابلة للتنفيذ). احتفظ بجميع المواد التقنية، والأكواد، والأخطاء، و URLs، والمعرفات الدقيقة."

وهذا يعمل بشكل جيد بشكل خاص من أجل:

- إنشاء التعليمات البرمجية (إخراج terser = عدد أقل من الرموز المميزة)
- أسئلة وأجوبة سريعة (لا حاجة لتفسيرات تفصيلية)
- معالجة الدفعات (زيادة الإنتاجية)

#### متى تستخدم

وضع إخراج رجل الكهف هو** الاشتراك** . مع تشغيل الضغط (`enabled: true`، مفتاح التبديل الرئيسي في صفحة إعدادات الضغط)، قم بتشغيله باستخدام `cavemanOutputMode.enabled`؛ يختار `intensity` `lite` أو `full` أو `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

التحرير والسرد الضغط** وضع الإخراج** يقوم التبديل (`outputMode`، المستوى في `outputModeIntensity`) بتعيين نفس المفتاح للطلبات التي ينطبق عليها التحرير والسرد، وتقوم أداة `omniroute_set_compression_engine` MCP بكتابتها من خلال وسيطة `outputMode` المنطقية الخاصة بها. يكون لتحديد `outputStyles` غير الفارغ الأسبقية على رمز التبديل هذا. في لوحة القيادة، تمكين** نثر مقتضب** يقوم نمط الإخراج بإدخال نفس الكتلة (انظر أنماط الإخراج أدناه).

يشحن كل نمط ثلاثة مستويات كثافة — `lite` و `full` و `ultra` — وينتهي كل مستوى بشرط الحدود المشتركة (`SHARED_BOUNDARIES` في `outputMode.ts`)، الذي يحافظ على كتل التعليمات البرمجية ومسارات الملفات والأوامر والأخطاء و URLs بدقة. تضيف النصوص على مستوى `terse-prose` و `terse-cjk` معرفات إلى تلك القائمة.

`terse-cjk` محصورة بـ `zh` في مكانين. تسرد صفحة إعدادات الضغط الصف الخاص بها فقط عندما تكون لغة لوحة المعلومات UI هي اللغة الصينية (`zh-CN` أو `zh-TW`)، ويقوم `applyOutputStyles()` بإدخالها فقط عندما تكون لغة حل الطلب (راجع تحديد اللغة أدناه) هي `zh`. لا يؤدي إخفاء الصف إلى مسح تحديد `terse-cjk` المحفوظ: تقبل الإعدادات API أي معرف نمط، ويحتفظ حفظ الأنماط الأخرى على الصفحة به. في وقت الطلب، يكون فحص اللغة `applyOutputStyles()` هو البوابة المحلية الوحيدة.

#### كيف يعمل الحقن

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) يحل التحديد مقابل الكتالوج (يتم إسقاط المعرفات غير المعروفة والأنماط المحلية غير المتطابقة، ولا يحدث أي خطأ أبدًا؛ التحديد الذي لا يؤدي إلى أي نمط يترك النص بدون تغيير، ويتم تخطيه كـ `no_styles`)، ويربط التعليمات المحددة بترتيب الكتالوج، ويلحق عبارة الحدود** مرة واحدة** (بالإضافة إلى شرط الأمان، `SAFETY_BOUNDARIES` أو ترجمته، عند تحديد `less-code` أو `ponytail` )، ويبدأ الكتلة بعلامة عجز واحدة (`[OmniRoute Output Styles]`)، لذا فإن إعادة التقديم أمر محظور. عندما تحتوي اللغة التي تم حلها (راجع تحديد اللغة أدناه) على ترجمة، يتم إدخال التعليمات المترجمة بدلاً من اللغة الإنجليزية.

في الجسم الذي يحتوي على مصفوفة `messages` غير فارغة، يتم تشغيل فحص idempotency قبل تجاوز المحتوى: عندما تكون علامة `[OmniRoute Output Styles]` موجودة بالفعل في حقل `system` ذي المستوى الأعلى (سلسلة أو مصفوفة كتلة محتوى) أو في رسالة نظام تحتوي على محتوى سلسلة، يتم ترك النص بدون تغيير مثل `already_applied` ولا يتم تشغيل فحص الكلمات الرئيسية. بخلاف ذلك، يتحقق تجاوز المحتوى (`shouldBypassCavemanOutputMode()` في `open-sse/services/compression/outputMode.ts`) من نص الرسائل الثلاث الأخيرة، أيًا كان دورها، ويتخطى الأنماط للدورة بأكملها عندما يتطابق هذا النص مع الكلمات الأساسية الخاصة بالأمان أو الإجراء غير القابل للإلغاء أو التوضيح، أو تسلسل حساس للترتيب: `first` أو `then` أو `after that` أو `before` أو `rollback` أو `backup` متبوعًا بـ 240 حرفًا بواسطة `delete` أو `drop` أو `migrate` أو `deploy` أو `release`. يتم تشغيل الالتفافية أثناء** تجاوز الوضوح التلقائي** التبديل (`cavemanOutputMode.autoClarity`، قيد التشغيل افتراضيًا) قيد التشغيل؛ يؤدي إيقاف تشغيل التبديل إلى تخطي التحقق من الكلمة الرئيسية.

عندما يسمح التجاوز بالانتقال، `placeSystemInstruction()` (نفس الملف)، الذي لا ينشئ `messages[0]` جديدًا أبدًا، يضع الكتلة في أول ما يجده:

1. رسالة نظام رئيسية تحتوي على محتوى سلسلة: يتم إلحاق الكتلة بعد النص الخاص بها.
2. حقل `system` ذو المستوى الأعلى: يتم إلحاق الكتلة بعد نص السلسلة، أو إضافتها ككتلة نصية جديدة إلى مصفوفة كتلة المحتوى.
3. أول رسالة نظام لاحقة تحتوي على محتوى سلسلة: يتم إلحاق الكتلة بعد النص الخاص بها.
4. لا شيء مما سبق: تنتقل الكتلة إلى رسالة نظام جديدة في نهاية `messages`.

في الجسم الذي لا يحتوي على مصفوفة `messages` (أو بمصفوفة فارغة)، لا يتم تشغيل أي تجاوز للمحتوى ولا تتم استشارة حقل `system` ذي المستوى الأعلى. يتم إلحاق الكتلة بعد نص حقل `instructions` ، ما لم يكن هذا الحقل يحتوي بالفعل على علامة `[OmniRoute Output Styles]` ، وفي هذه الحالة يتم ترك النص بدون تغيير كـ `already_applied`. عندما لا يحتوي الجسم على حقل سلسلة `instructions` ولكنه يحمل `input` (سلسلة أو مصفوفة)، تصبح الكتلة `instructions`، لتحل محل أي قيمة غير سلسلة يحتفظ بها هذا الحقل. يتم ترك النص الذي لا يحتوي على حقل سلسلة `instructions` ولا سلسلة أو صفيف `input` بدون تغيير ويتم تخطيه كـ `no_messages`.

#### كيفية التمكين

في لوحة القيادة:** إعدادات ضغط سياق الضغط →** (`/dashboard/context/settings`)، قسم أنماط الإخراج: صف واحد لكل نمط مع تبديل on/off ومحدد المستوى. يتم إدخال الأنماط أثناء تشغيل الضغط نفسه (التبديل الرئيسي للصفحة، `enabled`). ال** تجاوز الوضوح التلقائي** التبديل موجود على** رجل الكهف** الصفحة (`/dashboard/context/caveman`)، في** وضع الإخراج** بطاقة. برمجيًا، يستمر تكوين الضغط في التحديد على النحو التالي:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

التوافق الخلفي: عندما يكون `outputStyles` فارغًا، يتم تعيين إعداد `cavemanOutputMode.enabled` القديم إلى `terse-prose` عند `cavemanOutputMode.intensity`. تبدأ الكتلة بعد ذلك بعلامة `[OmniRoute Output Styles]` ، حيث كتب الحاقن `applyCavemanOutputMode()` القديم `[OmniRoute Caveman Output Mode]`. أسفل العلامة، يتطابق النص مع الإدخال القديم في en وpt-BR وes وde وfr وit وru وid وvi؛ في ja وzh يحمل مسافة إضافية واحدة قبل جملة الحدود. يتم ترجمة `terse-prose` إلى pt-BR وes وde وfr وit وru وzh وja وid وvi، وبالتالي فإن الطلب الذي تكون لغته التي تم حلها هي `hu` يحصل على النص الإنجليزي حيث استخدم الحاقن القديم اللغة المجرية.

تحديد لغة نمط الإخراج (`resolveOutputStyleLanguage()` في `outputStyles/apply.ts`): مع تشغيل `languageConfig.enabled` ، يقوم `autoDetect` باختبار أحدث رسالة مستخدم في مصفوفة `messages` الخاصة بالطلب والتي تحتوي على نص (محتوى سلسلة، أو `text` لأجزاء محتواها) ويقوم بتشغيل كاشف محرك Caveman (`detectCompressionLanguage()`) عليه. يقوم الكاشف بإرجاع `zh` للنص الذي يحتوي على أحرف هان ولا يوجد كانا؛ وإلا فإنه يُرجع أيًا من `it` و `pt-BR` `es` و `de` و `fr` و `ru` و `ja` و `hu` و `id` الذي يحتوي على أكبر عدد من تطابقات التلميحات، و `en` عندما لا يتطابق أي شيء مع نص — فإنه لا يمكن تصنيفه يحصل على اللغة الإنجليزية، ولا يتم `defaultLanguage` أبدًا، ولا يتم اكتشاف `vi` أبدًا على الرغم من أن الأنماط تشحن نص `vi`. يحتفظ جسم الاستجابة API بدوراته في `input`، والتي لم يتم أخذ عينات منها، لذلك يصبح `defaultLanguage`، ثم الإنجليزية. عندما لا تحتوي أي رسالة مستخدم في `messages` على نص، أو مع إيقاف تشغيل `autoDetect` ، يتم تطبيق `defaultLanguage` ، ثم الإنجليزية. مع إيقاف تشغيل `languageConfig.enabled` ، تكون اللغة هي الإنجليزية — ما لم يتم تطبيق مجموعة التحرير والسرد المضغوطة على الطلب (مجموعة التحرير والسرد المخصصة لمجموعة التحرير والسرد الخاصة بالطلب، أو مجموعة التحرير والسرد الافتراضية chatCore التي ترجع إلى خط الأنابيب المكدس المدمج): يؤدي تطبيق التحرير والسرد إلى تشغيل `languageConfig.enabled` لهذا الطلب وتعيين `defaultLanguage` من حزم لغات التحرير والسرد (القيمة المحفوظة إذا كانت إحدى حزم التحرير والسرد، وإلا فإن الحزمة الأولى للتحرير والسرد، والتي الافتراضي هو `en`) ، في حين أن `autoDetect` المحفوظ (تشغيل افتراضيًا) لا يزال ساريًا. يختار محرك الإدخال Caveman لغة حزمة القواعد الخاصة به بشكل مختلف — لكل جزء من النص، ومع إيقاف الاكتشاف التلقائي، يتم وضع بوابة على `enabledPacks`.

يتم تثبيت مصفوفة لغة النمط × بواسطة `tests/unit/compression/output-styles-i18n-matrix.test.ts`: يحتاج كل نمط كتالوج إلى إدخال في `BASELINE_LANGUAGES` الخاص بالاختبار؛ يجب أن يشحن النمط الذي لم يتم تحديده محليًا ترجمة pt-BR (يتم استثناء `terse-cjk` من هذه القاعدة) ما لم يكن مدرجًا في `KNOWN_ENGLISH_ONLY`، والذي قد يحتفظ فقط بالأنماط التي لا تحتوي على ترجمات على الإطلاق — ويفشل النمط المدرج الذي يحتوي على أي ترجمة في الاختبار؛ ويفشل النمط في الاختبار عندما يفقد اللغة التي يسردها إدخال `BASELINE_LANGUAGES` الخاص به. لإضافة نمط، راجع [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### أداة ضغط النتيجة

`compressToolResult()` في `open-sse/services/compression/toolResultCompressor.ts` يضغط نص نتيجة الأداة باستخدام** 5 استراتيجيات** . يتم تجربتها بهذا الترتيب، وتقرر الإستراتيجية الممكّنة الأولى التي يتطابق فحصها مع المحتوى النتيجة:

1. **`fileContent`** : محتوى من 3 أسطر أو أكثر يبدأ فيه سطر واحد على الأقل، مع تجاهل المسافة البادئة، بـ `import ` أو `export ` أو `function ` أو `class ` أو `const ` أو `let ` أو `var ` أو `return ` (الكلمة الأساسية بالإضافة إلى مسافة)، أو بـ `if` أو `for` أو `while` متبوعًا بـ `(` أو ` (`، ويحتفظ بأول 20 أسطرًا وآخر 5 أسطر، مع تحديد الوسط المحذوف.
2. **`grepSearch`** : محتوى يحتوي على سطر واحد على الأقل من النموذج `<path>:<digits>:`، حيث لا يحتوي النص الموجود قبل النقطتين الأولتين على مسافة بيضاء، ويحتفظ بهذه الأسطر فقط، بحد أقصى 30، متبوعًا بعدد أي تطابقات أخرى وقائمة الملفات المطابقة؛ يتم إسقاط كل سطر آخر. يكفي أحد هذه الأسطر لتفعيل الإستراتيجية، لذا فإن سطر السجل الذي يبدأ بطابع زمني مثل `12:30:45` يتم احتسابه أيضًا.
3. **`shellOutput`** : الإخراج الذي يحتوي على تسلسل ANSI CSI (`ESC[` ثم أرقام أو فواصل منقوطة ثم حرف، كما في رموز الألوان) أو `$` متبوعًا بمسافة بيضاء في أي مكان في النص يفقد تلك التسلسلات (يتم الاحتفاظ برموز الهروب الأخرى، مثل `ESC[?25l` أو تسلسل عنوان نافذة OSC ) ويحتفظ بآخر 50 سطرًا، مع طي الأسطر المتكررة المتتالية. نظرًا لأن هذا الفحص يتم تشغيله قبل `json` و `errorMessage`، JSON أو إخراج الخطأ الذي يحتوي على مثل هذا `$` لا يصل إليهم أبدًا أثناء تشغيل `shellOutput`.
4. **`json`** : حمولة JSON تزيد عن 2000 حرف تبدأ بـ `{` أو `[` (بعد مسافة بيضاء اختيارية) ويتم تلخيص التحليلات: تحتفظ مصفوفة مكونة من أكثر من 7 عناصر بأول 5 عناصر وآخر عنصرين وعددها الإجمالي، ويحتفظ الكائن بأول 20 مفتاحًا له، مع استبدال كل كائن متداخل أو قيمة صفيف بعنصر نائب `{…N keys}` (بالنسبة للمصفوفة، N هو طوله) وعلامة `_remaining_<N>_keys` تحسب المفاتيح التي تم إسقاطها بعد أول 20 مفتاحًا. يتم نسخ القيم العددية بالكامل، لذا فإن الكائن الذي يحتوي على 20 مفتاحًا أو أقل بدون قيم متداخلة يتم إعادة المسافة البادئة — فقط، بينما يكتسب الكائن المصغر الأحرف ويبقى دون تغيير.
5. **`errorMessage`** : الإخراج الذي يحتوي، في أي مكان وفي أي حالة حرف، `error:` أو `error ` (الكلمة متبوعة بمسافة، كما في `no error found`) أو `[error]` أو `exception:` أو `exception ` أو `[exception]` أو `traceback` يحتفظ بالسطر الأول، والأسطر العشرة التالية وآخر ثلاثة، مع علامة `… [N frames elided] …` بدلاً من الخطوط بينهما. تظهر العلامة فقط عندما يتبع السطر الأول أكثر من 13 سطرًا، لذلك لا يتم تقصير ناتج الخطأ البالغ 14 سطرًا أو أقل (عند 12 أو 13 سطرًا، تم الاحتفاظ بآخر 3 أسطر مكررة بالفعل).

بعد تطابق الإستراتيجية، حتى تلك التي لا توفر شيئًا، لا يتم تجربة الاستراتيجيات اللاحقة. عندما لا تحفظ استراتيجية المطابقة أي رموز مميزة (الطول ÷ 4، مقرب لأعلى) — على سبيل المثال ملف يشبه التعليمات البرمجية يتكون من 25 سطرًا أو أقل، أو مصفوفة JSON تزيد عن 2000 حرف مع 7 عناصر أو أقل — يحتفظ المحرك العدواني بنتيجة الأداة الأصلية: يحتفظ كلا المتصلين (`compressAggressive()` و `compressAnthropicToolResultBlock()`) بالأصل عندما تكون `saved` 0 أو أقل، بينما لا يزال `compressToolResult()` نفسه يُرجع مخرجات تلك الإستراتيجية. خطوة الأداة والنتيجة ليست الكلمة الأخيرة: لا يزال بإمكان الملخص الاحتياطي للمحرك تقصير رسالة `tool` أو `function` أطول من 8192 حرفًا (`maxTokensPerMessage`، 2048، ضرب 4).

#### متى تستخدم

يعد ضغط نتيجة الأداة هو الخطوة الأولى للمحرك العدواني (`compressAggressive()` في `open-sse/services/compression/aggressive.ts`)، لذلك يتم تشغيله في الوضع العدواني وفي خطوة `aggressive` لخط أنابيب مكدس. يقوم بضغط رسائل `tool` و `function` ذات شكل OpenAI والنص الموجود داخل كتل Anthropic `tool_result`. كل استراتيجية لها مفتاحها الخاص تحت `aggressive.toolStrategies`، كل ذلك يتم تشغيله بشكل افتراضي. في لوحة المعلومات، توجد المفاتيح في صفحة رجل الكهف** متقدم** عرض أثناء تشغيل الضغط ويكون الوضع الافتراضي عدوانيًا.

### خط أنابيب مكدس

يتم تشغيل الوضع المكدس** محركات متعددة بالتسلسل** — عادةً RTK أولاً (توفير 60-90% في مخرجات الأداة)، ثم Caveman على النص المتبقي (توفير إدخال 46%~). تتألف، وهذا هو** نطاق مؤهل 78-95%** (انظر رياضيات التوفير الأولية أعلاه): يبلغ متوسط `1 - (1 - 0.60..0.90) × (1 - 0.46)` ≈ 89%.

#### كيف يعمل

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

استخدم الوضع المكدس من أجل:

- سير العمل المثقل بالأدوات (الترميز الوكيل والبحث)
- معالجة الدفعات الحساسة للتكلفة
- عندما تحتاج إلى الحد الأقصى من المدخرات الرمزية

يتم تكوين خطوط الأنابيب المكدسة من خلال إعداد ضغط `stackedPipeline` العام، أو من خلال مجموعة ضغط مسماة تم تعيينها لمجموعة تحرير وسرد توجيه (انظر تجاوز لكل مجموعة كومبو أعلاه) — وليس من خلال مجموعة التحرير والسرد التلقائية `modePack` (يعيد هذا الحقل فقط ترجيح اختيار نموذج التحرير والسرد التلقائي، و `stacked` ليس اسم حزمة صالحًا).

---

## تجاوزات مجموعة الضغط

يمكنك تجاوز وضع الضغط العام **لكل مجموعة على حدة** لضبط السلوك بدقة
لحالات الاستخدام المختلفة:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

هذا مفيد لما يلي:

- **مجموعات البرمجة**: استخدم وضع `aggressive` للجلسات الطويلة
- **مجموعات الأسئلة والأجوبة السريعة**: استخدم وضع `lite` للحصول على استجابات سريعة
- **المجموعات كثيفة استخدام الأدوات**: استخدم وضع `stacked` لتحقيق أقصى قدر من التوفير
- **مجموعات الإنتاج**: اترك التجاوز معطّلًا لموفري التخزين المؤقت — إذ يعمل التعديل
  المدرك للتخزين المؤقت دائمًا على خفض `aggressive`/`ultra` إلى `standard` تلقائيًا
  (لا يوجد وضع `cache-aware` قابل للتحديد)
