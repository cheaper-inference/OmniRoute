استخدم هذا الدليل لاختيار أصغر دورة تطوير موثوقة لطلب سحب. وهو لا يحل محل مستندات البنية والأمان الخاصة بكل مجال والمرتبطة أدناه؛ بل يربط كل نوع شائع من التغييرات بعقوده وفحوصاته المركّزة وتغطية CI الخاصة به.

## المسار الذي يتبعه كل تغيير

1. **اختر الفرع الأساسي قبل التعديل.** ابحث عن أعلى فرع نشط من `release/v*` وأنشئ فرعك من أحدث نقطة فيه. استهدف ذلك الفرع، وليس `main`. إذا كان تجميد الإصدار نشطًا، فلا تستهدف الفرع المجمّد؛ استخدم دورة الإصدار النشطة التالية الموضحة في
   [نموذج التفريع والإصدار](BRANCHING_MODEL.md).
2. **حدّد العقود.** حدّد كل كتالوج أو مخطط أو عنصر مُنشأ أو API عام أو واجهة مستخدم يتأثر بها التغيير. يوضّح الجدول أدناه الحد الأدنى لمجموعة البداية.
3. **اكتب الاختبارات المركّزة أو حدّثها.** تتطلب تغييرات الإنتاج في `src/` أو `open-sse/` أو `electron/` أو
   `bin/` اختبارًا آليًا في طلب السحب نفسه. شغّل أصغر مجموعة من ملفات الاختبار التي تثبت السلوك، ثم بوابات التحقق المركّزة المدرجة.
4. **دع CI يشغّل المصفوفة الشاملة.** تُشغَّل في طلب السحب جميع أجزاء اختبارات الوحدة وVitest وآلية الرفع التدريجي للتغطية وبناء الإنتاج. لا تشغّل مجموعة واسعة محليًا إلا عندما يشير فشل مركّز إلى تأثير أوسع، أو عندما يمتد التغيير عبر عدة أنظمة فرعية.
5. **وفّق التغييرات قبل المراجعة.** اجلب الفرع الأساسي النشط، وافحص الالتزامات الجديدة فيه والفروقات الخاصة بك مقارنةً به، ثم نفّذ إعادة تأسيس للفرع أو ادمج الفرع الأساسي وفقًا لسير عمل المساهمين. عالج تعارضات الملفات المُنشأة والكتالوجات من مصادرها، ثم أعِد إنشاءها، وأعِد تشغيل الدورة المركّزة، وتأكد من أن طلب السحب لا يزال يستهدف فرع الإصدار النشط.
6. **سجّل الأدلة.** في قالب طلب السحب، أدرج الأوامر التي شغّلتها، وكل ملف اختبار أضفته أو غيّرته، وعمليات الترحيل أو علامات الميزات، وأي تحقق يقتصر على CI ولا يزال معلقًا.

## المسارات المثالية حسب نوع التغيير

الأوامر أدناه هي الحد الأدنى من الفحوصات المركّزة، وليست إذنًا بتخطي اختبار يغطي مباشرةً السلوك الذي غيّرته.

### المزوّد

**العقود**

- تعريف المزوّد في `src/shared/constants/providers/` ودمجه في
  `src/shared/constants/providers.ts`.
- النماذج والإمكانات في `open-sse/config/providerRegistry.ts` أو ملفات السجل المستخرجة منه.
- اختيار المنفّذ/المترجم، وإعداد OAuth أو مفتاح API، وأصول لوحة المعلومات، والمرجع المُنشأ للمزوّد عند الاقتضاء.
- يجب أن تستخدم بيانات الاعتماد العامة `resolvePublicCred()`، ويجب أن تستخدم استجابات الأخطاء أدوات الأخطاء المشتركة والمنقّحة. راجع `docs/security/PUBLIC_CREDS.md` (ضمن git؛ لا يُضمَّن في `/docs`) و
  [تنقيح الأخطاء](../security/ERROR_SANITIZATION.md).

**الدورة المركّزة**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # عند تغيير الكتالوج؛ ثبّت الفروقات المُنشأة
npm run lint
```

اختبر أيضًا كل عائلة طلبات متأثرة: المحادثة أو Responses أو الصور أو التضمينات أو الصوت أو الفيديو.
راجع فروقات الكتالوج المُنشأ والاختبارات المرجعية بوصفها تغييرات في العقود؛ ولا تقبلها دون تدقيق.

### التوجيه

**العقود**

- قيم الاستراتيجيات العامة وبيانات واجهة المستخدم الوصفية في `src/shared/constants/routingStrategies.ts`.
- الإرسال والترتيب ضمن `open-sse/services/combo.ts` و`open-sse/services/combo/`.
- مخططات Combo والتخزين الدائم وحالة المرونة وإمكانات النماذج وعناصر التحكم في API/واجهة المستخدم.
- [محرك Auto-Combo](../routing/AUTO-COMBO.md) ووثائق المرونة عند تغير السلوك.

**الدورة المركّزة**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # تغييرات الاستراتيجية أو الإرسال
npm run check:known-symbols      # تغييرات تسجيل الاستراتيجية
npm run lint
```

استخدم محليًا اختبارات حتمية تحاكي الخدمات المصدرية. تتطلب اختبارات Combo المباشرة السريعة بيانات اعتماد، وهي يدوية وليست بدائل لـ CI.

### واجهة المستخدم / تجربة المستخدم

**العقود**

- حدود المسار/الصفحة في Next.js والمكوّنات المشتركة ضمن `src/app/` و
  `src/shared/components/`.
- أشكال استجابات API، وحالات التحميل/الفراغ/الخطأ، وسلوك لوحة المفاتيح وقارئ الشاشة، والتخطيط المتجاوب، والسمات، وتوسيع اللغات.
- سلاسل واجهة المستخدم الإنجليزية المصدرية في `src/i18n/messages/en.json`؛ لا تُضمّن نصوصًا جديدة موجهة للمستخدم مباشرةً في الشفرة.

**الدورة المركّزة**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

شغّل التطبيق عند إجراء تغييرات تفاعلية أو مرئية، وتحقق من إطارات العرض الضيقة والواسعة. يشغّل CI بناء الإنتاج ومجموعات الاختبار الأوسع؛ ومع ذلك، لا يزال السلوك المرئي يحتاج إلى فحص مركّز مناسب للتغيير، سواء كان اختبار مكوّن أو Playwright أو فحصًا يدويًا موثقًا.

### التدويل

**العقود**

- `src/i18n/messages/en.json` هو مصدر واجهة المستخدم؛ و`config/i18n.json` هو مصدر اللغات.
- توجد كتالوجات CLI بشكل منفصل ضمن `bin/cli/locales/`.
- حافظ على العناصر النائبة والوسوم في ICU كما هي تمامًا. لا تترجم أسماء المنتجات/المزوّدين/النماذج، أو أسماء البروتوكولات والترويسات، أو الأوامر، أو معرّفات الشفرة/JSON، أو عناوين URL، أو متغيرات البيئة، أو المصطلحات المحمية مثل `OmniRoute` و`OAuth` و`MCP` و`A2A`. قائمة المصدر الحالية هي
  `scripts/i18n/glossary/protected-terms.json`.

**الدورة المركّزة**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # عند تغيير سلاسل/كتالوجات CLI
npm run lint
```

هذه إرشادات للنظام الحالي، وليست دعوة إلى توسيع أدواته أو نموذج مفاتيحه.
أبقِ تصحيحات التدويل محددة النطاق بينما يجري تصميم النظام البديل. لا تشغّل أوامر الترجمة التي تستدعي خدمات خارجية إلا إذا كانت المهمة تتطلب صراحةً ترجمات مُنشأة وكنت قد راجعت الفروقات الناتجة.

### واجهة سطر الأوامر

**العقود**

- الأوامر العامة والخيارات في `bin/cli/`، وأوامر API المُنشأة، ورموز الخروج، وstdout/stderr، وبُنى مخرجات
  JSON، وسلوك الإعدادات/البيئة، والملفات المضمّنة في الحزمة.
- يجب أن تستخدم السلاسل النصية الظاهرة للمستخدم في CLI طبقة التدويل i18n الخاصة بـCLI، مع إبقاء كتالوجَي `en`/`pt-BR` متوافقين.
- حافظ على Node بوصفه بيئة التشغيل المدعومة وعلى عقد الملف التنفيذي المنشور.

**حلقة العمل المركّزة**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # تغييرات CLI المُنشأة/المجمّعة
npm run check:pack-policy     # تغييرات السطح العام للحزمة
npm run lint
```

استخدم الأمر نفسه تمامًا داخل دليل بيانات مؤقت عندما يعتمد السلوك على التحليل أو الملفات أو حالة
الخروج. ينفّذ CI فحوصات أوسع لعناصر الحزمة والنظام البيئي.

### قاعدة البيانات

**العقود**

- توجد وحدات المجال ضمن `src/lib/db/`؛ استورد وحدات محددة مباشرةً (أُزيلت طبقة إعادة التصدير القديمة `localDb.ts`).
- ترحيلات SQL مرقّمة ومتكررة التنفيذ بأمان ضمن `src/lib/db/migrations/`، مع مراعاة سلامة المعاملات، وسلوك
  الترقية، والفهارس، وكل مستدعٍ يتأثر بالمخطط.
- لا تُصدر المسارات والمعالجات استعلامات SQL خامًا بشكل مباشر.

**حلقة العمل المركّزة**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

اختبر كلاً من قاعدة بيانات جديدة والترقية من المخطط السابق عند إضافة ترحيل. يجب على اختبارات قاعدة البيانات
إغلاق المقابض واستدعاء `resetDbInstance()` أثناء التنظيف. شغّل `npm run test:bun:db` فقط عندما
يتغير مسار محوّل Bun الذي يعمل وفق مبدأ أفضل جهد ممكن؛ وتبقى Node المرجع المعتمد.

### البناء / النشر

**العقود**

- ملفات التعريف/القفل في الجذر ومساحة العمل، و`scripts/build/`، وتجميع Next.js المستقل، ومحتويات حزمة `dist/`،
  وبيانات Electron الوصفية الخاصة بالمنصات، ومسارات عمل CI، ومؤشرات النشر.
- يجب الحفاظ على نطاقات Node المدعومة واستخدام Bun المدرج في قائمة السماح في `CLAUDE.md`.
- تظل نواتج البناء خارج التتبع؛ وتُطبَّق سياسات التبعيات والتراخيص ومسارات العمل والحزم.

**حلقة العمل المركّزة**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # تغييرات التبعيات أو ملف القفل
npm run check:pack-policy      # تغييرات السطح العام للحزمة المنشورة
npm run lint
```

استخدم `npm run build` محليًا فقط عندما يؤثر التغيير على الترجمة البرمجية أو التجميع المستقل أو الأصول
أو تجميع وقت التشغيل. استخدم `npm run build:release` فقط للتحقق من الإصدار/النشر. يُعد بناء CI
المؤشر النهائي العابر للمنصات؛ وتتطلب تغييرات Electron الخاصة بمنصة معينة دليلاً من البناء المركّز المطابق
أو من اختبار تمهيدي.

## نصوص المطوّرين لجهاز مشترك

تُجسّد أداتا `scripts/dev/` المساعدتان حلقة العمل المحلية على جهاز تطوير تكون عليه جلسات أخرى نشطة:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # الملفات من merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # هذه الملفات تحديدًا
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # شجرة عمل معزولة وآمنة للتشغيل المتوازي
```

- يجري `typecheck-touched.sh` التحقق من الأنواع لملفات `.ts/.tsx` التي تم تعديلها فقط، من خلال ملف
  `tsconfig.touched.tmp.json` مؤقت (`extends ./tsconfig.json`، و`types: ["node"]`، و`noEmit`،
  و`incremental: false`) ضمن ذاكرة كومة بحجم 6 GB، ولذلك فهو يحل محل `tsc -p tsconfig.json`
  على مستوى المشروع، الذي يتسبب في OOM على جهاز محمّل. ويطبع الأخطاء الموجودة في الملفات المعدّلة
  بالإضافة إلى سطر ملخص واحد، وينهي التنفيذ بالرمز `1` عند وجود أخطاء في الملفات المعدّلة، وبالرمز
  `2` عندما تكون الأخطاء الوحيدة في الملفات المستوردة أو عندما يتوقف tsc دون تشخيصات
  (اقرأ السجل الذي يذكره ضمن `_artifacts/typecheck-touched/`)، وبالرمز `0` عندما لا توجد
  أخطاء. ويُحذف ملف tsconfig المؤقت دائمًا؛ لا تقم أبدًا بإيداعه.
- يجعل `new-worktree.sh` عمليات التشغيل المتزامنة تسلسلية باستخدام `<git-common-dir>/omniroute-new-worktree.lock`
  (ينتظر حتى 600 s افتراضيًا، مع عرض رسالة واضحة؛ وتوثّق ترويسة النص البرمجي كيفية
  تجاوز ذلك)، كما يتراجع عن
  الفرع الذي أنشأه عندما يفشل `git worktree add` قبل وجود شجرة العمل، بحيث لا تتطلب إعادة المحاولة
  تنفيذ `git branch -D` يدويًا. وتظل الروابط الصلبة لـ`node_modules` ونسخة `.husky/_` دون تغيير.

## حلقة المرشح المحلية

لا يمكن لاختبارات المصدر إثبات أن الحزمة المنشأة ستبدأ بنجاح: فقوائم التحزيم، والتبعيات المشذّبة،
والملفات الثنائية الأصلية لا تفشل إلا بعد تثبيت ملف tarball وتشغيله. يمثّل `npm run dev:candidate`
‏(`scripts/dev/candidate.mjs`) الجانب المحلي من تدفق البناء مرة واحدة / التحقق / الترقية الوارد في
RFC #8084: فهو يبني مرشحًا واحدًا، ويتحقق من تلك الحزمة نفسها، ويرقّيها عبر إعادة تسمية
المجلدات، ويتراجع عنها عندما تفشل خانة الترقية في فحص السلامة.

```bash
npm run dev:candidate -- run --dry-run --json  # اطبع الخطة دون تغيير أي شيء
npm run dev:candidate -- run                   # ابنِ + تحقّق + رقِّ، مع تراجع تلقائي
npm run dev:candidate -- build                 # نفّذ npm pack + ثبّت في _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # شغّل على منفذ متاح، /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current، وcurrent → previous
npm run dev:candidate -- rollback              # بدّل current وprevious
npm run dev:candidate -- run --from-tarball <file.tgz>  # أعد استخدام ملف tarball بُني في مكان آخر (CI)
```

- **ابنِ مرة واحدة.** يحزّم `build` الشجرة الحالية (يحتاج إلى `dist/server.js`، لذا شغّل
  `npm run build:release` أولًا) أو ينسخ `--from-tarball`، ثم يثبّت ملف tarball في
  بادئة npm معزولة، لأن ملف tarball لا يتضمن `node_modules`. يكون المعرّف هو sha المختصر لـ`HEAD`
  (مع `-dirty` عندما تحتوي الشجرة على تغييرات محلية) أو `tgz-<sha256>` لملف tarball. ويُعاد استخدام
  المعرّف النظيف المبني مسبقًا بدلًا من إعادة بنائه؛ مرّر `--force` لإعادة بنائه.
- **تحقّق من الحزمة، لا من المصدر.** يشغّل `validate` واجهة CLI المثبّتة
  (`serve --port <free port>`) باستخدام `DATA_DIR=<candidate>/data` جديد وأسرار وهمية، مع إزالة
  `OMNIROUTE_API_KEY` و`STORAGE_ENCRYPTION_KEY` و`INITIAL_PASSWORD` الخاصة بالمشغّل من
  البيئة، بحيث يتحقق من وضع الاسترجاع المحلي بلا مفاتيح في تثبيت جديد. وينتظر حتى يعيد
  `GET /api/health` الحالة 200، ويشترط أن يعيد `GET /v1/models` الحالة 200، ثم يوقف مجموعة العمليات،
  ويسجل النتيجة في `validation.json` مع تجزئة ملف tarball.
- **رقِّ الحزمة نفسها.** يرفض `promote` أي مرشح لا يملك تحققًا ناجحًا لتجزئة
  ملف tarball الحالية الخاصة به. خانة التشغيل النشطة الافتراضية هي `_artifacts/candidate/current`؛ ويحدد `--target <dir>`
  مجلدًا آخر على نظام الملفات نفسه، وتكون خانته السابقة هي `<dir>.previous`.
  كل عملية إعادة تسمية ذرّية، وأي فشل في منتصف العملية يعكس عمليات إعادة التسمية التي نُفذت بالفعل.
- **تراجع.** يعيد `run` التحقق من خانة الترقية، ثم يبدّل `current` و`previous` مجددًا عندما
  يفشل ذلك الفحص. ولا تتم أبدًا ترقية مرشح يفشل في التحقق الأول.

يُكتب كل شيء ضمن `_artifacts/candidate/` المتجاهَل من git؛ ولا يتم أبدًا المساس بتثبيت OmniRoute
حالي أو بمجلد بياناته. توجد واجهة CLI التي تمت ترقيتها في
`_artifacts/candidate/current/prefix/bin/omniroute`؛ شغّلها باستخدام `DATA_DIR` الخاص بك عندما
تستخدمها. رموز الخروج: `0` للنجاح، و`1` لفشل التحقق أو الترقية، و`2` لخطأ في الاستخدام أو لغياب البناء.

## الحلقة المحلية مقابل CI

| التشغيل محليًا لكل تصحيح                                                  | يوفّر CI الإشارة الشاملة                                           |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| اختبارات السلوك المباشرة وبوابات الفئات المذكورة أعلاه                    | مجموعة اختبارات الوحدة الكاملة المقسّمة واختبارات التنفيذ التسلسلي |
| `npm run lint`                                                            | مجموعات Vitest وآليات الرفع التدريجي لتغطية الاختبارات والجودة     |
| فحص الأنواع أو البناء فقط عندما يتطلب العقد المتأثر ذلك                   | بناء الإنتاج وبوابات الأمان والتوثيق والتبعيات وسياسات طلبات السحب |
| التفاعل اليدوي/الفحوصات المباشرة فقط عندما يتعذر على الأتمتة إثبات السلوك | فحوصات التكامل بين المهام والمنصات المضبوطة بواسطة سير العمل       |

تُعد الحلقة المركّزة الناجحة دليلًا على صحة العقد الذي تم تغييره، وليست إثباتًا على أن فحوصات CI غير المرتبطة
ستنجح. وفي المقابل، لا تجعل كل تعديل محلي ينتظر مصفوفة المستودع الكاملة.

## قائمة التحقق من المزامنة

قبل طلب المراجعة:

- تأكد من أن أساس طلب السحب لا يزال أعلى فرع نشط من فروع `release/v*`.
- اجلب ذلك الأساس وراجع الالتزامات التي أُضيفت منذ إنشاء فرعك.
- راجع `git diff <active-base>...HEAD` بحثًا عن تغييرات عرضية أو مولّدة.
- حلّ تعارضات الفهرس والمستندات المولّدة عبر تحديث المصدر وإعادة توليد المخرجات.
- أعد تشغيل كل اختبار/بوابة مركّزة مدرجة في وصف طلب السحب بعد المزامنة.
- لا تُضعف التأكيدات أو تحذف الاختبارات المطلوبة لمجرد التوافق مع أساس تغيّر موضعه.

للاطلاع على قواعد تجميد الإصدار وإعادة الاستهداف، استخدم
[نموذج التفريع والإصدار](BRANCHING_MODEL.md). وللاطلاع على القائمة الكاملة لفحوصات CI، استخدم
[مرجع بوابات الجودة](../architecture/QUALITY_GATES.md).
