> **باختصار**: يستخدم OmniRoute قاعدة **SQLite مع تسجيل WAL** كمخزن أساسي، مع تشفير **AES-256-GCM** للحقول الحساسة في أثناء التخزين. يغطي هذا الدليل المخطط، وعمليات الترحيل، والنسخ الاحتياطي/الاسترداد، وأدلة التشغيل.

**المصادر:**

- `src/lib/db/core.ts` — نسخة مفردة + SCHEMA_SQL ‏(17 جدولًا أساسيًا)
- `src/lib/db/migrationRunner.ts` — عمليات ترحيل ذات إصدارات
- `src/lib/db/migrations/` — 167 ملف SQL ذا إصدار
- `src/lib/db/encryption.ts` — دوال مساعدة للتشفير
- `src/lib/db/backup.ts` — تصدير/استيراد النسخ الاحتياطية
- `src/lib/db/healthCheck.ts` — تشخيصات السلامة

## لماذا SQLite؟

اختار OmniRoute قاعدة SQLite بدلًا من PostgreSQL/MySQL لعدة أسباب:

| العامل              | SQLite                             | PostgreSQL                            |
| ------------------- | ---------------------------------- | ------------------------------------- |
| **النشر**           | مضمّنة — لا تتطلب خادمًا منفصلًا   | تتطلب إعداد خادم                      |
| **التشفير**         | على مستوى التطبيق (AES-256-GCM)    | تشفير TDE مدمج                        |
| **الأداء**          | أسرع لأحمال العمل الصغيرة/المتوسطة | أفضل لعمليات الكتابة المتزامنة الضخمة |
| **التزامن**         | يسمح وضع WAL بعمليات قراءة متزامنة | دعم MVCC كامل                         |
| **النسخ الاحتياطي** | نسخ ملف واحد                       | `pg_dump` أو لقطة لنظام الملفات       |
| **حالة الاستخدام**  | تثبيت لكل مستخدم، ومضمّنة          | خدمة SaaS متعددة المستأجرين           |

بالنسبة إلى عمليات النشر ذات **المستخدم الواحد والنسخة الواحدة** (حالة الاستخدام الأساسية لـ OmniRoute)، تكون SQLite أبسط وأسرع.

### تسجيل WAL

يفتح `core.ts` قاعدة البيانات باستخدام **وضع WAL (التسجيل المسبق للكتابة)**:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

يسمح WAL بإجراء **عمليات قراءة متزامنة** في أثناء عمليات الكتابة — وهذا مهم للوحة المعلومات التي تُجري الاستعلامات في أثناء تسجيل الطلبات.

الحجم الافتراضي لذاكرة التخزين المؤقت هو **65,536 KiB (64 MiB)**. تفسّر SQLite قيمة
`cache_size` السالبة بوصفها حدًا أعلى تقريبيًا بوحدة KiB، وتخصص الصفحات عند الطلب.
يقبل إعداد **الإعدادات > النظام والتخزين > حجم ذاكرة التخزين المؤقت** قيمًا صحيحة من **1 إلى
1,000,000 KiB**؛ ويؤدي حفظ الإعداد إلى تطبيقه على اتصال قاعدة البيانات النشط،
كما يستعيد OmniRoute القيمة المحفوظة عند بدء التشغيل.

## موقع قاعدة البيانات

يُخزَّن ملف SQLite في:

| نظام التشغيل | المسار                                                   |
| ------------ | -------------------------------------------------------- |
| Linux        | `~/.omniroute/storage.sqlite`                            |
| macOS        | `~/.omniroute/storage.sqlite`                            |
| Windows      | `%USERPROFILE%\.omniroute\storage.sqlite`                |
| Docker       | `/app/data/storage.sqlite` (قابل للتهيئة عبر `DATA_DIR`) |

الملفات المصاحبة:

- `storage.sqlite-wal` — سجل الكتابة المسبقة
- `storage.sqlite-shm` — ملف الذاكرة المشتركة
- `call_logs/` — عناصر حمولات الطلبات (إذا كانت مفعّلة)

**لتجاوز الموقع:**

```bash
DATA_DIR=/custom/path omniroute
```

## الهجرات

يستخدم OmniRoute** إصدارات، الهجرات العاجزة** في `src/lib/db/migrations/`. كل عملية ترحيل عبارة عن ملف SQL واحد. يتعايش تنسيقان للتسمية؛ الإصدار المسجل في `_omniroute_migrations` هو البادئة الرقمية.

### تسمية الهجرة

| شكل                                              | مثال                                 | تستخدم ل                                                                                                                                      |
| ------------------------------------------------ | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (3 أرقام بالضبط)           | `241_seen_models.sql`                | المسلسل القديم `001`–`241`. تم تجميده عند وصول تنسيق الطابع الزمني (تم دمج `240` و `241` قبل ذلك مباشرة): لا يحصل أي ملف جديد على رقم تسلسلي. |
| `YYYYMMDDHHMMSS_description.sql` (14 رقمًا، UTC) | `20261113120000_add_usage_index.sql` | تم إنشاء كل عملية ترحيل اعتبارًا من 13-11-2026 فصاعدًا.                                                                                       |

سبب التغيير: مع الأرقام التسلسلية، اختارت PRs الموازية نفس الرقم التالي وكان يجب إعادة ترقيم الجميع باستثناء رقم واحد قبل الدمج. يعطي الطابع الزمني UTC لكل PR نسخته الخاصة.

قواعد تنسيق الطابع الزمني (يتم فرضها بواسطة `npm run check:migration-numbering`، ومشاركتها مع المولد في `scripts/check/lib/migrationNaming.mjs`):

- الطابع الزمني هو تاريخ ووقت UTC حقيقي، وليس قبل `20261113000000` وليس أكثر من 10 دقائق في المستقبل.
- الوصف هو `snake_case` صغير يبدأ بحرف (`a-z`، `0-9`، `_` مفرد بين الكلمات)، بحد أقصى 80 حرفًا.
- هناك ملفان لهما نفس الطابع الزمني مكرران.
- تنطبق قاعدة عدم وجود فجوة فقط على المتسلسلة القديمة: كل رقم من `001` إلى `241` يجب أن يكون موجودًا، باستثناء الفجوات المعروفة `026` و `055` و `121`. حذف `241` (أو أي ملف قديم) يفشل البوابة. لا يمكن مطلقًا إضافة `001` و `241` إلى القائمة المسموح بها `KNOWN_GAPS`. الملفات ذات الطابع الزمني لا تخلق فجوة أبدًا.
- يجب أن يكون كل إدخال في `src/lib/db/migrations/` ملفًا عاديًا باسم `.sql` صالح بأحرف صغيرة. دليل أو رابط رمزي أو ملف `.SQL` أو `.sql.bak` أو ملف مخفي أو اسم بمسافة يفشل في البوابة، لأن العداء قد يتخطاها بصمت أو يتعطل عند التمهيد.

**تطبيق النظام.** يقوم العداء بالفرز حسب القيمة الرقمية للبادئة، وليس حسب النص: ملفات `001`–`241` القديمة أولاً، ثم الملفات ذات الطابع الزمني بترتيب الطابع الزمني، ثم أي أدلة ذات مساحة أسماء مسجلة باستخدام `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` (إصدارات مثل `ee-001`). الترحيل المعلق هو أي ملف إصداره ليس `_omniroute_migrations`، لذا فإن الترحيل من فرع أقدم يتم دمجه بعد فرع أحدث لا يزال ساريًا على قواعد البيانات الموجودة.

**الطابع الزمني هو أمر الإنشاء، وليس أمر الدمج.** إذا كان الترحيل يعتمد على جدول أو عمود تم إنشاؤه بواسطة الترحيل باستخدام ملف** أحدث** الطابع الزمني (على سبيل المثال، واحد من PR آخر تم دمجه أولاً)، ستعمل قاعدة البيانات الجديدة على تشغيل قاعدة البيانات الخاصة بك أولاً وتفشل. بينما لا يزال PR مفتوحًا، قم بإعادة إنشاء اسم الملف باستخدام `npm run db:new-migration` حتى يحصل على طابع زمني أحدث، أو اجعله مستقلاً. يطبق `npm run test:migrations:fresh` كل عملية ترحيل على قاعدة بيانات فارغة ويلتقط ذلك.

### لا يتم حذف الترحيل المدمج أو إعادة تسميته أبدًا

بمجرد وجود ملف الترحيل على فرع الإصدار أو `main`، يكون قد تم تشغيله بالفعل على قواعد بيانات المتماثلين والمطورين، وعلى عمليات تثبيت VPS وفي مزامنة Enterprise. ومنذ ذلك الحين:

- **لا تحذفه أبدًا.** ستفقد عمليات التثبيت الجديدة مخططها بينما تحتفظ به قواعد البيانات التي تمت ترقيتها.
- **أبدا إعادة تسميته.** لن يتطابق الإصدار الموجود في `_omniroute_migrations` مع الملف بعد الآن، لذا فإن كل قاعدة بيانات طبقته بالفعل ستعمل على تشغيله مرة أخرى. يقوم SQL غير الفعال بتكرار البيانات أو إيقاف التمهيد.
- **هل تحتاج إلى مخطط مختلف؟** قم بإنشاء ترحيل جديد باستخدام `npm run db:new-migration`.

تعتبر إعادة التسمية آمنة فقط للملف الذي لم يتم دمجه بعد، وهي الحالة التي تشير إليها تلميحات البوابة. علامة الإصدار لا تغير شيئًا هنا: كل دفعة إلى فرع `release/v*` تنشر صورة Docker `:next` وتعمل على التماثل، وتثبيتات VPS ومزامنة Enterprise، لذلك يتم تشغيل الترحيل المدمج على قواعد بيانات حقيقية قبل وجود أي علامة `vX.Y.Z`. تفشل البوابة في كل عملية إزالة للملف الأساسي، سواء تم وضع علامة عليه أم لا.

- **التراجع عن الهجرة المدمجة.** `git revert` الذي يحذف الملف يفشل في البوابة. احتفظ بالملف وتراجع عن مخططه في عملية ترحيل جديدة: `npm run db:new-migration -- <description>` و `DROP TABLE IF EXISTS` و `DROP INDEX IF EXISTS` وما إلى ذلك. ثم تنتهي قواعد البيانات التي تمت ترقيتها وجديدة بنفس المخطط.
- **إعادة التسمية المقبولة: إدخال توافق ومحتوى متطابق.** إذا كان يجب نقل ملف مدمج (على سبيل المثال، يشترك ملفان مدمجان في طابع زمني ويتوقف العداء مع تصادم الإصدار)، فأعد تسمية الملف الأحدث دون لمس SQL الخاص به وأضف `{ fromVersion, fromName, toVersion, toName }` إلى `RENAMED_MIGRATION_COMPATIBILITY` في `src/lib/db/migrationRunner/constants.ts`. يتم نقل صف `_omniroute_migrations` الخاص بقواعد البيانات التي طبقت الإصدار القديم بدلاً من تشغيل الملف مرة أخرى. تحذر البوابة من إعادة التسمية هذه وتقوم دائمًا بإجراء فحص التبديل عليها، مهما كان الطابع الزمني الجديد: تقوم عمليات التثبيت الجديدة بتطبيق الملف في موضعه الجديد، ولا تفعل ذلك قواعد البيانات التي تمت ترقيتها، لذا اختر طابعًا زمنيًا جديدًا بالقرب من الطابع القديم. تفشل البوابة في إعادة التسمية إذا تم تغيير المحتوى (لا يزال تغيير المخطط يحدث في عملية ترحيل جديدة)، أو إذا لم يكن الملف الهدف للإدخال موجودًا على القرص.
- **لا تقم أبدًا بإعادة التسمية خلال نفس الطابع الزمني.** إعادة التسمية التي تحافظ على الطابع الزمني وتغير الوصف فقط تفشل البوابة، مع أو بدون إدخال. مع الإدخال الذي `toVersion` يساوي `fromVersion` الخاص به، يحذف العداء صف `_omniroute_migrations` القديم ويطبق الملف مرة أخرى على كل قاعدة بيانات قامت بتشغيله بالفعل. بدون إدخال، يتتبع العداء الإصدار فقط: فهو يتخطى الملف الموجود على قواعد البيانات هذه (المحتوى الجديد لا يعمل هناك أبدًا) ويسجل خطأ إعادة ترقيم في كل عملية تمهيد. استخدم طابعًا زمنيًا آخر بالإضافة إلى إدخال التوافق، أو احتفظ بالاسم.
- **تتحقق البوابة من عدم تشغيل الملف المعاد تسميته مرة أخرى.** لكل عملية إعادة تسمية مغطاة، تقوم البوابة بتمرير اسم الملف الجديد إلى فحص التبديل باستخدام `--must-not-apply`. يقوم الفحص بتمهيد قاعدة البيانات التي تمت ترقيتها باستخدام برنامج التشغيل الحقيقي، وإذا قام برنامج التشغيل بتطبيق هذا الملف مرة أخرى (على سبيل المثال، لأن الإدخال يحتوي على إصدار أو اسم خاطئ، أو لأن محلل نص البوابة يقرأ `constants.ts` بشكل مختلف عن TypeScript)، تفشل البوابة مع `migration renomeada rodaria de novo` وتطلب منك التحقق من الإصدارات والأسماء القديمة والجديدة للإدخال.

### ما تتحقق البوابة ضد القاعدة

عند تشغيل طلب السحب وقائمة انتظار الدمج، يقوم `npm run check:migration-numbering` بمقارنة `src/lib/db/migrations/` الموجود على القرص بنفس الدليل الموجود على الفرع الأساسي. القاعدة هي بهذا الترتيب: `--base-latest-tag` أو `--base <ref>` أو المتغير `MIGRATION_BASE_REF` ، أو عندما يكون `GITHUB_EVENT_NAME` هو `pull_request` أو `pull_request_target` أو `merge_group`، فإن الأصل الأول لالتزام الدمج، أو `merge_group.base_sha` لحمولة الحدث، أو `git merge-base HEAD origin/$GITHUB_BASE_REF`. في طلب السحب أو تشغيل قائمة انتظار الدمج بدون قاعدة قابلة للحل، تفشل البوابة. خارج CI بدون `--base` فإنه يطبع `comparação com a base: pulada (sem --base)` ويتخطى هذه القواعد.

`--base-latest-tag` يقارن بأحدث علامة إصدار (`vX.Y.Z` بترتيب semver؛ العلامات اللاحقة مثل Nightlies لا تحتسب) الموجودة في تاريخ `HEAD`، بنفس القواعد مثل `--base`. يقوم Release-Green (`scripts/quality/validate-release-green.mjs`) بتشغيل البوابة بهذه الطريقة، لأن الدفع وعمليات التشغيل المجدولة ليس لها قاعدة طلب سحب ويمكن أن يتم الدمج بدون تشغيل CI جديد. مع عدم وجود علامة تحرير في التاريخ، تفشل البوابة؛ قم بتشغيل `git fetch --tags` (في CI، `actions/checkout` مع `fetch-depth: 0` يجلب العلامات).

لإجراء نفس المقارنة محليًا، قم بتمرير القاعدة بشكل صريح، على سبيل المثال `npm run check:migration-numbering -- --base origin/<base-branch>` أو `npm run check:migration-numbering -- --base-latest-tag` للمقارنة مع الإصدار الأخير.

### تحويل هجرة PR المفتوحة لـ `NNN`

قد يظل طلب السحب الذي تم فتحه قبل المحول يحمل ملفًا تسلسليًا مثل `242_add_widgets.sql`. تم رفض الأرقام القديمة الموجودة فوق `241` ، لذا قم بتحويلها قبل الدمج:

1. **أعد تسمية الملف باستخدام المولد، مع الاحتفاظ بالوصف.** قم بتشغيل `npm run db:new-migration -- <same description>` للحصول على الاسم الجديد، وانقل SQL إليه، واحذف ملف `NNN_` القديم. يجب أن يظل الوصف متطابقًا: يتطابق معه إدخال التوافق الموجود أدناه.
2. **قم بإضافة إدخال التوافق إذا كانت قاعدة البيانات المستمرة تقوم بتشغيل الرقم القديم.** إذا كانت أي قاعدة بيانات محفوظة (homolog، a VPS، تثبيت خاص بالمساهم) قد قامت بتشغيل إصدار PR باستخدام ملف `NNN_` ، أضف `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` إلى `RENAMED_MIGRATION_COMPATIBILITY` في `src/lib/db/migrationRunner/constants.ts`. هذا هو** مطلوب ل `237` إلى `241`** : تحتوي هذه الفتحات الآن على `237_usage_history_calculated_cost.sql` و `238_codex_connection_fences.sql` و `239_call_logs_pending_detail_index.sql` و `240_provider_node_custom_json_config.sql` و `241_seen_models.sql` الأساسية، وبدون الإدخال، تتخطى قاعدة البيانات هذه الترحيل الأساسي إلى الأبد وتقوم بتشغيل النسخة المحولة مرة أخرى. كما أنه يعمل أيضًا مع الفتحة التي تظل فارغة، مثل `242`، عندما تكون الوجهة عبارة عن طابع زمني. عندما تكون في شك، قم بإضافة الإدخال. لا يهم مكان إضافته في المصفوفة: عندما لا تزال الفتحة المستهدفة للإدخال تحتوي على صف يتحرك إليه إدخال آخر بعيدًا (على سبيل المثال `237` يحتفظ بصف PR بينما ينتظر صف `usage_history_calculated_cost` الأقدم للانتقال إلى `237`) ، يسمح العداء لهذا الإدخال بالانتظار حتى تصبح الفتحة مجانية. فقط التعارض الحقيقي، مثل الفتحة التي يحتفظ بها صف لا يتحرك فيه الإدخال، أو المدخلان اللذان يتبادلان الفتحات، يوقف التمهيد باستخدام `Cannot reconcile ...`.
3. **إبقاء SQL عاجزا** (`CREATE TABLE IF NOT EXISTS`، `CREATE INDEX IF NOT EXISTS`، `INSERT OR IGNORE`)، لأن الترحيل المحول قد يلبي قاعدة بيانات يوجد بها مخططها بالفعل.
4. **نقل الحالات الخاصة ذات المفاتيح الخاصة بالإصدار.** إذا أضافت PR حالة لرقمها القديم في `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) أو في `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`)، فقم بتغيير المفتاح إلى الطابع الزمني الجديد.

`tests/unit/db/codex-fence-migration-rename.test.ts` هو مثال عملي لاختبار الترحيل المُعاد تسميته.

### Backports إلى الفروع قبل التبديل

لا تقم مطلقًا باختيار ملف `YYYYMMDDHHMMSS_` أو نقله مرة أخرى إلى فرع يسبق التبديل (على سبيل المثال، فرع `release/v*` أقدم). يقوم العداء هناك بفرز أسماء الملفات كنص، لذلك سيتم تشغيل ملف ذو طابع زمني بين `201_` و `202_` في قاعدة بيانات جديدة، ولا تفهم البوابة القديمة هناك البادئات المكونة من 14 رقمًا. في مثل هذا الفرع، اكتب التغيير كملف `NNN_` التالي لهذا الفرع، وهو غير فعال، لذا فهو محظور عندما يصل الإصدار ذو الطابع الزمني لاحقًا.

### كيف تجري الهجرات

عند بدء التشغيل، `migrationRunner.ts`:

1. ينشئ جدول `_omniroute_migrations` إذا لم يكن موجودا
2. الاستعلامات عن عمليات الترحيل المطبقة بالفعل
3. يتم تطبيق أي عمليات ترحيل جديدة بالترتيب، كل منها في المعاملة
4. يسجل كل عملية ترحيل مطبقة بالطابع الزمني

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### العجز

يجب أن تكون الهجرات** عاجز** — تشغيلها مرتين يجب أن يكون محظورًا:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

استخدم عبارات `IF NOT EXISTS` و `IF EXISTS` و `OR IGNORE` / `OR REPLACE` بحرية.

### إضافة هجرة جديدة

1. **قم بإنشاء الملف باستخدام المولد** : `npm run db:new-migration -- <description>` (على سبيل المثال `npm run db:new-migration -- add combo priority`). فهو يكتب `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` مع وقت UTC الحالي ورأس التعليق، ويتحرك للأمام ثانية واحدة إذا تم أخذ هذا الطابع الزمني، ولا يقوم بالكتابة فوق الملف مطلقًا. لا تختار رقمًا يدويًا.
2. **استخدم DDL الآمنة** : `CREATE TABLE IF NOT EXISTS`، `CREATE INDEX IF NOT EXISTS`، `ALTER TABLE ... ADD COLUMN`
3. **تعبئة البيانات بعناية** : استخدم `UPDATE ... WHERE ...` للتعامل مع الصفوف الموجودة
4. **التحقق من الطلب والتسمية** : `npm run test:migrations:fresh` (جميع عمليات الترحيل في قاعدة بيانات فارغة) و `npm run check:migration-numbering`
5. **اختبار على نسخة** : لا تقم مطلقًا بتشغيل عمليات الترحيل غير المختبرة على الإنتاج
6. **يحتاج الجدول الذي تم إنشاؤه من التعليمات البرمجية إلى الترحيل أيضًا** : إذا قامت الوحدة أيضًا بإنشاء الجدول بتكاسل (`CREATE TABLE IF NOT EXISTS`، الذي تم الاحتفاظ به كمسار إصلاح ذاتي)، فيجب أن تقوم عملية الترحيل بإنشائه بنفس DDL. وإلا فإن التثبيت النظيف والتثبيت الذي تمت ترقيته سينتهي بمخططات مختلفة، اعتمادًا على ما إذا كان مسار التعليمات البرمجية هذا قد تم تشغيله أم لا. يقوم `tests/unit/db/lazy-table-migration-guard.test.ts` بمسح `src/` و `open-sse/` ويفشل في `CREATE` البطيء بدون ترحيل (#20557). مثال: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

مثال:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **تغييرات غير متوافقة مع الإصدارات السابقة** (على سبيل المثال، إسقاط الأعمدة) صعبة. OmniRoute هل يدعم NOT الرجوع إلى إصدار أقدم — بمجرد تطبيق الترحيل، يكون تغيير المخطط دائمًا. خطط وفقًا لذلك.

## التشفير في حالة السكون

تُشفّر الحقول الحساسة (مفاتيح API، ورموز OAuth، وسلاسل الاتصال) في حالة السكون باستخدام **AES-256-GCM**.

### كيفية عمله

```ts
// src/lib/db/encryption.ts (مبسّط)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### مواضع استخدامه

- `provider_connections.api_key` — مشفّر على مستوى التطبيق
- `provider_connections.access_token`، و`refresh_token`، و`id_token` — مشفّرة على مستوى التطبيق
- إدخالات `key_value` التي تحتوي على `namespace = "secrets"` — مشفّرة على مستوى التطبيق
- `proxy_registry.auth` — مشفّر على مستوى التطبيق (إن وُجد)

### مفتاح التشفير

يُشتق مفتاح التشفير من **عبارة مرور** (تُعيّن عبر متغير البيئة `STORAGE_ENCRYPTION_KEY`) و**قيمة salt** (تُخزّن في قاعدة البيانات). كلاهما مطلوب لفك تشفير البيانات.

```bash
# أنشئ عبارة مرور آمنة
openssl rand -hex 32

# عيّنها في .env
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **مهم للغاية**: فقدان مفتاح التشفير يعني فقدان إمكانية الوصول إلى جميع البيانات المشفّرة. **احتفظ بنسخة احتياطية من المفتاح بشكل منفصل عن قاعدة البيانات**.

### البيانات غير المشفّرة

لأسباب تتعلق بالأداء، تُخزّن البيانات التالية بنص صريح:

- أسماء العرض الخاصة بمزوّدي الخدمة
- تعريفات النماذج (متاحة للعامة بالفعل)
- قواعد التوجيه
- سجلات الاستخدام (لا تحتوي على معلومات تعريف شخصية)

## محاذير التشفير (v3.8.16+)

يستخدم OmniRoute الدالة **`migrateLegacyEncryptedString()`** للتعامل بشفافية مع نظامي تشفير:

- **القديم** (قبل v3.5.0): «تشفير» قائم على XOR (ليس تشفيرًا حقيقيًا)
- **الحالي**: AES-256-GCM مع IV مناسب ووسم مصادقة

تكتشف أداة الترحيل المساعدة التنسيق القديم وتعيد تشفيره باستخدام النظام الجديد عند القراءة الأولى. وهذا يعني أنه يمكنك ترقية قاعدة بيانات قديمة دون فقدان بيانات الاعتماد.

## ضبط الأداء

### وضع WAL

يتم تمكين WAL بشكل افتراضي. بالنسبة لأحمال العمل عالية الكتابة، ضع في اعتبارك ما يلي:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

لم يتم تعيين OmniRoute `journal_size_limit`. تقوم نقطة التفتيش بنقل إطارات WAL إلى الملف الرئيسي، لكن ملف WAL يحتفظ بأكبر حجم مخصص له. حارس `OMNIROUTE_WAL_GUARD_MAX_MB` يحذر فقط ويدير `wal_checkpoint(RESTART)`؛ إنه ليس غطاء بحجم القرص.

### الفهارس

الفهارس الرئيسية للأداء (يتم إنشاؤها تلقائيًا بواسطة عمليات الترحيل):

- عمليات البحث عن نموذج `idx_models_provider` — حسب الموفر
- `idx_combo_targets_combo_id` — والسرد الهدف التوسع
- تحليلات استخدام `idx_usage_history_api_key_timestamp` —
- `idx_quota_snapshots_api_key_window` — تتبع الحصص
- `idx_call_logs_timestamp` — استعلامات سجل المكالمات

لإضافة فهرس جديد، أنشئ عملية ترحيل:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### الذاكرة المعينة I/O

بالنسبة لقواعد البيانات الكبيرة جدًا (> 10 جيجابايت)، يمكن تعديل تعيين الذاكرة عبر SQLite pragma:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### الضغط

تستفيد مثيلات OmniRoute طويلة الأمد من `VACUUM` العرضي:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

قم بالتشغيل شهريًا أثناء النوافذ ذات حركة المرور المنخفضة. (وضع WAL يقلل الحاجة، لكنه لا يلغيها.)

## فحص السلامة

يوفّر `src/lib/db/healthCheck.ts` **تشخيصات السلامة على مستوى قاعدة البيانات**:

يتطلب كلا الفعلين المصادقة (`401` بخلاف ذلك). يقوم `GET` بالتشخيص فقط؛ بينما يشغّل `POST`
الفحص نفسه مع تفعيل `autoRepair`.

```bash
GET  /api/db/health   # تشخيص
POST /api/db/health   # تشخيص + إصلاح
```

تكون الاستجابة هي `DbHealthCheckResult` التي تنتجها `runDbHealthCheck()`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "Domain budgets referenced API keys that no longer exist.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| الحقل             | المعنى                                                                                                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | تكون القيمة `true` عندما تكون `issues` فارغة. ولا تؤثر `driver` فيها أبدًا.                                                                                                                       |
| `issues[].type`   | إحدى القيم `integrity_check_failed` أو `broken_reference` أو `stale_snapshot` أو `invalid_state`.                                                                                                 |
| `repairedCount`   | عدد الصفوف التي أُصلحت خلال هذا التشغيل؛ وتكون دائمًا `0` عندما تكون `autoRepair` بالقيمة `false`.                                                                                                |
| `backupCreated`   | ما إذا أُنشئت نسخة احتياطية قبل الإصلاح.                                                                                                                                                          |
| `checkedAt`       | طابع زمني بتنسيق ISO مشترك بين التشغيل وأي ملاحظة إصلاح يكتبها.                                                                                                                                   |
| `driver.name`     | برنامج تشغيل SQLite الذي يخدم قاعدة البيانات المفحوصة.                                                                                                                                            |
| `driver.degraded` | تكون القيمة `true` عندما لا تكون عمليات الكتابة مدعومة بشكل دائم بواسطة ملف قاعدة البيانات — أي عند استخدام بديل WASM المتمثل في `sql.js` (استمرارية الملف بالكامل) أو قاعدة بيانات داخل الذاكرة. |

تعيد أداة MCP المسماة `omniroute_db_health_check` الحمولة نفسها.

شغّل `PRAGMA integrity_check` لاكتشاف التلف:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# ينبغي أن يطبع: ok
```

إذا أعاد أي شيء بخلاف `ok`، **فتوقّف عن استخدام قاعدة البيانات فورًا** واستعدها من نسخة احتياطية.

## التعافي من الكوارث

### السيناريو 1: فقدان ملف WAL

ملف `-wal` مفقود، لكن ملف `-shm` وقاعدة البيانات الرئيسية سليمان:

```bash
# يتم التعافي تلقائيًا عند الفتح التالي
omniroute
```

إذا تعذّر على SQLite إجراء التعافي تلقائيًا:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### السيناريو 2: تلف ملف قاعدة البيانات الرئيسية

استعده من النسخة الاحتياطية:

```bash
omniroute backup restore <backup-id>
```

لا يقوم `omniroute sync pull [outPath]` إلا بتنزيل أرشيف `.tar.gz` كامل من خادم قيد التشغيل
(`GET /api/db-backups/exportAll`، يتطلب بيانات اعتماد المشغّل)؛ ولا يستعيد أي شيء.

### السيناريو 3: فقدان مفتاح التشفير

**لا يمكن إجراء أي استعادة** من دون المفتاح. الحقول المشفّرة غير قابلة للقراءة. أعِد إضافة جميع المزوّدين يدويًا باستخدام بيانات اعتماد جديدة.

> **إجراء وقائي**: احتفظ دائمًا بنسخة احتياطية من مفتاح التشفير بشكل منفصل، ويُفضّل أن تكون في مدير كلمات مرور أو KMS.

### السيناريو 4: امتلاء القرص

سيُرجع SQLite أخطاء `SQLITE_FULL`. حرّر بعض مساحة القرص، ثم نفّذ:

```bash
# نفّذ نقطة تحقق لـ WAL لتحرير مساحة
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## استكشاف الأخطاء وإصلاحها

### "قاعدة البيانات مقفلة"

هناك عملية أخرى تحتفظ بقفل كتابة. يمكنك:

- الانتظار حتى تنتهي العملية الأخرى (تحقق باستخدام `lsof | grep storage.sqlite`)
- إنهاء العملية الأخرى
- إعادة تشغيل OmniRoute إذا استمرت المشكلة

### "فشل قيد المفتاح الخارجي"

تنتهك إحدى وحدات النطاق التكامل المرجعي. تحقق من:

- الصفوف اليتيمة في الجداول التابعة
- عمليات الحذف المتتالية التي لم تنتشر
- عملية ترحيل حديثة غيّرت مفتاحًا خارجيًا

شغّل `PRAGMA foreign_key_check;` للعثور على الانتهاكات.

### "نفاد الذاكرة"

تتجاوز عمليات الإدخال/الإخراج المعينة إلى الذاكرة في SQLite حد نظام التشغيل. قلّلها باستخدام تعليمة pragma في SQLite:

```sql
PRAGMA mmap_size = 134217728;  -- ‏128MB بدلًا من 256MB
```

أو عطّلها:

```sql
PRAGMA mmap_size = 0;
```

### "فشل الترحيل في منتصف العملية"

نُفّذ الترحيل ضمن معاملة، لذا يُفترض أن يكون قد تم التراجع عنه. إذا لم يحدث ذلك:

1. **أوقف OmniRoute** (لمنع المزيد من المحاولات)
2. **تحقق من حالة قاعدة البيانات** باستخدام `sqlite3`
3. **أصلح يدويًا** الترحيل الجزئي
4. **أعد تشغيل** OmniRoute (ستُعاد محاولة الترحيل)

لمنع حدوث ذلك، اختبر عمليات الترحيل دائمًا على نسخة أولًا.
