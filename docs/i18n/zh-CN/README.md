## 💰 每月约 1.62B 代币，来自第三方免费套餐

</div>

> **使用你自己的提供者账户。** 这是对各个独立符合条件的第三方免费套餐的汇总估算，并非 OmniRoute 提供的代币额度。请注册账户、在需要时获取凭据，并连接你可以使用的提供者；每个提供者自行控制其限额、可用性和条款。
>
> 手动叠加免费套餐非常痛苦——数十个 SDK、数十种速率限制，而且根本不知道自己实际拥有多少额度。OmniRoute 收录了**分布于 34 个周期性池键中的 467 个免费套餐条目**，并根据**具有已公布正数月度预算的 17 个池，以及 Groq 的五个单模型上限**计算代币总量，同时按共享池去重。只有完成地区身份验证后才能使用的配额（目前为 ModelScope）会单独展示，即地区身份验证后可获得额外约 6M 代币，并且绝不会计入标题总量。结果会持续显示在仪表板上（`/dashboard/free-tiers`）。

<img src="./docs/diagrams/free-tier-budget.svg" width="100%" alt="OmniRoute 免费套餐预算卡片：每月稳定提供约 1.62B 免费代币，若计入注册赠送额度，首月最高约为 2.22B；来自 34 个已记录的周期性池键，涵盖通过一个端点访问的 467 个已收录免费套餐条目。诚实的池去重计算——每个共享池仅计算一次，其中包括具有已公布正数月度代币预算的 17 个周期性池，以及 Groq 的五个单模型上限；条款风险目录中有 12 个提供者被标记为应避免使用，由你自行决定。预算条包括 Mistral 1B、Nara 210M、LLM7 150M、xKiro 150M、Groq 30M（五个单模型上限）以及其他较小的池；此外，首月注册赠送额度和永久免费的无代币上限提供者会单独展示，因此绝不会夸大标题总量。可在 /dashboard/free-tiers 查看实时已用量和剩余额度。"/>

> 实时 `/dashboard/free-tiers` 页面的动画摘要。完整方法说明（池去重、额度层级、提供者条款）：**[docs/reference/FREE_TIERS.md](docs/reference/FREE_TIERS.md)**。
>
> <sub>我们每两周都会根据实时目录重新审核这些数字，而且它们会**双向变化**——某个提供者终止免费套餐，数字就会下降；新增一个免费套餐，数字就会上升。我们公布的是目录实际计算出的结果，绝不会采用向上取整的最佳情况。</sub>

## 🆓 安装、连接提供者，然后通过一个端点进行路由

</div>

<img src="./docs/diagrams/works-zero-config.svg" width="100%" alt="三个步骤：安装并启动 OmniRoute，使用您自己的账户或 API 密钥连接符合条件的提供者，然后使用 OmniRoute API 密钥和 auto 模型，将您的工具指向 localhost:20128/v1。路由取决于可用且符合条件的连接以及提供者限制。"/>

```bash
# 连接提供者后，从控制面板 → 端点复制您的 OmniRoute 密钥：
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer YOUR_OMNIROUTE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"Hello!"}]}'
```

<sub>`auto` 需要一条符合条件的路由。全新安装时可能没有符合条件的无密钥目标，而且无密钥提供者可能会拒绝第三方客户端。标记为 `tos: avoid` 的提供者（包括 Kiro）默认不会参与自动路由；连接账户并不会覆盖该设置。选择提供者之前，请参阅[免费套餐指南](docs/getting-started/FREE-TIERS-GUIDE.md)。</sub>

```bash
omniroute run claude   --model openai/gpt-5.4          # Claude Code
```

## 🗜️ 自动节省 15–95% 的 Token

</div>

### 📖 工作原理 — 流水线、架构与节省量计算

<img src="./docs/diagrams/compression-pipeline.svg" width="100%" alt="OmniRoute 压缩流水线：一个包含 10,000 个 Token 的客户端请求依次通过 12 个可组合引擎——Session-Dedup、CCR、Lite、RTK、Responses Tool Output、Headroom、Relevance、Caveman、Aggressive、LLMLingua-2、Ultra 和 OmniGlyph——在文档所示的堆叠示例中，到达提供者时可缩减至约 1,080 个 Token。结构化内容通过保留防护和逐步保真门控得到保护；显式启用的有损或实验性模式可能会转换符合条件的内容。"/>

默认堆叠组合按 `RTK → Caveman` 运行。当两者作用于同一工具/上下文载荷时，节省效果会复合叠加：

```txt
combined = 1 − (1 − RTK) × (1 − Caveman_input)
average  = 1 − (1 − 0.80) × (1 − 0.46) = 89.2%
range    = 78.4 – 94.6%
```

代码块、URL、JSON 和结构化数据**始终由保留引擎保护**。

> **能用少量 Token 解决，为什么还要使用大量 Token？** 每个请求都会**透明地**通过 OmniRoute 的压缩流水线——无需更改客户端。它现在是一个**由 12 个可组合引擎构成的堆栈**，这些引擎按顺序运行，并可针对不同路由组合灵活搭配——其设计借鉴了 [RTK](https://github.com/rtk-ai/rtk)、[Caveman](https://github.com/JuliusBrussee/caveman)（⭐ 90K+）、[LLMLingua-2](https://github.com/microsoft/LLMLingua) 和 [Troglodita](https://github.com/leninejunior/troglodita)（PT-BR）的理念。

### 🧱 12 引擎堆栈

引擎按流水线顺序运行；每个引擎均可针对不同组合独立启用、停用和配置：

  <tr><td align="center" nowrap>2</td><td align="left" nowrap><b>CCR</b></td><td align="left">将大型内容块归档到检索标记之后，并按需获取</td></tr>

**真实示例——标准模式：**

> **压缩前（69 个 Token）：** _“你的 React 组件之所以重新渲染，很可能是因为你在每个渲染周期中都创建了一个新的对象引用。当你将内联对象作为 prop 传递时，React 的浅比较会认为它每次都是不同的对象，从而触发重新渲染。我建议使用 useMemo 对该对象进行记忆化处理。”_
>
> **压缩后（19 个 Token）：** _“每次渲染都有新对象引用。内联对象 prop = 新引用 = 重新渲染。用 useMemo 包装。”_
>
> **答案相同。Token 减少 72%。准确性零损失。** ✅

**PT-BR 示例——[Troglodita](https://github.com/leninejunior/troglodita) 模式：**

> **之前（42 个 token）：** _“问题在于组件正在重新渲染，因为每个渲染周期都会创建一个新的对象引用。我建议使用 useMemo。”_
>
> **之后（12 个 token）：** _“重新渲染：每个周期都有新引用（内联对象被重新创建）。使用 `useMemo`。”_
>
> **回答相同。token 减少约 70%。技术准确性不变。** ✅

### 🎚️ 不止于引擎——输出风格、自适应旋钮与按请求控制

上述 12 个引擎缩减的是**输入**内容。另外三层用于塑造内容**如何**、**何时**以及以何种形式**输出**：

- **🪄 输出风格** _（输出维度引导）_ — 注入确定性的、缓存安全的响应塑形指令；可组合使用，每种风格均支持 `lite` / `full` / `ultra` 强度。添加一种风格只需在注册表中增加一行：
  - **简洁表述** — 去除赘词、冠词和模糊措辞；精确保留技术实质。
  - **减少代码** — “懒惰的资深开发者”式 YAGNI：提供可行的最小改动，不添加未要求的脚手架。
  - **马尾辫（懒惰的资深开发者）** — 沿 YAGNI 阶梯推进，修复根本原因，提供可行的最小差异。
  - **我有 ADHD（行动优先）** — 先给出下一步行动，步骤编号，仅提供一个具体的下一步，不写前言。
  - **简洁 CJK（文言）** — 极度简洁的文言文风格（仅限 `zh` 语言环境）。
- **🎯 自适应上下文预算** _（旋钮）_ — 不再使用单一的开/关 token 阈值，而是仅按需逐步启用成本最低、信息损失最小的引擎，以**适配模型的上下文窗口**。策略：`reserve-output`（默认，感知模型）· `percentage` · `absolute`。模式：`floor`（保证适配）· `replace-autotrigger`（以你的明确选择为准）· `off`（旧版阈值）。
- **🎛️ 压缩决策位置** _（优先级从高到低）_ — 按请求设置的 `x-omniroute-compression` 请求头 › 路由组合覆盖 › 当前命名配置文件 › 自适应／自动触发 › 面板默认值 › 关闭。实际应用的方案会通过 `X-OmniRoute-Compression: <mode>; source=<source>` 响应头返回。

可按 token 阈值自动触发、开启自适应旋钮、固定命名配置文件、为单次请求设置参数，或为每个路由组合分配管线——选择最适合工作负载的方式即可。可选择启用的离线**评估工具**（`npm run eval:compression`）会基于固定语料库评估保真度与节省量，然后你再推广变更。

## 📦 更多安装方式 — Docker、源码、pnpm、Arch

**🐳 Docker**

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

`:latest` 跟随已**发布**的最高稳定 SemVer 版本。它不会跟踪 git `main`。对于 GitOps，请固定使用 `:X.Y.Z`。请参阅 [Docker 发布渠道](docs/guides/DOCKER_GUIDE.md#release-channels)。该镜像固定设置了 **`OMNIROUTE_MEMORY_MB=1024`**。这足以运行仪表盘和轻量聊天。**编码代理**（来自 Claude Code、Codex、Grok 等的 `POST /v1/responses`）需要大得多的 V8 堆，否则在两个长上下文重叠时，进程会在约 12 GiB 处出现 `FATAL ERROR`。容器大小应高于堆大小（原生缓冲区位于 V8 之外）：

| 工作负载                          | 堆（`-e OMNIROUTE_MEMORY_MB`） | 容器（`--memory`） |
| --------------------------------- | ------------------------------ | ------------------ |
| 仪表盘／轻量聊天                  | `1024`（镜像默认值）           | ≥2 g               |
| 一个编码代理                      | `8192`                         | ≥10 g              |
| 两个并发的长 `/v1/responses` 请求 | `10240`–`12288`                | ≥12–16 g           |

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

**🥟 Bun**

通过 Bun 运行时检测，支持标准的 `bun install` 和全局安装（`bun install -g omniroute`）：

- **内置 `bun:sqlite`**：在 Bun 下运行时，OmniRoute 使用 Bun 内置的 `bun:sqlite` 驱动程序；在 Node.js 上则回退到 `better-sqlite3` 或 `sql.js`。
- **开发环境中自动选择 Webpack 打包器**：开发模式（`bun run dev`）会自动检测 Bun，并禁用 Turbopack、改用 Webpack，以防止原生 V8 绑定不兼容。生产构建（`bun run build`）与 Node 上一样，严格遵循 `OMNIROUTE_USE_TURBOPACK`：默认使用 Turbopack，设置 `OMNIROUTE_USE_TURBOPACK=0` 则使用 Webpack 构建（`Dockerfile.bun` 将其公开为 `--build-arg`）。
- **专用 Bun Dockerfile**：用于原生 Bun 生产部署的多阶段 `Dockerfile.bun`（`docker build -f Dockerfile.bun -t omniroute:bun .`）。


**⚡ 更快／更精简的安装方式（跳过原生构建）**

原生 SQLite 引擎（`better-sqlite3`）是一个**可选**依赖项，因此全局
安装绝不会因从源码编译而受阻：当存在与您的平台／Node 匹配的预构建二进制文件时，它会使用该文件；
否则会透明地回退到纯 JS 引擎
（Node 22+ 上使用 `node:sqlite`，否则使用捆绑的 `sql.js` WASM）——无需构建工具。

若要完全跳过安装后的**原生预热**步骤（适用于 CI、无头环境或较慢的机器），
请使用以下方式。注意：这只会跳过原生 SQLite 预热步骤（`scripts/postinstall.mjs`）；
二进制文件复制／修复钩子（`scripts/build/postinstall.mjs`）仍会正常运行：

```bash
OMNIROUTE_SKIP_POSTINSTALL=1 npm install -g omniroute   # CI=1 也会跳过该步骤
```

为获得最快的安装速度，建议使用 **pnpm**（内容寻址存储 + 硬链接——见上文）。
如需不含仪表盘的无头运行时，请使用 Docker `base` 配置文件（见上文）或
[Termux 指南](docs/guides/TERMUX_GUIDE.md)。CLI 和 Web 仪表盘由同一进程通过同一端口提供，
因此目前没有单独的纯 CLI 软件包。

### 如何贡献

1. Fork 此仓库
2. 从**当前活跃的** `release/vX.Y.Z` 分支顶端创建分支（而非 `main`）——请参阅[分支与发布模型](docs/ops/BRANCHING_MODEL.md)
3. 创建功能分支（`git checkout -b feat/amazing-feature`）
4. 提交更改（`git commit -m 'feat: add amazing feature'`）
5. 推送至该分支（`git push origin feat/amazing-feature`）
6. 创建 Pull Request，并将 **base 设置为对应的 `release/vX.Y.Z` 分支**

有关详细指南，请参阅 [CONTRIBUTING.md](CONTRIBUTING.md)。

```bash
# 创建发布版本——npm publish 会自动执行
```
