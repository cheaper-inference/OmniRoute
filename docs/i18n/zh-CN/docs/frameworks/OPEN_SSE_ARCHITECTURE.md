> **简而言之**：`open-sse/` 是为 OmniRoute 中每个 LLM 请求提供支持的核心流式处理引擎。它包含约 1,400 个文件，实现了请求管道、执行器、服务、MCP 服务器和转换层。本指南将说明这些组件如何协同工作。

**源代码：** `open-sse/`（工作区包，约 1,440 个非测试 `.ts` 文件）

---

## 为什么使用单独的工作区包？

出于以下几个原因，`open-sse/` 是 OmniRoute monorepo 中的一个**独立工作区**：

1. **可复用性** — `open-sse` 以 `@omniroute/open-sse` 的名称发布到 npm，因此其他项目可以独立使用它
2. **清晰的边界** — 流式处理引擎与 OmniRoute 特有的 UI/DB 层解耦
3. **性能** — 该引擎不依赖 Next.js，因此在 CLI/无服务器环境中能够实现更快的冷启动
4. **版本管理** — `open-sse` 可以按照自己的节奏发布版本

```json
// package.json
"workspaces": ["open-sse"]
```

## 请求管道

每个 LLM 请求都会流经一个**五阶段管道**：

```
                              ┌──────────────┐
   HTTP 请求                  │  1. 路由     │   组合解析、模型选择
   （Next.js 路由）            └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. 转换     │   格式转换（OpenAI ↔ Claude ↔ Gemini）
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. 执行     │   提供者执行器、HTTP、重试、断路器
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. 流式传输 │   SSE 转换、背压
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. 记录     │   用量跟踪、调用日志、错误分类
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP 响应（SSE 或 JSON）
```

### 阶段 1：路由（services/combo.ts）

**入口点**：`services/combo.ts` 中的 `handleComboChat()`

将请求解析为具体的 `(provider, model, account, credentials)` 元组：

- 按 ID 查找组合（或为 `auto/*` 模型构建虚拟组合）
- 应用路由策略（优先级、加权、轮询等）
- 过滤掉不健康的提供者（断路器）
- 选择下一个可用目标

对于 `auto/*` 模型，此阶段还会：

- 运行**十六因素评分**算法（`services/autoCombo/`）
- 根据健康状况、成本、延迟等因素选择一个 `provider+model` 组合

### 阶段 2：转换（translator/）

如果源格式（例如 OpenAI）与目标格式（例如 Claude）不同，则会**转换**请求：

- 系统提示词 → 系统消息
- 工具定义 → 提供者特有的工具格式
- 推理/思考参数 → 提供者特有的等效参数
- 消息角色规范化（对于非 OpenAI 提供者，将 `developer` → `system`）

`translator/index.ts` 对外提供：

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### 阶段 3：执行（executors/）

**入口点**：`getExecutor(providerId).execute(request, options)`

所有提供者都通过 `getExecutor()` 工厂的回退机制使用 `DefaultExecutor`（`executors/default.ts`）。执行器会：

- 构建上游 URL（`buildUrl()`）
- 添加提供者特有的请求头（`buildHeaders()`）
- 转换请求正文（`transformRequest()`）
- 发送 HTTP 请求，并执行重试和指数退避
- 在需要时处理身份验证刷新（OAuth 提供者）

所有执行器都扩展自 `BaseExecutor`（`executors/base.ts`，1170 行代码），后者提供：

- 通用重试逻辑
- 代理集成
- 断路器集成
- 用量记录钩子

### 阶段 4：流式传输（utils/stream.ts）

对于流式响应，执行器会返回一个 **ReadableStream**。处理器会：

- 通过 SSE 转换流传递数据（`createSSETransformStreamWithLogger`）
- 应用心跳 ping 以检测失效连接
- 妥善处理客户端断开连接（`pipeWithDisconnect`）
- 为非流式客户端将 SSE 转换为 JSON

对于非流式响应，执行器会返回一个已解析的 JSON 对象，并保持原样传递。

### 阶段 5：记录（services/usage.ts）

响应后（无论成功或失败），都会记录使用情况：

- 响应中的 `prompt_tokens`、`completion_tokens`、`cached_tokens`
- 根据定价数据计算的 `cost_usd`
- `latency_ms`、`status`，以及失败时的 `error_class`
- 持久化到 `usage_history` 表

调用日志制品（如果已启用）将写入 `${DATA_DIR}/call_logs/`。

## 关键文件深入探讨

### chatCore.ts （5977 行）

这**主请求处理程序**。尽管它的规模很大，但它具有清晰的结构：

```ts
// Pseudo-structure of chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body validation
  const body = await parseRequestBody(request);

  // 3. Format detection + translation
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continue to next target
    }
  }

  // 5. Emergency fallback
  return await emergencyFallback(body);
}
```

尽管它是一项庞大的功能，但它被组织成**评论部分**映射到 5 级管道。

### combo.ts (4456 LOC)

这**路由引擎**将组合解析为有序目标。

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

支持**22种路由策略**（参见`src/shared/constants/routingStrategies.ts`）：

| 战略                | 行为                                                       |
| ------------------- | ---------------------------------------------------------- |
| `priority`          | 第一目标有序列表                                           |
| `weighted`          | 按每个目标权重的概率                                       |
| `round-robin`       | 按顺序循环浏览目标                                         |
| `context-relay`     | 跨目标传递上下文                                           |
| `fill-first`        | 在进入下一步之前先填满配额                                 |
| `p2c`               | 两种选择的力量                                             |
| `random`            | 均匀随机                                                   |
| `least-used`        | 选择最近使用次数最少的一个                                 |
| `cost-optimized`    | 最便宜的健康目标优先                                       |
| `reset-aware`       | 了解提供者重置窗口                                         |
| `reset-window`      | 重置基于窗口的路由                                         |
| `expiry-first`      | 先使用额度到期未使用的账户                                 |
| `headroom`          | 最剩余的配额空间优先                                       |
| `quota-weighted`    | 跳过耗尽的帐户，然后按剩余配额提取÷飞行负载                |
| `strict-random`     | 真正统一（无质量加权）                                     |
| `auto`              | 使用 16 因素评分 (`autoCombo/`)                            |
| `lkgp`              | 最后已知的良好提供者优先                                   |
| `context-optimized` | 最适合长上下文请求                                         |
| `cache-optimized`   | 将每个可重复使用的提示前缀固定到同一帐户（提示缓存命中）   |
| `fusion`            | 并行扇出到面板，然后通过法官进行合成（`fusion.ts`）        |
| `pipeline`          | 链式步骤—每个目标的输出都会馈送到下一个目标                |
| `jev`               | 选择加入： TypeSafe Jev 承认哪些排名条目运行；否则你的订单 |

### base.ts (1170 LOC)

这**抽象执行者**每个执行器类都扩展（直接或通过`DefaultExecutor`和其他子类）。它包含：

- `buildUrl()` —默认URL构造（子类覆盖自定义）
- `buildHeaders()` —默认标头（auth、内容类型）
- `transformRequest()` —默认透传
- `execute()` —与retry/backoff/breaker的主HTTP循环

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Handles all OpenAI/Anthropic-compatible providers
  // Providers register configurations (URL, auth, headers) but share executor logic
}
```

特定于提供程序的行为（auth 标头、基本URL、版本标头）是通过提供程序注册表配置的，而不是单独的执行程序类。

## 执行器（150 个模块）

大多数情况下每个提供者一个文件。执行器类都扩展了`BaseExecutor`并覆盖了不同的部分；其他模块是每个提供者的帮助程序（工具模式、 fetch/TTS适配器、怪异处理程序）。

### 常见模式

提供者通过`getExecutor(providerId)`解析，它返回配置的执行器。 OpenAI/Anthropic-compatible提供者使用`DefaultExecutor` (`executors/default.ts`)。特定于提供者的行为（基本URL、身份验证标头、 API版本）在`open-sse/config/providers/`中配置，而请求正文转换在`open-sse/translator/`中处理。

**定制URL**通过提供者配置设置：

```ts
// Provider config in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**自定义授权**通过提供者注册表的身份验证配置（API密钥、 OAuth、标头配置文件）进行处理。

**自定义请求正文**转换（例如， Anthropic将`system`与`messages`分开）在`open-sse/translator/`中按提供者注册。

````

### The Executor Factory

`executors/index.ts` exports `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

解析通过`ExecutorRegistry` (`executors/registry.ts`)：每个专用执行器都在`executors/index.ts`的内置表中声明，并在模块加载时通过`registerExecutor(alias, instance)`注册； `getExecutor()`查阅注册表，并为没有专门条目的任何提供者回退到记忆的`DefaultExecutor` 。完整别名→执行器映射的特征是黄金测试`tests/unit/executor-map-golden.test.ts`。

## 转换器

在 **3 种格式**之间进行转换：OpenAI、Anthropic、Gemini，以及新的 Responses API。

### 何时进行转换

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

常见转换：

- `OpenAI → Anthropic`：独立的 `system` 字段、`x-api-key` 请求头
- `OpenAI → Gemini`：使用 `contents` 而非 `messages`，并使用 `systemInstruction`
- `OpenAI → Responses API`：`input` 数组、`previous_response_id` 状态

### 已处理的边界情况

- `developer` 角色 → 对于非 OpenAI 提供者转换为 `system`
- `system` 角色 → 对于 GLM/ERNIE 合并到第一条用户消息中
- `json_schema` → Gemini 的 `responseMimeType` + `responseSchema`
- `tools` → 提供者特定的工具格式
- 思考参数（o1、Claude）→ 提供者特定的等效参数

## MCP 服务器

`open-sse/mcp-server/` 实现了 **Model Context Protocol** 服务器：

- **110 个工具**（提供者管理、组合、内存、缓存、压缩、代理、技能、游戏化、插件、Notion、Obsidian、本地语料库）
- **3 种传输方式**：stdio、SSE、Streamable HTTP
- **33 个作用域**，用于细粒度授权

### 工具注册

工具以独立文件的形式注册在 `open-sse/mcp-server/tools/` 中，每个文件都导出名称、schema、handler 和 scope：

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### 传输方式

```ts
// stdio（CLI 用法）
startMcpStdio(server);

// SSE（基于 HTTP 的流式传输）
startMcpSse(server, port);

// Streamable HTTP（现代 MCP）
startMcpStreamable(server, port);
```

### 授权

每次工具调用都会经过作用域检查（`open-sse/mcp-server/auth/`）：

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## 转换器

`open-sse/transformer/` 在 **Chat Completions** 和 **Responses API** 格式之间进行转换。

### 为什么需要独立的转换器？

Responses API 是 OpenAI 推出的新格式，支持**有状态对话**（`previous_response_id`）。当客户端发送 Responses 请求时，OmniRoute 会：

1. 在内部将 Responses 转换为 Chat Completions
2. 将请求发送给提供者（任何支持 Chat Completions 的提供者）
3. 将响应转换回 Responses 格式
4. 将转换后的响应以流式方式发送给客户端

转换器（`transformer/responsesTransformer.ts`）提供：

```ts
createResponsesApiTransformStream(): TransformStream
```

它会处理：

- `response.output_item.added` 事件
- `response.output_text.delta` 事件
- `response.completed` 事件
- 工具调用映射（`function_call` ↔ `tool_calls`）

## 性能约束

路由引擎具有严格的性能预算：

| 操作                       | 目标  | 测量条件         |
| -------------------------- | ----- | ---------------- |
| 组合解析                   | <10ms | 针对 50 个目标   |
| 速率限制检查               | <1ms  | 内存令牌桶       |
| 模型系列回退               | <5ms  | 已缓存的系列定义 |
| 请求路由分发               | <2ms  | 热路径           |
| **路由热路径中无阻塞 I/O** | —     | 全部异步         |

## 反模式

❌ **在 `combo.ts` 中进行同步数据库调用** — 预先计算并缓存
❌ **在处理程序中实现重试逻辑** — 使用弹性服务中的 `retry()`
❌ **直接访问提供者配置** — 使用 `providerRegistry` 获取器
❌ **硬编码回退链** — 在 `modelFamilyFallback.ts` 中定义
❌ **跨并发请求修改状态** — 仅使用请求作用域上下文

## 添加新组件

### 添加新服务

1. 创建 `open-sse/services/[serviceName].ts`，并确保职责单一
2. 导出主处理函数和所有常量
3. 在 `tests/unit/services/[serviceName].test.mjs` 中添加单元测试
4. 在 `handlers/chatCore.ts` 中集成到请求管道（如果与路由相关）
5. 如果服务影响目标选择，则更新 `combo.ts` 中的路由逻辑
6. 在此文件中添加文档

### 添加新执行器

1. 创建扩展 `BaseExecutor` 的 `open-sse/executors/[provider].ts`
2. 在 `config/providerRegistry.ts` 中注册
3. 添加到 `executors/index.ts` 工厂
4. 为执行器添加单元测试
5. 在 `docs/architecture/ARCHITECTURE.md` 中添加文档

### 添加新 MCP 工具

1. 创建或更新 `open-sse/mcp-server/tools/[category]Tools.ts`
2. 为输入定义 Zod 模式
3. 在 `mcp-server/index.ts` 中注册工具
4. 添加到 `mcp-server/auth/` 中的作用域矩阵
5. 添加单元测试
