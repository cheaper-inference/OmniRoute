OmniRoute 发布 npm + Docker 工件。这些门禁提供溯源、清单 (SBOM) 和 CVE 扫描，所有这些都是开源的，并集成到发布工作流中。
**咨询优先**的姿态——它们现在报告，在第一次绿色发布后提升为阻塞。

| 门禁                | 工具                                           | 位置                          | 阻塞？         | 输出                                    |
| ------------------- | ---------------------------------------------- | ----------------------------- | -------------- | --------------------------------------- |
| SLSA 溯源 (npm)     | `npm --provenance` (OIDC)                      | `npm-publish.yml`             | 仅当发布失败时 | npmjs 徽章 / `npm audit signatures`     |
| SBOM npm            | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`             | 仅当生成失败时 | 发布资产 + 工件                         |
| SBOM 镜像           | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (合并)   | 咨询           | CycloneDX 工件                          |
| Trivy CVE (SARIF)   | `aquasecurity/trivy-action`                    | `docker-publish.yml` (合并)   | 咨询           | SARIF (HIGH+CRITICAL) → 安全选项卡      |
| Trivy CRITICAL 门禁 | `aquasecurity/trivy-action`                    | `docker-publish.yml` (合并)   | **阻塞**       | `exit-code: '1'` 在可修复的 CRITICAL 上 |
| osv vulnCount       | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`) | **阻塞**       | 棘轮 `metrics.vulnCount` (方向:down)    |
| OpenSSF Scorecard   | `ossf/scorecard-action`                        | `scorecard.yml` (cron)        | 咨询           | SARIF → 安全 + 徽章                     |

镜像 CVE 棘轮在 `docker-publish.yml` 中使用**两个步骤**：SARIF 步骤
(`HIGH,CRITICAL`, `exit-code: 0`) 使 HIGH+CRITICAL 在安全选项卡中可见而不阻塞；
_CRITICAL 门禁_ 步骤 (`severity: CRITICAL`, `ignore-unfixed: true`,
`exit-code: 1`) 在存在**可用修复**的 CRITICAL CVE 时使发布失败。`ignore-unfixed`
防止因没有上游补丁的基础镜像 CVE 而阻塞发布。

## ⚠️ CVE 波动（阻断 osv/Trivy 门禁）

osv 和 Trivy 会将依赖项与**持续增长**的 CVE 数据库进行比较。一个**未改动任何依赖项**的 PR 可能会突然变红，因为现有依赖项中新披露了 CVE（osv：测得的 `vulnCount` > 基线；Trivy：镜像中出现了新的可修复 CRITICAL 漏洞）。**这是阻断式 CVE 门禁的预期运维行为，而不是产品回归。**

当 osv 或 Trivy 因新披露的 CVE 而变红时，处理方法如下：

1. **升级受影响的依赖项**（首选）— 通过 `package.json` 中的 `overrides`（传递依赖项）升级到已修补版本，或基于已修补的基础镜像重新构建镜像。
2. **如果上游尚无修复：**
   - **osv：**在 `config/quality/quality-baseline.json` 中重新设定 `metrics.vulnCount` 基线（`npm run quality:ratchet -- --update` 不涵盖专用门禁——请手动编辑该值，并设置 `direction:down`），同时附上理由说明和跟踪议题。
   - **Trivy：**在 `.trivyignore` 中添加条目（每行一个 CVE-ID），并附上理由注释和跟踪议题。`ignore-unfixed: true` 已自动涵盖没有补丁的 CVE。

必需的 OSV 执行（`check:vuln-ratchet -- --ratchet`）采用失败关闭策略：当无法验证扫描器、报告或基线时，将返回 `INCOMPLETE` 并以退出码 2 结束。检测到指标回归时以退出码 1 结束。建议性执行仍可能返回 `SKIP` 并以退出码 0 结束，但这并不能证明依赖项已通过扫描。阻断式 Trivy 步骤同样要求成功完成检测：工具不可用、作业失败以及缺少镜像证据时，都无法证明镜像是干净的。

## 已停用依赖项的风险

升级固定版本的 promptfoo 开发工具后，根锁文件不再包含 `extract-zip`，也不再包含指向它的依赖关系。这消除了之前在 #14482 中记录并接受的 `promptfoo` → `@openai/codex-security` → `extract-zip` 依赖链。`tests/unit/extract-zip-14482-exposure.test.ts` 中的回归检查会阻止重新引入该依赖项，并继续禁止生产代码导入它。

当前的依赖修复还将兼容性覆盖限定于 Azure identity 的 MSAL 客户端、get-uri 的 FTP 客户端，以及 OpenCode v1 SDK 的 Zod 依赖项。Azure 令牌获取和 FTP 检索均使用受控传输进行测试；两个 OpenCode 软件包也都运行各自的构建和测试套件。注册表安全公告计数是特定时间点的测量值，在提交锁文件后可能会发生变化。
