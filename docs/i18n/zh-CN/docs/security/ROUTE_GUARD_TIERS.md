## 概述

所有 OmniRoute 管理 API 路由均被划分为三个保护层级之一。分类是静态的，定义于 `src/server/authz/routeGuard.ts` 中，并在运行任何其他身份验证分支之前进行评估。

## 层级

### 层级 1 — LOCAL_ONLY

**执行方式：** `isLocalOnlyPath(path)` → 环回主机检查  
**绕过方式：** 默认情况下不可绕过。对于
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 中的路径，如果请求携带具有
`manage` 作用域的有效 API 密钥，则允许有限例外（参见 [Manage 作用域例外](#manage-scope-carve-out)）。

这些路由会生成子进程或执行运行时代码。将其暴露给
非环回流量会使获得有效 JWT 的攻击者（例如，
通过 Cloudflared/Ngrok 隧道）能够触发进程生成——这是一类已知的 CVE
（[GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)）。

**GHSA-fhh6-4qxv-rpqj 的含义（攻击类型）：** 管理/代理服务器
暴露了一个可启动子进程的端点（`npm install`、`node`、浏览器、
代理、`git`、`tar`……）。如果该端点可从主机外部访问——例如
运维人员将 OmniRoute 置于 nginx/Cloudflare/Tailscale 隧道之后，而 JWT
发生泄露，或身份验证配置错误——攻击者便可将“调用 API”转化为“在
主机上运行命令”（远程代码执行）。OmniRoute 通过对每个
可生成进程的路由**无条件地在任何身份验证检查之前执行环回主机检查**来阻止此类攻击：
通过隧道泄露的令牌仍然无法触达进程生成功能。

**完整的 LOCAL_ONLY 集合。** 权威来源是
`src/server/authz/routeGuard.ts` 中的
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`；下表反映了当前状态。
`check-route-guard-membership` 门禁会枚举可生成进程的前缀下的每个
`route.ts`，如果其中任何一个未被归类为仅限本地访问，CI 就会失败。

#### 管理作用域例外

如果且仅当请求携带 `Authorization: Bearer <api-key>`，且其元数据包含
`manage` 作用域（或 `admin`），则也可以从非环回地址访问一部分 LOCAL_ONLY
路径。该例外通过 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 针对每条路径
显式启用，因此任何新增 LOCAL_ONLY 路径默认仍严格限制为环回地址访问。
未经身份验证的请求以及使用非管理密钥的请求仍会被拒绝，并返回
`403 LOCAL_ONLY`。

目前唯一可绕过限制的前缀是 `/api/mcp/`。`/api/cli-tools/runtime/` 和
`/api/services/` 被有意排除，因为它们可以启动任意子进程
（`npm install`、`node`），而这正是设置 LOCAL_ONLY 层所要防范的
CVE 类型。

**#7895 — `mcp:connect` 窄作用域：** `/api/mcp/` 例外还接受持有窄
`mcp:connect` 作用域的 Bearer 密钥
（`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`），该作用域通过
`src/server/authz/policies/management.ts` 中的 `hasMcpConnectOrManageScope()`
进行检查。此作用域**仅**适用于 `/api/mcp/` — `mcp:connect` 不会授予对任何其他
管理路由的权限（包括将来可能添加的所有其他 LOCAL_ONLY 绕过前缀），并且它被有意
排除在 `MANAGEMENT_API_KEY_SCOPES` 之外。持有 `manage`/`admin` 的密钥仍会
与以前完全一样通过此例外；对于只需远程调用 MCP、无需广泛管理访问权限的调用方，
`mcp:connect` 是一种较低权限的替代方案。

| 请求                                             | 路径                       | 结果             |
| ------------------------------------------------ | -------------------------- | ---------------- |
| 非环回地址，无 Bearer                            | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非环回地址，Bearer 具有 `manage` 作用域          | `/api/mcp/*`               | 允许             |
| 非环回地址，Bearer 具有 `mcp:connect` 作用域     | `/api/mcp/*`               | 允许             |
| 非环回地址，Bearer 不具有 `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非环回地址，Bearer 具有 `mcp:connect` 作用域     | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 非环回地址，Bearer 具有 `manage` 作用域          | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 环回地址，有或无任意 Bearer                      | 任意 LOCAL_ONLY            | 允许（通过门控） |

#### 运维人员指南与审计

如果你在反向代理或隧道（nginx、Caddy、Cloudflare Tunnel、Tailscale、
Ngrok）后运行 OmniRoute，环回检查仍会保护上述可启动进程的路由 — 客户端地址
为非环回地址的请求会在**身份验证运行之前**被拒绝，并返回 `403 LOCAL_ONLY`，
因此即使 JWT 泄露，也无法触发进程启动。运维人员仍需承担两项责任：

- **不要通过将客户端 IP 伪造成环回来“修复” 403。** 设置
  `X-Forwarded-For: 127.0.0.1`，或使用将源地址重写为
  环回地址的代理，会再次引入此层级所阻止的同一类 RCE 风险。通过代理暴露
  仪表板/API——绝不要暴露具备进程启动能力的路由。
- **将 manage 作用域绕过保持在最小范围。** 只有 `/api/mcp/` 可以被绕过，而且
  只能使用具有 `manage` 作用域的 API 密钥。`SPAWN_CAPABLE_PREFIXES` 绝不能被
  添加到绕过列表中——zod schema 会拒绝它们，并且
  `isLocalOnlyBypassableByManageScope` 会在运行时拒绝它们（纵深防御），
  这就是仪表板中“无法设置为可绕过”的含义。同一个
  拒绝列表还包含几个不会启动进程、但也绝不能允许远程访问的 LOCAL_ONLY 路由——
  `/api/oauth/kiro/auto-import`（读取主机本地的 Kiro
  凭据文件）、`/api/discovery/` 和 `/api/issue-agent/`。运行时
  快照加载器还会从已存储的设置行中移除此类条目，而旧版 JSON 导入
  （`/api/settings/import-json`）绝不会写入绕过键。
  每个 `LOCAL_ONLY_API_PREFIXES` 条目都必须位于拒绝列表中，或经审核确认可绕过
  （`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`）。`/api/providers/`
  下具有动态段和静态路径、且具备进程启动能力的路由（例如 `/login`、
  `/refresh-cursor`）由
  `src/shared/constants/spawnCapablePrefixes.ts` 中基于正则表达式的
  `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` 配套机制覆盖，而不是由扁平的
  `SPAWN_CAPABLE_PREFIXES` 数组覆盖——要捕获这些路由，扁平数组就必须覆盖
  整个 `/api/providers/` 前缀，这会过度扩大限制范围，影响远程仪表板为提供者 CRUD
  而合理使用的路由树。

**访问审计**——要验证没有来自主机外部的请求访问这些路由：

- 打开 `/dashboard/settings/security` 上的 **授权清单**：它会呈现实时的
  LOCAL_ONLY 前缀列表、哪些前缀可被绕过，以及编译时确定的具备进程启动能力的
  （“无法设置为可绕过”）集合。
- 在反向代理/访问日志中搜索上述前缀，并检查是否与非环回客户端地址同时出现。
  任何返回 `200` 而非 `403 LOCAL_ONLY` 的此类命中，都意味着代理掩盖了真实的
  客户端 IP——请修复代理。
- OmniRoute 日志中针对这些路径之一出现的 `403 LOCAL_ONLY` 表明防护机制正在
  按预期工作，并不是应该抑制的错误。

#### 设有调用点探测门控的远程可访问路由

某些路由必须保持可从远程仪表板访问，但会为本地调用者运行主机端探测
（`which <binary>`、`<binary> --version`、`tailscale status --json`）。
对于 `GET`，它们不属于 LOCAL_ONLY；相反，处理程序使用
`getRequestPeerLocality()`（`src/shared/utils/apiAuth.ts`）读取可信的对等端判定，
并且仅为 `loopback` / `lan` 调用者运行探测。`remote` 调用者会获得相同的响应结构，
但该结构由不启动进程的数据源（持久化状态、设置、fs 检查）构建，并标记为
`probed: false`。

| 路由                                                             | 针对远程调用者跳过的探测                                          |
| ---------------------------------------------------------------- | ----------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | CLI 运行时探测（`allowLocalRuntimeProbe`）和 CLI 回退进程启动     |
| `GET /api/headroom/status`                                       | `which headroom` 和 python `--version` 探测                       |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`、`tailscale status/funnel --json`、`which brew` |
| `GET /api/tunnels/cloudflared`（GET 不受 LOCAL_ONLY 限制）       | `which cloudflared` PATH 查找                                     |

新的主机探测读取路由应遵循相同模式，否则应直接归类为
LOCAL_ONLY。

### 第 2 层级 — ALWAYS_PROTECTED

**强制执行方式：** `isAlwaysProtectedPath(path)` → 跳过 `requireLogin=false` 绕过
**绕过：** 当 `requireLogin=false` 时也不可绕过；始终需要 JWT

这些路由具有破坏性，或者其操作不可逆。如果允许在“无密码”
安装中使用它们，就意味着同一 LAN 上的任何人都可以清空数据库或终止
服务器进程。

| 路径                                      | 原因                                           |
| ----------------------------------------- | ---------------------------------------------- |
| `/api/shutdown`                           | 终止服务器进程                                 |
| `/api/settings/database`                  | 数据库导出、导入和清空                         |
| `/api/db-backups`                         | 完整数据库备份归档访问                         |
| `/api/settings/export-json`               | 导出完整设置数据块（包括密钥）                 |
| `/api/settings/import-json`               | 替换完整设置数据块                             |
| `/api/providers/health-autopilot/actions` | 执行自动驾驶修复操作                           |
| `/api/settings/obsidian`                  | 为任意保险库根目录签发可重复使用的 WebDAV 凭据 |
| `/api/relay/tokens`                       | Mints, lists, edits and revokes relay tokens   |

**违规时的响应：** `401 Authentication required`

`/api/settings/obsidian` 涵盖其 `/webdav` 子路径：`POST` 会将 WebDAV 文件服务——
由自定义 Node 层在 Next.js 之前提供，位于此管线之外——指向调用者选择的根目录，
并回显新签发的 Basic 凭据；`DELETE` 会轮换这些凭据，而父级 `POST` 会存储
Obsidian REST API token。GHSA-62vw 仅掩盖了 `GET` 的密码泄露；凭据签发仍位于
故障时开放的层级（GHSA-7pq4-8pvv-rx7r）。`enableObsidianVaultSync()` 还会拒绝
本身是数据目录、位于数据目录内部或包含数据目录的保险库。

#### 凭据导出仅限操作员

上面的层级仅决定是否需要_某种_凭据。下载已存储凭据的路由会在处理程序中执行第二次检查：`GET /api/settings/export-json`（已解密的提供者连接和原始 API 密钥）、`GET /api/db-backups/export`（SQLite 文件）以及 `GET /api/db-backups/exportAll`（完整归档）会调用 `requireOperatorCredential()`（`src/lib/api/operatorCredential.ts`）。它接受仪表板会话、本地 CLI 主体，或已禁用登录的实例；对于任何作用域的 API 密钥（包括 `manage` 和 `admin`）以及 `oma_` 访问令牌，均返回 `403`。同步令牌签发（`POST /api/sync/tokens`）使用相同的辅助函数，此外还接受受信任的回环内部服务令牌。

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### 全新安装的引导仅限回环访问——依据真实对等端，而非 `Host`

在未配置管理密码（且没有 `INITIAL_PASSWORD`）的情况下，`src/shared/utils/apiAuth.ts` 中的 `isAuthRequired()` **仅对回环对等端**保持匿名引导开放。是否为回环会按以下顺序根据受信任的对等端信号判定：令牌标记的真实 TCP 对等端（`PEER_IP_HEADER` + `VIA_PROXY_HEADER`，即策略所看到的内容）、管道自身的 `AUTHZ_HEADER_PEER_LOCALITY` 判定结果（即路由处理程序所看到的内容，仅在设置了 `OMNIROUTE_PEER_STAMP_TOKEN` 时受信任），或直接调用方的真实套接字对等端。绝不会参考 `Host` / `nextUrl.hostname`，首次密码写入（`POST /api/settings/require-login`）也受相同约束，而不是对每个网络对等端开放（GHSA-7pq4-8pvv-rx7r）。`managementPolicy` 会显式向下传递其自身的 `peerContext` 判定结果，因此原始（剥离前）请求的标头绝不会决定该结果。

### 第 3 层 — 管理（默认）

所有其他管理路由。除非配置了 `requireLogin=false`，否则需要身份验证。CLI 令牌可以对这些路由进行身份验证（回环 + 有效的 HMAC）。

## 评估顺序

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → 回环地址                                  → 继续执行
     → 非回环地址、具有 manage 作用域的 Bearer
        且 isLocalOnlyBypassableByManageScope   → 允许 (management_key)
     → 否则                                      → 拒绝 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 允许 (system)
  3. hasValidCliToken(headers)?
     → 允许 (cli) [回环地址 + timingSafeEqual HMAC 检查]
  4. isAlwaysProtectedPath(path) 或 requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 允许 (dashboard_session)
     → 不可绕过路径上的具有 manage 作用域的 Bearer?
        → 允许 (management_key)
     → 拒绝 401/403
  5. requireLogin=false?
     → 允许 (anonymous)
```

步骤 1 中的 manage 作用域分支是唯一能够满足 LOCAL_ONLY 路由要求的认证路径；认证后端故障时返回 503（而不是 403），因此数据库过期不会静默降级为“拒绝”。

## 添加具有进程启动能力的新路由

1. 将路径前缀添加到
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES`
2. 在 `tests/unit/authz/routeGuard.test.ts` 中添加测试，断言
   `isLocalOnlyPath()` 对新前缀返回 true
3. **绝不要跳过此步骤** — 请参阅 `CLAUDE.md` 中的硬性规则 #15
4. 决定：此路由是否也应属于 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`？
   默认答案是**否**。仅当该路由可以安全地向 manage 作用域持有者公开时才选择加入（即不会启动任意用户控制的代码）。

## 添加可由 manage 作用域绕过的路径

1. 确认该路由不会执行用户提供的代码或命令。如果会，请停止 — 此例外机制并不适用。
2. 将前缀追加到
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`
3. 在 `tests/unit/authz/management-policy.test.ts` 中为全部四种请求形式添加覆盖：无 Bearer（403）、manage Bearer（允许）、非 manage Bearer（403），以及针对每个前缀的回归测试，确保 `/api/cli-tools/runtime/*` 即使带有 manage Bearer 也始终严格限制为回环地址。

## 在 OpenAPI 中记录安全层级

向 `docs/openapi.yaml` 添加新路由时，如果该路由已由 `routeGuard.ts` 分类，请应用对应的供应商扩展：

| routeGuard.ts 分类           | YAML 注解                  | 强制执行规则                             |
| ---------------------------- | -------------------------- | ---------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 无条件阻止来自非回环地址的访问           |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | 即使 `requireLogin=false` 也要求认证     |
| 内部管理/调试路由            | `x-internal: true`         | 默认不在 /dashboard/api-endpoints 中显示 |
| 无（公开/标准认证）          | （无需注解）               | 由标准 `requireLogin` 控制的访问         |

### 验证

以下两个脚本用于确保 YAML 注解与 `routeGuard.ts` 之间的一致性：

- `scripts/check/check-openapi-coverage.mjs` — 覆盖率低于 99% 时失败
- `scripts/check/check-openapi-security-tiers.mjs` — 当 `x-loopback-only` 或
  `x-always-protected` 注解与编译时常量不一致时失败

这两个脚本都会在预提交钩子和 CI 中运行。

### 误报规则

如果某个路由带有 `x-always-protected` 或 `x-loopback-only` 注解，但并不在
`routeGuard.ts` 常量中，覆盖率脚本将失败。正确的修复方式始终是让 YAML 与
`routeGuard.ts` 实际强制执行的规则保持一致 — 而不是在尚未实现相应强制执行逻辑的情况下，将路由添加到 `routeGuard.ts`。
