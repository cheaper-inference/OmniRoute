使用本指南为拉取请求选择最小且可靠的开发循环。它不能取代下方链接的特定领域架构和安全文档；它将每种常见变更类型与其契约、针对性检查和 CI 覆盖范围关联起来。

## 每项变更都遵循的路径

1. **编辑前选择基础分支。** 找到最高版本且仍处于活跃状态的 `release/v*` 分支，并从其最新提交创建分支。以该分支而非 `main` 为目标。如果当前处于发布冻结期，请勿以已冻结的分支为目标；请使用
   [分支与发布模型](BRANCHING_MODEL.md)中所述的下一个活跃周期。
2. **明确契约。** 识别变更影响的每个目录、架构、生成产物、公共 API 或用户界面。下表给出了最低起始集合。
3. **编写或更新针对性测试。** 对 `src/`、`open-sse/`、`electron/` 或
   `bin/` 中的生产代码所做的变更，必须在同一 PR 中包含自动化测试。先运行能够证明相关行为的最小测试文件集合，然后运行列出的针对性门禁检查。
4. **让 CI 运行广泛的测试矩阵。** 完整的单元测试分片、Vitest、覆盖率渐进门槛以及生产构建都会在 PR 上运行。仅当针对性测试失败表明存在更广泛的影响，或变更横跨多个子系统时，才在本地运行广泛的测试套件。
5. **评审前完成同步。** 获取活跃基础分支，检查其中的新提交以及你的分支相对于它的差异，然后根据贡献者工作流对基础分支执行 rebase 或 merge。应从源文件解决生成文件和目录冲突，重新生成这些文件，再次运行针对性循环，并确认 PR 仍以活跃的发布分支为目标。
6. **记录证据。** 在 PR 模板中列出已运行的命令、所有新增或修改的测试文件、迁移或功能标志，以及仍待 CI 验证的所有项目。

## 按变更类型划分的黄金路径

下面的命令是最低限度的重点检查，而不是跳过直接涵盖您更改的行为的测试的权限。

### 提供者

**合约**

- `src/shared/constants/providers/`中的提供者定义及其`src/shared/constants/providers.ts`中的组成。
- `open-sse/config/providerRegistry.ts`或其提取的注册表文件中的模型和功能。
- Executor/translator选择、 OAuth或 API 密钥配置和仪表板资产。不要提交重新生成的`docs/reference/PROVIDER_REFERENCE.md`或README图：发布刷新会重写它们（`check:pr-derived-paths`使承载它们的PR功能失败）。
- 公共凭证必须使用`resolvePublicCred()`；错误响应必须使用共享的清理错误助手。请参阅`docs/security/PUBLIC_CREDS.md` （git；未编译到`/docs`中）和[Error Sanitization](../security/ERROR_SANITIZATION.md) 。

**聚焦循环**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # preview the generated reference; do not commit it
npm run lint
```

还测试每个受影响的请求系列：聊天、响应、图像、嵌入、音频或视频。当合同发生变化时，审查生成的目录和黄金差异；不要盲目接受它们。

### 路由

**合约**

- `src/shared/constants/routingStrategies.ts`中的公共策略值和UI数据。
- 根据`open-sse/services/combo.ts`和`open-sse/services/combo/`进行调度和订购。
- 组合模式、持久性、弹性状态、模型功能和API/UI控制。
- 行为发生变化时的[自动组合引擎](../routing/AUTO-COMBO.md)和弹性文档。

**聚焦循环**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy or dispatch changes
npm run check:known-symbols      # strategy registration changes
npm run lint
```

在本地使用确定性模拟上游测试。现场组合烟雾需要凭证并且是手动的，而不是CI替代品。

### UI / UX

**合约**

- Next.js route/page以及`src/app/`和`src/shared/components/`下的共享组件边界。
- API响应形状、 loading/empty/error状态、键盘和屏幕阅读器行为、响应式布局、主题和区域设置扩展。
- `src/i18n/messages/en.json`中的英文UI源字符串；不要对新的面向用户的副本进行硬编码。

**聚焦循环**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

运行应用程序进行交互或视觉变化，并检查窄视口和宽视口。 CI运行生产构建和更广泛的套件；视觉行为仍然需要一个集中的组件、 Playwright或适合更改的记录的手动检查。

### 国际化

**合约**

- `src/i18n/messages/en.json`是UI源； `config/i18n.json`是语言环境源。
- CLI目录单独存在于`bin/cli/locales/`下。
- 准确保留ICU占位符和标签。请勿翻译product/provider/model名称、协议和标头名称、命令、 code/JSON标识符、 URLs、环境变量或受保护术语，例如`OmniRoute`、 `OAuth`、 `MCP`和`A2A`。当前源列表是`scripts/i18n/glossary/protected-terms.json`。

特征PR仅编辑`src/i18n/messages/en.json` (CLI: `bin/cli/locales/en.json`)；其他区域设置在每个版本中通过版本刷新或转换波完成一次（`docs/guides/I18N.md` → “仅限PRs touch `en.json`功能”）。 `npm run check:pr-derived-paths`未能实现编辑另一个语言环境目录的PR功能。

**聚焦循环**

```bash
npm run i18n:check-ui-coverage
npm run check:ui-icu
node scripts/i18n/check-key-completeness.mjs --mode=pr      # what CI runs on your PR
node scripts/i18n/check-ui-value-drift.mjs --mode=pr
node scripts/check/check-cli-i18n.mjs --mode=pr              # when CLI strings change
npm run i18n:check-glossary
npm run lint
```

如果没有`--mode=pr`这些门在本地以发布模式运行，并报告在`en.json`中添加或重写的周期的每个密钥；这是发布刷新的工作，而不是您的PR的工作。

这是对现有系统的指导，而不是扩展其工具或关键模型的邀请。在设计替代系统的同时，保持 i18n 补丁的外科手术。不要运行调用外部服务的翻译命令，除非任务明确需要生成的翻译并且您已查看生成的差异。

### CLI

**合约**

- `bin/cli/`中的公共命令和标志、生成的API命令、退出代码、 stdout/stderr和JSON输出形状、 config/environment行为和打包文件。
- CLI面向用户的字符串必须使用CLI i18n 层（ `bin/cli/locales/en.json`中存在的`t()`键）。特征PR仅编辑`en.json`； `pt-BR`和其他语言环境在发布时完成。
- 保留 Node 作为受支持的运行时和发布的二进制合约。

**聚焦循环**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
node scripts/check/check-cli-i18n.mjs --mode=pr
npm run build:cli             # generated/bundled CLI changes
npm run check:pack-policy     # package-surface changes
npm run lint
```

当行为取决于解析、文件或退出状态时，请在临时数据目录中使用精确命令。 CI执行更广泛的包工件和生态系统检查。

### 数据库

**合约**

- `src/lib/db/`下的域模块；直接导入特定模块（旧的`localDb.ts`重新导出层已删除）。
- `src/lib/db/migrations/`下的编号、幂等SQL迁移、事务安全、升级行为、索引以及受模式影响的每个调用者。
- 路由和处理程序从不直接发出原始SQL 。

**聚焦循环**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

添加迁移时，测试新数据库并从先前架构升级。数据库测试必须关闭句柄并在清理期间调用`resetDbInstance()` 。仅当尽力而为的Bun适配器路径发生变化时才运行`npm run test:bun:db` ；节点仍然具有权威性。

### 构建/部署

**合约**

- 根和工作区manifests/lockfile、 `scripts/build/`、 Next.js独立程序集、 `dist/`包内容、 Electron平台元数据、 CI工作流程和部署哨兵。
- 支持的节点范围和`CLAUDE.md`中允许使用的Bun必须保持不变。
- 构建工件不被追踪；依赖项、许可证、工作流程和包策略均适用。

**聚焦循环**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency or lockfile changes
npm run check:pack-policy      # published package surface changes
npm run lint
```

仅当更改影响编译、独立程序集、资产或运行时捆绑时，才在本地使用`npm run build` 。仅将`npm run build:release`用于release/deploy验证。 CI的构建是最终的跨平台信号；特定于平台的Electron更改需要匹配的重点构建或烟雾证据。

## 共享机器上的开发者脚本

两个 `scripts/dev/` 辅助脚本为其他会话仍在运行的 devbox 编码了本地开发循环：

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD 中的文件
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # 仅检查这些文件
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # 隔离的 worktree，可安全并行运行
```

- `typecheck-touched.sh` 仅通过临时
  `tsconfig.touched.tmp.json`（`extends ./tsconfig.json`、`types: ["node"]`、`noEmit`、
  `incremental: false`）对改动过的 `.ts/.tsx` 文件执行类型检查，并使用 6 GB 堆内存，因此它取代了会在高负载机器上因 OOM
  而失败的项目级 `tsc -p tsconfig.json`。它会输出改动文件中的错误以及一行摘要；当改动文件中存在错误时退出码为
  `1`，当错误仅存在于导入的文件中，或 tsc 在没有诊断信息的情况下终止时退出码为 `2`
  （请读取其指定的 `_artifacts/typecheck-touched/` 下的日志），没有错误时退出码为
  `0`。临时 tsconfig 始终会被删除；切勿提交它。
- `new-worktree.sh` 会通过 `<git-common-dir>/omniroute-new-worktree.lock`
  串行化并发运行（默认最多等待 600 秒，并显示提示消息；脚本头部记录了覆盖此设置的方法）；如果 `git worktree add`
  在 worktree 存在之前失败，它还会回滚所创建的分支，因此重试时无需手动执行 `git branch -D`。硬链接的 `node_modules`
  和 `.husky/_` 副本保持不变。

## 本地候选版本循环

源代码测试无法证明打包后的构件可以启动：打包清单、裁剪后的依赖项和原生二进制文件方面的问题，只有在 tarball
被安装并启动后才会暴露。`npm run dev:candidate`（`scripts/dev/candidate.mjs`）是 RFC #8084
中“构建一次 / 验证 / 提升”流程的本地实现：它构建一个候选版本、验证该确切构件、通过目录重命名提升它，并在提升后的槽位未通过健康检查时将其回滚。

```bash
npm run dev:candidate -- run --dry-run --json  # 输出计划，不进行任何更改
npm run dev:candidate -- run                   # 构建 + 验证 + 提升，自动回滚
npm run dev:candidate -- build                 # npm pack + 安装到 _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # 在空闲端口上启动，检查 /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current，current → previous
npm run dev:candidate -- rollback              # 交换 current 和 previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # 重用在其他位置（CI）构建的 tarball
```

- **只构建一次。** `build` 会打包当前工作树（它需要 `dist/server.js`，因此请先运行
  `npm run build:release`）或复制 `--from-tarball`，然后将 tarball 安装到隔离的 npm prefix 中，因为 tarball
  不包含 `node_modules`。id 是简短的 `HEAD` sha（工作树存在本地更改时附加 `-dirty`），对于 tarball 则为
  `tgz-<sha256>`。如果一个干净的 id 已完成构建，则会直接重用而不是重新构建；传入 `--force` 可强制重新构建。
- **验证软件包，而不是源代码。** `validate` 会使用全新的 `DATA_DIR=<candidate>/data`、伪造的密钥，并从环境中移除操作者的
  `OMNIROUTE_API_KEY`、`STORAGE_ENCRYPTION_KEY` 和 `INITIAL_PASSWORD`，然后启动已安装的 CLI
  （`serve --port <free port>`），从而检查全新安装在无密钥情况下的回环接口安全状态。它会等待
  `GET /api/health` 返回 200，要求 `GET /v1/models` 返回 200，停止进程组，并将判定结果连同 tarball
  哈希一起记录在 `validation.json` 中。
- **提升同一个构件。** 如果候选版本没有针对其当前 tarball 哈希的通过验证记录，`promote` 会拒绝提升。默认活动槽位是
  `_artifacts/candidate/current`；`--target <dir>` 可选择同一文件系统中的其他目录，其上一版本槽位为
  `<dir>.previous`。每次重命名都是原子的；如果流程中途失败，则会撤销已执行的重命名。
- **回滚。** `run` 会再次验证提升后的槽位，如果检查失败，则交换 `current` 和 `previous` 以执行回滚。首次验证失败的候选版本绝不会被提升。

所有内容都会写入已被 git 忽略的 `_artifacts/candidate/`；现有的 OmniRoute
安装及其数据目录绝不会被修改。提升后的 CLI 位于
`_artifacts/candidate/current/prefix/bin/omniroute`；使用时请通过你自己的 `DATA_DIR`
启动它。退出码：`0` 表示成功，`1` 表示验证或提升失败，`2` 表示用法错误或缺少构建。

## 本地循环与 CI

| 每个补丁均在本地运行                            | CI 提供广泛的验证信号                      |
| ----------------------------------------------- | ------------------------------------------ |
| 上述直接行为测试和类别门禁                      | 分片的完整单元测试套件和串行测试           |
| `npm run lint`                                  | Vitest 测试套件以及覆盖率/质量递进门槛     |
| 仅当受影响的契约需要时才进行类型检查或构建      | 生产构建、安全、文档、依赖项和 PR 策略门禁 |
| 仅当自动化无法验证行为时才进行手动交互/实时检查 | 工作流配置的跨作业集成和平台检查           |

聚焦的本地循环通过，只能证明变更的契约符合预期，并不能证明不相关的 CI 检查也会通过。
反过来，也不要让每次本地编辑都等待完整的仓库测试矩阵。

## 协调检查清单

请求审查之前：

- 确认 PR 的基础分支仍是最新的活跃 `release/v*` 分支。
- 获取该基础分支，并审查自创建当前分支以来合入的提交。
- 检查 `git diff <active-base>...HEAD`，确认没有意外变更或生成内容导致的无效变更。
- 通过更新源文件并重新生成输出来解决目录和生成文档的冲突。
- 完成协调后，重新运行 PR 描述中列出的每项聚焦测试/门禁。
- 切勿仅为适配已变动的基础分支而削弱断言或删除必需的测试。

有关发布冻结和重新指定目标分支的规则，请参阅
[分支与发布模型](BRANCHING_MODEL.md)。有关完整的 CI 清单，请参阅
[质量门禁参考](../architecture/QUALITY_GATES.md)。
