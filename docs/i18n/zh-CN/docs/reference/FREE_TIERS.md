## TL;DR — OmniRoute 实际汇总了多少免费推理额度？

这些数字涉及目录中不同的第三方账户和资格条件。OmniRoute 本身不提供这些额度：你必须取得所需的账户或凭据、连接符合条件的提供者，并遵守其限制。实际可用容量可能更低；对于未配置任何合格路由的全新安装，容量甚至可能为零。标记为 `tos: avoid` 的提供者默认不参与自动路由。

**核查于 2026-10-08：** [Cerebras](https://www.cerebras.ai/pricing) 提供一次性 $5 促销额度，需要绑定付款方式，并在 30 天后过期。[Gemini](https://ai.google.dev/gemini-api/docs/rate-limits) 公布了按项目/模型/层级划分的速率限制；它仍未计入量化后的月度核心数字。

## 2026-10-18 SiliconFlow 免费模型更正（#17028）

十个已公布正数每 token 价格的 SiliconFlow 旗舰模型被错误地作为 `recurring-uncapped` 免费访问发布。这十行现已从静态目录中**移除**，该目录目前共有 **467 个条目**。SiliconFlow 不再为静态总数贡献无条件免费模型条目，也不再计为永久免费的提供者。

这**并不**意味着 SiliconFlow 没有免费模型。仅限免费模型的导入和“Free”徽章现在要求从实时提供者模型载荷中获得**明确的按模型证据**，例如显式的免费布尔标记，或输入和输出 token 价格均为零。显式的付费标志或任何正数价格均优先于乐观的免费标记。对于没有可用实时证据的模型，**不会**假定其免费；新账户的一次性额度不能证明存在周期性免费配额。如果当前提供者 API 无法提供可靠的模型级定价，请在路由之前通过提供者控制台进行确认。这一保守选择可防止仅限免费模型的导入和自动组合产生意外费用。

下方的历史提供者表格并非对实时可用性的承诺。该表格原先的 SiliconFlow 无上限／10 模型条目已被有意移除，因为它已不再代表已确认的周期性免费配额。

[Bytez 计费](https://docs.bytez.com/model-api/docs/billing)将其免费计划中的开放模型限制为 7B 参数。70B 和 72B 条目需要购买积分后才能解锁，因此已被移除。Mistral-7B 仍属于 `recurring-credit`：积分每四周刷新一次，但按推理秒数计费，并且未公布 token 配额。其 token 计数器已设为零，用来表示数量未知，取代不受支持的 100 万 token 估算；这并不意味着免费积分为零。Nous 的变更详见下方的提供者说明。

## 两种机制——统计与判定

OmniRoute 通过两种有意读取不同来源的机制来回答“它是否免费？”：

| 机制          | 事实来源                                                                                                                                                 | 适用界面                                                                                              |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **统计/显示** | 解析后的目录——已发布的基线目录叠加 Radar 数据源（`getRadarCatalog`）                                                                                     | 免费层总量、预算卡片、仪表板                                                                          |
| **判定**      | 仅使用已发布的目录（`open-sse/config/freeModelCatalog.data.ts` 中的 `FREE_MODEL_BUDGETS`）以及本地启发式规则（`:free` 后缀、零定价、`grantsFreeAccess`） | `src/shared/utils/freeModels.ts` 的所有使用方：模型导入、`auto/*` 路由、`GET /v1/models` 和浏览器预览 |

只要数据源可用，统计结果就可以得到改进。判定则始终基于发布制品，因此浏览器和服务器给出的答案完全一致，可离线复现，也可以在没有数据库的情况下进行测试。如果让浏览器预览读取一个来源，而服务器导入读取另一个来源，就会导致预览结果与点击后实际发生的情况不一致——这种拆分是有意保留的。

## 方法与注意事项

- 这些数字是基于各提供者截至 **2026-06-17** 公布的免费层限制、通过网络调研得出的**上限估算值**。免费层经常变化——依赖任何数字之前，请重新核实。
- **条目实际担保的内容。** 任何条目都没有逐行置信度评级，API 也不提供此类评级——应将上述每个数字都视为质量相同但未明确说明的估算值。有两类事实有所不同，因为它们是人工维护的，而不是推断得出的：44 个条目带有独立记录的硬性停止机制（其中 39 个是 xKiro 条目，它们共享同一个每日配额），20 个条目带有提示词训练披露。仅当提供者自身的条款明确说明，超出免费配额后会拒绝请求，而不是静默开始计费时，才会设置 `hardStopGuaranteed`；其来源会写在条目旁边的注释中。该字段从不默认为 `true`，无人核实过的条目会保持未设置状态。因此，缺少硬性停止标志意味着“尚未证实”，而不是“已知会向你收费”。**STRICT 模式**（可选择启用的 `freeAccessPolicy=strict` 路由防护）仅信任带有该标志的条目；其他所有免费层都会以 `no-hard-stop` 为由被排除（参见 `open-sse/services/autoCombo/strictZeroCostFilter.ts`）。当该防护过滤模型池时，面向运维人员的日志会同时报告排除数量及其中 `no-hard-stop` 所占的比例。
- `estMonthlyFreeTokens` = 仅计算每月循环发放的 token。**一次性注册积分不会重复发放**，因此计为 0。已终止的免费层也计为 0。
- 每日 token 上限 → `monthly = daily × 30`。仅记录了 RPD → `RPD × ~800 output tokens × 30`。仅记录了 RPM/TPM（没有每日上限）→ **无上限**（见下文）。
- **永久免费，但未公布 token 上限**（`glm-cn`、`tencent`、`baidu`、`kilo-gateway`、`opencode-zen`、`gemini`、`ollama-cloud`）：这些确实是循环提供的免费访问权限，但受到速率或并发限制。我们将其归类为 `recurring-uncapped`，并且**绝不计入总和**——使用 `RPM × 24/7 × 30d` 计算会产生一个不切实际的上限（这正是我们拒绝采用的虚高算法）。列出这些服务是为了让你知道它们确实存在。
- **充值解锁提升：**一次性小额充值，可永久提高免费配额（OpenRouter：$10 → 1000 次请求/天 ≈ 每月额外 +24M）。该数字单独报告，不计入稳定配额的主要统计数字。
- **受资格限制的配额**（`eligibilityGate: "regional-identity"`）：真实存在的循环配额，但只有通过地区绑定的身份验证后才能使用（目前为中国大陆实名认证）。按照相同的池去重规则计入单独的数字（`gatedRecurringTokens`），绝不计入稳定配额的主要统计数字。其机制（`freeType`）保持不变，因此路由也不会变化。
- **证据类别。** 规则如下：目录中的数字必须在条目旁边的 `// evidence:` 注释中注明来源——`public-page`（任何人都可以访问的提供者页面）、`api-public`（提供者无需身份验证即可访问的端点，例如 NaraRouter 位于 router.bynara.id 的公共计划端点），或 `console-verified <date> por <who>`（该数字只能在账户控制台中看到；注释会记录查看者及查看日期，并附上说明该上限存在的公共页面）。当前状态：于 2026-09-02 重新审核的五个区块均带有此类证据（`gemini`、`groq`、`mistral`、`ollama-cloud`、`nara`）；早于 2026-09-02 重新审核的条目会沿用此前的调研结果，直到它们被修改；任何**新增或变更**的数字如果没有证据注释，都属于 bug。目前只有 `mistral` 经过控制台验证。

## 为什么我们的数字小于其他聚合器的数字

在这一领域，大多数“每月免费 token”数字都是各模型标注额度的总和。我们的数字并非如此，这是有意为之：

- **每个共享额度池只计算一次。** Mistral 的免费套餐为每个组织提供每月 1B 的统一额度；将其列在五个模型下并不会使其变成 5B。如果按模型累加，我们自己的目录会显示为 **~7.4B**（于 2026-09-03 重新计算；此数字不受 CI 检查约束——每当目录发生变化时都应重新测算）——标题显示 **~1.47B**，因为这才是每个提供者各使用一个账户时实际可以消耗的额度。
- **每日上限会进行换算，速率限制则不会。** 有明确记录的每日 token 上限会按 `× 30` 换算；有明确记录的每日请求上限会按 `RPD × ~800 tokens × 30` 换算；如果提供者只公布每分钟请求数，则**不会**计算月度数字，并将其列为_无上限_，绝不计入总和。将速率限制按 24/7 全天候运行来相乘，正是我们拒绝采用的虚高计算方式。
- **需要通过区域身份检查才能获得的配额会单独列出**（`+~6M behind regional identity verification`），因为大多数读者无法使用这些配额。
- **注册赠送额度仅适用于首月**，并作为第二个数字报告，绝不会混入持续可用额度中。
- **该数字由 CI 强制校验。** `npm run check:docs-counts` 会根据目录重新计算总额；当此文件、README 或预算卡片中的数字与计算结果不一致时，构建会失败。

## 术语表

| 术语                | 含义                                                      |
| ------------------- | --------------------------------------------------------- |
| **RPM / RPD / RPH** | 每分钟 / 每天 / 每小时的请求数                            |
| **TPM / TPD**       | 每分钟 / 每天的令牌数                                     |
| **明确记录的配额**  | 提供者公布了明确的每日/每月令牌上限（可作为可靠预算依据） |
| **理论上限**        | `速率限制 × 24/7 × 30 天`——这是最大值，并非授予的预算     |
| **神经元**          | Cloudflare 计算单位（约等于 1 个输出令牌）                |

> 基于 2026-06-05 对各提供者的研究生成。请重新运行研究工作流（参见 `_tasks/features-v3.8.12`）以刷新内容。
