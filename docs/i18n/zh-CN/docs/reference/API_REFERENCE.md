## 聊天补全

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### 自定义标头

| Header                   | 方向 | 描述                                                                                                                                                |
| ------------------------ | ---- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | 请求 | 设置为 `true` 以绕过缓存                                                                                                                            |
| `x-omniroute-no-memory`  | 请求 | 设置为 `true` 以跳过此次请求的 memory + skills 注入（与 no-cache 类似；避免每次调用产生额外的 token/成本开销）                                      |
| `X-OmniRoute-Progress`   | 请求 | 设置为 `true` 以启用进度事件                                                                                                                        |
| `X-Session-Id`           | 请求 | 用于外部会话粘性的固定会话键                                                                                                                        |
| `x_session_id`           | 请求 | 同时接受下划线变体（直接 HTTP）                                                                                                                     |
| `X-OmniRoute-Session-Id` | 请求 | 调用方提供的会话/对话标签（也会馈入 memory）。存在时，按原样持久化到 `call_logs.session_tag`，用于按会话进行成本归因（#8249）——缺失时绝不会自动生成 |
| `Idempotency-Key`        | 请求 | 去重键（5 秒窗口）                                                                                                                                  |
| `X-Request-Id`           | 请求 | 备用去重键                                                                                                                                          |
| `x-omniroute-connection` | 请求 | 通过连接 ID 将单模型请求固定到某个提供者连接（账户）——请参阅[按请求固定账户](#account-pinning-per-request)                                          |
| `X-OmniRoute-Cache`      | 响应 | `HIT` 或 `MISS`（非流式）                                                                                                                           |
| `X-OmniRoute-Idempotent` | 响应 | 如果已去重，则为 `true`                                                                                                                             |
| `X-OmniRoute-Progress`   | 响应 | 如果已启用进度跟踪，则为 `enabled`                                                                                                                  |
| `X-OmniRoute-Session-Id` | 响应 | OmniRoute 使用的有效会话 ID                                                                                                                         |
| `X-OmniRoute-Request-Id` | 响应 | 请求关联 ID（如果已知）                                                                                                                             |
| `X-OmniRoute-Version`    | 响应 | OmniRoute 构建版本（始终存在）                                                                                                                      |
| `X-OmniRoute-Cost-Saved` | 响应 | 缓存命中时缓存所节省的美元金额（仅缓存命中时存在）                                                                                                  |
| `X-OmniRoute-Decision`   | 响应 | 路由跟踪：`strategy=<name>; provider=<alias>; latency_ms=<n>`（`<name>` 是组合策略；对于非组合请求则为 `single`）——完成响应中始终存在               |

> Nginx 注意：如果依赖下划线标头（例如 `x_session_id`），请启用 `underscores_in_headers on;`。

#### 按请求固定账户

当某个提供者拥有多个连接（账户或密钥）时，OmniRoute 通常会通过其账户选择策略选择其中一个。请求也可以通过 `x-omniroute-connection` 标头改为固定到某个特定连接：

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **在哪里查找 ID。** 在控制面板中打开提供者页面
  （**Dashboard → Providers → <provider>**），然后点击连接行上的 `xxxxxxxx…` ID 标签 — 该操作会复制完整的连接 ID。
- **哪些请求会使用它。** `/v1/chat/completions`、`/v1/messages` 和
  `/v1/responses` 上的单模型请求（`provider/model`）。组合请求会忽略此标头：请通过每个组合步骤自身的连接，为该步骤固定一个账户。
- **固定是严格绑定，而非偏好设置。** 只会使用固定的连接。请求内部发生故障时，会记录该账户的冷却状态，但**不会**切换到同一提供者的其他账户。
- **冷却和配额会解除固定。** 在固定连接处于冷却状态、配额耗尽或被配额策略阻止期间，后续请求会回退到该提供者的其他连接，与未固定的流量完全相同。
- **未知或已停用的 ID 会导致失败。** 不在提供者活动连接池中的 ID（已删除、已停用或属于其他提供者）不会留下可用账户，因此请求会失败，而不是静默地路由到其他位置。

Claude Code 通过 `ANTHROPIC_CUSTOM_HEADERS` 发送自定义标头。将其放入
`~/.claude/settings.json` 的 `env` 块中，或者放入项目级别的 `.claude/settings.json`，即可为每个项目固定不同的账户：

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

来源：`src/sse/handlers/chat.ts`（读取标头）、`src/sse/services/auth.ts` 和
`src/sse/services/sessionAffinityPin.ts`（解除固定以及检查连接是否缺失于连接池）。

> **成本遥测标头：** 非流式成功响应还会携带 `X-OmniRoute-*` 成本遥测标头集 — `X-OmniRoute-Response-Cost`（美元，固定 10 位小数；免费/未定价时为 `0.0000000000`）、`X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`、`X-OmniRoute-Model`、`X-OmniRoute-Provider`、`X-OmniRoute-Latency-Ms`、`X-OmniRoute-Cache-Hit` 和 `X-OmniRoute-Fallback-Attempts`（仅当大于 0 时），以及 `X-OmniRoute-Request-Id` 和 `X-OmniRoute-Version`。这些标头由聊天补全、`/v1/responses`、`/v1/messages` **以及媒体端点** — `/v1/embeddings`、`/v1/images/generations`、`/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/rerank`、`/v1/videos/generations`、`/v1/music/generations` 和 `/v1/moderations` — 发送（成本始终为 `0`）。如果有可用定价，媒体成本会按模态计算（按图像、按秒、按字符、按搜索单元），否则为 `0`（故障开放）。

> **缓存命中时的成本语义：** 在语义缓存命中（`X-OmniRoute-Cache-Hit: true`）时，不会调用上游，因此 `X-OmniRoute-Response-Cost` 为 `0.0000000000`（提供此次命中的**增量**成本）。原始成本/本应产生的成本会单独报告在 `X-OmniRoute-Cost-Saved` 中。计费消费者应汇总 `X-OmniRoute-Response-Cost`（命中不产生费用）；缓存分析可以聚合 `X-OmniRoute-Cost-Saved`。

## 独占式托管会话租约

独占式托管会话租约是一种可选加入、与客户端无关的路由契约：一个活动所有者持有一个符合条件的
OmniRoute 连接。它不会租用模型、不要求 OAuth、不识别特定客户端，也不要求特定提供者。

用于身份验证的 API 密钥必须具有 `lease:exclusive` 作用域以及显式的非空
`allowedConnections` 列表。数据库变更边界会在创建密钥和执行部分更新时强制要求这两个字段同时存在。

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

成功的获取、续租和释放响应会公开时间戳、`state` 以及确切的正数
`generation`，但绝不会公开所选连接或凭据。续租和释放请求会在 JSON 请求体中提供
`generation`：

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

活动租约所有者可以显式请求其当前绑定的隐私安全显示元数据：

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

此可选加入的状态操作会在一个数据库事务中，通过不透明所有者、经过身份验证的托管 API 密钥和确切的
活动代次进行栅栏校验。`displayName` 仅是经过裁剪的已配置连接名称；当不存在安全的已配置名称时，
其值为 `null`。OmniRoute 绝不会替换为电子邮件或生成的帐户身份。提供者值是不敏感的显示标签，
绝不是生成的兼容提供者标识符。凭据、令牌、Cookie、原始连接或 API 密钥 ID、所有者哈希、栅栏密钥和
内部路由数据均会被排除。

错误密钥、错误所有者、过时代次、缺失、过期、已释放和已失效的查找请求，都会返回相同的
`409 LEASE_FENCE_STALE` 错误，且不包含连接元数据。收到容量等待响应的客户端没有可供检查的活动绑定。
当路由切换活动租约时，相同的代次仍然有效，状态会以原子方式返回新绑定，而绝不会返回旧绑定。
现有客户端保持不变，因为获取、续租、释放和等待响应仍保留之前的结构。

此服务器契约不会改变标准 OpenAI Codex `/status`。当前标准 Codex 会报告其模型提供者以及内置的
身份验证/帐户状态，但不会呈现任意自定义提供者帐户元数据；后续客户端集成必须调用此操作，并决定
如何显示 `connection.displayName`。

此后，每个托管推理请求都会提供以下两个控制标头：

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

在每次受支持的上游尝试之前，都会立即对确切的所有者、代次、活动连接和经过身份验证的 API 密钥执行
栅栏校验。即使另一个密钥也允许使用同一连接，使用该密钥重放所有者和代次仍会失败。
原始所有者不会被持久化、记录日志、保留在请求快照中，也不会转发到上游。

临时竞争会返回 HTTP `429`、`Retry-After` 以及：

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

此响应仅表示普通符合条件的集合非空，且每个空闲候选连接都被其他活动租约占用。不支持的模型/提供者、
策略不匹配、冷却、配额、健康状况以及其他普通资格检查失败，仍保留其现有的 OmniRoute 响应。

### `x-omniroute-compression`

按请求覆盖压缩计划。优先级最高——高于路由组合覆盖项、活动配置文件、自动触发和面板默认值。
取值：

| 值            | 效果                                                            |
| ------------- | --------------------------------------------------------------- |
| `off`         | 此请求不进行压缩。                                              |
| `default`     | 面板派生的默认配置文件（忽略活动配置文件）。有损引擎保持关闭。  |
| `safe`        | 仅执行去重和空白折叠。                                          |
| `allow-lossy` | 此请求保留操作员计划，包括摘要和样式重写。                      |
| `engine:<id>` | 启用时使用单个引擎，例如 `engine:rtk`。按请求选择性启用该引擎。 |
| `<combo>`     | 命名组合，先按名称（不区分大小写）匹配，再按 ID 匹配。          |

注意：

- 未知值会被忽略（请求绝不会因此被拒绝）；解析会继续沿用正常的操作员优先级。
- 如果多个组合共享同一名称，请传递组合 **id** 以实现确定性匹配。
- 名称为 `off` 或 `default` 的组合无法按名称选择（这些关键字会优先解释）；请通过其 ID 引用此类组合。
- 全局压缩主开关是硬性门控：当全局禁用压缩时，此标头无法启用压缩。

应用的计划会在响应标头中回显：

```
X-OmniRoute-Compression: <mode>; source=<source>
```

其中 `<source>` 为 `request-header`、`routing-override`、`active-profile`、`auto-trigger`、`default` 或
`off` 之一。

## 嵌入

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

可用提供者：Nebius、OpenAI、Mistral、Together AI、Fireworks、NVIDIA、**OpenRouter**、Jina AI。

目录 ID 的格式为 `provider/model`（例如：`jina-ai/jina-embeddings-v5-omni-small`）。注册表中出现的裸 Jina 模型 ID（例如 `jina-embeddings-v5-text-small`、`jina-reranker-v3.5`）也可以解析。Jina 的嵌入、重排、分类和分段功能会优先使用控制台中的 `jina-ai` 凭据；仅当不存在控制台密钥时，才会将 `JINA_AI_API_KEY` 作为备用密钥。`jina-reader` 卡片仅适用于 Reader / `r.jina.ai`（`POST /v1/web/fetch`），不会提供嵌入或重排服务。

声明支持多模态的注册表模型还接受最多 32 个与提供者无关的结构化
项目。媒体项目类型包括 `text`、`image`、`audio`、`video` 和 `document`。其媒体 `source`
可以是 `{"type":"url","url":"https://..."}` 或
`{"type":"base64","data":"...","media_type":"..."}`。

Jina v5 Omni（`jina-ai/jina-embeddings-v5-omni-small`、`jina-ai/jina-embeddings-v5-omni-nano`
以及系列别名 `jina-ai/jina-embeddings-v5-omni` → omni-small）还接受 Jina 原生的
EmbeddingsV5Request 文档，并将其**原样转发**到 `https://api.jina.ai/v1/embeddings`：

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

原生的 `{ image | audio | video | pdf }` 值可以是公共 HTTPS URL、`data:` URI 或原始
base64。OmniRoute 不会将这些对象转换为字符串，也不会获取原生图像 URL——Jina 会自行检索
公共媒体。额外的 Jina 字段（`task`、`normalized`、`truncate`、`embedding_type`）会被
转发。纯文本 Jina SKU 仍会拒绝非文本文档。

安全性和传输限制：

- 远程媒体 URL 必须是公共 HTTPS。规范的 `{type,source:url}` 项目会在服务器端获取
  （重新验证重定向、超时、大小限制、公共 DNS、连接固定），并在调用提供者前内联。
  Jina 原生的 `{image:"https://..."}` 项目在通过相同的公共 HTTPS 检查后会原样转发；
  URL 由 Jina 获取。
- 内联 base64 媒体每个项目解码后不得超过 8 MiB，整个请求解码后不得超过 16 MiB。

提供者转换（规范项目绝不会原样转发）：

- Jina 多模态模型：每个顶层项目都会变成一个按模态键标识的对象
  （`text` / `image` / `audio` / `video` / `pdf`），内联媒体使用 data URI；每个
  顶层项目生成一个向量。
- Gemini Embedding 2 系列：一个顶层数组会变成单个原生的
  `models/{model}:embedContent` 请求，其中包含 `content.parts`（`text` 或
  `inline_data`）。
- llama.cpp（`llama-cpp/<model>`，以及本地服务器已加载的任何模型）：规范的 `text` 项目
  会变成普通字符串，而 `image` / `audio` / `video` 会分别变成一个
  `{"content": [part]}` 对象，使用 llama-server 的聊天内容部分（`image_url`、
  `input_audio`，格式为 `wav` / `mp3` / `flac`，以及 `input_video`），并使用内联数据；
  每个顶层项目生成一个向量。服务器必须使用 `--embedding --mmproj …` 运行；没有投影器时，
  服务器本身会拒绝媒体。`document` 不受支持。
- 没有显式模态元数据的未知/动态模型会以 HTTP 400 拒绝结构化输入。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

不支持的模型/模态组合会返回 HTTP 400，而不会强制转换项目。旧版字符串/令牌请求中的非输入
扩展字段仍会原样传递，不发生变化。

```bash
# 列出所有嵌入模型
GET /v1/embeddings
```

## 图像生成

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

可用的提供者包括 OpenAI（GPT Image 2）、xAI（Grok Image）、Together AI（FLUX）、Fireworks AI、Nebius（FLUX）、Hyperbolic、NanoBanana、**OpenRouter**、**ZenMux**、SD WebUI（本地）和 ComfyUI（本地）。

`n` 会在 `data[]` 中返回 `n` 张图像。对于上游 API 每次调用仅返回一张图像的提供者
（Black Forest Labs、Stability AI、Leonardo、Ideogram、Haiper、Hyperbolic、Magnific/Freepik、
NVIDIA NIM、Cloudflare Workers AI），系统会分别发起 `n` 次上游调用，同时最多有 4 次调用在执行。
固定的 `seed` 会按调用索引进行偏移（`seed`、`seed + 1`、……），因此图像会有所不同，但仍可复现。
`n` 的上限为 10。如果任意一次调用失败，整个请求都会失败。扇出格式列表位于
`open-sse/handlers/imageGeneration/fanOut.ts` 中的 `SINGLE_IMAGE_FANOUT_FORMATS`。

ZenMux 会复用现有的 API 密钥连接，并接受 `zenmux/` 或 `zm/` 前缀：

- `zenmux/openai/gpt-image-2` 使用 ZenMux 的 OpenAI Images API。选项包括 `size`、
  `quality`、`n`、`output_format`、`output_compression`、`background` 和 `response_format`。
- 其他发布者（例如 `zm/meta/muse-image-1.0`）使用 ZenMux 的 Vertex AI `:predict`
  端点。`n` 映射到 `sampleCount`，`aspect_ratio` 映射到 `aspectRatio`，而 `image_size`
  （`1K`、`2K`、`4K`）映射到 `sampleImageSize`。像素 `size` 仅提供宽高比，
  不保证像素尺寸。支持的宽高比、分辨率和数量因模型而异。
- `zm/inclusionai/ming-image-0.1-design` 会自行选择尺寸。请省略 `size`、
  `aspect_ratio` 和 `image_size`；指定这些值会返回 HTTP 400。可以通过 `output_format`
  请求 PNG、JPEG 和 WebP。

此集成支持文生图，不支持参考图像编辑。Vertex 输出会规范化为 `data[].b64_json`；
当仅有图像字节可用时，`response_format: "url"` 会返回上游 HTTPS URL 或 Base64 数据 URL。
空输出或经过过滤的输出会返回错误，而不是空的成功响应。模型访问权限取决于 ZenMux 账户。
请参阅 [ZenMux 的 Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) 和
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image)。

Microsoft 365 Copilot 登录连接会通过 Copilot 的内置图像工具提供
`copilot-m365-web/m365-copilot-image`：每张图像对应一次 Copilot 轮次（`n` 为 1–4），
`size` 仅用于调整图像方向，图像以内联方式返回（`b64_json`，或者当
`response_format: "url"` 时返回数据 URL）。请参阅 [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation)。

## 文档 OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` 通过 `provider/model` 前缀选择 OCR 提供者；不带前缀的模型 ID（例如 `mistral-ocr-latest`）会解析到其注册的提供者，省略 `model` 时默认为 Mistral（`mistral-ocr-latest`）。已注册的提供者（`open-sse/config/ocrRegistry.ts`）：

| 提供者 ID                     | 模型 ID              | `model` 值                                                        | 备注                                                                                    |
| ----------------------------- | -------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest`（或不带前缀的 `mistral-ocr-latest`） | 同步 — 响应直接由单次上游调用返回。                                                     |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                       | 上游异步（`analyze` + 轮询）— 见下文。                                                  |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                           | 同步，通过 Vertex AI 的 `openapi/chat/completions` 合作伙伴端点 — 认证和 URL 详见下文。 |

三个提供者都会返回格式相同的 Mistral 结构化响应：

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence 轮询流程

Azure Document Intelligence 的 `analyze` API 是异步的：初始请求返回 `Operation-Location` 标头，而不是响应正文，必须对结果进行轮询。处理程序（`open-sse/handlers/ocr.ts`）每秒轮询该 URL，最多尝试 30 次；如果轮询响应不是 `ok` 或状态为 `"failed"`，则会快速失败（不再继续轮询）；如果操作在达到尝试次数上限后仍在运行，则返回 `504`。最终的 Azure 响应会在返回给调用方之前，规范化为与 Mistral 使用的相同 `pages`/`markdown` 结构，因此客户端代码无需针对不同提供者进行特殊处理。

### Vertex AI DeepSeek OCR 认证和端点解析

`vertex-deepseek-ocr` 复用了 OmniRoute 已支持的、用于聊天和图像请求的同一套 Vertex AI 认证机制（`open-sse/executors/vertex.ts`）：连接的 API 密钥可以是服务账号 JSON 凭据（通过 JWT bearer 流程交换为短期 OAuth 访问令牌），也可以是已签发的 OAuth 访问令牌，并按原样使用。上游端点 URL 是 Vertex 的通用 `openapi/chat/completions` 合作伙伴端点，根据连接的项目和区域构建：显式设置的 `providerSpecificData.project`/`providerSpecificData.region` 始终优先；否则，项目从服务账号 JSON 的 `project_id` 中派生，区域默认为 `us-central1`。这两种解析均发生在 `open-sse/handlers/ocr.ts` 中（`resolveVertexOcrAccessToken`、`resolveVertexOcrBaseUrl`），并由 `src/app/api/v1/ocr/route.ts` 在调度到 `handleOcr` 之前使用。

```bash
→ 返回 OpenAI 格式的所有聊天、嵌入和图像模型及组合
```

### 模型价格（`pricing`）

当 OmniRoute 知道模型价格时，条目会携带一个 `pricing` 对象。价格来自成本核算使用的价格表：内置默认值、同步价格以及通过 `/api/pricing` 设置的覆盖值。这些是公开标价，因此订阅型提供者也会显示每 token 的价格。

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| 字段                                                            | 单位                          | 说明                                                                                                       |
| --------------------------------------------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `prompt`、`completion`、`input_cache_read`、`input_cache_write` | 每 token 的 USD，十进制字符串 | 兼容 OpenRouter，绝不使用指数表示法。两个缓存字段仅在存在缓存价格时出现。                                  |
| `input`、`output`、`cached`、`cache_creation`                   | 每 1M token 的 USD，数字      | 来自早期目录版本的字段，为现有客户端保留。当价格行包含这些字段时，也会出现 `reasoning` 和 `long_context`。 |

- **组合**携带其第一个可见目标的价格。内置的 `auto/*` 组合会在请求时选择目标，因此没有 `pricing`。
- **免费模型**的价格为零时，会显示 `"0"`（以及 `0`）。没有价格行的模型，如果目录将其标记为免费（`free: true`），或内置免费模型目录中列出了该模型，也会显示 `"0"`。
- **未知价格：**条目没有 `pricing` 键。
- **按额度计费的提供者**（例如 Kiro）按请求而不是按 token 计费。其条目保留之前已有的每 1M token 数值字段，不携带每 token 字符串字段。
- **变体**（推理工作量 ID、无思考别名、发现和网关镜像）会复制其路由到的模型价格。
- 这些字段仅包含基础费率。长上下文层级（数值型 `long_context` 字段）和服务层级乘数（例如 Codex fast 或 flex）不会改变 `prompt` 或 `completion`。
- 对于所有身份验证方式，对象内容都相同，包括带有 `x-api-key` 和 `anthropic-version` 的 Anthropic 风格请求（响应仍为 `{ "object": "list", "data": [...] }`）。实现位置：`src/app/api/v1/models/catalogPricing.ts`。

### 模型 ID 前缀（`?prefix=`）

大多数模型都会以**提供者前缀**发布。获得哪种前缀由 `MODELS_CATALOG_PREFIX_MODE` 功能标志控制，也可以通过查询参数**按请求覆盖**——这对于希望获取简洁列表的客户端很有用，而无需更改服务器范围内对其他所有人的设置：

```bash
GET /v1/models?prefix=alias        # 每个模型一个 id — 短别名前缀
GET /v1/models?prefix=dual         # 两种形式（服务器默认值）
GET /v1/models?prefix=canonical    # 仅完整的提供者 id 前缀
```

| 模式        | 输出                                                     | 说明                                                                                                                                                 |
| ----------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **和** `claude/claude-sonnet-4-6` | **默认值。** 两个 ID 都路由到同一个模型；保留此设置是为了让硬编码了任一形式的客户端配置继续正常工作。目录规模大约翻倍。                              |
| `alias`     | `cc/claude-sonnet-4-6`                                   | 每个模型一个条目。没有独立别名的提供者仍会输出其条目，因此不会遗漏任何内容。                                                                         |
| `canonical` | `claude/claude-sonnet-4-6`                               | 每个模型都使用完整的提供者 ID 前缀输出一个条目。没有独立别名的提供者（例如 `antigravity/…`、`agy/…`）也会在此处输出其单个 ID，因此不会遗漏任何内容。 |

无需查询参数也可以识别 `dual` 模式的镜像：它携带一个指向主 ID 的 `parent` 字段。

渲染模型选择器的客户端应请求 `?prefix=alias`——[OmniCopilot VS Code 扩展](../guides/VSCODE-COPILOT.md)就是这样做的。

### 发现筛选器（`?capability=`、`?min_context=`、`?kind=`、`?q=`）

`GET /v1/models` 接受可选的发现筛选器。不使用任何筛选器时，响应保持不变。筛选器会缩小调用方当前可见的目录范围（先应用 API key 权限），并在 OpenAI 风格的 `limit` / `after` 分页之前运行：

```bash
GET /v1/models?capability=vision&capability=tool_calling   # 列出的每项能力都必须为 true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # 目录中的 `type`；没有该字段的行属于 `chat`
GET /v1/models?q=sonnet&limit=10                           # 对 id 或名称进行不区分大小写的匹配
```

| 参数          | 值                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`、`reasoning`、`structured_output`、`temperature`、`thinking`、`tool_calling`、`vision` |
| `min_context` | 非负整数，与 `context_length` 进行比较                                                              |
| `kind`        | `chat`、`audio`、`embedding`、`image`、`moderation`、`music`、`rerank`、`video`                     |
| `q`           | 1–200 个字符                                                                                        |

未知值，或不是非负整数的 `min_context`（例如 `1.5`），
将返回 HTTP `400`，并在消息中列出有效值。实现位置：
`src/app/api/v1/models/catalogFilters.ts`。

### 模型候选列表（`POST /v1/models/query`）

`POST /v1/models/query` 从同一目录中返回一个简短且确定性的列表，其身份验证和每个密钥的可见性规则与
`GET /v1/models` 相同：

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

所有字段均为可选。`capabilities` 和 `exclude` 接受数组或逗号分隔的字符串；
`max_output` 与 `max_output_tokens` 进行比较。结果按 `owned_by` 排序，然后按 `id` 排序。
`limit` 默认为 `20`，大于 `100` 的值将限制为 `100`。无效 JSON、未知字段或无效值将返回 HTTP `400`。

### 单独隐藏的聊天模型

在提供者页面上标记为**隐藏**的模型会从目录中排除；显式请求时将返回 HTTP `404` / `model_not_found`。
检查使用解析后的提供者和模型，包括提供者别名、兼容提供者节点前缀以及连接默认值。组合会跳过隐藏目标并可以使用可见的同级模型；当不再有可执行目标时，将返回相同的错误代码。取消隐藏将在下一次请求时生效。仅限图像的可见性覆盖不会隐藏具有相同 ID 的聊天模型。

此单独的模型设置与
[模型公开允许/拒绝列表](../routing/MODEL_EXPOSURE_LIST.md)不同；后者会过滤目录展示和自动路由候选项，同时保留显式分发。API 密钥的模型权限仍独立生效。默认目录前缀模式仍为 `dual`。

### 无思考模型变体

对于支持思考能力的 Claude 模型，`/v1/models` 还会展示一个**无思考**变体，其 ID 带有
`claude-3-omniroute-no-thinking/` 前缀：

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

选择此 ID（例如在始终附加 `thinking` 块的 Claude Code 配置中）会解析回实际的 `<provider>/<model>`，并抑制推理——在 `/v1/messages` 路径上使用
`thinking:{type:"disabled"}`，或者在 `/v1/chat/completions` 路径上删除
`reasoning`/`reasoning_effort` 字段。该变体仅会为支持思考能力**且**遵循 `disabled` 设置的 Claude 系列模型列出（例如拒绝 `disabled` 的仅自适应模型将被排除）。运维人员可以通过 `ModelSpec.noThinkingAlias` 按模型强制启用或禁用该变体。

## ElevenLabs 音频生成

在 OmniRoute 中配置一个 `elevenlabs` provider 连接，并提供您的 ElevenLabs API 密钥。
客户端使用其 **OmniRoute** 密钥进行身份验证（`Authorization: Bearer $OMNIROUTE_API_KEY`）；
网关会将已存储的 provider 密钥作为 `xi-api-key` 提供给上游。切勿将 ElevenLabs 密钥作为网关 bearer 令牌发送。

| 方法 | 路径                        | 响应                          | API 密钥端点类别 |
| ---- | --------------------------- | ----------------------------- | ---------------- |
| POST | `/v1/sound-generation`      | 原生音频字节                  | `elevenlabs`     |
| POST | `/v1/music`                 | 原生音频字节                  | `music`          |
| POST | `/v1/music/stream`          | 流式音频字节                  | `music`          |
| POST | `/v1/music/detailed`        | 原生 multipart 音频和编曲方案 | `music`          |
| POST | `/v1/music/detailed/stream` | 原生 SSE 元数据和音频块       | `music`          |
| POST | `/v1/music/plan`            | JSON 编曲方案                 | `music`          |

这些端点与现有的 `/v1/audio/speech`、`/v1/audio/transcriptions`、
`/v1/voices`、`/v1/text-to-speech/{voiceId}` 和 `/v1/speech-to-text` 路由互为补充。原生 JSON 字段
和 `output_format`、`enable_logging` 等查询参数会保留。
`/v1/music/detailed` 响应会保留其 multipart 边界；请将其作为 multipart 进行解析。
`/v1/music/detailed/stream` 返回包含编曲元数据和 Base64 音频块的 `text/event-stream`，
这些内容位于 SSE 事件中。全部六个路由均支持 CORS 预检请求。

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# 一个短音效。时长：0.5 到 30 秒。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# 音乐时长以毫秒表示：3000 到 600000。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

使用 `/v1/music/stream` 和相同的 JSON 请求体即可增量传输音频。编曲请求必须且只能接受
`prompt` 或 `composition_plan` 其中之一；`/v1/music/plan` 要求提供 `prompt`，
并可选接受 `source_composition_plan`。原生 schema 会保留其他 provider 字段，
因此编曲方案版本和微调选项可以传递到 ElevenLabs。

统一的 `/v1/music/generations` 端点还接受
`elevenlabs/music_v1`、`elevenlabs/music_v2` 和 `elevenlabs/music_v2_5`。在存在有效 ElevenLabs 连接时，
这些模型会由音乐目录公开。此端点返回
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`。其 `duration` 字段以
秒为单位，并映射到 `music_length_ms`；显式提供的 `music_length_ms` 优先级更高。
`instrumental` 映射到 `force_instrumental`，但原生字段优先级更高。
流式请求请使用原生流式端点；仅由编曲方案驱动的请求请使用原生编曲端点。

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

端点、模型、预算和连接限制会在调用上游之前生效。原生路由会原样返回上游状态代码和错误正文，
包括计划限制对应的 `402` 和配额限制对应的 `429`。如果存在，`character-cost`、`song-id`、`request-id` 和 `retry-after`
标头也会保留。免费额度余额并不保证可以访问每一种音乐模型、输出格式或 API 功能：
每个请求的访问权限由 ElevenLabs 决定。
统一端点会在 OmniRoute 的标准化错误封装中保留错误状态代码。

上游契约：[音效](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)、
[音乐编曲](https://elevenlabs.io/docs/api-reference/music/compose) 和
[流式音乐详情](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)。

```bash
# 重排序（云注册表提供者，或将 OpenAI 兼容提供者节点表示为 "<prefix>/<model>"）

POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# 视频/音乐生成（带提供者前缀的模型 ID）

POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **重新排序提供者节点：** `POST /v1/rerank` 也会路由到兼容 OpenAI 的提供者节点
> （oMLX、vLLM、Infinity、网关后的 TEI 等），其地址格式为 `<node-prefix>/<model>`。回环
> 节点（`localhost`、`127.0.0.1`、`172.16.0.0/12`）始终符合条件，操作员在
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` 中列出的主机名也符合条件（例如 Docker/Compose 服务名称，如
> `http://reranker:8080/v1`；这些节点会被直接调用，绝不会通过
> `HTTP(S)_PROXY` 或连接固定的代理调用）。位于其他主机上的节点——例如局域网设备或 Tailscale 对等节点——只有在操作员启用
> `RERANK_REMOTE_PROVIDER_NODES` 功能标志，且节点的基础 URL 通过提供者出站 URL 策略
> （`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`）时才符合条件。
> 内存引擎的重新排序步骤会通过回环调用此路由，因此相同规则也适用于 Memory 设置中的
> `rerankProviderModel`。
>
> **本地服务器形式：** 节点会调用 `<base>/v1/rerank`，如果返回 404，则调用 `<base>/rerank`
> （Infinity、TEI）。上游请求体同时包含 Cohere/OpenAI 拼写形式（`documents`、
> `return_documents`）和 TEI 拼写形式（`texts`、`return_text`），上游响应会被规范化为 Cohere 信封格式：
> TEI 的裸 `[{index, score, text}]`、精简网关返回的 `{results: [{index, score}]}`
> 以及 Voyage 风格的 `{data: [...]}`，最终都会以
> `{results: [{index, relevance_score, document?}]}` 的形式返回给客户端，按分数排序并限制为 `top_n` 条。

> **提供者节点发现：** 兼容 OpenAI 的提供者节点上的模型会在 `GET /v1/models` 中
> 以节点前缀显示。没有端点元数据的行（本地 `/v1/models` 列表中通常如此）会继承节点的
> `apiType`，因此 `embeddings` 节点的模型类型为 `type: "embedding"`，而
> `rerank` 节点的模型类型为 `type: "rerank"`，不会默认归类为 chat；同步或手动添加的行如果明确指定了
> `supportedEndpoints`，则仍以该设置为准。

## 搜索 API

Web/搜索提供者抽象层（Tavily、Brave、Exa、Serper 等）。

| 方法 | 路径                   | 描述                                                               |
| ---- | ---------------------- | ------------------------------------------------------------------ |
| GET  | `/v1/search`           | 列出已配置的搜索提供者及其功能                                     |
| POST | `/v1/search`           | 运行搜索查询 — 请求正文由 `v1SearchSchema` 验证，支持缓存/合并请求 |
| GET  | `/v1/search/analytics` | 按提供者统计命中/延迟/缓存数据                                     |

**身份验证：** Bearer API 密钥（`extractApiKey` + `isValidApiKey`）。搜索策略通过 `enforceApiKeyPolicy` 强制执行。

**自动选择：** 未提供 `provider` 时，首先运行已配置连接中最便宜的提供者，下一家最便宜的提供者作为故障转移。免费的最终备用提供者（`duckduckgo-free`）仅在没有其他提供者配置时使用。自托管的 SearXNG 一旦其连接存储了真实的 `baseUrl`（而不是目录默认值 `http://localhost:8888/search`），就会被视为已配置：随后它会作为 $0 提供者排在带密钥的提供者之前，并以最便宜的带密钥提供者作为故障转移，包括 SearXNG 返回 400、401、403 或 404 时。无效的 `http(s)` URL 或指向云元数据地址的 `baseUrl` 不计入配置。存储了令牌的 SearXNG 连接仅在使用 `https://` 或回环 `http://` 时按此方式排序。对于远程的纯 `http://`，它永远不会作为故障转移提供者，而会保持为最终备用提供者，仅在没有其他提供者配置或按名称请求时使用，因此在这两种情况下都会以明文发送令牌。

### Exa 和 Tavily 的 `provider_options`

Exa 和 Tavily 从命名空间对象中读取特定于提供者的字段：
`provider_options.exa`（或 `provider_options["exa-search"]`）以及 `provider_options.tavily`
（或 `provider_options["tavily-search"]`）。只有下面列出的键会被转发。每个键都会在
`open-sse/handlers/search/providerOptionsPassthrough.ts` 中根据各自的 Zod schema
进行检查，类型错误的键会被丢弃。其他任何键都会被忽略，包括身份验证、基础 URL、
`stream` 和 `outputSchema`。其他提供者使用的扁平键（`cx`、`depth` 等）保持原有行为。

| 提供者 | 顶层字段                                                                                                                                                                                                                                                                                                                                                                  | 嵌套                                                                                                                               |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Exa    | `type`、`category`、`userLocation`、`moderation`、`additionalQueries`、`objective`、`systemPrompt`、`compliance`（扁平原始值）、`startPublishedDate`、`endPublishedDate`                                                                                                                                                                                                  | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` 合并到默认值 `{ text: true, highlights: true }` 之上 |
| Tavily | `search_depth`、`chunks_per_source`、`time_range`、`start_date`、`end_date`、`include_published_date`、`filter_by_published_date`、`include_answer`、`include_raw_content`、`include_images`、`include_image_descriptions`、`include_favicon`、`include_domains_mode`、`language`、`filter_by_language`、`auto_parameters`、`exact_match`、`include_usage`、`safe_search` | —                                                                                                                                  |

通用字段始终具有优先权：`query`、`max_results`、`filters`（域名）、`country`，以及
从 `search_type` 派生的主题。在 Exa 中，`search_type: "news"` 会保留
`category: "news"`。Tavily 还接受 `search_type: "finance"`（`topic: "finance"`）。

Firecrawl 搜索成本按每开始处理一组 10 个返回结果计费，每组收费 $0.002（2 个
credits），且每次调用至少计费一组
（[Firecrawl 计费](https://docs.firecrawl.dev/billing)）：返回 11 个结果的成本为 $0.004。

通用的 `time_range` 现在会传递给两个提供者：Exa 获取 `startPublishedDate`（ISO
时间戳），Tavily 获取 `start_date`（`YYYY-MM-DD`）。`provider_options` 中显式指定的
日期会覆盖映射得到的日期。

Exa 结果会在 `provider_raw` 中保留 `id`、`highlights`（每个高亮，而不仅仅是用作
`snippet` 的第一个高亮）、`highlight_scores`、`summary`、`subpages`、`entities`
和 `extras`。Tavily 结果会保留 `images` 和 `favicon`。

Linkup 搜索成本为：`depth` 为 `fast` 和 `standard` 时收费 $0.005，`deep` 时收费
$0.05（[Linkup 定价](https://docs.linkup.so/pages/documentation/development/pricing)），
无论 `depth` 来自 `provider_options` 还是连接设置。

Exa `type: "lite"`（Exa 3.0）接受的字段集合更小，设置任何其他字段时都会拒绝整个请求。
对于 lite，在调用前会丢弃 `additionalQueries`、`systemPrompt` 以及除 `text` 和
`highlights` 之外的所有 `contents` 键。已弃用的 `subpages`、`subpageTarget`、
`highlights.numSentences` 和 `highlights.highlightsPerUrl` 不再转发。

Exa：`auto`（以及旧版 `fast`）每次调用 $0.007，`lite`（以及旧版 `instant`）每次调用 $0.004，均包含 10 条结果；每条额外结果收取 $0.001；设置 `contents.summary` 时，每条返回结果再收取 $0.001。Tavily 的 `search_depth` 为 `basic`、`fast` 和 `ultra-fast` 时，记为 1 个积分（$0.008）；为 `advanced` 时，记为 2 个积分（$0.016）（[Tavily API 积分](https://docs.tavily.com/documentation/api-credits)）。对于设置了 `auto_parameters: true` 且被 Tavily 升级为 advanced 的调用，仍记为 1 个积分。

## Web Fetch API

通过配置的 Web 抓取提供者（Firecrawl、Jina
Reader、Tavily Extract、TinyFish Fetch、Nimble Extract、Parallel Extract）从 URL 提取内容。

Parallel Extract（`parallel-search`，使用与 Parallel Search 相同的 API 密钥）仅返回 Markdown — 任何其他 `format` 都会返回 `400` — 并将内容限制为 100,000 个字符。当目标页面本身无法被提取时，上游会在 HTTP 200 响应中报告该情况；OmniRoute 会将其作为 `422` 及固定消息返回。

| 方法 | 路径            | 描述                                               |
| ---- | --------------- | -------------------------------------------------- |
| POST | `/v1/web/fetch` | 获取/抓取 URL — 请求正文由 `v1WebFetchSchema` 验证 |

**身份验证：** Bearer API 密钥（`extractApiKey` + `isValidApiKey`）。通过 `enforceApiKeyPolicy` 强制执行策略。

**配额感知回退（#8297）：** 未显式指定 `provider` 时，会按照固定优先级顺序遍历池
（`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`）（优先填充）— 已配置但受速率限制的提供者会被跳过，而不是使请求提前结束；可重试的/配额相关的上游失败（HTTP 429 始终如此；对于 Firecrawl/Tavily/TinyFish 的配额型免费层，402/403 也如此 — Jina Reader 除外，普通的 400 错误请求也绝不会如此）会在请求时继续尝试下一个尚未尝试且已配置凭据的提供者。当池中的所有提供者都耗尽时，端点会返回单个 `429`（带有 `Retry-After` 标头），而不是此前通用的 `400`。显式请求 `provider` 时，**不会**静默回退 — 受速率限制或失败的显式提供者会返回其自身的错误（受速率限制时为 `429`，否则为上游状态）。

## WebSocket 流式传输

```bash
GET /v1/ws?handshake=1
```

验证 WebSocket 升级握手，并返回线路协议示例消息（`request`、`cancel`）。实际的 WS 帧由捆绑的 WS 服务器在 Next.js 路由表之外处理。

**身份验证：** 握手期间使用 Bearer API 密钥。

### 通过 WebSocket 使用 Responses API（仅限 codex）

```bash
# 与 HTTP API 使用相同的 host:port（默认为 20128）；升级连接：
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# （或者：-H "Authorization: Bearer <OMNIROUTE_API_KEY>"）

# 第一个帧必须是 response.create：
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket 代理**专门用于 `codex`**（ChatGPT 后端）。它在与 API/仪表板相同的端口上监听路径 `/v1/responses`、`/responses` 和 `/api/v1/responses`。在第一个 `response.create` 帧上，它通过内部 `codex-responses-ws` 桥接进行身份验证和准备，选择一个 codex OAuth 连接，并通过 `wreq-js` 传输层隧道连接到 `wss://chatgpt.com/backend-api/codex/responses`。**不支持 codex 的模型会被拒绝**（`codex_ws_provider_required`）。如需使用配额共享路由，请使用 `model: "qtSd/<group>/codex/<model>"`。相关实现位于 `app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`。

**身份验证：** 握手期间使用 Bearer API 密钥。捆绑的 HTTP 服务器（`server-ws.mjs`）必须是活动入口（当 `app/server-ws.mjs` 存在时，默认即为该入口）。

#### 模型 ID：使用不带 `codex/` 前缀的 ChatGPT ID

当 `supports_websockets = true` 时，OpenAI **Codex CLI** 会在客户端验证模型名称，并拒绝类似 `codex/gpt-5.5` 的提供者前缀 ID（`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`）。请发送**不带前缀的** ID（例如 `gpt-5.5`）。OmniRoute 的桥接仅支持 codex，因此会在通过隧道连接上游之前，将不带前缀的 ID 重新解析为 codex 模型（`resolveCodexWsModelInfo`）— 尽管不带前缀的 `gpt-5.5` 通过 HTTP 时原本会路由到其他提供者。

#### 配置 OpenAI Codex CLI

通过在 `~/.codex/config.toml` 中添加支持 WebSocket 的自定义提供者，将 Codex CLI 指向 OmniRoute（使用单独的 `CODEX_HOME`，以避免修改现有配置）：

```toml
model = "gpt-5.5"                 # 不带前缀的 id — 不是 "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # 不要使用尾部斜杠；WS URL 会据此生成（生产环境中使用 https/wss）
wire_api = "responses"                    # 自 2026 年 2 月起唯一支持的值
supports_websockets = true                # 启用 Responses-over-WS 传输
env_key = "OMNIROUTE_API_KEY"             # 保存 OmniRoute API 密钥（Bearer）
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API 密钥（当 REQUIRE_API_KEY=false 时可使用任意密钥）
codex exec "Responda apenas: PONG"
```

CLI 会将 `base_url + /responses` 升级为 WebSocket，OmniRoute 再将其隧道连接到选定的 codex OAuth 连接。已针对本地服务器完成端到端验证：ChatGPT 返回 `codex.rate_limits` + `response.created`，并流式传输补全结果。

## 自助服务使用（`/api/usage/om-usage`）

任何API密钥都可以读取**它自己的**使用和配额—无管理授权。这是客户端（CLI、 OmniCopilot面板）用来向密钥持有者显示其支出的端点。

```bash
# Text form (the historical contract — plain text for a terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Structured form — what a UI consumes
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

钥匙必须有**`allowUsageCommand`**启用（默认情况下关闭， —仪表板的 API 密钥管理器会根据密钥切换它）。如果没有它，端点就会回答`403`。

`?format=json`返回一个可区分的形状，因此调用者永远不会读取拒绝的数据字段。关于成功：

```jsonc
{
  "allowed": true,
  // present only when the key opted into per-key usage limits (daily/weekly/5-hour USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // the selected provider quota snapshot, or null when nothing is cached yet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // every connection's snapshot, so a UI can render several providers side by side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

拒绝时（`401`错误密钥/不允许`403` ），相同的路由返回`{ "allowed": false, "error": { "message": "…" } }` —存在但为空的`personal`/`provider` （允许密钥，尚未学到任何内容）是与拒绝不同的状态，只有JSON形式区分它们。

**授权：**调用者自己的承载API密钥，通过`isValidApiKey` —进行验证，这不是管理表面 (`/api/keys/…`)，它位于`requireManagementAuth`后面。

### 原始配额百分比与截止值调整后的配额百分比

使用 `/api/usage/om-usage` 时，调用方应注意**纯文本输出**与结构化 **JSON 输出**所呈现百分比之间的区别：

| 方面           | 纯文本格式（`/api/usage/om-usage` / `@@om-usage`）                          | JSON 格式（`?format=json`）                                   |
| :------------- | :-------------------------------------------------------------------------- | :------------------------------------------------------------ |
| **输出字段**   | `NN% left`（例如 `20% left`）                                               | `provider.quotas` / `providers[].quotas`                      |
| **测量值**     | **按截止值调整后的可用额度**：高于截止值阈值的剩余容量                      | **上游原始配额**：未经调整的提供者测量值                      |
| **截止值缩放** | 通过 `effectiveRemainingPercent()` 缩放，使受保护的预留部分显示为 `0% left` | 无（提供者报告的原始快照值）                                  |
| **阈值数据**   | 已纳入显示百分比                                                            | 按连接存储在 `quotaWindowThresholds` 中（或使用服务器默认值） |
| **主要使用者** | 交互式 CLI、终端提示、人类操作员                                            | 程序化集成、信息中心、分析系统、计费跟踪器                    |

#### 截止值调整公式

OmniRoute 支持主动配额截止值，以防止上游配额耗尽（通过连接的
`quotaWindowThresholds`、提供者默认值或全局弹性设置进行配置）。当配额窗口启用截止值阈值（例如 `cutoff = 25%`）时，文本渲染器按如下方式计算剩余额度：

- 如果 `remaining <= cutoff`：返回 `0%`。
- 如果 `remaining > cutoff`：返回 `((remaining - cutoff) / (100 - cutoff)) * 100`。

格式化的文本输出会将结果四舍五入到最接近的整数（`Math.round(...)`）。

#### 示例示例

考虑一个提供者窗口，其**原始使用率为 60%**（因此**原始剩余配额为 40%**），并配置了**25% 的剩余配额截止阈值**：

| 表示形式                        | 计算                                               |  剩余   |           推导出的已使用量            |
| :------------------------------ | :------------------------------------------------- | :-----: | :-----------------------------------: |
| **原始 JSON（`?format=json`）** | 上游快照（`quotas[window]`）                       | **40%** |                **60%**                |
| **文本格式（`NN% left`）**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%**（如果计算 `100 - remaining`） |

- **为什么文本显示剩余 20%：**在账户物理剩余配额 40% 中，25% 由截止策略预留。连接在路由器停止向其路由流量之前，调用方实际上只有 75% 可用余量中的 15% 可用。通过缩放，可以确保连接在路由停止时恰好发出耗尽信号（`0% left`）。
- **为什么 JSON 保留原始值：**JSON 负载返回准确的提供者快照（`UsageSnapshot`），因此外部工具可以访问上游实际使用情况以及连接级别的 `quotaWindowThresholds`，而无需服务器端进行有损缩放。

#### 消费者迁移指南

如果某个外部集成（例如编辑器插件或代理扩展）之前抓取文本端点（`NN% left`）并将已使用百分比计算为 `100 - NN`，那么迁移到 `?format=json` 后：

- 读取原始 JSON 值将反映**实际的上游消耗**（在上述示例中为已使用 60%）。
- 如果该集成希望保留文本端点的可用额度语义，则可以使用连接级覆盖配置中的 `quotaWindowThresholds`，在客户端计算有效剩余量公式。

## 语义缓存

```bash
# 获取缓存统计信息
GET /api/cache/stats

# 清除所有缓存
DELETE /api/cache/stats
```

响应示例：

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### 延迟影响

语义缓存命中（HIT）会在**不调用上游**的情况下从缓存提供响应，因此报告的 `X-OmniRoute-Response-Latency` 接近于零（与原始上游延迟无关）。对延迟敏感的客户端（基准测试、p50/p99 监控）应检查 `X-OmniRoute-Cache-Latency` 响应标头：

| Value       | Meaning                              |
| ----------- | ------------------------------------ |
| `synthetic` | 响应来自缓存；延迟并非真实的上游耗时 |
| _(absent)_  | 响应来自真实的上游调用               |

### 按键绕过缓存

API 密钥可以通过 `cacheDefaultMode` 选择不读取语义缓存：

| Value    | Behavior                       |
| -------- | ------------------------------ |
| `legacy` | 正常的缓存行为（默认）         |
| `bypass` | 完全跳过缓存查找；始终访问上游 |

在创建密钥时（`POST /api/keys`）或更新密钥时（`PATCH /api/keys/[id]`）设置：

```json
{ "cacheDefaultMode": "bypass" }
```

### 按请求绕过缓存

无论密钥设置如何，任何请求都可以绕过缓存：

```
X-OmniRoute-No-Cache: true
```

- `api-call` 不是通用代理。仅接受 Claude `GET
https://api.anthropic.com/api/oauth/usage`，以及 Codex `GET
https://chatgpt.com/backend-api/wham/usage`、`GET .../wham/rate-limit-reset-credits` 和 `POST .../wham/rate-limit-reset-credits/consume`，且各自只能用于对应提供者的账户。其他请求会直接返回 `403`，不联系上游。调用方的 `Authorization` 请求头（包括 `$TOKEN$` 占位符）会被忽略：OmniRoute 注入连接的访问令牌，若即将过期则先刷新，并仅转发允许列表中的请求头（`anthropic-beta`；`OpenAI-Beta`、`Originator`、`Chatgpt-Account-Id`；`Accept`、`Content-Type`）。若缺少 `Chatgpt-Account-Id`，默认使用已保存的工作区 ID。如果首次上游响应为 `401`，则刷新一次，且仅在访问令牌发生变化时重试。每次上游尝试的超时时间为 15 秒，并使用该连接的代理。
- `reset-quota` 不更改终止状态（banned, expired, credits_exhausted）。未知的 `auth_index` 返回 `404`。

`modelOutputOverrides` 中返回这些值，包括没有自定义模型记录的模型。该覆盖设置使用运行时的
`max_output_tokens` 能力，并且在模型重新同步后仍然保留。OpenAI 兼容的

在兼容的提供者节点上，写入路径（`POST`、`PUT`、`PATCH`、`DELETE` 和
`/api/provider-models/validate-and-add`）会将模型 ID 存储为上游的原始 ID：从带前缀的列表中
粘贴的 ID 会移除节点自身前缀的所有连续重复项，并且响应会返回存储的 ID。规范提供者的带斜杠 ID（例如 `nvidia/nemotron-…`）会
按原样存储。`/v1/models` 永远不会发出堆叠的 `<prefix>/<prefix>/<model>` ID。

自定义 Chat Completions 节点会将显式的推理禁用选项适配到上游后端。连接测试成功后，对于 `/models` 条目中证明具有以下已识别 `owned_by` 值的每个精确模型 ID，会自动选择聊天模板控制项：`vllm`、`sglang` 或 `llamacpp`。\
透明的 OpenAI 兼容包装器可能会在嵌套的 `openai` 对象中保留原始模型条目；检测最多会沿着三个此类封装层进行。缺少所有者信息、所有者未知或所有者信息冲突的模型会保留普通的 OpenAI 行为。检测会复用现有的目录请求，不会生成任何补全 token，并且会在连接端点发生变化时失效。

若要为不公开此元数据的后端固定行为，请使用现有的部分提供者更新 API：

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

将该请求体与 `PUT /api/providers/<connection-id>` 一起发送。在该连接上，显式的推理强度 `none` 会以 `chat_template_kwargs.thinking=false` 和 `chat_template_kwargs.enable_thinking=false` 的形式发送。除非服务器端推理规则强制指定某种强度，否则显式的原生模板值仍具有最高优先级。此设置仅在自定义 OpenAI 兼容连接分派 Chat Completions 请求体时生效；Responses 请求和普通提供者仍保留其原生请求格式。将 `reasoningControl` 设置为 `openai` 可强制普通 OpenAI `reasoning_effort` 透传；省略该字段或将其设置为 `null` 则使用自动检测。

当 Claude Code 自动模式分类器请求不包含显式推理控制项时，其原生思考功能默认禁用。检测使用 Claude 格式请求中的分类器系统标记，而不是模型名称或补全限制。显式请求体控制项、受支持的强度/思考标头、路由规则以及已解析的模型强度会保留其现有优先级。两个分类器阶段都会保留其提示词、补全限制、停止序列和真实的上游权限判定；第二阶段仍可能将其请求的可见推理作为普通文本生成。

#### 模型限制来源

`GET /api/models?withLimits=1`（也支持 `true`；使用 `0`/`false` 或省略该参数会保持默认载荷不变）会为每个模型行添加 `contextWindow`、`maxInputTokens`、`maxOutputTokens` 和 `capsSource` 对象。`capsSource` 会指明为每个限制提供值的规则，因此可以追溯异常限制（例如，1M 模型被限制为 128k）的来源。解析后的值与路由使用的值相同；该标志仅添加字段，不会更改任何值。任何其他 `withLimits` 值都会被拒绝并返回 `400`。

| `capsSource` value                           | Origin                                                       |
| -------------------------------------------- | ------------------------------------------------------------ |
| `override:context`                           | 持久化的上下文窗口覆盖项（`model_context_overrides`）        |
| `override:max_input` / `override:max_output` | 持久化的 `max_input_tokens` / `max_output_tokens` 能力覆盖项 |
| `static-authoritative:<provider>/<model>`    | 静态权威上下文窗口表                                         |
| `synced:<provider>/<model>`                  | models.dev 同步的能力行                                      |
| `registry:<provider>/<model>`                | 提供者注册表条目                                             |
| `spec:<model>`                               | 静态模型规范                                                 |
| `effort-base:` prefix                        | 从带有推理强度后缀的变体的基础模型借用的行                   |
| `none`                                       | 没有来源声明该限制（值为 `null`）                            |

实现位置：`src/lib/modelCapabilities.ts` 中的 `getResolvedModelCapabilitiesWithLimitSources()`，以及 `src/lib/modelCapabilityLimits.ts` 中的优先级链。

### 视频帧深入分析

`GET /api/v1/video-bridge/drilldown` 读取在明确同意的 Video Bridge 请求后，通过
`x-omniroute-video-drilldown` 返回的租户绑定不透明句柄。
读取和 `DELETE` 始终需要有效的 API 密钥，以及操作员独立拥有的
`modalityBridgeVideoDrilldownRemoteEnabled` 权限。
生产环境中的保留功能还需要 `modalityBridgeVideoDrilldownEnabled`，并且每个分段都必须严格设置
`drilldown: true`。
如果密钥具有非空的端点允许列表，则无论调用方使用 `/v1` 还是 `/api/v1`，
该列表都必须包含 `video`，GET 和 DELETE 均是如此。

GET 查询参数：必需的 `handle`；可选的 `variant`（`preview`、`standard`、`detail`）、
`limit`（1–8；接受旧版参数 `frames`，但不能与 `limit` 组合）、
从零开始计数的 `page`，以及以秒为单位的 `start`/`end`。
同时提供两个焦点边界时，`end` 必须大于 `start`。
重复或未知的查询键会被拒绝。
成功响应包含 `derivation`、`durationSeconds`、`frames`、
`hasMore`、`page`、`variant`，以及可选的 `focusWindow`；无存储 JSON（no-store JSON）大小上限为
32 MiB，其中包括 Base64。
输出过大时返回 413；请请求更少的帧。

`DELETE /api/v1/video-bridge/drilldown?handle=...` 返回 `{ "removed": 0|1 }`。
未知、过期以及跨密钥 GET 请求均返回无法区分的 404 响应；跨密钥 DELETE 无法删除所有者的条目。
禁用访问返回 403，缺少或无效的身份验证返回 401，无效查询返回 400，取消操作返回 499，临时错误返回 503。
句柄仅在进程本地有效，十分钟后过期，并且不会在重启后保留。
新句柄使用 `v1.` 加上 32 字节的随机 Base64URL 令牌；仅保留令牌哈希。
为兼容性，旧版 64 位十六进制令牌仍可按语法读取。
有关同意、配额和变体派生的详细信息，请参阅[Video Bridge 防护措施](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets)。

### 版本和发布渠道

```bash
GET /api/system/version
```

仅限回环地址的管理路由（需要管理员身份验证）。返回正在运行的版本、最新
发布版本和自动更新状态。`releaseChannel` 和 `channels` 是新增字段（rail 3.8.54）；`channel` 保持其原有含义——仪表板更新器使用的部署模式
（`npm`、`source` 或 `docker-compose`）。

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — 正在运行的构建所使用的 npm 渠道：对于 `-nightly.*` 版本为
  `nightly`，对于其他预发布版本（`-rc.*`、`-beta.*`、`-alpha.*`）为 `next`，对于版本号低于
  `channels.latest` 中主要版本的稳定版本为 `lts`，否则为 `latest`。规则与
  `scripts/release/dist-tag.mjs` 相同，该文件会在发布时选择 npm dist-tag。
- `channels` — 每个 dist-tag 的已发布最新版本，来自 `npm view omniroute dist-tags`（通过注册表
  HTTP 回退机制获取），并与 `latest` 使用相同的 10 分钟 TTL 进行缓存。`latest` 始终存在
  （依次回退到 `latest` 字段，然后回退到 `"unavailable"`）；仅当相应 dist-tag 存在时，才会显示
  `next`、`nightly` 和 `lts`。带有 `Cache-Control: no-cache` 的请求会刷新这两个查询。

渠道模型（4.0 GA 之前，`latest` = v3；`next` = rc；`nightly` = `develop` 构建；
4.0 GA 之后，`lts` = v3 补丁版本）详见 `docs/ops/RELEASE_STRATEGY.md`。

## 音频转录

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

使用任何已配置的 STT 提供者转录音频文件。第一个路径段选择原生提供者（`openai/…`、`deepgram/…`）。重新导出其他供应商模型的网关使用限定 ID
（`openrouter/deepgram/nova-3`）。

**请求：**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**响应：**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**模型 ID 示例：**`openai/whisper-1`（需要 OpenAI 密钥）、
`openrouter/deepgram/nova-3`（需要 OpenRouter 密钥）、
`deepgram/nova-3`（需要原生 Deepgram 密钥）。单独的
`deepgram/nova-3` 请求**不会**使用 OpenRouter。

**支持的格式：**`mp3`、`wav`、`m4a`、`flac`、`ogg`、`webm`。

**Gemini Live（`gemini/gemini-3.5-transcribe-live`）：**通过 Gemini Live
WebSocket 进行文件模式转录（需要 Gemini API 密钥）。上传的文件会使用 `ffmpeg`
转换为 16 kHz 单声道 PCM（除非文件已经是 16 kHz 单声道 PCM WAV，否则 `ffmpeg` 必须位于
`PATH` 中），然后流式传输到会话，并以 `{ "text": "..." }` 的形式返回最终文本。可选的
`language` 和 `prompt` 表单字段会被转发。限制：超过 25 MiB 的上传文件或解码后时长超过 10 分钟的音频会返回
`413`；运行时间超过 60 秒的转换会被终止并返回 `504`。API 密钥仅通过
`x-goog-api-key` 标头发送，绝不会出现在 WebSocket URL 中。

## 令牌限制

每个 API 密钥的**令牌**配额（与上述基于 USD 的预算不同）。该限制在请求路径上以内联方式强制执行：当某个密钥在当前时间窗口中的使用量达到其限制时，请求将被 `429 Too Many Requests` 拒绝。限制可以限定于特定的 `model`、`provider`，或在整个密钥范围内应用于 `global`；当多个限制与请求匹配时，以限制最严格的一个为准。

```bash
# 列出某个密钥的令牌限制（包含实时窗口使用量）
GET /api/usage/token-limits?apiKeyId=key-123

# 创建或更新令牌限制
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# 按 id 删除令牌限制
DELETE /api/usage/token-limits?id=tl-abc
```

> **架构说明**（`setTokenLimitSchema`）：`apiKeyId` 和 `scopeType`（`model` | `provider` | `global`）为必填项。除非 `scopeType` 为 `global`，否则 `scopeValue` 为必填项（例如，对于 `model` 范围为模型 id，对于 `provider` 范围为提供者 id）。`tokenLimit` 必须为正整数（会从字符串强制转换）。可选项：`id`（创建时省略，更新时提供）、`resetInterval`（`daily` | `weekly` | `monthly`，默认为 `monthly`）、`resetTime`（`HH:MM`）、`enabled`（默认为 `true`）。`GET` 响应会为每个限制补充 `tokensUsed`、`remaining`、`windowStart`、`periodStartAt` 和 `nextResetAt`。这是一个管理类端点（由授权管道集中执行身份验证）。

## 请求处理

1. 客户端向 `/v1/*` 发送请求
2. 路由处理程序调用 `handleChat`、`handleEmbedding`、`handleAudioTranscription` 或 `handleImageGeneration`
3. 解析模型（直接指定提供者/模型，或使用别名/组合）
4. 从本地数据库中选择凭据，并筛选可用账户
5. 对于聊天请求：`handleChatCore` 检查语义缓存/签名缓存，并解析组合压缩设置
6. 启用主动压缩后，在提供者转换前运行（`lite`、Caveman、RTK 或堆叠模式）
7. 提供者执行器发送上游请求
8. 将响应转换回客户端格式（聊天请求），或原样返回（嵌入/图像/音频请求）
9. 记录使用量、压缩分析数据和请求日志
10. 根据组合规则，在发生错误时应用回退机制

完整架构参考：[`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## 弹性（扩展）

OmniRoute 提供三种相互独立的临时故障机制；以下管理端点允许操作员读取并覆盖这些机制：

| 范围         | 状态存储                          | 读取                                      | 重置 / 清除                              |
| ------------ | --------------------------------- | ----------------------------------------- | ---------------------------------------- |
| 提供者断路器 | `domain_circuit_breakers` + 内存  | `/api/monitoring/health`                  | `POST /api/resilience/reset`             |
| 连接冷却期   | 提供者连接上的 `rateLimitedUntil` | `/api/rate-limits`、`/api/providers/[id]` | （惰性重新启用；通过提供者 PUT 清除）    |
| 模型锁定     | 内存中的模型可用性注册表          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns` |

`PATCH /api/resilience` 接受 `providerBreaker.oauth` 和 `providerBreaker.apikey` 下的提供者断路器覆盖配置。每个配置文件支持 `degradationThreshold`、`failureThreshold` 和 `resetTimeoutMs`；相同字段也会显示在仪表板 → 设置 → 弹性中。

```bash
# 清除单个模型锁定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# 清除所有锁定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

完整的概念参考和断路器默认值，请参阅 [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" 和 [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)。

### 速率限制队列与自动启用安全网

- **受支持的写入路径**：带有请求体 `{"connectionId": "<id>", "enabled": true|false}` 的 `POST /api/rate-limits` 是用于切换连接速率限制保护的受支持管理端点。`PUT /api/providers/[id]` 不会修改或切换 `rateLimitProtection`（#11278）。
- **`enabled: false` 的语义**：将 `enabled: false` 设置为 false 会移除该连接的显式保护，但**不会**使活动的 API 密钥连接退出全局自动启用安全网（`autoEnableApiKeyProviders = true`）。在 `reconcileEnabledConnections`（`open-sse/services/rateLimitManager.ts`）中，`false` 和 `undefined` 等效；没有显式保护的活动 API 密钥连接仍会受到自动启用安全网的保护。
- **全局禁用**：如果要在没有速率限制队列的情况下运行 API 密钥连接，请通过 `RATE_LIMIT_AUTO_ENABLE=false`（环境变量）或 `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`（设置 → 弹性 / `PATCH /api/resilience`）全局禁用安全网。

## A2A 服务器

OmniRoute 提供一个 A2A（Agent-to-Agent）JSON-RPC 2.0 端点，以及一个用于检查和仪表板的 REST 包装器。

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # 除非设置了 OMNIROUTE_API_KEY，否则可选
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

支持的方法（均受 `settings.a2aEnabled` 控制）：

| 方法             | 描述                                             |
| ---------------- | ------------------------------------------------ |
| `message/send`   | 同步执行技能；返回 `{task, artifacts, metadata}` |
| `message/stream` | 对同一技能集执行流式 SSE                         |
| `tasks/get`      | 根据 `taskId` 获取任务                           |
| `tasks/cancel`   | 根据 `taskId` 取消任务                           |

内置技能：`smart-routing`、`quota-management`、`provider-discovery`、`cost-analysis`、`health-report`。

### Agent Card

```bash
GET /.well-known/agent.json
```

返回公开的 A2A agent card（名称、描述、功能、技能目录、身份验证方案），并公开缓存 1 小时。无需身份验证。

### REST 辅助接口

| 方法 | 路径                         | 描述                                                                                                           |
| ---- | ---------------------------- | -------------------------------------------------------------------------------------------------------------- |
| GET  | `/api/a2a/status`            | A2A 是否启用 + 任务统计信息 + 已缓存的 agent card 摘要                                                         |
| GET  | `/api/a2a/tasks`             | 列出任务 — `?state=submitted\|working\|completed\|failed\|cancelled`、`?skill=`、`?limit=`（≤200）、`?offset=` |
| POST | `/api/a2a/tasks`             | （未实现为 REST 辅助接口 — 通过 JSON-RPC `message/send` 创建）                                                 |
| GET  | `/api/a2a/tasks/[id]`        | 获取单个任务                                                                                                   |
| POST | `/api/a2a/tasks/[id]/cancel` | 取消任务                                                                                                       |

**身份验证：** REST 辅助接口无需管理身份验证即可运行（可由仪表板读取）；如果配置了 `OMNIROUTE_API_KEY`，JSON-RPC `/a2a` 路由将使用 Bearer 身份验证。

## 身份验证

请参阅[管理身份验证](../guides/MANAGEMENT-AUTH.md)，了解四类凭据（仪表板会话、本地 CLI 令牌、`oma_live_…` 访问令牌、管理作用域 API 密钥）以及它们与推理密钥的区别。

- 仪表板路由（`/dashboard/*`）使用 `auth_token` Cookie
- 登录使用已保存的密码哈希；回退时使用 `INITIAL_PASSWORD`
- 可通过 `/api/settings/require-login` 切换 `requireLogin`
- 当 `REQUIRE_API_KEY=true` 时，`/v1/*` 路由可选择要求 Bearer API 密钥
- 本参考中的“管理令牌”/“管理作用域 API 密钥”指该指南中列出的凭据类型之一，而不是某种未定义的额外密钥类型

> **破坏性变更（v3.8.0）** — `/api/v1/agents/tasks/*` 和冷却时间管理端点现在要求**管理身份验证**（仪表板 `auth_token` Cookie 或管理作用域 API 密钥）。此前未经身份验证调用这些路由的客户端将收到 `401 Unauthorized`。请参阅提交 `588a0333`（`fix(auth): require management auth for agent and cooldown APIs`）。
