## 🎯 使用场景

### 场景 1：“我有 Claude Pro 订阅”

**问题：** 配额未使用便失效，高强度编程时会遇到速率限制

```
组合："maximize-claude"
  1. cc/claude-opus-4-7        （充分利用订阅）
  2. glm/glm-4.7               （配额用尽时的低价备用方案）
  3. if/qwen3.8-max-preview       （免费的紧急后备方案）

每月费用：$20（订阅）+ 约 $5（备用）= 总计 $25
相比之下：支付 $20 却遭遇使用限制，令人沮丧
```

### 场景 2：“我希望零成本”

**问题：** 无力承担订阅费用，但需要可靠的 AI 编程工具

```
组合："zero-cost"
  1. if/kimi-k2.7-code          （标注为免费访问；可能存在速率限制）
  2. kr/qwen3-coder-next        （Kiro 免费后备方案）

每月费用：$0
质量：请针对你的工作负载核实模型、限制、隐私和 SLA
```

### 场景 3：“我需要全天候编程，不能中断”

**问题：** 截止日期临近，无法承受服务中断

```
组合："always-on"
  1. cc/claude-opus-4-7        （最佳质量）
  2. cx/gpt-5.5                （第二个订阅）
  3. glm/glm-4.7               （价格低廉，每日重置）
  4. minimax/MiniMax-M2.1      （最便宜，5 小时重置）
  5. if/deepseek-v4-flash       （标注为免费访问；可能存在速率限制）

结果：5 层后备方案可增强韧性；无法保证上游服务的可用性
每月费用：$20-200（订阅）+ $10-20（备用）
```

### 场景 4：“我想在 OpenClaw 中使用免费 AI”

**问题：** 需要在消息应用中使用完全免费的 AI 助手

```
组合："openclaw-free"
  1. if/qwen3.8-max-preview     （标注为免费访问；可能存在速率限制）
  2. if/deepseek-v4-flash       （标注为免费访问；可能存在速率限制）
  3. if/kimi-k2.7-code          （标注为免费访问；可能存在速率限制）

每月费用：$0
可通过以下平台访问：WhatsApp、Telegram、Slack、Discord、iMessage、Signal……
```

## 📖 提供者设置

要从 CSV 或 JSON 文件批量添加 API 密钥连接，请使用 **控制面板 → 提供者 → 从文件导入**。各列按位置对应（`provider,name,apiKey,baseUrl,priority`）；`provider` 必须已作为托管提供者或兼容节点存在。请参阅[从 CSV 或 JSON 文件导入提供者](../providers/CSV-IMPORT.md)。

### 🔐 订阅提供者

#### Claude Code (Pro/Max)

```bash
控制面板 → 提供者 → 连接 Claude Code
→ OAuth 登录 → 自动刷新令牌
→ 5 小时 + 每周配额跟踪

模型：
  cc/claude-opus-4-7
  cc/claude-sonnet-4-6
  cc/claude-haiku-4-5-20251001
```

**专业提示：** 复杂任务使用 Opus，追求速度则使用 Sonnet。OmniRoute 会按模型跟踪配额！

OmniRoute 主机上没有浏览器？在任何已登录 Claude Code 的环境中运行 `claude setup-token`，然后将有效期一年的令牌粘贴到 **Setup Token** 选项卡中。请参阅[使用 setup token 的 Claude Code](../providers/CLAUDE_CODE_SETUP_TOKEN.md)。

Claude 及与 Claude Code 兼容的路由会为 Opus 和 Sonnet 模型保留 `max` 思考强度。Haiku 模型不接受 `max` 强度级别，因此 OmniRoute 会在向上游发送请求前，将其降级为较高的思考预算。

#### OpenAI Codex (Plus/Pro)

```bash
控制面板 → 提供者 → 连接 Codex
→ OAuth 登录（端口 1455）
→ 每 5 小时 + 每周重置

模型：
  cx/gpt-5.5
  cx/gpt-5.4
  cx/gpt-5.3-codex
  cx/gpt-5.3-codex-spark
```

#### GitHub Copilot

```bash
控制面板 → 提供者 → 连接 GitHub
→ 通过 GitHub 进行 OAuth
→ 每月重置（每月 1 日）

模型：
  gh/gpt-5.5
  gh/gpt-5.4
  gh/claude-sonnet-4.6
  gh/claude-opus-4.7
  gh/gemini-3.1-pro-preview
```

**用法：** `qianfan/ernie-5.1`、`qianfan/ernie-x1.1` 或其他与 OpenAI 兼容的 Qianfan 模型 ID。

## 🎨 组合

你可以在 **仪表盘 → 组合** 中通过拖动每张卡片上的手柄直接重新排列组合卡片。顺序会存储在 SQLite 中，并在重新加载时恢复。

### 示例 1：最大化利用订阅 → 低成本备用

```
仪表盘 → 组合 → 新建
```

## 🚀 部署

### 全局 npm 安装（推荐）

```bash
npm install -g omniroute

# 创建配置目录
mkdir -p ~/.omniroute

# 创建 .env 文件（参见 .env.example）
cp .env.example ~/.omniroute/.env

# 启动服务器
omniroute
# 或使用自定义端口：
omniroute --port 3000
```

CLI 会自动从 `~/.omniroute/.env` 或 `./.env` 加载 `.env`。

### 托盘模式

在系统托盘中启动 OmniRoute：

```bash
omniroute serve --tray
```

服务器和托盘准备就绪后，该命令会返回。

服务器将在没有终端的情况下继续运行。

托盘模式支持 macOS、Windows 和图形化 Linux 会话。托盘模式不会自动打开仪表盘。

可以通过托盘菜单执行以下操作：

- 打开仪表盘。
- 打开 `/dashboard/logs`。
- 更改自动启动设置。
- 停止 OmniRoute。

不要将 `--tray` 与以下选项组合使用：

- `--daemon`
- `--log`
- `--no-recovery`

这些模式需要不同的进程所有权。

启用在下次登录计算机时启动：

```bash
omniroute autostart enable
```

在 macOS、Windows 和图形化 Linux 会话中，自动启动会使用托盘模式。无头 Linux 会使用现有的 systemd 用户服务。

禁用登录时启动：

```bash
omniroute autostart disable
```

### 卸载

当你不再需要 OmniRoute 时，我们提供了两个快速脚本以进行彻底移除：

| 命令                     | 操作                                                         |
| ------------------------ | ------------------------------------------------------------ |
| `npm run uninstall`      | 移除系统应用，但会**保留 `~/.omniroute` 中的数据库和配置**。 |
| `npm run uninstall:full` | 移除应用，并永久**删除所有配置、密钥和数据库**。             |

> 注意：要运行这些命令，请导航到 OmniRoute 项目文件夹（如果你克隆了该项目），然后运行它们。或者，如果是全局安装，只需运行 `npm uninstall -g omniroute`。

```bash
		aarch64*) _gyp_arch=arm64 ;;

	npm run test:unit
}

}
```

### 环境变量

| 变量                                    | 默认值                               | 描述                                                                            |
| --------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------- |
| `JWT_SECRET`                            | `omniroute-default-secret-change-me` | JWT 签名密钥（**在生产环境中请更改**）                                          |
| `INITIAL_PASSWORD`                      | `CHANGEME`                           | 首次登录密码                                                                    |
| `DATA_DIR`                              | `~/.omniroute`                       | 数据目录（数据库、使用情况、日志）                                              |
| `PORT`                                  | 框架默认值                           | 服务端口（示例中为 `20128`）                                                    |
| `HOSTNAME`                              | 框架默认值                           | 绑定主机（Docker 默认为 `0.0.0.0`）                                             |
| `NODE_ENV`                              | 运行时默认值                         | 部署时设置为 `production`                                                       |
| `NEXT_PUBLIC_BASE_URL`                  | `http://localhost:20128`             | 提供给仪表板并暴露给服务器的公共基础 URL（取代旧版 `BASE_URL`）                 |
| `NEXT_PUBLIC_CLOUD_URL`                 | `https://omniroute.dev`              | 云同步端点的基础 URL（取代旧版 `CLOUD_URL`）                                    |
| `API_KEY_SECRET`                        | `endpoint-proxy-api-key-secret`      | 用于生成 API 密钥的 HMAC 密钥                                                   |
| `REQUIRE_API_KEY`                       | `false`                              | 对 `/v1/*` 强制要求 Bearer API 密钥                                             |
| `ALLOW_API_KEY_REVEAL`                  | `false`                              | 允许经过身份验证的仪表板用户按需查看存储的完整 API 密钥值                       |
| `PROVIDER_LIMITS_SYNC_INTERVAL_MINUTES` | `70`                                 | 服务器端刷新已缓存 Provider Limits 数据的频率；界面中的刷新按钮仍会触发手动同步 |
| `DISABLE_SQLITE_AUTO_BACKUP`            | `false`                              | 禁用写入、导入或恢复前的自动 SQLite 快照；手动备份仍可用                        |
| `APP_LOG_TO_FILE`                       | `true`                               | 将应用程序日志和审计日志输出到磁盘                                              |
| `AUTH_COOKIE_SECURE`                    | `false`                              | 强制使用 `Secure` 身份验证 Cookie（适用于 HTTPS 反向代理之后）                  |
| `CLOUDFLARED_BIN`                       | 未设置                               | 使用现有的 `cloudflared` 二进制文件，而不是由系统管理下载                       |
| `CLOUDFLARED_PROTOCOL`                  | `http2`                              | 托管 Quick Tunnels 的传输协议（`http2`、`quic` 或 `auto`）                      |
| `OMNIROUTE_MEMORY_MB`                   | `512`                                | Node.js 堆内存限制（MB）                                                        |
| `PROMPT_CACHE_MAX_SIZE`                 | `50`                                 | 提示词缓存条目的最大数量                                                        |
| `SEMANTIC_CACHE_MAX_SIZE`               | `100`                                | 语义缓存条目的最大数量                                                          |

```bash
  -d '{"provider": "openai", "modelId": "gpt-5.2", "modelName": "GPT-5.2"}'

# 列出：curl http://localhost:20128/api/provider-models?provider=openai
# 移除：curl -X DELETE "http://localhost:20128/api/provider-models?provider=openai&model=gpt-5.2"
```

或使用 Dashboard：**Providers → [Provider] → Custom Models**。

注意：

- OpenRouter 以及 OpenAI/Anthropic 兼容提供者仅从 **Available Models** 管理。手动添加、导入和自动同步都会进入同一个可用模型列表，因此这些提供者没有单独的 Custom Models 部分。
- **Custom Models** 部分面向不提供受管可用模型导入的提供者。

### 自定义 OpenAI 兼容提供者

任何使用 OpenAI API 的网关（自托管代理、vLLM、第三方聚合器）都可以作为独立的提供者节点添加：

1. **Providers → Add OpenAI Compatible**。
2. **Name**：节点的显示标签。
3. **Prefix**：路由名称。客户端以 `<prefix>/<model>` 的形式调用模型，因此前缀为 `mygw` 的节点将提供 `mygw/gpt-4o-mini`。必填；没有字符限制。
4. **API Type**：网关提供的端点类型（Chat Completions、Responses、Embeddings、音频、图像）。
5. **Base URL**：API 根地址，包含到 `/v1` 为止（例如 `https://gateway.example.com/v1`），而不是完整的 `/chat/completions` 路径。使用非标准路径的网关可在 **Advanced Settings** 中设置（chat path、models path）。
6. **API Key (for Check)** 字段仅用于测试连接。创建节点后，打开它并使用 **Add Connection** 来存储请求实际使用的密钥。

该节点会获得一个形如 `openai-compatible-<apiType>-<uuid>` 的内部 id；你永远不需要输入它，前缀才是公开名称。

#### 保留前缀

前缀不能是内置提供者的 id 或别名（例如 `openai`、`cf`），也不能是已退役提供者的 id。模型解析器会先检查内置 id 和别名，再检查自定义节点，因此使用这些前缀的节点将永远不会收到流量：`<prefix>/model` 会被路由到内置提供者，或者在该提供者已退役时关闭式失败（fail closed）。使用此类前缀创建或编辑节点将被拒绝，并返回：

```text
prefix: "<prefix>" is a reserved provider prefix — choose a different prefix (reserved ids/aliases cannot be used for custom nodes because requests like <prefix>/model route to a built-in provider or fail closed when retired)
```

请选择一个不同的前缀（`mygw`、`acme-proxy`）。如果对自定义节点的请求失败，且错误信息中提及了内置提供者或其凭据，请检查该节点的前缀是否为保留前缀：在此规则引入之前保存的节点仍然会被存储，但其前缀会路由到内置提供者。编辑该节点并为其指定新前缀。

#### 按连接配置的网关选项

这些键放在连接的 `providerSpecificData` 中（例如通过 `PUT /api/providers/{id}`）：

- `toolNameMaxLength`（整数，1–1024）— 用于网关拒绝过长工具名称的 OpenAI chat 格式兼容连接。过长的名称将以短别名发送，并在响应中还原。
- `quotaEndpoint` — 网关的配额/额度端点，用于仪表板的配额条和配额感知路由。在 OpenAI 兼容和 Anthropic 兼容连接上均可使用；完整结构文档见 `open-sse/services/usage/openaiCompatible.ts`。

```json
{
  "toolNameMaxLength": 64,
  "quotaEndpoint": {
    "url": "https://gateway.example.com/key/info",
    "auth": "bearer",
    "quotas": {
      "budget": { "used": "$.info.spend", "total": "$.info.max_budget", "currency": "USD" }
    }
  }
}
```

### 串联 OmniRoute 对等节点

另一个 OmniRoute 网关可以作为 **Custom OpenAI-compatible** 提供者添加。使用对等节点的 `/v1` base URL 和由该对等节点签发的专用、最小权限 API 密钥。

对于双向或多跳链，请在每个网关上启用可选开启的环路防护：

```bash
# gateway-a
OMNIROUTE_INSTANCE_ID=gateway-a
OMNIROUTE_PEER_URLS=http://gateway-b:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

```bash
# gateway-b
OMNIROUTE_INSTANCE_ID=gateway-b
OMNIROUTE_PEER_URLS=http://gateway-a:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

只有发送到明确列入白名单的对等 URL 的请求才会携带 `X-OmniRoute-Peer-Trace` 标头。当网关检测到重复的实例 ID 或跳数预算耗尽时，会以 HTTP `508 Loop Detected` 拒绝请求；普通上游提供者不会收到任何对等元数据。

对等串联不是数据库复制或主机故障转移。每个网关都保持独立的 SQLite 状态、缓存、速率计数器和会话。如需主动/被动或主动/主动高可用性，请使用带健康检查的反向代理或客户端故障转移，并且永远不要将一个 SQLite 数据库挂载到多个正在运行的 OmniRoute 实例中。

### Cloudflare Quick Tunnel

- 在 **Dashboard → Endpoints** 中可用，适用于 Docker 及其他自托管部署
- 创建一个临时的 `https://*.trycloudflare.com` URL，转发到你当前的 OpenAI 兼容 `/v1` 端点
- 首次启用时仅在需要时安装 `cloudflared`；后续重启会复用同一个托管二进制文件
- Quick Tunnel 不会在 OmniRoute 或容器重启后自动恢复；需要时请从仪表盘重新启用

- 如果你希望使用预装的 `cloudflared` 二进制文件而非托管下载版本，可设置 `CLOUDFLARED_BIN`
- Cloudflare Quick Tunnel、Tailscale Funnel 和 ngrok Tunnel 面板可在 **Settings → Appearance** 中显示或隐藏。隐藏面板不会停止正在运行的隧道。

### 路由策略

通过 **Dashboard → Settings → Routing** 配置。仪表盘提供六种最常用的策略；组合（combo）和自动路由器在内部支持更广泛的策略集。

**仪表盘可见的策略（账户级路由）：**

| 策略                           | 描述                                                                |
| ------------------------------ | ------------------------------------------------------------------- |
| **Fill First**                 | 按优先级顺序使用账户——主账户处理所有请求，直到不可用                |
| **Round Robin**                | 在所有账户间循环，支持可配置的粘性限制（默认：每个账户 3 次调用）   |
| **P2C (Power of Two Choices)** | 随机选取 2 个账户并路由到更健康的那个——在感知健康状态的同时平衡负载 |
| **Random**                     | 使用 Fisher-Yates 洗牌算法为每个请求随机选择账户                    |
| **Least Used**                 | 路由到 `lastUsedAt` 时间戳最旧的账户，均匀分配流量                  |
| **Cost Optimized**             | 路由到优先级值最低的账户，优先选择成本最低的提供者                  |

**高级组合与自动策略**（可按组合配置，或通过 `auto/*` 前缀配置——参见 [AUTO-COMBO.md](../routing/AUTO-COMBO.md)）：

- `priority` —— 严格按顺序执行，绝不轮询
- `weighted` —— 按每个模型的权重按比例分配流量
- `fill-first` —— 持续使用第一个模型，直到达到限额
- `round-robin` / `strict-random` / `random`
- `p2c`（Power of Two Choices，二选一幂）
- `least-used` 与 `cost-optimized`
- `auto` —— 基于评分在所有候选中驱动选择
- `lkgp`（Last Known Good Provider，最近已知可用提供者）—— 固定使用最近成功的提供者，然后回退到规则
- `context-optimized` —— 选择剩余上下文窗口最大的模型
- `context-relay` —— 为后续轮次串联长上下文模型

#### 外部粘性会话请求头

对于外部会话亲和性（例如，位于反向代理之后的 Claude Code/Codex 代理），发送：

```http
X-Session-Id: your-session-key
```

OmniRoute 也接受 `x_session_id`，并在 `X-OmniRoute-Session-Id` 中返回实际生效的会话键。

如果你使用 Nginx 并发送下划线形式的请求头，请启用：

```nginx

```

#### 通配符模型别名


通配符支持 `*`（任意字符）和 `?`（单个字符）。

定义适用于所有请求的全局回退链：

```

  1. cc/claude-opus-4-7
  2. gh/gpt-5.3-codex
  3. glm/glm-4.7
```

### 弹性与熔断器

通过 **仪表盘 → 设置 → 弹性** 进行配置。

OmniRoute 通过五个组件实现提供者级别的弹性：

1. **请求队列与速率控制** —— 系统级请求整形：
   - **每分钟请求数（RPM）** —— 每个账户每分钟的最大请求数
   - **请求间最小间隔** —— 请求之间的最小间隔（毫秒）
   - **最大并发请求数** —— 每个账户的最大同时请求数

2. **连接冷却** —— 针对单个连接在发生可重试失败后、按认证类型进行的配置：
   - **基础冷却时间** —— 可重试的上游失败的默认冷却窗口
   - **使用上游重试提示** —— 当上游提供权威的 `Retry-After` 或重置提示时予以遵循
   - **最大退避步数** —— 连续失败时的最大指数退避级别

3. **提供者熔断器** —— 跟踪端到端的提供者失败，在达到配置的警告阈值时将提供者标记为降级，并在达到配置的失败阈值时打开熔断器：
   - **降级阈值** —— 进入 `DEGRADED` 状态前的连续提供者失败次数
   - **失败阈值** —— 进入 `OPEN` 状态前的连续提供者失败次数
   - **重置超时** —— 再次测试提供者之前的时间窗口
   - **CLOSED**（健康）—— 请求正常流动
   - **DEGRADED** —— 请求仍会流动，同时持续跟踪升高的失败情况
   - **OPEN** —— 在多次失败后暂时阻止该提供者
   - **HALF_OPEN** —— 正在测试提供者是否已恢复

   连接范围的 `429` 速率限制保留在**连接冷却**中，不会计入提供者熔断器。

   提供者熔断器的运行时状态仅显示在 **仪表盘 → 健康** 页面上。

4. **等待冷却** —— 如果所有候选连接都已在冷却中，OmniRoute 可以等待最早结束的冷却，并自动重试同一个客户端请求。

5. **速率限制自动检测** —— 当上游提供者返回明确的等待窗口时，如果启用了该设置，这些提示将覆盖本地连接冷却时间。

**专业提示：** 在故障后使用 **健康** 页面检查并重置活跃的提供者熔断器。弹性页面仅更改配置。

### Combo 均衡策略

在 **Dashboard → Combos → Create/Edit → Strategy** 中配置每个 combo 的均衡策略。

| 策略               | 说明                                          |
| ------------------ | --------------------------------------------- |
| **Round-Robin**    | 按顺序轮流使用各个模型                        |
| **Priority**       | 始终尝试第一个模型；仅在出错时回退            |
| **Random**         | 每个请求从 combo 中随机选择一个模型           |
| **Weighted**       | 根据为每个模型分配的权重按比例路由            |
| **Least-Used**     | 路由到最近请求数最少的模型（使用 combo 指标） |
| **Cost-Optimized** | 路由到最便宜的可用模型（使用定价表）          |

全局 combo 默认值可在 **Dashboard → Settings → Routing → Combo Defaults** 中设置。
combo 目标超时默认继承当前请求超时。只有当需要更短的单目标限制以触发
更快回退时，才在 combo 默认值或单个 combo 上使用 **Target timeout
(seconds)**。

零延迟 combo 优化是可选启用的。保持 **Zero-latency optimizations** 处于禁用状态可
防止这些延迟功能与回退目标竞争、基于 TTFT
历史跳过目标或压缩回退请求；启用后，已配置的对冲（hedging）、预测性 TTFT
跳过和主动回退压缩将以牺牲路由/请求保真度为代价，换取更低的尾部
延迟。

当上游提供者要求严格的 `max_tokens` / `maxOutputTokens` 限制时，请禁用 **Reasoning token buffer（推理令牌缓冲区）**。启用后，组合路由只会为具有已知输出上限的模型增加推理模型余量；当安全的缓冲值会超过该上限时，则保持客户端令牌限制不变。如果客户端限制已高于已知上限，OmniRoute 会在发送上游请求之前将其钳制到该上限。

通过 **Dashboard → Health**（仪表盘 → 健康）访问。实时系统健康概览，包含 6 张卡片：

| 卡片                                  | 显示内容                               |
| ------------------------------------- | -------------------------------------- |

## 🤖 自动路由（零配置）

OmniRoute 内置了一个**由评分驱动的自动路由器**，它会在所有已连接的提供者中，为每个请求选择最佳模型——无需维护任何组合。只需使用任一 `auto/*` 前缀发送请求，OmniRoute 就会即时构建一个虚拟组合，并根据延迟、成本、成功率、上下文适配度、模型对任务的适用性、近期故障、配额和熔断器状态对候选模型进行评分。

| 前缀           | 优化目标                                                                   |
| -------------- | -------------------------------------------------------------------------- |
| `auto`         | 平衡的默认选项（延迟 × 成本 × 成功率）                                     |
| `auto/coding`  | 编码任务：优先选择 Claude、GPT-5、GLM、Kimi、Qwen Coder、DeepSeek 编码模型 |
| `auto/cheap`   | 最低 $/token，可接受较高延迟                                               |
| `auto/fast`    | 最低延迟，忽略成本                                                         |
| `auto/offline` | 仅限本地提供者（Ollama、vLLM、llama.cpp）——适用于物理隔离环境              |
| `auto/smart`   | 推理质量优先（Opus、GPT-5 xhigh、R1、GLM 5.1 reasoning）                   |
| `auto/lkgp`    | “最后已知可用的提供者”——固定使用最近一次成功的提供者，失败后再回退到规则   |

示例：

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer $OMNIROUTE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto/coding",
    "messages": [{ "role": "user", "content": "Refactor this Python function" }],
    "stream": true
  }'
```

[AUTO-COMBO.md](../routing/AUTO-COMBO.md) 完整介绍了自动路由器，包括如何调整评分权重、将提供者加入黑名单，以及如何在**控制面板 → 自动组合**中检查路由决策。

## 🔌 MCP 与 A2A 集成

OmniRoute 既是 **MCP 服务器**（模型上下文协议），也是 **A2A 服务器**（智能体间 JSON-RPC 2.0）。任何兼容 MCP 的 IDE 或智能体宿主都可以直接调用 OmniRoute 工具——无需额外的封装器。

### MCP 传输方式

- **SSE**：`http://localhost:20128/api/mcp/sse`
- **可流式传输的 HTTP**：`http://localhost:20128/api/mcp/stream`
- **stdio**：`omniroute --mcp`（适用于偏好 stdio 的 IDE 插件）

### 连接 Claude Desktop

编辑 `~/Library/Application Support/Claude/claude_desktop_config.json`（macOS）或 Windows/Linux 上的等效文件：

```json
{
  "mcpServers": {
    "omniroute": {
      "command": "omniroute",
      "args": ["--mcp"]
    }
  }
}
```

### 连接 Cursor / Continue / VS Code MCP

使用 SSE URL `http://localhost:20128/api/mcp/sse`，并使用在**控制面板 → API 密钥**中生成的 Bearer API 密钥。

### 作用域

MCP 目前定义了 32 个命名作用域。每个 Bearer 密钥都可以限制为仅允许特定作用域——有关权威的作用域和工具清单，请参阅 [MCP-SERVER.md](../frameworks/MCP-SERVER.md)；有关 JSON-RPC 模式，请参阅 [A2A-SERVER.md](../frameworks/A2A-SERVER.md)。

## 💾 记忆系统

OmniRoute 通过混合检索持久保存**长期对话记忆**：

## 🔔 Webhook

订阅 OmniRoute 事件，以进行实时监控和自动化处理。

## 🛠️ 编程式管理

你可以使用**带有 `manage` 作用域的 Bearer 密钥**，通过 HTTP 管理所有 OmniRoute 资源（providers、combos、keys、settings）。

在 **Dashboard → API Keys → New Key → Scope: manage** 中生成密钥，然后：

```bash
# 列出 providers
curl http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"

# 添加 provider 连接
curl -X POST http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "provider": "openai", "apiKey": "sk-...", "name": "main" }'

# 创建 combo
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "premium", "strategy": "priority", "models": [{ "model": "cc/claude-opus-4-7" }, { "model": "glm/glm-5.1" }] }'

# 列出/创建 API 密钥
curl http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"
curl -X POST http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -d '{ "name": "ci-bot", "scopes": ["chat"] }'
```

完整的端点目录和请求/响应模式请参阅 [API_REFERENCE.md](../reference/API_REFERENCE.md)。

## 💻 内部 CLI

OmniRoute 提供了一个内部 CLI（`omniroute …`），用于设置、诊断和运行时控制。它与仪表板中的“CLI 工具”页面**相互独立**；该页面用于配置第三方 CLI（Claude Code、Cursor、Codex、Cline 等），使其能够与 OmniRoute 通信。

```bash
omniroute setup                    # 交互式向导（密码、提供者、组合）
omniroute setup --non-interactive  # 适用于 CI
omniroute doctor                   # 健康诊断（数据目录、数据库、提供者、端口）
omniroute providers available      # 列出支持的提供者
omniroute providers list           # 列出已配置的连接
omniroute providers test <id>      # 实时测试提供者连接
omniroute combos list              # 列出组合
omniroute combos switch <name>     # 设置默认组合
omniroute models                   # 列出可用模型（--json、--search）
omniroute keys add | list | remove # 从终端管理 API 密钥
omniroute backup                   # 创建配置和数据库快照
omniroute restore [<timestamp>]    # 从快照恢复
omniroute health                   # 详细健康状态（断路器、缓存、内存）
omniroute quota                    # 提供者配额使用情况
omniroute mcp status               # MCP 服务器状态
omniroute a2a status               # A2A 服务器状态
omniroute tunnel list|create|stop  # Cloudflare/Tailscale/ngrok 隧道
omniroute reset-password           # 重置管理员密码
omniroute --mcp                    # 通过 stdio 启动 MCP 服务器
omniroute --port 3000              # 在自定义端口上启动服务器
```

提示：将 `omniroute doctor --json` 与监控工具配合使用，以便在提供者连接不健康时发出警报。
