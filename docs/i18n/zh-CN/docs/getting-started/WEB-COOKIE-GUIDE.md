Web Cookie 提供者允许 OmniRoute 通过您现有的浏览器会话使用 AI 服务，而无需 API 密钥。当您已经可以通过某项服务的网站访问该服务，并希望 OmniRoute 使用相同的已认证会话时，它们非常有用。

与 API 密钥提供者不同，Web Cookie 提供者使用浏览器发送给网站的凭据进行身份验证。

---

# 开始之前

> **重要提示：**始终从**实时网络请求**中复制凭据，**不要**从浏览器的 Cookie 存储中复制。

许多身份验证问题都是由于从错误的位置复制 Cookie 导致的。

## 不要从 Cookie 存储中复制

大多数浏览器通过以下位置显示已存储的 Cookie：

```
DevTools
→ Application（或 Storage）
→ Cookies
```

尽管这些 Cookie 看起来正确，但它们可能：

- 已过期
- 不完整
- 缺少仅在已认证请求中发送的 Cookie

即使这些值看起来有效，使用它们也可能导致身份验证失败。

## 从实时请求中复制

请改为使用成功请求中的 Cookie：

```
DevTools
→ Network
→ 刷新页面
→ 打开一个聊天或对话请求
→ Request Headers
→ Cookie
```

`Cookie` 请求头包含浏览器成功使用的确切身份验证信息。

对于大多数 Web Cookie 提供者，应将此值粘贴到 OmniRoute 中。

# 常规设置

大多数 Web Cookie 提供者的设置流程都相同。

1. 登录提供者的网站。
2. 打开浏览器的开发者工具。
3. 打开 **Network** 选项卡。
4. 刷新页面。
5. 打开一个已认证的聊天或对话请求。
6. 复制所需的身份验证凭据。
7. 打开 OmniRoute。
8. 转到**提供者 → 添加提供者**。
9. 选择您的 Web Cookie 提供者。
10. 粘贴凭据。
11. 单击**测试连接**。
12. 保存提供者。

具体所需的凭据取决于提供者。

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) 是一个无需注册的免费消费者聊天平台——首次访问时会匿名创建会话，并通过三个 Cookie 持久保存：`uid`、`si_usr_id` 和 `si_ses_id`。OmniRoute 通过单一模型 ID（`notrack-c`，别名 `ntw`）代理同一个 `/api/dispatch` 端点。

### 连接步骤

1. 在浏览器中打开 [notrack.ai](https://notrack.ai)，并让网站设置匿名会话 Cookie。
2. 打开**开发者工具 → 网络**，刷新页面，然后点击任意 `/api` 请求。
3. 在**请求标头**中，复制完整的 `Cookie` 标头值。
4. 在 OmniRoute 中，前往**提供者 → 添加提供者 → NoTrack Web（免费）**。
5. 将 Cookie 字符串粘贴到 `apiKey` 字段中，然后点击**保存**。

OmniRoute 会从粘贴的字符串中提取 `uid`、`si_usr_id` 和 `si_ses_id`，并仅使用这些键值对重新构建一个干净的 `Cookie` 标头；如果存在 `nt_session`（为已登录账户设置的 `ntk_…` 令牌），也会将其包含在内。如果缺少这三个值中的任意一个，则会原样转发粘贴的原始字符串，以便运营人员尝试其他格式。

### 模型 ID

| 模型 ID     | 显示名称  | 说明                                     |
| ----------- | --------- | ---------------------------------------- |
| `notrack-c` | NoTrack C | 默认值——上游调度模型 `C`。               |
| `C`         | NoTrack C | `notrack-c` 的别名（原始上游调度代码）。 |
| `notrack`   | NoTrack C | `notrack-c` 的别名。                     |
| `ntw`       | NoTrack C | `notrack-c` 的短别名。                   |

所有四个模型 ID 都映射到同一个上游调度模型（`C`）。

### 请求选项

执行器接受请求正文中的以下可选字段：

| 正文字段              | 默认值  | 用途                                              |
| --------------------- | ------- | ------------------------------------------------- |
| `notrack_mode`        | `usual` | 调度模式（自由格式字符串；上游接受 `usual` 等值） |
| `notrack_max_turns`   | `6`     | 上游在回答前可以执行的内部轮次数。                |
| `notrack_chat_id`     | `null`  | 恢复现有的上游聊天（若要开始新聊天，请省略）。    |
| `notrack_attachments` | `[]`    | 透传上游附件描述符数组。                          |
| `notrack_regenerate`  | `false` | 设置为 `true`，可请求重新生成上一轮的回答。       |

### 功能

- **流式和非流式**聊天补全。
- **工具调用**——在请求中设置 `tools: [...]`；执行器会将其序列化为工具调用信封协议，并将模型的响应解析回 OpenAI `tool_calls`。
- **`response_format`**——支持 `json_object` 和 `json_schema`。执行器会从模型回复中提取第一个 JSON 对象，将其字符串化后再返回。
- **推理提示**——当上游发送 `thinking` 事件时，执行器会发出一个 `reasoning` 增量。

### 限制

- 上游会对匿名使用实施配额限制——触发限制时，执行器会返回 429 状态码和一条友好的提示消息。
- 所有模型 ID 都会解析到同一个上游调度模型；无法按模型进行切换。
- 执行器不会调用上游的 `/api/chats` 端点，因此不会自动管理聊天历史记录或会话。请使用 `notrack_chat_id` 恢复现有的上游聊天。

# Web Cookie 提供者可以做什么，以及不能做什么

Web Cookie 提供者复用网站的聊天界面。它们**不具备**与官方 API 相同的功能。

## 支持的功能

- 使用现有浏览器会话进行身份验证
- 访问您的账户可用的模型
- 流式传输聊天响应
- 无需 API 密钥

## 不支持的功能

- 函数调用
- 工具调用
- 自动编辑文件
- 智能体式 IDE 工作流
- 仅限 API 的功能

这是预期行为，**并非**错误。

如果您需要执行工具、自动编辑文件或使用其他智能体工作流，请使用 **API 密钥提供者**，而不是 Web Cookie 提供者。

# 验证注意事项

**测试连接**成功或 Cookie 验证成功，仅表示所提供的凭据格式似乎符合预期。

在 Issue #7857 解决之前，验证成功**并不能保证**提供者能够成功完成身份验证。

如果身份验证仍然失败，请确认您是从实时网络请求中复制凭据，而不是从浏览器的 Cookie 存储中复制。

# 故障排除

## 身份验证失败

请确认凭据复制自：

```
网络
→ 请求标头
→ Cookie
```

而**不是**复制自：

```
应用
→ Cookie
```

---

## Cookie 在浏览器中有效，但在 OmniRoute 中无效

某些提供者包含仅在已通过身份验证的请求中发送的 Cookie。

成功打开一个对话后，请从新的网络请求中重新复制凭据。

---

## 会话已过期

Web Cookie 提供者使用您现有的浏览器会话。

如果浏览器会话过期或您退出了登录，则必须复制一组新的凭据。要为受支持的 Web 提供者自动续期 Cookie，请参阅配套工具 [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md)。

---

## 测试连接通过，但请求失败

在 Issue #7857 解决之前，通过验证并不能保证身份验证请求一定会成功。

在进一步排查问题之前，请从新的已通过身份验证的请求中重新复制凭据。

---

## ChatGPT Web 因“Unsupported ChatGPT integrity dependency”而失败

```
[502] ChatGPT Web first-party bridge module failed to load:
pageerror: Unsupported ChatGPT integrity dependency: DD
```

凭据没有问题——该错误来自桥接模块，而不是会话。chatgpt.com 会在每次部署时分配其
模块 ID，而桥接模块过去会固定其所实例化的 Sentinel 辅助模块的 ID，因此，当
chatgpt.com 重新构建并重命名该辅助模块时，即使 Cookie 仍然有效，每轮请求也都会失败。重新授权
连接无法解决此问题。

已修复此问题的构建版本通过页面自身的运行时解析模块，不会固定任何 ID，因此不会遇到此问题。如果您看到此
错误，请升级 OmniRoute，然后重新运行连接检查。

# 最佳实践

- 从新的已通过身份验证的请求中复制凭据。
- 避免重复使用旧 Cookie。
- 使用 Web Cookie 提供者时，请保持浏览器会话处于活动状态。
- 将复制的 Cookie 视为敏感凭据。
- 如果需要函数调用或智能体工作流，请使用 API 密钥提供者。
