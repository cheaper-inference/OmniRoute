## Vue d’ensemble

Toutes les routes de l’API de gestion d’OmniRoute sont classées dans l’un des trois niveaux de protection. Cette classification est statique, définie dans `src/server/authz/routeGuard.ts`, et évaluée avant l’exécution de toute autre branche d’authentification.

## Niveaux

### Niveau 1 — LOCAL_ONLY

**Appliqué par :** `isLocalOnlyPath(path)` → vérification de l'hôte loopback
**Contournement :** Aucun par défaut. Exception étroite pour les chemins figurant dans
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` lorsque la requête porte une clé API
valide avec le scope `manage` (voir [Exception liée au scope manage](#manage-scope-carve-out)).

Ces routes génèrent des processus enfants ou exécutent du code au moment de
l'exécution. Les exposer à du trafic non loopback permettrait à un attaquant
ayant obtenu un JWT valide (par ex. via un tunnel Cloudflared/Ngrok) de
déclencher la génération de processus — une classe de CVE connue
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Ce qu'est GHSA-fhh6-4qxv-rpqj (la classe d'attaque) :** un serveur de
gestion/agent expose un endpoint qui lance un sous-processus (`npm install`,
`node`, un navigateur, un proxy, `git`, `tar`, …). Si cet endpoint est
accessible depuis l'extérieur de l'hôte — parce que l'opérateur a placé
OmniRoute derrière un tunnel nginx/Cloudflare/Tailscale et qu'un JWT a fuité,
ou que l'authentification était mal configurée — l'attaquant transforme
« appeler une API » en « exécuter une commande sur l'hôte » (exécution de code
à distance). OmniRoute comble cette faille en appliquant une **vérification de
l'hôte loopback de manière inconditionnelle, avant toute vérification
d'authentification**, sur chaque route capable de générer des processus : un
jeton divulgué via un tunnel ne peut toujours pas atteindre la génération de
processus.

**L'ensemble complet LOCAL_ONLY.** La source faisant autorité est
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` dans
`src/server/authz/routeGuard.ts` ; le tableau ci-dessous reflète l'état actuel.
Le contrôle `check-route-guard-membership` énumère chaque `route.ts` sous les
préfixes capables de générer des processus et fait échouer la CI si l'un d'eux
n'est pas classé local-only.

#### Dérogation du scope manage

Un sous-ensemble des chemins LOCAL_ONLY PEUT également être accessible depuis
une adresse non-loopback si et seulement si la requête porte un
`Authorization: Bearer <api-key>` dont les métadonnées incluent le scope
`manage` (ou `admin`). La dérogation est contrôlée explicitement par chemin
via `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, de sorte que le comportement
par défaut de tout nouveau chemin LOCAL_ONLY reste strictement loopback. Les
requêtes non authentifiées et celles avec des clés sans scope manage sont
toujours rejetées avec `403 LOCAL_ONLY`.

Aujourd'hui, le seul préfixe contournable est `/api/mcp/`.
`/api/cli-tools/runtime/` et `/api/services/` sont intentionnellement exclus
car ils peuvent lancer des sous-processus arbitraires (`npm install`, `node`),
ce qui correspond exactement à la classe de CVE que le niveau LOCAL_ONLY
existe pour prévenir.

**#7895 — scope restreint `mcp:connect` :** la dérogation `/api/mcp/` accepte
ÉGALEMENT une clé Bearer détenant le scope restreint `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), vérifié via
`hasMcpConnectOrManageScope()` dans `src/server/authz/policies/management.ts`.
Ceci est limité à `/api/mcp/` UNIQUEMENT — `mcp:connect` n'accorde rien sur
aucune autre route de gestion (y compris tout autre préfixe de contournement
LOCAL_ONLY, si jamais l'un venait à être ajouté), et il est délibérément exclu
de `MANAGEMENT_API_KEY_SCOPES`. Une clé détenant `manage`/`admin` passe
toujours la dérogation exactement comme avant ; `mcp:connect` est une
alternative à privilèges réduits pour les appelants distants MCP uniquement
qui ne devraient pas avoir besoin d'un accès de gestion étendu.

| Requête                                          | Chemin                     | Résultat                     |
| ------------------------------------------------ | -------------------------- | ---------------------------- |
| Non-loopback, sans Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Non-loopback, Bearer avec scope `manage`         | `/api/mcp/*`               | Autorisé                     |
| Non-loopback, Bearer avec scope `mcp:connect`    | `/api/mcp/*`               | Autorisé                     |
| Non-loopback, Bearer sans `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Non-loopback, Bearer avec scope `mcp:connect`    | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Non-loopback, Bearer avec scope `manage`         | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Loopback, avec/sans Bearer                       | tout LOCAL_ONLY            | Autorisé (le contrôle passe) |

#### Recommandations pour les opérateurs et audit

Si vous exécutez OmniRoute derrière un reverse proxy ou un tunnel (nginx,
Caddy, Cloudflare Tunnel, Tailscale, Ngrok), la vérification loopback protège
toujours les routes capables de spawn ci-dessus — une requête dont l'adresse
client est non-loopback est rejetée avec `403 LOCAL_ONLY` **avant l'exécution
de l'authentification**, de sorte qu'un JWT divulgué ne peut pas atteindre un
spawn. Deux responsabilités incombent encore à l'opérateur :

- **Ne « corrigez » pas un 403 en falsifiant l'IP du client en loopback.** Définir
  `X-Forwarded-For: 127.0.0.1`, ou utiliser un proxy qui réécrit l'adresse source en
  loopback, rouvre exactement la classe de RCE que ce niveau ferme. Exposez le
  tableau de bord/l'API via le proxy — jamais les routes capables de spawn.
- **Gardez le contournement à portée `manage` minimal.** Seul `/api/mcp/` est contournable, et
  uniquement avec une clé API à portée `manage`. Les `SPAWN_CAPABLE_PREFIXES` ne peuvent jamais être
  ajoutés à la liste de contournement — le schéma zod les rejette et
  `isLocalOnlyBypassableByManageScope` les refuse à l'exécution (défense en profondeur),
  ce que le tableau de bord entend par « ne peut pas être rendu contournable ». La même
  liste de refus contient aussi quelques routes LOCAL_ONLY qui ne lancent pas de processus mais ne doivent
  jamais être accessibles à distance non plus — `/api/oauth/kiro/auto-import` (lit des fichiers
  d'identifiants Kiro locaux à l'hôte), `/api/discovery/` et `/api/issue-agent/`. Le chargeur
  d'instantané à l'exécution écarte également ces entrées d'une ligne de paramètres stockée, et
  l'import JSON hérité (`/api/settings/import-json`) n'écrit jamais les clés de contournement.
  Chaque entrée de `LOCAL_ONLY_API_PREFIXES` doit être soit dans la liste de refus, soit
  examinée comme éligible au contournement (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Les routes capables de spawn
  à segment dynamique et à chemin statique sous `/api/providers/` (p. ex. `/login`,
  `/refresh-cursor`) sont couvertes par le compagnon basé sur les expressions régulières
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` dans
  `src/shared/constants/spawnCapablePrefixes.ts`, et non par le tableau plat
  `SPAWN_CAPABLE_PREFIXES` — le tableau plat devrait couvrir l'intégralité
  du préfixe `/api/providers/` pour les intercepter, ce qui élargirait à l'excès un
  arbre de routes que les tableaux de bord distants utilisent légitimement pour les
  opérations CRUD sur les fournisseurs.

**Audit des accès** — pour vérifier que rien hors de l'hôte n'atteint ces routes :

- Ouvrez l'**Inventaire des autorisations** sur `/dashboard/settings/security` : il affiche
  la liste en direct des préfixes LOCAL_ONLY, quels préfixes sont contournables, et l'ensemble
  des routes capables de spawn déterminé à la compilation (« ne peuvent pas être rendues contournables »).
- Recherchez dans vos journaux de proxy inverse / d'accès les préfixes ci-dessus associés à une
  adresse client non loopback. Toute occurrence ayant renvoyé `200` au lieu de
  `403 LOCAL_ONLY` signifie que le proxy masque l'IP réelle du client — corrigez le proxy.
- Un `403 LOCAL_ONLY` dans les journaux d'OmniRoute pour l'un de ces chemins est le signe que la
  protection fonctionne comme prévu, et non une erreur à supprimer.

#### Routes accessibles à distance avec un contrôle de sonde au point d'appel

Certaines routes doivent rester accessibles depuis un tableau de bord distant mais exécutent une
sonde côté hôte (`which <binary>`, `<binary> --version`, `tailscale status --json`) pour les
appelants locaux. Elles ne sont pas LOCAL_ONLY pour `GET` ; à la place, le gestionnaire lit le
verdict de localité du pair de confiance avec `getRequestPeerLocality()`
(`src/shared/utils/apiAuth.ts`) et n'exécute la sonde que pour les appelants `loopback` / `lan`.
Un appelant `remote` obtient la même forme de réponse construite à partir de sources sans spawn
(état persisté, paramètres, vérifications fs), marquée `probed: false`.

| Route                                                            | Sonde ignorée pour les appelants distants                              |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | Sonde d'exécution CLI (`allowLocalRuntimeProbe`) et spawn de repli CLI |
| `GET /api/headroom/status`                                       | `which headroom` et les sondes `--version` de python                   |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew`      |
| `GET /api/tunnels/cloudflared` (exempté de LOCAL_ONLY pour GET)  | Recherche dans le PATH via `which cloudflared`                         |

Une nouvelle route de lecture qui sonde l'hôte suit le même schéma, ou est classée
LOCAL_ONLY d'office.

### Niveau 2 — ALWAYS_PROTECTED

**Appliqué par :** `isAlwaysProtectedPath(path)` → ignore le contournement `requireLogin=false`
**Contournement :** aucun lorsque `requireLogin=false` ; le JWT est toujours requis

Ces routes sont destructrices ou irréversibles. Les autoriser dans une installation
« sans mot de passe » signifierait que quiconque sur le même LAN pourrait purger la
base de données ou tuer le processus du serveur.

| `/api/settings/import-json`               | Remplace le blob complet des paramètres                                |
| `/api/providers/health-autopilot/actions` | Exécute des actions de remédiation de l'autopilote                     |
| `/api/settings/obsidian`                  | Émet des identifiants WebDAV réutilisables pour toute racine de coffre |
| `/api/relay/tokens`                       | Émet, liste, modifie et révoque des jetons de relais                   |
| `/api/cli-tools/apply`                    | Réécrit la configuration CLI de l'hôte de l'opérateur                  |
| `/api/cli-tools/guide-settings`           | Écrit des fichiers de configuration CLI pilotés par guide              |
| `/api/cli-tools/hermes-agent-settings`    | Écrit la configuration de l'agent Hermes                               |
| `/api/cli-tools/backups`                  | Restaure et supprime des sauvegardes de configuration CLI              |

**Réponse en cas de violation :** `401 Authentication required`

`/api/settings/obsidian` couvre son enfant `/webdav` : `POST` pointe le service de fichiers WebDAV —
servi par la couche Node personnalisée avant Next.js, en dehors de ce pipeline — vers une racine
choisie par l'appelant et renvoie en écho des identifiants Basic fraîchement générés, `DELETE` en
effectue la rotation, et le `POST` parent stocke le jeton de l'API REST Obsidian. GHSA-62vw ne
masquait que la révélation du mot de passe par le `GET` ; l'émission restait sur le niveau
fail-open (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` refuse en outre un coffre qui est le
répertoire de données, se situe à l'intérieur de celui-ci ou le contient.

#### Les exports et restaurations d'identifiants sont réservés aux opérateurs

Le niveau ci-dessus détermine uniquement si _un identifiant_ est requis. Les routes qui
téléchargent les identifiants stockés ajoutent une seconde vérification dans le gestionnaire :
`GET /api/settings/export-json` (connexions fournisseur déchiffrées et clés API brutes),
`GET /api/db-backups/export` (le fichier SQLite) et `GET /api/db-backups/exportAll` (l'archive
complète) appellent `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`). Elle
accepte une session du tableau de bord, le sujet CLI local ou une instance avec la connexion
désactivée, et répond `403` aux clés API de toute portée (y compris `manage` et `admin`) ainsi
qu'aux jetons d'accès `oma_`. Leurs homologues destructrices appliquent la même frontière :
`POST /api/db-backups/import` (fichier `.sqlite` téléversé, `dryRun=true` inclus),
`POST /api/db-backups` (restauration d'une sauvegarde stockée par id) et
`POST /api/settings/import-json` (restauration JSON héritée) remplacent la base de données active
ou l'ensemble complet des paramètres/connexions/clés API, de sorte qu'un identifiant machine ne
peut pas non plus les déclencher. La destruction des points de restauration applique la même
frontière : `DELETE /api/db-backups` (nettoyage — conserver les N plus récents / supprimer ceux de
plus de D jours) et `PATCH /api/db-backups` (paramètres de rétention), car la rétention persistée
est exactement ce que `cleanupDbBackups()` applique après chaque sauvegarde automatique
(`src/lib/db/backup.ts`), de sorte qu'un identifiant machine qui pourrait enregistrer
`keepLatest: 1` élaguerait tout lors du prochain instantané. Le listage et la création de
sauvegardes (`GET`/`PUT /api/db-backups`) conservent l'authentification de gestion ordinaire.
L'émission de jetons de synchronisation (`POST /api/sync/tokens`) utilise le même utilitaire, plus
le jeton de service interne de boucle locale de confiance.

### L'amorçage d'une installation neuve est limité à la boucle locale — selon le pair réel, pas `Host`

Sans mot de passe de gestion configuré (et sans `INITIAL_PASSWORD`), `isAuthRequired()` dans
`src/shared/utils/apiAuth.ts` garde l'amorçage anonyme ouvert **uniquement pour les pairs de
boucle locale**. La boucle locale est déterminée à partir des signaux de pair de confiance, dans
l'ordre : le pair TCP réel estampillé par jeton (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ce que
voit la politique), le verdict `AUTHZ_HEADER_PEER_LOCALITY` propre au pipeline (ce que voient les
gestionnaires de routes, digne de confiance uniquement tant que `OMNIROUTE_PEER_STAMP_TOKEN` est
défini), ou un pair socket réel pour les appelants directs. `Host` / `nextUrl.hostname` ne sont
jamais consultés, et l'écriture du premier mot de passe (`POST /api/settings/require-login`) est
soumise à la même contrainte plutôt qu'ouverte à tout pair du réseau (GHSA-7pq4-8pvv-rx7r).
`managementPolicy` transmet explicitement son propre verdict `peerContext`, de sorte que les
en-têtes de la requête ORIGINALE (avant retrait) ne le décident jamais.

### Niveau 3 — MANAGEMENT (par défaut)

Toutes les autres routes de gestion. Authentification requise sauf si `requireLogin=false` est
configuré. Les jetons CLI peuvent authentifier ces routes (boucle locale + HMAC valide).

## Ordre d’évaluation

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → poursuivre
     → hors loopback, Bearer avec portée manage
        ET isLocalOnlyBypassableByManageScope    → autoriser (management_key)
     → sinon                                     → rejeter avec 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → autoriser (system)
  3. hasValidCliToken(headers)?
     → autoriser (cli) [loopback + vérification HMAC avec timingSafeEqual]
  4. isAlwaysProtectedPath(path) ou requireLogin=true?
     → isDashboardSessionAuthenticated?
        → autoriser (dashboard_session)
     → Bearer avec portée manage sur un chemin non contournable ?
        → autoriser (management_key)
     → rejeter avec 401/403
  5. requireLogin=false?
     → autoriser (anonymous)
```

La branche avec portée manage de l’étape 1 est le seul chemin authentifié pouvant satisfaire une route
LOCAL_ONLY ; le mode d’échec du backend d’authentification renvoie 503 (et non 403), afin qu’une
base de données expirée ne soit pas silencieusement rétrogradée en « refus ».

## Ajout d’une nouvelle route capable de lancer des processus

1. Ajoutez le préfixe du chemin à `LOCAL_ONLY_API_PREFIXES` dans
   `src/server/authz/routeGuard.ts`
2. Ajoutez un test dans `tests/unit/authz/routeGuard.test.ts` vérifiant que
   `isLocalOnlyPath()` renvoie true pour le nouveau préfixe
3. **Ne sautez jamais cette étape** — consultez la règle absolue nº 15 dans `CLAUDE.md`
4. Décidez : cette route doit-elle ÉGALEMENT figurer dans `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ?
   La réponse par défaut est **non**. N’y consentez que lorsque la route peut être exposée en toute sécurité à un
   détenteur de la portée manage (c.-à-d. qu’elle ne lance PAS de code arbitraire contrôlé par l’utilisateur).

## Ajout d’un chemin contournable avec la portée manage

1. Vérifiez que la route n’exécute pas de code ou de commandes fournis par l’utilisateur. Si c’est
   le cas, arrêtez-vous — cette exception n’est pas l’outil approprié.
2. Ajoutez le préfixe à `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` dans
   `src/server/authz/routeGuard.ts`
3. Ajoutez une couverture dans `tests/unit/authz/management-policy.test.ts` pour les quatre
   formes de requêtes : sans Bearer (403), Bearer avec portée manage (autorisation), Bearer sans portée manage
   (403), ainsi que la régression par préfixe vérifiant que `/api/cli-tools/runtime/*` reste
   strictement limité au loopback, même avec un Bearer doté de la portée manage.

## Documentation des niveaux de sécurité dans OpenAPI

Lors de l’ajout d’une nouvelle route à `docs/openapi.yaml`, appliquez l’extension
fournisseur correspondante si la route est classifiée par `routeGuard.ts` :

| Classification de routeGuard.ts               | Annotation YAML                | Application                                             |
| --------------------------------------------- | ------------------------------ | ------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                     | `x-loopback-only: true`        | Blocage inconditionnel hors loopback                    |
| `ALWAYS_PROTECTED_API_PATHS`                  | `x-always-protected: true`     | Authentification requise même avec `requireLogin=false` |
| Route interne d’administration/débogage       | `x-internal: true`             | Masquée de /dashboard/api-endpoints par défaut          |
| Aucune (publique / authentification standard) | (aucune annotation nécessaire) | Accès standard contrôlé par `requireLogin`              |

### Validation

Deux scripts garantissent la cohérence entre les annotations YAML et `routeGuard.ts` :

- `scripts/check/check-openapi-coverage.mjs` — échoue si la couverture est < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — échoue si les annotations `x-loopback-only` ou
  `x-always-protected` divergent des constantes définies à la compilation

Les deux scripts s’exécutent dans le hook de précommit et dans la CI.

### Règle relative aux faux positifs

Si `x-always-protected` ou `x-loopback-only` est annoté sur une route qui ne figure PAS dans
la constante de `routeGuard.ts`, le script de couverture échoue. La correction consiste toujours à aligner le
YAML sur ce que `routeGuard.ts` applique réellement — et non à ajouter des routes à `routeGuard.ts`
sans également implémenter la logique d’application.
