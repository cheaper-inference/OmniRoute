Le contrat `config/cli-tools-manifest.json` neutre déclare canonique IDs, les alias, les candidats binaires, les recettes de configuration, les arguments et les capacités du modèle. L'adaptateur Plain Node dans `bin/cli/cli-manifest.mjs` et l'adaptateur TypeScript dans `src/shared/constants/cliIntegrationManifest.ts` lisent le même fichier. Le runtime, le catalogue, la configuration, l'achèvement, les générateurs et l'enregistrement du backend sont vérifiés ensemble par `tests/unit/cli/cli-manifest-drift.test.ts`. Être catalogué ne signifie pas qu'un outil peut être lancé ou configuré. En particulier, 5dive reste uniquement configuré.

## Environnement et cycle de vie de l'enfant

`omniroute run`, `omniroute launch` et `omniroute launch-codex` héritent d'une liste blanche de compatibilité OS/terminal et injectent les informations d'identification de la cible sélectionnée. Les secrets de fournisseur et de base de données non liés ne sont pas hérités par défaut. `--inherit-env` restaure explicitement l'héritage complet de l'environnement parent ; utilisez-le uniquement lorsque le processus tiers sélectionné doit recevoir ces valeurs. Il s'agit d'un filtrage d'environnement, pas d'un bac à sable OS : le processus s'exécute toujours avec les autorisations du système de fichiers de l'appelant.

Les signaux d'interruption et de fin sont transmis à l'enfant. Le lanceur attend l'événement de fermeture de l'enfant avant de supprimer la configuration temporaire. `OMNIROUTE_CHILD_SIGNAL_TIMEOUT_MS` contrôle le délai de grâce avant la résiliation forcée (par défaut 5 000 millisecondes).

## configuration persistante Gemini

```bash
omniroute setup-gemini --remote https://omni.example --model provider/model --yes
omniroute configure gemini --model provider/model --yes
omniroute run gemini --model provider/model --dry-run --json
```

Les deux premières commandes configurent cette machine pour le serveur local ou distant sélectionné. Le programme d'installation conserve les paramètres JSON non liés, sélectionne l'authentification par clé API Gemini et écrit le point de terminaison et les informations d'identification dans un fichier `.gemini/.env` privé. Il refuse JSON invalide plutôt que de l'écraser. Le point de terminaison URLs doit être HTTP(S), sans informations d'identification intégrées, paramètres de requête ou fragments. L’exécution à sec imprime les chemins, pas les valeurs d’informations d’identification.

`GEMINI_CLI_HOME` ou `--gemini-home` sélectionne la racine locale persistante. Un véritable `run gemini` crée puis supprime sa propre maison temporaire. Aucun des deux modes ne contourne les vérifications de confiance dans l'espace de travail de Gemini.

## profils Codex

`configure codex` écrit un `<name>.config.toml` privé avec un modèle et son point de terminaison de fournisseur OmniRoute. Les informations d'identification sont référencées via `OMNIROUTE_API_KEY`, jamais intégrées. La commande de lancement définit le modèle sélectionné sur la clé `model` de niveau supérieur, et non à l'intérieur `model_providers`.

Les fichiers de profil distincts constituent le contrat Codex actuellement documenté ; ils superposent la configuration utilisateur lorsqu'ils sont sélectionnés avec `codex --profile <name>`. Voir [la référence officielle du profil](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles) et [le guide OmniRoute Codex](./CODEX-CLI-CONFIGURATION.md).

## Exécution de commandes hermétiques

Avec un `DATA_DIR` explicite, la définition `OMNIROUTE_CLI_SKIP_DEFAULT_DATA_ENV=1` empêche le démarrage de passer par l'environnement d'informations d'identification du répertoire de données utilisateur par défaut. Ceci est utile pour les tests isolés. Il ne désactive pas les autres fichiers d'environnement explicitement sélectionnés.

## Répertoire de travail `.env`

Le CLI lit les fichiers `.env` dans cet ordre, et le premier fichier à définir une clé gagne : le `DATA_DIR` explicite, le répertoire de données par défaut, le répertoire de travail actuel, puis le répertoire du package. Les variables Shell gagnent toujours.

Le répertoire de travail peut appartenir à quelqu'un d'autre (un référentiel cloné, une archive décompressée) et `omniroute serve` transmet l'environnement CLI au serveur et à chaque outil exécuté par le serveur. Ainsi, un `.env` ne peut définir que ces clés, répertoriées dans `bin/cli/utils/untrustedCwdEnv.mjs`:

| Clé                             | Valeurs acceptées                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------------- |
| `REQUIRE_API_KEY`               | `true`, `1` ou `yes` dans tous les cas, les valeurs que le serveur traite comme étant |
| `LANG`, `LC_ALL`, `LC_MESSAGES` | jusqu'à 64 lettres, chiffres, `_`, `.`, `@` ou `-`                                    |
| `LANGUAGE`                      | pareil, plus `:`                                                                      |
| `TZ`                            | jusqu'à 64 lettres, chiffres, `_`, `+`, `-` ou `/`, ne commençant pas par `/`         |
| `NO_COLOR`, `FORCE_COLOR`       | jusqu'à 16 lettres et chiffres                                                        |

Chaque valeur acceptée par `REQUIRE_API_KEY` active la vérification, de sorte que le fichier ne peut pas désactiver la vérification lui-même. Cependant, cela ne décide pas du résultat : le serveur lit un remplacement `REQUIRE_API_KEY` stocké dans la base de données avant l'environnement, tandis que l'avertissement de démarrage concernant l'écoute sur toutes les interfaces sans clé API lit uniquement l'environnement. Avec un remplacement stocké de `false`, un répertoire de travail `REQUIRE_API_KEY=true` laisse le API ouvert et masque cet avertissement. La règle `TZ` est plus étroite que POSIX: elle rejette `.`, `:`, `,` et `<>`, donc la forme `:Area/City` et les règles telles que `EST5EDT,M3.2.0,M11.1.0` doivent être définies dans le shell ou dans `<DATA_DIR>/.env`.

Les noms doivent correspondre exactement, en majuscules. Toute autre ligne, une valeur qui échoue à sa vérification et un nom qui n'est pas composé de lettres ASCII, de chiffres et `_` (par exemple un avec un octet NUL ou une lettre similaire) sont ignorés. Le CLI imprime un avertissement qui nomme les clés qu'il ne peut pas définir et un autre qui nomme les clés autorisées qu'il a ignorées, chacune avec ce qu'il faut changer (`TZ (expected a zone name such as Europe/Berlin)`, `lang (write the name as LANG)`). Ni l’un ni l’autre n’imprime les valeurs. Les chemins de fichiers dans ces messages, ainsi que les rapports de chemin `.env` `omniroute doctor`, sont échappés lorsqu'ils contiennent des caractères de contrôle ou de bidi. La restriction ne s'applique pas lorsque le répertoire de travail est le répertoire de données ou le répertoire de package.

`PORT`, `API_PORT` et `DASHBOARD_PORT` ne figurent pas sur la liste. Sans un URL de base provenant d'une source de priorité supérieure, le CLI parle à `localhost:<PORT>`, et tout ce qui y écoute reçoit la clé API du CLI, le jeton de contexte et le jeton de la machine CLI (`x-omniroute-cli-token`, voir [CLI_TOKEN.md](../security/CLI_TOKEN.md) ), que le serveur local accepte pour les appels de gestion à partir du bouclage. Un port du répertoire de travail permettrait à ce fichier de choisir l'écouteur, alors définissez les ports dans le shell, dans `<DATA_DIR>/.env` ou avec l'option `--port` des commandes qui en ont un (`serve`, `launch`, `run`).

L'analyseur n'a pas de syntaxe `export`. Une ligne telle que `export LD_PRELOAD=...` nomme une variable `export LD_PRELOAD`; à partir du répertoire de travail, il est ignoré et dans d'autres fichiers `.env` il définit ce nom littéral, que rien ne lit.

Le CLI associe le jeton stocké d'un contexte (jeton d'accès ou clé API héritée) uniquement avec la propre origine de ce contexte : schéma, hôte et port, par rapport à `URL.origin`. Cela s'applique aux requêtes effectuées via le client HTTP de CLI(`--base-url`, `OMNIROUTE_BASE_URL`, `omniroute connect <new-url>`) et aux commandes `launch`, `launch codex`, `configure` et `setup-*` qui écrivent un URL de base et le saisissent dans la configuration d'un autre outil. Pointés vers un autre serveur avec `--remote`, ils utilisent un `--api-key` ou `OMNIROUTE_API_KEY` explicite s'il en est un, et aucun jeton de contexte. La comparaison est exacte, donc `localhost` et `127.0.0.1`, ou un hôte avec et sans point final, comptent comme des serveurs différents et n'obtiennent aucun jeton de contexte. Un URL avec des informations utilisateur, une barre oblique inverse ou des espaces ne correspond jamais, car d'autres analyseurs URL ( `urllib` et `httpx` de Python, par exemple) peuvent en lire un hôte différent. Pour les requêtes que le CLI s'envoie lui-même, cette vérification couvre uniquement le schéma et l'autorité, donc un identifiant avec un espace dans le chemin ou la requête conserve le jeton.
