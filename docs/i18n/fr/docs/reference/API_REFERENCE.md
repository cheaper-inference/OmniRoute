Référence principale de l’API OmniRoute. Elle couvre l’interface publique `/v1` et les endpoints d’administration les plus utilisés ; le fichier [`docs/openapi.yaml`](../openapi.yaml), lisible par machine, ainsi que l’arbre des routes sous `src/app/api/` constituent les sources exhaustives.

Pour consulter la matrice ciblée du protocole compatible avec OpenAI et des fonctionnalités des fournisseurs, voir
[`OPENAI_COMPATIBILITY.md`](./OPENAI_COMPATIBILITY.md).

Chaque déploiement fournit sa propre copie de la spécification à l’emplacement `/openapi.yaml`, générée à partir de `docs/openapi.yaml` lors de la compilation. Elle contient la version de la compilation ainsi qu’une URL de serveur relative (`./`), afin que les requêtes restent dirigées vers l’hôte qui a servi le document. Un outil qui importe le fichier téléchargé ne dispose d’aucun hôte de ce type et nécessite que l’URL de base soit définie manuellement.

## Complétions de chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### En-têtes personnalisés

| Header                   | Direction | Description                                                                                                                                                                                                                                                             |
| ------------------------ | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Requête   | Définir sur `true` pour contourner le cache                                                                                                                                                                                                                             |
| `x-omniroute-no-memory`  | Requête   | Définir sur `true` pour ignorer l’injection de la mémoire et des compétences pour cette requête (comme no-cache ; évite le surcoût de jetons/coût par appel)                                                                                                            |
| `X-OmniRoute-Progress`   | Requête   | Définir sur `true` pour activer les événements de progression                                                                                                                                                                                                           |
| `X-Session-Id`           | Requête   | Clé de session persistante pour l’affinité de session externe                                                                                                                                                                                                           |
| `x_session_id`           | Requête   | Variante avec trait de soulignement également acceptée (HTTP direct)                                                                                                                                                                                                    |
| `X-OmniRoute-Session-Id` | Requête   | Balise de session/conversation fournie par l’appelant (alimente également la mémoire). Lorsqu’elle est présente, elle est persistée telle quelle dans `call_logs.session_tag` pour l’attribution des coûts par session (#8249) — jamais générée lorsqu’elle est absente |
| `Idempotency-Key`        | Requête   | Clé de déduplication (fenêtre de 5 s)                                                                                                                                                                                                                                   |
| `X-Request-Id`           | Requête   | Clé de déduplication alternative                                                                                                                                                                                                                                        |
| `x-omniroute-connection` | Requête   | Épingle une requête utilisant un seul modèle à une connexion fournisseur (compte) spécifique par son identifiant — voir [Épinglage d’un compte par requête](#account-pinning-per-request)                                                                               |
| `X-OmniRoute-Cache`      | Réponse   | `HIT` ou `MISS` (hors streaming)                                                                                                                                                                                                                                        |
| `X-OmniRoute-Idempotent` | Réponse   | `true` si la requête a été dédupliquée                                                                                                                                                                                                                                  |
| `X-OmniRoute-Progress`   | Réponse   | `enabled` si le suivi de la progression est activé                                                                                                                                                                                                                      |
| `X-OmniRoute-Session-Id` | Réponse   | ID de session effectif utilisé par OmniRoute                                                                                                                                                                                                                            |
| `X-OmniRoute-Request-Id` | Réponse   | ID de corrélation de la requête (lorsqu’il est connu)                                                                                                                                                                                                                   |
| `X-OmniRoute-Version`    | Réponse   | Version de build d’OmniRoute (toujours présente)                                                                                                                                                                                                                        |
| `X-OmniRoute-Cost-Saved` | Réponse   | Montant en USD économisé grâce au cache lors d’un `HIT` (uniquement pour les résultats du cache)                                                                                                                                                                        |
| `X-OmniRoute-Decision`   | Réponse   | Trace du routage : `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` est la stratégie combinée, ou `single` pour une requête non combinée) — toujours présente dans les réponses de fin                                                                     |

> Remarque concernant Nginx : si vous utilisez des en-têtes comportant des traits de soulignement (par exemple `x_session_id`), activez `underscores_in_headers on;`.

#### Épinglage d’un compte par requête

Lorsqu’un fournisseur dispose de plusieurs connexions (comptes ou clés), OmniRoute en sélectionne normalement une
à l’aide de sa stratégie de sélection de compte. Une requête peut à la place épingler une connexion spécifique
avec l’en-tête `x-omniroute-connection` :

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Où trouver l’id.** Ouvrez la page du fournisseur dans le tableau de bord
  (**Tableau de bord → Fournisseurs → <provider>**) et cliquez sur la pastille d’id
  `xxxxxxxx…` d’une ligne de connexion — l’id complet de la connexion est alors copié.
- **Requêtes qui le prennent en charge.** Requêtes à modèle unique (`provider/model`) sur
  `/v1/chat/completions`, `/v1/messages` et `/v1/responses`. Les combinaisons ignorent cet en-tête :
  épinglez un compte pour chaque étape de la combinaison via la propre connexion de l’étape.
- **L’épingle est stricte, et non une préférence.** La connexion épinglée est utilisée exclusivement. Une
  défaillance au cours de la requête enregistre le délai de récupération du compte, mais ne
  bascule pas vers un compte associé du même fournisseur.
- **Le délai de récupération et le quota libèrent l’épingle.** Tant que la connexion épinglée est en
  délai de récupération, que son quota est épuisé ou qu’elle est bloquée par une politique de quota,
  les requêtes suivantes se replient sur les autres connexions du fournisseur, exactement comme le trafic non épinglé.
- **Les ids inconnus ou désactivés échouent.** Un id qui ne se trouve pas dans le pool actif du fournisseur (supprimé,
  désactivé ou appartenant à un autre fournisseur) ne laisse aucun compte éligible ; la requête
  échoue au lieu d’être routée silencieusement ailleurs.

Claude Code envoie des en-têtes personnalisés via `ANTHROPIC_CUSTOM_HEADERS`. Placez-le dans le bloc `env`
de `~/.claude/settings.json`, ou dans un fichier `.claude/settings.json` au niveau du projet afin d’épingler un compte différent par projet :

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Source : `src/sse/handlers/chat.ts` (lecture de l’en-tête), `src/sse/services/auth.ts` et
`src/sse/services/sessionAffinityPin.ts` (libération de l’épingle et vérification de l’absence du pool).

> **En-têtes de télémétrie des coûts :** les réponses réussies sans streaming contiennent également l’ensemble de télémétrie des coûts `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, 10 décimales fixes ; `0.0000000000` pour les requêtes gratuites ou non tarifées), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` et `X-OmniRoute-Fallback-Attempts` (uniquement lorsque la valeur est > 0), ainsi que `X-OmniRoute-Request-Id` et `X-OmniRoute-Version`. Ils sont émis par les complétions de chat, `/v1/responses`, `/v1/messages`, **ainsi que par les points de terminaison multimédias** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` et `/v1/moderations` (coût toujours égal à `0`). Le coût multimédia est calculé par modalité (par image, par seconde, par caractère, par unité de recherche) lorsque la tarification est disponible, sinon `0` (fonctionnement tolérant aux échecs).

> **Sémantique du coût en cas d’accès au cache :** lors d’un accès au cache sémantique (`X-OmniRoute-Cache-Hit: true`), aucun appel en amont n’est effectué ; `X-OmniRoute-Response-Cost` vaut donc `0.0000000000` (le coût **incrémentiel** de traitement de l’accès au cache). Le coût d’origine ou celui qui aurait été appliqué est indiqué séparément dans `X-OmniRoute-Cost-Saved`. Les systèmes de facturation doivent additionner `X-OmniRoute-Response-Cost` (les accès au cache ne coûtent rien) ; les analyses du cache peuvent agréger `X-OmniRoute-Cost-Saved`.

## Baux de session gérés exclusifs

La mise en location exclusive de sessions gérées est un contrat de routage facultatif et neutre vis-à-vis du client : un seul propriétaire actif détient une connexion OmniRoute éligible. Elle ne loue pas de modèle, n’exige pas OAuth, n’identifie pas un client particulier et n’impose pas de fournisseur particulier.

La clé API d’authentification doit disposer de la portée `lease:exclusive` et d’une liste `allowedConnections` explicitement non vide. La limite de mutation de la base de données impose ces deux champs conjointement lors de la création des clés et des mises à jour partielles.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Les réponses réussies d’acquisition, de renouvellement et de libération exposent les horodatages, `state` et la `generation` positive exacte, mais jamais la connexion sélectionnée ni les identifiants d’authentification. Le renouvellement et la libération fournissent la génération dans le corps JSON :

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Un propriétaire de bail actif peut demander explicitement des métadonnées d’affichage respectueuses de la confidentialité pour sa liaison actuelle :

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Cette action d’état facultative est protégée par le propriétaire opaque, la clé API gérée authentifiée et la génération active exacte au sein d’une seule transaction de base de données. `displayName` correspond uniquement au nom de connexion configuré après suppression des espaces superflus ; sa valeur est `null` lorsqu’aucun nom configuré sûr n’existe. OmniRoute ne remplace jamais ce nom par une adresse e-mail ou une identité de compte générée. La valeur du fournisseur est un libellé d’affichage non sensible et jamais un identifiant de fournisseur compatible généré. Les identifiants d’authentification, jetons, cookies, identifiants bruts de connexion ou de clé API, hachages des propriétaires, secrets de protection contre le fencing et données de routage internes sont exclus.

Les recherches effectuées avec une mauvaise clé, un mauvais propriétaire, une génération obsolète, ou concernant une liaison absente, expirée, libérée ou invalidée renvoient toutes la même erreur `409 LEASE_FENCE_STALE`, sans métadonnées de connexion. Un client ayant reçu la réponse d’attente de capacité ne dispose d’aucune liaison active à inspecter. Lorsque le routage fait évoluer un bail actif, la même génération reste valide et l’état renvoie atomiquement la nouvelle liaison, jamais l’ancienne. Les clients existants restent inchangés, car les réponses d’acquisition, de renouvellement, de libération et d’attente conservent leurs formes précédentes.

Ce contrat serveur ne modifie pas `/status` de l’OpenAI Codex standard. Codex standard indique actuellement son fournisseur de modèle ainsi que l’état intégré de l’authentification et du compte, mais n’affiche pas les métadonnées de compte d’un fournisseur personnalisé arbitraire ; une intégration cliente ultérieure devra appeler cette action et décider de la manière d’afficher `connection.displayName`.

Chaque requête d’inférence gérée fournit ensuite les deux en-têtes de contrôle :

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Le propriétaire exact, la génération, la connexion active et la clé API authentifiée sont protégés immédiatement avant chaque tentative prise en charge vers l’amont. La réutilisation du propriétaire et de la génération avec une autre clé échoue, même lorsque cette clé autorise la même connexion. Les propriétaires bruts ne sont ni persistés, ni consignés, ni conservés dans l’instantané de la requête, ni transmis à l’amont.

Une contention temporaire renvoie HTTP `429` avec `Retry-After` et :

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Cette réponse signifie uniquement que l’ensemble éligible ordinaire n’était pas vide et que chaque candidat libre était détenu par un bail actif d’un tiers. Les modèles ou fournisseurs non pris en charge, les incompatibilités de politique, le délai de récupération, les quotas, l’état de santé et les autres échecs ordinaires d’éligibilité conservent leurs réponses OmniRoute existantes.

### `x-omniroute-compression`

Remplacement par requête du plan de compression. Priorité la plus élevée — prime sur le remplacement de la combinaison de routage, le profil actif, le déclenchement automatique et le panneau Default. Valeurs :

| Valeur        | Effet                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `off`         | Aucune compression pour cette requête.                                                                                    |
| `default`     | Profil Default dérivé du panneau (ignore le profil actif). Les moteurs avec pertes restent désactivés.                    |
| `safe`        | Déduplication et regroupement des espaces uniquement.                                                                     |
| `allow-lossy` | Conserve le plan de l’opérateur pour cette requête, y compris les résumés et les réécritures de style.                    |
| `engine:<id>` | Un seul moteur lorsqu’il est activé, par ex. `engine:rtk`. Activation ponctuelle de ce moteur pour la requête.            |
| `<combo>`     | Une combinaison nommée, comparée d’abord par nom (sans distinction entre majuscules et minuscules), puis par identifiant. |

Remarques :

- Les valeurs inconnues sont ignorées (la requête n’est jamais rejetée) ; la résolution revient à la précédence normale de l’opérateur.
- Si plusieurs combinaisons partagent un nom, transmettez l’**id** de la combinaison pour obtenir une correspondance déterministe.
- Une combinaison dont le nom est `off` ou `default` ne peut pas être sélectionnée par son nom (ces mots-clés sont interprétés en premier) ; référencez une telle combinaison à l’aide de son identifiant.
- Le commutateur maître de compression constitue une barrière stricte : lorsque la compression est désactivée globalement, cet en-tête ne peut pas l’activer.

Le plan appliqué est renvoyé dans l’en-tête de réponse :

```
X-OmniRoute-Compression: <mode>; source=<source>
```

où `<source>` est l’une des valeurs suivantes : `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ou `off`.

## Intégrations

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Fournisseurs disponibles : Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Les identifiants de catalogue sont au format `provider/model` (exemple : `jina-ai/jina-embeddings-v5-omni-small`). Les identifiants de modèles Jina seuls présents dans le registre (par exemple `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) sont également résolus. Les fonctions d’embedding, de reranking, de classification et de segmentation de Jina utilisent d’abord les identifiants `jina-ai` du tableau de bord ; `JINA_AI_API_KEY` est utilisé comme solution de repli uniquement lorsqu’aucune clé du tableau de bord n’existe. La carte `jina-reader` correspond uniquement à Reader / `r.jina.ai` (`POST /v1/web/fetch`) et ne fournit jamais d’embeddings ni de reranking.

Les modèles du registre qui annoncent la prise en charge multimodale acceptent également jusqu’à 32 éléments structurés indépendants du fournisseur. Les types d’éléments multimédias sont `text`, `image`, `audio`, `video` et `document`. Leur `source` multimédia est soit `{"type":"url","url":"https://..."}`, soit `{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano` et l’alias de famille `jina-ai/jina-embeddings-v5-omni` → omni-small) accepte également la documentation native EmbeddingsV5Request de Jina et la **transmet intacte** à `https://api.jina.ai/v1/embeddings` :

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Les valeurs natives `{ image | audio | video | pdf }` peuvent être une URL HTTPS publique, un URI `data:` ou du base64 brut. OmniRoute ne convertit pas ces objets en chaînes et ne récupère pas les URL d’images natives : Jina récupère elle-même les médias publics. Les champs Jina supplémentaires (`task`, `normalized`, `truncate`, `embedding_type`) sont transmis. Les SKU Jina réservés au texte refusent toujours les documents non textuels.

Limites de sécurité et de transport :

- Les URL de médias distants doivent être publiques et utiliser HTTPS. Les éléments canoniques `{type,source:url}` sont récupérés côté serveur (révalidation des redirections, délai d’expiration, limites de taille, DNS public, association de connexion), puis intégrés avant l’appel au fournisseur. Les éléments natifs Jina `{image:"https://..."}` sont transmis tels quels après le même contrôle HTTPS public ; Jina récupère l’URL.
- Les médias base64 intégrés sont limités à 8 Mio décodés par élément et à 16 Mio décodés pour l’ensemble de la requête.

Traduction par le fournisseur (les éléments canoniques ne sont jamais transmis inchangés) :

- Modèles multimodaux Jina : chaque élément de premier niveau devient un objet associé à une modalité (`text` / `image` / `audio` / `video` / `pdf`) utilisant des URI de données pour les médias intégrés ; un vecteur par élément de premier niveau.
- Famille Gemini Embedding 2 : un tableau de premier niveau devient une seule requête native `models/{model}:embedContent` avec `content.parts` (`text` ou `inline_data`).
- llama.cpp (`llama-cpp/<model>`, quel que soit le modèle chargé par le serveur local) : les éléments `text` canoniques deviennent des chaînes simples, tandis que `image` / `audio` / `video` deviennent chacun un objet `{"content": [part]}`, utilisant les parties de contenu de discussion de llama-server (`image_url`, `input_audio` avec le format `wav` / `mp3` / `flac`, `input_video`) avec des données intégrées ; un vecteur par élément de premier niveau. Le serveur doit être exécuté avec `--embedding --mmproj …` ; sans projecteur, il refuse lui-même les médias. `document` n’est pas pris en charge.
- Les modèles inconnus ou dynamiques dépourvus de métadonnées de modalité explicites refusent les entrées structurées avec HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Les combinaisons modèle/modalité non prises en charge renvoient HTTP 400 au lieu de convertir l’élément. Les champs d’extension autres que ceux d’entrée des requêtes historiques utilisant des chaînes ou des tokens continuent d’être transmis inchangés.

```bash
# Lister tous les modèles d’embeddings
GET /v1/embeddings
```

## Génération d'images

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Les fournisseurs disponibles incluent OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana,**OpenRouter** ,**ZenMux** , SD WebUI (local), ComfyUI (local).

`n` renvoie les images `n` dans `data[]`. Les fournisseurs dont API en amont renvoie une image par appel (Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik, NVIDIA NIM, Cloudflare Workers AI) reçoivent `n` appels en amont séparés, au plus 4 en vol. Un `seed` fixe est compensé par l'index d'appel (`seed`, `seed + 1`,…), donc les images diffèrent mais restent reproductibles. `n` est limité à 10. La requête échoue dans son ensemble si un appel échoue. La liste des formats de diffusion est `SINGLE_IMAGE_FANOUT_FORMATS` dans `open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux réutilise la connexion de clé API existante et accepte les préfixes `zenmux/` ou `zm/` :

- `zenmux/openai/gpt-image-2` utilise les images APIOpenAI de ZenMux. Les options incluent `size`, `quality`, `n`, `output_format`, `output_compression`, `background` et `response_format`.
- D'autres éditeurs, tels que `zm/meta/muse-image-1.0`, utilisent le point de terminaison Vertex AI `:predict` de ZenMux. `n` correspond à `sampleCount`, `aspect_ratio` à `aspectRatio` et `image_size` (`1K`, `2K`, `4K`) à `sampleImageSize`. Un pixel `size` fournit uniquement un rapport hauteur/largeur, et non des dimensions de pixel garanties. Les ratios, résolutions et nombres pris en charge varient selon le modèle.
- `zm/inclusionai/ming-image-0.1-design` choisit ses propres dimensions. Omettre `size`, `aspect_ratio` et `image_size`; les valeurs explicites renvoient HTTP 400. PNG, JPEG et WebP peuvent être demandés avec `output_format`.

Cette intégration prend en charge la génération de texte en image, et non l'édition d'images de référence. La sortie du sommet est normalisée en `data[].b64_json`; `response_format: "url"` renvoie un HTTPS URL en amont ou un URL de données base64 lorsque seuls les octets d'image sont disponibles. Les sorties Empty/filtered renvoient une erreur plutôt qu'un succès vide. L'accès au modèle dépend du compte ZenMux. Voir les images [APIZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) et [OpenAI API](https://docs.zenmux.ai/api/openai/generate-an-image).

Une connexion de connexion Microsoft 365 Copilot sert `copilot-m365-web/m365-copilot-image` via l'outil d'image intégré de Copilot: un tour Copilot par image (`n` 1–4), `size` contrôlant uniquement l'orientation et les images renvoyées en ligne (`b64_json`, ou une donnée URL pour `response_format: "url"`). Voir [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation).

```bash
# List all image models
GET /v1/images/generations
```

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",

```

`model` sélectionne le fournisseur OCR via un préfixe `provider/model` ; un identifiant de modèle
nu (par exemple `mistral-ocr-latest`) est associé à son fournisseur enregistré, et si `model` est
omis, Mistral est utilisé par défaut (`mistral-ocr-latest`). Fournisseurs enregistrés
(`open-sse/config/ocrRegistry.ts`) :

| Provider id                   | Model id             | `model` value                                               | Remarques                                                                                                                                     |
| ----------------------------- | -------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (or bare `mistral-ocr-latest`) | Synchrone — la réponse est renvoyée directement depuis l’unique appel en amont.                                                               |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                 | Appel en amont asynchrone (`analyze` + interrogation) — voir ci-dessous.                                                                      |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                     | Synchrone, via le point de terminaison partenaire `openapi/chat/completions` de Vertex AI — voir ci-dessous pour l’authentification et l’URL. |

Les trois fournisseurs renvoient un corps au même format que Mistral :

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Flux d’interrogation d’Azure Document Intelligence

L’API `analyze` d’Azure Document Intelligence est asynchrone : la requête initiale renvoie un
en-tête `Operation-Location` au lieu d’un corps, et le résultat doit être interrogé. Le gestionnaire
(`open-sse/handlers/ocr.ts`) interroge cette URL chaque seconde pendant 30 tentatives au maximum,
échoue immédiatement (sans continuer les interrogations) en cas de réponse d’interrogation
non `ok` ou de statut `"failed"`, et renvoie `504` si l’opération est toujours en cours après
épuisement du nombre de tentatives. La réponse Azure finale est normalisée dans la même structure
`pages`/`markdown` que celle utilisée par Mistral avant d’être renvoyée à l’appelant ; le code
client n’a donc pas besoin de traiter différemment ce fournisseur.

### Authentification et résolution du point de terminaison Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` réutilise la même authentification Vertex AI que celle déjà prise en charge
par OmniRoute pour le trafic de discussion et d’image (`open-sse/executors/vertex.ts`) : la clé API
de la connexion est soit un identifiant JSON de compte de service (échangé contre un jeton d’accès
OAuth de courte durée via le flux bearer JWT), soit un jeton d’accès OAuth déjà créé, utilisé tel quel.
L’URL du point de terminaison en amont est le point de terminaison partenaire générique
`openapi/chat/completions` de Vertex, construit à partir du projet et de la région de la connexion —
un `providerSpecificData.project`/`providerSpecificData.region` explicite est toujours prioritaire ;
sinon, le projet est dérivé du `project_id` du JSON du compte de service et la région est définie par
défaut sur `us-central1`. Les deux résolutions sont effectuées dans `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), puis utilisées par
`src/app/api/v1/ocr/route.ts` avant la transmission à `handleOcr`.

```bash
GET /v1/models
```

### Tarifs des modèles (`pricing`)

Une entrée contient un objet `pricing` lorsque OmniRoute connaît le tarif du modèle. Le tarif
provient de la table de tarification utilisée par la comptabilisation des coûts : valeurs par
défaut intégrées, tarifs synchronisés et remplacements définis via `/api/pricing`. Il s'agit de
tarifs catalogue ; les fournisseurs par abonnement affichent donc eux aussi un tarif par jeton.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Champs                                                          | Unité                             | Remarques                                                                                                                                                                               |
| --------------------------------------------------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD par jeton, chaîne décimale    | Compatible avec OpenRouter, jamais en notation exponentielle. Les deux champs de cache apparaissent uniquement lorsqu'un tarif de cache existe.                                         |
| `input`, `output`, `cached`, `cache_creation`                   | USD par million de jetons, nombre | Champs issus des versions précédentes du catalogue, conservés pour les clients existants. `reasoning` et `long_context` apparaissent également lorsque la ligne tarifaire les contient. |

- **Les combinaisons** portent le tarif de leur première cible visible. Les combinaisons
  intégrées `auto/*` sélectionnent une cible au moment de la requête ; elles n'ont donc pas de
  `pricing`.
- **Les modèles gratuits** affichent `"0"` (et `0`) lorsque leur tarif est nul. Un modèle sans
  ligne tarifaire affiche également `"0"` lorsque le catalogue le marque comme gratuit
  (`free: true`) ou que le catalogue intégré des modèles gratuits le répertorie.
- **Tarif inconnu :** l'entrée ne contient pas de clé `pricing`.
- **Les fournisseurs facturés au crédit** (comme Kiro) facturent par requête plutôt que par
  jeton. Leurs entrées conservent les champs numériques par million de jetons qu'elles
  possédaient auparavant et ne contiennent aucun champ de chaîne par jeton.
- **Les variantes** (identifiants d'effort de raisonnement, alias sans réflexion, miroirs de
  découverte et de passerelle) copient le tarif du modèle vers lequel elles acheminent les
  requêtes.
- Les champs contiennent uniquement les tarifs de base. Les paliers de contexte long (le champ
  numérique `long_context`) et les multiplicateurs de niveau de service (par exemple Codex fast
  ou flex) ne modifient pas `prompt` ni `completion`.
- L'objet est identique pour tous les modes d'authentification, y compris une requête au style
  Anthropic avec `x-api-key` et `anthropic-version` (la réponse reste `{ "object": "list",
"data": [...] }`). Implémentation : `src/app/api/v1/models/catalogPricing.ts`.

### Préfixes des identifiants de modèle (`?prefix=`)

La plupart des modèles sont annoncés avec un **préfixe de fournisseur**. Le préfixe obtenu est
contrôlé par l'indicateur de fonctionnalité `MODELS_CATALOG_PREFIX_MODE` et peut être remplacé
**par requête** à l'aide d'un paramètre de requête — ce qui est utile pour un client souhaitant
obtenir une liste épurée sans modifier le paramètre défini à l'échelle du serveur pour tous les
autres utilisateurs :

```bash
GET /v1/models?prefix=alias        # un identifiant par modèle — le préfixe d'alias court
GET /v1/models?prefix=dual         # les deux formes (valeur par défaut du serveur)
GET /v1/models?prefix=canonical    # uniquement le préfixe complet d'identifiant du fournisseur
```

| Mode        | Émet                                                     | Remarques                                                                                                                                                                                                                                                       |
| ----------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **et** `claude/claude-sonnet-4-6` | **Valeur par défaut.** Les deux identifiants acheminent les requêtes vers le même modèle ; ils sont conservés afin que les configurations client codant en dur l'une ou l'autre forme continuent de fonctionner. Le catalogue est environ deux fois plus grand. |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Une entrée par modèle. Les fournisseurs sans alias distinct émettent tout de même leur entrée, afin qu'aucun élément ne soit perdu.                                                                                                                             |
| `canonical` | `claude/claude-sonnet-4-6`                               | Une entrée par modèle sous le préfixe complet d'identifiant du fournisseur. Les fournisseurs sans alias distinct (par ex. `antigravity/…`, `agy/…`) émettent également leur identifiant unique ici, afin qu'aucun élément ne soit perdu.                        |

Un miroir en mode `dual` peut également être reconnu sans le paramètre de requête : il contient un
champ `parent` pointant vers l'identifiant principal.

Les clients qui affichent un sélecteur de modèles doivent demander `?prefix=alias` — c'est ce que
fait l'[extension OmniCopilot pour VS Code](../guides/VSCODE-COPILOT.md).

### Filtres de découverte (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` accepte des filtres de découverte facultatifs. Sans aucun d'eux, la réponse
reste inchangée. Ils réduisent le catalogue déjà visible par l'appelant (les autorisations de la
clé API s'appliquent en premier) et sont exécutés avant la pagination de style OpenAI avec
`limit` / `after` :

```bash
GET /v1/models?capability=vision&capability=tool_calling   # toutes les capacités répertoriées doivent être vraies
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` du catalogue ; les lignes qui n'en ont pas sont de type `chat`
GET /v1/models?q=sonnet&limit=10                           # correspondance insensible à la casse sur l'identifiant ou le nom
```

| Param         | Valeurs                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | entier non négatif, comparé à `context_length`                                                      |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1 à 200 caractères                                                                                  |

Une valeur inconnue ou un `min_context` qui n’est pas un entier non négatif (par exemple `1.5`)
renvoie HTTP `400` et le message répertorie les valeurs valides. Implémentation :
`src/app/api/v1/models/catalogFilters.ts`.

### Sélection de modèles (`POST /v1/models/query`)

`POST /v1/models/query` renvoie une liste courte et déterministe issue du même catalogue, avec la même
authentification et la même visibilité par clé que `GET /v1/models` :

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Tous les champs sont facultatifs. `capabilities` et `exclude` acceptent un tableau ou une chaîne séparée
par des virgules ; `max_output` est comparé à `max_output_tokens`. Les résultats sont triés par
`owned_by`, puis par `id`. `limit` vaut `20` par défaut et les valeurs supérieures à `100` sont plafonnées
à `100`. Un JSON non valide, un champ inconnu ou une valeur non valide renvoie HTTP `400`.

### Modèles de chat masqués individuellement

Un modèle marqué **Masqué** sur la page de son fournisseur est exclu du catalogue et rejeté
avec HTTP `404` / `model_not_found` lorsqu’il est demandé explicitement. La vérification utilise le
fournisseur et le modèle résolus, y compris les alias de fournisseur, les préfixes de nœud de fournisseur
compatible et les valeurs par défaut de connexion. Une combinaison ignore les cibles masquées et peut
utiliser un modèle frère visible ; lorsqu’il ne reste aucune cible exécutable, elle renvoie le même code
d’erreur. La levée du masquage prend effet à la requête suivante. Les remplacements de visibilité
exclusifs aux images ne masquent pas le modèle de chat portant le même ID.

Ce paramètre de modèle individuel est distinct des
[listes d’autorisation/de refus d’exposition des modèles](../routing/MODEL_EXPOSURE_LIST.md), qui filtrent
la publicité dans le catalogue et les candidats au routage automatique tout en conservant l’envoi explicite.
Les autorisations de modèles par clé API continuent de s’appliquer indépendamment. Le mode de préfixe
du catalogue par défaut reste `dual`.

### Variantes de modèles sans réflexion

Pour les modèles Claude capables de réflexion, `/v1/models` annonce également une variante
**sans réflexion** dont l’identifiant est préfixé par `claude-3-omniroute-no-thinking/` :

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

La sélection de cet identifiant (par exemple dans une configuration Claude Code qui joint toujours un bloc
`thinking`) renvoie au véritable `<provider>/<model>` avec la réflexion supprimée — `thinking:{type:"disabled"}`
sur le chemin `/v1/messages`, ou les champs `reasoning`/`reasoning_effort` supprimés sur le chemin
`/v1/chat/completions`. La variante n’est répertoriée que pour les modèles de la famille Claude qui
prennent en charge la réflexion **et** respectent `disabled` (ainsi, par exemple, les modèles uniquement
adaptatifs qui rejettent `disabled` sont exclus). Les opérateurs peuvent activer ou désactiver la variante
par modèle via `ModelSpec.noThinkingAlias`.

## Génération audio ElevenLabs

Configurez une connexion de fournisseur `elevenlabs` dans OmniRoute avec votre clé API ElevenLabs.
Les clients s’authentifient avec leur clé **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`) ;
la passerelle fournit la clé du fournisseur enregistrée sous la forme `xi-api-key`. N’envoyez jamais une clé
ElevenLabs comme jeton bearer de la passerelle.

| Méthode | Chemin                      | Réponse                                      | Catégorie du point de terminaison de clé API |
| ------- | --------------------------- | -------------------------------------------- | -------------------------------------------- |
| POST    | `/v1/sound-generation`      | Octets audio natifs                          | `elevenlabs`                                 |
| POST    | `/v1/music`                 | Octets audio natifs                          | `music`                                      |
| POST    | `/v1/music/stream`          | Octets audio en continu                      | `music`                                      |
| POST    | `/v1/music/detailed`        | Audio natif multipart et plan de composition | `music`                                      |
| POST    | `/v1/music/detailed/stream` | Métadonnées SSE natives et segments audio    | `music`                                      |
| POST    | `/v1/music/plan`            | Plan de composition JSON                     | `music`                                      |

Ces points de terminaison complètent les routes existantes `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` et `/v1/speech-to-text`. Les champs JSON natifs
et les paramètres de requête tels que `output_format` et `enable_logging` sont conservés.
Les réponses de `/v1/music/detailed` conservent leurs limites multipart ; analysez-les comme du multipart.
`/v1/music/detailed/stream` retourne `text/event-stream` avec les métadonnées de composition et
des segments audio encodés en base64 dans des événements SSE. Les six routes prennent en charge
le prévol CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Un court effet sonore. Durée : de 0,5 à 30 secondes.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# La durée de la musique est exprimée en millisecondes : de 3000 à 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Utilisez `/v1/music/stream` avec le même corps JSON pour une livraison audio incrémentielle. La composition
accepte exactement l’un des deux champs `prompt` ou `composition_plan` ; `/v1/music/plan` exige `prompt`
et accepte éventuellement `source_composition_plan`. Les schémas natifs conservent les champs
supplémentaires du fournisseur afin que les versions des plans de composition et les options
d’ajustement fin soient transmises à ElevenLabs.

Le point de terminaison unifié `/v1/music/generations` accepte également `elevenlabs/music_v1`,
`elevenlabs/music_v2` et `elevenlabs/music_v2_5`. Lorsqu’une connexion ElevenLabs active est disponible,
ces modèles sont exposés par le catalogue musical. Ce point de terminaison retourne
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Son champ `duration` est exprimé en
secondes et est mappé vers `music_length_ms` ; un champ `music_length_ms` explicite est prioritaire.
`instrumental` est mappé vers `force_instrumental`, le champ natif étant prioritaire.
Utilisez les points de terminaison natifs de diffusion en continu pour le streaming et le point de
terminaison natif de composition pour les requêtes pilotées uniquement par un plan de composition.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Les restrictions de point de terminaison, de modèle, de budget et de connexion s’appliquent avant
tout appel en amont. Les routes natives retournent les codes d’état et les corps d’erreur du service
en amont sans modification, notamment `402` pour une restriction liée au forfait et `429` pour une
limite de quota. Les en-têtes `character-cost`, `song-id`, `request-id` et `retry-after` sont conservés
lorsqu’ils sont présents. Un solde de crédits gratuits ne garantit pas l’accès à chaque modèle musical,
format de sortie ou fonctionnalité d’API : ElevenLabs détermine les droits pour chaque requête.
Le point de terminaison unifié conserve les codes d’état d’erreur dans l’enveloppe d’erreur normalisée
d’OmniRoute.

Contrats en amont : [effets sonores](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[composition musicale](https://elevenlabs.io/docs/api-reference/music/compose) et
[détails de la musique en streaming](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

```bash
# Reclassement (fournisseur du registre cloud ou nœud de fournisseur compatible OpenAI au format "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Recherche Jina (s.jina.ai ; alias de fournisseurs : jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Modérations
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — renvoie un corps audio/mpeg (ou au format demandé)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Le TTS Soniox nécessite une langue et une voix : `language` prend par défaut la valeur "en" ; une voix
# absente ou un nom de voix OpenAI standard (alloy, nova, …) devient "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Édition d’image (multipart)

```

> **Nœuds de fournisseur pour le reranking :** `POST /v1/rerank` achemine également les requêtes vers des nœuds de fournisseur compatibles avec OpenAI
> (oMLX, vLLM, Infinity, TEI derrière une passerelle, …) désignés sous la forme `<node-prefix>/<model>`. Les
> nœuds locaux (`localhost`, `127.0.0.1`, `172.16.0.0/12`) sont toujours admissibles, tout comme les noms d’hôte
> répertoriés par l’opérateur dans `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (par exemple, un nom de service Docker/Compose tel
> que `http://reranker:8080/v1` ; ces nœuds sont appelés directement, jamais via `HTTP(S)_PROXY` ou le proxy associé
> épinglé d’une connexion). Les nœuds situés sur tout autre
> hôte — une machine du réseau local ou un pair Tailscale — sont admissibles uniquement lorsque l’opérateur active
> l’indicateur de fonctionnalité `RERANK_REMOTE_PROVIDER_NODES` **et** que l’URL de base du nœud respecte la
> politique des URL sortantes des fournisseurs (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> L’étape de reranking du moteur de mémoire appelle cette route via la
> boucle locale ; la même règle régit donc `rerankProviderModel` dans les paramètres de la mémoire.
>
> **Formats des serveurs locaux :** le nœud est appelé à l’adresse `<base>/v1/rerank` et, en cas de 404, à l’adresse `<base>/rerank`
> (Infinity, TEI). Le corps de la requête en amont contient les deux syntaxes Cohere/OpenAI (`documents`,
> `return_documents`) et TEI (`texts`, `return_text`), et la réponse en amont est
> normalisée selon l’enveloppe Cohere : le tableau brut de TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> des passerelles intermédiaires et `{data: [...]}` de style Voyage sont tous renvoyés au client sous la forme
> `{results: [{index, relevance_score, document?}]}`, triés par score et limités à `top_n`.

> **Détection des nœuds de fournisseur :** les modèles d’un nœud de fournisseur compatible avec OpenAI apparaissent dans `GET /v1/models`
> sous le préfixe du nœud. Les entrées qui ne contiennent aucune métadonnée de point de terminaison (cas typique des listes locales
> `/v1/models`) héritent de l’`apiType` du nœud : les modèles d’un nœud `embeddings` sont donc de
> type `type: "embedding"` et ceux d’un nœud `rerank` de type `type: "rerank"`, au lieu d’être associés par défaut au chat ;
> la présence explicite de `supportedEndpoints` sur une entrée synchronisée ou ajoutée manuellement reste prioritaire.

### Combinaisons search/fetch nommées

`POST /v1/search` et `POST /v1/web/fetch` acceptent tous deux `model` comme nom de combo enregistré. Utilisez soit `model`, soit un `provider` explicite ; envoyer les deux retours `400`. Sans aucun de ces champs, la sélection automatique du fournisseur existante reste inchangée.

Le Combo Builder et son catalogue Ajouter un modèle exposent tous deux les entrées d'opération Web natives pour les fournisseurs connectés, même s'ils n'ont pas de liste de modèles LLM. Spectacles Serper** Recherche sur le Web** ; Tavily montre** Recherche Web / Extraction de pages** , et les fournisseurs de récupération uniquement affichent** Extraction de pages** . Choisissez l'entrée et le compte comme d'habitude. Une seule entrée Tavily dessert les deux points de terminaison Web ; ces entrées d'opération ne sont pas ajoutées aux sélecteurs de client de chat uniquement ou aux sondes de modèle de chat.

Par exemple, créez un** priorité** combo nommé `shared-free` avec ces cibles ordonnées :

1. `openai/gpt-4o`
2. `tavily-search/web`
3. `serper-search/web`
4. `jina-reader/fetch`

Utilisez ensuite le même nom sur chaque surface :

```json
{ "model": "shared-free", "query": "Open source speech recognition", "max_results": 5 }
```

```json
{ "model": "shared-free", "url": "https://example.com", "format": "markdown" }
```

Search considère Tavily puis Serper ; chercher considère Tavily puis Jina Reader ; le chat ignore les fournisseurs search/fetch dédiés et prend en compte OpenAI. La compatibilité vient des registres des exécuteurs search/fetch, et non des mots contenus dans le nom d'un modèle. Le filtrage précède la sélection et l'envoi des informations d'identification, et ne modifie jamais le combo enregistré.

Les routes sans fonction de chat prennent en charge `priority`, `fill-first`, `round-robin`, `weighted`, `random`, `strict-random`, `least-used` et `p2c`. Les stratégies de synthèse de chat uniquement telles que `fusion`, `pipeline` et `context-relay` sont rejetées sur les routes autres que le chat plutôt que d'être appliquées silencieusement aux médias de recherche ou générés. Le moteur combo existant gère le repli ordonné, y compris les échecs de quota en amont, et conserve l'étape IDs, les épingles de compte, les listes autorisées de compte par étape, les références imbriquées, les étendues connection/quota de l'appelant et la politique d'accès combo. Les résultats conservent leur schéma search/fetch natif, y compris le fournisseur réel ; `X-OmniRoute-Combo-Trace` identifie la décision de routage. Les combos inconnus renvoient `404`; les combos inactifs et les combinaisons sans cibles compatibles renvoient `400`.

Chaque tentative de combo utilise un fournisseur explicite. Il ne peut pas invoquer le pool de fournisseurs automatiques natifs dans le dos du combo. Les requêtes à fournisseur explicite conservent leur comportement existant à fournisseur unique. Les demandes de chat direct ciblant les fournisseurs search/fetch dédiés renvoient un JSON `400` exploitable au lieu de passer par un exécuteur de style OpenAI.

### Itinéraires combinés spécifiques aux capacités

Les combos enregistrés peuvent contenir un objet `routes` dont les clés sont des capacités API. Chaque route possède sa liste de cibles, sa stratégie et sa configuration d'exécution. Les `models`, `strategy` et `config` de niveau supérieur restent le plan Chat compatible avec l'ancien ; les anciens combos sans `routes` continuent de fonctionner sans changement.

Les clés de route prises en charge sont `chat`, `search`, `web-fetch`, `embeddings`, `rerank`, `images`, `image-edits`, `videos`, `music`, `ocr`, `audio-speech`, `audio-transcriptions`, `audio-translations` et `audio-generation`. La projection des points de terminaison a lieu avant la sélection, la notation ou l'envoi des informations d'identification. Les références de combo imbriquées sélectionnent l’itinéraire du combo enfant pour la même fonctionnalité.

`POST /v1/music/generations` et `POST /v1/ocr` acceptent un nom combo dans `model`. Le `POST /v1/music` natif compatible avec ElevenLabs accepte également un nom de combo dans `model_id`, mais chaque cible utilisable sur ce point de terminaison natif doit être un modèle musical ElevenLabs afin que son contrat de réponse binaire soit préservé. `POST /v1/sound-generation` accepte un combo `audio-generation` dans `model_id` sous la même contrainte binaire native. Utilisez `/v1/music/generations` pour les fournisseurs de musique hétérogènes.

**Sélection automatique :** sans `provider`, le fournisseur le moins cher avec une connexion configurée fonctionne en premier et le deuxième moins cher est le basculement. Les fournisseurs de dernier recours gratuits (`duckduckgo-free`) ne sont utilisés que lorsque rien d'autre n'est configuré. Un SearXNG auto-hébergé est considéré comme configuré une fois que sa connexion stocke un vrai `baseUrl` (et non le `http://localhost:8888/search` par défaut du catalogue) : il se classe alors comme un fournisseur à 0 $ devant ceux à clé, avec le fournisseur à clé le moins cher comme basculement, y compris lorsque SearXNG répond 400, 401, 403 ou 404. Un `baseUrl` qui n'est pas un `http(s)` URL valide ou qui pointe vers une adresse de métadonnées cloud ne le fait pas. compter. Une connexion SearXNG qui stocke un jeton se classe de cette façon uniquement par rapport à `https://` ou loopback `http://`. Sur `http://` distant, il ne s'agit jamais d'un basculement et reste un dernier recours, utilisé uniquement lorsqu'aucun autre fournisseur n'est configuré ou lorsqu'il est demandé par son nom, il envoie donc le jeton en texte clair dans ces deux cas.

### Exa et Tavily `provider_options`

Exa et Tavily lisent les champs spécifiques au fournisseur à partir d'un sac avec espace de noms : `provider_options.exa` (ou `provider_options["exa-search"]`) et `provider_options.tavily` (ou `provider_options["tavily-search"]`). Seules les clés ci-dessous sont transmises. Chacun est vérifié par rapport à son propre schéma Zod dans `open-sse/handlers/search/providerOptionsPassthrough.ts` et une clé du mauvais type est supprimée. Toute autre clé est ignorée, y compris auth, base URL, `stream` et `outputSchema`. Les clés plates utilisées par d'autres fournisseurs (`cx`, `depth`, ...) fonctionnent comme avant.

| Fournisseur | Champs de niveau supérieur                                                                                                                                                                                                                                                                                                                                                | Imbriqué                                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Examen      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitives plates), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` fusionné sur le `{ text: true, highlights: true }` par défaut |
| Tavily      | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                           |

Les champs génériques gagnent toujours : `query`, `max_results`, `filters` (domaines), `country` et le topic dérivé de `search_type`. Sur Exa, `search_type: "news"` conserve `category: "news"`. Tavily accepte également `search_type: "finance"` (`topic: "finance"`).

Le coût de recherche de Firecrawl est enregistré par bloc démarré de 10 résultats renvoyés, à 0,002 $ (2 crédits) par bloc et au moins un bloc par appel ( [facturation Firecrawl](https://docs.firecrawl.dev/billing) ) : 11 résultats coûtent 0,004 $.

Le `time_range` générique atteint désormais les deux fournisseurs : Exa obtient `startPublishedDate` (horodatage ISO ) et Tavily obtient `start_date` (`YYYY-MM-DD`). Une date explicite dans `provider_options` remplace celle mappée.

Les résultats Exa conservent `id`, `highlights` (chaque surbrillance, pas seulement le premier utilisé comme `snippet`), `highlight_scores`, `summary`, `subpages`, `entities` et `extras` dans `provider_raw`. Les résultats Tavily conservent `images` et `favicon`.

Le coût de recherche de Linkup est enregistré à 0,005 $ pour `depth` `fast` et `standard` et 0,05 $ pour `deep` ( [Tarif Linkup](https://docs.linkup.so/pages/documentation/development/pricing) ), que `depth` provienne de `provider_options` ou des paramètres de connexion.

Exa `type: "lite"` (Exa 3.0) accepte un ensemble plus petit de champs et rejette l'intégralité de la demande lorsqu'un autre champ est défini. Pour Lite, `additionalQueries`, `systemPrompt` et toutes les touches `contents` sauf `text` et `highlights` sont supprimées avant l'appel. Les `subpages`, `subpageTarget`, `highlights.numSentences` et `highlights.highlightsPerUrl` obsolètes ne sont plus transmis.

La comptabilité analytique est le registre plat `costPerQuery`, à l'exception d'Exa, qui suit la propre tarification d'Exa : 0,007 $ par appel pour `auto` (et l'ancien `fast`) ou 0,004 $ pour `lite` (et l'ancien `instant`), couvrant 10 résultats ; 0,001 $ pour chaque résultat supplémentaire ; et 0,001 $ par résultat renvoyé lorsque `contents.summary` est défini. Tavily est enregistré à 1 crédit (0,008 $) pour `search_depth` `basic`, `fast` et `ultra-fast`, et 2 crédits (0,016 $) pour `advanced` ( [crédits Tavily API](https://docs.tavily.com/documentation/api-credits) ). Un appel avec `auto_parameters: true` que Tavily met à niveau vers avancé est toujours enregistré à 1 crédit.

## Récupération Web API

Extrayez le contenu d'un URL via un fournisseur de récupération Web configuré (Firecrawl, Jina Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract, Keenable Fetch).

Parallel Extract (`parallel-search`, même clé API que Parallel Search) renvoie Markdown uniquement — tout autre `format` est un `400` — et limite le contenu à 100 000 caractères. Lorsque la page cible elle-même ne peut pas être extraite, l'amont la signale dans un HTTP 200 ; OmniRoute fait apparaître cela comme un `422` avec un message fixe.

Keenable Fetch (`keenable-search`) renvoie également Markdown uniquement (tout autre `format` est un `400`) et limite le contenu à 100 000 caractères. Cela fonctionne sans clé : une requête `provider: "keenable-search"` explicite sans connexion utilise le point de terminaison sans clé de Keenable (limites de débit par IP). Une clé configurée ne fait que lever ces limites ; la sélection automatique utilise Keenable uniquement lorsqu'une clé est configurée.

| Méthode | Chemin          | Description                                               |
| ------- | --------------- | --------------------------------------------------------- |
| POST    | `/v1/web/fetch` | Fetch/scrape un corps URL — validé par `v1WebFetchSchema` |

**Authentification :** Clé API au porteur (`extractApiKey` + `isValidApiKey`). Politique appliquée via `enforceApiKeyPolicy`.

Les combinaisons nommées utilisent le [contrat de routage `model`](#named-searchfetch-combinations) ci-dessus, préservant les options et réponses spécifiques à la récupération.

**Solution de repli tenant compte des quotas (#8297) :** lorsque ni `provider` ni `model` ne sont donnés, le pool (`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` → `parallel-search` → `keenable-search`) est parcouru dans un ordre de priorité fixe (remplir en premier). — un fournisseur à débit limité mais configuré est ignoré au lieu de court-circuiter la requête, et un échec retryable/quota en amont (HTTP 429 toujours ; 402/403 pour les niveaux gratuits de style quota Firecrawl/Tavily/TinyFish — pas pour Jina Reader, et jamais pour une simple mauvaise demande de 400) passe au prochain fournisseur accrédité non essayé au moment de la demande. Lorsque tous les fournisseurs du pool sont épuisés, le point de terminaison renvoie un seul `429` (avec un en-tête `Retry-After` ) au lieu du précédent `400` générique. Lorsqu'un `provider` explicite est demandé, il y a** Non** secours silencieux — un fournisseur explicite à débit limité ou défaillant fait apparaître sa propre erreur (`429` s'il est à débit limité, sinon le statut en amont).

### Récupération de session de quota (opt-in)

L'appelant s'inscrit par demande avec trois en-têtes :

| En-tête                      | Valeur                                                         |
| ---------------------------- | -------------------------------------------------------------- |

## Utilisation en libre-service (`/api/usage/om-usage`)

N'importe quelle clé API peut lire** le sien** utilisation et quotas — pas d'autorisation de gestion. Il s'agit du point de terminaison qu'un client (CLI, le panneau OmniCopilot ) utilise pour montrer à un détenteur de clé ses dépenses.

```bash
# Text form (the historical contract — plain text for a terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Structured form — what a UI consumes
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

La clé doit avoir**`allowUsageCommand`** activé (désactivé par défaut — le gestionnaire de clés API du tableau de bord le bascule par clé). Sans cela, le point final répond `403`.

`?format=json` renvoie une forme discriminée afin qu'un appelant ne lise jamais un champ de données suite à un refus. Sur le succès :

```jsonc
{
  "allowed": true,
  // present only when the key opted into per-key usage limits (daily/weekly/5-hour USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // the selected provider quota snapshot, or null when nothing is cached yet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // every connection's snapshot, so a UI can render several providers side by side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Sur refus (`401` bad key / `403` not approved) le même itinéraire renvoie `{ "allowed": false, "error": { "message": "…" } }` — un `personal`/`provider` présent mais vide (clé autorisée, rien appris pour l'instant) est un état différent d'un refus, et seule la forme JSON les distingue.

**Authentification :** la propre clé Bearer API de l'appelant, validée avec `isValidApiKey` — ce n'est _pas_ la surface de gestion (`/api/keys/…`), qui reste derrière `requireManagementAuth`.

### Pourcentages de quota bruts et ajustés au seuil

Lors de la consommation `/api/usage/om-usage`, les appelants doivent noter la distinction entre les pourcentages présentés par le** sortie en texte brut** et la structure** sortie JSON** :

| Aspect                        | Format de texte brut (`/api/usage/om-usage` / `@@om-usage`)                                              | format JSON (`?format=json`)                                                    |
| :---------------------------- | :------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------ |
| **Champ de sortie**           | `NN% left` (par exemple, `20% left`)                                                                     | `provider.quotas` / `providers[].quotas`                                        |
| **Mesures**                   | **Allocation utilisable ajustée en fonction du seuil** : capacité restante au dessus du seuil de coupure | **Quota brut en amont** : mesure non ajustée du fournisseur                     |
| **Mise à l'échelle du seuil** | Mis à l'échelle via `effectiveRemainingPercent()` pour que la réserve protégée se lit comme `0% left`    | Aucun (valeurs brutes des instantanés telles que signalées par le fournisseur)  |
| **Données de seuil**          | Incorporé au pourcentage affiché                                                                         | Stocké dans `quotaWindowThresholds` par connexion (ou par défaut du serveur)    |
| **Consommateur principal**    | CLIs interactif, invites de terminal, opérateurs humains                                                 | Intégrations programmatiques, tableaux de bord, analyses, suivis de facturation |

#### La formule d'ajustement du seuil

OmniRoute prend en charge les coupures de quota proactives pour éviter l'épuisement en amont (configuré via la connexion `quotaWindowThresholds`, les paramètres par défaut du fournisseur ou les paramètres de résilience globaux). Lorsqu'un seuil de coupure (par exemple, `cutoff = 25%`) est actif sur une fenêtre de quota, le moteur de rendu de texte calcule l'allocation restante comme :

- Si `remaining <= cutoff`: renvoie `0%`.
- Si `remaining > cutoff`: renvoie `((remaining - cutoff) / (100 - cutoff)) * 100`.

La sortie texte formatée arrondit à l'entier le plus proche (`Math.round(...)`).

#### Exemple illustratif

Considérons une fenêtre de fournisseur avec** 60 % d'utilisation brute** (ainsi** 40 % de quota brut restant** ) et un configuré** Seuil de 25 % du quota restant** seuil:

| Représentation                 | Calcul                                             | Restant |              Implicite utilisé               |
| :----------------------------- | :------------------------------------------------- | :-----: | :------------------------------------------: |
| **JSON brut (`?format=json`)** | Instantané en amont (`quotas[window]`)             | **40%** |                   **60%**                    |
| **Format texte (`NN% left`)**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (si vous calculez `100 - remaining`) |

- **Pourquoi le texte indique qu'il reste 20 % :** Sur le quota physique de 40 % restant sur le compte, 25 % sont réservés par la politique de coupure. L'appelant ne dispose que de 15 % de marge utilisable sur 75 % avant que le routeur n'arrête le routage vers cette connexion. La mise à l'échelle garantit l'épuisement des signaux de connexion (`0% left`) exactement au moment où le routage cessera.
- **Pourquoi JSON préserve les valeurs brutes :** La charge utile JSON renvoie l'instantané exact du fournisseur (`UsageSnapshot`) afin que les outils externes aient accès à l'utilisation en amont de la vérité terrain et `quotaWindowThresholds` au niveau de la connexion sans mise à l'échelle avec perte côté serveur.

#### Conseils de migration des consommateurs

Si une intégration externe (telle qu'un plugin d'éditeur ou une extension d'agent) a précédemment supprimé le point de terminaison du texte (`NN% left`) et calculé le pourcentage utilisé comme `100 - NN`, la migration vers `?format=json` signifie :

- La lecture des valeurs JSON brutes reflétera** consommation réelle en amont** (60% utilisés dans l'exemple ci-dessus).
- Si l'intégration souhaite préserver la sémantique d'allocation utilisable du point de terminaison de texte, elle peut évaluer la formule restante efficace côté client en utilisant `quotaWindowThresholds` pour les remplacements au niveau de la connexion.

### Impact sur la latence

Un HIT du cache sémantique renvoie la réponse depuis le cache **sans
appel en amont**. La valeur signalée par `X-OmniRoute-Response-Latency` est donc proche de zéro
(quelles que soient les valeurs de latence initiales en amont). Les clients sensibles à la latence
(mesures de performances, surveillance p50/p99) doivent consulter l'en-tête de réponse
`X-OmniRoute-Cache-Latency` :

| Valeur      | Signification                                                                          |
| ----------- | -------------------------------------------------------------------------------------- |
| `synthetic` | Réponse renvoyée depuis le cache ; la latence ne correspond pas au temps réel en amont |
| _(absent)_  | Réponse provenant d'un véritable appel en amont                                        |

### Contournement du cache par clé

Les clés API peuvent désactiver les lectures du cache sémantique via `cacheDefaultMode` :

| Valeur   | Comportement                                                                           |
| -------- | -------------------------------------------------------------------------------------- |
| `legacy` | Comportement normal du cache (par défaut)                                              |
| `bypass` | Ignore entièrement la recherche dans le cache ; interroge toujours le service en amont |

Définissez cette option lors de la création de la clé (`POST /api/keys`) ou de sa mise à jour (`PATCH /api/keys/[id]`) :

```json
{ "cacheDefaultMode": "bypass" }
```

### Contournement du cache par requête

Toute requête peut contourner le cache, quels que soient les paramètres de la clé :

```
X-OmniRoute-No-Cache: true
```

## Compatibilité de gestion avec CLIProxyAPI

OmniRoute répond aux trois points de terminaison de gestion de [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)
que les tableaux de bord d'utilisation interrogent pour lire les limites d'abonnement Claude et Codex
(par exemple, la source de limites d'utilisation `cliproxy` de T3 Code). Configurez l'URL de base du client sur
OmniRoute et utilisez une clé API disposant de la portée `manage` comme clé de gestion. Les routes sont
disponibles sous `/v0/management/*` et `/api/v0/management/*`.

| Méthode | Chemin                       | Description                                                                                                                                                 |
| ------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET     | `/v0/management/auth-files`  | Connexions OAuth Claude et Codex sous la forme `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Aucun jeton                          |
| POST    | `/v0/management/api-call`    | Corps `{ auth_index, method, url, header?, data? }`. Envoie une requête autorisée avec le jeton du compte et renvoie `{ status_code, body }`                |
| POST    | `/v0/management/reset-quota` | Corps `{ auth_index }`. Efface le délai de récupération de la connexion, les blocages de modèles et les délais de récupération par portée Codex d'un compte |

- `auth_index` est l'identifiant de connexion OmniRoute. `provider` vaut `claude` ou `codex` (connexions OAuth
  uniquement ; le fournisseur de clés API `anthropic` n'est pas répertorié). Pour Codex,
  `id_token.chatgpt_account_id` est l'identifiant d'espace de travail enregistré et `plan_type` le forfait enregistré.
- `api-call` n'est pas un proxy générique. Il accepte uniquement les requêtes Claude `GET
https://api.anthropic.com/api/oauth/usage` et Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` et
  `POST .../wham/rate-limit-reset-credits/consume`, chacune uniquement pour un compte du fournisseur correspondant.
  Toute autre requête renvoie `403` sans contacter le service en amont. L'en-tête
  `Authorization` de l'appelant (y compris l'espace réservé `$TOKEN$`) est ignoré : OmniRoute injecte
  le jeton d'accès de la connexion, en l'actualisant d'abord lorsqu'il est proche de l'expiration, et ne transmet que
  les en-têtes autorisés (`anthropic-beta` ; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id` ;
  `Accept`, `Content-Type`). Si `Chatgpt-Account-Id` est absent, l'identifiant d'espace de travail enregistré est utilisé par défaut.
  Les requêtes expirent après 15 secondes et utilisent le proxy de la connexion.
- `reset-quota` laisse les états terminaux (banned, expired, credits_exhausted) inchangés. Un
  `auth_index` inconnu renvoie `404`.

Le remplacement utilise la fonctionnalité d'exécution `max_output_tokens` et survit à une resynchronisation du modèle. La page du fournisseur compatible OpenAI propose les mêmes contrôles edit/clear et marque les modèles avec une prise en charge explicite de la vision.

Sur un nœud fournisseur compatible, les chemins d'écriture (`POST`, `PUT`, `PATCH`, `DELETE` et `/api/provider-models/validate-and-add`) stockent l'identifiant du modèle en tant qu'identifiant en amont : un identifiant collé à partir d'une liste préfixée a toute pile principale du préfixe du nœud réduite et les réponses font écho à l'identifiant stocké. Les identifiants réduits des fournisseurs canoniques (par exemple `nvidia/nemotron-…`) sont stockés textuellement. `/v1/models` n'émet jamais d'identifiant `<prefix>/<prefix>/<model>` empilé.

Les nœuds de complétion de chat personnalisés adaptent les désinscriptions de raisonnement explicite au backend en amont. Un test de connexion réussi sélectionne automatiquement les contrôles de modèle de discussion pour chaque modèle exact ID dont l'entrée `/models` prouve une valeur `owned_by` reconnue : `vllm`, `sglang` ou `llamacpp`. Les wrappers transparents compatibles OpenAI peuvent conserver l'entrée de modèle d'origine dans un objet `openai` imbriqué ; la détection suit jusqu'à trois de ces enveloppes. Les modèles dont la propriété est manquante, inconnue ou conflictuelle conservent le comportement OpenAI ordinaire. La détection réutilise la demande de catalogue existante, ne génère aucun jeton d'achèvement et est invalidée lorsque le point de terminaison de connexion change.

Pour épingler le comportement d'un backend qui n'expose pas ces métadonnées, utilisez la mise à jour partielle du fournisseur existante API:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Envoyez ce corps avec `PUT /api/providers/<connection-id>`. Sur cette connexion, un effort de raisonnement explicite de `none` est envoyé sous la forme `chat_template_kwargs.thinking=false` et `chat_template_kwargs.enable_thinking=false`. Les valeurs de modèle natif explicites font autorité à moins qu'une règle de raisonnement côté serveur n'impose un effort. Le paramètre s'applique uniquement lorsqu'une connexion personnalisée compatible avec OpenAI distribue un corps de fin de conversation ; Les demandes de réponses et les fournisseurs ordinaires conservent leur forme de demande native. Définissez `reasoningControl` sur `openai` pour forcer le relais OpenAI `reasoning_effort` ordinaire, ou omettez it/set sur `null` pour utiliser la détection automatique.

Le classificateur en mode automatique Claude Code demande la désactivation de la pensée native par défaut lorsqu'il ne contient aucun contrôle de raisonnement explicite. La détection utilise le marqueur système du classificateur dans les requêtes au format Claude, et non les noms de modèles ou les limites d'achèvement. Les contrôles de corps explicites, les en-têtes effort/thinking pris en charge, les règles de routage et l'effort de modèle résolu conservent leur priorité existante. Les deux étapes du classificateur conservent leurs invites, leurs limites d'achèvement, leurs séquences d'arrêt et leurs véritables verdicts d'autorisation en amont ; la deuxième étape peut toujours produire le raisonnement visible demandé sous forme de texte ordinaire.

#### Provenance limite du modèle

`GET /api/models?withLimits=1` (également `true`; `0`/`false` ou son omission maintient la charge utile par défaut inchangée) ajoute `contextWindow`, `maxInputTokens`, `maxOutputTokens` et un objet `capsSource` à chaque ligne du modèle. `capsSource` nomme la règle qui a fourni chaque limite, de sorte qu'une limite surprenante (par exemple 128k sur un modèle 1M) puisse être retracée jusqu'à son origine. ### Exploration de l'image vidéo

`GET /api/v1/video-bridge/drilldown` lit un handle opaque lié au locataire renvoyé dans `x-omniroute-video-drilldown` après une demande Video Bridge explicitement consentie. Les lectures et `DELETE` nécessitent toujours une clé API valide et l'autorisation `modalityBridgeVideoDrilldownRemoteEnabled` indépendante de l'opérateur. La rétention de la production nécessite en outre `modalityBridgeVideoDrilldownEnabled` et `drilldown: true` strict par pièce. Si la clé a une liste autorisée de point de terminaison non vide, elle doit inclure `video` pour GET et DELETE, que l'appelant utilise `/v1` ou `/api/v1`.

requête GET : `handle` requis ; `variant` facultatif (`preview`, `standard`, `detail`), `limit` (1 à 8 ; l'ancien `frames` est accepté mais ne peut pas être combiné avec `limit`), `page` de base zéro et `start`/`end` secondes. Lorsque les deux limites de focus sont fournies, `end` doit être supérieur à `start`. Les clés de requête Duplicate/unknown sont rejetées. Les réponses réussies contiennent `derivation`, `durationSeconds`, `frames`, `hasMore`, `page`, `variant` et facultatif `focusWindow`; JSON sans magasin est plafonné à 32 MiB Base64 comprise. La sortie surdimensionnée renvoie 413 ; demander moins de cadres.

`DELETE /api/v1/video-bridge/drilldown?handle=...` renvoie `{ "removed": 0|1 }`. GETs inconnus, expirés et croisés sont des réponses 404 indiscernables ; cross-key DELETE ne peut pas supprimer l'entrée du propriétaire. L'accès désactivé renvoie 403, l'authentification missing/invalid 401, les requêtes non valides 400, l'annulation 499 et les erreurs temporaires 503. Les handles sont locaux au processus, expirent après dix minutes et ne survivent pas à un redémarrage. Les nouveaux handles utilisent `v1.` plus un jeton Base64URL aléatoire de 32 octets ; seuls les hachages de jetons sont conservés. Les anciens jetons de 64 hexadécimaux restent syntaxiquement lisibles pour des raisons de compatibilité. Consultez [les garde-fous de Video Bridge](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets) pour connaître les détails du consentement, des quotas et de la dérivation des variantes.

Il en va de même pour `DELETE /api/db-backups` (élaguer les sauvegardes stockées) et `PATCH /api/db-backups` (paramètres de rétention : les valeurs persistantes entraînent l'élagage automatique après chaque sauvegarde). Le listing (`GET`) et la création d'une sauvegarde manuelle (`PUT`) conservent l'authentification de gestion ordinaire.

### Version et canal de publication

```bash
GET /api/system/version
```

Itinéraire de gestion en boucle uniquement (authentification administrateur). Renvoie la version en cours d'exécution, la dernière version publiée et l'état de mise à jour automatique. `releaseChannel` et `channels` sont des champs additifs (rail 3.8.54) ; `channel` garde sa signification — le mode de déploiement utilisé par le programme de mise à jour du tableau de bord (`npm`, `source` ou `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canal npm de la version en cours : `nightly` pour les versions `-nightly.*`, `next` pour les autres versions préliminaires (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` pour une version stable d'une version majeure plus ancienne que `channels.latest`, sinon `latest`. Mêmes règles que `scripts/release/dist-tag.mjs`, qui sélectionne la balise npm dist au moment de la publication.
- `channels` — a publié la tête de chaque balise de distribution, à partir de `npm view omniroute dist-tags` (remplacement de secours du registre HTTP ), mis en cache avec le même TTL de 10 minutes que `latest`. `latest` est toujours présent (revient au champ `latest`, puis `"unavailable"`) ; `next`, `nightly` et `lts` n'apparaissent que lorsque cette balise dist existe. Une requête `Cache-Control: no-cache` actualise les deux recherches.

Le modèle de canal (`latest` = v3 jusqu'à la version 4.0 GA, `next` = rc , `nightly` = `develop` builds, `lts` = v3 patchs après la 4.0 GA) est décrit dans `docs/ops/RELEASE_STRATEGY.md`.

## Transcription audio

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Transcrivez des fichiers audio à l’aide de n’importe quel fournisseur STT configuré. Le premier segment du chemin sélectionne le fournisseur natif (`openai/…`, `deepgram/…`). Les passerelles qui réexportent le modèle d’un autre fournisseur utilisent un identifiant qualifié
(`openrouter/deepgram/nova-3`).

**Requête :**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Réponse :**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Exemples d’identifiants de modèles :** `openai/whisper-1` (nécessite une clé OpenAI),
`openrouter/deepgram/nova-3` (nécessite une clé OpenRouter),
`deepgram/nova-3` (nécessite une clé Deepgram native). Une requête simple vers
`deepgram/nova-3` **n’utilise pas OpenRouter**.

**Formats pris en charge :** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`) :** transcription en mode fichier via le WebSocket Gemini Live (nécessite une clé API Gemini). Le fichier importé est converti en PCM mono 16 kHz avec `ffmpeg`
(`ffmpeg` doit être disponible dans `PATH`, sauf si le fichier est déjà un fichier WAV PCM mono 16 kHz), diffusé vers la session, puis le texte finalisé est renvoyé sous la forme `{ "text": "..." }`. Les champs de formulaire `language` et `prompt` facultatifs sont transmis. Limites : les importations de plus de 25 MiB ou les fichiers audio décodés de plus de 10 minutes renvoient
`413` ; une conversion qui dure plus de 60 s est arrêtée et renvoie `504`. La clé API est envoyée uniquement dans l’en-tête `x-goog-api-key`, jamais dans l’URL WebSocket.

## Limites de jetons

Budgets de **jetons** par clé d’API (distincts du budget en USD mentionné ci-dessus). Appliquées directement sur le chemin de la requête : lorsque l’utilisation actuelle de la fenêtre par une clé atteint sa limite, les requêtes sont rejetées avec `429 Too Many Requests`. Les limites peuvent être limitées à un `model` spécifique, à un `provider`, ou appliquées `global`ement à la clé ; lorsque plusieurs limites correspondent à une requête, la plus restrictive est appliquée.

```bash
# Répertorier les limites de jetons d'une clé (inclut l'utilisation actuelle de la fenêtre)
GET /api/usage/token-limits?apiKeyId=key-123

# Créer ou mettre à jour une limite de jetons
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Supprimer une limite de jetons par identifiant
DELETE /api/usage/token-limits?id=tl-abc
```

> **Notes sur le schéma** (`setTokenLimitSchema`) : `apiKeyId` et `scopeType` (`model` | `provider` | `global`) sont obligatoires. `scopeValue` est obligatoire sauf si `scopeType` est `global` (par exemple, un identifiant de modèle pour la portée `model`, ou un identifiant de fournisseur pour la portée `provider`). `tokenLimit` doit être un entier positif (converti depuis une chaîne). Facultatif : `id` (omettre pour créer, fournir pour mettre à jour), `resetInterval` (`daily` | `weekly` | `monthly`, valeur par défaut `monthly`), `resetTime` (`HH:MM`), `enabled` (valeur par défaut `true`). Les réponses de `GET` enrichissent chaque limite avec `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` et `nextResetAt`. Il s’agit d’un endpoint de classe gestion (l’authentification est appliquée de manière centralisée par le pipeline d’autorisation).

## Traitement des requêtes

1. Le client envoie une requête à `/v1/*`
2. Le gestionnaire de route appelle `handleChat`, `handleEmbedding`, `handleAudioTranscription` ou `handleImageGeneration`
3. Le modèle est résolu (fournisseur/modèle direct ou alias/combinaison)
4. Les identifiants sont sélectionnés dans la base de données locale avec filtrage selon la disponibilité des comptes
5. Pour le chat : `handleChatCore` vérifie le cache sémantique/de signature et résout les paramètres de compression de la combinaison
6. La compression proactive s’exécute avant la traduction vers le fournisseur lorsqu’elle est activée (`lite`, Caveman, RTK ou empilée)
7. L’exécuteur du fournisseur envoie la requête en amont
8. La réponse est retraduite au format du client (chat) ou renvoyée telle quelle (incorporations/images/audio)
9. L’utilisation, les analyses de compression et les journaux de requêtes sont enregistrés
10. Le mécanisme de secours s’applique en cas d’erreur conformément aux règles de la combinaison

Référence complète de l’architecture : [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Résilience (étendue)

OmniRoute expose trois mécanismes indépendants de gestion des défaillances temporaires ; les endpoints de gestion ci-dessous permettent aux opérateurs de les consulter et de les remplacer :

| Portée                     | Stockage de l’état                                     | Lecture                                   | Réinitialiser / effacer                                  |
| -------------------------- | ------------------------------------------------------ | ----------------------------------------- | -------------------------------------------------------- |
| Disjoncteur du fournisseur | `domain_circuit_breakers` + mémoire                    | `/api/monitoring/health`                  | `POST /api/resilience/reset`                             |
| Temporisation de connexion | `rateLimitedUntil` sur les connexions des fournisseurs | `/api/rate-limits`, `/api/providers/[id]` | (réactivation différée ; effacer via PUT du fournisseur) |
| Verrouillage du modèle     | Registre en mémoire de disponibilité des modèles       | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                 |

`PATCH /api/resilience` accepte les remplacements de configuration des disjoncteurs des fournisseurs sous `providerBreaker.oauth` et `providerBreaker.apikey`. Chaque profil prend en charge `degradationThreshold`, `failureThreshold` et `resetTimeoutMs` ; ces mêmes champs sont exposés dans Tableau de bord → Paramètres → Résilience.

```bash
# Effacer le verrouillage d'un seul modèle
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Effacer tous les verrouillages
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Pour la référence conceptuelle complète et les valeurs par défaut des disjoncteurs, consultez [`CLAUDE.md`](../../CLAUDE.md) → « Resilience Runtime State » et [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### File d’attente de limitation de débit et mécanisme de sécurité d’activation automatique

- **Méthode d’écriture prise en charge** : `POST /api/rate-limits` avec le corps `{"connectionId": "<id>", "enabled": true|false}` est l’endpoint de gestion pris en charge pour activer ou désactiver la protection contre les limitations de débit d’une connexion. `PUT /api/providers/[id]` ne modifie ni n’inverse délibérément `rateLimitProtection` (#11278).
- **Sémantique de `enabled: false`** : définir `enabled: false` supprime la protection explicite de la connexion, mais **ne désactive pas** une connexion active avec clé API du mécanisme global de sécurité d’activation automatique (`autoEnableApiKeyProviders = true`). Dans `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` et `undefined` sont équivalents ; les connexions actives avec clé API qui ne disposent pas d’une protection explicite restent protégées par le mécanisme de sécurité d’activation automatique.
- **Désactivation globale** : pour exécuter des connexions avec clé API sans files d’attente de limitation de débit, désactivez globalement le mécanisme de sécurité via `RATE_LIMIT_AUTO_ENABLE=false` (env) ou `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Paramètres → Résilience / `PATCH /api/resilience`).

## Serveur MCP

OmniRoute intègre un serveur Model Context Protocol avec 3 transports (stdio, SSE, streamable-http) et des outils associés à des portées. Les points de terminaison du tableau de bord ci-dessous lisent les données d’état et d’audit, et servent de proxy aux transports HTTP.

| Méthode | Chemin | Description |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |

| GET | `/api/mcp/sse` | Ouvre le flux SSE pour le transport SSE (renvoie `503` si MCP est désactivé ou si le transport ne correspond pas) |
| POST | `/api/mcp/sse` | Envoie une trame JSON-RPC sur le transport SSE |
| GET | `/api/mcp/stream` | Ouvre le côté SSE du transport Streamable HTTP (messages initiés par le serveur) |
| POST | `/api/mcp/stream` | Envoie une trame JSON-RPC sur le transport Streamable HTTP |
| DELETE | `/api/mcp/stream` | Met fin à une session Streamable HTTP |
| GET | `/api/mcp/audit` | Interroge le journal d’audit — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |

## Serveur A2A

OmniRoute expose un point de terminaison JSON-RPC 2.0 A2A (Agent-to-Agent), ainsi qu’une enveloppe REST destinée à l’inspection et au tableau de bord.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # facultatif, sauf si OMNIROUTE_API_KEY est défini
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Méthodes prises en charge (toutes soumises à `settings.a2aEnabled`) :

| Méthode          | Description                                                                  |
| ---------------- | ---------------------------------------------------------------------------- |
| `message/send`   | Exécution synchrone d’une compétence ; renvoie `{task, artifacts, metadata}` |
| `message/stream` | Exécution en streaming SSE du même ensemble de compétences                   |
| `tasks/get`      | Récupère une tâche via `taskId`                                              |
| `tasks/cancel`   | Annule une tâche via `taskId`                                                |

Compétences intégrées : `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Carte de l’agent

```bash
GET /.well-known/agent.json
```

Renvoie la carte publique de l’agent A2A (nom, description, capacités, catalogue des compétences, schéma d’authentification), mise en cache publiquement pendant 1 h. Aucune authentification n’est requise.

### Assistants REST

| Méthode | Chemin                       | Description                                                                                                           |
| ------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| GET     | `/api/a2a/status`            | État d’activation d’A2A + statistiques des tâches + résumé de la carte de l’agent mise en cache                       |
| GET     | `/api/a2a/tasks`             | Liste les tâches — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST    | `/api/a2a/tasks`             | (Non implémenté comme assistant REST — créer via JSON-RPC `message/send`)                                             |
| GET     | `/api/a2a/tasks/[id]`        | Récupère une tâche                                                                                                    |
| POST    | `/api/a2a/tasks/[id]/cancel` | Annule une tâche                                                                                                      |

**Authentification :** les assistants REST fonctionnent sans authentification de gestion (lisibles depuis le tableau de bord) ; la route JSON-RPC `/a2a` utilise le Bearer `OMNIROUTE_API_KEY` s’il est configuré.

## Authentification

Consultez [Authentification de la gestion](../guides/MANAGEMENT-AUTH.md) pour découvrir les quatre familles d’identifiants (session du tableau de bord, jeton CLI local, jeton d’accès `oma_live_…`, clé API dotée de la portée de gestion) et comprendre en quoi elles diffèrent des clés d’inférence.

- Les routes du tableau de bord (`/dashboard/*`) utilisent le cookie `auth_token`
- La connexion utilise le hachage du mot de passe enregistré ; à défaut, `INITIAL_PASSWORD`
- Le paramètre `requireLogin` peut être activé ou désactivé via `/api/settings/require-login`
- Les routes `/v1/*` peuvent exiger une clé API Bearer lorsque `REQUIRE_API_KEY=true`
- Dans cette référence, « jeton de gestion » / « clé API dotée de la portée de gestion » désigne l’une des familles décrites dans ce guide — et non un type de secret supplémentaire non défini

> **Modification majeure (v3.8.0)** — `/api/v1/agents/tasks/*` et les endpoints de gestion du délai de refroidissement exigent désormais une **authentification de gestion** (cookie `auth_token` du tableau de bord ou clé API dotée de la portée de gestion). Les clients qui appelaient auparavant ces routes sans authentification recevront `401 Unauthorized`. Consultez le commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
