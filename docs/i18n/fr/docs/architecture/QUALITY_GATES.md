Ce document constitue la référence faisant autorité pour tous les contrôles qualité de CI d’OmniRoute.
Il décrit chaque contrôle, ce qu’il valide, la tâche de CI dans laquelle il s’exécute, s’il utilise
une base de référence à effet de cliquet ou une politique de réussite/échec, et s’il bloque la compilation ou est consultatif.

Pour un bref résumé et la politique de liste d’autorisation, consultez la section « Quality Gates & Ratchets »
dans `AGENTS.md`. Pour l’évaluation critique, la classification de maturité et le
plan de réplication indépendant des outils du même système, consultez le
[guide des contrôles qualité](../ops/QUALITY_GATE_PLAYBOOK.md).

## Profils d’inventaire et d’exécution des portes

### Admission des candidats

Les workflows CI et Quality Gates émettent chacun un verdict stable : `Gate / CI` et `Gate / Quality`. Leur politique d'admission versionnée énumère chaque emploi en amont comme requis ou consultatif. Une tâche requise applicable doit réussir : les résultats manquants, annulés, ignorés, en attente et inconnus ne peuvent pas établir PASS. Une classification valide de documents uniquement ou de catalogue uniquement peut rendre une voie de code inapplicable ; un projet PR n'est pas un candidat accepté. Une étiquette `hotfix` ne renonce pas aux preuves.

Les deux flux de travail couvrent PRs dans les branches main/release, les push vers `main`, la répartition manuelle et les événements de groupe de fusion. Push, dispatch et merge-group exécutent la sélection complète. Les poussées vers `release/**` ne les démarrent pas (18/10/2026) : chaque modification a déjà exécuté la matrice sur son PR et la combinaison fusionnée est le travail de Release-Green (voie hébergée `docs/ops/RUNNER_BOX.md` → ). Les forks et les groupes de fusion utilisent des exécuteurs hébergés pour les tâches qui autrement sélectionnent des exécuteurs auto-hébergés ; une capacité hébergée suffisante doit être vérifiée avant le déploiement.

Un PR ordinaire exécute la sélection rapide. Les voies `full-code` et `full-code-e2e` de la politique d'admission (E2E, Integration, Package Artefact, Electron Smoke, Bun SQLite, Ecosystem et Protocol Clients) s'exécutent uniquement sur un brouillon de file d'attente Mergify ou sur une exécution complète : `gh workflow run ci.yml --ref <branch>`.

Chaque reçu JSON identifie le SHA extrait, l'exécution et la tentative de flux de travail. Le CLI rejette une inadéquation checkout/event SHA. Les tests de workflow lient l'adhésion à la stratégie à la liste `needs` de la tâche de verdict afin qu'une voie nouvelle ou supprimée ne puisse pas disparaître silencieusement. Les reçus couvrent leur propre flux de travail, et non la publication, le déploiement ou les éléments internes d'un scanner consultatif existant. L'activation des deux noms de contrôle dans les règles de branche est une modification administrative distincte ; l’ajout de ces emplois ne protège pas en soi une succursale.

### Fusionner la file d'attente

L'étiquette `queue` envoie un PR à la file d'attente Mergify (`.mergify.yml`). Mergify ouvre un brouillon PR sur une branche `mergify/merge-queue/`, CI y exécute la sélection complète et le PR original fusionne lorsque `Gate / CI`, `Gate / Quality` et `Merge integrity (changelog + generated skills)` passent.

Mergify écrit son résumé de file d'attente dans la description du brouillon, et d'autres applications peuvent également le modifier. Un événement `pull_request` `edited` sur un tel brouillon prend son propre groupe de concurrence (`-queue-edit-<run_id>`), il ne peut donc pas annuler l'exécution réelle du brouillon et ignore la porte et la matrice. Seul `Merge integrity` fonctionne toujours. Le travail de porte ignoré porte un nom de contrôle différent, car Mergify lit un `Gate / CI` ignoré comme un échec de contrôle et retire le PR.

Après une sortie de file d'attente, un push ne remet pas toujours le PR en file d'attente. Commentez `@mergifyio queue` dessus.

### Preuve conservée dans le réducteur d'acceptation

`scripts/quality/validate-release-acceptance.mjs` réduit un plan fourni et ses manifestes ; il n’établit pas que le plan couvre l’intégralité du pipeline de libération. Ses rapports définissent explicitement `releaseAcceptance: false`, même lorsque ce plan est `VERIFIED`. Le flux de travail `release-acceptance.yml` utilise toujours des appareils fantômes, et non de véritables reçus de construction, de package, de démarrage ou de promotion.

Le CLI exige que `--evidence-root` vérifie les preuves conservées. Les fichiers sont résolus en tant que `<evidence-root>/<artifact_id>/<member>` et hachés en tant que SHA-256. Un enregistrement PASS sans preuve, un fichier manquant ou modifié, un chemin dangereux ou un lien symbolique empêche la vérification. Les fichiers manquants ne sont pas équivalents à des journaux de réussite vides. Les contrôles SHA/run/attempt existants restent indépendants : les octets correspondants ne peuvent pas récupérer un reçu périmé. L'intégrité des fichiers ne constitue pas une preuve de l'authenticité de l'exécution ou de la promotion d'un artefact.

### Inventaire d'analyse statique

L'inventaire npm-alias versionné et l'adhésion à l'analyse statique se trouvent dans `config/quality/gate-manifest.json`. Exécutez `npm run check:gate-manifest` pour valider les noms de script et les commandes exactes par rapport à `package.json`; les ajouts, les suppressions et la dérive des commandes échouent à la fois au hook local et aux tâches de classification des changements dans CI. Un alias n'est pas une tâche de workflow, une instance matricielle ou un scénario de test : ces décomptes ne doivent pas être présentés comme interchangeables.

Utilisez `npm run quality:scan -- --list` ou `npm run quality:scan:fast -- --list` pour inspecter les alias sélectionnés sans les exécuter. Le coureur invoque le point d'entrée npm, de sorte que son environnement d'exécution (y compris Bun lorsqu'il est configuré) est préservé. Le manifeste enregistre les alias en dehors de ces profils comme invoqués séparément, et les commandes de maintenance sont interdites dans les profils d'analyse en lecture seule.

Ces profils couvrent uniquement l'analyse statique. Ils ne certifient pas les tests de produits, la couverture, l'emballage, les contrôles externes ou l'acceptation complète d'un candidat. L'admission au workflow utilise les `config/quality/admission-policy.json` et `scripts/quality/admission-verdict.mjs` liés. Les profils d’observateurs de libération restent distincts ; inspecter leurs chèques et reçus applicables de manière indépendante. Les commandes statiques de l'observateur complet sont déclarées dans `config/quality/release-green-static-profile.json`, y compris `audit:deps`, la sélection des tests de mutation et les contrôles de traduction. Le chargeur valide les commandes npm par rapport aux déclarations package.json et CI/Quality modélisées ; il rejette la dérive au lieu d'exécuter des jetons shell comme arguments. La sortie SKIP/INCOMPLETE requise du scanner ne peut pas établir PASS. Le profil enregistre ses exclusions externes et ne remplace pas la couverture hébergée, les matrices de test, les packages ou les preuves de déploiement. L'inventaire en prose ci-dessous est une référence et non une preuve qu'une porte a réellement fonctionné.

Les scripts vivent sous `scripts/check/` (portes de politique) et `scripts/quality/` (moteur à cliquet). La source de vérité CI est `.github/workflows/ci.yml`.

### Libérer le chemin rapide PR (`quality.yml`)

`.github/workflows/quality.yml` complète CI sur main/release PRs, pousse vers `main`, répartit et fusionne les groupes. PRs utilise des vérifications rapides filtrées par chemin. La version en double désactivée de façon permanente a été supprimée ; les vrais contrôles build/package/boot restent dans CI. La suite unitaire et vitest fonctionnent uniquement en CI (`Unit Tests (N/8)` et `Vitest`).

#### Rapport de tests de frères et sœurs oubliés

`npm run check:forgotten-sibling-tests` s'exécute comme une étape consultative de `Fast Quality Gates` et réutilise le résolveur d'importation derrière la carte test-impact. Pour chaque module de production modifié, il signale les chaînes `changed module/symbol -> static consumer -> candidate sibling test` déterministes lorsque le test candidat est absent du diff pull-request. Le résumé Markdown et le résultat JSON sont conservés en tant qu'artefact de flux de travail `forgotten-sibling-tests` pour l'étalonnage avant tout déploiement de blocage.

Les réexportations de barils et les importations dynamiques sont uniquement des diagnostics de résolution ; ils ne créent jamais de constatation bloquante. Les exceptions examinées sont disponibles dans `config/quality/forgotten-sibling-allowlist.json`. Chaque entrée doit nommer le test consommateur et candidat, donner une justification spécifique et lier un problème GitHub ou une pull request. Les entrées mal formées ne sont pas fermées. Les exceptions ne peuvent pas supprimer un test candidat supprimé ou un diff qui ajoute `.skip`/`.todo`; l'affaiblissement des assertions et autres masquages restent la propriété de la porte `check:test-masking` bloquant indépendamment.

#### Deux programmes de vérification de type répondent différemment

`typecheck:core` et `check:build-typecheck` compilent différents programmes sous différentes options, et le même fichier peut être propre dans l'un et plein d'erreurs dans l'autre.

`tsconfig.build.json` définit `"strict": false`, donc `noImplicitAny` est désactivé. La configuration principale compile une liste autorisée de 27 fichiers avec des options plus strictes et suit le graphique d'importation de chaque entrée, de sorte que les fichiers qui n'apparaissent jamais dans le programme de construction y sont toujours vérifiés.

La conséquence est importante pour juger si un fichier est typé :** zéro diagnostic sous `check:build-typecheck` ne signifie pas zéro** . La suppression de `@ts-nocheck` de 26 fichiers a montré que 23 d'entre eux étaient propres dans le programme de construction ; seize d’entre elles ont fait apparaître environ 120 erreurs implicites au sens strict. Vérifiez les deux avant d’appeler un fichier propre.

#### Les miroirs de traduction sont des fichiers dérivés (mode PR vs mode release)

Une fonctionnalité PR édite uniquement les sources anglaises. Les miroirs `docs/i18n/<locale>/**` (comprenant les 66 copies `llm.txt` et les fichiers `CHANGELOG.md` traduits) et `.i18n-state.json` sont réécrits en une seule étape par la vague de traduction (branches `docs/i18n-*` / `chore/i18n-*`, les `i18n-mirror-refresh.yml` programmés) et par la release (`npm run release:sync-changelog-i18n`). Les portes miroir fonctionnent donc selon deux modes, résolus par `scripts/check/lib/gateMode.mjs` (`--mode=pr|release`, puis `OMNIROUTE_GATE_MODE`, puis l'événement Actions ; une exécution locale est `release`) :

- Le mode de publication `check:docs-sync` — exécute chaque vérification. Le mode PR conserve la version package.json/OpenAPI, les en-têtes racine CHANGELOG et la garde des documents remplacés, et imprime `SKIP reason=pr-mode` pour les copies miroir `llm.txt` et les sections CHANGELOG traduites — à moins que le PR n'écrive des miroirs : une branche principale déclarée comme écrivain de la famille `docs/i18n/**` dans `config/quality/derived-paths/*.json` exécute les deux vérifications strictement, et, lorsque la base de diff est résolue, un changement dont le propre diff édite `docs/i18n/<locale>/llm.txt` ou `CHANGELOG.md` exécute cette vérification strictement. La base diff ne se résout pas dans une extraction depth-1 (le travail `docs-sync-strict` ), donc le mode PR exécute également une vérification qui ne nécessite aucune base : chaque miroir `llm.txt` doit exister, conserver son séparateur `---` et porter soit le corps racine, soit le corps que la plupart des miroirs partagent. Une base qui a bougé laisse tous les miroirs également obsolètes et passe ; une modification manuelle sur un miroir échoue. Les fichiers `CHANGELOG.md` traduits n'ont pas de vérification de ce type lors d'une extraction depth-1 PR.
- Le hook de pré-commit exécute `check-docs-sync.mjs --mode=pr`: un commit est jugé sur ce qu'il fait. Sans l'indicateur, une exécution locale est en mode release, et un PR fusionné qui modifie le `llm.txt` racine bloquerait chaque validation ultérieure sur cette base jusqu'à l'exécution de la vague. La même règle s'applique à toute porte sensible au mode qu'un hook Husky exécute : le hook passe `--mode=pr`, et le verdict strict reste avec les exécutions en mode release (la version PR, pousse vers `main`, une exécution locale simple).
- Tests unitaires de contenu miroir (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`, `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`, `docs/*-locales`) Le mode de publication — affirme chaque paramètre régional. Le mode PR affirme uniquement les miroirs qui sont à jour avec la source anglaise selon `.i18n-state.json` (hachage de fichier entier ou hachage de section enregistré de la section des broches de test) et ignore ceux qui sont périmés avec une raison. Les vérifications de provenance `target_hash` s'exécutent pour chaque paramètre régional dans les deux modes. La fraîcheur est par section `## `, l'unité de hachage `run-translation.mjs` ; une longue section (l'inventaire de porte de ce fichier représente environ la moitié de celui-ci) signifie que toute modification qu'il contient laisse ces miroirs obsolètes, et leurs assertions en mode PR passent jusqu'à la vague suivante. Une ancre que la source anglaise ne contient plus revient à la comparaison de l'ensemble du fichier.
- `i18n translation drift` — consultatif sur PRs, strict sur push, tous les soirs et la version coupée, donc un miroir périmé ne peut pas être expédié dans une version.

`scripts/i18n/sync-llm-mirrors.mjs` (également exporté sous `syncLlmMirrors()`, avec `--dry-run`) réécrit les miroirs `llm.txt` ; l'actualisation de la version, la vague de traduction et le `i18n-mirror-refresh.yml` planifié l'exécutent (l'actualisation détecte les miroirs `llm.txt` obsolètes avec un essai à sec, car le rapport de dérive ne les répertorie pas et les synchronise avant `check:docs-all`).

Les douze README SVGs sous `docs/diagrams/` sont générés (`scripts/docs/gen-readme-<name>.mjs`; `npm run docs:readme-diagrams` les régénère tous). Chacun a un test unitaire de comparaison d'octets (`tests/unit/docs/readme-*-svg.test.ts`, job `test-unit`) qui échoue lorsque le fichier validé est obsolète en mode version ; dans un PR, `check:generated-artifacts` juge un SVG, le PR modifie et la dérive de la base est laissée à l'actualisation de la version (voir [Fichiers générés et lignes de base dérivées](#generated-files-and-derived-baselines-written-at-release) ) — et `check:docs-counts` lisent les nombres canoniques à partir de leurs nœuds `<text>` — c'est pourquoi l'étape de description conserve chaque chaîne décrite dans le fichier comme invisible `<text>`. La vérification des nombres canoniques SVG lit les fichiers répertoriés dans `SVG_DIAGRAM_FILES` (`scripts/check/check-docs-counts-sync.mjs`) : `docs/diagrams/readme-hero.svg`, `free-tier-budget.svg`, `promise-pillars.svg`, `comparison-table.svg`, `cli-terminal.svg`, `tier-cascade.svg`, plus `public/images/tier-flow-dark.svg` et `tier-flow-light.svg`; les revendications de gratuité pour toujours, d'entrée dans le catalogue, de pool récurrent et de facteurs de notation se lisent également `promise-pillars.svg`, `free-tier-budget.svg` et `strategies-grid.svg`. Les décomptes que ces générateurs tirent (total du fournisseur, outils MCP, stratégies de routage, fournisseurs gratuits pour toujours, …) proviennent de l'instantané des faits `docs/reference/derived-facts.json` à `scripts/docs/readmeFacts.mjs`, et non de littéraux, donc la régénération d'un diagramme sur n'importe quelle branche reproduit le fichier validé. `free-tier-budget.svg` tire ses lignes du même instantané (`code.freeTierBudget`, le résumé du catalogue des enregistrements de la sonde de faits), donc une modification apportée à `FREE_MODEL_BUDGETS` atteint la carte lors de la prochaine actualisation au lieu de rendre CI rouge.

### Valeurs dérivées : les modes de porte `pr` et `release`

Une fonctionnalité PR n'écrit jamais une valeur qui dépend de l'état de sa base : fournisseurs, migrations, outils MCP et stratégies, nombres README SVG, instantané des faits. Une étape les recalcule tous, `npm run release:refresh-derived`, exécutés par la version et par l'actualisation dérivée nocturne PR. Donc** entre les versions, la base est derrière le code live de par sa conception** , et une porte ou un test comparant l'arborescence avec le code en direct serait rouge sur chaque PR après qu'un frère ou une sœur ait ajouté un fournisseur. Les portes qui jugent les valeurs dérivées fonctionnent donc dans l'un des deux modes, résolus par `scripts/check/lib/gateMode.mjs` (le premier match gagne) :

1. `--mode=pr|release` sur la ligne de commande ;
2. la variable d'environnement `OMNIROUTE_GATE_MODE` (`pr` ou `release`) ;
3. automatique, depuis l'événement GitHub Actions : un `pull_request` dont la tête n'est pas `release/v*`, un `merge_group`, ou un push vers `omni-queue/**` → `pr`; tout le reste (push, planification, répartition, la version PR `release/v* → main`, toute exécution locale) → `release`.

Qu'est-ce que `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) échoue dans chaque mode :

| Mode      | Échec                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | A besoin des faits en direct |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| `release` | A chaque contrôle, égalité stricte avec les faits collectés à partir de l'arbre (le comportement que le portail a toujours eu) : un décompte, une version, un plancher de couverture ou un numéro SVG est une dérive STRICT                                                                                                                                                                                                                                                                                      | Oui                          |
| `pr`      | Seul ce que le changement a fait, comparé à la base PR avec les mêmes extracteurs de réclamations : (1) une valeur gérée qui n'existait pas dans la base pour cette vérification et ce fichier ("PR a modifié un numéro géré — a restauré la ligne dans le texte de base "); (2) une réclamation requise pour la base transportée et la tête perdue. Les invariants de contenu qui ne nécessitent aucun fait s'exécutent comme en mode version ; les contrôles de version uniquement sont répertoriés et ignorés | Non                          |

Les fichiers d'instructions de l'agent portent** Non** nombre dérivé : `AGENTS.md`, `llm.txt` (et ses copies `docs/i18n/*/llm.txt` ), le fork bs `AGENTS.md`, `open-sse/services/AGENTS.md`, `src/shared/constants/agentSkills.ts`, `skills/README.md` et chaque `skills/*/SKILL.md` pointent vers la source (par exemple `ROUTING_STRATEGY_VALUES` dans `src/shared/constants/routingStrategies.ts`) et vers `npm run facts` à la place. L'invariant "Aucun décompte dérivé (fichier d'instructions d'agent …)" échoue dans un décompte (fournisseurs, migrations, outils et étendues MCP, stratégies de routage, facteurs de notation, packs de modes) dans les deux modes, de sorte que l'actualisation de la version n'a jamais besoin de réécrire un fichier d'instructions.

En mode `pr` les branches d'écriture peuvent modifier les valeurs gérées : `chore/derived-*` (l'actualisation nocturne PR), `release/v*` et les ondes de traduction `docs/i18n-*` et `chore/i18n-*` (`scripts/check/lib/derivedClaimsDiff.mjs`). Les lots de file d'attente (`merge_group`, Mergify drafts, `omni-queue/**`) ne sont pas jugés à nouveau : ils additionnent PRs la porte déjà jugée une par une.

Codes de sortie : `0` clean · `1` STRICT drift (ou soft drift avec `--strict`) ou violation de la valeur gérée · `2` infrastructure — les faits du code n'ont pas pu être collectés (la sonde tsx a échoué ou a expiré ; le délai d'attente est `OMNIROUTE_FACTS_TIMEOUT_MS`, par défaut 600 000 ms) ou, dans CI, la base de diff PR n'a pas pu être résolue. Une sortie 2 n'est jamais une divergence de documentation : réexécutez le travail ou corrigez l'environnement.

Où chaque mode s'exécute :

| Où                                                                                                                                | Mode                                                                                                                                                                                                                              |
| --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fonctionnalité PR — `ci.yml` job `docs-sync-strict`, étape `quality.yml` "Précision des documents"                                | `pr` (automatique); le travail passe la base en tant que `BASE_SHA` et est vérifié avec `fetch-depth: 2`                                                                                                                          |
| `merge_group`, candidats `omni-queue/**`, liste complète des portes du train de fusion                                            | `pr`                                                                                                                                                                                                                              |
| Libération PR (`release/v* → main`), push, exécutions planifiées et manuelles                                                     | `release`                                                                                                                                                                                                                         |
| Release-Green (`scripts/quality/validate-release-green.mjs`)                                                                      | les éléments HARD fonctionnent avec `OMNIROUTE_GATE_MODE=pr` (« la base est-elle cassée ? ») ; l'élément DRIFT `derived-refresh` exécute `npm run release:refresh-derived -- --check` (vue stricte, n'ouvre jamais de base-rouge) |
| Version (`/generate-release` phases 0a et 1 ; le câblage des compétences est un changement distinct approuvé par le propriétaire) | `npm run release:refresh-derived` écrit les fichiers dérivés ; les propres vérifications de la version PR sont ensuite exécutées en mode `release`                                                                                |
| `nightly-derived-refresh.yml` (quotidien, `release/vX.Y.Z` le plus élevé, ignoré sous libération-gel)                             | `npm run release:refresh-derived -- --profile=nightly`; sur un diff, il garde ONE PR ouvert depuis `chore/derived-refresh`; ne fusionne jamais                                                                                    |

Les commandes derrière:

- `npm run facts` imprime chaque nombre dérivé sous la forme JSON (`scripts/release/facts.mjs`). `--key=code.mcpTools` imprime une valeur, `--snapshot` lit l'instantané validé au lieu de l'arborescence active. Sortie 2 lorsque les faits ne peuvent pas être collectés.
- `npm run release:refresh-derived` (`scripts/release/refresh-derived.mjs`) recalcule les fichiers dérivés en une seule passe, dans cet ordre (identifiants d'étape pour `--only=`) : `provider-reference` (`docs/reference/PROVIDER_REFERENCE.md`), `facts` (l'instantané), `numbers` (le plan de réécriture de la porte des comptes appliqué aux documents, puis transféré à leurs miroirs `docs/i18n/` ), `readme-diagrams`, `skills` ( `SKILL.md` généré), `e2e-timings` (ignoré jusqu'à l'arborescence livré `syncE2eTimings`), `ui-keys` (élague les clés `en.json` abandonnées et, avec `--rewritten-since=<ref>` — par défaut `origin/main` — remet en file d'attente les valeurs anglaises réécrites depuis la dernière version ; les valeurs sont traduites dans la même exécution par le backend configuré dans l'environnement ou dans `.env` (`OMNIROUTE_TRANSLATION_*`, seules ces clés sont lues) ou par le moteur Google. Sans backend, il n'écrit jamais de marqueurs `__MISSING__` : le profil de version échoue, le nightly saute les clés, et `--allow-untranslated` les écrit exprès), `llm-mirrors` et `verify-generated` (après une écriture, `check:generated-artifacts` et `check:agent-skills-sync` en mode release doivent passer ; ignorés dans `--check` et quand `--only` le laisse de côté ; un échec est la sortie 2). L'étape `changelog` est opt-in (`--with-changelog`, profil de version uniquement). `--profile=nightly` ne touche jamais à une revendication de version. Avec `-- --check` il n'écrit rien et quitte 1 lorsqu'un fichier est susceptible de changer ou qu'une valeur gérée nécessite une modification manuelle (en répertoriant les deux) ; sortie 2 sur une panne d'infrastructure. `--json` imprime le résultat sous la forme JSON.
- `docs/reference/derived-facts.json` est l'instantané des faits utilisés lors de la dernière actualisation. Seul le rafraîchissement l'écrit. Les générateurs README SVG le lisent et les tests unitaires au moment des relations publiques comparent les documents validés et les fichiers générés avec — jamais avec le code live. La seule comparaison en direct de la suite est "l'actualisation de la version ferme le cycle" dans `tests/unit/check-docs-counts-sync.test.ts`: avec les faits en direct, le plan de réécriture de l'actualisation appliqué en mémoire ne laisse aucune dérive STRICT qu'il ne signale pas, et la replanification ne change rien.

#### `check-ui-value-drift` — porte de traduction périmée

Détecte la régression i18n que les autres portes ne peuvent structurellement pas voir : une valeur anglaise est réécrite et les traductions dérivées de l'anglais _précédent_ restent en arrière, de sorte que les utilisateurs non anglais continuent de lire une copie rédigée avec confiance et désormais erronée.

Ceci a été expédié pour de vrai. `oauthModal.googleOAuthWarning` a été réécrit lorsque l'assistant de connexion Antigravity a atterri (#5203);** 39 sur 43 localités** conservé le texte indiquant aux opérateurs de "copier le URL complet et de le coller ci-dessous" — un flux qui ne peut pas être terminé pour ce fournisseur. C'est passé inaperçu jusqu'à #8463 car :

- `sync-ui-keys` ne remplit que les clés qui sont** absent** , jamais ceux qui sont** vicié** ;
- `check-ui-keys-coverage` compte la _présence_ de clé, donc une traduction obsolète est considérée comme couverte ;
- `check-translation-drift` suit la documentation `docs/i18n/<locale>/**.md` et reflète — il ne lit jamais `src/i18n/messages/*.json`. Il s'exécute dans le job `docs-sync-strict`: consultatif sur PRs, strict sur push et nocturne ; l'onde de traduction rafraîchit les miroirs, pas la fonctionnalité PR.

**Prise en compte des différences, non basée sur une ligne de base.** Il compare `en.json` à la base de fusion avec l'arbre de travail ; pour chaque clé dont la valeur anglaise a changé, toute langue contenant encore une traduction intacte est obsolète. Ceci délibérément** gèle la dette préexistante** — a diff ne peut pas révéler de quel vieil anglais provient une traduction de longue date, donc la porte juge uniquement ce que touche le changement actuel. L'alternative (une ligne de base de hachage par clé) coûterait un fichier généré ~ 600 KB, 3 × la plus grande ligne de base existante, tournant sur chaque i18n PR.

Deux façons de le satisfaire :

1. mettre à jour les traductions concernées, ou
2. définissez-les sur `__MISSING__:<new english>` — le moteur d'exécution sert ensuite l'anglais corrigé (`src/i18n/request.ts::deepMergeFallback`, #7258) et les files d'attente de clés pour la traduction.

Si la chaîne est** signification** changé, préfère** renommer la clé** : une nouvelle clé ne peut pas hériter d'une traduction obsolète. C'est le modèle utilisé par #8463.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

Quitte 0 avec `SKIP reason=base-unresolved` lorsque le catalogue de base ne peut pas être lu (clone superficiel sans la référence de base), en miroir `check-openapi-breaking`. Mode release uniquement : une fonctionnalité PR réécrit l'anglais et s'arrête là ; l'actualisation de la version marque les traductions qu'elle a laissées (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, même `findStaleTranslations`).

## Phase de vitesse (2026-08-30 → v4.0 LTS) : chaque ligne de base relâchée de 20 %

Décision du propriétaire (30/08/2026) : jusqu'à la modularisation v4.0, la vitesse d'expédition compte plus que le maintien de la ligne de dette. Chaque** numérique** La ligne de base du cliquet a été relâchée de 20 % en une seule passe auditable, et la phase est déclarée en `config/quality/quality-baseline.json`:

```json
"_policy": { "phase": "velocity", "since": "2026-08-30", "until": "4.0.0",
             "relaxPct": 20, "requireTighten": false }
```

| Ce qui a changé                                                                                                                                                                                                                               | Où                                                                                                     |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `metrics.*.value` — le plus bas est le meilleur compte × 1.2, le plus élevé est le meilleur pourcentage ÷ 1.2 (le plancher de couverture 60 est conservé, `eslintErrors` reste 0, `eslintWarnings` 0 → 20 % du nombre de suppressions gelées) | `quality-baseline.json` (la note `_relax_velocity_2026_08_30` répertorie chaque avant → après)         |

| `cap`, `testCap`, chaque plafond de ligne `frozen[*]` / `testFrozen[*]` × 1.2                                                                                                                                                                 | `file-size-baseline.json`                                                                              |
| par fichier / par code TS compte × 1.2                                                                                                                                                                                                        | `api-typecheck-baseline.json`, `dashboard-typecheck-baseline.json`, `open-sse-typecheck-baseline.json` |
| `THRESHOLD` 36 → 30                                                                                                                                                                                                                           | `scripts/check/check-openapi-coverage.mjs`                                                             |

| `bank-ratchet-shrinks` fait une pause tous les soirs (cela mettrait en banque le rétrécissement mesuré et annulerait la marge)                                                                                                                | `.github/workflows/nightly-release-green.yml`                                                          |

Les listes autorisées (`eslint-suppressions.json`, `test-masking-allowlist.json`, `test-discovery-baseline.json`, …) sont** pas** budgets et n’ont pas été touchés. Les portes de politique Pass/fail (secrets, règles SQL, contrat docs/env, parité i18n, tests unitaires) sont inchangées — un test rouge est toujours un test rouge.

**Outillage**

- `npm run quality:relax-baselines -- --pct 20 --note velocity_YYYY_MM_DD [--dry-run]` — la relaxation one-shot (`scripts/quality/relax-baselines.mjs`) ; refuse de courir deux fois avec la même note.
- `npm run quality:headroom [-- --only deadExports,fileSize] [--json out.json --md out.md]` — mesure chaque porte numérique comme le fait CI et imprime la marge restante par porte (`scripts/quality/baseline-headroom.mjs`). La tâche `baseline-headroom` nocturne publie le tableau dans le résumé de l'exécution du flux de travail et télécharge son rapport JSON/Markdown sous le nom `baseline-headroom-<run_id>`, conservé pendant 90 jours. Les lignes d'avertissement et de critique identifient les portes à moins de 10 % de leur plafond ou déjà au-dessus de celui-ci. Examinez ces rapports comme alerte précoce pour les budgets consommés ; inspectez les notes `_rebaseline_*` de la porte incriminée. Le travail ne crée ou ne met plus à jour un problème permanent ; #12149 préserve l'historique du rapport précédent.

**Mode nouveau code (Clean-as-You-Code) — depuis le 30/08/2026, chemin rapide PR uniquement**

Lors des événements `pull_request` `quality.yml` transmet `--base-ref <PR base SHA>` à `check:file-size`, `check:complexity-ratchets` et `check:dead-code`. Pour `check:complexity-ratchets` et `check:dead-code` la porte compare HEAD avec la base de fusion** limité aux fichiers touchés par PR** (`scripts/check/newCodeMode.mjs`: la base de fusion est matérialisée dans un `git worktree` jetable, ESLint/knip s'exécute là-bas et sur HEAD, les décomptes par fichier sont différents) :

- **blocage** — le PR a ajouté des violations cyclomatic/cognitive ou des exportations mortes dans les fichiers qu'il a modifiés (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` dans le journal) ;
- **consultatif** — le total mondial par rapport à la référence gelée. La dérive héritée ne rend jamais un PR innocent ; la dérive est recongelée lors du rapprochement des versions et surveillée par le travail de marge.

`check:file-size` utilise la référence de base selon ses propres termes (`scripts/check/check-file-size.mjs`, #8522) : il vérifie chaque fichier source et test de l'arborescence, lit le nombre de lignes de chacun à la base PR avec `git show` et échoue un fichier uniquement lorsqu'il dépasse la plus grande de son plafond de base (`frozen` / `testFrozen` ou `cap` / `testCap` pour un fichier en dehors de la ligne de base) et de sa taille de base. Un dossier qui a déjà dérivé sur la base ne rend donc jamais un PR innocent.

`check:boundary:ratchet` applique la même règle à son numéro unique (`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`) : lors des événements PR, les fast-gates `quality.yml` et le travail `ci.yml` lint transmettent la base PR SHA, la validation de base est mesurée à partir d'une exportation `git archive`, et le PR échoue uniquement lorsque son nombre de bords `open-sse → src` dépasse le plus grand de `metrics.boundaryOpenSseToSrc` et le nombre sur la base. La dérive de la base au-dessus du plafond est signalée (`base drift herdado`) mais n'indique jamais un PR innocent ; push → main maintient le plafond absolu, et une base insoluble SHA y revient avec un avertissement.

Un candidat omni-file d'attente (un push vers `omni-queue/**`, voir [OMNI_QUEUE.md](../ops/OMNI_QUEUE.md) ) reçoit le même traitement qu'une pull request : les deux flux de travail transmettent la base de candidats (`needs.changes.outputs.candidateBase`) en tant que `--base-ref`, et `check:ts7-diagnostics-ratchet` s'exécute également contre elle. Pour les deux portes de nouveau code, la base de comparaison est ce SHA lui-même, et non le premier parent du commit de fusion supérieur, donc chaque demande d'extraction du lot est jugée.

`workflow_dispatch` s'exécute, le balayage release-green et le travail de marge nocturne n'ont pas de base PR et conservent la comparaison absolue (globale). La couverture, la duplication et la couverture de type restent globales pour l'instant (leurs outils ne produisent pas de différence par fichier à moindre coût) — candidats pour le même traitement.

**Clôture de la phase à la v4.0 (LTS = plus serré qu'avant, pas "retour à la normale")**

1. Sur le conseil pur `release/v4.0.0` : `npm run quality:headroom --json` pour mémoire, puis `npm run quality:ratchet -- --update`, `check:file-size --update`, `check:complexity-ratchets --update`, `check:dead-code --update`, `--update` — de chaque porte de vérification de type, chaque ligne de base tombe à la valeur mesurée.
2. Supprimez `_policy` de `quality-baseline.json` (réarme `--require-tighten` et les opérations bancaires nocturnes), restaurez `THRESHOLD = 36` (ou supérieur) dans `check-openapi-coverage.mjs`.
3. Resserrez au-delà de toute mesure là où la modularisation a porté ses fruits : taille de fichier `cap` revenue à 1000 (ou 800), niveaux de couverture + 5, exportations mortes 0 pour les packages modularisés.

### Ratchet CodeQL : cadence de rafraîchissement et déclenchement manuel

`check:codeql-ratchet` lit** état du dépôt, actualisé selon un calendrier — et non par PR.** `gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` rapporte `state: configured`, `schedule: weekly`: l'analyse de configuration par défaut de GitHub, pas une analyse par poussée. Conséquence : après la fusion d'un PR that FIXES alerts, le cliquet continue de lire l'ancien compte plus élevé jusqu'à ce que la prochaine analyse planifiée exécute — il signale donc une régression sur chaque PR ouvert, y compris les propres suivis du correctif PR, jusqu'à ce que l'analyse rattrape son retard.

**Actualisation manuelle** : `gh workflow run codeql.yml --ref release/vX.Y.Z` réexécute l'analyse et republie les alertes en quelques minutes. Lisez d'abord `.github/workflows/codeql.yml` — son en-tête explique qu'il s'agit `workflow_dispatch` -only** car il est en conflit avec la "configuration par défaut" de GitHub** (`CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled`). La restauration des déclencheurs `push`/`pull_request`/ `schedule` nécessite un** action du propriétaire en premier** : Paramètres → Sécurité du code → CodeQL: Par défaut → Advanced. N'ajoutez pas de déclencheur `schedule:` sans ce commutateur — cela ne produira que des exécutions défaillantes.

**Resserrez la ligne de base après que le décompte ait diminué** — `node scripts/check/check-codeql-ratchet.mjs --update` écrit le nouveau décompte mesuré dans `quality-baseline.json` → `metrics.codeqlAlerts.value`, de sorte que le cliquet ne permet pas silencieusement une régression jusqu'à l'ancien plafond. Exemple fonctionnel (2026-09-02/03) : PR #12502 a corrigé 7 alertes réelles (13 → 6 mesurées ouvertes) ; PR #12530 a resserré la ligne de base gelée 11 → 6 pour correspondre ; les 6 restants ont ensuite été rejetés avec une justification par alerte jusqu'à 0 ouvert.

**Les licenciements sont à la discrétion de l'opérateur (Hard Rule #14)** — ne rejette jamais une alerte CodeQL sans enregistrer la justification technique dans le commentaire de rejet : `won't fix` pour une exigence de protocole en amont, `used in tests` pour un appareil de test, `false positive` pour un désinfectant CodeQL ne peut pas voir (précédent : `docs/security/ERROR_SANITIZATION.md`).

## Politique de nouvelle tentative des tests (WS5.4, v3.8.49)

Les nouvelles tentatives sont configurées par runner, jamais globalement — une nouvelle tentative globale transforme de véritables régressions
en instabilités invisibles :

| Runner           | Politique                                                                                                                                                             | Pourquoi                                                                                                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Playwright (e2e) | `retries: 1` uniquement dans la CI, avec `trace: on-first-retry`                                                                                                      | La temporisation du navigateur/réseau est réellement non déterministe ; une nouvelle tentative avec une trace transforme une instabilité en artefact exploitable pour le diagnostic |
| Vitest           | AUCUNE nouvelle tentative globale. Un test dont l'instabilité est avérée reçoit une nouvelle tentative explicite par test (visible dans le diff, examinée dans la PR) | Conserve la liste de quarantaine dans le dépôt, sans jamais la rendre opaque                                                                                                        |
| node:test (unit) | AUCUNE nouvelle tentative, sans exception                                                                                                                             | Un test unitaire instable est un bug dans le test — corrigez-le, ne le relancez pas au hasard                                                                                       |

SLO cibles une fois la télémétrie des instabilités disponible (WS5.2/5.3) : taux d'instabilité <1 % par test
(seuil « corriger maintenant »), taux de réussite ≥95 % par pipeline. Valeurs de référence du secteur —
à recalibrer d'après nos propres mesures.

## Dérive des cliquets au niveau de la release (WS5.5, v3.8.49)

Lorsqu'un cliquet (taille de fichier, complexité, avertissements eslint) régresse sur la pointe PURE de la release
— c'est-à-dire que la COMBINAISON des fusions l'a fait régresser et qu'aucune PR prise isolément ne reproduit
la régression sur sa propre branche — la correction incombe au **responsable de la release, une seule fois, sur la
branche de release** : privilégiez l'extraction ou le refactoring ; ne redéfinissez la référence qu'avec l'entrée
de justification documentée. Ne reportez jamais une dérive combinée sur la PR d'un contributeur et ne
redéfinissez jamais la référence pour chaque PR (cela masque les véritables régressions). Commencez par faire
la distinction : reproduisez l'échec sur la pointe pure dans un worktree d'investigation avant de supposer que votre PR l'a causé.

## Fichiers générés et lignes de base dérivées (écrites lors de la sortie)

Plan 2026-11-13 ("numéros et textes dérivés résolus uniquement à la sortie") : une fonctionnalité PR modifie le** source** — `src/shared/constants/providers.ts`, `docs/openapi.yaml`, le catalogue de compétences, le catalogue gratuit, une nouvelle spécification e2e. Il ne régénère pas les fichiers calculés à partir de cette source et n’intègre pas une amélioration mesurée dans une référence. Ces fichiers sont réécrits une fois, par l'actualisation de la version (`release:refresh-derived`) ou par une actualisation nocturne PR. Avant cela, chaque frère PR portait sa propre copie régénérée et était en conflit avec la fusion suivante (2026-11-13 : 30 sur 321 PRs ouverts ont réécrit `PROVIDER_REFERENCE.md`, 26-28 ont réécrit les diagrammes README ).

**Le garde.** `check:pr-derived-paths` (job `pr-test-policy`) échoue à une fonctionnalité PR qui touche un fichier d'une famille dans `config/quality/derived-paths/`:

| Famille     | Fichiers                                                                                                                                                                                         | Réécrit par                                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `generated` | `docs/reference/derived-facts.json`; `docs/reference/PROVIDER_REFERENCE.md`; les douze générés README SVGs; `skills/*/references/**`; les fichiers `SKILL.md` qui n'ont pas de bloc personnalisé | `release:refresh-derived` (faits), `gen:provider-reference`, `docs:readme-diagrams`, `generate-agent-skills.mjs --apply` |
| `baselines` | `config/quality/e2e-timings.json`                                                                                                                                                                | `balance-e2e-shards.mjs --sync` (`syncE2eTimings()`)                                                                     |

Les rédacteurs (`release/v*`, `chore/derived-*` et `chore/bank-ratchet-*` pour les lignes de base) sont exemptés ; il en va de même pour un PR qui ne change qu'une seule famille plus ses compagnons (pour `generated`: les scripts du générateur, leurs tests, les entrées de compétences d'agent — `src/shared/constants/agentSkills.ts`, les documents `skills/**` écrits à la main, `docs/openapi.yaml` — et `changelog.d/**`), par exemple un changement de disposition de héros avec son SVG régénéré, ou un correctif de compétences dont le test lit les fichiers `SKILL.md` régénérés. Un `SKILL.md` avec un bloc `<!-- skill:custom-start -->` manuscrit ne fait pas partie de la famille : son bloc personnalisé reste modifiable à côté d'une fonctionnalité.

Le nettoyage des orphelins n'est pas non plus jugé par les familles : un PR peut supprimer `docs/i18n/<locale>/<doc>` lorsque la base de fusion avait ce miroir et `<doc>` n'existe plus dans la tête du PR, et peut modifier `.i18n-state.json` uniquement pour supprimer ces documents de `sources`. Le garde répertorie ces fichiers sous `orphan-cleanup`. La suppression du miroir d'un document qui existe toujours reste une violation : aucun autre pipeline ne suit cet état, et les miroirs `llm.txt` et `CHANGELOG.md` ont leurs propres rédacteurs.

**Les contrôles, par mode portail** (`scripts/check/lib/gateMode.mjs`; assistant `scripts/check/lib/derivedArtifactScope.mjs`):

| Vérifier                                                                                   | `release` (push, planning, release PR, local)                                      | `pr` (fonctionnalité PR, lot de file d'attente)                                                                                                                                                                                                            |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check:agent-skills-sync`                                                                  | chaque compétence doit être égale à la sortie du générateur                        | uniquement les compétences dont le texte généré (en dehors du bloc personnalisé) ou `references/` le PR édite ; sinon `SKIP reason=pr-mode`                                                                                                                |
| `check:generated-artifacts` (horaires README SVGs + e2e ; nécessite un historique complet) | chaque SVG est égal à son générateur ; chaque spécification a une entrée de timing | uniquement les artefacts modifiés par PR ; le reste `SKIP reason=pr-mode`; pas de base de différence → chaque artefact jugé (fermé en cas d'échec)                                                                                                         |
| README SVG tests de comparaison d'octets (`tests/unit/docs/readme-*-svg.test.ts`)          | chaque SVG                                                                         | seulement un SVG que le PR édite, lorsque la base est résolue ; La vérification PR peu profonde de `test-unit` n'a pas de base, donc là le test saute avec `SKIP reason=base-unresolved` et `check:generated-artifacts` est propriétaire de la comparaison |
| exhaustivité des horaires e2e (`tests/unit/balance-e2e-shards.test.ts`)                    | chaque spécification a une entrée                                                  | même règle que les tests SVG (une nouvelle spécification fonctionne avec le poids médian)                                                                                                                                                                  |
| `check-quality-ratchet.mjs --require-tighten`                                              | l'amélioration non bancarisée échoue (sauf si `_policy`)                           | amélioration signalée, jamais d'échec ; une régression échoue toujours                                                                                                                                                                                     |

Le mode Release conserve les verdicts, les codes de sortie et les messages que ces contrôles avaient avant la scission ; au plus une ligne est ajoutée, nommant le mode résolu (`[agent-skills-sync] mode=release (auto: local run)`). Les tests passent par l'option `{ skip: releaseOnlyUnlessTouched(...) }` de node:test, que `check:test-masking` répertorie dans un bloc de rapport uniquement (ce n'est ni `.skip(` ni `{ skip: true }`, donc cela ne compte pas comme un saut matériel). `check:generated-artifacts` s'exécute là où la base peut être résolue : job `lint` (`fetch-depth: 0`), juste après `check:agent-skills-sync`. Localement, `npm run check:generated-artifacts -- --mode=pr` montre ce que cette étape juge sur un PR. La vérification croisée du total du fournisseur de `check:docs-counts` ("Total de référence du fournisseur (doc vs modules live)") fait partie de la porte de comptage et suit les propres modes de cette porte.

Pas dans une famille, volontairement : les fichiers de stratégie décidés par les utilisateurs (`gate-manifest.json`, les listes autorisées, `admission-policy.json`, `provider-assets-provenance.jsonl`, `model-lifecycle.json`) et les plafonds qu'une fonctionnalité PR peut devoir modifier avec le code ( les entrées de métriques `quality-baseline.json`, les lignes de base typecheck/file-size/complexity, `eslint-suppressions.json` — élagué par l'exécution ESLint avant la validation lorsqu'un PR corrige une violation gelée). `src/i18n/routeNamespaces.generated.json` est également généré mais reste dans la fonctionnalité PRs: l'application l'importe au moment de l'exécution, elle ne peut donc pas attendre une actualisation.

## Enregistrement des réductions de cliquets — la direction descendante (#8584)

Le cliquet n'est qu'à moitié automatique, et c'est la mauvaise moitié. **Augmenter** une limite consiste en une
modification JSON manuelle qui prend dix secondes et constitue le moyen le plus rapide de débloquer une PR en échec.
**Réduire** une limite exige que quelqu'un exécute `--update` et commite le résultat — et jusqu'à l'arrivée
du job `bank-ratchet-shrinks`, aucun workflow ne le faisait. Conséquence mesurée
(2026-07-25) : 18 fichiers gelés se trouvent déjà au niveau ou en dessous de la limite de 800 lignes pour les nouveaux fichiers, le pire
étant à 132× (`src/shared/validation/schemas.ts`, 19 lignes pour une limite de 2 523) ; le
plafond de complexité est passé de `1794 → 2169` au fil d'environ 37 notes de redéfinition de référence, avec exactement une
diminution (−1) ; et « resserrer via `--update` au prochain cycle » a été écrit 31 fois et respecté
une seule fois. Une limite qui survit au code qui l'a justifiée transforme silencieusement chaque
décomposition achevée en marge de croissance pour la prochaine personne qui modifiera le fichier.

`nightly-release-green.yml` → le job **`bank-ratchet-shrinks`** referme cette boucle :

|             |                                                                                                                                  |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Exécuté sur | `schedule` (3×/jour) + `workflow_dispatch` — délibérément **pas** sur `push`                                                     |
| Mesure      | la branche `release/vX.Y.Z` la plus élevée, avec la même résolution et la même protection contre l'injection que `release-green` |
| Écrit       | `check:file-size --update` et `check:complexity-ratchets --update` (tous deux uniquement réducteurs par conception)              |
| Vérifie     | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                                         |
| Livre       | une seule PR toujours à jour ciblant la branche de release — mise à jour forcée, sans jamais générer de spam                     |

L'enregistrement est effectué par lots plutôt qu'à chaque push, car il n'a aucune exigence de latence (une réduction
enregistrée sous 8 h convient), tandis qu'une exécution à chaque fusion reconstruirait la branche de la PR à plusieurs reprises
pendant les campagnes de fusion et paierait à chaque fois le coût d'un parcours ESLint complet. La détection reste déclenchée lors du
push (`release-green`) ; seul l'enregistrement est effectué par lots.

### Le vérificateur de sécurité

Le job écrit dans les références sans surveillance ; `verify-ratchet-bank.mjs` est donc ce qui rend
cela acceptable. Il compare l'arborescence après `--update` à `HEAD` et **interrompt le job
avant qu'un commit n'existe** — sans ouvrir de PR — sauf si chaque modification correspond à l'un des cas suivants :

- une entrée numérique `frozen` / `testFrozen` **réduite** ou **supprimée**
- `complexity-baseline.json` → `count` **réduit**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **réduit**

Toute autre modification provoque un échec : augmenter un nombre, ajouter une entrée, modifier `cap`/`testCap`, ou
supprimer/réécrire une note `_rebaseline_*` (ces notes constituent la piste d'audit expliquant l'existence de chaque
plafond et sont stockées dans le même objet `frozen` que les entrées de fichiers).
Un bot capable d'augmenter une limite serait strictement pire que le statu quo. Protection contre les
régressions : `tests/unit/verify-ratchet-bank.test.ts`.

Le job n'effectue jamais de push vers `release/*` — un humain fusionne la PR, de sorte qu'une mauvaise mesure
ne puisse pas être intégrée sans examen.

## Politique de liste d'autorisation

Chaque porte qui ne peut pas échouer en raison de violations préexistantes utilise une liste verte gelée (par exemple, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). La politique est la suivante :

**Corrigez la cause première ; utilisez la liste verte uniquement lorsque la violation est préexistante et ne peut pas être corrigée dans le même PR.**

Lors de l'ajout d'une entrée à une liste verte :

1. Incluez un commentaire avec la justification.
2. Faites référence au problème de suivi (par exemple, `// #3498 — Phase 2 feature, not yet implemented`).
3. Supprimez l'entrée dans le même PR qui corrige la violation — Une entrée obsolète qui ne supprime plus une violation active est en soi un défaut (6A.3, l'application obsolète fera échouer la porte sur une entrée de liste autorisée orpheline une fois implémentée).

Faire** pas** ajoutez des entrées de liste verte pour accélérer la réussite des tests. Un portail vert avec une liste d’autorisation croissante est un faux sentiment de qualité.

### Quand un portail tombe en panne sur votre PR

1. **Lisez attentivement la sortie de la porte** — il vous indique exactement quel fichier ou symbole a violé la règle.
2. **Corriger la violation** — la plupart des portes sont des vérifications déterministes du système de fichiers qui réussissent dès que le code est correct.
3. **Si la violation est préexistante** (c'est-à-dire que vous ne l'avez pas introduit mais que la porte le couvre désormais) : ajoutez une entrée de liste verte avec un commentaire de justification et un problème de suivi.
4. **Si le portail est un cliquet** (couverture, avertissements ESLint, duplication, complexité) : votre modification a aggravé la métrique. Résolvez le problème sous-jacent ou (rarement) exécutez `npm run quality:ratchet -- --update` si le changement est intentionnel et que la dégradation des métriques est acceptable — mais expliquez pourquoi dans la description PR.
5. **Portes consultatives** (`continue-on-error: true`) sont — informatifs, ils ne bloquent pas la fusion mais apparaissent dans le résumé CI. Réparez-les quand même.

Un lot de paramètres régionaux est généré à partir du `en.json` du jour où sa branche est coupée et se traduit pendant des jours pendant que la base continue d'ajouter des clés ; le lot PR n'ajoute aucune clé lui-même, de sorte que les deux frères et sœurs sont restés silencieux lorsque le lot 1 (#13044) a atterri avec 43 clés courtes dans neuf paramètres régionaux et le lot 2 (#13660) avec 10 clés courtes dans huit (15/09/2026). Corriger un rouge avec `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers`; une feuille `extra` signifie que la source l'a déposé — `sync-ui-keys` le supprime (`--prune-extra`, la valeur par défaut). `--warn` rapporte sans échouer. `--catalog=cli` exécute la même comparaison sur `bin/cli/locales` (`npm run i18n:check-keys:cli`) ; les deux étapes vivent dans le travail `i18n-ui-coverage`. La vérification absolue concerne uniquement le mode release : une fonctionnalité PR voit `SKIP reason=pr-mode` et le correctif s'exécute lors de l'actualisation de la version ou d'une vague de traduction, jamais dans une fonctionnalité PR; un PR qui modifie les catalogues de paramètres régionaux voit chacun d'eux jugé par rapport à la base de fusion (voir "Deux modes" sous job `i18n-ui-coverage`).

#### `check-new-key-coverage` — nouvelle clé i18n porte

Frère et sœur de `check-ui-value-drift`. Celui-là capte une valeur anglaise qui était** réécrit** tandis que ses traductions ont été laissées pour compte ; celui-ci attrape une clé anglaise qui était** ajouté** alors que certains endroits ne l'ont jamais reçu.

`check-ui-keys-coverage` ne peut pas voir cette classe : il applique un pourcentage plancher par région, et onze clés absentes sur ~ 13 000 laissent une couverture à 99,9 %. Un pourcentage par langue ne peut pas exprimer "cette fonctionnalité livrée non traduite" — une fonctionnalité entière peut atterrir dans une nouvelle langue sans texte et ne jamais déplacer le numéro.

L'incident qu'il code : la phase 3 du canevas d'orchestration a traduit ses onze clés dans les 42 paramètres régionaux qui existaient à l'époque. Quelques heures plus tard, le lot en langue européenne (#13044) a porté le dépôt dans 51 locales, et les neuf nouveaux arrivants (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) ne les ont jamais reçus. `deepMergeFallback` remplace l'anglais par une clé absente, donc le mode d'échec était UI non traduit plutôt que UI — réel vide, et silencieux par construction.

Comme son frère, c'est** conscient des différences** , en comparant l'anglais de la base de fusion à l'arbre de travail, de sorte que les lacunes préexistantes restent gelées et que la porte n'ait besoin d'aucune migration pour s'activer.

**Un marqueur `__MISSING__:<english>` ne le satisfait pas (depuis le 17/09/2026).** Auparavant, c'était le report documenté — le runtime revient à corriger l'anglais — jusqu'à ce que huit fonctionnalités PRs du 16/09/2026 ajoutent 61 clés et tamponnent le marqueur dans les 65 paramètres régionaux au lieu de traduire : cette porte a accepté tout le monde, rien n'a bloqué le PRs, et la porte de blocage du rapport de traduction réelle a ensuite échoué sur la pointe de publication pour tout le monde (pt-BR 3,2 % > 2,5 % + 0,5). Un marqueur est désormais jugé comme une traduction absente. Mode de sortie uniquement depuis le 13/11/2026 : une fonctionnalité PR voit `SKIP reason=pr-mode`, et lors de la version PR (`BASE_REF=origin/main`), la porte juge chaque clé ajoutée par le cycle. Corrigez un rouge dans l'actualisation de la version ou une vague de traduction avec `node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers --batch-size=40`, ou tous les paramètres régionaux en parallèle avec `npm run i18n:translate-new-keys` (`scripts/i18n/translate-new-keys.sh`, détaché-safe, refuse de démarrer sans l'environnement `OMNIROUTE_TRANSLATION_*` ). Une clé qui doit rester en anglais (un nom product/engine/flag épinglé) appartient à `scripts/i18n/untranslatable-keys.json`, jamais derrière un marqueur. `vi` interdit purement et simplement les marqueurs (`tests/unit/i18n-vi-completeness.test.ts`).

#### porte d'essai garée `check-vitest-exclusions` —

Un fichier dans la liste `exclude` de `vitest.config.ts` est un test qui ne s'exécute pas, et il ressemble à une couverture pour quiconque lit l'arborescence. Soixante-deux fichiers accumulés derrière le commentaire `// #8618 — pre-existing failure; remove this exclusion when fixed`. Le numéro #8618 a été fermé le 11/08/2026 tandis que la liste qu'il suivait est passée de 45 entrées à 62, chaque nouvelle héritant d'un commentaire pointant vers un problème mort. Lorsque la liste a finalement été mesurée fichier par fichier (#13204),** 51 des 62 transmis à l'arborescence actuelle sans changement de source** .

La porte exige que chaque exclusion qui résout un fichier réel (a) nomme un problème de suivi et (b) apparaisse dans `config/quality/vitest-exclusions.json` avec son statut mesuré, donc en ajouter une est une différence révisable dans un fichier dédié plutôt qu'une ligne supplémentaire dans un tableau de 60 entrées. Il ne réexécute délibérément pas les tests exclus — qui coûtent ~ 10 minutes et appartiennent à un travail périodique ; l'inventaire enregistre la date à laquelle chacun a été mesuré pour la dernière fois.
