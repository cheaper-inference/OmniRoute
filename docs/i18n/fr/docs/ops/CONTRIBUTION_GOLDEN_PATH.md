Utilisez ce guide pour choisir la boucle de développement fiable la plus courte pour une pull request. Il ne
remplace pas les documents d’architecture et de sécurité propres à chaque domaine liés ci-dessous ; il associe chaque type
de modification courant à ses contrats, à ses vérifications ciblées et à sa couverture CI.

## Le parcours suivi par chaque modification

1. **Choisissez la base avant toute modification.** Trouvez la branche `release/v*` active la plus élevée et créez votre branche à partir
   de son dernier commit. Ciblez cette branche, et non `main`. Si un gel de version est en cours, ne ciblez pas la branche
   gelée ; utilisez le prochain cycle actif décrit dans
   [Modèle de branches et de versions](BRANCHING_MODEL.md).
2. **Nommez les contrats.** Identifiez chaque catalogue, schéma, artefact généré, API publique ou interface
   utilisateur affecté par la modification. Le tableau ci-dessous indique l’ensemble minimal de départ.
3. **Écrivez ou mettez à jour des tests ciblés.** Les modifications de production dans `src/`, `open-sse/`, `electron/` ou
   `bin/` nécessitent un test automatisé dans la même PR. Exécutez les fichiers de test les plus restreints qui prouvent le
   comportement, puis les contrôles ciblés indiqués.
4. **Laissez la CI exécuter la matrice complète.** Les partitions complètes de tests unitaires, Vitest, le seuil progressif de couverture et
   le build de production s’exécutent sur la PR. N’exécutez une suite étendue localement que lorsqu’un échec ciblé indique
   un impact plus large ou lorsque la modification couvre plusieurs sous-systèmes.
5. **Réconciliez avant la revue.** Récupérez la base active, inspectez ses nouveaux commits et votre diff par rapport
   à celle-ci, puis rebasez ou fusionnez la base conformément au workflow des contributeurs. Résolvez les conflits de fichiers
   générés et de catalogues à partir de leur source, régénérez-les, réexécutez la boucle ciblée et confirmez que la
   PR cible toujours la branche de version active.
6. **Consignez les preuves.** Dans le modèle de PR, répertoriez les commandes exécutées, chaque fichier de test ajouté ou modifié,
   les migrations ou feature flags, ainsi que toute validation réservée à la CI encore en attente.

## Parcours de référence par type de modification

Les commandes ci-dessous constituent les vérifications ciblées minimales, et non une autorisation d’ignorer un test qui couvre directement le
comportement que vous avez modifié.

### Fournisseur

**Contrats**

- Définition du fournisseur dans `src/shared/constants/providers/` et sa composition dans
  `src/shared/constants/providers.ts`.
- Modèles et capacités dans `open-sse/config/providerRegistry.ts` ou dans ses fichiers de registre extraits.
- Sélection de l’exécuteur/du traducteur, configuration OAuth ou par clé API, ressources du tableau de bord et référence
  fournisseur générée, le cas échéant.
- Les identifiants publics doivent utiliser `resolvePublicCred()` ; les réponses d’erreur doivent utiliser les utilitaires partagés
  d’assainissement des erreurs. Consultez `docs/security/PUBLIC_CREDS.md` (git ; non compilé dans `/docs`) et
  [Assainissement des erreurs](../security/ERROR_SANITIZATION.md).

**Boucle ciblée**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # lorsque le catalogue change ; validez le diff généré
npm run lint
```

Testez également chaque famille de requêtes affectée : chat, Responses, images, embeddings, audio ou vidéo.
Examinez les diffs des catalogues générés et des références comme des modifications de contrat ; ne les acceptez pas aveuglément.

### Routage

**Contrats**

- Valeurs publiques des stratégies et métadonnées de l’interface utilisateur dans `src/shared/constants/routingStrategies.ts`.
- Distribution et ordre sous `open-sse/services/combo.ts` et `open-sse/services/combo/`.
- Schémas de combo, persistance, état de résilience, capacités des modèles et contrôles API/interface utilisateur.
- [Moteur Auto-Combo](../routing/AUTO-COMBO.md) et documentation sur la résilience lorsque le comportement change.

**Boucle ciblée**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # modifications de stratégie ou de distribution
npm run check:known-symbols      # modifications de l’enregistrement des stratégies
npm run lint
```

Utilisez localement des tests déterministes avec des services en amont simulés. Les tests rapides de combo en conditions réelles nécessitent des identifiants et sont
manuels ; ils ne remplacent pas la CI.

### UI / UX

**Contrats**

- Route/page Next.js et limites des composants partagés sous `src/app/` et
  `src/shared/components/`.
- Formats des réponses API, états de chargement/vide/erreur, comportement au clavier et avec les lecteurs d’écran,
  mise en page adaptative, thèmes et extension des locales.
- Chaînes sources en anglais de l’interface utilisateur dans `src/i18n/messages/en.json` ; ne codez pas en dur de nouveau texte destiné aux utilisateurs.

**Boucle ciblée**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Exécutez l’application pour les modifications d’interaction ou visuelles et vérifiez les fenêtres d’affichage étroites et larges. La CI exécute le
build de production et les suites plus étendues ; le comportement visuel nécessite toujours un composant ciblé, Playwright
ou une vérification manuelle documentée adaptée à la modification.

### i18n

**Contrats**

- `src/i18n/messages/en.json` est la source de l’interface utilisateur ; `config/i18n.json` est la source des locales.
- Les catalogues de la CLI sont conservés séparément sous `bin/cli/locales/`.
- Préservez exactement les placeholders et balises ICU. Ne traduisez pas les noms de produits/fournisseurs/modèles,
  les noms de protocoles et d’en-têtes, les commandes, les identifiants de code/JSON, les URL, les variables d’environnement ou
  les termes protégés tels que `OmniRoute`, `OAuth`, `MCP` et `A2A`. La liste source actuelle est
  `scripts/i18n/glossary/protected-terms.json`.

**Boucle ciblée**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # lorsque les chaînes/catalogues de la CLI changent
npm run lint
```

Il s’agit de recommandations pour le système existant, et non d’une invitation à étendre ses outils ou son modèle de clés.
Gardez les correctifs i18n ciblés pendant la conception du système de remplacement. N’exécutez pas de commandes de traduction
qui appellent des services externes, sauf si la tâche exige explicitement des traductions générées et
que vous avez examiné le diff obtenu.

### CLI

**Contrats**

- Commandes publiques et options dans `bin/cli/`, commandes d’API générées, codes de sortie, stdout/stderr et
  structures de sortie JSON, comportement de la configuration/de l’environnement et fichiers empaquetés.
- Les chaînes de la CLI destinées aux utilisateurs doivent utiliser la couche i18n de la CLI et maintenir les catalogues `en`/`pt-BR` synchronisés.
- Préserver Node comme environnement d’exécution pris en charge ainsi que le contrat du binaire publié.

**Boucle ciblée**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # modifications de la CLI générée/regroupée
npm run check:pack-policy     # modifications de la surface du package
npm run lint
```

Utilisez la commande exacte dans un répertoire de données temporaire lorsque le comportement dépend de l’analyse, des fichiers ou du code
de sortie. La CI effectue les vérifications plus larges des artefacts du package et de l’écosystème.

### Base de données

**Contrats**

- Modules de domaine sous `src/lib/db/` ; importez directement les modules spécifiques (l’ancienne couche de réexportation `localDb.ts` a été supprimée).
- Migrations SQL numérotées et idempotentes sous `src/lib/db/migrations/`, sécurité des transactions, comportement de
  mise à niveau, index et chaque appelant affecté par le schéma.
- Les routes et les gestionnaires n’exécutent jamais directement de SQL brut.

**Boucle ciblée**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Lors de l’ajout d’une migration, testez à la fois une base de données neuve et la mise à niveau depuis le schéma précédent. Les tests de base de données
doivent fermer les handles et appeler `resetDbInstance()` pendant le nettoyage. Exécutez `npm run test:bun:db` uniquement lorsque
le chemin de l’adaptateur Bun fourni au mieux change ; Node reste l’autorité de référence.

### Build / déploiement

**Contrats**

- Manifestes et fichier de verrouillage à la racine et dans les espaces de travail, `scripts/build/`, assemblage autonome Next.js, contenu du package `dist/`,
  métadonnées de plateforme Electron, workflows de CI et sentinelles de déploiement.
- Les plages de versions Node prises en charge et l’utilisation de Bun figurant sur la liste d’autorisation dans `CLAUDE.md` doivent rester intactes.
- Les artefacts de build ne sont pas suivis ; les politiques relatives aux dépendances, aux licences, aux workflows et aux packages s’appliquent.

**Boucle ciblée**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # modifications des dépendances ou du fichier de verrouillage
npm run check:pack-policy      # modifications de la surface du package publié
npm run lint
```

Utilisez `npm run build` localement uniquement lorsque la modification affecte la compilation, l’assemblage autonome, les ressources
ou le regroupement à l’exécution. Utilisez `npm run build:release` uniquement pour la validation de la publication/du déploiement. Le build de la CI constitue
le signal multiplateforme final ; les modifications Electron propres à une plateforme nécessitent le build ciblé correspondant
ou des preuves issues d’un test de fumée.

## Scripts de développement pour une machine partagée

Deux utilitaires dans `scripts/dev/` encodent la boucle locale sur une devbox où d’autres sessions sont actives :

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # fichiers de merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # exactement ces fichiers
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # worktree isolé, sûr en parallèle
```

- `typecheck-touched.sh` vérifie les types uniquement pour les fichiers `.ts/.tsx` modifiés au moyen d’un
  `tsconfig.touched.tmp.json` temporaire (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) avec un tas de 6 Go, et remplace ainsi le `tsc -p tsconfig.json` à l’échelle du projet
  qui provoque une erreur de mémoire sur une machine chargée. Il affiche les erreurs dans les fichiers modifiés ainsi qu’une ligne récapitulative et renvoie
  `1` en cas d’erreurs dans les fichiers modifiés, `2` lorsque les seules erreurs se trouvent dans des fichiers importés ou que tsc s’est arrêté
  sans diagnostic (consultez le journal qu’il indique sous `_artifacts/typecheck-touched/`), et `0` lorsqu’il n’y a
  aucune erreur. Le tsconfig temporaire est toujours supprimé ; ne le commitez jamais.
- `new-worktree.sh` sérialise les exécutions simultanées au moyen de `<git-common-dir>/omniroute-new-worktree.lock`
  (attente maximale de 600 s par défaut, avec un message visible ; l’en-tête du script documente la
  méthode de remplacement) et annule
  la création de la branche lorsqu’il l’a créée mais que `git worktree add` échoue avant la création du worktree, afin qu’une nouvelle tentative
  ne nécessite pas de `git branch -D` manuel. Les `node_modules` liés physiquement et la copie de `.husky/_` restent inchangés.

## Boucle locale de candidat

Les tests des sources ne peuvent pas prouver que l’artefact empaqueté démarre : les listes d’empaquetage, les dépendances
élaguées et les binaires natifs n’échouent qu’une fois l’archive tar installée et démarrée. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) constitue le volet local du flux construire une fois / valider / promouvoir de la
RFC #8084 : il construit un candidat, valide cet artefact précis, le promeut par renommage de
répertoires et revient à la version précédente lorsque l’emplacement promu échoue à son contrôle d’intégrité.

```bash
npm run dev:candidate -- run --dry-run --json  # afficher le plan sans rien modifier
npm run dev:candidate -- run                   # construire + valider + promouvoir, retour automatique
npm run dev:candidate -- build                 # npm pack + installation dans _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # démarrer sur un port libre, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # permuter current et previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # réutiliser une archive tar construite ailleurs (CI)
```

- **Construire une seule fois.** `build` empaquette l’arborescence actuelle (il nécessite `dist/server.js`, exécutez donc
  d’abord `npm run build:release`) ou copie `--from-tarball`, puis installe l’archive tar dans un
  préfixe npm isolé, car l’archive tar ne contient aucun `node_modules`. L’identifiant est le sha court de `HEAD`
  (`-dirty` lorsque l’arborescence comporte des modifications locales) ou `tgz-<sha256>` pour une archive tar. Un identifiant propre déjà
  construit est réutilisé au lieu d’être reconstruit ; passez `--force` pour le reconstruire.
- **Valider le paquet, pas les sources.** `validate` démarre la CLI installée
  (`serve --port <free port>`) avec un nouveau `DATA_DIR=<candidate>/data`, de faux secrets, et les
  variables `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` et `INITIAL_PASSWORD` de l’opérateur supprimées de
  l’environnement, afin de vérifier le comportement sans clé sur l’interface de bouclage d’une nouvelle installation. Il attend que
  `GET /api/health` renvoie 200, exige que `GET /v1/models` renvoie 200, arrête le groupe de processus
  et enregistre le verdict dans `validation.json` avec le hachage de l’archive tar.
- **Promouvoir le même artefact.** `promote` refuse un candidat dépourvu d’une validation réussie pour le
  hachage de son archive tar actuelle. L’emplacement actif par défaut est `_artifacts/candidate/current` ; `--target <dir>`
  sélectionne un autre répertoire sur le même système de fichiers, et son emplacement précédent est `<dir>.previous`.
  Chaque renommage est atomique, et un échec en cours d’opération annule les renommages déjà effectués.
- **Revenir à la version précédente.** `run` valide à nouveau l’emplacement promu et permute à nouveau `current` et `previous` lorsque
  ce contrôle échoue. Un candidat qui échoue à la première validation n’est jamais promu.

Tout est écrit sous le répertoire ignoré par git `_artifacts/candidate/` ; une installation OmniRoute
existante et son répertoire de données ne sont jamais modifiés. La CLI promue est
`_artifacts/candidate/current/prefix/bin/omniroute` ; démarrez-la avec votre propre `DATA_DIR` lorsque vous
l’utilisez. Codes de sortie : `0` réussite, `1` échec de la validation ou de la promotion, `2` erreur d’utilisation ou build manquant.

## Boucle locale ou CI

| À exécuter localement pour chaque correctif                                                                                        | La CI fournit un signal global                                                             |
| ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Tests directs du comportement et contrôles de catégorie ci-dessus                                                                  | Suite complète de tests unitaires partitionnée et tests séquentiels                        |
| `npm run lint`                                                                                                                     | Suites Vitest et seuils progressifs de couverture/qualité                                  |
| Vérification des types ou build uniquement lorsque le contrat concerné l’exige                                                     | Build de production, sécurité, documentation, dépendances et contrôles de politique des PR |
| Interactions manuelles/vérifications en conditions réelles uniquement lorsque l’automatisation ne peut pas prouver le comportement | Vérifications d’intégration inter-jobs et de plateformes configurées par le workflow       |

Une boucle ciblée au vert constitue une preuve concernant le contrat modifié, et non la garantie que des vérifications CI sans rapport
réussiront. Inversement, ne faites pas attendre chaque modification locale jusqu’à l’exécution complète de la matrice du dépôt.

## Liste de contrôle de réconciliation

Avant de demander une revue :

- Confirmez que la base de la PR est toujours la branche `release/v*` active la plus récente.
- Récupérez cette base et examinez les commits intégrés depuis la création de votre branche.
- Examinez `git diff <active-base>...HEAD` afin de détecter toute modification accidentelle ou générée.
- Résolvez les conflits de catalogue et de documents générés en mettant à jour la source, puis en régénérant la sortie.
- Réexécutez chaque test/contrôle ciblé répertorié dans la description de la PR après la réconciliation.
- N’affaiblissez jamais les assertions et ne supprimez jamais les tests requis dans le seul but de vous adapter à une base qui a évolué.

Pour les règles de gel des versions et de reciblage, consultez
[Modèle de branches et de versions](BRANCHING_MODEL.md). Pour l’inventaire complet de la CI, consultez
[Référence des contrôles qualité](../architecture/QUALITY_GATES.md).
