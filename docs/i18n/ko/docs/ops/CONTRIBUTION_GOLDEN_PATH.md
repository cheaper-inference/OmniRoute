이 가이드를 사용하여 풀 리퀘스트에 적합한, 신뢰할 수 있는 최소 개발 루프를 선택하세요. 이 가이드는
아래에 링크된 영역별 아키텍처 및 보안 문서를 대체하지 않으며, 일반적인 각 변경 유형을 해당
계약, 집중 검사 및 CI 범위와 연결합니다.

## 모든 변경이 따르는 경로

1. **편집하기 전에 베이스를 선택하세요.** 활성 상태인 가장 높은 `release/v*` 브랜치를 찾아 해당
   브랜치의 최신 커밋에서 분기하세요. `main`이 아니라 해당 브랜치를 대상으로 지정하세요. 릴리스 동결이 활성화된 경우 동결된
   브랜치를 대상으로 지정하지 말고,
   [브랜치 및 릴리스 모델](BRANCHING_MODEL.md)에 설명된 다음 활성 주기를 사용하세요.
2. **계약을 명시하세요.** 변경의 영향을 받는 모든 카탈로그, 스키마, 생성된 아티팩트, 공개 API 또는 사용자
   인터페이스를 식별하세요. 아래 표는 최소한으로 확인해야 할 시작 항목을 제시합니다.
3. **집중 테스트를 작성하거나 업데이트하세요.** `src/`, `open-sse/`, `electron/` 또는
   `bin/`의 프로덕션 변경에는 동일한 PR에 자동화된 테스트가 필요합니다. 동작을 입증하는 최소한의 테스트 파일을
   실행한 다음, 나열된 집중 게이트를 실행하세요.
4. **광범위한 매트릭스는 CI에서 실행되도록 하세요.** 전체 단위 테스트 샤드, Vitest, 커버리지 래칫 및
   프로덕션 빌드는 PR에서 실행됩니다. 집중 테스트의 실패가 더 광범위한 영향을 가리키거나 변경이 여러
   하위 시스템에 걸쳐 있는 경우에만 로컬에서 광범위한 테스트 스위트를 실행하세요.
5. **리뷰 전에 변경 사항을 조정하세요.** 활성 베이스를 가져오고 새 커밋과 베이스 대비 자신의 diff를
   검사한 다음, 기여자 워크플로에 따라 베이스를 리베이스하거나 병합하세요. 생성된 파일 및
   카탈로그 충돌은 원본에서 해결하고, 다시 생성하고, 집중 루프를 재실행한 뒤 PR이 여전히 활성 릴리스
   브랜치를 대상으로 하는지 확인하세요.
6. **근거를 기록하세요.** PR 템플릿에 실행한 명령, 추가하거나 변경한 모든 테스트 파일,
   마이그레이션 또는 기능 플래그, 아직 대기 중인 CI 전용 검증을 나열하세요.

## 변경 유형별 골든 경로

아래 명령은 최소한의 집중 검사이며, 변경한 동작을 직접 다루는 테스트를 건너뛸 수 있는 권한이 아닙니다.

### 공급자

**계약**

- `src/shared/constants/providers/` 의 공급자 정의 및 `src/shared/constants/providers.ts` 의 구성.
- `open-sse/config/providerRegistry.ts` 또는 추출된 레지스트리 파일의 모델 및 기능.
- Executor/translator 선택, OAuth 또는 API 키 구성 및 대시보드 자산. 재생성된 `docs/reference/PROVIDER_REFERENCE.md` 또는 README 다이어그램을 커밋하지 마십시오. 릴리스 새로 고침으로 이를 다시 작성합니다(`check:pr-derived-paths` 이를 전달하는 기능 PR 에 실패합니다).
- 공개 자격 증명은 `resolvePublicCred()` 사용해야 합니다. 오류 응답은 공유된 삭제된 오류 도우미를 사용해야 합니다. `docs/security/PUBLIC_CREDS.md` (git; `/docs` 로 컴파일되지 않음) 및 [Error Sanitization 을](../security/ERROR_SANITIZATION.md) 참조하세요.

**집중 루프**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # preview the generated reference; do not commit it
npm run lint
```

또한 영향을 받는 모든 요청 계열(채팅, 응답, 이미지, 임베딩, 오디오 또는 비디오)을 테스트하세요. 계약 변경에 따라 생성된 카탈로그 및 골든 차이점을 검토합니다. 맹목적으로 받아들이지 마십시오.

### 라우팅

**계약**

- `src/shared/constants/routingStrategies.ts` 의 공개 전략 값 및 UI 메타데이터.
- `open-sse/services/combo.ts` 및 `open-sse/services/combo/` 에서 발송 및 주문.
- 콤보 스키마, 지속성, 탄력성 상태, 모델 기능 및 API/UI 제어.
- 동작 변경 시 [자동 콤보 엔진](../routing/AUTO-COMBO.md) 및 복원력 문서화.

**집중 루프**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy or dispatch changes
npm run check:known-symbols      # strategy registration changes
npm run lint
```

결정론적 모의 업스트림 테스트를 로컬에서 사용합니다. 라이브 콤보 연기에는 자격 증명이 필요하며 CI 대체품이 아닌 수동입니다.

### UI / UX

**계약**

- Next.js route/page 및 `src/app/` 및 `src/shared/components/` 아래의 공유 구성 요소 경계.
- API 응답 모양, loading/empty/error 상태, 키보드 및 화면 판독기 동작, 반응형 레이아웃, 테마 및 로케일 확장.
- `src/i18n/messages/en.json` 의 영어 UI 소스 문자열; 새로운 사용자용 사본을 하드 코딩하지 마십시오.

**집중 루프**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

상호 작용이나 시각적 변경을 위해 앱을 실행하고 좁은 뷰포트와 넓은 뷰포트를 모두 확인하세요. CI 프로덕션 빌드와 더 광범위한 제품군을 실행합니다. 시각적 동작에는 여전히 집중된 구성 요소인 Playwright 또는 변경 사항에 적합한 문서화된 수동 확인이 필요합니다.

### i18n

**계약**

- `src/i18n/messages/en.json` 는 UI 소스입니다. `config/i18n.json` 는 로케일 소스입니다.
- CLI 카탈로그는 `bin/cli/locales/` 아래에 별도로 존재합니다.
- ICU 자리표시자와 태그를 정확하게 유지합니다. product/provider/model 이름, 프로토콜 및 헤더 이름, 명령, code/JSON 식별자, URLs, 환경 변수 또는 `OmniRoute`, `OAuth`, `MCP` 및 `A2A` 와 같은 보호 용어를 번역하지 마십시오. 현재 소스 목록은 `scripts/i18n/glossary/protected-terms.json` 입니다.

PR 기능은 `src/i18n/messages/en.json` (CLI: `bin/cli/locales/en.json`)만 편집합니다. 다른 로케일은 릴리스 새로 고침 또는 번역 웨이브(`docs/guides/I18N.md` → "Feature PRs touch `en.json` only")에 의해 릴리스당 한 번씩 완료됩니다. `npm run check:pr-derived-paths` 다른 로케일 카탈로그를 편집하는 기능 PR 에 실패합니다.

**집중 루프**

```bash
npm run i18n:check-ui-coverage
npm run check:ui-icu
node scripts/i18n/check-key-completeness.mjs --mode=pr      # what CI runs on your PR
node scripts/i18n/check-ui-value-drift.mjs --mode=pr
node scripts/check/check-cli-i18n.mjs --mode=pr              # when CLI strings change
npm run i18n:check-glossary
npm run lint
```

`--mode=pr` 없으면 이러한 게이트는 로컬에서 릴리스 모드로 실행되고 사이클이 `en.json` 에 추가되거나 다시 작성된 모든 키를 보고합니다. 그것은 PR 의 작업이 아니라 릴리스 새로 고침의 작업입니다.

이는 도구나 핵심 모델을 확장하라는 제안이 아니라 기존 시스템에 대한 지침입니다. 교체 시스템이 설계되는 동안 i18n 패치를 수술적으로 유지하십시오. 작업에 명시적으로 생성된 번역이 필요하고 결과 차이점을 검토한 경우가 아니면 외부 서비스를 호출하는 번역 명령을 실행하지 마십시오.

### CLI

**계약**

- `bin/cli/` 의 공개 명령 및 플래그, 생성된 API 명령, 종료 코드, stdout/stderr 및 JSON 출력 형태, config/environment 동작 및 패키지 파일.
- CLI 사용자 대상 문자열은 CLI i18n 계층( `bin/cli/locales/en.json` 에 존재하는 `t()` 키)을 사용해야 합니다. PR 기능은 `en.json` 만 편집합니다. `pt-BR` 및 기타 로케일은 릴리스 시 완료됩니다.
- Node를 지원되는 런타임 및 게시된 바이너리 계약으로 유지합니다.

**집중 루프**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
node scripts/check/check-cli-i18n.mjs --mode=pr
npm run build:cli             # generated/bundled CLI changes
npm run check:pack-policy     # package-surface changes
npm run lint
```

동작이 구문 분석, 파일 또는 종료 상태에 따라 달라지는 경우 임시 데이터 디렉토리에서 정확한 명령을 사용하십시오. CI 더 광범위한 패키지 아티팩트 및 생태계 검사를 수행합니다.

### 데이터 베이스

**계약**

- `src/lib/db/` 아래의 도메인 모듈; 특정 모듈을 직접 가져옵니다(이전 `localDb.ts` 재내보내기 계층이 제거됨).
- `src/lib/db/migrations/` 에서 번호가 매겨진 멱등성 SQL 마이그레이션, 트랜잭션 안전, 업그레이드 동작, 인덱스 및 스키마의 영향을 받는 모든 호출자.
- 경로와 핸들러는 원시 SQL 직접 발행하지 않습니다.

**집중 루프**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

마이그레이션을 추가할 때 새로운 데이터베이스를 테스트하고 이전 스키마에서 업그레이드하세요. 데이터베이스 테스트는 정리 중에 핸들을 닫고 `resetDbInstance()` 호출해야 합니다. 최선의 Bun 어댑터 경로가 변경될 때만 `npm run test:bun:db` 실행하십시오. 노드는 권한을 유지합니다.

### 빌드/배포

**계약**

- 루트 및 작업 공간 manifests/lockfile, `scripts/build/`, Next.js 독립형 어셈블리, `dist/` 패키지 콘텐츠, Electron 플랫폼 메타데이터, CI 워크플로 및 배포 센티널.
- 지원되는 노드 범위와 `CLAUDE.md` 에서 허용 목록에 있는 Bun 사용은 그대로 유지되어야 합니다.
- 빌드 아티팩트는 추적되지 않습니다. 종속성, 라이선스, 워크플로 및 패키지 정책이 적용됩니다.

**집중 루프**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency or lockfile changes
npm run check:pack-policy      # published package surface changes
npm run lint
```

변경 사항이 컴파일, 독립형 어셈블리, 자산 또는 런타임 번들링에 영향을 미치는 경우에만 `npm run build` 로컬로 사용하세요. release/deploy 검증에만 `npm run build:release` 사용하십시오. CI 의 빌드는 최종 크로스 플랫폼 신호입니다. 플랫폼별 Electron 변경에는 일치하는 집중된 빌드 또는 연기 증거가 필요합니다.

## 공유 머신용 개발자 스크립트

다른 세션이 활성화된 devbox에서 로컬 개발 루프를 수행할 수 있도록 두 개의 `scripts/dev/` 헬퍼가 제공됩니다.

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD의 파일
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # 정확히 이 파일들만
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # 격리된 worktree, 병렬 실행에 안전함
```

- `typecheck-touched.sh`는 6 GB 힙에서 임시 `tsconfig.touched.tmp.json`
  (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`, `incremental: false`)을 통해 변경된
  `.ts/.tsx` 파일만 타입 검사하므로, 부하가 걸린 머신에서 OOM이 발생하는 프로젝트 전체
  `tsc -p tsconfig.json`을 대신합니다. 변경된 파일의 오류와 요약 한 줄을 출력하며, 변경된
  파일에 오류가 있으면 `1`, 오류가 가져온 파일에만 있거나 진단 없이 tsc가 종료된 경우
  `2`(`_artifacts/typecheck-touched/` 아래에서 출력된 이름의 로그를 확인하세요), 문제가
  없으면 `0`으로 종료합니다. 임시 tsconfig는 항상 제거되므로 절대 커밋하지 마세요.
- `new-worktree.sh`는 동시 실행을 `<git-common-dir>/omniroute-new-worktree.lock`에서
  직렬화하며(기본적으로 최대 600 s 동안 대기하고 안내 메시지를 표시합니다. 재정의 방법은
  스크립트 헤더에 설명되어 있습니다), worktree가 생성되기 전에 `git worktree add`가
  실패하면 자신이 생성한 브랜치를 롤백하므로 재시도할 때 수동으로 `git branch -D`를
  실행할 필요가 없습니다. 하드 링크된 `node_modules`와 `.husky/_` 복사본은 변경되지
  않습니다.

## 로컬 후보 빌드 루프

소스 테스트만으로는 패키징된 아티팩트가 부팅되는지 입증할 수 없습니다. 패키징 목록,
정리된 의존성, 네이티브 바이너리 관련 문제는 tarball을 설치하고 시작한 뒤에만 드러납니다.
`npm run dev:candidate`(`scripts/dev/candidate.mjs`)는 RFC #8084에 정의된 한 번 빌드 /
검증 / 승격 흐름의 로컬 측 구현입니다. 후보 하나를 빌드하고, 해당 아티팩트를 그대로
검증한 다음 디렉터리 이름 변경을 통해 승격하며, 승격된 슬롯의 상태 확인이 실패하면
롤백합니다.

```bash
npm run dev:candidate -- run --dry-run --json  # 계획만 출력하고 아무것도 변경하지 않음
npm run dev:candidate -- run                   # 빌드 + 검증 + 승격, 자동 롤백
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/에 설치
npm run dev:candidate -- validate --id <id>    # 사용 가능한 포트에서 부팅, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current와 previous 교환
npm run dev:candidate -- run --from-tarball <file.tgz>  # 다른 곳에서 빌드된 tarball 재사용(CI)
```

- **한 번만 빌드합니다.** `build`는 현재 트리를 패키징하거나(`dist/server.js`가
  필요하므로 먼저 `npm run build:release`를 실행하세요) `--from-tarball`을 복사한 다음,
  tarball에 `node_modules`가 포함되지 않으므로 격리된 npm prefix에 tarball을 설치합니다.
  id는 짧은 `HEAD` sha(트리에 로컬 변경 사항이 있으면 `-dirty`) 또는 tarball의
  `tgz-<sha256>`입니다. 이미 빌드된 깨끗한 id는 다시 빌드하지 않고 재사용됩니다. 다시
  빌드하려면 `--force`를 전달하세요.
- **소스가 아닌 패키지를 검증합니다.** `validate`는 새로운
  `DATA_DIR=<candidate>/data`, 가짜 secret을 사용하고 운영자의 `OMNIROUTE_API_KEY`,
  `STORAGE_ENCRYPTION_KEY`, `INITIAL_PASSWORD`를 환경에서 제거한 상태로 설치된 CLI
  (`serve --port <free port>`)를 시작하여, 신규 설치의 키 없는 루프백 구성을 확인합니다.
  `GET /api/health`가 200을 반환할 때까지 기다리고, `GET /v1/models`가 200을 반환해야
  통과하며, 프로세스 그룹을 중지한 다음 tarball 해시와 함께 판정 결과를
  `validation.json`에 기록합니다.
- **동일한 아티팩트를 승격합니다.** `promote`는 현재 tarball 해시에 대해 검증을 통과하지
  않은 후보의 승격을 거부합니다. 기본 활성 슬롯은 `_artifacts/candidate/current`이며,
  `--target <dir>`을 사용하면 동일한 파일 시스템에서 다른 디렉터리를 선택할 수 있고
  이전 슬롯은 `<dir>.previous`가 됩니다. 각 이름 변경은 원자적으로 수행되며, 도중에
  실패하면 이미 수행된 이름 변경을 되돌립니다.
- **롤백합니다.** `run`은 승격된 슬롯을 다시 검증하고, 해당 확인이 실패하면 `current`와
  `previous`를 원래대로 다시 교환합니다. 첫 번째 검증에 실패한 후보는 절대 승격되지
  않습니다.

모든 항목은 git에서 무시되는 `_artifacts/candidate/` 아래에 기록됩니다. 기존 OmniRoute
설치와 해당 데이터 디렉터리는 절대 변경되지 않습니다. 승격된 CLI는
`_artifacts/candidate/current/prefix/bin/omniroute`에 있습니다. 사용할 때는 자체
`DATA_DIR`을 지정하여 시작하세요. 종료 코드: 성공은 `0`, 검증 또는 승격 실패는 `1`,
사용법 오류 또는 빌드 누락은 `2`입니다.

## 로컬 루프와 CI 비교

| 각 패치에 대해 로컬에서 실행                                           | CI가 제공하는 광범위한 신호                         |
| ---------------------------------------------------------------------- | --------------------------------------------------- |
| 위에 명시된 직접 동작 테스트 및 카테고리 게이트                        | 샤딩된 전체 단위 테스트 스위트 및 직렬 테스트       |
| `npm run lint`                                                         | Vitest 스위트 및 커버리지/품질 기준 상향 검사       |
| 영향을 받는 계약에서 요구하는 경우에만 타입 검사 또는 빌드             | 프로덕션 빌드, 보안, 문서, 종속성 및 PR 정책 게이트 |
| 자동화로 동작을 입증할 수 없는 경우에만 수동 상호작용/라이브 검사 수행 | 워크플로에 구성된 작업 간 통합 및 플랫폼 검사       |

중점 로컬 루프의 성공은 변경된 계약에 대한 증거이지, 관련 없는 CI 검사가
통과할 것이라는 증명은 아닙니다. 반대로 로컬에서 수정할 때마다 전체 저장소 매트릭스가
완료될 때까지 기다리게 하지 마세요.

## 조정 체크리스트

리뷰를 요청하기 전에 다음을 수행하세요.

- PR의 베이스가 여전히 가장 높은 활성 `release/v*` 브랜치인지 확인합니다.
- 해당 베이스를 가져오고 브랜치를 만든 이후 반영된 커밋을 검토합니다.
- 의도하지 않았거나 생성된 변경 사항이 있는지 `git diff <active-base>...HEAD`를 검토합니다.
- 소스를 업데이트하고 출력을 다시 생성하여 카탈로그 및 생성된 문서의 충돌을 해결합니다.
- 조정 후 PR 설명에 나열된 모든 중점 테스트/게이트를 다시 실행합니다.
- 변경된 베이스에 맞추기 위해 어설션을 약화하거나 필수 테스트를 제거하지 마세요.

릴리스 동결 및 대상 변경 규칙은
[브랜칭 및 릴리스 모델](BRANCHING_MODEL.md)을 참조하세요. 전체 CI 목록은
[품질 게이트 참조](../architecture/QUALITY_GATES.md)를 참조하세요.
