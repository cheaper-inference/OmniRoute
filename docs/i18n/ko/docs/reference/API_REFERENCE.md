## 채팅 완성

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### 사용자 정의 헤더

| 헤더                     | 방향 | 설명                                                                                                                                                                                   |
| ------------------------ | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | 요청 | 캐시를 우회하려면 `true`로 설정                                                                                                                                                        |
| `x-omniroute-no-memory`  | 요청 | 이 요청에 대한 메모리 및 스킬 주입을 건너뛰려면 `true`로 설정합니다(no-cache와 동일하며, 호출별 토큰/비용 오버헤드를 방지함)                                                           |
| `X-OmniRoute-Progress`   | 요청 | 진행 이벤트를 받으려면 `true`로 설정                                                                                                                                                   |
| `X-Session-Id`           | 요청 | 외부 세션 선호도 유지를 위한 고정 세션 키                                                                                                                                              |
| `x_session_id`           | 요청 | 밑줄 변형도 허용됨(직접 HTTP 호출)                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | 요청 | 호출자가 제공하는 세션/대화 태그(메모리에도 전달됨). 지정된 경우 세션별 비용 귀속을 위해 그대로 `call_logs.session_tag`에 유지됩니다(#8249). 지정되지 않은 경우 절대 생성되지 않습니다 |
| `Idempotency-Key`        | 요청 | 중복 제거 키(5초 범위)                                                                                                                                                                 |
| `X-Request-Id`           | 요청 | 대체 중복 제거 키                                                                                                                                                                      |
| `x-omniroute-connection` | 요청 | ID를 사용하여 단일 모델 요청을 하나의 제공자 연결(계정)에 고정합니다. [요청별 계정 고정](#account-pinning-per-request)을 참조하세요                                                    |
| `X-OmniRoute-Cache`      | 응답 | `HIT` 또는 `MISS`(비스트리밍)                                                                                                                                                          |
| `X-OmniRoute-Idempotent` | 응답 | 중복 제거된 경우 `true`                                                                                                                                                                |
| `X-OmniRoute-Progress`   | 응답 | 진행 상황 추적이 활성화된 경우 `enabled`                                                                                                                                               |
| `X-OmniRoute-Session-Id` | 응답 | OmniRoute에서 사용한 유효 세션 ID                                                                                                                                                      |
| `X-OmniRoute-Request-Id` | 응답 | 요청 상관관계 ID(알려진 경우)                                                                                                                                                          |
| `X-OmniRoute-Version`    | 응답 | OmniRoute 빌드 버전(항상 포함됨)                                                                                                                                                       |
| `X-OmniRoute-Cost-Saved` | 응답 | HIT으로 인해 캐시가 절감한 USD 금액(캐시 적중에만 해당)                                                                                                                                |
| `X-OmniRoute-Decision`   | 응답 | 라우팅 추적 정보: `strategy=<name>; provider=<alias>; latency_ms=<n>`(`<name>`은 콤보 전략이며, 콤보가 아닌 요청에서는 `single`) — 완료 응답에 항상 포함됨                             |

> Nginx 참고: 밑줄이 포함된 헤더(예: `x_session_id`)를 사용하는 경우 `underscores_in_headers on;`을 활성화하세요.

#### 요청별 계정 고정

제공자에 여러 연결(계정 또는 키)이 있는 경우 OmniRoute는 일반적으로
계정 선택 전략을 통해 하나를 선택합니다. 대신 요청에서 `x-omniroute-connection`
헤더를 사용하여 특정 연결 하나를 고정할 수 있습니다.

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **ID를 찾는 위치.** 대시보드에서 제공자 페이지
  (**대시보드 → 제공자 → <provider>**)를 열고 연결 행의 `xxxxxxxx…` ID 칩을
  클릭하면 전체 연결 ID가 복사됩니다.
- **이 헤더를 적용하는 요청.** `/v1/chat/completions`, `/v1/messages`,
  `/v1/responses`의 단일 모델 요청(`provider/model`)에 적용됩니다. 콤보는 이 헤더를
  무시하므로, 대신 각 콤보 단계에 지정된 연결을 통해 단계별로 계정을 고정하세요.
- **고정은 선호 사항이 아니라 엄격한 지정입니다.** 고정된 연결만 사용됩니다.
  요청 내에서 오류가 발생하면 해당 계정의 쿨다운이 기록되지만, 동일한 제공자의
  다른 계정으로는 **전환되지 않습니다**.
- **쿨다운과 할당량 상태에 따라 고정이 해제됩니다.** 고정된 연결이 쿨다운 중이거나,
  할당량이 소진되었거나, 할당량 정책에 의해 차단된 동안에는 이후 요청이 고정되지
  않은 트래픽과 동일하게 제공자의 다른 연결로 폴백됩니다.
- **알 수 없거나 비활성화된 ID를 사용하면 실패합니다.** 제공자의 활성 풀에 없는
  ID(삭제되거나 비활성화되었거나 다른 제공자에 속한 ID)를 지정하면 적격 계정이
  남지 않으므로, 요청은 별도의 안내 없이 다른 곳으로 라우팅되는 대신 실패합니다.

Claude Code는 `ANTHROPIC_CUSTOM_HEADERS`를 통해 사용자 지정 헤더를 전송합니다. 이를
`~/.claude/settings.json`의 `env` 블록에 넣거나, 프로젝트마다 다른 계정을 고정하려면
프로젝트 수준의 `.claude/settings.json`에 넣으세요.

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

출처: `src/sse/handlers/chat.ts`(헤더 읽기), `src/sse/services/auth.ts` 및
`src/sse/services/sessionAffinityPin.ts`(고정 해제 및 풀에 없음 검사).

> **비용 텔레메트리 헤더:** 스트리밍이 아닌 성공 응답에는 `X-OmniRoute-*` 비용 텔레메트리 집합도 포함됩니다. 여기에는 `X-OmniRoute-Response-Cost`(USD, 소수점 이하 10자리 고정; 무료이거나 가격이 책정되지 않은 경우 `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit`, `X-OmniRoute-Fallback-Attempts`(0보다 큰 경우에만), 그리고 `X-OmniRoute-Request-Id` 및 `X-OmniRoute-Version`이 포함됩니다. 이러한 헤더는 채팅 완성, `/v1/responses`, `/v1/messages`, **그리고 미디어 엔드포인트**인 `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/moderations`(비용은 항상 `0`)에서 생성됩니다. 미디어 비용은 가격 정보가 있는 경우 양식별(이미지당, 초당, 문자당, 검색 단위당)로 계산되며, 그렇지 않으면 `0`으로 처리됩니다(실패 시 허용).

> **캐시 적중 비용의 의미:** 시맨틱 캐시가 적중하면(`X-OmniRoute-Cache-Hit: true`) 업스트림 호출이 발생하지 않으므로 `X-OmniRoute-Response-Cost`는 `0.0000000000`입니다(적중 결과를 제공하는 데 드는 **증분** 비용). 원래 발생했거나 발생할 예정이었던 비용은 `X-OmniRoute-Cost-Saved`에 별도로 보고됩니다. 청구 데이터 소비자는 `X-OmniRoute-Response-Cost`를 합산해야 하며(캐시 적중에는 비용이 들지 않음), 캐시 분석에서는 `X-OmniRoute-Cost-Saved`를 집계할 수 있습니다.

## 독점 관리형 세션 임대

독점 관리형 세션 임대는 선택적으로 사용하는 클라이언트 중립적 라우팅 계약입니다. 하나의 활성 소유자가
적격한 OmniRoute 연결 하나를 점유합니다. 모델을 임대하거나 OAuth를 요구하거나 특정 클라이언트를
식별하거나 특정 공급자를 요구하지 않습니다.

인증에 사용하는 API 키에는 `lease:exclusive` 범위와 명시적인 비어 있지 않은
`allowedConnections` 목록이 있어야 합니다. 데이터베이스 변경 경계는 키 생성과 부분 업데이트 시
두 필드가 함께 존재하도록 강제합니다.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

성공한 획득, 갱신 및 해제 응답에는 타임스탬프, `state`, 정확한 양의
`generation`이 포함되지만, 선택된 연결이나 자격 증명은 절대 포함되지 않습니다. 갱신 및 해제 시
JSON 본문에 generation을 제공합니다.

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

활성 임대 소유자는 현재 바인딩에 대해 개인정보를 보호하는 표시 메타데이터를 명시적으로 요청할 수 있습니다.

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

이 선택적 상태 작업은 하나의 데이터베이스 트랜잭션에서 불투명한 소유자, 인증된 관리형 API 키 및 정확한
활성 generation으로 펜싱됩니다. `displayName`에는 공백이 제거된 구성된 연결 이름만 사용되며,
안전한 구성 이름이 없으면 `null`입니다. OmniRoute는 이메일이나 생성된 계정 ID를 대신 사용하지
않습니다. 공급자 값은 민감하지 않은 표시 레이블이며 생성된 호환 공급자 식별자가 아닙니다. 자격 증명,
토큰, 쿠키, 원시 연결 또는 API 키 ID, 소유자 해시, 펜싱 시크릿 및 내부 라우팅 데이터는 제외됩니다.

잘못된 키, 잘못된 소유자, 오래된 generation, 누락된 임대, 만료된 임대, 해제된 임대 및 무효화된 임대에 대한 조회는 모두
연결 메타데이터 없이 동일한 `409 LEASE_FENCE_STALE` 오류를 반환합니다. 용량 대기 응답을 받은 클라이언트에는 조회할 활성 바인딩이 없습니다. 라우팅이 활성 임대를 전환할 때는
동일한 generation이 계속 유효하며 상태 조회는 이전 바인딩이 아닌 새 바인딩을 원자적으로 반환합니다.
획득, 갱신, 해제 및 대기 응답이 이전 형식을 유지하므로 기존 클라이언트는 변경되지 않습니다.

이 서버 계약은 기본 OpenAI Codex `/status`를 변경하지 않습니다. 현재 기본 Codex는
모델 공급자와 내장 인증/계정 상태를 보고하지만 임의의 사용자 지정 공급자 계정 메타데이터는 렌더링하지 않습니다.
향후 클라이언트 통합에서는 이 작업을 호출하고 `connection.displayName`을 표시할 방법을
결정해야 합니다.

이후 모든 관리형 추론 요청에는 다음 두 제어 헤더가 모두 포함됩니다.

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

지원되는 각 업스트림 시도 직전에 정확한 소유자, generation, 활성 연결 및 인증된 API 키가
펜싱됩니다. 다른 키가 동일한 연결을 허용하더라도 그 키로 소유자와 generation을 재사용하면
실패합니다. 원시 소유자는 영속화되거나 로깅되거나 요청 스냅샷에 보존되거나 업스트림으로 전달되지 않습니다.

일시적인 경합이 발생하면 HTTP `429`와 `Retry-After`, 그리고 다음 응답이 반환됩니다.

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

이 응답은 일반 적격 집합이 비어 있지 않았고 사용 가능한 모든 후보가 다른 소유자의 활성 임대에 의해
점유되어 있었음을 의미할 뿐입니다. 지원되지 않는 모델/공급자, 정책 불일치, 쿨다운, 할당량,
상태 및 기타 일반적인 적격성 실패에는 기존 OmniRoute 응답이 그대로 유지됩니다.

### `x-omniroute-compression`

요청별 압축 계획 재정의입니다. 우선순위가 가장 높으며 라우팅 조합
재정의, 활성 프로필, 자동 트리거 및 패널 기본값보다 우선합니다. 값은 다음과 같습니다.

| 값            | 효과                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------- |
| `off`         | 이 요청에 압축을 적용하지 않습니다.                                                           |
| `default`     | 패널에서 파생된 기본 프로필입니다(활성 프로필 무시). 손실형 엔진은 비활성 상태로 유지됩니다.  |
| `safe`        | 중복 제거 및 공백 접기만 수행합니다.                                                          |
| `allow-lossy` | 요약과 스타일 재작성을 포함하여 이 요청에 대한 운영자 계획을 유지합니다.                      |
| `engine:<id>` | 활성화된 경우 단일 엔진을 사용합니다(예: `engine:rtk`). 해당 엔진에 대한 요청별 옵트인입니다. |
| `<combo>`     | 이름(대소문자 구분 없음)을 먼저 확인한 다음 ID로 일치시키는 명명된 조합입니다.                |

참고:

- 알 수 없는 값은 무시되며 요청이 거부되는 일은 없습니다. 해석은 일반 운영자 우선순위로 넘어갑니다.
- 여러 조합이 같은 이름을 공유하는 경우 결정론적으로 일치시키려면 조합 **id**를 전달하세요.
- 이름이 `off` 또는 `default`인 조합은 이름으로 선택할 수 없습니다. 해당 키워드가 먼저 해석되기 때문입니다. 그러한 조합은 ID로 참조하세요.
- 마스터 압축 스위치는 절대적인 게이트입니다. 압축이 전역적으로 비활성화되어 있으면 이 헤더로 활성화할 수 없습니다.

적용된 계획은 다음 응답 헤더로 다시 전달됩니다.

```
X-OmniRoute-Compression: <mode>; source=<source>
```

여기서 `<source>`는 `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` 또는 `off` 중 하나입니다.

## 임베딩

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

사용 가능한 제공자: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

카탈로그 ID는 `provider/model` 형식입니다(예: `jina-ai/jina-embeddings-v5-omni-small`). 레지스트리에 있는 Jina 모델의 단축 ID(예: `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`)도 확인됩니다. Jina embed/rerank/classify/segment는 먼저 대시보드의 `jina-ai` 자격 증명을 사용하며, 대시보드 키가 없는 경우에만 `JINA_AI_API_KEY`를 대체 수단으로 사용합니다. `jina-reader` 카드는 Reader / `r.jina.ai` 전용이며(`POST /v1/web/fetch`), 임베딩이나 리랭크를 제공하지 않습니다.

멀티모달 지원을 명시하는 레지스트리 모델은 제공자 중립적인 구조화된 항목도 최대 32개까지 허용합니다. 미디어 항목 유형은 `text`, `image`, `audio`, `video`, `document`입니다. 각 미디어의 `source`는 `{"type":"url","url":"https://..."}` 또는 `{"type":"base64","data":"...","media_type":"..."}`입니다.

Jina v5 Omni(`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano` 및 패밀리 별칭 `jina-ai/jina-embeddings-v5-omni` → omni-small)는 Jina의 네이티브 EmbeddingsV5Request 문서도 허용하며, 해당 문서를 **변경 없이 전달**하여 `https://api.jina.ai/v1/embeddings`로 보냅니다.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

네이티브 `{ image | audio | video | pdf }` 값은 공개 HTTPS URL, `data:` URI 또는 원시 base64일 수 있습니다. OmniRoute는 이러한 객체를 문자열로 변환하거나 네이티브 이미지 URL을 가져오지 않습니다. Jina가 공개 미디어를 직접 가져옵니다. 추가 Jina 필드(`task`, `normalized`, `truncate`, `embedding_type`)도 전달됩니다. 텍스트 전용 Jina SKU는 텍스트가 아닌 문서를 계속 거부합니다.

보안 및 전송 제한:

- 원격 미디어 URL은 공개 HTTPS여야 합니다. 표준 `{type,source:url}` 항목은 서버 측에서 가져오며(리디렉션 재검증, 타임아웃, 크기 제한, 공개 DNS, 연결 고정 적용), 제공자 호출 전에 인라인 처리됩니다. Jina 네이티브 `{image:"https://..."}` 항목은 동일한 공개 HTTPS 검사를 거친 후 그대로 전달되며, Jina가 URL을 가져옵니다.
- 인라인 base64 미디어는 디코딩된 크기를 기준으로 항목당 8 MiB, 요청 전체에서 16 MiB로 제한됩니다.

제공자별 변환(표준 항목은 변경 없이 전달되지 않음):

- Jina 멀티모달 모델: 각 최상위 항목은 인라인 미디어에 데이터 URI를 사용하는 하나의 모달리티 키 기반 객체(`text` / `image` / `audio` / `video` / `pdf`)가 되며, 최상위 항목당 하나의 벡터를 생성합니다.
- Gemini Embedding 2 패밀리: 하나의 최상위 배열은 `content.parts`(`text` 또는 `inline_data`)를 포함하는 단일 네이티브 `models/{model}:embedContent` 요청이 됩니다.
- llama.cpp(`llama-cpp/<model>`, 로컬 서버에서 로드한 모든 모델): 표준 `text` 항목은 일반 문자열이 되고, `image` / `audio` / `video`는 각각 하나의 `{"content": [part]}` 객체가 됩니다. 이때 인라인 데이터와 함께 llama-server의 채팅 콘텐츠 파트(`image_url`, 형식이 `wav` / `mp3` / `flac`인 `input_audio`, `input_video`)를 사용하며, 최상위 항목당 하나의 벡터를 생성합니다. 서버는 `--embedding --mmproj …` 옵션으로 실행되어야 하며, 프로젝터가 없으면 서버 자체에서 미디어를 거부합니다. `document`는 지원되지 않습니다.
- 명시적인 모달리티 메타데이터가 없는 알 수 없거나 동적인 모델은 구조화된 입력을 HTTP 400으로 거부합니다.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

지원되지 않는 모델/모달리티 조합은 항목을 강제로 변환하는 대신 HTTP 400을 반환합니다. 기존 문자열/토큰 요청의 입력 외 확장 필드는 계속 변경 없이 전달됩니다.

```bash
# 모든 임베딩 모델 나열
GET /v1/embeddings
```

## 이미지 생성

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

사용 가능한 제공업체에는 OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (로컬), ComfyUI (로컬)가 포함됩니다.

`n`은 `data[]`에 `n`개의 이미지를 반환합니다. 업스트림 API가 호출당 하나의 이미지를 반환하는 제공업체
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI)의 경우 `n`번의 개별 업스트림 호출이 수행되며, 동시에 진행되는 호출은 최대 4개입니다.
고정된 `seed`는 호출 인덱스에 따라 오프셋됩니다(`seed`, `seed + 1`, …). 따라서 이미지는 서로 다르지만
재현 가능성은 유지됩니다. `n`의 최댓값은 10입니다. 호출 중 하나라도 실패하면 전체 요청이 실패합니다. 팬아웃
형식 목록은
`open-sse/handlers/imageGeneration/fanOut.ts`의 `SINGLE_IMAGE_FANOUT_FORMATS`에 있습니다.

ZenMux는 기존 API 키 연결을 재사용하며 `zenmux/` 또는 `zm/` 접두사를 허용합니다.

- `zenmux/openai/gpt-image-2`는 ZenMux의 OpenAI Images API를 사용합니다. 옵션에는 `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background`, `response_format`이 포함됩니다.
- `zm/meta/muse-image-1.0`과 같은 다른 게시자의 경우 ZenMux의 Vertex AI `:predict`
  엔드포인트를 사용합니다. `n`은 `sampleCount`에, `aspect_ratio`는 `aspectRatio`에, `image_size`
  (`1K`, `2K`, `4K`)는 `sampleImageSize`에 매핑됩니다. 픽셀 단위의 `size`는 종횡비만 제공하며,
  픽셀 크기를 보장하지 않습니다. 지원되는 비율, 해상도, 개수는 모델마다 다릅니다.
- `zm/inclusionai/ming-image-0.1-design`은 자체적으로 크기를 선택합니다. `size`,
  `aspect_ratio`, `image_size`를 생략하세요. 명시적인 값을 지정하면 HTTP 400이 반환됩니다. `output_format`을
  사용하여 PNG, JPEG, WebP를 요청할 수 있습니다.

이 통합은 텍스트-이미지 생성을 지원하지만 참조 이미지 편집은 지원하지 않습니다. Vertex
출력은 `data[].b64_json`으로 정규화됩니다. `response_format: "url"`은 업스트림
HTTPS URL을 반환하며, 이미지 바이트만 사용할 수 있는 경우에는 base64 데이터 URL을 반환합니다. 비어 있거나 필터링된 출력은
빈 성공 응답 대신 오류를 반환합니다. 모델 액세스 권한은 ZenMux 계정에 따라 달라집니다.
[ZenMux의 Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) 및
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image)를 참조하세요.

```bash

GET /v1/images/generations
```

## 문서 OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`은 `provider/model` 접두사를 통해 OCR 제공업체를 선택합니다. 접두사가 없는 모델 ID(예:
`mistral-ocr-latest`)는 등록된 제공업체로 확인되며, `model`을 생략하면 기본값으로
Mistral(`mistral-ocr-latest`)이 사용됩니다. 등록된 제공업체(`open-sse/config/ocrRegistry.ts`)는 다음과 같습니다.

| 제공업체 ID                   | 모델 ID              | `model` 값                                                             | 참고                                                                                                        |
| ----------------------------- | -------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (또는 접두사가 없는 `mistral-ocr-latest`) | 동기식 — 단일 업스트림 호출의 응답이 직접 반환됩니다.                                                       |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                            | 비동기 업스트림(`analyze` + 폴링) — 아래를 참조하세요.                                                      |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                | Vertex AI의 `openapi/chat/completions` 파트너 엔드포인트를 통한 동기식 처리 — 인증/URL은 아래를 참조하세요. |

세 제공업체 모두 동일한 Mistral 형식의 본문으로 응답합니다.

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence 폴링 흐름

Azure Document Intelligence의 `analyze` API는 비동기식입니다. 최초 요청은 본문 대신
`Operation-Location` 헤더를 반환하며, 결과를 얻으려면 폴링해야 합니다. 핸들러
(`open-sse/handlers/ocr.ts`)는 최대 30회까지 1초마다 해당 URL을 폴링합니다. `ok`가 아닌 폴링 응답이나
`"failed"` 상태가 발생하면 즉시 실패하며(폴링을 계속하지 않음), 허용된 시도 횟수를 모두 소진한 후에도
작업이 계속 실행 중이면 `504`를 반환합니다. 최종 Azure 응답은 호출자에게 반환되기 전에
Mistral에서 사용하는 것과 동일한 `pages`/`markdown` 형식으로 정규화되므로, 클라이언트 코드에서
제공업체별로 별도 처리할 필요가 없습니다.

### Vertex AI DeepSeek OCR 인증 및 엔드포인트 확인

`vertex-deepseek-ocr`은 OmniRoute가 채팅/이미지 트래픽에 대해 이미 지원하는 것과 동일한
Vertex AI 인증(`open-sse/executors/vertex.ts`)을 재사용합니다. 연결의 API 키는
Service Account JSON 자격 증명(JWT bearer 흐름을 통해 수명이 짧은 OAuth 액세스 토큰으로 교환됨)이거나
그대로 사용되는, 이미 발급된 OAuth 액세스 토큰입니다. 업스트림 엔드포인트 URL은 연결의 프로젝트와
리전을 기반으로 구성되는 Vertex의 범용 `openapi/chat/completions` 파트너 엔드포인트입니다.
명시적인 `providerSpecificData.project`/`providerSpecificData.region`이 항상 우선합니다.
그렇지 않으면 프로젝트는 Service Account JSON의 `project_id`에서 파생되고, 리전은
기본적으로 `us-central1`로 설정됩니다. 두 확인 작업 모두 `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`)에서 수행되며,
`handleOcr`로 전달하기 전에 `src/app/api/v1/ocr/route.ts`에서 사용됩니다.

### 모델 가격 (`pricing`)

OmniRoute가 모델의 가격을 알고 있는 경우 항목에 `pricing` 객체가 포함됩니다. 가격은
비용 계산에 사용되는 가격표, 즉 기본 제공 기본값, 동기화된 가격 및
`/api/pricing`을 통해 설정된 재정의 값에서 가져옵니다. 이는 정가이므로 구독형 제공자에도
토큰당 가격이 표시됩니다.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| 필드                                                            | 단위                      | 참고                                                                                                                                        |
| --------------------------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | 토큰당 USD, 10진수 문자열 | OpenRouter 호환이며 지수 표기법을 사용하지 않습니다. 두 캐시 필드는 캐시 가격이 있는 경우에만 표시됩니다.                                   |
| `input`, `output`, `cached`, `cache_creation`                   | 100만 토큰당 USD, 숫자    | 이전 카탈로그 버전의 필드로, 기존 클라이언트를 위해 유지됩니다. 가격 행에 `reasoning` 및 `long_context`가 있는 경우 해당 필드도 표시됩니다. |

- **콤보**에는 처음으로 표시되는 대상의 가격이 적용됩니다. 기본 제공 `auto/*` 콤보는
  요청 시 대상을 선택하므로 `pricing`이 없습니다.
- **무료 모델**은 가격이 0인 경우 `"0"`(및 `0`)을 표시합니다. 가격 행이 없는 모델도
  카탈로그에 무료로 표시되어 있거나(`free: true`) 기본 제공 무료 모델
  카탈로그에 포함되어 있으면 `"0"`을 표시합니다.
- **알 수 없는 가격:** 항목에 `pricing` 키가 없습니다.
- **크레딧 기준 과금 제공자**(예: Kiro)는 토큰당이 아니라 요청당 요금을 청구합니다. 해당
  항목은 이전부터 있던 숫자형 100만 토큰당 필드를 유지하며 토큰당 문자열 필드는 포함하지 않습니다.
- **변형 모델**(추론 노력 ID, 비사고 별칭, 디스커버리 및 게이트웨이 미러)은
  라우팅 대상 모델의 가격을 복사합니다.
- 필드에는 기본 요율만 포함됩니다. 긴 컨텍스트 티어(숫자형 `long_context` 필드)와
  서비스 티어 배수(예: Codex fast 또는 flex)는 `prompt`나
  `completion`을 변경하지 않습니다.
- 이 객체는 `x-api-key`와 `anthropic-version`을 사용하는 Anthropic 스타일
  요청을 포함해 모든 인증 방식에서 동일합니다(응답은 `{ "object": "list",
"data": [...] }` 형식을 유지합니다). 구현: `src/app/api/v1/models/catalogPricing.ts`.

### 모델 ID 접두사 (`?prefix=`)

대부분의 모델은 **제공자 접두사**를 사용하여 노출됩니다. 사용할 접두사는
`MODELS_CATALOG_PREFIX_MODE` 기능 플래그로 제어되며, 쿼리 매개변수를 사용해 **요청별로**
재정의할 수 있습니다. 이는 모든 사용자에게 적용되는 서버 전체 설정을 변경하지 않고도
깔끔한 목록을 원하는 클라이언트에 유용합니다.

```bash
GET /v1/models?prefix=alias        # 모델당 하나의 ID — 짧은 별칭 접두사
GET /v1/models?prefix=dual         # 두 형식 모두(서버 기본값)
GET /v1/models?prefix=canonical    # 전체 제공자 ID 접두사만
```

| 모드        | 출력                                                     | 참고                                                                                                                                                                            |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **및** `claude/claude-sonnet-4-6` | **기본값입니다.** 두 ID 모두 동일한 모델로 라우팅됩니다. 두 형식 중 하나를 하드코딩한 클라이언트 설정이 계속 작동하도록 유지됩니다. 카탈로그 크기가 약 두 배로 늘어납니다.      |
| `alias`     | `cc/claude-sonnet-4-6`                                   | 모델당 하나의 항목입니다. 별도의 별칭이 없는 제공자도 해당 항목을 계속 출력하므로 누락되는 항목이 없습니다.                                                                     |
| `canonical` | `claude/claude-sonnet-4-6`                               | 전체 제공자 ID 접두사 아래에 모델당 하나의 항목이 표시됩니다. 별도의 별칭이 없는 제공자(예: `antigravity/…`, `agy/…`)도 여기에서 단일 ID를 출력하므로 누락되는 항목이 없습니다. |

`dual` 모드 미러는 쿼리 매개변수 없이도 식별할 수 있습니다. 기본 ID를 가리키는 `parent`
필드가 포함되어 있기 때문입니다.

모델 선택기를 렌더링하는 클라이언트는 `?prefix=alias`를 요청해야 합니다. 이는
[OmniCopilot VS Code 확장 프로그램](../guides/VSCODE-COPILOT.md)에서 사용하는 방식입니다.

### 디스커버리 필터 (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models`는 선택적으로 적용되는 디스커버리 필터를 지원합니다. 이러한 필터를 지정하지 않으면 응답은
변경되지 않습니다. 필터는 호출자에게 이미 표시되는 카탈로그의 범위를 좁히며(API 키 권한이 먼저 적용됨),
OpenAI 스타일의 `limit` / `after` 페이지네이션보다 먼저 실행됩니다.

```bash
GET /v1/models?capability=vision&capability=tool_calling   # 나열된 모든 기능이 true여야 함
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # 카탈로그 `type`; 값이 없는 행은 `chat`
GET /v1/models?q=sonnet&limit=10                           # ID 또는 이름에서 대소문자를 구분하지 않고 일치
```

| 매개변수      | 값                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | 음이 아닌 정수이며, `context_length`와 비교됨                                                       |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1~200자                                                                                             |

알 수 없는 값이나 음이 아닌 정수가 아닌 `min_context`(예: `1.5`)를 지정하면
HTTP `400`이 반환되며 메시지에 유효한 값이 나열됩니다. 구현:
`src/app/api/v1/models/catalogFilters.ts`.

### 모델 후보 목록 (`POST /v1/models/query`)

`POST /v1/models/query`는 `GET /v1/models`와 동일한 카탈로그에서 동일한
인증 및 키별 가시성을 적용하여 결정론적으로 생성된 짧은 목록을 반환합니다.

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

모든 필드는 선택 사항입니다. `capabilities`와 `exclude`에는 배열 또는 쉼표로 구분된 문자열을 사용할 수 있으며,
`max_output`은 `max_output_tokens`와 비교됩니다. 결과는 먼저 `owned_by`, 그다음 `id`를 기준으로 정렬됩니다.
`limit`의 기본값은 `20`이며 `100`을 초과하는 값은 `100`으로 제한됩니다. 잘못된 JSON, 알 수 없는
필드 또는 유효하지 않은 값을 지정하면 HTTP `400`이 반환됩니다.

### 개별적으로 숨겨진 채팅 모델

제공자 페이지에서 **숨김**으로 표시된 모델은 카탈로그에서 제외되며, 명시적으로 요청하면
HTTP `404` / `model_not_found`로 거부됩니다. 이 검사는 제공자 별칭, 호환 제공자 노드 접두사 및
연결 기본값을 포함하여 확인된 제공자와 모델을 사용합니다. 콤보는 숨겨진 대상을 건너뛰고 표시되는 형제 모델을 사용할 수 있으며,
실행 가능한 대상이 남아 있지 않으면 동일한 오류 코드를 반환합니다. 숨김을 해제하면 다음
요청부터 적용됩니다. 이미지 전용 가시성 재정의는 동일한 ID를 가진 채팅 모델을 숨기지 않습니다.

이 개별 모델 설정은 명시적 디스패치를 유지하면서 카탈로그
표시 및 자동 라우팅 후보를 필터링하는 [모델 노출 허용/거부 목록](../routing/MODEL_EXPOSURE_LIST.md)과 별개입니다.
API 키 모델 권한도 계속 독립적으로 적용됩니다. 기본 카탈로그 접두사 모드는 `dual`로 유지됩니다.

### 사고 비활성화 모델 변형

사고를 지원하는 Claude 모델의 경우 `/v1/models`는 ID 앞에 `claude-3-omniroute-no-thinking/`이 붙은 **사고 비활성화** 변형도 표시합니다.

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

이 ID를 선택하면(예: 항상 `thinking` 블록을 첨부하는 Claude Code 구성에서) 추론이 억제된 실제 `<provider>/<model>`로 다시 확인됩니다. 즉, `/v1/messages` 경로에서는 `thinking:{type:"disabled"}`가 사용되고, `/v1/chat/completions` 경로에서는 `reasoning`/`reasoning_effort` 필드가 제거됩니다. 이 변형은 사고를 지원하면서 **동시에** `disabled`를 준수하는 Claude 계열 모델에만 나열됩니다(따라서 `disabled`를 거부하는 적응형 전용 모델 등은 제외됨). 운영자는 `ModelSpec.noThinkingAlias`를 통해 모델별로 이 변형을 강제로 활성화하거나 비활성화할 수 있습니다.

## ElevenLabs 오디오 생성

ElevenLabs API 키를 사용하여 OmniRoute에 `elevenlabs` 공급자 연결을 구성하세요. 클라이언트는 자신의 **OmniRoute** 키(`Authorization: Bearer $OMNIROUTE_API_KEY`)로 인증하며, 게이트웨이는 저장된 공급자 키를 `xi-api-key`로 제공합니다. ElevenLabs 키를 게이트웨이 Bearer 토큰으로 전송하지 마세요.

| 메서드 | 경로                        | 응답                                   | API 키 엔드포인트 범주 |
| ------ | --------------------------- | -------------------------------------- | ---------------------- |
| POST   | `/v1/sound-generation`      | 네이티브 오디오 바이트                 | `elevenlabs`           |
| POST   | `/v1/music`                 | 네이티브 오디오 바이트                 | `music`                |
| POST   | `/v1/music/stream`          | 스트리밍 오디오 바이트                 | `music`                |
| POST   | `/v1/music/detailed`        | 네이티브 멀티파트 오디오 및 구성 계획  | `music`                |
| POST   | `/v1/music/detailed/stream` | 네이티브 SSE 메타데이터 및 오디오 청크 | `music`                |
| POST   | `/v1/music/plan`            | JSON 구성 계획                         | `music`                |

이 엔드포인트들은 기존 `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/voices`, `/v1/text-to-speech/{voiceId}` 및 `/v1/speech-to-text` 경로를 보완합니다. `output_format` 및 `enable_logging` 같은 네이티브 JSON 필드와 쿼리 매개변수는 그대로 유지됩니다. `/v1/music/detailed` 응답은 멀티파트 경계를 유지하므로 멀티파트로 파싱하세요. `/v1/music/detailed/stream`은 구성 메타데이터 및 base64 오디오 청크가 포함된 SSE 이벤트를 `text/event-stream`으로 반환합니다. 여섯 경로 모두 CORS 프리플라이트를 지원합니다.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# 짧은 음향 효과입니다. 길이: 0.5~30초.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# 음악 길이는 밀리초 단위로 지정합니다: 3000~600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

점진적으로 오디오를 전송하려면 동일한 JSON 본문과 함께 `/v1/music/stream`을 사용하세요. 구성 요청에는 `prompt` 또는 `composition_plan` 중 정확히 하나만 사용할 수 있습니다. `/v1/music/plan`에는 `prompt`가 필수이며, 선택적으로 `source_composition_plan`을 사용할 수 있습니다. 네이티브 스키마는 추가 공급자 필드를 유지하므로 구성 계획 버전과 미세 조정 옵션이 ElevenLabs에 전달됩니다.

통합 `/v1/music/generations` 엔드포인트는 `elevenlabs/music_v1`, `elevenlabs/music_v2` 및 `elevenlabs/music_v2_5`도 허용합니다. 활성화된 ElevenLabs 연결이 있으면 이러한 모델이 음악 카탈로그에 표시됩니다. 이 엔드포인트는 `{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`를 반환합니다. `duration` 필드는 초 단위이며 `music_length_ms`에 매핑됩니다. `music_length_ms`를 명시적으로 지정하면 해당 값이 우선합니다. `instrumental`은 `force_instrumental`에 매핑되며, 네이티브 필드를 지정하면 해당 필드가 우선합니다. 스트리밍에는 네이티브 스트리밍 엔드포인트를 사용하고, 구성 계획만을 기반으로 하는 요청에는 네이티브 구성 엔드포인트를 사용하세요.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

업스트림 호출 전에 엔드포인트, 모델, 예산 및 연결 제한이 적용됩니다. 네이티브 경로는 요금제 제한에 대한 `402` 및 할당량 제한에 대한 `429`를 포함하여 업스트림 상태 코드와 오류 본문을 변경하지 않고 반환합니다. `character-cost`, `song-id`, `request-id` 및 `retry-after` 헤더가 있으면 그대로 유지됩니다. 무료 크레딧 잔액이 있다고 해서 모든 음악 모델, 출력 형식 또는 API 기능에 접근할 수 있는 것은 아닙니다. 각 요청에 대한 사용 권한은 ElevenLabs가 결정합니다. 통합 엔드포인트는 OmniRoute의 정규화된 오류 엔벌로프에서 오류 상태 코드를 유지합니다.

업스트림 계약: [음향 효과](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert), [음악 구성](https://elevenlabs.io/docs/api-reference/music/compose) 및 [스트리밍 음악 세부 정보](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

모든 POST 경로는 동일한 형식을 따릅니다: `Bearer your-api-key` + Zod로 검증된 JSON 본문(`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` 등, `src/shared/validation/schemas.ts` 참조). 스키마 검증에 실패하면 4xx가 반환됩니다.

`Authorization: Bearer ...`를 첨부할 수 없는 클라이언트를 위해 OmniRoute는 쿼리 문자열 호환성(`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) 또는 아래에 설명된 전용 `/api/v1/vscode/{token}/...` 엔드포인트를 통해 URL에 포함된 API 키도 허용합니다.

```bash
# 재순위 지정(클라우드 레지스트리 공급자 또는 "<prefix>/<model>" 형식의 OpenAI 호환 공급자 노드)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina 분류(Foundation API 자격 증명)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina 세그멘터
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina 검색(s.jina.ai; 공급자 별칭: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# 콘텐츠 조정
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg(또는 요청된 형식) 본문 반환
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS에는 언어와 음성이 필요합니다. `language`의 기본값은 "en"이며, 음성이
# 누락되었거나 OpenAI 기본 음성 이름(alloy, nova, …)이면 "Adrian"으로 설정됩니다
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# 이미지 편집(multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# 동영상/음악 생성(공급자 접두사가 포함된 모델 ID)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **리랭크 공급자 노드:** `POST /v1/rerank`는 `<node-prefix>/<model>` 형식으로 지정된 OpenAI 호환 공급자 노드
> (oMLX, vLLM, 게이트웨이 뒤의 Infinity 및 TEI 등)에도 요청을 라우팅합니다. 루프백
> 노드(`localhost`, `127.0.0.1`, `172.16.0.0/12`)는 항상 사용할 수 있으며, 운영자가
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`에 나열한 호스트 이름도 사용할 수 있습니다(예:
> `http://reranker:8080/v1`과 같은 Docker/Compose 서비스 이름. 이러한 노드는 항상 직접 호출되며
> `HTTP(S)_PROXY` 또는 연결에 고정된 프록시를 거치지 않습니다). 그 외 호스트의 노드
> (LAN 장비 또는 Tailscale 피어)는 운영자가 `RERANK_REMOTE_PROVIDER_NODES` 기능 플래그를
> 활성화하고 노드의 기본 URL이 공급자 아웃바운드 URL 정책
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`)을 통과하는
> 경우에만 사용할 수 있습니다. 메모리 엔진의 리랭크 단계는 루프백을 통해 이 경로를 호출하므로,
> 메모리 설정의 `rerankProviderModel`에도 동일한 규칙이 적용됩니다.
>
> **로컬 서버 형식:** 노드는 `<base>/v1/rerank`에서 호출되며, 404가 발생하면
> `<base>/rerank`(Infinity, TEI)에서 호출됩니다. 업스트림 본문에는 Cohere/OpenAI 표기
> (`documents`, `return_documents`)와 TEI 표기(`texts`, `return_text`)가 모두 포함되며,
> 업스트림 응답은 Cohere 엔벌로프로 정규화됩니다. TEI의 단순
> `[{index, score, text}]`, 경량 게이트웨이의 `{results: [{index, score}]}`, Voyage 형식의
> `{data: [...]}`는 모두 클라이언트에 `{results: [{index, relevance_score, document?}]}`
> 형식으로 반환되며, 점수순으로 정렬되고 `top_n`개로 제한됩니다.

> **공급자 노드 검색:** OpenAI 호환 공급자 노드의 모델은 노드 접두사 아래의 `GET /v1/models`에
> 표시됩니다. 엔드포인트 메타데이터가 없는 행(로컬 `/v1/models` 목록에서 일반적)은
> 노드의 `apiType`을 상속하므로, 기본값이 채팅으로 설정되는 대신 `embeddings` 노드의 모델은
> `type: "embedding"`이 되고 `rerank` 노드의 모델은 `type: "rerank"`가 됩니다. 동기화되었거나
> 수동으로 추가된 행에 명시된 `supportedEndpoints`가 있으면 여전히 그것이 우선합니다.

## Files API

배치 입력/출력 및 파일 용도별 업로드를 위한 OpenAI 호환 파일 엔드포인트입니다.

| 메서드 | 경로                     | 설명                                                                                                        |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | 파일 업로드(multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — 최대 512 MiB |
| GET    | `/v1/files`              | 인증된 API 키의 파일 목록 조회                                                                              |
| GET    | `/v1/files/[id]`         | 파일 메타데이터 조회                                                                                        |
| DELETE | `/v1/files/[id]`         | 파일 삭제                                                                                                   |
| GET    | `/v1/files/[id]/content` | 원시 파일 본문을 스트리밍하여 반환                                                                          |

**인증:** Bearer API 키 — 파일은 `getApiKeyRequestScope`를 통해 API 키별로 범위가 지정됩니다. 키는
자신의 파일만 조회, 다운로드 및 삭제할 수 있습니다. 키가 없는 대시보드 세션은
전체 인스턴스를 조회할 수 있습니다. 소유자가 없는 파일(익명 또는 대시보드 세션 업로드)은 모든
비세션 호출자의 접근이 거부됩니다. `GET /v1/files`는 `REQUIRE_API_KEY=false`인 경우에도 모든 테넌트의
파일을 나열하는 대신 익명 호출자 및 확인되지 않는 제시된 키에 대해 `401`을 반환합니다

| DELETE | `/v1/batches/[id]`        | 완료/실패한 배치 삭제                                                                           |
| POST   | `/v1/batches/[id]/cancel` | 진행 중인 배치 취소                                                                             |

**인증:** Bearer API 키. 배치는 파일과 동일한 세 가지 규칙에 따라 API 키별로 범위가
지정됩니다. 즉, 자신의 키에만 접근할 수 있고, 대시보드 세션은 인스턴스 전체에 접근할 수 있으며, 소유자가 null인 레코드는
모든 비세션 호출자의 접근이 거부됩니다(조회, 삭제, 취소 및 생성 시 `input_file_id` 검사).
`GET /v1/batches`는 `REQUIRE_API_KEY=false`인 경우에도 익명 호출자에게 `401`을 반환합니다.

## API 검색

Web/search 공급자 추상화(Tavily, Brave, Exa, Serper 등).

| 방법 | 길                     | 설명                                                                                  |
| ---- | ---------------------- | ------------------------------------------------------------------------------------- |
| GET  | `/v1/search`           | 구성된 검색 공급자 + 기능 나열                                                        |
| POST | `/v1/search`           | `v1SearchSchema` 로 검증된 — 본문 검색 쿼리를 실행하고 caching/coalescing 지원합니다. |
| GET  | `/v1/search/analytics` | 공급자별 hit/latency/cache 통계                                                       |

**인증:** 베어러 API 키(`extractApiKey` + `isValidApiKey`). `enforceApiKeyPolicy` 통해 시행되는 검색 정책.

### 엑사와 타빌리 `provider_options`

Exa와 Tavily는 네임스페이스 백( `provider_options.exa` (또는 `provider_options["exa-search"]`) 및 `provider_options.tavily` (또는 `provider_options["tavily-search"]`))에서 공급자별 필드를 읽습니다. 아래 키만 전달됩니다. 각각은 `open-sse/handlers/search/providerOptionsPassthrough.ts` 의 자체 Zod 스키마와 비교하여 검사되며 잘못된 유형의 키는 삭제됩니다. auth, base URL, `stream` 및 `outputSchema` 를 포함한 다른 모든 키는 무시됩니다. 다른 공급자(`cx`, `depth`, ...)에서 사용하는 일반 키는 이전과 같이 작동합니다.

| 공급자 | 최상위 필드                                                                                                                                                                                                                                                                                                                                                               | 중첩됨                                                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 엑사   | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (플랫 프리미티브), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                              | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` 기본 `{ text: true, highlights: true }` 위에 병합되었습니다. |
| 타빌리 | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                          |

일반 필드는 항상 승리합니다: `query`, `max_results`, `filters` (도메인), `country` 및 `search_type` 에서 파생된 주제. Exa에서 `search_type: "news"` `category: "news"` 유지합니다. Tavily는 `search_type: "finance"` (`topic: "finance"`)도 허용합니다.

Firecrawl 검색 비용은 반환된 결과 10개의 시작 블록당 $0.002(2크레딧), 호출당 최소 하나의 블록( [Firecrawl 청구](https://docs.firecrawl.dev/billing) )으로 기록됩니다. 11개 결과 비용은 $0.004입니다.

일반 `time_range` 이제 두 공급자 모두에 도달합니다. Exa는 `startPublishedDate` (ISO 타임스탬프)를 가져오고 Tavily는 `start_date` (`YYYY-MM-DD`)를 가져옵니다. `provider_options` 의 명시적인 날짜는 매핑된 날짜보다 우선합니다.

Exa 결과는 `id`, `highlight_scores`, `summary`, `subpages`, `entities` 및 `extras` `provider_raw` 에 유지합니다. Tavily 결과는 `images` 및 `favicon` 유지합니다.

링크업 검색 비용은 `depth` `provider_options` 또는 연결 설정에서 가져온 것인지 여부에 관계없이 `depth` `fast` 및 `standard` 의 경우 $0.005, `deep` 의 경우 $0.05로 기록됩니다( [링크업 가격](https://docs.linkup.so/pages/documentation/development/pricing) ).

Exa `type: "lite"` (Exa 3.0)는 더 작은 필드 집합을 허용하고 다른 필드가 설정되면 전체 요청을 거부합니다. 라이트의 경우 `additionalQueries`, `systemPrompt` 및 `text` 및 `highlights` 제외한 모든 `contents` 키는 호출 전에 삭제됩니다. 더 이상 사용되지 않는 `subpages`, `subpageTarget`, `highlights.numSentences` 및 `highlights.highlightsPerUrl` 는 더 이상 전달되지 않습니다.

비용 계산은 평면 레지스트리 `costPerQuery` 입니다. 단, Exa의 자체 가격을 따르는 Exa는 다음과 같습니다. `auto` (및 레거시 `fast`)의 경우 호출당 $0.007, `lite` (및 레거시 `instant`)의 경우 $0.004, 10개 결과 포함. 추가 결과당 $0.001; `contents.summary` 설정된 경우 반환된 결과당 $0.001입니다. Tavily는 `search_depth` `basic`, `fast` 및 `ultra-fast` 에 대해 1 크레딧($0.008), `advanced` ( [Tavily API 크레딧](https://docs.tavily.com/documentation/api-credits) )에 대해 2 크레딧($0.016)으로 기록됩니다. Tavily가 고급으로 업그레이드한 `auto_parameters: true` 사용한 통화는 여전히 1크레딧으로 기록됩니다.

## Web Fetch API

구성된 웹 가져오기 제공자(Firecrawl, Jina Reader, Tavily Extract, TinyFish Fetch,
Nimble Extract, Parallel Extract)를 통해 URL에서 콘텐츠를 추출합니다.

Parallel Extract(`parallel-search`, Parallel Search와 동일한 API 키)는 Markdown만
반환합니다. 다른 `format`을 사용하면 `400`이 반환되며, 콘텐츠는 100,000자로 제한됩니다.
대상 페이지 자체를 추출할 수 없는 경우 업스트림은 이를 HTTP 200 응답 내부에 보고하며,
OmniRoute는 이를 고정 메시지가 포함된 `422`로 노출합니다.

| 메서드 | 경로            | 설명                                                       |
| ------ | --------------- | ---------------------------------------------------------- |
| POST   | `/v1/web/fetch` | URL 가져오기/스크래핑 — 본문은 `v1WebFetchSchema`로 검증됨 |

**인증:** Bearer API 키(`extractApiKey` + `isValidApiKey`). 정책은 `enforceApiKeyPolicy`를 통해 적용됩니다.

**할당량 인식 폴백(#8297):** 명시적인 `provider`가 지정되지 않은 경우, 풀
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`)을
고정된 우선순위(우선 채우기)로
순회합니다. 속도 제한에 도달했지만 구성은 완료된 제공자는 요청을 즉시 중단하는 대신
건너뛰며, 재시도 가능한 오류나 할당량 관련 업스트림 오류(HTTP 429는 항상 해당,
Firecrawl/Tavily/TinyFish의 할당량 방식 무료 티어에서는 402/403도 해당 —
Jina Reader에는 적용되지 않으며, 단순한 400 잘못된 요청에는 절대 적용되지 않음)가 발생하면
요청 시점에 아직 시도하지 않은 자격 증명이 있는 다음 제공자로 넘어갑니다. 풀의 모든
제공자가 소진되면 엔드포인트는 이전의 일반적인 `400` 대신 단일 `429`
(`Retry-After` 헤더 포함)를 반환합니다. 명시적인 `provider`가 요청된 경우에는
자동 폴백이 **없습니다**. 속도 제한에 도달했거나 실패한 명시적 제공자의 자체 오류가
그대로 노출됩니다(속도 제한인 경우 `429`, 그 외에는 업스트림 상태).

## WebSocket 스트리밍

```bash
GET /v1/ws?handshake=1
```

WebSocket 업그레이드 핸드셰이크를 검증하고 유선 프로토콜 예시 메시지(`request`, `cancel`)를 반환합니다. 실제 WS 프레임은 Next.js 라우트 테이블 외부에 있는 번들 WS 서버에서 처리됩니다.

**인증:** 핸드셰이크 중 Bearer API 키를 사용합니다.

### WebSocket을 통한 Responses API(codex 전용)

```bash
# HTTP API와 동일한 호스트:포트(기본값 20128)를 사용하고 연결을 업그레이드합니다.
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (또는: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# 첫 번째 프레임은 반드시 response.create여야 합니다.
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket 프록시는 **오직 `codex`에만** 연결됩니다(ChatGPT
백엔드). 이 프록시는 API/대시보드와 동일한 포트에서 `/v1/responses`,
`/responses`, `/api/v1/responses` 경로를 수신합니다. 첫 번째 `response.create`
프레임에서 내부 `codex-responses-ws` 브리지를 통해 인증 및 준비를 수행하고, codex
OAuth 연결을 선택한 다음, `wreq-js` 전송 계층을 통해
`wss://chatgpt.com/backend-api/codex/responses`로 터널링합니다.
**codex가 아닌 모델은 거부됩니다**(`codex_ws_provider_required`).
할당량 공유 라우팅에는 `model: "qtSd/<group>/codex/<model>"`을 사용하세요. 구현 위치는
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`입니다.

**인증:** 핸드셰이크 중 Bearer API 키를 사용합니다. 번들 HTTP 서버(`server-ws.mjs`)가
활성 엔트리포인트여야 합니다(`app/server-ws.mjs`가 존재하면 기본적으로 활성화됨).

#### 모델 ID: `codex/` 접두사 없이 순수 ChatGPT ID 사용

OpenAI **Codex CLI**는 `supports_websockets = true`일 때 클라이언트 측에서
모델 이름을 검증하며, `codex/gpt-5.5`와 같이 제공자 접두사가 붙은 ID를
**거부합니다**(`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). **접두사 없는** ID(예: `gpt-5.5`)를 전송하세요. OmniRoute의
브리지는 codex 전용이므로, 접두사 없는 `gpt-5.5`가 HTTP를 통해서는 다른 제공자로
라우팅되더라도 업스트림으로 터널링하기 전에 접두사 없는 ID를 codex 모델로 다시
해석합니다(`resolveCodexWsModelInfo`).

#### OpenAI Codex CLI 구성

WebSocket을 지원하는 사용자 지정 제공자를 `~/.codex/config.toml`에 추가하여
Codex CLI가 OmniRoute를 가리키도록 설정하세요(기존 구성을 건드리지 않으려면 별도의
`CODEX_HOME`을 사용하세요).

```toml
model = "gpt-5.5"                 # 접두사 없는 ID — "codex/gpt-5.5"가 아님
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # 후행 슬래시 없음. WS URL은 이 값에서 파생됨(프로덕션에서는 https/wss 사용)
wire_api = "responses"                    # 2026년 2월 이후 지원되는 유일한 값
supports_websockets = true                # Responses-over-WS 전송 활성화
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API 키(Bearer)를 보관
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API 키(REQUIRE_API_KEY=false이면 아무 키나 가능)
codex exec "Responda apenas: PONG"
```

CLI는 `base_url + /responses`를 WebSocket으로 업그레이드하며, OmniRoute는 이를
선택된 codex OAuth 연결로 터널링합니다. 로컬 서버를 대상으로 엔드 투 엔드 검증을
완료했습니다. ChatGPT는 `codex.rate_limits` + `response.created`를 반환하고
완료 응답을 스트리밍합니다.

## 셀프서비스 사용량 조회(`/api/usage/om-usage`)

모든 API 키는 관리 인증 없이 **자체** 사용량과 할당량을 조회할 수 있습니다. 클라이언트(CLI, OmniCopilot 패널)는 이 엔드포인트를 사용하여 키 보유자에게 사용 비용을 표시합니다.

```bash
# 텍스트 형식(기존 계약 — 터미널용 일반 텍스트)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# 구조화된 형식 — UI에서 사용하는 형식
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

키에서 **`allowUsageCommand`**가 활성화되어 있어야 합니다(기본값은 비활성화이며, 대시보드의 API 키 관리자가 키별로 설정을 전환합니다). 활성화되어 있지 않으면 엔드포인트가 `403`으로 응답합니다.

`?format=json`은 호출자가 거부 응답에서 데이터 필드를 읽지 않도록 판별 가능한 구조를 반환합니다. 성공 시:

```jsonc
{
  "allowed": true,
  // 키가 키별 사용량 한도(일간/주간 USD)를 사용하도록 설정된 경우에만 존재:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // 선택된 제공자의 할당량 스냅샷. 아직 캐시된 항목이 없으면 null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // UI에서 여러 제공자를 나란히 렌더링할 수 있도록 모든 연결의 스냅샷을 제공:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

거부 시(`401` 잘못된 키 / `403` 허용되지 않음), 동일한 경로가
`{ "allowed": false, "error": { "message": "…" } }`를 반환합니다. 값은 존재하지만 비어 있는 `personal`/`provider`(키는 허용되었으나 아직 확인된 정보가 없음)는 거부와 다른 상태이며, JSON 형식만 이 상태들을 구분합니다.

**인증:** 호출자 자신의 Bearer API 키이며 `isValidApiKey`로 검증됩니다. 이는 `requireManagementAuth`로 계속 보호되는 관리 인터페이스(`/api/keys/…`)가 _아닙니다_.

### 원시 할당량 백분율과 컷오프 조정 할당량 백분율

`/api/usage/om-usage`를 사용할 때 호출자는 **일반 텍스트 출력**과 구조화된 **JSON 출력**에 표시되는 백분율의 차이를 유의해야 합니다.

| 항목                | 일반 텍스트 형식(`/api/usage/om-usage` / `@@om-usage`)                                | JSON 형식(`?format=json`)                                      |
| :------------------ | :------------------------------------------------------------------------------------ | :------------------------------------------------------------- |
| **출력 필드**       | `NN% left`(예: `20% left`)                                                            | `provider.quotas` / `providers[].quotas`                       |
| **측정값**          | **컷오프 조정 가용 허용량**: 컷오프 임계값을 초과하여 남아 있는 용량                  | **원시 업스트림 할당량**: 조정되지 않은 제공자 측정값          |
| **컷오프 스케일링** | 보호된 예비 용량이 `0% left`로 표시되도록 `effectiveRemainingPercent()`를 통해 조정됨 | 없음(제공자가 보고한 원시 스냅샷 값)                           |
| **임계값 데이터**   | 표시되는 백분율에 반영됨                                                              | 연결별 `quotaWindowThresholds`에 저장됨(또는 서버 기본값 사용) |
| **주요 소비자**     | 대화형 CLI, 터미널 프롬프트, 운영 담당자                                              | 프로그래밍 방식의 통합, 대시보드, 분석, 결제 추적기            |

#### 컷오프 조정 공식

OmniRoute는 업스트림 할당량 소진을 방지하기 위해 선제적 할당량 컷오프를 지원합니다(연결의
`quotaWindowThresholds`, 제공자 기본값 또는 전역 복원력 설정을 통해 구성). 할당량 기간에 컷오프 임계값
(예: `cutoff = 25%`)이 활성화되면 텍스트 렌더러는 남은 허용량을 다음과 같이 계산합니다.

- `remaining <= cutoff`인 경우: `0%`를 반환합니다.
- `remaining > cutoff`인 경우: `((remaining - cutoff) / (100 - cutoff)) * 100`을 반환합니다.

형식화된 텍스트 출력에서는 이 값을 가장 가까운 정수로 반올림합니다(`Math.round(...)`).

#### 예시

**원시 사용량이 60%**이고(따라서 **원시 잔여 할당량은 40%**) 구성된
**잔여 할당량 컷오프 임계값이 25%**인 제공자 기간을 가정해 보겠습니다.

| 표현 방식                      | 계산                                               | 남은 할당량 |                 추정 사용량                  |
| :----------------------------- | :------------------------------------------------- | :---------: | :------------------------------------------: |
| **원시 JSON (`?format=json`)** | 업스트림 스냅샷(`quotas[window]`)                  |   **40%**   |                   **60%**                    |
| **텍스트 형식(`NN% left`)**    | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |   **20%**   | **80%**(`100 - remaining`으로 계산하는 경우) |

- **텍스트에 20%가 남았다고 표시되는 이유:** 계정에 물리적으로 남아 있는 40%의 할당량 중 25%는 컷오프 정책에 의해 예비 용량으로 확보됩니다. 라우터가 이 연결로의 라우팅을 중단하기 전까지 호출자에게 남은 가용 여유분은 75% 중 15%뿐입니다. 스케일링을 적용하면 라우팅이 중단되는 정확한 시점에 연결이 소진 상태(`0% left`)를 표시합니다.
- **JSON이 원시 값을 유지하는 이유:** JSON 페이로드는 정확한 제공자 스냅샷(`UsageSnapshot`)을 반환하므로, 외부 도구는 서버 측의 손실성 스케일링 없이 실제 업스트림 사용률과 연결 수준의 `quotaWindowThresholds`에 접근할 수 있습니다.

#### 소비자 마이그레이션 지침

외부 통합(예: 편집기 플러그인 또는 에이전트 확장 프로그램)이 이전에 텍스트
엔드포인트(`NN% left`)를 스크래핑하고 사용 비율을 `100 - NN`으로 계산했다면, `?format=json`으로 마이그레이션할 경우 다음과 같습니다.

- 원시 JSON 값을 읽으면 **실제 업스트림 사용량**이 반영됩니다(위 예시에서는 60% 사용).
- 통합에서 텍스트 엔드포인트의 사용 가능한 허용량 의미 체계를 유지하려면, 연결 수준 재정의에 `quotaWindowThresholds`를 사용하여
  클라이언트 측에서 유효 잔여량 공식을 계산할 수 있습니다.

### 지연 시간에 미치는 영향

시맨틱 캐시 HIT는 **업스트림 호출 없이** 캐시에서 응답을 제공하므로,
보고되는 `X-OmniRoute-Response-Latency`는 거의 0에 가깝습니다
(원래 업스트림 지연 시간과 무관). 지연 시간에 민감한 클라이언트
(벤치마킹, p50/p99 모니터링)는 다음
`X-OmniRoute-Cache-Latency` 응답 헤더를 확인해야 합니다:

| 값          | 의미                                                            |
| ----------- | --------------------------------------------------------------- |
| `synthetic` | 캐시에서 제공된 응답이며, 지연 시간은 실제 업스트림 시간이 아님 |
| _(없음)_    | 실제 업스트림 호출의 응답                                       |

### 키별 캐시 우회

API 키는 `cacheDefaultMode`를 통해 시맨틱 캐시 읽기를 사용하지 않도록 설정할 수 있습니다:

| 값       | 동작                                           |
| -------- | ---------------------------------------------- |
| `legacy` | 일반적인 캐시 동작(기본값)                     |
| `bypass` | 캐시 조회를 완전히 건너뛰고 항상 업스트림 호출 |

키 생성 시(`POST /api/keys`) 설정하거나 업데이트(`PATCH /api/keys/[id]`)합니다:

```json
{ "cacheDefaultMode": "bypass" }
```

### 요청별 우회

모든 요청은 키 설정과 관계없이 캐시를 우회할 수 있습니다:

```
X-OmniRoute-No-Cache: true
```

동기화하거나 가져온 모델의 경우 `PUT /api/provider-models`는 `provider`, `modelId`,
`maxOutputTokenOverride`를 허용합니다. 양의 정수는 수동 출력 토큰 한도를 설정하고, `null`은
이를 해제하여 기본값을 복원합니다. `GET /api/provider-models?provider=<provider>`는 사용자 지정
모델 행이 없는 모델을 포함하여 이러한 값을 `modelOutputOverrides`에 반환합니다. 이 재정의는
런타임 `max_output_tokens` 기능을 사용하며 모델을 다시 동기화한 후에도 유지됩니다. OpenAI 호환
공급자 페이지에서는 동일한 편집/해제 컨트롤을 제공하며 명시적으로 비전을 지원하는 모델을 표시합니다.

사용자 지정 Chat Completions 노드는 명시적인 추론 비활성화 요청을 업스트림 백엔드에 맞게 조정합니다.
연결 테스트에 성공하면 `/models` 항목에서 인식되는 `owned_by` 값(`vllm`, `sglang` 또는 `llamacpp`)이
확인된 각 정확한 모델 ID에 대해 채팅 템플릿 컨트롤을 자동으로 선택합니다. 투명한 OpenAI 호환
래퍼는 중첩된 `openai` 객체 안에 원본 모델 항목을 유지할 수 있으며, 감지는 이러한 래퍼를 최대
3단계까지 추적합니다. 소유권 정보가 없거나, 알 수 없거나, 서로 충돌하는 모델은 일반적인 OpenAI
동작을 유지합니다. 감지에는 기존 카탈로그 요청이 재사용되고, 완료 토큰은 생성되지 않으며, 연결
엔드포인트가 변경되면 감지 결과가 무효화됩니다.

해당 메타데이터를 노출하지 않는 백엔드의 동작을 고정하려면 기존의 부분 공급자 업데이트 API를
사용하십시오.

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

이 본문을 `PUT /api/providers/<connection-id>`와 함께 전송하십시오. 해당 연결에서는 명시적인
추론 강도 `none`이 `chat_template_kwargs.thinking=false` 및
`chat_template_kwargs.enable_thinking=false`로 전송됩니다. 서버 측 추론 규칙이 특정 강도를
강제하지 않는 한, 명시적인 네이티브 템플릿 값이 우선합니다. 이 설정은 사용자 지정 OpenAI 호환
연결이 Chat Completions 본문을 전송할 때만 적용됩니다. Responses 요청과 일반 공급자는 기존의
네이티브 요청 형식을 유지합니다. 일반적인 OpenAI `reasoning_effort` 패스스루를 강제하려면
`reasoningControl`을 `openai`로 설정하고, 자동 감지를 사용하려면 이를 생략하거나 `null`로
설정하십시오.

Claude Code 자동 모드 분류기 요청에 명시적인 추론 컨트롤이 없으면 네이티브 thinking은 기본적으로
비활성화됩니다. 감지는 모델 이름이나 완료 한도가 아니라 Claude 형식 요청에 있는 분류기의 시스템
마커를 사용합니다. 명시적인 본문 컨트롤, 지원되는 추론 강도/thinking 헤더, 라우팅 규칙 및 결정된
모델 추론 강도는 기존 우선순위를 유지합니다. 두 분류 단계 모두 프롬프트, 완료 한도, 중지 시퀀스 및
실제 업스트림 권한 판정 결과를 유지합니다. 두 번째 단계에서는 요청된 표시 가능한 추론을 여전히 일반
텍스트로 생성할 수 있습니다.

| 필드                                        | 유형                                                       | 참고                                                                                                                      |

### 버전 및 릴리스 채널

```bash
GET /api/system/version
```

루프백 전용 관리 경로입니다(관리자 인증). 실행 중인 버전, 최근에 게시된 버전 및 자동 업데이트 상태를 반환합니다. `releaseChannel`과 `channels`는 추가 필드이며(rail 3.8.54), `channel`은 대시보드 업데이터가 사용하는 배포 모드(`npm`, `source` 또는 `docker-compose`)라는 기존 의미를 유지합니다.

```json

  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — 실행 중인 빌드의 npm 채널: `-nightly.*` 버전은 `nightly`, 그 외 프리릴리스(`-rc.*`, `-beta.*`, `-alpha.*`)는 `next`, `channels.latest`보다 이전 메이저의 안정 버전은 `lts`, 그 외에는 `latest`입니다. 게시 시 npm dist-tag를 선택하는 `scripts/release/dist-tag.mjs`와 동일한 규칙을 사용합니다.
- `channels` — `npm view omniroute dist-tags`에서 가져온 각 dist-tag의 최신 게시 버전입니다(레지스트리 HTTP 폴백 사용). `latest`와 동일하게 10분 TTL로 캐시됩니다. `latest`는 항상 존재하며(`latest` 필드로 폴백한 다음 `"unavailable"`로 폴백), `next`, `nightly`, `lts`는 해당 dist-tag가 존재할 때만 표시됩니다. `Cache-Control: no-cache` 요청은 두 조회 결과를 모두 새로 고칩니다.

채널 모델(`latest` = 4.0 GA 전까지 v3, `next` = rc, `nightly` = `develop` 빌드, `lts` = 4.0 GA 이후의 v3 패치)은 `docs/ops/RELEASE_STRATEGY.md`에 설명되어 있습니다.

## 토큰 제한

API 키별 **토큰** 예산입니다(위의 USD 기반 예산과는 별개). 요청 경로에서 인라인으로 적용됩니다. 키의 현재 기간 사용량이 제한에 도달하면 요청이 `429 Too Many Requests`로 거부됩니다. 제한은 특정 `model`이나 `provider`로 범위를 지정하거나 키 전체에 `global`로 적용할 수 있습니다. 하나의 요청에 여러 제한이 일치하면 가장 엄격한 제한이 적용됩니다.

```bash
# 키의 토큰 제한 목록 조회(현재 기간의 실시간 사용량 포함)
GET /api/usage/token-limits?apiKeyId=key-123

# 토큰 제한 생성 또는 업데이트
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ID로 토큰 제한 삭제
DELETE /api/usage/token-limits?id=tl-abc
```

> **스키마 참고 사항** (`setTokenLimitSchema`): `apiKeyId`와 `scopeType`(`model` | `provider` | `global`)은 필수입니다. `scopeType`이 `global`이 아닌 경우 `scopeValue`가 필요합니다(예: `model` 범위의 모델 ID, `provider` 범위의 제공자 ID). `tokenLimit`는 양의 정수여야 합니다(문자열에서 변환됨). 선택 사항: `id`(생성 시 생략하고 업데이트 시 지정), `resetInterval`(`daily` | `weekly` | `monthly`, 기본값 `monthly`), `resetTime`(`HH:MM`), `enabled`(기본값 `true`). `GET` 응답에서는 각 제한에 `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, `nextResetAt`가 추가됩니다. 이는 관리 유형 엔드포인트입니다(인증은 authz 파이프라인에서 중앙 집중식으로 적용됨).

## 요청 처리

1. 클라이언트가 `/v1/*`로 요청을 전송합니다
2. 라우트 핸들러가 `handleChat`, `handleEmbedding`, `handleAudioTranscription` 또는 `handleImageGeneration`을 호출합니다
3. 모델을 해석합니다(직접 지정한 제공자/모델 또는 별칭/콤보)
4. 계정 가용성 필터링을 적용하여 로컬 DB에서 자격 증명을 선택합니다
5. 채팅의 경우 `handleChatCore`가 의미론적/서명 캐시를 확인하고 콤보 압축 설정을 해석합니다
6. 활성화된 경우 제공자 변환 전에 선제적 압축이 실행됩니다(`lite`, Caveman, RTK 또는 스택 방식)
7. 제공자 실행기가 업스트림 요청을 전송합니다
8. 응답을 클라이언트 형식으로 다시 변환하거나(채팅) 그대로 반환합니다(임베딩/이미지/오디오)
9. 사용량, 압축 분석 및 요청 로그가 기록됩니다
10. 오류 발생 시 콤보 규칙에 따라 폴백이 적용됩니다

전체 아키텍처 참고 자료: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## 복원력 (확장)

OmniRoute는 서로 독립적인 세 가지 일시적 장애 대응 메커니즘을 제공합니다. 아래 관리 엔드포인트를 통해 운영자가 해당 상태를 조회하고 재정의할 수 있습니다.

| 범위          | 상태 저장소                          | 조회                                      | 재설정 / 해제                                         |
| ------------- | ------------------------------------ | ----------------------------------------- | ----------------------------------------------------- |
| 공급자 차단기 | `domain_circuit_breakers` + 인메모리 | `/api/monitoring/health`                  | `POST /api/resilience/reset`                          |
| 연결 쿨다운   | 공급자 연결의 `rateLimitedUntil`     | `/api/rate-limits`, `/api/providers/[id]` | (지연 방식으로 다시 활성화됨. 공급자 PUT을 통해 해제) |
| 모델 잠금     | 인메모리 모델 가용성 레지스트리      | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`              |

`PATCH /api/resilience`는 `providerBreaker.oauth` 및 `providerBreaker.apikey`에서 공급자 차단기 재정의를 허용합니다. 각 프로필은 `degradationThreshold`, `failureThreshold`, `resetTimeoutMs`를 지원하며, 동일한 필드가 대시보드 → 설정 → 복원력에도 제공됩니다.

```bash
# 단일 모델 잠금 해제
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# 모든 잠금 삭제
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

전체 개념 참고 자료와 차단기 기본값은 [`CLAUDE.md`](../../CLAUDE.md)의 "복원력 런타임 상태" 및 [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)를 참조하세요.

### 속도 제한 큐 및 자동 활성화 안전망

- **지원되는 쓰기 경로**: 본문이 `{"connectionId": "<id>", "enabled": true|false}`인 `POST /api/rate-limits`는 연결의 속도 제한 보호를 전환하기 위해 지원되는 관리 엔드포인트입니다. `PUT /api/providers/[id]`는 의도적으로 `rateLimitProtection`을 수정하거나 전환하지 않습니다(#11278).
- **`enabled: false`의 의미**: `enabled: false`를 설정하면 해당 연결에 대한 명시적 보호가 제거되지만, 활성 API 키 연결을 전역 자동 활성화 안전망(`autoEnableApiKeyProviders = true`)에서 **제외하지는 않습니다**. `reconcileEnabledConnections`(`open-sse/services/rateLimitManager.ts`)에서는 `false`와 `undefined`가 동일하게 취급됩니다. 명시적으로 보호가 설정되지 않은 활성 API 키 연결은 자동 활성화 안전망에 따라 계속 보호됩니다.
- **전역 비활성화**: 속도 제한 큐 없이 API 키 연결을 실행하려면 `RATE_LIMIT_AUTO_ENABLE=false`(환경 변수) 또는 `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`(설정 → 복원력 / `PATCH /api/resilience`)를 통해 안전망을 전역적으로 비활성화하세요.

## MCP 서버

OmniRoute에는 3가지 전송 방식(stdio, SSE, streamable-http)과 범위가 지정된 도구를 지원하는 Model Context Protocol 서버가 내장되어 있습니다. 아래 대시보드 엔드포인트는 상태/감사 데이터를 읽고 HTTP 전송을 프록시합니다.

| 메서드 | 경로 | 설명 |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | 하트비트, 전송 방식, 온라인 상태, 마지막 호출, 상위 도구, 24시간 성공률 |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints`가 포함된 MCP 도구 목록 |
| GET | `/api/mcp/sse` | SSE 전송용 SSE 스트림 열기(MCP가 비활성화되어 있거나 전송 방식이 일치하지 않으면 `503` 반환) |
| POST | `/api/mcp/sse` | SSE 전송을 통해 JSON-RPC 프레임 전송 |
| GET | `/api/mcp/stream` | Streamable HTTP 전송의 SSE 측 스트림 열기(서버에서 시작된 메시지) |
| POST | `/api/mcp/stream` | Streamable HTTP 전송을 통해 JSON-RPC 프레임 전송 |
| DELETE | `/api/mcp/stream` | Streamable HTTP 세션 종료 |
| GET | `/api/mcp/audit` | 감사 로그 조회 — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | 집계된 감사 통계(총계, 성공률, 평균 소요 시간, 상위 도구) |

**인증:** `sse`/`stream` 전송은 MCP 전용 인증 방식(`mcp` 범위가 있는 Bearer API 키)을 따릅니다. `status`/`tools`/`audit*` 경로는 대시보드에서 읽을 수 있습니다(대시보드 호스트에 접근하는 데 필요한 인증 외에 추가 인증은 필요하지 않음).

> 두 HTTP 전송 모두 `settings.mcpEnabled` 및 `settings.mcpTransport`에 의해 제한됩니다. 전송 방식이 일치하지 않으면 `400`을 반환하고, MCP가 비활성화되어 있으면 `503`을 반환합니다.

## A2A 서버

OmniRoute는 A2A(Agent-to-Agent) JSON-RPC 2.0 엔드포인트와 검사/대시보드용 REST 래퍼를 제공합니다.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY가 설정되지 않은 경우 선택 사항
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

지원되는 메서드(모두 `settings.a2aEnabled`에 의해 제어됨):

| 메서드           | 설명                                                         |
| ---------------- | ------------------------------------------------------------ |
| `message/send`   | 동기식 스킬 실행. `{task, artifacts, metadata}`를 반환합니다 |
| `message/stream` | 동일한 스킬 세트의 스트리밍 SSE 실행                         |
| `tasks/get`      | `taskId`로 작업을 가져옵니다                                 |
| `tasks/cancel`   | `taskId`로 작업을 취소합니다                                 |

기본 제공 스킬: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### 에이전트 카드

```bash
GET /.well-known/agent.json
```

공개 A2A 에이전트 카드(이름, 설명, 기능, 스킬 카탈로그, 인증 방식)를 반환하며, 공개적으로 1시간 동안 캐시됩니다. 인증은 필요하지 않습니다.

### REST 헬퍼

| 메서드 | 경로                         | 설명                                                                                                           |
| ------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A 활성화 여부 + 작업 통계 + 캐시된 에이전트 카드 요약                                                        |
| GET    | `/api/a2a/tasks`             | 작업 목록 — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (REST 헬퍼로 구현되지 않음 — JSON-RPC `message/send`를 통해 생성)                                              |
| GET    | `/api/a2a/tasks/[id]`        | 작업 하나 조회                                                                                                 |
| POST   | `/api/a2a/tasks/[id]/cancel` | 작업 취소                                                                                                      |

**인증:** REST 헬퍼는 관리 인증 없이 실행되며(대시보드에서 읽기 가능), JSON-RPC `/a2a` 경로는 구성된 경우 Bearer `OMNIROUTE_API_KEY`를 사용합니다.

## 인증

네 가지 자격 증명 유형(대시보드 세션, 로컬 CLI 토큰, `oma_live_…` 액세스 토큰, 관리 범위 API 키)과 추론 키와의 차이점은 [관리 인증](../guides/MANAGEMENT-AUTH.md)을 참조하세요.

- 대시보드 경로(`/dashboard/*`)는 `auth_token` 쿠키를 사용합니다
- 로그인에는 저장된 비밀번호 해시를 사용하며, 사용할 수 없는 경우 `INITIAL_PASSWORD`를 사용합니다
- `requireLogin`은 `/api/settings/require-login`을 통해 전환할 수 있습니다
- `REQUIRE_API_KEY=true`인 경우 `/v1/*` 경로에 Bearer API 키가 필요할 수 있습니다
- 이 참조 문서에서 "관리 토큰" / "관리 범위 API 키"는 해당 가이드에 설명된 유형 중 하나를 의미하며, 별도로 정의되지 않은 추가 비밀 유형을 의미하지 않습니다

> **호환성을 깨는 변경 사항(v3.8.0)** — 이제 `/api/v1/agents/tasks/*` 및 쿨다운 관리 엔드포인트에는 **관리 인증**(대시보드 `auth_token` 쿠키 또는 관리 범위 API 키)이 필요합니다. 이전에 인증 없이 이러한 경로를 호출했던 클라이언트는 `401 Unauthorized`를 받게 됩니다. 커밋 `588a0333`(`fix(auth): require management auth for agent and cooldown APIs`)을 참조하세요.
