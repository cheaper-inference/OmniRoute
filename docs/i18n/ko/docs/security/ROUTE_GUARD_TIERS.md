## 개요

모든 OmniRoute 관리 API 경로는 세 가지 보호 계층 중 하나로 분류됩니다. 분류는 정적이며 `src/server/authz/routeGuard.ts`에 정의되어 있고, 다른 모든 인증 분기가 실행되기 전에 평가됩니다.

## 등급

### Tier 1 — LOCAL_ONLY

**적용:** `isLocalOnlyPath(path)` → 루프백 호스트 검사
**우회:** 기본적으로 없음. 요청이 `manage` 스코프를 가진 유효한 API 키를
포함하는 경우 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`에 속한 경로에 대한
제한적 예외가 있음([Manage 스코프 예외](#manage-scope-carve-out) 참조).

이러한 라우트는 자식 프로세스를 생성하거나 런타임 코드를 실행합니다. 이를
루프백이 아닌 트래픽에 노출하면, 유효한 JWT를 탈취한 공격자(예:
Cloudflared/Ngrok 터널을 통해)가 프로세스 생성을 트리거할 수 있습니다. 이는
알려진 CVE 유형입니다
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj란 무엇인가(공격 유형):** 관리/에이전트 서버가
서브프로세스(`npm install`, `node`, 브라우저, 프록시, `git`, `tar`, …)를
실행하는 엔드포인트를 노출합니다. 운영자가 OmniRoute를
nginx/Cloudflare/Tailscale 터널 뒤에 배치했고 JWT가 유출되었거나 인증이 잘못
구성되어, 해당 엔드포인트가 호스트 외부에서 접근 가능한 상태라면, 공격자는
"API 호출"을 "호스트에서 명령 실행"(원격 코드 실행)으로 바꿀 수 있습니다.
OmniRoute는 프로세스 생성이 가능한 모든 라우트에 대해 **인증 검사보다 먼저,
무조건 루프백 호스트 검사를 적용**하여 이를 차단합니다. 터널을 통해 토큰이
유출되더라도 프로세스 생성에는 도달할 수 없습니다.

**전체 LOCAL_ONLY 집합.** 공식 기준 소스는
`src/server/authz/routeGuard.ts`의 `LOCAL_ONLY_API_PREFIXES` /
`LOCAL_ONLY_API_PATTERNS`이며, 아래 표는 현재 상태를 그대로 반영합니다.
`check-route-guard-membership` 게이트는 프로세스 생성이 가능한 프리픽스 아래의
모든 `route.ts`를 열거하고, local-only로 분류되지 않은 것이 하나라도 있으면
CI를 실패시킵니다.

#### Manage 스코프 예외

LOCAL_ONLY 경로의 일부는 요청이 메타데이터에 `manage` 스코프(또는 `admin`)를 포함하는
`Authorization: Bearer <api-key>`를 가지고 있는 경우에만 non-loopback에서도 접근할 수 있다.
이 예외는 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`를 통해 경로별로 명시적으로
게이트되므로, 새로운 LOCAL_ONLY 경로의 기본값은 strict-loopback으로 유지된다.
인증되지 않은 요청과 manage가 아닌 키를 가진 요청은 여전히 `403 LOCAL_ONLY`로 거부된다.

현재 우회 가능한 유일한 접두사는 `/api/mcp/`이다. `/api/cli-tools/runtime/`과
`/api/services/`는 임의의 서브프로세스(`npm install`, `node`)를 생성할 수 있으므로
의도적으로 제외되었으며, 이는 LOCAL_ONLY 계층이 방지하기 위해 존재하는 바로 그 CVE
클래스이다.

**#7895 — `mcp:connect` 좁은 스코프:** `/api/mcp/` 예외는 좁은 `mcp:connect` 스코프
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`)를 가진 Bearer 키도
허용하며, 이는 `src/server/authz/policies/management.ts`의
`hasMcpConnectOrManageScope()`를 통해 확인된다. 이는 `/api/mcp/`에만 적용된다 —
`mcp:connect`는 다른 어떤 관리 경로(향후 추가될 수 있는 다른 모든 LOCAL_ONLY 우회
접두사 포함)에서도 아무것도 허용하지 않으며, `MANAGEMENT_API_KEY_SCOPES`에서
의도적으로 제외된다. `manage`/`admin`을 가진 키는 여전히 이전과 동일하게 예외를
통과한다; `mcp:connect`는 광범위한 관리 접근이 필요하지 않은 원격 MCP 전용
호출자를 위한 더 낮은 권한의 대안이다.

| 요청                                               | 경로                       | 결과               |
| -------------------------------------------------- | -------------------------- | ------------------ |
| Non-loopback, Bearer 없음                          | `/api/mcp/*`               | 403 LOCAL_ONLY     |
| Non-loopback, `manage` 스코프를 가진 Bearer        | `/api/mcp/*`               | 허용               |
| Non-loopback, `mcp:connect` 스코프를 가진 Bearer   | `/api/mcp/*`               | 허용               |
| Non-loopback, `manage`/`mcp:connect`가 없는 Bearer | `/api/mcp/*`               | 403 LOCAL_ONLY     |
| Non-loopback, `mcp:connect` 스코프를 가진 Bearer   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY     |
| Non-loopback, `manage` 스코프를 가진 Bearer        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY     |
| Loopback, Bearer 있음/없음                         | 모든 LOCAL_ONLY            | 허용 (게이트 통과) |

#### 운영자 가이드 및 감사

OmniRoute를 리버스 프록시나 터널(nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) 뒤에서 실행하는 경우에도, loopback 검사는 위의 생성 가능
경로를 여전히 보호한다 — 클라이언트 주소가 non-loopback인 요청은 **인증이 실행되기
전에** `403 LOCAL_ONLY`로 거부되므로, 유출된 JWT도 생성에 도달할 수 없다. 두 가지
운영자 책임이 남아 있다:

- **클라이언트 IP를 루프백으로 위조하여 403을 "수정"하지 마세요.**
  `X-Forwarded-For: 127.0.0.1`을 설정하거나, 소스 주소를 루프백으로 재작성하는
  프록시는 이 계층이 차단하는 바로 그 RCE 클래스를 다시 엽니다. 대시보드/API는
  프록시를 통해 노출하되, 스폰 가능 라우트는 절대 노출하지 마세요.
- **manage 스코프 우회를 최소한으로 유지하세요.** `/api/mcp/`만 우회 가능하며,
  그것도 `manage` 스코프 API 키로만 가능합니다. `SPAWN_CAPABLE_PREFIXES`는
  우회 목록에 절대 추가될 수 없습니다. zod 스키마가 이를 거부하고
  `isLocalOnlyBypassableByManageScope`가 런타임에 이를 거부하기 때문입니다(심층 방어).
  이것이 바로 대시보드에서 말하는 "우회 불가로 만들 수 없음"의 의미입니다. 동일한
  거부 목록에는 스폰하지는 않지만 원격에서 절대 접근할 수 없어야 하는 몇몇 LOCAL_ONLY
  라우트도 포함되어 있습니다 — `/api/oauth/kiro/auto-import`(호스트 로컬 Kiro
  자격 증명 파일을 읽음), `/api/discovery/`, `/api/issue-agent/`. 런타임
  스냅샷 로더도 저장된 설정 행에서 이러한 항목을 제거하며, 레거시 JSON 가져오기
  (`/api/settings/import-json`)는 우회 키를 절대 기록하지 않습니다.
  모든 `LOCAL_ONLY_API_PREFIXES` 항목은 거부 목록에 있거나 우회 가능 대상으로
  검토되어야 합니다(`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`).
  `/api/providers/` 아래의 동적 세그먼트 및 정적 경로 스폰 가능 라우트
  (예: `/login`, `/refresh-cursor`)는 플랫 `SPAWN_CAPABLE_PREFIXES` 배열이 아니라
  `src/shared/constants/spawnCapablePrefixes.ts`의 정규식 기반
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` 보조 상수로
  처리됩니다. 플랫 배열이 이를 잡아내려면 전체 `/api/providers/` 접두사를
  포함해야 하므로, 원격 대시보드가 프로바이더 CRUD에 정당하게 사용하는 라우트
  트리를 지나치게 넓게 커버하게 될 것입니다.

**접근 감사** — 호스트 외부에서 이 라우트에 도달하는 것이 없는지 확인하려면:

- `/dashboard/settings/security`에서 **Authorization Inventory**(권한 인벤토리)를
  여세요. 실시간 LOCAL_ONLY 접두사 목록, 어떤 접두사가 우회 가능한지, 그리고 컴파일
  타임 스폰 가능("우회 불가로 만들 수 없음") 집합을 렌더링합니다.
- 리버스 프록시/접근 로그에서 위 접두사와 비루프백 클라이언트 주소가 함께
  나타나는지 grep으로 검색하세요. `403 LOCAL_ONLY` 대신 `200`을 반환한 이러한
  히트가 있다면 프록시가 실제 클라이언트 IP를 마스킹하고 있다는 의미입니다 —
  프록시를 수정하세요.
- OmniRoute 로그에서 이 경로들 중 하나에 대한 `403 LOCAL_ONLY`는 가드가 의도대로
  작동하고 있다는 것이며, 억제해야 할 오류가 아닙니다.

#### 호출 지점 프로브 게이트가 있는 원격 접근 가능 라우트

일부 라우트는 원격 대시보드에서 계속 접근 가능해야 하지만, 로컬 호출자에 대해서는
호스트 측 프로브(`which <binary>`, `<binary> --version`, `tailscale status --json`)를
실행합니다. 이들은 `GET`에 대해 LOCAL_ONLY가 아닙니다. 대신 핸들러가
`getRequestPeerLocality()`(`src/shared/utils/apiAuth.ts`)로 신뢰된 피어 판정을 읽고,
`loopback` / `lan` 호출자에 대해서만 프로브를 실행합니다. `remote` 호출자는 스폰하지
않는 소스(영속 상태, 설정, fs 검사)로 구축된 동일한 형태의 응답을 받으며, `probed: false`로
플래그됩니다.

| 라우트                                                           | 원격 호출자에 대해 건너뛰는 프로브                                |
| ---------------------------------------------------------------- | ----------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`     | CLI 런타임 프로브(`allowLocalRuntimeProbe`) 및 CLI 폴백 스폰      |
| `GET /api/headroom/status`                                       | `which headroom` 및 python `--version` 프로브                     |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check` | `which tailscale`, `tailscale status/funnel --json`, `which brew` |
| `GET /api/tunnels/cloudflared`(LOCAL_ONLY에서 GET 면제)          | `which cloudflared` PATH 조회                                     |

호스트를 프로브하는 새로운 읽기 라우트는 동일한 패턴을 따르거나, 아예 LOCAL_ONLY로
분류됩니다.

### 계층 2 — ALWAYS_PROTECTED

**적용 주체:** `isAlwaysProtectedPath(path)` → `requireLogin=false` 우회 건너뛰기
**우회:** `requireLogin=false`일 때 없음; JWT 항상 필요

이 라우트들은 파괴적이거나 되돌릴 수 없습니다. "비밀번호 없음" 설치에서 이를
허용하면 같은 LAN에 있는 누구나 데이터베이스를 지우거나 서버 프로세스를 종료할 수
있게 됩니다.

| `/api/shutdown`                           | 서버 프로세스 종료                                        |

| `/api/db-backups`                         | 전체 데이터베이스 백업 아카이브 접근                      |

`/api/settings/obsidian`은 그 하위인 `/webdav`를 포함합니다: `POST`는 WebDAV 파일
서비스(Next.js 이전의 커스텀 Node 계층에서 제공되며 이 파이프라인 외부에 있음)를
호출자가 선택한 루트로 지정하고 새로 발급된 Basic 자격 증명을 그대로 반환하며,

볼트를 거부합니다.

#### 자격 증명 내보내기와 복원은 운영자 전용

위 등급은 _어떤_ 자격 증명이 필요한지 여부만 결정합니다. 저장된 자격 증명을
다운로드하는 라우트는 핸들러에 두 번째 검사를 추가합니다: `GET /api/settings/export-json`
(복호화된 프로바이더 연결 및 원시 API 키), `GET /api/db-backups/export`(SQLite 파일),
`GET /api/db-backups/exportAll`(전체 아카이브)은 `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`)을 호출합니다. 이 함수는 대시보드 세션, 로컬 CLI
주체, 또는 로그인이 비활성화된 인스턴스를 허용하며, 어떤 범위의 API 키(`manage`와
`admin` 포함)와 `oma_` 액세스 토큰에도 `403`을 반환합니다. 파괴적인 반대편 작업들도
동일한 경계를 유지합니다: `POST /api/db-backups/import`(업로드된 `.sqlite`,
`dryRun=true` 포함), `POST /api/db-backups`(id로 저장된 백업 복원),
`POST /api/settings/import-json`(레거시 JSON 복원)은 라이브 데이터베이스 또는 전체
설정/연결/API 키 집합을 교체하므로, 머신 자격 증명으로도 이를 트리거할 수 없습니다.
복원 지점 삭제도 동일한 경계를 유지합니다: `DELETE /api/db-backups`(정리 — 최신
N개 유지 / D일보다 오래된 항목 삭제)와 `PATCH /api/db-backups`(보존 설정).
저장된 보존 정책은 `cleanupDbBackups()`가 자동 백업 후 매번 적용하는 바로 그 값이므로
(`src/lib/db/backup.ts`), `keepLatest: 1`을 저장할 수 있는 머신 자격 증명이 있다면
다음 스냅샷에서 모든 것을 정리해버리게 됩니다. 백업 나열 및 생성
(`GET`/`PUT /api/db-backups`)은 일반 관리 인증을 유지합니다. 동기화 토큰 발급
(`POST /api/sync/tokens`)은 동일한 헬퍼에 더해 신뢰된 루프백 내부 서비스 토큰도
사용합니다.

### 신규 설치 부트스트랩은 루프백 전용 — `Host`가 아닌 실제 피어 기준

관리 비밀번호가 설정되지 않은 경우(`INITIAL_PASSWORD`도 없는 경우),
`src/shared/utils/apiAuth.ts`의 `isAuthRequired()`는 익명 부트스트랩을 **루프백
피어에만** 열어 둡니다. 루프백 여부는 신뢰된 피어 신호로부터 다음 순서로 결정됩니다:
토큰으로 스탬프된 실제 TCP 피어(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, 정책이 보는 값),
파이프라인 자체의 `AUTHZ_HEADER_PEER_LOCALITY` 판정(라우트 핸들러가 보는 값으로,
`OMNIROUTE_PEER_STAMP_TOKEN`이 설정된 동안에만 신뢰됨), 또는 직접 호출자의 실제
소켓 피어. `Host` / `nextUrl.hostname`은 절대 참조되지 않으며, 첫 비밀번호 설정
(`POST /api/settings/require-login`)도 모든 네트워크 피어에 열려 있지 않고 동일한
제약 아래에 있습니다(GHSA-7pq4-8pvv-rx7r). `managementPolicy`는 자체 `peerContext`
판정을 명시적으로 아래로 전달하므로, 원본(제거 전) 요청의 헤더가 이를 결정하는 일은
없습니다.

### Tier 3 — MANAGEMENT (기본)

기타 모든 관리 라우트. `requireLogin=false`가 설정되지 않는 한 인증이 필요합니다.
CLI 토큰으로 이 라우트들을 인증할 수 있습니다(루프백 + 유효한 HMAC).

## 평가 순서

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → 루프백                                  → 다음 단계로 진행
     → 비루프백, manage 범위 Bearer
        AND isLocalOnlyBypassableByManageScope   → 허용 (management_key)
     → 그 외                                    → 거부 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 허용 (system)
  3. hasValidCliToken(headers)?
     → 허용 (cli) [루프백 + timingSafeEqual HMAC 검사]
  4. isAlwaysProtectedPath(path) 또는 requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 허용 (dashboard_session)
     → 우회할 수 없는 경로에서 manage 범위 Bearer?
        → 허용 (management_key)
     → 거부 401/403
  5. requireLogin=false?
     → 허용 (anonymous)
```

1단계의 manage 범위 분기만이 LOCAL_ONLY 경로를 충족할 수 있는 유일한 인증 경로입니다. 인증 백엔드 실패 시 만료된 DB로 인해 조용히 "거부"로 강등되지 않도록 403이 아닌 503을 반환합니다.

## OpenAPI에서 보안 계층 문서화

`docs/openapi.yaml`에 새 경로를 추가할 때, 해당 경로가 `routeGuard.ts`에 의해 분류되는 경우 그에 해당하는 벤더 확장을 적용하세요.

| routeGuard.ts 분류           | YAML 주석                  | 적용 방식                                    |
| ---------------------------- | -------------------------- | -------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 비루프백에서 무조건 차단                     |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | `requireLogin=false`인 경우에도 인증 필요    |
| 내부 관리자/디버그 경로      | `x-internal: true`         | 기본적으로 /dashboard/api-endpoints에서 숨김 |
| 없음(공개/표준 인증)         | (주석 불필요)              | 표준 `requireLogin` 제어 접근                |

### 검증

두 스크립트가 YAML 주석과 `routeGuard.ts` 간의 일관성을 강제합니다.

- `scripts/check/check-openapi-coverage.mjs` — 커버리지가 99% 미만이면 실패
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` 또는
  `x-always-protected` 주석이 컴파일 타임 상수와 일치하지 않으면 실패

두 스크립트 모두 pre-commit 훅과 CI에서 실행됩니다.

### 오탐 규칙

`routeGuard.ts` 상수에 포함되지 않은 경로에 `x-always-protected` 또는 `x-loopback-only`가 지정되어 있으면 커버리지 스크립트가 실패합니다. 해결 방법은 항상 YAML을 `routeGuard.ts`에서 실제로 적용하는 내용에 맞추는 것입니다. 적용 로직도 구현하지 않은 채 경로를 `routeGuard.ts`에 추가해서는 안 됩니다.
