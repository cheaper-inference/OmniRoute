> **요약**: OmniRoute는 모든 요청의 토큰 사용량을 추적하고, 비용을 계산하며, API 키별 할당량을 적용하고, 대시보드에 분석 데이터를 표시합니다. 이 가이드에서는 이 모든 기능이 어떻게 작동하는지 설명합니다.

**소스:**

- `open-sse/services/usage.ts` (~70KB) — 주요 사용량 추적
- `src/lib/usageAnalytics.ts` (~10KB) — 대시보드용 집계
- `src/lib/db/quotaSnapshots.ts` — 과거 할당량 데이터
- `src/lib/db/usage*.ts` — 여러 사용량 관련 DB 모듈

## 개요

OmniRoute를 통과하는 모든 요청은 다음 정보를 담은 **사용량 레코드**를 생성합니다.

- **식별 정보**: API 키, 제공자, 모델, 콤보
- **토큰**: 프롬프트 토큰, 완료 토큰, 캐시된 토큰, 총합
- **비용**: USD 금액(가격 데이터를 기반으로 계산)
- **시간 정보**: 지연 시간, 시작/종료 타임스탬프
- **상태**: 성공, 오류, 속도 제한 등

이러한 레코드는 **분석 데이터**로 집계되고, **할당량 스냅샷**으로 영구 저장되며, **키별 예산 한도**를 적용하는 데 사용됩니다.

```
요청 ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                       분석    할당량    청구
                    (대시보드)  (적용)  (내보내기)
```

## 기록되는 항목

`usage.ts` 서비스는 모든 요청에 대해 **사용량 이벤트**를 기록합니다:

| 필드               | 타입    | 출처                                                       |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | 기록 시 생성되는 UUID                                      |
| `apiKeyId`         | string  | 요청을 시작한 API 키                                       |
| `provider`         | string  | 제공업체 ID (openai, anthropic 등)                         |
| `model`            | string  | 모델 ID (gpt-5, claude-opus-4-6 등)                        |
| `comboId`          | string? | 콤보를 통해 라우팅된 경우 해당 콤보 ID                     |
| `promptTokens`     | number  | 업스트림 응답에서 추출                                     |
| `completionTokens` | number  | 업스트림 응답에서 추출                                     |
| `cachedTokens`     | number  | 캐시 적중 토큰 (Anthropic 프롬프트 캐싱 등)                |
| `totalTokens`      | number  | 프롬프트 + 완성                                            |
| `costUsd`          | number  | 가격 데이터를 기반으로 계산                                |
| `latencyMs`        | number  | 전체 요청 처리 시간                                        |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | 상태가 success가 아닌 경우의 오류 클래스                   |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | 플러그인이 삽입한 사용자 지정 데이터                       |

### 토큰 정보의 출처

토큰 정보는 **응답 핸들러**에서 업스트림 제공업체의 응답으로부터 추출됩니다:

```ts
// open-sse/handlers/chatCore.ts에서 발췌
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

사용량을 반환하지 않는 제공업체(일부 웹 쿠키 기반 제공업체)의 경우, OmniRoute는 `~4 chars per token` 휴리스틱을 사용해 토큰 수를 **추정**합니다(`open-sse/services/autoCombo/pipelineRouter.ts` 참조).

### 캐시된 토큰

OmniRoute가 `cached_tokens`를 `prompt_tokens`와 별도로 추적하는 이유는 다음과 같습니다:

- Anthropic 프롬프트 캐싱은 캐시된 토큰에 할인된 요금(일반 요금의 10%)을 적용합니다
- 일부 제공업체는 다른 요금을 적용해야 하는 `cache_read_input_tokens`를 반환합니다
- 분석에서 **캐시 적중률** = `cached_tokens / prompt_tokens`를 표시할 수 있습니다

### 캐시 쓰기 등급 진단

분석 대시보드의 프롬프트 캐시 상태 패널은 제공업체가 보고한
5분 및 1시간 캐시 쓰기를 구분합니다. Anthropic의
`usage.cache_creation.ephemeral_5m_input_tokens`와
`usage.cache_creation.ephemeral_1h_input_tokens`는 스트리밍 및
비스트리밍 사용량 변환 과정에서 유지되며 호출 로그 요약과 함께 저장됩니다. 합산된
캐시 쓰기 총량은 이러한 항목에 중복으로 더해지지 않습니다.

이전 기록을 포함하여 합산된 쓰기 카운터만 있는 호출은 등급을 알 수 없는 것으로
처리됩니다. 세부 내역이 일부만 있는 경우 할당되지 않은 나머지는 알 수 없는 상태로 유지됩니다. 유효하지 않거나
서로 충돌하는 카운터는 임의로 TTL을 할당하는 대신 문제가 있음을 표시합니다. 요청 측
TTL 표시는 청구 등급의 근거가 아닙니다.

패널의 API 환산 쓰기 추정치는 보고되었으며 가격이 있는 등급만 대상으로 하며,
전체 요청을 대상으로 하지 않습니다. 네이티브 Claude/Anthropic 모델 가격의 경우 5분 쓰기에는
입력 요금의 1.25배를, 1시간 쓰기에는 입력 요금의 2배를 사용합니다. 가격 정보가
없으면 0이 아니라 사용 불가로 처리됩니다. 가격은 각 새 호출이 기록될 때 저장되며,
과거 기록에는 가격을 다시 적용하지 않습니다. 따라서 구독 계정에는 해당 금액이
실제 지출이나 구독 할당량에서 차감되지 않더라도 API 환산 추정치가
표시될 수 있습니다. 기존 할당량, 예산 및 제공업체 기준의 정확한 비용 계산은 변경되지 않습니다.

이러한 진단은 기존의 범위가 제한된 캐시 상태 요약 및 호출 로그
보존 정책을 사용합니다. 요청 TTL 기본값, 라우팅 또는 계정 선택은 변경하지 않습니다.
제공업체로 전송하는 시점에 클라이언트가 요청한 TTL과 실제로 전송되는 TTL을
구분하여 기록하는 기능은 추후로 미뤄졌습니다. 이 패널은 실제 전송 TTL이 아니라 청구 내역에 나타난 등급을 보고합니다.

구현: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, `open-sse/utils/cacheWriteUsage.ts`.

## 비용 계산

비용은 LiteLLM에서 동기화된 **가격 데이터**(`src/lib/pricingSync.ts`)를 사용하여 계산됩니다.

| 모델              | 입력 $/1M | 출력 $/1M | 캐시 $/1M |
| ----------------- | --------- | --------- | --------- |
| gpt-5             | $2.50     | $10.00    | —         |
| claude-opus-4-6   | $15.00    | $75.00    | $1.50     |
| claude-sonnet-4-5 | $3.00     | $15.00    | $0.30     |
| gemini-2.5-pro    | $1.25     | $10.00    | —         |

비용 계산식(`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **캐시된 토큰을 프롬프트 토큰에서 빼는 이유는 무엇인가요?** 캐시된 부분은 별도로 가격이 책정되므로, 전체 프롬프트에 입력 가격을 적용하면 비용이 중복 계산됩니다.

### 가격 동기화

가격 데이터는 `/api/pricing/sync` 엔드포인트를 통해 LiteLLM에서 자동으로 동기화됩니다(사용자용 환경 변수가 아닌 내장 cron 작업에 의해 실행됨).

```bash
# 수동 실행
curl -X POST http://localhost:20128/api/pricing/sync
```

가격 데이터가 없는 모델의 경우 OmniRoute는 LiteLLM의 가격 데이터에서 가져온 내부 평균 요율을 사용하여 **비용을 추정**합니다.

## 날짜 범위 집계

`usageAnalytics.ts` 모듈은 원시 사용량 데이터로 대시보드 위젯을 계산합니다. 다음 7가지 기간을 지원합니다:

| 범위     | 기간                      | 사용 사례             |
| -------- | ------------------------- | --------------------- |
| `1d`     | 최근 24시간               | 시간별 비용 급증 감지 |
| `7d`     | 최근 7일                  | 주간 검토             |
| `30d`    | 최근 30일                 | 월별 청구             |
| `90d`    | 최근 90일                 | 분기별 분석           |
| `ytd`    | 올해 1월 1일부터 현재까지 | 연간 예산 추적        |
| `all`    | 전체 기간                 | 누적 통계             |
| `custom` | 사용자 지정 시작일/종료일 | 감사, 임시 쿼리       |

### 계산되는 대시보드 위젯

분석 계층은 모든 날짜 범위에 대해 다음을 계산합니다:

| 위젯                | 설명                                      |
| ------------------- | ----------------------------------------- |
| **요약 카드**       | 총 요청 수, 총비용, 총 토큰 수, 성공률    |
| **일별 추세 차트**  | 모델별로 누적한 일별 비용 + 토큰 수       |
| **활동 히트맵**     | 시간대 × 요일 격자, 색상 = 요청 수        |
| **모델별 분석**     | 모델별 비용 원형 차트                     |
| **제공업체별 분석** | 제공업체별 요청 수 막대 차트              |
| **상위 API 키**     | 비용 기준 상위 10개 키 표                 |
| **오류 분석**       | 시간 경과에 따른 오류율, 주요 오류 클래스 |

### 프로그래밍 방식 접근

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // 사용 이력 레코드
  "7d",                 // 기간: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // 제공업체 연결 맵 (connectionId → 계정 이름)
  {
    startDate: "2025-01-01",  // 선택 사항: "custom" 범위용
    endDate: "2025-06-01",   // 선택 사항: "custom" 범위용
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (센트)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## 할당량 적용

API 키별 할당량은 두 곳에서 적용됩니다:

1. **소프트 한도** (`quotaWarnAt`): 사용량이 임계값을 초과하면 대시보드에 경고 표시
2. **하드 한도** (`quotaLimit`): 초과하면 HTTP 429로 요청 거부

### 구성

```ts
// API 키별
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — 경고 표시
  quotaLimit: 10_00,    // $10.00 — 강제 중단
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### 적용 흐름

```
Request ──▶ quotaCheck()
              │
              ├── Within limit?  ──▶ allow
              │
              └── Over limit?  ──▶ 429 Too Many Requests
                                   with Retry-After header
```

### 할당량 스냅샷

`quotaSnapshots` 테이블은 추세 분석을 위해 **과거 할당량 상태**를 저장합니다:

| 필드 | 설명 |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | 추적 중인 키 |
| `window` | "day" | "week" | "month" |
| `used` | 이 기간에 사용한 비용(센트) |
| `limit` | 한도(센트) |
| `resetAt` | 기간이 초기화되는 시점 |
| `createdAt` | 스냅샷이 생성된 시점 |

스냅샷은 비용이 0보다 큰 **모든 요청에서** 생성되며, 다음 용도로 사용됩니다:

- 대시보드에 할당량 진행률 표시줄 렌더링
- 30일간의 할당량 추세 차트 표시
- 사용량이 한도에 가까워지면 알림 실행

## 보존 및 정리

사용량 데이터는 요청당 약 1~10KB씩 증가합니다. 규모가 커지면 상당한 용량을 차지할 수 있습니다.

### 보존 설정

사용량 이력 보존은 UI의 데이터베이스 설정 또는 `/api/settings/database`를 통해 구성합니다.

기본적으로 사용량 이력은 **90일** 동안 보존됩니다.

### 정리

오래된 기록은 `src/lib/db/cleanup.ts`에서 정리합니다:

- 백그라운드 cron 프로세스에 의해 실행됩니다
- `usage_history`에서 구성된 `usageHistory` 보존 기간보다 오래된 기록을 삭제합니다

### 저장 공간 추정

| 요청 빈도      | 30일 저장 공간 | 90일 저장 공간 |
| -------------- | -------------- | -------------- |
| 일일 100건     | 약 3MB         | 약 9MB         |
| 일일 1,000건   | 약 30MB        | 약 90MB        |
| 일일 10,000건  | 약 300MB       | 약 900MB       |
| 일일 100,000건 | 약 3GB         | 약 9GB         |

트래픽이 매우 많은 경우 다음을 고려하세요:

- 데이터베이스 설정에서 보존 기간 단축
- 원시 기록 대신 `aggregated_metrics` 사용(분석 전용)

## 비용 최적화 팁

### 1. 적절한 모델 사용

```bash
# 빠른 답변 — 저렴하고 빠른 모델 사용
curl -d '{"model":"auto/fast","messages":[...]}'

# 복잡한 작업 — 고품질 모델 사용
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. 캐싱 활성화

Anthropic 프롬프트 캐싱은 **반복되는 컨텍스트 비용을 90% 절감**합니다:

```ts
// 캐싱은 자동으로 이루어집니다 — 동일한 대용량 시스템 프롬프트를 포함하기만 하면 됩니다
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // 자동으로 캐싱됩니다
  messages: [{ role: "user", content: "..." }],
});
```

### 3. 압축 사용

RTK + Caveman 압축은 **도구 사용이 많은 세션에서 비용을 15-95% 절감**합니다:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. 키별 할당량 설정

비용이 과도하게 발생하지 않도록 항상 `quotaLimit`을 설정하세요:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // 월 $10 한도
```

### 5. 사용량이 많은 대상 점검

대시보드 또는 **`/api/usage/analytics`**를 사용하여 API 키별로 그룹화하고 비용순으로 정렬하세요:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## 문제 해결

### "비용이 예상보다 높음"

1. **`/api/usage/analytics?groupBy=model`** 확인 — 비용이 높은 모델 찾기
2. **`/api/usage/analytics?groupBy=apiKey`** 확인 — 사용량이 많은 대상 찾기
3. 가격 데이터가 최신인지 확인: `POST /api/pricing/sync`

### "기록 누락"

- 대시보드 → 데이터베이스 → 정리에서 DB 보존 설정 확인 — 오래된 기록은 주기적인 정리 작업(`src/lib/db/cleanup.ts`)에 의해 삭제됩니다
- `src/lib/db/usage*.ts`에서 오류 확인 — DB 쓰기 실패는 로그에 기록되지만 외부에 표시되지는 않습니다
- 요청이 실제로 `chatCore`에 도달했는지 확인 — 콤보 라우팅 확인

### "할당량 제한이 적용되지 않음"

- 키의 `quotaLimit` 설정 확인
- `quotaWindow`가 올바르게 설정되었는지 확인
- `quotaSnapshots` 기록 확인 — 요청마다 생성되어야 합니다
