## ఇది ఎలా పనిచేస్తుంది

```

Claude / Codex / OpenCode / Cline / KiloCode / Continue / Hermes Agent / Goose / ...
           │
           ▼  (అన్నీ OmniRoute వైపు మళ్లుతాయి)
    http://YOUR_SERVER:20128/v1
           │
           ▼  (OmniRoute సరైన ప్రొవైడర్కు రూట్ చేస్తుంది)
    Anthropic / OpenAI / Gemini / DeepSeek / Groq / Mistral / ...

ACP Agents (రివర్స్ స్పాన్ ప్రవాహం):
    క్లయింట్ అభ్యర్థన → OmniRoute → stdio/ACP ద్వారా CLIని ప్రారంభిస్తుంది → ప్రతిస్పందన
```

**ప్రయోజనాలు:**

- అన్ని సాధనాలను నిర్వహించడానికి ఒకే API కీ
- డ్యాష్బోర్డ్లో అన్ని CLIల వ్యయ ట్రాకింగ్
- ప్రతి సాధనాన్ని మళ్లీ కాన్ఫిగర్ చేయకుండానే మోడల్ మార్చడం
- స్థానికంగానూ, రిమోట్ సర్వర్లలోనూ పనిచేస్తుంది (VPS, Docker, Akamai, Cloudflare Tunnel)

## `setup-*`తో స్వయంచాలకంగా కాన్ఫిగర్ చేయడం

ప్రతి సాధనం యొక్క కాన్ఫిగరేషన్ను మీరు చేతితో వ్రాయాల్సిన అవసరం లేదు. అమలవుతున్న
OmniRoute (స్థానిక లేదా రిమోట్) నుండి **లైవ్** మోడల్ కేటలాగ్ను చదివి, మీ మెషీన్లో
ఆ సాధనం యొక్క స్వంత కాన్ఫిగరేషన్ను వ్రాసే `setup-*` కమాండ్ను, మద్దతు ఉన్న ప్రతి CLI కోసం
OmniRoute అందిస్తుంది:

```bash
omniroute setup-codex        omniroute setup-claude       omniroute setup-opencode
omniroute setup-cline        omniroute setup-kilo         omniroute setup-continue
omniroute setup-cursor       omniroute setup-roo          omniroute setup-crush
omniroute setup-goose        omniroute setup-qwen         omniroute setup-aider
omniroute setup-5dive        omniroute setup-zed
```

ప్రతి కమాండ్ `--remote <url> --api-key <key>` (రిమోట్ OmniRouteకు అనుగుణంగా స్థానిక
సాధనాన్ని కాన్ఫిగర్ చేయడం), `--dry-run` (వ్రాయకుండానే ప్రివ్యూ చూడడం), మరియు `--port`ను
ఆమోదిస్తుంది. మోడల్ స్వయంచాలక గుర్తింపు లేని సాధనాలు (Cline, Kilo, Roo, Goose, Aider,
Qwen, 5dive) `--model <id>`ను (మరియు ఇంటరాక్టివ్ కాని అమలుల కోసం `--yes`ను)
తీసుకుంటాయి. `$HOME` కింద వ్రాయని ఏకైక రెసిపీ `setup-5dive`: ఇది ఫ్లీట్ హోస్ట్లో
root యాజమాన్యంలోని auth ప్రొఫైల్ను వ్రాయడం ద్వారా 5dive ఏజెంట్ ఫ్లీట్ను కాన్ఫిగర్
చేస్తుంది, కాబట్టి ఇది `sudo` ద్వారా మళ్లీ అమలవుతుంది మరియు దీనికి స్వంత రిమోట్ మోడ్
లేదు. సరైన envను ఇంజెక్ట్ చేసి, ఎలాంటి కాన్ఫిగరేషన్నూ వ్రాయకుండా CLIని ప్రారంభించడానికి,
సాధారణ `omniroute run <target>` లాంచర్ను ఉపయోగించండి (claude, codex, aider, goose,
opencode, qwen, gemini — టార్గెట్లు మరియు అలియాస్లు `bin/cli/cli-manifest.mjs` నుండి
వస్తాయి); పాత, ఒక్కో సాధనానికి ప్రత్యేకమైన `omniroute launch` (Claude Code) మరియు
`omniroute launch-codex` (Codex) లాంచర్లు ఇప్పటికీ అందుబాటులో ఉన్నాయి. Gemini CLI
ప్రారంభించడానికి మాత్రమే ఉద్దేశించబడింది: ఇది `omniroute run` టార్గెట్, కానీ దీనికి
`setup-*`/`configure` రెసిపీ లేదు.

> **పూర్తి సూచిక:** ప్రతి కమాండ్ ఏమి వ్రాస్తుంది, ప్రతి ఫ్లాగ్, స్థానికం వర్సెస్ రిమోట్,
> మరియు ఏ సాధనాలకు `/v1` సఫిక్స్ అవసరం వంటి వివరాలతో కూడిన ప్రధాన పట్టిక
> **[CLI ఇంటిగ్రేషన్లు](../guides/CLI-INTEGRATIONS.md)**లో ఉంది.

### వీటిని కంటైనర్లో అమలు చేయడం

OmniRoute కంటైనర్లో అమలు చేసిన `setup-*` కమాండ్, కంటైనర్ యొక్క స్వంత homeలోకి
వ్రాస్తుంది; దాన్ని హోస్ట్లోని ఏ CLI కూడా చదవదు మరియు కంటైనర్తో పాటు అది కూడా
అదృశ్యమవుతుంది. OmniRoute దీన్ని గుర్తించి, వ్రాయడానికి బదులుగా సూచనలతో `2` కోడ్తో
నిష్క్రమిస్తుంది. ముందుకు వెళ్లడానికి మద్దతు ఉన్న రెండు మార్గాలు ఉన్నాయి — హోస్ట్లో
CLIని ఇన్స్టాల్ చేసి కంటైనర్కు `omniroute connect` చేయడం, లేదా కాన్ఫిగరేషన్ డైరెక్టరీలను
bind-mount చేసి `CLI_CONFIG_HOME`ను సెట్ చేయడం (compose `host` ప్రొఫైల్). ప్రతి
`setup-*` కమాండ్తో పాటు `omniroute configure` మరియు `omniroute config set` కూడా,
మీరు నిజంగా కంటైనర్ యొక్క స్వంత CLIలను కాన్ఫిగర్ చేయాలనుకున్నప్పుడు
`--allow-container-write`ను ఆమోదిస్తాయి; సర్వర్ కోసం
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` కూడా అదే పని చేస్తుంది. చూడండి:
[Docker గైడ్ → హోస్ట్ CLI సాధనాలను కాన్ఫిగర్ చేయడం](../guides/DOCKER_GUIDE.md#configuring-host-cli-tools-when-omniroute-runs-in-docker).

డాష్బోర్డ్ యొక్క **అప్లై ఎండ్పాయింట్** (`POST /api/cli-tools/apply`) కూడా ఇదే
రక్షణను అమలు చేస్తుంది: కంటైనర్లో, హోస్ట్ నుండి bind-mount చేయని టార్గెట్కు వ్రాయడానికి
ప్రయత్నిస్తే, సురక్షితమైన లోప సందేశంతో మరియు `containerEphemeralTarget: true`తో
**`422`** సమాధానం వస్తుంది; అలాగే హోస్ట్ రెసిపీ ఉన్న సాధనాల కోసం (claude, codex,
opencode, cline, kilo, continue), బదులుగా హోస్ట్లో అమలు చేయడానికి ఒక
`hostSetupCommand` (ఉదా. `omniroute setup-opencode`) కూడా అందుతుంది; ఏదీ వ్రాయబడదు.
కంటైనర్ మోడ్లో `dryRun: true` పని చేస్తూనే ఉంటుంది మరియు డిస్క్ను తాకకుండా సున్నితమైన
వివరాలు తొలగించిన ప్రివ్యూ + టార్గెట్ పాత్ను తిరిగి ఇస్తుంది. ప్రివ్యూ కంటెంట్ అనేది
కాపీ చేయడానికి లేదా ఇంపోర్ట్ చేయడానికి ఉద్దేశించిన, ఆధారాలను కలిగి ఉన్న కాన్ఫిగరేషన్
కాదు. అసలు సాధనం/base URL/API key/model ఇన్పుట్లతో హోస్ట్లో అప్లై చేయండి, లేదా
సూచించిన హోస్ట్-సైడ్ సెటప్ కమాండ్ను ఉపయోగించండి. ప్రివ్యూ హెడర్ మరియు రిక్వెస్ట్
కాంట్రాక్ట్ కోసం [CLI కాన్ఫిగరేషన్ భద్రత](../security/CLI-CONFIGURATION.md) చూడండి.
ఈ ప్రవర్తన ఉద్దేశపూర్వకమైనది మరియు
`tests/unit/api/cli-tools/apply-container-guard.test.ts` ద్వారా రిగ్రెషన్ నుండి
రక్షించబడుతుంది — ఈ రక్షణను తొలగించడం ద్వారా 422ను ఎప్పుడూ "పరిష్కరించవద్దు".

ప్రతి ఎంట్రీలో ఈ ఫీల్డ్లు ఉంటాయి (`src/shared/schemas/cliCatalog.ts`లో నిర్వచించబడ్డాయి):

| ఫీల్డ్                                          | రకం                                                          | వివరణ                                                        |
| ----------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `category`                                      | `"code" \| "agent"`                                          | టూల్ ఏ పేజీలో కనిపిస్తుందో                                   |
| `vendor`                                        | `string`                                                     | టూల్ మూలం ("Anthropic", "OSS (P. Gauthier)")                 |
| `acpSpawnable`                                  | `boolean`                                                    | ACP Agentగా కూడా ఉపయోగించవచ్చా (బ్యాడ్జ్ చూపబడుతుంది)        |
| `baseUrlSupport`                                | `"full" \| "partial" \| "none"`                              | అనుకూల ఎండ్పాయింట్ మద్దతు స్థాయి. `"none"` = MITM బ్యాక్లాగ్ |

`baseUrlSupport: "none"` ఉన్న ఎంట్రీలు డ్యాష్బోర్డ్ పేజీలలో **చూపబడవు** — అవి ప్లాన్ 11 కోసం MITM బ్యాక్లాగ్లో నమోదు చేయబడ్డాయి (`_tasks/features-v3.8.6/refactorpages/_orchestration/_plan11-mitm-backlog.md` చూడండి).

### సామర్థ్య స్థాయులు (కాటలాగ్ చేయబడినవి × గుర్తించదగినవి × కాన్ఫిగర్ చేయదగినవి × ప్రారంభించదగినవి)

కాటలాగ్ చేయబడిన ప్రతి టూల్ను గుర్తించడం, కాన్ఫిగర్ చేయడం లేదా ప్రారంభించడం సాధ్యం కాదు. ప్రతి స్థాయికి ఒక
ప్రకటన మూలం ఉంటుంది, అలాగే ఒక డ్రిఫ్ట్ పరీక్ష వాటిని సమలేఖనంలో ఉంచుతుంది:

| స్థాయి                  | అర్థం                                                                                       | దీనిలో ప్రకటించబడింది                                             |
| ----------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **కాటలాగ్ చేయబడినవి**   | డ్యాష్బోర్డ్ కాటలాగ్లో కనిపిస్తాయి (పేరు, విక్రేత, డాక్స్, కాన్ఫిగ్ రకం)                    | `src/shared/constants/cliTools.ts` (`CLI_TOOLS`)                  |
| **గుర్తించదగినవి**      | బైనరీ/కాన్ఫిగ్ గుర్తింపు, హెల్త్ చెక్లు, కాన్ఫిగ్ పాత్లు                                    | `src/shared/services/cliRuntime.ts` (`CLI_TOOLS` రన్టైమ్ కాటలాగ్) |
| **కాన్ఫిగర్ చేయదగినవి** | `omniroute configure <cli>` ద్వారా మద్దతు ఉంటుంది (సెటప్ రెసిపీ ఉంది)                       | `bin/cli/cli-manifest.mjs` (`configure: true`)                    |
| **ప్రారంభించదగినవి**    | `omniroute run <target>` ద్వారా మద్దతు ఉంటుంది (env/ఆర్గ్యుమెంట్ ఇంజెక్షన్ నిర్వచించబడింది) | `bin/cli/cli-manifest.mjs` (`run: true`)                          |

`bin/cli/cli-manifest.mjs` అనేది CLI కమాండ్
ఉపరితలాల కోసం ప్రామాణిక ఎగ్జిక్యూటబుల్ మానిఫెస్ట్: `run`, `configure` మరియు షెల్-కంప్లీషన్ జనరేటర్లు అన్నీ తమ
లక్ష్య జాబితాలు, అలియాస్ పరిష్కారం (ఉదాహరణకు `kilocode`/`kilo-code`/`kilo_cli` → `kilo`)
మరియు `--model` ఫ్లాగ్ వైరింగ్ను దీని నుంచే పొందుతాయి. డ్రిఫ్ట్ గార్డ్
`tests/unit/cli/cli-manifest-drift.test.ts`, మానిఫెస్ట్, రన్టైమ్
కాటలాగ్, UI కాటలాగ్ మరియు ప్రతి వినియోగదారు ఉపరితలం సమకాలీకరణలో ఉండేలా నిర్ధారిస్తుంది — ఇతర ఉపరితలాలకు జోడించకుండా
ఒక ఉపరితలానికి మాత్రమే లక్ష్యాన్ని జోడిస్తే, అది నిశ్శబ్దంగా డ్రిఫ్ట్ కావడానికి బదులుగా సూట్ విఫలమవుతుంది.

## 5. బ్యాచ్ డిటెక్షన్ API

అన్ని సాధనాల గుర్తింపు ఒకే ఎండ్పాయింట్ ద్వారా సమీకరించబడుతుంది:

**`GET /api/cli-tools/all-statuses`**

- ప్రామాణీకరణ: `requireCliToolsAuth(request)` (ఇతర `/api/cli-tools/` రూట్ల మాదిరిగానే)
- అందించేది: `Record<toolId, ToolBatchStatus>` (టైప్: `src/shared/types/cliBatchStatus.ts`)
- వ్యూహం: అన్ని సాధనాలపై `Promise.all`, ఒక్కో సాధనానికి 5s టైమ్అవుట్
- క్యాష్: కాన్ఫిగరేషన్ ఫైల్ `mtime` ద్వారా ఇండెక్స్ చేయబడిన ఇన్-మెమరీ LRU. mtime మారినప్పుడు క్యాష్ చెల్లుబాటు రద్దవుతుంది. సర్వర్ పునఃప్రారంభమైనప్పుడు రీసెట్ అవుతుంది.

ఒక్కో సాధనానికి రెస్పాన్స్ నిర్మాణం:

```ts
interface ToolBatchStatus {
  detection: {
    installed: boolean;
    runnable: boolean;
    version?: string;
    command?: string;
    commandPath?: string;
    reason?: string;
  };
  config: {
    status: "configured" | "not_configured" | "not_installed" | "unknown" | "other";
    endpoint?: string | null;
    lastConfiguredAt?: string | null;
  };
  error?: string; // శుద్ధీకరించబడింది, స్టాక్ ట్రేస్లు లేవు
}
```

#### VS Code Insiders (`chatLanguageModels.json`)

VS Code Insiders కస్టమ్ ఎండ్పాయింట్ మోడల్ల కోసం కాన్ఫిగర్ చేయబడి, కస్టమ్ హెడర్ ఫీల్డ్ లేకుండా OmniRoute పనిచేయాలని మీరు కోరుకున్నప్పుడు దీన్ని ఉపయోగించండి.

**సిఫార్సు చేసిన స్థానం:**

- Linux: `~/.config/Code - Insiders/User/chatLanguageModels.json`
- Windows: `%APPDATA%/Code - Insiders/User/chatLanguageModels.json`

**టోకెనైజ్ చేసిన OmniRoute అలియాస్ను ఉపయోగించే ఉదాహరణ:**

```json
[
  {
    "vendor": "customendpoint",
    "id": "auto",
    "name": "OmniRoute Auto",
    "family": "gpt-4",
    "version": "1.0.0",
    "url": "http://localhost:20128/api/v1/vscode/sk-your-omniroute-key/chat/completions",
    "modelsUrl": "http://localhost:20128/api/v1/vscode/sk-your-omniroute-key/models",
    "requestFormat": "openai-chat-completions",
    "contextWindow": 256000,
    "maxOutputTokens": 32768,
    "auth": {
      "type": "none"
    }
  }
]
```

**గమనికలు:**

- OmniRouteలో సృష్టించిన API కీతో `sk-your-omniroute-key`ను భర్తీ చేయండి.
- `url` ఫీల్డ్ `/api/v1/vscode/{token}/chat/completions`ను సూచించాలి.
- `modelsUrl` ఫీల్డ్ `/api/v1/vscode/{token}/models`ను సూచించాలి.
- క్లయింట్ అనుకూల హెడర్లకు మద్దతు ఇచ్చినప్పుడు, సాధారణ `/v1` + Bearer హెడర్ విధానానికి ప్రాధాన్యత ఇవ్వండి.
- URLలో పొందుపరిచిన టోకెన్లు అనుకూలత కోసం ఉపయోగించే ప్రత్యామ్నాయం; అవి ఎడిటర్ లాగ్లు లేదా ప్రాక్సీ చరిత్రలో కనిపించవచ్చు.

## 10. అంతర్గత OmniRoute CLI

`omniroute` బైనరీ సర్వర్ జీవితచక్రం, సెటప్, నిర్ధారణలు మరియు ప్రొవైడర్ నిర్వహణ కోసం కమాండ్లను అందిస్తుంది. ఎంట్రీ పాయింట్: `bin/omniroute.mjs`.

```bash
omniroute                              # సర్వర్ను ప్రారంభించండి (డిఫాల్ట్ పోర్ట్ 20128)
omniroute setup                        # ఇంటరాక్టివ్ సెటప్ విజార్డ్
omniroute doctor                       # కాన్ఫిగరేషన్, DB, పోర్ట్లు, రన్టైమ్ను తనిఖీ చేయండి
omniroute providers list               # కాన్ఫిగర్ చేసిన ప్రొవైడర్ కనెక్షన్లు
omniroute providers test-all           # ప్రతి సక్రియ కనెక్షన్ను పరీక్షించండి
omniroute reset-password               # అడ్మిన్ పాస్వర్డ్ను రీసెట్ చేయండి
omniroute logs                         # అభ్యర్థన లాగ్లను స్ట్రీమ్ చేయండి
omniroute health                       # వివరణాత్మక ఆరోగ్య స్థితి (బ్రేకర్లు, క్యాష్, మెమరీ)
omniroute --version                    # వెర్షన్ను ముద్రించండి
omniroute --help                       # అన్ని కమాండ్లను చూపండి
```

### సెటప్ & ప్రారంభీకరణ

```bash
omniroute setup                        # ఇంటరాక్టివ్ సెటప్ విజార్డ్
omniroute setup --non-interactive      # CI/ఆటోమేషన్ మోడ్ (env vars + ఫ్లాగ్లను చదువుతుంది)
omniroute setup --password '<value>'   # అడ్మిన్ పాస్వర్డ్ను నేరుగా సెట్ చేయండి
omniroute setup --add-provider \
  --provider openai \
  --api-key '<value>' \
  --test-provider                      # ఒకే ప్రయత్నంలో ప్రొవైడర్ను జోడించి పరీక్షించండి
```

నాన్-ఇంటరాక్టివ్ సెటప్ కోసం గుర్తించబడే ఎన్విరాన్మెంట్ వేరియబుల్లు:

| వేరియబుల్           | ప్రయోజనం                                                                       |
| ------------------- | ------------------------------------------------------------------------------ |
| `OMNIROUTE_API_KEY` | ప్రొవైడర్ API కీ (Commander `.env()` ద్వారా `--api-key`కు అనుసంధానించబడుతుంది) |
| `DATA_DIR`          | OmniRoute డేటా డైరెక్టరీని ఓవర్రైడ్ చేస్తుంది                                  |

ఇతర నాన్-ఇంటరాక్టివ్ ఇన్పుట్లన్నీ ఎన్విరాన్మెంట్ వేరియబుల్లుగా కాకుండా ఫ్లాగ్లుగా పంపబడతాయి:
`--password`, `--provider`, `--provider-name`, `--provider-base-url`, `--default-model`
(పైన ఉన్న `omniroute setup` ఎంపికలను చూడండి).

### నిర్ధారణలు

```bash
omniroute doctor                       # కాన్ఫిగరేషన్, DB, పోర్ట్లు, రన్టైమ్, మెమరీ, లైవ్నెస్ను తనిఖీ చేయండి
omniroute doctor --json                # మెషీన్ చదవగల JSON
omniroute doctor --no-liveness         # HTTP ఆరోగ్య ప్రోబ్ను దాటవేయండి
omniroute doctor --host 0.0.0.0        # లైవ్నెస్ హోస్ట్ను ఓవర్రైడ్ చేయండి
omniroute doctor --liveness-url <url>  # పూర్తి ఆరోగ్య ఎండ్పాయింట్ URLను ఓవర్రైడ్ చేయండి
```

doctor ఈ తనిఖీలను అమలు చేస్తుంది: `Config`, `Database`, `Storage/encryption`,
`Port availability`, `Node runtime`, `Native binary` (better-sqlite3),
`Memory`, మరియు `Server liveness`. ఏదైనా తనిఖీ `fail` అయితే ఇది సున్నా కాని నిష్క్రమణ కోడ్తో ముగుస్తుంది.

### ప్రొవైడర్ నిర్వహణ

```bash
omniroute providers available                       # OmniRoute ప్రొవైడర్ కేటలాగ్
omniroute providers available --search openai       # id/name/alias/category ఆధారంగా కేటలాగ్ను ఫిల్టర్ చేయండి
omniroute providers available --category api-key    # వర్గం ఆధారంగా ఫిల్టర్ చేయండి (api-key, oauth, free, ...)
omniroute providers available --json                # మెషీన్ చదవగల JSON

omniroute providers list                            # కాన్ఫిగర్ చేసిన ప్రొవైడర్ కనెక్షన్లు
omniroute providers list --json

omniroute providers test <id|name>                  # కాన్ఫిగర్ చేసిన ఒక కనెక్షన్ను పరీక్షించండి
omniroute providers test-all                        # ప్రతి సక్రియ కనెక్షన్ను పరీక్షించండి
omniroute providers validate                        # లోకల్-మాత్రమే నిర్మాణాత్మక ధ్రువీకరణ
omniroute providers add <provider> --credential-env PROVIDER_KEY
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth <provider>                 # ఇప్పటికే ఉన్న OAuth ప్రవాహం
omniroute providers edit <id|name> --default-model <model>
omniroute providers remove <id|name> --yes
```

`providers add/import/auth/edit/remove` API-ప్రథమ విధానాన్ని అనుసరిస్తాయి, అందువల్ల అవి
సక్రియ లోకల్ లేదా రిమోట్ సందర్భంపై పనిచేస్తాయి. క్రెడెన్షియల్ ఇన్పుట్ కోసం
`--credential-stdin` లేదా `--credential-env`ను ఉపయోగించాలి; `--dry-run --json` కేవలం
సవరించి దాచిన ఉనికి/ఆకృతిని మాత్రమే నివేదిస్తుంది. `providers available` OmniRoute కేటలాగ్ను చదువుతుంది;
`providers list/test/test-all/validate` తమ లోకల్ SQLite ప్రవర్తనను కొనసాగిస్తాయి మరియు
సర్వర్ నడుస్తూ ఉండాల్సిన అవసరం లేదు.

కస్టమ్ OpenAI-అనుకూల లేదా Anthropic-అనుకూల నోడ్ కోసం, `omniroute nodes add` తిరిగి ఇచ్చిన
నోడ్ IDకి క్రెడెన్షియల్లను జోడించడానికి `omniroute keys add "$NODE_ID" --stdin`ను ఉపయోగించండి.
దీనికి నడుస్తున్న సర్వర్ మరియు సక్రియ సందర్భం కోసం నిర్వహణ ప్రమాణీకరణ అవసరం.
CLI `POST /api/providers`ను ఉపయోగిస్తుంది; ఇది నోడ్ను ధ్రువీకరించి, దాని ఎండ్పాయింట్
సెట్టింగ్లను కనెక్షన్లోకి కాపీ చేస్తుంది. నోడ్ లేకపోవడం, అధికార వైఫల్యం లేదా అందుబాటులో లేని
సర్వర్ వల్ల లోకల్ ఫాల్బ్యాక్ క్రెడెన్షియల్ను సృష్టించకుండానే లోపం తిరిగి వస్తుంది.

`nodes add --base-url` నోడ్ ఎండ్పాయింట్ను సెట్ చేస్తుంది; ఇది
`OMNIROUTE_BASE_URL`లోని సర్వర్ చిరునామాకు భిన్నమైనది. OpenAPI ఫైల్ల కోసం,
`omniroute openapi dump --format json --out ./openapi.json`ను ఉపయోగించండి; గ్లోబల్ `--output`
CLI ప్రదర్శన ఫార్మాటింగ్ను ఎంచుకుంటుంది, గమ్యస్థాన ఫైల్ పేరును కాదు.

### పునరుద్ధరణ & రీసెట్

```bash
omniroute reset-password                # అడ్మిన్ పాస్వర్డ్ను రీసెట్ చేయండి (ఇంకా: omniroute-reset-password)
omniroute reset-encrypted-columns       # ఎన్క్రిప్ట్ చేసిన క్రెడెన్షియల్ రీసెట్ కోసం హెచ్చరిక + డ్రై-రన్ను చూపండి
omniroute reset-encrypted-columns --force  # SQLiteలోని ఎన్క్రిప్ట్ చేసిన క్రెడెన్షియల్లను నిజంగా nullగా మార్చండి
```

### క్రెడెన్షియల్ ఎగుమతి (⚠ జాగ్రత్తగా నిర్వహించండి)

```bash
omniroute auth export                                 # హెచ్చరిక + నిర్ధారణ గేట్ను చూపండి — DB యాక్సెస్ లేదు
omniroute auth export --force                          # అన్ని కనెక్షన్ల డీక్రిప్ట్ చేసిన క్రెడెన్షియల్లను JSONగా stdoutకు ఎగుమతి చేయండి
omniroute auth export --force --id <id>                 # సరిపోలే కనెక్షన్ను మాత్రమే ఎగుమతి చేయండి
omniroute auth export --force --format env               # OMNIROUTE_<PROVIDER>_<FIELD>=<value> పంక్తులను విడుదల చేయండి
omniroute auth export --force --out creds.json           # ఫైల్కు వ్రాయండి (0600 అనుమతులతో సృష్టించబడుతుంది)
```

`auth export` అనేది **లోకల్లో మాత్రమే** పనిచేస్తుంది (నేరుగా SQLite రీడ్ చేస్తుంది, HTTP రూట్ ఉండదు) మరియు ఉద్దేశపూర్వకంగానే
**ప్లెయిన్టెక్స్ట్** `apiKey`/`accessToken`/`refreshToken`/`idToken` విలువలను ప్రింట్ చేస్తుంది/వ్రాస్తుంది — ఇది ఒక ఫీచర్,
బగ్ కాదు. `--force` లేకుండా డేటాబేస్ నుండి ఏదీ చదవబడదు మరియు ఏదీ డీక్రిప్ట్ చేయబడదు. ఏదైనా ప్లెయిన్టెక్స్ట్ను విడుదల చేయడానికి ముందు stderrలో
హెచ్చరిక బ్యానర్ ఎల్లప్పుడూ ప్రింట్ అవుతుంది. `STORAGE_ENCRYPTION_KEY` తప్పనిసరిగా
సెట్ చేయబడి ఉండాలి. డీక్రిప్ట్ చేయడంలో విఫలమైన ఫీల్డ్ (కాలం చెల్లిన కీ, పాడైన సైఫర్టెక్స్ట్) మొత్తం ఎక్స్పోర్ట్ను నిలిపివేయడానికి లేదా అంతర్లీన ఎర్రర్ను బహిర్గతం చేయడానికి బదులుగా
`<field>DecryptFailed: true`గా నివేదించబడుతుంది.

### ఇతర సబ్కమాండ్లు

ప్రత్యేకంగా పేర్కొనకపోతే, ఇవి రన్ అవుతున్న OmniRoute సర్వర్ ఉందని భావిస్తాయి:

```bash
omniroute status                       # సమగ్ర రన్టైమ్ స్థితి
omniroute logs                         # రిక్వెస్ట్ లాగ్లను స్ట్రీమ్ చేయండి (--json, --search, --follow)
omniroute config list                  # కాన్ఫిగర్ చేసిన CLI టూల్లను ప్రదర్శించండి

omniroute provider list                # అందుబాటులో ఉన్న ప్రొవైడర్లను జాబితా చేయండి (providers listకు అలియాస్)
omniroute provider add                 # ఒక టూల్లో OmniRouteను ప్రొవైడర్గా నమోదు చేయండి
omniroute keys add | list | remove     # API కీలను నిర్వహించండి
omniroute models [provider]            # మోడల్లను జాబితా చేయండి (--json, --search)
omniroute combo list | switch | create | delete

omniroute backup                       # కాన్ఫిగ్ + DB స్నాప్షాట్ను సృష్టించండి
omniroute restore                      # మునుపటి స్నాప్షాట్ నుండి పునరుద్ధరించండి

omniroute health                       # వివరణాత్మక హెల్త్ స్థితి (బ్రేకర్లు, క్యాష్, మెమరీ)
omniroute quota                        # ప్రొవైడర్ కోటా వినియోగం
omniroute cache                        # క్యాష్ స్థితి
omniroute cache clear                  # సెమాంటిక్ + సిగ్నేచర్ క్యాష్లను క్లియర్ చేయండి

omniroute mcp status | restart         # MCP సర్వర్ స్థితి / రీస్టార్ట్
omniroute a2a status | card            # A2A సర్వర్ స్థితి / ఏజెంట్ కార్డ్

omniroute tunnel list | create | stop  # టన్నెల్లను నిర్వహించండి (cloudflare/tailscale/ngrok)
omniroute env show | get <k> | set <k> <v>  # env వేరియబుల్లను పరిశీలించండి / సెట్ చేయండి (తాత్కాలికం)

omniroute test                         # ప్రొవైడర్ కనెక్టివిటీ స్మోక్ టెస్ట్
omniroute update                       # అప్డేట్ల కోసం తనిఖీ చేయండి
omniroute completion                   # షెల్ కంప్లీషన్ను రూపొందించండి
```

## OmniRoute CLIతో ఇన్ఫరెన్స్-కీ విధానాన్ని నిర్వహించండి

ఇప్పటికే ఉన్న ఇన్ఫరెన్స్ కీని దాని ID ద్వారా పరిశీలించడానికి లేదా నవీకరించడానికి ప్రామాణీకరించిన నిర్వహణ సందర్భాన్ని ఉపయోగించండి ([రిమోట్ మోడ్](../guides/REMOTE-MODE.md) చూడండి):

```bash
omniroute --output json keys policy show KEY_ID
omniroute keys policy set KEY_ID --unrestricted
omniroute --output json keys policy show KEY_ID
```

`--unrestricted` అనేది `--model-access-mode all`కు మారుపేరు. ఈ నవీకరణ మోడల్ అనుమతి జాబితాను తొలగిస్తుంది. ఇది స్కోప్లు, కనెక్షన్ నియమాలు, బ్లాక్ చేసిన మోడళ్లు, రేట్ పరిమితులు మరియు ఖర్చు పరిమితులను అలాగే ఉంచుతుంది, కాబట్టి ఆ ఇతర నియంత్రణలు ఇప్పటికీ అభ్యర్థనను తిరస్కరించగలవు. స్పష్టంగా పేర్కొన్న `--allowed-models ""` కూడా `all`ను ఎంచుకుంటుంది; అనుమతించిన మోడళ్లు లేని పరిమిత కీని కొనసాగించడానికి దాన్ని `--model-access-mode restricted`తో కలపండి. స్పష్టంగా వేరేలా పేర్కొనకపోతే, ఖాళీ కాని కామాలతో వేరు చేసిన జాబితా `restricted`ను ఎంచుకుంటుంది. పరస్పర విరుద్ధమైన `all`తో పాటు ఖాళీ కాని అనుమతి జాబితా ఉంటే, అభ్యర్థనను పంపడానికి ముందే తిరస్కరించబడుతుంది.

`--rate-limit 30` నిమిషానికి అభ్యర్థనల సంఖ్యను సెట్ చేస్తుంది మరియు ఇతర సమయ విండోల నియమాలను అలాగే ఉంచుతుంది. `--max-cost 5` వారపు పరిమితిని మార్చకుండా రోజువారీ USD పరిమితిని ప్రారంభిస్తుంది; `--max-cost 0` రోజువారీ పరిమితిని తొలగించి, ఇప్పటికే ఉన్న వినియోగ-పరిమితి టాగుల్ మరియు వారపు పరిమితిని అలాగే ఉంచుతుంది. పేర్కొనని విధాన ఫీల్డ్లు మారకుండా ఉంటాయి. రేట్ మార్పులు ముందుగా ప్రస్తుత విధానాన్ని చదువుతాయి; ఒకే కీకి చెందిన రేట్-లిమిట్ అర్రేపై ఏకకాల సవరణలను నివారించండి.

విధాన కమాండ్లు ప్రామాణీకరించిన `GET`/`PATCH /api/keys/{id}`ను ఉపయోగిస్తాయి మరియు సక్రియ సందర్భాన్ని, గ్లోబల్ `--api-key` ఎంపికను గౌరవిస్తాయి. JSON అవుట్పుట్లో నిల్వ చేసిన కీ లేదా దాని మాస్క్ చేసిన రూపం లేకుండా, విధాన ఫీల్డ్లు మాత్రమే ఉంటాయి. ఇన్ఫరెన్స్కు మాత్రమే పరిమితమైన క్రెడెన్షియల్ నిర్వహణ మార్పులకు అధికారం ఇవ్వలేదు. 401/403 వచ్చినప్పుడు నిర్వహణ క్రెడెన్షియల్ మరియు సందర్భాన్ని తనిఖీ చేయాలి; అది స్థానిక CLI-టోకెన్ లేదా సాల్ట్ వైఫల్యాన్ని నిర్ధారించదు. ప్రత్యేక స్థానిక ప్రామాణీకరణ ఒప్పందం కోసం [CLI టోకెన్](../security/CLI_TOKEN.md) చూడండి.
