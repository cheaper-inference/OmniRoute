## చాట్ కంప్లీషన్లు

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### అనుకూల హెడర్లు

| హెడర్                    | దిశ         | వివరణ                                                                                                                                                                                                              |
| ------------------------ | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `X-OmniRoute-No-Cache`   | అభ్యర్థన    | క్యాష్ను దాటవేయడానికి `true`గా సెట్ చేయండి                                                                                                                                                                         |
| `x-omniroute-no-memory`  | అభ్యర్థన    | ఈ అభ్యర్థన కోసం మెమరీ + నైపుణ్యాల ఇంజెక్షన్ను దాటవేయడానికి `true`గా సెట్ చేయండి (నో-క్యాష్ను ప్రతిబింబిస్తుంది; ఒక్కో కాల్కు వచ్చే టోకెన్/ఖర్చు అదనపు భారాన్ని నివారిస్తుంది)                                      |
| `X-OmniRoute-Progress`   | అభ్యర్థన    | పురోగతి ఈవెంట్ల కోసం `true`గా సెట్ చేయండి                                                                                                                                                                          |
| `X-Session-Id`           | అభ్యర్థన    | బాహ్య సెషన్ అనుబంధం కోసం స్టికీ సెషన్ కీ                                                                                                                                                                           |
| `x_session_id`           | అభ్యర్థన    | అండర్స్కోర్ రూపాంతరం కూడా ఆమోదించబడుతుంది (ప్రత్యక్ష HTTP)                                                                                                                                                         |
| `X-OmniRoute-Session-Id` | అభ్యర్థన    | కాలర్ అందించిన సెషన్/సంభాషణ ట్యాగ్ (మెమరీకి కూడా అందించబడుతుంది). ఇది ఉన్నప్పుడు, ఒక్కో సెషన్ ఖర్చు కేటాయింపు కోసం `call_logs.session_tag`లో యథాతథంగా నిల్వ చేయబడుతుంది (#8249) — లేనప్పుడు ఎప్పటికీ రూపొందించబడదు |
| `Idempotency-Key`        | అభ్యర్థన    | డీడప్ కీ (5s విండో)                                                                                                                                                                                                |
| `X-Request-Id`           | అభ్యర్థన    | ప్రత్యామ్నాయ డీడప్ కీ                                                                                                                                                                                              |
| `x-omniroute-connection` | అభ్యర్థన    | ఒకే-మోడల్ అభ్యర్థనను దాని id ద్వారా ఒక ప్రొవైడర్ కనెక్షన్కు (ఖాతాకు) పిన్ చేయండి — [ఒక్కో అభ్యర్థనకు ఖాతా పిన్నింగ్](#account-pinning-per-request) చూడండి                                                          |
| `X-OmniRoute-Cache`      | ప్రతిస్పందన | `HIT` లేదా `MISS` (నాన్-స్ట్రీమింగ్)                                                                                                                                                                               |
| `X-OmniRoute-Idempotent` | ప్రతిస్పందన | డీడూప్లికేట్ చేయబడితే `true`                                                                                                                                                                                       |
| `X-OmniRoute-Progress`   | ప్రతిస్పందన | పురోగతి ట్రాకింగ్ ఆన్లో ఉంటే `enabled`                                                                                                                                                                             |
| `X-OmniRoute-Session-Id` | ప్రతిస్పందన | OmniRoute ఉపయోగించిన ప్రభావవంతమైన సెషన్ ID                                                                                                                                                                         |
| `X-OmniRoute-Request-Id` | ప్రతిస్పందన | అభ్యర్థన సహసంబంధ id (తెలిసినప్పుడు)                                                                                                                                                                                |
| `X-OmniRoute-Version`    | ప్రతిస్పందన | OmniRoute బిల్డ్ వెర్షన్ (ఎల్లప్పుడూ ఉంటుంది)                                                                                                                                                                      |
| `X-OmniRoute-Cost-Saved` | ప్రతిస్పందన | HITపై క్యాష్ నివారించిన USD ఖర్చు (క్యాష్ హిట్లకు మాత్రమే)                                                                                                                                                         |
| `X-OmniRoute-Decision`   | ప్రతిస్పందన | రూటింగ్ ట్రేస్: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` అనేది కాంబో వ్యూహం, లేదా నాన్-కాంబో అభ్యర్థనకు `single`) — పూర్తి ప్రతిస్పందనలలో ఎల్లప్పుడూ ఉంటుంది                                  |

> Nginx గమనిక: మీరు అండర్స్కోర్ హెడర్లపై (ఉదాహరణకు `x_session_id`) ఆధారపడితే, `underscores_in_headers on;`ను ప్రారంభించండి.

#### ఒక్కో అభ్యర్థనకు ఖాతా పిన్నింగ్

ఒక ప్రొవైడర్కు అనేక కనెక్షన్లు (ఖాతాలు లేదా కీలు) ఉన్నప్పుడు, OmniRoute సాధారణంగా తన ఖాతా-ఎంపిక వ్యూహం ద్వారా ఒకదాన్ని ఎంచుకుంటుంది.
దానికి బదులుగా, ఒక అభ్యర్థన `x-omniroute-connection` హెడర్తో ఒక నిర్దిష్ట కనెక్షన్ను పిన్ చేయవచ్చు:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id ఎక్కడ కనుగొనాలి.** డ్యాష్బోర్డ్లో ప్రొవైడర్ పేజీని తెరవండి
  (**డ్యాష్బోర్డ్ → ప్రొవైడర్లు → <provider>**) మరియు కనెక్షన్ వరుసలోని `xxxxxxxx…` id చిప్పై క్లిక్ చేయండి
  — అది పూర్తి కనెక్షన్ idని కాపీ చేస్తుంది.
- **ఏ అభ్యర్థనలు దీన్ని గౌరవిస్తాయి.** `/v1/chat/completions`, `/v1/messages` మరియు
  `/v1/responses`లోని సింగిల్-మోడల్ అభ్యర్థనలు (`provider/model`). కాంబోలు ఈ హెడర్ను విస్మరిస్తాయి:
  బదులుగా ప్రతి కాంబో దశకు, ఆ దశ యొక్క స్వంత కనెక్షన్ ద్వారా ఒక ఖాతాను పిన్ చేయండి.
- **పిన్ ఖచ్చితమైనది, ప్రాధాన్యత మాత్రమే కాదు.** పిన్ చేసిన కనెక్షన్ మాత్రమే ప్రత్యేకంగా ఉపయోగించబడుతుంది.
  అభ్యర్థనలో వైఫల్యం సంభవిస్తే, ఖాతా యొక్క కూల్డౌన్ నమోదు అవుతుంది కానీ అదే ప్రొవైడర్కు చెందిన
  మరొక ఖాతాకు **మారదు**.
- **కూల్డౌన్ మరియు కోటా పిన్ను విడుదల చేస్తాయి.** పిన్ చేసిన కనెక్షన్ కూల్డౌన్లో ఉన్నప్పుడు,
  కోటా పూర్తిగా వినియోగించబడినప్పుడు లేదా కోటా పాలసీ ద్వారా బ్లాక్ చేయబడినప్పుడు, తదుపరి అభ్యర్థనలు
  పిన్ చేయని ట్రాఫిక్ మాదిరిగానే ప్రొవైడర్ యొక్క ఇతర కనెక్షన్లకు ఫాల్బ్యాక్ అవుతాయి.
- **తెలియని లేదా నిలిపివేసిన ids విఫలమవుతాయి.** ప్రొవైడర్ యొక్క యాక్టివ్ పూల్లో లేని id (తొలగించబడినది,
  డీయాక్టివేట్ చేయబడినది లేదా మరొక ప్రొవైడర్కు చెందినది) అర్హమైన ఖాతా ఏదీ లేకుండా చేస్తుంది, కాబట్టి అభ్యర్థన
  నిశ్శబ్దంగా వేరే చోటుకు రూట్ చేయబడటానికి బదులుగా విఫలమవుతుంది.

Claude Code, `ANTHROPIC_CUSTOM_HEADERS` ద్వారా కస్టమ్ హెడర్లను పంపుతుంది. ప్రతి ప్రాజెక్ట్కు వేరే
ఖాతాను పిన్ చేయడానికి దీన్ని `~/.claude/settings.json`లోని `env` బ్లాక్లో లేదా ప్రాజెక్ట్-స్థాయి
`.claude/settings.json`లో ఉంచండి:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

మూలం: `src/sse/handlers/chat.ts` (హెడర్ రీడ్), `src/sse/services/auth.ts` మరియు
`src/sse/services/sessionAffinityPin.ts` (పిన్ విడుదల మరియు పూల్లో లేకపోవడాన్ని తనిఖీ చేయడం).

> **ఖర్చు టెలిమెట్రీ హెడర్లు:** నాన్-స్ట్రీమింగ్ విజయవంతమైన ప్రతిస్పందనలు `X-OmniRoute-*` ఖర్చు-టెలిమెట్రీ సెట్ను కూడా కలిగి ఉంటాయి — `X-OmniRoute-Response-Cost` (USD, స్థిరంగా 10 దశాంశ స్థానాలు; ఉచిత/ధర నిర్ణయించని వాటికి `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit`, మరియు `X-OmniRoute-Fallback-Attempts` (> 0 అయినప్పుడు మాత్రమే), వీటితో పాటు `X-OmniRoute-Request-Id` మరియు `X-OmniRoute-Version`. ఇవి చాట్ కంప్లీషన్లు, `/v1/responses`, `/v1/messages`, **మరియు మీడియా ఎండ్పాయింట్ల** ద్వారా విడుదల చేయబడతాయి — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations`, మరియు `/v1/moderations` (ఖర్చు ఎల్లప్పుడూ `0`). ధర అందుబాటులో ఉన్నప్పుడు మీడియా ఖర్చు ప్రతి మోడాలిటీ ప్రాతిపదికన (ప్రతి చిత్రం, ప్రతి సెకను, ప్రతి అక్షరం, ప్రతి సెర్చ్-యూనిట్) లెక్కించబడుతుంది; లేకపోతే `0` (ఫెయిల్-ఓపెన్).

> **క్యాష్-హిట్ ఖర్చు సెమాంటిక్స్:** సెమాంటిక్-క్యాష్ HIT (`X-OmniRoute-Cache-Hit: true`)లో అప్స్ట్రీమ్ కాల్ జరగదు, కాబట్టి `X-OmniRoute-Response-Cost` అనేది `0.0000000000` (హిట్ను అందించడానికి అయ్యే **అదనపు** ఖర్చు). అసలు/అయ్యుండే ఖర్చు `X-OmniRoute-Cost-Saved`లో విడిగా నివేదించబడుతుంది. బిల్లింగ్ వినియోగదారులు `X-OmniRoute-Response-Cost` మొత్తాన్ని లెక్కించాలి (హిట్లకు ఖర్చు ఉండదు); క్యాష్ అనలిటిక్స్ `X-OmniRoute-Cost-Saved`ను సమీకరించవచ్చు.

## ప్రత్యేకంగా నిర్వహించబడే సెషన్ లీజులు

ప్రత్యేకంగా నిర్వహించబడే సెషన్ లీజింగ్ అనేది ఒక ఆప్ట్-ఇన్, క్లయింట్-న్యూట్రల్ రూటింగ్ కాంట్రాక్ట్: ఒక యాక్టివ్ ఓనర్ ఒక అర్హత కలిగిన ఓమ్నిరూట్ కనెక్షన్ను కలిగి ఉంటుంది. ఇది ఒక మోడల్ను లీజుకు ఇవ్వదు, OAuth అవసరం లేదు, ఒక నిర్దిష్ట క్లయింట్ను గుర్తించదు లేదా ఒక నిర్దిష్ట ప్రొవైడర్ అవసరం లేదు.

అథెంటికేటింగ్ API కీకి `lease:exclusive` స్కోప్ మరియు స్పష్టమైన ఖాళీ లేని `allowedConnections` జాబితా ఉండాలి. డేటాబేస్ మ్యుటేషన్ బౌండరీ కీ సృష్టి మరియు పాక్షిక అప్డేట్లలో రెండు ఫీల్డ్లను కలిసి అమలు చేస్తుంది.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

విజయవంతమైన అక్వైర్, రెన్యూ మరియు రిలీజ్ ప్రతిస్పందనలు టైమ్స్టాంప్లు, `state` మరియు ఖచ్చితమైన పాజిటివ్ `generation`ను బహిర్గతం చేస్తాయి, కానీ ఎంచుకున్న కనెక్షన్ లేదా ఆధారాలను ఎప్పుడూ బహిర్గతం చేయవు. రెన్యూ మరియు రిలీజ్ JSON బాడీలో జనరేషన్ను అందిస్తాయి:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

ఒక యాక్టివ్ లీజు యజమాని దాని ప్రస్తుత బైండింగ్ కోసం గోప్యతా-సురక్షిత డిస్ప్లే మెటాడేటాను స్పష్టంగా అభ్యర్థించవచ్చు:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

ఈ ఆప్ట్-ఇన్ స్టేటస్ చర్య అపారదర్శక యజమాని, ప్రామాణీకరించబడిన నిర్వహించబడే API కీ మరియు ఒక డేటాబేస్ లావాదేవీలో ఖచ్చితమైన యాక్టివ్ జనరేషన్ ద్వారా ఫెన్స్ చేయబడుతుంది. `displayName` అనేది ట్రిమ్ చేయబడిన కాన్ఫిగర్ చేయబడిన కనెక్షన్ పేరు మాత్రమే; సురక్షితమైన కాన్ఫిగర్ చేయబడిన పేరు లేనప్పుడు అది `null` అవుతుంది. ఓమ్నిరూట్ ఎప్పుడూ ఇమెయిల్ లేదా రూపొందించబడిన ఖాతా గుర్తింపును ప్రత్యామ్నాయం చేయదు. ప్రొవైడర్ విలువ అనేది సున్నితత్వం లేని డిస్ప్లే లేబుల్ మరియు ఎప్పుడూ రూపొందించబడిన అనుకూల-ప్రొవైడర్ ఐడెంటిఫైయర్ కాదు. ఆధారాలు, టోకెన్లు, కుకీలు, రా కనెక్షన్ లేదా API కీ ఐడిలు, యజమాని హాష్లు, ఫెన్సింగ్ సీక్రెట్లు మరియు అంతర్గత రూటింగ్ డేటా మినహాయించబడతాయి.

తప్పు-కీ, తప్పు-యజమాని, పాత-జనరేషన్, తప్పిపోయిన, గడువు ముగిసిన, విడుదల చేయబడిన మరియు చెల్లని లుకప్లు అన్నీ కనెక్షన్ మెటాడేటా లేకుండా అదే `409 LEASE_FENCE_STALE` లోపాన్ని తిరిగి ఇస్తాయి. సామర్థ్యం-వేచి ఉన్న ప్రతిస్పందనను అందుకున్న క్లయింట్కు తనిఖీ చేయడానికి యాక్టివ్ బైండింగ్ లేదు. రూటింగ్ యాక్టివ్ లీజును మార్చినప్పుడు, అదే జనరేషన్ చెల్లుబాటు అవుతుంది మరియు స్టేటస్ అణువుగా కొత్త బైండింగ్ను తిరిగి ఇస్తుంది, పాతదాన్ని ఎప్పుడూ తిరిగి ఇవ్వదు. అక్వైర్, రెన్యూ, రిలీజ్ మరియు వేచి ఉన్న ప్రతిస్పందనలు వాటి మునుపటి ఆకృతులను నిలుపుకుంటాయి కాబట్టి ఇప్పటికే ఉన్న క్లయింట్లు మారవు.

ఈ సర్వర్ కాంట్రాక్ట్ స్టాక్ OpenAI Codex `/status`ను మార్చదు. స్టాక్ కోడెక్ ప్రస్తుతం దాని మోడల్ ప్రొవైడర్ మరియు అంతర్నిర్మిత అథెంటికేషన్/ఖాతా స్థితిని నివేదిస్తుంది కానీ ఏకపక్ష కస్టమ్ ప్రొవైడర్ ఖాతా మెటాడేటాను రెండర్ చేయదు; తదుపరి క్లయింట్ ఇంటిగ్రేషన్ ఈ చర్యను పిలవాలి మరియు `connection.displayName`ను ఎలా ప్రదర్శించాలో నిర్ణయించుకోవాలి.

ప్రతి నిర్వహించబడే ఇన్ఫరెన్స్ అభ్యర్థన అప్పుడు రెండు నియంత్రణ హెడర్లను అందిస్తుంది:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ఖచ్చితమైన యజమాని, జనరేషన్, యాక్టివ్ కనెక్షన్ మరియు ప్రామాణీకరించబడిన API కీ ప్రతి మద్దతు ఉన్న అప్స్ట్రీమ్ ప్రయత్నానికి ముందు వెంటనే ఫెన్స్ చేయబడతాయి. మరొక కీతో యజమాని మరియు జనరేషన్ను రీప్లే చేయడం విఫలమవుతుంది, ఆ కీ అదే కనెక్షన్ను అనుమతించినప్పటికీ. రా యజమానులు నిల్వ చేయబడరు, లాగ్ చేయబడరు, అభ్యర్థన స్నాప్షాట్లో నిలుపుకోబడరు లేదా అప్స్ట్రీమ్కు ఫార్వార్డ్ చేయబడరు.

తాత్కాలిక వివాదం HTTP `429`ను `Retry-After` మరియు:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

ఈ ప్రతిస్పందన సాధారణ అర్హత కలిగిన సెట్ ఖాళీగా లేదని మరియు ప్రతి ఉచిత అభ్యర్థి విదేశీ యాక్టివ్ లీజు ద్వారా కలిగి ఉన్నారని మాత్రమే అర్థం. మద్దతు లేని మోడల్లు/ప్రొవైడర్లు, పాలసీ సరిపోలకపోవడం, కూల్డౌన్, కోటా, ఆరోగ్యం మరియు ఇతర సాధారణ అర్హత వైఫల్యాలు వాటి ఇప్పటికే ఉన్న ఓమ్నిరూట్ ప్రతిస్పందనలను నిలుపుకుంటాయి.

### `x-omniroute-compression`

కంప్రెషన్ ప్లాన్ యొక్క ప్రతి-అభ్యర్థన ఓవర్రైడ్. అత్యధిక ప్రాధాన్యత — రూటింగ్-కాంబో ఓవర్రైడ్, యాక్టివ్ ప్రొఫైల్, ఆటో-ట్రిగ్గర్ మరియు ప్యానెల్ డిఫాల్ట్ను అధిగమిస్తుంది. విలువలు:

| విలువ         | ప్రభావం                                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------- |
| `off`         | ఈ అభ్యర్థన కోసం కంప్రెషన్ లేదు.                                                                         |
| `default`     | ప్యానెల్-ఉత్పన్న డిఫాల్ట్ ప్రొఫైల్ (యాక్టివ్ ప్రొఫైల్ను విస్మరిస్తుంది). లాస్సీ ఇంజిన్లు ఆఫ్ చేయబడతాయి. |
| `safe`        | డెడప్ మరియు వైట్స్పేస్ ఫోల్డింగ్ మాత్రమే.                                                               |
| `allow-lossy` | సారాంశాలు మరియు స్టైల్ రీరైట్లతో సహా ఈ అభ్యర్థన కోసం ఆపరేటర్ ప్లాన్ను ఉంచండి.                           |
| `engine:<id>` | ప్రారంభించబడినప్పుడు ఒకే ఇంజిన్, ఉదా. `engine:rtk`. ఆ ఇంజిన్ కోసం ప్రతి-అభ్యర్థన ఆప్ట్-ఇన్.             |
| `<combo>`     | పేరు ద్వారా సరిపోలిన (కేస్-ఇన్సెన్సిటివ్) పేరున్న కాంబో, ఆపై ఐడి ద్వారా.                                |

గమనికలు:

- తెలియని విలువలు విస్మరించబడతాయి (అభ్యర్థన ఎప్పుడూ తిరస్కరించబడదు); రిజల్యూషన్ సాధారణ ఆపరేటర్ ప్రాధాన్యతకు వస్తుంది.
- బహుళ కాంబోలు ఒక పేరును పంచుకుంటే, నిర్ణయాత్మక సరిపోలిక కోసం కాంబో **id**ని పాస్ చేయండి.
- `off` లేదా `default` అనే పేరు ఉన్న కాంబోను పేరు ద్వారా ఎంచుకోలేము (ఆ కీలకపదాలు మొదట అర్థం చేసుకోబడతాయి); అటువంటి కాంబోను దాని id ద్వారా సూచించండి.
- మాస్టర్ కంప్రెషన్ స్విచ్ ఒక హార్డ్ గేట్: కంప్రెషన్ ప్రపంచవ్యాప్తంగా నిలిపివేయబడినప్పుడు, ఈ హెడర్ దానిని ప్రారంభించదు.

వర్తించిన ప్లాన్ ప్రతిస్పందన హెడర్లో తిరిగి ప్రతిధ్వనిస్తుంది:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

ఇక్కడ `<source>` అనేది `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` లేదా `off` లలో ఒకటి.

## ఎంబెడింగ్స్

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

అందుబాటులో ఉన్న ప్రొవైడర్లు: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

కేటలాగ్ ఐడీలు `provider/model` ఆకృతిలో ఉంటాయి (ఉదాహరణ: `jina-ai/jina-embeddings-v5-omni-small`). రిజిస్ట్రీలో కనిపించే ప్రొవైడర్ ప్రిఫిక్స్ లేని Jina మోడల్ ఐడీలు (ఉదాహరణకు `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) కూడా పరిష్కరించబడతాయి. Jina embed/rerank/classify/segment మొదట డ్యాష్బోర్డ్లోని `jina-ai` క్రెడెన్షియల్స్ను ఉపయోగిస్తాయి; డ్యాష్బోర్డ్ కీ లేనప్పుడు మాత్రమే `JINA_AI_API_KEY` ఫాల్బ్యాక్గా ఉపయోగించబడుతుంది. `jina-reader` కార్డ్ Reader / `r.jina.ai` కోసం మాత్రమే (`POST /v1/web/fetch`), ఇది ఎప్పుడూ ఎంబెడింగ్స్ లేదా రీరాంక్ను అందించదు.

మల్టీమోడల్ మద్దతును ప్రకటించే రిజిస్ట్రీ మోడళ్లు, ప్రొవైడర్తో సంబంధం లేని నిర్మిత
అంశాలను గరిష్ఠంగా 32 వరకు కూడా అంగీకరిస్తాయి. మీడియా అంశ రకాలు `text`, `image`, `audio`, `video`, మరియు `document`. వాటి మీడియా `source`
`{"type":"url","url":"https://..."}` లేదా
`{"type":"base64","data":"...","media_type":"..."}` అయి ఉంటుంది.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
మరియు ఫ్యామిలీ అలియాస్ `jina-ai/jina-embeddings-v5-omni` → omni-small) Jina యొక్క స్థానిక
EmbeddingsV5Request డాక్యుమెంట్లను కూడా అంగీకరించి, వాటిని **మార్పు చేయకుండా** `https://api.jina.ai/v1/embeddings`కు ఫార్వర్డ్ చేస్తుంది:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    {
      "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }]
    }
  ]
}
```

స్థానిక `{ image | audio | video | pdf }` విలువలు పబ్లిక్ HTTPS URL, `data:` URI లేదా ముడి
base64 అయి ఉండవచ్చు. OmniRoute ఆ ఆబ్జెక్ట్లను స్ట్రింగ్లుగా మార్చదు లేదా స్థానిక ఇమేజ్ URLలను ఫెచ్ చేయదు — Jina
పబ్లిక్ మీడియాను స్వయంగా పొందుతుంది. అదనపు Jina ఫీల్డ్లు (`task`, `normalized`, `truncate`, `embedding_type`)
ఫార్వర్డ్ చేయబడతాయి. కేవలం టెక్స్ట్కు సంబంధించిన Jina SKUలు ఇప్పటికీ టెక్స్ట్ కాని డాక్యుమెంట్లను తిరస్కరిస్తాయి.

భద్రత మరియు రవాణా పరిమితులు:

- రిమోట్ మీడియా URLలు తప్పనిసరిగా పబ్లిక్ HTTPS అయి ఉండాలి. ప్రామాణిక `{type,source:url}` అంశాలు
  సర్వర్ వైపున ఫెచ్ చేయబడి (రీడైరెక్ట్ పునఃధ్రువీకరణ, టైమ్అవుట్, పరిమాణ పరిమితులు, పబ్లిక్ DNS, కనెక్షన్ పిన్నింగ్)
  ప్రొవైడర్ కాల్కు ముందు ఇన్లైన్ చేయబడతాయి. Jina-స్థానిక `{image:"https://..."}` అంశాలు అదే
  పబ్లిక్-HTTPS తనిఖీ తర్వాత యథాతథంగా ఫార్వర్డ్ చేయబడతాయి; Jina URLను ఫెచ్ చేస్తుంది.
- ఇన్లైన్ base64 మీడియా ప్రతి అంశానికి డీకోడ్ చేసిన రూపంలో 8 MiBకి, మొత్తం అభ్యర్థనలో డీకోడ్ చేసిన రూపంలో 16 MiBకి పరిమితం చేయబడింది.

ప్రొవైడర్ అనువాదం (ప్రామాణిక అంశాలు ఎప్పుడూ మార్పు లేకుండా ఫార్వర్డ్ చేయబడవు):

- Jina మల్టీమోడల్ మోడళ్లు: ప్రతి అగ్ర-స్థాయి అంశం, ఇన్లైన్ మీడియా కోసం డేటా URIలను ఉపయోగిస్తూ,
  ఒక మోడాలిటీ-కీడ్ ఆబ్జెక్ట్గా (`text` / `image` / `audio` / `video` / `pdf`) మారుతుంది; ప్రతి
  అగ్ర-స్థాయి అంశానికి ఒక వెక్టర్.
- Gemini Embedding 2 ఫ్యామిలీ: ఒక అగ్ర-స్థాయి అరే, `content.parts` (`text` లేదా `inline_data`)తో కూడిన ఒకే స్థానిక
  `models/{model}:embedContent` అభ్యర్థనగా మారుతుంది.
- llama.cpp (`llama-cpp/<model>`, స్థానిక సర్వర్ లోడ్ చేసిన ఏ మోడల్ అయినా): ప్రామాణిక `text` అంశాలు
  సాధారణ స్ట్రింగ్లుగా మారతాయి, అలాగే `image` / `audio` / `video` ప్రతి ఒక్కటి llama-server చాట్ కంటెంట్ పార్ట్లను (`image_url`,
  `input_audio`, `wav` / `mp3` / `flac` ఫార్మాట్తో, `input_video`) ఇన్లైన్ డేటాతో ఉపయోగించే
  ఒక్కో `{"content": [part]}` ఆబ్జెక్ట్గా మారతాయి; ప్రతి అగ్ర-స్థాయి అంశానికి ఒక వెక్టర్.
  సర్వర్ తప్పనిసరిగా `--embedding --mmproj …`తో రన్ అవ్వాలి; ప్రొజెక్టర్ లేకపోతే అది
  మీడియాను స్వయంగా తిరస్కరిస్తుంది. `document`కు మద్దతు లేదు.
- స్పష్టమైన మోడాలిటీ మెటాడేటా లేని తెలియని/డైనమిక్ మోడళ్లు నిర్మిత ఇన్పుట్ను HTTP 400తో తిరస్కరిస్తాయి.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

మద్దతు లేని మోడల్/మోడాలిటీ కలయికలు అంశాన్ని బలవంతంగా మార్చకుండా HTTP 400ను అందిస్తాయి. పాత స్ట్రింగ్/టోకెన్ అభ్యర్థనలలోని ఇన్పుట్ కాని
ఎక్స్టెన్షన్ ఫీల్డ్లు మార్పు లేకుండా యథాతథంగా పంపబడటం కొనసాగుతుంది.

```bash
# అన్ని ఎంబెడింగ్ మోడళ్లను జాబితా చేయండి
GET /v1/embeddings
```

## చిత్ర రూపొందింపు

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "పర్వతాలపై అందమైన సూర్యాస్తమయం",
  "size": "1024x1024"
}
```

అందుబాటులో ఉన్న ప్రొవైడర్లలో OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (స్థానికం), ComfyUI (స్థానికం) ఉన్నాయి.

`n`, `data[]`లో `n` చిత్రాలను అందిస్తుంది. ఒక్కో కాల్కు ఒక చిత్రాన్ని అందించే అప్స్ట్రీమ్ APIలు గల ప్రొవైడర్లకు
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) వేర్వేరుగా `n` అప్స్ట్రీమ్ కాల్స్ చేయబడతాయి, ఒకేసారి గరిష్ఠంగా 4 కాల్స్ ప్రాసెస్లో ఉంటాయి. స్థిరమైన
`seed`, కాల్ సూచిక ఆధారంగా ఆఫ్సెట్ చేయబడుతుంది (`seed`, `seed + 1`, …), తద్వారా చిత్రాలు వేర్వేరుగా ఉన్నప్పటికీ
పునరుత్పాదించగలిగేలా ఉంటాయి. `n` గరిష్ఠంగా 10కి పరిమితం చేయబడింది. ఏదైనా కాల్ విఫలమైతే అభ్యర్థన
మొత్తంగా విఫలమవుతుంది. ఫ్యాన్-అవుట్ ఫార్మాట్ల జాబితా
`open-sse/handlers/imageGeneration/fanOut.ts`లోని `SINGLE_IMAGE_FANOUT_FORMATS`.

ZenMux ఇప్పటికే ఉన్న API-కీ కనెక్షన్ను తిరిగి ఉపయోగిస్తుంది మరియు `zenmux/` లేదా `zm/` ప్రిఫిక్స్లను అంగీకరిస్తుంది:

- `zenmux/openai/gpt-image-2`, ZenMux యొక్క OpenAI Images APIని ఉపయోగిస్తుంది. ఎంపికలలో `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background`, మరియు `response_format` ఉన్నాయి.
- `zm/meta/muse-image-1.0` వంటి ఇతర పబ్లిషర్లు ZenMux యొక్క Vertex AI `:predict`
  ఎండ్పాయింట్ను ఉపయోగిస్తారు. `n`, `sampleCount`కు; `aspect_ratio`, `aspectRatio`కు; మరియు `image_size`
  (`1K`, `2K`, `4K`), `sampleImageSize`కు మ్యాప్ అవుతాయి. పిక్సెల్ `size` కేవలం కారక నిష్పత్తిని మాత్రమే అందిస్తుంది,
  హామీ ఇవ్వబడిన పిక్సెల్ కొలతలను కాదు. మద్దతు ఉన్న నిష్పత్తులు, రిజల్యూషన్లు మరియు సంఖ్యలు మోడల్ను బట్టి మారుతాయి.
- `zm/inclusionai/ming-image-0.1-design` తన కొలతలను తానే ఎంచుకుంటుంది. `size`,
  `aspect_ratio`, మరియు `image_size`ను వదిలివేయండి; స్పష్టంగా విలువలను అందిస్తే HTTP 400 తిరిగి వస్తుంది. `output_format`తో PNG, JPEG, మరియు WebPని
  అభ్యర్థించవచ్చు.

ఈ ఇంటిగ్రేషన్ టెక్స్ట్-టు-ఇమేజ్ రూపొందింపుకు మద్దతు ఇస్తుంది, రిఫరెన్స్-ఇమేజ్ ఎడిటింగ్కు కాదు. Vertex
అవుట్పుట్ `data[].b64_json`కు సాధారణీకరించబడుతుంది; `response_format: "url"` అప్స్ట్రీమ్
HTTPS URLను లేదా కేవలం చిత్ర బైట్లు మాత్రమే అందుబాటులో ఉన్నప్పుడు base64 డేటా URLను తిరిగి అందిస్తుంది. ఖాళీ/ఫిల్టర్ చేయబడిన అవుట్పుట్లు
ఖాళీ విజయవంతమైన ప్రతిస్పందనకు బదులుగా ఎర్రర్ను అందిస్తాయి. మోడల్ యాక్సెస్ ZenMux ఖాతాపై ఆధారపడి ఉంటుంది.
[ZenMux యొక్క Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) మరియు
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) చూడండి.

```bash
# అన్ని ఇమేజ్ మోడళ్లను జాబితా చేయండి
GET /v1/images/generations
```

## డాక్యుమెంట్ OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`, `provider/model` ప్రిఫిక్స్ ద్వారా OCR ప్రొవైడర్ను ఎంచుకుంటుంది; ప్రొవైడర్ లేని మోడల్ id (ఉదా.
`mistral-ocr-latest`) దాని నమోదిత ప్రొవైడర్కు పరిష్కరించబడుతుంది, అలాగే `model` పేర్కొనకపోతే డిఫాల్ట్గా
Mistral (`mistral-ocr-latest`) ఉపయోగించబడుతుంది. నమోదిత ప్రొవైడర్లు (`open-sse/config/ocrRegistry.ts`):

| ప్రొవైడర్ id                  | మోడల్ id             | `model` విలువ                                                           | గమనికలు                                                                                                                 |
| ----------------------------- | -------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (లేదా ప్రొవైడర్ లేని `mistral-ocr-latest`) | సమకాలికం — ఒకే అప్స్ట్రీమ్ కాల్ నుండి ప్రతిస్పందన నేరుగా తిరిగి ఇవ్వబడుతుంది.                                           |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                             | అసమకాలిక అప్స్ట్రీమ్ (`analyze` + పోల్) — క్రింద చూడండి.                                                                |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                 | సమకాలికం, Vertex AI యొక్క `openapi/chat/completions` భాగస్వామి ఎండ్పాయింట్ ద్వారా — ప్రామాణీకరణ/URL కోసం క్రింద చూడండి. |

మూడు ప్రొవైడర్లు ఒకే Mistral-ఆకృతిలోని బాడీతో ప్రతిస్పందిస్తారు:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence పోల్ ప్రవాహం

Azure Document Intelligence యొక్క `analyze` API అసమకాలికమైనది: ప్రారంభ అభ్యర్థన బాడీకి బదులుగా
`Operation-Location` హెడర్ను తిరిగి ఇస్తుంది, కాబట్టి ఫలితం కోసం పోల్ చేయాలి. హ్యాండ్లర్
(`open-sse/handlers/ocr.ts`) ఆ URLను ప్రతి సెకనుకు ఒకసారి, గరిష్ఠంగా 30 ప్రయత్నాల వరకు పోల్ చేస్తుంది; `ok` కాని పోల్ ప్రతిస్పందన లేదా `"failed"` స్థితి వచ్చినప్పుడు వెంటనే విఫలమవుతుంది (పోలింగ్ను
కొనసాగించదు), అలాగే ప్రయత్నాల పరిమితి ముగిసిన తర్వాత కూడా ఆపరేషన్ నడుస్తూనే ఉంటే `504`ని తిరిగి ఇస్తుంది. కాలర్కు తిరిగి ఇచ్చే ముందు తుది Azure ప్రతిస్పందనను
Mistral ఉపయోగించే అదే `pages`/`markdown` ఆకృతికి సాధారణీకరిస్తారు, కాబట్టి క్లయింట్ కోడ్లో ప్రొవైడర్ కోసం ప్రత్యేక సందర్భాన్ని నిర్వహించాల్సిన అవసరం లేదు.

### Vertex AI DeepSeek OCR ప్రామాణీకరణ మరియు ఎండ్పాయింట్ పరిష్కారం

`vertex-deepseek-ocr`, చాట్/చిత్ర ట్రాఫిక్ కోసం OmniRoute ఇప్పటికే మద్దతిచ్చే అదే Vertex AI ప్రామాణీకరణను
(`open-sse/executors/vertex.ts`) తిరిగి ఉపయోగిస్తుంది: కనెక్షన్ యొక్క API కీ అనేది Service Account JSON క్రెడెన్షియల్ (JWT-bearer
ప్రవాహం ద్వారా స్వల్పకాలిక OAuth యాక్సెస్ టోకెన్గా మార్పిడి చేయబడుతుంది) లేదా ఇప్పటికే రూపొందించిన OAuth యాక్సెస్ టోకెన్, దాన్ని ఉన్నదున్నట్లుగా ఉపయోగిస్తారు. అప్స్ట్రీమ్ ఎండ్పాయింట్ URL అనేది Vertex యొక్క
సాధారణ `openapi/chat/completions` భాగస్వామి ఎండ్పాయింట్; ఇది కనెక్షన్ యొక్క ప్రాజెక్ట్ మరియు
ప్రాంతం ఆధారంగా నిర్మించబడుతుంది — స్పష్టంగా పేర్కొన్న `providerSpecificData.project`/`providerSpecificData.region` ఎల్లప్పుడూ ప్రాధాన్యత పొందుతుంది;
లేకపోతే ప్రాజెక్ట్ Service Account JSON యొక్క `project_id` నుండి తీసుకోబడుతుంది, ప్రాంతం
డిఫాల్ట్గా `us-central1` అవుతుంది. ఈ రెండు పరిష్కారాలు `open-sse/handlers/ocr.ts`లో
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) జరుగుతాయి, ఆపై `handleOcr`కు పంపించే ముందు
`src/app/api/v1/ocr/route.ts` వాటిని వినియోగిస్తుంది.

## మోడళ్ల జాబితా

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ OpenAI ఆకృతిలో అన్ని చాట్, ఎంబెడ్డింగ్ మరియు ఇమేజ్ మోడళ్లు + కాంబోలను అందిస్తుంది
```

### మోడల్ id ప్రిఫిక్స్లు (`?prefix=`)

చాలా మోడళ్లు **ప్రొవైడర్ ప్రిఫిక్స్** కింద ప్రకటించబడతాయి. మీకు ఏ ప్రిఫిక్స్ లభిస్తుందో
`MODELS_CATALOG_PREFIX_MODE` ఫీచర్ ఫ్లాగ్ నియంత్రిస్తుంది, అలాగే క్వెరీ పారామీటర్తో దానిని
**ప్రతి అభ్యర్థనకు** ఓవర్రైడ్ చేయవచ్చు — మిగతా అందరికీ సర్వర్-వ్యాప్త సెట్టింగ్ను మార్చకుండా
స్వచ్ఛమైన జాబితాను కోరుకునే క్లయింట్కు ఇది ఉపయోగకరం:

```bash
GET /v1/models?prefix=alias        # ఒక్కో మోడల్కు ఒక id — సంక్షిప్త అలియాస్ ప్రిఫిక్స్
GET /v1/models?prefix=dual         # రెండు రూపాలు (సర్వర్ డిఫాల్ట్)
GET /v1/models?prefix=canonical    # పూర్తి provider-id ప్రిఫిక్స్ మాత్రమే
```

| మోడ్        | ఉత్పత్తి చేసేవి                                             | గమనికలు                                                                                                                                                                                           |
| ----------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **మరియు** `claude/claude-sonnet-4-6` | **డిఫాల్ట్.** రెండు idలు ఒకే మోడల్కు రూట్ అవుతాయి; ఏదో ఒక రూపాన్ని హార్డ్కోడ్ చేసిన క్లయింట్ కాన్ఫిగ్లు పని చేస్తూనే ఉండేలా ఇవి ఉంచబడ్డాయి. ఇది కేటలాగ్ పరిమాణాన్ని దాదాపు రెట్టింపు చేస్తుంది.   |
| `alias`     | `cc/claude-sonnet-4-6`                                      | ఒక్కో మోడల్కు ఒక ఎంట్రీ. ప్రత్యేకమైన అలియాస్ లేని ప్రొవైడర్లు కూడా తమ ఎంట్రీని ఉత్పత్తి చేస్తాయి, కాబట్టి ఏదీ కోల్పోదు.                                                                           |
| `canonical` | `claude/claude-sonnet-4-6`                                  | పూర్తి provider-id ప్రిఫిక్స్ కింద ఒక్కో మోడల్కు ఒక ఎంట్రీ. ప్రత్యేకమైన అలియాస్ లేని ప్రొవైడర్లు (ఉదా. `antigravity/…`, `agy/…`) కూడా తమ ఏకైక idని ఇక్కడ ఉత్పత్తి చేస్తాయి, కాబట్టి ఏదీ కోల్పోదు. |

`dual`-మోడ్ మిర్రర్ను క్వెరీ పారామీటర్ లేకుండా కూడా గుర్తించవచ్చు: అది ప్రాథమిక idని సూచించే `parent`
ఫీల్డ్ను కలిగి ఉంటుంది.

మోడల్ పికర్ను రెండర్ చేసే క్లయింట్లు `?prefix=alias`ని అభ్యర్థించాలి —
[OmniCopilot VS Code ఎక్స్టెన్షన్](../guides/VSCODE-COPILOT.md) ఇదే చేస్తుంది.

### డిస్కవరీ ఫిల్టర్లు (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` ఆప్ట్-ఇన్ డిస్కవరీ ఫిల్టర్లను అంగీకరిస్తుంది. వాటిలో ఏదీ లేకపోతే ప్రతిస్పందన
మారదు. అవి కాలర్ ఇప్పటికే చూడగల కేటలాగ్ను పరిమితం చేస్తాయి (API-కీ అనుమతులు ముందుగా వర్తిస్తాయి),
అలాగే అవి OpenAI-శైలి `limit` / `after` పేజింగ్కు ముందు అమలవుతాయి:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # జాబితాలోని ప్రతి సామర్థ్యం తప్పనిసరిగా true అయి ఉండాలి
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # కేటలాగ్ `type`; అది లేని వరుసలు `chat`
GET /v1/models?q=sonnet&limit=10                           # id లేదా పేరుపై కేస్-ఇన్సెన్సిటివ్ సరిపోలిక
```

| పారామీటర్     | విలువలు                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ఋణేతర పూర్ణసంఖ్య, `context_length`తో పోల్చబడుతుంది                                                  |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 అక్షరాలు                                                                                      |

తెలియని విలువ లేదా ఋణేతర పూర్ణసంఖ్య కాని `min_context` (ఉదాహరణకు `1.5`)
HTTP `400`ను అందిస్తుంది, అలాగే సందేశంలో చెల్లుబాటు అయ్యే విలువలు జాబితా చేయబడతాయి. అమలు:
`src/app/api/v1/models/catalogFilters.ts`.

### మోడల్ సంక్షిప్త జాబితా (`POST /v1/models/query`)

`POST /v1/models/query`, `GET /v1/models`తో సమానమైన ప్రామాణీకరణ మరియు ప్రతి-కీ విజిబిలిటీతో,
అదే కేటలాగ్ నుంచి ఒక చిన్న, నిర్ణీత జాబితాను అందిస్తుంది:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ప్రతి ఫీల్డ్ ఐచ్ఛికం. `capabilities` మరియు `exclude` ఒక అరే లేదా కామాలతో వేరు చేసిన స్ట్రింగ్ను
తీసుకుంటాయి; `max_output`, `max_output_tokens`తో పోల్చబడుతుంది. ఫలితాలు మొదట `owned_by`, ఆపై `id`
ఆధారంగా క్రమబద్ధీకరించబడతాయి. `limit` డిఫాల్ట్గా `20` ఉంటుంది మరియు `100` కంటే ఎక్కువ విలువలు `100`కు
పరిమితం చేయబడతాయి. చెల్లని JSON, తెలియని ఫీల్డ్ లేదా చెల్లని విలువ HTTP `400`ను అందిస్తుంది.

### వ్యక్తిగతంగా దాచబడిన చాట్ మోడళ్లు

తన ప్రొవైడర్ పేజీలో **దాచబడింది** అని గుర్తించబడిన మోడల్ కేటలాగ్ నుంచి మినహాయించబడుతుంది మరియు
దానిని స్పష్టంగా అభ్యర్థించినప్పుడు HTTP `404` / `model_not_found`తో తిరస్కరించబడుతుంది. ఈ తనిఖీ,
ప్రొవైడర్ అలియాస్లు, అనుకూల-ప్రొవైడర్ నోడ్ ప్రిఫిక్స్లు మరియు కనెక్షన్ డిఫాల్ట్లతో సహా,
రిజాల్వ్ చేసిన ప్రొవైడర్ మరియు మోడల్ను ఉపయోగిస్తుంది. ఒక కాంబో దాచబడిన లక్ష్యాలను దాటవేసి కనిపించే
సిబ్లింగ్ను ఉపయోగించగలదు; అమలు చేయగల లక్ష్యం ఏదీ మిగలనప్పుడు అదే ఎర్రర్ కోడ్ను అందిస్తుంది.
దాచడాన్ని తొలగించడం తదుపరి అభ్యర్థన నుంచి అమల్లోకి వస్తుంది. ఇమేజ్కు-మాత్రమే సంబంధించిన విజిబిలిటీ
ఓవర్రైడ్లు అదే ID గల చాట్ మోడల్ను దాచవు.

ఈ వ్యక్తిగత మోడల్ సెట్టింగ్,
[మోడల్ ఎక్స్పోజర్ అనుమతి/నిరాకరణ జాబితాల](../routing/MODEL_EXPOSURE_LIST.md) నుంచి వేరుగా ఉంటుంది;
అవి స్పష్టమైన డిస్పాచ్ను కొనసాగిస్తూనే కేటలాగ్ ప్రకటనలను మరియు ఆటో-రూటింగ్ అభ్యర్థులను ఫిల్టర్ చేస్తాయి.
API-కీ మోడల్ అనుమతులు స్వతంత్రంగా వర్తిస్తూనే ఉంటాయి. డిఫాల్ట్ కేటలాగ్ ప్రిఫిక్స్ మోడ్ `dual`గానే ఉంటుంది.

### నో-థింకింగ్ మోడల్ వేరియంట్లు

థింకింగ్ సామర్థ్యం గల Claude మోడళ్ల కోసం, `/v1/models` idకి `claude-3-omniroute-no-thinking/` ప్రిఫిక్స్ జోడించబడిన ఒక **నో-థింకింగ్** వేరియంట్ను కూడా ప్రకటిస్తుంది:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

ఈ idని ఎంచుకోవడం (ఉదా. ఎల్లప్పుడూ `thinking` బ్లాక్ను జోడించే Claude Code కాన్ఫిగరేషన్లో) రీజనింగ్ను నిలిపివేసి అసలు `<provider>/<model>`కు తిరిగి పరిష్కరిస్తుంది — `/v1/messages` పాత్లో `thinking:{type:"disabled"}` లేదా `/v1/chat/completions` పాత్లో `reasoning`/`reasoning_effort` ఫీల్డ్లను తొలగించడం ద్వారా. ఈ వేరియంట్ thinkingకు మద్దతిచ్చే **మరియు** `disabled`ను గౌరవించే Claude-కుటుంబ మోడల్లకు మాత్రమే జాబితా చేయబడుతుంది (కాబట్టి, ఉదా. `disabled`ను తిరస్కరించే adaptive-only మోడల్లు మినహాయించబడతాయి). ఆపరేటర్లు `ModelSpec.noThinkingAlias` ద్వారా ప్రతి మోడల్కు ఈ వేరియంట్ను బలవంతంగా ఆన్ లేదా ఆఫ్ చేయవచ్చు.

## ప్రొవైడర్ ప్లగిన్ మానిఫెస్ట్

```bash
GET /api/v1/provider-plugin-manifest
```

Bifrost, CLIProxyAPI మరియు భవిష్యత్ sidecar రౌటర్లు ఉపయోగించే JSON-సురక్షిత ప్రొవైడర్ ప్లగిన్ మానిఫెస్ట్ను అందిస్తుంది. ప్రతిస్పందన TypeScript ప్రొవైడర్ రిజిస్ట్రీ నుండి రూపొందించబడుతుంది మరియు OAuth క్లయింట్ సీక్రెట్లు, రన్టైమ్ ఎన్విరాన్మెంట్ రిజల్యూషన్, ఎగ్జిక్యూటర్ ఫంక్షన్లు, రిక్వెస్ట్ హెడర్లు మరియు ఖాతా డేటాను ఉద్దేశపూర్వకంగా మినహాయిస్తుంది.

sidecar ప్రక్రియ వెలుపల నడుస్తూ, `open-sse/config/providerPluginManifestRegistry.ts`ను నేరుగా ఇంపోర్ట్ చేయలేనప్పుడు ఈ ఎండ్పాయింట్ను ఉపయోగించండి.

| POST   | `/v1/api/chat`                            | Ollama                                |
| GET    | `/api/v1/vscode/{token}/`                 | OpenAI కేటలాగ్ ఉపనామం                 |
| GET    | `/api/v1/vscode/{token}/models`           | OpenAI మోడళ్ల ఉపనామం                  |
| POST   | `/api/v1/vscode/{token}/chat/completions` | OpenAI టోకెనైజ్డ్ ఉపనామం              |
| POST   | `/api/v1/vscode/{token}/responses`        | OpenAI Responses టోకెనైజ్డ్ ఉపనామం    |
| POST   | `/api/v1/vscode/{token}/api/chat`         | Ollama టోకెనైజ్డ్ ఉపనామం              |
| GET    | `/api/v1/vscode/{token}/api/tags`         | Ollama ట్యాగ్ల టోకెనైజ్డ్ ఉపనామం      |

అన్ని POST రూట్లు ఒకే ఆకృతిని అనుసరిస్తాయి: `Bearer your-api-key` + Zod ద్వారా ధృవీకరించబడిన JSON బాడీ (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` మొదలైనవి; `src/shared/validation/schemas.ts` చూడండి). స్కీమా ధృవీకరణ విఫలమైతే 4xx అందించబడుతుంది.

`Authorization: Bearer ...`ను జోడించలేని క్లయింట్ల కోసం, క్వెరీ-స్ట్రింగ్ అనుకూలత (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) లేదా దిగువ డాక్యుమెంట్ చేసిన ప్రత్యేక `/api/v1/vscode/{token}/...` ఎండ్పాయింట్ల ద్వారా URLలోని API కీలను కూడా OmniRoute అంగీకరిస్తుంది.

```bash
# రీర్యాంక్ (క్లౌడ్ రిజిస్ట్రీ ప్రొవైడర్ లేదా "<prefix>/<model>" రూపంలోని OpenAI-అనుకూల ప్రొవైడర్ నోడ్)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina వర్గీకరణ (Foundation API క్రెడెన్షియల్స్)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina సెగ్మెంటర్
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina శోధన (s.jina.ai; ప్రొవైడర్ ఉపనామాలు: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# మోడరేషన్లు
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (లేదా అభ్యర్థించిన ఫార్మాట్) బాడీని అందిస్తుంది
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTSకు భాష మరియు వాయిస్ అవసరం: `language` డిఫాల్ట్గా "en" ఉంటుంది; వాయిస్
# లేకపోతే లేదా OpenAI స్టాక్ వాయిస్ పేరు (alloy, nova, …) ఉంటే అది "Adrian"గా మారుతుంది
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# చిత్రం సవరణ (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# వీడియో / సంగీత జనరేషన్ (ప్రొవైడర్-ప్రిఫిక్స్ గల మోడల్ ID)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **రీర్యాంక్ ప్రొవైడర్ నోడ్లు:** `POST /v1/rerank` అభ్యర్థనలు `<node-prefix>/<model>` రూపంలో సూచించబడిన OpenAI-అనుకూల ప్రొవైడర్ నోడ్లకు
> (oMLX, vLLM, Infinity, గేట్వే వెనుక ఉన్న TEI, …) కూడా రూట్ చేయబడతాయి. లూప్బ్యాక్
> నోడ్లు (`localhost`, `127.0.0.1`, `172.16.0.0/12`) ఎల్లప్పుడూ అర్హమైనవే; అలాగే ఆపరేటర్
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`లో జాబితా చేసిన హోస్ట్నేమ్లు కూడా అర్హమైనవే (ఉదా. `http://reranker:8080/v1`
> వంటి Docker/Compose సర్వీస్ పేరు; వీటిని `HTTP(S)_PROXY` లేదా కనెక్షన్కు పిన్ చేసిన ప్రాక్సీ ద్వారా కాకుండా
> ఎల్లప్పుడూ నేరుగా కాల్ చేస్తారు). ఇతర
> హోస్ట్లలోని నోడ్లు — LAN బాక్స్ లేదా Tailscale పీర్ — ఆపరేటర్
> `RERANK_REMOTE_PROVIDER_NODES` ఫీచర్ ఫ్లాగ్ను ప్రారంభించినప్పుడు **మరియు** నోడ్ బేస్ URL ప్రొవైడర్
> అవుట్బౌండ్ URL విధానాన్ని (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) ఉత్తీర్ణమైనప్పుడు మాత్రమే అర్హమవుతాయి.
> మెమరీ ఇంజిన్లోని రీర్యాంక్ దశ ఈ రూట్ను
> లూప్బ్యాక్ ద్వారా కాల్ చేస్తుంది, కాబట్టి Memory సెట్టింగ్లలోని `rerankProviderModel`కు కూడా ఇదే నియమం వర్తిస్తుంది.
>
> **లోకల్ సర్వర్ ఆకృతులు:** నోడ్ను `<base>/v1/rerank` వద్ద, అలాగే 404 వచ్చినప్పుడు `<base>/rerank`
> వద్ద (Infinity, TEI) కాల్ చేస్తారు. అప్స్ట్రీమ్ బాడీలో Cohere/OpenAI స్పెల్లింగ్ (`documents`,
> `return_documents`) మరియు TEI స్పెల్లింగ్ (`texts`, `return_text`) రెండూ ఉంటాయి; అప్స్ట్రీమ్ స్పందన
> Cohere ఎన్వలప్కు సాధారణీకరించబడుతుంది: TEI యొక్క బేర్ `[{index, score, text}]`, పలుచని గేట్వేల నుంచి వచ్చే `{results: [{index, score}]}`
> మరియు Voyage-శైలి `{data: [...]}` అన్నీ క్లయింట్కు
> `{results: [{index, relevance_score, document?}]}` రూపంలో, స్కోర్ ఆధారంగా క్రమబద్ధీకరించబడి `top_n`కు పరిమితం చేయబడి తిరిగి వస్తాయి.

> **ప్రొవైడర్-నోడ్ డిస్కవరీ:** OpenAI-అనుకూల ప్రొవైడర్ నోడ్లోని మోడల్లు నోడ్ ప్రిఫిక్స్ కింద `GET /v1/models`లో
> కనిపిస్తాయి. ఎండ్పాయింట్ మెటాడేటా లేని వరుసలు (లోకల్ `/v1/models` జాబితాల్లో సాధారణంగా ఉండేవి)
> నోడ్ యొక్క `apiType`ను వారసత్వంగా పొందుతాయి; అందువల్ల `embeddings` నోడ్ మోడల్లు చాట్కు డిఫాల్ట్ కావడానికి బదులుగా `type: "embedding"`గా,
> అలాగే `rerank` నోడ్ మోడల్లు `type: "rerank"`గా ఉంటాయి; సింక్ చేసిన లేదా మాన్యువల్గా జోడించిన వరుసలో స్పష్టమైన
> `supportedEndpoints` ఉంటే, దానికే ఇప్పటికీ ప్రాధాన్యం ఉంటుంది.

## Files API

బ్యాచ్ ఇన్పుట్/అవుట్పుట్ మరియు ఫైల్-పర్పస్ అప్లోడ్ల కోసం OpenAI-అనుకూల ఫైల్స్ ఎండ్పాయింట్.

| పద్ధతి | పాత్                     | వివరణ                                                                                                                         |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | ఫైల్ను అప్లోడ్ చేయండి (మల్టీపార్ట్: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — గరిష్ఠంగా 512 MiB |
| GET    | `/v1/files`              | ప్రామాణీకరించబడిన API కీకి చెందిన ఫైళ్లను జాబితా చేయండి                                                                       |
| GET    | `/v1/files/[id]`         | ఫైల్ మెటాడేటాను పొందండి                                                                                                       |
| DELETE | `/v1/files/[id]`         | ఫైల్ను తొలగించండి                                                                                                             |
| GET    | `/v1/files/[id]/content` | ముడి ఫైల్ బాడీని తిరిగి స్ట్రీమ్ చేయండి                                                                                       |

**ప్రామాణీకరణ:** బేరర్ API కీ — `getApiKeyRequestScope` ద్వారా ఫైళ్లు ప్రతి API కీ పరిధిలో ఉంచబడతాయి. ఒక కీ
తన స్వంత ఫైళ్లను మాత్రమే చూస్తుంది, డౌన్లోడ్ చేస్తుంది మరియు తొలగిస్తుంది; కీ లేని డ్యాష్బోర్డ్ సెషన్ మొత్తం
ఇన్స్టాన్స్ను చదువుతుంది; యజమాని లేని ఫైల్కు (అనామక లేదా డ్యాష్బోర్డ్-సెషన్ అప్లోడ్) ప్రతి
నాన్-సెషన్ కాలర్కు యాక్సెస్ నిరాకరించబడుతుంది. `GET /v1/files`, `REQUIRE_API_KEY=false` అయినప్పటికీ, ప్రతి టెనెంట్కు చెందిన
ఫైళ్లను జాబితా చేయడానికి బదులుగా అనామక కాలర్ను — అలాగే సమర్పించిన కీ పరిష్కరించబడకపోతే దానిని కూడా —
`401`తో తిరస్కరిస్తుంది (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523).

## Batches API

OpenAI-అనుకూల బ్యాచ్ ప్రాసెసింగ్.

| పద్ధతి | పాత్                      | వివరణ                                                                                                                         |
| ------ | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/batches`             | బ్యాచ్ను సృష్టించండి — బాడీ `v1BatchCreateSchema` ద్వారా ధృవీకరించబడుతుంది (`input_file_id`, `endpoint`, `completion_window`) |
| GET    | `/v1/batches`             | బ్యాచ్లను జాబితా చేయండి                                                                                                       |
| GET    | `/v1/batches/[id]`        | బ్యాచ్ స్థితి + `request_counts`ను పొందండి                                                                                    |
| DELETE | `/v1/batches/[id]`        | పూర్తయిన/విఫలమైన బ్యాచ్ను తొలగించండి                                                                                          |
| POST   | `/v1/batches/[id]/cancel` | ప్రాసెసింగ్లో ఉన్న బ్యాచ్ను రద్దు చేయండి                                                                                      |

**ప్రామాణీకరణ:** బేరర్ API కీ. ఫైళ్లకు వర్తించే అదే త్రిముఖ నియమం ప్రకారం బ్యాచ్లు ప్రతి API కీ పరిధిలో
ఉంచబడతాయి: స్వంత కీకి మాత్రమే యాక్సెస్, డ్యాష్బోర్డ్ సెషన్కు ఇన్స్టాన్స్-వ్యాప్త యాక్సెస్, యజమాని లేని రికార్డులకు ప్రతి
నాన్-సెషన్ కాలర్కు యాక్సెస్ నిరాకరణ (పొందడం, తొలగించడం, రద్దు చేయడం మరియు సృష్టించేటప్పుడు `input_file_id` తనిఖీ).
`REQUIRE_API_KEY=false` అయినప్పటికీ, `GET /v1/batches` అనామక కాలర్ను `401`తో తిరస్కరిస్తుంది.

## Search API

వెబ్/శోధన ప్రొవైడర్ అబ్స్ట్రాక్షన్ (Tavily, Brave, Exa, Serper మొదలైనవి).

| పద్ధతి | పాత్                   | వివరణ                                                                                                              |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET    | `/v1/search`           | కాన్ఫిగర్ చేసిన శోధన ప్రొవైడర్లు + సామర్థ్యాలను జాబితా చేస్తుంది                                                   |
| POST   | `/v1/search`           | శోధన క్వెరీని అమలు చేస్తుంది — బాడీ `v1SearchSchema` ద్వారా ధృవీకరించబడుతుంది, క్యాషింగ్/కోలెసింగ్కు మద్దతిస్తుంది |
| GET    | `/v1/search/analytics` | ఒక్కో ప్రొవైడర్కు సంబంధించిన హిట్/లేటెన్సీ/క్యాష్ గణాంకాలు                                                         |

**ప్రామాణీకరణ:** Bearer API కీ (`extractApiKey` + `isValidApiKey`). `enforceApiKeyPolicy` ద్వారా శోధన విధానం అమలు చేయబడుతుంది.

### Exa మరియు Tavily `provider_options`

Exa మరియు Tavily, నేమ్స్పేస్ చేసిన బ్యాగ్ నుండి ప్రొవైడర్-నిర్దిష్ట ఫీల్డ్లను చదువుతాయి:
`provider_options.exa` (లేదా `provider_options["exa-search"]`) మరియు `provider_options.tavily`
(లేదా `provider_options["tavily-search"]`). దిగువన ఉన్న కీలు మాత్రమే ఫార్వర్డ్ చేయబడతాయి. ప్రతి ఒక్కటి
`open-sse/handlers/search/providerOptionsPassthrough.ts`లోని దాని స్వంత Zod స్కీమాతో
తనిఖీ చేయబడుతుంది, తప్పు రకం ఉన్న కీ విస్మరించబడుతుంది. ప్రామాణీకరణ, బేస్ URL,
`stream` మరియు `outputSchema` సహా ఇతర ఏ కీ అయినా విస్మరించబడుతుంది. ఇతర ప్రొవైడర్లు ఉపయోగించే ఫ్లాట్ కీలు (`cx`, `depth`, ...) మునుపటిలాగే
పని చేస్తాయి.

| ప్రొవైడర్ | అగ్ర-స్థాయి ఫీల్డ్లు                                                                                                                                                                                                                                                                                                                                                      | నెస్టెడ్                                                                                                                                                                |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (ఫ్లాట్ ప్రిమిటివ్లు), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                          | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` డిఫాల్ట్ `{ text: true, highlights: true }`పై మెర్జ్ చేయబడుతుంది |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                       |

జెనరిక్ ఫీల్డ్లకే ఎల్లప్పుడూ ప్రాధాన్యం ఉంటుంది: `query`, `max_results`, `filters` (డొమైన్లు), `country` మరియు
`search_type` నుండి పొందిన టాపిక్. Exaలో, `search_type: "news"` అనేది `category: "news"`ను అలాగే ఉంచుతుంది.
Tavily `search_type: "finance"` (`topic: "finance"`)ను కూడా అంగీకరిస్తుంది.

జెనరిక్ `time_range` ఇప్పుడు రెండు ప్రొవైడర్లకూ చేరుతుంది: Exaకు `startPublishedDate` (ISO
టైమ్స్టాంప్), Tavilyకు `start_date` (`YYYY-MM-DD`) అందుతాయి. `provider_options`లో స్పష్టంగా పేర్కొన్న తేదీ,
మ్యాప్ చేసిన తేదీని ఓవర్రైడ్ చేస్తుంది.

Exa ఫలితాలు `id`, `highlight_scores`, `summary`, `subpages`, `entities` మరియు `extras`ను
`provider_raw`లో ఉంచుతాయి. Tavily ఫలితాలు `images` మరియు `favicon`ను ఉంచుతాయి.

వ్యయ గణన ఇప్పటికీ ఫ్లాట్ రిజిస్ట్రీ `costPerQuery`గానే ఉంటుంది. Tavily ప్రతి కాల్కు
`search_depth: "advanced"` కోసం ఎక్కువ క్రెడిట్లను బిల్ చేస్తుంది, ఆ తేడా
`usage.search_cost_usd`లో ప్రతిబింబించదు.

## Web Fetch API

కాన్ఫిగర్ చేసిన web-fetch ప్రొవైడర్ (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) ద్వారా URL నుండి కంటెంట్ను సంగ్రహించండి.

Parallel Extract (`parallel-search`, Parallel Searchకు ఉపయోగించే అదే API కీ) Markdownను
మాత్రమే అందిస్తుంది — మరే ఇతర `format` అయినా `400` వస్తుంది — అలాగే కంటెంట్ను 100,000 అక్షరాలకు పరిమితం చేస్తుంది. లక్ష్య
పేజీని సంగ్రహించలేనప్పుడు, అప్స్ట్రీమ్ దానిని HTTP 200 లోపల నివేదిస్తుంది;
OmniRoute దాన్ని స్థిరమైన సందేశంతో `422`గా చూపిస్తుంది.

| పద్ధతి | మార్గం          | వివరణ                                                                            |
| ------ | --------------- | -------------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | URLను పొందండి/స్క్రాప్ చేయండి — బాడీ `v1WebFetchSchema` ద్వారా ధృవీకరించబడుతుంది |

**ప్రామాణీకరణ:** Bearer API కీ (`extractApiKey` + `isValidApiKey`). విధానం `enforceApiKeyPolicy` ద్వారా అమలు చేయబడుతుంది.

**కోటా-అవగాహనతో కూడిన ఫాల్బ్యాక్ (#8297):** స్పష్టమైన `provider` ఇవ్వనప్పుడు, పూల్
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) స్థిరమైన
ప్రాధాన్యతా క్రమంలో (fill-first) పరిశీలించబడుతుంది — రేట్-లిమిట్కు చేరుకున్నప్పటికీ కాన్ఫిగర్ చేయబడిన ప్రొవైడర్ను
అభ్యర్థనను వెంటనే నిలిపివేయకుండా దాటవేస్తుంది; అలాగే మళ్లీ ప్రయత్నించదగిన/కోటా సంబంధిత అప్స్ట్రీమ్ వైఫల్యం
(HTTP 429 ఎల్లప్పుడూ; Firecrawl/Tavily/TinyFish కోటా-శైలి ఉచిత టైర్లకు 402/403 —
Jina Readerకు కాదు, అలాగే సాధారణ 400 తప్పుడు అభ్యర్థనకు ఎప్పుడూ కాదు) అభ్యర్థన సమయంలో
ఇంకా ప్రయత్నించని, క్రెడెన్షియల్స్ ఉన్న తదుపరి ప్రొవైడర్కు కొనసాగుతుంది. పూల్లోని ప్రతి ప్రొవైడర్
అందుబాటులో లేకుండా పోయినప్పుడు, ఎండ్పాయింట్ మునుపటి సాధారణ `400`కు బదులుగా ఒకే `429`ను (`Retry-After`
హెడర్తో) అందిస్తుంది. స్పష్టమైన `provider`ను
అభ్యర్థించినప్పుడు, నిశ్శబ్ద ఫాల్బ్యాక్ **ఉండదు** — రేట్-లిమిట్కు చేరుకున్న లేదా విఫలమైన స్పష్టమైన
ప్రొవైడర్ తన స్వంత లోపాన్ని చూపిస్తుంది (రేట్-లిమిట్కు చేరితే `429`, లేకపోతే అప్స్ట్రీమ్
స్టేటస్).

## WebSocket స్ట్రీమింగ్

```bash
GET /v1/ws?handshake=1
```

WebSocket అప్గ్రేడ్ హ్యాండ్షేక్ను ధృవీకరిస్తుంది మరియు వైర్ ప్రోటోకాల్ ఉదాహరణ సందేశాలను (`request`, `cancel`) అందిస్తుంది. వాస్తవ WS ఫ్రేమ్లు Next.js రూట్ పట్టిక వెలుపల ఉన్న బండిల్ చేసిన WS సర్వర్ ద్వారా నిర్వహించబడతాయి.

**ప్రామాణీకరణ:** హ్యాండ్షేక్ సమయంలో Bearer API కీ.

### WebSocket ద్వారా Responses API (codex మాత్రమే)

```bash
# HTTP API ఉన్న అదే హోస్ట్:పోర్ట్ (డిఫాల్ట్ 20128); కనెక్షన్ను అప్గ్రేడ్ చేయండి:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (లేదా: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# మొదటి ఫ్రేమ్ తప్పనిసరిగా response.create అయి ఉండాలి:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket ప్రాక్సీ **ప్రత్యేకంగా `codex`కు మాత్రమే** (ChatGPT
బ్యాకెండ్) అనుసంధానించబడింది. ఇది API/డ్యాష్బోర్డ్ ఉన్న అదే పోర్ట్లో `/v1/responses`,
`/responses`, మరియు `/api/v1/responses` మార్గాలపై వింటుంది. మొదటి `response.create` ఫ్రేమ్పై ఇది
అంతర్గత `codex-responses-ws` బ్రిడ్జ్ ద్వారా ప్రామాణీకరించి + సిద్ధం చేస్తుంది, ఒక
codex OAuth కనెక్షన్ను ఎంచుకుని, `wreq-js` ట్రాన్స్పోర్ట్ ద్వారా `wss://chatgpt.com/backend-api/codex/responses`కు
టన్నెల్ చేస్తుంది. **codex కాని మోడల్లు తిరస్కరించబడతాయి** (`codex_ws_provider_required`).
కోటా-షేర్ రూటింగ్ కోసం `model: "qtSd/<group>/codex/<model>"` ఉపయోగించండి. ఇది
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`లో అమలు చేయబడింది.

**ప్రామాణీకరణ:** హ్యాండ్షేక్ సమయంలో Bearer API కీ. బండిల్ చేసిన HTTP సర్వర్ (`server-ws.mjs`)
సక్రియ ఎంట్రీపాయింట్గా ఉండాలి (`app/server-ws.mjs` ఉన్నప్పుడు డిఫాల్ట్గా అదే ఉంటుంది).

#### మోడల్ id: సాధారణ ChatGPT idను ఉపయోగించండి (`codex/` ప్రిఫిక్స్ లేకుండా)

OpenAI **Codex CLI**, `supports_websockets = true` అయినప్పుడు క్లయింట్ వైపు మోడల్ పేరును ధృవీకరిస్తుంది మరియు
`codex/gpt-5.5` వంటి **ప్రొవైడర్-ప్రిఫిక్స్ కలిగిన idsను తిరస్కరిస్తుంది**
(`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). **సాధారణ** idను పంపండి (ఉదా. `gpt-5.5`). OmniRoute బ్రిడ్జ్
codexకు మాత్రమే పరిమితమైనది, కాబట్టి అప్స్ట్రీమ్కు టన్నెల్ చేసే ముందు సాధారణ idను
codex మోడల్గా (`resolveCodexWsModelInfo`) మళ్లీ పరిష్కరిస్తుంది — సాధారణ
`gpt-5.5` HTTP ద్వారా అయితే మరొక ప్రొవైడర్కు రూట్ అయినప్పటికీ.

#### OpenAI Codex CLIని కాన్ఫిగర్ చేయడం

`~/.codex/config.toml`లో WebSocket మద్దతుతో కూడిన కస్టమ్ ప్రొవైడర్ను జోడించడం ద్వారా
Codex CLIని OmniRoute వైపు మళ్లించండి (ఇప్పటికే ఉన్న కాన్ఫిగరేషన్ను మార్చకుండా ఉండటానికి
ప్రత్యేక `CODEX_HOME` ఉపయోగించండి):

```toml
model = "gpt-5.5"                 # సాధారణ id — "codex/gpt-5.5" కాదు
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # చివర స్లాష్ ఉండకూడదు; WS URL ఉత్పన్నమవుతుంది (ప్రొడక్షన్లో https/wss ఉపయోగించండి)
wire_api = "responses"                    # Feb 2026 నుండి మద్దతు ఉన్న ఏకైక విలువ
supports_websockets = true                # Responses-over-WS ట్రాన్స్పోర్ట్ను ప్రారంభిస్తుంది
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API కీని కలిగి ఉంటుంది (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ఒక OmniRoute API కీ (REQUIRE_API_KEY=false అయితే ఏ కీ అయినా)
codex exec "Responda apenas: PONG"
```

CLI, `base_url + /responses`ను WebSocketకు అప్గ్రేడ్ చేస్తుంది మరియు OmniRoute దాన్ని
ఎంచుకున్న codex OAuth కనెక్షన్కు టన్నెల్ చేస్తుంది. స్థానిక సర్వర్తో ఆరంభం నుండి ముగింపు వరకు
ధృవీకరించబడింది: ChatGPT `codex.rate_limits` + `response.created`ను అందించి,
కంప్లీషన్ను స్ట్రీమ్ చేస్తుంది.

## స్వీయ-సేవ వినియోగం (`/api/usage/om-usage`)

ఏ API కీ అయినా **తన స్వంత** వినియోగం మరియు కోటాలను చదవగలదు — నిర్వహణ ప్రామాణీకరణ అవసరం లేదు. కీ హోల్డర్కు వారి వ్యయాన్ని చూపించడానికి క్లయింట్ (CLI, OmniCopilot ప్యానెల్) ఉపయోగించే ఎండ్పాయింట్ ఇదే.

```bash
# టెక్స్ట్ రూపం (చారిత్రక ఒప్పందం — టెర్మినల్ కోసం సాధారణ టెక్స్ట్)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# నిర్మిత రూపం — UI వినియోగించేది
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

కీకి **`allowUsageCommand`** ప్రారంభించబడి ఉండాలి (డిఫాల్ట్గా ఆఫ్లో ఉంటుంది — డాష్బోర్డ్లోని API-కీ మేనేజర్ ప్రతి కీకి దీన్ని టాగుల్ చేస్తుంది). అది లేకపోతే ఎండ్పాయింట్ `403`తో ప్రతిస్పందిస్తుంది.

`?format=json` ఒక వివక్షిత ఆకృతిని తిరిగి ఇస్తుంది, అందువల్ల కాలర్ తిరస్కరణ నుండి డేటా ఫీల్డ్ను ఎప్పటికీ చదవదు. విజయవంతమైనప్పుడు:

```jsonc
{
  "allowed": true,
  // ప్రతి కీ వినియోగ పరిమితులను (రోజువారీ/వారంవారీ USD) కీ ఎంచుకున్నప్పుడు మాత్రమే ఉంటుంది:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // ఎంచుకున్న ప్రొవైడర్ కోటా స్నాప్షాట్, లేదా ఇంకా ఏదీ క్యాష్ చేయబడకపోతే null:
  "provider": {
    "connectionId": "…",
    "provider": "claude",
    "plan": "…",
    "quotas": {/* … */},
  },
  // ప్రతి కనెక్షన్ స్నాప్షాట్, తద్వారా UI అనేక ప్రొవైడర్లను పక్కపక్కన రెండర్ చేయగలదు:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

తిరస్కరణపై (`401` చెల్లని కీ / `403` అనుమతి లేదు), అదే రూట్
`{ "allowed": false, "error": { "message": "…" } }`ను తిరిగి ఇస్తుంది — ఉన్నప్పటికీ ఖాళీగా ఉన్న `personal`/`provider` (కీకి అనుమతి ఉంది, ఇంకా ఏ సమాచారం లభించలేదు) అనేది తిరస్కరణకు భిన్నమైన స్థితి, మరియు JSON రూపం మాత్రమే వాటిని వేరు చేస్తుంది.

**ప్రామాణీకరణ:** కాలర్కు చెందిన స్వంత Bearer API కీ, `isValidApiKey`తో ధృవీకరించబడుతుంది — ఇది నిర్వహణ ఉపరితలం (`/api/keys/…`) _కాదు_; అది `requireManagementAuth` వెనుకే ఉంటుంది.

### ముడి మరియు కటాఫ్-సర్దుబాటు చేసిన కోటా శాతాలు

`/api/usage/om-usage`ను వినియోగించేటప్పుడు, కాలర్లు **సాధారణ-టెక్స్ట్ అవుట్పుట్** మరియు నిర్మిత **JSON అవుట్పుట్** చూపించే శాతాల మధ్య వ్యత్యాసాన్ని గమనించాలి:

| అంశం                   | సాధారణ-టెక్స్ట్ ఫార్మాట్ (`/api/usage/om-usage` / `@@om-usage`)                                 | JSON ఫార్మాట్ (`?format=json`)                                                         |
| :--------------------- | :---------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------- |
| **అవుట్పుట్ ఫీల్డ్**   | `NN% left` (ఉదా., `20% left`)                                                                   | `provider.quotas` / `providers[].quotas`                                               |
| **కొలత**               | **కటాఫ్-సర్దుబాటు చేసిన ఉపయోగించదగిన అలవెన్స్**: కటాఫ్ థ్రెషోల్డ్కు పైన మిగిలిన సామర్థ్యం       | **ముడి అప్స్ట్రీమ్ కోటా**: సర్దుబాటు చేయని ప్రొవైడర్ కొలత                              |
| **కటాఫ్ స్కేలింగ్**    | సంరక్షిత రిజర్వ్ `0% left`గా కనిపించేలా `effectiveRemainingPercent()` ద్వారా స్కేల్ చేయబడుతుంది | ఏదీ లేదు (ప్రొవైడర్ నివేదించిన ముడి స్నాప్షాట్ విలువలు)                                |
| **థ్రెషోల్డ్ డేటా**    | ప్రదర్శించబడే శాతంలో చేర్చబడుతుంది                                                              | ప్రతి కనెక్షన్కు `quotaWindowThresholds`లో (లేదా సర్వర్ డిఫాల్ట్లలో) నిల్వ చేయబడుతుంది |
| **ప్రధాన వినియోగదారు** | ఇంటరాక్టివ్ CLIలు, టెర్మినల్ ప్రాంప్ట్లు, మానవ ఆపరేటర్లు                                        | ప్రోగ్రామాటిక్ ఇంటిగ్రేషన్లు, డాష్బోర్డ్లు, విశ్లేషణలు, బిల్లింగ్ ట్రాకర్లు            |

#### కటాఫ్ సర్దుబాటు సూత్రం

అప్స్ట్రీమ్ పూర్తిగా ఖాళీ కావడాన్ని నివారించడానికి OmniRoute ముందస్తు కోటా కటాఫ్లకు మద్దతు ఇస్తుంది (కనెక్షన్ `quotaWindowThresholds`, ప్రొవైడర్ డిఫాల్ట్లు లేదా గ్లోబల్ రెసిలియన్స్ సెట్టింగ్ల ద్వారా కాన్ఫిగర్ చేయబడుతుంది). ఒక కోటా విండోపై కటాఫ్ థ్రెషోల్డ్ (ఉదా., `cutoff = 25%`) క్రియాశీలంగా ఉన్నప్పుడు, టెక్స్ట్ రెండరర్ మిగిలిన అలవెన్స్ను ఇలా లెక్కిస్తుంది:

- `remaining <= cutoff` అయితే: `0%`ను తిరిగి ఇస్తుంది.
- `remaining > cutoff` అయితే: `((remaining - cutoff) / (100 - cutoff)) * 100`ను తిరిగి ఇస్తుంది.

ఫార్మాట్ చేసిన టెక్స్ట్ అవుట్పుట్ దీన్ని సమీప పూర్ణసంఖ్యకు రౌండ్ చేస్తుంది (`Math.round(...)`).

#### వివరణాత్మక ఉదాహరణ

**60% ముడి వినియోగం** (అందువల్ల **40% ముడి మిగిలిన కోటా**) మరియు కాన్ఫిగర్ చేసిన **25% మిగిలిన-కోటా కటాఫ్** థ్రెషోల్డ్ కలిగిన ప్రొవైడర్ విండోను పరిగణించండి:

| ప్రాతినిధ్యం                       | గణన                                                | మిగిలినది |              సూచిత వినియోగం              |
| :--------------------------------- | :------------------------------------------------- | :-------: | :--------------------------------------: |
| **ముడి JSON (`?format=json`)**     | అప్స్ట్రీమ్ స్నాప్షాట్ (`quotas[window]`)          |  **40%**  |                 **60%**                  |
| **టెక్స్ట్ ఫార్మాట్ (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**  | **80%** (`100 - remaining`ను లెక్కిస్తే) |

- **టెక్స్ట్లో 20% మిగిలిందని ఎందుకు చూపిస్తుంది:** ఖాతాలో భౌతికంగా మిగిలిన 40% కోటాలో 25%ను కటాఫ్ విధానం రిజర్వ్ చేస్తుంది. రౌటర్ ఈ కనెక్షన్కు రూటింగ్ చేయడం ఆపే ముందు, ఉపయోగించదగిన 75% హెడ్రూమ్లో కాలర్కు కేవలం 15% మాత్రమే మిగిలి ఉంటుంది. రూటింగ్ నిలిచే సమయానికే కనెక్షన్ ఖాళీ అయిందని (`0% left`) సంకేతమిచ్చేలా స్కేలింగ్ నిర్ధారిస్తుంది.
- **JSON ముడి విలువలను ఎందుకు నిలుపుతుంది:** JSON పేలోడ్ ఖచ్చితమైన ప్రొవైడర్ స్నాప్షాట్ను (`UsageSnapshot`) తిరిగి ఇస్తుంది, తద్వారా బాహ్య సాధనాలు సర్వర్-సైడ్ నష్టదాయక స్కేలింగ్ లేకుండా వాస్తవ అప్స్ట్రీమ్ వినియోగం మరియు కనెక్షన్-స్థాయి `quotaWindowThresholds`ను యాక్సెస్ చేయగలవు.

#### వినియోగదారు మైగ్రేషన్ మార్గదర్శకం

ఒక బాహ్య ఇంటిగ్రేషన్ (ఎడిటర్ ప్లగిన్ లేదా ఏజెంట్ ఎక్స్టెన్షన్ వంటిది) గతంలో టెక్స్ట్ ఎండ్పాయింట్ను (`NN% left`) స్క్రాప్ చేసి, ఉపయోగించిన శాతాన్ని `100 - NN`గా లెక్కించి ఉంటే, `?format=json`కు మైగ్రేట్ చేయడం అంటే:

- ముడి JSON విలువలను చదవడం **వాస్తవ అప్స్ట్రీమ్ వినియోగాన్ని** ప్రతిబింబిస్తుంది (పై ఉదాహరణలో 60% ఉపయోగించబడింది).
- ఇంటిగ్రేషన్ టెక్స్ట్ ఎండ్పాయింట్లోని ఉపయోగించదగిన-అలవెన్స్ సెమాంటిక్స్ను కొనసాగించాలని అనుకుంటే, కనెక్షన్-స్థాయి ఓవర్రైడ్ల కోసం `quotaWindowThresholds`ను ఉపయోగించి క్లయింట్ వైపు ప్రభావవంతమైన మిగిలిన శాతం సూత్రాన్ని లెక్కించవచ్చు.

## సెమాంటిక్ క్యాష్

```bash
# క్యాష్ గణాంకాలను పొందండి
GET /api/cache/stats

# అన్ని క్యాష్లను క్లియర్ చేయండి
DELETE /api/cache/stats
```

ప్రతిస్పందన ఉదాహరణ:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### లేటెన్సీ ప్రభావం

సెమాంటిక్ క్యాష్ HIT ప్రతిస్పందనను క్యాష్ నుంచి **అప్స్ట్రీమ్ కాల్ లేకుండానే** అందిస్తుంది, కాబట్టి నివేదించబడే `X-OmniRoute-Response-Latency` దాదాపు శూన్యంగా ఉంటుంది (అసలు అప్స్ట్రీమ్ లేటెన్సీతో సంబంధం లేకుండా). లేటెన్సీకి సున్నితమైన క్లయింట్లు (బెంచ్మార్కింగ్, p50/p99 పర్యవేక్షణ) `X-OmniRoute-Cache-Latency` ప్రతిస్పందన హెడర్ను తనిఖీ చేయాలి:

| విలువ       | అర్థం                                                                        |
| ----------- | ---------------------------------------------------------------------------- |
| `synthetic` | ప్రతిస్పందన క్యాష్ నుంచి అందించబడింది; లేటెన్సీ నిజమైన అప్స్ట్రీమ్ సమయం కాదు |
| _(లేదు)_    | నిజమైన అప్స్ట్రీమ్ కాల్ నుంచి వచ్చిన ప్రతిస్పందన                             |

### ప్రతి-కీ క్యాష్ బైపాస్

API కీలు `cacheDefaultMode` ద్వారా సెమాంటిక్ క్యాష్ రీడ్లను నిలిపివేయగలవు:

| విలువ    | ప్రవర్తన                                                                 |
| -------- | ------------------------------------------------------------------------ |
| `legacy` | సాధారణ క్యాష్ ప్రవర్తన (డిఫాల్ట్)                                        |
| `bypass` | క్యాష్ లుకప్ను పూర్తిగా దాటవేయండి; ఎల్లప్పుడూ అప్స్ట్రీమ్ను సంప్రదించండి |

కీ సృష్టి (`POST /api/keys`) సమయంలో సెట్ చేయండి లేదా (`PATCH /api/keys/[id]`) ద్వారా నవీకరించండి:

```json
{ "cacheDefaultMode": "bypass" }
```

### ప్రతి-అభ్యర్థన బైపాస్

కీ సెట్టింగ్లతో సంబంధం లేకుండా ఏ అభ్యర్థన అయినా క్యాష్ను దాటవేయగలదు:

```
X-OmniRoute-No-Cache: true
```

## డ్యాష్బోర్డ్ & నిర్వహణ

నిర్వహణ రూట్లు (`/api/*` పబ్లిక్ auth/login మినహా) సాధారణ ఇన్ఫరెన్స్ API కీల ద్వారా అధికారం పొంద**వు**. క్రెడెన్షియల్ కుటుంబాలు, స్కోప్లు మరియు curl ఉదాహరణలు:
[నిర్వహణ ప్రామాణీకరణ](../guides/MANAGEMENT-AUTH.md).

| ఎండ్పాయింట్                   | పద్ధతి   | వివరణ                                                                                                                                                                                                                                                                                                                  |
| ----------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/auth/login`             | POST     | లాగిన్                                                                                                                                                                                                                                                                                                                 |

సింక్/దిగుమతి చేసిన మోడళ్ల కోసం, `PUT /api/provider-models` `provider`, `modelId` మరియు
`maxOutputTokenOverride`ను అంగీకరిస్తుంది: ధనాత్మక పూర్ణాంకం మాన్యువల్ అవుట్పుట్-టోకెన్ పరిమితిని సెట్ చేస్తుంది, మరియు `null`
దానిని క్లియర్ చేసి డిఫాల్ట్ను పునరుద్ధరిస్తుంది. `GET /api/provider-models?provider=<provider>` ఈ విలువలను
`modelOutputOverrides`లో అందిస్తుంది, కస్టమ్-మోడల్ వరుస లేని మోడళ్లతో సహా. ఓవర్రైడ్
రన్టైమ్ `max_output_tokens` సామర్థ్యాన్ని ఉపయోగిస్తుంది మరియు మోడల్ రీ-సింక్ తర్వాత కూడా కొనసాగుతుంది. OpenAI-అనుకూల
ప్రొవైడర్ పేజీ అదే ఎడిట్/క్లియర్ నియంత్రణలను అందిస్తుంది మరియు స్పష్టమైన విజన్ మద్దతు ఉన్న మోడళ్లను గుర్తిస్తుంది.

కస్టమ్ Chat Completions నోడ్లు స్పష్టమైన రీజనింగ్ ఆప్ట్-అవుట్లను అప్స్ట్రీమ్ బ్యాక్ఎండ్కు
అనుగుణంగా మారుస్తాయి. విజయవంతమైన కనెక్షన్ పరీక్ష, `/models` ఎంట్రీ గుర్తించబడిన `owned_by`
విలువను నిరూపించిన ప్రతి ఖచ్చితమైన మోడల్ ID కోసం చాట్-టెంప్లేట్ నియంత్రణలను స్వయంచాలకంగా ఎంచుకుంటుంది:
`vllm`, `sglang`, లేదా `llamacpp`. పారదర్శక OpenAI-అనుకూల ర్యాపర్లు అసలు మోడల్ ఎంట్రీని
సమూహ `openai` ఆబ్జెక్ట్ లోపల భద్రపరచవచ్చు; గుర్తింపు అటువంటి మూడు ఎన్వలప్ల వరకు అనుసరిస్తుంది.
తప్పిపోయిన, తెలియని లేదా వైరుధ్యమైన యాజమాన్యం ఉన్న మోడళ్లు సాధారణ OpenAI ప్రవర్తనను కొనసాగిస్తాయి.
గుర్తింపు ఇప్పటికే ఉన్న కాటలాగ్ అభ్యర్థనను తిరిగి ఉపయోగిస్తుంది, కంప్లీషన్ టోకెన్లను రూపొందించదు,
మరియు కనెక్షన్ ఎండ్పాయింట్ మారినప్పుడు చెల్లుబాటు అవ్వదు.

ఆ మెటాడేటాను బహిర్గతం చేయని బ్యాక్ఎండ్ కోసం ప్రవర్తనను పిన్ చేయడానికి, ఇప్పటికే ఉన్న పాక్షిక
ప్రొవైడర్ అప్డేట్ APIని ఉపయోగించండి:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

ఆ బాడీని `PUT /api/providers/<connection-id>` తో పంపండి. ఆ కనెక్షన్లో, `none` అనే స్పష్టమైన
reasoning effort `chat_template_kwargs.thinking=false` మరియు
`chat_template_kwargs.enable_thinking=false` గా పంపబడుతుంది. సర్వర్-సైడ్ reasoning నియమం
ఒక effortను బలవంతం చేయకపోతే, స్పష్టమైన నేటివ్ టెంప్లేట్ విలువలు అధికారికంగా ఉంటాయి.
కస్టమ్ OpenAI-అనుకూల కనెక్షన్ Chat Completions బాడీని డిస్ప్యాచ్ చేసినప్పుడు మాత్రమే ఈ సెట్టింగ్
వర్తిస్తుంది; Responses రిక్వెస్ట్లు మరియు సాధారణ ప్రొవైడర్లు వాటి నేటివ్ రిక్వెస్ట్ ఆకృతిని
కొనసాగిస్తాయి. సాధారణ OpenAI `reasoning_effort` పాస్త్రూను బలవంతం చేయడానికి `reasoningControl`ను
`openai`గా సెట్ చేయండి, లేదా స్వయంచాలక గుర్తింపును ఉపయోగించడానికి దాన్ని విస్మరించండి/`null`గా
సెట్ చేయండి.

Claude Code auto-mode classifier రిక్వెస్ట్లు స్పష్టమైన reasoning నియంత్రణలు ఏవీ లేనప్పుడు
నేటివ్ thinkingను డిఫాల్ట్గా నిలిపివేత (disabled) చేస్తాయి. గుర్తింపు మోడల్ పేర్లు లేదా
completion పరిమితులను కాకుండా, Claude-ఫార్మాట్ రిక్వెస్ట్లలోని classifier యొక్క సిస్టమ్ మార్కర్ను
ఉపయోగిస్తుంది. స్పష్టమైన బాడీ నియంత్రణలు, మద్దతు ఉన్న effort/thinking హెడర్లు, రూటింగ్ నియమాలు
మరియు రిజాల్వ్ చేయబడిన మోడల్ effort వాటి ప్రస్తుత ప్రాధాన్యతను కొనసాగిస్తాయి. రెండు classifier
దశలు తమ ప్రాంప్ట్లు, completion పరిమితులు, stop సీక్వెన్స్లు మరియు నిజమైన అప్స్ట్రీమ్ అనుమతి
తీర్పులను నిలుపుకుంటాయి; రెండవ దశ తన అభ్యర్థించిన కనిపించే reasoningను సాధారణ టెక్స్ట్గా
అయినా ఉత్పత్తి చేయగలదు.

### వెర్షన్ మరియు రిలీజ్ ఛానెల్

```bash
GET /api/system/version
```

లూప్బ్యాక్-మాత్రమే మేనేజ్మెంట్ రూట్ (అడ్మిన్ అథ్). రన్ అవుతున్న వెర్షన్, తాజాగా ప్రచురించిన వెర్షన్ మరియు ఆటో-అప్డేట్ స్థితిని తిరిగి ఇస్తుంది. `releaseChannel` మరియు `channels` యాడిటివ్ ఫీల్డ్లు (rail 3.8.54); `channel` తన అసలు అర్థాన్నే కొనసాగిస్తుంది — డాష్బోర్డ్ అప్డేటర్ ఉపయోగించే డిప్లాయ్మెంట్ మోడ్ (`npm`, `source` లేదా `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — రన్ అవుతున్న బిల్డ్ యొక్క npm ఛానెల్: `-nightly.*` వెర్షన్ల కోసం `nightly`, ఇతర ప్రీ-రిలీజ్ల కోసం (`-rc.*`, `-beta.*`, `-alpha.*`) `next`, `channels.latest` కంటే పాత మేజర్ యొక్క స్థిరమైన వెర్షన్ కోసం `lts`, మిగిలిన అన్ని సందర్భాల్లో `latest`. ప్రచురణ సమయంలో npm dist-tag ఎంచుకునే `scripts/release/dist-tag.mjs` తో అదే నియమాలు.
- `channels` — ప్రతి dist-tag యొక్క ప్రచురిత హెడ్, `npm view omniroute dist-tags` నుండి (registry HTTP ఫాల్బ్యాక్), `latest` వలె అదే 10-నిమిషాల TTL తో కాష్ చేయబడుతుంది. `latest` ఎల్లప్పుడూ ఉంటుంది (ముందు `latest` ఫీల్డ్కు, ఆ తర్వాత `"unavailable"` కు ఫాల్బ్యాక్ అవుతుంది); `next`, `nightly` మరియు `lts` ఆ dist-tag ఉన్నప్పుడు మాత్రమే కనిపిస్తాయి. `Cache-Control: no-cache` రిక్వెస్ట్ రెండు లుకప్లను రిఫ్రెష్ చేస్తుంది.

ఛానెల్ మోడల్ (4.0 GA వరకు `latest` = v3, `next` = rc, `nightly` = `develop` బిల్డ్లు, 4.0 GA తర్వాత `lts` = v3 ప్యాచ్లు) `docs/ops/RELEASE_STRATEGY.md` లో వివరించబడింది.

## ఆడియో ట్రాన్స్క్రిప్షన్

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

కాన్ఫిగర్ చేసిన ఏదైనా STT ప్రొవైడర్ను ఉపయోగించి ఆడియో ఫైల్లను ట్రాన్స్క్రైబ్ చేయండి. మొదటి పాత్
సెగ్మెంట్ స్థానిక ప్రొవైడర్ను (`openai/…`, `deepgram/…`) ఎంచుకుంటుంది. మరొక వెండర్ మోడల్ను
తిరిగి ఎక్స్పోర్ట్ చేసే గేట్వేలు క్వాలిఫైడ్ idను
(`openrouter/deepgram/nova-3`) ఉపయోగిస్తాయి.

**అభ్యర్థన:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**ప్రతిస్పందన:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**మోడల్ idల ఉదాహరణలు:** `openai/whisper-1` (OpenAI కీ అవసరం),
`openrouter/deepgram/nova-3` (OpenRouter కీ అవసరం),
`deepgram/nova-3` (స్థానిక Deepgram కీ అవసరం). కేవలం
`deepgram/nova-3` అభ్యర్థన OpenRouterను ఉపయోగించదు.

**మద్దతు ఉన్న ఫార్మాట్లు:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## టోకెన్తో కూడిన VS Code / హెడర్లెస్ అలియాస్లు

ఏదైనా ఇంటిగ్రేషన్ `Authorization` హెడర్ను చేర్చలేనప్పుడు మరియు API కీని బేస్ URLలో పొందుపరచాల్సి వచ్చినప్పుడు ఈ అలియాస్లను ఉపయోగించండి.

```bash
# OpenAI-శైలి కేటలాగ్ అలియాస్
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-శైలి చాట్ అలియాస్లు
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-శైలి అలియాస్లు
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

ఉదాహరణ:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

గమనికలు:

- టోకెన్తో కూడిన అలియాస్లు `/v1/*` మరియు `/api/tags` ఉపయోగించే హ్యాండ్లర్లనే తిరిగి ఉపయోగిస్తాయి; ప్రతిస్పందన ఆకృతులు యథాతథంగా ఉంటాయి.
- క్లయింట్ కస్టమ్ హెడర్లకు మద్దతు ఇచ్చినప్పుడల్లా `Authorization: Bearer ...`ను ప్రాధాన్యంగా ఉపయోగించండి.
- URL-ఆధారిత టోకెన్లు రివర్స్-ప్రాక్సీ లాగ్లు, బ్రౌజర్ చరిత్ర మరియు OmniRouteకు వెలుపలి టెలిమెట్రీలో కనిపించవచ్చు. వాటిని డిఫాల్ట్ ప్రమాణీకరణ మోడ్గా కాకుండా అనుకూలత ఎంపికగా పరిగణించండి.

## బడ్జెట్

```bash
# అన్ని API కీల బడ్జెట్ స్థితిని పొందండి
GET /api/usage/budget

# బడ్జెట్ను సెట్ చేయండి లేదా నవీకరించండి
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **స్కీమా గమనికలు** (`setBudgetSchema`): `apiKeyId` తప్పనిసరి; `dailyLimitUsd`, `weeklyLimitUsd` లేదా `monthlyLimitUsd`లో కనీసం ఒకటి సున్నా కంటే ఎక్కువగా ఉండాలి. ఐచ్ఛిక ఫీల్డ్లు: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). పాత `{keyId, limit, period}` ఆకృతి `400 Bad Request`ను అందిస్తుంది.

## టోకెన్ పరిమితులు

ప్రతి API కీకి **టోకెన్** బడ్జెట్లు (పైన ఉన్న USD-ఆధారిత బడ్జెట్కు భిన్నమైనవి). అభ్యర్థన మార్గంలోనే అమలు చేయబడతాయి: కీ యొక్క ప్రస్తుత విండో వినియోగం దాని పరిమితిని చేరుకున్నప్పుడు, అభ్యర్థనలు `429 Too Many Requests`తో తిరస్కరించబడతాయి. పరిమితులను నిర్దిష్ట `model`, `provider`కు వర్తింపజేయవచ్చు లేదా కీ అంతటా `global`గా వర్తింపజేయవచ్చు; ఒక అభ్యర్థనకు అనేక పరిమితులు సరిపోలినప్పుడు, అత్యంత కఠినమైనది వర్తిస్తుంది.

```bash
# కీ యొక్క టోకెన్ పరిమితులను జాబితా చేయండి (ప్రస్తుత విండో వినియోగంతో సహా)
GET /api/usage/token-limits?apiKeyId=key-123

# టోకెన్ పరిమితిని సృష్టించండి లేదా నవీకరించండి
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id ద్వారా టోకెన్ పరిమితిని తొలగించండి
DELETE /api/usage/token-limits?id=tl-abc
```

> **స్కీమా గమనికలు** (`setTokenLimitSchema`): `apiKeyId` మరియు `scopeType` (`model` | `provider` | `global`) తప్పనిసరి. `scopeType` అనేది `global` అయితే తప్ప `scopeValue` తప్పనిసరి (ఉదా. `model` స్కోప్ కోసం మోడల్ id, `provider` స్కోప్ కోసం ప్రొవైడర్ id). `tokenLimit` తప్పనిసరిగా ధన పూర్ణసంఖ్య అయి ఉండాలి (స్ట్రింగ్ నుండి మార్చబడుతుంది). ఐచ్ఛికం: `id` (సృష్టించడానికి వదిలివేయండి, నవీకరించడానికి అందించండి), `resetInterval` (`daily` | `weekly` | `monthly`, డిఫాల్ట్ `monthly`), `resetTime` (`HH:MM`), `enabled` (డిఫాల్ట్ `true`). `GET` ప్రతిస్పందనలు ప్రతి పరిమితికి `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, మరియు `nextResetAt`లను జోడిస్తాయి. ఇది నిర్వహణ-తరగతి ఎండ్పాయింట్ (authz పైప్లైన్ ద్వారా ప్రామాణీకరణ కేంద్రీయంగా అమలు చేయబడుతుంది).

## అభ్యర్థన ప్రాసెసింగ్

1. క్లయింట్ `/v1/*`కు అభ్యర్థనను పంపుతుంది
2. రూట్ హ్యాండ్లర్ `handleChat`, `handleEmbedding`, `handleAudioTranscription`, లేదా `handleImageGeneration`ను కాల్ చేస్తుంది
3. మోడల్ పరిష్కరించబడుతుంది (ప్రత్యక్ష provider/model లేదా alias/combo)
4. ఖాతా లభ్యత ఫిల్టరింగ్తో స్థానిక DB నుండి క్రెడెన్షియల్స్ ఎంచుకోబడతాయి
5. చాట్ కోసం: `handleChatCore` సెమాంటిక్/సిగ్నేచర్ క్యాష్ను తనిఖీ చేసి, కాంబో కంప్రెషన్ సెట్టింగ్లను పరిష్కరిస్తుంది
6. ప్రారంభ కంప్రెషన్ ప్రారంభించబడి ఉంటే, ప్రొవైడర్ అనువాదానికి ముందు అమలవుతుంది (`lite`, Caveman, RTK, లేదా స్టాక్డ్)
7. ప్రొవైడర్ ఎగ్జిక్యూటర్ అప్స్ట్రీమ్ అభ్యర్థనను పంపుతుంది
8. ప్రతిస్పందన తిరిగి క్లయింట్ ఫార్మాట్కు అనువదించబడుతుంది (చాట్) లేదా యథాతథంగా తిరిగి ఇవ్వబడుతుంది (ఎంబెడ్డింగ్లు/చిత్రాలు/ఆడియో)
9. వినియోగం, కంప్రెషన్ విశ్లేషణలు మరియు అభ్యర్థన లాగ్లు నమోదు చేయబడతాయి
10. లోపాలు సంభవించినప్పుడు కాంబో నియమాల ప్రకారం ఫాల్బ్యాక్ వర్తించబడుతుంది

పూర్తి ఆర్కిటెక్చర్ సూచన: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## కాంబో నిర్వహణ

ఉన్నత-స్థాయి రూటింగ్ కాంబోలను (`/api/combos*` కింద ఇప్పటికే సంగ్రహించబడినవి) మోడల్ id నమూనా నుండి 1:1గా కూడా మ్యాప్ చేయవచ్చు, తద్వారా OpenAI-శైలి మోడల్ idను కాంబోకు పారదర్శకంగా మళ్లించవచ్చు.

| పద్ధతి | పాత్                             | వివరణ                                                                                   |
| ------ | -------------------------------- | --------------------------------------------------------------------------------------- |
| GET    | `/api/model-combo-mappings`      | అన్ని model→combo మ్యాపింగ్లను జాబితా చేయండి                                            |
| POST   | `/api/model-combo-mappings`      | మ్యాపింగ్ను సృష్టించండి — బాడీ: `{pattern, comboId, priority?, enabled?, description?}` |
| GET    | `/api/model-combo-mappings/[id]` | ఒకే మ్యాపింగ్ను పొందండి                                                                 |
| PUT    | `/api/model-combo-mappings/[id]` | ఇప్పటికే ఉన్న మ్యాపింగ్ ఫీల్డ్లను నవీకరించండి                                           |
| DELETE | `/api/model-combo-mappings/[id]` | మ్యాపింగ్ను తొలగించండి                                                                  |

**Auth:** నిర్వహణ సెషన్/API కీ (`requireManagementAuth`).

| పద్ధతి | మార్గం                    | వివరణ                                                                            |
| ------ | ------------------------- | -------------------------------------------------------------------------------- |
| GET    | `/api/webhooks`           | వెబ్హుక్స్ను జాబితా చేస్తుంది (సీక్రెట్లు `<prefix>...` రూపంలో మాస్క్ చేయబడతాయి) |
| POST   | `/api/webhooks`           | వెబ్హుక్ను సృష్టిస్తుంది — బాడీ: `{url, events?: ["*"], secret?, description?}`  |
| GET    | `/api/webhooks/[id]`      | వెబ్హుక్ను పొందుతుంది                                                            |
| PUT    | `/api/webhooks/[id]`      | url/events/secret/descriptionను అప్డేట్ చేస్తుంది                                |
| DELETE | `/api/webhooks/[id]`      | వెబ్హుక్ను తొలగిస్తుంది                                                          |
| POST   | `/api/webhooks/[id]/test` | వెబ్హుక్ URLకు పరీక్ష పేలోడ్ను పంపి, డెలివరీ స్థితిని అందిస్తుంది                |

**ప్రామాణీకరణ:** నిర్వహణ సెషన్/API కీ (`requireManagementAuth`).

## నమోదు చేసిన కీలు (స్వయంచాలక నిర్వహణ)

రోజువారీ/గంటవారీ కోటాలతో, అనుసంధానిత ప్రొవైడర్/ఖాతాలో API కీలను జారీ చేయడానికి మరియు రొటేట్ చేయడానికి స్వయంచాలక కీ నిర్వహణ ఉపవ్యవస్థ ద్వారా ఉపయోగించబడుతుంది.

| పద్ధతి | మార్గం                                | వివరణ                                                                                                                                                                                                                           |
| ------ | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/registered-keys`             | నమోదు చేసిన కీల జాబితా (మాస్క్ చేసిన ప్రిఫిక్స్ మాత్రమే)                                                                                                                                                                        |
| POST   | `/api/v1/registered-keys`             | కొత్త నమోదు చేసిన కీని జారీ చేస్తుంది — బాడీ: `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}`. ముడి కీని **ఒక్కసారి మాత్రమే** తిరిగి ఇస్తుంది. కోటా తిరస్కరణపై `429` తిరిగి ఇస్తుంది. |
| GET    | `/api/v1/registered-keys/[id]`        | నమోదు చేసిన కీ మెటాడేటాను పొందుతుంది (ముడి మెటీరియల్ ఉండదు)                                                                                                                                                                     |
| DELETE | `/api/v1/registered-keys/[id]`        | నమోదు చేసిన కీని రద్దు చేస్తుంది                                                                                                                                                                                                |
| POST   | `/api/v1/registered-keys/[id]/revoke` | స్పష్టమైన రద్దు ఎండ్పాయింట్ (DELETE వలె అదే ప్రభావం)                                                                                                                                                                            |

**ప్రామాణీకరణ:** నిర్వహణ సెషన్/API కీ (`requireManagementAuth`) — `/api/keys`లో ఉన్న అదే గార్డ్: డాష్బోర్డ్ సెషన్, స్థానిక CLI టోకెన్ లేదా `manage`/`admin` స్కోప్ ఉన్న API కీ; ఇన్ఫరెన్స్కు మాత్రమే పరిమితమైన API కీలకు `403` వస్తుంది. `/v1/quotas/check` మరియు `/v1/issues/report` కూడా చూడండి.

## ఏజెంట్ల ప్రోటోకాల్

OmniRoute వినియోగదారుల తరఫున రిమోట్గా అమలు చేయబడే క్లౌడ్ ఏజెంట్ టాస్క్లు (Claude Code, Codex Cloud, OpenHands మొదలైనవి).

| పద్ధతి | పాత్                          | వివరణ                                                                                                                                                                    |
| ------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/v1/agents/tasks`        | టాస్క్ల జాబితా — ఐచ్ఛికంగా `?provider=`, `?status=`, `?limit=` (1–500, డిఫాల్ట్ 50)                                                                                      |
| POST   | `/api/v1/agents/tasks`        | టాస్క్ను సృష్టిస్తుంది — బాడీ `CreateCloudAgentTaskSchema` ద్వారా ధృవీకరించబడుతుంది (`providerId`, `prompt`, `source`, `options?`). టాస్క్ ఎన్వలప్తో `201`ను అందిస్తుంది |
| DELETE | `/api/v1/agents/tasks?id=...` | ఒక టాస్క్ను తొలగిస్తుంది                                                                                                                                                 |
| GET    | `/api/v1/agents/tasks/[id]`   | టాస్క్ను చదువుతుంది — `external_id` సెట్ చేయబడినప్పుడు అప్స్ట్రీమ్ క్లౌడ్ ఏజెంట్ నుండి స్థితిని సమకాలికంగా రిఫ్రెష్ చేస్తుంది                                            |
| POST   | `/api/v1/agents/tasks/[id]`   | ప్రత్యేకీకరించిన చర్య: `{action: "approve"}`, `{action: "message", message}`, లేదా `{action: "cancel"}`                                                                  |
| DELETE | `/api/v1/agents/tasks/[id]`   | id ద్వారా నిర్దిష్ట టాస్క్ను తొలగిస్తుంది                                                                                                                                |

> **ప్రామాణీకరణ:** ప్రతి పద్ధతికి మేనేజ్మెంట్ ప్రామాణీకరణ అవసరం (`requireCloudAgentManagementAuth`). v3.8.0కు ముందు ఇవి ప్రామాణీకరణ లేకుండానే ఉండేవి — బ్రేకింగ్ మార్పు కోసం `588a0333` కమిట్ను చూడండి.

```bash
# Claude Code క్లౌడ్ టాస్క్ను సృష్టించండి
curl -X POST http://localhost:20128/api/v1/agents/tasks \
  -H "Authorization: Bearer your-management-key" \
  -H "Content-Type: application/json" \
  -d '{"providerId":"claude-code-cloud","prompt":"Fix the failing test","source":{"repo":"...","branch":"..."}}'
```

## మేనేజ్మెంట్ ప్రాక్సీలు

ప్రొవైడర్లు, ఖాతాలు లేదా గ్లోబల్గా కేటాయించగల అవుట్బౌండ్ HTTP(S)/SOCKS ప్రాక్సీలు.

| పద్ధతి | పాత్                                         | వివరణ                                                                                                                                                                     |
| ------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## స్థితిస్థాపకత (విస్తరించబడింది)

OmniRoute మూడు స్వతంత్ర తాత్కాలిక-వైఫల్య యంత్రాంగాలను అందిస్తుంది; దిగువ నిర్వహణ ఎండ్పాయింట్లు ఆపరేటర్లకు వాటిని చదవడానికి మరియు భర్తీ చేయడానికి అనుమతిస్తాయి:

| పరిధి             | స్థితి నిల్వ                             | చదవడం                                     | రీసెట్ / క్లియర్                                                    |
| ----------------- | ---------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------- |
| ప్రొవైడర్ బ్రేకర్ | `domain_circuit_breakers` + ఇన్-మెమరీ    | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                        |
| కనెక్షన్ కూల్డౌన్ | ప్రొవైడర్ కనెక్షన్లపై `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (సోమరిగా మళ్లీ ప్రారంభమవుతుంది; provider PUT ద్వారా క్లియర్ చేయండి) |
| మోడల్ లాక్అవుట్   | ఇన్-మెమరీ మోడల్-లభ్యత రిజిస్ట్రీ         | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                            |

`PATCH /api/resilience` `providerBreaker.oauth` మరియు `providerBreaker.apikey` కింద ప్రొవైడర్ బ్రేకర్ భర్తీలను అంగీకరిస్తుంది. ప్రతి ప్రొఫైల్ `degradationThreshold`, `failureThreshold`, మరియు `resetTimeoutMs` లకు మద్దతు ఇస్తుంది; అదే ఫీల్డ్లు Dashboard → Settings → Resilience లో బహిర్గతం చేయబడతాయి.

```bash
# ఒకే మోడల్ లాక్అవుట్ను క్లియర్ చేయండి
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# ప్రతి లాక్అవుట్ను తుడిచివేయండి
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

పూర్తి భావనాత్మక సూచన మరియు బ్రేకర్ డిఫాల్ట్లు: [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" మరియు [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) చూడండి.

### రేటు-పరిమితి క్యూ & ఆటో-ఎనేబుల్ సేఫ్టీ నెట్

- **మద్దతు ఉన్న రైట్ పాత్**: `POST /api/rate-limits` బాడీ `{"connectionId": "<id>", "enabled": true|false}` తో కనెక్షన్ కోసం రేటు-పరిమితి రక్షణను టోగుల్ చేయడానికి మద్దతు ఉన్న నిర్వహణ ఎండ్పాయింట్. `PUT /api/providers/[id]` ఉద్దేశపూర్వకంగా `rateLimitProtection` ను సవరించదు లేదా ఫ్లిప్ చేయదు (#11278).
- **`enabled: false` యొక్క భాష్యం**: `enabled: false` సెట్టింగ్ కనెక్షన్ కోసం స్పష్టమైన రక్షణను తొలగిస్తుంది, కానీ చురుకైన API-key కనెక్షన్ను గ్లోబల్ ఆటో-ఎనేబుల్ సేఫ్టీ నెట్ (`autoEnableApiKeyProviders = true`) నుండి **మినహాయించదు**. `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) లో, `false` మరియు `undefined` సమానం; స్పష్టమైన రక్షణ లేని చురుకైన API-key కనెక్షన్లు ఆటో-ఎనేబుల్ సేఫ్టీ నెట్ కింద రక్షితంగానే ఉంటాయి.
- **గ్లోబల్ డిజేబుల్**: రేటు-పరిమితి క్యూలు లేకుండా API-key కనెక్షన్లను నడపడానికి, `RATE_LIMIT_AUTO_ENABLE=false` (env) లేదా `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) ద్వారా సేఫ్టీ నెట్ను గ్లోబల్గా డిజేబుల్ చేయండి.

## MCP సర్వర్

OmniRoute, 3 రవాణాలతో (stdio, SSE, streamable-http) మరియు పరిధి-పరిమిత సాధనాలతో కూడిన అంతర్నిర్మిత Model Context Protocol సర్వర్ను అందిస్తుంది. దిగువ డ్యాష్బోర్డ్ ఎండ్పాయింట్లు స్థితి/ఆడిట్ డేటాను చదివి, HTTP రవాణాలను ప్రాక్సీ చేస్తాయి.

| విధానం | మార్గం | వివరణ |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | హార్ట్బీట్, రవాణా, ఆన్లైన్ స్థితి, చివరి కాల్, అగ్ర సాధనాలు, 24గం విజయ శాతం |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints`తో కూడిన MCP సాధనాల జాబితా |
| GET | `/api/mcp/sse` | SSE రవాణా కోసం SSE స్ట్రీమ్ను తెరుస్తుంది (MCP నిలిపివేయబడి ఉంటే లేదా రవాణా సరిపోలకపోతే `503`ను తిరిగి ఇస్తుంది) |
| POST | `/api/mcp/sse` | SSE రవాణాపై JSON-RPC ఫ్రేమ్ను పంపుతుంది |
| GET | `/api/mcp/stream` | Streamable HTTP రవాణా యొక్క SSE వైపును తెరుస్తుంది (సర్వర్ ప్రారంభించిన సందేశాలు) |
| POST | `/api/mcp/stream` | Streamable HTTP రవాణాపై JSON-RPC ఫ్రేమ్ను పంపుతుంది |
| DELETE | `/api/mcp/stream` | Streamable HTTP సెషన్ను ముగిస్తుంది |
| GET | `/api/mcp/audit` | ఆడిట్ లాగ్ను ప్రశ్నిస్తుంది — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | సమగ్ర ఆడిట్ గణాంకాలు (మొత్తాలు, విజయ శాతం, సగటు వ్యవధి, అగ్ర సాధనాలు) |

**ప్రామాణీకరణ:** `sse`/`stream` రవాణాలు MCP-నిర్దిష్ట ప్రామాణీకరణ ఉపరితలాన్ని అనుసరిస్తాయి (`mcp` పరిధితో కూడిన Bearer API కీ); `status`/`tools`/`audit*` రూట్లను డ్యాష్బోర్డ్ నుండి చదవవచ్చు (డ్యాష్బోర్డ్ హోస్ట్ను చేరుకోవడానికి అవసరమైనదానికంటే అదనపు ప్రామాణీకరణ అవసరం లేదు).

> రెండు HTTP రవాణాలు `settings.mcpEnabled` మరియు `settings.mcpTransport` ద్వారా నియంత్రించబడతాయి — రవాణా సరిపోలకపోతే `400`, MCP నిలిపివేయబడిన స్థితిలో ఉంటే `503` తిరిగి వస్తుంది.

## A2A సర్వర్

OmniRoute తనిఖీ/డ్యాష్బోర్డ్ వినియోగం కోసం REST ర్యాపర్తో పాటు A2A (Agent-to-Agent) JSON-RPC 2.0 ఎండ్పాయింట్ను అందిస్తుంది.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY సెట్ చేయకపోతే ఐచ్ఛికం
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "ఈ కోడింగ్ టాస్క్ను రూట్ చేయండి"}]
  }
}
```

మద్దతు ఉన్న మెథడ్లు (అన్నీ `settings.a2aEnabled` ద్వారా నియంత్రించబడతాయి):

| మెథడ్            | వివరణ                                                                   |
| ---------------- | ----------------------------------------------------------------------- |
| `message/send`   | సింక్రోనస్ స్కిల్ అమలు; `{task, artifacts, metadata}`ను తిరిగి ఇస్తుంది |
| `message/stream` | అదే స్కిల్ సెట్ను స్ట్రీమింగ్ SSE ద్వారా అమలు చేస్తుంది                 |
| `tasks/get`      | `taskId` ద్వారా ఒక టాస్క్ను పొందుతుంది                                  |
| `tasks/cancel`   | `taskId` ద్వారా ఒక టాస్క్ను రద్దు చేస్తుంది                             |

అంతర్నిర్మిత స్కిల్లు: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### ఏజెంట్ కార్డ్

```bash
GET /.well-known/agent.json
```

పబ్లిక్ A2A ఏజెంట్ కార్డ్ను (పేరు, వివరణ, సామర్థ్యాలు, స్కిల్ కేటలాగ్, ప్రామాణీకరణ స్కీమ్) తిరిగి ఇస్తుంది — పబ్లిక్గా 1 గంట పాటు క్యాష్ చేయబడుతుంది. ప్రామాణీకరణ అవసరం లేదు.

### REST సహాయకాలు

| మెథడ్ | పాత్                         | వివరణ                                                                                                               |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | A2A ప్రారంభ స్థితి + టాస్క్ గణాంకాలు + క్యాష్ చేసిన ఏజెంట్ కార్డ్ సారాంశం                                           |
| GET   | `/api/a2a/tasks`             | టాస్క్ల జాబితా — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (REST సహాయకంగా అమలు చేయబడలేదు — JSON-RPC `message/send` ద్వారా సృష్టించండి)                                         |
| GET   | `/api/a2a/tasks/[id]`        | ఒక టాస్క్ను పొందండి                                                                                                 |
| POST  | `/api/a2a/tasks/[id]/cancel` | ఒక టాస్క్ను రద్దు చేయండి                                                                                            |

**ప్రామాణీకరణ:** REST సహాయకాలు నిర్వహణ ప్రామాణీకరణ లేకుండా పనిచేస్తాయి (డ్యాష్బోర్డ్ ద్వారా చదవగలిగేవి); కాన్ఫిగర్ చేసి ఉంటే JSON-RPC `/a2a` రూట్ Bearer `OMNIROUTE_API_KEY`ను ఉపయోగిస్తుంది.

## ACP (Agent Client Protocol) నిర్వహణ

చైల్డ్ ప్రాసెస్లుగా. ఈ ఎండ్పాయింట్లు ACP ఏజెంట్ గుర్తింపును మరియు కస్టమ్ ఏజెంట్
నమోదును నిర్వహిస్తాయి.

| పద్ధతి | పాత్              | వివరణ                                                                                                                                                                            |
| ------ | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | ఇన్స్టాలేషన్ స్థితి, వెర్షన్, బైనరీతో సహా తెలిసిన అన్ని CLI ఏజెంట్లను (అంతర్నిర్మిత + కస్టమ్) జాబితా చేస్తుంది                                                                   |
| POST   | `/api/acp/agents` | కస్టమ్ ACP ఏజెంట్ను నమోదు చేస్తుంది లేదా క్యాష్ను రిఫ్రెష్ చేస్తుంది — బాడీ: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` లేదా `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | కస్టమ్ ACP ఏజెంట్ను తొలగిస్తుంది — క్వెరీ పారామీటర్: `?id=<agentId>`                                                                                                             |

**ప్రతిస్పందన ఉదాహరణ** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**ప్రామాణీకరణ:** నిర్వహణ సెషన్ (డ్యాష్బోర్డ్ `auth_token` కుకీ) లేదా
నిర్వహణ-స్కోప్ గల API కీ అవసరం.

పూర్తి వివరాల కోసం [ACP ఫ్రేమ్వర్క్](../frameworks/ACP.md) చూడండి.

నాలుగు క్రెడెన్షియల్ కుటుంబాలు (డ్యాష్బోర్డ్ సెషన్, స్థానిక CLI టోకెన్, `oma_live_…` యాక్సెస్ టోకెన్, నిర్వహణ-పరిధి API కీ) మరియు అవి ఇన్ఫరెన్స్ కీలతో ఎలా భిన్నంగా ఉంటాయో తెలుసుకోవడానికి [నిర్వహణ ప్రమాణీకరణ](../guides/MANAGEMENT-AUTH.md) చూడండి.

- డ్యాష్బోర్డ్ రూట్లు (`/dashboard/*`) `auth_token` కుకీని ఉపయోగిస్తాయి
- లాగిన్ సేవ్ చేసిన పాస్వర్డ్ హాష్ను ఉపయోగిస్తుంది; అది అందుబాటులో లేకపోతే `INITIAL_PASSWORD`ను ఉపయోగిస్తుంది
- `requireLogin`ను `/api/settings/require-login` ద్వారా టాగుల్ చేయవచ్చు
- `REQUIRE_API_KEY=true` అయినప్పుడు `/v1/*` రూట్లకు ఐచ్ఛికంగా బేరర్ API కీ అవసరం
- ఈ రెఫరెన్స్లో "నిర్వహణ టోకెన్" / "నిర్వహణ-పరిధి API కీ" అంటే ఆ గైడ్లోని కుటుంబాలలో ఒకటి — నిర్వచించని అదనపు రహస్య రకం కాదు

> **బ్రేకింగ్ మార్పు (v3.8.0)** — `/api/v1/agents/tasks/*` మరియు కూల్డౌన్ నిర్వహణ ఎండ్పాయింట్లకు ఇప్పుడు **నిర్వహణ ప్రమాణీకరణ** (డ్యాష్బోర్డ్ `auth_token` కుకీ లేదా నిర్వహణ-పరిధి API కీ) అవసరం. గతంలో ఈ రూట్లను ప్రమాణీకరణ లేకుండా కాల్ చేసిన క్లయింట్లు `401 Unauthorized`ను అందుకుంటాయి. కమిట్ `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) చూడండి.
