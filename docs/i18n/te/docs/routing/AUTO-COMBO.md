## జీరో-కాన్ఫిగ్ ఆటో-రూటింగ్ (`auto/` ప్రిఫిక్స్)

> **కొత్తది:** కాంబోను సృష్టించాల్సిన అవసరం లేదు. ఏ క్లయింట్లోనైనా నేరుగా `auto/` ప్రిఫిక్స్ను ఉపయోగించండి.

### త్వరిత ఉదాహరణలు

| మోడల్ ID       | వేరియంట్ | ప్రవర్తన                                                                |
| -------------- | -------- | ----------------------------------------------------------------------- |
| `auto`         | డిఫాల్ట్ | కనెక్ట్ చేయబడిన అన్ని ప్రొవైడర్లు, LKGP వ్యూహం, సమతుల్య వెయిట్లు        |
| `auto/coding`  | కోడింగ్  | నాణ్యతకు ప్రాధాన్యమిచ్చే వెయిట్లు, కోడ్ జనరేషన్కు అనుకూలం               |
| `auto/fast`    | వేగవంతం  | తక్కువ-లేటెన్సీ వెయిటెడ్ ఎంపిక                                          |
| `auto/cheap`   | చౌక      | ఖర్చు-ఆప్టిమైజ్డ్ రూటింగ్ (మొదట అత్యల్ప ఖర్చు)                          |
| `auto/offline` | ఆఫ్లైన్  | అత్యధిక కోటా లభ్యత ఉన్న ప్రొవైడర్లకు ప్రాధాన్యం ఇస్తుంది                |
| `auto/smart`   | స్మార్ట్ | మెరుగైన మోడల్ అన్వేషణ కోసం నాణ్యత-ముందు + అధిక అన్వేషణ రేటు (10%)       |
| `auto/lkgp`    | lkgp     | స్పష్టమైన LKGP (డిఫాల్ట్ `auto` మాదిరిగానే)                             |
| `auto/chaos`   | కేయాస్   | సమాంతర ఫ్యాన్-అవుట్, ఒక్కో ప్రొవైడర్కు ఒక మోడల్ (ఫాల్ట్ ఇంజెక్షన్ కాదు) |

### కేటగిరీ × టియర్ కాంపోజిషన్ (`auto/<category>:<tier>`)

OpenRouter-శైలి సఫిక్స్లు **ఎలాంటి రూట్** (కేటగిరీ) కావాలో, దాన్ని **ఎలా ఆప్టిమైజ్ చేయాలో** (టియర్) వేరు చేస్తాయి; అందువల్ల వాటిని మీరు స్వేచ్ఛగా కలపవచ్చు (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **కేటగిరీలు** (సామర్థ్యం ఆధారంగా అభ్యర్థుల పూల్ను ఫిల్టర్ చేస్తాయి): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` విజన్ సామర్థ్యం ఉన్న మోడళ్లను ఉంచుతాయి; `reasoning` రీజనింగ్/థింకింగ్ మోడళ్లను ఉంచుతుంది.
- **టియర్లు** (స్కోరింగ్ వెయిట్లు / పూల్ ఫిల్టర్ను ఎంచుకుంటాయి): `fast` (త్వరిత డెలివరీ) · `cheap` (`floor` అలియాస్, ఖర్చు-పొదుపు) · `reliable` (సర్క్యూట్-బ్రేకర్ ఆరోగ్యం + లేటెన్సీ స్థిరత్వం) · `free` / `pro` (`classifyTier` ద్వారా మోడల్ టియర్ ఆధారంగా పూల్ను ఫిల్టర్ చేస్తాయి — ఉచిత టియర్ వర్సెస్ ప్రీమియం).

| ఉదాహరణ                 | ఇలా పరిష్కరించబడుతుంది                                        |
| ---------------------- | ------------------------------------------------------------- |
| `auto/coding:fast`     | కోడింగ్ పూల్, తక్కువ-లేటెన్సీ వెయిట్లు                        |
| `auto/coding:cheap`    | కోడింగ్ పూల్, ఖర్చు-ఆప్టిమైజ్డ్ (`auto/coding:floor` అలియాస్) |
| `auto/reasoning:pro`   | రీజనింగ్/థింకింగ్ మోడళ్లు మాత్రమే, ప్రీమియం టియర్             |
| `auto/vision`          | విజన్ సామర్థ్యం ఉన్న మోడళ్లు (టియర్ లేదు → సమతుల్య వెయిట్లు)  |
| `auto/multimodal:free` | మల్టీమోడల్ సామర్థ్యం ఉన్న మోడళ్లు, ఉచిత టియర్ మాత్రమే         |

చెల్లుబాటు అయ్యే ఏ `auto/<category>[:<tier>]` అయినా అవసరమైనప్పుడు పరిష్కరించబడుతుంది; ఎంపిక చేసిన ఉపసమితి `/v1/models` మరియు డ్యాష్బోర్డ్లో ప్రకటించబడుతుంది (`open-sse/services/autoCombo/builtinCatalog.ts`లోని `AUTO_SUFFIX_VARIANTS`). ఫిల్టరింగ్ **ఫెయిల్-ఓపెన్** — ఏ కనెక్ట్ చేయబడిన మోడల్కూ పరిమితి సరిపోలకపోతే, రూటింగ్ ఎప్పటికీ విఫలం కాకుండా పూర్తి పూల్ ఉపయోగించబడుతుంది. కోర్ స్కోరర్ (`combo.ts`) మారదు; కేటగిరీ/టియర్ ఫిల్టర్ `buildAutoCandidates`లో వర్తింపజేయబడుతుంది.

> **లైవ్ మోడల్ ఇంటెలిజెన్స్:** `ARENA_ELO_SYNC_ENABLED` ఫ్లాగ్ ఆన్లో ఉన్నప్పుడు, ఆటో-రూటింగ్ అనుకూలత లైవ్ **Arena ELO** ర్యాంకింగ్లు + **models.dev** టియర్ డేటా ఆధారంగా నిర్ణయించబడుతుంది (లేకపోతే స్టాటిక్ ఫిట్నెస్ మ్యాప్కు ఫాల్బ్యాక్ అవుతుంది).

**ఎలా ఉపయోగించాలి:**

```bash
# OpenAI ఫార్మాట్కు మద్దతిచ్చే ఏదైనా IDE లేదా CLI సాధనం
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# మీ కోడ్/కాన్ఫిగ్లో మోడల్ను ఇలా సెట్ చేయండి:
model: "auto"                 # సమతుల్య డిఫాల్ట్
model: "auto/coding"          # కోడింగ్ పనులకు ఉత్తమం
model: "auto/fast"            # అందుబాటులో ఉన్న వాటిలో అత్యంత వేగవంతమైనది
model: "auto/cheap"           # ఒక్కో టోకెన్కు అత్యంత చౌకైనది
```

**ఏం జరుగుతుంది:**

1. OmniRoute `src/sse/handlers/chat.ts`లోని `auto/` ప్రిఫిక్స్ను గుర్తిస్తుంది
2. డేటాబేస్ నుండి అన్ని **యాక్టివ్ ప్రొవైడర్ కనెక్షన్లను** క్వెరీ చేస్తుంది
3. చెల్లుబాటు అయ్యే క్రెడెన్షియల్స్ (API కీ లేదా OAuth టోకెన్) ఉన్న వాటిని ఫిల్టర్ చేస్తుంది
4. ఒక్కో కనెక్షన్కు మోడల్ను నిర్ణయిస్తుంది (`connection.defaultModel` లేదా ప్రొవైడర్ యొక్క మొదటి మోడల్)
5. మెమరీలో ఒక **వర్చువల్ కాంబో**ను నిర్మిస్తుంది (DBలో నిల్వ చేయదు)
6. ఎంచుకున్న వేరియంట్ వెయిట్ ప్రొఫైల్ + LKGP వ్యూహాన్ని ఉపయోగించి రూట్ చేస్తుంది

**ముఖ్య లక్షణాలు:**

- ✅ **ఎల్లప్పుడూ ఆన్లో:** టాగుల్, కాంబో సృష్టి లేదా కాన్ఫిగరేషన్ అవసరం లేదు
- ✅ **డైనమిక్:** ప్రస్తుతం కనెక్ట్ చేయబడిన ప్రొవైడర్లను స్వయంచాలకంగా ప్రతిబింబిస్తుంది
- ✅ **సెషన్ స్టికీనెస్:** చివరిగా విజయవంతమైన ప్రొవైడర్కు ప్రాధాన్యం దక్కేలా LKGP నిర్ధారిస్తుంది
- ✅ **మల్టీ-అకౌంట్ అవగాహన:** ఒక్కో ప్రొవైడర్ కనెక్షన్ ఒక ప్రత్యేక అభ్యర్థిగా మారుతుంది
- ✅ **DB రైట్లు లేవు:** వర్చువల్ కాంబో అభ్యర్థన కోసం మాత్రమే ఉంటుంది, పర్సిస్టెన్స్ ఓవర్హెడ్ సున్నా

### ఒక్కో కీకి అభ్యర్థుల నియంత్రణ (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` తర్వాత వచ్చే సఫిక్స్, లేదా
బేస్ ఛానల్ కోసం లిటరల్ `auto`) అనేది ఒక **రీడ్-ఓన్లీ** ఎండ్పాయింట్. ఇది ఇప్పటికే ఉన్న
రెసిలియన్స్ రీడ్లను తిరిగి ఉపయోగిస్తూ, లైవ్ రీచబిలిటీతో అలంకరించిన `auto/*` ఛానల్
ప్రస్తుత అభ్యర్థుల పూల్ను జాబితా చేస్తుంది (ముడి బ్రేకర్ `state`ను ఎప్పటికీ ఉపయోగించదు):

- ప్రొవైడర్ సర్క్యూట్ బ్రేకర్ — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- కనెక్షన్ కూల్డౌన్ — పరిష్కరించబడిన `provider_connections` రోలోని `rateLimitedUntil` / `testStatus`
- మోడల్ లాక్అవుట్ — `isModelLocked(provider, connectionId, model)`

ప్రతి అభ్యర్థి ఈ API కీకి సంబంధించిన `excluded` ఫ్లాగ్ను కూడా కలిగి ఉంటుంది. మినహాయింపులు
ఒక్కో API కీకి విడిగా నిల్వ చేయబడతాయి (`auto_candidate_overrides` టేబుల్, మైగ్రేషన్ `128`) —
OmniRouteలో `users` టేబుల్ లేకుండా సింగిల్-టెనెంట్గా ఉంటుంది, కాబట్టి `apiKeyId` అనేది
వాస్తవంగా ఒక్కో కాలర్కు అత్యంత సమీపమైన ఐడెంటిటీ — మరియు అవి
`open-sse/services/autoCombo/virtualFactory.ts`లోని అభ్యర్థి-పూల్ చోక్పాయింట్ వద్ద,
ప్యూర్, యూనిట్-టెస్ట్ చేయబడిన `filterExcludedCandidates()`
(`open-sse/services/autoCombo/candidateOverrides.ts`) ద్వారా అమలు చేయబడతాయి.
ఈ ఫిల్టర్ **ఫెయిల్-ఓపెన్**: సెట్ చేయని apiKeyId/ఛానల్ లేదా DB లుకప్ వైఫల్యం రెండూ
పూల్ను ఫిల్టర్ చేయకుండా ఉంచుతాయి; అందువల్ల ఎలాంటి ఓవర్రైడ్లు కాన్ఫిగర్ చేయని ఆపరేటర్కు
ఈ ఫీచర్కు ముందున్న రూటింగ్తో బైట్-స్థాయిలో ఒకే విధమైన ఫలితం కనిపిస్తుంది.

**తదుపరి ఇష్యూకు వాయిదా వేయబడింది:** ప్రతి-అభ్యర్థి వెయిట్లు + స్పష్టమైన క్రమం (స్థాయి 3
— ఇప్పటికే ఉన్న వెయిటెడ్/ప్రాధాన్యతా వ్యూహ మార్గాలకు అందించబడుతుంది) మరియు నిర్దిష్ట
`combo.ts` వ్యూహాన్ని ప్రతి `auto/*` ఛానెల్కు పిన్ చేయడం (స్థాయి 4). సింగిల్-టెనెంట్
మోడల్ను పరిగణనలోకి తీసుకున్నప్పుడు ఓవర్రైడ్లు ప్రతి-API-కీకి పరిమితంగా ఉండాలా లేదా
గ్లోబల్గా మారాలా అనే ఓపెన్ ప్రశ్న కోసం #7819 ప్రణాళికను చూడండి.

## సేవ్ చేయబడిన ఆటో కాంబోల కోసం ఖాతా ప్రాధాన్యతలు

ఇంటెలిజెంట్ ఆటో ఎడిటర్ ఐచ్ఛికాన్ని అందిస్తుంది** ఖాతా ప్రాధాన్యతలు** విభాగం. ప్రతి కనెక్షన్ ప్రాధాన్యమైనది, సాధారణం (డిఫాల్ట్), రిజర్వ్ లేదా మినహాయించబడింది. బహుళ కనెక్షన్లు ఒక శ్రేణిని పంచుకోగలవు. ఆటో మొదటి అర్హత కలిగిన శ్రేణిని ఎంచుకుంటుంది, దాని scoring/router ప్రవర్తనను అక్కడే ఉంచుతుంది; విఫలమైన ప్రయత్నాలు మిగిలిన కాంక్రీట్ ఖాతాలకు వస్తాయి, రిజర్వ్కు ముందు సాధారణం కంటే ముందు ప్రాధాన్యత ఇవ్వబడుతుంది. మినహాయించిన కనెక్షన్లు ఈ కాంబో ద్వారా ఎప్పుడూ ఉపయోగించబడవు.

సెట్టింగ్ `config.accountPreferences` గా నిల్వ చేయబడుతుంది, ID కనెక్షన్ ద్వారా కీ చేయబడింది:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

విస్మరించబడిన లేదా ఖాళీ మ్యాప్ ఇప్పటికే ఉన్న రూటింగ్ను కలిగి ఉంటుంది. ప్రాధాన్యతలు నిలిపివేయబడిన కనెక్షన్లను ప్రారంభించవు, API-కీ యాక్సెస్ను మంజూరు చేయవు, కోటా-నిరోధించిన అభ్యర్థులను పునరుద్ధరించవు లేదా బడ్జెట్ తనిఖీలను దాటవేయవు. ప్రతి ప్రయత్నం దాని కాంక్రీట్ కనెక్షన్కు పరిమితం చేయబడింది, కాబట్టి ఖాతా ఫాల్బ్యాక్ కాంబో రౌటర్ వెనుక శ్రేణులను అధిగమించదు. ఇప్పటికే ఉన్న సెషన్ అనుబంధం అర్హత కలిగిన ఖాతాను కలిగి ఉండవచ్చు; స్థానిక మలుపుకు కట్టుబడి ఉన్న ఖాతాను మినహాయించి, నిశ్శబ్దంగా ఖాతాలను మార్చే బదులు ఆ మలుపులు తిరుగుతాయి.

కాన్ఫిగర్ చేయబడిన ప్రాధాన్యతలు ఖాతా-అవేర్ ఆటో పాత్ను ఉపయోగిస్తాయి: అన్బౌండ్ కాంటెక్స్ట్-కాష్, స్మార్ట్-పైప్లైన్, గందరగోళం మరియు షాడో షార్ట్కట్లు పంపబడవు. ఈ అభ్యర్థనల కోసం స్పెక్యులేటివ్ హెడ్జింగ్ నిలిపివేయబడింది కాబట్టి రిజర్వ్ ఖాతాలు ప్రాధాన్యత కలిగిన వాటిని రేస్ చేయలేవు. ఇతర కాంబో వ్యూహాలు ఈ సెట్టింగ్ని అర్థం చేసుకోవు. స్వయంచాలకంగా కాంబోను మార్చడం వలన, తర్వాత స్విచ్ బ్యాక్ కోసం సేవ్ చేయబడిన ప్రాధాన్యతలు ఉంచబడతాయి.

## నిజమైన Model Idతో సరిపోలే Combo పేర్లు

`name` ఒక bare model idకి సమానంగా ఉండే combo (ఉదా. `gpt-5.5` అనే పేరు గల combo) ఒక **ఉద్దేశపూర్వకమైన, మద్దతు ఉన్న నమూనా**, బగ్ కాదు: ఇది [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940)లో డాక్యుమెంట్ చేయబడిన, ప్రతి model idకి provider fallbackను అందించే విధానం. Bare-model-id resolution కంటే ముందు combo resolution తనిఖీ చేయబడుతుంది కాబట్టి (`src/sse/services/model.ts`లోని `getComboForModel()`), bare id `gpt-5.5` కోసం వచ్చిన అభ్యర్థన నేరుగా ఒకే providerకు వెళ్లకుండా, combo లక్ష్యాల ద్వారా (ఉదా. `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) route చేయబడుతుంది — ఇది [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) కోసం రూపొందించిన combo-before-rewrite ప్రాధాన్యతను తిరిగి ఉపయోగిస్తుంది మరియు `tests/unit/responses-combo-resolution-3227.test.ts`, `tests/unit/combo-name-codex-responses-rewrite.test.ts` ద్వారా regression పరీక్ష చేయబడుతుంది.

నిజమైన model idను shadow చేసే పేరుతో comboను సృష్టించడం లేదా దాని పేరు మార్చడం **ఎప్పటికీ తిరస్కరించబడదు** — అలా చేయడం ఈ డాక్యుమెంట్ చేసిన workflowను విచ్ఛిన్నం చేస్తుంది. బదులుగా (#8530), (కొత్త) పేరు నిజమైన model idతో ఘర్షణ పడినప్పుడు `POST /api/combos` మరియు `PUT /api/combos/[id]` responseకు అభ్యర్థనను నిరోధించని `warning` fieldను జోడిస్తాయి:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

Boot సమయంలో, `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) కూడా model idను shadow చేసే ఇప్పటికే ఉన్న ప్రతి comboను జాబితా చేస్తూ ఒక-లైన్ `[STARTUP]` హెచ్చరికను log చేస్తుంది. అందువల్ల ఉద్దేశపూర్వకంగా కాకుండా (#6940 ప్రకారం), పొరపాటున దీనిని ఎదుర్కొన్న operatorsకు ఒక సంకేతం లభిస్తుంది. గుర్తింపు helper `src/lib/combos/modelNameCollision.ts`లో ఉంటుంది.

## Client నుండి Custom Comboను పిలవడం

Persist చేసిన combos (Settings → Combos), client `model` fieldలో combo యొక్క **ఖచ్చితమైన పేరును** పంపినప్పుడు మాత్రమే ఉపయోగించబడతాయి — combo పేరుకు fuzzy లేదా partial matching ఉండదు, అలాగే `auto/` prefix కూడా ఉండదు. Resolution క్రమం (`src/sse/services/model.ts`లోని `getComboForModel()`):

1. ఖచ్చితమైన combo-name సరిపోలిక (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

సాధారణంగా ఎదురయ్యే రెండు సమస్యలు:

- **`auto` మీ combosను ఉపయోగించదు.** `auto`/`auto/*` తన స్వంత zero-config candidate poolను నిర్మిస్తుంది మరియు ఏదైనా comboకు అక్షరాలా `auto` అనే పేరు ఉంటే మాత్రమే persist చేసిన combosను పరిశీలిస్తుంది (ఇది సిఫార్సు చేయబడదు). Combo ద్వారా route చేయడానికి, దాని ఖచ్చితమైన పేరును పంపండి — `auto`ను కాదు.
- **`openrouter/auto` అనేది నిజమైన paid OpenRouter product** ("Auto Best Available"), OmniRoute alias కాదు. ఇది OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`)లోని ఏకైక static model entry మరియు దీనికి విడిగా billing చేయబడుతుంది. దీన్ని `auto` pools నుండి మినహాయించడానికి Settings → Routing → Hide paid modelsను ఉపయోగించండి.

ఇక్కడ డాక్యుమెంట్ చేసిన అసలు గందరగోళం గురించి తెలుసుకోవడానికి [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) మరియు [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) చూడండి.

## ఇది ఎలా పనిచేస్తుంది (నిల్వ చేయబడిన Auto-Combos)

Auto-Combo Engine ప్రతి అభ్యర్థనకు ఉత్తమ provider/modelను **16-కారకాల స్కోరింగ్ ఫంక్షన్**ను ఉపయోగించి డైనమిక్గా ఎంచుకుంటుంది (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`లో నిర్వచించబడింది). డిఫాల్ట్ weights మొత్తం `1.0`కి సమానం; అనుకూల weightsను `normalizeScoringWeights()` ద్వారా మళ్లీ సాధారణీకరిస్తారు. పదహారు కారకాలలో రెండు — `cacheAffinity` మరియు `resetWindowAffinity` — డిఫాల్ట్ weight `0`ను కలిగి ఉంటాయి; `reliability`కి `DEFAULT_WEIGHTS`లో `0`, generic packsలో `0.03`, `reliability-first`లో `0.04` ఉంటాయి; అలాగే packsలో `quality`కి `0.02` (`quality-first`లో `0.03`) ఉంటుంది: ప్రతి candidate కోసం ఇవన్నీ లెక్కించబడుతూనే ఉంటాయి, మరియు `cacheAffinity` స్కోర్కు వెలుపల prompt-cache deduplicationను నియంత్రిస్తుంది. అందువల్ల సున్నా-డిఫాల్ట్ కారకాలు డిఫాల్ట్గా ఓటు వేయవు, అయితే packs వాటిని ఉపయోగిస్తాయి.

> **చదవలేని కోటా (#15347).** ప్రొవైడర్కు కోటా ఫెచర్ ఉన్నప్పటికీ, అది చదవదగినదేమీ తిరిగి ఇవ్వనప్పుడు
> (ఫెచ్ విఫలమవడం, ఆధారాలు లేకపోవడం, మెసేజ్-మాత్రమే వినియోగం లేదా పార్స్ చేయగల
> `windows` ఏవీ లేని మరియు పరిమిత `percentUsed` విలువ లేని తప్పుగా రూపొందిన స్నాప్షాట్,
> ఇందులో `percentUsed: null` కూడా ఉంటుంది), అభ్యర్థి `quota` అక్షంపై `0` స్కోరు పొందుతుంది
> మరియు దాని తుది స్కోరు `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` (0.5, `autoStrategy.ts`)తో
> గుణించబడుతుంది; ఇది కనెక్షన్-స్థితి పెనాల్టీకి సమానమైన సాఫ్ట్-పెనాల్టీ విధానం. విఫలమైన వినియోగ
> రీడ్ టెలిమెట్రీకి సంబంధించిన ఆధారం, ప్రొవైడర్కు సంబంధించినది కాదు; అందువల్ల ఇది నిజమైన రీడింగ్
> ఉన్న ఏ అభ్యర్థికన్నా, 100% వినియోగం నిర్ధారించబడినదానికన్నా కూడా, కచ్చితంగా దిగువన ర్యాంక్ అవుతుంది,
> అయితే దీనిపై ఎప్పుడూ హార్డ్-బ్లాక్ విధించబడదు లేదా తొలగించబడదు. పరిమితి లేని ప్రొవైడర్
> `unlimited: true`ని నివేదించి పూర్తి కోటా స్కోరు పొందుతుంది; నమోదు చేయబడిన కోటా ఫెచర్ ఏదీ లేని
> ప్రొవైడర్కు టెలిమెట్రీ మూలం అసలు ఉండదు మరియు డిఫాల్ట్ `100`ను కొనసాగిస్తుంది.

**మొత్తం:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` అని `DEFAULT_WEIGHTS`లో ప్రకటించబడింది; స్కోరింగ్కు ముందు వినియోగదారు-కాన్ఫిగర్ చేసిన వెయిట్లు `normalizeScoringWeights()` ద్వారా ఒక పంపిణీగా మళ్లీ సాధారణీకరించబడతాయి.

## మోడ్ ప్యాక్లు

`open-sse/services/autoCombo/modePacks.ts`లో ముందే నిర్వచించిన 6 వెయిట్ ప్రొఫైల్లు ఉన్నాయి. ఎంపికను ఒక లక్ష్యం వైపు మొగ్గు చూపేలా చేయడానికి ప్రతి ప్యాక్ డిఫాల్ట్ వెయిట్లను పూర్తిగా భర్తీ చేస్తుంది. ప్రతి ప్యాక్ మొత్తం ఇప్పటికే `1.0` అవుతుంది (నాలుగు దశాంశ స్థానాలకు ముద్రించినప్పుడు `0.9999`), కాబట్టి ఒక ప్యాక్ సక్రియంగా ఉన్నప్పుడు `normalizeScoringWeights()` అర్థవంతంగా సరిచేయడానికి ఏమీ ఉండదు — రౌండింగ్ను పరిగణనలోకి తీసుకుంటే, క్రింద ఉన్న విలువలనే స్కోరర్ వర్తింపజేస్తుంది.

### `weighted` semantics

`weighted` అనేది **ప్రతి requestకు proportional random draw**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), equalizer కాదు:

- ప్రతి అభ్యర్థన `weight / totalWeight` సంభావ్యతతో **ఒక** దశను ఎంచుకుంటుంది; మిగిలిన దశలు
  బరువు అవరోహణ క్రమంలో ఆ అభ్యర్థనకు fallback chainగా అమర్చబడతాయి.
- ఒక దశ బరువు `0` (లేదా అందుబాటులో లేకపోవడం) కాగా, మరే ఇతర దశకైనా
  weight > 0 ఉంటే అది **ఎప్పటికీ ఎంచుకోబడదు** — ఎంచుకున్న దశ విఫలమైన తర్వాత మాత్రమే
  fallbackగా సేవలందించగలదు. **అన్ని** బరువులు 0 అయినప్పుడే ఎంపిక uniform అవుతుంది.
- అన్ని targetలు అందుబాటులో లేని దశలు — provider circuit breaker `OPEN`, connection
  cooldown, model lockout — draw జరగడానికి ముందే తొలగించబడతాయి
  (`open-sse/services/combo/targetResolution.ts`), కాబట్టి ఒకే ఆరోగ్యకరమైన దశ తాత్కాలికంగా
  ప్రతి అభ్యర్థనలోనూ గెలవగలదు.
- `stickyWeightedLimit` (combo config, default `1` = off) ఎంచుకున్న దశను మళ్లీ డ్రా చేయడానికి
  ముందు వరుసగా జరిగే అంత స్థాయి విజయాల వరకు స్థిరంగా ఉంచుతుంది.

కఠినమైన rotation కోసం `round-robin` ఉపయోగించండి; `weighted`లో సమాన బరువులు
గణాంకపరమైన — కఠినమైనది కాని — సమతుల్యతను ఇస్తాయి.

### Agentic pipeline మోడ్

కనీసం రెండు models ఉన్న `pipeline` combo, `config.agenticOrchestration.enabled` ద్వారా
planner/executor routingను ప్రారంభించవచ్చు. మొదటి target planning మరియు తుది సమాధానాలకు
బాధ్యత వహిస్తుంది; రెండవ target client-native tool callsను ఉత్పత్తి చేస్తుంది. OmniRoute
అభ్యర్థన protocol నుండి tool-result continuationsను గుర్తించి, మరో tool round అవసరమా అని
plannerను అడుగుతుంది; ఆపై executor లేదా plannerను client-facing final stepగా
డైనమిక్గా ఎంపిక చేస్తుంది.

ఐచ్ఛికమైన `config.agenticOrchestration.contextCompaction`, ప్రతి planner లేదా executor
dispatchకు ముందు వేరే payload budgetను వర్తింపజేస్తుంది. దీన్ని స్పష్టంగా ప్రారంభించండి:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

ఇవి operator ఎంచుకున్న serialized JSON character budgets; ఇవి token context windows లేదా
హామీ ఇవ్వబడిన upstream limits కావు. ఖచ్చితమైన model IDs defaultను override చేస్తాయి.
threshold కంటే ఎక్కువగా ఉన్నప్పుడు, compaction ఒకే రకమైన tool definitionsను తొలగిస్తుంది,
పరిమాణం అధికంగా ఉన్న tool evidenceను digestతో కుదిస్తుంది, అలాగే పాత complete history
groupsను target ratio వైపు తొలగిస్తుంది. ఇది system/developer instructions, తాజా user
request, చివరి tool roundలోని parallel calls/results, మరియు Gemini యొక్క ప్రారంభ routing
instructionను ఉంచుతుంది. Top-level instructions మరియు tool settings భద్రంగా ఉంచబడతాయి.
తొలగించిన historyను omission marker నమోదు చేస్తుంది; ఇది semantic summary కాదు, deterministic
trimming. పిన్ చేసిన context ఇప్పటికీ budgetను మించితే, modelను సంప్రదించకముందే request
413ను తిరిగి ఇస్తుంది. Compaction నిలిపివేయబడితే లేదా threshold కంటే తక్కువగా ఉంటే request
మార్పులేకుండా pass through అవుతుంది.

Tool-result continuationsపై, వరుసగా పూర్తయిన రెండు roundsలో మార్పులేని resultsతో అదే
tool calls పునరావృతమైతే, లేదా వరుసగా పూర్తయిన రెండు roundsలో స్పష్టంగా గుర్తించబడిన ప్రతి
result విఫలమైతే, OmniRoute executionను కూడా ఆపుతుంది. మారిన results పునరావృత callsను
అనుమతిస్తాయి (ఉదాహరణకు, polling). కొత్త user requestపై guard reset అవుతుంది, parallel
callsను ఒక roundగా సమూహపరుస్తుంది, అలాగే Anthropic, Chat Completions, Responses మరియు
Gemini historiesకు మద్దతు ఇస్తుంది. Planner కారణాన్ని స్వీకరిస్తుంది మరియు మరో tool round
అడిగినా తుది సమాధానానికి బాధ్యత వహిస్తుంది.

రెండవ target తర్వాతి అదనపు models executor backupsగా క్రమబద్ధీకరించబడతాయి. విఫలమైన
HTTP response లేదా transport exception తదుపరి executorకు మారుతుంది; అదే planner decision
మరియు native toolsతో పాటు ఆ executor యొక్క స్వంత step prompt మరియు resolved connection
తీసుకెళ్తుంది. మొదటి విజయవంతమైన response మార్పులేకుండా తిరిగి ఇవ్వబడుతుంది, SSE streaming
తో సహా; విజయవంతమైన stream ప్రారంభమైన తర్వాతి failuresను ఇక్కడ మళ్లీ ప్రయత్నించలేము.
అన్ని executors విఫలమైతే, చివరి failure తిరిగి ఇవ్వబడుతుంది. Client aborts dispatchను
ఆపుతాయి.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Executor ఒకే responseలో అనేక స్వతంత్ర callsను ఉత్పత్తి చేయవచ్చు. ఆధారపడిన callsను
తర్వాతి client tool-result turnsలో నిర్వహిస్తారు; ప్రతి resultను planner సమీక్షిస్తుంది.
`maxToolRounds` defaultగా `8` మరియు `1`–`32` పరిధిని అంగీకరిస్తుంది; పరిమితి చేరుకున్నాక,
అందుబాటులో ఉన్న ఉత్తమ తుది సమాధానాన్ని planner తప్పనిసరిగా ఉత్పత్తి చేయాలి. Internal
planner decisions buffer చేయబడతాయి, అయితే ఎంపికైన client-facing response అసలు streaming
preferenceను కాపాడుతుంది.

### `round-robin` sticky batch మరియు account expansion

Round-robin ఒక్క requestకు ఒక step చొప్పున కాకుండా batchలుగా పనిచేస్తుంది:

- `stickyRoundRobinLimit` (combo config, తర్వాత `comboStickyRoundRobinLimit`, తర్వాత
  `settings.stickyRoundRobinLimit`, default **3**) rotate చేయడానికి ముందు వరుసగా జరిగే
  అంత స్థాయి విజయాల వరకు అదే targetను ఉంచుతుంది. ఒక్క-request rotation కోసం combo
  overrideను `1`గా సెట్ చేయండి. Combo editor effective value మరియు అది ఏ layer నుండి
  వచ్చిందో చూపిస్తుంది.
- `connectionAwareExpansion` (combo config, తర్వాత settings, default **false**) rotationకు
  ముందు ప్రతి provider-level stepను per-account targetsగా విస్తరిస్తుంది. Group-B strategies
  (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp,
  fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion,
  pipeline, jev) ఇది on అయ్యే వరకు provider-level viewను ఉంచుతాయి. Combo editor
  inherit / on / off ఎంపికలను అందిస్తుంది; inherit global default (off)ను ఉపయోగిస్తుంది.
- Prompt-cache locality routing (`promptCacheAffinityEnabled`, default **true**) సరిపోలే
  cache keys ఒకే accountపై ఉండేలా pinned connectionsను మళ్లీ క్రమబద్ధీకరిస్తుంది.
  Pinned per-account stepsపై round-robin మరియు weighted rotation కంటే దీనికి ప్రాధాన్యత
  ఉంటుంది. కఠినమైన rotation అవసరమైతే Settings → Combo defaults కింద దీన్ని ఆపివేయండి.
  Per-combo override లేదు.

ఒక modelపై multi-account rotation కోసం, మూడు pinned `connectionId`sకు బదులుగా sticky
limit `1`తో **ఒక dynamic-account step** (ఖాళీ `connectionId`, మొత్తం pool)ను
ఉపయోగించడం మంచిది. RR counter ముందుకు సాగుతున్నప్పటికీ pinned steps మరియు affinity
ఒకే accountపై కేంద్రీకృతమవుతాయి.

## ఫ్యూజన్ వ్యూహం

`fusion` అనేది ఒకే లక్ష్యాన్ని ఎంచుకోని ఏకైక వ్యూహం. ఇది ప్రాంప్ట్ను
**ప్రతి ప్యానెల్ మోడల్కు సమాంతరంగా** పంపి, ఆపై కాన్ఫిగర్ చేయగల **జడ్జ్ మోడల్**
అన్ని ప్యానెల్ ప్రతిస్పందనల నుండి ఒకే తుది సమాధానాన్ని సంశ్లేషిస్తుంది. అప్స్ట్రీమ్ `decolua/9router`
(OpenRouter యొక్క Fusion డిజైన్) నుండి పోర్ట్ చేయబడింది; అమలు `open-sse/services/fusion.ts`లో ఉంది.

ఇది ఎలా పనిచేస్తుంది:

0. **టూల్-బేరింగ్ బైపాస్** — ఖాళీ కాని `tools` అరేను కలిగి, `tool_choice`
   స్పష్టంగా `"none"`గా సెట్ చేయబడని అభ్యర్థన ప్యానెల్ను పూర్తిగా దాటవేస్తుంది: అది
   ఒకే మోడల్కు (కాన్ఫిగర్ చేసిన జడ్జ్ లేదా `panel[0]`) నేరుగా రూట్ అవుతుంది, అలాగే
   `tools`/`tool_choice` ఎలాంటి మార్పు లేకుండా పంపబడతాయి. ప్యానెల్ సభ్యులకు టూల్ యాక్సెస్ ఉండదు,
   అలాగే జడ్జ్ యొక్క సంశ్లేషణ నిర్దేశం టూల్-కాల్ ఉత్పత్తిని నిరుత్సాహపరుస్తుంది, కాబట్టి
   ఏజెంటిక్/టూల్-కాలింగ్ క్లయింట్లు సంశ్లేషించిన గద్యానికి బదులుగా నిజమైన టూల్-కాల్ నిర్ణయాన్ని
   పొందుతాయి (#6771).
1. **ఫ్యాన్-అవుట్** (టూల్-బేరింగ్ కాని అభ్యర్థనలకు మాత్రమే) — ప్రాంప్ట్ అన్ని ప్యానెల్
   మోడల్లకు ఒకేసారి పంపబడుతుంది, టూల్లను తొలగించి నాన్-స్ట్రీమింగ్గా బలవంతంగా అమలు చేయబడుతుంది
   (సంశ్లేషించడానికి జడ్జ్కు పూర్తి గద్యం అవసరం).
2. **కోరం-గ్రేస్ సేకరణ** — `minPanel` సమాధానాలు అందిన వెంటనే, వెనుకబడిన వాటి కోసం
   స్వల్ప గ్రేస్ టైమర్ ప్రారంభమవుతుంది; ఆ తర్వాత సేకరించిన వాటితో ఫ్యూజన్ కొనసాగుతుంది.
   ఇది హార్డ్ టైమ్అవుట్ పరిమితికి లోబడి, అత్యంత నెమ్మదైన మోడల్ వల్ల వాస్తవ సమయంపై పడే
   ప్రభావాన్ని పరిమితం చేస్తుంది.
3. **జడ్జ్ సంశ్లేషణ** — ప్యానెల్ సమాధానాలు అజ్ఞాతీకరించబడతాయి (`Source 1`, `Source 2`, … —
   తద్వారా జడ్జ్ మోడల్ బ్రాండ్ను కాకుండా విషయసారాన్ని అంచనా వేస్తుంది) మరియు జడ్జ్కు అందించబడతాయి.
   అది ఏకాభిప్రాయం / వైరుధ్యాలు / పాక్షిక కవరేజ్ / ప్రత్యేక అంతర్దృష్టులు / గుర్తించని అంశాలను
   విశ్లేషించి, ఆపై **ఒకే** ప్రామాణిక సమాధానాన్ని రాస్తుంది. జడ్జ్ కాల్ క్లయింట్ యొక్క అసలు
   `stream` ఫ్లాగ్ + టూల్లను అలాగే ఉంచుతుంది, కాబట్టి స్ట్రీమింగ్ మరియు దిగువస్థాయి టూల్ వినియోగం
   ఇప్పటికీ పనిచేస్తాయి.
4. **సమర్థవంతమైన క్షీణత** — 0 ప్యానెల్ సమాధానాలు → `503`; కేవలం 1 సమాధానం మాత్రమే మిగిలితే →
   ఆ సమాధానం నేరుగా తిరిగి ఇవ్వబడుతుంది (ఫ్యూజ్ చేయడానికి ఏమీ ఉండదు); ఒకే మోడల్ ఉన్న ప్యానెల్
   నేరుగా సమాధానం ఇస్తుంది.

ఒక ప్యానెల్ సభ్యుడు మరొక కాంబోను సూచించే `combo-ref` దశగా
(`{kind: "combo-ref", comboName: "..."}`) కూడా ఉండవచ్చు — అది **ఒకే బ్లాక్-బాక్స్ ప్యానెల్ స్వరం**గా
పరిష్కరించబడుతుంది (సూచించిన కాంబోలోకి పూర్తి రికర్సివ్ డిస్పాచ్; ఆ కాంబో యొక్క స్వంత లక్ష్యాల
ఫ్యాన్-అవుట్ కాదు), ఇప్పటికే ప్రతి ఇతర combo-ref-ఉపయోగించే వ్యూహం వాడుతున్న అదే లోతు/చక్ర
రక్షణతో (#6764).

### కాన్ఫిగరేషన్

కాంబో యొక్క `config` బ్లాబ్పై కాన్ఫిగర్ చేయబడుతుంది (స్కీమా మైగ్రేషన్ లేదు — ఇది ఇప్పటికే ఉన్న
`combos` పట్టికను మళ్లీ ఉపయోగిస్తుంది):

| ఫీల్డ్                                   | రకం      | డిఫాల్ట్             | ఉద్దేశ్యం                                                                                       |
| :--------------------------------------- | :------- | :------------------- | :---------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | మొదటి ప్యానెల్ మోడల్ | తుది సమాధానాన్ని సంశ్లేషించే మోడల్                                                              |
| `config.fusionTuning.minPanel`           | `number` | `2`                  | గ్రేస్ టైమర్ ప్రారంభం కావడానికి ముందు అవసరమైన విజయవంతమైన సమాధానాలు (`[2, panelSize]`కు పరిమితం) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`               | కోరం చేరుకున్న తర్వాత వెనుకబడిన వాటి కోసం ఎంతసేపు వేచి ఉండాలి                                   |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`              | ఒక నిలిచిపోయిన మోడల్ అభ్యర్థనను ఆపకుండా నిరోధించే సంపూర్ణ గరిష్ఠ పరిమితి                        |

డిఫాల్ట్లు `FUSION_DEFAULTS`లో (`open-sse/services/fusion.ts`) ఉన్నాయి.

## వర్చువల్ ఆటో-కాంబో ఫ్యాక్టరీ

ఆటో కాంబో ఇంజిన్కు ముందుగా నిర్వచించిన కాంబోలు అవసరం లేదు. బదులుగా, `open-sse/services/autoCombo/virtualFactory.ts` అవసరమైనప్పుడే అభ్యర్థులను రూపొందిస్తుంది:

1. `getProviderConnections({ isActive: true })` (ప్రారంభించబడిన అన్ని కనెక్షన్లు)ను పొందుతుంది
2. చెల్లుబాటు అయ్యే క్రెడెన్షియల్స్ ఉన్న వాటిని ఫిల్టర్ చేస్తుంది (API కీ లేదా `hasUsableOAuthToken()` ద్వారా గడువు ముగియని OAuth టోకెన్)
3. మోడల్ లభ్యత + ధరల కోసం `getProviderRegistry()`తో పరస్పరం సరిపోల్చుతుంది
4. ప్రతి `(provider, model, connection)` ట్యూపుల్ కోసం, ఒక `VirtualAutoComboCandidate`ను రూపొందిస్తుంది
5. డిస్పాచ్ లక్ష్యంగా `connection.defaultModel`ను (లేదా రిజిస్ట్రీలోని మొదటి మోడల్ను) ఎంచుకుంటుంది
6. 16-ఫ్యాక్టర్ `scorePool()` మరియు వేరియంట్ వెయిట్ ప్యాక్ను ఉపయోగించి ప్రతి అభ్యర్థికి స్కోర్ ఇస్తుంది
7. `handleComboChat()` కోసం ఫలితంగా వచ్చిన ఇన్-మెమరీ `AutoComboConfig`ను అందిస్తుంది — దాన్ని DBలో ఎప్పుడూ నిల్వ చేయదు

దీనర్థం **`auto/*` ప్రారంభించబడిన కొత్త ప్రొవైడర్ను జోడించడం ద్వారా అభ్యర్థుల పూల్ స్వయంచాలకంగా విస్తరిస్తుంది** — మాన్యువల్గా కాంబోను సవరించాల్సిన అవసరం లేదు. ప్రతి అభ్యర్థనకు వర్చువల్ కాంబో మళ్లీ రూపొందించబడుతుంది, కాబట్టి కొత్తగా జోడించిన లేదా కొత్తగా ఆరోగ్యకరంగా మారిన కనెక్షన్లు వెంటనే వినియోగించబడతాయి.

## స్వీయ-పునరుద్ధరణ

- **తాత్కాలిక మినహాయింపు**: స్కోర్ < 0.2 → 5 నిమిషాల పాటు మినహాయించబడుతుంది (క్రమంగా పెరిగే బ్యాక్ఆఫ్, గరిష్ఠంగా 30 నిమిషాలు)
- **సర్క్యూట్ బ్రేకర్ అవగాహన**: OPEN → స్వయంచాలకంగా మినహాయించబడుతుంది; HALF_OPEN → ప్రోబ్ అభ్యర్థనలు
- **సంఘటన మోడ్**: >50% OPEN → అన్వేషణను నిలిపివేసి, స్థిరత్వాన్ని గరిష్ఠం చేస్తుంది
- **కూల్డౌన్ పునరుద్ధరణ**: మినహాయింపు తర్వాత, మొదటి అభ్యర్థన తగ్గించిన టైమ్అవుట్తో కూడిన "ప్రోబ్" అవుతుంది

## బ్యాండిట్ అన్వేషణ

అభ్యర్థనల్లో 5% (కాన్ఫిగర్ చేయదగినవి) అన్వేషణ కోసం యాదృచ్ఛిక ప్రొవైడర్లకు రూట్ చేయబడతాయి. సంఘటన మోడ్లో ఇది నిలిపివేయబడుతుంది.

## API

ఉంది** అంకితమైన `POST /api/combos/auto` ముగింపు స్థానం లేదు** — ఆటో-కాంబో రెండు విధాలుగా వినియోగించబడుతుంది:

1. **జీరో-కాన్ఫిగరేషన్ (సిఫార్సు చేయబడింది):** `model: "auto"` లేదా `model: "auto/<variant>"` తో ఏదైనా చాట్ పూర్తి అభ్యర్థనను పంపండి. వర్చువల్ ఫ్యాక్టరీ కాంబో పర్ రిక్వెస్ట్ — ని నిర్మిస్తుంది, పట్టుదల లేదు, API కాల్స్ అవసరం లేదు.

2. **`strategy: "auto"` తో నిరంతర కాంబో:** `POST /api/combos` ద్వారా సాధారణ కాంబోని సృష్టించండి మరియు `strategy: "auto"` ప్లస్ `config.auto.weights` / `config.auto.candidatePool` సెట్ చేయండి. అదే స్కోరింగ్ ఇంజిన్ ఉపయోగించబడుతుంది; కాంబో `combos` లో నిల్వ చేయబడుతుంది మరియు ID ద్వారా పునర్వినియోగపరచబడుతుంది.

ఆవిష్కరణ కోసం, `GET /api/combos/auto` ప్రతి రూపాంతరాన్ని దాని పరిష్కరించబడిన అభ్యర్థి పూల్తో పాటు `context_length` / `max_output_tokens` — అభ్యర్థి పూల్ విండోస్లో MAX జాబితా చేస్తుంది. క్లయింట్లు (ఉదా. ఓపెన్కోడ్ ప్లగ్ఇన్) తప్పనిసరిగా `0` కి బదులుగా ఈ విలువలను ప్రచారం చేయాలి : సున్నా సందర్భం ఓపెన్కోడ్ యొక్క స్వీయ-కంపాక్షన్ను పూర్తిగా నిలిపివేస్తుంది, గేట్వే చరిత్ర ప్రక్షాళన సందర్భాన్ని నాశనం చేసే వరకు సెషన్లను పెంచడానికి అనుమతిస్తుంది. MAX ప్రచారం చేయడం సురక్షితం ఎందుకంటే ఆటో-కాంబో కాంటెక్స్ట్ ప్రీ-ఫిల్టర్ పెద్ద-విండో అభ్యర్థులకు భారీ అభ్యర్థనలను రూట్ చేస్తుంది.

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
```

### ఆటో రౌటర్ వ్యూహాలు

పట్టుదలతో ఉన్న `strategy: "auto"` కాంబోలు `config.routerStrategy` (లేదా లెగసీ `config.auto.routerStrategy`)ని వీటిలో ఒకదానికి సెట్ చేయవచ్చు:

- `rules` — డిఫాల్ట్ వెయిటెడ్ స్కోరింగ్
- `score` — అత్యధిక కాన్ఫిగర్ చేయబడిన వెయిటెడ్ స్కోర్ను ఎంచుకుంటుంది. ఖచ్చితమైన సంబంధాలు కాన్ఫిగర్ చేయబడిన అభ్యర్థి క్రమాన్ని సంరక్షిస్తాయి; పూర్తి ర్యాంక్ పూల్ నుండి ఇప్పటికే ఉన్న `explorationRate` నమూనాలు.
- `cost` / `eco` — చౌకైన ఆరోగ్యకరమైన ప్రొవైడర్
- `latency` / `fast` — విశ్వసనీయత పెనాల్టీతో అత్యల్ప p95 జాప్యం
- `sla-aware` / `sla` — p95 జాప్యం, ఎర్రర్-రేట్ మరియు ఐచ్ఛిక ధర SLOs ని సంతృప్తిపరిచే అభ్యర్థులను ఇష్టపడుతుంది
- `lkgp` — మొదటగా తెలిసిన మంచి ప్రొవైడర్
- `nadir` — [నాదిర్](https://getnadir.com) నిర్ణయాన్ని అడగండి API పూల్లో ఏ మోడల్ ప్రాంప్ట్ కావాలి; ఆప్ట్-ఇన్, ఫెయిల్-ఓపెన్ `rules`
- `decision` — కాన్ఫిగర్ చేయబడిన డిసైడర్ని అడగండి (TypeSafe సిస్టమ్ వన్, మీ స్వంత నిర్ణయం URL, లేదా కాంబో యొక్క స్వంత మోడల్లలో ఒకటి) పూల్లోని ఏ మోడల్ అభ్యర్థనకు సరిపోతుంది; డిఫాల్ట్-ఆఫ్ `COMBO_DECISION_ROUTER_ENABLED` ఫ్లాగ్ వెనుక, ఫెయిల్-ఓపెన్ `rules`

### రూటర్ వ్యూహాలు వివరంగా

ఆటో-కాంబో ఇంజిన్ 7 ప్లగ్బుల్ను బహిర్గతం చేస్తుంది**RouterStrategy** మీరు `config.routerStrategy` (లేదా లెగసీ `config.auto.routerStrategy`) ద్వారా మార్చుకోగల అమలులు. ప్రతి వ్యూహం `RoutingContext` (పని రకం, tool/vision సూచనలు, టోకెన్ అంచనా, ఐచ్ఛిక SLA విధానం, ఐచ్ఛికంగా చివరిగా తెలిసిన-మంచి ప్రొవైడర్) ఇచ్చిన అభ్యర్థి పూల్ నుండి ఒక ప్రొవైడర్ను ఎంచుకుంటుంది.

#### 1. `rules` (డిఫాల్ట్) — 16-ఫాక్టర్ వెయిటెడ్ స్కోరింగ్

ఇప్పటికే ఉన్న స్కోరింగ్ ఇంజిన్ను చుట్టేస్తుంది. `OPEN` సర్క్యూట్-బ్రేకర్ అభ్యర్థులను ఫిల్టర్ చేస్తుంది, ఆపై `scorePool()` ప్రస్తుత టాస్క్ రకం మరియు `getTaskFitness()` తో రన్ చేస్తుంది, టాప్ స్కోరింగ్ ప్రొవైడర్ను ఎంచుకుంటుంది.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**ఎప్పుడు ఉపయోగించాలి** : డిఫాల్ట్. మీరు అన్ని సిగ్నల్లలో సమతుల్య ట్రేడ్-ఆఫ్ కావాలనుకున్నప్పుడు ఉపయోగించండి.

**మారుపేరు** : `rules` (అలియాస్ లేదు)

---

#### 2. `cost` / `eco` — చౌకైన ఆరోగ్యకరమైన ప్రొవైడర్

అభ్యర్థి పూల్ను `costPer1MTokens` (ఆరోహణ) ద్వారా క్రమబద్ధీకరిస్తుంది మరియు చౌకైనదాన్ని ఎంచుకుంటుంది. ముందుగా `OPEN` అభ్యర్థులను ఫిల్టర్ చేస్తుంది.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ఎప్పుడు ఉపయోగించాలి** : వ్యయ-సెన్సిటివ్ పనిభారం, బ్యాచ్ ప్రాసెసింగ్ లేదా నేపథ్య ఉద్యోగాలు.

**మారుపేర్లు** : `cost`, `eco`

---

#### 3. విశ్వసనీయత పెనాల్టీతో `latency` / `fast` — అత్యల్ప p95 జాప్యం

`p95LatencyMs + (errorRate * 1000)` ద్వారా క్రమబద్ధీకరించబడింది. ఎర్రర్-రేట్ పెనాల్టీ విశ్వసనీయత లేని ప్రొవైడర్లు వారి నామమాత్రపు జాప్యం తక్కువగా ఉన్నప్పటికీ వారు తక్కువ ర్యాంక్లో ఉండేలా నిర్ధారిస్తుంది.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ఎప్పుడు ఉపయోగించాలి** : నిజ-సమయ చాట్, స్వీయపూర్తి లేదా ఇంటరాక్టివ్ కోడింగ్ అసిస్టెంట్ల వంటి జాప్యం-సెన్సిటివ్ వర్క్లోడ్లు.

**మారుపేర్లు** : `latency`, `fast`

#### 4. `sla-aware` / `sla` — latency/error/cost SLO సమ్మతి

కాన్ఫిగర్ చేయబడిన SLO విధానాన్ని ఎంతవరకు సంతృప్తి పరుస్తుందనే దాని ద్వారా ప్రతి అభ్యర్థిని స్కోర్ చేస్తుంది:

| కారకం            | బరువు | ఫార్ములా                                                  |
| ---------------- | ----- | --------------------------------------------------------- |
| జాప్యం స్కోర్    | 35%   | `threshold / max(value, ε)`                               |
| ఎర్రర్ స్కోర్    | 35%   | `threshold / max(value, ε)`                               |
| ఆరోగ్య స్కోరు    | 15%   | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)         |
| ఖర్చు స్కోరు     | 10%   | `threshold / max(value, ε)` లేదా విలోమ సాధారణీకరించబడింది |
| స్థిరత్వం స్కోర్ | 5%    | విలోమ సాధారణీకరించిన జాప్యం stddev                        |

`hardConstraints: true` ఉన్నప్పుడు, అభ్యర్థులు ప్రధానంగా క్రమబద్ధీకరించబడతారు** ఉల్లంఘన స్కోరు** (అవి ఏ SLO ఎంత దూరం మించిపోయాయి), ఆపై మిశ్రమ స్కోర్ ద్వారా. కాకపోతే అది కాంపోజిట్ స్కోర్ మాత్రమే.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA క్షేత్రాలు** (కాంబో కాన్ఫిగరేషన్లో సెట్ చేయబడింది):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**ఎప్పుడు ఉపయోగించాలి** : కఠినమైన జాప్యం, ఎర్రర్-రేట్ లేదా ఖర్చు బడ్జెట్లతో ఉత్పత్తి పనిభారం.

**మారుపేర్లు** : `sla-aware`, `sla`

#### 5. `lkgp` — మొదటగా తెలిసిన మంచి ప్రొవైడర్

ప్రయత్నిస్తుంది** చివరిగా తెలిసిన మంచి ప్రొవైడర్** (సెట్ చేస్తే) ముందుగా, `rules` వ్యూహానికి తిరిగి వస్తుంది. సెషన్ స్టిక్కీనెస్ — కోసం ఉపయోగకరమైనది అదే ప్రొవైడర్ సంభాషణలో ఫాలో-అప్ అభ్యర్థనలను నిర్వహిస్తారు.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**ఎప్పుడు ఉపయోగించాలి** : అదే ప్రొవైడర్ ఫాలో-అప్ అభ్యర్థనలను నిర్వహించాలని మీరు కోరుకునే బహుళ-మలుపు సంభాషణలు (ఉదా, కాషింగ్, సందర్భం కొనసాగింపు లేదా ధరల స్థిరత్వం కోసం).

**మారుపేరు** : `lkgp` (అలియాస్ లేదు)

#### 6. నాడిర్ ద్వారా `nadir` — ప్రాంప్ట్-అవేర్ మోడల్ ఎంపిక

పైన ఉన్న ప్రతి వ్యూహం అభ్యర్థులను వారి స్వంత టెలిమెట్రీ ద్వారా ర్యాంక్ చేస్తుంది; వారిలో ఎవరూ అభ్యర్థనను చదవరు. `nadir` చివరి వినియోగదారు టర్న్తో పాటు పూల్ మోడల్ ఐడిలను [నాదిర్](https://getnadir.com) నిర్ణయం API (`POST /v1/bucket`)కి పంపుతుంది మరియు మోడల్కు మార్గాలను నాదిర్ ఆ మెను నుండి ఎంచుకుంటాడు (`simple` → చౌకైన సామర్థ్యం గల మోడల్, `complex` → సరిహద్దు ఒకటి). ఆ మోడల్ను అందించే కనెక్షన్ ఇప్పటికీ `rules` ద్వారా ఎంపిక చేయబడుతోంది, కాబట్టి కోటా, ఆరోగ్యం మరియు ఖర్చు ఏ ఖాతాను నిర్ణయిస్తాయి.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` మరియు `OMNIROUTE_NADIR_BASE_URL` రెండు స్ట్రింగ్లకు env ఫాల్బ్యాక్లు. `baseUrl` స్వీయ-హోస్ట్ చేసిన నాదిర్కు మాత్రమే అవసరం (ఒక వెనుకంజలో ఉన్న `/v1` సహించబడుతుంది). కీలెస్ కాల్లు నాదిర్ యొక్క అనామక శ్రేణిలో ల్యాండ్ అవుతాయి, ఇది ప్రతి IP కి రేటు-పరిమితం . ఒక కీతో ( [ఒకటి సృష్టించండి](https://app.getnadir.com/dashboard/api-keys) ), ప్రతి నిర్ణయం మీ నాడిర్ డ్యాష్బోర్డ్కు లాగ్ చేయబడుతుంది. పూర్తి సెటప్ మరియు ధృవీకరణ: [getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/).

పెట్టెలో ఏమి మిగిలి ఉంది: చివరి వినియోగదారు సందేశం యొక్క వచనం (మొదటి 16k అక్షరాలు), అభ్యర్థి మోడల్ IDలు మరియు `source: "omniroute"` ఛానెల్ ట్యాగ్. సిస్టమ్ ప్రాంప్ట్, చరిత్ర, సాధనాలు లేదా శీర్షికలు లేవు.

వైఫల్య ప్రవర్తన విఫలమైంది-ఓపెన్: గడువు ముగిసింది (డిఫాల్ట్ 2000 ms), non-2xx, చేరుకోలేని హోస్ట్, తప్పుగా రూపొందించబడిన ప్రతిస్పందన లేదా పూల్ వెలుపల ఎంపిక `rules` నిర్ణయానికి పరిష్కరిస్తుంది మరియు కారణం `NadirStrategy: fallback (…)`. విఫలమైన కాల్ తర్వాత వ్యూహం నెట్వర్క్ను 30 సెకన్ల పాటు దాటవేస్తుంది, కాబట్టి ఒక అభ్యర్థనకు ఒకటి కాకుండా 30 సెకన్లకు ఒక సమయం ముగిసింది. నాదిర్ వాస్తవానికి ఎంపిక చేసినప్పుడు మాత్రమే రూటింగ్ ఈవెంట్లు `strategy: "nadir"` నివేదిస్తాయి.

**ఎప్పుడు ఉపయోగించాలి** : మోడల్ శ్రేణులను (చిన్న, మధ్య మరియు సరిహద్దు మోడల్) విస్తరించి ఉన్న పూల్పై మిశ్రమ-కష్టం ట్రాఫిక్, ఇక్కడ ఎల్లప్పుడూ-సరిహద్దు మీరు తగ్గించాలనుకుంటున్న ధర.

**మారుపేరు** : `nadir` (అలియాస్ లేదు)

#### 7. `decision` — ప్లగ్గబుల్ డిసైడర్ మోడల్ను ఎంచుకుంటుంది

`decision` అడుగుతుంది a** నిర్ణయించువాడు** పూల్లోని ఏ మోడల్ అభ్యర్థనకు సరిపోతుందో, ఆ మోడల్కు పూల్ను కుదించి, కనెక్షన్ను ఎంచుకునేందుకు `rules` అనుమతిస్తుంది (కోటా, ఆరోగ్యం మరియు ఖర్చు ఇప్పటికీ ఖాతాను ఎంచుకోండి). రూటర్ నాబ్లు `config` ఎగువన (డాష్బోర్డ్ ఏమి వ్రాస్తుంది) లేదా `config.auto.routerStrategy` పక్కన `config.auto.decision` ఉన్నప్పుడు కాంబో డెసిషన్ బ్లాక్ — `config.decision` లో డిసైడర్ సెట్ చేయబడుతుంది:

| `decider`     | ఎవరు సమాధానం చెబుతారు                                                                                               | అవసరాలు                               |
| ------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| `systemone`   | TypeSafe సిస్టమ్ వన్ (`POST https://api.typesafe.ai/v1/systemone`), డిఫాల్ట్ మోడల్ `jev-latest`                     | ఒక `typesafe` కనెక్షన్ లేదా env కీ    |
| `http`        | `baseUrl` వద్ద మీ స్వంత డిసైడ్: `wire: "systemone"` (`{baseUrl}/v1/systemone`) లేదా `"openai-chat"` (చాట్ పూర్తిలు) | `baseUrl` + `model`; కీ ఐచ్ఛికం       |
| `combo-model` | మీ ప్రొవైడర్ మోడల్లలో ఒకటి, ఫ్యూజన్ జడ్జి వంటి ప్రక్రియలో పిలువబడుతుంది                                             | `model` `provider/model` (కాంబో లేదు) |

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "decision",
    "decision": {
      "decider": "http",
      "baseUrl": "https://decider.example.com",
      "wire": "openai-chat",
      "model": "qwen-small",
      "connectionId": "<stored connection id>",
      "timeoutMs": 2000,
      "minConfidence": 0.6,
      "descriptions": { "gpt-4o-mini": "Quick drafts and short answers" }
    }
  }
}
```

ఫీల్డ్లు (సేవ్ మరియు మళ్లీ అభ్యర్థన సమయంలో కఠినమైన స్కీమా ద్వారా ధృవీకరించబడతాయి):

- `decider` — `systemone`, `http` లేదా `combo-model`.
- `model` — TypeSafe మోడల్, మీ URL వద్ద డెసిషన్ మోడల్ లేదా కాంబో మోడల్ కాల్ (200 అక్షరాల వరకు) `provider/model`.
- `baseUrl` — `http` మాత్రమే: ఒక `http(s)` URL 500 అక్షరాల వరకు, ఆధారాలు, ప్రశ్న లేదా భాగం లేకుండా. ఈ OmniRoute (లూప్బ్యాక్ + `PORT`) వద్ద సూచించే URL తిరస్కరించబడింది.
- `wire` — `http` మాత్రమే: `systemone` (డిఫాల్ట్) లేదా `openai-chat`.
- `connectionId` — నిల్వ చేయబడిన కనెక్షన్, దీని కీ ఉపయోగించబడింది (కాలింగ్ API కీ అనుమతించబడిన కనెక్షన్ల లోపల మాత్రమే). అది లేకుండా, `systemone` ఒక `typesafe` కనెక్షన్ని చదువుతుంది మరియు ప్రతి నెట్వర్క్ డిసైడ్ `OMNIROUTE_DECISION_API_KEY` కి తిరిగి వస్తుంది. `apiKey` ఫీల్డ్ లేదు: ఒక కీ కాంబోలో ఎప్పుడూ నిల్వ చేయబడదు.
- `timeoutMs` — పూర్ణాంకం, 100–5000, డిఫాల్ట్ 2000.
- `minConfidence` — 0–1; తక్కువ-విశ్వాసం సమాధానం `rules` కి తిరిగి వస్తుంది (విశ్వాసం లేదని నివేదించే డిసైడర్ 0గా పరిగణించబడుతుంది).
- `descriptions` — వరకు 50 ఎంట్రీలు (కీ వరకు 300, టెక్స్ట్ గరిష్టంగా 1000 అక్షరాలు), మోడల్ id లేదా `provider/model` ద్వారా కీ చేయబడింది ; సెట్ చేయని ఎంట్రీలు ఉత్పత్తి చేయబడిన ధర-ర్యాంక్ వివరణను పొందుతాయి.

**జెండా.** `COMBO_DECISION_ROUTER_ENABLED` (డిఫాల్ట్ `false`) ప్రతి డిసైడ్ను గేట్ చేస్తుంది. ఇది ఆఫ్లో ఉన్నప్పుడు, `decision` కాంబో ఎటువంటి ఆధారాలను చదవదు, కాల్ చేయదు మరియు `rules` తో రూట్లు చేయదు; లాగ్ `fallback (disabled)` అని చెప్పింది. నిల్వ చేయబడిన కీ మాత్రమే దానిని ఎప్పటికీ ఆన్ చేయదు. నిర్ణయం బ్లాక్ లేని కాంబోలు అస్సలు ప్రభావితం కావు.

**పెట్టె నుండి ఏమి వదిలేస్తుంది.** చివరి వినియోగదారు సందేశం యొక్క వచనం (గరిష్టంగా 8000 అక్షరాలు; chat/Claude `messages` లేదా ప్రతిస్పందనలు `input`) మరియు వాటి వివరణలతో కూడిన మోడల్ ఐడిల మెను మాత్రమే. ఎప్పుడూ సిస్టమ్ ప్రాంప్ట్, ప్రతిస్పందనలు `instructions`, సాధనాలు, చరిత్ర, హెడర్లు లేదా ఖాతా డేటా. నెట్వర్క్ కాల్లు ప్రొవైడర్ అవుట్బౌండ్ గార్డ్ ద్వారా మళ్లీ ప్రయత్నించకుండా, మళ్లింపులు లేకుండా మరియు 64 KB ప్రతిస్పందన టోపీని కలిగి ఉంటాయి. `combo-model` కాల్ స్ట్రీమింగ్ కానిది, టూల్-ఫ్రీ, `temperature: 0`, 256-టోకెన్ బడ్జెట్తో; నిర్ణయం కాల్ లోపల ప్రారంభించిన నిర్ణయం తిరస్కరించబడుతుంది.

**వైఫల్య ప్రవర్తన** వైఫల్యం-ఓపెన్ `network_error` ఏదైనా వైఫల్యం `rules` నిర్ణయాన్ని పరిష్కరిస్తుంది మరియు కారణం `decision(<decider>): fallback (<reason>)`, `<reason>`, `disabled`, `not_configured`, `missing_credential`, `timeout`, `http_error`, `invalid_response`, `out_of_menu`, `refused`, `cooldown`, `recursion` `low_confidence` `single_option` `no_user_text` గడువు ముగిసిన తర్వాత, HTTP లోపం లేదా నెట్వర్క్ లోపం ముగింపు పాయింట్ 30 సెకన్ల పాటు దాటవేయబడుతుంది. విజయవంతమైన ఎంపిక `decision(<decider>): selected <model> from <n>; confidence <c> (<rules reason>)` ని చదువుతుంది. URL, కీ, ప్రాంప్ట్ లేదా అప్స్ట్రీమ్ బాడీ లాగ్ను చేరుకోలేదు.

రౌటర్ వ్యూహం `decision` అయినప్పుడు కాంబో బిల్డర్ ఈ ఫీల్డ్లను చూపుతుంది, ప్లేస్హోల్డర్లుగా రూపొందించబడిన వివరణలు మరియు a** పరీక్ష నిర్ణయం** సేవ్ చేయని సెట్టింగ్లతో ఒకసారి `POST /api/combos/decision-preview` కాల్ చేసే బటన్ (అదే ఫ్లాగ్).

**ఎప్పుడు ఉపయోగించాలి** : మీరు ఎంచుకున్న క్లాసిఫైయర్ ద్వారా అభ్యర్థనకు శ్రేణిని ఎంచుకోవాలని మీరు కోరుకునే మిశ్రమ-కష్టం ట్రాఫిక్, ప్రత్యేకంగా నాదిర్ ద్వారా కాదు.

**మారుపేరు** : `decision` (అలియాస్ లేదు)

### కస్టమ్ రూటర్ వ్యూహాలు

మీరు పబ్లిక్ API ద్వారా మీ స్వంత `RouterStrategy` అమలును నమోదు చేసుకోవచ్చు:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

అప్పుడు దీన్ని ఉపయోగించండి:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## టియర్లు Auto-Comboకు ఎలా సరిపోతాయి

16-ఫ్యాక్టర్ స్కోరింగ్ ఫంక్షన్ (`open-sse/services/autoCombo/scoring.ts`) టియర్
సభ్యత్వాన్ని రెండు సంకేతాలుగా పరిగణిస్తుంది: `tierPriority` (0.0476) మరియు `tierAffinity` (0.0476). పూర్తి
`DEFAULT_WEIGHTS` సెట్ కోసం పైన ఉన్న ప్రామాణిక [స్కోరింగ్ ఫ్యాక్టర్ పట్టిక](#how-it-works-persisted-auto-combos)ను చూడండి — ఒక్కో ప్యాక్కు సంబంధించిన ఓవర్రైడ్లు (ship-fast/cost-saver/quality-first/
offline-friendly) "ఒక్కో ప్యాక్కు వెయిట్ ప్రొఫైల్లు" పట్టికలో ఇవ్వబడ్డాయి.

టియర్ ఒక్కటే **Tier 1**ని ముందుగా ఉంచదు — Tier 1 లేటెన్సీ అధ్వాన్నంగా ఉంటే లేదా
ఖర్చు-వర్సెస్-నాణ్యత అనుకూలంగా లేకపోతే, Tier 2 గెలుస్తుంది. టియర్ క్రమాన్ని తప్పనిసరి చేయడానికి, కాంబో
స్ట్రాటజీ `priority`ని ఉపయోగించి, ప్రొవైడర్లను టియర్ ప్రకారం అమర్చండి.

Tier 1 (సబ్స్క్రిప్షన్)కు బలమైన ప్రాధాన్యత ఇవ్వడానికి, `tierPriority` వెయిట్ను పెంచండి:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

టియర్ నిర్వచనాలు మరియు ప్రొవైడర్ వర్గీకరణ కోసం [`docs/guides/TIERS.md`](../guides/TIERS.md)ను చూడండి.

### నిర్ణయాత్మక రూటింగ్-నిర్ణయ మ్యాట్రిక్స్ (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` నిజమైన కాంబో పైప్లైన్ ద్వారా, మాక్ చేసిన అప్స్ట్రీమ్తో, ఇది కవర్ చేసే పబ్లిక్ స్ట్రాటజీల రూటింగ్ **నిర్ణయాన్ని** ఎండ్-టు-ఎండ్గా నిరూపిస్తుంది.
కవరేజ్లో ఇవి ఉన్నాయి:

- మొత్తం 21 `ROUTING_STRATEGY_VALUES` స్ట్రాటజీలు (ఆర్డర్డ్, వెయిటెడ్, కాస్ట్, కాంటెక్స్ట్, ఫ్యూజన్, …).
- `quota-share` (అంతర్గత) ఎండ్-టు-ఎండ్: నిజమైన `selectQuotaShareTarget` సీమ్ (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`) ద్వారా DRR ఫెయిర్నెస్ + స్యాచురేషన్ డీప్రయారిటైజేషన్.
- ప్రతి టార్గెట్ సంఖ్య అంతటా `context-relay` యూనివర్సల్-హ్యాండ్ఆఫ్ కవరేజ్.

ఈ సూట్ CI (`test:integration` జాబ్)లో `--test-concurrency=1` మరియు
`--test-force-exit`తో నడుస్తుంది, కాబట్టి ఇది నిర్ణయాత్మకంగా ఉంటుంది మరియు లైవ్ క్రెడెన్షియల్స్ అవసరం లేదు.
