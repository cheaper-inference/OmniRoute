## అవలోకనం

కోటా షేరింగ్ ఇంజిన్, ఒకే కనెక్షన్ను పంచుకునే అనేక API కీల మధ్య ప్రొవైడర్కు చెందిన సమయ-ఆధారిత కోటాను (ఉదా. Codex
5-గంటల విండో, Kimi 1500 req/h) న్యాయంగా పంపిణీ చేస్తుంది.

**ఇది పరిష్కరించే సమస్య:** OmniRoute ఒకే అప్స్ట్రీమ్ ప్రొవైడర్ ఖాతాకు అనేక API కీలను ప్రాక్సీ చేస్తుంది.
భాగస్వామ్య లాజిక్ లేకుండా, కీ A నుంచి వచ్చే అభ్యర్థనల ఉద్ధృతి ఆ గంటకు సంబంధించిన
ప్రొవైడర్ కోటాను పూర్తిగా వినియోగించగలదు, దీంతో విండో రీసెట్ అయ్యే వరకు కీలు B మరియు C బ్లాక్ అవుతాయి.
ఇంజిన్ దీనిని ఈ విధంగా నివారిస్తుంది:

1. ప్రతి డైమెన్షన్కు (%, అభ్యర్థనలు, టోకెన్లు, $) ప్రతి కీ యొక్క రోలింగ్ వినియోగాన్ని ట్రాక్ చేయడం.
2. పని-సంరక్షణ న్యాయ-వాటా అల్గారిథమ్ను వర్తింపజేయడం: గ్లోబల్ పూల్ సంతృప్తం కానంత వరకు ఒక కీ నిష్క్రియంగా ఉన్న
   వాటాల నుంచి అరువు తీసుకోవచ్చు.
3. అభ్యర్థన అప్స్ట్రీమ్ ఎగ్జిక్యూటర్ను చేరుకోవడానికి ముందే హాట్ పాత్లో (`chatCore.ts`)
   ఫలితాన్ని అమలు చేయడం.

## అల్గోరిథం: ఫెయిర్-షేర్ వర్క్-కన్జర్వింగ్

`src/lib/quota/fairShare.ts` లో అమలు చేయబడింది.

### మోడ్లు

| పరిస్థితి                                  | మోడ్           | ప్రవర్తన                                                       |
| ------------------------------------------ | -------------- | -------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **ఉదారంగా**    | కీ గ్లోబల్ లిమిట్ మైనస్ వినియోగిత-మొత్తం వరకు రుణం తీసుకోవచ్చు |
| `globalUsedPercent >= saturationThreshold` | **స్ట్రిక్ట్** | వ్యక్తిగత న్యాయమైన వాటాను ఖచ్చితంగా అమలు చేయండి                |

డిఫాల్ట్ `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`).

ఈ రెండు మోడ్లు డిఫాల్ట్ బారో మోడ్లో పూల్ను వివరిస్తాయి, `saturation`. `consent` మోడ్లోని పూల్ ఎల్లప్పుడూ సంతృప్తత ఏమైనప్పటికీ కఠినమైన నియమాలను వర్తింపజేస్తుంది. [సమ్మతించిన రుణాన్ని చూడండి (ప్రతి పూల్ ఎంపిక)](#consented-lending-per-pool-opt-in).

### పర్-డైమెన్షన్ నిర్ణయం

పూల్లోని ప్రతి క్రియాశీల పరిమాణం కోసం, ఇంజిన్ గణిస్తుంది:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

`percent` కొలతలు కోసం, `consumed` బదులుగా అట్రిబ్యూషన్ పుస్తకం నుండి వస్తుంది ( [శాతం కొలతలు చూడండి: ప్రతి కీ అట్రిబ్యూషన్](#percent-dimensions-per-key-attribution) ).

అప్పుడు:

- **`policy = hard`** : `consumed > fairShareAllowed` మరియు మోడ్ కఠినమైన → అయితే** నిరోధించు** .
- **`policy = soft`** : `consumed > fairShareAllowed` మరియు మోడ్ కఠినమైన → అయితే** దండించు** (కాంబోలో ప్రాధాన్యతను తగ్గించండి; ఎప్పుడూ హార్డ్-బ్లాక్ చేయండి).
- **`policy = burst`** : సరసమైన వాటాతో సంబంధం లేకుండా గ్లోబల్ హెడ్రూమ్ ఉనికిలో ఉన్నప్పుడు అనుమతించండి.

### టోపీ సంపూర్ణ

కేటాయింపుపై`capValue` + `capUnit` అనేది మోడ్ లేదా పాలసీతో సంబంధం లేకుండా హార్డ్ సీలింగ్. `consumed >= capValue` ఎల్లప్పుడూ ఉన్న ఏదైనా పరిమాణం** బ్లాక్స్** అభ్యర్థన. `percent` క్యాప్ కోసం, `consumed` అనేది కీకి ఆపాదించబడిన భాగం మాత్రమే.

### బహుళ డైమెన్షన్ తనిఖీ

ఒకవేళ అభ్యర్థన బ్లాక్ చేయబడుతుంది** ఏదైనా** కొలనులోని పరిమాణం దానిని అడ్డుకుంటుంది. కొలతలు స్వతంత్రంగా ఉంటాయి — a 5h% అలసట వారపు% కోణాన్ని ప్రభావితం చేయదు.

### రుణం తీసుకుంటున్నారు

ఉదార మోడ్లో, కేటాయింపు తక్కువగా ఉన్న కీ ఇతర కీల యొక్క కేటాయించని షేర్ల నుండి మిగులును ఉపయోగించవచ్చు. సూత్రం:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

ఎక్కడ `consumedByOtherKeys = consumedTotal - consumedByThisKey`. టెటో గ్లోబల్ (ఆ డైమెన్షన్ కోసం పూల్ `limit` ) ఎల్లప్పుడూ హార్డ్ సీలింగ్.

### సమ్మతించిన రుణం (ప్రతి పూల్ ఎంపిక)

ప్రతి పూల్కు అరువు మోడ్ ఉంటుంది. `saturation` డిఫాల్ట్ మరియు పైన ఉన్న నియమాలను ఉంచుతుంది. `consent` మోడ్లో ఇతర కీలు రుణం ఇవ్వడానికి అంగీకరించిన సామర్థ్యంలో మాత్రమే `hard` కీ దాని వాటాను పాస్ చేస్తుంది. నిర్వాహకుడు ప్రతి పూల్ యొక్క మోడ్ను సెట్ చేస్తాడు. ప్రతి కీ హోల్డర్ [లెండింగ్ సమ్మతి](#lending-consent) ద్వారా వారి స్వంత సమ్మతిని సెట్ చేస్తారు.

సమ్మతి అనేది 0 నుండి 100 వరకు ఉన్న శాతం మరియు ఎపోచ్ మిల్లీసెకన్లలో ఐచ్ఛిక గడువు. గడువు భవిష్యత్తులో ఉన్నప్పుడు కీ దాని నిష్క్రియ వాటాలో ఆ శాతాన్ని ఇస్తుంది.

ఒక డైమెన్షన్ కోసం, `L` అనేది సమర్థవంతమైన పరిమితి: ప్లాన్ పరిమితి పూల్లోని ఖాతాల కంటే ఎక్కువ సార్లు ఉంటుంది. అభ్యర్థించే కీ కోసం గేట్ గణిస్తుంది:

```
share_k         = w_k / 100 × L
idle_k          = max(0, share_k − consumed_k)
lent            = Σ over the other keys of lend_k / 100 × idle_k
taken           = Σ over the other keys of max(0, consumed_k − share_k)
borrowAvailable = max(0, lent − taken)
```

`w_k` అనేది కీ యొక్క బరువు, లేదా 0 కంటే ఎక్కువ బరువు లేనప్పుడు ప్రతి కీకి `100 / n` `lend_k` అనేది కీ యొక్క క్రియాశీల శాతం, మరియు దాని గడువు ముగిసిన తర్వాత 0. అభ్యర్థించే కీ యొక్క స్వంత సమ్మతి ఎప్పటికీ లెక్కించబడదు. `hard` కీ దాని వినియోగం దాని వాటాతో పాటు `borrowAvailable` చేరుకున్న తర్వాత తిరస్కరించబడుతుంది.

ఏ కేటాయింపు క్లెయిమ్ చేయని కెపాసిటీ (బరువుల మొత్తం 100 మైనస్) రుణంగా ఇవ్వబడదు. రుణం ఇవ్వడానికి ఏ కీ అంగీకరించలేదు.

**ఉదాహరణ.** `L` 1000.

| కీ  | బరువు | షేర్ చేయండి | వినియోగించారు | అప్పు ఇస్తుంది |
| --- | ----- | ----------- | ------------- | -------------- |
| ఎ   | 50    | 500         | 530           | 0%             |
| బి  | 30    | 300         | 100           | 50%            |
| సి  | 0     | 0           | 60            | 0%             |

- B దాని నిష్క్రియ 200లో 50% రుణం ఇస్తుంది, ఇది 100. C ఇప్పటికే దాని వాటా కంటే 60ని తీసుకుంది. A 40 రుణం తీసుకోవచ్చు.
- A 530కి అందించబడుతుంది మరియు దాని వినియోగం 540కి చేరుకున్న తర్వాత తిరస్కరించబడింది.
- C ఏదైనా ఉపయోగించే ముందు, A దాని వాటా వద్ద లేదా కింద, C 100 రుణం తీసుకోవచ్చు.
- C ఏదైనా ఉపయోగించే ముందు, A 530తో, C 70ని అరువు తీసుకోవచ్చు.

**సున్నా బరువు.** బరువు 0 ఉన్న కీ 0 వాటాను కలిగి ఉంటుంది. దాని వినియోగం ఇతరులు ఇచ్చే దాని కంటే తక్కువగా ఉన్నప్పుడు మాత్రమే అందించబడుతుంది. ఎవరూ రుణం ఇవ్వనప్పుడు, దాని మొదటి అభ్యర్థన నుండి తిరస్కరించబడుతుంది.

**గడువు తేదీలు.** ఏ బ్యాక్గ్రౌండ్ టాస్క్ సమ్మతి గడువు ముగియదు. ప్రతి అభ్యర్థన గడువును దాని స్వంత సమయంతో పోలుస్తుంది మరియు ఆ సమయానికి సమానమైన గడువు ముగిసింది. పరిమిత సంఖ్య కాని లేదా `Date` కలిగి ఉన్న అతిపెద్ద తేదీని దాటిన నిల్వ చేయబడిన గడువు, ఆమోదించినట్లుగా గణించబడుతుంది.

**`soft` మరియు `burst`.** రుణాలు ఇవ్వడం వారికి పరిమితం కాదు. ఒక `soft` కీ దాని వాటాను దాటిన తర్వాత తీసివేయబడుతుంది. పూల్ గదిని కలిగి ఉన్నప్పుడు ఒక `burst` కీ పాస్ అవుతుంది. పూల్ మొత్తం దాని పరిమితిని చేరుకున్న తర్వాత పూల్ సీలింగ్ ఇప్పటికీ ప్రతి కీని నిరాకరిస్తుంది.

**అభ్యర్థన మార్గంలో ఖర్చు.** ఒక `saturation` పూల్ మునుపటి కంటే ఎక్కువ ఏమీ చదవదు. `consent` పూల్లో, లెక్కించదగిన డైమెన్షన్ ఇతర కీలను `hard` కీని దాని వాటా వద్ద లేదా అంతకంటే ఎక్కువ ఉండేలా రీడ్ చేస్తుంది. ఇది ఒకదానికొకటి సమాంతరంగా మరొక కీని చదివేలా చేస్తుంది. విఫలమైన రీడ్ ఆ కీ కోసం 0 వినియోగంగా పరిగణించబడుతుంది. ఒక `percent` పరిమాణం రీడ్ను జోడించదు, ఎందుకంటే అట్రిబ్యూషన్ పుస్తకం ప్రతి కీని కలిగి ఉంటుంది.

**పూల్ను సవరించడం.** సవరించిన కీల సమ్మతిని ఉంచుతుంది. ఇది కేటాయింపు సవరణలు, గ్రూప్-వైడ్ రీప్లేస్మెంట్లు మరియు `ensure` కాల్ల కోసం కలిగి ఉంటుంది. తీసివేయబడిన కీ దాని సమ్మతిని కోల్పోతుంది మరియు జోడించిన కీ 0 నుండి ప్రారంభమవుతుంది. నిర్వాహక మార్గాలు ప్రతి కీ యొక్క సమ్మతిని తిరిగి ఇవ్వవు మరియు దానిని ఎప్పుడూ వ్రాయవు. పూల్ను తిరిగి `saturation` కి మార్చడం వలన నిల్వ చేయబడిన ప్రతి సమ్మతిని ఉంచుతుంది, ఇది ఆ మోడ్లో ఎటువంటి ప్రభావం చూపదు. పూల్ని `consent` కి మార్చడం వలన గడువు ముగియని నిల్వ చేసిన సమ్మతిని మళ్లీ సక్రియం చేస్తుంది. కీ హోల్డర్ రెండు మోడ్లలో నిల్వ చేసిన సమ్మతిని క్లియర్ చేయవచ్చు.

**అప్గ్రేడ్ చేస్తోంది.** `lending_percent` మరియు `lending_until` నిలువు వరుసలు ఇప్పటికే ఉన్నట్లయితే, మైగ్రేషన్ `borrow_mode` మాత్రమే జోడిస్తుంది మరియు నిల్వ చేయబడిన శాతాలు అలాగే ఉంటాయి. ప్రతి పూల్ `saturation` మోడ్లో ప్రారంభమవుతుంది. పూల్ విజార్డ్లో ప్రతి పూల్కు `consent` ఆన్ చేయండి. నిల్వ చేయబడిన విలువల నుండి ఏమీ ఊహించబడలేదు.

**పరిమితులు.**

- రుణదాత దాని స్వంత వాటాను ఉపయోగించే ముందు దాని పైకప్పు వద్ద పూల్ను కనుగొనవచ్చు. ఇతరులు అరువు తీసుకున్న సామర్థ్యం పూల్ మొత్తంలో లెక్కించబడుతుంది.
- చెక్ అభ్యర్థనకు ముందు నడుస్తుంది మరియు ఏమీ నిల్వ చేయదు. ఏదైనా రికార్డ్ చేయబడే ముందు ఏకకాల అభ్యర్థనలు వినియోగాన్ని రీడ్ చేస్తాయి, కాబట్టి ఫ్లైట్లోని అభ్యర్థనలకు కట్టుబడి, రుణ సామర్థ్యాన్ని ఒకటి కంటే ఎక్కువసార్లు ఖర్చు చేయవచ్చు. `saturation` మోడ్ యొక్క షేర్ చెక్ అదే ప్రాపర్టీని కలిగి ఉంది.

## స్లైడింగ్ విండో కౌంటర్

`src/lib/quota/sqliteQuotaStore.ts` మరియు `redisQuotaStore.ts`లో అమలు చేయబడింది.

ప్రతి `(apiKeyId, dimensionKey)`కు రెండు బకెట్లు:

- `curr`: ప్రస్తుత బకెట్ (`floor(nowMs / windowMs)`)
- `prev`: మునుపటి బకెట్ (`curr - 1`)

ప్రభావవంతమైన రోలింగ్ విలువ:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**ఖచ్చితత్వం**: ~99% ఖచ్చితమైనది. బకెట్ల మధ్య సరిహద్దు వద్ద లోపం గరిష్ఠంగా విండో పరిమాణంలో 1% ఉంటుంది
(ఇది 2-బకెట్ అంచనా విధానానికి అంతర్గతమైనది).

### ఏకకాలికత

SQLite డ్రైవర్: ప్రతి `(apiKeyId | dimensionKey)` కీకి ఇన్-మెమరీ మ్యూటెక్స్,
రీడ్-మాడిఫై-రైట్ రేస్ను నివారిస్తుంది. ఈ నమూనా `src/sse/services/auth.ts`లోని యాంటీ-థండరింగ్-హర్డ్ విధానాన్ని అనుసరిస్తుంది.

Redis డ్రైవర్: అటామిక్ ఇంక్రిమెంట్ కోసం Lua EVAL స్క్రిప్ట్ — ఇది ఒకే Redis కమాండ్గా అమలవుతుంది.

## డ్రైవర్లు

### SQLite (డిఫాల్ట్, ఇన్స్టాలేషన్ అవసరం లేదు)

- టేబుల్: `quota_consumption` (మైగ్రేషన్ `073_quota_pools.sql` / `074_quota_consumption.sql` చూడండి).
- ఒకే ఇన్స్టాన్స్తో కూడిన డిప్లాయ్మెంట్లకు ఉత్తమమైనది.
- మొత్తం పర్సిస్టెన్స్ ఇప్పటికే ఉన్న OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`)లో ఉంటుంది.

### Redis (ఐచ్ఛికం, బహుళ-ఇన్స్టాన్స్)

- `ioredis` npm ప్యాకేజీ అవసరం.
- కౌంటర్లు Redisలో నిల్వ చేయబడతాయి; మెటాడేటా (పూల్లు/కేటాయింపులు) మాత్రం SQLiteలోనే ఉంటుంది.
- కౌంటర్లను పంచుకోవాల్సిన బహుళ-రెప్లికా డిప్లాయ్మెంట్లకు ఉత్తమమైనది.

### డ్రైవర్లను మార్చడం

సెట్టింగ్ల UI (`/dashboard/settings` → కోటా స్టోర్) ద్వారా లేదా env వేరియబుల్స్ ద్వారా:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

env కంటే DB సెట్టింగ్కు ప్రాధాన్యత ఉంటుంది. `driver=redis`గా ఉండి URL లేకపోయినా లేదా
`ioredis` ఇన్స్టాల్ చేయకపోయినా, ఫ్యాక్టరీ SQLiteకు తిరిగి మారి హెచ్చరికను లాగ్ చేస్తుంది.

డ్రైవర్ ఎంపిక క్రమం:

1. DB సెట్టింగ్ `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. డిఫాల్ట్: `sqlite`

## బహుళ డైమెన్షన్

ఒక కొలను బహుళ కొలతలు కలిగి ఉంటుంది. ప్రతి పరిమాణం స్వతంత్రంగా ఉంటుంది:

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // global pool ceiling for this dimension
}
```

**ఉదాహరణ: Codex ప్రణాళిక** (5h% + వారానికి%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

ఒక అభ్యర్థన తప్పనిసరిగా అనుమతించబడటానికి అన్ని పరిమాణాలను సంతృప్తి పరచాలి.

### శాతం కొలతలు: ప్రతి కీ అట్రిబ్యూషన్

ఒక శాతం ప్లాన్ ఖాతా మరియు ప్లాన్ విండోకు ఒక వినియోగ సంఖ్యను నివేదిస్తుంది. ప్రొవైడర్ ప్రతి API కీకి కౌంటర్ ఇవ్వదు.

కీల మధ్య ఆ సంఖ్యను విభజించడానికి, ప్రతి పూల్ ఖాతా మరియు ప్లాన్ విండోకు ఒక అట్రిబ్యూషన్ పుస్తకాన్ని ఉంచుతుంది. `src/lib/quota/percentLedger.ts` పుస్తకం యొక్క నియమాలను కలిగి ఉంది. `src/lib/quota/percentAttribution.ts` పుస్తకాన్ని అమలు చేసే సంఖ్యలుగా మారుస్తుంది. ఫలితం ప్రతి కీలక మార్గాల టోకెన్ల నుండి రూపొందించబడిన అంచనా.

#### పుస్తకాన్ని కదిలించే చదువులు

పుస్తకం అభ్యర్థించిన ప్లాన్ విండో కోసం ప్రొవైడర్ స్వంత బొమ్మపై మాత్రమే కదులుతుంది. ఈ కనెక్షన్లు ఒకదానిని నివేదిస్తాయి:

| ప్రొవైడర్                     | విండోలను ప్లాన్ చేయండి |
| ----------------------------- | ---------------------- |
| Claude, OAuth కనెక్షన్ ద్వారా | `5h`, `weekly`         |
| Codex                         | `5h`, `weekly`         |

ఇవి పఠనంగా పరిగణించబడవు:

- ప్రొవైడర్ క్లయింట్ పాతదిగా గుర్తించిన ప్రతిస్పందన
- ప్రొవైడర్ రిపోర్ట్ చేయని Claude విండో
- మరొక విండో యొక్క బొమ్మ, లేదా విండోస్ అంతటా చెత్త కేసు
- రేటు-పరిమితి హెడర్ ఫాల్బ్యాక్
- విఫలమైన పఠనం

API కీతో Claude తో సహా ఇతర ప్రొవైడర్ల వద్ద పుస్తకం లేదు. ఈ మార్పుకు ముందు వలె ప్రతి కీ వాటి శాతం కొలతలపై 0 ఛార్జ్ చేయబడుతుంది.

పఠనం సంతృప్త సిగ్నల్ యొక్క 30-సెకన్ల కాష్ను పంచుకుంటుంది. ప్రతిస్పందన హెడర్లలో బొమ్మను గమనించినప్పుడు లేదా వినియోగ ముగింపు స్థానం నుండి చదవబడినప్పుడు, ఆ సమయం తెలిసినప్పుడు Claude రీడింగ్ తేదీని నిర్ణయించబడుతుంది. ఇతర రీడింగ్లు ఆ కాష్ ఎంట్రీ ఎప్పుడు నిర్మించబడిందో తేదీగా నిర్ణయించబడ్డాయి.

#### పుస్తకం ఏమి ఉంచుతుంది

ప్రతి రికార్డ్ చేసిన అభ్యర్థన దాని టోకెన్లను ఒకసారి, ఒక్కో పూల్, ఖాతా మరియు కీకి కౌంటర్కు జోడిస్తుంది. ఒక కౌంటర్ మాత్రమే పెరుగుతుంది. పుస్తకం మూడు విషయాలను ఉంచుతుంది:

- బేస్లైన్: పుస్తకం తెరిచినప్పుడు లేదా విండో చివరిగా తిరిగినప్పుడు బొమ్మ
- చివరిగా వర్తించే బొమ్మ
- ప్రతి కీ, అదే సమయంలో దాని టోకెన్ కౌంటర్, దాని గుర్తుగా పిలువబడుతుంది

ఎన్ఫోర్స్మెంట్ లేదా వినియోగ మార్గం అట్రిబ్యూషన్ను గణించినప్పుడు పుస్తకం నవీకరించబడుతుంది. వ్రాతలు పునర్విమర్శ సంఖ్యపై సరిపోల్చండి మరియు సెట్ చేయబడతాయి. ఓడిపోయిన రచయిత మళ్లీ మళ్లీ చదవడానికి ప్రయత్నించాడు.

#### కీ యొక్క భాగం ఎలా గణించబడుతుంది

పుస్తకం చదివినప్పుడు ప్రతి కీ భాగం గణించబడుతుంది. టోకెన్లకు అనులోమానుపాతంలో కీల మధ్య బేస్లైన్ విభజించబడినప్పటి నుండి ఫిగర్ యొక్క పెరుగుదల ప్రతి ఒక్కటి దాని గుర్తు నుండి రూట్ చేయబడింది.

Together, ఆ టోకెన్లు ఒక్కో `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` టోకెన్లకు ఫిగర్లో గరిష్టంగా ఒక పాయింట్లో వివరిస్తాయి (డిఫాల్ట్ 1,000). వారు వివరించని వృద్ధి బాహ్యమైనది. బేస్లైన్ కూడా బాహ్యంగా ఉంటుంది.

ఉదాహరణకు, ఒక పుస్తకం 0 వద్ద తెరుచుకుంటుంది. కీ A తర్వాత 900,000 టోకెన్లను మరియు కీ B మార్గాలను 100,000 రూట్ చేస్తుంది. 60 సంఖ్య వద్ద, A యొక్క భాగం 54 పాయింట్లు మరియు B యొక్క భాగం 6.

దాని కీ గుర్తు కంటే దిగువన ఉన్న కౌంటర్ పునఃప్రారంభించబడింది మరియు పూర్తిగా లెక్కించబడుతుంది. కిటికీ మధ్యలో ఉన్న పూల్ను కలిపే కీ వంటి గుర్తు లేని కీ, దాని అన్ని టోకెన్లను లెక్కిస్తుంది. టోకెన్ల వెనుక ఉన్న ఫిగర్ తదుపరి పఠనంలో లోపం ఏర్పడుతుంది. ఇది పేరుకుపోదు.

`QUOTA_PERCENT_MIN_TOKENS_PER_POINT` ప్రతి అట్రిబ్యూషన్పై చదవబడుతుంది. కనీసం 1 యొక్క పరిమిత సంఖ్య లేని విలువ 1,000కి తిరిగి వస్తుంది.

#### పఠనం పుస్తకాన్ని ఎలా మారుస్తుంది

మొదటి సరిపోలిక నియమం వర్తిస్తుంది:

1. **ఇంకా పుస్తకం లేదు:** పఠనం పుస్తకాన్ని తెరుస్తుంది. దీని ఫిగర్ బేస్లైన్ మరియు ప్రతి కౌంటర్ మార్క్ చేయబడింది.
2. **పాత పఠనం:** చివరిగా వర్తింపజేసిన దానికి ముందు నాటి పఠనం విస్మరించబడుతుంది. రీసెట్ సమయం నిల్వ చేయబడిన దాని కంటే 30 నిమిషాల కంటే ముందుగా ఉన్న రీడింగ్ కూడా అలాగే ఉంటుంది.
3. **కొత్త ప్రొవైడర్ విండో:** నిల్వ చేసిన సమయం కంటే 30 నిమిషాల కంటే ఎక్కువ సమయం రీసెట్ చేస్తే పుస్తకం మారుతుంది. ఫిగర్ బేస్లైన్ అవుతుంది మరియు ప్రతి కౌంటర్ మళ్లీ గుర్తించబడుతుంది. కౌంటర్ లేని కీలు పుస్తకాన్ని వదిలివేస్తాయి.
4. **ముగిసిన విండో:** పఠనం యొక్క డేటా సమయం తర్వాత లేని నిల్వ రీసెట్ సమయం అంటే విండో ముగిసింది. పఠనం పుస్తకాన్ని మలుపు తిప్పుతుంది, దాని బొమ్మ ఏదైనా.
5. **అధిక సంఖ్య:** చివరి బొమ్మ మాత్రమే కదులుతుంది. బేస్లైన్ మరియు మార్కులు ఉంటాయి.
6. **అదే బొమ్మ:** ఫిగర్, బేస్లైన్ మరియు మార్కులు ఉంటాయి. పుస్తకం లేని రీసెట్ సమయం మాత్రమే వ్రాయబడింది.
7. **దిగువ బొమ్మ:** తక్కువ ఫిగర్ ఎప్పుడూ వర్తించదు. మూడు విషయాలు పట్టుకున్నప్పుడు మాత్రమే అది పుస్తకాన్ని మారుస్తుంది. ఇది చివరిగా అప్లై చేసిన రీడింగ్ కంటే కనీసం రెండు నిమిషాలు కొత్తది. కిటికీ అదే తెరిచి ఉందని ఏమీ చెప్పలేదు. ఇది ఒక పాయింట్ కంటే తక్కువ.

మూడు అంశాలు పట్టుకున్నప్పుడు విండో అదే ఓపెన్గా గణించబడుతుంది. రెండు రీసెట్ సమయాలు తెలుసు. అవి ఒకదానికొకటి 30 నిమిషాలలోపు ఉంటాయి. నిల్వ చేసినది ఇంకా చదవడానికి ముందుంది. ఆ కిటికీలోపల ఉన్న తక్కువ బొమ్మ ఏమీ మారదు.

రీసెట్ సమయం దానిని కలిగి ఉన్న రీడింగ్ డేటా సమయం కంటే ముందుగా ఉన్నప్పుడు మాత్రమే నిల్వ చేయబడుతుంది. ఒక అధిక సంఖ్య దాని రీడింగ్ యొక్క రీసెట్ సమయాన్ని భద్రపరుస్తుంది, అది ఉపయోగించదగినదిగా ఉంటుంది మరియు నిల్వ చేయబడిన దానిని లేకపోతే ఉంచుతుంది. పుస్తకానికి ఏదీ లేనప్పుడు మాత్రమే సమాన సంఖ్య దాని రీడింగ్ యొక్క రీసెట్ సమయాన్ని రికార్డ్ చేస్తుంది. ఇది వేరే ఏమీ మార్చదు. పుస్తకాన్ని తిరగని తక్కువ సంఖ్య రీసెట్ సమయాన్ని నమోదు చేయదు.

#### పుస్తకం ఉపయోగించినప్పుడు

చదివిన తర్వాత, పుస్తకం దాని నిల్వ రీసెట్ సమయం ప్రస్తుత సమయం తర్వాత కాదు తప్ప ఉపయోగించబడుతుంది. రీసెట్ చేయడానికి ముందు తీసుకున్న రీడింగ్, కాష్ నుండి అందించబడినది వంటిది, దాని తర్వాత గమనించినప్పుడు ఆ సందర్భం తలెత్తుతుంది.

ఉపయోగించదగిన పఠనం లేకుండా, నిల్వ చేయబడిన పుస్తకం ప్రస్తుత విండో పుస్తకంగా ఉన్నప్పుడు మాత్రమే ఉపయోగించబడుతుంది. ఇది రెండు సందర్భాలలో ఉంది:

- దాని రీసెట్ సమయం తెలుసు మరియు ఇంకా ముందుకు ఉంది
- దీనికి రీసెట్ సమయం లేదు మరియు దానిని మార్చిన చివరి పఠనం గరిష్టంగా 15 నిమిషాల పాతది

లేకపోతే పుస్తకం లేనప్పుడు ఏమీ ఆపాదించబడదు. నిల్వ చేసిన రీసెట్ సమయం దాటిన పుస్తకానికి ఎప్పుడూ ఛార్జీ విధించబడదు.

#### అమలు

శాతం పరిమాణంలో కీ యొక్క వినియోగం దాని ఆపాదించబడిన భాగం మరియు బాహ్య భాగం యొక్క వాటా. బాహ్య భాగం మొదట కెపాసిటీ నో కేటాయింపు క్లెయిమ్లను ఉపయోగిస్తుంది (బరువుల మొత్తం 100 మైనస్). అదనపు బరువు మాత్రమే కీల మధ్య పంచుకోబడుతుంది.

ఆ వినియోగాన్ని కీ యొక్క సరసమైన వాటాతో ఏ ఇతర డైమెన్షన్తోనూ పోల్చారు. సంతృప్త సిగ్నల్ `QUOTA_SATURATION_THRESHOLD` (డిఫాల్ట్ 0.5)కి చేరుకున్నప్పుడు కఠినమైన మోడ్ ఇప్పటికీ ప్రారంభమవుతుంది. ప్రతి సంఖ్య ప్రభావవంతమైన పరిమితితో స్కేల్ చేయబడుతుంది: ఒక్కో ఖాతా పరిమితి పూల్లోని ఖాతాల సంఖ్యకు రెట్లు ఎక్కువ.

`capUnit: "percent"` తో ఒక సంపూర్ణ టోపీ కీకి ఆపాదించబడిన భాగాన్ని మాత్రమే గణిస్తుంది, అదే విధంగా స్కేల్ చేయబడింది. ప్రతి ఖాతా పరిమితిని 100 మరియు k ఖాతాలను తీసుకోండి. సర్వింగ్ ఖాతా యొక్క ఫిగర్లోని కీ భాగం N/k పాయింట్లకు చేరుకున్నప్పుడు N యొక్క టోపీని చేరుకుంటారు. ప్రతి ఖాతా దాని స్వంత పుస్తకంతో తనిఖీ చేయబడుతుంది. ఉదాహరణకు, రెండు ఖాతాలతో, ఒక ఖాతా యొక్క ఫిగర్లో 5 పాయింట్ల వద్ద 10 పరిమితిని చేరుకుంటారు.

స్టోర్ని చదవలేనప్పుడు, ఏదీ ఆపాదించబడదు మరియు ప్రతి కీ ఆ పరిమాణంపై 0 ఛార్జ్ చేయబడుతుంది. పుస్తకం రాయడం విఫలమైనప్పుడు, ఆ ఆపాదింపు పుస్తకాన్ని చదివినట్లుగా ఉపయోగిస్తుంది. విఫలమైన టోకెన్ రైట్ రిక్వెస్ట్ టోకెన్లను పుస్తకం నుండి వదిలివేస్తుంది. ఈ వైఫల్యాలు ఏవీ అభ్యర్థనను నిరోధించవు.

`consent` పూల్లో, లెండింగ్ ఫార్ములా పైన వివరించిన విధంగా శాతం పరిమాణంలో ప్రతి కీ వినియోగాన్ని ఉపయోగిస్తుంది. మరొక కీ అప్పుగా ఇచ్చినప్పుడు, పుస్తకం ఒకసారి చదివి ప్రతి కీకి ఆపాదించబడుతుంది. ఉపయోగించదగిన పుస్తకం లేకుండా ప్రతి కీకి 0 ఛార్జ్ చేయబడుతుంది. బరువు ఉన్న కీ తర్వాత పాస్ అవుతుంది మరియు మరొక కీ రుణం ఇచ్చినప్పుడు మాత్రమే బరువు 0 ఉన్న కీ పాస్ అవుతుంది.

#### వినియోగ మార్గం

`GET /api/quota/pools/{id}/usage` అదే ఫంక్షన్ ద్వారా అదే సంఖ్యలను నివేదిస్తుంది. ఒక శాతం పరిమాణం `accounts` లో ఒక్కో పూల్ కనెక్షన్కి ఒక ఎంట్రీని కలిగి ఉంటుంది. దాని ఉన్నత-స్థాయి `consumedTotal` మరియు `perKey` మొదటి ఎంట్రీని ప్రతిబింబిస్తాయి.

మార్గం ప్రస్తుత పఠనానికి కూడా వర్తిస్తుంది, కాబట్టి ఇది అభ్యర్థన చేసినట్లుగా పుస్తకాన్ని ముందుకు తీసుకెళ్లగలదు. ఉపయోగించదగిన రీడింగ్ లేనప్పుడు లేదా తక్కువ ఫిగర్ వర్తించనప్పుడు `internal + external` `consumedTotal` నుండి భిన్నంగా ఉంటుంది.

#### నిల్వ మరియు నిలుపుదల

రెండు కోటా దుకాణాలు పుస్తకాన్ని ఉంచుతాయి. SQLite లో, స్వయంచాలక డేటాబేస్ క్లీనప్, ప్రారంభించబడినప్పుడు, 60 రోజుల వరకు నవీకరించబడని అడ్డు వరుసలను తొలగిస్తుంది. Redis లో, పూల్ కనెక్షన్ యొక్క పుస్తకాలు మరియు కౌంటర్లు ఒక కీని పంచుకుంటాయి. దాని చివరి టోకెన్ వ్రాయడం లేదా పుస్తకాన్ని మార్చిన 60 రోజుల తర్వాత గడువు ముగుస్తుంది. మారని పుస్తకం తిరిగి వ్రాయబడదు, కాబట్టి కటాఫ్ పొడవైన ప్లాన్ విండో పైన సెట్ చేయబడింది. మాన్యువల్ యూసేజ్-హిస్టరీ రీసెట్ కూడా SQLite లో పుస్తకాలను క్లియర్ చేస్తుంది (పరిమితులు చూడండి).

#### పరిమితులు

- అప్పటి నుండి రూట్ చేయబడిన ప్రతి కీ టోకెన్ల ద్వారా బేస్లైన్ విభజించబడినప్పటి నుండి ఖాతా సంఖ్య యొక్క మొత్తం పెరుగుదల. ఆ ఎదుగుదల ఎప్పుడు జరిగిందనేది పట్టింపు లేదు.
- కాబట్టి OmniRoute వెలుపల చేసిన వినియోగానికి వాటి టోకెన్లు అనుమతించే వరకు కీలకు ఛార్జ్ చేయబడుతుంది. పుస్తకం ఇప్పటికే తెరిచి ఉన్నప్పుడు, విండో యొక్క కీ యొక్క మొదటి అభ్యర్థనకు ముందు చేసిన వినియోగాన్ని కలిగి ఉంటుంది.
- ఉదాహరణకు, బయటి ఉపయోగం ఖాతా 60 పాయింట్లను పెంచుతుంది, అయితే కీలక మార్గాలు లేవు. ఒక కీ అప్పుడు 30,000 టోకెన్లను రూట్ చేస్తుంది మరియు ఫిగర్ 60.6కి చేరుకుంటుంది.
- పుస్తకాన్ని ఉపయోగించే ముందు తెరిచి ఉంటే, కీ భాగం 30 పాయింట్లు. ఇది బరువు 25 యొక్క నాలుగు కీలతో 7.65 బాహ్య వినియోగాన్ని కూడా కలిగి ఉంటుంది.
- ఆ తర్వాత పుస్తకం తెరిస్తే, 60 పాయింట్లు బేస్లైన్గా ఉంటాయి. కీ యొక్క భాగం 0.6 పాయింట్లు మరియు ఇది 15 బాహ్య వినియోగాన్ని కలిగి ఉంటుంది.
- వినియోగ మార్గానికి అభ్యర్థన లేదా సందర్శన పుస్తకాన్ని తెరుస్తుంది. కాబట్టి అటువంటి వినియోగం బేస్లైన్గా పరిగణించబడుతుందా అనేది పుస్తకం ఎప్పుడు తెరవబడిందనే దానిపై ఆధారపడి ఉంటుంది.
- డిఫాల్ట్ ఫ్లోర్తో, 60,000 టోకెన్లను రూట్ చేసే కీ, బయటి ఉపయోగం ఖాతా 60 పాయింట్లను పెంచుతుంది, మొత్తం 60ని దాని స్వంత భాగంగా పొందుతుంది.
- 50,000 వద్ద నేలతో, దాని స్వంత భాగం 1.2 పాయింట్లు. ఇతర 58.8 బాహ్యంగా ఉంటాయి మరియు ఏదైనా బాహ్య వినియోగం వలె బరువుతో ఛార్జ్ చేయబడతాయి.
- మీ ప్లాన్లో ఒక పాయింట్ ధరకు దగ్గరగా `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` సెట్ చేయండి. వెలుపలి ఉపయోగం పూల్ వెలుపలి కీల నుండి ఒకే ఖాతాలో ట్రాఫిక్ను కలిగి ఉంటుంది.
- ప్రతి మోడ్లో ఒక శాతం క్యాప్ వర్తిస్తుంది. ఖాతా సంతృప్త థ్రెషోల్డ్ కంటే చాలా తక్కువగా ఉన్నప్పుడు క్యాప్డ్ కీని తిరస్కరించవచ్చు.
- విండోలో ముందుగా 10 మరియు 12 పాయింట్ల బాహ్య వినియోగం యొక్క టోపీని తీసుకోండి. 20,000 టోకెన్లను రూట్ చేసే కీ 12.4% ఖాతాలో తిరస్కరించబడుతుంది.
- విభజన అనేది టోకెన్ వాల్యూమ్ ద్వారా అంచనా వేయబడింది. అభ్యర్థన దాని ప్రాంప్ట్ టోకెన్లతో పాటు దాని పూర్తి టోకెన్లుగా పరిగణించబడుతుంది. కాష్ తగ్గింపులు మరియు మోడల్ ధరలు ఆ గణనను మార్చవు.
- స్థితి 200తో ముగియని అభ్యర్థన టోకెన్లను నమోదు చేయదు. క్లయింట్ డిస్కనెక్ట్ చేసే స్ట్రీమ్ మరియు వినియోగం వినియోగించిన తర్వాత అప్స్ట్రీమ్ లోపం ఉదాహరణలు.
- టోకెన్లను రికార్డ్ చేసిన కీలకు, వాటి టోకెన్లు అనుమతించే వరకు అటువంటి అభ్యర్థన కారణంగా వినియోగానికి ఛార్జ్ చేయబడుతుంది. మిగిలినది బాహ్యమైనది. అది వెనక్కి కదలదు. టోకెన్ వినియోగాన్ని నివేదించని ప్రతిస్పందన టోకెన్లను నమోదు చేయదు.
- ప్రోగ్రెస్లో ఉన్న అభ్యర్థన యొక్క ఉపయోగం మొత్తం అభ్యర్థన కోసం మరొక క్రియాశీల కీ యొక్క భాగంలో చూపబడుతుంది. అభ్యర్థన స్థితి 200తో ముగిసినప్పుడు మాత్రమే ఇది వెనుకకు కదులుతుంది.
- పుస్తకం తెరిచినప్పుడు ఖాతాలో ఇప్పటికే ఉన్న వినియోగం బాహ్యంగా పరిగణించబడుతుంది. ఇది అప్గ్రేడ్, కొత్త పూల్ మరియు కొత్త ఖాతాను కవర్ చేస్తుంది. కొత్త విండోలో దాని మొదటి పఠనానికి ముందు ఉపయోగించడం బాహ్యంగా కూడా లెక్కించబడుతుంది.
- ప్రతి కీ ఆ వినియోగంలో దాని బరువు వాటాతో ప్రారంభమవుతుంది, కెపాసిటీ తర్వాత ఎటువంటి కేటాయింపు క్లెయిమ్ చేయదు. ఒక ఖాతా 85% మరియు ఐదు కీల బరువు 20తో, ప్రతి ఒక్కటి దాని 20లో 17 ఉపయోగించి ప్రారంభమవుతుంది.
- అనేక ఖాతాలతో కూడిన పూల్లో, సర్వింగ్ ఖాతా యొక్క ఫిగర్ సారాంశ బడ్జెట్కు వర్తించబడుతుంది. ఇది పుస్తకం ప్రకారం మారదు.
- ప్రొవైడర్ తెరిచి ఉన్నట్లు నివేదించిన విండో లోపల తక్కువ ఫిగర్ వర్తించబడదు. 30 నిమిషాల కంటే ఎక్కువ సమయం వెనక్కి వెళ్లే రీసెట్ సమయం పాత రీడింగ్గా పరిగణించబడుతుంది.
- రెండు సందర్భాల్లో, నిల్వ చేయబడిన రీసెట్ సమయం గడిచే వరకు పుస్తకం దాని స్థితిని ఉంచుతుంది. ఆ తర్వాత, చదివిన తర్వాత పుస్తకానికి ఛార్జీ విధించబడదు.
- నివారణ అనేది మాన్యువల్ యూసేజ్-హిస్టరీ రీసెట్ (`POST /api/settings/purge-usage-history`). ఇది SQLite డేటాబేస్లోని అట్రిబ్యూషన్ పుస్తకాలు మరియు వాటి టోకెన్ కౌంటర్లను క్లియర్ చేస్తుంది.
- `all` కాలం ప్రతి పుస్తకం మరియు కౌంటర్ను క్లియర్ చేస్తుంది. తక్కువ వ్యవధిలో మొదట దానిలో వ్రాయని పుస్తకాలను క్లియర్ చేస్తుంది. ఇది దానిలో వ్రాయబడని కౌంటర్లను క్లియర్ చేస్తుంది, కానీ పుస్తకం మిగిలి లేని పూల్ కనెక్షన్ కోసం మాత్రమే. ఉంచబడిన పుస్తకం ఇప్పటికీ ప్రతి కీని దాని కౌంటర్కి వ్యతిరేకంగా గుర్తు చేస్తుంది.
- బొమ్మ కదలని పుస్తకం తిరిగి వ్రాయబడదు, కాబట్టి తక్కువ వ్యవధిలో ప్రస్తుత విండో పుస్తకాన్ని కూడా క్లియర్ చేయవచ్చు. తదుపరి పఠనం ప్రస్తుత బొమ్మ వద్ద తాజా పుస్తకాన్ని తెరుస్తుంది.
- రీసెట్ Redis కోటా స్టోర్ను తాకదు. అక్కడ పుస్తకం దాని విండోతో ముగుస్తుంది లేదా చివరిగా వ్రాసిన 60 రోజుల తర్వాత గడువు ముగుస్తుంది.
- ప్రొవైడర్ రీసెట్ సమయాన్ని పంపనప్పుడు, రెండు రీడింగ్ల మధ్య పాత ఫిగర్ను రీసెట్ చేసి రీఫిల్ చేసే విండో ఎక్కువ ఫిగర్గా కనిపిస్తుంది. పుస్తకం పాత బేస్లైన్ మరియు మార్కులను ఉంచుతుంది.
- రీడింగ్లు స్థానిక గడియారం ద్వారా తేదీ చేయబడ్డాయి. ఇది ప్రొవైడర్ కంటే ముందు నడుస్తున్నప్పుడు లేదా మూలాధారం రీసెట్ సమయాన్ని కొంచెం ముందుగానే నివేదించినప్పుడు, పుస్తకం ఆ వ్యత్యాసాన్ని ముందుగానే గుర్తించగలదు.
- ఆ తక్కువ వ్యవధిలో వృద్ధి దానిలో రూట్ చేయబడిన టోకెన్ల ద్వారా విభజించబడింది. తదుపరి విండో యొక్క మొదటి పఠనం దాన్ని సరిచేస్తుంది. మారిన పుస్తకానికి రీసెట్ సమయం లేనప్పుడు, ఆ దిద్దుబాటుకు చివరిగా వర్తింపజేసిన పఠనం కంటే కనీసం రెండు నిమిషాలు తక్కువ ఫిగర్ అవసరం.
- Redis స్టోర్ తేదీ రీడింగ్లను వారి స్వంత గడియారాలతో పంచుకునే సందర్భాలు, కాబట్టి ఆ గడియారాలను సమకాలీకరించండి. గడియారం వెనుక నడిచే సందర్భం యొక్క రీడింగ్లు పాతవిగా కనిపిస్తాయి మరియు విస్మరించబడతాయి.
- నిల్వ చేసిన రీసెట్ సమయం తర్వాత ఉపయోగించదగిన రీడింగ్ ఏదీ రానప్పుడు, రీడింగ్ రిటర్న్ అయ్యే వరకు ఒక్కో కీ పర్సెంట్ షేర్లు మరియు పర్సెంట్ క్యాప్లు అమలు చేయబడవు. రీసెట్ సమయం లేకుండా, ఇది పుస్తకాన్ని మార్చిన చివరి పఠనం తర్వాత 15 నిమిషాల తర్వాత ప్రారంభమవుతుంది.
- Redis స్టోర్లో, 60 రోజుల పాటు నిష్క్రియంగా ఉన్న పుస్తకం రైటర్ చెక్ మరియు దాని రైట్ మధ్య గడువు ముగుస్తుంది. ఇది చెల్లుబాటు అయ్యే స్థితి అయిన 1 పైన ఉన్న పునర్విమర్శలో మళ్లీ సృష్టించబడుతుంది.

## పైప్లైన్ ఇంటిగ్రేషన్

### PRE హుక్ (`open-sse/handlers/chatCore.ts`)

అప్స్ట్రీమ్ ఎగ్జిక్యూటర్ ముందు, ప్రామాణీకరణ మరియు విధాన తనిఖీల తర్వాత నడుస్తుంది:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() per dimension
      → fairShare.decideFairShare()
      → if block → return 429 (buildErrorBody, Hard Rule #12)
      → if allow + deprioritize → set quotaSoftPenalty=true on candidate
  → executor.execute()
```

**ఫెయిల్-ఓపెన్** : `enforceQuotaShare` విసిరితే, అభ్యర్థన `pino.warn` లాగ్తో అనుమతించబడుతుంది. ఇది మొత్తం ట్రాఫిక్ను నిరోధించకుండా కోటా-ఇంజిన్ బగ్ను నిరోధిస్తుంది.

**సామర్థ్యం తిరిగి వచ్చినప్పుడు.** కీ షేర్ వద్ద లేదా పూల్ సీలింగ్ వద్ద తిరస్కరణ రెండు వాక్యాలలో ఒకదానితో ముగుస్తుంది, రెండు అరువు మోడ్లలో:

- `percent` విండో: `. The <window> window resets at <time>.` ప్రొవైడర్ నివేదికలను రీసెట్ చేసే సమయం.
- గణించదగిన యూనిట్: `. Enough <window> usage is expected to clear by <time>.` కీ వేరే ఏమీ పంపకపోతే, స్లయిడింగ్ విండో నుండి సమయం పైభాగంలో ఉంటుంది.

`<time>` అనేది UTC లో ISO 8601 తక్షణం. తిరస్కరణ తర్వాత `Retry-After` కలిగి ఉంటుంది : ఆ తక్షణం వరకు మొత్తం సెకన్లు, ప్లస్ వన్. ఎక్కువసేపు వేచి ఉన్న క్లయింట్ తక్షణం తర్వాత గరిష్టంగా ఒక సెకను మళ్లీ ప్రయత్నిస్తుంది. తక్షణం తెలియనప్పుడు, తిరస్కరణ వాక్యం లేదా శీర్షికను కలిగి ఉండదు. ఒక సంపూర్ణ టోపీ తిరస్కరణ ఏదీ కలిగి ఉండదు. పబ్లిక్ కోడ్ `quota_share_blocked` ఉంటుంది.

షేర్ తిరస్కరణ భాగస్వామ్య కనెక్షన్ను తాకదు. ఇది కూల్డౌన్, మోడల్ లాక్ మరియు ప్రొవైడర్ బ్రేకర్ వైఫల్యాన్ని సెట్ చేయదు మరియు పూల్ యొక్క ఇతర కీలు అందిస్తూనే ఉంటాయి. కాంబో యొక్క ప్రతి లక్ష్యం దాని వాటా కోసం కీని తిరస్కరించినప్పుడు, కాంబో వేచి ఉండకుండా 429కి సమాధానం ఇస్తుంది. దీని సమాధానం `Retry-After` గా సూచనను కలిగి ఉంటుంది. ఎంబెడ్డింగ్ల మార్గం దాని తిరస్కరణను అదే వాక్యంతో ముగిస్తుంది మరియు `Retry-After` పంపదు.

### POST హుక్ (రికార్డ్ వినియోగం)

విజయవంతమైన ప్రతిస్పందన తర్వాత:

```
executor returns success
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() per dimension
      → fail-open: errors logged as pino.warn, never propagated to client
```

**డ్రిఫ్ట్ నోట్** : `consume` పోస్ట్-రెస్పాన్స్లో విఫలమైతే, రోలింగ్ కౌంటర్ అండర్ కౌంట్ అవుతుంది. ప్రొవైడర్ నుండి సంతృప్త సిగ్నల్ (ఉదా `anthropic-ratelimit-unified-5h-utilization`) తదుపరి అభ్యర్థనపై ప్రపంచ అంచనాను సరిచేస్తుంది.

### కాంబో సాఫ్ట్ పెనాల్టీ (`open-sse/services/combo.ts`)

ఎప్పుడు `decision.deprioritize === true`:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // default 0.7
}
```

పెనాల్టీ అన్ని ఇతర స్కోరింగ్ కారకాల తర్వాత వర్తించబడుతుంది. ఇది హార్డ్-బ్లాక్ చేయకుండా సంతృప్త కీని ఎంచుకునే ఆటో-కాంబో సంభావ్యతను తగ్గిస్తుంది.

లెండింగ్ బ్యాడ్జ్ శాతాన్ని చూపుతుంది మరియు సెట్ చేసినప్పుడు, జోన్ పేరుతో ఉన్న గడువును UTC లో చూపుతుంది. ఇది వినియోగ స్నాప్షాట్ సమయంలో గడువును నిర్ధారిస్తుంది. గడువు ముగిసిన లేదా చదవలేని గడువు `lending expired` గా చూపబడుతుంది.

పేజీ హుక్స్:

- `usePools` — ప్రతి 30 సెకన్లకు `GET /api/quota/pools` పొందుతుంది.
- `usePoolUsage` — డిమాండ్పై `GET /api/quota/pools/[id]/usage` ని పొందుతుంది.
- లెగసీ LS డేటాను తరలించడానికి`useLocalStoragePoolMigration` — మౌంట్పై ఒకసారి నడుస్తుంది.

పూల్ విజార్డ్ యొక్క కీస్ స్టెప్లో `Show usage by member to key holders` బాక్స్ ఉంది. ఇది పూల్ యొక్క `memberBreakdown` ఎంపికను సెట్ చేస్తుంది ( [సభ్యుల వినియోగం](#member-usage) చూడండి). దాని క్రింద, ఒక కీ ఏమి ఉపయోగించాలో తెలిసిన ఎవరైనా ఆ కీకి బార్ను సరిపోల్చగలరని విజర్డ్ హెచ్చరించాడు. టిక్ చేసిన పెట్టెతో, స్టెప్ మూడు కంటే తక్కువ లేదా 20 కంటే ఎక్కువ కీలను జాబితా చేసినప్పుడు, బార్లు దాచబడి ఉంటాయి. ఇది స్టెప్లోని కీలను లెక్కిస్తుంది మరియు వాటిలో ఏది అభ్యర్థనలు చేయగలదో చెప్పలేదు.

### `/dashboard/costs/quota-share/plans` — ప్రొవైడర్ ప్లాన్ కాన్ఫిగర్

- `ProviderPlanConfigClient.tsx`: ప్రొవైడర్ను ఎంచుకోవడానికి డ్రాప్డౌన్, పరిష్కరించబడిన ప్లాన్ను వీక్షించండి (కేటలాగ్ లేదా మాన్యువల్ ఓవర్రైడ్ నుండి స్వయంచాలకంగా), మరియు కొలతలు సవరించండి.

## స్వీయ-సేవ కోటా API (ఆప్ట్-ఇన్)

`GET /api/v1/me/quota/{provider}` ( `/v1/me/quota/{provider}` లో కూడా అందించబడుతుంది) ఒక API కీ హోల్డర్ను వారి స్వంత కీతో, ఎంత షేర్డ్ సబ్స్క్రిప్షన్ వారిది మరియు వాటిని ఏది బ్లాక్ చేస్తుందో చదవడానికి అనుమతిస్తుంది. మార్గం `src/server/selfService/quotaHandler.ts` పై ఒక సన్నని షెల్; వీక్షణ `src/lib/quota/selfView.ts` ద్వారా నిర్మించబడింది మరియు దాని ప్రతిస్పందన ఒప్పందం `src/shared/schemas/selfQuota.ts` (`SelfQuotaView` లో `docs/openapi.yaml`).

### ప్రారంభించడం మరియు ప్రామాణీకరణ

- ఫీచర్ ఫ్లాగ్ `QUOTA_SELF_PANEL`, డిఫాల్ట్ `false`. ఇది ఆఫ్లో ఉన్నప్పుడు, మార్గాన్ని చేరుకునే అభ్యర్థన 404ని పొందుతుంది. `REQUIRE_API_KEY=true` తో, క్లయింట్ API విధానం ఫ్లాగ్ ఏదైనప్పటికీ, రూట్ రన్ అయ్యే ముందు 401తో తప్పిపోయిన లేదా చెల్లని కీని నిరాకరిస్తుంది. కీ లేని అభ్యర్థన, సైన్ ఇన్ చేసిన డాష్బోర్డ్ సెషన్ ఆ విధానాన్ని ఆమోదించింది మరియు మార్గం యొక్క స్వంత సమాధానాన్ని పొందుతుంది. ఫ్లాగ్ ప్రతి ఇతర ఫ్లాగ్ లాగా పరిష్కరిస్తుంది (డ్యాష్బోర్డ్ లేదా REST ఓవర్రైడ్, ఆపై అదే పేరుతో ఉన్న ఎన్విరాన్మెంట్ వేరియబుల్); [`FEATURE_FLAGS.md`](../reference/FEATURE_FLAGS.md) చూడండి.
- ప్రతి పూల్ యొక్క ప్రదర్శన పేరు మరియు ప్రతి షెడ్యూల్ యొక్క లేబుల్ అడ్మినిస్ట్రేటర్ వ్రాసిన విధంగానే పూల్ కీ హోల్డర్లకు తిరిగి ఇవ్వబడతాయి. ఫ్లాగ్ను ఆన్ చేసే ముందు, ఆ కీ హోల్డర్లు చదవడానికి అవి సరిపోతాయో లేదో తనిఖీ చేయండి.
- కీ హెడర్ల నుండి మాత్రమే చదవబడుతుంది: `Authorization: Bearer <key>` లేదా `x-api-key: <key>`. రెండింటినీ పంపినప్పుడు, ధృవీకరించే మొదటిది ఉపయోగించబడుతుంది. ప్రశ్న స్ట్రింగ్లోని కీ లేదా కుక్కీ విస్మరించబడింది. సర్వర్ యొక్క పర్యావరణ కీ తిరస్కరించబడింది (401).
- కీకి `self:usage` స్కోప్ అవసరం (403 అది లేకుండా).
- ప్రొవైడర్ విభాగం ట్రిమ్ చేయబడింది, లోయర్ కేస్ చేయబడింది మరియు `^[a-z0-9][a-z0-9._-]{0,63}$` వ్యతిరేకంగా తనిఖీ చేయబడుతుంది (400 లేకపోతే), ఆపై ప్రొవైడర్ రిజిస్ట్రీ ద్వారా పరిష్కరించబడుతుంది, కాబట్టి `cc` వంటి మారుపేరు `claude` పూల్లను చదువుతుంది. `claude` మరియు `anthropic` ఒకే పూల్లను చదివాయి.

### ప్రతి విజిబిలిటీ ఏమి చూపిస్తుంది

| దృశ్యమానత   | అవసరం                                                                                   | ఫీల్డ్స్                                                                                                                                                                                                                                        |
| ----------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| సొంత వాటా   | `self:usage`                                                                            | `pools[]` (రిఫరెన్స్, పేరు, ప్రొవైడర్, పాలసీ, బరువు, క్యాప్), `yourShare` తో `dimensions[].yourShare`, `accounts[]` ( `attributed` మరియు `external` లేని `percent` విండోలో), `blocks`, `availableModels`, `expiresAt`, `apiBaseUrl`             |
| ఖాతా స్థాయి | `self:usage` + `self:account-quota`, మరియు కీ యొక్క `sharedQuotaProviders` లో ప్రొవైడర్ | `dimensions[].total`, `accounts[].dimensions[].account` మరియు `accounts[].modelWindows`, `percent` విండో యొక్క `yourShare` పై `attributed` మరియు `external` మరియు సభ్యుల వినియోగంతో పూల్పై `members` ( [సభ్యుల వినియోగం](#member-usage) చూడండి) |

- `sharedQuotaProviders` అనేది పర్-కీ సెట్టింగ్ (`PUT /api/keys/[id]/self-service`): `null`, డిఫాల్ట్, అంటే కీ చేరే ప్రతి ప్రొవైడర్; `[]` అంటే ఏదీ కాదు. ప్రతి పూల్ యొక్క `accountVisible` దానికి ఏ దృశ్యమానత వర్తించబడిందో చెబుతుంది.
- ఖాతా బార్లు మరియు మోడల్ విండోలు కీ ఉపయోగించగల కనెక్షన్ల కోసం మాత్రమే చూపబడతాయి. కీ అనుమతించబడిన కనెక్షన్ల జాబితాను కలిగి ఉన్నప్పుడు, దాని వెలుపల ఉన్న ఖాతా దాని `Account N` ఎంట్రీని `account` లేదా `modelWindows` లేకుండా ఉంచుతుంది. ఖాళీ జాబితా అంటే `/v1/me/status` కొరకు పరిమితి లేదు. పూల్ మొత్తం (`dimensions[].total`) ఆ జాబితాపై ఆధారపడి ఉండదు.
- `self:usage` తో మాత్రమే చూపబడిన రెండు బొమ్మలు ఇతర కీల వినియోగం నుండి వచ్చాయి. షెడ్యూల్ బడ్జెట్ యొక్క `exhausted` ఆ షెడ్యూల్లోని ప్రతి కీ వినియోగాన్ని ప్రతిబింబిస్తుంది. బరువులు అన్నీ సున్నా ఉన్న పూల్లో, కీ యొక్క `weight` `100 / number of members`. రెండూ కీకి అమలు చేసేవి.
- ఒక పూల్ `ref` ద్వారా మాత్రమే గుర్తించబడుతుంది, ఇది కాలింగ్ కీకి కట్టుబడి ఉండే అపారదర్శక విలువ. దాని ప్రదర్శన పేరు (`name`) నిర్వాహకుడు వ్రాసినట్లుగా చేర్చబడింది. సర్వర్ యొక్క API-కీ రహస్యం (`API_KEY_SECRET`)తో కీ మరియు పూల్ నుండి `ref` తీసుకోబడింది. క్లయింట్లు దానిని కొనసాగించకూడదు: ఆ రహస్యాన్ని తిప్పితే అది మారుతుంది.
- ఖాతాలు పూల్ క్రమంలో `Account 1`, `Account 2`, …గా జాబితా చేయబడ్డాయి. పూల్ ఐడి, కనెక్షన్ ఐడి, ఖాతా ఇ-మెయిల్ లేదా ఖాతా పేరు తిరిగి ఇవ్వబడలేదు మరియు ప్రతిస్పందన కాంట్రాక్ట్ స్కీమా ద్వారా వెళుతుంది, ఇది దాని వెలుపల ఏదైనా ఫీల్డ్ను తగ్గిస్తుంది.
- లెక్కించదగిన యూనిట్లు (`requests`, `tokens`, `usd`) కోటా గేట్ అమలు చేసే పూల్ బకెట్గా నివేదించబడ్డాయి: `limit` = ప్లాన్ పూల్లోని × ఖాతాల పరిమితి, `fairShare` = బరువు / 100 × `limit` (సమానంగా విభజించబడింది) ప్రతి బరువులో కౌంటర్ కీ = (సమాన విభజన `consumed` కోటా స్టోర్, `consumed` `remaining` = `fairShare` −, ఫ్లోర్డ్ 0.
- `blocks.schedules` కీ యొక్క షెడ్యూల్ విండోలను జాబితా చేస్తుంది (`open`/`closed`, `blackout` లేదా `outside-window`, `retryAfterSeconds`, రిజర్వ్ అంతస్తులు మరియు విండో యొక్క బడ్జెట్ ఖర్చు చేయబడిందా); `blocks.modelCaps` వినియోగంతో దాని ప్రతి మోడల్ గంట క్యాప్లను జాబితా చేస్తుంది.
- ప్రొవైడర్ యొక్క ప్రతి పూల్ వెలుపల ఒక కీ `pools: []` తో 200 పొందుతుంది; `availableModels` ( `/v1/models` లో కీ చూసే `qtSd/` idలు), `expiresAt` మరియు `apiBaseUrl` ఇప్పటికీ నిండి ఉన్నాయి.
- `apiBaseUrl` అనేది `OMNIROUTE_PUBLIC_API_BASE_URL`, తర్వాత `OMNIROUTE_PUBLIC_BASE_URL`, else `null`. ఇది ఎప్పుడూ అభ్యర్థన యొక్క స్వంత మూలం కాదు.

| `percent_attribution_unavailable` | `percent` విండోలో కీ యొక్క స్వంత వాటా: ఆ ఖాతా మరియు విండో కోసం ఇంకా అట్రిబ్యూషన్ పుస్తకం లేదు లేదా పుస్తకం కీని జాబితా చేయలేదు. |
| `percent_window_ended`            | `percent` విండోలో కీ యొక్క స్వంత వాటా: పుస్తకం ముగిసిన ప్లాన్ విండోకు చెందినది.                                                 |
| `account_not_used_by_key`         | `percent` విండోలో కీ యొక్క స్వంత వాటా: ఖాతా యొక్క కనెక్షన్ కీ అనుమతించబడిన కనెక్షన్ల వెలుపల ఉంది. దాని పుస్తకం చదవలేదు.         |
| `window_not_reported`             | ప్రొవైడర్-పరిమితుల కాష్లో ఆ ప్లాన్ విండో కోసం రీడింగ్ లేదు.                                                                     |
| `connection_lookup_failed`        | ఖాతా కనెక్షన్ చదవడం సాధ్యం కాలేదు.                                                                                              |
| `not_supported`                   | ఖాతా ప్రొవైడర్ కోసంOmniRoute వినియోగ పరిమితులను చదవలేదు.                                                                        |
| `fetch_failed`                    | కాష్ చేసిన రీడింగ్ ఏదీ ఉపయోగించబడదు మరియు ప్రొవైడర్ పరిమితుల రిఫ్రెష్ విఫలమైంది.                                                |
| `not_available`                   | రీడింగ్ ఎటువంటి వినియోగ విండోలను కలిగి ఉండదు లేదా ఖాతాకు చదవడం లేదు.                                                            |

కోటా స్టోర్ని చదవలేనప్పుడు, `blocks` యొక్క స్టోర్-బ్యాక్డ్ ఫీల్డ్లు (షెడ్యూల్ బడ్జెట్ యొక్క `exhausted`, మోడల్ క్యాప్ యొక్క `consumed` మరియు `reached`) అలాగే `null` ఉంటాయి.

### రుణ సమ్మతి

`PATCH /api/v1/me/quota/{provider}` ఒక పూల్ కోసం కాలింగ్ కీ యొక్క స్వంత సమ్మతిని రికార్డ్ చేస్తుంది. ఇది `GET` యొక్క ఫ్లాగ్, హెడర్లు మరియు ప్రొవైడర్ నియమాలను ఉపయోగిస్తుంది. `self:usage` స్కోప్ దీన్ని వ్రాయడానికి అధికారం ఇస్తుంది, అయితే దీని పేరు చదవడానికి మాత్రమే చదవబడుతుంది.

```json
{
  "pool": "qpr_0123456789abcdef0123456789abcdef",
  "lendingPercent": 30,
  "lendingUntil": 1893456000000
}
```

- `pool` అనేది ఆ పూల్ కోసం `GET` తిరిగి ఇచ్చే `ref`.
- `lendingPercent` అనేది 0 నుండి 100 వరకు ఉన్న పూర్ణాంకం. 0 విలువ సమ్మతిని మరియు దాని గడువును క్లియర్ చేస్తుంది. `lendingPercent` 0 ఉన్న శరీరం ఏ రీతిలోనైనా ఆమోదించబడుతుంది.
- `lendingUntil` ఐచ్ఛికం: ఎపోచ్ మిల్లీసెకన్లు, లేదా గడువు లేకుండా `null`. ఇది తప్పనిసరిగా భవిష్యత్తులో ఉండాలి మరియు గరిష్టంగా 8640000000000000. 100000000000 కంటే తక్కువ విలువ సెకన్లుగా చదవబడుతుంది మరియు తిరస్కరించబడుతుంది.
- ఏదైనా ఇతర ఫీల్డ్ నిరాకరించబడింది. 4096 బైట్ల కంటే ఎక్కువ పొడవు ఉన్న శరీరం తిరస్కరించబడింది. రీడ్ ఆ పరిమాణంలో ఆగిపోతుంది, కాబట్టి పొడవాటి శరీరం ఎప్పుడూ పూర్తిగా పట్టుకోబడదు.

తనిఖీలు ఈ పట్టిక క్రమంలో నడుస్తాయి. ప్రతి తిరస్కరణ స్థిర సందేశంతో ప్రామాణిక ఎర్రర్ బాడీని ఉపయోగిస్తుంది. ఈ చెక్కులలో ఒకదాని ద్వారా తిరస్కరణ ఏమీ వ్రాయదు.

| స్థితి | సందేశం                                                                                             | ఎప్పుడు                                                          |
| ------ | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 404    | `Not found`                                                                                        | `QUOTA_SELF_PANEL` ఫ్లాగ్ ఆఫ్ చేయబడింది.                         |
| 401    | `Valid API key required`                                                                           | కీ లేదు లేదా చెల్లదు, లేదా సర్వర్ పర్యావరణ కీ.                   |
| 403    | `API key lacks the self:usage scope`                                                               | కీలో `self:usage` లేదు.                                          |
| 400    | `Invalid provider`                                                                                 | ప్రొవైడర్ సెగ్మెంట్ చెల్లదు.                                     |
| 429    | `Too many lending changes. Retry later.`                                                           | కీ దాని పరిమితిని దాటింది. సమాధానం `Retry-After` కలిగి ఉంటుంది.  |
| 400    | `Body must be { pool, lendingPercent, lendingUntil }. lendingPercent is an integer from 0 to 100.` | శరీరం JSON కాదు , చాలా పొడవుగా ఉంది లేదా స్కీమాతో సరిపోలడం లేదు. |
| 400    | `lendingUntil must be a Unix time in milliseconds`                                                 | గడువు సెకన్లుగా చదవబడుతుంది.                                     |
| 400    | `lendingUntil must be in the future`                                                               | గడువు అభ్యర్థన సమయానికి లేదా ముందు ఉంటుంది.                      |
| 404    | `Pool not found`                                                                                   | ఈ ప్రొవైడర్ కోసం `ref` ఈ కీ యొక్క ఏ పూల్ను పేర్కొనలేదు.          |
| 403    | `Lending is not enabled for this pool`                                                             | పూల్ `saturation` మోడ్లో ఉంది మరియు `lendingPercent` 0 పైన ఉంది. |
| 500    | `Failed to build quota view`                                                                       | ఏదైనా ఇతర వైఫల్యం. దాని కారణం సర్వర్లో లాగ్ చేయబడింది.           |

పరిమితి ప్రతి కీ కోసం 60 సెకన్లకు 20 అభ్యర్థనలు. ప్రొవైడర్ చెక్ను పాస్ చేసే ప్రతి అభ్యర్థన కూడా తర్వాత తిరస్కరించబడింది లేదా ఏమీ మార్చలేనిది కూడా లెక్కించబడుతుంది. ఇది కీ అభ్యర్థన రేటు పరిమితి కాకుండా దాని స్వంత కౌంటర్ను కలిగి ఉంది.

నిల్వ చేసిన సమ్మతిని మార్చే అభ్యర్థన ఒక `quota.pool.lending.updated` ఆడిట్ రికార్డ్ను వ్రాస్తుంది. ఇది పాత మరియు కొత్త విలువలతో కీని పేరు పెట్టింది. పంపిన ఒకే శరీరం రెండుసార్లు ఒకసారి వ్రాసి ఒకసారి ఆడిట్ చేస్తుంది. పూర్తి `GET` వీక్షణతో సమాధానం 200, వ్రాసిన తర్వాత నిర్మించబడింది.

`GET` వీక్షణ రుణాలను ఈ క్రింది విధంగా నివేదిస్తుంది:

- ప్రతి పూల్ `borrowMode` (`saturation` లేదా `consent`) మరియు కీ యొక్క స్వంత `lendingPercent` మరియు `lendingUntil` కలిగి ఉంటుంది.
- `lendingActive` అనేది `true` అనేది `consent` పూల్లో మాత్రమే, 0 కంటే ఎక్కువ శాతం మరియు గడువు చేరుకోలేదు.
- `consent` పూల్లో, లెక్కించదగిన ప్రతి `dimensions[].yourShare` `borrowAvailable` కలిగి ఉంటుంది. ఇతర కీల ద్వారా అందించబడిన దాని వాటా కంటే కీ ఇప్పుడు ఉపయోగించబడవచ్చు.
- `borrowAvailable` గేట్ సూత్రాన్ని ఉపయోగిస్తుంది. ఇది ప్రతి ఇతర కీని చదువుతుంది, కీ దాని వాటా కింద ఉన్నప్పుడు కూడా. ఒక `hard` కీ కోసం ఒక ఇతర కీకి ఒక అదనపు రీడ్ మరియు సమాంతరంగా లెక్కించదగిన పరిమాణం.
- `borrowAvailable` అనేది `soft` లేదా `burst` కీకి `null`, మరియు రీడ్ విఫలమైనప్పుడు `null`.
- `borrowAvailable` అనేది అన్ని ఇతర కీలకు కలిపి ఒక అంకె. రెండు కీల కొలనులో ఇది మరొక కీ యొక్క స్వంత బొమ్మ.
- `borrowAvailable` ఇంకా `percent` విండోస్ లేదా `accounts[]` లో నివేదించబడలేదు.
- `saturation` పూల్లో వీక్షణ నిల్వ చేసిన సమ్మతిని `lendingActive: false` తో నివేదిస్తుంది మరియు `borrowAvailable` లేదు.

### లోపాలు

ఈ మార్గం యొక్క ప్రతి ప్రతిస్పందన, విజయం లేదా లోపం, `Cache-Control: no-store` కలిగి ఉంటుంది. రూట్ రన్కు ముందు జరిగే తిరస్కరణ దానిని తీసుకువెళ్లదు, ఉదాహరణకు క్లయింట్ API విధానం యొక్క 401 లేదా IP ఫిల్టర్ యొక్క 403. రూట్లోని లోపాలు స్థిర సందేశంతో ప్రామాణిక ఎర్రర్ బాడీని ఉపయోగిస్తాయి: 400 (చెల్లని ప్రొవైడర్), 401 (మిస్సింగ్ లేదా చెల్లని కీ), 403 (మిస్సింగ్ `self:usage` మరియు 4zq4)`Failed to build quota view`). అభ్యర్థన మార్గానికి చేరుకున్న తర్వాత, కీ లుక్అప్తో సహా ఏదైనా వైఫల్యాన్ని 500 కవర్ చేస్తుంది; దాని కారణం సర్వర్లో లాగ్ చేయబడింది మరియు తిరిగి రాలేదు. `PATCH` యొక్క లోపాలు [లెండింగ్ సమ్మతిలో](#lending-consent) జాబితా చేయబడ్డాయి.

### పరిమితులు

- `remaining` అనేది కీ యొక్క ఫెయిర్ షేర్లో అది ఉపయోగించని భాగం. ఇది హామీ కాదు. పూల్లో గది ఉన్నప్పుడే దానికి మించి ఒక కీ అందించబడవచ్చు. పూల్ యొక్క మొత్తం `limit` చేరుకున్న తర్వాత, పూల్ యొక్క ప్రతి కీ దాని స్వంత `remaining` అయినా తిరస్కరించబడుతుంది మరియు `self:account-quota` లేని కీ ఆ మొత్తాన్ని చూడదు.
- `remaining` కేటాయింపు యొక్క సంపూర్ణ `cap` పరిగణనలోకి తీసుకోదు. టోపీ యూనిట్ యొక్క విండోలో దాని స్వంత వినియోగం క్యాప్ విలువను చేరుకున్న తర్వాత ఎన్ఫోర్స్మెంట్ కీని నిరాకరిస్తుంది.
- ఖాతా-స్థాయి బార్ ప్రొవైడర్-పరిమితుల కాష్ నుండి వస్తుంది మరియు అమలు నిర్ణయంలో కొన్ని నిమిషాలు ఆలస్యం కావచ్చు. రీసెట్ సమయం దాటిన రీడింగ్ `stale` గా నివేదించబడింది.
- పర్-మోడల్ విండోస్ (`modelWindows`) అనేది ప్లాన్-విండో మ్యాపింగ్ను కలిగి ఉన్న ప్రొవైడర్ల కోసం మాత్రమే నివేదించబడింది: Claude మరియు Codex today. ఇతర ప్రొవైడర్ల కోసం ఖాతా డేటా చూపబడినప్పుడు `modelWindows` ఇప్పటికీ ఖాళీ `windows` జాబితాతో ఉంటుంది.
- `percent` విండోలో కీ యొక్క స్వంత వాటా అంచనా. ఇది అట్రిబ్యూషన్ పుస్తకం నుండి వస్తుంది మరియు పైన ఉన్న "శాతం డైమెన్షన్లు: పర్-కీ అట్రిబ్యూషన్" క్రింద జాబితా చేయబడిన ప్రతి పరిమితిని కలిగి ఉంటుంది.
- `consumed` అనేది ఫెయిర్ షేర్తో పోల్చిన నంబర్ ఎన్ఫోర్స్మెంట్. ఇది ఖచ్చితంగా `attributed` ప్లస్ `external`. `attributed` అనేది పుస్తకం రూట్ చేసిన టోకెన్లకు కీని ఇచ్చే భాగం. `external` అనేది పూల్ కీలు పరిగణనలోకి తీసుకోని ఖాతా ఉపయోగంలో కీ యొక్క భాగం.
- పూల్ యొక్క `accountVisible` నిజం అయినప్పుడు మాత్రమే రెండు భాగాలు పంపబడతాయి: కీకి `self:account-quota` ఉంది మరియు ప్రొవైడర్ దాని `sharedQuotaProviders` లో ఉన్నారు. అది లేని కీ అదే `status` మరియు `reason` లతో `consumed` మాత్రమే పొందుతుంది.
- రెండు భాగాలు మరియు దాని స్వంత బరువుతో, పూల్ యొక్క కీలకు ఛార్జ్ చేయబడిన పూల్ వెలుపల చేసిన వినియోగాన్ని హోల్డర్ పని చేయవచ్చు. ఖాతా స్కోప్ ఉన్న హోల్డర్ ఇప్పటికే ఖాతా మొత్తాన్ని చూసారు.
- విండోలో ఏదీ రూట్ చేయని కీ ఇప్పటికీ దాని బాహ్య ఛార్జ్ను `consumed` నుండి చదవగలదు, ఎందుకంటే దాని ఆపాదించబడిన భాగం 0.
- ఉదాహరణకు, ఒక పుస్తకం 0 వద్ద తెరుచుకుంటుంది, A మరియు B కీలు ఒక్కొక్కటి 50 బరువుతో ఉంటాయి. కీ A మార్గాలు 900,000 టోకెన్లు మరియు కీ B 100,000. ఖాతా 100 పరిమితిలో 60%కి చేరుకుంటుంది. అప్పుడు కీ Aకి `attributed` 54 మరియు కీ Bకి 6, మరియు `external` రెండింటికీ 0.
- వీక్షణ పుస్తకాన్ని చదువుతుంది మరియు దాని స్థితిని ఎప్పుడూ వ్రాయదు. ఇది పుస్తకాన్ని తెరవదు మరియు ప్రదాతని చదవమని అడగదు. Redis స్టోర్తో, గేట్ రీడ్లు చేసినట్లుగా రీడ్ బ్యాక్గ్రౌండ్లో భర్తీ చేయబడిన పునర్విమర్శ ఫీల్డ్లను తొలగిస్తుంది.
- గేట్ యొక్క కాష్ ఖాతా యొక్క రీడింగ్ను కలిగి ఉన్నప్పుడు మాత్రమే వాటా `ok` అవుతుంది. ఒకటి లేకుండా అది `stale`, కాబట్టి ఇటీవలి అభ్యర్థన లేని పూల్లో ఇది బహుశా పాతదిగా చూపబడుతుంది.
- పూల్ ద్వారా అభ్యర్థన వెళ్లే వరకు, వాటా అందుబాటులో ఉండదు. ఆ అభ్యర్థన పుస్తకాన్ని తెరుస్తుంది మరియు ఆ సమయంలో ఖాతా యొక్క సంఖ్య పూల్ వెలుపల ఉపయోగించినదిగా పరిగణించబడుతుంది.
- అనేక ఖాతాలతో కూడిన పూల్లో, ప్రతి ఖాతా నమోదు ఆ ఖాతా యొక్క స్వంత పుస్తకాన్ని మరియు ఒక ఖాతా యొక్క పరిమితిని ఉపయోగిస్తుంది. ఖాతాల సంఖ్య ద్వారా ఎన్ఫోర్స్మెంట్ రెండు వైపులా స్కేల్ చేస్తుంది, కాబట్టి నిష్పత్తి ఒకే విధంగా ఉంటుంది.
- ప్రతి-మోడల్ విండోస్ కీ కోసం వాటాను కలిగి ఉండవు. పుస్తకం ప్రతి మోడల్ డేటాను ఉంచదు.
- షెడ్యూల్ యొక్క రిజర్వ్ అంతస్తులు వీక్షణ ద్వారా మూల్యాంకనం చేయబడవు: `schedule-reserve` కారణంతో అభ్యర్థన తిరస్కరించబడినప్పుడు షెడ్యూల్ `open` గా చూపబడుతుంది.
- ఒకే కీకి చెందిన రెండు పూల్స్ కనెక్షన్ని పంచుకున్నప్పుడు, ఎన్ఫోర్స్మెంట్ వాటిలో ఒకదాన్ని వర్తింపజేస్తుంది మరియు వీక్షణ రెండింటినీ జాబితా చేస్తుంది.
- విఫలమైన కీ ప్రయత్నాలపై ఒక్కో చిరునామా పరిమితి లేదు: రివర్స్ ప్రాక్సీ కాలర్లు ఒక చిరునామాను పంచుకోగలరు (ఇది ఫార్వార్డ్ చేయబడిన క్లయింట్ చిరునామాలు విశ్వసించబడతాయా లేదా అనే దానిపై ఆధారపడి ఉంటుంది), కాబట్టి లాకౌట్ ప్రతి కీ హోల్డర్కు మార్గాన్ని తిరస్కరించవచ్చు. `REQUIRE_API_KEY=true` తో, క్లయింట్ API విధానం ద్వారా రూట్ రన్ అయ్యే ముందు చెల్లని కీ తిరస్కరించబడుతుంది, ఈ రూట్కి బదులుగా ఆ పాలసీ యొక్క 401 బాడీతో.

### సభ్యుల వినియోగం

పూల్ సభ్యుల మధ్య విండో వినియోగం ఎలా విడిపోతుందో చూడటానికి నిర్వాహకుడు కీ హోల్డర్లను అనుమతించగలరు. ఐచ్ఛికం పూల్ యొక్క `memberBreakdown`, డిఫాల్ట్గా ఆఫ్ చేయబడింది. ఇది పూల్ విజార్డ్లో లేదా `PATCH /api/quota/pools/{id}` తో సెట్ చేయబడింది. `GET /api/quota/pools` మరియు `GET /api/quota/pools/{id}` దీన్ని నివేదించాయి.

వీక్షణ యొక్క పరిమాణం ఇవన్నీ కలిగి ఉన్నప్పుడు మాత్రమే `members` కలిగి ఉంటుంది:

- పూల్ ఎంపిక ఆన్లో ఉంది
- పూల్లో గరిష్టంగా 20 కేటాయించబడిన కీలు ఉన్నాయి మరియు వాటిలో కనీసం ముగ్గురు అభ్యర్థనలను చేయవచ్చు: సక్రియం, రద్దు చేయబడలేదు, నిషేధించబడలేదు మరియు వాటి గడువు ముగియలేదు
- పూల్ యొక్క `accountVisible` నిజం: కీలో `self:account-quota` ఉంది మరియు ప్రొవైడర్ దాని `sharedQuotaProviders` లో ఉన్నారు
- `percent` విండోలో, ఖాతా యొక్క కనెక్షన్ కీ ఉపయోగించవచ్చు
- ఆ విండోలో కీ యొక్క స్వంత వాటా చదవబడింది: దాని `status` `unavailable` కాదు

లేకపోతే `members` లేదు. ఇది ఎప్పుడూ ఖాళీ జాబితా కాదు.

- ప్రతి స్లైస్ `{ slot, consumed, isYou }`. ప్రతిస్పందన స్కీమా స్లైస్లోని ఏదైనా ఇతర ఆస్తిని మరియు 20 కంటే ఎక్కువ స్లైస్ల జాబితాను తిరస్కరిస్తుంది. ముక్కలు స్లాట్ క్రమంలో జాబితా చేయబడ్డాయి.
- ఇకపై అభ్యర్థనలు చేయలేని కీతో సహా కేటాయించిన కీకి ఒక స్లైస్ ఉంటుంది. ఉపయోగం లేని సభ్యుడు నిజమైన సున్నాని చూపుతాడు.
- `isYou` ట్రూతో స్లాట్ 1 ఎల్లప్పుడూ అడిగే కీ. ఇతర స్లాట్ సంఖ్యలు కీడ్ హాష్ యొక్క ర్యాంక్లు. ఇది `API_KEY_SECRET` తో కీ చేయబడింది మరియు పూల్, అడిగే కీ మరియు సభ్యుని కవర్ చేస్తుంది.
- కాబట్టి సంఖ్యలు హోల్డర్ల మధ్య వరుసలో ఉండవు. ఒక హోల్డర్ కోసం వారు సందర్శనల మధ్య అలాగే ఉంటారు. ఒక కీ పూల్లో చేరినప్పుడు లేదా నిష్క్రమించినప్పుడు లేదా ఆ రహస్యాన్ని తిప్పినప్పుడు అవి మారవచ్చు.
- లెక్కించదగిన విండోలో ఒక స్లైస్ అనేది కోటా స్టోర్లోని సభ్యుల కౌంటర్, దాని స్వంత `consumed` వలె అదే కౌంటర్.
- `percent` విండోలో స్లైస్ అనేది సభ్యుని `attributed` భాగం, అదే పుస్తకం నుండి కీ యొక్క స్వంత వాటాగా చదవబడుతుంది. పూల్ వెలుపల చేసిన ఉపయోగం ఎప్పుడూ ముక్కలుగా విభజించబడదు. ఆ ఛార్జ్ బరువుతో విభజించబడింది, కాబట్టి దానిని మోసే ముక్కలు బరువులను చూపుతాయి.
- ప్రతి వీక్షణ ఇతర సభ్యునికి ఒక విలువను మరియు లెక్కించదగిన విండోను సమాంతరంగా చదువుతుంది. `percent` విండోలో స్లైస్లు షేర్ యొక్క స్వంత పుస్తకాన్ని చదవడానికి మించి చదవాల్సిన అవసరం లేదు. ఒక విలువను చదవలేనప్పుడు, ఆ విండోలో `members` ఉండదు మరియు కీ యొక్క స్వంత వాటా అలాగే ఉంటుంది.
- ఎంపిక మరియు ఉపయోగించగల కీల సంఖ్య ఒక్కో పూల్కు ఒకసారి చదవబడుతుంది మరియు ఖాతా డేటాను చూడగలిగే కీ కోసం మాత్రమే చదవబడుతుంది. ఎంపిక లేదా ఉపయోగించగల-కీ గణన యొక్క విఫలమైన రీడ్ ఆ పూల్ కోసం బార్లను ఆఫ్ చేస్తుంది. సర్వర్ హెచ్చరికను లాగ్ చేస్తుంది మరియు మిగిలిన వీక్షణ నిర్మించబడింది.

బార్లు పేర్లు లేదా ఐడిలను కలిగి ఉండవు. వారు ఇప్పటికీ ఇతర సభ్యుల గురించి కీ హోల్డర్కు విషయాలు చెబుతారు:

- హోల్డర్లు ఇప్పటికీ స్లైస్లను వాటి విలువలతో సరిపోల్చవచ్చు.
- స్థిరమైన నంబరింగ్, కాలక్రమేణా ఒక సభ్యుడిని అనుసరించడానికి హోల్డర్ను అనుమతిస్తుంది.
- పూల్లో ఎన్ని కీలు కేటాయించబడ్డాయో స్లైస్ల సంఖ్య చూపుతుంది.
- మూడు కీల పూల్లో, ఒక కీ ఏమి ఉపయోగించాలో తెలిసిన వ్యక్తి చివరి కీ ఏమి ఉపయోగించారో చెప్పగలరు.
- ఒక పూల్ మూడు ఉపయోగించదగిన కీల క్రింద పడిపోయినప్పుడు, బార్లు అదృశ్యమవుతాయి. ఇంతకు ముందు తీసుకున్న వీక్షణలు ఇప్పటికీ ప్రతి సభ్యుడు ఏమి ఉపయోగించారో చూపుతాయి.
- లెక్కించదగిన విండోలో, పూల్ మొత్తం మైనస్ స్లైస్లు ఇకపై కేటాయించబడని కీల వినియోగాన్ని చూపుతాయి.
- ఒక ఖాతాలో సున్నాని చూపి, మరొక ఖాతాలో ఉపయోగించే సభ్యుడు, ఏ సభ్యుడు ఏ ఖాతాను ఉపయోగిస్తున్నారో చూపవచ్చు.
- `hard` విధానంతో లెక్కించదగిన పూల్లో, సభ్యుని యొక్క సరసమైన వాటాలో పెరుగుదల ఆగిపోయే స్లైస్ ఆ సభ్యుని బరువును సూచిస్తుంది.

### వినియోగ శ్రేణి (`GET /api/v1/me/usage`)

`GET /api/v1/me/usage?range=<range>` ( `/v1/me/usage` లో కూడా అందించబడుతుంది) కాలింగ్ కీ యొక్క స్వంత అభ్యర్థనల వినియోగం మరియు ధరను అందిస్తుంది: మొత్తాలు, UTC రోజుకు ఒక ఎంట్రీ, ఒక రోజు మరియు మోడల్, ఒక్కో మోడల్ మరియు ఒక్కో ప్రొవైడర్. ఇది ఫ్లాగ్, ప్రామాణీకరణ నియమాలు, `self:usage` స్కోప్, `Cache-Control: no-store` మరియు ఎగువ కోటా మార్గం యొక్క దోష ప్రవర్తనను పంచుకుంటుంది. కీ `range` ముందు తనిఖీ చేయబడింది. లోపాలు 400 (`Invalid range`), 401, 403, 404 మరియు 500 (`Failed to build usage`).

- `range` అనేది `1d`, `7d`, `30d` (డిఫాల్ట్) లేదా `90d` లలో ఒకటి. ఏదైనా ఇతర విలువ, ఖాళీ విలువ లేదా పునరావృత పరామితి 400. కాల్ ధరను బంధించడానికి సెట్ `90d` వద్ద ఆగుతుంది. వీక్షణ ముడి వినియోగ చరిత్రను మాత్రమే చదువుతుంది, రోజువారీ సారాంశాలను ఎప్పుడూ చదవదు, ఇది కీని కలిగి ఉండదు.
- కాలింగ్ కీ ఐడి ద్వారా అడ్డు వరుసలు ఎంపిక చేయబడతాయి. కీ పేరు నిలువు వరుస సరిపోలలేదు మరియు కీ ఐడి లేకుండా రికార్డ్ చేయబడిన అడ్డు వరుసలు ఎప్పటికీ లెక్కించబడవు.
- శ్రేణిని రూపొందించడం విండోలోని కీ యొక్క అడ్డు వరుసలపై ఐదు సమూహ ప్రశ్నలను అమలు చేస్తుంది. నిర్మించబడిన సిరీస్ ప్రతి కీ మరియు శ్రేణికి 60 సెకన్ల పాటు తిరిగి ఉపయోగించబడుతుంది మరియు తిరిగి ఉపయోగించిన కాల్ ఏదీ అమలు చేయదు. దాని `generatedAt` దాని వయస్సును ఇస్తుంది.
- సిరీస్ నిర్మించబడినప్పుడు విండో ముగుస్తుంది. తర్వాత స్టాంప్ చేయబడిన అడ్డు వరుస, ఉదాహరణకు క్లాక్ స్కే ద్వారా, లెక్కించబడదు.
- `coverage.retentionDays` అనేది ఆపరేటర్ యొక్క ముడి వాడుక-చరిత్ర నిలుపుదల సెట్టింగ్ (డేటాబేస్ సెట్టింగ్లలో`retention.usageHistory` ). అభ్యర్థించిన పరిధి ఆ సెట్టింగ్ కంటే ఎక్కువగా ఉన్నప్పుడు `coverage.truncatedByRetention` నిజం. ఇది రెండు సంఖ్యలను పోల్చి చూస్తుంది మరియు అడ్డు వరుసలు నిజంగా తప్పిపోయాయో లేదో తనిఖీ చేయదు.
- కీ యొక్క స్వంత అభ్యర్థనల కోసం ప్రదాత రికార్డ్ చేసినట్లు తిరిగి ఇవ్వబడింది. మోడల్ అనేది దాని చివరి `/` తర్వాత రికార్డ్ చేయబడిన పేరు మరియు అడ్డు వరుసలు దాని ద్వారా సమూహం చేయబడతాయి. ప్రతి లక్ష్యం తిరస్కరించబడిన కాంబో అభ్యర్థన ప్రొవైడర్గా రూటింగ్ లేబుల్ (కాంబో పేరు, `auto` లేదా `combo`) మరియు క్లయింట్ పంపిన మోడల్ స్ట్రింగ్తో రికార్డ్ చేయబడుతుంది. ఇతర తిరస్కరించబడిన అభ్యర్థనలు, ఉదాహరణకు ఓపెన్ సర్క్యూట్ బ్రేకర్, మోడల్ కూల్డౌన్ లేదా కోటా-పార్క్డ్ స్కిప్ ద్వారా, టార్గెట్ ప్రొవైడర్ మరియు మోడల్ను ఉంచండి.
- గణనలు మరియు ఖర్చులతో పాటు, ప్రతిస్పందన సగటు జాప్యం, విజయ రేట్లు మరియు మొదటి మరియు చివరి అభ్యర్థన సమయాలను కలిగి ఉంటుంది.
- `byModel` అత్యధిక అభ్యర్థనలతో 50 ప్రొవైడర్ మరియు మోడల్ జతలను జాబితా చేస్తుంది. మరిన్ని జతలతో దాని ఎంట్రీలు `summary` వరకు జోడించబడవు మరియు `summary.uniqueModels` ప్రతి రికార్డ్ చేయబడిన మోడల్ స్పెల్లింగ్ను గణిస్తుంది. `byModelTruncated` అప్పుడు నిజం, మరియు కట్కి రెండు వైపులా జంటలు పడే మోడల్ పాక్షిక మొత్తాలను చూపుతుంది.
- రెండు ఖర్చులు నివేదించబడ్డాయి. `costUsd` అనేది బిల్ చేయబడిన ధర, వినియోగ విశ్లేషణలు దానిని చూపుతాయి. Claude కోడ్ ప్లాన్ వంటి ఫ్లాట్-రేట్ సబ్స్క్రిప్షన్ ప్రొవైడర్లు అక్కడ $0ని లెక్కించారు. `listPriceUsd` అనేది జాబితా ధరలో అదే వినియోగ ధర, సభ్యత్వాలు చేర్చబడ్డాయి. మోడల్ ధర వరుస లేని అభ్యర్థన దాని నిల్వ ధరను గణిస్తుంది: ప్రొవైడర్ నివేదించిన ధర లేదా అభ్యర్థన రికార్డ్ చేయబడినప్పుడు లెక్కించబడుతుంది. మార్కర్ లేని 0 గణనలు లేని అభ్యర్థన మాత్రమే, కాబట్టి మొత్తం పాక్షికంగా ఉంటుంది.
- ప్రతిస్పందన ఒప్పందం `src/shared/schemas/selfUsage.ts` ( `docs/openapi.yaml` లో`SelfUsageSeries` ).

### స్వీయ సేవా పేజీ

`QUOTA_SELF_PANEL` ఆన్తో, `/quota/{provider}` అనేది పబ్లిక్ పేజీ. ఒక కీ హోల్డర్ అక్కడ API కీని టైప్ చేసి, ప్రొవైడర్ కోసం ఆ కీ యొక్క పూల్లను చూస్తాడు. ప్రతి పూల్ ప్రతి ఒక్కరికీ పూల్ యొక్క ఉపయోగం మరియు కీ యొక్క స్వంత వాటాతో ఒక్కో పూల్ విండోకు ఒక కార్డ్ని చూపుతుంది. పూల్ యొక్క ప్రతి ఖాతా దాని స్వంత కార్డ్లను కలిగి ఉంటుంది, ఖాతా యొక్క ఉపయోగం మరియు కీ యొక్క వాటా. కీ ఖాతా డేటాను చూసినప్పుడు మాత్రమే ఖాతా యొక్క ఉపయోగం కనిపిస్తుంది. పేజీ ప్రతి ఖాతా యొక్క ఒక్కో మోడల్ పరిమితులను మరియు కీ యొక్క స్వంత వినియోగాన్ని కూడా జాబితా చేస్తుంది. షెడ్యూల్ ప్రస్తుతం కీని బ్లాక్ చేసినప్పుడు నోటీసు కనిపిస్తుంది. కార్డ్ దాని ఉపయోగంతో కీ యొక్క ప్రతి మోడల్ క్యాప్ను జాబితా చేస్తుంది మరియు చేరుకున్న వాటిని గుర్తు చేస్తుంది. `{provider}` అనేది ప్రొవైడర్ ఐడి లేదా దాని మారుపేరు (`/quota/claude`, `/quota/cc`). తెలియని ప్రొవైడర్ మరియు ఫ్లాగ్ ఆఫ్లో ఉన్నప్పుడు ప్రతి `/quota/*` పాత్కు సమాధానం 404. అనుకూల OpenAI- లేదా ఆంత్రోపిక్-అనుకూల నోడ్లోని పూల్స్కు పేజీ లేదు. API ఇప్పటికీ వాటికి సమాధానాలు ఇస్తుంది.

పేజీకి సెషన్ లేదు. కీ `GET /api/v1/me/quota/{provider}`, `PATCH /api/v1/me/quota/{provider}` మరియు `GET /api/v1/me/usage` యొక్క `Authorization` హెడర్లో మాత్రమే పంపబడుతుంది, ఎప్పుడూ URL లో కాదు. సర్వర్ అంగీకరించే కీ ట్యాబ్ యొక్క `sessionStorage` లో ఉంచబడుతుంది. "ఈ పరికరంలో గుర్తుంచుకో"తో ఇది బదులుగా `localStorage` లో ఉంచబడుతుంది మరియు "కీ మరచిపో" రెండింటి నుండి తీసివేస్తుంది. సర్వర్ తిరస్కరించిన కీ నిల్వ నుండి తీసివేయబడుతుంది.

`consent` మోడ్లోని పూల్ లెండింగ్ కార్డ్ని చూపుతుంది. అక్కడ కీ హోల్డర్ రుణం ఇవ్వడానికి కీ యొక్క నిష్క్రియ వాటాలో 0 నుండి 100 వరకు మొత్తం శాతాన్ని సెట్ చేస్తాడు. సమ్మతి ఎంతకాలం ఉంటుందో కూడా హోల్డర్ ఎంచుకుంటారు: ఆఫ్ చేసే వరకు, 1 గంట, 8 గంటలు, 24 గంటలు, 7 రోజులు లేదా 30 రోజులు. పొదుపు క్షణం నుండి వ్యవధి లెక్కించబడుతుంది. గడువు అమలులో ఉన్నప్పుడు, హోల్డర్ దానిని బదులుగా ఉంచుకోవచ్చు. సేవ్ చేయడానికి ముందు ఆ గడువు దాటితే, కార్డ్ ఏమీ పంపదు మరియు మరొక ఎంపిక కోసం అడుగుతుంది. 0%తో ఎటువంటి గడువు పంపబడదు. కార్డ్ దాని టైమ్ జోన్ పేరుతో నిల్వ చేయబడిన గడువును చూపుతుంది. గడువు ముగిసిన సమ్మతి ముగిసినట్లు చూపబడుతుంది.

`hard` కీ కోసం, కార్డ్ ప్రస్తుతం కీకి ఏ ఇతర కీలు అందజేస్తాయో, ఒక్కో పూల్ విండోను కూడా జాబితా చేస్తుంది. ప్రతి అడ్డు వరుస అన్ని ఇతర కీలకు కలిపి ఒక బొమ్మ. రెండు కీల కొలనులో ఇది మరొక కీ యొక్క స్వంత బొమ్మ. వీక్షణ నివేదించని సంఖ్య అందుబాటులో లేనట్లుగా చదవబడుతుంది, సున్నాగా కాదు. `soft` లేదా `burst` కీ కోసం కార్డ్ ఏ ఫిగర్ వర్తించదని చెబుతుంది.

`saturation` మోడ్లోని పూల్, 0 కంటే ఎక్కువ శాతాన్ని నిల్వ చేసే కీలు ఉపసంహరణను మాత్రమే చూపుతాయి. నిల్వ చేసిన శాతం అక్కడ ఎలాంటి ప్రభావం చూపదని చెబుతోంది. దీని ఉపసంహరణ బటన్ గడువు లేకుండా 0ని పంపుతుంది. నిల్వ చేయబడిన 0తో `saturation` మోడ్లో ఉన్న పూల్ ఎటువంటి లెండింగ్ కార్డ్ను చూపదు. సేవ్ చేసిన తర్వాత, తిరిగి వచ్చిన వీక్షణకు ఇకపై అవసరం లేని కార్డ్ పేజీ వీక్షణ మళ్లీ మారే వరకు దాని సందేశంతో పాటు ఉంటుంది.

హోల్డర్ సేవ్ లేదా ఉపసంహరణను నొక్కినంత వరకు ఏదీ సేవ్ చేయబడదు. ప్రతి ప్రెస్ ఒక `PATCH /api/v1/me/quota/{provider}` అభ్యర్థనను పంపుతుంది మరియు మొదటిది పెండింగ్లో ఉన్నప్పుడు రెండవ ప్రెస్ ఏమీ పంపదు. శరీరం వీక్షణ, శాతం మరియు గడువు నుండి పూల్ యొక్క అపారదర్శక `ref` కలిగి ఉంటుంది. సమాధానం రీబిల్ట్ కోటా వీక్షణ, మరియు పేజీ రెండవ రీడ్ లేకుండా చూపిస్తుంది. రెండు సేవ్లు అతివ్యాప్తి చెందినప్పుడు, చివరి సమాధానం తర్వాత పేజీ కోటాను ఒకసారి చదువుతుంది. పేజీ సమ్మతిని బ్రౌజర్ నిల్వలో ఉంచదు.

తిరస్కరించబడిన మార్పు HTTP స్థితి నుండి ఎంచుకున్న వచనం ద్వారా కార్డ్పై వివరించబడింది. లోపం శరీరం చదవబడలేదు. A 401 కీ అంగీకరించబడలేదు మరియు కోటాను మళ్లీ లోడ్ చేస్తుంది. A 403 పూల్ రుణ మార్పులను తీసుకోవడం లేదని మరియు 404 పూల్ పోయిందని చెప్పింది. రెండూ కోటాను రీలోడ్ చేసే బటన్ను అందిస్తాయి. 400 లేదా మరొక 4xx సమాధానం శాతం మరియు గడువును తనిఖీ చేయమని హోల్డర్ను అడుగుతుంది. A 429 హోల్డర్ను వేచి ఉండమని అడుగుతుంది, సమాధానం వారికి ఇచ్చినప్పుడు `Retry-After` సెకన్లు. 5xx సమాధానం, 408 లేదా నెట్వర్క్ వైఫల్యం మార్పు సేవ్ చేయబడలేదని చెబుతుంది మరియు టైప్ చేసిన విలువలను ఉంచుతుంది. ఒప్పందం వెలుపల ఉన్న సమాధానం కోటాను మళ్లీ లోడ్ చేస్తుంది. విఫలమైన సేవ్ కీని స్వయంగా తీసివేయదు. తిరస్కరించబడిన తర్వాత మళ్లీ లోడ్ చేసినప్పుడు, ఏదైనా తిరస్కరించబడిన రీడ్లో పేజీ కీని తీసివేస్తుంది.

ఒక కీ ఆమోదించబడిన తర్వాత, పేజీ మూడు ట్యాబ్లతో కూడిన "మీ సాధనాలను సెటప్ చేయండి" కార్డ్ని కూడా చూపుతుంది. "Claude కోడ్" `~/.claude/settings.json` కోసం `env` బ్లాక్ని ఇస్తుంది. "షెల్" `export` పంక్తుల వలె అదే వేరియబుల్స్ ఇస్తుంది. "Claude డెస్క్టాప్" దాని మూడవ పక్ష అనుమితి విండోకు విలువలను ఇస్తుంది. మోడల్లు కోటా-షేర్ మోడల్లు, ఆ ప్రొవైడర్ కోసం కీ కాల్ చేయవచ్చు. కీతో అటువంటి జాబితా రానప్పుడు, బ్లాక్ గేట్వే మోడల్ డిస్కవరీని ఆన్ చేస్తుంది. గేట్వే చిరునామా అనేది సర్వర్ నివేదించే పబ్లిక్ API మూలం (`OMNIROUTE_PUBLIC_API_BASE_URL`, తర్వాత `OMNIROUTE_PUBLIC_BASE_URL`). ఏదీ సెట్ చేయనప్పుడు, కార్డ్ ప్లేస్హోల్డర్ను చూపుతుంది మరియు నిర్వాహకుడిని అడగమని హోల్డర్కు చెబుతుంది. కీ ప్లేస్హోల్డర్గా చూపబడింది. "నా కీని చేర్చు" మొత్తం కీని స్క్రీన్పై ఉన్న టెక్స్ట్లో మరియు కాపీ బటన్ కాపీ చేసే దానిలో ఉంచుతుంది. పెట్టె క్లియర్ చేయబడే వరకు, కీ మరచిపోయే వరకు లేదా భర్తీ చేయబడే వరకు లేదా పేజీ మిగిలిపోయే వరకు అది కొనసాగుతుంది. కార్డ్ ఎటువంటి అభ్యర్థనను పంపదు మరియు ఫైల్ డౌన్లోడ్ను అందించదు.

API మార్కులను `stale` చదవడం బహుశా పాతదిగా చూపబడుతుంది. `unavailable` గుర్తుపెట్టే రీడింగ్ దాని కారణంతో చూపబడుతుంది, ఎప్పుడూ సున్నాగా ఉండదు.

శాతం ప్రణాళికలపై API నివేదించినప్పుడు పేజీ కీ యొక్క స్వంత వాటాను తీసుకుంటుంది. ఇది ఒక అంచనా అని చెబుతుంది మరియు దాని రెండు భాగాలకు పేరు పెట్టింది. ఒక్కో మోడల్ పరిమితులు ఖాతాను మాత్రమే చూపుతాయి.

ఒక విండో `members` కలిగి ఉన్నప్పుడు, దాని కార్డ్ స్లాట్ క్రమంలో ఒక్కో సభ్యునికి ఒక సెగ్మెంట్తో బార్ను కూడా చూపుతుంది. అడిగే కీ సెగ్మెంట్ యాస రంగును ఉపయోగిస్తుంది. ఇతర విభాగాలు థీమ్ యొక్క చార్ట్ రంగుల ద్వారా తిరుగుతాయి. టెక్స్ట్ లెజెండ్ ప్రతి సెగ్మెంట్ను దాని విలువతో జాబితా చేస్తుంది, కాబట్టి ఏదీ రంగుపై ఆధారపడి ఉండదు. విభాగాలు `You` లేదా `Member N` అని లేబుల్ చేయబడ్డాయి, ఇక్కడ N అనేది స్లాట్.

### పేజీ కోసం అంకితమైన పోర్ట్

`QUOTA_PANEL_PORT` స్వీయ-సేవ పేజీని మాత్రమే అందించే రెండవ శ్రోతను తెరుస్తుంది. వేరియబుల్ సెట్ చేయకపోతే ఇది ఆఫ్లో ఉంటుంది. `QUOTA_PANEL_HOST` అనేది `127.0.0.1` కి బైండ్ చిరునామా మరియు డిఫాల్ట్.

శ్రోత ఈ మార్గాలను ప్రధాన పోర్ట్కు ప్రసారం చేస్తాడు మరియు ప్రతి ఇతర మార్గానికి 404కు సమాధానమిస్తాడు:

| మార్గం                                                                   | సేవలందిస్తుంది                                    |
| ------------------------------------------------------------------------ | ------------------------------------------------- |
| `/quota/{provider}`                                                      | పేజీ                                              |
| `/api/v1/me/quota/{provider}`, `/v1/me/quota/{provider}`                 | పేజీ చదివే కోటా వీక్షణ                            |
| `/api/v1/me/usage`, `/v1/me/usage`                                       | పేజీ చదివే వినియోగ శ్రేణి                         |
| `/_next/static/`                                                         | బిల్డ్ యొక్క స్క్రిప్ట్లు, స్టైల్స్ మరియు ఫాంట్లు |
| `/favicon.ico`, `/favicon.svg`, `/icon-512.png`, `/apple-touch-icon.png` | చిహ్నాలు                                          |

`GET` మరియు `HEAD` శరీరం లేకుండా ప్రసారం చేయబడతాయి. బాడీతో ఒక అభ్యర్థన కూడా ప్రసారం చేయబడింది: కోటా వీక్షణ మార్గం యొక్క `PATCH`, రుణ ఎంపికను సేవ్ చేయడానికి పేజీ పంపుతుంది. CONNECT అభ్యర్థన మినహా ఏదైనా ఇతర పద్ధతి 404కి సమాధానం ఇస్తుంది, దీని కనెక్షన్ సమాధానం లేకుండా మూసివేయబడింది. శరీరం 404కి సమాధానమిచ్చి దాని కనెక్షన్ మూసివేయబడిందని ప్రకటించే ఏదైనా ఇతర అభ్యర్థన. అప్గ్రేడ్ అభ్యర్థనలు తిరస్కరించబడ్డాయి మరియు వాటి కనెక్షన్ మూసివేయబడింది. API పోర్ట్లో వలె డాట్ సెగ్మెంట్ లేదా ఫ్రాగ్మెంట్ మార్కర్తో ఉన్న మార్గం నిరాకరించబడింది. ముద్రించదగిన ASCII వెలుపల అక్షరంతో అభ్యర్థన లక్ష్యం కూడా. ఈ పోర్ట్ యొక్క స్వంత తనిఖీకి ముందు లక్ష్యంలోని ఒక ముడి నియంత్రణ అక్షరానికి HTTP పార్సర్ ద్వారా 400 అని సమాధానం ఇవ్వబడుతుంది. ఫ్రేమ్వర్క్ దాని స్వంత ఉపయోగం కోసం రిజర్వ్ చేయబడని అభ్యర్థన శీర్షికలు: `x-middleware-`, `x-invoke-`, `x-nextjs-`, `x-now-` లేదా `x-next-`, మరియు పేర్లు `x-matched-path` మరియు `next-resume` లతో ప్రారంభమయ్యే పేర్లు. వారు లేకుండా అభ్యర్థన ప్రసారం చేయబడుతుంది. డాష్బోర్డ్, లాగిన్ పేజీ, నిర్వహణ API మరియు అనుమితి మార్గాలను ఈ పోర్ట్ ద్వారా చేరుకోలేరు.

`PATCH` తప్పనిసరిగా `Content-Type: application/json` కలిగి ఉండాలి, పరామితి లేకుండా లేదా `charset=utf-8` తో మాత్రమే. ఇది తప్పనిసరిగా 1 నుండి 4096 వరకు ఒక `Content-Length` కలిగి ఉండాలి, సాదా అంకెలుగా వ్రాయబడి ఉంటుంది మరియు `Transfer-Encoding` లేదు . ఈ నియమాలలో ఒకదానిని ఉల్లంఘించిన `PATCH` 404కు సమాధానమిస్తుంది. సంతకం చేయబడిన లేదా పునరావృతమయ్యే వంటి కొన్ని తప్పుగా ఉండే పొడవులకు ఈ పోర్ట్ యొక్క స్వంత తనిఖీకి ముందు HTTP పార్సర్ ద్వారా 400 అని సమాధానం ఇవ్వబడుతుంది. ప్రధాన పోర్ట్ను సంప్రదించడానికి ముందు పోర్ట్ డిక్లేర్డ్ బైట్లను రీడ్ చేస్తుంది మరియు వాటి కోసం గరిష్టంగా 5 సెకన్లు వేచి ఉంటుంది. అప్పటికి పూర్తికాని శరీరం 404కి సమాధానం ఇస్తుంది మరియు దాని కనెక్షన్ మూసివేయబడింది. ఆ సందర్భంలో లేదా క్లయింట్ ముందుగా బయలుదేరినప్పుడు ఏదీ ప్రధాన పోర్ట్ను చేరుకోదు. పోర్ట్ అదే `Content-Length` తో ఖచ్చితంగా డిక్లేర్డ్ బైట్లను రిలే చేస్తుంది. వాటి తర్వాత బైట్లు కనెక్షన్పై తదుపరి అభ్యర్థనగా చదవబడతాయి. ముందు ఉన్న TLS రివర్స్ ప్రాక్సీ తప్పనిసరిగా `Content-Length` ఫార్వార్డ్ చేయాలి మరియు అభ్యర్థన బాడీని మళ్లీ భాగం చేయకూడదు. `GET` కొరకు ప్రధాన పోర్ట్ API కీని `Authorization` హెడర్లో తనిఖీ చేస్తుంది.

404 శరీరం `{"error":"not_found","message":"Not found."}`. విఫలమైన రిలే 502 (`api_bridge_unavailable`) లేదా 504 (`api_bridge_timeout`)కి `detail` ఫీల్డ్ లేకుండా సమాధానమిస్తుంది.

వినేవాడు `QUOTA_SELF_PANEL` చదవడు మరియు అది పేజీని ఆన్ చేయదు. ఫ్లాగ్ ఆఫ్లో ఉన్నప్పుడు, ప్రధాన పోర్ట్లో పేజీ మరియు దాని API 404కు సమాధానం ఇస్తాయి మరియు వినేవారు ఆ సమాధానాన్ని ప్రసారం చేస్తారు.

డెవలప్మెంట్ సర్వర్ (`next dev`) కింద, ఈ పోర్ట్ ద్వారా పేజీ ఇంటరాక్టివ్గా మారదు. డెవలప్మెంట్ హాట్-రీలోడ్ సాకెట్ అప్గ్రేడ్ అభ్యర్థన, మరియు పోర్ట్ దానిని నిరాకరిస్తుంది. అభివృద్ధి చేస్తున్నప్పుడు ప్రధాన పోర్ట్ ఉపయోగించండి.

పోర్ట్ సాదా HTTP అందిస్తుంది మరియు పేజీ API కీలను పంపుతుంది. డిఫాల్ట్ బైండ్ చిరునామాను ఉంచండి మరియు దాని ముందు TLS తో రివర్స్ ప్రాక్సీని ఉంచండి. లూప్బ్యాక్ కాకుండా బైండ్ చిరునామా ఈ నోటీసును లాగ్ చేస్తుంది:

```text
[Quota Panel] Bound to <host>. This port serves plain HTTP and the page sends API keys. Put a TLS reverse proxy in front of it.
```

ఫార్వార్డింగ్ హెడర్ను పంపని లూప్బ్యాక్ పీర్ ప్రధాన పోర్ట్లో స్థానికంగా పరిగణించబడుతుంది. కాబట్టి అదే హోస్ట్లోని ప్రాక్సీ తప్పనిసరిగా `X-Forwarded-For` పంపాలి. ప్రైవేట్ చిరునామాలోని ప్రాక్సీ `OMNIROUTE_TRUST_PROXY=private` (లేదా `lan`)తో మాత్రమే ఆ హెడర్ కోసం విశ్వసించబడుతుంది. ఏదైనా ఇతర పీర్ దాని కనెక్షన్ చిరునామా ద్వారా నివేదించబడింది మరియు అది పంపిన ఫార్వార్డింగ్ హెడర్లు తొలగించబడతాయి.

శ్రోత ఒక సమయంలో గరిష్టంగా 256 కనెక్షన్లను కలిగి ఉంటారు. అభ్యర్థన శీర్షికలను పంపడానికి క్లయింట్కు 10 సెకన్లు మరియు మొత్తం అభ్యర్థనను పంపడానికి 30 సెకన్లు ఉంటాయి. నిష్క్రియంగా ఉంచబడిన-సజీవంగా ఉన్న కనెక్షన్ దాదాపు 5 సెకన్ల తర్వాత మూసివేయబడుతుంది. 60 సెకన్ల పాటు ఎటువంటి కార్యాచరణ లేని కనెక్షన్ మూసివేయబడింది. ఈ విలువలు స్థిరంగా ఉంటాయి. ముందు ఉన్న రివర్స్ ప్రాక్సీలో కనెక్షన్ మరియు రేట్ పరిమితులను సెట్ చేయండి. ముందు ఉన్న రివర్స్ ప్రాక్సీ దాని అప్స్ట్రీమ్ కనెక్షన్లను 5 సెకన్ల కంటే తక్కువ సేపు ఉంచాలి లేదా వాటిని మళ్లీ ఉపయోగించకూడదు. ప్రధాన పోర్ట్కి రిలే API పోర్ట్ (`API_BRIDGE_*`) యొక్క అప్స్ట్రీమ్ టైమ్అవుట్లను ఉపయోగిస్తుంది.

`API_PORT` సెట్ చేయనప్పుడు శ్రోత కూడా ప్రారంభమవుతుంది. `QUOTA_PANEL_PORT` తప్పనిసరిగా 1 నుండి 65535 వరకు ఉన్న పోర్ట్ అయి ఉండాలి, అంకెల్లో మాత్రమే వ్రాయబడుతుంది. ఇది తప్పనిసరిగా డాష్బోర్డ్ పోర్ట్ మరియు API పోర్ట్ నుండి భిన్నంగా ఉండాలి. లైవ్ WebSocket సర్వర్ ఆన్లో ఉన్నప్పుడు, అది తప్పనిసరిగా `LIVE_WS_PORT` (డిఫాల్ట్ 20132)కి భిన్నంగా ఉండాలి. ఏదైనా ఇతర విలువ ఏమీ తెరవదు మరియు హెచ్చరికను లాగ్ చేస్తుంది. తిరస్కరించబడిన విలువ గురించిన హెచ్చరిక వేరియబుల్కు పేరు పెడుతుంది మరియు విలువను పునరావృతం చేయదు. ఇప్పటికే ఉపయోగంలో ఉన్న పోర్ట్ ఏమీ తెరవదు మరియు ఈ హెచ్చరికను లాగ్ చేస్తుంది:

```text
[Quota Panel] Port <port> is already in use. The quota panel port stays off.
```

`OMNIROUTE_BASE_PATH` సెట్తో, శ్రోత ఆ ఉపసర్గ కింద పైన ఉన్న ప్రతి మార్గాన్ని ఆశిస్తాడు. నిర్మాణ సమయంలో మరియు అమలు సమయంలో అదే `OMNIROUTE_BASE_PATH` ఉపయోగించండి. దీన్ని ప్రముఖ స్లాష్తో మరియు వెనుకబడిన స్లాష్ లేకుండా వ్రాయండి, ఉదాహరణకు `/omniroute`. `/` మరియు `/omniroute/` తో సహా మరొక ఆకారం, పోర్ట్ను హెచ్చరికతో వదిలివేస్తుంది, అయినప్పటికీ బిల్డ్ ఆ ఫారమ్లను అంగీకరిస్తుంది. మొదటి సెగ్మెంట్ అప్లికేషన్ రూట్కి పేరు పెట్టే బేస్ పాత్ కూడా చేస్తుంది: `api`, `v1`, `v1beta`, `_next`, `quota`, `dashboard`, `docs`, `login`, `codex`, `responses`, `anthropic`, `openai`, `v0`, లేదా `connect`.

పరిమితులు:

- ఈ పోర్ట్లో వెనుకంజలో ఉన్న స్లాష్తో`/quota/{provider}/` 404కి సమాధానం ఇస్తుంది.
- సేవా కార్యకర్త మరియు వెబ్ యాప్ మానిఫెస్ట్ ఈ పోర్ట్లో అందించబడవు.
- డ్యాష్బోర్డ్లో సెట్ చేసిన అనుకూల ఫేవికాన్ ఈ పోర్ట్లో చూపబడలేదు.
- అప్లికేషన్ బేస్ పాత్ కింద నడుస్తున్నప్పుడు చిహ్నాలు చూపబడవు.
- పోర్ట్ సాదా HTTP/1.1. మాట్లాడుతుంది
- ప్రక్రియ పునఃప్రారంభించే వరకు విఫలమైన బైండ్ మళ్లీ ప్రయత్నించబడదు.
- వినేవారికి కనెక్షన్ లేదా ప్రతి క్లయింట్ చిరునామాకు రేట్ పరిమితి లేదు.
- కంటైనర్ సెటప్లు ఈ విభాగం పరిధిలోకి రావు.

## సమస్య పరిష్కారం

### Redis కాన్ఫిగర్ చేయబడింది, కానీ కనెక్ట్ కావడం లేదు

`ioredis` ఇన్స్టాల్ అయిందో లేదో (`npm ls ioredis`), అలాగే `QUOTA_STORE_REDIS_URL`
అందుబాటులో ఉందో లేదో తనిఖీ చేయండి. కనెక్షన్ విఫలమైతే ఫ్యాక్టరీ SQLiteకు ఫాల్బ్యాక్ అవుతుంది (`warn` స్థాయిలో
లాగ్ చేయబడుతుంది).

### `peek` పాత డేటాను అందిస్తుంది / ఫెయిల్-ఓపెన్ అవుతుంది

`peek` ఎర్రర్ను విసిరితే, `enforceQuotaShare` ఫలితాన్ని "అనుమతించు"గా (ఫెయిల్-ఓపెన్)
పరిగణిస్తుంది. మూల కారణాన్ని గుర్తించడానికి `quota:enforce` మరియు `quota:factory` ఎంట్రీల కోసం
`pino` లాగ్లను తనిఖీ చేయండి.

### వినియోగ కౌంటర్ డ్రిఫ్ట్

వాస్తవ ప్రొవైడర్ వినియోగం కౌంటర్లతో భిన్నంగా ఉంటే, అది ఊహించినదే — 2-బకెట్
స్లైడింగ్ విండోలో విండో సరిహద్దుల వద్ద సుమారు 1% లోపం ఉంటుంది, అలాగే `consume`
రెస్పాన్స్ తర్వాత ఫైర్-అండ్-ఫర్గెట్ విధానంలో నడుస్తుంది. సాచురేషన్ సిగ్నల్ (`saturationSignals.ts`)
30 సెకన్ల TTLతో వాస్తవ ప్రొవైడర్ వినియోగాన్ని చదివి, దానికి అనుగుణంగా `globalUsedPercent`ను
సర్దుబాటు చేస్తుంది.

### బర్న్ రేట్ కోసం పూల్ "డేటా లేదు" అని చూపిస్తుంది

`computeBurnRate`కు కనీసం 2 చారిత్రక శాంపిల్స్ అవసరం. ఇంతకుముందు
`consume` కాల్స్ లేని కొత్త పూల్స్ `tokensPerSecond: 0` మరియు `timeToExhaustionMs: null`ను చూపిస్తాయి.

## localStorage నుండి మైగ్రేషన్

`/dashboard/costs/quota-share` మొదటిసారి లోడ్ అయినప్పుడు, `useLocalStoragePoolMigration`
హుక్ వీటిని తనిఖీ చేస్తుంది:

1. `localStorage.getItem("omniroute:quota-share:pools")` ఖాళీగా లేదు.
2. `GET /api/quota/pools` `[]`ను తిరిగి ఇస్తుంది (DB ఖాళీగా ఉంది).

రెండూ నిజమైతే, అది ప్రతి లెగసీ పూల్ను బ్యాచ్గా `POST /api/quota/pools`కు పోస్ట్ చేసి,
ఆ తర్వాత localStorage కీని తొలగిస్తుంది. ఈ మైగ్రేషన్ ఐడెంపోటెంట్గా ఉంటుంది: షరతు 2
మళ్లీ మైగ్రేట్ చేయడాన్ని నిరోధిస్తుంది.

## అంతర్గత వ్యూహ వర్గీకరణ

`quota-share` అనేది **అంతర్గత వినియోగానికి మాత్రమే** ఉద్దేశించిన రూటింగ్ వ్యూహం

UI లేదా APIలో వినియోగదారు ఎంచుకోగల ఎంపికగా ఎప్పుడూ కనిపించకుండా ఉద్దేశపూర్వకంగా
`ROUTING_STRATEGY_VALUES` నుండి మినహాయించబడింది.

## DB స్కీమా సారాంశం

`078`, `079` మరియు `085` వలసల ద్వారా మూడు పట్టికలు జోడించబడ్డాయి:

- `quota_pools` + `quota_allocations` — పూల్ నిర్వచనాలు మరియు ఒక్కో కీ కేటాయింపులు.
- `quota_consumption` — రోలింగ్ 2-బకెట్ కౌంటర్లు ప్రతి `(apiKeyId, dimensionKey)`.
- `provider_plans` — మాన్యువల్ ప్రొవైడర్ ప్లాన్ ఓవర్రైడ్లు ( connectionId కి JSON కొలతలు).

అన్ని పట్టికలు idempotent `CREATE TABLE IF NOT EXISTS` మైగ్రేషన్ల ద్వారా జోడించబడ్డాయి.

సమ్మతి రుణం మూడు నిలువు వరుసలను జోడిస్తుంది: `quota_allocations.lending_percent` (పూర్ణాంకం, డిఫాల్ట్ 0), `quota_allocations.lending_until` (యుగం మిల్లీసెకన్లు, లేదా గడువు లేకుండా `NULL` ) మరియు `quota_pools.borrow_mode` (డిఫాల్ట్ `saturation`). దీని మైగ్రేషన్ ఈ నిలువు వరుసలను మాత్రమే జోడిస్తుంది మరియు ఇప్పటికే ఉన్న అడ్డు వరుసలను వ్రాయదు.

శాతం అట్రిబ్యూషన్ పుస్తకం `quota_percent_ledger` (ఒక పూల్, ఖాతా మరియు ప్లాన్ విండోకు ఒక వరుస) మరియు `quota_percent_ledger_tokens` (ఒక పూల్, ఖాతా మరియు API కీకి ఒక టోకెన్ కౌంటర్) జోడిస్తుంది. `src/lib/db/quotaPercentLedger.ts` వాటిని చదివి వ్రాస్తాడు.
