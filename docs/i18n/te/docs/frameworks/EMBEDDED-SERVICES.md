### నిర్వహించబడే ప్రాక్సీ కోర్లు

కస్టమ్ ప్రాక్సీ హోస్ట్ ఫీల్డ్ కూడా V2Ray సోర్స్ లింక్ని అంగీకరిస్తుంది. ఎంచుకోండి** పాడే పెట్టె** లేదా** Xray** స్పష్టంగా, ఆపై సేవ్ క్లిక్ చేయండి. టైపింగ్ ఎప్పుడూ డౌన్లోడ్ చేయదు లేదా కోర్ను ప్రారంభించదు. సేవ్ అధికారిక విడుదల ఆర్కైవ్ను ధృవీకరిస్తుంది, స్థానిక కాన్ఫిగరేషన్ను ధృవీకరిస్తుంది, ప్రత్యేకమైన లోకల్ హోస్ట్ SOCKS లిజనర్ను ప్రారంభిస్తుంది మరియు ఆ తర్వాత మాత్రమే ప్రాక్సీ రిజిస్ట్రీ అసైన్మెంట్ను వ్రాస్తుంది. విఫలమైన క్రియాశీలత మునుపటి నిర్వహించబడిన కాన్ఫిగరేషన్ మరియు ప్రాసెస్ని పునరుద్ధరిస్తుంది. `STORAGE_ENCRYPTION_KEY` అవసరం; మూల లింక్లు గుప్తీకరించబడ్డాయి.

నిర్వహించబడే ఫైల్లు `DATA_DIR/services/managed-proxy/` క్రింద ప్రత్యక్షంగా ఉంటాయి, TPROXY నుండి వేరుగా ఉంటాయి. ఎంచుకున్న కోర్కి ఒక యాజమాన్య ప్రక్రియ ఉంది, గరిష్టంగా 100 మంది శ్రోతలు. ఆటోస్టార్ట్ లేదా గ్లోబల్ రూటింగ్ డిఫాల్ట్ ఏదీ మార్చబడలేదు. విజయవంతమైన సేవ్ ఈ నిర్వహించబడే కోర్ కోసం మాత్రమే యాక్టివేషన్ను గుర్తుంచుకుంటుంది; అప్లికేషన్ స్టార్టప్ ఇప్పటికే ధృవీకరించబడిన బైనరీని ఉపయోగించి ప్రారంభించబడిన సేవ్ చేయబడిన కోర్లను పునరుద్ధరిస్తుంది, ఇది బూట్-టైమ్ డౌన్లోడ్ కాదు. స్పష్టమైన స్టాప్ ఆ యాక్టివేషన్ ఫ్లాగ్ను క్లియర్ చేస్తుంది. తప్పిపోయిన లేదా దెబ్బతిన్న బైనరీకి మూలాన్ని మళ్లీ సేవ్ చేయడం అవసరం. రిజిస్ట్రీ తొలగింపు స్థానికంగా మూలం మరియు శ్రోతలను తొలగిస్తుంది; నిర్వహించబడే అడ్డు వరుసల కోసం సాధారణ ఎండ్పాయింట్ సవరణలు తిరస్కరించబడతాయి కాబట్టి సేవ్ చేయబడిన మూలం దాని రూట్ చేయబడిన శ్రోత నుండి నిశ్శబ్దంగా డ్రిఫ్ట్ అవ్వదు.

| మూలం ఫార్మాట్                         | పాడే పెట్టె                                                                        | Xray                                                                               |
| ------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| VLESS, VMess, ట్రోజన్, షాడోసాక్స్ URI | మద్దతు గల మార్పిడి                                                                 | మద్దతు గల మార్పిడి                                                                 |

తెలియని వైర్ ఎంపికలు, అసురక్షిత TLS ఫ్లాగ్లు, బాహ్య ప్లగిన్లు, స్థానిక ఫైల్-పాత్ ఎంపికలు మరియు మద్దతు లేని కలయికలు నిశ్శబ్దంగా విస్మరించబడకుండా తిరస్కరించబడతాయి. స్థానిక వస్తువులు అవుట్బౌండ్ నిర్వచనాలు, పూర్తి-కోర్ కాన్ఫిగరేషన్లు కాదు; control/direct/bypass అవుట్బౌండ్లు ఆమోదించబడవు. WireGuard on sing-box 1.14 ఎండ్పాయింట్లను ఉపయోగిస్తుంది, కాబట్టి ఇది స్థానిక అవుట్బౌండ్గా అంగీకరించబడదు. ఇది ఆల్-ఫార్మాట్ కన్వర్టర్ కాదు; SSR, లెగసీ whole-base64 షాడోసాక్స్ లింక్లు, ఆర్బిట్రరీ క్లాష్ ఆబ్జెక్ట్లు మరియు టేబుల్లో లేని రవాణా వేరియంట్లకు విడిగా మద్దతు ఉన్న సోర్స్ ఫార్మాట్ అవసరం.

`/api/services/managed-proxy` ప్రమాణీకరించబడింది మరియు లూప్బ్యాక్-మాత్రమే: GET సవరించిన మెటాడేటాను జాబితా చేస్తుంది, POST `{core,name,sourceLink,id?,assignment?}` సేవ్ చేస్తుంది, PATCH `{core,action:"start"|"stop"}` ని అంగీకరిస్తుంది. హోస్ట్ యొక్క విశ్వసనీయ పీర్-స్టాంప్ పైప్లైన్ తప్పనిసరిగా ఉండాలి. స్థానిక కోర్ డయాగ్నస్టిక్స్ అణచివేయబడతాయి ఎందుకంటే అవి ఆధారాలను కలిగి ఉంటాయి; లైఫ్సైకిల్ ఈవెంట్లు సోర్స్ లింక్లు లేదా అప్స్ట్రీమ్ పేలోడ్లు లేకుండా ఇప్పటికే ఉన్న నిర్మాణాత్మక అప్లికేషన్ ఫైల్ లాగర్ను ఉపయోగిస్తాయి. సపోర్ట్ కోసం శానిటైజ్ చేసిన అప్లికేషన్ లాగ్లను మాత్రమే అటాచ్ చేయండి. అధికారిక సంస్కరణలు విడుదల-ఆస్తి SHA-256 మానిఫెస్ట్లతో సింగ్-బాక్స్ 1.14.3 మరియు Xray 26.3.27కి పిన్ చేయబడ్డాయి; భవిష్యత్ అప్డేట్లకు సంస్కరణను మరియు అన్ని ధృవీకరించబడిన డైజెస్ట్లను కలిపి మార్చడం అవసరం.

```
                               └──────────┘
```

స్థితులు `version_manager` DB పట్టికలో (`status` నిలువు వరుస) నిల్వ చేయబడతాయి మరియు
`ServiceSupervisor` ఇన్-మెమరీ స్థితిలో ప్రతిబింబించబడతాయి. నడుస్తున్న ప్రాసెస్కు
ఇన్-మెమరీ స్థితియే ప్రామాణికమైనది; బూట్ సమయంలో DB స్థితి శాశ్వత ఫాల్బ్యాక్గా ఉంటుంది.

### స్థితి పరివర్తనలు

| నుండి           | ఈవెంట్                                   | కు                         |
| --------------- | ---------------------------------------- | -------------------------- |
| `not_installed` | `install()` విజయవంతమవుతుంది              | `stopped`                  |
| `stopped`       | `start()` కాల్ చేయబడుతుంది               | `starting`                 |
| `starting`      | ఆరోగ్య తనిఖీ 200ను అందిస్తుంది           | `running`                  |
| `starting`      | ఆరోగ్యవంతం కాకముందే ప్రాసెస్ ముగుస్తుంది | `error`                    |
| `running`       | `stop()` కాల్ చేయబడుతుంది                | `stopping` → `stopped`     |
| `running`       | ప్రాసెస్ అనూహ్యంగా ముగుస్తుంది (< 5 s)   | `error` (వేగవంతమైన క్రాష్) |
| `running`       | ప్రాసెస్ అనూహ్యంగా ముగుస్తుంది (> 5 s)   | `error`                    |
| `error`         | `start()` కాల్ చేయబడుతుంది               | `starting`                 |
| ఏదైనా           | `stopping`లో ఉన్నప్పుడు `stop()`         | ఎటువంటి చర్య లేదు          |

### ఆపరేషన్ లాక్

`ServiceSupervisor`, అసింక్ ఆపరేషన్ లాక్ (`withLock()`) ద్వారా జీవితచక్ర
ఆపరేషన్లను వరుసక్రమంలో అమలు చేస్తుంది. ఒకే సూపర్వైజర్పై ఏకకాలంలో చేసే `start()`
కాల్స్ ఖచ్చితంగా ఒక స్పాన్కు దారితీస్తాయి; రెండవ కాలర్ వేచి ఉండి, ఇప్పటికే ఉన్న
స్థితిని తిరిగి అందుకుంటుంది. ఉదాహరణకు, ఆటో-స్టార్ట్ మరియు UI బటన్ ఒకేసారి
ట్రిగ్గర్ అయినప్పుడు ఇది రేస్ కండిషన్లను నివారిస్తుంది.

## 4. API సూచన

`/api/services/` కింద ఉన్న అన్ని మార్గాలు**LOCAL_ONLY** (లూప్బ్యాక్ మాత్రమే, హార్డ్ రూల్ #17). నాన్-లూప్బ్యాక్ అభ్యర్థనలు ప్రామాణీకరణ టోకెన్తో సంబంధం లేకుండా `403 LOCAL_ONLY` స్వీకరిస్తాయి.

### 4.1 9రూటర్ ముగింపు పాయింట్లు (11 మార్గాలు)

#### `POST /api/services/9router/install`

npm నుండి 9 రూటర్ని ఇన్స్టాల్ చేయండి. `DATA_DIR/services/9router/` దాని స్వంత `package.json` మరియు `node_modules/` తో సృష్టిస్తుంది. OmniRoute స్వంత డెప్స్తో వైరుధ్యం లేదు.

**శరీరాన్ని అభ్యర్థించండి** (అన్నీ ఐచ్ఛికం):

```json
{ "version": "latest" }
```

| ఫీల్డ్    | టైప్ చేయండి | డిఫాల్ట్   | వివరణ                                              |
| --------- | ----------- | ---------- | -------------------------------------------------- |
| `version` | `string`    | `"latest"` | ఇన్స్టాల్ చేయడానికి npm వెర్షన్ ట్యాగ్ లేదా semver |

**ప్రతిస్పందనలు:**

| స్థితి | వివరణ                                                            |
| ------ | ---------------------------------------------------------------- |
| `200`  | `{ ok: true, installedVersion: "x.y.z", path: "..." }`           |
| `400`  | చెల్లని అభ్యర్థన విషయం (Zod ధ్రువీకరణ వైఫల్యం)                   |
| `409`  | ఇప్పటికే ఇన్స్టాల్ చేస్తోంది (లాక్ హోల్డ్)                       |
| `500`  | npm ఇన్స్టాల్ విఫలమైంది — స్నేహపూర్వక లోపం కోసం `message` చూడండి |

**గమనికలు:** `execFile('npm', [...])` — నో షెల్, ఇంటర్పోలేషన్ లేదు (హార్డ్ రూల్ #13). EACCES లోపాలు స్నేహపూర్వక సందేశాలుగా కనిపిస్తాయి.

#### `POST /api/services/9router/start`

9 రూటర్ని ప్రారంభించండి. ఇప్పటికే రిజిస్టర్ చేయకుంటే సూపర్వైజర్ను నమోదు చేస్తుంది, ఆపై `supervisor.start()` కాల్ చేస్తుంది. ఇప్పటికే అమలులో ఉన్నప్పుడు Idempotent.

**అభ్యర్థన శరీరం:** ఏదీ లేదు

**ప్రతిస్పందనలు:**

| స్థితి | వివరణ                                                   |
| ------ | ------------------------------------------------------- |

| `503`  | ప్రారంభం విఫలమైంది (ప్రాసెస్ లోపం — `lastError` చూడండి) |

**ServiceStatus స్కీమా:**

```json
{
  "tool": "9router",
  "state": "running",
  "pid": 12345,
  "port": 20130,
  "health": "healthy",
  "startedAt": "2026-05-25T10:00:00.000Z",
  "lastError": null
}
```

### 4.2 CLIProxyAPI ముగింపు పాయింట్లు (10 మార్గాలు)

CLIProxyAPI 9Router మైనస్ `rotate-key`, ప్లస్ `accounts`, `provider-expose` మరియు `auto-restart-adopted` వలె అదే ముగింపు ఆకారాన్ని కలిగి ఉంది. ఇది ఇప్పుడు స్పాన్లో ఇంజెక్ట్ చేయబడిన డెడికేటెడ్ డేటా-ప్లేన్ API కీని అందుకుంటుంది ( `bootstrap.ts` లో`needsApiKey: true`, మోడల్ సింక్ కోసం ఉపయోగించబడుతుంది); `status` లో తక్కువ ఫీల్డ్లు ఉన్నాయి.

| పద్ధతి | మార్గం                              | వివరణ                                        |
| ------ | ----------------------------------- | -------------------------------------------- |
| `POST` | `/api/services/cliproxy/install`    | npm నుండి CLIProxyAPI ఇన్స్టాల్ చేయండి       |
| `POST` | `/api/services/cliproxy/start`      | CLIProxyAPI ప్రారంభించండి                    |
| `POST` | `/api/services/cliproxy/stop`       | CLIProxyAPI ఆపు                              |
| `POST` | `/api/services/cliproxy/restart`    | CLIProxyAPI ని పునఃప్రారంభించండి             |
| `POST` | `/api/services/cliproxy/update`     | కొత్త వెర్షన్కి అప్డేట్ చేయండి               |
| `GET`  | `/api/services/cliproxy/status`     | ప్రత్యక్ష + DB స్థితి ( `apiKeyMasked` లేదు) |
| `POST` | `/api/services/cliproxy/auto-start` | స్వీయ-ప్రారంభాన్ని టోగుల్ చేయండి             |

భాగస్వామ్య `GET /api/services/{name}/logs` ఎండ్పాయింట్ (§4.1 చూడండి) `[name]` డైనమిక్ సెగ్మెంట్ని ఉపయోగించి మొత్తం నాలుగు సేవలకు పని చేస్తుంది.

**జత చేయడం:** open-wa అనధికారికమైనది మరియు WhatsApp — తో అనుబంధించబడనిది కనెక్ట్ చేయబడిన నంబర్ WhatsApp యొక్క స్వంత ఆటోమేషన్ గుర్తింపు నుండి నిషేధ ప్రమాదాన్ని కలిగి ఉంటుంది. మొదటి ప్రారంభంలో, జత చేసే QR కోడ్ stdoutకి ముద్రించబడుతుంది మరియు ఇప్పటికే ఉన్న లాగ్ల panel/SSE స్ట్రీమ్ — ద్వారా కనిపిస్తుంది, ఈ ఏకీకరణలో ఇంకా ప్రత్యేకమైన QR-చిత్రం ముగింపు స్థానం లేదు.

**TPROXY వైరింగ్:** `ensureSingboxTproxy()` (`src/mitm/tproxy/setup.ts`) `config.json` వ్రాస్తుంది మరియు `applyTproxy()` TPROXY ఫైర్వాల్ నియమాలను ఇన్స్టాల్ చేసే ముందు సూపర్వైజర్ను ప్రారంభిస్తుంది. సూపర్వైజర్ తప్పిపోయినా లేదా `running` చేరుకోవడంలో విఫలమైతే, అది ఇప్పుడు ఎర్రర్ లెవెల్లో లాగ్ అవుతుంది (నిశ్శబ్దంగా వైఫల్యాన్ని మింగడం కంటే) కాబట్టి ఆపరేటర్ TPROXY నియమాలు తమ వెనుక పని చేసే శ్రోతలు లేకుండా వర్తింపజేసినట్లు చెప్పగలరు.

### 4.9 రివర్స్ ప్రాక్సీ (9 రూటర్ డాష్బోర్డ్ పొందుపరచబడింది)

డాష్బోర్డ్ అంతర్గత రివర్స్ ప్రాక్సీ ద్వారా 9Router వెబ్ UI iframe లోపల పొందుపరిచింది:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

ఈ ప్రాక్సీ:

- అభ్యర్థనను `http://127.0.0.1:{port}/{path}` కి ఫార్వార్డ్ చేయండి (లూప్బ్యాక్ మాత్రమే)
- స్ట్రిప్స్ ఇన్కమింగ్ `cookie` మరియు `authorization` హెడర్లు ( OmniRoute సెషన్ లీకేజీ లేదు)
- 9Router ప్రమాణీకరణ కోసం `Authorization: Bearer {apiKey}` ఇంజెక్ట్ చేస్తుంది
- ప్రతిస్పందన నుండి `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` స్ట్రిప్స్
- `<base href>` ఇంజెక్ట్ చేయడానికి మరియు సంపూర్ణ మార్గాలను సాధారణీకరించడానికి HTML ప్రతిస్పందనలను తిరిగి వ్రాస్తుంది (`/foo` → `/dashboard/.../embed/foo`)

ఎంబెడెడ్ డాష్బోర్డ్ కోసంWebSocket అప్గ్రేడ్లు డెడికేటెడ్ పోర్ట్లో కంపానియన్ సర్వర్ ద్వారా నిర్వహించబడతాయి ( `src/lib/services/embedWsProxy.ts` చూడండి).

**భద్రత:** పొందుపరిచిన ప్రాక్సీ మార్గాలు `LOCAL_ONLY_API_PREFIXES` క్రింద వర్గీకరించబడ్డాయి మరియు లూప్బ్యాక్ నుండి మాత్రమే చేరుకోవచ్చు. Cloudflare/Ngrok టన్నెల్ ద్వారా JWT పొందిన దాడి చేసే వ్యక్తి ఎంబెడెడ్ సేవలకు ప్రాక్సీ చేయలేరు.

## 5. భద్రత

### LOCAL_ONLY అమలు (కఠిన నియమం #17)

`/api/services/` మరియు `/dashboard/providers/services/*/embed/` కింద ఉన్న అన్ని రూట్లు
`src/server/authz/routeGuard.ts`లో LOCAL_ONLYగా వర్గీకరించబడ్డాయి. ఏదైనా auth శాఖకు
ముందు loopback తనిఖీ ఎల్లప్పుడూ అమలవుతుంది:

```
అభ్యర్థన వస్తుంది
  → isLocalOnlyPath(path)?
      → non-loopback → 403 LOCAL_ONLY (ఎల్లప్పుడూ, auth తనిఖీకి ముందు)
      → loopback     → సాధారణ authకు కొనసాగుతుంది
```

ఇది లీకైన JWT (ఉదా., tunnel ద్వారా) `npm install`ను ట్రిగర్ చేయడం లేదా
ప్రాసెస్లను ప్రారంభించడాన్ని నిరోధిస్తుంది. పూర్తి tier matrix కోసం
`docs/security/ROUTE_GUARD_TIERS.md` చూడండి.

### API కీ ఇంజెక్షన్

9Router మరియు Muxలకు వాటి స్వంత HTTP endpointల కోసం API కీ/bearer token అవసరం.
OmniRoute:

1. సేవకు ప్రత్యేకమైన prefixతో (`nr_` 9Router కోసం, `mx_` Mux కోసం)
   `crypto.randomBytes(32).toString("base64url")` ద్వారా ఒక కీని రూపొందిస్తుంది.
2. AES-256-GCMను ఉపయోగించి నిల్వలో ఉన్నప్పుడు దాన్ని ఎన్క్రిప్ట్ చేస్తుంది (provider credentialల కోసం ఉపయోగించే అదే cipher).
3. spawn సమయంలో దాన్ని డీక్రిప్ట్ చేసి environment variableగా ఇంజెక్ట్ చేస్తుంది —
   9Router కోసం `NINEROUTER_API_KEY`, Mux కోసం `MUX_SERVER_AUTH_TOKEN` (CLI
   flagగా ఎప్పుడూ పంపదు, కాబట్టి token `ps`/process listingలలో ఎప్పుడూ కనిపించదు).
4. ఏ HTTP responseలోనూ plaintext కీని ఎప్పుడూ తిరిగి ఇవ్వదు.

CLIProxyAPI spawn సమయంలో ఇంజెక్ట్ చేయబడిన ప్రత్యేక data-plane కీని అందుకుంటుంది
(`needsApiKey: true` — adapterకు వ్యతిరేకంగా model sync కోసం ఉపయోగించబడుతుంది).

### SSRF రక్షణ

reverse HTTP proxy (`/dashboard/.../embed/[...path]`) కేవలం
`http://127.0.0.1:{port}`కు మాత్రమే forward చేసేలా hardcode చేయబడింది. ఇది
non-loopback destinationలకు redirectలను ఎప్పుడూ అనుసరించదు. loopback పరిధి వెలుపలికి
resolve అయ్యే ఏ upstream URLనైనా తిరస్కరించడానికి `ssrf-req-filter` library ఉపయోగించబడుతుంది.

### Shell భద్రత (కఠిన నియమం #13)

`npm install` అనేది `execFile('npm', ['install', pkg, '--prefix', dir])` ద్వారా అమలు చేయబడుతుంది —
template literalలు లేవు, shell లేదు, command stringలో external pathల interpolation లేదు.
Runtime విలువలు (portలు, API కీలు) child యొక్క `env` object ద్వారా పంపబడతాయి.

### Error శుద్ధీకరణ (కఠిన నియమం #12)

`/api/services/*` నుండి వచ్చే అన్ని error responseలు `buildErrorBody()` లేదా
`sanitizeErrorMessage()` ద్వారా వెళ్తాయి. ముడి `err.stack` మరియు `err.message`లను
callerకు యథాతథంగా ఎప్పుడూ తిరిగి ఇవ్వరు.

## 6. కొత్త embedded serviceను జోడించడం

ఈ 8 దశలను అనుసరించండి. ప్రామాణిక సూచనగా `src/lib/services/installers/`
మరియు `src/app/api/services/`లోని ప్రస్తుత implementationలను చదవండి.

### దశ 1 — installerను సృష్టించండి

`ninerouter.ts`ను నమూనాగా తీసుకొని `src/lib/services/installers/{name}.ts`ను సృష్టించండి:

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // ఖాళీ portను ఎంచుకోండి

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }
export function resolveSpawnArgs(apiKey: string, port: number): SpawnArgs { ... }
export async function getInstalledVersion(): Promise<string | null> { ... }
export async function getLatestVersion(): Promise<string | null> { ... }
```

`installers/utils.ts` నుండి `runNpm(['install', NAME_PACKAGE, '--prefix', dir])`ను
ఉపయోగించండి — `execSync` లేదా shell interpolationను ఎప్పుడూ ఉపయోగించవద్దు.

### దశ 2 — bootstrapలో నమోదు చేయండి

`src/lib/services/bootstrap.ts`లోని `SERVICES` arrayకు ఒక `ServiceEntry`ని జోడించండి:

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // API కీ అవసరం లేకపోతే false
}
```

`cfg.tool === "myservice"`ను నిర్వహించేలా `buildSpawnArgsFactory()`ను విస్తరించండి.

#### Pluggable provider-plugin ఒప్పందం (దశ 1, #7333)

`src/lib/services/providerPlugins/` ఒక backend యొక్క `bootstrap.ts` `ServiceEntry`
fieldలను మరియు `serviceBackends.ts` manifest-template fieldలను ఒక objectలో ప్యాకేజ్ చేసే
`ServiceProviderPlugin` ఒప్పందాన్ని ప్రవేశపెడుతుంది. దీని వల్ల ఒకే backend యొక్క ఆకృతిని
పరస్పర సంబంధం లేని రెండు వేర్వేరు fileలలో విడిగా వ్యక్తపరచాల్సిన అవసరం ఉండదు. ఇది వ్రాసే
సమయానికి **`9router` మాత్రమే migrate చేయబడింది** — `bootstrap.ts` తన `SERVICES[]`
entryని `getServiceProviderPlugin("9router")`
(`src/lib/services/providerPlugins/registry.ts`) నుండి పొందుతుంది; plugin ఎప్పుడైనా
లేకపోతే startup errorను throw చేస్తుంది. `cliproxy`, `mux`, మరియు `bifrost`లు
ఇప్పటికే ఉన్న inline `SERVICES[]` literalలపై ఎలాంటి మార్పులు లేకుండా కొనసాగుతాయి.

`open-sse/config/providerPluginManifest.ts`లో కూడా
`SERVICE_BACKEND_MANIFEST_TEMPLATE` entry నుండి సక్రమంగా రూపొందించిన
`ProviderPluginManifestEntry`ని నిర్మించే అదనపు
`createServiceBackendManifestEntry(pluginId, template)` helper జోడించబడింది — ఇది
ఇంకా ఏ live request pathకూ అనుసంధానించబడలేదు (`generateProviderPluginManifestFromRegistry()`
కూ కాదు, `/v1/providers/[provider]/models`కూ కాదు); రెండవ backend కోసం ఈ ఒప్పందం
నిరూపితమైన తర్వాత అది follow-upగా మిగిలి ఉంటుంది.

issue #7333 కింద ట్రాక్ చేయబడుతున్న follow-up PRలకు వాయిదా వేసిన అంశాలు:
`cliproxyapi`ని అదే registry ద్వారా migrate చేయడం, `mux`/`bifrost`ను
`ServiceBackendPluginId` unionలోకి సాధారణీకరించడం, executor-routing ప్రత్యేక నిర్వహణను
(`open-sse/executors/index.ts`, `open-sse/handlers/chatCore/executorProxy.ts`) plugin
ఒప్పందంలో కలపడం, మరియు `createServiceBackendManifestEntry()`ను live
manifest/models code pathకు అనుసంధానించడం.

### దశ 4 — 7 API endpointలను సృష్టించండి

`src/app/api/services/{name}/` కింద:

అవసరం లేదు.

### దశ 5 — LOCAL_ONLY_API_PREFIXESకు జోడించండి

`src/server/authz/routeGuard.ts`లో, `/api/services/` ఇప్పటికే జాబితాలో ఉందో లేదో ధృవీకరించండి.
మీరు కొత్త ప్రిఫిక్స్ను ప్రవేశపెడితే (ఉదా., `/api/tools/`), దాన్ని
`LOCAL_ONLY_API_PREFIXES`కు, అలాగే అది ప్రాసెస్లను ప్రారంభిస్తే `SPAWN_CAPABLE_PREFIXES`కు కూడా జోడించండి.
`tests/unit/authz/routeGuard.test.ts`లో ఒక టెస్ట్ను జోడించండి.

### దశ 7 — ప్రొవైడర్ ఎంట్రీని జోడించండి (సర్వీస్ ఒక రూటింగ్ లక్ష్యం అయితే)

ఎంబెడెడ్ సర్వీస్ OpenAI-అనుకూలమైన `/v1/chat/completions` ఎండ్పాయింట్ను అందిస్తే:

1. `src/shared/constants/providers.ts`లో `isEmbeddedService: true`తో ఒక ప్రొవైడర్ ఎంట్రీని జోడించండి.
2. `BaseExecutor`ను విస్తరించే `open-sse/executors/{name}.ts`ను సృష్టించండి. ప్రతి రిక్వెస్ట్కు పోర్ట్ మరియు
   API కీని మళ్లీ పొందండి (కన్స్ట్రక్టర్లో ఎప్పుడూ క్యాష్ చేయవద్దు). సూపర్వైజర్ స్థితి `"running"`గా లేనప్పుడు
   `503 service_not_running` రెస్పాన్స్ను తిరిగి ఇవ్వండి.
3. సర్వీస్ ప్రిఫిక్స్తో (ఉదా., `myservice/sub/model`) `open-sse/config/providerRegistry.ts`లో మోడల్లను
   నమోదు చేయండి. `modelSync.ts` వాటిని అప్డేట్గా ఉంచుతుంది.

### దశ 8 — డాక్యుమెంట్ చేసి టెస్ట్ చేయండి

1. `docs/frameworks/EMBEDDED-SERVICES.md`ను (ఈ ఫైల్) అప్డేట్ చేయండి — §1లోని
   పట్టికకు సర్వీస్ను, §4కు ఏవైనా కొత్త ఎండ్పాయింట్లను జోడించండి.
2. `tests/unit/services/`లో యూనిట్ టెస్ట్లను జోడించండి (లైఫ్సైకిల్, ఇన్స్టాలర్, API ఆకృతి).

## 7. సమస్య పరిష్కారం

### సర్వీస్ ప్రారంభం కావడం లేదు

**లక్షణాలు:** Start బటన్ 503ని అందిస్తుంది, స్థితి `"error"` లేదా `"starting"`గానే ఉంటుంది.

**తనిఖీ జాబితా:**

1. `GET /api/services/{name}/logs`ను (లేదా డాష్బోర్డ్లోని Logs ప్యానెల్ను) తనిఖీ చేయండి. `Error: ENOENT`, `address already in use`, లేదా `Cannot find module` వంటి లైన్ల కోసం చూడండి.
2. `npm` PATHలో ఉందని ధృవీకరించండి: OmniRouteను అమలు చేసే అదే వినియోగదారు ఖాతా నుండి `which npm`ను అమలు చేయండి.
3. సర్వీస్ ఇన్స్టాల్ అయిందని ధృవీకరించండి: `installedVersion` కోసం `GET /api/services/{name}/status`ను తనిఖీ చేయండి. అది `null` అయితే, ముందుగా ఇన్స్టాల్ను అమలు చేయండి.
4. `DATA_DIR/services/{name}/node_modules/` ఉనికిలో ఉందని, ఖాళీగా లేదని తనిఖీ చేయండి.
5. శుద్ధీకరించిన నిష్క్రమణ కారణం కోసం స్థితి ప్రతిస్పందనలోని `lastError` ఫీల్డ్ను తనిఖీ చేయండి.

---

### కోల్డ్ స్టార్ట్ నెమ్మదిగా ఉంది (`running` స్థితిని చేరుకోవడానికి > 10 s)

**లక్షణాలు:** `"running"` లేదా `"error"`కు మారడానికి ముందు స్థితి చాలా సేపు `"starting"`గానే ఉంటుంది.

**వివరణ:** 9Router కోల్డ్ స్టార్ట్లో పెద్ద డిపెండెన్సీ ట్రీలను (DNS, టన్నెల్, MITM మాడ్యూల్లు) ఇంపోర్ట్ చేయడం ఉంటుంది. డిఫాల్ట్ హెల్త్ విరామం 2 s; సూపర్వైజర్ టైమ్అవుట్గా ప్రకటించే ముందు 3 ప్రయత్నాలు చేస్తుంది (అయితే పోలింగ్ను కొనసాగిస్తుంది).

**పరిష్కారం:** `healthIntervalMs` మరియు `waitForHealthy` టైమ్అవుట్ (`healthIntervalMs * 3`)లను `bootstrap.ts`లో కాన్ఫిగర్ చేయవచ్చు. ప్రారంభం కావడానికి ఎక్కువ సమయం పట్టే సర్వీస్ల కోసం, `healthIntervalMs`ను 5000కు మరియు `stopTimeoutMs`ను 30 000కు పెంచండి.

---

### పోర్ట్ ఘర్షణ (`EADDRINUSE`)

**లక్షణాలు:** లాగ్లు `address already in use :::20130`ను చూపుతాయి.

**కారణాలు:**

- మరొక ప్రాసెస్ ఇప్పటికే పోర్ట్ 20130ను ఉపయోగిస్తోంది.
- మునుపటి 9Router ప్రాసెస్ పూర్తిగా ఆపబడలేదు (జాంబీ PID).

**పరిష్కారం:**

1. `.env`లోని `NINEROUTER_PORT` ఎన్విరాన్మెంట్ వేరియబుల్ ద్వారా డిఫాల్ట్ పోర్ట్ను మార్చండి.
2. ఘర్షణకు కారణమవుతున్న ప్రాసెస్ను కనుగొని నిలిపివేయండి: `lsof -ti :20130 | xargs kill -9`.
3. `port` ఫీల్డ్ ద్వారా `bootstrap.ts`లో ప్రతి సర్వీస్కు పోర్ట్ను కాన్ఫిగర్ చేయవచ్చు.

**గమనిక:** OmniRoute డిఫాల్ట్ పోర్ట్ 20128తో ఘర్షణను నివారించడానికి 9Router ప్రత్యేకంగా పోర్ట్ 20130ను డిఫాల్ట్గా ఉపయోగిస్తుంది.

---

### ఇన్స్టాల్ సమయంలో అనుమతి నిరాకరించబడింది (EACCES)

**లక్షణాలు:** ఇన్స్టాల్ 500ని అందిస్తుంది, లాగ్లు `EACCES` లేదా `permission denied`ను చూపుతాయి.

**కారణాలు:**

- `DATA_DIR` లేదా దాని పేరెంట్ డైరెక్టరీలో OmniRoute ప్రాసెస్కు రైట్ అనుమతి లేదు.
- మ్యాప్ చేసిన వాల్యూమ్కు రైట్ యాక్సెస్ లేకుండా Docker rootlessలో అమలు చేయడం.

**పరిష్కారం:**

1. `DATA_DIR`ను తనిఖీ చేయండి (డిఫాల్ట్: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. OmniRoute ప్రాసెస్ వినియోగదారు ఆ డైరెక్టరీకి యజమాని అని నిర్ధారించండి: `chown -R $USER ~/.omniroute/`
3. Dockerలో, కంటైనర్ వినియోగదారుకు వాల్యూమ్ మౌంట్పై సరైన అనుమతులు ఉన్నాయని నిర్ధారించండి.

---

### అప్డేట్ విఫలమవుతుంది (`npm install` టైమ్అవుట్ లేదా నెట్వర్క్ లోపం)

**లక్షణాలు:** అప్డేట్ `InstallError`తో 500ని అందిస్తుంది, లాగ్లు నెట్వర్క్ టైమ్అవుట్ను చూపుతాయి.

**తనిఖీ జాబితా:**

1. npm రిజిస్ట్రీని చేరుకోగలమని నిర్ధారించండి: `npm ping`.
2. కార్పొరేట్ ప్రాక్సీ ఉందేమో తనిఖీ చేయండి: `npm config get proxy`, `npm config get https-proxy`.
3. ఇన్స్టాల్ను మాన్యువల్గా ప్రయత్నించండి: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. ఎయిర్-గ్యాప్ వెనుక ఉంటే, tarballను ముందుగానే డౌన్లోడ్ చేసి `npm install /path/to/tarball.tgz`ను ఉపయోగించండి.

### ప్రారంభించిన వెంటనే సర్వీస్ `"error"` స్థితిని చూపుతుంది (వేగవంతమైన క్రాష్)

**లక్షణాలు:** స్థితి 5 సెకన్లలోపు `"starting"` నుండి `"error"`కు మారుతుంది. `lastError` `"Fast crash (exited with code 1)"`ను చూపుతుంది.

**తనిఖీ జాబితా:**

1. పూర్తి లాగ్ టెయిల్ను చదవండి: `GET /api/services/{name}/logs?tail=500`.
2. సాధారణ కారణం: సర్వీస్ ఆశించే ఎన్విరాన్మెంట్ వేరియబుల్లు లేకపోవడం.
3. 9Router కోసం: స్పాన్ సమయంలో పాస్ చేసిన ఎన్విరాన్మెంట్లో `NINEROUTER_DISABLE_MITM=true` మరియు `NINEROUTER_DISABLE_TUNNEL=true` ఉన్నాయని ధృవీకరించండి (`installers/ninerouter.ts`లోని `resolveSpawnArgs`ను చూడండి).

## 8. తరచుగా అడిగే ప్రశ్నలు

**ప్ర: ఎంబెడెడ్ సర్వీస్ల ఎండ్పాయింట్లను లూప్బ్యాక్ కాని క్లయింట్లకు అందుబాటులో ఉంచవచ్చా?**

లేదు. LOCAL_ONLY టైర్ ఉద్దేశపూర్వకంగా అమలు చేయబడింది (కఠిన నియమం #17). `npm install`ను అమలు చేయగల లేదా `node` ప్రాసెస్లను ప్రారంభించగల రూట్లు లూప్బ్యాక్ కాని ట్రాఫిక్కు అందుబాటులో ఉండకూడదు. లేకపోతే, టన్నెల్ (Cloudflare, Ngrok, Tailscale) ద్వారా లీకైన JWT ఏవైనా ప్రాసెస్లను ప్రారంభించడానికి అనుమతిస్తుంది. `/api/services/`కు మినహాయింపు ఎంపిక ఏదీ లేదు — `/api/mcp/`కు భిన్నంగా, ఇది manage-scope బైపాస్ జాబితా నుండి మినహాయించబడింది. `docs/security/ROUTE_GUARD_TIERS.md` చూడండి.

---

**ప్ర: ప్రొడక్షన్/క్లౌడ్ డిప్లాయ్మెంట్లలో 9Router మరియు CLIProxyAPI అందుబాటులో ఉంటాయా?**

అవును. రెండు సర్వీస్లు OmniRoute మాదిరిగానే local-first నమూనాను అనుసరిస్తాయి. అవి ఒకే మెషీన్పై రన్ అవుతూ, లూప్బ్యాక్ ద్వారా కమ్యూనికేట్ చేస్తాయి. ఇక్కడ "ప్రొడక్షన్" అంటే OmniRoute డిప్లాయ్ చేయబడిన VPS లేదా స్థానిక సర్వర్; రిమోట్ క్లౌడ్ ప్రొవైడర్ కాదు.

---

**ప్ర: సూపర్వైజర్ను ఎలా డీబగ్ చేయాలి?**

1. SSE లాగ్ స్ట్రీమ్ను నిరంతరం వీక్షించండి: `curl -N http://localhost:20128/api/services/9router/logs`.
2. OmniRoute యొక్క pino అవుట్పుట్లో `service:supervisor` నేమ్స్పేస్ ఆధారంగా ఫిల్టర్ చేసిన స్ట్రక్చర్డ్ లాగ్లను తనిఖీ చేయండి.
3. DB రోను పరిశీలించండి: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. ప్రస్తుత లైవ్ స్థితి, PID, హెల్త్ మరియు `lastError`ను ఒకే కాల్లో చూడటానికి `GET /api/services/9router/status`ను ఉపయోగించండి.

---

**ప్ర: సూపర్వైజర్ `health: "degraded"` లేదా `health: "unknown"` అని చూపుతోంది, కానీ స్థితి `"running"`గా ఉంది. ఇది సమస్యేనా?**

`"degraded"` అంటే హెల్త్ ప్రోబ్ 200 కాని ప్రతిస్పందనను ఇచ్చిందని అర్థం. `"unknown"` అంటే ఇంకా ఏ ప్రోబ్ కూడా పూర్తికాలేదని అర్థం (మొదటి పోల్తో రేస్). స్టార్టప్ సమయంలో రెండూ తాత్కాలిక స్థితులే. `"running"` అయిన తర్వాత `healthIntervalMs * 3` ms కంటే ఎక్కువసేపు హెల్త్ `"degraded"`గానే ఉంటే, ఎంబెడెడ్ సర్వీస్ రన్ అవుతోంది కానీ దాని HTTP API ప్రతిస్పందించడం లేదు. స్టేటస్ ప్రతిస్పందనలోని పోర్ట్ సరైనదో, సర్వీస్ నిజంగా ఆ పోర్ట్పై లిసన్ చేస్తోందో తనిఖీ చేయండి.

---

**ప్ర: పూర్తిగా రీస్టార్ట్ చేయకుండానే 9Router API కీని మార్చవచ్చా?**

లేదు. స్పాన్ సమయంలో API కీ ఒక ఎన్విరాన్మెంట్ వేరియబుల్ ద్వారా 9Routerకు పంపబడుతుంది. రన్ అవుతున్న ప్రాసెస్లో ఎన్విరాన్మెంట్ వేరియబుల్లను మార్చలేరు. కొత్త కీని వర్తింపజేయడానికి `POST .../rotate-key` ఆటోమేటిక్గా సర్వీస్ను ఆపి, తిరిగి ప్రారంభిస్తుంది. కీ రొటేషన్ సర్వీస్ యొక్క `stopTimeoutMs` (డిఫాల్ట్గా 15 s)తో పాటు దాని స్టార్టప్ సమయం లోపల అమల్లోకి వస్తుంది.

---

**ప్ర: రింగ్ బఫర్ పరిమితి ఎంత, అది నిండినప్పుడు ఏమవుతుంది?**

ప్రతి సర్వీస్కు ప్రత్యేకంగా 5 MB రింగ్ బఫర్ ఉంటుంది. బఫర్ నిండినప్పుడు, కొత్త లాగ్ లైన్లకు స్థలం కల్పించడానికి అత్యంత పాత లాగ్ లైన్లు తొలగించబడతాయి. SSE `snapshot` ఈవెంట్ `tail` పరిమితిలోని అత్యంత ఇటీవలి లైన్లను అందిస్తుంది. DB రోలో `logsBufferPath` సెట్ చేయకపోతే, లాగ్లు డిస్క్లో నిల్వ చేయబడవు.
