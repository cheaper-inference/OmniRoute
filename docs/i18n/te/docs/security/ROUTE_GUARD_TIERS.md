## అవలోకనం

అన్ని OmniRoute నిర్వహణ API రూట్లు మూడు రక్షణ స్థాయిలలో ఒకదానిగా వర్గీకరించబడతాయి. వర్గీకరణ స్థిరంగా ఉంటుంది, `src/server/authz/routeGuard.ts`లో నిర్వచించబడుతుంది, అలాగే ఇతర ఏ auth శాఖ అమలవడానికి ముందే మూల్యాంకనం చేయబడుతుంది.

## శ్రేణులు

### టైర్ 1 — LOCAL_ONLY

**దీని ద్వారా అమలు చేయబడింది:** `isLocalOnlyPath(path)` → లూప్బ్యాక్ హోస్ట్ చెక్** బైపాస్:** డిఫాల్ట్గా ఏదీ లేదు. అభ్యర్థన `manage` స్కోప్తో చెల్లుబాటు అయ్యే API కీని కలిగి ఉన్నప్పుడు `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` లోని మార్గాల కోసం ఇరుకైన కార్వ్-అవుట్ ( [మేనేజ్-స్కోప్ కార్వ్-అవుట్](#manage-scope-carve-out) చూడండి).

ఈ మార్గాలు చైల్డ్ ప్రాసెస్లకు దారితీస్తాయి లేదా రన్టైమ్ కోడ్ని అమలు చేస్తాయి. నాన్-లూప్బ్యాక్ ట్రాఫిక్కు వాటిని బహిర్గతం చేయడం వలన చెల్లుబాటు అయ్యే JWT (ఉదా, Cloudflared/Ngrok సొరంగం ద్వారా) పొందిన దాడి చేసే వ్యక్తి — తెలిసిన CVE తరగతి ( [GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj) ) స్పాన్నింగ్ ప్రక్రియను ట్రిగ్గర్ చేయడానికి అనుమతిస్తుంది.

**GHSA-fhh6-4qxv-rpqj అంటే ఏమిటి (దాడి తరగతి):** management/agent సర్వర్ ఉపప్రాసెస్ను ప్రారంభించే ముగింపు బిందువును బహిర్గతం చేస్తుంది (`npm install`, `node`, బ్రౌజర్, ప్రాక్సీ, `git`, `tar`, …). ఆ ఎండ్పాయింట్ ఆఫ్-హోస్ట్ — నుండి చేరుకోగలిగితే, ఆపరేటర్ nginx/Cloudflare/Tailscale టన్నెల్ వెనుక OmniRoute ఉంచి, ఒక JWT లీక్ చేయబడి ఉంటే, లేదా auth తప్పుగా కాన్ఫిగర్ చేయబడి — దాడి చేసే వ్యక్తి " API కి కాల్ చేయి"ని "హోస్ట్లో కమాండ్ను అమలు చేయండి" (రిమోట్ కోడ్ అమలు)గా మారుస్తాడు. OmniRoute దీన్ని అమలు చేయడం ద్వారా మూసివేస్తుంది** లూప్బ్యాక్ హోస్ట్ ఏదైనా ప్రామాణీకరణ తనిఖీకి ముందు బేషరతుగా తనిఖీ చేయండి** , స్పాన్-సామర్థ్యం గల ప్రతి మార్గంలో: సొరంగం మీదుగా లీక్ అయిన టోకెన్ ఇప్పటికీ స్పాన్ను చేరుకోలేదు.

**పూర్తి LOCAL_ONLY సెట్.** అధికారిక మూలం `src/server/authz/routeGuard.ts` లో `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ; దిగువ పట్టిక ప్రస్తుత స్థితిని ప్రతిబింబిస్తుంది. `check-route-guard-membership` గేట్ స్పాన్-సామర్థ్యం గల ప్రిఫిక్స్ల క్రింద ప్రతి `route.ts` గణిస్తుంది మరియు ఏదైనా స్థానికంగా మాత్రమే వర్గీకరించబడకపోతే CI విఫలమవుతుంది.

**ఉల్లంఘనపై ప్రతిస్పందన:** `403 LOCAL_ONLY`

#### నిర్వహణ-స్కోప్ కార్వే-అవుట్

మెటాడేటా `manage` స్కోప్ (లేదా `admin`) కలిగి ఉన్న `Authorization: Bearer <api-key>` ని అభ్యర్థన కలిగి ఉంటే మాత్రమే LOCAL_ONLY పాత్ల MAY యొక్క ఉపసమితి కూడా నాన్-లూప్బ్యాక్ నుండి యాక్సెస్ చేయబడుతుంది. కార్వ్-అవుట్ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ద్వారా ప్రతి-పాత్కు స్పష్టంగా గేట్ చేయబడింది కాబట్టి ఏదైనా కొత్త LOCAL_ONLY పాత్కు డిఫాల్ట్ స్ట్రిక్ట్-లూప్బ్యాక్గా ఉంటుంది. నాన్-మేనేజ్ కీలతో ప్రామాణీకరించని అభ్యర్థనలు మరియు అభ్యర్థనలు ఇప్పటికీ `403 LOCAL_ONLY` తో తిరస్కరించబడ్డాయి.

నేడు బైపాస్ చేయదగిన ఉపసర్గ `/api/mcp/` మాత్రమే. `/api/cli-tools/runtime/` మరియు `/api/services/` ఉద్దేశపూర్వకంగా మినహాయించబడ్డాయి ఎందుకంటే అవి ఏకపక్ష సబ్ప్రాసెస్లను (`npm install`, `node`) పుట్టించగలవు, ఇది LOCAL_ONLY టైర్ని నిరోధించడానికి ఉన్న ఖచ్చితమైన CVE తరగతి.

**#7895 — `mcp:connect` ఇరుకైన పరిధి:** `/api/mcp/` కార్వ్-అవుట్ ALSO ఇరుకైన `mcp:connect` స్కోప్ (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`)ని కలిగి ఉన్న బేరర్ కీని అంగీకరిస్తుంది, `src/server/authz/policies/management.ts` లో `hasMcpConnectOrManageScope()` ద్వారా తనిఖీ చేయబడుతుంది. ఇది `/api/mcp/` ONLY — `mcp:connect` ఏ ఇతర నిర్వహణ మార్గంలో ఏమీ మంజూరు చేయదు (ప్రతి ఇతర LOCAL_ONLY బైపాస్ ఉపసర్గతో సహా, ఎప్పుడైనా జోడించబడాలి), మరియు ఇది ఉద్దేశపూర్వకంగా `MANAGEMENT_API_KEY_SCOPES` నుండి మినహాయించబడింది. ఒక కీ హోల్డింగ్ `manage`/`admin` ఇప్పటికీ కార్వ్-అవుట్ను సరిగ్గా మునుపటిలానే పాస్ చేస్తుంది; `mcp:connect` అనేది విస్తృత నిర్వహణ యాక్సెస్ అవసరం లేని రిమోట్ MCP-మాత్రమే కాలర్లకు తక్కువ-ప్రత్యేక ప్రత్యామ్నాయం.

#### ఆపరేటర్ మార్గదర్శకత్వం & ఆడిటింగ్

మీరు రివర్స్ ప్రాక్సీ లేదా టన్నెల్ (nginx, Caddy, Cloudflare టన్నెల్, Tailscale, Ngrok) వెనుక OmniRoute నడుపుతున్నట్లయితే, లూప్బ్యాక్ చెక్ ఇప్పటికీ — పైన ఉన్న స్పాన్-సామర్థ్య మార్గాలను రక్షిస్తుంది, దీని క్లయింట్ చిరునామా `403 LOCAL_ONLY` తో తిరస్కరించబడుతుంది.** auth అమలుకు ముందు** , కాబట్టి లీక్ అయిన JWT స్పాన్ను చేరుకోలేదు. రెండు ఆపరేటర్ బాధ్యతలు మిగిలి ఉన్నాయి:

- **క్లయింట్ IP లూప్బ్యాక్గా ఫోర్జింగ్ చేయడం ద్వారా 403ని "పరిష్కరించవద్దు".** `X-Forwarded-For: 127.0.0.1`, లేదా మూల చిరునామాను లూప్బ్యాక్కు తిరిగి వ్రాసే ప్రాక్సీని సెట్ చేయడం, ఈ టైర్ మూసివేసే RCE క్లాస్ని సరిగ్గా మళ్లీ తెరుస్తుంది. dashboard/API ప్రాక్సీ — ద్వారా ఎప్పుడూ స్పాన్-సామర్థ్యం గల మార్గాలను బహిర్గతం చేయండి.
- **నిర్వహణ-స్కోప్ బైపాస్ను కనిష్టంగా ఉంచండి.** `/api/mcp/` మాత్రమే బైపాస్ చేయదగినది మరియు `manage` -scoped API కీతో మాత్రమే. `SPAWN_CAPABLE_PREFIXES` బైపాస్ జాబితాకు జోడించబడదు — zod స్కీమా వాటిని తిరస్కరిస్తుంది మరియు `isLocalOnlyBypassableByManageScope` వాటిని రన్టైమ్ (డిఫెన్స్-ఇన్-డెప్త్) వద్ద తిరస్కరిస్తుంది, డాష్బోర్డ్ అంటే "బైపాస్ చేయదగినదిగా చేయలేము". అదే తిరస్కరణ-జాబితా కొన్ని LOCAL_ONLY మార్గాలను కలిగి ఉంది, అవి పుట్టుకురావు కానీ ఎప్పుడూ రిమోట్గా చేరుకోకూడదు — `/api/oauth/kiro/auto-import` (హోస్ట్-లోకల్ Kiro క్రెడెన్షియల్ ఫైల్లను చదువుతుంది), `/api/discovery/` మరియు `/api/issue-agent/`. రన్టైమ్ స్నాప్షాట్ లోడర్ నిల్వ చేయబడిన సెట్టింగ్ల అడ్డు వరుస నుండి అటువంటి ఎంట్రీలను కూడా వదిలివేస్తుంది మరియు లెగసీ JSON దిగుమతి (`/api/settings/import-json`) బైపాస్ కీలను ఎప్పుడూ వ్రాయదు. ప్రతి `LOCAL_ONLY_API_PREFIXES` ఎంట్రీ తప్పనిసరిగా తిరస్కరణ-జాబితాలో ఉండాలి లేదా బైపాస్-అర్హత (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)గా సమీక్షించబడాలి. `/api/providers/` కింద డైనమిక్-సెగ్మెంట్ మరియు స్టాటిక్-పాత్ స్పాన్-సామర్థ్యం గల మార్గాలు (ఉదా `/login`, `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts` లోని రీజెక్స్-ఆధారిత `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` కంపానియన్ ద్వారా కవర్ చేయబడతాయి, ఫ్లాట్ `SPAWN_CAPABLE_PREFIXES` శ్రేణి — ద్వారా కాదు, ఫ్లాట్ శ్రేణి వాటిని రీమోట్ ట్రీని కవర్ చేయడానికి ప్రీ- `/api/providers/` ట్రీని కవర్ చేయాలి. డాష్బోర్డ్లు ప్రొవైడర్ CRUD కోసం చట్టబద్ధంగా ఉపయోగించబడతాయి.

**ఆడిటింగ్ యాక్సెస్** — ఆఫ్-హోస్ట్ ఏదీ ఈ మార్గాలను చేరుకోవడం లేదని ధృవీకరించడానికి:

- తెరవండి** ఆథరైజేషన్ ఇన్వెంటరీ** `/dashboard/settings/security` లో : ఇది లైవ్ LOCAL_ONLY ఉపసర్గ జాబితాను రెండర్ చేస్తుంది, ఇది ఉపసర్గలు బైపాస్ చేయదగినవి మరియు కంపైల్-టైమ్ స్పాన్-కెపాబుల్ ("బైపాస్ చేయగలిగేలా చేయలేము") సెట్.
- లూప్బ్యాక్ కాని క్లయింట్ చిరునామాతో జత చేసిన ఎగువ ఉపసర్గల కోసం మీ రివర్స్-ప్రాక్సీ / యాక్సెస్ లాగ్లను గ్రెప్ చేయండి. `403 LOCAL_ONLY` కి బదులుగా `200` తిరిగి వచ్చిన ఏదైనా అటువంటి హిట్ అంటే, ప్రాక్సీ నిజమైన క్లయింట్ IP — ప్రాక్సీని మాస్క్ చేస్తుందని అర్థం.
- ఈ పాత్లలో ఒకదానికి OmniRoute యొక్క లాగ్లలోని `403 LOCAL_ONLY` అనేది ఉద్దేశించిన విధంగా పనిచేసే గార్డు, అణచివేయడంలో లోపం కాదు.

#### కాల్-సైట్ ప్రోబ్ గేట్తో రిమోట్-రీచబుల్ రూట్లు

కొన్ని మార్గాలు తప్పనిసరిగా రిమోట్ డ్యాష్బోర్డ్ నుండి చేరుకోగలిగేలా ఉండాలి కానీ స్థానిక కాలర్ల కోసం హోస్ట్-సైడ్ ప్రోబ్ (`which <binary>`, `<binary> --version`, `tailscale status --json`)ని అమలు చేయాలి. అవి `GET` కి LOCAL_ONLY కాదు; బదులుగా హ్యాండ్లర్ విశ్వసనీయ పీర్ తీర్పును `getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`)తో చదువుతారు మరియు `loopback` / `lan` కాలర్ల కోసం మాత్రమే ప్రోబ్ను అమలు చేస్తారు. ఒక `remote` కాలర్ నాన్-స్పానింగ్ మూలాల నుండి రూపొందించబడిన అదే ప్రతిస్పందన ఆకారాన్ని పొందుతుంది (పరసిష్ట స్థితి, సెట్టింగ్లు, fs తనిఖీలు), ఫ్లాగ్ చేయబడిన `probed: false`.

| మార్గం                                                            | రిమోట్ కాలర్ల కోసం ప్రోబ్ దాటవేయబడింది                                    |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `POST /api/providers/{id}/test`, `/api/providers/test-batch`      | CLI రన్టైమ్ ప్రోబ్ (`allowLocalRuntimeProbe`) మరియు CLI-ఫాల్బ్యాక్ స్పాన్ |
| `GET /api/headroom/status`                                        | `which headroom` మరియు పైథాన్ `--version` ప్రోబ్స్                        |
| `GET /api/tunnels/tailscale`, `GET /api/tunnels/tailscale/check`  | `which tailscale`, `tailscale status/funnel --json`, `which brew`         |
| `GET /api/tunnels/cloudflared` ( LOCAL_ONLY నుండి GET-మినహాయింపు) | `which cloudflared` PATH శోధన                                             |

హోస్ట్ను ప్రోబ్ చేసే కొత్త రీడ్ రూట్ అదే పద్ధతిని అనుసరిస్తుంది లేదా పూర్తిగా LOCAL_ONLY వర్గీకరించబడుతుంది.

### టైర్ 2 — ALWAYS_PROTECTED

**దీని ద్వారా అమలు చేయబడింది:** `isAlwaysProtectedPath(path)` → `requireLogin=false` బైపాస్ని దాటవేయి** బైపాస్:** `requireLogin=false` ఉన్నప్పుడు ఏదీ లేదు; JWT ఎల్లప్పుడూ అవసరం

ఈ మార్గాలు విధ్వంసకరమైనవి లేదా తిరిగి మార్చలేనివి. వాటిని "నో-పాస్వర్డ్" ఇన్స్టాల్లో అనుమతించడం అంటే అదే LAN లో ఉన్న ఎవరైనా డేటాబేస్ను తుడిచివేయవచ్చు లేదా సర్వర్ ప్రాసెస్ను నాశనం చేయవచ్చు.

`/api/settings/obsidian` దాని `/webdav` చైల్డ్ను కవర్ చేస్తుంది: `POST` కస్టమ్ నోడ్ లేయర్ ద్వారా అందించబడిన WebDAV ఫైల్ సర్వీస్ — Next.js ముందు చూపుతుంది, ఈ పైప్లైన్ — వెలుపల కాలర్-ఎంచుకున్న రూట్ వద్ద ఉంది మరియు తాజాగా ముద్రించిన ప్రాథమిక ఆధారాలను ప్రతిధ్వనిస్తుంది, `DELETE` వాటిని తిప్పుతుంది మరియు పేరెంట్ `POST` Obsidian API REST చేస్తుంది. GHSA-62vw మాత్రమే `GET` పాస్వర్డ్ను బహిర్గతం చేస్తుంది; జారీ ఇప్పటికీ ఫెయిల్-ఓపెన్ టైర్ (GHSA-7pq4-8pvv-rx7r)లో ఉంది. `enableObsidianVaultSync()` అదనంగా వాల్ట్ని నిరాకరిస్తుంది, అది లోపల కూర్చుంటుంది లేదా డేటా డైరెక్టరీని కలిగి ఉంటుంది.

#### క్రెడెన్షియల్ ఎగుమతులు మరియు పునరుద్ధరణలు ఆపరేటర్-మాత్రమే

The tier above only decides whether _some_ credential is required. The routes that download stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and `GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()` (`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or an instance with login disabled, and answers `403` to API keys of any scope (including `manage` and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary: `POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups` (restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore) replace the live database or the whole settings/connections/API-key set, so a machine credential cannot trigger them either. Destroying restore points holds the same boundary: `DELETE /api/db-backups` (cleanup — keep the latest N / drop older than D days) and `PATCH /api/db-backups` (retention settings), because the persisted retention is exactly what `cleanupDbBackups()` applies after every automatic backup (`src/lib/db/backup.ts`), so a machine credential that could save `keepLatest: 1` would prune everything on the next snapshot. Listing and creating backups (`GET`/`PUT /api/db-backups`) keep ordinary management auth. Sync token issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback internal-service token.

### ఫ్రెష్-ఇన్స్టాల్ బూట్స్ట్రాప్ నిజమైన పీర్ ద్వారా లూప్బ్యాక్-మాత్రమే —, `Host` కాదు

నిర్వహణ పాస్వర్డ్ కాన్ఫిగర్ చేయబడలేదు (మరియు `INITIAL_PASSWORD` లేదు), `src/shared/utils/apiAuth.ts` లోని `isAuthRequired()` అనామక బూట్స్ట్రాప్ను తెరిచి ఉంచుతుంది** లూప్బ్యాక్ పీర్ల కోసం మాత్రమే** . లూప్బ్యాక్ విశ్వసనీయ పీర్ సిగ్నల్ల నుండి ఈ క్రమంలో నిర్ణయించబడుతుంది: టోకెన్-స్టాంప్డ్ రియల్ TCP పీర్ (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, పాలసీ ఏమి చూస్తుంది), పైప్లైన్ యొక్క స్వంత `AUTHZ_HEADER_PEER_LOCALITY` తీర్పు (రూట్ హ్యాండ్లర్లు ఏమి చూస్తారు, `OMNIROUTE_PEER_STAMP_TOKEN` సెట్ చేయబడినప్పుడు మాత్రమే విశ్వసిస్తారు) లేదా డైరెక్ట్ కాలర్ల కోసం నిజమైన సాకెట్ పీర్. `Host` / `nextUrl.hostname` ఎప్పుడూ సంప్రదించబడదు మరియు మొదటి-పాస్వర్డ్ రైట్ (`POST /api/settings/require-login`) ప్రతి నెట్వర్క్ పీర్ (GHSA-7pq4-8pvv-rx7r)కి ఓపెన్ కాకుండా అదే పరిమితిలో ఉంటుంది. `managementPolicy` దాని స్వంత `peerContext` తీర్పును స్పష్టంగా ఆమోదించింది, కాబట్టి ORIGINAL (ప్రీ-స్ట్రిప్) అభ్యర్థన యొక్క శీర్షికలు దానిని ఎన్నటికీ నిర్ణయించవు.

### టైర్ 3 — MANAGEMENT (డిఫాల్ట్)

అన్ని ఇతర నిర్వహణ మార్గాలు. `requireLogin=false` కాన్ఫిగర్ చేయబడితే తప్ప ప్రమాణీకరణ అవసరం. CLI టోకెన్లు ఈ మార్గాలను ప్రామాణీకరించగలవు (లూప్బ్యాక్ + చెల్లుబాటు అయ్యే HMAC).

## మూల్యాంకన క్రమం

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → తదుపరి దశకు వెళ్లండి
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → అనుమతించు (management_key)
     → లేకపోతే                                   → తిరస్కరించు 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → అనుమతించు (system)
  3. hasValidCliToken(headers)?
     → అనుమతించు (cli) [loopback + timingSafeEqual HMAC తనిఖీ]
  4. isAlwaysProtectedPath(path) లేదా requireLogin=true?
     → isDashboardSessionAuthenticated?
        → అనుమతించు (dashboard_session)
     → బైపాస్ చేయలేని మార్గంలో manage-scope Bearer ఉందా?
        → అనుమతించు (management_key)
     → తిరస్కరించు 401/403
  5. requireLogin=false?
     → అనుమతించు (anonymous)
```

LOCAL_ONLY మార్గాన్ని సంతృప్తిపరచగల ఏకైక ప్రామాణీకృత మార్గం దశ 1లోని manage-scope శాఖ;
గడువు ముగిసిన DB నిశ్శబ్దంగా "తిరస్కరించు" స్థితికి దిగజారకుండా ఉండేందుకు auth-backend వైఫల్య
స్థితి 403 కాకుండా 503ను అందిస్తుంది.

## కొత్త spawn-సామర్థ్య మార్గాన్ని జోడించడం

1. మార్గం ప్రిఫిక్స్ను
   `src/server/authz/routeGuard.ts`లోని `LOCAL_ONLY_API_PREFIXES`కు జోడించండి
2. కొత్త ప్రిఫిక్స్కు `isLocalOnlyPath()` trueను అందిస్తుందని నిర్ధారించే పరీక్షను
   `tests/unit/authz/routeGuard.test.ts`లో జోడించండి
3. **ఈ దశను ఎప్పటికీ దాటవేయవద్దు** — `CLAUDE.md`లోని Hard Rule #15 చూడండి
4. నిర్ణయించండి: ఈ మార్గం `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`లో కూడా ఉండాలా?
   డిఫాల్ట్ సమాధానం **లేదు**. manage-scope హోల్డర్కు బహిర్గతం చేయడానికి మార్గం
   సురక్షితమైనప్పుడు మాత్రమే ఎంపిక చేయండి (అంటే, అది వినియోగదారు నియంత్రించే ఏకపక్ష కోడ్ను spawn చేయకూడదు).

## manage-scope ద్వారా బైపాస్ చేయగల మార్గాన్ని జోడించడం

1. మార్గం వినియోగదారు అందించిన కోడ్ లేదా కమాండ్లను అమలు చేయదని నిర్ధారించండి. అలా
   చేస్తే, ఆపివేయండి — ఈ మినహాయింపు దీనికి సరైన సాధనం కాదు.
2. ప్రిఫిక్స్ను `src/server/authz/routeGuard.ts`లోని
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`కు జోడించండి
3. ఈ నాలుగు అభ్యర్థన రూపాలన్నింటికీ `tests/unit/authz/management-policy.test.ts`లో
   కవరేజ్ను జోడించండి: Bearer లేదు (403), manage Bearer (అనుమతించు), non-manage Bearer
   (403), అలాగే manage Bearer ఉన్నప్పటికీ `/api/cli-tools/runtime/*`
   strict-loopbackగానే ఉండేలా ప్రతి ప్రిఫిక్స్కు రిగ్రెషన్ పరీక్ష.

## OpenAPIలో భద్రతా టైర్లను డాక్యుమెంట్ చేయడం

`docs/openapi.yaml`కు కొత్త మార్గాన్ని జోడించేటప్పుడు, ఆ మార్గాన్ని `routeGuard.ts`
వర్గీకరిస్తే దానికి అనుగుణమైన vendor extensionను వర్తింపజేయండి:

| routeGuard.ts వర్గీకరణ             | YAML annotation            | అమలు                                                  |
| ---------------------------------- | -------------------------- | ----------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`          | `x-loopback-only: true`    | non-loopback నుంచి బేషరతుగా నిరోధించబడుతుంది          |
| `ALWAYS_PROTECTED_API_PATHS`       | `x-always-protected: true` | `requireLogin=false` ఉన్నప్పటికీ auth అవసరం           |
| అంతర్గత admin/debug మార్గం         | `x-internal: true`         | డిఫాల్ట్గా /dashboard/api-endpoints నుంచి దాచబడుతుంది |
| ఏదీ కాదు (public / ప్రామాణిక auth) | (annotation అవసరం లేదు)    | ప్రామాణిక `requireLogin`-నియంత్రిత యాక్సెస్           |

### ధ్రువీకరణ

YAML annotationలు మరియు `routeGuard.ts` మధ్య స్థిరత్వాన్ని రెండు స్క్రిప్ట్లు అమలు చేస్తాయి:

- `scripts/check/check-openapi-coverage.mjs` — కవరేజ్ < 99% అయితే విఫలమవుతుంది
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` లేదా
  `x-always-protected` annotationలు compile-time స్థిరాంకాల నుంచి భిన్నంగా ఉంటే విఫలమవుతుంది

రెండు స్క్రిప్ట్లు pre-commit hookలోనూ, CIలోనూ అమలవుతాయి.

### తప్పుడు పాజిటివ్ నియమం

`routeGuard.ts` స్థిరాంకంలో లేని మార్గంపై `x-always-protected` లేదా `x-loopback-only`
annotation ఉంటే, కవరేజ్ స్క్రిప్ట్ విఫలమవుతుంది. పరిష్కారం ఎల్లప్పుడూ YAMLను
`routeGuard.ts` వాస్తవంగా అమలు చేసే దానికి అనుగుణంగా సర్దుబాటు చేయడమే — enforcement
logicను కూడా అమలు చేయకుండా `routeGuard.ts`కు మార్గాలను జోడించడం కాదు.
