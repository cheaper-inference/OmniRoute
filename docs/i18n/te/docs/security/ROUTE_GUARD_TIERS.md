## అవలోకనం

అన్ని OmniRoute నిర్వహణ API రూట్లు మూడు రక్షణ స్థాయిలలో ఒకదానిగా వర్గీకరించబడతాయి. వర్గీకరణ స్థిరంగా ఉంటుంది, `src/server/authz/routeGuard.ts`లో నిర్వచించబడుతుంది, అలాగే ఇతర ఏ auth శాఖ అమలవడానికి ముందే మూల్యాంకనం చేయబడుతుంది.

## టైర్లు

### టైర్ 1 — LOCAL_ONLY

**అమలు చేసేది:** `isLocalOnlyPath(path)` → లూప్బ్యాక్ హోస్ట్ తనిఖీ
**బైపాస్:** అప్రమేయంగా ఏదీ లేదు. అభ్యర్థన `manage` స్కోప్ కలిగిన చెల్లుబాటు అయ్యే
API కీని కలిగి ఉన్నప్పుడు `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`లోని పాత్ల కోసం
ఇరుకైన మినహాయింపు మాత్రమే ([మేనేజ్-స్కోప్ మినహాయింపు](#manage-scope-carve-out) చూడండి).

ఈ రూట్లు చైల్డ్ ప్రాసెస్లను స్పాన్ చేస్తాయి లేదా రన్టైమ్ కోడ్ను అమలు చేస్తాయి. వీటిని
నాన్-లూప్బ్యాక్ ట్రాఫిక్కు బహిర్గతం చేస్తే, చెల్లుబాటు అయ్యే JWTని పొందిన దాడిచేసేవారు
(ఉదా., Cloudflared/Ngrok టన్నెల్ ద్వారా) ప్రాసెస్ స్పానింగ్ను ట్రిగర్ చేయగలరు — ఇది
ప్రసిద్ధ CVE తరగతి
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj అంటే ఏమిటి (దాడి తరగతి):** ఒక మేనేజ్మెంట్/ఏజెంట్ సర్వర్
సబ్ప్రాసెస్ను ప్రారంభించే ఎండ్పాయింట్ను బహిర్గతం చేస్తుంది (`npm install`, `node`, బ్రౌజర్,
ప్రాక్సీ, `git`, `tar`, …). ఆ ఎండ్పాయింట్ హోస్ట్ బయట నుండి చేరుకోగలిగితే — ఆపరేటర్
OmniRouteని nginx/Cloudflare/Tailscale టన్నెల్ వెనుక ఉంచడంతో JWT లీక్ అయింది లేదా
auth తప్పుగా కాన్ఫిగర్ చేయబడింది కాబట్టి — దాడిచేసేవారు "ఒక APIని కాల్ చేయడం"ను
"హోస్ట్పై ఒక కమాండ్ను అమలు చేయడం"గా మారుస్తారు (రిమోట్ కోడ్ ఎక్జిక్యూషన్). OmniRoute
దీనిని **లూప్బ్యాక్ హోస్ట్ తనిఖీని నిష్శరతంగా, ఏ auth తనిఖీకి ముందు**, స్పాన్-సామర్థ్యం
కలిగిన ప్రతి రూట్పై అమలు చేయడం ద్వారా మూసివేస్తుంది: టన్నెల్ ద్వారా లీకైన టోకెన్
ఇంకా స్పాన్ను చేరుకోలేదు.

**పూర్తి LOCAL_ONLY సెట్.** అధికారిక మూలం
`src/server/authz/routeGuard.ts`లోని `LOCAL_ONLY_API_PREFIXES` /
`LOCAL_ONLY_API_PATTERNS`; క్రింది పట్టిక ప్రస్తుత స్థితిని ప్రతిబింబిస్తుంది.
`check-route-guard-membership` గేట్ స్పాన్-సామర్థ్యం కలిగిన ప్రిఫిక్స్ల కింద ఉన్న ప్రతి
`route.ts`ను లెక్కించి, వాటిలో ఏదైనా local-onlyగా వర్గీకరించబడకపోతే CIని విఫలం చేస్తుంది.

#### మేనేజ్-స్కోప్ మినహాయింపు (carve-out)

LOCAL_ONLY పాత్ల ఉపసమితిని కూడా నాన్-లూప్బ్యాక్ నుండి యాక్సెస్ చేయవచ్చు, అయితే
అభ్యర్థన `Authorization: Bearer <api-key>` ను మోస్తే మరియు దాని మెటాడేటాలో
`manage` స్కోప్ (లేదా `admin`) ఉంటే మాత్రమే. ఈ మినహాయింపు
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ద్వారా ప్రతి-పాత్ వారీగా స్పష్టంగా గేట్
చేయబడింది, తద్వారా ఏ కొత్త LOCAL_ONLY పాత్కైనా డిఫాల్ట్ స్ట్రిక్ట్-లూప్బ్యాక్గానే
ఉంటుంది. ప్రమాణీకరించని అభ్యర్థనలు మరియు నాన్-మేనేజ్ కీలతో వచ్చే అభ్యర్థనలు
ఇప్పటికీ `403 LOCAL_ONLY` తో తిరస్కరించబడతాయి.

ఈరోజు బైపాస్ చేయగల ఏకైక ప్రీఫిక్స్ `/api/mcp/`. `/api/cli-tools/runtime/` మరియు
`/api/services/` లను ఉద్దేశపూర్వకంగా మినహాయించారు ఎందుకంటే అవి ఏవేళ సబ్ప్రాసెస్లను
(`npm install`, `node`) స్పాన్ చేయగలవి, ఇది LOCAL_ONLY టైర్ నివారించడానికి
ఏర్పడిన ఖచ్చితమైన CVE క్లాస్.

#### ఆపరేటర్ మార్గదర్శకత్వం & ఆడిటింగ్

మీరు OmniRoute ను రివర్స్ ప్రాక్సీ లేదా టన్నెల్ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) వెనుక నడుపుతుంటే, లూప్బ్యాక్ చెక్ ఇప్పటికీ పైన ఉన్న
స్పాన్-సామర్థ్య రూట్లను రక్షిస్తుంది — క్లయింట్ చిరునామా నాన్-లూప్బ్యాక్ అయిన
అభ్యర్థన **ఆత్ నడవడానికి ముందే** `403 LOCAL_ONLY` తో తిరస్కరించబడుతుంది, కాబట్టి
లీక్ అయిన JWT స్పాన్ను చేరుకోలేదు. రెండు ఆపరేటర్ బాధ్యతలు మిగిలి ఉన్నాయి:

- **క్లయింట్ IP ను loopback గా నకిలీ చేయడం ద్వారా 403 ను "సరిచేయవద్దు".**
  `X-Forwarded-For: 127.0.0.1` సెట్ చేయడం, లేదా సోర్స్ అడ్రస్ను loopback కు
  తిరగరాసే ప్రాక్సీ, ఈ టైర్ మూసివేసిన RCE క్లాస్ను సరిగ్గా మళ్లీ తెరుస్తుంది.
  డాష్బోర్డ్/API ను ప్రాక్సీ గుండా ఎక్స్పోజ్ చేయండి — స్పాన్-కేపబుల్ రూట్లను
  ఎప్పుడూ కాదు.
- **manage-scope బైపాస్ను కనీస స్థాయిలో ఉంచండి.** `/api/mcp/` మాత్రమే బైపాస్
  చేయగలదు, అది కూడా `manage`-స్కోప్డ్ API కీతో మాత్రమే. `SPAWN_CAPABLE_PREFIXES`
  ను బైపాస్ జాబితాకు ఎప్పుడూ జోడించలేము — zod స్కీమా వాటిని తిరస్కరిస్తుంది మరియు
  `isLocalOnlyBypassableByManageScope` రన్టైమ్లో వాటిని నిరాకరిస్తుంది
  (లోతైన రక్షణ — defence-in-depth), ఇదే డాష్బోర్డ్ "cannot be made bypassable"
  (బైపాస్ చేయగలిగేలా చేయలేము) అని అర్థం చేసుకునేది. అదే deny-list లో స్పాన్
  చేయని, కానీ రిమోట్గా కూడా ఎప్పుడూ చేరుకోకూడని కొన్ని LOCAL_ONLY రూట్లు కూడా
  ఉన్నాయి — `/api/oauth/kiro/auto-import` (హోస్ట్-లోకల్ Kiro క్రెడెన్షియల్
  ఫైళ్లను చదువుతుంది), `/api/discovery/` మరియు `/api/issue-agent/`. రన్టైమ్
  స్నాప్షాట్ లోడర్ కూడా నిల్వ చేయబడిన సెట్టింగ్స్ రో నుండి అలాంటి ఎంట్రీలను
  తొలగిస్తుంది, మరియు లెగసీ JSON ఇంపోర్ట్ (`/api/settings/import-json`) బైపాస్
  కీలను ఎప్పుడూ వ్రాయదు. ప్రతి `LOCAL_ONLY_API_PREFIXES` ఎంట్రీ deny-list లో
  ఉండాలి లేదా bypass-eligible గా రివ్యూ చేయబడాలి
  (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/`
  కింద ఉన్న డైనమిక్-సెగ్మెంట్ మరియు స్టాటిక్-పాత్ స్పాన్-కేపబుల్ రూట్లు (ఉదా.
  `/login`, `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts`
  లోని regex-ఆధారిత `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS`
  కంపానియన్ ద్వారా కవర్ చేయబడతాయి, ఫ్లాట్ `SPAWN_CAPABLE_PREFIXES` అర్రే ద్వారా
  కాదు — ఫ్లాట్ అర్రే వాటిని పట్టుకోవాలంటే మొత్తం `/api/providers/` ప్రీఫిక్స్ను
  కవర్ చేయాల్సి ఉంటుంది, అది రిమోట్ డాష్బోర్డ్లు provider CRUD కోసం
  చట్టబద్ధంగా ఉపయోగించే రూట్ ట్రీను అతిగా విస్తరిస్తుంది.

**యాక్సెస్ ఆడిటింగ్** — హోస్ట్ బయటి ఏదీ ఈ రూట్లను చేరుకోవడం లేదని ధృవీకరించడానికి:

- `/dashboard/settings/security` లో **Authorization Inventory (అధికార జాబితా)** ను తెరవండి:
  ఇది లైవ్ LOCAL_ONLY ప్రీఫిక్స్ జాబితాను, ఏ ప్రీఫిక్స్లు బైపాస్ చేయగలవో, మరియు
  compile-time స్పాన్-కేపబుల్ ("బైపాస్ చేయగలిగేలా చేయలేము") సెట్ను రెండర్ చేస్తుంది.
- పై ప్రీఫిక్స్లను non-loopback క్లయింట్ అడ్రస్తో జతగా మీ reverse-proxy /
  యాక్సెస్ లాగ్లలో grep చేయండి. `403 LOCAL_ONLY` బదులు `200` రిటర్న్ చేసిన అలాంటి
  ఏ హిట్ అయినా ప్రాక్సీ నిజమైన క్లయింట్ IP ను మాస్క్ చేస్తోందన్నమాట — ప్రాక్సీని
  సరిచేయండి.
- ఈ పాత్లలో ఒకదాని కోసం OmniRoute లాగ్లలో వచ్చే `403 LOCAL_ONLY` అనేది గార్డ్
  ఉద్దేశించిన విధంగానే పనిచేస్తున్నట్లు, అది అణచివేయాల్సిన ఎర్రర్ కాదు.

వాల్ట్ను తిరస్కరిస్తుంది.

#### క్రెడెన్షియల్ ఎక్స్పోర్ట్లు మరియు రీస్టోర్లు ఆపరేటర్-మాత్రమే

పై టైర్ _కొంత_ క్రెడెన్షియల్ అవసరమా అనేది మాత్రమే నిర్ణయిస్తుంది. స్టోర్ చేసిన
క్రెడెన్షియల్స్ను డౌన్లోడ్ చేసే రూట్లు హ్యాండ్లర్లో రెండవ చెక్ను జోడిస్తాయి: `GET /api/settings/export-json`
(డిక్రిప్ట్ చేసిన ప్రొవైడర్ కనెక్షన్లు మరియు రా API కీలు), `GET /api/db-backups/export` (SQLite ఫైల్) మరియు
`GET /api/db-backups/exportAll` (పూర్తి ఆర్కైవ్) `requireOperatorCredential()` ను కాల్ చేస్తాయి
(`src/lib/api/operatorCredential.ts`). ఇది డ్యాష్బోర్డ్ సెషన్ను, లోకల్ CLI సబ్జెక్ట్ను, లేదా
లాగిన్ డిసేబుల్ చేసిన ఇన్స్టన్స్ను అంగీకరిస్తుంది, మరియు ఏ స్కోప్లోనైనా ఉన్న API కీలకు (`manage`
మరియు `admin` తో సహా) మరియు `oma_` యాక్సెస్ టోకెన్లకు `403` తో సమాధానం ఇస్తుంది. డిస్ట్రక్టివ్
కౌంటర్పార్ట్స్ అదే బౌండరీను పాటిస్తాయి:
`POST /api/db-backups/import` (అప్లోడ్ చేసిన `.sqlite`, `dryRun=true` కలుపుకుని), `POST /api/db-backups`
(id ద్వారా స్టోర్ చేసిన బ్యాకప్ను రీస్టోర్ చేయడం) మరియు `POST /api/settings/import-json` (లెగసీ JSON రీస్టోర్)
లైవ్ డేటాబేస్ను లేదా మొత్తం సెట్టింగ్స్/కనెక్షన్లు/API-కీ సెట్ను రీప్లేస్ చేస్తాయి, కాబట్టి మెషిన్ క్రెడెన్షియల్
వాటిని కూడా ట్రిగర్ చేయలేదు. రీస్టోర్ పాయింట్లను నాశనం చేయడం అదే బౌండరీను పాటిస్తుంది:
`DELETE /api/db-backups` (క్లీనప్ — తాజా N ఉంచండి / D రోజుల కంటే పాతవాటిని తొలగించండి) మరియు
`PATCH /api/db-backups` (రిటెన్షన్ సెట్టింగ్స్), ఎందుకంటే పెర్సిస్ట్ చేసిన రిటెన్షన్ అనేది ప్రతి ఆటోమేటిక్
బ్యాకప్ తర్వాత `cleanupDbBackups()` వర్తింపజేసేదే (`src/lib/db/backup.ts`), కాబట్టి `keepLatest: 1` ను
సేవ్ చేయగల మెషిన్ క్రెడెన్షియల్ తదుపరి స్నాప్షాట్లో అన్నిటినీ ప్రూన్ చేస్తుంది. బ్యాకప్లను లిస్ట్ చేయడం
మరియు క్రియేట్ చేయడం (`GET`/`PUT /api/db-backups`) సాధారణ మేనేజ్మెంట్ ఆత్ను కొనసాగిస్తాయి. సింక్ టోకెన్
జారీ (`POST /api/sync/tokens`) అదే హెల్పర్ను ఉపయోగిస్తుంది, ప్లస్ ట్రస్టెడ్ లూప్బ్యాక్
ఇంటర్నల్-సర్వీస్ టోకెన్.

### ఫ్రెష్-ఇన్స్టాల్ బూట్స్ట్రాప్ లూప్బ్యాక్-మాత్రమే — రియల్ పీర్ ద్వారా, `Host` కాదు

మేనేజ్మెంట్ పాస్వర్డ్ కాన్ఫిగర్ చేయకుండా (మరియు `INITIAL_PASSWORD` లేకుండా),
`src/shared/utils/apiAuth.ts` లోని `isAuthRequired()` అనానిమస్ బూట్స్ట్రాప్ను **లూప్బ్యాక్ పీర్ల కోసం
మాత్రమే** ఓపెన్గా ఉంచుతుంది.
లూప్బ్యాక్ ట్రస్టెడ్ పీర్ సిగ్నల్స్ నుండి, క్రమంలో నిర్ణయించబడుతుంది: టోకెన్-స్టాంప్ చేసిన రియల్ TCP పీర్
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, పాలసీ చూసేది), పైప్లైన్ యొక్క స్వంత
`AUTHZ_HEADER_PEER_LOCALITY` తీర్పు (రూట్ హ్యాండ్లర్లు చూసేది, `OMNIROUTE_PEER_STAMP_TOKEN`
సెట్ చేయబడినప్పుడు మాత్రమే ట్రస్టెడ్), లేదా డైరెక్ట్ కాలర్ల కోసం రియల్ సాకెట్ పీర్. `Host` /
`nextUrl.hostname` ఎప్పుడూ కన్సల్ట్ చేయబడవు, మరియు ఫస్ట్-పాస్వర్డ్ రైట్
(`POST /api/settings/require-login`) ప్రతి నెట్వర్క్ పీర్కు ఓపెన్ కాకుండా
అదే కాన్స్ట్రెయింట్ కింద ఉంటుంది (GHSA-7pq4-8pvv-rx7r). `managementPolicy` దాని స్వంత `peerContext` తీర్పును
స్పష్టంగా క్రిందికి పంపుతుంది, కాబట్టి ORIGINAL (ప్రీ-స్ట్రిప్) రిక్వెస్ట్ హెడర్లు దాన్ని ఎప్పుడూ నిర్ణయించవు.

### టైర్ 3 — MANAGEMENT (డిఫాల్ట్)

మిగిలిన అన్ని మేనేజ్మెంట్ రూట్లు. `requireLogin=false` కాన్ఫిగర్ చేయకపోతే
ఆత్ అవసరం. CLI టోకెన్లు ఈ రూట్లను ఆథెంటికేట్ చేయగలవు (లూప్బ్యాక్ + వాలిడ్ HMAC).

## మూల్యాంకన క్రమం

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → తదుపరి దశకు వెళ్లండి
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → అనుమతించు (management_key)
     → లేకపోతే                                   → తిరస్కరించు 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → అనుమతించు (system)
  3. hasValidCliToken(headers)?
     → అనుమతించు (cli) [loopback + timingSafeEqual HMAC తనిఖీ]
  4. isAlwaysProtectedPath(path) లేదా requireLogin=true?
     → isDashboardSessionAuthenticated?
        → అనుమతించు (dashboard_session)
     → బైపాస్ చేయలేని మార్గంలో manage-scope Bearer ఉందా?
        → అనుమతించు (management_key)
     → తిరస్కరించు 401/403
  5. requireLogin=false?
     → అనుమతించు (anonymous)
```

LOCAL_ONLY మార్గాన్ని సంతృప్తిపరచగల ఏకైక ప్రామాణీకృత మార్గం దశ 1లోని manage-scope శాఖ;
గడువు ముగిసిన DB నిశ్శబ్దంగా "తిరస్కరించు" స్థితికి దిగజారకుండా ఉండేందుకు auth-backend వైఫల్య
స్థితి 403 కాకుండా 503ను అందిస్తుంది.

## కొత్త spawn-సామర్థ్య మార్గాన్ని జోడించడం

1. మార్గం ప్రిఫిక్స్ను
   `src/server/authz/routeGuard.ts`లోని `LOCAL_ONLY_API_PREFIXES`కు జోడించండి
2. కొత్త ప్రిఫిక్స్కు `isLocalOnlyPath()` trueను అందిస్తుందని నిర్ధారించే పరీక్షను
   `tests/unit/authz/routeGuard.test.ts`లో జోడించండి
3. **ఈ దశను ఎప్పటికీ దాటవేయవద్దు** — `CLAUDE.md`లోని Hard Rule #15 చూడండి
4. నిర్ణయించండి: ఈ మార్గం `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`లో కూడా ఉండాలా?
   డిఫాల్ట్ సమాధానం **లేదు**. manage-scope హోల్డర్కు బహిర్గతం చేయడానికి మార్గం
   సురక్షితమైనప్పుడు మాత్రమే ఎంపిక చేయండి (అంటే, అది వినియోగదారు నియంత్రించే ఏకపక్ష కోడ్ను spawn చేయకూడదు).

## manage-scope ద్వారా బైపాస్ చేయగల మార్గాన్ని జోడించడం

1. మార్గం వినియోగదారు అందించిన కోడ్ లేదా కమాండ్లను అమలు చేయదని నిర్ధారించండి. అలా
   చేస్తే, ఆపివేయండి — ఈ మినహాయింపు దీనికి సరైన సాధనం కాదు.
2. ప్రిఫిక్స్ను `src/server/authz/routeGuard.ts`లోని
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`కు జోడించండి
3. ఈ నాలుగు అభ్యర్థన రూపాలన్నింటికీ `tests/unit/authz/management-policy.test.ts`లో
   కవరేజ్ను జోడించండి: Bearer లేదు (403), manage Bearer (అనుమతించు), non-manage Bearer
   (403), అలాగే manage Bearer ఉన్నప్పటికీ `/api/cli-tools/runtime/*`
   strict-loopbackగానే ఉండేలా ప్రతి ప్రిఫిక్స్కు రిగ్రెషన్ పరీక్ష.

## OpenAPIలో భద్రతా టైర్లను డాక్యుమెంట్ చేయడం

`docs/openapi.yaml`కు కొత్త మార్గాన్ని జోడించేటప్పుడు, ఆ మార్గాన్ని `routeGuard.ts`
వర్గీకరిస్తే దానికి అనుగుణమైన vendor extensionను వర్తింపజేయండి:

| routeGuard.ts వర్గీకరణ             | YAML annotation            | అమలు                                                  |
| ---------------------------------- | -------------------------- | ----------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`          | `x-loopback-only: true`    | non-loopback నుంచి బేషరతుగా నిరోధించబడుతుంది          |
| `ALWAYS_PROTECTED_API_PATHS`       | `x-always-protected: true` | `requireLogin=false` ఉన్నప్పటికీ auth అవసరం           |
| అంతర్గత admin/debug మార్గం         | `x-internal: true`         | డిఫాల్ట్గా /dashboard/api-endpoints నుంచి దాచబడుతుంది |
| ఏదీ కాదు (public / ప్రామాణిక auth) | (annotation అవసరం లేదు)    | ప్రామాణిక `requireLogin`-నియంత్రిత యాక్సెస్           |

### ధ్రువీకరణ

YAML annotationలు మరియు `routeGuard.ts` మధ్య స్థిరత్వాన్ని రెండు స్క్రిప్ట్లు అమలు చేస్తాయి:

- `scripts/check/check-openapi-coverage.mjs` — కవరేజ్ < 99% అయితే విఫలమవుతుంది
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` లేదా
  `x-always-protected` annotationలు compile-time స్థిరాంకాల నుంచి భిన్నంగా ఉంటే విఫలమవుతుంది

రెండు స్క్రిప్ట్లు pre-commit hookలోనూ, CIలోనూ అమలవుతాయి.

### తప్పుడు పాజిటివ్ నియమం

`routeGuard.ts` స్థిరాంకంలో లేని మార్గంపై `x-always-protected` లేదా `x-loopback-only`
annotation ఉంటే, కవరేజ్ స్క్రిప్ట్ విఫలమవుతుంది. పరిష్కారం ఎల్లప్పుడూ YAMLను
`routeGuard.ts` వాస్తవంగా అమలు చేసే దానికి అనుగుణంగా సర్దుబాటు చేయడమే — enforcement
logicను కూడా అమలు చేయకుండా `routeGuard.ts`కు మార్గాలను జోడించడం కాదు.
