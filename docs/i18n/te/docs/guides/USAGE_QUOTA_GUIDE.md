> **TL;DR**: OmniRoute ప్రతి అభ్యర్థన యొక్క టోకెన్ వినియోగాన్ని ట్రాక్ చేస్తుంది, ఖర్చును లెక్కిస్తుంది, ప్రతి API కీకి కోటాను అమలు చేస్తుంది మరియు డ్యాష్బోర్డ్లో విశ్లేషణలను ప్రదర్శిస్తుంది. ఇవన్నీ ఎలా పనిచేస్తాయో ఈ మార్గదర్శిని వివరిస్తుంది.

**మూలాలు:**

- `open-sse/services/usage.ts` (~70KB) — ప్రధాన వినియోగ ట్రాకింగ్
- `src/lib/usageAnalytics.ts` (~10KB) — డ్యాష్బోర్డ్ కోసం సమీకరణ
- `src/lib/db/quotaSnapshots.ts` — చారిత్రక కోటా డేటా
- `src/lib/db/usage*.ts` — వినియోగానికి సంబంధించిన అనేక DB మాడ్యూళ్లు

## అవలోకనం

OmniRoute ద్వారా ప్రవహించే ప్రతి అభ్యర్థన కింది వివరాలను సంగ్రహించే **వినియోగ రికార్డ్**ను రూపొందిస్తుంది:

- **గుర్తింపు**: ఏ API కీ, ప్రొవైడర్, మోడల్, కాంబో
- **టోకెన్లు**: ప్రాంప్ట్ టోకెన్లు, కంప్లీషన్ టోకెన్లు, క్యాష్ చేసిన టోకెన్లు, మొత్తం
- **ఖర్చు**: USD మొత్తం (ధరల డేటా నుండి లెక్కించబడుతుంది)
- **సమయ వివరాలు**: లేటెన్సీ, ప్రారంభ/ముగింపు టైమ్స్టాంప్లు
- **స్థితి**: విజయవంతం, లోపం, రేట్-లిమిట్ చేయబడింది మొదలైనవి

ఈ రికార్డ్లు **విశ్లేషణలు**గా సమీకరించబడతాయి, **కోటా స్నాప్షాట్లు**గా నిల్వ చేయబడతాయి మరియు **ప్రతి కీకి బడ్జెట్ పరిమితులను** అమలు చేయడానికి ఉపయోగించబడతాయి.

```
అభ్యర్థన ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    విశ్లేషణలు  కోటా   బిల్లింగ్
                    (డ్యాష్బోర్డ్) (అమలు) (ఎగుమతి)
```

## ఏమి నమోదు చేయబడుతుంది

`usage.ts` సేవ ప్రతి అభ్యర్థనకు ఒక **వినియోగ ఈవెంట్‌ను** నమోదు చేస్తుంది:

| ఫీల్డ్             | రకం     | మూలం                                                                  |
| ------------------ | ------- | --------------------------------------------------------------------- |
| `id`               | string  | నమోదు సమయంలో రూపొందించిన UUID                                         |
| `apiKeyId`         | string  | అభ్యర్థనను ప్రారంభించిన API కీ                                        |
| `provider`         | string  | ప్రొవైడర్ ID (openai, anthropic, మొదలైనవి)                            |
| `model`            | string  | మోడల్ ID (gpt-5, claude-opus-4-6, మొదలైనవి)                           |
| `comboId`          | string? | కాంబో ద్వారా రూట్ చేయబడితే ఆ కాంబో ID                                 |
| `promptTokens`     | number  | అప్‌స్ట్రీమ్ ప్రతిస్పందన నుండి                                        |
| `completionTokens` | number  | అప్‌స్ట్రీమ్ ప్రతిస్పందన నుండి                                        |
| `cachedTokens`     | number  | క్యాష్‌లో లభించిన టోకెన్‌లు (Anthropic ప్రాంప్ట్ క్యాషింగ్, మొదలైనవి) |
| `totalTokens`      | number  | ప్రాంప్ట్ + కంప్లీషన్                                                 |
| `costUsd`          | number  | ధరల డేటా నుండి లెక్కించబడుతుంది                                       |
| `latencyMs`        | number  | అభ్యర్థన ప్రారంభం నుండి ముగింపు వరకు పట్టిన సమయం                      |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`            |
| `errorClass`       | string? | స్థితి success కాకపోతే దోష వర్గం                                      |
| `timestamp`        | string  | ISO 8601 UTC                                                          |
| `metadata`         | object  | ప్లగిన్ చేర్చిన అనుకూల డేటా                                           |

### టోకెన్‌లు ఎక్కడి నుండి వస్తాయి

**ప్రతిస్పందన హ్యాండ్లర్‌లో** అప్‌స్ట్రీమ్ ప్రొవైడర్ ప్రతిస్పందన నుండి టోకెన్‌లు సంగ్రహించబడతాయి:

```ts
// open-sse/handlers/chatCore.ts నుండి
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

వినియోగ వివరాలను తిరిగి ఇవ్వని ప్రొవైడర్ల కోసం (కొన్ని వెబ్-కుకీ ప్రొవైడర్లు), OmniRoute `~4 chars per token` అంచనా పద్ధతిని ఉపయోగించి టోకెన్‌లను **అంచనా వేస్తుంది** (`open-sse/services/autoCombo/pipelineRouter.ts` చూడండి).

### క్యాష్ చేసిన టోకెన్‌లు

OmniRoute `cached_tokens`ను `prompt_tokens` నుండి విడిగా ట్రాక్ చేస్తుంది, ఎందుకంటే:

- Anthropic ప్రాంప్ట్ క్యాషింగ్‌లో క్యాష్ చేసిన టోకెన్‌లకు తగ్గించిన రేటు వసూలు చేయబడుతుంది (సాధారణ రేటులో 10%)
- కొన్ని ప్రొవైడర్లు `cache_read_input_tokens`ను తిరిగి ఇస్తాయి; వీటికి వేరే ధర వర్తింపజేయాలి
- విశ్లేషణల్లో **క్యాష్ హిట్ రేటు** = `cached_tokens / prompt_tokens` చూపించవచ్చు

### క్యాష్-రైట్ శ్రేణి నిర్ధారణలు

విశ్లేషణల డ్యాష్‌బోర్డ్‌లోని ప్రాంప్ట్-క్యాష్ ఆరోగ్య ప్యానెల్, ప్రొవైడర్ నివేదించిన
5 నిమిషాల మరియు 1 గంట క్యాష్ రైట్‌లను వేరు చేస్తుంది. Anthropic యొక్క
`usage.cache_creation.ephemeral_5m_input_tokens` మరియు
`usage.cache_creation.ephemeral_1h_input_tokens` స్ట్రీమింగ్ మరియు
నాన్-స్ట్రీమింగ్ వినియోగ మార్పిడి అంతటా నిలుపుకోబడతాయి, కాల్-లాగ్ సారాంశాలతో నిల్వ చేయబడతాయి. కలిపిన
క్యాష్-రైట్ మొత్తం ఆ విభాగాలకు రెండోసారి జోడించబడదు.

పాత రికార్డులతో సహా, కలిపిన రైట్ కౌంటర్ మాత్రమే ఉన్న కాల్‌ల శ్రేణి
తెలియనిదిగా ఉంటుంది. పాక్షిక విభజనలో కేటాయించని మిగులు తెలియనిదిగానే ఉంటుంది; చెల్లని లేదా
విరుద్ధమైన కౌంటర్‌లకు నిశ్శబ్దంగా TTL కేటాయించే బదులు వాటిని గుర్తిస్తారు. అభ్యర్థన వైపు
TTL గుర్తులు బిల్ చేయబడిన శ్రేణికి ఆధారం కావు.

ఈ ప్యానెల్‌లోని API-సమాన రైట్ అంచనా, నివేదించబడిన మరియు ధరలు అందుబాటులో ఉన్న శ్రేణులకు మాత్రమే వర్తిస్తుంది,
మొత్తం అభ్యర్థనకు కాదు. స్థానిక Claude/Anthropic మోడల్ ధరల కోసం ఇది
5 నిమిషాల రైట్‌లకు ఇన్‌పుట్ రేటుకు 1.25 రెట్లు, 1 గంట రైట్‌లకు ఇన్‌పుట్ రేటుకు రెండింతలు ఉపయోగిస్తుంది. ధరలు
లేకపోతే అవి అందుబాటులో లేనివిగా పరిగణించబడతాయి, సున్నాగా కాదు. ప్రతి కొత్త కాల్ లాగ్ చేయబడినప్పుడు ధరలు నమోదు చేయబడతాయి;
చారిత్రక రికార్డులకు మళ్లీ ధరలు లెక్కించబడవు. అందువల్ల సబ్‌స్క్రిప్షన్ ఖాతాలకు
ఆ మొత్తం నగదు వ్యయంగా లేదా సబ్‌స్క్రిప్షన్
కోటాగా ఖర్చు కాకుండానే API-సమాన అంచనా ఉండవచ్చు. ఇప్పటికే ఉన్న కోటా, బడ్జెట్ మరియు ప్రొవైడర్‌కు ఖచ్చితమైన వ్యయ లెక్కలు మారవు.

ఈ నిర్ధారణలు ఇప్పటికే ఉన్న పరిమిత పరిమాణపు క్యాష్-ఆరోగ్య సారాంశాన్ని మరియు కాల్-లాగ్
నిల్వ వ్యవధిని ఉపయోగిస్తాయి. ఇవి అభ్యర్థన TTL డిఫాల్ట్‌లను, రూటింగ్‌ను లేదా ఖాతా ఎంపికను మార్చవు.
ప్రొవైడర్‌కు పంపే సరిహద్దు వద్ద క్లయింట్ అభ్యర్థించిన TTLను, వాస్తవంగా వర్తించే అవుట్‌గోయింగ్ TTLతో పోల్చి
నమోదు చేయడం వాయిదా వేయబడింది; ఈ ప్యానెల్ రసీదులోని శ్రేణులను నివేదిస్తుంది, వాస్తవ అవుట్‌గోయింగ్ TTLను కాదు.

అమలు: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, మరియు `open-sse/utils/cacheWriteUsage.ts`.

## ఖర్చు గణన

ఖర్చులు LiteLLM నుండి సమకాలీకరించబడిన **ధరల డేటా** ఆధారంగా గణించబడతాయి (`src/lib/pricingSync.ts`):

| మోడల్             | ఇన్పుట్ $/1M | అవుట్పుట్ $/1M | కాష్డ్ $/1M |
| ----------------- | ------------ | -------------- | ----------- |
| gpt-5             | $2.50        | $10.00         | —           |
| claude-opus-4-6   | $15.00       | $75.00         | $1.50       |
| claude-sonnet-4-5 | $3.00        | $15.00         | $0.30       |
| gemini-2.5-pro    | $1.25        | $10.00         | —           |

ఖర్చు సూత్రం (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **ప్రాంప్ట్ నుండి కాష్డ్ టోకెన్లను ఎందుకు తీసివేయాలి?** కాష్డ్ భాగానికి విడిగా ధర నిర్ణయించబడుతుంది; మొత్తం ప్రాంప్ట్పై ఇన్పుట్ ధరను వర్తింపజేస్తే ఖర్చు అధికంగా లెక్కించబడుతుంది.

### ధరల సమకాలీకరణ

అంతర్నిర్మిత cron టాస్క్ ద్వారా ట్రిగ్గర్ చేయబడే `/api/pricing/sync` ఎండ్పాయింట్ ద్వారా ధరల డేటా LiteLLM నుండి స్వయంచాలకంగా సమకాలీకరించబడుతుంది (ఇది వినియోగదారులకు అందుబాటులో ఉండే env var కాదు):

```bash
# మాన్యువల్ ట్రిగ్గర్
curl -X POST http://localhost:20128/api/pricing/sync
```

ధరల డేటా లేని మోడల్ల కోసం, OmniRoute అంతర్గత సగటు రేట్లను ఉపయోగించి **ఖర్చును అంచనా వేస్తుంది** (ఇవి LiteLLM ధరల డేటా నుండి సేకరించబడతాయి).

## తేదీ పరిధి సమీకరణ

`usageAnalytics.ts` మాడ్యూల్ ముడి వినియోగ డేటా నుంచి డాష్‌బోర్డ్ విడ్జెట్‌లను గణిస్తుంది. ఇది 7 సమయ పరిధులకు మద్దతు ఇస్తుంది:

| పరిధి    | వ్యవధి                                   | వినియోగ సందర్భం                   |
| -------- | ---------------------------------------- | --------------------------------- |
| `1d`     | గత 24 గంటలు                              | గంటలవారీ ఖర్చు పెరుగుదల గుర్తింపు |
| `7d`     | గత 7 రోజులు                              | వారపు సమీక్ష                      |
| `30d`    | గత 30 రోజులు                             | నెలవారీ బిల్లింగ్                 |
| `90d`    | గత 90 రోజులు                             | త్రైమాసిక విశ్లేషణ                |
| `ytd`    | ప్రస్తుత సంవత్సరం జనవరి 1 నుంచి          | వార్షిక బడ్జెట్ పర్యవేక్షణ        |
| `all`    | మొత్తం కాలం                              | మొత్తం కాలపు గణాంకాలు             |
| `custom` | వినియోగదారు నిర్వచించిన ప్రారంభం/ముగింపు | ఆడిట్‌లు, అవసరానుసార ప్రశ్నలు     |

### గణించబడే డాష్‌బోర్డ్ విడ్జెట్‌లు

ఏ తేదీ పరిధికైనా, విశ్లేషణ పొర కింది వాటిని గణిస్తుంది:

| విడ్జెట్                  | వివరణ                                                        |
| ------------------------- | ------------------------------------------------------------ |
| **సారాంశ కార్డులు**       | మొత్తం అభ్యర్థనలు, మొత్తం ఖర్చు, మొత్తం టోకెన్‌లు, విజయ శాతం |
| **రోజువారీ ధోరణి చార్ట్** | రోజుకు ఖర్చు + టోకెన్‌లు, మోడల్ ఆధారంగా పేర్చబడతాయి          |
| **కార్యకలాప హీట్‌మ్యాప్** | రోజులోని గంట × వారంలోని రోజు గ్రిడ్, రంగు = అభ్యర్థనల సంఖ్య  |
| **మోడల్ వారీ విభజన**      | మోడల్ వారీ ఖర్చు పై చార్ట్                                   |
| **ప్రొవైడర్ వారీ విభజన**  | ప్రొవైడర్ వారీ అభ్యర్థనల బార్ చార్ట్                         |
| **అగ్ర API కీలు**         | ఖర్చు ఆధారంగా అగ్ర 10 కీల పట్టిక                             |
| **లోపాల విశ్లేషణ**        | కాలక్రమంలో లోపాల రేటు, ప్రధాన లోపాల వర్గాలు                  |

### ప్రోగ్రామ్ ద్వారా ప్రాప్యత

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // వినియోగ చరిత్ర రికార్డులు
  "7d",                 // సమయ పరిధి: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // ప్రొవైడర్ కనెక్షన్ మ్యాప్ (connectionId → ఖాతా పేరు)
  {
    startDate: "2025-01-01",  // ఐచ్ఛికం: "custom" పరిధి కోసం
    endDate: "2025-06-01",   // ఐచ్ఛికం: "custom" పరిధి కోసం
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (సెంట్లు)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## కోటా అమలు

ప్రతి API కీ కోటా రెండు చోట్ల అమలు చేయబడుతుంది:

1. **మృదు పరిమితి** (`quotaWarnAt`): వినియోగం నిర్దేశిత స్థాయిని మించినప్పుడు డాష్‌బోర్డ్ హెచ్చరిక
2. **కఠిన పరిమితి** (`quotaLimit`): పరిమితి మించినప్పుడు HTTP 429తో అభ్యర్థన తిరస్కరించబడుతుంది

### కాన్ఫిగరేషన్

```ts
// ప్రతి API కీకి
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — హెచ్చరికను చూపించు
  quotaLimit: 10_00,    // $10.00 — పూర్తిగా నిలిపివేయి
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### అమలు ప్రవాహం

```
అభ్యర్థన ──▶ quotaCheck()
              │
              ├── పరిమితిలో ఉందా?  ──▶ అనుమతించు
              │
              └── పరిమితి మించిందా?  ──▶ 429 Too Many Requests
                                   Retry-After హెడర్‌తో
```

### కోటా స్నాప్‌షాట్‌లు

ధోరణి విశ్లేషణ కోసం `quotaSnapshots` పట్టిక **గత కోటా స్థితిని** నిల్వ చేస్తుంది:

| ఫీల్డ్ | వివరణ |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | పర్యవేక్షించబడుతున్న కీ |
| `window` | "day" | "week" | "month" |
| `used` | ఈ వ్యవధిలో వినియోగించిన ఖర్చు (సెంట్లు) |
| `limit` | పరిమితి (సెంట్లు) |
| `resetAt` | వ్యవధి రీసెట్ అయ్యే సమయం |
| `createdAt` | స్నాప్‌షాట్ తీసుకున్న సమయం |

ఖర్చు > 0 ఉన్న **ప్రతి అభ్యర్థనపై** స్నాప్‌షాట్‌లు తీసుకోబడతాయి, వాటిని కింది వాటికి ఉపయోగిస్తారు:

- డాష్‌బోర్డ్‌లో కోటా పురోగతి పట్టీని ప్రదర్శించడానికి
- 30-రోజుల కోటా ధోరణి చార్ట్‌లను చూపించడానికి
- వినియోగం పరిమితికి చేరువైనప్పుడు హెచ్చరికలను పంపడానికి

## నిల్వ వ్యవధి మరియు శుభ్రపరచడం

ప్రతి అభ్యర్థనకు వినియోగ డేటా ~1-10KB పెరుగుతుంది. భారీ స్థాయిలో ఇది గణనీయంగా ఉండవచ్చు.

### నిల్వ వ్యవధి సెట్టింగ్‌లు

వినియోగ చరిత్ర నిల్వ వ్యవధిని UIలోని డేటాబేస్ సెట్టింగ్‌ల ద్వారా లేదా `/api/settings/database` ద్వారా కాన్ఫిగర్ చేయవచ్చు.

డిఫాల్ట్‌గా, వినియోగ చరిత్ర **90 రోజులు** నిల్వ చేయబడుతుంది.

### శుభ్రపరచడం

పాత రికార్డులను `src/lib/db/cleanup.ts` శుభ్రపరుస్తుంది:

- నేపథ్య cron ప్రక్రియ ద్వారా ప్రారంభించబడుతుంది
- కాన్ఫిగర్ చేసిన `usageHistory` నిల్వ వ్యవధి సెట్టింగ్ కంటే పాత రికార్డులను `usage_history` నుండి తొలగిస్తుంది

### నిల్వ అంచనా

| అభ్యర్థన రేటు             | 30 రోజుల నిల్వ | 90 రోజుల నిల్వ |
| ------------------------- | -------------- | -------------- |
| రోజుకు 100 అభ్యర్థనలు     | ~3MB           | ~9MB           |
| రోజుకు 1,000 అభ్యర్థనలు   | ~30MB          | ~90MB          |
| రోజుకు 10,000 అభ్యర్థనలు  | ~300MB         | ~900MB         |
| రోజుకు 100,000 అభ్యర్థనలు | ~3GB           | ~9GB           |

అత్యధిక ట్రాఫిక్ ఉన్నప్పుడు, వీటిని పరిగణించండి:

- డేటాబేస్ సెట్టింగ్‌ల ద్వారా నిల్వ వ్యవధిని తగ్గించడం
- ముడి రికార్డులకు బదులుగా `aggregated_metrics` ఉపయోగించడం (విశ్లేషణ కోసం మాత్రమే)

## ఖర్చు తగ్గింపు చిట్కాలు

### 1. సరైన మోడల్‌ను ఉపయోగించండి

```bash
# త్వరిత సమాధానం — తక్కువ ఖర్చు + వేగవంతమైనది ఉపయోగించండి
curl -d '{"model":"auto/fast","messages":[...]}'

# సంక్లిష్టమైన పని — నాణ్యమైనది ఉపయోగించండి
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. కాషింగ్‌ను ప్రారంభించండి

Anthropic ప్రాంప్ట్ కాషింగ్‌తో **పునరావృత సందర్భంపై 90% ఆదా అవుతుంది**:

```ts
// కాషింగ్ స్వయంచాలకంగా జరుగుతుంది — అదే పెద్ద సిస్టమ్ ప్రాంప్ట్‌ను చేర్చండి చాలు
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // స్వయంచాలకంగా కాష్ చేయబడుతుంది
  messages: [{ role: "user", content: "..." }],
});
```

### 3. కంప్రెషన్‌ను ఉపయోగించండి

RTK + Caveman కంప్రెషన్‌తో **టూల్స్‌ను ఎక్కువగా ఉపయోగించే సెషన్‌లపై 15-95% ఆదా అవుతుంది**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. ప్రతి కీకి కోటాలను సెట్ చేయండి

ఖర్చులు అదుపు తప్పకుండా ఉండేందుకు ఎల్లప్పుడూ `quotaLimit` సెట్ చేయండి:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // నెలకు $10 పరిమితి
```

### 5. అత్యధికంగా వినియోగించేవారిని ఆడిట్ చేయండి

API కీ ఆధారంగా సమూహపరచడానికి, ఖర్చు ఆధారంగా క్రమబద్ధీకరించడానికి డాష్‌బోర్డ్ లేదా **`/api/usage/analytics`** ఉపయోగించండి:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## సమస్యల పరిష్కారం

### "ఖర్చు ఊహించిన దానికంటే ఎక్కువగా ఉంది"

1. **`/api/usage/analytics?groupBy=model`** తనిఖీ చేయండి — ఖరీదైన మోడల్‌ను గుర్తించండి
2. **`/api/usage/analytics?groupBy=apiKey`** తనిఖీ చేయండి — అధికంగా వినియోగించేవారిని గుర్తించండి
3. ధరల డేటా తాజాగా ఉందని నిర్ధారించుకోండి: `POST /api/pricing/sync`

### "రికార్డులు కనిపించడం లేదు"

- డాష్‌బోర్డ్ → డేటాబేస్ → క్లీనప్ కింద DB నిల్వ వ్యవధి సెట్టింగ్‌లను తనిఖీ చేయండి — పాత రికార్డులు క్రమానుగత క్లీనప్ టాస్క్ (`src/lib/db/cleanup.ts`) ద్వారా తొలగించబడతాయి
- `src/lib/db/usage*.ts`లో లోపాలను తనిఖీ చేయండి — DB రైట్ వైఫల్యాలు లాగ్ చేయబడతాయి కానీ బయటకు చూపబడవు
- అభ్యర్థన నిజంగా `chatCore`కు చేరిందని నిర్ధారించుకోండి — కాంబో రూటింగ్‌ను తనిఖీ చేయండి

### "కోటా అమలు కావడం లేదు"

- కీ యొక్క `quotaLimit` సెట్టింగ్‌ను తనిఖీ చేయండి
- `quotaWindow` సరిగ్గా సెట్ చేయబడిందని నిర్ధారించుకోండి
- `quotaSnapshots` రికార్డుల కోసం చూడండి — ప్రతి అభ్యర్థనపై అవి సృష్టించబడాలి
