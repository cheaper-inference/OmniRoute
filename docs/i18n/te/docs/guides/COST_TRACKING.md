## ఇది ఏమిటి (మరియు ఏమి కాదు)

OmniRoute టోకెన్ సంఖ్యలను మోడల్ ధరల రేట్లతో గుణించడం ద్వారా ప్రతి కంప్లీషన్కు
ఒక్కో అభ్యర్థన USD ఖర్చును కేటాయిస్తుంది. ఈ సంఖ్యలు **ఖర్చులు** డ్యాష్బోర్డ్,
`omniroute cost` / `omniroute usage` CLI, CSV/JSON ఎగుమతులు మరియు ఒక్కో API కీ బడ్జెట్లకు
ఆధారంగా ఉంటాయి.

> **డ్యాష్బోర్డ్లోని "ఖర్చు" ఒక పొదుపుల ట్రాకర్, బిల్లు కాదు.** OmniRoute మీ నుండి ఎప్పుడూ
> రుసుము వసూలు చేయదు — మీరు ఇప్పటికే అనుసంధానించిన ప్రొవైడర్లకు (మీ స్వంత
> సబ్స్క్రిప్షన్లు, ఉచిత టైర్లు మరియు API కీలు) మీ అభ్యర్థనలను రూట్ చేస్తుంది. పూర్తిగా ఉచిత
> మోడల్లపై నమోదైన "$290 మొత్తం ఖర్చు" అంటే, చెల్లింపు APIకి మీరు సుమారుగా
> **$290 చెల్లించలేదని** అర్థం. అదే ట్రాఫిక్కు ప్రామాణిక జాబితా ధరల ప్రకారం ఎంత ఖర్చయ్యేదో
> ఈ సంఖ్య ఒక _అంచనా_; తద్వారా మీ వినియోగం ఎక్కడ కేంద్రీకృతమైందో, తక్కువ ధర/ఉచిత
> ప్రొవైడర్లకు రూటింగ్ చేయడం వల్ల మీరు ఎంత ఆదా చేస్తున్నారో చూడవచ్చు.

ఈ వివరణ ప్రాజెక్ట్ [README](../../README.md)లో నేరుగా పేర్కొనబడింది ("డ్యాష్బోర్డ్లోని
'ఖర్చు' ఒక పొదుపుల ట్రాకర్, బిల్లు కాదు").

ఈ సంఖ్య ఒక అంచనా కాబట్టి:

- ప్రతి మోడల్కు OmniRoute వద్ద ఉన్న ధరల పట్టికపై ఇది ఆధారపడి ఉంటుంది. ధర నమోదు లేని
  మోడల్ `0` ఖర్చును జోడిస్తుంది (ఎక్స్ప్లోరర్లో అది "లెగసీ / ఉచితం" వరుసగా కనిపిస్తుంది).
- ఉచిత-టైర్ మరియు సబ్స్క్రిప్షన్ ట్రాఫిక్కు కూడా _అంచనా_ ఖర్చు నమోదవుతుంది — అది
  మీరు ఆదా చేస్తున్న మొత్తం, చెల్లించాల్సిన మొత్తం కాదు.

## ఖర్చులు ఎలా అంచనా వేయబడతాయి

### ధర మూలం

ఈ ప్రాధాన్యత క్రమంలో [`src/lib/db/settings/pricing.ts`](../../src/lib/db/settings/pricing.ts) లో విలీనమైన ధరల పట్టిక నుండి ఖర్చులు వస్తాయి (**అత్యధిక మొదటి** ):

1. **వినియోగదారు భర్తీ చేస్తారు** — ధరలు డాష్బోర్డ్లో లేదా `PATCH /api/pricing` ( `pricing` నేమ్స్పేస్) ద్వారా సెట్ చేయబడ్డాయి.
2. **models.dev సమకాలీకరణ** — ధర `https://models.dev/api.json` ( `models_dev_pricing` నేమ్స్పేస్) నుండి పొందబడింది.
3. **LiteLLM సమకాలీకరణ** — ధరలు LiteLLM యొక్క పబ్లిక్ `model_prices_and_context_window.json` ( `pricing_synced` నేమ్స్పేస్) నుండి పొందబడ్డాయి.
4. **హార్డ్కోడ్ చేసిన డిఫాల్ట్లు** — రేట్లు [`src/shared/constants/pricing/`](../../src/shared/constants/pricing/) లో రవాణా చేయబడ్డాయి.

అదే provider/model కోసం, అధిక ప్రాధాన్యత కలిగిన లేయర్ల నుండి విలువలు తక్కువ లేయర్లలో సరిపోలే ఫీల్డ్లను ఓవర్రైట్ చేస్తాయి; ఎగువ పొరలో లేని ఫీల్డ్లు ఇప్పటికీ దిగువ పొర నుండి రావచ్చు. స్వతంత్ర సమకాలీకరణ ఉద్యోగాలు రెండూ ఒకే సమయంలో అమలు చేయబడినప్పుడు కూడా ఆర్డర్ స్థిరంగా ఉంటుంది. `GET /api/pricing?includeSources=1` తిరిగి `pricing` మరియు `sourceMap`, దీని ప్రతి-మోడల్ లేబుల్లు (`user`, `modelsDev`, `litellm`, `default`) ఆ మోడల్ను కలిగి ఉన్న అత్యధిక ప్రాధాన్యత కలిగిన లేయర్ను గుర్తిస్తాయి.

**LiteLLM సమకాలీకరణ** ప్రారంభించబడింది, డిఫాల్ట్గా నిలిపివేయబడింది. దీని ఎన్విరాన్మెంట్ వేరియబుల్స్ ( [`.env.example`](../../.env.example) చూడండి):

| ఎన్వి వర్               | డిఫాల్ట్  | ప్రయోజనం                                                                      |
| ----------------------- | --------- | ----------------------------------------------------------------------------- |
| `PRICING_SYNC_ENABLED`  | `false`   | నేపథ్య LiteLLM ధర సమకాలీకరణను ప్రారంభించండి.                                  |
| `PRICING_SYNC_INTERVAL` | `86400`   | సెకన్లలో (రోజువారీ) విరామం సమకాలీకరించండి.                                    |
| `PRICING_SYNC_SOURCES`  | `litellm` | ఈ సమకాలీకరణ కోసం మాత్రమే మూలం ఎంపిక; ప్రస్తుతం `litellm` మాత్రమే మద్దతు ఉంది. |

**models.dev సమకాలీకరణ** LiteLLM సమకాలీకరణ నుండి వేరుగా ఉంటుంది మరియు డిఫాల్ట్గా కూడా నిలిపివేయబడుతుంది. దీన్ని సెట్టింగ్లలో (models.dev సమకాలీకరణ) ప్రారంభించండి లేదా ఈ వేరియబుల్లను ఉపయోగించండి:

| ఎన్వి వర్                  | డిఫాల్ట్         | ప్రయోజనం                                                                                                                                       |
| -------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `MODELS_DEV_SYNC_ENABLED`  | _(సెట్ చేయనిది)_ | సెట్టింగుల టోగుల్ను అన్సెట్ చేస్తుంది; `1/true/on/yes` ఫోర్స్ ఆన్ మరియు `0/false/off/no` ఫోర్స్ ఆఫ్ (సెట్టింగ్లు దీన్ని ఎనేబుల్ చేసినప్పటికీ). |
| `MODELS_DEV_SYNC_INTERVAL` | `86400`          | డిఫాల్ట్ models.dev సమకాలీకరణ విరామం సెకన్లలో (రోజువారీ).                                                                                      |

`PRICING_SYNC_SOURCES` చేస్తుంది**కాదు** models.devని ప్రారంభించు; ఇది LiteLLM సమకాలీకరణను మాత్రమే నియంత్రిస్తుంది. వినియోగదారు ఓవర్రైడ్ను తొలగించడం వలన సమకాలీకరించబడిన నేమ్స్పేస్ క్లియర్ చేయబడదు; తదుపరి అందుబాటులో ఉన్న ధర లేయర్ ప్రభావవంతంగా మారుతుంది. ధర లేని మోడల్ కోసం, మాన్యువల్ ఓవర్రైడ్ను జోడించే ముందు సమకాలీకరణ సెట్టింగ్లు మరియు `sourceMap` రెండింటినీ తనిఖీ చేయండి.

### ఖర్చు సూత్రం

[`src/lib/usage/costCalculator.ts`](../../src/lib/usage/costCalculator.ts) (`computeCostFromPricing` / `calculateCost`)లో టోకెన్ గణనలు మరియు ప్రతి-మిలియన్-టోకెన్ రేట్ల నుండి అభ్యర్థనకు ధర గణించబడుతుంది:

- **ఇన్పుట్ టోకెన్లు** (మైనస్ కాష్ రీడ్లు మరియు కాష్-క్రియేషన్ టోకెన్లు) × `input` రేట్.
- **కాష్-రీడ్ టోకెన్లు** × `cached` రేటు (ఇన్పుట్ రేట్కి తిరిగి వస్తుంది).
- **కాష్-క్రియేషన్ టోకెన్లు** × `cache_creation` రేటు (ఇన్పుట్ రేట్కి తిరిగి వస్తుంది).
- **అవుట్పుట్ టోకెన్లు** × `output` రేటు.
- **రీజనింగ్ టోకెన్లు** × `reasoning` రేటు (అవుట్పుట్ రేట్కి తిరిగి వస్తుంది).

అన్ని రేట్లు 1,000,000 టోకెన్లకు USD గా వివరించబడతాయి. Codex "ఫాస్ట్"/"ప్రాధాన్యత" లేదా "ఫ్లెక్స్" సర్వీస్ టైర్ ధర గుణకం (`getCodexFastCostMultiplier`) — వర్తింపజేస్తుంది ఉదా. ఫ్లెక్స్ 50% టోకెన్ తగ్గింపుతో బిల్ చేయబడుతుంది.**ఫ్లెక్స్ పొదుపు** డాష్బోర్డ్లో.

మోడల్ పేర్లు ముందుగా సాధారణీకరించబడతాయి ( `openai/` లేదా `accounts/fireworks/models/` వంటి ప్రొవైడర్-పాత్ ప్రిఫిక్స్లు తీసివేయబడతాయి) కాబట్టి చారిత్రక వరుసలు ఇప్పటికీ ధరతో సరిపోలుతున్నాయి.

### ఖర్చు ఎలా నమోదు చేయబడింది

- అభ్యర్థన పూర్తయిన తర్వాత ఒక్కో అభ్యర్థన ధర గణించబడుతుంది. [`src/lib/quota/spendRecorder.ts`](../../src/lib/quota/spendRecorder.ts) ద్వారా తదుపరి ఈవెంట్-లూప్ టిక్లో షేర్డ్-కోటా వినియోగం షెడ్యూల్ చేయబడింది.
- API-కీ ఖర్చు [`SpendBatchWriter`](../../src/lib/spend/batchWriter.ts) (డిఫాల్ట్ 60s ఫ్లష్ విరామం, 1,000-ఎంట్రీ బఫర్) ద్వారా బ్యాచ్లలో బఫర్ చేయబడింది మరియు ఫ్లష్ చేయబడుతుంది. దీని ద్వారా ట్యూన్ చేయవచ్చు:

  | ఎన్వి వర్                           | డిఫాల్ట్ | ప్రయోజనం                                             |
  | ----------------------------------- | -------- | ---------------------------------------------------- |
  | `OMNIROUTE_SPEND_FLUSH_INTERVAL_MS` | `60000`  | మిల్లీసెకన్లలో ఫ్లష్ విరామం.                         |
  | `OMNIROUTE_SPEND_MAX_BUFFER_SIZE`   | `1000`   | ఫ్లష్ చేయడానికి ముందు గరిష్టంగా బఫర్ చేసిన ఎంట్రీలు. |

ఖర్చులు ఖచ్చితమైన ప్రొవైడర్-నివేదిత ఛార్జ్ (`provider_cost_usd`), ఆపై కేటలాగ్-ధర అభ్యర్థన స్నాప్షాట్ (`calculated_cost_usd`), ఆపై ప్రస్తుత కేటలాగ్ నుండి టోకెన్ రీప్రైకింగ్ను ఇష్టపడతాయి. నిల్వ చేసిన ఖర్చులు వాటి టోకెన్ గణనల ద్వారా మళ్లీ వసూలు చేయబడవు. లెగసీ టోకెన్-మాత్రమే అడ్డు వరుసలు వాటి కేటలాగ్ ధర మారినప్పుడు ఇప్పటికీ మారుతాయి.

### OCR మరియు ఎంబెడ్డింగ్లు

- విజయవంతమైన `/v1/ocr` అభ్యర్థనలు అప్స్ట్రీమ్ `usage_info.pages_processed` ఉపయోగిస్తాయి, అభ్యర్థించిన పేజీ పరిధి లేదా తిరిగి వచ్చిన పేజీ ఆబ్జెక్ట్ల సంఖ్య కాదు. అంచనా పేజీలు × `ocr_cost_per_page` (సంపూర్ణ USD/page,**కాదు** USD/million).
- డాక్యుమెంట్ లేదా బౌండింగ్-బాక్స్ ఉల్లేఖనాలతో కూడిన అభ్యర్థనలకు ప్రత్యేక `ocr_cost_per_annotated_page` టారిఫ్ అవసరం. అది లేకుండా, ఖర్చు తెలియదు; సాధారణ OCR టారిఫ్ నిశ్శబ్దంగా భర్తీ చేయబడదు.
- LiteLLM సమకాలీకరణ దాని అప్స్ట్రీమ్ `annotation_cost_per_page` ఫీల్డ్ను `ocr_cost_per_annotated_page` లోకి మ్యాప్ చేస్తుంది, సంపూర్ణ USD/page విలువను మరియు స్పష్టమైన సున్నాతో సహా ఉల్లేఖన-మాత్రమే నమోదులను నిలుపుకుంటుంది. సరఫరా చేయబడిన కానానికల్ ఫీల్డ్ ప్రాధాన్యతనిస్తుంది; చెల్లని అలియాస్ విలువలు విస్మరించబడ్డాయి. వినియోగదారు ధర ఓవర్రైడ్లు వారి సాధారణ ప్రాధాన్యతను కలిగి ఉంటాయి. [LiteLLM యొక్క OCR ప్రైసింగ్ కీలను](https://docs.litellm.ai/docs/providers/mistral_batches#batch-ocr-cost-tracking) చూడండి.
- OCR వినియోగం పేజీ గణన, యూనిట్ ధర, లెక్కించిన USD ధర, API కీ మరియు ఎంచుకున్న కనెక్షన్ను నిల్వ చేస్తుంది. పేజీలు ఎప్పుడూ టోకెన్లుగా సూచించబడవు. కాల్ లాగ్లు బిల్లింగ్ మెటాడేటాను కలిగి ఉంటాయి, డాక్యుమెంట్ URLs, PDF బైట్లు లేదా సంగ్రహించిన టెక్స్ట్ కాదు.
- విజయవంతమైన `/v1/embeddings` అభ్యర్థనలు ఒకే మిల్లీసెకన్లో పూర్తి చేయబడిన ప్రత్యేక బ్యాచ్లతో సహా భౌతిక బ్యాచ్కు ఒక వినియోగ వరుసను రికార్డ్ చేస్తాయి. టోకెన్ అంచనాల కంటే ప్రొవైడర్ నివేదించిన ఛార్జీలు ప్రాధాన్యతనిస్తాయి; కాంబో రేపర్లు ఛార్జ్ను జోడించవు.
- వినియోగ చరిత్ర, ఖర్చుల విశ్లేషణలు, provider/account విండోస్, API-కీ ఖర్చు పరిమితులు, అభ్యర్థన-ధర లెడ్జర్ మరియు రోజువారీ వినియోగ రోల్అప్లు ఈ ఛార్జీలను కలిగి ఉంటాయి. నో-లాగ్ కీలు మూల వచనాన్ని ఉంచకుండా సంఖ్యాపరమైన అకౌంటింగ్ను కలిగి ఉంటాయి.
- తప్పిపోయిన వినియోగం లేదా సుంకాలు**తెలియని** , ఉచితం కాదు: ప్రతిస్పందన-ధర శీర్షిక విస్మరించబడింది మరియు ఇప్పటికే ఉన్న ధర లేని వినియోగ విధానం పరిమిత API కీలకు వర్తిస్తుంది. స్పష్టంగా కాన్ఫిగర్ చేయబడిన సున్నా రేట్లు చెల్లుబాటు అయ్యే సున్నా-ధర వినియోగంగానే ఉంటాయి.

ఇది ఫార్వర్డ్-ఓన్లీ అకౌంటింగ్. వినియోగ చరిత్రను ఎన్నడూ వ్రాయని పాత OCR/embedding కాల్లు ఈ మైగ్రేషన్ నుండి పునర్నిర్మించబడవు. కేటలాగ్ అంచనాలు USD అంచనాలు, ఇన్వాయిస్ కాదు మరియు కరెన్సీ మార్పిడి, పన్ను లేదా తగ్గింపులను కలిగి ఉండవు.

### ప్రసంగం మరియు చిత్రాలు

- విజయవంతమైన `/v1/audio/transcriptions`, `/v1/audio/speech` మరియు ఇమేజ్-జనరేషన్ ప్రయత్నాలు సంఖ్యాపరమైన అకౌంటింగ్ను పంచుకుంటాయి. డైరెక్ట్ మరియు కాంబో కాల్లు కాలర్ యొక్క API కీ మరియు ఎంచుకున్న కనెక్షన్ని కలిగి ఉంటాయి; కాంబో రేపర్ ఎప్పుడూ రెండవ డెబిట్ను జోడించదు.
- ప్రొవైడర్ నివేదించిన USD స్పష్టమైన సున్నా ఛార్జీతో సహా కేటలాగ్ అంచనాపై గెలుపొందింది. OpenRouter యొక్క JSON `usage.cost` `cost_usd` కి సాధారణీకరించబడింది. లేకపోతే, కొలిచిన టోకెన్లు టోకెన్ ధరలను ఉపయోగిస్తాయి, ట్రాన్స్క్రిప్షన్ సెకన్లు ప్రతి సెకను ధరలను ఉపయోగిస్తాయి, స్పీచ్ ఇన్పుట్ యూనికోడ్ క్యారెక్టర్ గణనలను ఉపయోగిస్తుంది మరియు ఫ్లాట్-ప్రైస్ ఇమేజ్లు అభ్యర్థించిన `n` కాకుండా వాస్తవానికి తిరిగి వచ్చిన సంఖ్యను ఉపయోగిస్తాయి.
- బైనరీ OpenRouter TTS JSON యూసేజ్ బాడీ లేదు. ఆడియో పూర్తయిన తర్వాత లేదా కాలర్ రద్దు చేసిన తర్వాత, OmniRoute దాని తరం ID ప్రశ్నిస్తుంది**అదే** OpenRouter మూలం కాన్ఫిగర్ చేయబడింది. EU అభ్యర్థన గ్లోబల్ మూలానికి తిరిగి రాదు. ఇది పరిమితమైన, చదవడానికి-మాత్రమే శోధన; అకౌంటింగ్ కోసం సంశ్లేషణ మళ్లీ ప్రయత్నించబడలేదు. ఆడియో పూర్తయిన తర్వాత బిల్లింగ్ రికార్డ్లు కనిపిస్తాయి: నెట్వర్క్ గడువులతో సహా దాదాపు 52 సెకన్ల వరకు బ్యాక్గ్రౌండ్లో లుక్అప్ రీట్రీలు అమలవుతాయి.
- ఆ శోధన సమయంలో, ఆడియో ప్రతిస్పందనలో `X-OmniRoute-Cost-Status: pending` ఉంది మరియు ప్రతిస్పందన-ధర శీర్షిక లేదు. దాని తుది ఛార్జ్ వినియోగ చరిత్ర, విశ్లేషణలు మరియు సయోధ్య తర్వాత కీ లెడ్జర్లో కనిపిస్తుంది. మెటాడేటా అందుబాటులో లేకుంటే, కాన్ఫిగర్ చేయబడిన టారిఫ్ స్నాప్షాట్ ఉపయోగించబడుతుంది; లేకుంటే ఖర్చు తెలియదు.
- సెకన్లు, అక్షరాలు మరియు చిత్ర గణనలు వేర్వేరు బిల్లింగ్-యూనిట్ ఫీల్డ్లను కలిగి ఉంటాయి, ఎప్పుడూ నకిలీ టోకెన్ గణనలు ఉండవు. అకౌంటింగ్ కేవలం సంఖ్యాపరమైన వినియోగాన్ని మాత్రమే కలిగి ఉంటుంది, ప్రసంగ వచనం, ట్రాన్స్క్రిప్ట్లు లేదా ఇమేజ్ బైట్లను కాదు. ప్రస్తుతం ఉన్న ధరలేని-చిత్రం మినహాయింపులు మారవు: వాస్తవంగా తప్పిపోయిన ఇమేజ్ టారిఫ్ పరిమిత కీని కొత్తగా లాక్ చేయదు మరియు ప్రతిస్పందన కాల్ను ఉచితంగా ప్రకటించకుండా ఖర్చు హెడర్ను విస్మరిస్తుంది. ప్రైసింగ్ స్టోర్ వైఫల్యం ఇప్పటికీ ఫెయిల్-క్లోజ్డ్ ఎన్ఫోర్స్మెంట్ కోసం వినియోగ సాక్ష్యాలను కలిగి ఉంది.

చారిత్రక speech/image ఛార్జ్ కనుగొనబడలేదు లేదా తిరిగి పూరించబడలేదు. ఇన్వాయిస్లు మరియు ఛార్జ్ నివేదించబడని కాల్లకు ప్రొవైడర్ బిల్లింగ్ సూచనగా మిగిలిపోయింది.

ఇది `GET /api/usage/analytics` నుండి మొత్తం డేటాను లోడ్ చేస్తుంది.

ఇది చూపించేవి:

- **వ్యయ టైల్స్** — _ఈ రోజు (1d)_, _7d_, _30d_, అలాగే ఎంచుకున్న
  వ్యవధికి అంచనా వ్యయం. వ్యవధి ఎంపిక సాధనం: `7d`, `30d`, `90d`, `all`.
- **ప్రధాన మెట్రిక్లు** — వ్యవధిలోని అభ్యర్థనలు, సక్రియ ప్రొవైడర్లు, సక్రియ మోడళ్లు, ఒక్కో
  అభ్యర్థనకు సగటు ఖర్చు.
- **ఖర్చుల ఎక్స్ప్లోరర్** — **ప్రొవైడర్**, **మోడల్**,
  **API కీ**, **ఖాతా** లేదా **సేవా స్థాయి** ఆధారంగా సమూహపరచగల, క్రమబద్ధీకరించగల/ఫిల్టర్ చేయగల పట్టిక; ఇందులో ఖర్చు, అభ్యర్థనలు, టోకెన్లు, సగటు
  ఖర్చు/అభ్యర్థన, అలాగే మొత్తం ఖర్చులో వాటా % ఉంటాయి.
- **టోకెన్ వినియోగం** — మొత్తం / ఇన్పుట్ / అవుట్పుట్ టోకెన్లు మరియు ఇన్పుట్:అవుట్పుట్ నిష్పత్తి.
- **రూటింగ్ సామర్థ్యం** — ఫాల్బ్యాక్ల సంఖ్య, ఫాల్బ్యాక్ రేటు, అలాగే అభ్యర్థించిన-మోడల్ కవరేజ్.
- **నెలవారీ అంచనా** — ఇటీవలి రోజువారీ సగటు ఆధారంగా నెలాఖరు వ్యయాన్ని అంచనా వేస్తుంది.
- **వ్యవధి పోలిక** — వ్యవధిలోని మొదటి, రెండవ భాగాల మధ్య % మార్పు.
- **చార్ట్లు** — రోజువారీ ఖర్చు ధోరణి, ప్రొవైడర్ వాటా (పై), అగ్ర ప్రొవైడర్లు, అగ్ర మోడళ్లు, API కీ
  వారీగా ఖర్చు, ఖాతా వారీగా ఖర్చు, వారపు వినియోగ నమూనా, అలాగే కార్యాచరణ హీట్మ్యాప్.
- **ఎగుమతి** — ప్రస్తుత వ్యవధిని **CSV** లేదా **JSON** రూపంలో డౌన్లోడ్ చేయండి (సున్నా కంటే ఎక్కువ ఖర్చు డేటా
  ఉన్నప్పుడు బటన్లు కనిపిస్తాయి).

ధర నిర్ణయించబడిన ట్రాఫిక్ లేనప్పుడు, వరుసలు `$0`కు బదులుగా "లెగసీ / ఉచితం" లేబుల్ను చూపిస్తాయి,
ఇది పొదుపు-ట్రాకర్ నమూనాను ప్రతిబింబిస్తుంది.

### సంబంధిత ఖర్చుల ఉప-పేజీలు

ఖర్చుల విభాగంలో ఇవి కూడా ఉంటాయి (అన్నీ `/dashboard/costs/` కింద):

- **ధరలు** (`/dashboard/costs/pricing`) — ఒక్కో మోడల్ ధరలను వీక్షించి, ఓవర్రైడ్ చేయండి (భాగస్వామ్య
  ధరల ట్యాబ్ను రెండర్ చేస్తుంది).
- **బడ్జెట్** (`/dashboard/costs/budget`) — ఒక్కో స్కోప్కు వ్యయ పరిమితులను సెట్ చేయండి (భాగస్వామ్య
  బడ్జెట్ ట్యాబ్ను రెండర్ చేస్తుంది).
- **కోటా భాగస్వామ్యం** (`/dashboard/costs/quota-share`) — భాగస్వామ్య-కోటా పూల్లు మరియు వినియోగ-రేటు
  వీక్షణలు.

## API ఎండ్పాయింట్లు

వేరుగా పేర్కొనని పక్షంలో, వీటన్నింటికీ నిర్వహణ ప్రమాణీకరణ (లూప్బ్యాక్/JWT, `requireManagementAuth` ద్వారా)
అవసరం.

### వినియోగం & ఖర్చు విశ్లేషణ

| పద్ధతి | ఎండ్పాయింట్              | ప్రయోజనం                                                                                                                                                            |
| ------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`  | `/api/usage/analytics`   | పూర్తి ఖర్చు/వినియోగ విశ్లేషణ: సారాంశం, రోజువారీ ధోరణి, ప్రొవైడర్/మోడల్/API కీ/ఖాతా/స్థాయి వారీగా. క్వెరీ: `range`, `startDate`, `endDate`, `apiKeyIds`, `presets`. |
| `GET`  | `/api/usage/utilization` | కాలక్రమంలో ఒక్కో ప్రొవైడర్ కోటా వినియోగం. క్వెరీ: `range` (`1h`/`24h`/`7d`/`30d`), `provider`.                                                                      |
| `GET`  | `/api/usage/history`     | ముడి వినియోగ చరిత్ర వరుసలు.                                                                                                                                         |
| `GET`  | `/api/usage/call-logs`   | ఒక్కో అభ్యర్థన కాల్ లాగ్లు (మోడల్, టోకెన్లు, ఖర్చు, లేటెన్సీ, స్థితి).                                                                                              |
| `GET`  | `/api/usage/quota`       | ప్రొవైడర్ కోటా స్థితి.                                                                                                                                              |
| `GET`  | `/api/usage/proxy-logs`  | ప్రాక్సీ అభ్యర్థన లాగ్లు.                                                                                                                                           |

### బడ్జెట్లు

| పద్ధతి | ఎండ్పాయింట్              | ప్రయోజనం                                                                                 |
| ------ | ------------------------ | ---------------------------------------------------------------------------------------- |
| `GET`  | `/api/usage/budget`      | ఒక API కీ కోసం ఖర్చు సారాంశం + బడ్జెట్ తనిఖీ (`apiKeyId` క్వెరీ పారామీటర్ అవసరం).        |
| `POST` | `/api/usage/budget`      | ఒక API కీ కోసం రోజువారీ/వారపు/నెలవారీ USD పరిమితులు + హెచ్చరిక థ్రెషోల్డ్ను సెట్ చేయండి. |

## CLI

OmniRoute యొక్క CLI, ఖర్చు, వినియోగం మరియు ధరల కమాండ్లను అందిస్తుంది (ఇవి
[`bin/cli/commands/registry.mjs`](../../bin/cli/commands/registry.mjs)లో నమోదు చేయబడ్డాయి).

### `omniroute cost`

`/api/usage/analytics` నుండి సమగ్రపరచిన ఖర్చు నివేదిక.

```bash
omniroute cost                          # గత 30 రోజులు, ప్రొవైడర్ వారీగా సమూహీకరించబడుతుంది
omniroute cost --period 7d              # గత 7 రోజులు
omniroute cost --group-by model         # provider | model | combo | api-key | day ఆధారంగా సమూహీకరించండి
omniroute cost --since 2026-06-01 --until 2026-06-13
omniroute cost --api-key <key> --limit 50
```

నిలువు వరుసలు: సమూహం, అభ్యర్థనలు, ఇన్పుట్/అవుట్పుట్ టోకెన్లు, ఖర్చు (USD) మరియు మొత్తం శాతం. చివరలో
సర్వమొత్తం పంక్తి ప్రదర్శించబడుతుంది (`--quiet` లేదా `--output json`తో ఇది అణచివేయబడుతుంది).

### `omniroute usage`

```bash
omniroute usage analytics --period 30d [--provider <id>]   # ప్రతి ప్రొవైడర్కు ఖర్చు సారాంశం
omniroute usage logs [--limit 100] [--follow] [--api-key <k>] [--search <q>]
omniroute usage quota [--provider <id>] [--check]
omniroute usage utilization [--api-key <k>]
omniroute usage history [--limit 100]
omniroute usage proxy-logs [--limit 100]

# బడ్జెట్లు
omniroute usage budget list
omniroute usage budget get [scope]
omniroute usage budget set <amount> [--scope global] [--period monthly]
omniroute usage budget reset [scope]
```

### `omniroute pricing`

```bash
omniroute pricing list [--provider <p>] [--model <m>] [--limit 200]
omniroute pricing get <model>
omniroute pricing sync [--provider <p>] [--force]   # POST /api/pricing/sync
omniroute pricing diff [--model <m>]
omniroute pricing defaults show
omniroute pricing defaults set [--input <p>] [--output <p>] [--cache-read <p>] [--cache-write <p>]
```

> `pricing defaults show`, `GET /api/pricing/defaults` నుండి చదువుతుంది. దానికి బదులుగా వ్యక్తిగత మోడల్
> ధరలను సవరించడానికి, **Pricing** డ్యాష్బోర్డ్ పేజీని లేదా `PATCH /api/pricing`ను ఉపయోగించండి.

## సమస్య పరిష్కారం

- **అన్ని ఖర్చులు $0 / "Legacy / Free"గా కనిపిస్తున్నాయి.** ఉపయోగంలో ఉన్న మోడల్లకు ధర నమోదు లేదు.
  బాహ్య సమకాలీకరణను ప్రారంభించి (`PRICING_SYNC_ENABLED=true`), `omniroute pricing sync`ను అమలు చేయండి లేదా
  Pricing పేజీ / `PATCH /api/pricing` ద్వారా ధరలను మాన్యువల్గా సెట్ చేయండి.
- **చారిత్రక మోడల్కు తప్పుగా ధర నిర్ణయించబడింది.** ధరను సరిచేయండి (ఓవర్రైడ్ చేయండి లేదా మళ్లీ సమకాలీకరించండి) — ప్రతి అనలిటిక్స్ రీడ్లోనూ టోకెన్ల సంఖ్య నుండి ఖర్చు
  మళ్లీ లెక్కించబడుతుంది, కాబట్టి అంచనాలు గత కాలానికి కూడా నవీకరించబడతాయి.
- **ఖర్చు నిజ సమయం కంటే ఆలస్యంగా కనిపిస్తోంది.** ప్రతి కీకి సంబంధించిన ఖర్చు బ్యాచ్లుగా ప్రాసెస్ చేయబడుతుంది; మరింత తాజా సంఖ్యలు అవసరమైతే
  `OMNIROUTE_SPEND_FLUSH_INTERVAL_MS`ను తగ్గించండి.
