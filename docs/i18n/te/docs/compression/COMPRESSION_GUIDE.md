> అర్హమైన సందర్భంపై స్వయంచాలకంగా 15-95% ఆదా చేయండి. త్వరిత అవలోకనం కోసం, [README Compression విభాగం](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) చూడండి.

## అవలోకనం

OmniRoute, అభ్యర్థనలు అప్స్ట్రీమ్ ప్రొవైడర్లకు చేరకముందే **ముందస్తుగా** అమలయ్యే మాడ్యులర్ ప్రాంప్ట్ కంప్రెషన్ పైప్లైన్ను అమలు చేస్తుంది. అంటే మీ టోకెన్ ఆదా పారదర్శకంగా జరుగుతుంది — మీ వర్క్ఫ్లోలో ఎలాంటి మార్పులు అవసరం లేదు.

```
క్లయింట్ అభ్యర్థన
  → కంప్రెషన్ వ్యూహ ఎంపిక సాధనం
    → కాంబో ఓవర్రైడ్ ఉందా? → కాంబో సెట్టింగ్ను ఉపయోగించండి
    → ఆటో-ట్రిగ్గర్ థ్రెషోల్డ్ చేరిందా? → ఆటో మోడ్ను ఉపయోగించండి
    → డిఫాల్ట్ మోడ్ ఉందా? → గ్లోబల్ సెట్టింగ్ను ఉపయోగించండి
    → Offలో ఉందా? → కంప్రెషన్ను దాటవేయండి
  → ఎంచుకున్న కంప్రెషన్ మోడ్
    → Off: కంప్రెషన్ లేదు
    → Lite: సురక్షితమైన వైట్స్పేస్/ఫార్మాటింగ్ శుభ్రపరచడం (~15%)
    → Standard: Caveman-శైలి అనవసర పదాల తొలగింపు (~30%)
    → Aggressive: హిస్టరీ ఏజింగ్ + సారాంశీకరణ (~50%)
    → Ultra: హ్యూరిస్టిక్ ప్రూనింగ్ + కోడ్-బ్లాక్ సన్నబరచడం (~75%)
    → RTK: కమాండ్ను గుర్తించే టెర్మినల్/టూల్-అవుట్పుట్ ఫిల్టరింగ్ (60-90% అప్స్ట్రీమ్ పరిధి)
    → Stacked: క్రమబద్ధమైన బహుళ-ఇంజిన్ పైప్లైన్, సాధారణంగా RTK తర్వాత Caveman (78-95% అర్హమైన పరిధి)
  → కంప్రెస్ చేసిన అభ్యర్థన → ప్రొవైడర్
```

## కంప్రెషన్ మోడ్లు

### ఆఫ్

కంప్రెషన్ వర్తించదు. అన్ని సందేశాలు మార్పు లేకుండా పంపబడతాయి.

### Lite మోడ్ (~15% ఆదా, <1ms ఆలస్యం)

అత్యంత సురక్షితమైన మోడ్ — ఫార్మాటింగ్ శుభ్రపరచడం. దీని టూల్-రిజల్ట్ ట్రంకేషన్ నష్టపూరితమైనది కాబట్టి, డిఫాల్ట్
పాత్ (`allow-lossy`, `engine:lite` లేదా పేరున్న కాంబో ఆప్ట్-ఇన్ లేకుండా) `compressToolResults: false`తో lite మోడ్లో నడుస్తుంది:
మునుపటి టూల్ రిజల్ట్లు మార్పు లేకుండా ప్రొవైడర్కు చేరతాయి.

| టెక్నిక్                 | వివరణ                                                                                        |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | వరుసగా ఉన్న ఖాళీ లైన్లు మరియు చివరి ఖాళీలను విలీనం చేయడం                                     |
| `dedupSystemPrompt`      | నకిలీ సిస్టమ్ సందేశాలను తొలగించడం                                                            |
| `compressToolResults`    | మునుపటి టూల్ రిజల్ట్లను lite పరిమితికి కుదించడం (నష్టపూరితం: రిక్వెస్ట్ ఆప్ట్-ఇన్తో మాత్రమే) |
| `removeRedundantContent` | పునరావృత సూచనలను తొలగించడం                                                                   |
| `replaceImageUrls`       | base64 ఇమేజ్ డేటా URIలను సంక్షిప్తం చేయడం                                                    |

**దీనికి ఉత్తమం:** ఎల్లప్పుడూ-ఆన్ వినియోగం, భద్రతా-కీలక వర్క్ఫ్లోలు.

### Standard మోడ్ (~30% ఆదా)

[Caveman](https://github.com/JuliusBrussee/caveman) నుండి ప్రేరణ పొందింది — అర్థాన్ని కాపాడుతూ పూరక పదాలు మరియు విస్తృతమైన పదబంధాలను తొలగిస్తుంది:

- పూరక పదాలను తొలగిస్తుంది ("please", "I think", "basically", "actually")
- విస్తృతమైన పదబంధాలను సంక్షిప్తం చేస్తుంది ("in order to" → "to", "as a result of" → "because")
- వినయపూర్వకమైన సందేహ సూచనలను తొలగిస్తుంది ("Would you mind...", "If you could possibly...")
- కోడింగ్ ప్రాంప్ట్ల కోసం మెరుగుపరచిన 30+ regex నియమాలు

**దీనికి ఉత్తమం:** రోజువారీ కోడింగ్ వర్క్ఫ్లోలు, ఖర్చు-చేతన బృందాలు.

### Aggressive మోడ్ (~50% ఆదా)

దీర్ఘకాలిక సెషన్ల కోసం స్మార్ట్ హిస్టరీ నిర్వహణ:

- **మెసేజ్ ఏజింగ్** — పాత సందేశాలు క్రమంగా మరింతగా కుదించబడతాయి
- **టూల్ రిజల్ట్ కంప్రెషన్** — దీర్ఘమైన టూల్ అవుట్పుట్లు ట్రంకేట్ లేదా ఎలైడ్ చేయబడతాయి (మొదటి/చివరి
  లైన్లు, మ్యాచ్-లైన్ ఫిల్టరింగ్, JSON కీ కాంపాక్షన్)
- **స్ట్రక్చరల్ ఇంటెగ్రిటీ గార్డ్స్** — `tool_use` + `tool_result` జతలు సుసంగతంగా ఉండేలా నిర్ధారిస్తాయి
- **కాంటెక్స్ట్ విండో అవగాహన** — ప్రతి మోడల్ టోకెన్ పరిమితులను గౌరవిస్తుంది

**దీనికి ఉత్తమం:** విస్తృత డీబగ్గింగ్ సెషన్లు, పెద్ద కోడ్బేస్లు.

### Ultra మోడ్ (~75% ఆదా)

టోకెన్-కీలక సందర్భాల కోసం గరిష్ఠ కంప్రెషన్:

- **హ్యూరిస్టిక్ ప్రూనింగ్** — ప్రోస్లో స్కోర్-ఆధారిత టోకెన్ తొలగింపు
- **స్ట్రక్చర్ పరిరక్షణ** — ఫెన్స్డ్ కోడ్ బ్లాక్లు, ఇన్లైన్ కోడ్, URLలు మరియు ఐడెంటిఫైయర్లు
  టాంబ్స్టోన్ చేసి, అక్షరాలా మళ్లీ కుట్టబడతాయి; ఎప్పుడూ తొలగించబడవు
- **ఐచ్ఛిక SLM స్థాయి** — కాన్ఫిగర్ చేసినప్పుడు చిన్న లోకల్ మోడల్ ప్రూన్ను మెరుగుపరచగలదు
- Aggressive మోడ్కు స్వతంత్రం: ఇది మెసేజ్ ఏజింగ్, టూల్-రిజల్ట్ కంప్రెషన్
  లేదా ఫాల్బ్యాక్ సమ్మరైజర్ను అమలు చేయదు (SLM-స్థాయి వైఫల్యం మాత్రమే ఫాల్బ్యాక్ పాస్ను
  aggressive ద్వారా రూట్ చేయగలదు)

**దీనికి ఉత్తమం:** మీరు పదేపదే కాంటెక్స్ట్ పరిమితులను తాకుతున్నప్పుడు.

### RTK మోడ్ (అప్స్ట్రీమ్ పరిధిలో 60-90%)

కోడింగ్-ఏజెంట్ సెషన్లలో కనిపించే విస్తృతమైన టూల్ అవుట్పుట్ల కోసం RTK మోడ్ ఆప్టిమైజ్ చేయబడింది:

- `git status`, `git diff`, `git log`, టెస్ట్ రన్నర్లు,
  TypeScript/Vite/Webpack బిల్డ్లు, ESLint/Biome/Prettier, npm ఆడిట్/ఇన్స్టాల్లు, Docker లాగ్లు, ఇన్ఫ్రా
  అవుట్పుట్ మరియు సాధారణ షెల్ అవుట్పుట్ వంటి కమాండ్/అవుట్పుట్ తరగతులను గుర్తిస్తుంది
- `open-sse/services/compression/engines/rtk/filters/` నుండి JSON ఫిల్టర్ ప్యాక్లను వర్తింపజేస్తుంది
- ప్రాజెక్ట్ లేదా గ్లోబల్ `filters.toml` ఫైళ్ల నుండి RTK TOML స్కీమా v1 ఫిల్టర్లను దిగుమతి చేస్తుంది, ఇన్లైన్-టెస్ట్
  ధృవీకరణ మరియు ప్రాజెక్ట్ ఫైళ్ల కోసం ట్రస్ట్-గేటింగ్తో
- ఇన్లైన్ వెరిఫై శాంపిళ్లతో 56 బిల్ట్-ఇన్ ఫిల్టర్లను అందిస్తుంది
- ANSI కంట్రోల్ సీక్వెన్స్లు, ప్రోగ్రెస్ బార్లు, పునరావృత లైన్లు మరియు చర్యకు ఉపయోగపడని శబ్దాన్ని తొలగిస్తుంది
- వైఫల్యాలు, లోపాలు, హెచ్చరికలు, మార్చబడిన ఫైళ్లు, సారాంశాలు మరియు దీర్ఘమైన అవుట్పుట్ చివరి భాగాన్ని కాపాడుతుంది
- ట్రస్ట్-గేటెడ్ ప్రాజెక్ట్ ఫిల్టర్లు, గ్లోబల్ ఫిల్టర్లు మరియు ఐచ్ఛిక రెడాక్ట్ చేసిన రా-అవుట్పుట్ రికవరీకి మద్దతు ఇస్తుంది

**దీనికి ఉత్తమం:** షెల్, బిల్డ్, టెస్ట్, git, grep మరియు ఫైల్-అవుట్పుట్ ట్రాన్స్క్రిప్ట్లతో కూడిన ఏజెంట్ సెషన్లు.

### Stacked మోడ్ (అర్హత ఉన్న పరిధిలో 78-95%)

Stacked మోడ్ అనేక కంప్రెషన్ ఇంజిన్లను నిర్ణీత క్రమంలో నడుపుతుంది. డిఫాల్ట్ పైప్లైన్:

```txt
RTK -> Caveman
```

ఈ క్రమం ముందుగా టెర్మినల్/టూల్ అవుట్పుట్ను సంక్షిప్తంగా ఉంచుతుంది, తరువాత మిగిలిన సహజ-భాషా ప్రాంప్ట్కు Caveman సెమాంటిక్ కండెన్సేషన్ను వర్తింపజేస్తుంది. Stacked పైప్లైన్లను గ్లోబల్గా లేదా రూటింగ్ కాంబోలకు కేటాయించిన
కంప్రెషన్ కాంబోల ద్వారా కాన్ఫిగర్ చేయవచ్చు.

**దీనికి ఉత్తమం:** పెద్ద టూల్ లాగ్లతో పాటు మానవ సూచనలు లేదా అసిస్టెంట్ సారాంశాలు ఉన్న మిశ్రమ సందర్భం.

## అప్స్ట్రీమ్ పొదుపుల గణితం

OmniRoute రెండు మూలాల నుండి కంప్రెషన్ పొదుపులను డాక్యుమెంట్ చేస్తుంది: అప్స్ట్రీమ్ ప్రాజెక్ట్ బెంచ్మార్క్లు మరియు
OmniRoute స్వంత ఇంజిన్ కూర్పు.

| మూలం    | ఇక్కడ ఉపయోగించిన అప్స్ట్రీమ్ README సంఖ్య                                                                                        |
| ------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` తక్కువ అవుట్పుట్ టోకెన్లు, `65%` బెంచ్మార్క్ సగటు అవుట్పుట్ పొదుపులు, `22-87%` పరిధి మరియు `~46%` ఇన్పుట్ కంప్రెషన్ సాధనం |
| RTK     | `60-90%` కమాండ్-అవుట్పుట్ పొదుపులు; నమూనా సెషన్లో `~118,000 -> ~23,900` టోకెన్లు లేదా `79.7%` పొదుపు (`~80%`)                    |

ఒకదానితో ఒకటి అతివ్యాప్తి చెందే సాధనం/కాంటెక్స్ట్ పేలోడ్ల కోసం, డిఫాల్ట్ OmniRoute కాంబో ఇంజిన్లను ఇలా వరుసగా అమర్చుతుంది:

```txt
RTK -> Caveman
```

సంయుక్త పొదుపులు సంకలనాత్మకమైనవి కావు, గుణకారాత్మకమైనవి:

```txt
సంయుక్తం = 1 - (1 - RTK పొదుపులు) * (1 - Caveman ఇన్పుట్ పొదుపులు)
సగటు    = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
పరిధి    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

RTK మరియు Caveman రెండూ ఒకే ఇన్పుట్/కాంటెక్స్ట్ పేలోడ్ను తగ్గించగలిగినప్పుడు ఆ `78-95%` సంఖ్య వర్తిస్తుంది.
Caveman రెస్పాన్స్ అవుట్పుట్ మోడ్ వేరు: అది ప్రారంభించబడినప్పుడు, Caveman స్వంత అవుట్పుట్ పొదుపులను (`65%`
సగటు, `~75%` ప్రధాన సంఖ్య, `22-87%` పరిధి) ఉపయోగించండి. మొత్తం బిల్లింగ్ పొదుపులు మీ ప్రాంప్ట్/అవుట్పుట్ నిష్పత్తిపై ఆధారపడి ఉంటాయి.

### "అర్హమైనది" అంటే నిజానికి ఏమిటి

15-95% ప్రధాన పరిధి వాస్తవమైనదే, కానీ అది **పునరావృతమైన లేదా అనవసరంగా సుదీర్ఘమైన** కంటెంట్కు మాత్రమే వర్తిస్తుంది — పదేపదే వచ్చే
ఎర్రర్ లైన్లు, ఒకే హెచ్చరికను వరుసగా ఉత్పత్తి చేసే బిల్డ్ లాగ్, పరిమితికి మించిన `grep`/ఫైల్-రీడ్ డంప్. ప్రతి
రిక్వెస్ట్ అంత పొదుపు చేస్తుందని దీని అర్థం **కాదు**.

ప్రయోగాత్మకంగా ధృవీకరించబడింది (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 ఒకే విధమైన
ఎర్రర్ లైన్లు కలిగిన Anthropic-ఆకృతి `tool_result` బ్లాక్పై `stacked` (RTK + Caveman) రన్ **95.93% టోకెన్ పొదుపులు / 96.26% అక్షర పొదుపులు** సాధించింది — ఇది ప్రచారం చేసిన
పరిధిలోనే ఉంది. కానీ సాధారణమైన, పునరావృతం కాని టూల్ అవుట్పుట్పై (శుభ్రమైన `grep` మ్యాచ్ జాబితా,
చిన్న ఫైల్ రీడ్, సాధారణ సంభాషణ టెక్స్ట్) అదే పైప్లైన్ను రన్ చేసినప్పుడు సరిగ్గా **దాదాపు సున్నా పొదుపులు** వస్తాయి, ఎందుకంటే
తొలగించడానికి పునరావృతమైనది ఏమీ ఉండదు మరియు కోడ్ బ్లాక్లు, URLలు, హెడ్డింగ్లు, వెర్షన్లు లేదా ALL-CAPS కాన్స్టంట్ ఐడెంటిఫైయర్లను తొలగించే లేదా మార్చే
రీరైట్ను పంపడానికి `validateCompression()` (`validation.ts`) నిరాకరిస్తుంది.

ఇది ఆశించిన, సురక్షితమైన ప్రవర్తనే, బగ్ కాదు: ప్రధానంగా శుభ్రమైన ఫైళ్లను రీడ్/grep చేసే కోడింగ్ సెషన్లో
కంప్రెషన్ పూర్తిగా ప్రారంభించబడినప్పటికీ మొత్తం పొదుపులు పరిమితంగానే ఉంటాయి, అయితే విఫలమవుతున్న
లూప్ లేదా అతిగా అవుట్పుట్ ఇచ్చే లింటర్ను ఎదుర్కొనే సెషన్లో ఆ ట్రాఫిక్పై పూర్తి 78-95% పరిధి కనిపిస్తుంది. ఒకే సెషన్లోని
తక్కువ సమగ్ర పొదుపు శాతాన్ని కంప్రెషన్ తప్పుగా కాన్ఫిగర్ చేయబడిందనే ఆధారంగా ఉపయోగించవద్దు — ముందుగా
అంతర్లీన టూల్ అవుట్పుట్ నిజంగా పునరావృతమైందో లేదో తనిఖీ చేయండి.

## కాన్ఫిగరేషన్

### డ్యాష్బోర్డ్

`Dashboard → Context & Cache` కి వెళ్లండి:

- **Caveman** — మోడ్ ఎంపిక, భాషా ప్యాక్లు, ప్రివ్యూ, మరియు గ్లోబల్ డిఫాల్ట్లు
- **RTK** — కమాండ్-ఫిల్టర్ ప్రివ్యూ, RTK భద్రతా సెట్టింగ్లు, మరియు ఫిల్టర్ కేటలాగ్
- **Compression Combos** — రూటింగ్ కాంబోలుకు కేటాయించిన పేరున్న ఇంజిన్ పైప్లైన్లు
- **Auto-Trigger Threshold** — టోకెన్ సంఖ్య థ్రెషోల్డ్ను మించినప్పుడు కంప్రెషన్ను స్వయంచాలకంగా ప్రారంభించడం

### ప్రతి కాంబోకు ఓవర్రైడ్

`Dashboard → Context & Cache → Compression Combos` లో ఒక కంప్రెషన్ కాంబోను రూటింగ్ కాంబోకు కేటాయించండి:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

దీని ద్వారా చెల్లింపు సబ్స్క్రిప్షన్లలో lite మోడ్ను కొనసాగిస్తూ, free/coding ప్రొవైడర్లపై స్టాక్డ్ కంప్రెషన్ను ఉపయోగించవచ్చు.

ఈ "Per-Combo Override" కేటాయింపు, **routing-combo compression
mode** ఓవర్రైడ్ (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ఫీల్డ్ స్కీమా `rtk`, `stacked` మరియు `omniglyph`లను కూడా అంగీకరిస్తుంది)కు భిన్నమైన నియంత్రణ. ఆ ఓవర్రైడ్ పేరున్న compression-combo పైప్లైన్ను ఎంచుకోదు; ఇది కేవలం
`resolveCompressionPlan` పరిశీలించే `compressionMode` ఫీల్డ్ను సెట్ చేస్తుంది. దీన్ని కాంబో కార్డ్లో (`Dashboard → Combos`) లేదా, #6760 నుంచి, పైన డాక్యుమెంట్ చేసిన పైప్లైన్-కేటాయింపు చెక్బాక్స్కు పక్కనే ఉన్న
`Dashboard → Context & Cache → Compression Combos` లోని "Assign to routing" జాబితాలో ప్రతి రూటింగ్ కాంబోకు సెట్ చేయవచ్చు. రెండు ఉపరితలాలూ ఒకే `PUT /api/combos/{id}` ఎండ్పాయింట్ ద్వారా నిల్వ చేయబడతాయి.

### ప్రతి అభ్యర్థనకు ఓవర్రైడ్

ఒకే అభ్యర్థన కోసం కంప్రెషన్ ప్లాన్ను ఓవర్రైడ్ చేయడానికి `x-omniroute-compression` రిక్వెస్ట్ హెడర్ను పంపండి. దీనికి అత్యధిక ప్రాధాన్యత ఉంటుంది — ఇది రూటింగ్-కాంబో ఓవర్రైడ్, యాక్టివ్ ప్రొఫైల్, ఆటో-ట్రిగ్గర్, మరియు ప్యానెల్ Default కంటే ప్రాధాన్యత పొందుతుంది. తెలియని విలువలు విస్మరించబడతాయి (అభ్యర్థన ఎప్పుడూ తిరస్కరించబడదు), అలాగే గ్లోబల్ మాస్టర్ స్విచ్ అన్నింటినీ నియంత్రిస్తుంది: గ్లోబల్గా కంప్రెషన్ ఆఫ్లో ఉన్నప్పుడు హెడర్ దాన్ని ఆన్ చేయలేదు. విలువలు:

| Value         | Effect                                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| `off`         | ఈ అభ్యర్థనకు కంప్రెషన్ ఉండదు.                                                                                         |
| `default`     | ప్యానెల్ నుంచి ఉద్భవించిన Default ప్రొఫైల్ (యాక్టివ్ ప్రొఫైల్ను విస్మరిస్తుంది). Lossy ఇంజిన్లు ఆఫ్లోనే ఉంటాయి.       |
| `safe`        | హెడర్ను పంపకుండా ఉండటంతో సమానం.                                                                                       |
| `allow-lossy` | ఈ అభ్యర్థన యొక్క ఆపరేటర్ ప్లాన్ను కొనసాగిస్తుంది; ఇందులో సారాంశాలు, ప్రాసంగికత ఫిల్టర్లు, మరియు శైలి రీరైట్లు ఉంటాయి. |
| `engine:<id>` | ఎనేబుల్ చేయబడినప్పుడు ఒకే ఇంజిన్, ఉదా. `engine:rtk`. ఇది ఆ ఇంజిన్కు ప్రతి అభ్యర్థనలో చేసే opt-in.                     |
| `<combo>`     | పేరుతో సరిపోల్చే పేరున్న కాంబో (మొదట case-insensitiveగా, ఆ తర్వాత id ద్వారా).                                         |

`allow-lossy`, `engine:<id>`, లేదా పేరున్న కాంబో లేకపోతే, lossy ఇంజిన్లు వర్తించవు. Lossy Default, auto-trigger, లేదా routing override డౌన్గ్రేడ్ చేయబడినప్పుడు, OmniRoute కాన్ఫిగర్ చేసిన స్టాక్డ్ పైప్లైన్లోని గుర్తించబడిన lossless దశలను కాన్ఫిగర్ చేసిన క్రమంలోనే ఉంచుతుంది. కాన్ఫిగర్ చేసిన lossless దశ ఏదీ మిగలకపోతే మాత్రమే ఇది
`session-dedup → lite`కి తిరిగి వస్తుంది.

Settings ప్యానెల్లోని **Effective pipeline** ప్రివ్యూ సాధారణంగా నిల్వలో ఉన్న ప్లాన్ను చూపిస్తుంది. ఆటో-ట్రిగ్గర్ అమలు చేయగలిగినప్పుడు, అదే ప్రివ్యూ దాని షరతులతో కూడిన effective pipelineను కూడా చూపిస్తుంది; తద్వారా ప్యానెల్ మరియు హెడర్-లేని రన్టైమ్ రిజల్యూషన్ సమకాలికంగా ఉంటాయి.

అమలు చేసిన ప్లాన్ `X-OmniRoute-Compression: <mode>; source=<source>` రెస్పాన్స్ హెడర్లో తిరిగి ఇవ్వబడుతుంది; ఇందులో `<source>` ఈ విలువల్లో ఒకటి: `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default`, లేదా `off`.

## అధునాతన కంప్రెషన్ సిస్టమ్స్

పైన వివరించిన 7 మోడ్లకు మించి (ఈ గైడ్ కవర్ చేయని మూలాధారం `codex-responses` మరియు `omniglyph` మోడ్లను కూడా అంగీకరిస్తుంది), క్రింద ఉన్న విభాగాలు ఆ మోడ్ల లోపల లేదా వాటితో పాటుగా పనిచేసే ఫీచర్లను కవర్ చేస్తాయి: సాధన ఫలితం కంప్రెషన్ మరియు ప్రోగ్రెసివ్ ఏజింగ్ అనేవి దూకుడు ఇంజిన్లోని 1 మరియు 2 దశలు (దూకుడు మోడ్ మరియు `aggressive` పైప్లైన్ స్టెప్లు, స్టాక్డ్ పైప్లైన్ స్టెప్ ఎలా నడుస్తుంది) కంప్రెషన్ ఆన్లో ఉన్నప్పుడు కాషింగ్ ప్రొవైడర్ల కోసం కాష్-అవేర్ కంప్రెషన్ `aggressive` మరియు `ultra` ని `standard` నుండి డౌన్గ్రేడ్ చేస్తుంది మరియు కేవ్మ్యాన్ అవుట్పుట్ మోడ్ మరియు అవుట్పుట్ స్టైల్లు డిఫాల్ట్గా ఆప్ట్-ఇన్ సిస్టమ్-ప్రాంప్ట్ సూచనలు, ఇవి అభ్యర్థనను కుదించడానికి బదులుగా మోడల్ అవుట్పుట్ను ఆకృతి చేస్తాయి.

### కాష్-అవేర్ కంప్రెషన్

కొంతమంది ప్రొవైడర్లు (ప్రాంప్ట్ కాషింగ్తో Anthropic వంటివి) మద్దతు ఇస్తారు** ప్రాంప్ట్ కాషింగ్** , ఇది ఖర్చులు మరియు జాప్యాన్ని తగ్గించడానికి ప్రాంప్ట్ యొక్క భాగాలను కాష్ చేయడానికి వారిని అనుమతిస్తుంది. కాషింగ్ ప్రారంభించబడినప్పుడు, నిజానికి దూకుడు కుదింపు చేయవచ్చు** బాధించింది** పనితీరు ఎందుకంటే ఇది కాష్ చేసిన టోకెన్లను మారుస్తుంది, కాష్ చెల్లదు.

`cachingAware.ts` మాడ్యూల్ దీనిని పరిష్కరిస్తుంది** కాషింగ్ సందర్భాన్ని గుర్తించడం** మరియు** కుదింపు వ్యూహాన్ని సర్దుబాటు చేయడం** తదనుగుణంగా.

#### ఇది ఎలా పనిచేస్తుంది

1. **కాషింగ్ సందర్భాన్ని గుర్తించండి** — `cache_control` మార్కర్ల కోసం అభ్యర్థన బాడీని స్కాన్ చేస్తుంది
2. **కాషింగ్ ప్రొవైడర్లను గుర్తించండి** — లక్ష్యం ప్రొవైడర్ కాషింగ్కు మద్దతు ఇస్తుందో లేదో తనిఖీ చేస్తుంది
3. **వ్యూహాన్ని సర్దుబాటు చేయండి** కాషింగ్ ప్రొవైడర్ల కోసం — `aggressive`/`ultra` నుండి `standard` వరకు డౌన్గ్రేడ్ చేస్తుంది
4. **సిస్టమ్ ప్రాంప్ట్ను దాటవేయి** — సిస్టమ్ ప్రాంప్ట్లు సాధారణంగా కాష్ చేయబడతాయి, కాబట్టి వాటిని కుదించవద్దు

వ్యూహ సహాయకుడు కూడా `deterministicOnly` ఫ్లాగ్ను తిరిగి అందజేస్తాడు, అయితే ప్లాన్ బిల్డర్ స్ట్రాటజీ — ని మాత్రమే వినియోగిస్తాడు, ఈ రోజు ఫ్లాగ్ను దిగువన ఏదీ చదవదు.

#### కోడ్ ఉదాహరణ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ఎప్పుడు ఉపయోగించాలి

కాష్-అవేర్ కంప్రెషన్** ఎల్లప్పుడూ ఆన్** — కాన్ఫిగరేషన్ అవసరం లేదు. కుదింపు ఆన్లో ఉన్నప్పుడల్లా ఇది ప్రారంభమవుతుంది మరియు లక్ష్య ప్రదాత ప్రాంప్ట్ కాషింగ్కు మద్దతు ఇస్తుంది (Anthropic, OpenAI, మొదలైనవి); స్పష్టమైన `cache_control` మార్కర్లు అవసరం లేదు — కాషింగ్ ప్రొవైడర్ మాత్రమే డౌన్గ్రేడ్ను ప్రేరేపిస్తుంది మరియు మార్కర్లు మాత్రమే ఎప్పుడూ చేయవు (మార్కర్ డిటెక్షన్ క్యాష్ టెలిమెట్రీని ఫీడ్ చేస్తుంది, వ్యూహ నిర్ణయం కాదు).

OpenRouter `anthropic/*` మోడల్లకు మాత్రమే కాషింగ్ ప్రొవైడర్గా పరిగణించబడుతుంది: Claude కోడ్ అభ్యర్థనలు వాటి `cache_control` బ్రేక్పాయింట్లను (గరిష్టంగా 4) ఉంచుతాయి మరియు గార్డు ఉపసర్గను రక్షిస్తుంది, అయితే ప్రతి ఇతర OpenRouter కుటుంబం (`openai/`, `google/`, `qwen/`, …) తీసివేయబడి మరియు రక్షణ లేకుండా ఉంటుంది.

### ప్రగతిశీల వృద్ధాప్యం

సుదీర్ఘ సంభాషణలు అనేక సందేశ మలుపులను కూడగట్టుకుంటాయి, కానీ పాత మలుపులు తక్కువ సందర్భోచితంగా మారతాయి. `progressiveAging.ts` మాడ్యూల్** మలుపు దూరం ద్వారా సందేశాలను క్షీణింపజేస్తుంది** (సంభాషణ ముగింపు నుండి దూరం కొలుస్తారు). రవాణా చేయబడిన డిఫాల్ట్లతో (`verbatim: 2, light: 2, moderate: 3`):

- **చివరి 2 మలుపులు (దూరం ≤ 2)** : పదజాలం ఉంచబడింది
- **దూరం 3** : కేవ్మ్యాన్ కంప్రెషన్ (ఫిల్లర్ రిమూవల్)
- **దూరం 4 +** : అసిస్టెంట్ సందేశాలు సంగ్రహించబడ్డాయి; వినియోగదారు సందేశాలు వారి మొదటి పంక్తికి తగ్గించబడ్డాయి, 120 అక్షరాలతో పరిమితం చేయబడ్డాయి; ఇతర పాత్రలు తాకబడలేదు. సిస్టమ్ ప్రాంప్ట్లు, ఇప్పటికే పాత సందేశాలు మరియు తాజా వినియోగదారు సందేశం ఎల్లప్పుడూ దూరంతో సంబంధం లేకుండా పదజాలం ఉంచబడతాయి. ఏదీ పూర్తిగా వదిలివేయబడదు మరియు షిప్ చేయబడిన డిఫాల్ట్లతో `light` బ్యాండ్ చేరుకోలేదు (`light` `verbatim` సమానం).

#### కోడ్ ఉదాహరణ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### ఎప్పుడు ఉపయోగించాలి

ప్రగతిశీల వృద్ధాప్యం** ఎల్లప్పుడూ ఆన్** `aggressive` మోడ్ — కోసం ఇది `compressAggressive()` యొక్క 2వ దశ. అల్ట్రా మోడ్ దీన్ని అమలు చేయదు. ఇది ప్రత్యేకంగా ప్రభావవంతంగా ఉంటుంది:

- దీర్ఘకాల కోడింగ్ సెషన్లు
- బహుళ-రోజుల సంభాషణలు
- అనేక టూల్ కాల్లతో ఏజెంట్ వర్క్ఫ్లోలు

### కేవ్మ్యాన్ అవుట్పుట్ మోడ్

కేవ్మ్యాన్ అవుట్పుట్ మోడ్ జోడిస్తుంది** సిస్టమ్ ప్రాంప్ట్ సూచనలు** టెర్సే అవుట్పుట్ — కోసం మోడల్ను అడగడం, `lite` స్థాయి పూర్తి వాక్యాలను ఉంచే సంక్షిప్త సమాధానాలను అడుగుతుంది, `full` దానిని "స్మార్ట్ కేవ్మ్యాన్లాగా స్పందించమని" అడుగుతుంది మరియు `ultra` టెలిగ్రాఫిక్ అవుట్పుట్ కోసం అడుగుతుంది; సూచనలు మాత్రమే అడుగుతాయి, వారు దానికి హామీ ఇవ్వలేరు. అభ్యర్థనలు వాటిని `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`): `open-sse/handlers/chatCore.ts` మొదట బ్యాక్-కంపాట్ షిమ్తో ఎంపికను పరిష్కరిస్తుంది ( `open-sse/services/compression/outputStyles/backCompat.ts` లో`resolveOutputStyleSelection()` ), ఇది `outputStyles` ఖాళీగా ఉన్నప్పుడు, ప్రారంభించబడిన `cavemanOutputMode` `cavemanOutputMode.intensity` వద్ద `terse-prose` అవుట్పుట్ స్టైల్కు మ్యాప్ చేస్తుంది (క్రింద బ్యాక్-కంపాట్ చూడండి); ఖాళీ కాని `outputStyles` ఎంపిక అలాగే ఉపయోగించబడుతుంది మరియు `cavemanOutputMode.enabled` మరియు `intensity` ప్రభావం ఉండదు, అయితే దాని `autoClarity` టోగుల్ ఇప్పటికీ వర్తిస్తుంది. `outputMode.ts` సూచన పాఠాలు (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), కంటెంట్ బైపాస్ మరియు ఇంజెక్షన్ ఉపయోగించే ప్లేస్మెంట్ హెల్పర్ను కలిగి ఉంటుంది; దాని స్వంత `applyCavemanOutputMode()` ఇంజెక్టర్కు ప్రొడక్షన్ కాలర్ లేదు.

#### ఇది ఎలా పనిచేస్తుంది

ఈ మోడ్ ఇన్పుట్ను కుదించదు. ఇది సిస్టమ్ ప్రాంప్ట్కు ఇన్స్ట్రక్షన్ బ్లాక్ను జోడిస్తుంది (క్రింద ఉన్న ఇంజెక్షన్ ఎలా పనిచేస్తుందో చూడండి), మరియు అభ్యర్థన కోసం ఎంచుకున్న ఏదైనా ఇన్పుట్ కంప్రెషన్ మోడ్ ఇప్పుడు బ్లాక్ను కలిగి ఉన్న శరీరంపై ఇప్పటికీ నడుస్తుంది. ప్రతి స్థాయి ముగిసే భాగస్వామ్య సరిహద్దుల నిబంధన ముందు, ఆంగ్ల `full` స్థాయి ఇలా ఉంటుంది:

> "స్మార్ట్ కేవ్మ్యాన్లాగా ప్రతిస్పందించండి. డ్రాప్ కథనాలు (a/an/the), పూరకం (just/really/basically/actually/simply), ఆహ్లాదకరమైనవి, హెడ్జింగ్. శకలాలు OK. చిన్న పర్యాయపదాలు (పెద్దవి కావు, అమలు చేయబడలేదు). అన్ని సాంకేతిక పదార్ధాలు, కోడ్, లోపాలు, URLs, ఐడెంటిఫైయర్లను ఖచ్చితంగా ఉంచండి."

ఇది ప్రత్యేకంగా పని చేస్తుంది:

- కోడ్ జనరేషన్ (టెర్సర్ అవుట్పుట్ = తక్కువ టోకెన్లు)
- త్వరిత ప్రశ్నోత్తరాలు (విస్తృతమైన వివరణలు అవసరం లేదు)
- బ్యాచ్ ప్రాసెసింగ్ (గరిష్ట నిర్గమాంశ)

#### ఎప్పుడు ఉపయోగించాలి

కేవ్మ్యాన్ అవుట్పుట్ మోడ్** ఎంపిక** . కంప్రెషన్ ఆన్తో (`enabled: true`, కంప్రెషన్ సెట్టింగ్ల పేజీలో మాస్టర్ టోగుల్), `cavemanOutputMode.enabled` తో దాన్ని ఆన్ చేయండి; `intensity` ఎంపికలు `lite`, `full` లేదా `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ఒక కుదింపు కాంబో** అవుట్పుట్ మోడ్** టోగుల్ (`outputMode`, `outputModeIntensity` లో స్థాయి) కాంబో వర్తించే అభ్యర్థనల కోసం అదే స్విచ్ను సెట్ చేస్తుంది మరియు `omniroute_set_compression_engine` MCP సాధనం దానిని దాని బూలియన్ `outputMode` ఆర్గ్యుమెంట్ ద్వారా వ్రాస్తుంది. ఈ స్విచ్ కంటే ఖాళీ కాని `outputStyles` ఎంపిక ప్రాధాన్యతనిస్తుంది. డాష్బోర్డ్లో, ఎనేబుల్ చేస్తోంది** గద్య గద్యము** అవుట్పుట్ శైలి అదే బ్లాక్ను ఇంజెక్ట్ చేస్తుంది (క్రింద అవుట్పుట్ స్టైల్స్ చూడండి).

ప్రతి శైలి — `lite`, `full`, `ultra` — అనే మూడు తీవ్రత స్థాయిలను రవాణా చేస్తుంది మరియు ప్రతి స్థాయి భాగస్వామ్య సరిహద్దుల నిబంధనతో ముగుస్తుంది ( `outputMode.ts` లో`SHARED_BOUNDARIES` ), ఇది కోడ్ బ్లాక్లు, ఫైల్ పాత్లు, ఆదేశాలు, లోపాలు మరియు URLs ఖచ్చితమైనదిగా ఉంచుతుంది. `terse-prose` మరియు `terse-cjk` స్థాయి టెక్స్ట్లు ఆ జాబితాకు ఐడెంటిఫైయర్లను జోడిస్తాయి.

`terse-cjk` రెండు ప్రదేశాలలో `zh` కి లొకేల్-గేట్ చేయబడింది. డాష్బోర్డ్ UI భాష చైనీస్ (`zh-CN` లేదా `zh-TW`) అయినప్పుడు మాత్రమే కంప్రెషన్ సెట్టింగ్ల పేజీ దాని అడ్డు వరుసను జాబితా చేస్తుంది మరియు అభ్యర్థన పరిష్కరించబడిన భాష (దిగువ భాష ఎంపికను చూడండి) `zh` అయినప్పుడు మాత్రమే `applyOutputStyles()` ఇంజెక్ట్ చేస్తుంది. అడ్డు వరుసను దాచడం సేవ్ చేయబడిన `terse-cjk` ఎంపికను క్లియర్ చేయదు: సెట్టింగులు API ఏదైనా స్టైల్ ఐడిని అంగీకరిస్తుంది మరియు పేజీలో ఇతర శైలులను సేవ్ చేయడం దానిని ఉంచుతుంది. అభ్యర్థన సమయంలో, `applyOutputStyles()` భాష తనిఖీ మాత్రమే లొకేల్ గేట్.

#### ఇంజెక్షన్ ఎలా పనిచేస్తుంది

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) కేటలాగ్కి వ్యతిరేకంగా ఎంపికను పరిష్కరిస్తుంది (తెలియని idలు మరియు లొకేల్-సరిపోలని శైలులు తొలగించబడవు, ఎప్పటికీ లోపం; ఏ శైలిని పరిష్కరించని ఎంపిక శరీరాన్ని మారదు, `no_styles` గా దాటవేయబడుతుంది), ఎంచుకున్న సూచనలను కేటలాగ్ క్రమంలో సంగ్రహిస్తుంది, సరిహద్దుల నిబంధనను జతచేస్తుంది** ఒకసారి** (అదనంగా భద్రతా నిబంధన, `SAFETY_BOUNDARIES` లేదా దాని అనువాదం, `less-code` లేదా `ponytail` ఎంచుకోబడినప్పుడు), మరియు బ్లాక్ను ఒకే ఐడెంపోటెన్సీ మార్కర్ (`[OmniRoute Output Styles]`)తో ప్రారంభిస్తుంది, కాబట్టి మళ్లీ దరఖాస్తు చేయడం నిషేధం. పరిష్కరించబడిన భాష (దిగువ భాష ఎంపికను చూడండి) అనువాదం కలిగి ఉన్నప్పుడు, ఆంగ్లానికి బదులుగా స్థానికీకరించిన సూచన ఇంజెక్ట్ చేయబడుతుంది.

ఖాళీ కాని `messages` శ్రేణితో ఉన్న బాడీలో, కంటెంట్ బైపాస్కు ముందు ఐడెమ్పోటెన్సీ చెక్ నడుస్తుంది: `[OmniRoute Output Styles]` మార్కర్ ఇప్పటికే అగ్ర-స్థాయి `system` ఫీల్డ్లో (స్ట్రింగ్ లేదా కంటెంట్-బ్లాక్ శ్రేణి) లేదా స్ట్రింగ్ కంటెంట్తో కూడిన సిస్టమ్ సందేశంలో ఉన్నప్పుడు, బాడీ `already_applied` వలె మారదు మరియు కీవర్డ్ చెక్ రన్ చేయబడదు. లేకపోతే కంటెంట్ బైపాస్ (`shouldBypassCavemanOutputMode()` ఇన్ `open-sse/services/compression/outputMode.ts`) చివరి మూడు సందేశాల టెక్స్ట్ని తనిఖీ చేస్తుంది, వాటి పాత్ర ఏదైనప్పటికీ, ఆ వచనం దాని భద్రత, తిరుగులేని చర్య లేదా స్పష్టీకరణ కీలక పదాలు లేదా ఆర్డర్ `deploy` సెన్సిటివ్ సీక్వెన్స్తో సరిపోలినప్పుడు మొత్తం మలుపు కోసం స్టైల్లను దాటవేస్తుంది: `first`, `then`, `after that` `migrate` `delete`, `before`, `drop`, `rollback` లేదా `backup` ద్వారా 240 `release`. బైపాస్ నడుస్తుంది** స్వీయ-స్పష్టత బైపాస్** టోగుల్ (`cavemanOutputMode.autoClarity`, డిఫాల్ట్గా ఆన్) ఆన్లో ఉంది; టోగుల్ ఆఫ్ చేయడం కీవర్డ్ చెక్ని దాటవేస్తుంది.

బైపాస్ టర్న్ను అనుమతించినప్పుడు, `placeSystemInstruction()` (అదే ఫైల్), ఇది ఎప్పుడూ కొత్త `messages[0]` సృష్టించదు , బ్లాక్ను వీటిలో మొదటి దానిలో ఉంచుతుంది:

1. స్ట్రింగ్ కంటెంట్తో ప్రముఖ సిస్టమ్ సందేశం: బ్లాక్ దాని టెక్స్ట్ తర్వాత జోడించబడింది.
2. అగ్ర-స్థాయి `system` ఫీల్డ్: స్ట్రింగ్ యొక్క టెక్స్ట్ తర్వాత బ్లాక్ జోడించబడుతుంది లేదా కంటెంట్-బ్లాక్ శ్రేణికి కొత్త టెక్స్ట్ బ్లాక్గా జోడించబడుతుంది.
3. స్ట్రింగ్ కంటెంట్తో మొదటి తర్వాత సిస్టమ్ సందేశం: బ్లాక్ దాని టెక్స్ట్ తర్వాత జోడించబడింది.
4. పైవేవీ కావు: `messages` చివరిలో బ్లాక్ కొత్త సిస్టమ్ సందేశంలోకి వెళుతుంది.

`messages` శ్రేణి లేని (లేదా ఖాళీగా ఉన్న) బాడీలో, కంటెంట్ బైపాస్ రన్ చేయబడదు మరియు ఉన్నత-స్థాయి `system` ఫీల్డ్ని సంప్రదించబడదు. స్ట్రింగ్ `instructions` ఫీల్డ్ యొక్క టెక్స్ట్ తర్వాత బ్లాక్ జోడించబడుతుంది, ఆ ఫీల్డ్ ఇప్పటికే `[OmniRoute Output Styles]` మార్కర్ను కలిగి ఉంటే తప్ప, ఆ సందర్భంలో శరీరం `already_applied` వలె మారదు. శరీరానికి స్ట్రింగ్ `instructions` ఫీల్డ్ లేనప్పుడు కానీ `input` (ఒక స్ట్రింగ్ లేదా అర్రే)ని కలిగి ఉన్నప్పుడు, బ్లాక్ `instructions` అవుతుంది, ఫీల్డ్ కలిగి ఉన్న ఏదైనా నాన్-స్ట్రింగ్ విలువను భర్తీ చేస్తుంది. స్ట్రింగ్ `instructions` ఫీల్డ్ లేదా స్ట్రింగ్ లేదా అర్రే `input` లేని శరీరం మారదు మరియు `no_messages` వలె దాటవేయబడుతుంది.

#### ఎలా ఎనేబుల్ చేయాలి

డ్యాష్బోర్డ్లో:** కుదింపు సందర్భం → కుదింపు సెట్టింగ్లు** (`/dashboard/context/settings`), అవుట్పుట్ స్టైల్స్ విభాగం: on/off టోగుల్ మరియు లెవెల్ సెలెక్టర్తో ఒక్కో స్టైల్కి ఒక అడ్డు వరుస. కంప్రెషన్ ఆన్లో ఉన్నప్పుడు స్టైల్స్ ఇంజెక్ట్ చేస్తాయి (పేజీ యొక్క మాస్టర్ టోగుల్, `enabled`). ది** స్వీయ-స్పష్టత బైపాస్** టోగుల్ ఆన్లో ఉంది** కేవ్ మాన్** పేజీ (`/dashboard/context/caveman`), దానిలో** అవుట్పుట్ మోడ్** కార్డు. ప్రోగ్రామాటిక్గా, కంప్రెషన్ కాన్ఫిగర్ ఎంపికను ఇలా కొనసాగిస్తుంది:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

బ్యాక్ కాంపాట్: `outputStyles` ఖాళీగా ఉన్నప్పుడు, లెగసీ `cavemanOutputMode.enabled` మ్యాప్లను `cavemanOutputMode.intensity` వద్ద `terse-prose` కి సెట్ చేస్తుంది. బ్లాక్ `[OmniRoute Output Styles]` మార్కర్తో ప్రారంభమవుతుంది, ఇక్కడ లెగసీ `applyCavemanOutputMode()` ఇంజెక్టర్ `[OmniRoute Caveman Output Mode]` అని వ్రాసింది. మార్కర్ క్రింద, టెక్స్ట్ en, pt-BR, es, de, fr, it, ru, id మరియు viలో లెగసీ ఇంజెక్షన్తో సరిపోలుతుంది; ja మరియు zh లలో ఇది సరిహద్దుల నిబంధనకు ముందు ఒక అదనపు స్థలాన్ని కలిగి ఉంటుంది. `terse-prose` అనేది pt-BR, es, de, fr, it, ru, zh, ja, id మరియు viలోకి అనువదిస్తుంది, కాబట్టి `hu` అనే పరిష్కరించబడిన భాష ఉన్న అభ్యర్థన, లెగసీ ఇంజెక్టర్ దాని హంగేరియన్ను ఉపయోగించిన ఆంగ్ల వచనాన్ని పొందుతుంది.

అవుట్పుట్-శైలి భాషా ఎంపిక ( `outputStyles/apply.ts` లో`resolveOutputStyleLanguage()` ): `languageConfig.enabled` ఆన్తో, అభ్యర్థన యొక్క `messages` శ్రేణిలో టెక్స్ట్ (స్ట్రింగ్ కంటెంట్, లేదా దాని కంటెంట్ భాగాల `text` ) ఉన్న తాజా వినియోగదారు సందేశాన్ని `autoDetect` నమూనా చేస్తుంది మరియు దానిపై కేవ్మ్యాన్ ఇంజిన్ డిటెక్టర్ (`detectCompressionLanguage()`)ని అమలు చేస్తుంది. డిటెక్టర్ హాన్ అక్షరాలు మరియు కనా లేని టెక్స్ట్ కోసం `zh` అందిస్తుంది; లేకుంటే అది `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` మరియు `id` లలో ఏది ఎక్కువ సూచన సరిపోలికలను అందిస్తుంది మరియు `en` ఏదీ సరిపోలనప్పుడు — టెక్స్ట్ని వర్గీకరించలేనప్పుడు `defaultLanguage` ఇంగ్లీషుని పొందదు, అయితే `vi` `vi` ఎప్పటికీ గుర్తించదు. ప్రతిస్పందనల API శరీరం దాని మలుపులను `input` లో ఉంచుతుంది, ఇది నమూనా చేయబడలేదు, కనుక ఇది `defaultLanguage`, ఆపై ఆంగ్లంలోకి వస్తుంది. `messages` లో ఏ వినియోగదారు సందేశం టెక్స్ట్ లేనప్పుడు లేదా `autoDetect` ఆఫ్తో ఉన్నప్పుడు, `defaultLanguage` వర్తిస్తుంది, ఆపై ఇంగ్లీష్. `languageConfig.enabled` ఆఫ్తో, అభ్యర్థనకు కంప్రెషన్ కాంబో వర్తించకపోతే భాష ఇంగ్లీష్ — అవుతుంది (అభ్యర్థన యొక్క రూటింగ్ కాంబోకి కేటాయించిన కాంబో లేదా డిఫాల్ట్ కంప్రెషన్ కాంబో chatCore అంతర్నిర్మిత పేర్చబడిన పైప్లైన్కు తిరిగి వస్తుంది): కాంబోను వర్తింపజేయడం వలన ఆ అభ్యర్థన కోసం `languageConfig.enabled` ప్యాక్ నుండి `defaultLanguage` ఆదా అవుతుంది. ఒకవేళ అది కాంబో ప్యాక్లలో ఒకటి అయితే, కాంబో మొదటి ప్యాక్, `en` కి డిఫాల్ట్ అవుతుంది, అయితే సేవ్ చేయబడిన `autoDetect` (డిఫాల్ట్గా ఆన్) ఇప్పటికీ వర్తిస్తుంది. కేవ్మ్యాన్ ఇన్పుట్ ఇంజిన్ దాని రూల్-ప్యాక్ భాషను ఒక్కో టెక్స్ట్ భాగానికి భిన్నంగా — ఎంచుకుంటుంది మరియు ఆటో-డిటెక్ట్ ఆఫ్తో, `enabledPacks` పై గేట్ చేయబడింది.

స్టైల్ × లాంగ్వేజ్ మ్యాట్రిక్స్ `tests/unit/compression/output-styles-i18n-matrix.test.ts` ద్వారా పిన్ చేయబడింది: ప్రతి కేటలాగ్ స్టైల్కి టెస్ట్ `BASELINE_LANGUAGES` లో ఎంట్రీ అవసరం; లొకేల్-గేటెడ్ లేని స్టైల్ తప్పనిసరిగా pt-BR అనువాదాన్ని రవాణా చేయాలి (లొకేల్-గేటెడ్ `terse-cjk` ఈ నియమం నుండి మినహాయించబడింది) ఇది `KNOWN_ENGLISH_ONLY` లో జాబితా చేయబడితే తప్ప, ఇది — లో ఎటువంటి అనువాదాలు లేని శైలులను మాత్రమే కలిగి ఉండవచ్చు, ఏదైనా అనువాదాన్ని కలిగి ఉన్న జాబితా చేయబడిన శైలి పరీక్షలో విఫలమవుతుంది; మరియు ఒక శైలి దాని `BASELINE_LANGUAGES` ఎంట్రీ జాబితా చేసిన భాషను కోల్పోయినప్పుడు పరీక్షలో విఫలమవుతుంది. శైలిని జోడించడానికి, [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) చూడండి.

### సాధనం ఫలితం కుదింపు

`open-sse/services/compression/toolResultCompressor.ts` లోని`compressToolResult()` టూల్-ఫలిత వచనాన్ని దీనితో కుదిస్తుంది** 5 వ్యూహాలు** . ఇది వాటిని ఈ క్రమంలో ప్రయత్నిస్తుంది మరియు కంటెంట్తో సరిపోలిన మొదటి ఎనేబుల్ చేసిన వ్యూహం ఫలితాన్ని నిర్ణయిస్తుంది:

1. **`fileContent`** : లీడింగ్ ఇండెంటేషన్ను విస్మరించి, కనీసం ఒక పంక్తి `import `, `export `, `function `, `class `, `const `, `let `, `var ` లేదా `return ` (కీవర్డ్తో పాటు ఒక ఖాళీ)తో లేదా `if`, `for` తర్వాత దాని తర్వాత ఉంచిన `(` లేదా ` (` `while` లైన్ల కంటెంట్ 20 మరియు చివరి 5 పంక్తులు, ఎలిడెడ్ మధ్య గుర్తుతో ఉంటాయి.
2. **`grepSearch`** : `<path>:<digits>:` ఫారమ్లో కనీసం ఒక పంక్తితో కూడిన కంటెంట్, మొదటి కోలన్కు ముందు ఉన్న టెక్స్ట్లో వైట్స్పేస్ ఉండదు, ఆ పంక్తులను మాత్రమే ఉంచుతుంది, గరిష్టంగా 30, తర్వాత ఏవైనా సరిపోలికలు మరియు సరిపోలిన ఫైల్ల జాబితా; ప్రతి ఇతర లైన్ డ్రాప్ చేయబడింది. వ్యూహాన్ని ట్రిగ్గర్ చేయడానికి అటువంటి లైన్ ఒకటి సరిపోతుంది, కాబట్టి `12:30:45` వంటి టైమ్స్టాంప్తో ప్రారంభమయ్యే లాగ్ లైన్ కూడా లెక్కించబడుతుంది.
3. **`shellOutput`** : ANSI CSI సీక్వెన్స్ని కలిగి ఉన్న అవుట్పుట్ (`ESC[` ఆపై అంకెలు లేదా సెమికోలన్లు ఆపై అక్షరం, రంగు కోడ్లలో) లేదా `$` తర్వాత టెక్స్ట్లో ఎక్కడైనా వైట్స్పేస్ ఉంటే ఆ సీక్వెన్స్లను కోల్పోతుంది ( `ESC[?25l` లేదా OSC విండో-టైటిల్ సీక్వెన్స్ వంటి ఇతర ఎస్కేప్లు ఉంచబడతాయి. 50 వరుస పంక్తులు కుదించబడిన పంక్తిని దాని చివరి వరుసలో ఉంచుతుంది. ఎందుకంటే ఈ చెక్ `json` మరియు `errorMessage`, JSON లేదా అటువంటి `$` కలిగి ఉన్న ఎర్రర్ అవుట్పుట్ `shellOutput` ఆన్లో ఉన్నప్పుడు వాటిని చేరుకోదు.
4. **`json`** : `{` లేదా `[` (ఐచ్ఛిక వైట్స్పేస్ తర్వాత)తో ప్రారంభమయ్యే 2,000 అక్షరాల కంటే ఎక్కువ ఉన్న JSON పేలోడ్ మరియు పార్స్లు సంగ్రహించబడ్డాయి: 7 కంటే ఎక్కువ ఐటెమ్ల శ్రేణి దాని మొదటి 5 మరియు చివరి 2 అంశాలను మరియు దాని మొత్తం గణనను ఉంచుతుంది మరియు ఒక వస్తువు దాని మొదటి 20 కీలను ఉంచుతుంది. దాని పొడవు) మరియు ఒక `{…N keys}` `_remaining_<N>_keys` మొదటి 20కి మించి పడిపోయింది. స్కేలార్ విలువలు పూర్తిగా కాపీ చేయబడతాయి, కాబట్టి 20 కీలు లేదా అంతకంటే తక్కువ విలువలు లేని వస్తువు — మాత్రమే మళ్లీ ఇండెంట్ చేయబడుతుంది, కనిష్టీకరించబడినది అక్షరాలను పొందుతుంది మరియు మారదు.
5. **`errorMessage`** : ఎక్కడైనా మరియు ఏ అక్షరం విషయంలోనైనా, `error:`, `error ` ( `no error found` లో వలె ఖాళీని కలిగి ఉన్న పదం), `[error]`, `exception:`, `exception `, `[exception]` లేదా `traceback` కలిగి ఉన్న అవుట్పుట్ దాని మొదటి పంక్తి, తదుపరి 10 పంక్తులు మరియు చివరి 3ని వాటి మధ్య `… [N frames elided] …` మార్కర్తో ఉంచుతుంది. 13 కంటే ఎక్కువ పంక్తులు మొదటి పంక్తిని అనుసరించినప్పుడు మాత్రమే మార్కర్ కనిపిస్తుంది, కాబట్టి 14 లైన్లు లేదా అంతకంటే తక్కువ లోపం అవుట్పుట్ కుదించబడదు (12 లేదా 13 లైన్లలో చివరి 3 పునరావృత పంక్తులు ఇప్పటికే ఉంచబడ్డాయి).

ఒక వ్యూహం సరిపోలిన తర్వాత, ఏమీ ఆదా చేయనిది కూడా, తదుపరి వ్యూహాలు ప్రయత్నించబడవు. సరిపోలే వ్యూహం అంచనా వేయబడిన టోకెన్లను (పొడవు ÷ 4, రౌండ్ అప్) సేవ్ చేయనప్పుడు — ఉదాహరణకు 25 పంక్తులు లేదా అంతకంటే తక్కువ కోడ్ లాంటి ఫైల్ లేదా 7 అంశాలు లేదా తక్కువ — ఉన్న 2,000 అక్షరాల కంటే ఎక్కువ ఉన్న JSON శ్రేణి `compressToolResult()` దూకుడు ఇంజిన్ అసలు టూల్ `saved` ఉంచినప్పుడు (`compressAggressive()` రెండు కాలర్లు) 0 లేదా అంతకంటే తక్కువ, `compressAnthropicToolResultBlock()` ఇప్పటికీ ఆ వ్యూహం యొక్క అవుట్పుట్ను అందిస్తుంది. సాధనం-ఫలితం దశ చివరి పదం కాదు: ఇంజిన్ యొక్క ఫాల్బ్యాక్ సారాంశం ఇప్పటికీ 8,192 అక్షరాల కంటే ఎక్కువ `tool` లేదా `function` సందేశాన్ని తగ్గించగలదు (`maxTokensPerMessage`, 2,048, సార్లు 4).

#### ఎప్పుడు ఉపయోగించాలి

సాధన ఫలితం కుదింపు అనేది అగ్రెసివ్ ఇంజిన్లో 1వ దశ ( `open-sse/services/compression/aggressive.ts` లో`compressAggressive()` ), కాబట్టి ఇది అగ్రెసివ్ మోడ్లో మరియు పేర్చబడిన పైప్లైన్ యొక్క `aggressive` దశలో నడుస్తుంది. ఇది OpenAI- ఆకారపు `tool` మరియు `function` సందేశాలను మరియు Anthropic `tool_result` బ్లాక్లలోని వచనాన్ని కంప్రెస్ చేస్తుంది. ప్రతి వ్యూహం `aggressive.toolStrategies` కింద దాని స్వంత స్విచ్ని కలిగి ఉంటుంది, అన్నీ డిఫాల్ట్గా ఆన్లో ఉంటాయి. డాష్బోర్డ్లో, స్విచ్లు కేవ్మ్యాన్ పేజీలో ఉన్నాయి** అధునాతనమైనది** కుదింపు ఆన్లో ఉన్నప్పుడు చూడండి మరియు డిఫాల్ట్ మోడ్ దూకుడుగా ఉంటుంది.

### పేర్చబడిన పైప్లైన్

పేర్చబడిన మోడ్ నడుస్తుంది** అనేక ఇంజన్లు వరుసగా** — సాధారణంగా మొదట RTK (టూల్ అవుట్పుట్పై 60-90% పొదుపులు), తర్వాత మిగిలిన టెక్స్ట్పై కేవ్మ్యాన్ (~ 46% ఇన్పుట్ సేవింగ్స్). కంపోజ్ చేయబడింది, అది** 78-95% అర్హత పరిధి** (పైన అప్స్ట్రీమ్ సేవింగ్స్ మ్యాథ్ని చూడండి): `1 - (1 - 0.60..0.90) × (1 - 0.46)` సగటు ≈ 89%.

#### ఇది ఎలా పనిచేస్తుంది

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### ఎప్పుడు ఉపయోగించాలి

దీని కోసం స్టాక్డ్ మోడ్ని ఉపయోగించండి:

- సాధనం-భారీ వర్క్ఫ్లోలు (ఏజెంటిక్ కోడింగ్, పరిశోధన)
- కాస్ట్ సెన్సిటివ్ బ్యాచ్ ప్రాసెసింగ్
- మీకు గరిష్ట టోకెన్ పొదుపులు అవసరమైనప్పుడు

పేర్చబడిన పైప్లైన్లు గ్లోబల్ `stackedPipeline` కంప్రెషన్ సెట్టింగ్ ద్వారా కాన్ఫిగర్ చేయబడతాయి లేదా రౌటింగ్ కాంబోకి కేటాయించిన పేరున్న కంప్రెషన్ కాంబో ద్వారా కాన్ఫిగర్ చేయబడతాయి (పైన ప్రతి కాంబో ఓవర్రైడ్ చూడండి) — ఆటో-కాంబో `modePack` ద్వారా కాదు (ఆ ఫీల్డ్ ఆటో-కాంబో మోడల్ ఎంపిక మాత్రమే తిరిగి బరువును కలిగి ఉంటుంది మరియు `stacked` చెల్లుబాటు అయ్యే ప్యాక్ పేరు కాదు).

## కాంబోకు ప్రత్యేకమైన కంప్రెషన్ ఓవర్రైడ్లు

వివిధ వినియోగ సందర్భాల కోసం ప్రవర్తనను సూక్ష్మంగా సర్దుబాటు చేయడానికి, గ్లోబల్ కంప్రెషన్ మోడ్ను **ప్రతి కాంబోకు** ఓవర్రైడ్ చేయవచ్చు:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ఇది వీటికి ఉపయోగకరంగా ఉంటుంది:

- **కోడింగ్ కాంబోలు**: సుదీర్ఘ సెషన్ల కోసం `aggressive` మోడ్ను ఉపయోగించండి
- **త్వరిత ప్రశ్నోత్తర కాంబోలు**: వేగవంతమైన ప్రతిస్పందనల కోసం `lite` మోడ్ను ఉపయోగించండి
- **టూల్స్ను ఎక్కువగా ఉపయోగించే కాంబోలు**: గరిష్ఠ ఆదా కోసం `stacked` మోడ్ను ఉపయోగించండి
- **ప్రొడక్షన్ కాంబోలు**: క్యాషింగ్ ప్రొవైడర్ల కోసం ఓవర్రైడ్ను ఆఫ్లోనే ఉంచండి — ఎల్లప్పుడూ ఆన్లో ఉండే
  క్యాష్-అవేర్ సర్దుబాటు `aggressive`/`ultra`ను స్వయంచాలకంగా `standard`కు డౌన్గ్రేడ్ చేస్తుంది
  (`cache-aware` మోడ్ను ఎంచుకునే అవకాశం లేదు)
