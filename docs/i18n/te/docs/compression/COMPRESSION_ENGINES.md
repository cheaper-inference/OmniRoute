OmniRoute కంప్రెషన్ ఇంజిన్ కాంట్రాక్ట్ల ఆధారంగా నిర్మించబడింది. ఒక మోడ్ ఒక ఇంజిన్ను నేరుగా
(`caveman` లేదా `rtk`) అమలు చేయగలదు లేదా బహుళ ఇంజిన్లను క్రమంగా అమలు చేసే నిర్ధారిత స్టాక్డ్ పైప్లైన్ను ఉపయోగించగలదు.

## మోడ్లు

| మోడ్         | ఇంజిన్ మార్గం                                                                         | ఉద్దేశించిన ఇన్పుట్                                  |
| ------------ | ------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `off`        | none                                                                                  | ఖచ్చితమైన ప్రాంప్ట్ సంరక్షణ                          |
| `lite`       | Caveman lite helpers                                                                  | తక్కువ-ప్రమాదకరమైన ఎల్లప్పుడూ ఆన్లో ఉండే శుభ్రపరచడం  |
| `standard`   | Caveman                                                                               | సహజ-భాషా ప్రాంప్ట్ సంక్షేపణం                         |
| `aggressive` | Caveman + history/tool summarizers                                                    | సుదీర్ఘ చాట్ సెషన్లు                                 |
| `ultra`      | Caveman + pruning helpers                                                             | సందర్భ పరిమితి పునరుద్ధరణ                            |
| `rtk`        | RTK                                                                                   | టెర్మినల్, షెల్, బిల్డ్, టెస్ట్ మరియు గిట్ అవుట్పుట్ |
| `omniglyph`  | OmniGlyph                                                                             | స్థానిక ప్రొవైడర్ వైర్పై సందర్భం-చిత్రంగా            |
| `stacked`    | Pipeline. The request default is `session-dedup -> lite`. `rtk -> caveman` is opt-in. | మిశ్రమ టూల్ లాగ్లు మరియు గద్యం, గరిష్ట పొదుపు        |

### OmniGlyph కంప్రెషన్ ప్రొఫైల్లు

`omniglyph` ఇంజిన్ (ప్యాకేజీ `omniglyph`, 1.4.0+) పేరున్న సెమాంటిక్ ప్రొఫైల్ను అంగీకరిస్తుంది, ఇది
కంప్రెషన్ సెట్టింగ్లలో `omniglyph.profile` ద్వారా ప్రపంచవ్యాప్తంగా లేదా స్టాక్డ్ పైప్లైన్ యొక్క
స్టెప్ కాన్ఫిగర్ ద్వారా ప్రతి స్టెప్కు సెట్ చేయబడుతుంది:

| ప్రొఫైల్      | సరిహద్దు                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------- |
| `aggressive`  | డిఫాల్ట్. ప్రచురించిన రసీదులు కొలిచిన విధానం — చిత్రాల సిస్టమ్, టూల్ డాక్యుమెంట్లు మరియు దట్టమైన చరిత్ర |
| `balanced`    | లైవ్ స్టేట్ను స్థానికంగా ఉంచుతుంది, చివరి 8 మలుపులను రక్షిస్తుంది, పాత మూసివేసిన చరిత్రను కుదించుతుంది  |
| `coding-safe` | అధికారం, టూల్ స్కీమాలు మరియు లైవ్ టూల్ అవుట్పుట్ను స్థానికంగా ఉంచుతుంది, చివరి 12 మలుపులను రక్షిస్తుంది |
| `passthrough` | రూట్ చేస్తుంది, మార్చకుండా; ఇంజిన్ దాటవేయబడుతుంది                                                       |

ప్రొఫైల్ ఒక **సీలింగ్, ఫ్లోర్ కాదు**: ప్యాకేజీలోని `mergeCompressionProfileOptions` ఒక కాలర్ను
ప్రొఫైల్ మూసివేసిన లాస్సీ లేన్ను తిరిగి తెరవడానికి అనుమతించదు, కాబట్టి `coding-safe` కింద ప్రతి-స్టెప్
`preserveSystemPrompt: false` సిస్టమ్ కంప్రెషన్ను తిరిగి ప్రారంభించదు.

ఈ కోడ్బేస్పై కొలవబడింది: `coding-safe` మరియు `balanced` `minCompressChars` ను దాని గరిష్ట స్థాయికి
పెంచుతాయి మరియు సిస్టమ్, టూల్ స్కీమాలు మరియు టూల్ ఫలితాలను స్థానికంగా ఉంచుతాయి, కాబట్టి ఇంకా చరిత్రను
కూడగట్టుకోని సెషన్ `below_min_chars` వద్ద ఆగిపోతుంది మరియు ఇంజిన్ ఏమీ మార్చదు. అందుకే డిఫాల్ట్
సురక్షితమైన ప్రొఫైల్ కాకుండా `aggressive` గా ఉంటుంది.

ప్యాకేజీ దాని స్వంత మోడల్ స్కోప్ మరియు ప్రొఫైల్ను దాని పర్యావరణ కాన్ఫిగరేషన్ నుండి పరిష్కరిస్తుంది.
ఓమ్నిరూట్ ఎప్పుడూ నిర్ణయాన్ని అప్పగించదు: అడాప్టర్ మోడల్ గేట్ను ప్యాకేజీ యొక్క అత్యంత పరిమిత స్కోప్కు
పిన్ చేస్తుంది, కాబట్టి హోస్ట్ పర్యావరణ సెట్టింగ్లు అనుమతించబడిన జాబితాను మాత్రమే తగ్గించగలవు,
ఓమ్నిరూట్ కొలిచిన రసీదులను దాటి విస్తరించలేవు.

## ఇంజిన్ రిజిస్ట్రీ

రిజిస్ట్రీ `open-sse/services/compression/engines/registry.ts`లో ఉంటుంది. ఇంజిన్లు ఉమ్మడి
ఒప్పందాన్ని అందుబాటులో ఉంచుతాయి:

- `id`: `caveman` లేదా `rtk` వంటి స్థిరమైన ఇంజిన్ id
- `apply(text, config)`: స్టాక్డ్ పైప్లైన్లు ఉపయోగించే లెగసీ అమలు మార్గం
- `compress(input, config)`: టెక్స్ట్ + గణాంకాలను తిరిగి ఇచ్చే ప్రాథమిక అమలు మార్గం
- `getConfigSchema()`: చెల్లుబాటు అయ్యే config యొక్క JSON-Schema-వంటి ఆకృతిని తిరిగి ఇస్తుంది
- `validateConfig(config)`: `{ valid, errors[] }`ను తిరిగి ఇస్తుంది

నమోదు కోసం `registerCompressionEngine(engine)` (లేదా అధునాతన సందర్భాల కోసం `registerEngine`)
ఉపయోగించబడుతుంది; ఇది ఆమోదించే ముందు `assertValidEngine()` మరియు `validateConfig(defaultConfig)`ను కాల్ చేస్తుంది.
రన్టైమ్లో ఒక ఇంజిన్ను తొలగించడానికి `unregisterCompressionEngine(id)` ఉపయోగించండి.

కంప్రెషన్ అమలవడానికి ముందు `strategySelector.ts` అంతర్నిర్మిత ఇంజిన్లను నమోదు చేస్తుంది. దీనివల్ల ప్రివ్యూ,
రన్టైమ్ కంప్రెషన్, స్టాక్డ్ మోడ్, పరీక్షలు మరియు భవిష్యత్ ఇంజిన్లు ఒకే అమలు మార్గాన్ని ఉపయోగించగలవు.

### MCP వివరణ కంప్రెషన్ (సంబంధితది)

ప్రత్యేక రిజిస్ట్రీ, రిజిస్ట్రీ స్థాయిలో MCP టూల్ వివరణ మెటాడేటాను కంప్రెస్ చేస్తుంది — చూడండి
`open-sse/mcp-server/descriptionCompressor.ts` మరియు [MCP-SERVER.md](../frameworks/MCP-SERVER.md). ఇది
Caveman నియమాలను తిరిగి ఉపయోగిస్తుంది, కానీ అభ్యర్థన పేలోడ్లపై కాకుండా టూల్ మెటాడేటాపై పనిచేస్తుంది.

### అదనపు అంతర్నిర్మిత ఇంజిన్లు

Caveman, RTK మరియు LLMLingua-2తో పాటు, రిజిస్ట్రీలో అనేక ప్రత్యేక నష్టం-లేని /
నిర్మాణాత్మక ఇంజిన్లు ఉంటాయి (స్టాక్డ్ పైప్లైన్లు, ప్లేగ్రౌండ్ మరియు పరీక్షలు వీటిని ఉపయోగిస్తాయి):

| ఇంజిన్        | Id              | ఇది చేసే పని                                                                                                                                                                                              |
| ------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CCR           | `ccr`           | Content-Compress-Retrieve (H4): పెద్ద, వరుసగా ఉన్న టెక్స్ట్ బ్లాక్లను కంటెంట్-అడ్రెస్డ్ రిఫరెన్స్లతో భర్తీ చేస్తుంది; తద్వారా పునరావృతమయ్యే/పెద్ద బ్లాక్లు ఒక్కసారి పంపబడి, ఆ తర్వాత రిఫరెన్స్ చేయబడతాయి. |
| headroom      | `headroom`      | SmartCrusher (H3 + N5): ఏకరీతి JSON-array పేలోడ్లను కాలమ్-ఆధారిత `[N rows]` రూపంలోకి నష్టం లేకుండా పట్టిక రూపంలో సంక్షిప్తం చేస్తుంది.                                                                    |
| ionizer       | `ionizer`       | చాలా పెద్ద ఏకరీతి బ్లాక్లలో మొదటి/మధ్య/చివరి వరుసల శాంప్లింగ్ను చేస్తూ, తొలగించిన మధ్య భాగాన్ని CCR కంటెంట్-అడ్రెస్డ్ రిఫరెన్స్గా నిల్వ చేస్తుంది.                                                        |
| session-dedup | `session-dedup` | కంటెంట్-అడ్రెస్డ్ క్రాస్-టర్న్ డీడూప్లికేషన్ (TokenMizer-ప్రేరేపితం): అదే సెషన్లోని మునుపటి టర్న్లలో ఇప్పటికే కనిపించిన టెక్స్ట్ను తొలగిస్తుంది.                                                          |

**CCR రిట్రీవ్-ప్రోటోకాల్ సూచన (#8033):** ఒక అభ్యర్థనలో CCR మొదటిసారి ≥1 బ్లాక్ను
భర్తీ చేసినప్పుడు, ఇంజిన్ ఒకే, ఐడెంపొటెంట్ `system` సందేశాన్ని (`[CCR protocol]`
సెంటినెల్తో ప్రారంభమయ్యేది) ముందుగా జోడించి, కాలర్కు మార్కర్ → టూల్ ఒప్పందాన్ని బోధిస్తుంది: ఒక
`[CCR retrieve hash=<24hex> chars=N]` మార్కర్ అర్థం ఏమిటి, హ్యాష్ను యథాతథంగా కాపీ చేయాలి
(మొత్తం 24 హెక్స్ అక్షరాలు — తప్పుగా కాపీ చేసిన హ్యాష్లే "block not found"
విఫలాలకు సంభావ్య కారణం), అలాగే `[dedup:ref sha=...]` మార్కర్ అంటే "చరిత్రలో వెనక్కి చూడండి", "టూల్ను కాల్ చేయండి"
అని కాదని వివరిస్తుంది. కాలర్ ప్రకటించిన `tools[]`, అది నిజంగా
`omniroute_ccr_retrieve`ను చేరుకోగలదని నిరూపించినప్పుడు **మాత్రమే ఈ గమనిక ఇంజెక్ట్ చేయబడుతుంది**
(`open-sse/services/compression/engines/ccr/protocolInstruction.ts`లోని
`callerSupportsCcrRetrieve()`) — ఆ టూల్ లేని సాధారణ OpenAI-అనుకూల కాలర్కు, అది
చేరుకోలేని దానిని కాల్ చేయమనే సూచన ఎప్పుడూ అందదు. ఇంజెక్ట్ చేసే ముందు సందేశ చరిత్రలో సెంటినెల్
ఉందో లేదో స్కాన్ చేయడం ద్వారా ఐడెంపొటెన్సీ అమలు చేయబడుతుంది; అందువల్ల మల్టీ-టర్న్ అభ్యర్థనలు
(మునుపటి సందేశాలను మళ్లీ ప్లే చేసేవి) ప్రతి టర్న్కు ఒకసారి చొప్పున గమనికను పేర్చవు.

## Caveman

Caveman మోడ్ సాధారణ గద్యాన్ని అర్థపరంగా సంక్షిప్తీకరించడంపై దృష్టి సారిస్తుంది:

- కోడ్ బ్లాక్లు, URLs, JSON, పాత్లు మరియు నిర్మిత డేటాను యథాతథంగా ఉంచుతుంది
- అనవసర పదాలు, సందిగ్ధతను సూచించే పదబంధాలు, పునరావృత సందర్భం మరియు సుదీర్ఘ అనుసంధాన పదబంధాలను తొలగిస్తుంది
- `open-sse/services/compression/rules/`లో భాషను పరిగణించే ఫైల్ రూల్ ప్యాక్లకు మద్దతు ఇస్తుంది
- లెగసీ `standard`, `aggressive` మరియు `ultra` మోడ్ల ద్వారా అందుబాటులోనే ఉంటుంది

డ్యాష్బోర్డ్లో దీని స్థానం `Dashboard -> Context & Cache -> Caveman`.

Caveman అప్స్ట్రీమ్ ప్రకారం అవుట్పుట్ టోకెన్లు `~75%` తక్కువగా ఉంటాయి, బెంచ్మార్క్లలో సగటు అవుట్పుట్ ఆదా `65%`,
దాని పరిధి `22-87%`, అలాగే ఇన్పుట్ కంప్రెషన్ సాధనం `~46%`. స్టాక్ చేసిన ప్రాంప్ట్/కాంటెక్స్ట్ ఆదాలను
డాక్యుమెంట్ చేసేటప్పుడు OmniRoute, Caveman ఇన్పుట్-సైడ్ సంఖ్యను ఉపయోగిస్తుంది; Caveman అవుట్పుట్ మోడ్
ప్రత్యేక ప్రతిస్పందన-ప్రవర్తన ఫీచర్గానే ఉంటుంది.

## RTK

RTK మోడ్ కమాండ్ మరియు టూల్ అవుట్పుట్పై దృష్టి సారిస్తుంది:

- `git status`, `git branch`, `git diff`, Vitest/Jest/Pytest, Cargo/Go పరీక్షలు,
  TypeScript/Vite/Webpack బిల్డ్లు, ESLint, npm audit/ఇన్స్టాలేషన్లు, Docker లాగ్లు,
  షెల్ `find`/`grep`, స్టాక్ ట్రేస్లు మరియు సాధారణ లాగ్లు వంటి అవుట్పుట్ వర్గాలను గుర్తిస్తుంది
- `open-sse/services/compression/engines/rtk/filters/`లోని 49 JSON ఫిల్టర్లను వర్తింపజేస్తుంది
- RTK-శైలి డిక్లరేటివ్ పైప్లైన్కు మద్దతు ఇస్తుంది: ANSI తొలగింపు, రీప్లేస్, మ్యాచ్-అవుట్పుట్ షార్ట్-సర్క్యూట్,
  లైన్ల తొలగింపు/ఉంచడం, ప్రతి లైన్ ట్రంకేషన్, హెడ్/టెయిల్/గరిష్ఠ-లైన్ ట్రంకేషన్ మరియు ఖాళీగా ఉన్నప్పుడు ఫాల్బ్యాక్
- `.rtk/filters.json`లో ట్రస్ట్-గేటెడ్ ప్రాజెక్ట్ ఫిల్టర్లకు మరియు
  `DATA_DIR/rtk/filters.json`లో గ్లోబల్ ఫిల్టర్లకు మద్దతు ఇస్తుంది
- ANSI సీక్వెన్స్లు, ప్రోగ్రెస్ నాయిస్, పునరావృత లైన్లు మరియు ఉపయోగంలేని బాయిలర్ప్లేట్ను తొలగిస్తుంది
- చర్య తీసుకోదగిన వైఫల్యాలు, హెచ్చరికలు, సారాంశాలు, మారిన ఫైల్లు మరియు టెయిల్ కాంటెక్స్ట్ను యథాతథంగా ఉంచుతుంది
- ప్రామాణీకరించిన మేనేజ్మెంట్ రూట్ల ద్వారా రికవరీ/డీబగ్గింగ్ కోసం సవరించిన ముడి అవుట్పుట్ను
  ఐచ్ఛికంగా నిల్వ ఉంచగలదు

డ్యాష్బోర్డ్లో దీని స్థానం `Dashboard -> Context & Cache -> RTK`.

కస్టమ్ ఫిల్టర్లు, ట్రస్ట్, వెరిఫై మరియు ముడి-అవుట్పుట్ రికవరీకి సంబంధించిన నిర్వహణ వివరాలు
[`RTK_COMPRESSION.md`](./RTK_COMPRESSION.md)లో ఉన్నాయి.

RTK అప్స్ట్రీమ్ ప్రకారం కమాండ్-అవుట్పుట్ కంప్రెషన్తో `60-90%` ఆదా అవుతుంది. దాని README ఉదాహరణలో
30 నిమిషాల Claude Code సెషన్ `~118,000` టోకెన్ల నుంచి `~23,900` టోకెన్లకు తగ్గి, `79.7%` ఆదా అయినట్లు చూపుతుంది.

## LLMLingua-2 (అర్థపరమైన ప్రూనింగ్)

LLMLingua-2 మోడ్ చిన్న ONNX టోకెన్ క్లాసిఫైయర్ను ఉపయోగించి గద్యంపై **అర్థపరమైన టోకెన్ ప్రూనింగ్**
చేస్తుంది, తద్వారా రూల్-ఆధారిత Caveman మరియు RTK ఇంజిన్లకు అనుబంధంగా పనిచేస్తుంది:

- సిస్టమ్-కాని సందేశాల్లోని గద్యాన్ని మాత్రమే కంప్రెస్ చేస్తుంది; ఫెన్స్డ్ కోడ్ బ్లాక్లు మరియు యథాతథంగా ఉంచాల్సిన ఇతర
  నిర్మాణాలు ఎప్పుడూ మార్చబడవు
- వర్కర్ థ్రెడ్లో `@atjsh/llmlingua-2` బ్యాకెండ్ను (ONNXను `@huggingface/transformers` ద్వారా) అమలు చేస్తుంది,
  కాబట్టి మోడల్ ఇన్ఫరెన్స్ అభ్యర్థన ఈవెంట్ లూప్ను ఎప్పుడూ బ్లాక్ చేయదు
- ఇది **స్టాక్ చేయదగినది** (`stackPriority` 35): స్టాక్ చేసిన పైప్లైన్లో ఇది నిర్మాణాత్మక
  ఇంజిన్ల (CCR, session-dedup, headroom, Caveman) తర్వాత, కానీ `ultra`కు ముందు అమలవుతుంది, ఎందుకంటే
  ఇప్పటికే నిర్మాణాత్మకంగా కంప్రెస్ చేసిన టెక్స్ట్పై అర్థపరమైన ప్రూనింగ్ అత్యంత ప్రభావవంతంగా ఉంటుంది — ఉదా.
  `rtk -> caveman -> llmlingua`
- **ఏ ఎరర్ వచ్చినా ఫెయిల్-ఓపెన్ అవుతుంది** (లేని ఐచ్ఛిక డిపెండెన్సీలు, వర్కర్ స్పాన్, మోడల్ లోడ్, ఇన్ఫరెన్స్
  లేదా టైమ్అవుట్) → ఎరర్కు బదులుగా అసలు టెక్స్ట్ ఎలాంటి మార్పు లేకుండా తిరిగి ఇవ్వబడుతుంది

ఇంజిన్ స్థానం: `open-sse/services/compression/engines/llmlingua/`. డ్యాష్బోర్డ్లో దీని స్థానం
`Dashboard -> Context & Cache -> LLMLingua`.

### మోడల్లు

డిఫాల్ట్ మోడల్ **TinyBERT** (`atjsh/llmlingua-2-js-tinybert-meetingbank`, ~57 MB,
వేగవంతమైనది). అధిక ఖచ్చితత్వం కలిగిన **BERT-base** మోడల్ (`Arcoldd/llmlingua4j-bert-base-onnx`,
~710 MB) ఇంజిన్ కాన్ఫిగ్లోని `model` ఫీల్డ్ ద్వారా అందుబాటులో ఉంటుంది. మొదటి కాల్ సమయంలో (`modelStore.ts`),
`@huggingface/transformers` ఎంచుకున్న మోడల్ను HuggingFace Hub నుంచి
`${DATA_DIR}/models/llmlingua`లోకి లేజీగా డౌన్లోడ్ చేస్తుంది; బదులుగా `modelPath` కాన్ఫిగ్
ఓవర్రైడ్ దాన్ని స్థానిక కాపీ వైపు మళ్లిస్తుంది (ఆఫ్లైన్ / ఎయిర్-గ్యాప్డ్ ఇన్స్టాలేషన్లు).

పీర్లు. ఐచ్ఛిక డిపెండెన్సీలను వదిలివేయకపోతే, ప్రామాణిక `npm install` (డెవలప్మెంట్) ఐచ్ఛిక స్టాక్ను
స్వయంచాలకంగా ఇన్స్టాల్ చేస్తుంది.

**అవసరమైనప్పుడు మాత్రమే ఎందుకు:** పరిమాణాన్ని తక్కువగా ఉంచేందుకు npmలో ప్రచురించిన ప్యాకేజీ, స్టాండ్అలోన్ బండిల్
మరియు Docker ఇమేజ్ ఈ డిపెండెన్సీలు **లేకుండానే** అందించబడతాయి. అవి లేనప్పుడు, వర్కర్ డిపెండెన్సీ
గేట్ (`worker.ts`లోని `@atjsh/llmlingua-2` రిజాల్వ్ ప్రోబ్) విఫలమై, ఇంజిన్
**నిశ్శబ్దంగా ఫెయిల్-ఓపెన్ అవుతుంది** — LLMLinguaను ఎంచుకోవడం వల్ల ఏ చర్యా జరగదు (టెక్స్ట్ మార్పు లేకుండా
తిరిగి ఇవ్వబడుతుంది, ఎలాంటి ఎరర్ లాగ్ చేయబడదు). ప్రూన్ చేసిన ఎన్విరాన్మెంట్లో దీన్ని యాక్టివేట్ చేయడానికి,
ఐచ్ఛిక స్టాక్ను ఇన్స్టాల్ చేయండి:

```bash
# package.json optionalDependenciesలో ప్రకటించిన వెర్షన్లకు పిన్ చేయండి
npm install @atjsh/llmlingua-2@2.0.5 js-tiktoken
```

`@tensorflow/tfjs` తొలగింపు (2.0.4+) గతంలో అత్యధికంగా ~800 MB ఆక్రమించిన భాగాన్ని తొలగిస్తుంది —
మిగిలిన ఫుట్ప్రింట్లో transformers.js + onnxruntime-node రన్టైమ్లు, అలాగే మొదటిసారి ఉపయోగించినప్పుడు
డౌన్లోడ్ అయ్యే TinyBERT మోడల్ (~57 MB) ఉంటాయి (npm ద్వారా కాదు).

ప్రతి ఎన్విరాన్మెంట్కు:

- **Dev / `npm install`** — మీరు `--omit=optional`
  (లేదా `--no-optional`) పాస్ చేయకపోతే స్వయంచాలకంగా ఇన్స్టాల్ అవుతుంది. ఎలాంటి చర్య అవసరం లేదు.
- **Global npm (`npm i -g omniroute`) / standalone** — ఇన్స్టాల్ చేసిన ప్యాకేజీ డైరెక్టరీలో
  పైన ఉన్న ఇన్స్టాల్ కమాండ్ను అమలు చేయండి లేదా ఐచ్ఛిక డిపెండెన్సీలను మినహాయించకుండా మళ్లీ ఇన్స్టాల్ చేయండి.
- **Docker** — ఉత్పన్నమైన ఇమేజ్ లేయర్లో ఇన్స్టాల్ కమాండ్ను జోడించండి; ప్రచురించిన ఇమేజ్
  ఉద్దేశపూర్వకంగానే కనిష్ఠ పరిమాణంలో అందించబడుతుంది.
- **VPS (PM2)** — యాప్ యొక్క `node_modules`లో ఇన్స్టాల్ చేసి, వర్కర్ గేట్ను మళ్లీ
  తనిఖీ చేసేలా ప్రాసెస్ను రీస్టార్ట్ చేయండి.
- **Raw Next standalone (`npm run build` → `.build/next/standalone/server.js`)** — ఈ
  standalone ట్రేస్లో వర్కర్ గానీ ఐచ్ఛిక డిపెండెన్సీలు గానీ ఉండవు, కాబట్టి ఇంజిన్ నిశ్శబ్దంగా
  fail-open అవుతుంది. `scripts/build/colocate-standalone.mjs` రెండింటినీ (వర్కర్ esbuild +
  standalone ట్రీలోకి ఐచ్ఛిక-డిపెండెన్సీ క్లోజర్) మళ్లీ వర్తింపజేస్తుంది; ప్రతి బిల్డ్ తర్వాత
  `postbuild` npm హుక్ ద్వారా ఇది స్వయంచాలకంగా అమలవుతుంది. ఇది idempotentగా ఉంటుంది, డిపెండెన్సీలు లేనప్పుడు fail-soft అవుతుంది.

**ఇది సక్రియంగా ఉందని ధృవీకరించండి:** LLMLinguaను ఎంచుకున్నప్పుడు, వాస్తవ గద్యం నిజంగానే కుదించబడుతుంది (ఇంజిన్
fail-open కావడం ఆగిపోతుంది), అలాగే మొదటి రిక్వెస్ట్ మోడల్ను
`${DATA_DIR}/models/llmlingua`లోకి డౌన్లోడ్ చేయడాన్ని ట్రిగ్గర్ చేస్తుంది. గేట్ ఉద్దేశపూర్వకంగా `@atjsh/llmlingua-2`ను మాత్రమే తనిఖీ చేస్తుంది —
ఇతర పీర్లు ESM-only కావడం వల్ల అవి ఉన్నప్పటికీ వాటిపై `require.resolve` ఎర్రర్ను విసురుతుంది — కాబట్టి
`import()` సమయంలో ఏదైనా పీర్ నిజంగా లేకపోతే వర్కర్ ఇప్పటికీ fail-open అవుతుంది.

## స్టాక్డ్ పైప్లైన్లు

స్టాక్డ్ మోడ్ పైప్లైన్ దశలను క్రమంగా అమలు చేస్తుంది. డిఫాల్ట్:

```txt
rtk -> caveman
```

ప్రాంప్ట్లో కమాండ్ అవుట్పుట్తో పాటు మానవ లేదా అసిస్టెంట్ గద్యం ఉండే కోడింగ్-ఏజెంట్ సెషన్ల కోసం దీనిని ఉపయోగించండి. మొదట RTK అనవసరమైన టూల్ లాగ్లను తగ్గిస్తుంది, ఆ తర్వాత Caveman మిగిలిన సహజ భాషను కుదిస్తుంది.

పైప్లైన్ దశలు కంప్రెషన్ సెట్టింగ్లలోని `stackedPipeline`తో లేదా కంప్రెషన్ కాంబోల ద్వారా కాన్ఫిగర్ చేయబడతాయి.

రెండు ఇంజిన్లు ఒకే అర్హతగల పేలోడ్ను తగ్గించినప్పుడు, ఆదా సమ్మిళితమవుతుంది:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## MCP యాక్సెసిబిలిటీ ట్రీ ఫిల్టర్

MCP యాక్సెసిబిలిటీ-ట్రీ స్మార్ట్ ఫిల్టర్ అనేది పోస్ట్-ఎగ్జిక్యూషన్ కంప్రెషన్ లేయర్. ఇది ప్రాంప్ట్లు లేదా కాంటెక్స్ట్పై కాకుండా MCP **టూల్ ఫలితాలపై** అమలవుతుంది. Playwright, computer-use, browser-automation MCP సర్వర్ల వంటి టూల్లు తిరిగి ఇచ్చే సుదీర్ఘ యాక్సెసిబిలిటీ-ట్రీ మరియు బ్రౌజర్ స్నాప్షాట్ పేలోడ్లను ఇది లక్ష్యంగా చేసుకుంటుంది.

### ఇది ఏమి చేస్తుంది

1. **నాయిస్ తొలగింపు** — ఖాళీ generic/text ఎంట్రీలను (`- generic:`, `- text: ""`) తొలగిస్తుంది
2. **సిబ్లింగ్ కుదింపు** — వరుసగా ≥ `collapseThreshold` (డిఫాల్ట్ 30) లైన్లు నిర్మాణాత్మక పునరావృతాలుగా ఉన్నప్పుడు, వాటిని మొదటి `collapseKeepHead` (డిఫాల్ట్ 10) లైన్లు + సంఖ్యా సారాంశం + చివరి `collapseKeepTail` (డిఫాల్ట్ 5) లైన్లుగా కుదిస్తుంది
3. **Ref సంరక్షణ** — Playwright/computer-useకు అవసరమైన `[ref=eXX]` యాంకర్లు ఎప్పటికీ మార్చబడవు
4. **కఠిన ట్రంకేషన్** — కుదించిన తర్వాత కూడా టెక్స్ట్ `maxTextChars` (డిఫాల్ట్ 50,000) దాటితే, ఏజెంట్ పనిని కొనసాగించగలిగేలా నావిగేషన్ సూచనతో దానిని కత్తిరిస్తుంది

### ఇంజిన్ స్థానం

```txt
open-sse/services/compression/engines/mcpAccessibility/
  index.ts            ← smartFilterText() ఎంట్రీ పాయింట్
  collapseRepeated.ts ← సిబ్లింగ్-కుదింపు అల్గోరిథమ్
  constants.ts        ← DEFAULT_MCP_ACCESSIBILITY_CONFIG
```

### కాన్ఫిగరేషన్

గ్లోబల్ సెట్టింగ్లలోని `compression.mcpAccessibility` ద్వారా నియంత్రించబడుతుంది (మైగ్రేషన్ 056). డిఫాల్ట్ కాన్ఫిగ్:

```json
{
  "enabled": true,
  "maxTextChars": 50000,
  "collapseThreshold": 30,
  "collapseKeepHead": 10,
  "collapseKeepTail": 5,
  "minLengthToProcess": 2000
}
```

`type` విలువ `"text"`గా ఉండి, నిడివి `minLengthToProcess`ను దాటే టూల్-రిజల్ట్ పేలోడ్లకు మాత్రమే ఈ ఫిల్టర్ వర్తింపజేయబడుతుంది. ఇది ప్రాంప్ట్ కంప్రెషన్ను లేదా రిక్వెస్ట్ పేలోడ్లను ప్రభావితం చేయదు.

### అంచనా ఆదా

పేజీ సంక్లిష్టతను బట్టి బ్రౌజర్ స్నాప్షాట్ టూల్ ఫలితాలపై 60–80% ఆదా. కుదింపు అల్గోరిథమ్ లైన్ల సంఖ్య పరంగా O(n)గా ఉంటుంది మరియు అతితక్కువ లేటెన్సీని జోడిస్తుంది.

### ఈ ఫిల్టర్ మరియు పైన పేర్కొన్న కంప్రెషన్ ఇంజిన్ల మధ్య తేడా

## కంప్రెషన్ కాంబోలు

కంప్రెషన్ కాంబోలు అనేవి రూటింగ్ కాంబోలకు కేటాయించగల పేరుగల కంప్రెషన్ ప్రొఫైల్లు:

- `compression_combos`: మోడ్, పైప్లైన్, RTK కాన్ఫిగరేషన్, భాషా కాన్ఫిగరేషన్ మరియు డిఫాల్ట్ మార్కర్ను నిల్వ చేస్తుంది
- `compression_combo_assignments`: కంప్రెషన్ కాంబోను రూటింగ్ కాంబోకు మ్యాప్ చేస్తుంది
- సాధారణ కాంబో ఓవర్రైడ్లకు ముందు రన్టైమ్ ఇంటిగ్రేషన్ కేటాయించిన కంప్రెషన్ కాంబోను పరిష్కరిస్తుంది
- అనలిటిక్స్లో `compression_combo_id` మరియు `engine` ఉంటాయి

డ్యాష్బోర్డ్ స్థానం: `Dashboard -> Context & Cache -> Compression Combos`.

## ముందస్తు అవసరాలు / ఆపరేటర్ గైడ్ (CCR & సెషన్-డెడప్)

CCR (`ccr`) మరియు `session-dedup` టెక్స్ట్ని రీప్లేస్ చేయండి లేదా ఎలైడ్ చేయండి మరియు a వదిలివేయండి** మార్కర్** వెనుక. క్లయింట్ను వైరింగ్ చేయడానికి, రెండు మార్కర్లను చదవడానికి మరియు ఎలిడెడ్ కంటెంట్ను తిరిగి పొందడం లేదా నిర్ధారించడం కోసం ఈ విభాగం ఆపరేటర్ సూచన. ప్రతి ఇంజిన్ యొక్క మెకానిక్స్ పైన కవర్ చేయబడ్డాయి; ఇది "నేను దీన్ని ఎలా అమలు చేయాలి" పొర.

### నిల్వ శ్రేణులు (పునఃప్రారంభించబడినవి)

CCR a** రెండు-స్థాయి** స్టోర్, మెమరీలో మాత్రమే కాదు:

- **హాట్ ఇన్-మెమరీ టైర్** — పర్-బ్లాక్ క్యాప్ 2 MiB, పర్-ప్రిన్సిపల్ 16 MiB, గ్లోబల్ 64 MiB. ఎంట్రీలు 24 h TTL (గరిష్టంగా 7 రోజులు)కి డిఫాల్ట్గా ఉంటాయి. మెమరీ నుండి పూర్తి MCP తిరిగి పొందడం 256 KiB వద్ద పరిమితం చేయబడింది; ఇంకా పెద్దది ఏదైనా పరిధి / grep మోడ్ల ద్వారా చేరుకోవచ్చు.
- **మన్నికైన SQLite టైర్** (`ccr_blocks`, `COMPRESSION_CCR_DURABLE_STORE`, డిఫాల్ట్గా ఆన్) — ఇన్-మెమరీ టైర్కు మద్దతు ఇస్తుంది కాబట్టి ఒక బ్లాక్ LRU తొలగింపు, పునఃప్రారంభం లేదా మరొక సందర్భంలో ల్యాండింగ్ను తిరిగి పొందుతుంది. అడ్డు వరుస బ్లాక్ యొక్క TTL ఉంచుతుంది, కాబట్టి దాని TTL దాటిన బ్లాక్ రెండు శ్రేణుల నుండి పోయింది.

ముగ్గురు గార్డులు మన్నికైన శ్రేణిని — బంధించి ఉంచుతారు ఒక బ్లాక్ మెమరీని మాత్రమే ఉంచుతుంది:

1. బ్లాక్ ముగిసింది** 512 KB** (`MAX_DURABLE_BLOCK_BYTES`);
2. రన్టైమ్ అనేది క్లౌడ్ రన్టైమ్ (స్థానిక డిస్క్ లేదు);
3. `COMPRESSION_CCR_DURABLE_STORE=false`.

కాబట్టి "బ్లాక్ అదృశ్యమైంది" అనేది బ్లాంకెట్ రీస్టార్ట్ స్టోరీ కాదు: లోకల్, నాన్-క్లౌడ్ రన్టైమ్లోని sub-512 KB బ్లాక్ దాని TTL అయిపోయే వరకు మన్నికైన టైర్ ద్వారా పునఃప్రారంభించబడుతుంది. వేరియబుల్ కోసం [పర్యావరణ సూచనను](../reference/ENVIRONMENT.md) చూడండి.

| మార్కర్                               | అర్థం                                                                                                                                                | మోడల్ ఏమి చేయాలి                                                                                                                                                                                                           |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[CCR retrieve hash=<24hex> chars=N]` | ఒక పెద్ద బ్లాక్ కంటెంట్ చిరునామాతో నిల్వ చేయబడింది.                                                                                                  | తో `omniroute_ccr_retrieve` కాల్ చేయండి** 24-హెక్స్ హాష్ అక్షరాలతో కాపీ చేయబడింది** అసలు వచనాన్ని తిరిగి పొందడానికి.                                                                                                       |
| `[dedup:ref sha=…]`                   | `session-dedup` ఎలిడెడ్ టెక్స్ట్ ఇప్పటికే అదే సెషన్ యొక్క మునుపటి మలుపులో పంపబడింది. ఇది ఒక** ఉద్దేశపూర్వకంగా తిరిగి చూడటం** , నష్టం లేదా లోపం కాదు. | చేయండి** కాదు** ఏదైనా సాధనానికి కాల్ చేసి చేయండి** కాదు** దానిని "పునర్నిర్మాణం" చేయడానికి ప్రయత్నించండి. టెక్స్ట్ యొక్క మొదటి సంఘటన కానానికల్ కాపీ; ప్రస్తుత మలుపు తిరిగి వ్రాయబడదు, అది తరువాతి మలుపులో తీసివేయబడుతుంది. |

`[dedup:ref]` లుక్-బ్యాక్ అనేది ఉద్దేశపూర్వక ప్రోటోకాల్ నిర్ణయం — ముందుగా పంపే పునర్నిర్మాణం లేదు. "ఈ ఖచ్చితమైన వచనం ఈ సెషన్లో ఇంతకు ముందు వైర్లో ఉంది" అని వ్యవహరించండి.

### క్లయింట్ ముందస్తు అవసరాలు

- **కీ (stdio):** ఒక stdio కాలర్ ప్రతి అభ్యర్థన గుర్తింపును కలిగి ఉండదు, కనుక ఇది `OMNIROUTE_API_KEY` ( MCP సర్వర్ యొక్క `env` లో సెట్ చేయబడింది)తో ప్రమాణీకరిస్తుంది. అది లేకుండా కాలర్ అనామకుడు మరియు ప్రిన్సిపాల్ అవసరమయ్యే సాధనాలు క్షీణించవచ్చు.
- **`tools[]` is the injection precondition.** The CCR retrieve-protocol instruction (#8033) is injected **only** when the request's advertised `tools[]` proves the client can actually reach `omniroute_ccr_retrieve`. The match is a trailing-segment match bounded by a separator (`__`, `.`, `/`, `:`) — never a bare substring — so a namespaced name such as `mcp__gateway__omniroute_ccr_retrieve` still counts. An absent or non-matching `tools[]` means the instruction is _not_ injected, by design.
- **`codemode:false` (OpenCode క్లయింట్లు).** OpenCode కోడ్ మోడ్కి డిఫాల్ట్ అవుతుంది, ఇది మోడల్కు దాని స్థానిక సాధనాలను మాత్రమే ప్రచారం చేస్తుంది మరియు** చేయదు** స్థానిక `tools[]` జాబితాలో MCP సాధనాలను ఉంచండి. MCP సర్వర్ ఎంట్రీపై `codemode: false` సెట్ చేయండి, తద్వారా `omniroute_ccr_*` సాధనాలు ప్రచారం చేయబడతాయి. ఇది ఎ** క్లయింట్** సెట్టింగ్, OmniRoute కాదు. ఇది ఇంకా CCR సూచనలను ఇంజెక్ట్ చేయలేదు: OpenCode ఒక సాధనం `<server>_<tool>` అని పేరు పెట్టింది, కాబట్టి `omniroute` అనే సర్వర్ `omniroute_omniroute_ccr_retrieve` బహిర్గతం చేస్తుంది మరియు `_` సరిపోలిన సెపరేటర్లలో ఒకటి కాదు.
- **ప్రధానోపాధ్యాయులు.** నిల్వ మరియు పునరుద్ధరణ అనేది ప్రమాణీకరించబడిన ప్రిన్సిపాల్ (ప్రతి API కీ) ద్వారా వేరు చేయబడుతుంది. ఒక కీ దాని స్వంత బ్లాక్లను మాత్రమే చూస్తుంది.

### ఒక్కో సాధనానికి స్కోప్లు

ఇరుకైన స్కోప్ ఉన్న HTTP/SSE కాలర్ల కోసం స్కోప్ ఎన్ఫోర్స్మెంట్ ఎల్లప్పుడూ ఆన్లో ఉంటుంది. `omniroute_` CCR సాధనాలు అవసరం:

| సాధనం                    | పరిధి               |
| ------------------------ | ------------------- |
| `omniroute_ccr_store`    | `write:compression` |
| `omniroute_ccr_delete`   | `write:compression` |
| `omniroute_ccr_retrieve` | `read:compression`  |
| `omniroute_ccr_inspect`  | `read:compression`  |
| `omniroute_ccr_list`     | `read:compression`  |
| `omniroute_ccr_stats`    | `read:compression`  |

తప్పిపోయిన పరిధిని అందిస్తుంది**MCP సాధనం లోపం ఫలితం** (`isError: true`, HTTP 403 — కాదు `403 LOCAL_ONLY` అనేది ప్రత్యేక లూప్బ్యాక్ రూట్-గార్డ్ auth): `Error: Insufficient MCP scopes for <tool>. Missing: <scope>.` కనిష్ట రిమోట్ కీ `mcp:connect` ( `/api/mcp/` లోకల్-ఓన్లీ కార్వ్-అవుట్ను ఆథరైజ్ చేస్తుంది) మరియు దానికి అవసరమైన నిర్దిష్ట read/write స్కోప్ను కలిగి ఉంటుంది.

### రిట్రీవల్ పరిమితులు & పేజినేషన్

MCP సాధనం టెక్స్ట్ ఫలితాలు `mcpAccessibility.maxTextChars` చుట్టూ క్లిప్ చేయబడ్డాయి (డిఫాల్ట్ `50000`). ఒక బ్లాక్ యొక్క `full` రిట్రీవ్ 256 KiB — వద్ద క్యాప్ చేయబడింది** అపరిమిత పూర్తి తిరిగి పొందడం లేదు** . బ్లాక్ యొక్క `chars=N` పెద్దగా ఉన్నప్పుడు, మొత్తం తీయడానికి బదులుగా దాన్ని పేజీ చేయండి:

- నియమం:**`chars > 40000` → ఒక `mode` ఉపయోగిస్తుంది** , ఎప్పుడూ బేర్ ఫుల్.
- `mode:"grep"` — regex `pattern` లైన్ వారీగా సరిపోలింది, 1,000 మ్యాచింగ్ లైన్ల వరకు (`unique: true` డ్రాప్స్ రిపీట్లు), "నాకు అవసరమైన ఒక లైన్ను కనుగొనండి" కోసం చౌకైనది.
- `mode:"lines"` — 1-ఇండెక్స్డ్ లైన్ పరిధి; `start` మరియు `end` రెండూ అవసరం.
- `mode:"head"` / `mode:"tail"` — first/last `n` లైన్లు.
- `mode:"stats"` — లైన్, అక్షరం మరియు బైట్ బాడీ లేకుండా గణనలు.

మొత్తం విషయాన్ని ఒకేసారి అభ్యర్థించడం కంటే పేజీలలో సుదీర్ఘ బ్లాక్ను నడవడానికి `start`/`end` తో `mode:"lines"` ఉపయోగించండి.

### సాధనం పేరు పెట్టడం

రిట్రీవ్ టూల్కు ప్రస్తుతం `omniroute_ccr_retrieve` అని పేరు పెట్టారు ( `omniroute_` ఉపసర్గ అనేది క్రాస్-సర్వర్ నేమ్ కొలిషన్ల కోసం డేటెడ్ వర్క్అరౌండ్). క్లీనర్ బౌండెడ్-సఫిక్స్ టూల్ పేరు మరియు MCP JSON ఫలితాలు కత్తిరించబడిన మిడ్-స్ట్రింగ్ కోసం పరిష్కారం అప్స్ట్రీమ్ ఫాలో-అప్లుగా ట్రాక్ చేయబడతాయి; ఈ పేజీ ప్రస్తుత, రవాణా చేయబడిన ప్రవర్తనను మాత్రమే డాక్యుమెంట్ చేస్తుంది.

### సెషన్ జీవితచక్రం

స్ట్రీమబుల్-HTTP సెషన్లు నిష్క్రియంగా ఉంటాయి మరియు సర్వర్ వాటిని రీప్ చేస్తుంది; నిష్క్రియ విండో `OMNIROUTE_MCP_SESSION_IDLE_MS` ద్వారా సెట్ చేయబడింది (డిఫాల్ట్ 5 నిమిషాలు; పేరు ద్వారా సూచించబడింది, హార్డ్కోడ్ విలువ కాదు, కాబట్టి ఈ పేజీ మారినప్పుడు డ్రిఫ్ట్ అవ్వదు). నిష్క్రియ-రీప్డ్ సెషన్ యొక్క లక్షణం `Unknown Mcp-Session-Id` — తో HTTP 404, సెషన్ను మళ్లీ కనెక్ట్ చేయడం లేదా పునఃప్రారంభించడం దీనికి పరిష్కారం,** కాదు** కీని తిప్పడానికి, స్కోప్ని మార్చడానికి లేదా సాధనం పేరు మార్చడానికి.

## పరిధి & మినహాయింపులు

**ఎంబెడ్డింగ్లు ఎప్పటికీ కంప్రెస్ చేయబడవు.** `open-sse/handlers/embeddings.ts` ఏ
కంప్రెషన్ ఇంజిన్నూ ఎప్పుడూ కాల్ చేయదు — అభ్యర్థన/ప్రతిస్పందన బాడీలు మార్పులేమీ లేకుండా నేరుగా ఎగ్జిక్యూటర్కు వెళ్తాయి.
ప్రస్తుతం ఇది నిర్మాణాత్మకమైనది (ఎంబెడ్డింగ్లు మరియు చాట్ కంప్లీషన్లకు వేర్వేరు హ్యాండ్లర్లు ఉన్నాయి), రన్టైమ్
తనిఖీ కాదు, కానీ దీని అర్థం #8034లోని వెక్టర్-వక్రీకరణ సమస్యకు ఎంబెడ్డింగ్ల మార్గంలో
ఎలాంటి ఎక్స్పోజర్ ఉపరితలమూ లేదని.

**ప్రతి-మోడల్/ఎండ్పాయింట్ మినహాయింపు ఫిల్టర్ (#8034).** చాట్ కంప్లీషన్ల కోసం, ఎప్పటికీ
కంప్రెస్ చేయకూడని మోడల్ idలు / `provider/model` లక్ష్యాలను ఆపరేటర్ పేర్కొనవచ్చు — భవిష్యత్తులో
కంప్రెషన్ను ఎంబెడ్డింగ్లకు సమీపమైన మార్గానికి అనుసంధానిస్తే ఇది ఉపయోగకరమైన రక్షణ, అలాగే ఖచ్చితమైన
బైట్-ఫర్-బైట్ ప్రాంప్ట్ ముఖ్యమైన ఏ మోడల్కైనా సాధారణంగా ఉపయోగకరం (డిటర్మినిస్టిక్ మూల్యాంకనాలు, క్యాష్-సెన్సిటివ్
ప్రిఫిక్స్లు మొదలైనవి).

- సెట్టింగ్ల ఫీల్డ్: గ్లోబల్ కంప్రెషన్ కాన్ఫిగరేషన్లో `exclusions?: string[]`
  (`GET`/`PUT /api/settings/compression`), ఇప్పటికే ఉన్న `key_value` కంప్రెషన్
  నేమ్స్పేస్ (`src/lib/db/compression.ts`) ద్వారా నిల్వ చేయబడుతుంది — కొత్త పట్టిక లేదు.
- డ్యాష్బోర్డ్ ట్యాబ్: **Dashboard → Compression → Exclusions**
  (`/dashboard/compression/exclusions`).
- ప్యాటర్న్ సింటాక్స్: `*` మాత్రమే వైల్డ్కార్డ్. ప్యాటర్న్లోని ప్రతి ఇతర regex మెటాక్యారెక్టర్
  మ్యాచింగ్కు ముందు ఎస్కేప్ చేయబడుతుంది, కాబట్టి `gpt-5.6` కేవలం అక్షరార్థ స్ట్రింగ్తోనే మ్యాచ్ అవుతుంది, `gpt-5x6`తో
  ఎప్పటికీ కాదు (ReDoS-సురక్షితం, పరిమితం చేయబడినది, నెస్టెడ్ క్వాంటిఫైయర్లు లేవు). ప్యాటర్న్లు
  బేర్ మోడల్ id మరియు `provider/model` కాంపోజిట్ రెండింటికీ కేస్-ఇన్సెన్సిటివ్గా మ్యాచ్ అవుతాయి — `gpt-5-6`, `openai/gpt-5-6`,
  మరియు `openai/*` అన్నీ పనిచేస్తాయి, అలాగే `*` ఒక్కటే ప్రతి మోడల్ను మినహాయిస్తుంది.
- మ్యాచింగ్: `open-sse/services/compression/exclusions.ts`లోని
  `isCompressionExcluded()` / `normalizeCompressionExclusions()`. కంప్రెషన్ సెట్టింగ్లను పరిష్కరించిన వెంటనే,
  **ఏ ఇంజిన్ అమలుకాకముందే**, `chatCore.ts` మినహాయించిన లక్ష్యాన్ని తనిఖీ చేసి, మ్యాచ్ను
  కంప్రెషన్ను గ్లోబల్గా నిలిపివేసినట్లుగానే పరిగణిస్తుంది — అభ్యర్థన బాడీ నిరూపించగలిగేలా
  బైట్-ఐడెంటికల్గా ఉంటుంది. అనలిటిక్స్లో కనిపించేలా స్కిప్ను `writeCompressionSkip(..., "excluded")` ద్వారా
  రికార్డ్ చేస్తారు.
- డిఫాల్ట్ (ఖాళీ/లేని జాబితా): #8034కు ముందున్న ప్రవర్తనతో సమానంగా ఉంటుంది — ఏదీ మినహాయించబడదు.

## తెలిసిన పరిమితులు

- **LLMLingua-2 (SLM) కోసం ఐచ్ఛిక డిపెండెన్సీలు ఒకేచోట ఉండాలి.** `@atjsh/llmlingua-2` + దాని పీర్ డిపెండెన్సీలు
  `dist/node_modules`లో ఒకేచోట ఉంచబడినప్పుడు మాత్రమే worker ప్రొడక్షన్ బిల్డ్లో నడుస్తుంది
  (`scripts/build/colocateOptionals.mjs`, #4286 చూడండి). అవి లేకపోతే ఇంజిన్ వైఫల్యాన్ని అనుమతిస్తూ
  అసలు టెక్స్ట్ను తిరిగి ఇస్తుంది. Worker రిజల్యూషన్ ఇకపై `import.meta.url`పై ఆధారపడదు
  (అది స్వతంత్ర బండిల్లో విఫలమవుతుంది) — బదులుగా రన్టైమ్ cwd / `argv[1]`ను ఆధారంగా
  చేసుకుంటుంది.
- **Caveman భాషా ప్యాక్లు `de` / `fr` / `ja` పాక్షికమైనవి.** వాటిలో `context` +
  `filler` + `structural` నియమాలు ఉంటాయి, కానీ `dedup` / `ultra` ప్యాక్లు ఉండవు; అందువల్ల
  ఆ భాషలకు `ultra` తీవ్రత `full` కంటే ఎక్కువ ప్రభావవంతంగా ఉండదు (అవి వాటి స్వంత నియమాలను
  మాత్రమే ఉపయోగిస్తాయి — విదేశీ టెక్స్ట్ను వికృతం చేసే ఆంగ్ల `dedup`/`ultra` నియమాలకు
  నిశ్శబ్ద ఫాల్బ్యాక్ ఉండదు). `en` / `es` / `id` / `pt-BR` పూర్తిగా ఉన్నాయి. పాక్షిక
  ప్యాక్ల కోసం `dedup.json` + `ultra.json` సహకారాలను స్వాగతిస్తున్నాము.
- **స్ట్యాక్డ్ టెలిమెట్రీ కుదింపును సాధించిన ఇంజిన్లను మాత్రమే జాబితా చేస్తుంది.** ఇంజిన్
  నడిచినా 0 % ఆదా మాత్రమే సాధించిన స్ట్యాక్డ్-పైప్లైన్ దశ `stats:null`ను తిరిగి ఇస్తుంది;
  అందువల్ల అది `engineBreakdown`లో కనిపించదు — దాటవేయబడిన దశతో దీన్ని వేరు చేసి
  గుర్తించలేము. "నడిచింది, 0 %" మరియు "దాటవేయబడింది" మధ్య తేడాను గుర్తించడానికి
  బ్రేక్డౌన్ మోడల్లో మార్పు అవసరం; అది వాయిదా వేయబడింది.
