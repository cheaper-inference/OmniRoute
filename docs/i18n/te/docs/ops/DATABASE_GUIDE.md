> **TL;DR**: OmniRoute తన ప్రాథమిక స్టోర్గా **WAL జర్నలింగ్తో SQLite**ని ఉపయోగిస్తుంది; సున్నితమైన ఫీల్డ్లకు నిల్వలో ఉన్నప్పుడు **AES-256-GCM** ఎన్క్రిప్షన్ను ఉపయోగిస్తుంది. ఈ గైడ్ స్కీమా, మైగ్రేషన్లు, బ్యాకప్/రికవరీ మరియు కార్యాచరణ రన్బుక్లను వివరిస్తుంది.

**మూలాలు:**

- `src/lib/db/core.ts` — సింగిల్టన్ + SCHEMA_SQL (17 ప్రాథమిక పట్టికలు)
- `src/lib/db/migrationRunner.ts` — వెర్షన్ చేయబడిన మైగ్రేషన్లు
- `src/lib/db/migrations/` — వెర్షన్ చేయబడిన 167 SQL ఫైళ్లు
- `src/lib/db/encryption.ts` — ఎన్క్రిప్షన్ సహాయకాలు
- `src/lib/db/backup.ts` — బ్యాకప్ ఎగుమతి/దిగుమతి
- `src/lib/db/healthCheck.ts` — స్థితి నిర్ధారణలు

## SQLite ఎందుకు?

అనేక కారణాల వల్ల OmniRoute, PostgreSQL/MySQLకు బదులుగా SQLiteని ఎంచుకుంది:

| అంశం                | SQLite                                 | PostgreSQL                            |
| ------------------- | -------------------------------------- | ------------------------------------- |
| **డిప్లాయ్మెంట్**   | ఎంబెడెడ్ — ప్రత్యేక సర్వర్ అవసరం లేదు  | సర్వర్ సెటప్ అవసరం                    |
| **ఎన్క్రిప్షన్**    | అప్లికేషన్-స్థాయి (AES-256-GCM)        | అంతర్నిర్మిత TDE                      |
| **పనితీరు**         | చిన్న/మధ్యస్థ పనిభారాలకు వేగవంతమైనది   | భారీ సమకాలీన రైట్లకు మెరుగైనది        |
| **సమకాలీనత**        | WAL మోడ్ సమకాలీన రీడ్లను అనుమతిస్తుంది | పూర్తి MVCC                           |
| **బ్యాకప్**         | ఒకే ఫైల్ కాపీ                          | `pg_dump` లేదా ఫైల్సిస్టమ్ స్నాప్షాట్ |
| **వినియోగ సందర్భం** | ఒక్కో వినియోగదారు ఇన్స్టాల్, ఎంబెడెడ్  | బహుళ-టెనెంట్ SaaS                     |

**ఒకే వినియోగదారు, ఒకే ఇన్స్టాన్స్** డిప్లాయ్మెంట్లకు (OmniRoute యొక్క ప్రధాన వినియోగ సందర్భం), SQLite మరింత సరళమైనది మరియు వేగవంతమైనది.

### WAL జర్నలింగ్

`core.ts` డేటాబేస్ను **WAL (Write-Ahead Logging) మోడ్**లో తెరుస్తుంది:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL, రైట్లు జరుగుతున్నప్పుడు **సమకాలీన రీడ్లను** అనుమతిస్తుంది — అభ్యర్థనలు రికార్డ్ అవుతున్న సమయంలో క్వెరీలు చేసే డ్యాష్బోర్డ్కు ఇది ముఖ్యమైనది.

డిఫాల్ట్ క్యాష్ పరిమాణం **65,536 KiB (64 MiB)**. SQLite ప్రతికూల
`cache_size`ను KiBలో సుమారు గరిష్ఠ పరిమితిగా పరిగణించి, అవసరానికి అనుగుణంగా పేజీలను కేటాయిస్తుంది.
**సెట్టింగ్లు > సిస్టమ్ & స్టోరేజ్ > క్యాష్ పరిమాణం** **1 నుండి
1,000,000 KiB** వరకు పూర్ణాంక విలువలను అంగీకరిస్తుంది; సెట్టింగ్ను సేవ్ చేయడం ద్వారా అది ప్రస్తుతం పనిచేస్తున్న డేటాబేస్ కనెక్షన్కు వర్తింపజేయబడుతుంది,
మరియు ప్రారంభ సమయంలో OmniRoute నిల్వ చేసిన విలువను పునరుద్ధరిస్తుంది.

## డేటాబేస్ స్థానం

SQLite ఫైల్ ఇక్కడ నిల్వ చేయబడుతుంది:

| OS      | పాత్                                                              |
| ------- | ----------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                     |
| macOS   | `~/.omniroute/storage.sqlite`                                     |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                         |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` ద్వారా కాన్ఫిగర్ చేయవచ్చు) |

అనుబంధ ఫైళ్లు:

- `storage.sqlite-wal` — రైట్-అహెడ్ లాగ్
- `storage.sqlite-shm` — షేర్డ్ మెమరీ ఫైల్
- `call_logs/` — అభ్యర్థన పేలోడ్ ఆర్టిఫాక్ట్లు (ప్రారంభించబడి ఉంటే)

**స్థానాన్ని ఓవర్రైడ్ చేయడం:**

```bash
DATA_DIR=/custom/path omniroute
```

### మాడ్యూల్ సరిహద్దులు

ఒక ప్రధాన ఆర్కిటెక్చరల్ నియమం: **మాడ్యూల్లు ఒకదాని పట్టికలను మరొకటి నేరుగా యాక్సెస్ చేయవు**. మరొక మాడ్యూల్ డేటాతో పని చేయడానికి, ఆ మాడ్యూల్ నుండి ఫంక్షన్ను దిగుమతి చేయండి.

```ts
// ❌ తప్పు: మరొక మాడ్యూల్ నుండి నేరుగా SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ సరైనది: providers మాడ్యూల్ ఫంక్షన్ను ఉపయోగించండి
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

ఈ నియమం కోడ్ సమీక్ష ద్వారా అమలు చేయబడుతుంది — ఎలాంటి స్థిర తనిఖీ లేదు, కానీ ఉల్లంఘనలు గుర్తించబడతాయి.

## వలసలు

OmniRoute ఉపయోగిస్తుంది** సంస్కరణ, అసంబద్ధమైన వలసలు** `src/lib/db/migrations/` లో. ప్రతి మైగ్రేషన్ ఒకే SQL ఫైల్. రెండు నామకరణ ఆకృతులు కలిసి ఉంటాయి; `_omniroute_migrations` లో నమోదు చేయబడిన సంస్కరణ సంఖ్యా ఉపసర్గ.

### వలస నామకరణం

| ఫార్మాట్                                          | ఉదాహరణ                               | కోసం ఉపయోగించబడింది                                                                                                                                                     |
| ------------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (ఖచ్చితంగా 3 అంకెలు)        | `241_seen_models.sql`                | పాత సిరీస్ `001`–`241`. టైమ్స్టాంప్ ఫార్మాట్ ల్యాండ్ అయినప్పుడు స్తంభింపజేయబడింది (`240` మరియు `241` దాని ముందు విలీనం చేయబడ్డాయి): కొత్త ఫైల్ ఏదీ క్రమ సంఖ్యను పొందదు. |
| `YYYYMMDDHHMMSS_description.sql` (14 అంకెలు, UTC) | `20261113120000_add_usage_index.sql` | 2026-11-13 నుండి సృష్టించబడిన ప్రతి వలస.                                                                                                                                |

ఎందుకు మార్పు: సీక్వెన్షియల్ నంబర్లతో, సమాంతర PRs అదే తదుపరి సంఖ్యను ఎంచుకుంది మరియు విలీనానికి ముందు ఒకటి తప్ప మిగతావన్నీ మళ్లీ నంబర్ను మార్చాలి. ఒక UTC టైమ్స్టాంప్ ప్రతి PR దాని స్వంత సంస్కరణను అందిస్తుంది.

టైమ్స్టాంప్ ఫార్మాట్ కోసం నియమాలు ( `npm run check:migration-numbering` ద్వారా అమలు చేయబడతాయి, `scripts/check/lib/migrationNaming.mjs` లో జనరేటర్తో భాగస్వామ్యం చేయబడ్డాయి):

- టైమ్స్టాంప్ నిజమైన UTC తేదీ మరియు సమయం, `20261113000000` కంటే ముందు కాదు మరియు భవిష్యత్తులో 10 నిమిషాల కంటే ఎక్కువ కాదు.
- వర్ణన చిన్న అక్షరం `snake_case` ఒక అక్షరంతో మొదలవుతుంది (`a-z`, `0-9`, పదాల మధ్య ఒకే `_` ), గరిష్టంగా 80 అక్షరాలు.
- ఒకే టైమ్స్టాంప్తో ఉన్న రెండు ఫైల్లు డూప్లికేట్.
- నో-గ్యాప్ నియమం పాత సిరీస్కు మాత్రమే వర్తిస్తుంది: తెలిసిన ఖాళీలు `026`, `055` మరియు `121` మినహా `001` నుండి `241` వరకు ప్రతి సంఖ్య తప్పనిసరిగా ఉండాలి. `241` (లేదా ఏదైనా పాత ఫైల్) తొలగించడం గేట్ విఫలమవుతుంది. `001` మరియు `241` ఎప్పటికీ `KNOWN_GAPS` అనుమతి జాబితాకు జోడించబడవు. టైమ్స్టాంప్ చేసిన ఫైల్లు ఎప్పుడూ గ్యాప్ని సృష్టించవు.
- `src/lib/db/migrations/` లోని ప్రతి ఎంట్రీ తప్పనిసరిగా చెల్లుబాటు అయ్యే చిన్న `.sql` పేరుతో ఒక సాధారణ ఫైల్ అయి ఉండాలి. డైరెక్టరీ, సిమ్లింక్, `.SQL` లేదా `.sql.bak` ఫైల్, దాచిన ఫైల్ లేదా ఖాళీ ఉన్న పేరు గేట్లో విఫలమవుతుంది, ఎందుకంటే రన్నర్ దాన్ని నిశ్శబ్దంగా దాటవేస్తుంది లేదా బూట్లో క్రాష్ అవుతుంది.

**ఆర్డర్ వర్తించు.** రన్నర్ ఉపసర్గ యొక్క సంఖ్యా విలువ ఆధారంగా క్రమబద్ధీకరిస్తాడు, వచనం ద్వారా కాకుండా: పాత `001`–`241` ఫైల్లు, తర్వాత టైమ్స్టాంప్ క్రమంలో టైమ్స్టాంప్ చేసిన ఫైల్లు, తర్వాత `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` ( `ee-001` వంటి వెర్షన్లు)తో రిజిస్టర్ చేయబడిన ఏవైనా నేమ్స్పేస్డ్ డైరెక్టరీలు. పెండింగ్లో ఉన్న మైగ్రేషన్ అనేది `_omniroute_migrations` లో లేని ఏదైనా ఫైల్, కాబట్టి పాత బ్రాంచ్ నుండి కొత్తది తర్వాత విలీనం అయిన మైగ్రేషన్ ఇప్పటికీ ఇప్పటికే ఉన్న డేటాబేస్లలో వర్తిస్తుంది.

**టైమ్స్టాంప్ సృష్టి క్రమం, విలీన క్రమం కాదు.** మీ మైగ్రేషన్ a తో మైగ్రేషన్ ద్వారా సృష్టించబడిన పట్టిక లేదా నిలువు వరుసపై ఆధారపడి ఉంటే** కొత్తది** టైమ్స్టాంప్ (ఉదాహరణకు, ముందుగా విలీనం చేసిన మరొక PR నుండి ఒకటి), తాజా డేటాబేస్ మొదట మీదే రన్ చేసి విఫలమవుతుంది. మీ PR ఇప్పటికీ తెరిచి ఉండగా, ఫైల్ పేరును `npm run db:new-migration` తో రీజెనరేట్ చేయండి, తద్వారా ఇది కొత్త టైమ్స్టాంప్ను పొందుతుంది లేదా స్వతంత్రంగా చేయండి. `npm run test:migrations:fresh` ప్రతి మైగ్రేషన్ని ఖాళీ డేటాబేస్కి వర్తింపజేస్తుంది మరియు దీన్ని క్యాచ్ చేస్తుంది.

### విలీనం చేయబడిన మైగ్రేషన్ ఎప్పటికీ తొలగించబడదు లేదా పేరు మార్చబడదు

ఒకసారి మైగ్రేషన్ ఫైల్ విడుదల శాఖ లేదా `main` లో ఉంటే, అది ఇప్పటికే హోమోలాగ్ మరియు డెవలపర్ డేటాబేస్లపై, VPS ఇన్స్టాల్లలో మరియు ఎంటర్ప్రైజ్ సింక్లో రన్ అవుతుంది. అప్పటి నుండి:

- **దాన్ని ఎప్పటికీ తొలగించవద్దు.** అప్గ్రేడ్ చేసిన డేటాబేస్లు దానిని ఉంచేటప్పుడు తాజా ఇన్స్టాల్లు దాని స్కీమాను కోల్పోతాయి.
- **పేరు మార్చవద్దు.** `_omniroute_migrations` లోని సంస్కరణ ఇకపై ఫైల్తో సరిపోలడం లేదు, కనుక ఇది ఇప్పటికే వర్తింపజేసిన ప్రతి డేటాబేస్ దాన్ని మళ్లీ అమలు చేస్తుంది. నాన్-ఐడెంపోటెంట్ SQL తర్వాత డేటాను నకిలీ చేస్తుంది లేదా బూట్ను ఆపివేస్తుంది.
- **వేరే స్కీమా కావాలా?** `npm run db:new-migration` తో కొత్త మైగ్రేషన్ని సృష్టించండి.

పేరు మార్చడం అనేది ఇంకా విలీనం చేయని ఫైల్కు మాత్రమే సురక్షితమైనది, ఇది గేట్ యొక్క సూచనలను సూచిస్తుంది. విడుదల ట్యాగ్ ఇక్కడ ఏమీ మారదు: `release/v*` బ్రాంచ్కి ప్రతి పుష్ Docker `:next` ఇమేజ్ను ప్రచురిస్తుంది మరియు హోమోలాగ్, VPS ఇన్స్టాల్లు మరియు ఎంటర్ప్రైజ్ సింక్పై రన్ అవుతుంది, కాబట్టి ఏదైనా `vX.Y.Z` ట్యాగ్ ఉనికిలో ఉండకముందే విలీనమైన మైగ్రేషన్ నిజమైన డేటాబేస్లపై అమలు చేయబడుతుంది. ట్యాగ్ చేయబడినా లేదా బేస్ ఫైల్ యొక్క ప్రతి తొలగింపులో గేట్ విఫలమవుతుంది.

- **విలీన మైగ్రేషన్ను తిరిగి మార్చడం.** ఫైల్ను తొలగించే `git revert` గేట్లో విఫలమవుతుంది. ఫైల్ని ఉంచి, దాని స్కీమాను కొత్త మైగ్రేషన్లో అన్డు చేయండి: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` మరియు మొదలైన వాటితో. అప్గ్రేడ్ చేయబడిన మరియు తాజా డేటాబేస్లు అదే స్కీమాతో ముగుస్తాయి.
- **ఆమోదించబడిన పేరు పేరు: అనుకూలత నమోదు మరియు ఒకేలాంటి కంటెంట్.** విలీనమైన ఫైల్ తప్పనిసరిగా తరలించబడితే (ఉదాహరణకు, రెండు విలీనమైన ఫైల్లు టైమ్స్టాంప్ను పంచుకుంటాయి మరియు రన్నర్ వెర్షన్ తాకిడితో ఆపివేసినట్లయితే), దాని SQL తాకకుండా తర్వాత దాని పేరు మార్చండి మరియు `src/lib/db/migrationRunner/constants.ts` లో `RENAMED_MIGRATION_COMPATIBILITY` కి `{ fromVersion, fromName, toVersion, toName }` జోడించండి. పాత సంస్కరణను వర్తింపజేసిన డేటాబేస్లు ఫైల్ను మళ్లీ అమలు చేయడానికి బదులుగా వాటి `_omniroute_migrations` వరుసను తరలించబడతాయి. గేట్ అటువంటి పేరు మార్చడం గురించి హెచ్చరిస్తుంది మరియు కొత్త టైమ్స్టాంప్ ఏమైనప్పటికీ దానిపై కమ్యుటేషన్ తనిఖీని ఎల్లప్పుడూ అమలు చేస్తుంది: తాజా ఇన్స్టాల్లు ఫైల్ను దాని కొత్త స్థానంలో వర్తింపజేయడం, అప్గ్రేడ్ చేసిన డేటాబేస్లు చేయవు, కాబట్టి పాతదానికి సమీపంలో కొత్త టైమ్స్టాంప్ని ఎంచుకోండి. కంటెంట్ మారితే (కొత్త మైగ్రేషన్లో స్కీమా మార్పు జరిగితే) లేదా ఎంట్రీ టార్గెట్ ఫైల్ డిస్క్లో లేకుంటే గేట్ పేరు మార్చడంలో విఫలమవుతుంది.
- **ఒకే టైమ్స్టాంప్లో పేరు మార్చవద్దు.** టైమ్స్టాంప్ను ఉంచి, వివరణను మాత్రమే మార్చే పేరుమార్పు ప్రవేశంతో లేదా లేకుండా గేట్ను విఫలమవుతుంది. `toVersion` దాని `fromVersion` కి సమానమైన ఎంట్రీతో, రన్నర్ పాత `_omniroute_migrations` అడ్డు వరుసను తొలగిస్తుంది మరియు ఫైల్ను ఇప్పటికే అమలు చేసిన ప్రతి డేటాబేస్లో మళ్లీ వర్తింపజేస్తుంది. ఎంట్రీ లేకుండా, రన్నర్ సంస్కరణను మాత్రమే ట్రాక్ చేస్తుంది: ఇది ఆ డేటాబేస్లలోని ఫైల్ను దాటవేస్తుంది (కొత్త కంటెంట్ ఎప్పుడూ అక్కడ అమలు చేయబడదు) మరియు ప్రతి బూట్లో రీనంబరింగ్ లోపాన్ని లాగ్ చేస్తుంది. మరొక టైమ్స్టాంప్తో పాటు అనుకూలత ఎంట్రీని ఉపయోగించండి లేదా పేరును ఉంచండి.
- **పేరు మార్చబడిన ఫైల్ మళ్లీ రన్ కాలేదని గేట్ తనిఖీ చేస్తుంది.** కవర్ చేయబడిన ప్రతి పేరుమార్పు కోసం, గేట్ కొత్త ఫైల్ పేరును `--must-not-apply` తో కమ్యుటేషన్ చెక్కి పంపుతుంది. చెక్ అప్గ్రేడ్ చేసిన డేటాబేస్ను నిజమైన రన్నర్తో బూట్ చేస్తుంది మరియు రన్నర్ ఆ ఫైల్ను మళ్లీ వర్తింపజేస్తే (ఉదాహరణకు, ఎంట్రీకి తప్పు వెర్షన్ లేదా పేరు ఉన్నందున లేదా గేట్ యొక్క టెక్స్ట్ పార్సర్ TypeScript నుండి భిన్నంగా `constants.ts` చదివినందున), గేట్ `migration renomeada rodaria de novo` తో విఫలమై, ఎంట్రీ యొక్క పాత మరియు కొత్త వెర్షన్లను తనిఖీ చేయమని అడుగుతుంది.

### గేట్ బేస్కు వ్యతిరేకంగా ఏమి తనిఖీ చేస్తుంది

పుల్ అభ్యర్థన మరియు విలీనం-క్యూ పరుగులపై, `npm run check:migration-numbering` బేస్ బ్రాంచ్లోని అదే డైరెక్టరీతో డిస్క్లోని `src/lib/db/migrations/` పోలుస్తుంది. ఆధారం, ఈ క్రమంలో: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` వేరియబుల్, లేదా, `GITHUB_EVENT_NAME` `pull_request` అయినప్పుడు , `pull_request_target` లేదా `merge_group`, విలీన కమిట్ యొక్క మొదటి పేరెంట్, ఈవెంట్ పేలోడ్ యొక్క `merge_group.base_sha` లేదా `git merge-base HEAD origin/$GITHUB_BASE_REF`. పుల్ రిక్వెస్ట్ లేదా మెర్జ్-క్యూ రన్లో పరిష్కరించదగిన బేస్ లేకుండా గేట్ విఫలమవుతుంది. `--base` లేకుండా CI వెలుపల ఇది `comparação com a base: pulada (sem --base)` ప్రింట్ చేస్తుంది మరియు ఈ నియమాలను దాటవేస్తుంది.

`--base-latest-tag` సరికొత్త విడుదల ట్యాగ్తో పోలుస్తుంది (సెమ్వర్ క్రమంలో`vX.Y.Z` ; నైట్లీస్ వంటి ప్రత్యయం ట్యాగ్లు లెక్కించబడవు) ఇది `HEAD` చరిత్రలో `--base` వలె అదే నిబంధనలతో ఉంటుంది. విడుదల-ఆకుపచ్చ (`scripts/quality/validate-release-green.mjs`) గేట్ను ఈ విధంగా నడుపుతుంది, ఎందుకంటే పుష్ మరియు షెడ్యూల్ చేసిన పరుగులకు పుల్ అభ్యర్థన బేస్ ఉండదు మరియు తాజా CI రన్ లేకుండా విలీనం చేయవచ్చు. చరిత్రలో విడుదల ట్యాగ్ లేకుండా గేట్ విఫలమైంది; `git fetch --tags` అమలు చేయండి ( CI లో, `actions/checkout` తో `fetch-depth: 0` ట్యాగ్లను తెస్తుంది).

కమ్యుటేషన్ చెక్ యొక్క ఒక పరుగు అవుట్-ఆఫ్-ఆర్డర్, ఎడిట్ చేయబడిన మరియు పేరు మార్చబడిన ఫైల్లను కలిపి కవర్ చేస్తుంది.

కమ్యుటేషన్ చెక్ (`scripts/check/migration-commutation.ts`) నిజమైన ఇన్స్టాల్ పాత్తో రెండు తాత్కాలిక డేటాబేస్లను నిర్మిస్తుంది: ఒక** అప్గ్రేడ్ చేయబడింది** ఒకటి (బేస్ మైగ్రేషన్లతో బూట్ చేయండి, ఆపై పుల్ రిక్వెస్ట్ మైగ్రేషన్లతో అదే ఫైల్లో మళ్లీ బూట్ చేయండి) మరియు a** తాజా** ఒకటి (పుల్ రిక్వెస్ట్ మైగ్రేషన్లతో ఒక బూట్). ఇది ఫలిత స్కీమాలను పోలుస్తుంది: పట్టికలు మరియు నిలువు వరుసలు (కాలమ్ క్రమాన్ని విస్మరించడం), UNIQUE / PRIMARY KEY మరియు FOREIGN KEY పరిమితులు, ప్రతి పట్టిక యొక్క సాధారణీకరించిన `CREATE TABLE` వచనం (ఇది CHECK పరిమితులు, సంకలనాలు, రూపొందించబడిన నిలువు వరుసలు మరియు పట్టిక ఎంపికలను కవర్ చేస్తుంది), సూచికలు, ట్రిగ్గర్లు మరియు వీక్షణలు. వరుస డేటా పోల్చబడలేదు. అవి సరిపోలితే, ఫైల్ ఆర్డర్లో లేదని గేట్ ప్రింట్ చేస్తుంది కానీ ప్రయాణిస్తుంది మరియు పాస్ అవుతుంది. అవి విభేదిస్తే, గేట్ తేడాతో విఫలమవుతుంది మరియు కేసు కోసం సూచన: అవుట్-ఆఫ్-ఆర్డర్ ఫైల్ కోసం, దాని పేరును `npm run db:new-migration` తో పునరుత్పత్తి చేయండి, ఫైల్ ఇంకా విలీనం కానందున ఇది సురక్షితం; సవరించిన బేస్ ఫైల్ కోసం, బేస్ కంటెంట్ను పునరుద్ధరించండి మరియు మార్పును కొత్త మైగ్రేషన్లో ఉంచండి; పేరు మార్చబడిన ఫైల్ కోసం, పేరు మార్చడాన్ని రద్దు చేయండి లేదా అది ప్రయాణించే చోట మరొక కొత్త టైమ్స్టాంప్ను ఎంచుకోండి, మరొక పేరుతో ఎప్పుడూ ఒకే టైమ్స్టాంప్ చేయవద్దు. చెక్ రన్ చేయలేకపోతే, గేట్ CI లో విఫలమవుతుంది మరియు స్థానికంగా మాత్రమే హెచ్చరిస్తుంది. సవరించిన బేస్ ఫైల్ కోసం, అప్గ్రేడ్ చేయబడిన డేటాబేస్ ఆ ఫైల్ యొక్క బేస్ కంటెంట్తో నిర్మించబడింది మరియు రెండవ బూట్ దానిని దాటవేస్తుంది ఎందుకంటే దాని వెర్షన్ ఇప్పటికే రికార్డ్ చేయబడింది. పేరు మార్చబడిన ఫైల్ కోసం, అప్గ్రేడ్ చేయబడిన డేటాబేస్ దాని పాత పేరుతో ఫైల్తో నిర్మించబడింది మరియు రెండవ బూట్ దాని `_omniroute_migrations` వరుసను మళ్లీ అమలు చేయడానికి బదులుగా అనుకూలత నమోదు ద్వారా కదిలిస్తుంది; గేట్ కొత్త పేరును `--must-not-apply` తో పంపుతుంది, కాబట్టి రెండవ బూట్ దానిని వర్తింపజేస్తే చెక్ విఫలమవుతుంది. అప్గ్రేడ్ చేసిన మార్గంలో పుల్ రిక్వెస్ట్ మైగ్రేషన్ దరఖాస్తు చేయడంలో విఫలమైతే, అంటే, ప్రతి బేస్ మైగ్రేషన్ తర్వాత (తాజా ఇన్స్టాల్లో కూడా విఫలమైనా లేదా), గేట్ `migration do PR não aplica` నివేదిస్తుంది మరియు బేస్ యొక్క ప్రస్తుత స్కీమాకు వ్యతిరేకంగా SQL సరిచేయమని మిమ్మల్ని అడుగుతుంది; ఫైల్ తర్వాతి టైమ్స్టాంప్తో మరొక పుల్ అభ్యర్థన మైగ్రేషన్పై ఆధారపడి ఉంటే, దాని పేరును `npm run db:new-migration` తో మళ్లీ రూపొందించండి.

అదే పోలికను స్థానికంగా అమలు చేయడానికి, బేస్ను స్పష్టంగా పాస్ చేయండి, ఉదాహరణకు `npm run check:migration-numbering -- --base origin/<base-branch>`, లేదా `npm run check:migration-numbering -- --base-latest-tag` తాజా విడుదలతో పోల్చడానికి.

### ఓపెన్ PR యొక్క `NNN` మైగ్రేషన్ని మారుస్తోంది

స్విచ్కి ముందు తెరిచిన పుల్ అభ్యర్థన ఇప్పటికీ `242_add_widgets.sql` వంటి సీక్వెన్షియల్ ఫైల్ను కలిగి ఉండవచ్చు. `241` పైన ఉన్న పాత సంఖ్యలు తిరస్కరించబడ్డాయి, కాబట్టి విలీనం చేసే ముందు దానిని మార్చండి:

1. **వివరణను ఉంచుతూ, జెనరేటర్తో ఫైల్ పేరు మార్చండి.** కొత్త పేరును పొందడానికి `npm run db:new-migration -- <same description>` అమలు చేయండి, SQL ని దానిలోకి తరలించండి మరియు పాత `NNN_` ఫైల్ను తొలగించండి. వివరణ తప్పనిసరిగా ఒకేలా ఉండాలి: దిగువన ఉన్న అనుకూలత నమోదు దానికి సరిపోలుతుంది.
2. **స్థిరమైన డేటాబేస్ పాత నంబర్ను అమలు చేస్తే అనుకూలత నమోదును జోడించండి.** ఉంచబడిన ఏదైనా డేటాబేస్ (హోమోలాగ్, ఒక VPS, కంట్రిబ్యూటర్ స్వంత ఇన్స్టాల్) `NNN_` ఫైల్తో PR బిల్డ్ను అమలు చేస్తే, `src/lib/db/migrationRunner/constants.ts` లో `RENAMED_MIGRATION_COMPATIBILITY` కి `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` జోడించండి. ఇది** `237` నుండి `241` వరకు అవసరం** : ఆ స్లాట్లు ఇప్పుడు కానానికల్ `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` మరియు `241_seen_models.sql` లను కలిగి ఉంటాయి మరియు నమోదు లేకుండా అటువంటి డేటాబేస్ కానానికల్ మైగ్రేషన్ను శాశ్వతంగా దాటవేస్తుంది మరియు మార్చబడిన దాన్ని మళ్లీ అమలు చేస్తుంది. గమ్యం టైమ్స్టాంప్ అయినప్పుడు `242` వంటి ఖాళీగా ఉండే స్లాట్ కోసం కూడా ఇది పని చేస్తుంది. సందేహం ఉంటే, ఎంట్రీని జోడించండి. మీరు దానిని శ్రేణిలో ఎక్కడ జోడించినా పట్టింపు లేదు: ఒక ఎంట్రీ యొక్క లక్ష్య స్లాట్లో మరొక ఎంట్రీ దూరంగా ఉన్న అడ్డు వరుసను కలిగి ఉన్నప్పుడు (ఉదాహరణకు `237` PR వరుసను పట్టుకున్నప్పుడు పాత `usage_history_calculated_cost` వరుస `237` లోకి వెళ్లడానికి వేచి ఉన్నప్పుడు), రన్నర్ ఆ ఎంట్రీని స్లాట్ ఖాళీ అయ్యే వరకు వేచి ఉండటానికి అనుమతిస్తుంది. ఒక వరుస నో ఎంట్రీ మూవ్లు లేదా స్లాట్లను మార్చుకునే రెండు ఎంట్రీలు కలిగి ఉన్న స్లాట్ వంటి నిజమైన వైరుధ్యం మాత్రమే `Cannot reconcile ...` తో బూట్ను ఆపివేస్తుంది.
3. **SQL నిరాడంబరంగా ఉంచండి** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), ఎందుకంటే మార్చబడిన మైగ్రేషన్ దాని స్కీమా ఇప్పటికే ఉన్న డేటాబేస్ను కలుసుకోవచ్చు.
4. **వెర్షన్-కీడ్ ప్రత్యేక కేసులను తరలించండి.** PR దాని పాత సంఖ్యకు `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) లేదా `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`)లో కేస్ను జోడించినట్లయితే, కీని కొత్త టైమ్స్టాంప్కి మార్చండి.

`tests/unit/db/codex-fence-migration-rename.test.ts` అనేది పేరు మార్చబడిన వలస కోసం ఒక పరీక్ష యొక్క పని ఉదాహరణ.

### స్విచ్కు ముందు బ్రాంచ్లకు బ్యాక్పోర్ట్లు

`YYYYMMDDHHMMSS_` ఫైల్ను స్విచ్కు ముందు ఉన్న బ్రాంచ్కి ఎప్పుడూ చెర్రీ-పిక్ లేదా బ్యాక్పోర్ట్ చేయవద్దు (ఉదాహరణకు పాత `release/v*` బ్రాంచ్). అక్కడ ఉన్న రన్నర్ ఫైల్ పేర్లను టెక్స్ట్గా క్రమబద్ధీకరిస్తాడు, కాబట్టి టైమ్స్టాంప్ చేయబడిన ఫైల్ తాజా డేటాబేస్లో `201_` మరియు `202_` మధ్య నడుస్తుంది మరియు అక్కడ ఉన్న పాత గేట్ 14-అంకెల ఉపసర్గలను అర్థం చేసుకోదు. అటువంటి బ్రాంచ్లో, మార్పును ఆ శాఖ యొక్క స్వంత తదుపరి `NNN_` ఫైల్, ఐడెమ్పోటెంట్గా వ్రాయండి, కాబట్టి టైమ్స్టాంప్ చేసిన వెర్షన్ తర్వాత వచ్చినప్పుడు ఇది నో-ఆప్.

### వలసలు ఎలా నడుస్తాయి

ప్రారంభంలో, `migrationRunner.ts`:

1. లేనట్లయితే `_omniroute_migrations` పట్టికను సృష్టిస్తుంది
2. ఇప్పటికే దరఖాస్తు చేసిన వలసల కోసం ప్రశ్నలు
3. ఏదైనా కొత్త మైగ్రేషన్లను క్రమంలో వర్తింపజేస్తుంది, ఒక్కొక్కటి లావాదేవీలో
4. ప్రతి దరఖాస్తు మైగ్రేషన్ను టైమ్స్టాంప్తో రికార్డ్ చేస్తుంది

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### చిత్తశుద్ధి

వలసలు ఉండాలి** బుద్ధిహీనుడు** — వాటిని రెండుసార్లు అమలు చేయడం నో-ఆప్ అయి ఉండాలి:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, మరియు `OR IGNORE` / `OR REPLACE` నిబంధనలను ఉదారంగా ఉపయోగించండి.

### కొత్త మైగ్రేషన్ని జోడిస్తోంది

1. **జెనరేటర్తో ఫైల్ను సృష్టించండి** : `npm run db:new-migration -- <description>` (ఉదాహరణకు `npm run db:new-migration -- add combo priority`). ఇది ప్రస్తుత UTC సమయం మరియు వ్యాఖ్య హెడర్తో `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` వ్రాస్తుంది, ఆ టైమ్స్టాంప్ తీసుకుంటే ఒక సెకను ముందుకు కదులుతుంది మరియు ఫైల్ను ఎప్పుడూ ఓవర్రైట్ చేయదు. చేతితో సంఖ్యను ఎంచుకోవద్దు.
2. **సురక్షిత DDL ఉపయోగించండి** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **డేటాను జాగ్రత్తగా పూరించండి** : ఇప్పటికే ఉన్న అడ్డు వరుసలను నిర్వహించడానికి `UPDATE ... WHERE ...` ఉపయోగించండి
4. **ఆర్డర్ మరియు పేరు పెట్టడాన్ని తనిఖీ చేయండి** : `npm run test:migrations:fresh` (ఖాళీ డేటాబేస్లోని అన్ని మైగ్రేషన్లు) మరియు `npm run check:migration-numbering`
5. **కాపీపై పరీక్షించండి** : ఉత్పత్తిపై ఎన్నడూ పరీక్షించని వలసలను అమలు చేయవద్దు
6. **కోడ్ నుండి సృష్టించబడిన టేబుల్కి మైగ్రేషన్ కూడా అవసరం** : ఒక మాడ్యూల్ కూడా పట్టికను బద్ధకంగా సృష్టిస్తే (`CREATE TABLE IF NOT EXISTS`, స్వీయ-స్వస్థత మార్గంగా ఉంచబడుతుంది), ఒక వలస దానిని అదే DDL తో సృష్టించాలి. లేకపోతే క్లీన్ ఇన్స్టాల్ మరియు అప్గ్రేడ్ చేసిన ఇన్స్టాల్ ఆ కోడ్ పాత్ నడుస్తుందా అనేదానిపై ఆధారపడి వివిధ స్కీమాలతో ముగుస్తుంది. `tests/unit/db/lazy-table-migration-guard.test.ts` `src/` మరియు `open-sse/` స్కాన్ చేస్తుంది మరియు మైగ్రేషన్ (#20557) లేకుండా లేజీ `CREATE` లో విఫలమవుతుంది. ఉదాహరణ: `src/lib/db/migrations/20261118120853_compression_run_telemetry.sql`.

ఉదాహరణ:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **వెనుకకు-అనుకూలమైన మార్పులు** (ఉదా, నిలువు వరుసలను వదలడం) గమ్మత్తైనవి. OmniRoute NOT మద్దతునిస్తుంది — డౌన్గ్రేడ్ ఒకసారి మైగ్రేషన్ వర్తించబడుతుంది, స్కీమా మార్పు శాశ్వతంగా ఉంటుంది. తదనుగుణంగా ప్లాన్ చేయండి.

## నిల్వలో ఉన్నప్పుడు ఎన్క్రిప్షన్

సున్నితమైన ఫీల్డ్లు (API కీలు, OAuth టోకెన్లు, కనెక్షన్ స్ట్రింగ్లు) నిల్వలో ఉన్నప్పుడు **AES-256-GCM** ఉపయోగించి ఎన్క్రిప్ట్ చేయబడతాయి.

### ఇది ఎలా పనిచేస్తుంది

```ts
// src/lib/db/encryption.ts (సరళీకరించబడింది)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### ఇది ఎక్కడ ఉపయోగించబడుతుంది

- `provider_connections.api_key` — అప్లికేషన్ స్థాయిలో ఎన్క్రిప్ట్ చేయబడుతుంది
- `provider_connections.access_token`, `refresh_token`, `id_token` — అప్లికేషన్ స్థాయిలో ఎన్క్రిప్ట్ చేయబడతాయి
- `namespace = "secrets"` కలిగిన `key_value` ఎంట్రీలు — అప్లికేషన్ స్థాయిలో ఎన్క్రిప్ట్ చేయబడతాయి
- `proxy_registry.auth` — ఉన్నట్లయితే, అప్లికేషన్ స్థాయిలో ఎన్క్రిప్ట్ చేయబడుతుంది

### ఎన్క్రిప్షన్ కీ

ఎన్క్రిప్షన్ కీ ఒక **పాస్ఫ్రేజ్** (`STORAGE_ENCRYPTION_KEY` ఎన్విరాన్మెంట్ వేరియబుల్ ద్వారా సెట్ చేయబడుతుంది) మరియు ఒక **సాల్ట్** (DBలో నిల్వ చేయబడుతుంది) నుండి ఉత్పన్నమవుతుంది. డేటాను డీక్రిప్ట్ చేయడానికి రెండూ అవసరం.

```bash
# సురక్షితమైన పాస్ఫ్రేజ్ను రూపొందించండి
openssl rand -hex 32

# .envలో సెట్ చేయండి
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **అత్యంత కీలకం**: ఎన్క్రిప్షన్ కీని కోల్పోవడం అంటే ఎన్క్రిప్ట్ చేసిన మొత్తం డేటాకు ప్రాప్యతను కోల్పోవడం. **కీని డేటాబేస్కు వేరుగా బ్యాకప్ చేయండి**.

### ఎన్క్రిప్ట్ చేయనివి

పనితీరు కారణాల వల్ల, కిందివి ప్లెయిన్టెక్స్ట్లో నిల్వ చేయబడతాయి:

- ప్రొవైడర్ ప్రదర్శన పేర్లు
- మోడల్ నిర్వచనాలు (ఇప్పటికే పబ్లిక్గా ఉన్నవి)
- రూటింగ్ నియమాలు
- వినియోగ రికార్డ్లు (PII లేదు)

ప్రతి 30 సెకన్లకు (డిఫాల్ట్) అమలయ్యే బ్యాక్గ్రౌండ్ జాబ్ ద్వారా షెడ్యూల్ సర్వర్ వైపు అమలు చేయబడుతుంది మరియు స్థానిక సర్వర్ సమయానికి అనుగుణంగా cron ఎక్స్ప్రెషన్ను మూల్యాంకనం చేస్తుంది.

| వేరియబుల్                                   | డిఫాల్ట్ | వివరణ                                                                                                              |
| ------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------ |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`  | msలో టిక్ విరామం (కనిష్ఠం `5000`). సరిపోలే cron నిమిషం లోపల విశ్వసనీయంగా అమలవడానికి ఇది 60 s కంటే తక్కువగా ఉండాలి. |

### SQLite హాట్ బ్యాకప్

లైవ్ DBకి జీరో-డౌన్టైమ్ బ్యాకప్ తీసుకోవడానికి:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".backup /backups/omniroute-hot.db"
```

ఇది SQLite యొక్క ఆన్లైన్ బ్యాకప్ APIని ఉపయోగిస్తుంది — OmniRoute అమలవుతున్నప్పుడు కూడా దీన్ని సురక్షితంగా అమలు చేయవచ్చు.

## పనితీరు ట్యూనింగ్

### WAL మోడ్

WAL డిఫాల్ట్గా ప్రారంభించబడింది. అధిక-వ్రాత పనిభారం కోసం, పరిగణించండి:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` సెట్ చేయలేదు. చెక్పాయింట్ WAL ఫ్రేమ్లను ప్రధాన ఫైల్లోకి తరలిస్తుంది, అయితే WAL ఫైల్ దాని అతిపెద్ద కేటాయించిన పరిమాణాన్ని ఉంచుతుంది. `OMNIROUTE_WAL_GUARD_MAX_MB` గార్డ్ `wal_checkpoint(RESTART)` మాత్రమే హెచ్చరిస్తుంది మరియు అమలు చేస్తుంది; అది డిస్క్-సైజ్ క్యాప్ కాదు.

### సూచికలు

పనితీరు కోసం కీలక సూచికలు (మైగ్రేషన్ల ద్వారా స్వయంచాలకంగా సృష్టించబడినవి):

- ప్రొవైడర్ ద్వారా`idx_models_provider` — మోడల్ లుకప్లు
- `idx_combo_targets_combo_id` — కాంబో లక్ష్య విస్తరణ
- `idx_usage_history_api_key_timestamp` — వినియోగ విశ్లేషణలు
- `idx_quota_snapshots_api_key_window` — కోటా ట్రాకింగ్
- `idx_call_logs_timestamp` — కాల్ లాగ్ ప్రశ్నలు

కొత్త సూచికను జోడించడానికి, మైగ్రేషన్ని సృష్టించండి:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### మెమరీ-మ్యాప్డ్ I/O

చాలా పెద్ద డేటాబేస్ల కోసం (> 10GB), మెమరీ మ్యాపింగ్ను SQLite ప్రాగ్మా ద్వారా సర్దుబాటు చేయవచ్చు:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### సంపీడనం

దీర్ఘకాలిక OmniRoute సందర్భాలు అప్పుడప్పుడు `VACUUM` నుండి ప్రయోజనం పొందుతాయి:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

తక్కువ ట్రాఫిక్ విండోస్ సమయంలో నెలవారీ అమలు చేయండి. (WAL మోడ్ అవసరాన్ని తగ్గిస్తుంది, కానీ దానిని తొలగించదు.)

## హెల్త్ చెక్

`src/lib/db/healthCheck.ts` **DB-స్థాయి హెల్త్ డయాగ్నస్టిక్స్**ను అందిస్తుంది:

రెండు HTTP verbsకూ ప్రామాణీకరణ అవసరం (లేకపోతే `401`). `GET` కేవలం నిర్ధారణ చేస్తుంది; `POST` అదే తనిఖీని `autoRepair` ప్రారంభించి అమలు చేస్తుంది.

```bash
GET  /api/db/health   # నిర్ధారించండి
POST /api/db/health   # నిర్ధారించండి + మరమ్మతు చేయండి
```

ప్రతిస్పందనగా `runDbHealthCheck()` రూపొందించిన `DbHealthCheckResult`
(`src/lib/db/healthCheck.ts`) వస్తుంది:

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "ఇకపై ఉనికిలో లేని API కీలను డొమైన్ బడ్జెట్లు సూచించాయి.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| ఫీల్డ్            | అర్థం                                                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `isHealthy`       | `issues` ఖాళీగా ఉన్నప్పుడు `true`. `driver` దీనిని ఎన్నడూ ప్రభావితం చేయదు.                                                                       |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state`లలో ఒకటి.                                                         |
| `repairedCount`   | ఈ అమలు సమయంలో మరమ్మతు చేసిన వరుసలు; `autoRepair` falseగా ఉన్నప్పుడు ఎల్లప్పుడూ `0`.                                                              |
| `backupCreated`   | మరమ్మతు చేయడానికి ముందు బ్యాకప్ తీసుకున్నారా లేదా.                                                                                               |
| `checkedAt`       | అమలుతోనూ, అది రాసే ఏదైనా మరమ్మతు నోట్తోనూ పంచుకోబడే ISO టైమ్స్టాంప్.                                                                             |
| `driver.name`     | తనిఖీ చేసిన డేటాబేస్కు సేవలందిస్తున్న SQLite డ్రైవర్.                                                                                            |
| `driver.degraded` | రైట్లు డేటాబేస్ ఫైల్ ద్వారా మన్నికగా బ్యాకప్ చేయబడనప్పుడు `true` — `sql.js` WASM ఫాల్బ్యాక్ (మొత్తం-ఫైల్ పర్సిస్టెన్స్) లేదా ఇన్-మెమరీ డేటాబేస్. |

ఇదే పేలోడ్ `omniroute_db_health_check` MCP టూల్ ద్వారా కూడా తిరిగి ఇవ్వబడుతుంది.

కరప్షన్ను గుర్తించడానికి `PRAGMA integrity_check` అమలు చేయండి:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# ఇలా ప్రింట్ కావాలి: ok
```

ఇది `ok` కాకుండా మరేదైనా తిరిగి ఇస్తే, **వెంటనే డేటాబేస్ను ఉపయోగించడం ఆపివేసి**, బ్యాకప్ నుండి పునరుద్ధరించండి.

## విపత్తు పునరుద్ధరణ

### సందర్భం 1: WAL ఫైల్ కోల్పోయినప్పుడు

`-wal` ఫైల్ కనిపించడం లేదు, కానీ `-shm` మరియు ప్రధాన DB చెక్కుచెదరకుండా ఉన్నాయి:

```bash
# తదుపరిసారి తెరిచినప్పుడు స్వయంచాలకంగా పునరుద్ధరిస్తుంది
omniroute
```

SQLite స్వయంచాలకంగా పునరుద్ధరించలేకపోతే:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### సందర్భం 2: ప్రధాన DB ఫైల్ దెబ్బతిన్నప్పుడు

బ్యాకప్ నుండి పునరుద్ధరించండి:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` అమలులో ఉన్న సర్వర్ నుండి పూర్తి `.tar.gz` ఆర్కైవ్ను మాత్రమే డౌన్లోడ్ చేస్తుంది
(`GET /api/db-backups/exportAll`, ఆపరేటర్ క్రెడెన్షియల్ అవసరం); ఇది దేనినీ పునరుద్ధరించదు.

### సందర్భం 3: ఎన్క్రిప్షన్ కీ కోల్పోయినప్పుడు

కీ లేకుండా **పునరుద్ధరణ సాధ్యం కాదు**. ఎన్క్రిప్ట్ చేసిన ఫీల్డ్లను చదవడం సాధ్యం కాదు. కొత్త క్రెడెన్షియల్లతో అన్ని ప్రొవైడర్లను మాన్యువల్గా మళ్లీ జోడించండి.

> **నష్టనివారణ**: ఎన్క్రిప్షన్ కీని ఎల్లప్పుడూ విడిగా బ్యాకప్ చేయండి, వీలైతే పాస్వర్డ్ మేనేజర్ లేదా KMSలో భద్రపరచండి.

### సందర్భం 4: డిస్క్ నిండినప్పుడు

SQLite `SQLITE_FULL` లోపాలను అందిస్తుంది. డిస్క్ స్థలాన్ని ఖాళీ చేసి, ఆపై:

```bash
# స్థలాన్ని ఖాళీ చేయడానికి WALను చెక్పాయింట్ చేయండి
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## సమస్య పరిష్కారం

### "డేటాబేస్ లాక్ చేయబడింది"

మరొక ప్రాసెస్ రైట్ లాక్ను కలిగి ఉంది. కింది వాటిలో ఏదో ఒకటి చేయండి:

- ఇతర ప్రాసెస్ పూర్తయ్యే వరకు వేచి ఉండండి (`lsof | grep storage.sqlite`తో తనిఖీ చేయండి)
- ఇతర ప్రాసెస్ను నిలిపివేయండి
- సమస్య కొనసాగితే, OmniRouteను పునఃప్రారంభించండి

### "ఫారిన్ కీ పరిమితి విఫలమైంది"

ఒక డొమైన్ మాడ్యూల్ రెఫరెన్షియల్ ఇంటెగ్రిటీని ఉల్లంఘిస్తోంది. వీటిని తనిఖీ చేయండి:

- ఆధారిత పట్టికలలో అనుబంధం లేని వరుసలు
- వ్యాప్తి చెందని క్యాస్కేడింగ్ తొలగింపులు
- ఫారిన్ కీని మార్చిన ఇటీవలి మైగ్రేషన్

ఉల్లంఘనలను కనుగొనడానికి `PRAGMA foreign_key_check;`ను అమలు చేయండి.

### "మెమరీ అయిపోయింది"

SQLite యొక్క మెమరీ-మ్యాప్డ్ I/O, OS పరిమితిని మించుతోంది. SQLite pragma ద్వారా తగ్గించండి:

```sql
PRAGMA mmap_size = 134217728;  -- 256MBకు బదులుగా 128MB
```

లేదా నిలిపివేయండి:

```sql
PRAGMA mmap_size = 0;
```

### "మైగ్రేషన్ మధ్యలో విఫలమైంది"

మైగ్రేషన్ ఒక ట్రాన్సాక్షన్లో అమలైంది, కాబట్టి అది రోల్బ్యాక్ అయి ఉండాలి. అలా జరగకపోతే:

1. **OmniRouteను ఆపండి** (తదుపరి ప్రయత్నాలను నిరోధించండి)
2. `sqlite3`తో **DB స్థితిని తనిఖీ చేయండి**
3. పాక్షిక మైగ్రేషన్ను **మాన్యువల్గా సరిచేయండి**
4. OmniRouteను **మళ్లీ అమలు చేయండి** (మైగ్రేషన్ మళ్లీ ప్రయత్నించబడుతుంది)
