పుల్ రిక్వెస్ట్ కోసం అత్యంత చిన్నదైన, నమ్మదగిన డెవలప్మెంట్ లూప్ను ఎంచుకోవడానికి ఈ మార్గదర్శిని ఉపయోగించండి. ఇది దిగువ లింక్ చేసిన
ప్రాంత-నిర్దిష్ట ఆర్కిటెక్చర్ మరియు భద్రతా పత్రాలకు ప్రత్యామ్నాయం కాదు; ఇది ప్రతి సాధారణ
మార్పు రకాన్ని దాని కాంట్రాక్ట్లు, కేంద్రీకృత తనిఖీలు మరియు CI కవరేజ్తో అనుసంధానిస్తుంది.

## ప్రతి మార్పు అనుసరించే మార్గం

1. **సవరించే ముందు బేస్ను ఎంచుకోండి.** అత్యధిక క్రియాశీల `release/v*` బ్రాంచ్ను కనుగొని, దాని
   తాజా కమిట్ నుండి బ్రాంచ్ను సృష్టించండి. `main`ను కాకుండా ఆ బ్రాంచ్ను లక్ష్యంగా చేసుకోండి. రిలీజ్ ఫ్రీజ్ అమల్లో ఉంటే, ఫ్రీజ్ చేసిన
   బ్రాంచ్ను లక్ష్యంగా చేసుకోవద్దు;
   [బ్రాంచింగ్ & రిలీజ్ మోడల్](BRANCHING_MODEL.md)లో వివరించిన తదుపరి క్రియాశీల సైకిల్ను ఉపయోగించండి.
2. **కాంట్రాక్ట్లను పేర్కొనండి.** మార్పు ప్రభావితం చేసే ప్రతి కేటలాగ్, స్కీమా, జనరేట్ చేసిన ఆర్టిఫ్యాక్ట్, పబ్లిక్ API లేదా వినియోగదారు
   ఇంటర్ఫేస్ను గుర్తించండి. దిగువ పట్టిక కనీస ప్రారంభ సమితిని అందిస్తుంది.
3. **కేంద్రీకృత పరీక్షలను రాయండి లేదా నవీకరించండి.** `src/`, `open-sse/`, `electron/`, లేదా
   `bin/`లోని ప్రొడక్షన్ మార్పులకు అదే PRలో ఆటోమేటెడ్ పరీక్ష అవసరం. ప్రవర్తనను నిరూపించే అత్యంత చిన్న పరీక్ష ఫైళ్లను
   అమలు చేసి, ఆ తర్వాత జాబితాలోని కేంద్రీకృత గేట్లను అమలు చేయండి.
4. **విస్తృత మ్యాట్రిక్స్ను CI అమలు చేయనివ్వండి.** పూర్తి యూనిట్ షార్డ్లు, Vitest, కవరేజ్ రాచెట్ మరియు
   ప్రొడక్షన్ బిల్డ్ PRపై అమలవుతాయి. కేంద్రీకృత వైఫల్యం విస్తృత ప్రభావాన్ని సూచించినప్పుడు లేదా మార్పు అనేక సబ్సిస్టమ్లకు
   విస్తరించినప్పుడు మాత్రమే విస్తృత సూట్ను లోకల్గా అమలు చేయండి.
5. **రివ్యూకు ముందు సమన్వయం చేయండి.** క్రియాశీల బేస్ను ఫెచ్ చేసి, దాని కొత్త కమిట్లను మరియు దానితో పోల్చిన మీ డిఫ్ను
   పరిశీలించి, కాంట్రిబ్యూటర్ వర్క్ఫ్లో ప్రకారం బేస్ను రీబేస్ లేదా మెర్జ్ చేయండి. జనరేట్ చేసిన ఫైల్
   మరియు కేటలాగ్ కాన్ఫ్లిక్ట్లను వాటి సోర్స్ వద్ద పరిష్కరించి, వాటిని మళ్లీ జనరేట్ చేసి, కేంద్రీకృత లూప్ను తిరిగి అమలు చేసి,
   PR ఇప్పటికీ క్రియాశీల రిలీజ్ బ్రాంచ్నే లక్ష్యంగా చేసుకుంటోందని నిర్ధారించండి.
6. **ఆధారాలను నమోదు చేయండి.** PR టెంప్లేట్లో అమలు చేసిన కమాండ్లు, జోడించిన లేదా మార్చిన ప్రతి పరీక్ష ఫైల్,
   మైగ్రేషన్లు లేదా ఫీచర్ ఫ్లాగ్లు మరియు ఇంకా పెండింగ్లో ఉన్న ఏదైనా CI-మాత్రమే వాలిడేషన్ను జాబితా చేయండి.

## మార్పు రకం వారీగా ప్రామాణిక మార్గాలు

దిగువ కమాండ్లు కనీస కేంద్రీకృత తనిఖీలు మాత్రమే; మీరు మార్చిన ప్రవర్తనను నేరుగా కవర్ చేసే పరీక్షను
దాటవేయడానికి ఇవి అనుమతి కావు.

### ప్రొవైడర్

**కాంట్రాక్ట్లు**

- `src/shared/constants/providers/`లోని ప్రొవైడర్ నిర్వచనం మరియు
  `src/shared/constants/providers.ts`లో దాని కంపోజిషన్.
- `open-sse/config/providerRegistry.ts` లేదా దాని నుండి విడదీసిన రిజిస్ట్రీ ఫైళ్లలోని మోడల్లు మరియు సామర్థ్యాలు.
- వర్తించే సందర్భంలో ఎగ్జిక్యూటర్/ట్రాన్స్లేటర్ ఎంపిక, OAuth లేదా API-కీ కాన్ఫిగరేషన్, డ్యాష్బోర్డ్ అసెట్లు మరియు జనరేట్ చేసిన
  ప్రొవైడర్ రిఫరెన్స్.
- పబ్లిక్ క్రెడెన్షియల్లు తప్పనిసరిగా `resolvePublicCred()`ను ఉపయోగించాలి; ఎర్రర్ రెస్పాన్స్లు తప్పనిసరిగా షేర్డ్ శానిటైజ్డ్
  ఎర్రర్ హెల్పర్లను ఉపయోగించాలి. `docs/security/PUBLIC_CREDS.md` (git; `/docs`లోకి కంపైల్ చేయబడదు) మరియు
  [ఎర్రర్ శానిటైజేషన్](../security/ERROR_SANITIZATION.md) చూడండి.

**కేంద్రీకృత లూప్**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # కేటలాగ్ మారినప్పుడు; జనరేట్ చేసిన డిఫ్ను కమిట్ చేయండి
npm run lint
```

ప్రభావితమైన ప్రతి రిక్వెస్ట్ ఫ్యామిలీని కూడా పరీక్షించండి: చాట్, Responses, ఇమేజ్లు, ఎంబెడ్డింగ్లు, ఆడియో లేదా వీడియో.
జనరేట్ చేసిన కేటలాగ్ మరియు గోల్డెన్ డిఫ్లను కాంట్రాక్ట్ మార్పులుగా రివ్యూ చేయండి; వాటిని ఆలోచించకుండా అంగీకరించవద్దు.

### రూటింగ్

**కాంట్రాక్ట్లు**

- `src/shared/constants/routingStrategies.ts`లోని పబ్లిక్ స్ట్రాటజీ విలువలు మరియు UI మెటాడేటా.
- `open-sse/services/combo.ts` మరియు `open-sse/services/combo/` కింద డిస్పాచ్ మరియు క్రమబద్ధీకరణ.
- కాంబో స్కీమాలు, పర్సిస్టెన్స్, రెసిలియెన్స్ స్థితి, మోడల్ సామర్థ్యాలు మరియు API/UI కంట్రోల్లు.
- ప్రవర్తన మారినప్పుడు [ఆటో-కాంబో ఇంజిన్](../routing/AUTO-COMBO.md) మరియు రెసిలియెన్స్ డాక్యుమెంటేషన్.

**కేంద్రీకృత లూప్**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # స్ట్రాటజీ లేదా డిస్పాచ్ మార్పులు
npm run check:known-symbols      # స్ట్రాటజీ రిజిస్ట్రేషన్ మార్పులు
npm run lint
```

లోకల్గా నిర్ధారిత ఫలితాలనిచ్చే మాక్డ్-అప్స్ట్రీమ్ పరీక్షలను ఉపయోగించండి. లైవ్ కాంబో స్మోక్లకు క్రెడెన్షియల్లు అవసరం మరియు అవి
మాన్యువల్ పరీక్షలు; CIకి ప్రత్యామ్నాయాలు కావు.

### UI / UX

**కాంట్రాక్ట్లు**

- `src/app/` మరియు `src/shared/components/` కింద Next.js రూట్/పేజ్ మరియు షేర్డ్ కంపోనెంట్ హద్దులు.
- API రెస్పాన్స్ ఆకృతులు, లోడింగ్/ఖాళీ/ఎర్రర్ స్థితులు, కీబోర్డ్ మరియు స్క్రీన్-రీడర్ ప్రవర్తన,
  రెస్పాన్సివ్ లేఅవుట్, థీమింగ్ మరియు లోకేల్ విస్తరణ.

### డేటాబేస్

**ఒప్పందాలు**

## భాగస్వామ్య మెషీన్ కోసం డెవలపర్ స్క్రిప్ట్లు

ఇతర సెషన్లు క్రియాశీలంగా ఉన్న devboxలో లోకల్ లూప్ను రెండు `scripts/dev/` సహాయకాలు అమలు చేస్తాయి:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEAD నుండి ఫైళ్లు
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # సరిగ్గా ఈ ఫైళ్లు మాత్రమే
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # వేరుచేసిన worktree, సమాంతర వినియోగానికి సురక్షితం
```

- `typecheck-touched.sh` తాకబడిన `.ts/.tsx` ఫైళ్లను మాత్రమే తాత్కాలిక
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) ద్వారా, 6 GB heap కింద typecheck చేస్తుంది; అందువల్ల అధిక లోడ్లో ఉన్న మెషీన్లో
  OOM అయ్యే ప్రాజెక్ట్-వ్యాప్త `tsc -p tsconfig.json` స్థానంలో ఇది ఉపయోగించబడుతుంది. ఇది తాకబడిన ఫైళ్లలోని
  లోపాలతో పాటు ఒక సారాంశ పంక్తిని ముద్రిస్తుంది; తాకబడిన ఫైళ్లలో లోపాలు ఉంటే `1`, లోపాలు కేవలం import
  చేసిన ఫైళ్లలో మాత్రమే ఉంటే లేదా diagnostics లేకుండా tsc విఫలమైతే `2` (అది సూచించే
  `_artifacts/typecheck-touched/` కిందనున్న logను చదవండి), లోపాలు లేకపోతే `0`తో నిష్క్రమిస్తుంది.
  తాత్కాలిక tsconfig ఎల్లప్పుడూ తొలగించబడుతుంది; దాన్ని ఎప్పుడూ commit చేయవద్దు.
- `new-worktree.sh`, `<git-common-dir>/omniroute-new-worktree.lock`పై సమకాలీన అమలులను వరుసగా
  నిర్వహిస్తుంది (డిఫాల్ట్గా 600 s వరకు, కనిపించే సందేశంతో వేచి ఉంటుంది; override గురించి స్క్రిప్ట్
  headerలో వివరించబడింది), అలాగే worktree ఉనికిలోకి రాకముందే `git worktree add` విఫలమైతే అది సృష్టించిన
  branchను వెనక్కి తీసివేస్తుంది; కాబట్టి మళ్లీ ప్రయత్నించడానికి మాన్యువల్గా `git branch -D` అవసరం లేదు.
  hard-link చేసిన `node_modules` మరియు `.husky/_` కాపీ మారవు.

## లోకల్ candidate లూప్

ప్యాకేజ్ చేసిన artifact boot అవుతుందని source tests నిరూపించలేవు: tarballను install చేసి ప్రారంభించిన
తర్వాత మాత్రమే packaging జాబితాలు, prune చేసిన dependencies, మరియు native binariesలోని వైఫల్యాలు
బయటపడతాయి. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) అనేది RFC #8084లోని
build-once / validate / promote ప్రవాహానికి లోకల్ భాగం: ఇది ఒక candidateను build చేసి, అదే artifactను
validate చేసి, directory renameలతో promote చేస్తుంది; promote చేసిన slot health checkలో విఫలమైతే
దాన్ని rollback చేస్తుంది.

```bash
npm run dev:candidate -- run --dry-run --json  # ప్రణాళికను ముద్రించు, ఏదీ మార్చవద్దు
npm run dev:candidate -- run                   # build + validate + promote, స్వయంచాలక rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/లో install
npm run dev:candidate -- validate --id <id>    # ఖాళీ portలో boot చేసి, /api/health + /v1/models తనిఖీ
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current మరియు previousను పరస్పరం మార్చు
npm run dev:candidate -- run --from-tarball <file.tgz>  # వేరే చోట (CI) build చేసిన tarballను మళ్లీ ఉపయోగించు
```

- **ఒక్కసారి మాత్రమే build చేయండి.** `build`, ప్రస్తుత treeను pack చేస్తుంది (దీనికి
  `dist/server.js` అవసరం, కాబట్టి ముందుగా `npm run build:release` అమలు చేయండి) లేదా
  `--from-tarball`ను కాపీ చేస్తుంది; తర్వాత tarballలో `node_modules` ఉండదు కాబట్టి దాన్ని వేరుచేసిన npm
  prefixలో install చేస్తుంది. id అనేది సంక్షిప్త `HEAD` sha (treeలో లోకల్ మార్పులు ఉన్నప్పుడు
  `-dirty`) లేదా tarball కోసం `tgz-<sha256>`. ఇప్పటికే build చేసిన clean idను మళ్లీ build చేయకుండా
  తిరిగి ఉపయోగిస్తుంది; దాన్ని మళ్లీ build చేయడానికి `--force` ఇవ్వండి.
- **Sourceను కాదు, packageను validate చేయండి.** `validate`, కొత్త `DATA_DIR=<candidate>/data`,
  నకిలీ secretsతో install చేసిన CLIని (`serve --port <free port>`) ప్రారంభిస్తుంది; అలాగే operatorకు
  చెందిన `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY`, మరియు `INITIAL_PASSWORD`ను environment
  నుండి తొలగిస్తుంది. తద్వారా కొత్త install యొక్క keyless loopback postureను ఇది తనిఖీ చేస్తుంది.
  `GET /api/health` 200ను తిరిగి ఇచ్చే వరకు ఇది వేచి ఉంటుంది, `GET /v1/models` తప్పనిసరిగా 200ను
  తిరిగి ఇవ్వాలని నిర్ధారిస్తుంది, process groupను ఆపుతుంది, మరియు tarball hashతో పాటు ఫలితాన్ని
  `validation.json`లో నమోదు చేస్తుంది.
- **అదే artifactను promote చేయండి.** ప్రస్తుత tarball hashకు విజయవంతమైన validation లేని candidateను
  `promote` తిరస్కరిస్తుంది. డిఫాల్ట్ active slot `_artifacts/candidate/current`;
  `--target <dir>` అదే filesystemలో మరొక directoryని ఎంచుకుంటుంది, దాని previous slot
  `<dir>.previous`. ప్రతి rename atomicగా ఉంటుంది; మధ్యలో వైఫల్యం సంభవిస్తే, అప్పటికే జరిగిన
  renameలను తిరిగి వెనక్కి మారుస్తుంది.
- **Rollback చేయండి.** `run`, promote చేసిన slotను మళ్లీ validate చేస్తుంది; ఆ తనిఖీ విఫలమైతే
  `current` మరియు `previous`ను తిరిగి పరస్పరం మారుస్తుంది. మొదటి validationలో విఫలమైన candidate
  ఎప్పటికీ promote చేయబడదు.

ప్రతిదీ gitignore చేసిన `_artifacts/candidate/` కింద వ్రాయబడుతుంది; ఇప్పటికే ఉన్న OmniRoute
installation మరియు దాని data directory ఎప్పటికీ మార్చబడవు. Promote చేసిన CLI
`_artifacts/candidate/current/prefix/bin/omniroute`; దాన్ని ఉపయోగించేటప్పుడు మీ స్వంత `DATA_DIR`తో
ప్రారంభించండి. Exit codes: విజయం కోసం `0`, విఫలమైన validation లేదా promotion కోసం `1`, వినియోగ
లోపం లేదా build లేకపోవడం కోసం `2`.

## స్థానిక లూప్ మరియు CI మధ్య తేడా

| ప్రతి ప్యాచ్కు స్థానికంగా అమలు చేయాల్సినవి                                      | CI అందించే విస్తృత సంకేతం                                                         |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| పైన పేర్కొన్న ప్రత్యక్ష ప్రవర్తన పరీక్షలు మరియు కేటగిరీ గేట్లు                  | షార్డ్ చేసిన పూర్తి యూనిట్ సూట్ మరియు సీరియల్ పరీక్షలు                            |
| `npm run lint`                                                                  | Vitest సూట్లు మరియు కవరేజ్/నాణ్యత రాచెట్లు                                        |
| ప్రభావిత కాంట్రాక్ట్ అవసరమైనప్పుడు మాత్రమే టైప్చెక్ లేదా బిల్డ్                 | ప్రొడక్షన్ బిల్డ్, భద్రత, డాక్స్, డిపెండెన్సీ మరియు PR-పాలసీ గేట్లు               |
| ఆటోమేషన్ ప్రవర్తనను నిరూపించలేనప్పుడు మాత్రమే మాన్యువల్ ఇంటరాక్షన్/లైవ్ తనిఖీలు | వర్క్ఫ్లో ద్వారా కాన్ఫిగర్ చేసిన క్రాస్-జాబ్ ఇంటిగ్రేషన్ మరియు ప్లాట్ఫామ్ తనిఖీలు |

విజయవంతమైన ఫోకస్డ్ లూప్ అనేది మార్చిన కాంట్రాక్ట్కు సంబంధించిన ఆధారం మాత్రమే; సంబంధం లేని CI తనిఖీలు
విజయవంతమవుతాయని నిరూపణ కాదు. అదే సమయంలో, ప్రతి స్థానిక సవరణ పూర్తి రిపోజిటరీ మ్యాట్రిక్స్ కోసం వేచి ఉండేలా చేయవద్దు.

## సమన్వయ చెక్లిస్ట్

రివ్యూ అభ్యర్థించే ముందు:

- PR బేస్ ఇప్పటికీ అత్యధిక యాక్టివ్ `release/v*` బ్రాంచ్గానే ఉందని నిర్ధారించండి.
- ఆ బేస్ను ఫెచ్ చేసి, మీరు బ్రాంచ్ చేసిన తర్వాత చేర్చబడిన కమిట్లను సమీక్షించండి.
- అనుకోకుండా జరిగిన లేదా జనరేట్ అయిన మార్పుల కోసం `git diff <active-base>...HEAD`ను సమీక్షించండి.
- సోర్స్ను అప్డేట్ చేసి, అవుట్పుట్ను తిరిగి జనరేట్ చేయడం ద్వారా కేటలాగ్ మరియు జనరేట్ చేసిన డాక్యుమెంట్ విభేదాలను పరిష్కరించండి.
- సమన్వయం తర్వాత PR వివరణలో పేర్కొన్న ప్రతి ఫోకస్డ్ టెస్ట్/గేట్ను మళ్లీ అమలు చేయండి.
- మారిన బేస్కు సరిపోల్చడం కోసం మాత్రమే అసర్షన్లను బలహీనపరచవద్దు లేదా అవసరమైన పరీక్షలను తొలగించవద్దు.

రిలీజ్-ఫ్రీజ్ మరియు రీటార్గెటింగ్ నియమాల కోసం,
[బ్రాంచింగ్ & రిలీజ్ మోడల్](BRANCHING_MODEL.md)ను ఉపయోగించండి. పూర్తి CI జాబితా కోసం,
[క్వాలిటీ గేట్స్ రిఫరెన్స్](../architecture/QUALITY_GATES.md)ను ఉపయోగించండి.
