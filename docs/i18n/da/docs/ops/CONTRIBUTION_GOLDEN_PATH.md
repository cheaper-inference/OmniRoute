Brug denne vejledning til at vælge den mindst omfattende, pålidelige udviklingscyklus til en pull request. Den erstatter ikke
de områdespecifikke arkitektur- og sikkerhedsdokumenter, der er linket til nedenfor; den forbinder hver almindelig
ændringstype med dens kontrakter, fokuserede kontroller og CI-dækning.

## Det forløb, som alle ændringer følger

1. **Vælg basisgrenen, før du redigerer.** Find den højeste aktive `release/v*`-gren, og opret din gren fra
   dens seneste commit. Brug denne gren som mål, ikke `main`. Hvis der er et aktivt release-freeze, må du ikke bruge den fastfrosne
   gren som mål; brug den næste aktive cyklus, der er beskrevet i
   [Forgrenings- og releasemodel](BRANCHING_MODEL.md).
2. **Angiv kontrakterne.** Identificer hvert katalog, skema, genereret artefakt, offentligt API eller hver
   brugergrænseflade, som ændringen påvirker. Tabellen nedenfor angiver det minimale udgangspunkt.
3. **Skriv eller opdater fokuserede tests.** Produktionsændringer i `src/`, `open-sse/`, `electron/` eller
   `bin/` kræver en automatiseret test i samme PR. Kør de mindst omfattende testfiler, der beviser
   funktionaliteten, og derefter de angivne fokuserede kontroller.
4. **Lad CI køre den brede matrix.** De komplette unit-testshards, Vitest, den trinvise dækningskontrol og
   produktionsbuildet kører på PR'en. Kør kun en bred testsuite lokalt, når en fokuseret fejl peger på
   en bredere påvirkning, eller når ændringen spænder over flere undersystemer.
5. **Afstem før gennemgang.** Hent den aktive basisgren, gennemgå dens nye commits og din diff i forhold
   til den, og foretag derefter rebase eller merge af basisgrenen i henhold til bidragyderworkflowet. Løs konflikter i genererede filer
   og kataloger ud fra deres kilde, generer dem igen, kør den fokuserede cyklus igen, og bekræft, at
   PR'en stadig er målrettet den aktive release-gren.
6. **Registrer dokumentation.** Angiv i PR-skabelonen de kørte kommandoer, hver testfil, der er tilføjet eller ændret,
   migreringer eller feature flags samt eventuel validering, der kun udføres i CI og stadig afventer.

## Gyldne stier efter ændringstype

Kommandoerne nedenfor er minimumsfokuserede kontroller, ikke tilladelse til at springe en test over, der direkte dækker den adfærd, du ændrede.

### Udbyder

**Kontrakter**

- Udbyderdefinition i `src/shared/constants/providers/` og dens sammensætning i `src/shared/constants/providers.ts`.
- Modeller og muligheder i `open-sse/config/providerRegistry.ts` eller dets udpakkede registreringsfiler.
- Executor/translator -valg, OAuth eller API-nøglekonfiguration og dashboardaktiver. Begå ikke de regenererede `docs/reference/PROVIDER_REFERENCE.md` eller README diagrammer: udgivelsesopdateringen omskriver dem (`check:pr-derived-paths` fejler en funktion PR, der bærer dem).
- Offentlige legitimationsoplysninger skal bruge `resolvePublicCred()`; fejlsvar skal bruge de delte rensede fejlhjælpere. Se `docs/security/PUBLIC_CREDS.md` (git; ikke kompileret i `/docs`) og [Fejlsanering](../security/ERROR_SANITIZATION.md).

**Fokuseret sløjfe**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # preview the generated reference; do not commit it
npm run lint
```

Test også alle berørte anmodningsfamilier: chat, svar, billeder, indlejringer, lyd eller video. Gennemgå genereret katalog og gyldne forskelle som kontraktændringer; ikke acceptere dem blindt.

### Routing

**Kontrakter**

- Offentlige strategiværdier og UI metadata i `src/shared/constants/routingStrategies.ts`.
- Forsendelse og bestilling under `open-sse/services/combo.ts` og `open-sse/services/combo/`.
- Kombinationsskemaer, persistens, modstandsdygtighed, modelkapaciteter og API/UI kontroller.
- [Auto-Combo Engine](../routing/AUTO-COMBO.md) og robusthedsdokumentation, når adfærd ændres.

**Fokuseret sløjfe**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy or dispatch changes
npm run check:known-symbols      # strategy registration changes
npm run lint
```

Brug deterministiske hånede opstrømstest lokalt. Live combo-ryger kræver legitimationsoplysninger og er manuelle, ikke CI erstatninger.

### UI / UX

**Kontrakter**

- Next.js route/page og delte komponentgrænser under `src/app/` og `src/shared/components/`.
- API svarformer, loading/empty/error tilstande, tastatur- og skærmlæseradfærd, responsivt layout, tematik og lokalitetsudvidelse.
- Engelske UI -kildestrenge i `src/i18n/messages/en.json`; ikke hårdkode ny brugervendt kopi.

**Fokuseret sløjfe**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Kør appen for interaktion eller visuelle ændringer, og tjek både smalle og brede visningsporte. CI kører produktionsbygningen og bredere suiter; visuel adfærd har stadig brug for en fokuseret komponent, Playwright eller dokumenteret manuel kontrol, der passer til ændringen.

### i18n

**Kontrakter**

- `src/i18n/messages/en.json` er UI kilden; `config/i18n.json` er lokalitetskilden.
- CLI kataloger lever separat under `bin/cli/locales/`.
- Bevar ICU pladsholdere og tags nøjagtigt. Oversæt ikke product/provider/model navne, protokol- og headernavne, kommandoer, code/JSON identifikatorer, URLs, miljøvariabler eller beskyttede termer såsom `OmniRoute`, `OAuth`, `MCP` og `A2A`. Den aktuelle kildeliste er `scripts/i18n/glossary/protected-terms.json`.

En funktion PR redigerer kun `src/i18n/messages/en.json` (CLI: `bin/cli/locales/en.json`); de andre lokaliteter afsluttes én gang pr. udgivelse ved udgivelsesopdateringen eller en oversættelsesbølge (`docs/guides/I18N.md` → "Feature PRs touch `en.json` only"). `npm run check:pr-derived-paths` fejler en funktion PR, der redigerer et andet lokalitetskatalog.

**Fokuseret sløjfe**

```bash
npm run i18n:check-ui-coverage
npm run check:ui-icu
node scripts/i18n/check-key-completeness.mjs --mode=pr      # what CI runs on your PR
node scripts/i18n/check-ui-value-drift.mjs --mode=pr
node scripts/check/check-cli-i18n.mjs --mode=pr              # when CLI strings change
npm run i18n:check-glossary
npm run lint
```

Uden `--mode=pr` kører disse porte i frigivelsestilstand lokalt og rapporterer hver nøgle, som cyklussen er tilføjet eller omskrevet i `en.json`; det er udgivelsesopdateringens arbejde, ikke dine PR.

Dette er vejledning til det eksisterende system, ikke en invitation til at udvide dets værktøj eller nøglemodel. Hold i18n plastre kirurgiske, mens erstatningssystemet bliver designet. Kør ikke oversættelseskommandoer, der kalder eksterne tjenester, medmindre opgaven eksplicit kræver genererede oversættelser, og du har gennemgået den resulterende forskel.

### CLI

**Kontrakter**

- Offentlige kommandoer og flag i `bin/cli/`, genererede API -kommandoer, exit-koder, stdout/stderr og JSON -outputformer, config/environment -adfærd og pakkede filer.
- CLI -brugervendte strenge skal bruge CLI i18n-laget (`t()` nøgler, der findes i `bin/cli/locales/en.json`). En funktion PR redigerer kun `en.json`; `pt-BR` og de andre lokaliteter er afsluttet ved udgivelsen.
- Bevar Node som den understøttede runtime og den offentliggjorte binære kontrakt.

**Fokuseret sløjfe**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
node scripts/check/check-cli-i18n.mjs --mode=pr
npm run build:cli             # generated/bundled CLI changes
npm run check:pack-policy     # package-surface changes
npm run lint
```

Brug den nøjagtige kommando i en midlertidig datamappe, når adfærd afhænger af parsing, filer eller afslutningsstatus. CI udfører den bredere pakkeartefakt og økosystemtjek.

### Database

**Kontrakter**

- Domænemoduler under `src/lib/db/`; importer specifikke moduler direkte (det gamle `localDb.ts` -re-eksportlag blev fjernet).
- Nummererede, idempotente SQL -migreringer under `src/lib/db/migrations/`, transaktionssikkerhed, opgraderingsadfærd, indekser og hver opkalder, der er påvirket af skemaet.
- Ruter og handlere udsteder aldrig rå SQL direkte.

**Fokuseret sløjfe**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Test både en ny database og opgradering fra det tidligere skema, når du tilføjer en migrering. Databasetest skal lukke håndtag og kalde `resetDbInstance()` under oprydning. Kør kun `npm run test:bun:db`, når den bedste Bun -adaptersti ændres; Node forbliver autoritativ.

### Byg/implementer

**Kontrakter**

- Rod og arbejdsområde manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/` pakkeindhold, Electron platformsmetadata, CI -arbejdsgange og implementeringsvagter.
- Understøttede nodeområder og den tilladte brug af Bun i `CLAUDE.md` skal forblive intakt.
- Byg artefakter forbliver usporede; afhængighed, licens, arbejdsgang og pakkepolitikker gælder.

**Fokuseret sløjfe**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency or lockfile changes
npm run check:pack-policy      # published package surface changes
npm run lint
```

Brug kun `npm run build` lokalt, når ændringen påvirker kompilering, selvstændig samling, aktiver eller runtime-bundling. Brug kun `npm run build:release` til release/deploy validering. CI's build er det endelige cross-platform signal; platformspecifikke Electron -ændringer kræver det matchende fokuserede bygge- eller røgbevis.

## Udviklerscripts til en delt maskine

To hjælpeværktøjer i `scripts/dev/` indkapsler den lokale arbejdsgang på en devbox, hvor andre sessioner er aktive:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # filer fra merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # præcis disse filer
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # isoleret worktree, sikkert parallelt
```

- `typecheck-touched.sh` typekontrollerer kun de berørte `.ts/.tsx`-filer via en midlertidig
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) med en heap på 6 GB, så det erstatter den projektdækkende `tsc -p tsconfig.json`,
  der løber tør for hukommelse på en belastet maskine. Det udskriver fejlene i de berørte filer samt
  én opsummeringslinje og afslutter med `1` for fejl i berørte filer, `2`, når de eneste fejl er i
  importerede filer, eller tsc afsluttede uden diagnostik (læs den logfil under
  `_artifacts/typecheck-touched/`, som det angiver), og `0`, når der ikke er nogen fejl. Den
  midlertidige tsconfig fjernes altid; commit aldrig en sådan fil.
- `new-worktree.sh` serialiserer samtidige kørsler via `<git-common-dir>/omniroute-new-worktree.lock`
  (venter som standard i op til 600 s med en synlig meddelelse; scriptets header dokumenterer,
  hvordan dette kan tilsidesættes) og ruller den branch tilbage, som det oprettede, når
  `git worktree add` fejler, før worktree'et findes, så et nyt forsøg ikke kræver en manuel
  `git branch -D`. De hardlinkede `node_modules` og kopien af `.husky/_` er uændrede.

## Lokal kandidatcyklus

Kildetests kan ikke bevise, at den pakkede artefakt starter: pakkelister, beskårede afhængigheder
og native binærfiler fejler først, når tarballen installeres og startes. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) er den lokale side af flowet byg én gang / valider / promover fra
RFC #8084: Det bygger én kandidat, validerer præcis denne artefakt, promoverer den ved at omdøbe
mapper og ruller den tilbage, når den promoverede plads ikke består sit sundhedstjek.

```bash
npm run dev:candidate -- run --dry-run --json  # udskriv planen, ændr intet
npm run dev:candidate -- run                   # byg + valider + promover, automatisk tilbagerulning
npm run dev:candidate -- build                 # npm pack + installer i _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # start på en ledig port, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # ombyt current og previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # genbrug en tarball bygget et andet sted (CI)
```

- **Byg én gang.** `build` pakker det aktuelle træ (det kræver `dist/server.js`, så kør
  `npm run build:release` først) eller kopierer `--from-tarball` og installerer derefter tarballen
  i et isoleret npm-præfiks, fordi tarballen ikke indeholder nogen `node_modules`. Id'et er den
  korte `HEAD`-sha (`-dirty`, når træet har lokale ændringer) eller `tgz-<sha256>` for en tarball.
  Et rent id, der allerede er bygget, genbruges i stedet for at blive bygget igen; angiv `--force`
  for at genbygge det.
- **Valider pakken, ikke kilden.** `validate` starter den installerede CLI
  (`serve --port <free port>`) med en ny `DATA_DIR=<candidate>/data`, falske hemmeligheder, og
  operatørens `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` og `INITIAL_PASSWORD` fjernet fra
  miljøet, så det kontrollerer en ny installations nøgleløse loopback-konfiguration. Det venter på,
  at `GET /api/health` returnerer 200, kræver, at `GET /v1/models` returnerer 200, stopper
  procesgruppen og registrerer resultatet i `validation.json` sammen med tarballens hash.
- **Promover den samme artefakt.** `promote` afviser en kandidat uden en bestået validering for
  dens aktuelle tarball-hash. Den aktive standardplads er `_artifacts/candidate/current`;
  `--target <dir>` vælger en anden mappe på det samme filsystem, og dens tidligere plads er
  `<dir>.previous`. Hver omdøbning er atomisk, og en fejl undervejs tilbagefører de omdøbninger,
  der allerede er udført.
- **Rul tilbage.** `run` validerer den promoverede plads igen og ombytter `current` og `previous`
  tilbage, når kontrollen fejler. En kandidat, der ikke består den første validering, promoveres
  aldrig.

Alt skrives under den gitignorerede `_artifacts/candidate/`; en eksisterende OmniRoute-installation
og dens datamappe berøres aldrig. Den promoverede CLI er
`_artifacts/candidate/current/prefix/bin/omniroute`; start den med din egen `DATA_DIR`, når du bruger
den. Afslutningskoder: `0` for succes, `1` for mislykket validering eller promovering, `2` for
brugsfejl eller manglende build.

## Lokal løkke kontra CI

| Kør lokalt for hver patch                                                          | CI leverer det brede signal                                                           |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Direkte adfærdstests og kategorikontroller ovenfor                                 | Opdelt komplet enhedstestsuite og serielle tests                                      |
| `npm run lint`                                                                     | Vitest-suiter og skralder for dækning/kvalitet                                        |
| Typekontrol eller build kun, når den berørte kontrakt kræver det                   | Produktionsbuild, sikkerheds-, dokumentations-, afhængigheds- og PR-politikkontroller |
| Manuel interaktion/livekontroller kun, når automatisering ikke kan bevise adfærden | Integration på tværs af jobs og platformskontroller konfigureret af workflowet        |

En grøn fokuseret løkke er dokumentation for den ændrede kontrakt, ikke bevis for, at ikke-relaterede CI-kontroller
vil bestå. Omvendt bør du ikke lade hver lokal ændring vente på hele repository-matricen.

## Tjekliste for afstemning

Før du anmoder om review:

- Bekræft, at PR-basen stadig er den højeste aktive `release/v*`-branch.
- Hent denne base, og gennemgå commits, der er landet, siden du oprettede din branch.
- Gennemgå `git diff <active-base>...HEAD` for utilsigtede eller genererede ændringer.
- Løs konflikter i kataloger og genererede dokumenter ved at opdatere kilden og regenerere outputtet.
- Kør alle fokuserede tests/kontroller, der er angivet i PR-beskrivelsen, igen efter afstemningen.
- Svæk aldrig assertions, og fjern ikke påkrævede tests blot for at matche en flyttet base.

For regler om release-freeze og retargeting, se
[Branching- og releasemodel](BRANCHING_MODEL.md). Den komplette CI-oversigt findes i
[Reference til kvalitetskontroller](../architecture/QUALITY_GATES.md).
