> **TOML er det eneste effektive format.** Moderne Codex læser udelukkende
> `~/.codex/config.toml` (bekræftet med codex-cli 0.147.0: `codex --help`
> dokumenterer, at `-c/--config`-tilsidesættelser "indlæses fra
> `~/.codex/config.toml`"). Den gamle `~/.codex/config.yaml` tilhørte den
> forældede npm-CLI og ignoreres uden nogen meddelelse. Dashboardgeneratoren
> (`/api/cli-tools/apply`, værktøjet `codex`) skriver TOML med en konservativ
> fletning — eksisterende nøgler og andre providerblokke bevares, API-nøglen
> forbliver i `OMNIROUTE_API_KEY` (aldrig i filen), og en tilbageværende ældre
> `config.yaml` rapporteres som en migreringsbemærkning uden at blive ændret.

## config.toml klar til at indsætte

Erstat `<YOUR_HOST>` og `<YOUR_KEY>` med dine værdier:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # grænse for historiklagring pr. værktøjskald

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc eller ~/.zshrc — den faktiske nøgleværdi, aldrig i config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex inkluderet i ChatGPT-appen

Hvis du installerede Codex via ChatGPT-skrivebordsappen, findes den binære
`codex`-fil muligvis kun i app-pakken og endnu ikke i din shells `PATH`. Føj
ressourcemappen til din shells opstartsfil:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Åbn en ny shell, og kontrollér derefter:

```bash
command -v codex
codex --version
```

### Lokal OmniRoute uden godkendelse: En pladsholdernøgle er tilstrækkelig

Codex kontrollerer, at den miljøvariabel, som er angivet af `env_key`, findes,
**før** den første anmodning forlader CLI'en. Hvis din **lokale**
OmniRoute-instans ikke kræver godkendelse, fungerer enhver ikke-tom pladsholder:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Brug i stedet en rigtig nøgle, når din OmniRoute-server er beskyttet eller ekstern.

> **Almindelige værtsindstillinger**
>
> | Adgang         | URL                           |
> | -------------- | ----------------------------- |
> | Lokalt netværk | `http://192.168.0.1:20128/v1` |
> | Tailscale      | `http://100.x.x.x:20128/v1`   |
> | Loopback       | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — derfor fungerer det for alle modeller

Codex CLI udfasede `wire_api = "chat"` (Chat Completions) i februar 2026 og
**kræver** nu `wire_api = "responses"` (OpenAI Responses API). Indstilling af
`wire_api = "chat"` medfører et øjeblikkeligt nedbrud ved opstart siden v0.138.

Mange providers, herunder GLM og Kimi, tilbyder stadig kun et Chat
Completions-endpoint. DeepSeek V4 tilbyder nu både en integreret Responses API
og et Anthropic-kompatibelt endpoint; OmniRoute bruger Responses som standard
og lader hver DeepSeek-forbindelse vælge Anthropic-kompatibilitet.

**OmniRoute løser dette på en gennemsigtig måde:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute vælger providerens integrerede protokol og oversætter efter behov
    → POST /responses (DeepSeek V4) eller /chat/completions (Mistral / GLM / Kimi / andre)
```

Du behøver aldrig en separat oversættelsesproxy, når du bruger OmniRoute.
**Alle modeller bruger `wire_api = "responses"`** — OmniRoute håndterer resten.

> **`wire_api` er standardindstillingen** — feltets standardværdi er
> `"responses"`, og det kan udelades helt fra `config.toml`. Angiv det kun
> eksplicit, hvis du dokumenterer hensigten.

## Kontekstvindue og komprimering

### Felter til tokenkonfiguration

| Felt                             | Beskrivelse                                                                                                                                                                                                                              |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Samlet tokenbudget for den aktive model. Indstil til modellens angivne grænse.                                                                                                                                                           |
| `model_auto_compact_token_limit` | Tærskel, der udløser automatisk komprimering af historikken. **Maksimum: 90 % af `model_context_window`** — værdier over 90 % ignoreres uden varsel.                                                                                     |
| `tool_output_token_limit`        | Grænse for antallet af tokens, der gemmes i historikken pr. output fra et værktøjskald. Forhindrer, at et enkelt stort værktøjssvar fylder vinduet. **Dette er ikke det maksimale output** — det er en grænse for lagring i historikken. |
| `compact_prompt`                 | Integreret tilsidesættelse af den systemprompt, der bruges under komprimering (v0.138+).                                                                                                                                                 |

> **Bemærkning om `model_max_output_tokens`**: Dette felt er **ikke en del af Codex CLI-konfigurationsskemaet** (det findes ikke i Codex-kodebasen i Rust). Det ignoreres uden varsel, hvis det angives. Stol ikke på det — brug `tool_output_token_limit` til at styre, hvor meget værktøjsoutput der gemmes i historikken.

## Ræsonneringsindsats

Styrer, hvor meget modellen "tænker", før den svarer.

| Værdi    | Bruges til                                           |
| -------- | ---------------------------------------------------- |
| `none`   | Ingen ræsonnering — direkte svar                     |
| `low`    | Trivielle opgaver (omdøbning, formatering)           |
| `medium` | **Serverstandard**, når det ikke er angivet          |
| `high`   | Opgaver på mellemniveau (refaktorering, fejlfinding) |
| `xhigh`  | Arkitektur, dybdegående analyse, komplekse problemer |

```bash
# Tilsidesættelse pr. kørsel
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Angiv også et **resumé** af ræsonneringen, så Desktop kan gengive tanketekst (ikke kun krypterede datablokke):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # eller ultra, når det understøttes
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute-tænkebudget (serverindstilling)

På OmniRoute-værten skal **Settings → AI → Thinking Budget** være indstillet til **`passthrough`**, for at Codex-indsats/resumé kan nå den overordnede tjeneste. Tilstanden **`auto` fjerner** alle klientfelter af typen `reasoning` / `reasoning_effort` og vil tømme tænkningspanelerne, selv når Codex er konfigureret korrekt.

Komplet vejledning: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Komprimering og promptcache er uafhængige og fortsætter med at fungere under `passthrough`.

## Profiler — navngivne konfigurationer pr. model/arbejdsgang

Profiler gør det muligt at skifte model + kontekstvindue med et enkelt flag. Hver profil er en flad
`~/.codex/<name>.config.toml`, der lægges oven på den grundlæggende `config.toml`.

> **Navngivningsregel (Codex CLI v0.137+):** filen skal hedde `~/.codex/<name>.config.toml` — **uden præfikset `profile-`**.
> CLI'en fortolker `-p kimi-k27` som `~/.codex/kimi-k27.config.toml`. Hvis filen ikke findes, anvendes standardindstillingen uden varsel.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # hurtig, billig
```

### Indsatsprofiler (samme model, forskellig indsats)

```bash
codex -p low      # cx/gpt-5.5, indsats=low
codex -p medium   # cx/gpt-5.5, indsats=medium
codex -p high     # cx/gpt-5.5, indsats=high
codex -p xhigh    # cx/gpt-5.5, indsats=xhigh (standard)
codex -p chat     # cx/gpt-5.5, ingen indsats angivet (serverstandard)
```

## Automatisk generering af profiler med `omniroute setup-codex`

Hvis du kører OmniRoute på en VPS, kan du automatisk generere profilfiler fra det aktive modelkatalog:

```bash
# Fra en VPS (bruger lokal OmniRoute på port 20128)
omniroute setup-codex

# Fra enhver maskine — peg på din VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Forhåndsvisning uden at skrive filer
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Generér kun GLM- og Kimi-profiler
omniroute setup-codex --only glm,kimi

# Skriv til en brugerdefineret mappe
omniroute setup-codex --codex-home /path/to/.codex
```

Kommandoen henter `/v1/models`, bruger finjusterede profiler til kendte modeller, falder tilbage til katalogmetadata for andre kompatible tekstmodeller og skriver `~/.codex/<name>.config.toml` for hver af dem. Den er idempotent — det er sikkert at køre den igen.

Hvis den grundlæggende `config.toml` ikke har en `model_providers.omniroute`-definition, inkluderer en eksplicit kørsel af
`setup-codex` denne definition i hvert genereret overlay ved hjælp af det valgte
lokale eller eksterne slutpunkt. Grundfilen forbliver uændret. En eksisterende udbyderdefinition
nedarves, inklusive dens slutpunkt og godkendelsesindstillinger. Ugyldig
TOML i grundfilen stopper genereringen, før profilerne skrives.

Når du angiver `--api-key` eller `OMNIROUTE_API_KEY`, henviser en nydefineret udbyder til
`env_key = "OMNIROUTE_API_KEY"`; selve nøglen gemmes eller vises aldrig i
forhåndsvisningen. Indstil denne variabel i det miljø, hvor du starter Codex. Uden en
angivet nøgle har den nye definition intet krav om en nøgle og er beregnet til en OmniRoute-instans,
der er konfigureret til at acceptere ikke-godkendte anmodninger.

Den tilvalgte automatiske katalogsynkronisering, der er beskrevet nedenfor, bevarer udbyderdefinitioner, som allerede findes
i et overlay, men opretter ikke nye udbyderindstillinger; konfigurer først udbyderen
med en eksplicit opsætning eller via kontrolpanelet. Eksisterende udbyderindstillinger udelades
fra forhåndsvisninger med `--dry-run`, fordi de kan indeholde legitimationsoplysninger, som administreres af operatøren.

OmniRoute kan også **automatisk synkronisere** de samme profilfiler, når en vellykket registrering/import af udbydermodeller ændrer det aktive katalog. Dette er **et tilvalg og er som standard slået fra**: slå det til via **CLI Code-kontrolpanelet** ("CLI profile auto-sync" → Codex), eller indstil `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (det respekterer også `CLI_ALLOW_CONFIG_WRITES`, som er slået til som standard). Når funktionen er aktiveret, skriver den kun separate `~/.codex/*.config.toml`-profilfiler; den ændrer aldrig den aktive/standardmæssige `~/.codex/config.toml`, Codex-lb-indstillinger, godkendelse eller valg af udbyder.

## Langvarige opgaver

To OmniRoute standardindstillinger kan lydløst sabotere Codex CLI sessioner på flere timer. En Codex CLI indstilling — er heller ikke live på OmniRoute siden. Brugere, der migrerer en konfiguration fra upstream-proxyer, der fastgør konti og deaktiverer inaktive cutoffs, rammer ofte begge og konkluderer, OmniRoute "ikke kan opretholde en lang session."

| Symptom                                                                                | Sandsynlig årsag                                                      | Knop                     |
| -------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------ |
| Session bliver ved med at skifte konti / prompt-cache-kontinuitet går tabt mellem ture | Sessionsaffinitet TTL er `0` (deaktiveret)                            | `sessionAffinityTtlMs`   |
| Forbindelsen dør midt i ræsonnementet uden nogen klient-vendt prompt                   | Stream inaktiv vagthund affyret efter 10 minutter uden opstrøms chunk | `STREAM_IDLE_TIMEOUT_MS` |

Relaterede diskussioner: [#7126](https://github.com/cheaper-inference/OmniRoute/discussions/7126) (lange opgave falder), [#5718](https://github.com/cheaper-inference/OmniRoute/discussions/5718) (hvorfor affinitet deaktiveres som standard). Sporing: [#7287](https://github.com/cheaper-inference/OmniRoute/issues/7287).

### 1. Sessionsaffinitet — fastgør én samtale til én konto

**Misligholdelse:** `sessionAffinityTtlMs = 0` (deaktiveret).

**Hvor skal den indstilles**

- Dashboard →** Indstillinger → Routing** →** Sessionsaffinitet** →** Affinitet TTL (sekunder)** (`ComboDefaultsTab`)
- Eller PATCH -indstillinger med `sessionAffinityTtlMs` in** millisekunder** (Zod range `0`–`86_400_000`, dvs. op til 24 timer)

> Omdøbt i #7274 fra Codex-only `codexSessionAffinityTtlMs`. Den ældre nøgle accepteres stadig som et skrivebeskyttet alias; nye konfigurationer skal bruge `sessionAffinityTtlMs`. Affinitet gælder nu** enhver** udbyder når TTL er over `0`, ikke kun Codex — se [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Sessionsaffinitet.

**Hvad går i stykker, når den forbliver på 0**

Hver tur i en Codex samtale med flere sving rutes uafhængigt af den aktive kombinationsstrategi og kan lande på en** forskellig konto pr. tur** . Det bryder opstrøms session / prompt-cache-kontinuitet. OmniRoute konsulterer kun Codex -sessionsoverskrifter (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) og kropsfelter såsom `prompt_cache_key` / `session_id`, når TTL er større end `0` (`extractSessionAffinityKey` i `src/sse/services/auth.ts`).

**Anbefales til en enkelt opgave på flere timer**

Indstil TTL** over opgavens forventede vægurlængde** (UI max er** 86400 sekunder** = 24 timer):

| Forventet opgavelængde | Affinitet TTL (UI, sekunder) | `sessionAffinityTtlMs` |
| ---------------------- | ---------------------------- | ---------------------- |
| Et par timer           | `14400` (4 timer)            | `14400000`             |
| Overnatning / ~ 12h    | `43200` (12 timer)           | `43200000`             |
| Hel dag                | `86400` (24 timer, maksimum) | `86400000`             |

Tilvalget er bevidst: Deaktivering af affinitet favoriserer belastningsbalancering på tværs af konti; at aktivere det fremmer kontinuitet i en lang agentsession. Det gør denne guide** ikke** ændre standard — operatører, der kører lange Codex opgaver, skal tilmelde sig.

### 2. Stream inaktiv timeout — dræber ikke stille ræsonnement vendinger

**Misligholdelse:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minutter). Den arver fra `REQUEST_TIMEOUT_MS` når den ikke er indstillet; den delte baseline er også 600000. Se [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Timeouts.

**Hvad går i stykker ved standard**

En Codex -ræsonnement / værktøjsvending, der forbliver tavs i mere end 10 minutter med** ingen reel opstrøms chunk** er tvangslukket af SSE tomgangsvagthunden (`open-sse/utils/stream.ts`). Klienten ser ofte en blottet forbindelse drop — matching "stoppet automatisk uden nogen meddelelse."

Kritiske detaljer: OmniRoute syntetiske SSE** hjerteslag nulstilles ikke** det ledige ur. Kun en rigtig opstrøms kropsdel opdaterer `lastChunkTime`. En stille model, der stadig "tænker", ser fra vagthundens synspunkt identisk ud med en stoppet opstrøms.

Relateret Undici-kroppsinaktivitet: `FETCH_BODY_TIMEOUT_MS` (standard til den samme 10-minutters baseline; `0` deaktiverer den). For streaming dækker `FETCH_TIMEOUT_MS` kun forbindelsesopsætning / første overskrifter —, når streamen er aktiv, er stallene styret af `STREAM_IDLE_TIMEOUT_MS` og `FETCH_BODY_TIMEOUT_MS`.

**Anbefales til en enkelt opgave på flere timer**

I OmniRoute -procesmiljøet (`.env` / compose / systemd):

```bash
# Disable stream idle + body inactivity cutoffs for long reasoning turns
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Eller hæv dem over det længste stille mellemrum, du forventer (værdier er millisekunder):

```bash
# Example: allow up to 2 hours of silence between upstream chunks
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Genstart OmniRoute efter at have ændret disse env vars.

### Konkret opskrift — multi-timers Codex opgave

1. **Fastgør kontoen:** Dashboard → Indstillinger → Routing → Sessionsaffinitet → Affinitet TTL = `43200` (12h) eller `86400` (24h maks.).
2. **Hæv/deaktiver tomgangsafbrydelser** i OmniRoute miljø:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Behold de sædvanlige Codex `config.toml` (`wire_api = "responses"`, correct `base_url`, `OMNIROUTE_API_KEY`) — ingen affinity/idle knapper på Codex-siden findes for disse to adfærd.
4. Genstart OmniRoute, og start derefter den lange Codex opgave.

### Standardbeslutning (#7287)

| Knop                     | Send standard     | Ændre i denne vejledning?                                                                                   |
| ------------------------ | ----------------- | ----------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (fra)         | **Ingen** — forbliver opt-in (belastningsbalancering vs kontinuitet; se diskussion #5718)                   |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min) | **Ingen** — forbliver 10 minutter for almindelig trafik; lange Codex operatører hæver eller deaktiverer den |

At vende enten standard globalt ville ændre adfærd for hver klient i en instans, ikke kun Codex. Dokumenter knapperne; lad standarderne være, indtil en eksplicit operatørbeslutning siger noget andet.

### Diagnosticering af tomgangssnit

Når den ledige vagthund skyder, logger OmniRoute en linje formet som:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Grep for `Idle timeout: no data from` (eller koden `stream_idle_timeout` / fejlnavn `StreamIdleTimeoutError`). Udbydersegmentet er uanset hvilken OmniRoute der bruges til den anmodning (`codex`, en anden udbyder-id eller `provider` hvis ukendt) — det er ikke altid den bogstavelige streng `codex`.

## Fejlfinding

**`Error: wire_api = "chat" is no longer supported`** Fjern `wire_api = "chat"` fra din config. Indstil `wire_api = "responses"` eller udelad feltet (standard til `"responses"` siden v0.138).

**`Error: model not found`** Bekræft, at modellen findes i OmniRoute med det korrekte præfiks. Brug `omniroute models list` eller åben `/dashboard/providers/<provider>`.

**`Authentication error`** Bekræft, at `OMNIROUTE_API_KEY` er eksporteret: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`** Codex validerer, at env var eksisterer før den første anmodning. Eksporter en rigtig nøgle til beskyttede servere eller en ikke-tom pladsholder såsom `OMNIROUTE_API_KEY=local` når din** lokal** OmniRoute forekomsten kræver ikke godkendelse. Genstart skallen, hvis du føjede den til `~/.bashrc` eller `~/.zshrc`.

**`Connection refused`** Kontroller, OmniRoute kører, og at `base_url` host/port er korrekt for dit netværk (lokal vs Tailscale vs VPS).

**Session går ned tæt på kontekstgrænsen** Indstil `model_context_window` og `model_auto_compact_token_limit` eksplicit. Se kontekstvinduet ovenfor.

**Komprimering affyrer for sent** Sænk `model_auto_compact_token_limit` til 80–85 % af vinduet. Indstil aldrig over 90%.

**Profilen indlæses ikke (`-p <name>` ignoreret stille)** Bekræft, at filen findes på `~/.codex/<name>.config.toml` (ingen `profile-` præfiks). Kør `ls ~/.codex/*.config.toml`.

**Lang Codex opgave falder midtvejs / skifter konto mellem sving** Se [Langvarige opgaver](#long-running-tasks). Aktiver sessionsaffinitet (TTL over opgavelængde) og hæv eller deaktiver `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Grep OmniRoute logfiler til `Idle timeout: no data from`.
