Den indeholder buildets version og en relativ server-URL (`./`), så anmodninger forbliver på den vært, der leverede dokumentet. Et værktøj, der importerer den downloadede fil, har ikke en sådan vært og skal have basis-URL'en angivet manuelt.

## Chatfuldførelser

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Tilpassede headere

| Header                   | Retning   | Beskrivelse                                                                                                                                                                                                                 |
| ------------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Anmodning | Sæt til `true` for at omgå cache                                                                                                                                                                                            |
| `x-omniroute-no-memory`  | Anmodning | Sæt til `true` for at springe memory- og skills-injektion over for denne anmodning (spejler no-cache; undgår token-/omkostningsoverhead pr. kald)                                                                           |
| `X-OmniRoute-Progress`   | Anmodning | Sæt til `true` for statusbegivenheder                                                                                                                                                                                       |
| `X-Session-Id`           | Anmodning | Sticky session-nøgle til ekstern sessionstilknytning                                                                                                                                                                        |
| `x_session_id`           | Anmodning | Variant med underscore accepteres også (direkte HTTP)                                                                                                                                                                       |
| `X-OmniRoute-Session-Id` | Anmodning | Session-/samtalemærke angivet af kaldende part (bruges også af memory). Når det er angivet, gemmes det ordret i `call_logs.session_tag` til omkostningsfordeling pr. session (#8249) — syntetiseres aldrig, når det mangler |
| `Idempotency-Key`        | Anmodning | Dedup-nøgle (5 sekunders vindue)                                                                                                                                                                                            |
| `X-Request-Id`           | Anmodning | Alternativ dedup-nøgle                                                                                                                                                                                                      |
| `x-omniroute-connection` | Anmodning | Fastgør en anmodning med én model til én provider-forbindelse (konto) efter dens id — se [Kontofastgørelse pr. anmodning](#account-pinning-per-request)                                                                     |
| `X-OmniRoute-Cache`      | Svar      | `HIT` eller `MISS` (ikke-streaming)                                                                                                                                                                                         |
| `X-OmniRoute-Idempotent` | Svar      | `true` hvis deduplikeret                                                                                                                                                                                                    |
| `X-OmniRoute-Progress`   | Svar      | `enabled` hvis statussporing er aktiveret                                                                                                                                                                                   |
| `X-OmniRoute-Session-Id` | Svar      | Effektivt sessions-id, der bruges af OmniRoute                                                                                                                                                                              |
| `X-OmniRoute-Request-Id` | Svar      | Korrelations-id for anmodningen (når det er kendt)                                                                                                                                                                          |
| `X-OmniRoute-Version`    | Svar      | OmniRoute-buildversion (altid til stede)                                                                                                                                                                                    |
| `X-OmniRoute-Cost-Saved` | Svar      | USD, som cachen sparede ved et HIT (kun cache-hits)                                                                                                                                                                         |
| `X-OmniRoute-Decision`   | Svar      | Routingsporing: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` er kombinationsstrategien eller `single` for en anmodning uden kombination) — altid til stede i svar ved afslutning                           |

> Nginx-bemærkning: Hvis du er afhængig af headers med underscore (for eksempel `x_session_id`), skal du aktivere `underscores_in_headers on;`.

#### Kontofastgørelse pr. anmodning

Når en provider har flere forbindelser (konti eller nøgler), vælger OmniRoute normalt én
via sin kontovælgsstrategi. En anmodning kan i stedet fastgøre én bestemt forbindelse
med headeren `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Hvor id'et findes.** Åbn udbydersiden i dashboardet
  (**Dashboard → Providers → <provider>**), og klik på `xxxxxxxx…`-id-chip'en på en forbindelsesrække — det kopierer hele forbindelses-id'et.
- **Hvilke requests der respekterer det.** Requests til en enkelt model (`provider/model`) på
  `/v1/chat/completions`, `/v1/messages` og `/v1/responses`. Kombinationer ignorerer headeren: fastlås
  en konto pr. kombinationstrin via trinnets egen forbindelse i stedet.
- **Fastlåsningen er strikt, ikke en præference.** Den fastlåste forbindelse bruges udelukkende. En
  fejl under requesten registrerer kontoens nedkølingsperiode, men skifter **ikke** til en
  søsterkonto hos samme udbyder.
- **Nedkøling og kvote frigiver fastlåsningen.** Mens den fastlåste forbindelse er under nedkøling,
  har opbrugt sin kvote eller er blokeret af en kvotepolitik, falder efterfølgende requests tilbage
  til udbyderens andre forbindelser, præcis som ikke-fastlåst trafik.
- **Ukendte eller deaktiverede id'er fejler.** Et id, der ikke findes i udbyderens aktive pulje (slettet,
  deaktiveret eller tilhører en anden udbyder), efterlader ingen kvalificeret konto, så requesten
  fejler i stedet for at blive dirigeret et andet sted hen uden besked.

Claude Code sender brugerdefinerede headers via `ANTHROPIC_CUSTOM_HEADERS`. Angiv den i `env`-blokken
i `~/.claude/settings.json` eller i en projektniveau-`.claude/settings.json` for at fastlåse en
anden konto pr. projekt:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Kilde: `src/sse/handlers/chat.ts` (læsning af headeren), `src/sse/services/auth.ts` og
`src/sse/services/sessionAffinityPin.ts` (frigivelse af fastlåsningen og kontrollen af, om den mangler i puljen).

> **Headers til omkostningstelemetri:** Svar med succes uden streaming indeholder også sættet af `X-OmniRoute-*`-headers til omkostningstelemetri — `X-OmniRoute-Response-Cost` (USD, fast 10 decimaler; `0.0000000000` for gratis/uden pris), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` og `X-OmniRoute-Fallback-Attempts` (kun når > 0) samt `X-OmniRoute-Request-Id` og `X-OmniRoute-Version`. Disse udsendes af chat completions, `/v1/responses`, `/v1/messages` **og medie-endpoints** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` og `/v1/moderations` (altid med omkostningen `0`). Medieomkostningen beregnes pr. modalitet (pr. billede, pr. sekund, pr. tegn, pr. søgeenhed), når prisoplysninger er tilgængelige, ellers `0` (fail-open).

> **Semantikken for omkostning ved cache-hit:** Ved et HIT i den semantiske cache (`X-OmniRoute-Cache-Hit: true`) foretages der intet upstream-kald, så `X-OmniRoute-Response-Cost` er `0.0000000000` (den **inkrementelle** omkostning ved at levere hittet). Den oprindelige/forventede omkostning rapporteres separat i `X-OmniRoute-Cost-Saved`. Faktureringsforbrugere bør summere `X-OmniRoute-Response-Cost` (hits koster intet); cacheanalyser kan aggregere `X-OmniRoute-Cost-Saved`.

## Eksklusive leases af administrerede sessioner

Eksklusiv leasing af administrerede sessioner er en valgfri, klientneutral routingaftale: én aktiv ejer
har én kvalificeret OmniRoute-forbindelse. Den leaser ikke en model, kræver ikke OAuth, identificerer ikke
en bestemt klient og kræver ikke en bestemt udbyder.

Den autentificerende API-nøgle skal have scope `lease:exclusive` og en eksplicit ikke-tom
`allowedConnections`-liste. Databasens mutationsgrænse håndhæver begge felter samlet ved oprettelse af
nøgler og delvise opdateringer.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Svar på vellykket acquire, renew og release viser tidsstempler, `state` og den nøjagtige positive
`generation`, men aldrig den valgte forbindelse eller legitimationsoplysninger. Renew og release angiver
generationen i JSON-brødteksten:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

En aktiv lease-ejer kan eksplicit anmode om privatlivssikre visningsmetadata for sin aktuelle binding:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Denne valgfri statushandling er sikret af den uigennemsigtige ejer, den autentificerede administrerede
API-nøgle og den nøjagtige aktive generation i én databasetransaktion. `displayName` er kun det trimmede
navn på den konfigurerede forbindelse; det er `null`, når der ikke findes et sikkert konfigureret navn.
OmniRoute indsætter aldrig en e-mail eller en genereret kontoidentitet i stedet. Udbyderværdien er en
ikke-følsom visningsetiket og aldrig en genereret identifikator for en kompatibel udbyder. Legitimationsoplysninger,
tokens, cookies, rå forbindelses- eller API-nøgle-id'er, ejerhashes, hegningshemmeligheder og interne
routingdata er udeladt.

Opslag med forkert nøgle, forkert ejer, forældet generation, manglende, udløbet, frigivet eller
ugyldiggjort lease returnerer alle den samme `409 LEASE_FENCE_STALE`-fejl uden forbindelsesmetadata. En klient,
der har modtaget svaret om kapacitetsventetid, har ingen aktiv binding, der kan inspiceres. Når routing
overgår en aktiv lease, forbliver den samme generation gyldig, og status returnerer atomisk den nye binding,
aldrig den gamle. Eksisterende klienter forbliver uændrede, fordi svarene på acquire, renew, release og
ventetid bevarer deres tidligere form.

Denne serverkontrakt ændrer ikke standard-OpenAI Codex `/status`. Standard-Codex rapporterer i øjeblikket sin
modeludbyder og indbyggede autentificerings-/kontotilstand, men viser ikke vilkårlige kontometadata for
tilpassede udbydere; en senere klientintegration skal kalde denne handling og beslutte, hvordan
`connection.displayName` skal vises.

Hver administreret inferensanmodning sender derefter begge kontrolheadere:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Den nøjagtige ejer, generation, aktive forbindelse og autentificerede API-nøgle sikres umiddelbart
før hvert understøttet upstream-forsøg. Genafspilning af ejer og generation med en anden nøgle mislykkes,
selv når denne nøgle giver adgang til den samme forbindelse. Rå ejere gemmes ikke, logges ikke, opbevares
ikke i request-snapshot'et og videresendes ikke upstream.

Midlertidig kapacitetskonflikt returnerer HTTP `429` med `Retry-After` og:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Dette svar betyder kun, at det almindelige kvalificerede sæt ikke var tomt, og at alle ledige kandidater
var optaget af en fremmed aktiv lease. Ikke-understøttede modeller/udbydere, politisk mismatch, cooldown,
kvote, tilstand og andre almindelige kvalificeringsfejl bevarer deres eksisterende OmniRoute-svar.

### `x-omniroute-compression`

Per-anmodnings-tilsidesættelse af komprimeringsplanen. Højeste prioritet — overstyrer routing-combo-
tilsidesættelsen, den aktive profil, automatisk udløsning og panelets Default. Værdier:

| Værdi         | Effekt                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| `off`         | Ingen komprimering for denne anmodning.                                                              |
| `default`     | Den panelafledte Default-profil (ignorerer den aktive profil). Lossy-motorer forbliver slået fra.    |
| `safe`        | Kun deduplikering og foldning af mellemrum.                                                          |
| `allow-lossy` | Bevar operatørens plan for denne anmodning, inklusive resuméer og stilomskrivninger.                 |
| `engine:<id>` | En enkelt motor, når den er aktiveret, f.eks. `engine:rtk`. Per-anmodnings-tilvalg for den motor.    |
| `<combo>`     | En navngiven combo, matchet først efter navn (uafhængigt af store/små bogstaver), derefter efter id. |

Bemærkninger:

- Ukendte værdier ignoreres (anmodningen afvises aldrig); opløsningen falder tilbage til den normale operatørprioritet.
- Hvis flere combos deler et navn, skal du angive comboens **id** for et deterministisk match.
- En combo, hvis navn er `off` eller `default`, kan ikke vælges efter navn (disse nøgleord fortolkes først); henvis til en sådan combo via dens id.
- Den overordnede komprimeringskontakt er en hård begrænsning: når komprimering er deaktiveret globalt, kan denne header ikke aktivere den.

Den anvendte plan returneres i svarheaderen:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

hvor `<source>` er én af `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` eller `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Tilgængelige udbydere: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Katalog-id'er er `provider/model` (eksempel: `jina-ai/jina-embeddings-v5-omni-small`). Rene Jina-model-id'er, der findes i registreringsdatabasen (for eksempel `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), løses også. Jina embed/rerank/classify/segment bruger legitimationsoplysninger fra dashboardet for `jina-ai` først; `JINA_AI_API_KEY` er kun en reserve, når der ikke findes en dashboard-nøgle. Kortet `jina-reader` er kun Reader / `r.jina.ai` (`POST /v1/web/fetch`) og leverer aldrig embeddings eller rerank.

Registreringsmodeller, der angiver understøttelse af multimodalitet, accepterer også op til 32 udbyderneutrale strukturerede elementer. Medieelementtyper er `text`, `image`, `audio`, `video` og `document`. Deres medie-`source` er enten `{"type":"url","url":"https://..."}` eller
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
og familiealiaset `jina-ai/jina-embeddings-v5-omni` → omni-small) accepterer også Jinas oprindelige
EmbeddingsV5Request-dokumentation og **videresender dem uændret** til `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Oprindelige `{ image | audio | video | pdf }`-værdier kan være en offentlig HTTPS-URL, en `data:`-URI eller rå
base64. OmniRoute konverterer ikke disse objekter til strenge eller henter oprindelige billed-URL'er — Jina henter
selv offentlige medier. Ekstra Jina-felter (`task`, `normalized`, `truncate`, `embedding_type`) videresendes. Jina-SKU'er, der kun understøtter tekst, afviser stadig ikke-tekst-dokumenter.

Sikkerheds- og transportgrænser:

- Eksterne medie-URL'er skal være offentlige HTTPS-URL'er. Kanoniske `{type,source:url}`-elementer hentes
  på serversiden (validering af omdirigeringer, timeout, størrelsesgrænser, offentlig DNS, forbindelsesfastlåsning) og
  indlejres, før udbyderkaldet foretages. Jina-oprindelige `{image:"https://..."}`-elementer videresendes som de er
  efter det samme tjek af offentlig HTTPS; Jina henter URL'en.
- Inline-base64-medier er begrænset til 8 MiB dekodet pr. element og 16 MiB dekodet på tværs af anmodningen.

Udbyderoversættelse (kanoniske elementer videresendes aldrig uændret):

- Jina-multimodale modeller: hvert element på øverste niveau bliver til ét modalitetsnøglebaseret objekt
  (`text` / `image` / `audio` / `video` / `pdf`), der bruger data-URI'er til inline-medier; én vektor pr.
  element på øverste niveau.
- Gemini Embedding 2-familien: ét array på øverste niveau bliver til én oprindelig
  `models/{model}:embedContent`-anmodning med `content.parts` (`text` eller `inline_data`).
- llama.cpp (`llama-cpp/<model>`, enhver model den lokale server har indlæst): kanoniske `text`-elementer
  bliver til almindelige strenge, og `image` / `audio` / `video` bliver hver til ét
  `{"content": [part]}`-objekt ved hjælp af llama-servers chatindholdsdele (`image_url`,
  `input_audio` med formatet `wav` / `mp3` / `flac`, `input_video`) med inline-data; én vektor pr.
  element på øverste niveau. Serveren skal køre med `--embedding --mmproj …`; uden en projektor
  afviser den selv medier. `document` understøttes ikke.
- Ukendte/dynamiske modeller uden eksplicitte modalitetsmetadata afviser struktureret input med HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Ikke-understøttede kombinationer af model/modalitet returnerer HTTP 400 i stedet for at tvinge elementet igennem. Ikke-input-relaterede udvidelsesfelter i ældre anmodninger med strenge/tokens videresendes fortsat uændret.

```bash
# Vis alle embeddingmodeller
GET /v1/embeddings
```

## Billedgenerering

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Tilgængelige udbydere inkluderer OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana,**OpenRouter** ,**ZenMux** , SD WebUI (lokal), ComfyUI (lokal).

`n` returnerer `n` billeder i `data[]`. Udbydere, hvis upstream- API returnerer ét billede pr. opkald (Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik, NVIDIA NIM, Cloudflare Workers AI) får `n` separate upstream-opkald, højst 4 under flyvning. En fast `seed` forskydes af opkaldsindeks (`seed`, `seed + 1`, …), så billederne er forskellige, men forbliver reproducerbare. `n` er begrænset til 10. Anmodningen mislykkes som helhed, hvis et opkald mislykkes. Listen over fan-out-formater er `SINGLE_IMAGE_FANOUT_FORMATS` i `open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux genbruger den eksisterende API-nøgleforbindelse og accepterer `zenmux/` eller `zm/` -præfikser:

- `zenmux/openai/gpt-image-2` bruger ZenMux's OpenAI Images API. Valgmuligheder omfatter `size`, `quality`, `n`, `output_format`, `output_compression`, `background` og `response_format`.
- Andre udgivere, såsom `zm/meta/muse-image-1.0`, bruger ZenMux Vertex AI `:predict` -slutpunkt. `n` kort til `sampleCount`, `aspect_ratio` til `aspectRatio` og `image_size` (`1K`, `2K`, `4K`) til `sampleImageSize`. En pixel `size` leverer kun et billedformat, ikke garanterede pixeldimensioner. Understøttede forhold, opløsninger og antal varierer efter model.
- `zm/inclusionai/ming-image-0.1-design` vælger sine egne dimensioner. Udelad `size`, `aspect_ratio` og `image_size`; eksplicitte værdier returnerer HTTP 400. PNG, JPEG og WebP kan anmodes med `output_format`.

Denne integration understøtter tekst-til-billede-generering, ikke reference-billedredigering. Vertex output er normaliseret til `data[].b64_json`; `response_format: "url"` returnerer en opstrøms HTTPS URL eller en base64 data URL når kun billedbytes er tilgængelige. Empty/filtered output returnerer en fejl snarere end en tom succes. Modeladgang afhænger af ZenMux kontoen. Se [ZenMux's Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) og [OpenAI billeder API](https://docs.zenmux.ai/api/openai/generate-an-image).

En Microsoft 365 Copilot -log-in-forbindelse betjener `copilot-m365-web/m365-copilot-image` gennem Copilot's indbyggede billedværktøj: én Copilot drejning pr. billede (`n` 1–4), `size` styrer kun orienteringen, og billeder returneret inline (`b64_json`, eller en data URL for `response_format: "url"`). Se [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation).

```bash
# List all image models
GET /v1/images/generations
```

## Dokument-OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` vælger OCR-udbyderen via et `provider/model`-præfiks; et model-id uden præfiks (f.eks.
`mistral-ocr-latest`) løses til den registrerede udbyder, og hvis `model` udelades, bruges
Mistral som standard (`mistral-ocr-latest`). Registrerede udbydere
(`open-sse/config/ocrRegistry.ts`):

| Udbyder-id                    | Model-id             | `model`-værdi                                                          | Bemærkninger                                                                                                    |
| ----------------------------- | -------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (eller `mistral-ocr-latest` uden præfiks) | Synkron — svaret returneres direkte fra det enkelte upstream-kald.                                              |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                            | Asynkront upstream-kald (`analyze` + polling) — se nedenfor.                                                    |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                | Synkron via Vertex AI's `openapi/chat/completions`-partnerendpoint — se nedenfor vedrørende godkendelse og URL. |

Alle tre udbydere svarer med den samme Mistral-formede body:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Pollingforløb for Azure Document Intelligence

Azure Document Intelligence's `analyze`-API er asynkron: den indledende anmodning returnerer en
`Operation-Location`-header i stedet for en body, og resultatet skal hentes via polling. Handleren
(`open-sse/handlers/ocr.ts`) poller denne URL hvert sekund i op til 30 forsøg, stopper straks
(fortsætter ikke med at polle) ved et poll-svar, der ikke er `ok`, eller ved status `"failed"`,
og returnerer `504`, hvis operationen stadig kører, efter forsøgsbudgettet er opbrugt. Det
endelige Azure-svar normaliseres til den samme `pages`/`markdown`-struktur, som Mistral bruger,
før det returneres til den kaldende part, så klientkode ikke behøver særbehandle udbyderen.

### Godkendelse og endpoint-opløsning for Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` genbruger den samme Vertex AI-godkendelse, som OmniRoute allerede understøtter til
chat-/billedtrafik (`open-sse/executors/vertex.ts`): Forbindelsens API-nøgle er enten en
Service Account JSON-legitimationsoplysning (udvekslet til et kortlivet OAuth-adgangstoken via JWT-bearer-
flowet) eller et allerede udstedt OAuth-adgangstoken, der bruges uændret. Upstream-endpointets URL er Vertex's
generiske `openapi/chat/completions`-partnerendpoint, opbygget ud fra forbindelsens projekt og
region — en eksplicit `providerSpecificData.project`/`providerSpecificData.region` vinder altid;
ellers udledes projektet fra Service Account JSON's `project_id`, og regionen sættes som standard til
`us-central1`. Begge opløsninger sker i `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), som anvendes af
`src/app/api/v1/ocr/route.ts`, før der videresendes til `handleOcr`.

## List modeller

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Returnerer alle chat-, embedding- og billedmodeller + kombinationer i OpenAI-format
```

### Modelpriser (`pricing`)

En post indeholder et `pricing`-objekt, når OmniRoute kender modellens pris. Prisen kommer
fra pristabellen, som omkostningsberegningen bruger: indbyggede standardværdier, synkroniserede priser og
tilsidesættelser angivet via `/api/pricing`. Dette er listepriser, så abonnementsudbydere viser også
en pris pr. token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Felter                                                          | Enhed                        | Bemærkninger                                                                                                                                |
| --------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD pr. token, decimalstreng | Kompatibel med OpenRouter, aldrig i eksponentnotation. De to cachefelter vises kun, når der findes en cachepris.                            |
| `input`, `output`, `cached`, `cache_creation`                   | USD pr. 1M tokens, tal       | Felter fra tidligere katalogversioner, bevaret for eksisterende klienter. `reasoning` og `long_context` vises også, når prisrækken har dem. |

- **Kombinationer** har prisen for deres første synlige mål. Indbyggede `auto/*`-kombinationer vælger et
  mål på anmodningstidspunktet, så de har ingen `pricing`.
- **Gratis modeller** viser `"0"` (og `0`), når deres pris er nul. En model uden prisrække
  viser også `"0"`, når kataloget markerer den som gratis (`free: true`), eller det indbyggede katalog over gratis modeller
  indeholder den.
- **Ukendt pris:** Posten har ingen `pricing`-nøgle.
- **Udbydere med kreditbaseret afregning** (såsom Kiro) fakturerer pr. anmodning i stedet for pr. token. Deres
  poster beholder de numeriske pr. 1M-felter, de havde tidligere, og indeholder ingen pr. token-strengfelter.
- **Varianter** (id'er for ræsonneringsindsats, aliaser uden tænkning, discovery- og gateway-spejle)
  kopierer prisen fra den model, de videresender til.
- Felterne indeholder kun grundpriser. Niveauer for lange kontekster (det numeriske `long_context`-felt) og
  multiplikatorer for serviceniveauer (f.eks. Codex fast eller flex) ændrer ikke `prompt` eller
  `completion`.
- Objektet er det samme for alle godkendelsesstile, herunder en anmodning i Anthropic-stil
  med `x-api-key` og `anthropic-version` (svaret forbliver `{ "object": "list",
"data": [...] }`). Implementering: `src/app/api/v1/models/catalogPricing.ts`.

### Præfikser for model-id'er (`?prefix=`)

De fleste modeller annonceres under et **udbyderpræfiks**. Hvilket præfiks du får, styres af
funktionsflaget `MODELS_CATALOG_PREFIX_MODE` og kan tilsidesættes **pr. anmodning**
med en forespørgselsparameter — nyttigt for en klient, der ønsker en ren liste uden at ændre
serverens indstilling for alle andre:

```bash
GET /v1/models?prefix=alias        # ét id pr. model — det korte aliaspræfiks
GET /v1/models?prefix=dual         # begge former (serverens standard)
GET /v1/models?prefix=canonical    # kun det fulde udbyder-id-præfiks
```

| Tilstand    | Udsender                                                 | Bemærkninger                                                                                                                                                                         |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dual`      | `cc/claude-sonnet-4-6` **og** `claude/claude-sonnet-4-6` | **Standard.** Begge id'er videresendes til den samme model; bevaret, så klientkonfigurationer, der har hardkodet en af formerne, fortsat virker. Kataloget bliver omtrent fordoblet. |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Én post pr. model. Udbydere uden et særskilt alias udsender stadig deres post, så intet går tabt.                                                                                    |
| `canonical` | `claude/claude-sonnet-4-6`                               | Én post pr. model under det fulde udbyder-id-præfiks. Udbydere uden et særskilt alias (f.eks. `antigravity/…`, `agy/…`) udsender også deres enkelte id her, så intet går tabt.       |

Et spejl i `dual`-tilstand kan også genkendes uden forespørgselsparameteren: det indeholder et `parent`-
felt, der peger på det primære id.

Klienter, der viser en modelvælger, bør anmode om `?prefix=alias` — det er det, som
[OmniCopilot VS Code-udvidelsen](../guides/VSCODE-COPILOT.md) gør.

### Discovery-filtre (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` accepterer valgfri discovery-filtrering. Uden nogen af dem er svaret
uændret. De indsnævrer det katalog, som kalderen allerede kan se (API-nøgletilladelser anvendes først),
og køres før OpenAI-lignende `limit` / `after`-sideinddeling:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # alle angivne funktioner skal være sande
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalogets `type`; rækker uden en sådan er `chat`
GET /v1/models?q=sonnet&limit=10                           # matchning uden hensyn til store og små bogstaver på id eller navn
```

| Parameter     | Værdier                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ikke-negativt heltal, sammenlignes med `context_length`                                             |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 tegn                                                                                          |

En ukendt værdi eller en `min_context`, der ikke er et ikke-negativt heltal (for eksempel `1.5`),
returnerer HTTP `400`, og meddelelsen viser de gyldige værdier. Implementering:
`src/app/api/v1/models/catalogFilters.ts`.

### Modeludvalg (`POST /v1/models/query`)

`POST /v1/models/query` returnerer en kort, deterministisk liste fra det samme katalog med samme
godkendelse og synlighed pr. nøgle som `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Alle felter er valgfri. `capabilities` og `exclude` accepterer et array eller en kommasepareret streng;
`max_output` sammenlignes med `max_output_tokens`. Resultaterne sorteres efter `owned_by` og derefter
`id`. `limit` er som standard `20`, og værdier over `100` begrænses til `100`. Ugyldig JSON, et ukendt
felt eller en ugyldig værdi returnerer HTTP `400`.

### Individuelt skjulte chatmodeller

En model, der er markeret som **Skjult** på sin udbyderside, udelukkes fra kataloget og afvises
med HTTP `404` / `model_not_found`, når den anmodes eksplicit. Kontrolleringen bruger den opløste
udbyder og model, herunder udbyderaliasser, nodepræfikser for kompatible udbydere og
forbindelsesstandarder. En kombination springer skjulte mål over og kan bruge en synlig søskendemodel;
når der ikke er noget eksekverbart mål tilbage, returneres den samme fejlkode. Hvis modellen gøres synlig
igen, træder det i kraft ved den næste anmodning. Synlighedstilsidesættelser, der kun gælder billeder,
skjuler ikke chatmodellen med samme ID.

Denne individuelle modelindstilling er separat fra
[allow/deny-listerne for modeleksponering](../routing/MODEL_EXPOSURE_LIST.md), som filtrerer
katalogannoncering og kandidater til automatisk routing, samtidig med at eksplicit videresendelse
bevares. API-nøglers modeltilladelser gælder fortsat uafhængigt. Standardtilstanden for katalogpræfikser
forbliver `dual`.

### Varianter af modeller uden tænkning

For Claude-modeller, der understøtter tænkning, annoncerer `/v1/models` også en **variant uden tænkning**,
hvis id har præfikset `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Hvis dette id vælges (f.eks. i en Claude Code-konfiguration, der altid vedhæfter en `thinking`-blok),
opløses det tilbage til den rigtige `<provider>/<model>` med undertrykt ræsonnering —
`thinking:{type:"disabled"}` på `/v1/messages`-stien eller felterne `reasoning`/`reasoning_effort`
fjernet på `/v1/chat/completions`-stien. Varianten vises kun for modeller i Claude-familien, der
understøtter tænkning **og** respekterer `disabled` (så f.eks. modeller, der kun understøtter adaptiv
tænkning, og som afviser `disabled`, udelukkes). Operatører kan gennemtvinge, at varianten er slået til
eller fra pr. model via `ModelSpec.noThinkingAlias`.

## Generering af ElevenLabs-lyd

Konfigurer en `elevenlabs`-providerforbindelse i OmniRoute med din ElevenLabs API-nøgle.
Klienter autentificerer med deres **OmniRoute**-nøgle (`Authorization: Bearer $OMNIROUTE_API_KEY`);
gatewayen leverer den gemte providernøgle som `xi-api-key`. Send aldrig en ElevenLabs-nøgle
som gatewayens bearer-token.

| Metode | Sti                         | Svar                                         | Kategori for API-nøgle-endpoint |
| ------ | --------------------------- | -------------------------------------------- | ------------------------------- |
| POST   | `/v1/sound-generation`      | Oprindelige lydb bytes                       | `elevenlabs`                    |
| POST   | `/v1/music`                 | Oprindelige lydb bytes                       | `music`                         |
| POST   | `/v1/music/stream`          | Streamede lydb bytes                         | `music`                         |
| POST   | `/v1/music/detailed`        | Oprindelig multipart-lyd og kompositionsplan | `music`                         |
| POST   | `/v1/music/detailed/stream` | Oprindelige SSE-metadata og lydchunks        | `music`                         |
| POST   | `/v1/music/plan`            | JSON-kompositionsplan                        | `music`                         |

Disse endpoints supplerer de eksisterende `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}`- og `/v1/speech-to-text`-ruter. Oprindelige JSON-felter
og query-parametre som `output_format` og `enable_logging` bevares.
Svar fra `/v1/music/detailed` beholder deres multipart-grænser; fortolk dem som multipart.
`/v1/music/detailed/stream` returnerer `text/event-stream` med kompositionsmetadata og
base64-lydchunks i SSE-events. Alle seks ruter understøtter CORS-preflight.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# En kort lydeffekt. Varighed: 0,5 til 30 sekunder.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Musikvarighed angives i millisekunder: 3000 til 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Brug `/v1/music/stream` med samme JSON-body for trinvis levering af lyd. Composition
accepterer præcis én af `prompt` eller `composition_plan`; `/v1/music/plan` kræver `prompt`
og accepterer valgfrit `source_composition_plan`. De oprindelige skemaer bevarer yderligere
providerfelter, så versioner af kompositionsplaner og finjusteringsindstillinger når frem til ElevenLabs.

Det samlede `/v1/music/generations`-endpoint accepterer også
`elevenlabs/music_v1`, `elevenlabs/music_v2` og `elevenlabs/music_v2_5`. Med en aktiv ElevenLabs-forbindelse
eksponeres disse modeller af musikkataloget. Dette endpoint returnerer
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Feltet `duration` angives i
sekunder og mappes til `music_length_ms`; en eksplicit `music_length_ms` har forrang.
`instrumental` mappes til `force_instrumental`, hvor det oprindelige felt har forrang.
Brug de oprindelige streaming-endpoints til streaming og det oprindelige composition-endpoint
til forespørgsler, der kun styres af en kompositionsplan.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Endpoint-, model-, budget- og forbindelsesbegrænsninger anvendes før et upstream-kald. Oprindelige
ruter returnerer upstream-statuskoder og -fejlbodyer uændret, herunder `402` for en planbegrænsning
og `429` for en kvotebegrænsning. Headere for `character-cost`, `song-id`, `request-id` og `retry-after`
bevares, når de findes. En gratis kreditbalance garanterer ikke adgang til alle
musikmodeller, outputformater eller API-funktioner: ElevenLabs afgør rettighederne for hver forespørgsel.
Det samlede endpoint bevarer fejlkoderne i OmniRoutes normaliserede fejlhylster.

Upstream-kontrakter: [lydeffekter](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[musikkomposition](https://elevenlabs.io/docs/api-reference/music/compose) og
[detaljer om streamet musik](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Omarrangering af providernoder:** `POST /v1/rerank` dirigerer også til OpenAI-kompatible providernoder
> (oMLX, vLLM, Infinity, TEI bag en gateway, …) adresseret som `<node-prefix>/<model>`. Loopback-
> noder (`localhost`, `127.0.0.1`, `172.16.0.0/12`) er altid kvalificerede, ligesom værtsnavne, som
> operatøren angiver i `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (f.eks. et Docker/Compose-servicenavn såsom
> `http://reranker:8080/v1`; disse kaldes direkte, aldrig via `HTTP(S)_PROXY` eller en forbindelses
> fastlåste proxy). Noder på alle andre værter — en LAN-maskine eller Tailscale-peer — er kun
> kvalificerede, når operatøren aktiverer funktionsflaget `RERANK_REMOTE_PROVIDER_NODES` **og** nodens
> basis-URL overholder den udgående URL-politik for providere (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` /
> `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`). Hukommelsesmotorens omrangerings trin kalder denne rute via
> loopback, så den samme regel gælder for `rerankProviderModel` i hukommelsesindstillingerne.
>
> **Lokale serverformer:** Noden kaldes på `<base>/v1/rerank` og, ved 404, på `<base>/rerank`
> (Infinity, TEI). Upstream-bodyen indeholder både Cohere/OpenAI-navngivningen (`documents`,
> `return_documents`) og TEI-navngivningen (`texts`, `return_text`), og upstream-svaret
> normaliseres til Cohere-indpakningen: TEI's ubetingede `[{index, score, text}]`, `{results: [{index, score}]}`
> fra tynde gateways og Voyage-lignende `{data: [...]}` returneres alle til klienten som
> `{results: [{index, relevance_score, document?}]}`, sorteret efter score og begrænset til `top_n`.

> **Opdagelse af providernoder:** Modeller på en OpenAI-kompatibel providernode vises i `GET /v1/models`
> under nodepræfikset. Rækker uden endpointmetadata (typisk for lokale `/v1/models`-lister)
> arver nodens `apiType`, så modellerne på en `embeddings`-node har `type: "embedding"`, og
> modellerne på en `rerank`-node har `type: "rerank"` i stedet for som standard at blive chatmodeller;
> en eksplicit `supportedEndpoints` på en synkroniseret eller manuelt tilføjet række har stadig forrang.

## Søg API

Web/search -udbyderabstraktion (Tavily, Brave, Exa, Serper osv.).

| Metode | Sti                    | Beskrivelse                                                                                   |
| ------ | ---------------------- | --------------------------------------------------------------------------------------------- |
| GET    | `/v1/search`           | Liste konfigurerede søgeudbyderes + funktioner                                                |
| POST   | `/v1/search`           | Kør en søgeforespørgsel — body valideret af `v1SearchSchema`, understøtter caching/coalescing |
| GET    | `/v1/search/analytics` | hit/latency/cache -statistikker pr. udbyder                                                   |

**Auth:** Bærer API nøgle (`extractApiKey` + `isValidApiKey`). Søgepolitik håndhæves via `enforceApiKeyPolicy`.

**Automatisk valg:** uden `provider` kører den billigste udbyder med en konfigureret forbindelse først, og den næstbilligste er failover. Gratis sidste udvej-udbydere (`duckduckgo-free`) bruges kun, når intet andet er konfigureret. En selv-hostet SearXNG tæller som konfigureret, når dens forbindelse lagrer en rigtig `baseUrl` (ikke katalogets standard `http://localhost:8888/search`): den rangerer derefter som en $0-udbyder foran de nøglede, med den billigste nøgleudbyder som failover, inklusive når SearXNG svarer 400, 401, 403 eller 404. A `baseUrl`, der ikke er a `http(s)` URL punkter cloud-metadata-adresse tæller ikke. En SearXNG forbindelse, der gemmer et token, rangerer kun på denne måde over `https://` eller loopback `http://`. Over remote plain `http://` er det aldrig en failover og forbliver en sidste udvej, der kun bruges, når ingen anden udbyder er konfigureret, eller når det anmodes om ved navn, så det sender tokenet i klartekst i disse to tilfælde.

### Exa og Tavily `provider_options`

Exa og Tavily læser udbyderspecifikke felter fra en pose med navneafstand: `provider_options.exa` (eller `provider_options["exa-search"]`) og `provider_options.tavily` (eller `provider_options["tavily-search"]`). Kun nedenstående nøgler videresendes. Hver enkelt kontrolleres mod sit eget Zod skema i `open-sse/handlers/search/providerOptionsPassthrough.ts`, og en nøgle med den forkerte type droppes. Enhver anden nøgle ignoreres, inklusive auth, base URL, `stream` og `outputSchema`. De flade nøgler, der bruges af andre udbydere (`cx`, `depth`, ...) fungerer som før.

| Udbyder | Felter på øverste niveau                                                                                                                                                                                                                                                                                                                                                  | Indlejret                                                                                                                                  |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Exa     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (flade primitiver), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                             | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` fusionerede over standard `{ text: true, highlights: true }` |
| Tavily  | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                          |

De generiske felter vinder altid: `query`, `max_results`, `filters` (domæner), `country` og emnet afledt af `search_type`. På Exa beholder `search_type: "news"` `category: "news"`. Tavily accepterer også `search_type: "finance"` (`topic: "finance"`).

Firecrawl-søgningsomkostninger registreres pr. startet blok af 10 returnerede resultater, til $0,002 (2 kreditter) en blokering og mindst én blokering pr. opkald ( [Firecrawl-fakturering](https://docs.firecrawl.dev/billing) ): 11 resultater koster $0,004.

Den generiske `time_range` når nu begge udbydere: Exa får `startPublishedDate` (ISO timestamp) og Tavily får `start_date` (`YYYY-MM-DD`). En eksplicit dato i `provider_options` tilsidesætter den tilknyttede.

Exa-resultater beholder `id`, `highlights` (hver fremhævning, ikke kun den første brugt som `snippet`), `highlight_scores`, `summary`, `subpages`, `entities` og `extras` i `provider_raw`. Tavily resultater holder `images` og `favicon`.

Linkup-søgningsomkostninger er registreret til $0,005 for `depth` `fast` og `standard` og $0,05 for `deep` ( [Linkup-prissætning](https://docs.linkup.so/pages/documentation/development/pricing) ), uanset om `depth` kommer fra `provider_options` eller forbindelsens indstillinger.

Exa `type: "lite"` (Exa 3.0) accepterer et mindre sæt felter og afviser hele anmodningen, når et hvilket som helst andet felt er indstillet. For lite slettes `additionalQueries`, `systemPrompt` og hver `contents` -tast undtagen `text` og `highlights` før opkaldet. De forældede `subpages`, `subpageTarget`, `highlights.numSentences` og `highlights.highlightsPerUrl` videresendes ikke længere.

Omkostningsregnskab er det flade register `costPerQuery` undtagen Exa, som følger Exas egen prissætning: $0,007 pr. opkald for `auto` (og den gamle `fast`) eller $0,004 for `lite` (og den ældre `instant`), der dækker 10 resultater; $0,001 for hvert yderligere resultat; og $0,001 pr. returneret resultat, når `contents.summary` er indstillet. Tavily er registreret til 1 kredit ($0,008) for `search_depth` `basic`, `fast` og `ultra-fast` og 2 kreditter ($0,016) for `advanced` ( [Tavily API credits](https://docs.tavily.com/documentation/api-credits) ). Et opkald med `auto_parameters: true`, som Tavily opgraderer til avanceret, optages stadig med 1 kredit.

## Web Fetch API

Udtræk indhold fra en URL via en konfigureret web-fetch-udbyder (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, samme API-nøgle som Parallel Search) returnerer kun Markdown — alle andre `format`-værdier giver en `400` — og begrænser indholdet til 100.000 tegn. Når selve målsiden ikke kan udtrækkes, rapporterer upstream dette i et HTTP 200-svar; OmniRoute viser det som en `422` med en fast meddelelse.

| Metode | Sti             | Beskrivelse                                              |
| ------ | --------------- | -------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Hent/scrap en URL — body valideres af `v1WebFetchSchema` |

**Godkendelse:** Bearer API-nøgle (`extractApiKey` + `isValidApiKey`). Politikken håndhæves via `enforceApiKeyPolicy`.

**Kvotebevidst fallback (#8297):** Når der ikke er angivet nogen eksplicit `provider`, gennemløbes puljen
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) i fast
prioritetsrækkefølge (først tilgængelige) — en hastighedsbegrænset, men konfigureret udbyder springes over
i stedet for at afkorte forespørgslen, og en genforsøgsbar/upstream-fejl relateret til kvoten
(HTTP 429 altid; 402/403 for Firecrawl/Tavily/TinyFish-kvotestile på gratis niveauer —
ikke for Jina Reader og aldrig for en almindelig 400-fejlanmodning) går videre til
den næste uprøvede udbyder med legitimationsoplysninger på forespørgselstidspunktet. Når alle udbydere i
puljen er opbrugt, returnerer endpointet en enkelt `429` (med en `Retry-After`-header)
i stedet for den tidligere generiske `400`. Når der anmodes om en eksplicit `provider`, er der **ingen** lydløs fallback — en hastighedsbegrænset eller fejlende eksplicit udbyder viser sin egen fejl (`429` ved hastighedsbegrænsning, ellers upstream-statussen).

## WebSocket-streaming

```bash
GET /v1/ws?handshake=1
```

Validerer et WebSocket-opgraderingshåndtryk og returnerer eksempler på wire-protokolmeddelelserne (`request`, `cancel`). Faktiske WS-frames håndteres af den medfølgende WS-server uden for Next.js-rutetabellen.

**Godkendelse:** Bearer API-nøgle under håndtrykket.

### Responses API over WebSocket (kun codex)

```bash
# Samme host:port som HTTP-API'et (standard 20128); opgradér forbindelsen:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (eller: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Første frame SKAL være response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

En Responses-API-over-WebSocket-proxy er **udelukkende forbundet til `codex`** (ChatGPT-backend). Den lytter på samme port som API'et/dashboardet på stierne `/v1/responses`,
`/responses` og `/api/v1/responses`. Ved den første `response.create`-frame
godkender den + forbereder via den interne `codex-responses-ws`-bro, vælger en
codex OAuth-forbindelse og tunnelerer til
`wss://chatgpt.com/backend-api/codex/responses`
via `wreq-js`-transporten. **Ikke-codex-modeller afvises** (`codex_ws_provider_required`).
Brug `model: "qtSd/<group>/codex/<model>"` til routing efter kvotedeling. Implementeret i
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Godkendelse:** Bearer API-nøgle under håndtrykket. Den medfølgende HTTP-server (`server-ws.mjs`)
skal være det aktive entrypoint (det er den som standard, når `app/server-ws.mjs` findes).

#### Model-id: brug det nøgne ChatGPT-id (uden præfikset `codex/`)

OpenAI **Codex CLI** validerer modelnavnet på klientsiden, når
`supports_websockets = true`, og **afviser provider-præfikserede id'er** som
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Send det **nøgne** id (f.eks. `gpt-5.5`). OmniRoute's bro er
kun til codex, så den opløser igen et nøgent id som en codex-model
(`resolveCodexWsModelInfo`), før den tunnelerer upstream — selvom en nøgen
`gpt-5.5` ellers ville blive routet til en anden udbyder over HTTP.

#### Konfiguration af OpenAI Codex CLI

Peg Codex CLI på OmniRoute ved at tilføje en brugerdefineret udbyder med WebSocket-understøttelse
til `~/.codex/config.toml` (brug en separat `CODEX_HOME` for at undgå at ændre en eksisterende konfiguration):

```toml
model = "gpt-5.5"                 # nøgent id — IKKE "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ingen afsluttende skråstreg; WS-URL'en afledes (brug https/wss i produktion)
wire_api = "responses"                    # eneste understøttede værdi siden februar 2026
supports_websockets = true                # aktiverer Responses-over-WS-transporten
env_key = "OMNIROUTE_API_KEY"             # indeholder OmniRoute API-nøglen (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # en OmniRoute API-nøgle (en hvilken som helst nøgle hvis REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI'en opgraderer `base_url + /responses` til en WebSocket, og OmniRoute tunnelerer den
til den valgte codex OAuth-forbindelse. Valideret fra ende til anden mod den lokale
server: ChatGPT returnerer `codex.rate_limits` + `response.created` og streamer
fuldførelsen.

### Gendannelse af kvotesession (tilvælgelse)

En ikke-streamende `POST /v1/chat/completions` eller `POST /v1/responses`, der mislykkes med
en terminal kvotefejl (`402`/`429`/`503` hvis body'en angiver, at kvoten eller kreditterne er opbrugt),
kan parkeres og afspilles senere i stedet for at returnere fejlen. Klienten tilvælger dette pr. anmodning med tre headers:

| Header                       | Værdi                                            |
| ---------------------------- | ------------------------------------------------ |
| `x-omniroute-quota-recovery` | `auto`                                           |
| `x-omniroute-session`        | sessions-id, `[A-Za-z0-9._:-]{1,128}`            |
| `x-omniroute-recovery-turn`  | turn-id, unikt inden for sessionen (samme regel) |

Kun `stream: false`-turns uden værktøjer, værktøjshistorik eller `previous_response_id` og uden
en `x-omniroute-connection`-fastlåsning er kvalificerede, og `STORAGE_ENCRYPTION_KEY` skal være angivet
(anmodningen gemmes krypteret i op til 24 timer). Svaret er derefter `202` med
`recovery.poll`; afvent med `GET /v1/quota-recoveries/{id}` (`202` mens den afventer, `200` med det
gendannede body, når den er færdig), eller annullér med `DELETE`. Billetter er kun synlige for den API-nøgle,
der oprettede dem. En afspilning, hvis resultat er usikkert, afsluttes i `needs_confirmation`
i stedet for at blive sendt to gange. Kilde: `src/lib/quota/quotaSessionRecovery.ts`.

## Selvbetjent forbrug (`/api/usage/om-usage`)

Enhver API-nøgle kan læse **sit eget** forbrug og sine egne kvoter — ingen administrationsgodkendelse. Dette er endpointet, som en
klient (CLI, OmniCopilot-panelet) bruger til at vise en nøgleindehaver deres forbrug.

```bash
# Tekstformat (den historiske kontrakt — almindelig tekst til en terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Struktureret format — det, som en brugergrænseflade bruger
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Nøglen skal have **`allowUsageCommand`** aktiveret (deaktiveret som standard — dashboardets API-nøgleadministrator
slår det til pr. nøgle). Uden dette svarer endpointet med `403`.

`?format=json` returnerer en diskrimineret struktur, så en klient aldrig læser et datafelt fra et
afslag. Ved succes:

```jsonc
{
  "allowed": true,
  // kun til stede, når nøglen har tilvalgt forbrugsgrænser pr. nøgle (daglige/ugentlige USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // snapshot af den valgte udbyderkvote eller null, når intet endnu er cachet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // snapshot for hver forbindelse, så en brugergrænseflade kan gengive flere udbydere side om side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Ved afslag (`401` ugyldig nøgle / `403` ikke tilladt) returnerer den samme rute
`{ "allowed": false, "error": { "message": "…" } }` — en tilstedeværende, men tom `personal`/`provider`
(nøglen er tilladt, men intet er blevet fundet endnu) er en anden tilstand end et afslag, og kun JSON-formatet
skelner mellem dem.

**Godkendelse:** den kaldende parts egen Bearer-API-nøgle, valideret med `isValidApiKey` — dette er _ikke_
administrationsfladen (`/api/keys/…`), som fortsat er beskyttet af `requireManagementAuth`.

### Rå kontra cutoff-justerede kvoteprocenter

Ved brug af `/api/usage/om-usage` bør klienter være opmærksomme på forskellen mellem
procenterne, der vises af **almindeligt tekstoutput**, og det strukturerede **JSON-output**:

| Aspekt               | Tekstformat (`/api/usage/om-usage` / `@@om-usage`)                                        | JSON-format (`?format=json`)                                              |
| :------------------- | :---------------------------------------------------------------------------------------- | :------------------------------------------------------------------------ |
| **Outputfelt**       | `NN% left` (f.eks. `20% left`)                                                            | `provider.quotas` / `providers[].quotas`                                  |
| **Måling**           | **Cutoff-justeret anvendelig kvote**: resterende kapacitet over cutoff-tærsklen           | **Rå upstream-kvote**: ikke-justeret måling fra udbyderen                 |
| **Cutoff-skalering** | Skaleret via `effectiveRemainingPercent()`, så den beskyttede reserve vises som `0% left` | Ingen (rå snapshot-værdier som rapporteret af udbyderen)                  |
| **Tærskeldata**      | Indarbejdet i den viste procent                                                           | Gemmes i `quotaWindowThresholds` pr. forbindelse (eller serverstandarder) |
| **Primær forbruger** | Interaktive CLI'er, terminalprompter, menneskelige operatører                             | Programmatisk integration, dashboards, analyse, faktureringssporing       |

#### Formlen for cutoff-justering

OmniRoute understøtter proaktive kvote-cutoffs for at forhindre opbrugning hos upstream-udbyderen (konfigureret via forbindelsens
`quotaWindowThresholds`, udbyderstandarder eller globale resiliensindstillinger). Når en cutoff-tærskel
(f.eks. `cutoff = 25%`) er aktiv i et kvotevindue, beregner tekstrendereren den resterende kvote som:

- Hvis `remaining <= cutoff`: returnerer `0%`.
- Hvis `remaining > cutoff`: returnerer `((remaining - cutoff) / (100 - cutoff)) * 100`.

Det formaterede tekstoutput afrunder dette til nærmeste heltal (`Math.round(...)`).

#### Illustrativt eksempel

Overvej et provider-vindue med **60 % råt forbrug** (og dermed **40 % rå resterende kvote**) samt en konfigureret tærskel for **25 % resterende kvote**:

| Repræsentation               | Beregning                                          | Resterende |                Beregnet forbrug                |
| :--------------------------- | :------------------------------------------------- | :--------: | :--------------------------------------------: |
| **Rå JSON (`?format=json`)** | Snapshot fra upstream (`quotas[window]`)           |  **40 %**  |                    **60 %**                    |
| **Tekstformat (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20 %**  | **80 %** (hvis der beregnes `100 - remaining`) |

- **Hvorfor teksten viser 20 % tilbage:** Ud af de 40 % fysiske kvote, der er tilbage på kontoen, er 25 % reserveret af
  cutoff-politikken. Kaldersiden har kun 15 % ud af 75 % brugbart råderum tilbage, før routeren stopper
  med at route til denne forbindelse. Skaleringen sikrer, at forbindelsen signalerer udtømning (`0% left`) præcis,
  når routingen ophører.
- **Hvorfor JSON bevarer rå værdier:** JSON-nyttelasten returnerer det nøjagtige provider-snapshot (`UsageSnapshot`),
  så eksterne værktøjer har adgang til den faktiske udnyttelse fra upstream samt forbindelsesniveauets
  `quotaWindowThresholds` uden tabsbehæftet skalering på serversiden.

#### Vejledning til migrering for forbrugere

Hvis en ekstern integration (f.eks. et editor-plugin eller en agentudvidelse) tidligere udtrak data fra tekstendepunktet
(`NN% left`) og beregnede den anvendte procent som `100 - NN`, betyder migrering til `?format=json`:

- Læsning af rå JSON-værdier afspejler **det faktiske forbrug fra upstream** (60 % anvendt i eksemplet ovenfor).
- Hvis integrationen ønsker at bevare tekstendepunktets semantik for brugbar tilladelse, kan den evaluere
  formlen for effektiv resterende kvote på klientsiden ved hjælp af `quotaWindowThresholds` for tilsidesættelser på forbindelsesniveau.

## Semantisk cache

```bash
# Hent cache-statistik
GET /api/cache/stats

# Ryd alle caches
DELETE /api/cache/stats
```

Eksempel på svar:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Latenpåvirkning

Et HIT fra en semantisk cache leverer svaret fra cachen **uden et upstream-kald**, så den rapporterede `X-OmniRoute-Response-Latency` er tæt på nul (uanset den oprindelige upstream-latens). Latensfølsomme klienter (benchmarking, p50/p99-overvågning) bør kontrollere svarheaderen `X-OmniRoute-Cache-Latency`:

| Værdi       | Betydning                                                           |
| ----------- | ------------------------------------------------------------------- |
| `synthetic` | Svar leveret fra cache; latenstiden er ikke den reelle upstream-tid |
| _(absent)_  | Svar fra et reelt upstream-kald                                     |

### Deaktivering af cache pr. nøgle

API-nøgler kan fravælge læsning fra den semantiske cache via `cacheDefaultMode`:

| Værdi    | Adfærd                                            |
| -------- | ------------------------------------------------- |
| `legacy` | Normal cacheadfærd (standard)                     |
| `bypass` | Spring cacheopslag helt over; kald altid upstream |

Indstil dette ved oprettelse af nøglen (`POST /api/keys`) eller ved opdatering (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Deaktivering af cache pr. anmodning

Enhver anmodning kan omgå cachen uanset nøgleindstillingerne:

```
X-OmniRoute-No-Cache: true
```

## CLIProxyAPI-kompatibilitet til administration

OmniRoute besvarer de tre administrationsendepunkter for [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI), som anvendelsesdashboards kalder for at læse abonnementsgrænser for Claude og Codex (f.eks. T3 Codes `cliproxy`-kilde til anvendelsesgrænser). Angiv klientens basis-URL til OmniRoute, og brug en API-nøgle med scopet `manage` som administrationsnøgle. Ruterne leveres på `/v0/management/*` og `/api/v0/management/*`.

| Metode | Sti                          | Beskrivelse                                                                                                                              |
| ------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | Claude- og Codex OAuth-forbindelser som `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Ingen tokens             |
| POST   | `/v0/management/api-call`    | Body `{ auth_index, method, url, header?, data? }`. Sender én tilladt anmodning med kontoens token og returnerer `{ status_code, body }` |
| POST   | `/v0/management/reset-quota` | Body `{ auth_index }`. Rydder forbindelsens cooldown, modellåsninger og Codex' cooldowns pr. scope for én konto                          |

- `auth_index` er OmniRoute-forbindelsens id. `provider` er `claude` eller `codex` (kun OAuth-forbindelser; API-nøgleudbyderen `anthropic` vises ikke). For Codex er `id_token.chatgpt_account_id` det gemte workspace-id, og `plan_type` den gemte plan.
- `api-call` er ikke en generisk proxy. Den accepterer kun Claude `GET
https://api.anthropic.com/api/oauth/usage` og Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` samt
  `POST .../wham/rate-limit-reset-credits/consume`, og kun for en konto hos den tilsvarende
  udbyder. Alt andet returnerer `403` uden at kontakte upstream. Den kaldendes
  `Authorization`-header (inklusive `$TOKEN$`-pladsholderen) ignoreres: OmniRoute indsætter
  forbindelsens access-token, opdaterer det først, når det nærmer sig udløb, og videresender kun
  tilladte headere (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`;
  `Accept`, `Content-Type`). En manglende `Chatgpt-Account-Id` bruger som standard det gemte workspace-id.
  Anmodninger får timeout efter 15 sekunder og bruger forbindelsens proxy.
- `reset-quota` ændrer ikke terminaltilstande (banned, expired, credits_exhausted). En ukendt
  `auth_index` returnerer `404`.

**Godkendelse:** Dashboard-session eller en API-nøgle med scopet `manage` kræves, også når login er deaktiveret (stierne findes i `ALWAYS_PROTECTED_API_PATHS`). Nøgler, der kun kan bruges til inferens, får `403`. Kilde: `src/lib/cliproxyCompat/managementApi.ts`.

For synced/imported modeller accepterer `PUT /api/provider-models` `provider`, `modelId` og `maxOutputTokenOverride`: et positivt heltal sætter det manuelle output-token-loft, og `null` rydder det for at gendanne standarden. `GET /api/provider-models?provider=<provider>` returnerer disse værdier i `modelOutputOverrides`, inklusive modeller uden en tilpasset modelrække. På en kompatibel udbyderknude gemmer skrivestierne (`POST`, `PUT`, `PATCH`, `DELETE` og `/api/provider-models/validate-and-add`) model-id'et som det blotte opstrøms-id: et id indsat fra en præfiksliste har en hvilken som helst ledende stak af nodens eget præfiks kollapset, og svar ekko det lagrede id. Kanoniske udbyderes skåret id (f.eks. `nvidia/nemotron-…`) gemmes ordret. `/v1/models` udsender aldrig et stablet `<prefix>/<prefix>/<model>` -id.

Custom Chat Completions noder tilpasser eksplicitte begrundelsesopt-outs til upstream backend. En vellykket forbindelsestest vælger automatisk chat-skabelonkontroller for hver eksakt model ID hvis `/models` indtastning beviser en anerkendt `owned_by` værdi: `vllm`, `sglang` eller `llamacpp`. Gennemsigtige OpenAI-kompatible indpakninger kan bevare den oprindelige modelindgang inde i et indlejret `openai` objekt; detektion følger op til tre sådanne konvolutter. Modeller med manglende, ukendt eller modstridende ejerskab bevarer almindelig OpenAI adfærd. Detektion genbruger den eksisterende kataloganmodning, genererer ingen færdiggørelsestokens og ugyldiggøres, når forbindelsens slutpunkt ændres.

For at fastgøre adfærden for en backend, der ikke afslører disse metadata, skal du bruge den eksisterende delvise udbyderopdatering API:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Send den krop med `PUT /api/providers/<connection-id>`. På den forbindelse sendes en eksplicit ræsonnement af `none` som `chat_template_kwargs.thinking=false` og `chat_template_kwargs.enable_thinking=false`. Eksplicitte native skabelonværdier forbliver autoritative, medmindre en ræsonnementsregel på serversiden fremtvinger en indsats. Indstillingen gælder kun, når en brugerdefineret OpenAI-kompatibel forbindelse sender en chat-afslutningstekst; Svaranmodninger og almindelige udbydere beholder deres oprindelige anmodningsform. Indstil `reasoningControl` til `openai` for at tvinge almindelig OpenAI `reasoning_effort` gennemgang, eller udelad it/set den til `null` for at bruge automatisk detektion.

Claude Code auto-mode classifier anmoder om standard native thinking til deaktiveret, når de ikke indeholder nogen eksplicitte ræsonnement kontroller. Detektion bruger klassifikatorens systemmarkør i Claude-formatanmodninger, ikke modelnavne eller færdiggørelsesgrænser. Eksplicitte kropskontroller, understøttede effort/thinking headere, routingregler og løst modelindsats bevarer deres eksisterende prioritet. Begge klassificeringsstadier bevarer deres prompter, fuldførelsesgrænser, stopsekvenser og rigtige upstream-tilladelsesdomme; anden fase kan stadig producere sin ønskede synlige begrundelse som almindelig tekst.

#### Modelgrænse herkomst

`GET /api/models?withLimits=1` (også `true`; `0`/`false` eller udeladelse af det bevarer standardnyttelasten uændret) tilføjer `contextWindow`, `maxInputTokens`, `maxOutputTokens` og et `capsSource` objekt til hver modelrække. `capsSource` navngiver reglen, der leverede hver grænse, så en overraskende grænse (for eksempel 128k på en 1M model) kan spores til dens oprindelse. De løste værdier er de samme, som routing bruger; flaget tilføjer kun felter og ændrer aldrig en værdi. Enhver anden `withLimits` værdi afvises med `400`.

| `override:context`                           | Vedvarende tilsidesættelse af kontekstvindue (`model_context_overrides`)          |
| `override:max_input` / `override:max_output` | Vedvarende tilsidesættelse af `max_input_tokens` / `max_output_tokens` -kapacitet |
| `static-authoritative:<provider>/<model>`    | Statisk autoritativ kontekst-vinduetabel                                          |
| `synced:<provider>/<model>`                  | models.dev synkroniseret funktionsrække                                           |

### Drill-down videoramme

`GET /api/v1/video-bridge/drilldown` læser et lejer-bundet uigennemsigtigt håndtag, der returneres i `x-omniroute-video-drilldown` efter en eksplicit godkendt Video Bridge-anmodning. Både læser og `DELETE` kræver altid en gyldig API nøgle og operatørens uafhængige `modalityBridgeVideoDrilldownRemoteEnabled` tilladelse. Produktionsfastholdelse kræver desuden `modalityBridgeVideoDrilldownEnabled` og strenge per-part `drilldown: true`. Hvis nøglen har en ikke-tom slutpunkttilladelsesliste, skal den inkludere `video` for både GET og DELETE, uanset om den, der ringer, bruger `/v1` eller `/api/v1`.

GET -forespørgsel: påkrævet `handle`; valgfri `variant` (`preview`, `standard`, `detail`), `limit` (1-8; legacy `frames` accepteres, men kan ikke kombineres med `limit`), nul-baseret `page` og `start`/`end` sekunder. Når begge fokusgrænser er angivet, skal `end` være større end `start`. Duplicate/unknown forespørgselsnøgler afvises. Succesfulde svar indeholder `derivation`, `durationSeconds`, `frames`, `hasMore`, `page`, `variant` og valgfri `focusWindow`; no-store JSON er begrænset til 32 MiB inklusive Base64. Overdimensioneret output returnerer 413; anmod om færre rammer.

`DELETE /api/v1/video-bridge/drilldown?handle=...` returnerer `{ "removed": 0|1 }`. Ukendt, udløbet og krydsnøgle GETs er 404-svar, der ikke kan skelnes; cross-key DELETE kan ikke fjerne ejerens indtastning. Deaktiveret adgang returnerer 403, missing/invalid -godkendelse 401, ugyldige forespørgsler 400, annullering 499 og midlertidige fejl 503. Håndtagene er proceslokale, udløber efter ti minutter og overlever ikke en genstart. Nye håndtag bruger `v1.` plus et 32-byte tilfældigt Base64URL token; kun token-hashes bevares. Legacy 64-hex tokens forbliver syntaktisk læsbare for kompatibilitet. Se [videobroens autoværn](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets) for oplysninger om samtykke, kvoter og variantafledning.

### Version og udgivelseskanal

```bash
GET /api/system/version
```

Loopback-kun administrationsrute (admin godkendelse). Returnerer den kørende version, den seneste offentliggjorte version og status for automatisk opdatering. `releaseChannel` og `channels` er additive felter (skinne 3.8.54); `channel` beholder sin betydning — den implementeringstilstand, som dashboardopdateringen bruger (`npm`, `source` eller `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-kanal for den kørende build: `nightly` for `-nightly.*` versioner, `next` for andre pre-releases (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` for en stabil version af en ældre dur end `channels.latest`, ellers `latest`. Samme regler som `scripts/release/dist-tag.mjs`, der vælger npm dist-tagget på udgivelsestidspunktet.
- `channels` — publicerede head of hver dist-tag, fra `npm view omniroute dist-tags` (registry HTTP fallback), cachelagret med den samme 10-minutters TTL som `latest`. `latest` er altid til stede (falder tilbage til `latest` feltet, derefter `"unavailable"`); `next`, `nightly` og `lts` vises kun, når det dist-tag findes. En `Cache-Control: no-cache` -anmodning opdaterer begge opslag.

Kanalmodellen (`latest` = v3 indtil 4.0 GA, `next` = rc, `nightly` = `develop` builds, `lts` = v3 patches efter 4.0 GA) er beskrevet i `docs/ops/RELEASE_STRATEGY.md`.

## Lydtransskription

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Transskriber lydfiler ved hjælp af en konfigureret STT-udbyder. Det første sti-segment
vælger den native udbyder (`openai/…`, `deepgram/…`). Gateways, der
videredistribuerer en anden leverandørs model, bruger et kvalificeret id
(`openrouter/deepgram/nova-3`).

**Anmodning:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Svar:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Eksempler på model-id'er:** `openai/whisper-1` (kræver en OpenAI-nøgle),
`openrouter/deepgram/nova-3` (kræver en OpenRouter-nøgle),
`deepgram/nova-3` (kræver en native Deepgram-nøgle). En anmodning med
`deepgram/nova-3` alene bruger **ikke** OpenRouter.

**Understøttede formater:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** filbaseret transskription via Gemini Live
WebSocket (kræver en Gemini API-nøgle). Uploaden konverteres til 16 kHz mono-PCM med `ffmpeg`
(skal være på `PATH`, medmindre filen allerede er en 16 kHz mono-PCM-WAV), streames til sessionen, og
den færdigbehandlede tekst returneres som `{ "text": "..." }`. Valgfrie formularfelter for `language` og
`prompt` videresendes. Begrænsninger: uploads over 25 MiB eller afkodet lyd, der varer længere end 10 minutter, svarer
med `413`; en konvertering, der kører længere end 60 sekunder, afsluttes og svarer med `504`. API-nøglen sendes
kun i headeren `x-goog-api-key`, aldrig i WebSocket-URL'en.

## Tokenbegrænsninger

**Token**-budgetter pr. API-nøgle (adskilt fra det USD-baserede budget ovenfor). Håndhæves inline i request-stien: når en nøgles forbrug i det aktuelle vindue når dens grænse, afvises requests med `429 Too Many Requests`. Begrænsninger kan afgrænses til en specifik `model`, en `provider` eller anvendes `global`t på tværs af nøglen; når flere begrænsninger matcher en request, vinder den mest restriktive.

```bash
# Vis en nøgles tokenbegrænsninger (inkluderer live-forbrug i vinduet)
GET /api/usage/token-limits?apiKeyId=key-123

# Opret eller opdater en tokenbegrænsning
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Slet en tokenbegrænsning efter id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Skemanoter** (`setTokenLimitSchema`): `apiKeyId` og `scopeType` (`model` | `provider` | `global`) er påkrævede. `scopeValue` er påkrævet, medmindre `scopeType` er `global` (f.eks. et model-id for `model`-afgrænsning eller et provider-id for `provider`-afgrænsning). `tokenLimit` skal være et positivt heltal (konverteres fra en streng). Valgfrit: `id` (udelad for at oprette, angiv for at opdatere), `resetInterval` (`daily` | `weekly` | `monthly`, standard er `monthly`), `resetTime` (`HH:MM`), `enabled` (standard er `true`). `GET`-svar udvider hver begrænsning med `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` og `nextResetAt`. Dette er et endpoint i management-klassen (godkendelse håndhæves centralt af authz-pipelinen).

## Behandling af requests

1. Klienten sender en request til `/v1/*`
2. Route-handleren kalder `handleChat`, `handleEmbedding`, `handleAudioTranscription` eller `handleImageGeneration`
3. Modellen resolveres (direkte provider/model eller alias/combo)
4. Legitimationsoplysninger udvælges fra den lokale database med filtrering efter kontotilgængelighed
5. For chat kontrollerer `handleChatCore` den semantiske/signaturbaserede cache og resolver combo-komprimeringsindstillinger
6. Proaktiv komprimering kører før provider-oversættelse, når den er aktiveret (`lite`, Caveman, RTK eller stablet)
7. Provider-eksekutoren sender en upstream-request
8. Svaret oversættes tilbage til klientformat (chat) eller returneres uændret (embeddings/images/audio)
9. Forbrug, komprimeringsanalyse og request-logge registreres
10. Fallback anvendes ved fejl i henhold til combo-reglerne

Fuld arkitekturreference: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Modstandsdygtighed (udvidet)

OmniRoute viser tre uafhængige mekanismer til midlertidige fejl; administrationsendepunkterne nedenfor giver operatører mulighed for at læse og tilsidesætte dem:

| Omfang             | Tilstandslagring                          | Læs                                       | Nulstil / ryd                                    |
| ------------------ | ----------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| Udbyderafbryder    | `domain_circuit_breakers` + in-memory     | `/api/monitoring/health`                  | `POST /api/resilience/reset`                     |
| Forbindelseskøling | `rateLimitedUntil` på udbyderforbindelser | `/api/rate-limits`, `/api/providers/[id]` | (genaktiveres efter behov; ryd via provider PUT) |
| Modellås           | In-memory-modeltilgængelighedsregister    | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`         |

`PATCH /api/resilience` accepterer tilsidesættelser af udbyderafbrydere under `providerBreaker.oauth` og `providerBreaker.apikey`. Hver profil understøtter `degradationThreshold`, `failureThreshold` og `resetTimeoutMs`; de samme felter vises i Dashboard → Indstillinger → Modstandsdygtighed.

```bash
# Ryd en enkelt modellås
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Ryd alle låse
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Se den fulde konceptuelle reference og standardværdierne for afbrydere i [`CLAUDE.md`](../../CLAUDE.md) → "Kørselstidstilstand for modstandsdygtighed" og [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Kø for hastighedsbegrænsning og sikkerhedsnet til automatisk aktivering

- **Understøttet skrivevej**: `POST /api/rate-limits` med body `{"connectionId": "<id>", "enabled": true|false}` er det understøttede administrationsendepunkt til at slå beskyttelse mod hastighedsbegrænsning til eller fra for en forbindelse. `PUT /api/providers/[id]` ændrer eller skifter bevidst ikke `rateLimitProtection` (#11278).
- **Semantik for `enabled: false`**: Indstillingen `enabled: false` fjerner eksplicit beskyttelse for forbindelsen, men **fravælger ikke** en aktiv API-nøgleforbindelse fra det globale sikkerhedsnet til automatisk aktivering (`autoEnableApiKeyProviders = true`). I `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts` er `false` og `undefined` ækvivalente; aktive API-nøgleforbindelser uden eksplicit beskyttelse forbliver beskyttet af sikkerhedsnettet til automatisk aktivering.
- **Global deaktivering**: Hvis API-nøgleforbindelser skal køre uden køer til hastighedsbegrænsning, skal sikkerhedsnettet deaktiveres globalt via `RATE_LIMIT_AUTO_ENABLE=false` (env) eller `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Indstillinger → Modstandsdygtighed / `PATCH /api/resilience`).

Understøttede metoder (alle kræver, at `settings.a2aEnabled` er aktiveret):

| Method           | Beskrivelse                                                             |
| ---------------- | ----------------------------------------------------------------------- |
| `message/send`   | Synkron udførelse af en skill; returnerer `{task, artifacts, metadata}` |
| `message/stream` | Streamet SSE-udførelse af det samme skill-sæt                           |
| `tasks/get`      | Hent en task efter `taskId`                                             |
| `tasks/cancel`   | Annuller en task efter `taskId`                                         |

Indbyggede skills: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

## Godkendelse

Se [Godkendelse af administration](../guides/MANAGEMENT-AUTH.md) for de fire
legitimationsfamilier (dashboard-session, lokal CLI-token, `oma_live_…` Access Token, API-nøgle med manage-scope), og hvordan de adskiller sig fra inferensnøgler.

- Dashboard-ruter (`/dashboard/*`) bruger cookien `auth_token`
- Login bruger den gemte adgangskode-hash; falder tilbage til `INITIAL_PASSWORD`
- `requireLogin` kan slås til og fra via `/api/settings/require-login`
- Ruter under `/v1/*` kræver valgfrit en Bearer-API-nøgle, når `REQUIRE_API_KEY=true`
- "management token" / "management-scoped API key" i denne reference betyder en af familierne i den vejledning — ikke en udefineret ekstra hemmelighedstype

> **Breaking change (v3.8.0)** — `/api/v1/agents/tasks/*` og administrationsendepunkterne for cooldown kræver nu **management auth** (dashboard-cookien `auth_token` eller en API-nøgle med management-scope). Klienter, der tidligere kaldte disse ruter uden godkendelse, vil modtage `401 Unauthorized`. Se committen `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
