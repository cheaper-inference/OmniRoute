ይህን መመሪያ በመጠቀም ለpull request አነስተኛውን አስተማማኝ የልማት ዑደት ይምረጡ። ይህ ከዚህ በታች የተገናኙትን
ለየአካባቢው የተለዩ የአርክቴክቸርና የደህንነት ሰነዶች አይተካም፤ ይልቁንም እያንዳንዱን የተለመደ
የለውጥ ዓይነት ከውሎቹ፣ ከተኮሩ ፍተሻዎቹ እና ከCI ሽፋኑ ጋር ያገናኛል።

## እያንዳንዱ ለውጥ የሚከተለው መንገድ

1. **አርትዖት ከመጀመርዎ በፊት መሠረቱን ይምረጡ።** ከፍተኛውን ንቁ `release/v*` branch ይፈልጉ እና ከ
   tip ላይ branch ይፍጠሩ። `main`ን ሳይሆን ያንን branch ዒላማ ያድርጉ። የrelease freeze በሥራ ላይ ከሆነ፣ የታገደውን
   branch ዒላማ አያድርጉ፤ በ
   [የBranch እና Release ሞዴል](BRANCHING_MODEL.md) ውስጥ የተገለጸውን ቀጣዩን ንቁ ዑደት ይጠቀሙ።
2. **ውሎቹን ይሰይሙ።** ለውጡ የሚነካቸውን እያንዳንዱን catalog፣ schema፣ የተፈጠረ artifact፣ ይፋዊ API ወይም የተጠቃሚ
   interface ይለዩ። ከዚህ በታች ያለው ሰንጠረዥ ዝቅተኛውን የመነሻ ስብስብ ያቀርባል።
3. **የተኮሩ tests ይጻፉ ወይም ያዘምኑ።** በ`src/`፣ `open-sse/`፣ `electron/` ወይም
   `bin/` ውስጥ ያሉ የproduction ለውጦች በተመሳሳዩ PR ውስጥ automated test ያስፈልጋቸዋል። ባህሪውን የሚያረጋግጡትን አነስተኛዎቹን test files ያስኪዱ፣
   ከዚያም የተዘረዘሩትን የተኮሩ gates ያስኪዱ።
4. **CI ሰፊውን matrix እንዲያስኬድ ያድርጉ።** ሙሉዎቹ unit shards፣ Vitest፣ coverage ratchet እና
   production build በPR ላይ ይሰራሉ። ሰፊ suiteን locally ያስኪዱት የተኮረ failure ሰፋ ያለ ተጽዕኖ እንዳለ ሲያመለክት
   ወይም ለውጡ በበርካታ subsystems ላይ ሲሰፋ ብቻ ነው።
5. **ከreview በፊት ያስታርቁ።** ንቁውን base fetch ያድርጉ፣ አዲሶቹን commits እና ከእሱ ጋር ሲነጻጸር የእርስዎን diff ይመርምሩ፣
   ከዚያም በcontributor workflow መሠረት baseን rebase ወይም merge ያድርጉ። የgenerated-file
   እና catalog conflictsን ከምንጫቸው ይፍቱ፣ እንደገና ያመንጩዋቸው፣ የተኮረውን ዑደት እንደገና ያስኪዱ እና
   PR አሁንም ንቁውን release branch ዒላማ ማድረጉን ያረጋግጡ።
6. **ማስረጃውን ይመዝግቡ።** በPR template ውስጥ ያስኬዷቸውን commands፣ የታከለ ወይም የተለወጠ እያንዳንዱን test file፣
   migrations ወይም feature flags እና አሁንም በመጠባበቅ ላይ ያለ CI-only validation ይዘርዝሩ።

## በለውጥ ዓይነት የተከፋፈሉ Golden paths

ከዚህ በታች ያሉት commands ዝቅተኛዎቹ የተኮሩ ፍተሻዎች ናቸው፤ እርስዎ የለወጡትን ባህሪ በቀጥታ የሚሸፍን test
ለመዝለል ፈቃድ አይደሉም።

### Provider

**ውሎች**

- በ`src/shared/constants/providers/` ውስጥ ያለው የProvider ትርጉም እና በ
  `src/shared/constants/providers.ts` ውስጥ ያለው composition።
- በ`open-sse/config/providerRegistry.ts` ወይም ከእሱ በተወጡ registry files ውስጥ ያሉ Models እና capabilities።
- Executor/translator selection፣ OAuth ወይም API-key configuration፣ dashboard assets እና በሚመለከተው ጊዜ generated
  provider reference።
- Public credentials `resolvePublicCred()`ን መጠቀም አለባቸው፤ error responses ደግሞ የጋራ sanitized
  error helpersን መጠቀም አለባቸው። `docs/security/PUBLIC_CREDS.md`ን (git፤ ወደ `/docs` አይጠናቀርም) እና
  [Error Sanitization](../security/ERROR_SANITIZATION.md)ን ይመልከቱ።

**የተኮረ ዑደት**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog ሲለወጥ፤ generated diffን commit ያድርጉ
npm run lint
```

እንዲሁም የተነካውን እያንዳንዱን request family ይፈትሹ፦ chat፣ Responses፣ images፣ embeddings፣ audio ወይም video።
የተፈጠሩ catalog እና golden diffsን እንደ contract changes ይገምግሙ፤ በጭፍን አይቀበሏቸው።

### Routing

**ውሎች**

- በ`src/shared/constants/routingStrategies.ts` ውስጥ ያሉ Public strategy values እና UI metadata።
- በ`open-sse/services/combo.ts` እና `open-sse/services/combo/` ስር ያሉ Dispatch እና ordering።
- Combo schemas፣ persistence፣ resilience state፣ model capabilities እና API/UI controls።
- ባህሪው ሲለወጥ [Auto-Combo Engine](../routing/AUTO-COMBO.md) እና resilience documentation።

**የተኮረ ዑደት**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # የstrategy ወይም dispatch ለውጦች
npm run check:known-symbols      # የstrategy registration ለውጦች
npm run lint
```

Deterministic mocked-upstream testsን locally ይጠቀሙ። Live combo smokes credentials ያስፈልጋቸዋል እና
manual ናቸው፤ የCI ምትክ አይደሉም።

### UI / UX

**ውሎች**

- በ`src/app/` እና
  `src/shared/components/` ስር ያሉ Next.js route/page እና shared component boundaries።
- API response shapes፣ loading/empty/error states፣ የkeyboard እና screen-reader ባህሪ፣
  responsive layout፣ theming እና locale expansion።
- በ`src/i18n/messages/en.json` ውስጥ ያሉ English UI source strings፤ አዲስ user-facing copyን hard-code አያድርጉ።

**የተኮረ ዑደት**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ለinteraction ወይም visual changes appን ያስኪዱ እና ጠባብም ሆነ ሰፊ viewportsን ይፈትሹ። CI
production buildን እና ሰፋ ያሉ suitesን ያስኬዳል፤ visual behavior ግን አሁንም ለለውጡ ተስማሚ የሆነ የተኮረ component፣ Playwright
ወይም በሰነድ የተመዘገበ manual check ያስፈልገዋል።

### i18n

**ውሎች**

- `src/i18n/messages/en.json` የUI source ነው፤ `config/i18n.json` ደግሞ የlocale source ነው።
- CLI catalogs በ`bin/cli/locales/` ስር ተለይተው ይገኛሉ።
- ICU placeholders እና tagsን በትክክል እንዳሉ ያቆዩ። የproduct/provider/model ስሞችን፣
  protocol እና header ስሞችን፣ commandsን፣ code/JSON identifiersን፣ URLsን፣ environment variablesን ወይም
  እንደ `OmniRoute`፣ `OAuth`፣ `MCP` እና `A2A` ያሉ protected termsን አይተርጉሙ። የአሁኑ source list
  `scripts/i18n/glossary/protected-terms.json` ነው።

**የተኮረ ዑደት**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # የCLI strings/catalogs ሲለወጡ
npm run lint
```

ይህ ለነባሩ system መመሪያ ነው፤ tooling ወይም key modelን ለማስፋት ግብዣ አይደለም።
ተተኪው system እየተነደፈ ባለበት ጊዜ i18n patchesን ጥቃቅንና የተወሰኑ ያድርጉ። ተግባሩ generated translationsን በግልጽ ካልጠየቀ እና
የተገኘውን diff ካልገመገሙ፣ external servicesን የሚጠሩ translation
commandsን አያስኪዱ።

### CLI

**ውሎች**

- በ`bin/cli/` ውስጥ ያሉ ይፋዊ ትዕዛዞችና flags፣ የሚመነጩ API ትዕዛዞች፣ exit codes፣ stdout/stderr እና
  የJSON ውጤት ቅርጾች፣ የconfig/environment ባህሪ እና በpackage ውስጥ የተካተቱ ፋይሎች።
- ለCLI ተጠቃሚ የሚታዩ ጽሑፎች የCLI i18n layerን መጠቀም እና የ`en`/`pt-BR` catalogsን የተመሳሰሉ አድርገው መጠበቅ አለባቸው።
- Nodeን እንደሚደገፍ runtime እና ይፋ የወጣውን binary contract ይጠብቁ።

**ያተኮረ ዑደት**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # የተመነጩ/የተጠቀለሉ CLI ለውጦች
npm run check:pack-policy     # የpackage surface ለውጦች
npm run lint
```

ባህሪው በparsing፣ በፋይሎች ወይም በexit status ላይ ሲመረኮዝ፣ ትክክለኛውን ትዕዛዝ በጊዜያዊ data directory ውስጥ ይጠቀሙ። CI ሰፋ ያሉትን የpackage artifact እና ecosystem ፍተሻዎች ያከናውናል።

### Database

**ውሎች**

- በ`src/lib/db/` ስር ያሉ domain modules፤ የተወሰኑ modulesን በቀጥታ import ያድርጉ (የቀድሞው `localDb.ts` re-export layer ተወግዷል)።
- በ`src/lib/db/migrations/` ስር ያሉ ቁጥር የተሰጣቸው፣ idempotent የSQL migrations፣ transaction safety፣ upgrade
  behavior፣ indexes እና በschemaው የሚነካ እያንዳንዱ caller።
- Routes እና handlers በቀጥታ raw SQL ፈጽሞ አያስኬዱም።

**ያተኮረ ዑደት**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migration ሲጨምሩ አዲስ databaseን እና ከቀድሞው schema የሚደረግ upgradeን ሁለቱንም ይፈትሹ። የDatabase tests በcleanup ጊዜ handlesን መዝጋት እና `resetDbInstance()`ን መጥራት አለባቸው። የbest-effort Bun adapter path ሲቀየር ብቻ `npm run test:bun:db`ን ያስኪዱ፤ Node ዋነኛው የታመነ መለኪያ ሆኖ ይቆያል።

### Build / deploy

**ውሎች**

- Root እና workspace manifests/lockfile፣ `scripts/build/`፣ Next.js standalone assembly፣ የ`dist/`
  package ይዘቶች፣ የElectron platform metadata፣ CI workflows እና deployment sentinels።
- የሚደገፉ የNode ranges እና በ`CLAUDE.md` ውስጥ ያለው allow-listed የBun አጠቃቀም ሳይለወጡ መቆየት አለባቸው።
- Build artifacts በversion control ያልተከታተሉ ሆነው ይቆያሉ፤ የdependency፣ license፣ workflow እና package policies ተፈጻሚ ናቸው።

**ያተኮረ ዑደት**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # የdependency ወይም lockfile ለውጦች
npm run check:pack-policy      # ይፋ የሚወጣው የpackage surface ለውጦች
npm run lint
```

ለውጡ compilationን፣ standalone assemblyን፣ assetsን ወይም runtime bundlingን ሲነካ ብቻ `npm run build`ን በአካባቢዎ ያስኪዱ። `npm run build:release`ን ለrelease/deploy validation ብቻ ይጠቀሙ። የCI build የመጨረሻው cross-platform signal ነው፤ platform-specific የElectron ለውጦች ተመሳሳዩን ያተኮረ build ወይም smoke evidence ያስፈልጋቸዋል።

## ለጋራ ማሽን የገንቢ ስክሪፕቶች

ሌሎች ክፍለ-ጊዜዎች ንቁ በሆኑበት devbox ላይ ያለውን የአካባቢ የሥራ ዑደት ሁለት የ`scripts/dev/` ረዳቶች ይተገብራሉ፦

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # ከmerge-base(HEAD, base)..HEAD የመጡ ፋይሎች
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # እነዚህ ፋይሎች ብቻ
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # የተነጠለ worktree፣ በትይዩ ለመጠቀም ደህንነቱ የተጠበቀ
```

- `typecheck-touched.sh` የተነኩትን `.ts/.tsx` ፋይሎች ብቻ በጊዜያዊ
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`፣ `types: ["node"]`፣ `noEmit`፣
  `incremental: false`) እና በ6 GB heap ስር typecheck ያደርጋል፤ ስለዚህ በከፍተኛ ጭነት ላይ ያለን ማሽን OOM
  የሚያደርገውን የመላው ፕሮጀክት `tsc -p tsconfig.json` ይተካል። በተነኩ ፋይሎች ውስጥ ያሉ ስህተቶችን ከአንድ የማጠቃለያ መስመር ጋር ያትማል፤ በተነኩ ፋይሎች ውስጥ
  ስህተቶች ካሉ `1`፣ ስህተቶቹ በተጫኑ ፋይሎች ውስጥ ብቻ ከሆኑ ወይም tsc
  ምርመራ ሳያቀርብ ከተቋረጠ `2` (በ`_artifacts/typecheck-touched/` ስር ስሙን የሚጠቅሰውን ምዝግብ ያንብቡ)፣ ስህተት
  ከሌለ `0` በማውጣት ይዘጋል። ጊዜያዊው tsconfig ሁልጊዜ ይወገዳል፤ ፈጽሞ commit አያድርጉት።
- `new-worktree.sh` በ`<git-common-dir>/omniroute-new-worktree.lock` ላይ የሚካሄዱ ተጓዳኝ አሂዶችን
  በተከታታይ ያስኬዳል (በነባሪ እስከ 600 s ይጠብቃል፣ የሚታይ መልዕክትም ያሳያል፤ የስክሪፕቱ ራስጌ
  override ማድረጊያውን ይገልጻል)፤ እንዲሁም worktree ከመፈጠሩ በፊት `git worktree add` ካልተሳካ
  የፈጠረውን branch ይመልሳል፣ ስለዚህ እንደገና ለመሞከር `git branch -D` ን በእጅ ማስኬድ
  አያስፈልግም። hard-linked የሆኑት `node_modules` እና የ`.husky/_` ቅጂ ሳይቀየሩ ይቀራሉ።

## የአካባቢ candidate ዑደት

የምንጭ ሙከራዎች የታሸገው artifact እንደሚነሳ ማረጋገጥ አይችሉም፤ የማሸጊያ ዝርዝሮች፣ የተቀነሱ dependencies
እና native binaries የሚወድቁት tarball ከተጫነና ከተጀመረ በኋላ ብቻ ነው። `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) በRFC #8084 ውስጥ ያለው አንድ ጊዜ ገንብቶ / አረጋግጦ / ወደ ምርት የማሳደግ ፍሰት
የአካባቢ ክፍል ነው፦ አንድ candidate ይገነባል፣ ያንኑ artifact ያረጋግጣል፣ የማውጫ
ስሞችን በመቀየር ወደ ምርት ያሳድገዋል፣ እና ወደ ምርት ያደገው slot የጤንነት ፍተሻውን ካላለፈ ወደነበረበት ይመልሰዋል።

```bash
npm run dev:candidate -- run --dry-run --json  # ዕቅዱን አትም፣ ምንም አትቀይር
npm run dev:candidate -- run                   # ገንባ + አረጋግጥ + ወደ ምርት አሳድግ፣ ራስ-ሰር መመለስ
npm run dev:candidate -- build                 # npm pack + ወደ _artifacts/candidate/<id>/ ጫን
npm run dev:candidate -- validate --id <id>    # በነጻ port ላይ አስነሳ፣ /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current፣ current → previous
npm run dev:candidate -- rollback              # current እና previous ን ቀያይር
npm run dev:candidate -- run --from-tarball <file.tgz>  # ሌላ ቦታ (CI) የተገነባን tarball እንደገና ተጠቀም
```

- **አንድ ጊዜ ይገንቡ።** `build` አሁን ያለውን tree ያሽጋል (`dist/server.js` ያስፈልገዋል፣ ስለዚህ መጀመሪያ
  `npm run build:release` ያስኪዱ) ወይም `--from-tarball` ን ይቀዳል፤ ከዚያም tarball ምንም `node_modules` ስለማይይዝ
  ወደተነጠለ npm prefix ይጭነዋል። id አጭሩ የ`HEAD`
  sha (tree ውስጥ የአካባቢ ለውጦች ሲኖሩ `-dirty`) ወይም ለtarball `tgz-<sha256>` ነው። አስቀድሞ
  የተገነባ clean id እንደገና ከመገንባት ይልቅ ዳግም ጥቅም ላይ ይውላል፤ እንደገና ለመገንባት `--force` ያስተላልፉ።
- **ምንጩን ሳይሆን package ን ያረጋግጡ።** `validate` የተጫነውን CLI
  (`serve --port <free port>`) በአዲስ `DATA_DIR=<candidate>/data`፣ በሐሰተኛ secrets እና የኦፕሬተሩ
  `OMNIROUTE_API_KEY`፣ `STORAGE_ENCRYPTION_KEY` እና `INITIAL_PASSWORD` ከenvironment ተወግደው
  ያስነሳል፤ በዚህም የአዲስ ጭነት keyless loopback posture ን ይፈትሻል።
  `GET /api/health` 200 እስኪመልስ ይጠብቃል፣ `GET /v1/models` 200 እንዲመልስ ይጠይቃል፣ የprocess group ን ያቆማል፣
  እና ውጤቱን ከtarball hash ጋር በ`validation.json` ውስጥ ይመዘግባል።
- **ያንኑ artifact ወደ ምርት ያሳድጉ።** `promote` ለአሁኑ
  tarball hash ያለፈ ማረጋገጫ የሌለውን candidate ይከለክላል። ነባሪው ንቁ slot `_artifacts/candidate/current` ነው፤ `--target <dir>`
  በዚያው filesystem ላይ ሌላ ማውጫ ይመርጣል፣ የቀድሞ slot ደግሞ `<dir>.previous` ነው።
  እያንዳንዱ የስም ለውጥ atomic ነው፤ በሂደቱ መካከል ችግር ከተፈጠረም አስቀድመው የተከናወኑትን የስም ለውጦች ይቀለብሳል።
- **ወደነበረበት ይመልሱ።** `run` ወደ ምርት ያደገውን slot እንደገና ያረጋግጣል፤ ያ ፍተሻ ካልተሳካ
  `current` እና `previous` ን ወደነበሩበት መልሶ ይቀያይራል። የመጀመሪያውን ማረጋገጫ የማያልፍ candidate በፍጹም ወደ ምርት አይተላለፍም።

ሁሉም ነገር gitignored በሆነው `_artifacts/candidate/` ስር ይጻፋል፤ አስቀድሞ ያለ OmniRoute
ጭነት እና የውሂብ ማውጫው ፈጽሞ አይነኩም። ወደ ምርት ያደገው CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ነው፤ ሲጠቀሙበት በራስዎ `DATA_DIR` ያስነሱት። የመውጫ ኮዶች፦ `0` ስኬት፣ `1` ያልተሳካ ማረጋገጫ ወይም ወደ ምርት ማሳደግ፣ `2` የአጠቃቀም ስህተት ወይም የጎደለ build።

## የማስታረቅ ማረጋገጫ ዝርዝር

ግምገማ ከመጠየቅዎ በፊት፦

- የPR መሠረት አሁንም ከፍተኛው ንቁ `release/v*` ቅርንጫፍ መሆኑን ያረጋግጡ።
- ያንን መሠረት fetch ያድርጉ እና ቅርንጫፍዎን ከፈጠሩ በኋላ የተጨመሩትን commits ይገምግሙ።
- ባለማወቅ የተፈጠሩ ወይም በራስ-ሰር የተመነጩ አላስፈላጊ ለውጦችን ለማግኘት `git diff <active-base>...HEAD`ን ይገምግሙ።
- ምንጩን በማዘመን እና ውጤቱን እንደገና በማመንጨት የካታሎግ እና የተመነጩ ሰነዶች ግጭቶችን ይፍቱ።
- ካስታረቁ በኋላ በPR መግለጫው ውስጥ የተዘረዘሩትን እያንዳንዱን የተወሰነ ሙከራ/መግቢያ እንደገና ያስኪዱ።
- ከተንቀሳቀሰ መሠረት ጋር ለማዛመድ ብቻ ማረጋገጫዎችን በፍጹም አያላሉ ወይም አስፈላጊ ሙከራዎችን አይተዉ።
