## npm Trusted Publishing (standard siden v3.8.51) — klargjort ved forespørsel, direkte som reserveløsning

`npm-publish.yml` publiserer som standard via **npm Trusted Publishing (OIDC)**:
`stage-npm`-jobben (GitHub-driftet) utveksler GitHubs id-token mot en kortvarig npm-
legitimasjon for den kjøringen — ingen langvarig npm-token i repositoriets hemmeligheter, ingen 2FA-forespørsel, proveniens vedlagt.
Dette er omgåelsen npm nå godkjenner etter hvert som tokener som hopper over 2FA, fases ut;
den gjenoppretter den helautomatiske flyten prosjektet hadde frem til v3.8.48, samtidig som
WS1.3-garantien opprettholdes (et lekket token kan ikke publisere alene — det finnes ikke noe token).

**Engangsoppsett (eier):** npmjs.com → pakken `omniroute` → Settings → _Trusted
Publisher_ → GitHub: eier `diegosouzapw`, repo `OmniRoute`, arbeidsflyt `npm-publish.yml`
(miljø: ingen). Frem til dette finnes, mislykkes det automatiske trinnet med `ENEEDAUTH`:
start arbeidsflyten på nytt med `publish_mode=staged` (nedenfor) eller `direct`.

### Trinnvis publisering (ved forespørsel — `publish_mode=staged`)

Arbeidsflyten npm-publish publiserer ikke lenger direkte: den starter den pakkede tarball-filen
(`check:pack-boot`) og kjører deretter `npm stage publish` — de nøyaktige bytene parkeres i
registeret og er **ikke installerbare** før eieren godkjenner dem. Den menneskelige 2FA-kontrollen er flyttet
til ETTER verifiseringen, ikke før den.

**Eierens flyt etter at arbeidsflyten blir grønn:**

1. `npm stage list omniroute` — finn trinn-ID-en (vises også i arbeidsflytsammendraget).
2. Verifiser de klargjorte bytene (anbefalt): `npm stage download <id>`, installer deretter den
   nedlastede tarball-filen i et midlertidig prefiks og start den (`npm run check:pack-boot` automatiserer
   den samme pakk→installer→start-vurderingen i CI).
3. `npm stage approve <id>` — 2FA-forespørselen ER publiseringen. `npm stage reject <id>` forkaster den.
4. Sikkerhetsnett etter publisering: verifikatoren etter publisering (WS1.4 i planen for v3.8.49) installerer den
   publiserte versjonen fra det offentlige registeret i en ren container og starter den.

**Reserveløsning for nødstilfeller:** `workflow_dispatch` med `publish_mode=direct` gjenoppretter den
eldre umiddelbare `npm publish`-flyten (brukes bare hvis selve klargjøringen ikke fungerer; dokumenter hvorfor).

**Engangsherding (eier, npmjs.com):** konfigurer Trusted Publisher for
`omniroute` i kun-klargjøringsmodus, slik at et lekket langvarig token ikke kan kjøre `npm publish`
direkte noe sted fra — CI kan bare klargjøre; bare eierens 2FA kan utgi.

**Prosedyre for ødelagte artefakter (uendret):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
som standardreaksjon (minutter, reversibelt); `npm unpublish` kun innenfor vinduet på 72 timer/ingen avhengige
og aldri som første tiltak. Docker: aldri overskriv en versjonstagg — tilbakerulling innebærer
å peke `latest` til den siste fungerende digesten.

**Docker Hub `latest` (påkrevd ved hver stabile SemVer-publisering):**
`docker-publish`-arbeidsflyten må tagge **både** `X.Y.Z` og, når
`should-promote-latest.sh` bekrefter at dette er den høyeste stabile SemVer-versjonen, `:latest`
med **samme digest**. Etter jobben: Hub-digesten for `latest` er lik den nye
SemVer-digesten, og `last_updated` er oppdatert. Ikke la `:latest` peke på en eldre
byggversjon mens utgivelsesnotatene omtaler rettelser som bare finnes i git. Compose-
hurtigstarter bruker `:latest`; GitOps bør fortsatt feste til `X.Y.Z`. Se
[Docker-utgivelseskanaler](../guides/DOCKER_GUIDE.md#release-channels) og #10317.

## Hurtigspor for kritiske feilrettinger (etikett `hotfix`)

En PR merket med `hotfix` hopper over den omfattende CI-matrisen (E2E med 9 deler, coverage ratchet,
quality-gate, quality-extended) og beholder de raske kontrollene med høy signalverdi: bygging,
enhetstestdeler, integrasjon, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
og oppstartstesten for tarball (`check:pack-boot`). Mål: grønt resultat på ≤15 min i stedet for ~33 min.

**Kriterier for bruk — alle fire må være oppfylt (modellert etter nødsporene til Chromium/VS Code/Node):**

1. **Alvorlighetsgrad**: produksjonen er ute av drift — en publisert artefakt krasjer ved oppstart / en
   sikkerhetsretting / alle brukere av utgivelsen er berørt. «Viktig» er ikke det samme som «ute av drift».
2. **Myndighet**: bare eieren av repositoriet bruker etiketten `hotfix`. Etiketten ER
   godkjenningen — den skal aldri brukes på eget initiativ i en kampanje-PR.
3. **Dokumentasjon**: PR-beskrivelsen lenker til den forrige fullstendig grønne, omfattende kjøringen (testpakken som
   de hoppede jobbene ellers ville validert på nytt), samt rettingens egen test som først feilet og deretter besto.
4. **Omfang**: kun cherry-pick — den minimale rettingen, ingen refaktoreringer, ingen medfølgende endringer.

Deknings-/ratchet-området som hoppes over, valideres på nytt av den neste fullstendige kjøringen på
utgivelsesgrenen (kontinuerlig grønn utgivelse) — sporet hopper over VENTING, aldri validering.
Endringer som kun gjelder tester (alle filer under `tests/`, ingen under `tests/e2e/`) hopper over E2E-
matrisen automatisk, uten noen etikett.

### Bygg layout

Depotet bruker tre distinkte utdatakataloger — blander dem aldri sammen:

| Katalog   | Hensikt                                                 | Sporet?          |
| --------- | ------------------------------------------------------- | ---------------- |
| `src/`    | Applikasjonskilde (TypeScript / TSX)                    | Ja               |
| `.build/` | Bygg mellomprodukter — `next build` -utgang (`distDir`) | Nei (gitignored) |
| `dist/`   | Sendbar npm-bunt — satt sammen av `assembleStandalone`  | Nei (gitignored) |

> **Operatørens merknad:** den eksterne VPS -bildekatalogen forblir `/usr/lib/node_modules/omniroute/app/`. Bare den** i repo** bygge utgang flyttet (`app/` → `dist/`). Deploy skills rsync `dist/` -innhold i den eksterne `app/` dir — ingen VPS -baneendringer kreves.

**Enkeltbyggende flyt:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Kjør NOT `npm run build` etterfulgt av en separat `npm run build:cli` for distribusjon av — bruk `npm run build:release` som gjør en ren gjenoppbygging av + sentinel i én kommando.

## 3.9.0 LTS-forgrening (øvd inn i 3.8.58)

Etter v3.8.59 er neste versjon 3.9.0, og dens spiss blir til to langsiktige grener:
`stable/v3` (v3 LTS-linjen, npm `latest`) og `develop` (v4, oppjustert til 4.0.0, npm
`nightly`). Gren-/kanalmodellen, fremoverportering og etiketter er beskrevet i
[RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md); planen finnes i [ROADMAP](../../ROADMAP.md) (fase 3). Forgreningen kjøres én gang;
3.8.58 øver inn hele prosessen på en fork, og 3.8.59 avsluttes med
[GO/NO-GO-sjekklisten](./LTS_GO_NO_GO.md).

### Prøvekjøring (skrivebeskyttet, trygg når som helst)

```bash
npm run release:dry-run-lts-cut                       # den virkelige forgreningen: 3.9.0 fra HEAD, forrige tagg v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # fest kilde-commiten
```

`scripts/release/dry-run-lts-cut.mjs` utfører ingenting: skriptet leser git og `gh` og skriver ut
hele sekvensen — forhåndsbetingelser (kilden kan slås opp, kilderepositoriet har full historikk —
en grunn klone kan ikke pushe `stable/v3`, mottakersiden avviser pakken ved den første
innskjøtede forelderen, så forgren fra en full klone eller kjør `git fetch --unshallow origin`
først — forrige tagg finnes, `package.json` har målversjonen, en `release-freeze`-sak er åpen, ingen åpen
`Release branch not green`-sak
på en eksisterende utgivelsesgren — en gren som ikke finnes, rapporterer `?` ukjent, aldri
grønn — Mergify-køen `release` er konfigurert (G11: `queue_rules`, `checks_timeout`,
etiketten `queue`), regelsettet `release/*` blokkerer fortsatt sletting og tvangspushing, og
`stable/v3` og `develop` finnes ikke ennå), de to grentrinnene, hvilke utløsere og
`if:`-betingelser for inaktive arbeidsflyter som blir sanne (og hvilke som fortsatt er sperret av en repositorievariabel eller
festet til det kanoniske repositoriet), de forventede dist-taggene (`latest` → 3.9.0, `next` og
`nightly` tomme) og tilbakerullingen. Avslutningskode `0` = `RESULT: READY`, `1` = en blokkerende forhåndsbetingelse
mislyktes (`✗`), `2` = bruksfeil. `--advisory <id,...>` nedgraderer en kontroll til en advarsel (`!`)
uten å skjule den.

Kjør prøvekjøringen for den virkelige forgreningen mens utgivelsesfrysingen for 3.9.0 fortsatt er aktiv — grenene
opprettes etter taggen og før fase 12c opphever frysingen.

### 3.8.58-øvelse (kun fork)

```bash
# 1. Prøvekjør på gjeldende spiss med øvelsesparametere
npm run release:dry-run-lts-cut -- --target-version 3.8.58 --previous-tag v3.8.57 \
  --advisory freeze,base-green

# 2. Kjør mot en FORK-fjernkilde (origin, eller en hvilken som helst fjernkilde med URL-en til det kanoniske
#    repositoriet, avvises; hvert trinn ber om bekreftelse i terminalen)
git remote add rehearsal https://github.com/<you>/OmniRoute.git
node scripts/release/dry-run-lts-cut.mjs --execute --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green

# 3. Test de inaktive arbeidsflytene i forken (workflow_dispatch der prøvekjøringen
#    rapporterer en binding til det kanoniske repositoriet), og rull deretter tilbake
node scripts/release/dry-run-lts-cut.mjs --execute --rollback --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green
```

Oppjusteringscommiten for develop bygges med git plumbing (arbeidstreet berøres ikke) og oppjusterer
de samme fem filene som en commit som åpner en syklus: `package.json`, `open-sse/package.json`,
`electron/package.json`, `package-lock.json` og `docs/openapi.yaml`. `[4.0.0]`-delen i
CHANGELOG og dens i18n-speil åpnes på `develop` etterpå, før grenens første
PR. Skriptet endrer aldri npm-dist-tagger — øv på disse med en midlertidig pakke.

### Forhåndsvisningsartefakt for PR (bygg én gang, promoter de samme bytene)

`.github/workflows/preview-artifact.yml` bygger én produksjonstarball fra hodet til en PR og
validerer nøyaktig dette bygget (#8084 del (a)). Kun PR-er fra samme repositorium; ingenting publiseres.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # eller legg til etiketten `preview-artifact`
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # installasjon av forhåndsvisning
```

Kjøringen utfører `npm ci`, `npm run build:release`, `npm run check:pack-artifact`, pakker
tarballen, kjører `npm run check:pack-boot` (falske hemmeligheter, midlertidig datamappe), pakker på nytt og
mislykkes med mindre kontrollsummen er identisk. Deretter registrerer den `artifact-identity.json` (hode-SHA, base-SHA,
låsfilhash, plattform, arkitektur, node ABI, bundler, byggpolicy —
`scripts/release/artifact-identity.mjs`) og attesterer tarballen i en separat jobb. Å promotere
en forhåndsvisning betyr å installere denne tarballen: bygg aldri på nytt fra kildekoden.

### Forgreningen (3.9.0, etter GO)

2. `npm run release:dry-run-lts-cut -- --from v3.9.0` skriver ut `RESULT: READY`.

   skriptet nekter å pushe til `origin`. For å gjenbruke en gjennomgått develop-commit kjører du
   `--execute`-øvelsen på 3.9.0-spissen mot forken din først; den skriver ut begge SHA-ene, og

## Tilbakerulling

Hvis utgivelsen har et kritisk problem:

1. `gh release edit vX.Y.Z --prerelease` (markerer den som ikke nyeste)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (bare hvis den ennå ikke er tatt i bruk av brukere)
3. Eller: hurtigretting på `release/vX.Y.0` → feilrettingsutgivelse `vX.Y.(Z+1)`
4. Kommuniser umiddelbart i GitHub Discussions og Discord

## Ufravikelige regler

- Aldri commit direkte til `main`
- Aldri bruk `git push --force` til `main`- eller `release/*`-grener
- Aldri hopp over Husky-hooks (`--no-verify`)
- Aldri commit hemmeligheter, påloggingsopplysninger eller `.env`-filer
- Kodedekningen må holde seg på ≥60/60/60/60 (setninger/linjer/funksjoner/grener)
- Inkluder eller oppdater alltid tester når du endrer produksjonskode i `src/`, `open-sse/`, `electron/` eller `bin/`
