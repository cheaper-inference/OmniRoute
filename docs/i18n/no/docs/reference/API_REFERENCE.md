Kjernereferanse for OmniRoute API-et. Den dekker det offentlige `/v1`-grensesnittet og de mest brukte administrasjonsendepunktene; den maskinlesbare [`docs/openapi.yaml`](../openapi.yaml) og rutetreet under `src/app/api/` er de uttømmende kildene.

For den fokuserte OpenAI-kompatible protokollen og matrisen over leverandørfunksjoner, se
[`OPENAI_COMPATIBILITY.md`](./OPENAI_COMPATIBILITY.md).

Hver distribusjon leverer sin egen kopi av spesifikasjonen på `/openapi.yaml`, generert fra `docs/openapi.yaml` under byggingen. Den inneholder byggets versjon og en relativ server-URL (`./`), slik at forespørsler forblir på verten som leverte dokumentet. Et verktøy som importerer den nedlastede filen, har ingen slik vert og trenger at basis-URL-en angis manuelt.

## Chat Completions

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Egendefinerte headere

| Header                   | Direction   | Description                                                                                                                                                                                                  |
| ------------------------ | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `X-OmniRoute-No-Cache`   | Forespørsel | Sett til `true` for å omgå hurtigbufferet                                                                                                                                                                    |
| `x-omniroute-no-memory`  | Forespørsel | Sett til `true` for å hoppe over injisering av minne + ferdigheter for denne forespørselen (speiler no-cache; unngår token-/kostnadsbelastningen per kall)                                                   |
| `X-OmniRoute-Progress`   | Forespørsel | Sett til `true` for fremdriftshendelser                                                                                                                                                                      |
| `X-Session-Id`           | Forespørsel | Klebrig øktnøkkel for ekstern økttilknytning                                                                                                                                                                 |
| `x_session_id`           | Forespørsel | Variant med understrek støttes også (direkte HTTP)                                                                                                                                                           |
| `X-OmniRoute-Session-Id` | Forespørsel | Økt-/samtaleetikett levert av klienten (mates også inn i minnet). Når den finnes, lagres den ordrett i `call_logs.session_tag` for kostnadstildeling per økt (#8249) — genereres aldri når den mangler       |
| `Idempotency-Key`        | Forespørsel | Dedupliseringsnøkkel (5 sekunders vindu)                                                                                                                                                                     |
| `X-Request-Id`           | Forespørsel | Alternativ dedupliseringsnøkkel                                                                                                                                                                              |
| `x-omniroute-connection` | Forespørsel | Fest en forespørsel til én modell til én leverandørtilkobling (konto) etter ID-en — se [Kontofesting per forespørsel](#account-pinning-per-request)                                                          |
| `X-OmniRoute-Cache`      | Svar        | `HIT` eller `MISS` (ikke-strømmende)                                                                                                                                                                         |
| `X-OmniRoute-Idempotent` | Svar        | `true` hvis deduplisert                                                                                                                                                                                      |
| `X-OmniRoute-Progress`   | Svar        | `enabled` hvis fremdriftssporing er aktiv                                                                                                                                                                    |
| `X-OmniRoute-Session-Id` | Svar        | Effektiv økt-ID brukt av OmniRoute                                                                                                                                                                           |
| `X-OmniRoute-Request-Id` | Svar        | Korrelasjons-ID for forespørselen (når kjent)                                                                                                                                                                |
| `X-OmniRoute-Version`    | Svar        | OmniRoute-byggversjon (alltid til stede)                                                                                                                                                                     |
| `X-OmniRoute-Cost-Saved` | Svar        | USD som hurtigbufferet sparte ved en HIT (kun hurtigbuffer-treff)                                                                                                                                            |
| `X-OmniRoute-Decision`   | Svar        | Ruting-spor: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` er kombinasjonsstrategien, eller `single` for en forespørsel som ikke er en kombinasjon) — alltid til stede i svar ved fullføring |

> Nginx-merknad: Hvis du er avhengig av overskrifter med understrek (for eksempel `x_session_id`), aktiver `underscores_in_headers on;`.

#### Kontofesting per forespørsel

Når en leverandør har flere tilkoblinger (kontoer eller nøkler), velger OmniRoute normalt én
gjennom strategien for kontovalg. En forespørsel kan i stedet feste én bestemt tilkobling
med overskriften `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Hvor finner du ID-en.** Åpne leverandørsiden i kontrollpanelet
  (**Dashboard → Providers → <provider>**) og klikk på `xxxxxxxx…`-ID-brikken på en tilkoblingsrad
  — den kopierer hele tilkoblings-ID-en.
- **Hvilke forespørsler bruker den.** Forespørsler til én modell (`provider/model`) på
  `/v1/chat/completions`, `/v1/messages` og `/v1/responses`. Kombinasjoner ignorerer headeren:
  fest en konto for hvert trinn i kombinasjonen via trinnets egen tilkobling.
- **Festingen er streng, ikke en preferanse.** Den festede tilkoblingen brukes utelukkende. En
  feil i forespørselen registrerer kontoens nedkjølingsperiode, men roterer **ikke** til en
  søsterkonto hos samme leverandør.
- **Nedkjøling og kvote frigjør festingen.** Mens den festede tilkoblingen er i nedkjøling,
  kvote er brukt opp eller tilkoblingen er blokkert av en kvotepolicy, faller senere forespørsler
  tilbake til leverandørens andre tilkoblinger, akkurat som ubundet trafikk.
- **Ukjente eller deaktiverte ID-er fører til feil.** En ID som ikke finnes i leverandørens aktive
  utvalg (slettet, deaktivert eller tilhører en annen leverandør) etterlater ingen kvalifisert
  konto, så forespørselen mislykkes i stedet for å bli rutet et annet sted uten varsel.

Claude Code sender egendefinerte headere gjennom `ANTHROPIC_CUSTOM_HEADERS`. Legg den i `env`-blokken
i `~/.claude/settings.json`, eller i en `.claude/settings.json` på prosjektnivå for å feste en
annen konto per prosjekt:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Kilde: `src/sse/handlers/chat.ts` (lesing av headeren), `src/sse/services/auth.ts` og
`src/sse/services/sessionAffinityPin.ts` (frigjøring av festingen og kontrollen av om den mangler i utvalget).

> **Headere for kostnadstelemetri:** svar uten strømming som lykkes, inneholder også `X-OmniRoute-*`-settet for kostnadstelemetri — `X-OmniRoute-Response-Cost` (USD, alltid 10 desimaler; `0.0000000000` for gratis eller ikke-prissatte forespørsler), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` og `X-OmniRoute-Fallback-Attempts` (bare når > 0), samt `X-OmniRoute-Request-Id` og `X-OmniRoute-Version`. Disse sendes av chat completions, `/v1/responses`, `/v1/messages` **og medieendepunktene** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` og `/v1/moderations` (alltid med kostnaden `0`). Mediekostnaden beregnes per modalitet (per bilde, per sekund, per tegn, per søkeenhet) når prissetting er tilgjengelig, ellers `0` (fail-open).

> **Semantikk for kostnad ved cache-treff:** Ved et treff i den semantiske hurtigbufferen (`X-OmniRoute-Cache-Hit: true`) foretas ingen oppstrømskall, så `X-OmniRoute-Response-Cost` er `0.0000000000` (den **inkrementelle** kostnaden ved å levere treffet). Den opprinnelige kostnaden / kostnaden som ellers ville ha påløpt, rapporteres separat i `X-OmniRoute-Cost-Saved`. Faktureringskonsumenter bør summere `X-OmniRoute-Response-Cost` (treff koster ingenting); hurtigbufferanalyse kan aggregere `X-OmniRoute-Cost-Saved`.

## Eksklusive administrerte sesjonsleieavtaler

Eksklusiv leie av administrerte sesjoner er en valgfri, klientuavhengig rutingskontrakt: én aktiv eier
har én kvalifisert OmniRoute-tilkobling. Den leier ikke en modell, krever ikke OAuth, identifiserer ikke
en bestemt klient og krever ikke en bestemt leverandør.

Den autentiserende API-nøkkelen må ha omfanget `lease:exclusive` og en uttrykkelig ikke-tom
`allowedConnections`-liste. Databasens mutasjonsgrense håndhever begge feltene samlet ved opprettelse
av nøkler og ved delvise oppdateringer.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Vellykkede svar på oppretting, fornyelse og frigivelse viser tidsstempler, `state` og den nøyaktige positive
`generation`, men aldri den valgte tilkoblingen eller legitimasjonen. Fornyelse og frigivelse oppgir
generasjonen i JSON-teksten:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

En aktiv leieeier kan eksplisitt be om personvernsikre visningsmetadata for sin nåværende binding:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Denne valgfrie statusoperasjonen er sikret av den ugjennomsiktige eieren, den autentiserte administrerte
API-nøkkelen og den nøyaktige aktive generasjonen i én databasetransaksjon. `displayName` er bare det
trimmede, konfigurerte tilkoblingsnavnet; det er `null` når det ikke finnes et trygt konfigurert navn.
OmniRoute erstatter aldri dette med en e-postadresse eller en generert kontoidentitet. Leverandørverdien
er en ikke-sensitiv visningsetikett og aldri en generert identifikator for en kompatibel leverandør.
Legitimasjon, tokens, informasjonskapsler, rå tilkoblings- eller API-nøkkel-ID-er, eier-hashverdier,
sikringshemmeligheter og interne rutingsdata er utelatt.

Oppslag med feil nøkkel, feil eier, foreldet generasjon, manglende, utløpt, frigitt eller ugyldiggjort
leieavtale returnerer alle den samme `409 LEASE_FENCE_STALE`-feilen uten tilkoblingsmetadata. En klient
som mottok svaret om kapasitetsventing, har ingen aktiv binding å inspisere. Når ruting endrer en aktiv
leieavtale, forblir den samme generasjonen gyldig, og status returnerer atomisk den nye bindingen, aldri
den gamle. Eksisterende klienter forblir uendret fordi svarene for oppretting, fornyelse, frigivelse og
venting beholder sine tidligere strukturer.

Denne serverkontrakten endrer ikke standard OpenAI Codex `/status`. Standard Codex rapporterer for
nærværende modellens leverandør og innebygde autentiserings-/kontotilstand, men gjengir ikke vilkårlige
kontometadata for egendefinerte leverandører; en senere klientintegrasjon må kalle denne operasjonen
og avgjøre hvordan `connection.displayName` skal vises.

Hver administrerte inferensforespørsel sender deretter begge kontrollhodene:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Den nøyaktige eieren, generasjonen, den aktive tilkoblingen og den autentiserte API-nøkkelen sikres
umiddelbart før hvert støttede oppstrømsforsøk. Gjentatt bruk av eier og generasjon med en annen nøkkel
mislykkes, selv når nøkkelen gir tilgang til den samme tilkoblingen. Rå eiere lagres ikke, loggføres ikke,
beholdes ikke i forespørselsbildet og videresendes ikke oppstrøms.

Midlertidig konkurranse returnerer HTTP `429` med `Retry-After` og:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Dette svaret betyr bare at det ordinære kvalifiserte settet ikke var tomt, og at alle ledige kandidater
var holdt av en annen aktiv leieavtale. Modeller/leverandører som ikke støttes, manglende samsvar med
policy, nedkjøling, kvote, helsetilstand og andre ordinære kvalifiseringsfeil beholder sine eksisterende
OmniRoute-svar.

### `x-omniroute-compression`

Overstyring av komprimeringsplanen per forespørsel. Høyeste prioritet — overstyrer rutingskombinasjonens
overstyring, den aktive profilen, automatisk utløsing og panelets Default. Verdier:

| Verdi         | Effekt                                                                                                         |
| ------------- | -------------------------------------------------------------------------------------------------------------- |
| `off`         | Ingen komprimering for denne forespørselen.                                                                    |
| `default`     | Panelets avledede Default-profil (ignorerer den aktive profilen). Tapsbaserte motorer forblir av.              |
| `safe`        | Bare deduplisering og sammenfolding av mellomrom.                                                              |
| `allow-lossy` | Behold operatørplanen for denne forespørselen, inkludert sammendrag og omskrivinger av stil.                   |
| `engine:<id>` | Én enkelt motor når den er aktivert, f.eks. `engine:rtk`. Eksplisiv aktivering av den motoren per forespørsel. |
| `<combo>`     | En navngitt kombinasjon, matchet først etter navn (uten hensyn til store og små bokstaver), deretter etter ID. |

Merknader:

- Ukjente verdier ignoreres (forespørselen avvises aldri); oppløsningen faller tilbake til den normale operatørprioriteten.
- Hvis flere kombinasjoner deler et navn, sender du kombinasjonens **id** for et deterministisk treff.
- En kombinasjon med navnet `off` eller `default` kan ikke velges etter navn (disse nøkkelordene tolkes først); referer til en slik kombinasjon med ID-en.
- Hovedbryteren for komprimering er en hard sperre: når komprimering er deaktivert globalt, kan ikke dette hodet aktivere den.

Den anvendte planen gjengis i svarhodet:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

der `<source>` er én av `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` eller `off`.

## Embeddinger

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Tilgjengelige leverandører: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Katalog-ID-er er `provider/model` (eksempel: `jina-ai/jina-embeddings-v5-omni-small`). Bare Jina-modell-ID-er som finnes i registeret (for eksempel `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) blir også løst. Jina embed/rerank/classify/segment bruker først `jina-ai`-legitimasjon fra kontrollpanelet; `JINA_AI_API_KEY` er kun en reserve når det ikke finnes noen nøkkel fra kontrollpanelet. Kortet `jina-reader` gjelder bare Reader / `r.jina.ai` (`POST /v1/web/fetch`) og leverer aldri embedding-er eller reranking.

Registermodeller som oppgir støtte for multimodalitet, godtar også opptil 32 leverandørnøytrale strukturerte elementer. Medieelementtypene er `text`, `image`, `audio`, `video` og `document`. Medieelementets `source` er enten `{"type":"url","url":"https://..."}` eller
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
og familiealiaset `jina-ai/jina-embeddings-v5-omni` → omni-small) godtar også Jinas opprinnelige
EmbeddingsV5Request-dokumentasjon og **videresender dem uendret** til `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Opprinnelige `{ image | audio | video | pdf }`-verdier kan være en offentlig HTTPS-URL, en `data:`-URI eller rå base64. OmniRoute gjør ikke disse objektene om til strenger eller henter opprinnelige bilde-URL-er — Jina henter offentlige medier selv. Ekstra Jina-felter (`task`, `normalized`, `truncate`, `embedding_type`) videresendes. Jina-SKU-er som bare støtter tekst, avviser fortsatt dokumenter som ikke er tekst.

Sikkerhets- og transportgrenser:

- Eksterne medie-URL-er må være offentlige HTTPS-URL-er. Kanoniske `{type,source:url}`-elementer hentes på serversiden (validering av omdirigeringer på nytt, tidsavbrudd, størrelsesgrenser, offentlig DNS, tilkoblingsbinding) og bygges inn før leverandørkallet. Jina-opprinnelige `{image:"https://..."}`-elementer videresendes som de er etter den samme kontrollen av offentlig HTTPS; Jina henter URL-en.
- Innebygde base64-medier er begrenset til 8 MiB dekodet per element og 16 MiB dekodet per forespørsel.

Leverandøroversettelse (kanoniske elementer videresendes aldri uendret):

- Jina-multimodale modeller: hvert element på øverste nivå blir til ett objekt med én modality-nøkkel
  (`text` / `image` / `audio` / `video` / `pdf`) som bruker data-URI-er for innebygde medier; én vektor per element på øverste nivå.
- Gemini Embedding 2-familien: én tabell på øverste nivå blir til én enkelt opprinnelig `models/{model}:embedContent`-forespørsel med `content.parts` (`text` eller `inline_data`).
- llama.cpp (`llama-cpp/<model>`, uansett hvilken modell den lokale serveren har lastet inn): kanoniske `text`-elementer blir til vanlige strenger, mens `image` / `audio` / `video` blir til ett `{"content": [part]}`-objekt hver, ved bruk av llama-serverens chat-innholdsdeler (`image_url`, `input_audio` med formatene `wav` / `mp3` / `flac`, `input_video`) med innebygde data; én vektor per element på øverste nivå. Serveren må kjøre med `--embedding --mmproj …`; uten en projektor avviser den medier selv. `document` støttes ikke.
- Ukjente/dynamiske modeller uten eksplisitte metadata for modalitet avviser strukturerte inndata med HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Kombinasjoner av modeller og modaliteter som ikke støttes, returnerer HTTP 400 i stedet for å tvinge gjennom elementet. Utvidelsesfelter som ikke er inndatafelt, i forespørsler med eldre streng-/tokenformat, videresendes fortsatt uendret.

```bash

GET /v1/embeddings
```

## Bildegenerering

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Tilgjengelige leverandører inkluderer OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana,**OpenRouter** ,**ZenMux** , SD WebUI (lokal), ComfyUI (lokal).

`n` returnerer `n` bilder i `data[]`. Leverandører hvis oppstrøms API returnerer ett bilde per samtale (Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik, NVIDIA NIM, Cloudflare Workers AI) får `n` separate oppstrømsanrop, maksimalt 4 under flyturen. En fast `seed` er forskjøvet av anropsindeks (`seed`, `seed + 1`, ...), så bildene er forskjellige, men forblir reproduserbare. `n` er begrenset til 10. Forespørselen mislykkes som helhet hvis et anrop mislykkes. Listen over fan-out-formater er `SINGLE_IMAGE_FANOUT_FORMATS` i `open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux gjenbruker den eksisterende API-nøkkelforbindelsen og godtar `zenmux/` eller `zm/` -prefikser:

- `zenmux/openai/gpt-image-2` bruker ZenMuxOpenAI Images API. Alternativene inkluderer `size`, `quality`, `n`, `output_format`, `output_compression`, `background` og `response_format`.
- Andre utgivere, som `zm/meta/muse-image-1.0`, bruker ZenMux Vertex AI `:predict` -endepunkt. `n` tilordner `sampleCount`, `aspect_ratio` til `aspectRatio` og `image_size` (`1K`, `2K`, `4K`) til `sampleImageSize`. En piksel `size` gir kun et sideforhold, ikke garanterte pikseldimensjoner. Støttede forhold, oppløsninger og antall varierer fra modell til modell.
- `zm/inclusionai/ming-image-0.1-design` velger sine egne dimensjoner. Utelat `size`, `aspect_ratio` og `image_size`; eksplisitte verdier returnerer HTTP 400. PNG, JPEG og WebP kan forespørres med `output_format`.

Denne integrasjonen støtter tekst-til-bilde-generering, ikke referanse-bilderedigering. Vertex-utgang er normalisert til `data[].b64_json`; `response_format: "url"` returnerer en oppstrøms HTTPS URL eller en base64 data URL når bare bildebyte er tilgjengelig. Empty/filtered -utganger returnerer en feil i stedet for en tom suksess. Modelltilgang avhenger av ZenMux kontoen. Se [ZenMux Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) og [OpenAI bilder API](https://docs.zenmux.ai/api/openai/generate-an-image).

En Microsoft 365 Copilot -påloggingstilkobling betjener `copilot-m365-web/m365-copilot-image` gjennom Copilot innebygde bildeverktøy: én Copilot omdreining per bilde (`n` 1–4), `size` styrer kun retningen, og bilder returnert inline (`b64_json`, eller en data URL for `response_format: "url"`). Se [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation).

```bash
# List all image models
GET /v1/images/generations
```

{

  "document": {

`model` velger OCR-leverandøren via et `provider/model`-prefiks; en frittstående modell-ID (f.eks.
`mistral-ocr-latest`) slås opp mot den registrerte leverandøren, og utelatt `model` bruker som
standard Mistral (`mistral-ocr-latest`). Registrerte leverandører (`open-sse/config/ocrRegistry.ts`):

| Leverandør-ID                 | Modell-ID            | `model`-verdi                                                          | Merknader                                                                                                    |
| ----------------------------- | -------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (eller frittstående `mistral-ocr-latest`) | Synkron — svaret returneres direkte fra det ene kallet oppstrøms.                                            |

| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                | Synkron, via Vertex AI sitt `openapi/chat/completions`-partnerendepunkt — se nedenfor for autentisering/URL. |

Alle tre leverandørene svarer med samme Mistral-formede innhold:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Pollingsflyt for Azure Document Intelligence

Azure Document Intelligence sitt `analyze`-API er asynkront: den første forespørselen returnerer
en `Operation-Location`-header i stedet for et innhold, og resultatet må hentes gjennom polling.
Håndtereren (`open-sse/handlers/ocr.ts`) poller denne URL-en hvert sekund i opptil 30 forsøk,
avslutter umiddelbart (fortsetter ikke å polle) ved et pollingsvar som ikke er `ok`, eller ved
statusen `"failed"`, og returnerer `504` hvis operasjonen fortsatt kjører etter at forsøksbudsjettet
er brukt opp. Det endelige Azure-svaret normaliseres til samme `pages`/`markdown`-struktur som
brukes av Mistral før det returneres til klienten, slik at klientkode ikke trenger å behandle
leverandøren særskilt.

### Autentisering og endepunktoppløsning for Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` gjenbruker den samme Vertex AI-autentiseringen som OmniRoute allerede støtter
for chat-/bildekommunikasjon (`open-sse/executors/vertex.ts`): Tilkoblingens API-nøkkel er enten en
Service Account JSON-legitimasjon (utvekslet mot et kortvarig OAuth-tilgangstoken via JWT-bearer-
flyten) eller et allerede utstedt OAuth-tilgangstoken som brukes direkte. URL-en til endepunktet
oppstrøms er Vertex sitt generiske `openapi/chat/completions`-partnerendepunkt, bygget fra
tilkoblingens prosjekt og region — en eksplisitt `providerSpecificData.project`/`providerSpecificData.region` vinner alltid;
ellers utledes prosjektet fra `project_id` i Service Account JSON, og regionen har standardverdien
`us-central1`. Begge oppløsningene skjer i `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), og brukes av
`src/app/api/v1/ocr/route.ts` før videresending til `handleOcr`.

### Modellpriser (`pricing`)

En oppføring inneholder et `pricing`-objekt når OmniRoute kjenner modellens pris. Prisen kommer
fra pristabellen som brukes til kostnadsberegning: innebygde standardverdier, synkroniserte priser og
overstyringer angitt via `/api/pricing`. Dette er listepriser, så abonnementsleverandører viser også
en pris per token.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| Felt                                                            | Enhet                        | Merknader                                                                                                                               |
| --------------------------------------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD per token, desimalstreng | OpenRouter-kompatibel, aldri i eksponentnotasjon. De to hurtigbufferfeltene vises bare når det finnes en hurtigbufferpris.              |
| `input`, `output`, `cached`, `cache_creation`                   | USD per 1M tokens, tall      | Felt fra tidligere katalogversjoner, beholdt for eksisterende klienter. `reasoning` og `long_context` vises også når prisraden har dem. |

- **Kombinasjoner** har prisen til sitt første synlige mål. Innebygde `auto/*`-kombinasjoner velger et
  mål ved forespørselstidspunktet, så de har ingen `pricing`.
- **Gratis modeller** viser `"0"` (og `0`) når prisen er null. En modell uten prisrad viser også `"0"`
  når katalogen markerer den som gratis (`free: true`), eller den er oppført i den innebygde katalogen
  over gratis modeller.
- **Ukjent pris:** Oppføringen har ingen `pricing`-nøkkel.
- **Leverandører med kredittbasert måling** (for eksempel Kiro) fakturerer per forespørsel i stedet
  for per token. Oppføringene deres beholder de numeriske feltene per 1M som de hadde tidligere, og
  har ingen strengfelt per token.
- **Varianter** (ID-er for resonneringsnivå, aliaser uten tenking, speil for oppdagelse og gateway)
  kopierer prisen til modellen de ruter til.
- Feltene inneholder bare grunnsatser. Nivåer for lang kontekst (det numeriske `long_context`-feltet)
  og multiplikatorer for tjenestenivå (for eksempel Codex fast eller flex) endrer ikke `prompt` eller
  `completion`.
- Objektet er det samme for alle autentiseringsmåter, inkludert en forespørsel i Anthropic-stil med
  `x-api-key` og `anthropic-version` (svaret forblir `{ "object": "list",
"data": [...] }`). Implementasjon: `src/app/api/v1/models/catalogPricing.ts`.

### Prefikser for modell-ID-er (`?prefix=`)

De fleste modeller annonseres med et **leverandørprefiks**. Hvilket prefiks du får, styres av
funksjonsflagget `MODELS_CATALOG_PREFIX_MODE`, og kan overstyres **per forespørsel** med en
spørringsparameter — nyttig for en klient som ønsker en ren liste uten å endre serverens
globale innstilling for alle andre:

```bash
GET /v1/models?prefix=alias        # én ID per modell — prefikset med det korte aliaset
GET /v1/models?prefix=dual         # begge former (serverstandard)
GET /v1/models?prefix=canonical    # bare det fullstendige leverandør-ID-prefikset
```

| Modus       | Genererer                                                | Merknader                                                                                                                                                                                                |
| ----------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **og** `claude/claude-sonnet-4-6` | **Standard.** Begge ID-ene rutes til samme modell; beholdt slik at klientkonfigurasjoner som hardkodet en av formene, fortsetter å fungere. Katalogen blir omtrent dobbelt så stor.                      |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Én oppføring per modell. Leverandører uten et særskilt alias genererer fortsatt oppføringen sin, slik at ingenting går tapt.                                                                             |
| `canonical` | `claude/claude-sonnet-4-6`                               | Én oppføring per modell under det fullstendige leverandør-ID-prefikset. Leverandører uten et særskilt alias (f.eks. `antigravity/…`, `agy/…`) genererer også sin ene ID her, slik at ingenting går tapt. |

Et speil i `dual`-modus kan også gjenkjennes uten spørringsparameteren: det har et `parent`-felt
som peker på den primære ID-en.

Klienter som gjengir en modellvelger, bør be om `?prefix=alias` — det er dette
[OmniCopilot VS Code-utvidelsen](../guides/VSCODE-COPILOT.md) gjør.

### Oppdagelsesfiltre (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` støtter valgfrie oppdagelsesfiltre. Uten noen av dem er svaret
uendret. De begrenser katalogen som innringeren allerede ser (API-nøkkelstillatelser brukes først),
og kjøres før sideinndelingen med `limit` / `after` i OpenAI-stil:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # alle oppførte egenskaper må være sanne
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalogens `type`; rader uten en slik er `chat`
GET /v1/models?q=sonnet&limit=10                           # samsvar uten hensyn til store og små bokstaver på ID eller navn
```

| Parameter     | Verdier                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ikke-negativt heltall, sammenlignes med `context_length`                                            |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 tegn                                                                                          |

En ukjent verdi, eller en `min_context` som ikke er et ikke-negativt heltall (for eksempel `1.5`),
returnerer HTTP `400`, og meldingen viser de gyldige verdiene. Implementasjon:
`src/app/api/v1/models/catalogFilters.ts`.

### Kort modelliste (`POST /v1/models/query`)

`POST /v1/models/query` returnerer en kort, deterministisk liste fra den samme katalogen, med samme
autentisering og synlighet per nøkkel som `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Alle felter er valgfrie. `capabilities` og `exclude` kan angis som en matrise eller som en kommaseparert streng;
`max_output` sammenlignes med `max_output_tokens`. Resultatene sorteres etter `owned_by` og deretter `id`.
`limit` er som standard `20`, og verdier over `100` begrenses til `100`. Ugyldig JSON, et ukjent
felt eller en ugyldig verdi returnerer HTTP `400`.

### Individuelt skjulte chatmodeller

En modell som er merket **Skjult** på leverandørsiden, utelates fra katalogen og avvises
med HTTP `404` / `model_not_found` når den eksplisitt etterspørres. Kontrollen bruker den
løste leverandøren og modellen, inkludert leverandøraliaser, nodeprefikser for kompatible leverandører
og tilkoblingsstandarder. En kombinasjon hopper over skjulte mål og kan bruke et synlig søskenmål;
når ingen kjørbart mål gjenstår, returneres den samme feilkoden. Når en modell gjøres synlig igjen,
trer dette i kraft ved neste forespørsel. Synlighets-overstyringer som bare gjelder bilder, skjuler ikke
chatmodellen med samme ID.

Denne individuelle modellinnstillingen er separat fra
[modellens eksponeringslister for tillatelse/avvisning](../routing/MODEL_EXPOSURE_LIST.md), som filtrerer
katalogannonsering og kandidater for automatisk ruting, samtidig som eksplisitt distribuering beholdes.
Modelltillatelser for API-nøkler gjelder fortsatt uavhengig. Standardmodus for katalogprefiks er fortsatt
`dual`.

### Modellvarianter uten tenkning

For Claude-modeller som støtter tenkning, annonserer `/v1/models` også en variant **uten tenkning**, hvis id har prefikset `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Når denne id-en velges (for eksempel i en Claude Code-konfigurasjon som alltid legger ved en `thinking`-blokk),
løses den tilbake til den virkelige `<provider>/<model>`, med undertrykt resonnering — `thinking:{type:"disabled"}` på `/v1/messages`-banen, eller feltene `reasoning`/`reasoning_effort` fjernet på `/v1/chat/completions`-banen. Varianten vises bare for Claude-familiemodeller som støtter tenkning **og** respekterer `disabled` (slik at for eksempel modeller som bare støtter adaptiv tenkning, men avviser `disabled`, utelates). Operatører kan tvinge varianten på eller av per modell via `ModelSpec.noThinkingAlias`.

## ElevenLabs-lydgenerering

Konfigurer en `elevenlabs`-leverandørtilkobling i OmniRoute med ElevenLabs API-nøkkelen din.
Klienter autentiserer med **OmniRoute**-nøkkelen sin (`Authorization: Bearer $OMNIROUTE_API_KEY`);
gatewayen leverer den lagrede leverandørnøkkelen som `xi-api-key`. Send aldri en ElevenLabs-nøkkel
som gatewayens bearer-token.

| Metode | Bane                        | Respons                                       | Kategori for API-nøkkeleendepunkt |
| ------ | --------------------------- | --------------------------------------------- | --------------------------------- |
| POST   | `/v1/sound-generation`      | Opprinnelige lydbyte                          | `elevenlabs`                      |
| POST   | `/v1/music`                 | Opprinnelige lydbyte                          | `music`                           |
| POST   | `/v1/music/stream`          | Strømmende lydbyte                            | `music`                           |
| POST   | `/v1/music/detailed`        | Opprinnelig multipart-lyd og komposisjonsplan | `music`                           |
| POST   | `/v1/music/detailed/stream` | Opprinnelige SSE-metadata og lydsegmenter     | `music`                           |
| POST   | `/v1/music/plan`            | JSON-komposisjonsplan                         | `music`                           |

Disse endepunktene utfyller de eksisterende rutene `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` og `/v1/speech-to-text`. Opprinnelige JSON-felt
og spørringsparametere som `output_format` og `enable_logging` bevares.
Responsene fra `/v1/music/detailed` beholder multipart-grensene sine; analyser dem som multipart.
`/v1/music/detailed/stream` returnerer `text/event-stream` med komposisjonsmetadata og
base64-lydsegmenter i SSE-hendelser. Alle de seks rutene støtter CORS-preflight.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# En kort lydeffekt. Varighet: 0,5 til 30 sekunder.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Musikkvarighet angis i millisekunder: 3000 til 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Bruk `/v1/music/stream` med samme JSON-innhold for trinnvis levering av lyd. Komposisjon
godtar nøyaktig én av `prompt` eller `composition_plan`; `/v1/music/plan` krever `prompt`
og godtar valgfritt `source_composition_plan`. De opprinnelige skjemaene bevarer ytterligere
leverandørfelt, slik at versjoner av komposisjonsplaner og finjusteringsalternativer når frem til ElevenLabs.

Det samlede endepunktet `/v1/music/generations` godtar også
`elevenlabs/music_v1`, `elevenlabs/music_v2` og `elevenlabs/music_v2_5`. Med en aktiv ElevenLabs-tilkobling
eksponeres disse modellene av musikkatalogen. Dette endepunktet returnerer
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Feltet `duration` angis i
sekunder og tilordnes til `music_length_ms`; en eksplisitt `music_length_ms` har prioritet.
`instrumental` tilordnes til `force_instrumental`, mens det opprinnelige feltet har prioritet.
Bruk de opprinnelige strømmeendepunktene for strømming og det opprinnelige komposisjonendepunktet
for forespørsler som kun styres av en komposisjonsplan.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Begrensninger for endepunkt, modell, budsjett og tilkobling håndheves før et oppstrømskall. Opprinnelige
ruter returnerer oppstrømsstatuskoder og feilinnhold uendret, inkludert `402` for en planbegrensning og
`429` for en kvotegrense. Hodene `character-cost`, `song-id`, `request-id` og `retry-after`
bevares når de finnes. En saldo med gratis kreditter garanterer ikke tilgang til alle
musikkmodeller, utdataformater eller API-funksjoner: ElevenLabs avgjør tilgangen for hver forespørsel.
Det samlede endepunktet bevarer feilkoder i OmniRoutes normaliserte feilkonvolutt.

Oppstrømskontrakter: [lydeffekter](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[musikkomposisjon](https://elevenlabs.io/docs/api-reference/music/compose) og
[detaljert strømming av musikk](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

```bash
# Omrangering (leverandør fra skyregisteret eller en OpenAI-kompatibel leverandørnode som "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina-klassifisering (Foundation API-legitimasjon)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina-segmentering
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina-søk (s.jina.ai; leverandøraliaser: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Moderering
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — returnerer en body med audio/mpeg (eller det forespurte formatet)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS krever et språk og en stemme: `language` har standardverdien "en"; en manglende
# stemme eller et OpenAI-standardstemmenavn (alloy, nova, …) blir til "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Bilderedigering (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Video-/musikkgenerering (leverandørprefikset modell-ID)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Noder for omrangeringstilbydere:** `POST /v1/rerank` ruter også til OpenAI-kompatible tilbydernoder
> (oMLX, vLLM, Infinity, TEI bak en gateway, …) adressert som `<node-prefix>/<model>`. Loopback-
> noder (`localhost`, `127.0.0.1`, `172.16.0.0/12`) er alltid kvalifisert, og det samme gjelder vertsnavnene
> operatøren oppgir i `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (f.eks. et Docker-/Compose-tjenestenavn som
> `http://reranker:8080/v1`; disse kalles direkte, aldri via `HTTP(S)_PROXY` eller en tilkoblings
> fastlåste proxy). Noder på alle andre
> verter — en LAN-maskin eller Tailscale-peer — er bare kvalifisert når operatøren aktiverer
> funksjonsflagget `RERANK_REMOTE_PROVIDER_NODES` **og** nodens basis-URL består policyen for utgående
> tilbyders-URL-er (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Minnemotorens omrangeringssteg kaller denne ruten via
> loopback, så den samme regelen gjelder for `rerankProviderModel` i minneinnstillingene.
>
> **Former for lokale servere:** noden kalles på `<base>/v1/rerank` og, ved 404, på `<base>/rerank`
> (Infinity, TEI). Oppstrømskroppen inneholder både Cohere-/OpenAI-notasjonen (`documents`,
> `return_documents`) og TEI-notasjonen (`texts`, `return_text`), og oppstrømssvaret
> normaliseres til Cohere-konvolutten: TEIs bare `[{index, score, text}]`, `{results: [{index, score}]}`
> fra tynne gatewayer og Voyage-lignende `{data: [...]}` returneres alle til klienten som
> `{results: [{index, relevance_score, document?}]}`, sortert etter poengsum og begrenset til `top_n`.

> **Oppdagelse av tilbydernoder:** Modeller på en OpenAI-kompatibel tilbydernod vises i `GET /v1/models`
> under nodeprefikset. Rader uten endepunktmetadata (typisk for lokale `/v1/models`-oppføringer)
> arver nodens `apiType`, slik at modellene til en `embeddings`-node får `type: "embedding"` og
> modellene til en `rerank`-node får `type: "rerank"` i stedet for å settes til chat som standard;
> en eksplisitt `supportedEndpoints` på en synkronisert eller manuelt lagt til rad har fortsatt prioritet.

## Søk API

Web/search leverandørabstraksjon (Tavily, Brave, Exa, Serper, etc.).

| Metode | Sti                    | Beskrivelse                                                                 |
| ------ | ---------------------- | --------------------------------------------------------------------------- |
| GET    | `/v1/search`           | Liste konfigurerte søkeleverandører + funksjoner                            |
| POST   | `/v1/search`           | Kjør et søk — body validert av `v1SearchSchema`, støtter caching/coalescing |
| GET    | `/v1/search/analytics` | hit/latency/cache -statistikk per leverandør                                |

**Auth:** Bærer API nøkkel (`extractApiKey` + `isValidApiKey`). Søkepolicy håndhevet via `enforceApiKeyPolicy`.

**Automatisk valg:** uten `provider` kjører den billigste leverandøren med en konfigurert tilkobling først, og den nest billigste er failover. Gratis siste utvei-leverandører (`duckduckgo-free`) brukes bare når ingenting annet er konfigurert. En selvvertsbasert SearXNG teller som konfigurert når tilkoblingen lagrer en ekte `baseUrl` (ikke standard katalogens `http://localhost:8888/search`): den rangerer da som en $0-leverandør foran nøkkelleverandører, med den billigste nøkkelleverandøren som failover, inkludert når SearXNG svarer 400, 401, 403 eller 404. A `baseUrl` eller som ikke er `http(s)` poeng URL sky-metadata-adressen teller ikke. En SearXNG tilkobling som lagrer et token rangerer bare på denne måten over `https://` eller loopback `http://`. Over ekstern plain `http://` er det aldri en failover og forblir en siste utvei, brukes bare når ingen annen leverandør er konfigurert eller når det blir bedt om ved navn, så det sender tokenet i klartekst i disse to tilfellene.

### `provider_options` for Exa og Tavily

Exa og Tavily leser leverandørspesifikke felt fra en navngitt beholder:
`provider_options.exa` (eller `provider_options["exa-search"]`) og `provider_options.tavily`
(eller `provider_options["tavily-search"]`). Bare nøklene nedenfor videresendes. Hver nøkkel
kontrolleres mot sitt eget Zod-skjema i `open-sse/handlers/search/providerOptionsPassthrough.ts`,
og en nøkkel med feil type forkastes. Alle andre nøkler ignoreres, inkludert autentisering, base-URL,
`stream` og `outputSchema`. De flate nøklene som brukes av andre leverandører (`cx`, `depth`, ...)
fungerer som før.

| Leverandør | Felter på toppnivå                                                                                                                                                                                                                                                                                                                                                        | Nøstet                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa        | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (flate primitive verdier), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                      | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` slått sammen over standardverdien `{ text: true, highlights: true }` |
| Tavily     | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                  |

De generiske feltene vinner alltid: `query`, `max_results`, `filters` (domener), `country` og
emnet som utledes fra `search_type`. For Exa beholder `search_type: "news"` `category: "news"`.
Tavily godtar også `search_type: "finance"` (`topic: "finance"`).

Kostnaden for Firecrawl-søk registreres per påbegynte blokk med 10 returnerte resultater, til $0.002
(2 kreditter) per blokk og minst én blokk per kall
([Firecrawl-fakturering](https://docs.firecrawl.dev/billing)): 11 resultater koster $0.004.

Den generiske `time_range` når nå begge leverandørene: Exa får `startPublishedDate` (ISO-tidsstempel)
og Tavily får `start_date` (`YYYY-MM-DD`). En eksplisitt dato i `provider_options`
overstyrer den tilordnede datoen.

Exa-resultater beholder `id`, `highlights` (hvert høydepunkt, ikke bare det første som brukes som
`snippet`), `highlight_scores`, `summary`, `subpages`, `entities` og `extras` i
`provider_raw`. Tavily-resultater beholder `images` og `favicon`.

Kostnaden for Linkup-søk registreres som $0.005 for `depth` `fast` og `standard`, og $0.05 for
`deep` ([Linkup-priser](https://docs.linkup.so/pages/documentation/development/pricing)),
uavhengig av om `depth` kommer fra `provider_options` eller tilkoblingens innstillinger.

Exa `type: "lite"` (Exa 3.0) godtar et mindre sett med felter og avviser hele forespørselen
når et annet felt er satt. For lite fjernes `additionalQueries`, `systemPrompt` og alle
`contents`-nøkler unntatt `text` og `highlights` før kallet. De foreldede
`subpages`, `subpageTarget`, `highlights.numSentences` og `highlights.highlightsPerUrl` videresendes
ikke lenger.

Exa: $0,007 per samtale for `auto` (og den eldre `fast`) eller $0,004 for `lite` (og den eldre `instant`), som dekker 10 resultater; $0,001 for hvert ytterligere resultat; og $0,001 per returnert resultat når `contents.summary` er satt. Tavily er registrert med 1 kreditt ($0,008) for `search_depth` `basic`, `fast` og `ultra-fast`, og 2 kreditter ($0,016) for `advanced` ( [Tavily API credits](https://docs.tavily.com/documentation/api-credits) ). En samtale med `auto_parameters: true` som Tavily oppgraderer til avansert blir fortsatt registrert med 1 kreditt.

## Web Fetch API

Hent ut innhold fra en URL via en konfigurert web-fetch-leverandør (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, samme API-nøkkel som Parallel Search) returnerer kun Markdown — alle andre `format`-verdier gir en `400` — og begrenser innholdet til 100 000 tegn. Når målsiden ikke kan hentes ut, rapporterer upstream dette i et HTTP 200-svar; OmniRoute eksponerer dette som en `422` med en fast melding.

| Metode | Bane            | Beskrivelse                                              |
| ------ | --------------- | -------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Hent/skrap en URL — body valideres av `v1WebFetchSchema` |

**Autentisering:** Bearer API-nøkkel (`extractApiKey` + `isValidApiKey`). Policy håndheves via `enforceApiKeyPolicy`.

**Kvotebevisst reserveløsning (#8297):** når ingen eksplisitt `provider` er angitt, gås poolen
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) gjennom i fast
prioritetsrekkefølge (fill-first) — en hastighetsbegrenset, men konfigurert leverandør hoppes over
i stedet for at forespørselen avbrytes, og en retrybar upstream-feil/kvotefeil (HTTP 429 alltid; 402/403 for Firecrawl/Tavily/TinyFish-kvoter i gratisnivåer —
ikke for Jina Reader, og aldri for en vanlig 400-feilforespørsel) går videre til
neste ikke-prøvde leverandør med gyldig legitimasjon ved forespørselstidspunktet. Når alle leverandørene i poolen er brukt opp, returnerer endepunktet én enkelt `429` (med en `Retry-After`
-header) i stedet for den tidligere generiske `400`-feilen. Når en eksplisitt `provider` er forespurt, finnes det **ingen** stille reserveløsning — en hastighetsbegrenset eller mislykket eksplisitt leverandør eksponerer sin egen feil (`429` ved hastighetsbegrensning, ellers upstream-statusen).

## WebSocket-strømming

```bash
GET /v1/ws?handshake=1
```

Validerer et WebSocket-oppgraderingshåndtrykk og returnerer eksempelmeldingene for wire-protokollen (`request`, `cancel`). Faktiske WS-rammer håndteres av den medfølgende WS-serveren utenfor Next.js-rutetabellen.

**Autentisering:** Bearer API-nøkkel under håndtrykket.

### Responses API over WebSocket (kun codex)

```bash
# Samme host:port som HTTP-API-et (standard 20128); oppgrader tilkoblingen:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (eller: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Første ramme MÅ være response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

En Responses-API-over-WebSocket-proxy er koblet **utelukkende til `codex`** (ChatGPT
backend). Den lytter på samme port som API-et/dashboardet på banene `/v1/responses`,
`/responses` og `/api/v1/responses`. På den første `response.create`-rammen autentiserer og klargjør den via den interne `codex-responses-ws`-broen, velger en codex OAuth-tilkobling og tunnelerer til `wss://chatgpt.com/backend-api/codex/responses`
via `wreq-js`-transporten. **Ikke-codex-modeller avvises** (`codex_ws_provider_required`).
For kvotedelt ruting bruker du `model: "qtSd/<group>/codex/<model>"`. Implementert i
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autentisering:** Bearer API-nøkkel under håndtrykket. Den medfølgende HTTP-serveren (`server-ws.mjs`)
må være det aktive inngangspunktet (det er den som standard når `app/server-ws.mjs` finnes).

#### Modell-ID: bruk den nakne ChatGPT-ID-en (uten `codex/`-prefiks)

OpenAI **Codex CLI** validerer modellnavnet på klientsiden når
`supports_websockets = true` og **avviser leverandørprefiksede ID-er** som
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Send den **nakne** ID-en (f.eks. `gpt-5.5`). OmniRoute-broen er kun for codex, så den slår opp en naken ID på nytt som en codex-modell
(`resolveCodexWsModelInfo`) før tunnelen opprettes mot upstream — selv om en naken
`gpt-5.5` ellers ville blitt rutet til en annen leverandør over HTTP.

#### Konfigurere OpenAI Codex CLI

Pek Codex CLI mot OmniRoute ved å legge til en egendefinert leverandør med WebSocket-støtte i
`~/.codex/config.toml` (bruk en separat `CODEX_HOME` for å unngå å endre en eksisterende konfigurasjon):

```toml
model = "gpt-5.5"                 # naken ID — IKKE "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ingen avsluttende skråstrek; WS-URL-en avledes (bruk https/wss i produksjon)
wire_api = "responses"                    # eneste støttede verdi siden februar 2026
supports_websockets = true                # aktiverer Responses-over-WS-transporten
env_key = "OMNIROUTE_API_KEY"             # inneholder OmniRoute API-nøkkelen (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # en OmniRoute API-nøkkel (hvilken som helst nøkkel hvis REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI-et oppgraderer `base_url + /responses` til en WebSocket, og OmniRoute tunnelerer den
til den valgte codex OAuth-tilkoblingen. Validert ende-til-ende mot den lokale
serveren: ChatGPT returnerer `codex.rate_limits` + `response.created` og strømmer
fullføringen.

| Metode | Sti                 | Beskrivelse                                                                                 |
| ------ | ------------------- | ------------------------------------------------------------------------------------------- |

### Gjenoppretting av kvoteøkter (valgfritt)

En ikke-strømmende `POST /v1/chat/completions` eller `POST /v1/responses` som mislykkes med
en terminal kvotefeil (`402`/`429`/`503` der brødteksten sier at kvoten eller kredittene er oppbrukt)
kan parkeres og spilles av på nytt senere i stedet for å returnere feilen. Avsenderen velger dette per
forespørsel med tre headere:

| Header                       | Verdi                                    |
| ---------------------------- | ---------------------------------------- |
| `x-omniroute-quota-recovery` | `auto`                                   |
| `x-omniroute-session`        | økt-ID, `[A-Za-z0-9._:-]{1,128}`         |
| `x-omniroute-recovery-turn`  | tur-ID som er unik i økten (samme regel) |

Bare turer med `stream: false` uten verktøy, verktøyhistorikk eller `previous_response_id`, og uten
`x-omniroute-connection`-binding, er kvalifisert, og `STORAGE_ENCRYPTION_KEY` må være angitt
(forespørselen lagres kryptert i opptil 24 timer). Svaret er deretter `202` med
`recovery.poll`; hent status med `GET /v1/quota-recoveries/{id}` (`202` mens den venter, `200` med den
gjenopprettede brødteksten når den er fullført), eller avbryt med `DELETE`. Billetter er bare synlige
for API-nøkkelen som opprettet dem. En avspilling der utfallet er usikkert, avsluttes med
`needs_confirmation` i stedet for å bli sendt to ganger. Kilde: `src/lib/quota/quotaSessionRecovery.ts`.

## Selvbetjent bruk (`/api/usage/om-usage`)

Enhver API -nøkkel kan lese **sin egen** bruk og kvoter — ingen administrasjonsgodkjenning. Dette er endepunktet en klient (CLI, OmniCopilot panelet) bruker for å vise en nøkkelinnehaver forbruket sitt.

```bash
# Text form (the historical contract — plain text for a terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Structured form — what a UI consumes
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Nøkkelen må ha **`allowUsageCommand`** aktivert (av som standard — dashbordets API-nøkkelbehandling veksler per nøkkel). Uten det svarer endepunktet `403`.

`?format=json` returnerer en diskriminert form slik at en innringer aldri leser et datafelt av et avslag. Om suksess:

```jsonc
{
  "allowed": true,
  // present only when the key opted into per-key usage limits (daily/weekly/5-hour USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // the selected provider quota snapshot, or null when nothing is cached yet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // every connection's snapshot, so a UI can render several providers side by side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Ved avslag (`401` dårlig nøkkel / `403` ikke tillatt) returnerer den samme ruten `{ "allowed": false, "error": { "message": "…" } }` — en nåværende-men-tom `personal`/`provider` (nøkkel tillatt, ingenting lært ennå) er en annen tilstand enn et avslag, og bare JSON skjemaet skiller dem.

**Auth:** innringerens egen Bærer API nøkkel, validert med `isValidApiKey` — dette er _ikke_ administrasjonsflaten (`/api/keys/…`), som forblir bak `requireManagementAuth`.

### Rå kontra avbruddsjusterte kvoteprosenter

Ved bruk av `/api/usage/om-usage` bør avsendere merke seg forskjellen mellom
prosentene som presenteres av **ren tekst-utdata** og strukturert **JSON-utdata**:

| Aspekt                | Ren tekst-format (`/api/usage/om-usage` / `@@om-usage`)                                       | JSON-format (`?format=json`)                                             |
| :-------------------- | :-------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------- |
| **Utdatafelt**        | `NN% left` (f.eks. `20% left`)                                                                | `provider.quotas` / `providers[].quotas`                                 |
| **Måling**            | **Avbruddsjustert tilgjengelig kvote**: gjenværende kapasitet over avbruddsgrensen            | **Rå oppstrømskvote**: ujustert leverandørmåling                         |
| **Avbruddsskalering** | Skalert via `effectiveRemainingPercent()` slik at den beskyttede reserven vises som `0% left` | Ingen (rå øyeblikksbildeverdier slik de rapporteres av leverandøren)     |
| **Grensedata**        | Inkludert i den viste prosentandelen                                                          | Lagret i `quotaWindowThresholds` per tilkobling (eller serverstandarder) |
| **Primærbruker**      | Interaktive CLI-er, terminalmeldinger, menneskelige operatører                                | Programmatisk integrasjon, dashbord, analyse, fakturasporing             |

#### Formelen for avbruddsjustering

OmniRoute støtter proaktive kvoteavbrudd for å forhindre at oppstrømskvoten tømmes (konfigurert via tilkoblingens
`quotaWindowThresholds`, leverandørstandarder eller globale innstillinger for robusthet). Når en avbruddsgrense
(f.eks. `cutoff = 25%`) er aktiv i et kvotevindu, beregner tekstgjengiveren gjenværende tilgjengelig kvote slik:

- Hvis `remaining <= cutoff`: returnerer `0%`.
- Hvis `remaining > cutoff`: returnerer `((remaining - cutoff) / (100 - cutoff)) * 100`.

Den formaterte tekstutdataen avrunder dette til nærmeste heltall (`Math.round(...)`).

#### Illustrerende eksempel

Vurder et leverandørvindu med **60 % råbruk** (dermed **40 % råkvote igjen**) og en konfigurert
terskel på **25 % gjenstående kvote**:

| Representasjon               | Beregning                                          | Gjenstående |                Implisitt brukt                 |
| :--------------------------- | :------------------------------------------------- | :---------: | :--------------------------------------------: |
| **Rå JSON (`?format=json`)** | Oppstrømsøyeblikksbilde (`quotas[window]`)         |  **40 %**   |                    **60 %**                    |
| **Tekstformat (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20 %**   | **80 %** (hvis beregnet som `100 - remaining`) |

- **Hvorfor teksten viser 20 % igjen:** Av de 40 % av den fysiske kvoten som er igjen på kontoen, er 25 % reservert av
  avskjæringspolicyen. Den som kaller tjenesten, har bare 15 % av 75 % brukbart spillerom igjen før ruteren slutter å rute
  til denne tilkoblingen. Skaleringen sørger for at tilkoblingen signaliserer at den er tom (`0% left`) nøyaktig når
  rutingen opphører.
- **Hvorfor JSON bevarer råverdier:** JSON-nyttelasten returnerer det nøyaktige leverandørøyeblikksbildet (`UsageSnapshot`)
  slik at eksterne verktøy får tilgang til fasitverdier for oppstrømsbruk og tilkoblingsnivåets
  `quotaWindowThresholds` uten tapsbringende skalering på serversiden.

#### Veiledning for migrering av forbrukere

Hvis en ekstern integrasjon (for eksempel et programtillegg for en redigerer eller en agentutvidelse) tidligere hentet data fra tekstendepunktet
(`NN% left`) og beregnet brukt prosent som `100 - NN`, betyr migrering til `?format=json` at:

- Lesing av rå JSON-verdier vil gjenspeile **faktisk forbruk oppstrøms** (60 % brukt i eksempelet ovenfor).
- Hvis integrasjonen ønsker å bevare tekstendepunktets semantikk for tilgjengelig bruk, kan den beregne
  formelen for effektivt gjenstående klientbasert ved hjelp av `quotaWindowThresholds` for overstyringer på tilkoblingsnivå.

## Semantisk hurtigbuffer

```bash
# Hent hurtigbufferstatistikk
GET /api/cache/stats

# Tøm alle hurtigbuffere
DELETE /api/cache/stats
```

Eksempel på svar:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Påvirkning på ventetid

Et treff i den semantiske hurtigbufferen leverer svaret fra hurtigbufferen **uten et kall til oppstrøms**, slik at den rapporterte `X-OmniRoute-Response-Latency` er nær null (uavhengig av den opprinnelige ventetiden til oppstrøms). Klienter som er følsomme for ventetid (referansemålinger, p50-/p99-overvåking) bør kontrollere svarhodet `X-OmniRoute-Cache-Latency`:

| Verdi       | Betydning                                                                        |
| ----------- | -------------------------------------------------------------------------------- |
| `synthetic` | Svaret ble levert fra hurtigbufferen; ventetiden er ikke reell tid til oppstrøms |
| _(absent)_  | Svaret kommer fra et reelt kall til oppstrøms                                    |

### Deaktivering av hurtigbuffer per nøkkel

API-nøkler kan velge bort lesing fra den semantiske hurtigbufferen via `cacheDefaultMode`:

| Verdi    | Virkemåte                                                      |
| -------- | -------------------------------------------------------------- |
| `legacy` | Normal virkemåte for hurtigbufferen (standard)                 |
| `bypass` | Hopper over oppslag i hurtigbufferen; treffer alltid oppstrøms |

Angis ved opprettelse av nøkkelen (`POST /api/keys`) eller ved oppdatering (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Deaktivering av hurtigbuffer per forespørsel

Alle forespørsler kan hoppe over hurtigbufferen uavhengig av innstillingene for nøkkelen:

```
X-OmniRoute-No-Cache: true
```

## Kompatibilitet med CLIProxyAPI-administrasjon

OmniRoute svarer på de tre [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)-administrasjonsendepunktene som bruksdashbord bruker til å lese abonnementsgrensene for Claude og Codex (for eksempel T3 Codes `cliproxy`-kilde for bruksgrenser). Angi klientens basis-URL til OmniRoute, og bruk en API-nøkkel med området `manage` som administrasjonsnøkkel. Rutene leveres på `/v0/management/*` og `/api/v0/management/*`.

| Metode | Bane                         | Beskrivelse                                                                                                                                |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/v0/management/auth-files`  | Claude- og Codex OAuth-tilkoblinger som `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. Ingen token                |
| POST   | `/v0/management/api-call`    | Body `{ auth_index, method, url, header?, data? }`. Sender én tillatt forespørsel med kontoens token og returnerer `{ status_code, body }` |
| POST   | `/v0/management/reset-quota` | Body `{ auth_index }`. Fjerner tilkoblingens nedkjøling, modellblokkeringer og Codex-nedkjøling per område for én konto                    |

- `auth_index` er OmniRoute-tilkoblingens ID. `provider` er `claude` eller `codex` (bare OAuth-tilkoblinger; API-nøkkelleverandøren `anthropic` er ikke oppført). For Codex er `id_token.chatgpt_account_id` den lagrede arbeidsområde-ID-en og `plan_type` det lagrede abonnementet.
- `api-call` er ikke en generell proxy. Den godtar bare Claude `GET
https://api.anthropic.com/api/oauth/usage` og Codex `GET
https://chatgpt.com/backend-api/wham/usage`, `GET .../wham/rate-limit-reset-credits` og `POST .../wham/rate-limit-reset-credits/consume`, hver bare for en konto hos tilsvarende leverandør. Alt annet returnerer `403` uten å kontakte oppstrømstjenesten. Kallerens `Authorization`-header (inkludert plassholderen `$TOKEN$`) ignoreres: OmniRoute setter inn tilkoblingens tilgangstoken, fornyer det først når det nærmer seg utløp, og videresender bare headere fra tillatelseslisten (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`; `Accept`, `Content-Type`). Manglende `Chatgpt-Account-Id` får den lagrede arbeidsområde-ID-en som standard. Hvis det første oppstrømssvaret er `401`, fornyer den én gang og prøver bare på nytt når tilgangstokenet endres. Hvert oppstrømsforsøk får tidsavbrudd etter 15 sekunder og bruker tilkoblingens proxy.
- `reset-quota` lar terminale tilstander (banned, expired, credits_exhausted) være uendret. En ukjent `auth_index` returnerer `404`.

**Autentisering:** dashbordøkt eller en API-nøkkel med området `manage`, som kreves selv når innlogging er deaktivert (banene finnes i `ALWAYS_PROTECTED_API_PATHS`). Nøkler som bare brukes til inferens, får `403`. Kilde: `src/lib/cliproxyCompat/managementApi.ts`.

For synkroniserte/importerte modeller godtar `PUT /api/provider-models` `provider`, `modelId` og
`maxOutputTokenOverride`: et positivt heltall angir den manuelle grensen for antall output-tokens, og
`null` fjerner den for å gjenopprette standardverdien. `GET /api/provider-models?provider=<provider>` returnerer disse verdiene i `modelOutputOverrides`, inkludert modeller uten en rad for egendefinert modell. leverandører tilbyr de samme kontrollene for redigering/fjerning og markerer modeller med eksplisitt visningsstøtte.

På en kompatibel leverandørnode lagrer skriveoperasjonene (`POST`, `PUT`, `PATCH`, `DELETE` og
`/api/provider-models/validate-and-add`) modell-ID-en som den rå upstream-ID-en: en ID
som limes inn fra en prefikset liste, får alle innledende forekomster av nodens eget prefiks slått sammen, og
svar gjengir den lagrede ID-en. Kanoniske leverandørers ID-er med skråstrek (f.eks. `nvidia/nemotron-…`) lagres
ordrett. `/v1/models` sender aldri ut en stablet `<prefix>/<prefix>/<model>`-ID.

Custom Chat Completions-noder tilpasser eksplisitte fravalg av resonnering til backend-systemet. En
vellykket tilkoblingstest velger automatisk kontroller for chat-maler for hver eksakte modell-ID
der oppføringen i `/models` bekrefter en gjenkjent `owned_by`-verdi: `vllm`, `sglang` eller `llamacpp`.
Transparente OpenAI-kompatible omslag kan bevare den opprinnelige modelloppføringen i et nestet
`openai`-objekt; deteksjonen følger opptil tre slike omslag. Modeller med manglende, ukjent eller
motstridende eierskap beholder vanlig OpenAI-atferd. Deteksjonen bruker den eksisterende
katalogforespørselen på nytt, genererer ingen completion-tokens og ugyldiggjøres når
tilkoblingsendepunktet endres.

For å låse atferden for en backend som ikke eksponerer disse metadataene, bruker du det eksisterende API-et for delvise leverandøroppdateringer:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Send denne body-en med `PUT /api/providers/<connection-id>`. På denne tilkoblingen sendes en eksplisitt
resonneringsinnsats på `none` som `chat_template_kwargs.thinking=false` og
`chat_template_kwargs.enable_thinking=false`. Eksplisitte opprinnelige malverdier forblir
autoritative, med mindre en regel på serversiden tvinger frem en innsats. Innstillingen gjelder bare
når en egendefinert OpenAI-kompatibel tilkobling sender en Chat Completions-body; Responses-forespørsler
og vanlige leverandører beholder sin opprinnelige forespørselsform. Angi `reasoningControl` til
`openai` for å tvinge gjennom vanlig OpenAI-passthrough av `reasoning_effort`, eller utelat den/sett
den til `null` for å bruke automatisk deteksjon.

Claude Code-forespørsler for klassifisering i automatisk modus bruker som standard opprinnelig
tenking deaktivert når de ikke inneholder eksplisitte resonneringskontroller. Deteksjonen bruker
klassifikatorens systemmarkør i forespørsler i Claude-format, ikke modellnavn eller
completion-begrensninger. Eksplisitte body-kontroller, støttede headere for innsats/tenking,
rutingsregler og løst modellnivå for innsats beholder sin eksisterende prioritet. Begge
klassifikatorstadiene beholder promptene, completion-begrensningene og stoppsekvensene sine, samt
de faktiske tillatelsesavgjørelsene fra upstream; det andre stadiet kan fortsatt produsere den
forespurte synlige resonneringen som vanlig tekst.

#### Opphav for modellbegrensninger

`GET /api/models?withLimits=1` (også `true`; `0`/`false`, eller hvis den utelates, beholdes
standard-nyttelasten uendret) legger til `contextWindow`, `maxInputTokens`, `maxOutputTokens` og et
`capsSource`-objekt i hver modellrad. `capsSource` navngir regelen som leverte hver begrensning, slik
at en overraskende begrensning (for eksempel 128k på en 1M-modell) kan spores til opphavet sitt. De
løste verdiene er de samme som rutingen bruker; flagget legger bare til felt og endrer aldri en verdi.
Alle andre `withLimits`-verdier avvises med `400`.

| `static-authoritative:<provider>/<model>`    | Statisk autoritativ tabell for kontekstvindu                            |

### Drill-down videoramme

`GET /api/v1/video-bridge/drilldown` leser et leietakerbundet ugjennomsiktig håndtak som returneres i `x-omniroute-video-drilldown` etter en eksplisitt samtykket til Video Bridge-forespørsel. Både reads og `DELETE` krever alltid en gyldig API nøkkel og operatørens uavhengige `modalityBridgeVideoDrilldownRemoteEnabled` tillatelse. Produksjonsbevaring krever i tillegg `modalityBridgeVideoDrilldownEnabled` og strenge per-part `drilldown: true`. Hvis nøkkelen har en ikke-tom endepunkttillatelsesliste, må den inkludere `video` for både GET og DELETE, enten den som ringer bruker `/v1` eller `/api/v1`.

GET -spørring: nødvendig `handle`; valgfri `variant` (`preview`, `standard`, `detail`), `limit` (1–8; eldre `frames` er akseptert, men kan ikke kombineres med `limit`), nullbasert `page` og `start`/`end` sekunder. Når begge fokusgrensene er angitt, må `end` være større enn `start`. Duplicate/unknown spørringsnøkler avvises. Vellykkede svar inneholder `derivation`, `durationSeconds`, `frames`, `hasMore`, `page`, `variant` og valgfri `focusWindow`; no-store JSON er begrenset til 32 MiB inkludert Base64. Overdimensjonert utgang returnerer 413; be om færre rammer.

`DELETE /api/v1/video-bridge/drilldown?handle=...` returnerer `{ "removed": 0|1 }`. Ukjent, utløpt og kryssnøkkel GETs er umulige å skille 404-svar; cross-key DELETE kan ikke fjerne eierens oppføring. Deaktivert tilgang returnerer 403, missing/invalid autentisering 401, ugyldige spørringer 400, kansellering 499 og midlertidige feil 503. Håndtakene er prosesslokale, utløper etter ti minutter og overlever ikke en omstart. Nye håndtak bruker `v1.` pluss et 32-byte tilfeldig Base64URL token; bare token-hasher beholdes. Legacy 64-hex tokens forblir syntaktisk lesbare for kompatibilitet. Se [Video Bridge-rekkverk](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets) for detaljer om samtykke, kvoter og variantavledning.

### Versjon og utgivelseskanal

```bash
GET /api/system/version
```

Administrasjonsrute som kun er tilgjengelig via loopback (admin-autentisering). Returnerer den kjørende versjonen, den nyeste publiserte versjonen og statusen for automatisk oppdatering. `releaseChannel` og `channels` er additive felter (rail 3.8.54); `channel` beholder betydningen sin — distribusjonsmodusen som oppdateringsfunksjonen i dashbordet bruker (`npm`, `source` eller `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-kanalen til det kjørende bygget: `nightly` for versjoner med `-nightly.*`, `next` for andre forhåndsutgivelser (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` for en stabil versjon av en eldre hovedversjon enn `channels.latest`, ellers `latest`. Samme regler som i `scripts/release/dist-tag.mjs`, som velger npm-distribusjonstaggen ved publisering.
- `channels` — publisert hode for hver distribusjonstag, fra `npm view omniroute dist-tags` (HTTP-reservebane til registeret), bufret med samme TTL på 10 minutter som `latest`. `latest` finnes alltid (faller tilbake til `latest`-feltet, deretter `"unavailable"`); `next`, `nightly` og `lts` vises bare når den aktuelle distribusjonstaggen finnes. En forespørsel med `Cache-Control: no-cache` oppdaterer begge oppslagene.

Kanalmodellen (`latest` = v3 frem til 4.0 GA, `next` = rc, `nightly` = `develop`-bygg, `lts` = v3-oppdateringer etter 4.0 GA) er beskrevet i `docs/ops/RELEASE_STRATEGY.md`.

## Lydtranskripsjon

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Transkriber lydfiler ved hjelp av en konfigurert STT-leverandør. Det første
baneanet velger den opprinnelige leverandøren (`openai/…`, `deepgram/…`). Gatewayer som
videredistribuerer en annen leverandørs modell, bruker en kvalifisert id
(`openrouter/deepgram/nova-3`).

**Forespørsel:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Svar:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Eksempler på modell-ider:** `openai/whisper-1` (krever en OpenAI-nøkkel),
`openrouter/deepgram/nova-3` (krever en OpenRouter-nøkkel),
`deepgram/nova-3` (krever en opprinnelig Deepgram-nøkkel). En ren
`deepgram/nova-3`-forespørsel bruker **ikke** OpenRouter.

**Støttede formater:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** filmodus-transkripsjon over Gemini Live
WebSocket (krever en Gemini API-nøkkel). Opplastingen konverteres til 16 kHz mono PCM med `ffmpeg`
(`PATH` må inneholde dette, med mindre filen allerede er en 16 kHz mono PCM WAV), strømmes til økten, og
den ferdigstilte teksten returneres som `{ "text": "..." }`. Valgfrie `language`- og `prompt`-skjemafelt
videresendes. Begrensninger: opplastinger på over 25 MiB eller dekodet lyd som varer lenger enn 10 minutter, gir
`413`; en konvertering som varer lenger enn 60 s, avsluttes og gir `504`. API-nøkkelen sendes
bare i `x-goog-api-key`-headeren, aldri i WebSocket-URL-en.

## Tokeniserte VS Code-/hodeløse aliaser

Bruk disse aliasene når en integrasjon ikke kan legge inn en `Authorization`-header og trenger API-nøkkelen innebygd i basis-URL-en.

```bash
# OpenAI-stil katalogalias
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-stil chat-aliaser
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-stil aliaser
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Eksempel:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Merknader:

- De tokeniserte aliasene bruker de samme behandlerne som `/v1/*` og `/api/tags`; svarformatene forblir identiske.
- Foretrekk `Authorization: Bearer ...` når klienten støtter egendefinerte headere.
- URL-baserte tokens kan vises i logger fra omvendte proxyer, nettleserhistorikk og telemetri utenfor OmniRoute. Behandle dem som et kompatibilitetsalternativ, ikke som standard autentiseringsmetode.

## Tokenbegrensninger

**Token**-budsjetter per API-nøkkel (atskilt fra det USD-baserte budsjettet ovenfor). Håndheves direkte i forespørselsbanen: når gjeldende vindusforbruk for en nøkkel når grensen, avvises forespørsler med `429 Too Many Requests`. Begrensninger kan begrenses til en spesifikk `model`, en `provider` eller brukes `global`t på tvers av nøkkelen; når flere begrensninger gjelder for en forespørsel, vinner den mest restriktive.

```bash
# List token limits for a key (includes live window usage)
GET /api/usage/token-limits?apiKeyId=key-123

# Create or update a token limit
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Delete a token limit by id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Skjemamerknader** (`setTokenLimitSchema`): `apiKeyId` og `scopeType` (`model` | `provider` | `global`) er obligatoriske. `scopeValue` er obligatorisk med mindre `scopeType` er `global` (f.eks. en modell-ID for `model`-omfang, en leverandør-ID for `provider`-omfang). `tokenLimit` må være et positivt heltall (konverteres fra streng). Valgfritt: `id` (utelat for å opprette, oppgi for å oppdatere), `resetInterval` (`daily` | `weekly` | `monthly`, standard er `monthly`), `resetTime` (`HH:MM`), `enabled` (standard er `true`). `GET`-svar utvider hver begrensning med `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` og `nextResetAt`. Dette er et endepunkt i administrasjonsklassen (autentisering håndheves sentralt av autorisasjonsrørledningen).

## Forespørselsbehandling

1. Klienten sender forespørsel til `/v1/*`
2. Rutehåndtereren kaller `handleChat`, `handleEmbedding`, `handleAudioTranscription` eller `handleImageGeneration`
3. Modellen løses (direkte leverandør/modell eller alias/kombinasjon)
4. Påloggingsopplysninger velges fra den lokale databasen med filtrering basert på kontotilgjengelighet
5. For chat kontrollerer `handleChatCore` semantisk/signaturbasert hurtigbuffer og løser innstillinger for komprimering av kombinasjoner
6. Proaktiv komprimering kjøres før leverandøroversettelse når dette er aktivert (`lite`, Caveman, RTK eller stablet)
7. Leverandørutføreren sender forespørsel oppstrøms
8. Svaret oversettes tilbake til klientformat (chat) eller returneres som det er (embeddings/bilder/lyd)
9. Bruk, komprimeringsanalyse og forespørselslogger registreres
10. Reservealternativ brukes ved feil i henhold til kombinasjonsreglene

Full arkitekturreferanse: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Robusthet (utvidet)

OmniRoute eksponerer tre uavhengige mekanismer for midlertidige feil; administrasjonsendepunktene nedenfor lar operatører lese og overstyre dem:

| Omfang                   | Tilstandslagring                             | Les                                       | Tilbakestill / tøm                                                |
| ------------------------ | -------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| Leverandørbryter         | `domain_circuit_breakers` + i minnet         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                      |
| Nedkjøling av tilkobling | `rateLimitedUntil` på leverandørtilkoblinger | `/api/rate-limits`, `/api/providers/[id]` | (aktiveres på nytt på en lat måte; tømmes via PUT for leverandør) |
| Modellutestenging        | Register for modelltilgjengelighet i minnet  | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                          |

`PATCH /api/resilience` godtar overstyringer av leverandørbrytere under `providerBreaker.oauth` og `providerBreaker.apikey`. Hver profil støtter `degradationThreshold`, `failureThreshold` og `resetTimeoutMs`; de samme feltene eksponeres i Dashboard → Settings → Resilience.

```bash
# Tøm en enkelt modellutestenging
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Tøm alle utstenginger
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Full konseptuell referanse og standardverdier for brytere: se [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" og [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Kø for hastighetsbegrensning og sikkerhetsnett for automatisk aktivering

- **Støttet skrivebane**: `POST /api/rate-limits` med brødteksten `{"connectionId": "<id>", "enabled": true|false}` er det støttede administrasjonsendepunktet for å slå av eller på beskyttelse mot hastighetsbegrensning for en tilkobling. `PUT /api/providers/[id]` endrer eller veksler med hensikt ikke `rateLimitProtection` (#11278).
- **Semantikken til `enabled: false`**: Angivelse av `enabled: false` fjerner eksplisitt beskyttelse for tilkoblingen, men **velger ikke bort** et aktivt API-nøkkelbasert tilkoblingsobjekt fra det globale sikkerhetsnettet for automatisk aktivering (`autoEnableApiKeyProviders = true`). I `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) er `false` og `undefined` ekvivalente; aktive API-nøkkelbaserte tilkoblinger uten eksplisitt beskyttelse forblir beskyttet av sikkerhetsnettet for automatisk aktivering.
- **Global deaktivering**: For å kjøre API-nøkkelbaserte tilkoblinger uten køer for hastighetsbegrensning, deaktiver sikkerhetsnettet globalt via `RATE_LIMIT_AUTO_ENABLE=false` (env) eller `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`).

## MCP-server

OmniRoute leveres med en innebygd Model Context Protocol-server med tre transportmekanismer (stdio, SSE, streamable-http) og tilgangsavgrensede verktøy. Endepunktene for dashbordet nedenfor leser status-/revisjonsdata og videresender HTTP-transportmekanismene.

| Metode | Bane                   | Beskrivelse                                                                                                                     |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/mcp/status`      | Pulsslag, transportmekanisme, tilkoblet status, siste kall, mest brukte verktøy, suksessrate siste 24 timer                     |
| GET    | `/api/mcp/tools`       | Liste over MCP-verktøy med `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints`                            |
| GET    | `/api/mcp/sse`         | Åpne SSE-strøm for SSE-transporten (returnerer `503` hvis MCP er deaktivert eller transportmekanismen ikke samsvarer)           |
| POST   | `/api/mcp/sse`         | Send JSON-RPC-ramme på SSE-transporten                                                                                          |
| GET    | `/api/mcp/stream`      | Åpne SSE-siden av Streamable HTTP-transporten (serverinitierte meldinger)                                                       |
| POST   | `/api/mcp/stream`      | Send JSON-RPC-ramme på Streamable HTTP-transporten                                                                              |
| DELETE | `/api/mcp/stream`      | Avslutt en Streamable HTTP-økt                                                                                                  |
| GET    | `/api/mcp/audit`       | Spør i revisjonsloggen — `?limit=`, `?offset=`, `?tool=`, `?success=true                                \| false`, `?apiKeyId=` |
| GET    | `/api/mcp/audit/stats` | Samlet revisjonsstatistikk (totaler, suksessrate, gjennomsnittlig varighet, mest brukte verktøy)                                |

**Autentisering:** `sse`-/`stream`-transportmekanismene bruker den MCP-spesifikke autentiseringsflaten (Bearer API-nøkkel med `mcp`-omfang); `status`-/`tools`-/`audit*`-rutene kan leses fra dashbordet (ingen ekstra autentisering kreves utover tilgang til dashbordverten).

## A2A-server

OmniRoute eksponerer et A2A-endepunkt (Agent-til-agent) for JSON-RPC 2.0 samt en REST-omslutter for inspeksjon og bruk av dashbord.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # valgfritt med mindre OMNIROUTE_API_KEY er satt
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Støttede metoder (alle er avhengige av `settings.a2aEnabled`):

| Metode           | Beskrivelse                                                            |
| ---------------- | ---------------------------------------------------------------------- |
| `message/send`   | Synkron kjøring av ferdighet; returnerer `{task, artifacts, metadata}` |
| `message/stream` | Strømmende SSE-kjøring av samme sett med ferdigheter                   |
| `tasks/get`      | Hent en oppgave etter `taskId`                                         |
| `tasks/cancel`   | Avbryt en oppgave etter `taskId`                                       |

Innebygde ferdigheter: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Agentkort

```bash
GET /.well-known/agent.json
```

Returnerer det offentlige A2A-agentkortet (navn, beskrivelse, funksjoner, ferdighetskatalog, autentiseringsskjema) — bufres offentlig i 1 time. Ingen autentisering kreves.

### REST-hjelpere

| Metode | Bane                         | Beskrivelse                                                                                                       |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A-status + oppgavestatistikk + sammendrag av bufret agentkort                                                   |
| GET    | `/api/a2a/tasks`             | Vis oppgaver — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Ikke implementert som REST-hjelper — opprett via JSON-RPC `message/send`)                                        |
| GET    | `/api/a2a/tasks/[id]`        | Hent én oppgave                                                                                                   |
| POST   | `/api/a2a/tasks/[id]/cancel` | Avbryt en oppgave                                                                                                 |

**Autentisering:** REST-hjelperne kjøres uten administrasjonsautentisering (kan leses fra dashbordet); JSON-RPC-ruten `/a2a` bruker Bearer `OMNIROUTE_API_KEY` hvis den er konfigurert.

## Autentisering

Se [Autentisering for administrasjon](../guides/MANAGEMENT-AUTH.md) for de fire
legitimasjonsfamiliene (dashboard-økt, lokalt CLI-token, `oma_live_…` Access Token,
API-nøkkel med administrasjonsomfang) og hvordan de skiller seg fra
inferensnøkler.

- Dashboard-ruter (`/dashboard/*`) bruker `auth_token`-cookie
- Innlogging bruker lagret passordhash; bruker `INITIAL_PASSWORD` som reserve
- `requireLogin` kan slås av og på via `/api/settings/require-login`
- `/v1/*`-ruter krever valgfritt Bearer-API-nøkkel når `REQUIRE_API_KEY=true`
- «management token» / «management-scoped API key» i denne referansen betyr én av familiene i den veiledningen — ikke en udefinert ekstra hemmelighetstype

> **Brytende endring (v3.8.0)** — `/api/v1/agents/tasks/*` og endepunktene for administrasjon av nedkjølingsperioder krever nå **administrasjonsautentisering** (dashboard-`auth_token`-cookie eller en API-nøkkel med administrasjonsomfang). Klienter som tidligere kalte disse rutene uten autentisering, vil motta `401 Unauthorized`. Se commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
