## અવલોકન

OmniRoute એક મોડ્યુલર પ્રોમ્પ્ટ કમ્પ્રેશન પાઇપલાઇન અમલમાં મૂકે છે, જે વિનંતીઓ અપસ્ટ્રીમ પ્રદાતાઓ સુધી પહોંચે તે પહેલાં **સક્રિય રીતે** ચાલે છે. આનો અર્થ એ છે કે તમારી ટોકન બચત પારદર્શક રીતે થાય છે — તમારા વર્કફ્લોમાં કોઈ ફેરફાર કરવાની જરૂર નથી.

```
ક્લાયન્ટ વિનંતી
  → કમ્પ્રેશન વ્યૂહરચના પસંદગીકાર
    → કૉમ્બો ઓવરરાઇડ? → કૉમ્બો સેટિંગનો ઉપયોગ કરો
    → સ્વચાલિત-ટ્રિગર થ્રેશોલ્ડ? → સ્વચાલિત મોડનો ઉપયોગ કરો
    → ડિફૉલ્ટ મોડ? → વૈશ્વિક સેટિંગનો ઉપયોગ કરો
    → બંધ? → કમ્પ્રેશન છોડો
  → પસંદ કરેલો કમ્પ્રેશન મોડ
    → બંધ: કોઈ કમ્પ્રેશન નહીં
    → લાઇટ: સુરક્ષિત વ્હાઇટસ્પેસ/ફોર્મેટિંગ સફાઈ (~15%)
    → સ્ટાન્ડર્ડ: Caveman-શૈલીમાં વધારાના શબ્દો દૂર કરવા (~30%)
    → એગ્રેસિવ: ઇતિહાસ એજિંગ + સારાંશીકરણ (~50%)
    → અલ્ટ્રા: હ્યુરિસ્ટિક પ્રૂનિંગ + કોડ-બ્લૉક પાતળા કરવા (~75%)
    → RTK: કમાન્ડ-અવેર ટર્મિનલ/ટૂલ-આઉટપુટ ફિલ્ટરિંગ (60-90% અપસ્ટ્રીમ રેન્જ)
    → સ્ટૅક્ડ: ક્રમબદ્ધ મલ્ટિ-એન્જિન પાઇપલાઇન, સામાન્ય રીતે પહેલાં RTK અને પછી Caveman (78-95% પાત્ર રેન્જ)
  → કમ્પ્રેસ કરેલી વિનંતી → પ્રદાતા
```

## કમ્પ્રેશન મોડ્સ

### બંધ

કોઈ કમ્પ્રેશન લાગુ કરવામાં આવતું નથી. બધા સંદેશાઓમાં કોઈ ફેરફાર કર્યા વિના પસાર થાય છે.

### લાઇટ મોડ (~15% બચત, <1ms લેટન્સી)

સૌથી સુરક્ષિત મોડ — ફોર્મેટિંગની સફાઈ. તેના ટૂલ-પરિણામ ટ્રંક્શનથી માહિતી ગુમાય છે, તેથી ડિફૉલ્ટ
પાથ (`allow-lossy`, `engine:lite` અથવા નામિત-કોમ્બો ઑપ્ટ-ઇન વિના) લાઇટને
`compressToolResults: false` સાથે ચલાવે છે: અગાઉના ટૂલ પરિણામો પ્રોવાઇડર સુધી અપરિવર્તિત પહોંચે છે.

| તકનીક                    | વર્ણન                                                                               |
| ------------------------ | ----------------------------------------------------------------------------------- |
| `collapseWhitespace`     | સતત ખાલી લાઇનો અને અંતિમ સ્પેસને એકત્રિત કરે છે                                     |
| `dedupSystemPrompt`      | ડુપ્લિકેટ સિસ્ટમ સંદેશાઓ દૂર કરે છે                                                 |
| `compressToolResults`    | અગાઉના ટૂલ પરિણામોને લાઇટ કૅપ સુધી ટ્રંિકેટ કરે છે (લોસી: ફક્ત વિનંતી ઑપ્ટ-ઇન સાથે) |
| `removeRedundantContent` | પુનરાવર્તિત સૂચનાઓ દૂર કરે છે                                                       |
| `replaceImageUrls`       | base64 ઇમેજ ડેટા URI ને ટૂંકા કરે છે                                                |

**આ માટે શ્રેષ્ઠ:** હંમેશાં ચાલુ ઉપયોગ, સલામતી-મહત્ત્વપૂર્ણ વર્કફ્લો.

### સ્ટાન્ડર્ડ મોડ (~30% બચત)

[Caveman](https://github.com/JuliusBrussee/caveman) થી પ્રેરિત — અર્થ જાળવીને ભરાવદાર શબ્દો અને લાંબી વાક્યરચના દૂર કરે છે:

- ભરાવદાર શબ્દો દૂર કરે છે ("please", "I think", "basically", "actually")
- લાંબા વાક્યપ્રયોગોને સંક્ષિપ્ત કરે છે ("in order to" → "to", "as a result of" → "because")
- નમ્ર હેજિંગ દૂર કરે છે ("Would you mind...", "If you could possibly...")
- કોડિંગ પ્રોમ્પ્ટ માટે સુસંગત 30+ regex નિયમો

**આ માટે શ્રેષ્ઠ:** દૈનિક કોડિંગ વર્કફ્લો, ખર્ચ પ્રત્યે સચેત ટીમો.

### એગ્રેસિવ મોડ (~50% બચત)

લાંબા સત્રો માટે સ્માર્ટ ઇતિહાસ વ્યવસ્થાપન:

- **સંદેશ એજિંગ** — જૂના સંદેશાઓને ક્રમશઃ વધુ સંકુચિત કરવામાં આવે છે
- **ટૂલ પરિણામ કમ્પ્રેશન** — લાંબા ટૂલ આઉટપુટને ટ્રંિકેટ અથવા દૂર કરવામાં આવે છે (પ્રથમ/છેલ્લી લાઇનો,
  મેચ-લાઇન ફિલ્ટરિંગ, JSON કી કમ્પેક્શન)
- **સ્ટ્રક્ચરલ ઇન્ટિગ્રિટી ગાર્ડ્સ** — `tool_use` + `tool_result` જોડીઓ સુસંગત રહે તેની ખાતરી કરે છે
- **કૉન્ટેક્સ્ટ વિન્ડો અવેરનેસ** — દરેક મોડલની ટોકન મર્યાદાઓનું પાલન કરે છે

**આ માટે શ્રેષ્ઠ:** વિસ્તૃત ડિબગિંગ સત્રો, મોટા કોડબેઝ.

### અલ્ટ્રા મોડ (~75% બચત)

ટોકન-મહત્ત્વપૂર્ણ પરિસ્થિતિઓ માટે મહત્તમ કમ્પ્રેશન:

- **હ્યુરિસ્ટિક પ્રૂનિંગ** — પ્રોઝનું સ્કોર-આધારિત ટોકન પ્રૂનિંગ
- **સ્ટ્રક્ચર પ્રિઝર્વેશન** — ફેન્સ્ડ કોડ બ્લોક્સ, ઇનલાઇન કોડ, URLs અને આઇડેન્ટિફાયર્સને
  ટોમ્બસ્ટોન કરીને ફરીથી મૂળરૂપે જોડવામાં આવે છે; તેમને ક્યારેય પ્રૂન કરવામાં આવતા નથી
- **વૈકલ્પિક SLM ટિયર** — ગોઠવાયેલ હોય ત્યારે નાનું સ્થાનિક મોડલ પ્રૂનને વધુ શુદ્ધ કરી શકે છે
- એગ્રેસિવ મોડથી સ્વતંત્ર: તે મેસેજ એજિંગ, ટૂલ-પરિણામ કમ્પ્રેશન અથવા ફૉલબૅક સમરાઇઝર ચલાવતું નથી
  (ફક્ત SLM-ટિયર નિષ્ફળતા જ ફૉલબૅક પાસને એગ્રેસિવ મારફતે રૂટ કરી શકે છે)

**આ માટે શ્રેષ્ઠ:** જ્યારે તમે વારંવાર કૉન્ટેક્સ્ટ મર્યાદાઓનો સામનો કરો છો.

### RTK મોડ (60-90% અપસ્ટ્રીમ રેન્જ)

RTK મોડ કોડિંગ-એજન્ટ સત્રોમાં દેખાતા વિસ્તૃત ટૂલ આઉટપુટ માટે ઑપ્ટિમાઇઝ કરાયેલ છે:

- `git status`, `git diff`, `git log`, ટેસ્ટ રનર્સ,
  TypeScript/Vite/Webpack બિલ્ડ્સ, ESLint/Biome/Prettier, npm audit/ઇન્સ્ટૉલ્સ, Docker લૉગ્સ, ઇન્ફ્રા
  આઉટપુટ અને સામાન્ય શેલ આઉટપુટ જેવા કમાન્ડ/આઉટપુટ વર્ગોને ઓળખે છે
- `open-sse/services/compression/engines/rtk/filters/` માંથી JSON ફિલ્ટર પૅક્સ લાગુ કરે છે
- પ્રોજેક્ટ અથવા વૈશ્વિક `filters.toml` ફાઇલોમાંથી RTK TOML સ્કીમા v1 ફિલ્ટર્સ આયાત કરે છે, જેમાં ઇનલાઇન-ટેસ્ટ
  વૅલિડેશન અને પ્રોજેક્ટ ફાઇલો માટે ટ્રસ્ટ-ગેટિંગનો સમાવેશ થાય છે
- ઇનલાઇન વેરિફાઇ સૅમ્પલ્સ સાથે 56 બિલ્ટ-ઇન ફિલ્ટર્સ આપે છે
- ANSI કંટ્રોલ સિક્વન્સ, પ્રોગ્રેસ બાર, પુનરાવર્તિત લાઇનો અને બિન-કાર્યક્ષમ અવાજ દૂર કરે છે
- નિષ્ફળતાઓ, ભૂલો, ચેતવણીઓ, બદલાયેલી ફાઇલો, સારાંશો અને લાંબા આઉટપુટનો અંતિમ ભાગ જાળવી રાખે છે
- ટ્રસ્ટ-ગેટેડ પ્રોજેક્ટ ફિલ્ટર્સ, વૈશ્વિક ફિલ્ટર્સ અને વૈકલ્પિક રેડેક્ટેડ રૉ-આઉટપુટ પુનઃપ્રાપ્તિનું સમર્થન કરે છે

**આ માટે શ્રેષ્ઠ:** શેલ, બિલ્ડ, ટેસ્ટ, git, grep અને ફાઇલ-આઉટપુટ ટ્રાન્સક્રિપ્ટ ધરાવતા એજન્ટ સત્રો.

### સ્ટૅક્ડ મોડ (78-95% યોગ્ય રેન્જ)

સ્ટૅક્ડ મોડ અનેક કમ્પ્રેશન એન્જિનોને નિર્ધારિત ક્રમમાં ચલાવે છે. ડિફૉલ્ટ પાઇપલાઇન છે:

```txt
RTK -> Caveman
```

આ ક્રમ પહેલાં ટર્મિનલ/ટૂલ આઉટપુટને સંક્ષિપ્ત રાખે છે, પછી બાકી રહેલા કુદરતી-ભાષાના પ્રોમ્પ્ટ પર
Caveman સેમેન્ટિક કન્ડેન્સેશન લાગુ કરે છે. સ્ટૅક્ડ પાઇપલાઇન્સ વૈશ્વિક સ્તરે અથવા રૂટિંગ કોમ્બોઝને
સોંપાયેલા કમ્પ્રેશન કોમ્બોઝ મારફતે ગોઠવી શકાય છે.

**આ માટે શ્રેષ્ઠ:** મોટા ટૂલ લૉગ્સ સાથેની માનવીય સૂચનાઓ અથવા સહાયક સારાંશો ધરાવતો મિશ્ર કૉન્ટેક્સ્ટ.

## અપસ્ટ્રીમ બચતનું ગણિત

OmniRoute બે સ્રોતોમાંથી કમ્પ્રેશનની બચતનું દસ્તાવેજીકરણ કરે છે: અપસ્ટ્રીમ પ્રોજેક્ટ બેન્ચમાર્ક્સ અને
OmniRouteનું પોતાનું એન્જિન સંયોજન.

| સ્રોત   | અહીં ઉપયોગમાં લેવાયેલ અપસ્ટ્રીમ READMEનો આંકડો                                                                    |
| ------- | ----------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` ઓછા આઉટપુટ ટોકન્સ, બેન્ચમાર્કમાં સરેરાશ `65%` આઉટપુટ બચત, `22-87%`ની શ્રેણી અને `~46%` ઇનપુટ કમ્પ્રેશન ટૂલ |
| RTK     | કમાન્ડ-આઉટપુટમાં `60-90%` બચત; નમૂના સત્રમાં `~118,000 -> ~23,900` ટોકન્સ, અથવા `79.7%` બચત (`~80%`)              |

ઓવરલેપ થતા ટૂલ/કોન્ટેક્સ્ટ પેલોડ્સ માટે, ડિફૉલ્ટ OmniRoute કોમ્બો એન્જિનોને આ ક્રમમાં સ્ટૅક કરે છે:

```txt
RTK -> Caveman
```

સંયુક્ત બચત ગુણાકાર આધારિત છે, સરવાળા આધારિત નહીં:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

આ `78-95%`નો આંકડો ત્યારે લાગુ પડે છે જ્યારે RTK અને Caveman બંને સમાન ઇનપુટ/કોન્ટેક્સ્ટ પેલોડને ઘટાડી શકે.
Cavemanનો રિસ્પોન્સ આઉટપુટ મોડ અલગ છે: જ્યારે તે સક્ષમ હોય, ત્યારે Cavemanની પોતાની આઉટપુટ બચતનો ઉપયોગ કરો (સરેરાશ `65%`,
મુખ્ય આંકડો `~75%`, શ્રેણી `22-87%`). કુલ બિલિંગ બચત તમારા પ્રોમ્પ્ટ/આઉટપુટના મિશ્રણ પર આધારિત છે.

### "પાત્ર"નો ખરેખર અર્થ શું છે

15-95%ની મુખ્ય શ્રેણી વાસ્તવિક છે, પરંતુ તે ફક્ત **પુનરાવર્તિત અથવા અતિવિસ્તૃત** સામગ્રી પર જ લાગુ પડે છે — વારંવાર આવતી
એરર લાઇનો, એક જ ચેતવણી વારંવાર બતાવતો બિલ્ડ લૉગ, અથવા જરૂર કરતાં મોટો `grep`/ફાઇલ-રીડ ડમ્પ. તેનો
અર્થ એ **નથી** કે દરેક રિક્વેસ્ટમાં એટલી બચત થાય છે.

પ્રાયોગિક રીતે ચકાસાયેલ (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 સમાન
એરર લાઇનો ધરાવતા Anthropic-આકારના `tool_result` બ્લૉક સામે `stacked` (RTK + Caveman) રન કરવાથી
**95.93% ટોકન બચત / 96.26% અક્ષર બચત** મળી — જે જાહેર કરેલી
શ્રેણીમાં ચોક્કસપણે આવે છે. પરંતુ સામાન્ય, બિન-પુનરાવર્તિત ટૂલ આઉટપુટ (સ્વચ્છ `grep` મેચ સૂચિ,
ટૂંકું ફાઇલ રીડ, સામાન્ય વાર્તાલાપી ટેક્સ્ટ) સામે એ જ પાઇપલાઇન ચલાવવાથી યોગ્ય રીતે **લગભગ શૂન્ય બચત** થાય છે, કારણ કે
દૂર કરવા માટે કંઈપણ પુનરાવર્તિત નથી અને `validateCompression()` (`validation.ts`) એવા
પુનર્લેખનને મોકલવાનો ઇનકાર કરે છે જે કોડ બ્લૉક્સ, URLs, હેડિંગ્સ, વર્ઝન્સ અથવા ALL-CAPS કૉન્સ્ટન્ટ આઇડેન્ટિફાયર્સને કાઢી નાખે કે બદલે.

આ અપેક્ષિત અને સુરક્ષિત વર્તન છે, બગ નહીં: જે કોડિંગ સત્રમાં મોટાભાગે સ્વચ્છ ફાઇલો વાંચવામાં/grep કરવામાં આવે છે તેમાં
કમ્પ્રેશન સંપૂર્ણપણે સક્ષમ હોવા છતાં કુલ બચત મર્યાદિત જોવા મળશે, જ્યારે નિષ્ફળ થતી
લૂપ અથવા ખૂબ વધુ આઉટપુટ આપતા લિન્ટરનો સામનો કરતું સત્ર તે ટ્રાફિક પર સંપૂર્ણ 78-95% શ્રેણી જોશે. કોઈ એક સત્રની
નીચી એકંદર બચત ટકાવારીને કમ્પ્રેશન ખોટી રીતે કૉન્ફિગર થયું હોવાના પુરાવા તરીકે ઉપયોગ કરશો નહીં — પહેલાં તપાસો કે
અંતર્ગત ટૂલ આઉટપુટ ખરેખર પુનરાવર્તિત હતું કે નહીં.

## રૂપરેખાંકન

### ડેશબોર્ડ

`Dashboard → Context & Cache` પર જાઓ:

- **Caveman** — મોડ પસંદગી, ભાષા પૅક્સ, પૂર્વાવલોકન અને વૈશ્વિક ડિફૉલ્ટ્સ
- **RTK** — કમાન્ડ-ફિલ્ટર પૂર્વાવલોકન, RTK સલામતી સેટિંગ્સ અને ફિલ્ટર કૅટલૉગ
- **Compression Combos** — રૂટિંગ કોમ્બોઝને સોંપવામાં આવેલી નામવાળી એન્જિન પાઇપલાઇનો
- **Auto-Trigger Threshold** — ટોકન સંખ્યા થ્રેશોલ્ડ કરતાં વધુ થાય ત્યારે આપમેળે કમ્પ્રેશન સક્રિય કરવું

### કોમ્બો-દીઠ ઓવરરાઇડ

`Dashboard → Context & Cache → Compression Combos` માં રૂટિંગ
કોમ્બોને કમ્પ્રેશન કોમ્બો સોંપો:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

આથી તમે મફત/કોડિંગ પ્રોવાઇડર્સ પર સ્ટૅક્ડ કમ્પ્રેશનનો ઉપયોગ કરી શકો છો અને પેઇડ
સબ્સ્ક્રિપ્શન્સ પર લાઇટ મોડ જાળવી શકો છો.

આ "કોમ્બો-દીઠ ઓવરરાઇડ" સોંપણી, **રૂટિંગ-કોમ્બો કમ્પ્રેશન
મોડ** ઓવરરાઇડ (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ફિલ્ડનું
સ્કીમા `rtk`, `stacked` અને `omniglyph` પણ સ્વીકારે છે) કરતાં અલગ નિયંત્રણ છે — આ ઓવરરાઇડ
નામવાળી કમ્પ્રેશન-કોમ્બો પાઇપલાઇન પસંદ કરતું નથી; તે માત્ર `resolveCompressionPlan` દ્વારા
પરામર્શવામાં આવતું `compressionMode` ફિલ્ડ સેટ કરે છે. તેને કોમ્બો કાર્ડ
(`Dashboard → Combos`) પર અથવા #6760થી, `Dashboard → Context & Cache → Compression Combos` પર
"Assign to routing" સૂચિમાં દરેક રૂટિંગ કોમ્બો માટે, ઉપર દસ્તાવેજીકૃત પાઇપલાઇન-સોંપણી ચેકબૉક્સની
બાજુમાં સેટ કરી શકાય છે. બંને સપાટીઓ સમાન `PUT /api/combos/{id}` એન્ડપૉઇન્ટ દ્વારા
સંગ્રહિત થાય છે.

### પ્રતિ-વિનંતી ઓવરરાઇડ

એક જ વિનંતી માટે કમ્પ્રેશન પ્લાનને ઓવરરાઇડ કરવા માટે
`x-omniroute-compression` વિનંતી હેડર મોકલો. તેની પ્રાથમિકતા સૌથી વધુ છે — તે રૂટિંગ-કોમ્બો
ઓવરરાઇડ, સક્રિય પ્રોફાઇલ, ઑટો-ટ્રિગર અને પેનલ ડિફૉલ્ટ કરતાં વધુ પ્રાધાન્ય ધરાવે છે. અજ્ઞાત
મૂલ્યો અવગણવામાં આવે છે (વિનંતી ક્યારેય નકારવામાં આવતી નથી) અને વૈશ્વિક માસ્ટર સ્વિચ હજુ પણ
બધું નિયંત્રિત કરે છે: જ્યારે કમ્પ્રેશન વૈશ્વિક રીતે બંધ હોય, ત્યારે હેડર તેને ચાલુ કરી શકતું નથી.
મૂલ્યો:

| Value         | Effect                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `off`         | આ વિનંતી માટે કોઈ કમ્પ્રેશન નહીં.                                                                   |
| `default`     | પેનલમાંથી મેળવેલી Default પ્રોફાઇલ (સક્રિય પ્રોફાઇલને અવગણે છે). Lossy એન્જિનો બંધ રાખવામાં આવે છે. |
| `safe`        | હેડર ન મોકલવા જેટલું જ.                                                                             |
| `allow-lossy` | સારાંશો, રિલેવન્સ ફિલ્ટર્સ અને સ્ટાઇલ રીરાઇટ્સ સહિત આ વિનંતીનો ઑપરેટર પ્લાન જાળવો.                  |
| `engine:<id>` | સક્ષમ હોય ત્યારે એક એન્જિન, ઉદાહરણ તરીકે `engine:rtk`. આ તે એન્જિન માટે પ્રતિ-વિનંતી ઑપ્ટ-ઇન છે.    |
| `<combo>`     | નામથી મેળ ખાતો નામવાળો કોમ્બો (પહેલા કેસ-ઇન્સેન્સિટિવ રીતે, પછી ID દ્વારા).                         |

`allow-lossy`, `engine:<id>` અથવા નામવાળા કોમ્બો વિના, lossy એન્જિનો લાગુ કરવામાં આવતા નથી. જ્યારે
lossy Default, ઑટો-ટ્રિગર અથવા રૂટિંગ ઓવરરાઇડને ડાઉનગ્રેડ કરવામાં આવે છે, ત્યારે OmniRoute
રૂપરેખાંકિત સ્ટૅક્ડ પાઇપલાઇનમાંથી ઓળખાયેલા lossless પગલાંને રૂપરેખાંકિત ક્રમમાં જાળવી રાખે છે.
જ્યારે કોઈ રૂપરેખાંકિત lossless પગલું બાકી રહેતું નથી ત્યારે જ તે
`session-dedup → lite` પર પાછું ફરે છે.

Settings પેનલનું **Effective pipeline** પૂર્વાવલોકન સામાન્ય, સ્થિર પ્લાન દર્શાવે છે. જ્યારે
ઑટો-ટ્રિગર ચાલી શકે, ત્યારે એ જ પૂર્વાવલોકન તેનો શરતી અસરકારક પાઇપલાઇન પણ દર્શાવે છે, જેથી
પેનલ અને હેડરવિહોણું રનટાઇમ રિઝોલ્યુશન સુસંગત રહે.

લાગુ કરાયેલ પ્લાન `X-OmniRoute-Compression: <mode>; source=<source>` પ્રતિસાદ
હેડરમાં પરત મોકલવામાં આવે છે, જ્યાં `<source>` નીચેના પૈકી એક હોય છે:
`request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` અથવા `off`.

## આભારવિધિ

Standard મોડના કમ્પ્રેશન નિયમો **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) દ્વારા બનાવાયેલા **[Caveman](https://github.com/JuliusBrussee/caveman)**થી પ્રેરિત છે — વાયરલ "જ્યારે થોડા ટોકનથી કામ થઈ જાય ત્યારે ઘણા ટોકન શા માટે વાપરવા" પ્રોજેક્ટ. Caveman `~75%` ઓછા આઉટપુટ ટોકન્સ, બેન્ચમાર્કમાં સરેરાશ `65%` આઉટપુટ બચત, `22-87%`ની આઉટપુટ રેન્જ અને `~46%`નું ઇનપુટ-કમ્પ્રેશન ટૂલ દર્શાવે છે.

RTK મોડ **[RTK AI](https://github.com/rtk-ai)** દ્વારા બનાવાયેલા **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)**થી પ્રેરિત છે — ટર્મિનલ, બિલ્ડ, ટેસ્ટ, git અને ટૂલ-આઉટપુટ ફિલ્ટરિંગ માટેનો ઉચ્ચ-પ્રદર્શન ધરાવતો કમાન્ડ-આઉટપુટ કમ્પ્રેશન પ્રોજેક્ટ. RTK `60-90%` બચત દર્શાવે છે, જ્યારે તેના READMEના નમૂના સેશનમાં `~80%` બચત બતાવવામાં આવી છે.

## અદ્યતન કમ્પ્રેશન સિસ્ટમ્સ

ઉપર વર્ણવેલ 7 મોડ્સ ઉપરાંત (સ્રોત `codex-responses` અને `omniglyph` મોડ્સ પણ સ્વીકારે છે, જેને આ માર્ગદર્શિકા આવરી લેતી નથી), નીચેના વિભાગો કવર સુવિધાઓ કે જે તે મોડ્સની અંદર અથવા તેની સાથે કામ કરે છે: ટૂલ રિઝલ્ટ કમ્પ્રેશન અને પ્રોગ્રેસિવ એજિંગ એ એગ્રેસિવ એન્જિનના સ્ટેપ્સ 1 અને 2 છે (આક્રમક મોડ અને `aggressive` સ્ટેપ સ્ટેક, સ્ટેક, સ્ટેક, સ્ટેક, સ્ટેક, સ્ટેક લાઇન) ના સ્ટેપ 1 અને 2 છે. જ્યારે કમ્પ્રેશન ચાલુ હોય ત્યારે કૅશ-અવેર કમ્પ્રેશન કૅશિંગ પ્રદાતાઓ માટે `aggressive` અને `ultra` ને `standard` પર ડાઉનગ્રેડ કરે છે, અને કૅવમેન આઉટપુટ મોડ અને આઉટપુટ સ્ટાઇલ ઑપ્ટ-ઇન સિસ્ટમ-પ્રોમ્પ્ટ સૂચનાઓ છે, જે ડિફૉલ્ટ રૂપે બંધ છે, જે વિનંતીને સંકુચિત કરવાને બદલે મોડેલના આઉટપુટને આકાર આપે છે.

### કેશ-અવેર કમ્પ્રેશન

કેટલાક પ્રદાતાઓ (જેમ કે પ્રોમ્પ્ટ કેશીંગ સાથે Anthropic ) સપોર્ટ** પ્રોમ્પ્ટ કેશીંગ** , જે તેમને ખર્ચ અને લેટન્સી ઘટાડવા માટે પ્રોમ્પ્ટના ભાગોને કેશ કરવા દે છે. જ્યારે કેશીંગ સક્ષમ હોય, ત્યારે વાસ્તવમાં આક્રમક સંકોચન થઈ શકે છે** નુકસાન** પ્રદર્શન કારણ કે તે કેશ્ડ ટોકન્સને બદલે છે, કેશને અમાન્ય બનાવે છે.

`cachingAware.ts` મોડ્યુલ આના દ્વારા ઉકેલે છે** કેશીંગ સંદર્ભ શોધી રહ્યા છે** અને** કમ્પ્રેશન વ્યૂહરચના ગોઠવી રહ્યા છીએ** તે મુજબ

#### તે કેવી રીતે કામ કરે છે

1. **કેશીંગ સંદર્ભ શોધો** — `cache_control` માર્કર્સ માટે વિનંતીના મુખ્ય ભાગને સ્કેન કરે છે
2. **કેશીંગ પ્રદાતાઓને ઓળખો** — તપાસે છે કે શું લક્ષ્ય પ્રદાતા કેશીંગને સપોર્ટ કરે છે
3. **વ્યૂહરચના ગોઠવો** — કેશીંગ પ્રદાતાઓ માટે `aggressive`/`ultra` ને `standard` થી ડાઉનગ્રેડ કરે છે
4. **સિસ્ટમ પ્રોમ્પ્ટ છોડો** — સિસ્ટમ પ્રોમ્પ્ટ સામાન્ય રીતે કેશ્ડ હોય છે, તેથી તેને સંકુચિત કરશો નહીં

સ્ટ્રેટેજી હેલ્પર પણ `deterministicOnly` ફ્લેગ પરત કરે છે, પરંતુ પ્લાન બિલ્ડર માત્ર વ્યૂહરચના — વાપરે છે જે આજે ધ્વજ વાંચતું નથી.

#### કોડ ઉદાહરણ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ક્યારે વાપરવું

કેશ-અવેર કમ્પ્રેશન છે** હંમેશા ચાલુ** — કોઈ રૂપરેખાંકનની જરૂર નથી. જ્યારે પણ કમ્પ્રેશન ચાલુ હોય ત્યારે તે કિક થાય છે અને લક્ષ્ય પ્રદાતા પ્રોમ્પ્ટ કેશીંગને સપોર્ટ કરે છે (Anthropic, OpenAI, વગેરે); સ્પષ્ટ `cache_control` માર્કર્સ જરૂરી નથી — કેશીંગ પ્રદાતા એકલા ડાઉનગ્રેડને ટ્રિગર કરે છે, અને એકલા માર્કર્સ ક્યારેય કરતા નથી (માર્કર ડિટેક્શન કેશ ટેલિમેટ્રી ફીડ કરે છે, વ્યૂહરચના નિર્ણય નહીં).

OpenRouter માત્ર `anthropic/*` મૉડલ્સ માટે કૅશિંગ પ્રદાતા તરીકે ગણાય છે: Claude કોડ વિનંતીઓ તેમના `cache_control` બ્રેકપોઇન્ટ્સ (વધુમાં વધુ 4) રાખે છે અને ગાર્ડ ઉપસર્ગનું રક્ષણ કરે છે, જ્યારે દરેક અન્ય OpenRouter કુટુંબ (`openai/`, `google/`, `qwen/`, …) છીનવી અને અસુરક્ષિત રહે છે.

### પ્રગતિશીલ વૃદ્ધત્વ

લાંબી વાતચીતો ઘણા સંદેશા વળાંકો એકઠા કરે છે, પરંતુ જૂના વળાંક ઓછા સુસંગત બને છે. `progressiveAging.ts` મોડ્યુલ** વારાફરતી અંતર દ્વારા સંદેશાઓને અધોગતિ કરે છે** (વાર્તાલાપના અંતથી માપવામાં આવેલ અંતર). મોકલેલ ડિફોલ્ટ્સ સાથે (`verbatim: 2, light: 2, moderate: 3`):

- **છેલ્લા 2 વળાંક (અંતર ≤ 2)** : શબ્દશઃ રાખ્યું
- **અંતર 3** : કેવમેન કમ્પ્રેશન (ફિલર દૂર કરવું)
- **અંતર 4 +** : સહાયક સંદેશાઓનો સારાંશ; વપરાશકર્તા સંદેશાઓ તેમની પ્રથમ લાઇનમાં ઘટાડી, 120 અક્ષરો પર મર્યાદિત; અન્ય ભૂમિકાઓ અસ્પૃશ્ય. સિસ્ટમ પ્રોમ્પ્ટ્સ, પહેલેથી જ જૂના સંદેશાઓ અને નવીનતમ વપરાશકર્તા સંદેશ હંમેશા અંતરને ધ્યાનમાં લીધા વિના શબ્દશઃ રાખવામાં આવે છે. કંઈપણ સીધું પડતું નથી, અને `light` બેન્ડ મોકલેલ ડિફોલ્ટ્સ (`light` બરાબર `verbatim`) સાથે અગમ્ય છે.

#### કોડ ઉદાહરણ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### ક્યારે વાપરવું

પ્રગતિશીલ વૃદ્ધત્વ છે** હંમેશા ચાલુ** `aggressive` મોડ — માટે તે `compressAggressive()` નું પગલું 2 છે. અલ્ટ્રા મોડ તેને ચલાવતું નથી. તે ખાસ કરીને અસરકારક છે:

- લાંબા સમયથી ચાલતા કોડિંગ સત્રો
- બહુ-દિવસીય વાર્તાલાપ
- ઘણા ટૂલ કૉલ્સ સાથે એજન્ટિક વર્કફ્લો

### કેવમેન આઉટપુટ મોડ

કેવમેન આઉટપુટ મોડ ઉમેરે છે** સિસ્ટમ પ્રોમ્પ્ટ સૂચનાઓ** જે મોડલને જ ટર્સ આઉટપુટ — માટે પૂછે છે, `lite` લેવલ સંક્ષિપ્ત જવાબો માટે પૂછે છે જે સંપૂર્ણ વાક્યો રાખે છે, `full` તેને "સ્માર્ટ કેવમેનની જેમ ટર્સ રિસ્પોન્ડ કરવા" કહે છે, અને `ultra` ટેલિગ્રાફિક આઉટપુટ માટે પૂછે છે; સૂચનાઓ ફક્ત પૂછે છે, તેઓ તેની ખાતરી આપી શકતા નથી. વિનંતીઓ તેમને `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) દ્વારા પ્રાપ્ત થાય છે : `open-sse/handlers/chatCore.ts` સૌપ્રથમ બેક-કોમ્પેટ શિમ ( `open-sse/services/compression/outputStyles/backCompat.ts` માં`resolveOutputStyleSelection()` ) વડે પસંદગીને ઉકેલે છે, જે જ્યારે `outputStyles` ખાલી હોય છે, ત્યારે `cavemanOutputMode.intensity` પર `terse-prose` આઉટપુટ શૈલીમાં સક્ષમ `cavemanOutputMode` ને મેપ કરે છે (નીચે બેક-કોમ્પેટ જુઓ); બિન-ખાલી `outputStyles` પસંદગીનો ઉપયોગ જેમ છે તેમ થાય છે, અને `cavemanOutputMode.enabled` અને `intensity` કોઈ અસર થતી નથી, જ્યારે તેનું `autoClarity` ટૉગલ હજી પણ લાગુ પડે છે. `outputMode.ts` સૂચના પાઠો ધરાવે છે (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), સામગ્રી બાયપાસ અને પ્લેસમેન્ટ હેલ્પર કે જે ઈન્જેક્શન વાપરે છે; તેના પોતાના `applyCavemanOutputMode()` ઇન્જેક્ટર પાસે કોઈ પ્રોડક્શન કોલર નથી.

#### તે કેવી રીતે કામ કરે છે

આ મોડ ઇનપુટને સંકુચિત કરતું નથી. તે સિસ્ટમ પ્રોમ્પ્ટમાં સૂચના બ્લોક ઉમેરે છે (નીચે ઈન્જેક્શન કેવી રીતે કાર્ય કરે છે તે જુઓ), અને વિનંતી માટે પસંદ કરેલ કોઈપણ ઇનપુટ કમ્પ્રેશન મોડ હજુ પણ પછીથી ચાલે છે, જે હવે બ્લોકને વહન કરે છે. દરેક સ્તર સાથે સમાપ્ત થાય છે તે વહેંચાયેલ સીમાઓ કલમની આગળ, અંગ્રેજી `full` સ્તર વાંચે છે:

> "સ્માર્ટ કેવમેનની જેમ સખત પ્રતિસાદ આપો. લેખો (a/an/the), ફિલર (just/really/basically/actually/simply), pleasantries, હેજિંગ. ટુકડાઓ OK. ટૂંકા સમાનાર્થી (મોટા વ્યાપક નથી, અમલમાં મૂક્યા નથી). તમામ તકનીકી પદાર્થ, કોડ, ભૂલો, URLs, exacter રાખો."

આ ખાસ કરીને આ માટે સારી રીતે કાર્ય કરે છે:

- કોડ જનરેશન (ટેર્સર આઉટપુટ = ઓછા ટોકન્સ)
- ઝડપી પ્રશ્ન અને જવાબ (વિસ્તૃત સમજૂતીની જરૂર નથી)
- બેચ પ્રોસેસિંગ (મહત્તમ થ્રુપુટ)

#### ક્યારે વાપરવું

કેવમેન આઉટપુટ મોડ છે** પસંદ કરો** . કમ્પ્રેશન ચાલુ સાથે (`enabled: true`, કમ્પ્રેશન સેટિંગ્સ પૃષ્ઠ પર માસ્ટર ટૉગલ), તેને `cavemanOutputMode.enabled` સાથે ચાલુ કરો; `intensity` પસંદ કરે છે `lite`, `full` અથવા `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

કમ્પ્રેશન કોમ્બો** આઉટપુટ મોડ** ટૉગલ (`outputMode`, `outputModeIntensity` માં સ્તર ) કૉમ્બો લાગુ પડતી વિનંતીઓ માટે સમાન સ્વીચ સેટ કરે છે, અને `omniroute_set_compression_engine` MCP ટૂલ તેને તેના બુલિયન `outputMode` દલીલ દ્વારા લખે છે. બિન-ખાલી `outputStyles` પસંદગી આ સ્વીચ પર અગ્રતા લે છે. ડેશબોર્ડમાં, સક્ષમ કરી રહ્યા છીએ** ટર્સ ગદ્ય** આઉટપુટ શૈલી સમાન બ્લોકને ઇન્જેક્ટ કરે છે (નીચે આઉટપુટ શૈલીઓ જુઓ).

`terse-cjk` એ બે જગ્યાએ `zh` માટે લોકેલ-ગેટેડ છે. કમ્પ્રેશન સેટિંગ્સ પૃષ્ઠ તેની પંક્તિને ફક્ત ત્યારે જ સૂચિબદ્ધ કરે છે જ્યારે ડેશબોર્ડ UI ભાષા ચાઇનીઝ હોય (`zh-CN` અથવા `zh-TW`), અને `applyOutputStyles()` તેને ત્યારે જ ઇન્જેક્ટ કરે છે જ્યારે વિનંતીની ઉકેલાયેલી ભાષા (નીચે ભાષા પસંદગી જુઓ) `zh` હોય. પંક્તિ છુપાવવાથી સાચવેલ `terse-cjk` પસંદગી સાફ થતી નથી: સેટિંગ્સ API કોઈપણ શૈલી id સ્વીકારે છે, અને પૃષ્ઠ પર અન્ય શૈલીઓ સાચવવાથી તે જાળવી રાખે છે. વિનંતીના સમયે, `applyOutputStyles()` ભાષા તપાસ એ એકમાત્ર લોકેલ ગેટ છે.

#### ઈન્જેક્શન કેવી રીતે કામ કરે છે

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) સૂચિની સામે પસંદગીને ઉકેલે છે (અજ્ઞાત ids અને લોકેલ-અસંગત શૈલીઓ છોડવામાં આવે છે, ક્યારેય ભૂલ થતી નથી; એક પસંદગી જે કોઈ શૈલીને ઉકેલે છે તે મુખ્ય ભાગને યથાવત રાખે છે, `no_styles` તરીકે અવગણવામાં આવે છે), કેટલોગ ક્રમમાં પસંદ કરેલ સૂચનાઓને જોડે છે, સીમાઓની કલમને જોડે છે** એકવાર** (ઉપરાંત સલામતી કલમ, `SAFETY_BOUNDARIES` અથવા તેનું ભાષાંતર, જ્યારે `less-code` અથવા `ponytail` પસંદ કરવામાં આવે છે), અને બ્લોકની શરૂઆત સિંગલ ઇડેમ્પોટન્સી માર્કર (`[OmniRoute Output Styles]`) થી કરે છે, તેથી ફરીથી અરજી કરવી એ નો-ઓપ છે. જ્યારે ઉકેલાયેલી ભાષામાં (નીચે ભાષા પસંદગી જુઓ) અનુવાદ હોય, ત્યારે અંગ્રેજીને બદલે સ્થાનિક સૂચના ઇન્જેક્ટ કરવામાં આવે છે.

બિન-ખાલી `messages` એરે સાથેના શરીર પર, સામગ્રીને બાયપાસ કરતા પહેલા idempotency ચેક ચાલે છે: જ્યારે `[OmniRoute Output Styles]` માર્કર પહેલેથી જ ઉચ્ચ-સ્તરના `system` ફીલ્ડમાં હોય (એક સ્ટ્રિંગ અથવા સામગ્રી-બ્લોક એરે) અથવા સ્ટ્રિંગ સામગ્રી સાથેના સિસ્ટમ સંદેશમાં, શરીરને `already_applied` તરીકે યથાવત રાખવામાં આવે છે અને કોઈ કીવર્ડ ચેક ચાલતું નથી. અન્યથા કન્ટેન્ટ બાયપાસ (`shouldBypassCavemanOutputMode()` in `open-sse/services/compression/outputMode.ts`) છેલ્લા ત્રણ સંદેશાના ટેક્સ્ટને તપાસે છે, તેમની ભૂમિકા ગમે તે હોય, અને જ્યારે તે ટેક્સ્ટ તેની સુરક્ષા, બદલી ન શકાય તેવી-ક્રિયા અથવા સ્પષ્ટતા કીવર્ડ્સ અથવા ઓર્ડર-સંવેદનશીલ ક્રમ સાથે મેળ ખાતી હોય ત્યારે સમગ્ર વળાંક માટે શૈલીઓને છોડી `deploy` `migrate`: `first`, `then`, , `after that`, `before`, `delete`, `drop`, `rollback` અથવા `backup` દ્વારા 240 અક્ષરોની `release`. બાયપાસ ચાલે છે જ્યારે ધ** સ્વતઃ-સ્પષ્ટતા બાયપાસ** ટૉગલ (`cavemanOutputMode.autoClarity`, મૂળભૂત રીતે ચાલુ) ચાલુ છે; ટૉગલને બંધ કરવાથી કીવર્ડ ચેક અવગણે છે.

જ્યારે બાયપાસથી પસાર થવા દે છે, ત્યારે `placeSystemInstruction()` (સમાન ફાઇલ), જે ક્યારેય નવું `messages[0]` બનાવતું નથી, તે બ્લોકને આમાંના પ્રથમ ભાગમાં મૂકે છે:

1. સ્ટ્રિંગ સામગ્રી સાથેનો અગ્રણી સિસ્ટમ સંદેશ: બ્લોક તેના ટેક્સ્ટ પછી જોડવામાં આવે છે.
2. ટોપ-લેવલ `system` ફીલ્ડ: બ્લોક સ્ટ્રિંગના ટેક્સ્ટ પછી ઉમેરવામાં આવે છે, અથવા સામગ્રી-બ્લોક એરેમાં નવા ટેક્સ્ટ બ્લોક તરીકે ઉમેરવામાં આવે છે.
3. શબ્દમાળા સામગ્રી સાથેનો પ્રથમ પછીનો સિસ્ટમ સંદેશ: બ્લોક તેના ટેક્સ્ટ પછી જોડવામાં આવે છે.
4. ઉપરોક્તમાંથી કોઈ નહીં: બ્લોક `messages` ના અંતે નવા સિસ્ટમ સંદેશમાં જાય છે.

`messages` એરે વિનાના શરીર પર (અથવા ખાલી એક સાથે), કોઈપણ સામગ્રી બાયપાસ ચાલતી નથી અને ટોચના સ્તરના `system` ફીલ્ડની સલાહ લેવામાં આવતી નથી. સ્ટ્રિંગ `instructions` ફીલ્ડના ટેક્સ્ટ પછી બ્લોક જોડવામાં આવે છે, સિવાય કે તે ફીલ્ડમાં પહેલાથી જ `[OmniRoute Output Styles]` માર્કર હોય, આ કિસ્સામાં બોડીને `already_applied` તરીકે યથાવત રાખવામાં આવે છે. જ્યારે બોડી પાસે કોઈ સ્ટ્રિંગ `instructions` ફીલ્ડ નથી પરંતુ તે `input` (એક સ્ટ્રિંગ અથવા એરે) ધરાવે છે, ત્યારે બ્લોક `instructions` બને છે, જે ફીલ્ડ ધરાવે છે તે કોઈપણ બિન-સ્ટ્રિંગ મૂલ્યને બદલે છે. સ્ટ્રિંગ `instructions` ફીલ્ડ કે સ્ટ્રિંગ અથવા અરે `input` સાથેનો બૉડી યથાવત રાખવામાં આવે છે અને `no_messages` તરીકે છોડવામાં આવે છે.

#### કેવી રીતે સક્ષમ કરવું

ડેશબોર્ડમાં:** કમ્પ્રેશન સંદર્ભ → કમ્પ્રેશન સેટિંગ્સ** (`/dashboard/context/settings`), આઉટપુટ શૈલીઓ વિભાગ: on/off ટૉગલ અને સ્તર પસંદગીકાર સાથે શૈલી દીઠ એક પંક્તિ. જ્યારે કમ્પ્રેશન પોતે ચાલુ હોય ત્યારે સ્ટાઇલ ઇન્જેક્શન આપે છે (પૃષ્ઠનું મુખ્ય ટૉગલ, `enabled`). આ** સ્વતઃ-સ્પષ્ટતા બાયપાસ** ટૉગલ ચાલુ છે** કેવમેન** પૃષ્ઠ (`/dashboard/context/caveman`), તેનામાં** આઉટપુટ મોડ** કાર્ડ પ્રોગ્રામેટિકલી, કમ્પ્રેશન રૂપરેખા પસંદગીને આ રીતે ચાલુ રાખે છે:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

બેક-કોમ્પેટ: જ્યારે `outputStyles` ખાલી હોય, ત્યારે લેગસી `cavemanOutputMode.enabled` સેટિંગ નકશા `cavemanOutputMode.intensity` પર `terse-prose` પર બનાવે છે. બ્લોક પછી `[OmniRoute Output Styles]` માર્કરથી શરૂ થાય છે, જ્યાં લેગસી `applyCavemanOutputMode()` ઇન્જેક્ટર `[OmniRoute Caveman Output Mode]` લખે છે. માર્કરની નીચે, લખાણ en, pt-BR, es, de, fr, it, ru, id અને vi માં લેગસી ઈન્જેક્શન સાથે મેળ ખાય છે; ja અને zh માં તે બાઉન્ડ્રી કલમ પહેલાં એક વધારાની જગ્યા ધરાવે છે. `terse-prose` pt-BR, es, de, fr, it, ru, zh, ja, id અને vi માં ભાષાંતર કરે છે, તેથી એક વિનંતી જેની ઉકેલાયેલી ભાષા `hu` છે તેને અંગ્રેજી ટેક્સ્ટ મળે છે જ્યાં લેગસી ઇન્જેક્ટરે તેના હંગેરિયનનો ઉપયોગ કર્યો હતો.

Output-style language selection (`resolveOutputStyleLanguage()` in `outputStyles/apply.ts`): with `languageConfig.enabled` on, `autoDetect` samples the latest user message in the request's `messages` array that has text (string content, or the `text` of its content parts) and runs the Caveman engine's detector (`detectCompressionLanguage()`) on it. The detector returns `zh` for text with Han characters and no kana; otherwise it returns whichever of `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` and `id` has the most hint matches, and `en` when none match — text it cannot classify gets English, never `defaultLanguage`, and `vi` is never detected although the styles ship `vi` text. A Responses API body keeps its turns in `input`, which is not sampled, so it gets `defaultLanguage`, then English. When no user message in `messages` has text, or with `autoDetect` off, `defaultLanguage` applies, then English. With `languageConfig.enabled` off, the language is English — unless a compression combo applies to the request (a combo assigned to the request's routing combo, or the default compression combo chatCore falls back to for the built-in stacked pipeline): applying a combo turns `languageConfig.enabled` on for that request and sets `defaultLanguage` from the combo's language packs (the saved value if it is one of the combo's packs, otherwise the combo's first pack, which defaults to `en`), while the saved `autoDetect` (on by default) still applies. The Caveman input engine picks its rule-pack language differently — per text part and, with auto-detect off, gated on `enabledPacks`.

શૈલી × ભાષા મેટ્રિક્સ `tests/unit/compression/output-styles-i18n-matrix.test.ts` દ્વારા પિન કરેલ છે: દરેક કેટલોગ શૈલીને પરીક્ષણના `BASELINE_LANGUAGES` માં પ્રવેશની જરૂર છે; લોકેલ-ગેટેડ ન હોય તેવી શૈલીએ pt-BR અનુવાદ મોકલવો આવશ્યક છે (લોકેલ-ગેટેડ `terse-cjk` આ નિયમમાંથી મુક્તિ છે) સિવાય કે તે `KNOWN_ENGLISH_ONLY` માં સૂચિબદ્ધ હોય, જે ફક્ત — પર કોઈ ભાષાંતર વિનાની શૈલીઓ ધરાવી શકે છે અને કોઈપણ અનુવાદ પરીક્ષણમાં નિષ્ફળ જાય છે; અને શૈલી પરીક્ષણમાં નિષ્ફળ જાય છે જ્યારે તે તેની `BASELINE_LANGUAGES` એન્ટ્રી સૂચિબદ્ધ ભાષા ગુમાવે છે. શૈલી ઉમેરવા માટે, જુઓ [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### સાધન પરિણામ સંકોચન

`open-sse/services/compression/toolResultCompressor.ts` માં`compressToolResult()` ટૂલ-પરિણામ ટેક્સ્ટને સંકુચિત કરે છે** 5 વ્યૂહરચના** . તે તેમને આ ક્રમમાં અજમાવશે, અને પ્રથમ સક્ષમ વ્યૂહરચના જેની ચકાસણી સામગ્રી સાથે મેળ ખાય છે તે પરિણામ નક્કી કરે છે:

1. **`fileContent`** : 3 અથવા વધુ લીટીઓની સામગ્રી જેમાં ઓછામાં ઓછી એક લીટી, અગ્રણી ઇન્ડેન્ટેશનને અવગણીને, `import `, `export `, `function `, `class `, `const `, `let `, `var ` અથવા `return ` (કીવર્ડ વત્તા સ્પેસ) થી શરૂ થાય છે, અથવા `if`, `for` અથવા ` (` `(` `while` અથવા તેને અનુસરે છે પ્રથમ 20 અને છેલ્લી 5 લીટીઓ, ચિહ્નિત મધ્યમ સાથે.
2. **`grepSearch`** : `<path>:<digits>:` ફોર્મની ઓછામાં ઓછી એક લીટી સાથેની સામગ્રી, જ્યાં પ્રથમ કોલોન પહેલાના લખાણમાં કોઈ વ્હાઇટસ્પેસ હોતી નથી, ફક્ત તે જ લીટીઓ રાખે છે, વધુમાં વધુ 30, ત્યારબાદ કોઈપણ વધુ મેચોની ગણતરી અને મેળ ખાતી ફાઈલોની સૂચિ; દરેક બીજી લાઇન નાખવામાં આવે છે. આવી એક લાઇન વ્યૂહરચનાને ટ્રિગર કરવા માટે પૂરતી છે, તેથી `12:30:45` જેવા ટાઇમસ્ટેમ્પથી શરૂ થતી લોગ લાઇન પણ ગણાય છે.
3. **`shellOutput`** : આઉટપુટ કે જેમાં ANSI CSI ક્રમ હોય છે (`ESC[` પછી અંકો અથવા અર્ધવિરામ પછી એક અક્ષર, જેમ કે રંગ કોડમાં હોય છે) અથવા ટેક્સ્ટમાં ગમે ત્યાં વ્હાઇટસ્પેસ દ્વારા અનુસરવામાં આવેલ `$` તે સિક્વન્સ ગુમાવે છે (અન્ય એસ્કેપ્સ, જેમ કે `ESC[?25l` અથવા OSC વિન્ડો-શીર્ષક અને ક્રમની પુનરાવર્તિત 5 સાથે, તેની અંતિમ લાઇનને પુનરાવર્તિત રાખવામાં આવે છે) રેખાઓ તૂટી. કારણ કે આ ચેક `json` અને `errorMessage` પહેલા ચાલે છે, JSON અથવા ભૂલ આઉટપુટ કે જેમાં આવા `$` હોય છે જ્યારે `shellOutput` ચાલુ હોય ત્યારે તેમના સુધી ક્યારેય પહોંચતું નથી.
4. **`json`** : 2,000 અક્ષરોથી વધુનો JSON પેલોડ જે `{` અથવા `[` (વૈકલ્પિક વ્હાઇટસ્પેસ પછી) થી શરૂ થાય છે અને પાર્સનો સારાંશ આપવામાં આવે છે: 7 થી વધુ વસ્તુઓનો એરે તેની પ્રથમ 5 અને છેલ્લી 2 વસ્તુઓ અને તેની કુલ ગણતરી રાખે છે, અને ઑબ્જેક્ટ તેની પ્રથમ 20 કીઓ રાખે છે, દરેક નેસ્ટેડ ઑબ્જેક્ટ અથવા એરે માટે એરે (NQZ) મૂલ્ય સાથે બદલો. લંબાઈ) અને એક `{…N keys}` માર્કર પ્રથમ 20 થી આગળ નીકળી ગયેલી કીની ગણતરી કરે છે. સ્કેલર મૂલ્યો સંપૂર્ણ નકલ કરવામાં આવે છે, તેથી 20 કી અથવા તેનાથી ઓછા કોઈ નેસ્ટેડ મૂલ્યો વગરના ઑબ્જેક્ટને માત્ર ફરીથી ઇન્ડેન્ટેડ — કરવામાં આવે છે અને એક મિનિફાઇડ અક્ષરો મેળવે `_remaining_<N>_keys` અને યથાવત રહે છે.
5. **`errorMessage`** : આઉટપુટ કે જેમાં, ગમે ત્યાં અને કોઈપણ અક્ષરના કિસ્સામાં, `error:`, `error ` (જેમ કે `no error found` માં સ્પેસ દ્વારા અનુસરવામાં આવેલો શબ્દ), `[error]`, `exception:`, `exception `, `[exception]` અથવા `traceback` તેની પ્રથમ લાઇન, પછીની 10 લીટીઓ અને છેલ્લી 3, તેમની વચ્ચે `… [N frames elided] …` માર્કર સાથે રાખે છે. માર્કર ત્યારે જ દેખાય છે જ્યારે 13 થી વધુ લીટીઓ પ્રથમ લીટીને અનુસરે છે, તેથી 14 લીટીઓ અથવા તેનાથી ઓછીની ભૂલનું આઉટપુટ ટૂંકું કરવામાં આવતું નથી (12 અથવા 13 લીટીઓ પર છેલ્લી 3 પુનરાવર્તિત લીટીઓ પહેલેથી જ રાખવામાં આવી છે).

વ્યૂહરચના મેચ થયા પછી, એક પણ જે કંઈ બચાવતું નથી, પછીની વ્યૂહરચનાઓ અજમાવવામાં આવતી નથી. જ્યારે મેચિંગ વ્યૂહરચના કોઈ અંદાજિત ટોકન્સ બચાવતી નથી (લંબાઈ ÷ 4, રાઉન્ડ અપ) — ઉદાહરણ તરીકે 25 અથવા ઓછી લાઇનની કોડ-જેવી ફાઇલ, અથવા 7 આઇટમ્સ અથવા ઓછા — સાથે 2,000 અક્ષરોથી વધુની JSON એરે `saved` `compressAnthropicToolResultBlock()` `compressAggressive()` અથવા નીચે, જ્યારે `compressToolResult()` પોતે હજુ પણ તે વ્યૂહરચનાનું આઉટપુટ આપે છે. ટૂલ-પરિણામ પગલું એ છેલ્લો શબ્દ નથી: એન્જિનનું ફોલબેક સારાંશ હજી પણ 8,192 અક્ષરો (`maxTokensPerMessage`, 2,048, ગુણ્યા 4) કરતાં લાંબા સમય સુધી `tool` અથવા `function` સંદેશને ટૂંકાવી શકે છે.

#### ક્યારે વાપરવું

ટૂલ રિઝલ્ટ કમ્પ્રેશન એ એગ્રેસિવ એન્જિનનું પગલું 1 છે (`compressAggressive()` માં `open-sse/services/compression/aggressive.ts`), તેથી તે આક્રમક મોડમાં અને સ્ટેક્ડ પાઇપલાઇનના `aggressive` સ્ટેપમાં ચાલે છે. તે OpenAI-shape `tool` અને `function` સંદેશાઓ અને Anthropic `tool_result` બ્લોકની અંદરના ટેક્સ્ટને સંકુચિત કરે છે. દરેક વ્યૂહરચના `aggressive.toolStrategies` હેઠળ તેની પોતાની સ્વિચ ધરાવે છે, બધુ ડિફોલ્ટ રૂપે ચાલુ છે. ડેશબોર્ડમાં, સ્વીચો કેવમેન પેજમાં છે** ઉન્નત** કમ્પ્રેશન ચાલુ હોય ત્યારે જુઓ અને ડિફોલ્ટ મોડ એગ્રેસીવ છે.

### સ્ટેક્ડ પાઇપલાઇન

સ્ટેક્ડ મોડ ચાલે છે** ક્રમમાં બહુવિધ એન્જિન** — સામાન્ય રીતે RTK પ્રથમ (ટૂલ આઉટપુટ પર 60-90% બચત), પછી બાકીના ટેક્સ્ટ પર કેવમેન (~ 46% ઇનપુટ બચત). બનેલું, તે છે** 78-95% પાત્ર શ્રેણી** (ઉપર અપસ્ટ્રીમ બચત ગણિત જુઓ): `1 - (1 - 0.60..0.90) × (1 - 0.46)` એવરેજ ≈ 89%.

#### તે કેવી રીતે કામ કરે છે

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### ક્યારે વાપરવું

આ માટે સ્ટેક્ડ મોડનો ઉપયોગ કરો:

- ટૂલ-હેવી વર્કફ્લો (એજન્ટિક કોડિંગ, સંશોધન)
- ખર્ચ-સંવેદનશીલ બેચ પ્રક્રિયા
- જ્યારે તમને મહત્તમ ટોકન બચતની જરૂર હોય

સ્ટૅક્ડ પાઇપલાઇન્સ વૈશ્વિક `stackedPipeline` કમ્પ્રેશન સેટિંગ દ્વારા અથવા રૂટીંગ કોમ્બોને સોંપેલ નામના કમ્પ્રેશન કોમ્બો દ્વારા ગોઠવવામાં આવે છે (ઉપર-કોમ્બો ઓવરરાઇડ જુઓ) — ઓટો-કોમ્બો `modePack` દ્વારા નહીં (તે ફીલ્ડ ફક્ત સ્વતઃ-કોમ્બો મોડલ પસંદગીને ફરીથી વજન આપે છે, અને `stacked` એ માન્ય pack નામ નથી).

## કોમ્પ્રેશન કોમ્બો ઓવરરાઇડ્સ

વિવિધ ઉપયોગના કિસ્સાઓ માટે વર્તનને વધુ ચોકસાઈથી ગોઠવવા તમે વૈશ્વિક કોમ્પ્રેશન મોડને **દરેક કોમ્બો માટે** ઓવરરાઇડ કરી શકો છો:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

આ નીચેના માટે ઉપયોગી છે:

- **કોડિંગ કોમ્બો**: લાંબા સત્રો માટે `aggressive` મોડનો ઉપયોગ કરો
- **ઝડપી પ્રશ્નોત્તરી કોમ્બો**: ઝડપી પ્રતિસાદો માટે `lite` મોડનો ઉપયોગ કરો
- **ટૂલ-હેવી કોમ્બો**: મહત્તમ બચત માટે `stacked` મોડનો ઉપયોગ કરો
- **પ્રોડક્શન કોમ્બો**: કૅશિંગ પ્રદાતાઓ માટે ઓવરરાઇડ બંધ રાખો — હંમેશાં સક્રિય
  કૅશ-અવેર સમાયોજન `aggressive`/`ultra`ને આપમેળે `standard`માં ડાઉનગ્રેડ કરે છે
  (પસંદ કરી શકાય એવો કોઈ `cache-aware` મોડ નથી)
