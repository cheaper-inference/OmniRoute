## ચેટ પૂર્ણતાઓ

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### કસ્ટમ હેડર્સ

| હેડર                     | દિશા     | વર્ણન                                                                                                                                                                                                                                     |
| ------------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | વિનંતી   | કૅશને બાયપાસ કરવા માટે `true` પર સેટ કરો                                                                                                                                                                                                  |
| `x-omniroute-no-memory`  | વિનંતી   | આ વિનંતી માટે મેમરી + કૌશલ્ય ઇન્જેક્શન છોડવા `true` પર સેટ કરો (નો-કૅશ જેવું જ; પ્રતિ-કૉલ ટોકન/ખર્ચનો વધારાનો ભાર ટાળે છે)                                                                                                                |
| `X-OmniRoute-Progress`   | વિનંતી   | પ્રગતિ ઇવેન્ટ્સ માટે `true` પર સેટ કરો                                                                                                                                                                                                    |
| `X-Session-Id`           | વિનંતી   | બાહ્ય સત્ર એફિનિટી માટે સ્ટિકી સત્ર કી                                                                                                                                                                                                    |
| `x_session_id`           | વિનંતી   | અન્ડરસ્કોર વેરિઅન્ટ પણ સ્વીકારવામાં આવે છે (સીધું HTTP)                                                                                                                                                                                   |
| `X-OmniRoute-Session-Id` | વિનંતી   | કૉલર દ્વારા આપેલ સત્ર/વાતચીત ટૅગ (મેમરીને પણ પૂરો પાડે છે). હાજર હોય ત્યારે, પ્રતિ-સત્ર ખર્ચ એટ્રિબ્યુશન (#8249) માટે તેને `call_logs.session_tag` માં જેમનો તેમ સંગ્રહિત કરવામાં આવે છે — ગેરહાજર હોય ત્યારે ક્યારેય બનાવવામાં આવતું નથી |
| `Idempotency-Key`        | વિનંતી   | ડિડુપ્લિકેશન કી (5s વિન્ડો)                                                                                                                                                                                                               |
| `X-Request-Id`           | વિનંતી   | વૈકલ્પિક ડિડુપ્લિકેશન કી                                                                                                                                                                                                                  |
| `x-omniroute-connection` | વિનંતી   | સિંગલ-મોડેલ વિનંતીને તેના id દ્વારા એક પ્રદાતા કનેક્શન (એકાઉન્ટ) સાથે પિન કરો — [દરેક વિનંતી માટે એકાઉન્ટ પિનિંગ](#account-pinning-per-request) જુઓ                                                                                       |
| `X-OmniRoute-Cache`      | પ્રતિસાદ | `HIT` અથવા `MISS` (નોન-સ્ટ્રીમિંગ)                                                                                                                                                                                                        |
| `X-OmniRoute-Idempotent` | પ્રતિસાદ | ડિડુપ્લિકેટ કરાયેલ હોય તો `true`                                                                                                                                                                                                          |
| `X-OmniRoute-Progress`   | પ્રતિસાદ | પ્રગતિ ટ્રૅકિંગ ચાલુ હોય તો `enabled`                                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | પ્રતિસાદ | OmniRoute દ્વારા ઉપયોગમાં લેવાયેલ અસરકારક સત્ર ID                                                                                                                                                                                         |
| `X-OmniRoute-Request-Id` | પ્રતિસાદ | વિનંતી કોરિલેશન id (જ્યારે જાણીતું હોય)                                                                                                                                                                                                   |
| `X-OmniRoute-Version`    | પ્રતિસાદ | OmniRoute બિલ્ડ વર્ઝન (હંમેશાં હાજર)                                                                                                                                                                                                      |
| `X-OmniRoute-Cost-Saved` | પ્રતિસાદ | HIT પર કૅશ દ્વારા બચાવાયેલ USD (માત્ર કૅશ હિટ્સ)                                                                                                                                                                                          |
| `X-OmniRoute-Decision`   | પ્રતિસાદ | રૂટિંગ ટ્રેસ: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` એ કોમ્બો વ્યૂહરચના છે અથવા નોન-કોમ્બો વિનંતી માટે `single`) — પૂર્ણતા પ્રતિસાદોમાં હંમેશાં હાજર હોય છે                                                        |

> Nginx નોંધ: જો તમે અન્ડરસ્કોરવાળા હેડર્સ પર આધાર રાખતા હોવ (ઉદાહરણ તરીકે `x_session_id`), તો `underscores_in_headers on;` સક્ષમ કરો.

#### દરેક રિક્વેસ્ટ માટે એકાઉન્ટ પિનિંગ

જ્યારે કોઈ પ્રદાતા પાસે અનેક કનેક્શન્સ (એકાઉન્ટ્સ અથવા કીઝ) હોય, ત્યારે OmniRoute સામાન્ય રીતે તેની એકાઉન્ટ-પસંદગી વ્યૂહરચના દ્વારા તેમાંથી એક પસંદ કરે છે. તેના બદલે, રિક્વેસ્ટ `x-omniroute-connection` હેડર વડે કોઈ ચોક્કસ કનેક્શનને પિન કરી શકે છે:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id ક્યાંથી મેળવવું.** ડૅશબોર્ડમાં પ્રદાતાનું પેજ ખોલો
  (**Dashboard → Providers → <provider>**) અને કનેક્શનની પંક્તિમાં રહેલી `xxxxxxxx…` id ચિપ પર ક્લિક કરો
  — તે સંપૂર્ણ કનેક્શન id કૉપી કરે છે.
- **કઈ રિક્વેસ્ટ્સ તેને માન્ય રાખે છે.** `/v1/chat/completions`, `/v1/messages` અને `/v1/responses`
  પરની સિંગલ-મોડલ રિક્વેસ્ટ્સ (`provider/model`). કોમ્બોઝ હેડરને અવગણે છે: તેના બદલે
  દરેક કોમ્બો સ્ટેપ માટે તેના પોતાના કનેક્શન દ્વારા એકાઉન્ટ પિન કરો.
- **પિન કડક છે, માત્ર પસંદગી નથી.** પિન કરેલું કનેક્શન જ વિશિષ્ટ રીતે વપરાય છે. રિક્વેસ્ટની
  અંદર નિષ્ફળતા થાય તો તે એકાઉન્ટનો કૂલડાઉન નોંધે છે, પરંતુ એ જ પ્રદાતાના અન્ય
  એકાઉન્ટ પર **રોટેટ થતું નથી**.
- **કૂલડાઉન અને ક્વોટા પિનને મુક્ત કરે છે.** જ્યારે પિન કરેલું કનેક્શન કૂલડાઉનમાં હોય,
  ક્વોટા સમાપ્ત થઈ ગયો હોય અથવા ક્વોટા નીતિ દ્વારા અવરોધિત હોય, ત્યારે પછીની રિક્વેસ્ટ્સ
  પિન ન કરેલા ટ્રાફિકની જેમ જ પ્રદાતાના અન્ય કનેક્શન્સ પર ફૉલબૅક થાય છે.
- **અજાણ્યા અથવા અક્ષમ કરેલા ids નિષ્ફળ જાય છે.** જે id પ્રદાતાના સક્રિય પૂલમાં ન હોય (ડિલીટ કરેલું,
  નિષ્ક્રિય કરેલું અથવા અન્ય પ્રદાતાનું હોય), તેના કારણે કોઈ પાત્ર એકાઉન્ટ બાકી રહેતું નથી,
  તેથી રિક્વેસ્ટને ચૂપચાપ બીજે રૂટ કરવાને બદલે તે નિષ્ફળ જાય છે.

Claude Code `ANTHROPIC_CUSTOM_HEADERS` દ્વારા કસ્ટમ હેડર્સ મોકલે છે. તેને `~/.claude/settings.json`
ના `env` બ્લોકમાં મૂકો અથવા દરેક પ્રોજેક્ટ માટે અલગ એકાઉન્ટ પિન કરવા પ્રોજેક્ટ-સ્તરની
`.claude/settings.json` ફાઇલમાં મૂકો:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

સ્રોત: `src/sse/handlers/chat.ts` (હેડર રીડ), `src/sse/services/auth.ts` અને
`src/sse/services/sessionAffinityPin.ts` (પિન રિલીઝ અને પૂલમાં ગેરહાજરીની ચકાસણી).

> **કિંમત ટેલિમેટ્રી હેડર્સ:** નોન-સ્ટ્રીમિંગ સફળ પ્રતિસાદોમાં `X-OmniRoute-*` કિંમત-ટેલિમેટ્રી સેટ પણ હોય છે — `X-OmniRoute-Response-Cost` (USD, નિશ્ચિત 10 દશાંશ અંકો; મફત/કિંમત નક્કી ન થયેલા માટે `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit`, અને `X-OmniRoute-Fallback-Attempts` (માત્ર જ્યારે > 0 હોય), તેમજ `X-OmniRoute-Request-Id` અને `X-OmniRoute-Version`. આ હેડર્સ chat completions, `/v1/responses`, `/v1/messages`, **અને મીડિયા એન્ડપોઇન્ટ્સ** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations`, અને `/v1/moderations` (હંમેશાં કિંમત `0`) દ્વારા ઉત્સર્જિત થાય છે. જ્યારે કિંમત ઉપલબ્ધ હોય ત્યારે મીડિયા ખર્ચની ગણતરી મોડેલિટી દીઠ (પ્રતિ-ઇમેજ, પ્રતિ-સેકન્ડ, પ્રતિ-અક્ષર, પ્રતિ સર્ચ-યુનિટ) કરવામાં આવે છે; અન્યથા `0` (ફેઇલ-ઓપન) હોય છે.

> **કૅશ-હિટ ખર્ચના અર્થશાસ્ત્ર:** સિમેન્ટિક-કૅશ HIT (`X-OmniRoute-Cache-Hit: true`) પર કોઈ અપસ્ટ્રીમ કૉલ થતો નથી, તેથી `X-OmniRoute-Response-Cost` `0.0000000000` હોય છે (હિટને સર્વ કરવાની **વધારાની** કિંમત). મૂળ/થવાની સંભાવના ધરાવતી કિંમત `X-OmniRoute-Cost-Saved` માં અલગથી રિપોર્ટ થાય છે. બિલિંગ ઉપભોક્તાઓએ `X-OmniRoute-Response-Cost` નો સરવાળો કરવો જોઈએ (હિટ્સ માટે કોઈ ખર્ચ નથી); કૅશ ઍનાલિટિક્સ `X-OmniRoute-Cost-Saved` ને એકત્રિત કરી શકે છે.

## વિશિષ્ટ સંચાલિત સત્ર લીઝ

વિશિષ્ટ સંચાલિત સત્ર લીઝિંગ એ પસંદગીયુક્ત, ક્લાયન્ટ-નિરપેક્ષ રાઉટિંગ કરાર છે: એક સક્રિય માલિક
એક પાત્ર OmniRoute કનેક્શન ધરાવે છે. તે કોઈ મોડલ લીઝ કરતું નથી, OAuth જરૂરી બનાવતું નથી, કોઈ
ચોક્કસ ક્લાયન્ટને ઓળખતું નથી અથવા કોઈ ચોક્કસ પ્રદાતા જરૂરી બનાવતું નથી.

પ્રમાણીકરણ કરતી API કી પાસે `lease:exclusive` સ્કોપ અને સ્પષ્ટપણે બિન-ખાલી
`allowedConnections` સૂચિ હોવી આવશ્યક છે. ડેટાબેઝ મ્યુટેશન સીમા કી બનાવતી વખતે અને
આંશિક અપડેટ દરમિયાન બંને ફીલ્ડને એકસાથે લાગુ કરે છે.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

સફળ acquire, renew અને release પ્રતિસાદો ટાઇમસ્ટૅમ્પ, `state` અને ચોક્કસ ધન
`generation` દર્શાવે છે, પરંતુ પસંદ કરેલું કનેક્શન અથવા ક્રેડેન્શિયલ્સ ક્યારેય દર્શાવતા નથી. Renew અને release
JSON બોડીમાં generation આપે છે:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

સક્રિય લીઝ માલિક તેના વર્તમાન બાઇન્ડિંગ માટે સ્પષ્ટ રીતે ગોપનીયતા-સુરક્ષિત ડિસ્પ્લે મેટાડેટાની વિનંતી કરી શકે છે:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

આ પસંદગીયુક્ત status ક્રિયા એક જ ડેટાબેઝ ટ્રાન્ઝેક્શનમાં અપારદર્શક માલિક, પ્રમાણિત સંચાલિત API કી અને ચોક્કસ
સક્રિય generation દ્વારા ફેન્સ કરવામાં આવે છે. `displayName` માત્ર ટ્રિમ કરેલું, ગોઠવેલું
કનેક્શન નામ છે; જ્યારે કોઈ સુરક્ષિત ગોઠવેલું નામ અસ્તિત્વમાં ન હોય ત્યારે તે `null` હોય છે. OmniRoute ક્યારેય તેના સ્થાને
ઇમેઇલ અથવા જનરેટ કરેલી એકાઉન્ટ ઓળખ મૂકતું નથી. પ્રદાતા મૂલ્ય બિન-સંવેદનશીલ ડિસ્પ્લે લેબલ છે અને ક્યારેય
જનરેટ કરેલું સુસંગત-પ્રદાતા ઓળખચિહ્ન નથી. ક્રેડેન્શિયલ્સ, ટોકન્સ, કુકીઝ, કાચા કનેક્શન અથવા API
કી ids, માલિક હૅશ, ફેન્સિંગ સિક્રેટ્સ અને આંતરિક રાઉટિંગ ડેટા બાકાત રાખવામાં આવે છે.

ખોટી કી, ખોટો માલિક, જૂનું generation, ગુમ થયેલું, સમાપ્ત થયેલું, રિલીઝ થયેલું અને અમાન્ય બનાવેલું lookup—આ બધાં
કનેક્શન મેટાડેટા વિના સમાન `409 LEASE_FENCE_STALE` ભૂલ પરત કરે છે. ક્ષમતા-પ્રતીક્ષા પ્રતિસાદ મેળવનારા ક્લાયન્ટ પાસે તપાસવા માટે કોઈ સક્રિય બાઇન્ડિંગ હોતું નથી. જ્યારે રાઉટિંગ સક્રિય લીઝનું સંક્રમણ કરે છે,
ત્યારે એ જ generation માન્ય રહે છે અને status પરમાણ્વિક રીતે નવું બાઇન્ડિંગ પરત કરે છે, જૂનું ક્યારેય નહીં.
હાલના ક્લાયન્ટ્સ યથાવત્ રહે છે કારણ કે acquire, renew, release અને પ્રતીક્ષા પ્રતિસાદો
તેમના અગાઉના આકારો જાળવી રાખે છે.

આ સર્વર કરાર મૂળ OpenAI Codex `/status` ને બદલતો નથી. હાલમાં મૂળ Codex તેના
મોડલ પ્રદાતા અને બિલ્ટ-ઇન પ્રમાણીકરણ/એકાઉન્ટ સ્થિતિની જાણ કરે છે, પરંતુ મનસ્વી કસ્ટમ
પ્રદાતા એકાઉન્ટ મેટાડેટા રેન્ડર કરતું નથી; ભવિષ્યના ક્લાયન્ટ એકીકરણે આ ક્રિયાને કૉલ કરીને
`connection.displayName` કેવી રીતે દર્શાવવું તે નક્કી કરવું આવશ્યક છે.

ત્યારબાદ દરેક સંચાલિત ઇન્ફરન્સ વિનંતી બંને નિયંત્રણ હેડર આપે છે:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

દરેક સમર્થિત upstream પ્રયાસથી તરત પહેલાં ચોક્કસ માલિક, generation, સક્રિય કનેક્શન અને પ્રમાણિત API કીને
ફેન્સ કરવામાં આવે છે. બીજા કી સાથે માલિક અને generation ફરી ચલાવવું નિષ્ફળ જાય છે, ભલે
તે કી સમાન કનેક્શનને મંજૂરી આપતી હોય. કાચા માલિકો કાયમી સંગ્રહિત થતા નથી, લૉગ થતા નથી, વિનંતી
સ્નૅપશૉટમાં જાળવાતા નથી અથવા upstream ફૉર્વર્ડ થતા નથી.

કામચલાઉ સ્પર્ધા HTTP `429` ને `Retry-After` સાથે તથા નીચે મુજબ પરત કરે છે:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

આ પ્રતિસાદનો અર્થ માત્ર એટલો છે કે સામાન્ય પાત્ર સેટ બિન-ખાલી હતો અને દરેક મુક્ત ઉમેદવાર
અન્ય સક્રિય લીઝ દ્વારા ધારિત હતો. અસમર્થિત મોડલ્સ/પ્રદાતાઓ, નીતિ અસંગતતા, cooldown, ક્વોટા,
આરોગ્ય અને અન્ય સામાન્ય પાત્રતા નિષ્ફળતાઓ તેમના હાલના OmniRoute પ્રતિસાદો જાળવી રાખે છે.

### `x-omniroute-compression`

કમ્પ્રેશન યોજનાનું પ્રતિ-વિનંતી ઓવરરાઇડ. સર્વોચ્ચ અગ્રતા — રાઉટિંગ-કોમ્બો
ઓવરરાઇડ, સક્રિય પ્રોફાઇલ, ઑટો-ટ્રિગર અને પૅનલના ડિફૉલ્ટ કરતાં અગ્રતા મેળવે છે. મૂલ્યો:

| મૂલ્ય         | અસર                                                                                                |
| ------------- | -------------------------------------------------------------------------------------------------- |
| `off`         | આ વિનંતી માટે કોઈ કમ્પ્રેશન નહીં.                                                                  |
| `default`     | પૅનલમાંથી મેળવેલી ડિફૉલ્ટ પ્રોફાઇલ (સક્રિય પ્રોફાઇલને અવગણે છે). લૉસી એન્જિનો બંધ રાખવામાં આવે છે. |
| `safe`        | માત્ર ડીડુપ્લિકેશન અને વ્હાઇટસ્પેસ ફોલ્ડિંગ.                                                       |
| `allow-lossy` | સારાંશો અને શૈલીના પુનર્લેખન સહિત, આ વિનંતી માટે ઑપરેટર યોજના જાળવે છે.                            |
| `engine:<id>` | સક્ષમ હોય ત્યારે એક જ એન્જિન, દા.ત. `engine:rtk`. તે એન્જિન માટે પ્રતિ-વિનંતી પસંદગી.              |
| `<combo>`     | નામવાળું કોમ્બો, પહેલા નામ (કેસ-ઇન્સેન્સિટિવ) દ્વારા અને પછી id દ્વારા મેળ ખાતું.                  |

નોંધો:

- અજ્ઞાત મૂલ્યો અવગણવામાં આવે છે (વિનંતી ક્યારેય નકારાતી નથી); રિઝોલ્યુશન સામાન્ય ઑપરેટર અગ્રતા તરફ આગળ વધે છે.
- જો એકથી વધુ કોમ્બો સમાન નામ ધરાવતા હોય, તો નિર્ધારિત મેળ માટે કોમ્બો **id** આપો.
- જે કોમ્બોનું નામ `off` અથવા `default` હોય તેને નામ દ્વારા પસંદ કરી શકાતું નથી (આ કીવર્ડ્સનું અર્થઘટન પહેલાં થાય છે); આવા કોમ્બોને તેના id દ્વારા સંદર્ભિત કરો.
- મુખ્ય કમ્પ્રેશન સ્વિચ કડક અવરોધ છે: જ્યારે કમ્પ્રેશન વૈશ્વિક રીતે અક્ષમ હોય, ત્યારે આ હેડર તેને સક્ષમ કરી શકતું નથી.

લાગુ કરેલી યોજના પ્રતિસાદ હેડરમાં પાછી દર્શાવવામાં આવે છે:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

જ્યાં `<source>` એ `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` અથવા `off` પૈકીનું એક છે.

## એમ્બેડિંગ્સ

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

ઉપલબ્ધ પ્રદાતાઓ: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

કૅટલૉગ ids `provider/model` સ્વરૂપે હોય છે (ઉદાહરણ: `jina-ai/jina-embeddings-v5-omni-small`). રજિસ્ટ્રીમાં દેખાતા માત્ર Jina model ids (ઉદાહરણ તરીકે `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) પણ રિઝોલ્વ થાય છે. Jina embed/rerank/classify/segment પહેલાં ડૅશબોર્ડના `jina-ai` ક્રેડેન્શિયલ્સનો ઉપયોગ કરે છે; કોઈ ડૅશબોર્ડ કી અસ્તિત્વમાં ન હોય ત્યારે જ `JINA_AI_API_KEY` ફૉલબૅક તરીકે વપરાય છે. `jina-reader` કાર્ડ માત્ર Reader / `r.jina.ai` માટે છે (`POST /v1/web/fetch`) અને તે ક્યારેય embeddings અથવા rerank પ્રદાન કરતું નથી.

મલ્ટિમોડલ સપોર્ટ દર્શાવતા રજિસ્ટ્રી models વધુમાં વધુ 32 પ્રદાતા-નિરપેક્ષ સંરચિત
આઇટમ્સ પણ સ્વીકારે છે. મીડિયા આઇટમના પ્રકારો `text`, `image`, `audio`, `video`, અને `document` છે. તેમનો મીડિયા `source`
કાં તો `{"type":"url","url":"https://..."}` અથવા
`{"type":"base64","data":"...","media_type":"..."}` હોય છે.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
અને ફૅમિલી ઉપનામ `jina-ai/jina-embeddings-v5-omni` → omni-small) Jinaના મૂળ
EmbeddingsV5Request ડૉક્સ પણ સ્વીકારે છે અને તેમને **યથાવત્ ફૉર્વર્ડ કરે છે** `https://api.jina.ai/v1/embeddings` પર:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

મૂળ `{ image | audio | video | pdf }` મૂલ્યો સાર્વજનિક HTTPS URL, `data:` URI, અથવા કાચું
base64 હોઈ શકે છે. OmniRoute તે ઑબ્જેક્ટ્સને સ્ટ્રિંગમાં રૂપાંતરિત કરતું નથી અથવા મૂળ image URLs ફેચ કરતું નથી — Jina પોતે
સાર્વજનિક મીડિયા મેળવે છે. વધારાના Jina ફીલ્ડ્સ (`task`, `normalized`, `truncate`, `embedding_type`)
ફૉર્વર્ડ કરવામાં આવે છે. માત્ર ટેક્સ્ટ માટેના Jina SKUs હજુ પણ ટેક્સ્ટ સિવાયના ડૉક્સને નકારે છે.

સુરક્ષા અને ટ્રાન્સપોર્ટ મર્યાદાઓ:

- રિમોટ મીડિયા URLs સાર્વજનિક HTTPS હોવા આવશ્યક છે. કૅનોનિકલ `{type,source:url}` આઇટમ્સને
  સર્વર-સાઇડ ફેચ કરવામાં આવે છે (રીડાયરેક્ટનું પુનઃમાન્યકરણ, ટાઇમઆઉટ, કદની મર્યાદાઓ, સાર્વજનિક DNS, કનેક્શન પિનિંગ) અને
  પ્રદાતાને કૉલ કરતા પહેલાં ઇનલાઇન કરવામાં આવે છે. Jinaના મૂળ `{image:"https://..."}` આઇટમ્સને સમાન સાર્વજનિક-HTTPS ચકાસણી બાદ યથાવત્
  ફૉર્વર્ડ કરવામાં આવે છે; Jina URL ફેચ કરે છે.
- ઇનલાઇન base64 મીડિયા માટે પ્રતિ આઇટમ ડિકોડ થયા બાદ 8 MiB અને સમગ્ર વિનંતીમાં ડિકોડ થયા બાદ 16 MiBની મર્યાદા છે.

પ્રદાતા રૂપાંતરણ (કૅનોનિકલ આઇટમ્સ ક્યારેય યથાવત્ ફૉર્વર્ડ કરવામાં આવતા નથી):

- Jina મલ્ટિમોડલ models: દરેક ટોચ-સ્તરની આઇટમ એક મોડાલિટી-કી ધરાવતું ઑબ્જેક્ટ બને છે
  (`text` / `image` / `audio` / `video` / `pdf`), જેમાં ઇનલાઇન મીડિયા માટે data URIs વપરાય છે; દરેક
  ટોચ-સ્તરની આઇટમ દીઠ એક vector.
- Gemini Embedding 2 ફૅમિલી: એક ટોચ-સ્તરીય array એક જ મૂળ
  `models/{model}:embedContent` વિનંતી બને છે, જેમાં `content.parts` (`text` અથવા `inline_data`) હોય છે.
- llama.cpp (`llama-cpp/<model>`, સ્થાનિક સર્વરે લોડ કરેલું કોઈપણ model): કૅનોનિકલ `text` આઇટમ્સ
  સાદી strings બને છે અને `image` / `audio` / `video` દરેક એક
  `{"content": [part]}` ઑબ્જેક્ટ બને છે, જેમાં ઇનલાઇન ડેટા સાથે llama-serverના chat content parts (`image_url`,
  `input_audio`, ફૉર્મેટ `wav` / `mp3` / `flac` સાથે, `input_video`) વપરાય છે; દરેક ટોચ-સ્તરની
  આઇટમ દીઠ એક vector. સર્વર `--embedding --mmproj …` સાથે ચાલવું આવશ્યક છે; projector વિના તે
  પોતે જ મીડિયાને નકારે છે. `document` સમર્થિત નથી.
- સ્પષ્ટ modality metadata વિનાના અજ્ઞાત/ડાયનેમિક models HTTP 400 સાથે સંરચિત inputને નકારે છે.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

અસમર્થિત model/modality સંયોજનો આઇટમને બળજબરીથી રૂપાંતરિત કરવાને બદલે HTTP 400 પરત કરે છે. જૂની string/token વિનંતીઓમાં input સિવાયના
extension fields યથાવત્ પસાર થતા રહે છે.

```bash
# બધા embedding modelsની સૂચિ બનાવો
GET /v1/embeddings
```

## છબી નિર્માણ

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ઉપલબ્ધ પ્રદાતાઓમાં OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (સ્થાનિક), ComfyUI (સ્થાનિક) સામેલ છે.

`n`, `data[]`માં `n` છબીઓ પરત કરે છે. જે પ્રદાતાઓની અપસ્ટ્રીમ API દરેક કૉલ દીઠ એક છબી પરત કરે છે
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), તેમના માટે `n` અલગ અપસ્ટ્રીમ કૉલ કરવામાં આવે છે, જેમાં એક સમયે વધુમાં વધુ 4 કૉલ ચાલુ હોય છે. સ્થિર
`seed`ને કૉલ ઇન્ડેક્સ અનુસાર ઑફસેટ કરવામાં આવે છે (`seed`, `seed + 1`, …), જેથી છબીઓ અલગ હોય છતાં
પુનઃઉત્પાદનક્ષમ રહે છે. `n`ની મહત્તમ મર્યાદા 10 છે. કોઈપણ કૉલ નિષ્ફળ જાય તો આખી વિનંતી
નિષ્ફળ જાય છે. ફૅન-આઉટ ફોર્મેટ્સની યાદી
`open-sse/handlers/imageGeneration/fanOut.ts`માં `SINGLE_IMAGE_FANOUT_FORMATS` છે.

ZenMux હાલના API-કી કનેક્શનનો ફરી ઉપયોગ કરે છે અને `zenmux/` અથવા `zm/` પ્રીફિક્સ સ્વીકારે છે:

- `zenmux/openai/gpt-image-2`, ZenMuxની OpenAI Images APIનો ઉપયોગ કરે છે. વિકલ્પોમાં `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background`, અને `response_format` સામેલ છે.
- અન્ય પ્રકાશકો, જેમ કે `zm/meta/muse-image-1.0`, ZenMuxના Vertex AI `:predict`
  એન્ડપોઇન્ટનો ઉપયોગ કરે છે. `n`, `sampleCount` સાથે, `aspect_ratio`, `aspectRatio` સાથે અને `image_size`
  (`1K`, `2K`, `4K`), `sampleImageSize` સાથે મેપ થાય છે. પિક્સેલ `size` માત્ર આસ્પેક્ટ રેશિયો પૂરો પાડે છે,
  ચોક્કસ પિક્સેલ પરિમાણોની ખાતરી આપતું નથી. સમર્થિત રેશિયો, રિઝોલ્યુશન અને સંખ્યાઓ મોડલ પ્રમાણે બદલાય છે.
- `zm/inclusionai/ming-image-0.1-design` પોતાનાં પરિમાણો પસંદ કરે છે. `size`,
  `aspect_ratio`, અને `image_size`ને છોડી દો; સ્પષ્ટ મૂલ્યો HTTP 400 પરત કરે છે. PNG, JPEG અને WebPની
  `output_format` વડે વિનંતી કરી શકાય છે.

આ ઇન્ટિગ્રેશન ટેક્સ્ટ-ટુ-ઇમેજ નિર્માણને સમર્થન આપે છે, સંદર્ભ-છબી સંપાદનને નહીં. Vertex

## દસ્તાવેજ OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`, `provider/model` પ્રીફિક્સ દ્વારા OCR પ્રદાતા પસંદ કરે છે; માત્ર મોડલ id (દા.ત.
`mistral-ocr-latest`) તેના નોંધાયેલા પ્રદાતા સાથે રિઝોલ્વ થાય છે, અને `model` ન આપ્યું હોય તો ડિફૉલ્ટ તરીકે
Mistral (`mistral-ocr-latest`) વપરાય છે. નોંધાયેલા પ્રદાતાઓ (`open-sse/config/ocrRegistry.ts`):

| પ્રદાતા id                    | મોડલ id              | `model` મૂલ્ય                                                  | નોંધો                                                                                                       |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (અથવા માત્ર `mistral-ocr-latest`) | સિંક્રોનસ — પ્રતિસાદ એકમાત્ર અપસ્ટ્રીમ કૉલમાંથી સીધો પરત કરવામાં આવે છે.                                    |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | અસિંક્રોનસ અપસ્ટ્રીમ (`analyze` + પોલ) — નીચે જુઓ.                                                          |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | સિંક્રોનસ, Vertex AIના `openapi/chat/completions` પાર્ટનર એન્ડપોઇન્ટ મારફતે — પ્રમાણીકરણ/URL માટે નીચે જુઓ. |

ત્રણેય પ્રદાતાઓ સમાન Mistral-આકારની બોડીમાં પ્રતિસાદ આપે છે:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence પોલ ફ્લો

Azure Document Intelligenceની `analyze` API અસિંક્રોનસ છે: પ્રારંભિક વિનંતી બોડીને બદલે
`Operation-Location` હેડર પરત કરે છે અને પરિણામ મેળવવા માટે પોલ કરવું આવશ્યક છે. હેન્ડલર
(`open-sse/handlers/ocr.ts`) તે URLને દર સેકન્ડે વધુમાં વધુ 30 પ્રયાસો સુધી પોલ કરે છે, non-`ok` પોલ પ્રતિસાદ અથવા `"failed"` સ્થિતિ પર તરત નિષ્ફળ જાય છે (પોલિંગ
ચાલુ રાખતું નથી), અને જો પ્રયાસોની મર્યાદા પૂરી થયા પછી પણ
ઑપરેશન ચાલુ હોય તો `504` પરત કરે છે. કૉલરને પરત કરતાં પહેલાં અંતિમ Azure પ્રતિસાદને
Mistral દ્વારા વપરાતા સમાન `pages`/`markdown` આકારમાં નોર્મલાઇઝ કરવામાં આવે છે,
જેથી ક્લાયન્ટ કોડમાં પ્રદાતા માટે ખાસ વ્યવસ્થા કરવાની જરૂર રહેતી નથી.

### Vertex AI DeepSeek OCR પ્રમાણીકરણ અને એન્ડપોઇન્ટ રિઝોલ્યુશન

`vertex-deepseek-ocr`, ચૅટ/છબી ટ્રાફિક માટે OmniRoute પહેલેથી જ સમર્થન આપતું હોય તે જ Vertex AI પ્રમાણીકરણનો ફરી ઉપયોગ કરે છે
(`open-sse/executors/vertex.ts`): કનેક્શનની API કી કાં તો
Service Account JSON ક્રેડેન્શિયલ હોય છે (જેને JWT-bearer ફ્લો દ્વારા ટૂંકી અવધિના OAuth ઍક્સેસ ટોકન માટે
એક્સચેન્જ કરવામાં આવે છે) અથવા પહેલેથી બનાવેલું OAuth ઍક્સેસ ટોકન હોય છે, જેનો જેમ છે તેમ ઉપયોગ થાય છે. અપસ્ટ્રીમ એન્ડપોઇન્ટ URL એ Vertexનું
સામાન્ય `openapi/chat/completions` પાર્ટનર એન્ડપોઇન્ટ છે, જે કનેક્શનના પ્રોજેક્ટ અને
રિજનમાંથી બનાવવામાં આવે છે — સ્પષ્ટ `providerSpecificData.project`/`providerSpecificData.region`ને હંમેશાં પ્રાથમિકતા મળે છે;
અન્યથા પ્રોજેક્ટ Service Account JSONના `project_id`માંથી મેળવવામાં આવે છે અને રિજન
ડિફૉલ્ટ તરીકે `us-central1` રહે છે. બંને રિઝોલ્યુશન `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`)માં થાય છે, જેનો ઉપયોગ
`handleOcr`ને ડિસ્પૅચ કરતાં પહેલાં `src/app/api/v1/ocr/route.ts` દ્વારા કરવામાં આવે છે.

### મોડેલની કિંમતો (`pricing`)

જ્યારે OmniRoute ને મોડેલની કિંમતની જાણ હોય ત્યારે એન્ટ્રીમાં `pricing` ઑબ્જેક્ટ હોય છે. કિંમત
ખર્ચના હિસાબ માટે ઉપયોગમાં લેવાતા કિંમત કોષ્ટકમાંથી આવે છે: બિલ્ટ-ઇન ડિફૉલ્ટ્સ, સિંક કરેલી કિંમતો અને
`/api/pricing` દ્વારા સેટ કરેલા ઓવરરાઇડ્સ. આ સૂચિ કિંમતો છે, તેથી સબ્સ્ક્રિપ્શન પ્રદાતાઓ પણ
ટોકન દીઠ કિંમત દર્શાવે છે.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| ફીલ્ડ્સ                                                         | એકમ                          | નોંધો                                                                                                                                                         |
| --------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | ટોકન દીઠ USD, દશાંશ સ્ટ્રિંગ | OpenRouter-સુસંગત, ક્યારેય ઘાતાંક સંકેતલિપિમાં નહીં. બે કૅશ ફીલ્ડ્સ ફક્ત ત્યારે જ દેખાય છે જ્યારે કૅશ કિંમત હોય.                                              |
| `input`, `output`, `cached`, `cache_creation`                   | 1M ટોકન દીઠ USD, સંખ્યા      | પહેલાંનાં કેટલોગ વર્ઝનનાં ફીલ્ડ્સ, હાલના ક્લાયન્ટ્સ માટે જાળવી રાખવામાં આવ્યા છે. કિંમતની પંક્તિમાં `reasoning` અને `long_context` હોય ત્યારે તે પણ દેખાય છે. |

- **કોમ્બોઝ** તેમના પ્રથમ દૃશ્યમાન ટાર્ગેટની કિંમત ધરાવે છે. બિલ્ટ-ઇન `auto/*` કોમ્બોઝ વિનંતીના સમયે
  ટાર્ગેટ પસંદ કરે છે, તેથી તેમની પાસે `pricing` હોતું નથી.
- **મફત મોડેલો**ની કિંમત શૂન્ય હોય ત્યારે `"0"` (અને `0`) દર્શાવે છે. કિંમતની પંક્તિ વિનાનો મોડેલ
  પણ `"0"` દર્શાવે છે જ્યારે કેટલોગ તેને મફત (`free: true`) તરીકે ચિહ્નિત કરે અથવા બિલ્ટ-ઇન મફત-મોડેલ
  કેટલોગમાં તે સૂચિબદ્ધ હોય.
- **અજ્ઞાત કિંમત:** એન્ટ્રીમાં `pricing` કી હોતી નથી.
- **ક્રેડિટ-આધારિત મીટરિંગ ધરાવતા પ્રદાતાઓ** (જેમ કે Kiro) ટોકન દીઠ નહીં પરંતુ વિનંતી દીઠ બિલ કરે છે. તેમની
  એન્ટ્રીઓમાં પહેલાં રહેલા સંખ્યાત્મક પ્રતિ-1M ફીલ્ડ્સ જળવાય છે અને પ્રતિ-ટોકન સ્ટ્રિંગ ફીલ્ડ્સ હોતાં નથી.
- **વેરિઅન્ટ્સ** (reasoning-effort ids, no-thinking aliases, discovery અને gateway mirrors)
  જે મોડેલ તરફ રૂટ કરે છે તેની કિંમતની નકલ કરે છે.
- ફીલ્ડ્સમાં ફક્ત આધાર દરો હોય છે. લાંબા-કૉન્ટેક્સ્ટ ટિયર્સ (સંખ્યાત્મક `long_context` ફીલ્ડ) અને
  સર્વિસ-ટિયર ગુણકો (ઉદાહરણ તરીકે Codex fast અથવા flex) `prompt` અથવા
  `completion` ને બદલતા નથી.
- Anthropic-શૈલીની `x-api-key` અને `anthropic-version` ધરાવતી વિનંતી સહિત, દરેક પ્રમાણીકરણ શૈલી માટે
  ઑબ્જેક્ટ સમાન રહે છે (પ્રતિસાદ `{ "object": "list",
"data": [...] }` જ રહે છે). અમલીકરણ: `src/app/api/v1/models/catalogPricing.ts`.

### મોડેલ id પ્રિફિક્સ (`?prefix=`)

મોટાભાગના મોડેલો **પ્રદાતા પ્રિફિક્સ** હેઠળ દર્શાવવામાં આવે છે. તમને કયો પ્રિફિક્સ મળે છે તે
`MODELS_CATALOG_PREFIX_MODE` ફીચર ફ્લૅગ દ્વારા નિયંત્રિત થાય છે અને તેને ક્વેરી પેરામીટર વડે
**દરેક વિનંતી માટે** ઓવરરાઇડ કરી શકાય છે — સર્વર-વ્યાપી સેટિંગ દરેક અન્ય વપરાશકર્તા માટે બદલ્યા વિના
સુવ્યવસ્થિત સૂચિ ઇચ્છતા ક્લાયન્ટ માટે આ ઉપયોગી છે:

```bash
GET /v1/models?prefix=alias        # દરેક મોડેલ માટે એક id — ટૂંકો alias પ્રિફિક્સ
GET /v1/models?prefix=dual         # બંને સ્વરૂપો (સર્વર ડિફૉલ્ટ)
GET /v1/models?prefix=canonical    # ફક્ત સંપૂર્ણ provider-id પ્રિફિક્સ
```

| મોડ         | ઉત્સર્જિત કરે છે                                          | નોંધો                                                                                                                                                                                      |
| ----------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dual`      | `cc/claude-sonnet-4-6` **અને** `claude/claude-sonnet-4-6` | **ડિફૉલ્ટ.** બંને ids સમાન મોડેલ તરફ રૂટ કરે છે; કોઈપણ સ્વરૂપને હાર્ડકોડ કરેલ ક્લાયન્ટ કૉન્ફિગ્સ કાર્યરત રહે તે માટે જાળવવામાં આવ્યા છે. કેટલોગનું કદ આશરે બમણું કરે છે.                   |
| `alias`     | `cc/claude-sonnet-4-6`                                    | દરેક મોડેલ દીઠ એક એન્ટ્રી. અલગ alias વિનાના પ્રદાતાઓ પણ તેમની એન્ટ્રી ઉત્સર્જિત કરે છે, તેથી કંઈ ગુમ થતું નથી.                                                                             |
| `canonical` | `claude/claude-sonnet-4-6`                                | સંપૂર્ણ provider-id પ્રિફિક્સ હેઠળ દરેક મોડેલ દીઠ એક એન્ટ્રી. અલગ alias વિનાના પ્રદાતાઓ (દા.ત. `antigravity/…`, `agy/…`) પણ તેમનો એકમાત્ર id અહીં ઉત્સર્જિત કરે છે, તેથી કંઈ ગુમ થતું નથી. |

`dual`-મોડ મિરરને ક્વેરી પેરામીટર વિના પણ ઓળખી શકાય છે: તેમાં પ્રાથમિક id તરફ નિર્દેશ કરતું `parent`
ફીલ્ડ હોય છે.

મોડેલ પિકર રેન્ડર કરતા ક્લાયન્ટ્સે `?prefix=alias` ની વિનંતી કરવી જોઈએ —
[OmniCopilot VS Code એક્સ્ટેન્શન](../guides/VSCODE-COPILOT.md) પણ આમ જ કરે છે.

### ડિસ્કવરી ફિલ્ટર્સ (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` ઑપ્ટ-ઇન ડિસ્કવરી ફિલ્ટર્સ સ્વીકારે છે. તેમાંના કોઈપણ વિના પ્રતિસાદ
અપરિવર્તિત રહે છે. તેઓ કૉલરને પહેલેથી દેખાતા કેટલોગને સંકુચિત કરે છે (API-key પરવાનગીઓ પહેલાં લાગુ થાય છે),
અને તેઓ OpenAI-શૈલીનાં `limit` / `after` પેજિંગ પહેલાં ચાલે છે:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # સૂચિબદ્ધ દરેક capability true હોવી આવશ્યક છે
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # કેટલોગ `type`; તેના વિનાની પંક્તિઓ `chat` છે
GET /v1/models?q=sonnet&limit=10                           # id અથવા name પર કેસ-અસંવેદનશીલ મેળ
```

| પેરામીટર      | મૂલ્યો                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | બિન-ઋણ પૂર્ણાંક, જેની સરખામણી `context_length` સાથે કરવામાં આવે છે                                  |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 અક્ષરો                                                                                        |

અજ્ઞાત મૂલ્ય અથવા બિન-ઋણ પૂર્ણાંક ન હોય તેવું `min_context` (ઉદાહરણ તરીકે `1.5`)
HTTP `400` પરત કરે છે અને સંદેશ માન્ય મૂલ્યોની સૂચિ દર્શાવે છે. અમલીકરણ:
`src/app/api/v1/models/catalogFilters.ts`.

### મોડલની ટૂંકી સૂચિ (`POST /v1/models/query`)

`POST /v1/models/query`, `GET /v1/models` જેવા જ પ્રમાણીકરણ અને કી-દીઠ દૃશ્યતા સાથે, સમાન કેટલૉગમાંથી ટૂંકી અને નિર્ધારિત સૂચિ પરત કરે છે:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

દરેક ફીલ્ડ વૈકલ્પિક છે. `capabilities` અને `exclude` એરે અથવા અલ્પવિરામથી અલગ કરેલી સ્ટ્રિંગ સ્વીકારે છે;
`max_output` ની સરખામણી `max_output_tokens` સાથે કરવામાં આવે છે. પરિણામોને પહેલાં `owned_by` અને પછી `id` મુજબ ગોઠવવામાં આવે છે.
`limit` નું ડિફૉલ્ટ મૂલ્ય `20` છે અને `100` કરતાં વધારે મૂલ્યોને `100` સુધી મર્યાદિત કરવામાં આવે છે. અમાન્ય JSON, અજ્ઞાત
ફીલ્ડ અથવા અમાન્ય મૂલ્ય HTTP `400` પરત કરે છે.

### વ્યક્તિગત રીતે છુપાવેલાં ચેટ મોડલ

તેના પ્રદાતા પેજ પર **છુપાયેલું** તરીકે ચિહ્નિત મોડલને કેટલૉગમાંથી બાકાત રાખવામાં આવે છે અને સ્પષ્ટપણે
વિનંતી કરવામાં આવે ત્યારે HTTP `404` / `model_not_found` સાથે નકારવામાં આવે છે. આ ચકાસણી રિઝોલ્વ થયેલા
પ્રદાતા અને મોડલનો ઉપયોગ કરે છે, જેમાં પ્રદાતા ઉપનામો, સુસંગત-પ્રદાતા નોડ પ્રીફિક્સ અને
કનેક્શન ડિફૉલ્ટનો સમાવેશ થાય છે. કૉમ્બો છુપાયેલા લક્ષ્યોને અવગણે છે અને દૃશ્યમાન સમકક્ષનો ઉપયોગ કરી શકે છે; જ્યારે કોઈ
એક્ઝિક્યુટ કરી શકાય તેવું લક્ષ્ય બાકી ન રહે, ત્યારે તે સમાન ભૂલ કોડ પરત કરે છે. છુપાવવાનું રદ કર્યાની અસર આગલી
વિનંતીથી લાગુ થાય છે. માત્ર-ઇમેજ દૃશ્યતાના ઓવરરાઇડ્સ સમાન ID ધરાવતા ચેટ મોડલને છુપાવતા નથી.

આ વ્યક્તિગત મોડલ સેટિંગ
[મોડલ એક્સપોઝર મંજૂરી/નકાર સૂચિઓ](../routing/MODEL_EXPOSURE_LIST.md)થી અલગ છે, જે સ્પષ્ટ ડિસ્પેચ જાળવી રાખીને કેટલૉગ
જાહેરાત અને ઑટો-રાઉટિંગ ઉમેદવારોને ફિલ્ટર કરે છે. API-કી મોડલ
પરવાનગીઓ સ્વતંત્ર રીતે લાગુ થતી રહે છે. ડિફૉલ્ટ કેટલૉગ પ્રીફિક્સ મોડ `dual` જ રહે છે.

### થિંકિંગ વિનાનાં મોડલ વેરિઅન્ટ

થિંકિંગની ક્ષમતા ધરાવતા Claude મોડલ માટે, `/v1/models` એક **થિંકિંગ વિનાનું** વેરિઅન્ટ પણ જાહેર કરે છે, જેનું id `claude-3-omniroute-no-thinking/` પ્રીફિક્સ ધરાવે છે:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

આ id પસંદ કરવાથી (દા.ત. હંમેશાં `thinking` બ્લૉક જોડતા Claude Code કૉન્ફિગમાં) રિઝનિંગને નિષ્ક્રિય રાખીને તે વાસ્તવિક `<provider>/<model>` પર પાછું રિઝોલ્વ થાય છે—`/v1/messages` પાથ પર `thinking:{type:"disabled"}`, અથવા `/v1/chat/completions` પાથ પર `reasoning`/`reasoning_effort` ફીલ્ડ્સ દૂર કરીને. આ વેરિઅન્ટ માત્ર એવા Claude-ફેમિલી મોડલ માટે સૂચિબદ્ધ થાય છે જે થિંકિંગને સપોર્ટ કરે છે **અને** `disabled` નું પાલન કરે છે (એટલે કે, `disabled` ને નકારતાં માત્ર-અડેપ્ટિવ મોડલને બાકાત રાખવામાં આવે છે). ઑપરેટર્સ `ModelSpec.noThinkingAlias` દ્વારા દરેક મોડલ માટે આ વેરિઅન્ટને ફરજિયાત રીતે ચાલુ અથવા બંધ કરી શકે છે.

## ElevenLabs ઑડિયો જનરેશન

તમારી ElevenLabs API કી સાથે OmniRouteમાં `elevenlabs` પ્રોવાઇડર કનેક્શન કૉન્ફિગર કરો.
ક્લાયન્ટ્સ તેમની **OmniRoute** કી (`Authorization: Bearer $OMNIROUTE_API_KEY`) વડે પ્રમાણિત થાય છે;
ગેટવે સંગ્રહિત પ્રોવાઇડર કીને `xi-api-key` તરીકે પૂરી પાડે છે. ગેટવે બેરર ટોકન તરીકે ક્યારેય ElevenLabs કી મોકલશો નહીં.

| પદ્ધતિ | પાથ                         | પ્રતિસાદ                                 | API કી એન્ડપોઇન્ટ કેટેગરી |
| ------ | --------------------------- | ---------------------------------------- | ------------------------- |
| POST   | `/v1/sound-generation`      | મૂળ ઑડિયો બાઇટ્સ                         | `elevenlabs`              |
| POST   | `/v1/music`                 | મૂળ ઑડિયો બાઇટ્સ                         | `music`                   |
| POST   | `/v1/music/stream`          | સ્ટ્રીમિંગ ઑડિયો બાઇટ્સ                  | `music`                   |
| POST   | `/v1/music/detailed`        | મૂળ મલ્ટિપાર્ટ ઑડિયો અને કમ્પોઝિશન પ્લાન | `music`                   |
| POST   | `/v1/music/detailed/stream` | મૂળ SSE મેટાડેટા અને ઑડિયો ચંક્સ         | `music`                   |
| POST   | `/v1/music/plan`            | JSON કમ્પોઝિશન પ્લાન                     | `music`                   |

આ એન્ડપોઇન્ટ્સ હાલના `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` અને `/v1/speech-to-text` રૂટ્સને પૂરક છે. `output_format` અને `enable_logging` જેવી મૂળ JSON ફીલ્ડ્સ અને ક્વેરી પેરામીટર્સ જાળવી રાખવામાં આવે છે.
`/v1/music/detailed` પ્રતિસાદો તેમની મલ્ટિપાર્ટ બાઉન્ડરીઝ જાળવી રાખે છે; તેમને મલ્ટિપાર્ટ તરીકે પાર્સ કરો.
`/v1/music/detailed/stream` કમ્પોઝિશન મેટાડેટા અને SSE ઇવેન્ટ્સમાં base64 ઑડિયો ચંક્સ સાથે `text/event-stream` પરત કરે છે. તમામ છ રૂટ્સ CORS પ્રીફ્લાઇટને સપોર્ટ કરે છે.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# ટૂંકી સાઉન્ડ ઇફેક્ટ. અવધિ: 0.5થી 30 સેકન્ડ.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# સંગીતની અવધિ મિલિસેકન્ડમાં દર્શાવવામાં આવે છે: 3000થી 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

ક્રમશઃ ઑડિયો ડિલિવરી માટે સમાન JSON બોડી સાથે `/v1/music/stream`નો ઉપયોગ કરો. કમ્પોઝિશન `prompt` અથવા `composition_plan`માંથી ચોક્કસ એકને સ્વીકારે છે; `/v1/music/plan` માટે `prompt` આવશ્યક છે અને તે વૈકલ્પિક રીતે `source_composition_plan` સ્વીકારે છે. મૂળ સ્કીમા વધારાની પ્રોવાઇડર ફીલ્ડ્સ જાળવે છે જેથી કમ્પોઝિશન-પ્લાન વર્ઝન્સ અને ફાઇન-ટ્યુનિંગ વિકલ્પો ElevenLabs સુધી પહોંચે.

એકીકૃત `/v1/music/generations` એન્ડપોઇન્ટ `elevenlabs/music_v1`,
`elevenlabs/music_v2` અને `elevenlabs/music_v2_5`ને પણ સ્વીકારે છે. સક્રિય ElevenLabs કનેક્શન સાથે, આ મોડલ્સ મ્યુઝિક કૅટલોગ દ્વારા ઉપલબ્ધ કરાવવામાં આવે છે. આ એન્ડપોઇન્ટ
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` પરત કરે છે. તેની `duration` ફીલ્ડ સેકન્ડમાં હોય છે અને `music_length_ms` સાથે મેપ થાય છે; સ્પષ્ટપણે આપેલ `music_length_ms`ને પ્રાથમિકતા મળે છે.
`instrumental`, `force_instrumental` સાથે મેપ થાય છે, જેમાં મૂળ ફીલ્ડને પ્રાથમિકતા મળે છે.
સ્ટ્રીમિંગ માટે મૂળ સ્ટ્રીમિંગ એન્ડપોઇન્ટ્સનો અને ફક્ત કમ્પોઝિશન પ્લાન દ્વારા સંચાલિત રિક્વેસ્ટ્સ માટે મૂળ કમ્પોઝિશન એન્ડપોઇન્ટનો ઉપયોગ કરો.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

અપસ્ટ્રીમ કૉલ પહેલાં એન્ડપોઇન્ટ, મોડલ, બજેટ અને કનેક્શન પ્રતિબંધો લાગુ પડે છે. મૂળ રૂટ્સ અપસ્ટ્રીમ સ્ટેટસ કોડ્સ અને એરર બોડીઝને કોઈ ફેરફાર વિના પરત કરે છે, જેમાં પ્લાન પ્રતિબંધ માટે `402` અને ક્વોટા મર્યાદા માટે `429`નો સમાવેશ થાય છે. `character-cost`, `song-id`, `request-id` અને `retry-after` હેડર્સ હાજર હોય ત્યારે જાળવી રાખવામાં આવે છે. મફત ક્રેડિટ બેલેન્સ દરેક મ્યુઝિક મોડલ, આઉટપુટ ફોર્મેટ અથવા API સુવિધાની ઍક્સેસની ખાતરી આપતું નથી: દરેક રિક્વેસ્ટ માટે પાત્રતા ElevenLabs નક્કી કરે છે.
એકીકૃત એન્ડપોઇન્ટ OmniRouteના નોર્મલાઇઝ્ડ એરર એન્વલપમાં એરર સ્ટેટસ કોડ્સ જાળવે છે.

અપસ્ટ્રીમ કોન્ટ્રાક્ટ્સ: [સાઉન્ડ ઇફેક્ટ્સ](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[મ્યુઝિક કમ્પોઝિશન](https://elevenlabs.io/docs/api-reference/music/compose) અને
[સ્ટ્રીમિંગ મ્યુઝિક વિગતો](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

બધા POST રૂટ્સ સમાન માળખાને અનુસરે છે: `Bearer your-api-key` + Zod દ્વારા માન્ય કરાયેલ JSON બૉડી (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema`, વગેરે, `src/shared/validation/schemas.ts` જુઓ). સ્કીમા નિષ્ફળ જાય ત્યારે 4xx પરત કરવામાં આવે છે.

જે ક્લાયન્ટ્સ `Authorization: Bearer ...` જોડી શકતા નથી, તેમના માટે OmniRoute ક્વેરી-સ્ટ્રિંગ સુસંગતતા (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) અથવા નીચે દસ્તાવેજીકૃત કરેલા સમર્પિત `/api/v1/vscode/{token}/...` એન્ડપોઇન્ટ્સ મારફતે URLમાં API કીઝ પણ સ્વીકારે છે.

```bash
# રિરૅન્ક (ક્લાઉડ રજિસ્ટ્રી પ્રદાતા અથવા "<prefix>/<model>" તરીકે OpenAI-સુસંગત પ્રદાતા નોડ)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina વર્ગીકરણ (Foundation API ઓળખપત્રો)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina સેગમેન્ટર
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina શોધ (s.jina.ai; પ્રદાતા ઉપનામો: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# મોડરેશન્સ
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (અથવા વિનંતી કરેલું ફોર્મેટ) બૉડી પરત કરે છે
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS માટે ભાષા અને અવાજ જરૂરી છે: `language`નું ડિફૉલ્ટ મૂલ્ય "en" છે; ખૂટતો
# અવાજ અથવા OpenAI સ્ટૉક અવાજનું નામ (alloy, nova, …) "Adrian" બની જાય છે
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# છબી સંપાદન (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# વિડિયો / સંગીત જનરેશન (પ્રદાતા-ઉપસર્ગવાળી મોડેલ ID)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **રિરૅન્ક પ્રોવાઇડર નોડ્સ:** `POST /v1/rerank` OpenAI-સુસંગત પ્રોવાઇડર નોડ્સ પર પણ રૂટ કરે છે
> (oMLX, vLLM, Infinity, ગેટવેની પાછળ TEI, …), જેને `<node-prefix>/<model>` તરીકે સંબોધવામાં આવે છે. લૂપબૅક
> નોડ્સ (`localhost`, `127.0.0.1`, `172.16.0.0/12`) હંમેશાં પાત્ર હોય છે, તેમજ ઑપરેટર
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` માં સૂચિબદ્ધ કરે તે હોસ્ટનેમ્સ પણ પાત્ર હોય છે (દા.ત. કોઈ Docker/Compose સેવા નામ,
> જેમ કે `http://reranker:8080/v1`; આને હંમેશાં સીધા કૉલ કરવામાં આવે છે, ક્યારેય `HTTP(S)_PROXY` અથવા
> કનેક્શનના પિન કરેલા પ્રૉક્સી મારફતે નહીં). અન્ય કોઈપણ
> હોસ્ટ પરના નોડ્સ — LAN બૉક્સ અથવા Tailscale પીઅર — માત્ર ત્યારે જ પાત્ર હોય છે જ્યારે ઑપરેટર
> `RERANK_REMOTE_PROVIDER_NODES` ફીચર ફ્લૅગ સક્ષમ કરે **અને** નોડનું બેઝ URL પ્રોવાઇડરની
> આઉટબાઉન્ડ URL નીતિ (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`)માંથી પસાર થાય.
> મેમરી એન્જિનનું રિરૅન્ક પગલું આ રૂટને
> લૂપબૅક મારફતે કૉલ કરે છે, તેથી આ જ નિયમ Memory સેટિંગ્સમાં `rerankProviderModel` ને લાગુ પડે છે.
>
> **લોકલ સર્વર સ્વરૂપો:** નોડને `<base>/v1/rerank` પર અને 404 મળે ત્યારે `<base>/rerank`
> (Infinity, TEI) પર કૉલ કરવામાં આવે છે. અપસ્ટ્રીમ બૉડીમાં Cohere/OpenAI સ્પેલિંગ (`documents`,
> `return_documents`) અને TEI સ્પેલિંગ (`texts`, `return_text`) બંને હોય છે, અને અપસ્ટ્રીમ પ્રતિસાદને
> Cohere એન્વલપમાં સામાન્યકૃત કરવામાં આવે છે: TEIનું મૂળ `[{index, score, text}]`, પાતળા ગેટવેમાંથી મળતું
> `{results: [{index, score}]}`, અને Voyage-શૈલીનું `{data: [...]}` — આ બધું ક્લાયન્ટને
> `{results: [{index, relevance_score, document?}]}` તરીકે પાછું મળે છે, સ્કોર પ્રમાણે ગોઠવેલું અને `top_n` સુધી મર્યાદિત.

> **પ્રોવાઇડર-નોડ શોધ:** OpenAI-સુસંગત પ્રોવાઇડર નોડ પરનાં મોડેલો `GET /v1/models` માં
> નોડ પ્રીફિક્સ હેઠળ દેખાય છે. જે પંક્તિઓમાં કોઈ એન્ડપૉઇન્ટ મેટાડેટા હોતું નથી (લોકલ `/v1/models` સૂચિઓ માટે સામાન્ય)
> તે નોડનું `apiType` વારસામાં મેળવે છે, તેથી ડિફૉલ્ટ રૂપે ચૅટ બનવાને બદલે `embeddings` નોડના મોડેલો
> `type: "embedding"` અને `rerank` નોડના મોડેલો `type: "rerank"` હોય છે; સિંક કરેલી અથવા મેન્યુઅલી ઉમેરેલી
> પંક્તિ પર સ્પષ્ટ `supportedEndpoints` ને હજી પણ પ્રાથમિકતા મળે છે.

## Files API

બૅચ ઇનપુટ/આઉટપુટ અને ફાઇલ-હેતુવાળા અપલોડ માટે OpenAI-સુસંગત ફાઇલ્સ એન્ડપોઇન્ટ.

| પદ્ધતિ | પાથ                      | વર્ણન                                                                                                              |
| ------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| POST   | `/v1/files`              | ફાઇલ અપલોડ કરો (મલ્ટિપાર્ટ: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — મહત્તમ 512 MiB |
| GET    | `/v1/files`              | પ્રમાણિત API કી માટેની ફાઇલોની સૂચિ મેળવો                                                                          |
| GET    | `/v1/files/[id]`         | ફાઇલનું મેટાડેટા મેળવો                                                                                             |
| DELETE | `/v1/files/[id]`         | ફાઇલ કાઢી નાખો                                                                                                     |
| GET    | `/v1/files/[id]/content` | કાચી ફાઇલ બૉડીને સ્ટ્રીમ સ્વરૂપે પરત મેળવો                                                                         |

**પ્રમાણીકરણ:** બેરર API કી — `getApiKeyRequestScope` દ્વારા ફાઇલોનો વ્યાપ દરેક API કી પ્રમાણે નિર્ધારિત થાય છે. કોઈ કી
માત્ર પોતાની ફાઇલો જોઈ, ડાઉનલોડ કરી અને કાઢી શકે છે; કી વિનાનું ડૅશબોર્ડ સત્ર
આખું ઇન્સ્ટન્સ વાંચે છે; માલિક વિનાની ફાઇલ (અનામી અથવા ડૅશબોર્ડ-સત્ર અપલોડ) દરેક
બિન-સત્ર કૉલર માટે પ્રતિબંધિત છે. `GET /v1/files` કોઈ અનામી કૉલરને — અને આપેલી એવી કીને જેનું
નિરાકરણ થતું નથી — `REQUIRE_API_KEY=false` હોય ત્યારે પણ દરેક ટેનન્ટની
ફાઇલોની સૂચિ આપવાને બદલે `401` સાથે નકારે છે (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523).

### Exa અને Tavily `provider_options`

Exa અને Tavily નેમસ્પેસવાળી બેગમાંથી પ્રદાતા-વિશિષ્ટ ફીલ્ડ્સ વાંચો: `provider_options.exa` (અથવા `provider_options["exa-search"]`) અને `provider_options.tavily` (અથવા `provider_options["tavily-search"]`). ફક્ત નીચેની કી ફોરવર્ડ કરવામાં આવી છે. દરેકને `open-sse/handlers/search/providerOptionsPassthrough.ts` માં તેની પોતાની Zod સ્કીમા સામે તપાસવામાં આવે છે, અને ખોટા પ્રકાર સાથેની કી છોડી દેવામાં આવે છે. auth, base URL, `stream` અને `outputSchema` સહિત કોઈપણ અન્ય કીને અવગણવામાં આવે છે. અન્ય પ્રદાતાઓ (`cx`, `depth`, ...) દ્વારા ઉપયોગમાં લેવાતી ફ્લેટ કીઓ પહેલાની જેમ કામ કરે છે.

| પ્રદાતા | ટોચના-સ્તરના ક્ષેત્રો                                                                                                                                                                                                                                                                                                                                                     | નેસ્ટેડ                                                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| એક્ઝા   | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (સપાટ આદિમ), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                                    | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` ડિફોલ્ટ `{ text: true, highlights: true }` પર મર્જ થયું |
| તવીલી   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                     |

સામાન્ય ક્ષેત્રો હંમેશા જીતે છે: `query`, `max_results`, `filters` (ડોમેન્સ), `country` અને `search_type` માંથી મેળવેલ વિષય. Exa પર, `search_type: "news"` `category: "news"` રાખે છે. Tavily `search_type: "finance"` (`topic: "finance"`) પણ સ્વીકારે છે.

ફાયરક્રોલ શોધ ખર્ચ 10 પાછલા પરિણામોના પ્રારંભ બ્લોક દીઠ રેકોર્ડ કરવામાં આવે છે, $0.002 (2 ક્રેડિટ) એક બ્લોક અને ઓછામાં ઓછા એક બ્લોક દીઠ કોલ ( [ફાયરક્રોલ બિલિંગ](https://docs.firecrawl.dev/billing) ): 11 પરિણામોની કિંમત $0.004 છે.

સામાન્ય `time_range` હવે બંને પ્રદાતાઓ સુધી પહોંચે છે: Exa ને `startPublishedDate` (ISO ટાઇમસ્ટેમ્પ) મળે છે અને Tavily ને `start_date` (`YYYY-MM-DD`) મળે છે. `provider_options` માં સ્પષ્ટ તારીખ મેપ કરેલ તારીખને ઓવરરાઇડ કરે છે.

Exa પરિણામો `id`, `highlight_scores`, `summary`, `subpages`, `entities` અને `extras` ને `provider_raw` માં રાખે છે. Tavily પરિણામો `images` અને `favicon` રાખે છે.

લિંકઅપ શોધ કિંમત `depth` `fast` અને `standard` માટે $0.005 અને `deep` ( [Linkup કિંમત નિર્ધારણ](https://docs.linkup.so/pages/documentation/development/pricing) ) માટે $0.05 રેકોર્ડ કરવામાં આવી છે, પછી ભલે `depth` `provider_options` અથવા કનેક્શનની સેટિંગ્સમાંથી આવે.

Exa `type: "lite"` (Exa 3.0) ફીલ્ડના નાના સેટને સ્વીકારે છે અને જ્યારે અન્ય કોઈ ફીલ્ડ સેટ કરવામાં આવે ત્યારે સમગ્ર વિનંતીને નકારી કાઢે છે. લાઇટ માટે, `additionalQueries`, `systemPrompt` અને `text` અને `highlights` સિવાયની દરેક `contents` કી કૉલ પહેલાં છોડી દેવામાં આવે છે. નાપસંદ કરેલ `subpages`, `subpageTarget`, `highlights.numSentences` અને `highlights.highlightsPerUrl` હવે ફોરવર્ડ કરવામાં આવશે નહીં.

કોસ્ટ એકાઉન્ટિંગ એ ફ્લેટ રજિસ્ટ્રી `costPerQuery` છે, Exa સિવાય, જે Exa ની પોતાની કિંમતોને અનુસરે છે: `auto` (અને લેગસી `fast`) માટે $0.007 અથવા `lite` (અને લેગસી `instant`) માટે $0.004, 10 પરિણામોને આવરી લે છે; દરેક વધુ પરિણામ માટે $0.001; અને જ્યારે `contents.summary` સેટ કરેલ હોય ત્યારે પરત કરેલા પરિણામ દીઠ $0.001. Tavily `search_depth` `basic`, `fast` અને `ultra-fast` માટે 1 ક્રેડિટ ($0.008) અને `advanced` ( [Tavily API ક્રેડિટ્સ](https://docs.tavily.com/documentation/api-credits) ) માટે 2 ક્રેડિટ ($0.016) પર નોંધાયેલ છે. `auto_parameters: true` સાથેનો કોલ કે જે Tavily એડવાન્સ્ડમાં અપગ્રેડ કરે છે તે હજુ પણ 1 ક્રેડિટ પર રેકોર્ડ કરવામાં આવે છે.

## Web Fetch API

ગોઠવાયેલા web-fetch પ્રદાતા (Firecrawl, Jina Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) દ્વારા URLમાંથી સામગ્રી કાઢો.

Parallel Extract (`parallel-search`, Parallel Search જેવી જ API key) માત્ર Markdown પરત કરે છે — અન્ય કોઈપણ `format` માટે `400` મળે છે — અને સામગ્રીને 100,000 અક્ષરો સુધી મર્યાદિત કરે છે. જ્યારે લક્ષ્ય પેજને જ કાઢી શકાતું નથી, ત્યારે અપસ્ટ્રીમ તેની જાણ HTTP 200ની અંદર કરે છે; OmniRoute તેને નિશ્ચિત સંદેશ સાથે `422` તરીકે રજૂ કરે છે.

| પદ્ધતિ | પાથ             | વર્ણન                                                                     |
| ------ | --------------- | ------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | URL મેળવો/સ્ક્રેપ કરો — bodyનું `v1WebFetchSchema` દ્વારા માન્યકરણ થાય છે |

**પ્રમાણીકરણ:** Bearer API key (`extractApiKey` + `isValidApiKey`). નીતિ `enforceApiKeyPolicy` દ્વારા લાગુ કરવામાં આવે છે.

**ક્વોટા-સજાગ fallback (#8297):** જ્યારે સ્પષ્ટ `provider` આપવામાં આવેલ ન હોય, ત્યારે pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`)ને
નિશ્ચિત
પ્રાથમિકતા ક્રમમાં (પહેલું ભરો) અજમાવવામાં આવે છે — rate-limited પરંતુ configured પ્રદાતાને
વિનંતી તરત અટકાવવાને બદલે છોડી દેવામાં આવે છે, અને retryable/quota અપસ્ટ્રીમ નિષ્ફળતા
(HTTP 429 હંમેશા; Firecrawl/Tavily/TinyFishના quota-પ્રકારના free tiers માટે 402/403 —
Jina Reader માટે નહીં, અને સાદી 400 bad request માટે ક્યારેય નહીં) વિનંતીના સમયે
આગલા હજી ન અજમાવાયેલા અને credentials ધરાવતા પ્રદાતા પર જાય છે. જ્યારે poolના દરેક
પ્રદાતાનો ઉપયોગ થઈ જાય, ત્યારે endpoint અગાઉના સામાન્ય `400`ના બદલે એકમાત્ર `429`
(`Retry-After` header સાથે) પરત કરે છે. જ્યારે સ્પષ્ટ `provider`ની વિનંતી કરવામાં આવે,
ત્યારે કોઈ શાંત fallback થતું **નથી** — rate-limited અથવા નિષ્ફળ સ્પષ્ટ
પ્રદાતા પોતાની ભૂલ જ રજૂ કરે છે (rate-limited હોય તો `429`, અન્યથા અપસ્ટ્રીમ
status).

## WebSocket સ્ટ્રીમિંગ

```bash
GET /v1/ws?handshake=1
```

WebSocket upgrade handshakeનું માન્યકરણ કરે છે અને wire protocolના ઉદાહરણ સંદેશા (`request`, `cancel`) પરત કરે છે. વાસ્તવિક WS framesને Next.js route tableની બહાર bundled WS server દ્વારા સંચાલિત કરવામાં આવે છે.

**પ્રમાણીકરણ:** handshake દરમિયાન Bearer API key.

### WebSocket મારફતે Responses API (માત્ર codex)

```bash
# HTTP API જેવું જ host:port (default 20128); connectionને upgrade કરો:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (અથવા: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# પહેલું frame response.create જ હોવું આવશ્યક છે:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxyને **ફક્ત `codex`** (ChatGPT
backend) સાથે જોડવામાં આવ્યું છે. તે API/dashboard જેવા જ port પર `/v1/responses`,
`/responses`, અને `/api/v1/responses` paths પર સાંભળે છે. પ્રથમ `response.create` frame પર તે
આંતરિક `codex-responses-ws` bridge દ્વારા પ્રમાણીકરણ + તૈયારી કરે છે, codex OAuth
connection પસંદ કરે છે અને `wreq-js` transport દ્વારા
`wss://chatgpt.com/backend-api/codex/responses` સુધી tunnel બનાવે છે.
**Non-codex modelsને નકારવામાં આવે છે** (`codex_ws_provider_required`).
Quota-share routing માટે `model: "qtSd/<group>/codex/<model>"` વાપરો. અમલીકરણ
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`માં છે.

**પ્રમાણીકરણ:** handshake દરમિયાન Bearer API key. Bundled HTTP server (`server-ws.mjs`)
સક્રિય entrypoint હોવું આવશ્યક છે (`app/server-ws.mjs` અસ્તિત્વમાં હોય ત્યારે તે default રૂપે સક્રિય હોય છે).

#### Model id: મૂળ ChatGPT id વાપરો (`codex/` prefix વિના)

OpenAI **Codex CLI**, જ્યારે `supports_websockets = true` હોય ત્યારે, client-side પર model nameનું માન્યકરણ કરે છે અને `codex/gpt-5.5` જેવા **provider-prefixed idsને નકારે છે** (`The 'codex/gpt-5.5' model is not supported when using Codex with a ChatGPT account`). **મૂળ** id મોકલો (દા.ત. `gpt-5.5`). OmniRouteનું bridge ફક્ત codex માટે છે, તેથી તે અપસ્ટ્રીમ તરફ tunnel બનાવતા પહેલાં મૂળ idને codex model તરીકે ફરી resolve કરે છે (`resolveCodexWsModelInfo`) — ભલે મૂળ `gpt-5.5` અન્યથા HTTP મારફતે બીજા પ્રદાતા તરફ route થતું હોય.

#### OpenAI Codex CLIને ગોઠવવું

`~/.codex/config.toml`માં WebSocket support ધરાવતો custom provider ઉમેરીને Codex CLIને OmniRoute તરફ દોરો (હાલની configને બદલવાનું ટાળવા માટે અલગ `CODEX_HOME` વાપરો):

```toml
model = "gpt-5.5"                 # મૂળ id — "codex/gpt-5.5" નહીં
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # અંતે slash નહીં; WS URL મેળવવામાં આવે છે (productionમાં https/wss વાપરો)
wire_api = "responses"                    # Feb 2026થી એકમાત્ર supported value
supports_websockets = true                # Responses-over-WS transportને સક્રિય કરે છે
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API key (Bearer) ધરાવે છે
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API key (જો REQUIRE_API_KEY=false હોય તો કોઈપણ key)
codex exec "Responda apenas: PONG"
```

CLI `base_url + /responses`ને WebSocketમાં upgrade કરે છે અને OmniRoute તેને પસંદ કરાયેલા codex OAuth connection સુધી tunnel કરે છે. સ્થાનિક server સામે end-to-end માન્યકરણ કરવામાં આવ્યું છે: ChatGPT `codex.rate_limits` + `response.created` પરત કરે છે અને completionને stream કરે છે.

## સ્વ-સેવા વપરાશ (`/api/usage/om-usage`)

કોઈપણ API કી **પોતાના** વપરાશ અને ક્વોટા વાંચી શકે છે — મેનેજમેન્ટ પ્રમાણીકરણની જરૂર નથી. આ તે એન્ડપોઇન્ટ છે જેનો
ક્લાયન્ટ (CLI, OmniCopilot પેનલ) કી ધારકને તેનો ખર્ચ બતાવવા માટે ઉપયોગ કરે છે.

```bash
# ટેક્સ્ટ સ્વરૂપ (ઐતિહાસિક કરાર — ટર્મિનલ માટે સાદો ટેક્સ્ટ)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# સ્ટ્રક્ચર્ડ સ્વરૂપ — UI જેનો ઉપયોગ કરે છે
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

કી માટે **`allowUsageCommand`** સક્ષમ હોવું આવશ્યક છે (ડિફૉલ્ટ રૂપે બંધ — ડૅશબોર્ડનું API-કી
મેનેજર તેને દરેક કી માટે ટૉગલ કરે છે). તેના વિના એન્ડપોઇન્ટ `403` જવાબ આપે છે.

`?format=json` એક ભેદદર્શક સંરચના પરત કરે છે, જેથી કૉલર ક્યારેય અસ્વીકારના પ્રતિસાદમાંથી ડેટા ફીલ્ડ ન વાંચે.
સફળતા પર:

```jsonc
{
  "allowed": true,
  // કીએ પ્રતિ-કી વપરાશ મર્યાદાઓ (દૈનિક/સાપ્તાહિક USD) પસંદ કરી હોય ત્યારે જ હાજર હોય છે:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // પસંદ કરેલા પ્રદાતાનો ક્વોટા સ્નૅપશૉટ, અથવા હજી કંઈ કૅશ ન થયું હોય ત્યારે null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // દરેક કનેક્શનનો સ્નૅપશૉટ, જેથી UI અનેક પ્રદાતાઓને બાજુબાજુ રેન્ડર કરી શકે:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

અસ્વીકાર પર (`401` અમાન્ય કી / `403` પરવાનગી નથી), એ જ રૂટ
`{ "allowed": false, "error": { "message": "…" } }` પરત કરે છે — હાજર પરંતુ ખાલી `personal`/`provider`
(કી માન્ય છે, હજી કંઈ જાણકારી મળી નથી) એ અસ્વીકારથી અલગ સ્થિતિ છે, અને માત્ર JSON સ્વરૂપ
તે બંનેને અલગ પાડે છે.

**પ્રમાણીકરણ:** કૉલરની પોતાની Bearer API કી, જે `isValidApiKey` વડે માન્ય કરવામાં આવે છે — આ
મેનેજમેન્ટ સપાટી (`/api/keys/…`) _નથી_, જે `requireManagementAuth` પાછળ જ રહે છે.

### રૉ અને કટઑફ-સમાયોજિત ક્વોટા ટકાવારી

`/api/usage/om-usage` નો ઉપયોગ કરતી વખતે, કૉલરોએ **સાદા-ટેક્સ્ટ આઉટપુટ** અને સંરચિત
**JSON આઉટપુટ** દ્વારા રજૂ થતી ટકાવારીઓ વચ્ચેનો તફાવત ધ્યાનમાં લેવો જોઈએ:

| પાસું              | સાદા-ટેક્સ્ટનું સ્વરૂપ (`/api/usage/om-usage` / `@@om-usage`)                                | JSON સ્વરૂપ (`?format=json`)                                               |
| :----------------- | :------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------- |
| **આઉટપુટ ફીલ્ડ**   | `NN% left` (દા.ત., `20% left`)                                                               | `provider.quotas` / `providers[].quotas`                                   |
| **માપન**           | **કટઑફ-સમાયોજિત ઉપયોગયોગ્ય મંજૂરી**: કટઑફ થ્રેશોલ્ડથી ઉપરની બાકી ક્ષમતા                      | **રૉ અપસ્ટ્રીમ ક્વોટા**: પ્રદાતાનું અસંશોધિત માપન                          |
| **કટઑફ સ્કેલિંગ**  | `effectiveRemainingPercent()` દ્વારા સ્કેલ કરેલું, જેથી સુરક્ષિત અનામત `0% left` તરીકે દેખાય | કોઈ નહીં (પ્રદાતા દ્વારા રિપોર્ટ કરાયેલા રૉ સ્નૅપશૉટ મૂલ્યો)               |
| **થ્રેશોલ્ડ ડેટા** | દર્શાવેલી ટકાવારીમાં સમાવિષ્ટ                                                                | દરેક કનેક્શનના `quotaWindowThresholds` માં સંગ્રહિત (અથવા સર્વર ડિફૉલ્ટ્સ) |
| **મુખ્ય ઉપભોક્તા** | ઇન્ટરેક્ટિવ CLI, ટર્મિનલ પ્રોમ્પ્ટ, માનવ ઑપરેટરો                                             | પ્રોગ્રામેટિક ઇન્ટિગ્રેશન, ડૅશબોર્ડ, એનાલિટિક્સ, બિલિંગ ટ્રૅકર             |

#### કટઑફ સમાયોજનનું સૂત્ર

OmniRoute અપસ્ટ્રીમ ક્ષમતા સંપૂર્ણપણે ખૂટી જતી અટકાવવા માટે સક્રિય ક્વોટા કટઑફને સપોર્ટ કરે છે (જે કનેક્શન
`quotaWindowThresholds`, પ્રદાતાના ડિફૉલ્ટ્સ અથવા વૈશ્વિક રેઝિલિયન્સ સેટિંગ્સ દ્વારા કૉન્ફિગર થાય છે). જ્યારે કોઈ ક્વોટા વિન્ડો પર કટઑફ થ્રેશોલ્ડ
(દા.ત., `cutoff = 25%`) સક્રિય હોય, ત્યારે ટેક્સ્ટ રેન્ડરર બાકી મંજૂરીની ગણતરી આ રીતે કરે છે:

- જો `remaining <= cutoff`: તો `0%` પરત કરે છે.
- જો `remaining > cutoff`: તો `((remaining - cutoff) / (100 - cutoff)) * 100` પરત કરે છે.

ફૉર્મેટ કરેલું ટેક્સ્ટ આઉટપુટ તેને નજીકના પૂર્ણાંક સુધી રાઉન્ડ કરે છે (`Math.round(...)`).

#### દૃષ્ટાંતરૂપ ઉદાહરણ

**60% રૉ વપરાશ** (અર્થાત્ **40% રૉ બાકી ક્વોટા**) ધરાવતી પ્રદાતા વિન્ડો અને કૉન્ફિગર કરેલા
**25% બાકી-ક્વોટા કટઑફ** થ્રેશોલ્ડનો વિચાર કરો:

| રજૂઆત                           | ગણતરી                                              |  બાકી   |                     સૂચિત વપરાશ                     |
| :------------------------------ | :------------------------------------------------- | :-----: | :-------------------------------------------------: |
| **રૉ JSON (`?format=json`)**    | અપસ્ટ્રીમ સ્નૅપશૉટ (`quotas[window]`)              | **40%** |                       **60%**                       |
| **ટેક્સ્ટ સ્વરૂપ (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (જો `100 - remaining` ની ગણતરી કરવામાં આવે) |

- **ટેક્સ્ટ 20% બાકી કેમ બતાવે છે:** એકાઉન્ટમાં બાકી રહેલા 40% ભૌતિક ક્વોટામાંથી 25% ભાગ
  કટઑફ નીતિ દ્વારા અનામત છે. રાઉટર આ કનેક્શન તરફ રાઉટ કરવાનું બંધ કરે તે પહેલાં કૉલર પાસે ઉપયોગ કરી શકાય તેવી
  75% હેડરૂમમાંથી માત્ર 15% જ બાકી છે. સ્કેલિંગ ખાતરી કરે છે કે રાઉટિંગ બંધ થશે તે જ ક્ષણે કનેક્શન
  ક્ષમતા ખૂટી ગયાનો સંકેત (`0% left`) આપે.
- **JSON રૉ મૂલ્યો કેમ જાળવે છે:** JSON પેલોડ પ્રદાતાનો ચોક્કસ સ્નૅપશૉટ (`UsageSnapshot`) પરત કરે છે,
  જેથી બાહ્ય ટૂલ્સને સર્વર-સાઇડ નુકસાનકારક સ્કેલિંગ વિના વાસ્તવિક અપસ્ટ્રીમ ઉપયોગ અને કનેક્શન-સ્તરના
  `quotaWindowThresholds` ની ઍક્સેસ મળે.

#### ઉપભોક્તા માઇગ્રેશન માર્ગદર્શન

જો કોઈ બાહ્ય ઇન્ટિગ્રેશન (જેમ કે એડિટર પ્લગઇન અથવા એજન્ટ એક્સ્ટેન્શન) અગાઉ ટેક્સ્ટ
એન્ડપોઇન્ટ (`NN% left`) ને સ્ક્રેપ કરતું હતું અને વપરાયેલી ટકાવારીની ગણતરી `100 - NN` તરીકે કરતું હતું, તો `?format=json` પર સ્થાનાંતરિત થવાનો અર્થ છે:

- કાચી JSON કિંમતો વાંચવાથી **વાસ્તવિક અપસ્ટ્રીમ વપરાશ** પ્રતિબિંબિત થશે (ઉપરના ઉદાહરણમાં 60% વપરાયેલ).
- જો ઇન્ટિગ્રેશન ટેક્સ્ટ એન્ડપોઇન્ટના ઉપયોગયોગ્ય-ભથ્થા સંબંધિત અર્થને જાળવી રાખવા માંગતું હોય, તો તે કનેક્શન-સ્તરના ઓવરરાઇડ્સ માટે `quotaWindowThresholds` નો ઉપયોગ કરીને
  અસરકારક બાકી રહેલા પ્રમાણના સૂત્રનું ક્લાયન્ટ-સાઇડ મૂલ્યાંકન કરી શકે છે.

### લેટન્સી પર અસર

સિમેન્ટિક કૅશ HIT પ્રતિસાદને કૅશમાંથી પ્રદાન કરે છે **અપસ્ટ્રીમ કૉલ કર્યા વિના**,
તેથી દર્શાવાયેલ `X-OmniRoute-Response-Latency` લગભગ શૂન્ય હોય છે
(મૂળ અપસ્ટ્રીમ લેટન્સી ગમે તેટલી હોય). લેટન્સી-સંવેદનશીલ ક્લાયન્ટ્સે
(બેન્ચમાર્કિંગ, p50/p99 મોનિટરિંગ) `X-OmniRoute-Cache-Latency`
પ્રતિસાદ હેડર તપાસવું જોઈએ:

| મૂલ્ય       | અર્થ                                                                |
| ----------- | ------------------------------------------------------------------- |
| `synthetic` | પ્રતિસાદ કૅશમાંથી પ્રદાન થયો છે; લેટન્સી વાસ્તવિક અપસ્ટ્રીમ સમય નથી |
| _(ગેરહાજર)_ | વાસ્તવિક અપસ્ટ્રીમ કૉલમાંથી મળેલો પ્રતિસાદ                          |

### કી-દીઠ કૅશ બાયપાસ

API કી `cacheDefaultMode` દ્વારા સિમેન્ટિક કૅશ રીડ્સમાંથી બહાર રહી શકે છે:

| મૂલ્ય    | વર્તણૂક                                                   |
| -------- | --------------------------------------------------------- |
| `legacy` | સામાન્ય કૅશ વર્તણૂક (ડિફૉલ્ટ)                             |
| `bypass` | કૅશ લુકઅપ સંપૂર્ણપણે અવગણો; હંમેશાં અપસ્ટ્રીમનો ઉપયોગ કરો |

કી બનાવતી વખતે (`POST /api/keys`) સેટ કરો અથવા (`PATCH /api/keys/[id]`) દ્વારા અપડેટ કરો:

```json
{ "cacheDefaultMode": "bypass" }
```

### વિનંતી-દીઠ બાયપાસ

કી સેટિંગ્સ ગમે તે હોય, કોઈપણ વિનંતી કૅશને બાયપાસ કરી શકે છે:

```
X-OmniRoute-No-Cache: true
```

સિંક કરેલા/આયાત કરેલા મોડલ્સ માટે, `PUT /api/provider-models` `provider`, `modelId`, અને
`maxOutputTokenOverride` સ્વીકારે છે: ધન પૂર્ણાંક મેન્યુઅલ આઉટપુટ-ટોકન મર્યાદા સેટ કરે છે અને `null`
ડિફૉલ્ટ પુનઃસ્થાપિત કરવા માટે તેને દૂર કરે છે. `GET /api/provider-models?provider=<provider>` આ
મૂલ્યોને `modelOutputOverrides`માં પરત કરે છે, જેમાં કસ્ટમ-મોડલ પંક્તિ વિનાનાં મોડલ્સ પણ સામેલ છે. ઓવરરાઇડ
રનટાઇમ `max_output_tokens` ક્ષમતાનો ઉપયોગ કરે છે અને મોડલના પુનઃ-સિંક પછી પણ જળવાઈ રહે છે. OpenAI-સુસંગત
પ્રદાતા પેજ સમાન સંપાદન/દૂર કરવાના નિયંત્રણો આપે છે અને સ્પષ્ટ વિઝન સપોર્ટ ધરાવતાં મોડલ્સને ચિહ્નિત કરે છે.

કસ્ટમ Chat Completions નોડ્સ સ્પષ્ટ રીઝનિંગ ઑપ્ટ-આઉટ્સને અપસ્ટ્રીમ બૅકએન્ડ અનુસાર અનુકૂલિત કરે છે.
સફળ કનેક્શન પરીક્ષણ એવા દરેક ચોક્કસ મોડલ ID માટે આપમેળે chat-template નિયંત્રણો પસંદ કરે છે,
જેની `/models` એન્ટ્રી માન્ય `owned_by` મૂલ્ય હોવાની પુષ્ટિ કરે છે: `vllm`, `sglang`, અથવા `llamacpp`.
પારદર્શક OpenAI-સુસંગત રૅપર્સ મૂળ મોડલ એન્ટ્રીને નેસ્ટેડ
`openai` ઑબ્જેક્ટની અંદર જાળવી શકે છે; શોધ વધુમાં વધુ આવા ત્રણ એન્વલપને અનુસરે છે. ગેરહાજર, અજ્ઞાત અથવા
વિરોધાભાસી માલિકી ધરાવતાં મોડલ્સ સામાન્ય OpenAI વર્તન જાળવી રાખે છે. શોધ હાલની કૅટલૉગ વિનંતીનો પુનઃઉપયોગ કરે છે,
કોઈ completion ટોકન્સ જનરેટ કરતી નથી અને કનેક્શન એન્ડપોઇન્ટ બદલાય ત્યારે અમાન્ય થઈ જાય છે.

જે બૅકએન્ડ આ મેટાડેટા દર્શાવતું નથી તેના માટે વર્તન નિશ્ચિત કરવા, હાલની આંશિક
પ્રદાતા અપડેટ APIનો ઉપયોગ કરો:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

તે બૉડીને `PUT /api/providers/<connection-id>` સાથે મોકલો. તે કનેક્શન પર, `none`નો સ્પષ્ટ
રીઝનિંગ પ્રયત્ન `chat_template_kwargs.thinking=false` અને
`chat_template_kwargs.enable_thinking=false` તરીકે મોકલવામાં આવે છે. સ્પષ્ટ નેટિવ ટેમ્પ્લેટ મૂલ્યો અધિકૃત રહે છે,
સિવાય કે સર્વર-સાઇડ રીઝનિંગ નિયમ કોઈ પ્રયત્નને ફરજિયાત કરે. આ સેટિંગ માત્ર ત્યારે લાગુ પડે છે જ્યારે કસ્ટમ
OpenAI-સુસંગત કનેક્શન Chat Completions બૉડી મોકલે; Responses વિનંતીઓ અને સામાન્ય
પ્રદાતાઓ તેમના નેટિવ વિનંતી સ્વરૂપને જાળવી રાખે છે. સામાન્ય OpenAI
`reasoning_effort` પાસથ્રૂ ફરજિયાત કરવા `reasoningControl`ને `openai` પર સેટ કરો, અથવા સ્વચાલિત શોધનો ઉપયોગ કરવા તેને છોડી દો/`null` પર સેટ કરો.

Claude Code ઑટો-મોડ ક્લાસિફાયર વિનંતીઓમાં કોઈ સ્પષ્ટ રીઝનિંગ નિયંત્રણો ન હોય ત્યારે ડિફૉલ્ટ રૂપે
નેટિવ થિંકિંગ અક્ષમ હોય છે. શોધ મોડલનાં નામો અથવા completion મર્યાદાઓને બદલે Claude-ફોર્મેટ
વિનંતીઓમાં ક્લાસિફાયરના સિસ્ટમ માર્કરનો ઉપયોગ કરે છે. સ્પષ્ટ બૉડી નિયંત્રણો, સપોર્ટેડ પ્રયત્ન/થિંકિંગ
હેડર્સ, રાઉટિંગ નિયમો અને નિર્ધારિત મોડલ પ્રયત્ન તેમની હાલની પ્રાથમિકતા જાળવી રાખે છે. ક્લાસિફાયરના બંને
તબક્કાઓ તેમના પ્રૉમ્પ્ટ્સ, completion મર્યાદાઓ, સ્ટૉપ સિક્વન્સ અને વાસ્તવિક અપસ્ટ્રીમ પરવાનગી
નિર્ણયો જાળવી રાખે છે; બીજો તબક્કો હજુ પણ સામાન્ય ટેક્સ્ટ તરીકે તેનું વિનંતી કરાયેલ દૃશ્યમાન રીઝનિંગ આપી શકે છે.

`PATCH /api/keys/{id}` હાલની કીની પરવાનગીઓ અપડેટ કરે છે. દરેક `/api/keys*` રૂટની જેમ, તેને વ્યવસ્થાપન અધિકૃતતા જરૂરી છે ([વ્યવસ્થાપન પ્રમાણીકરણ](../guides/MANAGEMENT-AUTH.md) જુઓ), ઇન્ફરન્સ કી નહીં. તમે બદલવા માગતા હો તે જ ફીલ્ડ્સ મોકલો; તેમાંથી કોઈપણ ફીલ્ડ વિનંતીમાં ન હોય તો વિનંતી `No valid fields to update` સાથે નકારવામાં આવે છે. સ્વીકાર્ય ફીલ્ડ્સ `src/shared/validation/schemas/keys.ts` માં `updateKeyPermissionsSchema` દ્વારા વ્યાખ્યાયિત કરવામાં આવ્યા છે.

પુનઃસ્થાપન) અને `POST /api/settings/import-json` લાઇવ ડેટાબેઝ અથવા સેટિંગ્સને બદલે છે, તેથી મશીન

`DELETE /api/db-backups` (સંગ્રહિત બૅકઅપ્સ દૂર કરવા) અને `PATCH /api/db-backups` (રિટેન્શન સેટિંગ્સ:
સાચવેલા મૂલ્યો દરેક બૅકઅપ પછી સ્વચાલિત રીતે થતી સફાઈને નિયંત્રિત કરે છે) પર પણ લાગુ પડે છે. સૂચિ મેળવવા (`GET`) અને
મેન્યુઅલ બૅકઅપ બનાવવા (`PUT`) માટે સામાન્ય મેનેજમેન્ટ પ્રમાણીકરણ જળવાઈ રહે છે.

### સંસ્કરણ અને રિલીઝ ચેનલ

```bash
GET /api/system/version
```

માત્ર લૂપબૅક માટેનો મેનેજમેન્ટ રૂટ (એડમિન પ્રમાણીકરણ). હાલમાં ચાલી રહેલું સંસ્કરણ, નવીનતમ
પ્રકાશિત સંસ્કરણ અને સ્વચાલિત અપડેટની સ્થિતિ પરત કરે છે. `releaseChannel` અને `channels` ઉમેરાયેલા
ફીલ્ડ્સ છે (રેલ 3.8.54); `channel` તેનો મૂળ અર્થ જાળવી રાખે છે — ડૅશબોર્ડ અપડેટર જે ડિપ્લોયમેન્ટ મોડનો
ઉપયોગ કરે છે (`npm`, `source` અથવા `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — હાલમાં ચાલી રહેલા બિલ્ડની npm ચેનલ: `-nightly.*` સંસ્કરણો માટે `nightly`,
  અન્ય પ્રી-રિલીઝ (`-rc.*`, `-beta.*`, `-alpha.*`) માટે `next`, `channels.latest` કરતાં જૂના મેજરના
  સ્થિર સંસ્કરણ માટે `lts`, અન્યથા `latest`. આ નિયમો
  `scripts/release/dist-tag.mjs` જેવા જ છે, જે પ્રકાશન સમયે npm dist-tag પસંદ કરે છે.
- `channels` — `npm view omniroute dist-tags`માંથી દરેક dist-tagનું પ્રકાશિત હેડ (રજિસ્ટ્રી
  HTTP ફૉલબૅક), જેને `latest` જેટલા જ 10-મિનિટના TTL સાથે કૅશ કરવામાં આવે છે. `latest` હંમેશાં હાજર
  રહે છે (પહેલાં `latest` ફીલ્ડ અને પછી `"unavailable"` પર ફૉલબૅક થાય છે); `next`, `nightly` અને `lts`
  માત્ર ત્યારે જ દેખાય છે જ્યારે તે dist-tag અસ્તિત્વમાં હોય. `Cache-Control: no-cache` વિનંતી બંને લુકઅપને રિફ્રેશ કરે છે.

ચેનલ મોડેલ (`latest` = 4.0 GA સુધી v3, `next` = rc, `nightly` = `develop` બિલ્ડ્સ,
`lts` = 4.0 GA પછીના v3 પૅચો)નું વર્ણન `docs/ops/RELEASE_STRATEGY.md`માં કરવામાં આવ્યું છે.

## ઑડિયો ટ્રાન્સક્રિપ્શન

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

કોઈપણ ગોઠવેલા STT પ્રદાતાનો ઉપયોગ કરીને ઑડિયો ફાઇલોનું ટ્રાન્સક્રિપ્શન કરો. પ્રથમ પાથ
સેગમેન્ટ મૂળ પ્રદાતા પસંદ કરે છે (`openai/…`, `deepgram/…`). અન્ય વિક્રેતાનું
મોડેલ ફરીથી નિકાસ કરતા ગેટવે ક્વૉલિફાઇડ id નો ઉપયોગ કરે છે
(`openrouter/deepgram/nova-3`).

**વિનંતી:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**પ્રતિસાદ:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**મોડેલ id નાં ઉદાહરણો:** `openai/whisper-1` (OpenAI કી જરૂરી છે),
`openrouter/deepgram/nova-3` (OpenRouter કી જરૂરી છે),
`deepgram/nova-3` (મૂળ Deepgram કી જરૂરી છે). સીધી
`deepgram/nova-3` વિનંતી OpenRouter નો ઉપયોગ **કરતી નથી**.

**સમર્થિત ફોર્મેટ્સ:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

```bash
GET /api/tags
```

વિનંતીઓનું Ollama અને આંતરિક ફોર્મેટ્સ વચ્ચે આપમેળે રૂપાંતર થાય છે.

## ટોકનયુક્ત VS Code / હેડર-રહિત ઉપનામો

જ્યારે કોઈ ઇન્ટિગ્રેશન `Authorization` હેડર ઉમેરી શકતું ન હોય અને API કીને બેઝ URL માં એમ્બેડ કરવાની જરૂર હોય, ત્યારે આ ઉપનામોનો ઉપયોગ કરો.

```bash
# OpenAI-શૈલીનું કેટલૉગ ઉપનામ
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-શૈલીનાં ચેટ ઉપનામો
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-શૈલીનાં ઉપનામો
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

ઉદાહરણ:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

નોંધો:

- ટોકનયુક્ત ઉપનામો `/v1/*` અને `/api/tags` જેવા જ હેન્ડલર્સનો પુનઃઉપયોગ કરે છે; પ્રતિસાદની સંરચના સમાન રહે છે.
- જ્યારે ક્લાયન્ટ કસ્ટમ હેડર્સને સમર્થન આપતો હોય ત્યારે `Authorization: Bearer ...` ને પ્રાધાન્ય આપો.
- URL-આધારિત ટોકન્સ રિવર્સ-પ્રૉક્સી લૉગ્સ, બ્રાઉઝર ઇતિહાસ અને OmniRoute ની બહારની ટેલિમેટ્રીમાં દેખાઈ શકે છે. તેમને ડિફૉલ્ટ પ્રમાણીકરણ મોડ તરીકે નહીં, પરંતુ સુસંગતતા વિકલ્પ તરીકે ગણો.

## બજેટ

```bash
# બધી API કી માટે બજેટની સ્થિતિ મેળવો
GET /api/usage/budget

# બજેટ સેટ અથવા અપડેટ કરો
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **સ્કીમા નોંધો** (`setBudgetSchema`): `apiKeyId` આવશ્યક છે; `dailyLimitUsd`, `weeklyLimitUsd` અથવા `monthlyLimitUsd` માંથી ઓછામાં ઓછું એક શૂન્ય કરતાં મોટું હોવું આવશ્યક છે. વૈકલ્પિક ફીલ્ડ્સ: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). લેગસી `{keyId, limit, period}` સંરચના `400 Bad Request` પરત કરે છે.

## ટોકન મર્યાદાઓ

પ્રતિ-API-key **ટોકન** બજેટ (ઉપરના USD-આધારિત બજેટથી અલગ). વિનંતીના પાથ પર જ લાગુ કરવામાં આવે છે: જ્યારે કીની વર્તમાન વિન્ડોનો ઉપયોગ તેની મર્યાદા સુધી પહોંચે છે, ત્યારે વિનંતીઓ `429 Too Many Requests` સાથે નકારવામાં આવે છે. મર્યાદાઓને ચોક્કસ `model`, `provider` સુધી મર્યાદિત કરી શકાય છે અથવા સમગ્ર કી પર `global` સ્તરે લાગુ કરી શકાય છે; જ્યારે એક વિનંતી સાથે અનેક મર્યાદાઓ મેળ ખાતી હોય, ત્યારે સૌથી વધુ પ્રતિબંધિત મર્યાદા લાગુ થાય છે.

```bash
# કીની ટોકન મર્યાદાઓની યાદી મેળવો (લાઇવ વિન્ડો ઉપયોગ સહિત)
GET /api/usage/token-limits?apiKeyId=key-123

# ટોકન મર્યાદા બનાવો અથવા અપડેટ કરો
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id દ્વારા ટોકન મર્યાદા કાઢી નાખો
DELETE /api/usage/token-limits?id=tl-abc
```

> **સ્કીમા નોંધો** (`setTokenLimitSchema`): `apiKeyId` અને `scopeType` (`model` | `provider` | `global`) આવશ્યક છે. `scopeType`, `global` ન હોય ત્યાં સુધી `scopeValue` આવશ્યક છે (દા.ત. `model` સ્કોપ માટે મોડેલ id, `provider` સ્કોપ માટે પ્રદાતા id). `tokenLimit` ધન પૂર્ણાંક હોવો આવશ્યક છે (સ્ટ્રિંગમાંથી રૂપાંતરિત). વૈકલ્પિક: `id` (બનાવવા માટે છોડો, અપડેટ કરવા માટે આપો), `resetInterval` (`daily` | `weekly` | `monthly`, ડિફૉલ્ટ `monthly`), `resetTime` (`HH:MM`), `enabled` (ડિફૉલ્ટ `true`). `GET` પ્રતિસાદો દરેક મર્યાદાને `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, અને `nextResetAt` વડે સમૃદ્ધ બનાવે છે. આ મેનેજમેન્ટ-ક્લાસ એન્ડપોઇન્ટ છે (authz પાઇપલાઇન દ્વારા પ્રમાણીકરણ કેન્દ્રીય રીતે લાગુ કરવામાં આવે છે).

## વિનંતી પ્રક્રિયા

1. ક્લાયન્ટ `/v1/*` પર વિનંતી મોકલે છે
2. રૂટ હેન્ડલર `handleChat`, `handleEmbedding`, `handleAudioTranscription`, અથવા `handleImageGeneration` ને કૉલ કરે છે
3. મોડેલનું નિરાકરણ કરવામાં આવે છે (સીધું provider/model અથવા alias/combo)
4. એકાઉન્ટ ઉપલબ્ધતા ફિલ્ટરિંગ સાથે સ્થાનિક DBમાંથી ઓળખપત્રો પસંદ કરવામાં આવે છે
5. ચેટ માટે: `handleChatCore` સિમેન્ટિક/સિગ્નેચર કૅશ તપાસે છે અને combo કમ્પ્રેશન સેટિંગ્સનું નિરાકરણ કરે છે
6. સક્રિય હોય ત્યારે પ્રદાતા અનુવાદ પહેલાં સક્રિય કમ્પ્રેશન ચાલે છે (`lite`, Caveman, RTK, અથવા સ્ટૅક્ડ)
7. પ્રદાતા એક્ઝિક્યુટર અપસ્ટ્રીમ વિનંતી મોકલે છે
8. પ્રતિસાદનું ફરીથી ક્લાયન્ટ ફોર્મેટમાં રૂપાંતર કરવામાં આવે છે (ચેટ) અથવા તે જેમ છે તેમ પરત કરવામાં આવે છે (એમ્બેડિંગ્સ/ઇમેજિસ/ઑડિયો)
9. ઉપયોગ, કમ્પ્રેશન એનાલિટિક્સ અને વિનંતી લૉગ્સ નોંધવામાં આવે છે
10. ભૂલો આવે ત્યારે combo નિયમો અનુસાર ફૉલબૅક લાગુ થાય છે

સંપૂર્ણ આર્કિટેક્ચર સંદર્ભ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Combo મેનેજમેન્ટ

ઉચ્ચ-સ્તરના રૂટિંગ combos (જેનો સારાંશ `/api/combos*` હેઠળ પહેલેથી આપવામાં આવ્યો છે) ને model id પેટર્નમાંથી 1:1 પણ મૅપ કરી શકાય છે, જેનાથી OpenAI-શૈલીના model id ને combo તરફ પારદર્શક રીતે રીડાયરેક્ટ કરી શકાય છે.

| પદ્ધતિ | પાથ                              | વર્ણન                                                                        |
| ------ | -------------------------------- | ---------------------------------------------------------------------------- |
| GET    | `/api/model-combo-mappings`      | બધા model→combo મૅપિંગ્સની યાદી મેળવો                                        |
| POST   | `/api/model-combo-mappings`      | મૅપિંગ બનાવો — બૉડી: `{pattern, comboId, priority?, enabled?, description?}` |
| GET    | `/api/model-combo-mappings/[id]` | એક મૅપિંગ મેળવો                                                              |
| PUT    | `/api/model-combo-mappings/[id]` | હાલના મૅપિંગના ફીલ્ડ્સ અપડેટ કરો                                             |
| DELETE | `/api/model-combo-mappings/[id]` | મૅપિંગ દૂર કરો                                                               |

**પ્રમાણીકરણ:** મેનેજમેન્ટ સેશન/API key (`requireManagementAuth`).

## નોંધાયેલ કીઓ (સ્વચાલિત વ્યવસ્થાપન)

દૈનિક/કલાકદીઠ ક્વોટા સાથે, અંતર્નિહિત પ્રદાતા/એકાઉન્ટ સામે API કીઓ જારી કરવા અને રોટેટ કરવા માટે સ્વચાલિત કી વ્યવસ્થાપન સબસિસ્ટમ દ્વારા ઉપયોગમાં લેવાય છે.

| પદ્ધતિ | પાથ                                   | વર્ણન                                                                                                                                                                                                             |
| ------ | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/registered-keys`             | નોંધાયેલ કીઓની યાદી આપો (માત્ર છુપાવેલો પ્રીફિક્સ)                                                                                                                                                                |
| POST   | `/api/v1/registered-keys`             | નવી નોંધાયેલ કી જારી કરો — બોડી: `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}`. મૂળ કી **માત્ર એક વાર** પરત કરે છે. ક્વોટાને કારણે ઇનકાર થાય ત્યારે `429` પરત કરે છે. |
| GET    | `/api/v1/registered-keys/[id]`        | નોંધાયેલ કીનું મેટાડેટા મેળવો (મૂળ કી સામગ્રી વિના)                                                                                                                                                               |
| DELETE | `/api/v1/registered-keys/[id]`        | નોંધાયેલ કી રદ કરો                                                                                                                                                                                                |
| POST   | `/api/v1/registered-keys/[id]/revoke` | સ્પષ્ટ રદબાતલ એન્ડપોઇન્ટ (DELETE જેવી જ અસર)                                                                                                                                                                      |

**પ્રમાણીકરણ:** મેનેજમેન્ટ સેશન/API કી (`requireManagementAuth`) — `/api/keys` જેવું જ સુરક્ષા નિયંત્રણ: ડેશબોર્ડ સેશન, સ્થાનિક CLI ટોકન અથવા `manage`/`admin` સ્કોપ ધરાવતી API કી; માત્ર ઇન્ફરન્સ માટેની API કીઓને `403` મળે છે. `/v1/quotas/check` અને `/v1/issues/report` પણ જુઓ.

## એજન્ટ્સ પ્રોટોકોલ

OmniRoute વપરાશકર્તાઓ વતી દૂરસ્થ રીતે ચલાવવામાં આવતા ક્લાઉડ એજન્ટ કાર્યો (Claude Code, Codex Cloud, OpenHands વગેરે).

| પદ્ધતિ | પાથ                           | વર્ણન                                                                                                                                                   |
| ------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/agents/tasks`        | કાર્યોની યાદી — વૈકલ્પિક `?provider=`, `?status=`, `?limit=` (1–500, ડિફૉલ્ટ 50)                                                                        |
| POST   | `/api/v1/agents/tasks`        | કાર્ય બનાવો — બૉડી `CreateCloudAgentTaskSchema` (`providerId`, `prompt`, `source`, `options?`) દ્વારા માન્ય કરાય છે. કાર્ય એન્વલપ સાથે `201` પરત કરે છે |
| DELETE | `/api/v1/agents/tasks?id=...` | કાર્ય કાઢી નાખો                                                                                                                                         |
| GET    | `/api/v1/agents/tasks/[id]`   | કાર્ય વાંચો — જ્યારે `external_id` સેટ હોય ત્યારે અપસ્ટ્રીમ ક્લાઉડ એજન્ટ પાસેથી સ્થિતિને સિંક્રોનસ રીતે રિફ્રેશ કરે છે                                  |

## મેનેજમેન્ટ પ્રોક્સીઓ

આઉટબાઉન્ડ HTTP(S)/SOCKS પ્રોક્સીઓ, જે પ્રદાતાઓ, એકાઉન્ટ્સ અથવા વૈશ્વિક સ્તરે અસાઇન કરી શકાય છે.

| પદ્ધતિ | પાથ                                          | વર્ણન                                                                                                                                                             |
| ------ | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | પ્રોક્સીઓની યાદી (`?id=` સાથે એક પ્રોક્સી પરત કરે છે; `?id=&where_used=1` સાથે અસાઇનમેન્ટ ગ્રાફ પરત કરે છે)                                                       |
| POST   | `/api/v1/management/proxies`                 | પ્રોક્સી બનાવો — બૉડી `createProxyRegistrySchema` દ્વારા માન્ય કરાય છે                                                                                            |
| PATCH  | `/api/v1/management/proxies`                 | પ્રોક્સી અપડેટ કરો — બૉડી `updateProxyRegistrySchema` દ્વારા માન્ય કરાય છે (`id` જરૂરી છે)                                                                        |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | પ્રોક્સી કાઢી નાખો (અસાઇનમેન્ટ્સ અલગ કરવા માટે `force=1` વાપરો)                                                                                                   |
| GET    | `/api/v1/management/proxies/assignments`     | અસાઇનમેન્ટ્સની યાદી — `proxy_id`, `scope`, `scope_id` દ્વારા ફિલ્ટર કરી શકાય છે; કનેક્શન માટે સક્રિય પ્રોક્સી નિર્ધારિત કરવા `resolve_connection_id=<id>` પાસ કરો |
| PUT    | `/api/v1/management/proxies/assignments`     | અસાઇન કરો — બૉડી `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) દ્વારા માન્ય કરાય છે. ડિસ્પેચર કૅશ સાફ કરે છે                                            |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | બલ્ક-અસાઇન કરો — બૉડી `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`) દ્વારા માન્ય કરાય છે                                                          |
| GET    | `/api/v1/management/proxies/health?hours=24` | સમયગાળા દરમિયાન એકંદર પ્રોક્સી હેલ્થ (સફળતા/નિષ્ફળતાની સંખ્યા, વિલંબ)                                                                                             |

## સ્થિતિસ્થાપકતા (વિસ્તૃત)

OmniRoute ત્રણ સ્વતંત્ર અસ્થાયી-નિષ્ફળતા મિકેનિઝમ ઉપલબ્ધ કરાવે છે; નીચેના મેનેજમેન્ટ એન્ડપોઇન્ટ્સ ઓપરેટર્સને તેમની સ્થિતિ વાંચવા અને તેને ઓવરરાઇડ કરવાની મંજૂરી આપે છે:

| વ્યાપ            | સ્થિતિનો સંગ્રહ                           | વાંચવું                                   | રીસેટ / સાફ કરવું                                          |
| ---------------- | ----------------------------------------- | ----------------------------------------- | ---------------------------------------------------------- |
| પ્રોવાઇડર બ્રેકર | `domain_circuit_breakers` + ઇન-મેમરી      | `/api/monitoring/health`                  | `POST /api/resilience/reset`                               |
| કનેક્શન કૂલડાઉન  | પ્રોવાઇડર કનેક્શન્સ પર `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (લેઝી રીતે ફરી સક્ષમ થાય છે; પ્રોવાઇડર PUT દ્વારા સાફ કરો) |
| મોડેલ લૉકઆઉટ     | ઇન-મેમરી મોડેલ-ઉપલબ્ધતા રજિસ્ટ્રી         | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                   |

`PATCH /api/resilience`, `providerBreaker.oauth` અને `providerBreaker.apikey` હેઠળ પ્રોવાઇડર બ્રેકર ઓવરરાઇડ્સ સ્વીકારે છે. દરેક પ્રોફાઇલ `degradationThreshold`, `failureThreshold`, અને `resetTimeoutMs`ને સપોર્ટ કરે છે; આ જ ફીલ્ડ્સ Dashboard → Settings → Resilienceમાં ઉપલબ્ધ છે.

```bash
# કોઈ એક મોડેલ લૉકઆઉટ સાફ કરો
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# બધા લૉકઆઉટ્સ સાફ કરો
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

સંપૂર્ણ વૈચારિક સંદર્ભ અને બ્રેકરના ડિફૉલ્ટ્સ માટે: [`CLAUDE.md`](../../CLAUDE.md) → "સ્થિતિસ્થાપકતા રનટાઇમ સ્થિતિ" અને [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) જુઓ.

### રેટ-લિમિટ ક્યૂ અને ઑટો-એનેબલ સુરક્ષા જાળ

- **સમર્થિત રાઇટ પાથ**: કનેક્શન માટે રેટ-લિમિટ સુરક્ષા ટૉગલ કરવા માટે બોડી `{"connectionId": "<id>", "enabled": true|false}` સાથેનું `POST /api/rate-limits` સમર્થિત મેનેજમેન્ટ એન્ડપોઇન્ટ છે. `PUT /api/providers/[id]` ઇરાદાપૂર્વક `rateLimitProtection`ને સંશોધિત કે ફ્લિપ કરતું નથી (#11278).
- **`enabled: false`ની સિમેન્ટિક્સ**: `enabled: false` સેટ કરવાથી કનેક્શન માટેની સ્પષ્ટ સુરક્ષા દૂર થાય છે, પરંતુ તે સક્રિય API-કી કનેક્શનને વૈશ્વિક ઑટો-એનેબલ સુરક્ષા જાળ (`autoEnableApiKeyProviders = true`)માંથી **બહાર રાખતું નથી**. `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`)માં, `false` અને `undefined` સમકક્ષ છે; સ્પષ્ટ સુરક્ષા વગરનાં સક્રિય API-કી કનેક્શન્સ ઑટો-એનેબલ સુરક્ષા જાળ હેઠળ સુરક્ષિત રહે છે.
- **વૈશ્વિક રીતે અક્ષમ કરવું**: રેટ-લિમિટ ક્યૂ વિના API-કી કનેક્શન્સ ચલાવવા માટે, `RATE_LIMIT_AUTO_ENABLE=false` (env) અથવા `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) દ્વારા સુરક્ષા જાળને વૈશ્વિક રીતે અક્ષમ કરો.

## MCP સર્વર

OmniRoute 3 ટ્રાન્સપોર્ટ (stdio, SSE, streamable-http) અને મર્યાદિત ટૂલ્સ સાથે એમ્બેડેડ Model Context Protocol સર્વર પ્રદાન કરે છે. નીચેના ડૅશબોર્ડ એન્ડપોઇન્ટ્સ સ્થિતિ/ઑડિટ ડેટા વાંચે છે અને HTTP ટ્રાન્સપોર્ટ્સને પ્રૉક્સી કરે છે.

| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | હાર્ટબીટ, ટ્રાન્સપોર્ટ, ઑનલાઇન સ્થિતિ, છેલ્લો કૉલ, ટોચના ટૂલ્સ, 24 કલાકનો સફળતા દર |

| GET | `/api/mcp/audit` | ઑડિટ લૉગ ક્વેરી કરો — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | એકત્રિત ઑડિટ આંકડા (કુલ સંખ્યા, સફળતા દર, સરેરાશ અવધિ, ટોચના ટૂલ્સ) |

**પ્રમાણીકરણ:** `sse`/`stream` ટ્રાન્સપોર્ટ્સ MCP-વિશિષ્ટ પ્રમાણીકરણ સપાટીને અનુસરે છે (`mcp` સ્કોપ સાથેની Bearer API કી); `status`/`tools`/`audit*` રૂટ્સ ડૅશબોર્ડ પરથી વાંચી શકાય છે (ડૅશબોર્ડ હોસ્ટ સુધી પહોંચવા ઉપરાંત કોઈ વધારાના પ્રમાણીકરણની જરૂર નથી).

> બંને HTTP ટ્રાન્સપોર્ટ્સ `settings.mcpEnabled` અને `settings.mcpTransport` દ્વારા નિયંત્રિત થાય છે — ટ્રાન્સપોર્ટ મેળ ન ખાય તો `400` પરત થાય છે, જ્યારે MCP અક્ષમ સ્થિતિમાં `503` પરત થાય છે.

## A2A સર્વર

OmniRoute નિરીક્ષણ/ડૅશબોર્ડના ઉપયોગ માટે REST રૅપર ઉપરાંત A2A (Agent-to-Agent) JSON-RPC 2.0 એન્ડપૉઇન્ટ ઉપલબ્ધ કરાવે છે.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # જ્યાં સુધી OMNIROUTE_API_KEY સેટ ન હોય ત્યાં સુધી વૈકલ્પિક
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

સમર્થિત પદ્ધતિઓ (તમામ `settings.a2aEnabled` પર નિર્ભર છે):

| પદ્ધતિ           | વર્ણન                                                              |
| ---------------- | ------------------------------------------------------------------ |
| `message/send`   | સિંક્રોનસ કૌશલ્ય અમલીકરણ; `{task, artifacts, metadata}` પરત કરે છે |
| `message/stream` | સમાન કૌશલ્ય સમૂહનું સ્ટ્રીમિંગ SSE અમલીકરણ                         |
| `tasks/get`      | `taskId` દ્વારા કાર્ય મેળવો                                        |
| `tasks/cancel`   | `taskId` દ્વારા કાર્ય રદ કરો                                       |

બિલ્ટ-ઇન કૌશલ્યો: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### એજન્ટ કાર્ડ

```bash
GET /.well-known/agent.json
```

જાહેર A2A એજન્ટ કાર્ડ (નામ, વર્ણન, ક્ષમતાઓ, કૌશલ્ય કૅટલૉગ, ઑથ સ્કીમ) પરત કરે છે — 1h માટે સાર્વજનિક રીતે કૅશ કરેલું. ઑથ જરૂરી નથી.

### REST સહાયકો

| પદ્ધતિ | પાથ                          | વર્ણન                                                                                                              |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/a2a/status`            | A2A સક્ષમ સ્થિતિ + કાર્યના આંકડા + કૅશ કરેલા એજન્ટ કાર્ડનો સારાંશ                                                  |
| GET    | `/api/a2a/tasks`             | કાર્યોની સૂચિ — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (REST સહાયક તરીકે અમલમાં મૂકેલું નથી — JSON-RPC `message/send` દ્વારા બનાવો)                                       |
| GET    | `/api/a2a/tasks/[id]`        | એક કાર્ય મેળવો                                                                                                     |
| POST   | `/api/a2a/tasks/[id]/cancel` | કાર્ય રદ કરો                                                                                                       |

**ઑથ:** REST સહાયકો મેનેજમેન્ટ ઑથ વિના ચાલે છે (ડૅશબોર્ડ દ્વારા વાંચી શકાય છે); જો કૉન્ફિગર કરેલું હોય, તો JSON-RPC `/a2a` રૂટ Bearer `OMNIROUTE_API_KEY` વાપરે છે.

| POST | `/api/cloud/model/resolve` | સ્થાનિક રાઉટિંગ કોષ્ટકનો ઉપયોગ કરીને લૉજિકલ મૉડલ idને ચોક્કસ પ્રોવાઇડર/મૉડલમાં રિઝૉલ્વ કરો |

| GET | `/api/assess` | નવીનતમ આકલન વર્ગીકરણો વાંચો (દરેક પ્રોવાઇડર/મૉડલ માટે) |
| POST | `/api/assess` | આકલન ચલાવો — બૉડી: `{scope: {type:"all"}                                                   | {type:"provider", providerId} | {type:"model", modelId}, trigger?}` |
| GET | `/api/evals` | બિલ્ટ-ઇન મૂલ્યાંકન સ્યુટ્સ + સૌથી તાજેતરના રન સૂચિબદ્ધ કરો |

| GET | `/api/evals/suites/[id]` | કસ્ટમ મૂલ્યાંકન સ્યુટ મેળવો |

## ACP (Agent Client Protocol) વ્યવસ્થાપન

ચાઇલ્ડ પ્રોસેસ તરીકે. આ એન્ડપોઇન્ટ્સ ACP એજન્ટની ઓળખ અને કસ્ટમ એજન્ટ
નોંધણીનું વ્યવસ્થાપન કરે છે.

| પદ્ધતિ | પાથ               | વર્ણન                                                                                                                                                          |
| ------ | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | ઇન્સ્ટોલેશન સ્થિતિ, વર્ઝન અને બાઇનરી સાથેના તમામ જાણીતા CLI એજન્ટ્સની (બિલ્ટ-ઇન + કસ્ટમ) યાદી બનાવે છે                                                         |
| POST   | `/api/acp/agents` | કસ્ટમ ACP એજન્ટ નોંધાવે છે અથવા કૅશ રિફ્રેશ કરે છે — બૉડી: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` અથવા `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | કસ્ટમ ACP એજન્ટ દૂર કરે છે — ક્વેરી પેરામ: `?id=<agentId>`                                                                                                     |

**પ્રતિસાદનું ઉદાહરણ** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**પ્રમાણીકરણ:** મેનેજમેન્ટ સેશન (ડૅશબોર્ડ `auth_token` કુકી) અથવા
મેનેજમેન્ટ-સ્કોપ્ડ API કીની જરૂર છે.

સંપૂર્ણ વિગતો માટે [ACP ફ્રેમવર્ક](../frameworks/ACP.md) જુઓ.

## CLI ટૂલ્સ મેનેજમેન્ટ

OmniRoute સાથે સંકલિત થતા CLI ટૂલ્સ (antigravity, commandCode,
devin-cli વગેરે) મેનેજ કરો. સંપૂર્ણ સૂચિ માટે [પ્રદાતા સંદર્ભ](./PROVIDER_REFERENCE.md) જુઓ.

| પદ્ધતિ | પાથ                                     | વર્ણન                                                                                                                                                                |
| ------ | --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/cli-tools/all-statuses`           | તમામ CLI ટૂલ્સની સ્થિતિ (ઇન્સ્ટોલ થયેલ, વર્ઝન, છેલ્લે જોવામાં આવ્યું)                                                                                                |
| GET    | `/api/cli-tools/status`                 | એક CLI ટૂલ માટે સ્થિતિની વિગતો (`?tool=` ક્વેરી)                                                                                                                     |
| POST   | `/api/cli-tools/apply`                  | ટૂલનું જનરેટ કરેલું કન્ફિગ લખો (`dryRun` પૂર્વાવલોકન આપે છે; કન્ટેનરાઇઝ્ડ હોય ત્યારે `422` + `containerEphemeralTarget`; `migration` લેગસી Codex YAMLની નોંધ આપે છે) |

## પ્રમાણીકરણ

ચાર પ્રકારના ક્રેડેન્શિયલ પરિવારો (ડૅશબોર્ડ સેશન, સ્થાનિક CLI ટોકન, `oma_live_…` ઍક્સેસ ટોકન, મેનેજમેન્ટ-સ્કોપ્ડ API કી) અને તેઓ ઇન્ફરન્સ કીઓથી કેવી રીતે અલગ પડે છે તે માટે [મેનેજમેન્ટ પ્રમાણીકરણ](../guides/MANAGEMENT-AUTH.md) જુઓ.

- ડૅશબોર્ડ રૂટ્સ (`/dashboard/*`) `auth_token` કૂકીનો ઉપયોગ કરે છે
- લૉગિન સાચવેલા પાસવર્ડ હૅશનો ઉપયોગ કરે છે; ફૉલબૅક તરીકે `INITIAL_PASSWORD` વપરાય છે
- `requireLogin` ને `/api/settings/require-login` દ્વારા ટૉગલ કરી શકાય છે
- `REQUIRE_API_KEY=true` હોય ત્યારે `/v1/*` રૂટ્સ માટે વૈકલ્પિક રીતે Bearer API કી જરૂરી છે
- આ સંદર્ભમાં "મેનેજમેન્ટ ટોકન" / "મેનેજમેન્ટ-સ્કોપ્ડ API કી"નો અર્થ એ માર્ગદર્શિકામાં દર્શાવેલા પરિવારોમાંથી એક છે — કોઈ અવ્યાખ્યાયિત વધારાનો ગુપ્ત પ્રકાર નહીં

> **મહત્ત્વપૂર્ણ ફેરફાર (v3.8.0)** — `/api/v1/agents/tasks/*` અને કૂલડાઉન મેનેજમેન્ટ એન્ડપૉઇન્ટ્સ માટે હવે **મેનેજમેન્ટ પ્રમાણીકરણ** (ડૅશબોર્ડ `auth_token` કૂકી અથવા મેનેજમેન્ટ-સ્કોપ્ડ API કી) જરૂરી છે. અગાઉ પ્રમાણીકરણ વિના આ રૂટ્સને કૉલ કરતા ક્લાયન્ટ્સને `401 Unauthorized` પ્રાપ્ત થશે. કમિટ `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) જુઓ.
