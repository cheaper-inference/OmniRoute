## npm Trusted Publishing (v3.8.51થી ડિફૉલ્ટ) — વિનંતી પર staged, fallback તરીકે direct

`npm-publish.yml` ડિફૉલ્ટ રૂપે **npm Trusted Publishing (OIDC)** દ્વારા પ્રકાશિત કરે છે:
`stage-npm` job (github-hosted) તે રન માટે GitHubના id-tokenનું ટૂંકા સમય માટે માન્ય npm
credentialમાં રૂપાંતર કરે છે — repository secretsમાં કોઈ લાંબા સમય માટે માન્ય npm token નહીં,
2FA prompt નહીં, અને provenance જોડાયેલું. હવે 2FAને બાયપાસ કરતા tokens નિવૃત્ત થઈ રહ્યા છે,
તેથી આ npm sanctionsનો bypass છે; તે v3.8.48 સુધી પ્રોજેક્ટ પાસે રહેલો સંપૂર્ણ
સ્વચાલિત પ્રવાહ પાછો લાવે છે, જ્યારે WS1.3ની ખાતરી જાળવે છે (લીક થયેલો token એકલો
પ્રકાશિત કરી શકતો નથી — token છે જ નહીં).

**એક વખતનું સેટઅપ (માલિક):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none). આ સેટઅપ ન થાય ત્યાં સુધી સ્વચાલિત પગલું `ENEEDAUTH` સાથે નિષ્ફળ જાય છે:
`publish_mode=staged` (નીચે) અથવા `direct` સાથે ફરી dispatch કરો.

### Staged publishing (વિનંતી પર — `publish_mode=staged`)

npm-publish workflow હવે સીધું પ્રકાશિત કરતું નથી: તે packed tarball
(`check:pack-boot`)ને boot કરે છે અને પછી `npm stage publish` ચલાવે છે — ચોક્કસ bytes
registry પર મૂકી દેવામાં આવે છે, **માલિક મંજૂરી આપે ત્યાં સુધી install કરી શકાય તેમ નથી**.
માનવીય 2FA gate હવે proof પછી ખસેડવામાં આવ્યો છે, પહેલાં નહીં.

**Workflow green થયા પછી માલિકનો પ્રવાહ:**

1. `npm stage list omniroute` — stage id શોધો (તે workflow summaryમાં પણ દર્શાવાય છે).
2. Staged bytesની ચકાસણી કરો (ભલામણ કરેલ): `npm stage download <id>`, પછી
   ડાઉનલોડ કરેલા tarballને અસ્થાયી prefixમાં install કરીને તેને boot કરો
   (`npm run check:pack-boot` CIમાં એ જ pack→install→boot verdict આપમેળે ચલાવે છે).
3. `npm stage approve <id>` — 2FA prompt જ publish છે. `npm stage reject <id>` તેને કાઢી નાખે છે.
4. Publish પછીનું net: post-publish verifier (v3.8.49 planનું WS1.4) clean containerમાં
   public registryમાંથી પ્રકાશિત version install કરીને તેને boot કરે છે.

**Emergency fallback:** `workflow_dispatch` સાથે `publish_mode=direct` legacy immediate
`npm publish` પાછું સક્રિય કરે છે (માત્ર staging પોતે ખોટી રીતે વર્તે ત્યારે વાપરો; કારણ નોંધો).

**એક વખતનું hardening (માલિક, npmjs.com):** `omniroute` માટે Trusted Publisherને
stage-only modeમાં configure કરો જેથી લીક થયેલો લાંબા સમય માટે માન્ય token ક્યાંયથી પણ
સીધું `npm publish` ન કરી શકે — CI માત્ર stage કરી શકે; માત્ર માલિકનું 2FA જ releases કરે.

**Broken-artifact playbook (અપરિવર્તિત):** ડિફૉલ્ટ reflex તરીકે
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` વાપરો (મિનિટોમાં, પાછું ફેરવી શકાય તેવું);
`npm unpublish` માત્ર 72h/no-dependents windowની અંદર અને ક્યારેય પ્રથમ પગલા તરીકે નહીં.
Docker: version tagને ક્યારેય ફરી લખશો નહીં — rollback એટલે `latest`ને છેલ્લે સારા digest તરફ
ફરી point કરવું.

**Docker Hub `latest` (દરેક stable SemVer publish પર ફરજિયાત):** `docker-publish` workflowએ
**બંને** `X.Y.Z` tag કરવા જોઈએ અને, જ્યારે `should-promote-latest.sh` આ સૌથી ઊંચું stable SemVer
છે એવું સ્વીકારે, ત્યારે સમાન digest સાથે `:latest` પણ tag કરવું જોઈએ. Job પછી: Hub `latest` digest
નવા SemVer digest સમાન હોવો જોઈએ અને `last_updated` આગળ વધેલું હોવું જોઈએ. Release notesમાં
માત્ર git પર રહેલા fixesની વાત હોય ત્યારે `:latest`ને જૂના build પર ન છોડો.
Compose quickstartsમાં `:latest` વપરાય છે; GitOpsએ `X.Y.Z` પર pin કરવાનું ચાલુ રાખવું જોઈએ.
[Docker release channels](../guides/DOCKER_GUIDE.md#release-channels) અને #10317 જુઓ.

**Docker Hub organization repository (`cheaperinference/omniroute`):** Docker Hub repositoryને
namespaces વચ્ચે ખસેડી શકતું નથી, તેથી `diegosouzapw/omniroute` પોતાનો pull history
અને દરેક release જાળવી રાખે છે, અને `docker-publish`નું `mirror-org-dockerhub` job
દરેક released version (અને promote કરવામાં આવે ત્યારે `:latest`)ને
`ghcr.io/cheaper-inference/omniroute`માંથી organization repositoryમાં copy કરે છે.
તેને `DOCKERHUB_ORG_USERNAME` / `DOCKERHUB_ORG_TOKEN` secretsની જરૂર છે; તે ન હોય તો
job "Docker Hub org mirror skipped" warning સાથે green રહે છે અને અન્ય registries સામાન્ય રીતે
publish થાય છે. ત્યાં પછી released version publish કરવા માટે **Actions → Mirror Docker image to the Docker Hub org → Run
workflow** ચલાવો, જેમાં `version=X.Y.Z` (અને સૌથી ઊંચા stable version માટે `promote_latest`) આપો:
તે existing images copy કરે છે, rebuild નહીં.

## હોટફિક્સ ફાસ્ટ-લેન (લેબલ `hotfix`)

`hotfix` લેબલ ધરાવતું PR ભારે CI મેટ્રિક્સ (9-શાર્ડ E2E, કવરેજ રેચેટ,
ક્વૉલિટી-ગેટ, ક્વૉલિટી-એક્સ્ટેન્ડેડ)ને સ્કિપ કરે છે અને ઝડપી, ઉચ્ચ-સિગ્નલ ગેટ્સ જાળવી રાખે છે: બિલ્ડ,
યૂનિટ શાર્ડ્સ, ઇન્ટિગ્રેશન, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
અને ટારબૉલ બૂટ-સ્મોક (`check:pack-boot`). લક્ષ્ય: લગભગ 33 મિનિટની બદલે ≤15 મિનિટમાં લીલું પરિણામ.

**પ્રવેશ નીતિ — ચારેય જરૂરી (Chromium/VS Code/Node ઇમર્જન્સી લેનના આધારે):**

1. **તીવ્રતા**: પ્રોડક્શન તૂટી ગયું છે — પ્રકાશિત આર્ટિફેક્ટ બૂટ સમયે ક્રેશ થાય છે / સુરક્ષા સુધારો છે / રિલીઝનો દરેક વપરાશકર્તા અસરગ્રસ્ત છે. "મહત્વપૂર્ણ" એટલે "તૂટેલું" નથી.
2. **સત્તા**: માત્ર રિપોઝિટરીનો માલિક `hotfix` લેબલ લાગુ કરે છે. લેબલ જ મંજૂરી છે — કેમ્પેઇન PR પર ક્યારેય સ્વ-સેવા ન કરવી.
3. **પુરાવો**: PR બૉડીમાં અગાઉના સંપૂર્ણ-લીલા ભારે રન (જે સ્કિપ થયેલી જોબ્સને ફરી માન્ય કરશે તે સ્યુટ) તેમજ ફિક્સના પોતાના નિષ્ફળ-પછી-પાસ થયેલા ટેસ્ટની લિંક હોવી જોઈએ.
4. **સ્કોપ**: માત્ર cherry-pick — ન્યૂનતમ ફિક્સ, કોઈ રિફેક્ટર નહીં, કોઈ સાથોસાથના ફેરફારો નહીં.

સ્કિપ થયેલી કવરેજ/રેચેટ સપાટી રિલીઝ બ્રાન્ચ પરના આગામી સંપૂર્ણ રન દ્વારા ફરી માન્ય કરવામાં આવે છે
(સતત release-green) — લેન WAITINGને સ્કિપ કરે છે, માન્યતાને નહીં.
માત્ર ટેસ્ટવાળા ડિફ્સ (બધી ફાઇલો `tests/` હેઠળ, `tests/e2e/` હેઠળ એકપણ નહીં) E2E
મેટ્રિક્સને આપમેળે સ્કિપ કરે છે, કોઈ લેબલ વિના.

### Build Layout

Repository ત્રણ અલગ output directories નો ઉપયોગ કરે છે — તેમને ક્યારેય એકબીજા સાથે ભેળવશો નહીં:

| Directory | Purpose                                                  | Tracked?        |
| --------- | -------------------------------------------------------- | --------------- |
| `src/`    | Application source (TypeScript / TSX)                    | Yes             |
| `.build/` | Build intermediates — `next build` output (`distDir`)    | No (gitignored) |
| `dist/`   | Shippable npm bundle — assembled by `assembleStandalone` | No (gitignored) |

> **Operator note:** remote VPS image directory હજુ પણ `/usr/lib/node_modules/omniroute/app/` છે.
> માત્ર **in-repo** build output બદલાયું (`app/` → `dist/`). Deploy skills
> `dist/` contents ને remote `app/` dir માં rsync કરે છે — VPS path માં ફેરફાર જરૂરી નથી.

**Single-build flow:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy માટે `npm run build` પછી અલગથી `npm run build:cli` ચલાવશો નહીં — એક જ command માં clean rebuild + sentinel કરતું `npm run build:release` વાપરો.

### ડ્રાય-રન (ફક્ત વાંચવા માટે, કોઈપણ સમયે સલામત)

```bash
npm run release:dry-run-lts-cut                       # the real cut: 3.9.0 from HEAD, previous tag v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # pin the source commit
```

`scripts/release/dry-run-lts-cut.mjs` કંઈપણ ચલાવતું નથી: તે git અને `gh` વાંચે છે અને સમગ્ર ક્રમ — પૂર્વશરતોને છાપે છે (સ્રોત ઉકેલો, સ્ત્રોત રીપોઝીટરીનો સંપૂર્ણ ઇતિહાસ — છે છીછરો ક્લોન `stable/v3` દબાણ કરી શકતો નથી, પ્રાપ્ત કરનાર બાજુ પ્રથમ કલમી પેરેન્ટ પર પેકને નકારી કાઢે છે, તેથી પહેલાના — ટેગને કાપી નાખો અથવા પહેલાના `git fetch --unshallow origin` ટેગમાંથી અસ્તિત્વમાં છે. `package.json` એ લક્ષ્ય સંસ્કરણ છે, `release-freeze` મુદ્દો ખુલ્લો છે, હાલની પ્રકાશન શાખા પર કોઈ ખુલ્લી `Release branch not green` સમસ્યા નથી — જે શાખા અસ્તિત્વમાં નથી `release/*` `?` અજ્ઞાત અહેવાલ આપે છે, ક્યારેય ગ્રીન — ઑમ્ની-ક્યૂ રિલીઝ PRs પર ઉતરતી નથી (G11: `config/merge-queue/config.json` માન્ય છે, તેનું `bases` પ્રકાશન શાખાનું સંચાલન કરે છે, `mode` `live` તેના નિયમો હજુ પણ અસ્તિત્વમાં છે) ડિલીશન અને ફોર્સ-પુશ, અને `stable/v3` અને `develop` હજી અસ્તિત્વમાં નથી), બે શાખા પગલાઓ, જે નિષ્ક્રિય-વર્કફ્લો ટ્રિગર કરે છે અને `if:` શરતો સાચી થાય છે (અને જે રિપોઝીટરી વેરીએબલ દ્વારા ગેટેડ રહે છે અથવા કેનોનિકલ રિપોઝીટરી પર પિન કરે છે), અપેક્ષિત ડિસ્ટ-ટેગ્સ (`latest` → 3.qz `next` અને `nightly` ) અને. `0` = `RESULT: READY` થી બહાર નીકળો , `1` = અવરોધિત કરવાની પૂર્વશરત નિષ્ફળ (`✗`), `2` = વપરાશ ભૂલ. `--advisory <id,...>` ચેકને છુપાવ્યા વિના ચેતવણી (`!`) પર ડાઉનગ્રેડ કરે છે.

વાસ્તવિક કટના ડ્રાય-રન ચલાવો જ્યારે 3.9.0 રીલીઝ ફ્રીઝ હજુ પણ ખુલ્લું છે — ટેગ પછી અને તબક્કો 12c ફ્રીઝ ઉપાડે તે પહેલાં શાખાઓ બનાવવામાં આવે છે.

```bash
npm install -g ./omniroute-*.tgz                          # preview install
```

રન `npm ci`, `npm run build:release`, `npm run check:pack-artifact`, ટારબોલને પેક કરે છે, `npm run check:pack-boot` (નકલી રહસ્યો, ક્ષણિક ડેટા ડીર) ચલાવે છે, ફરીથી પેક કરે છે અને નિષ્ફળ જાય છે સિવાય કે ડાયજેસ્ટ સમાન હોય, પછી `artifact-identity.json` રેકોર્ડ કરે છે (હેડ SHA, બેઝ SHA, lockfile હેશ, bqunde પોલિસી, બીલ્ડ પોલિસી, બિલ્ડ ABI, પ્લેટફોર્મ — `scripts/release/artifact-identity.mjs`) અને ટારબોલને અલગ કામમાં પ્રમાણિત કરે છે. પૂર્વાવલોકનનો પ્રચાર કરવાનો અર્થ એ છે કે તે ટારબોલ ઇન્સ્ટોલ કરવું: સ્ત્રોતમાંથી ક્યારેય પુનઃબીલ્ડ કરશો નહીં.

### કટ (3.9.0, GO પછી)

1. GO [LTS_GO_NO_GO માં નોંધાયેલ છે .md](./LTS_GO_NO_GO.md).
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` `RESULT: READY` પ્રિન્ટ કરે છે.
3. Create the branches on `origin` by hand with the commands the dry-run prints — the script refuses to push to `origin`. To reuse a reviewed develop commit, run the `--execute` rehearsal on the 3.9.0 tip against your fork first; it prints both SHAs, and the same commits can be pushed:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. પ્રથમ PR ઉતરતા પહેલા `stable/v3` અને `develop` (નિયમો + મર્જ કતાર) ને સુરક્ષિત કરો.
5. નિષ્ક્રિય વર્કફ્લો શાખાના અસ્તિત્વ દ્વારા સ્વિચ કરે છે: `forward-port.yml` ( `stable/v3` પર દબાણ કરો), `validate-stable-pr.yml` (PRs થી `stable/v3`) અને `nightly-v4-build.yml` ( `develop` બનાવે છે). ગો-લાઇવ પહેલાં, `secrets.FORWARD_PORT_TOKEN` રિપોઝીટરી સિક્રેટ સેટ કરો (જેથી CI ફોરવર્ડ-પોર્ટ PRs પર ચાલે છે); જ્યાં સુધી માલિક રીપોઝીટરી વેરીએબલ `vars.NIGHTLY_PUBLISH` ને `true` પર સેટ ન કરે અને npm ટ્રસ્ટેડ પબ્લિશિંગ `nightly-v4-build.yml` સ્વીકારે ત્યાં સુધી રાત્રિ પ્રકાશન બંધ રહે છે. ચેનલ રિઝોલ્યુશન `scripts/release/dist-tag.mjs` છે, તે જ રિઝોલ્વર `npm-publish.yml` વાપરે છે.
6. ચેનલો ચકાસો: `npm view omniroute dist-tags --json` `latest` = 3.9.0 બતાવે છે અને v4 પ્રકાશિત થાય ત્યાં સુધી `next` / `nightly` નહીં.
7. રોલબેક, જો જરૂરી હોય તો: `git push origin --delete refs/heads/stable/v3 refs/heads/develop` અને `npm dist-tag add omniroute@3.8.59 latest`.

## રોલબેક

જો રિલીઝમાં ગંભીર સમસ્યા હોય:

1. `gh release edit vX.Y.Z --prerelease` (તેને નવીનતમ રિલીઝ તરીકે ચિહ્નિત થતું અટકાવે છે)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (ફક્ત ત્યારે જ, જો વપરાશકર્તાઓએ હજી તેને અપનાવી ન હોય)
3. અથવા: `release/vX.Y.0` પર હોટફિક્સ → પેચ રિલીઝ `vX.Y.(Z+1)`
4. GitHub Discussions અને Discord પર તરત જ જાણ કરો

## કડક નિયમો

- ક્યારેય સીધું `main` પર કમિટ ન કરો
- `main` અથવા `release/*` બ્રાન્ચ પર ક્યારેય `git push --force` નો ઉપયોગ ન કરો
- ક્યારેય Husky હૂક્સને (`--no-verify`) સ્કિપ ન કરો
- ક્યારેય સિક્રેટ્સ, ઓળખપત્રો અથવા `.env` ફાઇલો કમિટ ન કરો
- કવરેજ ≥60/60/60/60 (સ્ટેટમેન્ટ્સ/લાઇન્સ/ફંક્શન્સ/બ્રાન્ચિસ) જળવાઈ રહેવું આવશ્યક છે
- `src/`, `open-sse/`, `electron/`, અથવા `bin/` માં પ્રોડક્શન કોડ બદલતી વખતે હંમેશાં ટેસ્ટ્સ ઉમેરો અથવા અપડેટ કરો
