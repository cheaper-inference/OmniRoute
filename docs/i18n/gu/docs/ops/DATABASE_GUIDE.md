**સ્ત્રોતો:**

- `src/lib/db/core.ts` — સિંગલટન + SCHEMA_SQL (17 મૂળભૂત કોષ્ટકો)
- `src/lib/db/migrationRunner.ts` — સંસ્કરણબદ્ધ માઇગ્રેશન્સ
- `src/lib/db/migrations/` — 167 સંસ્કરણબદ્ધ SQL ફાઇલો
- `src/lib/db/encryption.ts` — એન્ક્રિપ્શન સહાયક ફંક્શન્સ
- `src/lib/db/backup.ts` — બૅકઅપ નિકાસ/આયાત
- `src/lib/db/healthCheck.ts` — સ્વાસ્થ્ય નિદાન

## SQLite શા માટે?

OmniRoute એ PostgreSQL/MySQL કરતાં SQLite ને પસંદ કરવા પાછળ અનેક કારણો છે:

| પરિબળ              | SQLite                                 | PostgreSQL                             |
| ------------------ | -------------------------------------- | -------------------------------------- |
| **ડિપ્લોયમેન્ટ**   | એમ્બેડેડ — અલગ સર્વરની જરૂર નથી        | સર્વર સેટઅપ જરૂરી છે                   |
| **એન્ક્રિપ્શન**    | ઍપ્લિકેશન-સ્તરનું (AES-256-GCM)        | બિલ્ટ-ઇન TDE                           |
| **કાર્યક્ષમતા**    | નાના/મધ્યમ વર્કલોડ માટે વધુ ઝડપી       | ખૂબ મોટા સમકાલીન રાઇટ્સ માટે વધુ સારું |
| **સમવર્તિતા**      | WAL મોડ સમકાલીન રીડ્સની મંજૂરી આપે છે  | સંપૂર્ણ MVCC                           |
| **બૅકઅપ**          | એક જ ફાઇલની કૉપી                       | `pg_dump` અથવા ફાઇલસિસ્ટમ સ્નૅપશૉટ     |
| **ઉપયોગનો કિસ્સો** | પ્રતિ-વપરાશકર્તા ઇન્સ્ટોલેશન, એમ્બેડેડ | મલ્ટિ-ટેનન્ટ SaaS                      |

**એકલ-વપરાશકર્તા, એકલ-ઇન્સ્ટન્સ** ડિપ્લોયમેન્ટ્સ (OmniRoute નો મુખ્ય ઉપયોગનો કિસ્સો) માટે SQLite વધુ સરળ અને ઝડપી છે.

### WAL જર્નલિંગ

`core.ts` ડેટાબેઝને **WAL (Write-Ahead Logging) મોડ** સાથે ખોલે છે:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL રાઇટ્સ દરમિયાન **સમકાલીન રીડ્સ** કરવાની મંજૂરી આપે છે — આ ડૅશબોર્ડ માટે મહત્વપૂર્ણ છે, કારણ કે વિનંતીઓ રેકોર્ડ થઈ રહી હોય ત્યારે તે ક્વેરીઝ ચલાવે છે.

ડિફૉલ્ટ કૅશ કદ **65,536 KiB (64 MiB)** છે. SQLite નકારાત્મક
`cache_size` ને KiB માં અંદાજિત મહત્તમ મર્યાદા તરીકે અર્થઘટન કરે છે અને જરૂરિયાત મુજબ પેજિસ ફાળવે છે.
**સેટિંગ્સ > સિસ્ટમ અને સ્ટોરેજ > કૅશ કદ** **1 થી
1,000,000 KiB** સુધીના પૂર્ણાંક મૂલ્યો સ્વીકારે છે; સેટિંગ સાચવવાથી તે સક્રિય ડેટાબેઝ કનેક્શન પર લાગુ થાય છે,
અને OmniRoute સ્ટાર્ટઅપ વખતે સંગ્રહિત મૂલ્ય પુનઃસ્થાપિત કરે છે.

## ડેટાબેઝનું સ્થાન

SQLite ફાઇલ અહીં સંગ્રહિત થાય છે:

| OS      | પાથ                                                                    |
| ------- | ---------------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                          |
| macOS   | `~/.omniroute/storage.sqlite`                                          |
| Windows | `%USERPROFILE%\.omniroute\storage.sqlite`                              |
| Docker  | `/app/data/storage.sqlite` (`DATA_DIR` દ્વારા રૂપરેખાંકિત કરી શકાય છે) |

સહાયક ફાઇલો:

- `storage.sqlite-wal` — રાઇટ-અહેડ લૉગ
- `storage.sqlite-shm` — શેર્ડ મેમરી ફાઇલ
- `call_logs/` — વિનંતીના પેલોડની આર્ટિફેક્ટ્સ (જો સક્ષમ કરેલ હોય)

**સ્થાનને ઓવરરાઇડ કરો:**

```bash
DATA_DIR=/custom/path omniroute
```

## ડોમેન મોડ્યુલ આર્કિટેક્ચર

OmniRouteના ડેટાબેઝમાં `src/lib/db/` હેઠળ **110 ટોપ-લેવલ TypeScript મોડ્યુલ્સ** છે. દરેક ડોમેન મોડ્યુલ:

- એક અથવા વધુ ચોક્કસ ટેબલ્સની માલિકી ધરાવે છે
- ટાઇપ કરેલા CRUD ફંક્શન્સ એક્સપોર્ટ કરે છે
- અન્ય મોડ્યુલના ટેબલ્સને ક્યારેય સ્પર્શતું નથી
- DB ઍક્સેસ કરવા માટે `core.ts`માંથી `getDbInstance()`નો ઉપયોગ કરે છે

### મોડ્યુલ સીમાઓ

એક મુખ્ય આર્કિટેક્ચરલ નિયમ: **મોડ્યુલ્સ એકબીજાના ટેબલ્સને સીધા ઍક્સેસ કરતા નથી**. અન્ય મોડ્યુલના ડેટા સાથે કામ કરવા માટે, તે મોડ્યુલમાંથી ફંક્શન ઇમ્પોર્ટ કરો.

```ts
// ❌ ખોટું: અન્ય મોડ્યુલમાંથી સીધું SQL
db.prepare("SELECT * FROM provider_connections").all();

// ✅ સાચું: providers મોડ્યુલના ફંક્શનનો ઉપયોગ કરો
import { listProviders } from "@/lib/db/providers";
const providers = await listProviders();
```

આ નિયમ કોડ રિવ્યૂ દ્વારા લાગુ કરવામાં આવે છે — કોઈ સ્ટેટિક ચેક નથી, પરંતુ નિયમભંગને ફ્લૅગ કરવામાં આવે છે.

## સ્થળાંતર

OmniRoute વાપરે છે** વર્ઝનેડ, આડેધડ સ્થળાંતર** `src/lib/db/migrations/` માં દરેક સ્થળાંતર એક જ SQL ફાઇલ છે. બે નામકરણ ફોર્મેટ્સ સહઅસ્તિત્વ ધરાવે છે; `_omniroute_migrations` માં નોંધાયેલ સંસ્કરણ આંકડાકીય ઉપસર્ગ છે.

### સ્થળાંતર નામકરણ

| ફોર્મેટ                                         | ઉદાહરણ                               | માટે વપરાય છે                                                                                                                                                        |
| ----------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NNN_description.sql` (બરાબર 3 અંક)             | `241_seen_models.sql`                | જૂની શ્રેણી `001`–`241`. જ્યારે ટાઇમસ્ટેમ્પ ફોર્મેટ ઉતર્યું ત્યારે સ્થિર (`240` અને `241` તેના પહેલા મર્જ કરવામાં આવ્યા હતા): કોઈપણ નવી ફાઇલને ક્રમિક નંબર મળતો નથી. |
| `YYYYMMDDHHMMSS_description.sql` (14 અંકો, UTC) | `20261113120000_add_usage_index.sql` | 2026-11-13 થી સર્જાયેલ દરેક સ્થળાંતર.                                                                                                                                |

શા માટે બદલાવ: ક્રમિક સંખ્યાઓ સાથે, સમાંતર PRs એ જ આગળની સંખ્યા પસંદ કરી અને એક સિવાયના તમામને મર્જ કરતા પહેલા પુનઃનંબર કરવાની હતી. UTC ટાઇમસ્ટેમ્પ દરેક PR તેનું પોતાનું વર્ઝન આપે છે.

ટાઇમસ્ટેમ્પ ફોર્મેટ માટેના નિયમો ( `npm run check:migration-numbering` દ્વારા લાગુ કરાયેલ, `scripts/check/lib/migrationNaming.mjs` માં જનરેટર સાથે શેર કરેલ):

- ટાઇમસ્ટેમ્પ એ વાસ્તવિક UTC તારીખ અને સમય છે, જે `20261113000000` કરતા પહેલાનો નથી અને ભવિષ્યમાં 10 મિનિટથી વધુનો નથી.
- વર્ણન એક અક્ષર (`a-z`, `0-9`, શબ્દો વચ્ચે સિંગલ `_` ) થી શરૂ થતા લોઅરકેસ `snake_case` છે, વધુમાં વધુ 80 અક્ષરો.
- એક જ ટાઇમસ્ટેમ્પવાળી બે ફાઇલો ડુપ્લિકેટ છે.
- નો-ગેપ નિયમ ફક્ત જૂની શ્રેણીને લાગુ પડે છે: `001` થી `241` સુધીની દરેક સંખ્યા અસ્તિત્વમાં હોવી જોઈએ, સિવાય કે `026`, `055` અને `121`. `241` (અથવા કોઈપણ જૂની ફાઇલ) કાઢી નાખવાથી ગેટ નિષ્ફળ જાય છે. `001` અને `241` ક્યારેય `KNOWN_GAPS` મંજૂર સૂચિમાં ઉમેરી શકાતા નથી. ટાઇમસ્ટેમ્પ્ડ ફાઇલો ક્યારેય ગેપ બનાવતી નથી.
- `src/lib/db/migrations/` માં દરેક એન્ટ્રી માન્ય લોઅરકેસ `.sql` નામ સાથેની નિયમિત ફાઇલ હોવી આવશ્યક છે. ડિરેક્ટરી, સિમલિંક, `.SQL` અથવા `.sql.bak` ફાઇલ, છુપાયેલી ફાઇલ અથવા સ્પેસ સાથેનું નામ ગેટને નિષ્ફળ કરે છે, કારણ કે રનર તેને ચૂપચાપ છોડી દેશે અથવા બુટ વખતે ક્રેશ થઈ જશે.

**ઓર્ડર લાગુ કરો.** રનર ઉપસર્ગના આંકડાકીય મૂલ્ય દ્વારા વર્ગીકૃત કરે છે, ટેક્સ્ટ દ્વારા નહીં: જૂની `001`–`241` ફાઇલો પહેલા, પછી ટાઇમસ્ટેમ્પ ક્રમમાં ટાઇમસ્ટેમ્પ કરેલી ફાઇલો, પછી `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` સાથે નોંધાયેલ કોઈપણ નેમસ્પેસવાળી ડિરેક્ટરીઓ (આવૃત્તિઓ જેમ કે `ee-001`). બાકી સ્થળાંતર એ કોઈપણ ફાઇલ છે જેનું સંસ્કરણ `_omniroute_migrations` માં નથી, તેથી જૂની શાખામાંથી સ્થળાંતર જે નવી શાખા પછી મર્જ થાય છે તે હજી પણ અસ્તિત્વમાંના ડેટાબેઝ પર લાગુ થાય છે.

**ટાઇમસ્ટેમ્પ બનાવટ ક્રમ છે, મર્જ ઓર્ડર નથી.** જો તમારું સ્થળાંતર a સાથે સ્થળાંતર દ્વારા બનાવેલ ટેબલ અથવા કૉલમ પર આધાર રાખે છે** નવું** ટાઈમસ્ટેમ્પ (ઉદાહરણ તરીકે, બીજા PR માંથી એક કે જે પહેલા મર્જ થાય છે), એક તાજો ડેટાબેઝ તમારો પ્રથમ ચાલશે અને નિષ્ફળ જશે. જ્યારે તમારું PR હજી ખુલ્લું હોય, ત્યારે ફાઇલનું નામ `npm run db:new-migration` વડે પુનઃજનરેટ કરો જેથી તેને નવી ટાઇમસ્ટેમ્પ મળે, અથવા તેને સ્વતંત્ર બનાવો. `npm run test:migrations:fresh` દરેક સ્થાનાંતરણને ખાલી ડેટાબેઝમાં લાગુ કરે છે અને તેને પકડી લે છે.

### મર્જ કરેલ સ્થળાંતર ક્યારેય કાઢી નાખવામાં આવતું નથી અથવા નામ બદલાતું નથી

એકવાર સ્થળાંતર ફાઇલ પ્રકાશન શાખા અથવા `main` પર હોય, તે પહેલાથી જ હોમોલોગ અને ડેવલપર ડેટાબેસેસ પર, VPS ઇન્સ્ટોલ પર અને એન્ટરપ્રાઇઝ સિંકમાં ચાલે છે. ત્યારથી:

- **તેને ક્યારેય ડિલીટ કરશો નહીં.** જ્યારે અપગ્રેડ કરેલ ડેટાબેઝ તેને રાખે છે ત્યારે તાજા સ્થાપનો તેની સ્કીમા ગુમાવશે.
- **તેનું નામ ક્યારેય બદલશો નહીં.** `_omniroute_migrations` માંનું સંસ્કરણ હવે ફાઇલ સાથે મેળ ખાતું નથી, તેથી દરેક ડેટાબેઝ કે જેણે તેને પહેલેથી જ લાગુ કર્યું છે તે તેને ફરીથી ચલાવશે. નોન-ડિમ્પોટન્ટ SQL પછી ડેટા ડુપ્લિકેટ કરે છે અથવા બૂટ બંધ કરે છે.
- **અલગ સ્કીમા જોઈએ છે?** `npm run db:new-migration` સાથે નવું સ્થળાંતર બનાવો.

નામ બદલવું એ ફક્ત એવી ફાઇલ માટે સલામત છે કે જે હજી સુધી મર્જ કરવામાં આવી નથી, જે કિસ્સામાં ગેટના સંકેતોનો સંદર્ભ આપે છે. રીલીઝ ટેગ અહીં કંઈપણ બદલતું નથી: `release/v*` શાખામાં દરેક પુશ Docker `:next` ઇમેજ પ્રકાશિત કરે છે અને હોમોલોગ, VPS ઇન્સ્ટોલ અને એન્ટરપ્રાઇઝ સિંક પર ચાલે છે, તેથી કોઈપણ `vX.Y.Z` ટૅગ અસ્તિત્વમાં હોય તે પહેલાં મર્જ કરેલ સ્થળાંતર વાસ્તવિક ડેટાબેઝ પર ચાલે છે. દરવાજો બેઝ ફાઇલને દૂર કરવામાં નિષ્ફળ જાય છે, ટેગ કરેલ હોય કે ન હોય.

- **મર્જ કરેલ સ્થળાંતરને પાછું ફેરવી રહ્યું છે.** એક `git revert` જે ફાઇલને કાઢી નાખે છે તે ગેટને નિષ્ફળ કરે છે. ફાઇલને રાખો અને તેના સ્કીમાને નવા સ્થાનાંતરણમાં પૂર્વવત્ કરો: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` અને તેથી વધુ સાથે. અપગ્રેડ કરેલ અને તાજા ડેટાબેસેસ પછી સમાન સ્કીમા સાથે સમાપ્ત થાય છે.
- **એક સ્વીકૃત નામ બદલો: સુસંગતતા એન્ટ્રી અને સમાન સામગ્રી.** જો મર્જ કરેલી ફાઇલને ખસેડવી આવશ્યક છે (ઉદાહરણ તરીકે, બે મર્જ કરેલી ફાઇલો ટાઇમસ્ટેમ્પ શેર કરે છે અને રનર સંસ્કરણ અથડામણ સાથે અટકે છે), તો તેના SQL સ્પર્શ કર્યા વિના પછીનું નામ બદલો અને `src/lib/db/migrationRunner/constants.ts` માં `{ fromVersion, fromName, toVersion, toName }` ને `RENAMED_MIGRATION_COMPATIBILITY` માં ઉમેરો. ડેટાબેઝ કે જેઓ જૂના સંસ્કરણને લાગુ કરે છે તે ફાઇલને ફરીથી ચલાવવાને બદલે તેમની `_omniroute_migrations` પંક્તિ ખસેડવામાં આવે છે. દરવાજો આવા નામના બદલાવ વિશે ચેતવણી આપે છે અને હંમેશા તેના પર કમ્યુટેશન ચેક ચલાવે છે, ભલે ગમે તે નવો ટાઈમસ્ટેમ્પ હોય: તાજા ઈન્સ્ટોલ ફાઈલને તેની નવી સ્થિતિ પર લાગુ કરે છે, અપગ્રેડ કરેલા ડેટાબેસેસ નથી કરતા, તેથી જૂનાની નજીક એક નવો ટાઈમસ્ટેમ્પ પસંદ કરો. ગેટ નામ બદલવામાં નિષ્ફળ જાય છે જો સામગ્રી બદલાઈ હોય (સ્કીમા ફેરફાર હજુ પણ નવા સ્થાનાંતરણમાં જાય છે), અથવા જો એન્ટ્રીની લક્ષ્ય ફાઇલ ડિસ્ક પર ન હોય.
- **સમાન ટાઈમસ્ટેમ્પમાં ક્યારેય નામ બદલશો નહીં.** નામ બદલવું કે જે ટાઇમસ્ટેમ્પ રાખે છે અને ફક્ત વર્ણનમાં ફેરફાર કરે છે તે પ્રવેશ સાથે અથવા વગર, ગેટને નિષ્ફળ કરે છે. એન્ટ્રી સાથે જેની `toVersion` તેના `fromVersion` બરાબર છે, રનર જૂની `_omniroute_migrations` પંક્તિને કાઢી નાખે છે અને ફાઇલને પહેલાથી જ ચલાવતા દરેક ડેટાબેઝ પર ફરીથી લાગુ કરે છે. એન્ટ્રી વિના, રનર માત્ર વર્ઝનને ટ્રૅક કરે છે: તે તે ડેટાબેઝ પરની ફાઇલને છોડી દે છે (નવી સામગ્રી ત્યાં ક્યારેય ચાલતી નથી) અને દરેક બૂટ પર પુનઃક્રમાંકિત ભૂલ લોગ કરે છે. અન્ય ટાઇમસ્ટેમ્પ વત્તા સુસંગતતા એન્ટ્રીનો ઉપયોગ કરો અથવા નામ રાખો.
- **ગેટ ચકાસે છે કે નામ બદલાયેલ ફાઇલ ફરીથી ચાલતી નથી.** દરેક કવર કરેલા નામ માટે, ગેટ નવા ફાઇલ નામને `--must-not-apply` સાથે કમ્યુટેશન ચેકમાં પાસ કરે છે. ચેક અપગ્રેડ કરેલ ડેટાબેઝને વાસ્તવિક રનર સાથે બુટ કરે છે, અને જો રનર તે ફાઇલને ફરીથી લાગુ કરે છે (ઉદાહરણ તરીકે, કારણ કે એન્ટ્રીમાં ખોટું સંસ્કરણ અથવા નામ છે, અથવા કારણ કે ગેટના ટેક્સ્ટ પાર્સરે TypeScript થી અલગ રીતે `constants.ts` વાંચ્યું છે), તો ગેટ `migration renomeada rodaria de novo` સાથે નિષ્ફળ જાય છે અને તમને એન્ટ્રીના જૂના અને નવા સંસ્કરણો અને નામો તપાસવાનું કહે છે.

### ગેટ બેઝ સામે શું તપાસે છે

પુલ રિક્વેસ્ટ અને મર્જ-ક્યૂ રન પર, `npm run check:migration-numbering` ડિસ્ક પર `src/lib/db/migrations/` બેઝ બ્રાન્ચ પરની સમાન ડિરેક્ટરી સાથે સરખાવે છે. આધાર, આ ક્રમમાં છે: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` ચલ, અથવા, જ્યારે `GITHUB_EVENT_NAME` એ `pull_request`, `pull_request_target` અથવા `merge_group` છે, મર્જ કમિટનો પ્રથમ પિતૃ, ઇવેન્ટ પેલોડનો `merge_group.base_sha` અથવા `git merge-base HEAD origin/$GITHUB_BASE_REF`. પુલ વિનંતિ અથવા મર્જ-કતારમાં કોઈ ઉકેલી શકાય તેવા આધાર વિના દોડવામાં ગેટ નિષ્ફળ જાય છે. `--base` વગર CI બહાર તે `comparação com a base: pulada (sem --base)` છાપે છે અને આ નિયમોને છોડી દે છે.

`--base-latest-tag` `HEAD` નવા રીલીઝ ટેગ `--base` `vX.Y.Z` સેમેવર ક્રમમાં રીલીઝ-ગ્રીન (`scripts/quality/validate-release-green.mjs`) આ રીતે ગેટ ચલાવે છે, કારણ કે પુશ અને શેડ્યૂલ કરેલ રનમાં કોઈ પુલ રિક્વેસ્ટ બેઝ નથી અને મર્જ નવેસરથી CI રન વિના ઉતરી શકે છે. ઇતિહાસમાં કોઈ રીલીઝ ટેગ વિના દરવાજો નિષ્ફળ જાય છે; `git fetch --tags` ચલાવો ( CI માં, `actions/checkout` સાથે `fetch-depth: 0` ટૅગ્સ લાવે છે).

| આઉટ-ઓફ-ઓર્ડર, સંપાદિત અથવા નામ બદલાયેલી ફાઇલમાં `INSERT`, `UPDATE`, `DELETE` અથવા `REPLACE` સ્ટેટમેન્ટ હોય છે | **ચેતવણી** : કોમ્યુટેશન ચેક ડેટાની તુલના કરતું નથી, તેથી સમીક્ષા કરો કે જે ક્રમમાં અપગ્રેડ કરેલ અને તાજા ડેટાબેઝ લાગુ પડે છે તે પરિણામમાં ફેરફાર કરે છે કે કેમ.                                                                                                                                                                               |

કમ્યુટેશન ચેકનો એક રન આઉટ-ઓફ-ઓર્ડર, સંપાદિત અને નામ બદલાયેલ ફાઇલોને એકસાથે આવરી લે છે.

કમ્યુટેશન ચેક (`scripts/check/migration-commutation.ts`) વાસ્તવિક ઇન્સ્ટોલ પાથ સાથે બે અસ્થાયી ડેટાબેસેસ બનાવે છે: એક** અપગ્રેડ કર્યું** એક (બેઝ માઈગ્રેશન સાથે બુટ કરો, પછી પુલ રિક્વેસ્ટના સ્થળાંતર સાથે એ જ ફાઈલ પર ફરીથી બુટ કરો) અને a** તાજા** એક (પુલ વિનંતીના સ્થળાંતર સાથે એક બુટ). તે પરિણામી સ્કીમોની તુલના કરે છે: કોષ્ટકો અને કૉલમ્સ (કૉલમ ઑર્ડરને અવગણીને), UNIQUE / PRIMARY KEY અને FOREIGN KEY અવરોધો, દરેક કોષ્ટકનું સામાન્યકૃત `CREATE TABLE` ટેક્સ્ટ (જે CHECK અવરોધો, સંકલન, જનરેટ કરેલ કૉલમ્સ અને ઇન્ડેક્સ વિકલ્પોને આવરી લે છે), ટેબલ વ્યૂ વિકલ્પો. પંક્તિ ડેટાની સરખામણી કરવામાં આવતી નથી. જો તેઓ મેળ ખાય છે, તો ગેટ છાપે છે કે ફાઇલ ઓર્ડરની બહાર છે પરંતુ મુસાફરી કરે છે અને પસાર થાય છે. જો તેઓ અલગ હોય, તો દરવાજો તફાવત અને કેસ માટે સંકેત સાથે નિષ્ફળ જાય છે: આઉટ-ઓફ-ઓર્ડર ફાઇલ માટે, તેનું નામ `npm run db:new-migration` સાથે પુનઃજનરેટ કરો, જે સુરક્ષિત છે કારણ કે ફાઇલ હજુ સુધી મર્જ કરવામાં આવી નથી; સંપાદિત આધાર ફાઇલ માટે, આધાર સામગ્રી પુનઃસ્થાપિત કરો અને ફેરફારને નવા સ્થાનાંતરણમાં મૂકો; નામ બદલાયેલ ફાઇલ માટે, નામ બદલો અથવા અન્ય નવો ટાઇમસ્ટેમ્પ પસંદ કરો જ્યાં તે મુસાફરી કરે છે, અન્ય નામ સાથે સમાન ટાઇમસ્ટેમ્પ ક્યારેય નહીં. જો ચેક પોતે ચાલી શકતો નથી, તો દરવાજો CI માં નિષ્ફળ જાય છે અને માત્ર સ્થાનિક રીતે ચેતવણી આપે છે. સંપાદિત બેઝ ફાઈલ માટે, અપગ્રેડ કરેલ ડેટાબેઝ તે ફાઈલના આધારની સામગ્રી સાથે બનેલ છે, અને બીજું બુટ તેને છોડી દે છે કારણ કે તેનું સંસ્કરણ પહેલાથી જ રેકોર્ડ થયેલું છે. નામ બદલાયેલ ફાઇલ માટે, અપગ્રેડ કરેલ ડેટાબેઝ તેના જૂના નામ હેઠળ ફાઇલ સાથે બનેલ છે, અને બીજું બુટ તેની `_omniroute_migrations` પંક્તિને તેને ફરીથી ચલાવવાને બદલે સુસંગતતા એન્ટ્રી દ્વારા ખસેડે છે; ગેટ નવા નામને `--must-not-apply` સાથે પસાર કરે છે, તેથી જો બીજો બુટ તેને લાગુ કરે તો ચેક નિષ્ફળ જાય છે. જો પુલ રિક્વેસ્ટ માઈગ્રેશન અપગ્રેડ કરેલા પાથ પર લાગુ કરવામાં નિષ્ફળ જાય, એટલે કે, દરેક બેઝ માઈગ્રેશન પછી (ભલે તે નવા ઈન્સ્ટોલ પર પણ નિષ્ફળ જાય કે નહીં), ગેટ `migration do PR não aplica` રિપોર્ટ કરે છે અને તમને બેઝની વર્તમાન સ્કીમા સામે SQL ઠીક કરવા કહે છે; જો ફાઇલ પછીના ટાઇમસ્ટેમ્પ સાથે અન્ય પુલ વિનંતી સ્થળાંતર પર આધાર રાખે છે, તો તેનું નામ `npm run db:new-migration` સાથે પુનઃજનરેટ કરો.

સ્થાનિક રીતે સમાન સરખામણી ચલાવવા માટે, આધારને સ્પષ્ટ રીતે પાસ કરો, ઉદાહરણ તરીકે `npm run check:migration-numbering -- --base origin/<base-branch>`, અથવા `npm run check:migration-numbering -- --base-latest-tag` નવીનતમ પ્રકાશન સાથે સરખામણી કરવા માટે.

### ઓપન PR ના `NNN` સ્થળાંતર

સ્વીચ પહેલાં ખોલવામાં આવેલી પુલ વિનંતી હજુ પણ `242_add_widgets.sql` જેવી ક્રમિક ફાઇલ ધરાવી શકે છે. `241` ઉપરના જૂના નંબરો નકારવામાં આવ્યા છે, તેથી મર્જ કરતા પહેલા તેને કન્વર્ટ કરો:

1. **જનરેટર સાથે ફાઇલનું નામ બદલો, વર્ણન રાખીને.** નવું નામ મેળવવા માટે `npm run db:new-migration -- <same description>` ચલાવો, તેમાં SQL ખસેડો અને જૂની `NNN_` ફાઇલ કાઢી નાખો. વર્ણન એકસરખું રહેવું જોઈએ: નીચેની સુસંગતતા એન્ટ્રી તેના પર મેળ ખાય છે.
2. **જો સતત ડેટાબેઝ જૂનો નંબર ચલાવતો હોય તો સુસંગતતા એન્ટ્રી ઉમેરો.** જો કોઈપણ ડેટાબેઝ જે રાખવામાં આવે છે (હોમોલોગ, એક VPS, ફાળો આપનારનું પોતાનું ઇન્સ્ટોલ) `NNN_` ફાઇલ સાથે PR નું બિલ્ડ ચલાવે છે, તો `src/lib/db/migrationRunner/constants.ts` માં `{ fromVersion: "<NNN>", fromName: "<description>", toVersion: "<YYYYMMDDHHMMSS>", toName: "<description>" }` ને `RENAMED_MIGRATION_COMPATIBILITY` માં ઉમેરો. આ છે** `237` થી `241` માટે જરૂરી** : તે સ્લોટ્સ હવે પ્રમાણભૂત `237_usage_history_calculated_cost.sql`, `238_codex_connection_fences.sql`, `239_call_logs_pending_detail_index.sql`, `240_provider_node_custom_json_config.sql` અને `241_seen_models.sql` ધરાવે છે અને એન્ટ્રી વિના આવા ડેટાબેઝ કેનોનિકલ સ્થળાંતરને કાયમ માટે છોડી દે છે અને રૂપાંતરિતને ફરીથી ચલાવે છે. તે એવા સ્લોટ માટે પણ કામ કરે છે જે ખાલી રહે છે, જેમ કે `242`, જ્યારે ગંતવ્ય ટાઈમસ્ટેમ્પ હોય. જ્યારે શંકા હોય, ત્યારે એન્ટ્રી ઉમેરો. તમે તેને એરેમાં ક્યાં ઉમેરો છો તેનાથી કોઈ ફરક પડતો નથી: જ્યારે એન્ટ્રીના ટાર્ગેટ સ્લોટ હજુ પણ એવી પંક્તિ ધરાવે છે કે બીજી એન્ટ્રી ખસી જાય છે (ઉદાહરણ તરીકે `237` PR પંક્તિ ધરાવે છે જ્યારે જૂની `usage_history_calculated_cost` પંક્તિ `237` માં જવાની રાહ જુએ છે), દોડવીર તે પ્રવેશને સ્લોટ ખાલી ન થાય ત્યાં સુધી રાહ જોવા દે છે. માત્ર એક વાસ્તવિક સંઘર્ષ, જેમ કે એક પંક્તિ દ્વારા રાખવામાં આવેલ સ્લોટ નો એન્ટ્રી મૂવ, અથવા બે એન્ટ્રીઓ કે જે સ્લોટને સ્વેપ કરે છે, `Cannot reconcile ...` સાથે બુટ બંધ કરે છે.
3. **SQL નિર્બળ રાખો** (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT OR IGNORE`), કારણ કે રૂપાંતરિત સ્થળાંતર ડેટાબેઝને મળી શકે છે જ્યાં તેની સ્કીમા પહેલેથી જ અસ્તિત્વમાં છે.
4. **વર્ઝન-કીડ ખાસ કેસો ખસેડો.** જો PR એ તેના જૂના નંબર માટે `isSchemaAlreadyApplied()` (`src/lib/db/migrationRunner.ts`) અથવા `OPTIONAL_FTS5_MIGRATION_VERSIONS` (`src/lib/db/migrationRunner/constants.ts`) માં કેસ ઉમેર્યો હોય, તો નવા ટાઇમસ્ટેમ્પની કી બદલો.

`tests/unit/db/codex-fence-migration-rename.test.ts` એ નામ બદલાયેલ સ્થળાંતર માટેના પરીક્ષણનું કાર્યકારી ઉદાહરણ છે.

### સ્વીચ પહેલાં શાખાઓમાં બેકપોર્ટ

`YYYYMMDDHHMMSS_` ફાઇલને ક્યારેય ચેરી-પિક અથવા બેકપોર્ટ ન કરો કે જે સ્વીચની પહેલાની હોય (ઉદાહરણ તરીકે જૂની `release/v*` શાખા). ત્યાં દોડનાર ફાઇલના નામોને ટેક્સ્ટ તરીકે સૉર્ટ કરે છે, તેથી ટાઇમસ્ટેમ્પ્ડ ફાઇલ `201_` અને `202_` વચ્ચે તાજા ડેટાબેઝ પર ચાલશે, અને ત્યાંનો જૂનો ગેટ 14-અંકના ઉપસર્ગોને સમજી શકતો નથી. આવી શાખા પર, તે શાખાની પોતાની આગામી `NNN_` ફાઇલ તરીકે ફેરફાર લખો, idempotent, તેથી જ્યારે ટાઇમસ્ટેમ્પ્ડ સંસ્કરણ પછીથી આવે ત્યારે તે નો-ઓપ છે.

### સ્થળાંતર કેવી રીતે ચાલે છે

સ્ટાર્ટઅપ પર, `migrationRunner.ts`:

1. જો અસ્તિત્વમાં ન હોય તો `_omniroute_migrations` ટેબલ બનાવે છે
2. પહેલેથી-લાગુ કરેલ સ્થળાંતર માટે ક્વેરી
3. કોઈપણ નવા સ્થળાંતરને ક્રમમાં લાગુ કરે છે, દરેક વ્યવહારમાં
4. ટાઇમસ્ટેમ્પ સાથે દરેક લાગુ સ્થળાંતરને રેકોર્ડ કરે છે

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

### આઇડમ્પોટેન્સી

સ્થળાંતર હોવું જ જોઈએ** નિર્બળ** — તેમને બે વાર ચલાવવું એ નો-ઓપ હોવું જોઈએ:

```sql
-- 004_proxy_registry.sql
CREATE TABLE IF NOT EXISTS proxy_registry (
  id TEXT PRIMARY KEY,
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  ...
);
```

`IF NOT EXISTS`, `IF EXISTS`, અને `OR IGNORE` / `OR REPLACE` કલમોનો ઉદારતાપૂર્વક ઉપયોગ કરો.

### નવું સ્થળાંતર ઉમેરી રહ્યા છીએ

1. **જનરેટર સાથે ફાઇલ બનાવો** : `npm run db:new-migration -- <description>` (ઉદાહરણ તરીકે `npm run db:new-migration -- add combo priority`). તે વર્તમાન UTC સમય અને ટિપ્પણી હેડર સાથે `src/lib/db/migrations/<YYYYMMDDHHMMSS>_<description>.sql` લખે છે, જો તે ટાઇમસ્ટેમ્પ લેવામાં આવે તો એક સેકન્ડ આગળ વધે છે અને ફાઇલને ક્યારેય ઓવરરાઇટ કરતું નથી. હાથથી નંબર પસંદ કરશો નહીં.
2. **સલામત DDL ઉપયોગ કરો** : `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN`
3. **બેકફિલ ડેટા કાળજીપૂર્વક** : હાલની પંક્તિઓને હેન્ડલ કરવા માટે `UPDATE ... WHERE ...` ઉપયોગ કરો
4. **ઓર્ડર અને નામકરણ તપાસો** : `npm run test:migrations:fresh` (ખાલી ડેટાબેઝ પર તમામ સ્થળાંતર) અને `npm run check:migration-numbering`
5. **નકલ પર પરીક્ષણ કરો** : ઉત્પાદન પર ક્યારેય ચકાસાયેલ સ્થળાંતર ન ચલાવો

ઉદાહરણ:

```sql
-- 20261113120000_add_combo_priority.sql
ALTER TABLE combos ADD COLUMN priority INTEGER DEFAULT 100;
UPDATE combos SET priority = 100 WHERE priority IS NULL;
CREATE INDEX IF NOT EXISTS idx_combos_priority ON combos(priority);
```

> **પાછળ-અસંગત ફેરફારો** (દા.ત., કૉલમ છોડવી) મુશ્કેલ છે. એકવાર સ્થળાંતર લાગુ થઈ જાય પછી OmniRoute NOT ડાઉનગ્રેડ — ને સપોર્ટ કરે છે, સ્કીમા ફેરફાર કાયમી છે. તે મુજબ આયોજન કરો.

## સંગ્રહિત ડેટાનું એન્ક્રિપ્શન

સંવેદનશીલ ફીલ્ડ્સ (API કીઝ, OAuth ટોકન્સ, કનેક્શન સ્ટ્રિંગ્સ)ને સંગ્રહિત અવસ્થામાં **AES-256-GCM**નો ઉપયોગ કરીને એન્ક્રિપ્ટ કરવામાં આવે છે.

### તે કેવી રીતે કાર્ય કરે છે

```ts
// src/lib/db/encryption.ts (સરળીકૃત)
const key = deriveKeyFromPassphrase(passphrase, salt);
const iv = randomBytes(12);
const cipher = createCipheriv("aes-256-gcm", key, iv);
const encrypted = Buffer.concat([cipher.update(plaintext), cipher.final()]);
const authTag = cipher.getAuthTag();
return { encrypted, iv, authTag };
```

### તેનો ક્યાં ઉપયોગ થાય છે

- `provider_connections.api_key` — ઍપ્લિકેશન સ્તરે એન્ક્રિપ્ટ કરેલું
- `provider_connections.access_token`, `refresh_token`, `id_token` — ઍપ્લિકેશન સ્તરે એન્ક્રિપ્ટ કરેલા
- `namespace = "secrets"` ધરાવતી `key_value` એન્ટ્રીઓ — ઍપ્લિકેશન સ્તરે એન્ક્રિપ્ટ કરેલી
- `proxy_registry.auth` — ઍપ્લિકેશન સ્તરે એન્ક્રિપ્ટ કરેલું (જો હાજર હોય)

### એન્ક્રિપ્શન કી

એન્ક્રિપ્શન કી એક **પાસફ્રેઝ** (`STORAGE_ENCRYPTION_KEY` env var દ્વારા સેટ કરાયેલ) અને એક **સૉલ્ટ** (DBમાં સંગ્રહિત)માંથી મેળવવામાં આવે છે. ડેટાને ડિક્રિપ્ટ કરવા માટે બંને આવશ્યક છે.

```bash
# સુરક્ષિત પાસફ્રેઝ જનરેટ કરો
openssl rand -hex 32

# .envમાં સેટ કરો
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **અત્યંત મહત્વપૂર્ણ**: એન્ક્રિપ્શન કી ગુમાવવાનો અર્થ તમામ એન્ક્રિપ્ટેડ ડેટાની ઍક્સેસ ગુમાવવી થાય છે. **કીનો બૅકઅપ ડેટાબેઝથી અલગ રાખો**.

### શું એન્ક્રિપ્ટેડ નથી

કાર્યક્ષમતાના કારણોસર, નીચેની વસ્તુઓ પ્લેનટેક્સ્ટમાં સંગ્રહિત થાય છે:

- પ્રોવાઇડરના પ્રદર્શિત નામો
- મૉડલ વ્યાખ્યાઓ (પહેલેથી જ સાર્વજનિક)
- રાઉટિંગ નિયમો
- વપરાશ રેકોર્ડ્સ (કોઈ PII નથી)

## એન્ક્રિપ્શન સંબંધિત મર્યાદાઓ (v3.8.16+)

OmniRoute બે એન્ક્રિપ્શન યોજનાઓને પારદર્શક રીતે સંભાળવા માટે **`migrateLegacyEncryptedString()`** નો ઉપયોગ કરે છે:

- **લેગસી** (v3.5.0 પહેલાં): XOR-આધારિત "એન્ક્રિપ્શન" (વાસ્તવિક ક્રિપ્ટોગ્રાફી નથી)
- **વર્તમાન**: યોગ્ય IV અને ઑથેન્ટિકેશન ટૅગ સાથે AES-256-GCM

માઇગ્રેશન હેલ્પર લેગસી ફોર્મેટ શોધે છે અને પ્રથમ વાર વાંચતી વખતે નવી યોજના વડે ફરીથી એન્ક્રિપ્ટ કરે છે. આનો અર્થ એ છે કે તમે ઓળખપત્રો ગુમાવ્યા વિના જૂના ડેટાબેઝને અપગ્રેડ કરી શકો છો.

## રીડ કૅશ

વારંવાર વાંચવામાં આવતા ડેટા (મોડલ્સ, પ્રોવાઇડર્સ, સેટિંગ્સ) માટે, `readCache.ts` એક **ઇન-મેમરી કૅશ** પ્રદાન કરે છે:

```ts
// સ્ટાર્ટઅપ વખતે કૅશ થાય છે, લખાણ વખતે અમાન્ય થાય છે
```

સંબંધિત ટેબલમાં દરેક લખાણ વખતે કૅશ અમાન્ય કરવામાં આવે છે.

## બૅકઅપ અને પુનઃપ્રાપ્તિ

### મેન્યુઅલ બૅકઅપ

```bash
# સ્થાનિક બૅકઅપ બનાવવા માટે CLI નો ઉપયોગ કરો
omniroute backup create --name pre-migration

# અથવા API મારફતે
curl -X PUT http://localhost:20128/api/db-backups \

  -H "Content-Type: application/json" \
  -d '{"name": "pre-migration"}'
```

બૅકઅપ ફાઇલમાં આનો સમાવેશ થાય છે:

- તમામ DB ટેબલ્સ (JSON માં સિરિયલાઇઝ કરેલા)
- કૉલ લૉગ આર્ટિફૅક્ટ્સ (base64-એન્કોડેડ, વૈકલ્પિક)
- સેટિંગ્સ + સિક્રેટ્સ (એન્ક્રિપ્ટેડ)
- પ્લગઇન કન્ફિગરેશન

### પુનઃસ્થાપન

```bash
# CLI મારફતે

curl -X POST http://localhost:20128/api/db-backups/restore \
  -H "Authorization: Bearer $MANAGEMENT_KEY" \

```

> **ચેતવણી**: પુનઃસ્થાપન સમગ્ર DB ને ઓવરરાઇટ કરે છે. પહેલાં બધા ક્લાયન્ટ્સને બંધ કરો.

### સ્વચાલિત બૅકઅપ્સ

```bash
# CLI મારફતે સ્વચાલિત દૈનિક બૅકઅપ્સ સક્ષમ કરો
omniroute backup auto enable --cron "0 2 * * *" --retention 7
```

શેડ્યૂલ સર્વર-સાઇડ પર બૅકગ્રાઉન્ડ જૉબ દ્વારા ચલાવવામાં આવે છે, જે દર 30 સેકન્ડે

| વેરિએબલ                                     | ડિફૉલ્ટ | વર્ણન                                                                                                                |
| ------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000` | ms માં ટિક અંતરાલ (ન્યૂનતમ `5000`). મેળ ખાતી cron મિનિટની અંદર વિશ્વસનીય રીતે આવવા માટે તે 60 s કરતાં ઓછો હોવો જોઈએ. |

ચાલુ DB નો શૂન્ય-ડાઉનટાઇમ બૅકઅપ લેવા માટે:

આ SQLite ના ઑનલાઇન બૅકઅપ API નો ઉપયોગ કરે છે — OmniRoute ચાલી રહ્યું હોય ત્યારે ચલાવવા માટે સુરક્ષિત છે.

## પ્રદર્શન ટ્યુનિંગ

### WAL મોડ

WAL મૂળભૂત રીતે સક્રિય થયેલ છે. ઉચ્ચ-લેખન વર્કલોડ માટે, ધ્યાનમાં લો:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute `journal_size_limit` સેટ કરતું નથી. ચેકપોઇન્ટ WAL ફ્રેમ્સને મુખ્ય ફાઇલમાં ખસેડે છે, પરંતુ WAL ફાઇલ તેના સૌથી મોટા ફાળવેલ કદને રાખે છે. `OMNIROUTE_WAL_GUARD_MAX_MB` ગાર્ડ માત્ર ચેતવણી આપે છે અને `wal_checkpoint(RESTART)` ચલાવે છે; તે ડિસ્ક-સાઇઝ કેપ નથી.

### અનુક્રમણિકાઓ

પ્રદર્શન માટે મુખ્ય સૂચકાંકો (સ્થળાંતર દ્વારા સ્વતઃ-નિર્માણ):

- પ્રદાતા દ્વારા`idx_models_provider` — મોડેલ લુકઅપ્સ
- `idx_combo_targets_combo_id` — કોમ્બો લક્ષ્ય વિસ્તરણ
- `idx_usage_history_api_key_timestamp` — વપરાશ વિશ્લેષણ
- `idx_quota_snapshots_api_key_window` — ક્વોટા ટ્રેકિંગ
- `idx_call_logs_timestamp` — કૉલ લોગ પ્રશ્નો

નવી અનુક્રમણિકા ઉમેરવા માટે, સ્થળાંતર બનાવો:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### મેમરી-મેપ્ડ I/O

ખૂબ મોટા ડેટાબેસેસ માટે (> 10GB), મેમરી મેપિંગને SQLite pragma દ્વારા એડજસ્ટ કરી શકાય છે:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)

```

## હેલ્થ ચેક

`src/lib/db/healthCheck.ts` **DB-સ્તરના હેલ્થ ડાયગ્નોસ્ટિક્સ** પ્રદાન કરે છે:

બંને વર્બ્સ માટે પ્રમાણીકરણ જરૂરી છે (નહિતર `401`). `GET` માત્ર નિદાન કરે છે; `POST`
`autoRepair` સક્ષમ કરીને એ જ ચેક ચલાવે છે.

```bash
GET  /api/db/health   # નિદાન કરો
POST /api/db/health   # નિદાન કરો + સમારકામ કરો
```

પ્રતિસાદ એ `runDbHealthCheck()` દ્વારા ઉત્પન્ન થયેલું `DbHealthCheckResult` છે
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "ડોમેન બજેટ્સ એવા API કીઝને સંદર્ભિત કરતા હતા જે હવે અસ્તિત્વમાં નથી.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| ફીલ્ડ             | અર્થ                                                                                                                                           |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | જ્યારે `issues` ખાલી હોય ત્યારે `true`. `driver` તેને ક્યારેય પ્રભાવિત કરતું નથી.                                                              |
| `issues[].type`   | `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state` પૈકી એક.                                                       |
| `repairedCount`   | આ રન દરમિયાન સમારકામ કરાયેલી પંક્તિઓ; જ્યારે `autoRepair` false હોય ત્યારે હંમેશાં `0`.                                                        |
| `backupCreated`   | સમારકામ પહેલાં બૅકઅપ લેવામાં આવ્યું હતું કે નહીં.                                                                                              |
| `checkedAt`       | રન અને તેના દ્વારા લખવામાં આવતી કોઈપણ સમારકામ નોંધ દ્વારા વહેંચાયેલ ISO ટાઇમસ્ટૅમ્પ.                                                           |
| `driver.name`     | તપાસવામાં આવેલા ડેટાબેસને સેવા આપતો SQLite ડ્રાઇવર.                                                                                            |
| `driver.degraded` | જ્યારે લખાણો ડેટાબેસ ફાઇલ દ્વારા ટકાઉ રીતે બૅક ન થતા હોય ત્યારે `true` — `sql.js` WASM ફૉલબૅક (આખી ફાઇલનું પર્સિસ્ટન્સ) અથવા ઇન-મેમરી ડેટાબેસ. |

આ જ પેલોડ `omniroute_db_health_check` MCP ટૂલ દ્વારા પરત કરવામાં આવે છે.

કરપ્શન શોધવા માટે `PRAGMA integrity_check` ચલાવો:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# આ પ્રિન્ટ થવું જોઈએ: ok
```

જો તે `ok` સિવાય કંઈપણ પરત કરે, તો **તાત્કાલિક ડેટાબેસનો ઉપયોગ બંધ કરો** અને બૅકઅપમાંથી પુનઃસ્થાપિત કરો.

## આપત્તિ પુનઃપ્રાપ્તિ

### પરિસ્થિતિ 1: WAL ફાઇલ ખોવાઈ ગઈ

`-wal` ફાઇલ ઉપલબ્ધ નથી, પરંતુ `-shm` અને મુખ્ય DB અખંડિત છે:

```bash
# આગલી વખત ખોલવા પર આપમેળે પુનઃપ્રાપ્ત થાય છે
omniroute
```

જો SQLite આપમેળે પુનઃપ્રાપ્ત ન કરી શકે:

```bash
sqlite3 ~/.omniroute/storage.sqlite ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql
mv recovered.db ~/.omniroute/storage.sqlite
```

### પરિસ્થિતિ 2: મુખ્ય DB ફાઇલ દૂષિત થઈ ગઈ

બૅકઅપમાંથી પુનઃસ્થાપિત કરો:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` ફક્ત કાર્યરત સર્વરમાંથી સંપૂર્ણ `.tar.gz` આર્કાઇવ ડાઉનલોડ કરે છે
(`GET /api/db-backups/exportAll`, ઑપરેટર ઓળખપત્ર આવશ્યક છે); તે કંઈપણ પુનઃસ્થાપિત કરતું નથી.

### પરિસ્થિતિ 3: એન્ક્રિપ્શન કી ખોવાઈ ગઈ

કી વિના **પુનઃપ્રાપ્તિ શક્ય નથી**. એન્ક્રિપ્ટ કરેલાં ફીલ્ડ વાંચી શકાતાં નથી. નવા ઓળખપત્રો સાથે બધા પ્રદાતાઓને મૅન્યુઅલી ફરીથી ઉમેરો.

> **જોખમ ઘટાડવાનો ઉપાય**: એન્ક્રિપ્શન કીનો હંમેશાં અલગથી બૅકઅપ લો, આદર્શ રીતે પાસવર્ડ મેનેજર અથવા KMSમાં.

### પરિસ્થિતિ 4: ડિસ્ક ભરાઈ ગઈ

SQLite `SQLITE_FULL` ભૂલો આપશે. ડિસ્કમાં જગ્યા ખાલી કરો, ત્યારબાદ:

```bash
# જગ્યા ખાલી કરવા માટે WALને ચેકપોઇન્ટ કરો
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

## સામાન્ય કામગીરીઓ

### ટેબલનું નિરીક્ષણ કરો

```bash
sqlite3 ~/.omniroute/storage.sqlite "SELECT * FROM api_keys LIMIT 5;"
```

### બધા ટેબલમાં પંક્તિઓની ગણતરી કરો

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

### બધો ડેટા રીસેટ (સાફ) કરો

```bash
# પહેલાં OmniRoute બંધ કરો
omniroute stop

# DB ફાઇલ કાઢી નાખો
rm ~/.omniroute/storage.sqlite*

# ફરી શરૂ કરો (ખાલી DB ફરીથી બનાવવામાં આવશે)
omniroute
```

**પસંદગીયુક્ત** રીસેટ માટે (પ્રદાતાઓ રાખો, વપરાશ સાફ કરો):

```bash
DELETE FROM usage_history WHERE timestamp < datetime('now', '-30 day');
DELETE FROM call_logs WHERE timestamp < datetime('now', '-30 day');
DELETE FROM proxy_logs WHERE timestamp < datetime('now', '-30 day');
```

### એક ટેબલ નિકાસ કરો

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
.mode csv
.output api_keys.csv
SELECT * FROM api_keys;
EOF
```

## સમસ્યાનિવારણ

### "ડેટાબેઝ લૉક થયેલો છે"

અન્ય કોઈ પ્રક્રિયાએ રાઇટ લૉક પકડી રાખ્યો છે. આમાંથી કોઈ એક કરો:

- બીજી પ્રક્રિયા પૂર્ણ થાય ત્યાં સુધી રાહ જુઓ (`lsof | grep storage.sqlite` તપાસો)
- બીજી પ્રક્રિયાને સમાપ્ત કરો
- જો સમસ્યા ચાલુ રહે, તો OmniRoute ફરી શરૂ કરો

### "ફોરેન કી નિયંત્રણ નિષ્ફળ ગયું"

ડોમેન મોડ્યુલ રેફરેન્શિયલ ઇન્ટિગ્રિટીનું ઉલ્લંઘન કરી રહ્યું છે. આ તપાસો:

- આધારિત ટેબલમાં અનાથ પંક્તિઓ
- આગળ પ્રસારિત ન થયેલા કૅસ્કેડિંગ ડિલીટ
- ફોરેન કી બદલનાર તાજેતરનું માઇગ્રેશન

ઉલ્લંઘનો શોધવા માટે `PRAGMA foreign_key_check;` ચલાવો.

### "મેમરી સમાપ્ત થઈ ગઈ"

SQLiteનું મેમરી-મૅપ્ડ I/O, OSની મર્યાદા વટાવી રહ્યું છે. SQLite pragma દ્વારા તેને ઘટાડો:

```sql
PRAGMA mmap_size = 134217728;  -- 256MBને બદલે 128MB
```

અથવા તેને અક્ષમ કરો:

```sql
PRAGMA mmap_size = 0;
```

### "માઇગ્રેશન અધવચ્ચે નિષ્ફળ ગયું"

માઇગ્રેશન ટ્રાન્ઝેક્શનમાં ચાલ્યું હતું, તેથી તે રોલ બૅક થઈ ગયું હોવું જોઈએ. જો એવું ન થયું હોય:

1. **OmniRoute બંધ કરો** (વધુ પ્રયાસો અટકાવવા માટે)
2. `sqlite3` વડે **DBની સ્થિતિ તપાસો**
3. આંશિક માઇગ્રેશનને **મેન્યુઅલી સુધારો**
4. OmniRouteને **ફરીથી ચલાવો** (માઇગ્રેશનનો ફરી પ્રયાસ કરવામાં આવશે)

આને અટકાવવા માટે, માઇગ્રેશનનું હંમેશાં પહેલાં તેની નકલ પર પરીક્ષણ કરો.
