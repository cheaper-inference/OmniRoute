પુલ રિક્વેસ્ટ માટે સૌથી નાનો વિશ્વસનીય ડેવલપમેન્ટ લૂપ પસંદ કરવા આ માર્ગદર્શિકાનો ઉપયોગ કરો. આ નીચે લિંક કરેલા ક્ષેત્ર-વિશિષ્ટ આર્કિટેક્ચર અને સુરક્ષા દસ્તાવેજોને
બદલતું નથી; તે દરેક સામાન્ય ફેરફારના પ્રકારને તેના કરારો, કેન્દ્રિત તપાસો અને CI કવરેજ સાથે જોડે છે.

## દરેક ફેરફાર જે માર્ગને અનુસરે છે

1. **સંપાદન કરતાં પહેલાં બેઝ પસંદ કરો.** સૌથી ઉચ્ચ સક્રિય `release/v*` બ્રાન્ચ શોધો અને
   તેની ટિપ પરથી બ્રાન્ચ બનાવો. `main` ને નહીં, પરંતુ તે બ્રાન્ચને ટાર્ગેટ કરો. જો રિલીઝ ફ્રીઝ સક્રિય હોય, તો ફ્રીઝ કરેલી
   બ્રાન્ચને ટાર્ગેટ ન કરો; તેના બદલે
   [બ્રાન્ચિંગ અને રિલીઝ મોડેલ](BRANCHING_MODEL.md)માં વર્ણવેલા આગામી સક્રિય ચક્રનો ઉપયોગ કરો.
2. **કરારોનાં નામ આપો.** ફેરફારથી પ્રભાવિત થતા દરેક કૅટલૉગ, સ્કીમા, જનરેટ કરેલી આર્ટિફેક્ટ, જાહેર API અથવા વપરાશકર્તા
   ઇન્ટરફેસને ઓળખો. નીચેનું કોષ્ટક ન્યૂનતમ પ્રારંભિક સમૂહ આપે છે.
3. **કેન્દ્રિત ટેસ્ટ લખો અથવા અપડેટ કરો.** `src/`, `open-sse/`, `electron/` અથવા
   `bin/`માં પ્રોડક્શન ફેરફારો માટે એ જ PRમાં ઓટોમેટેડ ટેસ્ટ આવશ્યક છે. વર્તનને સાબિત કરતી સૌથી નાની ટેસ્ટ ફાઇલો
   ચલાવો અને પછી સૂચિબદ્ધ કેન્દ્રિત ગેટ્સ ચલાવો.
4. **CIને વ્યાપક મેટ્રિક્સ ચલાવવા દો.** સંપૂર્ણ યુનિટ શાર્ડ્સ, Vitest, કવરેજ રૅચેટ અને
   પ્રોડક્શન બિલ્ડ PR પર ચાલે છે. જ્યારે કેન્દ્રિત નિષ્ફળતા વધુ વ્યાપક અસર સૂચવે અથવા ફેરફાર
   અનેક સબસિસ્ટમ્સમાં ફેલાયેલો હોય ત્યારે જ સ્થાનિક રીતે વ્યાપક સ્યુટ ચલાવો.
5. **રિવ્યૂ પહેલાં સુસંગતતા સ્થાપિત કરો.** સક્રિય બેઝ ફેચ કરો, તેના નવા કમિટ્સ અને તેની સામેનો તમારો ડિફ
   તપાસો, ત્યારબાદ યોગદાનકર્તા વર્કફ્લો અનુસાર બેઝને રીબેઝ અથવા મર્જ કરો. જનરેટ કરેલી ફાઇલ
   અને કૅટલૉગના કૉન્ફ્લિક્ટ્સને તેમના સ્રોત પરથી ઉકેલો, તેમને ફરી જનરેટ કરો, કેન્દ્રિત લૂપ ફરી ચલાવો અને ખાતરી કરો કે
   PR હજુ પણ સક્રિય રિલીઝ બ્રાન્ચને ટાર્ગેટ કરે છે.
6. **પુરાવા નોંધો.** PR ટેમ્પલેટમાં ચલાવેલા કમાન્ડ્સ, ઉમેરેલી અથવા બદલેલી દરેક ટેસ્ટ ફાઇલ,
   માઇગ્રેશન્સ અથવા ફીચર ફ્લૅગ્સ અને હજુ બાકી રહેલું કોઈપણ માત્ર-CI વૅલિડેશન સૂચિબદ્ધ કરો.

## ફેરફારના પ્રકાર મુજબ ગોલ્ડન પાથ્સ

નીચેના કમાન્ડ્સ ન્યૂનતમ કેન્દ્રિત તપાસો છે; તમે બદલેલા વર્તનને સીધું આવરી લેતો ટેસ્ટ
છોડવાની આ પરવાનગી નથી.

### પ્રોવાઇડર

**કરારો**

- `src/shared/constants/providers/`માં પ્રોવાઇડરની વ્યાખ્યા અને
  `src/shared/constants/providers.ts`માં તેનું કમ્પોઝિશન.
- `open-sse/config/providerRegistry.ts` અથવા તેની એક્સ્ટ્રેક્ટ કરેલી રજિસ્ટ્રી ફાઇલોમાં મોડલ્સ અને ક્ષમતાઓ.
- લાગુ પડતું હોય ત્યારે એક્ઝિક્યુટર/ટ્રાન્સલેટર પસંદગી, OAuth અથવા API-key કન્ફિગરેશન, ડૅશબોર્ડ એસેટ્સ અને જનરેટ કરેલો
  પ્રોવાઇડર સંદર્ભ.
- જાહેર ક્રેડેન્શિયલ્સે `resolvePublicCred()`નો ઉપયોગ કરવો આવશ્યક છે; ભૂલ પ્રતિભાવોએ શેર કરેલા સૅનિટાઇઝ્ડ
  એરર હેલ્પર્સનો ઉપયોગ કરવો આવશ્યક છે. `docs/security/PUBLIC_CREDS.md` (git; `/docs`માં કમ્પાઇલ થતું નથી) અને
  [એરર સૅનિટાઇઝેશન](../security/ERROR_SANITIZATION.md) જુઓ.

**કેન્દ્રિત લૂપ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # જ્યારે કૅટલૉગ બદલાય; જનરેટ કરેલો ડિફ કમિટ કરો
npm run lint
```

પ્રભાવિત થયેલા દરેક રિક્વેસ્ટ ફેમિલીનું પણ પરીક્ષણ કરો: ચેટ, Responses, ઇમેજિસ, એમ્બેડિંગ્સ, ઑડિયો અથવા વિડિયો.
જનરેટ કરેલા કૅટલૉગ અને ગોલ્ડન ડિફ્સને કરારના ફેરફારો તરીકે રિવ્યૂ કરો; તેમને વિચાર્યા વિના સ્વીકારશો નહીં.

### રાઉટિંગ

**કરારો**

- `src/shared/constants/routingStrategies.ts`માં જાહેર સ્ટ્રેટેજી મૂલ્યો અને UI મેટાડેટા.
- `open-sse/services/combo.ts` અને `open-sse/services/combo/` હેઠળ ડિસ્પૅચ અને ક્રમ.
- કોમ્બો સ્કીમા, પર્સિસ્ટન્સ, રેઝિલિયન્સ સ્ટેટ, મોડલ ક્ષમતાઓ અને API/UI કન્ટ્રોલ્સ.
- વર્તન બદલાય ત્યારે [ઑટો-કોમ્બો એન્જિન](../routing/AUTO-COMBO.md) અને રેઝિલિયન્સ દસ્તાવેજીકરણ.

**કેન્દ્રિત લૂપ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # સ્ટ્રેટેજી અથવા ડિસ્પૅચમાં ફેરફારો
npm run check:known-symbols      # સ્ટ્રેટેજી રજિસ્ટ્રેશનમાં ફેરફારો
npm run lint
```

સ્થાનિક રીતે નિર્ધારિત પરિણામ આપતા મૉક કરેલા અપસ્ટ્રીમ ટેસ્ટ્સનો ઉપયોગ કરો. લાઇવ કોમ્બો સ્મોક ટેસ્ટ્સ માટે ક્રેડેન્શિયલ્સ જરૂરી છે અને તે
મેન્યુઅલ છે, CIના વિકલ્પ નથી.

### UI / UX

**કરારો**

- `src/app/` અને `src/shared/components/` હેઠળ Next.js રૂટ/પેજ અને શેર કરેલી કમ્પોનન્ટ સીમાઓ.
- API પ્રતિભાવના આકારો, લોડિંગ/ખાલી/ભૂલ સ્ટેટ્સ, કીબોર્ડ અને સ્ક્રીન-રીડર વર્તન,
  રિસ્પોન્સિવ લેઆઉટ, થીમિંગ અને લોકેલ વિસ્તરણ.
- `src/i18n/messages/en.json`માં અંગ્રેજી UI સ્રોત સ્ટ્રિંગ્સ; વપરાશકર્તાને દેખાતું નવું લખાણ હાર્ડ-કોડ કરશો નહીં.

**કેન્દ્રિત લૂપ**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ઇન્ટરૅક્શન અથવા વિઝ્યુઅલ ફેરફારો માટે ઍપ ચલાવો અને સાંકડા તેમજ પહોળા બંને વ્યૂપોર્ટ તપાસો. CI
પ્રોડક્શન બિલ્ડ અને વધુ વ્યાપક સ્યુટ્સ ચલાવે છે; વિઝ્યુઅલ વર્તન માટે હજી પણ ફેરફારને અનુરૂપ કેન્દ્રિત કમ્પોનન્ટ, Playwright
અથવા દસ્તાવેજીકૃત મેન્યુઅલ તપાસ જરૂરી છે.

### i18n

**કરારો**

- `src/i18n/messages/en.json` UI સ્રોત છે; `config/i18n.json` લોકેલ સ્રોત છે.
- CLI કૅટલૉગ્સ `bin/cli/locales/` હેઠળ અલગથી રહે છે.
- ICU પ્લેસહોલ્ડર્સ અને ટૅગ્સને બરાબર જાળવો. પ્રોડક્ટ/પ્રોવાઇડર/મોડલ નામો,
  પ્રોટોકૉલ અને હેડર નામો, કમાન્ડ્સ, કોડ/JSON આઇડેન્ટિફાયર્સ, URLs, એન્વાયરમેન્ટ વેરિએબલ્સ અથવા
  `OmniRoute`, `OAuth`, `MCP` અને `A2A` જેવા સુરક્ષિત શબ્દોનું ભાષાંતર કરશો નહીં. વર્તમાન સ્રોત સૂચિ
  `scripts/i18n/glossary/protected-terms.json` છે.

**કેન્દ્રિત લૂપ**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # જ્યારે CLI સ્ટ્રિંગ્સ/કૅટલૉગ્સ બદલાય
npm run lint
```

આ હાલની સિસ્ટમ માટેનું માર્ગદર્શન છે, તેના ટૂલિંગ અથવા કી મોડલને વિસ્તૃત કરવાનું આમંત્રણ નથી.
રિપ્લેસમેન્ટ સિસ્ટમ ડિઝાઇન થઈ રહી હોય ત્યારે i18n પૅચને ચોક્કસ અને મર્યાદિત રાખો. બાહ્ય સેવાઓને કૉલ કરતા ટ્રાન્સલેશન
કમાન્ડ્સ ચલાવશો નહીં, સિવાય કે કાર્યમાં સ્પષ્ટપણે જનરેટ કરેલા અનુવાદો જરૂરી હોય અને
તમે પરિણામી ડિફનું રિવ્યૂ કર્યું હોય.

### CLI

**કરારો**

- `bin/cli/` માંના જાહેર commands અને flags, જનરેટ કરેલા API commands, exit codes, stdout/stderr અને
  JSON output shapes, config/environment વર્તણૂક તથા પૅકેજ કરેલી files.
- CLI ની વપરાશકર્તાને દેખાતી strings એ CLI i18n layer નો ઉપયોગ કરવો આવશ્યક છે અને `en`/`pt-BR` catalogs સુસંગત રાખવા આવશ્યક છે.
- સમર્થિત runtime તરીકે Node અને પ્રકાશિત binary contract જાળવી રાખો.

**કેન્દ્રિત લૂપ**

```bash

npm run check:cli-i18n
npm run build:cli             # જનરેટ કરેલા/બંડલ કરેલા CLI ફેરફારો
npm run check:pack-policy     # package-surface ફેરફારો
npm run lint
```

જ્યારે વર્તણૂક parsing, files અથવા exit status પર આધાર રાખતી હોય ત્યારે કામચલાઉ data directory માં ચોક્કસ command નો ઉપયોગ કરો. CI વધુ વ્યાપક package artifact અને ecosystem checks કરે છે.

### Database

**કરારો**

- `src/lib/db/` હેઠળના domain modules; ચોક્કસ modules ને સીધા import કરો (જૂનું `localDb.ts` re-export layer દૂર કરવામાં આવ્યું હતું).
- `src/lib/db/migrations/` હેઠળ numbered, idempotent SQL migrations, transaction safety, upgrade
  વર્તણૂક, indexes અને schema થી પ્રભાવિત થતો દરેક caller.
- Routes અને handlers ક્યારેય સીધી raw SQL ચલાવતા નથી.

**કેન્દ્રિત લૂપ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migration ઉમેરતી વખતે નવી database અને અગાઉના schema માંથી upgrade—બંનેનું પરીક્ષણ કરો. Database tests એ handles બંધ કરવા અને cleanup દરમિયાન `resetDbInstance()` call કરવું આવશ્યક છે. શ્રેષ્ઠ-પ્રયાસવાળા Bun adapter path માં ફેરફાર થાય ત્યારે જ `npm run test:bun:db` ચલાવો; Node અધિકૃત રહે છે.

## શેર કરેલા મશીન માટે ડેવલપર સ્ક્રિપ્ટ્સ

અન્ય સેશન્સ સક્રિય હોય તેવા devbox પર સ્થાનિક લૂપને બે `scripts/dev/` સહાયકોમાં વ્યાખ્યાયિત કરવામાં આવ્યો છે:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # merge-base(HEAD, base)..HEADમાંથી ફાઇલો
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # ચોક્કસપણે આ ફાઇલો
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # અલગ કરેલું worktree, સમાંતર રીતે સુરક્ષિત
```

- `typecheck-touched.sh` ફક્ત સ્પર્શાયેલી `.ts/.tsx` ફાઇલોનું અસ્થાયી
  `tsconfig.touched.tmp.json` (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`) મારફતે 6 GB heap હેઠળ typecheck કરે છે, તેથી તે લોડ થયેલા મશીન પર OOM થતું
  સમગ્ર પ્રોજેક્ટનું `tsc -p tsconfig.json` બદલે છે. તે સ્પર્શાયેલી ફાઇલોમાંની ભૂલો ઉપરાંત એક સારાંશ
  લાઇન છાપે છે અને સ્પર્શાયેલી ફાઇલોમાં ભૂલો માટે `1`, જ્યારે માત્ર import કરેલી ફાઇલોમાં ભૂલો હોય
  અથવા tsc diagnostics વિના બંધ થઈ ગયું હોય ત્યારે `2` (`_artifacts/typecheck-touched/` હેઠળ તે
  દર્શાવેલી log વાંચો), અને કોઈ ભૂલ ન હોય ત્યારે `0` સાથે બહાર નીકળે છે. અસ્થાયી tsconfig હંમેશાં
  દૂર કરવામાં આવે છે; તેને ક્યારેય commit કરશો નહીં.
- `new-worktree.sh` `<git-common-dir>/omniroute-new-worktree.lock` પર સમકાલીન runs ને ક્રમબદ્ધ કરે છે
  (ડિફૉલ્ટ રૂપે 600 s સુધી રાહ જુએ છે અને દૃશ્યમાન સંદેશ બતાવે છે; override સ્ક્રિપ્ટના header માં
  દસ્તાવેજિત છે) અને worktree અસ્તિત્વમાં આવે તે પહેલાં `git worktree add` નિષ્ફળ જાય તો તેણે બનાવેલી
  branch ને પાછી ફેરવે છે, તેથી ફરી પ્રયાસ કરવા માટે મેન્યુઅલ `git branch -D` ની જરૂર પડતી નથી.
  Hard-link કરેલું `node_modules` અને `.husky/_` નું copy અપરિવર્તિત રહે છે.

## સ્થાનિક candidate લૂપ

Source tests એ સાબિત કરી શકતા નથી કે packaged artifact શરૂ થાય છે: packaging lists, pruned dependencies
અને native binaries ફક્ત tarball ને install કરીને શરૂ કર્યા પછી જ નિષ્ફળ થાય છે. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) એ RFC #8084 માંથી build-once / validate / promote flow ની સ્થાનિક બાજુ છે:
તે એક candidate build કરે છે, તે જ artifact ને validate કરે છે, directory renames વડે તેને promote કરે છે
અને promoted slot તેની health check માં નિષ્ફળ જાય ત્યારે તેને roll back કરે છે.

```bash
npm run dev:candidate -- run --dry-run --json  # યોજના છાપો, કંઈપણ બદલશો નહીં
npm run dev:candidate -- run                   # build + validate + promote, આપમેળે rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/માં install
npm run dev:candidate -- validate --id <id>    # ખાલી port પર boot, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current અને previous ને અદલાબદલી કરો
npm run dev:candidate -- run --from-tarball <file.tgz>  # અન્યત્ર (CIમાં) બનેલા tarball નો ફરી ઉપયોગ કરો
```

- **એક જ વાર build કરો.** `build` વર્તમાન tree ને pack કરે છે (તેને `dist/server.js` જોઈએ છે, તેથી
  પહેલાં `npm run build:release` ચલાવો) અથવા `--from-tarball` ને copy કરે છે, અને ત્યારબાદ tarball ને
  અલગ કરેલા npm prefix માં install કરે છે, કારણ કે tarball માં `node_modules` હોતું નથી. id ટૂંકું
  `HEAD` sha છે (tree માં સ્થાનિક ફેરફારો હોય ત્યારે `-dirty`) અથવા tarball માટે `tgz-<sha256>` છે.
  પહેલેથી build થયેલ clean id ને ફરી build કરવાને બદલે પુનઃઉપયોગમાં લેવામાં આવે છે; તેને ફરી build
  કરવા માટે `--force` આપો.
- **Source નહીં, package ને validate કરો.** `validate` નવા `DATA_DIR=<candidate>/data`, નકલી secrets
  સાથે installed CLI (`serve --port <free port>`) શરૂ કરે છે અને operator ના `OMNIROUTE_API_KEY`,
  `STORAGE_ENCRYPTION_KEY` તથા `INITIAL_PASSWORD` ને environment માંથી દૂર કરે છે, જેથી તે નવા install
  ની keyless loopback સ્થિતિ ચકાસે છે. તે `GET /api/health` દ્વારા 200 પરત મળે તેની રાહ જુએ છે,
  `GET /v1/models` દ્વારા 200 પરત મળવું જરૂરી બનાવે છે, process group ને રોકે છે અને tarball hash સાથે
  નિર્ણયને `validation.json` માં નોંધે છે.
- **તે જ artifact ને promote કરો.** `promote` તેના વર્તમાન tarball hash માટે સફળ validation ન ધરાવતા
  candidate ને નકારે છે. ડિફૉલ્ટ active slot `_artifacts/candidate/current` છે; `--target <dir>` એ જ
  filesystem પર બીજી directory પસંદ કરે છે અને તેનું previous slot `<dir>.previous` છે. દરેક rename
  atomic છે અને પ્રક્રિયાની વચ્ચે નિષ્ફળતા આવે તો પહેલેથી થયેલા renames ને પાછા ફેરવવામાં આવે છે.
- **Roll back કરો.** `run` promoted slot ને ફરી validate કરે છે અને તે check નિષ્ફળ જાય ત્યારે
  `current` તથા `previous` ને પાછાં અદલાબદલી કરે છે. પ્રથમ validation માં નિષ્ફળ જતો candidate ક્યારેય
  promote થતો નથી.

બધું gitignored `_artifacts/candidate/` હેઠળ લખવામાં આવે છે; હાલના OmniRoute installation અને તેની
data directory ને ક્યારેય સ્પર્શવામાં આવતાં નથી. Promoted CLI
`_artifacts/candidate/current/prefix/bin/omniroute` છે; તેનો ઉપયોગ કરતી વખતે તેને તમારા પોતાના
`DATA_DIR` સાથે શરૂ કરો. Exit codes: સફળતા માટે `0`, નિષ્ફળ validation અથવા promotion માટે `1`, અને
usage error અથવા ગુમ થયેલ build માટે `2`.

| ઓટોમેશન વર્તન સાબિત ન કરી શકે ત્યારે જ મેન્યુઅલ ઇન્ટરેક્શન/લાઇવ તપાસો | વર્કફ્લો દ્વારા ગોઠવેલ ક્રોસ-જૉબ ઇન્ટિગ્રેશન અને પ્લેટફોર્મ તપાસો     |

સફળ કેન્દ્રિત લૂપ એ બદલાયેલા કોન્ટ્રાક્ટ વિશેનો પુરાવો છે, અસંબંધિત CI તપાસો
સફળ થશે તેનો પુરાવો નથી. તેનાથી વિપરીત, દરેક સ્થાનિક ફેરફારને સંપૂર્ણ રિપોઝિટરી મેટ્રિક્સ માટે રાહ જોવાની ફરજ પાડશો નહીં.

## સમાધાન ચેકલિસ્ટ

સમીક્ષાની વિનંતી કરતાં પહેલાં:

- ખાતરી કરો કે PR બેઝ હજી પણ સર્વોચ્ચ સક્રિય `release/v*` બ્રાન્ચ છે.
- તે બેઝને ફેચ કરો અને તમે બ્રાન્ચ બનાવ્યા પછી ઉમેરાયેલા કમિટ્સની સમીક્ષા કરો.
- આકસ્મિક અથવા જનરેટ થયેલા અનાવશ્યક ફેરફારો માટે `git diff <active-base>...HEAD` ની સમીક્ષા કરો.
- સ્રોતને અપડેટ કરીને અને આઉટપુટ ફરીથી જનરેટ કરીને કેટલોગ તથા જનરેટ થયેલા દસ્તાવેજોના કૉન્ફ્લિક્ટ્સ ઉકેલો.
- સમાધાન પછી PR વર્ણનમાં સૂચિબદ્ધ દરેક કેન્દ્રિત પરીક્ષણ/ગેટ ફરીથી ચલાવો.
- બદલાયેલા બેઝ સાથે મેળ બેસાડવા માત્ર માટે અસર્શન્સ ક્યારેય નબળા ન કરો અથવા જરૂરી પરીક્ષણો દૂર ન કરો.

રિલીઝ-ફ્રીઝ અને રિટાર્ગેટિંગ નિયમો માટે,
[બ્રાન્ચિંગ અને રિલીઝ મોડેલ](BRANCHING_MODEL.md) નો ઉપયોગ કરો. સંપૂર્ણ CI સૂચિ માટે,
[ગુણવત્તા ગેટ્સ સંદર્ભ](../architecture/QUALITY_GATES.md) નો ઉપયોગ કરો.
