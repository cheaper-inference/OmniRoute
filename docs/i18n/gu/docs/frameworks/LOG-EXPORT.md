OmniRoute કૉલ લૉગ્સનું બાહ્ય એનાલિટિક્સ સ્ટોરમાં સતત, વૃદ્ધિશીલ નિકાસ.

લૉગ્સ ડૅશબોર્ડ ટૅબ વિનંતીઓનો ઇતિહાસ SQLite (`call_logs`)માં રાખે છે, જે
રોટેશન અને રિટેન્શન દ્વારા મર્યાદિત હોય છે. લૉગ નિકાસ એ જ રેકોર્ડ સમૂહને નિર્ધારિત સમયે બહાર મોકલે છે, જેથી તે
સ્થાનિક ડેટાબેઝ કરતાં વધુ સમય સુધી જળવાઈ શકે અને અન્ય ડેટા સાથે જોડાઈ શકે. BigQuery પ્રથમ ગંતવ્ય છે;
પાઇપલાઇન એક રજિસ્ટ્રી છે, તેથી વધુ ગંતવ્યો ઉમેરવા પૂરક ફેરફાર છે.

## 1. તે કેવી રીતે કાર્ય કરે છે

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **સમયપત્રક** — એક `JobRegistry` cron જૉબ, `log_export`, જેનું ડિફૉલ્ટ `0 * * * *` (દર કલાકે,
  UTC) છે. તે `src/lib/initCloudSync.ts`માં નોંધાયેલું છે; `OMNIROUTE_LOG_EXPORT_CRON`થી તેને બદલી શકાય છે.
  દરેક ટિક પર દરેક **સક્રિય** ગંતવ્યનો બાકી ડેટા ક્રમશઃ નિકાસ થાય છે.
- **કર્સર** — SQLiteનું ગર્ભિત `call_logs.rowid`, જે દરેક ગંતવ્ય માટે
  `log_export_destinations.cursor_row_id`માં સંગ્રહિત થાય છે. `timestamp`ને જાણીજોઈને કર્સર બનાવવામાં આવ્યું નથી: કૉલ કરનારાઓ
  પોતાનું મૂલ્ય આપી શકે છે, તેથી ધીમી વિનંતી તેના કરતાં પછી શરૂ થયેલી ઝડપી વિનંતી બાદ લખાઈ શકે છે,
  અને ટાઇમસ્ટૅમ્પ કર્સર તેને છોડી દેશે.
- **બૅચિંગ** — દરેક વિનંતીમાં `batch_size` પંક્તિઓ (ડિફૉલ્ટ 500), દરેક રનમાં `max_rows_per_run` પંક્તિઓ
  (ડિફૉલ્ટ 10000), જેથી મોટો બૅકલૉગ એક ટિકને અવરોધવાને બદલે ઘણી ટિકમાં નિકાસ થાય.
- **વિતરણ** — `send()` પૂર્ણ થાય ત્યાર પછી જ કર્સર આગળ વધે છે. નિષ્ફળ બૅચ કર્સરને
  તેની મૂળ જગ્યાએ જ રાખે છે, તેથી આગામી રનમાં એ જ પંક્તિઓ માટે ફરી પ્રયાસ થાય છે. ખાતરી
  ઓછામાં ઓછું એકવાર વિતરણ અને ગંતવ્ય-પક્ષે ડુપ્લિકેટ દૂર કરવાની છે, સાચા અર્થમાં ચોક્કસ એકવાર વિતરણની નહીં: BigQuery દરેક
  પંક્તિ માટે કૉલ-લૉગ idને કી તરીકે વાપરે છે, જેને તે પોતાની ડુપ્લિકેટ દૂર કરવાની સમયમર્યાદામાં શ્રેષ્ઠ પ્રયાસના ધોરણે માન્ય રાખે છે.
- **ઓવરલૅપ સુરક્ષા** — cron ટિક અને `POST .../run` એકસાથે શરૂ થઈ શકે છે. જે ગંતવ્યમાંથી
  નિકાસ પહેલેથી ચાલી રહી હોય તેને બે વાર નિકાસ કરવાને બદલે છોડી દેવામાં આવે છે (રનના પરિણામમાં `skipped: true`),
  જેથી સમવર્તી રન બૅચને ફરી મોકલી કે કર્સરને પાછળ લખી ન શકે.
- **પર્જ પછી પુનઃપ્રાપ્તિ** — જો `cursor_row_id`, `MAX(rowid)` કરતાં વધી જાય (આખું ટેબલ
  પર્જ થયું હોય અને rowid ફરીથી શરૂ થયા હોય), તો રનર કાયમ માટે નવા રેકોર્ડ જોવાનું ચૂકી જવાને બદલે 0 પર પાછો ફરે છે.

### અલગ પાડેલો રનર અને મર્યાદાઓ

Node પર દરેક ગંતવ્ય રન એક અલગ, અલ્પજીવી OS ચાઇલ્ડ પ્રોસેસ શરૂ કરે છે (IPC સાથે `child_process`,
`worker_threads` નહીં). બૉડી વાંચન, પેલોડ JSON પાર્સિંગ/સીરિયલાઇઝેશન, ગંતવ્યનું
`prepare()` અને ગંતવ્ય નેટવર્ક I/O બધું ત્યાં ચાલે છે, સર્વરના ઇવેન્ટ લૂપ પર નહીં.
માત્ર કન્ફિગરેશન અને નાના પ્રગતિ સંદેશાઓ IPC મારફતે પસાર થાય છે; નિકાસ કરેલા રેકોર્ડ ક્યારેય
સર્વર પર પાછા આવતા નથી. cron જૉબ અને તાત્કાલિક ચલાવવાનો રૂટ સમાન જાહેર પરિણામ અને ઓવરલૅપ સુરક્ષા જાળવી રાખે છે.

ચાઇલ્ડ, `node:sqlite` વાપરીને સર્વરના નિર્ધારિત `DATA_DIR/storage.sqlite`ને ફક્ત વાંચવા માટે ખોલે છે,
અને તેમાં `busy_timeout=5000` તથા `query_only=ON` હોય છે. તે કોઈ DB સિંગલટન ઇમ્પોર્ટ કરતું નથી અને કોઈ
માઇગ્રેશન, બૅકઅપ કે SQLite અપડેટ કરતું નથી. ગુમ/દૂષિત આર્ટિફેક્ટનું હિસાબ-સંચાલન (દૂષિત-આર્ટિફેક્ટ
UPDATE સહિત) માત્ર ડૅશબોર્ડની વિગત દર્શાવતી પ્રક્રિયામાં જ રહે છે. બંને પ્રક્રિયાઓ એક શુદ્ધ
વિગત રિઝૉલ્વર વાપરે છે; નિકાસ અસિંક્રોનસ ફાઇલસિસ્ટમ વાંચન અને સમાન આર્ટિફેક્ટ → લેગસી
ઇનલાઇન → લેગસી ડિસ્ક → કશું નહીં એવા નિરાકરણ ક્રમનો ઉપયોગ કરે છે. ચાઇલ્ડ પોતાનું રીડર ખોલે ત્યારે રન મહત્તમ ઇન્સર્શન rowidનો સ્નૅપશૉટ લે છે;
તેના પછીના ઇન્સર્ટ આગામી રન સુધી રાહ જુએ છે. આ ઇન્સર્શનની
સીમા છે, લાંબા સમય સુધી ચાલતું SQLite ટ્રાન્ઝૅક્શન નહીં: નેટવર્કની રાહ જોતી વખતે WAL રાઇટર્સ અને ચેકપૉઇન્ટ્સ મુક્ત રહે છે.
આ સીમા હાલની પંક્તિઓના અપડેટ/ડિલીટને સ્થગિત કરતી નથી.

દરેક સ્વીકારેલી બૅચ પછી ચાઇલ્ડ સ્વીકૃતિની રાહ જુએ છે. સર્વર પહેલાં
`advanceLogExportCursor` વડે કર્સર સંગ્રહિત કરે છે, પછી `ack` મોકલે છે; તે પહેલાં કોઈ આગામી બૅચ શરૂ થતી નથી.
મોકલવામાં નિષ્ફળતા, ક્રૅશ અથવા ટાઇમઆઉટ થાય તો તે બૅચને આગળ વધાર્યા વિના નિષ્ફળતા નોંધાય છે. અગાઉ
સ્વીકૃત થયેલી બૅચ કમિટ થયેલી રહે છે; વધુમાં વધુ એક સ્વીકૃતિ ન મળેલી બૅચ ફરી મોકલાઈ શકે છે.
`done` અને ચાઇલ્ડના સ્વચ્છ એક્ઝિટ પછી જ સફળતા નોંધાય છે. નિષ્ફળતા આવે ત્યારે ચાઇલ્ડને
SIGTERM વડે બંધ કરવામાં આવે છે, 500 ms પછી SIGKILL સુધી કાર્યવાહી વધારવામાં આવે છે, અને રનર પ્રોસેસ બંધ થવાની રાહ જુએ છે.

| એન્વાયર્નમેન્ટ વેરિએબલ                        | ડિફૉલ્ટ | હેતુ                                           |
| --------------------------------------------- | ------- | ---------------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000  | દરેક ગંતવ્ય માટે વાસ્તવિક વીતેલા સમયની મર્યાદા |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024    | ચાઇલ્ડની V8 old-space મર્યાદા MBમાં            |

અમાન્ય/બિન-ધન/બિન-પૂર્ણાંક મૂલ્યો માટે ડિફૉલ્ટ વપરાય છે. હીપ સેટિંગ કુલ
RSS મર્યાદા નથી; ખૂબ મોટી બૅચ હજી પણ ચાઇલ્ડની મેમરી પૂરી કરી શકે છે અને રનને સુરક્ષિત રીતે નિષ્ફળ બનાવી શકે છે.
1024 MBનું ડિફૉલ્ટ, બૉડી સક્રિય હોય ત્યારે 512 KiB આર્ટિફેક્ટની ડિફૉલ્ટ 500-પંક્તિ બૅચ માટે
વધારાની જગ્યા રાખે છે, જેમાં BigQueryનું બાઇટ-ચંક્સમાં થતું JSON સીરિયલાઇઝેશન પણ સામેલ છે. તે
બૉડી ધરાવતી 10000-પંક્તિ બૅચને સુરક્ષિત બનાવતું નથી. V8 હીપ ખૂટી જવાથી પગલાં લઈ શકાય તેવી નિષ્ફળતા નોંધાય છે: બૅચનું
કદ ઘટાડો અથવા `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` વધારો; કર્સર છેલ્લી
સ્વીકૃત બૅચ પર જ રહે છે. ઐતિહાસિક ઇનલાઇન/ડિસ્ક બૉડી આધુનિક આર્ટિફેક્ટ મર્યાદા હેઠળ આવતી નથી.
સંચાલકોએ RSS માટે અલગથી સંસાધનો ફાળવવા જોઈએ, ખાસ કરીને મર્યાદિત મેમરી ધરાવતા કન્ટેનરમાં.

ચાઇલ્ડને ફક્ત રિઝોલ્વ કરાયેલ `DATA_DIR`, `NODE_ENV`, સ્પષ્ટ રીતે આપેલ `TZ` (લેગસી ફાઇલનામના
સ્થાનિક-સમય રિઝોલ્યુશન માટે), હાજર હોય ત્યારે `ELECTRON_RUN_AS_NODE`, અને નીચેના આઉટબાઉન્ડ ઇનપુટ્સ વારસામાં મળે છે:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (અને તેમનાં લોઅરકેસ સ્વરૂપો),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
વૈશ્વિક Undici ડિસ્પેચર સર્વરના ફક્ત એન્વાયર્નમેન્ટ પર આધારિત પ્રોક્સી રિઝોલ્યુશન અને સ્થાનિક-હોસ્ટ
બાયપાસ નિયમોનો ઉપયોગ કરે છે, જેમાં `NO_PROXY` પણ સામેલ છે; તે `proxyFetch.ts` કે તેના DB/ફીચર ફ્લેગ્સ ઇમ્પોર્ટ કરતું નથી.
ફોરવર્ડ કરાયેલા આઉટપુટ અને નોંધાયેલી ભૂલોમાંથી પ્રોક્સી ઓળખપત્રો છુપાવવામાં આવે છે. ગંતવ્યનાં ઓળખપત્રો
ફક્ત એક પ્રારંભિક IPC સંદેશમાં જ મોકલાય છે, argv કે એન્વાયર્નમેન્ટમાં ક્યારેય નહીં; આઉટપુટ/ભૂલ ફોરવર્ડ કરતી વખતે
પ્રીફિક્સ ઉમેરાય છે અને સંવેદનશીલ માહિતી દૂર કરાય છે. દરેક cron રનમાં Node ની SQLite ચેતવણીનું
પુનરાવર્તન ટાળવા ચાઇલ્ડના exec આર્ગ્યુમેન્ટ્સમાં ફક્ત `ExperimentalWarning` અક્ષમ કરાય છે; અન્ય પ્રકારની ચેતવણીઓ દેખાતી રહે છે.

ગંતવ્ય મોડ્યુલો Next.js/server-only ડિપેન્ડન્સીઓ વિના ઇમ્પોર્ટ કરી શકાય તેવા હોવા જોઈએ. હાલનું
BigQuery અમલીકરણ આ શરત પહેલેથી જ પૂરી કરે છે. ઍક્સેસ-ટોકન કૅશ ફક્ત ચાઇલ્ડના
રન પૂરતા જ રહે છે, અલગ-અલગ રન વચ્ચે નહીં. Node એ સમર્થિત રનટાઇમ છે (`package.json` engines), પરંતુ README નો Bun
ઇન્સ્ટોલેશન વિભાગ અને `Dockerfile.bun` પણ `bun:sqlite` (`src/lib/db/core.ts` / એડેપ્ટર્સ) નો ઉપયોગ કરતો
પ્રોડક્શન સુસંગતતા માર્ગ દર્શાવે છે. તેથી Bun હેઠળ, એક્સપોર્ટ અગાઉનો
ઇન-પ્રોસેસ માર્ગ જાળવી રાખે છે અને એક વખત ચેતવણી આપે છે: ચાઇલ્ડ હીપ/ટાઇમઆઉટ આઇસોલેશન ઉપલબ્ધ નથી.
ઇવેન્ટ-લૂપ અને OOM આઇસોલેશન માટે Node નો ઉપયોગ કરો; અહીં Bun ને ફક્ત ડેવલપમેન્ટ માટેનું માનવામાં આવતું નથી.

`includeBodies` સક્ષમ હોય ત્યારે, કલાકભરનો પેલોડ બૅકલૉગ એકઠો કરવા કરતાં
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` જેવી મિનિટ-સ્તરની આવર્તન-વ્યવસ્થા પસંદ કરો.
બૅચ અને પંક્તિ મર્યાદાઓ હજી પણ દરેક રનને મર્યાદિત રાખે છે. દરેક રનમાં દરેક ગંતવ્ય માટે
પ્રોસેસ શરૂ કરવાનો ખર્ચ થાય છે; આ કુલ CPU વપરાશ ઘટાડવાને બદલે, થોડા સ્ટાર્ટઅપ ખર્ચના બદલામાં સર્વર ઇવેન્ટ-લૂપ આઇસોલેશન આપે છે.

### પેલોડ્સ (પ્રોમ્પ્ટ્સ અને કમ્પ્લીશન્સ)

ડિફૉલ્ટ રૂપે એક્સપોર્ટમાં ફક્ત Logs ની **યાદી**માં દેખાતાં સારાંશ ફીલ્ડ્સ જ સામેલ હોય છે.
**પ્રોમ્પ્ટ્સ અને પ્રતિભાવો એક્સપોર્ટ કરો** (`includeBodies`) ચાલુ કરવાથી દરેક કૉલ માટે Logs ની **વિગતો**
પેનમાં દેખાતી માહિતી પણ મોકલાય છે:

| ફીલ્ડ                            | તેમાં શું હોય છે                                                |
| -------------------------------- | --------------------------------------------------------------- |
| `request_body` / `response_body` | ડૅશબોર્ડ જે રીતે દર્શાવે છે તે રીતે કૉલના પેલોડ્સ               |
| `pipeline_route_decision`        | રાઉટરે કયું લક્ષ્ય અને મોડેલ પસંદ કર્યું                        |
| `pipeline_client_request`        | ક્લાયન્ટે જે રીતે મોકલી હતી તે જ રીતે કાચી વિનંતી               |
| `pipeline_openai_request`        | આંતરિક OpenAI સ્વરૂપમાં રૂપાંતર કર્યા પછીની વિનંતી              |
| `pipeline_provider_request`      | પ્રદાતાના સ્વરૂપમાં, અપસ્ટ્રીમને વાસ્તવમાં મોકલાયેલી વિનંતી     |
| `pipeline_provider_response`     | કાચો અપસ્ટ્રીમ પ્રતિભાવ                                         |
| `pipeline_client_response`       | કૉલ કરનારને પાછું શું અપાયું                                    |
| `pipeline_error`                 | નિષ્ફળ કૉલ માટે પાઇપલાઇન-સ્તરની ભૂલની વિગતો                     |
| `bodies_truncated`               | ઉપરના કોઈપણ ફીલ્ડે `maxBodyBytes` મર્યાદા વટાવી હોય ત્યારે True |

આ પ્રોમ્પ્ટની સામગ્રી છે, તેથી તે **ડિફૉલ્ટ રૂપે બંધ** હોય છે અને ઇરાદાપૂર્વક દરેક ગંતવ્ય માટે અલગ પસંદગી છે.
ડૅશબોર્ડમાં જે દેખાય છે તે જ મોકલાય છે, કારણ કે એક્સપોર્ટ અને `getCallLogById` એક જ વિગત
રિઝોલ્યુશનનો ઉપયોગ કરે છે: પેલોડ્સ લખાય ત્યારે જ તેમાંથી
PII દૂર કરવામાં આવે છે અને ગુપ્ત માહિતી છુપાવવામાં આવે છે, અને
`noLog` API કી વડે કરાયેલ કૉલ કોઈ પેલોડ સંગ્રહિત કરતો નથી, તેથી એક્સપોર્ટ કરવા માટે કંઈ હોતું નથી.

પેલોડ્સ દરેક પંક્તિ માટે ફાઇલસિસ્ટમ આર્ટિફૅક્ટમાંથી વાંચવામાં આવે છે, તેથી હાઇડ્રેશન ફક્ત તે માંગનારાં
ગંતવ્યો માટે જ ચાલે છે. આર્ટિફૅક્ટ ગુમ હોય કે બગડેલું હોય તો, બૅચને નિષ્ફળ બનાવી કર્સરને અટકાવી દેવાને
બદલે તેનો સારાંશ null પેલોડ્સ સાથે એક્સપોર્ટ થાય છે.

`maxBodyBytes` (ડિફૉલ્ટ 262144) દરેક ફીલ્ડને મર્યાદિત કરે છે. લાંબા પેલોડ્સને **કાઢી નાખવાને બદલે
ટૂંકાવવામાં આવે છે** — ટૂંકાવેલો પ્રોમ્પ્ટ પણ "શું પૂછવામાં આવ્યું હતું" તેનો જવાબ આપે છે — અને પંક્તિને
`bodies_truncated` વડે ચિહ્નિત કરાય છે. સ્ટ્રીમ કરાયેલા ચંક-દર-ચંક ડેલ્ટા એક્સપોર્ટ થતા નથી; સંકલિત પ્રતિભાવ
પહેલેથી જ `pipeline_provider_response` અને `pipeline_client_response` માં હોય છે.

## 3. REST API

બધા રૂટ માટે મેનેજમેન્ટ પ્રમાણીકરણ જરૂરી છે (`requireManagementAuth`). ગુપ્ત માહિતી ક્યારેય પરત આપવામાં આવતી નથી:
સંગ્રહિત ગુપ્ત માહિતી શાબ્દિક મૂલ્ય `__stored__` તરીકે પરત આવે છે, અને અપડેટ કરતી વખતે તે મૂલ્ય પાછું મોકલવાથી
સંગ્રહિત ઓળખપત્ર જળવાઈ રહે છે.

જેનો પ્રકાર ગુપ્ત માહિતી જાહેર કરે છે તેવું ગંતવ્ય બનાવવા કે અપડેટ કરવા માટે **`STORAGE_ENCRYPTION_KEY`
જરૂરી છે**. તેના વિના `encrypt()` કોઈ સૂચના વિના ઇનપુટને યથાવત્ પસાર કરે છે, તેથી ઓળખપત્રને
SQLite માં સાદા લખાણ તરીકે મૂકવાને બદલે લખવાની વિનંતી 400 સાથે નકારવામાં આવે છે (Telegram webhook
પણ આ જ સુરક્ષા તપાસ લાગુ કરે છે).

| પદ્ધતિ   | પાથ                                      | હેતુ                                                 |
| -------- | ---------------------------------------- | ---------------------------------------------------- |
| `GET`    | `/api/log-export/types`                  | ગંતવ્યના પ્રકારો + તેમના ગોઠવણી ફીલ્ડની યાદી         |
| `GET`    | `/api/log-export/destinations`           | ગંતવ્યોની યાદી (ગુપ્ત માહિતી છુપાવેલી)               |
| `POST`   | `/api/log-export/destinations`           | ગંતવ્ય બનાવવું                                       |
| `GET`    | `/api/log-export/destinations/{id}`      | એક ગંતવ્ય વાંચવું                                    |
| `PUT`    | `/api/log-export/destinations/{id}`      | નામ / સક્ષમ સ્થિતિ / ગોઠવણી / બેચિંગ અપડેટ કરવું     |
| `DELETE` | `/api/log-export/destinations/{id}`      | કાઢી નાખવું                                          |
| `POST`   | `/api/log-export/destinations/{id}/test` | ઓળખપત્રો તપાસવાં, કંઈ લખવું નહીં                     |
| `POST`   | `/api/log-export/destinations/{id}/run`  | હમણાં બાકી નિકાસ પૂર્ણ કરવી, નિર્ધારિત રન જેવો જ પાથ |
| `GET`    | `/api/log-export/status`                 | Cron સ્થિતિ, તાજેતરના રન, દરેક લક્ષ્ય માટે બાકી કામ  |

`GET /api/log-export/types` UI ને સામાન્ય ઉપયોગ માટે યોગ્ય બનાવે છે: ડેશબોર્ડ ફોર્મ
પરત મળેલા ફીલ્ડ વર્ણનકારોના આધારે રેન્ડર થાય છે, તેથી નવા ગંતવ્ય માટે UI માં ફેરફાર કરવાની જરૂર પડતી નથી.

## 4. BigQuery ગંતવ્ય

રૂપરેખાંકન કીઓ (`type: "bigquery"`):

| કી                   | નોંધો                                                                                |
| -------------------- | ------------------------------------------------------------------------------------ |
| `projectId`          | ડેટાસેટ ધરાવતો GCP પ્રોજેક્ટ                                                         |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                      |
| `tableId`            | `[A-Za-z0-9_]+`                                                                      |
| `location`           | ડેટાસેટ બનાવવાનો હોય ત્યારે જ વપરાય છે (ડિફૉલ્ટ `EU`)                                |
| `serviceAccountJson` | સર્વિસ-એકાઉન્ટ કી. ગુપ્ત: સંગ્રહિત સ્થિતિમાં એન્ક્રિપ્ટ કરેલી, ક્યારેય પરત અપાતી નથી |
| `autoCreate`         | પ્રથમ નિકાસ વખતે ડેટાસેટ અને ટેબલ બનાવો (ડિફૉલ્ટ `true`)                             |

સર્વિસ એકાઉન્ટને લક્ષ્ય ટેબલ પર `bigquery.tables.updateData`ની જરૂર છે, અને
`autoCreate` ચાલુ હોય ત્યારે `bigquery.datasets.create` / `bigquery.tables.create`ની પણ જરૂર છે.

રૂપરેખાંકિત બૅચ એ **કર્સર**નું એકમ છે, HTTPનું નહીં: `send()` તેને વધુમાં વધુ 500 પંક્તિઓના insertAll
કૉલમાં વિભાજિત કરે છે, તેથી મોટું `batch_size` BigQueryની 10 MB વિનંતી મર્યાદા વટાવી શકતું નથી.
ક્ષણિક સ્ટેટસ (408/429/500/502/503/504) માટે એ જ insertIds ફરી વાપરીને, એક્સ્પોનેન્શિયલ
બૅકઑફ સાથે વધુમાં વધુ ત્રણ વાર પુનઃપ્રયાસ થાય છે; પ્રમાણીકરણ અને સ્કીમાની નિષ્ફળતાઓ આખું રન વેડફવાને બદલે
પ્રથમ પ્રયાસે જ અપવાદ ફેંકે છે.

થોડી ક્ષણો પહેલાં બનાવેલું ટેબલ હજી સ્ટ્રીમિંગ એન્ડપૉઇન્ટને દેખાતું નથી, જે થોડા સેકન્ડ માટે
404 આપે છે. તે 404 માટે પુનઃપ્રયાસ થાય છે, પરંતુ **માત્ર ત્યારે જ જ્યારે આ રને ટેબલ બનાવ્યું હોય** —
ખરેખર ગેરહાજર ટેબલ માટે હજી પણ તરત જ નિષ્ફળતા મળે છે. ધ્યાનમાં રાખો કે તાજેતરમાં કાઢી નાખેલા નામ હેઠળ
ટેબલ ફરી બનાવવાથી BigQuery ઘણી મિનિટો સુધી સ્ટ્રીમિંગ ઇન્સર્ટ સ્વીકારતું નથી; આ
કાઢી નાખીને ફરી બનાવવાની પ્રક્રિયાનો ગુણધર્મ છે, તેથી ટેબલ કાઢીને ફરી ઉમેરવાને બદલે નવું ટેબલ નામ પસંદ કરો.

**આંશિક નિષ્ફળતા HTTP 200 સાથે બિન-ખાલી `insertErrors[]` તરીકે આવે છે.** તેને
નિષ્ફળતા ગણવામાં આવે છે અને અપવાદ ફેંકવામાં આવે છે, જે કર્સરને BigQueryએ ક્યારેય
સ્વીકારી ન હોય તેવી પંક્તિઓથી આગળ વધતો અટકાવે છે; `tests/unit/log-export-bigquery.test.ts` આ વર્તન સુનિશ્ચિત કરે છે.

પરિવહન સાદા REST દ્વારા થાય છે — સ્વ-હસ્તાક્ષરિત RS256 અસર્શનના બદલામાં
`https://oauth2.googleapis.com/token` પર ઍક્સેસ ટોકન મેળવવામાં આવે છે, પછી પંક્તિઓ `tabledata.insertAll` પર મોકલાય છે. કોઈ Google SDK
સામેલ કરવામાં આવતું નથી. ઍક્સેસ ટોકન દરેક (સર્વિસ એકાઉન્ટ, સ્કોપ) માટે પ્રક્રિયાની અંદર કૅશ થાય છે.

બનાવેલા ટેબલમાં Logs ટૅબના દરેક ફીલ્ડ માટે એક કૉલમ ઉપરાંત `exported_at` હોય છે, અને તેની ગોઠવણી
કૉલ લૉગ પર વાસ્તવમાં ક્વેરી કેવી રીતે કરવામાં આવે છે તે મુજબ હોય છે:

- **`timestamp` પર દિવસ પ્રમાણે પાર્ટિશન કરેલું**, જેથી તારીખથી સીમિત ક્વેરી માત્ર તે દિવસો જ સ્કૅન કરે.
- **`api_key_name`, `provider`, `model`, `status` દ્વારા ક્લસ્ટર કરેલું** (આ ક્રમમાં), જેથી
  કોણે ચલાવ્યું, તે ક્યાં ગયું, અથવા તે નિષ્ફળ થયું કે નહીં તેના આધારે ફિલ્ટર કરવાથી દરેક પાર્ટિશનની અંદરના બ્લૉક સ્કૅનમાંથી બાકાત થાય છે. BigQuery
  વધુમાં વધુ ચાર ક્લસ્ટરિંગ કૉલમની મંજૂરી આપે છે અને ક્રમ મહત્વનો છે: માત્ર `api_key_name` પરનું ફિલ્ટર
  બ્લૉક બાકાત કરે છે, માત્ર `status` પરનું ફિલ્ટર તેમ કરતું નથી.
- `partitionExpirationDays` દ્વારા **વૈકલ્પિક પાર્ટિશન જાળવણી** (0 બધું જાળવી રાખે છે), જે
  ટેબલ બનાવતી વખતે લાગુ થાય છે.

બંને સેટિંગ બનાવતી વખતે લાગુ થાય છે. હાલનું ટેબલ તેની પહેલેથી રહેલી ગોઠવણી જાળવી રાખે છે, તેથી
જો તમે આ સેટિંગ અપનાવવા માગતા હો તો ગંતવ્યને નવા ટેબલ આઈડી તરફ નિર્દેશિત કરો.

`tests/unit/log-export-bigquery.test.ts` ખાતરી કરે છે કે મૅપર અને ટેબલ સ્કીમા એકબીજા સાથે
સુસંગત રહે, જેથી નિકાસ દરમિયાન નવી કૉલ-લૉગ કૉલમ ચૂપચાપ છૂટી ન જાય.

બૅચને પંક્તિઓની સંખ્યા અને સિરિયલાઇઝ કરેલા બાઇટ્સ **બંને**ના આધારે ભાગોમાં વિભાજિત કરવામાં આવે છે. પેલોડની નિકાસ થવા લાગે પછી
માત્ર પંક્તિઓની સંખ્યા પૂરતી નથી: પ્રૉમ્પ્ટ ધરાવતી 500 પંક્તિઓ દસેક મેગાબાઇટથી પણ વધુ હોઈ શકે છે, અને insertAll
10 MBથી મોટી વિનંતી નકારે છે. 500 પંક્તિઓ અથવા 9 MB, બેમાંથી જે પહેલાં આવે ત્યારે ભાગ પૂર્ણ થાય છે.

## 5. OTLP/HTTP ટ્રેસનું ગંતવ્ય

કન્ફિગરેશનમાં `type: "otlp-http"` વપરાય છે. આ સંગ્રહિત કૉલ લૉગનું શેડ્યૂલ કરેલું, કર્સર-આધારિત એક્સપોર્ટ છે,
`open-sse/services/routing/otel.ts` માંનું શ્રેષ્ઠ-પ્રયાસવાળું લાઇવ રૂટિંગ-ઇવેન્ટ સિંક નથી.
તે આ સિંકનાં એન્વાયરન્મેન્ટ વેરિએબલ, ટાઇમર કે બફર વાંચતું કે બદલતું નથી.
બંને સક્ષમ કરવાથી બે સ્વતંત્ર પ્રકારના સ્પાન ઉત્પન્ન થઈ શકે છે;
આ કૉલ-લૉગ સ્પાનને અલગ ઓળખવા માટે `omniroute.log-export` ઇન્સ્ટ્રુમેન્ટેશન સ્કોપ વાપરો.

| કી                       | ડિફૉલ્ટ / હેતુ                                                                     |
| ------------------------ | ---------------------------------------------------------------------------------- |
| `endpoint`               | સંપૂર્ણ HTTP(S) ટ્રેસ URL જરૂરી છે; `/v1/traces` પ્રત્યય ઉમેરાતો નથી               |
| `headers`                | વૈકલ્પિક `Name: value` લાઇનો અથવા સ્ટ્રિંગ ધરાવતો JSON ઑબ્જેક્ટ; એન્ક્રિપ્ટ કરેલું |
| `requestHeaderAllowlist` | ખાલી (બંધ); સ્પાન એટ્રિબ્યુટ તરીકે કૅપ્ચર કરવાના ક્લાયન્ટ હેડરનાં નામ/ઉપસર્ગ       |
| `serviceName`            | `omniroute`; રિસોર્સ `service.name`                                                |
| `langfuseMapping`        | `false`; Langfuse જનરેશન/સેશન/વપરાશકર્તા એટ્રિબ્યુટ ઉમેરે છે                       |
| `identity`               | `pseudonymous`, `keyName`, અથવા `none`                                             |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                            |
| `timeoutMs`              | દરેક HTTP પ્રયાસ દીઠ `30000`                                                       |
| `environment`            | સેટ કરેલું નથી; વૈકલ્પિક `langfuse.environment`                                    |

સામાન્ય ડૅશબોર્ડ આ ફીલ્ડ દર્શાવે છે. `paths` API ઍરે અથવા નવી લાઇન/અલ્પવિરામથી
અલગ કરેલા ચોક્કસ પાથ ધરાવતો ટેક્સ્ટએરિયા સ્વીકારે છે. એમ્બેડિંગ, રીરૅન્ક અને અન્ય પાથને
સ્પષ્ટ રીતે મંજૂરી ન અપાઈ હોય તો છોડવામાં આવે છે. છોડેલી પંક્તિઓ પણ કર્સરને આગળ વધારે છે; હાલના
રનરના `exported`/`exportedTotal` કાઉન્ટર સ્વીકારેલા સ્પાનને બદલે, ફિલ્ટર કરેલી પંક્તિઓ સહિત
પ્રક્રિયા કરેલી સ્રોત પંક્તિઓ ગણે છે. ફિલ્ટરિંગ ચાઇલ્ડમાં થાય છે, તેના
IPC/કર્સર કરારમાં ફેરફાર કર્યા વિના.

URL વેલિડેશન `src/shared/network/outboundUrlGuard.ts` માંથી DB વિના ચાલતું
`parseAndValidateNonMetadataUrl` હેલ્પર વાપરે છે: `block-metadata` પૉલિસી. ખાનગી URLને
મંજૂરી આપતા વેબહૂક વેલિડેટર જેવી જ બિનશરતી મેટાડેટા/પ્રોટોકોલ/એમ્બેડેડ-ક્રેડેન્શિયલ તપાસો તેમાં છે,
પરંતુ તે વૈશ્વિક ફીચર-ફ્લૅગ ઓવરરાઇડ વિના localhost/LAN લક્ષ્યોને જાણીજોઈને મંજૂરી આપે છે.
આથી ખાનગી HTTP એન્ડપોઇન્ટ સહિત સ્વ-હોસ્ટ કરેલા Langfuse, Phoenix, Tempo અને Collector
એન્ડપોઇન્ટ વાપરી શકાય છે. ક્લાઉડ-મેટાડેટા હોસ્ટ હંમેશાં અવરોધિત રહે છે.
રીડાયરેક્ટ અનુસરવામાં આવતા નથી, તેથી કલેક્ટર ક્રેડેન્શિયલને બીજા હોસ્ટ પર રીડાયરેક્ટ કરી શકતો નથી.
હાલના લેક્સિકલ URL ગાર્ડની જેમ, આ DNS રિઝોલ્યુશનને પિન કરતું નથી; માત્ર
ઑપરેટરના નિયંત્રણ હેઠળના હોસ્ટ જ કન્ફિગર કરો. એન્ડપોઇન્ટ વિશ્વસનીય નેટવર્ક પર ન હોય ત્યારે HTTPSને પ્રાધાન્ય આપો.

### પેલોડ અને ડિલિવરી

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) દરેક
મંજૂર પંક્તિ દીઠ એક CLIENT સ્પાન મોકલે છે, જેનું નામ તેના ચોક્કસ રિક્વેસ્ટ પાથ મુજબ હોય છે. પાથ-આધારિત નામકરણ
સ્પાનના નામમાં મોડેલ કે ઓળખનો ડેટા ઉમેર્યા વિના Chat Completions, Responses અને Messagesને
અલગ પાડે છે. રિસોર્સ એટ્રિબ્યુટમાં `service.name` અને પૅકેજનું `service.version` સામેલ છે.

સામાન્ય ચેટ પ્રયાસ લૉગર (`open-sse/handlers/chatCore/attemptLogging.ts`) પૂર્ણ થવા પર
`duration = Date.now() - startTime` લખે છે અને ટાઇમસ્ટૅમ્પ આપતો નથી;
`src/lib/usage/callLogs.ts` માંનું `saveCallLogOperation` ટાઇમસ્ટૅમ્પને ડિફૉલ્ટ રૂપે લખવાના
(પૂર્ણ થવાના) સમય પર સેટ કરે છે. તેથી એક્સપોર્ટમાં અંત = પંક્તિનો ટાઇમસ્ટૅમ્પ અને શરૂઆત = અંત − અવધિ
(મિલિસેકન્ડને દશાંશ નેનોસેકન્ડમાં રૂપાંતરિત કરીને) સેટ થાય છે. કૉલર દ્વારા અપાયેલા ઐતિહાસિક ટાઇમસ્ટૅમ્પ
પણ અંત સમય તરીકે જાળવવામાં આવે છે; દરેક પંક્તિ માટે શરૂઆત/પૂર્ણતા વચ્ચે ભેદ કરનાર સૂચક નથી.
null અવધિ શૂન્ય બને છે. અમાન્ય/ગેરહાજર ટાઇમસ્ટૅમ્પ બિનનિર્ધારિત સ્પાન બનાવવાને બદલે
બૅચને નિષ્ફળ બનાવે છે. `ttftMs` nullable છે અને `omniroute.ttft_ms` સાથે મૅપ થાય છે.

એટ્રિબ્યુટમાં `gen_ai.operation.name="chat"`, પ્રોવાઇડર, વિનંતી કરાયેલ/પ્રતિસાદ મોડેલ,
ઇનપુટ/આઉટપુટ ટોકન, વૈકલ્પિક કૅશ-રીડ/કૅશ-ક્રિએશન/રીઝનિંગ ટોકન, HTTP સ્ટેટસ,
કોમ્બો, કૅશ સ્રોત, સેશન ટૅગ અને કોરિલેશન આઇડી સામેલ છે. પૂર્ણાંક OTLP મૂલ્યો અને ટાઇમસ્ટૅમ્પ
દશાંશ સ્ટ્રિંગ હોય છે; સ્ટ્રિંગ, બૂલિયન અને અપૂર્ણાંક સંખ્યાઓ તેમના મૂળ OTLP મૂલ્ય
પ્રકારો વાપરે છે. એરર સ્પાનમાં ERROR સ્ટેટસ અને સૅનિટાઇઝ કરેલો સ્ટેટસ સંદેશ હોય છે. કૅનોનિકલ
રેકોર્ડમાં અપસ્ટ્રીમ હોસ્ટ URL નથી, તેથી કલેક્ટરને ખોટી રીતે મોડેલ સર્વર તરીકે
ઓળખાવવાને બદલે `server.address` છોડવામાં આવે છે. ખર્ચ એક્સપોર્ટ થતો નથી.

માત્ર `includeBodies=true` કન્ટેન્ટ હાઇડ્રેટ કરે છે. `langfuseMapping=false` હોય ત્યારે,
`gen_ai.input.messages` / `gen_ai.output.messages` માં OmniRoute દ્વારા સંગ્રહિત સૅનિટાઇઝ કરેલું રિક્વેસ્ટ/રિસ્પોન્સ
બૉડી JSON હોય છે (પાર્સ કરી શકાય ત્યારે કૅનોનિકલ સ્વરૂપમાં), પુનઃઆકારિત semconv
મેસેજ ઍરે નહીં. કાપેલી/બિન-JSON બૉડી કાચા ટેક્સ્ટ તરીકે રહે છે. `langfuseMapping=true` હોય ત્યારે,
બૉડી માત્ર `langfuse.observation.input` / `langfuse.observation.output` તરીકે મોકલાય છે;
`gen_ai.*.messages` એટ્રિબ્યુટ છોડવામાં આવે છે જેથી દરેક બૉડી એક જ વાર મોકલાય. બંને મોડ
હાલના હાઇડ્રેશન પાથમાંથી `maxBodyBytes` વારસામાં મેળવે છે;
`omniroute.bodies_truncated=true` કાપ મૂકાયો હોવાનું દર્શાવે છે.
આ ગંતવ્ય કોઈ વધારાના પાઇપલાઇન સ્નૅપશૉટ કે સૅનિટાઇઝ કર્યા વિનાના આર્ટિફૅક્ટ રીડ ઉમેરતું નથી;
વૈકલ્પિક રિક્વેસ્ટ-હેડર કૅપ્ચર નીચે વર્ણવેલા હાલના હાઇડ્રેટ કરેલા ક્લાયન્ટ સ્નૅપશૉટનો ઉપયોગ કરે છે.
બૉડી એક્સપોર્ટ કરતી વખતે કલાકવાર બૅકલૉગ એકઠો કરવાને બદલે
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` જેવી મિનિટ-સ્તરની આવર્તન ગોઠવણી વાપરો.

### વૈકલ્પિક ક્લાયન્ટ રિક્વેસ્ટ હેડર

હેડર કૅપ્ચર **ડિફૉલ્ટ રૂપે બંધ** છે. ગંતવ્યના કન્ફિગરેશનમાં `requestHeaderAllowlist` સેટ કરો
અને **પ્રોમ્પ્ટ અને પ્રતિસાદ એક્સપોર્ટ કરો** સક્ષમ કરો (ગંતવ્ય પર `includeBodies: true`).
અલાઉલિસ્ટ API ઍરે અથવા નવી લાઇન/અલ્પવિરામથી અલગ કરેલાં નામ ધરાવતો ટેક્સ્ટએરિયા સ્વીકારે છે:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

નામો મોટા-નાના અક્ષરોના ભેદ વિના અને ચોક્કસ રીતે મેળ ખાય છે, સિવાય કે અંતે આવતો એકમાત્ર `*` ખાલી ન હોય તેવો
હેડર-નામ ઉપસર્ગ પસંદ કરે. એકલું `*`, વચ્ચે આવેલા વાઇલ્ડકાર્ડ અને અમાન્ય HTTP હેડર નામો નકારવામાં આવે છે.
વધુમાં વધુ 64 પસંદગીકારો હોઈ શકે છે, દરેકનું નામ/ઉપસર્ગ વધુમાં વધુ 256 ASCII બાઇટનું હોઈ શકે છે.
આ સેટિંગ `headers`થી અલગ છે, જે કલેક્ટર સમક્ષ એક્સપોર્ટરનું પ્રમાણીકરણ કરે છે.

કેપ્ચર માત્ર `pipeline_client_request` વાંચે છે, જે સાચવેલી વિગતવાર પાઇપલાઇનના
`clientRawRequest` (અથવા જૂના `clientRequest`)માંથી ભરવામાં આવે છે. તે ક્યારેય પ્રોવાઇડરના રિક્વેસ્ટ હેડરોનો વૈકલ્પિક સ્ત્રોત તરીકે ઉપયોગ કરતું નથી.
રિક્વેસ્ટ રેકોર્ડ કરવામાં આવી ત્યારે વિગતવાર પાઇપલાઇન લૉગિંગ સક્ષમ હોવું જરૂરી છે.
`includeBodies` અક્ષમ હોય, અથવા ક્લાયન્ટ-સ્નેપશૉટ JSON ગાયબ, બગડેલું કે કપાયેલું હોય, તો કોઈ હેડર
એટ્રિબ્યુટ ઉત્સર્જિત થતા નથી. `maxBodyBytes` વધારવાથી એક્સપોર્ટ સમયે સ્નેપશૉટ કપાતું અટકાવી શકાય છે;
જે વિગત ક્યારેય સાચવવામાં જ ન આવી હોય તેને તે પુનઃસ્થાપિત કરી શકતું નથી. 1 MiB કરતાં મોટો અથવા
256 કરતાં વધુ હેડર એન્ટ્રીઓ ધરાવતો સ્નેપશૉટ અવગણવામાં આવે છે. હેડર કેપ્ચરની સાથે હાલનું પ્રોમ્પ્ટ/રિસ્પોન્સ એક્સપોર્ટ સક્ષમ રહે છે;
મંજૂરીસૂચિ માત્ર હેડરો માટેનો હાઇડ્રેશન મોડ પ્રદાન કરતી નથી.

પસંદ કરેલાં મૂલ્યો `http.request.header.<full lowercase header name>` OTLP સ્ટ્રિંગ એરે બને છે,
એક જ સ્ટ્રિંગ હોય ત્યારે પણ. ઉદાહરણ તરીકે, `X-OmniRoute-Meta-Team: example-team`
`http.request.header.x-omniroute-meta-team` બને છે, જેમાં
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}` હોય છે.
સંપૂર્ણ ઉપસર્ગ જાળવવામાં આવે છે: આ સામાન્ય હેડરો છે, જેમાં બિઝનેસ-ફીલ્ડ પાર્સિંગ કે
`omniroute.metadata.*` / Langfuse મેટાડેટા રૂપાંતરણ થતું નથી. `langfuseMapping` હેડરના
અર્થઘટનમાં ફેરફાર કરતું નથી. પસંદ કરાયેલ એકમૂલ્ય ધરાવતું `User-Agent` માનક સ્કેલર
`user_agent.original` પણ સેટ કરે છે. એક મૂલ્યની અંદરના અલ્પવિરામોના આધારે તેને વિભાજિત કરવામાં આવતું નથી. મોટા-નાના અક્ષરોમાં ભિન્ન સ્વરૂપો સાચવેલી
એન્ટ્રીઓના ક્રમમાં મર્જ થાય છે; કોઈ પણ અમાન્ય સ્વરૂપ હોય તો તે આખું હેડર છોડી દેવામાં આવે છે. એટ્રિબ્યુટો નાના અક્ષરોવાળા નામ પ્રમાણે ગોઠવાય છે.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, API-key હેડરો, auth/token/secret/password/credential
ચિહ્નો ધરાવતાં નામો અને આંતરિક ગેટવે ક્રેડેન્શિયલ્સ હંમેશાં
બાકાત રાખવામાં આવે છે, ભલે તેઓ પસંદ કરાયેલાં હોય અથવા સ્ટોરેજમાં આંશિક રીતે ઢાંકેલાં હોય. જાણીતા ક્રેડેન્શિયલ પેટર્ન માટે
સહિયારા ક્રેડેન્શિયલ ડિટેક્ટરનો ફરી ઉપયોગ થાય છે; રિડૅક્શન ચિહ્નો છોડી દેવામાં આવે છે, સુરક્ષિત મૂલ્યો તરીકે એક્સપોર્ટ કરવામાં આવતાં નથી.
માત્ર સ્ટ્રિંગ અને ખાલી ન હોય તેવા સ્ટ્રિંગ એરે સ્વીકારવામાં આવે છે; સંખ્યાઓ કે ઑબ્જેક્ટનું બળજબરીથી રૂપાંતરણ થતું નથી.
અમાન્ય નામો, પ્રોટોટાઇપ કી, નિયંત્રણ અક્ષરો (હોરિઝોન્ટલ ટૅબ સિવાય) અને ખોટી રચનાવાળા Unicode
ને બૅચ નિષ્ફળ કર્યા વિના કે તેમની સામગ્રી ભૂલોમાં દર્શાવ્યા વિના અવગણવામાં આવે છે.

દરેક સ્પૅન વધુમાં વધુ 32 હેડર, દરેક હેડર દીઠ 16 મૂલ્ય, દરેક મૂલ્ય દીઠ 4096 UTF-8 બાઇટ,
અને કેપ્ચર કરેલાં હેડર નામો તથા મૂલ્યોમાં કુલ 16384 UTF-8 બાઇટ કેપ્ચર કરે છે. અતિમોટાં/અમાન્ય હેડરો
આખેઆખાં છોડી દેવામાં આવે છે, કાપવામાં આવતાં નથી. પસંદગી એ ઑપરેટરનો ગોપનીયતા સંબંધિત નિર્ણય છે: સુરક્ષિત લાગતાં નામોમાં
પણ વ્યક્તિગત ડેટા હોઈ શકે છે, અને આ મર્યાદાઓ/ડિટેક્ટરો સામાન્ય PII દૂર કરનાર સાધન નથી.

### ડિલિવરી મર્યાદાઓ

રિક્વેસ્ટો એન્વલપ સહિત 500 સ્પૅન અને 4 MiB UTF-8 JSON સુધી મર્યાદિત છે.
કર્સર બૅચની પ્રથમ રિક્વેસ્ટ પહેલાં દરેક મંજૂર સ્પૅનનું કદ તપાસવામાં આવે છે. મર્યાદા કરતાં મોટો કોઈ એક
સ્પૅન હોય તો તે બૅચનો કોઈ ભાગ મોકલાતો નથી અને `maxBodyBytes`
ઘટાડવાના માર્ગદર્શન સાથે નિષ્ફળતા આવે છે; તેને ચૂપચાપ છોડી દેવામાં આવતો નથી. પ્રીફ્લાઇટ માત્ર રેકોર્ડ સંદર્ભો અને
બાઇટ ગણતરીઓ જાળવે છે અને દરેક અસ્થાયી સ્પૅન/JSON કાઢી નાખે છે; બૅચની બીજી સિરિયલાઇઝ કરેલી નકલ રાખવાને બદલે
મર્યાદિત ખંડો માટે સ્પૅન ફરી બનાવવામાં આવે છે. HTTP 408/429/5xx, નેટવર્ક નિષ્ફળતાઓ અને ટાઇમઆઉટ માટે વધુમાં વધુ
ત્રણ પ્રયાસો થાય છે, જેમાં 250/500 msનો ઘાતાંકીય બૅકઑફ હોય છે. `Retry-After` સેકન્ડ અથવા HTTP તારીખો
વિલંબને વધુમાં વધુ 5 સેકન્ડ સુધી લંબાવી શકે છે. અન્ય સ્ટેટસ તરત જ નિષ્ફળ જાય છે. OTLP 2xx આંશિક અસ્વીકાર પણ
ખોવાયેલા સ્પૅનની સ્વીકૃતિ આપવાને બદલે ભૂલ ફેંકે છે; ખાલી અથવા માન્ય JSON સ્વીકૃતિઓ સ્વીકારવામાં આવે છે, જેમાં
રિસ્પોન્સ વાંચવાની મર્યાદા 64 KiB છે.

ભૂલોમાં માત્ર એક્સપોર્ટરની પોતાની હકીકતો હોય છે: HTTP સ્ટેટસ, રીટ્રાય વર્ગ, પ્રયાસો અને મોકલેલા સ્પૅનની
સંખ્યા, અથવા સ્વીકૃતિ/નેટવર્ક નિષ્ફળતાનું નિશ્ચિત લખાણ. કલેક્ટર રિસ્પોન્સ બોડી,
આંશિક સફળતાની સંખ્યાઓ અને રિસ્પોન્સ હેડરો ક્યારેય ભૂલો, લૉગ કે
ડૅશબોર્ડમાં નકલ કરવામાં આવતાં નથી. નિષ્ફળ અથવા આંશિક રીતે સ્વીકારેલી બૅચની સ્વીકૃતિ આપવામાં આવતી નથી: ડેસ્ટિનેશન તે સ્ટેટસ સાથે
નિષ્ફળ થતું હોવાનું દર્શાવે છે, કર્સર છેલ્લી સ્વીકૃત બૅચ પર રહે છે અને આગામી રન
એ જ પંક્તિઓ ફરી મોકલે છે. કલેક્ટર અથવા કન્ફિગરેશન
સુધારવામાં ન આવે ત્યાં સુધી કાયમી સ્ટેટસ નિષ્ફળ થતા રહે છે. રિસ્પોન્સની વિગતો માટે કલેક્ટરના પોતાના લૉગ વાપરો. કૉલ-લૉગ ભૂલ સારાંશોનું
અલગ રિડૅક્શન યથાવત્ રહે છે.
`prepare()` કંઈ પ્રોવિઝન કરતું નથી; ટેસ્ટ ચોક્કસપણે `{"resourceSpans":[]}` પોસ્ટ કરે છે અને
કૉલ-લૉગ સ્પૅન લખ્યા વિના HTTP સ્ટેટસ દર્શાવે છે.

ટ્રેસ આઇડી અને સ્પૅન આઇડી અનુક્રમે
`"omniroute.trace\\0" + callLogId` અને `"omniroute.span\\0" + callLogId` પરના SHA-256ના પ્રથમ 32/16 હેક્સ અંકો છે. ફરી મોકલવામાં
સમાન આઇડી હોય છે. આ ડિડુપ્લિકેશનની ખાતરી નથી: Langfuse
v4 ઇન્જેશન સહિત કેટલાક બૅકએન્ડ સમાન આઇડીવાળા સ્પૅનનું ડિડુપ્લિકેશન કરતા નથી. ક્રૅશ અથવા આંશિક ખંડ નિષ્ફળતા
વધુમાં વધુ એક અસ્વીકૃત કર્સર બૅચ ફરી મોકલી શકે છે; તે આખી બૅચ ડુપ્લિકેટ થઈ શકે છે,
માત્ર તેનો છેલ્લો HTTP ખંડ નહીં. આ સમાધાન ધ્યાનમાં રાખીને કર્સર બૅચનું કદ પસંદ કરો.

### Langfuse ઉદાહરણ

સ્વ-હોસ્ટેડ Langfuse ઇન્સ્ટન્સ માટે આ ફીલ્ડ કન્ફિગર કરો:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

શાબ્દિક `public-key:secret-key` સ્ટ્રિંગના Base64 તરીકે Authorization મૂલ્ય સ્થાનિક રીતે બનાવો
(ઉદાહરણ તરીકે `Buffer.from(publicKey + ":" + secretKey).toString("base64")` વડે).
વાસ્તવિક ક્રેડેન્શિયલ્સ લૉગ, સ્ક્રીનશૉટ કે ઇશ્યૂમાં પેસ્ટ કરશો નહીં. મૅપિંગ આપમેળે
`x-langfuse-ingestion-version: 4` સેટ કરે છે; Authorization હજી પણ `headers`માં આપવામાં આવે છે.
હેડરો અને જનરેટ કરાયેલ આઇડેન્ટિટી સૉલ્ટ બંને હાલની એન્ક્રિપ્ટેડ સિક્રેટ-ફીલ્ડ
વ્યવસ્થા અને API પ્લેસહોલ્ડરનો ઉપયોગ કરે છે; `STORAGE_ENCRYPTION_KEY` જરૂરી છે.

મૅપિંગ જનરેશનનો પ્રકાર/મોડેલ, JSON વપરાશની વિગતો (ઇનપુટ/આઉટપુટ/કુલ અને ઉપલબ્ધ
કૅશ કીઓ), JSON ઇનપુટ/આઉટપુટ સ્નૅપશૉટ્સ, ERROR/DEFAULT સ્તર, સૅનિટાઇઝ કરેલો સ્થિતિ સંદેશ,
ટ્રેસનું નામ, સેશન આઇડી, વૈકલ્પિક એન્વાયર્નમેન્ટ અને પ્રોવાઇડર, વિનંતી કરેલું મોડેલ, પાથ, કોમ્બો, કૅશ
સ્રોત અને સ્થિતિ માટે ફિલ્ટર કરી શકાય એવું `langfuse.observation.metadata.<key>` ઉમેરે છે.
`langfuse.observation.completion_start_time` એ શરૂઆત + TTFT સમયે ISO 8601 સ્વરૂપમાં હોય છે,
પરંતુ માત્ર ત્યારે જ જ્યારે TTFT જાણીતું હોય અને સમયગાળાની અંદર હોય. ખર્ચનાં કોઈ એટ્રિબ્યૂટ્સ મોકલવામાં આવતાં નથી.

ઓળખ મોડ `langfuse.user.id` પર લાગુ પડે છે:

- `pseudonymous` (ડિફૉલ્ટ): દરેક ડેસ્ટિનેશન માટેના રૅન્ડમ
  32-બાઇટ સૉલ્ટ સાથે API કીના આંતરિક આઇડીનું HMAC-SHA256. સૉલ્ટ ગેરહાજર હોય તો બનાવતી વખતે જનરેટ થાય છે, તેને
  `identitySalt` તરીકે એન્ક્રિપ્ટ કરવામાં આવે છે, ક્યારેય પરત આપવામાં આવતું નથી અને ફેરફારો દરમિયાન જાળવી રાખવામાં આવે છે. મૂળ કી આઇડી ક્યારેય
  સ્પાન એટ્રિબ્યૂટ્સમાં મૂકવામાં આવતા નથી. ડેસ્ટિનેશનનો સૉલ્ટ ફરી બનાવવાથી/રોટેટ કરવાથી ઓળખ બદલાય છે.
- `keyName`: કન્ફિગર કરેલું API કીનું નામ, જે ઇરાદાપૂર્વક તે ઑપરેટર લેબલ જાહેર કરે છે.
- `none`: કોઈ યુઝર આઇડી નહીં. સેશન ટૅગ્સ હાજર હોય ત્યારે હજી પણ એક્સપોર્ટ થાય છે; આ મોડ
  મનસ્વી પ્રોમ્પ્ટ સામગ્રી અથવા ઑપરેટરે આપેલાં સેશન/કોરિલેશન લેબલ્સને અનામી બનાવતા નથી.

### બૅકફિલ વિના શરૂઆત કરવી

માત્ર બનાવતી વખતે, **વર્તમાન સ્થાનથી શરૂ કરો (હાલના લૉગ્સ છોડો)** સક્રિય કરો અથવા
બનાવવાના API પેલોડના ટોચના સ્તરે `startFromCurrentPosition: true` આપો. તે હાલના કર્સર
હેલ્પર્સનો ઉપયોગ કરીને, માઇગ્રેશન વિના, `cursor_row_id` ને હાલમાં જાળવી રાખેલા કૉલ-લૉગના મહત્તમ rowid પર
પ્રારંભિત કરે છે. ડિફૉલ્ટ false છે (કર્સર 0 અને જાળવી રાખેલા ઇતિહાસનું બૅકફિલ).
આ અપડેટ કરતી વખતે કર્સર રીસેટ કરવા માટેનું સેટિંગ નથી.

શેર કરેલા `ttftMs` ના ઉમેરાથી BigQuery મૅપર
અને નવા ટેબલના સ્કીમામાં નલ સ્વીકારી શકતી `ttft_ms` કૉલમ પણ ઉમેરાય છે: તેની સ્કીમા ટેસ્ટ માટે દરેક કેનોનિકલ રેકોર્ડ ફીલ્ડની
કૉલમ હોવી જરૂરી છે. હાલનાં ટેબલ્સ કોઈ ફેરફાર વિના એક્સપોર્ટ થતા રહે છે: `prepare()` ટેબલનો સ્કીમા વાંચે છે અને
તે કૉલમ ગેરહાજર હોય ત્યારે માત્ર `ttft_ms` ને બાકાત રાખે છે. આગામી રનમાં TTFT મેળવવા માટે નલ સ્વીકારી શકતી INT64 કૉલમ ઉમેરો,
અથવા નવું ટેબલ વાપરો. કોઈ PATCH, આપમેળે સ્કીમામાં ફેરફાર કે વધારાની
પરવાનગીઓની જરૂર નથી; રોના અન્ય તમામ ફીલ્ડ્સ માટે સ્કીમાની કડક ચકાસણી યથાવત્ રહે છે.

## 6. ડેસ્ટિનેશન ઉમેરવું

1. `LogExportDestinationType` એક્સપોર્ટ કરતી `src/lib/logExport/destinations/<name>.ts` બનાવો:
   Zod `configSchema`, UI માટે `fields` ડિસ્ક્રિપ્ટર એરે, `secretFields`, અને
   `test()` / `prepare()` / `send(records)` પરત આપતું `createClient(config)`.
2. તેને `src/lib/logExport/registry.ts` માંના `DESTINATIONS` એરેમાં ઉમેરો.
3. `tests/unit/` હેઠળ ટેસ્ટ લખો.

આટલો જ ફેરફાર કરવાનો છે: પર્સિસ્ટન્સ, cron જોબ, REST લેયર, સિક્રેટ એન્ક્રિપ્શન અને
ડેશબોર્ડ ફોર્મ બધાં રજિસ્ટ્રી વાંચે છે.

નવા ડેસ્ટિનેશન માટે બે નિયમો:

- આંશિક નિષ્ફળતા પર `send()` **એક્સેપ્શન થ્રો કરવું જ જોઈએ**. સફળતાપૂર્વક પૂર્ણ થવાનો અર્થ છે "ડેસ્ટિનેશન પાસે આ પંક્તિઓ છે",
  અને કર્સર કાયમી ધોરણે તેમની આગળ વધી જાય છે.
- વપરાશકર્તાએ આપેલો URL સ્વીકારતું ડેસ્ટિનેશન ફેચ કરતાં પહેલાં
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) દ્વારા તેની માન્યતા ચકાસે તે જરૂરી છે,
  જેમ વેબહૂક કરે છે. BigQuery ને આની જરૂર નથી: તેના હોસ્ટ સ્થિર છે.

## 7. તેનું સંચાલન

- **ડેશબોર્ડ**: ઇન્ટિગ્રેશન્સ → લોગ એક્સપોર્ટ. ડેસ્ટિનેશન ઉમેરો, પંક્તિઓ લખ્યા વિના
  ઓળખપત્રો ચકાસવા **ટેસ્ટ** ચલાવો, પછી તેને સક્ષમ કરો.
- **બાકી કામ**: દરેક ડેસ્ટિનેશન કાર્ડ બાકી પંક્તિઓ અને કર્સર દર્શાવે છે; `GET
/api/log-export/status` એ જ આંકડાઓ સાથે જોબના છેલ્લા 20 રન પરત આપે છે.
- **એક ડેસ્ટિનેશનની નિષ્ફળતા અન્ય ડેસ્ટિનેશનને નિષ્ફળ કરતી નથી** — રનનો સારાંશ દરેક ડેસ્ટિનેશનની
  સ્થિતિ `last_status` / `last_error` માં નોંધે છે, અને જોબ રનનો ઇતિહાસ એકંદર માહિતી રાખે છે.
- **ડેસ્ટિનેશન કાઢી નાખવાથી તેનો કર્સર પણ કાઢી નાખવામાં આવે છે.** તેને ફરી ઉમેરવાથી સૌથી જૂના જાળવી રાખેલા
  કૉલ લોગથી શરૂઆત થાય છે, જેના કારણે ડેસ્ટિનેશન પાસે પહેલેથી હોઈ શકે તેવી પંક્તિઓ ફરી મોકલાય છે. BigQuery પર દરેક પંક્તિનું
  `insertId` ફક્ત BigQuery ની પોતાની ડી-ડુપ્લિકેશન સમયમર્યાદામાં જ આ પુનરાવર્તન સંભાળે છે, તેથી
  ડેસ્ટિનેશન કાઢી નાખવાને બદલે તેને નિષ્ક્રિય કરવાનું પસંદ કરો.
