## અવલોકન

તમામ OmniRoute મેનેજમેન્ટ API રૂટને સુરક્ષાના ત્રણ સ્તરોમાંથી એકમાં વર્ગીકૃત કરવામાં આવે છે. વર્ગીકરણ સ્થિર છે, `src/server/authz/routeGuard.ts`માં વ્યાખ્યાયિત છે અને અન્ય કોઈપણ પ્રમાણીકરણ શાખા ચાલે તે પહેલાં તેનું મૂલ્યાંકન કરવામાં આવે છે.

## સ્તરો

### સ્તર 1 — LOCAL_ONLY

**દ્વારા અમલમાં મૂકાયેલ:** `isLocalOnlyPath(path)` → લૂપબૅક હોસ્ટ ચકાસણી  
**બાયપાસ:** મૂળભૂત રીતે કોઈ નહીં. જ્યારે વિનંતીમાં `manage` સ્કોપ ધરાવતી માન્ય API કી હોય ત્યારે `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`માંના પાથ માટે મર્યાદિત અપવાદ (જુઓ [Manage-સ્કોપ અપવાદ](#manage-scope-carve-out)).

આ રૂટ્સ ચાઇલ્ડ પ્રોસેસ શરૂ કરે છે અથવા રનટાઇમ કોડ ચલાવે છે. તેમને નોન-લૂપબૅક ટ્રાફિક માટે ખુલ્લા મૂકવાથી માન્ય JWT મેળવનાર હુમલાખોર (દા.ત., Cloudflared/Ngrok ટનલ મારફતે) પ્રોસેસ શરૂ કરી શકે છે — જે જાણીતો CVE વર્ગ છે ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj શું છે (હુમલાનો વર્ગ):** મેનેજમેન્ટ/એજન્ટ સર્વર એવું એન્ડપોઇન્ટ ખુલ્લું મૂકે છે જે સબપ્રોસેસ (`npm install`, `node`, બ્રાઉઝર, પ્રોક્સી, `git`, `tar`, …) શરૂ કરે છે. જો તે એન્ડપોઇન્ટ ઓફ-હોસ્ટથી પહોંચી શકાય તેવું હોય — કારણ કે ઑપરેટરે OmniRouteને nginx/Cloudflare/Tailscale ટનલ પાછળ મૂક્યું હોય અને JWT લીક થયું હોય, અથવા ઑથેન્ટિકેશન ખોટી રીતે કૉન્ફિગર થયું હોય — તો હુમલાખોર "API કૉલ કરો"ને "હોસ્ટ પર કમાન્ડ ચલાવો"માં ફેરવી દે છે (રિમોટ કોડ એક્ઝિક્યુશન). OmniRoute દરેક પ્રોસેસ શરૂ કરી શકતા રૂટ પર **કોઈપણ ઑથેન્ટિકેશન ચકાસણી પહેલાં, બિનશરતી રીતે લૂપબૅક હોસ્ટ ચકાસણી** લાગુ કરીને આ ખામી બંધ કરે છે: ટનલ મારફતે લીક થયેલું ટોકન પણ પ્રોસેસ શરૂ કરવાની ક્ષમતા સુધી પહોંચી શકતું નથી.

**સંપૂર્ણ LOCAL_ONLY સમૂહ.** અધિકૃત સ્રોત `src/server/authz/routeGuard.ts`માંના `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` છે; નીચેનું કોષ્ટક વર્તમાન સ્થિતિ દર્શાવે છે. `check-route-guard-membership` ગેટ પ્રોસેસ શરૂ કરી શકતા પ્રિફિક્સ હેઠળની દરેક `route.ts`ની ગણતરી કરે છે અને જો કોઈને local-only તરીકે વર્ગીકૃત ન કરવામાં આવી હોય, તો CI નિષ્ફળ કરે છે.

**ઉલ્લંઘન પર પ્રતિસાદ:** `403 LOCAL_ONLY`

#### મેનેજ-સ્કોપ અપવાદ

LOCAL_ONLY પાથનો એક ઉપસમૂહ નોન-લૂપબૅકથી પણ ઍક્સેસ કરી શકાય છે, જો અને
માત્ર જો વિનંતીમાં એવું `Authorization: Bearer <api-key>` હોય જેનાં
મેટાડેટામાં `manage` સ્કોપ (અથવા `admin`) સામેલ હોય. આ અપવાદ
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` મારફતે દરેક પાથ માટે સ્પષ્ટપણે નિયંત્રિત
થાય છે, જેથી કોઈપણ નવા LOCAL_ONLY પાથ માટે ડિફૉલ્ટ કડક-લૂપબૅક જ રહે. પ્રમાણીકરણ
વગરની વિનંતીઓ અને નોન-મેનેજ કી ધરાવતી વિનંતીઓ હજુ પણ
`403 LOCAL_ONLY` સાથે નકારવામાં આવે છે.

હાલમાં બાયપાસ કરી શકાય એવો એકમાત્ર પ્રીફિક્સ `/api/mcp/` છે. `/api/cli-tools/runtime/` અને
`/api/services/`ને ઇરાદાપૂર્વક બાકાત રાખવામાં આવ્યા છે કારણ કે તેઓ મનસ્વી
સબપ્રોસેસ (`npm install`, `node`) સ્પૉન કરી શકે છે, અને આ ચોક્કસપણે એ CVE વર્ગ છે જેને
રોકવા માટે LOCAL_ONLY ટિયર અસ્તિત્વમાં છે.

#### ઑપરેટર માર્ગદર્શન અને ઑડિટિંગ

જો તમે OmniRouteને રિવર્સ પ્રૉક્સી અથવા ટનલ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) પાછળ ચલાવો છો, તો પણ લૂપબૅક તપાસ ઉપરના સ્પૉન-સક્ષમ
રૂટ્સને સુરક્ષિત રાખે છે — જે વિનંતીનું ક્લાયન્ટ સરનામું નોન-લૂપબૅક હોય તેને
**ઑથ ચાલે તે પહેલાં** `403 LOCAL_ONLY` સાથે નકારવામાં આવે છે, તેથી લીક થયેલું JWT
સ્પૉન સુધી પહોંચી શકતું નથી. ઑપરેટરની બે જવાબદારીઓ બાકી રહે છે:

- **ક્લાયન્ટ IP ને લૂપબૅક તરીકે બનાવટી રીતે દર્શાવીને 403 ને "ઠીક" કરશો નહીં.** `X-Forwarded-For: 127.0.0.1` સેટ કરવું, અથવા સ્રોત સરનામાને
  લૂપબૅક તરીકે ફરી લખતો પ્રોક્સી વાપરવો, આ સ્તર જે RCE વર્ગને બંધ કરે છે તેને
  ફરીથી ખોલે છે. પ્રોક્સી મારફતે dashboard/API ને ઉપલબ્ધ કરાવો — spawn-સક્ષમ રૂટ્સને ક્યારેય નહીં.
- **manage-scope બાયપાસને ન્યૂનતમ રાખો.** ફક્ત `/api/mcp/` ને બાયપાસ કરી શકાય છે, અને
  તે પણ ફક્ત `manage`-સ્કોપવાળી API કી વડે. `SPAWN_CAPABLE_PREFIXES` ને ક્યારેય
  બાયપાસ સૂચિમાં ઉમેરી શકાતા નથી — zod સ્કીમા તેમને નકારે છે અને
  `isLocalOnlyBypassableByManageScope` તેમને રનટાઇમ પર અવરોધે છે (બહુસ્તરીય સુરક્ષા),
  dashboard પર "cannot be made bypassable" નો આ જ અર્થ છે. આ જ
  અસ્વીકાર-સૂચિમાં કેટલાક એવા LOCAL_ONLY રૂટ્સ પણ છે જે spawn કરતા નથી, પરંતુ
  તેમને પણ ક્યારેય દૂરસ્થ રીતે ઍક્સેસ કરી શકાય તેવા ન હોવા જોઈએ —
  `/api/oauth/kiro/auto-import` (હોસ્ટ-લોકલ Kiro
  ક્રેડેન્શિયલ ફાઇલો વાંચે છે), `/api/discovery/` અને `/api/issue-agent/`. રનટાઇમ
  સ્નૅપશૉટ લોડર સંગ્રહિત settings પંક્તિમાંથી પણ આવી એન્ટ્રીઓ કાઢી નાખે છે, અને
  લેગસી JSON ઇમ્પોર્ટ (`/api/settings/import-json`) બાયપાસ કીઓ ક્યારેય લખતું નથી.
  દરેક `LOCAL_ONLY_API_PREFIXES` એન્ટ્રી કાં તો અસ્વીકાર-સૂચિમાં હોવી જોઈએ અથવા
  બાયપાસ માટે પાત્ર છે કે નહીં તેની સમીક્ષા થવી જોઈએ (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/` હેઠળના ડાયનેમિક-સેગમેન્ટ
  અને સ્ટેટિક-પાથવાળા spawn-સક્ષમ રૂટ્સ (દા.ત. `/login`,
  `/refresh-cursor`) ને
  `src/shared/constants/spawnCapablePrefixes.ts` માં રહેલા regex-આધારિત `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` સહયોગી દ્વારા આવરી લેવામાં આવે છે, સપાટ
  `SPAWN_CAPABLE_PREFIXES` ઍરે દ્વારા નહીં — તેમને પકડવા માટે સપાટ ઍરેએ
  સમગ્ર `/api/providers/` પ્રિફિક્સને આવરી લેવો પડે, જેનાથી દૂરસ્થ dashboards દ્વારા
  provider CRUD માટે કાયદેસર રીતે વપરાતું રૂટ-ટ્રી અતિશય વ્યાપક બની જાય.

**ઍક્સેસનું ઑડિટિંગ** — હોસ્ટની બહારથી આ રૂટ્સ સુધી કશું પહોંચી રહ્યું નથી તેની ચકાસણી કરવા માટે:

- `/dashboard/settings/security` પર **Authorization Inventory** ખોલો: તે લાઇવ LOCAL_ONLY પ્રિફિક્સ સૂચિ, કયા પ્રિફિક્સ બાયપાસ કરી શકાય છે અને કમ્પાઇલ-ટાઇમ spawn-સક્ષમ ("cannot be made bypassable") સમૂહ દર્શાવે છે.
- ઉપરના પ્રિફિક્સની સાથે non-loopback ક્લાયન્ટ સરનામું હોય તેવી એન્ટ્રીઓ માટે તમારા reverse-proxy / access લૉગ્સમાં grep કરો. `403 LOCAL_ONLY` ના બદલે `200` પરત કરનારી આવી કોઈ પણ હિટનો અર્થ છે કે પ્રોક્સી વાસ્તવિક ક્લાયન્ટ IP ને છુપાવી રહ્યો છે — પ્રોક્સીને ઠીક કરો.
- આ પૈકીના કોઈ પાથ માટે OmniRoute ના લૉગ્સમાં `403 LOCAL_ONLY` આવવું એ guard અપેક્ષા મુજબ કાર્ય કરી રહ્યો હોવાનું સૂચવે છે, દબાવી દેવાની ભૂલ નથી.

#### કૉલ-સાઇટ પ્રોબ ગેટ ધરાવતા દૂરસ્થ રીતે ઍક્સેસ કરી શકાય તેવા રૂટ્સ

`getRequestPeerLocality()` (`src/shared/utils/apiAuth.ts`) વડે વાંચે છે અને ફક્ત
`loopback` / `lan` કૉલર્સ માટે જ પ્રોબ ચલાવે છે. `remote` કૉલરને

જે `probed: false` તરીકે ચિહ્નિત હોય છે.

| રૂટ                                                              | દૂરસ્થ કૉલર્સ માટે છોડવામાં આવતો પ્રોબ                             |

હોસ્ટને પ્રોબ કરતો નવો read રૂટ આ જ પેટર્ન અનુસરે છે, અથવા તેને સીધો

આ pipeline ની બહાર સર્વ થતી WebDAV file service ને કૉલરે પસંદ કરેલા root
તરફ નિર્દેશિત કરે છે અને તાજા બનાવેલા Basic credentials પાછા આપે છે, `DELETE` તેમને rotate કરે છે, અને parent `POST`
Obsidian REST API token સંગ્રહે છે. GHSA-62vw એ ફક્ત `GET` દ્વારા password જાહેર થવાનું ઢાંક્યું હતું;
જારી કરવાની પ્રક્રિયા હજુ પણ fail-open સ્તર પર હતી (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` વધુમાં
એવા vault ને નકારે છે જે data directory જ હોય, તેની અંદર આવેલું હોય, અથવા તેને પોતાની અંદર સમાવતું હોય.

#### ક્રેડેન્શિયલ exports ફક્ત ઑપરેટર માટે છે

ઉપરનું સ્તર માત્ર એટલું નક્કી કરે છે કે _કોઈક_ ઓળખપત્ર જરૂરી છે કે નહીં. સંગ્રહિત
ઓળખપત્રો ડાઉનલોડ કરતા રૂટ્સ હેન્ડલરમાં બીજી તપાસ ઉમેરે છે: `GET /api/settings/export-json` (ડિક્રિપ્ટ કરેલા
પ્રોવાઇડર કનેક્શન્સ અને મૂળ API કીઝ), `GET /api/db-backups/export` (SQLite ફાઇલ) અને
`GET /api/db-backups/exportAll` (સંપૂર્ણ આર્કાઇવ) `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`) ને કૉલ કરે છે. તે ડૅશબોર્ડ સેશન, સ્થાનિક CLI સબ્જેક્ટ અથવા
લૉગિન અક્ષમ કરેલું ઇન્સ્ટન્સ સ્વીકારે છે અને કોઈપણ સ્કોપની API કીઝ (`manage`
અને `admin` સહિત) તથા `oma_` ઍક્સેસ ટોકન્સને `403` જવાબ આપે છે. સિંક ટોકન જારી કરવાની પ્રક્રિયા (`POST /api/sync/tokens`) એ જ
હેલ્પરનો, તેમજ વિશ્વસનીય લૂપબૅક ઇન્ટર્નલ-સર્વિસ ટોકનનો ઉપયોગ કરે છે.

#### Credential exports and restores are operator-only

The tier above only decides whether _some_ credential is required. The routes that download
stored credentials add a second check in the handler: `GET /api/settings/export-json` (decrypted
provider connections and raw API keys), `GET /api/db-backups/export` (the SQLite file) and
`GET /api/db-backups/exportAll` (the full archive) call `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). It accepts a dashboard session, the local CLI subject, or
an instance with login disabled, and answers `403` to API keys of any scope (including `manage`
and `admin`) and to `oma_` access tokens. The destructive counterparts hold the same boundary:
`POST /api/db-backups/import` (uploaded `.sqlite`, `dryRun=true` included), `POST /api/db-backups`
(restore a stored backup by id) and `POST /api/settings/import-json` (legacy JSON restore)
replace the live database or the whole settings/connections/API-key set, so a machine credential
cannot trigger them either. Listing, creating, retention and cleanup of backups
(`GET`/`PUT`/`PATCH`/`DELETE /api/db-backups`) keep ordinary management auth. Sync token
issuance (`POST /api/sync/tokens`) uses the same helper, plus the trusted loopback
internal-service token.

### નવા ઇન્સ્ટોલેશનનું બુટસ્ટ્રૅપ માત્ર લૂપબૅક માટે છે — વાસ્તવિક પિયર દ્વારા, `Host` દ્વારા નહીં

કોઈ મેનેજમેન્ટ પાસવર્ડ કૉન્ફિગર ન હોય (અને `INITIAL_PASSWORD` પણ ન હોય) ત્યારે,
`src/shared/utils/apiAuth.ts` માંનું `isAuthRequired()` અનામી બુટસ્ટ્રૅપને **માત્ર લૂપબૅક પિયર્સ માટે**
ખુલ્લું રાખે છે. લૂપબૅકનો નિર્ણય વિશ્વસનીય પિયર સિગ્નલ્સ પરથી આ ક્રમમાં લેવાય છે: ટોકનથી સ્ટૅમ્પ કરાયેલ વાસ્તવિક TCP પિયર
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, જે પોલિસી જુએ છે), પાઇપલાઇનનો પોતાનો
`AUTHZ_HEADER_PEER_LOCALITY` નિર્ણય (જે રૂટ હેન્ડલર્સ જુએ છે અને માત્ર
`OMNIROUTE_PEER_STAMP_TOKEN` સેટ હોય ત્યાં સુધી વિશ્વસનીય છે), અથવા સીધા કૉલર્સ માટે વાસ્તવિક સૉકેટ પિયર. `Host` /
`nextUrl.hostname` નો ક્યારેય ઉપયોગ થતો નથી અને પ્રથમ પાસવર્ડ લખવાની ક્રિયા
(`POST /api/settings/require-login`) પણ એ જ નિયંત્રણ હેઠળ છે, દરેક
નેટવર્ક પિયર માટે ખુલ્લી નથી (GHSA-7pq4-8pvv-rx7r). `managementPolicy` તેનો પોતાનો `peerContext` નિર્ણય
સ્પષ્ટ રીતે નીચે મોકલે છે, તેથી ORIGINAL (સ્ટ્રિપ કરતા પહેલાંની) રિક્વેસ્ટના હેડર્સ ક્યારેય તેનો નિર્ણય લેતા નથી.

### સ્તર 3 — MANAGEMENT (ડિફૉલ્ટ)

અન્ય તમામ મેનેજમેન્ટ રૂટ્સ. `requireLogin=false`
કૉન્ફિગર ન હોય ત્યાં સુધી ઑથેન્ટિકેશન જરૂરી છે. CLI ટોકન્સ આ રૂટ્સને ઑથેન્ટિકેટ કરી શકે છે (લૂપબૅક + માન્ય HMAC).

## મૂલ્યાંકન ક્રમ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → લૂપબૅક                                  → આગળ વધો
     → નોન-લૂપબૅક, manage-સ્કોપ Bearer
        AND isLocalOnlyBypassableByManageScope   → મંજૂરી આપો (management_key)
     → અન્યથા                                    → 403 LOCAL_ONLY સાથે નકારો
  2. isInternalModelSyncRequest(ctx)?
     → મંજૂરી આપો (system)
  3. hasValidCliToken(headers)?
     → મંજૂરી આપો (cli) [લૂપબૅક + timingSafeEqual HMAC ચકાસણી]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → મંજૂરી આપો (dashboard_session)
     → બાયપાસ ન કરી શકાય તેવા પાથ પર manage-સ્કોપ Bearer?
        → મંજૂરી આપો (management_key)
     → 401/403 સાથે નકારો
  5. requireLogin=false?
     → મંજૂરી આપો (anonymous)
```

પગલું 1ની manage-સ્કોપ શાખા એકમાત્ર પ્રમાણિત પાથ છે જે
LOCAL_ONLY રૂટને સંતોષી શકે છે; auth-backend નિષ્ફળતા મોડ 503 પરત કરે છે (403 નહીં), જેથી
સમાપ્ત થયેલ DB મૌન રીતે "નકારો" પર ડાઉનગ્રેડ ન થાય.

## નવો spawn-સક્ષમ રૂટ ઉમેરવો

1. `src/server/authz/routeGuard.ts`માં `LOCAL_ONLY_API_PREFIXES`માં પાથ પ્રીફિક્સ ઉમેરો
2. `tests/unit/authz/routeGuard.test.ts`માં એક ટેસ્ટ ઉમેરો જે ખાતરી કરે કે
   નવા પ્રીફિક્સ માટે `isLocalOnlyPath()` true પરત કરે છે
3. **આ પગલું ક્યારેય છોડશો નહીં** — `CLAUDE.md`માં કડક નિયમ #15 જુઓ
4. નક્કી કરો: શું આ રૂટ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`માં પણ સામેલ થવો જોઈએ?
   ડિફૉલ્ટ જવાબ **ના** છે. રૂટને manage-સ્કોપ ધારક માટે ખુલ્લો મૂકવો સુરક્ષિત હોય
   ત્યારે જ ઑપ્ટ-ઇન કરો (એટલે કે તે વપરાશકર્તા દ્વારા નિયંત્રિત મનસ્વી કોડ spawn કરતો ન હોય).

## manage-સ્કોપ દ્વારા બાયપાસ કરી શકાય તેવો પાથ ઉમેરવો

1. ખાતરી કરો કે રૂટ વપરાશકર્તા દ્વારા પૂરો પાડવામાં આવેલ કોડ અથવા કમાન્ડ ચલાવતો નથી. જો તે
   ચલાવતો હોય, તો અટકો — આ અપવાદ તે માટે યોગ્ય સાધન નથી.
2. `src/server/authz/routeGuard.ts`માં `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` સાથે પ્રીફિક્સ જોડો

## OpenAPIમાં સુરક્ષા ટિયર્સનું દસ્તાવેજીકરણ

`docs/openapi.yaml`માં નવો રૂટ ઉમેરતી વખતે, જો રૂટને `routeGuard.ts` દ્વારા વર્ગીકૃત
કરવામાં આવ્યો હોય, તો અનુરૂપ vendor extension લાગુ કરો:

| routeGuard.ts વર્ગીકરણ       | YAML ઍનોટેશન               | અમલીકરણ                                         |
| ---------------------------- | -------------------------- | ----------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | નોન-લૂપબૅકથી બિનશરતી અવરોધિત                    |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | `requireLogin=false` હોવા છતાં auth આવશ્યક      |
| આંતરિક admin/debug રૂટ       | `x-internal: true`         | ડિફૉલ્ટ રૂપે /dashboard/api-endpointsથી છુપાયેલ |
| કોઈ નહીં (જાહેર / માનક auth) | (કોઈ ઍનોટેશન જરૂરી નથી)    | માનક `requireLogin`-નિયંત્રિત ઍક્સેસ            |

### માન્યતા

બે સ્ક્રિપ્ટ્સ YAML ઍનોટેશન્સ અને `routeGuard.ts` વચ્ચે સુસંગતતા લાગુ કરે છે:

- `scripts/check/check-openapi-coverage.mjs` — કવરેજ < 99% હોય તો નિષ્ફળ થાય છે
- `scripts/check/check-openapi-security-tiers.mjs` — જો `x-loopback-only` અથવા
  `x-always-protected` ઍનોટેશન્સ compile-time કૉન્સ્ટન્ટ્સથી અલગ હોય તો નિષ્ફળ થાય છે

બંને સ્ક્રિપ્ટ્સ pre-commit hook અને CIમાં ચાલે છે.

### False Positive નિયમ

જો `routeGuard.ts` કૉન્સ્ટન્ટમાં ન હોય તેવા રૂટ પર `x-always-protected` અથવા `x-loopback-only`
ઍનોટેટ કરવામાં આવે, તો કવરેજ સ્ક્રિપ્ટ નિષ્ફળ થાય છે. ઉકેલ હંમેશાં YAMLને
`routeGuard.ts` ખરેખર જે લાગુ કરે છે તેની સાથે સંરેખિત કરવાનો છે — અમલીકરણ લૉજિક પણ લાગુ કર્યા વિના
રૂટ્સને `routeGuard.ts`માં ઉમેરવાનો નથી.
