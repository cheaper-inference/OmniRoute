> **સત્યનો સ્રોત:** `src/lib/guardrails/`
> **છેલ્લે અપડેટ:** 2026-10-17 — v3.8.52 ([Coverage and limits](#coverage-and-limits) ઉમેર્યું):
> હૂક્સ કયા રૂટ્સ અને રિસ્પોન્સ પાથ સુધી પહોંચે છે, મર્જ થયેલા ડિસેબલ હેડર્સ (#16412), ફરજિયાત બાઉન્ડરી તરીકે ઇન્જેક્શન
> બ્લોક મોડ (#16413), અને post-call પહેલાં રિસ્પોન્સને શું જુએ છે

Guardrails એ OmniRoute અને અપસ્ટ્રીમ પ્રોવાઇડર્સ વચ્ચેની બાઉન્ડરી પર
સેફ્ટી, પોલિસી અને કન્ટેન્ટ ટ્રાન્સફોર્મેશન લાગુ કરે છે. દરેક guardrail
રિક્વેસ્ટ પેલોડ (`preCall`) અને અપસ્ટ્રીમ રિસ્પોન્સ (`postCall`) ની તપાસ કરી શકે છે (અને
વૈકલ્પિક રીતે નકારી, ટ્રાન્સફોર્મ અથવા એનોટેટ કરી શકે છે).

આ સિસ્ટમ **fail-open** છે: જો કોઈ guardrail એક્ઝિક્યુટ થતી વખતે એરર ફેંકે, તો રજિસ્ટ્રી
એરર રેકોર્ડ કરે છે અને રિક્વેસ્ટ ફેલ કરવાને બદલે આગલા guardrail સાથે ચાલુ રાખે છે.
બ્લોકિંગ એ સ્પષ્ટ નિર્ણય છે (`block: true`), ક્યારેય અકસ્માત નહીં.
એક જ અપવાદ એબોર્ટ થયેલી રિક્વેસ્ટ છે: જ્યારે કૉલરનું `signal` એબોર્ટ થાય છે,
ત્યારે એરર ફેંકતું guardrail સ્કિપ થવાને બદલે હૂક રનને રિજેક્ટ કરે છે.

હૂક્સ દરેક રૂટ કે દરેક રિસ્પોન્સ પર ચાલતા **નથી**. Guardrail પર
સિક્યોરિટી કંટ્રોલ તરીકે આધાર રાખતા પહેલાં
[Coverage and limits](#coverage-and-limits) વાંચો.

## બિલ્ટ-ઇન Guardrails

રજિસ્ટ્રી ઇમ્પોર્ટ પર પ્રાયોરિટી ક્રમમાં છ guardrails ઓટો-લોડ કરે છે
(જુઓ `registry.ts` → `registerDefaultGuardrails()`):

| પ્રાયોરિટી | નામ                 | સ્ટેજ(ો)       | ફાઇલ                  |
| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`       | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`       | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`       | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ઓછા પ્રાયોરિટી નંબર **પહેલા** ચાલે છે.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

GLM 5.3 બેઝ મોડલ અને `glm-5.3-{low,high,max}` પાસે સ્પષ્ટ
`supportsVision:false` રજિસ્ટ્રી/સ્પેક મેટાડેટા છે. GLM 5.3 Flash વેરિઅન્ટ્સ
નેટિવ-વિઝન મોડલ્સ જ રહે છે. Claude Code નો `/v1/messages` રૂટ Claude-to-OpenAI
ટ્રાન્સલેશન **પહેલાં** શેર થયેલી `handleChat` પ્રી-કૉલ guardrail ચેઇનમાં પ્રવેશે છે; નેસ્ટેડ `Read`
ટૂલ-રિઝલ્ટ ઇમેજોનું વર્ણન કરવું અથવા હેન્ડલ કરવું જરૂરી છે
એ ટ્રાન્સલેશન તેમને OpenAI `image_url` કન્ટેન્ટમાં ઉપાડે એ પહેલાં (#17069).

**નોન-વિઝન મોડલ્સ** પર લક્ષ્ય રાખતી ઇમેજ-ધરાવતી રિક્વેસ્ટને ઇન્ટરસેપ્ટ કરે છે અને
કાં તો આખી રિક્વેસ્ટને વિઝન-સક્ષમ મોડલ પર રીરૂટ કરે છે અથવા
અપસ્ટ્રીમ કૉલ પહેલાં ઇમેજ પાર્ટ્સને કન્ફિગરેબલ વિઝન મોડલ દ્વારા બનાવેલા
ટેક્સ્ટ વર્ણનોથી બદલે છે. આ ટેક્સ્ટ-ઓનલી પ્રોવાઇડર્સને
મલ્ટિમોડલ પેલોડ્સ પારદર્શક રીતે હેન્ડલ કરવા દે છે.

ફ્લો:

1. જો ટાર્ગેટ મોડલ પહેલેથી જ વિઝન સપોર્ટ કરતું હોય તો સ્કિપ કરો (સિવાય કે તે
   ફોર્સ્ડ-બ્રિજ લિસ્ટ `isVisionBridgeForcedModel` માં દેખાતું હોય).
2. `extractImageParts(messages)` દ્વારા ઇમેજ પાર્ટ્સ એક્સટ્રાક્ટ કરો
   (`visionBridgeHelpers.ts`), જે `open-sse/utils/mediaParts.ts` માં રહેલા **યુનિફાઇડ મીડિયા
   ડિટેક્ટર** `detectMediaParts()` ને ડેલિગેટ કરે છે — કોમ્બો કમ્પેટિબિલિટી ફિલ્ટર સાથે શેર થયેલો
   સત્યનો એકમાત્ર સ્રોત.
   એક્સટ્રાક્શન એ આકારો સુધી મર્યાદિત છે જેમને `replaceImageParts` પાછા સ્પ્લાઇસ કરી શકે
   (extract↔replace કોન્ટ્રાક્ટ): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"`, અને Responses
   API `input_image`. Claude Code
   `tool_result.content` અને Responses ટૂલ આઉટપુટ્સની અંદર નેસ્ટેડ મેચ થતી ઇમેજો પણ એક્સટ્રાક્ટ થાય છે અને
   તેમના મૂળ પાથ પર રિપ્લેસ થાય છે; ફક્ત-ઇન્ડિકેટર આકારો કોમ્બો-ફિલ્ટર
   મટિરિયલ છે અને એક્સટ્રાક્ટ થતા નથી.
   કોઈ ન મળે તો સ્કિપ કરો.
3. `resolveVisionBridgeRuntimeSettings()` દ્વારા રનટાઇમ કન્ફિગ રિઝોલ્વ કરો
   (`src/shared/constants/modalityBridgeDefaults.ts`): નવી `modalityBridge*`
   સેટિંગ કીઝ જીતે છે; લિગસી `visionBridge*` કીઝ **એક-સાયકલ
   ફોલબેક** (રોલબેક વિન્ડો) તરીકે રહે છે. બ્રિજ ડિસેબલ હોય ત્યારે
   કોઈપણ મીડિયા ટ્રાવર્સલ પહેલાં સ્કિપ કરો.
4. મોડ સિલેક્ટર (`modalityBridgeVisionMode`, નીચેનું કોષ્ટક જુઓ) રીરૂટ વિરુદ્ધ ડિસ્ક્રાઇબ નક્કી કરે છે.
   રીરૂટ ફક્ત `model` સ્વૉપ થયેલું `modifiedPayload` રિટર્ન કરે છે,
   ઉપરાંત મેટા `{ rerouted, fromModel, toModel, imagesKept }`.
5. ડિસ્ક્રાઇબ પાથ: ઇમેજોને `maxImages` પર કેપ કરો, ટાસ્ક-અવેર પ્રોમ્પ્ટ બનાવો,
   ડિસ્ક્રાઇબ કેશ તપાસો, વિઝન મોડલને **પેરેલલમાં**
   (`Promise.allSettled`) કૉલ કરો, અને તેમની જગ્યાએ `[Image N]: <description>` ટેક્સ્ટ પાર્ટ્સ
   ઇન્જેક્ટ કરો. નિષ્ફળ ડિસ્ક્રાઇબ `null` આપે છે: અજ્ઞાત/વિઝન-સક્ષમ ટાર્ગેટ્સ માટે કાચી ઇમેજ જાળવી રાખવામાં આવે છે
   (#4012), પરંતુ **કન્ફર્મ થયેલ ટેક્સ્ટ-ઓનલી ડાયરેક્ટ ટાર્ગેટ** અથવા ઝીરો-વિઝન કોમ્બોને દરેક અવર્ણિત ઇમેજ માટે સ્પષ્ટ
   `(unavailable — no vision-capable provider connected)` ટેક્સ્ટ સ્ટબ મળે છે,
   આંશિક નિષ્ફળતાઓ અને ડિસ્ક્રાઇબ-કૉલ કેપની બહારની ઇમેજો સહિત (#17069). હાલનો ઓલ-ફેલ્ડ કોમ્બો ડિસ્ક્રાઇબ ફોલબેક
   યથાવત રહે છે (#8430).
6. `modifiedPayload` + મેટા (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) રિટર્ન કરો.

#### મોડ સિલેક્ટર (`modalityBridgeVisionMode`)

| મોડ        | ડિફોલ્ટ | વર્તન                                                                                                                                                                                                                                                                                 |
| ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | લેગસી હ્યુરિસ્ટિક, અછાંત (#6640/#7204): non-combo/`auto/` મોડલ્સ શ્રેષ્ઠ વિઝન મોડલ પર રીરાઉટ થાય છે સિવાય કે મૂળ મોડલ પાસે પહેલેથી જ ઉપયોગી ક્રેડેન્શિયલ્સ હોય (પછી describe); combo ટાર્ગેટ્સ હંમેશા describe કરે છે.                                                                |
| `describe` |         | હંમેશા describe — રીરાઉટ બ્લોક સંપૂર્ણપણે સ્કિપ થાય છે; વપરાશકર્તાનું પસંદ કરેલું મોડલ હંમેશા જવાબ આપે છે.                                                                                                                                                                            |
| `reroute`  |         | ફોર્સ રીરાઉટ: keep-credentialed-model ગાર્ડ બાયપાસ થાય છે. રીરાઉટ-**ટાર્ગેટ** ક્રેડેન્શિયલ ગાર્ડ હજુ લાગુ પડે છે — જ્યારે કોઈ ઉપયોગી વિઝન ટાર્ગેટ અસ્તિત્વમાં ન હોય, ત્યારે બ્રિજ describe કરવાને બદલે અથવા text-only ટાર્ગેટને રો ઇમેજીસ મોકલવાને બદલે સ્પષ્ટ એરર સાથે બ્લોક કરે છે. |

ફોર્સ્ડ મોડ્સ auto હ્યુરિસ્ટિક ચાલે તે **પહેલાં** શોર્ટ-સર્કિટ થાય છે; `auto`
વર્તન pre-PR-1 ગાર્ડરેલ સાથે બાઇટ-એકસમાન છે.

#### API-કી સ્કોપ (`visionBridgeKeyScope.ts`)

જ્યારે કોલરની API કી `allowedConnections`, ક્વોટા પૂલ્સ
(`allowedQuotas`) અથવા મોડલ્સ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) ને મર્યાદિત કરે છે, ત્યારે બ્રિજ ફક્ત એવા
reroute અને describe મોડલ્સ પસંદ કરે છે જેનો કી ઉપયોગ કરી શકે, એવા કનેક્શન્સ પર જેનો કી ઉપયોગ
કરી શકે. describe કોલ પછી હંમેશા `x-omniroute-self-loop-key-id` હેડર સાથે
OmniRoute self-loop મારફતે જાય છે, જેથી પ્રાપ્ત થતી ચેટ રિક્વેસ્ટ
તે કીની કનેક્શન અને મોડલ પોલિસી ફરીથી લાગુ કરે. `enforceApiKeyPolicy()`
તે હેડરને ફક્ત self-loop bearer સાથે મળીને જ સ્વીકારે છે, જેથી તે ફક્ત
ઍક્સેસ સાંકડી શકે, અને જે id રિઝોલ્વ થતી ન હોય તે રિજેક્ટ થાય છે.

જો કી માટે કોઈ વિઝન મોડલ પરવાનગીયુક્ત ન હોય, તો **કન્ફર્મ્ડ text-only
ટાર્ગેટ** ઇમેજ બાઇટ્સને અસમર્થ upstream પર ફોરવર્ડ કરવાને બદલે
સ્પષ્ટ HTTP 400 સાથે ઇમેજ રિક્વેસ્ટને સ્થાનિક રૂપે રિજેક્ટ કરે છે (#17069). અજ્ઞાત અથવા નેટિવ વિઝન ક્ષમતા ધરાવતા
ટાર્ગેટ્સ માટે, describe પાથ તેનું અગાઉનું
fail-open વર્તન જાળવી રાખે છે (મેટા `{ skipped: true, reason: "no_permitted_vision_model" }`).
કી વિનાની રિક્વેસ્ટ્સ, અને આ મર્યાદાઓ વિનાની કીઓ, બરાબર
પહેલાં જેમ વર્તે છે.

#### ટાસ્ક-અવેર describe પ્રોમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફોલ્ટ **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) બેઝ
describe પ્રોમ્પ્ટ પર **છેલ્લા યુઝર મેસેજ**નો ટેક્સ્ટ (500 અક્ષરો સુધી ટ્રંકેટેડ)
ઉમેરે છે, જે વર્ણનને વપરાશકર્તાએ ખરેખર જે પૂછ્યું તે દિશામાં દોરે છે
(codex-vision-proxy પેટર્ન) અને વિઝન મોડલને દૃશ્યમાન
ટેક્સ્ટ ટ્રાન્સક્રાઇબ કરવા કહે છે. ફ્લેગ બંધ હોય તો — અથવા યુઝર ટેક્સ્ટ ન હોય તો —
બેઝ પ્રોમ્પ્ટ અપરિવર્તિત વપરાય છે.

describe self-loop ની પોતાની OpenAI-સુસંગત રિક્વેસ્ટ (`visionBridgeHelpers.ts` માં
`callVisionModelSingle()`) હંમેશા `image_url.detail: "high"` માંગે છે —
નિઃશરત રીતે, દરેક કોલર/પ્રોવાઇડર માટે, કોઈપણ ક્લાયન્ટ સિગ્નલ પર ગેટેડ વિના.
લો-ડિટેઇલ સેમ્પલિંગ OCR ચોકસાઈને બગાડે છે ઠીક એ જ ટેક્સ્ટ-ટ્રાન્સક્રિપ્શન
ટાસ્ક માટે જે આ પ્રોમ્પ્ટ માંગે છે, તેથી describe કોલ પોતે હંમેશા હાઈ
ડિટેઇલ માંગે છે, મૂળ ઇનબાઉન્ડ રિક્વેસ્ટે જે ડિટેઇલ લેવલ વાપર્યું હોય તેને અલગ રાખીને. આ
ફક્ત આંતરિક describe રિક્વેસ્ટ બોડીને અસર કરે છે; તે OmniRoute કોલરના પોતાના
`image_url.detail` ને પ્રાઇમરી રિક્વેસ્ટ પર કેવી રીતે ફોરવર્ડ કરે છે તે બદલતું નથી —
તે ડિફોલ્ટ અલગથી લાગુ થાય છે, અને ફક્ત ડિટેક્ટ થયેલા OpenCode ક્લાયન્ટ્સ માટે,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) માં. describe self-loop ની
Anthropic wire-format બ્રાન્ચમાં કોઈ `detail` ફીલ્ડ નથી
અને બંને ડિફોલ્ટ્સથી તે અસરગ્રસ્ત નથી.

#### Describe આઉટપુટ કેપ (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફોલ્ટ | રેન્જ              |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફોલ્ટ) નો અર્થ **કોઈ કેપ નહીં** — `callVisionModel()` દ્વારા પરત કરેલું
વર્ણન અપરિવર્તિત પાસ થાય છે, હાલનું
વર્તન જાળવી રાખીને. 100–50000 રેન્જમાં કોઈપણ મૂલ્ય વર્ણનને
`…` સફિક્સ સાથે ટ્રંકેટ કરે છે, તે `[Image N]: <description>`
તરીકે પાછું સ્પ્લાઇસ થાય તે પહેલાં
(`src/lib/guardrails/visionBridge.ts` માં `VisionBridgeGuardrail.preCall()`).
ડિટેઇલ-હેવી OCR ટાસ્ક્સ માટે આ વધારો જ્યાં ડાઉનસ્ટ્રીમ મોડલને
સંપૂર્ણ ટ્રાન્સક્રિપ્શન જોઈએ છે; વાતુક વિઝન મોડલ્સ પર ટોકન વપરાશ મર્યાદિત કરવા માટે તે ઘટાડો.
ડેશબોર્ડ ફીલ્ડ Vision ટેબના Advanced પેનલ પર રહે છે
(`ModalityBridgeVisionTab.tsx` માં `modality-bridge-max-chars`) અને
1 થી 99 વચ્ચેનું કોઈપણ મૂલ્ય 100 ફ્લોર સુધી ક્લેમ્પ કરે છે, જ્યારે સ્પષ્ટ `0`
ને અછાંત રાખે છે — `0` પોતાના અધિકારમાં માન્ય Zod મૂલ્ય છે
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), માત્ર
"unset" ડિફોલ્ટ નહીં.

#### Describe કેશ (`modalityBridge/bridgeCache.ts`)

describe આઉટપુટ્સ માટે ઇન-મેમરી LRU + TTL કેશ, પ્રોસેસ-વાઇડ શેર્ડ.
કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)`
લેન્થ-પ્રિફિક્સ ફ્રેમિંગ સાથે (કોઈ ફીલ્ડ-બાઉન્ડરી કોલિઝન નહીં). મોડલ ઘટક એ
**કન્ફિગર્ડ** બ્રિજ મોડલ છે, ખરેખર જવાબ આપનારું મોડલ નહીં —
`callVisionModel` આંતરિક રીતે ફોલ બેક થઈ શકે છે, અને દરેક પ્રયાસ પ્રમાણે કીંગ
કેશને ફ્રેગમેન્ટ કરી દે. નિષ્ફળ describes ક્યારેય કેશ થતા નથી. સેટિંગ્સ:

| કી                              | ડિફોલ્ટ | રેન્જ   |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ ઈમેજ નોર્મલાઈઝેશન (સેલ્ફ-લૂપ describe/base64 ફેચ)

જ્યારે બ્રિજ જાતે જ કોઈ **રિમોટ** ઈમેજ ફેચ કરે છે — Anthropic describe
સેલ્ફ-કૉલ અને claude-wire-format base64 રૂપાંતરણ
(`ensureBase64ImagesForClaudeWire`), બંને `visionBridgeHelpers.ts` માં
`fetchRemoteImageAsDataUri()` મારફતે — પરિણામી data
URI વિઝન-મોડલ રિક્વેસ્ટમાં એમ્બેડ થાય તે પહેલાં `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) મારફતે પસાર થાય છે. વધુ પડતી મોટી
ઈમેજો **2048px લાંબી ધાર** સુધી ડાઉનસ્કેલ થાય છે (OpenAI/Anthropic સર્વર-સાઈડ
પહેલેથી લાગુ કરે છે તે resize કેપને મેળ ખાતું), જે વિઝન મોડલ જે જુએ છે તે બદલ્યા
વિના અપલોડ બાઈટ્સ/લેટન્સી ઘટાડે છે. રીસાઈઝિંગ `sharp` વાપરે છે, જે ડાયનેમિક
ઈમ્પોર્ટ દ્વારા લોડ થાય છે: જે પ્લેટફોર્મ પર તેનું નેટિવ
બાઈનરી લોડ થવામાં નિષ્ફળ જાય, ત્યાં `normalizeDataUri()` **ક્યારેય throw કરતું
નથી** — તે મૂળ બાઈટ્સના પાસથ્રુ પર પાછું ફરે છે, જેથી describe/base64-રૂપાંતરણ
પાથ હંમેશા કાર્યરત રહે. નોન-ઈમેજ બાઈટ્સ (એવી ફેચ જે ડીકોડ કરી શકાય તેવી
ઈમેજ પરત કરતી નથી) પણ વિના સ્પર્શે પાસથ્રુ થાય છે. આ નોર્મલાઈઝેશન ફક્ત એ જ
ઈમેજો માટે સ્કોપ થયેલું છે જે બ્રિજ પોતાના સેલ્ફ-કૉલ માટે ફેચ કરે છે — તે
કૉલરના રૉ પાસથ્રુ પેલોડ પર ક્યારેય લાગુ કરવામાં આવતું નથી, જે
opt-in-only મ્યુટેશન સિદ્ધાંત (હાર્ડ રૂલ #20) સાથે સુસંગત છે.

`visionBridge*` વેલ્યુઝને અનુરૂપ નવી કીઝ પર કોપી કરે છે (idempotent, ઓપરેટર-સેટ

#### ટ્રાન્સપેરન્સી હેડર + સ્ટેટ્સ

Describe-ટ્રાન્સફોર્મ થયેલા રિસ્પોન્સ સાથે
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
હોય છે (`modalityBridge/bridgeStats.ts` માં `buildModalityBridgeHeader()` દ્વારા બનાવેલ,
`src/sse/handlers/chatHelpers.ts` માં `withModalityBridgeHeader()` દ્વારા સ્ટેમ્પ કરેલ).
રીરાઉટ થયેલી રિક્વેસ્ટ્સને **કોઈ હેડર મળતું નથી** — પેલોડ અસ્પર્શિત હતો
અને મોડલ સ્વૉપ રિસ્પોન્સ બોડીના `model` ફીલ્ડમાં પહેલેથી જ દેખાય છે.

`GET /api/modality-bridge/stats` (મેનેજમેન્ટ ઓથ, `GET /api/settings` જેવું જ
ટાયર) `vision`, `audio` અને `video` માટે ઈન-મેમરી પ્રતિ-મોડાલિટી
કાઉન્ટર્સ `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` પરત કરે છે.
`averageLatencyMs` તેના ડિનોમિનેટર તરીકે બધા attempts નહીં, પણ `latencySamples`
વાપરે છે; ટાઈમિંગ વગરનું ઓપરેશન શૂન્ય-મિલિસેકન્ડ સેમ્પલ ફેબ્રિકેટ કરતું
નથી. `bridged` સફળ રૂપાંતરણો માટે બેકવર્ડ-કમ્પેટિબલ એલિયાસ રહે છે;
નિષ્ફળ પ્રયાસો તેને ઈન્ક્રિમેન્ટ કરતા નથી.
પ્રોસેસ રીસ્ટાર્ટ પર કાઉન્ટર્સ ડિઝાઈન મુજબ રીસેટ થાય છે
(એકાઉન્ટિંગ નહીં, ટેલિમેટ્રી).

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ઓડિયો ધરાવતી ચેટ રિક્વેસ્ટ્સને એવા ટાર્ગેટ સુધી પહોંચે તે પહેલાં
ઈન્ટરસેપ્ટ કરે છે જે ઓડિયો ઈનપુટ સ્વીકારતું હોવાનું જાણીતું નથી. તે ચેટ
રિક્વેસ્ટને ક્યારેય રીરાઉટ કરતું નથી: ઓડિયો પાર્ટ્સ હાલના
OpenAI-કમ્પેટિબલ મલ્ટિપાર્ટ એન્ડપોઈન્ટ મારફતે ટ્રાન્સક્રાઈબ થાય છે અને પસંદ કરેલું
ચેટ મોડલ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ્સ સાથે આગળ ચાલુ રહે છે.

ફ્લો:

1. `getResolvedModelCapabilities()` દ્વારા `supportsAudio` ઉકેલો. સ્પષ્ટ પ્રોવાઇડર-રજિસ્ટ્રી મેટાડેટાને પ્રાથમિકતા મળે છે, પછી સ્ટેટિક મોડેલ મેટાડેટા, પછી સિંક કરેલું
   `modalities_input`. `audio` વગરની જાહેર કરેલી ઇનપુટ સૂચિ `false` છે; કોઈ ક્ષમતા પુરાવો ન હોય તો
   `null` જ રહે છે. `false` અને `null` બંને કન્ઝર્વેટિવ બ્રિજ સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સ ઉકેલો અને શેર કરેલા `detectMediaParts()` ડિટેક્ટર દ્વારા દરેક મેસેજમાંથી સ્પ્લાઇસ કરી શકાય તેવા ટોપ-લેવલ
   ઓડિયો પાર્ટ્સ કાઢો. સપોર્ટેડ વાયર આકારો OpenAI `input_audio`, `audio_url`, અને
   `source.media_type: "audio/*"` છે. નેસ્ટેડ ઓડિયો રાઉટિંગ માટે શોધવામાં આવે છે પરંતુ સ્પ્લાઇસ પાથ દ્વારા દૂર કરવામાં આવતું નથી. કામ `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે;
   પછીના પાર્ટ્સ અછૂતા રહે છે.
3. ગોઠવેલા `provider/model` ને માન આપો, અથવા `selectAudioBridgeModel()` ને
   `AUDIO_TRANSCRIPTION_PROVIDERS` માં સ્થિર કેટલોગ ક્રમમાં ફરવા દો અને ઉપયોગમાં લઈ શકાય તેવું સક્રિય પ્રોવાઇડર ક્રેડેન્શિયલ ધરાવતું પ્રથમ
   મોડેલ પસંદ કરવા દો.
4. `callAudioTranscription()` base64/data-URI ઓડિયોને multipart
   `file` માં રૂપાંતરિત કરે છે, અથવા DNS પિનિંગ અને 25 MB મર્યાદા સાથે public-only આઉટબાઉન્ડ
   ગાર્ડ દ્વારા રિમોટ `audio_url` ડાઉનલોડ કરે છે. પછી તે ફાઇલ અને પસંદ કરેલું
   મોડેલ લોકલ `/v1/audio/transcriptions` સેલ્ફ-લૂપ પર POST કરે છે, જે
   `resolveSelfLoopBearer()` થી ઓથેન્ટિકેટ થાય છે. હાલનો ટ્રાન્સક્રિપ્શન રાઉટ સામાન્ય
   ક્રેડેન્શિયલ લુકઅપ, કૂલડાઉન/રેટ-લિમિટ હેન્ડલિંગ, અને પ્રોવાઇડર ડિસ્પેચ કરે છે.
5. સફળ કોલ્સ તેમના પાર્ટ્સને `[Audio N]: <transcript>` થી બદલે છે. કોલ્સ
   `Promise.allSettled` સાથે ચાલે છે: વ્યક્તિગત નિષ્ફળતા તે મૂળ
   ઓડિયો પાર્ટ જાળવી રાખે છે (#4012 કોન્ટ્રાક્ટ). જો દરેક કોલ નિષ્ફળ જાય અને ટાર્ગેટ સાબિત થયેલું
   `supportsAudio === false` હોય, તો પાર્ટ્સ
   `[Audio N]: (unavailable — no STT provider connected)` બની જાય છે (#8430 કોન્ટ્રાક્ટ).
   અજ્ઞાત ટાર્ગેટ (`null`) માટે, સંપૂર્ણ-નિષ્ફળતાનું પરિણામ અછૂતું રહે છે. ઉપયોગમાં લઈ શકાય તેવું STT ક્રેડેન્શિયલ વિનાનું સાબિત
   થયેલું ટેક્સ્ટ-ઓનલી ટાર્ગેટ નેટવર્ક કોલ કર્યા વિના જ સમાન સ્પષ્ટ સ્ટબ મેળવે છે.

સફળ ટ્રાન્સક્રિપ્ટ પ્રોસેસ-વ્યાપી Modality Bridge LRU/TTL કેશનો ઉપયોગ કરે છે. કી
ઓડિયો સંદર્ભ, સ્થિર `audio-transcription` ઓપરેશન
લેબલ, અને પસંદ કરેલું STT મોડેલ જોડે છે; નિષ્ફળતાઓ ક્યારેય કેશ થતી નથી. ઓડિયો પ્રયાસો
શેર કરેલા `bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર અપડેટ કરે છે.
રૂપાંતરિત રિસ્પોન્સ
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` વહન કરે છે; અછૂતી
રિક્વેસ્ટને Audio Bridge સેગમેન્ટ મળતું નથી.

### વિડીયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ચેટ કમ્પ્લીશન્સ `messages` માં ટોપ-લેવલ વિડીયો પાર્ટ્સને ઇન્ટરસેપ્ટ કરે છે અને API `input` જાણીતા નેટીવ વિડીયો સપોર્ટ વગરના ટાર્ગેટને બોલાવવામાં આવે તે પહેલા પ્રતિસાદ આપે છે. સપોર્ટેડ આકારો `input_video`, `video_url`, `video_source`, HTTPS URLs, અને `data:video/*;base64,...` ડેટા URIs છે. ટેક્સ્ટમાં સાદા ફાઇલનામોને વિડિયો તરીકે ગણવામાં આવતા નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતી ટ્રાવર્સલ, capability/policy ચેક, પ્રતિ-વિનંતી એકત્રીકરણ અને પ્રતિભાવ પેલોડની માલિકી ધરાવે છે. પ્રતિ-વિડિયો કાર્ય — સંપાદન, સંપૂર્ણ-પરિણામ કેશ, ફ્રેમ ક્રમનું વર્ણન કરતી (જે કોઈપણ કોલર-ઘોષિત ઑડિઓ ટ્રાન્સક્રિપ્ટને ફ્યુઝ કરે છે), અને પ્રતિ-પ્રયાસ metrics/abort/cleanup — `videoBridgePipeline.ts` માં `processVideoPart` પાછળ છુપાયેલ છે, જેને `preCall` ના લૂપની અંદર વિડિઓ ભાગ દીઠ એકવાર કહેવાય છે. તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓ `VideoMediaBrokerPort` (બાઇટ્સ મેળવવી અને નમૂનારૂપ ફ્રેમ્સ કાઢવા), `VideoAudioTranscriptionPort` (સેમ્પલ કૅપ્શન્સ સાથે કૉલર-ઘોષિત ઑડિઓ ટ્રાન્સક્રિપ્ટને ફ્યુઝ કરીને), અને `VideoDrilldownPort` (લેગસી કાચો-સ્ટોર આકાર) પણ વ્યાખ્યાયિત કરે છે. ઉત્પાદન STT અને ફ્રેમ રીટેન્શન `createVideoSttAdapter` અને `createVideoDrilldownAdapter` દ્વારા વર્ણન કરતા પોર્ટની આસપાસ બનેલું છે; બાદમાં વહેંચાયેલ અપારદર્શક-હેન્ડલ જીવનચક્રનો ઉપયોગ કરે છે.

સાર્વજનિક `/v1` વિનંતી પાથ ક્યારેય સબપ્રોસેસની આયાત અથવા વિનંતી કરતું નથી. રિમોટ વિડિયોઝ 50 MiB બાઉન્ડ હેઠળ ડાઉનલોડ થાય છે; ઇનલાઇન બેઝ64 વિડિયોઝમાં રૂઢિચુસ્ત 36 MiB ડીકોડેડ પ્રતિ-વિડિયો કેપ હોય છે જેથી model/messages/framing એન્વલપ 50 MiB ની જાહેર JSON વિનંતીની પ્રવેશ મર્યાદાની અંદર રહી શકે. ફાળવણી પહેલાં ઇનલાઇન લંબાઈ અને ડીકોડેડ-કદના અંદાજો તપાસવામાં આવે છે. DNS પિનિંગ સાથે હાલના પબ્લિક-ઓન્લી આઉટબાઉન્ડ ગાર્ડનો ઉપયોગ કરીને પ્રારંભિક રિમોટ URL અને દરેક રીડાયરેક્ટ પર HTTPS જરૂરી છે. પછી બાઇટ્સ ચોક્કસ આંતરિક `POST /api/modality-bridge/video/extract` બ્રોકર સીમાને પાર કરે છે. તે રૂટ `LOCAL_ONLY` અને `SPAWN_CAPABLE` બંને છે, માત્ર પ્રતિ-પ્રક્રિયા પ્રમાણિત, વિશ્વસનીય-લૂપબેક વિનંતી સ્વીકારે છે, અને ક્યારેય URL, ફાઇલસિસ્ટમ પાથ, એક્ઝેક્યુટેબલ અથવા દલીલ સૂચિને સ્વીકારતું નથી. API બોડી-સાઇઝ પાઇપલાઇન અને હેન્ડલરના ઇન્ક્રીમેન્ટલ બોડી રીડર સ્વતંત્ર રીતે 50 MiB બ્રોકર ઇનપુટ કેપ લાગુ કરે છે. તેની બાઉન્ડેડ કતાર એક સમયે એક નિષ્કર્ષણ ચલાવે છે, ચાર બાકી નોકરીઓને મંજૂરી આપે છે અને 100 MiB પર પેન્ડિંગ ઇનપુટ કેપ્સ કરે છે.

બ્રોકરની અંદર, `ffprobe` ખાનગી સ્થાનિક ફાઇલ વાંચે છે; નિશ્ચિત ફોર્મેટ મંજૂર સૂચિમાં પ્લેલિસ્ટ અને મેનિફેસ્ટ ફોર્મેટનો સમાવેશ થતો નથી. મંજૂર MOV-ફેમિલી કન્ટેનર માટે, બાહ્ય MOV ડેટા સંદર્ભો ડિફૉલ્ટ રૂપે અક્ષમ રહે છે, અને નિશ્ચિત આદેશ તેમને પસંદ કરતું નથી. `ffprobe` અને `ffmpeg` બંને `file` -only પ્રોટોકોલ વ્હાઇટલિસ્ટ, એક થ્રેડ, નિશ્ચિત દલીલ એરે, કોઈ શેલ અને `PATH` માંથી ઉકેલાયેલ એક્ઝિક્યુટેબલનો ઉપયોગ કરે છે. જોડાયેલ-ચિત્ર કવર સ્ટ્રીમ રમવા યોગ્ય ઉમેદવારો નથી. તમામ વગાડવા યોગ્ય સ્ટ્રીમ્સે મર્યાદાઓ સંતોષવી આવશ્યક છે, અને નિર્ણાયક સૌથી નીચા-ઇન્ડેક્સ ફોલબેક પહેલાં સ્પષ્ટ ડિફોલ્ટ સ્ટ્રીમ પસંદ કરવામાં આવે છે. વિડિઓઝ 600 સેકન્ડ, 8,192 પિક્સેલ્સ પ્રતિ પરિમાણ અને 33,554,432 સ્રોત પિક્સેલ્સ સુધી મર્યાદિત છે. FFmpeg સેમ્પલ 1-16 મિડપોઇન્ટ JPEG ફ્રેમ્સ, નાના ઇનપુટ્સને અપસ્કેલ કર્યા વિના લાંબા કિનારે મહત્તમ 1,024 પિક્સેલ સુધી સ્કેલ કરે છે, અને ક્યારેય URL પ્રાપ્ત કરતું નથી. સેમ્પલિંગ મૂળભૂત રીતે `uniform` છે. વૈકલ્પિક `scene_aware` અને પ્રાયોગિક `segment_aware` નીતિઓ પહેલાથી જ માન્ય સ્થાનિક સ્ટ્રીમ પર એક વધારાનો નિશ્ચિત FFmpeg પાસ કરે છે, બાઉન્ડેડ `showinfo` સીન ટાઇમસ્ટેમ્પ પસંદ કરે છે અને ડિટેક્ટર નિષ્ફળતા, સમયસમાપ્તિ, દૂષિત આઉટપુટ અથવા ખાલી ઉમેદવાર સેટ પર સમાન સમાન મધ્યબિંદુઓ પર નિશ્ચિતપણે પાછા ફરે છે. સેગમેન્ટ-અવેર મોડ માન્ય દ્રશ્ય અંતરાલો માટે પ્રમાણસર મધ્યબિંદુ નમૂનાઓ ફાળવે છે; સેગમેન્ટ-અવેર પુરાવા અને ફોલબેક વર્તન નીચે વિગતવાર છે. હાર્ડ 16-ફ્રેમ કેપ દરેક પોલિસીમાં પસંદગી પછી લાગુ કરવામાં આવે છે. જ્યારે દ્રશ્ય-જાગૃત વિનંતીમાં માત્ર એક-ફ્રેમ બજેટ હોય છે, ત્યારે તે સક્રિય પૂર્ણ-વિડિયો અથવા ફોકસ વિન્ડોના સમાન મધ્યબિંદુનો ઉપયોગ કરે છે અને `policyEffective: uniform` નો અહેવાલ આપે છે: એક પસંદ કરેલ દ્રશ્ય ફ્રેમ બંને ટેમ્પોરલ છેડાને સાચવી શકતી નથી. કોલર વૈકલ્પિક રીતે મર્યાદિત ફોકસ વિન્ડો પ્રદાન કરી શકે છે (`start`/`end` સેકન્ડ્સ); બાઉન્ડ્સને મીડિયા અવધિ સાથે ક્લેમ્પ કરવામાં આવે છે, વિપરીત અથવા બિન-મર્યાદિત વિંડોઝને નકારી કાઢવામાં આવે છે, અને તમામ નમૂના નીતિઓ સામાન્ય અંતરાલની અંદર જ કરવામાં આવે છે. પરિણામી વિન્ડો સેમ્પલિંગ મેટાડેટામાં અને અવિશ્વસનીય વર્ણન ઉપસર્ગમાં સમાવવામાં આવેલ છે જેથી ડાઉનસ્ટ્રીમ મોડલ્સ સંપૂર્ણ સમયરેખામાંથી કેન્દ્રિત અવતરણને અલગ કરી શકે.

સિમેન્ટીક કૅપ્શન ફોકસ એ એક અલગ, સ્પષ્ટ સેટિંગ છે. ડિફૉલ્ટ `full` પૃથ્થકરણ મોડ હાલના ફ્રેમ પ્રોમ્પ્ટને સાચવે છે અને વિનંતીના ટેક્સ્ટને કૅપ્શન મોડલમાં ક્યારેય ફોરવર્ડ કરતું નથી. `focused` મોડમાં, બ્રિજ એ જ ચેટ અથવા રિસ્પોન્સ કન્ટેનરમાંથી ફક્ત નવીનતમ બિન-ખાલી વપરાશકર્તા-લેખિત `text`/`input_text` વાંચે છે, તેને NFC પર સામાન્ય બનાવે છે, નિયંત્રણ અક્ષરો અને વ્હાઇટસ્પેસને સંકુચિત કરે છે, અને તેને 500 યુનિકોડ કોડ પોઇન્ટ્સ સુધી મર્યાદિત કરે છે. ખાલી પરિણામ ચોક્કસ `full` પ્રોમ્પ્ટ પર પાછું આવે છે. સમર્પિત અવિશ્વસનીય-વપરાશકર્તા-સંદર્ભ બ્લોકમાં ઉપયોગ કરી શકાય તેવા સંકેતને JSON તરીકે ક્રમાંકિત કરવામાં આવે છે અને તે માત્ર અવલોકનક્ષમ વિગતોને પ્રાથમિકતા આપી શકે છે; તે મીડિયામાં દેખાતી અથવા સાંભળી શકાય તેવી નીચેની સૂચનાઓ સામે અલગ ચેતવણીને ઓવરરાઇડ કરી શકતી નથી. ટેક્સ્ચ્યુઅલ ફોકસ ક્યારેય `start`/`end` અનુમાન કરતું નથી અથવા ટેમ્પોરલ સેમ્પલરમાં ફેરફાર કરતું નથી.

#### FU-07 માળખાકીય સેગમેન્ટ પુરાવા

`segment_aware` પહેલાથી જ માન્ય સ્થાનિક વિડિયો સ્ટ્રીમ પર એક બાઉન્ડેડ પૂર્વ-વિશ્લેષણ પાસનો ઉપયોગ કરે છે. ફિક્સ્ડ ફિલ્ટર ચેઇન પહેલા વધુમાં વધુ 320 પિક્સેલ્સ પહોળાઈ સુધી સ્કેલ કરે છે, દ્રશ્ય ફેરફારો અને સ્થિર અંતરાલોને શોધે છે, પછી અસ્પષ્ટતા, સરેરાશ લુમા અને spatial/temporal માહિતી માટે 1 ફ્રેમ પ્રતિ સેકન્ડના દરે નમૂનાઓ. પાસ 600 માળખાકીય નમૂનાઓ, એક FFmpeg/filter થ્રેડ, સમાન `file` -only પ્રોટોકોલ અને કન્ટેનર મંજૂર સૂચિઓ, 1 MiB પ્રક્રિયા-આઉટપુટ બાઉન્ડ અને બ્રોકરના શેર કરેલ abort/deadline. ની અંદર વધુમાં વધુ 30 સેકન્ડ સુધી મર્યાદિત છે તે ક્યારેય આદેશ, ફિલ્ટર, પાથ અથવા URL તરફથી વિનંતી સ્વીકારતું નથી.

માળખાકીય મૂલ્યો નિર્ણાયક નમૂનાના પુરાવા છે, સિમેન્ટીક વિડિયો સમજણ નથી. તેઓ વિષયો, ક્રિયાઓ, કૅપ્શન્સ, ભાષણ અથવા વપરાશકર્તાના ઉદ્દેશ્યનું અનુમાન કરતા નથી. દ્રશ્ય અને સ્થિર સીમાઓ વિભાગો બનાવે છે; ફ્રીઝ કવરેજ, અસ્પષ્ટતા, એક્સપોઝર, અવકાશી વિગતો અને ટેમ્પોરલ ફેરફાર ફક્ત વર્તમાન 1-16 ફ્રેમ બજેટને કેવી રીતે ફાળવવામાં આવે છે તે પ્રભાવિત કરે છે. સંપૂર્ણ સ્થિર સેગમેન્ટને એક ફ્રેમ પર કેપ કરવામાં આવે છે, જ્યારે નોન-ફ્રોઝન સેગમેન્ટ બાકીના બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓ ફ્રેમની સંખ્યા કરતાં વધી જાય છે, ત્યારે સમાન સમયરેખા કવરેજ જાળવી રાખવામાં આવે છે જેથી ઝડપી પ્રારંભિક કાપ લાંબા પાછળના ભાગને છુપાવી શકતા નથી. ફ્રીઝ બાઉન્ડ્રીના 1-સેકન્ડના વિશ્લેષણ રિઝોલ્યુશનની અંદર સીન સીમાઓ એકસાથે કરવામાં આવે છે.

ગુમ થયેલ ફિલ્ટર્સ, malformed/empty પુરાવા, ડિટેક્ટર ભૂલ અથવા બાઉન્ડેડ પૂર્વ-વિશ્લેષણ સમયસમાપ્તિ ચોક્કસ યુનિફોર્મ મિડપોઇન્ટ નીતિ માટે નિષ્ફળ જાય છે. કોલર એબોર્ટ અથવા બ્રોકર ડેડલાઈન ખુલ્લી નિષ્ફળ જતી નથી: તે ઇન-ફ્લાઇટ સબપ્રોસેસને સમાપ્ત કરે છે, પછીથી ફ્રેમ નિષ્કર્ષણ અટકાવે છે, અને ખાનગી કામચલાઉ વૃક્ષ `finally` માં દૂર કરવામાં આવે છે.

`scripts/perf/video-bridge-fu07-eval.ts` પોસ્ટ-ડેડઅપ કૅપ્શન-કોલ બચત, ગાઢ-મોશન બજેટ ફાળવણી, blur/exposure/SI-TI પુરાવા, લાંબી પૂંછડી સાથે ઝડપી કટ અને ધીમે ધીમે ફેડ ખોટા હકારાત્મક માટે નિર્ણાયક વાસ્તવિક FFmpeg ફિક્સર જનરેટ કરે છે. તે પૂર્વ-વિશ્લેષણ દિવાલ સમય અને જ્યાં `/usr/bin/time` ઉપલબ્ધ છે ત્યાં ચાઇલ્ડ CPU અને પીક RSS રેકોર્ડ કરે છે. તેની ગુણવત્તાની તપાસ માત્ર માળખાકીય ઓરેકલ્સ છે. વાસ્તવિક કૅપ્શન-મૉડલ ગુણવત્તા `HOLD` રહે છે કારણ કે આ હાર્નેસ પાસે કોઈ અધિકૃત અંતિમ બિંદુ અથવા સ્થિર ન્યાયાધીશ નથી. નાણાકીય બચત પણ `HOLD` રહે છે સિવાય કે `--caption-cost-per-call-usd` સ્પષ્ટ હકારાત્મક પ્રતિ-કોલ અંદાજ પૂરો પાડે છે; સ્ક્રિપ્ટ ક્યારેય પરિણામ બનાવતી નથી.

દરેક ફ્રેમ 4 MiB સુધી મર્યાદિત છે, બધી કાચી ફ્રેમ એકસાથે 23 MiB સુધી અને સીરીયલાઇઝ્ડ બ્રોકર પ્રતિસાદ 32 MiB સુધી છે. ખાનગી કામચલાઉ ડિરેક્ટરી `finally` માં દૂર કરવામાં આવે છે. OmniRoute FFmpeg બંડલ કરતું નથી અને કસ્ટમ એક્ઝેક્યુટેબલ પાથ સ્વીકારતું નથી. કૅપ્શન આપતા પહેલા, બ્રિજ એક રૂઢિચુસ્ત વિઝ્યુઅલ ડિડપ્લિકેશન પાસ લાગુ કરે છે: દરેક JPEG 16 × 16 ગ્રેસ્કેલ બફર સુધી ઘટાડી દેવામાં આવે છે અને તેની સરખામણી માત્ર છેલ્લી ફ્રેમ સાથે કરવામાં આવે છે. એક ફ્રેમની ઉપરના વિનંતી કરેલ કૅપ્શન બજેટ માટે, નિષ્કર્ષણ તે બજેટના બમણા અને 16 ફ્રેમથી વધુ ક્યારેય ન હોય તેવા બાઉન્ડેડ ઉમેદવાર પૂલ પૂરા પાડે છે. વિનંતિ કરેલ કેપ ડિડુપ્લિકેશન પછી જ લાગુ કરવામાં આવે છે, જ્યારે બજેટ ઓછામાં ઓછું બે હોય ત્યારે પ્રથમ અને અંતિમ પસંદ કરેલા ઉમેદવારોને અંતિમ પાતળું કરતી વખતે સાચવવામાં આવે છે. વર્ઝનેડ `grayscale-16x16-mean-cells-v2` પોલિસી સરેરાશ લુમા ડેલ્ટાના મોટા અને થંબનેલ કોષોના ગુણોત્તરનો ઉપયોગ કરે છે જેનો સામાન્યકૃત ડેલ્ટા ઓછામાં ઓછો 0.05 છે. ડુપ્લિકેટ થ્રેશોલ્ડ એ સતત 0.04 છે, જે રનટાઈમ સેટિંગ તરીકે પ્રગટ કરવાને બદલે અનુમાનિતતા માટે પસંદ કરવામાં આવે છે. આ ગૌણ ઉચ્ચ-કોન્ટ્રાસ્ટ સિગ્નલ નાની ગતિ અને દૃશ્યમાન-ટેક્સ્ટ ફેરફારોને સાચવે છે જેને સરેરાશ-માત્ર સરખામણી છુપાવી શકે છે. તુલનાત્મક અથવા ડીકોડર ભૂલો ખુલ્લી નિષ્ફળ જાય છે અને કવરેજ રાખે છે. આઉટપુટ મેટાડેટા એક્સટ્રેક્ટેડ ઉમેદવારો, સફળતાપૂર્વક ઉપયોગમાં લેવાતા ફ્રેમ્સ અને વિઝ્યુઅલ ડુપ્લિકેટ્સને અલગ કરે છે.

સ્પષ્ટ રીતે ચિહ્નિત થયેલ વિડિઓ ભાગ ટાઇમસ્ટેમ્પ્ડ સંપર્ક શીટની વિનંતી કરી શકે છે. પુલ વધુમાં વધુ 4-કૉલમ, 16-ફ્રેમ JPEG ગ્રીડ બનાવે છે. દરેક 512-પિક્સેલ સેલ તેના સ્ત્રોત ટાઇમસ્ટેમ્પને ઉચ્ચ-કોન્ટ્રાસ્ટ બોટમ બેન્ડમાં બર્ન કરે છે, જ્યારે તે જ ટાઇમસ્ટેમ્પ ડાઉનસ્ટ્રીમ એસોસિએશન અને ઓડિટ માટે ટેક્સ્ટ મેટાડેટામાં રહે છે. સંપૂર્ણ JPEG 32 MiB પર મર્યાદિત રહે છે. જો `sharp` ગ્રીડને ડીકોડ અથવા કંપોઝ કરી શકતું નથી, તો પુલ વ્યક્તિગત JPEG ફ્રેમમાં પાછો આવે છે; ક્લાયંટ એબોર્ટ હજુ પણ શીટ ઓપરેશન દ્વારા પ્રચાર કરે છે.

પ્રમોશન પુરાવા ઇરાદાપૂર્વક કૃત્રિમ રચના માઇક્રોબેન્ચમાર્કથી અલગ છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI- સુસંગત વિઝન મોડલ્સ માટે સ્કીમા-વર્ઝનવાળી A/B હાર્નેસને વ્યાખ્યાયિત કરે છે. તે પ્રદાતા-રિપોર્ટેડ ટોકન્સ, એન્ડ-ટુ-એન્ડ વોલ લેટન્સી (શીટ કમ્પોઝિશન સહિત), મોડલ-કોલ કાઉન્ટ અને મેનિફેસ્ટ-વ્યાખ્યાયિત હકીકત રીટેન્શનને માપે છે. કાચા મોડલના જવાબો રિપોર્ટ પર લખવામાં આવતા નથી; માત્ર SHA-256 ડાયજેસ્ટ અને મેળ ખાતી હકીકત IDs જાળવી રાખવામાં આવે છે. જ્યાં સુધી `--execute-real` પાસ ન થાય અને `--model`, `OMNIROUTE_BASE_URL` અને `OMNIROUTE_API_KEY` રૂપરેખાંકિત ન થાય ત્યાં સુધી હાર્નેસ કોઈ નેટવર્ક અથવા પેઇડ મોડેલ કૉલ કરતું નથી. તે સ્પષ્ટ વાસ્તવિક રન વિના, તેનો મશીન વાંચી શકાય એવો ચુકાદો `HOLD` રહે છે; એકલા સિન્થેટિક payload/call-count માપન પ્રમોશન પુરાવા નથી.

કોલર્સ સમર્થિત વિડિયો ભાગ સાથે વૈકલ્પિક `transcript.cues` એરે જોડી શકે છે જ્યારે તેમની પાસે પહેલેથી સંરેખિત ટેક્સ્ટ હોય. દરેક સંકેત `text`, ચકાસણી અવધિની અંદર એક મર્યાદિત `start`/`end` અંતરાલ અને વ્હાઇટલિસ્ટેડ `source` (`client`, `embedded`, અથવા `audio-bridge`); `confidence` `1` માં ડિફોલ્ટ છે અને `0` અને `1` વચ્ચે રહેવું જોઈએ. ચોક્કસ ડુપ્લિકેટ સંકેતો સંકુચિત છે. OmniRoute આ મેટાડેટામાંથી ક્યારેય ટ્રાન્સક્રિપ્શન શરૂ કરતું નથી: માન્ય સંકેતોને સ્રોત, વિશ્વાસ અને અંતરાલ સાથે વર્ણવેલ પરિણામમાં કૉપિ કરવામાં આવે છે અને ફ્રેમ કૅપ્શન્સની સાથે અવિશ્વસનીય અવલોકનો તરીકે પ્રસ્તુત કરવામાં આવે છે. કૅપ્શન સ્ટ્રીમમાં ભળવાને બદલે અમાન્ય, આઉટ ઑફ રેન્જ અથવા ઉત્પત્તિ-મુક્ત ટેક્સ્ટ નકારવામાં આવે છે. બંને રિક્વેસ્ટ-બોડી ટ્રાન્સક્રિપ્ટ ચેનલો `client` ને પૂરા પાડવામાં આવેલ ઉત્પત્તિને સામાન્ય બનાવે છે, જેમાં સ્વ-આગ્રહિત `embedded` અથવા `audio-bridge` લેબલ્સનો સમાવેશ થાય છે. માત્ર સર્વર-માલિકીનું એડેપ્ટર જ કોડ-ઓન્લી `trustedSource` દલીલ દ્વારા તે વિશ્વસનીય લેબલ્સ અસાઇન કરી શકે છે; વિનંતી JSON ફીલ્ડ તે દલીલ સુધી પહોંચી શકતું નથી. ટ્રાંસ્ક્રિપ્ટ ટેક્સ્ટ અવિશ્વસનીય મીડિયા-ઉત્પાદિત સામગ્રી રહે છે, તેના મૂળને ધ્યાનમાં લીધા વિના, અને ક્યારેય અધિકૃતતા નક્કી કરવી જોઈએ નહીં.

એક અદ્યતન કૉલર સમાન વિડિઓ માટે `audioTranscript` ટ્રેક પ્રદાન કરી શકે છે; તેને ક્લાયંટ દ્વારા આપવામાં આવેલ ટેક્સ્ટ તરીકે ગણવામાં આવે છે, સર્વર ટ્રાન્સક્રિપ્શનનો પુરાવો નથી. ફ્યુઝન સીમ વિઝ્યુઅલ અને ઑડિયો અવલોકનોને એક સમયમર્યાદા અને અબોર્ટ સિગ્નલ હેઠળ ચલાવે છે, તેમને સામાન્ય સમયરેખા પર ઓર્ડર આપે છે, ચોક્કસ ડુપ્લિકેટને સંકુચિત કરે છે અને જ્યારે માત્ર એક બાજુ સફળ થાય છે ત્યારે આંશિક પરિણામની જાણ કરે છે. એક અમાન્ય `audioTranscript` તે આંશિક પરિણામ — માટે અધોગતિ કરે છે વિઝ્યુઅલ વર્ણન રાખવામાં આવે છે અને ઑડિઓ શાખા સમગ્ર વિડિઓને નિષ્ફળ કરવાને બદલે સેનિટાઈઝ્ડ નિષ્ફળતા કોડ — રેકોર્ડ કરે છે. પ્રતિ-શાળા ઉપલબ્ધતા, આંશિક ધ્વજ અને સેનિટાઈઝ્ડ નિષ્ફળતા કોડ વર્ણવેલ પરિણામમાં, ગાર્ડરેલ મેટાડેટા (`audioFusionRuns`/`audioFusionPartials`/ `audioFusionFailureCodes`), પરિણામ-કેશ મેટાડેટામાં અને બ્રિજ ફ્યુઝન કાઉન્ટર્સમાં સાચવેલ છે. ડિફૉલ્ટ વિડિયો બ્રિજ પાથ સ્પીચ-ટુ-ટેક્સ્ટનો ઉપયોગ કરતું નથી અથવા બીજી મીડિયા કૉપિ ડાઉનલોડ કરતું નથી; તે સ્પષ્ટ ટ્રેક વિના, તે માત્ર વિડિયો જ રહે છે.

**ટ્રાન્સક્રિપ્ટ રીટેન્શન (#12150 P1).** જ્યારે પણ વિડિયો બ્રિજ (પોતે પસંદ કરે છે) ટ્રાન્સક્રિપ્ટ ક્યુ — રેન્ડર કરે છે ત્યારે આ આપમેળે લાગુ થાય છે ત્યાં કોઈ અલગ રીટેન્શન ફ્લેગ નથી. જ્યારે વિનંતિ કોઈપણ ટ્રાન્સક્રિપ્ટ કયૂ (કોલર-ઘોષિત `transcript` અથવા ફ્યુઝ્ડ `audioTranscript`) રેન્ડર કરે છે, ત્યારે ગાર્ડ્રેલ તેને `videoBridgeObserved` ચિહ્નિત કરે છે અને વિડિયો વર્ણન — એક સરખું રેન્ડરિંગ બનાવે છે જેમાં દરેક કયૂના ફ્રી-ટેક્સ્ટ બૉડીને `[redacted-video-transcript]` દ્વારા બદલવામાં આવે છે, જે stcd ફીલ્ડની રચના પહેલાં સ્ટ્રક્ચર દ્વારા બનાવવામાં આવે છે. (ક્યારેય ચપટી લખાણનું પદચ્છેદન કરીને નહીં, તેથી `[inaudible]`/`[music]` — જેવા `]` ધરાવતી સંસ્થાઓ સહિત — પ્રતિકૂળ અથવા સામાન્ય ક્યુ કન્ટેન્ટ ટકી શકશે નહીં). સતત કૉલ-લૉગ વિનંતીનો મુખ્ય ભાગ તે રીડેક્ટેડ શેડો માટે દરેક વિડિયો-પ્રાપ્ત ટેક્સ્ટ ભાગને સ્વેપ કરે છે, જે સામગ્રી સમાનતા દ્વારા મેળ ખાતી હોય છે; `fullText` એન્કરને ફિનિશ્ડ પ્રી-કોલ ગાર્ડરેલ પેલોડમાંથી ફરીથી વાંચવામાં આવે છે, તેથી મેચ હજુ પણ પછીની સાંકળ ગાર્ડરેલ્સ ( PII અને ઓળખપત્ર માસ્કર્સ, પ્રાથમિકતાઓ 10/95) સ્થાને વર્ણન ટેક્સ્ટને ફરીથી લખે છે અને system-prompt/handoff/memory ઈન્જેક્શન પછી સંદેશ એરેને ફરીથી આકાર આપે છે પછી પણ સફળ થાય છે. મોડલ પર અપસ્ટ્રીમ મોકલવામાં આવેલ શરીર અપરિવર્તિત છે. અવલોકન કરાયેલ વિનંતી પણ કોઈ ટકાઉ મેમરી ધરાવતી નથી.

**કાચો વિડિઓ ક્ષેત્રો (#12430).** જ્યારે બ્રિજ સક્ષમ હોય અને મૂળ વિડિયો સપોર્ટ અજ્ઞાત અથવા ગેરહાજર હોય, ત્યારે વ્યાખ્યાયિત `transcript`/`audioTranscript` ફીલ્ડ પણ `videoBridgeObserved` સક્રિય કરે છે, વર્ણન નિષ્ફળતા અથવા `maxVideos` મર્યાદા પછી પણ. `null` અને ખાલી શબ્દમાળાઓની ગણતરી; ગેરહાજર ફીલ્ડ્સ અને નોન-વિડિયો મેટાડેટા નથી. જાળવી રાખેલી નકલો આ ક્ષેત્રોને સુધારે છે અથવા વિનંતીને છોડી દે છે, અને caches/Memory બાયપાસ કરવામાં આવે છે.

તે ફોલબેક પાથ પર, માન્ય કોલર સંકેતો બિન-માનક પ્રદાતા ક્ષેત્રોને બદલે આધારભૂત `text`/`input_text` ભાગો બની જાય છે. વિનંતિ-સપ્લાય કરેલ બંને ટ્રેક અવિશ્વસનીય `client` અવલોકનો રહે છે, સ્પષ્ટ ચેતવણી સાથે કે વિડિઓનું વર્ણન કરવામાં આવ્યું નથી અને મીડિયા સામે ટાઇમસ્ટેમ્પ ચકાસવામાં આવ્યા નથી. હાલના 256-cue/64-KiB કુલ અને પ્રતિ-ક્યૂ બજેટ એકસાથે બે ટ્રેક પર લાગુ થાય છે; ટાઇમસ્ટેમ્પ બ્રોકરની 600-સેકન્ડની ટોચમર્યાદા અને કોઈપણ સપ્લાય કરેલ ફોકસ વિન્ડોમાં ફિટ હોવા જોઈએ. અમાન્ય ટ્રૅક્સ કાઢી નાખવામાં આવે છે, મનસ્વી ટેક્સ્ટ તરીકે આગળ મોકલવામાં આવતા નથી; માન્ય ભાઈ-બહેનનો ઉપયોગ હજુ પણ થઈ શકે છે સિવાય કે તેમનું સંયુક્ત બજેટ ઓળંગાઈ જાય. Null/empty ફીલ્ડ્સ કોઈ ટેક્સ્ટ ઉમેરતા નથી. આ ફોલબેક દ્વારા કોઈ મીડિયા આનયન અથવા ટ્રાન્સક્રિપ્શન ઉમેરવામાં આવ્યું નથી. ટ્રાંસ્ક્રિપ્ટ એક્સ્ટેંશન ફીલ્ડ્સ ફોલબેક વિડિયો કેરિયર અને તેના `video_url`/`source` ઑબ્જેક્ટ્સમાંથી દૂર કરવામાં આવે છે. OpenAI વાયર મંજૂર સૂચિ કડક રહે છે; અજ્ઞાત-મૂળ વિડિયો કેરિયર્સ ઉપલબ્ધ રહે છે અને જાણીતા લખાણ-માત્ર લક્ષ્યો સલામત માર્કર્સ રાખે છે. સ્ટ્રક્ચર્ડ રિડેક્શન શેડોઝ જોડાયેલ ટ્રાન્સક્રિપ્ટ ટેક્સ્ટને સુરક્ષિત કરે છે, જ્યારે મૂળ કૉલરની માલિકીની વિનંતી યથાવત રહે છે. મૂળ-સમર્થિત લક્ષ્યો અને અક્ષમ પુલ તેમના હાલના બાયપાસ વર્તનને જાળવી રાખે છે.

વધારાની જાળવી રાખેલી નકલો સમાન અવલોકન-વિનંતી સિગ્નલનો ઉપયોગ કરે છે. કાચો પ્રી-ગાર્ડ્રેલ ક્લાયંટ-વિનંતી સ્નેપશોટ, ઇન-મેમરી પેન્ડિંગ વિનંતી, અને પ્રારંભિક અસ્વીકાર-વિનંતી લોગ વિડિયો ભાગોમાં ટ્રાન્સક્રિપ્ટ ફીલ્ડ્સને માળખાકીય રીતે બદલો; પાઈપલાઈન સ્ટેજ અને કોન્ટેસ્ટ હેન્ડઓફ દ્વારા સંશ્લેષિત સ્ટ્રિંગ પ્રોમ્પ્ટને પર્સિસ્ટેડ-રિક્વેસ્ટ-બોડી સિંક પર રીડેક્ટ કરવામાં આવે છે. સતત `video_content_removed` માર્કર ઇરાદાપૂર્વક કાઢી નાખવામાં આવેલ ટેક્સ્ટને પુનઃનિર્માણ કરવાને બદલે `previous_response_id` ચાલુ રાખવાને નિષ્ફળ બનાવે છે. જો અવલોકન કરેલ વિનંતી લોગીંગ કરતા પહેલા તેનો ભાગ-દીઠ રીડેક્શન શેડો ગુમાવે છે, અથવા તો પછીની વિનંતીના પરિવર્તનો પછી કેટલાક વિડિયો પડછાયાઓમાંથી એક પણ મેચ થવામાં નિષ્ફળ જાય છે, તો આંશિક રીતે રીડેક્ટ કરેલ ટ્રાન્સક્રિપ્ટને જાળવી રાખવાને બદલે જાળવી રાખેલી વિનંતીના મુખ્ય ભાગને સંપૂર્ણપણે છોડી દેવામાં આવે છે.

અવલોકન કરેલ વિનંતી માટે, મોડેલ પ્રતિસાદ સંરચિત કયૂ બાઉન્ડ્રી વિના ટ્રાન્સક્રિપ્ટના કોઈપણ ભાગને ટાંકી શકે છે. તેથી તેના સતત કોલ-લોગ `responseBody` ઓમિશન માર્કર દ્વારા બદલવામાં આવે છે; વિગતવાર પાઇપલાઇન આર્ટિફેક્ટ (જેમાં upstream/client બોડી અને સ્ટ્રીમ હિસ્સાનો સમાવેશ થઈ શકે છે) જાળવી રાખ્યો નથી. તે વિનંતી માટે સિમેન્ટીક, આઇડમ્પોટેન્સી અને રિઝનિંગ-રીપ્લે કેશ બાયપાસ વાંચે છે અને લખે છે. પ્રદાતા વિનંતી અને ક્લાયંટ-દ્રશ્ય પ્રતિભાવ યથાવત રહે છે. જ્યારે વિગતવાર આર્ટિફેક્ટ અવગણવામાં આવે છે ત્યારે પ્રારંભિક કીપલાઈવ બાઇટ્સ અસ્થાયી બફરમાંથી બહાર કાઢવામાં આવે છે. Kiro ની દૂષિત EventStream ચેતવણી માત્ર પેલોડ બાઈટ ગણતરીની જાણ કરે છે, તેની સામગ્રીઓ અથવા JSON પાર્સરની કાચી ભૂલ ક્યારેય નહીં. આ દાવો કરતું નથી કે દરેક અસંબંધિત provider/plugin ડાયગ્નોસ્ટિકનું ઓડિટ કરવામાં આવ્યું છે; વ્યાપક જાળવી રાખેલ-સિંક સ્વીપને #11658 માં ટ્રૅક કરવામાં આવે છે.

આંતરિક `/api/modality-bridge/video/drilldown` જીવનચક્ર એ એક અલગ, loopback/token-authenticated કેશ સબસ્ટ્રેટ છે. દરેક ઓપરેશન માટે પ્રમાણભૂત અપારદર્શક મુખ્ય ID પણ જરૂરી છે. પ્રોડક્શન કૉલર સક્ષમ થાય તે પહેલાં, તેણે તે ID પ્રમાણિત ભાડૂત પાસેથી મેળવવું જોઈએ અને ક્લાયન્ટ-પસંદ કરેલ મૂલ્યને ક્યારેય ફોરવર્ડ કરવું જોઈએ નહીં. કેશ કીઓ તે પ્રિન્સિપલને કેનોનિકલ સત્ર અને વિડિયો-રેફરન્સ IDs સાથે જોડે છે, માત્ર તેમની SHA-256-derived કી સ્ટોર કરે છે અને તે જ પ્રિન્સિપાલને વાંચવા અને કાઢી નાખવાનો અવકાશ બંને આપે છે. કેશ એન્ટ્રી દીઠ વધુમાં વધુ 16 વ્યુત્પન્ન JPEG ફ્રેમ્સ સંગ્રહિત કરે છે, તે દસ મિનિટ પછી સમાપ્ત થાય છે, અને બાઉન્ડેડ `start`/`end` રીડ અથવા સ્પષ્ટ સત્ર કાઢી નાખવાને સપોર્ટ કરે છે.

દરેક પ્રિન્સિપલ 16 એન્ટ્રીઓ અને 64 MiB પ્રમાણભૂત JPEG ડેટા સુધી મર્યાદિત છે. તે મર્યાદાઓ વૈશ્વિક 64-entry/256 MiB ટોચમર્યાદાથી સ્વતંત્ર છે: મુખ્ય ક્વોટા દબાણ ફક્ત તે જ પ્રિન્સિપાલની ઓછામાં ઓછી-તાજેતરમાં ઉપયોગમાં લેવાતી એન્ટ્રીઓને વૈશ્વિક LRU ઇવિક્શન ગણવામાં આવે તે પહેલાં બહાર કાઢે છે. સમયસીમા સમાપ્ત થયેલ એન્ટ્રીઓ કેશ પ્રવૃત્તિ પર મુખ્ય અને વૈશ્વિક એકાઉન્ટિંગ બંનેમાંથી સ્વિપ કરવામાં આવે છે, જ્યારે રદ અને માન્યતા નિષ્ફળતા આંશિક રિપ્લેસમેન્ટ કરતી નથી.

કેશ બિન-કેનોનિકલ Base64, અધિક પેડિંગ, બિન-JPEG મીડિયા, દૂષિત અથવા કપાયેલ JPEGs, અને JPEGs ને નકારે છે જે બાઉન્ડેડ પૂર્ણ-ઇમેજ `sharp` ડીકોડ દરમિયાન ચેતવણી ઉત્પન્ન કરે છે. તે દરેક સ્વીકૃત ઈમેજને કેનોનિકલ JPEG તરીકે ફરીથી એન્કોડ કરે છે, કોલર ફીલ્ડ્સ પર વિશ્વાસ કરવાને બદલે ડીકોડેડ બાઈટમાંથી પહોળાઈ અને ઊંચાઈ મેળવે છે અને કોઈપણ પાછળના પોલીગ્લોટ બાઈટ્સને જાળવી રાખવાને બદલે તેને કાઢી નાખે છે. બંને ક્વોટા માટે માત્ર બાઉન્ડેડ કેનોનિકલ કમ્પ્રેસ્ડ બફરનો ચાર્જ લેવામાં આવે છે. JSON વાયર મર્યાદામાં 32 MiB ડીકોડેડ-ઇનપુટ ટોચમર્યાદા માટે Base64 ઓવરહેડનો સમાવેશ થાય છે. દરેક સંગ્રહિત વ્યુત્પન્નતા તેની માન્ય JPEG format/resolution, સેમ્પલિંગ નીતિ, વ્યુત્પન્ન સંસ્કરણ, બનાવટનો સમય, સર્વર-કમ્પ્યુટેડ સામગ્રી હેશ અને હેશ કરેલ પેરેન્ટ રેફરન્સ વત્તા વિશ્વસનીય કોલરની પેરેન્ટ-કન્ટેન્ટ હેશ રેકોર્ડ કરે છે. અણુ કેશ કમિટ પહેલાં અસુમેળ decode/hash તબક્કાઓ વચ્ચે રદ કરવાની તપાસ કરવામાં આવે છે.

પ્રોડક્શન નિર્માતા સફળ વિઝ્યુઅલ પૃથ્થકરણ પછી જ પહેલાથી મેળવેલી બ્રોકર ફ્રેમનો પુનઃઉપયોગ કરે છે, જેમાં બીજા વિડિયો download/extraction. નથી તેને ઓપરેટર `modalityBridgeVideoDrilldownEnabled=true`, ભાગ દીઠ કડક `drilldown: true`, અને પ્રમાણિત API-કી રેકોર્ડ ID ની જરૂર છે. ક્લાયન્ટ-ઘોષિત principal/session મૂલ્યો ક્યારેય માલિકી સ્થાપિત કરતા નથી. ત્રણેય શરતો વિના તે વધારાની ફ્રેમને હેશ કરતું નથી, માપ બદલી શકતું નથી અથવા જાળવી શકતું નથી. રીટેન્શન નિષ્ફળતા ઉપયોગી દ્રશ્ય પ્રતિભાવને સાચવે છે. સંમતિ આપેલી વિનંતીઓ આખા-વિડિયો પરિણામ કૅશને બાયપાસ કરે છે જેથી કૅશ્ડ પરિણામો ક્યારેય હૅન્ડલને રિપ્લે નહીં કરે.

સફળ JSON અને SSE પ્રતિસાદો બાઉન્ડેડ `x-omniroute-video-drilldown` હેડરમાં વધુમાં વધુ ચાર અપારદર્શક હેન્ડલ્સનો પર્દાફાશ કરે છે. અધિકૃત બ્રાઉઝર મૂળ CORS મૂળ નીતિને વિસ્તૃત કર્યા વિના તે હેડરને વાંચી શકે છે. નવા હેન્ડલ્સ `v1.<32-byte random base64url token>` ઉપયોગ કરે છે, અને રજિસ્ટ્રી ફક્ત તેમના SHA-256 હેશને જાળવી રાખે છે. reader/header પાર્સર લેગસી 64-હેક્સ ટોકન્સ પણ સ્વીકારે છે. અધિકૃત જાહેર ઉપભોક્તા `GET /api/v1/video-bridge/drilldown?handle=...` છે, સ્વતંત્ર રીતે `modalityBridgeVideoDrilldownRemoteEnabled=true` દ્વારા ગેટેડ છે. જ્યારે લેગસી `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env ફોલબેક સક્ષમ હોય ત્યારે પણ સ્પષ્ટ રીતે ચાલુ રહેલ ખોટા ઍક્સેસને રદ કરે છે. ઉત્પાદન રીટેન્શનમાં સમાન લેગસી `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` ફોલબેક છે. બંને ફૉલબૅક્સ ડિફૉલ્ટ બંધ છે.

ગ્રાહક અધિકૃત કીમાંથી માલિકી મેળવે છે અને કી નીતિ લાગુ કરે છે: GET અને DELETE બંને `/v1` અને `/api/v1` ઉપનામો સહિત `video` એન્ડપોઇન્ટ કેટેગરીના છે. બિન-ખાલી એન્ડપોઇન્ટની મંજૂરીવાળી કીમાં `video` શામેલ હોવી આવશ્યક છે; અપ્રતિબંધિત કીઓ સુસંગત રહે છે. ઉપભોક્તા અજાણ્યા, એક્સપાયર થયેલ અને અન્ય કીના હેન્ડલ્સ માટે એ જ 404 પરત કરે છે. તે `variant=preview|standard|detail` (મહત્તમ JPEG પરિમાણ 320/640/1280, ક્યારેય અપસ્કેલ્ડ નહીં), `limit=1..8` (અથવા વારસાગત `frames` ઉપનામ, બંને ક્યારેય નહીં), શૂન્ય-આધારિત `page`, અને વૈકલ્પિક `start`/`end` ફોકસ સેકન્ડ સ્વીકારે છે. ડુપ્લિકેટ ક્વેરી કી અને રિવર્સ્ડ ફોકસ વિન્ડો નકારવામાં આવે છે. દરેક પરત કરેલ વેરિઅન્ટમાં તેની વાસ્તવિક સામગ્રી અને વાસ્તવિક રિઝોલ્યુશન મેટાડેટાનો હેશ હોય છે, જે જાળવી રાખેલા સ્ત્રોત સાથે લિંક થયેલ હોય છે. વેરિઅન્ટ્સ વધારાની જાળવી રાખેલી નકલો તરીકે સંગ્રહિત કરવાને બદલે વાંચવા પર લેવામાં આવે છે. JSON પ્રતિસાદ, Base64/envelope સહિત, 32 MiB પર મર્યાદિત છે; મોટા કદનું પૃષ્ઠ 413 પરત કરે છે અને ક્લાયન્ટે ઓછા ફ્રેમની વિનંતી કરવી આવશ્યક છે. દરેક પુન: માપની આસપાસ ચેક કેન્સલેશન વાંચે છે અને પાછા ફરતા પહેલા હેન્ડલની માન્યતા ફરીથી તપાસો. માલિક દ્વારા `DELETE` નિર્બળ છે; કાઢી નાખવું અથવા TTL સમાપ્તિ જાળવી રાખેલા સ્રોત અને વપરાશ એકાઉન્ટિંગને પ્રકાશિત કરે છે.

શેર કરેલ સ્ટોર પ્રક્રિયા-સ્થાનિક છે: હેન્ડલ્સ પુનઃપ્રારંભ પર સમાપ્ત થાય છે અને સ્વતંત્ર OmniRoute પ્રક્રિયાઓ વચ્ચે ટ્રાન્સફર કરી શકાતા નથી. મેનેજમેન્ટના આંકડા અસરકારક રીટેન્શન/રિમોટ પોલિસી અને એકંદર જાળવી રાખેલા entries/bytes જાહેર કરે છે, ક્યારેય મીડિયા, સંદર્ભો, મુખ્ય IDs અથવા હેન્ડલ્સ નહીં. વિડિઓ સેટિંગ્સ પેનલ તે મૂલ્યો બતાવે છે અને બંને સંમતિ સ્વિચ ચાલુ રાખી શકે છે. આ અમલીકરણ દસ્તાવેજીકરણ જીવંત જમાવટ અથવા પ્રમોશન પુરાવા નથી; વાસ્તવિક-મૉડલ સ્વીકૃતિને અલગથી ટ્રૅક કરવામાં આવે છે.

રૂપરેખાંકિત વિડિઓ મોડલ સાથે ફ્રેમ્સને અનુક્રમે કૅપ્શન આપવામાં આવે છે. ખાલી વિડિયો ઓવરરાઇડ વિઝન સેટિંગને વારસામાં મેળવે છે; જો બંને ખાલી હોય, તો વિઝન ઓટો-રાઉટર અસરકારક દ્રષ્ટિ-સક્ષમ મોડલ પસંદ કરે છે. સફળ કૅપ્શન્સ મૂળ ભાગને સ્થિર `[Video description:` ઉપસર્ગ સાથે બદલે છે જે ટેક્સ્ટને અવિશ્વસનીય મીડિયા દ્વારા મેળવેલા અવલોકન તરીકે પણ ચિહ્નિત કરે છે અને ડાઉનસ્ટ્રીમ મોડલ્સને મીડિયામાં મળેલી સૂચનાઓનું પાલન ન કરવાનું કહે છે. ફ્રેમ-કેપ્શન કેશ કીમાં JPEG બાઇટ્સ, પ્રોમ્પ્ટ, ટાઇમસ્ટેમ્પ અને અસરકારક મોડલનો સમાવેશ થાય છે; માત્ર સફળ કૅપ્શન્સ કેશ કરવામાં આવે છે. કેશ એન્ટ્રીઓ વાસ્તવિક સફળ નિર્માતા મોડેલને જાળવી રાખે છે, જેમાં ફોલબેક મોડલનો સમાવેશ થાય છે; બ્રિજ `mixed` નો અહેવાલ આપે છે જ્યારે વિવિધ મોડેલો દ્વારા વિવિધ ફ્રેમ્સ બનાવવામાં આવી હતી. કેશ હિટ તે નિર્માતા ઓળખને વિનંતી કરેલ રૂટીંગ પ્લાન તરીકે રીલેબલ કરવાને બદલે ફરીથી ઉપયોગ કરે છે. આઉટપુટ — પ્રોમ્પ્ટ, અસરકારક મોડલ, સેમ્પલિંગ પોલિસી, ફ્રેમ કાઉન્ટ, સિમેન્ટીક એનાલિસિસ મોડ, નોર્મલાઇઝ્ડ ફોકસ હિંટની SHA-256 ફિંગરપ્રિન્ટ, ફોકસ વિન્ડો, `transcript`, `audioTranscript` અને કોન્ટેક્ટ-શીટ ફ્લેગ — ને બદલતા દરેક ઇનપુટ પર સંપૂર્ણ-વિડિયો પરિણામ કેશ ચાવી દેવામાં આવે છે તેથી તેમાંથી કોઈપણને બદલવાનું ક્યારેય ચૂકશો નહીં. વિઝ્યુઅલ ડેડઅપ પોલિસી વર્ઝન, થ્રેશોલ્ડ અને બાઉન્ડેડ ઉમેદવાર-ફ્રેમ કાઉન્ટ પણ પરિણામ-કેશ કી અને મેટાડેટામાં સ્પષ્ટ છે; તેથી નીતિમાં ફેરફાર વાસી સંપૂર્ણ-વિડિયો વર્ણનનો ફરીથી ઉપયોગ કરી શકતો નથી. પરિણામ-કેશ v4 મેટાડેટા મોડ અને ફિંગરપ્રિન્ટ રાખે છે, ક્યારેય કાચો વપરાશકર્તા કાર્ય નથી. ગાર્ડ્રેલ મેટાડેટા વિનંતી કરેલ અને અસરકારક વિશ્લેષણ મોડ બંનેની જાણ કરે છે; ઉપયોગ કરી શકાય તેવા વપરાશકર્તા ટેક્સ્ટ વિના વિનંતી કરેલ `focused` મોડને અસરકારક રીતે `full` તરીકે જાણ કરવામાં આવે છે.

ગાર્ડરેલ દરેક સપોર્ટેડ વિડિયો ભાગને બહાર કાઢે છે પરંતુ `modalityBridgeVideoMaxVideos` કરતાં વધુનું વર્ણન કરતું નથી. `supportsVideo === false` હોવાનું સાબિત થયેલ લક્ષ્ય માટે, નિષ્ફળ અને ઓવર-લિમિટ વિડિઓઝ સ્પષ્ટ સલામત ટેક્સ્ટ માર્કર બની જાય છે જેથી કોઈ કાચો વિડિઓ ટકી રહેતો નથી. જ્યારે ક્ષમતા અજાણ હોય, ત્યારે તે ભાગો તેમના વિડિયો કેરિયરને જાળવી રાખે છે; કોઈપણ ફોલબેક ટ્રાન્સક્રિપ્ટ ઉપરના બાઉન્ડેડ ટેક્સ્ટ કન્વર્ઝનને અનુસરે છે. `supportsVideo === true` સાથેના લક્ષ્યો પુલને બાયપાસ કરે છે. ક્લાયંટની વિનંતી એબોર્ટ સિગ્નલ ડાઉનલોડ, બ્રોકર કતાર, સબપ્રોસેસ અને કૅપ્શન કૉલ્સ દ્વારા પ્રચાર કરે છે; એબોર્ટ્સ વિડીયો વચ્ચે અટકે છે અને કાચા મીડિયા માટે ક્યારેય નિષ્ફળ જતા નથી.

120 સેકન્ડથી ઉપરના વિડિયો સમયસમાપ્તિ મૂલ્યો બ્રોકરની સમયમર્યાદામાં ક્લેમ્પ્ડ છે; નવી સેટિંગ્સ તે મર્યાદા ઉપર લખે છે તે નકારવામાં આવે છે. `GET /api/modality-bridge/video/runtime` પ્રમાણીકરણ અથવા રનટાઇમ પ્રોબિંગ પહેલાં વિશ્વસનીય સ્ટેમ્પ્ડ લૂપબેક સ્થાનની જરૂર છે, પછી મેનેજમેન્ટ પ્રમાણીકરણની જરૂર છે. તે માત્ર `available`, સેનિટાઈઝ્ડ FFmpeg/ffprobe સંસ્કરણો અને જ્યારે રનટાઈમ અનુપલબ્ધ હોય ત્યારે નિશ્ચિત કારણ પરત કરે છે. આંતરિક નિષ્કર્ષણ અંતિમ બિંદુ એ સાર્વજનિક અપલોડ API નથી : કતાર સંતૃપ્તિ `503` વત્તા `Retry-After` પરત કરે છે, કૉલર ડિસ્કનેક્ટ `499` પરત કરે છે, અને નિશ્ચિત બ્રોકર સમયમર્યાદા `504` પરત કરે છે. રૂપાંતરિત પ્રતિસાદો વિઝન અથવા ઑડિઓ સેગમેન્ટ્સને દૂર કર્યા વિના કેન્દ્રિય `x-omniroute-modality-bridge` હેડરમાં `video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે.

### PII માસ્કર (`piiMasker.ts`)

પર ચાલે છે**બંને** તબક્કાઓ

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને `prompt` (સાદા સ્ટ્રિંગ આઇટમ્સ સહિત) પર ચાલે છે અને `content`/`text` ફીલ્ડ્સને સ્ટ્રિંગ પર `processPII()` ( `@/shared/utils/inputSanitizer` માંથી) લાગુ કરે છે. જ્યારે `PII_REDACTION_ENABLED=true`, શોધાયેલ PII આઉટબાઉન્ડ પેલોડમાં રીડેક્ટ કરવામાં આવે છે. આ `INPUT_SANITIZER_MODE` થી સ્વતંત્ર છે (જે માત્ર પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે). જ્યારે રીડેક્શન બંધ હોય, ત્યારે સામગ્રીને ફરીથી લખ્યા વિના કોલ રેકોર્ડ ડિટેક્શન ગણતરીઓ.
- **`postCall`** પ્રતિભાવને ડીપ-ક્લોન કરે છે, `sanitizePIIResponse()` વત્તા રિસ્પોન્સ-API-આકાર માસ્કર ચલાવે છે (`maskResponsesOutput` — `output_text` અને `output[].content[].text` ને આવરી લે છે). જો કોઈ સુધારણા થાય છે, તો સંશોધિત પ્રતિસાદ મૂળને બદલે છે.

રક્ષક ક્યારેય અવરોધતું નથી; તે ફક્ત ટીકા કરે છે (`meta.detections`, `meta.redacted`) અથવા ફરીથી લખે છે.

#### પ્રતિ-પ્રકાર પસંદગી, કસ્ટમ પેટર્ન અને શોધ કાઉન્ટર્સ

**ડેશબોર્ડ → સેટિંગ્સ → સુરક્ષા → PII માસ્કિંગ** _what_ માસ્ક કરેલ છે તે પસંદ કરે છે. તે માસ્કિંગને સ્વિચ કરતું નથી: તે હજી પણ `PII_REDACTION_ENABLED` (વિનંતી) અને `PII_RESPONSE_SANITIZATION` (પ્રતિસાદ + SSE), બંને ડિફૉલ્ટ રૂપે બંધ છે.

- **પ્રતિ-પ્રકાર પસંદગી** — બિલ્ટ-ઇન આઈડી `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`) માં સૂચિબદ્ધ છે. અનસેટ એટલે દરેક પ્રકાર (આ સેટિંગ પહેલાની વર્તણૂક અસ્તિત્વમાં હતી). વિનંતી એન્જિનની `ssn_us` પેટર્ન `ssn` પર નકશા કરે છે. નમૂનાઓ (ન્યૂનતમ, માનક, નાણાકીય, બ્રાઝિલિયન, USA, GDPR, POPIA, સંપૂર્ણ) UI માં ફક્ત ચેકબોક્સ ભરો.
- **GDPR અને POPIA ઓળખકર્તાઓ** — બાર બિલ્ટ-ઇન આઈડી જે EU અને દક્ષિણ આફ્રિકાના વ્યક્તિગત ઓળખકર્તાઓને આવરી લે છે (નીચેનું કોષ્ટક). તેમના રેજેક્સિસ, વેલિડેટર અને અધિકારક્ષેત્ર ટૅગ્સ એક ટેબલ, `src/shared/utils/piiPatterns.ts` માં રહે છે, જે રિસ્પોન્સ સેનિટાઈઝર (`src/lib/piiSanitizer.ts`) અને રિક્વેસ્ટ માસ્કર (`src/shared/utils/inputSanitizer.ts`) બંને વાપરે છે. મેચને ત્યારે જ રીડેક્ટ કરવામાં આવે છે જ્યારે તેનો માન્યકર્તા તેને સ્વીકારે છે; અંકોની એકદમ દોડ ક્યારેય પૂરતી હોતી નથી. એક ઓપરેટર કે જેણે આ ids અસ્તિત્વમાં હોય તે પહેલાં એક સંકુચિત પસંદગી સાચવી છે, જ્યાં સુધી નવા ids પર ટિક ન થાય ત્યાં સુધી તેની પાસે જે વર્તન હતું તે જાળવી રાખે છે.
- **કસ્ટમ પેટર્ન** — સુધી 20 રેજેક્સ અથવા વાઇલ્ડકાર્ડ પેટર્ન (`*` = 64 બિન-વ્હાઇટસ્પેસ અક્ષરો સુધી, `?` = એક). મેચો `[CUSTOM_REDACTED]` બની જાય છે. દરેક પેટર્ન `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`) દ્વારા જાય છે : વધુમાં વધુ 500 અક્ષરો, `g i m s u` સુધી મર્યાદિત ફ્લેગ્સ, કમ્પાઈલ કરવા જોઈએ, `safe-regex` (આપત્તિજનક બેકટ્રેકિંગ) પાસ કરવા જોઈએ, અને ખાલી સ્ટ્રિંગ અથવા રિડક્શન પ્લેસહોલ્ડર સાથે મેળ ખાતો ન હોવો જોઈએ. એક પેટર્ન જે નિષ્ફળ જાય છે તે સાચવવામાં આવે ત્યારે અને પરીક્ષણ કરવામાં આવે ત્યારે નકારવામાં આવે છે, અને સંગ્રહિત પંક્તિ કે જે નિષ્ફળ જાય છે તે સંકલિત થવાને બદલે રનટાઇમ પર છોડવામાં આવે છે. માસ્કિંગ ચાલુ હોય ત્યારે જ કસ્ટમ પેટર્ન ચાલે છે.
- **તપાસ કાઉન્ટર્સ** — પ્રતિ-પ્રકારની ગણતરીઓ (ક્યારેય મેળ ખાતી નથી), મેમરીમાં રાખવામાં આવે છે અને પુનઃપ્રારંભ પર રીસેટ થાય છે (`src/lib/pii/piiDetectionStats.ts`). માસ્કિંગ ચાલુ હોય ત્યારે જ તેઓ વધે છે.

સેટિંગ્સ `key_value` કોષ્ટકમાં રહે છે (નેમસ્પેસ `pii_settings`, `src/lib/db/piiSettings.ts`) અને 1 સે કેશ દ્વારા વાંચવામાં આવે છે. API:

| મેથડ   | પાથ                      | હેતુ                                                                     |
| ------ | ------------------------ | ------------------------------------------------------------------------ |
| `GET`  | `/api/settings/pii`      | ફ્લેગ સ્થિતિ, `enabledTypes`, `customPatterns`, ડિટેક્શન કાઉન્ટર         |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = બધા) અને/અથવા `customPatterns` બદલો             |
| `POST` | `/api/settings/pii/test` | વધુમાં વધુ 8 KB ના નમૂના સામે એક પેટર્નનો ડ્રાય-રન; કંઈપણ સંગ્રહાતું નથી |

આ ત્રણેયને મેનેજમેન્ટ ઓથની જરૂર છે અને Zod (`src/shared/validation/schemas/piiSettings.ts`) વડે બોડીને માન્ય કરો. લૉગિન અક્ષમ સાથે (`requireLogin=false`) `GET` અને ટેસ્ટ એન્ડપોઇન્ટ ખુલ્લા છે, પરંતુ `PUT` હજુ પણ ડેશબોર્ડ સત્ર, `manage` -scope API કી, `oma_` એક્સેસ ટોકન લખવાની અવકાશ અથવા ઉચ્ચ સાથે અથવા CLI ટોકન અથવા લૂપબેકથી મોકલેલ આંતરિક-સેવા ટોકનની જરૂર છે.

| સેટિંગ          | Env var                                                                                              | ડિફોલ્ટ | અસર                                                                                                                                                                                                          |
| --------------- | ---------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| સક્ષમ           | `INPUT_SANITIZER_ENABLED`                                                                            | `true`  | જ્યારે `false` હોય, ત્યારે ગાર્ડરેલ શોર્ટ-સર્કિટ થઈ જાય છે.                                                                                                                                                  |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                      | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` બેક-કમ્પેટ માટે સ્વીકારવામાં આવે છે પરંતુ ઇન્જેક્શન ટેક્સ્ટ **દૂર કરતું નથી**; રિક્વેસ્ટ PII રીરાઇટ `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત થાય છે.) |
| બ્લોક થ્રેશોલ્ડ | `blockThreshold` ઓપ્શન / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉપનામ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | બ્લોક કરવા માટે જરૂરી લઘુત્તમ ગંભીરતા. ડિફોલ્ટ પર મધ્યમ ફક્ત અવલોકન માટે છે.                                                                                                                                 |

**મોડ અગ્રતા** (`getMode`): કૉલર `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લેગ ઓવરરાઇડ** (ડેશબોર્ડ → સેટિંગ્સ →
ફીચર ફ્લેગ્સ) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. તેથી ડેશબોર્ડ ઓવરરાઇડ env વેરિએબલ પર જીતે છે, જેથી ફીચર ફ્લેગ્સ UI
ચાલતા ગાર્ડને લાઇવ નિયંત્રિત કરે છે (રીસ્ટાર્ટ વિના). DB વાંચન ફેલ-સેફ છે:
જો તેમાં ભૂલ આવે, તો ગાર્ડ env-આધારિત વર્તન પર પાછું ફરે છે, અને જ્યારે કોઈ
ઓવરરાઇડ સેટ ન હોય ત્યારે વર્તન env-only રિઝોલ્યુશન જેવું જ હોય છે.

ડિટેક્શન સ્ત્રોતો:

1. `@/shared/utils/inputSanitizer` માંથી `sanitizeRequest()` (પાઇપલાઇનમાં
   બીજે પણ વપરાતો શેર્ડ ડિટેક્ટર સેટ).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
   `markdown_system_block`, બંને `high` ગંભીરતા).
3. કન્સ્ટ્રક્ટર ઓપ્શન મારફતે પાસ થતા વૈકલ્પિક `customPatterns` (સ્ટ્રિંગ,
   regex, અથવા `{ name, pattern, severity }` રેકોર્ડ).

જ્યારે `mode === "block"` હોય **અને** ઓછામાં ઓછું એક ડિટેક્શન ગંભીરતા
થ્રેશોલ્ડ પૂરું કરે, ત્યારે `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` પરત કરે છે. `warn`/`log` મોડમાં ગાર્ડરેલ લોગ
કરે છે પરંતુ કોલને મંજૂરી આપે છે. શેર્ડ હેલ્પર `evaluatePromptInjection()` પણ એ
કોલર્સ માટે એક્સપોર્ટ કરવામાં આવે છે જેમને રજિસ્ટ્રી મારફતે ગયા વગર પ્રોમ્પ્ટનું
મૂલ્યાંકન કરવું હોય.

**સ્કેન મર્યાદા (v3.8.20):** ડિટેક્ટર ફક્ત જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટના **પ્રથમ
16 KB** ની જ તપાસ કરે છે — `src/shared/utils/inputSanitizer.ts` માં
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ્સ). `detectInjection()` અને
`evaluatePromptInjection()` બંને પેટર્ન લૂપ ચલાવતા પહેલાં
`slice(0, MAX_INJECTION_SCAN_BYTES)` કરે છે. ઇન્જેક્શન ડિરેક્ટિવ્સ ઇનપુટની ટોચ
નજીક હોય છે, તેથી આ ડિટેક્શનને નબળું પાડ્યા વગર મલ્ટિ-હન્ડ્રેડ-KB પેલોડ પર
regex CPU/GC ને મર્યાદિત કરે છે (જુઓ #3932, #4041).

### ક્રેડેન્શિયલ માસ્કર (`credentialMasker.ts`)

**બંને** સ્ટેજ પર ચાલે છે, ડિફોલ્ટ ચેનમાં છેલ્લે (પ્રાયોરિટી `95`). આઉટબાઉન્ડ
પેલોડ (મેસેજ કન્ટેન્ટ, ટૂલ-કોલ આર્ગ્યુમેન્ટ્સ, ટૂલ રિઝલ્ટ્સ) **અને** પ્રોવાઇડર
રિસ્પોન્સમાંથી જાણીતા API-કી / સીક્રેટ-ટોકન પેટર્નને રિડાક્ટ કરે છે, જેથી
પ્રોમ્પ્ટમાં પેસ્ટ કરેલું ક્રેડેન્શિયલ (અથવા ટૂલ રિઝલ્ટ દ્વારા પાછું ઇકો થયેલું)
અપસ્ટ્રીમ પ્રોવાઇડર કે ક્લાયન્ટ પાસે લીક થતું નથી.

- **ફક્ત ઑપ્ટ-ઇન**, PII રિડાક્શન જેવી જ કન્વેન્શન (Hard Rule #20-સંલગ્ન):
  `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` ન હોય ત્યાં સુધી ડિસેબલ્ડ. તે બંધ હોય ત્યારે,
  ગાર્ડરેલ no-op છે — તે ક્યારેય બ્લોક કરતું નથી અને ક્યારેય રીરાઇટ કરતું નથી.
- `redactCredentials()` સંપૂર્ણ પેલોડ/રિસ્પોન્સ ટ્રીમાં ફરે છે (`walkValue()`,
  પ્રોટોટાઇપ-પોલ્યુશન-સેફ, `WeakSet` દ્વારા સાયકલ-સેફ) અને મેચને
  `[REDACTED:<type>]` પ્લેસહોલ્ડરથી બદલે છે, ફક્ત એ જ બ્રાન્ચને ક્લોન કરે છે જે
  ખરેખર બદલાઈ છે.
- `CREDENTIAL_PATTERNS` LLM પ્રોવાઇડર કી (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), પેમેન્ટ કી (Stripe, Square), ક્લાઉડ
  કી (AWS એક્સેસ કી, Twilio, SendGrid, Mailgun), પ્રાઇવેટ કી / JWT,
  ક્રેડેન્શિયલ ધરાવતી કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  જેનરિક `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-વેલ્યુ પેટર્નને
  કવર કરે છે. હેડર-આકારની કી (`authorization`, `x-api-key`, `api-key`,
  `apikey`) સ્ટ્રક્ચરલી રિડાક્ટ થાય છે (ફક્ત વેલ્યુ, `Bearer `/`Basic ` જેવું
  સ્કીમ પ્રીફિક્સ જાળવવામાં આવે છે) જેનરિક ટેક્સ્ટ regex દ્વારા નહીં.
- ગાર્ડરેલ ક્યારેય બ્લોક કરતું નથી; તે ફક્ત રીરાઇટ કરે છે (`modifiedPayload` /
  `modifiedResponse`) અને એનોટેટ કરે છે (`meta.credentialsRedacted`, `meta.count`).

રિગ્રેશન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## બેઝ કોન્ટ્રાક્ટ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને શોર્ટ-સર્કિટ કરે છે
  message?: string; // બ્લોક કરતી વખતે દેખાય છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિભાવને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેઇલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં" સૂચવે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ડાઉનસ્ટ્રીમ ગાર્ડરેઇલ્સ માટે ચેઇનમાંથી વહેતી વેલ્યુ બદલાઈ જાય છે. `signal?: AbortSignal` કૉલર લાઇફસાઇકલને ગાર્ડરેઇલ્સ સુધી પહોંચાડે છે. વિનંતી abort એ જાણીજોઈને રાખવામાં આવેલો fail-open અપવાદ છે: મીડિયા બ્રિજીસ કામ બંધ કરે છે અને કાચું મીડિયા એવા ટાર્ગેટ પર પુનઃસ્થાપિત કર્યા વગર cleanup કરે છે જે તેને સપોર્ટ કરતું નથી એવું જાણીતું છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` આ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેઇલ ઉમેરે છે (અથવા સામાન્યકૃત નામ મુજબ બદલે છે) અને
  ઊંચતા `priority` મુજબ ફરીથી ક્રમમાં ગોઠવે છે.
- `clear()` / `list()` — વહીવટી મદદરૂપો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેઇલ્સ પર ફરે છે, પેલોડને
  `modifiedPayload` દ્વારા આગળ વધારે છે, અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિભાવ બાજુ પર સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્થિતિ સાફ કરે છે અને સ્વચ્છ
  ટેસ્ટ આઇસોલેશન માટે વૈકલ્પિક રીતે ડિફોલ્ટ્સ ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }` પરત કરે છે
જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સનું એરે છે જેમાં
દરેક ગાર્ડરેઇલ માટે `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સામેલ છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### પ્રતિ-વિનંતી ગાર્ડરેઇલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન વિનંતી માટે
અવગણવામાં આવવા જોઈએ તેવા ગાર્ડરેઇલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
પાંચ ચેનલો છે, જે આ ક્રમમાં વાંચવામાં આવે છે અને એક યાદીમાં મર્જ થાય છે
(ડુપ્લિકેટ દૂર કરતી વખતે પ્રથમ ઉપસ્થિતિ જીતે છે):

1. `apiKeyInfo.disabledGuardrails`
2. વિનંતી બોડી `disabledGuardrails` (ટોપ-લેવલ)
3. વિનંતી બોડી `metadata.disabledGuardrails` (ફક્ત જ્યારે `metadata` ઓબ્જેક્ટ હોય)
4. હેડર `x-omniroute-disabled-guardrails`
5. લિગસી હેડર `x-disabled-guardrails`

બધી પાંચ ચેનલો મર્જ થાય છે, બંને હેડરો સહિત: બંને
`x-omniroute-disabled-guardrails` અને `x-disabled-guardrails` મોકલવાથી તેમની
યાદીઓના સંયોગને અવગણવામાં આવે છે, અને ખાલી આધુનિક હેડર હવે લિગસી હેડરને
છુપાવતું નથી
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), જે
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805) માં ઠીક કરવામાં આવ્યું).

વેલ્યુઝ સ્ટ્રિંગ્સની એરે અથવા અલ્પવિરામથી અલગ થયેલી સ્ટ્રિંગ હોઈ શકે છે; નામો
ટ્રિમ કરવામાં આવે છે અને લોઅરકેસ kebab-case માં સામાન્યકૃત કરવામાં આવે છે
(`pii_masker` → `pii-masker`), અને ખાલી એન્ટ્રીઓ કાઢી નાખવામાં આવે છે. પરિણામ
`context.disabledGuardrails` દ્વારા રજિસ્ટ્રી સુધી પહોંચાડવામાં આવે છે, જે
મેળ ખાતી ગાર્ડરેઇલ્સને અવગણે છે (`results` માં `skipped: true`).

અક્ષમ યાદી ફક્ત **રજિસ્ટ્રી**ને અસર કરે છે. પ્રોમ્પ્ટ-ઇન્જેક્શન `block` મોડ એ
ફરજિયાત સીમા છે: ઇન્જેક્શન-ગાર્ડ મિડલવેર
(`src/middleware/promptInjectionGuard.ts`) કોઈપણ કૉલર-નિયંત્રિત અક્ષમ યાદી વગર
`evaluatePromptInjection()` ને કૉલ કરે છે (તે અગાઉ કરતું હતું તે મૃત
`resolveDisabledGuardrails({ body })` કૉલ
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934) માં દૂર કરવામાં આવ્યો હતો),
તેથી `prompt-injection` ને અક્ષમ કરતી વિનંતી હજુ પણ `block` મોડમાં નકારવામાં આવે છે.
આ ડિઝાઇન મુજબ છે. અક્ષમ ચેનલો કૉલર-નિયંત્રિત છે (વિનંતી બોડી, મેટાડેટા, હેડરો),
અને કૉલર ઓપરેટર દ્વારા સેટ કરેલા સુરક્ષા નિયંત્રણને બંધ કરી શકવો જોઈએ નહીં
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).
[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412) નો હેડર સંયોગ
ફક્ત કઈ રજિસ્ટ્રી ગાર્ડરેઇલ્સ અવગણવામાં આવે છે તે બદલે છે; તે ક્લાયન્ટને
મિડલવેરને બાયપાસ કરવા દેતું નથી. ફરજિયાત પ્રતિ-કી અને પ્રતિ-જૂથ ગાર્ડરેઇલ નીતિઓ
v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417) માં ટ્રેક કરવામાં આવે છે.
[કવરેજ અને મર્યાદાઓ](#coverage-and-limits) જુઓ.

## એક્ઝિક્યુશન ક્રમ

`src/sse/handlers/chat.ts` અને `open-sse/handlers/chatCore.ts` માંથી પસાર થતી દરેક વિનંતી માટે ([કવરેજ અને મર્યાદાઓ](#coverage-and-limits) હેઠળ સૂચિબદ્ધ ચેટ-ફેમિલી રૂટ્સ):

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ લિસ્ટ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ગાર્ડરેલ્સને ઊંચતા પ્રાથમિકતા ક્રમમાં ચલાવે છે:
   - ડિસેબલ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall` `modifiedPayload` દ્વારા પેલોડને ફરીથી લખી શકે છે.
   - પ્રથમ `block: true` ચેઈનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવતઃ ફરી લખાયેલ) પેલોડ કોમ્બો રૂટિંગ અને અપસ્ટ્રીમ ડિસ્પેચમાં વહે છે.
4. **ફક્ત નોન-સ્ટ્રીમિંગ:** પ્રતિસાદ એકત્રિત થયા પછી, `guardrailRegistry.runPostCallHooks(...)` પ્રતિસાદ પર સમાન ચેઈન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ પ્રતિસાદને કાઢી નાખે છે અને HTTP 400 પરત કરે છે. સ્ટ્રીમ કરેલા પ્રતિસાદો આ પગલું સંપૂર્ણપણે અવગણે છે.

થ્રો કરનારા ગાર્ડરેલ્સ `error: <message>` સાથે નોંધાય છે અને `logger.warn` દ્વારા લોગ થાય છે, પરંતુ ચેઈન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેલ-ઓપન.

## કવરેજ અને મર્યાદાઓ

ગાર્ડરેલ રજિસ્ટ્રી ફક્ત ચેટ પાઇપલાઇનમાં જ વાયર્ડ છે. આ મર્યાદાઓ `tests/unit/guardrail-pipeline-wiring-characterization.test.ts` અને `tests/unit/guardrail-pipeline-characterization.test.ts` દ્વારા પિન કરવામાં આવી છે; વર્તન બદલાય ત્યારે તે ટેસ્ટ્સને જાણીજોઈને અપડેટ કરો.

### શું કવર થતું નથી

- **મીડિયા, એમ્બેડિંગ્સ અને ડેટા રૂટ્સ** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) રજિસ્ટ્રી સુધી ક્યારેય પહોંચતા
  નથી. ત્યાં કોઈ PII માસ્કિંગ, ક્રેડેન્શિયલ માસ્કિંગ કે મોડાલિટી બ્રિજ ચાલતું
  નથી. તેમની એકમાત્ર તપાસ લિગસી ઇન્જેક્શન-ગાર્ડ મિડલવેર છે.
- **સ્ટ્રીમ કરેલા પ્રતિસાદો**ને કોઈ પોસ્ટ-કોલ ગાર્ડરેલ્સ મળતા નથી: કોઈ `pii-masker`
  કે `credential-masker` પોસ્ટ-કોલ નહીં, અને કોઈ પોસ્ટ-કોલ બ્લોક નહીં. ફક્ત સ્ટ્રીમિંગ PII
  ટ્રાન્સફોર્મ લાગુ પડે છે (જ્યારે `PII_RESPONSE_SANITIZATION` ચાલુ હોય). સ્ટ્રીમ કરેલા
  પ્રતિસાદમાં ઇકો થયેલું ક્રેડેન્શિયલ રિડૅક્ટ થતું નથી.
- **ડિસેબલ ચેનલો વિરુદ્ધ મિડલવેર (ડિઝાઇન મુજબ):** મિડલવેર કોઈપણ કોલર-નિયંત્રિત
  ડિસેબલ લિસ્ટ પાસ કર્યા વગર, `evaluatePromptInjection()` ના પોતાના કોલથી પ્રોમ્પ્ટ
  ઇન્જેક્શનનું મૂલ્યાંકન કરે છે. `block` મોડ એ ફરજિયાત સીमा છે જેને કોલર-નિયંત્રિત
  ડિસેબલ બાયપાસ કરી શકતા નથી, ચેટ-ફેમિલી રૂટ્સ પર પણ નહીં
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). `prompt-injection`
  ને ડિસેબલ કરવું ફક્ત રજિસ્ટ્રી ગાર્ડરેલને જ સ્કિપ કરે છે.

### પોસ્ટ-કોલ પહેલાં પ્રતિસાદ શું જુએ છે

નોન-સ્ટ્રીમિંગ પાથ પર ક્રમ આ છે: મેમરી એક્સટ્રેક્શન → બિલ્ટ-ઇન ટૂલ
એક્ઝિક્યુશન → પોસ્ટ-કોલ ગાર્ડરેલ્સ → પોસ્ટ-કોલ બ્લોક એક્ઝિટ → સિમેન્ટિક-કેશ સ્ટોર.

- **મેમરી એક્સટ્રૅક્શન** અને **ટૂલ એક્ઝિક્યુશન** post-call ગાર્ડરેલ્સ
  પ્રતિભાવને ફરીથી લખી શકે અથવા બ્લોક કરી શકે તે પહેલાં જ તેને જુએ છે.
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) થી, જ્યારે
  `PII_RESPONSE_SANITIZATION` ચાલુ હોય ત્યારે મેમરી એક્સટ્રૅક્શન એક્સટ્રૅક્ટ
  કરેલા ટેક્સ્ટને `sanitizePII` મારફતે પસાર કરે છે (સ્ટ્રીમિંગ અને
  નોન-સ્ટ્રીમિંગ બંનેમાં), પરંતુ post-call પછી બ્લોક થતો પ્રતિભાવ તે પહેલાં જ
  મેમરી અને ટૂલ્સને આપવામાં આવ્યો હોય છે.
- **સિમેન્ટિક કેશ** post-call પછી પ્રતિભાવ સંગ્રહે છે, તેથી તે ફરીથી લખાયેલો
  પ્રતિભાવ સંગ્રહે છે, અને બ્લોક થયેલો પ્રતિભાવ ક્યારેય કેશ થતો નથી. કેશ
  એન્ટ્રીઓ દરેક API કી પ્રમાણે અલગ રાખવામાં આવે છે.

## રૂપરેખાંકન

બિલ્ટ-ઇન ગાર્ડરેલ્સ દ્વારા વાંચવામાં આવતા એન્વાયરનમેન્ટ વેરિએબલ્સ:

| વેરિએબલ                               | દ્વારા વપરાય છે            | અસર                                                                                                     |
| ------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | ડિટેક્શન સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                    |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | ઇન્જેક્શન નીતિ: `warn`, `block`, અથવા `log`. લેગસી મૂલ્ય `redact` ઇન્જેક્શન ટેક્સ્ટને ફરીથી લખતું નથી.  |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | ઇન્જેક્શન ગાર્ડ માટેનો મોડ; તે એક DB ફીચર ફ્લેગ પણ છે જે env વેરિએબલ્સને **ઓવરરાઇડ** કરે છે (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` જે નામંજૂર કરે છે તેની લઘુત્તમ ગંભીરતા: `high` (ડિફોલ્ટ), `medium`, અથવા `low`.            |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` માટે લેગસી ઉપનામ.                                                     |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | જ્યારે `true` હોય, ત્યારે રિક્વેસ્ટ PII રિડેક્ટ કરવામાં આવે છે (ઇન્જેક્શન મોડથી સ્વતંત્ર).              |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ડાઉનસ્ટ્રીમ) | રિસ્પોન્સ-સાઇડ માસ્કર વર્તનને નિયંત્રિત કરે છે.                                                         |

Modality Bridge ગાર્ડરેલ્સ રનટાઇમ કોન્ફિગ DB-સમર્થિત સેટિંગ્સ
સ્ટોર (`getSettings()`) માંથી વાંચે છે, env વેરિએબલ્સમાંથી નહીં. Vision ની પ્રાથમિક કીઓ
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને
`modalityBridgeCacheMaxEntries` છે. લેગસી
`visionBridge*` કીઓ ફક્ત દસ્તાવેજીકૃત વન-સાયકલ રીડ
ફોલબેક તરીકે સ્વીકારવામાં આવે છે; ડેશબોર્ડ રાઇટ્સ પ્રાથમિક કીઓનો ઉપયોગ કરે છે. ડિફોલ્ટ્સ અને ફોલબેક
રિઝોલ્વર `src/shared/constants/modalityBridgeDefaults.ts` માં રહે છે, જ્યારે લેગસી
કોન્સ્ટન્ટ્સ `src/shared/constants/visionBridgeDefaults.ts` માં જાળવવામાં આવ્યા છે.

ઓડિયો `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail` ને વિસ્તારતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે રજિસ્ટર કરો (`registerDefaultGuardrails` માંથી પુશ કરીને) અથવા
   રનટાઇમે `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન
   નોર્મલાઇઝ્ડ નામ ધરાવતા અગાઉના કોઈપણ ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ ટેસ્ટ ઉમેરો (હાલના ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

ટેસ્ટો વચ્ચે જાણીતી સ્થિતિથી શરૂઆત કરવા માટે `resetGuardrailsForTests()` વાપરો.
ખાલી રજિસ્ટ્રીથી શરૂ કરવા અને ફક્ત પરીક્ષણ હેઠળના ગાર્ડરેલ્સ જ રજિસ્ટર કરવા માટે
`{ registerDefaults: false }` પાસ કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન સ્વીકારે છે (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge સેટિંગ્સ, ક્ષમતાઓ, STT મોડલ પસંદગી, ક્રેડેન્શિયલ
તપાસો અને ટ્રાન્સક્રિપ્શન માટે સમાન સીમ્સ એક્સપોઝ કરે છે. તેથી ટેસ્ટો DB
અથવા નેટવર્ક ઍક્સેસ વગર બંને ફ્લોનું પરીક્ષણ કરી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લોક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) યુઝર પ્રોમ્પ્ટ સ્વીકારતા
તમામ રૂટ્સને કવર કરે છે. તે `INJECTION_GUARD_MODE` નું પાલન કરે છે (ડિફૉલ્ટ `warn` = ફક્ત લોગ;
`block` = HTTP 400 `SECURITY_001` પરત આપે છે).

| પ્રકાર          | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલના) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા            | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ એક્સ્ટ્રૅક્શન (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ને કવર કરે છે.

**રેડ-ટીમ (નાઇટલી, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે `INJECTION_GUARD_MODE=block` માં
દરેક રૂટ OWASP-LLM કોર્પસને બ્લોક કરે છે; garak પ્રોબ્સ ચલાવે છે (સિક્રેટ વગર સ્કિપ કરે છે).
સુસંગતતા માટે `moderations` સામેલ છે. બ્લોક મોડ એક ફરજિયાત સીમા છે: `evaluatePromptInjection()`
મિડલવેર તેને પાસ કરેલી પ્રતિ-રિક્વેસ્ટ ડિસેબલ યાદીને અવગણે છે, તેથી `disabledGuardrails`
કોઈ રૂટને તેનાથી મુક્તિ આપતું **નથી** ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

નાઇટલી વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ) માં બે જોબ્સ છે:

- **`promptfoo-guard` (અવરોધક)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ
  (દા.ત. "અગાઉની તમામ સૂચનાઓને અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે
  પ્રતિભાવમાં `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે ખરેખર
  રિક્વેસ્ટ નકારી છે.
- **`garak` (સલાહકાર)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ (`http://localhost:20128/v1`)
  સામે garak `--probes promptinject,dan,leakreplay` ચલાવે છે. પ્રોવાઇડર
  સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સુવ્યવસ્થિત રીતે સ્કિપ કરે છે અને
  `|| true` સફિક્સ ધરાવે છે, તેથી CI નિષ્ફળ કર્યા વગર રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`) નું કવરેજ
દરેક પ્રોમ્પ્ટ-ધરાવતા `/v1` રૂટ સુધી ફેલાયેલું છે; પ્રોમ્પ્ટ ટેક્સ્ટ
`src/shared/utils/inputSanitizer.ts` માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` માંથી ખેંચવામાં આવે છે.
