> **છેલ્લે અપડેટ:** 2026-10-17 — v3.8.52 ([Coverage and limits](#coverage-and-limits) ઉમેર્યું):
> હૂક્સ કયા રૂટ્સ અને રિસ્પોન્સ પાથ સુધી પહોંચે છે, મર્જ થયેલા ડિસેબલ હેડર્સ (#16412), ફરજિયાત બાઉન્ડરી તરીકે ઇન્જેક્શન
> બ્લોક મોડ (#16413), અને post-call પહેલાં રિસ્પોન્સને શું જુએ છે

Guardrails એ OmniRoute અને અપસ્ટ્રીમ પ્રોવાઇડર્સ વચ્ચેની બાઉન્ડરી પર
સેફ્ટી, પોલિસી અને કન્ટેન્ટ ટ્રાન્સફોર્મેશન લાગુ કરે છે. દરેક guardrail
રિક્વેસ્ટ પેલોડ (`preCall`) અને અપસ્ટ્રીમ રિસ્પોન્સ (`postCall`) ની તપાસ કરી શકે છે (અને
વૈકલ્પિક રીતે નકારી, ટ્રાન્સફોર્મ અથવા એનોટેટ કરી શકે છે).

આ સિસ્ટમ **fail-open** છે: જો કોઈ guardrail એક્ઝિક્યુટ થતી વખતે એરર ફેંકે, તો રજિસ્ટ્રી
એરર રેકોર્ડ કરે છે અને રિક્વેસ્ટ ફેલ કરવાને બદલે આગલા guardrail સાથે ચાલુ રાખે છે.
બ્લોકિંગ એ સ્પષ્ટ નિર્ણય છે (`block: true`), ક્યારેય અકસ્માત નહીં.
એક જ અપવાદ એબોર્ટ થયેલી રિક્વેસ્ટ છે: જ્યારે કૉલરનું `signal` એબોર્ટ થાય છે,
ત્યારે એરર ફેંકતું guardrail સ્કિપ થવાને બદલે હૂક રનને રિજેક્ટ કરે છે.

હૂક્સ દરેક રૂટ કે દરેક રિસ્પોન્સ પર ચાલતા **નથી**. Guardrail પર
સિક્યોરિટી કંટ્રોલ તરીકે આધાર રાખતા પહેલાં
[Coverage and limits](#coverage-and-limits) વાંચો.

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડાલિટી બ્રિજ PR-1

GLM 5.3 બેઝ મોડલ અને `glm-5.3-{low,high,max}` પાસે સ્પષ્ટ `supportsVision:false` registry/spec મેટાડેટા છે. GLM 5.3 ફ્લેશ વેરિઅન્ટ્સ નેટિવ-વિઝન મોડલ જ રહે છે. Claude કોડનો `/v1/messages` માર્ગ વહેંચાયેલ `handleChat` પ્રી-કોલ ગાર્ડ્રેલ સાંકળમાં પ્રવેશે છે** પહેલાં** ક્લાઉડ-ટુ-ઓપનએઆઈ અનુવાદ; નેસ્ટેડ `Read` ટૂલ-પરિણામ ઇમેજનું વર્ણન OpenAI `image_url` સામગ્રી (#17069) માં થાય તે પહેલાં તેનું વર્ણન અથવા હેન્ડલ કરવું આવશ્યક છે.

ઇમેજ-બેરિંગ વિનંતીઓને ધ્યાનમાં રાખીને ઇન્ટરસેપ્ટ કરે છે** નોન-વિઝન મોડલ** અને કાં તો સમગ્ર વિનંતિને વિઝન-સક્ષમ મોડેલમાં ફેરવે છે અથવા અપસ્ટ્રીમ કૉલ પહેલાં કન્ફિગરેબલ વિઝન મોડલ દ્વારા ઉત્પાદિત ટેક્સ્ટ વર્ણનો સાથે છબીના ભાગોને બદલે છે. આ ફક્ત ટેક્સ્ટ-પ્રદાતાઓને મલ્ટિમોડલ પેલોડ્સને પારદર્શક રીતે હેન્ડલ કરવા દે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડેલ પહેલાથી જ વિઝનને સપોર્ટ કરતું હોય તો છોડો (જ્યાં સુધી તે ફોર્સ્ડ-બ્રિજ સૂચિ `isVisionBridgeForcedModel` માં દેખાતું નથી).
2. `extractImageParts(messages)` (`visionBridgeHelpers.ts`) દ્વારા છબીના ભાગોને બહાર કાઢો, જે આને સોંપે છે** એકીકૃત મીડિયા ડિટેક્ટર** `detectMediaParts()` `open-sse/utils/mediaParts.ts` માં — એ કૉમ્બો સુસંગતતા ફિલ્ટર સાથે વહેંચાયેલ સત્યનો એકમાત્ર સ્રોત છે. `replaceImageParts` પાછા વિભાજિત કરી શકે તેવા આકારોમાં એક્સટ્રેક્શનને મંજૂરી આપવામાં આવી છે (અર્ક ↔ રિપ્લેસ કોન્ટ્રાક્ટ): OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL `source.type:"url"`, અને પ્રતિસાદો API `input_image`. Claude કોડ `tool_result.content` અને રિસ્પોન્સ ટૂલ આઉટપુટની અંદર નેસ્ટેડ મેચિંગ ઈમેજો પણ કાઢવામાં આવે છે અને તેમના મૂળ પાથ પર બદલવામાં આવે છે; માત્ર-સૂચક આકારો કોમ્બો-ફિલ્ટર સામગ્રી છે અને કાઢવામાં આવતા નથી. જો કોઈ મળ્યું ન હોય તો છોડો.
3. રનટાઇમ રૂપરેખાને `resolveVisionBridgeRuntimeSettings()` (`src/shared/constants/modalityBridgeDefaults.ts`) દ્વારા ઉકેલો : નવી `modalityBridge*` સેટિંગ્સ કી જીતે છે; લેગસી `visionBridge*` કી રહે છે** વન-સાયકલ ફોલબેક** (રોલબેક વિન્ડો). જ્યારે બ્રિજ અક્ષમ હોય ત્યારે કોઈપણ મીડિયા ટ્રાવર્સલ પહેલાં અવગણો.
4. મોડ સિલેક્ટર (`modalityBridgeVisionMode`, નીચે કોષ્ટક જુઓ) reroute vs describe નક્કી કરે છે. માત્ર `model` સ્વેપ કરેલ, વત્તા મેટા `{ rerouted, fromModel, toModel, imagesKept }` સાથે `modifiedPayload` પરત કરે છે.
5. પાથનું વર્ણન કરો: `maxImages` પર છબીઓ કેપ કરો, ટાસ્ક-અવેર પ્રોમ્પ્ટ કંપોઝ કરો, કેશનું વર્ણન કરો, વિઝન મોડેલને કૉલ કરો** સમાંતર માં** (`Promise.allSettled`), અને `[Image N]: <description>` ટેક્સ્ટ ભાગોને તેમની જગ્યાએ ઇન્જેક્ટ કરો. નિષ્ફળ વર્ણન `null` ઉપજ આપે છે : કાચી છબી unknown/vision-capable લક્ષ્યો (#4012) માટે સાચવેલ છે, પરંતુ a** પુષ્ટિ થયેલ ટેક્સ્ટ-ફક્ત ડાયરેક્ટ લક્ષ્ય** અથવા શૂન્ય-વિઝન કોમ્બો દરેક અનિર્ણિત છબી માટે સ્પષ્ટ `(unavailable — no vision-capable provider connected)` ટેક્સ્ટ સ્ટબ મેળવે છે, જેમાં આંશિક નિષ્ફળતાઓ અને વર્ણન-કોલ કેપ (#17069)ની બહારની છબીઓ શામેલ છે. હાલના તમામ-નિષ્ફળ કોમ્બો ફોલબેકનું વર્ણન કરે છે (#8430).
6. `modifiedPayload` + મેટા (`imagesProcessed`, `descriptions`, `processingTimeMs`, `visionModel`) પરત કરો.

#### મોડ સિલેક્ટર (`modalityBridgeVisionMode`)

| મોડ        | ડિફૉલ્ટ | વર્તન                                                                                                                                                                                                                                                                             |
| ---------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | લેગસી હ્યુરિસ્ટિક, અનટચ્ડ (#6640/#7204): નોન-કોમ્બો/`auto/` મોડલ શ્રેષ્ઠ વિઝન મોડલ પર પાછા ફરે છે સિવાય કે મૂળ મોડલ પાસે પહેલેથી જ ઉપયોગી ઓળખપત્રો હોય (પછી તેનું વર્ણન કરો); કોમ્બો લક્ષ્યો હંમેશા વર્ણવે છે.                                                                    |
| `describe` |         | હમેશા — વર્ણન કરો કે રીરુટ બ્લોક સંપૂર્ણપણે છોડી દેવામાં આવ્યો છે; વપરાશકર્તાનું પસંદ કરેલ મોડેલ હંમેશા જવાબ આપે છે.                                                                                                                                                              |
| `reroute`  |         | ફોર્સ રિરુટ: કીપ-ક્રેડેન્ટિયલ-મોડેલ ગાર્ડને બાયપાસ કરવામાં આવ્યો છે. રસ્તો-** લક્ષ્ય** ઓળખપત્ર ગાર્ડ હજુ પણ — લાગુ કરે છે જ્યારે કોઈ ઉપયોગી વિઝન લક્ષ્ય અસ્તિત્વમાં નથી, બ્રિજ ફક્ત ટેક્સ્ટ-માત્ર લક્ષ્ય પર કાચી છબીઓનું વર્ણન કરવા અથવા મોકલવાને બદલે સ્પષ્ટ ભૂલ સાથે અવરોધે છે. |

ફોર્સ્ડ મોડ્સ શોર્ટ-સર્કિટ** પહેલાં** ઓટો હ્યુરિસ્ટિક રન; `auto` વર્તણૂક pre-PR-1 ગાર્ડ્રેલ માટે બાઈટ-સમાન છે.

#### API-કી સ્કોપ (`visionBridgeKeyScope.ts`)

જ્યારે કોલરની API કી `allowedConnections`, ક્વોટા પુલ (`allowedQuotas`) અથવા મોડલ (`allowedModels` / `blockedModels` / `modelAccessMode: "restricted"` / `disableNonPublicModels`) ને પ્રતિબંધિત કરે છે, ત્યારે બ્રિજ ફક્ત રીરુટ પસંદ કરે છે અને કી ઉપયોગ કરી શકે તેવા મોડલ્સનું વર્ણન કરે છે, કી ઉપયોગ કરી શકે તેવા જોડાણો પર. વર્ણન કૉલ પછી હંમેશા `x-omniroute-self-loop-key-id` હેડર સાથે OmniRoute સ્વ-લૂપમાંથી પસાર થાય છે, તેથી પ્રાપ્ત થતી ચેટ વિનંતી તે કીના જોડાણ અને મોડેલ નીતિને ફરીથી લાગુ કરે છે. `enforceApiKeyPolicy()` તે હેડરને ફક્ત સ્વ-લૂપ બેરર સાથે મળીને સન્માનિત કરે છે, તેથી તે ફક્ત સાંકડી ઍક્સેસ કરી શકે છે, અને જે id ઉકેલતું નથી તેને નકારવામાં આવે છે.

જો કી માટે કોઈ વિઝન મોડલની પરવાનગી નથી, તો એ** પુષ્ટિ થયેલ ટેક્સ્ટ-ફક્ત લક્ષ્ય** ઇમેજ બાઇટ્સને અસમર્થ અપસ્ટ્રીમ (#17069) પર ફોરવર્ડ કરવાને બદલે સ્પષ્ટ HTTP 400 સાથે સ્થાનિક રીતે ઇમેજ વિનંતીને નકારી કાઢે છે. અજ્ઞાત અથવા મૂળ દ્રષ્ટિ ક્ષમતાવાળા લક્ષ્યો માટે, વર્ણન પાથ તેના અગાઉના નિષ્ફળ-ઓપન વર્તન (meta `{ skipped: true, reason: "no_permitted_vision_model" }`) ને જાળવી રાખે છે. ચાવી વિનાની વિનંતીઓ, અને આ નિયંત્રણો વિનાની ચાવીઓ, પહેલાની જેમ બરાબર વર્તે છે.

#### ટાસ્ક-અવેર ડિસ્ક્રાઇબ પ્રોમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફૉલ્ટ** સાચું** . `composeVisionPrompt()` (`visionBridgeHelpers.ts`) ના ટેક્સ્ટને જોડે છે** છેલ્લો વપરાશકર્તા સંદેશ** (500 અક્ષરોમાં કાપવામાં આવે છે) બેઝ ડિસ્ક્રાઇબ પ્રોમ્પ્ટ પર, વપરાશકર્તાએ ખરેખર શું પૂછ્યું હતું તેના તરફ વર્ણનનું સંચાલન કરે છે (કોડેક્સ-વિઝન-પ્રોક્સી પેટર્ન) અને વિઝન મોડેલને દૃશ્યમાન ટેક્સ્ટને ટ્રાંસ્ક્રાઇબ કરવા માટે કહે છે. ફ્લેગ ઓફ — સાથે અથવા કોઈ વપરાશકર્તા ટેક્સ્ટ — આધાર પ્રોમ્પ્ટનો ઉપયોગ યથાવત છે.

વર્ણન સ્વ-લૂપની પોતાની OpenAI- સુસંગત વિનંતી (`callVisionModelSingle()` in `visionBridgeHelpers.ts`) હંમેશા `image_url.detail: "high"` — બિનશરતી વિનંતી કરે છે, દરેક caller/provider માટે, કોઈપણ ક્લાયંટ સિગ્નલ પર ગેટેડ નથી. આ પ્રોમ્પ્ટ જે ટેક્સ્ટ-ટ્રાન્સક્રિપ્શન માટે પૂછે છે તે બરાબર માટે ઓછી-વિગતવાર સેમ્પલિંગ OCR ચોકસાઈને ઘટાડે છે, તેથી વર્ણન કૉલ પોતે જ હંમેશા ઉચ્ચ વિગત માટે પૂછે છે, પછી ભલેને મૂળ ઇનબાઉન્ડ વિનંતીનો ઉપયોગ કયા વિગત સ્તરે કરવામાં આવ્યો હોય. આ ફક્ત આંતરિક વર્ણન વિનંતીના મુખ્ય ભાગને અસર કરે છે; પ્રાથમિક વિનંતી — પર OmniRoute કૉલરના પોતાના `image_url.detail` કેવી રીતે ફોરવર્ડ કરે છે તે બદલાતું નથી કે ડિફોલ્ટ અલગથી લાગુ થાય છે, અને માત્ર `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) માં શોધાયેલ OpenCode ક્લાયન્ટ્સ માટે. ડિસ્ક્રાઇબ સેલ્ફ-લૂપની Anthropic વાયર-ફોર્મેટ શાખામાં કોઈ `detail` ફીલ્ડ નથી અને તે ડિફોલ્ટ દ્વારા અપ્રભાવિત છે.

| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

#### કેશનું વર્ણન કરો (`modalityBridge/bridgeCache.ts`)

આઉટપુટનું વર્ણન કરવા માટે ઇન-મેમરી LRU + TTL કેશ, વહેંચાયેલ પ્રક્રિયા-વ્યાપી. લંબાઈ-ઉપસર્ગ ફ્રેમિંગ સાથે કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)` (કોઈ ક્ષેત્ર-સીમા અથડામણ નથી). મોડેલ ઘટક છે** રૂપરેખાંકિત** બ્રિજ મૉડલ, જે મૉડલ વાસ્તવમાં — `callVisionModel` જવાબ આપે છે તે આંતરિક રીતે પાછું પડી શકે છે, અને પ્રયાસ દીઠ કી કરવાનું કૅશને ફ્રેગમેન્ટ કરશે. નિષ્ફળ વર્ણનો ક્યારેય કેશ થતા નથી. સેટિંગ્સ:

| કી                              | ડિફૉલ્ટ | શ્રેણી  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ ઇમેજ નોર્મલાઇઝેશન (સેલ્ફ-લૂપ describe/base64 ફેચ)

જ્યારે બ્રિજ ફેચીસ એ** દૂરસ્થ** ઇમેજ પોતે — Anthropic સ્વ-કોલનું વર્ણન કરે છે અને ક્લાઉડ-વાયર-ફોર્મેટ બેઝ64 કન્વર્ઝન (`ensureBase64ImagesForClaudeWire`), બંને `visionBridgeHelpers.ts` — માં `fetchRemoteImageAsDataUri()` દ્વારા પરિણામી ડેટા URI વિઝન-મોડલ વિનંતીમાં એમ્બેડ કરવામાં આવે તે પહેલાં `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) દ્વારા પસાર થાય છે. મોટા કદની છબીઓને a** 2048px લાંબી ધાર** (પુન: માપ કેપ OpenAI/Anthropic સાથે મેળ ખાતા પહેલાથી સર્વર-સાઇડ લાગુ કરો), જે વિઝન મોડેલ જે જુએ છે તે બદલ્યા વિના અપલોડ bytes/latency કાપે છે. માપ બદલવામાં `sharp` ઉપયોગ થાય છે, જે ગતિશીલ આયાત દ્વારા લોડ થાય છે: પ્લેટફોર્મ પર જ્યાં તેની મૂળ બાઈનરી લોડ કરવામાં નિષ્ફળ જાય છે, `normalizeDataUri()`** ક્યારેય ફેંકતું નથી** — તે મૂળ બાઈટના પાસથ્રુ પર પાછા આવે છે, તેથી describe/base64-conversion પાથ હંમેશા કામ કરતું રહે છે. બિન-ઇમેજ બાઇટ્સ (એક આનયન કે જે ડીકોડ કરી શકાય તેવી ઇમેજ પરત કરતું નથી) પણ અસ્પૃશ્યમાંથી પસાર થાય છે. આ નોર્મલાઇઝેશન બ્રિજ દ્વારા તેના પોતાના સ્વ-કોલ — માટે મેળવેલી છબીઓ માટે અવકાશિત છે, તે કૉલરના કાચા પાસથ્રુ પેલોડ પર ક્યારેય લાગુ પડતું નથી, ફક્ત ઑપ્ટ-ઇન-મ્યુટેશન સિદ્ધાંત (હાર્ડ રૂલ #20) સાથે સુસંગત છે.

#### સેટિંગ્સ સ્કીમા + સ્થળાંતર

નવી `modalityBridge*` કીઓ `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` ત્રિપુટી અને ઑડિઓ બ્રિજ દ્વારા ઉપયોગમાં લેવાતા `modalityBridgeAudio*` જૂથમાં Zod- માન્ય છે. સ્થળાંતર `141_modality_bridge_settings.sql` હાલની લેગસી `visionBridge*` મૂલ્યોને મેળ ખાતી નવી કીઝમાં નકલ કરે છે (અદમ્ય, ક્યારેય ઓપરેટર-સેટ `modalityBridge*` મૂલ્યને ઓવરરાઇટ કરતું નથી); લેગસી કી એક રીલીઝ સાયકલ માટે રીડ ફોલબેક તરીકે સ્વીકારવામાં આવે છે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન-રૂપાંતરિત પ્રતિસાદો `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` ધરાવે છે ( `modalityBridge/bridgeStats.ts` માં `buildModalityBridgeHeader()` દ્વારા બનાવેલ, `src/sse/handlers/chatHelpers.ts` માં `withModalityBridgeHeader()` દ્વારા સ્ટેમ્પ્ડ). પુનઃપ્રાપ્ત વિનંતીઓ મળે છે** ના** હેડર — પેલોડ અસ્પૃશ્ય હતું અને પ્રતિભાવ બોડીના `model` ફીલ્ડમાં મોડેલ સ્વેપ પહેલેથી જ દૃશ્યમાન છે.

`GET /api/modality-bridge/stats` (મેનેજમેન્ટ ઓથ, `GET /api/settings` જેવું જ સ્તર) `vision`, `audio` અને `video` માટે ઇન-મેમરી પ્રતિ-મોડલિટી કાઉન્ટર્સ `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` પરત કરે છે. `averageLatencyMs` તેના છેદ તરીકે `latencySamples` ઉપયોગ કરે છે, બધા પ્રયાસો નહીં; સમય વગરનું ઓપરેશન શૂન્ય-મિલિસેકન્ડના નમૂનાનું નિર્માણ કરતું નથી. `bridged` સફળ રૂપાંતરણ માટે બેકવર્ડ-સુસંગત ઉપનામ રહે છે; નિષ્ફળ પ્રયાસો તેને વધારતા નથી. ડિઝાઇન દ્વારા પ્રક્રિયા પુનઃપ્રારંભ પર કાઉન્ટર્સ રીસેટ (ટેલિમેટ્રી, એકાઉન્ટિંગ નહીં).

#### ડેશબોર્ડ ગોઠવણી

The dedicated dashboard page is `/dashboard/settings/modality-bridge`. Its URL-addressable `Vision`, `Audio`, and `Video` tabs preserve query parameters while switching the `tab` value. The Vision tab exposes enablement, mode, model selection (including the automatic default), task-aware prompting, advanced timeout/image/description-length/cache limits, runtime counters, and a guarded sample request. The Audio tab is also live: it exposes enablement, an STT-only model picker with Auto, timeout/max-clip limits, audio counters, and an `input_audio` sample test. The Video tab is functional: it reports the FFmpeg/ffprobe runtime state — one of four explicit UI states (`unknown` while the probe is in flight or could not complete, `restricted` on a non-loopback dashboard host where the probe is skipped client-side, `unavailable` once probed and confirmed missing, or `available` with the FFmpeg/ffprobe versions) — persists enable/model/frame/video/timeout limits, filters the model picker to vision-capable models, and exposes video counters.

AI સેટિંગ્સ હેઠળનું ભૂતપૂર્વ વિઝન બ્રિજ કાર્ડ નવા પૃષ્ઠની સુસંગતતા લિંક છે; તે હવે ફોર્મની બીજી નકલની માલિકી ધરાવતું નથી. મીડિયા પ્રદાતાઓ ઇમેજ-ટુ-ટેક્સ્ટ અને સ્પીચ-ટુ-ટેક્સ્ટ વર્કફ્લોને અનુરૂપ મોડાલિટી બ્રિજ ટેબ્સ સાથે વર્તમાન સ્પીચ-ટુ-ટેક્સ્ટ પ્લેગ્રાઉન્ડને દૂર કર્યા વિના પણ લિંક કરે છે.

**સ્વ-લૂપ પ્રવેશ બાયપાસ:** જ્યારે OmniRoute ના પોતાના `/v1` સેલ્ફ-લૂપ (નોન-સ્ટાન્ડર્ડ પ્રોવાઈડર મોડલ) દ્વારા કોલ રૂટ્સનું વર્ણન કરવામાં આવે છે, ત્યારે પેટા-વિનંતી `x-omniroute-admission-bypass: internal` મોકલે છે અને સ્થાનિક મોડમાં સ્થાનિક `sk_omniroute` સેન્ટિનલ — અથવા ઑપરેટર-રૂપરેખાંકિત `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350 enqqzqyplo) દ્વારા ઉકેલાયેલ સ્વ-લૂપ ઓળખપત્ર સાથે પ્રમાણિત કરવામાં આવે છે. હજુ પણ `REQUIRE_API_KEY=true` કૉલ ચલાવી શકે છે. બાયપાસ ફક્ત તે ચોક્કસ ઓળખપત્રો માટે સન્માનિત કરવામાં આવે છે, તેથી બાહ્ય ક્લાયન્ટ્સ પ્રવેશ છોડવા માટે હેડરનો ઉપયોગ કરી શકતા નથી.

લેગસી ડિફોલ્ટ્સ `src/shared/constants/visionBridgeDefaults.ts` માં રહે છે; નવા mode/task-aware/cache ડિફોલ્ટ્સ અને સેટિંગ્સ રિઝોલ્વર `src/shared/constants/modalityBridgeDefaults.ts` માં રહે છે. ગાર્ડરેલ એક `deps` કન્સ્ટ્રક્ટર વિકલ્પને ઉજાગર કરે છે જેથી પરીક્ષણો નકલી `getSettings` અને `callVisionModel` અમલીકરણને ઇન્જેક્ટ કરી શકે.

### ઓડિયો બ્રિજ (`audioBridge.ts`) — મોડાલિટી બ્રિજ PR-3

ઑડિયો-બેરિંગ ચેટ વિનંતીઓને તેઓ લક્ષ્ય સુધી પહોંચે તે પહેલાં અટકાવે છે જે ઑડિઓ ઇનપુટ સ્વીકારવા માટે જાણીતું નથી. તે ચેટ વિનંતીને ક્યારેય રૂટ કરતું નથી: ઑડિઓ ભાગો હાલના OpenAI- સુસંગત મલ્ટિપાર્ટ એન્ડપોઇન્ટ દ્વારા ટ્રાન્સક્રિપ્ટ કરવામાં આવે છે અને પસંદ કરેલ ચેટ મોડલ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ સાથે ચાલુ રહે છે.

પ્રવાહ:

1. `supportsAudio` `getResolvedModelCapabilities()` દ્વારા ઉકેલો. સ્પષ્ટ પ્રદાતા-રજિસ્ટ્રી મેટાડેટા જીતે છે, પછી સ્થિર મોડેલ મેટાડેટા, પછી સમન્વયિત `modalities_input`. `audio` વિના જાહેર કરેલ ઇનપુટ યાદી `false` છે; કોઈ ક્ષમતાનો પુરાવો `null` રહેતો નથી. `false` અને `null` બંને રૂઢિચુસ્ત પુલને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સને ઉકેલો અને શેર કરેલ `detectMediaParts()` ડિટેક્ટર દ્વારા દરેક સંદેશમાંથી વિભાજિત કરી શકાય તેવા ઉચ્ચ-સ્તરના ઑડિઓ ભાગોને બહાર કાઢો. સપોર્ટેડ વાયર આકારો OpenAI `input_audio`, `audio_url`, અને `source.media_type: "audio/*"` છે. નેસ્ટેડ ઓડિયો રૂટીંગ માટે શોધાયેલ છે પરંતુ સ્પ્લીસ પાથ દ્વારા દૂર કરવામાં આવ્યો નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે; પછીના ભાગો અસ્પૃશ્ય રહે છે.
3. રૂપરેખાંકિત `provider/model` સન્માન કરો, અથવા `selectAudioBridgeModel()` `AUDIO_TRANSCRIPTION_PROVIDERS` સ્થિર કેટલોગ ક્રમમાં ચાલવા દો અને ઉપયોગી સક્રિય પ્રદાતા ઓળખપત્ર સાથે પ્રથમ મોડેલ પસંદ કરો.
4. `callAudioTranscription()` base64/data-URI ઑડિયોને મલ્ટિપાર્ટ `file` માં રૂપાંતરિત કરે છે, અથવા DNS પિનિંગ અને 25 MB બાઉન્ડ સાથે પબ્લિક-ઓન્લી આઉટબાઉન્ડ ગાર્ડ દ્વારા રિમોટ `audio_url` ડાઉનલોડ કરે છે. તે પછી ફાઇલને POSTs અને સ્થાનિક `/v1/audio/transcriptions` સ્વ-લૂપમાં પસંદ કરેલ મોડેલને `resolveSelfLoopBearer()` સાથે પ્રમાણિત કરે છે. વર્તમાન ટ્રાન્સક્રિપ્શન રૂટ સામાન્ય ઓળખપત્ર લુકઅપ, cooldown/rate-limit હેન્ડલિંગ અને પ્રદાતા રવાનગી કરે છે.
5. સફળ કૉલ્સ તેમના ભાગોને `[Audio N]: <transcript>` થી બદલે છે. કૉલ્સ `Promise.allSettled` સાથે ચાલે છે: વ્યક્તિગત નિષ્ફળતા તે મૂળ ઑડિઓ ભાગને સાચવે છે (#4012 કરાર). જો દરેક કૉલ નિષ્ફળ જાય અને લક્ષ્ય `supportsAudio === false` સાબિત થાય, તો ભાગો `[Audio N]: (unavailable — no STT provider connected)` (#8430 કરાર) બની જાય છે. અજ્ઞાત લક્ષ્ય (`null`) માટે, તમામ-નિષ્ફળતા પરિણામ અસ્પૃશ્ય રહે છે. ઉપયોગ કરી શકાય તેવા STT ઓળખપત્ર વગરનું સાબિત લખાણ-માત્ર લક્ષ્ય નેટવર્ક કૉલ જારી કર્યા વિના સમાન સ્પષ્ટ સ્ટબ મેળવે છે.

સફળ ટ્રાન્સક્રિપ્ટ પ્રક્રિયા-વ્યાપી મોડાલિટી બ્રિજ LRU/TTL કેશનો ઉપયોગ કરે છે. કી ઑડિયો સંદર્ભ, સ્થિર `audio-transcription` ઑપરેશન લેબલ અને પસંદ કરેલ STT મોડલને જોડે છે; નિષ્ફળતાઓ ક્યારેય કેશ થતી નથી. ઓડિયો પ્રયાસો શેર કરેલ `bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સને અપડેટ કરે છે. રૂપાંતરિત પ્રતિભાવો `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` વહન કરે છે; અસ્પૃશ્ય વિનંતીઓ ઑડિઓ બ્રિજ સેગમેન્ટ પ્રાપ્ત કરતી નથી.

રનટાઇમ સેટિંગ્સ DB-બેક્ડ અને Zod-માન્ય છે:

| કી                            | ડિફૉલ્ટ | શ્રેણી          |
| ----------------------------- | ------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —               |
| `modalityBridgeAudioModel`    | `""`    | ઓટો અથવા STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10            |

વહેંચાયેલ કેશ `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` દ્વારા નિયંત્રિત રહે છે.

### વિડીયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ચેટ કમ્પ્લીશન્સ `messages` માં ટોપ-લેવલ વિડીયો પાર્ટ્સને ઇન્ટરસેપ્ટ કરે છે અને API `input` જાણીતા નેટીવ વિડીયો સપોર્ટ વગરના ટાર્ગેટને બોલાવવામાં આવે તે પહેલા પ્રતિસાદ આપે છે. સપોર્ટેડ આકારો `input_video`, `video_url`, `video_source`, HTTPS URLs, અને `data:video/*;base64,...` ડેટા URIs છે. ટેક્સ્ટમાં સાદા ફાઇલનામોને વિડિયો તરીકે ગણવામાં આવતા નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતી ટ્રાવર્સલ, capability/policy ચેક, પ્રતિ-વિનંતી એકત્રીકરણ અને પ્રતિભાવ પેલોડની માલિકી ધરાવે છે. પ્રતિ-વિડિયો કાર્ય — સંપાદન, સંપૂર્ણ-પરિણામ કેશ, ફ્રેમ ક્રમનું વર્ણન કરતી (જે કોઈપણ કોલર-ઘોષિત ઑડિઓ ટ્રાન્સક્રિપ્ટને ફ્યુઝ કરે છે), અને પ્રતિ-પ્રયાસ metrics/abort/cleanup — `videoBridgePipeline.ts` માં `processVideoPart` પાછળ છુપાયેલ છે, જેને `preCall` ના લૂપની અંદર વિડિઓ ભાગ દીઠ એકવાર કહેવાય છે. તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓ `VideoMediaBrokerPort` (બાઇટ્સ મેળવવી અને નમૂનારૂપ ફ્રેમ્સ કાઢવા), `VideoAudioTranscriptionPort` (સેમ્પલ કૅપ્શન્સ સાથે કૉલર-ઘોષિત ઑડિઓ ટ્રાન્સક્રિપ્ટને ફ્યુઝ કરીને), અને `VideoDrilldownPort` (લેગસી કાચો-સ્ટોર આકાર) પણ વ્યાખ્યાયિત કરે છે. ઉત્પાદન STT અને ફ્રેમ રીટેન્શન `createVideoSttAdapter` અને `createVideoDrilldownAdapter` દ્વારા વર્ણન કરતા પોર્ટની આસપાસ બનેલું છે; બાદમાં વહેંચાયેલ અપારદર્શક-હેન્ડલ જીવનચક્રનો ઉપયોગ કરે છે.

સાર્વજનિક `/v1` વિનંતી પાથ ક્યારેય સબપ્રોસેસની આયાત અથવા વિનંતી કરતું નથી. રિમોટ વિડિયોઝ 50 MiB બાઉન્ડ હેઠળ ડાઉનલોડ થાય છે; ઇનલાઇન બેઝ64 વિડિયોઝમાં રૂઢિચુસ્ત 36 MiB ડીકોડેડ પ્રતિ-વિડિયો કેપ હોય છે જેથી model/messages/framing એન્વલપ 50 MiB ની જાહેર JSON વિનંતીની પ્રવેશ મર્યાદાની અંદર રહી શકે. ફાળવણી પહેલાં ઇનલાઇન લંબાઈ અને ડીકોડેડ-કદના અંદાજો તપાસવામાં આવે છે. DNS પિનિંગ સાથે હાલના પબ્લિક-ઓન્લી આઉટબાઉન્ડ ગાર્ડનો ઉપયોગ કરીને પ્રારંભિક રિમોટ URL અને દરેક રીડાયરેક્ટ પર HTTPS જરૂરી છે. પછી બાઇટ્સ ચોક્કસ આંતરિક `POST /api/modality-bridge/video/extract` બ્રોકર સીમાને પાર કરે છે. તે રૂટ `LOCAL_ONLY` અને `SPAWN_CAPABLE` બંને છે, માત્ર પ્રતિ-પ્રક્રિયા પ્રમાણિત, વિશ્વસનીય-લૂપબેક વિનંતી સ્વીકારે છે, અને ક્યારેય URL, ફાઇલસિસ્ટમ પાથ, એક્ઝેક્યુટેબલ અથવા દલીલ સૂચિને સ્વીકારતું નથી. API બોડી-સાઇઝ પાઇપલાઇન અને હેન્ડલરના ઇન્ક્રીમેન્ટલ બોડી રીડર સ્વતંત્ર રીતે 50 MiB બ્રોકર ઇનપુટ કેપ લાગુ કરે છે. તેની બાઉન્ડેડ કતાર એક સમયે એક નિષ્કર્ષણ ચલાવે છે, ચાર બાકી નોકરીઓને મંજૂરી આપે છે અને 100 MiB પર પેન્ડિંગ ઇનપુટ કેપ્સ કરે છે.

બ્રોકરની અંદર, `ffprobe` ખાનગી સ્થાનિક ફાઇલ વાંચે છે; નિશ્ચિત ફોર્મેટ મંજૂર સૂચિમાં પ્લેલિસ્ટ અને મેનિફેસ્ટ ફોર્મેટનો સમાવેશ થતો નથી. મંજૂર MOV-ફેમિલી કન્ટેનર માટે, બાહ્ય MOV ડેટા સંદર્ભો ડિફૉલ્ટ રૂપે અક્ષમ રહે છે, અને નિશ્ચિત આદેશ તેમને પસંદ કરતું નથી. `ffprobe` અને `ffmpeg` બંને `file` -only પ્રોટોકોલ વ્હાઇટલિસ્ટ, એક થ્રેડ, નિશ્ચિત દલીલ એરે, કોઈ શેલ અને `PATH` માંથી ઉકેલાયેલ એક્ઝિક્યુટેબલનો ઉપયોગ કરે છે. જોડાયેલ-ચિત્ર કવર સ્ટ્રીમ રમવા યોગ્ય ઉમેદવારો નથી. તમામ વગાડી શકાય તેવા સ્ટ્રીમ્સે મર્યાદાઓને સંતોષવી આવશ્યક છે, અને નિર્ણાયક લઘુત્તમ-ઇન્ડેક્સ ફોલબેક પહેલાં સ્પષ્ટ ડિફોલ્ટ સ્ટ્રીમને પ્રાધાન્ય આપવામાં આવે છે. વિડિઓઝ 600 સેકન્ડ, 8,192 પિક્સેલ્સ પ્રતિ પરિમાણ અને 33,554,432 સ્રોત પિક્સેલ્સ સુધી મર્યાદિત છે. FFmpeg સેમ્પલ 1-16 મિડપોઇન્ટ JPEG ફ્રેમ્સ, નાના ઇનપુટ્સને અપસ્કેલ કર્યા વિના લાંબા કિનારે મહત્તમ 1,024 પિક્સેલ સુધી સ્કેલ કરે છે, અને ક્યારેય URL પ્રાપ્ત કરતું નથી. સેમ્પલિંગ મૂળભૂત રીતે `uniform` છે. વૈકલ્પિક `scene_aware` અને પ્રાયોગિક `segment_aware` નીતિઓ પહેલાથી જ માન્ય સ્થાનિક સ્ટ્રીમ પર એક વધારાનો નિશ્ચિત FFmpeg પાસ કરે છે, બાઉન્ડેડ `showinfo` સીન ટાઇમસ્ટેમ્પ પસંદ કરે છે અને ડિટેક્ટર નિષ્ફળતા, સમયસમાપ્તિ, દૂષિત આઉટપુટ અથવા ખાલી ઉમેદવાર સેટ પર સમાન સમાન મધ્યબિંદુઓ પર નિશ્ચિતપણે પાછા ફરે છે. સેગમેન્ટ-અવેર મોડ માન્ય દ્રશ્ય અંતરાલો માટે પ્રમાણસર મધ્યબિંદુ નમૂનાઓ ફાળવે છે; સેગમેન્ટ-અવેર પુરાવા અને ફોલબેક વર્તન નીચે વિગતવાર છે. હાર્ડ 16-ફ્રેમ કેપ દરેક પોલિસીમાં પસંદગી પછી લાગુ કરવામાં આવે છે. જ્યારે દ્રશ્ય-જાગૃત વિનંતીમાં માત્ર એક-ફ્રેમ બજેટ હોય છે, ત્યારે તે સક્રિય પૂર્ણ-વિડિયો અથવા ફોકસ વિન્ડોના સમાન મધ્યબિંદુનો ઉપયોગ કરે છે અને `policyEffective: uniform` નો અહેવાલ આપે છે: એક પસંદ કરેલ દ્રશ્ય ફ્રેમ બંને ટેમ્પોરલ છેડાને સાચવી શકતી નથી. કોલર વૈકલ્પિક રીતે મર્યાદિત ફોકસ વિન્ડો પ્રદાન કરી શકે છે (`start`/`end` સેકન્ડ્સ); બાઉન્ડ્સને મીડિયા અવધિ સાથે ક્લેમ્પ કરવામાં આવે છે, વિપરીત અથવા બિન-મર્યાદિત વિંડોઝને નકારી કાઢવામાં આવે છે, અને તમામ નમૂના નીતિઓ સામાન્ય અંતરાલની અંદર જ કરવામાં આવે છે. પરિણામી વિન્ડો સેમ્પલિંગ મેટાડેટામાં અને અવિશ્વસનીય વર્ણન ઉપસર્ગમાં સમાવવામાં આવેલ છે જેથી ડાઉનસ્ટ્રીમ મોડલ્સ સંપૂર્ણ સમયરેખામાંથી કેન્દ્રિત અવતરણને અલગ કરી શકે.

સિમેન્ટીક કૅપ્શન ફોકસ એ એક અલગ, સ્પષ્ટ સેટિંગ છે. ડિફૉલ્ટ `full` પૃથ્થકરણ મોડ હાલના ફ્રેમ પ્રોમ્પ્ટને સાચવે છે અને વિનંતીના ટેક્સ્ટને કૅપ્શન મોડલમાં ક્યારેય ફોરવર્ડ કરતું નથી. `focused` મોડમાં, બ્રિજ એ જ ચેટ અથવા રિસ્પોન્સ કન્ટેનરમાંથી ફક્ત નવીનતમ બિન-ખાલી વપરાશકર્તા-લેખિત `text`/`input_text` વાંચે છે, તેને NFC પર સામાન્ય બનાવે છે, નિયંત્રણ અક્ષરો અને વ્હાઇટસ્પેસને સંકુચિત કરે છે, અને તેને 500 યુનિકોડ કોડ પોઇન્ટ્સ સુધી મર્યાદિત કરે છે. ખાલી પરિણામ ચોક્કસ `full` પ્રોમ્પ્ટ પર પાછું આવે છે. સમર્પિત અવિશ્વસનીય-વપરાશકર્તા-સંદર્ભ બ્લોકમાં ઉપયોગી સંકેતને JSON તરીકે શ્રેણીબદ્ધ કરવામાં આવે છે અને તે માત્ર અવલોકનક્ષમ વિગતોને પ્રાથમિકતા આપી શકે છે; તે મીડિયામાં દેખાતી અથવા સાંભળી શકાય તેવી નીચેની સૂચનાઓ સામે અલગ ચેતવણીને ઓવરરાઇડ કરી શકતી નથી. ટેક્સ્ચ્યુઅલ ફોકસ ક્યારેય `start`/`end` અનુમાન કરતું નથી અથવા ટેમ્પોરલ સેમ્પલરમાં ફેરફાર કરતું નથી.

#### FU-07 માળખાકીય સેગમેન્ટ પુરાવા

`segment_aware` પહેલાથી માન્ય સ્થાનિક વિડિયો સ્ટ્રીમ પર એક બાઉન્ડેડ પૂર્વ-વિશ્લેષણ પાસનો ઉપયોગ કરે છે. ફિક્સ્ડ ફિલ્ટર ચેઇન પહેલા વધુમાં વધુ 320 પિક્સેલ્સ પહોળાઈ સુધી સ્કેલ કરે છે, દ્રશ્ય ફેરફારો અને સ્થિર અંતરાલોને શોધે છે, પછી અસ્પષ્ટતા, સરેરાશ લુમા અને spatial/temporal માહિતી માટે 1 ફ્રેમ પ્રતિ સેકન્ડના દરે નમૂનાઓ. પાસ 600 માળખાકીય નમૂનાઓ, એક FFmpeg/filter થ્રેડ, સમાન `file` -only પ્રોટોકોલ અને કન્ટેનર મંજૂર સૂચિઓ, 1 MiB પ્રક્રિયા-આઉટપુટ બાઉન્ડ અને બ્રોકરના શેર કરેલ abort/deadline. ની અંદર વધુમાં વધુ 30 સેકન્ડ સુધી મર્યાદિત છે તે ક્યારેય આદેશ, ફિલ્ટર, પાથ અથવા URL તરફથી વિનંતી સ્વીકારતું નથી.

માળખાકીય મૂલ્યો નિર્ણાયક નમૂનાના પુરાવા છે, સિમેન્ટીક વિડિયો સમજણ નથી. તેઓ વિષયો, ક્રિયાઓ, કૅપ્શન્સ, ભાષણ અથવા વપરાશકર્તાના ઉદ્દેશ્યનું અનુમાન કરતા નથી. દ્રશ્ય અને સ્થિર સીમાઓ વિભાગો બનાવે છે; ફ્રીઝ કવરેજ, અસ્પષ્ટતા, એક્સપોઝર, અવકાશી વિગતો અને ટેમ્પોરલ ફેરફાર ફક્ત વર્તમાન 1-16 ફ્રેમ બજેટને કેવી રીતે ફાળવવામાં આવે છે તે પ્રભાવિત કરે છે. સંપૂર્ણ સ્થિર સેગમેન્ટને એક ફ્રેમ પર કેપ કરવામાં આવે છે, જ્યારે નોન-ફ્રોઝન સેગમેન્ટ બાકીના બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓ ફ્રેમની સંખ્યા કરતાં વધી જાય છે, ત્યારે સમાન સમયરેખા કવરેજ જાળવી રાખવામાં આવે છે જેથી ઝડપી પ્રારંભિક કાપ લાંબા પાછળના ભાગને છુપાવી શકતા નથી. ફ્રીઝ બાઉન્ડ્રીના 1-સેકન્ડના વિશ્લેષણ રિઝોલ્યુશનની અંદર સીન સીમાઓ એકસાથે કરવામાં આવે છે.

ગુમ થયેલ ફિલ્ટર્સ, malformed/empty પુરાવા, ડિટેક્ટર ભૂલ અથવા બાઉન્ડેડ પૂર્વ-વિશ્લેષણ સમયસમાપ્તિ ચોક્કસ યુનિફોર્મ મિડપોઇન્ટ નીતિ માટે નિષ્ફળ જાય છે. કોલર એબોર્ટ અથવા બ્રોકર ડેડલાઈન ખુલ્લી નિષ્ફળ જતી નથી: તે ઇન-ફ્લાઇટ સબપ્રોસેસને સમાપ્ત કરે છે, પછીથી ફ્રેમ નિષ્કર્ષણ અટકાવે છે, અને ખાનગી કામચલાઉ વૃક્ષ `finally` માં દૂર કરવામાં આવે છે.

`scripts/perf/video-bridge-fu07-eval.ts` પોસ્ટ-ડેડઅપ કૅપ્શન-કોલ બચત, ગાઢ-મોશન બજેટ ફાળવણી, blur/exposure/SI-TI પુરાવા, લાંબી પૂંછડી સાથે ઝડપી કટ અને ધીમે ધીમે ફેડ ખોટા હકારાત્મક માટે નિર્ણાયક વાસ્તવિક FFmpeg ફિક્સર જનરેટ કરે છે. તે પૂર્વ-વિશ્લેષણ દિવાલ સમય અને જ્યાં `/usr/bin/time` ઉપલબ્ધ છે ત્યાં ચાઇલ્ડ CPU અને પીક RSS રેકોર્ડ કરે છે. તેની ગુણવત્તાની તપાસ માત્ર માળખાકીય ઓરેકલ્સ છે. વાસ્તવિક કૅપ્શન-મોડલ ગુણવત્તા `HOLD` રહે છે કારણ કે આ હાર્નેસ પાસે કોઈ અધિકૃત એન્ડપોઇન્ટ અથવા સ્થિર જજ નથી. નાણાકીય બચત પણ `HOLD` રહે છે સિવાય કે `--caption-cost-per-call-usd` સ્પષ્ટ હકારાત્મક પ્રતિ-કોલ અંદાજ પૂરો પાડે છે; સ્ક્રિપ્ટ ક્યારેય પરિણામ બનાવતી નથી.

દરેક ફ્રેમ 4 MiB સુધી મર્યાદિત છે, બધી કાચી ફ્રેમ એકસાથે 23 MiB સુધી અને સીરીયલાઇઝ્ડ બ્રોકર પ્રતિસાદ 32 MiB સુધી છે. ખાનગી કામચલાઉ ડિરેક્ટરી `finally` માં દૂર કરવામાં આવે છે. OmniRoute FFmpeg બંડલ કરતું નથી અને કસ્ટમ એક્ઝેક્યુટેબલ પાથ સ્વીકારતું નથી. કૅપ્શન આપતા પહેલા, બ્રિજ એક રૂઢિચુસ્ત વિઝ્યુઅલ ડિડપ્લિકેશન પાસ લાગુ કરે છે: દરેક JPEG 16 × 16 ગ્રેસ્કેલ બફર સુધી ઘટાડી દેવામાં આવે છે અને તેની સરખામણી માત્ર છેલ્લી ફ્રેમ સાથે કરવામાં આવે છે. એક ફ્રેમની ઉપરના વિનંતી કરેલ કૅપ્શન બજેટ માટે, નિષ્કર્ષણ તે બજેટના બમણા અને 16 ફ્રેમથી વધુ ક્યારેય ન હોય તેવા બાઉન્ડેડ ઉમેદવાર પૂલ પૂરા પાડે છે. વિનંતિ કરેલ કેપ ડિડુપ્લિકેશન પછી જ લાગુ કરવામાં આવે છે, જ્યારે બજેટ ઓછામાં ઓછું બે હોય ત્યારે પ્રથમ અને અંતિમ પસંદ કરેલા ઉમેદવારોને અંતિમ પાતળું કરતી વખતે સાચવવામાં આવે છે. વર્ઝનેડ `grayscale-16x16-mean-cells-v2` પોલિસી સરેરાશ લુમા ડેલ્ટાના મોટા અને થંબનેલ કોષોના ગુણોત્તરનો ઉપયોગ કરે છે જેનો સામાન્યકૃત ડેલ્ટા ઓછામાં ઓછો 0.05 છે. ડુપ્લિકેટ થ્રેશોલ્ડ એ સતત 0.04 છે, જે રનટાઈમ સેટિંગ તરીકે પ્રગટ કરવાને બદલે અનુમાનિતતા માટે પસંદ કરવામાં આવે છે. આ ગૌણ ઉચ્ચ-કોન્ટ્રાસ્ટ સિગ્નલ નાની ગતિ અને દૃશ્યમાન-ટેક્સ્ટ ફેરફારોને સાચવે છે જેને સરેરાશ-માત્ર સરખામણી છુપાવી શકે છે. તુલનાત્મક અથવા ડીકોડર ભૂલો ખુલ્લી નિષ્ફળ જાય છે અને કવરેજ રાખે છે. આઉટપુટ મેટાડેટા એક્સટ્રેક્ટેડ ઉમેદવારો, સફળતાપૂર્વક ઉપયોગમાં લેવાતા ફ્રેમ્સ અને વિઝ્યુઅલ ડુપ્લિકેટ્સને અલગ કરે છે.

સ્પષ્ટ રીતે ચિહ્નિત થયેલ વિડિઓ ભાગ ટાઇમસ્ટેમ્પ્ડ સંપર્ક શીટની વિનંતી કરી શકે છે. પુલ વધુમાં વધુ 4-કૉલમ, 16-ફ્રેમ JPEG ગ્રીડ બનાવે છે. દરેક 512-પિક્સેલ સેલ તેના સ્ત્રોત ટાઇમસ્ટેમ્પને ઉચ્ચ-કોન્ટ્રાસ્ટ બોટમ બેન્ડમાં બર્ન કરે છે, જ્યારે તે જ ટાઇમસ્ટેમ્પ ડાઉનસ્ટ્રીમ એસોસિએશન અને ઓડિટ માટે ટેક્સ્ટ મેટાડેટામાં રહે છે. સંપૂર્ણ JPEG 32 MiB પર મર્યાદિત રહે છે. જો `sharp` ગ્રીડને ડીકોડ અથવા કંપોઝ કરી શકતું નથી, તો પુલ વ્યક્તિગત JPEG ફ્રેમમાં પાછો આવે છે; ક્લાયંટ એબોર્ટ હજુ પણ શીટ ઓપરેશન દ્વારા પ્રચાર કરે છે.

પ્રમોશન પુરાવા ઇરાદાપૂર્વક કૃત્રિમ રચના માઇક્રોબેન્ચમાર્કથી અલગ છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI- સુસંગત વિઝન મોડલ્સ માટે સ્કીમા-વર્ઝનવાળી A/B હાર્નેસને વ્યાખ્યાયિત કરે છે. તે પ્રદાતા-રિપોર્ટેડ ટોકન્સ, એન્ડ-ટુ-એન્ડ વોલ લેટન્સી (શીટ કમ્પોઝિશન સહિત), મોડલ-કોલ કાઉન્ટ અને મેનિફેસ્ટ-વ્યાખ્યાયિત હકીકત રીટેન્શનને માપે છે. કાચા મોડલના જવાબો રિપોર્ટ પર લખવામાં આવતા નથી; માત્ર SHA-256 ડાયજેસ્ટ અને મેળ ખાતી હકીકત IDs જાળવી રાખવામાં આવે છે. જ્યાં સુધી `--execute-real` પાસ કરવામાં ન આવે અને `--model`, `OMNIROUTE_BASE_URL` અને `OMNIROUTE_API_KEY` ગોઠવેલ ન હોય ત્યાં સુધી હાર્નેસ કોઈ નેટવર્ક અથવા પેઇડ મોડલ કૉલ કરતું નથી. તે સ્પષ્ટ વાસ્તવિક રન વિના, તેનો મશીન વાંચી શકાય એવો ચુકાદો `HOLD` રહે છે; એકલા સિન્થેટિક payload/call-count માપન પ્રમોશન પુરાવા નથી.

અલગ `scripts/perf/video-bridge-promotion-eval.ts` FU-07 અથવા FU-09 અવલોકનો વાપરે છે. પ્રમોશન એડમિશન માટે તમામ આઠ સિન્થેટીક સિન્થેટીક સિનેરીયો પ્રકારો ઉપરાંત સેનિટાઇઝ્ડ રીઅલ ક્લિપ, રોલ અને કેસ દીઠ ઓછામાં ઓછા ત્રણ માપેલ પુનરાવર્તનો, તમામ દસ ઘોષિત મેટ્રિક્સ, ફ્રોઝન media/prompt/expected-fact/settings ડાયજેસ્ટ, અનન્ય અવલોકન IDs અને ચકાસાયેલ સીડેડ A/B ઓર્ડરની જરૂર છે. અમલની રસીદ કોર્પસ ડાયજેસ્ટ, ચોક્કસ ઉમેદવાર SHA અને મોડેલ રિવિઝનને જોડે છે. ખૂટતું અથવા અમાન્ય માપન `HOLD` રહે છે, જેમાં 30 સે.થી ઉપરનો CPU, 512 MiB ઉપરનો પીક RSS અથવા 30 સેકંડથી ઉપરનો પૂર્વ-વિશ્લેષણનો સમાવેશ થાય છે. આ પુરાવા-પ્રવેશ કેપ્સ છે, નવી રનટાઇમ RSS અમલીકરણ ગેરંટી નથી.

FU-07 ઓછામાં ઓછી 98% ગુણવત્તા જાળવી રાખવાની અને p95 લેટન્સી 1.2x બેઝલાઈનથી વધુની જરૂર નથી, ઉપરાંત કાં તો 0.05 સંપૂર્ણ કેસ-બેલેન્સ્ડ સરેરાશ રિકોલ સુધારણા સમકક્ષ સરેરાશ કૅપ્શન કૉલ્સ પર અથવા ઓછામાં ઓછા 10% ઓછા અર્થ પોસ્ટ-ડેડઅપ કૅપ્શન કૉલ્સ. FU-09 માટે ઓછામાં ઓછી 0.85 ગુણવત્તા, 95% રીટેન્શન, 20% મધ્ય વિલંબિત ઘટાડો અને 10% ટોકન ઘટાડો જરૂરી છે. ગંભીર-તથ્ય નુકશાન, ઈન્જેક્શન અનુપાલન અથવા ખોવાયેલ ઉપયોગ પ્રમોશનને અટકાવે છે. એક અમલ કંઈપણને પ્રોત્સાહન આપી શકતું નથી: `--previous-report` જ policy/model revision/candidate/corpus. ના બે અલગ, બિન-ઓવરલેપિંગ, સળંગ લાયક અમલની પુષ્ટિ કરે છે એક નમૂના પ્રયોગ સંપર્ક-શીટ પ્રયોગની પુષ્ટિ કરી શકતો નથી.

કલેક્ટરે મેમરીમાં પ્રતિસાદો સ્કોર કરવો જોઈએ અને `responseDigest` પ્લસ મેટ્રિક્સ અને અવલોકન બાઈન્ડિંગ્સ સાચવવા જોઈએ, ટેક્સ્ટનો ક્યારેય જવાબ આપવો જોઈએ નહીં. ઉપભોક્તા પણ લેગસી કાચા અવલોકનો વાંચે છે પરંતુ તે ટેક્સ્ટને તેના અહેવાલોમાં ક્યારેય નકલ કરતા નથી. દરેક અવલોકન માટે બરાબર એક `responseDigest` અથવા `rawResponseText` સ્વીકારવામાં આવે છે. વર્ઝન કરેલ મંજૂર સૂચિ અપરિવર્તનશીલ `hold` ડિફોલ્ટ સાથે ખાલી રહે છે. પાત્ર પ્રવેશ માટે તેના પુરાવા સંદર્ભ, નીતિ, મોડલ રિવિઝન, ચોક્કસ ઉમેદવાર SHA, મેનિફેસ્ટ ડાયજેસ્ટ અને બે અલગ-અલગ રન IDs જરૂર છે; વિરોધાભાસી સંદર્ભો નકારવામાં આવે છે. આ મેટાડેટા ઓડિટ કોન્ટ્રાક્ટ છે, તે સાબિતી નથી કે સંદર્ભિત ફાઇલમાં વાસ્તવિક માપન છે. કોઈપણ એન્ટ્રી ઉમેરતા પહેલા વાસ્તવિક રસીદોની સમીક્ષા કરો. મેનેજમેન્ટ સ્ટેટ્સ એન્ડપોઇન્ટ અને વિડીયો ડેશબોર્ડ રૂઢિચુસ્ત તત્પરતાને છતી કરે છે. રૂપરેખાંકિત મોડલ ઉપનામ એકલા તેનું પુનરાવર્તન અથવા ચાલી રહેલ ઉમેદવાર SHA સ્થાપિત કરતું નથી, તેથી વર્તમાન ડેશબોર્ડ અન્ય એક્ઝેક્યુશન સંદર્ભમાંથી યોગ્યતાનો ફરીથી ઉપયોગ કરવાને બદલે `HOLD` અહેવાલ આપે છે. સ્પષ્ટ પ્રાયોગિક પસંદગી પ્રમોશનથી અલગ રહે છે; કોઈ ડિફોલ્ટ આપમેળે બદલાતું નથી.

કોલર્સ સમર્થિત વિડિયો ભાગ સાથે વૈકલ્પિક `transcript.cues` એરે જોડી શકે છે જ્યારે તેઓ પહેલેથી જ સંરેખિત ટેક્સ્ટ ધરાવે છે. દરેક સંકેત `text`, ચકાસણી અવધિની અંદર એક મર્યાદિત `start`/`end` અંતરાલ અને વ્હાઇટલિસ્ટેડ `source` (`client`, `embedded`, અથવા `audio-bridge`); `confidence` `1` માં ડિફોલ્ટ છે અને `0` અને `1` વચ્ચે રહેવું જોઈએ. ચોક્કસ ડુપ્લિકેટ સંકેતો સંકુચિત છે. OmniRoute આ મેટાડેટામાંથી ક્યારેય ટ્રાન્સક્રિપ્શન શરૂ કરતું નથી: માન્ય સંકેતોને સ્રોત, વિશ્વાસ અને અંતરાલ સાથે વર્ણવેલ પરિણામમાં કૉપિ કરવામાં આવે છે અને ફ્રેમ કૅપ્શન્સની સાથે અવિશ્વસનીય અવલોકનો તરીકે પ્રસ્તુત કરવામાં આવે છે. કૅપ્શન સ્ટ્રીમમાં ભળવાને બદલે અમાન્ય, આઉટ ઑફ રેન્જ અથવા ઉત્પત્તિ-મુક્ત ટેક્સ્ટ નકારવામાં આવે છે. બંને રિક્વેસ્ટ-બોડી ટ્રાન્સક્રિપ્ટ ચેનલો `client` ને પૂરા પાડવામાં આવેલ ઉત્પત્તિને સામાન્ય બનાવે છે, જેમાં સ્વ-આગ્રહિત `embedded` અથવા `audio-bridge` લેબલ્સનો સમાવેશ થાય છે. માત્ર સર્વર-માલિકીનું એડેપ્ટર જ કોડ-ઓન્લી `trustedSource` દલીલ દ્વારા તે વિશ્વસનીય લેબલ્સ અસાઇન કરી શકે છે; વિનંતી JSON ફીલ્ડ તે દલીલ સુધી પહોંચી શકતું નથી. ટ્રાંસ્ક્રિપ્ટ ટેક્સ્ટ અવિશ્વસનીય મીડિયા-ઉત્પન્ન સામગ્રી રહે છે, તેના મૂળને ધ્યાનમાં લીધા વિના, અને ક્યારેય અધિકૃતતા નક્કી કરવી જોઈએ નહીં.

એક અદ્યતન કૉલર સમાન વિડિઓ માટે `audioTranscript` ટ્રેક પ્રદાન કરી શકે છે; તેને ક્લાયન્ટ દ્વારા આપવામાં આવેલ ટેક્સ્ટ તરીકે ગણવામાં આવે છે, સર્વર ટ્રાન્સક્રિપ્શનના પુરાવા તરીકે નહીં. ફ્યુઝન સીમ વિઝ્યુઅલ અને ઑડિયો અવલોકનોને એક સમયમર્યાદા અને અબોર્ટ સિગ્નલ હેઠળ ચલાવે છે, તેમને સામાન્ય સમયરેખા પર ઓર્ડર આપે છે, ચોક્કસ ડુપ્લિકેટને સંકુચિત કરે છે અને જ્યારે માત્ર એક બાજુ સફળ થાય છે ત્યારે આંશિક પરિણામની જાણ કરે છે. એક અમાન્ય `audioTranscript` તે આંશિક પરિણામ — માટે અધોગતિ કરે છે વિઝ્યુઅલ વર્ણન રાખવામાં આવે છે અને ઑડિઓ શાખા સમગ્ર વિડિઓને નિષ્ફળ કરવાને બદલે સેનિટાઈઝ્ડ નિષ્ફળતા કોડ — રેકોર્ડ કરે છે. પ્રતિ-શાળા ઉપલબ્ધતા, આંશિક ધ્વજ અને સેનિટાઈઝ્ડ નિષ્ફળતા કોડ વર્ણવેલ પરિણામમાં, ગાર્ડરેલ મેટાડેટા (`audioFusionRuns`/`audioFusionPartials`/ `audioFusionFailureCodes`), પરિણામ-કેશ મેટાડેટામાં અને બ્રિજ ફ્યુઝન કાઉન્ટર્સમાં સાચવેલ છે. ડિફૉલ્ટ વિડિયો બ્રિજ પાથ સ્પીચ-ટુ-ટેક્સ્ટનો ઉપયોગ કરતું નથી અથવા બીજી મીડિયા કૉપિ ડાઉનલોડ કરતું નથી; તે સ્પષ્ટ ટ્રેક વિના, તે માત્ર વિડિયો જ રહે છે.

**ટ્રાન્સક્રિપ્ટ રીટેન્શન (#12150 P1).** જ્યારે પણ વિડિયો બ્રિજ (પોતે પસંદ કરે છે) ટ્રાન્સક્રિપ્ટ ક્યુ — રેન્ડર કરે છે ત્યારે આ આપમેળે લાગુ થાય છે ત્યાં કોઈ અલગ રીટેન્શન ફ્લેગ નથી. જ્યારે વિનંતિ કોઈપણ ટ્રાન્સક્રિપ્ટ કયૂ (કોલર-ઘોષિત `transcript` અથવા ફ્યુઝ્ડ `audioTranscript`) રેન્ડર કરે છે, ત્યારે ગાર્ડ્રેલ તેને `videoBridgeObserved` ચિહ્નિત કરે છે અને વિડિયો વર્ણન — એક સરખું રેન્ડરિંગ બનાવે છે જેમાં દરેક કયૂના ફ્રી-ટેક્સ્ટ બૉડીને `[redacted-video-transcript]` દ્વારા બદલવામાં આવે છે, જે stcd ફીલ્ડની રચના પહેલાં સ્ટ્રક્ચર દ્વારા બનાવવામાં આવે છે. (ક્યારેય ચપટી લખાણનું પદચ્છેદન કરીને નહીં, તેથી `[inaudible]`/`[music]` — જેવા `]` ધરાવતી સંસ્થાઓ સહિત — પ્રતિકૂળ અથવા સામાન્ય ક્યુ કન્ટેન્ટ ટકી શકશે નહીં). સતત કૉલ-લોગ વિનંતીનો મુખ્ય ભાગ તે રીડેક્ટેડ શેડો માટે દરેક વિડિયો-ઉત્પાદિત ટેક્સ્ટ ભાગને સ્વેપ કરે છે, જે સામગ્રી સમાનતા દ્વારા મેળ ખાતી હોય છે; `fullText` એન્કરને ફિનિશ્ડ પ્રી-કોલ ગાર્ડરેલ પેલોડમાંથી ફરીથી વાંચવામાં આવે છે, તેથી મેચ હજુ પણ પછીની સાંકળ ગાર્ડરેલ્સ ( PII અને ઓળખપત્ર માસ્કર્સ, પ્રાથમિકતાઓ 10/95) સ્થાને વર્ણન ટેક્સ્ટને ફરીથી લખે છે અને system-prompt/handoff/memory ઈન્જેક્શન પછી સંદેશ એરેને ફરીથી આકાર આપે છે પછી પણ સફળ થાય છે. મોડલ પર અપસ્ટ્રીમ મોકલવામાં આવેલ શરીર અપરિવર્તિત છે. અવલોકન કરાયેલ વિનંતી પણ કોઈ ટકાઉ મેમરી ધરાવતી નથી.

**કાચો વિડિઓ ક્ષેત્રો (#12430).** જ્યારે બ્રિજ સક્ષમ હોય અને મૂળ વિડિયો સપોર્ટ અજ્ઞાત અથવા ગેરહાજર હોય, ત્યારે વ્યાખ્યાયિત `transcript`/`audioTranscript` ફીલ્ડ પણ `videoBridgeObserved` સક્રિય કરે છે, વર્ણન નિષ્ફળતા અથવા `maxVideos` મર્યાદા પછી પણ. `null` અને ખાલી શબ્દમાળાઓની ગણતરી; ગેરહાજર ફીલ્ડ્સ અને નોન-વિડિયો મેટાડેટા નથી. જાળવી રાખેલી નકલો આ ક્ષેત્રોને સુધારે છે અથવા વિનંતીને છોડી દે છે, અને caches/Memory બાયપાસ કરવામાં આવે છે.

તે ફોલબેક પાથ પર, માન્ય કોલર સંકેતો બિન-માનક પ્રદાતા ક્ષેત્રોને બદલે આધારભૂત `text`/`input_text` ભાગો બની જાય છે. વિનંતિ-સપ્લાય કરેલ બંને ટ્રેક અવિશ્વસનીય `client` અવલોકનો રહે છે, સ્પષ્ટ ચેતવણી સાથે કે વિડિઓનું વર્ણન કરવામાં આવ્યું નથી અને મીડિયા સામે ટાઇમસ્ટેમ્પ ચકાસવામાં આવ્યા નથી. હાલના 256-cue/64-KiB કુલ અને પ્રતિ-ક્યુ બજેટ બે ટ્રેક પર એકસાથે લાગુ થાય છે; ટાઇમસ્ટેમ્પ બ્રોકરની 600-સેકન્ડની ટોચમર્યાદા અને કોઈપણ સપ્લાય કરેલ ફોકસ વિન્ડોમાં ફિટ હોવા જોઈએ. અમાન્ય ટ્રૅક્સ કાઢી નાખવામાં આવે છે, મનસ્વી ટેક્સ્ટ તરીકે આગળ મોકલવામાં આવતા નથી; માન્ય ભાઈ-બહેનનો ઉપયોગ હજુ પણ થઈ શકે છે સિવાય કે તેમનું સંયુક્ત બજેટ ઓળંગાઈ જાય. Null/empty ફીલ્ડ્સ કોઈ ટેક્સ્ટ ઉમેરતા નથી. આ ફોલબેક દ્વારા કોઈ મીડિયા આનયન અથવા ટ્રાન્સક્રિપ્શન ઉમેરવામાં આવ્યું નથી. ટ્રાંસ્ક્રિપ્ટ એક્સ્ટેંશન ફીલ્ડ્સ ફોલબેક વિડિયો કેરિયર અને તેના `video_url`/`source` ઑબ્જેક્ટ્સમાંથી દૂર કરવામાં આવે છે. OpenAI વાયર મંજૂર સૂચિ કડક રહે છે; અજ્ઞાત-મૂળ વિડિયો કેરિયર્સ ઉપલબ્ધ રહે છે અને જાણીતા લખાણ-માત્ર લક્ષ્યો સલામત માર્કર્સ રાખે છે. સ્ટ્રક્ચર્ડ રિડેક્શન શેડોઝ જોડાયેલ ટ્રાન્સક્રિપ્ટ ટેક્સ્ટને સુરક્ષિત કરે છે, જ્યારે મૂળ કૉલરની માલિકીની વિનંતી યથાવત રહે છે. મૂળ-સમર્થિત લક્ષ્યો અને અક્ષમ પુલ તેમના હાલના બાયપાસ વર્તનને જાળવી રાખે છે.

વધારાની જાળવી રાખેલી નકલો સમાન અવલોકન-વિનંતી સિગ્નલનો ઉપયોગ કરે છે. કાચો પ્રી-ગાર્ડ્રેલ ક્લાયંટ-વિનંતી સ્નેપશોટ, ઇન-મેમરી પેન્ડિંગ વિનંતી, અને પ્રારંભિક અસ્વીકાર-વિનંતી લોગ વિડિયો ભાગોમાં ટ્રાન્સક્રિપ્ટ ફીલ્ડ્સને માળખાકીય રીતે બદલો; પાઈપલાઈન સ્ટેજ અને કોન્ટેસ્ટ હેન્ડઓફ દ્વારા સંશ્લેષિત સ્ટ્રિંગ પ્રોમ્પ્ટને પર્સિસ્ટેડ-રિક્વેસ્ટ-બોડી સિંક પર રીડેક્ટ કરવામાં આવે છે. સતત `video_content_removed` માર્કર ઇરાદાપૂર્વક કાઢી નાખવામાં આવેલ ટેક્સ્ટને પુનઃનિર્માણ કરવાને બદલે `previous_response_id` ચાલુ રાખવાને નિષ્ફળ બનાવે છે. જો અવલોકન કરેલ વિનંતી લોગીંગ કરતા પહેલા તેનો ભાગ-દીઠ રીડેક્શન શેડો ગુમાવે છે, અથવા તો પછીની વિનંતીના પરિવર્તનો પછી કેટલાક વિડિયો પડછાયાઓમાંથી એક પણ મેચ થવામાં નિષ્ફળ જાય છે, તો આંશિક રીતે રીડેક્ટ કરેલ ટ્રાન્સક્રિપ્ટને જાળવી રાખવાને બદલે જાળવી રાખેલી વિનંતીના મુખ્ય ભાગને સંપૂર્ણપણે છોડી દેવામાં આવે છે.

અવલોકન કરેલ વિનંતી માટે, મોડેલ પ્રતિસાદ સંરચિત કયૂ સીમા વિના ટ્રાન્સક્રિપ્ટના કોઈપણ ભાગને ટાંકી શકે છે. તેથી તેના સતત કોલ-લોગ `responseBody` ઓમિશન માર્કર દ્વારા બદલવામાં આવે છે; વિગતવાર પાઇપલાઇન આર્ટિફેક્ટ (જેમાં upstream/client બોડી અને સ્ટ્રીમ હિસ્સાનો સમાવેશ થઈ શકે છે) જાળવી રાખ્યો નથી. તે વિનંતી માટે સિમેન્ટીક, આઇડમ્પોટેન્સી અને રિઝનિંગ-રીપ્લે કેશ બાયપાસ વાંચે છે અને લખે છે. પ્રદાતા વિનંતી અને ક્લાયંટ-દ્રશ્ય પ્રતિભાવ યથાવત રહે છે. જ્યારે વિગતવાર આર્ટિફેક્ટ અવગણવામાં આવે છે ત્યારે પ્રારંભિક કીપલાઈવ બાઇટ્સ અસ્થાયી બફરમાંથી બહાર કાઢવામાં આવે છે. Kiro ની દૂષિત EventStream ચેતવણી માત્ર પેલોડ બાઈટ ગણતરીની જાણ કરે છે, તેની સામગ્રીઓ અથવા JSON પાર્સરની કાચી ભૂલ ક્યારેય નહીં. આ દાવો કરતું નથી કે દરેક અસંબંધિત provider/plugin ડાયગ્નોસ્ટિકનું ઓડિટ કરવામાં આવ્યું છે; વ્યાપક જાળવી રાખેલ-સિંક સ્વીપને #11658 માં ટ્રૅક કરવામાં આવે છે.

આંતરિક `/api/modality-bridge/video/drilldown` જીવનચક્ર એ એક અલગ, loopback/token-authenticated કેશ સબસ્ટ્રેટ છે. દરેક ઓપરેશન માટે પ્રમાણભૂત અપારદર્શક મુખ્ય ID પણ જરૂરી છે. પ્રોડક્શન કૉલર સક્ષમ થાય તે પહેલાં, તેણે તે ID પ્રમાણિત ભાડૂત પાસેથી મેળવવું જોઈએ અને ક્લાયન્ટ-પસંદ કરેલ મૂલ્યને ક્યારેય ફોરવર્ડ કરવું જોઈએ નહીં. કેશ કીઓ તે પ્રિન્સિપલને કેનોનિકલ સત્ર અને વિડિયો-રેફરન્સ IDs સાથે જોડે છે, માત્ર તેમની SHA-256-derived કી સ્ટોર કરે છે અને તે જ પ્રિન્સિપાલને વાંચવા અને કાઢી નાખવાનો અવકાશ બંને આપે છે. કેશ એન્ટ્રી દીઠ વધુમાં વધુ 16 વ્યુત્પન્ન JPEG ફ્રેમ્સ સંગ્રહિત કરે છે, તે દસ મિનિટ પછી સમાપ્ત થાય છે, અને બાઉન્ડેડ `start`/`end` રીડ અથવા સ્પષ્ટ સત્ર કાઢી નાખવાને સપોર્ટ કરે છે.

દરેક પ્રિન્સિપલ 16 એન્ટ્રીઓ અને 64 MiB પ્રમાણભૂત JPEG ડેટા સુધી મર્યાદિત છે. તે મર્યાદાઓ વૈશ્વિક 64-entry/256 MiB ટોચમર્યાદાથી સ્વતંત્ર છે: મુખ્ય ક્વોટા દબાણ ફક્ત તે જ પ્રિન્સિપાલની ઓછામાં ઓછી-તાજેતરમાં ઉપયોગમાં લેવાતી એન્ટ્રીઓને વૈશ્વિક LRU ઇવિક્શન ગણવામાં આવે તે પહેલાં બહાર કાઢે છે. સમયસીમા સમાપ્ત થયેલ એન્ટ્રીઓ કેશ પ્રવૃત્તિ પર મુખ્ય અને વૈશ્વિક એકાઉન્ટિંગ બંનેમાંથી સ્વિપ કરવામાં આવે છે, જ્યારે રદ અને માન્યતા નિષ્ફળતા આંશિક રિપ્લેસમેન્ટ કરતી નથી.

કેશ બિન-કેનોનિકલ Base64, અધિક પેડિંગ, બિન-JPEG મીડિયા, દૂષિત અથવા કપાયેલ JPEGs, અને JPEGs ને નકારે છે જે બાઉન્ડેડ પૂર્ણ-ઇમેજ `sharp` ડીકોડ દરમિયાન ચેતવણી ઉત્પન્ન કરે છે. તે દરેક સ્વીકૃત ઈમેજને કેનોનિકલ JPEG તરીકે ફરીથી એન્કોડ કરે છે, કોલર ફીલ્ડ્સ પર વિશ્વાસ કરવાને બદલે ડીકોડેડ બાઈટમાંથી પહોળાઈ અને ઊંચાઈ મેળવે છે અને કોઈપણ પાછળના પોલીગ્લોટ બાઈટ્સને જાળવી રાખવાને બદલે તેને કાઢી નાખે છે. બંને ક્વોટા માટે માત્ર બાઉન્ડેડ કેનોનિકલ કમ્પ્રેસ્ડ બફરનો ચાર્જ લેવામાં આવે છે. JSON વાયર મર્યાદામાં 32 MiB ડીકોડેડ-ઇનપુટ ટોચમર્યાદા માટે Base64 ઓવરહેડનો સમાવેશ થાય છે. દરેક સંગ્રહિત વ્યુત્પન્નતા તેની માન્ય JPEG format/resolution, સેમ્પલિંગ નીતિ, વ્યુત્પન્ન સંસ્કરણ, બનાવટનો સમય, સર્વર-કમ્પ્યુટેડ સામગ્રી હેશ અને હેશ કરેલ પેરેન્ટ રેફરન્સ વત્તા વિશ્વસનીય કોલરની પેરેન્ટ-કન્ટેન્ટ હેશ રેકોર્ડ કરે છે. અણુ કેશ કમિટ પહેલાં અસુમેળ decode/hash તબક્કાઓ વચ્ચે રદ કરવાની તપાસ કરવામાં આવે છે.

પ્રોડક્શન નિર્માતા સફળ વિઝ્યુઅલ પૃથ્થકરણ પછી જ પહેલાથી મેળવેલી બ્રોકર ફ્રેમનો પુનઃઉપયોગ કરે છે, જેમાં બીજા વિડિયો download/extraction. નથી તેને ઓપરેટર `modalityBridgeVideoDrilldownEnabled=true`, ભાગ દીઠ કડક `drilldown: true`, અને પ્રમાણિત API-કી રેકોર્ડ ID ની જરૂર છે. ક્લાયન્ટ-ઘોષિત principal/session મૂલ્યો ક્યારેય માલિકી સ્થાપિત કરતા નથી. ત્રણેય શરતો વિના તે વધારાની ફ્રેમને હેશ કરતું નથી, માપ બદલી શકતું નથી અથવા જાળવી શકતું નથી. રીટેન્શન નિષ્ફળતા ઉપયોગી દ્રશ્ય પ્રતિભાવને સાચવે છે. સંમતિ આપેલી વિનંતીઓ આખા-વિડિયો પરિણામ કૅશને બાયપાસ કરે છે જેથી કૅશ્ડ પરિણામો ક્યારેય હૅન્ડલને રિપ્લે નહીં કરે.

સફળ JSON અને SSE પ્રતિસાદો બાઉન્ડેડ `x-omniroute-video-drilldown` હેડરમાં વધુમાં વધુ ચાર અપારદર્શક હેન્ડલ્સનો પર્દાફાશ કરે છે. અધિકૃત બ્રાઉઝર મૂળ CORS મૂળ નીતિને વિસ્તૃત કર્યા વિના તે હેડરને વાંચી શકે છે. નવા હેન્ડલ્સ `v1.<32-byte random base64url token>` ઉપયોગ કરે છે, અને રજિસ્ટ્રી ફક્ત તેમના SHA-256 હેશને જાળવી રાખે છે. reader/header પાર્સર લેગસી 64-હેક્સ ટોકન્સ પણ સ્વીકારે છે. અધિકૃત જાહેર ઉપભોક્તા `GET /api/v1/video-bridge/drilldown?handle=...` છે, સ્વતંત્ર રીતે `modalityBridgeVideoDrilldownRemoteEnabled=true` દ્વારા ગેટેડ છે. જ્યારે લેગસી `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env ફોલબેક સક્ષમ હોય ત્યારે પણ સ્પષ્ટ રીતે ચાલુ રહેલ ખોટા ઍક્સેસને રદ કરે છે. ઉત્પાદન રીટેન્શનમાં સમાન લેગસી `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` ફોલબેક છે. બંને ફૉલબૅક્સ ડિફૉલ્ટ બંધ છે.

ગ્રાહક અધિકૃત કીમાંથી માલિકી મેળવે છે અને કી નીતિ લાગુ કરે છે: GET અને DELETE બંને `/v1` અને `/api/v1` ઉપનામો સહિત `video` એન્ડપોઇન્ટ કેટેગરીના છે. બિન-ખાલી એન્ડપોઇન્ટની મંજૂરીવાળી કીમાં `video` શામેલ હોવી આવશ્યક છે; અપ્રતિબંધિત કીઓ સુસંગત રહે છે. ઉપભોક્તા અજાણ્યા, એક્સપાયર થયેલ અને અન્ય કીના હેન્ડલ્સ માટે એ જ 404 પરત કરે છે. તે `variant=preview|standard|detail` (મહત્તમ JPEG પરિમાણ 320/640/1280, ક્યારેય અપસ્કેલ્ડ નહીં), `limit=1..8` (અથવા વારસાગત `frames` ઉપનામ, બંને ક્યારેય નહીં), શૂન્ય-આધારિત `page`, અને વૈકલ્પિક `start`/`end` ફોકસ સેકન્ડ સ્વીકારે છે. ડુપ્લિકેટ ક્વેરી કી અને રિવર્સ્ડ ફોકસ વિન્ડો નકારવામાં આવે છે. દરેક પરત કરેલ વેરિઅન્ટમાં તેની વાસ્તવિક સામગ્રી અને વાસ્તવિક રિઝોલ્યુશન મેટાડેટાનો હેશ હોય છે, જે જાળવી રાખેલા સ્ત્રોત સાથે લિંક થયેલ હોય છે. વેરિઅન્ટ્સ વધારાની જાળવી રાખેલી નકલો તરીકે સંગ્રહિત કરવાને બદલે વાંચવા પર લેવામાં આવે છે. JSON પ્રતિસાદ, Base64/envelope સહિત, 32 MiB પર મર્યાદિત છે; મોટા કદનું પૃષ્ઠ 413 પરત કરે છે અને ક્લાયન્ટે ઓછા ફ્રેમની વિનંતી કરવી આવશ્યક છે. દરેક પુન: માપની આસપાસ ચેક કેન્સલેશન વાંચે છે અને પાછા ફરતા પહેલા હેન્ડલની માન્યતા ફરીથી તપાસો. માલિક દ્વારા `DELETE` નિર્બળ છે; કાઢી નાખવું અથવા TTL સમાપ્તિ જાળવી રાખેલા સ્રોત અને વપરાશ એકાઉન્ટિંગને પ્રકાશિત કરે છે.

શેર કરેલ સ્ટોર પ્રક્રિયા-સ્થાનિક છે: હેન્ડલ્સ પુનઃપ્રારંભ પર સમાપ્ત થાય છે અને સ્વતંત્ર OmniRoute પ્રક્રિયાઓ વચ્ચે સ્થાનાંતરિત નથી. મેનેજમેન્ટના આંકડા અસરકારક રીટેન્શન/રિમોટ પોલિસી અને એકંદર જાળવી રાખેલા entries/bytes જાહેર કરે છે, ક્યારેય મીડિયા, સંદર્ભો, મુખ્ય IDs અથવા હેન્ડલ્સ નહીં. વિડિઓ સેટિંગ્સ પેનલ તે મૂલ્યો દર્શાવે છે અને બંને સંમતિ સ્વીચ ચાલુ રાખી શકે છે. આ અમલીકરણ દસ્તાવેજીકરણ જીવંત જમાવટ અથવા પ્રમોશન પુરાવા નથી; વાસ્તવિક-મૉડલ સ્વીકૃતિને અલગથી ટ્રૅક કરવામાં આવે છે.

રૂપરેખાંકિત વિડિઓ મોડલ સાથે ફ્રેમ્સને અનુક્રમે કૅપ્શન આપવામાં આવે છે. ખાલી વિડિયો ઓવરરાઇડ વિઝન સેટિંગને વારસામાં મેળવે છે; જો બંને ખાલી હોય, તો વિઝન ઓટો-રાઉટર અસરકારક દ્રષ્ટિ-સક્ષમ મોડલ પસંદ કરે છે. સફળ કૅપ્શન્સ મૂળ ભાગને સ્થિર `[Video description:` ઉપસર્ગ સાથે બદલે છે જે ટેક્સ્ટને અવિશ્વસનીય મીડિયા દ્વારા મેળવેલા અવલોકન તરીકે પણ ચિહ્નિત કરે છે અને ડાઉનસ્ટ્રીમ મોડલ્સને મીડિયામાં મળેલી સૂચનાઓનું પાલન ન કરવાનું કહે છે. ફ્રેમ-કેપ્શન કેશ કીમાં JPEG બાઇટ્સ, પ્રોમ્પ્ટ, ટાઇમસ્ટેમ્પ અને અસરકારક મોડલનો સમાવેશ થાય છે; માત્ર સફળ કૅપ્શન્સ કેશ કરવામાં આવે છે. કેશ એન્ટ્રીઓ વાસ્તવિક સફળ નિર્માતા મોડેલને જાળવી રાખે છે, જેમાં ફોલબેક મોડલનો સમાવેશ થાય છે; બ્રિજ `mixed` નો અહેવાલ આપે છે જ્યારે વિવિધ મોડેલો દ્વારા વિવિધ ફ્રેમ્સ બનાવવામાં આવી હતી. કેશ હિટ તે નિર્માતા ઓળખને વિનંતી કરેલ રૂટીંગ પ્લાન તરીકે રીલેબલ કરવાને બદલે ફરીથી ઉપયોગ કરે છે. આઉટપુટ — પ્રોમ્પ્ટ, અસરકારક મોડલ, સેમ્પલિંગ પોલિસી, ફ્રેમ કાઉન્ટ, સિમેન્ટીક એનાલિસિસ મોડ, નોર્મલાઇઝ્ડ ફોકસ હિંટની SHA-256 ફિંગરપ્રિન્ટ, ફોકસ વિન્ડો, `transcript`, `audioTranscript` અને કોન્ટેક્ટ-શીટ ફ્લેગ — ને બદલતા દરેક ઇનપુટ પર સંપૂર્ણ-વિડિયો પરિણામ કેશ ચાવી દેવામાં આવે છે તેથી તેમાંથી કોઈપણને બદલવાનું ક્યારેય ચૂકશો નહીં. વિઝ્યુઅલ ડેડઅપ પોલિસી વર્ઝન, થ્રેશોલ્ડ અને બાઉન્ડેડ ઉમેદવાર-ફ્રેમ કાઉન્ટ પણ પરિણામ-કેશ કી અને મેટાડેટામાં સ્પષ્ટ છે; તેથી નીતિમાં ફેરફાર વાસી સંપૂર્ણ-વિડિયો વર્ણનનો ફરીથી ઉપયોગ કરી શકતો નથી. પરિણામ-કેશ v4 મેટાડેટા મોડ અને ફિંગરપ્રિન્ટ રાખે છે, ક્યારેય કાચો વપરાશકર્તા કાર્ય નથી. ગાર્ડ્રેલ મેટાડેટા વિનંતી કરેલ અને અસરકારક વિશ્લેષણ મોડ બંનેની જાણ કરે છે; ઉપયોગ કરી શકાય તેવા વપરાશકર્તા ટેક્સ્ટ વિના વિનંતી કરેલ `focused` મોડને અસરકારક રીતે `full` તરીકે જાણ કરવામાં આવે છે.

ગાર્ડરેલ દરેક સપોર્ટેડ વિડિયો ભાગને બહાર કાઢે છે પરંતુ `modalityBridgeVideoMaxVideos` કરતાં વધુ વર્ણન કરતું નથી. `supportsVideo === false` હોવાનું સાબિત થયેલ લક્ષ્ય માટે, નિષ્ફળ અને ઓવર-લિમિટ વિડિઓઝ સ્પષ્ટ સલામત ટેક્સ્ટ માર્કર બની જાય છે જેથી કોઈ કાચો વિડિઓ ટકી રહેતો નથી. જ્યારે ક્ષમતા અજાણ હોય, ત્યારે તે ભાગો તેમના વિડિયો કેરિયરને જાળવી રાખે છે; કોઈપણ ફોલબેક ટ્રાન્સક્રિપ્ટ ઉપરના બાઉન્ડેડ ટેક્સ્ટ કન્વર્ઝનને અનુસરે છે. `supportsVideo === true` સાથેના લક્ષ્યો પુલને બાયપાસ કરે છે. ક્લાયંટની વિનંતી એબોર્ટ સિગ્નલ ડાઉનલોડ, બ્રોકર કતાર, સબપ્રોસેસિસ અને કૅપ્શન કૉલ્સ દ્વારા પ્રચાર કરે છે; વિડિયો વચ્ચે અબોર્ટ્સ અટકે છે અને કાચા મીડિયા માટે ક્યારેય નિષ્ફળ જતા નથી.

### PII માસ્કર (`piiMasker.ts`)

પર ચાલે છે** બંને** તબક્કાઓ

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને `prompt` (સાદા સ્ટ્રિંગ આઇટમ્સ સહિત) ચાલે છે, અને `content`/`text` ફીલ્ડમાં `processPII()` ( `@/shared/utils/inputSanitizer` માંથી) લાગુ કરે છે. જ્યારે `PII_REDACTION_ENABLED=true`, શોધાયેલ PII આઉટબાઉન્ડ પેલોડમાં રીડેક્ટ કરવામાં આવે છે. આ `INPUT_SANITIZER_MODE` થી સ્વતંત્ર છે (જે માત્ર પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે). જ્યારે રીડેક્શન બંધ હોય, ત્યારે સામગ્રીને ફરીથી લખ્યા વિના કોલ રેકોર્ડ ડિટેક્શન ગણતરીઓ.
- **`postCall`** પ્રતિભાવને ડીપ-ક્લોન્સ કરે છે, `sanitizePIIResponse()` વત્તા રિસ્પોન્સ-API-આકાર માસ્કર ચલાવે છે (`maskResponsesOutput` — `output_text` અને `output[].content[].text` ને આવરી લે છે). જો કોઈ સુધારણા થાય છે, તો સંશોધિત પ્રતિસાદ મૂળને બદલે છે.

રક્ષક ક્યારેય અવરોધતું નથી; તે ફક્ત ટીકા કરે છે (`meta.detections`, `meta.redacted`) અથવા ફરીથી લખે છે.

**ઉલટાવી શકાય તેવું વૉલ્ટ (`PII_REVERSIBLE_VAULT_ENABLED`, ડિફોલ્ટ `false`).** જ્યારે `PII_REDACTION_ENABLED` અને `PII_REVERSIBLE_VAULT_ENABLED` બંને ચાલુ હોય (DB ઓવરરાઇડ > env > ડિફૉલ્ટ, વિનંતી દીઠ એકવાર વાંચો), `handleChat` પ્રતિ ક્લાયન્ટ વિનંતી (`src/lib/pii/requestTokenVaultScope.ts`) દીઠ એક વૉલ્ટ ખોલે છે અને તેને `GuardrailContext.tokenVault` તરીકે પ્રી-કોલ પાસમાં પાસ કરે છે. માસ્કર પછી સરોગેટ ટોકન્સ લખે છે જેમ કે `[EMAIL_REDACTED]` ને બદલે `<<PII_EMAIL_QWERTYUI_1>>`, બિલ્ટ-ઇન, વેલિડેટેડ (GDPR/POPIA) અને કસ્ટમ નિયમો એકસરખા માટે. નોન્સ એ વિનંતી દીઠ 8 રેન્ડમ અપરકેસ અક્ષરો છે, અને વિનંતીમાં સમાન મૂલ્ય સમાન ટોકન મેળવે છે. માત્ર માસ્કર મિન્ટ્સ: પ્રોમ્પ્ટ-ઇન્જેક્શન ગાર્ડ અને `/api/guardrails/test` વૉલ્ટ વિના ચાલે છે અને પ્લેસહોલ્ડર્સ રાખે છે.

- પ્રદાતા, દરેક કોમ્બો લેગ, ફરી પ્રયાસ, ફ્યુઝન પેનલ મેમ્બર અને ફ્યુઝન જજ માત્ર ટોકન્સ જ જુએ છે. ટોકન્સ એકવાર પુનઃસ્થાપિત કરવામાં આવે છે, 2xx પ્રતિસાદ પર, જે `handleChat` છોડે છે : પદચ્છેદ કરેલ SSE પર ફીલ્ડ દીઠ (ઇવેન્ટ્સમાં ટોકનનું વિભાજન હજુ પણ ઉકેલાય છે; ટૂલ-કોલ દલીલો JSON-એસ્કેપ છે) અથવા JSON બોડી પર ફીલ્ડ દીઠ, પુનઃગણિત `Content-Length` સાથે. સામગ્રી અને તર્ક ટેક્સ્ટ અને ટૂલ-કોલ દલીલો પુનઃસ્થાપિત કરવામાં આવે છે. ભૂલ સંસ્થાઓ (4xx/5xx) ટોકન્સ રાખે છે.
- નિષ્ફળતાઓ ખાનગી રહે છે: જો મિન્ટિંગ નિષ્ફળ જાય અથવા વૉલ્ટ મૂલ્યનો ઇનકાર કરે છે (1000 એન્ટ્રીઓ, મૂલ્ય દીઠ 256 અક્ષરો, કુલ 64 KB ), તેના બદલે પ્લેસહોલ્ડર લખવામાં આવે છે; એક ટોકન તિજોરી ઉકેલી શકતું નથી, અથવા પુનઃસ્થાપના જે નિષ્ફળ જાય છે, તે શાબ્દિક રહે છે અને માત્ર ગણતરી લોગ થાય છે. તિજોરીમાં કોઈ ટાઈમર નથી અને કોઈ વૈશ્વિક સ્થિતિ નથી; જ્યારે પ્રતિસાદ પ્રવાહ સમાપ્ત થાય છે, રદ થાય છે અથવા ભૂલો થાય છે ત્યારે તે સાફ થાય છે.
- જ્યારે વિનંતિમાં ટોકન્સ, મેમરી એક્સટ્રેક્શન, આઇડમ્પોટન્સી સેવ અને સિમેન્ટીક-કેશ રાઇટ્સને છોડવામાં આવે છે, કારણ કે પછીની કોઈપણ વિનંતી તે ટોકન્સને ઉકેલી શકતી નથી. કોલ લોગમાં પ્રદાતા વિનંતી અને પ્રતિસાદ ટોકન્સ વહન કરે છે; લૉગ કરેલ ક્લાયંટ રિક્વેસ્ટ બોડી હજુ પણ કાચો ક્લાયંટ ઇનપુટ છે, જેમ કે સાદા રીડેક્શન સાથે.
- ટોકન્સ પ્રતિ-વિનંતી રેન્ડમ નોન્સનો ઉપયોગ કરે છે, તેથી દરેક વળાંક પર પ્રોમ્પ્ટ ઉપસર્ગ બદલાય છે: પ્રદાતા-બાજુ પ્રોમ્પ્ટ કેશીંગ માસ્ક કરેલા વળાંકો માટે હિટ થતું નથી, અને ટોકન જે પાછળથી વળાંકમાં પાછો આવે છે (ઉદાહરણ તરીકે `previous_response_id` દ્વારા) જૂની વિનંતીથી સંબંધિત છે અને શાબ્દિક રહે છે.

#### પ્રતિ-પ્રકાર પસંદગી, કસ્ટમ પેટર્ન અને શોધ કાઉન્ટર્સ

**ડેશબોર્ડ → સેટિંગ્સ → સુરક્ષા → PII માસ્કીંગ** _what_ માસ્ક કરેલ છે તે પસંદ કરે છે. તે માસ્કિંગને સ્વિચ કરતું નથી: તે હજી પણ `PII_REDACTION_ENABLED` (વિનંતી) અને `PII_RESPONSE_SANITIZATION` (પ્રતિસાદ + SSE), બંને મૂળભૂત રીતે બંધ છે.

- **પ્રતિ-પ્રકાર પસંદગી** — બિલ્ટ-ઇન આઈડી `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`) માં સૂચિબદ્ધ છે. અનસેટ એટલે દરેક પ્રકાર (આ સેટિંગ પહેલાની વર્તણૂક અસ્તિત્વમાં હતી). વિનંતી એન્જિનની `ssn_us` પેટર્ન `ssn` પર નકશા કરે છે. નમૂનાઓ (ન્યૂનતમ, માનક, નાણાકીય, બ્રાઝિલિયન, USA, GDPR, POPIA, સંપૂર્ણ) માત્ર UI માં ચેકબોક્સ ભરો.
- **GDPR અને POPIA ઓળખકર્તાઓ** — બાર બિલ્ટ-ઇન id EU અને દક્ષિણ આફ્રિકાના વ્યક્તિગત ઓળખકર્તાઓને આવરી લે છે (નીચેનું કોષ્ટક). તેમના regexes, માન્યકર્તાઓ અને અધિકારક્ષેત્ર ટૅગ્સ એક ટેબલ, `src/shared/utils/piiPatterns.ts` માં રહે છે, જે રિસ્પોન્સ સેનિટાઈઝર (`src/lib/piiSanitizer.ts`) અને રિક્વેસ્ટ માસ્કર (`src/shared/utils/inputSanitizer.ts`) બંને વાપરે છે. મેચને ત્યારે જ રીડેક્ટ કરવામાં આવે છે જ્યારે તેનો માન્યકર્તા તેને સ્વીકારે છે; અંકોની એકદમ દોડ ક્યારેય પૂરતી હોતી નથી. એક ઓપરેટર કે જેણે આ ids અસ્તિત્વમાં હોય તે પહેલાં એક સંકુચિત પસંદગી સાચવી છે, જ્યાં સુધી નવા ids પર ટિક ન થાય ત્યાં સુધી તેની પાસે જે વર્તન હતું તે જાળવી રાખે છે.
- **કસ્ટમ પેટર્ન** 20 રેજેક્સ અથવા વાઇલ્ડકાર્ડ પેટર્ન સુધી — (`*` = સુધી 64 બિન-વ્હાઇટસ્પેસ અક્ષરો, `?` = વન). મેચો `[CUSTOM_REDACTED]` બની જાય છે. દરેક પેટર્ન `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`) દ્વારા પસાર થાય છે : વધુમાં વધુ 500 અક્ષરો, `g i m s u` સુધી મર્યાદિત ફ્લેગ્સ, કમ્પાઈલ કરવા જોઈએ, `safe-regex` (આપત્તિજનક બેકટ્રેકિંગ) પાસ કરવા જોઈએ, અને ખાલી સ્ટ્રિંગ અથવા રિડેક્શન પ્લેસહોલ્ડર સાથે મેળ ખાતો હોવો જોઈએ નહીં. એક પેટર્ન જે નિષ્ફળ જાય છે તે સાચવવામાં આવે ત્યારે અને પરીક્ષણ કરવામાં આવે ત્યારે નકારવામાં આવે છે, અને સંગ્રહિત પંક્તિ કે જે નિષ્ફળ જાય છે તે સંકલિત થવાને બદલે રનટાઇમ પર છોડવામાં આવે છે. માસ્કિંગ ચાલુ હોય ત્યારે જ કસ્ટમ પેટર્ન ચાલે છે.
- **તપાસ કાઉન્ટર્સ** — પ્રતિ-પ્રકાર ગણતરીઓ (ક્યારેય મેળ ખાતી નથી), મેમરીમાં રાખવામાં આવે છે અને પુનઃપ્રારંભ પર રીસેટ થાય છે (`src/lib/pii/piiDetectionStats.ts`). માસ્કિંગ ચાલુ હોય ત્યારે જ તેઓ વધે છે.

સેટિંગ્સ `key_value` કોષ્ટકમાં રહે છે (નેમસ્પેસ `pii_settings`, `src/lib/db/piiSettings.ts`) અને 1 સે કેશ દ્વારા વાંચવામાં આવે છે. API:

| પદ્ધતિ | પાથ                      | હેતુ                                                                     |
| ------ | ------------------------ | ------------------------------------------------------------------------ |
| `GET`  | `/api/settings/pii`      | ફ્લેગ સ્ટેટ, `enabledTypes`, `customPatterns`, ડિટેક્શન કાઉન્ટર્સ        |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = all) and/or `customPatterns` બદલો               |
| `POST` | `/api/settings/pii/test` | વધુમાં વધુ 8 KB ના નમૂના સામે એક પેટર્ન ડ્રાય-રન કરો; કંઈપણ સંગ્રહિત નથી |

ત્રણેયને મેનેજમેન્ટ ઓથની જરૂર છે અને બોડીને Zod (`src/shared/validation/schemas/piiSettings.ts`) વડે માન્ય કરો. લોગિન અક્ષમ સાથે (`requireLogin=false`) `GET` અને ટેસ્ટ એન્ડપોઇન્ટ ખુલ્લું છે, પરંતુ `PUT` હજુ પણ ડેશબોર્ડ સત્ર, `manage` -scope API કી, લખવાના અવકાશ અથવા ઉચ્ચ સાથે `oma_` એક્સેસ ટોકન અથવા લૂપબેકથી મોકલેલ CLI ટોકન અથવા આંતરિક-સેવા ટોકનની જરૂર છે.

કારણ કે માત્ર-અંક-માત્ર ફોર્મેટ્સ ઓર્ડર નંબર્સ, બિલ્ડ નંબર્સ અને ટાઇમસ્ટેમ્પ્સ સાથે અથડાય છે, સૌથી નબળા (`za_vat`, `za_tax_ref`) ને કીવર્ડ ક્યુની જરૂર છે, અને એકદમ દસ-અંકના `0..` નંબરને દક્ષિણ આફ્રિકાના ફોન નંબર તરીકે ગણવામાં આવતો નથી. અંતરે IBANs (`GB29 NWBK ...`) મેળ ખાતા નથી. સ્ટ્રીમિંગ પાથ પર કયૂ ફક્ત વર્તમાન ભાગની અંદર જ જોવામાં આવે છે. આઇડી સામાન્ય ફોન પેટર્નથી આગળ બેસે છે, તેથી માન્ય ઓળખકર્તા તેનું પોતાનું પ્લેસહોલ્ડર (`[IBAN_REDACTED]`, `[NL_BSN_REDACTED]`, ...) રાખે છે. `gdpr` અને `popia` નમૂનાઓ અનુક્રમે EU અને દક્ષિણ આફ્રિકાના id પસંદ કરે છે. માસ્કિંગ પોતે જ ઑપ્ટ-ઇન રહે છે (હાર્ડ રૂલ #20): અહીં કંઈપણ ફીચર-ફ્લેગ ડિફોલ્ટને બદલતું નથી.

### પ્રોમ્પ્ટ ઇન્જેક્શન (`promptInjection.ts`)

વપરાશકર્તા દ્વારા પૂરી પાડવામાં આવેલ સામગ્રીમાં પ્રતિકૂળ રચનાઓ શોધે છે અને ગોઠવેલી નીતિને લાગુ કરે છે. વર્તન પર્યાવરણ ચલ અને કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા સંચાલિત થાય છે:

| સેટિંગ          | Env var                                                                                               | ડિફૉલ્ટ | અસર                                                                                                                                                                                                               |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| સક્ષમ           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false`, ગાર્ડ્રેલ શોર્ટ-સર્કિટ.                                                                                                                                                                           |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` બેક-કોમ્પેટ માટે સ્વીકારવામાં આવે છે પરંતુ કરે છે** નથી** સ્ટ્રીપ ઈન્જેક્શન ટેક્સ્ટ; વિનંતી PII પુનઃલેખન `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત થાય છે.) |
| બ્લોક થ્રેશોલ્ડ | `blockThreshold` વિકલ્પ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉર્ફે `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | અવરોધિત કરવા માટે જરૂરી ન્યૂનતમ ગંભીરતા. ડિફૉલ્ટ પર માધ્યમ માત્ર અવલોકન કરે છે.                                                                                                                                   |

**મોડ અગ્રતા** (`getMode`): કોલર `options.mode` → `INJECTION_GUARD_MODE`**DB લક્ષણ-ધ્વજ ઓવરરાઇડ** (ડેશબોર્ડ → સેટિંગ્સ → ફીચર ફ્લેગ્સ) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env → `warn`. તેથી ડેશબોર્ડ ઓવરરાઇડ env vars પર જીતે છે, તેથી ફિચર ફ્લેગ્સ UI રનિંગ ગાર્ડ લાઇવને નિયંત્રિત કરે છે (કોઈ રીસ્ટાર્ટ નહીં). DB રીડ નિષ્ફળ-સલામત છે: જો તે ભૂલ કરે છે, તો રક્ષક env-આધારિત વર્તણૂક પર પાછા આવે છે, અને જ્યારે કોઈ ઓવરરાઇડ સેટ કરવામાં આવતું નથી ત્યારે વર્તણૂક ફક્ત env-રિઝોલ્યુશનની સમાન હોય છે.

શોધ સ્ત્રોતો:

1. `@/shared/utils/inputSanitizer` માંથી`sanitizeRequest()` (પાઈપલાઈનમાં અન્યત્ર વપરાયેલ વહેંચાયેલ ડિટેક્ટર સેટ).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને `markdown_system_block`, બંને `high` ગંભીરતા).
3. વૈકલ્પિક `customPatterns` કન્સ્ટ્રક્ટર વિકલ્પો (સ્ટ્રિંગ્સ, રેજેક્સ અથવા `{ name, pattern, severity }` રેકોર્ડ્સ) દ્વારા પસાર થાય છે.

જ્યારે `mode === "block"`** અને** ઓછામાં ઓછી એક તપાસ ગંભીરતાના થ્રેશોલ્ડને પૂર્ણ કરે છે, `preCall` `{ block: true, message: "Request rejected: suspicious content detected" }` પરત કરે છે. `warn`/`log` મોડમાં ગાર્ડરેલ લૉગ કરે છે પરંતુ કૉલ કરવાની મંજૂરી આપે છે. શેર કરેલ હેલ્પર `evaluatePromptInjection()` એ કોલર્સ માટે પણ નિકાસ કરવામાં આવે છે જેમને રજિસ્ટ્રીમાંથી પસાર થયા વિના પ્રોમ્પ્ટનું મૂલ્યાંકન કરવાની જરૂર હોય છે.

**સ્કેન બાઉન્ડ (v3.8.20):** ડિટેક્ટર માત્ર તપાસ કરે છે** પ્રથમ 16 KB** `src/shared/utils/inputSanitizer.ts` માં જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટ — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ્સ) નું. પેટર્ન લૂપ ચલાવતા પહેલા `detectInjection()` અને `evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` બંને. ઇન્જેક્શન ડાયરેક્ટિવ્સ ઇનપુટની ટોચની નજીક બેસે છે, તેથી આ નબળા ડિટેક્શન (cf. #3932, #4041) વગર મલ્ટિ-સો-KB પેલોડ્સ પર રેગેક્સ CPU/GC ને કૅપ કરે છે.

### ઓળખપત્ર માસ્કર (`credentialMasker.ts`)

પર ચાલે છે** બંને** તબક્કાઓ, મૂળભૂત સાંકળમાં છેલ્લી (અગ્રતા `95`). આઉટબાઉન્ડ પેલોડ (સંદેશ સામગ્રી, ટૂલ-કોલ દલીલો, સાધન પરિણામો) માંથી જાણીતા API-કી / ગુપ્ત-ટોકન પેટર્નને સુધારે છે** અને** પ્રદાતાનો પ્રતિસાદ, જેથી પ્રોમ્પ્ટમાં પેસ્ટ કરેલ ઓળખપત્ર (અથવા ટૂલ પરિણામ દ્વારા ઇકોડ બેક) અપસ્ટ્રીમ પ્રદાતાને અથવા ક્લાયન્ટને પાછું લીક કરવામાં આવતું નથી.

- **ફક્ત પસંદ કરો** PII #20 `settings.credentialRedactionEnabled === true`** અથવા** `CREDENTIAL_REDACTION_ENABLED=true` તેને બંધ કરીને, ગાર્ડરેલ એક નો-ઓપ — છે તે ક્યારેય અવરોધતું નથી અને ક્યારેય ફરીથી લખતું નથી.
- `redactCredentials()` સંપૂર્ણ payload/response ટ્રી પર ચાલે છે (`walkValue()`, પ્રોટોટાઇપ-પોલ્યુશન-સેફ, સાયકલ-સેફ વાયા `WeakSet`) અને મેચોને `[REDACTED:<type>]` પ્લેસહોલ્ડરથી બદલે છે, ફક્ત તે શાખાઓનું ક્લોનિંગ કરે છે જે ખરેખર બદલાઈ હોય.
- `CREDENTIAL_PATTERNS` LLM પ્રદાતા કીઓ (OpenAI, OpenAI-proj, Anthropic, Google, હગિંગ ફેસ, રિપ્લિકેટ), VCS/SaaS ટોકન્સ (GitHub, Slack, લીનિયર, Notion, npm, પોસ્ટમેન, Discord), પેમેન્ટ કી (AWS કવર કરે છે Twilio, SendGrid, Mailgun), ખાનગી કીઓ / JWTs, ઓળખપત્ર-બેરિંગ કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-વેલ્યુ પેટર્ન. હેડર-આકારની ચાવીઓ (`authorization`, `x-api-key`, `api-key`, `apikey`) સામાન્ય ટેક્સ્ટ રેજેક્સ દ્વારા બદલે માળખાકીય રીતે (માત્ર મૂલ્ય, યોજના ઉપસર્ગ જેમ કે `Bearer `/`Basic ` સાચવેલ છે) સુધારેલ છે.
- રક્ષક ક્યારેય અવરોધતું નથી; તે ફક્ત ફરીથી લખે છે (`modifiedPayload` / `modifiedResponse`) અને ટીકા કરે છે (`meta.credentialsRedacted`, `meta.count`).

રીગ્રેશન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## બેઝ કોન્ટ્રાક્ટ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને શોર્ટ-સર્કિટ કરે છે
  message?: string; // બ્લોક કરતી વખતે દેખાય છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિભાવને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેઇલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં" સૂચવે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ડાઉનસ્ટ્રીમ ગાર્ડરેઇલ્સ માટે ચેઇનમાંથી વહેતી વેલ્યુ બદલાઈ જાય છે. `signal?: AbortSignal` કૉલર લાઇફસાઇકલને ગાર્ડરેઇલ્સ સુધી પહોંચાડે છે. વિનંતી abort એ જાણીજોઈને રાખવામાં આવેલો fail-open અપવાદ છે: મીડિયા બ્રિજીસ કામ બંધ કરે છે અને કાચું મીડિયા એવા ટાર્ગેટ પર પુનઃસ્થાપિત કર્યા વગર cleanup કરે છે જે તેને સપોર્ટ કરતું નથી એવું જાણીતું છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` આ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેઇલ ઉમેરે છે (અથવા સામાન્યકૃત નામ મુજબ બદલે છે) અને
  ઊંચતા `priority` મુજબ ફરીથી ક્રમમાં ગોઠવે છે.
- `clear()` / `list()` — વહીવટી મદદરૂપો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેઇલ્સ પર ફરે છે, પેલોડને
  `modifiedPayload` દ્વારા આગળ વધારે છે, અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિભાવ બાજુ પર સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્થિતિ સાફ કરે છે અને સ્વચ્છ
  ટેસ્ટ આઇસોલેશન માટે વૈકલ્પિક રીતે ડિફોલ્ટ્સ ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }` પરત કરે છે
જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સનું એરે છે જેમાં
દરેક ગાર્ડરેઇલ માટે `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સામેલ છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### પ્રતિ-વિનંતી ગાર્ડરેઇલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન વિનંતી માટે
અવગણવામાં આવવા જોઈએ તેવા ગાર્ડરેઇલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
પાંચ ચેનલો છે, જે આ ક્રમમાં વાંચવામાં આવે છે અને એક યાદીમાં મર્જ થાય છે
(ડુપ્લિકેટ દૂર કરતી વખતે પ્રથમ ઉપસ્થિતિ જીતે છે):

1. `apiKeyInfo.disabledGuardrails`
2. વિનંતી બોડી `disabledGuardrails` (ટોપ-લેવલ)
3. વિનંતી બોડી `metadata.disabledGuardrails` (ફક્ત જ્યારે `metadata` ઓબ્જેક્ટ હોય)
4. હેડર `x-omniroute-disabled-guardrails`
5. લિગસી હેડર `x-disabled-guardrails`

બધી પાંચ ચેનલો મર્જ થાય છે, બંને હેડરો સહિત: બંને
`x-omniroute-disabled-guardrails` અને `x-disabled-guardrails` મોકલવાથી તેમની
યાદીઓના સંયોગને અવગણવામાં આવે છે, અને ખાલી આધુનિક હેડર હવે લિગસી હેડરને
છુપાવતું નથી
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), જે
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805) માં ઠીક કરવામાં આવ્યું).

વેલ્યુઝ સ્ટ્રિંગ્સની એરે અથવા અલ્પવિરામથી અલગ થયેલી સ્ટ્રિંગ હોઈ શકે છે; નામો
ટ્રિમ કરવામાં આવે છે અને લોઅરકેસ kebab-case માં સામાન્યકૃત કરવામાં આવે છે
(`pii_masker` → `pii-masker`), અને ખાલી એન્ટ્રીઓ કાઢી નાખવામાં આવે છે. પરિણામ
`context.disabledGuardrails` દ્વારા રજિસ્ટ્રી સુધી પહોંચાડવામાં આવે છે, જે
મેળ ખાતી ગાર્ડરેઇલ્સને અવગણે છે (`results` માં `skipped: true`).

અક્ષમ યાદી ફક્ત **રજિસ્ટ્રી**ને અસર કરે છે. પ્રોમ્પ્ટ-ઇન્જેક્શન `block` મોડ એ
ફરજિયાત સીમા છે: ઇન્જેક્શન-ગાર્ડ મિડલવેર
(`src/middleware/promptInjectionGuard.ts`) કોઈપણ કૉલર-નિયંત્રિત અક્ષમ યાદી વગર
`evaluatePromptInjection()` ને કૉલ કરે છે (તે અગાઉ કરતું હતું તે મૃત
`resolveDisabledGuardrails({ body })` કૉલ
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934) માં દૂર કરવામાં આવ્યો હતો),
તેથી `prompt-injection` ને અક્ષમ કરતી વિનંતી હજુ પણ `block` મોડમાં નકારવામાં આવે છે.
આ ડિઝાઇન મુજબ છે. અક્ષમ ચેનલો કૉલર-નિયંત્રિત છે (વિનંતી બોડી, મેટાડેટા, હેડરો),
અને કૉલર ઓપરેટર દ્વારા સેટ કરેલા સુરક્ષા નિયંત્રણને બંધ કરી શકવો જોઈએ નહીં
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).
[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412) નો હેડર સંયોગ
ફક્ત કઈ રજિસ્ટ્રી ગાર્ડરેઇલ્સ અવગણવામાં આવે છે તે બદલે છે; તે ક્લાયન્ટને
મિડલવેરને બાયપાસ કરવા દેતું નથી. ફરજિયાત પ્રતિ-કી અને પ્રતિ-જૂથ ગાર્ડરેઇલ નીતિઓ
v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417) માં ટ્રેક કરવામાં આવે છે.
[કવરેજ અને મર્યાદાઓ](#coverage-and-limits) જુઓ.

## એક્ઝેક્યુશન ઓર્ડર

`src/sse/handlers/chat.ts` અને `open-sse/handlers/chatCore.ts` દ્વારા વહેતી દરેક વિનંતી માટે ( [કવરેજ અને મર્યાદા](#coverage-and-limits) હેઠળ સૂચિબદ્ધ ચેટ-ફેમિલી રૂટ્સ):

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડરોમાંથી સ્કીપ લિસ્ટ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા અગ્રતા ક્રમમાં રક્ષકો ચલાવે છે:
   - વિકલાંગ રક્ષકોને `skipped` તરીકે નોંધવામાં આવે છે.
   - દરેક રક્ષકનું `preCall` પેલોડને `modifiedPayload` દ્વારા ફરીથી લખી શકે છે.
   - પ્રથમ `block: true` સાંકળને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર રક્ષક અસ્વીકાર પ્રતિસાદ આપે છે.
3. (સંભવિત રીતે ફરીથી લખાયેલ) પેલોડ કોમ્બો રૂટીંગ અને અપસ્ટ્રીમ ડિસ્પેચમાં વહે છે.
4. **માત્ર બિન-સ્ટ્રીમિંગ:** પ્રતિભાવ એસેમ્બલ થયા પછી, `guardrailRegistry.runPostCallHooks(...)` પ્રતિસાદ પર સમાન સાંકળ ચલાવે છે. `block: true` અહીં અપસ્ટ્રીમ પ્રતિસાદને ડ્રોપ કરે છે અને HTTP 400 પરત કરે છે. સ્ટ્રીમ કરેલા પ્રતિસાદો આ પગલું સંપૂર્ણપણે છોડી દે છે.
5. **માત્ર ઉલટાવી શકાય તેવું વૉલ્ટ:** જ્યારે વિનંતી ટોકન્સ મિન્ટ કરે છે, ત્યારે `handleChat` તેમને 2xx પ્રતિસાદ પર પુનઃસ્થાપિત કરે છે, જે પોસ્ટ-કોલ હુક્સ અને સ્ટ્રીમિંગ PII ટ્રાન્સફોર્મ પછી આપે છે, તેથી `PII_RESPONSE_SANITIZATION` ટોકન્સ અને મોડેલ-જનરેટેડ PII જુએ છે, જે ક્યારેય પુનઃસ્થાપિત મૂળ નથી.

ગાર્ડરેલ્સ જે ફેંકે છે તે `error: <message>` સાથે રેકોર્ડ કરવામાં આવે છે અને `logger.warn` દ્વારા લૉગ કરવામાં આવે છે, પરંતુ સાંકળ ડિઝાઇન દ્વારા — ફેલ-ઓપન ચાલુ રહે છે.

## કવરેજ અને મર્યાદા

ગાર્ડરેલ રજિસ્ટ્રી માત્ર ચેટ પાઇપલાઇનમાં વાયર્ડ છે. આ મર્યાદાઓ `tests/unit/guardrail-pipeline-wiring-characterization.test.ts` અને `tests/unit/guardrail-pipeline-characterization.test.ts` દ્વારા પિન કરેલ છે; જ્યારે વર્તન બદલાય ત્યારે તે પરીક્ષણોને જાણીજોઈને અપડેટ કરો.

### શું આવરી લેવામાં આવતું નથી

- **મીડિયા, એમ્બેડિંગ્સ અને ડેટા રૂટ્સ** (`/v1/images/*`, `/v1/embeddings`, `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/rerank`, `/v1/search`, `/v1/moderations`) ક્યારેય રજિસ્ટ્રી સુધી પહોંચતા નથી. ત્યાં કોઈ PII માસ્કિંગ, ઓળખપત્ર માસ્કિંગ અથવા મોડલિટી બ્રિજ ચાલતું નથી. તેમની એકમાત્ર તપાસ એ લેગસી ઈન્જેક્શન-ગાર્ડ મિડલવેર છે.
- **સ્ટ્રીમ કરેલ પ્રતિસાદો** કોઈ પોસ્ટ-કોલ ગાર્ડરેલ્સ મેળવો નહીં: કોઈ `pii-masker` અથવા `credential-masker` પોસ્ટ-કોલ નહીં, અને કોઈ પોસ્ટ-કોલ બ્લોક નહીં. માત્ર સ્ટ્રીમિંગ PII ટ્રાન્સફોર્મ લાગુ થાય છે (જ્યારે `PII_RESPONSE_SANITIZATION` ચાલુ હોય). સ્ટ્રીમ કરેલ પ્રતિસાદમાં પાછા પડઘો પાડેલ ઓળખપત્રને સુધારેલ નથી.
- **ચેનલો વિ. મિડલવેર (ડિઝાઇન દ્વારા) અક્ષમ કરો:** મિડલવેર કોઈપણ કોલર-નિયંત્રિત અક્ષમ સૂચિને પસાર કર્યા વિના, `evaluatePromptInjection()` ને તેના પોતાના કોલ સાથે પ્રોમ્પ્ટ ઈન્જેક્શનનું મૂલ્યાંકન કરે છે. `block` મોડ એ ફરજિયાત સીમા છે જેને કૉલર-નિયંત્રિત ડિસેબલ બાયપાસ કરી શકતું નથી, જેમાં ચેટ-ફેમિલી રૂટ્સ ( [#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413) )નો સમાવેશ થાય છે. `prompt-injection` ને અક્ષમ કરવાથી માત્ર રજિસ્ટ્રી ગાર્ડ્રેલ છૂટી જાય છે.

### પોસ્ટ-કોલ પહેલાં પ્રતિસાદ શું જુએ છે

નોન-સ્ટ્રીમિંગ પાથ પર ઓર્ડર છે: મેમરી એક્સટ્રેક્શન → બિલ્ટ-ઇન ટૂલ એક્ઝેક્યુશન → પોસ્ટ-કોલ ગાર્ડરેલ્સ → પોસ્ટ-કોલ બ્લોક એક્ઝિટ → સિમેન્ટીક-કેશ સ્ટોર.

- **મેમરી નિષ્કર્ષણ** અને** સાધન અમલ** પોસ્ટ-કોલ ગાર્ડરેલ્સ તેને ફરીથી લખી અથવા અવરોધિત કરી શકે તે પહેલાં પ્રતિસાદ જુઓ. [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) થી, મેમરી એક્સટ્રેક્શન એ એક્સટ્રેક્ટેડ ટેક્સ્ટને `sanitizePII` દ્વારા ચલાવે છે જ્યારે `PII_RESPONSE_SANITIZATION` ચાલુ હોય (બંને સ્ટ્રીમિંગ અને નોન-સ્ટ્રીમિંગ), પરંતુ એક પ્રતિભાવ કે જે પોસ્ટ-કોલ પછીના બ્લોક્સ હજુ પણ મેમરી અને ટૂલ્સને ઓફર કરવામાં આવે છે.
- **સિમેન્ટીક કેશ** પોસ્ટ-કોલ પછી પ્રતિભાવને સંગ્રહિત કરે છે, તેથી તે ફરીથી લખેલા પ્રતિભાવને સંગ્રહિત કરે છે, અને અવરોધિત પ્રતિસાદ ક્યારેય કેશ થતો નથી. કેશ એન્ટ્રીઝ API કી દીઠ કી કરવામાં આવે છે.

## રૂપરેખાંકન

બિલ્ટ-ઇન ગાર્ડરેલ્સ દ્વારા વાંચવામાં આવતા પર્યાવરણીય ચલો:

| ચલ                                    | દ્વારા વપરાય છે            | અસર                                                                                                    |
| ------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | શોધને સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                      |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | ઇન્જેક્શન નીતિ: `warn`, `block`, અથવા `log`. લેગસી મૂલ્ય `redact` ઇન્જેક્શન ટેક્સ્ટને ફરીથી લખતું નથી. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | ઈન્જેક્શન ગાર્ડ માટે મોડ; પણ એક DB લક્ષણ ધ્વજ કે** ઓવરરાઇડ કરે છે** env vars (DB > ENV).               |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | ન્યૂનતમ ગંભીરતા કે જે `MODE=block` નકારે છે: `high` (ડિફોલ્ટ), `medium`, અથવા `low`.                   |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` માટે લેગસી ઉપનામ.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | જ્યારે `true`, વિનંતી PII રીડેક્ટ કરવામાં આવે છે (ઇન્જેક્શન મોડથી સ્વતંત્ર).                           |
| `PII_REVERSIBLE_VAULT_ENABLED`        | `pii-masker`, `handleChat` | `PII_REDACTION_ENABLED` સાથે, મિન્ટ રિવર્સિબલ ટોકન્સ અને તેમને 2xx પ્રતિસાદોમાં પુનઃસ્થાપિત કરો.       |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ડાઉનસ્ટ્રીમ) | પ્રતિભાવ-બાજુના માસ્કર વર્તનને નિયંત્રિત કરે છે.                                                       |

મોડાલિટી બ્રિજ ગાર્ડરેલ્સ ડીબી-બેક્ડ સેટિંગ્સ સ્ટોરમાંથી રનટાઇમ રૂપરેખા વાંચે છે (`getSettings()`), env vars નહીં. વિઝનની પ્રાથમિક કીઓ `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` છે. લેગસી `visionBridge*` કી માત્ર દસ્તાવેજીકૃત વન-સાયકલ રીડ ફોલબેક તરીકે સ્વીકારવામાં આવે છે; ડેશબોર્ડ લખે છે પ્રાથમિક કીનો ઉપયોગ કરે છે. ડિફોલ્ટ્સ અને ફોલબેક રિઝોલ્વર `src/shared/constants/modalityBridgeDefaults.ts` માં રહે છે, `src/shared/constants/visionBridgeDefaults.ts` માં લેગસી સ્થિરાંકો જાળવી રાખવામાં આવે છે.

ઑડિયો `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`, `modalityBridgeAudioTimeout`, અને `modalityBridgeAudioMaxClips`, વત્તા વહેંચાયેલ `modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે. ઑડિયોમાં કોઈ લેગસી-કી ફૉલબૅક નથી કારણ કે આ કીઓ મોડાલિટી બ્રિજ સ્કીમા સાથે રજૂ કરવામાં આવી હતી.

વિડિઓ `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`, `modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos`, અને `modalityBridgeVideoTimeout`, વત્તા શેર કરેલ `modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે. તે ડિફૉલ્ટ રૂપે અક્ષમ છે કારણ કે FFmpeg/ffprobe એ વૈકલ્પિક ઓપરેશનલ અવલંબન છે અને ફ્રેમ કૅપ્શનિંગ લેટન્સી અને મોડેલ ખર્ચ ઉમેરે છે.

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail` ને વિસ્તારતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે રજિસ્ટર કરો (`registerDefaultGuardrails` માંથી પુશ કરીને) અથવા
   રનટાઇમે `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન
   નોર્મલાઇઝ્ડ નામ ધરાવતા અગાઉના કોઈપણ ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ ટેસ્ટ ઉમેરો (હાલના ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

ટેસ્ટો વચ્ચે જાણીતી સ્થિતિથી શરૂઆત કરવા માટે `resetGuardrailsForTests()` વાપરો.
ખાલી રજિસ્ટ્રીથી શરૂ કરવા અને ફક્ત પરીક્ષણ હેઠળના ગાર્ડરેલ્સ જ રજિસ્ટર કરવા માટે
`{ registerDefaults: false }` પાસ કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન સ્વીકારે છે (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge સેટિંગ્સ, ક્ષમતાઓ, STT મોડલ પસંદગી, ક્રેડેન્શિયલ
તપાસો અને ટ્રાન્સક્રિપ્શન માટે સમાન સીમ્સ એક્સપોઝ કરે છે. તેથી ટેસ્ટો DB
અથવા નેટવર્ક ઍક્સેસ વગર બંને ફ્લોનું પરીક્ષણ કરી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લોક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) યુઝર પ્રોમ્પ્ટ સ્વીકારતા
તમામ રૂટ્સને કવર કરે છે. તે `INJECTION_GUARD_MODE` નું પાલન કરે છે (ડિફૉલ્ટ `warn` = ફક્ત લોગ;
`block` = HTTP 400 `SECURITY_001` પરત આપે છે).

| પ્રકાર          | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલના) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા            | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ એક્સ્ટ્રૅક્શન (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ને કવર કરે છે.

**રેડ-ટીમ (નાઇટલી, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે `INJECTION_GUARD_MODE=block` માં
દરેક રૂટ OWASP-LLM કોર્પસને બ્લોક કરે છે; garak પ્રોબ્સ ચલાવે છે (સિક્રેટ વગર સ્કિપ કરે છે).
સુસંગતતા માટે `moderations` સામેલ છે. બ્લોક મોડ એક ફરજિયાત સીમા છે: `evaluatePromptInjection()`
મિડલવેર તેને પાસ કરેલી પ્રતિ-રિક્વેસ્ટ ડિસેબલ યાદીને અવગણે છે, તેથી `disabledGuardrails`
કોઈ રૂટને તેનાથી મુક્તિ આપતું **નથી** ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

નાઇટલી વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ) માં બે જોબ્સ છે:

- **`promptfoo-guard` (અવરોધક)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ
  (દા.ત. "અગાઉની તમામ સૂચનાઓને અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે
  પ્રતિભાવમાં `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે ખરેખર
  રિક્વેસ્ટ નકારી છે.
- **`garak` (સલાહકાર)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ (`http://localhost:20128/v1`)
  સામે garak `--probes promptinject,dan,leakreplay` ચલાવે છે. પ્રોવાઇડર
  સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સુવ્યવસ્થિત રીતે સ્કિપ કરે છે અને
  `|| true` સફિક્સ ધરાવે છે, તેથી CI નિષ્ફળ કર્યા વગર રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`) નું કવરેજ
દરેક પ્રોમ્પ્ટ-ધરાવતા `/v1` રૂટ સુધી ફેલાયેલું છે; પ્રોમ્પ્ટ ટેક્સ્ટ
`src/shared/utils/inputSanitizer.ts` માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` માંથી ખેંચવામાં આવે છે.
