## અવલોકન

Quota Sharing Engine એક જ કનેક્શન શેર કરતી બહુવિધ API કીઓ વચ્ચે પ્રદાતાનો સમય-આધારિત ક્વોટા (દા.ત. Codex
5-કલાકની વિન્ડો, Kimi 1500 req/h) ન્યાયસંગત રીતે વિતરિત કરે છે.

**તે જે સમસ્યા ઉકેલે છે:** OmniRoute એક જ અપસ્ટ્રીમ પ્રદાતા એકાઉન્ટ સામે ઘણી API કીઓને
પ્રોક્સી કરે છે. શેરિંગ લોજિક વિના, કી A તરફથી આવતો અચાનક ભારે પ્રવાહ એક કલાક માટેનો
પ્રદાતાનો ક્વોટા સમાપ્ત કરી શકે છે, જેના કારણે વિન્ડો રીસેટ થાય ત્યાં સુધી કીઓ B અને C અવરોધિત રહે છે.
એન્જિન આને નીચે મુજબ અટકાવે છે:

1. દરેક પરિમાણ (%, requests, tokens, $) માટે પ્રત્યેક કીના રોલિંગ વપરાશને ટ્રૅક કરીને.
2. કાર્ય-સંરક્ષક ન્યાયસંગત-હિસ્સા અલ્ગોરિધમ લાગુ કરીને: જ્યાં સુધી વૈશ્વિક પૂલ સંતૃપ્ત ન હોય ત્યાં સુધી કી નિષ્ક્રિય
   હિસ્સાઓમાંથી ઉધાર લઈ શકે છે.
3. વિનંતી અપસ્ટ્રીમ એક્ઝિક્યુટર સુધી પહોંચે તે પહેલાં હૉટ પાથ (`chatCore.ts`) માં પરિણામ
   લાગુ કરીને.

## અલ્ગોરિધમ: ફેર-શેર વર્ક-કન્સર્વિંગ

`src/lib/quota/fairShare.ts` માં અમલી.

### મોડ્સ

| શરત                                        | મોડ      | વર્તન                                                  |
| ------------------------------------------ | -------- | ------------------------------------------------------ |
| `globalUsedPercent < saturationThreshold`  | **ઉદાર** | કી વૈશ્વિક મર્યાદા માઈનસ વપરાશ-કુલ સુધી ઉધાર લઈ શકે છે |
| `globalUsedPercent >= saturationThreshold` | **કડક**  | વ્યક્તિગત વાજબી શેરને સખત રીતે લાગુ કરો                |

ડિફૉલ્ટ `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`).

આ બે સ્થિતિઓ ડિફોલ્ટ બોરો મોડ, `saturation` માં પૂલનું વર્ણન કરે છે. `consent` મોડમાં પૂલ હંમેશા કડક નિયમો લાગુ કરે છે, ગમે તે સંતૃપ્તિ હોય. [સંમતિ ધિરાણ (પ્રતિ-પૂલ ઑપ્ટ-ઇન)](#consented-lending-per-pool-opt-in) જુઓ.

### પરિમાણ દીઠ નિર્ણય

પૂલમાં દરેક સક્રિય પરિમાણ માટે, એન્જિન ગણતરી કરે છે:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

`percent` પરિમાણો માટે, `consumed` તેના બદલે એટ્રિબ્યુશન પુસ્તકમાંથી આવે છે (જુઓ [ટકાના પરિમાણો: પ્રતિ-કી એટ્રિબ્યુશન](#percent-dimensions-per-key-attribution) ).

પછી:

- **`policy = hard`** : જો `consumed > fairShareAllowed` અને મોડ કડક → છે** બ્લોક** .
- **`policy = soft`** : જો `consumed > fairShareAllowed` અને મોડ કડક → છે** દંડ કરવો** (કોમ્બોમાં વંચિત કરો; હાર્ડ-બ્લોક ક્યારેય નહીં).
- **`policy = burst`** : વાજબી શેરને ધ્યાનમાં લીધા વિના વૈશ્વિક હેડરૂમ અસ્તિત્વમાં હોય ત્યારે મંજૂરી આપો.

### સંપૂર્ણ કેપ

ફાળવણી પર `capValue` + `capUnit` એ મોડ અથવા પોલિસીથી સ્વતંત્ર સખત ટોચમર્યાદા છે. કોઈપણ પરિમાણ જ્યાં હંમેશા `consumed >= capValue`** બ્લોક્સ** વિનંતી. `percent` કેપ માટે, `consumed` એ ફક્ત કીને આભારી ભાગ છે.

### મલ્ટી-ડાયમેન્શન ચેક

એક વિનંતી અવરોધિત છે જો** કોઈપણ** પૂલમાં પરિમાણ તેને અવરોધિત કરશે. પરિમાણો સ્વતંત્ર — છે અને 5h% થાક સાપ્તાહિક% પરિમાણને અસર કરતું નથી.

### ઉધાર

ઉદાર મોડમાં, એક ચાવી જેની ફાળવણી ઓછી છે તે અન્ય કીના ફાળવણી ન કરાયેલ શેરમાંથી સરપ્લસનો ઉપયોગ કરી શકે છે. સૂત્ર છે:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

જ્યાં `consumedByOtherKeys = consumedTotal - consumedByThisKey` ટેટો ગ્લોબલ (તે પરિમાણ માટે પૂલ `limit` ) હંમેશા સખત ટોચમર્યાદા હોય છે.

### સંમત ધિરાણ (પ્રતિ-પૂલ ઑપ્ટ-ઇન)

દરેક પૂલમાં ઉધાર મોડ હોય છે. `saturation` એ ડિફોલ્ટ છે અને ઉપરના નિયમો રાખે છે. `consent` મોડમાં `hard` કી તેનો હિસ્સો માત્ર ક્ષમતાની અંદર જ પસાર કરે છે જે અન્ય કી ઉધાર આપવા માટે સંમત થાય છે. એડમિનિસ્ટ્રેટર દરેક પૂલનો મોડ સેટ કરે છે. દરેક કી ધારક [ધિરાણ સંમતિ](#lending-consent) દ્વારા તેમની પોતાની સંમતિ નક્કી કરે છે.

સંમતિ એ 0 થી 100 સુધીની ટકાવારી છે અને યુગ મિલિસેકન્ડમાં વૈકલ્પિક સમયમર્યાદા છે. કી તેના નિષ્ક્રિય શેરની તે ટકાવારી આપે છે જ્યારે અંતિમ તારીખ ભવિષ્યમાં હોય છે.

એક પરિમાણ માટે, `L` એ અસરકારક મર્યાદા છે: યોજના મર્યાદા પૂલના એકાઉન્ટ્સને ગણી દે છે. વિનંતી કરતી કી માટે ગેટ ગણતરી કરે છે:

```
share_k         = w_k / 100 × L
idle_k          = max(0, share_k − consumed_k)
lent            = Σ over the other keys of lend_k / 100 × idle_k
taken           = Σ over the other keys of max(0, consumed_k − share_k)
borrowAvailable = max(0, lent − taken)
```

`w_k` એ કીનું વજન છે, અથવા દરેક કી માટે `100 / n` જ્યારે કોઈ વજન 0 થી ઉપર ન હોય. `lend_k` એ કીની સક્રિય ટકાવારી છે, અને 0 તેની સમયમર્યાદા પસાર થઈ જાય તે પછી. વિનંતી કરતી કીની પોતાની સંમતિ ક્યારેય ગણાતી નથી. `hard` કી એકવાર તેનો વપરાશ તેના શેર વત્તા `borrowAvailable` સુધી પહોંચે ત્યારે તેને નકારવામાં આવે છે.

કોઈ ફાળવણીનો દાવો ન કરે તેવી ક્ષમતા (વજનના સરવાળાથી 100 ઓછા) ધિરાણપાત્ર નથી. કોઈ ચાવી તેને ઉધાર આપવા માટે સંમત થયા નથી.

**ઉદાહરણ.** `L` 1000 છે.

| કી  | વજન | શેર કરો | વપરાશ | ધિરાણ આપે છે |
| --- | --- | ------- | ----- | ------------ |
| એ   | 50  | 500     | 530   | 0%           |
| બી  | 30  | 300     | 100   | 50%          |
| સી  | 0   | 0       | 60    | 0%           |

- B તેના નિષ્ક્રિય 200 ના 50% ધિરાણ આપે છે, જે 100 છે. C પહેલેથી જ તેના હિસ્સા ઉપર 60 લે છે. A 40 ઉધાર લઈ શકે છે.
- A 530 પર પીરસવામાં આવે છે અને જ્યારે તેનો વપરાશ 540 સુધી પહોંચે ત્યારે તેનો ઇનકાર કરવામાં આવે છે.
- C કંઈપણ વાપરે તે પહેલાં, A સાથે તેના શેર પર અથવા તેની નીચે, C 100 ઉધાર લઈ શકે છે.
- C કંઈપણ વાપરે તે પહેલાં, A સાથે 530 પર, C 70 ઉધાર લઈ શકે છે.

**શૂન્ય વજન.** વજન 0 વાળી ચાવી 0 નો હિસ્સો ધરાવે છે. તે ફક્ત ત્યારે જ પીરસવામાં આવે છે જ્યારે તેનો વપરાશ અન્ય લોકો જે ઉધાર આપે છે તેનાથી ઓછો હોય. જ્યારે કોઈ ધિરાણ કરતું નથી, ત્યારે તેની પ્રથમ વિનંતીથી તેને નકારવામાં આવે છે.

**સમયમર્યાદા.** કોઈપણ પૃષ્ઠભૂમિ કાર્ય સંમતિ સમાપ્ત થતું નથી. દરેક વિનંતી તેના પોતાના સમય સાથે સમયમર્યાદાની તુલના કરે છે, અને તે સમયની સમાન સમયમર્યાદા પસાર થઈ ગઈ છે. એક સંગ્રહિત સમયમર્યાદા કે જે મર્યાદિત સંખ્યા નથી, અથવા `Date` ધારણ કરી શકે તે સૌથી મોટી તારીખથી વધુ છે, તે પસાર તરીકે ગણવામાં આવે છે.

**`soft` અને `burst`.** ધિરાણ તેમને મર્યાદિત કરતું નથી. એક `soft` કી એકવાર તેનો હિસ્સો પસાર થઈ જાય પછી વંચિત કરવામાં આવે છે. જ્યારે પૂલમાં જગ્યા હોય ત્યારે `burst` કી પસાર થાય છે. જ્યારે પૂલની કુલ મર્યાદા પહોંચી જાય ત્યારે પૂલની ટોચમર્યાદા હજુ પણ દરેક કીને નકારે છે.

**વિનંતી પાથ પર ખર્ચ.** એક `saturation` પૂલ પહેલા કરતાં વધુ કંઈ વાંચતું નથી. `consent` પૂલમાં, ગણતરીપાત્ર પરિમાણ તેના શેર પર અથવા તેની ઉપરની `hard` કી માટે જ અન્ય કી વાંચે છે જ્યારે બીજી કી ઉધાર આપે છે. તે પછી સમાંતર રીતે, અન્ય કી દીઠ એક વાંચન બનાવે છે. નિષ્ફળ વાંચન તે કી માટે 0 ના વપરાશ તરીકે ગણાય છે. એક `percent` પરિમાણ કોઈ વાંચન ઉમેરતું નથી, કારણ કે એટ્રિબ્યુશન પુસ્તક દરેક કી ધરાવે છે.

**પૂલ સંપાદિત કરી રહ્યા છીએ.** સંપાદન રહેતી કીની સંમતિ રાખે છે. આ ફાળવણી સંપાદનો, જૂથ-વ્યાપી રિપ્લેસમેન્ટ અને `ensure` કૉલ્સ માટે ધરાવે છે. દૂર કરેલી કી તેની સંમતિ ગુમાવે છે, અને ફરીથી ઉમેરવામાં આવેલી કી 0 થી શરૂ થાય છે. એડમિન રૂટ દરેક કીની સંમતિ પરત કરે છે અને તેને ક્યારેય લખતા નથી. પૂલને `saturation` પર પાછા સ્વિચ કરવાથી દરેક સંગ્રહિત સંમતિ જળવાઈ રહે છે, જેની તે મોડમાં કોઈ અસર થતી નથી. પૂલને `consent` પર સ્વિચ કરવાથી સંગ્રહિત સંમતિઓ ફરીથી સક્રિય થાય છે જેની સમયમર્યાદા પસાર થઈ નથી. કી ધારક કોઈપણ સ્થિતિમાં સંગ્રહિત સંમતિ સાફ કરી શકે છે.

**અપગ્રેડ કરી રહ્યું છે.** જો કૉલમ `lending_percent` અને `lending_until` પહેલેથી અસ્તિત્વમાં છે, તો સ્થળાંતર માત્ર `borrow_mode` ઉમેરે છે, અને સંગ્રહિત ટકાવારી જેમ છે તેમ રહે છે. દરેક પૂલ `saturation` મોડમાં શરૂ થાય છે. પૂલ વિઝાર્ડમાં પૂલ દીઠ `consent` ચાલુ કરો. સંગ્રહિત મૂલ્યોમાંથી કંઈપણ અનુમાનિત નથી.

**મર્યાદાઓ.**

- ધિરાણકર્તા તેના પોતાના હિસ્સાનો ઉપયોગ કરે તે પહેલાં તેની ટોચમર્યાદા પર પૂલ શોધી શકે છે. અન્ય લોકોએ ઉધાર લીધેલી ક્ષમતા પૂલના કુલમાં ગણાય છે.
- ચેક વિનંતી પહેલાં ચાલે છે અને કંઈપણ અનામત રાખતું નથી. સહવર્તી વિનંતીઓ કોઈપણ રેકોર્ડ થાય તે પહેલાં વપરાશ વાંચે છે, તેથી ઉધાર ક્ષમતા એક કરતા વધુ વખત ખર્ચી શકાય છે, જે ફ્લાઇટમાં વિનંતીઓ દ્વારા બંધાયેલ છે. `saturation` મોડના શેર ચેકમાં સમાન મિલકત છે.

## સ્લાઇડિંગ વિન્ડો કાઉન્ટર

`src/lib/quota/sqliteQuotaStore.ts` અને `redisQuotaStore.ts` માં અમલમાં મૂકાયેલ છે.

પ્રત્યેક `(apiKeyId, dimensionKey)` માટે બે બકેટ:

- `curr`: વર્તમાન બકેટ (`floor(nowMs / windowMs)`)
- `prev`: અગાઉનું બકેટ (`curr - 1`)

અસરકારક રોલિંગ મૂલ્ય:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**ચોકસાઈ**: ~99% ચોક્કસ. બકેટ્સ વચ્ચેની સીમા પર ભૂલ વધુમાં વધુ વિન્ડોના કદના 1% જેટલી હોય છે
(2-બકેટના અંદાજમાં આ સ્વાભાવિક છે).

### સમકાલીનતા

SQLite ડ્રાઇવર: પ્રત્યેક `(apiKeyId | dimensionKey)` કી માટેનો ઇન-મેમરી mutex
read-modify-write રેસને અટકાવે છે. પેટર્ન `src/sse/services/auth.ts` ના anti-thundering-herd જેવું છે.

Redis ડ્રાઇવર: ઍટોમિક ઇન્ક્રિમેન્ટ માટે Lua EVAL સ્ક્રિપ્ટ — એક જ Redis કમાન્ડ તરીકે ચાલે છે.

## ડ્રાઇવર્સ

### SQLite (ડિફૉલ્ટ, 0-ઇન્સ્ટૉલ)

- ટેબલ: `quota_consumption` (માઇગ્રેશન `073_quota_pools.sql` / `074_quota_consumption.sql` જુઓ).
- સિંગલ-ઇન્સ્ટન્સ ડિપ્લોયમેન્ટ માટે શ્રેષ્ઠ.
- તમામ પર્સિસ્ટન્સ હાલના OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`)માં રહે છે.

### Redis (વૈકલ્પિક, મલ્ટિ-ઇન્સ્ટન્સ)

- `ioredis` npm પૅકેજ જરૂરી છે.
- કાઉન્ટર્સ Redisમાં સંગ્રહિત થાય છે; મેટાડેટા (પૂલ્સ/ફાળવણીઓ) હજુ પણ SQLiteમાં રહે છે.
- જ્યાં કાઉન્ટર્સ શેર કરવા આવશ્યક હોય તેવા મલ્ટિ-રેપ્લિકા ડિપ્લોયમેન્ટ માટે શ્રેષ્ઠ.

### ડ્રાઇવર્સ બદલવા

સેટિંગ્સ UI (`/dashboard/settings` → ક્વોટા સ્ટોર) દ્વારા, અથવા env vars દ્વારા:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

DB સેટિંગને env કરતાં પ્રાથમિકતા મળે છે. જો `driver=redis` હોય પરંતુ URL ગેરહાજર હોય અથવા
`ioredis` ઇન્સ્ટૉલ ન હોય, તો ફેક્ટરી SQLite પર પાછી ફરે છે અને ચેતવણી લૉગ કરે છે.

ડ્રાઇવર પસંદગીનો ક્રમ:

1. DB સેટિંગ `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. ડિફૉલ્ટ: `sqlite`

## બહુ-પરિમાણ

પૂલમાં બહુવિધ પરિમાણો હોઈ શકે છે. દરેક પરિમાણ સ્વતંત્ર છે:

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // global pool ceiling for this dimension
}
```

**ઉદાહરણ: Codex યોજના** (5h% + સાપ્તાહિક%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

વિનંતીને મંજૂરી આપવા માટેના તમામ પરિમાણોને સંતોષવા આવશ્યક છે.

### ટકાના પરિમાણો: પ્રતિ-કી એટ્રિબ્યુશન

ટકાવારી યોજના એકાઉન્ટ અને પ્લાન વિન્ડો દીઠ એક વપરાશનો આંકડો જણાવે છે. પ્રદાતા API કી દીઠ કોઈ કાઉન્ટર આપતા નથી.

તે આકૃતિને કી વચ્ચે વિભાજિત કરવા માટે, દરેક પૂલ એકાઉન્ટ અને પ્લાન વિન્ડો દીઠ એટ્રિબ્યુશન બુક રાખે છે. `src/lib/quota/percentLedger.ts` પુસ્તકના નિયમો ધરાવે છે. `src/lib/quota/percentAttribution.ts` પુસ્તકને સંખ્યાઓમાં ફેરવે છે જે અમલીકરણ વાપરે છે. પરિણામ એ દરેક કી રૂટના ટોકન્સથી બનેલ અંદાજ છે.

#### વાંચન જે પુસ્તકને ખસેડે છે

વિનંતી કરેલ પ્લાન વિન્ડો માટે પુસ્તક ફક્ત પ્રદાતાના પોતાના આકૃતિ પર જ ફરે છે. આ જોડાણો એકની જાણ કરે છે:

| પ્રદાતા                      | પ્લાન વિન્ડોઝ  |
| ---------------------------- | -------------- |
| Claude, OAuth કનેક્શન દ્વારા | `5h`, `weekly` |
| Codex                        | `5h`, `weekly` |

આને વાંચન તરીકે ગણવામાં આવતા નથી:

- પ્રતિભાવ પ્રદાતા ક્લાયંટ વાસી તરીકે ચિહ્નિત કરે છે
- એક Claude વિન્ડો જેની ટકાવારી પ્રદાતાએ જાણ કરી નથી
- અન્ય વિન્ડોની આકૃતિ, અથવા સમગ્ર વિન્ડો પર સૌથી ખરાબ કેસ
- દર-મર્યાદા હેડર ફોલબેક
- નિષ્ફળ વાંચન

API કી સાથે Claude સહિત અન્ય પ્રદાતાઓ પાસે કોઈ પુસ્તક નથી. આ ફેરફાર પહેલાની જેમ દરેક કીને તેમના ટકાના પરિમાણો પર 0 ચાર્જ કરવામાં આવે છે.

એક વાંચન સંતૃપ્તિ સિગ્નલની 30-સેકન્ડ કેશ શેર કરે છે. Claude રીડિંગની તારીખ જ્યારે પ્રતિભાવ હેડરમાં જોવામાં આવી હતી અથવા ઉપયોગના અંતિમ બિંદુ પરથી વાંચવામાં આવી હતી, જ્યારે તે સમય જાણીતો છે. અન્ય રીડિંગ્સ કેશ એન્ટ્રી ક્યારે બનાવવામાં આવી હતી તેની તારીખ છે.

#### પુસ્તક શું રાખે છે

દરેક રેકોર્ડ કરેલી વિનંતી તેના ટોકન્સ, એકવાર, પૂલ દીઠ કાઉન્ટર, એકાઉન્ટ અને કીમાં ઉમેરે છે. એક કાઉન્ટર માત્ર વધે છે. પુસ્તક ત્રણ વસ્તુઓ રાખે છે:

- આધારરેખા: જ્યારે પુસ્તક ખોલ્યું અથવા બારી છેલ્લે ફેરવાઈ ત્યારે આકૃતિ
- છેલ્લી લાગુ આકૃતિ
- કી દીઠ, તે જ ક્ષણે તેનું ટોકન કાઉન્ટર, તેનું ચિહ્ન કહેવાય છે

જ્યારે અમલીકરણ અથવા ઉપયોગ માર્ગ એટ્રિબ્યુશનની ગણતરી કરે છે ત્યારે પુસ્તક અપડેટ થાય છે. રાઇટ્સ પુનરાવર્તન નંબર પર સરખામણી-અને-સેટ કરવામાં આવે છે. એક લેખક કે જે ગુમાવે છે તે તાજા વાંચન પર એકવાર ફરી પ્રયાસ કરે છે.

#### કીના ભાગની ગણતરી કેવી રીતે કરવામાં આવે છે

જ્યારે પુસ્તક વાંચવામાં આવે ત્યારે દરેક કીના ભાગની ગણતરી કરવામાં આવે છે. આકૃતિની વૃદ્ધિ કારણ કે બેઝલાઈન ચાવીઓ વચ્ચે ટોકન્સના પ્રમાણમાં વિભાજિત કરવામાં આવે છે જે દરેકને તેના ચિહ્નથી રૂટ કરવામાં આવે છે.

Together, તે ટોકન્સ `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` ટોકન્સ (ડિફોલ્ટ 1,000) દીઠ આકૃતિના મહત્તમ એક બિંદુએ સમજાવે છે. તેઓ જે વૃદ્ધિ સમજાવતા નથી તે બાહ્ય છે. આધારરેખા બાહ્ય પણ છે.

ઉદાહરણ તરીકે, પુસ્તક 0 પર ખુલે છે. કી A પછી રૂટ 900,000 ટોકન્સ અને કી B રૂટ 100,000. 60 ના આંકડા પર, A નો ભાગ 54 પોઈન્ટ છે અને B નો ભાગ 6 છે.

તેના કીના ચિહ્નની નીચેનું કાઉન્ટર પુનઃપ્રારંભ થયું છે અને સંપૂર્ણ ગણાય છે. ચિહ્ન વિનાની ચાવી, જેમ કે એક કી જે વિન્ડોની મધ્યમાં પૂલ સાથે જોડાય છે, તેના તમામ ટોકન્સની ગણતરી કરે છે. ટોકન્સ પાછળ રહેતી આકૃતિ એક ભૂલનું કારણ બને છે જે આગળના વાંચન વખતે દૂર થઈ જાય છે. તે જમા થતું નથી.

`QUOTA_PERCENT_MIN_TOKENS_PER_POINT` દરેક એટ્રિબ્યુશન પર વાંચવામાં આવે છે. એક મૂલ્ય કે જે ઓછામાં ઓછી 1 ની મર્યાદિત સંખ્યા નથી તે 1,000 પર આવે છે.

#### વાંચન પુસ્તક કેવી રીતે બદલી નાખે છે

પ્રથમ મેચિંગ નિયમ લાગુ પડે છે:

1. **હજી સુધી કોઈ પુસ્તક નથી:** વાંચન પુસ્તક ખોલે છે. તેની આકૃતિ આધારરેખા છે અને દરેક કાઉન્ટર ચિહ્નિત થયેલ છે.
2. **જૂનું વાંચન:** છેલ્લી લાગુ પડેલી પહેલાંની તારીખનું વાંચન અવગણવામાં આવે છે. તેથી રીસેટ સમય સંગ્રહિત કરતાં 30 મિનિટ વહેલો છે.
3. **નવી પ્રદાતા વિન્ડો:** સંગ્રહિત વ્યક્તિ પુસ્તક ફેરવે તેના કરતાં 30 મિનિટ કરતાં વધુ સમય પછી રીસેટ સમય. આકૃતિ આધારરેખા બની જાય છે અને દરેક કાઉન્ટરને ફરીથી ચિહ્નિત કરવામાં આવે છે. કાઉન્ટર વગરની ચાવીઓ પુસ્તક છોડી દે છે.
4. **સમાપ્ત થયેલ વિન્ડો:** સંગ્રહિત રીસેટ સમય કે જે વાંચનના ડેટા સમય પછીનો નથી એટલે કે વિન્ડો સમાપ્ત થઈ ગઈ છે. વાંચન પુસ્તકને ફેરવે છે, તેની આકૃતિ ગમે તે હોય.
5. **ઉચ્ચ આકૃતિ:** માત્ર છેલ્લો આંકડો ખસે છે. આધારરેખા અને ગુણ રહે છે.
6. **સમાન આકૃતિ:** આકૃતિ, આધારરેખા અને ગુણ રહે છે. પુસ્તકનો અભાવ માત્ર રીસેટ સમય લખવામાં આવે છે.
7. **નીચલી આકૃતિ:** નીચી આકૃતિ ક્યારેય લાગુ પડતી નથી. જ્યારે ત્રણ વસ્તુઓ પકડી રાખે છે ત્યારે જ તે પુસ્તક ફેરવે છે. તે છેલ્લી લાગુ વાંચન કરતાં ઓછામાં ઓછી બે મિનિટ નવી છે. કંઈ કહે છે કે બારી એક જ ખુલ્લી છે. તે એક કરતાં વધુ પોઈન્ટ નીચું છે.

જ્યારે ત્રણ વસ્તુઓ પકડી રાખે છે ત્યારે વિન્ડો એક જ ખુલ્લી તરીકે ગણવામાં આવે છે. બંને રીસેટ સમય જાણીતા છે. તેઓ એકબીજાથી 30 મિનિટની અંદર છે. સંગ્રહિત એક હજુ વાંચન આગળ છે. તે વિંડોની અંદરની નીચેની આકૃતિ કંઈપણ બદલતી નથી.

રીસેટ સમય ફક્ત ત્યારે જ સંગ્રહિત થાય છે જ્યારે તે વાંચનના ડેટા સમય કરતા આગળ હોય જે તેને વહન કરે છે. ઉચ્ચ આકૃતિ તેના વાંચનના રીસેટ સમયને સંગ્રહિત કરે છે જ્યારે તે ઉપયોગ કરી શકાય તેવું હોય છે, અને અન્યથા સંગ્રહિત રાખે છે. એક સમાન આંકડો તેના વાંચનના રીસેટ સમયને ત્યારે જ રેકોર્ડ કરે છે જ્યારે પુસ્તકમાં કોઈ ન હોય. તેનાથી બીજું કંઈ બદલાતું નથી. એક નીચો આંકડો જે પુસ્તકને ચાલુ કરતું નથી તે કોઈ રીસેટ સમય નથી.

#### જ્યારે પુસ્તકનો ઉપયોગ થાય છે

વાંચન પછી, પુસ્તકનો ઉપયોગ કરવામાં આવે છે સિવાય કે તેનો સંગ્રહિત રીસેટ સમય વર્તમાન સમય પછીનો ન હોય. તે કિસ્સો ત્યારે ઉદ્ભવે છે જ્યારે રીસેટ પહેલા લેવામાં આવેલ રીડિંગ, જેમ કે કેશમાંથી આપવામાં આવેલ રીડિંગ, તેના પછી જ જોવામાં આવે છે.

ઉપયોગી વાંચન વિના, સંગ્રહિત પુસ્તકનો ઉપયોગ ત્યારે જ થાય છે જ્યારે તે હજુ પણ વર્તમાન વિન્ડોની પુસ્તક હોઈ શકે. તે બે કિસ્સાઓમાં ધરાવે છે:

- તેનો રીસેટ સમય જાણીતો છે અને હજુ આગળ છે
- તેનો કોઈ રીસેટ સમય નથી, અને છેલ્લું વાંચન જેણે તેને બદલ્યું છે તે વધુમાં વધુ 15 મિનિટ જૂનું છે

નહિંતર, જ્યારે કોઈ પુસ્તક ન હોય ત્યારે કંઈપણ આભારી નથી. જે પુસ્તકનો સંગ્રહિત રીસેટ સમય પસાર થઈ ગયો હોય તેના પર ક્યારેય શુલ્ક લેવામાં આવતું નથી.

#### અમલીકરણ

ટકાના પરિમાણ પર કીનો વપરાશ એ તેનો આભારી ભાગ વત્તા બાહ્ય ભાગનો હિસ્સો છે. બાહ્ય ભાગ પ્રથમ ક્ષમતાનો ઉપયોગ કરે છે જેમાં કોઈ ફાળવણીના દાવાઓ નથી (100 ઓછા વજનના સરવાળા). વજન દ્વારા કીઓ વચ્ચે ફક્ત વધારાની વહેંચણી કરવામાં આવે છે.

તે વપરાશની સરખામણી અન્ય કોઈપણ પરિમાણની જેમ કીના વાજબી શેર સાથે કરવામાં આવે છે. જ્યારે સંતૃપ્તિ સિગ્નલ `QUOTA_SATURATION_THRESHOLD` (ડિફૉલ્ટ 0.5) સુધી પહોંચે છે ત્યારે સખત મોડ હજી પણ શરૂ થાય છે. દરેક સંખ્યાને અસરકારક મર્યાદા દ્વારા માપવામાં આવે છે: પ્રતિ-એકાઉન્ટ મર્યાદા પૂલમાં એકાઉન્ટ્સની સંખ્યાને ગણી વધારે છે.

`capUnit: "percent"` સાથેની સંપૂર્ણ કેપ ફક્ત કીને આભારી ભાગની ગણતરી કરે છે, તે જ રીતે માપવામાં આવે છે. 100 અને k એકાઉન્ટ દીઠ એકાઉન્ટની મર્યાદા લો. જ્યારે સેવા આપતા ખાતાની આકૃતિનો કીનો ભાગ N/k પોઈન્ટ સુધી પહોંચે છે ત્યારે N ની કેપ સુધી પહોંચી જાય છે. દરેક એકાઉન્ટ તેની પોતાની ચોપડી સામે તપાસવામાં આવે છે. ઉદાહરણ તરીકે, બે ખાતા સાથે, એક ખાતાના આકૃતિના 5 પોઈન્ટ પર 10 ની કેપ પહોંચી છે.

જ્યારે સ્ટોર વાંચી શકાતો નથી, ત્યારે કંઈપણ આભારી નથી અને દરેક કી તે પરિમાણ પર 0 ચાર્જ કરવામાં આવે છે. જ્યારે કોઈ પુસ્તક લખવામાં નિષ્ફળ જાય છે, ત્યારે તે એટ્રિબ્યુશન પુસ્તકનો ઉપયોગ કરે છે જેમ તે વાંચવામાં આવ્યું હતું. એક નિષ્ફળ ટોકન લખવાથી વિનંતીના ટોકન પુસ્તકમાંથી બહાર નીકળી જાય છે. આમાંની કોઈપણ નિષ્ફળતા વિનંતીને અવરોધિત કરતી નથી.

`consent` પૂલમાં, ધિરાણ સૂત્ર ઉપર વર્ણવ્યા મુજબ ટકાના પરિમાણ પર દરેક કીના વપરાશનો ઉપયોગ કરે છે. જ્યારે બીજી કી ઉધાર આપે છે, ત્યારે પુસ્તક એકવાર વાંચવામાં આવે છે અને દરેક કીને આભારી છે. ઉપયોગી પુસ્તક વિના દરેક કી 0 ચાર્જ કરવામાં આવે છે. વજનવાળી કી પછી પસાર થાય છે, અને 0 વજનવાળી ચાવી ત્યારે જ પસાર થાય છે જ્યારે બીજી કી ઉધાર આપે છે.

#### ઉપયોગ માર્ગ

`GET /api/quota/pools/{id}/usage` સમાન ફંક્શન દ્વારા સમાન સંખ્યાઓની જાણ કરે છે. એક ટકા પરિમાણ `accounts` માં પૂલ કનેક્શન દીઠ એક એન્ટ્રી ધરાવે છે. તેના ટોપ-લેવલ `consumedTotal` અને `perKey` પ્રથમ એન્ટ્રીને પ્રતિબિંબિત કરે છે.

રૂટ વર્તમાન વાંચનને પણ લાગુ કરે છે, જેથી તે વિનંતી પ્રમાણે પુસ્તકને આગળ વધારી શકે. `internal + external` `consumedTotal` થી અલગ હોઈ શકે છે જ્યારે કોઈ ઉપયોગી વાંચન ન હોય, અથવા જ્યારે નીચું આંકડો લાગુ ન હોય.

#### સંગ્રહ અને રીટેન્શન

બંને ક્વોટા સ્ટોર પુસ્તક રાખે છે. SQLite પર, ઓટોમેટિક ડેટાબેઝ ક્લિનઅપ, જ્યારે સક્ષમ હોય, ત્યારે 60 દિવસ સુધી અપડેટ ન થયેલી પંક્તિઓ દૂર કરે છે. Redis પર, પૂલ કનેક્શનના પુસ્તકો અને કાઉન્ટર્સ એક કી શેર કરે છે. તે તેના છેલ્લા ટોકન લખવા અથવા પુસ્તકમાં ફેરફાર કર્યાના 60 દિવસ પછી સમાપ્ત થાય છે. એક પુસ્તક જે બદલાતું નથી તે ફરીથી લખવામાં આવતું નથી, તેથી કટઓફ સૌથી લાંબી યોજના વિંડોની ઉપર સેટ કરવામાં આવે છે. મેન્યુઅલ વપરાશ-ઇતિહાસ રીસેટ પણ SQLite પરના પુસ્તકોને સાફ કરે છે (મર્યાદાઓ જુઓ).

#### મર્યાદાઓ

- ત્યારથી રાઉટ કરાયેલ દરેક કી ટોકન્સ દ્વારા આધારરેખાને વિભાજિત કરવામાં આવી હોવાથી એકાઉન્ટ આકૃતિની તમામ વૃદ્ધિ. જ્યારે તે વૃદ્ધિ થઈ ત્યારે કોઈ વાંધો નથી.
- તેથી OmniRoute બહાર કરવામાં આવેલ ઉપયોગનો ચાર્જ તેમના ટોકન્સ દ્વારા આપવામાં આવે છે તેટલી કી પર લેવામાં આવે છે. તેમાં વિન્ડોની કીની પ્રથમ વિનંતી પહેલાં કરવામાં આવેલ ઉપયોગનો સમાવેશ થાય છે, જ્યારે પુસ્તક પહેલેથી જ ખુલ્લું હતું.
- ઉદાહરણ તરીકે, બહારનો ઉપયોગ એકાઉન્ટ 60 પોઈન્ટ વધારે છે જ્યારે કોઈ કી રૂટ નથી. પછી એક કી 30,000 ટોકન્સને રૂટ કરે છે અને આંકડો 60.6 સુધી પહોંચે છે.
- જો તે ઉપયોગ પહેલાં પુસ્તક ખુલ્લું હતું, તો કીનો ભાગ 30 પોઈન્ટ છે. તે બાહ્ય વપરાશના 7.65 પણ વહન કરે છે, જેમાં વજન 25 ની ચાર કી છે.
- જો તે ઉપયોગ પછી પુસ્તક ખોલવામાં આવે, તો 60 પોઈન્ટ બેઝલાઈન છે. કીનો ભાગ 0.6 પોઈન્ટ છે, અને તે 15 બાહ્ય વપરાશ ધરાવે છે.
- વિનંતી અથવા ઉપયોગ માર્ગની મુલાકાત પુસ્તક ખોલે છે. તેથી આવા ઉપયોગને આધારરેખા તરીકે ગણવામાં આવે છે કે કેમ તે પુસ્તક ક્યારે ખોલવામાં આવ્યું તેના પર આધાર રાખે છે.
- ડિફોલ્ટ ફ્લોર સાથે, એક કી કે જે 60,000 ટોકન્સને રૂટ કરે છે જ્યારે બહારનો ઉપયોગ એકાઉન્ટને 60 પોઈન્ટ વધારે છે તે તમામ 60 તેના પોતાના ભાગ તરીકે મેળવે છે.
- 50,000 પર ફ્લોર સાથે, તેનો પોતાનો ભાગ 1.2 પોઈન્ટ છે. અન્ય 58.8 બાહ્ય છે અને કોઈપણ બાહ્ય ઉપયોગની જેમ વજન દ્વારા ચાર્જ કરવામાં આવે છે.
- `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` તમારી યોજના પર એક પોઈન્ટની કિંમતની નજીક સેટ કરો. બહારના ઉપયોગમાં પૂલની બહારની કીમાંથી સમાન ખાતા પરનો ટ્રાફિક શામેલ છે.
- દરેક મોડમાં ટકાની મર્યાદા લાગુ પડે છે. જ્યારે ખાતું સંતૃપ્તિ થ્રેશોલ્ડથી ઘણું નીચે હોય ત્યારે કેપ કરેલી કીને નકારી શકાય છે.
- વિન્ડોમાં પહેલા બહારના ઉપયોગ માટે 10 અને 12 પોઈન્ટની કેપ લો. એક કી કે જે 20,000 ટોકન્સને રૂટ કરે છે તે પછી 12.4% ના એકાઉન્ટ આંકડા પર નકારવામાં આવે છે.
- વિભાજન એ ટોકન વોલ્યુમ દ્વારા એક અંદાજ છે. વિનંતીને તેના પ્રોમ્પ્ટ ટોકન્સ વત્તા તેના પૂર્ણતા ટોકન્સ તરીકે ગણવામાં આવે છે. કેશ ડિસ્કાઉન્ટ અને મોડલની કિંમતો તે ગણતરીમાં ફેરફાર કરતા નથી.
- એક વિનંતી કે જે સ્ટેટસ 200 રેકોર્ડ સાથે સમાપ્ત થતી નથી કોઈ ટોકન્સ નથી. ઉદાહરણો ક્લાયંટ ડિસ્કનેક્ટ કરે છે તે સ્ટ્રીમ અને વપરાશ પછી અપસ્ટ્રીમ ભૂલ છે.
- આવી વિનંતિના કારણે થયેલ વપરાશનો ચાર્જ ટોકન્સ રેકોર્ડ કરતી કી પર વસૂલવામાં આવે છે, જે તેમના ટોકન્સની મંજૂરી આપે છે. બાકીનું બાહ્ય છે. એ પાછળ ખસતો નથી. એક પ્રતિસાદ કે જે કોઈ ટોકન વપરાશની જાણ કરતું નથી તે પણ કોઈ ટોકન નથી.
- ચાલુ વિનંતીનો ઉપયોગ સમગ્ર વિનંતી માટે અન્ય સક્રિય કીના ભાગમાં દેખાઈ શકે છે. જ્યારે વિનંતી સ્ટેટસ 200 સાથે સમાપ્ત થાય ત્યારે જ તે પાછા ફરે છે.
- જ્યારે કોઈ પુસ્તક ખુલે છે ત્યારે એકાઉન્ટ પર પહેલેથી જ ઉપયોગ બાહ્ય તરીકે ગણવામાં આવે છે. આ અપગ્રેડ, નવો પૂલ અને નવું એકાઉન્ટ આવરી લે છે. નવી વિન્ડોમાં ઉપયોગ તેના પ્રથમ વાંચન પહેલાં બાહ્ય તરીકે પણ ગણવામાં આવે છે.
- દરેક કી તે વપરાશના તેના વજનના હિસ્સા સાથે શરૂ થાય છે, ક્ષમતા પછી કોઈ ફાળવણીનો દાવો કરવામાં આવતો નથી. 85% પર એક એકાઉન્ટ અને 20 વજનની પાંચ ચાવીઓ સાથે, દરેક તેની 20 માંથી 17 ઉપયોગથી શરૂ થાય છે.
- અનેક એકાઉન્ટ્સ ધરાવતા પૂલમાં, સર્વિંગ એકાઉન્ટનો આંકડો સરવાળો બજેટ પર લાગુ થાય છે. આ પુસ્તક દ્વારા અપરિવર્તિત છે.
- પ્રદાતા ખુલ્લી હોવાનો અહેવાલ આપે છે તે વિન્ડોની અંદરનો નીચો આંકડો લાગુ થયો નથી. રીસેટ સમય જે 30 મિનિટથી વધુ પાછળ જાય છે તેને જૂના વાંચન તરીકે ગણવામાં આવે છે.
- બંને કિસ્સાઓમાં સંગ્રહિત રીસેટ સમય પસાર ન થાય ત્યાં સુધી પુસ્તક તેની સ્થિતિ જાળવી રાખે છે. તે પછી, જ્યાં સુધી વાંચન તેને ફેરવે નહીં ત્યાં સુધી પુસ્તકનો ચાર્જ લેવામાં આવતો નથી.
- ઉપાય એ મેન્યુઅલ ઉપયોગ-ઇતિહાસ રીસેટ (`POST /api/settings/purge-usage-history`) છે. તે SQLite ડેટાબેઝમાં એટ્રિબ્યુશન પુસ્તકો અને તેમના ટોકન કાઉન્ટર્સને સાફ કરે છે.
- `all` અવધિ દરેક પુસ્તક અને કાઉન્ટરને સાફ કરે છે. નાનો સમયગાળો પ્રથમ તેની અંદર લખાયેલ પુસ્તકોને સાફ કરે છે. તે પછી તેની અંદર લખેલા કાઉન્ટર્સને સાફ કરે છે, પરંતુ માત્ર એક પૂલ કનેક્શન માટે કે જેની પાસે કોઈ પુસ્તક બાકી નથી. સાચવેલ પુસ્તક હજુ પણ દરેક કીને તેના કાઉન્ટર સામે ચિહ્નિત કરે છે.
- એક પુસ્તક કે જેની આકૃતિ ખસેડવામાં આવી નથી તે ફરીથી લખવામાં આવતી નથી, તેથી ટૂંકા સમયગાળો પણ વર્તમાન વિંડોના પુસ્તકને સાફ કરી શકે છે. પછીનું વાંચન વર્તમાન આંકડા પર એક નવું પુસ્તક ખોલે છે.
- રીસેટ Redis ક્વોટા સ્ટોરને સ્પર્શતું નથી. ત્યાં એક પુસ્તક તેની વિન્ડો સાથે સમાપ્ત થાય છે, અથવા તેના છેલ્લા લખાણના 60 દિવસ પછી સમાપ્ત થાય છે.
- જ્યારે પ્રદાતા કોઈ રીસેટ સમય મોકલતા નથી, ત્યારે એક વિન્ડો જે રીસેટ કરે છે અને બે રીડિંગ્સ વચ્ચે જૂની આકૃતિની ઉપર ફરી ભરે છે તે ઉચ્ચ આકૃતિ જેવી દેખાય છે. પુસ્તક જૂની આધારરેખા અને ગુણ રાખે છે.
- રીડિંગ્સ સ્થાનિક ઘડિયાળ દ્વારા તારીખ છે. જ્યારે તે પ્રદાતાની આગળ ચાલે છે, અથવા સ્રોત રીસેટ સમય થોડો વહેલો જણાવે છે, ત્યારે પુસ્તક તે તફાવતને વહેલા સુધી પહોંચી શકે છે.
- તે ટૂંકા ગાળામાં વૃદ્ધિને તેમાં રૂટ કરાયેલા ટોકન્સ દ્વારા વિભાજિત કરવામાં આવે છે. આગલી વિંડોનું પ્રથમ વાંચન તેને સુધારે છે. જ્યારે ફેરવેલ પુસ્તકમાં કોઈ રીસેટ સમય નથી, ત્યારે તે કરેક્શન માટે છેલ્લા લાગુ કરેલા વાંચન કરતાં ઓછામાં ઓછા બે મિનિટ નવા આંકડાની જરૂર છે.
- દાખલાઓ કે જે Redis સ્ટોરની તારીખ વાંચન તેમની પોતાની ઘડિયાળો સાથે શેર કરે છે, તેથી તે ઘડિયાળોને સુમેળમાં રાખો. એક દાખલાની રીડિંગ્સ કે જેની ઘડિયાળ પાછળ ચાલે છે તે જૂની દેખાય છે અને અવગણવામાં આવે છે.
- જ્યારે સંગ્રહિત રીસેટ સમય પછી કોઈ ઉપયોગી વાંચન ન આવે, ત્યારે પ્રતિ-કી ટકા શેર અને ટકા કેપ્સ જ્યાં સુધી રીડિંગ પરત ન આવે ત્યાં સુધી લાગુ કરવામાં આવતાં નથી. રીસેટ સમય વિના, આ પુસ્તક બદલાયેલ છેલ્લું વાંચન પછી 15 મિનિટ પછી શરૂ થાય છે.
- Redis સ્ટોર પર, 60 દિવસ માટે નિષ્ક્રિય પુસ્તક લેખકના ચેક અને તેના લખાણ વચ્ચે સમાપ્ત થઈ શકે છે. તે પછી 1 થી ઉપરના પુનરાવર્તન પર ફરીથી બનાવવામાં આવે છે, જે એક માન્ય સ્થિતિ છે.

## પાઇપલાઇન એકીકરણ

### PRE હૂક (`open-sse/handlers/chatCore.ts`)

ઓથ અને પોલિસી તપાસ પછી, અપસ્ટ્રીમ એક્ઝિક્યુટર પહેલાં ચાલે છે:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() per dimension
      → fairShare.decideFairShare()
      → if block → return 429 (buildErrorBody, Hard Rule #12)
      → if allow + deprioritize → set quotaSoftPenalty=true on candidate
  → executor.execute()
```

**ફેલ-ઓપન** : જો `enforceQuotaShare` ફેંકે છે, તો વિનંતીને `pino.warn` લોગ દ્વારા મંજૂરી આપવામાં આવે છે. આ ક્વોટા-એન્જિન બગને તમામ ટ્રાફિકને અવરોધિત કરવાથી અટકાવે છે.

**જ્યારે ક્ષમતા પાછી આવે છે.** કીના શેર પર અથવા પૂલની ટોચમર્યાદા પરનો ઇનકાર બેમાંથી એક વાક્ય સાથે સમાપ્ત થાય છે, બંને ઉધાર મોડમાં:

- `percent` વિન્ડો: `. The <window> window resets at <time>.` પ્રદાતા અહેવાલોને રીસેટ કરવાનો સમય છે.
- ગણતરીપાત્ર એકમ: `. Enough <window> usage is expected to clear by <time>.` સમય એ સ્લાઇડિંગ વિન્ડોમાંથી ઉપલા બાઉન્ડ છે, જો કી બીજું કંઈ મોકલતી નથી.

`<time>` એ UTC માં ISO 8601 ઇન્સ્ટન્ટ છે. ઇનકાર પછી `Retry-After` વહન કરે છે : તે ત્વરિત સુધી સમગ્ર સેકન્ડ, વત્તા એક. એક ક્લાયન્ટ કે જે લાંબા સમય સુધી રાહ જુએ છે તે ત્વરિત પછી વધુમાં વધુ એક સેકન્ડ પછી ફરી પ્રયાસ કરે છે. જ્યારે ઇન્સ્ટન્ટ જાણીતું નથી, ત્યારે ઇનકારમાં ન તો વાક્ય હોય છે કે ન તો હેડર. નિરપેક્ષ કેપ ઇનકાર બેમાંથી કોઈને વહન કરે છે. જાહેર કોડ `quota_share_blocked` રહે છે.

શેરનો ઇનકાર શેર કરેલ કનેક્શનને સ્પર્શતો નથી. તે કોઈ કૂલડાઉન સેટ કરે છે, કોઈ મોડેલ લૉક નથી અને કોઈ પ્રદાતા બ્રેકર નિષ્ફળતા નથી, અને પૂલની અન્ય ચાવીઓ પીરસવામાં આવતી રહે છે. જ્યારે કોમ્બોનું દરેક લક્ષ્ય તેના શેર માટેની ચાવીનો ઇનકાર કરે છે, ત્યારે કોમ્બો રાહ જોયા વિના 429 નો જવાબ આપે છે. તેનો જવાબ `Retry-After` તરીકે સંકેત ધરાવે છે. એમ્બેડિંગ્સ પાથ તેના ઇનકારને સમાન વાક્ય સાથે સમાપ્ત કરે છે અને કોઈ `Retry-After` મોકલતો નથી.

### POST હૂક (રેકોર્ડ વપરાશ)

સફળ પ્રતિસાદ પછી:

```
executor returns success
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() per dimension
      → fail-open: errors logged as pino.warn, never propagated to client
```

**ડ્રિફ્ટ નોંધ** : જો `consume` પ્રતિસાદ પછી નિષ્ફળ જાય છે, તો રોલિંગ કાઉન્ટર ઓછા ગણાય છે. પ્રદાતા તરફથી સંતૃપ્તિ સંકેત (દા.ત. `anthropic-ratelimit-unified-5h-utilization`) આગામી વિનંતી પર વૈશ્વિક અંદાજને સુધારે છે.

### કોમ્બો સોફ્ટ પેનલ્ટી (`open-sse/services/combo.ts`)

જ્યારે `decision.deprioritize === true`:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // default 0.7
}
```

અન્ય તમામ સ્કોરિંગ પરિબળો પછી દંડ લાગુ કરવામાં આવે છે. તે હાર્ડ-બ્લોક કર્યા વિના સંતૃપ્ત કી પસંદ કરવાની ઓટો-કોમ્બો સંભાવનાને ઘટાડે છે.

## સ્વ-સેવા ક્વોટા API (ઓપ્ટ-ઇન)

`GET /api/v1/me/quota/{provider}` ( `/v1/me/quota/{provider}` પર પણ સેવા આપવામાં આવે છે) API કી ધારકને તેમની પોતાની કી વડે વાંચવા દે છે, કેટલું વહેંચાયેલ સબ્સ્ક્રિપ્શન તેમનું છે અને તેમને શું અવરોધિત કરી રહ્યું છે. રૂટ `src/server/selfService/quotaHandler.ts` પર પાતળો શેલ છે; દૃશ્ય `src/lib/quota/selfView.ts` દ્વારા બનાવવામાં આવ્યું છે અને તેનો પ્રતિભાવ કરાર `src/shared/schemas/selfQuota.ts` ( `docs/openapi.yaml` માં`SelfQuotaView` ) છે.

### સક્ષમ અને પ્રમાણીકરણ

- ફિચર ફ્લેગ `QUOTA_SELF_PANEL`, ડિફોલ્ટ `false`. જ્યારે તે બંધ હોય, ત્યારે રૂટ પર પહોંચતી વિનંતીને 404 મળે છે. `REQUIRE_API_KEY=true` સાથે, ક્લાયંટ API પોલિસી રૂટ ચાલે તે પહેલાં 401 સાથે ખૂટતી અથવા અમાન્ય કીનો ઇનકાર કરે છે, ભલે ગમે તે ધ્વજ હોય. કોઈ કી વગરની વિનંતી પરંતુ સાઇન-ઇન થયેલ ડેશબોર્ડ સત્ર તે નીતિને પસાર કરે છે અને રૂટનો પોતાનો જવાબ મેળવે છે. ધ્વજ દરેક અન્ય ધ્વજની જેમ ઉકેલે છે (ડેશબોર્ડ અથવા REST ઓવરરાઇડ, પછી સમાન નામનું પર્યાવરણ ચલ); [`FEATURE_FLAGS.md`](../reference/FEATURE_FLAGS.md) જુઓ.
- દરેક પૂલનું ડિસ્પ્લે નામ અને દરેક શેડ્યૂલનું લેબલ પૂલના કી ધારકોને એડમિનિસ્ટ્રેટરે લખ્યા પ્રમાણે બરાબર પરત કરવામાં આવે છે. ધ્વજને ચાલુ કરતા પહેલા, તપાસો કે તે તે કી ધારકો દ્વારા વાંચવા માટે યોગ્ય છે.
- કી ફક્ત હેડરોમાંથી વાંચવામાં આવે છે: `Authorization: Bearer <key>` અથવા `x-api-key: <key>`. જ્યારે બંને મોકલવામાં આવે છે, ત્યારે પ્રથમ જે માન્ય કરે છે તેનો ઉપયોગ કરવામાં આવે છે. ક્વેરી સ્ટ્રીંગમાંની કી અથવા કૂકીને અવગણવામાં આવે છે. સર્વરની પર્યાવરણ કી નકારી છે (401).
- કીને `self:usage` સ્કોપની જરૂર છે (તેના વિના 403).
- પ્રદાતા સેગમેન્ટને સુવ્યવસ્થિત, લોઅર-કેસ અને `^[a-z0-9][a-z0-9._-]{0,63}$` (400 અન્યથા) ની સામે તપાસવામાં આવે છે, પછી પ્રદાતા રજિસ્ટ્રી દ્વારા ઉકેલવામાં આવે છે, તેથી `cc` જેવા ઉપનામ `claude` પુલને વાંચે છે. `claude` અને `anthropic` સમાન પૂલ વાંચે છે.

### દરેક દૃશ્યતા શું બતાવે છે

| દૃશ્યતા       | જરૂરી છે                                                                         | ક્ષેત્રો                                                                                                                                                                                                                                          |
| ------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| પોતાનો હિસ્સો | `self:usage`                                                                     | `pools[]` (સંદર્ભ, નામ, પ્રદાતા, નીતિ, વજન, કેપ), `dimensions[].yourShare`, `yourShare` `accounts[]` `attributed` અને `external` વિના `percent` વિન્ડો પર), `blocks`, `availableModels`, `expiresAt`, `apiBaseUrl`                                |
| એકાઉન્ટ સ્તર  | `self:usage` + `self:account-quota`, અને કીના `sharedQuotaProviders` માં પ્રદાતા | `dimensions[].total`, `accounts[].dimensions[].account` અને `accounts[].modelWindows`, `attributed` અને `external` `percent` વિન્ડોની `yourShare` પર અને `members` ને સભ્ય વપરાશ ચાલુ ધરાવતા પૂલ પર ઉમેરે છે ( [સભ્યનો ઉપયોગ](#member-usage) જુઓ) |

- `sharedQuotaProviders` એ પ્રતિ-કી સેટિંગ છે (`PUT /api/keys/[id]/self-service`): `null`, ડિફોલ્ટ, એટલે દરેક પ્રદાતા સુધી કી પહોંચે છે; `[]` અર્થ કોઈ નથી. દરેક પૂલના `accountVisible` કહે છે કે તેના પર કઈ દૃશ્યતા લાગુ થઈ છે.
- એકાઉન્ટ બાર અને મોડલ વિન્ડો માત્ર એવા એકાઉન્ટ્સ માટે જ બતાવવામાં આવે છે કે જેના કનેક્શન કી ઉપયોગ કરી શકે છે. જ્યારે કી પાસે માન્ય જોડાણોની સૂચિ હોય છે, ત્યારે તેની બહારનું ખાતું તેની `Account N` એન્ટ્રી `account` અથવા `modelWindows` વગર રાખે છે. ખાલી સૂચિનો અર્થ છે કોઈ પ્રતિબંધ નથી, જેમ કે `/v1/me/status` માટે. પૂલ કુલ (`dimensions[].total`) તે સૂચિ પર આધારિત નથી.
- એકલા `self:usage` સાથે બતાવેલ બે આંકડા અન્ય કીના ઉપયોગથી આવે છે. શેડ્યૂલ બજેટનો `exhausted` તે શેડ્યૂલ હેઠળની દરેક કીના વપરાશને પ્રતિબિંબિત કરે છે. એક પૂલમાં જેનું વજન શૂન્ય છે, કીનું `weight` `100 / number of members` છે. અમલીકરણ કી પર લાગુ થાય છે તે બંને છે.
- પૂલને ફક્ત `ref` દ્વારા ઓળખવામાં આવે છે, જે કોલિંગ કી સાથે બંધાયેલ અપારદર્શક મૂલ્ય છે. તેનું ડિસ્પ્લે નેમ (`name`) એડમિનિસ્ટ્રેટરે લખ્યું છે તેમ શામેલ છે. `ref` એ સર્વરની API-કી સિક્રેટ (`API_KEY_SECRET`) સાથે કી અને પૂલમાંથી લેવામાં આવે છે. ગ્રાહકોએ તેને ચાલુ રાખવું જોઈએ નહીં: જો તે રહસ્ય ફેરવવામાં આવે તો તે બદલાય છે.
- એકાઉન્ટ્સ પૂલ ક્રમમાં `Account 1`, `Account 2`, … તરીકે સૂચિબદ્ધ છે. કોઈ પૂલ આઈડી, કનેક્શન આઈડી, એકાઉન્ટ ઈ-મેલ અથવા એકાઉન્ટ નામ પરત કરવામાં આવતું નથી, અને પ્રતિસાદ કોન્ટ્રાક્ટ સ્કીમા દ્વારા જાય છે, જે તેની બહારના કોઈપણ ફીલ્ડને છોડી દે છે.
- ગણતરીપાત્ર એકમો (`requests`, `tokens`, `usd`) ક્વોટા ગેટ દ્વારા લાગુ કરવામાં આવતી પૂલ બકેટ તરીકે નોંધવામાં આવે છે: `limit` = યોજના = × એકાઉન્ટ્સ પૂલમાં, `fairShare` = વજન / 100 × `limit` (સમાન વિભાજન જ્યારે દરેક કાઉન્ટર `consumed` ' ક્વોટ ક્વોટમાં પોતાનું વજન હોય છે), સ્ટોર, `remaining` = `fairShare` − `consumed`, 0 પર ફ્લોર્ડ.
- `blocks.schedules` કીના શેડ્યૂલ વિન્ડોઝની યાદી આપે છે (`open`/`closed`, `blackout` અથવા `outside-window`, `retryAfterSeconds`, અનામત માળ, અને વિન્ડોનું બજેટ ખર્ચવામાં આવ્યું છે કે કેમ); `blocks.modelCaps` વપરાશ સાથે તેના પ્રતિ-મોડલ કલાકદીઠ કેપ્સની યાદી આપે છે.
- પ્રદાતાના દરેક પૂલની બહારની ચાવી `pools: []` સાથે 200 મળે છે; `availableModels` ( `qtSd/` ids જે કી `/v1/models` માં જુએ છે), `expiresAt` અને `apiBaseUrl` હજુ પણ ભરાયેલા છે.
- `apiBaseUrl` એ `OMNIROUTE_PUBLIC_API_BASE_URL` છે , પછી `OMNIROUTE_PUBLIC_BASE_URL`, બાકી `null`. તે ક્યારેય વિનંતીનું પોતાનું મૂળ નથી.

| `unavailable` | કોઈ વાંચન નથી; નંબરો `null` છે, ક્યારેય `0`. `reason` શા માટે કહે છે.                                                                                                                                                                                                                                                                                                                   |

| `account_not_used_by_key`         | `percent` વિન્ડોની કીનો પોતાનો હિસ્સો: એકાઉન્ટનું કનેક્શન કીના માન્ય કનેક્શનની બહાર છે. તેનું પુસ્તક વાંચવામાં આવતું નથી.                       |

| `connection_lookup_failed`        | એકાઉન્ટનું કનેક્શન વાંચી શકાયું નથી.                                                                                                            |

### ધિરાણ સંમતિ

`PATCH /api/v1/me/quota/{provider}` એક પૂલ માટે કોલિંગ કીની પોતાની સંમતિ રેકોર્ડ કરે છે. તે `GET` ના ધ્વજ, હેડરો અને પ્રદાતા નિયમોનો ઉપયોગ કરે છે. `self:usage` સ્કોપ આ લખાણને અધિકૃત કરે છે, જો કે તેનું નામ ફક્ત વાંચવા માટે વાંચે છે.

```json
{
  "pool": "qpr_0123456789abcdef0123456789abcdef",
  "lendingPercent": 30,
  "lendingUntil": 1893456000000
}
```

- `pool` એ `ref` છે `GET` તે પૂલ માટે પરત કરે છે.
- `lendingPercent` એ 0 થી 100 સુધીનો પૂર્ણાંક છે. 0 નું મૂલ્ય સંમતિ અને તેની અંતિમ તારીખને સાફ કરે છે. `lendingPercent` 0 સાથેનું શરીર કોઈપણ સ્થિતિમાં સ્વીકારવામાં આવે છે.
- `lendingUntil` વૈકલ્પિક છે: યુગ મિલિસેકન્ડ્સ, અથવા કોઈ સમયમર્યાદા વિના `null`. તે ભવિષ્યમાં અને વધુમાં વધુ 8640000000000000 હોવું જોઈએ. 1000000000000 થી નીચેનું મૂલ્ય સેકન્ડ તરીકે વાંચે છે અને તેને નકારવામાં આવે છે.
- અન્ય કોઈપણ ક્ષેત્રનો ઇનકાર કરવામાં આવે છે. 4096 બાઇટ્સથી વધુ લાંબી બોડી નકારવામાં આવી છે. વાંચન તે કદ પર અટકી જાય છે, તેથી લાંબા શરીરને ક્યારેય આખું પકડી શકાતું નથી.

ચેક આ કોષ્ટકના ક્રમમાં ચાલે છે. દરેક ઇનકાર એક નિશ્ચિત સંદેશ સાથે પ્રમાણભૂત ભૂલ મુખ્ય ભાગનો ઉપયોગ કરે છે. આમાંના એક ચેકનો ઇનકાર કંઈ લખતો નથી.

| સ્થિતિ | સંદેશ                                                                                              | જ્યારે                                                       |
| ------ | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |

| 403    | `API key lacks the self:usage scope`                                                               | કીમાં `self:usage` અભાવ છે.                                  |
| 400    | `Invalid provider`                                                                                 | પ્રદાતા સેગમેન્ટ અમાન્ય છે.                                  |
| 429    | `Too many lending changes. Retry later.`                                                           | ચાવી તેની મર્યાદા વટાવી ગઈ. જવાબ `Retry-After` વહન કરે છે.   |
| 400    | `Body must be { pool, lendingPercent, lendingUntil }. lendingPercent is an integer from 0 to 100.` | શરીર JSON નથી, ખૂબ લાંબુ છે, અથવા સ્કીમા સાથે મેળ ખાતું નથી. |

| 400    | `lendingUntil must be in the future`                                                               | સમયમર્યાદા વિનંતી સમય પર અથવા તે પહેલાં છે.                  |

મર્યાદા દરેક કી માટે 60 સેકન્ડ દીઠ 20 વિનંતીઓ છે. દરેક વિનંતી કે જે પ્રદાતાના ચેક પાસ કરે છે તેની ગણતરી કરવામાં આવે છે, એક પણ પછીથી નકારવામાં આવે છે અથવા જે કંઈપણ બદલાતું નથી. કીની વિનંતી દર મર્યાદા સિવાય તેનું પોતાનું કાઉન્ટર છે.

એક વિનંતી જે સંગ્રહિત સંમતિમાં ફેરફાર કરે છે તે એક `quota.pool.lending.updated` ઓડિટ રેકોર્ડ લખે છે. તે કીને જૂના અને નવા મૂલ્યો સાથે નામ આપે છે. બે વાર મોકલેલ એ જ બોડી એકવાર લખે છે અને એકવાર ઓડિટ કરે છે. જવાબ સંપૂર્ણ `GET` વ્યુ સાથે 200 છે, જે લખ્યા પછી બનેલ છે.

`GET` વ્યુ નીચે મુજબ ધિરાણનો અહેવાલ આપે છે:

- દરેક પૂલ `borrowMode` (`saturation` અથવા `consent`), અને કીની પોતાની `lendingPercent` અને `lendingUntil` વહન કરે છે.
- `lendingActive` એ માત્ર `consent` પૂલમાં `true` છે, જેની ટકાવારી 0 થી ઉપર છે અને સમયમર્યાદા પહોંચી નથી.
- `consent` પૂલમાં, દરેક ગણી શકાય તેવું `dimensions[].yourShare` `borrowAvailable` ધરાવે છે. તે તે છે જેનો ઉપયોગ હવે તેના શેરની ઉપર કરી શકે છે, જે અન્ય કી દ્વારા આપવામાં આવે છે.
- `borrowAvailable` ગેટના સૂત્રનો ઉપયોગ કરે છે. તે દરેક બીજી કી વાંચે છે, જ્યારે કી તેના શેર હેઠળ હોય છે. `hard` કી માટે જે અન્ય કી અને ગણતરીપાત્ર પરિમાણ દીઠ એક વધારાનું વાંચન છે, સમાંતરમાં.
- `borrowAvailable` એ `soft` અથવા `burst` કી માટે `null` છે અને જ્યારે વાંચન નિષ્ફળ જાય ત્યારે `null`.
- `borrowAvailable` એ બીજી બધી કી માટે એક આકૃતિ છે. બે કીના પૂલમાં તે બીજી કીની પોતાની આકૃતિ છે.
- `borrowAvailable` જાણ હજુ સુધી `percent` વિન્ડોઝ અથવા `accounts[]` માં કરવામાં આવી નથી.
- `saturation` પૂલમાં વ્યુ `lendingActive: false` સાથે સંગ્રહિત સંમતિની જાણ કરે છે અને `borrowAvailable` નહીં.

### ભૂલો

આ માર્ગનો દરેક પ્રતિભાવ, સફળતા કે ભૂલ, `Cache-Control: no-store` વહન કરે છે. રૂટ ચાલે તે પહેલાં જે ઇનકાર થાય છે તે તેને વહન કરતું નથી, ઉદાહરણ તરીકે ક્લાયન્ટ API પોલિસીની 401 અથવા IP ફિલ્ટરની 403. રૂટની ભૂલો નિશ્ચિત સંદેશ સાથે પ્રમાણભૂત ભૂલના મુખ્ય ભાગનો ઉપયોગ કરે છે: 400 (અમાન્ય પ્રદાતા), 401 (ગુમ થયેલ અથવા અમાન્ય કી), 403 ( `self:usage`) અને 403 (મિસિંગ) (`Failed to build quota view`) 500 કોઈપણ નિષ્ફળતાને આવરી લે છે એકવાર વિનંતી રૂટ પર પહોંચે છે, જેમાં કી લુકઅપનો સમાવેશ થાય છે; તેનું કારણ સર્વર પર લોગ થયેલ છે અને ક્યારેય પરત આવ્યુ નથી. `PATCH` ની ભૂલો [ધિરાણ સંમતિમાં](#lending-consent) સૂચિબદ્ધ છે.

### મર્યાદાઓ

- `remaining` એ કીના વાજબી શેરનો એક ભાગ છે જેનો તેણે ઉપયોગ કર્યો નથી. તે ગેરંટી નથી. જ્યારે પૂલમાં જગ્યા હોય ત્યારે પણ ચાવી તેની બહાર સેવા આપી શકાય છે. એકવાર પૂલની કુલ સંખ્યા `limit` પર પહોંચી જાય, પૂલની દરેક ચાવી નકારવામાં આવે છે, પછી ભલે તે તેની પોતાની `remaining` હોય, અને `self:account-quota` વગરની ચાવી તે કુલ જોઈ શકતી નથી.
- `remaining` ફાળવણીના સંપૂર્ણ `cap` ને ધ્યાનમાં લેતું નથી. જ્યારે કેપના યુનિટની વિન્ડોમાં તેનો પોતાનો વપરાશ કેપના મૂલ્ય સુધી પહોંચે ત્યારે અમલીકરણ કીને નકારે છે.
- એકાઉન્ટ-લેવલ બાર પ્રદાતા-મર્યાદા કેશમાંથી આવે છે અને અમલીકરણના નિર્ણયને થોડી મિનિટોમાં પાછળ રાખી શકે છે. રીસેટનો સમય પસાર થઈ ગયો હોય તેવું વાંચન `stale` તરીકે જાણ કરવામાં આવે છે.
- પ્રતિ-મોડલ વિન્ડો (`modelWindows`) માત્ર એવા પ્રદાતાઓ માટે જ જાણ કરવામાં આવે છે કે જેમની પાસે પ્લાન-વિન્ડો મેપિંગ છે: Claude અને Codex આજે. અન્ય પ્રદાતાઓ માટે `modelWindows` ખાલી `windows` સૂચિ સાથે, એકાઉન્ટ ડેટા બતાવવામાં આવે ત્યારે પણ હાજર હોય છે.
- `percent` વિન્ડોની કીનો પોતાનો હિસ્સો એક અંદાજ છે. તે એટ્રિબ્યુશન પુસ્તકમાંથી આવે છે અને ઉપર "ટકા પરિમાણો: પ્રતિ-કી એટ્રિબ્યુશન" હેઠળ સૂચિબદ્ધ દરેક મર્યાદા ધરાવે છે.
- `consumed` એ સંખ્યા છે જે અમલીકરણ વાજબી શેર સાથે સરખાવે છે. તે `attributed` વત્તા `external` છે, બરાબર. `attributed` એ ભાગ છે જે પુસ્તક તેને રૂટ કરેલા ટોકન્સ માટે ચાવી આપે છે. `external` એ ખાતાના ઉપયોગનો કીનો ભાગ છે કે જે પૂલની ચાવીઓનો હિસ્સો નથી.
- બંને ભાગો ત્યારે જ મોકલવામાં આવે છે જ્યારે પૂલનો `accountVisible` સાચો હોય: કીમાં `self:account-quota` હોય છે અને પ્રદાતા તેના `sharedQuotaProviders` માં હોય છે. તેના વગરની ચાવી એ જ `status` અને `reason` સાથે એકલા `consumed` મળે છે.
- બંને ભાગો અને તેના પોતાના વજન સાથે, ધારક પૂલની ચાવીઓ પર ચાર્જ કરવામાં આવતા પૂલની બહાર કરવામાં આવેલ ઉપયોગનું કામ કરી શકે છે. એકાઉન્ટ સ્કોપ ધરાવનાર ધારક પહેલાથી જ એકાઉન્ટની કુલ રકમ જુએ છે.
- એક કી કે જે વિન્ડોમાં કશું રાઉટ કરતી નથી તે હજુ પણ `consumed` માંથી તેનો બાહ્ય ચાર્જ વાંચી શકે છે, કારણ કે તેનો એટ્રિબ્યુટેડ ભાગ 0 છે.
- ઉદાહરણ તરીકે, એક પુસ્તક 0 પર ખુલે છે, જેમાં A અને B કી દરેકના વજન 50 છે. કી A રૂટ 900,000 ટોકન્સ અને કી B 100,000. પછી ખાતું 100 ની મર્યાદાના 60% સુધી પહોંચે છે. પછી `attributed` કી A માટે 54 અને કી B માટે 6 છે, અને `external` બંને માટે 0 છે.
- દૃશ્ય પુસ્તક વાંચે છે અને તેની સ્થિતિ ક્યારેય લખતો નથી. તે કોઈ પુસ્તક ખોલતું નથી, અને તે ક્યારેય પ્રદાતાને વાંચન માટે પૂછતું નથી. Redis સ્ટોર સાથે, રીડ બેકગ્રાઉન્ડમાં સુપરસીડ કરેલ રીવીઝન ફીલ્ડને દૂર કરે છે, જેમ કે ગેટના રીડ કરે છે.
- જ્યારે ગેટની કેશ એકાઉન્ટનું રીડિંગ ધરાવે છે ત્યારે જ શેર `ok` છે. એક વિના તે `stale` છે, તેથી કોઈ તાજેતરની વિનંતી વિનાના પૂલમાં તે કદાચ જૂનું હોય તેવું બતાવે છે.
- જ્યાં સુધી વિનંતી પૂલમાંથી પસાર ન થાય, ત્યાં સુધી શેર અનુપલબ્ધ છે. તે વિનંતી પુસ્તક ખોલે છે, અને તે સમયે એકાઉન્ટનો આંકડો પૂલની બહાર કરવામાં આવેલા ઉપયોગ તરીકે ગણવામાં આવે છે.
- ઘણા એકાઉન્ટ્સ ધરાવતા પૂલમાં, દરેક એકાઉન્ટ એન્ટ્રી તે એકાઉન્ટની પોતાની બુક અને એક એકાઉન્ટની મર્યાદાનો ઉપયોગ કરે છે. અમલીકરણ ખાતાઓની સંખ્યા દ્વારા બંને બાજુ માપે છે, તેથી પ્રમાણ સમાન છે.
- પ્રતિ-મોડલ વિન્ડો ચાવી માટે કોઈ શેર ધરાવતું નથી. પુસ્તક પ્રતિ-મોડલ ડેટા રાખતું નથી.
- શેડ્યૂલના અનામત માળનું દૃશ્ય દ્વારા મૂલ્યાંકન કરવામાં આવતું નથી: શેડ્યૂલ `open` તરીકે બતાવી શકે છે જ્યારે `schedule-reserve` કારણ સાથે વિનંતીનો ઇનકાર કરવામાં આવે છે.
- જ્યારે સમાન કીના બે પૂલ કનેક્શન શેર કરે છે, ત્યારે અમલીકરણ તેમાંથી એકને લાગુ કરે છે, અને દૃશ્ય બંનેને સૂચિબદ્ધ કરે છે.
- નિષ્ફળ કી પ્રયાસો પર સરનામાં દીઠ કોઈ મર્યાદા નથી: રિવર્સ પ્રોક્સી કૉલર પાછળ એક સરનામું શેર કરી શકે છે (તે તેના પર નિર્ભર કરે છે કે ફોરવર્ડ કરેલા ક્લાયન્ટ સરનામાંઓ વિશ્વાસપાત્ર છે કે નહીં), તેથી લોકઆઉટ દરેક કી ધારકના માર્ગને નકારી શકે છે. `REQUIRE_API_KEY=true` સાથે, રૂટ ચાલે તે પહેલાં ક્લાયન્ટ API પોલિસી દ્વારા અમાન્ય કીને નકારવામાં આવે છે, આ રૂટની જગ્યાએ તે પોલિસીના 401 બોડી સાથે.

### સભ્ય વપરાશ

એડમિનિસ્ટ્રેટર કી ધારકોને એ જોવા આપી શકે છે કે કેવી રીતે વિન્ડોનો ઉપયોગ પૂલના સભ્યો વચ્ચે વિભાજિત થાય છે. વિકલ્પ એ પૂલનો `memberBreakdown` છે, મૂળભૂત રીતે બંધ છે. તે પૂલ વિઝાર્ડમાં અથવા `PATCH /api/quota/pools/{id}` સાથે સેટ કરેલ છે. `GET /api/quota/pools` અને `GET /api/quota/pools/{id}` તેની જાણ કરે છે.

દૃશ્યનું એક પરિમાણ `members` ત્યારે જ વહન કરે છે જ્યારે આ બધા ધરાવે છે:

- પૂલનો વિકલ્પ ચાલુ છે
- પૂલમાં વધુમાં વધુ 20 કીઓ ફાળવવામાં આવી છે, અને તેમાંથી ઓછામાં ઓછી ત્રણ વિનંતીઓ કરી શકે છે: સક્રિય, રદ કરાયેલ નથી, પ્રતિબંધિત નથી અને તેમની મુદત વીતી ગઈ નથી
- પૂલનો `accountVisible` સાચો છે: કીમાં `self:account-quota` છે અને પ્રદાતા તેના `sharedQuotaProviders` માં છે
- `percent` વિન્ડો પર, એકાઉન્ટનું જોડાણ એ એક કી છે જેનો ઉપયોગ કરી શકે છે
- તે વિંડોની ચાવીનો પોતાનો શેર વાંચવામાં આવ્યો હતો: તેનો `status` `unavailable` નથી

અન્યથા `members` ગેરહાજર છે. તે ક્યારેય ખાલી યાદી નથી.

- દરેક સ્લાઇસ `{ slot, consumed, isYou }` છે. રિસ્પોન્સ સ્કીમા સ્લાઈસ પરની કોઈપણ અન્ય પ્રોપર્ટી અને 20 થી વધુ સ્લાઈસની યાદીને નકારે છે. સ્લાઇસેસ સ્લોટ ક્રમમાં સૂચિબદ્ધ છે.
- ફાળવેલ કી દીઠ એક સ્લાઇસ છે, જેમાં એવી કીનો સમાવેશ થાય છે જે હવે વિનંતીઓ કરી શકશે નહીં. ઉપયોગ વિનાનો સભ્ય વાસ્તવિક શૂન્ય બતાવે છે.
- સ્લોટ 1 એ હંમેશા પૂછતી કી છે, `isYou` સાચી સાથે. અન્ય સ્લોટ નંબરો કીડ હેશની રેન્ક છે. તે `API_KEY_SECRET` સાથે કીડ છે અને પૂલ, પૂછતી કી અને સભ્યને આવરી લે છે.
- તેથી નંબરો ધારકો વચ્ચે રેખા નથી. એક ધારક માટે તેઓ મુલાકાતો વચ્ચે સમાન રહે છે. જ્યારે કી જોડાય છે અથવા પૂલમાંથી બહાર નીકળે છે, અથવા જ્યારે તે રહસ્ય ફેરવાય છે ત્યારે તેઓ બદલી શકે છે.
- ગણી શકાય તેવી વિન્ડો પર ક્વોટા સ્ટોરમાં સભ્યનું કાઉન્ટર છે, તેના પોતાના `consumed` જેવું જ કાઉન્ટર છે.
- `percent` વિન્ડો પર એક સ્લાઇસ એ સભ્યનો `attributed` ભાગ છે, જે કીના પોતાના શેર તરીકે વાંચવામાં આવે છે તે જ પુસ્તકમાંથી. પૂલની બહાર કરવામાં આવેલ ઉપયોગને ક્યારેય ટુકડાઓમાં વિભાજિત કરવામાં આવતો નથી. તે ચાર્જ વજન દ્વારા વિભાજિત થાય છે, તેથી સ્લાઇસેસ કે જે તેને વહન કરે છે તે વજન બતાવશે.
- પ્રત્યેક દૃશ્ય અન્ય સભ્ય દીઠ એક મૂલ્ય અને ગણતરીપાત્ર વિન્ડો, સમાંતર વાંચે છે. `percent` વિન્ડો પર સ્લાઇસની કિંમત શેરના પોતાના પુસ્તક વાંચ્યા સિવાય વાંચવામાં આવતી નથી. જ્યારે એક મૂલ્ય વાંચી શકાતું નથી, ત્યારે તે વિંડોમાં કોઈ `members` હોતું નથી, અને કીનો પોતાનો શેર રહે છે.
- વિકલ્પ અને ઉપયોગ કરી શકાય તેવી કીની સંખ્યા પૂલ દીઠ એકવાર વાંચવામાં આવે છે, અને માત્ર એક કી માટે જે એકાઉન્ટ ડેટા જોઈ શકે છે. વિકલ્પ અથવા ઉપયોગી-કી કાઉન્ટનું નિષ્ફળ વાંચન તે પૂલ માટે બારને બંધ કરે છે. સર્વર ચેતવણીને લૉગ કરે છે, અને બાકીનું દૃશ્ય બનાવવામાં આવે છે.

બારમાં કોઈ નામ અથવા આઈડી નથી. તેઓ હજુ પણ મુખ્ય ધારકને અન્ય સભ્યો વિશે વસ્તુઓ કહે છે:

- ધારકો હજુ પણ તેમના મૂલ્યો દ્વારા સ્લાઇસેસ સાથે મેચ કરી શકે છે.
- સ્થિર નંબરિંગ ધારકને સમય જતાં એક સભ્યને અનુસરવા દે છે.
- સ્લાઇસેસની સંખ્યા દર્શાવે છે કે પૂલમાં કેટલી કી ફાળવવામાં આવી છે.
- ત્રણ કીના પૂલમાં, એક કી કઈ વપરાય છે તે જાણનાર વ્યક્તિ કહી શકે છે કે છેલ્લી કી કઈ વપરાયેલી છે.
- જ્યારે પૂલ ત્રણ ઉપયોગી કીની નીચે આવે છે, ત્યારે બાર અદૃશ્ય થઈ જાય છે. અગાઉ લીધેલા દૃશ્યો હજુ પણ દર્શાવે છે કે દરેક સભ્ય શું વાપરે છે.
- ગણતરીપાત્ર વિન્ડો પર, પૂલની કુલ બાદબાકી એ કીનો ઉપયોગ બતાવી શકે છે જે હવે ફાળવવામાં આવતી નથી.
- એક સભ્ય જે એક એકાઉન્ટ પર શૂન્ય બતાવે છે અને બીજામાં ઉપયોગ કરે છે તે બતાવી શકે છે કે કયો સભ્ય કયો એકાઉન્ટ વાપરે છે.
- `hard` પૉલિસી સાથે ગણનાપાત્ર પૂલમાં, સભ્યના વાજબી શેર પર વધતી અટકી ગયેલી સ્લાઇસ તે સભ્યના વજનનો સંકેત આપે છે.

### ઉપયોગ શ્રેણી (`GET /api/v1/me/usage`)

`GET /api/v1/me/usage?range=<range>` ( `/v1/me/usage` પર પણ સેવા આપવામાં આવે છે) કૉલિંગ કીની પોતાની વિનંતીઓનો ઉપયોગ અને ખર્ચ પરત કરે છે: કુલ, UTC દિવસ દીઠ એક એન્ટ્રી, પ્રતિ દિવસ અને મોડેલ, પ્રતિ મોડેલ અને પ્રદાતા દીઠ. તે ધ્વજ, પ્રમાણીકરણ નિયમો, `self:usage` સ્કોપ, `Cache-Control: no-store` અને ઉપરના ક્વોટા માર્ગની ભૂલ વર્તણૂક શેર કરે છે. `range` પહેલાં કી તપાસવામાં આવે છે. ભૂલો 400 (`Invalid range`), 401, 403, 404 અને 500 (`Failed to build usage`) છે.

- `range` એ `1d`, `7d`, `30d` (મૂળભૂત) અથવા `90d` માંથી એક છે. અન્ય કોઈપણ મૂલ્ય, ખાલી મૂલ્ય અથવા પુનરાવર્તિત પરિમાણ એ 400 છે. કૉલની કિંમતને બાંધવા માટે સેટ `90d` પર અટકે છે. દૃશ્ય માત્ર ઉપયોગનો કાચો ઇતિહાસ વાંચે છે, ક્યારેય દૈનિક સારાંશ નથી, જેમાં કોઈ કી નથી.
- કૉલિંગ કીના આઈડી દ્વારા પંક્તિઓ પસંદ કરવામાં આવે છે. કી નામની કૉલમ ક્યારેય મેળ ખાતી નથી અને કી આઈડી વિના રેકોર્ડ કરેલી પંક્તિઓ ક્યારેય ગણાતી નથી.
- શ્રેણી બનાવવાથી વિન્ડોમાં કીની પંક્તિઓ પર પાંચ જૂથબદ્ધ પ્રશ્નો ચાલે છે. બિલ્ટ સીરિઝનો પુનઃઉપયોગ 60 સેકન્ડ પ્રતિ કી અને રેન્જ માટે થાય છે, અને પુનઃઉપયોગ થયેલ કૉલ કોઈ ચાલતો નથી. તેનો `generatedAt` તેની ઉંમર આપે છે.
- જ્યારે શ્રેણી બાંધવામાં આવે ત્યારે વિંડો સમાપ્ત થાય છે. પાછળથી સ્ટેમ્પ કરેલી પંક્તિ, ઉદાહરણ તરીકે ઘડિયાળના ત્રાંસા દ્વારા, ગણવામાં આવતી નથી.
- `coverage.retentionDays` એ ઓપરેટરની કાચી વપરાશ-ઇતિહાસ રીટેન્શન સેટિંગ છે ( ડેટાબેઝ સેટિંગ્સમાં`retention.usageHistory` ). જ્યારે વિનંતી કરેલ શ્રેણી તે સેટિંગ કરતા લાંબી હોય ત્યારે `coverage.truncatedByRetention` સાચું હોય છે. તે બે સંખ્યાઓની તુલના કરે છે અને પંક્તિઓ ખરેખર ખૂટે છે કે કેમ તે તપાસતું નથી.
- પ્રદાતાને કીની પોતાની વિનંતીઓ માટે રેકોર્ડ કર્યા મુજબ પરત કરવામાં આવે છે. મોડલ તેના છેલ્લા `/` પછી નોંધાયેલ નામ છે, અને પંક્તિઓ તેના દ્વારા જૂથબદ્ધ છે. કોમ્બો વિનંતી કે જેના પ્રત્યેક લક્ષ્યને નકારવામાં આવ્યું હતું તે પ્રદાતા તરીકે રૂટીંગ લેબલ સાથે રેકોર્ડ કરવામાં આવે છે (કોમ્બો નામ, `auto` અથવા `combo`) અને ક્લાયંટે મોકલેલ મોડેલ સ્ટ્રીંગ. અન્ય નકારવામાં આવેલી વિનંતીઓ, ઉદાહરણ તરીકે ઓપન સર્કિટ બ્રેકર, મોડલ કૂલડાઉન અથવા ક્વોટા-પાર્ક કરેલ સ્કીપ દ્વારા, લક્ષ્ય પ્રદાતા અને મોડેલ રાખો.
- ગણતરીઓ અને ખર્ચ ઉપરાંત, પ્રતિભાવ સરેરાશ વિલંબ, સફળતા દર અને પ્રથમ અને છેલ્લી વિનંતીનો સમય ધરાવે છે.
- `byModel` સૌથી વધુ વિનંતીઓ સાથે 50 પ્રદાતા-અને-મોડલ જોડીની યાદી આપે છે. વધુ જોડી સાથે તેની એન્ટ્રીઓ `summary` સુધી ઉમેરાતી નથી, અને `summary.uniqueModels` દરેક રેકોર્ડ કરેલ મોડલ જોડણીની ગણતરી કરે છે. `byModelTruncated` પછી સાચું છે, અને એક મોડેલ જેની જોડી કટની બંને બાજુએ પડે છે તે આંશિક સરવાળો દર્શાવે છે.
- બે ખર્ચની જાણ કરવામાં આવી છે. `costUsd` એ બિલની કિંમત છે, કારણ કે વપરાશ વિશ્લેષણ દર્શાવે છે. ફ્લેટ-રેટ સબસ્ક્રિપ્શન પ્રદાતાઓ, જેમ કે Claude કોડ પ્લાન, ત્યાં $0 ગણો. `listPriceUsd` એ સૂચિ કિંમત પરનો સમાન વપરાશ છે, સબ્સ્ક્રિપ્શન્સ શામેલ છે. વિનંતિ કે જેના મોડેલમાં કોઈ કિંમતની પંક્તિ નથી તે તેની સંગ્રહિત કિંમતની ગણતરી કરે છે: પ્રદાતાએ જાણ કરેલ ખર્ચ અથવા વિનંતી રેકોર્ડ કરવામાં આવે ત્યારે ગણતરી કરેલ ખર્ચ. માત્ર 0 ની ગણતરી સાથેની વિનંતી, કોઈ માર્કર વિના, તેથી કુલ આંશિક હોઈ શકે છે.
- પ્રતિભાવ કરાર `src/shared/schemas/selfUsage.ts` ( `docs/openapi.yaml` માં`SelfUsageSeries` ) છે.

### સ્વ-સેવા પૃષ્ઠ

`QUOTA_SELF_PANEL` ચાલુ સાથે, `/quota/{provider}` એ સાર્વજનિક પૃષ્ઠ છે. કી ધારક ત્યાં API કી ટાઈપ કરે છે અને પ્રદાતા માટે તે કીના પુલ જુએ છે. દરેક પૂલ દરેક માટે પૂલનો ઉપયોગ અને કીના પોતાના શેર સાથે, દરેક પૂલ વિન્ડો દીઠ એક કાર્ડ બતાવે છે. પૂલના દરેક ખાતાના પોતાના કાર્ડ હોય છે, જેમાં ખાતાના ઉપયોગ અને ચાવીનો હિસ્સો હોય છે. જ્યારે કી એકાઉન્ટ ડેટા જોઈ શકે ત્યારે જ એકાઉન્ટનો ઉપયોગ દેખાય છે. પૃષ્ઠ દરેક એકાઉન્ટની પ્રતિ-મોડલ મર્યાદા અને કીના પોતાના ઉપયોગની સૂચિ પણ આપે છે. જ્યારે શેડ્યૂલ હમણાં કીને અવરોધિત કરે છે ત્યારે એક સૂચના દેખાય છે. કાર્ડ તેના ઉપયોગ સાથે કીની દરેક પ્રતિ-મોડલ કેપને સૂચિબદ્ધ કરે છે, અને પહોંચી ગયેલા લોકોને ચિહ્નિત કરે છે. `{provider}` એ પ્રદાતા id અથવા તેનું ઉપનામ (`/quota/claude`, `/quota/cc`) છે. અજાણ્યા પ્રદાતા, અને દરેક `/quota/*` પાથ જ્યારે ફ્લેગ બંધ હોય, 404 નો જવાબ આપો. કસ્ટમ OpenAI- અથવા એન્થ્રોપિક-સુસંગત નોડ પરના પૂલ પાસે કોઈ પૃષ્ઠ નથી. API હજુ પણ તેમના માટે જવાબ આપે છે.

પૃષ્ઠ પર કોઈ સત્ર નથી. કી ફક્ત `GET /api/v1/me/quota/{provider}`, `PATCH /api/v1/me/quota/{provider}` અને `GET /api/v1/me/usage` ના `Authorization` હેડરમાં મોકલવામાં આવે છે , ક્યારેય URL માં નહીં. સર્વર સ્વીકારે છે તે કી ટેબના `sessionStorage` માં રાખવામાં આવે છે. "આ ઉપકરણ પર યાદ રાખો" સાથે તેને બદલે `localStorage` માં રાખવામાં આવે છે, અને "Forget key" તેને બંનેમાંથી દૂર કરે છે. સર્વરે નકારી કાઢેલી કી સ્ટોરેજમાંથી દૂર કરવામાં આવે છે.

`consent` મોડમાં આવેલ પૂલ ધિરાણ કાર્ડ બતાવે છે. ત્યાં કી ધારક ધિરાણ માટે કીના નિષ્ક્રિય શેરના 0 થી 100 સુધીની સંપૂર્ણ ટકાવારી સેટ કરે છે. ધારક એ પણ પસંદ કરે છે કે સંમતિ કેટલો સમય ચાલે છે: બંધ ન થાય ત્યાં સુધી, 1 કલાક, 8 કલાક, 24 કલાક, 7 દિવસ અથવા 30 દિવસ. સમયગાળો બચતની ક્ષણથી ગણાય છે. જ્યારે સમયમર્યાદા અમલમાં હોય, ત્યારે ધારક તેને બદલે રાખી શકે છે. જો તે સમયમર્યાદા સેવ પહેલાં પસાર થઈ જાય, તો કાર્ડ કંઈ મોકલતું નથી અને બીજી પસંદગી માટે પૂછે છે. 0% સાથે કોઈ સમયમર્યાદા મોકલવામાં આવતી નથી. કાર્ડ તેના સમય ઝોન નામ સાથે સંગ્રહિત સમયમર્યાદા બતાવે છે. સંમતિ જેની સમયમર્યાદા પસાર થઈ ગઈ છે તે સમાપ્ત તરીકે બતાવવામાં આવે છે.

એક `hard` કી માટે કાર્ડ પણ સૂચિ આપે છે, પૂલ વિન્ડો દીઠ, અન્ય કીઓ અત્યારે કીને ઉધાર આપે છે. દરેક પંક્તિ અન્ય બધી કી માટે એક આકૃતિ છે. બે કીના પૂલમાં તે બીજી કીની પોતાની આકૃતિ છે. દૃશ્ય જે આકૃતિની જાણ કરતું નથી તે ઉપલબ્ધ નથી તરીકે વાંચે છે, શૂન્ય તરીકે નહીં. `soft` અથવા `burst` કી માટે કાર્ડ કહે છે કે કોઈ આકૃતિ લાગુ પડતી નથી.

`saturation` મોડમાં એક પૂલ જેની કી 0 થી ઉપરની ટકાવારી સ્ટોર કરે છે તે માત્ર ઉપાડ દર્શાવે છે. તે કહે છે કે સંગ્રહિત ટકાવારીની ત્યાં કોઈ અસર નથી. તેનું ઉપાડ બટન કોઈ સમયમર્યાદા વિના 0 મોકલે છે. સંગ્રહિત 0 સાથે `saturation` મોડમાં આવેલ પૂલ કોઈ ધિરાણ કાર્ડ બતાવતું નથી. સેવ કર્યા પછી, એક કાર્ડ કે જે પાછું આપેલું દૃશ્ય હવે તેના સંદેશા સાથે રહે છે જ્યાં સુધી પૃષ્ઠનું દૃશ્ય ફરીથી બદલાય નહીં.

જ્યાં સુધી ધારક સાચવો અથવા ઉપાડો દબાવશે ત્યાં સુધી કંઈપણ સાચવવામાં આવતું નથી. દરેક પ્રેસ એક `PATCH /api/v1/me/quota/{provider}` વિનંતી મોકલે છે, અને બીજી પ્રેસ જ્યારે પ્રથમ બાકી હોય ત્યારે કશું મોકલતું નથી. શરીર દૃશ્ય, ટકાવારી અને સમયમર્યાદામાંથી પૂલના અપારદર્શક `ref` વહન કરે છે. જવાબ પુનઃબિલ્ટ ક્વોટા વ્યૂ છે, અને પૃષ્ઠ તેને કોઈ સેકન્ડ વાંચ્યા વિના બતાવે છે. જ્યારે બે સેવ ઓવરલેપ થાય છે, ત્યારે પેજ છેલ્લા જવાબ પછી એકવાર ક્વોટા વાંચે છે. પૃષ્ઠ બ્રાઉઝર સ્ટોરેજમાં સંમતિ રાખતું નથી.

ઇનકાર કરેલ ફેરફારને HTTP સ્ટેટસમાંથી પસંદ કરેલ ટેક્સ્ટ દ્વારા કાર્ડ પર સમજાવવામાં આવે છે. ભૂલ મુખ્ય ભાગ વાંચવામાં આવતો નથી. A 401 કહે છે કે કી સ્વીકારવામાં આવી ન હતી અને ક્વોટાને ફરીથી લોડ કરે છે. 403 કહે છે કે પૂલ ધિરાણમાં ફેરફાર કરી રહ્યો નથી, અને 404 કહે છે કે પૂલ સમાપ્ત થઈ ગયો છે. બંને એક બટન ઓફર કરે છે જે ક્વોટાને ફરીથી લોડ કરે છે. 400 અથવા અન્ય 4xx જવાબ ધારકને ટકાવારી અને સમયમર્યાદા તપાસવા કહે છે. A 429 ધારકને `Retry-After` ની સેકન્ડ સાથે રાહ જોવાનું કહે છે જ્યારે જવાબ તેમને આપે છે. 5xx જવાબ, 408 અથવા નેટવર્ક નિષ્ફળતા કહે છે કે ફેરફાર કદાચ સાચવવામાં આવ્યો નથી, અને ટાઇપ કરેલ મૂલ્યો રાખે છે. કરારની બહારનો જવાબ ક્વોટાને ફરીથી લોડ કરે છે. નિષ્ફળ સેવ કી જાતે જ દૂર કરતું નથી. જ્યારે તેને નકારવામાં આવે તે પછી ફરીથી લોડ કરવામાં આવે છે, ત્યારે પૃષ્ઠ કોઈપણ નકારેલ વાંચ્યાની જેમ કીને દૂર કરે છે.

એકવાર કી સ્વીકારવામાં આવે તે પછી, પૃષ્ઠ ત્રણ ટેબ સાથે "તમારા સાધનો સેટ કરો" કાર્ડ પણ બતાવે છે. "Claude કોડ" `~/.claude/settings.json` માટે `env` બ્લોક આપે છે. "શેલ" એ `export` રેખાઓ જેવા જ ચલો આપે છે. "Claude ડેસ્કટોપ" તેની તૃતીય-પક્ષ અનુમાન વિન્ડો માટે મૂલ્યો આપે છે. મૉડલ એ ક્વોટા-શેર મૉડલ છે જે કી તે પ્રદાતા માટે કૉલ કરી શકે છે. જ્યારે આવી કોઈ સૂચિ કી સાથે આવતી નથી, ત્યારે બ્લોક તેના બદલે ગેટવે મોડલ શોધ ચાલુ કરે છે. ગેટવે સરનામું એ જાહેર API મૂળ સર્વર અહેવાલો છે (`OMNIROUTE_PUBLIC_API_BASE_URL`, પછી `OMNIROUTE_PUBLIC_BASE_URL`). જ્યારે બેમાંથી કોઈ સેટ ન હોય, ત્યારે કાર્ડ પ્લેસહોલ્ડર બતાવે છે અને ધારકને એડમિનિસ્ટ્રેટરને પૂછવાનું કહે છે. કી પ્લેસહોલ્ડર તરીકે બતાવવામાં આવે છે. "મારી કી શામેલ કરો" આખી કીને સ્ક્રીન પરના ટેક્સ્ટમાં અને કોપી બટન કોપી કરે છે તેમાં મૂકે છે. તે ત્યાં સુધી ચાલે છે જ્યાં સુધી બોક્સ સાફ ન થાય, કી ભૂલી ન જાય અથવા બદલાઈ જાય અથવા પૃષ્ઠ બાકી રહે. કાર્ડ કોઈ વિનંતી મોકલતું નથી અને કોઈ ફાઇલ ડાઉનલોડ કરવાની ઑફર કરતું નથી.

API માર્ક `stale` વાંચવું એ કદાચ જૂનું હોય તેમ બતાવવામાં આવ્યું છે. તે `unavailable` ને ચિહ્નિત કરે છે તે વાંચન તેના કારણ સાથે બતાવવામાં આવે છે, ક્યારેય શૂન્ય તરીકે નહીં.

ટકાવારી યોજનાઓ પર જ્યારે API તેની જાણ કરે છે ત્યારે પૃષ્ઠ કીનો પોતાનો હિસ્સો દોરે છે. તે કહે છે કે સંખ્યા એક અંદાજ છે અને તેના બે ભાગોને નામ આપે છે. પ્રતિ-મોડલ મર્યાદા માત્ર એકાઉન્ટ દર્શાવે છે.

જ્યારે વિન્ડો `members` વહન કરે છે, ત્યારે તેનું કાર્ડ સ્લોટ ક્રમમાં સભ્ય દીઠ એક સેગમેન્ટ સાથે બાર પણ દર્શાવે છે. પૂછતી કીનો સેગમેન્ટ ઉચ્ચાર રંગનો ઉપયોગ કરે છે. અન્ય સેગમેન્ટ્સ થીમના ચાર્ટ રંગો દ્વારા ચક્રમાં જાય છે. ટેક્સ્ટ લિજેન્ડ દરેક સેગમેન્ટને તેના મૂલ્ય સાથે સૂચિબદ્ધ કરે છે, તેથી કંઈપણ રંગ પર આધારિત નથી. સેગમેન્ટ્સને `You` અથવા `Member N` લેબલ કરવામાં આવે છે, જ્યાં N એ સ્લોટ છે.

### પૃષ્ઠ માટે સમર્પિત પોર્ટ

`QUOTA_PANEL_PORT` બીજા શ્રોતા ખોલે છે જે ફક્ત સ્વ-સેવા પૃષ્ઠને સેવા આપે છે. જ્યાં સુધી ચલ સેટ ન થાય ત્યાં સુધી તે બંધ છે. `QUOTA_PANEL_HOST` એ બાઇન્ડ સરનામું છે અને `127.0.0.1` માટે ડિફોલ્ટ છે.

શ્રોતા આ પાથને મુખ્ય પોર્ટ પર રીલે કરે છે અને દરેક અન્ય પાથ માટે 404 નો જવાબ આપે છે:

| પાથ                                                                      | સેવા આપે છે                           |
| ------------------------------------------------------------------------ | ------------------------------------- |
| `/quota/{provider}`                                                      | પાનું                                 |
| `/api/v1/me/quota/{provider}`, `/v1/me/quota/{provider}`                 | ક્વોટા વ્યુ પેજ વાંચે છે              |
| `/api/v1/me/usage`, `/v1/me/usage`                                       | પૃષ્ઠ વાંચે છે તે વપરાશ શ્રેણી        |
| `/_next/static/`                                                         | બિલ્ડની સ્ક્રિપ્ટો, શૈલીઓ અને ફોન્ટ્સ |
| `/favicon.ico`, `/favicon.svg`, `/icon-512.png`, `/apple-touch-icon.png` | ચિહ્નો                                |

`GET` અને `HEAD` બોડી વિના રીલે કરવામાં આવે છે. બોડી સાથેની એક વિનંતી પણ રીલે કરવામાં આવે છે: ક્વોટા વ્યૂ પાથનો `PATCH`, જે પેજ ધિરાણની પસંદગી બચાવવા માટે મોકલે છે. અન્ય કોઈપણ પદ્ધતિ 404 નો જવાબ આપે છે, એક CONNECT વિનંતી સિવાય, જેનું કનેક્શન કોઈ જવાબ વિના બંધ છે. અન્ય કોઈપણ વિનંતી કે જે બોડી જાહેર કરે છે તે 404 નો જવાબ આપે છે અને તેનું જોડાણ બંધ છે. અપગ્રેડ વિનંતીઓ નકારવામાં આવી છે અને તેમનું કનેક્શન બંધ છે. API પોર્ટની જેમ ડોટ સેગમેન્ટ અથવા ફ્રેગમેન્ટ માર્કર સાથેનો પાથ નકારવામાં આવ્યો છે. તેથી છાપવાયોગ્ય ASCII બહારના અક્ષર સાથે વિનંતી લક્ષ્ય છે. આ પોર્ટની પોતાની તપાસ પહેલા, HTTP પાર્સર દ્વારા લક્ષ્યમાં એક કાચા નિયંત્રણ પાત્રને 400 જવાબ આપવામાં આવે છે. હેડરોને વિનંતી કરો કે ફ્રેમવર્ક તેના પોતાના ઉપયોગ માટે અનામત છે તે રીલે કરવામાં આવતું નથી: નામો જે `x-middleware-`, `x-invoke-`, `x-nextjs-`, `x-now-` અથવા `x-next-`, અને `x-matched-path` અને `next-resume` નામોથી શરૂ થાય છે. વિનંતી તેમના વિના રીલે કરવામાં આવે છે. આ પોર્ટ દ્વારા ડેશબોર્ડ, લોગિન પેજ, મેનેજમેન્ટ API અને અનુમાન માર્ગો સુધી પહોંચી શકાતું નથી.

`PATCH` એ `Content-Type: application/json` વહન કરવું આવશ્યક છે, કોઈ પરિમાણ વિના અથવા ફક્ત `charset=utf-8` સાથે. તે 1 થી 4096 સુધી એક `Content-Length` ધરાવતું હોવું જોઈએ, સાદા અંકો તરીકે લખાયેલું હોવું જોઈએ અને `Transfer-Encoding` નહીં. આમાંના એક નિયમનો ભંગ કરનાર `PATCH` 404 નો જવાબ આપે છે. કેટલીક દૂષિત લંબાઈ, જેમ કે સહી કરેલ અથવા પુનરાવર્તિત, આ પોર્ટની પોતાની તપાસ પહેલા HTTP પાર્સર દ્વારા 400 નો જવાબ આપવામાં આવે છે. પોર્ટ મુખ્ય પોર્ટનો સંપર્ક કરે તે પહેલા ઘોષિત બાઈટ્સ વાંચે છે અને તેના માટે વધુમાં વધુ 5 સેકન્ડ રાહ જુએ છે. એક બોડી કે જે ત્યાં સુધીમાં પૂર્ણ નથી 404 નો જવાબ આપે છે અને તેનું જોડાણ બંધ છે. તે કિસ્સામાં, અથવા જ્યારે ક્લાયંટ પ્રથમ છોડે છે ત્યારે કંઈપણ મુખ્ય બંદર સુધી પહોંચતું નથી. પોર્ટ એ જ `Content-Length` સાથે, ઘોષિત બાઇટ્સ બરાબર રિલે કરે છે. તેમના પછીના બાઇટ્સ કનેક્શન પરની આગલી વિનંતી તરીકે વાંચવામાં આવે છે. સામેની TLS રિવર્સ પ્રોક્સી એ `Content-Length` ફોરવર્ડ કરવી જોઈએ અને વિનંતીના મુખ્ય ભાગને ફરીથી કટ ન કરવો જોઈએ. મુખ્ય પોર્ટ `Authorization` હેડરમાં API કી તપાસે છે, જેમ કે `GET` માટે.

404 બોડી `{"error":"not_found","message":"Not found."}` છે. નિષ્ફળ રિલે 502 (`api_bridge_unavailable`) અથવા 504 (`api_bridge_timeout`) `detail` ફીલ્ડ વિના જવાબ આપે છે.

સાંભળનાર `QUOTA_SELF_PANEL` વાંચતો નથી, અને તે પૃષ્ઠ ચાલુ કરતું નથી. જ્યારે ધ્વજ બંધ હોય, ત્યારે મુખ્ય પોર્ટ પર પૃષ્ઠ અને તેનું API જવાબ 404 આપે છે, અને સાંભળનાર તે જવાબને રિલે કરે છે.

ડેવલપમેન્ટ સર્વર (`next dev`) હેઠળ, પૃષ્ઠ આ પોર્ટ દ્વારા ઇન્ટરેક્ટિવ થતું નથી. ડેવલપમેન્ટ હોટ-રીલોડ સોકેટ એ અપગ્રેડ વિનંતી છે, અને પોર્ટ તેનો ઇનકાર કરે છે. વિકાસ કરતી વખતે મુખ્ય પોર્ટનો ઉપયોગ કરો.

પોર્ટ સાદા HTTP સેવા આપે છે અને પૃષ્ઠ API કી મોકલે છે. ડિફૉલ્ટ બાઈન્ડ એડ્રેસ રાખો અને તેની સામે TLS સાથે રિવર્સ પ્રોક્સી મૂકો. લૂપબેક સિવાયનું બાઈન્ડ સરનામું આ સૂચનાને લૉગ કરે છે:

```text
[Quota Panel] Bound to <host>. This port serves plain HTTP and the page sends API keys. Put a TLS reverse proxy in front of it.
```

લૂપબેક પીઅર કે જે કોઈ ફોરવર્ડિંગ હેડર મોકલતું નથી તે મુખ્ય પોર્ટ પર સ્થાનિક તરીકે ગણાય છે. તેથી સમાન હોસ્ટ પર પ્રોક્સીએ `X-Forwarded-For` મોકલવો આવશ્યક છે. ખાનગી સરનામાં પરની પ્રોક્સી તે હેડર માટે માત્ર `OMNIROUTE_TRUST_PROXY=private` (અથવા `lan`) સાથે વિશ્વસનીય છે. કોઈપણ અન્ય પીઅરને તેના કનેક્શનના સરનામા દ્વારા જાણ કરવામાં આવે છે, અને તેણે મોકલેલા ફોરવર્ડિંગ હેડરોને છોડી દેવામાં આવે છે.

સાંભળનાર એક સમયે વધુમાં વધુ 256 કનેક્શન ધરાવે છે. ક્લાયન્ટ પાસે વિનંતી હેડર મોકલવા માટે 10 સેકન્ડ અને સમગ્ર વિનંતી મોકલવા માટે 30 સેકન્ડ છે. નિષ્ક્રિય-જીવંત કનેક્શન લગભગ 5 સેકન્ડ પછી બંધ થાય છે. 60 સેકન્ડ માટે કોઈ પ્રવૃત્તિ વિનાનું જોડાણ બંધ છે. આ મૂલ્યો નિશ્ચિત છે. આગળના રિવર્સ પ્રોક્સી પર પણ કનેક્શન અને રેટ મર્યાદા સેટ કરો. સામેની રિવર્સ પ્રોક્સીએ તેના નિષ્ક્રિય અપસ્ટ્રીમ કનેક્શન્સને 5 સેકન્ડ કરતાં ઓછા સમય માટે રાખવા જોઈએ, અથવા તેનો ફરીથી ઉપયોગ ન કરવો જોઈએ. મુખ્ય પોર્ટ પરનો રિલે API પોર્ટ (`API_BRIDGE_*`) ના અપસ્ટ્રીમ સમયસમાપ્તિનો ઉપયોગ કરે છે.

જ્યારે `API_PORT` સેટ ન હોય ત્યારે સાંભળનાર પણ શરૂ થાય છે. `QUOTA_PANEL_PORT` 1 થી 65535 સુધીનું પોર્ટ હોવું જોઈએ, માત્ર અંકોમાં લખાયેલું હોવું જોઈએ. તે ડેશબોર્ડ પોર્ટ અને API પોર્ટથી અલગ હોવું જોઈએ. જ્યારે લાઇવ WebSocket સર્વર ચાલુ હોય, ત્યારે તે `LIVE_WS_PORT` (ડિફોલ્ટ 20132) થી અલગ પણ હોવું જોઈએ. કોઈપણ અન્ય મૂલ્ય કંઈપણ ખોલતું નથી અને ચેતવણી લૉગ કરે છે. નકારેલ મૂલ્ય વિશેની ચેતવણી ચલને નામ આપે છે અને મૂલ્યનું પુનરાવર્તન કરતું નથી. એક પોર્ટ જે પહેલેથી ઉપયોગમાં છે તે કંઈપણ ખોલતું નથી અને આ ચેતવણીને લૉગ કરે છે:

```text
[Quota Panel] Port <port> is already in use. The quota panel port stays off.
```

`OMNIROUTE_BASE_PATH` સેટ સાથે, સાંભળનાર તે ઉપસર્ગ હેઠળ ઉપરના દરેક પાથની અપેક્ષા રાખે છે. બિલ્ડ ટાઇમ અને રન ટાઇમ પર સમાન `OMNIROUTE_BASE_PATH` ઉપયોગ કરો. તેને અગ્રણી સ્લેશ સાથે લખો અને પાછળના સ્લેશ વગર, ઉદાહરણ તરીકે `/omniroute`. `/` અને `/omniroute/` સહિત અન્ય આકાર, ચેતવણી સાથે પોર્ટને છોડી દે છે, જોકે બિલ્ડ તે સ્વરૂપોને સ્વીકારે છે. તેથી આધાર પાથ કે જેના પ્રથમ સેગમેન્ટમાં એપ્લિકેશન રૂટનું નામ છે: `api`, `v1`, `v1beta`, `_next`, `quota`, `dashboard`, `docs`, `login`, `codex`, `responses`, `anthropic`, `openai`, `v0`, અથવા કોઈપણ કિસ્સામાં `connect`.

મર્યાદાઓ:

- આ પોર્ટ પર પાછળના સ્લેશ સાથે`/quota/{provider}/` 404 નો જવાબ આપે છે.
- સેવા કાર્યકર અને વેબ એપ્લિકેશન મેનિફેસ્ટ આ પોર્ટ પર આપવામાં આવતા નથી.
- ડેશબોર્ડમાં કસ્ટમ ફેવિકોન સેટ આ પોર્ટ પર બતાવવામાં આવ્યો નથી.
- જ્યારે એપ્લિકેશન બેઝ પાથ હેઠળ ચાલે છે ત્યારે ચિહ્નો બતાવવામાં આવતાં નથી.
- બંદર સાદા HTTP/1.1. બોલે છે
- જ્યાં સુધી પ્રક્રિયા પુનઃપ્રારંભ ન થાય ત્યાં સુધી નિષ્ફળ રહેલ બંધનનો ફરીથી પ્રયાસ કરવામાં આવતો નથી.
- શ્રોતા પાસે ક્લાયંટ સરનામાં દીઠ કોઈ જોડાણ અથવા દર મર્યાદા નથી.
- કન્ટેનર સેટઅપ આ વિભાગ દ્વારા આવરી લેવામાં આવતા નથી.

## DB સ્કીમા સારાંશ

સ્થાનાંતરણ `078`, `079` અને `085` દ્વારા ઉમેરવામાં આવેલ ત્રણ કોષ્ટકો :

- `quota_pools` + `quota_allocations` — પૂલ વ્યાખ્યાઓ અને પ્રતિ-કી ફાળવણી.
- `quota_consumption` — રોલિંગ 2-બકેટ કાઉન્ટર્સ પ્રતિ `(apiKeyId, dimensionKey)`.
- `provider_plans` — મેન્યુઅલ પ્રોવાઇડર પ્લાન ઓવરરાઇડ કરે છે ( connectionId દીઠ JSON પરિમાણો).

બધા કોષ્ટકો idempotent `CREATE TABLE IF NOT EXISTS` સ્થળાંતર દ્વારા ઉમેરવામાં આવ્યા છે.

સંમત ધિરાણ ત્રણ કૉલમ ઉમેરે છે: `quota_allocations.lending_percent` (પૂર્ણાંક, ડિફૉલ્ટ 0), `quota_allocations.lending_until` (એપોચ મિલિસેકન્ડ્સ, અથવા કોઈ સમયમર્યાદા માટે `NULL` ) અને `quota_pools.borrow_mode` (ડિફૉલ્ટ `saturation`). તેનું સ્થાનાંતરણ ફક્ત આ કૉલમ્સ ઉમેરે છે અને કોઈ અસ્તિત્વમાંની પંક્તિ લખતું નથી.

ટકા એટ્રિબ્યુશન બુકમાં `quota_percent_ledger` (પૂલ દીઠ એક પંક્તિ, એકાઉન્ટ અને પ્લાન વિન્ડો) અને `quota_percent_ledger_tokens` (પૂલ દીઠ એક ટોકન કાઉન્ટર, એકાઉન્ટ અને API કી) ઉમેરાય છે. `src/lib/db/quotaPercentLedger.ts` તેમને વાંચે છે અને લખે છે.
