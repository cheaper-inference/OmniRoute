> **TL;DR**: OmniRoute દરેક વિનંતીના ટોકન વપરાશને ટ્રૅક કરે છે, ખર્ચની ગણતરી કરે છે, દરેક API કી માટેનો ક્વોટા લાગુ કરે છે અને ડૅશબોર્ડમાં એનાલિટિક્સ દર્શાવે છે. આ માર્ગદર્શિકા સમજાવે છે કે આ બધું કેવી રીતે કાર્ય કરે છે.

**સ્રોતો:**

- `open-sse/services/usage.ts` (~70KB) — મુખ્ય વપરાશ ટ્રૅકિંગ
- `src/lib/usageAnalytics.ts` (~10KB) — ડૅશબોર્ડ માટે એકત્રીકરણ
- `src/lib/db/quotaSnapshots.ts` — ઐતિહાસિક ક્વોટા ડેટા
- `src/lib/db/usage*.ts` — વપરાશ-સંબંધિત અનેક DB મોડ્યુલો

## અવલોકન

OmniRouteમાંથી પસાર થતી દરેક વિનંતી એક **વપરાશ રેકોર્ડ** બનાવે છે, જેમાં નીચેની વિગતો સામેલ હોય છે:

- **ઓળખ**: કઈ API કી, પ્રદાતા, મોડેલ અને કોમ્બો
- **ટોકન્સ**: પ્રોમ્પ્ટ ટોકન્સ, કમ્પ્લીશન ટોકન્સ, કૅશ કરેલા ટોકન્સ અને કુલ
- **ખર્ચ**: USD રકમ (કિંમતના ડેટામાંથી ગણવામાં આવેલી)
- **સમય**: વિલંબ, શરૂઆત/સમાપ્તિના ટાઇમસ્ટૅમ્પ
- **સ્થિતિ**: સફળતા, ભૂલ, રેટ-લિમિટેડ વગેરે

આ રેકોર્ડ્સને એકત્રિત કરીને **એનાલિટિક્સ** બનાવવામાં આવે છે, **ક્વોટા સ્નૅપશૉટ્સ** તરીકે સંગ્રહિત કરવામાં આવે છે અને **દરેક કી માટેની બજેટ મર્યાદાઓ** લાગુ કરવા માટે ઉપયોગમાં લેવામાં આવે છે.

```
વિનંતી ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    એનાલિટિક્સ  ક્વોટા   બિલિંગ
                    (ડૅશબોર્ડ) (અમલ) (નિકાસ)
```

## શું નોંધવામાં આવે છે

`usage.ts` સેવા દરેક વિનંતી માટે એક **વપરાશ ઇવેન્ટ** નોંધે છે:

| ફીલ્ડ              | પ્રકાર  | સ્રોત                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | નોંધ કરતી વખતે જનરેટ કરાયેલ UUID                           |
| `apiKeyId`         | string  | વિનંતી શરૂ કરનાર API કી                                    |
| `provider`         | string  | પ્રદાતા ID (openai, anthropic, વગેરે)                      |
| `model`            | string  | મોડેલ ID (gpt-5, claude-opus-4-6, વગેરે)                   |
| `comboId`          | string? | કોમ્બો મારફતે રૂટ કરવામાં આવ્યું હોય તો કોમ્બો ID          |
| `promptTokens`     | number  | અપસ્ટ્રીમ પ્રતિસાદમાંથી                                    |
| `completionTokens` | number  | અપસ્ટ્રીમ પ્રતિસાદમાંથી                                    |
| `cachedTokens`     | number  | કૅશ હિટ ટોકન્સ (Anthropic પ્રોમ્પ્ટ કૅશિંગ, વગેરે)         |
| `totalTokens`      | number  | પ્રોમ્પ્ટ + કમ્પ્લીશન                                      |
| `costUsd`          | number  | કિંમતના ડેટા પરથી ગણતરી કરેલ                               |
| `latencyMs`        | number  | વિનંતીનો શરૂઆતથી અંત સુધીનો સમયગાળો                        |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | સ્થિતિ != success હોય તો ભૂલનો વર્ગ                        |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | પ્લગઇન દ્વારા ઉમેરાયેલ કસ્ટમ ડેટા                          |

### ટોકન્સ ક્યાંથી આવે છે

**પ્રતિસાદ હેન્ડલર**માં અપસ્ટ્રીમ પ્રદાતાના પ્રતિસાદમાંથી ટોકન્સ કાઢવામાં આવે છે:

```ts
// open-sse/handlers/chatCore.ts માંથી
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

જે પ્રદાતાઓ વપરાશ પરત કરતા નથી (કેટલાક વેબ-કુકી પ્રદાતાઓ), તેમના માટે OmniRoute `~4 chars per token` હ્યુરિસ્ટિકનો ઉપયોગ કરીને ટોકન્સનો **અંદાજ કાઢે છે** (`open-sse/services/autoCombo/pipelineRouter.ts` જુઓ).

### કૅશ કરેલા ટોકન્સ

OmniRoute `cached_tokens` ને `prompt_tokens` થી અલગ ટ્રૅક કરે છે કારણ કે:

- Anthropic પ્રોમ્પ્ટ કૅશિંગ કૅશ કરેલા ટોકન્સ માટે ઓછો દર વસૂલે છે (સામાન્ય દરના 10%)
- કેટલાક પ્રદાતાઓ `cache_read_input_tokens` પરત કરે છે, જેની કિંમત અલગ રીતે ગણવી જોઈએ
- એનાલિટિક્સ **કૅશ હિટ દર** = `cached_tokens / prompt_tokens` બતાવી શકે છે

### કૅશ-રાઇટ સ્તરનું નિદાન

એનાલિટિક્સ ડૅશબોર્ડની પ્રોમ્પ્ટ-કૅશ હેલ્થ પૅનલ પ્રદાતા દ્વારા નોંધાયેલા
5-મિનિટ અને 1-કલાકના કૅશ રાઇટ્સ વચ્ચે ભેદ પાડે છે. Anthropic ના
`usage.cache_creation.ephemeral_5m_input_tokens` અને
`usage.cache_creation.ephemeral_1h_input_tokens` સ્ટ્રીમિંગ અને
નોન-સ્ટ્રીમિંગ વપરાશ રૂપાંતરણ દરમિયાન જાળવી રાખવામાં આવે છે અને કૉલ-લૉગ સારાંશો સાથે સંગ્રહિત થાય છે. સંયુક્ત
કૅશ-રાઇટ કુલને તે બકેટ્સમાં બીજી વાર ઉમેરવામાં આવતું નથી.

જૂના રેકોર્ડ્સ સહિત, માત્ર સંયુક્ત રાઇટ કાઉન્ટર ધરાવતા કૉલ્સનું સ્તર અજ્ઞાત હોય છે.
આંશિક વિભાજનમાં ફાળવણી ન થયેલો બાકીનો ભાગ અજ્ઞાત જ રહે છે; અમાન્ય અથવા
પરસ્પર વિરોધી કાઉન્ટર્સને ચૂપચાપ TTL ફાળવવાને બદલે ચિહ્નિત કરવામાં આવે છે. વિનંતી-બાજુના
TTL માર્કર્સ બિલ કરાયેલા સ્તરનો પુરાવો નથી.

પૅનલનો API-સમકક્ષ રાઇટ અંદાજ માત્ર નોંધાયેલા, કિંમત ઉપલબ્ધ હોય તેવા સ્તરોને આવરી લે છે,
સમગ્ર વિનંતીને નહીં. મૂળ Claude/Anthropic મોડેલની કિંમત માટે તે
5-મિનિટના રાઇટ્સ માટે ઇનપુટ દરના 1.25 ગણા અને 1-કલાકના રાઇટ્સ માટે ઇનપુટ દરના બમણા દરનો ઉપયોગ કરે છે. કિંમત
ગેરહાજર હોય તો તે અનુપલબ્ધ ગણાય છે, શૂન્ય નહીં. દરેક નવો કૉલ લૉગ થાય ત્યારે કિંમતો નોંધવામાં આવે છે;
ઐતિહાસિક રેકોર્ડ્સની કિંમત ફરી ગણવામાં આવતી નથી. તેથી સબ્સ્ક્રિપ્શન એકાઉન્ટ્સ માટે
API-સમકક્ષ અંદાજ હોઈ શકે છે, છતાં તેટલી રકમનો રોકડ ખર્ચ કે સબ્સ્ક્રિપ્શન
ક્વોટાનો વપરાશ થતો નથી. હાલની ક્વોટા, બજેટ અને પ્રદાતા-ચોક્કસ ખર્ચની ગણતરીઓ યથાવત્ રહે છે.

આ નિદાન હાલના મર્યાદિત કૅશ-હેલ્થ સારાંશ અને કૉલ-લૉગ
જાળવણીનો ઉપયોગ કરે છે. તે વિનંતીના ડિફૉલ્ટ TTL, રૂટિંગ કે એકાઉન્ટ પસંદગીમાં ફેરફાર કરતા નથી.
પ્રદાતાને મોકલવાના બિંદુએ ક્લાયન્ટે વિનંતી કરેલા TTL સામે વાસ્તવમાં બહાર મોકલાતા TTL ને નોંધવાનું
મુલતવી રાખવામાં આવ્યું છે; આ પૅનલ રસીદમાં દર્શાવેલા સ્તરો જણાવે છે, વાસ્તવમાં બહાર મોકલાતો TTL નહીં.

અમલીકરણ: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts`, અને `open-sse/utils/cacheWriteUsage.ts`.

## ખર્ચની ગણતરી

ખર્ચની ગણતરી LiteLLMમાંથી સિંક કરાયેલા **કિંમત-નિર્ધારણ ડેટા** (`src/lib/pricingSync.ts`) પરથી કરવામાં આવે છે:

| મોડેલ             | ઇનપુટ $/1M | આઉટપુટ $/1M | કૅશ કરેલ $/1M |
| ----------------- | ---------- | ----------- | ------------- |
| gpt-5             | $2.50      | $10.00      | —             |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50         |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30         |
| gemini-2.5-pro    | $1.25      | $10.00      | —             |

ખર્ચનું સૂત્ર (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **પ્રોમ્પ્ટમાંથી કૅશ કરેલ ટોકન્સ શા માટે બાદ કરવામાં આવે છે?** કૅશ કરેલા ભાગની કિંમત અલગથી ગણવામાં આવે છે; સમગ્ર પ્રોમ્પ્ટ પર ઇનપુટ કિંમત વસૂલવાથી ખર્ચ વધારે ગણાઈ જશે.

### કિંમત-નિર્ધારણ સિંક

## તારીખ શ્રેણીનું એકત્રીકરણ

`usageAnalytics.ts` મોડ્યુલ કાચા વપરાશ ડેટામાંથી ડેશબોર્ડ વિજેટ્સની ગણતરી કરે છે. તે 7 સમય શ્રેણીઓને સમર્થન આપે છે:

| શ્રેણી   | સમયગાળો                               | ઉપયોગ                             |
| -------- | ------------------------------------- | --------------------------------- |
| `1d`     | છેલ્લા 24 કલાક                        | કલાકદીઠ ખર્ચમાં અચાનક વધારાની શોધ |
| `7d`     | છેલ્લા 7 દિવસ                         | સાપ્તાહિક સમીક્ષા                 |
| `30d`    | છેલ્લા 30 દિવસ                        | માસિક બિલિંગ                      |
| `90d`    | છેલ્લા 90 દિવસ                        | ત્રિમાસિક વિશ્લેષણ                |
| `ytd`    | ચાલુ વર્ષની 1 જાન્યુઆરીથી             | વાર્ષિક બજેટનું ટ્રેકિંગ          |
| `all`    | સમગ્ર સમય                             | સમગ્ર સમયગાળાના આંકડા             |
| `custom` | વપરાશકર્તા દ્વારા નિર્ધારિત શરૂઆત/અંત | ઓડિટ, તદર્થ ક્વેરીઓ               |

### ગણતરી કરવામાં આવતા ડેશબોર્ડ વિજેટ્સ

કોઈપણ તારીખ શ્રેણી માટે, એનાલિટિક્સ સ્તર નીચેની ગણતરી કરે છે:

| વિજેટ                      | વર્ણન                                                       |
| -------------------------- | ----------------------------------------------------------- |
| **સારાંશ કાર્ડ્સ**         | કુલ વિનંતીઓ, કુલ ખર્ચ, કુલ ટોકન્સ, સફળતાનો દર               |
| **દૈનિક વલણ ચાર્ટ**        | દિવસદીઠ ખર્ચ + ટોકન્સ, મોડેલ પ્રમાણે સ્તરોમાં ગોઠવેલ        |
| **પ્રવૃત્તિ હીટમેપ**       | દિવસનો કલાક × અઠવાડિયાનો દિવસ ગ્રીડ, રંગ = વિનંતીઓની સંખ્યા |
| **મોડેલ પ્રમાણે વિભાજન**   | મોડેલ પ્રમાણે ખર્ચનો પાઇ ચાર્ટ                              |
| **પ્રદાતા પ્રમાણે વિભાજન** | પ્રદાતા પ્રમાણે વિનંતીઓનો બાર ચાર્ટ                         |
| **ટોચની API કીઝ**          | ખર્ચ પ્રમાણે ટોચની 10 કીઝનું કોષ્ટક                         |
| **ભૂલ વિશ્લેષણ**           | સમય સાથે ભૂલનો દર, મુખ્ય ભૂલ વર્ગો                          |

### પ્રોગ્રામ દ્વારા ઍક્સેસ

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // વપરાશ ઇતિહાસના રેકોર્ડ્સ

    startDate: "2025-01-01",  // વૈકલ્પિક: "custom" શ્રેણી માટે

  }
);

console.log(analytics.summary.totalCost);   // 12.34 (સેન્ટ)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## ક્વોટાનો અમલ

દરેક API કી માટેનો ક્વોટા બે જગ્યાએ લાગુ કરવામાં આવે છે:

1. **નરમ મર્યાદા** (`quotaWarnAt`): વપરાશ નિર્ધારિત સીમા વટાવે ત્યારે ડેશબોર્ડ પર ચેતવણી
2. **કડક મર્યાદા** (`quotaLimit`): મર્યાદા વટાવે ત્યારે HTTP 429 સાથે વિનંતી નકારવામાં આવે છે

### ગોઠવણી

```ts
// દરેક API કી માટે
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — ચેતવણી બતાવો
  quotaLimit: 10_00,    // $10.00 — સંપૂર્ણ રોક
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### અમલનો પ્રવાહ

```
વિનંતી ──▶ quotaCheck()
              │
              ├── મર્યાદામાં છે?  ──▶ મંજૂરી આપો
              │
              └── મર્યાદાથી વધુ છે?  ──▶ 429 Too Many Requests
                                   Retry-After હેડર સાથે
```

### ક્વોટા સ્નૅપશૉટ્સ

`quotaSnapshots` કોષ્ટક વલણના વિશ્લેષણ માટે **ક્વોટાની ઐતિહાસિક સ્થિતિ** સંગ્રહે છે:

| ફીલ્ડ | વર્ણન |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | જે કીને ટ્રેક કરવામાં આવે છે |
| `window` | "day" | "week" | "month" |
| `used` | આ સમયગાળામાં વપરાયેલ ખર્ચ (સેન્ટ) |
| `limit` | મર્યાદા (સેન્ટ) |
| `resetAt` | સમયગાળો ક્યારે રીસેટ થાય છે |
| `createdAt` | સ્નૅપશૉટ ક્યારે લેવામાં આવ્યો હતો |

> 0 ખર્ચ કરતી **દરેક વિનંતી પર** સ્નૅપશૉટ્સ લેવામાં આવે છે, અને તેનો ઉપયોગ નીચેના માટે થાય છે:

- ડેશબોર્ડમાં ક્વોટાનો પ્રગતિ બાર દર્શાવવો
- 30-દિવસના ક્વોટા વલણ ચાર્ટ્સ બતાવવા
- વપરાશ મર્યાદાની નજીક પહોંચે ત્યારે ચેતવણીઓ સક્રિય કરવી

### સફાઈ


### 5. સૌથી વધુ વપરાશ કરનારાઓનું ઑડિટ કરો

API કી પ્રમાણે જૂથ બનાવવા અને ખર્ચ પ્રમાણે ગોઠવવા માટે ડૅશબોર્ડ અથવા **`/api/usage/analytics`** વાપરો:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

---

## સમસ્યાનિવારણ

### "ખર્ચ અપેક્ષા કરતાં વધારે છે"

1. **`/api/usage/analytics?groupBy=model`** તપાસો — મોંઘું મોડેલ શોધો
2. **`/api/usage/analytics?groupBy=apiKey`** તપાસો — વધુ વપરાશ કરનારને શોધો
3. કિંમત નિર્ધારણનો ડેટા અદ્યતન છે તેની ખાતરી કરો: `POST /api/pricing/sync`

### "રેકોર્ડ ગાયબ છે"

- ડૅશબોર્ડ → ડેટાબેઝ → સફાઈ હેઠળ DB રિટેન્શન સેટિંગ્સ તપાસો — સમયાંતરે ચાલતા સફાઈ કાર્ય દ્વારા જૂના રેકોર્ડ કાઢી નાખવામાં આવે છે (`src/lib/db/cleanup.ts`)
- `src/lib/db/usage*.ts` માં ભૂલો તપાસો — DB માં લખવાની નિષ્ફળતાઓ લૉગ થાય છે પરંતુ દર્શાવવામાં આવતી નથી
- વિનંતી ખરેખર `chatCore` સુધી પહોંચી હતી તેની ખાતરી કરો — કોમ્બો રૂટિંગ તપાસો

### "ક્વોટા લાગુ થતો નથી"

- કીની `quotaLimit` સેટિંગ તપાસો
- `quotaWindow` યોગ્ય રીતે સેટ કરેલું છે તેની ખાતરી કરો
- `quotaSnapshots` રેકોર્ડ શોધો — તે દરેક વિનંતી પર બનવા જોઈએ
