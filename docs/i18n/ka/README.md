## 💰 ~ 1.62B ჟეტონები / თვე მესამე მხარის უფასო დონეებზე

</div>

> **მოიყვანეთ თქვენი პროვაიდერის ანგარიშები.** ეს არის სავარაუდო აგრეგატი ცალ-ცალკე დასაშვები მესამე მხარის უფასო საფეხურებზე და არა OmniRoute ს სიმბოლური გრანტი. დარეგისტრირდით, მიიღეთ რწმუნებათა სიგელები საჭიროების შემთხვევაში და დაუკავშირდით პროვაიდერებს, რომელთა გამოყენებაც შეგიძლიათ; თითოეული პროვაიდერი აკონტროლებს მის ლიმიტებს, ხელმისაწვდომობას და პირობებს.
>
> უფასო იარუსების ხელით დაწყობა მტკივნეულია — ათობით SDKs, ათობით განაკვეთის ლიმიტი და წარმოდგენა არ გაქვთ რეალურად რამდენი გაქვთ. ## 📡 OmniRoute Radar

უფასო დონის მთავარი მაჩვენებელი კვლავ არის **~1.62B ტოკენი/თვეში**, ზემოთ მოცემული დოკუმენტირებული, პულების მიხედვით დუბლიკატებისგან გაწმენდილი კატალოგიდან. პროვაიდერთან რეგისტრაციის დროებით კრედიტებს შეუძლია, ცალკე, პირველი თვის მაჩვენებელი **~2.22B-მდე** გაზარდოს. Radar არის არასავალდებულო, ხელმოწერილი კატალოგის ზედნადები მათთვის, ვისაც OmniRoute-ის გამოშვებებს შორის უფასო მოდელების ხელმისაწვდომობის შესახებ უფრო ახალი ინფორმაცია სურს; საზოგადოების კატალოგი და ყველა არსებული უფასო ფუნქცია კვლავ უფასოა.

მხარდამჭერებს შეუძლიათ მიიღონ ცოცხალი კატალოგი და დამატებითი შესაძლებლობები პროვაიდერებისგან. მისი ცალკეული, ცვალებადი ზედა ზღვარი არის **მაქსიმუმ დაახლოებით 3B ტოკენი/თვეში**, პროვაიდერების ხელმისაწვდომობის მიხედვით. ეს ზედა ზღვარი გარანტირებული არ არის: პროვაიდერებს ნებისმიერ დროს შეუძლიათ შეცვალონ კვოტები, შესაბამისობის მოთხოვნები, მოდელები ან რეგიონები.

Radar-ში მონაწილეობა ნებაყოფლობითია და ის მხოლოდ GET-მოთხოვნებს იყენებს. OmniRoute-ის კლიენტი არ ტვირთავს მოთხოვნებს, ტრაფიკს, პროვაიდერის კონფიგურაციას, გამოყენების ტელემეტრიას ან განცხადებების დახურვის ლოკალურ მდგომარეობას. შესაბამისობის პირობებისა და მიმდინარე კატალოგის შესახებ იხილეთ **[radar.omniroute.online/planos](https://radar.omniroute.online/planos)**.

## 🗜️ დაზოგეთ ტოკენების 15–95% — ავტომატურად

### 📖 როგორ მუშაობს — პაიპლაინი, არქიტექტურა და დაზოგვის მათემატიკა

<img src="./docs/diagrams/compression-pipeline.svg" width="100%" alt="OmniRoute-ის შეკუმშვის პაიპლაინი: ილუსტრატიული 10 000-ტოკენიანი კლიენტის მოთხოვნა გადის 12 კომპონირებად ძრავზე — Session-Dedup, CCR, Lite, RTK, Responses Tool Output, Headroom, Relevance, Caveman, Aggressive, LLMLingua-2, Ultra და OmniGlyph — და დოკუმენტირებულ დაწყვილებულ მაგალითში პროვაიდერამდე დაახლოებით 1 080 ტოკენით მიდის. სტრუქტურირებული შინაარსი დაცულია შენარჩუნების დამცავებითა და ნაბიჯ-ნაბიჯ ერთგულების კარიბჭეებით; აშკარა დანაკარგიანი ან ექსპერიმენტული რეჟიმები შეიძლება გარდაქმნას შესაბამისი შინაარსი."/>

ნაგულისხმევი დაწყვილებული კომბო იყენებს `RTK → Caveman`-ს. როდესაც ორივე მოქმედებს ერთსა და იმავე ინსტრუმენტის/კონტექსტის მონაცემებზე, დაზოგვა ერთდება:

```txt
combined = 1 − (1 − RTK) × (1 − Caveman_input)
average  = 1 − (1 − 0.80) × (1 − 0.46) = 89.2%
range    = 78.4 – 94.6%
```

კოდის ბლოკები, URL-ები, JSON და სტრუქტურირებული მონაცემები შენარჩუნების ძრავის მიერ **ყოველთვის დაცულია**.

> **რატომ ვხარჯოთ ბევრი ტოკენი, როცა ცოტაც კმარა?** ყოველი მოთხოვნა OmniRoute-ის შეკუმშვის პაიპლაინს **გამჭვირვალედ** გადის — კლიენტში ცვლილებების გარეშე. ეს ახლა **12 კომპონირებადი ძრავის სტეკია**, რომელიც მიმდევრობით მუშაობს და თითოეული მარშრუტიზაციის კომბოსთვის ირჩევა და ირევა — იდეებით [RTK](https://github.com/rtk-ai/rtk), [Caveman](https://github.com/JuliusBrussee/caveman) (⭐ 90K+), [LLMLingua-2](https://github.com/microsoft/LLMLingua) და [Troglodita](https://github.com/leninejunior/troglodita) (PT-BR) პროექტებიდან.

**2) დააკავშირეთ შესაბამისი პროვაიდერი თქვენი საკუთარი ანგარიშის გამოყენებით**

`:latest` მიჰყვება ყველაზე მაღალ **გამოქვეყნებულ** სტაბილურ SemVer-ს. ის არ მიჰყვება git-ის `main` შტოს. GitOps-ისთვის გამოიყენეთ ფიქსირებული `:X.Y.Z`. იხილეთ [Docker-ის გამოშვების არხები](docs/guides/DOCKER_GUIDE.md#release-channels). იმიჯში ფიქსირებულია **`OMNIROUTE_MEMORY_MB=1024`**. ეს საკმარისია მართვის პანელისა და მსუბუქი ჩატისთვის. **კოდირების აგენტებს** (`POST /v1/responses` Claude Code-იდან, Codex-იდან, Grok-იდან, …) სჭირდებათ გაცილებით დიდი V8 heap, წინააღმდეგ შემთხვევაში ორი გადაფარული გრძელი კონტექსტის დროს პროცესი დაახლოებით 12 GiB-ზე `FATAL ERROR`-ით წყდება. კონტეინერის ზომა heap-ზე მეტი უნდა იყოს (ნატიური ბუფერები V8-ის გარეთაა განთავსებული):

| დატვირთვა                            | Heap (`-e OMNIROUTE_MEMORY_MB`)          | კონტეინერი (`--memory`) |
| ------------------------------------ | ---------------------------------------- | ----------------------- |
| მართვის პანელი / მსუბუქი ჩატი        | `1024` (იმიჯის ნაგულისხმევი მნიშვნელობა) | ≥2 g                    |
| ერთი კოდირების აგენტი                | `8192`                                   | ≥10 g                   |
| ორი ერთდროული გრძელი `/v1/responses` | `10240`–`12288`                          | ≥12–16 g                |

**🥟 Bun**

სტანდარტული `bun install` და გლობალური ინსტალაცია (`bun install -g omniroute`) მხარდაჭერილია Bun-ის გაშვების გარემოს ამოცნობის მეშვეობით:

- **ჩაშენებული `bun:sqlite`**: Bun-ის გარემოში მუშაობისას OmniRoute იყენებს Bun-ის ჩაშენებულ `bun:sqlite` დრაივერს, ხოლო Node.js-ზე — `better-sqlite3`-ს ან `sql.js`-ს.
- **Webpack-ის შემკვრელის ავტომატური არჩევა შემუშავებისას**: შემუშავების რეჟიმი (`bun run dev`) ავტომატურად ამოიცნობს Bun-ს და ნატიური V8-ის ბაინდინგებთან შეუთავსებლობის თავიდან ასაცილებლად Turbopack-ს თიშავს Webpack-ის სასარგებლოდ. საწარმოო აგებები (`bun run build`) `OMNIROUTE_USE_TURBOPACK`-ს ზუსტად ისევე მიჰყვება, როგორც Node-ზე: ნაგულისხმევად Turbopack, ხოლო Webpack-ით ასაგებად — `OMNIROUTE_USE_TURBOPACK=0` (`Dockerfile.bun` მას `--build-arg`-ის სახით წარმოადგენს).
- **Bun-ისთვის განკუთვნილი Dockerfile**: მრავალეტაპიანი `Dockerfile.bun` Bun-ის ნატიური საწარმოო განთავსებებისთვის (`docker build -f Dockerfile.bun -t omniroute:bun .`).

**⚡ უფრო სწრაფი / მსუბუქი ინსტალაცია (ნატიური აგების გამოტოვებით)**

ნატიური SQLite ძრავა (`better-sqlite3`) **არასავალდებულო** დამოკიდებულებაა, ამიტომ გლობალური
ინსტალაცია საწყისი კოდიდან კომპილირების გამო არასდროს ფერხდება: როდესაც თქვენი
პლატფორმისა და Node-ისთვის შესაფერისი წინასწარ აგებული ბინარული ფაილი არსებობს, ის გამოიყენება,
წინააღმდეგ შემთხვევაში კი სისტემა შეუმჩნევლად გადადის სუფთა JS ძრავაზე
(`node:sqlite` Node 22+-ზე, სხვა შემთხვევაში კი პაკეტში ჩართულ `sql.js` WASM-ზე) — აგების ხელსაწყოები საჭირო არ არის.

ინსტალაციის შემდგომი **ნატიური წინასწარი გახურების** სრულად გამოსატოვებლად (CI, უთავო ან ნელი მანქანები).
შენიშვნა: ეს გამოტოვებს მხოლოდ ნატიური SQLite-ის წინასწარი გახურების ეტაპს (`scripts/postinstall.mjs`);
ბინარული ფაილის კოპირების/აღდგენის ჰუკი (`scripts/build/postinstall.mjs`) კვლავ ჩვეულებრივ შესრულდება:

```bash
OMNIROUTE_SKIP_POSTINSTALL=1 npm install -g omniroute   # CI=1-იც გამოტოვებს მას
```

ყველაზე სწრაფი ინსტალაციისთვის უპირატესობა მიანიჭეთ **pnpm**-ს (შიგთავსით მისამართებადი საცავი + მყარი ბმულები — იხილეთ ზემოთ).
მართვის პანელის გარეშე, უთავო გაშვების გარემოსთვის გამოიყენეთ Docker-ის `base` პროფილი (ზემოთ) ან
[Termux-ის სახელმძღვანელო](docs/guides/TERMUX_GUIDE.md). CLI-სა და ვებმართვის პანელს ერთი და იგივე
