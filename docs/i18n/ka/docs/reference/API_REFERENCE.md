OmniRoute API-ის ძირითადი საცნობარო დოკუმენტაცია. იგი მოიცავს საჯარო `/v1` ზედაპირსა და ყველაზე ხშირად გამოყენებულ მართვის საბოლოო წერტილებს; მანქანურად წაკითხვადი [`docs/openapi.yaml`](../openapi.yaml) და `src/app/api/`-ის ქვეშ მდებარე მარშრუტების ხე წარმოადგენს ამომწურავ წყაროებს.

OpenAI-თან თავსებადი პროტოკოლისა და პროვაიდერების შესაძლებლობების ორიენტირებული მატრიცისთვის იხილეთ
[`OPENAI_COMPATIBILITY.md`](./OPENAI_COMPATIBILITY.md).

თითოეული განთავსება სპეციფიკაციის საკუთარ ასლს `/openapi.yaml`-ზე აწვდის, რომელიც აგების პროცესში `docs/openapi.yaml`-იდან გენერირდება. იგი შეიცავს აგების ვერსიასა და ფარდობით სერვერის URL-ს (`./`), ამიტომ მოთხოვნები რჩება იმ ჰოსტზე, რომელმაც დოკუმენტი მოაწოდა. ჩამოტვირთული ფაილის იმპორტირების ხელსაწყოს ასეთი ჰოსტი არ აქვს და საბაზისო URL-ის ხელით მითითება სჭირდება.

## ჩატის დასრულებები

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### მორგებული ჰედერები

| Header                   | Direction | Description                                                                                                                                                                                                                                   |
| ------------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | მოთხოვნა  | დააყენეთ `true` მნიშვნელობა ქეშის გვერდის ასავლელად                                                                                                                                                                                           |
| `x-omniroute-no-memory`  | მოთხოვნა  | დააყენეთ `true` მნიშვნელობა ამ მოთხოვნისთვის მეხსიერებისა და უნარების ინექციის გამოსატოვებლად (ასახავს no-cache-ს; თავიდან იცილებს თითოეულ გამოძახებაზე ტოკენებისა და ხარჯების ზედნადებს)                                                     |
| `X-OmniRoute-Progress`   | მოთხოვნა  | პროგრესის მოვლენებისთვის დააყენეთ `true`                                                                                                                                                                                                      |
| `X-Session-Id`           | მოთხოვნა  | გარე სესიის აფინიტეტისთვის განკუთვნილი წებოვანი სესიის გასაღები                                                                                                                                                                               |
| `x_session_id`           | მოთხოვნა  | ქვედა ტირის შემცველი ვარიანტიც მიიღება (პირდაპირი HTTP)                                                                                                                                                                                       |
| `X-OmniRoute-Session-Id` | მოთხოვნა  | გამომძახებლის მიერ მიწოდებული სესიის/საუბრის ტეგი (ასევე მიეწოდება მეხსიერებას). არსებობის შემთხვევაში პირდაპირ უცვლელად ინახება `call_logs.session_tag`-ში სესიების მიხედვით ხარჯების ატრიბუციისთვის (#8249) — არ სინთეზდება, თუ არ არსებობს |
| `Idempotency-Key`        | მოთხოვნა  | დუბლირების აღმოსაფხვრელი გასაღები (5-წამიანი ფანჯარა)                                                                                                                                                                                         |
| `X-Request-Id`           | მოთხოვნა  | დუბლირების აღმოსაფხვრელი ალტერნატიული გასაღები                                                                                                                                                                                                |
| `x-omniroute-connection` | მოთხოვნა  | ერთმოდელიანი მოთხოვნის ერთ პროვაიდერის კავშირზე (ანგარიშზე) მიბმა მისი ID-ის მიხედვით — იხილეთ [მოთხოვნის მიხედვით ანგარიშზე მიბმა](#account-pinning-per-request)                                                                             |
| `X-OmniRoute-Cache`      | პასუხი    | `HIT` ან `MISS` (არასტრიმინგული)                                                                                                                                                                                                              |
| `X-OmniRoute-Idempotent` | პასუხი    | `true`, თუ დუბლირება აღმოიფხვრა                                                                                                                                                                                                               |
| `X-OmniRoute-Progress`   | პასუხი    | `enabled`, თუ პროგრესის თვალყურის დევნება ჩართულია                                                                                                                                                                                            |
| `X-OmniRoute-Session-Id` | პასუხი    | OmniRoute-ის მიერ გამოყენებული ეფექტური სესიის ID                                                                                                                                                                                             |
| `X-OmniRoute-Request-Id` | პასუხი    | მოთხოვნის კორელაციის ID (თუ ცნობილია)                                                                                                                                                                                                         |
| `X-OmniRoute-Version`    | პასუხი    | OmniRoute-ის ბილდის ვერსია (ყოველთვის წარმოდგენილია)                                                                                                                                                                                          |
| `X-OmniRoute-Cost-Saved` | პასუხი    | აშშ დოლარში გამოხატული თანხა, რომელიც ქეშმა დაზოგა HIT-ის შემთხვევაში (მხოლოდ ქეშის HIT-ებისთვის)                                                                                                                                             |
| `X-OmniRoute-Decision`   | პასუხი    | მარშრუტიზაციის კვალი: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` არის კომბინირებული სტრატეგია, ან `single` არაკომბინირებული მოთხოვნისთვის) — დასრულების პასუხებზე ყოველთვის წარმოდგენილია                                  |

> Nginx-ის შენიშვნა: თუ ეყრდნობით ქვედა ტირის შემცველ სათაურებს (მაგალითად, `x_session_id`), ჩართეთ `underscores_in_headers on;`.

#### მოთხოვნის მიხედვით ანგარიშზე მიბმა

როდესაც პროვაიდერს რამდენიმე კავშირი აქვს (ანგარიში ან გასაღები), OmniRoute ჩვეულებრივ ერთ-ერთს ანგარიშების არჩევის სტრატეგიის
მეშვეობით ირჩევს. ამის ნაცვლად, მოთხოვნას შეუძლია ერთი კონკრეტული კავშირი მიამაგროს `x-omniroute-connection` სათაურის
გამოყენებით:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **სად ვიპოვოთ ID.** გახსენით პროვაიდერის გვერდი dashboard-ში
  (**Dashboard → Providers → <provider>**) და კავშირის მწკრივში დააწკაპუნეთ `xxxxxxxx…` ID-ის ჩიპზე —
  ეს კავშირის სრულ ID-ს დააკოპირებს.
- **რომელი მოთხოვნები ითვალისწინებს მას.** ერთმოდელიანი მოთხოვნები (`provider/model`)
  `/v1/chat/completions`, `/v1/messages` და `/v1/responses` მისამართებზე. კომბინაციები ჰედერს
  უგულებელყოფს: თითოეული კომბინაციის ნაბიჯისთვის ანგარიში დაამაგრეთ უშუალოდ ამ ნაბიჯის კავშირის მეშვეობით.
- **დამაგრება მკაცრია და არა უბრალოდ პრეფერენცია.** დამაგრებული კავშირი გამოიყენება მხოლოდ.
  მოთხოვნის შიგნით წარმოქმნილი შეცდომა ანგარიშის cooldown-ს აფიქსირებს, მაგრამ იმავე პროვაიდერის
  მეზობელ ანგარიშზე გადართვას **არ** იწვევს.
- **Cooldown და კვოტა ხსნის დამაგრებას.** სანამ დამაგრებული კავშირი cooldown-ის მდგომარეობაშია,
  კვოტა ამოწურულია ან კვოტის პოლიტიკით დაბლოკილია, შემდგომი მოთხოვნები გადაერთვება პროვაიდერის
  სხვა კავშირებზე, ზუსტად ისე, როგორც დაუმაგრებელი ტრაფიკი.
- **უცნობი ან გამორთული ID-ები შეცდომას იწვევს.** ID, რომელიც პროვაიდერის აქტიურ პულში არ
  არის (წაშლილია, დეაქტივირებულია ან სხვა პროვაიდერს ეკუთვნის), ხელმისაწვდომ ანგარიშს აღარ ტოვებს,
  ამიტომ მოთხოვნა ჩავარდება და სხვა მიმართულებით ჩუმად არ გადაიგზავნება.

Claude Code მორგებულ ჰედერებს `ANTHROPIC_CUSTOM_HEADERS`-ის მეშვეობით აგზავნის. დაამატეთ ის
`~/.claude/settings.json`-ის `env` ბლოკში, ან პროექტის დონის `.claude/settings.json`-ში, რათა
თითოეული პროექტისთვის განსხვავებული ანგარიში დაამაგროთ:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

წყარო: `src/sse/handlers/chat.ts` (ჰედერის წაკითხვა), `src/sse/services/auth.ts` და
`src/sse/services/sessionAffinityPin.ts` (დამაგრების გათავისუფლება და პულში არყოფნის შემოწმება).

> **ღირებულების ტელემეტრიის ჰედერები:** არასტრმინგული წარმატებული პასუხები ასევე შეიცავს `X-OmniRoute-*` ღირებულების ტელემეტრიის ნაკრებს — `X-OmniRoute-Response-Cost` (USD, ფიქსირებული 10 ათობითი ნიშნით; `0.0000000000` უფასო/დაუფასებელი შემთხვევებისთვის), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` და `X-OmniRoute-Fallback-Attempts` (მხოლოდ მაშინ, როცა > 0), ასევე `X-OmniRoute-Request-Id` და `X-OmniRoute-Version`. ისინი გამოიცემა chat completions-ის, `/v1/responses`, `/v1/messages` **და მედიის endpoint-ების** მიერ — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` და `/v1/moderations` (ღირებულება ყოველთვის `0`). მედიის ღირებულება გამოითვლება თითოეული მოდალობის მიხედვით (თითოეულ გამოსახულებაზე, წამზე, სიმბოლოზე, საძიებო ერთეულზე), როცა ფასები ხელმისაწვდომია; წინააღმდეგ შემთხვევაში არის `0` (fail-open).

> **Cache-hit-ის ღირებულების სემანტიკა:** semantic-cache HIT-ის დროს (`X-OmniRoute-Cache-Hit: true`) upstream გამოძახება არ ხდება, ამიტომ `X-OmniRoute-Response-Cost` არის `0.0000000000` (HIT-ის მოწოდების **ინკრემენტული** ღირებულება). თავდაპირველი/სავარაუდო ღირებულება ცალკე აისახება `X-OmniRoute-Cost-Saved`-ში. ბილინგის მომხმარებლებმა უნდა დააჯამონ `X-OmniRoute-Response-Cost` (HIT-ები არაფერს ღირს); cache-ის ანალიტიკას კი შეუძლია `X-OmniRoute-Cost-Saved`-ის აგრეგირება.

## ექსკლუზიური მართული სესიის ლიზინგი

ექსკლუზიური მართული სესიის ლიზინგი არჩევითი, კლიენტისგან დამოუკიდებელი მარშრუტიზაციის კონტრაქტია: ერთი აქტიური მფლობელი ფლობს ერთ შესაბამის OmniRoute კავშირს. ის არ აქირავებს მოდელს, არ საჭიროებს OAuth-ს, არ განსაზღვრავს კონკრეტულ კლიენტს და არ მოითხოვს კონკრეტულ პროვაიდერს.

ავთენტიფიკაციის API გასაღებს უნდა ჰქონდეს `lease:exclusive` scope და მკაფიო, არაცარიელი `allowedConnections` სია. მონაცემთა ბაზის მუტაციის საზღვარი ორივე ველის ერთად არსებობას ამოწმებს გასაღების შექმნისა და ნაწილობრივი განახლებებისას.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

წარმატებული acquire, renew და release პასუხები ავლენს დროის ნიშნულებს, `state`-ს და ზუსტ დადებით `generation`-ს, მაგრამ არასოდეს ავლენს არჩეულ კავშირს ან ავტორიზაციის მონაცემებს. Renew და release `generation`-ს JSON სხეულში აგზავნის:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

აქტიური ლიზინგის მფლობელს შეუძლია თავისი მიმდინარე მიბმისთვის კონფიდენციალურობის დამცავი ჩვენების მეტამონაცემები ცალსახად მოითხოვოს:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

ეს არჩევითი სტატუსის მოქმედება ერთ მონაცემთა ბაზის ტრანზაქციაში მოწმდება გაუმჭვირვალე მფლობელის, ავთენტიფიცირებული მართული API გასაღებისა და ზუსტი აქტიური `generation`-ის მიხედვით. `displayName` მხოლოდ კონფიგურირებული კავშირის სახელია, რომელსაც ზედმეტი ცარიელი სიმბოლოები მოცილებული აქვს; ის არის `null`, როდესაც უსაფრთხო კონფიგურირებული სახელი არ არსებობს. OmniRoute არასოდეს ანაცვლებს მას ელფოსტით ან გენერირებული ანგარიშის იდენტობით. პროვაიდერის მნიშვნელობა არასენსიტიური საჩვენებელი იარლიყია და არასოდეს წარმოადგენს გენერირებულ თავსებად-პროვაიდერის იდენტიფიკატორს. გამოირიცხება ავტორიზაციის მონაცემები, ტოკენები, cookie-ები, დაუმუშავებელი კავშირის ან API გასაღების იდენტიფიკატორები, მფლობელების ჰეშები, ფენცინგის საიდუმლოებები და შიდა მარშრუტიზაციის მონაცემები.

არასწორი გასაღების, არასწორი მფლობელის, მოძველებული generation-ის, არმოძებნის, ვადის გასვლის, გათავისუფლებისა და ინვალიდაციის შემთხვევებში ყველა ძიება აბრუნებს ერთსა და იმავე `409 LEASE_FENCE_STALE` შეცდომას კავშირის მეტამონაცემების გარეშე. კლიენტს, რომელმაც capacity-wait პასუხი მიიღო, შესამოწმებელი აქტიური მიბმა არ გააჩნია. როდესაც მარშრუტიზაცია აქტიურ ლიზინგს გარდაქმნის, იგივე generation ძალაში რჩება და სტატუსი ატომურად აბრუნებს ახალ მიბმას, არასოდეს ძველს. არსებული კლიენტები უცვლელი რჩებიან, რადგან acquire, renew, release და ლოდინის პასუხები თავიანთ წინა ფორმებს ინარჩუნებს.

ეს სერვერული კონტრაქტი არ ცვლის სტანდარტულ OpenAI Codex `/status`-ს. ამჟამად სტანდარტული Codex აცნობებს თავისი მოდელის პროვაიდერსა და ჩაშენებულ ავთენტიფიკაციის/ანგარიშის მდგომარეობას, მაგრამ არ აჩვენებს თვითნებური მორგებული პროვაიდერის ანგარიშის მეტამონაცემებს; კლიენტის შემდგომმა ინტეგრაციამ უნდა გამოიძახოს ეს მოქმედება და თავად გადაწყვიტოს, როგორ აჩვენოს `connection.displayName`.

ყოველი მართული ინფერენსის მოთხოვნა შემდეგ ორივე საკონტროლო თავსართს აგზავნის:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ზუსტი მფლობელის, generation-ის, აქტიური კავშირისა და ავთენტიფიცირებული API გასაღების შესაბამისობა მოწმდება დაუყოვნებლივ ყოველი მხარდაჭერილი upstream მცდელობის წინ. მფლობელისა და generation-ის სხვა გასაღებით გამეორება ვერ მოხდება, მაშინაც კი, თუ ამ გასაღებს იგივე კავშირის გამოყენების უფლება აქვს. დაუმუშავებელი მფლობელები არ ინახება, არ ლოგირდება, არ ნარჩუნდება მოთხოვნის snapshot-ში და upstream-ზე არ გადაიგზავნება.

დროებითი კონკურენცია აბრუნებს HTTP `429`-ს `Retry-After`-თან ერთად და:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

ეს პასუხი მხოლოდ იმას ნიშნავს, რომ ჩვეულებრივი შესაბამისი ნაკრები ცარიელი არ იყო და ყოველი თავისუფალი კანდიდატი უცხო აქტიურ ლიზინგს ეკავა. მხარდაუჭერელი მოდელები/პროვაიდერები, პოლიტიკის შეუსაბამობა, cooldown, კვოტა, ჯანმრთელობის მდგომარეობა და შესაბამისობის სხვა ჩვეულებრივი წარუმატებლობები ინარჩუნებს OmniRoute-ის არსებულ პასუხებს.

### `x-omniroute-compression`

მოთხოვნის მიხედვით compression გეგმის გადაფარვა. უმაღლესი პრიორიტეტი — უპირატესობას ანიჭებს routing-combo-ის გადაფარვას, აქტიურ პროფილს, auto-trigger-სა და პანელის Default-ს. მნიშვნელობები:

| Value         | Effect                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------ |
| `off`         | ამ მოთხოვნისთვის compression არ გამოიყენება.                                                     |
| `default`     | პანელიდან მიღებული Default პროფილი (აქტიურ პროფილს უგულებელყოფს). Lossy ძრავები გამორთულია.      |
| `safe`        | მხოლოდ Dedup და whitespace folding.                                                              |
| `allow-lossy` | ამ მოთხოვნისთვის ოპერატორის გეგმა ნარჩუნდება, შეჯამებებისა და სტილის rewrite-ების ჩათვლით.       |
| `engine:<id>` | ერთი ძრავა, როდესაც ის ჩართულია, მაგალითად `engine:rtk`. ამ ძრავისთვის თითო მოთხოვნაზე opt-in.   |
| `<combo>`     | დასახელებული combo, რომელიც ჯერ სახელით (რეგისტრის გაუთვალისწინებლად), შემდეგ კი id-ით იძებნება. |

შენიშვნები:

- უცნობი მნიშვნელობები იგნორირდება (მოთხოვნა არასოდეს უარყოფილა); გადაწყვეტა ჩვეულებრივი ოპერატორის პრიორიტეტების მიხედვით გრძელდება.
- თუ რამდენიმე combo-ს ერთი და იგივე სახელი აქვს, დეტერმინისტული დამთხვევისთვის მიუთითეთ combo **id**.
- combo, რომლის სახელია `off` ან `default`, სახელით ვერ შეირჩევა (ეს საკვანძო სიტყვები ჯერ ინტერპრეტირდება); ასეთ combo-ს მიმართეთ მისი id-ით.
- compression-ის მთავარი გადამრთველი მკაცრი ბარიერია: როდესაც compression გლობალურად გამორთულია, ეს თავსართი მის ჩართვას ვერ შეძლებს.

გამოყენებული გეგმა პასუხის თავსართში ბრუნდება:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

სადაც `<source>`-ის ერთ-ერთი მნიშვნელობაა `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ან `off`.

## ემბედინგები

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"

```

ხელმისაწვდომი პროვაიდერები: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

კატალოგის იდენტიფიკატორებია `provider/model` (მაგალითი: `jina-ai/jina-embeddings-v5-omni-small`). რეესტრში არსებული Jina-ს მოდელების შიშველი იდენტიფიკატორებიც (მაგალითად, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ასევე განისაზღვრება. Jina-ს embed/rerank/classify/segment იყენებს dashboard-ის `jina-ai` ავტორიზაციის მონაცემებს პირველ რიგში; `JINA_AI_API_KEY` გამოიყენება მხოლოდ მაშინ, როდესაც dashboard-ის გასაღები არ არსებობს. `jina-reader` ბარათი განკუთვნილია მხოლოდ Reader / `r.jina.ai`-სთვის (`POST /v1/web/fetch`) და არასოდეს ემსახურება embeddings-ს ან rerank-ს.

რეესტრის მოდელები, რომლებიც მულტიმოდალურ მხარდაჭერას აცხადებენ, ასევე იღებენ მაქსიმუმ 32 პროვაიდერისგან დამოუკიდებელ სტრუქტურირებულ ელემენტს. მედიის ელემენტების ტიპებია `text`, `image`, `audio`, `video` და `document`. მათი მედიის `source` არის ან `{"type":"url","url":"https://..."}`, ან `{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano` და ოჯახის ფსევდონიმი `jina-ai/jina-embeddings-v5-omni` → omni-small) ასევე იღებს Jina-ს მშობლიურ EmbeddingsV5Request დოკუმენტაციას და **უცვლელად გადაამისამართებს** მას `https://api.jina.ai/v1/embeddings`-ზე:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

მშობლიური `{ image | audio | video | pdf }` მნიშვნელობები შეიძლება იყოს საჯარო HTTPS URL, `data:` URI ან დაუმუშავებელი base64. OmniRoute არ გარდაქმნის ამ ობიექტებს სტრიქონებად და არ ჩამოტვირთავს მშობლიურ image URL-ებს — Jina თავად იღებს საჯარო მედიას. Jina-ს დამატებითი ველები (`task`, `normalized`, `truncate`, `embedding_type`) გადამისამართდება. მხოლოდ ტექსტზე მომუშავე Jina SKU-ები კვლავ უარყოფენ არატექსტურ დოკუმენტებს.

უსაფრთხოებისა და ტრანსპორტის შეზღუდვები:

- დისტანციური მედიის URL-ები საჯარო HTTPS უნდა იყოს. კანონიკური `{type,source:url}` ელემენტები სერვერის მხარეს იტვირთება (გადამისამართების ხელახალი ვალიდაცია, ტაიმაუტი, ზომის ლიმიტები, საჯარო DNS, კავშირის მიბმა) და პროვაიდერთან გამოძახებამდე ინლაინდება. Jina-ს მშობლიური `{image:"https://..."}` ელემენტები იმავე საჯარო-HTTPS შემოწმების შემდეგ უცვლელად გადამისამართდება; URL-ს Jina იღებს.
- ინლაინ base64 მედია თითოეულ ელემენტზე შემოიფარგლება 8 MiB დეკოდირებული მონაცემით, ხოლო მთელ მოთხოვნაზე — 16 MiB დეკოდირებული მონაცემით.

პროვაიდერისთვის გარდაქმნა (კანონიკური ელემენტები უცვლელად არასოდეს გადამისამართდება):

- Jina-ს მულტიმოდალური მოდელები: ყოველი ზედა დონის ელემენტი გარდაიქმნება ერთ მოდალობაზე დაფუძნებულ ობიექტად (`text` / `image` / `audio` / `video` / `pdf`), ინლაინ მედიისთვის data URI-ების გამოყენებით; თითო ზედა დონის ელემენტზე იქმნება ერთი ვექტორი.
- Gemini Embedding 2-ის ოჯახი: ერთი ზედა დონის მასივი გარდაიქმნება ერთ მშობლიურ `models/{model}:embedContent` მოთხოვნად `content.parts`-ით (`text` ან `inline_data`).
- llama.cpp (`llama-cpp/<model>`, ნებისმიერი მოდელი, რომელიც ლოკალურმა სერვერმა ჩატვირთა): კანონიკური `text` ელემენტები გარდაიქმნება უბრალო სტრიქონებად, ხოლო `image` / `audio` / `video` გარდაიქმნება თითო `{"content": [part]}` ობიექტად, llama-server-ის ჩატის კონტენტის ნაწილების გამოყენებით (`image_url`, `input_audio` ფორმატებით `wav` / `mp3` / `flac`, `input_video`) და ინლაინ მონაცემებით; თითო ზედა დონის ელემენტზე იქმნება ერთი ვექტორი. სერვერი უნდა გაეშვას `--embedding --mmproj …` პარამეტრებით; პროექტორის გარეშე ის თავად უარყოფს მედიას. `document` მხარდაჭერილი არ არის.
- უცნობი/დინამიკური მოდელები, რომლებსაც მოდალობის შესახებ მკაფიო მეტამონაცემები არ აქვთ, სტრუქტურირებულ შეყვანას HTTP 400 შეცდომით უარყოფენ.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
```

მოდელისა და მოდალობის მხარდაუჭერელი კომბინაციები აბრუნებს HTTP 400-ს ელემენტის იძულებითი გარდაქმნის ნაცვლად. ძველი string/token მოთხოვნების არასაიმპუტო გაფართოების ველები კვლავ უცვლელად გადაეცემა.

## გამოსახულების გენერაცია

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ხელმისაწვდომი პროვაიდერები მოიცავს OpenAI (GPT სურათი 2), xAI (Grok სურათი), Together AI (FLUX), Fireworks AI, ნებიუსი (FLUX), ჰიპერბოლური, NanoBanana,**OpenRouter** ,**ZenMux** , SD WebUI (ადგილობრივი), ComfyUI (ადგილობრივი).

`n` აბრუნებს `n` სურათებს `data[]` ში. პროვაიდერები, რომელთა ზემოთ API აბრუნებს ერთ სურათს თითო ზარზე (Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik, NVIDIA NIM, Cloudflare Workers AI) იღებენ `n` ცალკეულ ზედა დინების ზარებს, მაქსიმუმ 4 ფრენის დროს. ფიქსირებული `seed` ოფსეტურია ზარის ინდექსით (`seed`, `seed + 1`,…), ასე რომ, სურათები განსხვავდება, მაგრამ რჩება რეპროდუცირებადი. `n` დახურულია 10-ზე. მოთხოვნა მთლიანად ვერ ხერხდება, თუ რომელიმე ზარი ვერ მოხერხდა. fan-out ფორმატების სია არის `SINGLE_IMAGE_FANOUT_FORMATS` in `open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux ხელახლა იყენებს არსებულ API-გასაღების კავშირს და იღებს `zenmux/` ან `zm/` პრეფიქსებს:

- `zenmux/openai/gpt-image-2` იყენებს ZenMux- ის OpenAI სურათებს API. ვარიანტები მოიცავს `size`, `quality`, `n`, `output_format`, `output_compression`, `background` და `response_format`.
- სხვა გამომცემლები, როგორიცაა `zm/meta/muse-image-1.0`, იყენებენ ZenMux ის Vertex AI `:predict` ბოლო წერტილს. `n` რუკები `sampleCount`, `aspect_ratio` `aspectRatio` ზე და `image_size` (`1K`, `2K`, `4K`) `sampleImageSize` ზე. პიქსელი `size` აწვდის მხოლოდ ასპექტის თანაფარდობას და არ არის გარანტირებული პიქსელის ზომები. მხარდაჭერილი კოეფიციენტები, გარჩევადობა და რაოდენობა განსხვავდება მოდელის მიხედვით.
- `zm/inclusionai/ming-image-0.1-design` ირჩევს საკუთარ ზომებს. გამოტოვეთ `size`, `aspect_ratio` და `image_size`; გამოკვეთილი მნიშვნელობები აბრუნებს HTTP 400-ს. PNG, JPEG და WebP შეიძლება მოითხოვოს `output_format` ით.

ეს ინტეგრაცია მხარს უჭერს ტექსტის გამოსახულების გენერირებას და არა მიმართვის გამოსახულების რედაქტირებას. Vertex გამომავალი ნორმალიზებულია `data[].b64_json` მდე; `response_format: "url"` აბრუნებს ზედა დინების HTTPS URL ან base64 მონაცემთა URL როდესაც ხელმისაწვდომია მხოლოდ სურათის ბაიტი. Empty/filtered გამომავალი აბრუნებს შეცდომას და არა ცარიელ წარმატებას. მოდელის წვდომა დამოკიდებულია ZenMux ანგარიშზე. იხილეთ [ZenMux- ს Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) და [OpenAI სურათები API](https://docs.zenmux.ai/api/openai/generate-an-image).

Microsoft 365 Copilot შესვლის კავშირი ემსახურება `copilot-m365-web/m365-copilot-image` Copilot ის ჩაშენებული გამოსახულების ხელსაწყოს მეშვეობით: თითო Copilot შემობრუნება თითო სურათზე (`n` 1–4), `size` მართავს მხოლოდ ორიენტაციას და სურათები დაბრუნებული inline (`b64_json`, ან მონაცემები URL `response_format: "url"` სთვის). იხილეთ [Microsoft 365 Copilot](../providers/COPILOT-M365.md#image-generation).


(`open-sse/config/ocrRegistry.ts`):

| პროვაიდერის ID                | მოდელის ID           | `model` მნიშვნელობა                                           | შენიშვნები                                                                                                                           |
| ----------------------------- | -------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (ან მხოლოდ `mistral-ocr-latest`) | სინქრონული — პასუხი პირდაპირ ერთი upstream გამოძახებიდან ბრუნდება.                                                                   |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                   | ასინქრონული upstream (`analyze` + poll) — იხილეთ ქვემოთ.                                                                             |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                       | სინქრონული, Vertex AI-ის `openapi/chat/completions` პარტნიორი endpoint-ის მეშვეობით — ავტორიზაციისა და URL-ის შესახებ იხილეთ ქვემოთ. |

### Azure Document Intelligence-ის polling-ის ნაკადი

Azure Document Intelligence-ის `analyze` API ასინქრონულია: საწყისი მოთხოვნა სხეულის ნაცვლად
აბრუნებს `Operation-Location` header-ს და შედეგის მისაღებად საჭიროა polling. დამმუშავებელი
(`open-sse/handlers/ocr.ts`) ამ URL-ს ყოველ წამს ამოწმებს, მაქსიმუმ 30 მცდელობის განმავლობაში;
ის დაუყოვნებლივ წყვეტს მუშაობას (polling-ს აღარ აგრძელებს), თუ poll-ის პასუხს არ აქვს `ok`
მნიშვნელობა ან სტატუსია `"failed"`, ხოლო `504`-ს აბრუნებს, თუ მცდელობებისთვის გამოყოფილი
ლიმიტის ამოწურვის შემდეგ ოპერაცია კვლავ მიმდინარეობს. საბოლოო Azure პასუხი დაბრუნებამდე
ნორმალიზდება იმავე `pages`/`markdown` ფორმატში, რომელსაც Mistral იყენებს, ამიტომ კლიენტის
კოდს არ სჭირდება პროვაიდერის მიხედვით სპეციალური დამუშავება.

### Vertex AI DeepSeek OCR-ის ავტორიზაცია და endpoint-ის განსაზღვრა

`vertex-deepseek-ocr` ხელახლა იყენებს იმავე Vertex AI-ის ავტორიზაციას, რომელსაც OmniRoute
უკვე უჭერს მხარს ჩატისა და გამოსახულებების ტრაფიკისთვის
(`open-sse/executors/vertex.ts`): კავშირის API-გასაღები ან Service Account JSON
ავტორიზაციის მონაცემებია (რომლებიც JWT-bearer ნაკადის მეშვეობით მოკლევადიან OAuth წვდომის
ტოკენად იცვლება), ან უკვე გაცემული OAuth წვდომის ტოკენია, რომელიც პირდაპირ გამოიყენება.
Upstream endpoint URL არის Vertex-ის ზოგადი `openapi/chat/completions` პარტნიორი endpoint,
რომელიც კავშირის პროექტისა და რეგიონის მიხედვით იგება — მკაფიოდ მითითებული
`providerSpecificData.project`/`providerSpecificData.region` ყოველთვის უპირატესია;
წინააღმდეგ შემთხვევაში პროექტი მიიღება Service Account JSON-ის `project_id`-დან, ხოლო
რეგიონად ნაგულისხმევად გამოიყენება `us-central1`. ორივე განსაზღვრა ხდება
`open-sse/handlers/ocr.ts`-ში
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), ხოლო მათი გამოყენება ხდება
`src/app/api/v1/ocr/route.ts`-ში, `handleOcr`-ზე გადაცემამდე.

### მოდელის ფასები (`pricing`)

ჩანაწერი შეიცავს `pricing` ობიექტს, როდესაც OmniRoute-მა იცის მოდელის ფასი. ფასი აღებულია
ფასების ცხრილიდან, რომელსაც ხარჯების აღრიცხვა იყენებს: ჩაშენებული ნაგულისხმევი მნიშვნელობები,
სინქრონიზებული ფასები და `/api/pricing`-ის მეშვეობით დაყენებული გადაფარვები. ეს არის საჯარო
ფასები, ამიტომ გამოწერაზე დაფუძნებული პროვაიდერებიც აჩვენებენ თითო ტოკენის ფასს.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| ველები                                                          | ერთეული                            | შენიშვნები                                                                                                                                                     |
| --------------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD თითო ტოკენზე, ათობითი სტრიქონი | OpenRouter-თან თავსებადი, არასოდეს გამოიყენება ექსპონენტური აღნიშვნა. ქეშის ორი ველი ჩნდება მხოლოდ მაშინ, როდესაც ქეშის ფასი არსებობს.                         |
| `input`, `output`, `cached`, `cache_creation`                   | USD ყოველ 1M ტოკენზე, რიცხვი       | ადრინდელი კატალოგის ველები, რომლებიც არსებული კლიენტებისთვის შენარჩუნებულია. `reasoning` და `long_context` ასევე ჩნდება, როდესაც ფასების სტრიქონი მათ შეიცავს. |

- **კომბინაციებს** აქვთ მათი პირველი ხილული სამიზნის ფასი. ჩაშენებული `auto/*` კომბინაციები
  სამიზნეს მოთხოვნის შესრულების დროს ირჩევენ, ამიტომ მათ `pricing` არ აქვთ.
- **უფასო მოდელებში** ნაჩვენებია `"0"` (და `0`), როდესაც მათი ფასი ნულია. მოდელი, რომელსაც
  ფასების სტრიქონი არ აქვს, ასევე აჩვენებს `"0"`-ს, როდესაც კატალოგი მას უფასოდ აღნიშნავს
  (`free: true`) ან ჩაშენებული უფასო მოდელების კატალოგი მას შეიცავს.
- **უცნობი ფასი:** ჩანაწერს `pricing` გასაღები არ აქვს.
- **კრედიტით აღრიცხვადი პროვაიდერები** (როგორიცაა Kiro) ანგარიშსწორებას თითო მოთხოვნაზე და
  არა თითო ტოკენზე ახორციელებენ. მათი ჩანაწერები ინარჩუნებს ადრე არსებულ რიცხვით
  თითო-1M ველებს და არ შეიცავს თითო-ტოკენიან სტრიქონულ ველებს.
- **ვარიანტები** (reasoning-effort იდენტიფიკატორები, no-thinking მეტსახელები, აღმოჩენისა და
  gateway-ის სარკეები) აკოპირებენ იმ მოდელის ფასს, რომელზეც მარშრუტდებიან.
- ველები შეიცავს მხოლოდ საბაზისო განაკვეთებს. გრძელი კონტექსტის საფეხურები (რიცხვითი
  `long_context` ველი) და სერვისის დონის მულტიპლიკატორები (მაგალითად Codex fast ან flex)
  `prompt`-სა და `completion`-ს არ ცვლის.
- ობიექტი ერთნაირია ავთენტიფიკაციის ყველა სტილისთვის, მათ შორის Anthropic-ის სტილის
  მოთხოვნისთვის `x-api-key`-ითა და `anthropic-version`-ით (პასუხი კვლავ არის
  `{ "object": "list", "data": [...] }`). იმპლემენტაცია: `src/app/api/v1/models/catalogPricing.ts`.

### მოდელის id პრეფიქსები (`?prefix=`)

მოდელების უმეტესობა რეკლამირდება **პროვაიდერის პრეფიქსით**. თქვენ მიერ მიღებულ პრეფიქსს
აკონტროლებს `MODELS_CATALOG_PREFIX_MODE` ფუნქციური დროშა, რომლის გადაფარვაც შესაძლებელია
**თითოეული მოთხოვნისთვის** query პარამეტრით — ეს სასარგებლოა კლიენტისთვის, რომელსაც სურს
სუფთა სია, სერვერის საერთო პარამეტრის სხვა მომხმარებლებისთვის შეცვლის გარეშე:

```bash
GET /v1/models?prefix=alias        # თითო მოდელზე ერთი id — მოკლე alias პრეფიქსი
GET /v1/models?prefix=dual         # ორივე ფორმა (სერვერის ნაგულისხმევი)
GET /v1/models?prefix=canonical    # მხოლოდ პროვაიდერის სრული id-პრეფიქსი
```

| რეჟიმი      | გაცემული მნიშვნელობა                                     | შენიშვნები                                                                                                                                                                                                      |
| ----------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **და** `claude/claude-sonnet-4-6` | **ნაგულისხმევი.** ორივე id ერთსა და იმავე მოდელზე მარშრუტდება; შენარჩუნებულია იმისთვის, რომ კლიენტის კონფიგურაციებმა, რომლებშიც რომელიმე ფორმა იყო ჩაწერილი, მუშაობა გააგრძელონ. კატალოგი დაახლოებით ორმაგდება. |
| `alias`     | `cc/claude-sonnet-4-6`                                   | თითო მოდელზე ერთი ჩანაწერი. პროვაიდერები, რომლებსაც განსხვავებული alias არ აქვთ, მაინც გასცემენ თავიანთ ჩანაწერს, ამიტომ არაფერი იკარგება.                                                                      |
| `canonical` | `claude/claude-sonnet-4-6`                               | თითო მოდელზე ერთი ჩანაწერი სრული provider-id პრეფიქსის ქვეშ. პროვაიდერები, რომლებსაც განსხვავებული alias არ აქვთ (მაგ., `antigravity/…`, `agy/…`), აქაც გასცემენ თავიანთ ერთ id-ს, ამიტომ არაფერი იკარგება.     |

`dual` რეჟიმის სარკის ამოცნობა query პარამეტრის გარეშეც შესაძლებელია: მას აქვს `parent`
ველი, რომელიც ძირითად id-ზე მიუთითებს.

კლიენტებმა, რომლებიც მოდელის ამრჩევს აჩვენებენ, უნდა მოითხოვონ `?prefix=alias` — სწორედ ამას
აკეთებს [OmniCopilot VS Code გაფართოება](../guides/VSCODE-COPILOT.md).

### აღმოჩენის ფილტრები (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` მხარს უჭერს აღმოჩენის არჩევით ფილტრებს. მათი არგამოყენების შემთხვევაში პასუხი
უცვლელი რჩება. ისინი ავიწროებენ კატალოგს, რომელსაც გამომძახებელი უკვე ხედავს (API-key-ის
ნებართვები პირველ რიგში გამოიყენება) და სრულდება OpenAI-ის სტილის `limit` / `after` გვერდებად
დაყოფამდე:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # ყველა ჩამოთვლილი capability true უნდა იყოს
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # კატალოგის `type`; მის გარეშე დარჩენილი სტრიქონები არის `chat`
GET /v1/models?q=sonnet&limit=10                           # id-ზე ან name-ზე რეგისტრისგან დამოუკიდებელი დამთხვევა
```

| პარამეტრი     | მნიშვნელობები                                                                                       |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | არაუარყოფითი მთელი რიცხვი, შედარებული `context_length`-თან                                          |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 სიმბოლო                                                                                       |

უცნობი მნიშვნელობა ან `min_context`, რომელიც არ არის არაუარყოფითი მთელი რიცხვი (მაგალითად, `1.5`),
აბრუნებს HTTP `400`-ს და შეტყობინებაში ჩამოთვლილია მოქმედი მნიშვნელობები. იმპლემენტაცია:
`src/app/api/v1/models/catalogFilters.ts`.

### მოდელების მოკლე სია (`POST /v1/models/query`)

`POST /v1/models/query` აბრუნებს მოკლე, დეტერმინისტულ სიას იმავე კატალოგიდან, იგივე
ავთენტიფიკაციითა და თითოეული გასაღებისთვის ხილვადობით, რაც აქვს `GET /v1/models`-ს:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ყველა ველი არასავალდებულოა. `capabilities` და `exclude` იღებს მასივს ან მძიმით გამოყოფილ სტრიქონს;
`max_output` შედარდება `max_output_tokens`-თან. შედეგები დალაგებულია `owned_by`-ის, შემდეგ კი `id`-ის
მიხედვით. `limit`-ის ნაგულისხმევი მნიშვნელობაა `20`, ხოლო `100`-ზე მეტი მნიშვნელობები იზღუდება `100`-ით. არასწორი JSON,
უცნობი ველი ან არასწორი მნიშვნელობა აბრუნებს HTTP `400`-ს.

### ინდივიდუალურად დამალული ჩეთის მოდელები

მოდელი, რომელიც მისი პროვაიდერის გვერდზე მონიშნულია როგორც **დამალული**, გამოირიცხება კატალოგიდან და
ექსპლიციტურად მოთხოვნისას უარყოფილი იქნება HTTP `404` / `model_not_found` შეცდომით. შემოწმება იყენებს
განსაზღვრულ პროვაიდერსა და მოდელს, მათ შორის პროვაიდერის მეტსახელებს, თავსებად-პროვაიდერის კვანძის
პრეფიქსებსა და კავშირის ნაგულისხმევ მნიშვნელობებს. კომბინაცია გამოტოვებს დამალულ სამიზნეებს და
შეუძლია გამოიყენოს ხილული თანამოდელი; როდესაც არცერთი შესრულებადი სამიზნე აღარ რჩება, ის აბრუნებს
იმავე შეცდომის კოდს. დამალვის მოხსნას ეფექტი აქვს შემდეგ მოთხოვნაზე. მხოლოდ გამოსახულებებისთვის
განკუთვნილი ხილვადობის გადაფარვები არ მალავს იმავე ID-ის მქონე ჩეთის მოდელს.

მოდელის ეს ინდივიდუალური პარამეტრი განცალკევებულია
[მოდელების გამოჩენის დაშვების/უარყოფის სიებისგან](../routing/MODEL_EXPOSURE_LIST.md), რომლებიც ფილტრავს კატალოგის
გამოცხადებასა და ავტომატური მარშრუტიზაციის კანდიდატებს, ამასთან ინარჩუნებს ექსპლიციტურ დისპეტჩერიზაციას.
API-გასაღების მოდელის ნებართვები კვლავ დამოუკიდებლად მოქმედებს. კატალოგის პრეფიქსის ნაგულისხმევი რეჟიმი კვლავ `dual`-ია.

### thinking-ის გარეშე მოდელის ვარიანტები

thinking-ის მხარდაჭერის მქონე Claude-ის მოდელებისთვის `/v1/models` ასევე აცხადებს **thinking-ის გარეშე**
ვარიანტს, რომლის ID პრეფიქსია `claude-3-omniroute-no-thinking/`:

## ElevenLabs აუდიოს გენერირება

OmniRoute-ში დააკონფიგურირეთ `elevenlabs` პროვაიდერის კავშირი თქვენი ElevenLabs API გასაღებით.
კლიენტები ავთენტიფიცირდებიან თავიანთი **OmniRoute** გასაღებით (`Authorization: Bearer $OMNIROUTE_API_KEY`);
გეითვეი შენახულ პროვაიდერის გასაღებს `xi-api-key`-ის სახით აწვდის. ElevenLabs-ის გასაღები არასოდეს
გაგზავნოთ გეითვეის bearer ტოკენის სახით.

| მეთოდი | გზა                         | პასუხი                                           | API გასაღების endpoint-ის კატეგორია |
| ------ | --------------------------- | ------------------------------------------------ | ----------------------------------- |
| POST   | `/v1/sound-generation`      | აუდიოს ნატიური ბაიტები                           | `elevenlabs`                        |
| POST   | `/v1/music`                 | აუდიოს ნატიური ბაიტები                           | `music`                             |
| POST   | `/v1/music/stream`          | აუდიოს ნაკადური ბაიტები                          | `music`                             |
| POST   | `/v1/music/detailed`        | აუდიოს ნატიური multipart და კომპოზიციის გეგმა    | `music`                             |
| POST   | `/v1/music/detailed/stream` | ნატიური SSE მეტამონაცემები და აუდიოს ფრაგმენტები | `music`                             |
| POST   | `/v1/music/plan`            | კომპოზიციის JSON გეგმა                           | `music`                             |

ეს endpoint-ები ავსებს არსებულ `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` და `/v1/speech-to-text` მარშრუტებს. ნატიური JSON ველები
და მოთხოვნის ისეთი პარამეტრები, როგორიცაა `output_format` და `enable_logging`, შენარჩუნებულია.
`/v1/music/detailed`-ის პასუხები ინარჩუნებს multipart საზღვრებს; გააანალიზეთ ისინი როგორც multipart.
`/v1/music/detailed/stream` აბრუნებს `text/event-stream`-ს კომპოზიციის მეტამონაცემებითა და
SSE მოვლენებში მოთავსებული base64 აუდიოს ფრაგმენტებით. ექვსივე მარშრუტს აქვს CORS preflight-ის მხარდაჭერა.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# მოკლე ხმოვანი ეფექტი. ხანგრძლივობა: 0.5-დან 30 წამამდე.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# მუსიკის ხანგრძლივობა მილიწამებში გამოიხატება: 3000-დან 600000-მდე.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

გამოიყენეთ `/v1/music/stream` იგივე JSON სხეულით აუდიოს ეტაპობრივი მიწოდებისთვის. კომპოზიცია
ზუსტად ერთ-ერთს იღებს: `prompt`-ს ან `composition_plan`-ს; `/v1/music/plan` მოითხოვს `prompt`-ს
და სურვილისამებრ იღებს `source_composition_plan`-ს. ნატიური სქემები ინარჩუნებს დამატებით
პროვაიდერის ველებს, რათა კომპოზიციის გეგმის ვერსიებმა და დეტალური მორგების პარამეტრებმა ElevenLabs-მდე მიაღწიოს.

ერთიანი `/v1/music/generations` endpoint ასევე იღებს
`elevenlabs/music_v1`, `elevenlabs/music_v2` და `elevenlabs/music_v2_5`-ს. აქტიური ElevenLabs კავშირის
არსებობისას ეს მოდელები მუსიკის კატალოგში არის ხელმისაწვდომი. ეს endpoint აბრუნებს
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`-ს. მისი `duration` ველი
წამებშია და აისახება `music_length_ms`-ზე; ცხადად მითითებულ `music_length_ms`-ს უპირატესობა ენიჭება.
`instrumental` აისახება `force_instrumental`-ზე, ხოლო ნატიურ ველს უპირატესობა ენიჭება.
ნაკადური რეჟიმისთვის გამოიყენეთ ნატიური streaming endpoint-ები, ხოლო მხოლოდ კომპოზიციის გეგმით მართული
მოთხოვნებისთვის — ნატიური კომპოზიციის endpoint.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Endpoint-ის, მოდელის, ბიუჯეტისა და კავშირის შეზღუდვები გამოიყენება upstream-თან ზარის განხორციელებამდე. ნატიური
მარშრუტები აბრუნებს upstream-ის სტატუსის კოდებსა და შეცდომის სხეულებს უცვლელად, მათ შორის `402`-ს გეგმის
შეზღუდვისთვის და `429`-ს კვოტის ლიმიტისთვის. `character-cost`, `song-id`, `request-id` და `retry-after`
სათაურები, არსებობის შემთხვევაში, შენარჩუნებულია. უფასო კრედიტის ბალანსი არ იძლევა გარანტიას, რომ ყველა
მუსიკის მოდელზე, გამომავალი ფორმატზე ან API ფუნქციაზე გექნებათ წვდომა: ElevenLabs თითოეული მოთხოვნისთვის
განსაზღვრავს უფლებამოსილებას. ერთიანი endpoint შეცდომის სტატუსის კოდებს OmniRoute-ის ნორმალიზებულ შეცდომის
კონვერტში ინარჩუნებს.

Upstream კონტრაქტები: [ხმოვანი ეფექტები](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[მუსიკის კომპოზიცია](https://elevenlabs.io/docs/api-reference/music/compose) და
[მუსიკის დეტალების ნაკადური მიწოდება](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

ყველა POST მარშრუტი ერთსა და იმავე სტრუქტურას მიჰყვება: `Bearer your-api-key` + Zod-ით ვალიდირებული JSON სხეული (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` და სხვ.; იხილეთ `src/shared/validation/schemas.ts`). სქემის ვალიდაციის წარუმატებლობისას ბრუნდება 4xx.

### დაასახელა search/fetch კომბინაციები

როგორც `POST /v1/search` ასევე `POST /v1/web/fetch` მიიღება `model` როგორც შენახული კომბინირებული სახელი. გამოიყენეთ ან `model` ან აშკარა `provider`; ორივე აბრუნებს `400` გაგზავნას. არცერთი ველის გარეშე, არსებული ავტომატური პროვაიდერის შერჩევა უცვლელი რჩება.

Combo Builder და მისი Add Model Catalog ასახავს მშობლიურ ვებ-ოპერაციების ჩანაწერებს დაკავშირებული პროვაიდერებისთვის, მაშინაც კი, როდესაც მათ არ აქვთ LLM მოდელების სია. სერპერი აჩვენებს** ვებ ძიება** ; ტავილი შოუები** ვებ ძიება / გვერდის ამოღება** , და მხოლოდ მისაღებად პროვაიდერების ჩვენება** გვერდის ამოღება** . აირჩიეთ ჩანაწერი და ანგარიში, როგორც ყოველთვის. Tavily-ის ერთი ჩანაწერი ემსახურება ორივე ვებ ბოლო წერტილს; ოპერაციების ეს ჩანაწერები არ ემატება მხოლოდ ჩეთის კლიენტის ამომრჩეველს ან ჩეთის მოდელის ზონდებს.

მაგალითად, შექმენით ა** პრიორიტეტი** კომბინაცია სახელად `shared-free` ამ მოწესრიგებულ სამიზნეებთან:

1. `openai/gpt-4o`
2. `tavily-search/web`
3. `serper-search/web`
4. `jina-reader/fetch`

შემდეგ გამოიყენეთ იგივე სახელი თითოეულ ზედაპირზე:

```json
{ "model": "shared-free", "query": "Open source speech recognition", "max_results": 5 }
```

```json
{ "model": "shared-free", "url": "https://example.com", "format": "markdown" }
```

ძიება განიხილავს Tavily შემდეგ Serper; Fetch განიხილავს Tavily შემდეგ Jina Reader; ჩატი გამოტოვებს სპეციალურ search/fetch პროვაიდერებს და განიხილავს OpenAI. თავსებადობა მოდის search/fetch აღმასრულებელი რეესტრებიდან და არა მოდელის სახელის სიტყვებიდან. გაფილტვრა წინ უსწრებს ავტორიზაციის არჩევანს და გაგზავნას და არასოდეს არედაქტირებს შენახულ კომბინაციას.

არაჩეთის შესაძლებლობების მარშრუტები მხარს უჭერს `priority`, `fill-first`, `round-robin`, `weighted`, `random`, `strict-random`, `least-used` და `p2c`. მხოლოდ ჩატის სინთეზის სტრატეგიები, როგორიცაა `fusion`, `pipeline` და `context-relay` უარყოფილია არაჩეთის მარშრუტებზე, ვიდრე ჩუმად გამოიყენება საძიებო ან გენერირებულ მედიაში. არსებული კომბინირებული ძრავა ამუშავებს შეკვეთილ სარეზერვო სისტემას, მათ შორის კვოტის უკმარისობას, და ინარჩუნებს საფეხურს IDs, ანგარიშის ქინძისთავებს, თითო ნაბიჯის ანგარიშის დასაშვებ სიებს, ჩადგმულ მითითებებს, აბონენტის connection/quota სკოპებს და კომბინირებული წვდომის პოლიტიკას. შედეგები ინარჩუნებს მშობლიურ search/fetch სქემას, მათ შორის რეალურ პროვაიდერს; `X-OmniRoute-Combo-Trace` განსაზღვრავს მარშრუტიზაციის გადაწყვეტილებას. უცნობი კომბინაციები აბრუნებენ `404`; არააქტიური კომბინაციები და კომბინაციები თავსებადი სამიზნეების გარეშე აბრუნებს `400`.

ყოველი კომბინირებული მცდელობა იყენებს ერთ გამოკვეთილ პროვაიდერს. მას არ შეუძლია გამოიძახოს ადგილობრივი ავტომატური პროვაიდერის აუზი კომბინაციის უკანა მხარეს. ექსპლიციტური პროვაიდერის მოთხოვნები ინარჩუნებს ერთ პროვაიდერთან არსებულ ქცევას. პირდაპირი ჩეთის მოთხოვნები, რომლებიც მიზნად ისახავს ერთგულ search/fetch პროვაიდერებს, აბრუნებს მოქმედ JSON `400` ნაცვლად იმისა, რომ გადალახოს OpenAI-ს სტილის შემსრულებელი.

### შესაძლებლობების სპეციფიკური კომბინირებული მარშრუტები

შენახული კომბინაციები შეიძლება შეიცავდეს `routes` ობიექტს, რომლის კლავიშები არის API შესაძლებლობები. ყველა მარშრუტს აქვს თავისი სამიზნე სია, სტრატეგია და გაშვების კონფიგურაცია. ზედა დონის `models`, `strategy` და `config` რჩება მემკვიდრეობით თავსებადი ჩატის გეგმა; ძველი კომბინაციები `routes` გარეშე აგრძელებენ მუშაობას უცვლელად.

მხარდაჭერილი მარშრუტის გასაღებებია `chat`, `search`, `web-fetch`, `embeddings`, `rerank`, `images`, `image-edits`, `videos`, `music`, `ocr`, `audio-speech`, `audio-transcriptions`, `audio-translations` და `audio-generation`. საბოლოო წერტილის პროექცია ხდება რწმუნებათა სიგელის შერჩევამდე, ქულის მინიჭებამდე ან გაგზავნამდე. ჩადგმული კომბინირებული მითითებები ირჩევს ბავშვის კომბინაციის მარშრუტს იმავე შესაძლებლობისთვის.

`POST /v1/music/generations` და `POST /v1/ocr` იღებენ კომბინირებულ სახელს `model` ში. მშობლიურ ElevenLabs-თან თავსებადი `POST /v1/music` ასევე იღებს კომბინირებულ სახელს `model_id` ში, მაგრამ ყველა გამოსაყენებელი სამიზნე ამ მშობლიურ ბოლო წერტილზე უნდა იყოს ElevenLabs მუსიკალური მოდელი, ასე რომ მისი ორობითი საპასუხო კონტრაქტი დაცული იქნება. `POST /v1/sound-generation` იღებს `audio-generation` კომბინაციას `model_id` ში იმავე მშობლიურ-ორობითი შეზღუდვის ქვეშ. გამოიყენეთ `/v1/music/generations` ჰეტეროგენული მუსიკის პროვაიდერებისთვის.

**ავტომატური შერჩევა:** `provider` გარეშე, კონფიგურირებული კავშირის მქონე ყველაზე იაფი პროვაიდერი გადის ჯერ, ხოლო შემდეგი ყველაზე იაფი არის მარცხი. უფასო ბოლო კურორტის პროვაიდერები (`duckduckgo-free`) გამოიყენება მხოლოდ მაშინ, როცა სხვა არაფერია კონფიგურირებული. თვითმმართველობის მქონე SearXNG ითვლება კონფიგურირებულად, მას შემდეგ რაც მისი კავშირი ინახავს რეალურ `baseUrl` (არა კატალოგის ნაგულისხმევი `http://localhost:8888/search`): ის შემდეგ ფასდება როგორც $0 პროვაიდერი კლავიშებზე წინ, ხოლო ყველაზე იაფი კლავიშიანი პროვაიდერი, როგორც failover, მათ შორის, როდესაც SearXNG პასუხობს 400, 401, 403 ან `baseUrl` a არ არის მოქმედი `http(s)` ქულაზე, რომ URL 404. ღრუბლოვანი მეტამონაცემების მისამართი არ ითვლება. SearXNG კავშირი, რომელიც ინახავს ჟეტონს, ამ გზით მხოლოდ `https://` ზე ან loopback `http://` ზე ინახავს. დისტანციურ უბრალო `http://` ზე ის არასოდეს არ არის წარუმატებელი და რჩება უკანასკნელ კურორტად, გამოიყენება მხოლოდ მაშინ, როდესაც სხვა პროვაიდერი არ არის კონფიგურირებული ან როცა მოითხოვება სახელით, ასე რომ, ის აგზავნის ჟეტონს მკაფიო ტექსტში ამ ორ შემთხვევაში.

### ეგსა და ტავილი `provider_options`

Exa და Tavily კითხულობენ პროვაიდერის სპეციფიკურ ველებს სახელების სივრცის ჩანთიდან: `provider_options.exa` (ან `provider_options["exa-search"]`) და `provider_options.tavily` (ან `provider_options["tavily-search"]`). გადამისამართებულია მხოლოდ ქვემოთ მოცემული გასაღებები. თითოეული მოწმდება `open-sse/handlers/search/providerOptionsPassthrough.ts` ში საკუთარი Zod სქემის მიხედვით და არასწორი ტიპის გასაღები ამოვარდნილია. ნებისმიერი სხვა გასაღები იგნორირებულია, მათ შორის auth, base URL, `stream` და `outputSchema`. სხვა პროვაიდერების მიერ გამოყენებული ბრტყელი კლავიშები (`cx`, `depth`, ...) მუშაობს როგორც ადრე.

| პროვაიდერი | უმაღლესი დონის ველები                                                                                                                                                                                                                                                                                                                                                     | დაბუდებული                                                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| ეგზა       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (ბრტყელი პრიმიტივები), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                          | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` გაერთიანდა ნაგულისხმევ `{ text: true, highlights: true }` ზე |
| ტავილი     | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                          |

ყოველთვის იმარჯვებს ზოგადი ველები: `query`, `max_results`, `filters` (დომენები), `country` და `search_type` დან მიღებული თემა. Exa-ზე, `search_type: "news"` ინახავს `category: "news"`. ტავილი ასევე იღებს `search_type: "finance"` (`topic: "finance"`).

Firecrawl ძიების ღირებულება აღირიცხება 10 დაბრუნებული შედეგის დაწყებულ ბლოკზე, 0,002$ (2 კრედიტი) ბლოკი და მინიმუმ ერთი ბლოკი თითო ზარზე ( [Firecrawl billing](https://docs.firecrawl.dev/billing) ): 11 შედეგი ღირს 0,004$.

ზოგადი `time_range` ახლა აღწევს ორივე პროვაიდერს: Exa იღებს `startPublishedDate` (ISO დროის ნიშანს) და Tavily იღებს `start_date` (`YYYY-MM-DD`). აშკარა თარიღი `provider_options` ში აჭარბებს შედგენილ თარიღს.

Exa-ის შედეგები ინახავს `id`, `highlights` (ყოველი მონიშვნა, არა მხოლოდ პირველი გამოყენებული `snippet` ად), `highlight_scores`, `summary`, `subpages`, `entities` და `extras` `provider_raw` ში. შედეგები შენარჩუნებულია `images` და `favicon`.

Linkup-ის ძიების ღირებულება აღირიცხება 0,005$ `depth` `fast` და `standard` და 0,05$ `deep` ( [Linkup pricing](https://docs.linkup.so/pages/documentation/development/pricing) ), მიუხედავად იმისა, `depth` მოდის `provider_options` დან თუ კავშირის პარამეტრებიდან.

Exa `type: "lite"` (Exa 3.0) იღებს ველების უფრო მცირე კომპლექტს და უარყოფს მთელ მოთხოვნას, როდესაც დაყენებულია ნებისმიერი სხვა ველი. Lite-ისთვის, `additionalQueries`, `systemPrompt` და ყველა `contents` კლავიატურა `text` და `highlights` გარდა იშლება ზარის წინ. მოძველებული `subpages`, `subpageTarget`, `highlights.numSentences` და `highlights.highlightsPerUrl` აღარ არის გადაგზავნილი.

ხარჯების აღრიცხვა არის ბინა რეესტრი `costPerQuery`, გარდა Exa-ისა, რომელიც მიჰყვება Exa-ს საკუთარ ფასებს: $0,007 თითო ზარზე `auto` (და მემკვიდრეობითი `fast`) ან $0,004 `lite` (და მემკვიდრე `instant`), რომელიც მოიცავს 10 შედეგს; $0,001 ყოველი შემდგომი შედეგისთვის; და $0,001 თითო დაბრუნებულ შედეგზე, როდესაც `contents.summary` დაყენებულია. Tavily აღირიცხება 1 კრედიტით (0,008$) `search_depth` `basic`, `fast` და `ultra-fast`, და 2 კრედიტით (0,016$) `advanced` ( [Tavily API კრედიტები](https://docs.tavily.com/documentation/api-credits) ). ზარი `auto_parameters: true` ით, რომელსაც Tavily განაახლებს გაფართოებულზე, კვლავ ჩაწერილია 1 კრედიტით.

## ვებ Fetch API

ამოიღეთ შინაარსი URL დან კონფიგურირებული ვებ-შეტანის პროვაიდერის საშუალებით (Firecrawl, Jina Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract, Keenable Fetch).

პარალელური ამონაწერი (`parallel-search`, იგივე API კლავიატურა, როგორც პარალელური ძებნა) აბრუნებს Markdown-ს მხოლოდ — ნებისმიერი სხვა `format` არის `400` — და 100,000 სიმბოლოს შეიცავს. როდესაც თავად სამიზნე გვერდის ამოღება შეუძლებელია, ზემორეა აცნობებს მას HTTP 200-ში; OmniRoute ასახავს როგორც `422` ფიქსირებული შეტყობინებით.

Keenable Fetch (`keenable-search`) ასევე აბრუნებს მხოლოდ Markdown-ს (ნებისმიერი სხვა `format` არის `400`) და კონტენტს 100000 სიმბოლოს აფარებს. ის მუშაობს გასაღების გარეშე: გამოკვეთილი `provider: "keenable-search"` მოთხოვნა კავშირის გარეშე იყენებს Keenable-ის უ გასაღების ბოლო წერტილს (თითო IP სიჩქარის ლიმიტები). კონფიგურირებული გასაღები მხოლოდ ამ ლიმიტებს ხსნის; ავტომატური არჩევა იყენებს Keenable-ს მხოლოდ გასაღების კონფიგურაციის დროს.

| მეთოდი | ბილიკი          | აღწერა                                                          |
| ------ | --------------- | --------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Fetch/scrape a URL — სხეული დადასტურებული `v1WebFetchSchema` ით |

**ავტორიზაცია:** მატარებელი API გასაღები (`extractApiKey` + `isValidApiKey`). პოლიტიკა აღსრულებულია `enforceApiKeyPolicy` მეშვეობით.

დასახელებული კომბინაციები იყენებენ ზემოთ მოყვანილ [`model` მარშრუტიზაციის კონტრაქტს](#named-searchfetch-combinations), ინარჩუნებენ მოპოვების სპეციფიკურ ვარიანტებსა და პასუხებს.

**Quota-ware backback (#8297):** როდესაც არც `provider` და არც `model` არ არის მოცემული, აუზი (`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` → `parallel-search` → `keenable-search`) მოძრაობს ფიქსირებული პრიორიტეტის მიმდევრობით (fill-first) — rate-limited-but-configured პროვაიდერის გამოტოვება და მოკლე ნაკადის ნაცვლად retryable/quota HTTP 429 ყოველთვის 402/403 Firecrawl/Tavily/TinyFish სტილის უფასო ფენებისთვის — არა Jina Reader-ისთვის და არასდროს 400 ცუდი მოთხოვნისთვის) ხვდება შემდეგ გამოუცდელ სერთიფიცირებულ პროვაიდერს მოთხოვნის დროს. როდესაც აუზში ყველა პროვაიდერი ამოიწურება, საბოლოო წერტილი აბრუნებს ერთ `429` ( `Retry-After` სათაურით) წინა ზოგადი `400` ნაცვლად. როდესაც აშკარა `provider` მოითხოვება, არსებობს** არა** მდუმარე სარეზერვო — განაკვეთით შეზღუდული ან წარუმატებელი პროვაიდერი ავლენს საკუთარ შეცდომას (`429` თუ განაკვეთი შეზღუდულია, წინააღმდეგ შემთხვევაში ზემორეული სტატუსი).

## WebSocket Streaming

```bash
GET /v1/ws?handshake=1
```

ამოწმებს WebSocket upgrade handshake-ს და აბრუნებს wire protocol-ის მაგალით შეტყობინებებს (`request`, `cancel`). რეალური WS frames-ები მუშავდება ჩაშენებული WS სერვერის მიერ Next.js-ის route table-ის გარეთ.

**ავთენტიფიკაცია:** Bearer API გასაღები handshake-ის დროს.

### Responses API WebSocket-ის მეშვეობით (მხოლოდ codex)

```bash
# იგივე host:port, რაც HTTP API-ს აქვს (ნაგულისხმევად 20128); კავშირის upgrade:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ან: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# პირველი frame აუცილებლად უნდა იყოს response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxy დაკავშირებულია **მხოლოდ `codex`-თან** (ChatGPT backend). ის უსმენს API/dashboard-ის იმავე პორტზე შემდეგ გზებზე: `/v1/responses`,
`/responses` და `/api/v1/responses`. პირველი `response.create` frame-ის მიღებისას ის ახორციელებს ავთენტიფიკაციას + მომზადებას შიდა `codex-responses-ws` bridge-ის მეშვეობით, ირჩევს codex OAuth კავშირს და `wreq-js` transport-ის გავლით tunnel-ს ქმნის
`wss://chatgpt.com/backend-api/codex/responses`-მდე. **არა-codex მოდელები უარყოფილია** (`codex_ws_provider_required`).
კვოტის გაზიარებით routing-ისთვის გამოიყენეთ `model: "qtSd/<group>/codex/<model>"`. იმპლემენტაცია მდებარეობს
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**ავთენტიფიკაცია:** Bearer API გასაღები handshake-ის დროს. ჩაშენებული HTTP სერვერი (`server-ws.mjs`)
უნდა იყოს აქტიური entrypoint (ნაგულისხმევად ასეა, როდესაც `app/server-ws.mjs` არსებობს).

#### მოდელის id: გამოიყენეთ ChatGPT-ის შიშველი id (`codex/` პრეფიქსის გარეშე)

OpenAI **Codex CLI** კლიენტის მხარეს ამოწმებს მოდელის სახელს, როდესაც
`supports_websockets = true` არის და უარყოფს პროვაიდერის პრეფიქსიან id-ებს, როგორიცაა
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). გაგზავნეთ **შიშველი** id (მაგ., `gpt-5.5`). OmniRoute-ის bridge მხოლოდ codex-თან მუშაობს, ამიტომ ის ხელახლა განსაზღვრავს შიშველ id-ს, როგორც codex მოდელს
(`resolveCodexWsModelInfo`) upstream-მდე tunnel-ის შექმნამდე — მიუხედავად იმისა, რომ შიშველი
`gpt-5.5` HTTP-ის მეშვეობით სხვაგვარად სხვა პროვაიდერთან გაიგზავნებოდა.

#### OpenAI Codex CLI-ის კონფიგურაცია

მიუთითეთ Codex CLI OmniRoute-ზე, WebSocket-ის მხარდაჭერის მქონე custom provider-ის დამატებით
`~/.codex/config.toml`-ში (არსებულ კონფიგურაციაზე გავლენის თავიდან ასაცილებლად გამოიყენეთ ცალკე `CODEX_HOME`):

```toml
model = "gpt-5.5"                 # შიშველი id — არა "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ბოლოში slash-ის გარეშე; WS URL წარმოიქმნება აქედან (production-ში გამოიყენეთ https/wss)
wire_api = "responses"                    # ერთადერთი მხარდაჭერილი მნიშვნელობა 2026 წლის თებერვლიდან
supports_websockets = true                # ააქტიურებს Responses-over-WS transport-ს
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API გასაღები (ნებისმიერი გასაღები, თუ REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI `base_url + /responses`-ს WebSocket-ზე გადაიყვანს, OmniRoute კი მას არჩეულ codex OAuth კავშირზე tunnel-ის მეშვეობით გადაამისამართებს. შემოწმებულია end-to-end ადგილობრივ სერვერთან: ChatGPT აბრუნებს `codex.rate_limits` + `response.created`-ს და სტრიმინგით აგზავნის completion-ს.

## თვითმომსახურების გამოყენება (`/api/usage/om-usage`)

ნებისმიერ API კლავიშს შეუძლია წაიკითხოს** საკუთარი** გამოყენება და კვოტები — no management auth. ეს არის ბოლო წერტილი, რომელსაც კლიენტი (CLI, OmniCopilot პანელი) იყენებს გასაღების მფლობელს თავისი ხარჯების საჩვენებლად.

```bash
# Text form (the historical contract — plain text for a terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Structured form — what a UI consumes
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

გასაღები უნდა ჰქონდეს**`allowUsageCommand`** ჩართულია (ნაგულისხმევად გამორთულია — დაფის API კლავიშების მენეჯერი გადართავს მას თითო კლავიშზე). მის გარეშე ბოლო წერტილი პასუხობს `403`.

`?format=json` აბრუნებს დისკრიმინირებულ ფორმას, ასე რომ აბონენტი არასოდეს კითხულობს მონაცემთა ველს უარის თქმიდან. წარმატების შესახებ:

```jsonc
{
  "allowed": true,
  // present only when the key opted into per-key usage limits (daily/weekly/5-hour USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // the selected provider quota snapshot, or null when nothing is cached yet:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // every connection's snapshot, so a UI can render several providers side by side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

უარის შემთხვევაში (`401` ცუდი გასაღები / `403` დაუშვებელია) იგივე მარშრუტი აბრუნებს `{ "allowed": false, "error": { "message": "…" } }` — აწმყო, მაგრამ ცარიელი `personal`/`provider` (გასაღები დაშვებულია, ჯერ არაფერი ვისწავლე) არის განსხვავებული მდგომარეობა უარისგან და მხოლოდ JSON ფორმა განასხვავებს მათ.

**ავტორიზაცია:** აბონენტის საკუთარი Bearer API კლავიატურა, დამოწმებული `isValidApiKey` — ით ეს _ არ არის მართვის ზედაპირი (`/api/keys/…`), რომელიც რჩება `requireManagementAuth` უკან.

### Raw წინააღმდეგ Cutoff-მორგებული კვოტის პროცენტები

`/api/usage/om-usage` მოხმარებისას, მომხმარებლებმა უნდა გაითვალისწინონ განსხვავება წარმოდგენილი პროცენტებს შორის** უბრალო ტექსტის გამომავალი** და სტრუქტურირებული**JSON გამომავალი** :

| ასპექტი                    | უბრალო ტექსტის ფორმატი (`/api/usage/om-usage` / `@@om-usage`)                                             | JSON ფორმატი (`?format=json`)                                                         |
| :------------------------- | :-------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------ |
| **გამომავალი ველი**        | `NN% left` (მაგ., `20% left`)                                                                             | `provider.quotas` / `providers[].quotas`                                              |
| **გაზომვა**                | **შეწყვეტით მორგებული გამოსაყენებელი შემწეობა** : დარჩენილი სიმძლავრე ათვლის ზღურბლზე ზემოთ               | **ნედლეულის ზედა დინების კვოტა** : მოურგებელი პროვაიდერის გაზომვა                     |
| **Cutoff სკალირება**       | მასშტაბირებულია `effectiveRemainingPercent()` მეშვეობით, ასე რომ დაცული რეზერვი იკითხება როგორც `0% left` | არცერთი (დაუმუშავებელი სნეპშოტის მნიშვნელობები, როგორც მოხსენებულია პროვაიდერის მიერ) |
| **ბარიერის მონაცემები**    | ჩართულია გამოტანილ პროცენტში                                                                              | ინახება `quotaWindowThresholds` ში თითო კავშირზე (ან სერვერის ნაგულისხმევად)          |
| **პირველადი მომხმარებელი** | ინტერაქტიული CLIs, ტერმინალის მოთხოვნა, ადამიანის ოპერატორები                                             | პროგრამული ინტეგრაციები, დაფები, ანალიტიკა, ბილინგის ტრეკერები                        |

#### Cutoff Adjustment ფორმულა

OmniRoute მხარს უჭერს კვოტების პროაქტიულ შეზღუდვებს, რათა თავიდან აიცილოს ზემო დინებაში ამოწურვა (კონფიგურირებულია `quotaWindowThresholds` კავშირის, პროვაიდერის ნაგულისხმევი პარამეტრების ან გლობალური გამძლეობის პარამეტრების მეშვეობით). როდესაც ათვლის ზღვარი (მაგ., `cutoff = 25%`) აქტიურია კვოტის ფანჯარაში, ტექსტის გამომსახველი ითვლის დარჩენილ ზღვარს, როგორც:

- თუ `remaining <= cutoff`: აბრუნებს `0%`.
- თუ `remaining > cutoff`: აბრუნებს `((remaining - cutoff) / (100 - cutoff)) * 100`.

ფორმატირებული ტექსტის გამომავალი ამრგვალებს მას უახლოეს მთელ რიცხვამდე (`Math.round(...)`).

#### საილუსტრაციო მაგალითი

განიხილეთ პროვაიდერის ფანჯარა** 60% ნედლეულის გამოყენება** (აქედან გამომდინარე** 40% ნედლეულის დარჩენილი კვოტა** ) და კონფიგურირებული** 25% დარჩენილი კვოტის შეწყვეტა** ბარიერი:

| წარმომადგენლობა                  | გაანგარიშება                                       | დარჩენილი |            ნაგულისხმევი მეორადი             |
| :------------------------------- | :------------------------------------------------- | :-------: | :-----------------------------------------: |
| **Raw JSON (`?format=json`)**    | ზემოთ ნაკადის სნეპშოტი (`quotas[window]`)          |  **40%**  |                   **60%**                   |
| **ტექსტის ფორმატი (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**  | **80%** (თუ ვიანგარიშებთ `100 - remaining`) |

- **რატომ ჩანს ტექსტი 20% დარჩა:** ანგარიშზე დარჩენილი 40%-იანი ფიზიკური კვოტიდან 25%-ს რეზერვირებულია შეწყვეტის პოლიტიკა. აბონენტს აქვს მხოლოდ 15% 75%-დან გამოსაყენებელი სათავე ოთახიდან, სანამ როუტერი შეწყვეტს მარშრუტს ამ კავშირთან. სკალირება უზრუნველყოფს კავშირის სიგნალების ამოწურვას (`0% left`) ზუსტად მაშინ, როდესაც მარშრუტიზაცია შეწყვეტს.
- **რატომ ინარჩუნებს JSON ნედლეულ მნიშვნელობებს:** JSON payload აბრუნებს პროვაიდერის ზუსტ სურათს (`UsageSnapshot`), რათა გარე ხელსაწყოებს ჰქონდეთ წვდომა მიწის ჭეშმარიტების ზემო დინებაში გამოყენებაზე და კავშირის დონის `quotaWindowThresholds` სერვერის მხრიდან დაკარგვის სკალირების გარეშე.

#### სამომხმარებლო მიგრაციის სახელმძღვანელო

თუ გარე ინტეგრაციამ (როგორიცაა რედაქტორის დანამატი ან აგენტის გაფართოება) მანამდე გაანადგურა ტექსტის ბოლო წერტილი (`NN% left`) და გამოითვალა გამოყენებული პროცენტი, როგორც `100 - NN`, `?format=json` ში მიგრაცია ნიშნავს:

- დაუმუშავებელი JSON მნიშვნელობების წაკითხვა აისახება** ფაქტობრივი ზემოთ მოხმარება** (60% გამოყენებულია ზემოთ მოცემულ მაგალითში).
- თუ ინტეგრაციას სურს შეინარჩუნოს ტექსტის საბოლოო წერტილის გამოსაყენებელი დაშვების სემანტიკა, მას შეუძლია შეაფასოს ეფექტური დარჩენილი ფორმულა კლიენტის მხარეს `quotaWindowThresholds` გამოყენებით კავშირის დონის გადაფარვისთვის.

## CLIProxyAPI-ის მართვის თავსებადობა

OmniRoute პასუხობს სამ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)
მართვის endpoint-ს, რომლებსაც გამოყენების საინფორმაციო დაფები Claude-ისა და Codex-ის გამოწერის ლიმიტების
წასაკითხად იძახებენ (მაგალითად, T3 Code-ის `cliproxy` usage-limit წყარო). მიუთითეთ კლიენტის საბაზისო URL
OmniRoute-ზე და მართვის გასაღებად გამოიყენეთ API-გასაღები `manage` scope-ით. მარშრუტები
მომსახურებულია მისამართებზე `/v0/management/*` და `/api/v0/management/*`.

| მეთოდი | გზა                          | აღწერა                                                                                                                                      |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v0/management/auth-files`  | Claude-ისა და Codex-ის OAuth კავშირები ფორმატში `{ files: [{ id, auth_index, provider, email, disabled, id_token }] }`. ტოკენების გარეშე    |
| POST   | `/v0/management/api-call`    | სხეული `{ auth_index, method, url, header?, data? }`. აგზავნის ერთ დაშვებულ მოთხოვნას ანგარიშის ტოკენით და აბრუნებს `{ status_code, body }` |
| POST   | `/v0/management/reset-quota` | სხეული `{ auth_index }`. ასუფთავებს ერთი ანგარიშის კავშირის cooldown-ს, მოდელის lockout-ებსა და Codex-ის scope-ების მიხედვით cooldown-ებს   |

- `auth_index` არის OmniRoute-ის კავშირის id. `provider` არის `claude` ან `codex` (მხოლოდ OAuth
  კავშირები; `anthropic` API-გასაღების პროვაიდერი ჩამონათვალში არ შედის). Codex-ისთვის
  `id_token.chatgpt_account_id` არის შენახული workspace id, ხოლო `plan_type` — შენახული გეგმა.
- `api-call` ზოგადი proxy არ არის. ის იღებს მხოლოდ Claude-ის `GET
https://api.anthropic.com/api/oauth/usage`-ს და Codex-ის `GET https://chatgpt.com/backend-api/wham/usage`-ს, `GET .../wham/rate-limit-reset-credits`-სა და
  `POST .../wham/rate-limit-reset-credits/consume`-ს, თითოეულს მხოლოდ შესაბამისი
  provider-ის ანგარიშისთვის. სხვა ნებისმიერი მოთხოვნა აბრუნებს `403`-ს upstream-თან დაკავშირების გარეშე. გამომძახებლის
  `Authorization` ჰედერი (`$TOKEN$` placeholder-ის ჩათვლით) იგნორირებულია: OmniRoute
  ჩასვამს კავშირის access token-ს, საჭიროების შემთხვევაში კი ჯერ განაახლებს მას ვადის
  ამოწურვამდე ცოტა ხნით ადრე, და გადააგზავნის მხოლოდ დაშვებულ ჰედერებს (`anthropic-beta`; `OpenAI-Beta`, `Originator`, `Chatgpt-Account-Id`;
  `Accept`, `Content-Type`). თუ `Chatgpt-Account-Id` არ არის მითითებული, ნაგულისხმევად გამოიყენება შენახული workspace id.
  მოთხოვნებს ვადა 15 წამის შემდეგ ეწურება და ისინი იყენებენ კავშირის proxy-ს.
- `reset-quota` უცვლელად ტოვებს terminal მდგომარეობებს (banned, expired, credits_exhausted). უცნობი
  `auth_index` აბრუნებს `404`-ს.

**ავთენტიფიკაცია:** dashboard-ის სესია ან `manage` scope-ით API-გასაღები, რომელიც საჭიროა მაშინაც კი, როცა შესვლა გამორთულია
(გზები შედის `ALWAYS_PROTECTED_API_PATHS`-ში). მხოლოდ inference-ისთვის განკუთვნილი გასაღებები იღებენ `403`-ს. წყარო:
`src/lib/cliproxyCompat/managementApi.ts`.

synced/imported მოდელებისთვის `PUT /api/provider-models` იღებს `provider`, `modelId` და `maxOutputTokenOverride`: დადებითი მთელი რიცხვი აყენებს ხელით გამომავალი ნიშნის თავსახურს და `null` ასუფთავებს მას ნაგულისხმევის აღსადგენად. `GET /api/provider-models?provider=<provider>` აბრუნებს ამ მნიშვნელობებს `modelOutputOverrides` ში, მათ შორის მოდელებს მორგებული მოდელის მწკრივის გარეშე. Override იყენებს Runtime `max_output_tokens` შესაძლებლობებს და გადარჩება მოდელის ხელახლა სინქრონიზაციას. OpenAI-თან თავსებადი პროვაიდერის გვერდი გთავაზობთ იგივე edit/clear კონტროლს და მარკირებს მოდელებს აშკარა ხედვის მხარდაჭერით.

თავსებადი პროვაიდერის კვანძზე, ჩაწერის ბილიკები (`POST`, `PUT`, `PATCH`, `DELETE` და `/api/provider-models/validate-and-add`) ინახავს მოდელის id-ს, როგორც შიშველი ზემოთ ნაკადის id-ს: პრეფიქსირებული სიიდან ჩასმული id-ს აქვს კვანძის საკუთარი პრეფიქსის ნებისმიერი წამყვანი დასტა ჩამოშლილი და პასუხები ეხმიანება შენახულ ID-ს. კანონიკური პროვაიდერების დაჭრილი ID (მაგ. `nvidia/nemotron-…`) ინახება სიტყვასიტყვით. `/v1/models` არასოდეს ასხივებს დაწყობილ `<prefix>/<prefix>/<model>` id-ს.

ჩეთის დასრულებების მორგებული კვანძები ადაპტირებენ მკაფიო მსჯელობის გამორთვას ზემოთ დინებაში. წარმატებული კავშირის ტესტი ავტომატურად ირჩევს ჩატის შაბლონის კონტროლს თითოეული ID მოდელისთვის, რომლის `/models` ჩანაწერი ადასტურებს აღიარებულ `owned_by` მნიშვნელობას: `vllm`, `sglang` ან `llamacpp`. გამჭვირვალე OpenAI-თან თავსებადი სახვევებმა შეიძლება შეინარჩუნონ ორიგინალური მოდელის ჩანაწერი ჩადგმული `openai` ობიექტის შიგნით; აღმოჩენა მოჰყვება სამ ასეთ კონვერტს. დაკარგული, უცნობი ან კონფლიქტური საკუთრების მქონე მოდელები ინარჩუნებენ ჩვეულებრივ OpenAI ქცევას. Detection ხელახლა იყენებს კატალოგის არსებულ მოთხოვნას, არ წარმოქმნის დასრულების ჟეტონებს და გაუქმებულია კავშირის ბოლო წერტილის შეცვლისას.

ქცევის დასამაგრებლად, რომელიც არ ასახავს ამ მეტამონაცემებს, გამოიყენეთ არსებული ნაწილობრივი პროვაიდერის განახლება API:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

გაგზავნე ეს სხეული `PUT /api/providers/<connection-id>` ერთად. ამასთან დაკავშირებით, `none` ის აშკარა მსჯელობის ძალისხმევა იგზავნება როგორც `chat_template_kwargs.thinking=false` და `chat_template_kwargs.enable_thinking=false`. ექსპლიციტური მშობლიური შაბლონის მნიშვნელობები რჩება ავტორიტეტული, თუ სერვერის მხარის მსჯელობის წესი არ აიძულებს ძალისხმევას. პარამეტრი მოქმედებს მხოლოდ მაშინ, როდესაც მორგებული OpenAI-თან თავსებადი კავშირი აგზავნის ჩატის დასრულებების ორგანოს; პასუხების მოთხოვნები და ჩვეულებრივი პროვაიდერები ინარჩუნებენ მშობლიურ მოთხოვნის ფორმას. დააყენეთ `reasoningControl` `openai` ზე, რათა აიძულოთ ჩვეულებრივი OpenAI `reasoning_effort` გავლა, ან გამოტოვეთ it/set ზე `null` ავტომატური ამოცნობის გამოსაყენებლად.

Claude Code ავტომატური რეჟიმის კლასიფიკატორი ითხოვს ნაგულისხმევი მშობლიური აზროვნების გამორთვას, როდესაც ისინი არ შეიცავს აშკარა მსჯელობის კონტროლს. Detection იყენებს კლასიფიკატორის სისტემის მარკერს Claude-ის ფორმატის მოთხოვნებში და არა მოდელების სახელებს ან დასრულების ლიმიტებს. სხეულის აშკარა კონტროლი, მხარდაჭერილი effort/thinking სათაურები, მარშრუტიზაციის წესები და გადაწყვეტილი მოდელის ძალისხმევა ინარჩუნებს არსებულ პრიორიტეტს. კლასიფიკატორის ორივე სტადია ინარჩუნებს მოთხოვნებს, დასრულების ლიმიტებს, გაჩერების თანმიმდევრობებს და რეალურ ზემო დინებაში ნებართვის ვერდიქტებს; მეორე ეტაპს მაინც შეუძლია აწარმოოს მოთხოვნილი თვალსაჩინო მსჯელობა, როგორც ჩვეულებრივი ტექსტი.

#### მოდელის ლიმიტის წარმოშობა

`GET /api/models?withLimits=1` (ასევე `true`; `0`/`false` ან მისი გამოტოვება ინარჩუნებს ნაგულისხმევ დატვირთვას უცვლელად) ყველა მოდელის მწკრივს ამატებს `contextWindow`, `maxInputTokens`, `maxOutputTokens` და `capsSource` ობიექტს. `capsSource` ასახელებს წესს, რომელიც აწვდიდა თითოეულ ლიმიტს, ამიტომ გასაკვირი ლიმიტი (მაგალითად, 128k 1M მოდელზე) შეიძლება მივაკვლიოთ მის წარმოშობას. გადაწყვეტილი მნიშვნელობები იგივეა, რაც მარშრუტიზაციის გამოყენებას; დროშა მხოლოდ ამატებს ველებს და არასოდეს ცვლის მნიშვნელობას. ნებისმიერი სხვა `withLimits` მნიშვნელობა უარყოფილია `400` ით.

### ვიდეო ჩარჩოს საბურღი

`GET /api/v1/video-bridge/drilldown` კითხულობს დამქირავებლებთან დაკავშირებულ გაუმჭვირვალე სახელურს, რომელიც დაბრუნდა `x-omniroute-video-drilldown` ში ცალსახად დათანხმებული Video Bridge მოთხოვნის შემდეგ. წაკითხვისთვის და `DELETE` ყოველთვის სჭირდება მოქმედი API გასაღები და ოპერატორის დამოუკიდებელი `modalityBridgeVideoDrilldownRemoteEnabled` ნებართვა. წარმოების შეკავება დამატებით მოითხოვს `modalityBridgeVideoDrilldownEnabled` და მკაცრი თითო ნაწილი `drilldown: true`. თუ გასაღებს აქვს ცარიელი ბოლო წერტილის დასაშვები სია, ის უნდა შეიცავდეს `video` როგორც GET სთვის, ასევე DELETE, მიუხედავად იმისა, აბონენტი იყენებს `/v1` თუ `/api/v1`.

GET შეკითხვა: საჭიროა `handle`; არასავალდებულო `variant` (`preview`, `standard`, `detail`), `limit` (1–8; მემკვიდრეობითი `frames` მიღებულია, მაგრამ შეუძლებელია `limit` სთან კომბინირება), ნულზე დაფუძნებული `page` და `start`/`end` წამი. როდესაც ორივე ფოკუსის საზღვრები მიწოდებულია, `end` უნდა იყოს `start` ზე მეტი. Duplicate/unknown მოთხოვნის გასაღებები უარყოფილია. წარმატებული პასუხები შეიცავს `derivation`, `durationSeconds`, `frames`, `hasMore`, `page`, `variant` და არჩევით `focusWindow`; no-store JSON არის 32 MiB, Base64 ჩათვლით. დიდი გამომავალი აბრუნებს 413; მოითხოვეთ ნაკლები ჩარჩო.

`DELETE /api/v1/video-bridge/drilldown?handle=...` აბრუნებს `{ "removed": 0|1 }`. უცნობი, ვადაგასული და ჯვარედინი კლავიშების GETs არ განარჩევენ 404 პასუხებს; cross-key DELETE ვერ წაშლის მფლობელის ჩანაწერს. გამორთული წვდომა აბრუნებს 403-ს, missing/invalid ავთენტიფიკაციას 401, არასწორი მოთხოვნების 400-ს, გაუქმების 499-ს და დროებით შეცდომებს 503-ს. სახელურები არის პროცესის ლოკალური, ვადა ეწურება ათი წუთის შემდეგ და არ გადარჩება გადატვირთვის შემდეგ. ახალი სახელურები იყენებენ `v1.` პლუს 32-ბაიტიანი შემთხვევითი Base64URL ჟეტონს; შენახულია მხოლოდ სიმბოლური ჰეშები. Legacy 64-hex ჟეტონები რჩება სინტაქსურად იკითხება თავსებადობისთვის. თანხმობის, კვოტებისა და ვარიანტების დერივაციის დეტალებისთვის იხილეთ [ვიდეო ხიდის დამცავი მოაჯირები](../security/GUARDRAILS.md#video-bridge-videobridgets-videobridgepipelinets).

### ვერსიის და გამოშვების არხი

```bash
GET /api/system/version
```

Loopback-მხოლოდ მართვის მარშრუტი (admin auth). აბრუნებს გაშვებულ ვერსიას, უახლეს გამოქვეყნებულ ვერსიას და ავტომატური განახლების სტატუსს. `releaseChannel` და `channels` არის დანამატის ველები (რკინიგზა 3.8.54); `channel` ინარჩუნებს თავის მნიშვნელობას — განლაგების რეჟიმში, რომელსაც იყენებს დაფის განახლება (`npm`, `source` ან `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm არხი გაშვებული build-ისთვის: `nightly` `-nightly.*` ვერსიებისთვის, `next` სხვა წინასწარი გამოშვებებისთვის (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` უფრო ძველი მაიორის სტაბილური ვერსიისთვის, ვიდრე `channels.latest`, წინააღმდეგ შემთხვევაში `latest`. იგივე წესები, როგორც `scripts/release/dist-tag.mjs`, რომელიც არჩევს npm dist-tag-ს გამოქვეყნების დროს.
- `channels` — გამოქვეყნდა თითოეული დისტანციური ტეგის ხელმძღვანელი, `npm view omniroute dist-tags` დან (რეესტრი HTTP სარეზერვო), ქეშირებული იგივე 10 წუთიანი TTL როგორც `latest`. `latest` ყოველთვის იმყოფება (უბრუნდება `latest` ველს, შემდეგ `"unavailable"`); `next`, `nightly` და `lts` ჩნდება მხოლოდ მაშინ, როდესაც ეს dist-tag არსებობს. `Cache-Control: no-cache` მოთხოვნა განაახლებს ორივე ძიებას.

არხის მოდელი (`latest` = v3 4.0 GA მდე, `next` = rc, `nightly` = `develop` builds, `lts` = v3 პატჩები 4.0 GA ის შემდეგ) აღწერილია `docs/ops/RELEASE_STRATEGY.md` ში.

## აუდიოს ტრანსკრიფცია

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

აუდიოფაილების ტრანსკრიფცია ნებისმიერი კონფიგურირებული STT პროვაიდერის გამოყენებით. გზის პირველი
სეგმენტი ირჩევს ნატიურ პროვაიდერს (`openai/…`, `deepgram/…`). Gateway-ები, რომლებიც
სხვა მომწოდებლის მოდელს ხელახლა აქვეყნებენ, იყენებენ კვალიფიციურ id-ს
(`openrouter/deepgram/nova-3`).

**მოთხოვნა:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**პასუხი:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**მოდელის id-ების მაგალითები:** `openai/whisper-1` (საჭიროებს OpenAI-ის გასაღებს),
`openrouter/deepgram/nova-3` (საჭიროებს OpenRouter-ის გასაღებს),
`deepgram/nova-3` (საჭიროებს ნატიურ Deepgram-ის გასაღებს). უბრალო
`deepgram/nova-3` მოთხოვნა **არ** იყენებს OpenRouter-ს.

**მხარდაჭერილი ფორმატები:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

**Gemini Live (`gemini/gemini-3.5-transcribe-live`):** ფაილის რეჟიმში ტრანსკრიფცია Gemini Live-ის
WebSocket-ის მეშვეობით (საჭიროებს Gemini API-ის გასაღებს). ატვირთული ფაილი გარდაიქმნება
16 kHz mono PCM-ად `ffmpeg`-ის გამოყენებით
(ის უნდა იყოს `PATH`-ში, გარდა იმ შემთხვევისა, როდესაც ფაილი უკვე 16 kHz mono PCM WAV-ია), გადაიცემა სესიაში და
დასრულებული ტექსტი ბრუნდება `{ "text": "..." }` ფორმით. არასავალდებულო `language` და `prompt` ველების მნიშვნელობები
გადაეცემა შემდგომ. შეზღუდვები: 25 MiB-ზე დიდი ატვირთვები ან 10 წუთზე ხანგრძლივი დეკოდირებული აუდიო აბრუნებს
`413`-ს; თუ კონვერტაცია 60 წამზე მეტხანს გაგრძელდა, პროცესი წყდება და ბრუნდება `504`. API-ის გასაღები იგზავნება
მხოლოდ `x-goog-api-key` სათაურში და არასდროს WebSocket-ის URL-ში.

გამოიყენეთ ეს ალიასები, როდესაც ინტეგრაციას არ შეუძლია `Authorization` header-ის დამატება და API გასაღების base URL-ში ჩაშენება სჭირდება.

```bash

GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-ის სტილის ჩატის ალიასები
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-ს სტილის ალიასები
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

მაგალითი:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

შენიშვნები:

- ტოკენიზებული ალიასები ხელახლა იყენებენ იმავე დამმუშავებლებს, რომლებსაც `/v1/*` და `/api/tags`; პასუხების სტრუქტურები უცვლელი რჩება.
- უპირატესობა მიანიჭეთ `Authorization: Bearer ...`-ს, როდესაც კლიენტს მორგებული header-ების მხარდაჭერა აქვს.
- URL-ზე დაფუძნებული ტოკენები შეიძლება გამოჩნდეს reverse-proxy-ის ჟურნალებში, ბრაუზერის ისტორიასა და OmniRoute-ის გარეთ არსებულ ტელემეტრიაში. განიხილეთ ისინი თავსებადობის ვარიანტად და არა ავთენტიფიკაციის ნაგულისხმევ რეჟიმად.

```bash
# ყველა API გასაღებისთვის ბიუჯეტის სტატუსის მიღება
```

## ტოკენის ლიმიტები

თითოეული API-გასაღებისთვის **ტოკენის** ბიუჯეტები (ცალკე ზემოთ აღწერილი USD-ზე დაფუძნებული ბიუჯეტისგან). ისინი მოთხოვნის გზაზე inline რეჟიმში მოწმდება: როდესაც გასაღების მიმდინარე ფანჯრის გამოყენება ლიმიტს მიაღწევს, მოთხოვნები უარყოფილია `429 Too Many Requests` შეცდომით. ლიმიტები შეიძლება მიესადაგოს კონკრეტულ `model`-ს, `provider`-ს ან გავრცელდეს გასაღების მასშტაბით `global`-ურად; როდესაც მოთხოვნას რამდენიმე ლიმიტი ემთხვევა, ძალაში შედის მათგან ყველაზე მკაცრი.

```bash
# გასაღების ტოკენის ლიმიტების სიის მიღება (მოიცავს ფანჯრის მიმდინარე გამოყენებას)
GET /api/usage/token-limits?apiKeyId=key-123

# ტოკენის ლიმიტის შექმნა ან განახლება
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ტოკენის ლიმიტის წაშლა id-ის მიხედვით
DELETE /api/usage/token-limits?id=tl-abc
```

> **სქემის შენიშვნები** (`setTokenLimitSchema`): `apiKeyId` და `scopeType` (`model` | `provider` | `global`) სავალდებულოა. `scopeValue` სავალდებულოა, თუ `scopeType` არ არის `global` (მაგ., მოდელის id `model` მასშტაბისთვის, პროვაიდერის id `provider` მასშტაბისთვის). `tokenLimit` უნდა იყოს დადებითი მთელი რიცხვი (სტრიქონიდან გარდაიქმნება). არასავალდებულო ველები: `id` (შექმნისას გამოტოვეთ, განახლებისას მიუთითეთ), `resetInterval` (`daily` | `weekly` | `monthly`, ნაგულისხმევია `monthly`), `resetTime` (`HH:MM`), `enabled` (ნაგულისხმევია `true`). `GET` პასუხები თითოეულ ლიმიტს ამდიდრებს `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` და `nextResetAt` ველებით. ეს არის მართვის კლასის endpoint (ავტორიზაცია ცენტრალურად, authz pipeline-ის მიერ, მოწმდება).

## მოთხოვნის დამუშავება

1. კლიენტი აგზავნის მოთხოვნას `/v1/*`-ზე
2. მარშრუტის დამმუშავებელი იძახებს `handleChat`, `handleEmbedding`, `handleAudioTranscription` ან `handleImageGeneration`
3. ხდება მოდელის განსაზღვრა (პირდაპირი პროვაიდერი/მოდელი ან alias/combo)
4. ადგილობრივი DB-დან ირჩევა ანგარიშის ხელმისაწვდომობის მიხედვით გაფილტრული ავტორიზაციის მონაცემები
5. ჩატისთვის: `handleChatCore` ამოწმებს სემანტიკურ/signature cache-ს და განსაზღვრავს combo-ს კომპრესიის პარამეტრებს
6. ჩართული მდგომარეობისას პროაქტიული კომპრესია ხორციელდება პროვაიდერისთვის თარგმნამდე (`lite`, Caveman, RTK ან stacked)
7. პროვაიდერის executor აგზავნის upstream მოთხოვნას
8. პასუხი კვლავ ითარგმნება კლიენტის ფორმატში (chat-ისთვის) ან ბრუნდება უცვლელად (embeddings/images/audio)
9. იწერება გამოყენება, კომპრესიის ანალიტიკა და მოთხოვნის ლოგები
10. შეცდომების შემთხვევაში fallback გამოიყენება combo-ს წესების შესაბამისად

არქიტექტურის სრული მითითება: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## მდგრადობა (გაფართოებული)

OmniRoute გთავაზობთ დროებითი წარუმატებლობების მართვის სამ დამოუკიდებელ მექანიზმს; ქვემოთ მოცემული მართვის endpoint-ები ოპერატორებს მათი წაკითხვისა და გადაფარვის საშუალებას აძლევს:

| ფარგლები            | მდგომარეობის შენახვა                                    | წაკითხვა                                  | გადაყენება / გასუფთავება                                                      |
| ------------------- | ------------------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------- |
| პროვაიდერის breaker | `domain_circuit_breakers` + მეხსიერებაში                | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                                  |
| კავშირის cooldown   | `rateLimitedUntil` პროვაიდერის კავშირებზე               | `/api/rate-limits`, `/api/providers/[id]` | (ხელახლა ჩართვა ხდება lazy რეჟიმში; გასუფთავება შესაძლებელია provider PUT-ით) |
| მოდელის lockout     | მეხსიერებაში არსებული მოდელის ხელმისაწვდომობის registry | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                                      |

`PATCH /api/resilience` იღებს პროვაიდერის breaker-ის გადაფარვებს `providerBreaker.oauth` და `providerBreaker.apikey`-ში. თითოეული პროფილი მხარს უჭერს `degradationThreshold`, `failureThreshold` და `resetTimeoutMs` ველებს; იგივე ველები ხელმისაწვდომია Dashboard → Settings → Resilience-ში.

```bash
# ერთი მოდელის lockout-ის გასუფთავება
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# ყველა lockout-ის წაშლა
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

სრული კონცეპტუალური ცნობარი და breaker-ის ნაგულისხმევი მნიშვნელობები იხილეთ [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" და [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Rate-Limit რიგი და ავტომატური ჩართვის უსაფრთხოების მექანიზმი

- **მხარდაჭერილი ჩაწერის გზა**: `POST /api/rate-limits` body-ით `{"connectionId": "<id>", "enabled": true|false}` წარმოადგენს მხარდაჭერილ მართვის endpoint-ს კავშირისთვის rate-limit დაცვის ჩასართავად ან გამოსართავად. `PUT /api/providers/[id]` განზრახ არ ცვლის ან არ აბრუნებს `rateLimitProtection`-ს (#11278).
- **`enabled: false`-ის სემანტიკა**: `enabled: false`-ის დაყენება კავშირისთვის explicit დაცვას ხსნის, თუმცა **აქტიურ API-key კავშირს გლობალური ავტომატური ჩართვის უსაფრთხოების მექანიზმიდან (`autoEnableApiKeyProviders = true`) არ გამორთავს**. `reconcileEnabledConnections`-ში (`open-sse/services/rateLimitManager.ts`) `false` და `undefined` ეკვივალენტურია; explicit დაცვის არმქონე აქტიური API-key კავშირები ავტომატური ჩართვის უსაფრთხოების მექანიზმით დაცული რჩება.
- **გლობალური გამორთვა**: API-key კავშირების rate-limit რიგების გარეშე გასაშვებად, გამორთეთ უსაფრთხოების მექანიზმი გლობალურად `RATE_LIMIT_AUTO_ENABLE=false`-ის (env) ან `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`-ის საშუალებით (Settings → Resilience / `PATCH /api/resilience`).

## A2A სერვერი

OmniRoute ავლენს A2A (Agent-to-Agent) JSON-RPC 2.0 endpoint-ს და REST wrapper-ს ინსპექტირებისა და dashboard-ის გამოყენებისთვის.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # არასავალდებულოა, თუ OMNIROUTE_API_KEY დაყენებული არ არის
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

მხარდაჭერილი მეთოდები (ყველა მათგანი `settings.a2aEnabled`-ზეა დამოკიდებული):

## დამცავი მექანიზმები

შეამოწმეთ გაშვების დროის დამცავი მექანიზმები (PII-ის აღმოჩენა, prompt injection-ის აღმოჩენა, ხედვის ხიდი). დამცავი მექანიზმები მუშაობს ყველა მოთხოვნაზე; თითოეული გამოძახებისთვის უარის თქმა ხორციელდება `x-omniroute-disabled-guardrails` მოთხოვნის სათაურის მეშვეობით — შენახული ჩართვის/გამორთვის ზედაპირი არ არსებობს.

| მეთოდი | გზა                    | აღწერა                                                                                        |
| ------ | ---------------------- | --------------------------------------------------------------------------------------------- |
| GET    | `/api/guardrails`      | რეგისტრირებული დამცავი მექანიზმებისა და მათი სტატუსის სია (სახელი / ჩართულია / პრიორიტეტი)    |
| POST   | `/api/guardrails/test` | ზარისწინა მილსადენის საცდელი გაშვება ნიმუშის შეყვანაზე — body: `{input, disabledGuardrails?}` |

იხილეთ [უსაფრთხოება > დამცავი მექანიზმები](../security/GUARDRAILS.md) სრული დეტალებისთვის.

## ავთენტიფიკაცია

იხილეთ [Management Authentication](../guides/MANAGEMENT-AUTH.md) ოთხი
საიდენტიფიკაციო მონაცემების ოჯახის შესახებ (დაფის სესია, ლოკალური CLI ტოკენი, `oma_live_…` Access Token, manage-სკოპის API გასაღები) და იმის გასაგებად, თუ რით განსხვავდებიან ისინი inference გასაღებებისგან.

- Dashboard-ის მარშრუტები (`/dashboard/*`) იყენებს `auth_token` ქუქის
- შესვლა იყენებს შენახულ პაროლის ჰეშს; სარეზერვო ვარიანტია `INITIAL_PASSWORD`
- `requireLogin` გადართვადია `/api/settings/require-login`-ის მეშვეობით
- `/v1/*` მარშრუტებს სურვილისამებრ ესაჭიროება Bearer API გასაღები, როდესაც `REQUIRE_API_KEY=true`
- „management token“ / „management-scoped API key“ ამ ცნობარში ნიშნავს ამ სახელმძღვანელოში აღწერილ ერთ-ერთ ოჯახს — არა დამატებით, განუსაზღვრელი ტიპის საიდუმლოებას

> **მტეხი ცვლილება (v3.8.0)** — `/api/v1/agents/tasks/*` და cooldown-ის მართვის endpoint-ებს ახლა ესაჭიროება **management auth** (Dashboard-ის `auth_token` ქუქი ან management-სკოპის API გასაღები). კლიენტები, რომლებიც ამ მარშრუტებს ადრე ავთენტიფიკაციის გარეშე იძახებდნენ, მიიღებენ `401 Unauthorized` პასუხს. იხილეთ commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
