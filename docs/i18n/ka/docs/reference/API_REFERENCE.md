## ჩატის დასრულებები

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### მორგებული სათაურები

| სათაური                  | მიმართულება | აღწერა                                                                                                                                                                                                                    |
| ------------------------ | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | მოთხოვნა    | კეშის გვერდის ასავლელად დააყენეთ `true`                                                                                                                                                                                   |
| `x-omniroute-no-memory`  | მოთხოვნა    | ამ მოთხოვნისთვის მეხსიერებისა და უნარების ინექციის გამოსატოვებლად დააყენეთ `true` (იმეორებს კეშის გამოტოვების ქცევას; თავიდან აგაცილებთ თითოეული გამოძახების ტოკენებისა და ღირებულების ზედნადებს)                         |
| `X-OmniRoute-Progress`   | მოთხოვნა    | პროგრესის მოვლენებისთვის დააყენეთ `true`                                                                                                                                                                                  |
| `X-Session-Id`           | მოთხოვნა    | გარე სესიის აფინურობისთვის განკუთვნილი მიბმული სესიის გასაღები                                                                                                                                                            |
| `x_session_id`           | მოთხოვნა    | ასევე მიიღება ქვედატირიანი ვარიანტი (პირდაპირი HTTP)                                                                                                                                                                      |
| `X-OmniRoute-Session-Id` | მოთხოვნა    | გამომძახებლის მიერ მოწოდებული სესიის/საუბრის ტეგი (ასევე მიეწოდება მეხსიერებას). არსებობისას უცვლელად ინახება `call_logs.session_tag`-ში, სესიაზე ღირებულების მისაკუთვნებლად (#8249) — არარსებობისას არასოდეს გენერირდება |
| `Idempotency-Key`        | მოთხოვნა    | დუბლირების აღმომჩენი გასაღები (5-წამიანი ფანჯარა)                                                                                                                                                                         |
| `X-Request-Id`           | მოთხოვნა    | დუბლირების აღმომჩენი ალტერნატიული გასაღები                                                                                                                                                                                |
| `x-omniroute-connection` | მოთხოვნა    | ერთი მოდელის მოთხოვნის მიბმა პროვაიდერის ერთ კავშირზე (ანგარიშზე) მისი id-ის მიხედვით — იხილეთ [ანგარიშზე მიბმა თითოეული მოთხოვნისთვის](#account-pinning-per-request)                                                     |
| `X-OmniRoute-Cache`      | პასუხი      | `HIT` ან `MISS` (არასტრიმინგული)                                                                                                                                                                                          |
| `X-OmniRoute-Idempotent` | პასუხი      | `true`, თუ დუბლირება აღმოიფხვრა                                                                                                                                                                                           |
| `X-OmniRoute-Progress`   | პასუხი      | `enabled`, თუ პროგრესის თვალყურის დევნება ჩართულია                                                                                                                                                                        |
| `X-OmniRoute-Session-Id` | პასუხი      | OmniRoute-ის მიერ გამოყენებული ფაქტობრივი სესიის ID                                                                                                                                                                       |
| `X-OmniRoute-Request-Id` | პასუხი      | მოთხოვნის კორელაციის id (როდესაც ცნობილია)                                                                                                                                                                                |
| `X-OmniRoute-Version`    | პასუხი      | OmniRoute-ის აგების ვერსია (ყოველთვის წარმოდგენილია)                                                                                                                                                                      |
| `X-OmniRoute-Cost-Saved` | პასუხი      | USD-ში გამოხატული თანხა, რომელიც კეშმა დაზოგა HIT-ისას (მხოლოდ კეშის თანხვედრები)                                                                                                                                         |
| `X-OmniRoute-Decision`   | პასუხი      | მარშრუტიზაციის ტრასა: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` არის კომბინაციის სტრატეგია, ან `single` არაკომბინირებული მოთხოვნისთვის) — დასრულების პასუხებში ყოველთვის წარმოდგენილია                |

> Nginx-ის შენიშვნა: თუ იყენებთ ქვედა ტირეს შემცველ სათაურებს (მაგალითად, `x_session_id`), ჩართეთ `underscores_in_headers on;`.

#### ანგარიშის მიბმა თითოეული მოთხოვნისთვის

როდესაც პროვაიდერს რამდენიმე კავშირი (ანგარიში ან გასაღები) აქვს, OmniRoute ჩვეულებრივ ერთ-ერთს
ანგარიშის შერჩევის საკუთარი სტრატეგიით ირჩევს. ამის ნაცვლად, მოთხოვნას შეუძლია ერთი კონკრეტული კავშირი
`x-omniroute-connection` სათაურის მეშვეობით მიაბას:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **სად ვიპოვოთ id.** გახსენით პროვაიდერის გვერდი მართვის პანელში
  (**მართვის პანელი → პროვაიდერები → <provider>**) და კავშირის
  მწკრივში დააწკაპუნეთ `xxxxxxxx…` id-ის ნიშნულზე — სრული კავშირის id დაკოპირდება.
- **რომელი მოთხოვნები ითვალისწინებს მას.** ერთმოდელიანი მოთხოვნები (`provider/model`)
  `/v1/chat/completions`, `/v1/messages` და `/v1/responses` მისამართებზე. კომბინაციები სათაურს უგულებელყოფს:
  თითოეული კომბინაციის ეტაპისთვის ანგარიში ამ ეტაპის საკუთარი კავშირის მეშვეობით მიაბით.
- **მიბმა მკაცრია და არა უპირატესობის მინიჭება.** გამოიყენება მხოლოდ მიბმული კავშირი.
  მოთხოვნის შიგნით წარმოქმნილი შეცდომა ანგარიშის დაყოვნების პერიოდს აღრიცხავს, მაგრამ **არ**
  გადაერთვება იმავე პროვაიდერის სხვა ანგარიშზე.
- **დაყოვნების პერიოდი და კვოტა მიბმას აუქმებს.** სანამ მიბმული კავშირი დაყოვნების პერიოდშია,
  კვოტა ამოწურული აქვს ან კვოტის პოლიტიკითაა დაბლოკილი, შემდგომი მოთხოვნები პროვაიდერის
  სხვა კავშირებზე გადაერთვება, ზუსტად ისე, როგორც მიუბმელი ტრაფიკი.
- **უცნობი ან გამორთული id-ები შეცდომას იწვევს.** id, რომელიც პროვაიდერის აქტიურ პულში არ არის (წაშლილია,
  დეაქტივირებულია ან სხვა პროვაიდერს ეკუთვნის), არცერთ შესაბამის ანგარიშს არ ტოვებს, ამიტომ მოთხოვნა
  სხვა მიმართულებით შეუმჩნევლად გადამისამართების ნაცვლად შეცდომით სრულდება.

Claude Code მორგებულ სათაურებს `ANTHROPIC_CUSTOM_HEADERS`-ის მეშვეობით აგზავნის. განათავსეთ ის
`~/.claude/settings.json`-ის `env` ბლოკში, ან პროექტის დონის `.claude/settings.json`-ში, რათა თითოეული
პროექტისთვის განსხვავებული ანგარიში მიაბათ:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

წყარო: `src/sse/handlers/chat.ts` (სათაურის წაკითხვა), `src/sse/services/auth.ts` და
`src/sse/services/sessionAffinityPin.ts` (მიბმის გაუქმება და პულში არყოფნის შემოწმება).

> **ღირებულების ტელემეტრიის სათაურები:** წარმატებული არანაკადური პასუხები ასევე შეიცავს `X-OmniRoute-*` ღირებულების ტელემეტრიის ნაკრებს — `X-OmniRoute-Response-Cost` (USD, ფიქსირებული 10 ათწილადი ნიშნით; `0.0000000000` უფასო/შეუფასებელი შემთხვევებისთვის), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` და `X-OmniRoute-Fallback-Attempts` (მხოლოდ მაშინ, როდესაც > 0), ასევე `X-OmniRoute-Request-Id` და `X-OmniRoute-Version`. მათ აბრუნებს ჩატის დასრულებები, `/v1/responses`, `/v1/messages` **და მედიის საბოლოო წერტილები** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` და `/v1/moderations` (ღირებულება ყოველთვის `0`). როდესაც ფასები ხელმისაწვდომია, მედიის ღირებულება გამოითვლება მოდალობის მიხედვით (თითოეულ სურათზე, წამზე, სიმბოლოზე ან ძიების ერთეულზე), წინააღმდეგ შემთხვევაში კი არის `0` (შეცდომისას მოთხოვნა არ იბლოკება).

> **ქეშში დამთხვევის ღირებულების სემანტიკა:** სემანტიკურ ქეშში დამთხვევისას (`X-OmniRoute-Cache-Hit: true`) ზედა დონის სერვისთან გამოძახება არ სრულდება, ამიტომ `X-OmniRoute-Response-Cost` არის `0.0000000000` (დამთხვევის მომსახურების **დამატებითი** ღირებულება). თავდაპირველი/სავარაუდო ღირებულება ცალკე აისახება `X-OmniRoute-Cost-Saved`-ში. ბილინგის მომხმარებლებმა უნდა შეაჯამონ `X-OmniRoute-Response-Cost` (ქეშში დამთხვევა უფასოა); ქეშის ანალიტიკას შეუძლია `X-OmniRoute-Cost-Saved`-ის აგრეგირება.

## ექსკლუზიური მართული სესიის იჯარები

ექსკლუზიური მართული სესიის იჯარა არჩევითი, კლიენტისგან დამოუკიდებელი მარშრუტიზაციის კონტრაქტია: ერთი აქტიური მფლობელი
ფლობს ერთ შესაფერის OmniRoute კავშირს. ის არ გასცემს მოდელს იჯარით, არ მოითხოვს OAuth-ს, არ განსაზღვრავს
კონკრეტულ კლიენტს და არ მოითხოვს კონკრეტულ პროვაიდერს.

ავთენტიფიკაციისთვის გამოყენებულ API გასაღებს უნდა ჰქონდეს `lease:exclusive` მოქმედების სფერო და ცალსახად მითითებული, არაცარიელი
`allowedConnections` სია. მონაცემთა ბაზის ცვლილების საზღვარი ორივე ველს ერთობლივად ამოწმებს გასაღების
შექმნისა და ნაწილობრივი განახლებების დროს.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

წარმატებული მიღების, განახლებისა და გათავისუფლების პასუხები შეიცავს დროის ნიშნულებს, `state`-ს და ზუსტ დადებით
`generation`-ს, მაგრამ არასდროს — არჩეულ კავშირს ან ავტორიზაციის მონაცემებს. განახლებისა და გათავისუფლებისას
თაობა JSON სხეულში გადაიცემა:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

აქტიური იჯარის მფლობელს შეუძლია ცალსახად მოითხოვოს კონფიდენციალურობისთვის უსაფრთხო საჩვენებელი მეტამონაცემები თავისი მიმდინარე მიბმისთვის:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

ეს არჩევითი სტატუსის მოქმედება ერთ მონაცემთა ბაზის ტრანზაქციაში იზღუდება გაუმჭვირვალე მფლობელით, ავთენტიფიცირებული მართული API გასაღებითა და ზუსტი
აქტიური თაობით. `displayName` მხოლოდ კონფიგურირებული კავშირის სახელია, რომელსაც დასაწყისისა და დასასრულის ჰარეები მოცილებული აქვს;
ის არის `null`, როდესაც უსაფრთხო კონფიგურირებული სახელი არ არსებობს. OmniRoute არასდროს ანაცვლებს მას
ელფოსტის მისამართით ან გენერირებული ანგარიშის იდენტობით. პროვაიდერის მნიშვნელობა არასენსიტიური საჩვენებელი წარწერაა და არასდროს
არის გენერირებული თავსებადი პროვაიდერის იდენტიფიკატორი. ავტორიზაციის მონაცემები, ტოკენები, cookie-ები, კავშირის ან API
გასაღების ნედლი იდენტიფიკატორები, მფლობელის ჰეშები, შემზღუდავი საიდუმლოებები და მარშრუტიზაციის შიდა მონაცემები გამორიცხულია.

არასწორი გასაღებით, არასწორი მფლობელით, მოძველებული თაობით, არარსებული, ვადაგასული, გათავისუფლებული და გაუქმებული იჯარების ძიებები
ყველა აბრუნებს ერთსა და იმავე `409 LEASE_FENCE_STALE` შეცდომას კავშირის მეტამონაცემების გარეშე. კლიენტს, რომელმაც მოცულობის ლოდინის პასუხი მიიღო, დასათვალიერებელი აქტიური მიბმა არ აქვს. როდესაც მარშრუტიზაცია აქტიურ იჯარას სხვა კავშირზე გადაიყვანს,
იგივე თაობა ძალაში რჩება და სტატუსი ატომურად აბრუნებს ახალ მიბმას, არასდროს — ძველს.
არსებული კლიენტები უცვლელი რჩება, რადგან მიღების, განახლების, გათავისუფლებისა და ლოდინის პასუხები
თავიანთ წინა სტრუქტურებს ინარჩუნებს.

ეს სერვერის კონტრაქტი არ ცვლის სტანდარტულ OpenAI Codex `/status`-ს. სტანდარტული Codex ამჟამად აჩვენებს თავის
მოდელის პროვაიდერსა და ჩაშენებული ავთენტიფიკაციის/ანგარიშის მდგომარეობას, მაგრამ არ ასახავს ნებისმიერი მორგებული
პროვაიდერის ანგარიშის მეტამონაცემებს; კლიენტის მომავალმა ინტეგრაციამ უნდა გამოიძახოს ეს მოქმედება და გადაწყვიტოს, როგორ
აჩვენოს `connection.displayName`.

ამის შემდეგ ყოველი მართული ინფერენციის მოთხოვნა ორივე საკონტროლო სათაურს გადასცემს:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ზუსტი მფლობელი, თაობა, აქტიური კავშირი და ავთენტიფიცირებული API გასაღები ყოველი მხარდაჭერილი ზედა დონის სერვისთან დაკავშირების მცდელობის
უშუალოდ წინ მოწმდება. მფლობელისა და თაობის სხვა გასაღებით ხელახლა გამოყენება წარუმატებელია მაშინაც კი,
როდესაც ეს გასაღები იმავე კავშირს უშვებს. მფლობელების ნედლი მნიშვნელობები არ ინახება მუდმივად, არ იწერება ჟურნალში, არ რჩება
მოთხოვნის სნეპშოტში და არ გადაიგზავნება ზედა დონის სერვისთან.

დროებითი კონკურენცია აბრუნებს HTTP `429`-ს `Retry-After`-თან ერთად და:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

ეს პასუხი მხოლოდ იმას ნიშნავს, რომ ჩვეულებრივი შესაფერისი ნაკრები არაცარიელი იყო და ყველა თავისუფალი კანდიდატი
უცხო აქტიურ იჯარას ეკავა. მხარდაჭერის არმქონე მოდელები/პროვაიდერები, პოლიტიკასთან შეუსაბამობა, დაყოვნების პერიოდი, კვოტა,
მდგომარეობა და შესაფერისობის სხვა ჩვეულებრივი წარუმატებლობები OmniRoute-ის არსებულ პასუხებს ინარჩუნებს.

### `x-omniroute-compression`

შეკუმშვის გეგმის ცალკეული მოთხოვნის დონეზე ჩანაცვლება. აქვს უმაღლესი პრიორიტეტი — უპირატესია მარშრუტიზაციის კომბინაციის
ჩანაცვლებაზე, აქტიურ პროფილზე, ავტომატურ ტრიგერსა და პანელის ნაგულისხმევ პარამეტრზე. მნიშვნელობები:

| მნიშვნელობა   | ეფექტი                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------------- |
| `off`         | ამ მოთხოვნისთვის შეკუმშვა არ გამოიყენება.                                                                       |
| `default`     | პანელიდან მიღებული ნაგულისხმევი პროფილი (აქტიურ პროფილს უგულებელყოფს). დანაკარგიანი ძრავები გამორთული რჩება.    |
| `safe`        | მხოლოდ დუბლიკატების მოცილება და თეთრი სივრცეების შეკვეცა.                                                       |
| `allow-lossy` | ამ მოთხოვნისთვის ინარჩუნებს ოპერატორის გეგმას, შეჯამებებისა და სტილის გადაწერის ჩათვლით.                        |
| `engine:<id>` | ერთი ძრავა, როდესაც ის ჩართულია, მაგ. `engine:rtk`. ამ ძრავის გამოყენების არჩევა ცალკეული მოთხოვნისთვის.        |
| `<combo>`     | დასახელებული კომბინაცია, რომელიც ჯერ სახელით (რეგისტრის გაუთვალისწინებლად), შემდეგ კი იდენტიფიკატორით ემთხვევა. |

შენიშვნები:

- უცნობი მნიშვნელობები უგულებელყოფილია (მოთხოვნა არასდროს უარიყოფა); ამოხსნა ოპერატორის ჩვეულებრივ პრიორიტეტებზე გადადის.
- თუ რამდენიმე კომბინაციას ერთი და იგივე სახელი აქვს, ცალსახა შესაბამისობისთვის გადაეცით კომბინაციის **იდენტიფიკატორი**.
- კომბინაცია, რომლის სახელია `off` ან `default`, სახელით ვერ შეირჩევა (ჯერ ეს საკვანძო სიტყვები განიმარტება); ასეთ კომბინაციას მისი იდენტიფიკატორით მიმართეთ.
- შეკუმშვის მთავარი გადამრთველი მკაცრი ბარიერია: როდესაც შეკუმშვა გლობალურად გამორთულია, ეს სათაური მას ვერ ჩართავს.

გამოყენებული გეგმა პასუხის სათაურში აისახება:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

სადაც `<source>` არის ერთ-ერთი შემდეგიდან: `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ან `off`.

## ემბედინგები

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

ხელმისაწვდომი პროვაიდერები: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

კატალოგის იდენტიფიკატორების ფორმატია `provider/model` (მაგალითი: `jina-ai/jina-embeddings-v5-omni-small`). რეესტრში არსებული Jina-ს მოდელების მხოლოდ იდენტიფიკატორებიც (მაგალითად, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ასევე ამოიცნობა. Jina-ს embed/rerank/classify/segment ოპერაციები ჯერ მართვის პანელის `jina-ai` ავტორიზაციის მონაცემებს იყენებს; `JINA_AI_API_KEY` სათადარიგო ვარიანტია მხოლოდ მაშინ, როდესაც მართვის პანელის გასაღები არ არსებობს. `jina-reader` ბარათი განკუთვნილია მხოლოდ Reader-ისთვის / `r.jina.ai`-სთვის (`POST /v1/web/fetch`) და არასოდეს ემსახურება ემბედინგების ან rerank ოპერაციებს.

რეესტრის მოდელები, რომლებიც მულტიმოდალურ მხარდაჭერას აცხადებენ, ასევე იღებს პროვაიდერისგან დამოუკიდებელ 32-მდე სტრუქტურირებულ
ელემენტს. მედიაელემენტების ტიპებია `text`, `image`, `audio`, `video` და `document`. მათი მედიის `source`
არის ან `{"type":"url","url":"https://..."}`, ან
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
და ოჯახის ფსევდონიმი `jina-ai/jina-embeddings-v5-omni` → omni-small) ასევე იღებს Jina-ს მშობლიურ
EmbeddingsV5Request დოკუმენტებს და **უცვლელად გადააგზავნის მათ** მისამართზე `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

მშობლიური `{ image | audio | video | pdf }` მნიშვნელობები შეიძლება იყოს საჯარო HTTPS URL, `data:` URI ან დაუმუშავებელი
base64. OmniRoute ამ ობიექტებს სტრიქონებად არ გარდაქმნის და მშობლიურ სურათების URL-ებს არ ჩამოტვირთავს — საჯარო
მედიას თავად Jina იღებს. Jina-ს დამატებითი ველები (`task`, `normalized`, `truncate`, `embedding_type`)
გადაიგზავნება. მხოლოდ ტექსტისთვის განკუთვნილი Jina SKU-ები კვლავ უარყოფს არატექსტურ დოკუმენტებს.

უსაფრთხოებისა და ტრანსპორტირების შეზღუდვები:

- დისტანციური მედიის URL-ები უნდა იყოს საჯარო HTTPS. კანონიკური `{type,source:url}` ელემენტები
  სერვერის მხარეს ჩამოიტვირთება (გადამისამართებების ხელახალი შემოწმება, დროის ლიმიტი, ზომის შეზღუდვები, საჯარო DNS, კავშირის მიბმა) და
  პროვაიდერის გამოძახებამდე ჩაშენდება. Jina-ს მშობლიური `{image:"https://..."}` ელემენტები უცვლელად
  გადაიგზავნება იმავე საჯარო HTTPS შემოწმების შემდეგ; URL-ს Jina ჩამოტვირთავს.
- ჩაშენებული base64 მედია შეზღუდულია თითოეულ ელემენტზე დეკოდირებული 8 MiB-ით და მთელ მოთხოვნაზე დეკოდირებული 16 MiB-ით.

პროვაიდერისთვის გარდაქმნა (კანონიკური ელემენტები არასოდეს გადაიგზავნება უცვლელად):

- Jina-ს მულტიმოდალური მოდელები: თითოეული ზედა დონის ელემენტი გარდაიქმნება მოდალობის გასაღების მქონე ერთ ობიექტად
  (`text` / `image` / `audio` / `video` / `pdf`), ხოლო ჩაშენებული მედიისთვის გამოიყენება data URI-ები; თითო ვექტორი
  ზედა დონის თითოეულ ელემენტზე.
- Gemini Embedding 2 ოჯახი: ზედა დონის ერთი მასივი გარდაიქმნება ერთ მშობლიურ
  `models/{model}:embedContent` მოთხოვნად `content.parts`-ით (`text` ან `inline_data`).
- llama.cpp (`llama-cpp/<model>`, ნებისმიერი მოდელი, რომელიც ადგილობრივმა სერვერმა ჩატვირთა): კანონიკური `text` ელემენტები
  გარდაიქმნება უბრალო სტრიქონებად, ხოლო `image` / `audio` / `video` — თითო
  `{"content": [part]}` ობიექტად, llama-server-ის ჩატის შიგთავსის ნაწილების (`image_url`,
  `input_audio` ფორმატით `wav` / `mp3` / `flac`, `input_video`) და ჩაშენებული მონაცემების გამოყენებით; თითო ვექტორი
  ზედა დონის თითოეულ ელემენტზე. სერვერი უნდა მუშაობდეს `--embedding --mmproj …` პარამეტრებით; პროექტორის გარეშე ის
  თავად უარყოფს მედიას. `document` მხარდაჭერილი არ არის.
- უცნობი/დინამიკური მოდელები, რომლებსაც მოდალობის მკაფიო მეტამონაცემები არ აქვს, სტრუქტურირებულ შეყვანას HTTP 400 პასუხით უარყოფს.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

მოდელისა და მოდალობის მხარდაუჭერელი კომბინაციები ელემენტის იძულებითი გარდაქმნის ნაცვლად HTTP 400 პასუხს აბრუნებს. შეყვანისგან განსხვავებული
გაფართოების ველები ძველ სტრიქონულ/ტოკენურ მოთხოვნებში კვლავ უცვლელად გადაიცემა.

## სურათების გენერირება

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ხელმისაწვდომ პროვაიდერებს შორისაა OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (ლოკალური), ComfyUI (ლოკალური).

`n` აბრუნებს `n` რაოდენობის სურათს `data[]`-ში. პროვაიდერებისთვის, რომელთა ზედა დონის API თითო გამოძახებაზე ერთ სურათს აბრუნებს
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), სრულდება `n` ცალკეული ზედა დონის გამოძახება, რომელთაგან ერთდროულად მაქსიმუმ 4 მიმდინარეობს. ფიქსირებულ
`seed`-ს ემატება გამოძახების ინდექსი (`seed`, `seed + 1`, …), ამიტომ სურათები განსხვავდება, თუმცა
კვლავ განმეორებადად გენერირდება. `n`-ის მაქსიმალური მნიშვნელობაა 10. თუ რომელიმე გამოძახება ვერ შესრულდება, მთლიანად
მოთხოვნაც წარუმატებლად დასრულდება. პარალელურად დასამუშავებელი ფორმატების სია არის `SINGLE_IMAGE_FANOUT_FORMATS` ფაილში
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux ხელახლა იყენებს არსებულ API-გასაღების კავშირს და იღებს `zenmux/` ან `zm/` პრეფიქსებს:

- `zenmux/openai/gpt-image-2` იყენებს ZenMux-ის OpenAI Images API-ს. პარამეტრებს შორისაა `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` და `response_format`.
- სხვა გამომცემლები, როგორიცაა `zm/meta/muse-image-1.0`, იყენებენ ZenMux-ის Vertex AI `:predict`
  საბოლოო წერტილს. `n` შეესაბამება `sampleCount`-ს, `aspect_ratio` — `aspectRatio`-ს, ხოლო `image_size`
  (`1K`, `2K`, `4K`) — `sampleImageSize`-ს. პიქსელებში მითითებული `size` განსაზღვრავს მხოლოდ გვერდების თანაფარდობას
  და არა გარანტირებულ პიქსელურ ზომებს. მხარდაჭერილი თანაფარდობები, გარჩევადობები და რაოდენობები მოდელის მიხედვით განსხვავდება.
- `zm/inclusionai/ming-image-0.1-design` ზომებს თავად ირჩევს. გამოტოვეთ `size`,
  `aspect_ratio` და `image_size`; მათი აშკარად მითითება დააბრუნებს HTTP 400-ს. PNG, JPEG და WebP
  ფორმატების მოთხოვნა შესაძლებელია `output_format`-ის მეშვეობით.

ეს ინტეგრაცია მხარს უჭერს ტექსტიდან სურათის გენერირებას და არა საცნობარო სურათის რედაქტირებას. Vertex-ის
გამომავალი ნორმალიზდება `data[].b64_json`-ში; `response_format: "url"` აბრუნებს ზედა დონის

იხილეთ [ZenMux-ის Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) და
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

## დოკუმენტის OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` ირჩევს OCR პროვაიდერს `provider/model` პრეფიქსის მეშვეობით; პრეფიქსის გარეშე მოდელის იდენტიფიკატორი (მაგ.
`mistral-ocr-latest`) მის რეგისტრირებულ პროვაიდერად გარდაიქმნება, ხოლო გამოტოვებული `model` ნაგულისხმევად
Mistral-ს (`mistral-ocr-latest`) იყენებს. რეგისტრირებული პროვაიდერები (`open-sse/config/ocrRegistry.ts`):

| პროვაიდერის იდენტიფიკატორი    | მოდელის იდენტიფიკატორი | `model`-ის მნიშვნელობა                                                  | შენიშვნები                                                                                                                             |
| ----------------------------- | ---------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest`   | `mistral/mistral-ocr-latest` (ან პრეფიქსის გარეშე `mistral-ocr-latest`) | სინქრონული — პასუხი პირდაპირ ბრუნდება ზედა დონის ერთადერთი გამოძახებიდან.                                                              |
| `azure-document-intelligence` | `prebuilt-read`        | `azure-document-intelligence/prebuilt-read`                             | ასინქრონული ზედა დონე (`analyze` + გამოკითხვა) — იხილეთ ქვემოთ.                                                                        |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`    | `vertex-deepseek-ocr/deepseek-ocr-maas`                                 | სინქრონული, Vertex AI-ის `openapi/chat/completions` პარტნიორის საბოლოო წერტილის მეშვეობით — ავტორიზაციის/URL-ის შესახებ იხილეთ ქვემოთ. |

სამივე პროვაიდერი პასუხობს Mistral-ის ფორმის მქონე ერთნაირი სხეულით:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence-ის გამოკითხვის ნაკადი

Azure Document Intelligence-ის `analyze` API ასინქრონულია: საწყისი მოთხოვნა სხეულის ნაცვლად
`Operation-Location` სათაურს აბრუნებს, ხოლო შედეგის მისაღებად პერიოდული გამოკითხვაა საჭირო. დამმუშავებელი
(`open-sse/handlers/ocr.ts`) ამ URL-ს ყოველ წამს, მაქსიმუმ 30 მცდელობის განმავლობაში ამოწმებს; არა-`ok` გამოკითხვის პასუხის ან `"failed"` სტატუსის შემთხვევაში ის დაუყოვნებლივ ასრულებს მუშაობას შეცდომით (გამოკითხვას
აღარ აგრძელებს), ხოლო თუ მცდელობების ლიმიტის ამოწურვის შემდეგ ოპერაცია კვლავ მიმდინარეობს, აბრუნებს `504`-ს.
Azure-ის საბოლოო პასუხი გამომძახებელთან დაბრუნებამდე ნორმალიზდება იმავე `pages`/`markdown` ფორმაში, რომელსაც Mistral იყენებს,
ამიტომ კლიენტის კოდს პროვაიდერისთვის სპეციალური შემთხვევის დამუშავება არ სჭირდება.

### Vertex AI DeepSeek OCR-ის ავტორიზაცია და საბოლოო წერტილის განსაზღვრა

`vertex-deepseek-ocr` ხელახლა იყენებს იმავე Vertex AI ავტორიზაციას, რომელსაც OmniRoute უკვე უჭერს მხარს
ჩატის/სურათების ტრაფიკისთვის (`open-sse/executors/vertex.ts`): კავშირის API-გასაღები არის ან

ან უკვე შექმნილი OAuth წვდომის ტოკენი, რომელიც უცვლელად გამოიყენება. ზედა დონის საბოლოო წერტილის URL არის Vertex-ის
ზოგადი `openapi/chat/completions` პარტნიორის საბოლოო წერტილი, რომელიც კავშირის პროექტისა და
რეგიონის საფუძველზე იქმნება — აშკარად მითითებულ `providerSpecificData.project`/`providerSpecificData.region`-ს ყოველთვის ენიჭება უპირატესობა;

`us-central1`. ორივე მნიშვნელობის განსაზღვრა ხდება `open-sse/handlers/ocr.ts`-ში
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) და მათ
`handleOcr`-ზე გადამისამართებამდე `src/app/api/v1/ocr/route.ts` იყენებს.

### მოდელების ფასები (`pricing`)

ჩანაწერი შეიცავს `pricing` ობიექტს, როდესაც OmniRoute-მა მოდელის ფასი იცის. ფასი აღებულია
ფასების ცხრილიდან, რომელსაც ხარჯების აღრიცხვა იყენებს: ჩაშენებული ნაგულისხმევი მნიშვნელობები, სინქრონიზებული ფასები და
`/api/pricing`-ის მეშვეობით დაყენებული გადაფარვები. ეს ჩამონათვალის ფასებია, ამიტომ გამოწერაზე დაფუძნებული მომწოდებლებიც
აჩვენებენ თითოეული ტოკენის ფასს.

```json
"pricing": {
  "prompt": "0.000005",
  "completion": "0.000025",
  "input_cache_read": "0.0000005",
  "input_cache_write": "0.00000625",
  "input": 5,
  "output": 25,
  "cached": 0.5,
  "cache_creation": 6.25
}
```

| ველები                                                          | ერთეული                            | შენიშვნები                                                                                                                                                |
| --------------------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`, `completion`, `input_cache_read`, `input_cache_write` | USD თითო ტოკენზე, ათობითი სტრიქონი | OpenRouter-თან თავსებადი, არასოდესაა ექსპონენციალურ ჩანაწერში. ქეშის ორი ველი მხოლოდ მაშინ ჩნდება, როდესაც ქეშის ფასი არსებობს.                           |
| `input`, `output`, `cached`, `cache_creation`                   | USD 1M ტოკენზე, რიცხვი             | კატალოგის წინა ვერსიების ველები, შენარჩუნებული არსებული კლიენტებისთვის. `reasoning` და `long_context` ასევე ჩნდება, როდესაც ფასების სტრიქონი მათ შეიცავს. |

- **კომბინაციები** შეიცავს მათი პირველი ხილული სამიზნის ფასს. ჩაშენებული `auto/*` კომბინაციები
  სამიზნეს მოთხოვნის დროს ირჩევს, ამიტომ მათ `pricing` არ აქვთ.
- **უფასო მოდელები** აჩვენებს `"0"`-ს (და `0`-ს), როდესაც მათი ფასი ნულის ტოლია. მოდელი, რომელსაც ფასების სტრიქონი
  არ აქვს, ასევე აჩვენებს `"0"`-ს, როდესაც კატალოგი მას უფასოდ მონიშნავს (`free: true`) ან ჩაშენებული უფასო მოდელების
  კატალოგი მას შეიცავს.
- **უცნობი ფასი:** ჩანაწერს `pricing` გასაღები არ აქვს.
- **კრედიტებით აღრიცხული მომწოდებლები** (მაგალითად, Kiro) საფასურს თითო მოთხოვნაზე ითვლიან და არა თითო ტოკენზე. მათი
  ჩანაწერები ინარჩუნებს 1M-ზე დათვლილ რიცხვით ველებს, რომლებიც მანამდე ჰქონდათ, და არ შეიცავს თითო ტოკენის სტრიქონულ ველებს.
- **ვარიანტები** (მსჯელობის ძალისხმევის id-ები, აზროვნების გარეშე ალიასები, აღმოჩენისა და კარიბჭის სარკეები)
  აკოპირებს იმ მოდელის ფასს, რომელზეც მარშრუტიზდება.
- ველები მხოლოდ საბაზისო ტარიფებს შეიცავს. გრძელი კონტექსტის დონეები (რიცხვითი `long_context` ველი) და
  სერვისის დონის მამრავლები (მაგალითად, Codex fast ან flex) არ ცვლის `prompt`-ს ან
  `completion`-ს.
- ობიექტი ერთნაირია ავთენტიფიკაციის ყველა სტილისთვის, მათ შორის Anthropic-ის სტილის
  მოთხოვნისთვის `x-api-key`-ითა და `anthropic-version`-ით (პასუხი რჩება `{ "object": "list",
"data": [...] }`). იმპლემენტაცია: `src/app/api/v1/models/catalogPricing.ts`.

### მოდელის id-ის პრეფიქსები (`?prefix=`)

მოდელების უმეტესობა წარმოდგენილია **მომწოდებლის პრეფიქსით**. მიღებულ პრეფიქსს მართავს
`MODELS_CATALOG_PREFIX_MODE` ფუნქციური ალამი და მისი გადაფარვა შესაძლებელია **თითოეული მოთხოვნისთვის**
მოთხოვნის პარამეტრით — ეს სასარგებლოა კლიენტისთვის, რომელსაც სუფთა სია სურს ყველასთვის განკუთვნილი
სერვერის მასშტაბის პარამეტრის შეცვლის გარეშე:

```bash
GET /v1/models?prefix=alias        # თითო მოდელზე ერთი id — მოკლე ალიასის პრეფიქსი
GET /v1/models?prefix=dual         # ორივე ფორმა (სერვერის ნაგულისხმევი მნიშვნელობა)
GET /v1/models?prefix=canonical    # მხოლოდ მომწოდებლის სრული id-ის პრეფიქსი
```

| რეჟიმი      | გამოსცემს                                                | შენიშვნები                                                                                                                                                                                                       |
| ----------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **და** `claude/claude-sonnet-4-6` | **ნაგულისხმევი.** ორივე id იმავე მოდელზე მარშრუტიზდება; შენარჩუნებულია, რათა კლიენტის კონფიგურაციებმა, რომლებშიც რომელიმე ფორმა პირდაპირ იყო გაწერილი, მუშაობა გააგრძელოს. კატალოგის ზომას დაახლოებით აორმაგებს. |
| `alias`     | `cc/claude-sonnet-4-6`                                   | თითო მოდელზე ერთი ჩანაწერი. განსხვავებული ალიასის არმქონე მომწოდებლებიც გამოსცემს საკუთარ ჩანაწერს, ამიტომ არაფერი იკარგება.                                                                                     |
| `canonical` | `claude/claude-sonnet-4-6`                               | თითო მოდელზე ერთი ჩანაწერი მომწოდებლის სრული id-ის პრეფიქსით. განსხვავებული ალიასის არმქონე მომწოდებლებიც (მაგ., `antigravity/…`, `agy/…`) აქაც გამოსცემს საკუთარ ერთადერთ id-ს, ამიტომ არაფერი იკარგება.        |

`dual` რეჟიმის სარკის ამოცნობა მოთხოვნის პარამეტრის გარეშეც შესაძლებელია: ის შეიცავს `parent`
ველს, რომელიც ძირითად id-ზე მიუთითებს.

კლიენტებმა, რომლებიც მოდელის ამომრჩეველს ასახავს, უნდა მოითხოვონ `?prefix=alias` — სწორედ ამას აკეთებს
[OmniCopilot VS Code გაფართოება](../guides/VSCODE-COPILOT.md).

### აღმოჩენის ფილტრები (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` იღებს არჩევით აღმოჩენის ფილტრებს. მათ გარეშე პასუხი
უცვლელია. ისინი ავიწროებს კატალოგს, რომელსაც გამომძახებელი უკვე ხედავს (ჯერ API გასაღების ნებართვები გამოიყენება),
და სრულდება OpenAI-ის სტილის `limit` / `after` გვერდებად დაყოფამდე:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # ჩამოთვლილი ყველა შესაძლებლობა ჭეშმარიტი უნდა იყოს
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # კატალოგის `type`; მის გარეშე სტრიქონები არის `chat`
GET /v1/models?q=sonnet&limit=10                           # რეგისტრისგან დამოუკიდებელი დამთხვევა id-ზე ან სახელზე
```

| პარამეტრი     | მნიშვნელობები                                                                                       |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | არაუარყოფითი მთელი რიცხვი, რომელიც შედარებულია `context_length`-თან                                 |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 სიმბოლო                                                                                       |

უცნობი მნიშვნელობა ან `min_context`, რომელიც არ არის არაუარყოფითი მთელი რიცხვი (მაგალითად, `1.5`),
აბრუნებს HTTP `400`-ს, ხოლო შეტყობინებაში ჩამოთვლილია დასაშვები მნიშვნელობები. იმპლემენტაცია:
`src/app/api/v1/models/catalogFilters.ts`.

### მოდელების მოკლე სია (`POST /v1/models/query`)

`POST /v1/models/query` იმავე კატალოგიდან აბრუნებს მოკლე, დეტერმინისტულ სიას, ავტორიზაციისა და თითოეული
გასაღებისთვის ხილვადობის იმავე წესებით, რომლებსაც `GET /v1/models` იყენებს:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ყველა ველი არასავალდებულოა. `capabilities` და `exclude` იღებს მასივს ან მძიმეებით გამოყოფილ სტრიქონს;
`max_output` შედარებულია `max_output_tokens`-თან. შედეგები ჯერ `owned_by`-ის, შემდეგ კი `id`-ის მიხედვით ლაგდება.
`limit`-ის ნაგულისხმევი მნიშვნელობაა `20`, ხოლო `100`-ზე მეტი მნიშვნელობები იზღუდება `100`-მდე. არასწორი JSON, უცნობი
ველი ან არასწორი მნიშვნელობა აბრუნებს HTTP `400`-ს.

### ინდივიდუალურად დამალული ჩატის მოდელები

პროვაიდერის გვერდზე **დამალულად** მონიშნული მოდელი კატალოგიდან გამოირიცხება და მისი
ცალსახად მოთხოვნისას მოთხოვნა უარყოფილი იქნება HTTP `404` / `model_not_found`-ით. შემოწმება იყენებს განსაზღვრულ
პროვაიდერსა და მოდელს, მათ შორის პროვაიდერის ფსევდონიმებს, თავსებადი პროვაიდერის კვანძის პრეფიქსებსა და
კავშირის ნაგულისხმევ მნიშვნელობებს. კომბინაცია გამოტოვებს დამალულ სამიზნეებს და შეუძლია ხილული მონათესავე მოდელის გამოყენება; თუ
შესრულებადი სამიზნე აღარ რჩება, იგი იმავე შეცდომის კოდს აბრუნებს. დამალვის გაუქმება მომდევნო
მოთხოვნიდან ამოქმედდება. მხოლოდ გამოსახულებებისთვის განკუთვნილი ხილვადობის გადაფარვები არ მალავს იმავე ID-ის მქონე ჩატის მოდელს.

ინდივიდუალური მოდელის ეს პარამეტრი განცალკევებულია
[მოდელების გამოჩენის დაშვებისა და აკრძალვის სიებისგან](../routing/MODEL_EXPOSURE_LIST.md), რომლებიც ფილტრავს კატალოგში
გამოქვეყნებულ მოდელებსა და ავტომატური მარშრუტიზაციის კანდიდატებს, თუმცა ინარჩუნებს ცალსახა გადამისამართებას. API-გასაღების მოდელებზე
ნებართვები დამოუკიდებლად განაგრძობს მოქმედებას. კატალოგის პრეფიქსის ნაგულისხმევ რეჟიმად კვლავ `dual` რჩება.

### აზროვნების გარეშე მოდელების ვარიანტები

აზროვნების შესაძლებლობის მქონე Claude-ის მოდელებისთვის `/v1/models` ასევე აქვეყნებს **აზროვნების გარეშე** ვარიანტს, რომლის ID-ს აქვს პრეფიქსი `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

ამ ID-ის არჩევისას (მაგალითად, Claude Code-ის კონფიგურაციაში, რომელიც ყოველთვის ურთავს `thinking` ბლოკს) იგი კვლავ რეალურ `<provider>/<model>`-ად გარდაიქმნება, თუმცა მსჯელობა გამორთული იქნება — `/v1/messages` მარშრუტზე `thinking:{type:"disabled"}`, ხოლო `/v1/chat/completions` მარშრუტზე `reasoning`/`reasoning_effort` ველები ამოიშლება. ეს ვარიანტი ჩამონათვალში მხოლოდ Claude-ის ოჯახის იმ მოდელებისთვის ჩნდება, რომლებიც მხარს უჭერს აზროვნებას **და** ითვალისწინებს `disabled`-ს (ამიტომ, მაგალითად, მხოლოდ ადაპტიური მოდელები, რომლებიც `disabled`-ს უარყოფს, გამორიცხულია). ოპერატორებს შეუძლიათ თითოეული მოდელისთვის ამ ვარიანტის იძულებით ჩართვა ან გამორთვა `ModelSpec.noThinkingAlias`-ის საშუალებით.

## აუდიოს გენერაცია ElevenLabs-ით

OmniRoute-ში დააკონფიგურირეთ `elevenlabs` პროვაიდერის კავშირი თქვენი ElevenLabs API გასაღებით.
კლიენტები ავთენტიფიკაციას გადიან თავიანთი **OmniRoute** გასაღებით (`Authorization: Bearer $OMNIROUTE_API_KEY`);
კარიბჭე შენახულ პროვაიდერის გასაღებს გადასცემს, როგორც `xi-api-key`. არასოდეს გაგზავნოთ ElevenLabs-ის გასაღები
კარიბჭის bearer-ტოკენის სახით.

| მეთოდი | გზა                         | პასუხი                                         | API გასაღების საბოლოო წერტილის კატეგორია |
| ------ | --------------------------- | ---------------------------------------------- | ---------------------------------------- |
| POST   | `/v1/sound-generation`      | ნატიური აუდიობაიტები                           | `elevenlabs`                             |
| POST   | `/v1/music`                 | ნატიური აუდიობაიტები                           | `music`                                  |
| POST   | `/v1/music/stream`          | ნაკადური აუდიობაიტები                          | `music`                                  |
| POST   | `/v1/music/detailed`        | ნატიური multipart აუდიო და კომპოზიციის გეგმა   | `music`                                  |
| POST   | `/v1/music/detailed/stream` | ნატიური SSE მეტამონაცემები და აუდიოფრაგმენტები | `music`                                  |
| POST   | `/v1/music/plan`            | JSON კომპოზიციის გეგმა                         | `music`                                  |

ეს საბოლოო წერტილები ავსებს არსებულ `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` და `/v1/speech-to-text` მარშრუტებს. ნატიური JSON ველები
და მოთხოვნის პარამეტრები, როგორიცაა `output_format` და `enable_logging`, უცვლელად ინახება.
`/v1/music/detailed`-ის პასუხები ინარჩუნებს multipart საზღვრებს; დაამუშავეთ ისინი, როგორც multipart.
`/v1/music/detailed/stream` აბრუნებს `text/event-stream`-ს კომპოზიციის მეტამონაცემებითა და
base64 აუდიოფრაგმენტებით SSE მოვლენებში. ექვსივე მარშრუტს აქვს CORS preflight-ის მხარდაჭერა.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# მოკლე ხმოვანი ეფექტი. ხანგრძლივობა: 0.5-დან 30 წამამდე.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# მუსიკის ხანგრძლივობა მილიწამებში გამოისახება: 3000-დან 600000-მდე.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

აუდიოს ნაწილ-ნაწილ მისაწოდებლად გამოიყენეთ `/v1/music/stream` იმავე JSON სხეულით. კომპოზიცია
იღებს მხოლოდ ერთ-ერთს — `prompt`-ს ან `composition_plan`-ს; `/v1/music/plan` მოითხოვს `prompt`-ს
და სურვილისამებრ იღებს `source_composition_plan`-ს. ნატიური სქემები ინარჩუნებს პროვაიდერის დამატებით
ველებს, რათა კომპოზიციის გეგმის ვერსიებმა და ზუსტი გამართვის პარამეტრებმა ElevenLabs-მდე მიაღწიოს.

გაერთიანებული `/v1/music/generations` საბოლოო წერტილი ასევე იღებს `elevenlabs/music_v1`,
`elevenlabs/music_v2` და `elevenlabs/music_v2_5` მოდელებს. ElevenLabs-ის აქტიური კავშირის შემთხვევაში
ეს მოდელები მუსიკის კატალოგში გამოჩნდება. ეს საბოლოო წერტილი აბრუნებს
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. მისი `duration` ველი იზომება
წამებში და აისახება `music_length_ms`-ში; აშკარად მითითებულ `music_length_ms`-ს უპირატესობა ენიჭება.
`instrumental` აისახება `force_instrumental`-ში, ხოლო ნატიურ ველს უპირატესობა ენიჭება.
ნაკადური გადაცემისთვის გამოიყენეთ ნატიური ნაკადური საბოლოო წერტილები, ხოლო მხოლოდ კომპოზიციის გეგმით
განსაზღვრული მოთხოვნებისთვის — ნატიური კომპოზიციის საბოლოო წერტილი.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

საბოლოო წერტილის, მოდელის, ბიუჯეტისა და კავშირის შეზღუდვები მოწმდება upstream გამოძახებამდე. ნატიური
მარშრუტები upstream სტატუსის კოდებსა და შეცდომის სხეულებს უცვლელად აბრუნებს, მათ შორის `402`-ს გეგმის
შეზღუდვისთვის და `429`-ს კვოტის ლიმიტისთვის. არსებობის შემთხვევაში უცვლელად ინახება `character-cost`, `song-id`, `request-id` და `retry-after`
სათაურები. უფასო საკრედიტო ბალანსი არ იძლევა ყველა მუსიკალურ მოდელზე, გამომავალ ფორმატსა თუ API ფუნქციაზე
წვდომის გარანტიას: თითოეული მოთხოვნის უფლებამოსილებას ElevenLabs განსაზღვრავს.

```bash
# ხელახალი რანჟირება (ღრუბლოვანი რეესტრის პროვაიდერი ან OpenAI-თან თავსებადი პროვაიდერის კვანძი ფორმატით "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina-ს კლასიფიკაცია (Foundation API-ის ავტორიზაციის მონაცემები)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina-ს სეგმენტატორი
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina-ს ძიება (s.jina.ai; პროვაიდერის ფსევდონიმები: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# მოდერაცია
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — აბრუნებს audio/mpeg-ის (ან მოთხოვნილი ფორმატის) სხეულს
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS მოითხოვს ენასა და ხმას: `language`-ის ნაგულისხმევი მნიშვნელობაა "en"; გამოტოვებული
# ხმა ან OpenAI-ის სტანდარტული ხმის სახელი (alloy, nova, …) ჩანაცვლდება მნიშვნელობით "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# სურათის რედაქტირება (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
```

> **გადახარისხების პროვაიდერის კვანძები:** `POST /v1/rerank` ასევე მარშრუტდება OpenAI-თან თავსებადი პროვაიდერის კვანძებისკენ
> (oMLX, vLLM, Infinity, TEI კარიბჭის მიღმა, …), რომლებიც მისამართდება როგორც `<node-prefix>/<model>`. უკუკავშირის
> კვანძები (`localhost`, `127.0.0.1`, `172.16.0.0/12`) ყოველთვის დაშვებულია, ისევე როგორც ჰოსტების სახელები, რომლებსაც
> ოპერატორი ჩამოთვლის `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`-ში (მაგ., Docker/Compose სერვისის სახელი,
> როგორიცაა `http://reranker:8080/v1`; მათთან დაკავშირება ხდება პირდაპირ და არასოდეს — `HTTP(S)_PROXY`-ის ან
> კავშირის ფიქსირებული პროქსის გავლით). ნებისმიერ სხვა
> ჰოსტზე განთავსებული კვანძები — LAN-ის კომპიუტერი ან Tailscale-ის თანაბარი კვანძი — დაშვებულია მხოლოდ მაშინ, როცა ოპერატორი ჩართავს
> `RERANK_REMOTE_PROVIDER_NODES` ფუნქციურ დროშას **და** კვანძის საბაზისო URL შეესაბამება პროვაიდერის
> გამავალი URL-ების პოლიტიკას (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> მეხსიერების ძრავის გადახარისხების ეტაპი ამ მარშრუტს
> უკუკავშირის ინტერფეისის მეშვეობით იძახებს, ამიტომ იგივე წესი არეგულირებს `rerankProviderModel`-საც მეხსიერების პარამეტრებში.
>
> **ლოკალური სერვერის ფორმები:** კვანძი გამოიძახება მისამართზე `<base>/v1/rerank`, ხოლო 404-ის შემთხვევაში — მისამართზე `<base>/rerank`
> (Infinity, TEI). ზედა დონის მოთხოვნის სხეული შეიცავს როგორც Cohere/OpenAI-ის სახელდებას (`documents`,
> `return_documents`), ისე TEI-ის სახელდებას (`texts`, `return_text`), ხოლო ზედა დონის პასუხი
> ნორმალიზდება Cohere-ის გარსში: TEI-ის უბრალო `[{index, score, text}]`, მსუბუქი კარიბჭეებიდან მიღებული `{results: [{index, score}]}`
> და Voyage-ის სტილის `{data: [...]}` კლიენტს ყველა უბრუნდება ფორმით
> `{results: [{index, relevance_score, document?}]}`, ქულის მიხედვით დალაგებული და `top_n`-ით შეზღუდული.

> **პროვაიდერის კვანძების აღმოჩენა:** OpenAI-თან თავსებადი პროვაიდერის კვანძის მოდელები `GET /v1/models`-ში
> კვანძის პრეფიქსით გამოჩნდება. ჩანაწერები, რომლებიც საბოლოო წერტილის მეტამონაცემებს არ შეიცავს (რაც ტიპურია ლოკალური `/v1/models` ჩამონათვალებისთვის),
> მემკვიდრეობით იღებს კვანძის `apiType`-ს, ამიტომ `embeddings` კვანძის მოდელებია `type: "embedding"`, ხოლო
> `rerank` კვანძის მოდელებია `type: "rerank"`, ნაცვლად ნაგულისხმევად ჩატის ტიპის მინიჭებისა; სინქრონიზებულ ან ხელით დამატებულ ჩანაწერში აშკარად მითითებულ
> `supportedEndpoints`-ს კვლავ უპირატესობა ენიჭება.

## Files API

OpenAI-თან თავსებადი ფაილების endpoint პაკეტური შეყვანა/გამოტანისა და დანიშნულების მიხედვით ფაილების ატვირთვისთვის.

| მეთოდი | გზა                      | აღწერა                                                                                                            |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | ფაილის ატვირთვა (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — მაქს. 512 MiB |
| GET    | `/v1/files`              | ავთენტიფიცირებული API გასაღების ფაილების ჩამონათვალი                                                              |
| GET    | `/v1/files/[id]`         | ფაილის მეტამონაცემების მიღება                                                                                     |
| DELETE | `/v1/files/[id]`         | ფაილის წაშლა                                                                                                      |
| GET    | `/v1/files/[id]/content` | ფაილის დაუმუშავებელი შიგთავსის ნაკადის სახით დაბრუნება                                                            |

**ავთენტიფიკაცია:** Bearer API გასაღები — `getApiKeyRequestScope`-ის მეშვეობით ფაილების წვდომის არე თითოეული API გასაღებით განისაზღვრება. გასაღები
ხედავს, ჩამოტვირთავს და შლის მხოლოდ საკუთარ ფაილებს; საინფორმაციო პანელის სესია გასაღების გარეშე კითხულობს
მთელ ინსტანციას; მფლობელის არმქონე ფაილზე (ანონიმური ან საინფორმაციო პანელის სესიიდან ატვირთული) წვდომა აკრძალულია ყველა
არასესიური გამომძახებლისთვის. `GET /v1/files` ანონიმურ გამომძახებელს — ასევე წარდგენილი გასაღების შემთხვევაში, რომლის
ამოცნობაც ვერ ხერხდება — უბრუნებს `401`-ს მაშინაც კი, როცა `REQUIRE_API_KEY=false`, ნაცვლად იმისა, რომ ყველა მოიჯარის
ფაილები ჩამოთვალოს (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523).

| POST   | `/v1/search`           | გაუშვით საძიებო მოთხოვნა — ორგანო დამოწმებული `v1SearchSchema` ით, მხარს უჭერს caching/coalescing |
| GET    | `/v1/search/analytics` | თითო პროვაიდერის hit/latency/cache სტატისტიკა                                                     |

**ავტორიზაცია:** მატარებელი API გასაღები (`extractApiKey` + `isValidApiKey`). ძიების პოლიტიკა განხორციელდა `enforceApiKeyPolicy` მეშვეობით.

### ეგზა და ტავილი `provider_options`

Exa და Tavily კითხულობენ პროვაიდერის სპეციფიკურ ველებს სახელების სივრცის ჩანთიდან: `provider_options.exa` (ან `provider_options["exa-search"]`) და `provider_options.tavily` (ან `provider_options["tavily-search"]`). გადამისამართებულია მხოლოდ ქვემოთ მოცემული გასაღებები. თითოეული მოწმდება `open-sse/handlers/search/providerOptionsPassthrough.ts` ში საკუთარი Zod სქემის მიხედვით და არასწორი ტიპის გასაღები ამოვარდნილია. ნებისმიერი სხვა გასაღები იგნორირებულია, მათ შორის auth, base URL, `stream` და `outputSchema`. სხვა პროვაიდერების მიერ გამოყენებული ბრტყელი კლავიშები (`cx`, `depth`, ...) მუშაობს როგორც ადრე.

| პროვაიდერი | უმაღლესი დონის ველები                                                                                                                                                                                                                                                                                                                                                     | დაბუდებული                                                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Exa        | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (ბრტყელი პრიმიტივები), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                          | `contents.{text, highlights, summary, extras, livecrawlTimeout, maxAgeHours}` გაერთიანდა ნაგულისხმევ `{ text: true, highlights: true }` ზე |
| ტავილი     | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                          |

ყოველთვის იმარჯვებს ზოგადი ველები: `query`, `max_results`, `filters` (დომენები), `country` და `search_type` დან მიღებული თემა. Exa-ზე, `search_type: "news"` ინახავს `category: "news"`. ტავილი ასევე იღებს `search_type: "finance"` (`topic: "finance"`).

Firecrawl ძიების ღირებულება აღირიცხება 10 დაბრუნებული შედეგის დაწყებულ ბლოკზე, 0,002$ (2 კრედიტი) ბლოკი და მინიმუმ ერთი ბლოკი თითო ზარზე ( [Firecrawl ბილინგი](https://docs.firecrawl.dev/billing) ): 11 შედეგი ღირს 0,004$.

ზოგადი `time_range` ახლა აღწევს ორივე პროვაიდერს: Exa იღებს `startPublishedDate` (ISO დროის ნიშანს) და Tavily იღებს `start_date` (`YYYY-MM-DD`). აშკარა თარიღი `provider_options` ში აჭარბებს შედგენილ თარიღს.

Exa შედეგები ინახავს `id`, `highlight_scores`, `summary`, `subpages`, `entities` და `extras` `provider_raw` ში. შედეგების შენარჩუნება `images` და `favicon`.

Linkup-ის ძიების ღირებულება აღირიცხება $0,005 `depth` `fast` სთვის და `standard` სთვის და $0,05-ად `deep` სთვის ( [Linkup pricing](https://docs.linkup.so/pages/documentation/development/pricing) ), მიუხედავად იმისა, `depth` მოდის `provider_options` დან თუ კავშირის პარამეტრებიდან.

Exa `type: "lite"` (Exa 3.0) იღებს ველების უფრო მცირე კომპლექტს და უარყოფს მთელ მოთხოვნას, როდესაც დაყენებულია ნებისმიერი სხვა ველი. Lite-ისთვის, `additionalQueries`, `systemPrompt` და ყველა `contents` კლავიატურა `text` და `highlights` გარდა იშლება ზარის წინ. მოძველებული `subpages`, `subpageTarget`, `highlights.numSentences` და `highlights.highlightsPerUrl` აღარ არის გადაგზავნილი.

ხარჯების აღრიცხვა არის ბინა რეესტრი `costPerQuery`, გარდა Exa-ისა, რომელიც მიჰყვება Exa-ს საკუთარ ფასებს: $0,007 თითო ზარზე `auto` (და მემკვიდრეობითი `fast`) ან $0,004 `lite` (და მემკვიდრე `instant`), რომელიც მოიცავს 10 შედეგს; $0,001 ყოველი შემდგომი შედეგისთვის; და $0,001 თითო დაბრუნებულ შედეგზე, როდესაც `contents.summary` დაყენებულია. Tavily აღირიცხება 1 კრედიტით (0,008$) `search_depth` `basic`, `fast` და `ultra-fast`, და 2 კრედიტით (0,016$) `advanced` ( [Tavily API კრედიტები](https://docs.tavily.com/documentation/api-credits) ). ზარი `auto_parameters: true` ით, რომელსაც Tavily განაახლებს გაფართოებულზე, კვლავ ჩაწერილია 1 კრედიტით.

## Web Fetch API

ამოიღეთ კონტენტი URL-დან კონფიგურირებული ვებ-ამოღების პროვაიდერის მეშვეობით (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, იგივე API გასაღები, რაც Parallel Search-ს აქვს) მხოლოდ Markdown-ს
აბრუნებს — ნებისმიერი სხვა `format` იწვევს `400`-ს — და კონტენტს 100,000 სიმბოლომდე ზღუდავს. როდესაც
სამიზნე გვერდის ამოღება შეუძლებელია, ზედა დონის სერვისი ამის შესახებ HTTP 200 პასუხში იტყობინება;
OmniRoute ამას ფიქსირებული შეტყობინების მქონე `422` პასუხად გარდაქმნის.

| მეთოდი | მისამართი       | აღწერა                                                        |
| ------ | --------------- | ------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | URL-ის მიღება/ამოღება — სხეული მოწმდება `v1WebFetchSchema`-ით |

**ავთენტიფიკაცია:** Bearer API გასაღები (`extractApiKey` + `isValidApiKey`). პოლიტიკა აღსრულდება `enforceApiKeyPolicy`-ის მეშვეობით.

**კვოტის გათვალისწინებით სარეზერვო გადართვა (#8297):** როდესაც აშკარა `provider` მითითებული არ არის, პული
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`)
ფიქსირებული
პრიორიტეტული თანმიმდევრობით მუშავდება (პირველის სრულად გამოყენება) — სიხშირით შეზღუდული, მაგრამ კონფიგურირებული პროვაიდერი გამოიტოვება
მოთხოვნის შეწყვეტის ნაცვლად, ხოლო ზედა დონის სერვისის ხელახლა ცდადი/კვოტასთან დაკავშირებული შეცდომის
(HTTP 429 ყოველთვის; 402/403 Firecrawl/Tavily/TinyFish-ის კვოტის ტიპის უფასო დონეებისთვის —
არა Jina Reader-ისთვის და არასდროს ჩვეულებრივი 400 არასწორი მოთხოვნისთვის) შემთხვევაში მოთხოვნის შესრულებისას
ხდება გადასვლა შემდეგ ჯერ გამოუცდელ პროვაიდერზე, რომლის ავტორიზაციის მონაცემებიც ხელმისაწვდომია. როდესაც პულში შემავალი ყველა პროვაიდერი
ამოწურულია, საბოლოო წერტილი წინა ზოგადი `400` პასუხის ნაცვლად ერთიან `429` პასუხს
(`Retry-After` სათაურით) აბრუნებს. როდესაც მოთხოვნილია აშკარად მითითებული `provider`,
**არავითარი** ფარული სარეზერვო გადართვა არ ხდება — სიხშირით შეზღუდული ან გაუმართავი აშკარად მითითებული
პროვაიდერის საკუთარი შეცდომა პირდაპირ ბრუნდება (`429`, თუ სიხშირითაა შეზღუდული, სხვა შემთხვევაში კი ზედა დონის
სერვისის სტატუსი).

## WebSocket-ის ნაკადური გადაცემა

```bash
GET /v1/ws?handshake=1
```

ამოწმებს WebSocket-ის განახლების ხელის ჩამორთმევას და აბრუნებს სადენური პროტოკოლის შეტყობინებების მაგალითებს (`request`, `cancel`). რეალურ WS კადრებს ამუშავებს თანდართული WS სერვერი, Next.js-ის მარშრუტების ცხრილის გარეთ.

**ავთენტიფიკაცია:** Bearer API გასაღები ხელის ჩამორთმევისას.

### Responses API WebSocket-ის მეშვეობით (მხოლოდ codex)

```bash
# იგივე ჰოსტი:პორტი, რასაც HTTP API იყენებს (ნაგულისხმევად 20128); განაახლეთ კავშირი:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ან: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# პირველი კადრი აუცილებლად response.create უნდა იყოს:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket პროქსი დაკავშირებულია **ექსკლუზიურად `codex`-თან** (ChatGPT-ის
ბეკენდი). ის უსმენს იმავე პორტს, რომელსაც API/საინფორმაციო პანელი იყენებს, მისამართებზე `/v1/responses`,
`/responses` და `/api/v1/responses`. პირველ `response.create` კადრზე ის
შიდა `codex-responses-ws` ხიდის მეშვეობით ასრულებს ავთენტიფიკაციას და მომზადებას, ირჩევს
codex OAuth კავშირს და `wreq-js` ტრანსპორტის მეშვეობით გვირაბს ქმნის `wss://chatgpt.com/backend-api/codex/responses`-მდე.
**არა-codex მოდელები უარყოფილია** (`codex_ws_provider_required`).
კვოტის გაზიარებით მარშრუტიზაციისთვის გამოიყენეთ `model: "qtSd/<group>/codex/<model>"`. იმპლემენტაცია მოცემულია
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` ფაილებში.

**ავთენტიფიკაცია:** Bearer API გასაღები ხელის ჩამორთმევისას. თანდართული HTTP სერვერი (`server-ws.mjs`)
აქტიური შესვლის წერტილი უნდა იყოს (ის ნაგულისხმევად აქტიურია, როდესაც `app/server-ws.mjs` არსებობს).

#### მოდელის id: გამოიყენეთ ChatGPT-ის სუფთა id (`codex/` პრეფიქსის გარეშე)

OpenAI **Codex CLI** მოდელის სახელს კლიენტის მხარეს ამოწმებს, როდესაც
`supports_websockets = true`, და **უარყოფს პროვაიდერის პრეფიქსიან id-ებს**, როგორიცაა
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). გაგზავნეთ **სუფთა** id (მაგალითად, `gpt-5.5`). OmniRoute-ის ხიდი
მხოლოდ codex-ს ემსახურება, ამიტომ ზედა დონის სერვისში გვირაბის შექმნამდე ის სუფთა id-ს ხელახლა განსაზღვრავს, როგორც codex მოდელს
(`resolveCodexWsModelInfo`) — მიუხედავად იმისა, რომ სუფთა
`gpt-5.5` HTTP-ის მეშვეობით სხვა პროვაიდერთან იქნებოდა მარშრუტიზებული.

#### OpenAI Codex CLI-ის კონფიგურაცია

მიუთითეთ Codex CLI-ს OmniRoute-ზე `~/.codex/config.toml`-ში WebSocket-ის
მხარდაჭერის მქონე მორგებული პროვაიდერის დამატებით (არსებულ კონფიგურაციაზე ზემოქმედების თავიდან ასაცილებლად
გამოიყენეთ ცალკე `CODEX_HOME`):

```toml
model = "gpt-5.5"                 # სუფთა id — არა "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ბოლოში დახრილი ხაზი არ უნდა ჰქონდეს; WS URL მისგან მიიღება (საწარმოო გარემოში გამოიყენეთ https/wss)
wire_api = "responses"                    # ერთადერთი მხარდაჭერილი მნიშვნელობა 2026 წლის თებერვლიდან
supports_websockets = true                # რთავს Responses-over-WS ტრანსპორტს
env_key = "OMNIROUTE_API_KEY"             # შეიცავს OmniRoute API გასაღებს (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API გასაღები (ნებისმიერი გასაღები, თუ REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI `base_url + /responses` მისამართს WebSocket კავშირად აახლებს, ხოლო OmniRoute მას
არჩეულ codex OAuth კავშირთან გვირაბით აკავშირებს. სრულად შემოწმებულია ლოკალურ
სერვერთან: ChatGPT აბრუნებს `codex.rate_limits` + `response.created`-ს და პასუხს
ნაკადის სახით გადასცემს.

## თვითმომსახურების გამოყენება (`/api/usage/om-usage`)

ნებისმიერ API-გასაღებს შეუძლია ნახოს **საკუთარი** გამოყენება და კვოტები — მართვის ავთენტიფიკაციის გარეშე. ეს არის საბოლოო წერტილი, რომელსაც
კლიენტი (CLI, OmniCopilot-ის პანელი) იყენებს გასაღების მფლობელისთვის მისი დანახარჯის საჩვენებლად.

```bash
# ტექსტური ფორმა (ისტორიული კონტრაქტი — უბრალო ტექსტი ტერმინალისთვის)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# სტრუქტურირებული ფორმა — რასაც UI მოიხმარს
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

გასაღებისთვის **`allowUsageCommand`** ჩართული უნდა იყოს (ნაგულისხმევად გამორთულია — საინფორმაციო დაფის API-გასაღებების
მენეჯერი მას თითოეული გასაღებისთვის რთავს ან თიშავს). მის გარეშე საბოლოო წერტილი პასუხობს `403`-ით.

`?format=json` აბრუნებს დისკრიმინირებულ სტრუქტურას, რათა გამომძახებელმა უარის პასუხიდან მონაცემთა ველი არასოდეს წაიკითხოს.
წარმატების შემთხვევაში:

```jsonc
{
  "allowed": true,
  // წარმოდგენილია მხოლოდ მაშინ, როდესაც გასაღებისთვის ჩართულია გამოყენების ინდივიდუალური ლიმიტები (დღიური/კვირეული USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // არჩეული პროვაიდერის კვოტის მდგომარეობის სურათი, ან null, როდესაც ქეშში ჯერ არაფერია:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // თითოეული კავშირის მდგომარეობის სურათი, რათა UI-მ რამდენიმე პროვაიდერი გვერდიგვერდ გამოსახოს:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

უარის შემთხვევაში (`401` არასწორი გასაღები / `403` ნებართვა არ არის), იგივე მარშრუტი აბრუნებს
`{ "allowed": false, "error": { "message": "…" } }` — წარმოდგენილი, მაგრამ ცარიელი `personal`/`provider`
(გასაღები დაშვებულია, თუმცა ჯერ ინფორმაცია არ არის მიღებული) უარისგან განსხვავებული მდგომარეობაა და მათ ერთმანეთისგან
მხოლოდ JSON-ფორმა განასხვავებს.

**ავთენტიფიკაცია:** გამომძახებლის საკუთარი Bearer API-გასაღები, რომელიც მოწმდება `isValidApiKey`-ით — ეს _არ არის_
მართვის ინტერფეისი (`/api/keys/…`), რომელიც კვლავ `requireManagementAuth`-ით არის დაცული.

### კვოტის დაუმუშავებელი და შეზღუდვის ზღვრის მიხედვით კორექტირებული პროცენტული მაჩვენებლები

`/api/usage/om-usage`-ის გამოყენებისას გამომძახებლებმა უნდა გაითვალისწინონ განსხვავება **უბრალო ტექსტის გამომავალში**
და სტრუქტურირებულ **JSON-გამომავალში** წარმოდგენილ პროცენტულ მაჩვენებლებს შორის:

| ასპექტი                   | უბრალო ტექსტის ფორმატი (`/api/usage/om-usage` / `@@om-usage`)                                      | JSON-ფორმატი (`?format=json`)                                                                      |
| :------------------------ | :------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------- |
| **გამომავალი ველი**       | `NN% left` (მაგ., `20% left`)                                                                      | `provider.quotas` / `providers[].quotas`                                                           |
| **გაზომვა**               | **შეზღუდვის ზღვრის მიხედვით კორექტირებული გამოსაყენებელი ლიმიტი**: ზღვარს ზემოთ დარჩენილი მოცულობა | **პროვაიდერის დაუმუშავებელი კვოტა**: პროვაიდერის არაკორექტირებული მაჩვენებელი                      |
| **ზღვრის მასშტაბირება**   | მასშტაბირდება `effectiveRemainingPercent()`-ით, რათა დაცული რეზერვი გამოჩნდეს როგორც `0% left`     | არ გამოიყენება (პროვაიდერისგან მიღებული დაუმუშავებელი მდგომარეობის სურათი)                         |
| **ზღვრის მონაცემები**     | გათვალისწინებულია ნაჩვენებ პროცენტულ მაჩვენებელში                                                  | ინახება `quotaWindowThresholds`-ში თითოეული კავშირისთვის (ან სერვერის ნაგულისხმევი მნიშვნელობებით) |
| **ძირითადი მომხმარებელი** | ინტერაქციული CLI-ები, ტერმინალის მოთხოვნები, ოპერატორები                                           | პროგრამული ინტეგრაციები, საინფორმაციო დაფები, ანალიტიკა, ბილინგის ტრეკერები                        |

#### შეზღუდვის ზღვრის მიხედვით კორექტირების ფორმულა

OmniRoute მხარს უჭერს კვოტის პროაქტიულ შეზღუდვის ზღვრებს ზედა დონის რესურსის ამოწურვის თავიდან ასაცილებლად (კონფიგურირდება კავშირის
`quotaWindowThresholds`-ით, პროვაიდერის ნაგულისხმევი მნიშვნელობებით ან მდგრადობის გლობალური პარამეტრებით). როდესაც კვოტის ფანჯარაზე
აქტიურია შეზღუდვის ზღვარი (მაგ., `cutoff = 25%`), ტექსტის რენდერერი დარჩენილ ლიმიტს შემდეგნაირად ითვლის:

- თუ `remaining <= cutoff`: აბრუნებს `0%`-ს.
- თუ `remaining > cutoff`: აბრუნებს `((remaining - cutoff) / (100 - cutoff)) * 100`-ს.

ფორმატირებული ტექსტური გამომავალი მნიშვნელობას უახლოეს მთელ რიცხვამდე ამრგვალებს (`Math.round(...)`).

#### საილუსტრაციო მაგალითი

განვიხილოთ პროვაიდერის ფანჯარა **60% დაუმუშავებელი გამოყენებით** (შესაბამისად, **40% დაუმუშავებელი დარჩენილი კვოტით**) და კონფიგურირებული
**დარჩენილი კვოტის 25%-იანი შეზღუდვის ზღვრით**:

| წარმოდგენა                              | გამოთვლა                                           | დარჩენილი |         ნაგულისხმევი გამოყენებული          |
| :-------------------------------------- | :------------------------------------------------- | :-------: | :----------------------------------------: |
| **დაუმუშავებელი JSON (`?format=json`)** | ზედა დონის მდგომარეობის სურათი (`quotas[window]`)  |  **40%**  |                  **60%**                   |
| **ტექსტური ფორმატი (`NN% left`)**       | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**  | **80%** (`100 - remaining`-ის გამოთვლისას) |

- **რატომ აჩვენებს ტექსტი 20%-ის დარჩენას:** ანგარიშზე ფიზიკურად დარჩენილი 40%-იანი კვოტიდან 25% შეზღუდვის
  პოლიტიკის მიერაა რეზერვირებული. გამომძახებელს აქვს გამოსაყენებელი 75%-იანი მარაგიდან მხოლოდ 15% დარჩენილი, სანამ როუტერი
  ამ კავშირზე მარშრუტიზაციას შეწყვეტს. მასშტაბირება უზრუნველყოფს, რომ კავშირმა ამოწურვის სიგნალი (`0% left`) ზუსტად მაშინ
  გამოსცეს, როდესაც მარშრუტიზაცია შეწყდება.
- **რატომ ინარჩუნებს JSON დაუმუშავებელ მნიშვნელობებს:** JSON-ის მონაცემები აბრუნებს პროვაიდერის ზუსტ მდგომარეობის სურათს (`UsageSnapshot`),
  რათა გარე ხელსაწყოებს ჰქონდეთ წვდომა ზედა დონის გამოყენების სარწმუნო მონაცემებსა და კავშირის დონის
  `quotaWindowThresholds`-ზე სერვერის მხრიდან ინფორმაციის დამკარგავი მასშტაბირების გარეშე.

#### მომხმარებლების მიგრაციის სახელმძღვანელო

თუ გარე ინტეგრაცია (მაგალითად, რედაქტორის დანამატი ან აგენტის გაფართოება) ადრე ტექსტურ
endpoint-ს (`NN% left`) ამუშავებდა და გამოყენებულ პროცენტს `100 - NN` ფორმულით ითვლიდა, `?format=json`-ზე მიგრაცია ნიშნავს:

- დაუმუშავებელი JSON მნიშვნელობების წაკითხვა ასახავს **წყაროს მხარეს ფაქტობრივ მოხმარებას** (ზემოთ მოცემულ მაგალითში გამოყენებულია 60%).
- თუ ინტეგრაციას სურს შეინარჩუნოს ტექსტური endpoint-ის ხელმისაწვდომი ლიმიტის სემანტიკა, მას შეუძლია კლიენტის მხარეს
  გამოთვალოს ეფექტურად დარჩენილი ლიმიტი, კავშირის დონეზე გადაფარვებისთვის `quotaWindowThresholds`-ის გამოყენებით.

### გავლენა დაყოვნებაზე

სემანტიკურ ქეშში დამთხვევის შემთხვევაში პასუხი მოეწოდება ქეშიდან **upstream
გამოძახების გარეშე**, ამიტომ ნაჩვენები `X-OmniRoute-Response-Latency` თითქმის ნულის ტოლია
(თავდაპირველი upstream დაყოვნების მიუხედავად). დაყოვნების მიმართ მგრძნობიარე კლიენტებმა
(ბენჩმარკინგი, p50/p99 მონიტორინგი) უნდა შეამოწმონ
`X-OmniRoute-Cache-Latency` პასუხის სათაური:

| მნიშვნელობა | განმარტება                                                            |
| ----------- | --------------------------------------------------------------------- |
| `synthetic` | პასუხი მოწოდებულია ქეშიდან; დაყოვნება რეალურ upstream დროს არ ასახავს |
| _(არ არის)_ | პასუხი რეალური upstream გამოძახებიდანაა                               |

### ქეშის გვერდის ავლა ცალკეული გასაღებისთვის

API გასაღებებს შეუძლიათ უარი თქვან სემანტიკური ქეშიდან წაკითხვაზე `cacheDefaultMode`-ის მეშვეობით:

| მნიშვნელობა | ქცევა                                                              |
| ----------- | ------------------------------------------------------------------ |
| `legacy`    | ქეშის ჩვეულებრივი ქცევა (ნაგულისხმევი)                             |
| `bypass`    | ქეშში ძიების მთლიანად გამოტოვება; ყოველთვის upstream-ის გამოძახება |

დააყენეთ გასაღების შექმნისას (`POST /api/keys`) ან განახლებისას (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### ქეშის გვერდის ავლა ცალკეული მოთხოვნისთვის

ნებისმიერ მოთხოვნას შეუძლია ქეშის გვერდის ავლა გასაღების პარამეტრების მიუხედავად:

```
X-OmniRoute-No-Cache: true
```

სინქრონიზებული/იმპორტირებული მოდელებისთვის `PUT /api/provider-models` იღებს `provider`, `modelId` და
`maxOutputTokenOverride` ველებს: დადებითი მთელი რიცხვი ადგენს გამომავალი ტოკენების ხელით განსაზღვრულ ზღვარს, ხოლო `null`
ასუფთავებს მას ნაგულისხმევი მნიშვნელობის აღსადგენად. `GET /api/provider-models?provider=<provider>` აბრუნებს ამ
მნიშვნელობებს `modelOutputOverrides`-ში, მათ შორის იმ მოდელებისთვისაც, რომლებსაც მორგებული მოდელის მწკრივი არ აქვთ. ჩანაცვლებითი პარამეტრი
იყენებს შესრულების დროის `max_output_tokens` შესაძლებლობას და ნარჩუნდება მოდელის ხელახალი სინქრონიზაციის შემდეგ. OpenAI-თან თავსებადი
პროვაიდერის გვერდი გვთავაზობს რედაქტირების/გასუფთავების იმავე კონტროლებს და აღნიშნავს მოდელებს, რომლებსაც ხედვის აშკარად განსაზღვრული მხარდაჭერა აქვთ.

მორგებული Chat Completions კვანძები მსჯელობის აშკარად გამორთვის მოთხოვნებს ზემდგომ ბეკენდს უსადაგებენ.
კავშირის წარმატებული შემოწმება ავტომატურად ირჩევს ჩატის შაბლონის კონტროლებს თითოეული ზუსტი მოდელის ID-სთვის,
რომლის `/models` ჩანაწერიც ადასტურებს ცნობილ `owned_by` მნიშვნელობას: `vllm`, `sglang` ან `llamacpp`.
OpenAI-თან თავსებადმა გამჭვირვალე გარსებმა შესაძლოა მოდელის თავდაპირველი ჩანაწერი ჩადგმულ
`openai` ობიექტში შეინარჩუნონ; აღმოჩენა მაქსიმუმ სამ ასეთ გარსს მიჰყვება. მოდელები, რომელთა კუთვნილება არ არის მითითებული, უცნობია ან
კონფლიქტურია, ინარჩუნებენ OpenAI-ის ჩვეულებრივ ქცევას. აღმოჩენა ხელახლა იყენებს კატალოგის არსებულ მოთხოვნას,
არ წარმოქმნის დასრულების ტოკენებს და უქმდება, როდესაც კავშირის endpoint იცვლება.

იმ ბეკენდისთვის, რომელიც ამ მეტამონაცემებს არ ამჟღავნებს, ქცევის დასაფიქსირებლად გამოიყენეთ პროვაიდერის ნაწილობრივი
განახლების არსებული API:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

ეს body გააგზავნეთ `PUT /api/providers/<connection-id>`-თან ერთად. ამ კავშირზე მსჯელობის
აშკარად მითითებული ძალისხმევა `none` იგზავნება როგორც `chat_template_kwargs.thinking=false` და
`chat_template_kwargs.enable_thinking=false`. აშკარად მითითებული ნატიური შაბლონის მნიშვნელობები კვლავ პრიორიტეტულია,
თუ სერვერის მხარეს არსებული მსჯელობის წესი ძალისხმევას იძულებით არ განსაზღვრავს. ეს პარამეტრი მოქმედებს მხოლოდ მაშინ, როდესაც მორგებული
OpenAI-თან თავსებადი კავშირი Chat Completions body-ს აგზავნის; Responses მოთხოვნები და ჩვეულებრივი
პროვაიდერები მოთხოვნის ნატიურ სტრუქტურას ინარჩუნებენ. OpenAI-ის ჩვეულებრივი
`reasoning_effort` მნიშვნელობის უცვლელად გადასაცემად `reasoningControl` დააყენეთ `openai`-ზე, ხოლო ავტომატური აღმოჩენის გამოსაყენებლად გამოტოვეთ ან დააყენეთ `null`-ზე.

Claude Code-ის ავტომატური რეჟიმის კლასიფიკატორის მოთხოვნებში ნატიური აზროვნება ნაგულისხმევად გამორთულია, როდესაც ისინი
მსჯელობის აშკარად მითითებულ კონტროლებს არ შეიცავს. აღმოჩენა იყენებს კლასიფიკატორის სისტემურ მარკერს Claude-ის ფორმატის
მოთხოვნებში და არა მოდელის სახელებს ან დასრულების ლიმიტებს. body-ში აშკარად მითითებული კონტროლები, მხარდაჭერილი ძალისხმევის/აზროვნების
header-ები, მარშრუტიზაციის წესები და მოდელისთვის განსაზღვრული ძალისხმევა არსებულ პრიორიტეტს ინარჩუნებს. კლასიფიკატორის ორივე
ეტაპი ინარჩუნებს თავის prompt-ებს, დასრულების ლიმიტებს, გაჩერების მიმდევრობებსა და ზემდგომი სისტემის რეალურ ნებართვის
გადაწყვეტილებებს; მეორე ეტაპს კვლავ შეუძლია მოთხოვნილი ხილული მსჯელობა ჩვეულებრივი ტექსტის სახით წარმოქმნას.

### ვერსია და გამოშვების არხი

```bash
GET /api/system/version
```

მხოლოდ loopback-ზე ხელმისაწვდომი მართვის მარშრუტი (ადმინისტრატორის ავტორიზაციით). აბრუნებს გაშვებულ ვერსიას, უახლეს
გამოქვეყნებულ ვერსიასა და ავტომატური განახლების სტატუსს. `releaseChannel` და `channels` დამატებითი
ველებია (rail 3.8.54); `channel` ინარჩუნებს თავის მნიშვნელობას — განთავსების რეჟიმს, რომელსაც მართვის პანელის განახლების კომპონენტი
იყენებს (`npm`, `source` ან `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — გაშვებული build-ის npm არხი: `nightly` — `-nightly.*` ვერსიებისთვის,
  `next` — სხვა წინასწარი გამოშვებებისთვის (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` — სტაბილური ვერსიისთვის, რომლის
  ძირითადი ვერსია `channels.latest`-ზე ძველია, სხვა შემთხვევაში კი `latest`. იგივე წესებია, რაც
  `scripts/release/dist-tag.mjs`-ში, რომელიც გამოქვეყნებისას npm dist-tag-ს ირჩევს.
- `channels` — თითოეული dist-tag-ის უახლესი გამოქვეყნებული ვერსია, მიღებული `npm view omniroute dist-tags`-იდან (რეესტრის
  HTTP სარეზერვო ვარიანტით), რომელიც `latest`-ის მსგავსად იგივე 10-წუთიანი TTL-ით კეშირდება. `latest` ყოველთვის არსებობს
  (სარეზერვოდ გამოიყენება `latest` ველი, შემდეგ კი `"unavailable"`); `next`, `nightly` და `lts` გამოჩნდება
  მხოლოდ შესაბამისი dist-tag-ის არსებობისას. `Cache-Control: no-cache` მოთხოვნა ორივე მოძიებას განაახლებს.

არხების მოდელი (`latest` = v3 4.0 GA-მდე, `next` = rc, `nightly` = `develop` build-ები,
`lts` = v3 პატჩები 4.0 GA-ის შემდეგ) აღწერილია `docs/ops/RELEASE_STRATEGY.md`-ში.

## ტოკენების ლიმიტები

თითოეული API გასაღებისთვის განსაზღვრული **ტოკენების** ბიუჯეტები (განსხვავდება ზემოთ აღწერილი USD-ზე დაფუძნებული ბიუჯეტისგან). კონტროლი უშუალოდ მოთხოვნის დამუშავების გზაზე ხორციელდება: როდესაც გასაღების მიმდინარე დროის ფანჯარაში გამოყენება მის ლიმიტს მიაღწევს, მოთხოვნები უარყოფილი იქნება შეცდომით `429 Too Many Requests`. ლიმიტები შეიძლება გავრცელდეს კონკრეტულ `model`-ზე, `provider`-ზე ან გასაღებზე `global` მასშტაბით; როდესაც მოთხოვნას რამდენიმე ლიმიტი შეესაბამება, მოქმედებს ყველაზე მკაცრი.

```bash
# გასაღების ტოკენების ლიმიტების სია (მოიცავს მიმდინარე დროის ფანჯრის გამოყენებას)
GET /api/usage/token-limits?apiKeyId=key-123

# ტოკენების ლიმიტის შექმნა ან განახლება
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ტოკენების ლიმიტის წაშლა id-ის მიხედვით
DELETE /api/usage/token-limits?id=tl-abc
```

> **სქემის შენიშვნები** (`setTokenLimitSchema`): `apiKeyId` და `scopeType` (`model` | `provider` | `global`) სავალდებულოა. `scopeValue` სავალდებულოა, გარდა იმ შემთხვევისა, როდესაც `scopeType` არის `global` (მაგ., მოდელის id `model` მოქმედების სფეროსთვის, პროვაიდერის id კი `provider` მოქმედების სფეროსთვის). `tokenLimit` უნდა იყოს დადებითი მთელი რიცხვი (სტრიქონიდან გარდაქმნილი). არასავალდებულო: `id` (გამოტოვეთ შესაქმნელად, მიუთითეთ გასაახლებლად), `resetInterval` (`daily` | `weekly` | `monthly`, ნაგულისხმევია `monthly`), `resetTime` (`HH:MM`), `enabled` (ნაგულისხმევია `true`). `GET` პასუხებში თითოეულ ლიმიტს ემატება `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` და `nextResetAt`. ეს მართვის კლასის endpoint-ია (ავთენტიფიკაცია ცენტრალიზებულად კონტროლდება ავტორიზაციის pipeline-ის მიერ).

## მდგრადობა (გაფართოებული)

OmniRoute უზრუნველყოფს დროებითი შეფერხებების მართვის სამ დამოუკიდებელ მექანიზმს; ქვემოთ მოცემული მართვის endpoint-ები ოპერატორებს მათი მდგომარეობის წაკითხვისა და პარამეტრების ხელით შეცვლის საშუალებას აძლევს:

| მოქმედების არეალი   | მდგომარეობის საცავი                                      | წაკითხვა                                  | ჩამოყრა / გასუფთავება                                            |
| ------------------- | -------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| პროვაიდერის ბრეკერი | `domain_circuit_breakers` + მეხსიერებაში                 | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                     |
| კავშირის დაყოვნება  | `rateLimitedUntil` პროვაიდერის კავშირებზე                | `/api/rate-limits`, `/api/providers/[id]` | (ხელახლა ჩაირთვება საჭიროებისას; გაასუფთავეთ პროვაიდერის PUT-ით) |
| მოდელის დაბლოკვა    | მეხსიერებაში არსებული მოდელების ხელმისაწვდომობის რეესტრი | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                         |

`PATCH /api/resilience` იღებს პროვაიდერის ბრეკერის ხელით განსაზღვრულ პარამეტრებს `providerBreaker.oauth`-ისა და `providerBreaker.apikey`-ის ქვეშ. თითოეულ პროფილს აქვს `degradationThreshold`-ის, `failureThreshold`-ისა და `resetTimeoutMs`-ის მხარდაჭერა; იგივე ველები ხელმისაწვდომია Dashboard → Settings → Resilience-ში.

```bash
# ერთი მოდელის დაბლოკვის გასუფთავება
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# ყველა დაბლოკვის წაშლა
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

სრული კონცეპტუალური ცნობარისა და ბრეკერის ნაგულისხმევი პარამეტრებისთვის იხილეთ [`CLAUDE.md`](../../CLAUDE.md) → „მდგრადობის შესრულების დროის მდგომარეობა“ და [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### სიხშირის შეზღუდვის რიგი და ავტომატური ჩართვის დამცავი მექანიზმი

- **მხარდაჭერილი ჩაწერის გზა**: `POST /api/rate-limits`, სხეულით `{"connectionId": "<id>", "enabled": true|false}`, არის მხარდაჭერილი მართვის endpoint-ი კავშირისთვის სიხშირის შეზღუდვის დაცვის ჩასართავად ან გამოსართავად. `PUT /api/providers/[id]` განზრახ არ ცვლის და არ გადართავს `rateLimitProtection`-ს (#11278).
- **`enabled: false`-ის სემანტიკა**: `enabled: false`-ის დაყენება კავშირისთვის ცალსახად განსაზღვრულ დაცვას აუქმებს, თუმცა აქტიურ API-გასაღების კავშირს **არ** გამორიცხავს ავტომატური ჩართვის გლობალური დამცავი მექანიზმიდან (`autoEnableApiKeyProviders = true`). `reconcileEnabledConnections`-ში (`open-sse/services/rateLimitManager.ts`) `false` და `undefined` ეკვივალენტურია; ცალსახად განსაზღვრული დაცვის არმქონე აქტიური API-გასაღების კავშირები ავტომატური ჩართვის დამცავი მექანიზმით დაცული რჩება.
- **გლობალური გამორთვა**: API-გასაღების კავშირების სიხშირის შეზღუდვის რიგების გარეშე გამოსაყენებლად, გლობალურად გამორთეთ დამცავი მექანიზმი `RATE_LIMIT_AUTO_ENABLE=false`-ის (გარემოს ცვლადი) ან `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`-ის მეშვეობით (Settings → Resilience / `PATCH /api/resilience`).

## MCP სერვერი

## A2A სერვერი

OmniRoute უზრუნველყოფს A2A (აგენტებს შორის) JSON-RPC 2.0 ბოლო წერტილს, ასევე REST გარსს ინსპექტირებისა და საინფორმაციო დაფის გამოყენებისთვის.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # არასავალდებულოა, თუ OMNIROUTE_API_KEY არ არის დაყენებული
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

მხარდაჭერილი მეთოდები (ყველა დამოკიდებულია `settings.a2aEnabled`-ზე):

| მეთოდი           | აღწერა                                                              |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | უნარის სინქრონული შესრულება; აბრუნებს `{task, artifacts, metadata}` |
| `message/stream` | იმავე უნარების ნაკრების ნაკადური SSE შესრულება                      |
| `tasks/get`      | დავალების მიღება `taskId`-ის მიხედვით                               |
| `tasks/cancel`   | დავალების გაუქმება `taskId`-ის მიხედვით                             |

ჩაშენებული უნარები: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### აგენტის ბარათი

```bash
GET /.well-known/agent.json
```

აბრუნებს საჯარო A2A აგენტის ბარათს (სახელი, აღწერა, შესაძლებლობები, უნარების კატალოგი, ავტორიზაციის სქემა) — საჯაროდ კეშირდება 1 საათით. ავტორიზაცია საჭირო არ არის.

### REST დამხმარე საშუალებები

| მეთოდი | მისამართი                    | აღწერა                                                                                                               |
| ------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A-ის ჩართულობის სტატუსი + დავალებების სტატისტიკა + კეშირებული აგენტის ბარათის შეჯამება                             |
| GET    | `/api/a2a/tasks`             | დავალებების სია — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (არ არის იმპლემენტირებული REST დამხმარე საშუალების სახით — შექმენით JSON-RPC `message/send`-ის მეშვეობით)            |
| GET    | `/api/a2a/tasks/[id]`        | ერთი დავალების მიღება                                                                                                |
| POST   | `/api/a2a/tasks/[id]/cancel` | დავალების გაუქმება                                                                                                   |

**ავტორიზაცია:** REST დამხმარე საშუალებები მართვის ავტორიზაციის გარეშე მუშაობს (წაკითხვადია საინფორმაციო დაფიდან); JSON-RPC `/a2a` მარშრუტი იყენებს Bearer `OMNIROUTE_API_KEY`-ს, თუ ის კონფიგურირებულია.

## ACP-ის (Agent Client Protocol) მართვა

შვილობილ პროცესებად. ეს საბოლოო წერტილები მართავს ACP აგენტების აღმოჩენასა და მორგებული აგენტების
რეგისტრაციას.

| მეთოდი | გზა               | აღწერა                                                                                                                                                                     |
| ------ | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | ყველა ცნობილი CLI აგენტის (ჩაშენებული + მორგებული) სია ინსტალაციის სტატუსით, ვერსიითა და ბინარული ფაილით                                                                   |
| POST   | `/api/acp/agents` | მორგებული ACP აგენტის რეგისტრაცია ან კეშის განახლება — მოთხოვნის სხეული: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` ან `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | მორგებული ACP აგენტის წაშლა — მოთხოვნის პარამეტრი: `?id=<agentId>`                                                                                                         |

**პასუხის მაგალითი** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**ავთენტიფიკაცია:** საჭიროა მართვის სესია (მართვის პანელის `auth_token` cookie) ან
მართვის არეზე შეზღუდული API გასაღები.

სრული დეტალებისთვის იხილეთ [ACP-ის ფრეიმვორკი](../frameworks/ACP.md).

## ავთენტიფიკაცია

ავტორიზაციის მონაცემთა ოთხი ტიპისა (დაფის სესია, ლოკალური CLI ტოკენი, `oma_live_…` წვდომის
ტოკენი, მართვის არეალის API გასაღები) და მათი ინფერენსის გასაღებებისგან განსხვავებების შესახებ იხილეთ
[მართვის ავთენტიფიკაცია](../guides/MANAGEMENT-AUTH.md).

- დაფის მარშრუტები (`/dashboard/*`) იყენებს `auth_token` cookie-ს
- შესვლისას გამოიყენება შენახული პაროლის ჰეში; სარეზერვო ვარიანტია `INITIAL_PASSWORD`
- `requireLogin`-ის ჩართვა ან გამორთვა შესაძლებელია `/api/settings/require-login`-ის მეშვეობით
- `/v1/*` მარშრუტები, როდესაც `REQUIRE_API_KEY=true`, შესაძლოა მოითხოვდეს Bearer API გასაღებს
- ამ ცნობარში „მართვის ტოკენი“ / „მართვის არეალის API გასაღები“ ნიშნავს ამ სახელმძღვანელოში აღწერილ ერთ-ერთ ტიპს და არა დამატებით, განუსაზღვრელ საიდუმლო მონაცემთა ტიპს

> **შეუთავსებელი ცვლილება (v3.8.0)** — `/api/v1/agents/tasks/*` და დაყოვნების პერიოდის მართვის საბოლოო წერტილები ახლა მოითხოვს **მართვის ავთენტიფიკაციას** (დაფის `auth_token` cookie-ს ან მართვის არეალის API გასაღებს). კლიენტები, რომლებიც ადრე ამ მარშრუტებს ავთენტიფიკაციის გარეშე იძახებდნენ, მიიღებენ `401 Unauthorized` პასუხს. იხილეთ კომიტი `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
