## მიმოხილვა

OmniRoute ახორციელებს მოთხოვნის მოდულურ შეკუმშვის კონვეიერს, რომელიც **პროაქტიულად** მუშაობს მანამ, სანამ მოთხოვნები ზედა დონის პროვაიდერებამდე მიაღწევს. ეს ნიშნავს, რომ ტოკენების დაზოგვა გამჭვირვალედ ხდება — თქვენს სამუშაო პროცესში ცვლილებები საჭირო არ არის.

```
კლიენტის მოთხოვნა
  → შეკუმშვის სტრატეგიის ამომრჩევი
    → არის კომბინაციის ჩანაცვლება? → გამოიყენე კომბინაციის პარამეტრი
    → მიღწეულია ავტომატური გააქტიურების ზღვარი? → გამოიყენე ავტომატური რეჟიმი
    → არის ნაგულისხმევი რეჟიმი? → გამოიყენე გლობალური პარამეტრი
    → გამორთულია? → გამოტოვე შეკუმშვა
  → არჩეული შეკუმშვის რეჟიმი
    → Off: შეკუმშვის გარეშე
    → Lite: ჰარების/ფორმატირების უსაფრთხო გასუფთავება (~15%)
    → Standard: Caveman-ის სტილში შემავსებელი სიტყვების მოცილება (~30%)
    → Aggressive: ისტორიის დაძველება + შეჯამება (~50%)
    → Ultra: ევრისტიკული შემცირება + კოდის ბლოკების გათხელება (~75%)
    → RTK: ბრძანებების გათვალისწინებით ტერმინალის/ხელსაწყოს გამომავალი მონაცემების გაფილტვრა (ზედა დონის 60-90%-იანი დიაპაზონი)
    → Stacked: მოწესრიგებული მრავალძრავიანი კონვეიერი, ჩვეულებრივ ჯერ RTK, შემდეგ Caveman (შესაბამისი კონტექსტის 78-95%-იანი დიაპაზონი)
  → შეკუმშული მოთხოვნა → პროვაიდერი
```

## შეკუმშვის რეჟიმები

### Off

შეკუმშვა არ გამოიყენება. ყველა შეტყობინება უცვლელად გადაიცემა.

### Lite რეჟიმი (~15% დაზოგვა, <1ms დაყოვნება)

ყველაზე უსაფრთხო რეჟიმი — სემანტიკური ცვლილების გარეშე, მხოლოდ ფორმატირების გასუფთავება:

| ტექნიკა                  | აღწერა                                                              |
| ------------------------ | ------------------------------------------------------------------- |
| `collapseWhitespace`     | ზედიზედ არსებული ცარიელი ხაზებისა და დაბოლოების ჰარების გაერთიანება |
| `dedupSystemPrompt`      | დუბლირებული სისტემური შეტყობინებების მოცილება                       |
| `compressToolResults`    | ვრცელი ხელსაწყოს/ფუნქციის გამომავალი მონაცემების შეკუმშვა           |
| `removeRedundantContent` | განმეორებითი ინსტრუქციების მოცილება                                 |
| `replaceImageUrls`       | base64 გამოსახულების მონაცემთა URI-ების შემოკლება                   |

**საუკეთესოა:** მუდმივად ჩართული გამოყენებისთვის და უსაფრთხოების მხრივ კრიტიკული სამუშაო პროცესებისთვის.

### Standard რეჟიმი (~30% დაზოგვა)

შთაგონებულია [Caveman-ით](https://github.com/JuliusBrussee/caveman) — მნიშვნელობის შენარჩუნებით აშორებს შემავსებელ სიტყვებსა და ზედმეტად ვრცელ ფორმულირებებს:

- აშორებს შემავსებელ სიტყვებს ("გთხოვთ", "ვფიქრობ", "ზოგადად", "სინამდვილეში")
- ამოკლებს ზედმეტად ვრცელ ფრაზებს ("იმისათვის, რომ" → "რომ", "ამის შედეგად" → "რადგან")
- აშორებს თავაზიან შემარბილებელ ფრაზებს ("ხომ არ შეგაწუხებდათ...", "თუ შეძლებდით...")
- 30-ზე მეტი regex წესი, მორგებული პროგრამირების მოთხოვნებზე

**საუკეთესოა:** ყოველდღიური პროგრამირების სამუშაო პროცესებისა და ხარჯებზე ორიენტირებული გუნდებისთვის.

### Aggressive რეჟიმი (~50% დაზოგვა)

ისტორიის გონივრული მართვა ხანგრძლივი სესიებისთვის:

- **შეტყობინებების დაძველება** — ძველი შეტყობინებები თანდათან უფრო მეტად იკუმშება
- **ხელსაწყოს შედეგების შეკუმშვა** — ხელსაწყოს გრძელი გამომავალი მონაცემები იკვეთება ან გამოტოვებით ჩანაცვლდება (პირველი/ბოლო ხაზები,
  დამთხვევის მქონე ხაზების გაფილტვრა, JSON გასაღებების კომპაქტურად წარმოდგენა)
- **სტრუქტურული მთლიანობის დამცავი მექანიზმები** — უზრუნველყოფს `tool_use` + `tool_result` წყვილების თანმიმდევრულობას
- **კონტექსტის ფანჯრის გათვალისწინება** — იცავს თითოეული მოდელის ტოკენების ლიმიტებს

**საუკეთესოა:** ხანგრძლივი გამართვის სესიებისა და დიდი კოდური ბაზებისთვის.

### Ultra რეჟიმი (~75% დაზოგვა)

მაქსიმალური შეკუმშვა ტოკენების მხრივ კრიტიკული სცენარებისთვის:

- **ევრისტიკული შემცირება** — ტექსტის ქულებზე დაფუძნებული ტოკენური შემცირება
- **სტრუქტურის შენარჩუნება** — შემოსაზღვრული კოდის ბლოკები, სტრიქონშიდა კოდი, URL-ები და იდენტიფიკატორები
  დროებითი ნიშნებით ჩანაცვლდება და შემდეგ სიტყვასიტყვით აღდგება; ისინი არასოდეს იკვეცება
- **არასავალდებულო SLM დონე** — კონფიგურაციის შემთხვევაში მცირე ლოკალურ მოდელს შეუძლია შემცირების დახვეწა
- Aggressive რეჟიმისგან დამოუკიდებელია: ის არ ახორციელებს შეტყობინებების დაძველებას, ხელსაწყოს შედეგების შეკუმშვას
  ან სარეზერვო შემაჯამებლის გამოყენებას (მხოლოდ SLM დონის შეცდომამ შეიძლება გადაამისამართოს სარეზერვო დამუშავება
  aggressive რეჟიმის გავლით)

**საუკეთესოა:** როდესაც კონტექსტის ლიმიტებს განმეორებით აწყდებით.

### RTK რეჟიმი (ზედა დონის 60-90%-იანი დიაპაზონი)

RTK რეჟიმი ოპტიმიზებულია პროგრამირების აგენტის სესიებში არსებული ვრცელი ხელსაწყოს გამომავალი მონაცემებისთვის:

- ამოიცნობს ბრძანებების/გამომავალი მონაცემების კლასებს, როგორიცაა `git status`, `git diff`, `git log`, ტესტების გამშვები საშუალებები,
  TypeScript/Vite/Webpack აგებები, ESLint/Biome/Prettier, npm აუდიტები/ინსტალაციები, Docker ჟურნალები, ინფრასტრუქტურის
  გამომავალი მონაცემები და გარსის ზოგადი გამომავალი მონაცემები
- იყენებს JSON ფილტრების პაკეტებს `open-sse/services/compression/engines/rtk/filters/`-დან
- პროექტის ან გლობალური `filters.toml` ფაილებიდან შემოაქვს RTK TOML schema v1 ფილტრები, ჩაშენებული ტესტების
  ვალიდაციითა და პროექტის ფაილების სანდოობის შემოწმებით
- მოიცავს 55 ჩაშენებულ ფილტრს, ჩაშენებული შემოწმების ნიმუშებით
- აშორებს ANSI საკონტროლო მიმდევრობებს, პროგრესის ზოლებს, განმეორებით ხაზებსა და არაპრაქტიკულ ხმაურს
- ინარჩუნებს ჩავარდნებს, შეცდომებს, გაფრთხილებებს, შეცვლილ ფაილებს, შეჯამებებსა და გრძელი გამომავალი მონაცემების ბოლო ნაწილს
- მხარს უჭერს სანდოობის შემოწმებით დაცულ პროექტის ფილტრებს, გლობალურ ფილტრებსა და სურვილისამებრ დაფარული საწყისი გამომავალი მონაცემების აღდგენას

**საუკეთესოა:** აგენტის სესიებისთვის, რომლებიც შეიცავს გარსის, აგების, ტესტირების, git-ის, grep-ისა და ფაილების გამომავალი მონაცემების ჩანაწერებს.

### Stacked რეჟიმი (შესაბამისი კონტექსტის 78-95%-იანი დიაპაზონი)

Stacked რეჟიმი რამდენიმე შეკუმშვის ძრავას განსაზღვრული თანმიმდევრობით ამუშავებს. ნაგულისხმევი კონვეიერია:

ეს თანმიმდევრობა ჯერ ტერმინალის/ხელსაწყოს გამომავალ მონაცემებს ამცირებს, შემდეგ კი
დარჩენილ ბუნებრივ ენაზე დაწერილ მოთხოვნაზე Caveman-ის სემანტიკურ შეკუმშვას იყენებს. Stacked კონვეიერების კონფიგურაცია შესაძლებელია გლობალურად ან

## ზედა დონის დაზოგვის გამოთვლა

OmniRoute შეკუმშვით მიღებულ დაზოგვას ორი წყაროს საფუძველზე აღწერს: ზედა დონის პროექტების საორიენტაციო ტესტებისა და
OmniRoute-ის საკუთარი ძრავების კომბინაციის.

| წყარო   | ზედა დონის README-დან აქ გამოყენებული მაჩვენებელი                                                                                                                                        |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%`-ით ნაკლები გამომავალი ტოკენი, საორიენტაციო ტესტებში გამომავალი მონაცემების საშუალოდ `65%`-იანი დაზოგვა, `22-87%` დიაპაზონი და `~46%`-იანი შემავალი მონაცემების შეკუმშვის ხელსაწყო |
| RTK     | ბრძანების გამომავალი მონაცემების `60-90%`-იანი დაზოგვა; სანიმუშო სესიაში `~118,000 -> ~23,900` ტოკენი, ანუ დაზოგილია `79.7%` (`~80%`)                                                    |

ხელსაწყოს/კონტექსტის ურთიერთგადამფარავი მონაცემებისთვის, OmniRoute-ის ნაგულისხმევი კომბინაცია ძრავებს თანმიმდევრულად იყენებს:

```txt
RTK -> Caveman
```

საერთო დაზოგვა მულტიპლიკაციურია და არა ადიტიური:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ეს `78-95%` მაჩვენებელი მოქმედებს მაშინ, როდესაც RTK-საც და Caveman-საც შეუძლია ერთი და იმავე შემავალი მონაცემების/კონტექსტის შემცირება.
Caveman-ის პასუხის გამომავალი რეჟიმი განცალკევებულია: მისი ჩართვისას გამოიყენეთ თავად Caveman-ის გამომავალი მონაცემების დაზოგვის მაჩვენებლები (საშუალოდ `65%`,
მთავარი მაჩვენებელი `~75%`, დიაპაზონი `22-87%`). ბილინგის ჯამური დაზოგვა დამოკიდებულია თქვენს მოთხოვნებსა და გამომავალ მონაცემებს შორის თანაფარდობაზე.

### რას ნიშნავს სინამდვილეში „შესაფერისი“

მთავარ სათაურში მითითებული 15-95%-იანი დიაპაზონი რეალურია, თუმცა ის ვრცელდება მხოლოდ **ჭარბ ან ზედმეტად ვრცელ** შიგთავსზე — განმეორებად
შეცდომის სტრიქონებზე, აგების ჟურნალზე, რომელიც ერთი და იმავე გაფრთხილებას განუწყვეტლივ იმეორებს, ზედმეტად დიდ `grep`/ფაილის წაკითხვის ამონაწერზე. ეს
**არ** ნიშნავს, რომ თითოეული მოთხოვნა ამდენს დაზოგავს.

ემპირიულად დადასტურებულია (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): `stacked`
(RTK + Caveman) გაშვებამ Anthropic-ის ფორმის `tool_result` ბლოკზე, რომელიც 300 იდენტურ
შეცდომის სტრიქონს შეიცავდა, უზრუნველყო **ტოკენების 95.93%-იანი დაზოგვა / სიმბოლოების 96.26%-იანი დაზოგვა** — ზუსტად რეკლამირებულ
დიაპაზონში. თუმცა იმავე დამუშავების ჯაჭვის გაშვება ხელსაწყოს ჩვეულებრივ, არაჭარბ გამომავალ მონაცემებზე (სუფთა `grep` დამთხვევების სია,
მოკლე ფაილის წაკითხვა, ჩვეულებრივი სასაუბრო ტექსტი) მართებულად იძლევა **ნულთან მიახლოებულ დაზოგვას**, რადგან
წასაშლელი განმეორებადი შიგთავსი არ არსებობს, ხოლო `validateCompression()` (`validation.ts`) უარს ამბობს ისეთი
გადაწერილი ვერსიის გაგზავნაზე, რომელიც კოდის ბლოკებს, URL-ებს, სათაურებს, ვერსიებს ან ALL-CAPS მუდმივების იდენტიფიკატორებს ამოიღებდა ან შეცვლიდა.

ეს მოსალოდნელი და უსაფრთხო ქცევაა, არა შეცდომა: პროგრამირების სესიაში, რომელიც ძირითადად სუფთა ფაილებს კითხულობს ან მათში `grep`-ით ეძებს,
ჯამური დაზოგვა ზომიერი იქნება მაშინაც კი, როცა შეკუმშვა სრულადაა ჩართული, ხოლო სესიაში, რომელიც წარუმატებელ
ციკლს ან ზედმეტად ბევრის გამომტან ლინტერს წააწყდება, ამ ტრაფიკზე სრულ 78-95%-იან დიაპაზონს მიიღებთ. ერთი სესიის
დაზოგვის დაბალი ჯამური პროცენტი არ გამოიყენოთ იმის მტკიცებულებად, რომ შეკუმშვა არასწორადაა კონფიგურირებული — ჯერ შეამოწმეთ, იყო თუ არა

## კონფიგურაცია

### მართვის პანელი

გადადით `Dashboard → Context & Cache`-ში:

- **Caveman** — რეჟიმის არჩევა, ენის პაკეტები, წინასწარი გადახედვა და გლობალური ნაგულისხმევი პარამეტრები
- **RTK** — ბრძანებების ფილტრის წინასწარი გადახედვა, RTK-ის უსაფრთხოების პარამეტრები და ფილტრების კატალოგი
- **Compression Combos** — სახელდებული ძრავების კონვეიერები, რომლებიც მარშრუტიზაციის კომბინაციებს ენიჭება
- **Auto-Trigger Threshold** — შეკუმშვის ავტომატურად ჩართვა, როდესაც ტოკენების რაოდენობა ზღვრულ მნიშვნელობას გადააჭარბებს

### ცალკეული კომბინაციის გადაფარვა

`Dashboard → Context & Cache → Compression Combos`-ში მიანიჭეთ შეკუმშვის კომბინაცია მარშრუტიზაციის
კომბინაციას:

```txt
კომბინაცია: "free-tier-fallback"
  შეკუმშვის კომბინაცია: "coding-agent-stack"
  კონვეიერი: RTK -> Caveman
  სამიზნეები:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ეს საშუალებას გაძლევთ, უფასო/კოდირებისთვის განკუთვნილ პროვაიდერებთან გამოიყენოთ საფეხურებრივი შეკუმშვა, ხოლო ფასიან
გამოწერებში მსუბუქი რეჟიმი შეინარჩუნოთ.

ეს „ცალკეული კომბინაციის გადაფარვის“ მინიჭება განსხვავდება **მარშრუტიზაციის კომბინაციის შეკუმშვის
რეჟიმის** გადაფარვისგან (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ველის
სქემა ასევე იღებს `rtk`, `stacked` და `omniglyph` მნიშვნელობებს) — ეს გადაფარვა არ ირჩევს სახელდებულ
შეკუმშვის კომბინაციის კონვეიერს; ის მხოლოდ ადგენს `compressionMode` ველს, რომელსაც
`resolveCompressionPlan` ამოწმებს. მისი დაყენება შესაძლებელია როგორც კომბინაციის ბარათზე (`Dashboard → Combos`), ასევე,
#6760-დან მოყოლებული, თითოეული მარშრუტიზაციის კომბინაციისთვის „Assign to routing“ სიაში,
`Dashboard → Context & Cache → Compression Combos`-ში, ზემოთ აღწერილი კონვეიერის მინიჭების მოსანიშნი ველის
გვერდით. ორივე ინტერფეისი მონაცემებს იმავე `PUT /api/combos/{id}` ბოლო წერტილის მეშვეობით ინახავს.

### ცალკეული მოთხოვნის გადაფარვა

ერთი მოთხოვნისთვის შეკუმშვის გეგმის გადასაფარად გაგზავნეთ `x-omniroute-compression` მოთხოვნის
სათაური. მას უმაღლესი პრიორიტეტი აქვს — ის უპირატესია მარშრუტიზაციის კომბინაციის გადაფარვაზე, აქტიურ პროფილზე,
ავტომატურ გააქტიურებასა და პანელის ნაგულისხმევ პარამეტრზე. უცნობი მნიშვნელობები იგნორირდება (მოთხოვნა არასოდეს უარყოფილა) და
გლობალური მთავარი გადამრთველი კვლავ ყველაფერს აკონტროლებს: როდესაც შეკუმშვა გლობალურად გამორთულია, სათაური მას
ვერ ჩართავს. მნიშვნელობები:

| მნიშვნელობა   | ეფექტი                                                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| `off`         | ამ მოთხოვნისთვის შეკუმშვა არ გამოიყენება.                                                                         |
| `default`     | პანელიდან მიღებული ნაგულისხმევი პროფილი (აქტიურ პროფილს უგულებელყოფს). დანაკარგიანი ძრავები გამორთული რჩება.      |
| `safe`        | იგივეა, რაც სათაურის გამოტოვება: მხოლოდ დუბლიკატების მოცილება და ჰარიების შეკუმშვა.                               |
| `allow-lossy` | ამ მოთხოვნის ოპერატორის გეგმის შენარჩუნება, შეჯამებების, რელევანტურობის ფილტრებისა და სტილის გადაწერის ჩათვლით.   |
| `engine:<id>` | ერთი ძრავა, თუ ის ჩართულია, მაგალითად `engine:rtk`. ეს ამ ძრავისთვის ცალკეული მოთხოვნის დონეზე თანხმობის მიცემაა. |
| `<combo>`     | სახელდებული კომბინაცია, რომელიც ჯერ სახელით (რეგისტრის გაუთვალისწინებლად), შემდეგ კი id-ით ემთხვევა.              |

`allow-lossy`-ის, `engine:<id>`-ის ან სახელდებული კომბინაციის გარეშე დანაკარგიანი ძრავები არ გამოიყენება.
როდესაც შეკუმშვა ჩართულია, მოთხოვნაზე კვლავ ვრცელდება სესიის დუბლიკატების მოცილება და ჰარიების შეკუმშვა.

გამოყენებული გეგმა პასუხში აისახება `X-OmniRoute-Compression: <mode>; source=<source>` სათაურში,
სადაც `<source>` არის ერთ-ერთი: `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` ან `off`.

RTK-ის მონაცემებით, ეკონომია `60-90%`-ია, ხოლო მის README-ში მოცემულ სესიის ნიმუშში დაზოგილია `~80%`.

## შეკუმშვის გაფართოებული სისტემები

ზემოთ აღწერილი 7 რეჟიმის გარდა (საწყისი კოდი ასევე იღებს `codex-responses` და
`omniglyph` რეჟიმებს, რომლებსაც ეს სახელმძღვანელო არ მოიცავს), ქვემოთ მოცემულ სექციებში აღწერილია ფუნქციები,
რომლებიც ამ რეჟიმების შიგნით ან მათთან ერთად მუშაობს: ხელსაწყოს შედეგის შეკუმშვა და პროგრესული დაძველება
აგრესიული ძრავის 1-ლი და მე-2 ნაბიჯებია (Aggressive რეჟიმი და
დაწყობილი კონვეიერის `aggressive` ნაბიჯი), დაწყობილი კონვეიერი განსაზღვრავს Stacked რეჟიმის მუშაობას, ქეშის გათვალისწინებით შეკუმშვა
`aggressive` და `ultra` რეჟიმებს `standard` რეჟიმამდე აქვეითებს ქეშირების მხარდამჭერი პროვაიდერებისთვის, როდესაც შეკუმშვა
ჩართულია, ხოლო Caveman გამომავალი რეჟიმი და გამომავალი სტილები სისტემური მოთხოვნის ნებაყოფლობითი ინსტრუქციებია,
რომლებიც ნაგულისხმევად გამორთულია და მოთხოვნის შეკუმშვის ნაცვლად მოდელის გამომავალს აყალიბებს.

### ქეშის გათვალისწინებით შეკუმშვა

ზოგიერთი პროვაიდერი (მაგალითად, Anthropic მოთხოვნის ქეშირებით) მხარს უჭერს **მოთხოვნის ქეშირებას**,
რაც მათ საშუალებას აძლევს, მოთხოვნის ნაწილები დააქეშონ ხარჯებისა და დაყოვნების შესამცირებლად. როდესაც
ქეშირება ჩართულია, აგრესიულმა შეკუმშვამ შეიძლება რეალურად **გააუარესოს** წარმადობა,
რადგან ის ცვლის დაქეშილ ტოკენებს და ამით ქეშს აუქმებს.

`cachingAware.ts` მოდული ამ პრობლემას **ქეშირების კონტექსტის აღმოჩენითა** და
**შეკუმშვის სტრატეგიის შესაბამისად მორგებით** აგვარებს.

#### როგორ მუშაობს

1. **ქეშირების კონტექსტის აღმოჩენა** — მოთხოვნის სხეულში `cache_control` მარკერებს ეძებს
2. **ქეშირების პროვაიდერების იდენტიფიცირება** — ამოწმებს, აქვს თუ არა სამიზნე პროვაიდერს ქეშირების მხარდაჭერა
3. **სტრატეგიის მორგება** — ქეშირების პროვაიდერებისთვის `aggressive`/`ultra` რეჟიმებს `standard` რეჟიმამდე აქვეითებს
4. **სისტემური მოთხოვნის გამოტოვება** — სისტემური მოთხოვნები, როგორც წესი, დაქეშილია, ამიტომ მათ არ კუმშავს

სტრატეგიის დამხმარე ფუნქცია ასევე აბრუნებს `deterministicOnly` ალამს, თუმცა გეგმის შემქმნელი
მხოლოდ სტრატეგიას მოიხმარს — ამჟამად ქვემოთ ნაკადში ამ ალამს არაფერი კითხულობს.

#### კოდის მაგალითი

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← ქეშის მარკერი
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### როდის გამოვიყენოთ

ქეშის გათვალისწინებით შეკუმშვა **ყოველთვის ჩართულია** — კონფიგურაცია საჭირო არ არის. ის ამოქმედდება ყოველთვის,
როდესაც შეკუმშვა ჩართულია და სამიზნე პროვაიდერი მოთხოვნის ქეშირებას მხარს უჭერს (Anthropic, OpenAI
და სხვ.); აშკარად მითითებული `cache_control` მარკერები საჭირო არ არის — დაქვეითებას მხოლოდ
ქეშირების პროვაიდერის არსებობაც იწვევს, ხოლო მხოლოდ მარკერები ამას არასოდეს აკეთებს (მარკერების აღმოჩენა ქეშის
ტელემეტრიას მიეწოდება და არა სტრატეგიის გადაწყვეტილებას).

### პროგრესული დაძველება

ხანგრძლივი საუბრები შეტყობინებების მრავალ მიმოცვლას აგროვებს, თუმცა ძველი მიმოცვლები თანდათან ნაკლებად
რელევანტური ხდება. `progressiveAging.ts` მოდული **შეტყობინებებს მიმოცვლის დაშორების მიხედვით ამარტივებს**
(დაშორება საუბრის ბოლოდან იზომება). მოწოდებული ნაგულისხმევი პარამეტრებით
(`verbatim: 2, light: 2, moderate: 3`):

- **ბოლო 2 მიმოცვლა (დაშორება ≤ 2)**: უცვლელად ინახება
- **დაშორება 3**: Caveman შეკუმშვა (შემავსებელი სიტყვების მოცილება)
- **დაშორება 4+**: ასისტენტის შეტყობინებები შეჯამდება; მომხმარებლის შეტყობინებებიდან მხოლოდ პირველი
  სტრიქონი რჩება, მაქსიმუმ 120 სიმბოლომდე; სხვა როლები უცვლელია. სისტემური მოთხოვნები, უკვე დაძველებული
  შეტყობინებები და მომხმარებლის უახლესი შეტყობინება, დაშორების მიუხედავად, ყოველთვის უცვლელად ინახება.
  არაფერი იშლება სრულად, ხოლო `light`
  დიაპაზონი მოწოდებული ნაგულისხმევი პარამეტრებით მიუწვდომელია (`light` უდრის `verbatim`-ს).

#### კოდის მაგალითი

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... კიდევ 50 მიმოცვლა ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // ბოლო 3 მიმოცვლა: უცვლელად
  light: 8, // დაშორება <= 8: მსუბუქი შეკუმშვა
  moderate: 20, // დაშორება <= 20: caveman შეკუმშვა
  fullSummary: 5, // ტიპისთვის სავალდებულოა, მაგრამ დიაპაზონების განმსაზღვრელი კოდი არ კითხულობს
  // დაშორება > 20: შეჯამებული (ასისტენტი) / პირველი სტრიქონი შენარჩუნებულია (მომხმარებელი)
});

// saved = დაზოგილი ტოკენების რაოდენობა
```

#### როდის გამოვიყენოთ

პროგრესული დაძველება `aggressive` რეჟიმისთვის **ყოველთვის ჩართულია** — ის
`compressAggressive()`-ის მე-2 ნაბიჯია. Ultra რეჟიმი მას არ ასრულებს. ის
განსაკუთრებით ეფექტურია შემდეგ შემთხვევებში:

- ხანგრძლივი პროგრამირების სესიები
- მრავალდღიანი საუბრები
- მრავალი ხელსაწყოს გამოძახების მქონე აგენტური სამუშაო პროცესები

### Caveman გამომავალი რეჟიმი

Caveman გამომავალი რეჟიმი ამატებს **სისტემური მოთხოვნის ინსტრუქციებს**, რომლებიც თავად მოდელს
ლაკონიური გამომავლის გენერირებას სთხოვს — `lite` დონე ითხოვს მოკლე პასუხებს სრული წინადადებების შენარჩუნებით, `full`
სთხოვს მას, „უპასუხოს მოკლედ, როგორც ჭკვიანმა გამოქვაბულის ადამიანმა“, ხოლო `ultra` ითხოვს ტელეგრაფულ გამომავალს;
ინსტრუქციები ამას მხოლოდ ითხოვს და გარანტიას ვერ იძლევა. მოთხოვნები მათ
`applyOutputStyles()`-ის (`open-sse/services/compression/outputStyles/apply.ts`) მეშვეობით იღებს:
`open-sse/handlers/chatCore.ts` თავდაპირველად არჩევანს უკუთავსებადობის შიმის საშუალებით ადგენს
(`resolveOutputStyleSelection()` ფაილში
`open-sse/services/compression/outputStyles/backCompat.ts`), რომელიც, სანამ `outputStyles`
ცარიელია, ჩართულ `cavemanOutputMode`-ს `terse-prose` გამომავალ სტილზე ასახავს
`cavemanOutputMode.intensity` ინტენსივობით (იხილეთ უკუთავსებადობა ქვემოთ); არაცარიელი `outputStyles`
არჩევანი უცვლელად გამოიყენება, რის შემდეგაც `cavemanOutputMode.enabled` და `intensity`
გავლენას აღარ ახდენს, თუმცა მისი `autoClarity` გადამრთველი კვლავ მოქმედებს. `outputMode.ts` შეიცავს
ინსტრუქციების ტექსტებს (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), შიგთავსის გვერდის ავლისა და
განთავსების დამხმარე ფუნქციებს, რომლებსაც ჩასმა იყენებს; მის საკუთარ `applyCavemanOutputMode()` ჩამსმელს
საწარმოო გარემოში გამომძახებელი არ ჰყავს.

#### როგორ მუშაობს

ეს რეჟიმი შემავალ მონაცემებს არ კუმშავს. ის სისტემურ პრომპტს ინსტრუქციების ბლოკს უმატებს
(იხილეთ ქვემოთ, როგორ მუშაობს ჩასმა), ხოლო მოთხოვნისთვის არჩეული შემავალი მონაცემების კუმშვის
ნებისმიერი რეჟიმი კვლავ სრულდება ამის შემდეგ, იმ სხეულზე, რომელიც ახლა ამ ბლოკსაც შეიცავს. იმ
საერთო საზღვრების პუნქტის წინ, რომლითაც ყველა დონე სრულდება, ინგლისური `full` დონე ამბობს:

> „უპასუხე მოკლედ, როგორც ჭკვიანმა გამოქვაბულის ადამიანმა. გამოტოვე არტიკლები (a/an/the), შემავსებელი სიტყვები (just/really/basically/actually/simply), თავაზიანობის ფორმები, ყოყმანის გამომხატველი სიტყვები. ფრაგმენტები დასაშვებია. გამოიყენე მოკლე სინონიმები (big და არა extensive, fix და არა implement). ზუსტად შეინარჩუნე მთელი ტექნიკური შინაარსი, კოდი, შეცდომები, URL-ები და იდენტიფიკატორები.“

ეს განსაკუთრებით კარგად მუშაობს შემდეგ შემთხვევებში:

- კოდის გენერაცია (უფრო მოკლე შედეგი = ნაკლები ტოკენი)
- სწრაფი კითხვა-პასუხი (ვრცელი ახსნა საჭირო არ არის)
- პაკეტური დამუშავება (მაქსიმალური გამტარუნარიანობა)

#### როდის გამოვიყენოთ

გამოქვაბულის ადამიანის შედეგის რეჟიმი **არჩევითია**. როდესაც კუმშვა ჩართულია (`enabled: true`, მთავარი გადამრთველი
Compression Settings გვერდზე), ჩართეთ ის `cavemanOutputMode.enabled`-ით; `intensity`
ირჩევს `lite`, `full` ან `ultra` დონეს:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

კუმშვის კომბინაციის **Output Mode** გადამრთველი (`outputMode`, დონე — `outputModeIntensity`-ში)
იმავე გადამრთველს ადგენს იმ მოთხოვნებისთვის, რომლებზეც ეს კომბინაცია ვრცელდება, ხოლო
`omniroute_set_compression_engine` MCP ხელსაწყო მას თავისი ლოგიკური `outputMode`
არგუმენტის მეშვეობით წერს. არაცარიელი `outputStyles` არჩევანი ამ გადამრთველზე უპირატესია. მართვის
პანელში **Terse prose** შედეგის სტილის ჩართვა იმავე ბლოკს ამატებს (იხილეთ ქვემოთ, შედეგის
სტილები).

კატალოგთან ადარებს (უცნობი id-ები და ლოკალთან შეუსაბამო სტილები
გამოირიცხება და შეცდომას არასოდეს იწვევს; თუ არჩევანის შედეგად არცერთი სტილი არ დარჩა,
სხეული უცვლელი რჩება და გამოტოვების მიზეზად `no_styles` მიეთითება), არჩეულ ინსტრუქციებს
კატალოგის თანმიმდევრობით აერთიანებს,
საზღვრების პუნქტს **ერთხელ** ამატებს (ასევე უსაფრთხოების პუნქტს, `SAFETY_BOUNDARIES`-ს ან მის
თარგმანს, როდესაც არჩეულია `less-code` ან `ponytail`) და ბლოკს
ერთადერთი იდემპოტენტურობის მარკერით (`[OmniRoute Output Styles]`) იწყებს, ამიტომ ხელახლა
გამოყენება არაფერს ცვლის. როდესაც განსაზღვრულ ენას (იხილეთ ქვემოთ ენის შერჩევა) თარგმანი
აქვს, ინგლისურის ნაცვლად ლოკალიზებული ინსტრუქცია ჩაისმება.

არაცარიელი `messages` მასივის მქონე სხეულში იდემპოტენტურობის შემოწმება შიგთავსის
გვერდის ავლამდე სრულდება: როდესაც `[OmniRoute Output Styles]` მარკერი უკვე არის ზედა დონის
`system` ველში (სტრიქონში ან შიგთავსის ბლოკების მასივში) ან სისტემურ შეტყობინებაში, რომლის
შიგთავსიც სტრიქონია, სხეული უცვლელი რჩება მიზეზით `already_applied` და საკვანძო სიტყვების
შემოწმება არ სრულდება.
წინააღმდეგ შემთხვევაში, შიგთავსის გვერდის ავლა (`shouldBypassCavemanOutputMode()`
ფაილში `open-sse/services/compression/outputMode.ts`) ამოწმებს ბოლო სამი
შეტყობინების ტექსტს, მათი როლის მიუხედავად, და მთელი სვლისთვის სტილებს გამოტოვებს, როდესაც ეს
ტექსტი ემთხვევა უსაფრთხოების, შეუქცევადი მოქმედების ან დაზუსტების საკვანძო სიტყვებს, ან
თანმიმდევრობაზე დამოკიდებულ კომბინაციას: `first`, `then`, `after that`, `before`, `rollback` ან
`backup`, რომელსაც 240 სიმბოლოს ფარგლებში მოსდევს `delete`, `drop`, `migrate`, `deploy` ან
`release`. გვერდის ავლა სრულდება, სანამ **Auto-Clarity Bypass** გადამრთველი
(`cavemanOutputMode.autoClarity`, ნაგულისხმევად ჩართული) ჩართულია; გადამრთველის გამორთვა
საკვანძო სიტყვების შემოწმებას გამოტოვებს.

როდესაც გვერდის ავლა სვლას ატარებს, `placeSystemInstruction()` (იმავე ფაილში), რომელიც
არასოდეს ქმნის ახალ `messages[0]`-ს, ბლოკს ათავსებს პირველივე ნაპოვნ ადგილას შემდეგი
თანმიმდევრობით:

1. საწყისი სისტემური შეტყობინება სტრიქონული შიგთავსით: ბლოკი მის ტექსტს ემატება.
2. ზედა დონის `system` ველი: ბლოკი ემატება სტრიქონის ტექსტს ან
   შიგთავსის ბლოკების მასივს ახალი ტექსტური ბლოკის სახით.
3. პირველი მომდევნო სისტემური შეტყობინება სტრიქონული შიგთავსით: ბლოკი მის
   ტექსტს ემატება.
4. თუ ზემოთ ჩამოთვლილთაგან არცერთი არ არის: ბლოკი თავსდება ახალ სისტემურ შეტყობინებაში
   `messages`-ის ბოლოში.

სხეულში, რომელსაც `messages` მასივი არ აქვს (ან ცარიელი მასივი აქვს), შიგთავსის გვერდის ავლა
არ სრულდება და ზედა დონის `system` ველი არ განიხილება. ბლოკი ემატება სტრიქონული
`instructions` ველის ტექსტს, თუ ეს ველი უკვე არ შეიცავს
`[OmniRoute Output Styles]` მარკერს — ამ შემთხვევაში სხეული უცვლელი რჩება მიზეზით
`already_applied`. როდესაც სხეულს არ აქვს სტრიქონული `instructions` ველი, მაგრამ შეიცავს
`input`-ს (სტრიქონს ან მასივს), ბლოკი ხდება `instructions` და ანაცვლებს ამ ველში მანამდე
არსებულ ნებისმიერ არასტრიქონულ მნიშვნელობას. სხეული, რომელსაც არც სტრიქონული
`instructions` ველი აქვს და არც სტრიქონული ან მასივის ტიპის `input`, უცვლელი რჩება და
გამოტოვების მიზეზად `no_messages` მიეთითება.

#### როგორ ჩავრთოთ

მართვის პანელში: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles სექცია: თითო სტილზე ერთი მწკრივი ჩართვა/გამორთვის
გადამრთველითა და დონის ამომრჩევით. სტილები ჩაისმება, სანამ თავად შეკუმშვა ჩართულია (გვერდის
მთავარი გადამრთველი, `enabled`). **Auto-Clarity Bypass** გადამრთველი მდებარეობს **Caveman**
გვერდზე (`/dashboard/context/caveman`), მის **Output Mode** ბარათში. პროგრამულად,
შეკუმშვის კონფიგურაცია არჩევანს ასე ინახავს:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

უკუთავსებადობა: სანამ `outputStyles` ცარიელია, ძველი `cavemanOutputMode.enabled`
პარამეტრი `terse-prose`-ს შეესაბამება `cavemanOutputMode.intensity` დონეზე. ამ შემთხვევაში
ბლოკი იწყება `[OmniRoute Output Styles]` მარკერით, მაშინ როცა ძველი
`applyCavemanOutputMode()` ჩამსმელი `[OmniRoute Caveman Output Mode]`-ს წერდა.
მარკერის ქვემოთ ტექსტი ძველ ჩამატებას ემთხვევა en, pt-BR, es, de, fr, it, ru, id და vi
ენებზე; ja და zh ენებზე კი მას საზღვრების პუნქტის წინ ერთი დამატებითი გამოტოვება აქვს.
`terse-prose` ითარგმნება pt-BR, es, de, fr, it, ru, zh, ja, id და vi ენებზე, ამიტომ მოთხოვნა,
რომლის განსაზღვრული ენაც `hu` არის, იღებს ინგლისურ ტექსტს იქ, სადაც ძველი ჩამსმელი მის
უნგრულ ვარიანტს იყენებდა.

გამოტანის სტილის ენის შერჩევა (`resolveOutputStyleLanguage()` ფაილში
`outputStyles/apply.ts`): როდესაც `languageConfig.enabled` ჩართულია, `autoDetect` ნიმუშად იღებს
მოთხოვნის `messages` მასივში ტექსტის მქონე ბოლო მომხმარებლის შეტყობინებას (სტრიქონულ
შიგთავსს ან მისი შიგთავსის ნაწილების `text`-ს) და მასზე Caveman ძრავის დეტექტორს
(`detectCompressionLanguage()`) უშვებს. დეტექტორი აბრუნებს `zh`-ს ტექსტისთვის, რომელიც
ჰანის სიმბოლოებს შეიცავს, მაგრამ კანას — არა; სხვა შემთხვევაში ის აბრუნებს `it`, `pt-BR`,
`es`, `de`, `fr`, `ru`, `ja`, `hu` და `id` ენებიდან იმას, რომელსაც მინიშნებების ყველაზე მეტი
დამთხვევა აქვს, ხოლო როცა არცერთი არ ემთხვევა — `en`-ს; ტექსტისთვის, რომლის კლასიფიკაციაც
შეუძლებელია, გამოიყენება ინგლისური და არასოდეს `defaultLanguage`, ხოლო `vi` არასოდეს
განისაზღვრება, მიუხედავად იმისა, რომ სტილებს `vi` ტექსტი მოჰყვება. Responses API-ს სხეული
თავის სვლებს `input`-ში ინახავს, რომელიც ნიმუშად არ აიღება, ამიტომ მისთვის ჯერ
`defaultLanguage`, შემდეგ კი ინგლისური გამოიყენება. როდესაც `messages`-ში არცერთ
მომხმარებლის შეტყობინებას არ აქვს ტექსტი, ან როდესაც `autoDetect` გამორთულია, ჯერ
`defaultLanguage`, შემდეგ კი ინგლისური გამოიყენება. როდესაც `languageConfig.enabled`
გამორთულია, ენა ინგლისურია — გარდა იმ შემთხვევისა, როდესაც მოთხოვნაზე შეკუმშვის კომბინაცია
ვრცელდება (მოთხოვნის მარშრუტიზაციის კომბინაციაზე მინიჭებული კომბინაცია, ან ნაგულისხმევი
შეკუმშვის კომბინაცია, რომელსაც chatCore ჩაშენებული თანმიმდევრული კონვეიერისთვის მიმართავს):
კომბინაციის გამოყენება ამ მოთხოვნისთვის `languageConfig.enabled`-ს რთავს და
`defaultLanguage`-ს კომბინაციის ენობრივი პაკეტებიდან ადგენს (შენახული მნიშვნელობა, თუ ის
კომბინაციის ერთ-ერთ პაკეტს წარმოადგენს; წინააღმდეგ შემთხვევაში კომბინაციის პირველი პაკეტი,
რომლის ნაგულისხმევი მნიშვნელობაა `en`), ხოლო შენახული `autoDetect` (ნაგულისხმევად ჩართული)
კვლავ გამოიყენება. Caveman-ის შეყვანის ძრავა წესების პაკეტის ენას სხვაგვარად ირჩევს —
თითოეული ტექსტური ნაწილისთვის ცალ-ცალკე და, როდესაც ავტომატური ამოცნობა გამორთულია,
`enabledPacks`-ით შეზღუდულად.

   `<path>:<digits>:`, სადაც პირველი ორწერტილის წინა ტექსტი ცარიელ სივრცეს არ შეიცავს;
   ინარჩუნებს მხოლოდ ასეთ ხაზებს, მაქსიმუმ 30-ს, რასაც მოსდევს დარჩენილი დამთხვევების
   რაოდენობა და დამთხვევების მქონე ფაილების სია; ყველა სხვა ხაზი იშლება. სტრატეგიის
   გასააქტიურებლად ერთი ასეთი ხაზიც საკმარისია, ამიტომ დროის ნიშნულით დაწყებული ჟურნალის
   ხაზი, მაგალითად `12:30:45`, ასევე ითვლება.
3. **`shellOutput`**: გამოტანა, რომელიც შეიცავს ANSI CSI მიმდევრობას (`ESC[`, შემდეგ
   ციფრები ან წერტილმძიმეები და ბოლოს ასო, როგორც ფერის კოდებში) ან ტექსტის ნებისმიერ
   ადგილას `$`-ს, რომელსაც ცარიელი სივრცე მოსდევს, კარგავს ამ მიმდევრობებს (სხვა
   escape-მიმდევრობები, როგორიცაა `ESC[?25l` ან OSC ფანჯრის სათაურის მიმდევრობა,
   შენარჩუნდება) და ინარჩუნებს ბოლო 50 ხაზს, ხოლო ზედიზედ გამეორებული ხაზები
   გაერთიანდება. რადგან ეს შემოწმება `json`-სა და `errorMessage`-ზე ადრე სრულდება,
   ასეთი `$`-ის შემცველი JSON ან შეცდომის გამოტანა მათამდე ვერ აღწევს, სანამ
   `shellOutput` ჩართულია.
4. **`json`**: 2,000 სიმბოლოზე მეტი სიგრძის JSON მონაცემი, რომელიც იწყება `{`-ით ან
   `[`-ით (არასავალდებულო საწყისი ცარიელი სივრცის შემდეგ) და წარმატებით იშლება,
   მოკლედ შეჯამდება: 7-ზე მეტი ელემენტის მქონე მასივი ინარჩუნებს პირველ 5 და ბოლო 2
   ელემენტს და ელემენტების მთლიან რაოდენობას, ხოლო ობიექტი — პირველ 20 გასაღებს;
   თითოეული ჩადგმული ობიექტის ან მასივის მნიშვნელობა ჩანაცვლდება `{…N keys}`
   ადგილმჭერით (მასივისთვის N მისი სიგრძეა), ხოლო `_remaining_<N>_keys` მარკერი
   ითვლის პირველი 20-ის შემდეგ გამოტოვებულ გასაღებებს. სკალარული მნიშვნელობები
   მთლიანად კოპირდება, ამიტომ 20 ან ნაკლები გასაღების მქონე ობიექტი ჩადგმული
   მნიშვნელობების გარეშე მხოლოდ ხელახლა დაიწევა — მინიფიცირებულს სიმბოლოები ემატება
   და ის უცვლელი რჩება.
5. **`errorMessage`**: გამოტანა, რომელიც ნებისმიერ ადგილას და ასოების ნებისმიერი
   რეგისტრით შეიცავს `error:`, `error `-ს (სიტყვა, რომელსაც გამოტოვება მოსდევს,
   როგორც `no error found`-ში), `[error]`, `exception:`, `exception `,
   `[exception]` ან `traceback`-ს, ინარჩუნებს პირველ ხაზს, მომდევნო 10 ხაზსა და ბოლო
   3 ხაზს, ხოლო მათ შორის ხაზების ადგილას სვამს `… [N frames elided] …` მარკერს.
   მარკერი მხოლოდ მაშინ ჩნდება, როცა პირველ ხაზს 13-ზე მეტი ხაზი მოსდევს, ამიტომ
   14 ან ნაკლები ხაზისგან შემდგარი შეცდომის გამოტანა არ მოკლდება (12 ან 13 ხაზის
   შემთხვევაში ბოლო 3 ხაზი უკვე შენარჩუნებულ ხაზებს იმეორებს).

სტრატეგიის დამთხვევის შემდეგ, მაშინაც კი, თუ ის არაფერს ზოგავს, მომდევნო სტრატეგიები
აღარ გამოიცდება. როდესაც დამთხვეული სტრატეგია სავარაუდო ტოკენებს არ ზოგავს
(სიგრძე ÷ 4, ზემოთ დამრგვალებით) — მაგალითად, კოდის მსგავსი ფაილი 25 ან ნაკლები
ხაზით, ან 2,000 სიმბოლოზე მეტი სიგრძის JSON მასივი 7 ან ნაკლები ელემენტით —
აგრესიული ძრავა ხელსაწყოს თავდაპირველ შედეგს ინარჩუნებს: ორივე გამომძახებელი
(`compressAggressive()` და `compressAnthropicToolResultBlock()`) ინარჩუნებს საწყის
შედეგს, როდესაც `saved` არის 0 ან ნაკლები, ხოლო თავად `compressToolResult()` მაინც
აბრუნებს ამ სტრატეგიის გამოტანას. ხელსაწყოს შედეგის ეტაპი საბოლოო გადაწყვეტილება
არ არის: ძრავის სარეზერვო შემაჯამებელს კვლავ შეუძლია 8,192 სიმბოლოზე გრძელი `tool`
ან `function` შეტყობინების შემოკლება (`maxTokensPerMessage`, 2,048, გამრავლებული 4-ზე).

#### როდის გამოვიყენოთ

ხელსაწყოს შედეგის შეკუმშვა აგრესიული ძრავის პირველი ეტაპია (`compressAggressive()`
ფაილში `open-sse/services/compression/aggressive.ts`), ამიტომ ის მუშაობს აგრესიულ
რეჟიმში და მრავალსაფეხურიანი მილსადენის `aggressive` ეტაპზე. ის კუმშავს OpenAI-ს
ფორმის `tool` და `function` შეტყობინებებს და Anthropic-ის `tool_result` ბლოკებში
არსებულ ტექსტს. თითოეულ სტრატეგიას აქვს საკუთარი გადამრთველი
`aggressive.toolStrategies`-ში და ნაგულისხმევად ყველა ჩართულია. მართვის პანელში
გადამრთველები Caveman გვერდის **გაფართოებულ** ხედშია, როცა შეკუმშვა ჩართულია და
ნაგულისხმევი რეჟიმი აგრესიულია.

### მრავალსაფეხურიანი მილსადენი

მრავალსაფეხურიანი რეჟიმი **რამდენიმე ძრავას თანმიმდევრულად** უშვებს — ჩვეულებრივ,
ჯერ RTK-ს (ხელსაწყოს გამოტანის 60-90%-ით შემცირება), შემდეგ კი Caveman-ს დარჩენილ
ტექსტზე (შეტანის ~46%-ით შემცირება). მათი გაერთიანებით მიიღება **დასაშვები
78-95%-იანი დიაპაზონი** (იხილეთ ზემოთ „ზედა ნაკადის დანაზოგის გამოთვლა“):
`1 - (1 - 0.60..0.90) × (1 - 0.46)` საშუალოდ ≈89%-ია.

#### როგორ მუშაობს

```
შეტანა (1000 ტოკენი)
  → RTK (ბრძანებების მცოდნე ფილტრი) → 200 ტოკენი
    → Caveman (შემავსებელი ტექსტის ამოღება) → 108 ტოკენი
  → გამოტანა (108 ტოკენი, ~89%-იანი დანაზოგი)
```

#### როდის გამოვიყენოთ

გამოიყენეთ მრავალსაფეხურიანი რეჟიმი:

- ხელსაწყოებით დატვირთული სამუშაო პროცესებისთვის (აგენტური პროგრამირება, კვლევა)
- ხარჯებისადმი მგრძნობიარე პაკეტური დამუშავებისთვის
- როცა ტოკენების მაქსიმალური დაზოგვა გჭირდებათ

მრავალსაფეხურიანი მილსადენების კონფიგურაცია ხდება შეკუმშვის გლობალური
`stackedPipeline` პარამეტრით ან სახელდებული შეკუმშვის კომბინაციით, რომელიც
მარშრუტიზაციის კომბინაციას ენიჭება (იხილეთ ზემოთ „თითოეული კომბინაციისთვის
გადაფარვა“) — და არა ავტოკომბინაციის `modePack`-ით (ეს ველი მხოლოდ ავტოკომბინაციის
მოდელის შერჩევის წონებს ცვლის, ხოლო `stacked` პაკეტის დასაშვები სახელი არ არის).

## შეკუმშვის კომბინაციების გადაფარვები

სხვადასხვა გამოყენების შემთხვევისთვის ქცევის ზუსტად მოსარგებად, შეგიძლიათ შეკუმშვის გლობალური რეჟიმი **თითოეული კომბინაციისთვის** გადააფაროთ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ეს სასარგებლოა შემდეგ შემთხვევებში:

- **პროგრამირების კომბინაციები**: ხანგრძლივი სესიებისთვის გამოიყენეთ `aggressive` რეჟიმი
- **სწრაფი კითხვა-პასუხის კომბინაციები**: სწრაფი პასუხებისთვის გამოიყენეთ `lite` რეჟიმი
- **ინსტრუმენტებზე ძლიერ დამოკიდებული კომბინაციები**: მაქსიმალური ეკონომიისთვის გამოიყენეთ `stacked` რეჟიმი
- **საწარმოო კომბინაციები**: ქეშირების პროვაიდერებისთვის გადაფარვა გამორთული დატოვეთ — მუდმივად ჩართული, ქეშის გათვალისწინებით შესრულებული კორექტირება `aggressive`/`ultra` რეჟიმებს ავტომატურად `standard` რეჟიმამდე აქვეითებს
  (ასარჩევი `cache-aware` რეჟიმი არ არსებობს)
