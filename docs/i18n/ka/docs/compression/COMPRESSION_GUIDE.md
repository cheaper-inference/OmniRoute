## მიმოხილვა

OmniRoute ახორციელებს მოთხოვნის მოდულურ შეკუმშვის კონვეიერს, რომელიც **პროაქტიულად** მუშაობს მანამ, სანამ მოთხოვნები ზედა დონის პროვაიდერებამდე მიაღწევს. ეს ნიშნავს, რომ ტოკენების დაზოგვა გამჭვირვალედ ხდება — თქვენს სამუშაო პროცესში ცვლილებები საჭირო არ არის.

```
კლიენტის მოთხოვნა
  → შეკუმშვის სტრატეგიის ამომრჩევი
    → არის კომბინაციის ჩანაცვლება? → გამოიყენე კომბინაციის პარამეტრი
    → მიღწეულია ავტომატური გააქტიურების ზღვარი? → გამოიყენე ავტომატური რეჟიმი
    → არის ნაგულისხმევი რეჟიმი? → გამოიყენე გლობალური პარამეტრი
    → გამორთულია? → გამოტოვე შეკუმშვა
  → არჩეული შეკუმშვის რეჟიმი
    → Off: შეკუმშვის გარეშე
    → Lite: ჰარების/ფორმატირების უსაფრთხო გასუფთავება (~15%)
    → Standard: Caveman-ის სტილში შემავსებელი სიტყვების მოცილება (~30%)
    → Aggressive: ისტორიის დაძველება + შეჯამება (~50%)
    → Ultra: ევრისტიკული შემცირება + კოდის ბლოკების გათხელება (~75%)
    → RTK: ბრძანებების გათვალისწინებით ტერმინალის/ხელსაწყოს გამომავალი მონაცემების გაფილტვრა (ზედა დონის 60-90%-იანი დიაპაზონი)
    → Stacked: მოწესრიგებული მრავალძრავიანი კონვეიერი, ჩვეულებრივ ჯერ RTK, შემდეგ Caveman (შესაბამისი კონტექსტის 78-95%-იანი დიაპაზონი)
  → შეკუმშული მოთხოვნა → პროვაიდერი
```

## შეკუმშვის რეჟიმები

### გამორთული

შეკუმშვა არ გამოიყენება. ყველა შეტყობინება უცვლელად გადაეცემა.

### Lite რეჟიმი (~15% დანაზოგი, <1ms დაყოვნება)

ყველაზე უსაფრთხო რეჟიმი — ფორმატირების გასუფთავება. მისი ხელსაწყოს შედეგების შემოკლება კარგავს ინფორმაციას, ამიტომ ნაგულისხმევი
გზა (`allow-lossy`, `engine:lite` ან დასახელებული კომბინაციის არჩევის გარეშე) Lite რეჟიმს უშვებს
`compressToolResults: false` პარამეტრით: ხელსაწყოს ადრინდელი შედეგები პროვაიდერს უცვლელად მიეწოდება.

| ტექნიკა                  | აღწერა                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------------------- |
| `collapseWhitespace`     | ზედიზედ ცარიელი ხაზებისა და ბოლოში არსებული სივრცეების გაერთიანება                                |
| `dedupSystemPrompt`      | დუბლირებული სისტემური შეტყობინებების წაშლა                                                        |
| `compressToolResults`    | ადრინდელი ხელსაწყოს შედეგების Lite-ლიმიტამდე შემოკლება (ინფორმაციის დაკარგვა: მხოლოდ მოთხოვნისას) |
| `removeRedundantContent` | განმეორებითი ინსტრუქციების ამოღება                                                                |
| `replaceImageUrls`       | base64 სურათების მონაცემთა URI-ების შემოკლება                                                     |

**საუკეთესოა:** ყოველთვის ჩართული გამოყენებისთვის, უსაფრთხოებაზე კრიტიკული სამუშაო პროცესებისთვის.

### სტანდარტული რეჟიმი (~30% დანაზოგი)

შთაგონებულია [Caveman](https://github.com/JuliusBrussee/caveman)-ით — შლის შემავსებელ სიტყვებსა და ვრცელ ფორმულირებებს მნიშვნელობის შენარჩუნებით:

- შლის შემავსებელ სიტყვებს („please“, „I think“, „basically“, „actually“)
- ამოკლებს ვრცელ ფრაზებს („in order to“ → „to“, „as a result of“ → „because“)
- შლის თავაზიან შემარბილებელ ფორმულირებებს („Would you mind...“, „If you could possibly...“)
- 30-ზე მეტი რეგულარული გამოსახულება, რომლებიც კოდირებისთვის განკუთვნილ მოთხოვნებზეა მორგებული

**საუკეთესოა:** ყოველდღიური კოდირების სამუშაო პროცესებისთვის, ხარჯებზე ორიენტირებული გუნდებისთვის.

### აგრესიული რეჟიმი (~50% დანაზოგი)

გრძელი სესიებისთვის ისტორიის ჭკვიანური მართვა:

- **შეტყობინებების დაძველება** — ძველი შეტყობინებები თანდათან უფრო მეტად იკუმშება
- **ხელსაწყოს შედეგების შეკუმშვა** — ხელსაწყოს გრძელი შედეგები იჭრება ან იფარება (პირველი/ბოლო ხაზები,
  შესაბამისი ხაზების გაფილტვრა, JSON გასაღებების შემოკლება)
- **სტრუქტურული მთლიანობის დამცავები** — უზრუნველყოფს `tool_use` + `tool_result` წყვილების თანმიმდევრულობას
- **კონტექსტის ფანჯრის გათვალისწინება** — ითვალისწინებს თითოეული მოდელის ტოკენების ლიმიტებს

**საუკეთესოა:** ხანგრძლივი გამართვის სესიებისთვის, დიდი კოდბაზებისთვის.

### Ultra რეჟიმი (~75% დანაზოგი)

მაქსიმალური შეკუმშვა ტოკენებზე კრიტიკული სცენარებისთვის:

- **ევრისტიკული შემცირება** — პროზის ტოკენების ქულებზე დაფუძნებული შემცირება
- **სტრუქტურის შენარჩუნება** — შემოსაზღვრული კოდის ბლოკები, ინლაინ კოდი, URL-ები და იდენტიფიკატორები
  უცვლელად ინიშნება და ხელახლა ერთიანდება; მათი შემცირება არასოდეს ხდება
- **არჩევითი SLM-დონე** — კონფიგურაციის შემთხვევაში მცირე ლოკალურ მოდელს შეუძლია შემცირების დახვეწა
- აგრესიული რეჟიმისგან დამოუკიდებელია: ის არ ახორციელებს შეტყობინებების დაძველებას, ხელსაწყოს შედეგების შეკუმშვას
  ან სარეზერვო შემაჯამებელს (მხოლოდ SLM-დონის ჩავარდნას შეუძლია სარეზერვო გავლა აგრესიულ რეჟიმში გადაიყვანოს)

**საუკეთესოა:** როდესაც კონტექსტის ლიმიტებს განმეორებით აწყდებით.

### RTK რეჟიმი (ზედა დონის დიაპაზონში 60-90%)

RTK რეჟიმი ოპტიმიზებულია კოდირების აგენტების სესიებში გამოჩენილი ვრცელი ხელსაწყოს შედეგებისთვის:

- ამოიცნობს ბრძანებების/გამოსავლის კლასებს, როგორიცაა `git status`, `git diff`, `git log`, ტესტების გამშვებები,
  TypeScript/Vite/Webpack-ის build-ები, ESLint/Biome/Prettier, npm audit/install-ები, Docker-ის ჟურნალები, ინფრასტრუქტურის
  გამოსავალი და ზოგადი shell-ის გამოსავალი
- იყენებს JSON ფილტრების პაკეტებს `open-sse/services/compression/engines/rtk/filters/`-დან
- ახდენს RTK TOML სქემა v1-ის ფილტრების იმპორტს პროექტის ან გლობალური `filters.toml` ფაილებიდან, შიდა ტესტების
  ვალიდაციითა და პროექტის ფაილებისთვის ნდობის შემოწმებით
- მოყვება 56 ჩაშენებული ფილტრი შიდა გადამოწმების ნიმუშებით
- შლის ANSI საკონტროლო მიმდევრობებს, პროგრესის ზოლებს, განმეორებით ხაზებსა და ქმედებისთვის არარელევანტურ ხმაურს
- ინარჩუნებს ჩავარდნებს, შეცდომებს, გაფრთხილებებს, შეცვლილ ფაილებს, შეჯამებებსა და გრძელი გამოსავლის ბოლო ნაწილს
- მხარს უჭერს ნდობით მართულ პროექტის ფილტრებს, გლობალურ ფილტრებსა და ნედლი გამოსავლის აღდგენის არჩევით შესაძლებლობას რედაქტირების შემდეგ

**საუკეთესოა:** აგენტის სესიებისთვის, რომლებშიც გამოიყენება shell, build, test, git, grep და ფაილების გამოსავლის ტრანსკრიპტები.

### კომბინირებული რეჟიმი (დასაშვებ დიაპაზონში 78-95%)

კომბინირებული რეჟიმი შეკუმშვის რამდენიმე ძრავას დეტერმინისტული თანმიმდევრობით ამუშავებს. ნაგულისხმევი კონვეიერია:

```txt
RTK -> Caveman
```

ეს თანმიმდევრობა ჯერ ტერმინალის/ხელსაწყოს გამოსავალს ამოკლებს, შემდეგ კი დარჩენილ ბუნებრივენოვან მოთხოვნაზე Caveman-ის
სემანტიკურ კონდენსაციას იყენებს. კომბინირებული კონვეიერების გლობალურად ან მარშრუტიზაციის კომბინაციებისთვის მინიჭებული
შეკუმშვის კომბინაციების მეშვეობით კონფიგურაცია შესაძლებელია.

**საუკეთესოა:** შერეული კონტექსტისთვის, რომელშიც დიდი ხელსაწყოს ჟურნალები და ადამიანური ინსტრუქციები ან ასისტენტის შეჯამებებია.

## ზედა დონის დაზოგვის გამოთვლა

OmniRoute შეკუმშვით მიღებულ დაზოგვას ორი წყაროს საფუძველზე აღწერს: ზედა დონის პროექტების საორიენტაციო ტესტებისა და
OmniRoute-ის საკუთარი ძრავების კომბინაციის.

| წყარო   | ზედა დონის README-დან აქ გამოყენებული მაჩვენებელი                                                                                                                                        |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%`-ით ნაკლები გამომავალი ტოკენი, საორიენტაციო ტესტებში გამომავალი მონაცემების საშუალოდ `65%`-იანი დაზოგვა, `22-87%` დიაპაზონი და `~46%`-იანი შემავალი მონაცემების შეკუმშვის ხელსაწყო |
| RTK     | ბრძანების გამომავალი მონაცემების `60-90%`-იანი დაზოგვა; სანიმუშო სესიაში `~118,000 -> ~23,900` ტოკენი, ანუ დაზოგილია `79.7%` (`~80%`)                                                    |

ხელსაწყოს/კონტექსტის ურთიერთგადამფარავი მონაცემებისთვის, OmniRoute-ის ნაგულისხმევი კომბინაცია ძრავებს თანმიმდევრულად იყენებს:

```txt
RTK -> Caveman
```

საერთო დაზოგვა მულტიპლიკაციურია და არა ადიტიური:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ეს `78-95%` მაჩვენებელი მოქმედებს მაშინ, როდესაც RTK-საც და Caveman-საც შეუძლია ერთი და იმავე შემავალი მონაცემების/კონტექსტის შემცირება.
Caveman-ის პასუხის გამომავალი რეჟიმი განცალკევებულია: მისი ჩართვისას გამოიყენეთ თავად Caveman-ის გამომავალი მონაცემების დაზოგვის მაჩვენებლები (საშუალოდ `65%`,
მთავარი მაჩვენებელი `~75%`, დიაპაზონი `22-87%`). ბილინგის ჯამური დაზოგვა დამოკიდებულია თქვენს მოთხოვნებსა და გამომავალ მონაცემებს შორის თანაფარდობაზე.

### რას ნიშნავს სინამდვილეში „შესაფერისი“

მთავარ სათაურში მითითებული 15-95%-იანი დიაპაზონი რეალურია, თუმცა ის ვრცელდება მხოლოდ **ჭარბ ან ზედმეტად ვრცელ** შიგთავსზე — განმეორებად
შეცდომის სტრიქონებზე, აგების ჟურნალზე, რომელიც ერთი და იმავე გაფრთხილებას განუწყვეტლივ იმეორებს, ზედმეტად დიდ `grep`/ფაილის წაკითხვის ამონაწერზე. ეს
**არ** ნიშნავს, რომ თითოეული მოთხოვნა ამდენს დაზოგავს.

ემპირიულად დადასტურებულია (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): `stacked`
(RTK + Caveman) გაშვებამ Anthropic-ის ფორმის `tool_result` ბლოკზე, რომელიც 300 იდენტურ
შეცდომის სტრიქონს შეიცავდა, უზრუნველყო **ტოკენების 95.93%-იანი დაზოგვა / სიმბოლოების 96.26%-იანი დაზოგვა** — ზუსტად რეკლამირებულ
დიაპაზონში. თუმცა იმავე დამუშავების ჯაჭვის გაშვება ხელსაწყოს ჩვეულებრივ, არაჭარბ გამომავალ მონაცემებზე (სუფთა `grep` დამთხვევების სია,
მოკლე ფაილის წაკითხვა, ჩვეულებრივი სასაუბრო ტექსტი) მართებულად იძლევა **ნულთან მიახლოებულ დაზოგვას**, რადგან
წასაშლელი განმეორებადი შიგთავსი არ არსებობს, ხოლო `validateCompression()` (`validation.ts`) უარს ამბობს ისეთი
გადაწერილი ვერსიის გაგზავნაზე, რომელიც კოდის ბლოკებს, URL-ებს, სათაურებს, ვერსიებს ან ALL-CAPS მუდმივების იდენტიფიკატორებს ამოიღებდა ან შეცვლიდა.

ეს მოსალოდნელი და უსაფრთხო ქცევაა, არა შეცდომა: პროგრამირების სესიაში, რომელიც ძირითადად სუფთა ფაილებს კითხულობს ან მათში `grep`-ით ეძებს,
ჯამური დაზოგვა ზომიერი იქნება მაშინაც კი, როცა შეკუმშვა სრულადაა ჩართული, ხოლო სესიაში, რომელიც წარუმატებელ
ციკლს ან ზედმეტად ბევრის გამომტან ლინტერს წააწყდება, ამ ტრაფიკზე სრულ 78-95%-იან დიაპაზონს მიიღებთ. ერთი სესიის
დაზოგვის დაბალი ჯამური პროცენტი არ გამოიყენოთ იმის მტკიცებულებად, რომ შეკუმშვა არასწორადაა კონფიგურირებული — ჯერ შეამოწმეთ, იყო თუ არა

გადადით `Dashboard → Context & Cache`-ზე:

- **RTK** — ბრძანებების ფილტრაციის წინასწარი დათვალიერება, RTK-ის უსაფრთხოების პარამეტრები და ფილტრების კატალოგი
- **Compression Combos** — მარშრუტიზაციის კომბოებისთვის მინიჭებული სახელდებული ძრავების პაიპლაინები
- **Auto-Trigger Threshold** — შეკუმშვის ავტომატურად ჩართვა, როდესაც ტოკენების რაოდენობა ზღვარს აჭარბებს

### თითოეული კომბოს გადაფარვა

`Dashboard → Context & Cache → Compression Combos`-ში მარშრუტიზაციის
კომბოს მიუთითეთ შეკუმშვის კომბო:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ეს საშუალებას გაძლევთ, უფასო/კოდირებისთვის განკუთვნილ პროვაიდერებზე გამოიყენოთ დაწყობილი შეკუმშვა,
ხოლო ფასიან გამოწერებზე შეინარჩუნოთ lite რეჟიმი.

ეს **Per-Combo Override** მინიჭება განსხვავდება **routing-combo compression
mode**-ის გადაფარვისგან (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ველის
სქემა ასევე იღებს `rtk`, `stacked` და `omniglyph` მნიშვნელობებს) — ეს გადაფარვა არ ირჩევს
სახელდებულ compression-combo პაიპლაინს; ის მხოლოდ ადგენს `compressionMode` ველს, რომელსაც
`resolveCompressionPlan` ამოწმებს. მისი დაყენება შესაძლებელია როგორც კომბოს ბარათზე
(`Dashboard → Combos`), ისე, #6760-ის შემდეგ, თითოეული მარშრუტიზაციის კომბოსთვის
`Dashboard → Context & Cache → Compression Combos`-ში, „Assign to routing“ სიაში,
ზემოთ აღწერილი პაიპლაინზე მინიჭების ჩამრთველის გვერდით. ორივე ინტერფეისი ცვლილებებს ერთი და იმავე
`PUT /api/combos/{id}` endpoint-ის მეშვეობით ინახავს.

### თითოეული მოთხოვნის გადაფარვა

გაგზავნეთ `x-omniroute-compression` მოთხოვნის ჰედერი, რათა ერთი კონკრეტული მოთხოვნისთვის
გადაფაროთ შეკუმშვის გეგმა. მას ყველაზე მაღალი პრიორიტეტი აქვს — ის უპირატესია მარშრუტიზაციის
კომბოს გადაფარვაზე, აქტიურ პროფილზე, ავტომატურ ჩართვასა და პანელის Default-ზე. უცნობი
მნიშვნელობები იგნორირდება (მოთხოვნა არასდროს უარყოფილა), ხოლო გლობალური მთავარი ჩამრთველი
კვლავ აკონტროლებს ყველაფერს: როდესაც შეკუმშვა გლობალურად გამორთულია, ჰედერი მას ვერ ჩართავს.
მნიშვნელობები:

| Value         | Effect                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `off`         | ამ მოთხოვნისთვის შეკუმშვა არ გამოიყენება.                                                                                    |
| `default`     | პანელიდან მიღებული Default პროფილი (აქტიური პროფილი იგნორირდება). დანაკარგიანი ძრავები გამორთული რჩება.                      |
| `safe`        | იგივე, რაც ჰედერის გამოტოვების შემთხვევაში.                                                                                  |
| `allow-lossy` | ამ მოთხოვნის ოპერატორის გეგმის შენარჩუნება, მათ შორის შეჯამებების, რელევანტურობის ფილტრებისა და სტილის გარდაქმნების.         |
| `engine:<id>` | ერთი ძრავა, როდესაც ის ჩართულია, მაგალითად, `engine:rtk`. ეს არის ამ ძრავისთვის თითოეული მოთხოვნის დონეზე ჩართვის საშუალება. |
| `<combo>`     | სახელდებული კომბო, რომელიც ჯერ სახელით (რეგისტრის უგულებელყოფით), შემდეგ კი id-ით მოიძებნება.                                |

`allow-lossy`-ის, `engine:<id>`-ის ან სახელდებული კომბოს გარეშე დანაკარგიანი ძრავები არ გამოიყენება.
როდესაც დანაკარგიანი Default, ავტომატური ჩართვა ან მარშრუტიზაციის გადაფარვა დაბალ რეჟიმში გადადის,
OmniRoute კონფიგურირებული დაწყობილი პაიპლაინიდან ინარჩუნებს ამოცნობილ უდანაკარგო ნაბიჯებს
კონფიგურირებულ თანმიმდევრობაში. ის `session-dedup → lite`-ზე გადადის მხოლოდ მაშინ, როდესაც
კონფიგურირებული უდანაკარგო ნაბიჯებიდან არცერთი არ რჩება.

Settings პანელის **Effective pipeline**-ის წინასწარი დათვალიერება აჩვენებს ჩვეულებრივ, მუდმივად
გამოყენებად გეგმას. როდესაც ავტომატური ჩართვა შესაძლებელია, იგივე წინასწარი დათვალიერება ასევე
აჩვენებს მის პირობით ეფექტურ პაიპლაინს, რათა პანელისა და ჰედერის გარეშე შესრულებული runtime-ის
გადაწყვეტა ერთმანეთთან თანხვედრაში დარჩეს.

გამოყენებული გეგმა ბრუნდება `X-OmniRoute-Compression: <mode>; source=<source>` პასუხის
ჰედერში, სადაც `<source>`-ის მნიშვნელობა ერთ-ერთია: `request-header`, `routing-override`,
`active-profile`, `auto-trigger`, `default` ან `off`.

## გაფართოებული შეკუმშვის სისტემები

ზემოთ აღწერილი 7 რეჟიმის მიღმა (წყარო ასევე იღებს `codex-responses` და `omniglyph` რეჟიმებს, რომლებსაც ეს სახელმძღვანელო არ მოიცავს), ქვემოთ მოყვანილი სექციები მოიცავს ფუნქციებს, რომლებიც მუშაობენ ამ რეჟიმებში ან მის გვერდით: ხელსაწყოს შედეგის შეკუმშვა და პროგრესული დაბერება არის აგრესიული ძრავის 1 და 2 საფეხური (აგრესიული რეჟიმი და `aggressive` ნაბიჯი stacked-checked pipeline). შეკუმშვა ამცირებს `aggressive` და `ultra` `standard` მდე ქეშირების პროვაიდერებისთვის, სანამ შეკუმშვა ჩართულია, ხოლო Caveman Output Mode და Output Styles არის სისტემის მოთხოვნის ინსტრუქციები, რომლებიც სტანდარტულად გამორთულია, რომლებიც აყალიბებენ მოდელის გამომავალს მოთხოვნის შეკუმშვის ნაცვლად.

### Cache-Aware შეკუმშვა

ზოგიერთი პროვაიდერი (როგორიცაა Anthropic სწრაფი ქეშირებით) მხარდაჭერა** სწრაფი ქეშირება** , რაც მათ საშუალებას აძლევს შეინახონ მოთხოვნის ნაწილები, შეამცირონ ხარჯები და შეყოვნება. როდესაც ქეშირება ჩართულია, აგრესიული შეკუმშვა რეალურად შეიძლება** დააზარალებს** შესრულება, რადგან ის ცვლის ქეშირებულ ტოკენებს, არღვევს ქეშს.

`cachingAware.ts` მოდული წყვეტს ამას** ქეშირების კონტექსტის აღმოჩენა** და** შეკუმშვის სტრატეგიის რეგულირება** შესაბამისად.

#### როგორ მუშაობს

1. **ქეშირების კონტექსტის აღმოჩენა** — სკანირებს მოთხოვნის სხეულს `cache_control` მარკერებისთვის
2. **ქეშირების პროვაიდერების იდენტიფიცირება** — ამოწმებს, მხარს უჭერს თუ არა სამიზნე პროვაიდერს ქეშირება
3. **სტრატეგიის მორგება** — ამცირებს `aggressive`/`ultra` `standard` მდე ქეშირების პროვაიდერებისთვის
4. **სისტემის მოთხოვნის გამოტოვება** — სისტემის მოთხოვნა ჩვეულებრივ ქეშირებულია, ასე რომ არ შეკუმშოთ ისინი

სტრატეგიის დამხმარე ასევე აბრუნებს `deterministicOnly` დროშას, მაგრამ გეგმის შემქმნელი მოიხმარს მხოლოდ სტრატეგიას — ქვემოთ არაფერი კითხულობს დროშას დღეს.

#### კოდის მაგალითი

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### როდის გამოვიყენოთ

ქეში-ცნობის შეკუმშვა არის** ყოველთვის ჩართული** — კონფიგურაცია არ არის საჭირო. ის ჩართულია, როდესაც შეკუმშვა ჩართულია და სამიზნე პროვაიდერი მხარს უჭერს სწრაფი ქეშირებას (Anthropic, OpenAI და ა.შ.); აშკარა `cache_control` მარკერები არ არის საჭირო — ქეშირების პროვაიდერი მარტო იწვევს დაქვეითებას და მარტო მარკერები არასდროს აკეთებენ (მარკერის აღმოჩენა აწვდის ქეში ტელემეტრიას და არა სტრატეგიის გადაწყვეტილებას).

OpenRouter ითვლება ქეშირების პროვაიდერად მხოლოდ `anthropic/*` მოდელებისთვის: Claude კოდის მოთხოვნა ინახავს `cache_control` წყვეტის წერტილებს (მაქსიმუმ 4) და მცველი იცავს პრეფიქსს, ხოლო ყველა სხვა OpenRouter ოჯახი (`openai/`, `google/`, `qwen/`,…) რჩება გაშიშვლებული და დაუცველი.

### პროგრესული დაბერება

გრძელი საუბრები აგროვებს ბევრ შეტყობინებას, მაგრამ უფრო ძველი მონაცვლეობა ნაკლებად აქტუალური ხდება. `progressiveAging.ts` მოდული** ამცირებს შეტყობინებებს მოხვევის მანძილით** (დისტანცია იზომება საუბრის ბოლოდან). გაგზავნილი ნაგულისხმევი (`verbatim: 2, light: 2, moderate: 3`):

- **ბოლო 2 შემობრუნება (მანძილი ≤ 2)** : სიტყვასიტყვით ინახება
- **მანძილი 3** : Caveman შეკუმშვა (შემავსებლის მოცილება)
- **მანძილი 4 +** : ასისტენტის შეტყობინებები შეჯამებულია; მომხმარებლის შეტყობინებები შემცირდა მათ პირველ სტრიქონამდე, დახურული 120 სიმბოლოთი; სხვა როლები ხელუხლებელი. სისტემის მოთხოვნილებები, უკვე დაძველებული შეტყობინებები და მომხმარებლის უახლესი შეტყობინება ყოველთვის სიტყვასიტყვით ინახება მანძილის მიუხედავად. არაფერი არ არის ამოღებული და `light` დიაპაზონი მიუწვდომელია გაგზავნილი ნაგულისხმევი (`light` უდრის `verbatim`).

#### კოდის მაგალითი

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // last 3 turns: verbatim
  light: 8, // distance <= 8: lite compression
  moderate: 20, // distance <= 20: caveman compression
  fullSummary: 5, // required by the type, not read by the banding code
  // distance > 20: summarized (assistant) / first line kept (user)
});

// saved = number of tokens saved
```

#### როდის გამოვიყენოთ

პროგრესირებადი დაბერება არის** ყოველთვის ჩართული** `aggressive` რეჟიმისთვის — ეს არის `compressAggressive()` ის მე-2 ნაბიჯი. ულტრა რეჟიმი არ მუშაობს. განსაკუთრებით ეფექტურია:

- გრძელვადიანი კოდირების სესიები
- მრავალდღიანი საუბრები
- აგენტური სამუშაო ნაკადები ხელსაწყოების მრავალი გამოძახებით

### Caveman გამომავალი რეჟიმი

Caveman გამომავალი რეჟიმი ამატებს** სისტემის სწრაფი ინსტრუქციები** რომ თავად მოდელს სთხოვს მოკლე გამომავალს — `lite` დონე ითხოვს მოკლე პასუხებს, რომლებიც ინახავს სრულ წინადადებებს, `full` სთხოვს მას "მოკლედ უპასუხოს, როგორც ჭკვიანი გამოქვაბულის კაცი", და `ultra` ითხოვს ტელეგრაფიულ გამომავალს; ინსტრუქციები მხოლოდ ითხოვენ, მათ ამის გარანტია არ შეუძლიათ. მოთხოვნები მათ იღებენ `applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) მეშვეობით: `open-sse/handlers/chatCore.ts` ჯერ წყვეტს არჩევანს back-compat shim-ით (`resolveOutputStyleSelection()` in `open-sse/services/compression/outputStyles/backCompat.ts`), რომელიც, სანამ `outputStyles` ცარიელია, ჩართული `cavemanOutputMode` ასახავს `terse-prose` გამომავალი სტილს `cavemanOutputMode.intensity` ზე (იხ. Back-compat ქვემოთ); არა ცარიელი `outputStyles` შერჩევა გამოიყენება როგორც არის, და `cavemanOutputMode.enabled` და `intensity` არ აქვთ ეფექტი, ხოლო მისი `autoClarity` გადართვა კვლავ მოქმედებს. `outputMode.ts` ინახავს ინსტრუქციის ტექსტებს (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), შიგთავსის შემოვლით და განლაგების დამხმარეს, რომელსაც იყენებს ინექცია; საკუთარ `applyCavemanOutputMode()` ინჟექტორს არ აქვს წარმოების აბონენტი.

#### როგორ მუშაობს

ეს რეჟიმი არ შეკუმშავს შეყვანას. ის ამატებს ინსტრუქციის ბლოკს სისტემის მოთხოვნას (იხ. როგორ მუშაობს ინექცია ქვემოთ), და მოთხოვნისთვის შერჩეული შეყვანის შეკუმშვის რეჟიმი კვლავ მუშაობს შემდეგ სხეულზე, რომელიც ახლა ატარებს ბლოკს. საერთო საზღვრების პუნქტის წინ, რომლითაც მთავრდება ყველა დონე, ინგლისური `full` დონე კითხულობს:

> "უპასუხეთ მოკლედ, როგორც ჭკვიანი გამოქვაბულის კაცი. ჩამოაგდეთ სტატიები (a/an/the), შემავსებელი (just/really/basically/actually/simply), სასიამოვნო ნივთები, ჰეჯირება. ფრაგმენტები OK. მოკლე სინონიმები (დიდი არა ვრცელი, შესწორება არ განხორციელდება). შეინახეთ ყველა ტექნიკური ნივთიერება, კოდი, შეცდომები, URLs, იდენტიფიკატორები ზუსტად."

ეს განსაკუთრებით კარგად მუშაობს:

- კოდის გენერირება (ტერზერის გამომავალი = ნაკლები ჟეტონები)
- სწრაფი კითხვა-პასუხი (არ არის საჭირო დეტალური განმარტებები)
- ჯგუფური დამუშავება (გამტარუნარიანობის მაქსიმალური გაზრდა)

#### როდის გამოვიყენოთ

Caveman გამომავალი რეჟიმი არის** აირჩიე** . შეკუმშვის ჩართულით (`enabled: true`, ძირითადი გადართვა შეკუმშვის პარამეტრების გვერდზე), ჩართეთ იგი `cavemanOutputMode.enabled` ით; `intensity` ირჩევს `lite`, `full` ან `ultra`:

```json
{

  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"

}
```

#### როგორ მუშაობს ინექცია

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) წყვეტს არჩევანს კატალოგთან (უცნობი ID და ლოკალური შეუსაბამობის სტილები იშლება, არასოდეს არის შეცდომა; შერჩევა, რომელიც წყვეტს სტილს, ტოვებს სხეულს უცვლელად, გამოტოვებს როგორც `no_styles`), აერთიანებს არჩეულ ინსტრუქციებს კატალოგის თანმიმდევრობით, ანიჭებს საზღვრების პუნქტს** ერთხელ** (პლუს უსაფრთხოების პუნქტი, `SAFETY_BOUNDARIES` ან მისი თარგმანი, როდესაც არჩეულია `less-code` ან `ponytail` ) და იწყებს ბლოკს ერთი იდემპოტენციის მარკერით (`[OmniRoute Output Styles]`), ასე რომ ხელახალი გამოყენება არის არა-ოპ. როდესაც ამოხსნილ ენას (იხ. ენის შერჩევა ქვემოთ) აქვს თარგმანი, ლოკალიზებული ინსტრუქცია ინექცია ინგლისურის ნაცვლად.

On a body with a non-empty `messages` array, the idempotency check runs before the content bypass: when the `[OmniRoute Output Styles]` marker is already in the top-level `system` field (a string or a content-block array) or in a system message with string content, the body is left unchanged as `already_applied` and no keyword check runs. Otherwise a content bypass (`shouldBypassCavemanOutputMode()` in `open-sse/services/compression/outputMode.ts`) checks the text of the last three messages, whatever their role, and skips the styles for the whole turn when that text matches its security, irreversible-action or clarification keywords, or an order-sensitive sequence: `first`, `then`, `after that`, `before`, `rollback` or `backup` followed within 240 characters by `delete`, `drop`, `migrate`, `deploy` or `release`. The bypass runs while the **Auto-Clarity Bypass** toggle (`cavemanOutputMode.autoClarity`, on by default) is on; turning the toggle off skips the keyword check.

როდესაც შემოვლითი გზა შემობრუნებას უშვებს, `placeSystemInstruction()` (იგივე ფაილი), რომელიც არასოდეს ქმნის ახალ `messages[0]`, ათავსებს ბლოკს პირველში, რომელსაც აღმოაჩენს:

1. წამყვანი სისტემის შეტყობინება სტრიქონის შინაარსით: ბლოკი დართულია მისი ტექსტის შემდეგ.
2. ზედა დონის `system` ველი: ბლოკი ემატება სტრიქონის ტექსტის შემდეგ, ან ემატება როგორც ახალი ტექსტური ბლოკი შინაარსის ბლოკის მასივში.
3. პირველი მოგვიანებით სისტემური შეტყობინება სტრიქონის შინაარსით: ბლოკი დართულია მისი ტექსტის შემდეგ.
4. არცერთი ზემოთ ჩამოთვლილიდან: ბლოკი გადადის ახალ სისტემურ შეტყობინებაში `messages` ს ბოლოს.

სხეულზე `messages` მასივის გარეშე (ან ცარიელი მასივის გარეშე), შიგთავსის გვერდის ავლა არ გადის და ზედა დონის `system` ველი არ არის კონსულტირებული. ბლოკი მიმაგრებულია სტრიქონის `instructions` ველის ტექსტის შემდეგ, გარდა იმ შემთხვევისა, როდესაც ეს ველი უკვე შეიცავს `[OmniRoute Output Styles]` მარკერს, ამ შემთხვევაში სხეული უცვლელი რჩება, როგორც `already_applied`. როდესაც სხეულს არ აქვს სტრიქონი `instructions` ველი, მაგრამ ატარებს `input` (სტრიქონი ან მასივი), ბლოკი ხდება `instructions`, ჩაანაცვლებს ნებისმიერ არასტრიქონულ მნიშვნელობას, რომელიც შეიცავს ამ ველს. სხეული, რომელსაც არც სიმებიანი `instructions` ველი აქვს და არც სტრიქონი ან მასივი `input` რჩება უცვლელი და გამოტოვებულია როგორც `no_messages`.

#### როგორ ჩართოთ

დაფაზე:** შეკუმშვის კონტექსტი → შეკუმშვის პარამეტრები** (`/dashboard/context/settings`), გამომავალი სტილის განყოფილება: თითო მწკრივი თითო სტილში on/off გადართვით და დონის ამომრჩევით. სტილების ინექცია ხდება მაშინ, როცა თავად შეკუმშვა ჩართულია (გვერდის ძირითადი გადართვა, `enabled`). The** ავტომატური სიცხადის შემოვლითი გზა** გადართვა არის** Caveman** გვერდი (`/dashboard/context/caveman`), თავის** გამომავალი რეჟიმი** ბარათი. პროგრამულად, შეკუმშვის კონფიგურაცია განაგრძობს არჩევანს, როგორც:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Back-compat: სანამ `outputStyles` ცარიელია, მემკვიდრეობითი `cavemanOutputMode.enabled` დაყენება რუკებს ასახავს `terse-prose` ზე `cavemanOutputMode.intensity` ზე. შემდეგ ბლოკი იწყება `[OmniRoute Output Styles]` მარკერით, სადაც მემკვიდრე `applyCavemanOutputMode()` ინჟექტორმა დაწერა `[OmniRoute Caveman Output Mode]`. მარკერის ქვემოთ ტექსტი ემთხვევა legacy ინექციას en, pt-BR, es, de, fr, it, ru, id და vi; ja და zh-ში ის ატარებს ერთ დამატებით სივრცეს საზღვრების პუნქტამდე. `terse-prose` ითარგმნება pt-BR, es, de, fr, it, ru, zh, ja, id და vi, ასე რომ მოთხოვნა, რომლის გადაჭრის ენა არის `hu` იღებს ინგლისურ ტექსტს, სადაც მოძველებული ინჟექტორმა გამოიყენა თავისი უნგრული.

გამომავალი სტილის ენის შერჩევა (`resolveOutputStyleLanguage()` in `outputStyles/apply.ts`): `languageConfig.enabled` ში ჩართულით, `autoDetect` ირჩევს მომხმარებლის უახლეს შეტყობინებას მოთხოვნის `messages` მასივში, რომელსაც აქვს ტექსტი (სტრიქონის შინაარსი ან მისი შინაარსის ნაწილები `text` ) და მასზე ამუშავებს Caveman ძრავის დეტექტორს (`detectCompressionLanguage()`). დეტექტორი აბრუნებს `zh` ტექსტს ჰანის სიმბოლოებით და კანას გარეშე; წინააღმდეგ შემთხვევაში ის აბრუნებს `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` და `id` რომელს აქვს ყველაზე მეტი მინიშნება შესატყვისი და `en` როცა არცერთი არ ემთხვევა — ტექსტს ის ვერ კლასიფიცირებს იღებს ინგლისურს, არასოდეს `defaultLanguage`, და `vi` არასოდეს არის გამოვლენილი, თუმცა სტილები გზავნის `vi`. Responses API კორპუსი ინახავს თავის მონაცვლეობას `input` ში, რომელიც არ არის შერჩეული, ამიტომ იღებს `defaultLanguage`, შემდეგ ინგლისურს. როდესაც `messages` ში მომხმარებლის არცერთ შეტყობინებას არ აქვს ტექსტი, ან `autoDetect` გამორთულია, მოქმედებს `defaultLanguage`, შემდეგ ინგლისური. თუ `languageConfig.enabled` გამორთულია, ენა არის ინგლისური — თუ მოთხოვნაზე არ ვრცელდება შეკუმშვის კომბინაცია (კომბო, რომელიც მინიჭებულია მოთხოვნის მარშრუტიზაციის კომბინაციისთვის, ან ნაგულისხმევი შეკუმშვის კომბინაცია chatCore ბრუნდება ჩაშენებული დაწყობილი მილსადენისთვის): კომბინაციის გამოყენება ჩართავს `languageConfig.enabled` ამ მოთხოვნისთვის და აყენებს `defaultLanguage` ს მნიშვნელობას. Combo-ის პაკეტები, წინააღმდეგ შემთხვევაში კომბინირებულის პირველი პაკეტი, რომელიც ნაგულისხმევად არის `en`), ხოლო შენახული `autoDetect` (ნაგულისხმევად ჩართული) კვლავ მოქმედებს. Caveman-ის შეყვანის ძრავა ირჩევს თავის წესების პაკეტის ენას სხვაგვარად — ტექსტის ნაწილზე და, ავტომატური ამოცნობის გამორთვით, დახურულია `enabledPacks` ზე.

სტილის × ენის მატრიცა მიმაგრებულია `tests/unit/compression/output-styles-i18n-matrix.test.ts` ით: კატალოგის ყველა სტილს სჭირდება ჩანაწერი ტესტის `BASELINE_LANGUAGES` ში; სტილი, რომელიც არ არის ლოკალიზებული, უნდა გამოაგზავნოს pt-BR თარგმანი (ლოკალური შეზღუდვა `terse-cjk` გათავისუფლებულია ამ წესისგან), თუ ის არ არის ჩამოთვლილი `KNOWN_ENGLISH_ONLY` ში, რომელიც შეიძლება შეიცავდეს მხოლოდ სტილებს თარგმანის გარეშე — ჩამოთვლილი სტილი, რომელსაც აქვს ნებისმიერი თარგმანი, ვერ გამოცდას; და სტილი ჩაუვარდება ტესტს, როდესაც ის კარგავს ენას, რომელიც ჩამოთვლილია მის `BASELINE_LANGUAGES` ჩანაწერში. სტილის დასამატებლად იხილეთ [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### ინსტრუმენტის შედეგის შეკუმშვა

`compressToolResult()` `open-sse/services/compression/toolResultCompressor.ts` ში შეკუმშავს ხელსაწყო-შედეგის ტექსტს** 5 სტრატეგია** . ის ცდის მათ ამ თანმიმდევრობით და პირველი ჩართული სტრატეგია, რომლის შემოწმებაც შეესაბამება შინაარსს, წყვეტს შედეგს:

1. **`fileContent`**: content of 3 or more lines in which at least one line, ignoring leading indentation, starts with `import `, `export `, `function `, `class `, `const `, `let `, `var ` or `return ` (the keyword plus a space), or with `if`, `for` or `while` followed by `(` or ` (`, keeps its first 20 and last 5 lines, with the elided middle marked.
2. **`grepSearch`** : შინაარსი `<path>:<digits>:` ფორმის მინიმუმ ერთი სტრიქონით, სადაც ტექსტს პირველ ორწერტილამდე არ აქვს უფსკრული, ინახავს მხოლოდ იმ ხაზებს, მაქსიმუმ 30, რასაც მოჰყვება შემდგომი შესატყვისების რაოდენობა და შესატყვისი ფაილების სია; ყოველი მეორე ხაზი გამორთულია. ერთი ასეთი ხაზი საკმარისია სტრატეგიის გასააქტიურებლად, ასე რომ, ჟურნალის ხაზი, რომელიც იწყება დროის ნიშნულით, როგორიცაა `12:30:45` ასევე ითვლება.
3. **`shellOutput`** : გამომავალი, რომელიც შეიცავს ANSI CSI თანმიმდევრობას (`ESC[` შემდეგ ციფრებს ან მძიმით, შემდეგ ასოს, როგორც ფერთა კოდებში) ან `$` რასაც მოჰყვება ცარიელი სივრცე ტექსტის ნებისმიერ ადგილას, კარგავს ამ თანმიმდევრობებს (სხვა გაქცევები, როგორიცაა `ESC[?25l` ან OSC ფანჯრის სათაურის თანმიმდევრობა, ინახება) და ინახავს ხაზების გამეორებას ბოლო 5-ით. იმის გამო, რომ ეს შემოწმება გადის `json` და `errorMessage` მდე, JSON ან შეცდომის გამომავალი, რომელიც შეიცავს ასეთ `$` არასოდეს აღწევს მათ, სანამ `shellOutput` ჩართულია.
4. **`json`** : JSON 2000 სიმბოლოზე მეტი დატვირთვა, რომელიც იწყება `{` ით ან `[` (არასავალდებულო უფსკრულის შემდეგ) და აანალიზებს შეჯამებულია: 7-ზე მეტი ერთეულის მასივი ინახავს პირველ 5 და ბოლო 2 ერთეულს და მის საერთო რაოდენობას, ხოლო ობიექტი ინახავს პირველ 20 კლავიშს, თითოეული ჩადგმული ობიექტის ან zray-ის სიგრძით ჩანაცვლებულია N-ით. `{…N keys}` `_remaining_<N>_keys`, რომელიც ითვლის კლავიშებს, რომლებიც ჩამოვიდა პირველ 20-ს. სკალარული მნიშვნელობები კოპირდება მთლიანად, ასე რომ, 20 კლავიშის ან ნაკლები მნიშვნელობის მქონე ობიექტი მხოლოდ ხელახლა ჩაღრმავდება — მინიმირებული იძენს სიმბოლოებს და რჩება უცვლელი.
5. **`errorMessage`** : გამომავალი, რომელიც შეიცავს, სადმე და ნებისმიერ ასოში, `error:`, `error ` (სიტყვა, რომელსაც მოსდევს ინტერვალი, როგორც `no error found`), `[error]`, `exception:`, `exception `, `[exception]` ან `traceback` ინარჩუნებს თავის პირველ ხაზს, შემდეგ 10 სტრიქონს და ბოლო 3, `… [N frames elided] …` მარკერით მათ შორის ხაზების ნაცვლად. მარკერი ჩნდება მხოლოდ მაშინ, როდესაც 13 სტრიქონზე მეტი მიჰყვება პირველ ხაზს, ამიტომ 14 ან ნაკლები სტრიქონის შეცდომის გამომავალი არ შემცირდება (12 ან 13 სტრიქონზე ბოლო 3 განმეორებითი ხაზი უკვე დაცულია).

მას შემდეგ, რაც სტრატეგია ემთხვევა, თუნდაც ის, რომელიც არაფერს ზოგავს, მოგვიანებით სტრატეგიები არ ცდება. როდესაც შესატყვისი სტრატეგია არ ინახავს სავარაუდო ნიშნებს (სიგრძე ÷ 4, დამრგვალებული) — მაგალითად, კოდის მსგავსი ფაილი 25 სტრიქონისგან ან ნაკლები, ან JSON მასივი 2000 სიმბოლოზე მეტი 7 ელემენტით ან — ნაკლები, აგრესიული ძრავა ინახავს ხელსაწყოს თავდაპირველ შედეგს: ორივე აბონენტი (`compressAggressive()` და `compressAnthropicToolResultBlock()` არის ორიგინალი, როდესაც ჯერ კიდევ არ არის, შეინახეთ `saved` ან `compressToolResult()` ქვემოთ). აბრუნებს ამ სტრატეგიის გამომუშავებას. ინსტრუმენტის შედეგის ნაბიჯი არ არის ბოლო სიტყვა: ძრავის სარეზერვო შეჯამებელს შეუძლია კვლავ შეამციროს `tool` ან `function` შეტყობინება 8,192 სიმბოლოზე მეტი (`maxTokensPerMessage`, 2,048, 4-ჯერ).

#### როდის გამოვიყენოთ

ხელსაწყოს შედეგის შეკუმშვა არის აგრესიული ძრავის 1 ნაბიჯი (`compressAggressive()` in `open-sse/services/compression/aggressive.ts`), ამიტომ ის მუშაობს აგრესიულ რეჟიმში და დაწყობილი მილსადენის `aggressive` საფეხურზე. იგი შეკუმშავს OpenAI-ის ფორმის `tool` და `function` შეტყობინებებს და ტექსტს Anthropic `tool_result` ბლოკებში. თითოეულ სტრატეგიას აქვს საკუთარი გადამრთველი `aggressive.toolStrategies` ქვეშ, ყველაფერი ჩართულია ნაგულისხმევად. დაფაზე გადამრთველები არის Caveman-ის გვერდზე** გაფართოებული** ნახვა, როდესაც შეკუმშვა ჩართულია და ნაგულისხმევი რეჟიმი არის აგრესიული.

### დაწყობილი მილსადენი

დაწყობილი რეჟიმი მუშაობს** რამდენიმე ძრავა თანმიმდევრობით** — როგორც წესი, ჯერ RTK (60-90% დანაზოგი ხელსაწყოს გამომუშავებაზე), შემდეგ Caveman დანარჩენ ტექსტზე (~ 46% შეყვანის დანაზოგი). შედგენილი, ეს არის** 78-95% დასაშვები დიაპაზონი** (იხ. ზემოთ ნაკადის შემნახველი მათემატიკა): `1 - (1 - 0.60..0.90) × (1 - 0.46)` საშუალოდ ≈ 89%.

#### როგორ მუშაობს

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 108 tokens
  → Output (108 tokens, ~89% savings)
```

#### როდის გამოვიყენოთ

გამოიყენეთ დაწყობის რეჟიმი:

- ინსტრუმენტებით მძიმე სამუშაო ნაკადები (აგენტიკური კოდირება, კვლევა)
- ხარჯებისადმი მგრძნობიარე სერიული დამუშავება
- როცა გჭირდება მაქსიმალური სიმბოლური დანაზოგი

დაწყობილი მილსადენები კონფიგურირებულია გლობალური `stackedPipeline` შეკუმშვის პარამეტრით, ან დასახელებული შეკუმშვის კომბინაციის მეშვეობით, რომელიც მინიჭებულია მარშრუტიზაციის კომბინაციით (იხ. Per-Combo Override ზემოთ) — და არა ავტომატური კომბინირებული `modePack` (ეს ველი მხოლოდ ხელახლა აწონის ავტომატური კომბინირებული მოდელის შერჩევას და `stacked` არ არის სწორი პაკეტის სახელი).

## შეკუმშვის კომბინაციების გადაფარვები

სხვადასხვა გამოყენების შემთხვევისთვის ქცევის ზუსტად მოსარგებად, შეგიძლიათ შეკუმშვის გლობალური რეჟიმი **თითოეული კომბინაციისთვის** გადააფაროთ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ეს სასარგებლოა შემდეგ შემთხვევებში:

- **პროგრამირების კომბინაციები**: ხანგრძლივი სესიებისთვის გამოიყენეთ `aggressive` რეჟიმი
- **სწრაფი კითხვა-პასუხის კომბინაციები**: სწრაფი პასუხებისთვის გამოიყენეთ `lite` რეჟიმი
- **ინსტრუმენტებზე ძლიერ დამოკიდებული კომბინაციები**: მაქსიმალური ეკონომიისთვის გამოიყენეთ `stacked` რეჟიმი
- **საწარმოო კომბინაციები**: ქეშირების პროვაიდერებისთვის გადაფარვა გამორთული დატოვეთ — მუდმივად ჩართული, ქეშის გათვალისწინებით შესრულებული კორექტირება `aggressive`/`ultra` რეჟიმებს ავტომატურად `standard` რეჟიმამდე აქვეითებს
  (ასარჩევი `cache-aware` რეჟიმი არ არსებობს)
