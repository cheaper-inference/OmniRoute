## npm Trusted Publishing (ნაგულისხმევი v3.8.51-დან) — მოთხოვნის შემთხვევაში ეტაპობრივი, სარეზერვოდ პირდაპირი

`npm-publish.yml` ნაგულისხმევად აქვეყნებს **npm Trusted Publishing-ის (OIDC)** მეშვეობით:
`stage-npm` დავალება (github-hosted) GitHub-ის id-token-ს ამ კონკრეტული გაშვებისთვის
ხანმოკლე npm ავტორიზაციის მონაცემებზე ცვლის — რეპოზიტორიის საიდუმლოებებში აღარ არის
ხანგრძლივად მოქმედი npm ტოკენი, არ ჩნდება 2FA მოთხოვნა და თან ერთვის წარმომავლობის დამადასტურებელი ინფორმაცია.
ეს არის შემოვლითი გზა, რომელსაც npm ახლა უჭერს მხარს, რადგან 2FA-ს გამომტოვებელი ტოკენები
ხმარებიდან ამოიღება; იგი აღადგენს სრულად ავტომატურ პროცესს, რომელიც პროექტს v3.8.48-მდე
ჰქონდა, ამავდროულად კი ინარჩუნებს WS1.3 გარანტიას (გაჟონილი ტოკენი დამოუკიდებლად ვერ გამოაქვეყნებს — ტოკენი საერთოდ არ არსებობს).

**ერთჯერადი დაყენება (მფლობელი):** npmjs.com → პაკეტი `omniroute` → Settings → _Trusted
Publisher_ → GitHub: მფლობელი `diegosouzapw`, რეპოზიტორია `OmniRoute`, სამუშაო პროცესი `npm-publish.yml`
(გარემო: არცერთი). მის შექმნამდე ავტომატური ნაბიჯი დასრულდება `ENEEDAUTH` შეცდომით:
ხელახლა გაუშვით `publish_mode=staged`-ით (ქვემოთ) ან `direct`-ით.

### ეტაპობრივი გამოქვეყნება (მოთხოვნის შემთხვევაში — `publish_mode=staged`)

npm-publish სამუშაო პროცესი პირდაპირ აღარ აქვეყნებს: ის ჩატვირთავს შეფუთულ tarball-ს
(`check:pack-boot`) და შემდეგ გაუშვებს `npm stage publish`-ს — ზუსტად ეს ბაიტები განთავსდება
რეესტრში, თუმცა მფლობელის დამტკიცებამდე **მათი დაყენება შეუძლებელია**. ადამიანის მიერ გასავლელი
2FA ბარიერი მტკიცებულების მიღების შემდეგ გადავიდა და არა მის წინ.

**მფლობელის პროცესი სამუშაო პროცესის წარმატებით დასრულების შემდეგ:**

1. `npm stage list omniroute` — იპოვეთ ეტაპის id (ის ასევე სამუშაო პროცესის შეჯამებაში იბეჭდება).
2. შეამოწმეთ ეტაპობრივად განთავსებული ბაიტები (რეკომენდებულია): `npm stage download <id>`, შემდეგ
   ჩამოტვირთული tarball დროებით პრეფიქსში დააყენეთ და ჩატვირთეთ (`npm run check:pack-boot`
   CI-ში იმავე შეფუთვა→დაყენება→ჩატვირთვის შედეგს ავტომატიზებს).
3. `npm stage approve <id>` — 2FA მოთხოვნა თავად გამოქვეყნებაა. `npm stage reject <id>` უარყოფს მას.
4. გამოქვეყნების შემდგომი დამცავი მექანიზმი: გამოქვეყნების შემდგომი შემმოწმებელი (v3.8.49 გეგმის WS1.4)
   სუფთა კონტეინერში საჯარო რეესტრიდან აყენებს გამოქვეყნებულ ვერსიას და ჩატვირთავს მას.

**საგანგებო სარეზერვო გზა:** `workflow_dispatch` პარამეტრით `publish_mode=direct` აღადგენს
ძველ, დაუყოვნებელ `npm publish`-ს (გამოიყენეთ მხოლოდ მაშინ, თუ თავად ეტაპობრივი გამოქვეყნება
არასწორად მუშაობს; დააფიქსირეთ მიზეზი).

**ერთჯერადი გამკაცრება (მფლობელი, npmjs.com):** `omniroute`-ისთვის Trusted Publisher
მხოლოდ ეტაპობრივ რეჟიმში დააკონფიგურირეთ, რათა გაჟონილმა ხანგრძლივად მოქმედმა ტოკენმა
ვერსად შეძლოს პირდაპირ `npm publish`-ის შესრულება — CI-ს მხოლოდ ეტაპობრივად განთავსება
შეუძლია; გამოშვება მხოლოდ მფლობელის 2FA-ს შეუძლია.

**დაზიანებული არტეფაქტის სამოქმედო გეგმა (უცვლელი):** ნაგულისხმევი დაუყოვნებელი მოქმედებაა
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` (წუთებში სრულდება და შექცევადია);
`npm unpublish` გამოიყენეთ მხოლოდ 72-საათიან/დამოკიდებულებების არმქონე ფანჯარაში და არასდროს
პირველ ნაბიჯად. Docker: არასდროს გადაწეროთ ვერსიის ტეგი — უკან დაბრუნება ნიშნავს `latest`-ის
ბოლო გამართულ დაიჯესტზე გადამისამართებას.

**Docker Hub-ის `latest` (სავალდებულოა ყოველი სტაბილური SemVer გამოქვეყნებისას):**
`docker-publish` სამუშაო პროცესმა უნდა მიანიჭოს **ორივე** ტეგი, `X.Y.Z` და, როდესაც
`should-promote-latest.sh` დაადასტურებს, რომ ეს უმაღლესი სტაბილური SemVer-ია, `:latest`,
**ერთი და იმავე დაიჯესტით**. დავალების შემდეგ: Hub-ზე `latest`-ის დაიჯესტი ახალი
SemVer-ის დაიჯესტის ტოლი უნდა იყოს და `last_updated` უნდა განახლდეს. არ დატოვოთ `:latest`
ძველ აგებაზე, როცა გამოშვების შენიშვებში აღწერილია შესწორებები, რომლებიც მხოლოდ git-ში
არსებობს. Compose-ის სწრაფი დაწყების მაგალითები `:latest`-ს იყენებს; GitOps-მა კვლავ
`X.Y.Z` უნდა დააფიქსიროს. იხილეთ [Docker-ის გამოშვების არხები](../guides/DOCKER_GUIDE.md#release-channels) და #10317.

## Hotfix-ის სწრაფი ზოლი (ჭდე `hotfix`)

PR, რომელსაც აქვს ჭდე `hotfix`, გამოტოვებს CI-ის მძიმე მატრიცას (9-შარდიანი E2E, დაფარვის ratchet,
quality-gate, quality-extended) და ინარჩუნებს სწრაფ, მაღალი სიგნალის მქონე შემოწმებებს: build,
unit-შარდები, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
და tarball-ის ჩატვირთვის smoke-ტესტი (`check:pack-boot`). მიზანი: ~33 წუთის ნაცვლად მწვანე სტატუსი ≤15 წუთში.

**შესვლის პოლიტიკა — ოთხივე პირობა სავალდებულოა (Chromium/VS Code/Node-ის საგანგებო ზოლების მოდელის მიხედვით):**

1. **სიმძიმე**: production გატეხილია — გამოქვეყნებული არტეფაქტი ჩატვირთვისას ითიშება /
   უსაფრთხოების შესწორებაა საჭირო / რელიზის ყველა მომხმარებელი დაზარალებულია. „მნიშვნელოვანი“ არ ნიშნავს „გატეხილს“.
2. **უფლებამოსილება**: `hotfix` ჭდეს მხოლოდ რეპოზიტორიის მფლობელი ანიჭებს. ჭდე თავად არის
   დამტკიცება — campaign PR-ზე მისი თვითნებურად გამოყენება დაუშვებელია.
3. **მტკიცებულება**: PR-ის აღწერაში მოცემულია ბმული წინა სრულად მწვანე მძიმე გაშვებაზე (პაკეტზე, რომელსაც
   გამოტოვებული დავალებები ხელახლა გადაამოწმებდა), ასევე შესწორების საკუთარ ტესტზე, რომელიც ჯერ ჩავარდა, შემდეგ კი გაიარა.
4. **მოცულობა**: მხოლოდ cherry-pick — მინიმალური შესწორება, refactor-ების და თანმხლები ცვლილებების გარეშე.

(რელიზის უწყვეტი მწვანე სტატუსი) — ზოლი გამოტოვებს მხოლოდ ლოდინს და არასოდეს ვალიდაციას.

### აშენების განლაგება

საცავი იყენებს სამ განსხვავებულ გამომავალ დირექტორიას — არასოდეს აურიეთ ისინი:

| დირექტორია | მიზანი                                                             | თვალყური ადევნეთ?   |
| ---------- | ------------------------------------------------------------------ | ------------------- |
| `src/`     | აპლიკაციის წყარო (TypeScript / TSX)                                | დიახ                |
| `.build/`  | შუალედური პროდუქტების შექმნა — `next build` გამომავალი (`distDir`) | არა (იგნორირებულია) |
| `dist/`    | მიწოდებადი npm პაკეტი — აწყობილი `assembleStandalone` მიერ         | არა (იგნორირებულია) |

> **ოპერატორის შენიშვნა:** დისტანციური VPS სურათების დირექტორია რჩება `/usr/lib/node_modules/omniroute/app/`. მხოლოდ** რეპოში** build output გადავიდა (`app/` → `dist/`). უნარების დანერგვა rsync `dist/` შინაარსი დისტანციურ `app/` dir — არ არის საჭირო VPS ბილიკის ცვლილებები.

**ერთჯერადი ნაკადი:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

შეასრულეთ NOT გაუშვით `npm run build` რასაც მოჰყვება ცალკე `npm run build:cli` — განსათავსებლად გამოიყენეთ `npm run build:release`, რომელიც ასრულებს + sentinel-ის სუფთა აღდგენას ერთი ბრძანებით.

ჩანერგილ მშობელზე უარყოფს, ამიტომ განშტოება სრული clone-იდან შეასრულეთ ან ჯერ
`git fetch --unshallow origin` გაუშვით — წინა ჭდე არსებობს, `package.json`-ში სამიზნე ვერსიაა,

`Release branch not green` issue არ არის — არარსებული განშტოება აბრუნებს `?` უცნობს და არასოდეს
მწვანეს — Mergify-ის `release` რიგი კონფიგურირებულია (G11: `queue_rules`, `checks_timeout`,

რომელი ტრიგერები და `if:` პირობები ხდება ჭეშმარიტი (და რომელი რჩება რეპოზიტორიის ცვლადით
შეზღუდული ან კანონიკურ რეპოზიტორიაზე დაფიქსირებული), მოსალოდნელ dist-tag-ებს (`latest` → 3.9.0,
`next` და `nightly` ცარიელია) და უკან დაბრუნებას. გასვლის კოდი `0` = `RESULT: READY`, `1` =
დაბლოკვის გამომწვევი წინაპირობა ვერ შესრულდა (`✗`), `2` = გამოყენების შეცდომა.

### PR-ის წინასწარი გადახედვის არტეფაქტი (ერთხელ ააწყვეთ, იგივე ბაიტები დაწინაურეთ)

`.github/workflows/preview-artifact.yml` PR-ის head-იდან ერთ production tarball-ს აწყობს და

### განშტოება (3.9.0, GO-ს შემდეგ)

1. GO დაფიქსირებულია [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md)-ში.

3. `origin`-ზე განშტოებები ხელით შექმენით, საცდელი გაშვების მიერ დაბეჭდილი ბრძანებებით —
   სკრიპტი `origin`-ზე push-ს უარყოფს. განხილული develop commit-ის ხელახლა გამოსაყენებლად,
   ჯერ 3.9.0-ის წვეროზე `--execute` რეპეტიცია თქვენი fork-ის მიმართ გაუშვით; ის ორივე SHA-ს

4. დაიცავით `stable/v3` და `develop` (წესების ნაკრებები + შერწყმის რიგი) პირველი PR-ის მიღებამდე.

   push), `validate-stable-pr.yml` (`stable/v3`-ისთვის განკუთვნილი PR-ები) და `nightly-v4-build.yml`

   forward-port PR-ებზე); ღამის გამოქვეყნება გამორთული დარჩება, სანამ მფლობელი საცავის
   ცვლადს `vars.NIGHTLY_PUBLISH` მნიშვნელობად `true`-ს არ მიანიჭებს და npm Trusted Publishing
   არ მიიღებს `nightly-v4-build.yml`-ს. არხის განსაზღვრას ასრულებს `scripts/release/dist-tag.mjs` — იგივე
   განმსაზღვრელი, რომელსაც `npm-publish.yml` იყენებს.
6. გადაამოწმეთ არხები: `npm view omniroute dist-tags --json` აჩვენებს, რომ `latest` = 3.9.0, ხოლო
   `next` / `nightly` არ არსებობს, სანამ v4 არ გამოქვეყნდება.
7. საჭიროების შემთხვევაში, უკან დასაბრუნებლად გამოიყენეთ: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
