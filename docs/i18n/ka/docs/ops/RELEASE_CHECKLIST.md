## npm Trusted Publishing (ნაგულისხმევი v3.8.51-დან) — დადგმული მოთხოვნით, პირდაპირ, როგორც სარეზერვო

`npm-publish.yml` აქვეყნებს მეშვეობით** npm Trusted Publishing (OIDC)** ნაგულისხმევად: `stage-npm` სამუშაო (github-hosted) ცვლის GitHub ის id-token-ს ხანმოკლე npm სერთიფიკატზე, რომ გაშვებული — არ არის გრძელვადიანი npm ნიშანი საცავის საიდუმლოებებში, არ არის 2FA მოთხოვნა, თანდართული წარმოშობა. ეს არის შემოვლითი npm სანქციები ახლა, როდესაც ტოკენები, რომლებიც გამოტოვებენ 2FA-ს, ამოღებულია; ის აღადგენს სრულად ავტომატურ ნაკადს, რომელსაც პროექტი ჰქონდა v3.8.48-მდე, ხოლო ინარჩუნებს WS1.3 გარანტიას (გაჟონულ ჟეტონს არ შეუძლია გამოაქვეყნოს მარტო — არ არსებობს ჟეტონი).

**ერთჯერადი დაყენება (მფლობელი):** npmjs.com → პაკეტი `omniroute` → პარამეტრები → _Trusted Publisher_ → GitHub: მფლობელი `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml` (გარემო: არ არის). სანამ ეს არ არსებობს, ავტომატური ნაბიჯი ვერ ხერხდება `ENEEDAUTH` ით: ხელახლა გაგზავნა `publish_mode=staged` ით (ქვემოთ) ან `direct`.

### ეტაპობრივი გამოცემა (მოთხოვნით — `publish_mode=staged`)

npm-publish სამუშაო პროცესი პირდაპირ აღარ ქვეყნდება: ის ჩატვირთავს შეფუთულ tarball-ს (`check:pack-boot`) და შემდეგ აწარმოებს `npm stage publish` — ზუსტი ბაიტები გაჩერებულია რეესტრში,** არ არის დაინსტალირებული** სანამ მფლობელი არ დაამტკიცებს. ადამიანის 2FA კარიბჭე გადავიდა AFTER მტკიცებულებაზე და არა მის წინ.

**სამუშაო პროცესის შემდეგ მფლობელის ნაკადი მწვანე გახდება:**

1. `npm stage list omniroute` — იპოვნეთ ეტაპის ID (ასევე დაბეჭდილი სამუშაო პროცესის შეჯამებაში).
2. გადაამოწმეთ დადგმული ბაიტები (რეკომენდირებულია): `npm stage download <id>`, შემდეგ დააინსტალირეთ გადმოწერილი tarball ტემპ პრეფიქსში და ჩატვირთეთ (`npm run check:pack-boot` ავტომატიზირებს იმავე პაკეტს → დააინსტალირე → ჩატვირთვის ვერდიქტი CI ში).
3. `npm stage approve <id>` — 2FA მოთხოვნა IS გამოქვეყნება. `npm stage reject <id>` უგულებელყოფს.
4. Post-publish net: post-publish verfier (WS1.4 v3.8.49 plan) აყენებს გამოქვეყნებულ ვერსიას საჯარო რეესტრიდან სუფთა კონტეინერში და ჩატვირთავს მას.

**გადაუდებელი სარეზერვო:** `workflow_dispatch` `publish_mode=direct` ით აღადგენს მემკვიდრეობას უშუალო `npm publish` (გამოიყენეთ მხოლოდ იმ შემთხვევაში, თუ დადგმა არასწორად იქცევა; ჩაწერეთ რატომ).

**ერთჯერადი გამკვრივება (მფლობელი, npmjs.com):** დააკონფიგურირეთ Trusted Publisher `omniroute` სთვის მხოლოდ ეტაპის რეჟიმში, რათა გაჟონულმა ხანგრძლივმა ჟეტონმა არ შეძლოს `npm publish` პირდაპირ ნებისმიერი ადგილიდან — CI შეუძლია მხოლოდ დადგმა; მხოლოდ მფლობელის 2FA რელიზები.

**გატეხილი არტეფაქტის სათამაშო წიგნი (უცვლელი):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"` როგორც ნაგულისხმევი რეფლექსი (წუთები, შექცევადი); `npm unpublish` მხოლოდ 72h/no-dependents ფანჯრის შიგნით და არასდროს როგორც პირველი ნაბიჯი. Docker: არასოდეს გადაწეროთ ვერსიის — `latest`

**Docker Hub `latest` (აუცილებელია ყოველი სტაბილური SemVer გამოქვეყნებისთვის):** `docker-publish` სამუშაო ნაკადი უნდა მონიშნოს** ორივე** `X.Y.Z` და, როდესაც `should-promote-latest.sh` ეთანხმება, ეს არის უმაღლესი სტაბილური SemVer, `:latest` ერთად** იგივე დაიჯესტი** . სამუშაოს შემდეგ: Hub `latest` დაიჯესტი უდრის ახალ SemVer დაიჯესტს და `last_updated` გადატანილს. არ დატოვოთ `:latest` ძველ ნაგებობაზე, სანამ გამოშვების შენიშვნები საუბრობენ შესწორებებზე, რომლებიც მხოლოდ git-ზე არსებობს. სწრაფი სტარტების შედგენა `:latest` გამოყენებით; GitOps უნდა გააგრძელოს `X.Y.Z` დამაგრება. იხილეთ [Docker გამოშვების არხები](../guides/DOCKER_GUIDE.md#release-channels) და #10317.

**Docker Hub ორგანიზაციის საცავი (`cheaperinference/omniroute`):** Docker Hub-ს არ შეუძლია გადაიტანოს საცავი სახელთა სივრცეებს შორის, ამიტომ `diegosouzapw/omniroute` ინახავს თავის მოზიდვის ისტორიას და ყოველ გამოშვებას, ხოლო `mirror-org-dockerhub` სამუშაო `docker-publish` აკოპირებს თითოეულ გამოშვებულ ვერსიას (და `:latest` დაწინაურებისას) `ghcr.io/cheaper-inference/omniroute` დან ორგანიზაციის საცავში. მას სჭირდება `DOCKERHUB_ORG_USERNAME` / `DOCKERHUB_ORG_TOKEN` საიდუმლოებები; მათ გარეშე სამუშაო რჩება მწვანე გაფრთხილებით "Docker Hub org mirror skipped" და სხვა რეესტრები აქვეყნებენ ჩვეულებრივად. გამოქვეყნებული ვერსიის იქ მოგვიანებით გამოსაქვეყნებლად, გაუშვით** ქმედებები → ასახეთ Docker გამოსახულება Docker Hub org → სამუშაო ნაკადის გაშვება** `version=X.Y.Z` ით (და `promote_latest` უმაღლესი სტაბილური ვერსიისთვის): ის აკოპირებს არსებულ სურათებს, რეკონსტრუქციის გარეშე.

## Hotfix-ის სწრაფი ზოლი (ჭდე `hotfix`)

PR, რომელსაც აქვს ჭდე `hotfix`, გამოტოვებს CI-ის მძიმე მატრიცას (9-შარდიანი E2E, დაფარვის ratchet,
quality-gate, quality-extended) და ინარჩუნებს სწრაფ, მაღალი სიგნალის მქონე შემოწმებებს: build,
unit-შარდები, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
და tarball-ის ჩატვირთვის smoke-ტესტი (`check:pack-boot`). მიზანი: ~33 წუთის ნაცვლად მწვანე სტატუსი ≤15 წუთში.

**შესვლის პოლიტიკა — ოთხივე პირობა სავალდებულოა (Chromium/VS Code/Node-ის საგანგებო ზოლების მოდელის მიხედვით):**

1. **სიმძიმე**: production გატეხილია — გამოქვეყნებული არტეფაქტი ჩატვირთვისას ითიშება /
   უსაფრთხოების შესწორებაა საჭირო / რელიზის ყველა მომხმარებელი დაზარალებულია. „მნიშვნელოვანი“ არ ნიშნავს „გატეხილს“.
2. **უფლებამოსილება**: `hotfix` ჭდეს მხოლოდ რეპოზიტორიის მფლობელი ანიჭებს. ჭდე თავად არის
   დამტკიცება — campaign PR-ზე მისი თვითნებურად გამოყენება დაუშვებელია.
3. **მტკიცებულება**: PR-ის აღწერაში მოცემულია ბმული წინა სრულად მწვანე მძიმე გაშვებაზე (პაკეტზე, რომელსაც
   გამოტოვებული დავალებები ხელახლა გადაამოწმებდა), ასევე შესწორების საკუთარ ტესტზე, რომელიც ჯერ ჩავარდა, შემდეგ კი გაიარა.
4. **მოცულობა**: მხოლოდ cherry-pick — მინიმალური შესწორება, refactor-ების და თანმხლები ცვლილებების გარეშე.

გამოტოვებული დაფარვის/ratchet-ის ზედაპირი ხელახლა მოწმდება release-ბრენჩზე შემდეგი სრული გაშვებით

### აშენების განლაგება

საცავი იყენებს სამ განსხვავებულ გამომავალ დირექტორიას — არასოდეს აურიეთ ისინი:

| დირექტორია | მიზანი                                                             | თვალყური ადევნეთ?   |
| ---------- | ------------------------------------------------------------------ | ------------------- |
| `src/`     | აპლიკაციის წყარო (TypeScript / TSX)                                | დიახ                |
| `.build/`  | შუალედური პროდუქტების შექმნა — `next build` გამომავალი (`distDir`) | არა (იგნორირებულია) |
| `dist/`    | მიწოდებადი npm პაკეტი — აწყობილი `assembleStandalone` მიერ         | არა (იგნორირებულია) |

> **ოპერატორის შენიშვნა:** დისტანციური VPS სურათების დირექტორია რჩება `/usr/lib/node_modules/omniroute/app/`. მხოლოდ** რეპოში** build output გადავიდა (`app/` → `dist/`). უნარების დანერგვა rsync `dist/` შინაარსი დისტანციურ `app/` dir — არ არის საჭირო VPS ბილიკის ცვლილებები.

**ერთჯერადი ნაკადი:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

შეასრულეთ NOT გაუშვით `npm run build` რასაც მოჰყვება ცალკე `npm run build:cli` — განსათავსებლად გამოიყენეთ `npm run build:release`, რომელიც ასრულებს + sentinel-ის სუფთა აღდგენას ერთი ბრძანებით.

### მშრალი გაშვება (მხოლოდ წაკითხვადი, უსაფრთხო ნებისმიერ დროს)

```bash
npm run release:dry-run-lts-cut                       # the real cut: 3.9.0 from HEAD, previous tag v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # pin the source commit
```

`scripts/release/dry-run-lts-cut.mjs` executes nothing: it reads git and `gh` and prints the whole sequence — preconditions (source resolves, the source repository has full history — a shallow clone cannot push `stable/v3`, the receiving side rejects the pack at the first grafted parent, so cut from a full clone or `git fetch --unshallow origin` first — previous tag exists, `package.json` is the target version, a `release-freeze` issue is open, no open `Release branch not green` issue on an existing release branch — a branch that does not exist reports `?` unknown, never green — omni-queue lands the release PRs (G11: `config/merge-queue/config.json` valid, its `bases` manage the release branch, `mode` `live`, its label exists), the `release/*` ruleset still blocks deletion and force-push, and `stable/v3` and `develop` do not exist yet), the two branch steps, which dormant-workflow triggers and `if:` conditions turn true (and which stay gated by a repository variable or pinned to the canonical repository), the expected dist-tags (`latest` → 3.9.0, `next` and `nightly` empty) and the rollback. Exit `0` = `RESULT: READY`, `1` = a blocking precondition failed (`✗`), `2` = usage error. `--advisory <id,...>` downgrades a check to a warning (`!`) without hiding it.

გაუშვით რეალური ჭრის მშრალი გაშვება, სანამ 3.9.0 გამოშვების გაყინვა ჯერ კიდევ ღიაა — ტოტები იქმნება ტეგის შემდეგ და სანამ ფაზა 12c არ მოხსნის გაყინვას.
