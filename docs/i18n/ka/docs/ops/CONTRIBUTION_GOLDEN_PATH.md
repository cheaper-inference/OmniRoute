გამოიყენეთ ეს სახელმძღვანელო pull request-ისთვის უმცირესი საიმედო დეველოპმენტის ციკლის ასარჩევად. ის არ
ანაცვლებს ქვემოთ ბმულებით მითითებულ კონკრეტული სფეროს არქიტექტურისა და უსაფრთხოების დოკუმენტებს; ის თითოეულ გავრცელებულ
ცვლილების ტიპს აკავშირებს მის კონტრაქტებთან, მიზნობრივ შემოწმებებთან და CI დაფარვასთან.

## გზა, რომელსაც ყოველი ცვლილება გადის

1. **რედაქტირებამდე აირჩიეთ საბაზო branch.** იპოვეთ ყველაზე მაღალი აქტიური `release/v*` branch და შექმენით ახალი branch
   მისი ბოლო commit-იდან. სამიზნედ აირჩიეთ ეს branch და არა `main`. თუ გამოცემის გაყინვა აქტიურია, სამიზნედ არ აირჩიოთ გაყინული
   branch; გამოიყენეთ შემდეგი აქტიური ციკლი, რომელიც აღწერილია
   [Branching & Release Model](BRANCHING_MODEL.md)-ში.
2. **დაასახელეთ კონტრაქტები.** განსაზღვრეთ ყველა კატალოგი, სქემა, გენერირებული არტეფაქტი, საჯარო API ან მომხმარებლის
   ინტერფეისი, რომელზეც ცვლილება მოქმედებს. ქვემოთ მოცემული ცხრილი მინიმალურ საწყის ნაკრებს განსაზღვრავს.
3. **დაწერეთ ან განაახლეთ მიზნობრივი ტესტები.** `src/`, `open-sse/`, `electron/` ან
   `bin/`-ში შეტანილი production ცვლილებები იმავე PR-ში ავტომატიზებულ ტესტს საჭიროებს. გაუშვით უმცირესი ტესტ-ფაილები, რომლებიც
   ქცევას ადასტურებს, შემდეგ კი ჩამოთვლილი მიზნობრივი შემოწმებები.
4. **ფართო მატრიცის გაშვება CI-ს მიანდეთ.** სრული unit-შარდები, Vitest, დაფარვის ზღვრის კონტროლი და
   production build PR-ზე გაეშვება. ფართო ნაკრები ლოკალურად გაუშვით მხოლოდ მაშინ, როდესაც მიზნობრივი შემოწმების ჩავარდნა
   უფრო ფართო გავლენაზე მიუთითებს ან ცვლილება რამდენიმე ქვესისტემას მოიცავს.
5. **რევიუმდე მოახდინეთ შეჯერება.** ჩამოტვირთეთ აქტიური საბაზო branch, შეამოწმეთ მისი ახალი commit-ები და მასთან შედარებული
   თქვენი diff, შემდეგ კი კონტრიბუტორის სამუშაო პროცესის შესაბამისად შეასრულეთ rebase ან merge. გენერირებული ფაილებისა
   და კატალოგების კონფლიქტები მათი წყაროდან მოაგვარეთ, ხელახლა დააგენერირეთ, კვლავ გაუშვით მიზნობრივი ციკლი და დაადასტურეთ,
   რომ PR კვლავ აქტიურ release branch-ს უმიზნებს.
6. **დააფიქსირეთ მტკიცებულებები.** PR-ის შაბლონში ჩამოთვალეთ გაშვებული ბრძანებები, ყველა დამატებული ან შეცვლილი ტესტ-ფაილი,
   მიგრაციები ან ფუნქციური ალმები და ნებისმიერი მხოლოდ CI-ში შესასრულებელი ვალიდაცია, რომელიც ჯერ კიდევ მოლოდინშია.

## რეკომენდებული გზები ცვლილების ტიპების მიხედვით

ქვემოთ მოცემული ბრძანებები მინიმალური მიზნობრივი შემოწმებებია და არა იმ ტესტის გამოტოვების ნებართვა, რომელიც უშუალოდ ფარავს
თქვენ მიერ შეცვლილ ქცევას.

### პროვაიდერი

**კონტრაქტები**

- პროვაიდერის განსაზღვრება `src/shared/constants/providers/`-ში და მისი კომპოზიცია
  `src/shared/constants/providers.ts`-ში.
- მოდელები და შესაძლებლობები `open-sse/config/providerRegistry.ts`-ში ან მისგან გამოყოფილ რეესტრის ფაილებში.
- Executor/translator-ის არჩევა, OAuth-ის ან API-გასაღების კონფიგურაცია, dashboard-ის რესურსები და, შესაბამის შემთხვევაში, გენერირებული
  პროვაიდერის ცნობარი.
- საჯარო ავტორიზაციის მონაცემებმა უნდა გამოიყენოს `resolvePublicCred()`; შეცდომის პასუხებმა უნდა გამოიყენოს საზიარო სანიტიზებული
  შეცდომების დამხმარე ფუნქციები. იხილეთ `docs/security/PUBLIC_CREDS.md` (git; არ კომპილირდება `/docs`-ში) და
  [Error Sanitization](../security/ERROR_SANITIZATION.md).

**მიზნობრივი ციკლი**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # როდესაც კატალოგი იცვლება; შეიტანეთ გენერირებული diff commit-ში
npm run lint
```

ასევე შეამოწმეთ ყველა დაზარალებული მოთხოვნის ოჯახი: chat, Responses, images, embeddings, audio ან video.
გენერირებული კატალოგისა და golden diff-ები განიხილეთ, როგორც კონტრაქტის ცვლილებები; ბრმად ნუ მიიღებთ მათ.

### მარშრუტიზაცია

**კონტრაქტები**

- საჯარო სტრატეგიის მნიშვნელობები და UI მეტამონაცემები `src/shared/constants/routingStrategies.ts`-ში.
- დისპეტჩერიზაცია და თანმიმდევრობა `open-sse/services/combo.ts`-ისა და `open-sse/services/combo/`-ის ფარგლებში.
- Combo-ს სქემები, შენახვა, მდგრადობის მდგომარეობა, მოდელის შესაძლებლობები და API/UI მართვის ელემენტები.
- [Auto-Combo Engine](../routing/AUTO-COMBO.md) და მდგრადობის დოკუმენტაცია, როდესაც ქცევა იცვლება.

**მიზნობრივი ციკლი**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # სტრატეგიის ან დისპეტჩერიზაციის ცვლილებები
npm run check:known-symbols      # სტრატეგიის რეგისტრაციის ცვლილებები
npm run lint
```

ლოკალურად გამოიყენეთ დეტერმინისტული ტესტები იმიტირებული upstream-ით. რეალური combo smoke-ტესტები ავტორიზაციის მონაცემებს საჭიროებს და
ხელით სრულდება; ისინი CI-ის შემცვლელი არ არის.

### UI / UX

**კონტრაქტები**

- Next.js-ის route/page და საზიარო კომპონენტების საზღვრები `src/app/`-ისა და
  `src/shared/components/`-ის ფარგლებში.
- API პასუხების ფორმები, ჩატვირთვის/ცარიელი/შეცდომის მდგომარეობები, კლავიატურითა და ეკრანის წამკითხველით მუშაობა,
  ადაპტიური განლაგება, თემები და ლოკალების გაფართოება.
- ინგლისური UI-ის საწყისი სტრიქონები `src/i18n/messages/en.json`-ში; მომხმარებლისთვის ხილული ახალი ტექსტი პირდაპირ კოდში არ ჩაწეროთ.

**მიზნობრივი ციკლი**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ინტერაქციის ან ვიზუალური ცვლილებებისთვის გაუშვით აპლიკაცია და შეამოწმეთ როგორც ვიწრო, ისე ფართო viewport-ები. CI გაუშვებს
production build-სა და უფრო ფართო ნაკრებებს; ვიზუალურ ქცევას მაინც სჭირდება ცვლილებისთვის შესაფერისი მიზნობრივი კომპონენტური ტესტი, Playwright,
ან დოკუმენტირებული ხელით შემოწმება.

### i18n

**კონტრაქტები**

- `src/i18n/messages/en.json` არის UI-ის წყარო; `config/i18n.json` არის ლოკალების წყარო.
- CLI კატალოგები ცალკე, `bin/cli/locales/`-ის ქვეშ მდებარეობს.
- ზუსტად შეინარჩუნეთ ICU placeholder-ები და ტეგები. არ თარგმნოთ პროდუქტის/პროვაიდერის/მოდელის სახელები,
  პროტოკოლებისა და header-ების სახელები, ბრძანებები, კოდის/JSON-ის იდენტიფიკატორები, URL-ები, გარემოს ცვლადები ან
  დაცული ტერმინები, როგორიცაა `OmniRoute`, `OAuth`, `MCP` და `A2A`. მიმდინარე საწყისი სია მდებარეობს
  `scripts/i18n/glossary/protected-terms.json`-ში.

**მიზნობრივი ციკლი**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # როდესაც CLI-ის სტრიქონები/კატალოგები იცვლება
```

ბრძანებები, რომლებიც გარე სერვისებს იძახებს, თუ ამოცანა პირდაპირ არ მოითხოვს გენერირებულ თარგმანებს და

## დეველოპერის სკრიპტები საზიარო მანქანისთვის

ორი `scripts/dev/` დამხმარე სკრიპტი განსაზღვრავს ლოკალურ ციკლს devbox-ზე, სადაც სხვა სესიებიც აქტიურია:

```bash
scripts/dev/typecheck-touched.sh --base release/vX.Y.Z   # ფაილები დიაპაზონიდან merge-base(HEAD, base)..HEAD
scripts/dev/typecheck-touched.sh src/a.ts tests/unit/b.test.ts   # ზუსტად ეს ფაილები
scripts/dev/new-worktree.sh fix/1234-slug release/vX.Y.Z  # იზოლირებული worktree, უსაფრთხოა პარალელურად
```

- `typecheck-touched.sh` ტიპებს ამოწმებს მხოლოდ შეცვლილ `.ts/.tsx` ფაილებში დროებითი
  `tsconfig.touched.tmp.json`-ის მეშვეობით (`extends ./tsconfig.json`, `types: ["node"]`, `noEmit`,
  `incremental: false`), 6 GB heap-ის პირობებში, ამიტომ ის ანაცვლებს მთელ პროექტზე გაშვებულ `tsc -p tsconfig.json`-ს,
  რომელიც დატვირთულ მანქანაზე OOM-ით სრულდება. ის ბეჭდავს შეცვლილ ფაილებში არსებულ შეცდომებს და ერთ შემაჯამებელ სტრიქონს, ხოლო
  ასრულებს კოდით `1`, თუ შეცდომები შეცვლილ ფაილებშია, `2`, თუ შეცდომები მხოლოდ იმპორტირებულ ფაილებშია ან tsc
  დიაგნოსტიკის გარეშე დასრულდა (წაიკითხეთ მის მიერ მითითებული ჟურნალი `_artifacts/typecheck-touched/`-ში), `0`, თუ
  შეცდომები არ არის. დროებითი tsconfig ყოველთვის იშლება; არასოდეს დაამატოთ ის კომიტში.
- `new-worktree.sh` თანმიმდევრულად ასრულებს პარალელურ გაშვებებს `<git-common-dir>/omniroute-new-worktree.lock`-ზე
  (ნაგულისხმევად ელოდება მაქსიმუმ 600 s-ს და აჩვენებს შეტყობინებას; გადაფარვის წესი აღწერილია
  სკრიპტის სათაურში) და უკან აბრუნებს
  მის მიერ შექმნილ ბრენჩს, როდესაც `git worktree add` worktree-ის შექმნამდე ვერ სრულდება, ამიტომ ხელახლა ცდისთვის
  `git branch -D`-ის ხელით გაშვება საჭირო არ არის. მყარი ბმულებით დაკავშირებული `node_modules` და `.husky/_`-ის ასლი უცვლელია.

## კანდიდატის ლოკალური ციკლი

საწყისი კოდის ტესტები ვერ დაამტკიცებს, რომ შეფუთული არტეფაქტი გაეშვება: შეფუთვის სიები, შემცირებული დამოკიდებულებები
და ნატიური ბინარული ფაილები შეცდომას მხოლოდ tarball-ის ინსტალაციისა და გაშვების შემდეგ გამოავლენს. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) არის RFC #8084-ით განსაზღვრული ერთხელ აგების / ვალიდაციის / დაწინაურების პროცესის ლოკალური მხარე:
ის აგებს ერთ კანდიდატს, ამოწმებს ზუსტად ამ არტეფაქტს, დირექტორიების სახელების შეცვლით აწინაურებს მას
და უკან აბრუნებს, თუ დაწინაურებული სლოტი ჯანმრთელობის შემოწმებას ვერ გაივლის.

```bash
npm run dev:candidate -- run --dry-run --json  # გეგმის დაბეჭდვა ცვლილებების გარეშე
npm run dev:candidate -- run                   # აგება + ვალიდაცია + დაწინაურება, ავტომატური უკან დაბრუნება
npm run dev:candidate -- build                 # npm pack + ინსტალაცია _artifacts/candidate/<id>/-ში
npm run dev:candidate -- validate --id <id>    # გაშვება თავისუფალ პორტზე, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current-ისა და previous-ის ადგილების გაცვლა
npm run dev:candidate -- run --from-tarball <file.tgz>  # სხვაგან აგებული tarball-ის ხელახლა გამოყენება (CI)
```

- **ააგეთ ერთხელ.** `build` აფუთავს მიმდინარე ხეს (მას სჭირდება `dist/server.js`, ამიტომ ჯერ გაუშვით
  `npm run build:release`) ან აკოპირებს `--from-tarball`-ს, შემდეგ კი tarball-ს იზოლირებულ npm prefix-ში
  აინსტალირებს, რადგან tarball არ შეიცავს `node_modules`-ს. id არის მოკლე `HEAD`
  sha (`-dirty`, როდესაც ხეს ლოკალური ცვლილებები აქვს) ან `tgz-<sha256>` tarball-ისთვის. უკვე აგებული სუფთა id
  ხელახლა აგების ნაცვლად ხელახლა გამოიყენება; მის თავიდან ასაგებად მიუთითეთ `--force`.
- **შეამოწმეთ პაკეტი და არა საწყისი კოდი.** `validate` უშვებს დაინსტალირებულ CLI-ს
  (`serve --port <free port>`) ახალი `DATA_DIR=<candidate>/data`-ითა და ყალბი საიდუმლო მნიშვნელობებით, ხოლო
  ოპერატორის `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` და `INITIAL_PASSWORD` გარემოდან ამოღებულია,
  რათა შემოწმდეს ახალი ინსტალაციის გასაღების გარეშე loopback-რეჟიმი. ის ელოდება, რომ
  `GET /api/health` დააბრუნებს 200-ს, მოითხოვს, რომ `GET /v1/models`-მაც დააბრუნოს 200, აჩერებს პროცესების ჯგუფს
  და შედეგს tarball-ის ჰეშთან ერთად `validation.json`-ში იწერს.
- **დააწინაურეთ იგივე არტეფაქტი.** `promote` უარყოფს კანდიდატს, თუ მისი
  მიმდინარე tarball-ის ჰეშისთვის წარმატებული ვალიდაცია არ არსებობს. ნაგულისხმევი აქტიური სლოტია `_artifacts/candidate/current`; `--target <dir>`
  იმავე ფაილურ სისტემაში სხვა დირექტორიას ირჩევს, ხოლო მისი წინა სლოტია `<dir>.previous`.
  თითოეული სახელის შეცვლა ატომურია, ხოლო პროცესის შუაში მომხდარი შეცდომა უკვე შესრულებულ სახელის ცვლილებებს უკან აბრუნებს.
- **უკან დაბრუნება.** `run` დაწინაურებულ სლოტს ხელახლა ამოწმებს და, თუ
  ეს შემოწმება ვერ გაიარა, `current`-სა და `previous`-ს ადგილებს კვლავ უცვლის. კანდიდატი, რომელიც პირველ ვალიდაციას ვერ გაივლის, არასოდეს დაწინაურდება.

ყველაფერი იწერება git-ის მიერ უგულებელყოფილ `_artifacts/candidate/`-ში; არსებული OmniRoute-ის
ინსტალაცია და მისი მონაცემთა დირექტორია არასოდეს იცვლება. დაწინაურებული CLI არის
`_artifacts/candidate/current/prefix/bin/omniroute`; მისი გამოყენებისას გაუშვით საკუთარი `DATA_DIR`-ით.
გასვლის კოდები: `0` — წარმატება, `1` — წარუმატებელი ვალიდაცია ან დაწინაურება, `2` — გამოყენების შეცდომა ან არარსებული build.

წარმატებით გაივლის. ამასთანავე, ნუ აიძულებთ ყოველ ლოკალურ ცვლილებას, დაელოდოს რეპოზიტორიის სრულ მატრიცას.

## შეჯერების საკონტროლო სია

რევიუს მოთხოვნამდე:

- დაადასტურეთ, რომ PR-ის საბაზისო ტოტი კვლავ უმაღლესი აქტიური `release/v*` ტოტია.
- ჩამოტვირთეთ ეს საბაზისო ტოტი და გადახედეთ კომიტებს, რომლებიც თქვენი ტოტის შექმნის შემდეგ დაემატა.
- შემთხვევითი ან გენერირებული ზედმეტი ცვლილებების გამოსავლენად გადახედეთ `git diff <active-base>...HEAD`-ს.
- კატალოგისა და გენერირებული დოკუმენტების კონფლიქტები გადაჭერით წყაროს განახლებითა და გამომავალი შედეგის ხელახლა გენერირებით.
- შეჯერების შემდეგ ხელახლა გაუშვით PR-ის აღწერაში ჩამოთვლილი ყველა ფოკუსირებული ტესტი/გეითი.
- არასოდეს შეასუსტოთ მტკიცებები ან ამოიღოთ სავალდებულო ტესტები მხოლოდ შეცვლილ საბაზისო ტოტთან შესაბამისობისთვის.
