## რატომ SQLite?

OmniRoute-მა PostgreSQL/MySQL-ის ნაცვლად SQLite რამდენიმე მიზეზით აირჩია:

| ფაქტორი                   | SQLite                                            | PostgreSQL                                              |
| ------------------------- | ------------------------------------------------- | ------------------------------------------------------- |
| **განთავსება**            | ჩაშენებული — ცალკე სერვერი არ სჭირდება            | მოითხოვს სერვერის გამართვას                             |
| **დაშიფვრა**              | აპლიკაციის დონეზე (AES-256-GCM)                   | ჩაშენებული TDE                                          |
| **წარმადობა**             | უფრო სწრაფია მცირე/საშუალო დატვირთვებისთვის       | უკეთესია უზარმაზარი რაოდენობის პარალელური ჩაწერებისთვის |
| **პარალელურობა**          | WAL რეჟიმი პარალელური წაკითხვის საშუალებას იძლევა | სრული MVCC                                              |
| **სარეზერვო ასლი**        | ერთი ფაილის კოპირება                              | `pg_dump` ან ფაილური სისტემის მომენტალური ასლი          |
| **გამოყენების შემთხვევა** | თითოეული მომხმარებლის ინსტალაცია, ჩაშენებული      | მრავალმომხმარებლიანი SaaS                               |

**ერთმომხმარებლიანი, ერთინსტანციანი** განთავსებისთვის (OmniRoute-ის გამოყენების ძირითადი შემთხვევა) SQLite უფრო მარტივი და სწრაფია.

### WAL ჟურნალირება

`core.ts` მონაცემთა ბაზას **WAL (წინასწარი ჩაწერის ჟურნალის) რეჟიმში** ხსნის:

```ts
// src/lib/db/core.ts
db.pragma("journal_mode = WAL");
db.pragma("busy_timeout = 2000");
db.pragma("synchronous = NORMAL");
db.pragma(`cache_size = -${DEFAULT_DATABASE_SETTINGS.optimization.cacheSize}`);
```

WAL ჩაწერის დროს **პარალელური წაკითხვის** საშუალებას იძლევა — ეს მნიშვნელოვანია მართვის პანელისთვის, რომელიც მოთხოვნების ჩაწერის პარალელურად ასრულებს მოთხოვნებს მონაცემთა ბაზაში.

ქეშის ნაგულისხმევი ზომაა **65,536 KiB (64 MiB)**. SQLite უარყოფით
`cache_size`-ს აღიქვამს, როგორც KiB-ში გამოსახულ მიახლოებით ზედა ზღვარს და გვერდებს საჭიროებისამებრ გამოყოფს.
**პარამეტრები > სისტემა და საცავი > ქეშის ზომა** იღებს მთელ რიცხვებს **1-დან
1,000,000 KiB-მდე**; პარამეტრის შენახვა მას მონაცემთა ბაზის აქტიურ კავშირზე
გამოიყენებს, ხოლო OmniRoute გაშვებისას შენახულ მნიშვნელობას აღადგენს.

| OS      | გზა                                                                  |
| ------- | -------------------------------------------------------------------- |
| Linux   | `~/.omniroute/storage.sqlite`                                        |
| macOS   | `~/.omniroute/storage.sqlite`                                        |

## საბაზისო სქემა (17 ცხრილი)

## მიგრაციები

OmniRoute იყენებს** ვერსიული, იდემპოტენტური მიგრაციები** `src/lib/db/migrations/` ში. თითოეული მიგრაცია არის ერთი SQL ფაილი. დასახელების ორი ფორმატი თანაარსებობს; `_omniroute_migrations` ში ჩაწერილი ვერსია არის რიცხვითი პრეფიქსი.

### მიგრაციის დასახელება

დროის ანაბეჭდის ფორმატის წესები (აღსრულებულია `npm run check:migration-numbering` მიერ, გაზიარებულია გენერატორთან `scripts/check/lib/migrationNaming.mjs` ში):

- აღწერა არის პატარა `snake_case` რომელიც იწყება ასოთი (`a-z`, `0-9`, ერთი `_` სიტყვებს შორის), მაქსიმუმ 80 სიმბოლო.
- ორი ფაილი ერთი და იგივე დროის შტამპით არის დუბლიკატი.
- უფსკრულის წესი ვრცელდება მხოლოდ ძველ სერიებზე: ყველა რიცხვი `001` დან `241` მდე უნდა არსებობდეს, გარდა ცნობილი ხარვეზებისა `026`, `055` და `121`. `241` (ან ნებისმიერი ძველი ფაილის) წაშლა ვერ ახერხებს კარიბჭეს. `001` და `241` ვერასოდეს დაემატება `KNOWN_GAPS` დაშვებულ სიას. დროში მონიშნული ფაილები არასოდეს ქმნიან ხარვეზს.
- `src/lib/db/migrations/` ში ყოველი ჩანაწერი უნდა იყოს ჩვეულებრივი ფაილი მოქმედი მცირე ზომის `.sql` სახელით. დირექტორია, symlink, `.SQL` ან `.sql.bak` ფაილი, დამალული ფაილი ან სახელი ინტერვალით არ იშლება კარიბჭეში, რადგან მორბენალი ჩუმად გამოტოვებს მას ან ჩატვირთვისას ავარია.

**შეკვეთის გამოყენება.** runner ახარისხებს პრეფიქსის რიცხვითი მნიშვნელობის მიხედვით და არა ტექსტის მიხედვით: ჯერ ძველი `001`–`241` ფაილები, შემდეგ დროის შტამპით დატანილი ფაილები დროის ნიშნულის მიხედვით, შემდეგ ნებისმიერი სახელების სივრცის დირექტორიები, რომლებიც რეგისტრირებულია `OMNIROUTE_EXTRA_MIGRATIONS_DIRS` (ვერსიები, როგორიცაა `ee-001`). მომლოდინე მიგრაცია არის ნებისმიერი ფაილი, რომლის ვერსიაც არ არის `_omniroute_migrations` ში, ამიტომ მიგრაცია ძველი ფილიალიდან, რომელიც გაერთიანდება ახლის შემდეგ, კვლავ ვრცელდება არსებულ მონაცემთა ბაზებზე.

**დროის ანაბეჭდი არის შექმნის ბრძანება და არა შერწყმის ბრძანება.** თუ თქვენი მიგრაცია დამოკიდებულია ცხრილზე ან სვეტზე, რომელიც შექმნილ იქნა მიგრაციით a** უფრო ახალი** დროის ანაბეჭდი (მაგალითად, ერთი მეორე PR დან, რომელიც პირველად გაერთიანდა), ახალი მონაცემთა ბაზა გაშვებული იქნება თქვენი და წარუმატებელი. სანამ თქვენი PR ჯერ კიდევ ღიაა, განაახლეთ ფაილის სახელი `npm run db:new-migration` ით, რათა მან მიიღოს უფრო ახალი დროის ანაბეჭდი, ან გახადეთ იგი დამოუკიდებელი. `npm run test:migrations:fresh` იყენებს ყველა მიგრაციას ცარიელ მონაცემთა ბაზაში და იჭერს ამას.

### გაერთიანებული მიგრაცია არასოდეს წაიშლება ან არ სახელდება

მას შემდეგ, რაც მიგრაციის ფაილი იქნება გამოშვების ფილიალში ან `main`, ის უკვე გაშვებულია ჰომოლოგიურ და დეველოპერთა მონაცემთა ბაზებზე, VPS ინსტალაციაზე და Enterprise სინქრონიზაციაში. მას შემდეგ:

- **არასოდეს წაშალოთ იგი.** ახალი ინსტალაციები დაკარგავს თავის სქემას, სანამ განახლებული მონაცემთა ბაზები ინახავს მას.
- **არასოდეს გადარქმევა.** ვერსია `_omniroute_migrations` ში აღარ ემთხვევა ფაილს, ამიტომ ყველა მონაცემთა ბაზა, რომელიც უკვე გამოიყენებდა მას, კვლავ გაუშვებს მას. არა idempotent SQL შემდეგ ახდენს მონაცემების დუბლირებას ან აჩერებს ჩატვირთვას.
- **გჭირდებათ განსხვავებული სქემა?** შექმენით ახალი მიგრაცია `npm run db:new-migration` სთან ერთად.

სახელის გადარქმევა უსაფრთხოა მხოლოდ იმ ფაილისთვის, რომელიც ჯერ არ არის გაერთიანებული, რაც ეხება კარიბჭის მინიშნებებს. გამოშვების ტეგი აქ არაფერს ცვლის: `release/v*` ფილიალში ყოველი ბიძგი აქვეყნებს Docker `:next` სურათს და მუშაობს ჰომოლოგზე, VPS ინსტალაციაზე და Enterprise სინქრონიზაციაზე, ასე რომ, გაერთიანებული მიგრაცია გაშვებულია რეალურ მონაცემთა ბაზაზე, სანამ რაიმე `vX.Y.Z` ტეგი იარსებებს. კარიბჭე ვერ ხერხდება საბაზისო ფაილის ყოველი წაშლა, მონიშნული თუ არა.

- **მიმდინარეობს გაერთიანებული მიგრაციის დაბრუნება.** `git revert`, რომელიც წაშლის ფაილს, არღვევს კარიბჭეს. შეინახეთ ფაილი და გააუქმეთ მისი სქემა ახალ მიგრაციაში: `npm run db:new-migration -- <description>`, `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS` და ასე შემდეგ. განახლებული და ახალი მონაცემთა ბაზები შემდეგ მთავრდება იგივე სქემით.
- **ერთი მიღებული გადარქმევა: თავსებადობის ჩანაწერი და იდენტური შინაარსი.** თუ გაერთიანებული ფაილი უნდა გადავიდეს (მაგალითად, ორი გაერთიანებული ფაილი იზიარებს დროის ანაბეჭდს და runner ჩერდება ვერსიის შეჯახებისას), გადაარქვით შემდეგს მისი SQL შეხების გარეშე და დაამატეთ `{ fromVersion, fromName, toVersion, toName }` `RENAMED_MIGRATION_COMPATIBILITY` ს `src/lib/db/migrationRunner/constants.ts` ში. მონაცემთა ბაზები, რომლებმაც გამოიყენეს ძველი ვერსია, გადაიტანენ `_omniroute_migrations` მწკრივს ფაილის ხელახლა გაშვების ნაცვლად. კარიბჭე აფრთხილებს ასეთი გადარქმევის შესახებ და ყოველთვის აწარმოებს მასზე შესაცვლელობის შემოწმებას, როგორიც არ უნდა იყოს ახალი დროის შტამპი: ახალი ინსტალაციები ვრცელდება ფაილს მის ახალ პოზიციაზე, განახლებული მონაცემთა ბაზები არა, ასე რომ, აირჩიეთ ახალი დროის შტამპი ძველთან ახლოს. კარიბჭე ვერ გადარქმევს, თუ კონტენტი შეიცვალა (სქემის ცვლილება კვლავ ხდება ახალ მიგრაციაში), ან თუ ჩანაწერის სამიზნე ფაილი არ არის დისკზე.
- **არასოდეს გადარქმევა ერთი და იგივე დროის შტამპის ფარგლებში.** გადარქმევა, რომელიც ინახავს დროის ნიშანს და ცვლის მხოლოდ აღწერილობას, არღვევს კარიბჭეს, ჩანაწერით ან მის გარეშე. ჩანაწერით, რომლის `toVersion` უდრის მის `fromVersion`, runner წაშლის ძველ `_omniroute_migrations` მწკრივს და კვლავ იყენებს ფაილს ყველა მონაცემთა ბაზაში, რომელიც უკვე გაშვებულია. ჩანაწერის გარეშე, მორბენალი თვალს ადევნებს მხოლოდ ვერსიას: ის გამოტოვებს ფაილს ამ მონაცემთა ბაზებზე (ახალი კონტენტი არასოდეს გადის იქ) და აღრიცხავს ხელახალი ნუმერაციის შეცდომას ყოველ ჩატვირთვაზე. გამოიყენეთ სხვა დროის ანაბეჭდი პლუს თავსებადობის ჩანაწერი, ან შეინახეთ სახელი.
- **კარიბჭე ამოწმებს, რომ გადარქმეული ფაილი აღარ გაუშვას.** ყოველი დაფარული სახელის გადარქმევისთვის, კარიბჭე გადასცემს ფაილის ახალ სახელს შეცვლის შემოწმებას `--must-not-apply` ით. ჩეკი ჩატვირთავს განახლებულ მონაცემთა ბაზას რეალური runner-ით და თუ runner კვლავ გამოიყენებს ამ ფაილს (მაგალითად, იმიტომ, რომ ჩანაწერს აქვს არასწორი ვერსია ან სახელი, ან იმიტომ, რომ კარიბჭის ტექსტის პარსერი კითხულობს `constants.ts` TypeScript სგან განსხვავებულად), კარიბჭე ვერ ახერხებს `migration renomeada rodaria de novo` და გთხოვს შეამოწმოთ ჩანაწერის ძველი და ახალი ვერსიები და სახელები.

### რას ამოწმებს კარიბჭე ბაზის წინააღმდეგ

ამოღების მოთხოვნისა და შერწყმის რიგის გაშვებისას, `npm run check:migration-numbering` ადარებს `src/lib/db/migrations/` დისკზე იმავე დირექტორიასთან საბაზისო ფილიალში. ბაზა არის ამ თანმიმდევრობით: `--base-latest-tag`, `--base <ref>`, `MIGRATION_BASE_REF` ცვლადი, ან, როდესაც `GITHUB_EVENT_NAME` არის `pull_request`, `pull_request_target` ან `merge_group`, შერწყმის ჩადენის პირველი მშობელი, მოვლენის დატვირთვის `merge_group.base_sha` ან `git merge-base HEAD origin/$GITHUB_BASE_REF`. ამოღების მოთხოვნის ან შერწყმის რიგის გაშვებისას გადასაჭრელი ბაზის გარეშე, კარიბჭე ვერ ხერხდება. CI გარეთ `--base` გარეშე ის ბეჭდავს `comparação com a base: pulada (sem --base)` და გამოტოვებს ამ წესებს.

`--base-latest-tag` ადარებს უახლეს გამოშვების ტეგს (`vX.Y.Z` სემვერის თანმიმდევრობით; სუფიქსური ტეგები, როგორიცაა ღამის თვლები არ ითვლება), რომელიც არის `HEAD` ის ისტორიაში, იგივე წესებით, როგორც `--base`. Release-Green (`scripts/quality/validate-release-green.mjs`) აწარმოებს კარიბჭეს ამ გზით, რადგან push და დაგეგმილ გაშვებებს არ გააჩნიათ pull-ის მოთხოვნის ბაზა და შერწყმა შეიძლება დაეშვას ახალი CI გაშვების გარეშე. ისტორიაში გამოშვების ტეგის გარეშე, კარიბჭე იშლება; გაუშვით `git fetch --tags` ( CI ში, `actions/checkout` `fetch-depth: 0` ით მოაქვს ტეგები).

რედაქტირებული საბაზისო ფაილისთვის, აღადგინეთ საბაზისო შინაარსი და ჩადეთ ცვლილება ახალ მიგრაციაში; გადარქმეული ფაილისთვის გააუქმეთ სახელის გადარქმევა ან აირჩიეთ სხვა ახალი დროის შტამპი, სადაც ის გადაადგილდება, არასოდეს იგივე დროის შტამპი სხვა სახელით. თუ ჩეკი თავად ვერ გადის, კარიბჭე იშლება CI ში და მხოლოდ აფრთხილებს ადგილობრივად. რედაქტირებული საბაზისო ფაილისთვის, განახლებული მონაცემთა ბაზა აგებულია ამ ფაილის ბაზის შინაარსით და მეორე ჩატვირთვა გამოტოვებს მას, რადგან მისი ვერსია უკვე ჩაწერილია. გადარქმეული ფაილისთვის, განახლებული მონაცემთა ბაზა აგებულია ფაილით მისი ძველი სახელით და მეორე ჩატვირთვა გადააქვს თავის `_omniroute_migrations` სტრიქონს თავსებადობის ჩანაწერში იმის ნაცვლად, რომ ხელახლა გაუშვას; კარიბჭე გადასცემს ახალ სახელს `--must-not-apply` ით, ამიტომ შემოწმება ვერ ხერხდება, თუ მეორე ჩატვირთვა გამოიყენებს მას. თუ pull მოთხოვნის მიგრაცია ვერ გამოიყენება განახლებულ გზაზე, ანუ ყოველი ბაზის მიგრაციის შემდეგ (მიუხედავად იმისა, ვერ მოხერხდება ის ასევე ახალ ინსტალაციაზე), კარიბჭე იტყობინება `migration do PR não aplica` და გთხოვთ დააფიქსიროთ SQL ბაზის მიმდინარე სქემთან მიმართებაში; ### როგორ მიმდინარეობს მიგრაცია

გაშვებისას, `migrationRunner.ts`:

1. ქმნის `_omniroute_migrations` ცხრილს, თუ არ არსებობს
2. მოთხოვნები უკვე გამოყენებული მიგრაციებისთვის
3. იყენებს ნებისმიერ ახალ მიგრაციას თანმიმდევრობით, თითოეულს ტრანზაქციაში

```ts
// src/lib/db/migrationRunner.ts (simplified)
export async function runMigrations(db: SqliteDatabase, migrationsDir: string) {
  const applied = getAppliedMigrations(db);
  const available = readMigrationFiles(migrationsDir);

  for (const migration of available) {
    if (applied.includes(migration.id)) continue;
    db.transaction(() => {
      db.exec(migration.sql);
      recordAppliedMigration(db, migration.id);
    })();
  }
}
```

3. **შეავსეთ მონაცემები ყურადღებით** : გამოიყენეთ `UPDATE ... WHERE ...` არსებული რიგების დასამუშავებლად

- `provider_connections.access_token`, `refresh_token`, `id_token` — დაშიფრულია აპლიკაციის დონეზე
- `key_value` ჩანაწერები, სადაც `namespace = "secrets"` — დაშიფრულია აპლიკაციის დონეზე
- `proxy_registry.auth` — დაშიფრულია აპლიკაციის დონეზე (თუ არსებობს)

### დაშიფვრის გასაღები

დაშიფვრის გასაღები მიიღება **საიდუმლო ფრაზიდან** (დაყენებულია `STORAGE_ENCRYPTION_KEY` გარემოს ცვლადის მეშვეობით) და **salt**-იდან (ინახება მონაცემთა ბაზაში). მონაცემების გაშიფვრისთვის ორივე აუცილებელია.

```bash
# უსაფრთხო საიდუმლო ფრაზის გენერირება
openssl rand -hex 32

# დაყენება .env-ში
STORAGE_ENCRYPTION_KEY=<your-key>
```

> **კრიტიკულად მნიშვნელოვანია**: დაშიფვრის გასაღების დაკარგვა ნიშნავს ყველა დაშიფრულ მონაცემზე წვდომის დაკარგვას. **გასაღების სარეზერვო ასლი მონაცემთა ბაზისგან განცალკევებით შეინახეთ**.

### რა არ არის დაშიფრული

წარმადობის გამო შემდეგი მონაცემები ღია ტექსტის სახით ინახება:

- პროვაიდერების საჩვენებელი სახელები

- მარშრუტიზაციის წესები
- გამოყენების ჩანაწერები (არ შეიცავს PII-ს)

## დაშიფვრის თავისებურებები (v3.8.16+)

OmniRoute ორი დაშიფვრის სქემის გამჭვირვალედ დასამუშავებლად იყენებს **`migrateLegacyEncryptedString()`**-ს:

## სარეზერვო ასლის შექმნა და აღდგენა

### სარეზერვო ასლის ხელით შექმნა

```bash
# ლოკალური სარეზერვო ასლის შესაქმნელად გამოიყენეთ CLI

curl -X PUT http://localhost:20128/api/db-backups \

```

სარეზერვო ასლის ფაილი მოიცავს:

- DB-ის ყველა ცხრილს (JSON-ად სერიალიზებულს)
- გამოძახებების ჟურნალის არტეფაქტებს (base64-ით კოდირებულს, არასავალდებულო)
- პარამეტრებსა და საიდუმლო მონაცემებს (დაშიფრულს)
- პლაგინების კონფიგურაციას

### აღდგენა

### ავტომატური სარეზერვო ასლები

```bash
# CLI-ის მეშვეობით ყოველდღიური ავტომატური სარეზერვო ასლების შექმნის ჩართვა
```

განრიგი სერვერის მხარეს სრულდება ფონური დავალების მიერ, რომელიც ყოველ 30 წამში

| ------------------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_BACKUP_SCHEDULE_JOB_INTERVAL_MS` | `30000`      | აქტივაციის ინტერვალი მწმ-ში (მინ. `5000`). შესაბამის cron-წუთში საიმედოდ მოსახვედრად 60 წმ-ზე ნაკლები უნდა იყოს. |

## შესრულების Tuning

### WAL რეჟიმი

WAL ჩართულია ნაგულისხმევად. მაღალი წერის დატვირთვისთვის განიხილეთ:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- Checkpoint every 1000 pages
```

OmniRoute არ აყენებს `journal_size_limit`. გამშვები პუნქტი გადააქვს WAL ჩარჩოებს მთავარ ფაილში, მაგრამ WAL ფაილი ინარჩუნებს ყველაზე დიდ გამოყოფილ ზომას. `OMNIROUTE_WAL_GUARD_MAX_MB` მცველი მხოლოდ აფრთხილებს და აწარმოებს `wal_checkpoint(RESTART)`; ეს არ არის დისკის ზომის თავსახური.

### ინდექსები

შესრულების ძირითადი ინდექსები (ავტომატურად შექმნილი მიგრაციებით):

- `idx_models_provider` — მოდელის ძიება პროვაიდერის მიერ
- `idx_combo_targets_combo_id` — კომბინირებული სამიზნე გაფართოება
- `idx_usage_history_api_key_timestamp` — გამოყენების ანალიტიკა
- `idx_quota_snapshots_api_key_window` — კვოტის თვალყურის დევნება
- `idx_call_logs_timestamp` — ზარის ჟურნალის მოთხოვნები

ახალი ინდექსის დასამატებლად შექმენით მიგრაცია:

```sql
-- 023_add_my_index.sql
CREATE INDEX IF NOT EXISTS idx_my_table_my_column ON my_table(my_column);
```

### მეხსიერების რუკაზე მოყვანილი I/O

ძალიან დიდი მონაცემთა ბაზებისთვის (> 10 GB), მეხსიერების რუკების კორექტირება შესაძლებელია SQLite პრაგმის საშუალებით:

```sql
-- Set via SQLite pragma (adjust in core.ts or runtime)
PRAGMA mmap_size = 268435456;  -- 256MB
```

### დატკეპნა

OmniRoute გრძელვადიანი შემთხვევები სარგებლობს შემთხვევითი `VACUUM` ით:

```bash
sqlite3 ~/.omniroute/storage.sqlite "VACUUM;"
```

იმოძრავეთ ყოველთვიურად დაბალი ტრაფიკის ფანჯრების დროს. (WAL რეჟიმი ამცირებს საჭიროებას, მაგრამ არ გამორიცხავს მას.)

## მდგომარეობის შემოწმება

`src/lib/db/healthCheck.ts` უზრუნველყოფს **მონაცემთა ბაზის დონის მდგომარეობის დიაგნოსტიკას**:

ორივე HTTP მეთოდი ავთენტიფიკაციას მოითხოვს (წინააღმდეგ შემთხვევაში — `401`). `GET` მხოლოდ დიაგნოსტიკას ასრულებს; `POST` კი იმავე შემოწმებას გაშვებული `autoRepair`-ით ასრულებს.

```bash
GET  /api/db/health   # დიაგნოსტიკა
POST /api/db/health   # დიაგნოსტიკა + შეკეთება
```

პასუხი არის `runDbHealthCheck()`-ის მიერ შექმნილი `DbHealthCheckResult`
(`src/lib/db/healthCheck.ts`):

```json
{
  "isHealthy": false,
  "issues": [
    {
      "type": "broken_reference",
      "table": "domain_budgets",
      "description": "დომენის ბიუჯეტები მიუთითებდა API გასაღებებზე, რომლებიც აღარ არსებობს.",
      "count": 2
    }
  ],
  "repairedCount": 0,
  "backupCreated": false,
  "autoRepair": false,
  "checkedAt": "2026-08-18T09:00:00.000Z",
  "driver": { "name": "better-sqlite3", "degraded": false }
}
```

| ველი              | მნიშვნელობა                                                                                                                                                                                     |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isHealthy`       | არის `true`, როდესაც `issues` ცარიელია. `driver` მასზე არასოდეს მოქმედებს.                                                                                                                      |
| `issues[].type`   | ერთ-ერთი შემდეგთაგანი: `integrity_check_failed`, `broken_reference`, `stale_snapshot`, `invalid_state`.                                                                                         |
| `repairedCount`   | ამ გაშვებისას შეკეთებული მწკრივები; ყოველთვის `0`-ია, როდესაც `autoRepair` არის false.                                                                                                          |
| `backupCreated`   | შეიქმნა თუ არა სარეზერვო ასლი შეკეთებამდე.                                                                                                                                                      |
| `checkedAt`       | ISO დროის ნიშნული, რომელიც საერთოა გაშვებისთვის და მის მიერ ჩაწერილი ნებისმიერი შეკეთების შენიშვნისთვის.                                                                                        |
| `driver.name`     | SQLite დრაივერი, რომელიც შემოწმებულ მონაცემთა ბაზას ემსახურება.                                                                                                                                 |
| `driver.degraded` | არის `true`, როდესაც ჩაწერები მონაცემთა ბაზის ფაილში საიმედოდ არ ინახება — `sql.js` WASM სარეზერვო ვარიანტის (მთლიანი ფაილის შენახვა) ან მეხსიერებაში განთავსებული მონაცემთა ბაზის შემთხვევაში. |

იმავე მონაცემებს აბრუნებს `omniroute_db_health_check` MCP ინსტრუმენტიც.

დაზიანების აღმოსაჩენად გაუშვით `PRAGMA integrity_check`:

```bash
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"
# უნდა გამოიტანოს: ok
```

თუ ის `ok`-ის გარდა სხვა რამეს აბრუნებს, **დაუყოვნებლივ შეწყვიტეთ მონაცემთა ბაზის გამოყენება** და აღადგინეთ ის სარეზერვო ასლიდან.


### სცენარი 2: ძირითადი DB ფაილი დაზიანებულია

აღადგინეთ სარეზერვო ასლიდან:

```bash
omniroute backup restore <backup-id>
```

`omniroute sync pull [outPath]` მხოლოდ სრულ `.tar.gz` არქივს ჩამოტვირთავს გაშვებული სერვერიდან

### სცენარი 3: დაშიფვრის გასაღები დაკარგულია

გასაღების გარეშე **აღდგენა შეუძლებელია**. დაშიფრული ველები წაუკითხავია. ხელახლა დაამატეთ ყველა პროვაიდერი ახალი ავტორიზაციის მონაცემებით.

> **პრევენციული ზომა**: დაშიფვრის გასაღების სარეზერვო ასლი ყოველთვის ცალკე შეინახეთ, სასურველია პაროლების მენეჯერში ან KMS-ში.

### სცენარი 4: დისკი სავსეა

SQLite დააბრუნებს `SQLITE_FULL` შეცდომებს. გაათავისუფლეთ ადგილი დისკზე, შემდეგ კი:

```bash
# სივრცის გასათავისუფლებლად შეასრულეთ WAL-ის საკონტროლო წერტილის შექმნა
sqlite3 ~/.omniroute/storage.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

```bash
sqlite3 ~/.omniroute/storage.sqlite <<EOF
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';
EOF
```

## პრობლემების აღმოფხვრა

### „მონაცემთა ბაზა დაბლოკილია“

სხვა პროცესს ჩაწერის ბლოკირება უჭირავს. შეგიძლიათ:

- დაელოდოთ სხვა პროცესის დასრულებას (შეამოწმეთ `lsof | grep storage.sqlite`)
- დაასრულოთ სხვა პროცესი
- თუ პრობლემა არ აღმოიფხვრა, ხელახლა გაუშვათ OmniRoute

### „გარე გასაღების შეზღუდვა დაირღვა“

დომენის მოდული რეფერენციულ მთლიანობას არღვევს. შეამოწმეთ:

- დამოკიდებულ ცხრილებში უპატრონო სტრიქონები
- კასკადური წაშლები, რომლებიც არ გავრცელდა
- ბოლო მიგრაცია, რომელმაც გარე გასაღები შეცვალა

დარღვევების საპოვნელად გაუშვით `PRAGMA foreign_key_check;`.

### „მეხსიერება არასაკმარისია“

SQLite-ის მეხსიერებაში ასახული შეყვანა/გამოტანა ოპერაციული სისტემის ლიმიტს აჭარბებს. შეამცირეთ SQLite pragma-ის მეშვეობით:

```sql
PRAGMA mmap_size = 134217728;  -- 256MB-ის ნაცვლად 128MB
```

ან გამორთეთ:

```sql
PRAGMA mmap_size = 0;
```

### „მიგრაცია შუა პროცესში ჩავარდა“

მიგრაცია ტრანზაქციაში შესრულდა, ამიტომ ცვლილებები უკან უნდა დაბრუნებულიყო. თუ ასე არ მოხდა:

1. **გააჩერეთ OmniRoute** (შემდგომი მცდელობების თავიდან ასაცილებლად)
2. **შეამოწმეთ მონაცემთა ბაზის მდგომარეობა** `sqlite3`-ის მეშვეობით
3. **ხელით გამოასწორეთ** ნაწილობრივ შესრულებული მიგრაცია
4. **ხელახლა გაუშვით** OmniRoute (მიგრაციის შესრულება ხელახლა სცდება)

ამის თავიდან ასაცილებლად, მიგრაციები ყოველთვის ჯერ ასლზე გამოცადეთ.
