> **TL;DR**: OmniRoute-ს მოჰყვება ჩაშენებული ჯანმრთელობის მონიტორინგი, პროვაიდერის ავტოპილოტი, კვოტების თვალყურის დევნება და დაკვირვებადობის ჰუკები. ეს სახელმძღვანელო მოიცავს მართვის პანელს, გაფრთხილებებსა და პრობლემების აღმოფხვრას.

**წყაროები:**

- `src/lib/monitoring/observability.ts` — დაკვირვებადობის სნეპშოტი
- `src/lib/monitoring/comboHealthAutopilot.ts` — კომბინაციის ჯანმრთელობის ავტოპილოტი
- `src/lib/monitoring/providerHealthAutopilot.ts` — პროვაიდერის ავტოპილოტი
- `src/lib/monitoring/providerHealthMatrix.ts` — პროვაიდერის ჯანმრთელობის მატრიცა
- `src/lib/localHealthCheck.ts` — ლოკალური ჯანმრთელობის შემოწმება
- `src/lib/tokenHealthCheck.ts` — ტოკენის განახლების ჯანმრთელობა
- `src/lib/proxyHealth.ts` — პროქსის ჯანმრთელობის ქეში (განხილულია PROXY_GUIDE.md-ში)

## ჯანმრთელობის შემოწმება API

OmniRoute ამხელს** ორი** HTTP ჯანმრთელობის ზედაპირები. ისინი არ არის ურთიერთშემცვლელი ორკესტრებისთვის.

| ბილიკი                       | მიზანი                                                                  | წონა                                            | გამოიყენეთ ამისთვის                                                                     |
| ---------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------- |
| `GET /healthz`               | სიცოცხლის ციკლი liveness/readiness (`ok` / `starting` / `stopping`)     | ტრივიალური (მხოლოდ ფაზის დროშა)                 | კუბერნეტები** მზადყოფნა** ; რბილი** სიცოცხლისუნარიანობა** თუ თქვენ უნდა გამოიყენოთ HTTP |
| `GET /api/monitoring/health` | ღრმა სისტემის + პროვაიდერის შეჯამება (DB, გროვა, კატალოგის რაოდენობა,…) | მძიმე (სინქრონიზაცია DB / მონიტორინგის სამუშაო) | დაფები, შავი ყუთის ღრმა შემოწმება, Docker ს ჩაშენებული ჯანმრთელობის შემოწმება           |

> **შენიშვნა:** პროვაიდერის ჯანმრთელობის მატრიცები, ავტოპილოტის საკითხები, კვოტების მონიტორები, ნიშნების ჯანმრთელობა და შეყოვნების დეტალები `/api/monitoring/health` მიღმა ხელმისაწვდომია**MCP ინსტრუმენტი** `observability_snapshot` ან** დაფა** გვერდებზე — არ არის გამოყოფილი REST მარშრუტები მათთვის.

ორივე მარშრუტი გადის** იგივე კვანძის მოვლენის ციკლი** როგორც მოთხოვნის დამუშავება. CPU-ით მიბმული გზა (დიდი `GET /v1/models` კატალოგის მუშაობა, გრძელი კონტექსტის შეკუმშვა / ჟეტონების დათვლა) შეიძლება შეფერხდეს** ყველა** HTTP დამმუშავებლები, მათ შორის `/healthz`. Event-loop დაკავებული ≠ პროცესი მკვდარია. ურჩევნია ღორის დაფიქსირება; ზონდის დარეგულირება მხოლოდ ამცირებს ცრუ მკვლელობებს.

### მსუბუქი ორკესტრის ზონდი

```bash
GET /healthz
# or HEAD /healthz
```

- **200** + body `ok` როდესაც სერვერის სასიცოცხლო ციკლის ფაზა მზად არის
- **503** + `starting` / `stopping` ჩატვირთვის ან გამორთვის დროს
- განხორციელება: `src/app/healthz/route.ts` ( DB ping არ არის)

#### `credentialHealth`: probe-cache vs SQLite `test_status`

`GET /api/monitoring/health` → `credentialHealth` არის** მეხსიერების ზონდი-ქეში ლიანდაგი** , არ არის ცოცხალი ნაგავსაყრელი `provider_connections.test_status`. #12532 შემდეგ მოთხოვნის გზა იკითხება მხოლოდ `getCachedCredentialHealthSummary()` ; ფონური ზონდები განაახლებს ქეშს მოვლენის ციკლიდან.

| ფენა                         | სად                                                                   | რას ნიშნავს                                                                                                                                                                                                                   |
| ---------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ზონდ-ქეშის ლიანდაგი          | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | ბოლო სერთიფიკატები-ჯანმრთელობის გამოძიების შედეგები ჯერ კიდევ ინახება პროცესის მეხსიერებაში. `source` ყოველთვის არის `probe-cache`.                                                                                           |
| კავშირის დეტალი ვერ მოხერხდა | `credentialHealth.failedConnections`                                  | აწმყო** მხოლოდ მაშინ, როდესაც `failed > 0`** . ქეში რიგების შემოსაზღვრული სია `status=error` ით (`connectionId`, `status`, გაწმენდილი `lastError` / `lastErrorType`). `failedOmitted` არის დაყენებული, როდესაც სია დახურულია. |
| SQLite წებოვანი სტატუსი      | `credentialHealth.staleDbNonOkCount`                                  | რაოდენობა** აქტიური** (`is_active=1`) კავშირის რიგები, რომელთა შენარჩუნებული `test_status` არის ცნობილი არა-ok (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`).                             |

ორი ფენა შეიძლება არ ეთანხმებოდეს მიზანმიმართულად:

- გაზომეთ `failed=0` ხოლო `staleDbNonOkCount>0` — SQLite ჯერ კიდევ აქვს წებოვანი `test_status` (მაგალითად `expired` ან `credits_exhausted`), რომელიც უახლესი ზონდის ქეშის სნეპშოტი არ ითვლება `status=error`.
- გაზომეთ `failed>0` ხოლო SQLite გამოიყურება ჯანსაღად — ბოლო ზონდი ვერ მოხერხდა და ქეშირებულია; DB მწკრივი არ განახლებულა ან მოგვიანებით გასუფთავდა.

არ გააფრთხილოთ მხოლოდ `provider_connections.test_status` ზე ამ ბოლო წერტილის გაფხეკისას. გამოიყენეთ `failed` + `failedConnections` ცოცხალი ზონდის უკმარისობისთვის და `staleDbNonOkCount`, როდესაც გჭირდებათ მუდმივი წებოვანი სტატუსის რაოდენობა.

### Kubernetes-ის გამოძიების რეკომენდაციები

OmniRoute არის ა** ერთი კვანძის პროცესი** (ერთი მოვლენის ციკლი). საფონდო Docker `HEALTHCHECK` მიზნად ისახავს მსუბუქ `/healthz`. `/api/monitoring/health` არის** ძალიან მძიმე** კუბელეტის სიცოცხლისუნარიანობის ინტერვალებისთვის.

| ზონდი                   | რეკომენდებული სამიზნე                                                             | შენიშვნები                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **სტარტაპი**            | HTTP `GET /healthz` გრძელი `failureThreshold` ით (ან დიდი `startPeriod`)          | ცივი დაწყება + SQLite მიგრაცია შეიძლება აღემატებოდეს რამდენიმე წამს                                                                                                                                                                                                                                                                                                                         |
| **მზადყოფნა**           | HTTP `GET /healthz`                                                               | სიცოცხლის ციკლი `ok` / `starting` / `stopping` (200 vs 503). კვლავ იკეცება, თუ მარყუჟი დაბლოკილია CPU-ით. ა** 200 რამდენიმე წამში არ არის ჯანსაღი** (#10303) — ეს ნიშნავს, რომ მოვლენის ციკლი შიმშილობდა 3-ბაიტიანი დამმუშავებლის გაშვებამდე                                                                                                                                                |
| **სიცოცხლისუნარიანობა** | HTTP `GET /livez`,** ან TCP** მთავარ სერვის პორტზე (`PORT`, ნაგულისხმევი `20128`) | `/livez` არის მხოლოდ პროცესის ცოცხალი (ყოველთვის 200, თუ დამმუშავებელი მუშაობს). ის მაინც იზიარებს მოვლენის მარყუჟს — დაკავებულია ≠ dead, და ის არ ავლენს მოვლენის მარყუჟის შიმშილს (#10303) უკეთესად, ვიდრე TCP. ურჩევნია**TCP** თუ HTTP გამოკვლევების დრო ამოიწურება catalog/compression დატვირთვის ქვეშ; გააკეთე** არა** მოკლე მოვლენის მარყუჟის სადგომებზე მოკვლა ნებისმიერ შემთხვევაში |
| **ღრმა ჯანმრთელობა**    | `GET /api/monitoring/health` გარე გამშვებიდან                                     | არა kubelet `livenessProbe` / მჭიდრო `readinessProbe`                                                                                                                                                                                                                                                                                                                                       |

მაგალითის ფორმა (ზღვრების დარეგულირება ცივი დაწყების და შეკუმშვის დატვირთვაზე):

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # Under event-loop stall HTTP /livez can still time out. TCP is the
  # conservative alternative:
  # tcpSocket:
  #   port: http
```

**ნუ** წერტილი kubelet** სიცოცხლისუნარიანობა** `/api/monitoring/health`. ეს გზა ასრულებს რეალურ DB/monitoring მუშაობას და იქნება ცრუ დადებითი დატვირთვის ქვეშ.

დაკავშირებული: [#10052](https://github.com/cheaper-inference/OmniRoute/issues/10052) (გამოკვლევები, როდესაც მოვლენის მარყუჟი დაკავებულია), [#9685](https://github.com/cheaper-inference/OmniRoute/issues/9685) / [#10055](https://github.com/cheaper-inference/OmniRoute/pull/10055) (კატალოგის ფასების hog), [#10117](https://github.com/cheaper-inference/OmniRoute/issues/10117) (შეკუმშვის ტოკენის დათვლის hog).

### systemd watchdog (გაყინული მოვლენის ციკლი)

სისტემურ ჰოსტზე, OmniRoute ეუბნება სერვის მენეჯერს, როდის არის ის მზად და აგრძელებს მის პინგს, ასე რომ სერვერი, რომლის ღონისძიების მარყუჟი შეჩერებულია, კლავს და გადაიტვირთება იმის ნაცვლად, რომ დარჩეს და ჩუმად. პინგები მომდინარეობს სერვერის საკუთარი მოვლენის მარყუჟიდან: როდესაც ის იბლოკება, ისინი ჩერდებიან და systemd განაახლებს სერვისს, როგორც კი `WatchdogSec` გადის ერთის გარეშე.

[`omniroute autostart enable`](../../bin/cli/tray/autostart.mjs) უკვე წერს მომხმარებლის ერთეულს ამით. ერთეული, რომელსაც თავად წერთ (ნაგულისხმევი `Type=simple`) არ იღებს დამკვირვებელს, ამიტომ დაამატეთ ეს სტრიქონები მის `[Service]` განყოფილებაში:

```ini
[Service]
Type=notify
NotifyAccess=all
WatchdogSec=180
TimeoutStartSec=300
```

გენერირებული ერთეული აყენებს `Restart=on-failure`, ასე რომ დაამატეთ ეს ხაზიც — მის გარეშე, დამკვირვებელი მხოლოდ კლავს ჩარჩენილ სერვისს მისი გადატვირთვის ნაცვლად.

- `Type=notify`: სერვისი "იწყება", როდესაც სერვერი აგზავნის `READY=1` და არა პროცესის ჩანგლის დროს. `TimeoutStartSec` ზღუდავს ნელ დაწყებას.
- `NotifyAccess=all`: პინგები იგზავნება სერვერის პროცესით, რომელიც არის `omniroute serve` ხელმძღვანელის შვილი.
- `WatchdogSec`: პინგები გადის ყოველ 60 წამში, ამიტომ გამოიყენეთ** 120 ან მეტი** . მცირე მნიშვნელობები განაახლებს ჯანსაღ სერვერს.
- გაუშვით `omniroute serve` წინა პლანზე. `--daemon` აშორებს სერვერს ერთეულის cჯგუფიდან და შეტყობინებების ხელის ჩამორთმევა არასოდეს სრულდება.

შეამოწმეთ, რომ ის აქტიურია გადატვირთვის შემდეგ:

```bash
systemctl --user show omniroute -p WatchdogUSec -p WatchdogTimestamp
```

`WatchdogUSec` აჩვენებს კონფიგურირებულ შეფერხებას და `WatchdogTimestamp` ყოველ წუთს წინ მიიწევს. დამკვირვებლის მიერ გამოწვეული გადატვირთვა ჩაწერილია როგორც `Result=watchdog`. იმისათვის, რომ გამორთოთ პინგები, სანამ მოწყობილობას ისეთად ინახავთ, დააყენეთ `OMNIROUTE_DISABLE_SD_NOTIFY=1`; `NOTIFY_SOCKET` გარეშე (ტერმინალი, Docker, Electron, Windows) არაფერი იგზავნება.

დამკვირვებელი მხოლოდ ამოწმებს, რომ ღონისძიების მარყუჟი განაგრძობს მუშაობას. სერვერი, რომელიც ნელია, მაგრამ მაინც ბრუნავს, არ გადაიტვირთება.

### სურვილისამებრ მოთხოვნის გზაზე მუშაობა (მეხსიერება, უნარები, ნიშნების განახლება)

> **REST საბოლოო წერტილი არ არსებობს.** ავტოპილოტის პრობლემები ხელმისაწვდომია MCP ინსტრუმენტის `observability_snapshot` ან მართვის პანელის მეშვეობით. ავტოპილოტი შიდა რეჟიმში მუშაობს; მისი ქცევა კონფიგურირდება პარამეტრების მონაცემთა ბაზის მეშვეობით (თითოეული კავშირის `autopilotMode` ველი) და არა გარემოს ცვლადებით — ავტოპილოტის რეჟიმის გარემოს ცვლადის მოსაძებნად `grep -rn` ნულ შედეგს აბრუნებს.

## პრობლემების აღმოფხვრა

### „პროვაიდერი მიუთითებს, რომ გამართულად მუშაობს, მაგრამ მოთხოვნები ვერ სრულდება“

2. კონკრეტული შეცდომის კლასის სანახავად გადახედეთ **ბოლო შეცდომებს**

4. შეამოწმეთ, ხომ არ არის პროვაიდერი **ზედა დონეზე სიხშირით შეზღუდული** (ლოკალურად არ ჩანს)

### „კვოტა მიუთითებს, რომ ყველაფერი გამართულადაა, მაგრამ ვხედავ 429 შეცდომებს“

- 429 ნიშნავს, რომ პროვაიდერის მიხედვით თქვენი კვოტა ამოწურეთ
- OmniRoute-ის კვოტის აღრიცხვა შეიძლება **მოძველებული** იყოს — ჭეშმარიტი მონაცემები პროვაიდერთანაა
- კვოტის მონაცემები ავტომატურად ახლდება კვოტის შიდა მონიტორის საშუალებით

### „კომბინაცია ვერ მუშაობს, თუმცა ყველა სამიზნე გამართულად გამოიყურება“

- სამიზნეების მიმდევრობასთან დაკავშირებული პრობლემების სანახავად შეამოწმეთ **კომბინაციის მდგომარეობის** მართვის პანელი
- გადახედეთ **სარეზერვო გადართვის მოვლენებს** — შესაძლოა, კომბინაცია ვარიანტებს ზედმეტად სწრაფად ამოწურავს
- დარწმუნდით, რომ **სტრატეგია** შეესაბამება თქვენს გამოყენების შემთხვევას (პრიორიტეტული, ციკლური ან ავტომატური)

### „მონაცემთა ბაზის მდგომარეობის შემოწმება ვერ სრულდება“

- გაუშვით `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"`
- თუ შედეგია „ok“ — ეს ცრუ განგაშია და მდგომარეობის შემოწმება ზედმეტად მკაცრია
- ნებისმიერი სხვა შედეგის შემთხვევაში — **გააჩერეთ OmniRoute** და მიჰყევით [კატასტროფის შემდეგ აღდგენის სახელმძღვანელოს](./DATABASE_GUIDE.md#disaster-recovery)

### „მეხსიერების გროვაზე დატვირთვა კრიტიკულია“

```bash
# მიმდინარე გროვის შემოწმება
node -e "console.log(process.memoryUsage())"

# მეხსიერების ხელით გაწმენდის გაშვება (თუ გამოყენებულია --expose-gc)
node --expose-gc -e "global.gc(); console.log(process.memoryUsage())"

# ერთდროული მოთხოვნების რაოდენობის შემცირება (დააყენეთ მართვის პანელის Settings გვერდიდან და არა გარემოს ცვლადით)
# `MAX_CONCURRENT_REQUESTS` გარემოს ცვლადი არ არსებობს — დააკონფიგურირეთ Settings → Concurrency განყოფილებაში.
```
