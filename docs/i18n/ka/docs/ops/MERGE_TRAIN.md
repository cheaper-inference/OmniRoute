## დაშვება გამოშვების ტოტზე

omni-რიგი მართავს დაშვებას `release/vX.Y.Z` ში. წაიკითხეთ ზედა დონის `mode` `config/merge-queue/config.json` ში ნაგულისხმევ ფილიალში PR დაშვებამდე. იხილეთ [Omni-Queue](OMNI_QUEUE.md).

- **`shadow`** აწარმოებს ვალიდაციას და ტოვებს სადესანტო შერწყმას ხელით. გამოიყენეთ `omni-queue` დამტკიცებულ PR ზე მის საბოლოო თავში. შეამოწმეთ შესაბამისობა `npm run queue -- why <PR>` ით. დაელოდე განაჩენს იმ ხელმძღვანელისთვის `npm run queue -- history --base <branch>`. გააგრძელეთ `would-land`. `culprit-found` ზე ან `would-dequeue` ზე, გააჩერეთ შერწყმა და დააფიქსირეთ მიზეზი.
- **ჩრდილოვანი გამონაკლისები.** მატარებელი მწვანე სრული CI ით მიმდინარე საბაზისო წვერით შეიძლება გაგრძელდეს ცალკეული რიგის განაჩენის გარეშე. იგივე გამონაკლისი გამოიყენება, როდესაც PR ხელმძღვანელი უკვე შეიცავს მიმდინარე ბაზის წვერი.
- **`live`** იყენებს `omni-queue` ეტიკეტს დაშვების გასააქტიურებლად. რიგს მარტო ეშვება PR. დატოვეთ შერწყმის ბრძანებები და პირდაპირ უბიძგებს რიგში.

ყოველი დაშვება მოითხოვს მფლობელის ავტორიზაციას და შესაბამის აუცილებელ შემოწმებას. გამოიყენეთ `omni-queue` მხოლოდ მას შემდეგ, რაც მფლობელი დაშვების უფლებას მისცემს. რიგი PRs დაცულ ბილიკებთან შეხება ასევე მოითხოვს მფლობელის `protected-approved` გადაწყვეტილებას ამ PR სთვის.

"მოითხოვს მწვანე კარიბჭე აქტიურ გამოშვებას" წესები მოითხოვს მწვანე `Gate / CI` და `Gate / Quality` თავზე. არასოდეს გამოიყენოთ `--admin` წითელი კარიბჭის გვერდის ავლით. გათავისუფლების გაყინვის ბლოკები გაერთიანებულია გაყინულ ტოტში. იხილეთ [მძიმე წესი 21](HARD_RULES_DETAIL.md). არასოდეს მიანიშნოთ ლეიბლი, შერწყმა და არ დააყენოთ pull მოთხოვნა, რომ სხვა სესია მუშაობს. იხილეთ [მძიმე წესი 22](HARD_RULES_DETAIL.md).

## მატარებლის გაყვანის მოთხოვნა

1. დაიწყეთ მატარებლის ფილიალი მიმდინარე გამოშვების ბაზის წვერით. ზუსტი დამტკიცებული წევრების ხელმძღვანელების ინტეგრირება შერწყმის ვალდებულებების გამოყენებით. შეინახეთ მათი ჩადენის ისტორია სკვოშისა და რებაზის თავიდან აცილებით.
2. გახსენით ერთი გაყვანის მოთხოვნა მატარებლის ფილიალისთვის. დაადასტურეთ ეს PR თავისი სრული CI ით მიმდინარე ბაზის წვერიზე. დაშვებამდე გადაამოწმეთ ბაზის წვერი და დამტკიცებული წევრების თავები. განაახლეთ მატარებელი და მისი CI როდესაც დადასტურებული კანდიდატი შეიცვლება.
3. ჩამოდით მატარებელი PR შერწყმის ჩადენით მოქმედი რიგის რეჟიმში. ლაივ რეჟიმში, რიგის `merge-ff` დაშვების მეთოდი ინარჩუნებს შერწყმის ვალდებულებებს. თავდაპირველი წევრების თავები ხელმისაწვდომი ხდება გამოშვების ფილიალიდან. GitHub აღნიშნავს წევრს PRs როგორც გაერთიანებულს და ვალდებულებები ინარჩუნებენ ავტორებს.

საჯარო მაგალითია [PR #21071](https://github.com/cheaper-inference/OmniRoute/pull/21071). მან გააერთიანა 18 წევრი PRs და დაეშვა შერწყმის ვალდებულებით 2026-11-24.

სინქრონიზაცია `main` დან მომდევნო გამოშვების ფილიალზე ასევე მიდის შერწყმის კომითის მეშვეობით. `main` წინაპრების შენარჩუნება საჭიროა შემდგომი სინქრონიზაციისთვის. იხილეთ [სამუშაო ხეების იზოლაცია](WORKTREE_ISOLATION.md#sync-back-landings-are-merge-commits-never-squash).

## ადგილობრივი შერწყმის მატარებლის ვალიდატორი

```bash
scripts/release/merge-train.sh [--plan] [--fast] <base-branch> <PR#> [<PR#>...]
```

ვალიდატორი იღებს საფუძველს და PR თავებს და აერთიანებს მათ ერთჯერად სამუშაო ხეში. იგი აწარმოებს თავის პარიტეტულ კომპლექტს ერთხელ მიღებულ ხეზე. წარუმატებელი ხელმძღვანელის მოძიება ან შერწყმის კონფლიქტი ამოიღებს ამ PR და სკრიპტი გრძელდება დარჩენილი PRs ით.

- **`--plan`** ბეჭდავს არჩეული რეჟიმის ნაბიჯებს და გამოდის სამუშაო ხის შექმნისა და დისტანციურთან დაკავშირების გარეშე. შეუთავსეთ იგი `--fast` სწრაფი გეგმის შესამოწმებლად.
- **`--fast`** აწარმოებს საერთო სტატიკური კარიბჭეებს, არჩეულ შეცვლილ `node:test` ფაილებს `tests/unit/`, და `npm run test:vitest`. განახორციელეთ სრული ლოკალური ვალიდაცია დღეში ერთხელ მაინც დაგროვილ წვერიზე სწრაფი რეჟიმის გამოყენებისას.
- **სრული რეჟიმი** ამატებს მხოლოდ სტატიკური კარიბჭეებს და აწარმოებს `npm run test:unit` და `npm run test:vitest`.

წარუმატებელი სტატიკური კარიბჭე ხელახლა გაიშვება ხელუხლებელ ბაზაზე, თუ ბაზის ზონდი ხელმისაწვდომია. სკრიპტი იტყობინება მემკვიდრეობით წარუმატებლობებს და გრძელდება, როდესაც ყველა აღიარებული დარღვევის ხაზი ასევე გამოჩნდება ბაზაზე და მთლიანი რაოდენობა არ გაიზარდა.

| გასვლა | მნიშვნელობა                                                                                                                                                           |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`    | დაბეჭდა გეგმა ან დაასრულა კომპლექტი. კომპლექტის შეჯამება ჩამოთვლილია ნებისმიერი მემკვიდრეობითი სტატიკური წარუმატებლობისა და ამოღებული PRs.                            |
| `1`    | არასწორი არგუმენტები, Git-ის გადახდა, წარუმატებელი ფრენა ან PR ჩასხდომის გარეშე.                                                                                      |
| `2`    | კომპლექტის შემოწმება ვერ მოხერხდა და არ კვალიფიცირდება, როგორც მემკვიდრეობითი. ოპერატორს შეუძლია ნახევრად გაყოს პარტია, ამოიღოს შეურაცხმყოფელი PR და ხელახლა გაუშვას. |

ადგილობრივი საშვი აწვდის სადიაგნოსტიკო მტკიცებულებებს მხოლოდ მფლობელის დოსიისთვის. ყოველი დაშვება კვლავ მოითხოვს მფლობელის ავტორიზაციას, მის საჭირო შემოწმებას და ჩრდილოვანი რიგის განაჩენს, როდესაც ეს შესაძლებელია.

## Tiering

- **პერ PR.** CI და Quality აირჩიეთ შემოწმებები შეცვლილი ბილიკების საფუძველზე. Code PRs აწარმოებს სწრაფი ხარისხის კარიბჭეებს და ზემოქმედების ტესტებს, ცალკეული ერთეულისა და Vitest სამუშაოებით CI ში.
- **თითო რიგში კანდიდატი.** CI და Quality აწარმოებენ შედგენილი კანდიდატის სრულ პროფილს მის რიგზე.
- **თითო გამოშვების წვერი.** Release-Green აწარმოებს სწრაფ მყარ კარიბჭეს ბიძგებზე, რომლებიც ემთხვევა მის ბილიკების ფილტრებს. დღეში სამი დაგეგმილი გაშვება იყენებს სრულ წმენდას გამოშვების ფილიალისთვის.
- **თითო გამოშვება.** სრული CI მატრიცა მოიცავს E2E ფრაგმენტებს, პაკეტის ვალიდაციას, ტარბოლის ჩექმის კვამლს და დაფარვის შემოწმებებს. იხილეთ [გამოშვების ჩამონათვალი](RELEASE_CHECKLIST.md).

## ახალი შეკვეთის წინაპირობები `merge-train.sh` სთვის

ფრენის წინ გადის სამუშაო ხეების შექმნამდე. დააინსტალირეთ დამოკიდებულებები `npm ci` სთან ერთად. დაადასტურეთ, რომ `node_modules/.bin/tsc` შესრულებადია და რომ `node_modules/node_modules` არ არის. შეამოწმეთ, რომ `node_modules/.bin/bun --version` წარმატებულია.

თუ Bun postinstall გამოტოვებულია, გაუშვით `(cd node_modules/bun && node install.js)`. პროვაიდერის თანმიმდევრულობა და ცნობილი სიმბოლოების შემოწმებები იყენებს Bun. ვალიდატორი მუშაობს `npm run check:cycles:ratchet` როგორც ბლოკირების კარიბჭე. დამოუკიდებელი `npm run check:cycles` ბრძანება საკონსულტაციოა.
