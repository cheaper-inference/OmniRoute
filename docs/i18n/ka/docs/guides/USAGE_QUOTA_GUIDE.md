> **TL;DR**: OmniRoute აღრიცხავს თითოეული მოთხოვნის ტოკენების გამოყენებას, ითვლის ღირებულებას, აღასრულებს თითოეული API გასაღებისთვის განსაზღვრულ კვოტას და ანალიტიკას მართვის პანელში აჩვენებს. ეს სახელმძღვანელო განმარტავს, როგორ მუშაობს ეს ყველაფერი.

**წყაროები:**

- `open-sse/services/usage.ts` (~70KB) — გამოყენების ძირითადი აღრიცხვა
- `src/lib/usageAnalytics.ts` (~10KB) — მონაცემების აგრეგაცია მართვის პანელისთვის
- `src/lib/db/quotaSnapshots.ts` — კვოტის ისტორიული მონაცემები
- `src/lib/db/usage*.ts` — გამოყენებასთან დაკავშირებული მონაცემთა ბაზის რამდენიმე მოდული

## მიმოხილვა

OmniRoute-ში გამავალი თითოეული მოთხოვნა ქმნის **გამოყენების ჩანაწერს**, რომელიც მოიცავს:

- **იდენტიფიკაციას**: რომელი API გასაღები, პროვაიდერი, მოდელი და კომბინაცია გამოიყენებოდა
- **ტოკენებს**: პრომპტის ტოკენები, დასრულების ტოკენები, ქეშირებული ტოკენები და ჯამური რაოდენობა
- **ღირებულებას**: თანხა აშშ დოლარში (გამოთვლილი ფასების მონაცემების საფუძველზე)
- **დროით მონაცემებს**: დაყოვნებას, დაწყებისა და დასრულების დროის ნიშნულებს
- **სტატუსს**: წარმატება, შეცდომა, სიხშირის შეზღუდვა და სხვ.

ეს ჩანაწერები ერთიანდება **ანალიტიკურ მონაცემებად**, ინახება **კვოტის სნეპშოტების** სახით და გამოიყენება **თითოეული გასაღებისთვის განსაზღვრული ბიუჯეტის ლიმიტების** აღსასრულებლად.

```
მოთხოვნა ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    ანალიტიკა   კვოტა   ბილინგი
                 (მართვის პანელი) (აღსრულება) (ექსპორტი)
```

## რა აღირიცხება

`usage.ts` სერვისი ყოველი მოთხოვნისთვის აფიქსირებს **გამოყენების მოვლენას**:

| ველი               | ტიპი    | წყარო                                                               |
| ------------------ | ------- | ------------------------------------------------------------------- |
| `id`               | string  | ჩანაწერის შექმნისას გენერირებული UUID                               |
| `apiKeyId`         | string  | API გასაღები, რომლითაც მოთხოვნა ინიციირდა                           |
| `provider`         | string  | პროვაიდერის ID (openai, anthropic და სხვ.)                          |
| `model`            | string  | მოდელის ID (gpt-5, claude-opus-4-6 და სხვ.)                         |
| `comboId`          | string? | კომბინაციის ID, თუ მარშრუტიზაცია კომბინაციის გავლით მოხდა           |
| `promptTokens`     | number  | ზედა დონის პროვაიდერის პასუხიდან                                    |
| `completionTokens` | number  | ზედა დონის პროვაიდერის პასუხიდან                                    |
| `cachedTokens`     | number  | ქეშიდან წაკითხული ტოკენები (Anthropic-ის პრომპტის ქეშირება და სხვ.) |
| `totalTokens`      | number  | პრომპტი + გენერირებული პასუხი                                       |
| `costUsd`          | number  | გამოთვლილია ფასების მონაცემებიდან                                   |
| `latencyMs`        | number  | მოთხოვნის სრული ხანგრძლივობა                                        |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`          |
| `errorClass`       | string? | შეცდომის კლასი, თუ სტატუსი != success                               |
| `timestamp`        | string  | ISO 8601 UTC                                                        |
| `metadata`         | object  | დანამატის მიერ ჩასმული მორგებული მონაცემები                         |

### საიდან მიიღება ტოკენები

ტოკენები ამოიღება ზედა დონის პროვაიდერის პასუხიდან **პასუხის დამმუშავებელში**:

```ts
// წყარო: open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

პროვაიდერებისთვის, რომლებიც გამოყენების მონაცემებს არ აბრუნებენ (ზოგიერთი ვებქუქიზე დაფუძნებული პროვაიდერი), OmniRoute ტოკენების რაოდენობას **აფასებს** `~4 chars per token` ევრისტიკის გამოყენებით (იხილეთ `open-sse/services/autoCombo/pipelineRouter.ts`).

### ქეშირებული ტოკენები

OmniRoute `cached_tokens`-ს `prompt_tokens`-ისგან განცალკევებით აღრიცხავს, რადგან:

- Anthropic-ის პრომპტის ქეშირებისას ქეშირებული ტოკენებისთვის მოქმედებს შემცირებული ტარიფი (ჩვეულებრივის 10%)
- ზოგიერთი პროვაიდერი აბრუნებს `cache_read_input_tokens`-ს, რომლის ღირებულებაც განსხვავებულად უნდა გამოითვალოს
- ანალიტიკას შეუძლია აჩვენოს **ქეშის გამოყენების წილი** = `cached_tokens / prompt_tokens`

### ქეშში ჩაწერის დონის დიაგნოსტიკა

ანალიტიკის დაფის პრომპტის ქეშის მდგომარეობის პანელი განასხვავებს პროვაიდერის მიერ მოწოდებულ
5-წუთიან და 1-საათიან ქეშში ჩაწერებს. Anthropic-ის
`usage.cache_creation.ephemeral_5m_input_tokens` და
`usage.cache_creation.ephemeral_1h_input_tokens` შენარჩუნებულია გამოყენების მონაცემების როგორც ნაკადური, ისე
არანაკადური გარდაქმნისას და ინახება გამოძახებების ჟურნალის შეჯამებებთან ერთად. ქეშში ჩაწერის ჯამური
რაოდენობა ამ კატეგორიებს მეორედ აღარ ემატება.

გამოძახებებს, რომლებსაც მხოლოდ ჩაწერის ჯამური მრიცხველი აქვთ, ძველი ჩანაწერების ჩათვლით, უცნობი
დონე ენიჭება. ნაწილობრივი დაყოფისას გაუნაწილებელი ნაშთი უცნობად რჩება; არასწორი ან
ურთიერთგამომრიცხავი მრიცხველები მოინიშნება და მათ TTL ჩუმად არ ენიჭება. მოთხოვნის მხარეს არსებული
TTL მარკერები დარიცხული დონის მტკიცებულება არ არის.

პანელის API-ეკვივალენტური ჩაწერის ღირებულების შეფასება მოიცავს მხოლოდ მოწოდებულ, ფასის მქონე დონეებს და არა
მთელ მოთხოვნას. Claude/Anthropic-ის მოდელების მშობლიური ფასების შემთხვევაში იგი 5-წუთიანი ჩაწერებისთვის იყენებს
შემავალი ტოკენების ტარიფის 1.25-მაგ მნიშვნელობას, ხოლო 1-საათიანი ჩაწერებისთვის — ორმაგს. არარსებული
ფასი მიუწვდომლად ითვლება და არა ნულად. ფასები ფიქსირდება ყოველი ახალი გამოძახების ჟურნალში აღრიცხვისას;
ისტორიული ჩანაწერების ღირებულება ხელახლა არ ითვლება. შესაბამისად, სააბონენტო ანგარიშებს შეიძლება ჰქონდეთ
API-ეკვივალენტური შეფასება ისე, რომ ეს თანხა ფულად ხარჯად ან სააბონენტო
კვოტის მოხმარებად არ დაერიცხოთ. კვოტის, ბიუჯეტისა და პროვაიდერის ზუსტი ღირებულების არსებული გამოთვლები უცვლელია.

ეს დიაგნოსტიკა იყენებს ქეშის მდგომარეობის არსებულ, შეზღუდული მოცულობის შეჯამებასა და გამოძახებების ჟურნალის
შენახვის წესებს. ის არ ცვლის მოთხოვნის TTL-ის ნაგულისხმევ მნიშვნელობებს, მარშრუტიზაციას ან ანგარიშის არჩევას.
კლიენტის მიერ მოთხოვნილი TTL-ისა და რეალური გამავალი TTL-ის დაფიქსირება პროვაიდერთან გაგზავნის
საზღვარზე გადადებულია; ეს პანელი აჩვენებს ქვითარში დაფიქსირებულ დონეებს და არა რეალურ გამავალ TTL-ს.

იმპლემენტაცია: `src/lib/usage/cacheWriteEstimate.ts`,
`src/lib/usage/cacheHealth.ts` და `open-sse/utils/cacheWriteUsage.ts`.

## ღირებულების გამოთვლა

ღირებულება გამოითვლება LiteLLM-იდან სინქრონიზებული **ფასების მონაცემების** საფუძველზე (`src/lib/pricingSync.ts`):

| მოდელი            | შეყვანა $/1M | გამოყვანა $/1M | კეშირებული $/1M |
| ----------------- | ------------ | -------------- | --------------- |
| gpt-5             | $2.50        | $10.00         | —               |
| claude-opus-4-6   | $15.00       | $75.00         | $1.50           |
| claude-sonnet-4-5 | $3.00        | $15.00         | $0.30           |
| gemini-2.5-pro    | $1.25        | $10.00         | —               |

ღირებულების ფორმულა (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **რატომ აკლდება კეშირებული ტოკენები მოთხოვნის ტოკენებს?** კეშირებული ნაწილი ცალკე ფასდება; შეყვანის ფასის მთელ მოთხოვნაზე დარიცხვა ღირებულების გადაჭარბებულად დათვლას გამოიწვევდა.

### ფასების სინქრონიზაცია

ფასების მონაცემები ავტომატურად სინქრონიზდება LiteLLM-იდან `/api/pricing/sync` ბოლო წერტილის მეშვეობით (ამოქმედდება ჩაშენებული cron ამოცანით და არა მომხმარებლისთვის განკუთვნილი გარემოს ცვლადით):

```bash

```

მოდელებისთვის, რომლებისთვისაც ფასების მონაცემები არ არსებობს, OmniRoute ღირებულების **შეფასებისთვის** იყენებს შიდა საშუალო ტარიფებს (რომლებიც LiteLLM-ის ფასების მონაცემებიდანაა მიღებული).

## კვოტის აღსრულება

თითოეული API გასაღების კვოტა ორ ადგილას კონტროლდება:

1. **რბილი ლიმიტი** (`quotaWarnAt`): გაფრთხილება მართვის პანელზე, როდესაც გამოყენება ზღვარს აჭარბებს
2. **მკაცრი ლიმიტი** (`quotaLimit`): გადაჭარბებისას მოთხოვნა უარყოფილია HTTP 429 კოდით

### კონფიგურაცია

```ts
// თითოეული API გასაღებისთვის
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — გაფრთხილების ჩვენება
  quotaLimit: 10_00,    // $10.00 — სრული შეჩერება
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### აღსრულების პროცესი

```
მოთხოვნა ──▶ quotaCheck()
              │
              ├── ლიმიტის ფარგლებშია?  ──▶ დაშვება
              │
              └── ლიმიტს აჭარბებს?  ──▶ 429 მეტისმეტად ბევრი მოთხოვნა
                                   Retry-After სათაურით
```

### კვოტის მდგომარეობის ანაბეჭდები

`quotaSnapshots` ცხრილი ინახავს **კვოტის ისტორიულ მდგომარეობას** ტენდენციების ანალიზისთვის:

| ველი | აღწერა |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | გასაღები, რომლის მონიტორინგიც მიმდინარეობს |
| `window` | "დღე" | "კვირა" | "თვე" |
| `used` | ამ პერიოდში გაწეული ხარჯი (ცენტებში) |
| `limit` | ლიმიტი (ცენტებში) |
| `resetAt` | როდის განულდება პერიოდი |
| `createdAt` | როდის შეიქმნა მდგომარეობის ანაბეჭდი |

მდგომარეობის ანაბეჭდები იქმნება **ყოველი მოთხოვნისას**, რომლის ხარჯიც > 0-ია, და გამოიყენება შემდეგი მიზნებისთვის:

- მართვის პანელზე კვოტის პროგრესის ზოლის გამოსახვა
- კვოტის 30-დღიანი ტენდენციის დიაგრამების ჩვენება
- შეტყობინებების გააქტიურება, როდესაც გამოყენება ლიმიტს უახლოვდება

## პრობლემების მოგვარება

### "ხარჯი მოსალოდნელზე მაღალია"

1. შეამოწმეთ **`/api/usage/analytics?groupBy=model`** — იპოვეთ ძვირადღირებული მოდელი
2. შეამოწმეთ **`/api/usage/analytics?groupBy=apiKey`** — იპოვეთ ინტენსიური მომხმარებელი
3. გადაამოწმეთ, რომ ფასების მონაცემები განახლებულია: `POST /api/pricing/sync`

### "ჩანაწერები აკლია"

- შეამოწმეთ მონაცემთა ბაზის შენახვის ვადის პარამეტრები განყოფილებაში მართვის პანელი → მონაცემთა ბაზა → გასუფთავება — ძველი ჩანაწერები იშლება პერიოდული გასუფთავების ამოცანის მიერ (`src/lib/db/cleanup.ts`)
- შეამოწმეთ შეცდომები `src/lib/db/usage*.ts`-ში — მონაცემთა ბაზაში ჩაწერის წარუმატებლობები ჟურნალში აღირიცხება, მაგრამ მომხმარებელს არ ეჩვენება
- გადაამოწმეთ, რომ მოთხოვნამ ნამდვილად მიაღწია `chatCore`-ს — შეამოწმეთ კომბინირებული მარშრუტიზაცია

### "კვოტის შეზღუდვა არ მოქმედებს"

- შეამოწმეთ გასაღების `quotaLimit` პარამეტრი
- გადაამოწმეთ, რომ `quotaWindow` სწორად არის დაყენებული
- მოძებნეთ `quotaSnapshots` ჩანაწერები — ისინი ყოველ მოთხოვნაზე უნდა იქმნებოდეს
