## 🎯 გამოყენების შემთხვევები

### შემთხვევა 1: „მე მაქვს Claude Pro-ს გამოწერა“

**პრობლემა:** კვოტა გამოუყენებლად იწურება, ინტენსიური კოდირებისას კი მოქმედებს სიხშირის ლიმიტები

```
კომბინაცია: "maximize-claude"
  1. cc/claude-opus-4-7        (გამოწერის სრულად გამოყენება)
  2. glm/glm-4.7               (იაფი სარეზერვო ვარიანტი კვოტის ამოწურვისას)
  3. if/qwen3.8-max-preview       (უფასო საგანგებო სარეზერვო ვარიანტი)

თვიური ღირებულება: $20 (გამოწერა) + ~$5 (სარეზერვო ვარიანტი) = სულ $25
$20-ისა და ლიმიტების მიღწევით გამოწვეული იმედგაცრუების ნაცვლად
```

### შემთხვევა 2: „მსურს ნულოვანი ღირებულება“

**პრობლემა:** გამოწერების საფასურს ვერ ვწვდები და მჭირდება საიმედო AI კოდირებისთვის

```
კომბინაცია: "zero-cost"
  1. if/kimi-k2.7-code          (მითითებულია უფასო წვდომა; შესაძლოა მოქმედებდეს სიხშირის ლიმიტები)
  2. kr/qwen3-coder-next        (Kiro-ს უფასო სარეზერვო ვარიანტი)

თვიური ღირებულება: $0
ხარისხი: თქვენი სამუშაო დატვირთვისთვის გადაამოწმეთ მოდელი, ლიმიტები, კონფიდენციალურობა და SLA
```

სისტემურ პანელში მუშაობის რეჟიმი მხარდაჭერილია macOS-ზე, Windows-ზე და გრაფიკულ Linux-სესიებში. ამ რეჟიმში მართვის პანელი ავტომატურად არ იხსნება.

- გახსენით მართვის პანელი.
- გახსენით `/dashboard/logs`.
- შეცვალეთ ავტომატური გაშვების პარამეტრი.
- გააჩერეთ OmniRoute.

არ გამოიყენოთ `--tray` შემდეგ პარამეტრებთან ერთად:

- `--log`

ამ რეჟიმებს პროცესზე ფლობის განსხვავებული მოდელები სჭირდება.

### მორგებული მოდელები

დაამატეთ ნებისმიერი მოდელის ID ნებისმიერ პროვაიდერს აპლიკაციის განახლების ლოდინის გარეშე:

```bash
# API-ს მეშვეობით
curl -X POST http://localhost:20128/api/provider-models \
  -H "Content-Type: application/json" \
  -d '{"provider": "openai", "modelId": "gpt-5.2", "modelName": "GPT-5.2"}'

# ჩამონათვალი: curl http://localhost:20128/api/provider-models?provider=openai
# წაშლა: curl -X DELETE "http://localhost:20128/api/provider-models?provider=openai&model=gpt-5.2"
```

ან გამოიყენეთ მართვის პანელი (Dashboard): **პროვაიდერები → [პროვაიდერი] → მორგებული მოდელები**.

შენიშვნები:

- OpenRouter და OpenAI/Anthropic-თან თავსებადი პროვაიდერები მართვადია მხოლოდ **ხელმისაწვდომი მოდელებიდან**. ხელით დამატება, იმპორტი და ავტომატური სინქრონიზაცია ყველა ერთსა და იმავე ხელმისაწვდომი მოდელების სიაში ხვდება, ამიტომ ამ პროვაიდერებისთვის ცალკე „მორგებული მოდელების" განყოფილება არ არსებობს.
- **მორგებული მოდელების** განყოფილება განკუთვნილია იმ პროვაიდერებისთვის, რომლებსაც არ აქვთ მართვადი ხელმისაწვდომი მოდელების იმპორტი.

### მორგებული OpenAI-თან თავსებადი პროვაიდერები

ნებისმიერი გეიტვეი, რომელიც OpenAI API-ს ენაზე „საუბრობს" (თვითმასპინძლებული პროქსი, vLLM, მესამე მხარის აგრეგატორი), შეიძლება დაემატოს ცალკე პროვაიდერის კვანძად:

1. **პროვაიდერები → OpenAI-თან თავსებადის დამატება**.
2. **სახელი**: კვანძის საჩვენებელი ეტიკეტი.
3. **პრეფიქსი**: მარშრუტიზაციის სახელი. კლიენტები მოდელებს `<prefix>/<model>` ფორმით მიმართავენ, ამიტომ `mygw` პრეფიქსის მქონე კვანძი ემსახურება `mygw/gpt-4o-mini`-ს. სავალდებულოა; სიმბოლოებზე შეზღუდვა არ მოქმედებს.
4. **API-ს ტიპი**: ენდპოინტების ოჯახი, რომელსაც გეიტვეი ემსახურება (Chat Completions, Responses,
   Embeddings, აუდიო, სურათები).
5. **საბაზისო URL**: API-ს ფესვი, `/v1`-ის ჩათვლით (მაგალითად
   `https://gateway.example.com/v1`), და არა სრული `/chat/completions` ბილიკი. არასტანდარტული ბილიკების მქონე გეიტვეები მათ
   **დამატებით პარამეტრებში** (Advanced Settings) ადგენენ (chat-ის ბილიკი, მოდელების ბილიკი).
6. **API-ს გასაღები (შემოწმებისთვის)** ველი მხოლოდ კავშირს ამოწმებს. კვანძის შექმნის შემდეგ
   გახსენით იგი და გამოიყენეთ **კავშირის დამატება** იმ გასაღების შესანახად, რომელსაც მოთხოვნები გამოიყენებენ.

კვანძს ენიჭება შინაგანი id ფორმით `openai-compatible-<apiType>-<uuid>`; მისი აკრეფა არასოდეს
დაგჭირდებათ — პრეფიქსი არის საჯარო სახელი.

#### დაჯავშნული პრეფიქსები

პრეფიქსი ვერ იქნება ჩაშენებული პროვაიდერის id ან ფსევდონიმი (მაგალითად `openai`, `cf`) და არც
მოხსნილი პროვაიდერის id. მოდელის გამხსნელი (resolver) ჩაშენებულ id-ებსა და ფსევდონიმებს მორგებულ
კვანძებამდე ამოწმებს, ამიტომ ასეთი პრეფიქსებიდან რომელიმეს მქონე კვანძი ტრაფიკს არასოდეს მიიღებდა:
`<prefix>/model` ნაცვლად ჩაშენებულ პროვაიდერზე გადავიდოდა, ან მოთხოვნა დაცულად უარდებოდა (fail closed),
თუ ეს პროვაიდერი მოხსნილი იქნებოდა. ასეთი პრეფიქსით კვანძის შექმნა ან რედაქტირება უარდება შეტყობინებით:

```text
prefix: "<prefix>" is a reserved provider prefix — choose a different prefix (reserved ids/aliases cannot be used for custom nodes because requests like <prefix>/model route to a built-in provider or fail closed when retired)
```

აირჩიეთ გამორჩეული პრეფიქსი (`mygw`, `acme-proxy`). თუ მორგებულ კვანძზე მოთხოვნები ვერ სრულდება
შეცდომით, რომელიც ჩაშენებულ პროვაიდერს ან მის რწმუნებათსიგნებს ასახელებს, შეამოწმეთ, დაჯავშნული ხომ
არაა კვანძის პრეფიქსი: ამ წესის არსებობამდე შენახული კვანძები მაინც ინახება, მაგრამ მათი პრეფიქსი
ჩაშენებულ პროვაიდერზე მიმართავს. შეცვალეთ კვანძი და მიანიჭეთ მას ახალი პრეფიქსი.

#### კავშირის დონის გეიტვეის პარამეტრები

ეს გასაღებები თავსდება კავშირის `providerSpecificData`-ში (მაგალითად
`PUT /api/providers/{id}`-ით):

- `toolNameMaxLength` (მთელი რიცხვი, 1–1024) — OpenAI-ის chat-ფორმატის თავსებადი კავშირებისთვის,
  რომელთა გეიტვეიც გრძელ ინსტრუმენტის სახელებზე უარს ამბობს. უფრო გრძელი სახელები იგზავნება მოკლე
  ფსევდონიმებად და პასუხში ისევ აღდგება.
- `quotaEndpoint` — გეიტვეის კვოტის/კრედიტების ენდპოინტი, რომელიც იკითხება მართვის პანელის კვოტის
  ზოლისა და კვოტის გათვალისწინებით მარშრუტიზაციისთვის. მუშაობს როგორც OpenAI-, ისე Anthropic-თან

### OmniRoute-ის თანატოლების ჯაჭვური გაერთიანება

სხვა OmniRoute გეიტვეი შეიძლება დაემატოს როგორც **მორგებული OpenAI-თან თავსებადი** პროვაიდერი.
გამოიყენეთ თანატოლის `/v1` საბაზისო URL და ამ თანატოლის მიერ გაცემული გამოყოფილი, მინიმალური
უფლებების მქონე API-ს გასაღები.

ორმხრივი ან მრავალსაფეხურიანი (multi-hop) ჯაჭვებისთვის ჩართეთ მარყუჟის (loop) დაცვის ამორჩევითი
მექანიზმი ყველა გეიტვეიზე:

```bash
# gateway-a
OMNIROUTE_INSTANCE_ID=gateway-a
OMNIROUTE_PEER_URLS=http://gateway-b:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

```bash
# gateway-b
OMNIROUTE_INSTANCE_ID=gateway-b
OMNIROUTE_PEER_URLS=http://gateway-a:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

მხოლოდ ექსპლიციტურად ნებადართულ სიაში შეყვანილ თანატოლის URL-ზე გაგზავნილი მოთხოვნები იღებენ
`X-OmniRoute-Peer-Trace` თავსართს. განმეორებული instance ID-ს ან ამოწურული hop-ების ლიმიტის
შემთხვევაში გეიტვეი მოთხოვნას უარს ამბობს HTTP `508 Loop Detected`-ით; ჩვეულებრივი upstream
პროვაიდერები თანატოლის მეტამონაცემებს საერთოდ არ იღებენ.

თანატოლების ჯაჭვური გაერთიანება არ არის მონაცემთა ბაზის რეპლიკაცია ან ჰოსტის failover. თითოეული
გეიტვეი ინახავს დამოუკიდებელ SQLite მდგომარეობას, ქეშებს, მოთხოვნების სიხშირის მთვლელებსა და სესიებს.
აქტიური/პასიური ან აქტიური/აქტიური ხელმისაწვდომობისთვის გამოიყენეთ ჯანმრთელობის შემოწმების მქონე
შებრუნებული პროქსი (reverse proxy) ან კლიენტის failover და არასოდეს მიაერთოთ ერთი SQLite მონაცემთა
ბაზა რამდენიმე ერთდროულად გაშვებულ OmniRoute ინსტანციას.

### გამოყოფილი პროვაიდერის მარშრუტები

გააგზავნეთ მოთხოვნები პირდაპირ კონკრეტულ პროვაიდერზე მოდელის ვალიდაციით:


### Cloudflare Quick Tunnel

- ხელმისაწვდომია **Dashboard → Endpoints**-ში Docker-ისა და სხვა self-hosted განლაგებებისთვის
- ქმნის დროებით `https://*.trycloudflare.com` URL-ს, რომელიც გადამისამართებს თქვენს მიმდინარე OpenAI-თავსებად `/v1` ენდპოინტზე
- პირველი ჩართვისას `cloudflared`-ს ხელმისაძღვანელეთ მხოლოდ საჭიროებისამებრ; შემდეგი გადატვირთვები იყენებენ იმავე მართულ ბინარულ ფაილს
- Quick Tunnels არ აღდგება ავტომატურად OmniRoute-ის ან კონტეინერის გადატვირთვის შემდეგ; საჭიროებისამებრ თავიდან ჩართეთ დაფიდან
- ტუნელის URL-ები ეფემერულია და იცვლება ყოველ ჯერზე, როცა ტუნელს ჩერთავთ/ჩართავთ
- მართული Quick Tunnels ნაგულისხმევად იყენებს HTTP/2 ტრანსპორტს, რათა თავიდან აიცილოს ხმაურიანი QUIC UDP ბუფერის გაფრთხილებები შეზღუდულ კონტეინერებში
- დააყენეთ `CLOUDFLARED_PROTOCOL=quic` ან `auto`, თუ გსურთ გადაფაროთ მართული ტრანსპორტის არჩევანი
- დააყენეთ `CLOUDFLARED_BIN`, თუ არჩეული გაქვთ წინასწარ დაყენებული `cloudflared` ბინარული ფაილის გამოყენება მართული ჩამოტვირთვის ნაცვლად
- Cloudflare Quick Tunnel, Tailscale Funnel და ngrok Tunnel პანელები შეიძლება ნაჩვენები ან დამალული იყოს **Settings → Appearance**-ში. პანელის დამალვა არ აჩერებს მიმდინარე ტუნელს.

### LLM Gateway Intelligence (Phase 9)

- **სემანტიკური კეში** — ავტომატურად ინახავს non-streaming, temperature=0 პასუხებს (გვერდის ავლით `X-OmniRoute-No-Cache: true`)

### Routing Strategies

მოირგეთ **Dashboard → Settings → Routing**-ის მეშვეობით. დაფა აჩვენებს ექვს ყველაზე გამოყენებულ სტრატეგიას; კომბინაციები და ავტო-როუტერი შიგნით უფრო ფართო ნაკრებს მხმარეობენ.

**დაფაზე ხილული სტრატეგიები (ანგარიშის დონის როუტინგი):**

| სტრატეგია                      | აღწერილობა                                                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| **Fill First**                 | იყენებს ანგარიშებს პრიორიტეტის მიხედვით — ძირითადი ანგარიში იღებს ყველა მოთხოვნას, სანამ ხელმისაწვდომია     |
| **Round Robin**                | მონაცვლეობს ყველა ანგარიშს შორის მორგებადი sticky ლიმიტით (ნაგულისხმევი: 3 ზარი ანგარიშზე)                  |
| **P2C (Power of Two Choices)** | ირჩევს 2 შემთხვევით ანგარიშს და მიმართავს უფრო ჯანსაღს — ტვირთის ბალანსირება ჯანმრთელობის გათვალისწინებით   |
| **Random**                     | თითოეული მოთხოვნისთვის შემთხვევით ირჩევს ანგარიშს Fisher-Yates shuffle-ის გამოყენებით                       |
| **Least Used**                 | მიმართავს ანგარიშს, რომელსაც აქვს ყველაზე ძველი `lastUsedAt` timestamp, ტრაფიკის თანაბრად გადანაწილებისთვის |
| **Cost Optimized**             | მიმართავს ანგარიშს ყველაზე დაბალი პრიორიტეტის მნიშვნელობით, ყველაზე იაფი პროვაიდერებისთვის ოპტიმიზაციისთვის |

**გაუმჯობესებული კომბინაციისა და ავტო სტრატეგიები** (მორგებადი თითო კომბინაციისთვის ან `auto/*` პრეფიქსების მეშვეობით — იხილეთ [AUTO-COMBO.md](../routing/AUTO-COMBO.md)):

- `priority` — მკაცრი თანმიმდევრობა, არ ახდენს round-robin-ს
- `weighted` — პროპორციული ტრაფიკის გადანაწილება მოდელის საწონების მიხედვით
- `fill-first` — პირველი მოდელის ამოწურვა, სანამ ლიმიტები არ მიეღწევა
- `round-robin` / `strict-random` / `random`
- `p2c` (Power of Two Choices)
- `least-used` და `cost-optimized`
- `auto` — ქულაზე დაფუძნებული შერჩევა ყველა კანდიდატს შორის
- `lkgp` (Last Known Good Provider) — მიმაგრებულია ბოლო წარმატებულ პროვაიდერზე, შემდეგ კი ვარდება წესებზე
- `context-optimized` — ირჩევს მოდელს ყველაზე დიდი თავისუფალი კონტექსტის ფანჯრით
- `context-relay` — ურთიერთდაკავშირებული long-context მოდელები გაგრძელების თანმიმდევრობებისთვის

#### გარე Sticky Session ჰედერი

გარე სესიის აფინირებისთვის (მაგალითად, Claude Code/Codex აგენტები რევერსული პროქსის უკან), გაგზავნეთ:

```http
X-Session-Id: your-session-key
```

OmniRoute ასევე იღებს `x_session_id`-ს და აბრუნებს ეფექტურ სესიის გასაღებს `X-OmniRoute-Session-Id`-ში.

თუ იყენებთ Nginx-ს და უგზავნით ქვედა ტირის ფორმის ჰედერებს, ჩართეთ:

```nginx
underscores_in_headers on;
```

#### Wildcard Model Aliases

შექმენით wildcard შაბლონები მოდელების სახელების გადასაკუთვნელად:

```
Pattern: claude-sonnet-*     →  Target: cc/claude-sonnet-4-6
Pattern: gpt-*               →  Target: gh/gpt-5.3-codex
```

Wildcard-ები მხმარეობენ `*`-ს (ნებისმიერ სიმბოლოებს) და `?`-ს (ერთ სიმბოლოს).

#### Fallback Chains

განსაზღვრეთ გლობალური fallback ჯაჭვები, რომლებიც ყველა მოთხოვნაზე ვრცელდება:

```
Chain: production-fallback
  1. cc/claude-opus-4-7
  2. gh/gpt-5.3-codex
  3. glm/glm-4.7
```

### Common Provider Combinations & Routing Patterns

აქ მოცემულია მაგალითები, როგორ შეიძლება გაერთიანდეს რამდენიმე პროვაიდერი და როგორ მოხდეს მათ შორის როუტინგი OmniRoute-ში:

#### 1. კოდირების აგენტის კომბო: მაღალი დონის მსჯელობა ღირებულება/სიჩქარის სარეზერვო ვარიანტებით

იდეალურია კოდირების აგენტებისთვის (OpenCode, Claude Code, Cursor, Cline). თავდაპირველად მოთხოვნებს ამისამართებს წამყვან მსჯელობის მოდელებზე, ხოლო კვოტის ამოწურვის ან შეცდომების შემთხვევაში გადადის სწრაფ კოდირების მოდელებზე.

- **დაფა**: კომბოები → ახალი კომბო → სახელი: `agent-coding` → სტრატეგია: `Priority`
- **მოდელები**:
  1. `claude/claude-sonnet-4-6` (ძირითადი კოდირების აგენტი)
  2. `openai/gpt-4o` (მეორადი მაღალტევადი სარეზერვო ვარიანტი)
  3. `deepseek/deepseek-v4-flash` (მაღალეფექტური, ეკონომიური სარეზერვო ვარიანტი)

```bash
# მაგალითი API-ის მეშვეობით
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "agent-coding",
    "strategy": "priority",
    "models": [
      { "model": "claude/claude-sonnet-4-6" },
      { "model": "openai/gpt-4o" },
      { "model": "deepseek/deepseek-v4-flash" }
    ]
  }'
```

#### 2. უფასო დონის ავტომატური გადართვის (Failover) კომბო

აერთიანებს მრავალ უფასო დონისა და გასაღების გარეშე მომუშავე პროვაიდერს, რათა API-ს ხარჯების გარეშე მაქსიმალურად გაიზარდოს მუშაობის უწყვეტობა.

- **სტრატეგია**: `Least Used` ან `Round Robin` (ნაწილებს დატვირთვას კვოტებს შორის)
- **მოდელები**:
  1. `groq/llama-3.3-70b-versatile`
  2. `gemini/gemini-2.5-flash`
  3. `cerebras/gpt-oss-120b`

```bash
# მაგალითი CLI-ის მეშვეობით
omniroute combo create free-stack \
  --models "groq/llama-3.3-70b-versatile,gemini/gemini-2.5-flash,cerebras/gpt-oss-120b" \
  --strategy round-robin
```

#### 3. მულტიმოდალური / ვიზუალური და ტექსტური ჯაჭვი

აერთიანებს სპეციალიზებულ ვიზუალურ მოდელებს მაღალსიჩქარიან ტექსტის გენერაციასთან იმ სამუშაო პროცესებისთვის, რომლებიც მოიცავს გამოსახულების გაგებასა და კოდის გენერაციას.

- **შაბლონი**: `Priority` კომბო, რომელიც ჯერ ჩამოთვლის ვიზუალური შესაძლებლობების მქონე მოდელებს, ხოლო ბოლოს — მაღალი გამტარუნარიანობის ტექსტის/კოდის მოდელს.
- **მოდელები**:
  1. `gemini/gemini-2.5-pro` (გამოსახულების/მულტიმოდალური შინაარსის ძლიერი გაგება)
  2. `openai/gpt-4o` (დაბალანსებული ვიზუალური აღქმა და ინსტრუმენტების გამოყენება)
  3. `deepseek/deepseek-v4-flash` (ტექსტის/კოდის გენერაცია)

### გამძლეობა და წრიული გამწყვეტები (Circuit Breakers)

კონფიგურაცია ხდება **დაფა → პარამეტრები → გამძლეობა** გვერდზე.

OmniRoute ახორციელებს პროვაიდერის დონის გამძლეობას ხუთი კომპონენტით:

1. **მოთხოვნების რიგი და ტემპი** — მოთხოვნების ფორმირება სისტემის დონეზე:
   - **მოთხოვნები წუთში (RPM)** — მოთხოვნების მაქსიმალური რაოდენობა წუთში თითო ანგარიშზე
   - **მინიმალური დრო მოთხოვნებს შორის** — მინიმალური ინტერვალი მილიწამებში მოთხოვნებს შორის
   - **მაქსიმალური ერთდროული მოთხოვნები** — ერთდროული მოთხოვნების მაქსიმალური რაოდენობა თითო ანგარიშზე

2. **კავშირის გაგრილება (Cooldown)** — ავტორიზაციის ტიპის მიხედვით კონფიგურაცია ცალკეული კავშირისთვის განმეორებადი შეცდომების შემდეგ:
   - **საბაზო გაგრილება** — ნაგულისხმევი გაგრილების ფანჯარა განმეორებადი upstream შეცდომებისთვის
   - **Upstream ხელახლა ცდის მინიშნებების გამოყენება** — ითვალისწინებს ავტორიტეტულ `Retry-After` ან განულების მინიშნებებს, როდესაც ისინი მოწოდებულია
   - **Backoff-ის მაქსიმალური ნაბიჯები** — ექსპონენციური backoff-ის მაქსიმალური დონე განმეორებადი შეცდომებისთვის

3. **პროვაიდერის წრიული გამწყვეტი** — თვალყურს ადევნებს პროვაიდერის სრულ (end-to-end) შეცდომებს, აღნიშნავს პროვაიდერს დეგრადირებულად კონფიგურირებული გაფრთხილების ზღვარის მიღწევისას და ხსნის გამწყვეტს კონფიგურირებული შეცდომების ზღვარის მიღწევისას:
   - **დეგრადაციის ზღვარი** — თანმიმდევრული პროვაიდერის შეცდომების რაოდენობა `DEGRADED` მდგომარეობაში გადასვლამდე
   - **შეცდომების ზღვარი** — თანმიმდევრული პროვაიდერის შეცდომების რაოდენობა `OPEN` მდგომარეობაში გადასვლამდე
   - **განულების ვადა** — დროის ფანჯარა, რომლის შემდეგაც პროვაიდერი ხელახლა მოწმდება
   - **CLOSED** (ჯანსაღი) — მოთხოვნები ნორმალურად მიედინება
   - **DEGRADED** — მოთხოვნები კვლავ მიედინება, მაშინ როდესაც გაზრდილი შეცდომები ფიქსირდება
   - **OPEN** — პროვაიდერი დროებით იბლოკება განმეორებადი შეცდომების შემდეგ
   - **HALF_OPEN** — მოწმდება, აღდგა თუ არა პროვაიდერი

   კავშირის მასშტაბის `429` სიჩქარის შეზღუდვები რჩება **კავშირის გაგრილების** ფარგლებში და არ ჩაითვლება პროვაიდერის გამწყვეტში.

   პროვაიდერის გამწყვეტის სამუშაო მდგომარეობა ნაჩვენებია მხოლოდ **დაფა → ჯანმრთელობა** გვერდზე.

4. **გაგრილების ლოდინი** — თუ ყველა სავარაუდო კავშირი უკვე გაგრილების რეჟიმშია, OmniRoute-ს შეუძლია დაელოდოს უადრესი გაგრილების დასრულებას და ავტომატურად გაიმეოროს იგივე კლიენტის მოთხოვნა.

5. **სიჩქარის შეზღუდვის ავტომატური გამოვლენა** — როდესაც upstream პროვაიდერები აბრუნებენ ლოდინის კონკრეტულ ფანჯრებს, ჩართული პარამეტრის შემთხვევაში ეს მინიშნებები უპირატესად ითვლება ლოკალურ კავშირის გაგრილებასთან შედარებით.

**რჩევა:** გამოიყენეთ **ჯანმრთელობის** გვერდი პროვაიდერის აქტიური გამწყვეტების შესამოწმებლად და გასანულებლად გათიშვის შემდეგ. გამძლეობის გვერდი მხოლოდ კონფიგურაციას ცვლის.

### მონაცემთა ბაზის ექსპორტი / იმპორტი

მართეთ მონაცემთა ბაზის სარეზერვო ასლები **დაფა → პარამეტრები → სისტემა და საცავი** გვერდზე.

| მოქმედება                        | აღწერა                                                                                                                                                                               |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **მონაცემთა ბაზის ექსპორტი**     | ჩამოტვირთავს მიმდინარე SQLite მონაცემთა ბაზას `.sqlite` ფაილის სახით                                                                                                                 |
| **ყველაფრის ექსპორტი (.tar.gz)** | ჩამოტვირთავს სრულ სარეზერვო არქივს, რომელიც მოიცავს: მონაცემთა ბაზას, პარამეტრებს, კომბოებს, პროვაიდერის კავშირებს (ავტორიზაციის მონაცემების გარეშე), API გასაღებების მეტამონაცემებს |
| **მონაცემთა ბაზის იმპორტი**      | ატვირთეთ `.sqlite` ფაილი მიმდინარე მონაცემთა ბაზის შესაცვლელად. იმპორტამდე სარეზერვო ასლი ავტომატურად იქმნება, გარდა იმ შემთხვევისა, როდესაც `DISABLE_SQLITE_AUTO_BACKUP=true`       |

```bash
# API: მონაცემთა ბაზის ექსპორტი
curl -o backup.sqlite http://localhost:20128/api/db-backups/export

# API: ყველაფრის ექსპორტი (სრული არქივი)
curl -o backup.tar.gz http://localhost:20128/api/db-backups/exportAll

# API: მონაცემთა ბაზის იმპორტი
curl -X POST http://localhost:20128/api/db-backups/import \
  -F "file=@backup.sqlite"
```

**იმპორტის ვალიდაცია:** იმპორტირებული ფაილი მოწმდება მთლიანობაზე (SQLite pragma შემოწმება), აუცილებელ ცხრილებზე (`provider_connections`, `provider_nodes`, `combos`, `api_keys`) და ზომაზე (მაქს. 100MB).

**გამოყენების შემთხვევები:**

- OmniRoute-ის მიგრაცია კომპიუტერებს შორის
- გარე სარეზერვო ასლების შექმნა კატასტროფის შემდეგ აღდგენისთვის
- კონფიგურაციების გაზიარება გუნდის წევრებს შორის (ყველაფრის ექსპორტი → არქივის გაზიარება)

| სტრატეგია          | აღწერა                                                                                    |
| ------------------ | ----------------------------------------------------------------------------------------- |
| **Round-Robin**    | მოდელებს თანმიმდევრობით ატრიალებს                                                         |
| **Priority**       | ყოველთვის პირველ მოდელს ცდის; სარეზერვოზე მხოლოდ შეცდომისას გადადის                       |
| **Random**         | თითოეული მოთხოვნისთვის კომბოდან შემთხვევით მოდელს ირჩევს                                  |
| **Weighted**       | ამისამართებს პროპორციულად, თითო მოდელზე მინიჭებული წონების მიხედვით                       |
| **Least-Used**     | ამისამართებს ყველაზე ნაკლები უახლესი მოთხოვნების მქონე მოდელზე (იყენებს კომბოს მეტრიკებს) |
| **Cost-Optimized** | ამისამართებს ყველაზე იაფ ხელმისაწვდომ მოდელზე (იყენებს ფასების ცხრილს)                    |

კომბოს გლობალური ნაგულისხმევების დაყენება შესაძლებელია **მართვის პანელი → პარამეტრები → მარშრუტიზაცია → კომბოს ნაგულისხმევები**-ში.
კომბოს სამიზნეების ტაიმაუტები ნაგულისხმევად მემკვიდრეობით იღებენ მიმდინარე მოთხოვნის ტაიმაუტს. გამოიყენეთ **სამიზნის
ტაიმაუტი (წამები)** კომბოს ნაგულისხმევებში ან ცალკეულ კომბოზე მხოლოდ მაშინ, როდესაც თითო სამიზნეზე უფრო მოკლე
ლიმიტმა უნდა უზრუნველყოს უფრო სწრაფი fallback.

კომბოს ნულოვანი-ლატენტობის ოპტიმიზაციები მუშაობს ჩართვის პრინციპით (opt-in). დატოვეთ **ნულოვანი-ლატენტობის
ოპტიმიზაციები** გამორთული, რათა ეს ლატენტობის ფუნქციები არ ეჯიბრებოდეს fallback-სამიზნეებს, არ გამოტოვებდეს
სამიზნეებს TTFT-ისტორიის საფუძველზე და არ შეკუმშავდეს fallback-მოთხოვნები; მისი ჩართვა საშუალებას აძლევს
კონფიგურირებულ hedging-ს, პროგნოზირებად TTFT-გამოტოვებებსა და პროაქტიულ fallback-შეკუმშვას მარშრუტიზაციის/მოთხოვნის
ერთგულების სანაცვლოდ შეამცირონ კუდის (tail) ლატენტობა.

გამორთეთ **მსჯელობის ტოკენის ბუფერი (Reasoning token buffer)**, როდესაც აპსტრიმ პროვაიდერები მოითხოვენ მკაცრ
`max_tokens` / `maxOutputTokens` ლიმიტებს. როდესაც ჩართულია, კომბო მარშრუტიზაცია მსჯელობის მოდელის დამატებით
მარაგს მხოლოდ იმ მოდელებისთვის უზრუნველყოფს, რომლებსაც ცნობილი გამომავალი ზღვარი აქვთ, და კლიენტის ტოკენის
ლიმიტს უცვლელად ტოვებს, როდესაც უსაფრთხო ბუფერული მნიშვნელობა ამ ზღვარს გადააჭარბებდა. თუ კლიენტის ლიმიტი
უკვე ცნობილ ზღვარზე მაღლაა, OmniRoute მას ამ ზღვარამდე ამცირებს აპსტრიმ მოთხოვნის გაგზავნამდე.

## 🤖 ავტომარშრუტიზაცია (ნულოვანი კონფიგურაცია)

OmniRoute-ს მოჰყვება **შეფასებებზე დაფუძნებული ავტომარშრუტიზატორი**, რომელიც თითოეული მოთხოვნისთვის ყველა დაკავშირებულ პროვაიდერს შორის საუკეთესო მოდელს ირჩევს — ხელით სამართავი კომბინაციის გარეშე. უბრალოდ გაგზავნეთ მოთხოვნა ერთ-ერთი `auto/*` პრეფიქსით და OmniRoute დინამიკურად შექმნის ვირტუალურ კომბინაციას, კანდიდატებს კი შეაფასებს დაყოვნების, ღირებულების, წარმატების მაჩვენებლის, კონტექსტთან შესაბამისობის, ამოცანისთვის მოდელის ვარგისიანობის, ბოლოდროინდელი წარუმატებლობების, კვოტისა და circuit breaker-ის მდგომარეობის მიხედვით.

| პრეფიქსი       | ოპტიმიზაციის მიზანი                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `auto`         | დაბალანსებული ნაგულისხმევი რეჟიმი (დაყოვნება × ღირებულება × წარმატების მაჩვენებელი)                                             |

| `auto/smart`   | მსჯელობის ხარისხი უპირველესად (Opus, GPT-5 xhigh, R1, GLM 5.1 reasoning)                                                        |

## 🔌 MCP-სა და A2A-ს ინტეგრაცია

OmniRoute ერთდროულად არის **MCP სერვერი** (Model Context Protocol) და **A2A სერვერი** (Agent-to-Agent JSON-RPC 2.0). ნებისმიერ MCP-თავსებად IDE-ს ან აგენტის ჰოსტს შეუძლია OmniRoute-ის ხელსაწყოები პირდაპირ გამოიძახოს — დამატებითი გარსი საჭირო არ არის.

### MCP ტრანსპორტები

- **SSE**: `http://localhost:20128/api/mcp/sse`
- **ნაკადური HTTP**: `http://localhost:20128/api/mcp/stream`
- **stdio**: `omniroute --mcp` (IDE-ის დანამატებისთვის, რომლებიც stdio-ს ამჯობინებენ)

### Claude Desktop-ის დაკავშირება

ჩაასწორეთ `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS) ან მისი ეკვივალენტი Windows/Linux-ზე:

```json
{
  "mcpServers": {
    "omniroute": {
      "command": "omniroute",
      "args": ["--mcp"]
    }
  }
}
```

### Cursor-ის / Continue-ის / VS Code MCP-ის დაკავშირება

გამოიყენეთ SSE URL `http://localhost:20128/api/mcp/sse` და Bearer API გასაღები, რომელიც შექმნილია განყოფილებაში **მართვის პანელი → API Keys**.

### წვდომის სფეროები

MCP ამჟამად განსაზღვრავს 32 დასახელებულ წვდომის სფეროს. თითოეული Bearer გასაღები შეიძლება შეიზღუდოს კონკრეტული სფეროებით — წვდომის სფეროებისა და ხელსაწყოების ავტორიტეტული ჩამონათვალისთვის იხილეთ [MCP-SERVER.md](../frameworks/MCP-SERVER.md), ხოლო JSON-RPC სქემისთვის — [A2A-SERVER.md](../frameworks/A2A-SERVER.md).

- თითოეული მონაცემთა დატვირთვა გადამოწმებისთვის შეიცავს `X-OmniRoute-Signature`-ს (HMAC-SHA256)
- განმეორებითი მცდელობები: 3 მცდელობა ექსპონენციალური დაყოვნებით, შემდეგ კი გადატანა დაუმუშავებელი შეტყობინებების რიგში

სრული სქემა იხილეთ [WEBHOOKS.md](../frameworks/WEBHOOKS.md)-ში.

## 🛠️ პროგრამული მართვა

შეგიძლიათ OmniRoute-ის ყველა რესურსი (პროვაიდერები, კომბინაციები, გასაღებები, პარამეტრები) HTTP-ის მეშვეობით მართოთ, **`manage` მოქმედების არეალის მქონე Bearer გასაღების** გამოყენებით.

დააგენერირეთ გასაღები **მართვის პანელი → API გასაღებები → ახალი გასაღები → მოქმედების არე: manage** განყოფილებაში, შემდეგ:

```bash
# პროვაიდერების სიის ჩვენება
curl http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"

# პროვაიდერთან კავშირის დამატება
curl -X POST http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "provider": "openai", "apiKey": "sk-...", "name": "main" }'

# კომბინაციის შექმნა
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "premium", "strategy": "priority", "models": [{ "model": "cc/claude-opus-4-7" }, { "model": "glm/glm-5.1" }] }'

# API გასაღებების სიის ჩვენება/შექმნა
curl http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"
curl -X POST http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -d '{ "name": "ci-bot", "scopes": ["chat"] }'
```

საბოლოო წერტილების სრული კატალოგისა და მოთხოვნის/პასუხის სქემებისთვის იხილეთ [API_REFERENCE.md](../reference/API_REFERENCE.md).

## 💻 შიდა CLI

OmniRoute-ს მოჰყვება შიდა CLI (`omniroute …`) კონფიგურაციისთვის, დიაგნოსტიკისა და გაშვების პროცესის მართვისთვის. ეს **განსხვავდება მართვის პანელში არსებული „CLI Tools“ გვერდისგან**, რომელიც აკონფიგურირებს მესამე მხარის CLI-ებს (Claude Code, Cursor, Codex, Cline, …), რათა მათ OmniRoute-თან კომუნიკაცია შეძლონ.

```bash
omniroute setup                    # ინტერაქტიული ოსტატი (პაროლი, პროვაიდერები, კომბინაციები)
omniroute setup --non-interactive  # მოსახერხებელია CI-სთვის
omniroute doctor                   # მდგომარეობის დიაგნოსტიკა (მონაცემთა დირექტორია, DB, პროვაიდერები, პორტები)
omniroute providers available      # მხარდაჭერილი პროვაიდერების სიის ჩვენება
omniroute providers list           # კონფიგურირებული კავშირების სიის ჩვენება
omniroute providers test <id>      # პროვაიდერის კავშირის რეალურ დროში შემოწმება
omniroute combos list              # კომბინაციების სიის ჩვენება
omniroute combos switch <name>     # ნაგულისხმევი კომბინაციის დაყენება
omniroute models                   # ხელმისაწვდომი მოდელების სიის ჩვენება (--json, --search)
omniroute keys add | list | remove # API გასაღებების მართვა ტერმინალიდან
omniroute backup                   # კონფიგურაციისა და DB-ის სარეზერვო ასლის შექმნა
omniroute restore [<timestamp>]    # სარეზერვო ასლიდან აღდგენა
omniroute health                   # მდგომარეობის დეტალური ინფორმაცია (ამომრთველები, კეში, მეხსიერება)
omniroute quota                    # პროვაიდერის კვოტის გამოყენება
omniroute mcp status               # MCP სერვერის სტატუსი
omniroute a2a status               # A2A სერვერის სტატუსი
omniroute tunnel list|create|stop  # Cloudflare/Tailscale/ngrok გვირაბები
omniroute reset-password           # ადმინისტრატორის პაროლის გადაყენება
omniroute --mcp                    # MCP სერვერის გაშვება stdio-ს მეშვეობით
omniroute --port 3000              # სერვერის გაშვება მორგებულ პორტზე
```

რჩევა: გამოიყენეთ `omniroute doctor --json` თქვენს მონიტორინგის ხელსაწყოსთან ერთად, რათა მიიღოთ შეტყობინებები პროვაიდერების გაუმართავი კავშირების შესახებ.

OmniRoute ხელმისაწვდომია როგორც ნატიური დესკტოპ-აპლიკაცია Windows-ისთვის, macOS-ისა და Linux-ისთვის.

### ინსტალაცია

```bash
# electron დირექტორიიდან:
cd electron
npm install

# დეველოპმენტის რეჟიმი (უკავშირდება გაშვებულ Next.js დეველოპმენტის სერვერს):
npm run dev

# საწარმოო რეჟიმი (იყენებს standalone ანაწყობს):
npm start
```

### ინსტალატორების აგება

```bash
cd electron
npm run build          # მიმდინარე პლატფორმა

npm run build:mac      # macOS (.dmg უნივერსალური)
npm run build:linux    # Linux (.AppImage)
```
