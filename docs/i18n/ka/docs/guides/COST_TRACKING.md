`omniroute cost` / `omniroute usage` CLI-ში, CSV/JSON ექსპორტებში და თითოეული API-გასაღების ბიუჯეტებში.

> ნიშნავს, რომ ფასიანი API-ს გამოყენების შემთხვევაში დაახლოებით **$290-ის გადახდა _არ_ მოგიწიათ**. ეს მაჩვენებელი არის
> _შეფასება_ იმისა, თუ რა ეღირებოდა იგივე ტრაფიკი სტანდარტული კატალოგური ფასებით, რათა დაინახოთ,

## როგორ ფასდება ხარჯები

### ფასების წყარო

ხარჯები მოდის გაერთიანებული ფასების ცხრილიდან [`src/lib/db/settings/pricing.ts`](../../src/lib/db/settings/pricing.ts) ში, ამ პრიორიტეტის მიხედვით (**პირველი უმაღლესი** ):

1. **მომხმარებლის უგულებელყოფა** — ფასები მითითებულია დაფაზე ან `PATCH /api/pricing` ( `pricing` სახელების სივრცის) მეშვეობით.
2. **models.dev სინქრონიზაცია** — ფასი ჩამოტანილია `https://models.dev/api.json` დან ( `models_dev_pricing` სახელთა სივრცე).
3. **LiteLLM სინქრონიზაცია** — ფასები მიღებულია LiteLLM ის საჯარო `model_prices_and_context_window.json` დან ( `pricing_synced` სახელთა სივრცე).
4. **მყარი კოდირებული ნაგულისხმევი** — განაკვეთები გაიგზავნება [`src/shared/constants/pricing/`](../../src/shared/constants/pricing/) ში.

იგივე provider/model სთვის, უფრო მაღალი პრიორიტეტული ფენების მნიშვნელობები გადაწერს შესატყვის ველებს ქვედა შრეებში; ზედა ფენიდან არ მყოფი ველები მაინც შეიძლება იყოს ქვედა ფენიდან. შეკვეთა ფიქსირდება მაშინაც კი, როდესაც ორივე დამოუკიდებელი სინქრონიზაციის სამუშაო ერთდროულად მუშაობს. `GET /api/pricing?includeSources=1` აბრუნებს `pricing` და `sourceMap`, რომელთა თითო მოდელის ეტიკეტები (`user`, `modelsDev`, `litellm`, `default`) განსაზღვრავს ამ მოდელის შემცველ ყველაზე პრიორიტეტულ ფენას.

**LiteLLM სინქრონიზაცია** ჩართულია, ნაგულისხმევად გამორთულია. მისი გარემოს ცვლადები (იხ. [`.env.example`](../../.env.example) ) არის:

| Env var                 | ნაგულისხმევი | მიზანი                                                                                   |
| ----------------------- | ------------ | ---------------------------------------------------------------------------------------- |
| `PRICING_SYNC_ENABLED`  | `false`      | ჩართეთ ფონური LiteLLM ფასების სინქრონიზაცია.                                             |
| `PRICING_SYNC_INTERVAL` | `86400`      | სინქრონიზაციის ინტერვალი წამებში (ყოველდღიურად).                                         |
| `PRICING_SYNC_SOURCES`  | `litellm`    | წყაროს შერჩევა მხოლოდ ამ სინქრონიზაციისთვის; ამჟამად მხოლოდ `litellm` არის მხარდაჭერილი. |

**models.dev სინქრონიზაცია** ცალკეა LiteLLM სინქრონიზაციისგან და ასევე გამორთულია ნაგულისხმევად. ჩართეთ ის პარამეტრებში (models.dev sync) ან გამოიყენეთ ეს ცვლადები:

| Env var                    | ნაგულისხმევი    | მიზანი                                                                                                                                                     |
| -------------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MODELS_DEV_SYNC_ENABLED`  | _(დაუყენებელი)_ | გაუქმება მიჰყვება პარამეტრების გადართვას; `1/true/on/yes` აიძულებს ჩართოს და `0/false/off/no` აიძულებს გამორთვას (მაშინაც კი, თუ პარამეტრები ჩართავს მას). |
| `MODELS_DEV_SYNC_INTERVAL` | `86400`         | ნაგულისხმევი models.dev სინქრონიზაციის ინტერვალი წამებში (ყოველდღიურად).                                                                                   |

`PRICING_SYNC_SOURCES` აკეთებს **არა** ჩართეთ models.dev; ის აკონტროლებს მხოლოდ LiteLLM სინქრონიზაციას. მომხმარებლის უგულებელყოფის წაშლა არ ასუფთავებს არც სინქრონიზებულ სახელთა სივრცეს; შემდეგი ხელმისაწვდომი ფასების ფენა მოქმედებს. უფასო მოდელისთვის, შეამოწმეთ სინქრონიზაციის პარამეტრები და `sourceMap` სანამ დაამატებთ მექანიკურ გადაფარვას.

### ღირებულების ფორმულა

ღირებულება გამოითვლება თითო მოთხოვნაზე ტოკენების დათვლიდან და მილიონ ტოკენის ტარიფებიდან [`src/lib/usage/costCalculator.ts`](../../src/lib/usage/costCalculator.ts) ში (`computeCostFromPricing` / `calculateCost`):

- **შეიტანეთ ნიშნები** (მინუს ქეში წაკითხვები და ქეში-შექმნის ნიშნები) × `input` მაჩვენებელი.
- **ქეშის წაკითხვის ნიშნები** × `cached` მაჩვენებელი (უბრუნდება შეყვანის სიჩქარეს).
- **ქეშის შექმნის ნიშნები** × `cache_creation` მაჩვენებელი (უბრუნდება შეყვანის სიჩქარეს).
- **გამომავალი ნიშნები** × `output` განაკვეთი.
- **მსჯელობის ნიშნები** × `reasoning` მაჩვენებელი (უბრუნდება გამომავალი მაჩვენებელი).

ყველა ტარიფი ინტერპრეტირებულია, როგორც USD 1,000,000 ტოკენზე. Codex "სწრაფი"/"პრიორიტეტული" ან "მოქნილი" სერვისის დონე იყენებს ხარჯების მულტიპლიკატორს (`getCodexFastCostMultiplier`) — მაგ. flex ანგარიშდება 50%-იანი ფასდაკლებით, გამოსახულია როგორც **flex დანაზოგი** დაფაში.

მოდელების სახელები ჯერ ნორმალიზდება (პროვაიდერის ბილიკის პრეფიქსები, როგორიცაა `openai/` ან `accounts/fireworks/models/` ამოღებულია), ამიტომ ისტორიული რიგები მაინც ემთხვევა ფასს.

### როგორ აღირიცხება ხარჯვა

- თითო მოთხოვნის ღირებულება გამოითვლება მოთხოვნის დასრულებისას. გაზიარებული კვოტის მოხმარება დაგეგმილია მომდევნო ღონისძიების მარყუჟზე [`src/lib/quota/spendRecorder.ts`](../../src/lib/quota/spendRecorder.ts) მეშვეობით.
- API გასაღების ხარჯვა ბუფერირებულია და ნაწილებად იშლება [`SpendBatchWriter`](../../src/lib/spend/batchWriter.ts) ით (ნაგულისხმევი 60 წმ. რეგულირება შესაძლებელია:

  | Env var                             | ნაგულისხმევი | მიზანი                                    |
  | ----------------------------------- | ------------ | ----------------------------------------- |
  | `OMNIROUTE_SPEND_FLUSH_INTERVAL_MS` | `60000`      | ფლეშის ინტერვალი მილიწამებში.             |
  | `OMNIROUTE_SPEND_MAX_BUFFER_SIZE`   | `1000`       | მაქს ბუფერირებული ჩანაწერები ჩარეცხვამდე. |

ხარჯებს ურჩევნიათ ზუსტი პროვაიდერის მიერ მოხსენებული გადასახადი (`provider_cost_usd`), შემდეგ კატალოგის ფასიანი მოთხოვნის სნეპშოტი (`calculated_cost_usd`), შემდეგ ტოკენის გადაფასება მიმდინარე კატალოგიდან. შენახული ხარჯები ხელახლა არ ირიცხება მათი სიმბოლური დათვლის მეშვეობით. მხოლოდ მოძველებული ტოკენის რიგები კვლავ იცვლება, როდესაც იცვლება მათი კატალოგის ფასი.

### OCR და ჩაშენებები

- წარმატებული `/v1/ocr` მოთხოვნები იყენებს ზემოთ დინებაში `usage_info.pages_processed` და არა მოთხოვნილ გვერდების დიაპაზონს ან დაბრუნებული გვერდის ობიექტების რაოდენობას. შეფასება არის გვერდები × `ocr_cost_per_page` (აბსოლუტური USD/page,**არა** USD/million).
- მოთხოვნები დოკუმენტის ან სასაზღვრო ყუთის ანოტაციებით მოითხოვს ცალკე `ocr_cost_per_annotated_page` ტარიფს. ამის გარეშე, ღირებულება უცნობია; ჩვეულებრივი OCR ტარიფი ჩუმად არ იცვლება.
- LiteLLM სინქრონიზაცია ასახავს მის ზემოთ `annotation_cost_per_page` ველს `ocr_cost_per_annotated_page` ში, ინარჩუნებს აბსოლუტურ USD/page მნიშვნელობას და მხოლოდ ანოტაციის ჩანაწერებს, მათ შორის აშკარა ნულს. მიწოდებულ კანონიკურ ველს უპირატესობა აქვს; მეტსახელის არასწორი მნიშვნელობები იგნორირებულია. მომხმარებლის ფასების უგულებელყოფა ინარჩუნებს ჩვეულებრივ პრიორიტეტს. იხილეთ [LiteLLM- ს OCR ფასების გასაღებები](https://docs.litellm.ai/docs/providers/mistral_batches#batch-ocr-cost-tracking).
- OCR გამოყენება ინახავს გვერდების რაოდენობას, ერთეულის ფასს, გამოთვლილ USD ღირებულებას, API კლავიშს და არჩეულ კავშირს. გვერდები არასოდეს არის წარმოდგენილი, როგორც ნიშნები. ზარების ჟურნალი შეიცავს ბილინგის მეტამონაცემებს და არა დოკუმენტს URLs, PDF ბაიტს ან ამოღებულ ტექსტს.
- წარმატებულ `/v1/embeddings` მოთხოვნებში ჩაიწერება გამოყენების ერთი მწკრივი ფიზიკურ პარტიაში, მათ შორის ცალკეული პარტიები დასრულებული იმავე მილიწამში. პროვაიდერის მიერ მოხსენებული გადასახადები უპირატესობას ანიჭებს სიმბოლურ შეფასებებს; კომბინირებული შეფუთვა არ ამატებს გადასახადს.
- გამოყენების ისტორია, ხარჯების ანალიტიკა, provider/account windows, API-გასაღების ხარჯვის ლიმიტები, მოთხოვნა-ღირებულების წიგნი და ყოველდღიური გამოყენების შეგროვება მოიცავს ამ გადასახადებს. No-log კლავიშები ინარჩუნებენ ციფრულ აღრიცხვას წყაროს ტექსტის შენარჩუნების გარეშე.
- გამოტოვებულია გამოყენება ან ტარიფები **უცნობი** , არ არის უფასო: პასუხის ღირებულების სათაური გამოტოვებულია და არსებული არაფასიანი გამოყენების პოლიტიკა ვრცელდება შეზღუდული API გასაღებებზე. ცალსახად კონფიგურირებული ნულოვანი ტარიფები ძალაში რჩება ნულოვანი ხარჯების გამოყენებაზე.

ეს არის მხოლოდ წინასწარი აღრიცხვა. ძველი OCR/embedding ზარები, რომლებსაც არასოდეს დაუწერიათ გამოყენების ისტორია, ვერ აღდგება ამ მიგრაციიდან. კატალოგის შეფასებები არის USD შეფასებები და არა ინვოისი და არ შეიცავს ვალუტის კონვერტაციას, გადასახადს ან ფასდაკლებას.

### მეტყველება და სურათები

- წარმატებული `/v1/audio/transcriptions`, `/v1/audio/speech` და გამოსახულების გენერირების მცდელობები იზიარებენ რიცხვით აღრიცხვას. პირდაპირი და კომბინირებული ზარები ატარებენ აბონენტის API კლავიშს და არჩეულ კავშირს; კომბინირებული შეფუთვა არასოდეს ამატებს მეორე დებეტს.
- პროვაიდერის მიერ მოხსენებული USD იგებს კატალოგის შეფასებას, აშკარა ნულოვანი გადასახადის ჩათვლით. OpenRouter ის JSON `usage.cost` ნორმალიზებულია `cost_usd` მდე. წინააღმდეგ შემთხვევაში, გაზომილი ჟეტონები იყენებენ ტოკენის ფასებს, ტრანსკრიფციის წამებში იყენებენ ფასებს წამში, მეტყველების შეყვანა იყენებს Unicode სიმბოლოების რაოდენობას, ხოლო ცალსახა ფასის გამოსახულებები იყენებენ რეალურად დაბრუნებულ რიცხვს და არა მოთხოვნილ `n`.
- ორობითი OpenRouter TTS არ აქვს JSON გამოყენების ორგანო. აუდიოს დასრულების ან აბონენტის გაუქმების შემდეგ, OmniRoute ითხოვს მის თაობას ID ზე **იგივე** კონფიგურირებული OpenRouter წარმოშობა. EU მოთხოვნა არასოდეს უბრუნდება გლობალურ წარმოშობას. ეს არის შეზღუდული, მხოლოდ წაკითხვადი ძიება; სინთეზი არ განმეორდება აღრიცხვისთვის. ბილინგის ჩანაწერები შეიძლება გამოჩნდეს აუდიოს დასრულების შემდეგ: საძიებო განმეორებითი ცდები გადის ფონზე დაახლოებით 52 წამამდე, ქსელის ვადების ჩათვლით.
- ამ ძიების დროს, აუდიო პასუხს აქვს `X-OmniRoute-Cost-Status: pending` და არ არის პასუხის ღირებულების სათაური. მისი საბოლოო დატენვა ჩნდება გამოყენების ისტორიაში, ანალიტიკაში და გასაღების წიგნში შერიგების შემდეგ. თუ მეტამონაცემები მიუწვდომელია, გამოიყენება კონფიგურირებული ტარიფის სნეპშოტი; წინააღმდეგ შემთხვევაში, ღირებულება უცნობია.
- წამებს, სიმბოლოებს და გამოსახულების რაოდენობას აქვს ბილინგის ერთეულის ცალკეული ველები, არასოდეს არის ყალბი ტოკენების რაოდენობა. ბუღალტრული აღრიცხვა ინარჩუნებს მხოლოდ ციფრულ გამოყენებას და არა მეტყველების ტექსტს, ტრანსკრიპტებს ან გამოსახულების ბაიტებს. არსებული უფასო გამონაკლისები უცვლელია: რეალურად დაკარგული გამოსახულების ტარიფი ახლად არ იკეტება შეზღუდული გასაღები და პასუხი გამოტოვებს ხარჯების სათაურს, ვიდრე ზარის უფასო გამოცხადებას. ფასების მაღაზიის უკმარისობა კვლავ ინარჩუნებს გამოყენების მტკიცებულებებს წარუმატებლობის დახურვის აღსრულებისთვის.

არცერთი ისტორიული speech/image გადასახადი არ არის გამოგონილი ან შევსებული. პროვაიდერის ბილინგი რჩება მითითებად ინვოისებისთვის და ზარებისთვის, რომელთა გადასახადი არ იყო მოხსენებული.

  ხედები.

## CLI

OmniRoute-ის CLI გთავაზობთ ღირებულების, გამოყენებისა და ფასების ბრძანებებს (რეგისტრირებულია
[`bin/cli/commands/registry.mjs`](../../bin/cli/commands/registry.mjs)-ში).

### `omniroute cost`

ღირებულების ანგარიში, აგრეგირებული `/api/usage/analytics`-დან.

```bash
omniroute cost                          # ბოლო 30 დღე, დაჯგუფებული პროვაიდერის მიხედვით
omniroute cost --period 7d              # ბოლო 7 დღე
omniroute cost --group-by model         # დაჯგუფება: provider | model | combo | api-key | day
omniroute cost --since 2026-06-01 --until 2026-06-13
omniroute cost --api-key <key> --limit 50
```

სვეტები: ჯგუფი, მოთხოვნები, შემავალი/გამავალი ტოკენები, ღირებულება (USD) და საერთო
ღირებულების %. საბოლოოდ იბეჭდება ჯამური შედეგის სტრიქონი (ითიშება `--quiet`-ით ან
`--output json`-ით).

### `omniroute usage`

```bash
omniroute usage analytics --period 30d [--provider <id>]   # ღირებულების შეჯამება თითოეული პროვაიდერისთვის
omniroute usage logs [--limit 100] [--follow] [--api-key <k>] [--search <q>]
omniroute usage quota [--provider <id>] [--check]
omniroute usage utilization [--api-key <k>]
omniroute usage history [--limit 100]
omniroute usage proxy-logs [--limit 100]

# ბიუჯეტები
omniroute usage budget list
omniroute usage budget get [scope]
omniroute usage budget set <amount> [--scope global] [--period monthly]
omniroute usage budget reset [scope]
```

### `omniroute pricing`

```bash
omniroute pricing list [--provider <p>] [--model <m>] [--limit 200]
omniroute pricing get <model>
omniroute pricing sync [--provider <p>] [--force]   # POST /api/pricing/sync
omniroute pricing diff [--model <m>]
omniroute pricing defaults show
omniroute pricing defaults set [--input <p>] [--output <p>] [--cache-read <p>] [--cache-write <p>]
```

> `pricing defaults show` კითხულობს `GET /api/pricing/defaults`-ს. ცალკეული მოდელების
> ფასების შესაცვლელად გამოიყენეთ მართვის პანელის **Pricing** გვერდი ან `PATCH /api/pricing`.

  ანალიტიკის ყოველი წაკითხვისას ღირებულება თავიდან გამოითვლება ტოკენების რაოდენობის მიხედვით,
  ამიტომ შეფასებები რეტროაქტიულად განახლდება.
