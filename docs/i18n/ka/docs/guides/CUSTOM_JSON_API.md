მორგებული JSON API კვანძი აკავშირებს JSON ბიზნეს საბოლოო წერტილს, რომელიც არ საუბრობს OpenAI ან Anthropic პროტოკოლზე. OmniRoute ავსებს JSON მოთხოვნის შაბლონს, აგზავნის მას სრულ საბოლოო წერტილში URL, კითხულობს პასუხს პასუხის ბილიკიდან და უბრუნებს მას კლიენტს კლიენტის საკუთარი ფორმატით (ჩეთის დასრულებები, პასუხები, შეტყობინებები, ...).

ეს არის OpenAI-თან თავსებადი კვანძი `apiType: "custom-json"` სთან; მის id-ს აქვს ფორმა `openai-compatible-custom-json-<suffix>`. დაფის ფორმა ჯერ არ არის ხელმისაწვდომი. შექმენით და შეცვალეთ ეს კვანძები ქვემოთ მოცემული პროვაიდერის კვანძის API მეშვეობით.

## შექმენით კვანძი

`POST /api/provider-nodes` (მენეჯმენტის ავტორიზაცია):

```json
{
  "type": "openai-compatible",
  "apiType": "custom-json",
  "name": "Business API",
  "prefix": "biz",
  "baseUrl": "https://api.example.com/v1/answer",
  "customHeaders": { "X-Tenant": "demo" },
  "customJson": {
    "method": "POST",
    "authType": "api-key",
    "authHeader": "X-Service-Key",
    "requestTemplate": {
      "project_id": "demo-project",
      "question": "{{prompt}}",
      "history": "{{messages}}"
    },
    "responsePath": "data.answer"
  }
}
```

- `baseUrl` არის** სრული** ბოლო წერტილი URL. არაფერი არ არის დამატებული (არ არის `/chat/completions`, არა `/models`) და, განსხვავებით სხვა OpenAI-თან თავსებადი კვანძებისგან, არ არის ნაგულისხმევი URL. ის უნდა იყოს `http(s)`, ჩაშენებული სერთიფიკატების ან `#fragment` გარეშე და გადის იგივე გამავალი URL მცველი, როგორც ყველა პროვაიდერის კვანძი, როგორც კვანძის შენახვისას, ასევე ყველა მოთხოვნისას.
- კვანძმა, რომელიც აგზავნის კავშირის გასაღებს (`authType` `bearer` ან `api-key`, ნაგულისხმევის ჩათვლით) უნდა გამოიყენოს `https://`. Plain `http://` მიიღება მხოლოდ loopback ჰოსტისთვის (`localhost`, `127.0.0.0/8`, `::1`) ან `authType: "none"` ით, რომელიც არ აგზავნის გასაღებს. პირადი LAN მისამართები (`10.x`, `172.16-31.x`, `192.168.x`) არ არის გათავისუფლებული: ამ ქსელში ნებისმიერს შეეძლო გასაღების წაკითხვა. ასეთი კვანძის შენახვა ვერ ხერხდება `400` ით, ხოლო ადრე შენახული კვანძი ვერ იხურება ყველა მოთხოვნაზე იმავე შეტყობინებით, სანამ რაიმე მოთხოვნა გაიგზავნება. LAN ზე დაჭერილი ბოლო წერტილისთვის, ჩადეთ იგი TLS უკან (მაგალითად, საპირისპირო პროქსი).
- `customJson` დამოწმებულია Zod ით; უცნობი გასაღებები უარყოფილია. ყველა ველი არჩევითია:

| ველი              | ღირებულებები                               | ნაგულისხმევი                                           |
| ----------------- | ------------------------------------------ | ------------------------------------------------------ |
| `method`          | `POST`, `PUT`, `PATCH`                     | `POST`                                                 |
| `authType`        | `bearer`, `api-key`, `none`                | `bearer`                                               |
| `authHeader`      | სათაურის სახელი გამოიყენება `api-key` დროს | `X-API-Key`                                            |
| `requestTemplate` | JSON ობიექტი (≤ 64 KB, სიღრმე ≤ 32)        | `{ "model": "{{model}}", "messages": "{{messages}}" }` |
| `responsePath`    | საველე გზა, ან `$` მთელი სხეულისთვის       | `choices[0].message.content`                           |

- საიდუმლო რჩება კავშირის API კლავიშში და არასდროს შაბლონში. `bearer` აგზავნის `Authorization: Bearer <key>`; `api-key` აგზავნის `<authHeader>: <key>`. auth სათაური არ შეიძლება იყოს `Host`, `Content-Type`, `Content-Length`, `Connection`, `Transfer-Encoding`, `Authorization`, `Cookie` ან hop-by-hop სათაური. `none` ით კავშირებს გასაღები არ სჭირდება.
- დამატებითი სტატიკური სათაურები იყენებენ კვანძის რეგულარულ `customHeaders` ს (იგივე ვალიდაცია, როგორც ყველა სხვა თავსებადი კვანძი; auth სათაურები დაუშვებელია).

`PUT /api/provider-nodes/<id>` იღებს იგივე `customJson` და ხელახლა წერს `baseUrl` და კონფიგურაციას კვანძის ყველა არსებულ კავშირზე. `customJson` გამოტოვება ინახავს შენახულ კონფიგურაციას; `apiType` ზე `chat` ზე ან `responses` გადართვა აშორებს მას კვანძიდან და მისი კავშირებიდან.

შემდეგ დაამატეთ კავშირი კვანძთან ჩვეულებისამებრ (`POST /api/providers` კვანძის id-ით) და მოითხოვეთ `<prefix>/<model>`, მაგალითად `biz/assistant-v1`. საბოლოო წერტილი არ ავლენს მოდელების სიას, ამიტომ დაამატეთ მოდელის ID ხელით.

## მოითხოვეთ შაბლონები

შაბლონები არის უბრალო JSON. სტრიქონის მნიშვნელობა შეიძლება შეიცავდეს `{{placeholder}}` მარკერებს; არაფერი არ არის შეფასებული ან შესრულებული და ობიექტის გასაღებები არასოდეს იცვლება.

| ადგილის დამჭერი      | ღირებულება                                                                       |
| -------------------- | -------------------------------------------------------------------------------- |
| `{{prompt}}`         | მომხმარებლის უახლესი შეტყობინების ტექსტი (ტექსტის ნაწილები შეუერთდა ახალ ხაზებს) |
| `{{messages}}`       | საუბარი OpenAI ჩატის ფორმატში                                                    |
| `{{model}}`          | მოთხოვნილი მოდელის ID, პროვაიდერის პრეფიქსის გარეშე                              |
| `{{stream}}`         | ყოველთვის `false` — საბოლოო წერტილი პასუხობს ერთი JSON დოკუმენტით                |
| `{{request.<path>}}` | თარგმნილი (OpenAI ჩატის ფორმატი) მოთხოვნის ველი                                  |

- მნიშვნელობა, რომელიც არის ზუსტად ერთი ადგილი, ინარჩუნებს თავის JSON ტიპს (`"{{messages}}"` ხდება მასივი); ჩანაცვლების ადგილი უფრო გრძელი სტრიქონის შიგნით ჩასმულია ტექსტად.
- ჩანაცვლების დამფუძნებელი, რომელიც არაფერს წყვეტს, არღვევს მოთხოვნას HTTP 400-ით არასრული დატვირთვის გაგზავნის ნაცვლად.
- ბილიკები იყენებენ წერტილოვან აღნიშვნას და ციფრულ ინდექსებს (`data.items[0].text`). `__proto__`, `prototype` და `constructor` უარყოფილია გასაღებებში და ბილიკებში.

## პასუხები

მნიშვნელობა `responsePath` ზე ხდება ასისტენტის პასუხი: სტრიქონები გადის, სხვა JSON მნიშვნელობები სერიულირდება. გამოტოვებული ან `null` ველი, ან სხეული, რომელიც არ არის JSON, აბრუნებს HTTP 502-ს. ზედა ნაკადის შეცდომის სტატუსები გადადის. სტრიმინგის კლიენტებისთვის OmniRoute ელოდება მთელ JSON პასუხს და შემდეგ ასხივებს მას, როგორც ერთი შინაარსის ნაწილს პლუს დასრულების ნაწილი; ეს არ არის სიმბოლური ნაკადი. ხელსაწყოების ზარები და გამოყენების ველები არ არის შედგენილი.

## არასოდეს გამეორებულა

ბიზნეს მოთხოვნას შეიძლება ჰქონდეს გვერდითი მოვლენები მაშინაც კი, როდესაც ის ვერ მოხერხდება. ამიტომ OmniRoute აგზავნის ერთხელ:

- ტრანსპორტის ხელახალი ცდა და შემდგომი გადამისამართების გარეშე;
- სხვა კავშირზე ხელახლა არ სცადოთ (ანგარიშის უკან დაბრუნება) — წარუმატებლობა დაბრუნდა როგორც არის და კავშირი არ გაცივდა;
- შემდეგი კომბინირებული სამიზნეზე დაბრუნება არ არის, თუნდაც ცარიელი ან წარუმატებელი პასუხისთვის.

კლიენტის ცალკეული მოთხოვნები და შერწყმის პანელები, რომლებიც ცალსახად იძახებენ რამდენიმე მოდელს, მაინც დამოუკიდებლად იწვევენ საბოლოო წერტილს.

## კვანძის ტესტირება

კავშირის შენახვა, კავშირი** ტესტი** ღილაკებისა და ფონის ჯანმრთელობის შემოწმებები არასოდეს იძახიან საბოლოო წერტილს: ისინი მხოლოდ ამოწმებენ შენახულ კონფიგურაციას და აცნობებენ კავშირს, როგორც შეუმოწმებელი.

`POST /api/provider-nodes/validate` `"apiType": "custom-json"` და კვანძის ველებით (`baseUrl`, `apiKey`, `customJson`, სურვილისამებრ `customHeaders` და `modelId`) აგზავნის ზუსტად ერთ რეალურ მოთხოვნას, `ping`, როგორც მომხმარებლის უახლესი ტექსტი. ის პასუხობს `{ "valid": true }` ან ზედა დინების სტატუსს (არასდროს ზედა დინების სხეულს).

## შენახვა

კონფიგურაცია ინახება `provider_nodes.custom_json_config_json` ში (მიგრაცია `240_provider_node_custom_json_config.sql`) და კოპირებულია თითოეული კავშირის `providerSpecificData.customJson` ში.
