ნეიტრალური `config/cli-tools-manifest.json` კონტრაქტი აცხადებს კანონიკურ IDs, მეტსახელებს, ბინარულ კანდიდატებს, დაყენების რეცეპტებს, მოდელის არგუმენტებსა და შესაძლებლობებს. ჩვეულებრივი Node ადაპტერი `bin/cli/cli-manifest.mjs` ში და TypeScript ადაპტერი `src/shared/constants/cliIntegrationManifest.ts` ში კითხულობს იმავე ფაილს. გაშვების დრო, კატალოგი, კონფიგურაცია, დასრულება, გენერატორები და backend რეგისტრაცია ერთად შემოწმებულია `tests/unit/cli/cli-manifest-drift.test.ts` მიერ. კატალოგში ყოფნა არ ნიშნავს იმას, რომ ინსტრუმენტის გაშვება ან კონფიგურაცია შესაძლებელია. კერძოდ, 5dive რჩება მხოლოდ კონფიგურაციისთვის.

## ბავშვის გარემო და ცხოვრების ციკლი

`omniroute run`, `omniroute launch` და `omniroute launch-codex` მემკვიდრეობით იღებენ OS/terminal თავსებადობის ნებადართულ სიას და შეაქვთ შერჩეული სამიზნის სერთიფიკატები. დაუკავშირებელი პროვაიდერის და მონაცემთა ბაზის საიდუმლოებები ნაგულისხმევად არ არის მემკვიდრეობით მიღებული. `--inherit-env` ცალსახად აღადგენს მშობლების გარემოს სრულ მემკვიდრეობას; გამოიყენეთ იგი მხოლოდ მაშინ, როდესაც არჩეულმა მესამე მხარის პროცესმა უნდა მიიღოს ეს მნიშვნელობები. ეს არის გარემოს ფილტრაცია და არა OS sandbox: პროცესი კვლავ მუშაობს აბონენტის ფაილური სისტემის ნებართვებით.

შეწყვეტის და შეწყვეტის სიგნალები გადაეგზავნება ბავშვს. გამშვები ელოდება ბავშვის ახლო მოვლენას დროებითი კონფიგურაციის წაშლამდე. `OMNIROUTE_CHILD_SIGNAL_TIMEOUT_MS` აკონტროლებს საშეღავათო პერიოდს იძულებით შეწყვეტამდე (ნაგულისხმევი 5000 მილიწამი).

## Gemini მუდმივი დაყენება

```bash
omniroute setup-gemini --remote https://omni.example --model provider/model --yes
omniroute configure gemini --model provider/model --yes
omniroute run gemini --model provider/model --dry-run --json
```

პირველი ორი ბრძანება აკონფიგურირებს ამ მანქანას არჩეული ლოკალური ან დისტანციური სერვერისთვის. Setup ინახავს დაუკავშირებელ JSON პარამეტრებს, ირჩევს Gemini API-გასაღების ავტორიზაციას და წერს საბოლოო წერტილს და რწმუნებათა სიგელებს კერძო `.gemini/.env` ფაილში. ის უარს ამბობს არასწორ JSON, ვიდრე გადაწერს. ბოლო წერტილი URLs უნდა იყოს HTTP(S), ჩაშენებული სერთიფიკატების, მოთხოვნის პარამეტრების ან ფრაგმენტების გარეშე. მშრალი გაშვება ბეჭდავს ბილიკებს და არა ავტორიზაციის მნიშვნელობებს.

`GEMINI_CLI_HOME` ან `--gemini-home` ირჩევს მუდმივ მთავარ ფესვს. რეალური `run gemini` ქმნის და მოგვიანებით შლის საკუთარ დროებით სახლს. არც ერთი რეჟიმი გვერდს არ უვლის Gemini ის სამუშაო სივრცის ნდობის შემოწმებებს.

## Codex პროფილები

`configure codex` წერს კერძო `<name>.config.toml` მოდელით და მისი OmniRoute პროვაიდერის საბოლოო წერტილით. სერთიფიკატების მითითება ხდება `OMNIROUTE_API_KEY` მეშვეობით, არასოდეს არის ჩაშენებული. გაშვების ბრძანება აყენებს არჩეულ მოდელს ზედა დონის `model` კლავიშზე და არა `model_providers` ში.

ცალკე პროფილის ფაილები არის მიმდინარე დოკუმენტირებული Codex კონტრაქტი; ისინი აფარებენ მომხმარებლის კონფიგურაციას `codex --profile <name>` ით არჩევისას. იხილეთ [პროფილის ოფიციალური მითითება](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles) და [OmniRoute Codex სახელმძღვანელო](./CODEX-CLI-CONFIGURATION.md).

## ჰერმეტული ბრძანების შესრულება

აშკარა `DATA_DIR` ით, `OMNIROUTE_CLI_SKIP_DEFAULT_DATA_ENV=1` დაყენება ხელს უშლის გაშვებას ნაგულისხმევი მომხმარებლის მონაცემების დირექტორიაში რწმუნებათა სიგელების გარემოში ჩავარდნას. ეს სასარგებლოა იზოლირებული ტესტებისთვის. ის არ გამორთავს სხვა აშკარად შერჩეულ გარემო ფაილებს.

## სამუშაო-ცნობარი `.env`

CLI კითხულობს `.env` ფაილებს ამ თანმიმდევრობით და იმარჯვებს პირველი ფაილი, რომელმაც დააყენა გასაღები: აშკარა `DATA_DIR`, მონაცემთა ნაგულისხმევი დირექტორია, მიმდინარე სამუშაო დირექტორია, შემდეგ პაკეტის დირექტორია. Shell ცვლადები ყოველთვის იმარჯვებენ.

სამუშაო დირექტორია შეიძლება ეკუთვნოდეს ვინმეს (კლონირებული საცავი, დაუფასოებელი არქივი) და `omniroute serve` გადასცემს CLI გარემოს სერვერს და ყველა ხელსაწყოს, რომელსაც სერვერი აწარმოებს. ასე რომ, `.env` შეუძლია დააყენოს მხოლოდ ეს კლავიშები, რომლებიც ჩამოთვლილია `bin/cli/utils/untrustedCwdEnv.mjs` ში:

| გასაღები                        | მიღებული ღირებულებები                                                                       |
| ------------------------------- | ------------------------------------------------------------------------------------------- |
| `REQUIRE_API_KEY`               | `true`, `1` ან `yes` ნებისმიერ შემთხვევაში, მნიშვნელობებს სერვერი განიხილავს როგორც ჩართულს |
| `LANG`, `LC_ALL`, `LC_MESSAGES` | 64-მდე ასო, ციფრი, `_`, `.`, `@` ან `-`                                                     |
| `LANGUAGE`                      | იგივე, პლუს `:`                                                                             |
| `TZ`                            | 64-მდე ასო, ციფრი, `_`, `+`, `-` ან `/`, არ იწყება `/` ით                                   |
| `NO_COLOR`, `FORCE_COLOR`       | 16-მდე ასო და ციფრი                                                                         |

ყოველი მნიშვნელობა, რომელსაც `REQUIRE_API_KEY` იღებს, ჩართავს შემოწმებას, ასე რომ, ფაილი თავად ვერ გამორთავს შემოწმებას. ის არ წყვეტს შედეგს, თუმცა: სერვერი კითხულობს მონაცემთა ბაზაში შენახულ `REQUIRE_API_KEY` გადაფარვას გარემოს წინ, ხოლო გაშვების გაფრთხილება ყველა ინტერფეისზე API კლავიშის გარეშე მოსმენის შესახებ კითხულობს მხოლოდ გარემოს. `false` ის შენახული გადაფარვით, სამუშაო დირექტორია `REQUIRE_API_KEY=true` ტოვებს API ს ღიად და მალავს ამ გაფრთხილებას. `TZ` წესი უფრო ვიწროა ვიდრე POSIX: ის უარყოფს `.`, `:`, `,` და `<>`, ამიტომ `:Area/City` ფორმა და წესები, როგორიცაა `EST5EDT,M3.2.0,M11.1.0` უნდა იყოს მითითებული ჭურვიში ან `<DATA_DIR>/.env` ში.

სახელები ზუსტად უნდა ემთხვეოდეს, დიდი ასოებით. ნებისმიერი სხვა ხაზი, მნიშვნელობა, რომელიც ვერ შემოწმდება და სახელი, რომელიც არ არის ჩვეულებრივი ASCII ასოები, ციფრები და `_` (მაგალითად, ერთი NUL ბაიტით ან მსგავსი ასოებით) გამოტოვებულია. CLI ბეჭდავს ერთ გაფრთხილებას, რომელიც ასახელებს კლავიშებს, რომელთა დაყენება შეუძლებელია და ერთი, რომელიც ასახელებს დაშვებულ კლავიშებს, რომლებიც იგნორირებულია, თითოეულში რა უნდა შეიცვალოს (`TZ (expected a zone name such as Europe/Berlin)`, `lang (write the name as LANG)`). არც ბეჭდავს მნიშვნელობებს. ფაილის ბილიკები ამ შეტყობინებებში, და `.env` ბილიკი `omniroute doctor` ანგარიშები, გაურკვეველია, როდესაც ისინი შეიცავს საკონტროლო ან bidi სიმბოლოებს. შეზღუდვა არ ვრცელდება, როდესაც სამუშაო დირექტორია არის მონაცემთა დირექტორია ან პაკეტის დირექტორია.

`PORT`, `API_PORT` და `DASHBOARD_PORT` არ არის სიაში. უფრო მაღალი პრიორიტეტული წყაროდან URL ის გარეშე, CLI ესაუბრება `localhost:<PORT>` ს და რაც მოისმენს იქ იღებს CLI ის API კლავიშს, კონტექსტურ ჟეტონს და CLI მანქანის ჟეტონს (`x-omniroute-cli-token`, იხილეთ [CLI_TOKEN.md](../security/CLI_TOKEN.md) ), რომელსაც ადგილობრივი სერვერი იღებს სამართავი ზარებისთვის loopback-დან. სამუშაო დირექტორიადან პორტი საშუალებას აძლევს ამ ფაილს აირჩიოს მსმენელი, ამიტომ დააყენეთ პორტები ჭურვიში, `<DATA_DIR>/.env` ში ან ბრძანებების `--port` ვარიანტით, რომლებსაც აქვთ ერთი (`serve`, `launch`, `run`).

პარსერს არ აქვს `export` სინტაქსი. ხაზი, როგორიცაა `export LD_PRELOAD=...` ასახელებს ცვლადს `export LD_PRELOAD`; სამუშაო დირექტორიადან ის გამოტოვებულია და სხვა `.env` ფაილებში აყენებს იმ ლიტერატურულ სახელს, რომელსაც არაფერი კითხულობს.

CLI აწყვილებს კონტექსტის შენახულ ჟეტონს (წვდომის ჟეტონი ან მოძველებული API გასაღები) მხოლოდ ამ კონტექსტის საწყისთან: სქემასთან, ჰოსტთან და პორტთან შედარებით `URL.origin` თან. ეს ეხება CLI ის HTTP კლიენტის მეშვეობით შესრულებულ მოთხოვნებს (`--base-url`, `OMNIROUTE_BASE_URL`, `omniroute connect <new-url>`) და `launch`, `launch codex`, `configure` და `setup-*` ბრძანებებს, რომლებიც წერენ საბაზისო URL და კლავიშს სხვა ხელსაწყოს კონფიგურაციაში. მითითებულ სხვა სერვერზე `--remote`, ისინი იყენებენ გამოკვეთილ `--api-key` ან `OMNIROUTE_API_KEY`, თუ ერთი დაყენებულია, და კონტექსტური ნიშნის გარეშე. შედარება ზუსტია, ამიტომ `localhost` და `127.0.0.1`, ან ჰოსტი ბოლო წერტილით და მის გარეშე, ითვლება სხვადასხვა სერვერად და არ იღებენ კონტექსტურ ნიშანს. URL მომხმარებლის ინფორმაციის, უკუღმა ან თეთრი სივრცით არასოდეს ემთხვევა, რადგან სხვა URL პარსერებს (მაგალითად, Python-ის `urllib` და `httpx`) შეუძლიათ მისგან განსხვავებული ჰოსტის წაკითხვა. მოთხოვნებისთვის CLI აგზავნის საკუთარ თავს, ეს ჩეკი მოიცავს მხოლოდ სქემას და ავტორიტეტს, ასე რომ, id, რომელსაც აქვს სივრცე გზაზე ან მოთხოვნაში, ინახავს ჟეტონს.
