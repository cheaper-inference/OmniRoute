ეს დოკუმენტი OmniRoute-ში CI-ის ხარისხის ყველა ბარიერის ავტორიტეტული ცნობარია.
იგი აღწერს თითოეულ ბარიერს, რას ამოწმებს ის, რომელ CI დავალებაში სრულდება, იყენებს თუ არა
ეტალონის ეტაპობრივი გამკაცრების ან ჩაბარება/ჩავარდნის პოლიტიკას და ბლოკავს თუ არა აგებას, თუ მხოლოდ სარეკომენდაციო ხასიათი აქვს.

მოკლე შეჯამებისა და დაშვებული გამონაკლისების სიის პოლიტიკისთვის იხილეთ სექცია „Quality Gates & Ratchets“
ფაილში `AGENTS.md`. იმავე სისტემის კრიტიკული შეფასების, სიმწიფის კლასიფიკაციისა და კონკრეტულ ხელსაწყოებზე დამოუკიდებელი
გამეორების გეგმისთვის იხილეთ
[ხარისხის ბარიერების სახელმძღვანელო](../ops/QUALITY_GATE_PLAYBOOK.md).

## გეითების ინვენტარი და შესრულების პროფილები

### კანდიდატის დაშვება

CI-ისა და Quality Gates-ის სამუშაო პროცესები თითოეული გასცემს სტაბილურ ვერდიქტს: `Gate / CI` და
`Gate / Quality`. მათი ვერსირებული დაშვების პოლიტიკა თითოეულ ზედა დონის დავალებას
სავალდებულოდ ან სარეკომენდაციოდ განსაზღვრავს. შესაბამისი სავალდებულო დავალება წარმატებით უნდა დასრულდეს:
არარსებული, გაუქმებული, გამოტოვებული, მოლოდინის რეჟიმში მყოფი და უცნობი შედეგები PASS-ს ვერ ადასტურებს. მხოლოდ
დოკუმენტაციასთან ან მხოლოდ კატალოგთან დაკავშირებული მართებული კლასიფიკაციით კოდის შესრულების ზოლი შეიძლება შეუსაბამო გახდეს;
PR-ის მონახაზი მიღებულ კანდიდატად არ ითვლება. `hotfix` ჭდე მტკიცებულების მოთხოვნას არ აუქმებს.

ორივე სამუშაო პროცესი მოიცავს PR-ებს main/release ბრენჩების მიმართულებით, `main`-ზე push-ებს, ხელით გაშვებას
და merge-group-ის მოვლენებს. Push, dispatch და merge-group სრულ შერჩევას უშვებს. Push-ები
`release/**`-ზე მათ არ უშვებს (2026-10-18): თითოეულმა ცვლილებამ მატრიცა უკვე გაიარა საკუთარ PR-ზე,
ხოლო გაერთიანებული კომბინაცია Release-Green-ის ამოცანაა (`docs/ops/RUNNER_BOX.md` → Hosted ზოლი). Fork-ები
და merge group-ები იმ დავალებებისთვის, რომლებიც სხვა შემთხვევაში self-hosted
runner-ებს ირჩევს, hosted runner-ებს იყენებს; დანერგვამდე საკმარისი hosted სიმძლავრე უნდა გადამოწმდეს.

თითოეული JSON ქვითარი მიუთითებს checkout-ის SHA-ს, სამუშაო პროცესის გაშვებასა და მცდელობას.
CLI უარყოფს checkout-ისა და მოვლენის SHA-ების შეუსაბამობას. სამუშაო პროცესის ტესტები პოლიტიკის წევრობას
ვერდიქტის დავალების `needs` სიას უკავშირებს, რათა ახალი ან ამოღებული ზოლი შეუმჩნევლად არ გაქრეს.
ქვითრები მოიცავს საკუთარ სამუშაო პროცესს და არა გამოქვეყნებას, განთავსებას ან არსებული საკონსულტაციო სკანერის შიდა მექანიზმებს. შესაბამისი შემოწმებების branch rules-ში სავალდებულოდ განსაზღვრა ცალკე ადმინისტრაციული ცვლილებაა; მათი დავალებების განსაზღვრა თავისთავად branch-ს არ იცავს.

`API Route Typecheck` დამოუკიდებელი სამუშაო პროცესის შემოწმებაა, რომელიც არ შედის არც ერთ აგრეგირებულ ვერდიქტში და არც ლოკალური სრული დამკვირვებლის სტატიკურ პროფილში. ზუსტი კანდიდატისთვის მისი შედეგი ცალკე შეამოწმეთ. `.github/workflows/api-route-typecheck.yml` ეშვება `main` ან `release/**` branch-ში მიმართულ PR-ებზე, რომელიმე branch-ის ოჯახში push-ისას და ხელით გაშვებისას. მას path filter არ აქვს. PR-ის base-ის შეცვლა ახალ შემოწმებას მოითხოვს; body/title-ის რედაქტირებები იყენებს მხოლოდ დაკვირვებისთვის განკუთვნილ სახელს `Admission not requested / API Route Typecheck` და admission check-ს ვერ ჩაანაცვლებს. სამუშაო პროცესი merge-group trigger-ს არ აცხადებს. merge queue-ის ნებისმიერმა დანერგვამ, რომელიც ამ შემოწმებას მოითხოვს, ჯერ ამ event-ისთვის მისი შესრულება უნდა უზრუნველყოს.

### UI-ის შესრულების სიმძლავრე

CI UI-ის სრულ ინვენტარს ოთხი `test-vitest` მატრიცული შარდის სახით უშვებს, თითოეულში არაუმეტეს
ორი worker-ითა და არსებული 15-წუთიანი დავალების ვადით. პირველი შარდი ასევე უშვებს
MCP/autoCombo Vitest კომპლექტს. სავალდებულო დავალების შედეგი მატრიცის ყველა განშტოებას მოიცავს; ერთი
შარდის წარუმატებლობა ან გაუქმება კანდიდატის დაშვებას ვერ ადასტურებს.

ღამის დამკვირვებელი UI-ის თითოეული შარდისთვის ინარჩუნებს ზუსტი კანდიდატის ცალკე ქვითარს,
პირველ ქვითარში MCP-ის შესრულების ჩათვლით. საჭიროა ოთხივე ქვითარი, ჟურნალი და შესაბამისი
შესრულების იდენტობა. ლოკალური `npm run test:vitest:ui` კვლავ სრულ
კომპლექტს ირჩევს; მხოლოდ ერთი `--shard` გაშვება ნაწილობრივი მტკიცებულებაა.

### Unit coverage-ის შეგროვება

თორმეტი unit შარდი არსებული ტესტების შესრულებისას V8 coverage-ს აგროვებს. წარმატებული
შარდი თავდაპირველი ფაილების შუალედური Istanbul ანგარიშის შექმნის გარეშე შესაკუმშად
`scripts/ci/compact-v8-coverage.mjs`-ს უშვებს. საბოლოო Coverage დავალება თორმეტივე მანიფესტს
კანდიდატის SHA-სთან, runtime-თან, წყაროს root-თან და მონაცემთა ჰეშებთან მიმართებით ამოწმებს, შემდეგ კი c8-ის
რეპორტერებსა და coverage-ის არსებულ ზღვრებს უშვებს. შემავალი მონაცემები ინარჩუნებს c8-ის ფაილთა სახელების გლობალურ
მიმდევრობას; ფუნქციის/ბლოკის შერეული coverage-ისთვის თითოეული შარდის წინასწარი გაერთიანება სახიფათოა.
არარსებული, არასწორად ფორმირებული ან შეუთავსებელი შარდები დაშვებას წარუმატებელს ხდის.
წარუმატებელი სატესტო შარდები ნედლ დიაგნოსტიკურ coverage-ს ცალკე ინარჩუნებს; ის საბოლოო გაერთიანებაში ვერ მოხვდება.

### მოდულური ტესტების შესრულების პროგრესის ქვითრები

საერთო `test:unit:ci:shard` ბრძანება `primary`, `dashboard` და `serial`
ფაზებს `scripts/ci/unit-progress-reporter.mjs`-ის მეშვეობით აღრიცხავს. ტესტირების ჩვეულებრივი ანგარიში კვლავ
ხელმისაწვდომია. ცალკე, მხოლოდ მეტამონაცემების შემცველი ქვითარი აღრიცხავს თითოეული ფაილის დაწყებასა და დასრულებას,
ხოლო 30-წამიანი გულისცემის სიგნალი ჩამოთვლის ჯერ კიდევ აქტიურ ფაილებს და მათი შესრულების გასულ დროს. ის აღრიცხავს
მხოლოდ ნებადართულ სიაში შეტანილ შესრულების მეტამონაცემებს; ტესტების აღწერილობები, გამომავალი მონაცემები, შეცდომების შიგთავსი და სრული
გარემო არ სერიალიზდება.

CI და Quality JSONL ფაილებს ინახავენ სახელებით `unit-progress-ci-<run>-<attempt>-<shard>` და
`unit-progress-quality-<run>-<attempt>-<shard>`. დავალების დროის ამოწურვამ შეიძლება ხელი შეუშალოს შემდგომ ატვირთვას;
უკვე გაგზავნილი გულისცემის სიგნალები დიაგნოსტიკურ მტკიცებულებად რჩება. გულისცემის სიგნალების არარსებობა ასევე შეიძლება
მიუთითებდეს დაბლოკილ ან შეწყვეტილ გამშვებ პროცესზე. ეს ქვითრები უცვლელად ინარჩუნებს ტესტების არსებულ შერჩევას,
პარალელურობას, ვადებსა და გასვლის სტატუსს; ისინი კანდიდატის დაშვების შესახებ გადაწყვეტილებები არ არის.

### შენახული მტკიცებულებები მიღების შედეგების შემაჯამებელში

`scripts/quality/validate-release-acceptance.mjs` აჯამებს მიწოდებულ გეგმასა და მის მანიფესტებს; ის არ ადასტურებს, რომ გეგმა გამოშვების სრულ პროცესს მოიცავს. მისი ანგარიშები აშკარად ადგენს `releaseAcceptance: false`-ს მაშინაც კი, როცა გეგმა `VERIFIED` არის. `release-acceptance.yml` სამუშაო პროცესი კვლავ shadow სატესტო მონაცემებს იყენებს და არა აგების, შეფუთვის, გაშვების ან შემდეგ ეტაპზე გადატანის ნამდვილ ქვითრებს.

შენახული მტკიცებულებების შესამოწმებლად CLI-ს სჭირდება `--evidence-root`. ფაილები მოიძებნება გზით `<evidence-root>/<artifact_id>/<member>` და ითვლება მათი SHA-256 ჰეში. მტკიცებულების გარეშე PASS ჩანაწერი, დაკარგული ან შეცვლილი ფაილი, არაუსაფრთხო გზა ან სიმბოლური ბმული ვერიფიკაციას ხელს უშლის. დაკარგული ფაილები წარმატებული გაშვების ცარიელ ჟურნალებს არ უდრის. არსებული SHA/run/attempt შემოწმებები დამოუკიდებელი რჩება: შესაბამისი ბაიტები მოძველებულ ქვითარს ვალიდურს ვერ გახდის. ფაილის მთლიანობა არ არის შესრულების ნამდვილობის ან არტეფაქტის შემდეგ ეტაპზე გადატანის მტკიცებულება.

### სტატიკური სკანირების ინვენტარი

ვერსირებული npm-ალიასების ინვენტარი და სტატიკური სკანირების წევრობა ინახება
`config/quality/gate-manifest.json`-ში. სკრიპტების სახელებისა და ზუსტი ბრძანებების
`package.json`-თან შესამოწმებლად გაუშვით `npm run check:gate-manifest`; დამატებები, ამოღებები და
ბრძანებების გადახრები წარუმატებელს ხდის როგორც ლოკალურ hook-ს, ისე CI-ში ცვლილებების კლასიფიკაციის დავალებებს.
ალიასი არ არის სამუშაო პროცესის დავალება, მატრიცის ეგზემპლარი ან სატესტო შემთხვევა: ეს რაოდენობები
ურთიერთჩანაცვლებადად არ უნდა იყოს წარმოდგენილი.

შერჩეული ალიასების შესრულების გარეშე სანახავად გამოიყენეთ `npm run quality:scan -- --list` ან
`npm run quality:scan:fast -- --list`. Runner npm-ის entrypoint-ს იძახებს, ამიტომ მისი
runtime (მათ შორის Bun, სადაც ის კონფიგურირებულია) შენარჩუნებულია.
მანიფესტი ამ პროფილების მიღმა არსებულ ალიასებს ცალკე გამოძახებულად აღრიცხავს, ხოლო
ტექნიკური მომსახურების ბრძანებები მხოლოდ წაკითხვის სკანირების პროფილებში აკრძალულია.

ეს პროფილები მხოლოდ სტატიკურ სკანირებას მოიცავს. ისინი არ ადასტურებს პროდუქტის ტესტებს,
coverage-ს, პაკეტირებას, გარე შემოწმებებს ან კანდიდატის სრულ მიღებას რელიზისთვის.
სამუშაო პროცესის დაშვება იყენებს დაკავშირებულ `config/quality/admission-policy.json`-სა და
`scripts/quality/admission-verdict.mjs`-ს. Release-observer-ის პროფილები განცალკევებული რჩება;
მათი შესაბამისი შემოწმებები და ქვითრები დამოუკიდებლად შეამოწმეთ. სრული დამკვირვებლის სტატიკური
ბრძანებები გამოცხადებულია `config/quality/release-green-static-profile.json`-ში, მათ შორის
`audit:deps`, mutation-test-ის შერჩევა და თარგმანის შემოწმებები. ჩამტვირთველი npm-ის
ბრძანებებს package.json-ისა და მოდელირებული CI/Quality დეკლარაციების მიხედვით ამოწმებს; shell-ის ტოკენების
არგუმენტებად შესრულების ნაცვლად, ის გადახრას უარყოფს. სავალდებულო სკანერის SKIP/INCOMPLETE შედეგი
PASS-ს ვერ ადასტურებს. პროფილი აღრიცხავს თავის გარე გამონაკლისებს და არ ანაცვლებს
hosted coverage-ს, ტესტების მატრიცებს, პაკეტის ან განთავსების მტკიცებულებებს. ქვემოთ მოცემული ტექსტური ინვენტარი
საცნობაროა და არა მტკიცებულება იმისა, რომ გეითი მართლაც გაეშვა.

სკრიპტები განთავსებულია `scripts/check/`-ში (პოლიტიკის გეითები) და `scripts/quality/`-ში (ratchet-ის ძრავა).
CI-ის ჭეშმარიტების წყაროა `.github/workflows/ci.yml`.

### გამოქვეყნებული საბაზისო დოკუმენტაციის მდგომარეობა

`.github/workflows/i18n-base-health.yml` აკვირდება დოკუმენტაციის მდგომარეობას `main`-სა და `release/v*`-ზე შერჩეული
push-ების შემდეგ, ასევე ხელით გაშვებისას. მისი ფილტრები მოიცავს დოკუმენტაციას,
ძირეულ Markdown-ს, `llm.txt`-ს, თარგმანის მდგომარეობას/კონფიგურაციას და შესაბამის i18n ინსტრუმენტებს.
ერთადერთი `Published base documentation health` დავალება იყენებს ჰოსტირებულ Ubuntu-ს და ხუთწუთიან
ვადას. ის ასრულებს მხოლოდ წაკითხვად ვალიდაციას და წერს დიაგნოსტიკურ ქვითარს
დამოკიდებულებების ინსტალაციის, თარგმნის ან მდგომარეობის მიღების გარეშე.

`scripts/i18n/check-base-health.mjs` მოითხოვს, რომ წყაროს ჰეშთან, გამოტოვებულ სამიზნესთან, სამიზნის ჰეშთან,
მოძველებულ თარგმანთან და სექციების ქეშთან დაკავშირებული შეუსაბამობების რაოდენობა ნულის ტოლი იყოს. ის ასევე ამოწმებს მიმდინარე ძირითადი
დოკუმენტის/ლოკალის ფარგლებსა და მათ ჩაწერილ წარმომავლობას. არასწორი კონტექსტი, არასრული დაფარვა
ან შემმოწმებლის მუშაობის შეწყვეტა წარმოქმნის `INCOMPLETE`-ს; დადასტურებული აცდენა წარმოქმნის `FAIL`-ს. ორივე
აბრუნებს წარუმატებლობის აღმნიშვნელ დასრულების სტატუსს. ქვითარი მიბმულია checkout SHA-ზე, workflow-ზე, გაშვებასა და
მცდელობაზე და ინახება სახელით `i18n-base-health-<sha>-<run>-<attempt>`.

ეს გამოქვეყნებულ საბაზისო ვერსიაზე დამოუკიდებელი დაკვირვებაა. ის არ ამატებს PR-ის ან
merge-group-ის მოვლენას, სავალდებულო PR შემოწმებას, npm-ის alias-ს ან static-scan პროფილის წევრს.
არსებული დიფერენციალური PR პოლიტიკა და საბაზისო შემმოწმებლის საკონსულტაციო კლასიფიკაციები
კვლავ განცალკევებულია. წარმატებული ატვირთვა ვერ შეცვლის მდგომარეობის წარუმატებელ შედეგს PASS-ად.

#### დავიწყებული მონათესავე ტესტების ანგარიში

`npm run check:forgotten-sibling-tests` ხელახლა იყენებს იმპორტების გადამწყვეტ მექანიზმს, რომელიც ტესტებზე ზემოქმედების რუკის საფუძველია.
ყოველი შეცვლილი სამუშაო მოდულისთვის ის ქმნის დეტერმინისტულ
`changed module/symbol -> static consumer -> candidate sibling test` ჯაჭვებს, როდესაც სავარაუდო
ტესტი pull request-ის განსხვავებებში არ არის. Markdown-ის შეჯამება და JSON-ის შედეგი ინახება
`forgotten-sibling-tests` სამუშაო პროცესის არტეფაქტად, რათა ნებისმიერი დამბლოკავი დანერგვის წინ კალიბრაცია შესრულდეს.

Barrel-ის რეექსპორტები და დინამიკური იმპორტები მხოლოდ გარჩევადობის დიაგნოსტიკაა; ისინი არასოდეს წარმოქმნის
დამბლოკავ აღმოჩენას. განხილული გამონაკლისები ინახება
`config/quality/forgotten-sibling-allowlist.json`-ში. თითოეულ ჩანაწერში მითითებული უნდა იყოს მომხმარებელი და სავარაუდო
ტესტი, მოცემული უნდა იყოს კონკრეტული დასაბუთება და GitHub-ის საკითხის ან pull request-ის ბმული. არასწორად ფორმირებული ჩანაწერები
იწვევს უსაფრთხო დაბლოკვას. გამონაკლისები ვერ ჩაახშობს წაშლილ სავარაუდო ტესტს ან განსხვავებას, რომელიც ამატებს `.skip`/`.todo`-ს;
მტკიცებების შესუსტება და სხვა შენიღბვა კვლავ დამოუკიდებლად დამბლოკავი

#### `check-ui-value-drift` — მოძველებული თარგმანის ბარიერი

ავლენს i18n-ის იმ ერთადერთ რეგრესიას, რომლის დანახვაც სხვა ბარიერებს სტრუქტურულად არ შეუძლიათ: ინგლისური მნიშვნელობა
ხელახლა იწერება, ხოლო _წინა_ ინგლისურიდან მიღებული თარგმანები უცვლელი რჩება, ამიტომ
არაინგლისურენოვანი მომხმარებლები თავდაჯერებულად ფორმულირებულ, მაგრამ უკვე მცდარ ტექსტს კითხულობენ.

ეს რეალურ რელიზშიც მოხვდა. `oauthModal.googleOAuthWarning` ხელახლა დაიწერა, როდესაც Antigravity-ის
შესვლის დამხმარე დაემატა (#5203); **43 ლოკალიდან 39-ში** დარჩა ტექსტი, რომელიც ოპერატორებს ეუბნებოდა, „დააკოპირეთ
სრული URL და ჩასვით ქვემოთ“ — პროცესი, რომელიც ამ პროვაიდერისთვის ვერ სრულდება. ეს
#8463-მდე შეუმჩნეველი დარჩა, რადგან:

- `sync-ui-keys` მხოლოდ **არარსებულ** გასაღებებს ამატებს და არასდროს — **მოძველებულებს**;
- `check-ui-keys-coverage` გასაღების _არსებობას_ ითვლის, ამიტომ მოძველებული თარგმანი დაფარულად მიიჩნევა;
- `check-translation-drift` აკონტროლებს `docs/i18n/<locale>/**.md` დოკუმენტაციის ასლებს —
  ის `src/i18n/messages/*.json`-ს საერთოდ არ კითხულობს. დავალებაში `docs-sync-strict` დამბლოკავია
  2026-09-ის ხელახალი სინქრონიზაციის შემდეგ: შეცვალეთ ძირითადი დოკუმენტი → `npm run i18n:run -- --files=<doc>` (სექციის დონეზე, იაფი).

**ითვალისწინებს სხვაობას და არა საბაზისო ფაილს.** ის შერწყმის საბაზისო წერტილში არსებულ `en.json`-ს
სამუშაო ხეს ადარებს; თითოეული გასაღებისთვის, რომლის ინგლისური მნიშვნელობაც შეიცვალა, ნებისმიერი ლოკალი, სადაც
ხელუხლებელი თარგმანი კვლავ ინახება, მოძველებულად ითვლება. ეს განზრახ **აყინავს მანამდე არსებულ დავალიანებას** — სხვაობით
ვერ დადგინდება, ხანგრძლივად არსებული თარგმანი რომელი ძველი ინგლისური ტექსტიდან მომდინარეობს, ამიტომ ბარიერი
მხოლოდ მიმდინარე ცვლილებით შეხებულ ნაწილს აფასებს. ალტერნატივა (თითოეულ გასაღებზე ჰეშების საბაზისო ფაილი)
მოითხოვდა დაახლოებით 600 KB-იან გენერირებულ ფაილს, რომელიც უდიდეს არსებულ საბაზისო ფაილზე 3-ჯერ დიდი იქნებოდა
და ყოველი i18n PR-ისას შეიცვლებოდა.

მის დასაკმაყოფილებლად ორი გზა არსებობს:

1. განაახლეთ შესაბამისი თარგმანები, ან
2. მათი მნიშვნელობა დააყენეთ `__MISSING__:<new english>`-ზე — შესრულების გარემო შემდეგ სწორ ინგლისურ ტექსტს
   მოემსახურება (`src/i18n/request.ts::deepMergeFallback`, #7258), ხოლო გასაღები სათარგმნელ რიგში ჩადგება.

თუ სტრიქონის **მნიშვნელობა** შეიცვალა, უმჯობესია **გასაღებს სახელი შეუცვალოთ**: ახალი გასაღები
მოძველებულ თარგმანს ვერ მემკვიდრეობს. სწორედ ეს მიდგომა გამოიყენა #8463-მა.

```bash
npm run i18n:check-value-drift          # მკაცრი (რასაც CI უშვებს)
```

მნიშვნელობების გადახრისა და ახალი გასაღებების შემოწმებები იზიარებს ერთ უცვლელ შედარებას
