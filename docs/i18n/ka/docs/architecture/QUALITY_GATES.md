იგი აღწერს თითოეულ ბარიერს, რას ამოწმებს ის, რომელ CI დავალებაში სრულდება, იყენებს თუ არა
ეტალონის ეტაპობრივი გამკაცრების ან ჩაბარება/ჩავარდნის პოლიტიკას და ბლოკავს თუ არა აგებას, თუ მხოლოდ სარეკომენდაციო ხასიათი აქვს.

მოკლე შეჯამებისა და დაშვებული გამონაკლისების სიის პოლიტიკისთვის იხილეთ სექცია „Quality Gates & Ratchets“

## კარიბჭის ინვენტარი და შესრულების პროფილები

### კანდიდატის მიღება

CI და Quality Gates სამუშაო ნაკადები გამოსცემს სტაბილურ ვერდიქტს: `Gate / CI` და `Gate / Quality`. მათი ვერსიით დაშვების პოლიტიკა ჩამოთვლის ყველა ზემოთ ნაკადის სამუშაოს, როგორც საჭირო ან საკონსულტაციო. საჭირო სამუშაო უნდა იყოს წარმატებული: გამოტოვებული, გაუქმებული, გამოტოვებული, მომლოდინე და უცნობი შედეგები ვერ დაადგენს PASS. მხოლოდ დოკუმენტებისთვის ან მხოლოდ კატალოგისთვის განკუთვნილი მოქმედი კლასიფიკაციით შეიძლება კოდის ზოლი გამოუსადეგარი გახდეს; ჩვეულებრივი პროექტი PR არ არის მიღებული კანდიდატი. `hotfix` ეტიკეტი არ უარს ამბობს მტკიცებულებაზე.

ორივე სამუშაო ნაკადი მოიცავს PRs main/release ფილიალებში, უბიძგებს `main`, ხელით გაგზავნას და შერწყმის ჯგუფურ მოვლენებს. დააწკაპუნეთ, გაგზავნეთ და შერწყმა-ჯგუფური გაუშვით სრული შერჩევა. სანდო Mergify რიგის მონახაზი ასევე აწარმოებს მოქმედ `full-code`/`full-code-e2e` სამუშაოებს; ჩვეულებრივი PRs გამოტოვეთ ისინი. ხელით შერწყმამდე, განახორციელეთ სრული გაგზავნა ზუსტ კანდიდატზე. `release/**` ის ბიძგი არ იწყებს ამ სამუშაო პროცესებს; Release-Green აკვირდება გაერთიანებულ ბაზას ცალკე (`docs/ops/RUNNER_BOX.md` → Hosted lane). Forks და შერწყმის ჯგუფები იყენებენ მასპინძელ მორბენლებს სამუშაოებისთვის, რომლებიც სხვაგვარად ირჩევენ თვითმასპინძელ მორბენლებს; საკმარისი ჰოსტინგის მოცულობა უნდა დადასტურდეს გაშვებამდე.

ჩვეულებრივი PR მართავს სწრაფ შერჩევას. დაშვების პოლიტიკის `full-code` და `full-code-e2e` ზოლები (E2E, ინტეგრაცია, პაკეტის არტეფაქტი, Electron smoke, Bun SQLite, ეკოსისტემა და პროტოკოლის კლიენტები) მუშაობს მხოლოდ Mergify რიგის პროექტზე ან სრულ გაშვებაზე: `gh workflow run ci.yml --ref <branch>`.

თითოეული JSON ქვითარი განსაზღვრავს გამოტანილ SHA, სამუშაო პროცესის გაშვებას და მცდელობას. CLI უარყოფს checkout/event SHA შეუსაბამობას. სამუშაო პროცესის ტესტები აკავშირებს პოლიტიკის წევრობას ვერდიქტის სამუშაოს `needs` სიაში, ასე რომ ახალი ან ამოღებული ზოლი არ შეიძლება ჩუმად გაქრეს. ქვითრები მოიცავს საკუთარ სამუშაო პროცესს და არა პუბლიკაციას, განლაგებას ან არსებული საკონსულტაციო სკანერის ინტერიერს. ფილიალის წესებით მოთხოვნილი შესაბამისი შემოწმებების გაკეთება ცალკე ადმინისტრაციული ცვლილებაა; მათი სამუშაოს განსაზღვრა თავისთავად არ იცავს ფილიალს.

`API Route Typecheck` არის სამუშაო პროცესის დამოუკიდებელი შემოწმება, როგორც მთლიანი ვერდიქტების, ასევე ადგილობრივი სრული დამკვირვებლის სტატიკური პროფილის მიღმა. შეამოწმეთ მისი შედეგი ცალკე კონკრეტული კანდიდატისთვის. `.github/workflows/api-route-typecheck.yml` მუშაობს PRs ზე `main` ში ან `release/**`, უბიძგებს რომელიმე ფილიალის ოჯახს, სახელმძღვანელოს გაგზავნას და `merge_group` ტიპის `checks_requested` მოვლენებს. მას არ აქვს ბილიკის ფილტრი. ჯგუფების შერწყმა შეამოწმეთ `merge_group.head_sha`; სხვა ღონისძიებები შეამოწმეთ `github.sha`. ყველა ღონისძიება იყენებს იგივე API დიაგნოსტიკური კარიბჭის და კარიბჭის ერთეულის ტესტებს. PR საბაზისო რეტარგეტები ითხოვენ ახალ შემოწმებას; body/title რედაქტირება იყენებს მხოლოდ დაკვირვების სახელს `Admission not requested / API Route Typecheck` და ვერ შეცვლის დაშვების შემოწმებას.

### შენახული მტკიცებულება მიღების რედუქტორში

`scripts/quality/validate-release-acceptance.mjs` ამცირებს მიწოდებულ გეგმას და მის მანიფესტებს; იგი არ ადგენს, რომ გეგმა მოიცავს სრულ გაშვების მილსადენს. მისი ანგარიშები ცალსახად განსაზღვრავს `releaseAcceptance: false`, მაშინაც კი, როდესაც ეს გეგმა არის `VERIFIED`. `release-acceptance.yml` სამუშაო ნაკადი კვლავ იყენებს ჩრდილოვან მოწყობილობებს და არა რეალურ კონსტრუქციას, პაკეტს, ჩატვირთვის ან სარეკლამო ქვითრებს.

CLI მოითხოვს `--evidence-root` შენახული მტკიცებულებების გადამოწმებას. ფაილები წყდება როგორც `<evidence-root>/<artifact_id>/<member>` და ჰეშირდება როგორც SHA-256. PASS ჩანაწერი მტკიცებულების გარეშე, დაკარგული ან შეცვლილი ფაილი, სახიფათო გზა ან სიმბლაკი ხელს უშლის გადამოწმებას. დაკარგული ფაილები არ არის ცარიელი წარმატებული ჟურნალის ექვივალენტი. არსებული SHA/run/attempt ჩეკები რჩება დამოუკიდებელი: ბაიტების შესატყვისი ვერ გადაარჩენს შემორჩენილ ქვითარს. ფაილის მთლიანობა არ არის შესრულების ავთენტურობის ან არტეფაქტის პოპულარიზაციის მტკიცებულება.

### DAST მოიხმარს დამოწმებულ CI ს

საჭირო `dast-smoke` CI სამუშაო მოუწოდებს `.github/workflows/dast-smoke.yml` `build` შემდეგ. ის მიჰყვება იგივე code/draft შერჩევას, როგორც კონსტრუქციას, მათ შორის მხარდაჭერილი ჩანგალი PRs, გამოშვება-სამიზნე PRs და შერწყმის ჯგუფები. გამოტოვებული, წარუმატებელი, გაუქმებული ან მოულოდნელად გამოტოვებული DAST სამუშაო ბლოკავს `Gate / CI`. მრავალჯერად გამოყენებადი სამუშაო პროცესს არ აქვს დამოუკიდებელი PR/dispatch ტრიგერი; მექანიკური ვალიდაცია იყენებს CI ის დისპეტჩერს, ასე რომ კონსტრუქცია და მომხმარებელი რჩება ერთ გაშვებაში.

`scripts/ci/next-build-provenance.mjs` დალუქავს სრულ Next artifact-ს თავისი tar digest-ით, repository/event/run, მწარმოებლის მცდელობით, head/base/checkout/tree, სამუშაო პროცესის იდენტობებით, lockfile-ით, ზუსტი კვანძის version/ABI ით, პლატფორმით და ბანდლერით. DAST ირჩევს უცვლელ ID არტეფაქტს `needs.build.outputs` დან, მოითხოვს ჩამოტვირთვის დაიჯესტის გადამოწმებას და დამოუკიდებლად ანაწილებს ZIP მწარმოებლის დაიჯესტის წინააღმდეგ, სანამ ამოიღებს მის ორ დასაშვებ წევრს `scripts/ci/unpack-ci-build.py` მეშვეობით. მანიფესტი და tar არქივი ასევე უნდა ემთხვეოდეს დამოუკიდებელი მწარმოებლის შედეგებს შემდეგი ხის ამოღებამდე. ის არასოდეს ეძებს ფილიალის უახლეს წარმატებულ მშენებლობას. ნაწილობრივი გამეორება შეიძლება ხელახლა გამოიყენოს იგივე პროდიუსერის მცდელობა, როდესაც მისი ID და ყველა შენატანი მაინც ემთხვევა; ქვითარი აღრიცხავს ორივე მცდელობას.

მომხმარებელი რჩება მასპინძელ Linux runner-ზე მხოლოდ წაკითხვის საცავის ნებართვით და საცავის საიდუმლოების გარეშე. ის დააინსტალირებს მწარმოებლის ზუსტ Node ვერსიას, შემდეგ აწყობს CLI ს `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1` ით. `scripts/build/standaloneInput.mjs` უარყოფს გამოტოვებულ დამოუკიდებელ სერვერს რაიმე სარეზერვო აწყობამდე; ნორმალური ადგილობრივი CLI კონსტრუქციები ინარჩუნებენ არსებულ სარეზერვო სისტემას. სერვერის მზადყოფნა, Schemathesis და promptfoo ყველა უნდა იყოს წარმატებული უცვლელი 25 წუთიანი სამუშაო ლიმიტის ფარგლებში. წარმოშობის ქვითარი ადასტურებს შეყვანის იდენტურობას და ბაიტებს და არა წარმატებულ DAST სკანირებას. არტეფაქტის ვადის გასვლა, მორბენალი შეფერხება ან წარუმატებელი სკანერი რჩება არასრული ან წარუმატებელი მტკიცებულება; ის არ შეიძლება გახდეს PASS საკონსულტაციო შეფუთვის მეშვეობით.

### UI შესრულების უნარი

CI აწარმოებს UI სრულ ინვენტარს ოთხი `test-vitest` მატრიცის ფრაგმენტის სახით, თითოეულში მაქსიმუმ ორი მუშაკით თითო ნატეხზე და არსებული 15 წუთიანი სამუშაო ვადა. პირველი ნატეხი ასევე მუშაობს MCP/autoCombo Vitest კომპლექტს. სამუშაოს საჭირო შედეგი მოიცავს მატრიცის ყველა ფეხს; ერთი ფრაგმენტის წარუმატებლობა ან გაუქმება ვერ დაადგენს კანდიდატის მიღებას.

ღამის დამკვირვებელი ინახავს ცალკე ზუსტი კანდიდატურის ქვითარს თითოეული UI ფრაგმენტისთვის, მათ შორის MCP შესრულების პირველ ქვითარში. ოთხივე ქვითარი, ჟურნალი და შესატყვისი შესრულების იდენტობაა საჭირო. ადგილობრივი `npm run test:vitest:ui` კვლავ ირჩევს სრულ კომპლექტს; ერთი `--shard` გაშვება მხოლოდ ნაწილობრივი მტკიცებულებაა.

### ერთეულის დაფარვის კოლექცია

თორმეტი ერთეული ფრაგმენტი აგროვებს V8 დაფარვას მათი არსებული ტესტის შესრულების დროს. წარმატებული ფრაგმენტი აწარმოებს `scripts/ci/compact-v8-coverage.mjs`, რათა შეკუმშოს ორიგინალი ფაილები შუალედური სტამბულის ანგარიშის გენერირების გარეშე. დაფარვის საბოლოო სამუშაო ამოწმებს თორმეტივე მანიფესტს კანდიდატის SHA, გაშვების დროის, წყაროს root და მონაცემთა ჰეშების წინააღმდეგ, შემდეგ აწარმოებს c8-ის რეპორტიორებს და არსებულ დაფარვის ზღურბლებს. შეყვანები ინარჩუნებს c8-ის ფაილის სახელების გლობალურ წესრიგს; თითო ნაჭრის წინასწარ შერწყმა სახიფათოა შერეული function/block დაფარვისთვის. დაკარგული, არასწორი ან შეუთავსებელი ფრაგმენტები ვერ მიიღება. წარუმატებელი ტესტის ნაჭრები ცალკე ინარჩუნებს ნედლეულ დიაგნოსტიკურ დაფარვას; ის ვერ შედის საბოლოო შერწყმაში.

### ერთეულის შესრულების პროგრესის ქვითრები

გაზიარებული `test:unit:ci:shard` ბრძანება აღრიცხავს `primary`, `dashboard` და `serial` ფაზებს `scripts/ci/unit-progress-reporter.mjs` მეშვეობით. ნორმალური ტესტის ანგარიში ხელმისაწვდომი რჩება. ცალკეული მხოლოდ მეტამონაცემების ქვითარი აღრიცხავს თითოეული ფაილის დაწყებას და დასრულებას, ხოლო 30 წამიანი გულისცემა ჩამოთვლის ფაილებს ჯერ კიდევ აქტიურ და მათ გასულ დროს. ის იწერს მხოლოდ დაშვებულ სიაში შესრულების მეტამონაცემებს; ტესტის აღწერილობები, გამომავალი, შეცდომების ორგანოები და სრული გარემო არ არის სერიული.

CI ინახავს JSONL ფაილებს, როგორც `unit-progress-ci-<run>-<attempt>-<shard>`. სამუშაოს ვადამ შეიძლება თავიდან აიცილოს მოგვიანებით ატვირთვა; უკვე გამოსხივებული გულისცემა რჩება დიაგნოსტიკურ მტკიცებულებად. გამოტოვებული გულისცემა ასევე შეიძლება ასახავდეს მორბენალის დაბლოკილ ან შეწყვეტილ პროცესს. ამ ქვითრებში დაცულია არსებული ტესტის შერჩევა, თანხვედრა, ვადები და გასვლის სტატუსი; ისინი არ არის კანდიდატის მისაღები ვერდიქტები.

### რიგის შერწყმა

`queue` ლეიბლი აგზავნის PR Mergify რიგში (`.mergify.yml`). Mergify ხსნის PR მონახაზს `mergify/merge-queue/` ფილიალში, CI აწარმოებს სრულ შერჩევას იქ და ორიგინალური PR ერწყმის `Gate / CI`, `Gate / Quality` და `Merge integrity (changelog + generated skills)` გავლისას.

Mergify წერს თავის რიგის შეჯამებას მონახაზის აღწერაში. Body/title-only `pull_request` `edited` მოვლენები იყენებს გაშვების სპეციფიკურ კონკურენტულ ჯგუფს და არ აწარმოებს კლასიფიკაციას, ტესტის მატრიცებს, შერწყმის მთლიანობას ან დაშვების ვერდიქტს. მხოლოდ დაკვირვების საკონტროლო სახელები ვერ შეცვლის `Gate / CI` ან `Gate / Quality`. რედაქტირება, რომელიც ცვლის სამიზნე ბაზას, ითხოვს კანდიდატის ახალ ვალიდაციას.

Dequeue-ის შემდეგ, Push ყოველთვის არ ითხოვს PR ს. დაწერეთ კომენტარი `@mergifyio queue` ზე.

### სტატიკური სკანირების ინვენტარი

ვერსიული npm-alias ინვენტარი და სტატიკური სკანირების წევრობა ცოცხალია `config/quality/gate-manifest.json` ში. გაუშვით `npm run check:gate-manifest` სკრიპტის სახელებისა და ზუსტი ბრძანებების დასადასტურებლად `package.json` წინააღმდეგ; დამატებები, ამოღება და ბრძანების დრიფტი ვერ ახერხებს CI ში ლოკალური ჰუკის და შეცვლა-კლასიფიკაციის სამუშაოებს. მეტსახელი არ არის სამუშაო პროცესის სამუშაო, მატრიცის მაგალითი ან საცდელი შემთხვევა: ეს რიცხვები არ უნდა იყოს წარმოდგენილი, როგორც ურთიერთშემცვლელი.

გამოიყენეთ `npm run quality:scan -- --list` ან `npm run quality:scan:fast -- --list` არჩეული მეტსახელების შესამოწმებლად მათი შესრულების გარეშე. მორბენალი გამოიძახებს npm შესვლის წერტილს, ამიტომ მისი გაშვების დრო (მათ შორის Bun სადაც არის კონფიგურირებული) შენარჩუნებულია. მანიფესტი იწერს ფსევდონიმებს ამ პროფილების გარეთ, როგორც ცალკე გამოძახებული, და ტექნიკური ბრძანებები აკრძალულია მხოლოდ წასაკითხად სკანირებულ პროფილებში.

ეს პროფილები მოიცავს მხოლოდ სტატიკურ სკანირებას. ისინი არ ამოწმებენ პროდუქტის ტესტებს, დაფარვას, შეფუთვას, გარე შემოწმებას ან კანდიდატის სრულ გამოშვებას. სამუშაო პროცესის მიღება იყენებს დაკავშირებულ `config/quality/admission-policy.json` და `scripts/quality/admission-verdict.mjs`. გამოშვება-დამკვირვებლის პროფილები რჩება ცალკე; დამოუკიდებლად შეამოწმოს მათი შესაბამისი ჩეკები და ქვითრები. დამკვირვებლის სრული სტატიკური ბრძანებები გამოცხადებულია `config/quality/release-green-static-profile.json` ში, მათ შორის `audit:deps`, მუტაციის ტესტის შერჩევა და თარგმანის შემოწმება. ჩამტვირთავი ამოწმებს npm ბრძანებებს package.json და მოდელირებული CI/Quality დეკლარაციების წინააღმდეგ; ის უარყოფს დრიფტს, ნაცვლად იმისა, რომ არგუმენტად განახორციელოს shell ტოკენები. საჭირო სკანერის SKIP/INCOMPLETE გამომავალი ვერ ადგენს PASS. პროფილი აღრიცხავს მის გარე გამონაკლისებს და არ ცვლის ჰოსტირებული გაშუქებას, ტესტის მატრიცებს, პაკეტს ან განლაგების მტკიცებულებებს. ქვემოთ მოცემული პროზაული ინვენტარი არის მითითება და არა მტკიცებულება იმისა, რომ კარიბჭე რეალურად გაიქცა.

სკრიპტები ცხოვრობს `scripts/check/` (პოლიტიკის კარიბჭე) და `scripts/quality/` (რაკეტის ძრავის ქვეშ). CI სიმართლის წყაროა `.github/workflows/ci.yml`.

### გამოქვეყნებული საბაზისო დოკუმენტაციის ჯანმრთელობა

`.github/workflows/i18n-base-health.yml` აკვირდება დოკუმენტაციის სიჯანსაღეს `main` და `release/v*` ზე შერჩეული ბიძგების შემდეგ და ხელით გაგზავნისას. მისი ფილტრები მოიცავს დოკუმენტაციას, root Markdown, `llm.txt`, თარგმანი state/configuration და შესაბამისი i18n ინსტრუმენტები. ერთი `Published base documentation health` სამუშაო იყენებს მასპინძელ Ubuntu-ს და ხუთწუთიან ვადას. ის ახორციელებს მხოლოდ წაკითხვის ვალიდაციას და წერს დიაგნოსტიკურ ქვითარს დამოკიდებულების ინსტალაციის, თარგმანის ან მდგომარეობის მიღების გარეშე.

`scripts/i18n/check-base-health.mjs` მოითხოვს ნულოვანი წყაროს ჰეშს, დაკარგული სამიზნე, სამიზნე-ჰეში, შემორჩენილი თარგმანი და სექცია-ქეში შეუსაბამობები. ის ასევე ადასტურებს document/locale მიმდინარე ძირითად ფარგლებს და მის დაფიქსირებულ წარმომავლობას. არასწორი კონტექსტი, არასრული გაშუქება ან შეწყვეტილი შემოწმება წარმოქმნის `INCOMPLETE`; დადასტურებული დრიფტი აწარმოებს `FAIL`. ორივე უბრუნდება წარუმატებელი გასვლის სტატუსს. ქვითარი ვალდებულია გადაიხადოს SHA, სამუშაო პროცესი, გაშვება და მცდელობა და ინახება როგორც `i18n-base-health-<sha>-<run>-<attempt>`.

ეს არის გამოქვეყნებული ბაზის დამოუკიდებელი დაკვირვება. ის არ ამატებს PR ან გაერთიანების ჯგუფის მოვლენას, საჭირო PR შემოწმებას, npm მეტსახელს ან სტატიკური სკანირების პროფილის წევრს. ძირეული გამშვები ასევე ბლოკავს ხუთივე კლასს აბსოლუტურ რეჟიმში. ჩვეულებრივი PR მომზადება დაშვებისგან ცალკე რჩება. წარმატებული ატვირთვა ვერ გადააქცევს წარუმატებელ ჯანმრთელობის შედეგს PASS ად.

ჩვეულებრივი PR იყენებს `--preflight` `--baseline-evidence` მიერ გენერირებული საბაზისო ანგარიშით. მან შეიძლება დატოვოს ინგლისური წყარო მოლოდინის რეჟიმში მხოლოდ მაშინ, როდესაც სრული თარგმანის ჩანაწერი და რეალური სამიზნე ბაიტები უცვლელია ამ ზუსტი ბაზისგან. ახალი სამიზნე ან სექცია-ქეში შეუსაბამობები კვლავ იბლოკება და არასრული მტკიცებულებები არ იძლევა მომზადების უფლებას. ანგარიში ცალ-ცალკე ასახავს `preparationPending` და `mergeReady` : წარმატებული მომზადება არ ამზადებს მომლოდინე თარგმანებს გაერთიანებისთვის. განაახლეთ დაზარალებული სარკეები შედგენილ კანდიდატში მიღებამდე. სანდო Mergify რიგის კანდიდატი, `merge_group`, ფილიალი ბიძგები და ხელით CI გაშვებები იყენებენ აბსოლუტურ შემოწმებას, `--warn` ან მემკვიდრეობითი წარუმატებლობის პატიების გარეშე. გამოტოვებული სამიზნე ჰეშები და წაშლილი ჩაწერილი ძირითადი ფაილებით შემცირებული ფარგლები ვერ წარმოადგენენ წარმატებულ აბსოლუტურ ვერდიქტს.

### გამოუშვით PR სწრაფი გზა (`quality.yml`)

PRs იყენებს ბილიკით გაფილტრულ სწრაფ შემოწმებებს. სამუდამოდ გამორთული დუბლიკატი build წაიშალა; რეალური build/package/boot ჩეკები რჩება CI ში. ერთეულის კომპლექტი და ვიტესტი მუშაობს მხოლოდ CI ში (`Unit Tests (N/12)` და `Vitest`).

#### დავიწყებული და-ძმის ტესტების ანგარიში

`npm run check:forgotten-sibling-tests` მუშაობს როგორც `Fast Quality Gates` ის საკონსულტაციო ნაბიჯი და ხელახლა იყენებს იმპორტის გადამწყვეტს ტესტის ზემოქმედების რუკის უკან. ყოველი შეცვლილი წარმოების მოდულისთვის, ის აცნობებს განმსაზღვრელ `changed module/symbol -> static consumer -> candidate sibling test` ჯაჭვებს, როდესაც კანდიდატის ტესტი არ არის pull-მოთხოვნის განსხვავებაში. Markdown-ის შეჯამება და JSON შედეგი ინახება, როგორც `forgotten-sibling-tests` სამუშაო ნაკადის არტეფაქტი კალიბრაციისთვის ნებისმიერი დაბლოკვის გაშვებამდე.

ლულის რეექსპორტი და დინამიური იმპორტი მხოლოდ გარჩევადობის დიაგნოსტიკაა; ისინი არასოდეს ქმნიან ბლოკირების აღმოჩენას. განხილული გამონაკლისები პირდაპირ ეთერში `config/quality/forgotten-sibling-allowlist.json` ში. თითოეულ ჩანაწერში უნდა ასახელებდეს მომხმარებლისა და კანდიდატის ტესტს, მიუთითებდეს კონკრეტულ დასაბუთებას და დაუკავშირდეს GitHub საკითხს ან მოთხოვნას. არასწორი ჩანაწერები ვერ დაიხურა. გამონაკლისები ვერ ახშობს წაშლილი კანდიდატის ტესტს ან განსხვავებას, რომელიც ამატებს `.skip`/`.todo`; მტკიცების შესუსტება და სხვა ნიღბები რჩება დამოუკიდებლად დამბლოკავი `check:test-masking` კარიბჭის საკუთრებაში.

#### ტიპის შემოწმების ორი პროგრამა განსხვავებულად პასუხობს

`typecheck:core` (`noImplicitAny: false`) / `typecheck:noimplicit:core` (`noImplicitAny: true`) და `check:build-typecheck` აგროვებენ სხვადასხვა პროგრამებს სხვადასხვა ვარიანტში და ერთი და იგივე ფაილი შეიძლება იყოს სუფთა ერთში და სავსე იყოს შეცდომებით მეორეში.

`tsconfig.build.json` აყენებს `"strict": false`, ამიტომ `noImplicitAny` გამორთულია. ძირითადი კონფიგურაცია აგროვებს კურირებულ 27-ფაილის დაშვებულ სიას უფრო მკაცრი ვარიანტებით და მიჰყვება თითოეული ჩანაწერის იმპორტის გრაფიკს, ასე რომ ფაილები, რომლებიც არასოდეს გამოჩნდება build პროგრამაში, კვლავ იქ მოწმდება.

შედეგი მნიშვნელოვანია, როდესაც ვიმსჯელებთ, არის თუ არა ფაილის აკრეფილი:**ნულოვანი დიაგნოსტიკა `check:build-typecheck` ში არ ნიშნავს ნულს** . `@ts-nocheck` 26 ფაილიდან ამოღებამ აჩვენა, რომ 23 მათგანი სუფთაა build პროგრამაში; მათგან თექვსმეტმა გამოავლინა დაახლოებით 120 იმპლიციტური შეცდომა მკაცრში. გადაამოწმეთ ორივე სანამ ფაილის გაწმენდას გამოიძახებთ.

#### `check-ui-value-drift` — შემორჩენილი თარგმანის კარიბჭე

იჭერს ერთ i18n რეგრესიას, რომელსაც სხვა კარიბჭეები სტრუქტურულად ვერ ხედავენ: ინგლისური მნიშვნელობა ხელახლა იწერება და _previous_ ინგლისურიდან მიღებული თარგმანები უკან რჩება, ამიტომ არაინგლისელი მომხმარებლები აგრძელებენ თავდაჯერებულად ფორმულირებულ, ახლა უკვე არასწორ ასლს.

ეს გაიგზავნება რეალურად. `oauthModal.googleOAuthWarning` ხელახლა დაიწერა, როდესაც Antigravity შესვლის დამხმარე დაეშვა (#5203);**43 ლოკალიდან 39** ინახავდა ტექსტს, რომელიც ეუბნებოდა ოპერატორებს "დააკოპირეთ სრული URL და ჩასვით ქვემოთ" — ნაკადი, რომელიც ვერ დაასრულებს ამ პროვაიდერს. ის შეუმჩნეველი დარჩა #8463 მდე, რადგან:

- `sync-ui-keys` ავსებს მხოლოდ გასაღებებს **არყოფნის** , არასოდეს ისეთები, რომლებიც არიან **შემორჩენილი** ;
- `check-ui-keys-coverage` ითვლის საკვანძო _ყოფნას, ასე რომ, შემორჩენილი თარგმანი ფასდება, როგორც დაფარული;
- `check-translation-drift` თვალს ადევნებს `docs/i18n/<locale>/**.md` დოკუმენტაციას, ასახავს — ის არასოდეს კითხულობს `src/i18n/messages/*.json`. სამუშაო `docs-sync-strict` ბლოკირება 2026-09 წლების ხელახალი სინქრონიზაციის შემდეგ: შეცვალეთ ძირითადი დოკუმენტი → `npm run i18n:run -- --files=<doc>` (სექციის დონის, იაფი).

**Diff-ის ცოდნა, არა საბაზისო მხარდაჭერით.** იგი ადარებს `en.json` შერწყმის ბაზაზე სამუშაო ხესთან; ყველა გასაღებისთვის, რომლის ინგლისური მნიშვნელობა შეიცვალა, ნებისმიერი ლოკალი, რომელსაც ჯერ კიდევ ხელუხლებელი თარგმანი აქვს, მოძველებულია. ეს შეგნებულად **ყინავს ადრე არსებულ ვალს** — განსხვავება ვერ ავლენს, რომელი ძველი ინგლისურიდან მოვიდა დიდი ხნის თარგმანი, ამიტომ კარიბჭე განსჯის მხოლოდ იმას, რასაც ეხება მიმდინარე ცვლილება. ალტერნატივა (თითო კლავიშის ჰეშის საბაზისო ხაზი) ეღირება ~ 600 KB გენერირებული ფაილი, 3 × ყველაზე დიდი არსებული საბაზისო ხაზი, რომელიც იშლება ყოველ i18n PR ზე.

მისი დაკმაყოფილების ორი გზა:

1. განაახლეთ დაზარალებული თარგმანები, ან
2. დააყენეთ ისინი `__MISSING__:<new english>` — მუშაობის დროს, შემდეგ ემსახურება შესწორებულ ინგლისურს (`src/i18n/request.ts::deepMergeFallback`, #7258) და თარგმანის საკვანძო რიგებს.

თუ სიმებიანი **მნიშვნელობა** შეიცვალა, ურჩევნია **გასაღების სახელის გადარქმევა** : ახალი გასაღები ვერ დაიმკვიდრებს ძველ თარგმანს. ეს არის ნიმუში, რომელიც გამოიყენება #8463.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ღირებულების დრიფტი და ახალი გასაღების კარიბჭეები იზიარებენ ერთ უცვლელ შედარებას `scripts/i18n/resolve-ui-diff-base.mjs` სგან. სამუშაო ნაკადი ორივე შემოწმებას გადასცემს ერთსა და იმავე ბაზას, საბაზისო წვერას და კანდიდატ SHAs. PR/base-retarget, push და შერწყმის ჯგუფის გაშვებები იყენებენ თავიანთ მოვლენის კონტექსტს. კანდიდატი ფილიალის გაგზავნისთვის საჭიროა მისი ზუსტი ღია PR ან აშკარა `i18n_base_sha` შეყვანა. `main` ან `release/vX.Y.Z` ზე გაგზავნა ან დაგეგმილი დაკვირვება ამ შეყვანის გარეშე ადარებს ბოლო ჩადენას მის პირველ მშობელს; ეს არ არის ყველა მემკვიდრეობით მიღებული თარგმანის დავალიანების აუდიტი. ლოკალური გამოძახება მოითხოვს მკაფიო შედარების ბაზას, მაგალითად `BASE_REF` ბრძანებას ზემოთ.

გამოტოვებული ან ორაზროვანი შედარების კონტექსტი, წაუკითხავი ან არასწორი საჭირო კატალოგი და შეცვლილი კანდიდატი აწარმოებს `INCOMPLETE` გასასვლელი კოდით **2** , მათ შორის გაფრთხილების რეჟიმში. კატალოგის წაკითხვა იყენებს `scripts/i18n/read-ui-catalog.mjs`; წაკითხვის წარუმატებლობა არ შეიცვლება ცარიელი ობიექტებით. არც მიუწვდომელი ბაზა და არც არასრული შეყვანა არ ადგენს PASS.

### CodeQL ratchet: კანდიდატის მისაღები და საცავის ინვენტარი

CI ფლობს კანდიდატს CodeQL დაშვებას აშკარა დამოკიდებულების ჯაჭვის მეშვეობით: `codeql-scan` უწოდებს ოთხენოვან მატრიცას `codeql.yml` ში, შემდეგ `codeql-admission` აწარმოებს `node scripts/check/check-codeql-ratchet.mjs --candidate`. `Gate / CI` მოითხოვს ორივე შედეგს. ხარისხი ინარჩუნებს საკუთარ ციფრულ შემოწმებებს, მაგრამ არ კითხულობს სკანერს, სანამ პროდიუსერი დაასრულებს; მარტო `Gate / Quality` არ არის სრული კანდიდატის მიღება. CodeQL რჩება მოთხოვნადი მხოლოდ დოკუმენტების კანდიდატებისთვის.

პოლიტიკა `config/quality/codeql-admission-policy.json` ში ირჩევს მოქმედებებს, C/C++, JavaScript/TypeScript და Python, მოთხოვნების ნაკრები ნაგულისხმევი, დისტანციური საფრთხის მოდელს და build-ის რეჟიმს არცერთს. პროდიუსერის წინასწარი ფრენა უარყოფს აქტივაციის მომლოდინე ჩანაწერს და განშტოება აშკარა სამიზნე სიის გარეთ. მიმდინარე სამიზნეები არის ძირითადი და release/v3.8.54. კონტრაქტის ტესტები ადარებს ამ სასრულ ჩამონათვალს და შენარჩუნების ბიძგს პაკეტის ვერსიასთან; შემდეგი გამოშვება საჭიროებს გადახედვას ბორტზე. CI ის არსებული უფრო ფართო გამოშვების PR ტრიგერი შენარჩუნებულია, მაგრამ არაბორტზე მოხვედრილი სამიზნე აცნობებს HOLD მოპოვებამდე, ვიდრე გაუზომავი PASS მიღებას.

თითოეული მატრიცის სამუშაო აღრიცხავს მის რეალურ SARIF ატვირთვას ID, ენას, კატეგორიას, გაშვებას და მცდელობას, აბონენტის სამუშაო ნაკადის იდენტურობას, მოვლენას ref/head/base/merge SHA და პოლიტიკის ჰეშს. დამოკიდებული სამუშაო ჩამოტვირთავს მხოლოდ ამ გაშვების ქვითრებს და ამოწმებს არტეფაქტის დაჯესტებს. ის მოითხოვს ოთხივე კატეგორიას, წარმატებულ პროდიუსერს და თითოეული ზუსტი ატვირთვის დასრულებულ დამუშავებას. ის იყენებს API ის sarif_id ფილტრს და არა ფილიალზე ნაპოვნი უახლეს ანალიზს. ნაწილობრივი გამეორება შეიძლება ხელახლა გამოიყენოს წარმატებული კატეგორიები ერთი და იგივე კანდიდატის ადრინდელი მცდელობიდან, პროდიუსერის მცდელობის შენარჩუნებით; წარუმატებელი მიმდინარე პროდიუსერი ვერ გამოიყენებს წინა მწვანე მტკიცებულებებს.

CodeQL მოქმედება ელოდება დამუშავებას, მაგრამ მის დამაგრებულ განხორციელებას შეუძლია გააფრთხილოს და გაგრძელდეს სტატუსის წაკითხვის წარუმატებლობის ან ამოწურული ლოდინის შემდეგ. ამიტომ დაშვება კვლავ ამოწმებს დამუშავებას. გამოტოვებული კატეგორიები, მომლოდინე დამუშავება, წარუმატებელი ან გაუქმებული სამუშაოები, ძველი იდენტურობა, არასრული პაგინაცია ან მიუწვდომელი APIs წარმოქმნის HOLD და გასასვლელს 2. სკანერის დამოუკიდებელი სამუშაო პროცესისთვის ფიქსირებული ლოდინი არ რჩება. დაუსკანირებელი PR ვერ გაივლის, რადგან გაფრთხილების მოთხოვნამ დააბრუნა 0. გაზომილი რაოდენობა `metrics.codeqlAlerts.value` ზევით გამოდის 1; საბაზისო არ არის აწეული სხვა ფილიალის სიგნალიზაციის ათვისებისთვის. [ატვირთვის სტატუსი და ანალიზის ძებნა](https://docs.github.com/en/rest/code-scanning/code-scanning).

ქვითარი აღწერს ატვირთვას და ანალიზს IDs, კატეგორიებს, ხელსაწყოების ვერსიებს, ref/SHA, საბაზისო და გაფრთხილების ნომრებს. SARIF identity/result რაოდენობა, მინიმალური წესების რაოდენობა და ზუსტი გაფრთხილების შემთხვევები რჩება სავალდებულო. PR/analysis ვინაობა ხელახლა შემოწმდება მიღებამდე. ეს შემოწმებები ადგენს კონფიგურირებული კატეგორიის დაფარვას და არა ყველა ამოღებული წყაროს ფაილის ინვენტარს. C/C++ უშენობის ამოღება არ შეიცავს კოდს, რომელიც გენერირებულია პროექტის აშენების დროს. წყაროს გამონაკლისები ჯერ კიდევ საჭიროებს განხილვას, ხოლო კონტრიბუტორის კუთვნილება საჭიროებს შესადარებელ ზუსტ საფუძველს.

`codeql-maintenance.yml` აწვდის აქტიური გამოშვების სკანირებას და ყოველკვირეულ განრიგს PR/main მწარმოებლების დუბლირების გარეშე. `nightly-codeql-inventory.yml` ინახავს საცავში საბაზისო ხაზს განცალკევებულად, `--strict-measurement` ით და წარუმატებლობით, როდესაც გაზომვა მიუწვდომელია. ადგილობრივი მემკვიდრეობის კოლექციონერის მოხდენილი გამოტოვება არ არის კანდიდატის მიღება. გამკაცრება რჩება გამოკვეთილ `--update` ად დამოწმებული დაბალი გლობალური დათვლის შემდეგ.
