იგი აღწერს თითოეულ ბარიერს, რას ამოწმებს ის, რომელ CI დავალებაში სრულდება, იყენებს თუ არა
ეტალონის ეტაპობრივი გამკაცრების ან ჩაბარება/ჩავარდნის პოლიტიკას და ბლოკავს თუ არა აგებას, თუ მხოლოდ სარეკომენდაციო ხასიათი აქვს.

## გეითების ინვენტარი და შესრულების პროფილები

### კანდიდატის მიღება

CI და Quality Gates სამუშაო ნაკადები გამოსცემს სტაბილურ ვერდიქტს: `Gate / CI` და `Gate / Quality`. მათი ვერსიით დაშვების პოლიტიკა ჩამოთვლის ყველა ზემოთ ნაკადის სამუშაოს, როგორც საჭირო ან საკონსულტაციო. საჭირო სამუშაო უნდა იყოს წარმატებული: გამოტოვებული, გაუქმებული, გამოტოვებული, მომლოდინე და უცნობი შედეგები ვერ დაადგენს PASS. მხოლოდ დოკუმენტებისთვის ან მხოლოდ კატალოგისთვის განკუთვნილი მოქმედი კლასიფიკაციით შეიძლება კოდის ზოლი გამოუსადეგარი გახდეს; ჩვეულებრივი პროექტი PR არ არის მიღებული კანდიდატი. `hotfix` იარლიყი არ უარყოფს მტკიცებულებებს.

ორივე სამუშაო ნაკადი მოიცავს PRs main/release ტოტებად, უბიძგებს `main`, ხელით გაგზავნას და გაერთიანების მოვლენებს. დააწკაპუნეთ, გაგზავნეთ და შერწყმა-ჯგუფური გაუშვით სრული შერჩევა. სანდო Mergify რიგის მონახაზი ასევე აწარმოებს მოქმედ `full-code`/`full-code-e2e` სამუშაოებს; ჩვეულებრივი PRs გამოტოვეთ ისინი. ხელით შერწყმამდე, განახორციელეთ სრული გაგზავნა ზუსტ კანდიდატზე. `release/**` ზე ბიძგი არ იწყებს ამ სამუშაო პროცესებს; Release-Green აკვირდება გაერთიანებულ ბაზას ცალკე (`docs/ops/RUNNER_BOX.md` → Hosted lane). Forks და შერწყმის ჯგუფები იყენებენ მასპინძელ მორბენლებს სამუშაოებისთვის, რომლებიც სხვაგვარად ირჩევენ თვითმასპინძელ მორბენლებს; საკმარისი ჰოსტინგის მოცულობა უნდა დადასტურდეს გაშვებამდე.

ჩვეულებრივი PR მართავს სწრაფ შერჩევას. დაშვების პოლიტიკის `full-code` და `full-code-e2e` ზოლები (E2E, ინტეგრაცია, პაკეტის არტეფაქტი, Electron smoke, Bun SQLite, ეკოსისტემის და პროტოკოლის კლიენტები) მუშაობს მხოლოდ Mergify რიგის პროექტზე ან სრულ გაშვებაზე: `gh workflow run ci.yml --ref <branch>`.

თითოეული JSON ქვითარი განსაზღვრავს გამოტანილ SHA, სამუშაო პროცესის გაშვებას და მცდელობას. CLI უარყოფს checkout/event SHA შეუსაბამობას. სამუშაო პროცესის ტესტები აკავშირებს პოლიტიკის წევრობას ვერდიქტის სამუშაოს `needs` სიაში, ასე რომ ახალი ან ამოღებული ზოლი არ შეიძლება ჩუმად გაქრეს. ქვითრები მოიცავს საკუთარ სამუშაო პროცესს და არა პუბლიკაციას, განლაგებას ან არსებული საკონსულტაციო სკანერის ინტერიერს. ფილიალის წესებით მოთხოვნილი შესაბამისი შემოწმებების გაკეთება ცალკე ადმინისტრაციული ცვლილებაა; მათი სამუშაოს განსაზღვრა თავისთავად არ იცავს ფილიალს.

`API Route Typecheck` არის სამუშაო ნაკადის დამოუკიდებელი შემოწმება, როგორც მთლიანი ვერდიქტების, ასევე ადგილობრივი სრული დამკვირვებლის სტატიკური პროფილის მიღმა. შეამოწმეთ მისი შედეგი ცალკე კონკრეტული კანდიდატისთვის. `.github/workflows/api-route-typecheck.yml` მუშაობს PRs ზე `main` ში ან `release/**`, უბიძგებს რომელიმე ფილიალის ოჯახს, ხელით გაგზავნას და `merge_group` ტიპის `checks_requested` მოვლენებს. მას არ აქვს ბილიკის ფილტრი. ჯგუფების შერწყმა შეამოწმეთ `merge_group.head_sha`; სხვა ღონისძიებები შეამოწმეთ `github.sha`. ყველა ღონისძიება იყენებს იგივე API დიაგნოსტიკური კარიბჭის და კარიბჭის ერთეულის ტესტებს. PR ბაზის რეტარგეტები ითხოვენ ახალ შემოწმებას; body/title რედაქტირება იყენებს მხოლოდ დაკვირვების სახელს `Admission not requested / API Route Typecheck` და ვერ შეცვლის დაშვების შემოწმებას.

### შენარჩუნებული მტკიცებულება მიღების რედიუსერში

`scripts/quality/validate-release-acceptance.mjs` ამუშავებს მიწოდებულ გეგმასა და მის
მანიფესტებს; ის არ ადასტურებს, რომ გეგმა გამოშვების სრულ კონვეიერს მოიცავს.
მის ანგარიშებში პირდაპირ არის მითითებული `releaseAcceptance: false`, მაშინაც კი, როცა გეგმა
`VERIFIED`-ია. `release-acceptance.yml` სამუშაო პროცესი კვლავ ჩრდილოვან ფიქსტურებს იყენებს და არა
რეალურ აგების, შეფუთვის, გაშვების ან დაწინაურების ქვითრებს.

შენარჩუნებული მტკიცებულების დასადასტურებლად CLI მოითხოვს `--evidence-root`-ს. ფაილები იძებნება
როგორც `<evidence-root>/<artifact_id>/<member>` და ჰეშირდება SHA-256-ით. მტკიცებულების გარეშე PASS ჩანაწერი,
არარსებული ან შეცვლილი ფაილი, სახიფათო გზა ან სიმბოლური ბმული
ვერიფიკაციას ხელს უშლის. არარსებული ფაილები ცარიელ, წარმატებულ ჟურნალებს არ უდრის. არსებული
SHA/run/attempt შემოწმებები დამოუკიდებლად რჩება: თანხვედრილი ბაიტები მოძველებულ
ქვითარს ვერ გამოასწორებს. ფაილის მთლიანობა შესრულების ავთენტიკურობის ან არტეფაქტის დაწინაურების მტკიცებულება არ არის.

### DAST იყენებს CI-ის შემოწმებულ ანაწყობს

CI-ის სავალდებულო დავალება `dast-smoke` იძახებს `.github/workflows/dast-smoke.yml`-ს `build`-ის შემდეგ. ის კოდის ცვლილებებისა და მონახაზის სტატუსის შერჩევის იმავე წესს მიჰყვება, რასაც აწყობა, მხარდაჭერილი fork PR-ების, release-ზე მიმართული PR-ებისა და შერწყმის ჯგუფების ჩათვლით. დაკარგული, ჩავარდნილი, გაუქმებული ან მოულოდნელად გამოტოვებული DAST დავალება ბლოკავს `Gate / CI`-ს. ხელახლა გამოსაყენებელ სამუშაო პროცესს დამოუკიდებელი PR ან ხელით გაშვების ტრიგერი არ აქვს; ხელით შემოწმება CI-ის გაშვებას იყენებს, რათა აწყობა და მისი მომხმარებელი ერთ გაშვებაში დარჩეს.

`scripts/ci/next-build-provenance.mjs` სრულ Next არტეფაქტს აფიქსირებს tar-ის დაიჯესტთან, საცავთან/მოვლენასთან/გაშვებასთან, მწარმოებლის მცდელობასთან, head/base/checkout/tree-სთან, სამუშაო პროცესების იდენტობებთან, lockfile-თან, Node-ის ზუსტ ვერსიასთან/ABI-სთან, პლატფორმასა და ბანდლერთან ერთად. DAST ირჩევს არტეფაქტის უცვლელ ID-ს `needs.build.outputs`-იდან, მოითხოვს ჩამოტვირთვის დაიჯესტის შემოწმებას და დამოუკიდებლად ითვლის ZIP-ის ჰეშს მწარმოებლის დაიჯესტთან შესადარებლად, სანამ `scripts/ci/unpack-ci-build.py`-ით ნებადართულ სიაში მყოფ ორ წევრს ამოიღებს. მანიფესტი და tar არქივიც უნდა ემთხვეოდეს მწარმოებლის დამოუკიდებელ გამოსავალს, სანამ Next-ის ფაილური ხე ამოიღება. ის არასოდეს ეძებს შტოს ბოლო წარმატებულ ანაწყობს. ნაწილობრივ ხელახალ გაშვებას შეუძლია იმავე მწარმოებლის მცდელობის გამოყენება, თუ მისი ID და ყველა შემავალი მონაცემი კვლავ ემთხვევა; დამადასტურებელი ჩანაწერი ორივე მცდელობას ინახავს.

მომხმარებელი რჩება ჰოსტირებულ Linux შემსრულებელზე, საცავის მხოლოდ წაკითხვის უფლებით და საცავის საიდუმლოებების გარეშე. ის აყენებს მწარმოებლის Node-ის ზუსტ ვერსიას, შემდეგ კი CLI-ს აწყობს `OMNIROUTE_REQUIRE_PREBUILT_NEXT=1`-ით. `scripts/build/standaloneInput.mjs` დამოუკიდებელი სერვერის არქონას უარყოფს ნებისმიერი სარეზერვო აწყობის დაწყებამდე; ჩვეულებრივი ლოკალური CLI აწყობები არსებულ სარეზერვო მექანიზმს ინარჩუნებს. სერვერის მზადყოფნის შემოწმება, Schemathesis და promptfoo ყველა წარმატებით უნდა დასრულდეს დავალების უცვლელ 25-წუთიან ზღვარში. წარმომავლობის ჩანაწერი ამტკიცებს შემავალი მონაცემების იდენტობასა და ბაიტებს და არა DAST სკანირების წარმატებას. არტეფაქტის ვადის გასვლა, შემსრულებლის შეფერხება ან სკანერის ჩავარდნა კვლავ არასრულ ან წარუმატებელ მტკიცებულებად რჩება; სარეკომენდაციო გარსი მას PASS-ად ვერ გადააქცევს.

### შერწყმის რიგი

`queue` ჭდე PR-ს Mergify-ის რიგში აგზავნის (`.mergify.yml`). Mergify ქმნის შავ PR-ს
`mergify/merge-queue/` განშტოებაზე, CI იქ სრულ ნაკრებს უშვებს, ხოლო თავდაპირველი PR მაშინ ერთიანდება,
როდესაც `Gate / CI`, `Gate / Quality` და `Merge integrity (changelog + generated skills)` წარმატებით დასრულდება.

Mergify თავის რიგის შეჯამებას შავი ვერსიის აღწერაში წერს და მისი რედაქტირება სხვა აპებსაც შეუძლიათ.
ასეთ შავ ვერსიაზე `pull_request` `edited` მოვლენა საკუთარ კონკურენტულ ჯგუფს იღებს
(`-queue-edit-<run_id>`), ამიტომ ის შავი ვერსიის რეალურ გაშვებას ვერ გააუქმებს და გეითსა და
მატრიცას გამოტოვებს. მხოლოდ `Merge integrity` აგრძელებს შესრულებას. გამოტოვებულ გეითის დავალებას შემოწმების სხვა სახელი აქვს,
რადგან Mergify გამოტოვებულ `Gate / CI`-ს წარუმატებელ შემოწმებად აღიქვამს და PR-ს რიგიდან იღებს.

რიგიდან ამოღების შემდეგ push ყოველთვის არ აბრუნებს PR-ს რიგში. მასზე დაწერეთ კომენტარი `@mergifyio queue`.

### სტატიკური სკანირების ინვენტარი

ვერსიონირებული npm-ალიასების ინვენტარი და სტატიკური სკანირების წევრობა განთავსებულია
`config/quality/gate-manifest.json`-ში. სკრიპტების სახელებისა და ზუსტი ბრძანებების
`package.json`-თან შესადარებლად გაუშვით `npm run check:gate-manifest`; დამატებები, წაშლები და
ბრძანებების აცდენა ჩააგდებს როგორც ლოკალურ hook-ს, ისე CI-ში ცვლილებების კლასიფიკაციის დავალებებს.
ალიასი არ არის სამუშაო პროცესის დავალება, მატრიცის ეგზემპლარი ან სატესტო შემთხვევა: ეს რაოდენობები
ურთიერთჩანაცვლებადად არ უნდა იყოს წარმოდგენილი.

არჩეული ალიასების შესრულების გარეშე შესამოწმებლად გამოიყენეთ `npm run quality:scan -- --list` ან
`npm run quality:scan:fast -- --list`. Runner npm entrypoint-ს იძახებს, ამიტომ მისი
runtime (მათ შორის Bun, სადაც კონფიგურირებულია) შენარჩუნებულია.
მანიფესტი ამ პროფილების მიღმა არსებულ ალიასებს ცალკე გამოძახებულად აღრიცხავს, ხოლო
ტექნიკური მომსახურების ბრძანებები მხოლოდ წაკითხვის სკანირების პროფილებში აკრძალულია.

ეს პროფილები მხოლოდ სტატიკურ სკანირებას მოიცავს. ისინი არ ადასტურებს პროდუქტის ტესტებს,
coverage-ს, შეფუთვას, გარე შემოწმებებს ან კანდიდატის გამოშვების სრულ მიღებას.
სამუშაო პროცესის დაშვება იყენებს დაკავშირებულ `config/quality/admission-policy.json`-სა და
`scripts/quality/admission-verdict.mjs`-ს. Release-observer პროფილები განცალკევებული რჩება;
მათი შესაბამისი შემოწმებები და ქვითრები დამოუკიდებლად შეამოწმეთ. სრული დამკვირვებლის სტატიკური
ბრძანებები განსაზღვრულია `config/quality/release-green-static-profile.json`-ში, მათ შორის
`audit:deps`, მუტაციური ტესტების შერჩევა და თარგმანის შემოწმებები. ჩამტვირთველი npm
ბრძანებებს package.json-სა და მოდელირებულ CI/Quality დეკლარაციებთან მიმართებით ამოწმებს; ის აცდენას
უარყოფს, ნაცვლად shell-ის ტოკენების არგუმენტებად შესრულებისა. სავალდებულო სკანერის SKIP/INCOMPLETE გამომავალი

### გამოქვეყნებული საბაზისო დოკუმენტაციის მდგომარეობა

`.github/workflows/i18n-base-health.yml` აკვირდება დოკუმენტაციის მდგომარეობას `main`-სა და `release/v*`-ზე შერჩეული
push-ების შემდეგ, ასევე ხელით გაშვებისას. მისი ფილტრები მოიცავს დოკუმენტაციას,
ძირეულ Markdown-ს, `llm.txt`-ს, თარგმანის მდგომარეობას/კონფიგურაციას და შესაბამის i18n ინსტრუმენტებს.
ერთადერთი `Published base documentation health` დავალება იყენებს ჰოსტირებულ Ubuntu-ს და ხუთწუთიან
ვადას. ის ასრულებს მხოლოდ წაკითხვად ვალიდაციას და წერს დიაგნოსტიკურ ქვითარს
დამოკიდებულებების ინსტალაციის, თარგმნის ან მდგომარეობის მიღების გარეშე.

`scripts/i18n/check-base-health.mjs` მოითხოვს, რომ წყაროს ჰეშთან, გამოტოვებულ სამიზნესთან, სამიზნის ჰეშთან,
მოძველებულ თარგმანთან და სექციების ქეშთან დაკავშირებული შეუსაბამობების რაოდენობა ნულის ტოლი იყოს. ის ასევე ამოწმებს მიმდინარე ძირითადი
დოკუმენტის/ლოკალის ფარგლებსა და მათ ჩაწერილ წარმომავლობას. არასწორი კონტექსტი, არასრული დაფარვა
ან შემმოწმებლის მუშაობის შეწყვეტა წარმოქმნის `INCOMPLETE`-ს; დადასტურებული აცდენა წარმოქმნის `FAIL`-ს. ორივე
აბრუნებს წარუმატებლობის აღმნიშვნელ დასრულების სტატუსს. ქვითარი მიბმულია checkout SHA-ზე, workflow-ზე, გაშვებასა და
მცდელობაზე და ინახება სახელით `i18n-base-health-<sha>-<run>-<attempt>`.

ეს გამოქვეყნებულ საბაზისო ვერსიაზე დამოუკიდებელი დაკვირვებაა. ის არ ამატებს PR-ის ან
merge-group-ის მოვლენას, სავალდებულო PR შემოწმებას, npm-ის alias-ს ან static-scan პროფილის წევრს.
არსებული დიფერენციალური PR პოლიტიკა და საბაზისო შემმოწმებლის საკონსულტაციო კლასიფიკაციები
კვლავ განცალკევებულია. წარმატებული ატვირთვა ვერ შეცვლის მდგომარეობის წარუმატებელ შედეგს PASS-ად.

### გაათავისუფლეთ PR სწრაფი გზა (`quality.yml`)

`.github/workflows/quality.yml` ავსებს CI main/release PRs ზე, უბიძგებს `main` ზე, აგზავნის და აერთიანებს ჯგუფებს. PRs იყენებს ბილიკით გაფილტრულ სწრაფ შემოწმებებს. სამუდამოდ გამორთული დუბლიკატი build წაიშალა; რეალური build/package/boot ჩეკები რჩება CI ში. ერთეულის კომპლექტი და ვიტესტი მუშაობს მხოლოდ CI ში (`Unit Tests (N/8)` და `Vitest`).

#### დავიწყებული და-ძმის ტესტების ანგარიში

`npm run check:forgotten-sibling-tests` მუშაობს, როგორც `Fast Quality Gates` ის საკონსულტაციო ნაბიჯი და ხელახლა იყენებს იმპორტის გადამწყვეტს ტესტის ზემოქმედების რუკის უკან. ყოველი შეცვლილი წარმოების მოდულისთვის, ის აცნობებს განმსაზღვრელ `changed module/symbol -> static consumer -> candidate sibling test` ჯაჭვებს, როდესაც კანდიდატის ტესტი არ არის pull-მოთხოვნის განსხვავებაში. Markdown-ის შეჯამება და JSON შედეგი შენარჩუნებულია, როგორც `forgotten-sibling-tests` სამუშაო ნაკადის არტეფაქტი კალიბრაციისთვის ნებისმიერი დაბლოკვის გაშვებამდე.

ლულის რეექსპორტი და დინამიური იმპორტი მხოლოდ გარჩევადობის დიაგნოსტიკაა; ისინი არასოდეს ქმნიან ბლოკირების აღმოჩენას. განხილული გამონაკლისები ცხოვრობს `config/quality/forgotten-sibling-allowlist.json` ში. თითოეულ ჩანაწერში უნდა იყოს მითითებული მომხმარებლისა და კანდიდატის ტესტი, მიუთითოს კონკრეტული დასაბუთება და დააკავშიროს GitHub საკითხი ან pull მოთხოვნა. არასწორი ჩანაწერები ვერ დაიხურა. გამონაკლისები ვერ ახშობს წაშლილი კანდიდატის ტესტს ან განსხვავებას, რომელიც ამატებს `.skip`/`.todo`; მტკიცების შესუსტება და სხვა ნიღბები რჩება დამოუკიდებლად ჩამკეტი `check:test-masking` კარიბჭის საკუთრებაში.

`tsconfig.build.json`-ში `"strict": false` არის მითითებული, ამიტომ `noImplicitAny` გამორთულია. core-ის კონფიგურაცია უფრო მკაცრი პარამეტრებით აკომპილირებს შერჩეულ 27-ფაილიან დაშვებულ სიას და თითოეული ჩანაწერის იმპორტების გრაფს მიჰყვება, ამიტომ ფაილები, რომლებიც build-ის პროგრამაში არასოდეს ჩნდება, იქ მაინც მოწმდება.

ეს შედეგი მნიშვნელოვანია, როცა აფასებთ, არის თუ არა ფაილი ტიპიზებული: **`check:build-typecheck`-ის ქვეშ ნულოვანი დიაგნოსტიკა არ ნიშნავს ნულს**. 26 ფაილიდან `@ts-nocheck`-ის ამოღებამ აჩვენა, რომ build-ის პროგრამაში მათგან 23 სუფთა იყო; ამ 23-დან თექვსმეტმა მკაცრ პროგრამაში დაახლოებით 120 implicit-any შეცდომა გამოავლინა. ფაილის სუფთად მიჩნევამდე ორივე შეამოწმეთ.

#### `check-ui-value-drift` — მოძველებული თარგმანის კარიბჭე

აფიქსირებს იმ ერთადერთ i18n რეგრესიას, რომელსაც სხვა შემოწმებები სტრუქტურულად ვერ ხედავენ: ინგლისური მნიშვნელობა
ხელახლა იწერება, ხოლო _წინა_ ინგლისური ტექსტიდან მიღებული თარგმანები უცვლელი რჩება, რის გამოც
არაინგლისურენოვანი მომხმარებლები კვლავ თავდაჯერებულად ჩამოყალიბებულ, მაგრამ უკვე არასწორ ტექსტს კითხულობენ.

ეს რეალურ რელიზშიც მოხვდა. `oauthModal.googleOAuthWarning` ხელახლა დაიწერა, როდესაც Antigravity-ის
შესვლის დამხმარე დაემატა (#5203); **43 ლოკალიდან 39-ში** დარჩა ტექსტი, რომელიც ოპერატორებს ეუბნებოდა, რომ „სრული
URL დაეკოპირებინათ და ქვემოთ ჩაესვათ“ — ამ პროვაიდერისთვის ეს პროცესი ვერ დასრულდება. პრობლემა
#8463-მდე შეუმჩნეველი დარჩა, რადგან:

- `sync-ui-keys` მხოლოდ იმ გასაღებებს ავსებს, რომლებიც **არ არსებობს**, და არასოდეს — **მოძველებულებს**;
- `check-ui-keys-coverage` გასაღების _არსებობას_ ითვლის, ამიტომ მოძველებული თარგმანი დაფარულად მიიჩნევა;
- `check-translation-drift` აკონტროლებს `docs/i18n/<locale>/**.md` დოკუმენტაციის ასლებს —
  ის `src/i18n/messages/*.json`-ს არასოდეს კითხულობს. 2026-09-ის ხელახალი სინქრონიზაციის შემდეგ ბლოკირებადია `docs-sync-strict` დავალებაში:
  შეცვალეთ ძირითადი დოკუმენტი → `npm run i18n:run -- --files=<doc>` (სექციის დონეზე, ნაკლებრესურსიანი).

**ცვლილებაზე ორიენტირებული და არა საბაზისო მონაცემებზე დაფუძნებული.** ის შერწყმის ბაზაში არსებულ `en.json`-ს
სამუშაო ხეს ადარებს; თითოეული გასაღებისთვის, რომლის ინგლისური მნიშვნელობაც შეიცვალა, ნებისმიერი ლოკალი, სადაც
ხელუხლებელი თარგმანი ჯერ კიდევ რჩება, მოძველებულია. ეს განზრახ **ყინავს მანამდე არსებულ ტექნიკურ ვალს** — ცვლილებების სხვაობით

არ გააჩნიათ და ისინი ინარჩუნებენ აბსოლუტურ (გლობალურ) შედარებას. დაფარვა, დუბლირება და ტიპების დაფარვა ჯერჯერობით
გლობალური რჩება (მათი ხელსაწყოები თითოეული ფაილის სხვაობას მცირე დანახარჯით ვერ ქმნიან) — მომავალში მათზეც შეიძლება იგივე მიდგომა გავრცელდეს.

**ფაზის დახურვა v4.0-ზე (LTS = წინანდელზე მკაცრი და არა „ნორმალურ მდგომარეობაში დაბრუნება“)**

1. სუფთა `release/v4.0.0` წვერზე: ჩანაწერისთვის გაუშვით `npm run quality:headroom --json`, შემდეგ
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update` და თითოეული typecheck შემოწმების
   `--update` — ყველა საბაზო მნიშვნელობა გაზომილ მნიშვნელობამდე მცირდება.
2. წაშალეთ `_policy` ფაილიდან `quality-baseline.json` (ხელახლა ააქტიურებს `--require-tighten`-სა და ღამის
   დაგროვებას), აღადგინეთ `THRESHOLD = 36` (ან უფრო მაღალი მნიშვნელობა) ფაილში `check-openapi-coverage.mjs`.
3. გაზომილ მნიშვნელობაზე მეტად გაამკაცრეთ იქ, სადაც მოდულარიზაციამ შედეგი გამოიღო: file-size-ის `cap` დააბრუნეთ 1000-ზე
   (ან 800-ზე), დაფარვის მინიმალური ზღვრები გაზარდეთ +5-ით, ხოლო მოდულარიზებული პაკეტებისთვის გამოუყენებელი ექსპორტების რაოდენობა დააყენეთ 0-ზე.

## Ratchet-ის საბაზისო დონე (`quality-baseline.json`)

Ratchet-ის ძრავა (`scripts/quality/check-quality-ratchet.mjs`) კითხულობს `quality-baseline.json`-ს
და ადარებს მას ახლად შეგროვებულ `quality-metrics.json`-ს. ნებისმიერი მეტრიკა, რომელიც
მის epsilon-ზე მეტად გაუარესდება, აგების პროცესს წარუმატებლად დაასრულებს.

ამჟამად თვალყურისდევნებული მეტრიკები:

| მეტრიკა               | მიმართულება | მნიშვნელობა                                          |
| --------------------- | ----------- | ---------------------------------------------------- |
| `eslintWarnings`      | `down`      | ESLint-ის გაფრთხილებების რაოდენობა არ უნდა გაიზარდოს |
| `coverage.statements` | `up`        | ინსტრუქციების დაფარვა არ უნდა შემცირდეს              |
| `coverage.lines`      | `up`        | ხაზების დაფარვა არ უნდა შემცირდეს                    |
| `coverage.functions`  | `up`        | ფუნქციების დაფარვა არ უნდა შემცირდეს                 |
| `coverage.branches`   | `up`        | განშტოებების დაფარვა არ უნდა შემცირდეს               |

რეალური გაუმჯობესების შემდეგ საბაზისო დონის განახლებისთვის:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` ალამი მიმდინარე გაზომილ მნიშვნელობებს `quality-baseline.json`-ში წერს.
ეს ფაილი დააკომიტეთ იმ ცვლილებასთან ერთად, რომელმაც მეტრიკა გააუმჯობესა. PR, რომელიც
მეტრიკას საბაზისო დონის განახლების გარეშე აუმჯობესებს, გამოვლინდება `--require-tighten`-ის მიერ (ფაზა 6A.5,
განხორციელება მოსალოდნელია).

### CodeQL რატჩეტი: კანდიდატის მიღება და საცავის ინვენტარი

CI კანდიდატის CodeQL მიღებას აშკარა დამოკიდებულებათა ჯაჭვით მართავს: `codeql-scan` იძახებს ოთხი ენის მატრიცას `codeql.yml`-ში, შემდეგ `codeql-admission` ასრულებს `node scripts/check/check-codeql-ratchet.mjs --candidate`-ს. `Gate / CI` ორივე შედეგს მოითხოვს. Quality საკუთარ რიცხვით შემოწმებებს ინარჩუნებს, მაგრამ მწარმოებლის დასრულებამდე სკანერს არ მიმართავს; მარტო `Gate / Quality` კანდიდატის სრულ მიღებას არ ნიშნავს. CodeQL მხოლოდ დოკუმენტაციის შემცვლელი კანდიდატებისთვისაც სავალდებულოა.

პოლიტიკა `config/quality/codeql-admission-policy.json`-ში ირჩევს Actions-ს, C/C++-ს, JavaScript/TypeScript-სა და Python-ს, მოთხოვნათა ნაკრებს default, საფრთხის მოდელს remote და აწყობის რეჟიმს none. მწარმოებლის წინასწარი შემოწმება უარყოფს გააქტიურების მოლოდინში მყოფ ჩანაწერს და აშკარა სამიზნე სიის გარეთ არსებულ შტოებს. საწყისი სამიზნეებია main და release/v3.8.53; შემდეგ release-ს განხილული ჩართვის პროცედურა სჭირდება. CI-ის არსებული უფრო ფართო release PR ტრიგერი შენარჩუნებულია, მაგრამ ჯერ ჩაურთველი სამიზნე ამოღებამდე HOLD-ს აცხადებს და გაზომვის გარეშე PASS-ს ვერ იღებს.

მატრიცის თითოეული დავალება იწერს SARIF ატვირთვის ფაქტობრივ ID-ს, ენას, კატეგორიას, გაშვებასა და მცდელობას, გამომძახებელი სამუშაო პროცესის იდენტობას, მოვლენის ref/head/base/merge SHA-სა და პოლიტიკის ჰეშს. დამოკიდებული დავალება ჩამოტვირთავს მხოლოდ ამ გაშვების დამადასტურებელ ჩანაწერებს და ამოწმებს არტეფაქტების დაიჯესტებს. საჭიროა ოთხივე კატეგორია, წარმატებული მწარმოებელი და თითოეული ზუსტი ატვირთვის დასრულებული დამუშავება. ის იყენებს API-ის sarif_id ფილტრს და არა შტოზე ნაპოვნ უახლეს ანალიზს. ნაწილობრივ ხელახალ გაშვებას შეუძლია იმავე გაშვებისა და კანდიდატის წინა მცდელობიდან წარმატებული კატეგორიების გამოყენება, მწარმოებელი მცდელობის შენარჩუნებით; მიმდინარე ჩავარდნილ მწარმოებელს წინა მწვანე მტკიცებულების ხელახლა გამოყენება არ შეუძლია.

CodeQL action დამუშავებას ელოდება, თუმცა მის დაფიქსირებულ იმპლემენტაციას სტატუსის წაკითხვის ჩავარდნის ან ლოდინის ამოწურვის შემდეგ შეუძლია გაფრთხილება და გაგრძელება. ამიტომ მიღების ეტაპი დამუშავებას ხელახლა ამოწმებს. გამოტოვებული კატეგორიები, დაუმთავრებელი დამუშავება, ჩავარდნილი ან გაუქმებული დავალებები, მოძველებული იდენტობა, არასრული პაგინაცია ან მიუწვდომელი API-ები წარმოშობს HOLD-ს და გამოსვლის კოდს 2. დამოუკიდებელი სკანერის სამუშაო პროცესისთვის ფიქსირებული ლოდინი აღარ არსებობს. დაუსკანერებელი PR ვერ გაივლის მხოლოდ იმიტომ, რომ გაფრთხილებების მოთხოვნამ 0 დააბრუნა. გაზომილი რაოდენობა, რომელიც `metrics.codeqlAlerts.value`-ს აღემატება, იწვევს გამოსვლის კოდს 1; სხვა შტოს გაფრთხილებების დასატევად საბაზისო ზღვარი არ იზრდება. [ატვირთვის სტატუსი და ანალიზის მოძიება](https://docs.github.com/en/rest/code-scanning/code-scanning).

დამადასტურებელი ჩანაწერი ინახავს ატვირთვისა და ანალიზის ID-ებს, კატეგორიებს, ხელსაწყოთა ვერსიებს, ref/SHA-ს, საბაზისო ზღვარსა და გაფრთხილებების რაოდენობას. SARIF-ის იდენტობა/შედეგების რაოდენობა, წესების მინიმალური რაოდენობა და გაფრთხილებების ზუსტი შემთხვევები კვლავ სავალდებულოა. მიღებამდე PR/ანალიზის იდენტობები ხელახლა მოწმდება. ეს შემოწმებები ადასტურებს კონფიგურირებული კატეგორიების დაფარვას და არა ყოველი ამოღებული საწყისი ფაილის ინვენტარს. C/C++-ის აწყობის გარეშე ამოღება არ მოიცავს პროექტის აწყობისას გენერირებულ კოდს. წყაროს გამონაკლისებს კვლავ განხილვა სჭირდება, ხოლო ცვლილების კონტრიბუტორზე მიკუთვნებას — შედარებადი მტკიცებულება ზუსტი საბაზისო ვერსიიდან.

`codeql-maintenance.yml` უზრუნველყოფს აქტიური release-ის push სკანირებებსა და ყოველკვირეულ განრიგს PR/main მწარმოებლების დუბლირების გარეშე. `nightly-codeql-inventory.yml` მთელი საცავის საბაზისო ზღვარს ცალკე ინახავს, იყენებს `--strict-measurement`-ს და გაზომვის მიუწვდომლობისას მარცხდება. ძველი ლოკალური შემგროვებლის შემწყნარებელი გამოტოვება კანდიდატის მიღება არ არის. გამკაცრება კვლავ მოითხოვს აშკარა `--update`-ს მას შემდეგ, რაც საერთო რაოდენობის შემცირება დადასტურდება.

Advanced სამუშაო პროცესი არ უნდა გამოქვეყნდეს, სანამ Default Setup კონფიგურირებულია: GitHub ასეთ კომბინაციას უარყოფს. ვერსირებული პოლიტიკა მოლოდინში რჩება, სანამ განხილული ადმინისტრაციული გადასვლა განმეორებითი წაკითხვით არ დადასტურდება. გამოქვეყნებამდე ოპერატორი აფიქსირებს საცავს, head/base/tree-ს, პოლიტიკის/პატჩის/უკუგების ჰეშებსა და დაკვირვებულ კონფიგურაციის მდგომარეობას; `node scripts/quality/codeql-producer.mjs verify-admin-readback` ამოწმებს მიწოდებულ მოსალოდნელ და ფაქტობრივ JSON ჩანაწერებს. ეს ტექნიკური დაცვაა და არა ოპერატორის თანხმობა ან ახალი განმეორებითი წაკითხვების მოპოვების შემცვლელი. PR ტოკენი Administration წვდომას არასოდეს ითხოვს. გაშვებასა და სკანერის ნებისმიერ ცვლილებას ეს ცალკე განმეორებითი წაკითხვა სჭირდება, რეალური PR-ის, fork-ისა და შერწყმის ჯგუფის თავსებადობის მტკიცებულებასთან ერთად.
