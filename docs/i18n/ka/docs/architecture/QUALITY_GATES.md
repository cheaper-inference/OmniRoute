## კარიბჭის ინვენტარი და შესრულების პროფილები

### კანდიდატის მიღება

CI და Quality Gates სამუშაო ნაკადები გამოსცემს სტაბილურ ვერდიქტს: `Gate / CI` და `Gate / Quality`. მათი ვერსიით დაშვების პოლიტიკა ჩამოთვლის ყველა ზემოთ ნაკადის სამუშაოს, როგორც საჭირო ან საკონსულტაციო. საჭირო სამუშაო უნდა იყოს წარმატებული: გამოტოვებული, გაუქმებული, გამოტოვებული, მომლოდინე და უცნობი შედეგები ვერ დაადგენს PASS. მხოლოდ დოკუმენტებისთვის ან მხოლოდ კატალოგისთვის განკუთვნილი მოქმედი კლასიფიკაციით შეიძლება კოდის ზოლი გამოუსადეგარი გახდეს; პროექტი PR არ არის მიღებული კანდიდატი. `hotfix` იარლიყი არ უარყოფს მტკიცებულებებს.

ორივე სამუშაო ნაკადი მოიცავს PRs main/release ტოტებად, უბიძგებს `main`, ხელით გაგზავნას და გაერთიანების მოვლენებს. დააწკაპუნეთ, გაგზავნეთ და შერწყმა-ჯგუფური გაუშვით სრული შერჩევა. `release/**` ზე გადასვლები არ იწყებენ მათ (2026-10-18): ყოველმა ცვლილებამ უკვე გაუშვა მატრიცა მის PR ზე და გაერთიანებული კომბინაცია არის Release-Green-ის სამუშაო (`docs/ops/RUNNER_BOX.md` → Hosted lane). Forks და შერწყმის ჯგუფები იყენებენ მასპინძელ მორბენლებს სამუშაოებისთვის, რომლებიც სხვაგვარად ირჩევენ თვითმასპინძელ მორბენლებს; საკმარისი ჰოსტინგის მოცულობა უნდა დადასტურდეს გაშვებამდე.

ჩვეულებრივი PR მართავს სწრაფ შერჩევას. დაშვების პოლიტიკის `full-code` და `full-code-e2e` ზოლები (E2E, ინტეგრაცია, პაკეტის არტეფაქტი, Electron smoke, Bun SQLite, ეკოსისტემის და პროტოკოლის კლიენტები) მუშაობს მხოლოდ Mergify რიგის პროექტზე ან სრულ გაშვებაზე: `gh workflow run ci.yml --ref <branch>`.

თითოეული JSON ქვითარი განსაზღვრავს გამოტანილ SHA, სამუშაო პროცესის გაშვებას და მცდელობას. CLI უარყოფს checkout/event SHA შეუსაბამობას. სამუშაო პროცესის ტესტები აკავშირებს პოლიტიკის წევრობას ვერდიქტის სამუშაოს `needs` სიაში, ასე რომ ახალი ან ამოღებული ზოლი არ შეიძლება ჩუმად გაქრეს. ქვითრები მოიცავს საკუთარ სამუშაო პროცესს და არა პუბლიკაციას, განლაგებას ან არსებული საკონსულტაციო სკანერის ინტერიერს. ფილიალის წესებში ორივე გამშვები სახელის გააქტიურება ცალკე ადმინისტრაციული ცვლილებაა; ამ სამუშაოების დამატება თავისთავად არ იცავს ფილიალს.

### რიგის შერწყმა

`queue` ლეიბლი აგზავნის PR Mergify რიგში (`.mergify.yml`). Mergify ხსნის PR მონახაზს `mergify/merge-queue/` ფილიალზე, CI აწარმოებს სრულ შერჩევას იქ და ორიგინალური PR ერწყმის, როდესაც `Gate / CI`, `Gate / Quality` და `Merge integrity (changelog + generated skills)` გაივლის.

Mergify წერს თავის რიგის შეჯამებას მონახაზის აღწერაში და სხვა აპებსაც შეუძლიათ მისი რედაქტირება. `pull_request` `edited` მოვლენა ასეთ დრაფტზე იღებს თავის კონკურენტულ ჯგუფს (`-queue-edit-<run_id>`), ამიტომ მას არ შეუძლია გააუქმოს მონახაზის რეალური გაშვება და გამოტოვებს კარიბჭეს და მატრიცას. მხოლოდ `Merge integrity` ჯერ კიდევ მუშაობს. გამოტოვებული კარიბჭის სამუშაოს აქვს სხვა შემოწმების სახელი, რადგან Mergify კითხულობს გამოტოვებულ `Gate / CI`, როგორც წარუმატებელ შემოწმებას და წყვეტს PR.

დეკეუის შემდეგ, ბიძგი ყოველთვის არ ითხოვს PR ს. კომენტარი `@mergifyio queue` ამაზე.

### შენახული მტკიცებულება მიღების რედუქტორში

`scripts/quality/validate-release-acceptance.mjs` ამცირებს მიწოდებულ გეგმას და ავლენს მას; იგი არ ადგენს, რომ გეგმა მოიცავს სრულ გაშვების მილსადენს. მისი ანგარიშები ცალსახად ადგენს `releaseAcceptance: false`, მაშინაც კი, როდესაც ეს გეგმა არის `VERIFIED`. `release-acceptance.yml` სამუშაო ნაკადი კვლავ იყენებს ჩრდილოვან მოწყობილობებს და არა რეალურ კონსტრუქციას, პაკეტს, ჩატვირთვის ან სარეკლამო ქვითრებს.

CLI მოითხოვს `--evidence-root` შენახული მტკიცებულებების გადამოწმებისთვის. ფაილები წყდება როგორც `<evidence-root>/<artifact_id>/<member>` და ჰეშირებულია როგორც SHA-256. PASS ჩანაწერი მტკიცებულების გარეშე, დაკარგული ან შეცვლილი ფაილი, სახიფათო გზა ან სიმბლაკი ხელს უშლის გადამოწმებას. დაკარგული ფაილები არ არის ცარიელი წარმატებული ჟურნალის ექვივალენტი. არსებული SHA/run/attempt ჩეკები რჩება დამოუკიდებლად: ბაიტების შესატყვისი ვერ გადაარჩენს შემორჩენილ ქვითარს. ფაილის მთლიანობა არ არის შესრულების ავთენტურობის ან არტეფაქტის პოპულარიზაციის მტკიცებულება.

### სტატიკური სკანირების ინვენტარი

ვერსიული npm-alias ინვენტარი და სტატიკური სკანირების წევრობა ცოცხალია `config/quality/gate-manifest.json` ში. გაუშვით `npm run check:gate-manifest` სკრიპტის სახელებისა და ზუსტი ბრძანებების დასადასტურებლად `package.json` მიმართებაში; დამატებები, ამოღება და ბრძანების დრიფტი ვერ ახერხებს როგორც ლოკალურ ჰუკს, ასევე ცვლილება-კლასიფიკაციის სამუშაოებს CI ში. მეტსახელი არ არის სამუშაო პროცესის სამუშაო, მატრიცის მაგალითი ან საცდელი შემთხვევა: ეს რიცხვები არ უნდა იყოს წარმოდგენილი, როგორც ურთიერთშემცვლელი.

გამოიყენეთ `npm run quality:scan -- --list` ან `npm run quality:scan:fast -- --list` არჩეული მეტსახელების შესამოწმებლად მათი შესრულების გარეშე. მორბენალი იწვევს npm შესვლის წერტილს, ასე რომ, მისი გაშვების დრო (მათ შორის, Bun სადაც არის კონფიგურირებული) შენარჩუნებულია. მანიფესტი იწერს ფსევდონიმებს ამ პროფილების გარეთ, როგორც ცალკე გამოძახებული, და ტექნიკური ბრძანებები აკრძალულია მხოლოდ წასაკითხად სკანირებულ პროფილებში.

ეს პროფილები მოიცავს მხოლოდ სტატიკურ სკანირებას. ისინი არ ამოწმებენ პროდუქტის ტესტებს, დაფარვას, შეფუთვას, გარე შემოწმებას ან კანდიდატის სრულ გამოშვებას. სამუშაო პროცესის დაშვება იყენებს დაკავშირებულ `config/quality/admission-policy.json` და `scripts/quality/admission-verdict.mjs`. გამოშვება-დამკვირვებლის პროფილები რჩება ცალკე; დამოუკიდებლად შეამოწმოს მათი შესაბამისი ჩეკები და ქვითრები. დამკვირვებლის სრული სტატიკური ბრძანებები გამოცხადებულია `config/quality/release-green-static-profile.json` ში, მათ შორის `audit:deps`, მუტაციის ტესტის შერჩევა და თარგმანის შემოწმება. ჩამტვირთავი ამოწმებს npm ბრძანებებს package.json და მოდელირებული CI/Quality დეკლარაციების წინააღმდეგ; ის უარყოფს დრიფტს, ნაცვლად იმისა, რომ არგუმენტად განახორციელოს shell ტოკენები. სკანერის საჭირო SKIP/INCOMPLETE გამომავალი ვერ ადგენს PASS. პროფილი აღრიცხავს მის გარე გამონაკლისებს და არ ცვლის ჰოსტირებული გაშუქებას, ტესტის მატრიცებს, პაკეტს ან განლაგების მტკიცებულებებს. ქვემოთ მოცემული პროზაული ინვენტარი არის მითითება და არა მტკიცებულება იმისა, რომ კარიბჭე რეალურად გაიქცა.

სკრიპტები ცხოვრობენ `scripts/check/` (პოლიტიკის კარიბჭე) და `scripts/quality/` (რათეტის ძრავის) ქვეშ. ჭეშმარიტების CI წყაროა `.github/workflows/ci.yml`.

### გაათავისუფლეთ PR სწრაფი გზა (`quality.yml`)

`.github/workflows/quality.yml` ავსებს CI main/release PRs ზე, უბიძგებს `main` ზე, აგზავნის და აერთიანებს ჯგუფებს. PRs იყენებს ბილიკით გაფილტრულ სწრაფ შემოწმებებს. სამუდამოდ გამორთული დუბლიკატი build წაიშალა; რეალური build/package/boot ჩეკები რჩება CI ში. ერთეულის კომპლექტი და ვიტესტი მუშაობს მხოლოდ CI ში (`Unit Tests (N/8)` და `Vitest`).

#### დავიწყებული და-ძმის ტესტების ანგარიში

`npm run check:forgotten-sibling-tests` მუშაობს `Fast Quality Gates` ის საკონსულტაციო ნაბიჯის სახით და ხელახლა იყენებს იმპორტის გადამწყვეტს ტესტის ზემოქმედების რუკის უკან. ყოველი შეცვლილი წარმოების მოდულისთვის, ის აცნობებს განმსაზღვრელ `changed module/symbol -> static consumer -> candidate sibling test` ჯაჭვებს, როდესაც კანდიდატის ტესტი არ არის pull-მოთხოვნის განსხვავებაში. Markdown-ის შეჯამება და JSON შედეგი შენარჩუნებულია, როგორც `forgotten-sibling-tests` სამუშაო ნაკადის არტეფაქტი კალიბრაციისთვის ნებისმიერი დაბლოკვის გაშვებამდე.

ლულის რეექსპორტი და დინამიური იმპორტი მხოლოდ გარჩევადობის დიაგნოსტიკაა; ისინი არასოდეს ქმნიან ბლოკირების აღმოჩენას. განხილული გამონაკლისები ცხოვრობს `config/quality/forgotten-sibling-allowlist.json` ში. თითოეულ ჩანაწერში უნდა იყოს მითითებული მომხმარებლისა და კანდიდატის ტესტი, მიუთითოს კონკრეტული დასაბუთება და დააკავშიროს GitHub საკითხი ან pull მოთხოვნა. არასწორი ჩანაწერები ვერ დაიხურა. გამონაკლისები ვერ ახშობს წაშლილი კანდიდატის ტესტს ან განსხვავებას, რომელიც ამატებს `.skip`/`.todo`; მტკიცების შესუსტება და სხვა ნიღბები რჩება დამოუკიდებლად ჩამკეტი `check:test-masking` კარიბჭის საკუთრებაში.

#### ტიპის შემოწმების ორი პროგრამა განსხვავებულად პასუხობს

`typecheck:core` და `check:build-typecheck` აგროვებენ სხვადასხვა პროგრამებს სხვადასხვა ვარიანტში და ერთი და იგივე ფაილი შეიძლება იყოს სუფთა ერთში და სავსე იყოს შეცდომებით მეორეში.

#### თარგმანის სარკეები მიღებული ფაილებია (PR რეჟიმი vs გამოშვების რეჟიმი)

ფუნქცია PR არედაქტირებს მხოლოდ ინგლისურ წყაროებს. `docs/i18n/<locale>/**` სარკეები (მათ შორის 66 `llm.txt` ასლები და თარგმნილი `CHANGELOG.md` ფაილები) და `.i18n-state.json` გადაიწერება ერთი ნაბიჯით მთარგმნელობითი ტალღით (`docs/i18n-*` / `chore/i18n-*` ტოტები, დაგეგმილი `i18n-mirror-refresh.yml`) და გამოშვებით (`npm run release:sync-changelog-i18n`). ამრიგად, სარკის კარიბჭეები მუშაობს ორ რეჟიმში, გადაწყვეტილი `scripts/check/lib/gateMode.mjs` ით (`--mode=pr|release`, შემდეგ `OMNIROUTE_GATE_MODE`, შემდეგ მოქმედებების მოვლენა; ლოკალური გაშვება არის `release`):

- `check:docs-sync` — გამოშვების რეჟიმი გადის ყოველ შემოწმებას. PR რეჟიმი ინახავს package.json/OpenAPI ვერსიას, root CHANGELOG სათაურებს და გადანაცვლებულ-docs მცველს და ბეჭდავს `SKIP reason=pr-mode` `llm.txt` სარკის ასლებისთვის და თარგმნილი CHANGELOG სექციებისთვის — გარდა იმ შემთხვევისა, როცა PR არ წერს სარკეებს: `config/quality/derived-paths/*.json` ში `docs/i18n/**` ოჯახის დამწერად გამოცხადებული head ფილიალი, რომელიც ამოწმებს diff-ს და წყვეტს diff-ს, და წყვეტს difff-ს და წყვეტს. `docs/i18n/<locale>/llm.txt` გადის `CHANGELOG.md` რომელიც მკაცრად ამოწმებს. განსხვავება ბაზა არ წყდება depth-1 checkout-ში ( `docs-sync-strict` სამუშაო), ამიტომ PR რეჟიმი ასევე აწარმოებს ერთ შემოწმებას, რომელიც არ საჭიროებს ბაზას: ყოველი `llm.txt` სარკე უნდა არსებობდეს, შეინარჩუნოს მისი `---` გამყოფი და ატარებდეს ან ძირის სხეულს, ან სარკეების უმეტესობას. ძირი, რომელიც გადაადგილდება, ყველა სარკეს თანაბრად აფუჭებს და გადის; ერთი სარკეში ხელით შესწორება ვერ ხერხდება. თარგმნილ `CHANGELOG.md` ფაილებს არ აქვთ ასეთი შემოწმება depth-1 PR შეკვეთაში.
- წინასწარი ჩადენის კაუჭი გადის `check-docs-sync.mjs --mode=pr`: ვალდებულება ფასდება იმის მიხედვით, რასაც აკეთებს. დროშის გარეშე ლოკალური გაშვება არის გამოშვების რეჟიმი და ერთი გაერთიანებული PR, რომელიც არედაქტირებს root `llm.txt` დაბლოკავს ყოველი მოგვიანებით ჩადენას ამ ბაზაზე, სანამ ტალღა გაიქცა. იგივე წესი მოქმედებს ნებისმიერი რეჟიმის გაცნობის კარიბჭისთვის, Husky Hook გადის: Hook გადის `--mode=pr`, და მკაცრი განაჩენი რჩება გამოშვების რეჟიმის გაშვებაზე (გამოშვება PR, უბიძგებს `main` ზე, ჩვეულებრივი ლოკალური გაშვება).
- სარკის შემცველი ერთეულის ტესტები (`tests/_helpers/mirrorFreshness.ts`: `cycle-docs-mirror-contract`, `resilience-pre-dispatch-docs-mirrors`, `cli-env-quality-docs-mirrors`, `docs/*-locales`) — გამოშვების რეჟიმი ამტკიცებს ყველა ლოკალს. PR რეჟიმი ამტკიცებს მხოლოდ იმ სარკეებს, რომლებიც აქტუალურია ინგლისურ წყაროსთან `.i18n-state.json` მიხედვით (მთლიანი ფაილის ჰეში, ან ჩაწერილი სექციის ჰეში ტესტის ქინძისთავები) და გამოტოვებს ძველ სარკეებს მიზეზით. `target_hash` წარმოშობის შემოწმებები მუშაობს ყველა ლოკალისთვის ორივე რეჟიმში. სიახლე არის `## ` მონაკვეთზე, ერთეული `run-translation.mjs` ჰეშები; გრძელი სექცია (ამ ფაილის კარიბჭის ინვენტარი დაახლოებით მისი ნახევარია) ნიშნავს, რომ მასში არსებული ნებისმიერი რედაქტირება ტოვებს ამ სარკეებს და მათი PR რეჟიმის მტკიცებულებები გამოტოვებს შემდეგ ტალღას. წამყვანი, რომელსაც ინგლისური წყარო აღარ შეიცავს, უბრუნდება მთლიანი ფაილის შედარებას.
- `i18n translation drift` — რჩევები PRs ზე, მკაცრი ბიძგების, ღამით და გამოშვების ჭრის შესახებ, ამიტომ მოძველებული სარკე ვერ გაიგზავნება გამოშვებაში.

`scripts/i18n/sync-llm-mirrors.mjs` (ასევე ექსპორტირებული როგორც `syncLlmMirrors()`, `--dry-run` ით) ხელახლა წერს `llm.txt` სარკეებს; გამოშვების განახლება, მთარგმნელობითი ტალღა და დაგეგმილი `i18n-mirror-refresh.yml` აწარმოებს მას (განახლება აღმოაჩენს შემორჩენილ `llm.txt` სარკეებს მშრალი გაშვებით, რადგან დრიფტის ანგარიში არ არის ჩამოთვლილი და სინქრონიზებს მათ `check:docs-all` მდე).

PR ფუნქცია არასოდეს წერს მნიშვნელობას, რომელიც დამოკიდებულია მისი ბაზის მდგომარეობაზე: პროვაიდერი, მიგრაცია, MCP-ინსტრუმენტები და სტრატეგიის რაოდენობა, README SVG ნომრები, ფაქტების სურათი. ერთი ნაბიჯი ხელახლა გამოითვლება ყველა მათგანს, `npm run release:refresh-derived`, გაშვებული გამოშვებით და ღამით მიღებული-განახლების PR. ასე რომ** რელიზებს შორის ბაზა დგას ცოცხალი კოდის უკან დიზაინის მიხედვით** და კარიბჭე ან ტესტი, რომელიც ადარებს ხეს ცოცხალ კოდთან, წითელი იქნება ყველა PR ზე მას შემდეგ, რაც და-ძმა დაამატებს პროვაიდერს. ამიტომ, კარიბჭეები, რომლებიც აფასებენ მნიშვნელობებს, მუშაობს ორიდან ერთ-ერთ რეჟიმში, გადაწყვეტილი `scripts/check/lib/gateMode.mjs` ით (პირველი მატჩის მოგება):

1. `--mode=pr|release` ბრძანების ხაზზე;
2. `OMNIROUTE_GATE_MODE` გარემოს ცვლადი (`pr` ან `release`);
3. ავტომატური, GitHub მოქმედებების მოვლენიდან: `pull_request` რომლის თავი არ არის `release/v*`, `merge_group`, ან ბიძგი `omni-queue/**` → `pr`; ყველაფერი დანარჩენი (დაძაბვა, განრიგი, გაგზავნა, გამოშვება PR `release/v* → main`, ნებისმიერი ლოკალური გაშვება) → `release`.

რა `check:docs-counts` (`scripts/check/check-docs-counts-sync.mjs`) ვერ ხერხდება თითოეულ რეჟიმში:

| რეჟიმი    | მარცხდება                                                                                                                                                                                                                                                                                                                                                                                                                                               | ცოცხალი ფაქტები სჭირდება |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `release` | ყოველი შემოწმება, მკაცრი თანასწორობა ხისგან შეგროვებული ფაქტების მიმართ (ქცევა, რომელსაც კარიბჭე ყოველთვის ჰქონდა): შემორჩენილი რაოდენობა, ვერსია, დაფარვის სართული ან SVG რიცხვი არის STRICT დრიფტი.                                                                                                                                                                                                                                                   | დიახ                     |

აგენტ-ინსტრუქციის ფაილები ატარებენ** არა** საერთოდ მიღებული რაოდენობა: `AGENTS.md`, `llm.txt` (და მისი `docs/i18n/*/llm.txt` ასლები), bs `AGENTS.md` fork, `open-sse/services/AGENTS.md`, `src/shared/constants/agentSkills.ts`, `skills/README.md` და ყოველი `skills/*/SKILL.md` მიუთითებს წყაროზე (მაგალითად `ROUTING_STRATEGY_VALUES` `src/shared/constants/routingStrategies.ts` ში) და ნაცვლად `npm run facts` ზე. უცვლელი "არ არის მიღებული რაოდენობა (აგენტის ინსტრუქციის ფაილი ...)" ვერ ითვლის იქ (პროვაიდერები, მიგრაცია, MCP ინსტრუმენტები და სპექტები, მარშრუტიზაციის სტრატეგიები, ქულების ფაქტორები, რეჟიმის პაკეტები) ორივე რეჟიმში, ასე რომ, გამოშვების განახლებას არასოდეს მოუწევს ინსტრუქციის ფაილის გადაწერა.

`pr` რეჟიმში დამწერის ფილიალებს შეუძლიათ შეცვალონ მართული მნიშვნელობები: `chore/derived-*` (ღამის განახლება PR), `release/v*` და თარგმანის ტალღები `docs/i18n-*` და `chore/i18n-*` (`scripts/check/lib/derivedClaimsDiff.mjs`). რიგის პარტიები (`merge_group`, Mergify drafts, `omni-queue/**`) კვლავ არ განიხილება: ისინი აჯამებენ PRs უკვე შეფასებულ კარიბჭეს სათითაოდ.

გასასვლელი კოდები: `0` clean · `1` STRICT დრიფტი (ან რბილი დრიფტი `--strict`) ან მართული მნიშვნელობის დარღვევა PR `2` ინფრასტრუქტურა — კოდის ფაქტების შეგროვება ვერ მოხერხდა (tsx გამოძიების წარუმატებლობა ან დრო ამოიწურა; დროის ლიმიტი არის `OMNIROUTE_FACTS_TIMEOUT_MS`, ნაგულისხმევი 600000 ms) ან CI ბაზაში ვერ გადაიჭრება. გასასვლელი 2 არასოდეს არის დოკუმენტაციის განსხვავება: ხელახლა გაუშვით სამუშაო ან შეასწორეთ გარემო.

- `docs/reference/derived-facts.json` არის ბოლო განახლება გამოყენებული ფაქტების სურათი. ამას მხოლოდ განახლება წერს. README SVG გენერატორები კითხულობენ მას და PR-time ერთეულის ტესტები ადარებენ ჩადენილ დოკუმენტებს და მასში გენერირებულ ფაილებს — არასოდეს ცოცხალ კოდს. კომპლექტის ერთჯერადი პირდაპირი შედარება არის "გამოშვების განახლება ხურავს ციკლს" `tests/unit/check-docs-counts-sync.test.ts` ში: ცოცხალი ფაქტებით, მეხსიერებაში გამოყენებული განახლების გადაწერის გეგმა არ ტოვებს STRICT დრიფტს, ის არ აცნობებს და ხელახალი დაგეგმვა არაფერს ცვლის.

**ორი რეჟიმი (2026-11-13 წლიდან).** PR ფუნქცია ამატებს ან ხელახლა წერს კლავიშებს `en.json` ში (და `bin/cli/locales/en.json`) და არ ეხება სხვა ლოკალს; `check:pr-derived-paths` (სამუშაო `pr-test-policy`, ოჯახი `config/quality/derived-paths/translation.json`) ვერ ახერხებს PR ფუნქციას. სხვა ლოკალები სრულდება თითო გამოშვებაზე ერთხელ `release:refresh-derived` მიერ, რომელიც უწოდებს `syncUiKeys()` `scripts/i18n/sync-ui-keys.mjs` ში (დაამატეთ დაკარგული კლავიშები, ამოიღეთ ისინი, მონიშნეთ ხელახლა დაწერილი ინგლისური თარგმანი `rewrittenSinceRef` ით, თარგმნეთ) ან თარგმანის ტალღით. კარიბჭეები კითხულობენ რეჟიმს `scripts/check/lib/gateMode.mjs` დან: `pr` რეჟიმში (მახასიათებელი PRs, `merge_group`, `omni-queue/**`) გამოშვების რეჟიმის კარიბჭეები ბეჭდავს `SKIP reason=pr-mode` და გამოდის 0; `release` რეჟიმში (გამოშვება PR, უბიძგებს `main`, `workflow_dispatch`, ლოკალური გაშვებები) ისინი მკაცრია როგორც ადრე, ხოლო PR გამოშვებისას diff-aware ღებულობენ `BASE_REF=origin/main`, ასე რომ ისინი აფასებენ ყველა კლავიშს დამატებული ან გადაწერილი ციკლის შესახებ. გადახედეთ ფუნქცია-PR განაჩენს ადგილობრივად `--mode=pr` ით.

PR, რომელიც კვლავ ცვლის ლოკალურ კატალოგებს `pr` რეჟიმში (თარგმანის ტალღა, გამოშვების განახლება, მხოლოდ თარგმანის შესწორება) გამოტოვებული არ არის: `check-key-completeness` განიხილავს თითოეულ კატალოგს, რომელიც შეცვლილია იმავე კატალოგთან შერწყმის ბაზაზე (`scripts/i18n/lib/touched-catalogs.mjs`) და არღვევს კლავიშს, კატალოგი დაკარგულია, გასაღები `en.json` აკლია, რეალური ტექსტი არ არის გადაქცეული ან `__MISSING__:` მნიშვნელობად გადაქცეული. placeholders/tags ინგლისური სიმებიანი PR არ შეხებია. კატალოგში ახალი PR უნდა იყოს მთელი `en.json` გასაღებების ნაკრები. ეს მოიცავს, კატალოგებისთვის, რომელიც ეხება PR, რას დაინახავს თანაფარდობა და CLI-პარიტეტის კარიბჭე.

ლოკალური პარიტეტის ერთეულის ტესტები (`cli-i18n-catalog`, `i18n-pt-br`, `i18n-vi-completeness`, `i18n-placeholder-parity`) მიჰყვება იმავე რეჟიმებს `tests/_helpers/localeParityMode.ts` მეშვეობით: `pr` რეჟიმში ისინი გამოტოვებენ გასაღების პარიტეტის მტკიცებას და გამოშვებას ტოვებენ გასაღებების ადგილის დამცველის პარიტეტის განახლებას, რომელთა ინგლისური შეიცვალა შერწყმის ბაზის შემდეგ (თითოეული კლავიში ვერ კითხულობს ერთეულების ტესტის სამუშაოს ზედაპირულად). ეს დამხმარე არის** მხოლოდ** სანქცირებული რეჟიმი-პირობითი გამოტოვება: `check:test-masking` ითვლის `.skip(` და `{ skip: true }`, მაგრამ არა გამოთვლილ `{ skip: "<reason>" }`, რომელსაც აბრუნებს, ამიტომ `tests/unit/locale-parity-mode.test.ts` ამაგრებს ტესტების სიას, რომლებიც ნებადართულია გამოიყენოს — ერთ-ერთის დამატება არის ამ სიაში განხილული რედაქტირება.

#### `check-ui-value-drift` — შემორჩენილი-თარგმანის კარიბჭე

იჭერს ერთ i18n რეგრესიას, რომელსაც სხვა კარიბჭეები სტრუქტურულად ვერ ხედავენ: ინგლისური მნიშვნელობა ხელახლა იწერება და _previous_ ინგლისურიდან მიღებული თარგმანები უკან რჩება, ამიტომ არაინგლისელი მომხმარებლები აგრძელებენ თავდაჯერებულად ფორმულირებულ, ახლა უკვე არასწორ ასლს.

ეს გაიგზავნება რეალურად. `oauthModal.googleOAuthWarning` ხელახლა დაიწერა, როდესაც Antigravity შესვლის დამხმარე დაეშვა (#5203);** 43 ლოკალიდან 39** ინახავდა ტექსტს, რომელიც ეუბნებოდა ოპერატორებს „დააკოპირონ სრული URL და ჩასვათ ქვემოთ“ — ნაკადი, რომელიც ვერ დაასრულებს ამ პროვაიდერს. ეს შეუმჩნეველი დარჩა #8463, რადგან:

- `sync-ui-keys` ავსებს მხოლოდ გასაღებებს** არყოფნის** , არასოდეს ისეთები, რომლებიც არიან** შემორჩენილი** ;
- `check-ui-keys-coverage` ითვლის საკვანძო _ყოფნას_, ასე რომ, შემორჩენილი თარგმანი გაშუქებულია;
- `check-translation-drift` აკონტროლებს `docs/i18n/<locale>/**.md` დოკუმენტაციას ასახავს — ის არასოდეს კითხულობს `src/i18n/messages/*.json`. ის მუშაობს სამუშაო `docs-sync-strict` ში: საკონსულტაციო PRs ზე, მკაცრი დაჭერისას და ღამის განმავლობაში; მთარგმნელობითი ტალღა განაახლებს სარკეებს და არა PR ფუნქციას.

**Diff-ის ცოდნა, არა საბაზისო მხარდაჭერით.** იგი ადარებს `en.json` შერწყმის ბაზაზე სამუშაო ხესთან; ყველა გასაღებისთვის, რომლის ინგლისური მნიშვნელობა შეიცვალა, ნებისმიერი ლოკალი, რომელსაც ჯერ კიდევ ხელუხლებელი თარგმანი აქვს, მოძველებულია. ეს შეგნებულად** ყინავს ადრე არსებულ ვალს** — a diff-ს არ შეუძლია აჩვენოს, რომელი ძველი ინგლისურიდან მოვიდა დიდი ხნის თარგმანი, ამიტომ კარიბჭე განსჯის მხოლოდ იმას, რასაც ეხება მიმდინარე ცვლილება. ალტერნატივა (თითო კლავიშის ჰეშის საბაზისო ხაზი) ეღირება ~ 600 KB გენერირებული ფაილი, 3 × ყველაზე დიდი არსებული საბაზისო ხაზი, რომელიც იშლება ყოველ i18n PR ზე.

მისი დაკმაყოფილების ორი გზა:

1. განაახლეთ დაზარალებული თარგმანები, ან
2. დააყენეთ ისინი `__MISSING__:<new english>` — გაშვების დროს, შემდეგ ემსახურება შესწორებულ ინგლისურს (`src/i18n/request.ts::deepMergeFallback`, #7258) და საკვანძო რიგებს თარგმანისთვის.

თუ სიმებიანი** მნიშვნელობა** შეიცვალა, ურჩევნია** გასაღების სახელის გადარქმევა** : ახალი გასაღები ვერ დაიმკვიდრებს ძველ თარგმანს. ეს არის #8463 გამოყენებული ნიმუში.

```bash
npm run i18n:check-value-drift          # strict (what CI runs)
npm run i18n:check-value-drift:warn     # report only
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

გამოდის 0-დან `SKIP reason=base-unresolved` ით, როდესაც საბაზისო კატალოგის წაკითხვა შეუძლებელია (არაღრმა კლონი საბაზისო ref-ის გარეშე), ასახავს `check-openapi-breaking`. მხოლოდ გამოშვების რეჟიმი: PR ფუნქცია ხელახლა წერს ინგლისურს და ჩერდება იქ; გამოშვების განახლება აღნიშნავს მის მიერ დატოვებულ თარგმანებს (`node scripts/i18n/sync-ui-keys.mjs --rewritten-since=<ref>`, იგივე `findStaleTranslations`).

`check:codeql-ratchet` კითხულობს** რეპო მდგომარეობა, განახლებული გრაფიკით — არა თითო PR.** `gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` იტყობინება `state: configured`, `schedule: weekly`: GitHub ის ნაგულისხმევი დაყენების სკანირება და არა თითო დაჭერის ანალიზი. შედეგი: PR შერწყმის შემდეგ, რომელიც FIXES სიგნალიზაციას შერწყმდება, თხრილი აგრძელებს ძველი, უფრო მაღალი რაოდენობის კითხვას, სანამ მომდევნო დაგეგმილი სკანირება არ დასრულდება — ასე რომ, ის აცნობებს რეგრესიას ყოველ ღია PR ზე, მათ შორის PR ის საკუთარი შემდგომი მოქმედებების დაფიქსირება, სანამ სკანირება არ დაასრულებს.

ინციდენტი მასში დაშიფრულია: საორკესტრო ტილოს მე-3 ფაზამ თარგმნა მისი თერთმეტი გასაღები 42 ლოკალზე, რომელიც იმ დროს არსებობდა. რამდენიმე საათის შემდეგ ევროკავშირის ენაზე (#13044) აიღო რეპო 51 ლოკალამდე, ხოლო ცხრა ახალმოსულმა (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) არასოდეს მიუღია ისინი. `deepMergeFallback` ანაცვლებს ინგლისურს არარსებული კლავიშით, ამიტომ წარუმატებლობის რეჟიმი იყო თარგმნილი UI ვიდრე ცარიელი UI — რეალური, და ჩუმად კონსტრუქციით.

როგორც მისი ძმა არის** განსხვავებულად შეგნებული** , ინგლისური ენის შერწყმის ბაზაზე სამუშაო ხესთან შედარება, ასე რომ, მანამდე არსებული ხარვეზები რჩება გაყინული და კარიბჭეს არ სჭირდებოდა მიგრაცია ჩასართავად.
