ეს დოკუმენტი OmniRoute-ში CI-ის ხარისხის ყველა ბარიერის ავტორიტეტული ცნობარია.
იგი აღწერს თითოეულ ბარიერს, რას ამოწმებს ის, რომელ CI დავალებაში სრულდება, იყენებს თუ არა
ეტალონის ეტაპობრივი გამკაცრების ან ჩაბარება/ჩავარდნის პოლიტიკას და ბლოკავს თუ არა აგებას, თუ მხოლოდ სარეკომენდაციო ხასიათი აქვს.

მოკლე შეჯამებისა და დაშვებული გამონაკლისების სიის პოლიტიკისთვის იხილეთ სექცია „Quality Gates & Ratchets“
ფაილში `AGENTS.md`. იმავე სისტემის კრიტიკული შეფასების, სიმწიფის კლასიფიკაციისა და კონკრეტულ ხელსაწყოებზე დამოუკიდებელი
გამეორების გეგმისთვის იხილეთ
[ხარისხის ბარიერების სახელმძღვანელო](../ops/QUALITY_GATE_PLAYBOOK.md).

## გეითების ინვენტარი და შესრულების პროფილები

### კანდიდატის დაშვება

CI-ისა და Quality Gates-ის სამუშაო პროცესები თითოეული გასცემს სტაბილურ ვერდიქტს: `Gate / CI` და
`Gate / Quality`. მათი ვერსირებული დაშვების პოლიტიკა ყველა ზემდგომ დავალებას
სავალდებულოდ ან სარეკომენდაციოდ განსაზღვრავს. შესაბამისი სავალდებულო დავალება წარმატებით უნდა
დასრულდეს: არარსებული, გაუქმებული, გამოტოვებული, მოლოდინის რეჟიმში მყოფი და უცნობი შედეგები PASS-ის დადგენას ვერ უზრუნველყოფს. მხოლოდ
დოკუმენტაციასთან ან მხოლოდ კატალოგთან დაკავშირებულმა მართებულმა კლასიფიკაციამ შეიძლება კოდის ნაკადი არარელევანტური გახადოს;
შავი PR მიღებულ კანდიდატად არ ითვლება. `hotfix` ჭდე მტკიცებულების მოთხოვნას არ აუქმებს.

ორივე სამუშაო პროცესი მოიცავს main/release განშტოებებისკენ მიმართულ PR-ებს, `main`-ზე push-ებს, ხელით გაშვებას
და შერწყმის ჯგუფის მოვლენებს. Push, dispatch და merge-group სრულ ნაკრებს უშვებს. `release/**`-ზე
push-ები მათ არ უშვებს (2026-10-18): თითოეულმა ცვლილებამ მატრიცა უკვე გაიარა საკუთარ PR-ში,
ხოლო გაერთიანებული კომბინაცია Release-Green-ის ამოცანაა (`docs/ops/RUNNER_BOX.md` → ჰოსტირებული ნაკადი). Fork-ები
და შერწყმის ჯგუფები იმ დავალებებისთვის, რომლებიც სხვა შემთხვევაში თვითჰოსტირებულ
რანერებს ირჩევენ, ჰოსტირებულ რანერებს იყენებს; გაშვებამდე უნდა დადასტურდეს საკმარისი ჰოსტირებული სიმძლავრე.

ჩვეულებრივი PR სწრაფ ნაკრებს უშვებს. დაშვების პოლიტიკის `full-code` და `full-code-e2e` ნაკადები
(E2E, ინტეგრაცია, პაკეტის არტეფაქტი, Electron-ის smoke-ტესტი, Bun SQLite, ეკოსისტემა
და პროტოკოლის კლიენტები) მხოლოდ Mergify-ის რიგის შავ ვერსიაზე ან სრული გაშვებისას სრულდება:
`gh workflow run ci.yml --ref <branch>`.

თითოეული JSON ქვითარი მიუთითებს checkout-ით მიღებულ SHA-ს, სამუშაო პროცესის გაშვებასა და მცდელობას.
CLI უარყოფს checkout-ისა და მოვლენის SHA-ების შეუსაბამობას. სამუშაო პროცესის ტესტები პოლიტიკის წევრობას
ვერდიქტის დავალების `needs` სიას უკავშირებს, რათა ახალი ან წაშლილი ნაკადი შეუმჩნევლად ვერ გაქრეს.
ქვითრები მოიცავს საკუთარ სამუშაო პროცესს და არა გამოქვეყნებას, განთავსებას ან არსებული
სარეკომენდაციო სკანერის შიდა მოქმედებებს. განშტოების წესებში ორივე შემოწმების სახელის გააქტიურება
ცალკე ადმინისტრაციული ცვლილებაა; ამ დავალებების დამატება თავისთავად განშტოებას არ იცავს.

### შერწყმის რიგი

`queue` ჭდე PR-ს Mergify-ის რიგში აგზავნის (`.mergify.yml`). Mergify ქმნის შავ PR-ს
`mergify/merge-queue/` განშტოებაზე, CI იქ სრულ ნაკრებს უშვებს, ხოლო თავდაპირველი PR მაშინ ერთიანდება,
როდესაც `Gate / CI`, `Gate / Quality` და `Merge integrity (changelog + generated skills)` წარმატებით დასრულდება.

Mergify თავის რიგის შეჯამებას შავი ვერსიის აღწერაში წერს და მისი რედაქტირება სხვა აპებსაც შეუძლიათ.
ასეთ შავ ვერსიაზე `pull_request` `edited` მოვლენა საკუთარ კონკურენტულ ჯგუფს იღებს
(`-queue-edit-<run_id>`), ამიტომ ის შავი ვერსიის რეალურ გაშვებას ვერ გააუქმებს და გეითსა და
მატრიცას გამოტოვებს. მხოლოდ `Merge integrity` აგრძელებს შესრულებას. გამოტოვებულ გეითის დავალებას შემოწმების სხვა სახელი აქვს,
რადგან Mergify გამოტოვებულ `Gate / CI`-ს წარუმატებელ შემოწმებად აღიქვამს და PR-ს რიგიდან იღებს.

რიგიდან ამოღების შემდეგ push ყოველთვის არ აბრუნებს PR-ს რიგში. მასზე დაწერეთ კომენტარი `@mergifyio queue`.

### სტატიკური სკანირების ინვენტარი

npm-ფსევდონიმების ვერსირებული ინვენტარი და სტატიკური სკანირების წევრობა განთავსებულია
`config/quality/gate-manifest.json`-ში. `package.json`-თან მიმართებით სკრიპტების სახელებისა და
ზუსტი ბრძანებების შესამოწმებლად გაუშვით `npm run check:gate-manifest`; დამატებები, წაშლები და
ბრძანებების ცვლილებები წარუმატებელს ხდის როგორც ლოკალურ hook-ს, ისე CI-ში ცვლილებების კლასიფიკაციის დავალებებს.
ფსევდონიმი არ არის სამუშაო პროცესის დავალება, მატრიცის ეგზემპლარი ან ტესტ-ქეისი: ეს რაოდენობები
ურთიერთჩანაცვლებადად არ უნდა იყოს წარმოდგენილი.

არჩეული ფსევდონიმების შესრულების გარეშე სანახავად გამოიყენეთ `npm run quality:scan -- --list` ან `npm run quality:scan:fast -- --list`.
რანერი npm-ის შესვლის წერტილს იძახებს, ამიტომ მისი შესრულების გარემო
(მათ შორის Bun, სადაც ის კონფიგურირებულია) შენარჩუნებულია.
მანიფესტი ამ პროფილების მიღმა არსებულ ფსევდონიმებს ცალკე გამოსაძახებლებად აღრიცხავს, ხოლო
მომსახურების ბრძანებები მხოლოდ წაკითხვის სკანირების პროფილებში აკრძალულია.

ეს პროფილები მხოლოდ სტატიკურ სკანირებას მოიცავს. ისინი არ ადასტურებს პროდუქტის ტესტებს,
დაფარვას, შეფუთვას, გარე შემოწმებებს ან კანდიდატის სრულ მიღებას რელიზისთვის.
სამუშაო პროცესის დაშვება იყენებს დაკავშირებულ `config/quality/admission-policy.json`-სა და
`scripts/quality/admission-verdict.mjs`-ს. რელიზის დამკვირვებლის პროფილები ცალკე რჩება;
მათი შესაბამისი შემოწმებები და ქვითრები დამოუკიდებლად შეამოწმეთ. ქვემოთ მოცემული ტექსტური
ინვენტარი საცნობაროა და არა იმის მტკიცებულება, რომ გეითი რეალურად გაეშვა.

სკრიპტები განთავსებულია `scripts/check/`-ში (პოლიტიკის გეითები) და `scripts/quality/`-ში (რატჩეტის ძრავა).
CI-ის სიმართლის წყაროა `.github/workflows/ci.yml`.

### Release PR-ის სწრაფი გზა (`quality.yml`)

`.github/workflows/quality.yml` ავსებს CI-ს main/release PR-ებზე, `main`-ზე push-ებისას,
dispatch-ისა და შერწყმის ჯგუფებისთვის. PR-ები გზების მიხედვით გაფილტრულ სწრაფ შემოწმებებს იყენებს. მუდმივად
გამორთული დუბლირებული build წაიშალა; რეალური build/package/boot შემოწმებები CI-ში რჩება.
ერთეულის ტესტების ნაკრები და vitest მხოლოდ CI-ში სრულდება (`Unit Tests (N/8)` და `Vitest`).

| დავალება                                         | მასშტაბი                                                                                                                                                | ბლოკირებადი             |

#### დავიწყებული მონათესავე ტესტების ანგარიში

`npm run check:forgotten-sibling-tests` სრულდება, როგორც `Fast Quality Gates`-ის საკონსულტაციო ეტაპი და ხელახლა იყენებს

`changed module/symbol -> static consumer -> candidate sibling test` ჯაჭვებს. Markdown-ის შეჯამება და JSON-ის შედეგი ინახება,
როგორც `forgotten-sibling-tests` workflow-ის არტეფაქტი, ნებისმიერი დამბლოკავი დანერგვის დაწყებამდე კალიბრაციისთვის.

დახურულ მდგომარეობაში წარუმატებლად სრულდება. გამონაკლისები ვერ ჩაახშობს წაშლილ კანდიდატ ტესტს ან diff-ს, რომელიც ამატებს `.skip`/`.todo`-ს;

#### `check-ui-value-drift` — მოძველებული თარგმანის ბარიერი

აფიქსირებს i18n-ის იმ ერთადერთ რეგრესიას, რომელსაც სხვა შემოწმებები სტრუქტურულად ვერ ხედავს: ინგლისური მნიშვნელობა
გადაიწერება, ხოლო _წინა_ ინგლისური ტექსტიდან მიღებული თარგმანები უცვლელი რჩება, ამიტომ
არაინგლისურენოვანი მომხმარებლები კვლავ კითხულობენ დამაჯერებლად ჩამოყალიბებულ, თუმცა უკვე მცდარ ტექსტს.

ეს რეალურად მოხვდა გამოშვებულ ვერსიაში. `oauthModal.googleOAuthWarning` გადაიწერა, როდესაც Antigravity-ის
შესვლის დამხმარე დაემატა (#5203); **43 ლოკალიდან 39-ში** დარჩა ტექსტი, რომელიც ოპერატორებს ეუბნებოდა, „დააკოპირეთ
სრული URL და ჩასვით ქვემოთ“ — პროცესი, რომლის დასრულებაც ამ პროვაიდერისთვის შეუძლებელია. პრობლემა
#8463-მდე შეუმჩნეველი დარჩა, რადგან:

- `sync-ui-keys` მხოლოდ **არარსებულ** გასაღებებს ამატებს და არასოდეს ეხება **მოძველებულ** გასაღებებს;
- `check-ui-keys-coverage` ითვლის გასაღების _არსებობას_, ამიტომ მოძველებული თარგმანი დაფარულად ითვლება;
- `check-translation-drift` აკონტროლებს `docs/i18n/<locale>/**.md` დოკუმენტაციის ასლებს —
  ის არასოდეს კითხულობს `src/i18n/messages/*.json`-ს. 2026-09-ის ხელახალი სინქრონიზაციის შემდეგ
  `docs-sync-strict` დავალებაში ბლოკავს: შეცვალეთ ძირითადი დოკუმენტი → `npm run i18n:run -- --files=<doc>` (სექციის დონეზე, იაფი).

**სხვაობაზე ორიენტირებული და არა საბაზისო მონაცემებზე დაფუძნებული.** ის გაერთიანების საბაზისო წერტილში არსებულ `en.json`-ს
ადარებს სამუშაო ხეს; თითოეული გასაღებისთვის, რომლის ინგლისური მნიშვნელობაც შეიცვალა, ნებისმიერი ლოკალი, რომელშიც
ხელუხლებელი თარგმანი დარჩა, მოძველებულად ითვლება. ეს განზრახ **ყინავს უკვე არსებულ დავალიანებას** — სხვაობით
შეუძლებელია დადგინდეს, ხანგრძლივად არსებული თარგმანი რომელი ძველი ინგლისური ტექსტიდან მომდინარეობს, ამიტომ შემოწმება
აფასებს მხოლოდ იმას, რასაც მიმდინარე ცვლილება ეხება. ალტერნატივა (თითოეული გასაღებისთვის ჰეშების საბაზისო ნაკრები) მოითხოვდა
დაახლოებით 600 KB-იან გენერირებულ ფაილს, რაც უდიდეს არსებულ საბაზისო ფაილზე 3-ჯერ დიდია და ყოველ i18n PR-ზე შეიცვლებოდა.

მისი დაკმაყოფილების ორი გზა არსებობს:

1. განაახლეთ შესაბამისი თარგმანები, ან
2. მიანიჭეთ მათ `__MISSING__:<new english>` — შესრულების დროს სისტემა შემდეგ გასცემს შესწორებულ ინგლისურ ტექსტს
   (`src/i18n/request.ts::deepMergeFallback`, #7258), ხოლო გასაღები თარგმნის რიგში მოხვდება.

მოძველებულ თარგმანს ვერ მემკვიდრეობს. სწორედ ეს მიდგომა გამოიყენა #8463-მა.
