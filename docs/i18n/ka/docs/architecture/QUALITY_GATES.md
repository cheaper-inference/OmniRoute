ეს დოკუმენტი OmniRoute-ში CI-ის ხარისხის ყველა ბარიერის ავტორიტეტული ცნობარია.
იგი აღწერს თითოეულ ბარიერს, რას ამოწმებს ის, რომელ CI დავალებაში სრულდება, იყენებს თუ არა
ეტალონის ეტაპობრივი გამკაცრების ან ჩაბარება/ჩავარდნის პოლიტიკას და ბლოკავს თუ არა აგებას, თუ მხოლოდ სარეკომენდაციო ხასიათი აქვს.

მოკლე შეჯამებისა და დაშვებული გამონაკლისების სიის პოლიტიკისთვის იხილეთ სექცია „Quality Gates & Ratchets“
ფაილში `AGENTS.md`. იმავე სისტემის კრიტიკული შეფასების, სიმწიფის კლასიფიკაციისა და კონკრეტულ ხელსაწყოებზე დამოუკიდებელი
გამეორების გეგმისთვის იხილეთ
[ხარისხის ბარიერების სახელმძღვანელო](../ops/QUALITY_GATE_PLAYBOOK.md).

## გეითების ინვენტარი და შესრულების პროფილები

### კანდიდატის დაშვება

CI-ისა და Quality Gates-ის სამუშაო პროცესები თითოეული გამოსცემს სტაბილურ ვერდიქტს: `Gate / CI` და
`Gate / Quality`. მათი ვერსიონირებული დაშვების პოლიტიკა თითოეულ ზედა დონის დავალებას
სავალდებულოდ ან სარეკომენდაციოდ განსაზღვრავს. შესაბამისი სავალდებულო დავალება წარმატებით უნდა დასრულდეს:
არარსებული, გაუქმებული, გამოტოვებული, მომლოდინე და უცნობი შედეგები PASS-ს ვერ ადასტურებს. მხოლოდ
დოკუმენტაციასთან ან მხოლოდ კატალოგთან დაკავშირებულმა ვალიდურმა კლასიფიკაციამ შეიძლება კოდის ნაკადი არარელევანტური გახადოს;
შავი PR მიღებულ კანდიდატად არ ითვლება. `hotfix` იარლიყი მტკიცებულების მოთხოვნას არ აუქმებს.

ორივე სამუშაო პროცესი მოიცავს main/release ბრენჩებში მიმართულ PR-ებს, `main`-ზე push-ებს, ხელით გაშვებას
და merge-group მოვლენებს. Push, dispatch და merge-group სრულ შერჩევას ასრულებს. `release/**`-ზე
push-ები მათ არ უშვებს (2026-10-18): თითოეულმა ცვლილებამ მატრიცა უკვე გაიარა საკუთარ PR-ზე,
ხოლო გაერთიანებული კომბინაცია Release-Green-ის პასუხისმგებლობაა (`docs/ops/RUNNER_BOX.md` → Hosted ნაკადი). Fork-ები
და merge group-ები იმ დავალებებისთვის ჰოსტირებულ runner-ებს იყენებს, რომლებიც სხვა შემთხვევაში self-hosted
runner-ებს აირჩევდა; დანერგვამდე უნდა დადასტურდეს საკმარისი ჰოსტირებული სიმძლავრე.

თითოეული JSON ქვითარი განსაზღვრავს checkout-ით მიღებულ SHA-ს, სამუშაო პროცესის გაშვებასა და მცდელობას.
CLI უარყოფს checkout/event SHA-ს შეუსაბამობას. სამუშაო პროცესის ტესტები პოლიტიკის წევრობას
ვერდიქტის დავალების `needs` სიას უკავშირებს, რათა ახალი ან წაშლილი ნაკადი შეუმჩნევლად ვერ გაქრეს.
ქვითრები მოიცავს საკუთარ სამუშაო პროცესს და არა გამოქვეყნებას, განთავსებას ან არსებული
სარეკომენდაციო სკანერის შიდა ლოგიკას. ბრენჩის წესებში ორივე შემოწმების სახელის გააქტიურება
ცალკე ადმინისტრაციული ცვლილებაა; ამ დავალებების დამატება თავისთავად ბრენჩს არ იცავს.

### შენარჩუნებული მტკიცებულება მიღების რედიუსერში

`scripts/quality/validate-release-acceptance.mjs` ამუშავებს მიწოდებულ გეგმასა და მის
მანიფესტებს; ის არ ადასტურებს, რომ გეგმა გამოშვების სრულ კონვეიერს მოიცავს.
მის ანგარიშებში პირდაპირ არის მითითებული `releaseAcceptance: false`, მაშინაც კი, როცა გეგმა
`VERIFIED`-ია. `release-acceptance.yml` სამუშაო პროცესი კვლავ ჩრდილოვან ფიქსტურებს იყენებს და არა
რეალურ აგების, შეფუთვის, გაშვების ან დაწინაურების ქვითრებს.

შენარჩუნებული მტკიცებულების დასადასტურებლად CLI მოითხოვს `--evidence-root`-ს. ფაილები იძებნება
როგორც `<evidence-root>/<artifact_id>/<member>` და ჰეშირდება SHA-256-ით. მტკიცებულების გარეშე PASS ჩანაწერი,
არარსებული ან შეცვლილი ფაილი, სახიფათო გზა ან სიმბოლური ბმული
ვერიფიკაციას ხელს უშლის. არარსებული ფაილები ცარიელ, წარმატებულ ჟურნალებს არ უდრის. არსებული
SHA/run/attempt შემოწმებები დამოუკიდებლად რჩება: თანხვედრილი ბაიტები მოძველებულ
ქვითარს ვერ გამოასწორებს. ფაილის მთლიანობა შესრულების ავთენტიკურობის ან არტეფაქტის დაწინაურების მტკიცებულება არ არის.

### UI-ის შესრულების სიმძლავრე

CI UI-ის სრულ ინვენტარს ოთხი `test-vitest` მატრიცული შარდის სახით უშვებს, თითოეულ შარდზე მაქსიმუმ
ორი worker-ითა და არსებული 15-წუთიანი დავალების ვადით. პირველი შარდი ასევე უშვებს
MCP/autoCombo Vitest კომპლექტს. სავალდებულო დავალების შედეგი მატრიცის ყველა ნაწილს მოიცავს; ერთი
შარდის წარუმატებლობა ან გაუქმება კანდიდატის დაშვებას ვერ ადასტურებს.

ღამის დამკვირვებელი UI-ის თითოეული შარდისთვის ინარჩუნებს ზუსტი კანდიდატის ცალკე ქვითარს,
პირველ ქვითარში MCP-ის შესრულების ჩათვლით. ოთხივე ქვითარი, ჟურნალი და თანხვედრილი
შესრულების იდენტიფიკატორი სავალდებულოა. ლოკალური `npm run test:vitest:ui` კვლავ სრულ
კომპლექტს ირჩევს; ერთი `--shard` გაშვება მხოლოდ ნაწილობრივი მტკიცებულებაა.

### Unit coverage-ის შეგროვება

თორმეტი unit შარდი არსებული ტესტების შესრულებისას V8 coverage-ს აგროვებს. წარმატებით დასრულებული
შარდი თავდაპირველი ფაილების შესაკუმშად `scripts/ci/compact-v8-coverage.mjs`-ს უშვებს
Istanbul-ის შუალედური ანგარიშის შექმნის გარეშე. საბოლოო Coverage დავალება თორმეტივე მანიფესტს
კანდიდატის SHA-სთან, runtime-თან, წყაროს root-თან და მონაცემთა ჰეშებთან მიმართებით ამოწმებს, შემდეგ კი c8-ის
რეპორტერებსა და არსებულ coverage ზღვრულ მნიშვნელობებს უშვებს. შეყვანის მონაცემები ინარჩუნებს c8-ის ფაილის სახელების
გლობალურ თანმიმდევრობას; ფუნქციებისა და ბლოკების შერეული coverage-ისთვის თითოეული შარდის წინასწარი გაერთიანება სახიფათოა.
არარსებული, არასწორად ფორმირებული ან შეუთავსებელი შარდები დაშვებას ჩააგდებს.
წარუმატებელი სატესტო შარდები ნედლ დიაგნოსტიკურ coverage-ს ცალკე ინარჩუნებს; ის საბოლოო გაერთიანებაში ვერ შევა.

### სტატიკური სკანირების ინვენტარი

ვერსიონირებული npm-ალიასების ინვენტარი და სტატიკური სკანირების წევრობა განთავსებულია
`config/quality/gate-manifest.json`-ში. სკრიპტების სახელებისა და ზუსტი ბრძანებების
`package.json`-თან შესადარებლად გაუშვით `npm run check:gate-manifest`; დამატებები, წაშლები და
ბრძანებების აცდენა ჩააგდებს როგორც ლოკალურ hook-ს, ისე CI-ში ცვლილებების კლასიფიკაციის დავალებებს.
ალიასი არ არის სამუშაო პროცესის დავალება, მატრიცის ეგზემპლარი ან სატესტო შემთხვევა: ეს რაოდენობები
ურთიერთჩანაცვლებადად არ უნდა იყოს წარმოდგენილი.

არჩეული ალიასების შესრულების გარეშე შესამოწმებლად გამოიყენეთ `npm run quality:scan -- --list` ან
`npm run quality:scan:fast -- --list`. Runner npm entrypoint-ს იძახებს, ამიტომ მისი
runtime (მათ შორის Bun, სადაც კონფიგურირებულია) შენარჩუნებულია.
მანიფესტი ამ პროფილების მიღმა არსებულ ალიასებს ცალკე გამოძახებულად აღრიცხავს, ხოლო
ტექნიკური მომსახურების ბრძანებები მხოლოდ წაკითხვის სკანირების პროფილებში აკრძალულია.

ეს პროფილები მხოლოდ სტატიკურ სკანირებას მოიცავს. ისინი არ ადასტურებს პროდუქტის ტესტებს,
coverage-ს, შეფუთვას, გარე შემოწმებებს ან კანდიდატის გამოშვების სრულ მიღებას.
სამუშაო პროცესის დაშვება იყენებს დაკავშირებულ `config/quality/admission-policy.json`-სა და
`scripts/quality/admission-verdict.mjs`-ს. Release-observer პროფილები განცალკევებული რჩება;
მათი შესაბამისი შემოწმებები და ქვითრები დამოუკიდებლად შეამოწმეთ. სრული დამკვირვებლის სტატიკური
ბრძანებები განსაზღვრულია `config/quality/release-green-static-profile.json`-ში, მათ შორის
`audit:deps`, მუტაციური ტესტების შერჩევა და თარგმანის შემოწმებები. ჩამტვირთველი npm
ბრძანებებს package.json-სა და მოდელირებულ CI/Quality დეკლარაციებთან მიმართებით ამოწმებს; ის აცდენას
უარყოფს, ნაცვლად shell-ის ტოკენების არგუმენტებად შესრულებისა. სავალდებულო სკანერის SKIP/INCOMPLETE გამომავალი
PASS-ს ვერ ადასტურებს. პროფილი თავის გარე გამონაკლისებს აღრიცხავს და არ ანაცვლებს
ჰოსტირებული coverage-ის, სატესტო მატრიცების, პაკეტის ან განთავსების მტკიცებულებებს. ქვემოთ მოცემული ტექსტური ინვენტარი
საცნობაროა და არა იმის მტკიცებულება, რომ გეითი რეალურად გაეშვა.

სკრიპტები განთავსებულია `scripts/check/`-ში (პოლიტიკის გეითები) და `scripts/quality/`-ში (ratchet ძრავა).
CI-ის ჭეშმარიტების წყაროა `.github/workflows/ci.yml`.

#### დავიწყებული sibling-ტესტების ანგარიში

`npm run check:forgotten-sibling-tests` ხელახლა იყენებს test-impact რუკის უკან არსებულ import resolver-ს.
ყოველი შეცვლილი production მოდულისთვის ის წარმოქმნის დეტერმინისტულ
`changed module/symbol -> static consumer -> candidate sibling test` ჯაჭვებს, როდესაც სავარაუდო
ტესტი pull-request-ის diff-ში არ არის. Markdown შეჯამება და JSON შედეგი ინახება
`forgotten-sibling-tests` workflow artifact-ის სახით, ნებისმიერი დამბლოკავი დანერგვის წინ კალიბრაციისთვის.

Barrel re-export-ები და dynamic import-ები მხოლოდ resolution-ის დიაგნოსტიკაა; ისინი არასდროს ქმნის
დამბლოკავ აღმოჩენას. გადახედილი გამონაკლისები ინახება
`config/quality/forgotten-sibling-allowlist.json`-ში. თითოეულ ჩანაწერში მითითებული უნდა იყოს მომხმარებელი და სავარაუდო
ტესტი, მოცემული უნდა იყოს კონკრეტული დასაბუთება და GitHub issue-ის ან pull request-ის ბმული. არასწორად ფორმირებული ჩანაწერები
იწვევს დახურულად დაბლოკვას. გამონაკლისები ვერ უგულებელყოფს წაშლილ სავარაუდო ტესტს ან diff-ს, რომელიც ამატებს `.skip`/`.todo`-ს;
assertion-ების შესუსტება და სხვა სახის შენიღბვა კვლავ დამოუკიდებლად დამბლოკავი
`check:test-masking` gate-ის პასუხისმგებლობაში რჩება.

აფიქსირებს იმ ერთადერთ i18n რეგრესიას, რომელსაც სხვა შემოწმებები სტრუქტურულად ვერ ხედავენ: ინგლისური მნიშვნელობა
ხელახლა იწერება, ხოლო _წინა_ ინგლისური ტექსტიდან მიღებული თარგმანები უცვლელი რჩება, რის გამოც
არაინგლისურენოვანი მომხმარებლები კვლავ თავდაჯერებულად ჩამოყალიბებულ, მაგრამ უკვე არასწორ ტექსტს კითხულობენ.

ეს რეალურ რელიზშიც მოხვდა. `oauthModal.googleOAuthWarning` ხელახლა დაიწერა, როდესაც Antigravity-ის
შესვლის დამხმარე დაემატა (#5203); **43 ლოკალიდან 39-ში** დარჩა ტექსტი, რომელიც ოპერატორებს ეუბნებოდა, რომ „სრული
URL დაეკოპირებინათ და ქვემოთ ჩაესვათ“ — ამ პროვაიდერისთვის ეს პროცესი ვერ დასრულდება. პრობლემა
#8463-მდე შეუმჩნეველი დარჩა, რადგან:

- `sync-ui-keys` მხოლოდ იმ გასაღებებს ავსებს, რომლებიც **არ არსებობს**, და არასოდეს — **მოძველებულებს**;
- `check-ui-keys-coverage` გასაღების _არსებობას_ ითვლის, ამიტომ მოძველებული თარგმანი დაფარულად მიიჩნევა;
- `check-translation-drift` აკონტროლებს `docs/i18n/<locale>/**.md` დოკუმენტაციის ასლებს —

## Ratchet-ის საბაზისო დონე (`quality-baseline.json`)

Ratchet-ის ძრავა (`scripts/quality/check-quality-ratchet.mjs`) კითხულობს `quality-baseline.json`-ს
და ადარებს მას ახლად შეგროვებულ `quality-metrics.json`-ს. ნებისმიერი მეტრიკა, რომელიც
მის epsilon-ზე მეტად გაუარესდება, აგების პროცესს წარუმატებლად დაასრულებს.

ამჟამად თვალყურისდევნებული მეტრიკები:

| მეტრიკა               | მიმართულება | მნიშვნელობა                                          |
| --------------------- | ----------- | ---------------------------------------------------- |
| `eslintWarnings`      | `down`      | ESLint-ის გაფრთხილებების რაოდენობა არ უნდა გაიზარდოს |
| `coverage.statements` | `up`        | ინსტრუქციების დაფარვა არ უნდა შემცირდეს              |
| `coverage.lines`      | `up`        | ხაზების დაფარვა არ უნდა შემცირდეს                    |
| `coverage.functions`  | `up`        | ფუნქციების დაფარვა არ უნდა შემცირდეს                 |
| `coverage.branches`   | `up`        | განშტოებების დაფარვა არ უნდა შემცირდეს               |

რეალური გაუმჯობესების შემდეგ საბაზისო დონის განახლებისთვის:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` ალამი მიმდინარე გაზომილ მნიშვნელობებს `quality-baseline.json`-ში წერს.
ეს ფაილი დააკომიტეთ იმ ცვლილებასთან ერთად, რომელმაც მეტრიკა გააუმჯობესა. PR, რომელიც
მეტრიკას საბაზისო დონის განახლების გარეშე აუმჯობესებს, გამოვლინდება `--require-tighten`-ის მიერ (ფაზა 6A.5,
განხორციელება მოსალოდნელია).

### CodeQL ratchet: განახლების პერიოდულობა და ხელით გაშვება

`check:codeql-ratchet` კითხულობს **რეპოზიტორიის მდგომარეობას, რომელიც გრაფიკის მიხედვით ახლდება — არა თითოეულ PR-ზე.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` აბრუნებს
`state: configured`, `schedule: weekly`: ეს არის GitHub-ის ნაგულისხმევი კონფიგურაციის სკანირება და არა
ყოველი push-ის ანალიზი. შედეგი: გაფრთხილებების გამომასწორებელი PR-ის გაერთიანების შემდეგ ratchet განაგრძობს
ძველი, უფრო მაღალი რაოდენობის კითხვას მომდევნო დაგეგმილი სკანირების გაშვებამდე — ამიტომ ის რეგრესიას აფიქსირებს
ყველა ღია PR-ზე, მათ შორის გამომასწორებელი PR-ის შემდგომ ცვლილებებზეც, სანამ სკანირება მიმდინარე მდგომარეობას არ დაეწევა.

**ხელით განახლება**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ხელახლა უშვებს
ანალიზს და რამდენიმე წუთში თავიდან აქვეყნებს გაფრთხილებებს. ჯერ წაიკითხეთ `.github/workflows/codeql.yml` —
მის სათაურში განმარტებულია, რომ ის მხოლოდ `workflow_dispatch`-ისთვისაა განკუთვნილი, **რადგან კონფლიქტშია
GitHub-ის „ნაგულისხმევ კონფიგურაციასთან“** (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`). `push`/`pull_request`/
`schedule` ტრიგერების აღდგენამდე აუცილებელია **მფლობელის მოქმედება**: Settings → Code security →
CodeQL: Default → Advanced. ამ გადართვის გარეშე არ დაამატოთ `schedule:` ტრიგერი — ის
მხოლოდ წარუმატებელ გაშვებებს გამოიწვევს.

**რაოდენობის შემცირების შემდეგ გაამკაცრეთ საბაზისო დონე** — `node scripts/check/check-codeql-ratchet.mjs
--update` ახალ გაზომილ რაოდენობას წერს `quality-baseline.json`-ში →
`metrics.codeqlAlerts.value`, რათა ratchet-მა ჩუმად არ დაუშვას რეგრესია ძველ ზედა ზღვრამდე.
პრაქტიკული მაგალითი (2026-09-02/03): PR #12502-მა გამოასწორა 7 რეალური გაფრთხილება
(13 → 6 გაზომილი ღია გაფრთხილება); PR #12530-მა გაყინული საბაზისო დონე 11-დან 6-მდე გაამკაცრა შესაბამისობისთვის;
