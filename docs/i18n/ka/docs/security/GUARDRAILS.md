დამცავი მექანიზმები უზრუნველყოფს უსაფრთხოების, პოლიტიკისა და შიგთავსის გარდაქმნების აღსრულებას OmniRoute-სა
და ზემდგომ პროვაიდერებს შორის არსებულ საზღვარზე. თითოეულ დამცავ მექანიზმს შეუძლია შეამოწმოს (და
სურვილისამებრ უარყოს, გარდაქმნას ან ანოტაცია დაუმატოს) მოთხოვნის დატვირთვები (`preCall`) და
ზემდგომი პროვაიდერების პასუხები (`postCall`).

სისტემა **შეცდომისას ღიაა**: თუ შესრულებისას დამცავი მექანიზმი გამონაკლისს გამოიწვევს, რეესტრი
აფიქსირებს შეცდომას და მოთხოვნის წარუმატებლად დასრულების ნაცვლად შემდეგ დამცავ მექანიზმზე
გადადის. ბლოკირება ყოველთვის მკაფიო გადაწყვეტილებაა (`block: true`) და არასდროს — შემთხვევითობა.
ერთადერთი გამონაკლისია გაუქმებული მოთხოვნა: როდესაც გამომძახებლის `signal` გაუქმებულია,
შეცდომის გამომწვევი დამცავი მექანიზმი გამოტოვების ნაცვლად ჰუკის შესრულებას უარყოფს.

ჰუკები **არ** სრულდება ყველა მარშრუტზე ან ყველა პასუხისთვის. სანამ დამცავ მექანიზმს
უსაფრთხოების კონტროლის საშუალებად დაეყრდნობით, წაიკითხეთ
[დაფარვა და შეზღუდვები](#coverage-and-limits).

უფრო დაბალი პრიორიტეტის ნომრები **პირველად** სრულდება.

### ხედვის ხიდი (`visionBridge.ts`) — მოდალობის ხიდი PR-1

GLM 5.3-ის საბაზისო მოდელსა და `glm-5.3-{low,high,max}`-ს რეესტრის/სპეციფიკაციის მკაფიო
`supportsVision:false` მეტამონაცემები აქვს. GLM 5.3 Flash-ის ვარიანტები
კვლავ ხედვის მშობლიურ მოდელებად რჩება. Claude Code-ის `/v1/messages` მარშრუტი
Claude-იდან OpenAI-ზე გარდაქმნამდე შედის საერთო `handleChat`-ის გამოძახებამდელი დამცავი მექანიზმების ჯაჭვში;
ჩადგმული `Read` ხელსაწყოს შედეგის სურათები ამ გარდაქმნამდე უნდა აღიწეროს ან დამუშავდეს,
რადგან გარდაქმნა მათ OpenAI-ის `image_url` შიგთავსად გადააქცევს (#17069).

იჭერს სურათების შემცველ მოთხოვნებს, რომლებიც მიმართულია **ხედვის არმქონე მოდელებისკენ**, და ან
მთლიან მოთხოვნას გადაამისამართებს ხედვის შესაძლებლობის მქონე მოდელზე, ან ზემდგომი
გამოძახების წინ სურათის ნაწილებს ჩაანაცვლებს კონფიგურირებადი ხედვის მოდელის მიერ
შექმნილი ტექსტური აღწერებით. ეს მხოლოდ ტექსტზე მომუშავე პროვაიდერებს საშუალებას აძლევს,
მულტიმოდალური დატვირთვები გამჭვირვალედ დაამუშაონ.

მიმდინარეობა:

1. გამოტოვება, თუ სამიზნე მოდელს უკვე აქვს ხედვის მხარდაჭერა (გარდა იმ შემთხვევისა, როდესაც ის
   იძულებითი ხიდის სიაში `isVisionBridgeForcedModel` გვხვდება).
2. სურათის ნაწილების ამოღება `extractImageParts(messages)`-ის მეშვეობით
   (`visionBridgeHelpers.ts`), რომელიც დელეგირებას უკეთებს **მედიის ერთიან
   დეტექტორს** `detectMediaParts()` ფაილში `open-sse/utils/mediaParts.ts` — ეს არის
   ჭეშმარიტების ერთადერთი წყარო, რომელიც კომბინირებული თავსებადობის ფილტრთან საზიაროა.
   ამოღება ნებადართულ სიაში ზღუდავს იმ ფორმებს, რომელთა თავდაპირველ ადგილას ჩასმაც
   `replaceImageParts`-ს შეუძლია (ამოღება↔ჩანაცვლების კონტრაქტი): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"` და Responses
   API `input_image`. Claude Code-ის `tool_result.content`-სა და Responses-ის ხელსაწყოების
   შედეგებში ჩადგმული შესაბამისი სურათებიც ამოიღება და თავდაპირველ გზებზე ჩანაცვლდება;
   მხოლოდ ინდიკატორის შემცველი ფორმები კომბინირებული ფილტრისთვისაა განკუთვნილი და არ ამოიღება.
   გამოტოვება, თუ არცერთი არ მოიძებნა.
3. შესრულების დროის კონფიგურაციის განსაზღვრა `resolveVisionBridgeRuntimeSettings()`-ის მეშვეობით
   (`src/shared/constants/modalityBridgeDefaults.ts`): უპირატესობა ენიჭება ახალ `modalityBridge*`
   პარამეტრების გასაღებებს; მოძველებული `visionBridge*` გასაღებები რჩება **ერთი ციკლის
   სარეზერვო ვარიანტად** (უკან დაბრუნების ფანჯარა). თუ ხიდი გამორთულია, გამოტოვება ხდება
   მედიის ნებისმიერ შემოვლამდე.
4. რეჟიმის ამომრჩეველი (`modalityBridgeVisionMode`, იხილეთ ქვემოთ მოცემული ცხრილი) განსაზღვრავს
   გადაამისამართებას ან აღწერას. გადაამისამართება აბრუნებს `modifiedPayload`-ს, რომელშიც მხოლოდ `model`
   არის შეცვლილი, ასევე მეტამონაცემებს `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერის გზა: სურათების რაოდენობის შეზღუდვა `maxImages`-ით, ამოცანის შესაბამისი მოთხოვნის შედგენა,
   აღწერის კეშის შემოწმება, ხედვის მოდელის **პარალელურად** გამოძახება
   (`Promise.allSettled`) და მათ ადგილას `[Image N]: <description>` ტექსტური ნაწილების
   ჩასმა. წარუმატებელი აღწერა იძლევა `null`-ს: უცნობი/ხედვის შესაძლებლობის მქონე სამიზნეებისთვის
   დაუმუშავებელი სურათი შენარჩუნდება (#4012), თუმცა **დადასტურებული, მხოლოდ ტექსტზე მომუშავე პირდაპირი
   სამიზნე** ან ხედვის არმქონე კომბინაცია ყველა აღუწერელი სურათისთვის იღებს მკაფიო
   `(unavailable — no vision-capable provider connected)` ტექსტურ ჩამნაცვლებელს,
   მათ შორის ნაწილობრივი წარუმატებლობებისა და აღწერის გამოძახებების ლიმიტს მიღმა დარჩენილი
   სურათებისთვის (#17069). ყველა აღწერის წარუმატებლობის შემთხვევისთვის არსებული კომბინირებული
   სარეზერვო მექანიზმი უცვლელად რჩება (#8430).
6. `modifiedPayload`-ისა და მეტამონაცემების (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) დაბრუნება.

#### დისტანციური სურათის ნორმალიზაცია (self-loop describe/base64 მოთხოვნა)

როდესაც ხიდი თავად იტვირთება **დისტანციურ** სურათს — Anthropic-ის describe თვითგამოძახება და claude-wire-format-ის base64 კონვერტაცია (`ensureBase64ImagesForClaudeWire`), ორივე `fetchRemoteImageAsDataUri()`-ის საშუალებით `visionBridgeHelpers.ts`-ში — მიღებული data URI გადის `normalizeDataUri()`-ით (`open-sse/utils/imageNormalize.ts`) სანამ ხედვის მოდელის მოთხოვნაში ჩაიწება. ზედმეტად დიდი სურათები მცირდება **2048px გრძელ კიდემდე** (რაც შეესაბამება ზომაშეცვლის ლიმიტს, რომელსაც OpenAI/Anthropic უკვე ამოქმედებს სერვერის მხარეს), რაც ამცირებს ატვირთული ბაიტების მოცულობას/დაგვიანებას ხედვის მოდელის ხილვის შეცვლის გარეშე. ზომის შეცვლა იყენებს `sharp`-ს, რომელიც იტვირთება დინამიური იმპორტით: პლატფორმაზე, სადაც მისი ნეიტივ ბინარული ვერ იტვირთება, `normalizeDataUri()` **არასოდეს აგდებს შეცდომას** — ის ბრუნდება ორიგინალური ბაიტების უცვლელად გადაცემაზე, ასე რომ describe/base64-კონვერტაციის გზა ყოველთვის მუშაობს. არა-სურათის ბაიტები (მოთხოვნა, რომელმაც არ დააბრუნა დეკოდირებადი სურათი) ასევე გადაეცემა ხელუხლებლად. ეს ნორმალიზაცია შეზღუდულია იმ სურათებით, რომლებსაც ხიდი იტვირთება საკუთარი თვითგამოძახებისთვის — ის არასოდეს გამოიყენება გამომძახებლის უმუშავებელ passthrough მონაცემებზე, რაც შეესაბამება მხოლოდ-opt-in მუტაციის პრინციპს (მკაცრი წესი #20).

#### პარამეტრების სქემა + მიგრაცია

ახალი `modalityBridge*` გასაღებები Zod-ით ვალიდირდება `updateSettingsSchema`-ში (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` სამეული და `modalityBridgeAudio*` ჯგუფი, რომელსაც Audio Bridge იყენებს. მიგრაცია `141_modality_bridge_settings.sql` აკოპირებს არსებულ მემკვიდრეობით `visionBridge*` მნიშვნელობებს შესაბამის ახალ გასაღებებზე (იდემპოტენტურად, არასოდეს გადაწერს ოპერატორის მიერ დაყენებულ `modalityBridge*` მნიშვნელობას); მემკვიდრეობითი გასაღებები რჩება მიღებული წაკითხვის სარეზერვო ვარიანტად ერთი გამოშვების ციკლის განმავლობაში.

#### გამჭვირვალობის ჰედერი + სტატისტიკა

Describe-ით გარდაქმნილი პასუხები ატარებენ ჰედერს `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (აგებული `buildModalityBridgeHeader()`-ით `modalityBridge/bridgeStats.ts`-ში, დასმული `withModalityBridgeHeader()`-ით `src/sse/handlers/chatHelpers.ts`-ში). გადამისამართებული მოთხოვნები ჰედერს **არ** იღებენ — მონაცემები ხელუხლებელი დარჩა და მოდელის შეცვლა უკვე ხილულია პასუხის სხეულის `model` ველში.

`GET /api/modality-bridge/stats` (სამართავი ავთენტიკაცია, იგივე დონით, როგორც `GET /api/settings`) აბრუნებს მეხსიერებაში არსებულ თითოეული მოდალობის მრიცხველებს `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` `vision`, `audio` და `video`-სთვის. `averageLatencyMs` გამყოფად იყენებს `latencySamples`-ს და არა ყველა მცდელობას; ოპერაცია დროის გაზომვის გარეშე არ ქმნის ნულოვანი მილიწამის ნიმუშს. `bridged` რჩება უკუთავსებადი ფსევდონიმად წარმატებული კონვერტაციებისთვის; წარუმატებელი მცდელობები მას არ ზრდიან. მრიცხველები პროცესის გადატვირთვისას ნულდება განზრახ (ტელემეტრიაა, არა აღრიცხვა).

#### დაფის კონფიგურაცია

სპეციალური დაფის გვერდია `/dashboard/settings/modality-bridge`. მისი URL-ით მისამართიანი `Vision`, `Audio` და `Video` ჩანართები ინახავს query პარამეტრებს `tab` მნიშვნელობის გადართვისას. Vision ჩანართი გვაძლევს ჩართვის მართვას, რეჟიმს, მოდელის არჩევას (მათ შორის ავტომატურ ნაგულისხმევს), task-aware პრომპტინგს, გაფართოებული timeout/სურათების/აღწერის-სიგრძის/ქეშის ლიმიტებს, runtime მრიცხველებს და დაცულ სანიმუშო მოთხოვნას. Audio ჩანართიც ცოცხალია: ის გვაძლევს ჩართვას, მხოლოდ-STT მოდელის ამომრჩევს Auto-სთან ერთად, timeout/მაქს. კლიპის ლიმიტებს, აუდიო მრიცხველებს და `input_audio` სანიმუშო ტესტს. Video ჩანართი ფუნქციონალურია: ის ანგარიშობს FFmpeg/ffprobe-ის runtime მდგომარეობას — ერთ-ერთს ოთხი ექსპლიციტური UI მდგომარეობიდან (`unknown` სანამ შემოწმება მიმდინარეობს ან ვერ დასრულდა, `restricted` არა-loopback დაფის ჰოსტზე, სადაც შემოწმება კლიენტის მხარეს გამოიტოვება, `unavailable` როცა შემოწმება მოხდა და დადასტურდა, რომ არ არის ხელმისაწვდომი, ან `available` FFmpeg/ffprobe-ის ვერსიებით) — ინახავს ჩართვა/მოდელი/კადრი/ვიდეო/timeout ლიმიტებს, აფილტრავს მოდელის ამომრჩევს ხედვის შესაძლებლობის მქონე მოდელებზე და აჩვენებს ვიდეო მრიცხველებს.

ყოფილი Vision Bridge ბარათი AI პარამეტრებში ახლა თავსებადობის ბმულია ახალ გვერდზე; ის აღარ ფლობს ფორმის მეორე ასლს. Media Providers ასევე აკავშირებს Image-to-Text და Speech-to-Text სამუშაო ნაკადებს შესაბამის Modality Bridge ჩანართებთან, არსებული Speech-to-Text playground-ის ამოღების გარეშე.

**Self-loop დაშვების გვერდის ავლა:** როდესაც describe გამოძახება მარშრუტიზირდება OmniRoute-ის საკუთარი `/v1` self-loop-ით (არასტანდარტული პროვაიდერის მოდელი), ქვემოთხოვნა აგზავნის `x-omniroute-admission-bypass: internal` ჰედერს და ავთენტიფიცირდება განსაზღვრული self-loop რწმუნებათა სიგნალით — ლოკალური `sk_omniroute` სენტინელით ლოკალურ რეჟიმში ან ოპერატორის მიერ კონფიგურირებული `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env გასაღებით (#1350), ასე რომ `REQUIRE_API_KEY=true` განლაგებებს მაინც შეუძლიათ describe გამოძახების გაშვება. გვერდის ავლა მხოლოდ ამ ზუსტი რწმუნებათა სიგნალებისთვის მუშაობს, ამიტომ გარე კლიენტებს ვერ შეუძლიათ ჰედერის გამოყენება დაშვების გამოსატოვებლად.

მემკვიდრეობითი ნაგულისხმევი მნიშვნელობები მდებარეობს `src/shared/constants/visionBridgeDefaults.ts`-ში; ახალი რეჟიმის/task-aware/ქეშის ნაგულისხმევი მნიშვნელობები და პარამეტრების რეზოლვერი მდებარეობს `src/shared/constants/modalityBridgeDefaults.ts`-ში. guardrail-ი ამჟღავნებს `deps` კონსტრუქტორის პარამეტრს, რათა ტესტებმა შეძლონ ყალბი `getSettings` და `callVisionModel` იმპლემენტაციების ჩანერგვა.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ხვეულავს აუდიოს შემცველ ჩატის მოთხოვნებს, სანამ ისინი მიწვდებიან მიზანს, რომელიც ცნობილად არ იღებს აუდიო შეყვანას. ის არასოდეს გადამისამართებს ჩატის მოთხოვნას: აუდიო ნაწილები ტრანსკრიბირდება არსებული OpenAI-თან თავსებადი multipart ბოლო-წერტილით და არჩეული ჩატის მოდელი განაგრძობს ტექსტური ტრანსკრიპტებით.

ნაკადი:

1. `supportsAudio` განსაზღვრეთ `getResolvedModelCapabilities()`-ის მეშვეობით. უპირატესობა
   ენიჭება პროვაიდერების რეესტრში ცხადად მითითებულ მეტამონაცემებს, შემდეგ — მოდელის
   სტატიკურ მეტამონაცემებს, ბოლოს კი — სინქრონიზებულ `modalities_input`-ს. თუ
   გამოცხადებულ შეყვანის სიაში `audio` არ არის, მნიშვნელობაა `false`; თუ
   შესაძლებლობის დამადასტურებელი მონაცემები საერთოდ არ არსებობს, მნიშვნელობაა
   `null`. როგორც `false`, ისე `null` ააქტიურებს კონსერვატიულ ხიდს, ხოლო `true`
   მას გვერდს უვლის.
2. განსაზღვრეთ `modalityBridgeAudio*` პარამეტრები და თითოეული შეტყობინებიდან
   გაზიარებული `detectMediaParts()` დეტექტორის მეშვეობით ამოიღეთ ჩასანაცვლებელი
   ზედა დონის აუდიონაწილები. მხარდაჭერილი გადაცემის ფორმატებია OpenAI-ის
   `input_audio`, `audio_url` და `source.media_type: "audio/*"`. ჩადგმული აუდიო
   მარშრუტიზაციისთვის აღმოჩნდება, თუმცა ჩანაცვლების გზით არ წაიშლება. სამუშაოს
   მოცულობა შეზღუდულია `modalityBridgeAudioMaxClips`-ით; შემდგომი ნაწილები
   უცვლელი რჩება.
3. გამოიყენეთ კონფიგურირებული `provider/model`, ან მიეცით
   `selectAudioBridgeModel()`-ს საშუალება, სტაბილური კატალოგის თანმიმდევრობით
   გაიაროს `AUDIO_TRANSCRIPTION_PROVIDERS` და აირჩიოს პირველი მოდელი, რომლისთვისაც
   ხელმისაწვდომია გამოსადეგი, აქტიური პროვაიდერის ავტორიზაციის მონაცემები.
4. `callAudioTranscription()` base64/data-URI აუდიოს გარდაქმნის მრავალნაწილიან
   `file`-ად, ან დისტანციურ `audio_url`-ს ჩამოტვირთავს მხოლოდ საჯარო მისამართებზე
   დაშვების გამავალი დაცვის მეშვეობით, DNS-ის ფიქსაციითა და 25 MB ლიმიტით. შემდეგ
   ის ფაილსა და არჩეულ მოდელს POST მოთხოვნით აგზავნის ლოკალურ
   `/v1/audio/transcriptions` თვითმარყუჟში, `resolveSelfLoopBearer()`-ით
   ავტორიზაციის გამოყენებით. ტრანსკრიფციის არსებული მარშრუტი ასრულებს
   ავტორიზაციის მონაცემების ჩვეულებრივ მოძიებას, დაყოვნებისა და სიხშირის ლიმიტის
   დამუშავებას და პროვაიდერთან გადამისამართებას.
5. წარმატებული გამოძახებები შესაბამის ნაწილებს ანაცვლებს
   `[Audio N]: <transcript>`-ით. გამოძახებები სრულდება `Promise.allSettled`-ით:
   ცალკეული შეცდომის შემთხვევაში თავდაპირველი აუდიონაწილი შენარჩუნდება (#4012
   კონტრაქტი). თუ ყველა გამოძახება წარუმატებელია და სამიზნისთვის დადასტურებულია
   `supportsAudio === false`, ნაწილები გარდაიქმნება
   `[Audio N]: (unavailable — no STT provider connected)`-ად (#8430 კონტრაქტი).
   უცნობი სამიზნის (`null`) შემთხვევაში, თუ ყველა გამოძახება წარუმატებელია,
   ნაწილები უცვლელი რჩება. დადასტურებულად მხოლოდ ტექსტურ სამიზნეს, რომლისთვისაც
   გამოსადეგი STT ავტორიზაციის მონაცემები არ არსებობს, ქსელური გამოძახების გარეშე
   მიეწოდება იგივე ცხადი ჩამნაცვლებელი ტექსტი.

წარმატებული ტრანსკრიფციები იყენებს პროცესის მასშტაბით მოქმედ Modality Bridge-ის
LRU/TTL კეშს. გასაღები აერთიანებს აუდიოს ბმულს, სტაბილურ
`audio-transcription` ოპერაციის ჭდეს და არჩეულ STT მოდელს; შეცდომები არასოდეს
კეშირდება. აუდიოს დამუშავების მცდელობები აახლებს გაზიარებულ `bridged`,
`cacheHits`, `failures` და `lastUsedAt` მრიცხველებს. გარდაქმნილ პასუხებს ახლავს
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; უცვლელად
გატარებულ მოთხოვნებს Audio Bridge-ის სეგმენტი არ ემატება.

შესრულების გარემოს პარამეტრები ინახება DB-ში და მოწმდება Zod-ით:

| გასაღები                      | ნაგულისხმევი | დიაპაზონი            |
| ----------------------------- | ------------ | -------------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —                    |
| `modalityBridgeAudioModel`    | `""`         | ავტომატური ან STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000          |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10                 |

გაზიარებული კეში კვლავ იმართება `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` და `modalityBridgeCacheMaxEntries`
პარამეტრებით.

### ვიდეო ხიდი (`videoBridge.ts`, `videoBridgePipeline.ts`)

წყვეტს უმაღლესი დონის ვიდეო ნაწილებს Chat Completions `messages` ში და Responses API `input` მანამ, სანამ სამიზნე გამოიძახება ცნობილი მშობლიური ვიდეო მხარდაჭერის გარეშე. მხარდაჭერილი ფორმებია `input_video`, `video_url`, `video_source`, HTTPS URLs და `data:video/*;base64,...` მონაცემები URIs. მარტივი ფაილის სახელები ტექსტში არ განიხილება, როგორც ვიდეო.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ფლობს მოთხოვნის გავლას, capability/policy შემოწმებას, თითო მოთხოვნის აგრეგაციას და პასუხების დატვირთვას. თითო ვიდეოზე მუშაობა — შეძენა, მთლიანი შედეგის ქეში, რომელიც აღწერს კადრების თანმიმდევრობას (რომელიც აერთიანებს აბონენტის მიერ გამოცხადებულ ნებისმიერ აუდიო ტრანსკრიპტს) და თითო მცდელობისას metrics/abort/cleanup — იმალება `processVideoPart` ში `videoBridgePipeline.ts` ში, გამოძახებული ერთხელ თითო ვიდეო ნაწილზე `preCall` ს მარყუჟის შიგნით. ეს მოდული ასევე განსაზღვრავს პორტის გამოკვეთილ საზღვრებს `VideoMediaBrokerPort` (ბაიტების მოპოვება და ნიმუშის ჩარჩოების ამოღება), `VideoAudioTranscriptionPort` (აბონენტის მიერ გამოცხადებული აუდიო ტრანსკრიპტის შერწყმა ნიმუშების წარწერებთან) და `VideoDrilldownPort` (მოძველებული ნედლეულის მაღაზიის ფორმა). წარმოების STT და ჩარჩოს შეკავება შედგება აღწერის პორტის გარშემო `createVideoSttAdapter` და `createVideoDrilldownAdapter` მეშვეობით; ეს უკანასკნელი იყენებს საერთო გაუმჭვირვალე სახელურის სასიცოცხლო ციკლს.

საჯარო `/v1` მოთხოვნის გზა არასოდეს ახდენს ქვეპროცესის იმპორტს ან გამოძახებას. დისტანციური ვიდეოები ჩამოტვირთულია 50 MiB ლიმიტის ქვეშ; inline base64 ვიდეოებს აქვს კონსერვატიული 36 MiB დეკოდირებული თითო ვიდეო ქუდი, ასე რომ model/messages/framing კონვერტი შეიძლება დარჩეს საჯარო JSON მოთხოვნის დაშვების ლიმიტის შიგნით 50 MiB. ინლაინ სიგრძისა და გაშიფრული ზომის შეფასებები მოწმდება განაწილებამდე. HTTPS საჭიროა თავდაპირველ დისტანციურ URL ზე და ყველა გადამისამართებაზე, არსებული მხოლოდ საჯარო გამავალი მცველის გამოყენებით DNS ჩამაგრებით. ბაიტები შემდეგ კვეთენ `POST /api/modality-bridge/video/extract` ბროკერის ზუსტ შიდა საზღვარს. ეს მარშრუტი არის როგორც `LOCAL_ONLY`, ასევე `SPAWN_CAPABLE`, იღებს მხოლოდ თითო პროცესის ავთენტიფიკაციას, სანდო მარყუჟის დაბრუნება მოთხოვნას და არასოდეს იღებს URL, ფაილური სისტემის გზას, შესრულებად ან არგუმენტების სიას. API სხეულის ზომის მილსადენი და დამმუშავებლის დამატებითი სხეულის წამკითხველი დამოუკიდებლად ახორციელებენ 50 MiB ბროკერის შეყვანის თავსახურს. მისი შემოსაზღვრული რიგი აწარმოებს თითო მოპოვებას ერთდროულად, იძლევა ოთხი მოლოდინის სამუშაოს და აფარებს მოლოდინის რეჟიმში შეყვანას 100 MiB.

ბროკერის შიგნით `ffprobe` კითხულობს კერძო ლოკალურ ფაილს; ფიქსირებული ფორმატის დასაშვები სია გამორიცხავს დასაკრავი სიის და მანიფესტის ფორმატებს. MOV ოჯახის დაშვებული კონტეინერებისთვის, MOV მონაცემთა გარე მითითებები ნაგულისხმევად გათიშული რჩება და ფიქსირებული ბრძანება არ ეთანხმება მათ. ორივე `ffprobe` და `ffmpeg` იყენებენ `file` -only პროტოკოლის თეთრ სიას, ერთ თემას, ფიქსირებულ არგუმენტებს, ჭურვის გარეშე და `PATH` დან გადაწყვეტილ შესრულებადებს. მიმაგრებული სურათის საფარის ნაკადები არ არის დაკვრადი კანდიდატები. ყველა დაკვრადი ნაკადი უნდა აკმაყოფილებდეს ლიმიტებს და აშკარად ნაგულისხმევი ნაკადი სასურველია დეტერმინისტული ყველაზე დაბალი ინდექსის სარეზერვო სტრიმინგის წინ. ვიდეოები შეზღუდულია 600 წამით, 8192 პიქსელი თითო განზომილებაში და 33554432 წყაროს პიქსელი. FFmpeg ირჩევს 1–16 შუა წერტილის JPEG ჩარჩოებს, ამცირებს გრძელ კიდეს მაქსიმუმ 1024 პიქსელამდე, მცირე შენატანების გაზრდის გარეშე და არასოდეს იღებს URL. სინჯის აღება ნაგულისხმევად არის `uniform`. არასავალდებულო `scene_aware` და ექსპერიმენტული `segment_aware` პოლიტიკა ახორციელებს ერთ დამატებით ფიქსირებულ FFmpeg გადასასვლელს უკვე დადასტურებულ ლოკალურ ნაკადზე, ირჩევს შეზღუდულ `showinfo` სცენის დროის ნიშნულებს და დეტერმინისტულად ბრუნდება იმავე ერთგვაროვან შუა წერტილებზე დეტექტორის გაუმართაობის, დროის ამოწურვის, არასწორი გამომავალი ან ცარიელი კანდიდატის ნაკრების შემთხვევაში. სეგმენტური რეჟიმი ანაწილებს შუა წერტილის ნიმუშებს სცენის დამოწმებული ინტერვალების პროპორციულად; სეგმენტური მტკიცებულებები და სარეზერვო ქცევა დეტალურად არის აღწერილი ქვემოთ. მყარი 16 კადრის ქუდი გამოიყენება შერჩევის შემდეგ ყველა პოლიტიკაში. როდესაც სცენაზე გათვითცნობიერებულ მოთხოვნას აქვს მხოლოდ ერთი კადრის ბიუჯეტი, ის იყენებს აქტიური სრული ვიდეოს ან ფოკუსის ფანჯრის ერთგვაროვან შუა წერტილს და აცნობებს `policyEffective: uniform`: ერთი შერჩეული სცენის ჩარჩო ვერ შეინარჩუნებს ორივე დროებით ბოლოს. აბონენტს შეუძლია სურვილისამებრ უზრუნველყოს სასრული ფოკუსის ფანჯარა (`start`/`end` წამი); საზღვრები მიმაგრებულია მედიის ხანგრძლივობაზე, შებრუნებული ან არასასრული ფანჯრები უარყოფილია და ყველა შერჩევის პოლიტიკა ხორციელდება მხოლოდ ნორმალიზებული ინტერვალის შიგნით. შედეგად მიღებული ფანჯარა შედის სინჯის მეტამონაცემებში და არასანდო აღწერილობის პრეფიქსში, ასე რომ, ქვედა დინების მოდელებს შეუძლიათ განასხვავონ ორიენტირებული ამონაწერი სრული ვადებიდან.

სემანტიკური წარწერის ფოკუსი არის ცალკე, აშკარა პარამეტრი. ნაგულისხმევი `full` ანალიზის რეჟიმი ინახავს ჩარჩოს არსებულ მოთხოვნას და არასოდეს გადააგზავნის მოთხოვნის ტექსტს წარწერის მოდელზე. `focused` რეჟიმში, ხიდი კითხულობს მხოლოდ უახლეს არა ცარიელი მომხმარებლის მიერ ავტორიზებულ `text`/`input_text` ს იმავე Chat-ის ან Responses კონტეინერიდან, ახდენს მის ნორმალიზებას NFC მდე, ანგრევს საკონტროლო სიმბოლოებს და თეთრ სივრცეს და ზღუდავს მას 500 Unicode კოდის წერტილამდე. ცარიელი შედეგი ბრუნდება ზუსტად `full` მოთხოვნაზე. გამოსაყენებელი მინიშნება არის სერიული, როგორც JSON გამოყოფილი არასანდო მომხმარებლის კონტექსტის ბლოკში და შეიძლება პრიორიტეტული იყოს მხოლოდ დაკვირვებადი დეტალები; მას არ შეუძლია უგულებელყოს ცალკეული გაფრთხილება მედიაში ხილული ან მოსმენილი ინსტრუქციების შესახებ. ტექსტური ფოკუსი არასოდეს არ იძლევა დასკვნებს `start`/`end` ან არ ცვლის დროებით სემპლერს.

#### FU-07 სტრუქტურული სეგმენტის მტკიცებულება

`segment_aware` იყენებს ერთ შემოსაზღვრულ წინასწარ ანალიზს უკვე დადასტურებულ ადგილობრივ ვიდეო ნაკადზე. ფიქსირებული ფილტრის ჯაჭვი ჯერ მასშტაბირდება მაქსიმუმ 320 პიქსელამდე, ამოიცნობს სცენის ცვლილებებს და გაყინულ ინტერვალებს, შემდეგ იღებენ ნიმუშებს 1 კადრი წამში დაბინდვის, საშუალო ლუმასა და spatial/temporal ინფორმაციისთვის. საშვი შემოიფარგლება 600 სტრუქტურული ნიმუშით, ერთი FFmpeg/filter ძაფით, იგივე `file` -only პროტოკოლისა და კონტეინერების დაშვების სიებით, 1 MiB პროცესის გამომავალი შეკვრით და მაქსიმუმ 30 წამით ბროკერის საერთო abort/deadline. ში ის არასოდეს იღებს ბრძანებას, ფილტრს, გზას ან URL მოთხოვნიდან.

სტრუქტურული მნიშვნელობები არის დეტერმინისტული შერჩევის მტკიცებულება და არა სემანტიკური ვიდეო გაგება. ისინი არ ადგენენ საგნებს, მოქმედებებს, წარწერებს, მეტყველებას ან მომხმარებლის განზრახვას. სცენისა და ყინვის საზღვრები ქმნიან სეგმენტებს; გაყინვის გაშუქება, დაბინდვა, ექსპოზიცია, სივრცითი დეტალები და დროითი ცვლილება გავლენას ახდენს მხოლოდ არსებული 1-16 ჩარჩო ბიუჯეტის განაწილებაზე. სრულად გაყინული სეგმენტი იფარება ერთ ჩარჩოზე, ხოლო არაგაყინული სეგმენტები კონკურენციას უწევენ დარჩენილი ბიუჯეტისთვის. როდესაც საზღვრები აღემატება ჩარჩოებს, ერთგვაროვანი ქრონოლოგიის დაფარვა შენარჩუნებულია, ასე რომ სწრაფი ადრეული ჭრა ვერ მალავს გრძელ მიმავალი სეგმენტს. სცენის საზღვრები გაყინვის საზღვრის 1-წამიანი ანალიზის გარჩევადობის ფარგლებში გაერთიანებულია.

ფილტრების გამოტოვება, malformed/empty მტკიცებულება, დეტექტორის შეცდომა ან შეზღუდული წინასწარი ანალიზის დრო ვერ იხსნება ზუსტად ერთიანი შუა წერტილის პოლიტიკაში. აბონენტის შეწყვეტის ან ბროკერის ვადა არ იხსნება: ის წყვეტს ფრენის დროს ქვეპროცესს, ხელს უშლის მოგვიანებით ჩარჩოს ამოღებას და კერძო დროებითი ხე ამოღებულია `finally` ში.

`scripts/perf/video-bridge-fu07-eval.ts` წარმოქმნის დეტერმინისტულ რეალურ FFmpeg ინსტრუმენტებს წარწერის შემდგომი ზარის დაზოგვისთვის, ბიუჯეტის მკვრივი მოძრაობის გამოყოფისთვის, blur/exposure/SI-TI მტკიცებულებების, სწრაფი ჭრების გრძელი კუდით და თანდათანობით ქრებოდა ცრუ დადებითი. ის იწერს წინასწარი ანალიზის კედლის დროს და, სადაც `/usr/bin/time` ხელმისაწვდომია, ბავშვის CPU და პიკ RSS. მისი ხარისხის შემოწმებები მხოლოდ სტრუქტურული ორაკულებია. წარწერის მოდელის რეალური ხარისხი რჩება `HOLD` რადგან ამ აღკაზმულობას არ აქვს ავტორიზებული საბოლოო წერტილი ან გაყინული მოსამართლე. ფულადი დანაზოგი ასევე რჩება `HOLD`, თუ `--caption-cost-per-call-usd` არ აწვდის აშკარა პოზიტიურ შეფასებას თითო ზარზე; სკრიპტი არასოდეს აყალიბებს არცერთ შედეგს.

თითოეული ფრეიმი შემოიფარგლება 4 MiB, ყველა ნედლი ფრეიმი ერთად 23 MiB, ხოლო სერიული ბროკერის პასუხი 32 MiB. პირადი დროებითი დირექტორია ამოღებულია `finally` ში. OmniRoute არ აერთიანებს FFmpeg და არ იღებს მორგებულ შესრულებად ბილიკს. სუბტიტრების წარწერამდე ხიდი იყენებს კონსერვატიულ ვიზუალურ დედუპლიკაციის უღელტეხილს: თითოეული JPEG მცირდება 16 × 16 ნაცრისფერი ფერის ბუფერამდე და შედარებულია მხოლოდ შენარჩუნებულ ბოლო ჩარჩოსთან. ერთი ჩარჩოს ზემოთ მოთხოვნილი სუბტიტრების ბიუჯეტისთვის, მოპოვება უზრუნველყოფს შემოსაზღვრულ კანდიდატთა აუზს ორჯერ მეტი ბიუჯეტით და არა უმეტეს 16 ფრეიმის. მოთხოვნილი ლიმიტი გამოიყენება მხოლოდ დუბლირების შემდეგ, პირველი და საბოლოო შერჩეული კანდიდატები შენარჩუნებულია საბოლოო შეთხელების დროს, როდესაც ბიუჯეტი მინიმუმ ორია. ვერსიული `grayscale-16x16-mean-cells-v2` პოლიტიკა იყენებს საშუალო ლუმა დელტას უფრო დიდს და ესკიზების უჯრედების თანაფარდობას, რომელთა ნორმალიზებული დელტა არის მინიმუმ 0.05. დუბლიკატის ზღვარი არის მუდმივი 0.04, რომელიც არჩეულია პროგნოზირებადობისთვის და არა როგორც გაშვების დროის პარამეტრი. ეს მეორადი მაღალი კონტრასტული სიგნალი ინარჩუნებს მცირე მოძრაობას და ხილულ ტექსტურ ცვლილებებს, რომელთა დამალვაც მხოლოდ საშუალო შედარებას შეუძლია. შედარების ან დეკოდერის შეცდომები ვერ იხსნება და ინარჩუნებს დაფარვას. გამომავალი მეტამონაცემები გამოყოფს ამოღებულ კანდიდატებს, წარმატებით გამოყენებულ კადრებს და ამოღებულ ვიზუალურ დუბლიკატებს.

ცალსახად მონიშნულმა ვიდეო ნაწილმა შეიძლება მოითხოვოს საკონტაქტო ფურცლის დროით შტამპი. ხიდი აშენებს მაქსიმუმ 4-სვეტიან, 16-ჩარჩოან JPEG ბადეს. ყოველი 512 პიქსელიანი უჯრედი წვავს თავის წყაროს დროის ანაბეჭდს მაღალი კონტრასტის ქვედა ზოლში, ხოლო იგივე დროის ანაბეჭდები რჩება ტექსტურ მეტამონაცემებში ქვედა დინებაში ასოციაციისა და აუდიტისთვის. სრული JPEG რჩება 32 MiB ზე. თუ `sharp` არ შეუძლია ბადის გაშიფვრა ან შედგენა, ხიდი უბრუნდება ცალკეულ JPEG ჩარჩოებს; კლიენტის შეწყვეტა კვლავ ვრცელდება ფურცლის ოპერაციით.

სარეკლამო მტკიცებულება მიზანმიმართულად განცალკევებულია სინთეზური შემადგენლობის მიკრობენჩმარკისგან. `scripts/perf/video-bridge-contact-sheet-eval.ts` განსაზღვრავს სქემის ვერსიით A/B აღკაზმულობას რეალური OpenAI-თან თავსებადი ხედვის მოდელებისთვის. ის ზომავს პროვაიდერის მიერ მოხსენებულ ჟეტონებს, კედლის ბოლოდან ბოლომდე შეყოვნებას (ფურცლის შემადგენლობის ჩათვლით), მოდელის ზარების რაოდენობას და მანიფესტში განსაზღვრულ ფაქტების შენახვას. დაუმუშავებელი მოდელის პასუხები არ იწერება ანგარიშში; შენარჩუნებულია მხოლოდ SHA-256 დაიჯესტები და შესაბამისი ფაქტი IDs. აღკაზმულობა არ აკეთებს ქსელის ან ფასიანი მოდელის ზარს, თუ `--execute-real` არ არის გადაცემული და `--model`, `OMNIROUTE_BASE_URL` და `OMNIROUTE_API_KEY` არ არის კონფიგურირებული. ამ აშკარა რეალური გაშვების გარეშე, მისი მანქანით წაკითხვადი ვერდიქტი რჩება `HOLD`; მხოლოდ სინთეზური payload/call-count გაზომვები არ არის ხელშეწყობის მტკიცებულება.

აბონენტებს შეუძლიათ დაურთონ არჩევითი `transcript.cues` მასივი მხარდაჭერილ ვიდეო ნაწილზე, როცა უკვე ფლობენ გასწორებულ ტექსტს. თითოეულ ნიშანს უნდა ჰქონდეს `text`, სასრული `start`/`end` ინტერვალი შემოწმებული ხანგრძლივობის შიგნით და თეთრ სიაში შეტანილი `source` (`client`, `embedded` ან `audio-bridge`); `confidence` ნაგულისხმევია `1` და უნდა დარჩეს `0` და `1` შორის. ზუსტი დუბლიკატი მინიშნებები იშლება. OmniRoute არასოდეს იწყებს ტრანსკრიფციას ამ მეტამონაცემებიდან: დადასტურებული მინიშნებები კოპირდება აღწერილ შედეგში წყაროსთან, ნდობითა და ინტერვალით და გადაიცემა როგორც არასანდო დაკვირვებები კადრის წარწერებთან ერთად. არასწორი, დიაპაზონის გარეთ ან წარმოშობის გარეშე ტექსტი უარყოფილია, ვიდრე შერეული სუბტიტრების ნაკადში. ორივე მოთხოვნის სხეულის ტრანსკრიპტის არხი ახდენს `client` მიწოდებული წარმოშობის ნორმალიზებას, მათ შორის თვითდამტკიცებული `embedded` ან `audio-bridge` ლეიბლები. მხოლოდ სერვერის მფლობელობაში მყოფ ადაპტერს შეუძლია მინიჭოს ეს სანდო ლეიბლები მხოლოდ კოდის `trustedSource` არგუმენტით; მოთხოვნის JSON ველი ვერ აღწევს ამ არგუმენტს. ტრანსკრიპტის ტექსტი რჩება არასანდო მედიისგან მიღებული კონტენტი, მიუხედავად მისი წარმოშობისა და არასოდეს უნდა განსაზღვროს ავტორიზაცია.

მოწინავე აბონენტმა შეიძლება უზრუნველყოს `audioTranscript` ტრეკი იმავე ვიდეოსთვის; ის განიხილება როგორც კლიენტის მიერ მოწოდებული ტექსტი და არა სერვერის ტრანსკრიფციის დამადასტურებელი. fusion seam აწარმოებს ვიზუალურ და აუდიო დაკვირვებებს ერთი ვადის ქვეშ და აჩერებს სიგნალს, აწესრიგებს მათ საერთო ვადაზე, არღვევს ზუსტ დუბლიკატებს და აცნობებს ნაწილობრივ შედეგს, როდესაც მხოლოდ ერთი მხარე წარმატებას მიაღწევს. არასწორი `audioTranscript` მცირდება ამ ნაწილობრივ შედეგამდე. — ვიზუალური აღწერილობა ინახება და აუდიო ფილიალი ჩაწერს გაწმენდილი უკმარისობის კოდს — მთლიანი ვიდეოს ჩავარდნის ნაცვლად. თითო ფილიალზე ხელმისაწვდომობა, ნაწილობრივი დროშა და გაწმენდილი უკმარისობის კოდები დაცულია აღწერილ შედეგში, დამცავი რელსების მეტამონაცემებში (`audioFusionRuns`/`audioFusionPartials`/ `audioFusionFailureCodes`), შედეგების ქეში მეტამონაცემებში და ხიდის შერწყმის მრიცხველებში. ნაგულისხმევი ვიდეო ხიდის ბილიკი არ იწვევს მეტყველების ტექსტს ან არ ჩამოტვირთავს მეორე მედიის ასლს; ამ აშკარა ტრეკის გარეშე, ის რჩება მხოლოდ ვიდეოზე.

**ტრანსკრიპტის შენახვა (#12150 P1).** ეს ავტომატურად მოქმედებს, როდესაც ვიდეო ხიდი (თვითონ ჩართვა) ასახავს ტრანსკრიპტის მინიშნებას — ცალკე შენარჩუნების დროშა არ არის. როდესაც მოთხოვნა წარმოქმნის რაიმე ტრანსკრიპტის სიგნალს (დარეკვის მიერ გამოცხადებული `transcript` ან შერწყმული `audioTranscript`), დამცავი მოაჯირი აღნიშნავს მას `videoBridgeObserved` და აწარმოებს ვიდეოს აღწერილობის რედაქტირებულ ჩრდილს — იდენტურ რენდერირებას, რომელშიც თითოეული სიგნალის თავისუფალი ტექსტის სხეული იცვლება `[redacted-video-transcript]` ით, რომელიც აგებულია ველის სტრუქტურის აწყობამდე. გაბრტყელებული ტექსტი, ასე რომ, არ შეიძლება გადარჩეს ცილის შემცველობა — წინააღმდეგობრივი ან ჩვეულებრივი, მათ შორის `]` შემცველი ორგანოები, როგორიცაა `[inaudible]`/`[music]` —. მუდმივი ზარის ჟურნალის მოთხოვნის ძირითადი ნაწილი ცვლის ვიდეოდან მიღებულ ტექსტის თითოეულ ნაწილს იმ რედაქტირებულ ჩრდილში, რომელიც შეესაბამება შინაარსის თანასწორობას; `fullText` წამყვანი ხელახლა იკითხება წინასწარ გამოძახების დასრულებული დამცავი სარკინიგზო დატვირთვიდან, ასე რომ, მატჩი მაინც წარმატებულია მას შემდეგ, რაც მოგვიანებით ჯაჭვის დამცავი მოაჯირები ( PII და რწმუნებათა სიგელების მასკერები, პრიორიტეტები 10/95) გადაწერენ აღწერილობის ტექსტს ადგილზე და system-prompt/handoff/memory ინექციის შემდეგ შეცვლიან შეტყობინებების მასივს. მოდელის ზემოთ გაგზავნილი სხეული უცვლელია. დაკვირვებული მოთხოვნა ასევე არ შეიცავს გამძლე მეხსიერებას (როგორც მოთხოვნის, ასევე პასუხის შედეგად მიღებული ამონაწერი გამოტოვებულია), ასე რომ, მოდელის პასუხი არ შეუძლია ტრანსკრიპტის ტექსტის მეხსიერების გამეორებას მეხსიერებაში.

**ნედლი ვიდეო ველები (#12430).** როდესაც ხიდი ჩართულია და მშობლიური ვიდეო მხარდაჭერა უცნობია ან არ არსებობს, განსაზღვრული `transcript`/`audioTranscript` ველები ასევე ააქტიურებს `videoBridgeObserved`, აღწერის წარუმატებლობის ან `maxVideos` ლიმიტის შემდეგაც კი. `null` და ცარიელი სტრიქონების რაოდენობა; არ არსებობს ველები და არა ვიდეო მეტამონაცემები. შენახული ასლები ასწორებენ ამ ველებს ან გამოტოვებენ მოთხოვნას და caches/Memory გვერდის ავლით ხდება.

ამ სარეზერვო ბილიკებზე, აბონენტის მოქმედი მინიშნებები ხდება მხარდაჭერილი `text`/`input_text` ნაწილები, ვიდრე არასტანდარტული პროვაიდერის ველები. მოთხოვნით მიწოდებული ორივე ჩანაწერი რჩება არასანდო `client` დაკვირვებებად, აშკარა გაფრთხილებით, რომ ვიდეო არ იყო აღწერილი და დროის ანაბეჭდები არ იყო დამოწმებული მედიის მიმართ. არსებული 256-cue/64-KiB ჯამური და per-cue ბიუჯეტები ვრცელდება ორ ტრასაზე ერთად; დროის ანაბეჭდები უნდა შეესაბამებოდეს ბროკერის 600 წამიან ჭერს და ნებისმიერ მიწოდებულ ფოკუსის ფანჯარას. არასწორი ჩანაწერები გაუქმებულია, არ არის გადაგზავნილი, როგორც თვითნებური ტექსტი; მოქმედი და-ძმა შეიძლება კვლავ იყოს გამოყენებული, თუ მათი ერთობლივი ბიუჯეტი არ გადააჭარბებს. Null/empty ველები არ ამატებენ ტექსტს. მედიის მიღება ან ტრანსკრიფცია არ არის დამატებული ამ სარეზერვო საშუალებით. ტრანსკრიპტის გაფართოების ველები ამოღებულია სარეზერვო ვიდეო ოპერატორიდან და მისი `video_url`/`source` ობიექტებიდან. OpenAI მავთულის ნებადართული სია რჩება მკაცრი; უცნობი მშობლიური ვიდეო ოპერატორები რჩება ხელმისაწვდომი და ცნობილი მხოლოდ ტექსტური სამიზნეები ინახავს უსაფრთხო მარკერებს. სტრუქტურირებული რედაქციის ჩრდილები იცავს დამატებულ ტრანსკრიპტის ტექსტს, ხოლო თავდაპირველი აბონენტის მოთხოვნა უცვლელი რჩება. ადგილობრივი მხარდაჭერილი სამიზნეები და გამორთული ხიდები ინარჩუნებენ არსებულ შემოვლითი ქცევას.

კადრებს თანმიმდევრულად ეწერება კონფიგურირებული ვიდეო მოდელი. ცარიელი ვიდეოს გადაფარვა მემკვიდრეობით იღებს Vision პარამეტრს; თუ ორივე ცარიელია, Vision ავტომატური როუტერი ირჩევს ეფექტურ ხედვის შესაძლებლობის მოდელს. წარმატებულმა წარწერებმა ორიგინალურ ნაწილს შეცვალა სტაბილური `[Video description:` პრეფიქსი, რომელიც ასევე აღნიშნავს ტექსტს, როგორც არასანდო მედიის დაკვირვებას და ეუბნება ქვედა დინების მოდელებს, არ დაიცვან მედიაში ნაპოვნი ინსტრუქციები. ქეშის კადრების წარწერის კლავიშები მოიცავს JPEG ბაიტებს, მოთხოვნას, დროის ნიშანს და ეფექტურ მოდელს; მხოლოდ წარმატებული წარწერები ინახება ქეშში. ქეში ჩანაწერები ინარჩუნებს რეალურ წარმატებულ პროდიუსერის მოდელს, მათ შორის სარეზერვო მოდელს; ხიდი იტყობინება `mixed` როდესაც სხვადასხვა მოდელები იწარმოებოდა სხვადასხვა ჩარჩოებით. ქეში დარტყმა ხელახლა იყენებს ამ პროდიუსერის იდენტიფიკაციას იმის ნაცვლად, რომ ხელახლა მოაწეროს ის, როგორც მოთხოვნილი მარშრუტიზაციის გეგმა. მთლიანი ვიდეოს შედეგების ქეში ჩართულია ყველა შეყვანაზე, რომელიც ცვლის გამომავალ — მოთხოვნას, ეფექტურ მოდელს, შერჩევის პოლიტიკას, კადრების რაოდენობას, სემანტიკური ანალიზის რეჟიმს, ნორმალიზებული ფოკუსის მინიშნების SHA-256 თითის ანაბეჭდს, ფოკუსის ფანჯარას, `transcript`, `audioTranscript` და საკონტაქტო ფურცლის დროშას —, ასე რომ, ამ განზომილების შეცვლა არასოდეს არ არის ქეში ხელახლა გამოყენება. ვიზუალური წაშლის პოლიტიკის ვერსია, ბარიერი და შეზღუდული კანდიდატის ჩარჩოების რაოდენობა ასევე აშკარაა შედეგის ქეშის გასაღებსა და მეტამონაცემებში; შესაბამისად, პოლიტიკის ცვლილება არ შეიძლება ხელახლა გამოიყენოს შემორჩენილი მთლიანი ვიდეო აღწერილობა. Result-cache v4 მეტამონაცემები ინარჩუნებს რეჟიმს და თითის ანაბეჭდს და არასოდეს არის მომხმარებლის დაუმუშავებელი დავალება. Guardrail მეტამონაცემები იუწყება როგორც მოთხოვნილი, ასევე ეფექტური ანალიზის რეჟიმებს; მოთხოვნილი `focused` რეჟიმი გამოსაყენებელი მომხმარებლის ტექსტის გარეშე მოხსენებულია, როგორც ეფექტურად `full`.

დამცავი მოაჯი ამოაქვს ყველა მხარდაჭერილ ვიდეო ნაწილს, მაგრამ აღწერს არაუმეტეს `modalityBridgeVideoMaxVideos`. იმისათვის, რომ სამიზნე დადასტურდეს, რომ აქვს `supportsVideo === false`, წარუმატებელი და ზედმეტად ლიმიტირებული ვიდეოები ხდება აშკარა უსაფრთხო ტექსტის მარკერები, ასე რომ არცერთი ნედლი ვიდეო არ გადარჩება. როდესაც შესაძლებლობები უცნობია, ეს ნაწილები ინარჩუნებენ ვიდეო ოპერატორს; ნებისმიერი სარეზერვო ტრანსკრიპტი მიჰყვება ზემოთ შემოსაზღვრული ტექსტის კონვერტაციას. `supportsVideo === true` სამიზნეები ხიდს გვერდის ავლით. კლიენტის მოთხოვნის შეწყვეტის სიგნალი ვრცელდება ჩამოტვირთვის, ბროკერის რიგის, ქვეპროცესების და წარწერის ზარების მეშვეობით; წყვეტს გაჩერებას ვიდეოებს შორის და არასოდეს იშლება ღია მედიისთვის.

### PII Masker (`piiMasker.ts`)

ეშვება **ორივე** ეტაპები.

- **`preCall`** ახდენს დატვირთვის კლონირებას, დადის `system`, `messages`, `input` და `prompt` (მათ შორის უბრალო სტრიქონი) და იყენებს `processPII()` ( `@/shared/utils/inputSanitizer` დან) სიმებიანი `content`/`text` ველებზე. როდესაც `PII_REDACTION_ENABLED=true`, აღმოჩენილი PII რედაქტირდება გამავალ დატვირთვაში. ეს დამოუკიდებელია `INPUT_SANITIZER_MODE` ისგან (რომელიც მხოლოდ აკონტროლებს სწრაფი ინექციის პოლიტიკას). როდესაც რედაქცია გამორთულია, ზარის ჩანაწერების აღმოჩენა ითვლის კონტენტის გადაწერის გარეშე.
- **`postCall`** ღრმად კლონირებს პასუხს, აწარმოებს `sanitizePIIResponse()` პლუს Responses-API- ფორმის მასკერი (`maskResponsesOutput` — მოიცავს `output_text` და `output[].content[].text`). თუ რაიმე რედაქცია მოხდა, შეცვლილი პასუხი ცვლის ორიგინალს.

დამცავი მოაჯირი არასოდეს იკეტება; ის მხოლოდ ანოტაციას აკეთებს (`meta.detections`, `meta.redacted`) ან გადაწერს.

Unset ნიშნავს ყველა ტიპს (ქცევა ამ პარამეტრამდე არსებობდა). მოთხოვნის ძრავის `ssn_us` ნიმუშის რუკები `ssn` ზე. შაბლონები (მინიმალური, სტანდარტული, ფინანსური, ბრაზილიური, USA, GDPR, POPIA, სრული) მხოლოდ ავსებენ ველებს UI ში.
- **GDPR და POPIA იდენტიფიკატორები** — თორმეტი ჩაშენებული ID, რომელიც მოიცავს EU და სამხრეთ აფრიკის პირად იდენტიფიკატორებს (ქვემოთ ცხრილი). მათი რეგექსები, ვალიდატორები და იურისდიქციის ტეგები ცხოვრობენ ერთ მაგიდაში, `src/shared/utils/piiPatterns.ts`, რომელსაც მოიხმარს როგორც პასუხის გამაჯანსაღებელი (`src/lib/piiSanitizer.ts`) ასევე მოთხოვნის მასკერი (`src/shared/utils/inputSanitizer.ts`). შესატყვისი რედაქტირდება მხოლოდ მაშინ, როდესაც მისი ვალიდატორი მიიღებს მას; ციფრების შიშველი რაოდენობა არასდროს არის საკმარისი. ოპერატორი, რომელმაც შეინახა შევიწროებული არჩევანი ამ id-ების არსებობამდე, ინარჩუნებს ქცევას, რაც მას ჰქონდა, სანამ ახალი id-ების მონიშვნა არ მოხდება.
- **მორგებული ნიმუშები** — 20-მდე რეგექსის ან ბუნების შაბლონი (`*` = 64-მდე არა-სივრცის სიმბოლო, `?` = ერთი). მატჩები ხდება `[CUSTOM_REDACTED]`. ყველა ნიმუში გადის `compilePiiCustomPattern()` ში (`src/shared/utils/piiCustomPatterns.ts`): მაქსიმუმ 500 სიმბოლო, დროშები შემოიფარგლება `g i m s u` ით, უნდა შედგეს, უნდა გაიაროს `safe-regex` (კატასტროფული უკან დახევა) და არ უნდა ემთხვეოდეს ცარიელ სტრიქონს ან რედაქციის ჩანაცვლების ველს. წარუმატებელი შაბლონი უარყოფილია შენახვისა და ტესტირებისას, ხოლო შენახული მწკრივი, რომელიც წარუმატებელია, გამოტოვებულია გაშვების დროს, კომპილაციის ნაცვლად. მორგებული შაბლონები მუშაობს მხოლოდ მაშინ, როცა ნიღაბი ჩართულია.
- **გამოვლენის მრიცხველები** — თითო ტიპის დათვლა (არასდროს ემთხვევა მნიშვნელობები), ინახება მეხსიერებაში და გადატვირთულია გადატვირთვისას (`src/lib/pii/piiDetectionStats.ts`). ისინი იზრდებიან მხოლოდ ნიღბის ჩართვის დროს.

პარამეტრები ცხოვრობს `key_value` ცხრილში (სახელთა სივრცე `pii_settings`, `src/lib/db/piiSettings.ts`) და იკითხება 1 წამის ქეშით. API:

| მეთოდი | მისამართი                | დანიშნულება                                                               |
| ------ | ------------------------ | ------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | დროშის მდგომარეობა, `enabledTypes`, `customPatterns`, აღმოჩენის მთვლელები |

სამივე მოითხოვს მენეჯმენტის ავტორიზაციას და ორგანოს ვალიდაციას Zod (`src/shared/validation/schemas/piiSettings.ts`) გამოყენებით. თუ შესვლა გამორთულია (`requireLogin=false`) `GET` და სატესტო ბოლო წერტილი ღიაა, მაგრამ `PUT` მაინც სჭირდება დაფის სესია, `manage` -scope API კლავიში, `oma_` წვდომის ჟეტონი ჩაწერის მასშტაბით ან უფრო მაღალი, ან CLI ჟეტონი ან შიდა სერვისის ჟეტონი გამოგზავნილი loopback-დან.

### პრომპტ-ინექცია (`promptInjection.ts`)

აღმოაჩენს მტრულ სტრუქტურებს მომხმარებლის მიერ მოწოდებულ შინაარსში და
უზრუნველყოფს კონფიგურირებული პოლიტიკის დაცვას. ქცევა განისაზღვრება გარემოს
ცვლადებითა და კონსტრუქტორის პარამეტრებით:

| პარამეტრი         | გარემოს ცვლადი                                                                                            | ნაგულისხმევი | შედეგი                                                                                                                                                                               |
| ----------------- | --------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ჩართვა            | `INPUT_SANITIZER_ENABLED`                                                                                 | `true`       | როდესაც `false`, guardrail დაუყოვნებლივ ჩერდება (short-circuit).                                                                                                                     |
| რეჟიმი            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                           | `warn`       | ინექციის პოლიტიკა: `block`, `warn` ან `log`. (`redact` მიიღება უკუთავსებადობისთვის, მაგრამ **არ** შლის ინექციის ტექსტს; მოთხოვნის PII-გადაწერა მართულია `PII_REDACTION_ENABLED`-ით.) |
| ბლოკირების ზღვარი | `blockThreshold` პარამეტრი / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ალიოსი `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | ბლოკირებისთვის აუცილებელი მინიმალური სიმძიმე. ნაგულისხმევად საშუალო (Medium) მხოლოდ დაკვირვებითი რეჟიმია.                                                                            |

**რეჟიმის პრიორიტეტი** (`getMode`): გამომძახებლის `options.mode` →
`INJECTION_GUARD_MODE` **DB feature-flag-ის გადაფარვა** (დაფა → პარამეტრები →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. ამრიგად, დაფის გადაფარვა უპირატესია env ცვლადებზე, ასე რომ Feature
Flags UI მართავს მოქმედ დამცავს რეალურ დროში (გადატვირთვის გარეშე).
DB-წაკითხვა fail-safe-ია: შეცდომის შემთხვევაში დამცავი უბრუნდება env-ზე
დაფუძნებულ ქცევას, ხოლო როდესაც გადაფარვა არ არის დაყენებული, ქცევა იდენტურია
მხოლოდ env-ზე დაფუძნებული განსაზღვრის.

აღმოჩენის წყაროები:

1. `sanitizeRequest()` მოდულიდან `@/shared/utils/inputSanitizer` (დეტექტორების
   საერთო ნაკრები, რომელიც პაიპლაინის სხვა ნაწილებშიც გამოიყენება).
2. ჩაშენებული `DEFAULT_GUARD_PATTERNS` (ამჟამად `system_override_inline` და
   `markdown_system_block`, ორივე `high` სიმძიმით).
3. არასავალდებულო `customPatterns`, გადაცემული კონსტრუქტორის პარამეტრებით
   (სტრიქონები, regex-ები ან `{ name, pattern, severity }` ჩანაწერები).

როდესაც `mode === "block"` **და** მინიმუმ ერთი აღმოჩენა სიმძიმის
ზღვარს აკმაყოფილებს, `preCall` აბრუნებს
`{ block: true, message: "Request rejected: suspicious content detected" }`-ს.
`warn`/`log` რეჟიმებში guardrail-ი ლოგავს, მაგრამ ზარს ტოვებს.
საერთო დამხმარე ფუნქცია `evaluatePromptInjection()` ასევე
ექსპორტირებულია იმ გამომძახებლებისთვის, რომლებსაც prompt-ების
შეფასება სჭირდებათ რეესტრის გვერდის ავლით.

**სკანირების ზღვარი (v3.8.20):** დეტექტორი მხოლოდ გაერთიანებული
prompt ტექსტის **პირველ 16 კბ**-ს ამოწმებს —
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ბაიტი) ფაილში
`src/shared/utils/inputSanitizer.ts`. ორივე `detectInjection()` და
`evaluatePromptInjection()` ასრულებს `slice(0, MAX_INJECTION_SCAN_BYTES)`-ს
შაბლონების ციკლის გაშვებამდე. ინექციის დირექტივები შეყვანის
დასაწყისთანაა განთავსებული, ამიტომ ეს ზღუდავს regex-ის CPU/GC
დატვირთვას ასობით კილობაიტიან payload-ებზე აღმოჩენის დასუსტების
გარეშე (იხ. #3932, #4041).

### ავტორიზაციის მონაცემების დამმალვი (`credentialMasker.ts`)

მუშაობს **ორივე** ეტაპზე, ნაგულისხმევი ჯაჭვის ბოლო რგოლად
(პრიორიტეტი `95`). ფარავს ცნობილი API-გასაღების / საიდუმლო
ტოკენის შაბლონებს გამავალი payload-დან (შეტყობინების შიგთავსი,
ინსტრუმენტის გამოძახების არგუმენტები, ინსტრუმენტის შედეგები) **და**
პროვაიდერის პასუხიდან, რათა prompt-ში ჩასმული ავტორიზაციის მონაცემი
(ან ინსტრუმენტის შედეგით დაბრუნებული) არ გაჟონოს აპსტრიმ
პროვაიდერამდე ან უკან კლიენტამდე.

- **მხოლოდ opt-in**, იგივე კონვენციით, რაც PII-ის დაფარვა
  (მკაცრი წესი #20-თან დაკავშირებული): გამორთულია, სანამ
  `settings.credentialRedactionEnabled === true` **ან**
  `CREDENTIAL_REDACTION_ENABLED=true` არ იქნება. გამორთული
  მდგომარეობით guardrail-ი არაფერს აკეთებს (no-op) — არასდროს
  ბლოკავს და არასდროს გადაწერს.
- `redactCredentials()` ვლის მთელ payload/პასუხის ხეს
  (`walkValue()`, prototype-pollution-ისგან უსაფრთხო, ციკლებისგან
  დაცული `WeakSet`-ით) და ცვლის დამთხვევებს `[REDACTED:<type>]`
  placeholder-ით, კლონირებს კი მხოლოდ იმ ტოტებს, რომლებიც რეალურად
  შეიცვალა.
- `CREDENTIAL_PATTERNS` მოიცავს LLM პროვაიდერის გასაღებებს (OpenAI,
  OpenAI-proj, Anthropic, Google, Hugging Face, Replicate),
  VCS/SaaS ტოკენებს (GitHub, Slack, Linear, Notion, npm, Postman,
  Discord), გადახდის გასაღებებს (Stripe, Square), ღრუბლის
  გასაღებებს (AWS access key, Twilio, SendGrid, Mailgun), პირად
  გასაღებებს / JWT-ებს, ავტორიზაციის მონაცემების შემცველ კავშირის
  სტრიქონებს (`mongodb://user:pass@...` და ა.შ.) და ზოგად
  `Authorization`/`x-api-key`/`api-key`/`apikey`
  ჰედერ-მნიშვნელობის შაბლონს. ჰედერისებრი გასაღებები
  (`authorization`, `x-api-key`, `api-key`, `apikey`) იფარება
  სტრუქტურულად (მხოლოდ მნიშვნელობა; სქემის პრეფიქსი, როგორიცაა
  `Bearer `/`Basic `, შენარჩუნებული რჩება) და არა ზოგადი
  ტექსტური regex-ით.
- guardrail-ი არასდროს ბლოკავს; ის მხოლოდ გადაწერს
  (`modifiedPayload` / `modifiedResponse`) და ანოტირებს
  (`meta.credentialsRedacted`, `meta.count`).

რეგრესიის დაცვა: `tests/unit/credential-masker-guardrail.test.ts`.

## საბაზო კონტრაქტი (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true მოკლედ წყვეტს ჯაჭვს
  message?: string; // გამოჩნდება დაბლოკვისას
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // preCall-ის მიერ დაბრუნებული მოთხოვნის გადასაწერად
  modifiedResponse?: TValue; // postCall-ის მიერ დაბრუნებული პასუხის გადასაწერად
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail-ი „ცვლილების არარსებობის" სიგნალს იძლევა `void`-ის, `{}`-ის ან
`{ block: false }`-ის დაბრუნებით. `modifiedPayload`/`modifiedResponse`-ის დაბრუნება
ცვლის მნიშვნელობას, რომელიც მიმდინარეობს ჯაჭვში შემდგომი guardrail-ებისთვის.
`signal?: AbortSignal` გამომძახებლის სასიცოცხლო ციკლს ატარებს guardrail-ებში. მოთხოვნის
შეწყვეტა (abort) არის განზრახ fail-open გამონაკლისი: მედია ხიდები წყვეტენ მუშაობას და
ასუფთავებენ რესურსებს ნედლი მედიის იმ მიზნისთვის დაბრუნების გარეშე, რომელზეც ცნობილია,
რომ მისი მხარდაჭერა არ შეუძლია.

## რეესტრი (`registry.ts`)

სინგლტონი `guardrailRegistry` ამჟღავნებს:

- `register(guardrail)` — ამატებს (ან ნორმალიზებული სახელით ცვლის) guardrail-ს და
  ხელახლა ალაგებს `priority`-ის ზრდადობით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარეები.
- `runPreCallHooks(payload, context)` — გადაუვლის აქტიურ guardrail-ებს, ატარებს
  payload-ს `modifiedPayload`-ით და ჩერდება პირველ `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე ნაკადი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და
  სურვილისამებრ ხელახლა არეგისტრირებს ნაგულისხმებებს სუფთა ტესტის იზოლაციისთვის.

ორივე გამშვები აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც მოიცავს
თითოეული guardrail-ის `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც სასარგებლოა ტრასირებისთვის.

### Guardrail-ების გამორთვა თითო მოთხოვნის მიხედვით

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აგრეგავს guardrail-ების
სახელების დედუპლიკირებულ სიას, რომლებიც უნდა გამოიტოვოს მიმდინარე მოთხოვნისთვის.
არსებობს ხუთი არხი, რომლებიც იკითხება ამ თანმიმდევრობით და ერთ სიაში ერთიანდება
(დედუპლიკაციისას პირველი შემთხვევა იგებს):

1. `apiKeyInfo.disabledGuardrails`
2. მოთხოვნის სხეულის `disabledGuardrails` (უმაღლესი დონის)
3. მოთხოვნის სხეულის `metadata.disabledGuardrails` (მხოლოდ მაშინ, როდესაც `metadata` ობიექტია)
4. ჰედერი `x-omniroute-disabled-guardrails`
5. მოძველებული ჰედერი `x-disabled-guardrails`

ყველა ხუთი არხი ერთიანდება, ორი ჰედერის ჩათვლით: ორივე
`x-omniroute-disabled-guardrails`-ისა და `x-disabled-guardrails`-ის გაგზავნა გამოტოვებს
მათი სიების გაერთიანებას, ხოლო ცარიელი თანამედროვე ჰედერი აღარ მალავს მოძველებულს
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), გასწორდა
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)-ში).

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივი ან მძიმით გამოყოფილი სტრიქონი; სახელები
იჭრება და ნორმალიზდება პატარა ასოების kebab-case ფორმატში (`pii_masker` → `pii-masker`),
ხოლო ცარიელი ჩანაწერები გამოირიცხება. შედეგი გადაეცემა რეესტრს `context.disabledGuardrails`-ის
მეშვეობით, რომელიც გამოტოვებს შესაბამის guardrail-ებს (`skipped: true` `results`-ში).

გამორთვის სია მოქმედებს მხოლოდ **რეესტრზე**. Prompt-injection-ის `block` რეჟიმი
სავალდებულო საზღვარია: injection-guard middleware
(`src/middleware/promptInjectionGuard.ts`) იძახებს `evaluatePromptInjection()`-ს
ყოველგვარი გამომძახებლის მიერ კონტროლირებადი გამორთვის სიის გარეშე (მკვდარი
`resolveDisabledGuardrails({ body })` გამოძახება, რომელსაც ის ადრე აკეთებდა, წაიშალა
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)-ში), ამიტომ მოთხოვნა,
რომელიც თიშავს `prompt-injection`-ს, მაინც უარსაცდება `block` რეჟიმში. ეს განზრახ
არის ასე დაპროექტებული. გამორთვის არხები გამომძახებლის მიერ არის კონტროლირებადი
(მოთხოვნის სხეული, მეტამონაცემები, ჰედერები), და გამომძახებელმა არ უნდა შეძლოს
ოპერატორის მიერ დაყენებული უსაფრთხოების კონტროლის გამორთვა
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). ჰედერების გაერთიანება
[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)-დან ცვლის მხოლოდ იმას,
თუ რომელი რეესტრის guardrail-ები გამოიტოვება; ის კლიენტს არ აძლევს middleware-ის
გვერდის ავლის საშუალებას. სავალდებულო per-key და per-group guardrail პოლიტიკები
თვალყურსდევნებულია v4 RFC-ში [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
იხილეთ [დაფარვა და შეზღუდვები](#coverage-and-limits).

## შესრულების რიგითობა

თითოეული მოთხოვნისთვის, რომელიც გადის `src/sse/handlers/chat.ts`-ისა და
`open-sse/handlers/chatCore.ts`-ის გავლით (ჩატის ოჯახის მარშრუტები, ჩამოთვლილია
[დაფარვა და შეზღუდვები](#coverage-and-limits)-ში):

1. `resolveDisabledGuardrails(...)` ქმნის გამოტოვების სიას API გასაღებიდან,
   მოთხოვნის სხეულიდან და თავსართებიდან.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ასრულებს guardrail-ებს
   პრიორიტეტის ზრდადი რიგითობით:
   - გამორთული guardrail-ები ინიშნება როგორც `skipped`.
   - თითოეული guardrail-ის `preCall` შეუძლია გადაწეროს payload
     `modifiedPayload`-ის მეშვეობით.
   - პირველი `block: true` წყვეტს ჯაჭვს და დამმუშავებელი აბრუნებს
     guardrail-ის უარყოფის პასუხს.
3. (შესაძლო გადაწერილი) payload გადადის კომბინირებული მარშრუტიზაციისა და
   upstream-ში გადაგზავნის ეტაპზე.
4. **მხოლოდ არა-ნაკადური:** პასუხის აწყობის შემდეგ,
   `guardrailRegistry.runPostCallHooks(...)` იგივე ჯაჭვს ასრულებს პასუხზე.
   აქ `block: true` ყრის upstream პასუხს და აბრუნებს HTTP 400-ს. ნაკადური
   პასუხები ამ ნაბიჯს მთლიანად გამოტოვებს.

Guardrail-ები, რომლებიც შეცდომას ისვრიან, ინიშნება `error: <message>`-ით და
ილოგება `logger.warn`-ით, მაგრამ ჯაჭვი გრძელდება — განზრახ fail-open
პრინციპით.

## დაფარვა და შეზღუდვები

guardrail-ების რეესტრი ჩართულია მხოლოდ ჩატის pipeline-ში. ეს შეზღუდვები
დაფიქსირებულია `tests/unit/guardrail-pipeline-wiring-characterization.test.ts`-ითა და
`tests/unit/guardrail-pipeline-characterization.test.ts`-ით; როცა ქცევა
იცვლება, ეს ტესტები განზრახ განაახლეთ.

[მარშრუტების დაფარვა](#injection-guard-route-coverage--red-team-phase-8--block-d)). მხოლოდ prompt injection.                                                                                                                                                                                                                                                             |

### რა არ არის დაფარული

- **მედიის, embeddings-ისა და მონაცემების მარშრუტები** (`/v1/images/*`,
  `/v1/embeddings`, `/v1/audio/*`, `/v1/videos/generations`,
  `/v1/music/generations`, `/v1/rerank`, `/v1/search`, `/v1/moderations`)
  არასდროს აღწევს რეესტრს. იქ არ სრულდება არც PII-ის მასკირება, არც
  credential-ების მასკირება და არც modality bridge. მათი ერთადერთი შემოწმებაა
  მოძველებული injection-guard middleware.
- **ნაკადურ პასუხებს** არ აქვთ post-call guardrail-ები: არც `pii-masker` ან
  `credential-masker` post-call და არც post-call ბლოკი. მოქმედებს მხოლოდ
  ნაკადური PII ტრანსფორმაცია (როცა `PII_RESPONSE_SANITIZATION` ჩართულია).
  ნაკადურ პასუხში უკან დაბრუნებული credential არ იმალება.
- **გამორთვის არხები vs. middleware (განზრახ):** middleware აფასებს prompt
  injection-ს საკუთარი `evaluatePromptInjection()`-ის გამოძახებით,
  გამომძახებლის მიერ კონტროლირებადი გამორთვის სიის გადაცემის გარეშე. `block`
  რეჟიმი არის სავალდებულო საზღვარი, რომლის გვერდის ავლაც გამომძახებლის მიერ
  კონტროლირებად გამორთვებს არ შეუძლიათ, მათ შორის ჩატის ოჯახის მარშრუტებზე
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).
  `prompt-injection`-ის გამორთვა მხოლოდ რეესტრის guardrail-ს გამოტოვებს.

### რა ხედავს პასუხს post-call-მდე

არა-ნაკადურ გზაზე რიგითობა შემდეგია: მეხსიერების ამოღება → ჩაშენებული
ინსტრუმენტების შესრულება → post-call guardrail-ები → post-call ბლოკით
გასვლა → სემანტიკურ ქეშში შენახვა.

- **მეხსიერების ამოღება** და **ინსტრუმენტების შესრულება** პასუხს ხედავს მანამ, სანამ post-call
  guardrails მას გადაწერს ან დაბლოკავს.
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401)-დან, მეხსიერების
  ამოღება ამოღებულ ტექსტს ამუშავებს `sanitizePII`-ით, როდესაც
  `PII_RESPONSE_SANITIZATION` ჩართულია (როგორც სტრიმინგის, ასევე არასტრიმინგის რეჟიმში), მაგრამ
  პასუხი, რომელსაც post-call მოგვიანებით ბლოკავს, უკვე შეთავაზებულია მეხსიერებასა და
  ინსტრუმენტებს.
- **სემანტიკური ქეში** პასუხს post-call-ის შემდეგ ინახავს, ამიტომ ის
  გადაწერილ პასუხს ინახავს, ხოლო დაბლოკილი პასუხი არასოდეს ქეშირდება. ქეშის ჩანაწერები
  გასაღებივებულია თითოეული API გასაღების მიხედვით.

## კონფიგურაცია

გარემოს ცვლადები, რომლებსაც ჩაშენებული დამცავი მექანიზმები (guardrails) კითხულობენ:

| ცვლადი                                | გამომყენებელი               | ეფექტი                                                                                                             |
| ------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`          | დააყენეთ `false` აღმოჩენის სრულად გამოსართავად.                                                                    |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`          | ინექციის პოლიტიკა: `warn`, `block` ან `log`. მემკვიდრეობითი მნიშვნელობა `redact` არ გადაწერს ინექციის ტექსტს.      |
| `INJECTION_GUARD_MODE`                | `prompt-injection`          | ინექციის დამცავის რეჟიმი; ასევე DB-ში შენახული feature flag-ი, რომელიც **გადაფარავს** გარემოს ცვლადებს (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`          | სიმძიმის მინიმალური დონე, რომელსაც `MODE=block` უარყოფს: `high` (ნაგულისხმევი), `medium` ან `low`.                 |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`          | `INPUT_SANITIZER_BLOCK_THRESHOLD`-ის მემკვიდრეობითი ფსევდონიმი.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`                | როდესაც `true`, მოთხოვნაში არსებული PII იმალება (ინექციის რეჟიმისგან დამოუკიდებლად).                               |

## მორგებული Guardrail-ები

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1. შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც აფართოებს `BaseGuardrail`-ს.
2. განახორციელეთ `preCall` და/ან `postCall`.
3. დაარეგისტრირეთ იმპორტის დროს (push-ით `registerDefaultGuardrails`-დან) ან
   გამოიძახეთ `guardrailRegistry.register(...)` გაშვების დროს — რეესტრი ცვლის
   ნებისმიერ ადრე რეგისტრირებულ guardrail-ს იგივე ნორმალიზებული სახელით.
4. დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ტესტირება

გამოიყენეთ `resetGuardrailsForTests()` ტესტებს შორის, რათა ცნობილი მდგომარეობიდან დაიწყოთ.
გადაეცით `{ registerDefaults: false }`, რათა დაიწყოთ ცარიელი რეესტრით და დაარეგისტრიროთ

არჩევისთვის, credential-ების შემოწმებისთვის და ტრანსკრიფციისთვის. შესაბამისად,
ტესტებს შეუძლიათ ორივე ნაკადის შემოწმება მონაცემთა ბაზის ან ქსელური წვდომის გარეშე.

## Injection-guard-ის მარშრუტების დაფარვა და red-team (ფაზა 8 · ბლოკი D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) ფარავს ყველა
მარშრუტს, რომელიც იღებს მომხმარებლის prompt-ებს. იგი ითვალისწინებს
`INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ლოგირება;
`block` = აბრუნებს HTTP 400-ს `SECURITY_001`-ით).

| ტიპი              | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| ტექსტი (არსებული) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| გენერატიული       | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| მონაცემები        | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ველებს.

**Red-team (ყოველღამით, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი
ბლოკავს OWASP-LLM კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak უშვებს probe-ებს
(secret-ის გარეშე გამოტოვებს). `moderations` ჩართულია თანმიმდევრობისთვის. Block რეჟიმი
სავალდებულო საზღვარია: `evaluatePromptInjection()` უგულებელყოფს თითოეული მოთხოვნის
გამორთვის სიას, რომელსაც middleware გადასცემს, ამიტომ `disabledGuardrails` **არ**
ათავისუფლებს მარშრუტს მისგან ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

ღამის workflow (`.github/workflows/nightly-llm-security.yml`, cron + ხელით
გაშვება) შეიცავს ორ job-ს:

- **`promptfoo-guard` (ბლოკირებადი)** — უშვებს `promptfoo eval -c promptfooconfig.yaml`-ს
  `INJECTION_GUARD_MODE=block`-ით. თითოეული adversarial შემთხვევა (მაგ. „უგულებელყე
  ყველა წინა ინსტრუქცია…", DAN-სტილის jailbreak-ები) ამტკიცებს, რომ პასუხი შეიცავს
  `error.code === "SECURITY_001"`-ს, ანუ guard-მა ნამდვილად უარყო მოთხოვნა.
- **`garak` (სარეკომენდაციო)** — უშვებს garak-ს `--probes promptinject,dan,leakreplay`
  ლოკალური OmniRoute ინსტანციის მიმართ (`http://localhost:20128/v1`). გაპირობებულია
  provider-ის secret-ით (`PROMPTFOO_PROVIDER_KEY`); უპრობლემოდ გამოტოვებს და დასრულებულია
  `|| true`-ით, ამიტომ აწვდის ანგარიშს CI-ის ჩავარდნის გარეშე.

Guard helper-ის (`createInjectionGuard` / `withInjectionGuard`) დაფარვა მოიცავს
ყველა prompt-ის შემცველ `/v1` მარშრუტს; prompt-ის ტექსტი ამოიღება
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ველებიდან
`extractMessageContents()`-ით, `src/shared/utils/inputSanitizer.ts`-ში.
