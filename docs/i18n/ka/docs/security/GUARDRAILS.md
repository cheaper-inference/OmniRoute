### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

GLM 5.3 საბაზო მოდელს და `glm-5.3-{low,high,max}` აქვს აშკარა `supportsVision:false` registry/spec მეტამონაცემები. GLM 5.3 Flash ვარიანტები რჩება მშობლიური ხედვის მოდელებად. Claude Code-ის `/v1/messages` მარშრუტი შედის საზიარო `handleChat` წინასწარ გამოძახებისას დამცავი რელსების ჯაჭვში** ადრე** Claude-to-OpenAI თარგმანი; ჩადგმული `Read` ინსტრუმენტის შედეგების სურათები უნდა იყოს აღწერილი ან დამუშავებული მანამ, სანამ თარგმანი გადაიყვანს მათ OpenAI `image_url` შიგთავსში (#17069).

წყვეტს გამოსახულების მატარებელ მოთხოვნებს, რომლებიც მიმართულია** უხილავი მოდელები** და ან გადააგზავნის მთელ მოთხოვნას ხედვის უნარიან მოდელზე, ან ცვლის გამოსახულების ნაწილებს ტექსტის აღწერებით, რომლებიც წარმოებულია კონფიგურირებადი ხედვის მოდელის მიერ ზემოთ დინებაში ზარამდე. ეს საშუალებას აძლევს მხოლოდ ტექსტურ პროვაიდერებს გამჭვირვალედ აწარმოონ მულტიმოდალური დატვირთვები.

ნაკადი:

1. გამოტოვეთ, თუ სამიზნე მოდელი უკვე მხარს უჭერს ხედვას (თუ ის არ ჩანს იძულებითი ხიდის სიაში `isVisionBridgeForcedModel`).
2. გამოსახულების ნაწილების ამოღება `extractImageParts(messages)` (`visionBridgeHelpers.ts`) მეშვეობით, რომელიც დელეგირებს** ერთიანი მედიის დეტექტორი** `detectMediaParts()` in `open-sse/utils/mediaParts.ts` — სიმართლის ერთი წყარო, რომელიც გაზიარებულია კომბინირებული თავსებადობის ფილტრთან. ექსტრაქცია ნებადართულია იმ ფორმებში, რომლებსაც `replaceImageParts` შეუძლია უკან შეაერთოს (ატრაქტი ↔ ცვლის კონტრაქტს): OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL `source.type:"url"` და პასუხები API `input_image`. შესატყვისი გამოსახულებები ჩადებული Claude Code `tool_result.content` ში და Responses ინსტრუმენტის შედეგები ასევე ამოღებულია და იცვლება თავდაპირველ ბილიკებზე; მხოლოდ ინდიკატორის ფორმები არის კომბინირებული ფილტრის მასალა და არ არის ამოღებული. გამოტოვეთ, თუ არცერთი არ მოიძებნა.
3. Runtime-ის კონფიგურაციის გადაჭრა `resolveVisionBridgeRuntimeSettings()` (`src/shared/constants/modalityBridgeDefaults.ts`) საშუალებით: ახალი `modalityBridge*` პარამეტრების ღილაკები გაიმარჯვებს; მემკვიდრეობითი `visionBridge*` გასაღებები რჩება ა** ერთი ციკლის სარეზერვო** (უკან ფანჯარა). გამოტოვეთ მედიის გადაკვეთამდე, როდესაც ხიდი გამორთულია.
4. რეჟიმის ამომრჩევი (`modalityBridgeVisionMode`, იხილეთ ცხრილი ქვემოთ) გადაწყვეტს გადამისამართებას და აღწერას. გადამისამართება აბრუნებს `modifiedPayload` მხოლოდ `model` შეცვლით, პლუს მეტა `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერეთ ბილიკი: გამოსახულებების დახურვა `maxImages` ზე, შეადგინეთ ამოცანების ცოდნის მოთხოვნა, იხილეთ აღწერის ქეში, დარეკეთ ხედვის მოდელს** პარალელურად** (`Promise.allSettled`) და შეიტანეთ `[Image N]: <description>` ტექსტის ნაწილები მათ ადგილას. წარუმატებელი აღწერა იძლევა `null`: ნედლეული სურათი შენახულია unknown/vision-capable სამიზნეებისთვის (#4012), მაგრამ** დადასტურებული მხოლოდ ტექსტური პირდაპირი სამიზნე** ან ნულოვანი ხედვის კომბინაცია იღებს ცალსახა `(unavailable — no vision-capable provider connected)` ტექსტის ნაკვთს ყველა აუწერელი სურათისთვის, მათ შორის ნაწილობრივი წარუმატებლობისა და აღწერის ზარის (#17069) მიღმა გამოსახულებები. სარეზერვო აღწერის არსებული ყველა წარუმატებელი კომბინაცია რჩება ადგილზე (#8430).
6. დააბრუნეთ `modifiedPayload` + meta (`imagesProcessed`, `descriptions`, `processingTimeMs`, `visionModel`).

იძულებითი რეჟიმის მოკლე ჩართვა** ადრე** ავტო ევრისტიკული გაშვებები; `auto` ქცევა ბაიტის იდენტურია pre-PR-1 დამცავი მოაჯირის.

#### API კლავიშის ფარგლები (`visionBridgeKeyScope.ts`)

როდესაც აბონენტის API კლავიატურა ზღუდავს `allowedConnections`, კვოტირების აუზებს (`allowedQuotas`) ან მოდელებს (`allowedModels` / `blockedModels` / `modelAccessMode: "restricted"` / `disableNonPublicModels`), ხიდი ირჩევს მხოლოდ გადამისამართებას და აღწერს მოდელებს, რომლებსაც გასაღები შეიძლება გამოიყენოს, კავშირებზე კი შეიძლება გამოიყენოს გასაღები. ამის შემდეგ აღწერის ზარი ყოველთვის გადის OmniRoute თვითგამორკვევას `x-omniroute-self-loop-key-id` სათაურით, ასე რომ, ჩეთის მიმღები მოთხოვნა ხელახლა ახორციელებს ამ გასაღების კავშირს და მოდელის პოლიტიკას. `enforceApiKeyPolicy()` აფასებს ამ სათაურს მხოლოდ self-loop-ის მატარებელთან ერთად, ასე რომ, მას შეუძლია მხოლოდ ვიწრო წვდომა და ID, რომელიც არ წყვეტს, უარყოფილია.

თუ გასაღებისთვის არ არის ნებადართული ხედვის მოდელი, ა** დადასტურებული მხოლოდ ტექსტური სამიზნე** უარყოფს გამოსახულების მოთხოვნას ადგილობრივად მკაფიო HTTP 400-ით გამოსახულების ბაიტების გადამისამართების ნაცვლად უუნარო ზედა ნაკადში (#17069). უცნობი ან მშობლიური ხედვის შესაძლებლობის მქონე სამიზნეებისთვის, აღწერის გზა ინარჩუნებს თავის წინა ქცევას, რომელიც არ არის გახსნილი (meta `{ skipped: true, reason: "no_permitted_vision_model" }`). მოთხოვნები გასაღების გარეშე და გასაღებები ამ შეზღუდვების გარეშე იქცევიან ზუსტად ისე, როგორც ადრე.

#### ამოცანების გაცნობიერებული აღწერის მოთხოვნა (`modalityBridgeVisionTaskAware`)

ნაგულისხმევი** მართალია** . `composeVisionPrompt()` (`visionBridgeHelpers.ts`) ანიჭებს ტექსტს** მომხმარებლის ბოლო შეტყობინება** (შემოკლებულია 500 სიმბოლოზე) საბაზისო აღწერის მოთხოვნაზე, აღწერილობის მიმართვა იმისკენ, თუ რა სთხოვა მომხმარებელმა რეალურად (codex-vision-proxy pattern) და ხედვის მოდელს სთხოვს ხილული ტექსტის ტრანსკრიფციას. თუ დროშა გამორთულია — ან არ არის მომხმარებლის ტექსტი — საბაზისო მოთხოვნა გამოიყენება უცვლელად.

აღწერს self-loop-ის საკუთარი OpenAI-თან თავსებადი მოთხოვნა (`callVisionModelSingle()` in `visionBridgeHelpers.ts`) ყოველთვის ითხოვს `image_url.detail: "high"` — ს უპირობოდ, ყველა caller/provider სთვის, რომელიც არ არის დაბლოკილი კლიენტის სიგნალზე. დაბალი დეტალების შერჩევა ამცირებს OCR სიზუსტეს ზუსტად ტექსტის ტრანსკრიფციის ამოცანისთვის, რომელსაც ეს მოთხოვნა ითხოვს, ასე რომ, თავად აღწერის ზარი ყოველთვის ითხოვს მაღალ დეტალებს, მიუხედავად იმისა, თუ რა დეტალის დონეს იყენებდა თავდაპირველი შემომავალი მოთხოვნა. ეს გავლენას ახდენს მხოლოდ შიდა აღწერის მოთხოვნის ორგანოზე; ის არ ცვლის, თუ როგორ გადასცემს OmniRoute აბონენტის საკუთარ `image_url.detail` პირველად — მოთხოვნაზე, რომელიც ნაგულისხმევი გამოიყენება ცალკე და მხოლოდ აღმოჩენილი OpenCode კლიენტებისთვის, `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Anthropic მავთულის ფორმატის განშტოებას describe self-loop არ აქვს `detail` ველი და მასზე გავლენას არ ახდენს არც ერთი ნაგულისხმევი.

#### აღწერეთ გამომავალი ქუდი (`modalityBridgeVisionMaxChars`)

| გასაღები                       | ნაგულისხმევი | დიაპაზონი        |
| ------------------------------ | ------------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` ან 100–50000 |

`0` (ნაგულისხმევი) ნიშნავს** არა ქუდი** — `callVisionModel()` ის მიერ დაბრუნებული აღწერა გადადის უცვლელად, არსებული ქცევის შენარჩუნებით. ნებისმიერი მნიშვნელობა 100-50000 დიაპაზონში წყვეტს აღწერილობას `…` სუფიქსით, სანამ ის უკან გაიყოფა, როგორც `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts` ში). გაზარდეთ ეს დეტალურად მძიმე OCR ამოცანებისთვის, სადაც ქვედა დინების მოდელს სჭირდება სრული ტრანსკრიფცია; დაწიეთ იგი შეკრული ჟეტონის გამოყენებამდე ჭკვიანური ხედვის მოდელებზე. დაფის ველი ცხოვრობს Vision ჩანართის Advanced პანელზე (`modality-bridge-max-chars` in `ModalityBridgeVisionTab.tsx`) და ამაგრებს ნებისმიერ მნიშვნელობას 1-დან 99-მდე 100 სართულამდე, ხოლო აშკარა `0` ხელუხლებლად ტოვებს — `0` არის მოქმედი Zod მნიშვნელობა თავისთავად (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) და არა მხოლოდ ნაგულისხმევი "დაუყენებელი".

#### აღწერეთ ქეში (`modalityBridge/bridgeCache.ts`)

მეხსიერებაში LRU + TTL ქეში შედეგების აღწერისთვის, საერთო პროცესის მასშტაბით. გასაღები = `sha256(imageRef + composedPrompt + configuredBridgeModel)` სიგრძის პრეფიქსის ჩარჩოებით (ველის საზღვრის შეჯახების გარეშე). მოდელის კომპონენტია** კონფიგურირებული** ხიდის მოდელი და არა ის მოდელი, რომელმაც რეალურად უპასუხა — `callVisionModel`, შეიძლება შიგადაშიგ დაბრუნდეს და თითო მცდელობაზე დაჭერა ქეშის დანაწევრებას მოახდენს. წარუმატებელი აღწერილობები არასოდეს ინახება ქეშში. პარამეტრები:

| გასაღები                        | ნაგულისხმევი | დიაპაზონი |
| ------------------------------- | ------------ | --------- |
| `modalityBridgeCacheEnabled`    | `true`       | —         |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440    |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000   |

#### გამოსახულების დისტანციური ნორმალიზაცია (self-loop describe/base64 fetch)

როცა ხიდს ა** დისტანციური** თავად სურათი — Anthropic აღწერს თვითგამოძახებას და claude-wire-format base64 კონვერტაციას (`ensureBase64ImagesForClaudeWire`), ორივე `fetchRemoteImageAsDataUri()` მეშვეობით `visionBridgeHelpers.ts` — ში მიღებული მონაცემები URI გადაეცემა `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) ხედვის მოდელის მოთხოვნაში ჩასვლამდე. დიდი ზომის სურათები შემცირებულია A-მდე** სიგრძე 2048 პიქსელი** (ზომის შეცვლის ქუდის შესატყვისი OpenAI/Anthropic უკვე გამოიყენება სერვერის მხარეს), რაც წყვეტს ატვირთვას bytes/latency ხედვის მოდელის დანახვის გარეშე. ზომის შეცვლა იყენებს `sharp`, დატვირთული დინამიური იმპორტის საშუალებით: პლატფორმაზე, სადაც მისი მშობლიური ორობითი ვერ იტვირთება, `normalizeDataUri()`** არასოდეს ისვრის** — ის ბრუნდება თავდაპირველი ბაიტების გავლაზე, ამიტომ describe/base64-conversion ბილიკი ყოველთვის აგრძელებს მუშაობას. არა-გამოსახულების ბაიტები (ჩამოტვირთვა, რომელმაც არ დააბრუნა დეკოდირებადი სურათი) ასევე გადაიცემა ხელუხლებლად. ეს ნორმალიზება მიზნად ისახავს ხიდის სურათებს, რომლებიც იღებენ საკუთარ თვითგამოძახებას — ის არასოდეს გამოიყენება აბონენტის ნედლეული გადასასვლელის დატვირთვაზე, რაც შეესაბამება მხოლოდ არჩევის მუტაციის პრინციპს (Hard Rule #20).

#### პარამეტრების სქემა + მიგრაცია

ახალი `modalityBridge*` კლავიშები Zod-დამოწმებულია `updateSettingsSchema` ში (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` ტრიო და `modalityBridgeAudio*` ჯგუფი, რომელსაც იყენებს აუდიო ხიდი. Migration `141_modality_bridge_settings.sql` აკოპირებს არსებულ ძველ `visionBridge*` მნიშვნელობებს შესატყვის ახალ გასაღებებზე (იდემპოტენტური, არასოდეს გადაწერს ოპერატორის ნაკრების `modalityBridge*` მნიშვნელობას); მემკვიდრეობითი კლავიშები მიიღება, როგორც წაკითხვის სარეზერვო საშუალება ერთი გამოშვების ციკლისთვის.

#### გამჭვირვალობის სათაური + სტატისტიკა

აღწერე-ტრანსფორმირებული პასუხები შეიცავს `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (აშენებული `buildModalityBridgeHeader()` მიერ `modalityBridge/bridgeStats.ts` ში, შტამპი `withModalityBridgeHeader()` ით `src/sse/handlers/chatHelpers.ts` ში). გადამისამართებული მოთხოვნები მიიღება** არა** header — დატვირთვა ხელუხლებელი იყო და მოდელის შეცვლა უკვე ჩანს საპასუხო ორგანოს `model` ველში.

`GET /api/modality-bridge/stats` (მართვის ავტორიზაცია, იგივე იარუსი, როგორც `GET /api/settings`) აბრუნებს მეხსიერების თითო მოდალობის მრიცხველებს `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` `vision`, `audio` და `video`. `averageLatencyMs` იყენებს `latencySamples` და არა ყველა მცდელობას, როგორც მის მნიშვნელს; ოპერაცია დროის გარეშე არ ქმნის ნულოვანი მილიწამიან ნიმუშს. `bridged` რჩება წარმატებულ კონვერტაციებში ჩამორჩენილ თავსებად მეტსახელად; წარუმატებელი მცდელობები არ ზრდის მას. მრიცხველები გადატვირთულია პროცესის გადატვირთვისას დიზაინის მიხედვით (ტელემეტრია, არა აღრიცხვა).

#### დაფის კონფიგურაცია

სპეციალური დაფის გვერდი არის `/dashboard/settings/modality-bridge`. მისი URL-მისამართიანი `Vision`, `Audio` და `Video` ჩანართები ინარჩუნებს მოთხოვნის პარამეტრებს `tab` მნიშვნელობის გადართვისას. Vision ჩანართი ასახავს ჩართვას, რეჟიმს, მოდელის არჩევანს (ავტომატური ნაგულისხმევის ჩათვლით), ამოცანების გაცნობიერების მოთხოვნას, გაფართოებულ timeout/image/description-length/cache ლიმიტებს, გაშვების დროის მრიცხველებს და დაცული ნიმუშის მოთხოვნას. აუდიო ჩანართი ასევე ცოცხალია: ის ასახავს ჩართვას, მხოლოდ STT მოდელის ამომრჩევს Auto-ით, timeout/max-clip ლიმიტები, აუდიო მრიცხველები და `input_audio` ნიმუშის ტესტი. ვიდეო ჩანართი ფუნქციონირებს: ის იტყობინება FFmpeg/ffprobe გაშვების მდგომარეობას — ოთხი გამოკვეთილი UI მდგომარეობიდან ერთ-ერთს (`unknown` როცა ზონდი ფრენის დროს ან ვერ სრულდება, `restricted` არა-დაბრუნების დაფის ჰოსტზე, სადაც ზონდი გამოტოვებულია კლიენტის მხარეს, `unavailable` ერთხელ გამოკვლეული და დადასტურებულია, რომ აკლია, ან `available` — FFmpeg/ffprobe ფილტრების მიხედვით, ვერსიების მიხედვით) ხედვის უნარიანი მოდელები და ამჟღავნებს enable/model/frame/video/timeout მრიცხველებს.

ყოფილი Vision Bridge ბარათი AI პარამეტრებით არის თავსებადობის ბმული ახალ გვერდზე; იგი აღარ ფლობს ფორმის მეორე ასლს. Media Providers ასევე აკავშირებს Image-to-Text და Speech-to-Text სამუშაო პროცესებს Modality Bridge-ის შესაბამის ჩანართებთან, არსებული მეტყველების ტექსტის სათამაშო მოედანის ამოღების გარეშე.

**თვითმმართველობის მარყუჟის დაშვების შემოვლითი გზა:** როდესაც აღწერს ზარის მარშრუტს OmniRoute ს საკუთარი `/v1` თვითმარყუჟის (არასტანდარტული პროვაიდერის მოდელი) მეშვეობით, ქვემოთხოვნა აგზავნის `x-omniroute-admission-bypass: internal` და ავთენტიფიცირებულია გადაწყვეტილი თვითმარყუჟის რწმუნებით — ადგილობრივი `sk_omniroute` `REQUIRE_API_KEY=true` ლოკალურ რეჟიმში, ან ოპერატორის მიერ კონფიგურირებული `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env კლავიშის (#1350 deploy ზარის) კვლავ გაშვება. შემოვლითი გზა მხოლოდ იმ ზუსტი სერთიფიკატებისთვისაა დაცული, ამიტომ გარე კლიენტებს არ შეუძლიათ გამოიყენონ სათაური დაშვების გამოტოვებისთვის.

მემკვიდრეობითი ნაგულისხმევები ცხოვრობენ `src/shared/constants/visionBridgeDefaults.ts` ში; ახალი mode/task-aware/cache ნაგულისხმევი და პარამეტრების გადამწყვეტი ცხოვრობს `src/shared/constants/modalityBridgeDefaults.ts` ში. დამცავი მოაჯი ავლენს `deps` კონსტრუქტორის ვარიანტს, ასე რომ ტესტებმა შეიძლება შეიყვანონ ყალბი `getSettings` და `callVisionModel` განხორციელება.

### აუდიო ხიდი (`audioBridge.ts`) — მოდალობის ხიდი PR-3

წყვეტს აუდიო შემცველი ჩეთის მოთხოვნებს, სანამ ისინი მიაღწევენ სამიზნეს, რომელიც ცნობილია აუდიო შეყვანის მისაღებად. ის არასოდეს ცვლის ჩეთის მოთხოვნის მარშრუტს: აუდიო ნაწილები გადაიწერება არსებული OpenAI-თან თავსებადი მრავალნაწილიანი ბოლო წერტილის მეშვეობით და არჩეული ჩატის მოდელი გრძელდება ტექსტის ტრანსკრიპტებით.

ნაკადი:

1. გადაჭრით `supportsAudio` `getResolvedModelCapabilities()` მეშვეობით. იმარჯვებს აშკარა პროვაიდერის რეესტრის მეტამონაცემები, შემდეგ სტატიკური მოდელის მეტამონაცემები, შემდეგ სინქრონიზებული `modalities_input`. დეკლარირებული შეყვანის სია `audio` გარეშე არის `false`; არავითარი მტკიცებულება არ რჩება `null`. ორივე `false` და `null` ააქტიურებს კონსერვატიულ ხიდს, ხოლო `true` გვერდს უვლის მას.
2. გადაწყვიტეთ `modalityBridgeAudio*` პარამეტრები და ამოიღეთ შემაერთებელი უმაღლესი დონის აუდიო ნაწილები ყოველი გზავნილიდან საერთო `detectMediaParts()` დეტექტორის მეშვეობით. მავთულის მხარდაჭერილი ფორმებია OpenAI `input_audio`, `audio_url` და `source.media_type: "audio/*"`. ჩადგმული აუდიო აღმოჩენილია მარშრუტიზაციისთვის, მაგრამ არ არის ამოღებული შერწყმის გზაზე. სამუშაო დახურულია `modalityBridgeAudioMaxClips` ით; შემდგომი ნაწილები ხელუხლებელი რჩება.
3. პატივი ეცით კონფიგურირებულ `provider/model`, ან მიეცით ნება `selectAudioBridgeModel()`, გაიაროს `AUDIO_TRANSCRIPTION_PROVIDERS` სტაბილური კატალოგის თანმიმდევრობით და შეარჩიეთ პირველი მოდელი გამოსაყენებელი აქტიური პროვაიდერის რწმუნებით.
4. `callAudioTranscription()` გარდაქმნის base64/data-URI აუდიოს მრავალნაწილიან `file` ად, ან ჩამოტვირთავს დისტანციურ `audio_url` მხოლოდ საჯარო გამავალი მცველის მეშვეობით DNS ჩამაგრებით და 25 MB შეკრული. შემდეგ ის ფაილს POSTs და არჩეულ მოდელს ადგილობრივ `/v1/audio/transcriptions` თვითგამორკვევაში, ავთენტიფიცირებული `resolveSelfLoopBearer()` ით. არსებული ტრანსკრიფციის მარშრუტი ასრულებს რწმუნებათა სიგელების ნორმალურ ძიებას, cooldown/rate-limit დამუშავებას და პროვაიდერის გაგზავნას.
5. წარმატებული ზარები ცვლის მათ ნაწილებს `[Audio N]: <transcript>` ით. ზარები ხორციელდება `Promise.allSettled` ით: ინდივიდუალური წარუმატებლობა ინარჩუნებს აუდიო ორიგინალ ნაწილს (#4012 კონტრაქტი). თუ ყველა ზარი ვერ მოხერხდა და მიზანი დადასტურდა `supportsAudio === false`, ნაწილები ხდება `[Audio N]: (unavailable — no STT provider connected)` (#8430 კონტრაქტი). უცნობი სამიზნისთვის (`null`), ყველა მარცხის შედეგი ხელუხლებელი რჩება. მხოლოდ ტექსტის დადასტურებული სამიზნე, რომელსაც არ აქვს გამოსაყენებელი STT სერთიფიკატი, იღებს იმავე ცალსახა სტატიას ქსელის ზარის გაცემის გარეშე.

წარმატებული ტრანსკრიპტები იყენებს პროცესის მასშტაბით Modality Bridge LRU/TTL ქეშს. გასაღები აერთიანებს აუდიო მითითებას, სტაბილურ `audio-transcription` ოპერაციულ ეტიკეტს და შერჩეულ STT მოდელს; წარუმატებლობები არასოდეს ინახება ქეშში. აუდიო მცდელობები განაახლებს საერთო `bridged`, `cacheHits`, `failures` და `lastUsedAt` მრიცხველებს. ტრანსფორმირებული პასუხები ატარებს `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; ხელუხლებელი მოთხოვნები არ იღებენ აუდიო ხიდის სეგმენტს.

Runtime პარამეტრები არის DB მხარდაჭერილი და Zod-ის დამოწმება:

| გასაღები                      | ნაგულისხმევი | დიაპაზონი      |
| ----------------------------- | ------------ | -------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —              |
| `modalityBridgeAudioModel`    | `""`         | ავტო ან STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10           |

გაზიარებული ქეში რჩება `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` და `modalityBridgeCacheMaxEntries`.

### ვიდეო ხიდი (`videoBridge.ts`, `videoBridgePipeline.ts`)

წყვეტს უმაღლესი დონის ვიდეო ნაწილებს Chat Completions `messages` ში და Responses API `input` მანამ, სანამ სამიზნე გამოიძახება ცნობილი მშობლიური ვიდეო მხარდაჭერის გარეშე. მხარდაჭერილი ფორმებია `input_video`, `video_url`, `video_source`, HTTPS URLs და `data:video/*;base64,...` მონაცემები URIs. მარტივი ფაილის სახელები ტექსტში არ განიხილება, როგორც ვიდეო.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ფლობს მოთხოვნის გავლას, capability/policy შემოწმებას, თითო მოთხოვნის აგრეგაციას და პასუხების დატვირთვას. თითო ვიდეოზე მუშაობა — შეძენა, მთლიანი შედეგის ქეში, რომელიც აღწერს კადრების თანმიმდევრობას (რომელიც აერთიანებს აბონენტის მიერ გამოცხადებულ ნებისმიერ აუდიო ტრანსკრიპტს) და თითო მცდელობისას metrics/abort/cleanup — იმალება `processVideoPart` ში `videoBridgePipeline.ts` ში, გამოძახებული ერთხელ თითო ვიდეო ნაწილზე `preCall` ს მარყუჟის შიგნით. ეს მოდული ასევე განსაზღვრავს პორტის გამოკვეთილ საზღვრებს `VideoMediaBrokerPort` (ბაიტების მოპოვება და ნიმუშის ჩარჩოების ამოღება), `VideoAudioTranscriptionPort` (აბონენტის მიერ გამოცხადებული აუდიო ტრანსკრიპტის შერწყმა ნიმუშების წარწერებთან) და `VideoDrilldownPort` (მოძველებული ნედლეულის მაღაზიის ფორმა). წარმოების STT და ჩარჩოს შეკავება შედგება აღწერის პორტის გარშემო `createVideoSttAdapter` და `createVideoDrilldownAdapter` მეშვეობით; ეს უკანასკნელი იყენებს საერთო გაუმჭვირვალე სახელურის სასიცოცხლო ციკლს.

საჯარო `/v1` მოთხოვნის გზა არასოდეს ახდენს ქვეპროცესის იმპორტს ან გამოძახებას. დისტანციური ვიდეოები ჩამოტვირთულია 50 MiB ლიმიტის ქვეშ; inline base64 ვიდეოებს აქვს კონსერვატიული 36 MiB დეკოდირებული თითო ვიდეო ქუდი, ასე რომ model/messages/framing კონვერტი შეიძლება დარჩეს საჯარო JSON მოთხოვნის დაშვების ლიმიტის შიგნით 50 MiB. ინლაინ სიგრძისა და გაშიფრული ზომის შეფასებები მოწმდება განაწილებამდე. HTTPS საჭიროა თავდაპირველ დისტანციურ URL ზე და ყველა გადამისამართებაზე, არსებული მხოლოდ საჯარო გამავალი მცველის გამოყენებით DNS ჩამაგრებით. ბაიტები შემდეგ კვეთენ `POST /api/modality-bridge/video/extract` ბროკერის ზუსტ შიდა საზღვარს. ეს მარშრუტი არის როგორც `LOCAL_ONLY`, ასევე `SPAWN_CAPABLE`, იღებს მხოლოდ თითო პროცესის ავთენტიფიკაციას, სანდო მარყუჟის დაბრუნება მოთხოვნას და არასოდეს იღებს URL, ფაილური სისტემის გზას, შესრულებად ან არგუმენტების სიას. API სხეულის ზომის მილსადენი და დამმუშავებლის დამატებითი სხეულის წამკითხველი დამოუკიდებლად ახორციელებენ 50 MiB ბროკერის შეყვანის თავსახურს. მისი შემოსაზღვრული რიგი აწარმოებს თითო მოპოვებას ერთდროულად, იძლევა ოთხი მოლოდინის სამუშაოს და აფარებს მოლოდინის რეჟიმში შეყვანას 100 MiB.

ბროკერის შიგნით `ffprobe` კითხულობს კერძო ლოკალურ ფაილს; ფიქსირებული ფორმატის დასაშვები სია გამორიცხავს დასაკრავი სიის და მანიფესტის ფორმატებს. MOV ოჯახის დაშვებული კონტეინერებისთვის, MOV მონაცემთა გარე მითითებები ნაგულისხმევად გათიშული რჩება და ფიქსირებული ბრძანება არ ეთანხმება მათ. ორივე `ffprobe` და `ffmpeg` იყენებენ `file` -only პროტოკოლის თეთრ სიას, ერთ თემას, ფიქსირებულ არგუმენტებს, ჭურვის გარეშე და `PATH` დან გადაწყვეტილ შესრულებადებს. მიმაგრებული სურათის საფარის ნაკადები არ არის დაკვრადი კანდიდატები. ყველა დაკვრადი ნაკადი უნდა აკმაყოფილებდეს ლიმიტებს და აშკარად ნაგულისხმევი ნაკადი სასურველია დეტერმინისტული ყველაზე დაბალი ინდექსის სარეზერვო ნაკადამდე. ვიდეოები შეზღუდულია 600 წამით, 8192 პიქსელით თითო განზომილება და 33554432 წყაროს პიქსელით. FFmpeg ირჩევს 1–16 შუა წერტილის JPEG ჩარჩოებს, ამცირებს გრძელ კიდეს მაქსიმუმ 1024 პიქსელამდე, მცირე შენატანების გაზრდის გარეშე და არასოდეს იღებს URL. სინჯის აღება ნაგულისხმევად არის `uniform`. არასავალდებულო `scene_aware` და ექსპერიმენტული `segment_aware` პოლიტიკა ახორციელებს ერთ დამატებით ფიქსირებულ FFmpeg გადასასვლელს უკვე დადასტურებულ ლოკალურ ნაკადზე, ირჩევს შეზღუდულ `showinfo` სცენის დროის ნიშნულებს და დეტერმინისტულად ბრუნდება იმავე ერთგვაროვან შუა წერტილებზე დეტექტორის გაუმართაობის, დროის ამოწურვის, არასწორი გამომავალი ან ცარიელი კანდიდატის ნაკრების შემთხვევაში. Segment-aware რეჟიმი გამოყოფს შუა წერტილის ნიმუშებს სცენის დადასტურებული ინტერვალების პროპორციულად; სეგმენტური მტკიცებულებები და სარეზერვო ქცევა დეტალურად არის აღწერილი ქვემოთ. მყარი 16 კადრის ქუდი გამოიყენება შერჩევის შემდეგ ყველა პოლიტიკაში. როდესაც სცენაზე გათვითცნობიერებულ მოთხოვნას აქვს მხოლოდ ერთი კადრის ბიუჯეტი, ის იყენებს აქტიური სრული ვიდეოს ან ფოკუსის ფანჯრის ერთგვაროვან შუა წერტილს და აცნობებს `policyEffective: uniform`: ერთი შერჩეული სცენის ჩარჩო ვერ შეინარჩუნებს ორივე დროებით ბოლოს. აბონენტს შეუძლია სურვილისამებრ უზრუნველყოს სასრული ფოკუსის ფანჯარა (`start`/`end` წამი); საზღვრები მიმაგრებულია მედიის ხანგრძლივობაზე, შებრუნებული ან არასასრული ფანჯრები უარყოფილია და ყველა შერჩევის პოლიტიკა ხორციელდება მხოლოდ ნორმალიზებული ინტერვალის შიგნით. შედეგად მიღებული ფანჯარა შედის სინჯის მეტამონაცემებში და არასანდო აღწერილობის პრეფიქსში, ასე რომ, ქვედა დინების მოდელებს შეუძლიათ განასხვავონ ორიენტირებული ამონაწერი სრული ვადებიდან.

სემანტიკური წარწერის ფოკუსი არის ცალკე, აშკარა პარამეტრი. ნაგულისხმევი `full` ანალიზის რეჟიმი ინახავს ჩარჩოს არსებულ მოთხოვნას და არასოდეს გადასცემს მოთხოვნის ტექსტს წარწერის მოდელზე. `focused` რეჟიმში, ხიდი კითხულობს მხოლოდ უახლეს არა ცარიელი მომხმარებლის მიერ ავტორიზებულ `text`/`input_text` ს იმავე Chat-ის ან Responses კონტეინერიდან, ახდენს მის ნორმალიზებას NFC მდე, ანგრევს საკონტროლო სიმბოლოებს და თეთრ სივრცეს და ზღუდავს მას 500 Unicode კოდის წერტილამდე. ცარიელი შედეგი ბრუნდება ზუსტად `full` მოთხოვნაზე. გამოსაყენებელი მინიშნება არის სერიული, როგორც JSON გამოყოფილი არასანდო მომხმარებლის კონტექსტის ბლოკში და შეიძლება პრიორიტეტული იყოს მხოლოდ დაკვირვებადი დეტალები; მას არ შეუძლია უგულებელყოს ცალკეული გაფრთხილება მედიაში ხილული ან მოსმენილი ინსტრუქციების შესახებ. ტექსტური ფოკუსი არასოდეს არ იძლევა დასკვნებს `start`/`end` ან ცვლის დროებით სემპლერს.

#### FU-07 სტრუქტურული სეგმენტის მტკიცებულება

`segment_aware` იყენებს ერთ შემოსაზღვრულ წინასწარი ანალიზის გადასასვლელს უკვე დადასტურებულ ადგილობრივ ვიდეო ნაკადზე. ფიქსირებული ფილტრის ჯაჭვი ჯერ მასშტაბირდება მაქსიმუმ 320 პიქსელამდე, ამოიცნობს სცენის ცვლილებებს და გაყინულ ინტერვალებს, შემდეგ იღებენ ნიმუშებს 1 კადრი წამში დაბინდვის, საშუალო ლუმასა და spatial/temporal ინფორმაციისთვის. საშვი შემოიფარგლება 600 სტრუქტურული ნიმუშით, ერთი FFmpeg/filter ძაფით, იგივე `file` -only პროტოკოლისა და კონტეინერების დაშვების სიებით, 1 MiB პროცესის გამომავალი შეკვრით და მაქსიმუმ 30 წამით ბროკერის საერთო abort/deadline. ში ის არასოდეს იღებს ბრძანებას, ფილტრს, გზას ან URL მოთხოვნიდან.

სტრუქტურული მნიშვნელობები არის დეტერმინისტული შერჩევის მტკიცებულება და არა სემანტიკური ვიდეო გაგება. ისინი არ ადგენენ საგნებს, მოქმედებებს, წარწერებს, მეტყველებას ან მომხმარებლის განზრახვას. სცენისა და ყინვის საზღვრები ქმნიან სეგმენტებს; გაყინვის გაშუქება, დაბინდვა, ექსპოზიცია, სივრცითი დეტალები და დროითი ცვლილება გავლენას ახდენს მხოლოდ არსებული 1-16 ჩარჩო ბიუჯეტის განაწილებაზე. სრულად გაყინული სეგმენტი იფარება ერთ ჩარჩოზე, ხოლო არაგაყინული სეგმენტები კონკურენციას უწევენ დარჩენილი ბიუჯეტისთვის. როდესაც საზღვრები აღემატება ჩარჩოებს, ერთგვაროვანი ქრონოლოგიის დაფარვა შენარჩუნებულია, ასე რომ სწრაფი ადრეული ჭრა ვერ მალავს გრძელ მიმავალი სეგმენტს. სცენის საზღვრები გაყინვის საზღვრის 1-წამიანი ანალიზის გარჩევადობის ფარგლებში გაერთიანებულია.

ფილტრების გამოტოვება, malformed/empty მტკიცებულება, დეტექტორის შეცდომა ან შეზღუდული წინასწარი ანალიზის დრო ვერ იხსნება ზუსტად ერთიანი შუა წერტილის პოლიტიკაში. აბონენტის შეწყვეტის ან ბროკერის ვადა არ იხსნება: ის წყვეტს ფრენის დროს ქვეპროცესს, ხელს უშლის მოგვიანებით ჩარჩოს ამოღებას და კერძო დროებითი ხე ამოღებულია `finally` ში.

თითოეული ფრეიმი შემოიფარგლება 4 MiB, ყველა ნედლი ფრეიმი ერთად 23 MiB, ხოლო სერიული ბროკერის პასუხი 32 MiB. პირადი დროებითი დირექტორია ამოღებულია `finally` ში. კოლექციონერებმა უნდა შეაგროვონ პასუხები მეხსიერებაში და შეინახონ `responseDigest` პლუს მეტრიკა და დაკვირვების შეკვრა, არასოდეს უპასუხონ ტექსტს. მომხმარებელი ასევე კითხულობს მემკვიდრეობით ნედლეულ დაკვირვებებს, მაგრამ არასოდეს აკოპირებს ამ ტექსტს თავის ანგარიშებში. თითოეული დაკვირვებისთვის მიიღება ზუსტად ერთი `responseDigest` ან `rawResponseText`. დაშვებული ვერსიების სია ცარიელი რჩება უცვლელი `hold` ნაგულისხმევი. დასაშვები ჩანაწერი მოითხოვს მტკიცებულების მითითებას, პოლიტიკას, მოდელის გადახედვას, ზუსტ კანდიდატს SHA, მანიფესტის შეჯამებას და ორ განსხვავებულ გაშვებას IDs; წინააღმდეგობრივი კონტექსტები უარყოფილია. ეს მეტამონაცემები არის აუდიტის კონტრაქტი და არა მტკიცებულება იმისა, რომ მითითებული ფაილი შეიცავს ნამდვილ გაზომვებს. ნებისმიერი ჩანაწერის დამატებამდე გადახედეთ ფაქტობრივ ქვითრებს. მენეჯმენტის სტატისტიკის საბოლოო წერტილი და ვიდეო დაფა ავლენს კონსერვატიულ მზადყოფნას. მხოლოდ კონფიგურირებული მოდელის მეტსახელი არ ადგენს მის გადახედვას ან კანდიდატს SHA, ამიტომ მიმდინარე დაფა აცნობებს `HOLD` ვიდრე ხელახლა გამოიყენებს უფლებამოსილებას სხვა შესრულების კონტექსტში. ექსპლიციტური ექსპერიმენტული შერჩევა დაწინაურებისგან განცალკევებულია; ნაგულისხმევი არ იცვლება ავტომატურად.

აბონენტებს შეუძლიათ დაურთონ არჩევითი `transcript.cues` მასივი მხარდაჭერილ ვიდეო ნაწილზე, როცა უკვე ფლობენ გასწორებულ ტექსტს. თითოეულ ნიშანს უნდა ჰქონდეს `text`, სასრული `start`/`end` ინტერვალი შემოწმებული ხანგრძლივობის შიგნით და თეთრ სიაში შეტანილი `source` (`client`, `embedded` ან `audio-bridge`); `confidence` ნაგულისხმევია `1` და უნდა დარჩეს `0` და `1` შორის. ზუსტი დუბლიკატი მინიშნებები იშლება. OmniRoute არასოდეს იწყებს ტრანსკრიფციას ამ მეტამონაცემებიდან: დადასტურებული მინიშნებები კოპირდება აღწერილ შედეგში წყაროსთან, ნდობითა და ინტერვალით და გადაიცემა როგორც არასანდო დაკვირვებები კადრის წარწერებთან ერთად. არასწორი, დიაპაზონის გარეთ ან წარმოშობის გარეშე ტექსტი უარყოფილია, ვიდრე შერეული სუბტიტრების ნაკადში. ორივე მოთხოვნის სხეულის ტრანსკრიპტის არხი ახდენს მიწოდების წარმოშობის ნორმალიზებას `client` სთვის, მათ შორის თვითდამტკიცებული `embedded` ან `audio-bridge` ლეიბლების ჩათვლით. მხოლოდ სერვერის მფლობელობაში მყოფ ადაპტერს შეუძლია მინიჭოს ეს სანდო ლეიბლები მხოლოდ კოდის `trustedSource` არგუმენტით; მოთხოვნის JSON ველი ვერ აღწევს ამ არგუმენტს. ტრანსკრიპტის ტექსტი რჩება არასანდო მედიისგან მიღებული კონტენტი, მიუხედავად მისი წარმოშობისა და არასოდეს უნდა განსაზღვროს ავტორიზაცია.

მოწინავე აბონენტმა შეიძლება უზრუნველყოს `audioTranscript` ტრეკი იმავე ვიდეოსთვის; ის განიხილება როგორც კლიენტის მიერ მოწოდებული ტექსტი და არა სერვერის ტრანსკრიფციის დამადასტურებელი. fusion seam აწარმოებს ვიზუალურ და აუდიო დაკვირვებებს ერთი ვადის ქვეშ და აჩერებს სიგნალს, აწესრიგებს მათ საერთო ვადაზე, არღვევს ზუსტ დუბლიკატებს და აცნობებს ნაწილობრივ შედეგს, როდესაც მხოლოდ ერთი მხარე წარმატებას მიაღწევს. არასწორი `audioTranscript` მცირდება ამ ნაწილობრივ შედეგამდე. — ვიზუალური აღწერილობა ინახება და აუდიო ფილიალი ჩაწერს გაწმენდილი უკმარისობის კოდს — მთლიანი ვიდეოს ჩავარდნის ნაცვლად. თითო ფილიალზე ხელმისაწვდომობა, ნაწილობრივი დროშა და გაწმენდილი უკმარისობის კოდები დაცულია აღწერილ შედეგში, დამცავი რელსების მეტამონაცემებში (`audioFusionRuns`/`audioFusionPartials`/ `audioFusionFailureCodes`), შედეგების ქეში მეტამონაცემებში და ხიდის შერწყმის მრიცხველებში. ნაგულისხმევი ვიდეო ხიდის ბილიკი არ იწვევს მეტყველების ტექსტს ან არ ჩამოტვირთავს მეორე მედიის ასლს; ამ აშკარა ტრეკის გარეშე, ის რჩება მხოლოდ ვიდეოზე.

**ტრანსკრიპტის შენახვა (#12150 P1).** ეს ავტომატურად მოქმედებს, როდესაც ვიდეო ხიდი (თვითონ ჩართვა) ასახავს ტრანსკრიპტის მინიშნებას — ცალკე შენარჩუნების დროშა არ არის. როდესაც მოთხოვნა წარმოქმნის რაიმე ტრანსკრიპტის სიგნალს (დარეკვის მიერ გამოცხადებული `transcript` ან შერწყმული `audioTranscript`), დამცავი მოაჯირი აღნიშნავს მას `videoBridgeObserved` და აწარმოებს ვიდეოს აღწერილობის რედაქტირებულ ჩრდილს — იდენტურ რენდერირებას, რომელშიც თითოეული სიგნალის თავისუფალი ტექსტის სხეული იცვლება `[redacted-video-transcript]` ით, რომელიც აგებულია ველის სტრუქტურის აწყობამდე. გაბრტყელებული ტექსტი, ასე რომ, არ შეიძლება გადარჩეს ცილის შემცველობა — წინააღმდეგობრივი ან ჩვეულებრივი, მათ შორის `]` შემცველი ორგანოები, როგორიცაა `[inaudible]`/`[music]` —. მუდმივი ზარის ჟურნალის მოთხოვნის ძირითადი ნაწილი ცვლის ვიდეოდან მიღებულ ტექსტის თითოეულ ნაწილს იმ რედაქტირებულ ჩრდილში, რომელიც შეესაბამება შინაარსის თანასწორობას; `fullText` წამყვანი ხელახლა იკითხება წინასწარ გამოძახების დასრულებული დამცავი სარკინიგზო დატვირთვიდან, ასე რომ, მატჩი მაინც წარმატებულია მას შემდეგ, რაც მოგვიანებით ჯაჭვის დამცავი მოაჯირები ( PII და რწმუნებათა სიგელების მასკერები, პრიორიტეტები 10/95) გადაწერენ აღწერილობის ტექსტს ადგილზე და system-prompt/handoff/memory ინექციის შემდეგ შეცვლიან შეტყობინებების მასივს. მოდელის ზემოთ გაგზავნილი სხეული უცვლელია. დაკვირვებული მოთხოვნა ასევე არ შეიცავს გამძლე მეხსიერებას (როგორც მოთხოვნის, ასევე პასუხის შედეგად მიღებული ამონაწერი გამოტოვებულია), ასე რომ, მოდელის პასუხი არ შეუძლია ტრანსკრიპტის ტექსტის მეხსიერების გამეორებას მეხსიერებაში.

**ნედლი ვიდეო ველები (#12430).** როდესაც ხიდი ჩართულია და მშობლიური ვიდეო მხარდაჭერა უცნობია ან არ არსებობს, განსაზღვრული `transcript`/`audioTranscript` ველები ასევე ააქტიურებს `videoBridgeObserved`, აღწერის წარუმატებლობის ან `maxVideos` ლიმიტის შემდეგაც კი. `null` და ცარიელი სტრიქონების რაოდენობა; არ არსებობს ველები და არა ვიდეო მეტამონაცემები. შენახული ასლები ასწორებენ ამ ველებს ან გამოტოვებენ მოთხოვნას და caches/Memory გვერდის ავლით ხდება.

ამ სარეზერვო ბილიკებზე, აბონენტის მოქმედი მინიშნებები ხდება მხარდაჭერილი `text`/`input_text` ნაწილები, ვიდრე არასტანდარტული პროვაიდერის ველები. მოთხოვნით მიწოდებული ორივე ჩანაწერი რჩება არასანდო `client` დაკვირვებებად, აშკარა გაფრთხილებით, რომ ვიდეო არ იყო აღწერილი და დროის ანაბეჭდები არ იყო დამოწმებული მედიის მიმართ. არსებული 256-cue/64-KiB ჯამური და per-cue ბიუჯეტები ვრცელდება ორ ტრასაზე ერთად; დროის ანაბეჭდები უნდა შეესაბამებოდეს ბროკერის 600 წამიან ჭერს და ნებისმიერ მიწოდებულ ფოკუსის ფანჯარას. არასწორი ჩანაწერები გაუქმებულია, არ არის გადაგზავნილი, როგორც თვითნებური ტექსტი; მოქმედი და-ძმა შეიძლება კვლავ იყოს გამოყენებული, თუ მათი ერთობლივი ბიუჯეტი არ გადააჭარბებს. საზიარო მაღაზია არის პროცესის ლოკალური: სახელურები იწურება გადატვირთვისას და არ არის გადაცემული დამოუკიდებელ OmniRoute პროცესებს შორის. მენეჯმენტის სტატისტიკა ავლენს ეფექტურ შეკავებას/დისტანციურ პოლიტიკას და აერთიანებს მხოლოდ შენახულ entries/bytes, არასოდეს მედიას, ცნობებს, ძირითად IDs ან სახელურებს. ვიდეოს პარამეტრების პანელი აჩვენებს ამ მნიშვნელობებს და შეიძლება შენარჩუნდეს ორივე თანხმობის გადამრთველი. განხორციელების ეს დოკუმენტაცია არ არის პირდაპირი განლაგების ან ხელშეწყობის მტკიცებულება; რეალური მოდელის მიღებას ცალკე აკონტროლებენ.

კადრებს თანმიმდევრულად ეწერება კონფიგურირებული ვიდეო მოდელი. ცარიელი ვიდეოს გადაფარვა მემკვიდრეობით იღებს Vision პარამეტრს; თუ ორივე ცარიელია, Vision ავტომატური როუტერი ირჩევს ეფექტურ ხედვის შესაძლებლობის მოდელს. წარმატებულმა წარწერებმა ორიგინალურ ნაწილს შეცვალა სტაბილური `[Video description:` პრეფიქსი, რომელიც ასევე აღნიშნავს ტექსტს, როგორც არასანდო მედიის დაკვირვებას და ეუბნება ქვედა დინების მოდელებს, არ დაიცვან მედიაში ნაპოვნი ინსტრუქციები. ქეშის კადრების წარწერის კლავიშები მოიცავს JPEG ბაიტებს, მოთხოვნას, დროის ნიშანს და ეფექტურ მოდელს; მხოლოდ წარმატებული წარწერები ინახება ქეშში. ქეში ჩანაწერები ინარჩუნებს რეალურ წარმატებულ პროდიუსერის მოდელს, მათ შორის სარეზერვო მოდელს; ხიდი იტყობინება `mixed` როდესაც სხვადასხვა მოდელის მიერ წარმოებული სხვადასხვა ჩარჩოები. ქეში დარტყმა ხელახლა იყენებს ამ პროდიუსერის იდენტიფიკაციას იმის ნაცვლად, რომ ხელახლა მოაწეროს ის, როგორც მოთხოვნილი მარშრუტიზაციის გეგმა. მთლიანი ვიდეოს შედეგების ქეში ჩართულია ყველა შეყვანაზე, რომელიც ცვლის გამომავალ — მოთხოვნას, ეფექტურ მოდელს, შერჩევის პოლიტიკას, კადრების რაოდენობას, სემანტიკური ანალიზის რეჟიმს, ნორმალიზებული ფოკუსის მინიშნების SHA-256 თითის ანაბეჭდს, ფოკუსის ფანჯარას, `transcript`, `audioTranscript` და საკონტაქტო ფურცლის დროშას —, ასე რომ, ამ განზომილების შეცვლა არასოდეს არ არის ქეში ხელახლა გამოყენება. ვიზუალური წაშლის პოლიტიკის ვერსია, ბარიერი და შეზღუდული კანდიდატის ჩარჩოების რაოდენობა ასევე აშკარაა შედეგის ქეშის გასაღებსა და მეტამონაცემებში; შესაბამისად, პოლიტიკის ცვლილება არ შეიძლება ხელახლა გამოიყენოს შემორჩენილი მთლიანი ვიდეო აღწერილობა. Result-cache v4 მეტამონაცემები ინარჩუნებს რეჟიმს და თითის ანაბეჭდს და არასოდეს არის მომხმარებლის დაუმუშავებელი დავალება. Guardrail მეტამონაცემები იუწყება როგორც მოთხოვნილი, ასევე ეფექტური ანალიზის რეჟიმებს; მოთხოვნილი `focused` რეჟიმი გამოსაყენებელი მომხმარებლის ტექსტის გარეშე მოხსენებულია, როგორც ეფექტურად `full`.

დამცავი მოაჯი ამოაქვს ყველა მხარდაჭერილ ვიდეო ნაწილს, მაგრამ აღწერს არაუმეტეს `modalityBridgeVideoMaxVideos`. იმისათვის, რომ სამიზნე დადასტურდეს, რომ აქვს `supportsVideo === false`, წარუმატებელი და ზედმეტად ლიმიტირებული ვიდეოები ხდება აშკარა უსაფრთხო ტექსტის მარკერები, ასე რომ არცერთი ნედლი ვიდეო არ გადარჩება. როდესაც შესაძლებლობები უცნობია, ეს ნაწილები ინარჩუნებენ ვიდეო ოპერატორს; ნებისმიერი სარეზერვო ტრანსკრიპტი მიჰყვება ზემოთ შემოსაზღვრული ტექსტის კონვერტაციას. `supportsVideo === true` სამიზნეები ხიდს გვერდის ავლით. კლიენტის მოთხოვნის შეწყვეტის სიგნალი ვრცელდება ჩამოტვირთვის, ბროკერის რიგის, ქვეპროცესების და წარწერის ზარების მეშვეობით; წყვეტს გაჩერებას ვიდეოებს შორის და არასოდეს იშლება ღია მედიისთვის.

### PII Masker (`piiMasker.ts`)

ეშვება** ორივე** ეტაპები.

- **`preCall`** კლონირებს დატვირთვას, დადის `system`, `messages`, `input` და `prompt` (მათ შორის უბრალო სიმებიანი ელემენტები) და იყენებს `processPII()` ( `@/shared/utils/inputSanitizer` დან) სიმებიანი `content`/`text` ველებზე. როდესაც `PII_REDACTION_ENABLED=true`, აღმოჩენილი PII რედაქტირდება გამავალ დატვირთვაში. ეს დამოუკიდებელია `INPUT_SANITIZER_MODE` ისგან (რომელიც მხოლოდ აკონტროლებს სწრაფი ინექციის პოლიტიკას). როდესაც რედაქცია გამორთულია, ზარის ჩანაწერების აღმოჩენა ითვლის კონტენტის გადაწერის გარეშე.
- **`postCall`** ღრმად კლონირებს პასუხს, აწარმოებს `sanitizePIIResponse()` პლუს Responses-API-shape masker (`maskResponsesOutput` — მოიცავს `output_text` და `output[].content[].text`). თუ რაიმე რედაქცია მოხდა, შეცვლილი პასუხი ცვლის ორიგინალს.

დამცავი მოაჯირი არასოდეს იკეტება; ის მხოლოდ ანოტაციას აკეთებს (`meta.detections`, `meta.redacted`) ან ხელახლა წერს.

**შექცევადი სარდაფი (`PII_REVERSIBLE_VAULT_ENABLED`, ნაგულისხმევი `false`).** როდესაც `PII_REDACTION_ENABLED` და `PII_REVERSIBLE_VAULT_ENABLED` ჩართულია (DB override > env > ნაგულისხმევი, წაიკითხეთ ერთხელ მოთხოვნაზე), `handleChat` ხსნის ერთ სარდაფს კლიენტის მოთხოვნაზე (`src/lib/pii/requestTokenVaultScope.ts`) და გადასცემს მას წინასწარ გამოძახების საშვს, როგორც `GuardrailContext.tokenVault`. შემდეგ მასკერი წერს სუროგატ ჟეტონებს, როგორიცაა `<<PII_EMAIL_QWERTYUI_1>>` `[EMAIL_REDACTED]` ნაცვლად, ჩაშენებული, დადასტურებული (GDPR/POPIA) და მორგებული წესებისთვის. Nonce არის 8 შემთხვევითი დიდი ასო თითო მოთხოვნაზე, და იგივე მნიშვნელობა იღებს იგივე ნიშანს მოთხოვნის ფარგლებში. მხოლოდ ნიღბიანი ზარაფხანა: სწრაფი ინექციის დამცავი და `/api/guardrails/test` მუშაობს სარდაფის გარეშე და ინარჩუნებს ადგილს.

- პროვაიდერი, ყველა კომბინირებული ფეხი, ხელახალი ცდა, შერწყმის პანელის წევრი და შერწყმის მსაჯი ხედავენ მხოლოდ ჟეტონებს. ჟეტონები აღდგება ერთხელ, 2xx პასუხზე, რომელიც ტოვებს `handleChat`: თითო ველში გაანალიზებულ SSE ზე (მოვლენებზე გაყოფა კვლავ წყდება; ხელსაწყოების გამოძახების არგუმენტები JSON-ის გაქცევით) ან თითო ველზე JSON სხეულზე, ხელახლა გამოთვლილი `Content-Length`. შიგთავსი და დასაბუთებული ტექსტი და ხელსაწყო-ზარის არგუმენტები აღდგენილია. შეცდომის ორგანოები (4xx/5xx) ინახავს ტოკენებს.
- წარუმატებლობები რჩება პირადი: თუ მოჭრა ვერ მოხერხდა ან სარდაფი უარს იტყვის მნიშვნელობაზე (1000 ჩანაწერი, 256 სიმბოლო თითო მნიშვნელობაზე, ჯამში 64 KB ), ჩანაცვლების ადგილი იწერება; ნიშანი, რომელსაც სარდაფი ვერ აგვარებს, ან აღდგენა, რომელიც ვერ ხერხდება, რჩება სიტყვასიტყვით და მხოლოდ რაოდენობა აღირიცხება. სარდაფში არ არის ტაიმერები და გლობალური მდგომარეობა; ის წაშლილია, როდესაც პასუხის ნაკადი მთავრდება, გაუქმდება ან შეცდომებს.

#### თითო ტიპის შერჩევა, მორგებული შაბლონები და გამოვლენის მრიცხველები

**დაფის → პარამეტრები → უსაფრთხოება → PII ნიღაბი** ირჩევს _ რა არის ნიღბიანი. ის არ რთავს ნიღბვას: ეს ისევ არის `PII_REDACTION_ENABLED` (მოთხოვნა) და `PII_RESPONSE_SANITIZATION` (პასუხი + SSE), ორივე ნაგულისხმევად გამორთულია.

- **თითო ტიპის შერჩევა** — ჩაშენებული id-ები ჩამოთვლილია `src/shared/constants/piiTypes.ts` ში (`PII_BUILTIN_TYPES`). Unset ნიშნავს ყველა ტიპს (ქცევა ამ პარამეტრამდე არსებობდა). მოთხოვნის ძრავის `ssn_us` ნიმუში რუკაზე `ssn`. შაბლონები (მინიმალური, სტანდარტული, ფინანსური, ბრაზილიური, USA, GDPR, POPIA, სრული) ავსებენ მხოლოდ UI ველებს.
- **GDPR და POPIA იდენტიფიკატორები** — თორმეტი ჩაშენებული ID, რომელიც მოიცავს EU და სამხრეთ აფრიკის პირად იდენტიფიკატორებს (ქვემოთ ცხრილი). მათი რეგექსები, ვალიდატორები და იურისდიქციის ტეგები ცხოვრობენ ერთ ცხრილში, `src/shared/utils/piiPatterns.ts`, რომელსაც მოიხმარს როგორც პასუხის გამაჯანსაღებელი (`src/lib/piiSanitizer.ts`) ასევე მოთხოვნის მასკერი (`src/shared/utils/inputSanitizer.ts`). შესატყვისი რედაქტირდება მხოლოდ მაშინ, როდესაც მისი ვალიდატორი მიიღებს მას; ციფრების შიშველი რაოდენობა არასდროს არის საკმარისი. ოპერატორი, რომელმაც შეინახა შევიწროებული არჩევანი ამ id-ების არსებობამდე, ინარჩუნებს ქცევას, რაც მას ჰქონდა, სანამ ახალი id-ების მონიშვნა არ მოხდება.
- **მორგებული ნიმუშები** — 20-მდე რეგექსის ან ბუნების შაბლონი (`*` = 64-მდე არა თეთრი სივრცის სიმბოლო, `?` = ერთი). მატჩები ხდება `[CUSTOM_REDACTED]`. ყველა ნიმუში გადის `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`): მაქსიმუმ 500 სიმბოლოს, დროშები შემოიფარგლება `g i m s u` ით, უნდა იყოს კომპილირებული, უნდა გაიაროს `safe-regex` (კატასტროფული უკან დახევა) და არ უნდა ემთხვეოდეს ცარიელ სტრიქონს ან რედაქციის ჩანაცვლების ველს. წარუმატებელი შაბლონი უარყოფილია შენახვისა და ტესტირებისას, ხოლო შენახული მწკრივი, რომელიც წარუმატებელია, გამოტოვებულია გაშვების დროს, კომპილაციის ნაცვლად. მორგებული შაბლონები მუშაობს მხოლოდ მაშინ, როცა ნიღაბი ჩართულია.

### სწრაფი ინექცია (`promptInjection.ts`)

აღმოაჩენს მოწინააღმდეგე სტრუქტურებს მომხმარებლის მიერ მოწოდებულ კონტენტში და ახორციელებს კონფიგურირებულ პოლიტიკას. ქცევა განპირობებულია გარემოს ცვლადებით და კონსტრუქტორის ვარიანტებით:

| დაყენება       | Env var                                                                                                       | ნაგულისხმევი | ეფექტი                                                                                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ჩართულია       | `INPUT_SANITIZER_ENABLED`                                                                                     | `true`       | როდესაც `false`, დამცავი მოაჯირები მოკლე ჩართვაა.                                                                                                                                                   |
| რეჟიმი         | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                               | `warn`       | ინექციის პოლიტიკა: `block`, `warn` ან `log`. (`redact` მიიღება უკანა კომპატისთვის, მაგრამ ასეა** არა** ზოლის საინექციო ტექსტი; PII გადაწერის მოთხოვნა კონტროლდება `PII_REDACTION_ENABLED` ის მიერ.) |
| ბლოკის ბარიერი | `blockThreshold` ვარიანტი / `INPUT_SANITIZER_BLOCK_THRESHOLD` (სხვა სახელი `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | ბლოკირებისთვის საჭირო მინიმალური სიმძიმე. ნაგულისხმევად საშუალო არის მხოლოდ დაკვირვება.                                                                                                             |

**რეჟიმის უპირატესობა** (`getMode`): გამრეკელი `options.mode` → `INJECTION_GUARD_MODE`**DB ფუნქცია-დროშის გადაფარვა** (დაფა → პარამეტრები → ფუნქციების დროშები) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env → `warn`. ამიტომ, დაფის გადახურვა იგებს env vars-ს, ამიტომ Feature Flags UI აკონტროლებს გაშვებულ მცველს პირდაპირ ეთერში (არ გადატვირთვა). DB წაკითხვა უსაფრთხოა წარუმატებლობისთვის: თუ ის შეცდომებს უშვებს, მცველი უბრუნდება env-ზე დაფუძნებულ ქცევას და როდესაც არ არის დაყენებული override, ქცევა იდენტურია env-მხოლოდ გარჩევადობის.

გამოვლენის წყაროები:

1. `sanitizeRequest()` `@/shared/utils/inputSanitizer` დან (საზიარო დეტექტორების ნაკრები გამოიყენება მილსადენის სხვაგან).
2. ჩაშენებული `DEFAULT_GUARD_PATTERNS` (ამჟამად `system_override_inline` და `markdown_system_block`, ორივე `high` სიმძიმის).
3. არასავალდებულო `customPatterns` გადაცემულია კონსტრუქტორის ოფციების მეშვეობით (სტრიქონები, რეგექსი ან `{ name, pattern, severity }` ჩანაწერები).

როცა `mode === "block"`** და** მინიმუმ ერთი აღმოჩენა აკმაყოფილებს სიმძიმის ზღვარს, `preCall` აბრუნებს `{ block: true, message: "Request rejected: suspicious content detected" }`. `warn`/`log` რეჟიმებში დამცავი მოაჯირები იწერება, მაგრამ ზარის საშუალებას იძლევა. გაზიარებული დამხმარე `evaluatePromptInjection()` ასევე ექსპორტირებულია იმ აბონენტებისთვის, რომლებმაც უნდა შეაფასონ მოთხოვნები რეესტრის გავლის გარეშე.

**სკანირება შეკრული (v3.8.20):** დეტექტორი მხოლოდ ამოწმებს** პირველი 16 KB** შეერთებული მოთხოვნის ტექსტი — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ბაიტი) `src/shared/utils/inputSanitizer.ts` ში. როგორც `detectInjection()`, ასევე `evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` ნიმუშის მარყუჟის გაშვებამდე. საინექციო დირექტივები განთავსებულია შეყვანის ზედა ნაწილთან, ასე რომ, ეს ზღუდავს regex CPU/GC მრავალ ასეულ კბაიტიან დატვირთვაზე შესუსტების გამოვლენის გარეშე (შდრ. #3932, #4041).

### სერთიფიკატის მასკერი (`credentialMasker.ts`)

ეშვება** ორივე** ეტაპები, ბოლო ნაგულისხმევ ჯაჭვში (პრიორიტეტული `95`). ასწორებს კარგად ცნობილ API გასაღების / საიდუმლო ნიშნის შაბლონებს გამავალი დატვირთვიდან (შეტყობინებების შინაარსი, ხელსაწყო-ზარის არგუმენტები, ხელსაწყოს შედეგები)** და** პროვაიდერის პასუხი, ამიტომ მოთხოვნაში ჩასმული რწმუნებათა სიგელები (ან ეხმიანება ხელსაწყოს შედეგით) არ არის გაჟონილი ზედა დინების პროვაიდერთან ან უკან კლიენტთან.

- **მხოლოდ ჩართვა** , იგივე კონვენცია, როგორც PII რედაქცია (მყარი წესი #20- მიმდებარე): გამორთულია, თუ `settings.credentialRedactionEnabled === true`** ან** `CREDENTIAL_REDACTION_ENABLED=true`. როდესაც ის გამორთულია, დამცავი მოაჯი არ არის ოპტიმალური — ის არასოდეს იბლოკება და არასოდეს იწერება.
- `redactCredentials()` დადის სრულ payload/response ხეზე (`walkValue()`, პროტოტიპი-დაბინძურება-უსაფრთხო, ციკლი-უსაფრთხო მეშვეობით `WeakSet`) და ცვლის მატჩებს `[REDACTED:<type>]` ჩანაცვლებით, კლონირებს მხოლოდ იმ ტოტებს, რომლებიც რეალურად შეიცვალა.
- `CREDENTIAL_PATTERNS` მოიცავს LLM პროვაიდერის კლავიშებს (OpenAI, OpenAI-proj, Anthropic, Google, ჩახუტებული სახე, რეპლიკატი), VCS/SaaS ჟეტონებს (GitHub, Slack, ხაზოვანი, Notion, npm, ფოსტალიონი, Discord), გადახდის გასაღებები (AWS, Square), ღრუბლოვანი გასაღებები (Twickl, წვდომა SendGrid). JWTs, სერთიფიკატის შემცველი კავშირის სტრიქონები (`mongodb://user:pass@...` და ა.შ.) და ზოგადი `Authorization`/`x-api-key`/`api-key`/`apikey` სათაურის მნიშვნელობის ნიმუში. სათაურის ფორმის კლავიშები (`authorization`, `x-api-key`, `api-key`, `apikey`) რედაქტირდება სტრუქტურულად (მხოლოდ მნიშვნელობა, სქემის პრეფიქსი, როგორიცაა `Bearer `/`Basic ` შენახული) და არა ზოგადი ტექსტის რეგექსის მეშვეობით.
- დამცავი მოაჯირი არასოდეს იკეტება; ის მხოლოდ ხელახლა წერს (`modifiedPayload` / `modifiedResponse`) და ანოტაციას აკეთებს (`meta.credentialsRedacted`, `meta.count`).

რეგრესიის მცველი: `tests/unit/credential-masker-guardrail.test.ts`.

## საბაზო კონტრაქტი (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true მოკლედ წყვეტს ჯაჭვს
  message?: string; // გამოჩნდება დაბლოკვისას
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // preCall-ის მიერ დაბრუნებული მოთხოვნის გადასაწერად
  modifiedResponse?: TValue; // postCall-ის მიერ დაბრუნებული პასუხის გადასაწერად
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail-ი „ცვლილების არარსებობის" სიგნალს იძლევა `void`-ის, `{}`-ის ან
`{ block: false }`-ის დაბრუნებით. `modifiedPayload`/`modifiedResponse`-ის დაბრუნება
ცვლის მნიშვნელობას, რომელიც მიმდინარეობს ჯაჭვში შემდგომი guardrail-ებისთვის.
`signal?: AbortSignal` გამომძახებლის სასიცოცხლო ციკლს ატარებს guardrail-ებში. მოთხოვნის
შეწყვეტა (abort) არის განზრახ fail-open გამონაკლისი: მედია ხიდები წყვეტენ მუშაობას და
ასუფთავებენ რესურსებს ნედლი მედიის იმ მიზნისთვის დაბრუნების გარეშე, რომელზეც ცნობილია,
რომ მისი მხარდაჭერა არ შეუძლია.

## რეესტრი (`registry.ts`)

სინგლტონი `guardrailRegistry` ამჟღავნებს:

- `register(guardrail)` — ამატებს (ან ნორმალიზებული სახელით ცვლის) guardrail-ს და
  ხელახლა ალაგებს `priority`-ის ზრდადობით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარეები.
- `runPreCallHooks(payload, context)` — გადაუვლის აქტიურ guardrail-ებს, ატარებს
  payload-ს `modifiedPayload`-ით და ჩერდება პირველ `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე ნაკადი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და
  სურვილისამებრ ხელახლა არეგისტრირებს ნაგულისხმებებს სუფთა ტესტის იზოლაციისთვის.

ორივე გამშვები აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც მოიცავს
თითოეული guardrail-ის `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც სასარგებლოა ტრასირებისთვის.

### Guardrail-ების გამორთვა თითო მოთხოვნის მიხედვით

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აგრეგავს guardrail-ების
სახელების დედუპლიკირებულ სიას, რომლებიც უნდა გამოიტოვოს მიმდინარე მოთხოვნისთვის.
არსებობს ხუთი არხი, რომლებიც იკითხება ამ თანმიმდევრობით და ერთ სიაში ერთიანდება
(დედუპლიკაციისას პირველი შემთხვევა იგებს):

1. `apiKeyInfo.disabledGuardrails`
2. მოთხოვნის სხეულის `disabledGuardrails` (უმაღლესი დონის)
3. მოთხოვნის სხეულის `metadata.disabledGuardrails` (მხოლოდ მაშინ, როდესაც `metadata` ობიექტია)
4. ჰედერი `x-omniroute-disabled-guardrails`
5. მოძველებული ჰედერი `x-disabled-guardrails`

ყველა ხუთი არხი ერთიანდება, ორი ჰედერის ჩათვლით: ორივე
`x-omniroute-disabled-guardrails`-ისა და `x-disabled-guardrails`-ის გაგზავნა გამოტოვებს
მათი სიების გაერთიანებას, ხოლო ცარიელი თანამედროვე ჰედერი აღარ მალავს მოძველებულს
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), გასწორდა
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)-ში).

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივი ან მძიმით გამოყოფილი სტრიქონი; სახელები
იჭრება და ნორმალიზდება პატარა ასოების kebab-case ფორმატში (`pii_masker` → `pii-masker`),
ხოლო ცარიელი ჩანაწერები გამოირიცხება. შედეგი გადაეცემა რეესტრს `context.disabledGuardrails`-ის
მეშვეობით, რომელიც გამოტოვებს შესაბამის guardrail-ებს (`skipped: true` `results`-ში).

გამორთვის სია მოქმედებს მხოლოდ **რეესტრზე**. Prompt-injection-ის `block` რეჟიმი
სავალდებულო საზღვარია: injection-guard middleware
(`src/middleware/promptInjectionGuard.ts`) იძახებს `evaluatePromptInjection()`-ს
ყოველგვარი გამომძახებლის მიერ კონტროლირებადი გამორთვის სიის გარეშე (მკვდარი
`resolveDisabledGuardrails({ body })` გამოძახება, რომელსაც ის ადრე აკეთებდა, წაიშალა
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)-ში), ამიტომ მოთხოვნა,
რომელიც თიშავს `prompt-injection`-ს, მაინც უარსაცდება `block` რეჟიმში. ეს განზრახ
არის ასე დაპროექტებული. გამორთვის არხები გამომძახებლის მიერ არის კონტროლირებადი
(მოთხოვნის სხეული, მეტამონაცემები, ჰედერები), და გამომძახებელმა არ უნდა შეძლოს
ოპერატორის მიერ დაყენებული უსაფრთხოების კონტროლის გამორთვა

## აღსრულების ბრძანება

თითოეული მოთხოვნისთვის, რომელიც მიედინება `src/sse/handlers/chat.ts` და `open-sse/handlers/chatCore.ts` ში (ჩეთის ოჯახის მარშრუტები, რომლებიც ჩამოთვლილია [დაფარვისა და შეზღუდვების](#coverage-and-limits) ქვეშ):

1. `resolveDisabledGuardrails(...)` აშენებს გამოტოვების სიას API კლავიშიდან, ტექსტიდან და სათაურებიდან.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` გადის დამცავ მოაჯირებს აღმავალი პრიორიტეტის მიხედვით:
   - შეზღუდული შესაძლებლობის მქონე დამცავი მოაჯირები აღირიცხება როგორც `skipped`.
   - ყოველი დამცავი სარკინიგზო `preCall` ს შეუძლია გადაწეროს დატვირთვა `modifiedPayload` საშუალებით.
   - პირველი `block: true` ახდენს ჯაჭვის მოკლე ჩართვას და დამჭერი უბრუნებს დამცავი რელსების უარყოფის პასუხს.
3. (პოტენციურად გადაწერილი) ტვირთამწეობა მიედინება კომბინირებულ მარშრუტში და ზემო დინებაში.
4. **მხოლოდ არასტრიმინგისთვის:** პასუხის აწყობის შემდეგ, `guardrailRegistry.runPostCallHooks(...)` აწარმოებს იმავე ჯაჭვს პასუხზე. `block: true` აქ ჩამოაგდებს ზემოთ ნაკადის პასუხს და აბრუნებს HTTP 400-ს. სტრიმირებული პასუხები მთლიანად გამოტოვებს ამ საფეხურს.
5. **მხოლოდ შექცევადი სარდაფი:** როდესაც მოთხოვნით ფორმდება ტოკენები, `handleChat` აღადგენს მათ 2xx პასუხზე, რომელიც მას უბრუნდება, ზარის შემდგომი კაუჭებისა და სტრიმინგის PII ტრანსფორმაციის შემდეგ, ასე რომ, `PII_RESPONSE_SANITIZATION` ხედავს ტოკენებს და მოდელის მიერ გენერირებულ PII, არასოდეს აღდგენილ ორიგინალს.

დამცავი რელსები, რომლებიც ისვრიან, ჩაიწერება `error: <message>` ით და იწერება `logger.warn` მეშვეობით, მაგრამ ჯაჭვი გრძელდება — ავარიულად გახსნა დიზაინის მიხედვით.

### რაც არ არის დაფარული

- **მედია, ჩაშენებები და მონაცემთა მარშრუტები** (`/v1/images/*`, `/v1/embeddings`, `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/rerank`, `/v1/search`, `/v1/moderations`) არასოდეს მიაღწევთ რეესტრს. იქ არ გადის PII masking, სერთიფიკატის დამალვა ან მოდალობის ხიდი. მათი ერთადერთი შემოწმება არის ძველი საინექციო მცველი შუა პროგრამა.
- **სტრიმირებული პასუხები** არ მიიღოთ ზარის შემდგომი დამცავი ღობე: არც `pii-masker` ან `credential-masker` ზარის შემდგომი და არც ზარის შემდგომი ბლოკი. მოქმედებს მხოლოდ ნაკადის PII ტრანსფორმაცია (როდესაც `PII_RESPONSE_SANITIZATION` ჩართულია). სტრიმინგებულ პასუხში გამოხმაურებული რწმუნებათა სიგელები არ არის რედაქტირებული.
- **გამორთეთ არხები შუაპროგრამის წინააღმდეგ (დიზაინის მიხედვით):** Middleware აფასებს სწრაფ ინექციას `evaluatePromptInjection()` ზე საკუთარი გამოძახებით, აბონენტის მიერ კონტროლირებადი გამორთვის სიის გავლის გარეშე. `block` რეჟიმი არის სავალდებულო ზღვარი, რომელსაც აბონენტის მიერ კონტროლირებადი გამორთვა არ შეუძლია გვერდის ავლით, მათ შორის ჩეთის ოჯახის მარშრუტებზე ( [#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413) ). `prompt-injection` გამორთვა გამოტოვებს მხოლოდ რეესტრის დამცავ სარტყელს.

### რა ხედავს პასუხს ზარის შემდგომ

არასტრიმინგ გზაზე ბრძანება არის: მეხსიერების ამოღება → ჩაშენებული ხელსაწყოს შესრულება → ზარის შემდგომი დამცავი ზოლები → ზარის შემდგომი ბლოკი გასვლა → სემანტიკური ქეშის საცავიდან.

- **მეხსიერების ამოღება** და** ინსტრუმენტის შესრულება** იხილეთ პასუხი მანამ, სანამ ზარის შემდგომი დამცავი მოაჯირები შეძლებენ მის გადაწერას ან დაბლოკვას. [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) დან მოყოლებული, მეხსიერების ამოღება აწარმოებს ამოღებულ ტექსტს `sanitizePII` მეშვეობით, როდესაც `PII_RESPONSE_SANITIZATION` ჩართულია (როგორც ნაკადი, ისე არასტრიმინგზე), მაგრამ პასუხი, რომ შემდგომი ზარის დაბლოკვა კვლავ შესთავაზა მეხსიერებას და ხელსაწყოებს.
- **სემანტიკური ქეში** ინახავს პასუხს ზარის შემდეგ, ასე რომ, ის ინახავს ხელახლა დაწერილ პასუხს და დაბლოკილი პასუხი არასოდეს ინახება ქეში. ქეში ჩანაწერები ჩაიწერება თითო API გასაღები.

აუდიო იყენებს `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`, `modalityBridgeAudioTimeout` და `modalityBridgeAudioMaxClips`, პლუს გაზიარებულ `modalityBridgeCache*` პარამეტრებს. აუდიოს არ აქვს მემკვიდრეობითი გასაღების სარეზერვო საშუალება, რადგან ეს კლავიშები დაინერგა Modality Bridge სქემით.

ვიდეო იყენებს `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`, `modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` და `modalityBridgeVideoTimeout`, პლუს გაზიარებულ `modalityBridgeCache*` პარამეტრებს. ის ნაგულისხმევად გამორთულია, რადგან FFmpeg/ffprobe არის არასავალდებულო ოპერაციული დამოკიდებულებები და ჩარჩოს წარწერა ამატებს შეყოვნებას და მოდელის ღირებულებას.

## მორგებული Guardrail-ები

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1. შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც აფართოებს `BaseGuardrail`-ს.
2. განახორციელეთ `preCall` და/ან `postCall`.
3. დაარეგისტრირეთ იმპორტის დროს (push-ით `registerDefaultGuardrails`-დან) ან
   გამოიძახეთ `guardrailRegistry.register(...)` გაშვების დროს — რეესტრი ცვლის
   ნებისმიერ ადრე რეგისტრირებულ guardrail-ს იგივე ნორმალიზებული სახელით.
4. დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## Injection-guard-ის მარშრუტების დაფარვა და red-team (ფაზა 8 · ბლოკი D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) ფარავს ყველა
მარშრუტს, რომელიც იღებს მომხმარებლის prompt-ებს. იგი ითვალისწინებს
`INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ლოგირება;
`block` = აბრუნებს HTTP 400-ს `SECURITY_001`-ით).

| ტიპი              | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| ტექსტი (არსებული) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| გენერატიული       | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| მონაცემები        | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ველებს.

**Red-team (ყოველღამით, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი
ბლოკავს OWASP-LLM კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak უშვებს probe-ებს
(secret-ის გარეშე გამოტოვებს). `moderations` ჩართულია თანმიმდევრობისთვის. Block რეჟიმი
სავალდებულო საზღვარია: `evaluatePromptInjection()` უგულებელყოფს თითოეული მოთხოვნის
გამორთვის სიას, რომელსაც middleware გადასცემს, ამიტომ `disabledGuardrails` **არ**
ათავისუფლებს მარშრუტს მისგან ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

ღამის workflow (`.github/workflows/nightly-llm-security.yml`, cron + ხელით
გაშვება) შეიცავს ორ job-ს:

- **`promptfoo-guard` (ბლოკირებადი)** — უშვებს `promptfoo eval -c promptfooconfig.yaml`-ს
  `INJECTION_GUARD_MODE=block`-ით. თითოეული adversarial შემთხვევა (მაგ. „უგულებელყე
  ყველა წინა ინსტრუქცია…", DAN-სტილის jailbreak-ები) ამტკიცებს, რომ პასუხი შეიცავს
  `error.code === "SECURITY_001"`-ს, ანუ guard-მა ნამდვილად უარყო მოთხოვნა.
- **`garak` (სარეკომენდაციო)** — უშვებს garak-ს `--probes promptinject,dan,leakreplay`
  ლოკალური OmniRoute ინსტანციის მიმართ (`http://localhost:20128/v1`). გაპირობებულია
  provider-ის secret-ით (`PROMPTFOO_PROVIDER_KEY`); უპრობლემოდ გამოტოვებს და დასრულებულია
  `|| true`-ით, ამიტომ აწვდის ანგარიშს CI-ის ჩავარდნის გარეშე.

Guard helper-ის (`createInjectionGuard` / `withInjectionGuard`) დაფარვა მოიცავს
ყველა prompt-ის შემცველ `/v1` მარშრუტს; prompt-ის ტექსტი ამოიღება
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ველებიდან
`extractMessageContents()`-ით, `src/shared/utils/inputSanitizer.ts`-ში.
