## ჩანართები

### ძებნა ჩანართი

ავითარებს არსებულ `SearchForm` + `ResultsPanel` + `RerankPanel` ჩანართად:

- მოითხოვეთ → შედეგები (სათაური, URL, ფრაგმენტი, შესაბამისობის ქულა).
- პროვაიდერის მეტამონაცემები კონფიგურაციის პანელში (ღირებულება, კვოტა, სტატუსი).
- განყოფილების ხელახალი რანჟირება: აირჩიეთ ხელახალი რანგის მოდელი, გადაანაწილეთ შედეგები, აჩვენეთ `positionDelta`.
- ცარიელი მდგომარეობა CTA ით, როდესაც არ არის კონფიგურირებული საძიებო პროვაიდერები.
- ძიების ისტორია `SearchHistory.tsx` საშუალებით.
- იძახის `POST /v1/search` (არსებული ბოლო წერტილი, ცვლილებები არ არის).

### Scrape Tab

ახალი ჩანართი URL დან `POST /v1/web/fetch` საშუალებით შინაარსის ამოსაღებად (შექმნილია გეგმა 05-ში):

- შეყვანა: URL + სრული გვერდის გადართვა + ფორმატის ამომრჩევი (ჩანიშვნა / ტექსტი / HTML).
- გაგზავნეთ → fetch → render `ScrapeResult.tsx`.
- `ScrapeResult` ახდენს მარკდაუნის გადახედვისას + raw გადართვას.
- ქუდი: თუ საპასუხო ორგანო >** 256 KB** , UI აჩვენებს `(truncated, view raw)` და იხსნება ნედლი მონაკოს მოდალში (D21).
- მეტამონაცემების პანელი: პროვაიდერი (firecrawl/jina-reader/tavily-search/tinyfish/nimble-search/anysearch-search/parallel-search/keenable-search), შეყოვნება, ღირებულება, პასუხის ზომა, ბმულების რაოდენობა.
- იყენებს `useScrapeFetch.ts` hook-ს.

### შედარება ჩანართი

გადის იგივე query/URL მასშტაბით მდე** 4 პროვაიდერი პარალელურად** (D22):

- გვერდიგვერდ სვეტები თითო პროვაიდერზე.
- მეტრიკა: შეყოვნება, ღირებულება, შედეგების რაოდენობა, პასუხის ზომა.
- URL გადახურვის გაანგარიშება ძიებისთვის (გაზიარებული URLs ის რაოდენობა თავდაპირველ შედეგთან შედარებით).
- ურეკავს `POST /v1/search` (ძებნა) ან `POST /v1/web/fetch` (სკრაპი) პროვაიდერზე.

## პროვაიდერის კატალოგი

`ProviderCatalog.tsx` ასახავს პროვაიდერების სრულ სიას `GET /api/search/providers` დან (გაფართოებულია F4-ში, რათა შეიცავდეს მიწოდების პროვაიდერებს):

| `kind` | `"search"` (24 პროვაიდერი) ან `"fetch"` (firecrawl, jina-reader, tavily-search, tinyfish, nimble-search, anysearch-search, პარალელური ძიება, საძიებო ძიება) |

სტატუსი არის** მიღებული მოთხოვნის დროს** იმის შემოწმებით, არსებობს თუ არა სერთიფიკატები და არის თუ არა ყველა კლავიშის გაგრილება.

`codex-search` (Codex ვებ ძიებას) არ აქვს საკუთარი გასაღები: ის ხელახლა იყენებს დაკავშირებულ Codex (ChatGPT) ანგარიშს, ასე რომ, თითოეული ძიება ხარჯავს ChatGPT გამოწერის კვოტას და სჭირდება დაახლოებით 10–40 წმ. ის მუშაობს, როდესაც მოთხოვნა ასახელებს მას; ავტომატურ არჩევას სჭირდება `CODEX_SEARCH_AUTO_FALLBACK_ENABLED` ფუნქციის დროშა (ნაგულისხმევად გამორთულია).

## Backend ცვლილებები

ამ ფუნქციისთვის საჭირო იყო მხოლოდ ერთი სარეზერვო ცვლილება:

### გაფართოებული `GET /api/search/providers`

`src/app/api/search/providers/route.ts` გაფართოვდა:

- ჩართეთ ყველა fetch პროვაიდერი (`firecrawl`, `jina-reader`, `tavily-search`, `tinyfish`, `nimble-search`, `anysearch-search`, `parallel-search`, `keenable-search`) მასივში.
- დაამატეთ `kind: "search" | "fetch"` ყველა ნივთს.
- დაამატეთ `status: "configured" | "missing" | "rate_limited"` რომელიც მიღებულია პირდაპირი რწმუნების მდგომარეობიდან.
- უცვლელად შეინარჩუნეთ ჩამორჩენილი თავსებადობა — არსებული ველები (`id`, `name` და ა.შ.).
