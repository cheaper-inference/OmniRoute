OmniRoute-ის ზარების ჟურნალების უწყვეტი, ინკრემენტული ექსპორტი გარე ანალიტიკურ საცავში.

Logs დაფის ჩანართი მოთხოვნების ისტორიას ინახავს SQLite-ში (`call_logs`), რომლის მოცულობაც
როტაციითა და შენახვის ვადითაა შეზღუდული. ჟურნალების ექსპორტი იმავე ჩანაწერთა ნაკრებს გრაფიკის
მიხედვით აგზავნის, რათა მონაცემები ადგილობრივ მონაცემთა ბაზაზე დიდხანს შენარჩუნდეს და სხვა
მონაცემებთან გაერთიანდეს. პირველი დანიშნულებაა BigQuery; კონვეიერი რეესტრს წარმოადგენს, ამიტომ
დამატებითი დანიშნულებების დამატება მარტივად შეიძლება.

## 1. როგორ მუშაობს

```
სერვერი (კონფიგურაციის გაშიფვრა + ვალიდაცია, კურსორის შეჯერება)
  → IPC-ის გაშვება → იზოლირებული exportChild OS-პროცესი
    → მხოლოდ წასაკითხი storage.sqlite → ზარების ჟურნალის საერთო მოთხოვნა/ასახვა
      → არტეფაქტების ასინქრონული ჰიდრატაცია → დანიშნულების prepare()/send()
        → პაკეტის IPC → სერვერი ინახავს კურსორს → დადასტურების IPC
          → შემდეგი პაკეტი; დასრულების IPC → სერვერი აღრიცხავს წარმატებას
```

- **განრიგი** — ერთი `JobRegistry` cron-დავალება, `log_export`, ნაგულისხმევად `0 * * * *` (ყოველ საათში,
  UTC). რეგისტრირებულია `src/lib/initCloudSync.ts`-ში; მისი გადაფარვა შესაძლებელია `OMNIROUTE_LOG_EXPORT_CRON`-ით.
  ყოველი ტაქტი თანმიმდევრულად ამუშავებს ყველა **ჩართულ** დანიშნულებას.
- **კურსორი** — SQLite-ის არაცხადი `call_logs.rowid`, რომელიც თითოეული დანიშნულებისთვის ინახება
  `log_export_destinations.cursor_row_id`-ში. `timestamp` განზრახ არ გამოიყენება კურსორად: გამომძახებლებმა
  შეიძლება საკუთარი მნიშვნელობა მიაწოდონ, ამიტომ ნელი მოთხოვნა შეიძლება ჩაიწეროს მასზე გვიან დაწყებული
  უფრო სწრაფი მოთხოვნის შემდეგ, ხოლო დროის ნიშნულზე დაფუძნებული კურსორი მას გამოტოვებდა.
- **პაკეტებად დაყოფა** — თითო მოთხოვნაზე `batch_size` სტრიქონი (ნაგულისხმევად 500), თითო გაშვებაზე
  `max_rows_per_run` სტრიქონი (ნაგულისხმევად 10000), რათა დიდი დაგროვილი რიგი რამდენიმე ტაქტის
  განმავლობაში დამუშავდეს, ნაცვლად იმისა, რომ ერთი ტაქტი დაბლოკოს.
- **მიწოდება** — კურსორი მხოლოდ `send()`-ის წარმატებით დასრულების შემდეგ წინ მიიწევს. წარუმატებელი
  პაკეტის შემთხვევაში კურსორი უცვლელი რჩება, ამიტომ მომდევნო გაშვებისას იგივე სტრიქონები ხელახლა
  გაიგზავნება. გარანტია არის მინიმუმ ერთხელ მიწოდება და დანიშნულების მხარეს დუბლიკატების მოცილება,
  და არა ნამდვილი ზუსტად ერთხელ მიწოდება: BigQuery თითოეულ სტრიქონს ზარის ჟურნალის id-ით აკლავიშებს,
  რასაც საკუთარი დუბლიკატების მოცილების ფანჯრის ფარგლებში შესაძლებლობისამებრ ითვალისწინებს.
- **გადაფარვისგან დაცვა** — cron-ის ტაქტი და `POST .../run` შეიძლება ერთდროულად გაეშვას. დანიშნულება,
  რომლის დამუშავებაც უკვე მიმდინარეობს, მეორედ დამუშავების ნაცვლად გამოტოვდება (გაშვების შედეგში
  `skipped: true`), ამიტომ პარალელური გაშვება ვერ გაგზავნის პაკეტს ხელახლა და ვერ გადაწერს კურსორს
  უკუსვლით.
- **გასუფთავების შემდეგ აღდგენა** — თუ `cursor_row_id` `MAX(rowid)`-ზე მეტი აღმოჩნდება (მთელი ცხრილი
  გასუფთავდა და rowid-ები თავიდან დაიწყო), გამშვები კურსორს 0-ზე აბრუნებს, რათა სამუდამოდ არ დაკარგოს
  ახალი ჩანაწერების დანახვის შესაძლებლობა.

### იზოლირებული გამშვები და ლიმიტები

Node-ზე თითოეული დანიშნულების გაშვება იწყებს ცალკე, ხანმოკლე OS შვილობილ პროცესს (`child_process`
IPC-ით და არა `worker_threads`-ით). შიგთავსის წაკითხვა, სასარგებლო დატვირთვის JSON-ის
პარსინგი/სერიალიზაცია, დანიშნულების `prepare()` და დანიშნულების ქსელური I/O სრულდება იქ და არა
სერვერის მოვლენათა ციკლში. IPC-ით გადადის მხოლოდ კონფიგურაცია და პროგრესის მცირე შეტყობინებები;
ექსპორტირებული ჩანაწერები სერვერზე არასოდეს ბრუნდება. cron-დავალება და ახლავე გაშვების მარშრუტი
ინარჩუნებს იმავე საჯარო შედეგსა და გადაფარვისგან დაცვას.

შვილობილი პროცესი სერვერის მიერ განსაზღვრულ `DATA_DIR/storage.sqlite`-ს მხოლოდ წაკითხვის რეჟიმში
ხსნის `node:sqlite`-ის გამოყენებით, `busy_timeout=5000`-ითა და `query_only=ON`-ით. ის არ ახდენს DB-ის
სინგლტონის იმპორტს და არ ასრულებს მიგრაციებს, სარეზერვო ასლების შექმნას ან SQLite-ის განახლებებს.
არარსებული/დაზიანებული არტეფაქტების აღრიცხვა (დაზიანებული არტეფაქტის UPDATE-ის ჩათვლით) მხოლოდ
მართვის პანელის დეტალების გზაზე რჩება. ორივე გზა იყენებს საერთო სუფთა დეტალების რეზოლვერს; ექსპორტი
იყენებს ფაილური სისტემიდან ასინქრონულ წაკითხვას და გადაწყვეტის იმავე თანმიმდევრობას: არტეფაქტი →
მემკვიდრეობითი ჩაშენებული მონაცემები → მემკვიდრეობითი დისკი → არაფერი. გაშვება აფიქსირებს
ჩასმის მაქსიმალურ rowid-ს იმ მომენტში, როცა შვილობილი პროცესი წამკითხველს ხსნის; მოგვიანებით
ჩასმული ჩანაწერები მომდევნო გაშვებას ელოდება. ეს ჩასმის საზღვარია და არა ხანგრძლივი SQLite
ტრანზაქცია: WAL-ის ჩამწერები და საკონტროლო წერტილები ქსელის მოლოდინისას თავისუფლად აგრძელებენ
მუშაობას. არსებული სტრიქონების განახლებები/წაშლები ამ საზღვრით არ ფიქსირდება.

თითოეული მიღებული პაკეტის შემდეგ შვილობილი პროცესი დადასტურებას ელოდება. სერვერი ჯერ ინახავს
კურსორს `advanceLogExportCursor`-ით, შემდეგ კი აგზავნის `ack`-ს; მანამდე შემდეგი პაკეტი არ იწყება.
გაგზავნის წარუმატებლობა, ავარია ან დროის ლიმიტის ამოწურვა აღირიცხება წარუმატებლობად ამ პაკეტის
კურსორის წინ წაწევის გარეშე. ადრე დადასტურებული პაკეტები შენახული რჩება; ხელახლა შეიძლება გაიგზავნოს
მაქსიმუმ ერთი დაუდასტურებელი პაკეტი. წარმატება აღირიცხება მხოლოდ `done`-ისა და შვილობილი პროცესის
სუფთად დასრულების შემდეგ. წარუმატებლობის შემთხვევაში შვილობილი პროცესი წყდება SIGTERM-ით, ხოლო
500 ms-ის შემდეგ — SIGKILL-ით, და გამშვები პროცესის სრულ დახურვას ელოდება.

| გარემოს ცვლადი                                | ნაგულისხმევი | დანიშნულება                            |
| --------------------------------------------- | ------------ | -------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000       | თითო დანიშნულების სრული დროის ლიმიტი   |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024         | შვილობილი V8-ის old-space ლიმიტი MB-ში |

არასწორი/არადადებითი/არამთელი მნიშვნელობების შემთხვევაში გამოიყენება ნაგულისხმევი მნიშვნელობები.
გროვის პარამეტრი RSS-ის სრული ლიმიტი არ არის; ძალიან დიდმა პაკეტებმა მაინც შეიძლება ამოწუროს შვილობილი
პროცესის მეხსიერება და უსაფრთხოდ დაასრულოს გაშვება წარუმატებლად. ნაგულისხმევი 1024 MB ტოვებს
საკმარის მარაგს ნაგულისხმევი 500-სტრიქონიანი პაკეტისთვის, რომელიც შეიცავს 512 KiB ზომის არტეფაქტებს
და ჩართული აქვს შიგთავსები, BigQuery-ის ბაიტების ნაწილებად დაყოფილი JSON-სერიალიზაციის ჩათვლით.
ეს არ ხდის 10000-სტრიქონიან პაკეტს შიგთავსებით უსაფრთხოს. V8-ის გროვის ამოწურვა აღრიცხავს ქმედით
შეცდომას: შეამცირეთ პაკეტის ზომა ან გაზარდეთ `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`;
კურსორი ბოლო დადასტურებულ პაკეტზე რჩება. ისტორიული ჩაშენებული/დისკზე შენახული შიგთავსები არტეფაქტების
თანამედროვე ლიმიტით არ იფარება. ოპერატორებმა RSS ცალკე უნდა დაგეგმონ, განსაკუთრებით მეხსიერებით
შეზღუდულ კონტეინერებში.

შვილობილი პროცესი მემკვიდრეობით იღებს მხოლოდ განსაზღვრულ `DATA_DIR`-ს, `NODE_ENV`-ს, ცხადად მითითებულ
`TZ`-ს (მემკვიდრეობითი ფაილის სახელისთვის ლოკალური დროის განსაზღვრა), `ELECTRON_RUN_AS_NODE`-ს, თუ ის
არსებობს, და შემდეგ გამავალი კავშირის პარამეტრებს: `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`
(და მათ ქვედა რეგისტრში ჩაწერილ ფორმებს), `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`,
`SSL_CERT_FILE`, `SSL_CERT_DIR`. Undici-ის გლობალური დისპეტჩერი იზიარებს სერვერის გარემოს ცვლადებზე
დაფუძნებული პროქსის სუფთა გადაწყვეტისა და ლოკალური ჰოსტების გვერდის ავლის წესებს, `NO_PROXY`-ის
ჩათვლით; ის არ ახდენს `proxyFetch.ts`-ის ან მისი DB-ის/ფუნქციონალის ალმების იმპორტს. პროქსის
ავტორიზაციის მონაცემები გადაგზავნილი გამოტანიდან და აღრიცხული შეცდომებიდან იფარება. დანიშნულების
ავტორიზაციის მონაცემები გადაიცემა მხოლოდ ერთ საწყის IPC შეტყობინებაში და არასოდეს — argv-ში ან
გარემოში; გამოტანასა და შეცდომების გადაგზავნას ემატება პრეფიქსი და მათგან მგრძნობიარე მონაცემები
იშლება. შვილობილი პროცესის შესრულების არგუმენტებში გამორთულია მხოლოდ `ExperimentalWarning`, რათა
cron-ის ყოველი გაშვებისას Node-ის SQLite გაფრთხილება არ განმეორდეს; სხვა ტიპის გაფრთხილებები
კვლავ ხილულია.

დანიშნულების მოდულების იმპორტი შესაძლებელი უნდა იყოს Next.js-ის/server-only დამოკიდებულებების გარეშე. არსებული
BigQuery-ის იმპლემენტაცია ამ კონტრაქტს უკვე აკმაყოფილებს. წვდომის ტოკენების ქეშები მხოლოდ შვილობილი
პროცესის გაშვების განმავლობაში ინახება და არა სხვადასხვა გაშვებას შორის. მხარდაჭერილი გარემოა Node (`package.json`-ის engines), თუმცა README-ის Bun-ის
ინსტალაციის განყოფილება და `Dockerfile.bun` ასევე გვთავაზობს production-თან თავსებადობის გზას
`bun:sqlite`-ის გამოყენებით (`src/lib/db/core.ts` / ადაპტერები). ამიტომ Bun-ის შემთხვევაში ექსპორტები ინარჩუნებს წინა
პროცესშიდა გზას და ერთხელ აჩვენებს გაფრთხილებას: შვილობილი პროცესის heap-ის/timeout-ის იზოლაცია მიუწვდომელია. გამოიყენეთ
Node event loop-ისა და OOM-ის იზოლაციისთვის; Bun აქ მხოლოდ development-ისთვის განკუთვნილად არ განიხილება.

როდესაც `includeBodies` ჩართულია, საათობრივი payload-ების დაგროვების ნაცვლად უპირატესობა მიანიჭეთ წუთობრივ სიხშირეს, მაგალითად
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`.
პაკეტებისა და მწკრივების ლიმიტები კვლავ ზღუდავს თითოეულ გაშვებას. პროცესის გაშვების საფასური გადაიხდება თითოეული დანიშნულებისთვის, ყოველი გაშვებისას;
ეს მცირე გაშვების დანახარჯს server-ის event loop-ის იზოლაციაში ცვლის და არა CPU-ის ჯამური გამოყენების შემცირებაში.

### Payload-ები (prompt-ები და completion-ები)

ნაგულისხმევად ექსპორტი შეიცავს მხოლოდ იმ შემაჯამებელ ველებს, რომლებსაც Logs-ის **სია** აჩვენებს. ფუნქციის
**Prompt-ებისა და პასუხების ექსპორტი** (`includeBodies`) ჩართვისას დამატებით იგზავნება ის, რასაც Logs-ის **დეტალების**
პანელი თითოეული გამოძახებისთვის აჩვენებს:

| ველი                             | რას შეიცავს                                                      |
| -------------------------------- | ---------------------------------------------------------------- |
| `request_body` / `response_body` | გამოძახების payload-ები ისე, როგორც dashboard აჩვენებს           |
| `pipeline_route_decision`        | router-ის მიერ არჩეული target და model                           |
| `pipeline_client_request`        | დაუმუშავებელი request ზუსტად ისე, როგორც client-მა გაგზავნა      |
| `pipeline_openai_request`        | შიდა OpenAI ფორმატში გარდაქმნის შემდეგ                           |
| `pipeline_provider_request`      | როგორც რეალურად გაიგზავნა upstream-ში, provider-ის დიალექტზე     |
| `pipeline_provider_response`     | დაუმუშავებელი upstream response                                  |
| `pipeline_client_response`       | ის, რაც caller-ს უკან გადაეცა                                    |
| `pipeline_error`                 | pipeline-ის დონის შეცდომის დეტალები წარუმატებელი გამოძახებისთვის |
| `bodies_truncated`               | True, როდესაც ზემოთ ჩამოთვლილ რომელიმე ველს `maxBodyBytes` შეეხო |

ეს prompt-ის შიგთავსია, ამიტომ **ნაგულისხმევად გამორთულია** და მიზანმიმართულად თითოეული დანიშნულებისთვის ცალ-ცალკე ირჩევა.
იგზავნება ის, რასაც dashboard აჩვენებს, რადგან ექსპორტი და `getCallLogById` დეტალების
ამოხსნის საერთო მექანიზმს იყენებს: payload-ები ჩაწერისას
უკვე გაწმენდილია PII-ისგან და მათში საიდუმლო მონაცემები დაფარულია, ხოლო `noLog` API გასაღებით შესრულებული გამოძახება
საერთოდ არ ინახავს payload-ს, ამიტომ საექსპორტო არაფერია.

Payload-ები თითოეული მწკრივისთვის filesystem-ის artifact-იდან იკითხება, ამიტომ ჰიდრატაცია მხოლოდ იმ დანიშნულებებისთვის სრულდება,
რომლებმაც ის მოითხოვეს. დაკარგული ან დაზიანებული artifact-ის შემთხვევაში მისი შეჯამება null payload-ებით ექსპორტირდება,
ნაცვლად იმისა, რომ პაკეტი ჩავარდეს და cursor გაჩერდეს.

`maxBodyBytes` (ნაგულისხმევად 262144) თითოეული ველის ზომას ზღუდავს. უფრო გრძელი payload-ები **მოკლდება და არ იშლება**
— მოჭრილი prompt მაინც პასუხობს კითხვას „რა იყო მოთხოვნილი“ — და მწკრივი ინიშნება
`bodies_truncated`-ით. ნაწილ-ნაწილ stream-ით მიღებული delta-ები არ ექსპორტირდება; აწყობილი response
უკვე წარმოდგენილია `pipeline_provider_response`-სა და `pipeline_client_response`-ში.

## 3. REST API

ყველა მარშრუტი მართვის ავთენტიფიკაციას იყენებს (`requireManagementAuth`). საიდუმლო მონაცემები არასდროს ბრუნდება:
შენახული საიდუმლო მონაცემი ბრუნდება ზუსტი მნიშვნელობით `__stored__`, ხოლო განახლებისას ამ მნიშვნელობის უკან გაგზავნა
შენახულ ავტორიზაციის მონაცემს უცვლელად ტოვებს.

დანიშნულების შექმნა ან განახლება, რომლის ტიპიც საიდუმლო მონაცემს განსაზღვრავს, **მოითხოვს
`STORAGE_ENCRYPTION_KEY`-ს**. მის გარეშე `encrypt()` შეუმჩნევლად ტოვებს მონაცემს უცვლელად, ამიტომ ჩაწერა
უარყოფილია 400 კოდით, ნაცვლად იმისა, რომ ავტორიზაციის მონაცემი SQLite-ში ღია ტექსტის სახით მოთავსდეს (იგივე დაცვა,
რომელსაც Telegram-ის webhook იყენებს).

| გასაღები             | შენიშვნები                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------- |
| `projectId`          | GCP პროექტი, რომელშიც მონაცემთა ნაკრებია განთავსებული                                        |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                              |
| `tableId`            | `[A-Za-z0-9_]+`                                                                              |
| `location`           | გამოიყენება მხოლოდ მაშინ, როცა მონაცემთა ნაკრები შესაქმნელია (ნაგულისხმევი მნიშვნელობა `EU`) |
| `serviceAccountJson` | სერვისული ანგარიშის გასაღები. საიდუმლო მონაცემი: შენახვისას დაშიფრულია და არასდროს ბრუნდება  |
| `autoCreate`         | მონაცემთა ნაკრებისა და ცხრილის შექმნა პირველი ექსპორტისას (ნაგულისხმევი მნიშვნელობა `true`)  |

სერვისულ ანგარიშს სამიზნე ცხრილზე სჭირდება `bigquery.tables.updateData`, ხოლო
როცა `autoCreate` ჩართულია — `bigquery.datasets.create` / `bigquery.tables.create`.

კონფიგურირებული პაკეტი **კურსორის** ერთეულია და არა HTTP-ის: `send()` მას ყოფს insertAll-ის
გამოძახებებად, თითოეულში მაქსიმუმ 500 სტრიქონით, ამიტომ დიდმა `batch_size`-მა BigQuery-ის 10 MB-იანი მოთხოვნის ლიმიტი ვერ უნდა გადააჭარბოს.
დროებითი სტატუსების (408/429/500/502/503/504) შემთხვევაში მცდელობა მეორდება მაქსიმუმ სამჯერ, ექსპონენციალური
დაყოვნებით და იგივე insertIds-ების ხელახლა გამოყენებით; ავთენტიფიკაციისა და სქემის შეცდომები პირველივე მცდელობისას იწვევს გამონაკლისს,
ნაცვლად იმისა, რომ გაშვების რესურსები უშედეგოდ დაიხარჯოს.

რამდენიმე წამის წინ შექმნილი ცხრილი ნაკადური ჩასმის endpoint-ისთვის ჯერ არ ჩანს, რომელიც
რამდენიმე წამის განმავლობაში 404-ს აბრუნებს. ამ 404-ის შემთხვევაში მცდელობა მეორდება, მაგრამ **მხოლოდ მაშინ, როცა ეს ცხრილი მიმდინარე გაშვებამ შექმნა** —
რეალურად არარსებული ცხრილის შემთხვევაში ოპერაცია კვლავ დაუყოვნებლივ სრულდება შეცდომით. გაითვალისწინეთ, რომ ახლახან წაშლილი ცხრილის სახელით
ცხრილის ხელახლა შექმნა BigQuery-ს აიძულებს, რამდენიმე წუთის განმავლობაში უარი თქვას ნაკადურ ჩასმებზე; ეს
წაშლისა და ხელახლა შექმნის თვისებაა, ამიტომ ცხრილის წაშლისა და ხელახლა დამატების ნაცვლად უმჯობესია ახალი სახელი გამოიყენოთ.

**ნაწილობრივი წარუმატებლობა მოდის HTTP 200 პასუხის სახით, არაცარიელი `insertErrors[]`-ით.** ეს განიხილება როგორც
წარუმატებლობა და იწვევს გამონაკლისს, რაც კურსორს არ აძლევს საშუალებას გასცდეს იმ სტრიქონებს, რომლებიც BigQuery-მ არ
მიიღო; `tests/unit/log-export-bigquery.test.ts` ამ ქცევას აფიქსირებს.

ტრანსპორტი ჩვეულებრივი REST-ია — თვითხელმოწერილი RS256 მტკიცება იცვლება წვდომის ტოკენზე მისამართზე
`https://oauth2.googleapis.com/token`, შემდეგ კი სტრიქონები იგზავნება `tabledata.insertAll`-ში. Google SDK
არ ემატება. წვდომის ტოკენები პროცესის ფარგლებში ქეშირდება თითოეული (სერვისული ანგარიში, მოქმედების არე) წყვილისთვის.

შექმნილი ცხრილი შეიცავს თითო სვეტს Logs ჩანართის თითოეული ველისთვის, დამატებული `exported_at`-ით, და სტრუქტურირებულია
გამოძახებების ჟურნალების რეალური მოთხოვნების შესაბამისად:

- **დღეების მიხედვით დაყოფილია `timestamp`-ზე**, ამიტომ თარიღით შეზღუდული მოთხოვნა მხოლოდ შესაბამის დღეებს სკანირებს.
- **კლასტერიზებულია `api_key_name`, `provider`, `model`, `status` ველებით** (ამ თანმიმდევრობით), ამიტომ გაფილტვრა იმის მიხედვით,
  თუ ვინ გაუშვა, სად გაიგზავნა ან იყო თუ არა წარუმატებელი, თითოეული დანაყოფის შიგნით ბლოკებს გამორიცხავს. BigQuery
  მაქსიმუმ ოთხ კლასტერიზაციის სვეტს უშვებს და თანმიმდევრობას მნიშვნელობა აქვს: მხოლოდ `api_key_name`-ზე ფილტრი
  ბლოკებს გამორიცხავს, ხოლო მხოლოდ `status`-ზე ფილტრი — არა.
- **დანაყოფების არასავალდებულო შენახვის ვადა** `partitionExpirationDays`-ის საშუალებით (0 ყველაფერს ინახავს), რომელიც
  ცხრილის შექმნისას გამოიყენება.

ორივე პარამეტრი შექმნის დროს გამოიყენება. არსებული ცხრილი ინარჩუნებს უკვე არსებულ განლაგებას, ამიტომ, თუ მათი გამოყენება გსურთ, დანიშნულებად ახალი ცხრილის id მიუთითეთ.

`tests/unit/log-export-bigquery.test.ts` ამოწმებს, რომ mapper და ცხრილის სქემა სინქრონულად დარჩეს, რათა call-log-ის ახალი სვეტი ექსპორტისას შეუმჩნევლად არ დაიკარგოს.

პაკეტები ნაწილდება ნაწილებად **როგორც** მწკრივების რაოდენობის, **ისე** სერიალიზებული ბაიტების მიხედვით. payload-ების ექსპორტისას მხოლოდ მწკრივების რაოდენობა საკმარისი არ არის: prompts-ის შემცველი 500 მწკრივი შეიძლება ათეულობით მეგაბაიტი იყოს, ხოლო insertAll 10 MB-ზე დიდ მოთხოვნას უარყოფს. ნაწილი იხურება 500 მწკრივის ან 9 MB-ის მიღწევისას — იმის მიხედვით, თუ რომელი მოხდება პირველი.

## 5. OTLP/HTTP ტრასების დანიშნულება

კონფიგურაცია იყენებს `type: "otlp-http"`-ს. ეს არის შენახული გამოძახებების ჟურნალების დაგეგმილი,
კურსორზე დაფუძნებული ექსპორტი და არა რეალურ დროში მარშრუტიზაციის მოვლენების მაქსიმალური ძალისხმევით მიმღები
`open-sse/services/routing/otel.ts`-ში. ის არ კითხულობს და არ ცვლის ამ მიმღების გარემოს
ცვლადებს, ტაიმერებსა თუ ბუფერებს. ორივეს ჩართვამ შეიძლება წარმოქმნას სპანების ორი დამოუკიდებელი სახეობა;
ამ გამოძახებების ჟურნალის სპანების გასარჩევად გამოიყენეთ `omniroute.log-export` ინსტრუმენტაციის არეალი.

| გასაღები                 | ნაგულისხმევი მნიშვნელობა / დანიშნულება                                                         |
| ------------------------ | ---------------------------------------------------------------------------------------------- |
| `endpoint`               | სავალდებულო სრული HTTP(S) ტრასების URL; `/v1/traces` სუფიქსი არ ემატება                        |
| `headers`                | არასავალდებულო `Name: value` სტრიქონები ან სტრიქონების JSON ობიექტი; დაშიფრული                 |
| `requestHeaderAllowlist` | ცარიელი (გამორთული); კლიენტის ჰედერების სახელები/პრეფიქსები სპანის ატრიბუტებად დასაფიქსირებლად |
| `serviceName`            | `omniroute`; რესურსის `service.name`                                                           |
| `langfuseMapping`        | `false`; ამატებს Langfuse-ის გენერაციის/სესიის/მომხმარებლის ატრიბუტებს                         |
| `identity`               | `pseudonymous`, `keyName` ან `none`                                                            |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                                        |
| `timeoutMs`              | `30000` თითო HTTP მცდელობაზე                                                                   |
| `environment`            | დაუყენებელი; არასავალდებულო `langfuse.environment`                                             |

ზოგადი მართვის პანელი აჩვენებს ამ ველებს. `paths` იღებს API მასივს ან ტექსტურ არეს,
სადაც ზუსტი გზები გამოყოფილია ახალი ხაზებით/მძიმეებით. ემბედინგების, ხელახალი რანჟირებისა და სხვა გზები
გამოტოვებულია, თუ ისინი აშკარად არ არის დაშვებული. გამოტოვებული სტრიქონებიც წინ სწევს კურსორს; არსებული
გამშვების `exported`/`exportedTotal` მრიცხველები ითვლის დამუშავებულ წყაროს სტრიქონებს, გაფილტრულის
ჩათვლით, და არა მიღებულ სპანებს. ფილტრაცია ხდება შვილობილ პროცესში, მისი
IPC/კურსორის კონტრაქტის შეცვლის გარეშე.

URL-ის ვალიდაცია იყენებს მონაცემთა ბაზისგან დამოუკიდებელ `parseAndValidateNonMetadataUrl` დამხმარე ფუნქციას
`src/shared/network/outboundUrlGuard.ts`-დან: `block-metadata` პოლიტიკას. მას აქვს მეტამონაცემების/პროტოკოლის/ჩაშენებული ავტორიზაციის მონაცემების
იგივე უპირობო შემოწმებები, რაც ვებჰუკის ვალიდატორს კერძო URL-ების დაშვებისას,
თუმცა განზრახ უშვებს localhost/LAN სამიზნეებს გლობალური ფუნქციის ალმის გადაფარვის გარეშე.
ეს შესაძლებელს ხდის საკუთარ ინფრასტრუქტურაზე განთავსებული Langfuse, Phoenix, Tempo და Collector
საბოლოო წერტილების გამოყენებას, კერძო HTTP საბოლოო წერტილების ჩათვლით. ღრუბლოვანი მეტამონაცემების ჰოსტები ყოველთვის დაბლოკილია.
გადამისამართებებს არ მიჰყვება, ამიტომ კოლექტორს არ შეუძლია ავტორიზაციის მონაცემების სხვა ჰოსტზე გადამისამართება.
არსებული ლექსიკური URL დამცავის მსგავსად, ეს არ აფიქსირებს DNS გადაწყვეტის შედეგს; დააკონფიგურირეთ მხოლოდ
ოპერატორის მიერ კონტროლირებადი ჰოსტები. უპირატესობა მიანიჭეთ HTTPS-ს, როდესაც საბოლოო წერტილი სანდო ქსელში არ არის.

### მონაცემთა პაკეტი და მიწოდება

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) თითო დაშვებულ
სტრიქონზე გადასცემს ერთ CLIENT სპანს, რომელსაც სახელი მოთხოვნის ზუსტი გზის მიხედვით ენიჭება. გზის მიხედვით დასახელება განასხვავებს
ჩატის დასრულებებს, პასუხებსა და შეტყობინებებს ისე, რომ სპანის სახელში მოდელის ან იდენტობის მონაცემები
არ ჩაშენდეს. რესურსის ატრიბუტები მოიცავს `service.name`-სა და პაკეტის `service.version`-ს.

ჩატის მცდელობების სტანდარტული ჟურნალის ჩამწერი (`open-sse/handlers/chatCore/attemptLogging.ts`) დასრულებისას წერს
`duration = Date.now() - startTime`-ს და დროის ნიშნულს არ აწვდის;
`saveCallLogOperation` ფუნქცია `src/lib/usage/callLogs.ts`-ში ნაგულისხმევად დროის ნიშნულად ჩაწერის
(დასრულების) დროს იყენებს. ამიტომ ექსპორტი ადგენს: დასასრული = სტრიქონის დროის ნიშნული, ხოლო დასაწყისი = დასასრული − ხანგრძლივობა
(მილიწამები, გადაყვანილი ათობით ნანოწამებში). გამომძახებლის მიერ მოწოდებული ისტორიული დროის ნიშნულებიც
დასრულების დროდ ინახება; ცალკეული სტრიქონისთვის დაწყების/დასრულების განმასხვავებელი არ არსებობს.
ნულოვანი (`null`) ხანგრძლივობა ნულად გარდაიქმნება. არასწორი/გამოტოვებული დროის ნიშნულები იწვევს პაკეტის წარუმატებლობას და არა
არადეტერმინისტული სპანების შექმნას. `ttftMs` შეიძლება იყოს null და შეესაბამება `omniroute.ttft_ms`-ს.

ატრიბუტები მოიცავს `gen_ai.operation.name="chat"`-ს, პროვაიდერს, მოთხოვნილ/პასუხის მოდელს,
შემავალ/გამომავალ ტოკენებს, არასავალდებულო ქეშიდან წაკითხვის/ქეშის შექმნის/მსჯელობის ტოკენებს, HTTP სტატუსს,
კომბინაციას, ქეშის წყაროს, სესიის ჭდესა და კორელაციის იდენტიფიკატორს. OTLP-ის მთელი მნიშვნელობები და დროის ნიშნულები
ათობითი სტრიქონებია; სტრიქონები, ლოგიკური მნიშვნელობები და წილადი რიცხვები იყენებს შესაბამის ბუნებრივ OTLP მნიშვნელობის
ვარიანტებს. შეცდომის სპანებს აქვს ERROR სტატუსი და გასუფთავებული სტატუსის შეტყობინება. კანონიკურ
ჩანაწერში არ არის ზედა დონის ჰოსტის URL, ამიტომ `server.address` გამოტოვებულია, რათა კოლექტორი შეცდომით
მოდელის სერვერად არ იქნეს მიჩნეული. ღირებულება არ ექსპორტირდება.

მხოლოდ `includeBodies=true` ტვირთავს შიგთავსს. `langfuseMapping=false`-ის შემთხვევაში,
`gen_ai.input.messages` / `gen_ai.output.messages` შეიცავს OmniRoute-ის მიერ შენახულ, გასუფთავებულ მოთხოვნის/პასუხის
სხეულის JSON-ს (კანონიკურ ფორმაში მოყვანილს, როცა მისი გარჩევა შესაძლებელია) და არა semconv-ის ფორმატში გარდაქმნილ
შეტყობინებების მასივს. შეკვეცილი/არა-JSON სხეულები რჩება დაუმუშავებელ ტექსტად. `langfuseMapping=true`-ის შემთხვევაში,
სხეულები იგზავნება მხოლოდ `langfuse.observation.input` / `langfuse.observation.output` სახით;
`gen_ai.*.messages` ატრიბუტები გამოტოვებულია, რათა თითოეული სხეული ერთხელ გაიგზავნოს. ორივე რეჟიმი
`maxBodyBytes`-ს მემკვიდრეობით იღებს შიგთავსის ჩატვირთვის არსებული მექანიზმიდან;
`omniroute.bodies_truncated=true` აღნიშნავს შეკვეცას.
ეს დანიშნულება არ ამატებს დამუშავების ჯაჭვის დამატებით სნეპშოტებს ან გაუსუფთავებელი არტეფაქტების წაკითხვას;
მოთხოვნის ჰედერების არასავალდებულო დაფიქსირება იყენებს ქვემოთ აღწერილ, უკვე ჩატვირთულ კლიენტის სნეპშოტს.
სხეულების ექსპორტისას გამოიყენეთ წუთების დონის პერიოდულობა, მაგალითად `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`,
ნაცვლად იმისა, რომ საათობრივი რიგი დააგროვოთ.

### კლიენტის მოთხოვნის არასავალდებულო ჰედერები

ჰედერების დაფიქსირება **ნაგულისხმევად გამორთულია**. დანიშნულების კონფიგურაციაში დააყენეთ `requestHeaderAllowlist`
და ჩართეთ **პრომპტებისა და პასუხების ექსპორტი** (დანიშნულებაზე `includeBodies: true`).
დაშვებების სია იღებს API მასივს ან ტექსტურ არეს, სადაც სახელები გამოყოფილია ახალი ხაზებით/მძიმეებით:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

სახელები ემთხვევა ზუსტად, ასოების რეგისტრის გაუთვალისწინებლად, გარდა შემთხვევისა, როცა ბოლოში არსებული ერთი `*` სათაურის სახელის არაცარიელ
პრეფიქსს არჩევს. ცალკე მდგომი `*`, სახელში ჩასმული ჩანაცვლების სიმბოლოები და HTTP სათაურების არავალიდური სახელები უარყოფილია.
დასაშვებია მაქსიმუმ 64 სელექტორი, თითოეულის სახელი/პრეფიქსი კი მაქსიმუმ 256 ASCII ბაიტისგან უნდა შედგებოდეს.
ეს პარამეტრი განცალკევებულია `headers`-ისგან, რომელიც კოლექტორთან ექსპორტიორის ავთენტიფიკაციას უზრუნველყოფს.

აღრიცხვა კითხულობს მხოლოდ `pipeline_client_request`-ს, რომელიც შევსებულია შენახული დეტალური პაიპლაინის
`clientRawRequest`-იდან (ან მოძველებული `clientRequest`-იდან). ის არასოდეს იყენებს პროვაიდერის მოთხოვნის სათაურებს სათადარიგო წყაროდ.
მოთხოვნის ჩაწერისას პაიპლაინის დეტალური ჟურნალირება ჩართული უნდა ყოფილიყო. თუ
`includeBodies` გამორთულია, ან კლიენტის მყისიერი ასლის JSON აკლია, დაზიანებულია ან მოჭრილია, სათაურის
ატრიბუტები არ გაიცემა. `maxBodyBytes`-ის გაზრდამ შეიძლება თავიდან აგაცილოთ ექსპორტისას მყისიერი ასლის მოჭრა;
თუმცა ის ვერ აღადგენს დეტალებს, რომლებიც არასოდეს შენახულა. 1 MiB-ზე დიდი ან
256-ზე მეტი სათაურის ჩანაწერის შემცველი მყისიერი ასლი უგულებელყოფილია. პრომპტის/პასუხის არსებული ექსპორტი სათაურების
აღრიცხვასთან ერთად ჩართული რჩება; დაშვებულთა სია მხოლოდ სათაურების ჩატვირთვის რეჟიმს არ უზრუნველყოფს.

არჩეული მნიშვნელობები გარდაიქმნება `http.request.header.<full lowercase header name>` OTLP სტრიქონულ მასივებად,
მაშინაც კი, თუ მხოლოდ ერთი სტრიქონია. მაგალითად, `X-OmniRoute-Meta-Team: example-team` გარდაიქმნება
`http.request.header.x-omniroute-meta-team`-ად შემდეგი მნიშვნელობით:
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`.
სრული პრეფიქსი შენარჩუნებულია: ეს ჩვეულებრივი სათაურებია, ბიზნესველების გარჩევის ან
`omniroute.metadata.*` / Langfuse მეტამონაცემებად გარდაქმნის გარეშე. `langfuseMapping` სათაურების
სემანტიკას არ ცვლის. არჩეული ერთმნიშვნელობიანი `User-Agent` ასევე ადგენს სტანდარტულ სკალარულ
`user_agent.original`-ს. ერთ მნიშვნელობაში არსებული მძიმეები გამყოფებად არ გამოიყენება. რეგისტრით განსხვავებული ვარიანტები ერთიანდება შენახული
ჩანაწერების მიმდევრობით; ნებისმიერი არავალიდური ვარიანტის შემთხვევაში სათაური მთლიანად გამოიტოვება. ატრიბუტები დალაგებულია ქვედა რეგისტრის სახელების მიხედვით.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, API-გასაღების სათაურები, სახელები, რომლებიც შეიცავს
auth/token/secret/password/credential მარკერებს, და შიდა გეიტვეის ავტორიზაციის მონაცემები ყოველთვის
გამოირიცხება, მაშინაც კი, თუ ისინი არჩეულია ან საცავში ნაწილობრივ შენიღბულია. ავტორიზაციის მონაცემების ცნობილი შაბლონები იყენებს
ავტორიზაციის მონაცემების საერთო დეტექტორს; დაფარვის მარკერები გამოიტოვება და უსაფრთხო მნიშვნელობებად არ ექსპორტირდება.
მიიღება მხოლოდ სტრიქონები და არაცარიელი სტრიქონული მასივები; რიცხვები ან ობიექტები იძულებით არ გარდაიქმნება.
არავალიდური სახელები, პროტოტიპის გასაღებები, საკონტროლო სიმბოლოები (ჰორიზონტალური ტაბულაციის გარდა) და არასწორად ფორმირებული Unicode
უგულებელყოფილია პაკეტის ჩავარდნისა და შეცდომებში მათი შიგთავსის ასახვის გარეშე.

თითოეული სპანი აღრიცხავს მაქსიმუმ 32 სათაურს, თითო სათაურზე 16 მნიშვნელობას, თითო მნიშვნელობაზე 4096 UTF-8 ბაიტს
და აღრიცხული სათაურების სახელებსა და მნიშვნელობებში ჯამურად 16384 UTF-8 ბაიტს. ზედმეტად დიდი/არავალიდური სათაურები
მთლიანად გამოიტოვება და არ იჭრება. შერჩევა ოპერატორის გადაწყვეტილებაა კონფიდენციალურობის შესახებ: უსაფრთხოდ მიჩნეული სახელებიც
შეიძლება შეიცავდეს პერსონალურ მონაცემებს და ეს შეზღუდვები/დეტექტორები პერსონალური საიდენტიფიკაციო ინფორმაციის ზოგადი გამწმენდი არ არის.

### მიწოდების შეზღუდვები

მოთხოვნები შეზღუდულია 500 სპანითა და 4 MiB UTF-8 JSON-ით, გარსის ჩათვლით.
კურსორის პაკეტის პირველ მოთხოვნამდე თითოეული დაშვებული სპანის ზომა მოწმდება. ცალკეული
სპანი, რომელიც ლიმიტს აღემატება, ამ პაკეტის არცერთ ნაწილს არ აგზავნის და სრულდება შეცდომით, რომელიც
`maxBodyBytes`-ის შემცირებას გირჩევთ; ის ჩუმად არ გამოიტოვება. წინასწარი შემოწმება ინარჩუნებს მხოლოდ ჩანაწერებზე მითითებებსა და
ბაიტების რაოდენობებს და შლის თითოეულ დროებით სპანს/JSON-ს; სპანები ხელახლა იქმნება შეზღუდული ზომის ფრაგმენტებისთვის,
ნაცვლად იმისა, რომ პაკეტის მეორე სერიალიზებული ასლი მეხსიერებაში ინახებოდეს. HTTP 408/429/5xx-ის, ქსელური შეფერხებებისა და დროის ამოწურვისას სრულდება მაქსიმუმ
სამი მცდელობა, 250/500 მწმ ექსპონენციურად მზარდი დაყოვნებით. `Retry-After`-ში მითითებულმა წამებმა ან HTTP თარიღებმა
შეიძლება დაყოვნება 5 წამამდე გაზარდოს. სხვა სტატუსები დაუყოვნებლივ იწვევს ჩავარდნას. OTLP 2xx ნაწილობრივი უარყოფაც შეცდომას იწვევს,
დაკარგული სპანის მიღების დადასტურების ნაცვლად; ცარიელი ან ვალიდური JSON დადასტურებები მიიღება,
პასუხის წაკითხვის 64 KiB ლიმიტით.

შეცდომები შეიცავს მხოლოდ ექსპორტიორის საკუთარ ფაქტებს: HTTP სტატუსს, განმეორებითი მცდელობის კლასს, მცდელობებისა და გაგზავნილი სპანების
რაოდენობას, ან დადასტურების/ქსელური შეფერხების ფიქსირებულ ფორმულირებას. კოლექტორის პასუხის სხეულები,
ნაწილობრივი წარმატების რაოდენობები და პასუხის სათაურები არასოდეს კოპირდება შეცდომებში, ჟურნალებსა თუ
მართვის პანელში. ჩავარდნილი ან ნაწილობრივ მიღებული პაკეტი დადასტურებულად არ ითვლება: დანიშნულების ადგილას ნაჩვენებია
ჩავარდნის მდგომარეობა შესაბამისი სტატუსით, კურსორი რჩება ბოლო დადასტურებულ პაკეტზე, ხოლო შემდეგი გაშვება
იმავე სტრიქონებს ხელახლა აგზავნის. მუდმივი სტატუსები ჩავარდნას გამოიწვევს, სანამ კოლექტორი ან კონფიგურაცია
არ გამოსწორდება. პასუხის დეტალებისთვის გამოიყენეთ თავად კოლექტორის ჟურნალები. გამოძახებების ჟურნალის შეცდომების შეჯამებები ინარჩუნებს
ცალკე დაფარვის მექანიზმს.
`prepare()` არაფერს ამზადებს ინფრასტრუქტურულად; ტესტი აგზავნის ზუსტად `{"resourceSpans":[]}`-ს და აჩვენებს
HTTP სტატუსს გამოძახებების ჟურნალის სპანების ჩაწერის გარეშე.

ტრეისისა და სპანის იდენტიფიკატორებია SHA-256-ის პირველი 32/16 თექვსმეტობითი ციფრი, გამოთვლილი, შესაბამისად,
`"omniroute.trace\0" + callLogId`-სა და `"omniroute.span\0" + callLogId`-ზე. ხელახლა გაგზავნისას
იდენტიფიკატორები უცვლელია. ეს დუბლირების აღმოფხვრის გარანტია არ არის: ზოგიერთი ბექენდი, მათ შორის Langfuse-ის
v4 მიღების მექანიზმი, ერთნაირი იდენტიფიკატორის მქონე სპანების დუბლირებას არ აღმოფხვრის. ავარიამ ან ფრაგმენტის ნაწილობრივმა ჩავარდნამ შეიძლება
ხელახლა გაგზავნოს მაქსიმუმ ერთი დაუდასტურებელი კურსორის პაკეტი; შესაძლოა მთელი ეს პაკეტი დუბლირდეს
და არა მხოლოდ მისი ბოლო HTTP ფრაგმენტი. კურსორის პაკეტის ზომა ამ კომპრომისის გათვალისწინებით აირჩიეთ.

### Langfuse-ის მაგალითი

საკუთარ ინფრასტრუქტურაზე განთავსებული Langfuse-ის ეგზემპლარისთვის დააკონფიგურირეთ ეს ველები:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

Authorization-ის მნიშვნელობა ლოკალურად შექმენით ლიტერალური `public-key:secret-key`
სტრიქონის Base64-კოდირებით (მაგალითად, `Buffer.from(publicKey + ":" + secretKey).toString("base64")`-ით).
რეალური ავტორიზაციის მონაცემები არ ჩასვათ ჟურნალებში, ეკრანის სურათებსა თუ პრობლემების ჩანაწერებში. გარდაქმნა ავტომატურად
ადგენს `x-langfuse-ingestion-version: 4`-ს; Authorization კვლავ `headers`-ში მიეწოდება.
როგორც სათაურები, ისე გენერირებული იდენტობის მარილი იყენებს საიდუმლო ველების დაშიფვრის
არსებულ მექანიზმსა და API-ის ჩანაცვლების მარკერებს; საჭიროა `STORAGE_ENCRYPTION_KEY`.

მაპინგი ამატებს გენერაციის ტიპს/მოდელს, მოხმარების დეტალებს JSON ფორმატში (შეყვანა/გამოყვანა/ჯამი და ხელმისაწვდომი
ქეშის გასაღებები), შეყვანის/გამოყვანის სნეპშოტებს JSON ფორმატში, ERROR/DEFAULT დონეს, გასუფთავებულ სტატუსის შეტყობინებას,
ტრეისის სახელს, სესიის იდენტიფიკატორს, არასავალდებულო გარემოს და გაფილტვრად
`langfuse.observation.metadata.<key>` ატრიბუტს პროვაიდერისთვის, მოთხოვნილი მოდელისთვის, გზისთვის, კომბინაციისთვის, ქეშის
წყაროსა და სტატუსისთვის. `langfuse.observation.completion_start_time` არის ISO 8601 ფორმატის დრო,
რომელიც უდრის დაწყების დროს + TTFT-ს, მხოლოდ მაშინ, როცა TTFT ცნობილია და ხანგრძლივობის ფარგლებშია. ღირებულების ატრიბუტები არ იგზავნება.

იდენტიფიკაციის რეჟიმები ვრცელდება `langfuse.user.id`-ზე:

- `pseudonymous` (ნაგულისხმევი): API გასაღების შიდა იდენტიფიკატორის HMAC-SHA256, შემთხვევითი,
  თითოეული დანიშნულების ადგილისთვის უნიკალური 32-ბაიტიანი მარილით. თუ მარილი არ არსებობს, ის იქმნება შექმნისას, იშიფრება
  როგორც `identitySalt`, არასოდეს ბრუნდება პასუხში და ნარჩუნდება რედაქტირებისას. გასაღების დაუმუშავებელი იდენტიფიკატორები არასოდეს
  თავსდება სპანის ატრიბუტებში. დანიშნულების ადგილის მარილის ხელახლა შექმნა/როტაცია ცვლის იდენტობებს.
- `keyName`: API გასაღების კონფიგურირებული სახელი, რომელიც განზრახ ამჟღავნებს ოპერატორის მიერ მინიჭებულ ამ იარლიყს.
- `none`: მომხმარებლის იდენტიფიკატორის გარეშე. სესიის ტეგები, არსებობის შემთხვევაში, მაინც ექსპორტირდება; ეს რეჟიმები არ
  ახდენს პრომპტის ნებისმიერი შიგთავსის ან ოპერატორის მიერ მითითებული სესიის/კორელაციის იარლიყების ანონიმიზაციას.

### დაწყება ისტორიული მონაცემების შევსების გარეშე

მხოლოდ შექმნისას ჩართეთ **დაწყება მიმდინარე პოზიციიდან (არსებული ჟურნალების გამოტოვება)** ან მიუთითეთ
`startFromCurrentPosition: true` შექმნის API მოთხოვნის მონაცემების ზედა დონეზე. ეს ანიჭებს
`cursor_row_id`-ს შენარჩუნებული გამოძახებების ჟურნალის მიმდინარე მაქსიმალურ rowid-ს, არსებული კურსორის
დამხმარე ფუნქციების გამოყენებით, მიგრაციის გარეშე. ნაგულისხმევი მნიშვნელობაა false (კურსორი 0 და შენარჩუნებული ისტორიის შევსება).
ეს არ არის განახლებისას კურსორის განულების პარამეტრი.

საზიარო `ttftMs` დამატება ასევე ამატებს nullable `ttft_ms` სვეტს BigQuery მაპერსა
და ახალი ცხრილის სქემას: მისი სქემის ტესტი მოითხოვს, რომ კანონიკური ჩანაწერის ყოველ ველს ჰქონდეს
სვეტი. არსებული ცხრილების ექსპორტი უცვლელად გრძელდება: `prepare()` კითხულობს ცხრილის სქემას და
გამოტოვებს მხოლოდ `ttft_ms`-ს, როცა ეს სვეტი არ არსებობს. დაამატეთ nullable INT64 სვეტი, რათა TTFT მიიღოთ
შემდეგი გაშვებისას, ან გამოიყენეთ ახალი ცხრილი. PATCH, სქემის ავტომატური ცვლილება ან დამატებითი
ნებართვები საჭირო არ არის; მწკრივის ყველა სხვა ველისთვის სქემის მკაცრი შემოწმება ძალაში რჩება.
