OmniRoute-ის გამოძახებების ჟურნალების უწყვეტი, ინკრემენტული ექსპორტი გარე ანალიტიკურ საცავში.

ჟურნალების დაფის ჩანართი მოთხოვნების ისტორიას SQLite-ში (`call_logs`) ინახავს, რომლის მოცულობაც
როტაციითა და შენახვის ვადით იზღუდება. ჟურნალების ექსპორტი ჩანაწერების იმავე ნაკრებს განრიგის მიხედვით აგზავნის გარეთ, რათა ის
ლოკალურ მონაცემთა ბაზაზე მეტხანს შენარჩუნდეს და სხვა მონაცემებთან გაერთიანდეს. პირველი დანიშნულების ადგილი BigQuery-ია;
დამუშავების ჯაჭვი რეესტრზეა დაფუძნებული, ამიტომ დამატებითი დანიშნულების ადგილების დამატება არსებული სტრუქტურის შეცვლას არ მოითხოვს.

## 1. როგორ მუშაობს

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **განრიგი** — ერთი `JobRegistry` cron სამუშაო, `log_export`, ნაგულისხმევი `0 * * * *` (საათობრივი, UTC). რეგისტრირებულია `src/lib/initCloudSync.ts` ში; `OMNIROUTE_LOG_EXPORT_CRON` ით . თითოეული ტკიპა დრუნავს თითოეულს** ჩართულია** დანიშნულების ადგილი, თანმიმდევრობით.
- **Cursor** — SQLite- ის ნაგულისხმევი `call_logs.rowid`, შენარჩუნებულია თითო დანიშნულების ადგილზე `log_export_destinations.cursor_row_id`. `timestamp` შეგნებულად არ არის კურსორი: აბონენტებმა შეიძლება მიაწოდონ საკუთარი მნიშვნელობა, ამიტომ ნელი მოთხოვნა შეიძლება დაიწეროს უფრო სწრაფის შემდეგ, რომელიც მოგვიანებით დაიწყო და დროის ანაბეჭდის კურსორი გამოტოვებს მას.
- **Batching** — `batch_size` რიგები თითო მოთხოვნაზე (ნაგულისხმევი 500), `max_rows_per_run` რიგები თითო პერსპექტივაში (ნაგულისხმევი 10000), ასე რომ, დიდი ნარჩენი იშლება რამდენიმე ტკიპზე, ერთის დაბლოკვის ნაცვლად.
- **მიწოდება** — კურსორი წინ მიიწევს მხოლოდ `send()` გადაწყვეტის შემდეგ. წარუმატებელი პარტია ტოვებს კურსორს იქ, სადაც იყო, ამიტომ იგივე სტრიქონები განმეორდება მომდევნო გაშვებაზე. გარანტია არის ერთხელ მაინც, პლუს დანიშნულების მხარის დუბლირება, არ არის ჭეშმარიტი ზუსტად ერთხელ: BigQuery კლავს თითოეულ სტრიქონს ზარის ჟურნალის ID-ით, რომელსაც იგი პატივს სცემს საუკეთესო ძალისხმევის საფუძველზე საკუთარი გამორთვის ფანჯარაში.
- **გადახურვის მცველი** — cron tick-ს და `POST .../run` შეუძლიათ ერთად გასროლა. დანიშნულების ადგილი, რომელიც უკვე იშლება, გამოტოვებულია და არა ორჯერ ამოწურვა (`skipped: true` გაშვების შედეგში), ასე რომ, ერთდროულ გაშვებას არ შეუძლია სერიის ხელახლა გაგზავნა ან კურსორის უკან დაწერა.
- **გაწმენდის აღდგენა** — თუ `cursor_row_id` მთავრდება `MAX(rowid)` ზე მაღლა (მთელი ცხრილი გასუფთავდა და რიგები განახლდა), მორბენალი გადახვევს 0-ზე, ვიდრე მუდმივად დაბრმავდეს.

### იზოლირებული მორბენალი და ლიმიტები

Node-ზე გაშვებული ყველა დანიშნულება იწყებს ცალკეულ, ხანმოკლე OS შვილო პროცესს (`child_process` IPC ით და არა `worker_threads`). Body reads, payload JSON parsing/serialization, დანიშნულების `prepare()` და დანიშნულების ქსელი I/O ყველა იქ მუშაობს და არა სერვერის მოვლენის ციკლში. მხოლოდ კონფიგურაციის და მცირე პროგრესის შეტყობინებები კვეთს IPC; ექსპორტირებული ჩანაწერები არასოდეს ბრუნდება სერვერზე. cron job და Run now მარშრუტი ინარჩუნებს ერთსა და იმავე საჯარო შედეგს და გადაფარავს დაცვას.

ბავშვი ხსნის სერვერის გადაწყვეტილ `DATA_DIR/storage.sqlite` მხოლოდ წაკითხვის საშუალებას `node:sqlite` ით, `busy_timeout=5000` ით და `query_only=ON`. ის არ ახდენს DB singleton-ის იმპორტს და არ ახორციელებს მიგრაციას, სარეზერვო ასლებს ან SQLite განახლებებს. Missing/corrupt არტეფაქტის აღრიცხვა (მათ შორის კორუმპირებული არტეფაქტი UPDATE) რჩება მხოლოდ დაფის დეტალების გზაზე. ორივე გზა იზიარებს წმინდა დეტალების გადამწყვეტს; ექსპორტი იყენებს ასინქრონულ ფაილურ სისტემას წაკითხულს და იგივე არტეფაქტს → legacy inline → legacy disk → არცერთი რეზოლუციის წესრიგში. გაშვება ასახავს მაქსიმალურ ჩასმა რიგს, როდესაც ბავშვი ხსნის მკითხველს; მოგვიანებით ჩანართები ელოდება შემდეგ გაშვებას. ეს არის ჩასმის საზღვარი და არა ხანგრძლივი SQLite ტრანზაქცია: WAL დამწერები და გამშვები პუნქტები თავისუფალი რჩება ქსელის ლოდინის დროს. არსებული რიგების Updates/deletions არ არის გაყინული ამ საზღვრებით.

ყოველი მიღებული სერიის შემდეგ, ბავშვი ელოდება აღიარებას. სერვერი ჯერ აგრძელებს კურსორს `advanceLogExportCursor` ით, შემდეგ აგზავნის `ack`; არცერთი შემდეგი პარტია არ იწყება მანამდე. გაგზავნის წარუმატებლობა, ავარია ან დროის ამოწურვა აღრიცხავს წარუმატებლობას ამ ჯგუფის წინსვლის გარეშე. ადრე აღიარებული პარტიები რჩება ერთგულად; მაქსიმუმ ერთი არაღიარებული პარტია შეიძლება ხელახლა გაიგზავნოს. წარმატება აღირიცხება მხოლოდ `done` და სუფთა ბავშვის გასვლის შემდეგ. წარუმატებლობა წყვეტს ბავშვს SIGTERM ით, იზრდება SIGKILL მდე 500 ms-ის შემდეგ და მორბენალი ელოდება პროცესის დახურვას.

| გარემოს ცვლადი                                | ნაგულისხმევი | მიზანი                                    |
| --------------------------------------------- | ------------ | ----------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000       | კედლის საათის ლიმიტი დანიშნულების ადგილზე |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024         | ბავშვის V8 ძველი სივრცის ლიმიტი MB ში     |

Invalid/non-positive/non-integer მნიშვნელობები იყენებს ნაგულისხმევს. გროვის პარამეტრი არ არის მთლიანი RSS ლიმიტი; ძალიან დიდ პარტიებს შეუძლიათ კვლავ ამოწურონ ბავშვის მეხსიერება და ვერ შეძლონ უსაფრთხოდ გაშვება. 1024 MB ნაგულისხმევი ტოვებს სათავეს ნაგულისხმევი 500 მწკრივი პარტიისთვის 512 KiB არტეფაქტისთვის, ჩართული ორგანოებით, BigQuery ის ბაიტი-ნაწილებად JSON სერიალიზაციის ჩათვლით. ეს არ ხდის 10000 მწკრივი სხეულის პარტიას უსაფრთხოდ. V8 გროვის ამოწურვა აღრიცხავს ქმედით წარუმატებლობას: შეამცირეთ სერიის ზომა ან გაზარდეთ `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`; კურსორი რჩება ბოლო აღიარებულ პარტიაზე. ისტორიული inline/disk სხეულები არ არის დაფარული თანამედროვე არტეფაქტის ქუდით. ოპერატორებმა ცალკე უნდა დააფინანსონ RSS, განსაკუთრებით მეხსიერებით შეზღუდული კონტეინერების შიგნით.

ბავშვი მემკვიდრეობით იღებს მხოლოდ გადაწყვეტილ `DATA_DIR`, `NODE_ENV`, აშკარა `TZ` (ფაილის სახელის მემკვიდრეობითი რეზოლუცია), `ELECTRON_RUN_AS_NODE` როდესაც ეს არის და შემდეგ გამავალ შეყვანას: `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (და მათი მცირე ასოები), `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`. გლობალური Undici დისპეჩერი იზიარებს სერვერის სუფთა გარემოს პროქსი რეზოლუციას და ლოკალური ჰოსტის შემოვლითი წესებს, `NO_PROXY` ჩათვლით; ის არ შემოაქვს `proxyFetch.ts` ან მისი DB/feature დროშები. პროქსის სერთიფიკატები რედაქტირდება გადაგზავნილი გამომავალი და ჩაწერილი შეცდომებიდან. დანიშნულების სერთიფიკატები იგზავნება მხოლოდ ერთი დაწყების IPC შეტყობინებაში, არასოდეს argv ან გარემო; output/error გადამისამართება არის პრეფიქსი და გაწმენდილი. მხოლოდ `ExperimentalWarning` არის გამორთული ბავშვის exec არგუმენტებში, რათა თავიდან იქნას აცილებული Node-ის SQLite გაფრთხილების ყოველი cron გაშვება; გაფრთხილების სხვა ტიპები რჩება ხილული.

დანიშნულების მოდულები უნდა იყოს იმპორტირებული Next.js/server-only დამოკიდებულების გარეშე. არსებული BigQuery განხორციელება უკვე აკმაყოფილებს ამ კონტრაქტს. ხელმისაწვდომობის ნიშნული ქეში გრძელდება მხოლოდ ბავშვის გაშვებისთვის და არა გაშვებების გასწვრივ. Node არის მხარდაჭერილი გაშვების დრო (`package.json` ძრავები). საუკეთესო ძალისხმევით, მხარდაჭერილი Bun თავსებადობის გზა არსებობს (`bun:sqlite` `src/lib/db/core.ts` / გადამყვანებში და `Dockerfile.bun`), ამიტომ ექსპორტი არ უნდა დაირღვეს მის ქვეშ. Bun, ექსპორტი ინარჩუნებს წინა პროცესის გზას და გამოსცემს ერთჯერად გაფრთხილებას: ბავშვის heap/timeout იზოლაცია მიუწვდომელია. გამოიყენეთ Node მოვლენის მარყუჟის და OOM იზოლაციისთვის.

როდესაც `includeBodies` ჩართულია, უპირატესობა მიანიჭეთ წუთების დონის კადენციას, როგორიცაა `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` ვიდრე საათობრივი დატვირთვის დაგროვება. პარტიებისა და მწკრივების ლიმიტები კვლავ შემოიფარგლება თითოეული გაშვებით. პროცესის გაშვების გადახდა ხდება დანიშნულების ადგილზე თითო გაშვებაზე; ეს ცვლის მცირე გაშვების ღირებულებას სერვერის მოვლენის მარყუჟის იზოლაციისთვის, არ შემცირდება CPU მთლიანი გამოყენება.

### ტვირთამწეობა (მოთხოვნები და დასრულებები)

ნაგულისხმევად, ექსპორტი შეიცავს მხოლოდ შემაჯამებელ ველებს ჟურნალებს** სია** აჩვენებს. ჩართვა** მოთხოვნისა და პასუხების ექსპორტი** (`includeBodies`) დამატებით აგზავნის იმას, რასაც Logs** დეტალი** პანელი აჩვენებს თითოეულ ზარს:

| ველი                             | რასაც ის ფლობს                                                |
| -------------------------------- | ------------------------------------------------------------- |
| `request_body` / `response_body` | ზარი იტვირთება, როგორც დაფა აჩვენებს მათ                      |
| `pipeline_route_decision`        | რომელი სამიზნე და მოდელი აირჩია როუტერმა                      |
| `pipeline_client_request`        | დაუმუშავებელი მოთხოვნა ზუსტად ისე, როგორც კლიენტმა გაგზავნა   |
| `pipeline_openai_request`        | შიდა OpenAI ფორმაში გადაყვანის შემდეგ                         |
| `pipeline_provider_request`      | როგორც რეალურად გაგზავნილია ზემოთ, პროვაიდერის დიალექტზე      |
| `pipeline_provider_response`     | ნედლეული ზედა დინების რეაქცია                                 |
| `pipeline_client_response`       | რა გადასცეს უკან გამრეკელს                                    |
| `pipeline_error`                 | მილსადენის დონის შეცდომის დეტალი წარუმატებელი ზარისთვის       |
| `bodies_truncated`               | მართალია, როდესაც ზემოთ რომელიმე ველი მოხვდება `maxBodyBytes` |

ეს არის სწრაფი შინაარსი, ასეც არის** გამორთულია ნაგულისხმევად** და განზრახ არჩევანი თითო დანიშნულების ადგილზე. რას გვიჩვენებს დაფა, რადგან ექსპორტი და `getCallLogById` იზიარებენ დეტალურ გარჩევადობას: ტვირთამწეობა უკვე გაწმენდილია PII-ით და საიდუმლოდ რედაქტირებულია, როდესაც ისინი წერენ, და `noLog` API გასაღებით განხორციელებული ზარი საერთოდ არ ინახავს დატვირთვას, ასე რომ ექსპორტი არაფერია.

დატვირთვა იკითხება თითო მწკრივზე ფაილური სისტემის არტეფაქტიდან, ასე რომ, ჰიდრატაცია მუშაობს მხოლოდ იმ მიმართულებებისთვის, რომლებიც ამას ითხოვენ. დაკარგული ან კორუმპირებული არტეფაქტი ახორციელებს მის რეზიუმეს ექსპორტს ნულოვანი დატვირთვით, ვიდრე სერიული ნაწილის გაფუჭება და კურსორის ჩაკეტვა.

`maxBodyBytes` (ნაგულისხმევი 262144) იკავებს თითოეულ ველს. უფრო გრძელი დატვირთვებია** შეკვეცილი ვიდრე ჩამოშვებული** — ამოჭრილი მოთხოვნა კვლავ პასუხობს „რა იყო დასმული“ — და მწკრივი მონიშნულია `bodies_truncated` ით. ნაკადი ნაწილ-ნაწილ დელტა არ არის ექსპორტირებული; აწყობილი პასუხი უკვე არის `pipeline_provider_response` და `pipeline_client_response`.

| `serviceAccountJson` | Service Account-ის გასაღები. საიდუმლო: დაშიფრულია შენახვისას და არასოდეს ბრუნდება                           |
| `autoCreate`         | შექმნას არარსებული dataset/table; პირობითად დაამატოს nullable usage-evidence სვეტები (ნაგულისხმევია `true`) |

Service Account-ს სამიზნე table-ზე სჭირდება `bigquery.tables.updateData`, ხოლო `autoCreate`-ის ჩართვისას —
`bigquery.datasets.create` / `bigquery.tables.create`.
არსებული table-ის განახლება ორი nullable usage-evidence ველის დასამატებლად ასევე მოითხოვს
`bigquery.tables.update`-ს. დაკარგული ნებართვა export-ს შეწყვეტს cursor-ის წინ წაწევის გარეშე.

კონფიგურირებული batch არის **cursor-ის** ერთეული და არა HTTP-ის: `send()` მას ყოფს insertAll
გამოძახებებად, თითოეულში მაქსიმუმ 500 row-ით, ამიტომ დიდი `batch_size` BigQuery-ის 10 MB-იან
request-ის ლიმიტს ვერ გადააჭარბებს. დროებითი სტატუსები (408/429/500/502/503/504) ხელახლა მუშავდება
მაქსიმუმ სამჯერ, ექსპონენციური backoff-ით და იმავე insertIds-ების ხელახლა გამოყენებით; auth-ისა და
schema-ის შეცდომები პირველივე მცდელობაზე იწვევს შეცდომას, მიმდინარე გაშვების უშედეგოდ ხარჯვის
ნაცვლად.

ახლახან შექმნილი table streaming endpoint-ისთვის ჯერ ხილული არ არის და რამდენიმე წამის განმავლობაში
აბრუნებს 404-ს. ეს 404 ხელახლა მუშავდება, მაგრამ **მხოლოდ მაშინ, როდესაც table ამ გაშვებამ შექმნა** —
ნამდვილად არარსებული table-ის შემთხვევაში შეცდომა დაუყოვნებლივ ფიქსირდება. გაითვალისწინეთ, რომ
ახლახან წაშლილი table-ის იმავე სახელით ხელახლა შექმნისას BigQuery რამდენიმე წუთის განმავლობაში
უარს ამბობს streaming insert-ებზე; ეს წაშლისა და ხელახლა შექმნის თავისებურებაა, ამიტომ table-ის
წაშლისა და ხელახლა დამატების ნაცვლად უმჯობესია ახალი table-ის სახელი გამოიყენოთ.

**ნაწილობრივი შეცდომა HTTP 200-ის სახით მოდის და არაცარიელ `insertErrors[]`-ს შეიცავს.** ეს
შეცდომად განიხილება და იწვევს exception-ს, რაც ხელს უშლის cursor-ს იმ row-ების მიღმა წინ წაწევაში,
რომლებიც BigQuery-მ არ მიიღო; `tests/unit/log-export-bigquery.test.ts` ამ ქცევას აფიქსირებს.

ტრანსპორტი არის უბრალო REST — თვითხელმოწერილი RS256 assertion იცვლება access token-ზე მისამართზე
`https://oauth2.googleapis.com/token`, შემდეგ კი row-ები იგზავნება `tabledata.insertAll`-ში. Google-ის
SDK არ იტვირთება. Access token-ები პროცესის ფარგლებში ინახება თითოეული (service account, scope)-სთვის.

შექმნილი table შეიცავს თითო სვეტს Logs ჩანართის თითოეული ველისთვის, ასევე `exported_at`-ს, და
ოპტიმიზებულია call log-ების რეალური მოთხოვნებისთვის:

- **დღის მიხედვით დაყოფილია `timestamp`-ზე**, ამიტომ მხოლოდ თარიღით შემოსაზღვრული query მხოლოდ
  შესაბამის დღეებს ასკანერებს.
- **კლასტერდება `api_key_name`, `provider`, `model`, `status`-ით** (ამ თანმიმდევრობით), ამიტომ
  იმის მიხედვით გაფილტვრა, ვინ გაუშვა მოთხოვნა, სად გაიგზავნა ან ჩავარდა თუ არა, თითოეული
  partition-ის შიგნით ბლოკებს გამოტოვებს. BigQuery მაქსიმუმ ოთხ clustering სვეტს უშვებს და
  თანმიმდევრობას მნიშვნელობა აქვს: მხოლოდ `api_key_name`-ით გაფილტვრა ბლოკებს გამოტოვებს,
  მხოლოდ `status`-ით გაფილტვრა — არა.
- **Partition-ის არასავალდებულო შენარჩუნება** `partitionExpirationDays`-ის მეშვეობით
  (`0` ყველაფერს ინარჩუნებს), რომელიც table-ის შექმნისას გამოიყენება.

ორივე პარამეტრი მხოლოდ შექმნის დროს გამოიყენება. არსებულ table-ს ის განლაგება უნარჩუნდება, რაც
უკვე აქვს, ამიტომ თუ მათი გამოყენება გსურთ, destination ახალ table id-ზე მიუთითეთ.

`tests/unit/log-export-bigquery.test.ts` ამოწმებს, რომ mapper და table schema სინქრონში რჩება,
რათა ახალი call-log სვეტი გზაში ჩუმად არ გამოტოვდეს.

Batch-ები იყოფა **როგორც row-ების რაოდენობის, ისე სერიალიზებული ბაიტების მიხედვით**. მხოლოდ
row-ების რაოდენობა საკმარისი არ არის, როდესაც payload-ები export-დება: prompt-ების შემცველი
500 row შეიძლება ათეულობით მეგაბაიტს შეადგენდეს, ხოლო insertAll 10 MB-ზე დიდ request-ს უარყოფს.
Chunk-ები იხურება 500 row-ის ან 9 MB-ის მიღწევისას — იმის მიხედვით, რომელი პირობა შესრულდება პირველად.

## 5. OTLP/HTTP ტრეისების დანიშნულება

კონფიგურაცია იყენებს `type: "otlp-http"`-ს. ეს არის შენახული ზარების ჟურნალების დაგეგმილი,
კურსორზე დაფუძნებული ექსპორტი და არა `open-sse/services/routing/otel.ts`-ში არსებული
მარშრუტიზაციის მოვლენების საუკეთესო ძალისხმევით მიწოდების sink-ი. ის არ კითხულობს და არ ცვლის
ამ sink-ის გარემოს ცვლადებს, ტაიმერებს ან ბუფერებს. ორივეს ჩართვამ შეიძლება სპანების ორი
დამოუკიდებელი სახეობა წარმოქმნას; ამ ზარების ჟურნალის სპანების გასარჩევად გამოიყენეთ
`omniroute.log-export` instrumentation scope.

| Key                      | Default / purpose                                                                         |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| `endpoint`               | საჭიროა სრული HTTP(S) ტრეისების URL; `/v1/traces` სუფიქსი არ ემატება                      |
| `headers`                | არასავალდებულო `Name: value` ხაზები ან სტრიქონების JSON ობიექტი; დაშიფრული                |
| `requestHeaderAllowlist` | ცარიელი (გამორთული); კლიენტის სათაურების სახელები/პრეფიქსები სპანის ატრიბუტებად ჩასაწერად |
| `serviceName`            | `omniroute`; რესურსის `service.name`                                                      |
| `langfuseMapping`        | `false`; ამატებს Langfuse-ის generation/session/user ატრიბუტებს                           |
| `identity`               | `pseudonymous`, `keyName` ან `none`                                                       |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                                   |
| `timeoutMs`              | `30000` თითო HTTP მცდელობაზე                                                              |
| `environment`            | დაყენებული არ არის; არასავალდებულო `langfuse.environment`                                 |

ზოგადი dashboard ამ ველებს ასახავს. `paths` იღებს API მასივს ან textarea-ს, რომელშიც ზუსტი
გზები ახალი ხაზებით/მძიმეებით არის გამოყოფილი. Embeddings, rerank და სხვა გზები გამოტოვებულია,
თუ ისინი ცალსახად არ არის დაშვებული. გამოტოვებული მწკრივებიც წინ წევს კურსორს; არსებული
runner-ის `exported`/`exportedTotal` მრიცხველები ითვლის დამუშავებულ წყაროს მწკრივებს,
მათ შორის გაფილტრულ მწკრივებსაც, და არა მიღებულ სპანებს. გაფილტვრა child-ში სრულდება
მისი IPC/cursor კონტრაქტის შეცვლის გარეშე.

URL-ის ვალიდაცია იყენებს DB-ისგან დამოუკიდებელ `parseAndValidateNonMetadataUrl` დამხმარეს
`src/shared/network/outboundUrlGuard.ts`-დან: `block-metadata` პოლიტიკას. მას აქვს იგივე
უპირობო metadata/protocol/embedded-credential შემოწმებები, რაც webhook-ის ვალიდატორს, თუმცა
private URL-ები დაშვებულია; ამასთან, ის განზრახ უშვებს localhost/LAN სამიზნეებს გლობალური
feature-flag override-ის გარეშე. ეს საშუალებას იძლევა გამოიყენოთ self-hosted Langfuse,
Phoenix, Tempo და Collector endpoint-ები, მათ შორის private HTTP endpoint-ებიც. Cloud-metadata
ჰოსტები ყოველთვის იბლოკება. Redirect-ებს არ მიჰყვება, ამიტომ collector-ს არ შეუძლია
credentials სხვა ჰოსტზე გადაამისამართოს. არსებული lexical URL guard-ის მსგავსად, ეს მექანიზმი
DNS resolution-ს არ აფიქსირებს; დააკონფიგურირეთ მხოლოდ ოპერატორის მიერ კონტროლირებადი ჰოსტები.
როდესაც endpoint სანდო ქსელში არ მდებარეობს, უპირატესობა მიანიჭეთ HTTPS-ს.

### Payload და მიწოდება

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) ატარებს ერთ
CLIENT სპანს თითო დაშვებულ მწკრივზე; მისი სახელი ზუსტად შესაბამისი request path-ია. გზის
დასახელება განასხვავებს Chat Completions-ს, Responses-სა და Messages-ს ისე, რომ სპანის
სახელში model ან identity მონაცემები არ ჩანდეს. რესურსის ატრიბუტები მოიცავს `service.name`-სა
და პაკეტის `service.version`-ს.

ჩვეულებრივი chat attempt logger (`open-sse/handlers/chatCore/attemptLogging.ts`) დასრულებისას
წერს `duration = Date.now() - startTime`-ს და timestamp-ს არ აწვდის;
`saveCallLogOperation` `src/lib/usage/callLogs.ts`-ში timestamp-ს ჩაწერის (დასრულების)
დროზე აყენებს ნაგულისხმევად. ამიტომ ექსპორტი end-ს მწკრივის timestamp-ად აყენებს, ხოლო
start-ს — end − duration მნიშვნელობად (მილიწამები გარდაიქმნება ათობით ნანოწამებად).
გამომძახებლის მიერ მიწოდებული ისტორიული timestamp-ებიც end დროდ ინარჩუნებს მნიშვნელობას;
თითო მწკრივზე start/completion-ის განმასხვავებელი არ არსებობს. null duration ნულად იქცევა.
არასწორი ან არმითითებული timestamp-ები batch-ს წარუმატებლად ასრულებს და არ ქმნის
არადეტერმინისტულ სპანებს. `ttftMs` nullable-ია და გარდაიქმნება `omniroute.ttft_ms`-ად.

ატრიბუტები მოიცავს `gen_ai.operation.name="chat"`-ს, provider-ს, მოთხოვნილ/პასუხის model-ს,
input/output tokens-ს, სურვილისამებრ cache-read/cache-creation/reasoning tokens-ს, HTTP
status-ს, combo-ს, cache source-ს, session tag-სა და correlation id-ს. მთელი რიცხვის OTLP
მნიშვნელობები და timestamp-ები ათობითი სტრიქონებია; სტრიქონები, ლოგიკური მნიშვნელობები და
წილადი რიცხვები იყენებს საკუთარ OTLP value variant-ებს. Error სპანებს აქვთ ERROR status და
გასუფთავებული status message. კანონიკურ ჩანაწერში upstream host URL არ არის, ამიტომ
`server.address` გამოტოვებულია და collector-ის model server-ად არასწორად იდენტიფიცირება
არ ხდება. Cost არ ექსპორტირდება.

მხოლოდ `includeBodies=true` ტვირთავს content-ს. `langfuseMapping=false`-ის დროს
`gen_ai.input.messages` / `gen_ai.output.messages` ატარებს OmniRoute-ის მიერ შენახულ,
გასუფთავებულ request/response body JSON-ს (parse-ვადობის შემთხვევაში კანონიკურად
გარდაქმნილს) და არა ხელახლა ფორმირებულ semconv messages მასივს. დამოკლებული/non-JSON
body-ები ნედლ ტექსტად რჩება. `langfuseMapping=true`-ის დროს body-ები გამოიცემა მხოლოდ
`langfuse.observation.input` / `langfuse.observation.output`-ის სახით; `gen_ai.*.messages`
ატრიბუტები გამოტოვებულია, რათა თითოეული body ერთხელ გაიგზავნოს. ორივე რეჟიმი მემკვიდრეობით
იღებს `maxBodyBytes`-ს hydration-ის არსებული გზიდან; `omniroute.bodies_truncated=true`
მიუთითებს დამოკლებაზე.
ამ destination-ის მიერ დამატებითი pipeline snapshot-ები ან გაუსუფთავებელი artifact-ების
წაკითხვა არ ემატება; request-header-ის არასავალდებულო capture იყენებს ქვემოთ აღწერილ
არსებულ hydrated client snapshot-ს. body-ების ექსპორტისას გამოიყენეთ წუთების სიხშირე,
მაგალითად `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`, საათობრივი backlog-ის დაგროვების
ნაცვლად.

### კლიენტის request headers-ის არასავალდებულო capture

Header capture **ნაგულისხმევად გამორთულია**. destination-ის კონფიგურაციაში დააყენეთ
`requestHeaderAllowlist` და ჩართეთ **Export prompts and responses**
(`includeBodies: true` destination-ზე).
Allowlist იღებს API მასივს ან textarea-ს, რომელშიც სახელები ახალი ხაზებით/მძიმეებით არის
გამოყოფილი:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

სახელები ერთმანეთს ემთხვევა რეგისტრის უგულებელყოფით და ზუსტად, გარდა იმ შემთხვევისა, როდესაც ბოლო პოზიციაში არსებული ერთი `*` ირჩევს header-name-ის არაცარიელ პრეფიქსს. ცალკე მდგომი `*`, ჩაშენებული wildcards და HTTP header-ის არასწორი სახელები უარყოფილია. სელექტორების რაოდენობა მაქსიმუმ 64-ია, ხოლო თითოეულის სახელი/პრეფიქსი — მაქსიმუმ 256 ASCII ბაიტი. ეს პარამეტრი განცალკევებულია `headers`-ისგან, რომელიც exporter-ს collector-თან ავთენტიფიკაციას უტარებს.

Capture კითხულობს მხოლოდ `pipeline_client_request`-ს, რომელიც შევსებულია შენახული დეტალური pipeline-ის `clientRawRequest`-იდან (ან legacy `clientRequest`-იდან). ის არასდროს იყენებს provider request headers-ს სარეზერვო წყაროდ. დეტალური pipeline logging ჩართული უნდა ყოფილიყო მოთხოვნის ჩაწერისას. `includeBodies`-ის გამორთვისას, ან client-snapshot JSON-ის არქონის, დაზიანების ან მოჭრის შემთხვევაში, header-ის ატრიბუტები არ გენერირდება. `maxBodyBytes`-ის გაზრდამ შეიძლება თავიდან აიცილოს export-ის დროს snapshot-ის მოჭრა; ის ვერ აღადგენს დეტალს, რომელიც თავდაპირველად არ იყო შენახული. 1 MiB-ზე დიდი snapshot, ან snapshot, რომელიც 256-ზე მეტ header ჩანაწერს შეიცავს, იგნორირდება. prompt/response export-ის არსებული ფუნქციონალი header capture-თან ერთად კვლავ ჩართულია; allowlist headers-only hydration რეჟიმს არ უზრუნველყოფს.

არჩეული მნიშვნელობები იქცევა `http.request.header.<full lowercase header name>` OTLP string array-ებად, ერთი სტრინგის შემთხვევაშიც კი. მაგალითად, `X-OmniRoute-Meta-Team: example-team` გადაიქცევა `http.request.header.x-omniroute-meta-team`-ად, მნიშვნელობით
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`.
სრული პრეფიქსი შენარჩუნებულია: ეს ჩვეულებრივი header-ებია, ბიზნეს-ველების parsing-ის ან `omniroute.metadata.*` / Langfuse metadata conversion-ის გარეშე. `langfuseMapping` header-ების სემანტიკას არ ცვლის. ცალკე მნიშვნელობის მქონე არჩეული `User-Agent` ასევე ადგენს სტანდარტულ scalar-ს `user_agent.original`. ერთ მნიშვნელობაში არსებული მძიმეები არ იყოფა. რეგისტრის ვარიანტები გაერთიანებულია შენახულ entry-ების მიმდევრობაში; ნებისმიერი არასწორი ვარიანტი მთლიან header-ს გამოტოვებს. ატრიბუტები დალაგებულია lowercase სახელის მიხედვით.

`Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, API-key header-ები, auth/token/secret/password/credential მარკერების შემცველი სახელები და gateway-ის შიდა credentials ყოველთვის გამოირიცხება, მაშინაც კი, თუ ისინი არჩეულია ან storage-ში ნაწილობრივ არის დაფარული. ცნობილი credential-ის შაბლონები იყენებს credential detector-ს; რედაქციის მარკერები გამოიტოვება და უსაფრთხო მნიშვნელობებად არ გაიგზავნება. მიიღება მხოლოდ სტრინგები და არაცარიელი string array-ები; რიცხვები და ობიექტები არ გარდაიქმნება. არასწორი სახელები, prototype keys, საკონტროლო სიმბოლოები (გარდა horizontal tab-ისა) და არასწორად ფორმირებული Unicode იგნორირდება ისე, რომ batch არ ჩავარდეს ან მათი შემცველობა შეცდომებში არ აისახოს.

თითოეული span იწერს მაქსიმუმ 32 header-ს, თითო header-ზე 16 მნიშვნელობას, თითო მნიშვნელობაზე 4096 UTF-8 ბაიტს და ყველა აღებული header-ის სახელსა და მნიშვნელობაზე ჯამში 16384 UTF-8 ბაიტს. ზომაზე დიდი ან არასწორი header-ები მთლიანად გამოიტოვება და არ იჭრება. Selection ოპერატორის მიერ მიღებული კონფიდენციალურობის გადაწყვეტილებაა: უსაფრთხოდ მოჩანილ სახელებშიც შეიძლება პერსონალური მონაცემები იყოს, ხოლო ეს ლიმიტები და detector-ები PII-ის ზოგადი გამწმენდი არ არის.

### მიწოდების ლიმიტები

მოთხოვნები შეზღუდულია 500 span-ით და UTF-8 JSON-ის 4 MiB-ით, envelope-ის ჩათვლით. ყოველი დაშვებული span-ის ზომა მოწმდება cursor batch-ის პირველი მოთხოვნის გაგზავნამდე. ლიმიტზე დიდი ცალკეული span batch-ის არცერთ ნაწილს არ აგზავნის და იწვევს შეცდომას მითითებით, რომ შემცირდეს
`maxBodyBytes`; ის ჩუმად არ იშლება. Preflight ინარჩუნებს მხოლოდ ჩანაწერების reference-ებსა და ბაიტების რაოდენობებს და შლის თითოეულ დროებით span-ს/JSON-ს; span-ები ხელახლა იქმნება შეზღუდული ზომის chunk-ებისთვის, რათა batch-ის მეორე სერიალიზებული ასლი მეხსიერებაში არ შეინახოს. HTTP 408/429/5xx, ქსელის შეცდომები და timeout-ები იღებს მაქსიმუმ
სამ მცდელობას, 250/500 ms-იანი ექსპონენციური backoff-ით. `Retry-After`-ის წამებმა ან HTTP თარიღებმა შეიძლება დაყოვნება 5 წამამდე გაზარდოს. სხვა სტატუსები დაუყოვნებლივ იწვევს შეცდომას. OTLP-ის 2xx partial rejection ასევე იწვევს შეცდომას დაკარგული span-ის acknowledgement-ის ნაცვლად; ცარიელი ან ვალიდური JSON acknowledgement-ები მიიღება, response-read კი 64 KiB-ით არის შეზღუდული.

შეცდომები შეიცავს მხოლოდ exporter-ის მიერ ცნობილ ფაქტებს: HTTP status-ს, retry class-ს, მცდელობების რაოდენობასა და გაგზავნილი span-ების რაოდენობას, ან acknowledgement/network failure-ის ფიქსირებულ ტექსტს. Collector-ის response body-ები, partial-success count-ები და response header-ები არასდროს კოპირდება შეცდომებში, log-ებში ან dashboard-ში. ჩავარდნილი ან ნაწილობრივ მიღებული batch acknowledgement-ს არ იღებს: destination აჩვენებს Failing-ს ამ სტატუსით, cursor რჩება ბოლოს acknowledged batch-ზე, ხოლო შემდეგი run ხელახლა აგზავნის იმავე rows-ს. Permanent status-ები განაგრძობს ჩავარდნას, სანამ collector ან configuration არ გამოსწორდება. response-ის დეტალებისთვის გამოიყენეთ collector-ის საკუთარი log-ები. Call-log-ის შეცდომების შეჯამებები ინარჩუნებს საკუთარ, განცალკევებულ redaction-ს.
`prepare()` არაფერს provision-ს არ უკეთებს; Test აგზავნის ზუსტად `{"resourceSpans":[]}`-ს და აბრუნებს
HTTP status-ს call-log span-ების ჩაწერის გარეშე.

Trace id-ები და span id-ები არის SHA-256-ის პირველი 32/16 hex ციფრი, რომელიც გამოითვლება
`"omniroute.trace\\0" + callLogId` და `"omniroute.span\\0" + callLogId` მნიშვნელობებზე. ხელახლა გაგზავნილ მონაცემებს იდენტური id-ები აქვს. ეს deduplication-ის გარანტია არ არის: ზოგი backend, მათ შორის Langfuse v4 ingestion, ერთნაირი id-ების მქონე span-ებს დუბლიკატებად არ მიიჩნევს. Crash-მა ან chunk-ის ნაწილობრივმა ჩავარდნამ შეიძლება ხელახლა გაგზავნოს მაქსიმუმ ერთი unacknowledged cursor batch; შეიძლება დუბლირდეს მთელი ეს batch და არა მხოლოდ მისი ბოლო HTTP chunk. cursor batch-ის ზომა ამ კომპრომისის გათვალისწინებით შეარჩიეთ.

### Langfuse-ის მაგალითი

Self-hosted Langfuse instance-ისთვის დააკონფიგურირეთ ეს ველები:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

Authorization-ის მნიშვნელობა ლოკალურად ააგეთ literal `public-key:secret-key`
სტრინგის Base64-ად გარდაქმნით (მაგალითად, `Buffer.from(publicKey + ":" + secretKey).toString("base64")`-ით).
რეალური credentials არ ჩასვათ log-ებში, screenshot-ებში ან issue-ებში. Mapping ავტომატურად
ადგენს `x-langfuse-ingestion-version: 4`-ს; Authorization კვლავ მიეწოდება `headers`-ში.
ორივე header და გენერირებული identity salt იყენებს დაშიფრული secret-field-ის არსებულ მექანიზმსა და API placeholder-ებს; საჭიროა `STORAGE_ENCRYPTION_KEY`.

Mapping ამატებს გენერაციის ტიპს/მოდელს, JSON-ის გამოყენების დეტალებს (შეყვანა/გამოტანა/ჯამური რაოდენობა და ხელმისაწვდომი
ქეშის გასაღებები), JSON-ის შეყვანისა და გამოტანის სნეპშოტებს, ERROR/DEFAULT დონეს, გასუფთავებულ სტატუსის შეტყობინებას,
ტრასის სახელს, სესიის ID-ს, არასავალდებულო გარემოსა და ფილტრირებად
`langfuse.observation.metadata.<key>`-ს პროვაიდერისთვის, მოთხოვნილი მოდელისთვის, გზისთვის, კომბინაციისთვის, ქეშის
წყაროსა და სტატუსისთვის. `langfuse.observation.completion_start_time` არის ISO 8601 ფორმატის მნიშვნელობა
დაწყებისას + TTFT მხოლოდ მაშინ, როდესაც TTFT ცნობილია და ხანგრძლივობის ფარგლებშია. ხარჯის ატრიბუტები არ იგზავნება.

იდენტობის რეჟიმები ვრცელდება `langfuse.user.id`-ზე:

- `pseudonymous` (ნაგულისხმევი): API გასაღების შიდა ID-ის HMAC-SHA256, თითოეული დანიშნულებისთვის შემთხვევით გენერირებული
  32-ბაიტიანი salt-ით. salt გენერირდება შექმნისას, თუ ის არ არსებობს, იშიფრება როგორც `identitySalt`, არასდროს ბრუნდება
  პასუხში და რედაქტირებისას ინარჩუნებს მნიშვნელობას. ნედლი გასაღების ID-ები არასდროს თავსდება span-ის ატრიბუტებში. დანიშნულების
  salt-ის ხელახლა შექმნა ან როტაცია ცვლის იდენტობებს.
- `keyName`: კონფიგურირებული API გასაღების სახელი, რაც განზრახ ამჟღავნებს ოპერატორის ამ იარლიყს.
- `none`: მომხმარებლის ID არ გამოიყენება. სესიის ტეგები კვლავ გაიტანება, თუ ისინი არსებობს; ეს რეჟიმები არ ანონიმიზებს
  თვითნებურ prompt-ის შიგთავსს ან ოპერატორის მიერ მიწოდებულ სესიის/კორელაციის იარლიყებს.

### უკომპენსაციოდ დაწყება

მხოლოდ შექმნისას ჩართეთ **დაიწყეთ მიმდინარე პოზიციიდან (გამოტოვეთ არსებული ჟურნალები)** ან create API-ის payload-ის ზედა დონეზე
გადასცით `startFromCurrentPosition: true`. ეს `cursor_row_id`-ს ანიჭებს შენარჩუნებული call-log-ის მწკრივების მიმდინარე მაქსიმალურ
rowid-ს არსებული cursor დამხმარე ფუნქციების გამოყენებით, მიგრაციის გარეშე. ნაგულისხმევია false (cursor 0 და შენარჩუნებული
ისტორიის უკომპენსაციოდ ჩატვირთვა). ეს არ არის განახლების დროს cursor-ის გადატვირთვის პარამეტრი.

გაზიარებული `ttftMs` დამატება ასევე ამატებს nullable `ttft_ms` სვეტს BigQuery mapper-სა და ახალი ცხრილის სქემაში:
მისი სქემის ტესტი მოითხოვს, რომ ყოველ კანონიკურ ჩანაწერის ველს ჰქონდეს სვეტი. არსებული ცხრილები უცვლელად აგრძელებენ
ექსპორტს: `prepare()` კითხულობს ცხრილის სქემას და გამოტოვებს მხოლოდ `ttft_ms`-ს, როდესაც ეს სვეტი არ არსებობს. დაამატეთ nullable INT64
სვეტი, რათა TTFT მიიღოთ შემდეგ გაშვებაზე, ან გამოიყენეთ ახალი ცხრილი. არასავალდებულო TTFT სვეტი სქემის განახლებას არ იწვევს. გამოყენების მტკიცებულების სვეტები
მიჰყვება ქვემოთ მოცემულ პირობით, არჩევით თავსებადობის პროცესს; მწკრივის სხვა ველები ინარჩუნებს სქემის მკაცრ შემოწმებას.

## 6. დანიშნულების ადგილის დამატება

1. შექმენით `src/lib/logExport/destinations/<name>.ts`, რომელიც ექსპორტზე გაიტანს `LogExportDestinationType`-ს:
   Zod-ის `configSchema`-ს, ინტერფეისისთვის განკუთვნილ `fields` აღწერილობების მასივს, `secretFields`-ს და
   `createClient(config)`-ს, რომელიც აბრუნებს `test()` / `prepare()` / `send(records)`-ს.
2. დაამატეთ ის `DESTINATIONS` მასივში, ფაილში `src/lib/logExport/registry.ts`.
3. დაწერეთ ტესტები `tests/unit/`-ში.

სულ ეს არის შესაცვლელი: მონაცემების შენახვის მექანიზმი, cron-ის დავალება, REST ფენა, საიდუმლო მონაცემების დაშიფვრა და
მართვის პანელის ფორმა — ყველა რეესტრს კითხულობს.

ორი წესი ახალი დანიშნულების ადგილისთვის:

- `send()`-მა ნაწილობრივი წარუმატებლობისას **აუცილებლად უნდა გამოისროლოს გამონაკლისი**. წარმატებით დასრულება ნიშნავს, რომ „დანიშნულების ადგილს ეს ჩანაწერები აქვს“,
  და კურსორი მათ სამუდამოდ გასცდება.
- დანიშნულების ადგილმა, რომელიც მომხმარებლის მიერ მითითებულ URL-ს იღებს, მოთხოვნის გაგზავნამდე ის უნდა შეამოწმოს
  `parseAndValidateWebhookUrl`-ის (`src/shared/network/outboundUrlGuardPolicy.ts`) მეშვეობით,
  ისევე, როგორც ამას ვებჰუკები აკეთებენ. BigQuery-ს ეს არ სჭირდება: მისი ჰოსტები მუდმივებია.

## 7. მისი გამოყენება

- **დაფა**: ინტეგრაციები → ჟურნალის ექსპორტი. დაამატეთ დანიშნულების ადგილი, გაუშვით **ტესტი**, რათა შეამოწმოთ ავტორიზაციის მონაცემები
  სტრიქონების ჩაწერის გარეშე, შემდეგ კი ჩართეთ ის.
- **დაგროვილი რიგი**: დანიშნულების თითოეული ბარათი აჩვენებს მომლოდინე სტრიქონებსა და კურსორს; `GET
/api/log-export/status` აბრუნებს იმავე მონაცემებს და ბოლო 20 დავალების გაშვებას.
- **ერთი დანიშნულების ადგილის შეცდომა სხვებს არ აჩერებს** — გაშვების შეჯამება თითოეული დანიშნულების
  სტატუსს აფიქსირებს `last_status` / `last_error`-ში, ხოლო დავალების გაშვების ისტორია ინახავს აგრეგირებულ შედეგს.
- **დანიშნულების ადგილის წაშლა მის კურსორსაც შლის.** მისი ხელახლა დამატება იწყება შენახული
  ზარების ჟურნალის უძველესი ჩანაწერიდან, რის გამოც ხელახლა იგზავნება სტრიქონები, რომლებიც დანიშნულების ადგილს შესაძლოა უკვე ჰქონდეს. BigQuery-ში თითო სტრიქონის
  `insertId` ამას მხოლოდ BigQuery-ის საკუთარი დუბლიკატების აღმოფხვრის დროის ფანჯარაში აგვარებს, ამიტომ დანიშნულების
  ადგილის წაშლას მისი გამორთვა სჯობს.

### გამოყენების მტკიცებულების სქემასთან თავსებადობა

ახალი BigQuery ცხრილები მოიცავს nullable `usage_evidence`-ს (STRING, რომელიც JSON-ს შეიცავს) და
`usage_estimated`-ს (BOOL). ჩართული `autoCreate`-ის შემთხვევაში, არსებულ ცხრილს შეიძლება დაემატოს
მხოლოდ ეს აკლებული nullable სვეტები. ექსპორტიორი ინარჩუნებს არსებულ სრულ
სქემას, ველების მეტამონაცემების ჩათვლით, და დაბრუნებული etag-ის გამოყენებით აგზავნის პირობით PATCH მოთხოვნას. სქემის
ერთდროული ცვლილება ექსპორტს წარუმატებლად ასრულებს, ნაცვლად მისი გადაწერისა; შემდეგი გაშვება ცხრილს ხელახლა წაიკითხავს.

გამორთული `autoCreate`-ის შემთხვევაში, გამოყენების მტკიცებულების მქონე ჩანაწერების ექსპორტამდე
ეს სვეტები თავად დაამატეთ. სქემის/etag-ის ნაკლული მეტამონაცემები ან წარუმატებელი განახლება ასევე ხელს უშლის
მტკიცებულების შემცველი ჩანაწერების ჩასმას. ექსპორტის კურსორი ამ შეცდომის შემთხვევაში წინ არ გადაინაცვლებს და
მტკიცებულება ჩუმად არასოდეს წაიშლება. ექსპორტის დაბლოკვისას ადგილობრივი ჟურნალის შენახვის წესები კვლავ მოქმედებს, ამიტომ
შეცდომა მოაგვარეთ, სანამ შენახული წყაროს სტრიქონებს ვადა გაუვა.
