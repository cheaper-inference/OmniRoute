OmniRoute-ის გამოძახებების ჟურნალების უწყვეტი, ინკრემენტული ექსპორტი გარე ანალიტიკურ საცავში.

ჟურნალების დაფის ჩანართი მოთხოვნების ისტორიას SQLite-ში (`call_logs`) ინახავს, რომლის მოცულობაც
როტაციითა და შენახვის ვადით იზღუდება. ჟურნალების ექსპორტი ჩანაწერების იმავე ნაკრებს განრიგის მიხედვით აგზავნის გარეთ, რათა ის
ლოკალურ მონაცემთა ბაზაზე მეტხანს შენარჩუნდეს და სხვა მონაცემებთან გაერთიანდეს. პირველი დანიშნულების ადგილი BigQuery-ია;
დამუშავების ჯაჭვი რეესტრზეა დაფუძნებული, ამიტომ დამატებითი დანიშნულების ადგილების დამატება არსებული სტრუქტურის შეცვლას არ მოითხოვს.

## 1. როგორ მუშაობს

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **განრიგი** — ერთი `JobRegistry` cron-დავალება, `log_export`, ნაგულისხმევი მნიშვნელობით `0 * * * *` (ყოველ საათში,
  UTC). რეგისტრირდება `src/lib/initCloudSync.ts`-ში; მისი გადაფარვა შესაძლებელია `OMNIROUTE_LOG_EXPORT_CRON`-ით.
  ყოველი გაშვება თანმიმდევრულად ამუშავებს ყველა **ჩართულ** დანიშნულების ადგილას გასაგზავნ ჩანაწერებს.
- **კურსორი** — SQLite-ის არაცხადი `call_logs.rowid`, რომელიც თითოეული დანიშნულების ადგილისთვის ინახება
  `log_export_destinations.cursor_row_id`-ში. `timestamp` განზრახ არ გამოიყენება კურსორად: გამომძახებელს
  შეუძლია საკუთარი მნიშვნელობა მიუთითოს, ამიტომ ნელი მოთხოვნა შეიძლება ჩაიწეროს უფრო სწრაფი მოთხოვნის შემდეგ, რომელიც
  მოგვიანებით დაიწყო, და დროის ნიშნულზე დაფუძნებული კურსორი მას გამოტოვებდა.
- **პაკეტებად დაყოფა** — თითო მოთხოვნაზე `batch_size` სტრიქონი (ნაგულისხმევად 500), თითო გაშვებაზე `max_rows_per_run` სტრიქონი
  (ნაგულისხმევად 10000), რათა დაგროვილი დიდი მოცულობა რამდენიმე გაშვებაზე დამუშავდეს და ერთი გაშვება არ დაბლოკოს.
- **მიწოდება** — კურსორი წინ მხოლოდ `send()`-ის წარმატებით დასრულების შემდეგ გადაადგილდება. პაკეტის გაგზავნის წარუმატებლობისას
  კურსორი უცვლელი რჩება, ამიტომ იმავე სტრიქონების გაგზავნა მომდევნო გაშვებისას ხელახლა ხდება. გარანტიაა
  სულ მცირე ერთხელ მიწოდება და დანიშნულების მხარეს დუბლიკატების მოცილება, და არა ნამდვილად ზუსტად ერთხელ მიწოდება: BigQuery თითოეული
  სტრიქონის გასაღებად გამოძახების ჟურნალის იდენტიფიკატორს იყენებს, რომელსაც დუბლიკატების მოცილების საკუთარი დროითი ფანჯრის ფარგლებში შესაძლებლობისამებრ ითვალისწინებს.
- **ერთდროული გაშვებისგან დაცვა** — cron-ის გაშვება და `POST .../run` შეიძლება ერთდროულად ამოქმედდეს. დანიშნულების ადგილი,
  რომლის ჩანაწერებიც უკვე მუშავდება, ორჯერ დამუშავების ნაცვლად გამოტოვებულია (გაშვების შედეგში `skipped: true`),
  ამიტომ პარალელური გაშვება ვერ გაგზავნის პაკეტს ხელახლა და ვერ გადაწერს კურსორს უფრო მცირე მნიშვნელობით.
- **აღდგენა გასუფთავების შემდეგ** — თუ `cursor_row_id` აღმოჩნდება `MAX(rowid)`-ზე მეტი (მთელი ცხრილი
  გასუფთავდა და rowid-ების ათვლა თავიდან დაიწყო), გამშვები კურსორს 0-ზე აბრუნებს, ნაცვლად იმისა, რომ ახალი ჩანაწერები მუდმივად ვეღარ დაინახოს.

### იზოლირებული გამშვები და შეზღუდვები

Node-ზე დანიშნულების ადგილისთვის ყოველი გაშვება ცალკე, ხანმოკლე ოპერაციული სისტემის შვილ პროცესს იწყებს (`child_process`
IPC-ით და არა `worker_threads`). შიგთავსის წაკითხვა, გადასაცემი მონაცემების JSON-ის პარსინგი/სერიალიზაცია, დანიშნულების ადგილის
`prepare()` და დანიშნულების ადგილის ქსელური შეტანა-გამოტანა სრულდება იქ და არა სერვერის მოვლენების ციკლში.
IPC-ით გადაიცემა მხოლოდ კონფიგურაცია და პროგრესის მცირე შეტყობინებები; ექსპორტირებული ჩანაწერები სერვერზე არასოდეს ბრუნდება.
cron-დავალება და „ახლავე გაშვების“ მარშრუტი ინარჩუნებს იმავე საჯარო შედეგსა და ერთდროული გაშვებისგან დაცვას.

შვილი პროცესი სერვერის მიერ განსაზღვრულ `DATA_DIR/storage.sqlite`-ს მხოლოდ წაკითხვის რეჟიმში ხსნის `node:sqlite`-ის გამოყენებით,
პარამეტრებით `busy_timeout=5000` და `query_only=ON`. მას არ შემოაქვს მონაცემთა ბაზის ერთიანი ეგზემპლარი და არ ასრულებს
მიგრაციებს, სარეზერვო ასლების შექმნას ან SQLite-ის განახლებებს. არტეფაქტების არარსებობის/დაზიანების აღრიცხვა (დაზიანებული
არტეფაქტის UPDATE-ის ჩათვლით) მხოლოდ დაფის დეტალური ხედის დამუშავებაში რჩება. ორივე გზა იყენებს საერთო, გვერდითი ეფექტებისგან თავისუფალ
დეტალების განმსაზღვრელ კომპონენტს; ექსპორტი იყენებს ფაილური სისტემიდან ასინქრონულ წაკითხვას და წყაროს შერჩევის იმავე რიგითობას: არტეფაქტი → ძველი
ჩაშენებული მონაცემები → ძველი დისკური მონაცემები → არაფერი. გაშვება აფიქსირებს ჩასმული ჩანაწერების მაქსიმალურ rowid-ს
იმ მომენტში, როცა შვილი პროცესი წამკითხველს ხსნის; მოგვიანებით ჩასმული ჩანაწერები შემდეგ გაშვებას ელოდება. ეს ჩასმის
საზღვარია და არა ხანგრძლივი SQLite-ტრანზაქცია: ქსელური ლოდინისას WAL-ში ჩამწერებსა და საკონტროლო წერტილების შექმნას არაფერი ზღუდავს.
არსებული სტრიქონების განახლებები/წაშლები ამ საზღვრით არ იყინება.

ყოველი მიღებული პაკეტის შემდეგ შვილი პროცესი დადასტურებას ელოდება. სერვერი ჯერ ინახავს
კურსორს `advanceLogExportCursor`-ით, შემდეგ კი აგზავნის `ack`-ს; მანამდე შემდეგი პაკეტის დამუშავება არ იწყება.
გაგზავნის შეცდომა, ავარიული შეწყვეტა ან დროის ამოწურვა აღირიცხება წარუმატებლობად ამ პაკეტისთვის კურსორის წინ გადაადგილების გარეშე. მანამდე
დადასტურებული პაკეტები შენარჩუნებული რჩება; ხელახლა შეიძლება გაიგზავნოს მაქსიმუმ ერთი დაუდასტურებელი პაკეტი.
წარმატება აღირიცხება მხოლოდ `done`-ისა და შვილი პროცესის ნორმალურად დასრულების შემდეგ. წარუმატებლობისას შვილი პროცესი წყდება
SIGTERM-ით, 500 მწმ-ის შემდეგ საჭიროების შემთხვევაში SIGKILL-ის გამოყენებით, ხოლო გამშვები პროცესის დახურვას ელოდება.

| გარემოს ცვლადი                                | ნაგულისხმევი | დანიშნულება                                                   |
| --------------------------------------------- | ------------ | ------------------------------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000       | თითოეული დანიშნულების ადგილისთვის გასული რეალური დროის ზღვარი |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024         | შვილი პროცესის V8-ის ძველი ობიექტების სივრცის ზღვარი მბ-ში    |

არასწორი/არადადებითი/არამთელი მნიშვნელობების შემთხვევაში გამოიყენება ნაგულისხმევი მნიშვნელობები. ჰიპის პარამეტრი არ არის სრული
RSS-ის ზღვარი; ძალიან დიდმა პაკეტებმა მაინც შეიძლება ამოწუროს შვილი პროცესის მეხსიერება და გაშვება უსაფრთხოდ დასრულდეს წარუმატებლობით.
ნაგულისხმევი 1024 მბ ტოვებს მეხსიერების მარაგს ნაგულისხმევი 500-სტრიქონიანი პაკეტისთვის, რომელიც 512 KiB ზომის არტეფაქტებს შეიცავს
ჩართული შიგთავსით, BigQuery-ის ბაიტებად დაყოფილი JSON-სერიალიზაციის ჩათვლით. ეს არ ხდის
უსაფრთხოს შიგთავსის შემცველ 10000-სტრიქონიან პაკეტს. V8-ის ჰიპის ამოწურვისას აღირიცხება წარუმატებლობა გამოსწორების მითითებით: შეამცირეთ პაკეტის
ზომა ან გაზარდეთ `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`; კურსორი რჩება ბოლო
დადასტურებულ პაკეტზე. ძველ ჩაშენებულ/დისკზე შენახულ შიგთავსზე თანამედროვე არტეფაქტის ზომის ზღვარი არ ვრცელდება.
ოპერატორებმა RSS-ის ბიუჯეტი ცალკე უნდა განსაზღვრონ, განსაკუთრებით მეხსიერებაშეზღუდულ კონტეინერებში.

შვილობილი პროცესი მემკვიდრეობით იღებს მხოლოდ განსაზღვრულ `DATA_DIR`-ს, `NODE_ENV`-ს, აშკარად მითითებულ `TZ`-ს (ძველი ფორმატის ფაილის სახელში
ადგილობრივი დროის განსაზღვრისთვის), `ELECTRON_RUN_AS_NODE`-ს, თუ ის არსებობს, და შემდეგ გამავალ პარამეტრებს:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (და მათ ქვედარეგისტრიან ფორმებს),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
გლობალური Undici დისპეტჩერი იყენებს სერვერის იმავე, მხოლოდ გარემოზე დაფუძნებულ პროქსის განსაზღვრისა და ლოკალური ჰოსტებისთვის
გვერდის ავლის წესებს, მათ შორის `NO_PROXY`-ს; ის არ ახდენს `proxyFetch.ts`-ის ან მისი მონაცემთა ბაზის/ფუნქციონალის ალმების იმპორტს.
პროქსის ავტორიზაციის მონაცემები იფარება გადამისამართებულ გამოტანასა და ჩაწერილ შეცდომებში. დანიშნულების ავტორიზაციის მონაცემები
გადაიცემა მხოლოდ გაშვების ერთ IPC შეტყობინებაში და არასოდეს — argv-ში ან გარემოში; გამოტანისა და შეცდომების გადამისამართებისას
ემატება პრეფიქსი და იფილტრება სენსიტიური ინფორმაცია. შვილობილი პროცესის გაშვების არგუმენტებში გამორთულია მხოლოდ `ExperimentalWarning`, რათა
Node-ის SQLite გაფრთხილება cron-ის ყოველი გაშვებისას არ განმეორდეს; სხვა ტიპის გაფრთხილებები ხილული რჩება.

დანიშნულების მოდულების იმპორტი შესაძლებელი უნდა იყოს Next.js/server-only დამოკიდებულებების გარეშე. არსებული
BigQuery იმპლემენტაცია უკვე აკმაყოფილებს ამ მოთხოვნას. წვდომის ტოკენების ქეშები მოქმედებს მხოლოდ შვილობილი პროცესის
ერთი გაშვების განმავლობაში და არა გაშვებებს შორის. მხარდაჭერილი გაშვების გარემოა Node (`package.json` engines), თუმცა README-ის Bun-ის
ინსტალაციის განყოფილება და `Dockerfile.bun` ასევე გვთავაზობს საწარმოო გარემოსთან თავსებადობის გზას
`bun:sqlite`-ის გამოყენებით (`src/lib/db/core.ts` / ადაპტერები). ამიტომ Bun-ში ექსპორტი ინარჩუნებს წინა,
იმავე პროცესში შესრულების გზას და ერთჯერად გაფრთხილებას აჩვენებს: შვილობილი პროცესის heap-ისა და დროის ლიმიტის იზოლაცია მიუწვდომელია. გამოიყენეთ
Node მოვლენათა ციკლისა და OOM-ის იზოლაციისთვის; Bun აქ მხოლოდ დეველოპმენტისთვის განკუთვნილად არ განიხილება.

როდესაც `includeBodies` ჩართულია, უპირატესობა მიანიჭეთ წუთების მასშტაბის სიხშირეს, მაგალითად,
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`, ნაცვლად საათობრივი მონაცემების დაგროვებისა.
პაკეტისა და მწკრივების ლიმიტები კვლავ ზღუდავს თითოეულ გაშვებას. პროცესის გაშვების ხარჯი თითოეულ დანიშნულებაზე ყოველი გაშვებისას გაიწევა;
ეს მცირე საწყისი ხარჯის სანაცვლოდ სერვერის მოვლენათა ციკლის იზოლაციას უზრუნველყოფს და არა CPU-ის ჯამური მოხმარების შემცირებას.

### მონაცემთა შიგთავსი (პრომპტები და გენერირებული პასუხები)

ნაგულისხმევად ექსპორტი შეიცავს მხოლოდ იმ შემაჯამებელ ველებს, რომლებსაც ჟურნალების **სია** აჩვენებს. პარამეტრის
**პრომპტებისა და პასუხების ექსპორტი** (`includeBodies`) ჩართვა დამატებით აგზავნის იმას, რასაც ჟურნალების **დეტალების**
პანელი აჩვენებს თითოეული გამოძახებისთვის:

| ველი                             | რას შეიცავს                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------- |
| `request_body` / `response_body` | გამოძახების შიგთავსი, როგორც მას მართვის პანელი აჩვენებს                              |
| `pipeline_route_decision`        | რომელი სამიზნე და მოდელი აირჩია მარშრუტიზატორმა                                       |
| `pipeline_client_request`        | დაუმუშავებელი მოთხოვნა ზუსტად ისე, როგორც კლიენტმა გაგზავნა                           |
| `pipeline_openai_request`        | შიდა OpenAI ფორმატში გარდაქმნის შემდეგ                                                |
| `pipeline_provider_request`      | როგორც რეალურად გაეგზავნა ზემდგომ სერვისს, პროვაიდერის ფორმატში                       |
| `pipeline_provider_response`     | ზემდგომი სერვისის დაუმუშავებელი პასუხი                                                |
| `pipeline_client_response`       | რაც გამომძახებელს დაუბრუნდა                                                           |
| `pipeline_error`                 | დამუშავების ჯაჭვის დონის შეცდომის დეტალები წარუმატებელი გამოძახებისთვის               |
| `bodies_truncated`               | ჭეშმარიტია, როდესაც ზემოთ ჩამოთვლილთაგან რომელიმე ველმა `maxBodyBytes` ლიმიტს მიაღწია |

ეს პრომპტის შიგთავსია, ამიტომ **ნაგულისხმევად გამორთულია** და განზრახ ირჩევა თითოეული დანიშნულებისთვის ცალ-ცალკე.
იგზავნება ის, რასაც მართვის პანელი აჩვენებს, რადგან ექსპორტი და `getCallLogById` დეტალების
ამოკითხვის საერთო მექანიზმს იყენებს: მონაცემთა შიგთავსიდან
პერსონალური საიდენტიფიკაციო ინფორმაცია და საიდუმლო მონაცემები უკვე გაფილტრულია ჩაწერისას, ხოლო
`noLog` API გასაღებით შესრულებული გამოძახება საერთოდ არ ინახავს შიგთავსს, ამიტომ საექსპორტოც არაფერია.

მონაცემთა შიგთავსი თითოეული მწკრივისთვის ფაილური სისტემის არტეფაქტიდან იკითხება, ამიტომ სრული მონაცემებით შევსება მხოლოდ იმ დანიშნულებებისთვის სრულდება,
რომლებმაც ეს მოითხოვეს. არტეფაქტის არარსებობის ან დაზიანების შემთხვევაში ექსპორტირდება მისი შეჯამება null შიგთავსით,
ნაცვლად იმისა, რომ პაკეტის დამუშავება ჩავარდეს და კურსორი გაიჭედოს.

`maxBodyBytes` (ნაგულისხმევად 262144) ზღუდავს თითოეული ველის ზომას. უფრო გრძელი შიგთავსი **იჭრება და არა
გამოიტოვება** — მოჭრილი პრომპტიც კი პასუხობს კითხვას „რა იყო მოთხოვნილი“ — და მწკრივი ინიშნება
`bodies_truncated`-ით. ნაკადად მიღებული, ფრაგმენტების მიხედვით ცვლილებები არ ექსპორტირდება; აწყობილი პასუხი
უკვე მოცემულია `pipeline_provider_response`-სა და `pipeline_client_response`-ში.

## 3. REST API

ყველა მარშრუტი მოითხოვს მართვის ავთენტიფიკაციას (`requireManagementAuth`). საიდუმლო მონაცემები არასოდეს ბრუნდება:
შენახული საიდუმლო მონაცემის ნაცვლად ბრუნდება ლიტერალი `__stored__`, ხოლო განახლებისას ამ მნიშვნელობის უკან გაგზავნა
ინარჩუნებს შენახულ ავტორიზაციის მონაცემს.

იმ დანიშნულების შექმნა ან განახლება, რომლის ტიპიც საიდუმლო მონაცემს განსაზღვრავს, **მოითხოვს
`STORAGE_ENCRYPTION_KEY`-ს**. მის გარეშე `encrypt()` მონაცემებს უცვლელად, შეტყობინების გარეშე ატარებს, ამიტომ ჩაწერა
უარყოფილია 400 კოდით, ნაცვლად იმისა, რომ ავტორიზაციის მონაცემი SQLite-ში ღია ტექსტად შეინახოს (იგივე დაცვა გამოიყენება
Telegram-ის ვებჰუკშიც).

| მეთოდი   | გზა                                      | დანიშნულება                                                                     |
| -------- | ---------------------------------------- | ------------------------------------------------------------------------------- |

## 4. BigQuery დანიშნულების ადგილი

კონფიგურაციის გასაღებები (`type: "bigquery"`):

| გასაღები             | შენიშვნები                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------ |
| `projectId`          | GCP პროექტი, რომელშიც მონაცემთა ნაკრები ინახება                                            |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                            |
| `tableId`            | `[A-Za-z0-9_]+`                                                                            |
| `location`           | გამოიყენება მხოლოდ მაშინ, როცა მონაცემთა ნაკრები შესაქმნელია (ნაგულისხმევად `EU`)          |
| `serviceAccountJson` | სერვისული ანგარიშის გასაღები. საიდუმლო: შენახვისას დაშიფრულია და არასდროს ბრუნდება პასუხში |
| `autoCreate`         | მონაცემთა ნაკრებისა და ცხრილის შექმნა პირველი ექსპორტისას (ნაგულისხმევად `true`)           |

სერვისულ ანგარიშს სამიზნე ცხრილზე სჭირდება `bigquery.tables.updateData`, ასევე
`bigquery.datasets.create` / `bigquery.tables.create`, როცა `autoCreate` ჩართულია.

კონფიგურირებული პაკეტი **კურსორის** ერთეულია და არა HTTP-ის: `send()` მას ყოფს insertAll-ის
გამოძახებებად, თითოეულში მაქსიმუმ 500 სტრიქონით, ამიტომ დიდი `batch_size` ვერ გადააჭარბებს BigQuery-ის მოთხოვნის 10 MB-იან ზღვარს.
დროებითი სტატუსების (408/429/500/502/503/504) შემთხვევაში მცდელობა მეორდება მაქსიმუმ სამჯერ, ექსპონენციალურად
მზარდი დაყოვნებით და იმავე insertIds-ის ხელახალი გამოყენებით; ავთენტიფიკაციისა და სქემის შეცდომები გამონაკლისს პირველივე მცდელობაზე წარმოშობს,
ნაცვლად იმისა, რომ შესრულების რესურსი ფუჭად დაიხარჯოს.

ახლახან შექმნილი ცხრილი სტრიმინგის ენდპოინტისთვის ჯერ არ ჩანს და ის რამდენიმე წამის
განმავლობაში 404-ს აბრუნებს. ამ 404-ის შემთხვევაში მცდელობა მეორდება, მაგრამ **მხოლოდ მაშინ, თუ ცხრილი ამ შესრულებისას შეიქმნა** —
რეალურად არარსებული ცხრილის შემთხვევაში ოპერაცია კვლავ სწრაფად წყდება შეცდომით. გაითვალისწინეთ, რომ ახლახან წაშლილი ცხრილის სახელით
ცხრილის ხელახლა შექმნისას BigQuery რამდენიმე წუთის განმავლობაში უარს ამბობს სტრიმინგულ ჩასმებზე; ეს
წაშლისა და შემდეგ ხელახლა შექმნის თავისებურებაა, ამიტომ ცხრილის წაშლასა და ხელახლა დამატებას ახალი სახელის გამოყენება ამჯობინეთ.

**ნაწილობრივი შეცდომა ბრუნდება HTTP 200-ის სახით, არაცარიელი `insertErrors[]`-ით.** ეს შეცდომად
მიიჩნევა და გამონაკლისს წარმოშობს, რაც კურსორს არ აძლევს საშუალებას, გასცდეს სტრიქონებს, რომლებიც BigQuery-ს
არ მიუღია; `tests/unit/log-export-bigquery.test.ts` ამ ქცევას აფიქსირებს.

ტრანსპორტისთვის გამოიყენება ჩვეულებრივი REST — თვითხელმოწერილი RS256 მტკიცება წვდომის ტოკენში იცვლება მისამართზე
`https://oauth2.googleapis.com/token`, შემდეგ კი სტრიქონები იგზავნება `tabledata.insertAll`-ში. Google SDK
არ ერთვება. წვდომის ტოკენები პროცესის შიგნით კეშირდება თითოეული წყვილისთვის (სერვისული ანგარიში, წვდომის არეალი).

შექმნილი ცხრილი შეიცავს თითო სვეტს ჟურნალების ჩანართის თითოეული ველისთვის და დამატებით `exported_at`-ს; მისი სტრუქტურა მორგებულია იმაზე,
თუ რეალურად როგორ სრულდება მოთხოვნები გამოძახებების ჟურნალებზე:

- **დღეების მიხედვით დაყოფილია `timestamp`-ის საფუძველზე**, ამიტომ თარიღით შეზღუდული მოთხოვნა მხოლოდ შესაბამის დღეებს ასკანირებს.
- **კლასტერიზებულია `api_key_name`, `provider`, `model`, `status`-ის მიხედვით** (ამ თანმიმდევრობით), ამიტომ გაფილტვრა იმის მიხედვით,
  თუ ვინ გაუშვა გამოძახება, სად გაიგზავნა ის ან დასრულდა თუ არა შეცდომით, თითოეულ დანაყოფში გამოსარიცხ ბლოკებს გამოტოვებს. BigQuery
  კლასტერიზაციის მაქსიმუმ ოთხ სვეტს უშვებს და თანმიმდევრობას მნიშვნელობა აქვს: მხოლოდ `api_key_name`-ით ფილტრი
  ბლოკებს გამორიცხავს, მხოლოდ `status`-ით ფილტრი კი — არა.
- **დანაყოფების შენახვის არასავალდებულო ვადა** განისაზღვრება `partitionExpirationDays`-ით (0 ყველაფერს ინახავს) და გამოიყენება
  ცხრილის შექმნისას.

ორივე პარამეტრი შექმნის დროს გამოიყენება. არსებული ცხრილი თავის ამჟამინდელ სტრუქტურას ინარჩუნებს, ამიტომ,
თუ მათი გამოყენება გსურთ, დანიშნულების ადგილს ახალი ცხრილის იდენტიფიკატორი მიუთითეთ.

`tests/unit/log-export-bigquery.test.ts` ამოწმებს, რომ გარდამქმნელი და ცხრილის სქემა ერთმანეთთან
შეთანხმებული დარჩეს, რათა გამოძახებების ჟურნალის ახალი სვეტი ექსპორტისას შეუმჩნევლად არ დაიკარგოს.

პაკეტები ნაწილებად იყოფა **როგორც** სტრიქონების რაოდენობის, **ისე** სერიალიზებული ბაიტების მოცულობის მიხედვით. მხოლოდ სტრიქონების რაოდენობა საკმარისი არ არის,
როცა მონაცემთა შიგთავსიც ექსპორტირდება: პრომპტების შემცველი 500 სტრიქონი შეიძლება ათობით მეგაბაიტს იკავებდეს, ხოლო insertAll
10 MB-ზე დიდ მოთხოვნას უარყოფს. ნაწილი სრულდება 500 სტრიქონზე ან 9 MB-ზე — იმის მიხედვით, რომელი ზღვარი მიიღწევა პირველი.

## 5. OTLP/HTTP ტრასების დანიშნულება

კონფიგურაცია იყენებს `type: "otlp-http"`-ს. ეს არის შენახული გამოძახებების ჟურნალების დაგეგმილი,
კურსორზე დაფუძნებული ექსპორტი და არა რეალურ დროში მარშრუტიზაციის მოვლენების მაქსიმალური ძალისხმევით მიმღები
`open-sse/services/routing/otel.ts`-ში. ის არ კითხულობს და არ ცვლის ამ მიმღების გარემოს
ცვლადებს, ტაიმერებსა თუ ბუფერებს. ორივეს ჩართვამ შეიძლება წარმოქმნას სპანების ორი დამოუკიდებელი სახეობა;
ამ გამოძახებების ჟურნალის სპანების გასარჩევად გამოიყენეთ `omniroute.log-export` ინსტრუმენტაციის არეალი.

| გასაღები                 | ნაგულისხმევი მნიშვნელობა / დანიშნულება                                                         |
| ------------------------ | ---------------------------------------------------------------------------------------------- |
| `endpoint`               | სავალდებულო სრული HTTP(S) ტრასების URL; `/v1/traces` სუფიქსი არ ემატება                        |
| `headers`                | არასავალდებულო `Name: value` სტრიქონები ან სტრიქონების JSON ობიექტი; დაშიფრული                 |
| `requestHeaderAllowlist` | ცარიელი (გამორთული); კლიენტის ჰედერების სახელები/პრეფიქსები სპანის ატრიბუტებად დასაფიქსირებლად |

| `identity`               | `pseudonymous`, `keyName` ან `none`                                                            |
| `paths`                  | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                                        |
| `timeoutMs`              | `30000` თითო HTTP მცდელობაზე                                                                   |

ზოგადი მართვის პანელი აჩვენებს ამ ველებს. `paths` იღებს API მასივს ან ტექსტურ არეს,
სადაც ზუსტი გზები გამოყოფილია ახალი ხაზებით/მძიმეებით. ემბედინგების, ხელახალი რანჟირებისა და სხვა გზები
გამოტოვებულია, თუ ისინი აშკარად არ არის დაშვებული. გამოტოვებული სტრიქონებიც წინ სწევს კურსორს; არსებული
გამშვების `exported`/`exportedTotal` მრიცხველები ითვლის დამუშავებულ წყაროს სტრიქონებს, გაფილტრულის
ჩათვლით, და არა მიღებულ სპანებს. ფილტრაცია ხდება შვილობილ პროცესში, მისი
IPC/კურსორის კონტრაქტის შეცვლის გარეშე.

URL-ის ვალიდაცია იყენებს მონაცემთა ბაზისგან დამოუკიდებელ `parseAndValidateNonMetadataUrl` დამხმარე ფუნქციას
`src/shared/network/outboundUrlGuard.ts`-დან: `block-metadata` პოლიტიკას. მას აქვს მეტამონაცემების/პროტოკოლის/ჩაშენებული ავტორიზაციის მონაცემების
იგივე უპირობო შემოწმებები, რაც ვებჰუკის ვალიდატორს კერძო URL-ების დაშვებისას,
თუმცა განზრახ უშვებს localhost/LAN სამიზნეებს გლობალური ფუნქციის ალმის გადაფარვის გარეშე.
ეს შესაძლებელს ხდის საკუთარ ინფრასტრუქტურაზე განთავსებული Langfuse, Phoenix, Tempo და Collector
საბოლოო წერტილების გამოყენებას, კერძო HTTP საბოლოო წერტილების ჩათვლით. ღრუბლოვანი მეტამონაცემების ჰოსტები ყოველთვის დაბლოკილია.
გადამისამართებებს არ მიჰყვება, ამიტომ კოლექტორს არ შეუძლია ავტორიზაციის მონაცემების სხვა ჰოსტზე გადამისამართება.
არსებული ლექსიკური URL დამცავის მსგავსად, ეს არ აფიქსირებს DNS გადაწყვეტის შედეგს; დააკონფიგურირეთ მხოლოდ
ოპერატორის მიერ კონტროლირებადი ჰოსტები. უპირატესობა მიანიჭეთ HTTPS-ს, როდესაც საბოლოო წერტილი სანდო ქსელში არ არის.

### მონაცემთა პაკეტი და მიწოდება

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) თითო დაშვებულ
სტრიქონზე გადასცემს ერთ CLIENT სპანს, რომელსაც სახელი მოთხოვნის ზუსტი გზის მიხედვით ენიჭება. გზის მიხედვით დასახელება განასხვავებს
ჩატის დასრულებებს, პასუხებსა და შეტყობინებებს ისე, რომ სპანის სახელში მოდელის ან იდენტობის მონაცემები
არ ჩაშენდეს. რესურსის ატრიბუტები მოიცავს `service.name`-სა და პაკეტის `service.version`-ს.

ჩატის მცდელობების სტანდარტული ჟურნალის ჩამწერი (`open-sse/handlers/chatCore/attemptLogging.ts`) დასრულებისას წერს
`duration = Date.now() - startTime`-ს და დროის ნიშნულს არ აწვდის;
`saveCallLogOperation` ფუნქცია `src/lib/usage/callLogs.ts`-ში ნაგულისხმევად დროის ნიშნულად ჩაწერის
(დასრულების) დროს იყენებს. ამიტომ ექსპორტი ადგენს: დასასრული = სტრიქონის დროის ნიშნული, ხოლო დასაწყისი = დასასრული − ხანგრძლივობა
(მილიწამები, გადაყვანილი ათობით ნანოწამებში). გამომძახებლის მიერ მოწოდებული ისტორიული დროის ნიშნულებიც
დასრულების დროდ ინახება; ცალკეული სტრიქონისთვის დაწყების/დასრულების განმასხვავებელი არ არსებობს.
ნულოვანი (`null`) ხანგრძლივობა ნულად გარდაიქმნება. არასწორი/გამოტოვებული დროის ნიშნულები იწვევს პაკეტის წარუმატებლობას და არა
არადეტერმინისტული სპანების შექმნას. `ttftMs` შეიძლება იყოს null და შეესაბამება `omniroute.ttft_ms`-ს.

ატრიბუტები მოიცავს `gen_ai.operation.name="chat"`-ს, პროვაიდერს, მოთხოვნილ/პასუხის მოდელს,
შემავალ/გამომავალ ტოკენებს, არასავალდებულო ქეშიდან წაკითხვის/ქეშის შექმნის/მსჯელობის ტოკენებს, HTTP სტატუსს,
კომბინაციას, ქეშის წყაროს, სესიის ჭდესა და კორელაციის იდენტიფიკატორს. OTLP-ის მთელი მნიშვნელობები და დროის ნიშნულები
ათობითი სტრიქონებია; სტრიქონები, ლოგიკური მნიშვნელობები და წილადი რიცხვები იყენებს შესაბამის ბუნებრივ OTLP მნიშვნელობის
ვარიანტებს. შეცდომის სპანებს აქვს ERROR სტატუსი და გასუფთავებული სტატუსის შეტყობინება. კანონიკურ
ჩანაწერში არ არის ზედა დონის ჰოსტის URL, ამიტომ `server.address` გამოტოვებულია, რათა კოლექტორი შეცდომით
მოდელის სერვერად არ იქნეს მიჩნეული. ღირებულება არ ექსპორტირდება.

მხოლოდ `includeBodies=true` ტვირთავს შიგთავსს. `langfuseMapping=false`-ის შემთხვევაში,
`gen_ai.input.messages` / `gen_ai.output.messages` შეიცავს OmniRoute-ის მიერ შენახულ, გასუფთავებულ მოთხოვნის/პასუხის
სხეულის JSON-ს (კანონიკურ ფორმაში მოყვანილს, როცა მისი გარჩევა შესაძლებელია) და არა semconv-ის ფორმატში გარდაქმნილ
შეტყობინებების მასივს. შეკვეცილი/არა-JSON სხეულები რჩება დაუმუშავებელ ტექსტად. `langfuseMapping=true`-ის შემთხვევაში,
სხეულები იგზავნება მხოლოდ `langfuse.observation.input` / `langfuse.observation.output` სახით;
`gen_ai.*.messages` ატრიბუტები გამოტოვებულია, რათა თითოეული სხეული ერთხელ გაიგზავნოს. ორივე რეჟიმი
`maxBodyBytes`-ს მემკვიდრეობით იღებს შიგთავსის ჩატვირთვის არსებული მექანიზმიდან;
`omniroute.bodies_truncated=true` აღნიშნავს შეკვეცას.
ეს დანიშნულება არ ამატებს დამუშავების ჯაჭვის დამატებით სნეპშოტებს ან გაუსუფთავებელი არტეფაქტების წაკითხვას;
მოთხოვნის ჰედერების არასავალდებულო დაფიქსირება იყენებს ქვემოთ აღწერილ, უკვე ჩატვირთულ კლიენტის სნეპშოტს.
სხეულების ექსპორტისას გამოიყენეთ წუთების დონის პერიოდულობა, მაგალითად `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`,
ნაცვლად იმისა, რომ საათობრივი რიგი დააგროვოთ.

### კლიენტის მოთხოვნის არასავალდებულო ჰედერები

ჰედერების დაფიქსირება **ნაგულისხმევად გამორთულია**. დანიშნულების კონფიგურაციაში დააყენეთ `requestHeaderAllowlist`
და ჩართეთ **პრომპტებისა და პასუხების ექსპორტი** (დანიშნულებაზე `includeBodies: true`).
დაშვებების სია იღებს API მასივს ან ტექსტურ არეს, სადაც სახელები გამოყოფილია ახალი ხაზებით/მძიმეებით:

```json
{
  "requestHeaderAllowlist": ["User-Agent", "X-Project", "X-OmniRoute-Meta-*"]
}
```

სახელები ემთხვევა ზუსტად, ასოების რეგისტრის გაუთვალისწინებლად, გარდა შემთხვევისა, როცა ბოლოში არსებული ერთი `*` სათაურის სახელის არაცარიელ
პრეფიქსს არჩევს. ცალკე მდგომი `*`, სახელში ჩასმული ჩანაცვლების სიმბოლოები და HTTP სათაურების არავალიდური სახელები უარყოფილია.
დასაშვებია მაქსიმუმ 64 სელექტორი, თითოეულის სახელი/პრეფიქსი კი მაქსიმუმ 256 ASCII ბაიტისგან უნდა შედგებოდეს.
ეს პარამეტრი განცალკევებულია `headers`-ისგან, რომელიც კოლექტორთან ექსპორტიორის ავთენტიფიკაციას უზრუნველყოფს.

აღრიცხვა კითხულობს მხოლოდ `pipeline_client_request`-ს, რომელიც შევსებულია შენახული დეტალური პაიპლაინის
`clientRawRequest`-იდან (ან მოძველებული `clientRequest`-იდან). ის არასოდეს იყენებს პროვაიდერის მოთხოვნის სათაურებს სათადარიგო წყაროდ.
მოთხოვნის ჩაწერისას პაიპლაინის დეტალური ჟურნალირება ჩართული უნდა ყოფილიყო. თუ
`includeBodies` გამორთულია, ან კლიენტის მყისიერი ასლის JSON აკლია, დაზიანებულია ან მოჭრილია, სათაურის
ატრიბუტები არ გაიცემა. `maxBodyBytes`-ის გაზრდამ შეიძლება თავიდან აგაცილოთ ექსპორტისას მყისიერი ასლის მოჭრა;
თუმცა ის ვერ აღადგენს დეტალებს, რომლებიც არასოდეს შენახულა. 1 MiB-ზე დიდი ან
256-ზე მეტი სათაურის ჩანაწერის შემცველი მყისიერი ასლი უგულებელყოფილია. პრომპტის/პასუხის არსებული ექსპორტი სათაურების
აღრიცხვასთან ერთად ჩართული რჩება; დაშვებულთა სია მხოლოდ სათაურების ჩატვირთვის რეჟიმს არ უზრუნველყოფს.

არჩეული მნიშვნელობები გარდაიქმნება `http.request.header.<full lowercase header name>` OTLP სტრიქონულ მასივებად,
მაშინაც კი, თუ მხოლოდ ერთი სტრიქონია. მაგალითად, `X-OmniRoute-Meta-Team: example-team` გარდაიქმნება
`http.request.header.x-omniroute-meta-team`-ად შემდეგი მნიშვნელობით:
`{"arrayValue":{"values":[{"stringValue":"example-team"}]}}`.
სრული პრეფიქსი შენარჩუნებულია: ეს ჩვეულებრივი სათაურებია, ბიზნესველების გარჩევის ან
`omniroute.metadata.*` / Langfuse მეტამონაცემებად გარდაქმნის გარეშე. `langfuseMapping` სათაურების
სემანტიკას არ ცვლის. არჩეული ერთმნიშვნელობიანი `User-Agent` ასევე ადგენს სტანდარტულ სკალარულ
`user_agent.original`-ს. ერთ მნიშვნელობაში არსებული მძიმეები გამყოფებად არ გამოიყენება. რეგისტრით განსხვავებული ვარიანტები ერთიანდება შენახული
ჩანაწერების მიმდევრობით; ნებისმიერი არავალიდური ვარიანტის შემთხვევაში სათაური მთლიანად გამოიტოვება. ატრიბუტები დალაგებულია ქვედა რეგისტრის სახელების მიხედვით.

Authorization, Proxy-Authorization, Cookie, Set-Cookie, API-გასაღების სათაურები, სახელები, რომლებიც შეიცავს
auth/token/secret/password/credential მარკერებს, და შიდა გეიტვეის ავტორიზაციის მონაცემები ყოველთვის
გამოირიცხება, მაშინაც კი, თუ ისინი არჩეულია ან საცავში ნაწილობრივ შენიღბულია. ავტორიზაციის მონაცემების ცნობილი შაბლონები იყენებს
ავტორიზაციის მონაცემების საერთო დეტექტორს; დაფარვის მარკერები გამოიტოვება და უსაფრთხო მნიშვნელობებად არ ექსპორტირდება.
მიიღება მხოლოდ სტრიქონები და არაცარიელი სტრიქონული მასივები; რიცხვები ან ობიექტები იძულებით არ გარდაიქმნება.
არავალიდური სახელები, პროტოტიპის გასაღებები, საკონტროლო სიმბოლოები (ჰორიზონტალური ტაბულაციის გარდა) და არასწორად ფორმირებული Unicode
უგულებელყოფილია პაკეტის ჩავარდნისა და შეცდომებში მათი შიგთავსის ასახვის გარეშე.

თითოეული სპანი აღრიცხავს მაქსიმუმ 32 სათაურს, თითო სათაურზე 16 მნიშვნელობას, თითო მნიშვნელობაზე 4096 UTF-8 ბაიტს
და აღრიცხული სათაურების სახელებსა და მნიშვნელობებში ჯამურად 16384 UTF-8 ბაიტს. ზედმეტად დიდი/არავალიდური სათაურები
მთლიანად გამოიტოვება და არ იჭრება. შერჩევა ოპერატორის გადაწყვეტილებაა კონფიდენციალურობის შესახებ: უსაფრთხოდ მიჩნეული სახელებიც
შეიძლება შეიცავდეს პერსონალურ მონაცემებს და ეს შეზღუდვები/დეტექტორები პერსონალური საიდენტიფიკაციო ინფორმაციის ზოგადი გამწმენდი არ არის.

### მიწოდების შეზღუდვები

მოთხოვნები შეზღუდულია 500 სპანითა და 4 MiB UTF-8 JSON-ით, გარსის ჩათვლით.
კურსორის პაკეტის პირველ მოთხოვნამდე თითოეული დაშვებული სპანის ზომა მოწმდება. ცალკეული
სპანი, რომელიც ლიმიტს აღემატება, ამ პაკეტის არცერთ ნაწილს არ აგზავნის და სრულდება შეცდომით, რომელიც
`maxBodyBytes`-ის შემცირებას გირჩევთ; ის ჩუმად არ გამოიტოვება. წინასწარი შემოწმება ინარჩუნებს მხოლოდ ჩანაწერებზე მითითებებსა და
ბაიტების რაოდენობებს და შლის თითოეულ დროებით სპანს/JSON-ს; სპანები ხელახლა იქმნება შეზღუდული ზომის ფრაგმენტებისთვის,
ნაცვლად იმისა, რომ პაკეტის მეორე სერიალიზებული ასლი მეხსიერებაში ინახებოდეს. HTTP 408/429/5xx-ის, ქსელური შეფერხებებისა და დროის ამოწურვისას სრულდება მაქსიმუმ
სამი მცდელობა, 250/500 მწმ ექსპონენციურად მზარდი დაყოვნებით. `Retry-After`-ში მითითებულმა წამებმა ან HTTP თარიღებმა
შეიძლება დაყოვნება 5 წამამდე გაზარდოს. სხვა სტატუსები დაუყოვნებლივ იწვევს ჩავარდნას. OTLP 2xx ნაწილობრივი უარყოფაც შეცდომას იწვევს,
დაკარგული სპანის მიღების დადასტურების ნაცვლად; ცარიელი ან ვალიდური JSON დადასტურებები მიიღება,
პასუხის წაკითხვის 64 KiB ლიმიტით.

შეცდომები შეიცავს მხოლოდ ექსპორტიორის საკუთარ ფაქტებს: HTTP სტატუსს, განმეორებითი მცდელობის კლასს, მცდელობებისა და გაგზავნილი სპანების
რაოდენობას, ან დადასტურების/ქსელური შეფერხების ფიქსირებულ ფორმულირებას. კოლექტორის პასუხის სხეულები,
ნაწილობრივი წარმატების რაოდენობები და პასუხის სათაურები არასოდეს კოპირდება შეცდომებში, ჟურნალებსა თუ
მართვის პანელში. ჩავარდნილი ან ნაწილობრივ მიღებული პაკეტი დადასტურებულად არ ითვლება: დანიშნულების ადგილას ნაჩვენებია
ჩავარდნის მდგომარეობა შესაბამისი სტატუსით, კურსორი რჩება ბოლო დადასტურებულ პაკეტზე, ხოლო შემდეგი გაშვება
იმავე სტრიქონებს ხელახლა აგზავნის. მუდმივი სტატუსები ჩავარდნას გამოიწვევს, სანამ კოლექტორი ან კონფიგურაცია
არ გამოსწორდება. პასუხის დეტალებისთვის გამოიყენეთ თავად კოლექტორის ჟურნალები. გამოძახებების ჟურნალის შეცდომების შეჯამებები ინარჩუნებს
ცალკე დაფარვის მექანიზმს.
`prepare()` არაფერს ამზადებს ინფრასტრუქტურულად; ტესტი აგზავნის ზუსტად `{"resourceSpans":[]}`-ს და აჩვენებს
HTTP სტატუსს გამოძახებების ჟურნალის სპანების ჩაწერის გარეშე.

ტრეისისა და სპანის იდენტიფიკატორებია SHA-256-ის პირველი 32/16 თექვსმეტობითი ციფრი, გამოთვლილი, შესაბამისად,
`"omniroute.trace\\0" + callLogId`-სა და `"omniroute.span\\0" + callLogId`-ზე. ხელახლა გაგზავნისას
იდენტიფიკატორები უცვლელია. ეს დუბლირების აღმოფხვრის გარანტია არ არის: ზოგიერთი ბექენდი, მათ შორის Langfuse-ის
v4 მიღების მექანიზმი, ერთნაირი იდენტიფიკატორის მქონე სპანების დუბლირებას არ აღმოფხვრის. ავარიამ ან ფრაგმენტის ნაწილობრივმა ჩავარდნამ შეიძლება
ხელახლა გაგზავნოს მაქსიმუმ ერთი დაუდასტურებელი კურსორის პაკეტი; შესაძლოა მთელი ეს პაკეტი დუბლირდეს
და არა მხოლოდ მისი ბოლო HTTP ფრაგმენტი. კურსორის პაკეტის ზომა ამ კომპრომისის გათვალისწინებით აირჩიეთ.

### Langfuse-ის მაგალითი

საკუთარ ინფრასტრუქტურაზე განთავსებული Langfuse-ის ეგზემპლარისთვის დააკონფიგურირეთ ეს ველები:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

Authorization-ის მნიშვნელობა ლოკალურად შექმენით ლიტერალური `public-key:secret-key`
სტრიქონის Base64-კოდირებით (მაგალითად, `Buffer.from(publicKey + ":" + secretKey).toString("base64")`-ით).
რეალური ავტორიზაციის მონაცემები არ ჩასვათ ჟურნალებში, ეკრანის სურათებსა თუ პრობლემების ჩანაწერებში. გარდაქმნა ავტომატურად
ადგენს `x-langfuse-ingestion-version: 4`-ს; Authorization კვლავ `headers`-ში მიეწოდება.
როგორც სათაურები, ისე გენერირებული იდენტობის მარილი იყენებს საიდუმლო ველების დაშიფვრის
არსებულ მექანიზმსა და API-ის ჩანაცვლების მარკერებს; საჭიროა `STORAGE_ENCRYPTION_KEY`.

მაპინგი ამატებს გენერაციის ტიპს/მოდელს, მოხმარების დეტალებს JSON ფორმატში (შეყვანა/გამოყვანა/ჯამი და ხელმისაწვდომი
ქეშის გასაღებები), შეყვანის/გამოყვანის სნეპშოტებს JSON ფორმატში, ERROR/DEFAULT დონეს, გასუფთავებულ სტატუსის შეტყობინებას,
ტრეისის სახელს, სესიის იდენტიფიკატორს, არასავალდებულო გარემოს და გაფილტვრად
`langfuse.observation.metadata.<key>` ატრიბუტს პროვაიდერისთვის, მოთხოვნილი მოდელისთვის, გზისთვის, კომბინაციისთვის, ქეშის
წყაროსა და სტატუსისთვის. `langfuse.observation.completion_start_time` არის ISO 8601 ფორმატის დრო,
რომელიც უდრის დაწყების დროს + TTFT-ს, მხოლოდ მაშინ, როცა TTFT ცნობილია და ხანგრძლივობის ფარგლებშია. ღირებულების ატრიბუტები არ იგზავნება.

იდენტიფიკაციის რეჟიმები ვრცელდება `langfuse.user.id`-ზე:

- `pseudonymous` (ნაგულისხმევი): API გასაღების შიდა იდენტიფიკატორის HMAC-SHA256, შემთხვევითი,
  თითოეული დანიშნულების ადგილისთვის უნიკალური 32-ბაიტიანი მარილით. თუ მარილი არ არსებობს, ის იქმნება შექმნისას, იშიფრება
  როგორც `identitySalt`, არასოდეს ბრუნდება პასუხში და ნარჩუნდება რედაქტირებისას. გასაღების დაუმუშავებელი იდენტიფიკატორები არასოდეს
  თავსდება სპანის ატრიბუტებში. დანიშნულების ადგილის მარილის ხელახლა შექმნა/როტაცია ცვლის იდენტობებს.
- `keyName`: API გასაღების კონფიგურირებული სახელი, რომელიც განზრახ ამჟღავნებს ოპერატორის მიერ მინიჭებულ ამ იარლიყს.
- `none`: მომხმარებლის იდენტიფიკატორის გარეშე. სესიის ტეგები, არსებობის შემთხვევაში, მაინც ექსპორტირდება; ეს რეჟიმები არ
  ახდენს პრომპტის ნებისმიერი შიგთავსის ან ოპერატორის მიერ მითითებული სესიის/კორელაციის იარლიყების ანონიმიზაციას.

### დაწყება ისტორიული მონაცემების შევსების გარეშე

მხოლოდ შექმნისას ჩართეთ **დაწყება მიმდინარე პოზიციიდან (არსებული ჟურნალების გამოტოვება)** ან მიუთითეთ
`startFromCurrentPosition: true` შექმნის API მოთხოვნის მონაცემების ზედა დონეზე. ეს ანიჭებს
`cursor_row_id`-ს შენარჩუნებული გამოძახებების ჟურნალის მიმდინარე მაქსიმალურ rowid-ს, არსებული კურსორის
დამხმარე ფუნქციების გამოყენებით, მიგრაციის გარეშე. ნაგულისხმევი მნიშვნელობაა false (კურსორი 0 და შენარჩუნებული ისტორიის შევსება).
ეს არ არის განახლებისას კურსორის განულების პარამეტრი.

საზიარო `ttftMs` დამატება ასევე ამატებს nullable `ttft_ms` სვეტს BigQuery მაპერსა
და ახალი ცხრილის სქემას: მისი სქემის ტესტი მოითხოვს, რომ კანონიკური ჩანაწერის ყოველ ველს ჰქონდეს
სვეტი. არსებული ცხრილების ექსპორტი უცვლელად გრძელდება: `prepare()` კითხულობს ცხრილის სქემას და
გამოტოვებს მხოლოდ `ttft_ms`-ს, როცა ეს სვეტი არ არსებობს. დაამატეთ nullable INT64 სვეტი, რათა TTFT მიიღოთ
შემდეგი გაშვებისას, ან გამოიყენეთ ახალი ცხრილი. PATCH, სქემის ავტომატური ცვლილება ან დამატებითი
ნებართვები საჭირო არ არის; მწკრივის ყველა სხვა ველისთვის სქემის მკაცრი შემოწმება ძალაში რჩება.

## 6. დანიშნულების ადგილის დამატება

1. შექმენით `src/lib/logExport/destinations/<name>.ts`, რომელიც ექსპორტზე გაიტანს `LogExportDestinationType`-ს:
   Zod-ის `configSchema`-ს, ინტერფეისისთვის განკუთვნილ `fields` აღწერილობების მასივს, `secretFields`-ს და
   `createClient(config)`-ს, რომელიც აბრუნებს `test()` / `prepare()` / `send(records)`-ს.
2. დაამატეთ ის `DESTINATIONS` მასივში, ფაილში `src/lib/logExport/registry.ts`.
3. დაწერეთ ტესტები `tests/unit/`-ში.

სულ ეს არის შესაცვლელი: მონაცემების შენახვის მექანიზმი, cron-ის დავალება, REST ფენა, საიდუმლო მონაცემების დაშიფვრა და
მართვის პანელის ფორმა — ყველა რეესტრს კითხულობს.

ორი წესი ახალი დანიშნულების ადგილისთვის:

- `send()`-მა ნაწილობრივი წარუმატებლობისას **აუცილებლად უნდა გამოისროლოს გამონაკლისი**. წარმატებით დასრულება ნიშნავს, რომ „დანიშნულების ადგილს ეს ჩანაწერები აქვს“,
  და კურსორი მათ სამუდამოდ გასცდება.
- დანიშნულების ადგილმა, რომელიც მომხმარებლის მიერ მითითებულ URL-ს იღებს, მოთხოვნის გაგზავნამდე ის უნდა შეამოწმოს
  `parseAndValidateWebhookUrl`-ის (`src/shared/network/outboundUrlGuardPolicy.ts`) მეშვეობით,
  ისევე, როგორც ამას ვებჰუკები აკეთებენ. BigQuery-ს ეს არ სჭირდება: მისი ჰოსტები მუდმივებია.

## 7. გამოყენება

- **მართვის პანელი**: ინტეგრაციები → ჟურნალის ექსპორტი. დაამატეთ დანიშნულების ადგილი, გაუშვით **ტესტი**, რათა შეამოწმოთ ავტორიზაციის მონაცემები
  ჩანაწერების ჩაწერის გარეშე, შემდეგ კი ჩართეთ ის.
- **დაგროვილი ჩანაწერები**: დანიშნულების ადგილის თითოეულ ბარათზე ნაჩვენებია მომლოდინე ჩანაწერები და კურსორი; `GET
/api/log-export/status` აბრუნებს იმავე მაჩვენებლებს და დავალების ბოლო 20 გაშვებას.
- **ერთი დანიშნულების ადგილის წარუმატებლობა სხვების წარუმატებლობას არ იწვევს** — გაშვების შეჯამება თითოეული დანიშნულების ადგილის
  სტატუსს ინახავს `last_status` / `last_error`-ში, ხოლო დავალების გაშვებების ისტორია ინახავს ერთობლივ შედეგს.
- **დანიშნულების ადგილის წაშლა მის კურსორსაც შლის.** მისი ხელახლა დამატებისას დამუშავება იწყება შენახული გამოძახებების ჟურნალის
  უძველესი ჩანაწერიდან, რაც ხელახლა აგზავნის ჩანაწერებს, რომლებიც დანიშნულების ადგილს შესაძლოა უკვე ჰქონდეს. BigQuery-ში თითოეული ჩანაწერის
  `insertId` დუბლირებას მხოლოდ თავად BigQuery-ის დუბლიკატების მოცილების დროითი ფანჯრის ფარგლებში აღკვეთს, ამიტომ დანიშნულების ადგილის
  წაშლას მისი გამორთვა ამჯობინეთ.
