## ნულოვანი კონფიგურაციის ავტომარშრუტიზაცია (`auto/` პრეფიქსი)

> **ახალი:** კომბოს შექმნა საჭირო არ არის. გამოიყენეთ `auto/` პრეფიქსი პირდაპირ ნებისმიერ კლიენტში.

### სწრაფი მაგალითები

| მოდელის ID     | ვარიანტი | ქცევა                                                                                  |
| -------------- | -------- | -------------------------------------------------------------------------------------- |
| `auto`         | default  | ყველა დაკავშირებული პროვაიდერი, LKGP სტრატეგია, დაბალანსებული წონები                   |
| `auto/coding`  | coding   | ხარისხზე ორიენტირებული წონები, შესაფერისია კოდის გენერირებისთვის                       |
| `auto/fast`    | fast     | დაბალი დაყოვნების მქონე შეწონილი არჩევა                                                |
| `auto/cheap`   | cheap    | ხარჯზე ოპტიმიზებული მარშრუტიზაცია (ჯერ ყველაზე დაბალი ღირებულება)                      |
| `auto/offline` | offline  | უპირატესობას ანიჭებს კვოტის უმაღლესი ხელმისაწვდომობის მქონე პროვაიდერებს               |
| `auto/smart`   | smart    | ხარისხი უპირველესად + კვლევის უფრო მაღალი მაჩვენებელი (10%) მოდელების უკეთ აღმოსაჩენად |
| `auto/lkgp`    | lkgp     | ცხადად მითითებული LKGP (იგივეა, რაც ნაგულისხმევი `auto`)                               |
| `auto/chaos`   | chaos    | პარალელური განშტოება, თითო მოდელი თითო პროვაიდერზე (არა ხარვეზების ინიექცია)           |

### კატეგორია × დონის კომპოზიცია (`auto/<category>:<tier>`)

OpenRouter-ის სტილის სუფიქსები ერთმანეთისგან გამოყოფს **მარშრუტის ტიპს** (კატეგორია) და **მისი ოპტიმიზაციის გზას** (დონე), ამიტომ მათი თავისუფლად კომბინირება შეგიძლიათ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **კატეგორიები** (კანდიდატების ნაკრების შესაძლებლობების მიხედვით გაფილტვრა): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` ტოვებს ხედვის შესაძლებლობის მქონე მოდელებს; `reasoning` ტოვებს მსჯელობის/აზროვნების მოდელებს.
- **დონეები** (შეფასების წონების / ნაკრების ფილტრის არჩევა): `fast` (სწრაფი მიწოდება) · `cheap` (`floor`-ის ფსევდონიმი, ხარჯების დამზოგავი) · `reliable` (ავარიული გამთიშველის მდგომარეობა + დაყოვნების სტაბილურობა) · `free` / `pro` (ნაკრების გაფილტვრა მოდელის დონის მიხედვით `classifyTier`-ის მეშვეობით — უფასო დონე პრემიუმის წინააღმდეგ).

| მაგალითი               | რად გარდაიქმნება                                                           |
| ---------------------- | -------------------------------------------------------------------------- |
| `auto/coding:fast`     | კოდირების ნაკრები, დაბალი დაყოვნების წონები                                |
| `auto/coding:cheap`    | კოდირების ნაკრები, ხარჯზე ოპტიმიზებული (`auto/coding:floor`-ის ფსევდონიმი) |
| `auto/reasoning:pro`   | მხოლოდ მსჯელობის/აზროვნების მოდელები, პრემიუმ-დონე                         |
| `auto/vision`          | ხედვის შესაძლებლობის მქონე მოდელები (დონის გარეშე → დაბალანსებული წონები)  |
| `auto/multimodal:free` | მულტიმოდალური შესაძლებლობის მქონე მოდელები, მხოლოდ უფასო დონე              |

ნებისმიერი მართებული `auto/<category>[:<tier>]` მოთხოვნისას დინამიკურად განისაზღვრება; შერჩეული ქვეჯგუფი გამოქვეყნებულია `/v1/models`-ში და მართვის პანელში (`AUTO_SUFFIX_VARIANTS` ფაილში `open-sse/services/autoCombo/builtinCatalog.ts`). გაფილტვრა არის **fail-open** — თუ შეზღუდვას არცერთი დაკავშირებული მოდელი არ შეესაბამება, გამოიყენება სრული ნაკრები, რათა მარშრუტიზაცია არასოდეს შეფერხდეს. ძირითადი შემფასებელი (`combo.ts`) უცვლელია; კატეგორიის/დონის ფილტრი გამოიყენება `buildAutoCandidates`-ში.

> **მოდელების რეალურ დროში მიღებული მონაცემები:** ავტომარშრუტიზაციის შესაბამისობა ეფუძნება რეალურ დროში მიღებულ **Arena ELO** რეიტინგებს + **models.dev**-ის დონის მონაცემებს, როდესაც `ARENA_ELO_SYNC_ENABLED` დროშა ჩართულია (წინააღმდეგ შემთხვევაში გამოიყენება შესაბამისობის სტატიკური რუკა).

**გამოყენების წესი:**

```bash
# ნებისმიერი IDE ან CLI ინსტრუმენტი, რომელსაც OpenAI-ის ფორმატის მხარდაჭერა აქვს
Base URL: http://localhost:20128/v1
API Key:  <თქვენი-ბოლო-წერტილის-გასაღები>

# თქვენს კოდში/კონფიგურაციაში მოდელი დააყენეთ შემდეგ მნიშვნელობაზე:
model: "auto"                 # დაბალანსებული ნაგულისხმევი ვარიანტი
model: "auto/coding"          # საუკეთესოა კოდირების ამოცანებისთვის
model: "auto/fast"            # ყველაზე სწრაფი ხელმისაწვდომი
model: "auto/cheap"           # ყველაზე იაფი თითო ტოკენზე
```

**რა ხდება:**

1. OmniRoute აფიქსირებს `auto/` პრეფიქსს `src/sse/handlers/chat.ts`-ში
2. მონაცემთა ბაზიდან მოითხოვს ყველა **აქტიურ პროვაიდერულ კავშირს**
3. ფილტრავს და ტოვებს მათ, რომლებსაც მართებული ავტორიზაციის მონაცემები აქვთ (API გასაღები ან OAuth ტოკენი)
4. განსაზღვრავს მოდელს თითოეული კავშირისთვის (`connection.defaultModel` ან პროვაიდერის პირველი მოდელი)
5. მეხსიერებაში ქმნის **ვირტუალურ კომბოს** (DB-ში არ ინახება)
6. მარშრუტიზაციას ახორციელებს არჩეული ვარიანტის წონების პროფილის + LKGP სტრატეგიის გამოყენებით

**ძირითადი მახასიათებლები:**

- ✅ **ყოველთვის ჩართული:** გადამრთველი, კომბოს შექმნა ან კონფიგურაცია საჭირო არ არის
- ✅ **დინამიკური:** ავტომატურად ასახავს ამჟამად დაკავშირებულ პროვაიდერებს
- ✅ **სესიის მიჯაჭვულობა:** LKGP უზრუნველყოფს, რომ ბოლო წარმატებულ პროვაიდერს პრიორიტეტი მიენიჭოს
- ✅ **მრავალი ანგარიშის მხარდაჭერა:** თითოეული პროვაიდერული კავშირი ცალკე კანდიდატი ხდება
- ✅ **DB-ში ჩაწერის გარეშე:** ვირტუალური კომბო მხოლოდ მოთხოვნის განმავლობაში არსებობს, შენახვის ნულოვანი ზედნადები ხარჯით

### კანდიდატების მართვა თითოეული გასაღებისთვის (#7819, დონე 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = სუფიქსი `auto/`-ის შემდეგ, ან
საბაზისო არხისთვის სიტყვასიტყვითი `auto`) არის **მხოლოდ წასაკითხი** ბოლო წერტილი, რომელიც ჩამოთვლის
`auto/*` არხის კანდიდატების მიმდინარე ნაკრებს რეალურ დროში მიღებული ხელმისაწვდომობის მონაცემებით,
არსებული მდგრადობის წაკითხვების ხელახლა გამოყენებით (არასოდეს გამოიყენება გამთიშველის დაუმუშავებელი `state`):

- პროვაიდერის ავარიული გამთიშველი — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- კავშირის მოცდის პერიოდი — `rateLimitedUntil` / `testStatus` შესაბამის
  `provider_connections` მწკრივში
- მოდელის დაბლოკვა — `isModelLocked(provider, connectionId, model)`

თითოეულ კანდიდატს ასევე ახლავს ამ API გასაღების `excluded` დროშა. გამონაკლისები ინახება
ცალ-ცალკე თითოეული API გასაღებისთვის (`auto_candidate_overrides` ცხრილი, მიგრაცია `128`) — OmniRoute
ერთმომხმარებლიანია და `users` ცხრილი არ გააჩნია, ამიტომ `apiKeyId` არის რეალური
ინდივიდუალური გამომძახებლის იდენტობის უახლოესი ანალოგი — და აღსრულდება კანდიდატების ნაკრების საკონტროლო წერტილში,
`open-sse/services/autoCombo/virtualFactory.ts`-ში, სუფთა, მოდულურად ტესტირებული
`filterExcludedCandidates()`-ის მეშვეობით (`open-sse/services/autoCombo/candidateOverrides.ts`).
ფილტრი არის **fail-open**: დაუყენებელი apiKeyId/არხი ან DB-ის ძიების შეცდომა
ნაკრებს გაუფილტრავს ტოვებს, ამიტომ ოპერატორისთვის, რომელსაც გამონაკლისები კონფიგურირებული არ აქვს, მარშრუტიზაცია
ბაიტობრივად იდენტური რჩება ამ ფუნქციის დამატებამდელ ქცევასთან.

**გადადებულია შემდგომ საკითხზე:** თითოეული კანდიდატის წონები + ცხადი თანმიმდევრობა (დონე 3
— ერთვის არსებულ შეწონილ/პრიორიტეტულ სტრატეგიათა გზებს) და კონკრეტული
`combo.ts` სტრატეგიის მიბმა თითოეულ `auto/*` არხზე (დონე 4). იხილეთ #7819 გეგმა ღია
კითხვისთვის: ერთმომხმარებლიანი მოდელის გათვალისწინებით, ჩანაცვლებები თითოეულ API გასაღებზე უნდა დარჩეს თუ გლობალური გახდეს.

ავტომატური შეფასება თითოეული მოთხოვნისთვის საუკეთესო პროვაიდერს/მოდელს ირჩევს

## ანგარიშის პარამეტრები შენახული ავტომატური კომბინაციებისთვის

ინტელექტუალური ავტო რედაქტორი გთავაზობთ არასავალდებულო** ანგარიშის პარამეტრები** განყოფილება. თითოეული კავშირი შეიძლება იყოს სასურველი, ნორმალური (ნაგულისხმევი), დაჯავშნა ან გამორიცხული. მრავალ კავშირს შეუძლია იარუსის გაზიარება. ავტო ირჩევს პირველ დასაშვებ იარუსში, ინარჩუნებს თავის scoring/router ქცევას იქ; წარუმატებელი მცდელობები გადადის დანარჩენ კონკრეტულ ანგარიშებზე, რომლებიც სასურველია რეზერვამდე ნორმალურად ადრე. გამორიცხული კავშირები არასოდეს გამოიყენება ამ კომბინაციის მიერ.

პარამეტრი ინახება როგორც `config.accountPreferences`, ჩართულია ID კავშირით:

```json
{
  "accountPreferences": {
    "connection-a": "preferred",
    "connection-b": "preferred",
    "connection-c": "reserve",
    "connection-d": "excluded"
  }
}
```

გამოტოვებული ან ცარიელი რუკა ინარჩუნებს არსებულ მარშრუტიზაციას. პრეფერენციები არ რთავს გათიშულ კავშირებს, არ ანიჭებს API კლავიშზე წვდომას, არ აღადგენს კვოტით დაბლოკილ კანდიდატებს ან არ არღვევს ბიუჯეტის შემოწმებებს. ყოველი მცდელობა შემოიფარგლება მისი კონკრეტული კავშირით, ასე რომ, ანგარიშის სარეზერვო სისტემა ვერ გადალახავს საფეხურებს კომბინირებული როუტერის უკან. სესიის არსებულმა კავშირმა შეიძლება შეინარჩუნოს შესაბამისი ანგარიში; ანგარიშების ჩუმად შეცვლის ნაცვლად, ანგარიშების ჩუმად შეცვლის ნაცვლად, აჩერებს ისეთ ტურს, რომელიც დაკავშირებულია ბუნებრივ ბრუნთან დაკავშირებული ანგარიშის გამოკლებით.

კონფიგურირებული პრეფერენციები იყენებს ანგარიშის ცოდნის ავტო გზას: შეუზღუდავი კონტექსტური ქეში, ჭკვიანი მილსადენი, ქაოსი და ჩრდილოვანი მალსახმობები არ იგზავნება. სპეკულაციური ჰეჯირება გამორთულია ამ მოთხოვნებისთვის, ამიტომ სარეზერვო ანგარიშებს არ შეუძლიათ შეჯიბრება უპირატესობებთან. სხვა კომბინირებული სტრატეგიები არ ახდენს ამ პარამეტრის ინტერპრეტაციას. კომბინაციის შეცვლა Auto-დან დაშორებით ინახავს შენახულ პრეფერენციებს მოგვიანებით გადართვისთვის.

## კლიენტიდან მორგებული კომბოს გამოძახება

შენახული კომბოები (პარამეტრები → კომბოები) გამოიყენება მხოლოდ მაშინ, როდესაც კლიენტი `model` ველში აგზავნის კომბოს **ზუსტ სახელს** — კომბოს სახელის მიახლოებითი ან ნაწილობრივი დამთხვევა არ ხდება და `auto/` პრეფიქსიც არ გამოიყენება. განსაზღვრის თანმიმდევრობა (`getComboForModel()` ფაილში `src/sse/services/model.ts`):

1. კომბოს სახელის ზუსტი დამთხვევა (`model: "my-combo"`),
2. `combo/<name>` პრეფიქსი (`model: "combo/my-combo"`),
3. model→combo glob შესაბამისობები (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ორი გავრცელებული შეცდომა:

- **`auto` თქვენს კომბოებს არ იყენებს.** `auto`/`auto/*` ქმნის საკუთარ, ნულოვანი კონფიგურაციის მქონე კანდიდატთა ერთობლიობას და შენახულ კომბოებს მხოლოდ მაშინ ამოწმებს, თუ რომელიმე კომბოს პირდაპირ `auto` ჰქვია (არ არის რეკომენდებული). კომბოს გავლით მარშრუტიზაციისთვის გაგზავნეთ მისი ზუსტი სახელი — არა `auto`.
- **`openrouter/auto` არის OpenRouter-ის რეალური ფასიანი პროდუქტი** („ავტომატურად საუკეთესო ხელმისაწვდომი“) და არა OmniRoute-ის ფსევდონიმი. ის OpenRouter-ის რეესტრის ერთადერთი სტატიკური მოდელის ჩანაწერია (`open-sse/config/providers/registry/openrouter/index.ts`) და მისი საფასური ცალკე ირიცხება. `auto` ერთობლიობებიდან მის გამოსარიცხად გამოიყენეთ პარამეტრები → მარშრუტიზაცია → ფასიანი მოდელების დამალვა.

თავდაპირველი გაუგებრობის შესახებ, რომელსაც ეს დოკუმენტაცია განმარტავს, იხილეთ [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) და [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111).

## როგორ მუშაობს (შენახული Auto-Combo-ები)

Auto-Combo Engine თითოეული მოთხოვნისთვის დინამიკურად ირჩევს საუკეთესო პროვაიდერს/მოდელს **16-ფაქტორიანი შეფასების ფუნქციის** გამოყენებით (განსაზღვრულია `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`-ში). ნაგულისხმევი წონების ჯამია `1.0`; მორგებული წონების ხელახალი ნორმალიზება ხდება `normalizeScoringWeights()`-ის მიერ. თექვსმეტი ფაქტორიდან ორს — `cacheAffinity`-სა და `resetWindowAffinity`-ს — ნაგულისხმევად აქვს წონა `0`; `reliability`-ს `DEFAULT_WEIGHTS`-ში აქვს `0`, მაგრამ ზოგად პაკეტებში — `0.03`, ხოლო `reliability-first`-ში — `0.04`; `quality`-ს კი პაკეტებში აქვს `0.02` (`quality-first`-ში — `0.03`): ისინი მაინც გამოითვლება თითოეული კანდიდატისთვის, ხოლო `cacheAffinity` შეფასების მიღმა მართავს მოთხოვნის ქეშის დუბლირების აღმოფხვრას, ამიტომ ნულოვანი ნაგულისხმევი წონის მქონე ფაქტორები ნაგულისხმევად უბრალოდ არ მონაწილეობენ შეფასებაში, პაკეტებში კი მონაწილეობენ.

### `weighted` სემანტიკა

`weighted` არის ა** პროპორციული შემთხვევითი გათამაშება თითო მოთხოვნაზე** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), არა ექვალაიზერი:

- თითოეული მოთხოვნა იხრება** ერთი** ნაბიჯი ალბათობით `weight / totalWeight`; დარჩენილი საფეხურები დალაგებულია წონის კლებადობით, როგორც ამ მოთხოვნის სარეზერვო ჯაჭვი.
- ნაბიჯი, რომლის წონა არის `0` (ან აკლია) არის** არასოდეს დახატული** მაშინ, როცა ნებისმიერ სხვა საფეხურს აქვს წონა > 0 — ის შეიძლება გამოდგეს მხოლოდ შედგენილი ნაბიჯის ჩავარდნის შემდეგ. მხოლოდ მაშინ, როცა** ყველა** წონა არის 0, თუ შერჩევა ხდება ერთგვაროვანი.
- საფეხურები, რომელთა სამიზნეები ყველა მიუწვდომელია — პროვაიდერის ამომრთველი `OPEN`, კავშირის გაგრილება, მოდელის ჩაკეტვა — ამოღებულია გათამაშებიდან სანამ ის მოხდება (`open-sse/services/combo/targetResolution.ts`), ასე რომ, ერთ ჯანსაღ ნაბიჯს შეუძლია დროებით მოიგოს ყველა მოთხოვნა.
- `stickyWeightedLimit` (კომბო კონფიგურაცია, ნაგულისხმევი `1` = გამორთულია) ამაგრებს შედგენილ საფეხურს ამდენი თანმიმდევრული წარმატებისთვის ხელახლა დახატვამდე.

მკაცრი როტაციისთვის გამოიყენეთ `round-robin`; თანაბარი წონა `weighted` ზე იძლევა სტატისტიკურ — და არა მკაცრ — ბალანსს.

### აგენტური მილსადენის რეჟიმი

`pipeline` კომბინაციას მინიმუმ ორი მოდელით შეუძლია აირჩიოს planner/executor მარშრუტიზაცია `config.agenticOrchestration.enabled` ით. პირველი სამიზნე ფლობს დაგეგმვას და საბოლოო პასუხებს; მეორე სამიზნე ასხივებს კლიენტის მშობლიური ინსტრუმენტის ზარებს. OmniRoute ამოიცნობს ხელსაწყოს შედეგის გაგრძელებას მოთხოვნის პროტოკოლიდან, ეკითხება დამგეგმავს, საჭიროა თუ არა სხვა ხელსაწყოს რაუნდი და დინამიურად აქცევს ან შემსრულებელს ან დამგეგმავს კლიენტის წინაშე მყოფ საბოლოო ნაბიჯს.

ინსტრუმენტის შედეგების გაგრძელებისას, OmniRoute ასევე აჩერებს შესრულებას, როდესაც ორი ზედიზედ დასრულებული რაუნდი იმეორებს იგივე ხელსაწყოს გამოძახებას უცვლელი შედეგებით, ან როდესაც ყოველი აშკარად მონიშნული შედეგი ორ რაუნდში ვერ მოხერხდა. შეცვლილი შედეგები იძლევა განმეორებით ზარებს (მაგალითად, კენჭისყრას). მცველი გადაიტვირთება მომხმარებლის ახალი მოთხოვნით, აჯგუფებს პარალელურ ზარებს ერთ რაუნდში და მხარს უჭერს Anthropic, ჩატის დასრულებებს, პასუხებს და Gemini ისტორიებს. დამგეგმავი იღებს მიზეზს და ფლობს საბოლოო პასუხს მაშინაც კი, თუ ის ითხოვს სხვა ხელსაწყოს რაუნდს.

მეორე სამიზნის შემდეგ დამატებით მოდელებს უბრძანებენ შემსრულებლის სარეზერვო ასლებს. წარუმატებელი HTTP პასუხი ან სატრანსპორტო გამონაკლისი მიდის შემდეგ შემსრულებელზე, რომელსაც აქვს იგივე დამგეგმავი გადაწყვეტილება და მშობლიური ხელსაწყოები, მაგრამ ამ შემსრულებლის საკუთარი ნაბიჯის სწრაფი და გადაწყვეტილი კავშირი. პირველი წარმატებული პასუხი ბრუნდება უცვლელი, SSE სტრიმინგის ჩათვლით; წარუმატებლობის წარმატებული ნაკადის დაწყების შემდეგ აქ ხელახლა ცდა შეუძლებელია. თუ ყველა შემსრულებელი ვერ ხერხდება, ბოლო წარუმატებლობა დაბრუნდება. კლიენტი წყვეტს გაგზავნას.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

შემსრულებელს შეუძლია გამოსცეს რამდენიმე დამოუკიდებელი ზარი ერთ პასუხში. დამოკიდებული ზარები განიხილება კლიენტის ხელსაწყოების შედეგის შემდგომ მონაცვლეობით, დამგეგმავი განიხილავს ყველა შედეგს. `maxToolRounds` ნაგულისხმევია `8` და იღებს `1`–`32`; მიღწევის შემდეგ დამგეგმავმა უნდა წარმოადგინოს საუკეთესო ხელმისაწვდომი საბოლოო პასუხი. დამგეგმავის შიდა გადაწყვეტილებები ბუფერულია, ხოლო კლიენტის მიმართ შერჩეული პასუხი ინარჩუნებს ნაკადის თავდაპირველ უპირატესობას.

### `round-robin` წებოვანი პარტია და ანგარიშის გაფართოება

მრგვალი რობინი არის ჯგუფური და არა ერთი მოთხოვნა ნაბიჯზე:

- `stickyRoundRobinLimit` (კომბო კონფიგურაცია, შემდეგ `comboStickyRoundRobinLimit`, შემდეგ `settings.stickyRoundRobinLimit`, ნაგულისხმევი** 3** ) ინარჩუნებს ერთსა და იმავე სამიზნეს ამდენი თანმიმდევრული წარმატებისთვის როტაციამდე. დააყენეთ კომბინირებული გადაფარვა `1` ზე ერთი მოთხოვნის როტაციისთვის. კომბინირებული რედაქტორი აჩვენებს ეფექტურ მნიშვნელობას და რომელი ფენიდან მოვიდა.
- `connectionAwareExpansion` (კომბო კონფიგურაცია, შემდეგ პარამეტრები, ნაგულისხმევი** ყალბი** ) აფართოებს პროვაიდერის დონის თითოეულ საფეხურს თითო ანგარიშის სამიზნეებად როტაციამდე. ჯგუფი-B სტრატეგიები (პრიორიტეტული, შეწონილი, მრგვალი, შემთხვევითი, p2c, ყველაზე ნაკლებად გამოყენებული, ხარჯების ოპტიმიზებული, lkgp, შევსება-პირველი, მკაცრი შემთხვევითი, კონტექსტში ოპტიმიზებული, ქეში-ოპტიმიზებული, კონტექსტური რელე, შერწყმა, მილსადენი) ინარჩუნებს პროვაიდერის დონის ხედს, სანამ ეს ჩართულია. კომბინირებული რედაქტორი აჩვენებს მემკვიდრეობას / ჩართვას / გამორთვას; მემკვიდრეობა იყენებს გლობალურ ნაგულისხმევს (გამორთული).
- მოთხოვნის ქეში ლოკალიზაციის მარშრუტიზაცია (`promptCacheAffinityEnabled`, ნაგულისხმევი** მართალია** ) აწესრიგებს ჩამაგრებულ კავშირებს, რათა შესაბამისი ქეში კლავიშები დარჩეს ერთ ანგარიშზე. ის უპირატესობას ანიჭებს მრგვალ და შეწონილ როტაციას თითოეულ ანგარიშზე დამაგრებულ საფეხურებზე. გამორთეთ ის პარამეტრების → Combo ნაგულისხმევად, თუ მკაცრი როტაცია გჭირდებათ. არ არსებობს თითო კომბინირებული გადაფარვა.

ერთ მოდელზე მრავალ ანგარიშის როტაციისთვის, უპირატესობა მიანიჭეთ** ერთი დინამიური ანგარიშის ნაბიჯი** (ცარიელი `connectionId`, მთელი აუზი) წებოვანი ლიმიტით `1`, არა სამი დამაგრებული `connectionId` s. ჩამაგრებული ნაბიჯები და აფინურობა იშლება იმავე ანგარიშზე მაშინაც კი, როცა RR მრიცხველი წინ მიიწევს.

## შერწყმის სტრატეგია

`fusion` ერთადერთი სტრატეგიაა, რომელიც ერთ სამიზნეს **არ** ირჩევს. ის მოთხოვნას
**პანელის ყველა მოდელს პარალელურად** უგზავნის, შემდეგ კი კონფიგურირებადი **მსაჯი მოდელი**
პანელის ყველა პასუხიდან ერთ საბოლოო პასუხს აყალიბებს. გადმოტანილია საწყისი `decolua/9router`-იდან
(OpenRouter-ის Fusion დიზაინი); იმპლემენტაცია მდებარეობს `open-sse/services/fusion.ts`-ში.

როგორ მუშაობს:

0. **ინსტრუმენტების მქონე მოთხოვნის გვერდის ავლა** — მოთხოვნა, რომელიც შეიცავს არაცარიელ `tools` მასივს და
   რომლის `tool_choice` აშკარად არ არის `"none"`, პანელს მთლიანად გამოტოვებს: ის პირდაპირ
   ერთ მოდელთან (კონფიგურირებულ მსაჯთან ან `panel[0]`-თან) მარშრუტდება, ხოლო `tools`/`tool_choice`
   უცვლელად გადაეცემა. პანელის წევრებს ინსტრუმენტებზე წვდომა არ აქვთ, ხოლო მსაჯის
   სინთეზის დირექტივა ხელს უშლის ინსტრუმენტის გამოძახების გენერირებას, ამიტომ აგენტური/ინსტრუმენტების გამომძახებელი კლიენტები
   სინთეზირებული პროზის ნაცვლად ინსტრუმენტის გამოძახების რეალურ გადაწყვეტილებას იღებენ (#6771).
1. **პარალელური განაწილება** (მხოლოდ ინსტრუმენტების არმქონე მოთხოვნებისთვის) — მოთხოვნა ერთდროულად ეგზავნება პანელის
   ყველა მოდელს, იძულებით არანაკადურ რეჟიმში და ინსტრუმენტების გარეშე (მსაჯს სინთეზისთვის
   სრული ტექსტი სჭირდება).
2. **კვორუმისა და დამატებითი დროის გათვალისწინებით შეგროვება** — როგორც კი `minPanel` რაოდენობის პასუხი მოვა, დაგვიანებული
   პასუხებისთვის მოკლე დამატებითი დროის ტაიმერი იწყება, რის შემდეგაც შერწყმა შეგროვებული მასალით გრძელდება.
   ეს ზღუდავს ყველაზე ნელი მოდელის გავლენას შესრულების მთლიან დროზე, ხოლო ზედა ზღვარს მკაცრი დროის ლიმიტი ადგენს.
3. **მსაჯის სინთეზი** — პანელის პასუხები ანონიმიზებულია (`Source 1`, `Source 2`, … — რათა
   მსაჯმა მოდელის ბრენდის ნაცვლად შინაარსი შეაფასოს) და გადაეცემა მსაჯს, რომელიც აანალიზებს
   კონსენსუსს / წინააღმდეგობებს / ნაწილობრივ დაფარვას / უნიკალურ მიგნებებს / გამორჩენილ ასპექტებს, შემდეგ კი
   წერს **ერთ** ავტორიტეტულ პასუხს. მსაჯის გამოძახება ინარჩუნებს კლიენტის თავდაპირველ
   `stream` პარამეტრსა და ინსტრუმენტებს, ამიტომ ნაკადური რეჟიმი და შემდგომი ინსტრუმენტების გამოყენება კვლავ მუშაობს.
4. **თანდათანობითი დეგრადაცია** — პანელის 0 პასუხი → `503`; ზუსტად 1 გადარჩენილი პასუხი → ეს პასუხი
   პირდაპირ ბრუნდება (შესარწყმელი არაფერია); ერთმოდელიანი პანელი პირდაპირ პასუხობს.

პანელის წევრი ასევე შეიძლება იყოს `combo-ref` ნაბიჯი (`{kind: "combo-ref", comboName: "..."}`), რომელიც
სხვა კომბინაციას მიუთითებს — ის გადაიჭრება, როგორც **პანელის ერთი შავი ყუთის ტიპის ხმა** (სრული რეკურსიული გადამისამართება
მითითებულ კომბინაციაში და არა ამ კომბინაციის საკუთარ სამიზნეებზე პარალელური განაწილება), სიღრმისა და ციკლის იმავე
დაცვით, რომელსაც `combo-ref`-ის მომხმარებელი ყველა სხვა სტრატეგია უკვე იყენებს (#6764).

### კონფიგურაცია

კონფიგურირდება კომბინაციის `config` ბლობში (სქემის მიგრაცია საჭირო არ არის — ის არსებულ
`combos` ცხრილს ხელახლა იყენებს):

| ველი                                     | ტიპი     | ნაგულისხმევი მნიშვნელობა | დანიშნულება                                                                                             |
| :--------------------------------------- | :------- | :----------------------- | :------------------------------------------------------------------------------------------------------ |
| `config.judgeModel`                      | `string` | პანელის პირველი მოდელი   | მოდელი, რომელიც საბოლოო პასუხს ასინთეზებს                                                               |
| `config.fusionTuning.minPanel`           | `number` | `2`                      | დამატებითი დროის ტაიმერის დაწყებამდე საჭირო წარმატებული პასუხები (იზღუდება `[2, panelSize]` დიაპაზონით) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`                   | რამდენ ხანს უნდა დაელოდოს დაგვიანებულ პასუხებს კვორუმის მიღწევის შემდეგ                                 |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`                  | აბსოლუტური ზღვარი, რათა ერთმა გაჭედილმა მოდელმა მოთხოვნა ვერ შეაყოვნოს                                  |

ნაგულისხმევი მნიშვნელობები განსაზღვრულია `FUSION_DEFAULTS`-ში (`open-sse/services/fusion.ts`).

## ვირტუალური Auto-Combo ქარხანა

Auto Combo ძრავას წინასწარ განსაზღვრული კომბოები არ სჭირდება. ამის ნაცვლად, `open-sse/services/autoCombo/virtualFactory.ts` კანდიდატებს დინამიკურად ქმნის:

1. იღებს `getProviderConnections({ isActive: true })`-ს (ყველა ჩართული კავშირი)
2. ფილტრავს და ტოვებს მოქმედი ავტორიზაციის მონაცემების მქონე კავშირებს (API გასაღები ან `hasUsableOAuthToken()`-ის მეშვეობით შემოწმებული, ვადაგაუსვლელი OAuth ტოკენი)
3. მოდელების ხელმისაწვდომობისა და ფასების დასადგენად ადარებს `getProviderRegistry()`-ს
4. თითოეული `(provider, model, connection)` სამეულისთვის ქმნის `VirtualAutoComboCandidate`-ს
5. მოთხოვნის გადაგზავნის სამიზნედ ირჩევს `connection.defaultModel`-ს (ან რეესტრის პირველ მოდელს)
6. თითოეულ კანდიდატს აფასებს 16-ფაქტორიანი `scorePool()`-ისა და ვარიანტის წონების ნაკრების გამოყენებით
7. `handleComboChat()`-ისთვის აბრუნებს მეხსიერებაში შექმნილ საბოლოო `AutoComboConfig`-ს — ის არასოდეს ინახება DB-ში

ეს ნიშნავს, რომ **ახალი პროვაიდერის დამატება, რომელზეც `auto/*` ჩართულია, კანდიდატების ერთობლიობას ავტომატურად აფართოებს** — კომბოს ხელით რედაქტირება საჭირო არ არის. ვირტუალური კომბო ყოველი მოთხოვნისთვის თავიდან იქმნება, ამიტომ ახლად დამატებული ან ახლახან გამართულად ამუშავებული კავშირები დაუყოვნებლივ გამოიყენება.

## თვითაღდგენა

- **დროებითი გამორიცხვა**: ქულა < 0.2 → გამოირიცხება 5 წუთით (პროგრესული დაყოვნება, მაქს. 30 წუთი)
- **Circuit breaker-ის მდგომარეობის გათვალისწინება**: OPEN → ავტომატურად გამოირიცხება; HALF_OPEN → საცდელი მოთხოვნები
- **ინციდენტის რეჟიმი**: >50% OPEN → კვლევის გამორთვა, სტაბილურობის მაქსიმიზაცია
- **აღდგენა მოცდის პერიოდის შემდეგ**: გამორიცხვის დასრულების შემდეგ პირველი მოთხოვნა არის შემცირებული timeout-ის მქონე „საცდელი“ მოთხოვნა

## Bandit კვლევა

მოთხოვნების 5% (კონფიგურირებადია) კვლევის მიზნით შემთხვევით პროვაიდერებთან იგზავნება. ინციდენტის რეჟიმში გამორთულია.

## API

**გამოყოფილი `POST /api/combos/auto` endpoint არ არსებობს** — Auto-Combo გამოიყენება ორი გზით:

1. **ნულოვანი კონფიგურაცია (რეკომენდებული):** გაგზავნეთ ჩატის დასრულების ნებისმიერი მოთხოვნა `model: "auto"` ან `model: "auto/<variant>"` პარამეტრით. ვირტუალური factory თითოეული მოთხოვნისთვის ქმნის combo-ს — მუდმივი შენახვა და API-ის გამოძახებები საჭირო არ არის.

2. **შენახული combo `strategy: "auto"` პარამეტრით:** შექმენით ჩვეულებრივი combo `POST /api/combos`-ის მეშვეობით და მიუთითეთ `strategy: "auto"`, ასევე `config.auto.weights` / `config.auto.candidatePool`. გამოიყენება იგივე შეფასების ძრავა; combo ინახება `combos`-ში და მისი ხელახლა გამოყენება ID-ის მიხედვით არის შესაძლებელი.

აღმოჩენისთვის, `GET /api/combos/auto` ჩამოთვლის ყველა ვარიანტს მისი განსაზღვრული კანდიდატების ჯგუფით, ასევე `context_length` / `max_output_tokens` მნიშვნელობებით — კანდიდატების ჯგუფის ფანჯრებს შორის მაქსიმალური მნიშვნელობით. კლიენტებმა (მაგ., opencode plugin-მა) `0`-ის ნაცვლად ეს მნიშვნელობები უნდა გამოაცხადონ: ნულოვანი კონტექსტი სრულად თიშავს opencode-ის ავტომატურ შეკუმშვას, რის გამოც სესიები იზრდება მანამ, სანამ gateway-ის ისტორიის გასუფთავება კონტექსტს არ გაანადგურებს. მაქსიმალური მნიშვნელობის გამოცხადება უსაფრთხოა, რადგან auto-combo-ს კონტექსტის წინასწარი ფილტრი ზედმეტად დიდ მოთხოვნებს დიდი ფანჯრის მქონე კანდიდატებთან გადაამისამართებს.

```bash
# გამოყენება ნულოვანი კონფიგურაციით (combo-ს შექმნის გარეშე)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# შენახული auto combo ჩვეულებრივი combos endpoint-ის მეშვეობით
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### ავტომატური როუტერის სტრატეგიები

შენახულ `strategy: "auto"` combo-ებს შეუძლიათ `config.routerStrategy` (ან ძველი
`config.auto.routerStrategy`) დააყენონ ერთ-ერთ შემდეგ მნიშვნელობაზე:

- `rules` — ნაგულისხმევი შეწონილი შეფასება
- `score` — ირჩევს ყველაზე მაღალი კონფიგურირებული შეწონილი შეფასების მქონე ვარიანტს. ზუსტი თანაბრობის შემთხვევაში შენარჩუნებულია კანდიდატების კონფიგურირებული
  თანმიმდევრობა; არსებული `explorationRate` ნიმუშს იღებს სრული რანჟირებული ჯგუფიდან.
- `cost` / `eco` — ყველაზე იაფი გამართული პროვაიდერი
- `latency` / `fast` — ყველაზე დაბალი p95 დაყოვნება საიმედოობის ჯარიმის გათვალისწინებით
- `sla-aware` / `sla` — უპირატესობას ანიჭებს კანდიდატებს, რომლებიც აკმაყოფილებენ p95 დაყოვნების, შეცდომების სიხშირისა და არასავალდებულო
  ღირებულების SLO-ებს
- `lkgp` — პირველ რიგში ბოლო ცნობილი გამართული პროვაიდერი
- `nadir` — ეკითხება [Nadir](https://getnadir.com)-ის გადაწყვეტილების API-ს, ჯგუფში შემავალი რომელი მოდელი სჭირდება
  მოთხოვნას; საჭიროებს ცხადად ჩართვას და შეცდომის შემთხვევაში გადადის `rules`-ზე

### როუტერის სტრატეგიები დეტალურად

auto-combo-ს ძრავა გთავაზობთ 7 ჩანაცვლებად **RouterStrategy** იმპლემენტაციას, რომელთა
შეცვლაც შეგიძლიათ `config.routerStrategy`-ის (ან ძველი `config.auto.routerStrategy`-ის) მეშვეობით.
თითოეული სტრატეგია კანდიდატების ჯგუფიდან ერთ პროვაიდერს ირჩევს მოცემული `RoutingContext`-ის
(დავალების ტიპი, ხელსაწყოს/ხედვის მინიშნებები, ტოკენების სავარაუდო რაოდენობა, არასავალდებულო SLA პოლიტიკა, არასავალდებულო
ბოლო ცნობილი გამართული პროვაიდერი) საფუძველზე.

#### 1. `rules` (ნაგულისხმევი) — 16-ფაქტორიანი შეწონილი შეფასება

არსებულ შეფასების ძრავას გარს აკრავს. ფილტრავს `OPEN` circuit-breaker-ის მდგომარეობის მქონე
კანდიდატებს, შემდეგ კი მიმდინარე დავალების ტიპითა და `getTaskFitness()`-ით უშვებს `scorePool()`-ს
და ირჩევს უმაღლესი შეფასების მქონე პროვაიდერს.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**როდის გამოიყენოთ**: ნაგულისხმევად. გამოიყენეთ, როცა ყველა სიგნალს შორის დაბალანსებული კომპრომისი გსურთ.

**ფსევდონიმი**: `rules` (ფსევდონიმის გარეშე)

---

#### 2. `cost` / `eco` — ყველაზე იაფი გამართული პროვაიდერი

კანდიდატების ჯგუფს `costPer1MTokens`-ის მიხედვით (ზრდადობით) ახარისხებს და ყველაზე იაფს ირჩევს.
ჯერ ფილტრავს `OPEN` კანდიდატებს.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**როდის გამოიყენოთ**: ღირებულებისადმი მგრძნობიარე დატვირთვები, პაკეტური დამუშავება ან ფონური დავალებები.

**ფსევდონიმები**: `cost`, `eco`

---

#### 3. `latency` / `fast` — ყველაზე დაბალი p95 დაყოვნება საიმედოობის ჯარიმის გათვალისწინებით

ახარისხებს `p95LatencyMs + (errorRate * 1000)`-ის მიხედვით. შეცდომების სიხშირის ჯარიმა უზრუნველყოფს,
რომ არასაიმედო პროვაიდერები უფრო დაბალ პოზიციაზე მოხვდნენ მაშინაც კი, თუ მათი ნომინალური დაყოვნება დაბალია.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**როდის გამოიყენოთ**: დაყოვნებისადმი მგრძნობიარე დატვირთვები, როგორიცაა რეალურ დროში ჩატი, ავტომატური შევსება ან
ინტერაქტიული პროგრამირების ასისტენტები.

**ფსევდონიმები**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — დაყოვნების/შეცდომების/ღირებულების SLO-სთან შესაბამისობა

თითოეულ კანდიდატს აფასებს იმის მიხედვით, თუ რამდენად კარგად აკმაყოფილებს ის კონფიგურირებულ SLO პოლიტიკას:

| ფაქტორი           | წონა | ფორმულა                                                                   |
| ----------------- | ---- | ------------------------------------------------------------------------- |
| დაყოვნების ქულა   | 35%  | `threshold / max(value, ε)`                                               |
| შეცდომების ქულა   | 35%  | `threshold / max(value, ε)`                                               |
| გამართულობის ქულა | 15%  | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)                         |
| ღირებულების ქულა  | 10%  | `threshold / max(value, ε)` ან უკუპროპორციულად ნორმალიზებული              |
| სტაბილურობის ქულა | 5%   | დაყოვნების სტანდარტული გადახრის უკუპროპორციულად ნორმალიზებული მნიშვნელობა |

როდესაც `hardConstraints: true`, კანდიდატები პირველ რიგში **დარღვევის ქულის**
მიხედვით ლაგდება (რამდენად აჭარბებენ ისინი რომელიმე SLO-ს), შემდეგ კი — კომპოზიტური ქულის მიხედვით. წინააღმდეგ შემთხვევაში გამოიყენება მხოლოდ
კომპოზიტური ქულა.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... თითოეულ კანდიდატს აფასებს პოლიტიკის მიხედვით: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }

}
```

**როდის გამოვიყენოთ**: საწარმოო დატვირთვებისთვის, რომლებსაც დაყოვნების, შეცდომების სიხშირის ან ღირებულების მკაცრი ბიუჯეტები აქვთ.

#### 5. `lkgp` — ბოლოს ცნობილი გამართული პროვაიდერი პირველ რიგში

თავდაპირველად ცდილობს **ბოლოს ცნობილ გამართულ პროვაიდერს** (თუ მითითებულია), შემდეგ კი
გადადის `rules` სტრატეგიაზე. გამოსადეგია სესიის მიბმისთვის — საუბრის
შემდგომ მოთხოვნებს იგივე პროვაიდერი ამუშავებს.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // სარეზერვო ვარიანტად rules სტრატეგიის გამოყენება
    return getStrategy("rules").select(pool, context);
  }
}
```

**როდის გამოვიყენოთ**: მრავალეტაპიანი საუბრებისთვის, როდესაც გსურთ, რომ შემდგომი
მოთხოვნები იმავე პროვაიდერმა დაამუშაოს (მაგ., კეშირებისთვის, კონტექსტის უწყვეტობისთვის ან ფასების თანმიმდევრულობისთვის).

**ფსევდონიმი**: `lkgp` (ფსევდონიმი არ აქვს)

#### 6. `nadir` — მოთხოვნის შინაარსზე დაფუძნებული მოდელის არჩევა Nadir-ის მეშვეობით

ზემოთ ჩამოთვლილი თითოეული სტრატეგია კანდიდატებს საკუთარი ტელემეტრიის მიხედვით ალაგებს; არცერთი მათგანი
არ კითხულობს მოთხოვნას. `nadir` აგზავნის მომხმარებლის ბოლო შეტყობინებას და პულში არსებული მოდელების იდენტიფიკატორებს
[Nadir](https://getnadir.com)-ის გადაწყვეტილების API-ში (`POST /v1/bucket`) და მარშრუტს მიმართავს იმ მოდელზე,
რომელსაც Nadir მოცემული სიიდან აირჩევს (`simple` → მოთხოვნის დამუშავების უნარის მქონე ყველაზე იაფი მოდელი, `complex` → მოწინავე
მოდელი). ამ მოდელის მომსახურე კავშირს კვლავ `rules` ირჩევს, ამიტომ კვოტა,
გამართულობა და ღირებულება კვლავ განსაზღვრავს, რომელი ანგარიში იქნება გამოყენებული.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` და `OMNIROUTE_NADIR_BASE_URL` გარემოს ცვლადები ამ ორი
სტრიქონის სარეზერვო მნიშვნელობებია. `baseUrl` საჭიროა მხოლოდ დამოუკიდებლად განთავსებული Nadir-ისთვის (ბოლოში დართული `/v1` დასაშვებია).
გასაღების გარეშე შესრულებული გამოძახებები ხვდება Nadir-ის ანონიმურ დონეზე, სადაც მოთხოვნების სიხშირე თითოეული IP-ის მიხედვით იზღუდება. გასაღების გამოყენებისას
([შექმენით გასაღები](https://app.getnadir.com/dashboard/api-keys)) თითოეული გადაწყვეტილება
თქვენს Nadir-ის მართვის პანელში აღირიცხება. სრული დაყენებისა და შემოწმების ინსტრუქცია:
[getnadir.com/docs/gateway-omniroute](https://getnadir.com/docs/gateway-omniroute/).

რა იგზავნება სისტემის გარეთ: მომხმარებლის ბოლო შეტყობინების ტექსტი (პირველი 16 ათასი სიმბოლო), კანდიდატი
მოდელების იდენტიფიკატორები და `source: "omniroute"` არხის ტეგი. სისტემური მოთხოვნა, ისტორია, ხელსაწყოები ან
სათაურები არ იგზავნება.

შეცდომის შემთხვევაში სისტემა მუშაობას აგრძელებს: დროის ამოწურვა (ნაგულისხმევად 2000 ms), არა-2xx პასუხი, მიუწვდომელი
ჰოსტი, არასწორად ფორმირებული პასუხი ან პულის მიღმა არსებული არჩევანი იწვევს `rules`
გადაწყვეტილების გამოყენებას, ხოლო მიზეზს წინ ემატება `NadirStrategy: fallback (…)`. წარუმატებელი გამოძახების შემდეგ
სტრატეგია ქსელურ მოთხოვნებს 30 s-ის განმავლობაში გამოტოვებს, ამიტომ შეფერხება 30 s-ში ერთხელ მხოლოდ ერთ ტაიმაუტს იწვევს და არა
თითოეულ მოთხოვნაზე ერთს. მარშრუტიზაციის მოვლენები `strategy: "nadir"`-ს მხოლოდ მაშინ აფიქსირებს,
როდესაც არჩევანი რეალურად Nadir-მა გააკეთა.

**როდის გამოვიყენოთ**: შერეული სირთულის ტრაფიკისთვის პულში, რომელიც მოდელების რამდენიმე დონეს მოიცავს (მცირე, საშუალო
და მოწინავე მოდელი), როდესაც გსურთ, შეამციროთ ყოველთვის მოწინავე მოდელის გამოყენების ხარჯი.

**ფსევდონიმი**: `nadir` (ფსევდონიმი არ აქვს)

### მარშრუტიზატორის მორგებული სტრატეგიები

  registerStrategy,
  type RouterStrategy,

      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());

## Auto ვარიანტების შეჯამება

საბაზისო `auto`-ს (ნაგულისხმევი) და `autoPrefix.ts`-ში გამოცხადებული 6 `AutoVariant` მნიშვნელობის ჩათვლით, ხელმისაწვდომია **7 გამოძახებადი მოდელის ID**:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` თავად 6 მნიშვნელობას ჩამოთვლის; მე-7 ვარიანტია „ვარიანტის გარეშე“ — საბაზისო `auto` — რომელსაც `parseAutoPrefix()` ამუშავებს როგორც `variant: undefined`.)

## როგორ ერგება დონეები Auto-Combo-ს

16-ფაქტორიანი შეფასების ფუნქცია (`open-sse/services/autoCombo/scoring.ts`) დონისადმი
კუთვნილებას ორ სიგნალად განიხილავს: `tierPriority` (0.0476) და `tierAffinity` (0.0476). `DEFAULT_WEIGHTS`-ის
სრული ნაკრებისთვის იხილეთ ზემოთ მოცემული კანონიკური [შეფასების ფაქტორების ცხრილი](#how-it-works-persisted-auto-combos) —
თითოეული პაკეტისთვის განსაზღვრული ჩანაცვლებები (ship-fast/cost-saver/quality-first/
offline-friendly) ჩამოთვლილია ცხრილში „წონების პროფილები თითოეული პაკეტისთვის“.

მხოლოდ დონე **არ** აიძულებს სისტემას, დონე 1 პირველ ადგილზე დააყენოს — თუ დონე 1-ის დაყოვნება მაღალია ან
ღირებულებისა და ხარისხის თანაფარდობა არაოპტიმალურია, დონე 2 იმარჯვებს. დონეების თანმიმდევრობის იძულებით დასაცავად გამოიყენეთ კომბინაციის
სტრატეგია `priority` და პროვაიდერები დონეების მიხედვით დაალაგეთ.

დონე 1-ისთვის (გამოწერა) მკაფიო უპირატესობის მისანიჭებლად გაზარდეთ `tierPriority`-ის წონა:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

დონეების განმარტებებისა და პროვაიდერების კლასიფიკაციისთვის იხილეთ [`docs/guides/TIERS.md`](../guides/TIERS.md).
