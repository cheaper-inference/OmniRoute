Web Cookie პროვაიდერები საშუალებას აძლევს OmniRoute-ს, API გასაღების ნაცვლად, AI სერვისი თქვენი არსებული ბრაუზერის სესიის მეშვეობით გამოიყენოს. ისინი გამოსადეგია, როდესაც სერვისზე უკვე გაქვთ წვდომა მისი ვებსაიტის მეშვეობით და გსურთ, რომ OmniRoute-მა იგივე ავთენტიფიცირებული სესია გამოიყენოს.

API გასაღებზე დაფუძნებული პროვაიდერებისგან განსხვავებით, Web Cookie პროვაიდერები ავთენტიფიკაციისთვის იმ ავტორიზაციის მონაცემებს იყენებენ, რომლებსაც თქვენი ბრაუზერი ვებსაიტს უგზავნის.

# დაწყებამდე

> **მნიშვნელოვანია:** ავტორიზაციის მონაცემები ყოველთვის დააკოპირეთ **აქტიური ქსელური მოთხოვნიდან** და **არა** თქვენი ბრაუზერის cookie-ების საცავიდან.

ავთენტიფიკაციის მრავალი პრობლემა cookie-ების არასწორი ადგილიდან კოპირებით არის გამოწვეული.

## არ დააკოპიროთ Cookie Storage-იდან

ბრაუზერების უმეტესობა შენახულ cookie-ებს შემდეგი გზით აჩვენებს:

```
DevTools
→ Application (ან Storage)
→ Cookies
```

მიუხედავად იმისა, რომ ეს cookie-ები შეიძლება სწორად გამოიყურებოდეს, ისინი შესაძლოა იყოს:

- მოძველებული
- არასრული
- ისეთი cookie-ების გარეშე, რომლებიც მხოლოდ ავთენტიფიცირებული მოთხოვნებისას იგზავნება

ამ მნიშვნელობების გამოყენებამ შესაძლოა ავთენტიფიკაციის შეცდომები გამოიწვიოს, მაშინაც კი, თუ ისინი მართებული ჩანს.

## დააკოპირეთ აქტიური მოთხოვნიდან

ამის ნაცვლად, გამოიყენეთ წარმატებული მოთხოვნის cookie-ები:

```
DevTools
→ Network
→ განაახლეთ გვერდი
→ გახსენით ჩატის ან საუბრის მოთხოვნა
→ Request Headers
→ Cookie
```

`Cookie` მოთხოვნის სათაური შეიცავს ზუსტად იმ ავთენტიფიკაციის ინფორმაციას, რომელიც თქვენმა ბრაუზერმა წარმატებით გამოიყენა.

Web Cookie პროვაიდერების უმეტესობისთვის სწორედ ეს მნიშვნელობა უნდა ჩასვათ OmniRoute-ში.

# ზოგადი კონფიგურაცია

კონფიგურაციის პროცესი Web Cookie პროვაიდერების უმეტესობისთვის ერთნაირია.

1. შედით პროვაიდერის ვებსაიტზე.
2. გახსენით ბრაუზერის Developer Tools.
3. გახსენით **Network** ჩანართი.
4. განაახლეთ გვერდი.
5. გახსენით ავთენტიფიცირებული ჩატის ან საუბრის მოთხოვნა.
6. დააკოპირეთ საჭირო ავტორიზაციის მონაცემები.
7. გახსენით OmniRoute.
8. გადადით **Providers → Add Provider**-ზე.
9. აირჩიეთ თქვენი Web Cookie პროვაიდერი.
10. ჩასვით ავტორიზაციის მონაცემები.
11. დააწკაპუნეთ **Test Connection**-ზე.
12. შეინახეთ პროვაიდერი.

ზუსტად რომელი ავტორიზაციის მონაცემებია საჭირო, პროვაიდერზეა დამოკიდებული.

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) არის მომხმარებლებისთვის განკუთვნილი უფასო ჩატის პლატფორმა, რომელიც რეგისტრაციას არ საჭიროებს — სესია პირველი ვიზიტისას ანონიმურად იქმნება და ინახება სამი cookie-ს მეშვეობით: `uid`, `si_usr_id` და `si_ses_id`. OmniRoute იმავე `/api/dispatch` საბოლოო წერტილს ერთი მოდელის ID-ის (`notrack-c`, ფსევდონიმი `ntw`) მეშვეობით პროქსირებს.

### დაკავშირების ნაბიჯები

1. ბრაუზერში გახსენით [notrack.ai](https://notrack.ai) და დაელოდეთ ანონიმური სესიის cookie-ს დაყენებას.
2. გახსენით **DevTools → Network**, განაახლეთ გვერდი და დააწკაპუნეთ ნებისმიერ `/api` მოთხოვნაზე.
3. განყოფილებაში **Request Headers** დააკოპირეთ `Cookie` სათაურის სრული მნიშვნელობა.
4. OmniRoute-ში გადადით **Providers → Add Provider → NoTrack Web (Free)**.
5. ჩასვით cookie-ს სტრიქონი `apiKey` ველში და დააჭირეთ **Save**-ს.

OmniRoute ჩასმული სტრიქონიდან ამოიღებს `uid`, `si_usr_id` და `si_ses_id` მნიშვნელობებს და ხელახლა შექმნის სუფთა `Cookie` სათაურს, რომელიც მხოლოდ ამ წყვილებს შეიცავს — ხოლო არსებობის შემთხვევაში, ასევე `nt_session`-ს (სისტემაში შესული ანგარიშებისთვის დაყენებულ `ntk_…` ტოკენს). თუ ამ სამიდან რომელიმე აკლია, ჩასმული დაუმუშავებელი სტრიქონი უცვლელად გადაიგზავნება, რათა ოპერატორებმა ალტერნატიული ფორმატების გამოცდა შეძლონ.

### მოდელის ID-ები

| მოდელის ID  | საჩვენებელი სახელი | შენიშვნები                                                          |
| ----------- | ------------------ | ------------------------------------------------------------------- |
| `notrack-c` | NoTrack C          | ნაგულისხმევი — ზედა დონის გადამისამართების მოდელი `C`.              |
| `C`         | NoTrack C          | `notrack-c`-ის ფსევდონიმი (ზედა დონის გადამისამართების ნედლი კოდი). |
| `notrack`   | NoTrack C          | `notrack-c`-ის ფსევდონიმი.                                          |
| `ntw`       | NoTrack C          | `notrack-c`-ის მოკლე ფსევდონიმი.                                    |

ოთხივე მოდელის ID შეესაბამება ზედა დონის გადამისამართების ერთსა და იმავე მოდელს (`C`).

### მოთხოვნის პარამეტრები

შემსრულებელი მოთხოვნის სხეულში იღებს შემდეგ არასავალდებულო ველებს:

| სხეულის ველი          | ნაგულისხმევი | დანიშნულება                                                                      |
| --------------------- | ------------ | -------------------------------------------------------------------------------- |
| `notrack_mode`        | `usual`      | გადამისამართების რეჟიმი (თავისუფალი ფორმის სტრიქონი; ზედა დონე იღებს `usual`, …) |
| `notrack_max_turns`   | `6`          | შიდა ციკლების რაოდენობა, რომლებიც ზედა დონეს პასუხამდე შეუძლია შეასრულოს.        |
| `notrack_chat_id`     | `null`       | არსებული ზედა დონის ჩატის გაგრძელება (ახალი ჩატისთვის გამოტოვეთ).                |
| `notrack_attachments` | `[]`         | ზედა დონის დანართების აღმწერების უცვლელად გადასაცემი მასივი.                     |
| `notrack_regenerate`  | `false`      | წინა ციკლისთვის პასუხის ხელახლა გენერირების მოთხოვნისთვის მიუთითეთ `true`.       |

### შესაძლებლობები

- ჩატის დასრულებები **ნაკადურ და არანაკადურ რეჟიმებში**.
- **ხელსაწყოების გამოძახება** — მოთხოვნაში მიუთითეთ `tools: [...]`; შემსრულებელი მათ ხელსაწყოს გამოძახების გარსის კონტრაქტის ფორმატში სერიალიზებს და მოდელის პასუხებს კვლავ OpenAI-ის `tool_calls` ფორმატში გარდაქმნის.
- **`response_format`** — მხარდაჭერილია `json_object` და `json_schema`. შემსრულებელი მოდელის პასუხიდან პირველ JSON ობიექტს ამოიღებს და დაბრუნებამდე სტრიქონად გარდაქმნის.
- **მსჯელობის მინიშნება** — როდესაც ზედა დონე `thinking` მოვლენას აგზავნის, შემსრულებელი `reasoning` დელტას გამოსცემს.

### შეზღუდვები

- ზედა დონე ანონიმური გამოყენების კვოტებს აწესებს — მათი გადაჭარბებისას შემსრულებელი აბრუნებს 429 სტატუსს და გასაგებ შეტყობინებას.
- მოდელის ყველა ID ერთსა და იმავე ზედა დონის გადამისამართების მოდელს შეესაბამება; ცალკეული მოდელის არჩევის შესაძლებლობა არ არსებობს.
- შემსრულებელი არ იძახებს ზედა დონის `/api/chats` საბოლოო წერტილს, ამიტომ ჩატის ისტორია / სესიები ავტომატურად არ იმართება. არსებული ზედა დონის ჩატის გასაგრძელებლად გამოიყენეთ `notrack_chat_id`.

# რისი გაკეთება შეუძლიათ და არ შეუძლიათ Web Cookie პროვაიდერებს

Web Cookie პროვაიდერები ვებსაიტის ჩატის ინტერფეისს ხელახლა იყენებენ. ისინი ოფიციალური API-ების იმავე შესაძლებლობებს **არ** უზრუნველყოფენ.

## მხარდაჭერილია

- ავთენტიფიკაცია ბრაუზერის არსებული სესიის გამოყენებით
- თქვენი ანგარიშისთვის ხელმისაწვდომ მოდელებზე წვდომა
- ჩატის პასუხების ნაკადის რეჟიმში მიღება
- API გასაღები საჭირო არ არის

## არ არის მხარდაჭერილი

- ფუნქციების გამოძახება
- ხელსაწყოების გამოძახება
- ფაილების ავტომატური რედაქტირება
- აგენტური IDE სამუშაო პროცესები
- მხოლოდ API-ისთვის განკუთვნილი შესაძლებლობები

ეს მოსალოდნელი ქცევაა და **არ არის** შეცდომა.

თუ გჭირდებათ ხელსაწყოების შესრულება, ფაილების ავტომატური რედაქტირება ან სხვა აგენტური სამუშაო პროცესები, Web Cookie პროვაიდერის ნაცვლად გამოიყენეთ **API გასაღების პროვაიდერი**.

# ვალიდაციის შეზღუდვა

წარმატებული **კავშირის შემოწმება** ან cookie-ის ვალიდაცია მხოლოდ იმას ადასტურებს, რომ მიწოდებული ავტორიზაციის მონაცემები, სავარაუდოდ, მოსალოდნელ ფორმატშია.

Issue #7857-ის გადაწყვეტამდე წარმატებული ვალიდაცია **არ იძლევა გარანტიას**, რომ პროვაიდერი წარმატებით გაივლის ავთენტიფიკაციას.

თუ ავთენტიფიკაცია კვლავ ვერ ხერხდება, დარწმუნდით, რომ ავტორიზაციის მონაცემები დააკოპირეთ აქტიური ქსელური მოთხოვნიდან და არა ბრაუზერის cookie-ების საცავიდან.

# პრობლემების აღმოფხვრა

## ავთენტიფიკაცია ვერ ხერხდება

დარწმუნდით, რომ ავტორიზაციის მონაცემები დააკოპირეთ აქედან:

```
Network
→ Request Headers
→ Cookie
```

და **არა** აქედან:

```
Application
→ Cookies
```

## Cookie მუშაობს ბრაუზერში, მაგრამ არა OmniRoute-ში

ზოგიერთი პროვაიდერის cookie-ები იგზავნება მხოლოდ ავთენტიფიცირებული მოთხოვნების დროს.

საუბრის წარმატებით გახსნის შემდეგ ხელახლა დააკოპირეთ ავტორიზაციის მონაცემები ახალი ქსელური მოთხოვნიდან.

---

## სესიის ვადა ამოიწურა

Web Cookie პროვაიდერები იყენებენ ბრაუზერის თქვენს არსებულ სესიას.

თუ ბრაუზერის სესიის ვადა ამოიწურება ან ანგარიშიდან გამოხვალთ, ავტორიზაციის მონაცემების ახალი ნაკრები უნდა დააკოპიროთ. მხარდაჭერილი ვებ-პროვაიდერებისთვის cookie-ების განახლების ავტომატიზაციის შესახებ იხილეთ თანმხლები ხელსაწყო [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md).

Issue #7857-ის გადაწყვეტამდე ვალიდაციის წარმატებით გავლა არ იძლევა გარანტიას, რომ ავთენტიფიკაციის მოთხოვნა წარმატებით შესრულდება.

## ChatGPT Web ვერ მუშაობს შეცდომით "Unsupported ChatGPT integrity dependency"

```
[502] ChatGPT Web first-party bridge module failed to load:
pageerror: Unsupported ChatGPT integrity dependency: DD
```

ავტორიზაციის მონაცემები გამართულია — ეს შეცდომა bridge-იდან მოდის და არა სესიიდან. chatgpt.com თითოეული განთავსებისთვის საკუთარ მოდულის ID-ებს ანიჭებს, ხოლო bridge ადრე მის მიერ შექმნილი Sentinel დამხმარის ID-ს აფიქსირებდა, ამიტომ chatgpt.com-ის ხელახალი აგება, რომელმაც დამხმარეს სახელი შეუცვალა, ყველა მიმართვას არღვევდა, მიუხედავად იმისა, რომ cookie მოქმედი რჩებოდა. კავშირის ხელახლა ავტორიზაცია ამას ვერ გამოასწორებს.

ვერსიები, რომლებიც მოდულს გვერდის საკუთარი runtime-ის მეშვეობით პოულობენ, არცერთ ID-ს არ აფიქსირებენ და ეს პრობლემა არ ეხებათ. თუ ამ შეცდომას ხედავთ, განაახლეთ OmniRoute და ხელახლა გაუშვით კავშირის შემოწმება.
